## Clarifications

### Session 2026-08-25

- Q: Convert the HTML to PPTX with a script, or have an agent author PptxGenJS? → A: **Agent
  authors PptxGenJS.** HTML→PPTX conversion is lossy by construction (CSS gradients on text, blend
  modes, and reflow have no PPTX equivalent) and faithfully reproduces any bug in the source CSS.
  An agent reading the finished deck transcribes *intent* — e.g. drawing a bar chart from the
  underlying percentages rather than from bar heights that collapsed in the browser. No
  deterministic converter exists in the repo; `pptx-generator/SKILL.md` is a catalogue stub and
  `pptx-html-fidelity-audit/scripts/` is audit-only.
- Q: Can `ppt_v2` reuse `deliverable.strategy: ppt`? → A: No. That strategy resolves to
  `ctx.last_streamed` — the **last** step's output — so a 4th step emitting JavaScript would
  replace the deck. `ppt_v2` declares `single_file` / `presentation.html`, a sandbox readback that
  is immune to step order.
- Q: May `agents/workflows/ppt/workflow.yaml` be modified? → A: **No.** `ppt_v2` is a separate
  workflow; the existing `ppt` must not break.
- Q: Where does the `.pptx` live, given the platform cannot store binary? → A: It is generated
  **during the run** by a tool, into the run sandbox. For download, phase 1 regenerates it from the
  stored PptxGenJS source (text, so it persists in `agent_outputs`) via the existing
  `POST /api/runs/export-pptx`. Phase 2's Sandbox tab serves the file itself.

## 1. Problem

The `ppt` workflow is named for PowerPoint and its deliverable is called `presentation.pptx`, but
**no `.pptx` is ever produced**. The run delivers an HTML deck. Every other piece of the export
chain already exists and works:

- `POST /api/runs/export-pptx` — built, with request caps and filename sanitisation
- `generate_pptx_from_code()` — a hardened Node subprocess (scrubbed env, POSIX rlimits,
  semaphore, wall clock, size cap). **Verified working: produced a valid 45,474-byte, 1-slide
  `.pptx` on demand.**
- A **Download PPTX** button, already wired in `FilesTab`, `PreviewPanel` and `PPTPreview`
- `pptxgenjs` 3.12, installed and resolving

The single missing link is that **nothing emits PptxGenJS source**. The endpoint's Strategy 1 looks
up agent id `ppt-code-generator`, which is not in the pipeline; its Strategy 2 scans the deck HTML
for a `generatePresentation()` function, which the deck does not contain. Both find nothing, so the
download fails and the user gets HTML only.

## 2. What it does

**One run of `ppt_v2` produces two artifacts: the HTML deck it previews, and a real, editable
`.pptx` — generated by the workflow itself, not as a download-time side effect.**

A fourth step reads the finished deck, authors PptxGenJS, and **calls a tool** that builds the file
and reports back. The same step then runs a deterministic geometry audit on the result and revises
until it is clean. `ppt` is untouched.

## 3. User Scenarios & Testing *(mandatory)*

### Primary user story

A user picks **Pitch an idea (v2)**, describes their deck, and answers the clarify questions. The
run produces a deck they can preview in the browser, download as `.html`, **and** download as a
`.pptx` that opens in PowerPoint with editable text boxes — not a picture of a slide.

### Acceptance scenarios

1. **Both artifacts exist.** Given a completed `ppt_v2` run, then the deliverable is a valid HTML
   deck AND `presentation.pptx` exists in the run sandbox.
2. **The pptx is real.** Given that file, when opened with `python-pptx`, then it parses, reports
   the expected slide count, and its text frames carry the deck's actual text.
3. **The HTML is unharmed.** Given a `ppt_v2` run, then the preview renders the deck exactly as
   `ppt` does — the added step must not degrade the existing surface.
4. **A bad generation fails loudly, in-run.** Given a step-4 output that does not compile, then the
   tool returns the compile error and the agent revises; the run does not silently ship no pptx.
5. **Geometry is gated.** Given a generated pptx with a shape crossing the footer rail or the
   canvas bound, then the audit tool reports the violation and the agent revises.
6. **`ppt` is unchanged.** Given the same brief on `ppt`, then its compiled plan and its output are
   byte-identical to before this feature.

### Edge cases

- **Step 4 fails entirely** → the composer's `presentation.html` is still on disk, so `single_file`
  still resolves a valid deck. The user loses the pptx, never the deck.
- **The sandbox is TTL-swept** before download → the pptx is regenerated from the stored PptxGenJS
  source, which is text and persists in `agent_outputs`.
- **`node` is not on the child PATH** → currently fatal and silent-ish; see FR-008.

## 4. Requirements *(mandatory)*

### Functional Requirements

- **FR-001** — `ppt_v2` MUST be a new workflow. `agents/workflows/ppt/workflow.yaml` and the three
  existing ppt agents MUST NOT be modified.
- **FR-002** — `ppt_v2` MUST declare `deliverable: {strategy: single_file, name: presentation.html}`
  so the HTML deliverable is immune to step order.
- **FR-003** — Exactly ONE step may write each artifact. `presentation.html` is **written** by the
  composer and **edited in place** by QA; `presentation.pptx` is written only by the render tool.
  (`write_file` does not overwrite in deepagents' `FilesystemBackend`.)
- **FR-004** — A `render_pptx` tool MUST accept PptxGenJS source, build the file via the existing
  `generate_pptx_from_code`, and return either a success with byte count or the compile error.
- **FR-005** — A `verify_pptx_layout` tool MUST wrap `verify_layout.py` **unmodified** and return
  its violations as actionable text.
- **FR-006** — An `extract_pptx_shapes` tool MUST wrap `extract_pptx.py` **unmodified** for
  ground-truth inspection.
- **FR-007** — The retry loop MUST live inside step 4 via tool return values — no conditional gate,
  no workflow branching, no engine change.
- **FR-008** — `pptx_export.py` MUST resolve the `node` binary rather than assuming
  `/usr/local/bin`. It currently hardcodes `PATH: "/usr/local/bin:/usr/bin:/bin"`, so a Homebrew
  install (`/opt/homebrew/bin/node`) dies with `FileNotFoundError: node`. The child env MUST remain
  scrubbed — resolving the path adds no secrets.
- **FR-009** — The step-4 agent MUST be registered such that the existing Download PPTX button
  resolves its output with no change to `runs.py` (i.e. its id matches `_PPT_CODE_AGENT_IDS`).
- **FR-010** — `ppt_v2` MUST have a `PIPELINE_AGENTS` entry — required by
  `allowed_custom_agent_ids` for any wizard-launched pipeline, which sends `agent_ids`.
- **FR-011** — Its steps MUST satisfy `presort_specs`' produces/consumes DAG check, not only the
  workflow compiler (spec 016 §6 G-2).

### Key Entities

- **PptxGenJS source** — the step-4 agent's text output. Text, so it stores in `agent_outputs` like
  any other agent output; this indirection is what lets a real `.pptx` ship with no schema change,
  since `WorkflowRun.output` and `ArtifactRef.content` are both `Text` columns.
- **`html-deck-to-pptx` skill** — the output contract: `pres` as the variable, `write("nodebuffer")`
  as the return, hex without `#`, inches on a 13.333 × 7.5 canvas, no `require`/`import`.

## 5. Out of scope

- A deterministic HTML→PPTX converter. See Clarifications.
- Visual screenshot diffing of HTML vs PPTX. `render_check.py` drives headless Chromium but is
  built for prototype nav-testing; pointing it at a deck is a misuse. The geometry gate catches the
  failure that matters — overlapping and off-canvas text — deterministically and cheaply.
- Storing binary in artifacts. Blocked by the `Text` columns; not being changed here.
- Retrofitting any of this onto `ppt`.

## 6. Phase 2 — Sandbox tab (specified, not in this build)

Replaces a bolted-on `.pptx` row in FilesTab: both artifacts appear in a real workspace view.
Needs `RunSandbox.list_files()`, `GET /api/runs/{id}/sandbox`, `GET /api/runs/{id}/sandbox/file`,
and a `SandboxTab` reusing `AppBuilderPreview`'s tree.

**Security, built in from the start:**

1. Owner scoping on every request — the sandbox path derives from `user_id`, so a miss is
   cross-tenant.
2. `Content-Disposition: attachment` + `application/octet-stream` for anything not explicitly
   whitelisted. Serving agent-authored HTML inline from the API origin is stored XSS with the
   session in scope. The preview iframe keeps using `srcdoc`.
3. Size and file-count caps on listing and read.
4. A real "workspace expired" empty state for TTL-swept runs.

## 7. Success Criteria *(mandatory)*

- **SC-001** — A completed `ppt_v2` run yields an HTML deck that renders AND a `.pptx` that
  `python-pptx` opens with the expected slide count.
- **SC-002** — `compile_for_run("ppt")` is byte-identical before and after this feature.
- **SC-003** — Step 4 emitting invalid JavaScript costs the pptx only; the HTML deliverable still
  resolves.
- **SC-004** — `verify_layout.py` exits 0 on the shipped pptx.
- **SC-005** — The existing Download PPTX button returns a valid file with no change to `runs.py`.

## 8. Risks

| risk | containment |
|---|---|
| Step 4 authors invalid PptxGenJS | Tool returns the compile error; agent retries. Worst case: no pptx, deck unaffected. |
| Model cannot satisfy the geometry gate | Bounded retries, then ship with a logged warning. The gate has teeth but is not a hard run failure. |
| `qwen3.5:4b` too weak for step 4 | Real locally. Design is provider-agnostic; the dry run proved it on a frontier model. Local runs may need a larger model. |
| A 4th step slows every deck run | `ppt` is untouched; users who want speed keep using it. |

## Assumptions

- Node and `pptxgenjs` are available wherever the backend runs (true locally and in the prod image).
- The deck HTML that reaches step 4 is complete — which is only true since the `num_ctx` and
  code-fence fixes landed; before those, both deck agents were being truncated mid-attribute.
