# Observed: PLAN vs MEMBERSHIP vs RESOLVER

What the three views of "what runs" actually contain, measured rather than described.

Raw data was generated by `dump_raw.py` / `dump_plan_vs_membership.py` at the repo root
(`workflow.compiled.json`, `agents.membership.json`) — plain `dataclasses.asdict()` of the
real `CompiledWorkflow` and `AgentSpec` objects, nothing filtered or computed. Both
scripts and their JSON output were removed 2026-08-13 once this report was written; the
findings below are unaffected.

## The three views

| | source | shape |
|---|---|---|
| **PLAN** | `compile_for_run(pt).steps` ← `agents/workflows/<id>/workflow.yaml` | an ordered **list**, no edges |
| **MEMBERSHIP** | `get_pipeline_agents(compiled.id)` ← `pipeline_type:` + `order:` in each `AGENT.md` | a **set + order ints** |
| **RESOLVER** | `WorkflowResolver().validate(agents)` ← `produces`/`consumes` | a **graph**, flattened by topo-sort |

## The equality condition

Verbatim, `engine.py:1715-1722`:

```python
_compiled_agent_ids = [s.agent_id for s in compiled.steps]
_membership_ids     = [a.id for a in get_pipeline_agents(compiled.id)]
if _compiled_agent_ids and _compiled_agent_ids != _membership_ids:
    raise RuntimeError(...)
```

Equality is **exact, ordered, element-by-element `list[str]` comparison**. Not set equality, not length. Nothing about the DAG, `produces`/`consumes`, `order:`, or any other field — both rich objects are flattened to name lists first.

`if _compiled_agent_ids and ...` is two tests joined by `and`: a bare list in boolean context (empty = false) followed by the comparison. So the check is *"if the plan is non-empty AND it differs from membership."* The `and` short-circuits, letting an empty plan skip entirely.

| plan | vs membership | raises? |
|---|---|---|
| `[]` | anything | no — guard short-circuits |
| `['a','b']` | `['a','b']` | no |
| `['a','b']` | `['b','a']` | **yes** |
| `['a','b']` | `[]` | **yes** |

The guard excuses an empty **plan**, never an empty **membership** — exactly backwards for a template-instance workflow, where empty membership is the normal and correct state.

## They are lists of different things

MEMBERSHIP entry — an *agent identity* (`hello_html`):

```json
{ "id": "writer", "order": 2, "pipeline_type": "hello_html",
  "tools": ["coin_flip"], "produces": ["writer"], "consumes": ["emoji-picker"],
  "gate": null, "max_tokens": 500 }
```

PLAN entry — a *position in a workflow* (`sample_subagents`):

```json
{ "agent_id": "custom-agent:fact", "instance_id": "fact",
  "display_name": "Fact Writer", "strategy": "single_shot",
  "depends_on": ["custom-agent:emoji"], "skills": ["playful-tone"],
  "prompt": "The user's message is the topic. Write exactly 1 line…",
  "tools": {"read_files": true, "write_files": false, "exec": false, "…": "…"},
  "hooks": ["audit_logger", "secret_scan"], "on_conflict": "human_gate" }
```

`prompt`, `skills`, `instance_id`, `display_name`, `depends_on`, `strategy` exist only on the plan side — and cannot exist on the other, since four steps share one `AGENT.md`. `produces`/`consumes`/`order`/`gate` exist only on the membership side, and for these four are empty or identical, which is why the resolver returns no DAG.

**Membership can describe `hello_html`. It cannot describe `sample_subagents`. The plan can describe both.**

## Which graph exists where

| | has a graph? | has an order? |
|---|---|---|
| `app_builder` PLAN | no | yes (the list) |
| `app_builder` MEMBERSHIP | **yes** (produces/consumes) | yes (order ints) |
| `sample_subagents` PLAN | **yes** (`depends_on`) | yes |
| `sample_subagents` MEMBERSHIP | no — empty | no — empty |

Each side carries the graph exactly where the other cannot.

## What the engine actually runs

```
930   execute(agents=…, pipeline_type=…)     agents arrives FROM THE CALLER, registry-sourced
1463  compiled = compile_for_run(...)        the PLAN is built
1477  _apply_selections(...)                 user overlay on the plan
1644  validation = self._resolver.validate(agents)   the DAG is built — from `agents`, not compiled
1661  halt if not satisfiable
1672  ordered_agents = validation.dag or list(agents)   ← execution order decided
1715  the membership assertion                          (compares plan vs registry)
2185  _steps_by_agent = {s.agent_id: s for s in compiled.steps}
2307  for i, spec in enumerate(ordered_agents):         ← THE LOOP
```

The loop runs over `ordered_agents` — the **resolver DAG**. The compiled plan never drives the sequence; at 2185 it becomes a dictionary keyed by `agent_id`, and inside the loop each step is fetched by name:

```python
step = _steps_by_agent.get(spec.id)
strategy_name = getattr(step, "strategy", "single_shot") if step else "single_shot"
```

Note `.get` — an agent in the DAG with no step in the plan does not error; it runs with defaults.

| | decides |
|---|---|
| registry → `agents` → DAG | **who runs, and in what order** |
| compiled plan | **how each one runs**, looked up by name after the fact |

Three consequences of `validate(agents)` taking `agents` and not `compiled`:

1. The manifest's step order has **no influence** on the DAG — disjoint inputs
2. A step existing only in the manifest (`custom-agent:emoji`) is invisible to the resolver
3. The DAG is built before the assertion, and the assertion never feeds back into it

And the ordering matters: `ordered_agents` is set at **1672**, the assertion runs at **1715**. The engine picks its order from the DAG, then validates that plan and membership agree with *each other* — two lists, neither of which is necessarily the one executing.

For `app_builder` all three exist and the DAG differs from the other two. The assertion passes, and the run proceeds in an order neither compared list describes.

## Why sample_subagents could not run

`get_pipeline_agents` returns `[]`, so `agents = []`, so `validate([])` yields an empty DAG, so `ordered_agents` is empty and the loop at 2307 has nothing to iterate. Meanwhile `compiled.steps` held all four instances, sitting in a lookup table nothing ever queried.

Rebuilding `agents` from `compiled.steps` right after 1463 fixes it by making the plan feed both the resolver and the loop — which is why one edit at the top resolved what looked like five separate bugs.

## Also visible in the data

- **`spec_kit` is unsatisfiable**: `"satisfiable": false` — *"Agent 'clarify-agent' consumes 'brief' but no upstream agent produces it."* Pre-existing; harmless only because it has no manifest.
- **`chat`'s DAG is an identity function**: all seven agents have empty `produces` and `consumes`, so the "DAG" is the input order handed back unchanged. Same for the `sample_*`, where it is `null`.
- **`tools` is two different things**, side by side: `["coin_flip"]` on the agent, `{read_files: true, …}` on the step.
