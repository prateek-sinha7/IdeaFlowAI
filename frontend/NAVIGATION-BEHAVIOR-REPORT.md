- **SAME** — the screen, mode, and data the user ends up looking at is **unchanged**. Nothing about what you *see* is different.
- **DIFFERENT** — the actual screen, mode, data, or messaging shown genuinely changed: a bug fix, new messaging, a changed default, a destination that used to go nowhere/somewhere else.
- **NEW** — the button/page/route did not exist before this branch at all.

**"Action Taken" column:** what was actually done, if anything, in response to your "give me the same experience back" request — a real fix, or "none needed" if the row was already fine.

**"QA Notes" column:** what genuinely happens when you click it, based on live testing — not inferred from code. Where I have not personally live-tested a row in this pass, it says so explicitly rather than guessing. A few rows carry evidence from earlier in this session (the `/library` consolidation work, the page-width/back-button fix) — those are labeled as such, distinct from this pass's fresh testing.

## New bugs found during this live-validation pass (not fixed yet)

This pass live-tested essentially everything that could be reached without an active/in-flight pipeline run (login fresh as `qa-admin`, 50 real runs, real saved workflows, real library/settings/analytics data). Two genuine, previously-undocumented bugs turned up — both are URL/state desyncs, same family as the one already fixed in §1, but in different components:

1. **Library detail modal's X button doesn't close the URL, only the modal.** Open any Agent/Skill/Hook card → URL becomes `/library/agents/{slug}` and the modal opens (correct). Click the modal's own X button → the modal visually closes, but the URL stays on the detail path. Refresh at that point and the modal **reopens** even though you just closed it — because the URL never actually left. Browser Back, by contrast, closes it correctly (URL reverts too). Fix would be: make the X button call the same close handler Back uses (or `router.back()`), not just a local `setOpen(false)`.
2. **Settings tab clicks don't update the URL, only direct navigation does.** Cold-opening `/settings/usage` (typing the URL, or via a link) correctly opens the "Usage & Limits" tab. But clicking between tabs *within* the Settings page — e.g. starting on `/settings/ai-model` and clicking "Usage & Limits" — switches the visible content correctly but leaves the URL at `/settings/ai-model`. Refresh mid-session and you're silently bounced back to whichever tab the stale URL still points to.

Neither was in the original 93-row code-level audit — both only surfaced from actually clicking through the live app. I have not fixed either yet; flagging for you to say whether you want them fixed now or left for later since neither is what you originally reported.
