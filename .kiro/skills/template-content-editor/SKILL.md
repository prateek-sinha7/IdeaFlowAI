# Template Content Editor Skill

Edit only the human-readable text inside an OpenDesign template. The design is
already correct — your job is to change what the words say, not how the page
looks or is built.

The new copy is **generated by you (the AI)** after a deep analysis of the
template. Do not ask the user to hand you the exact strings. Read the template,
understand what each section is for, then write copy that fits it. The user
supplies the *subject* (their product, topic, or brand); you supply the words.

## Core invariant — content only

This skill changes **text and nothing else**. Everything that is not
human-readable copy must be byte-for-byte identical before and after your edit:
tags, nesting, element count, `class` / `id` / `style` / `data-*` attributes
(especially `data-od-id`), every `<style>` and `<script>` block, CSS tokens and
`:root` variables, image sources and `.ph-img` placeholders, layout, section
order, and responsive behavior. If a change would touch any of those, it is out
of scope — do not make it. When in doubt, leave it exactly as it was.

## Preserve length & aesthetics

The layout was tuned to the *length* of the original copy — line breaks, the
number of lines a headline wraps to, how a stat fits its column, whether a
CTA stays on one line. Changing length silently breaks that tuning: text
reflows onto new lines, a one-line headline becomes two, a tight grid cell
overflows, and the deliberate visual rhythm and impact are diminished.

So match the size of every slot, not just its role:

- Keep the new copy within roughly ±10% of the original's **character count**
  for that slot. Headlines, buttons, eyebrows, stats, and other short slots
  are the strictest — aim to match their character count almost exactly; long
  body paragraphs have a little more slack.
- Keep the same **word count and shape**: a 3-word headline stays ~3 words, a
  two-sentence lede stays two sentences, and a stat value keeps the same
  character footprint (e.g. `38ms → 4ms` → `920ms → 45ms`, not a long phrase).
- Preserve punctuation density and any hard line breaks (`<br>`) exactly —
  they are layout, not prose.
- If the ideal wording would run much longer or shorter than the original,
  rewrite it until it fits the original's footprint rather than letting it
  reflow. Fitting the length takes priority over the perfect phrasing.

When you record each slot in the deep analysis (Step 3), note its character
and line count so you have a concrete target to match when generating.

## Scope

OpenDesign templates live under `skills/opendesign/design-templates/<id>/`.
The files that carry visible content are:

- `example.html`         — the rendered preview / reference document
- `assets/template.html` — the seed (present on some templates)
- `references/*.md`      — paste-ready section skeletons (text only, no CSS)

Design tokens live in `skills/opendesign/design-systems/<id>/DESIGN.md`. This
skill does **not** touch design systems, craft rules, or CSS.

## Workflow

### Step 1 — Resolve the template

1. Identify which template the user means (a slug like `saas-landing`,
   `web-prototype`, `html-ppt-pitch-deck`). If ambiguous, list the closest
   matches from `design-templates/` and ask which one.
2. Confirm the folder exists: `skills/opendesign/design-templates/<id>/`.

### Step 2 — Read the whole template

Read the target file(s) end-to-end **before** proposing any change. Never edit
HTML you have not read. Also read, when present, the template's `SKILL.md`
(its `od:` frontmatter states mode/platform/scenario and intent) and its
`references/*.md` so you understand how each section is meant to be used.

### Step 3 — Deep analysis (do this before writing any copy)

This is the core of the skill. Build a written understanding of the template
first, then generate copy from it. Produce a short internal analysis covering:

1. **Purpose & type** — what is this template for (landing page, pitch deck,
   dashboard, docs, pricing)? Who is the audience?
2. **Section inventory** — walk the DOM top to bottom and list every content
   region in order (nav, hero, feature grid, stats, quote, pricing table,
   CTA, footer, slide 1..N, etc.), keyed by its `data-od-id` when present.
3. **Role of each slot** — for every editable slot, note what job the copy
   does: an eyebrow, a headline, a supporting paragraph, a metric, a CTA
   label, an alt text. A headline persuades; a caption clarifies; a stat is a
   number + unit.
3a. **Length target per slot** — record each slot's current character count
   (and line count for headlines/labels/stats). This is the footprint the new
   copy must fit so the layout does not reflow (see "Preserve length &
   aesthetics").
4. **Voice & constraints from the existing copy** — capture the tone (formal
   vs punchy), the length/shape of each slot (word count, sentence vs
   fragment), any repeated strings that must stay in sync, and template rules
   (e.g. single-accent budget, no filler, `.ph-img` placeholders).
5. **Gaps** — bracketed slots like `[REPLACE]` / `[HEADLINE]` are explicit
   fill points; note them.

Summarize this analysis to the user in a few lines before writing, so they can
redirect the direction (topic, tone, audience) cheaply before you edit.

### Step 3b — Generate the content

Using the analysis plus the user's subject/brief, write new copy for each slot:

- Generate **specific, real** copy for the subject — names, benefits, concrete
  claims — never lorem ipsum or generic filler.
- Match each slot's role, tone, AND length so the layout does not break: hit
  the character/word footprint you recorded in Step 3a (±10%, tighter for
  short slots), keep the same sentence count, and preserve any `<br>` breaks.
  A headline stays a short one-line headline, a paragraph stays a paragraph,
  a stat stays the same number of characters. Re-word until it fits.
- Keep repeated strings consistent everywhere they appear.
- If the user gave little detail, make reasonable, coherent assumptions for the
  subject and state them briefly rather than stalling.

### Step 4 — Classify what is editable

Change ONLY text nodes and human-readable attribute values:

- Headings (`<h1>`–`<h6>`), paragraphs (`<p>`), spans, list items (`<li>`)
- Button and link labels, nav items, eyebrows, captions
- Table cell content (`<td>`, `<th>`)
- Visible text inside `<section>`, `<article>`, `<figure>` etc.
- Human-readable attributes: `alt`, `title`, `aria-label`, `placeholder`,
  and the document `<title>`

Do NOT change (treat as structure — leave byte-for-byte identical):

- Tag names, nesting, or the number of elements
- `class`, `id`, `style`, `data-*` attributes (especially `data-od-id`,
  which comment mode targets — see the web-prototype hard rules)
- Anything inside `<style>` or `<script>`, and CSS `:root` variables/tokens
- Image sources / placeholders (keep `.ph-img` placeholders; do not add
  external stock-photo URLs)
- Layout structure, section order, or responsive behavior

### Step 5 — Make targeted edits

- Use `str_replace` with enough surrounding context to hit exactly the right
  occurrence. Do not rewrite whole files.
- Replace each slot (including bracketed `[REPLACE]` / `[HEADLINE]` fill
  points) with the copy you generated in Step 3b.
- Keep the new copy roughly the same length/shape as the original so the
  layout does not break (a headline stays a headline, not a paragraph).
- Preserve inline markup inside the text (e.g. `<strong>`, `<br>`, entities).
- If the same string appears in multiple places and all should change, use
  `replace_all=true`; if only one should change, add context to isolate it.

### Step 6 — Verify (content-only gate)

Before finishing, prove the edit changed text only. This step is mandatory.

- Run a diff of the file (e.g. `git diff -- <path>`). Inspect every changed
  line: the ONLY differences allowed are text nodes and human-readable
  attribute values (`alt`, `title`, `aria-label`, `placeholder`, `<title>`).
- If the diff shows any change to a tag, attribute name, `class`/`id`/`style`/
  `data-*` value, `<style>`/`<script>` content, CSS variable, image `src`, or
  the number/order of elements, **revert that change** and redo the edit
  targeting only the text.
- Confirm element count and `data-od-id` set are unchanged, and the HTML still
  balances (no tags dropped or added).
- If the file is HTML, optionally open it to confirm it still renders. If you
  cannot verify, say so explicitly rather than assuming success.

## Hard rules

- Never introduce new design tokens, colors, fonts, or CSS. Content only.
- Never delete or renumber `<section>` blocks or their `data-od-id`s.
- Never touch the `od:` frontmatter of a `SKILL.md` or any `DESIGN.md`.
- If the user's request actually needs structural or design changes (new
  sections, different layout, restyling), say so and stop — that is out of
  scope for this skill and belongs to the template/design-system authoring
  flow, not a content edit.

## Output

After editing, summarize in one or two sentences: which template file(s) you
changed and which pieces of copy were updated (header, paragraph, labels).
Do not paste the whole file back.
