# velocity

Entry point for the Velocity knowledge-base skill family. Velocity maintains a
structured knowledge base under `.knowledge/` that captures architecture,
decisions, bugs, fixes and open issues as individual markdown cards, plus a
compacted context pack for fast priming.

## Knowledge base layout

```
.knowledge/
├── cards/            469 cards, filename {YYYYMMDD}[-{HHMM}]-{ID}.md
│                     HHMM only when a real authoring commit provides it
│                     frontmatter: id, type, kind, title, status, applies_to{phases,modules,globs,requirements},
│                     locked_constraints, verification, compact_summary,
│                     last_updated, author
│                     type: fix|bug|issue|adr  — four, and no others.
│                     `requirement`, `phase` and `doc` were RETIRED: every card of
│                     those types was a GSD-generated stub whose body only pointed
│                     into `.planning/`. They were deleted, not migrated.
│                     `adr` is reinstated for technical decisions; none exist yet.
│                     kind: state (adr) | event (fix, bug, issue)
│                     ID scheme: {TYPE_CODE}[-{SUBTYPE}]-{rest}, TYPE_CODE one of
│                     FIX|BUG|ISS|ADR — e.g. FIX-233, ISS-147, BUG-012-sse.
│                     **the ID linter** (see `cli.md`) checks this.
├── architecture/     DOMAIN-<slug>.md (14) -- hand-authored SYSTEM CONCERNS. A domain
│                     declares `members:` as globs and may overlap other domains;
│                     it carries ## Purpose / ## Shape / ## In practice / ## Why this
│                     shape. **Diagrams live here and nowhere else** -- each card's
│                     ## Shape diagram is inlined into ARCHITECTURE.md by the build.
│                     MOD-<slug>.md (36) + modules.json -- one per FOLDER, generated
│                     from pydeps/dependency-cruiser. Prose is preserved; MOD cards
│                     carry no diagrams by design.
│                     files/**.md (789) -- one per source file, generated.
│                     Staleness: every card carries `code_signature` (derived from
│                     the files it is answerable for) and `prose_signature` (stamped
│                     when its prose was last written). Unequal = stale.
├── .stage/           delta approval queue — created on demand by `sync`, consumed and
│                     removed once proposals are applied. Absent = nothing pending (normal).
├── INDEX.md          one line per card: `- <ID> — <one-line description>`
├── ARCHITECTURE.md   what Velocity is + the module map
├── CONTEXT.md        the compacted context pack (built by prime)
└── state.yaml        {last_sync_commit, last_sync_date, cards_count, architecture_count}
```

Derived artifacts are regenerated by script, never hand-edited. One command
rebuilds all of them in dependency order:

```
architecture -> index -> context -> validate
```

That is **the full rebuild**. Every command has a name in `cli.md`; this
file never spells one out.

**`cli.md` in this directory is the authority on tooling** — every script,
flag, failure mode, and which sub-skill runs what. Read it before running
anything under `tools/`, and never paste a command to the user for them to
run: `/velocity` exists so they talk to the skill and the skill drives the
tools.

## `.planning/` is a read-only fallback

`.knowledge/` is the source of truth. `.planning/` is kept ONLY as a
fallback for history the cards do not carry — the five legacy registers
(`FIX-REGISTER.md`, `FIX-TEST-REGISTER.md`, `ISSUES-REGISTER.md`,
`IMPLEMENTATION-REGISTER.md`, `STATE.md`) plus per-phase and per-task
narrative under `phases/` and `quick/`.

- **Look in `.knowledge/` first, always.** Only fall back to `.planning/`
  when the answer genuinely is not in the cards or `INDEX.md`.
- **Never write to `.planning/`.** No new rows, no edits, no ID allocation.
  It is a frozen archive.
- **Say so when you use it.** If any part of an answer came from
  `.planning/`, tell the user plainly — name the file, and say the cards did
  not carry it. Never present `.planning/`-derived facts as though they came
  from the knowledge base; the two can disagree, and `.planning/` is the
  older, unmaintained one.
- Registers are large — `grep` them, never read one whole.

`legacy-registrars.md` documents their structure. Read it for shape, not as
a licence to maintain them.

Nothing in this skill family runs `git commit`, `git add`, `git push`, or any
branch operation. The user handles all git themselves.

**This repo has more than one checkout.** A main checkout plus git worktrees
under `.claude/worktrees/`, each on its own branch with its own `.knowledge/`
— separate cards, separate `state.yaml`, separate counts. Whenever you report
numbers or state, say which tree and branch they came from. Two sessions in
two trees will legitimately disagree, and unlabelled figures make that look
like corruption rather than two different knowledge bases. If the user
reports output that contradicts yours, check `git worktree list` before
investigating drift. See `status.md` § Two trees.

**Cross-card references live in the `## Related` block**, in the body, right
below the frontmatter and delimited by `<!-- RELATED -->` / `<!-- /RELATED -->`.
They are ordinary markdown links — `[FIX-034](20260704-1815-FIX-034.md)` —
so they are clickable in any editor. They were in frontmatter once; YAML is
not a rendering context, so nothing there was ever clickable.

The ID is the stable key and the filename is not (it carries a datetime), so
`build_index.py` re-resolves every target on each rebuild: rename a card and
the links pointing at it follow. **Always author the full markdown link form**
(`[FIX-034](20260704-1815-FIX-034.md)`) — in the `## Related` block AND
anywhere else a card references another (there is no separate bare-id or
`[[wikilink]]` shorthand; one pattern everywhere). The rebuild's re-resolution
on rename is what keeps that link correct later, not a reason to author it
any other way.
`validate_links.py` checks all 1,278 — both that the id names a real card and
that the target file exists — so a dead reference fails the rebuild rather
than rotting unnoticed. IDs are permanent — corrections
happen by SUPERSESSION (new card, old card's `status` -> `superseded`), never
by rewriting an existing card's meaning in place.

The one sanctioned exception is `tools/knowledge/normalize_card_ids.py`, an approved
one-time migration onto the ID scheme above. It rewrites IDs and every
reference to them in a single pass. Do not reach for it to "fix" an
individual card — that is still a supersession.

## Dispatch

Look at the first argument passed to `/velocity`:

- `status` -> read and follow `status.md` in this directory. Cheap and
  read-only; good default when the user asks "what's the state of things".
- `analyze` -> read and follow `analyze.md` in this directory.
- `fix` -> read and follow `fix.md` in this directory.
- `sync` -> read and follow `sync.md` in this directory.
- `prime` -> read and follow `prime.md` in this directory.
- `book-keeping` or `bookkeeping` -> read and follow `book-keeping.md` in this
  directory. Both spellings are the same verb, not two verbs.
- `diagrams` -> read and follow `diagrams.md` in this directory. Re-authors the
  DOMAIN architecture cards whose code has moved and re-inlines their diagrams
  into `ARCHITECTURE.md`. This is the manual fallback for the
  `knowledge-domains` pre-commit hook, which does the same work automatically
  but never blocks a commit -- when it cannot reach the `claude` CLI, or the
  change touches more cards than its cap allows, it prints the affected cards
  and tells the user to run this.
- no argument, or anything else -> print the following and stop:

```
velocity: choose one —
  status        what the knowledge base holds and what is stale (cheap)
  analyze       find the root cause of a bug or symptom
  fix           analyze, propose, and apply a fix
  sync          reconcile the knowledge base with recent commits
  prime         (re)build the compacted context pack
  book-keeping  record a card or architecture update
  diagrams      re-author stale DOMAIN cards and their diagrams
```

**These seven are the complete set. There are no others, and no synonyms.** Do
not accept, invent, or document an extra verb — an undocumented verb that
appears to work is worse than one that prints the menu, because it hides which
procedure actually ran. If the user asks for something outside the six, print
the menu and say which of the six is closest.

Regenerating derived artifacts is **not** a verb. It is the closing step of
`sync`, `prime` and `book-keeping`, each of which runs it as part of its own
procedure. `cli.md` names the commands.

The sub-skill file is the authority for its procedure — always read it in
full before acting, even if you believe you already know the steps. Do not
improvise a shortcut version of a sub-skill from memory.
