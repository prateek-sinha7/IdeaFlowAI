Velocity AI — To-Be Architecture

The production target for Velocity AI (internally Flowin), designed from the verified as-is record rather than from a reference model. The premise throughout: the workflow kernel, the capability layer, the 86 agent definitions, the SSE event contract and the frontend are already built and verified, and they do not change. What changes is the plumbing underneath them — where state lives, how runs are dispatched, how events reach the browser, and how the whole thing is packaged per tenant. Every diagram is colour-coded by change budget so the cost of each flow is visible on the drawing, and every node that corresponds to something that exists today carries its repository path.

as-is baseline: dev @ 2d8d9f60 (as-is-architecture.html — 12 planes / 36 flows / 641 steps / 296 findings) decision 1: compute = ECS Fargate + ALB decision 2 (v2): Cognito broker in the control plane; internal JWT contract unchanged decision 3: durable task graph in v1 - custom, hardened lease rules decision 4 (v2): tiered tenancy - pooled default; dedicated + customer-hosted tiers date: 2026-08-02

The change budget

Three columns of concrete modules. The kernel, the capability layer, the agents, the event contract and the frontend do not change; the plumbing underneath a handful of modules does.

Unchanged — do not touch

  • agents/workflows/ manifest layer, compiler and CompiledWorkflow (18 manifests) — already declarative and correct
  • All 68 registered capabilities across 22 kinds and their ports (agents/capabilities/registry.py)
  • All 86 AGENT.md definitions, guardrails, skills, hooks and prompt composition (agents/factory.py)
  • ExecutionEngine._execute_impl step loop, gates and clarify logic (budget's per-tenant concurrency ceiling is NOT frozen - see 3.7's per-tenant cap replacing budget.py's hardcoded 4)
  • DeepAgentRunner / create_deep_agent runtime, runner and model factory (retries and fallback included)
  • The SSE v1 vocabulary and wire format, wire-compatible throughout the re-platform — the frontend is untouched until the negotiated v2 migration (Phase 5)
  • Postgres schema changes stay additive-only within a release cycle; contraction only in the dedicated compaction release (Phase 5)

Same seam, new implementation

  • run_engine.py registries (queues, cancel, tasks) → Redis-backed bus and leases
  • artifact_store/store.py gate + clarify waiters → durable answer + Redis wake-up
  • _RunEventSink persist (authz.py:296) → batched, off the event loop
  • sandbox.py local disk → task-local ephemeral tree + S3 step checkpoints (EFS only if measured restore latency demands it)
  • artifact_refs.content inline Text → S3 object via the existing unused location column
  • get_current_user → identity adapter fronted by the Cognito broker; internal JWT + a real /api/auth/refresh unchanged for the routers
  • main.py router registration → ROLE-gated (control / web / worker / scheduler)
  • StateMachine → Aurora-authoritative state with one status vocabulary

Net new

  • ECS Fargate services + ALB; seven roles from one image
  • Aurora PostgreSQL Multi-AZ + RDS Proxy (replaces host Postgres + hourly dump)
  • ElastiCache Redis — event fan-out, control nudges, quota counters; never a queue, never truth (the dispatch queue lives in Aurora via FOR UPDATE SKIP LOCKED)
  • Run ownership leases + reaper in Aurora; Aurora is also the dispatch queue
  • Durable task graph + scheduler role for multi-day builds (decision 3)
  • Per-tenant plane as a Terraform module: VPC, Aurora, Redis, S3, CMK, services (decision 4 (v2))
  • Velocity control plane: tenant registry, entitlement, catalogue, provisioning
  • Migration runner task (advisory-locked, gates rollout)
The cost of decisions 3 and 4, stated honestly, once. The durable task graph and full per-tenant isolation are the two largest items in this programme — together they are the majority of the net-new engineering, and per-tenant isolation also multiplies the monthly infrastructure bill by tenant count (see the cost model below). Both were re-examined in v2 (task graph stays, hardened; tenancy is tiered, pooled default) and are designed for here, not re-litigated. The mitigation baked into the design is that neither reaches into the kernel: the task graph is a scheduler service beside the existing strategies, reusing the task parsers and the subagent_runs / wave_runs tables that already exist; per-tenant isolation is a Terraform packaging concern plus closing three nullable-tenancy gaps in the schema. If the programme must shrink, these are the two dials — not the re-platform, and not the Phase 0 defect fixes.
Non-goals, stated explicitly. No non-AWS cloud support (AWS only, by requirement). No replacement of the manifest format. No frontend rewrite — the v1 event contract stays wire-compatible through the re-platform, and its v2 successor is a negotiated migration (Phase 5), not a break. Owning a password database long-term is a non-goal: identity federates through the OIDC broker; local bcrypt remains only as the fallback path.

Level 1 — end-to-end workflows

Each flow as it will run after the re-platform, colour-coded by what it costs to get there. Nodes that correspond to something that exists today carry the repository path.

What changes and what does not. The wizard, the compile path, the kernel and the run screen are the product as it exists today and are untouched. The re-platform is entirely in how the run is dispatched (a worker claims it from an Aurora dispatch queue (SKIP LOCKED) instead of asyncio.create_task on the API process, run_commands.py:1779), how events are persisted (batched off the event loop instead of one synchronous commit() per streamed chunk, authz.py:296), and how they are fanned out (published to every viewer instead of one exclusive queue.get() consumer, run_stream.py:200). The event vocabulary and seq-based replay are unchanged.
Almost nothing changes. Revisions are shipped and live-proven: parent_run_id (resolved only for *_revision types, run_commands.py:1745), the parent-artifact fallback chain (engine.py:5759) and revises_existing lineage all work today. The one structural change is that the parent's working tree is restored from an S3 checkpoint rather than assumed present on the same box — which is what lets a revision land on any worker. Two as-is defects are fixed in passing: revision runs get a milestone sink (today they emit no narrator cards, run_commands.py:2403) and the child no longer silently drops the parent's template/design-system context (engine.py:5931 forces od_context=None).
Nothing here is new work. Chaining is shipped and live-proven (chain chips + matchChainTarget, RunChatLane.tsx:1114; chain context via chain_hints). The flow is drawn to show that the child run is dispatched exactly like any other run, so it inherits admission control, tenancy scoping and leasing for free once those exist.
The largest new build in the programme (decision 3). Today app_builder is 15 agents executed strictly serially inside one coroutine (engine.py:2276); if the process dies at agent 12 the restart scan orphan-fails the run (engine.py:5519). The target turns the plan into durable task rows — a ~500-task build is 500 rows with dependency edges, attempts, leases and heartbeats — dispatched by a scheduler with bounded per-tenant parallelism and a write-domain lock per lane. Each task still executes through the existing step machinery: the scheduler decides what runs, the unchanged kernel decides how. The task parsers (heading_tasks, json_tasks) and the subagent_runs / wave_runs audit tables are reused, not rebuilt. The flow is drawn on app_builder because it is the extreme consumer - the graph itself is keyed to task-producing strategies, not workflow names: the prototype's task_loop step and any builder-composed fan-out stage ride the same rows (see the task-graph drill-down). See the three-day timeline board below for why this is worth building.
Mid-run questions without interrupting execution — a stated product requirement that already works. The Concierge answers from real run data through owner-scoped read tools (concierge.py:431) and streams over chat_reply_chunk (run_commands.py:1332). On the target it reads from Aurora rather than a process-local context, so any web task can answer while the run executes on a different worker. Two as-is defects are fixed on this path: the reply is published to all viewers, not only the tab that POSTed (run_commands.py:1319), and the per-turn full-log read that grows with run length (run_commands.py:1105) is replaced by an indexed open-gate lookup.
The single most important correctness change in the document. Today every human-gate and clarify wake-up is an asyncio.Event in a module-level dict (artifact_store/store.py:42): a gate can only be resolved by the exact process running the run, answers submitted with no waiting coroutine are silently dropped (run_commands.py:274), and a restart loses the wait entirely. On the target the answer is durable in Aurora and the wake-up travels over Redis, so any web task can accept an approval and the owning worker is woken wherever it runs. The same change removes the bare-text-defaults-to-approve hazard (chat_router.py:222): an untyped chat turn at an open gate becomes a question, never an implicit approval.
Decision 2 (v2), concretely: Amazon Cognito is the broker; the internal JWT is untouched. One Cognito user pool per control-plane environment; each tenant configures its own IdP (Okta, Entra, any SAML/OIDC provider) as a federated identity provider, so their users sign in with their corporate identity and MFA policy — we never hold their passwords. Sign-in is the authorization-code + PKCE flow (hosted UI acceptable for v1); the control plane exchanges the code, validates Cognito's tokens, links or JIT-provisions the user (matched by verified email on first federated login), resolves tenant, tier and tenant-admin role from Aurora, and mints exactly the internal JWT + rotating refresh the 20 routers already verify — federation is an edge concern and zero router code changes. Email + password against the user pool remains the fallback for tenants without an IdP and for local dev; bcrypt-local survives only for air-gapped customer planes. SCIM arrives with the first contract that demands it; invite, reset and tenant-admin flows land in Phase 1 regardless. Auth events gain an audit log (today auth.py has no logger at all).
Fixes a live defect, not just a scale limit. Today _PIPELINE_QUEUES holds one asyncio.Queue per run and every SSE attach consumes it exclusively (run_stream.py:200), so two tabs on one run split the event stream and only one receives the end sentinel (run_stream.py:201). Publishing each persisted event to a per-run channel gives every viewer a full copy; the durable log remains the replay source of truth by seq, exactly as today. This is also the prerequisite for running more than one web task. The stream gets its own rate budget — today it shares the generic /api/ 120 r/min zone and a reconnect storm competes with all other traffic (bootstrap-ec2.sh:710).
Also fixes a live defect. Cancel is currently a silent no-op for every run driven by the resume tier — _drive_resumed_stream never passes cancel_event into _execute_impl (engine.py:7789) while POST /cancel still answers cancelled: true (run_commands.py:301). Routing control commands over Redis to whichever worker holds the run lease makes stop, pause and resume uniform across launch, user resume and restart auto-resume. The v3.0 resume spine itself is kept wholesale - the kernel-computed cursor with content-addressed task identity, gate re-entry with all five actions live post-restart, clarify replay without re-generation, and resume-from-failed - all live-proven on Bedrock; the target re-homes the wake-up signals, not the machinery. The intent is durable before anything is signalled, and the UI repaints only on the state actually reached — fixing the cancel-at-clarify screen that today keeps showing Clarifying. Pause is net new; no pause command exists today.
The agent-facing contract is unchanged. write_file / edit_file / read_file / ls / glob / grep against a per-run tree with traversal containment (sandbox.py:79) stay exactly as they are. What changes is where the tree lives (task-local ephemeral storage - fast for the many-small-file agent loop; a replacement task restores from the checkpoint) and that it is checkpointed to S3 at step boundaries, so a run can resume on a different worker or after a deploy. Cleanup becomes explicit at run end instead of relying solely on the 7-day TTL sweep (RunSandbox.cleanup() has no production caller today, sandbox.py:152).
Two additions to a path that otherwise works. Provider selection, 600 s read timeout, adaptive retries and the model fallback chain (model_factory.py:104, engine.py:3830) are kept. Added: a per-tenant token and concurrency lease before invoke, so one tenant cannot starve another (today there is no admission control at all, run_commands.py:1779); and invocation through a VPC endpoint (already present on the instance today, compute/main.tf:85; preserved per tenant plane). Prompt caching is configured (BEDROCK_PROMPT_CACHE_ENABLED default true) but has never been observed to register cache reads — that is a Phase 0 measurement task, and at 5–21M tokens per prototype build it is the single largest cost lever in the system.
Where a generic target would over-specify us. The shipped prototype deliverable is a single HTML file rendered in a browser iframe — no container is involved, and none is added. The container preview tier applies to app_builder output only. The real, urgent issue on this path is different: the prototype and deck previews frame model-generated HTML with sandbox="allow-scripts allow-same-origin" (PrototypePreview.tsx:611, PPTPreview.tsx:234), which does not isolate the framed document from our origin — a token-theft primitive given the JWT sits in localStorage. Target: serve all model-generated previews from an isolated origin, and make the sandbox policy uniform across the three renderers.
Keep the default, fix the sharp edge. The compiler injects audit_logger and secret_scan into every step that omits a hooks: key, and no manifest declares one, so both hooks already fire on every step of every workflow (compiler.py:401). The audit trail (gate_events, hook_runs, exec_runs, validation_results) already carries tenancy keys. Two fixes: a secret_scan block on before_write currently halts the deliverable write and emits no stream event (engine.py:3999) — it will emit a visible blocked event; and hook_run events currently bypass the seq/persist chokepoint entirely (kernel_services.py:387) — they will go through it, so audits replay like everything else.
Decision 4 (v2) — tiered tenancy. Pooled is the default tier; the control plane stays pooled and shared; everything that touches tenant data — Aurora, Redis, S3, KMS key, ECS services, sandboxes — comes from one Terraform tenant-plane module instantiated per tenant. Deploying into a customer account is a deploy of the same module, not a rebuild, which is the requirement that pays for the packaging work. Three schema gaps must close first: workflow_runs.owner_id / workspace_id are nullable (workflow.py:58), workflow_memory has no workspace key at all (workflow_memory.py:23), and scope is stamped only mid-engine rather than at INSERT (engine.py:1331), which today makes a freshly launched run's own SSE attach transiently 404.
The Cursor model, which is a stated requirement. The frontend, identity, entitlement and workflow catalogue stay in the Velocity control plane and are centrally upgraded. Everything that touches customer data — runtime, database, artifacts, sandboxes, keys, audit, Bedrock — runs inside the customer's own AWS account, reached over PrivateLink. Source code and generated artefacts never leave their VPC; only run metadata and stream events come back. The connector enforces local guardrails and quotas (for example, a ceiling on concurrent generations) so the customer plane is protected even from our control plane. It is the same tenant-plane Terraform module, pointed at a different account.
Replaces irreversible startup failure with bounded, observable recovery. Today a restart scan writes status='failed' to any non-terminal run without durable rows and emits no event (engine.py:5519), so an attached client shows the run mid-flight forever (useRunStream.ts:399); a parked waiting_for_user run with no derivable gate has no driver and no resume path (engine.py:5412); and there is no cross-process resume lock (engine.py:7576). On the target a dead worker's lease expires, a reaper marks the run reclaimable, a replacement claims it and resumes from the last completed step using the existing resume-offset computation (engine.py:7645). Every transition emits an event; repeated failure routes to a DLQ instead of an infinite retry.

The rule that makes scale-out possible: memory and cache are never sources of truth. This rule must be established, not maintained — today it is broken in six places, all authoritative in process memory: the per-run SSE queue, the driver task handle, the cancel signal, every human-gate and clarify wake-up, the live execution context, and the run state machine's state dict. Anything needed to resume, revise, chain, answer a status question or replay a stream must survive process replacement. Closing those six is the re-platform.
Two housekeeping items become urgent before per-tenant Aurora multiplies their cost. run_events grows unbounded — one row per streamed LLM chunk, no TTL, no partitioning, only a per-run delete cascade (engine.py:1032, runs.py:549). And the four LangGraph checkpoint tables are outside Alembic and never pruned while every task, retry, redo and fan-out worker mints a new thread. Both get a retention policy in the data migration plan below.

What this deployment model deliberately is NOT. It is not one container per agent: the 86 agents are AGENT.md markdown files loaded as runtime configuration into one deepagents graph inside a worker process (agents/prompts/*/AGENT.md, factory.py:186). They are not services, and making them services would add a network hop and a cold start to every reasoning step for no isolation benefit, because agents in one run share that run's context by design. It is not one container per tool command — a run reuses its warm working tree rather than paying a cold start on every ls. And it is not one process that must survive three days — the durable task graph exists precisely so no single process has to. What scales independently is the seven roles above, nothing finer-grained.
What this replaces. Today: one EC2 instance per environment in a single AZ, nginx and Postgres native on the host beside two containers, one uvicorn process, no ASG, no load balancer, no managed database, no standby (compute/main.tf:72, docker-entrypoint.sh:24) — and production served on a nip.io wildcard-DNS hostname with no Route 53 record and no ACM certificate (prod.tfvars:23). Instance loss is total environment loss. That single instance is also the only reason the six in-memory registries have been survivable until now.

A three-day build, end to end

A multi-day build is not a sequence diagram — it is a timeline that survives events. One 500-task app_builder run across three days, with a deploy, a backend restart, a human gate, a throttling episode and a reconnect happening during it, and what the user sees at each moment.

Why this board exists. Read the top lane alone: at every moment the user sees an honest, current state — including while a deploy rolls, while Bedrock throttles, and after a worker dies overnight. Each of those three events is fatal today: a deploy replaces the process that holds every run; the restart scan writes status='failed' with no event (engine.py:5519), so a reconnecting client replays nothing and shows the run mid-flight forever; and a throttle that outlives the model fallback chain fails the step permanently because no task-level retry exists (engine.py:6557). The durable task graph is what turns all three into non-events, which is the clearest justification for building it.
What is being demonstrated per event. The deploy (T4) drains and checkpoints, and version pinning keeps the run on the engine and manifest versions it started with (see the environments section). The overnight gate (T5–T6) is a durable row, so the approval from a phone the next morning lands on any web task and wakes the owning worker over the control channel. The throttle (T7) holds tasks in ready rather than failing them; the quota lease is what stops a retry storm. The worker loss (T8) is detected by lease expiry, and a replacement claims the run and remounts the tree from the last checkpoint. The reconnect (T9) replays by seq from the durable log exactly as it does today — the one mechanism in this timeline that already works.

Rejected alternatives

What was considered and set aside, with the reason and the trigger that would reopen it. Recorded so the next review does not re-litigate from scratch.

REJECTEDTemporal (or another durable-execution engine) instead of a custom task graph

The honest version of this trade-off, revisited now that a durable task graph is locked for v1. A large fraction of what Phase 3 builds — durable task state, leases, heartbeats, bounded retries, a DLQ, worker crash recovery — is exactly what Temporal provides off the shelf, battle-tested. Choosing to build it ourselves means owning the correctness of leasing and scheduling code forever. That cost is real and is not being waved away.

Why it is still rejected for v1. (1) The unit being orchestrated is not a free function: it is a step of the existing ExecutionEngine, a streaming async generator with mid-step human gates, cooperative cancel and an event chokepoint. Porting that into Temporal workflows/activities either wraps the kernel awkwardly (activities that stream events sideways into our own transport anyway) or restructures it — and restructuring the kernel is the one thing this programme forbids. (2) The scheduler we need is deliberately small because six of its seven concerns already exist in this codebase (parsers, strategies, isolation modes, merge strategies, audit tables); the genuinely new code is task rows plus a dispatch loop. (3) Temporal adds an operational surface (cluster or paid cloud, a new failure domain, a new programming model for the team) inside every tenant plane and every customer account — multiplied by decision 4 (v2). (4) The event history that Temporal would keep is redundant with the run_events log that the product already depends on for replay.

Reopen if: scheduler/lease correctness defects consume more than a few engineer-weeks after Phase 3 ships, or cross-region orchestration or saga-style compensation appears on the roadmap. The task-row schema deliberately mirrors Temporal's concepts (attempt, lease, heartbeat) so a later port is a backend swap, not a redesign.

REJECTEDOne container per agent

An agent is an AGENT.md markdown file loaded as configuration into a deepagents graph (factory.py:186) — not a process. The 86 agents in one run share the run's context, sandbox and checkpointer by design. Containerising them converts every reasoning step into a network hop plus a cold start, adds 86 deployables to version, and buys no isolation, because the trust boundary is the run (whose code execution is already isolated at the sandbox), not the agent. The product owner has also rejected this directly. Reopen if: a capability requires per-agent resource isolation (e.g. an agent that must run untrusted plugins in-process) — none exists today.

REJECTEDEKS instead of ECS Fargate

The workload is seven long-running service roles from one image plus ephemeral preview tasks — squarely inside Fargate's envelope. EKS would add cluster lifecycle, upgrade cadence, node/pod security posture and a skills requirement, multiplied by every tenant plane and every customer account under decisions 3 and 4. Locked decision 1 chose Fargate. Reopen if: a customer mandates Kubernetes in their account, or sandbox isolation requirements outgrow Fargate task boundaries (e.g. microVM-per-task control).

REVISED (v2)Identity: the OIDC broker moves in scope

The existing bcrypt + JWT path works and is verified; the defects on it are a missing refresh endpoint and a 24 h token, both cheap to fix in place. Migrating credential storage to Cognito now would spend a phase on undifferentiated work while the frontend contract churns. Decision 2 (v2): fix refresh, shorten the token, and put an adapter behind get_current_user so Cognito or a customer IdP is a later slot-in that touches none of the 20 routers. SSO is deferred, not cancelled — enterprise deals will force it, and the adapter is the preparation. v2 revision: the lock is removed; the broker is Amazon Cognito (one user pool per control plane; per-tenant IdP federation via SAML/OIDC; hosted UI acceptable for v1; direct OIDC only if Cognito's federation limits bite) and it lands with the control plane in Phase 4 — per-tenant IdP federation, SCIM-ready provisioning, MFA via the IdP; invite/reset/tenant-admin flows land in Phase 1. The internal contract the 20 routers verify is unchanged, so this stays an edge swap, not an app change.

REVISED (v2)Tenancy: tiered — pooled default, isolation as a tier

Pooled is roughly 10x cheaper per tenant (see the cost model) and is the industry default at this scale. It was still set aside for v1 (decision 4 (v2)) because: the customer-hosted requirement forces the tenant-plane Terraform module to exist anyway, and per-tenant SaaS is then the same module pointed at our account; physical isolation is the strongest possible answer to the enterprise data-residency and blast-radius questions this product will face; and the as-is tenancy enforcement is not yet strong enough to bet a pooled plane on (nullable keys, an unscoped launch window, one table with no tenant key at all). The schema work in Phase 1 deliberately makes a pooled tier possible later without a redesign. Reopen when: a self-serve or low-ARPU tier is planned — the cost cliff in the cost model is the deciding number. v2 revision: the lock is removed and the cliff decided it — pooled becomes the default tier (row-level isolation on NOT NULL keys + ScopedStore), with dedicated planes (tier 2) and customer-hosted (tier 3) from the same module on contractual demand. Nothing in the plane module is wasted; tiers 2-3 require it regardless.

REJECTEDKeeping EC2 with an autoscaling group instead of ECS

An ASG of the current image does not help: the application is single-process by construction, so a second instance silently breaks gates, cancel and live streams rather than sharing load (engine.py:7573). Fixing that requires exactly the Redis/Aurora externalisation this document describes — after which self-managed EC2 retains only its costs: host nginx and Postgres to operate, AMI patching (today's instance auto-reboots at 04:00 with runs in flight), capacity planning per instance, and none of Fargate's task-scoped IAM. Reopen if: sustained-load economics at large scale favour reserved EC2 capacity for the worker pool — ECS on EC2 capacity providers is the path then, not a return to one box.

REJECTED (in revision)Redis Streams as the dispatch queue

The first draft used Redis Streams consumer groups for dispatch with leases in Aurora — two overlapping coordination mechanisms with a consistency seam between them (a job visible in the stream before its row commits, or vice versa). Revised to an Aurora-native queue (SELECT ... FOR UPDATE SKIP LOCKED) with Redis reduced to wake-up nudges, fan-out and quota counters. Rationale: the design's own rule is that only Aurora is truth; SKIP LOCKED is the standard Postgres job-queue pattern; at 200 users the polling load is trivial; the scheduler stops needing leader election; and a dual-write bug class disappears. Reopen if: dispatch volume ever makes Aurora polling material — the claim loop is the only code that would change.

REVISED (v2)The freeze-forever contracts

Two standing constraints functioned as unexamined locks and are replaced with disciplined exits. (1) The SSE wire format: frozen for v1 clients, but since we own both ends, a negotiated contract v2 (Phase 5) retires the dead event types and moves prompt text out of the durable log — versioned conformance tests replace freeze-forever. (2) Additive-only migrations: additive within a release cycle, with contraction allowed only in a dedicated compaction release under the advisory-locked migrate task. Alongside these, the deepagents mandate becomes a pinned default with a CI conformance test, and the model provider becomes per-plane configuration rather than a global switch. Reopen if: a third-party client ever consumes the SSE stream — then v1 freezes for real.

Operational and security requirements

The standing requirements the target must satisfy, with the as-is condition each one corrects.

Network and execution isolation
Private subnets, no public IPs on runtime or execution tasks, task-scoped IAM roles, controlled egress, VPC endpoints for Bedrock, S3, ECR, Secrets and Logs. Code execution and previews run in dedicated tasks with no route to the application database and an egress allowlist; CPU, memory, disk and runtime limits with automatic termination.

Carried over from the as-is and closed explicitly, not assumed: LLM-generated Node code spawned by the PPTX exporter can reach the instance metadata service from inside the backend container, and the bootstrap records all five candidate mitigations as rejected (bootstrap-ec2.sh:360-478). On Fargate the equivalent risk is the task credential endpoint; the sandbox task's network policy blocks link-local addresses and the verification suite carries an in-sandbox probe that must fail.
Content isolation for model-generated output
All model-generated previews (prototype HTML, deck HTML, app previews) are served from an isolated origin so that same-origin access grants nothing, with one uniform sandbox policy across the three renderers. Today two of the three use sandbox="allow-scripts allow-same-origin" (PrototypePreview.tsx:611, PPTPreview.tsx:234) against the app origin while the bearer token sits in localStorage — the combination this requirement exists to eliminate.
Secrets and keys
Per-tenant CMK for data at rest, envelope encryption for stored credentials, and a re-encryption path so key rotation is an operation rather than an outage. Stop deriving the Fernet key from the JWT signing SECRET_KEY (crypto.py:29) — today rotating the signing key would brick every stored PAT and MCP credential. Stop passing the GitHub PAT in child-process argv (handoff_github.py:225). Signing keys rotate; API keys carry an expiry; secrets live in Secrets Manager with per-role access, not in a host-composed env file.
Observability
Correlation identifiers (tenant, session, run, step, agent invocation, task, sandbox) on every log record and span; structured JSON logs at INFO; a global exception handler returning typed, renderable errors (today there is none, main.py:245); distributed traces across web → worker → model; per-tenant cost attribution; and alarms that are proven to fire — the as-is ships an alarm on a metric nothing publishes (monitoring/main.tf:727) and another on a transport that no longer exists.
Backup and recovery
Aurora Multi-AZ with PITR (replacing an hourly logical dump and an RPO of up to one hour), S3 versioning and lifecycle for artifacts, checkpoints and the event archive, immutable audit retention, and restoration procedures that are rehearsed — including the sandbox-tree restore path, since today run sandboxes live on an unbacked-up root volume with delete_on_termination=true. Cross-region DR only for contracted tiers. Every RPO/RTO figure is validated by game-day before appearing in a contract.
Upgrade safety
Version-pinned releases (image digest + manifest/agent bundle hash) so an active run keeps the versions it started with; migrations as a gated, advisory-locked pre-deploy task, never on container start (docker-entrypoint.sh:22); additive-only schema changes as a standing rule; rolling deploys that drain and checkpoint instead of terminating work in flight; and no unattended host reboots with runs live — today unattended-upgrades reboots the single host at 04:00 with no drain (bootstrap-ec2.sh:163).
