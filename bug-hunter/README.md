# bug-hunter/

Everything the autonomous bug hunt writes lives here. Nothing else writes to this folder, and
the hunt writes nowhere else — no application source, no test files, no `.knowledge/` cards.

Agents live in `.claude/agents/` — `0-orchestrator` is the only one you talk to; it dispatches
`1a-page-hunter`, `1b-flow-hunter`, `2-validator`, `3-analyzer`, `4-test-writer`, `5-fixer`,
`6-verifier` and `7-closer`. See `WORKFLOW.md`.

## Layout

Four real subdirectories — `tools/`, `docs/`, `evidence/`, `reports/`. Everything else sits at
the top level, so what you open is separate from what executes. The `← labels` on the right are
groupings, not paths.

```
bug-hunter/
├── README.md              this file — the storage contract          ← docs
├── WORKFLOW.md            the stages, the bug lifecycle, who does what
│
├── ledger.md              THE LEDGER — append-only, one per bug     ← data
├── ledger-index.md        the lookup table over it (generated by report.py)
├── ledger.lock/           mkdir write lock (transient; absent when idle)
├── hunt-state.md          run state + accumulated hunt knowledge
├── velocity.json          the target definition — routes, selectors, quirks
│
├── tools/                 runs, not read                            ← tooling
│   ├── report.py          build the HTML report + regenerate ledger-index.md
│   ├── lane.js            per-lane isolated Chrome (own port, own profile)
│   ├── state.py           update hunt-state page rows
│   └── watch.sh           hunt budget watchdog
│
├── docs/
│   └── bug_tracker.docx   the original design document
├── reports/                                                          ← output
│   ├── velocity-bug-report.html   shareable, self-contained
│   └── <UTC>-<phase>.md           one per run
└── evidence/
    └── <page-slug>/               one folder per page, e.g. settings-profile
        ├── <BUG-ID>/              one folder per FILED bug
        │   ├── 01-before.png
        │   ├── 02-failure.png
        │   ├── 03-<detail>.png    optional further states
        │   ├── console.log        optional — only when it carries the diagnosis
        │   ├── network.log        optional — failed/unexpected requests only
        │   └── notes.md           optional — longer repro detail
        └── _scratch/              disposable exploration shots; safe to delete
```

**Standing instructions live in the agent definitions**, not here. Anything run-specific —
credential status, entries pending reconciliation, the bug classes established so far — is in
`hunt-state.md`. The split is deliberate: a standing doc carrying dated facts goes stale and
starts lying to whoever reads it next.

## `velocity.json` — we own this copy

The target definition every UI-driving agent reads before its first browser action: 39 routes,
32 selectors, 25 quirks, 20 recipes, and the seeded QA credentials.

**This repo's copy is canonical for the hunt.** It is committed, so it is versioned with the
branch, reviewable in a diff, and reachable by a relative path — no `/Users/<someone>` baked
into six agent files.

Upstream is the `ba-browser` skill's copy, which interactive browser sessions keep improving:

```sh
# pull upstream improvements in
cp ~/.agents/skills/ba-browser/definitions/velocity.json bug-hunter/velocity.json

# push a hunt's discoveries back out
cp bug-hunter/velocity.json ~/.agents/skills/ba-browser/definitions/velocity.json
```

Both directions are **manual and deliberate** — diff before you copy either way. Nothing syncs
automatically, because a definition changing underneath a running hunt is its own class of bug.

Workers never write to it. A worker that learns a new selector, route or quirk **reports** it;
`0-orchestrator` merges it here.

## Rules

- **`ledger.md` is the single source of truth.** One file, append-only. Workers read it
  whole before touching the browser and re-read it under the lock before appending. Never
  overwrite it, never split it, never rewrite an existing entry.
- **A bug folder is created only when a bug is actually filed.** `<BUG-ID>` matches the ledger
  section heading exactly, so a ledger entry and its evidence are one lookup apart.
- **Screenshots are ordinal-prefixed** (`01-`, `02-`, …) so they sort in reproduction order.
  Slug the rest: `01-before.png`, `02-failure.png`, `03-after-reload-still-broken.png`.
- **`_scratch/` is disposable.** Exploration shots land there; the ones that prove a bug get
  moved into its `<BUG-ID>/` folder. A round that finds nothing may leave scratch behind — it is
  safe to delete at any time and nothing may depend on it persisting.
- **Logs are excerpts, not dumps.** `console.log` / `network.log` carry only the lines that help
  reproduce or diagnose. Never paste a full console transcript.
- **`ledger.lock/` is a directory**, acquired with `mkdir` and released with `rmdir`. If it
  is present, a worker is mid-write — wait, do not delete it.
- **Page slugs are the route with slashes flattened**: `/settings/profile` → `settings-profile`,
  `/runs/<id>/steps` → `runs-id-steps`, `/` never appears (bare `/` is not a page here).

## Ledger entry shape

```markdown
## BUG-<UTC timestamp>-<page-slug> — <short title>

- **Page:** <page name>
- **Route:** <route or URL>
- **Severity:** Critical | High | Medium | Low
- **Status:** Open
- **Found at:** <UTC timestamp>
- **Found by:** <worker identifier, e.g. bug-settings-profile-r7>
- **Fingerprint:** `<route>|<component>|<trigger>|<symptom>`
- **Evidence:** `bug-hunter/evidence/<page-slug>/<BUG-ID>/`

### Summary
### Reproduction
### Expected
### Actual
### Evidence
### Browser Signals
```

`Status` is the pipeline's state, and the only thing that tells a phase what to pick up:

```
Open ─► CONFIRMED ─► ANALYZED ─► TESTED ─► FIXED ─► CLOSED
  │         ▲                                 └─► REOPENED ─┐
  ├─► FLAKY ┘                                               │
  ├─► UNREPRODUCIBLE                                        └─► back to FIXED
  └─► DUPLICATE
```

A hunter only ever writes `Open` — the hunt observes and documents, it does not fix. Every later
status is written by the phase that earned it, and `WONTFIX` is never set by an agent: candidates
go to `wontfix-candidates.md` and a human rules on them. Full lifecycle in `WORKFLOW.md`.
