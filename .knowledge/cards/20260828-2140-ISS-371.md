## Sibling of ISS-275 (INFERRED — not yet reproduced)

Filed while analyzing `BUG-20260828-003800-workflows-new` (ComposerPage's Back button
silently discards unsaved workflow name/agents, root card [ISS-275](20260828-1855-ISS-275.md)).
`IdeaInputPage` — the pre-composer "describe your idea" screen mounted at
`mainView === "input"` — is wired through the exact same shared, ungated navigation
handler and holds an analogous amount of not-yet-persisted user input. This has NOT
been independently reproduced in the browser; it is derived from reading the code path
and is a lead, not a confirmed defect.

## Why the root cause implies this

`ComposerPage`'s Back button calls `onBack` directly with no dirty-check
(`frontend/src/components/workflow/composer/ComposerPage.tsx:979`), and `onBack` is the
shared `handleBackNav` (`frontend/src/components/layout/DashboardLayout.tsx:1701-1712`),
which unconditionally does `router.back()` / `router.push(routes.home())` with zero
knowledge of any mounted child's own uncommitted state — it only clears ITS OWN
cross-cutting state (questionnaire, pending pipeline run) via `onResetPipeline()`.

`handleBackNav` is passed as `onBack` to exactly 5 call sites in `DashboardLayout.tsx`
(confirmed via `grep -rn "onBack=" frontend/src`, excluding `*.test.tsx`):
`WorkflowHistory` (:2767), `AccountSettings` (:2849), `AnalyticsPage` (:2863),
`IdeaInputPage` (:2893), `ComposerPage` (:2946). `IdeaInputPage` wires its own Back
button the identical way — `onClick={onBack}`, no gate — at
`frontend/src/components/workflow/IdeaInputPage.tsx:1577`.

`IdeaInputPage` holds real, not-yet-submitted user input in local `useState`, seeded
from `initial*` props and mutated as the user works, all confirmed present in the file:
- `ideaInput` (the typed brief) — `IdeaInputPage.tsx:855`
- `pipelineAgents` (the agent selections built up before "Start"/"Save") —
  `IdeaInputPage.tsx:892`
- `attachedFiles` / `attachedFileContents` / `attachedImages` — `IdeaInputPage.tsx:477,
  480, 484`

None of this is persisted until the user explicitly runs or saves. This is the same
shape of loss as the reported composer bug (typed content + selections, silently
dropped on Back), just one screen earlier in the same launch flow.

## Expected vs Actual (to be confirmed by reproduction)

**Expected:** Leaving `/workflows/new`'s idea-input step (or wherever `mainView ===
"input"` is reached) via its own Back control while `ideaInput` is non-empty or
`pipelineAgents` is non-empty should prompt for confirmation before discarding, same as
the fix expected for ISS-275.

**Actual (inferred, unverified):** Clicking Back should silently navigate away and
discard `ideaInput`/`pipelineAgents`/attachments with no warning, by the same mechanism
as ISS-275.

## What would settle it

Reproduce in the browser: navigate to the idea-input screen, type a brief and/or add an
agent, click the header Back button (`aria-label="Back to dashboard"`,
`IdeaInputPage.tsx:1578`), and confirm the content is gone with no confirmation prompt
shown.
