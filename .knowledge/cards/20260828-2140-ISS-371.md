## Why the root cause implies this

`ComposerPage`'s Back button calls `onBack` directly with no dirty-check
(`frontend/src/components/workflow/composer/ComposerPage.tsx:979`), and `onBack` is the
shared `handleBackNav` (`frontend/src/components/layout/DashboardLayout.tsx:1701-1712`),
which unconditionally does `router.back()` / `router.push(routes.home())` with zero
knowledge of any mounted child's own uncommitted state — it only clears ITS OWN
cross-cutting state (questionnaire, pending pipeline run) via `onResetPipeline()`.

`handleBackNav` is passed as `onBack` to exactly 5 call sites in `DashboardLayout.tsx`
(confirmed via `grep -rn "onBack=" frontend/src`, excluding `*.test.tsx`):
`WorkflowHistory` (:2767), `AccountSettings` (:2849), `AnalyticsPage` (:2863),
`IdeaInputPage` (:2893), `ComposerPage` (:2946). `IdeaInputPage` wires its own Back
button the identical way — `onClick={onBack}`, no gate — at
`frontend/src/components/workflow/IdeaInputPage.tsx:1577`.

`IdeaInputPage` holds real, not-yet-submitted user input in local `useState`, seeded
from `initial*` props and mutated as the user works, all confirmed present in the file:
- `ideaInput` (the typed brief) — `IdeaInputPage.tsx:855`
- `pipelineAgents` (the agent selections built up before "Start"/"Save") —
  `IdeaInputPage.tsx:892`
- `attachedFiles` / `attachedFileContents` / `attachedImages` — `IdeaInputPage.tsx:477,
  480, 484`

None of this is persisted until the user explicitly runs or saves. This is the same
shape of loss as the reported composer bug (typed content + selections, silently
dropped on Back), just one screen earlier in the same launch flow.

### Root cause — CONFIRMED

One mechanism. [FIX-352](20260828-2346-FIX-352.md) built the Back guard in the shared handler and
wired exactly one page into it. The per-page wiring it explicitly deferred for this page ("each still
needs its own one-line wiring plus its own definition of dirty") was never done.

- **The guard (works, unchanged).** `DashboardLayout.tsx:1847` `const hasUnsavedWork = useRef(false)`;
  `:1848-1850` `handleUnsavedChange` writes it; `:1875-1880` `handleBackNav` runs
  `if (hasUnsavedWork.current) { setConfirmingBackNav(true); return; }` and otherwise clears the
  questionnaire state and calls `goBackOr` (`:1881-1888`). The in-app dialog is `:3478-3517`.
- **Page side.** `IdeaInputPageProps` (`IdeaInputPage.tsx:775-777`) declares `onBack` and no
  `onUnsavedChange`. The Back button is a bare `onClick={onBack}` (`:1874`, `aria-label="Back to
  dashboard"` at `:1875`). Nothing in the file reports unsaved state.
- **Mount side.** The IdeaInputPage mount (`DashboardLayout.tsx:3159-3177`) passes
  `onBack={handleBackNav}` (`:3161`) and no `onUnsavedChange`. The ComposerPage mount passes it
  (`:3215`). That is the only `onUnsavedChange={...}` in the frontend: outside tests, `grep -rn
  onUnsavedChange frontend/src` returns `DashboardLayout.tsx:3215` and
  `ComposerPage.tsx:190,227,377-379` and nothing else.
- **Net.** Nothing sets `hasUnsavedWork.current = true` while IdeaInputPage is mounted, so
  `handleBackNav` always takes the unguarded branch. That is the validator's 3/3 (zero dialogs).

State lost on Back: `ideaInput` (`:958`), `pipelineAgents` (`:995-1006`), the attachments held by
`useBriefAttachments()` (`:507-639`), and the Advanced selections, overrides, review gates and design
pick.

Route correction: the ledger row says `/workflows/new`, which is ComposerPage (already guarded).
IdeaInputPage mounts at `/create/user-stories` and the other non-wizard `/create/<type>` routes.

### Fix — where it belongs

Not in the guard: it is correct, and FIX-352 locked it there ("the dirty-check lives in
handleBackNav ... never a per-page confirm() in each onClick"). Two touch points, frontend only:

1. `IdeaInputPage.tsx`: an optional prop `onUnsavedChange?: (dirty: boolean) => void` (`:775-777`,
   destructured at `:956`) and one reporting effect that mirrors `ComposerPage.tsx:371-379`.
2. `DashboardLayout.tsx`: `onUnsavedChange={handleUnsavedChange}` beside `onBack={handleBackNav}` in
   the mount at `:3159-3177`.

### Verdict on the agreed minimal fix (BUGS.md notes): ACCEPT the shape, OVERRULE two details

Accepted: the prop, the effect, the one-line wiring, no change to the guard, no native confirm.
Overruled, because as written they ship a regression.

**(a) A baseline captured at the first effect run is wrong for this page.** The mechanism is
CONFIRMED; the visible effect is INFERRED until a test drives it.

`pipelineAgents` is not stable after mount. The effect at `IdeaInputPage.tsx:1343-1410` calls
`setPipelineAgents(...)` with no user action at `:1363`, `:1373` and `:1404`, and re-runs on
`[LIBRARY_AGENTS, effectiveType, initialAgentIds, ALL_LIBRARY_AGENTS, manifestAgents, showOverride,
overrideAgents]`:

- The agent library is async. `useAgentLibrary.ts:19-20`: "The Redux store initializes with empty
  arrays and is populated when the API fetch completes". On a cold load the lazy initialiser
  (`:995-1006`) yields `[]` and the effect fills the roster in afterwards.
- A composed, saved or dynamic workflow has no AGENT.md-backed library roster (comment `:1378-1382`),
  so the roster is `[]` at mount and becomes the manifest's steps when `getWorkflowDetail` resolves
  (`:1403`).
- A saved override replaces the roster when `overrideAgents` lands (`:1404-1408`).

Each of these moves the roster after a first-commit baseline was taken, so the page would be born
dirty and Back would open "Leave without saving?" on an untouched page. ComposerPage hit the same
race and re-baselines at its re-seed (`ComposerPage.tsx:350-353`: "the one taken at mount was read
before this ran and would read as a user edit").

Suggested shape: two independent baselines held in state, so a programmatic seed can never absorb a
typed brief (or the reverse), and `dirty` derived in render so the effect stays lint-clean.

```tsx
// sketch, not a patch
const rosterKey = (a: AgentDef[]) => a.map((x) => x.id).join(",");
const [briefBase, setBriefBase] = useState(initialInput ?? "");              // as seeded / last saved
const [rosterBase, setRosterBase] = useState(() => rosterKey(pipelineAgents));
// at :1363, :1373, :1404: setRosterBase(rosterKey(next)) next to setPipelineAgents(next)
// after each successful save: setBriefBase(ideaInput); setRosterBase(rosterKey(pipelineAgents))
const dirty = ideaInput !== briefBase || rosterKey(pipelineAgents) !== rosterBase || hasAttachments;
useEffect(() => { onUnsavedChange?.(dirty); return () => onUnsavedChange?.(false); }, [dirty, onUnsavedChange]);
```

Do not null the baseline to mean "recapture on the next change": if the re-seed leaves the snapshot
unchanged the null survives, and the user's first edit is adopted as the baseline, which is the
original silent discard again. A snapshot diff also fails safe: a seed site added later over-prompts
instead of losing work, whereas flagging only user-driven edits fails the other way. `ideaInput` needs
no special care: it is written only by the textarea (`:1915`) and dictation (`:1518`) and is never
re-seeded from `initialInput`, so `useState(initialInput ?? "")` (`:958`) is a valid baseline.

**(b) "The cleanup resets the flag on unmount, so running or saving does not leave a stale dirty
state" is true for Run and false for Save.** CONFIRMED. Run unmounts the page (comment
`:1549-1555`). Save does not: `handleSaveWorkflow` (`:1665-1701`) and `handleSaveAsOverride`
(`:1743-1785`) end in `setSavedConfirm(true)` and the page stays mounted, so a just-saved composition
would still say "You have unsaved changes" on Back. ComposerPage re-baselines after a successful save
(FIX-352, "again after a successful save"); do the same on both save paths.

Also recommended, not in the agreed fix: count attachments (`briefAttachments.attachedFiles`,
`attachedImages`, `stagedUploads` non-empty) as dirty. This card's "Why the root cause implies this"
section lists them as lost state, only the user writes them so they need no rebaseline, and Save
does not persist them.

**Both fixes edit `DashboardLayout.tsx`**, at disjoint hunks (`:3117` and `:3159-3177`). Apply them in

shared hook yet: three inline effects are cheaper than a new file two fixes both depend on; extract

Reporter contract both fixes must meet (it follows from the guard's shape):

1. Report `false` at mount. Dirty is relative to a baseline, never "non-empty": a custom workflow
   legitimately starts with an empty brief and no agents, a built-in starts with a populated roster.
2. Return `() => onUnsavedChange?.(false)`. `hasUnsavedWork` is ONE ref for the whole layout
   (`:1847`), last writer wins, and `<AnimatePresence mode="sync">` (`:2956`) keeps the leaving page
   mounted for its exit animation, so its cleanup lands after the entering page's first report. That
   is safe only because every reporter starts at `false`.
3. Rebaseline whenever the page re-seeds or persists its own state.
4. Use the in-app dialog only, never `window.confirm` (S-19-17; the 2026-09-02 FIX-481 change
   removed the one FIX-352 had added).
