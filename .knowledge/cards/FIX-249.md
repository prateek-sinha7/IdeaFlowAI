## Description

The Concierge told a user the product "does not expose billing or token usage metrics" and referred them to support, for a number rendered inches away in the same viewport (ISS-148). Asked "how many tokens did this run use in total, and what did it cost?", it recited a false product limitation. Per the original investigation (run 5ecb990f-2c80-4752-a615-2bed3280387a chat_usage rows — not independently re-observed this session, Bedrock unreachable): the question was answered in a SINGLE bare model turn, 4,816 input tokens, 0 cache-read, ZERO tool calls, versus 9,937-12,781 input tokens with cache reads for tool-using sibling questions in the same session. Two independent, verified causes, both fixed. concierge.py:898 (pre-fix) forbade the model from exposing "token counts" in its RESPONSE RULES, paired with a :893-895 denial template ("say they are not available") written for internal identifiers that the model over-applied. Separately, _read_tools (:867-870, pre-fix) returned exactly 7 tools; none touched workflow_runs.token_usage, already-populated JSON (app/models/workflow.py:36, written at app/api/run_commands.py:2332-2354). A second instance of the same failure mode fired in the same investigation and was initially graded correct — asked what FILE the run produced, the Concierge gave the document TITLE, never workflow_runs.deliverable_filename, because ArtifactRef (app/models/artifact_ref.py) has no filename column for list_artifacts (concierge.py:792-801) to project; filed separately (ISS-149), deliberately not fixed here. Fix, both halves, inside concierge.py only. Half 1: a new no-parameter get_token_usage tool added after read_gate_history, reading the run via the EXISTING _safe_run(scoped_store, run_id) helper (no new ScopedStore method, no raw ORM; the tolerant app/api/analytics.py:66 _parse_token_usage was deliberately NOT reused — importing it would create an app.agents.chat -> app.api layering edge, so the in-file _agent_output_entries guarded-json.loads idiom is mirrored instead). Returns EXACTLY available/total_tokens/input_tokens/output_tokens/estimated_cost_usd — an EXACT key-set, not a subset, asserted by test — so cache read/write, model_id, and the uncached-counterfactual cost (all present in the same source blob) cannot become answerable by accident; deliberately deferred (ISS-149), not incidentally included. Degrades to {"available": false, "error": "..."} — never zeros — when the column is None (a legitimate state: the writer only persists it when total_input + total_output > 0) or the blob fails to parse; the error key is LOAD-BEARING, since the standing cross-owner security guard test_every_read_tool_denies_cross_owner accepts a denied/degraded result only if it is falsy, {}, carries a truthy error, or has agents_started == 0 — a bare {"available": false} would have turned that guard red. Half 2 (LOAD-BEARING — a tool alone would have fixed one question and left the failure MODE live for every other gap with no tool): removed token counts, from the forbidden list; added a new honesty rule — if no tool can answer, say so plainly ("I can't see that from here") and stop, never claim what the product does or does not support, never invent a reason, never redirect to billing/support; added one TOOLS routing line. model names deliberately left forbidden — a genuine open product question, surfaced not decided (ISS-149).

## Root cause

concierge.py:898's RESPONSE RULES literally forbade exposing "token counts", paired with a :893-895 denial template the model over-applied from the neighboring internal-identifiers rule — and no read tool existed that could have answered honestly even without that rule (_read_tools returned exactly 7 tools, none touching workflow_runs.token_usage).
