# ISS-701

**Register source:** `QA-PS-024` in root `LEDGER.md` / `BUGS.md`.

## What was wrong

A `degraded` pipeline run that has at least one agent left in `status: "error"`
(the normal, correct persisted state for a degraded outcome — it names which
agent(s) failed) shows **"Run failed"** in the Steps tab's main status summary
(`StepsOverviewSpine`), never "Run degraded". This is not a resume/live-race
condition: the run is fully terminal, `isRunning` is `false`, and
`pipelineState.failed` is `false` — only `pipelineState.degraded` is `true`.

Reproduced 3/3 on cold starts (fresh `/dashboard` -> deep link to
`/runs/353bb0af-590b-4acb-8fbb-6c280b39e192/steps`, click the Steps tab) on a
persisted `degraded` run whose `Validator` agent is in `error` status
(10/11 agents). All three cycles show the amber icon area rendering the RED
"Run failed" summary with "10 / 11 agents", not the amber "Run degraded"
seen on a sibling degraded run (`ab2d555e-fa45-47c7-90da-a9f1adaba98a`) whose
agents *all* completed without an `error` status.

**Named trigger:** a terminal `degraded` run whose `agents` array contains at
least one entry with `status === "error"`. When no agent carries `error`
status, the same degraded run correctly renders "Run degraded" — proving the
per-agent-status branch of the OR, not `pipelineState.degraded` itself, is
what flips the label.

## Root cause

`frontend/src/components/results/StepsOverviewSpine.tsx:408`:

```ts
const isRunning = pipelineState?.isRunning ?? false;
// ISS-317: a pipeline that is actively running is never "failed". Gate the
// derived flag on !isRunning so a leftover per-agent `error` status can never
// pin this panel on "Run failed" while the header reads "Running".
const failed = !isRunning && (pipelineState?.failed || agents.some(a => a.status === "error"));
```

and the label selection at line ~449-452:

```ts
const statusLabel = failed ? "Run failed" : isRunning ? "Running"
    : (pipelineState?.degraded) ? "Run degraded"
```

[ISS-317](20260828-1755-ISS-317.md) identified this exact OR'd derivation and
[FIX-379](20260829-0210-FIX-379.md) resolved it by adding the `!isRunning`
guard — but that guard only protects the case ISS-317 reproduced (a *resumed,
still-running* pipeline carrying a stale pre-resume `error` status forward).
It does nothing for a run that is genuinely terminal: `agents.some(a =>
a.status === "error")` is still evaluated and, for any degraded run with a
real (not stale) per-agent failure, is still `true`, so `failed` wins the
ternary over the correct `pipelineState?.degraded` branch that follows it.

The fix needs `failed` to come from `pipelineState?.failed` alone (matching
how `LaneRunHeader.tsx` derives its own failed/degraded distinction), not
from per-agent status at all — a degraded run legitimately has `error`-status
agents; that is what "degraded" *means*, not evidence the whole run failed.

## Side observation (not part of this card's verdict)

In the current codebase, `RunHeader.tsx` (top-of-page pill, fed by
`PreviewPanel.tsx`'s `headerFailed = terminalFailure && !isCancelledTerminal`,
where `terminalFailure` includes `pipelineState?.degraded`) and
`LaneRunHeader.tsx` (left-column badge, explicit comment: "degraded... shares
the failed token rather than get its own amber") **both** intentionally show
"Failed"/"Run failed" for a degraded run — this reads as a documented product
decision, not a bug. The original report (`QA-PS-024`) describes those two
surfaces as correctly showing "Degraded"; that is no longer accurate for this
codebase revision. Only `StepsOverviewSpine`'s label is inconsistent with
itself (varies by per-agent error status across otherwise-identical degraded
runs), which is the defect this card targets.
