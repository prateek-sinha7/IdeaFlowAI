## What was wrong

Bug QA-KB-017, validated 3/3 (`evidence/qa-kb-017/01..05`). Signed in as `basic@velocity.ai`, the
`POST /api/user-workflows` the canvas Save issues, carrying
`model_overrides={"epic-architect": "eu.anthropic.claude-opus-4-6-v1"}`, returned 201 and stored
the premium override. The analysis on [ISS-398](20260828-2106-ISS-398.md) then found the same
result through every door a model id enters by. Its siblings:

- [ISS-934](20261001-2231-ISS-934.md): `selections[agent].model`, the door the Canvas Model lever
  actually uses.
- [ISS-935](20261001-2231-ISS-935.md): manifest step models, plus the Case 3 launch, which skipped
  the override validator and forwarded the body maps unchecked.
- [ISS-936](20261001-2231-ISS-936.md): a premium `preferred_model` left over from before a
  downgrade, which every launch still used.

## Root cause (from the cards, re-checked before editing)

No ingress validator for a user-supplied model id knew the caller's tier.
`can_use_model` (`backend/app/core/entitlements.py:144`, [FIX-361](20260829-0029-FIX-361.md))
existed, but only `settings.py` called it, and only where the preference is written.

- `backend/app/api/run_engine.py:546-606` and `backend/app/api/user_workflows.py:348-383` are the
  two `_validate_model_overrides` copies. They take `(model_overrides, run_agent_ids)` and check
  catalog membership only.
- `backend/agents/workflows/selections.py:245` (`validate_selection_model_ids`) checks the
  catalog only. It sits under `agents.workflows`, which import-linter keeps away from `app`.
- Manifest models were never inspected. `_validated_manifest` (`user_workflows.py:138`) checks
  `instance_id`. The compiler records any string (`compiler.py:1404-1449`). At HEAD `024c03ef8`,
  `run_commands.py:3722-3733` skipped `_validate_model_overrides` for Case 3 on the claim that
  the compiler's trust checks were "a stricter, per-step equivalent". Those checks cover
  capabilities, not model ids.
- `preferred_model` was read raw at ten sites in `run_commands.py`, and none checked the tier.

Blast radius re-checked by grep before editing:

- Callers of `_validate_model_overrides`: `run_commands.py` launch, `user_workflows.py` create
  and PATCH.
- `preferred_model` readers: `run_commands.py` only, plus `settings.py`'s writer and getter.
- `_launch_run_core`, `_drive_launch_to_queue` and `_drive_revision_to_queue` read only `.id`
  and `.preferred_model` from their `user`.

## What changed, and why there

There is one gate, an app-layer helper, called from the three ingress points every door reaches:
create, PATCH and launch. The kernel, `ModelResolver`, the compiler and `selections.py` were not
touched (import-linter, SC-001).

1. `backend/app/api/run_engine.py:609` adds
   `_model_entitlement_error(tier, *, model_overrides, selections, manifest) -> (status, message) | None`.
   It collects every id from the three shapes. For a manifest that means the workflow-level
   `model`, each step's `model`, nested `subagents.steps` and each `fallback` list. It asks each
   id two questions:
   - Is it a known, user-allowed catalog id? If not, the answer is 422.
   - Does `can_use_model(tier, id)` allow it? If not, the answer is 403.

   `tier` has no default, so a caller that forgets it fails loudly instead of skipping the gate.
   The 403 versus 422 split follows FIX-361's locked constraint. The helper lives beside
   `_validate_model_overrides`, in the module both routers already treat as the home of the
   ingress validators.
2. `backend/app/api/user_workflows.py:747` (create): the gate runs after
   `_compile_selections_trust_user`, so the existing catalog messages for overrides and
   selections are unchanged, and before any row is written. `:951-967` (PATCH): the route now
   depends on `get_current_principal` (as create does) and gates right after `_owned`. A
   cross-owner row is therefore still 404, and nothing on the row changes before a denial.
3. `backend/app/api/run_commands.py:3769-3784` (launch): the gate sits after the Case 1/2
   validator block and outside the Case 3 skip, so it covers every case. It walks only
   user-authored sources: `model_overrides` (the row's map in Case 2), `body.selections`,
   `persisted_manifest` (Case 3, inline or the saved row) or `{"steps": _ov_steps}` (an enabled
   spec-016 override). `_ov_steps = None` is initialised at `:3288` because Case 3 never assigns
   it. Denials are `_reject("tier_not_entitled", ..., 403)`, or `invalid_model_override` with
   422 for an uncatalogued id, both before any mint. The skip comment (`:3743-3748`) is
   corrected. Reading the stored manifest at launch also closes the downgrade-after-save gap
   that the agreed minimal fix left out of scope.
4. `backend/app/api/run_commands.py:2604` adds `_entitled_user(user, tier)` for
   [ISS-936](20261001-2231-ISS-936.md). It returns `user`, or a
   `SimpleNamespace(id=user.id, preferred_model=None)` when the stored preference is a model the
   tier may no longer select. That is the same stand-in shape `run_trigger_workflow` already
   passes to `_launch_run_core`. All ten read sites now go through it:
   - `launch_run` (`:3784`, image guard `:3794`, core `:3871`)
   - `post_message` (`:1791`, `:1882`, revision driver `:2039`)
   - `_dispose_concierge_proposal` (`:1643`, classifier `:1685`/`:1698`, driver `:1757`)
   - `create_revision` (`:5635`, classifier `:5648`/`:5661`, driver `:5702`)

   The four driver reads (`model_id=` into `engine.execute` / `_handle_revision` and the
   terminal `model_id` column) read the user they are handed, so no driver or
   `_launch_run_core` signature changed. This keeps the signature-pin test
   `test_launch_run_core_is_plain_async_function_decoupled_from_fastapi` and the direct-driver
   tests unchanged.

### Beyond the analysis, stated explicitly

- **The workflow-level manifest `model` (resolver tier 4) is walked too.** ISS-398's door table
  listed only `steps[].model`. The resolver does not catalog-check tier 4
  (`model_policy.py:249-271`), so leaving it out would have left a 403 bypass through an inline
  manifest. Probe A covers it.
- **The catalog question runs on every collected id**, as ISS-935 asked. `can_use_model` passes
  unknown ids through by design, and the resolver trusts a tier-1 override outright. Without
  this check, a Case 3 body map carrying `us.anthropic.claude-opus-4-6-v1` (not in the catalog,
  geo-normalised to the eu Opus at run time) passed the tier gate. Probe B covers it.

### Deliberately not changed

- The two `_validate_model_overrides` copies stay as they are. Collapsing them is not needed
  because the gate is one shared helper (ISS-398 analysis, point 6).
- [ISS-937](20261001-2231-ISS-937.md) stays **open**. `settings.py` still calls
  `can_use_model(user.tier, ...)`. No failing test was written for it, and moving those routes to
  `get_current_principal` needs the settings test harnesses changed, which is not the fixer's
  call. The new gates read `effective_tier` as that card requires.
- No frontend changes. The Canvas Model lever still offers the whole catalog, so a basic account
  now gets the 403 reason ("This model requires Pro or higher...") on Save or Run. A locked
  option would be the [ISS-430](20260829-0029-ISS-430.md) pattern, which is out of scope. The
  DECIDE-02 comments in `AgentModelPicker.tsx` and `AgentsPopup.tsx` were not reconciled.
- Runs started through `run_trigger_workflow` never pass this gate. That residual is
  [ISS-946](20261002-0107-ISS-946.md).

### Policy note

The frozen `.planning/` archive records DECIDE-02 ("premium models selectable by all tiers",
Phase 22). This fix follows the later, in-code policy of [FIX-361](20260829-0029-FIX-361.md)
(`TIER_MODEL_COST_CLASSES["basic"] = {cheap, standard}`) and the bug's own Expected, as the
ISS-398 analysis did. If the owner still wants DECIDE-02 for per-agent models, this card is the
one to revert.
