## What was wrong

Register entry: `BUG-20260828-093400-library-skills-id-r2` in `bug-hunter/ledger.md`.

A skill's `content` is its `SKILL.md` body. Two surfaces showed it and neither parsed it:

- **`frontend/src/components/workflow/composer/AgentSkillsPicker.tsx:280-283`** — the `detailSkill`
  modal opened by the "View details" (Info) button placed `detailSkill.content` directly as the text
  of a bare `<pre>`. Every heading/list/emphasis marker showed as literal source characters
  (`dialog.querySelectorAll('h1,h2,h3,h4').length === 0`), confirmed live 3/3 on three different
  skills ([ISS-359](20260828-1918-ISS-359.md)).
- **`frontend/src/components/library/LibraryPage.tsx:205-218` + `:285-301`** — `SkillDetailModal`'s
  "Formatted content" section hand-rolled a line-splitter that recognized only a leading `# `/`## `
  heading line and `-`/`*`/numbered bullet prefixes, dropping the rest of each line into `<p>{text}</p>`
  verbatim. Inline `**bold**`, `` `code` ``, `[link](url)`, `_em_` and any `###`/`####` heading passed
  through as literal characters ([ISS-591](20260829-0114-ISS-591.md)).

## Root cause

`AgentSkillsPicker.tsx:280-283` — no markdown parsing step existed anywhere in that component. The
broken markup lives inside `AgentSkillsPicker` itself, not in anything a caller supplies, and the Info
button that opens the modal (`:208-216`) carries no `readOnly` gate — only the Add/Remove toggle does
(`:226`). So all three JSX mounts reached the identical broken render, not just the Canvas rail the
report named ([ISS-590](20260829-0113-ISS-590.md)); blast radius re-confirmed by grep before editing:

- `composer/CanvasConfigRail.tsx:468` (Canvas config rail — the reported path)
- `composer/AgentRow.tsx:267` (Composer Simple view)
- `workflow/AgentsPopup.tsx:870` (`AgentCapabilitiesModal`'s Skills tab), itself mounted from
  `library/LibraryPage.tsx:1009` (agent drawer, `readOnly=true`) and `workflow/AgentLibrary.tsx:349`
  ("Add agent" popup)

## What changed and why there

**New — `frontend/src/components/ui/SkillMarkdown.tsx`.** One `react-markdown` + `remark-gfm`
renderer with a token-styled `components` map (headings, paragraphs, lists, inline vs fenced code,
links, strong/em, blockquote, hr, GFM tables). `react-markdown` and `remark-gfm` were already
dependencies (`frontend/package.json:38,40`) and already the app's markdown path
(`preview/MarkdownPreview.tsx`, `chat/MessageBubble.tsx`, `results/SandboxTab.tsx`,
`results/artifactPreview.tsx`). It lives in `components/ui/` because its two consumers sit in
different trees (`components/workflow/composer/` and `components/library/`).

It carries `MarkdownPreview`'s WR-03 security invariant verbatim: **no `rehype-raw`, no rehypePlugins
of any kind**, so react-markdown's default escapes embedded raw HTML to literal text. Skill bodies
render inline and unsandboxed here, so parsing raw HTML would execute a skill's `<script>` in the
app's own origin.

**`AgentSkillsPicker.tsx:280-287`** — the `<pre>` is replaced by `<SkillMarkdown content={detailSkill.content} />`.
The fix is inside the shared component, so all three mounts (plus the two indirect
`AgentCapabilitiesModal` mounts) inherit it with **zero caller edits** — the alternative was four
copies of the same fix drifting apart.

**`LibraryPage.tsx`** — the section-splitting loop and its per-line JSX are deleted; the "Formatted
content" block is now `<SkillMarkdown content={skill.content} />`. Deleting the loop orphaned nothing
else (`Zap` is still imported and used at `:418` and `:672`). The separate "SKILL.md content" raw
`<pre>` block below it (with its own Copy button) is deliberate source view and is **untouched** — no
card asked for its removal, and `ISS-591`'s own evidence section names it as a legitimate fallback.

## Not fixed here

`LibraryPage.skillMarkdown.test.tsx`'s second assertion cannot pass without deleting that deliberate
raw-source block, so the app was NOT bent to it — see [ISS-605](20260829-0216-ISS-605.md).
`ISS-591` therefore stays `open`: the code change landed, its regression test cannot yet confirm it.

`frontend/src/components/workflow/SkillManager.tsx:258,269` also shows skill content unparsed, but
that is a skill *authoring* surface (textarea + source view) where raw source is correct. Out of
scope, not a defect, no card filed.
