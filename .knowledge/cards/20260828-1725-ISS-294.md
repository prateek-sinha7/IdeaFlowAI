## Relationship to the root bug

Sibling of [ISS-230](20260828-1805-ISS-230.md) — a second consumer with the same flaw.
ISS-230 characterizes the symptom as "switching tabs DROPS an established pin." This card
shows the pin may never be established at all, even on a genuine cold load of
`/runs/{rootId}/versions/{v}`, before any tab is ever touched.

**Overlaps with [ISS-286](20260828-1712-ISS-286.md)** (root cause of the earlier, narrower
`BUG-20260828-020900-runs-id-versions`, `verification: passed` — a real browser reproduction,
3/3). ISS-286 independently traced the EXACT same mechanism — `reopenedRunIdFor` (`page.tsx:182-196`)
discarding `parsed.version`, `activeRunId` therefore resolving to the root — and confirmed via
browser that the version-picker LABEL reads "v1" on cold `/versions/2` while claiming the
DELIVERABLE CONTENT shown was still correctly v2. See the "Important discrepancy" note below:
this card's own inference (content also reverts, not just the label) has NOT been reconciled
against that observation.

## Root cause (INFERRED from static reading — not yet re-driven through the browser this pass)

- `parseViewPath`'s `versions` branch (`frontend/src/lib/routes.ts:335-339`) parses
  `/runs/{id}/versions/{v}` into `{screen: 'run-version', runId, version}`:
  ```ts
  if (subpath === 'versions') {
    const version = segments[3];
    return { screen: 'run-version', runId, version };
  }
  ```
  `runId` here is `segments[1]` — the ROOT run id embedded in the URL — and `version` is a
  separate field.
- `reopenedRunIdFor` (`frontend/src/app/[...view]/page.tsx:182-196`) — the only function that
  turns a `ParsedView` into "which run id to fetch" for a cold mount — returns `parsed.runId`
  for the `run-version` case and never reads `parsed.version`:
  ```ts
  function reopenedRunIdFor(parsed: ParsedView): string | undefined {
    switch (parsed.screen) {
      case "run-detail":
      ...
      case "run-version":
      case "run-preview-full":
        return parsed.runId;
      default:
        return undefined;
    }
  }
  ```
- The cold-mount effect that consumes it (`page.tsx:3154-3157`) calls
  `handleSelectWorkflowRun({ id: runId })`, which fetches `getWorkflow(token, run.id)`
  (`page.tsx:2718`) and writes its `.output` straight into `userStoryContent`/`pptContent`/
  `prototypeContent` (`page.tsx:2982-3011`) — the ROOT run's own persisted output, never the
  pinned revision's.
- A full-file search (`grep -n "version" frontend/src/app/[...view]/page.tsx`) confirms
  `parsed.version` is referenced NOWHERE outside the two `case "run-version":` switch arms
  (`initialMainViewFor` line 149, `reopenedRunIdFor` line 190), both of which key off
  `.screen`/`.runId` only — the version number is parsed once and then never read again by any
  consumer in the file.
- Visual evidence from this bug's OWN reproduction is consistent with this: both
  `bug-hunter/evidence/runs-id-versions/BUG-20260828-090732-runs-id-versions/01-before-versions-2-preview.png`
  and `bug-hunter/evidence/runs-id-versions/_scratch/attempt1-01-before.png` — captured
  immediately after navigating to `/runs/{rootId}/versions/2`, before any tab click — already
  show the version picker reading **"Version v1"**, not "Version v2", contrary to the
  reproduction narrative's claim that the initial load correctly fetched and rendered v2.

## Expected vs actual

- **Expected:** cold-loading (or refreshing) `/runs/{id}/versions/{v}` resolves `v` against the
  run's revision family and displays that specific member's content — the deep link works
  standalone, with no prior UI interaction required.
- **Actual:** the version segment is parsed into `ParsedView` and then silently discarded; the
  screen shows the root run, indistinguishable from loading the bare `/runs/{id}`.

## Important discrepancy with ISS-286 — unresolved, flagged for the next pass

ISS-286's browser-CONFIRMED reproduction (3/3, `verification: passed`) states the version
picker mislabels "v1" on `/versions/2` while "the content itself is correct (v2)" — i.e., only
the LABEL is wrong, not the deliverable. That is stronger evidence (an actual browser run) than
this card's static trace, which infers the DELIVERABLE content is ALSO wrong (root's own
`.output`, not v2's) because `contentSourceRunId`/`userStoryContent` are populated from
`reopenedRunIdFor`'s root-id fetch with no separate resolution step.

One plausible reconciliation, NOT verified: ISS-286's "content itself is correct (v2)" quote
describes the **chat transcript** ("Page body (chat transcript) showed the v2 revision text")
— which page.tsx seeds from the WHOLE revision family regardless of `parsed.version`
(`getRunFamily` + per-member `getRunEvents`, `page.tsx:2866-2953`, a working, separate
mechanism) — not the Preview panel's rendered deliverable/iframe output, which is what this
card and [ISS-230](20260828-1805-ISS-230.md)'s Files-tab byte-size evidence are about. If that
reconciliation is right, both cards are correct and non-contradictory: label wrong (ISS-286) +
deliverable content wrong (this card), via the same root-cause function. **This needs a live
re-check to settle** — cold-load `/versions/2` and check the Preview tab's actual RENDERED
iframe/HTML (not just the chat lane) against v1 vs v2's known content before assuming either
direction.

## Why this matters together with ISS-230 / ISS-296

ISS-230's fix (preserve `/versions/<v>` across `handlePreviewPanelTabSelect`'s routeMap) only
helps once something else makes that URL segment mean something on arrival. Without also
closing this consumption gap, a "successful" ISS-230 fix would keep the URL stable across tabs
while still rendering the root run's content on every one of them — the user-visible symptom
would persist even though the URL stopped changing. The three cards (this one, ISS-230, and
[ISS-296](20260828-1724-ISS-296.md)'s write-side gap) point at the same missing piece: one
shared place that resolves `(rootId, version)` -> the actual family-member run id, read by the
tab router, the cold-mount fetch, and the Version-menu write path alike.

## Fix direction (not applied — analysis/fix only)

`reopenedRunIdFor` (or its caller) needs to resolve `parsed.version` against the run family
(`getRunFamily`) into the matching member's run id before fetching, instead of only ever
fetching `parsed.runId`.
