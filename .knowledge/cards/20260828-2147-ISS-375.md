## Status: INFERRED — not independently reproduced by this pass

This card is derived mechanically from the CONFIRMED root cause in
[ISS-374](20260828-2146-ISS-374.md), not from a fresh browser reproduction (out of scope for
analysis — no source edits, no new browser session run here). It is filed as a lead, not a
proven defect. See "What would confirm/refute this" below.

## Why the root cause implies this (the inverse/boundary case)

[ISS-374](20260828-2146-ISS-374.md) established that `IdeaInputPage.tsx`'s roster ends up
permanently empty (`pipelineAgents = []`, all actions disabled, zero error UI) whenever BOTH
of these hold at once:

- `fromLibrary` (`LIBRARY_AGENTS` filtered by `agentMatchesPipelineType`,
  `IdeaInputPage.tsx:1231-1233`) is empty — true for any pipeline_type no `AGENT.md` declares.
  The code's OWN comments (`IdeaInputPage.tsx:1248-1254`) confirm this is a real, by-design
  category, not a hypothetical: "A composed workflow has no AGENT.md-backed library agents, so
  the filter above is empty for it." ppt_v2 is cited there as a partial case (2 of 4 steps);
  a fully custom/composed/user-saved workflow is the zero-of-N case.
- `manifestAgents` is `undefined` — set by the `.catch()` at `IdeaInputPage.tsx:1172-1181`,
  which is reached on **any** rejected promise from `getWorkflowDetail`, not only a 404 for an
  id that never existed. The catch's own comment says as much: "Unknown id (404) **or
  transient error** ⇒ treat as 'nothing declared'" (emphasis mine, `IdeaInputPage.tsx:1173`) —
  the swallow is already documented as covering both cases identically, it just was not
  followed through to what that means for a workflow that DOES exist.

The bug this pass validated (`BUG-20260828-001720-workflow-create-prototype`) hits this via
the first bullet's cause: an id that never existed, so `getWorkflowDetail` always 404s and
`manifestAgents` is always `undefined` for it. The INFERRED sibling here is the second bullet
taken on its own: a manifest-only/composed workflow id that is **real** (an existing, saved,
accessible workflow) but whose `GET /api/workflows/{id}` call fails for a **transient** reason
— a dropped connection, a momentary 5xx, the `REQUEST_TIMEOUT_MS` abort in
`frontend/src/lib/api.ts:112` firing on a slow response — would land in the exact same
`.catch()`, leave `manifestAgents` `undefined`, and (because `fromLibrary` is empty for this
workflow BY DESIGN, not because anything is wrong with it) dead-end identically: `pipelineAgents
= []`, "Add agents first" forever, no brief text can recover it, and — per
[ISS-374](20260828-2146-ISS-374.md)'s reading of this same catch — no error text anywhere.

This is materially worse than the parent bug: the parent's trigger is a bad URL for a workflow
that never existed; this one's trigger is a single slow/flaky response for a workflow the user
legitimately owns and can normally open, with no retry and no way to tell the two situations
apart from the screen.

## Expected vs Actual (expected reproduction, not yet run)

**Expected:** a transient failure fetching a real workflow's detail should be retryable or at
least distinguishable from "this workflow does not exist" — not permanently disable every
action with zero indication of what went wrong.

**Actual (inferred):** identical outcome to the parent bug's nonexistent-slug case — permanent
0-agent composer, all actions disabled, no error text — for a workflow that genuinely exists.

## What would confirm or refute this

1. Identify or create a saved/composed workflow whose `base_pipeline_type` has no matching
   `AGENT.md` (`fromLibrary.length === 0` for it — any user-saved custom workflow qualifies,
   per `IdeaInputPage.tsx:1248-1254`).
2. Open `/create/{that-workflow-id}` while forcing exactly one `GET
   /api/workflows/{that-workflow-id}` call to fail WITHOUT the id being invalid — e.g. block
   that single request in devtools (Network → block request URL, or throttle to trigger the
   30s `REQUEST_TIMEOUT_MS` abort in `api.ts:112`) rather than requesting a bad id.
3. Confirm: `pipelineAgents.length === 0`, all three action buttons `disabled === true`, and
   `document.body.innerText` contains no error/failure text — matching ISS-374's reproduction
   exactly, for an id that is valid.
4. If the app instead shows a retry/error affordance today (e.g. a higher-level boundary this
   analysis did not find), this card is refuted — say so and close it rather than forcing a fix.

## Fix

Same location as [ISS-374](20260828-2146-ISS-374.md)'s: the visible error/not-found state
proposed there should differentiate `ApiError.status === 404` ("this workflow does not exist")
from any other rejection ("could not load right now — retry"), since the two want different
copy and arguably different affordances (a 404 has no useful retry; a transient failure does).
A single boolean `loadError` cannot express that distinction — the state needs to carry which
case it is, not just that a failure happened.
