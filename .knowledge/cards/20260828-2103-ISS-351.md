## What happened

Filed while validating `BUG-20260828-082706-runs-id-files` (register entry in
`bug-hunter/ledger.md`). CONFIRMED 3/3 on 2026-08-28, all three from a cold start (fresh
navigation, no soft re-click), on `/runs/b9feac1c-ec21-4531-8ba7-bb391786993e/files` as
`qa-admin`, default theme, default viewport:

- Cycle 1 (dashboard -> direct URL nav): `prompt.md` declared "620 B".
- Cycle 2 (dashboard -> direct URL nav, repeated fresh): same "620 B".
- Cycle 3 (`about:blank` -> direct URL, coldest entry): `01-presentation-strategist-agent.md`
  declared "9.5 KB".

No axis variation was needed — reproduced cleanly on every attempt with no trigger condition
beyond "the file's content contains a multi-byte UTF-8 character" (this pipeline's LLM output
uses em dashes `—` and right-arrows `→`).

## Root cause

`frontend/src/components/results/FilesTab.tsx` — every file-size label is computed by calling
`formatSize(content.length)` where `content` is a JS string. `String.prototype.length` counts
UTF-16 code units (effectively characters here), not UTF-8 bytes. `formatSize` itself (around
line 1116) is a correct bytes-to-`B`/`KB`/`MB` formatter — the defect is that every call site
feeds it a character count instead of a byte count. Call sites, all `formatSize(x.length)` or
`formatSize(x.output.length)`: lines 102, 115, 232, 389, 397, 414, 422, 542, 568, 612, 645.

Any character in the content that is multi-byte in UTF-8 (em dash `—` = 3 bytes but 1 UTF-16
unit, right-arrow `→` = 3 bytes but 1 unit, etc.) makes the declared size smaller than the true
byte size the Download button actually delivers. Measured deltas on the reproduction run:
`prompt.md` declared 620 vs true 626 bytes; `01-presentation-strategist-agent.md` declared 9686
chars (9.5 KB rounded) vs true 9845 bytes (9.62 KB); `02-deck-engineer-agent.md` declared 56398
vs true 56564 bytes; `04-pptx-code-generator.md` declared 29459 vs true 29584 bytes.

The backend already reports correct byte sizes elsewhere — per the register entry's browser
signals, `GET /api/runs/{id}/sandbox` returns true byte counts (e.g.
`conversation_history/...ppt-code-generator.md` = 319756, `presentation.html` = 54551) — so this
is purely a client-side display defect in `FilesTab.tsx`, not a backend data problem.

## Expected vs actual

- **Expected:** the size label next to each file matches the actual byte size of the file
  Download delivers (what `wc -c` / the OS reports on the downloaded artifact).
- **Actual:** the label reflects `content.length` (UTF-16 code units), understating the true size
  whenever the content has multi-byte UTF-8 characters — by 6 bytes on the smallest file checked,
  100-200+ bytes on larger agent-output files.
