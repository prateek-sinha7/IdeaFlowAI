## The symptom

Chaining one run's deliverable into a workflow of a DIFFERENT type was refused
outright. `prototype` → `user_stories` came back
`ChainRefused("source_provenance_conflict")`, which reads as a provenance
failure and is not one. In practice chaining was a same-type-only feature.

## The root cause

`admit_chain_launch` derived `declared_output_basename` from the RECEIVING
workflow's own deliverable name:

```python
declared_output_basename = (
    effective_compiled.deliverable.name if effective_compiled is not None else None
)
```

and the payload selector then enforced equality (`run_commands.py:4566-4567`):

```python
if declared_output_basename and found_basename != declared_output_basename:
    raise ChainRefused("source_provenance_conflict")
```

The receiving manifest declares `user_stories.md`. The `.chain/` payload carries
`prototype.html`. Two different workflow types produce differently named
deliverables by construction, so the check could never pass across types.

## What changed

`declared_output_basename` is passed `None` unconditionally, so the filename
constraint is skipped and any single non-fixed file in `.chain/` is accepted as
the deliverable regardless of type.

## Why that is safe — and why not to restore it

This **amends** [ADR-0041](20260907-ADR-0041.md)'s fail-closed admission model,
so the argument has to live next to it or the next reader will put the check
back as a security guard.

Payload identity is already proven elsewhere: `summary.md` carries `run_id` and
`output_filename`, and those are what establish that this payload came from the
run the launch claims it came from. The basename equality check never added
provenance — it only ever meant something for a **same-type revision chain**,
where the caller genuinely knows the source's expected output name.

Crucially, only ONE `source_provenance_conflict` check in this module was
relaxed — the basename equality at `run_commands.py:4566`. The other five raises
are untouched and still fail closed: `:4537`, `:4561`, `:4588`, `:4621` and
`:4719`. If a future reader is auditing the fail-closed posture, those are the checks that carry it.
