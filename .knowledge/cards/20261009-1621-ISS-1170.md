# ISS-1170

**Register source:** sibling derived during the `QA-KB-109` analysis on 2026-10-09 (root [ISS-1153](20261009-1340-ISS-1153.md)). Not its own bug row, but it is the one sibling the root's "the server refuses with 400, so this is UI-only" does not hold for, and the only one that needs a backend change. Severity high because of what it does to the account, not because of how likely a click is.

**Confidence.** CONFIRMED offline: the handler accepts actor == target and performs the reset against the admin's own account (`evidence/qa-kb-109/analysis-01-probe-admin-self-target-matrix.txt`, blocks `[S]` and `[R]`; in-memory SQLite, Cognito client mocked, nothing real was called); and the own-row Key button sends it (`analysis-02-probe-own-row-today.txt`, `[P6]`: `adminResetUserPassword("tok", <own id>)`, toast "Temporary password issued; user must change it at next login."). INFERRED: that the admin cannot get back in afterwards. What would settle it: `AdminSetUserPassword(Permanent=False)` on a throwaway user in the dev pool, then a sign-in and a forgot-password attempt with a password nobody knows. Never on `admin@velocity.ai`.

## Condition

`POST /api/admin/users/{user_id}/reset-password` with `user_id == admin.id`, reachable from the admin's own row: the Key button (`frontend/src/app/admin/page.tsx:584-591`, `handleResetPassword` `:318-328`) is rendered on every row.

## What the server does

`reset_user_password` (`backend/app/api/admin.py:501-546`) looks the target up (`:523-527`) and calls `cognito_admin.reset_password(db, user)` (`:529-532`). There is no `user_id == admin.id` check. Its four siblings all have one: tier `:301-305`, role `:365-369`, disable `:566-570`, delete `:686-690`. The probe's `[S]` lines put the five side by side: four answer 400 before touching Cognito, `reset-password` is accepted.

`reset_password` (`backend/app/core/cognito_admin.py:579-618`), for the admin's own row:

1. stamps `tokens_valid_from = now` and commits (`:590-591`), so every access token issued before now is rejected, the admin's own current one included (`[R]`: `tokens_valid_from stamped: True`);
2. `AdminUserGlobalSignOut` on the admin's email (`:593-595`);
3. `AdminSetUserPassword(Permanent=False)` with `generate_temporary_password()` (`:597-605`), a 12-character random value whose docstring says "Never logged or echoed in the response" (`:252-259`). The endpoint answers `{"status": "temporary_password_set"}` and nothing else.

So the admin is signed out at once and their credential is replaced by a value no one is shown. INFERRED: with the dev pool's only admin (`ADMINS 1` on the dashboard) that is a lockout. If it is one, nothing in the application can undo it: `docs/runbooks/admin-recovery.md:3` says "There is no local-password admin, no break-glass account, and no code-level bypass of any kind left in this application. Every recovery path below goes through AWS Cognito itself, using an operator's own AWS IAM credentials". A second admin could reset again, but that only replaces the value with another one nobody sees.

## Expected vs actual

Expected: refuse an admin acting on themselves with a 400, as the four siblings do. The endpoint's own docstring says it sets a temporary password "for another user" (`admin.py:508`), and its audit comment calls it "privilege-adjacent ... with the same weight as a role change" (`:536-538`). The recorded policy is the locked constraint of [FIX-310](20260826-0124-FIX-310.md): every privilege-mutating admin endpoint refuses an actor targeting their own account. Actual: accepted, with the side effects above.

Nothing in the test suite covers it. `backend/tests/integration/api/test_admin_authorization_matrix.py` has self-action cases for tier (`:605`), delete (`:739`) and disable (`:929`) and no reset-password case of any kind; `test_admin_privilege_atomicity_api.py:230-295` (`TestPasswordResetAtomicity`) tests reset only against another user.

## Why the root cause implies it

[ISS-1153](20261009-1340-ISS-1153.md) is "the page offers every control on the own row and relies on the server to refuse". For four controls the server does refuse. For this one nothing does, so the missing UI branch is the only thing between a click and the account change. This is FIX-310's shape again: a self-action guard present on the siblings and missing on one route, with the matrix test file silent about it.

## Fix direction (INFERRED, not applied)

Two small changes, in this order of importance:

1. `reset_user_password`: `if user_id == admin.id: raise HTTPException(400, ...)` before the lookup, matching the siblings' shape and 400 status. A UI-only fix would leave the endpoint open to any other client and to a stale tab.
2. The root's change: no Key button on the own row. Self-service paths for one's own password already exist: `POST /api/auth/change-password` (`backend/app/api/auth.py:1173`, called by `changePassword` at `frontend/src/lib/api.ts:1938`) and the forgot-password page (`frontend/src/app/forgot-password/page.tsx`).

Whether an admin should ever be able to reset their own password through `/admin` is the one question the owner could still answer differently; the docstring, the audit comment and FIX-310 all say no, so this card proceeds on that reading.

## Operational warning for the line

Do not click Reset password (the Key) on `admin@velocity.ai`'s own row in any browser lane, and do not call the endpoint with the admin's own id. The probe shows it is accepted; it would revoke the shared admin's session mid-run.

## Resolution

Resolved by [FIX-779](20261009-1659-FIX-779.md) (5-fixer, 2026-10-09), both halves: `reset_user_password` refuses `user_id == admin.id` with 400 before the lookup (`admin.py:523-530`), so nothing is stamped and Cognito is not called; and the own-row Key is no longer rendered. The test stage left no test for this card; FIX-779 added `TestResetPasswordSelfAction::test_reset_password_cannot_target_self` to `test_admin_authorization_matrix.py`, observed red first (`assert 200 == 400`), then XPASS(strict); marker left for the 6-verifier. The analyzer's `[X]` probe also XPASSes and `[C]` (reset of another user) still passes. The lockout remains INFERRED and was never driven. The operational warning above still applies to any server that has not reloaded `admin.py`.
