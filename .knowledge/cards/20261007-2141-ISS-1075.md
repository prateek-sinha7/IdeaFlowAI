for QA-KB-067. The code chain is CONFIRMED by reading; the network count has not
been measured. [ISS-856](20260923-0028-ISS-856.md) is marked resolved on a
source-level test (`page.iss856.test.tsx` pins that an `if (` guard sits before
the call), never on a request count.

## Condition

On `/runs`, open a run that has two or more revisions and pick another member in
the family picker.

## Chain

1. `WorkflowHistory.handleSelectVersion` awaits `getWorkflow(token, memberId)`
   (`WorkflowHistory.tsx:398`), then calls `onOpenRun(full)` (`:403`).
2. `onOpenRun` (`DashboardLayout.tsx:3065`) calls `onSelectWorkflowRun?.(full)`
   and then `router.push(routes.runDetail(full.id))`.
3. The click-time `handleSelectWorkflowRun(full)` sees `run.input !== undefined`
   and skips its fetch (ISS-856's guard, `page.tsx:2972`). It does so on the page
   instance the push is about to destroy.
4. The push remounts the page. T7 (`page.tsx:3554`) calls
   `handleSelectWorkflowRun({ id: runId } as WorkflowRun)`. A bare id carries no
   `input`, so the guard misses and `getWorkflow` runs again.

## Expected vs actual

Expected (ISS-856): one `GET /api/runs/{memberId}`.

Actual (inferred): two, the picker's and the remounted page's. Before ISS-856 it
was three (picker, click-time, remounted), consistent with the original "fetched
3x" report ISS-856 cites.

## Why ISS-840's root cause implies it

The record is handed to the one instance that cannot use it: writes from an
unmounted page are discarded (`useRunStateStore.ts:399`). The instance that
renders receives only an id.

## Fix implication

- ISS-840's smallest fix shape (the click-time call stops reopening) does not
  close this on its own: the picker still pre-fetches and the remounted page
  still fetches. With the click-time reopen gone, the picker's `getWorkflow`
  feeds nothing when `onOpenRun` is set, so that pre-fetch can go too; the push
  needs only `memberId`.
- The alternative is a token- and run-keyed module-scope hand-off of the fetched
  record across the remount (the [FIX-632](20260922-2221-FIX-632.md) pattern), so
  the remounted page consumes it.
- ISS-856's test should be re-pointed at the request count rather than the source
  shape.

## What would settle it

Open a run with two or more revisions on `/runs`, reset the Network log, pick
another version, and count `GET /api/runs/{memberId}`: two today if the
inference holds.

## Fixer note 2026-10-07 (5-fixer, QA-KB-067): left open, entry point not reachable in production

[FIX-753](20261007-2216-FIX-753.md) fixed ISS-840 at the click hand-off. `onOpenRun` now reaches
`primeRunOpen` (no fetch), not `handleSelectWorkflowRun`. This card's chain no longer has a click-time reopen, and
the picker's record now feeds only the prime, which reads `run.id`. Two fetches of the record are left: the
picker's `getWorkflow` (`WorkflowHistory.tsx:398`) and the remounted T7. FIX-753 did not change
`WorkflowHistory.tsx`.

The reason is that the chain's first step cannot be reached in production (CONFIRMED by grep, 2026-10-07):

- `handleSelectVersion` is passed only to `<RunDetailPage onSelectVersion=...>` (`WorkflowHistory.tsx:684-690`).
  It renders only inside `if (selectedRun)` (`:594`).
- `selectedRun` is set at `:362` and `:374`, inside `handleSelectRun`, and only after
  `if (onOpenRun && !opts?.forChain) { onOpenRun(run); return; }` (`:358`). It is also set at `:405`, the
  `onOpenRun`-absent branch of `handleSelectVersion` itself.
- The only production mount, `<WorkflowHistory` at `DashboardLayout.tsx:3038` (post-FIX-753 numbering), always
  passes `onOpenRun`.
- `forChain` appears only in that definition (`grep -rn forChain frontend/src`, test files excluded, returns
  `WorkflowHistory.tsx:341,354,358`). No caller sets it since FIX-584 removed the Chain row action.

The family picker a user can reach on `/runs` is the expanded `FamilyGroupCard` member list
(`RevisionFamilyView.tsx:719` `onSelectRun(member)`). It goes through `handleSelectRun` and `onOpenRun` with a slim
row, which is ISS-840's own path, now measured at 1 `GET /api/runs/{id}`.

Decision for the owner or analyzer: re-scope this card or close it. To remove the picker's pre-fetch anyway
(`onOpenRun({ id: memberId })` when `onOpenRun` is set), the sanity assertions in `page.iss856.test.tsx` must be
re-pointed first, as this card already suggests. They pin `await getWorkflow(token, memberId)` and
`onOpenRun(full)` in `handleSelectVersion`.
