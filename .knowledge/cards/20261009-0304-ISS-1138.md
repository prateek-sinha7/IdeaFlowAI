# ISS-1138

**Register source:** sibling derived during the `QA-KB-106` analysis on 2026-10-09 (root [ISS-1137](20261009-0304-ISS-1137.md)). Not its own bug row. **INFERRED:** the code is
read end to end, the screen was not driven. An unreproduced sibling is a lead, not a defect.

## Condition

Any refusal of `POST /api/runs` after the user presses Run workflow (or Cmd/Ctrl+Enter in the brief) on `/create/app`, `/create/user-stories`, or any `/create/<workflow>`
Input panel: 503 `model_provider_unavailable`, 422 and 400 manifest and agent errors. The 403 `tier_not_entitled` case is mostly closed on this surface by the client lock from
[ISS-472](20260829-0110-ISS-472.md) (`locked` is in the Run button's `disabled`, `IdeaInputPage.tsx:2033`); the others are not.

## Why the root cause implies it

1. `handleRun` latches exactly like `handleRunOnce`: `if (submittingRef.current) return; submittingRef.current = true; setIsSubmitting(true);`
   (`IdeaInputPage.tsx:1605-1607`). The comment above it (`:1598-1604`) says "Nothing clears it on the success path because there is no success path back to this screen —
   `onRun` reaches startPipeline ... and the surface switches to mainView="execution", unmounting this page whether or not the POST itself succeeds." `submittingRef` is written
   nowhere else in the file. The button is `disabled={isSubmitting || locked || ...}` (`:2033`), and the shortcut is `onSubmitShortcut={handleRun}` (`:1974`).
2. `onRun` is `handleRunPipeline` (`DashboardLayout.tsx:3182`), typed `=> void` (`IdeaInputPage.tsx:792`). It calls `onStartPipeline` and discards the outcome
   (`DashboardLayout.tsx:1841`). The refusal ends in the same `.catch` (`page.tsx:4454-4467`) that shows nothing.
3. This surface differs from the composer in one way: `handleRunPipeline` does call `setMainView("execution")` before the POST (`DashboardLayout.tsx:1786`). But
   `/create/<type>` maps to `initialMainView = "input"` (`page.tsx:150-157`), and the URL-sync effect
   `if (initialMainView && initialMainView !== mainView) setMainView(initialMainView)` (`DashboardLayout.tsx:603-607`) puts it back, because the URL has not changed: it only
   moves to `/runs/<id>/stream` once the run's id arrives (`DashboardLayout.tsx:871-873`). That is also why QA-SG-002 found the Run button still on screen and clickable after
   the click ([ISS-729](20260922-1338-ISS-729.md)). All views sit under one `<AnimatePresence mode="sync">` with keyed children (`DashboardLayout.tsx:2974`; `key="input"` on the
   input view), and `AnimatePresence` keeps a keyed child that re-enters before its exit finishes (`frontend/node_modules/framer-motion/dist/es/components/AnimatePresence/index.mjs`,
   the `exitComplete.delete(key)` branch), so the same `IdeaInputPage` instance probably survives.
4. Result, by reading: either the instance survives (brief intact, Run workflow and Cmd/Ctrl+Enter dead, no message), or it remounts (empty form, no message).
   [ISS-969](20261002-0338-ISS-969.md) predicted "moved off the form onto the execution view"; the URL-sync effect makes that unlikely.

## Expected vs actual

- **Expected:** the backend's message appears inline (the page already has a `saveError` line, `IdeaInputPage.tsx:2072-2073`), Run workflow is enabled again and the brief is
  intact.
- **Actual (derived):** no message; the button, or the whole form, is dead.

## What settles it

Playwright on `/create/user-stories` with a POST-only `page.route` stub of `/api/runs` (503, as in the root card's test recipe; let `GET /api/runs` through). Fill the brief,
press Run workflow, then read the button state, the brief box and the page text. Retest with the Cmd/Ctrl+Enter shortcut.

## Where the fix belongs

The same seam as the root: release on refusal only, driven by the outcome `onStartPipeline` hands back, with one helper shared by the two panels if it can be done without a new
abstraction. Not a `finally`: it would re-open the double-click window that [FIX-614](20260922-1850-FIX-614.md) closed for this button too
(`tests/integration/e2e/suites/03_launch_panels/test_iss729_run_workflow_double_click_guard.py`).

## Resolved 2026-10-09 by [FIX-773](20261009-0952-FIX-773.md)

`IdeaInputPage.handleRun` now releases the latch when `onRun`'s outcome is `null` (`IdeaInputPage.tsx:1702-1711`). `handleRunPipeline`
returns that outcome (`DashboardLayout.tsx:1846-1848`). Observed after the fix on `/create/user-stories`, with `POST /api/runs` stubbed so
nothing was minted:

- a same-tick double-click sent 1 POST;
- Run workflow was disabled while the POST was pending;
- after a 503, the banner showed the backend text, Run workflow was enabled again, the brief was intact and the URL was unchanged;
- a second click, then Cmd/Ctrl+Enter, each sent another POST.

Evidence: `evidence/qa-kb-106/fix-06-stubbed-latch-check.txt` and `fix-05-input-panel-after-refusal.png`. The pre-fix state on this
surface was not driven; the root card's composer reproduction stands for it. A launch parked while the connection is not connected
still never unlatches: [ISS-1151](20261009-0952-ISS-1151.md).
