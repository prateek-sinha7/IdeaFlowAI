## Summary

`/runs/{id}/preview/full` is the dedicated route whose purpose is to force-select and show a
run's Preview tab. For a `failed`-status run with no deliverable, no Preview tab exists at all
(`visibleTabs` drops it — see mechanism below), and the route silently auto-selects the **Audit**
tab and renders its full content instead, with no banner or text indicating a fallback occurred.

Validates register entry **BUG-20260828-014416-runs-id-preview-full**.

## Reproduction (3/3, cycle 1)

Run used: `826d09f0-21b0-4b8f-a79f-843fc5c82adb` (status `failed`, confirmed via
`GET /api/runs/826d09f0-...` — `"v1 · partial"`, "Run failed · Presentation Strategist Agent").
The register's original run id (`d6e425b6-...`) has since transitioned to `cancelled` in the
shared seed data, so a currently-`failed` run was substituted to test the same premise; the
mechanism reproduced identically.

1. Cold nav to `/runs/826d09f0-21b0-4b8f-a79f-843fc5c82adb` (plain route). Tablist:
   `Steps | Files | Workspace | Audit` — no Preview tab, no tab `[selected]`, body shows
   "Output will appear here".
2. Cold nav to `/runs/826d09f0-21b0-4b8f-a79f-843fc5c82adb/preview/full`. Tablist is identical
   (still no Preview tab), but `Audit` is now `[selected]` and the pane renders a full 8-record
   audit trail with no text indicating this is a substitution for an unavailable Preview.
3. Repeated from two more distinct cold entry paths (via `/dashboard` and via `/library` as the
   preceding page) — identical result both times: Audit silently selected, deterministic across
   all 3 cycles.

## Root cause

`frontend/src/components/preview/PreviewPanel.tsx:727-785` — the Phase 42-02/42-03 state-keyed
default-tab effect. `terminalFailureNoDeliverable` (line 664, `showFailureAffordance &&
!isCancelledTerminal`) is true for this run (`hasContent` false, `isTerminal` true, not
cancelled). `defaultTabDiscriminator` becomes `"failed"` (line 760), and the effect's target
selection (line 779) maps `"failed"` straight to `"audit"` with no conditional on which ROUTE
requested the view — `run-detail` and `run-preview-full` are treated identically by
`reopenTabFor` (`frontend/src/app/[...view]/page.tsx:214-224`, neither is a case there, both fall
through to `undefined`), so nothing in the deep-link layer distinguishes "the user explicitly
asked to force-open Preview" from "the user opened the run normally." The generic per-state
default (Audit) wins in both cases, and no code path renders a message explaining that the
requested Preview view was substituted with Audit content.

Note: on the plain `/runs/{id}` route, the observed result was no tab visually `[selected]` and
a neutral "Output will appear here" placeholder rather than Audit — the exact reason the two
routes diverge in outcome despite sharing `reopenTabFor`'s `undefined` return was not fully
traced (a plausible read-through of the ALREADY-TRACKED branch at `page.tsx:3175` suggests a
`?? "preview"` fallback specific to `run-detail` that `run-preview-full` never gets, but this
was not confirmed against every render path). What is confirmed 3/3 is `/preview/full`'s own
behavior: Audit silently selected, no fallback affordance.

## Expected vs actual

- **Expected:** `/preview/full` degrades honestly when no Preview tab exists — either the same
  neutral "nothing to show" placeholder the plain route uses, or an explicit inline message
  explaining a different tab is being shown instead (mirroring the honest cancelled-run empty
  state this same route already renders correctly one state over, per the register's step 4).
- **Actual:** Audit tab is silently auto-selected and fully rendered with zero indication this
  is a fallback.

## Analyzer confirmation (2026-08-28, BUG-20260828-014416-runs-id-preview-full analysis pass)

Re-read against the current working tree (line numbers below shift from this card's original
citations — other uncommitted fixes in the same tree touched this file since this card was
written; mechanism and conclusion are unchanged, only line numbers moved):

- `terminalFailureNoDeliverable` now at `PreviewPanel.tsx:716`, `visibleTabs`'s preview-drop at
  `:737-739`, `defaultTabDiscriminator` at `:812`, the merged deep-link/default-tab effect at
  `:814-837`, its `"failed" -> "audit"` mapping at `:830-831`.
- **CONFIRMED, fully traced** (this card's own root-cause note left this open): `reopenTabFor`
  (`frontend/src/app/[...view]/page.tsx:228-244`) is a `switch` over `ParsedView["screen"]` with
  exactly five cases — `run-steps`, `run-steps-agent`, `run-files`, `run-workspace`, `run-audit` —
  each returning its own tab id. `"run-preview-full"` is not one of them, so it falls through the
  `default: return undefined` at `:242`. Both call sites gate on that value being truthy
  (`page.tsx:3191` warm path, `:3264` cold path via `if (tab) runTabDeepLink.requestOpenTab(tab)`),
  so for `run-preview-full` neither ever calls `requestOpenTab` — no deep-link nonce bumps, and
  PreviewPanel's per-state generic default (Audit, for a terminal-failed run) wins by default with
  zero awareness that this specific route's entire purpose is forcing Preview open. This is the
  root cause: not a rendering bug in the Audit tab, but a missing case in `reopenTabFor` combined
  with a default-tab effect that never checks `visibleTabs` before accepting a target.
- **Not resolved (still INFERRED):** why the plain `/runs/{id}` route was observed showing NO tab
  selected + the neutral "Output will appear here" placeholder rather than also landing on Audit.
  Traced every reachable path (`reopenTabFor`, both `page.tsx` call sites, PreviewPanel's own
  effect) and found no code that treats `run-detail` and `run-preview-full` differently on a cold
  mount — both get `tab = undefined` and rely on the identical generic per-state default. The
  `activeTab` `useState` initial value is `"preview"` (`PreviewPanel.tsx:501`), which IS what
  renders that exact placeholder (the tab-content switch at `:1230` gates the whole
  "Output will appear here" branch on `activeTab === "preview"`) — consistent with a screenshot
  taken before the per-state effect had committed for that particular navigation, but this was not
  re-driven live to confirm a timing race versus a genuine second mechanism. Does not change this
  card's root cause or proposed fix location; flagging only so the fixer doesn't assume a
  route-specific branch exists to preserve.
- Blast radius: only one JSX mount of `PreviewPanel` exists (`DashboardLayout.tsx:3107`), so every
  "execution" screen (`run-detail`, `run-steps*`, `run-files`, `run-workspace`, `run-audit`,
  `run-stream`, `run-version`, `run-preview-full`) funnels through this one component — a fix
  belongs in PreviewPanel's default-tab effect/tab-content switch (or in `reopenTabFor` plus a
  `visibleTabs` check there), not duplicated per-route in `page.tsx`.
- Two siblings derived from this same mechanism, on different `headerRunState`/data branches:
  [ISS-388](20260828-2234-ISS-388.md) (a building run lands on Steps instead of Preview),
  [ISS-389](20260828-2234-ISS-389.md) (a zero-audit-record failed run compounds this into a
  content-free, unexplained Audit pane).
