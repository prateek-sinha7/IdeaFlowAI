# ISS-916

**INFERRED, not reproduced.** Derived while analysing QA-KB-002 ([BUG-023](20260827-BUG-023.md)): the same missing
URL-to-type mapping that breaks a cold load of `/create/app` should also break the in-app routes that arrive at
`/create/app` by `router.push`. Every link below was read in source; what has not happened is anyone clicking the tile
and reading the panel. An unreproduced sibling is a lead, not a defect.

Line numbers are the working tree on 2026-10-01. `page.tsx` has uncommitted edits from other work after line 1340, so its
numbers after that point are 3 to 5 higher than at HEAD `024c03ef8`; every other file cited is clean against HEAD.

## Condition

Two in-app entry points end in `router.push("/create/app")` for an `app_builder` workflow:

- **Home tile.** `/dashboard`, click "Build an end-to-end application".
- **Edit brief & run again.** On an `app_builder` run, `effectiveReviseType = viewedRunType ?? workflowType`
  (`DashboardLayout.tsx:2330`), then `setMainView("input"); router.push(createRouteForType(effectiveReviseType))`
  (`DashboardLayout.tsx:2395-2396`).

## Why the root cause implies it (each step read)

1. `HomeLaunchGrid.tsx:245-250` `handleClick` hands a non-wizard type to `onSelectFeature(type)`, which is
   `handleHomeSelectFeature` (`DashboardLayout.tsx:1621-1624`) and then `handleSelectFeature`
   (`DashboardLayout.tsx:1569-1581`): `setWorkflowType(type)` (`:1571`), `setMainView("input")`, then
   `router.push(createRouteForType(type))` (`:1579-1580`).
2. `createRouteForType` maps `app_builder` to `routes.createApp()` (`DashboardLayout.tsx:404-406`), which is the literal
   `'/create/app'` (`routes.ts:67`).
3. `router.push` under the `[...view]` catch-all **remounts** `page.tsx`. The repo says so in three places, each marked
   "confirmed live": `page.tsx:3472-3476` ("a fresh render-instance id appears right after router.push"),
   `DashboardLayout.tsx:540-550`, and [ISS-775](20260922-1330-ISS-775.md). Next's own code agrees: the page subtree is keyed
   by the segment value, `create-router-cache-key.js:16` builds `view|create/app|c` for a catch-all and
   `layout-router.js:673` passes it as the React `key` (Next 16.3.4, `frontend/package.json:40`). A different value is a
   different key, so `/dashboard` to `/create/app` mounts a new `DashboardLayout`.
4. The new instance seeds `workflowType` once, from `initialWorkflowType` and nothing else (`DashboardLayout.tsx:627-637`,
   falling through to `"user_stories"`). None of the 20 `setWorkflowType(` call sites reads the URL (835, 1206-1324,
   1417, 1488, 1571, 1738, 1768, 1946, 2072, 3061-3093), and no `usePathname`/`useParams` feeds it.
5. `initialWorkflowType` is `initialWorkflowTypeFor(parsedView)` (`page.tsx:4230`), which is `undefined` for
   `create-app` (`page.tsx:384-386`, the BUG-023 defect; executed, not just read, in that card).

So the in-memory `setWorkflowType("app_builder")` of step 1 is thrown away by the remount, and the URL, which the page
cannot map back to a type, is all that survives.

## Expected vs actual

- Expected: the tile opens the App Builder panel at `/create/app`. Per `IdeaInputPage.tsx:912-918` that is H1
  "Describe the application", eyebrow "Generate a full-stack application".
- Actual (inferred): the `user_stories` panel at `/create/app`: H1 "Provide the brief", eyebrow "Generate product
  requirements". Run then dispatches `user_stories` (`resolveDispatchType(pipelineAgents, effectiveType)`,
  `IdeaInputPage.tsx:1589`) and "Save as my version" writes `My user_stories` (`IdeaInputPage.tsx:1759-1765`).

Not affected: `/create/app_builder` and the `*_revision` types, which take the generic `create-workflow` screen and
carry their own type (`routes.ts:298`); `ppt`/`prototype`, which take the wizard path (`HomeLaunchGrid.tsx:247-248`).

## Why nobody has seen it

- Scenario S-02-04 (`test_home_catalog.py:75-90`) clicks only "Generate product requirements", the one type whose
  default coincides with the bug.
- The live smoke launches App Builder through the same tile (`tests/integration/e2e/framework/live.py:56`), but the only
  check that the right workflow ran is a regex over the run page (`test_pipeline_smoke.py:88`, `names` at `:41`), and the
  `@live` tier is deselected by default. From reading it I cannot tell that it would catch a `user_stories` run.
- No card, capture, BUGS.md entry or test records the App Builder panel copy ("Describe the application" /
  "Generate a full-stack application"): zero hits outside `IdeaInputPage.tsx:912-918`.

## What would settle it (two minutes, no run launched)

1. Chrome as admin@velocity.ai: `/dashboard`, click the "Build an end-to-end application" tile, read the URL and H1.
   H1 "Provide the brief" at `/create/app` confirms this card. "Describe the application" refutes it, and then something
   other than `initialWorkflowType` carries the type across the push, which would make that finding worth its own card.
2. Open a completed `app_builder` run and use "Edit brief & run again"; same reading.
3. Note whether the brief that handler pre-fills survives. `pendingHomeBrief` is DashboardLayout state
   (`DashboardLayout.tsx:1563`, set at `:2374`, read at `:3166`), so the same remount would drop it for every non-wizard
   type. That would be a different root cause (state set before `router.push`) and needs its own card; it is not claimed here.

## Fix

Expected to need nothing beyond BUG-023's one-function change: once `initialWorkflowTypeFor` returns `"app_builder"`
for `create-app`, the remounted instance seeds correctly on the click path too. Do not patch `handleSelectFeature` or
`createRouteForType`; both are right. After that fix lands, add the missing click scenario by parametrising S-02-04
over `user_stories` and `app_builder`.

## Resolution (QA-KB-002, fixer, 2026-10-01)

Resolved by [FIX-699](20261001-2238-FIX-699.md), BUG-023's one-function change. As this card predicted,
`handleSelectFeature` and `createRouteForType` were left alone.

**What the test shows.** "ISS-916 the in-app push target survives the page remount"
(`initialWorkflowType.bug023.source.test.ts`) now reports "Expect test to fail", which is the pass signal. So the URL
the App Builder tile pushes, `routes.createApp()`, maps back to `"app_builder"` on a remount. The marker is left for
the verifier.

**Still unobserved: the click itself.** That is step 1 of "What would settle it" above: on `/dashboard`, click "Build
an end-to-end application" and read the H1 at `/create/app`. The verifier owns that step.

**Not done.** The suggested S-02-04 parametrisation over `app_builder` was not written; it is not in BUG-023's fix
scope. Step 3's `pendingHomeBrief` question also stays unclaimed, as this card says.
