# ISS-901

Found while fixing QA-KB-045 ([FIX-688](20261001-2140-FIX-688.md)). Since that fix, `ScopedStore.append_event_next_seq`
makes one keyed `event_id` lookup plus one `_max_event_seq` probe per attempt (`authz.py:556-575`). It no longer
calls `read_events`. Three docstrings outside the regions QA-KB-045's cards named still describe the old cost. No
behaviour is affected.

## Where (working tree of feat/user-stories-v2, 2026-10-01)

- `backend/agents/authz.py:476-479`, `read_events_of_types`:

  > ``read_events`` deliberately does NOT gain a LIMIT: it is the replay primitive behind SSE resume, the events
  > API, engine resume and this class's own ``append_event_next_seq`` seq allocation -- capping it would silently
  > truncate replays.

  `append_event_next_seq` is no longer a `read_events` caller. The conclusion (do not cap `read_events`) still
  holds for the other three.
- `backend/agents/authz.py:595-598`, `_max_event_seq`:

  > deliberately NOT ``read_events``, which materialises every row (the local corpus holds a 36k-row run) and is
  > why the engine sink cannot allocate through :meth:`append_event_next_seq`.

  The first half still holds. The "and is why" clause is now history. The engine sink keeps its in-memory counter
  because `append_event_next_seq` would add two index probes per event, not because it reads the log.
- `backend/agents/execution_engine/engine.py:13037-13040`, `_stamp_resume_marker`:

  > NOT ``append_event_next_seq``: that allocator re-reads EVERY row of the run per attempt to derive one integer
  > (the local corpus holds a 36k-row run), which is the same cost that rules it out for the engine sink.

  The cost claim is no longer true. The marker's other reason still stands: it mints a fresh `event_id` and never
  needs the idempotent no-op.

## Disposition

Open, trivial. A reader of these docstrings would take `append_event_next_seq` to be the whole-log allocator and
could re-file the cost that FIX-688 removed. QA-KB-045 left them alone because its dispatch limited the fix to the
regions the cards name. `authz.py:595-598` also sits next to `append_event_at_or_after`, which QA-KB-007 was
editing at the same time.

## Fix shape

Reword the three passages in place, prose only:

- `read_events_of_types`: drop `append_event_next_seq` from the list of `read_events` callers.
- `_max_event_seq`: replace the "and is why" clause with the current reason (two probes per event against the
  sink's in-memory counter), or drop it.
- `_stamp_resume_marker`: keep the idempotency reason and drop the cost claim.

No test is needed, because no behaviour changes.

   `tests/agents/test_resume_seed_bounded_aggregate.py` is `4 passed in 1.20s`, including
   `test_append_event_next_seq_does_not_read_whole_log` (`evidence/qa-kb-074/01-baseline-test_resume_seed_bounded_aggregate.txt`), and
   a probe that wraps `_run_bounded` and `read_events` shows a fresh `event_id` makes
   `['append_event_next_seq', '_max_event_seq', 'append_event']` with 0 `read_events` calls, and a replayed one makes
   `['append_event_next_seq']` with 0 (`evidence/qa-kb-074/02-probe-cost-of-append_event_next_seq.txt`).
2. **Each passage was true when written.** `git log -S` on a phrase from each returns only the commit that introduced it:
   `read_events_of_types` clause `7b79e4266` (2026-08-12, [ISS-092](20260812-0701-ISS-092.md) part 2), `_max_event_seq` clause `885219202`
   (2026-08-12, [ISS-121](20260812-1804-ISS-121.md)), `_stamp_resume_marker` sentence `835793a99` (2026-08-31,
   [FIX-499](20260831-1641-FIX-499.md)). No later commit added or removed that phrase.

The mechanism in one line: a function's cost was restated in four docstrings, and the fix that changed the cost updated one of them.

### What is still true in each passage (the fix removes only the dead part)

- `read_events_of_types`: "do not give `read_events` a LIMIT, it is the replay primitive" holds for the callers that remain, which are
  SSE resume (`run_stream.py:413`), the events API (`runs.py:1559`) and engine resume (`engine.py:12979`, `:16221`, ...).
- `_max_event_seq`: "deliberately NOT `read_events`, which materialises every row (a 36k-row run)" holds, and is why the resume seeds
  and the boot probe use it (FIX-688 locked constraint 1).
- `_stamp_resume_marker`: "the marker mints a fresh `event_id` per call, so it never needs that method's `(run_id, event_id)`
  idempotent no-op" holds, and is now the only reason it avoids the method (the extra keyed lookup could never hit).

### Fix, and where it belongs (prose only)

Two files, three hunks. `append_event_next_seq` and its docstring are already correct and stay untouched. Logical change per site (re-wrap
the lines as needed):

```
authz.py  read_events_of_types
-  ... the replay primitive behind SSE resume, the events API, engine resume and this class's own
-  ``append_event_next_seq`` seq allocation -- capping it would silently truncate replays.
+  ... the replay primitive behind SSE resume, the events API and engine resume -- capping it
+  would silently truncate replays.

authz.py  _max_event_seq
-  ``read_events``, which materialises every row (the local corpus holds a 36k-row run) and is why the engine sink cannot allocate
-  through :meth:`append_event_next_seq`.
+  ``read_events``, which materialises every row (the local corpus holds a 36k-row run).

engine.py  _stamp_resume_marker
-  NOT ``append_event_next_seq``: that allocator re-reads EVERY row of the run per attempt to derive one integer (the local corpus
-  holds a 36k-row run), which is the same cost that rules it out for the engine sink. The marker mints a fresh ``event_id`` per call,
-  so it never needs that method's ``(run_id, event_id)`` idempotent no-op.
+  NOT ``append_event_next_seq``: the marker mints a fresh ``event_id`` per call, so it never needs that method's
+  ``(run_id, event_id)`` idempotent no-op.
```

**Where it belongs.** At these three sites, because the claim is restated there; there is no shared function to guard and no caller to
change. The rule for the rewrite is the structural remedy: state `append_event_next_seq`'s cost only in its own docstring
(`authz.py:539-545`) and refer to it with `:meth:` everywhere else, so the next change to its cost cannot stale a second copy.

**What a naive fix would get wrong**
- Rewriting `append_event_next_seq`'s docstring: already correct.
- Deleting the whole `read_events_of_types` sentence: loses the live conclusion (never cap `read_events`); only the fourth caller is dead.
- Deleting the `_max_event_seq` contrast with `read_events`: its first half is the reason the seeds and probes use the aggregate.
- Swapping the marker's dead cost claim for a new one ("two index probes"): then a second docstring restates a cost that lives in
  `authz.py:541-543`. Give the idempotency reason only.
- Editing `.knowledge/architecture/DOMAIN-*` cards or the generated `files/backend/agents/authz.py.md` card: user-owned and derived
  (see [ISS-1080](20261007-2204-ISS-1080.md)).
- Trusting line numbers from this card or from BUGS.md: `engine.py` has already moved by 48 lines.
