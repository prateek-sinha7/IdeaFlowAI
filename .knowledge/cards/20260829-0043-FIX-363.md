## What was wrong

On `/settings/usage` the "Manage plan" button rendered enabled, brand-styled and
hover-affordanced, with **no `onClick` prop in the JSX at all** — clicking it
fired no request, opened no dialog and navigated nowhere, for every tier.
Validated 3/3 on register entry `BUG-20260828-031600-settings-usage`
(enterprise-admin warm session, basic-tier cold login, basic-tier hard reload).

The consequence is not cosmetic for a basic-tier account: `TIER_PIPELINES`
entitles `basic` to 2 of the 8 deliverable types, and the page's own copy
("Your plan determines which deliverables you can run… Manage plan") promises a
way to act on that. There was none anywhere in the app.

## Root cause

Not a wiring gap — there was nothing to wire to. No plan-management capability
existed in the codebase at all (`.knowledge` [ISS-291](20260828-1917-ISS-291.md),
confirmed by exhaustive grep: `"Manage plan"` occurs once frontend-wide, and
`backend/app/api/` has no billing/subscription/stripe endpoint). The button was
shipped as a visual promise with no destination built behind it:

- `frontend/src/components/settings/AccountSettings.tsx:459` — the `<Button>` with
  no `onClick`. The other four Buttons in that file (321, 425, 618, 627) are wired,
  so this was an isolated omission, not a repeated pattern.
- `frontend/src/components/layout/AppHeader.tsx:523` — the persistent app shell's
  account-menu "Upgrade" link for `userTier === "basic"` did fire an `onClick`, but
  it called `onNavigate("settings")`, landing the user on the very page whose only
  upgrade control was the dead button above ([ISS-397](20260828-2105-ISS-397.md)).

Both call sites terminated at the same missing capability, which is why the fix is
one shared component rather than an `onClick` bolted onto line 459.

## What changed and why there

**New — `frontend/src/components/settings/UpgradePlanModal.tsx`** (the shared
affordance, the only new file):

- Reads the existing `TIER_LABELS` / `TIER_PIPELINES` / `UPGRADE_PATH` maps from
  `frontend/src/lib/entitlements.ts`; no new data source, no new API call. It names
  the current plan, the next tier from `UPGRADE_PATH`, how many additional base
  deliverable types that tier unlocks (revision variants excluded, same rule as the
  Usage & Limits deliverable-access grid), and directs the request to a workspace
  administrator. On the top tier (`UPGRADE_PATH[tier] === null`) it says so instead.
- A real billing/tier-change backend is deliberately NOT implied: `UPGRADE_PATH`
  labels the next tier, it does not action a change, and adding an endpoint is
  outside this bug (see [ISS-291](20260828-1917-ISS-291.md)'s fix-location note).
- Dialog shell cloned from the delete-confirm modal at
  `SavedWorkflowsPage.tsx:410-443` (backdrop, scale-in, `role="dialog"` +
  `aria-modal` + `aria-labelledby`), Escape-to-close from
  `WorkflowPickerModal.tsx:196-203`. No new route is needed for a modal (ADR-0018).
- Portalled to `<body>` (`createPortal`, as `WorkflowPickerModal.tsx:213` does)
  because `AppHeader`'s root `<header>` is `z-40 relative` and would otherwise trap
  the overlay in its stacking context.

**`AccountSettings.tsx`** — `upgradeOpen` state, `onClick={() => setUpgradeOpen(true)}`
on the "Manage plan" Button, and the modal rendered at the end of the surface,
passing the already-loaded `userTier`.

**`AppHeader.tsx`** — the basic-tier "Upgrade" link now opens the same modal
(`setUpgradeOpen(true)`) instead of relocating the user to the settings page. Same
three-line shape as above; nothing else in the header changed.
