## Source

Derived by the analyzer from the root cause of `BUG-20260828-012500-runs-id-steps`
([ISS-278](20260828-1700-ISS-278.md)) — same formula, independently duplicated into a second
component. **Not reachable via any current UI route** — filed so the shared-fix decision (see
`Fix` below) accounts for it before it ships live, not after.

## Mechanism (CONFIRMED by code read, INFERRED as a live symptom)

`frontend/src/components/chat/ChatTokenWidget.tsx` — the chat lane's token-usage widget
(Phase 31, CHATUI-03), whose own docstring (`:5`) states it "Mirrors `TokenUsageSummary` (P26)":

- `:93` — `const input = totalInputTokens ?? 0;` — full gross input, same source field as
  `TokenUsageSummary.tsx:24`.
- `:95` — `const total = totalTokens ?? input + output;` — total computed from the gross
  figures, same as `TokenUsageSummary.tsx:26`.
- `:103` — `const uncachedInput = Math.max(0, input - cacheRead - cacheWrite);` — identical
  subtraction to `TokenUsageSummary.tsx:32`.
- `:104` — `const hasCaching = cacheRead > 0 || cacheWrite > 0;` — identical gate.
- `:117` — `{formatTokens(total)} tokens` always renders the full total.
- `:123-124` — when `hasCaching`, renders `{formatTokens(uncachedInput)} in` with
  `title={\`Total context: ${formatTokens(input)}\`}` — the same "correct value sits in the
  tooltip, wrong value is the visible label" shape as `TokenUsageSummary.tsx:54,56`.

Confirmed via `grep -rn "ChatTokenWidget" frontend/src` that the `<ChatTokenWidget>` component
itself is rendered ONLY inside its own test file (`ChatTokenWidget.test.tsx`). The one
production consumer, `RunChatLane.tsx:67-71`, imports just `composedContextUsage` /
`COMPACT_THRESHOLD_PCT` / `ComposedContextTelemetry` from the module — never the component
itself. So today this defect ships in the bundle and is exercised by its own unit tests
(`ChatTokenWidget.test.tsx:44-63` renders the `hasCaching` branch and asserts only the cache
segment text, never the "in" figure against the total), but is not reachable by a user.

## Expected vs actual (predicted from the mechanism above)

**Expected:** if/when `ChatTokenWidget` is mounted in the chat lane, its "in" figure should be
reconcilable against its own "tokens" total — matching or explicitly qualified, not silently
understating input by the cached amount.

**Actual (predicted, unverified live — component is not mounted anywhere today):** the same
class of self-contradictory reading `TokenUsageSummary` shows: a "tokens" total computed from
the full input, sitting beside an "in" figure computed from `input − cacheRead − cacheWrite`,
whenever `cacheReadTokens > 0 || cacheWriteTokens > 0`.

## What would settle it

Either (a) mount `<ChatTokenWidget>` somewhere reachable and repeat ISS-278's reproduction with
a caching-active run, or (b) treat this as settled-by-construction once the shared fix below
lands, since both components read the identical `PipelineRunState` fields through the identical
formula.

## Fix

Not a second, independent fix. `TokenUsageSummary.tsx` and `ChatTokenWidget.tsx` each hand-roll
the same `input` / `uncachedInput` / `hasCaching` computation (compare
`TokenUsageSummary.tsx:24-33` to `ChatTokenWidget.tsx:93-104` — the comments even say so). The
5-fixer should extract that computation into one shared helper both components call, so fixing
ISS-278 in one file does not leave this dormant copy to reintroduce the identical bug the day
`ChatTokenWidget` gets wired up. `AnalyticsPage.tsx:224-232,604-619` shows a third, independent
implementation of the same arithmetic that already labels the uncached figure "New Input"
inside a 4-segment breakdown that reconciles to the total — a candidate reference for what the
shared helper should return.
