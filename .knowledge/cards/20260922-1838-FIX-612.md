# FIX-612

**Register source:** `QA-PS-027` in root `LEDGER.md` / `BUGS.md`.

## What was wrong

A run whose agents never got real tools or context still finished with a green
**"Done"** badge and a "Delivered" deliverable. The published artefact was the
agents narrating their own confusion — *"I don't have access to a `write_file`
tool"*, *"I'm ready to help"*, *"the pipeline may have failed or the files were
not properly generated"* — and `pipeline_complete.published_status` said
`"completed"` for all of it (ISS-721 cycles A–C: runs `aa2c0684`, `dfc27751`,
`6829bdef`; BUGS.md#qa-ps-027 examples 2 and 3: runs `7b00ac65`, `e2903536`).

## Root cause

Every terminal degrade signal the engine had was **presence/absence, never
content** — see [ISS-721](20260922-1242-ISS-721.md) for the full read:

- `_unrecovered_agents` (`engine.py`, Step 5 completion gate) is built only
  from `ectx.failed_invocations` — invocations that RAISED. An agent that
  streams an apology and returns normally is a completion by construction.
- The other three signals are a budget cap (`ectx.budget_degraded_reasons`), a
  blocked last commit (`ectx.last_commit_blocked`), and the finalizer's
  `output_unmaterializable` trigger — and that last one only checks a declared
  file EXISTS, not that it says anything.
- `_check_artifact_fallback` (`engine.py`, `sandbox.write(filename, output or "")`)
  is what puts the narration on disk in the first place: when a custom-agent
  step's declared file is missing, the engine writes whatever the model
  streamed, verbatim.
- All four deliverable resolvers then accept it — `streamed_text` and `ppt`
  return the last stream unconditionally, `single_file` returns any non-empty
  read, and `serialized_sandbox` gates on `count_sandbox_deliverables(root) > 0`,
  a file COUNT that the single `_check_artifact_fallback` write satisfies by
  itself ([ISS-763](20260922-1426-ISS-763.md)).

Because that gate lives in `_execute_impl` — the one pipeline-agnostic kernel
path (SC-001) — the same hole was open for native `prototype`/`ppt`/
`user_stories` runs ([ISS-761](20260922-1424-ISS-761.md)) and for every
`*_revision` pipeline, whose three `run_commands.py` drivers
(`_reconcile_terminal_status`, `_drive_launch_to_queue`,
`_drive_revision_to_queue`) persist `WorkflowRun.status` straight off this same
field ([ISS-762](20260922-1425-ISS-762.md)).

## What changed and why there

One new signal, in the ONE block all four cards point at. Three files:

1. **`backend/agents/capabilities/deliverables/_placeholder.py` (new)** —
   `placeholder_narration_reason(deliverable) -> str | None`. Stdlib-only, so
   both the kernel and a resolver capability can call it without crossing an
   import-linter boundary (the same position `_mimetype.py` already occupies).
   It flags a deliverable only when BOTH hold: the text is under
   `_MAX_NARRATION_CHARS` (2000) **and** it contains one of twelve lowercase
   first-person incapacity markers — each one a phrase observed in a reproduced
   run or its immediate variant. Non-`str` payloads (e.g. `repo_diff`'s dict),
   empty text and anything longer return `None`.
2. **`backend/agents/execution_engine/engine.py`** — two insertions inside the
   Step 5 completion gate, next to the existing `budget_degraded_reasons` /
   `last_commit_blocked` degrades:
   - `_placeholder_reason = placeholder_narration_reason(final_output)`; when
     set, `_pipeline_complete_data["status"] = "degraded"` plus a
     `degraded_reason` naming the matched marker and the character count.
   - the same flag escalates `_s5_pub` to `"degraded"`. This second line is
     load-bearing: `finalize_terminal_run` runs in the `finally` block ABOVE,
     *before* the deliverable is resolved, so `_fin_record.published_status`
     structurally cannot carry a content signal — without the escalation
     `published_status` (the field the three `run_commands.py` drivers read)
     would still publish `"completed"`.
   No `pipeline_type` branch was added, and the four resolvers were left alone
   rather than each carrying a copy of the logic — ISS-721's explicit fix
   direction.
3. **`backend/agents/capabilities/deliverables/serialized_sandbox.py`** — the
   `count > 0` gate now also refuses a bundle that is only narration, so a
   sandbox holding the single `_check_artifact_fallback` file falls through to
   `streamed_text` exactly as an empty sandbox does, and the engine gate above
   degrades the run ([ISS-763](20260922-1426-ISS-763.md)). This is a call to
   the shared helper, not a second implementation.

Both call sites are DORMANT on any run whose deliverable is real, so INV-3
byte-parity holds — confirmed by the four characterization/golden files run
below.

## Known limits (deliberate)

- **The filename/mimetype half of QA-PS-027 was NOT fixed here.**
  [ISS-721](20260922-1242-ISS-721.md) confirms the asymmetry (`engine.py`
  re-derives `_deliverable_mimetype` from the EFFECTIVE strategy on a
  `serialized_sandbox`→`streamed_text` fallback, per WR-01, but reads
  `_deliverable_name` once from the DECLARED spec), which is how example 2
  produced `output.html` + `text/markdown`. That same pair is the whole subject
  of bug `QA-SG-014` — [ISS-770](20260922-1305-ISS-770.md) (root) and
  [ISS-776](20260922-1557-ISS-776.md) (sibling) — whose already-written tests
  (`backend/tests/unit/test_qa_sg_014_output_format.py`) require the OPPOSITE
  resolution: convert the CONTENT to the declared `.html` format rather than
  rename the file to match the bytes. Renaming here would have made those two
  tests unfixable. Left to that bug's fixer.
- The marker list is literal and short by design. It will miss a novel phrasing
  of "I could not do this"; widening it to a general output-quality judgement
  would put false "degraded" badges on real runs, which is the worse failure.
  `_NARRATION_MARKERS` is the single place to extend.
- The token/duration heuristic the bug report suggested ("5–10s, 100–300
  tokens") was NOT used. ISS-721 already flagged it as unconfirmed, and it
  cannot distinguish a placeholder from a legitimately terse agent.
