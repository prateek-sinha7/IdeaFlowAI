## Sibling of ISS-371 — the other launch surface (formerly INFERRED, now reproduced 3/3: see Validated and Analysis below)

Filed while analyzing QA-KB-014, whose root card is [ISS-371](20260828-2140-ISS-371.md)
(IdeaInputPage Back). The root cause there is "Back is ungated unless the page feeds the

## Condition

`/create/{ppt|ppt_v2|prototype|prototype_v2}`, `/workflow/create` and the resolved ppt/prototype
branch of `/workflows/{id}/run` render `LaunchWizard`. Its header Back button is a bare
navigation, `frontend/src/components/workflow/LaunchWizard.tsx:1057-1068`:

```tsx
onClick={() => goBackOr(router, () => router.push(routes.home()))}
aria-label="Back to dashboard"
```

No dirty check, no `onUnsavedChange`, no confirm. Nothing else guards leaving: there is no
`beforeunload` anywhere in `frontend/src` and no `window.confirm` in the wizard.

Unsaved input the wizard holds in local state: `brief` (:256), `selectedTemplateId` /
`customTemplateBody` (:252-253), `selectedDsId` / `customDsBody` (:254-255),
`discoveryAnswers` (:257), the attachments `attachedFiles` / `attachedFileContents` /
`attachedImages` / `stagedUploads` (:259-272) and `pipelineAgents` (:290). The `*.draft`
sessionStorage hand-off is read once at mount and removed (`:405-438`), and written only on
Continue/Launch (`:1029`), so typing is never autosaved and Back loses it.

## Why the root cause implies this

ISS-371's mechanism needs the page to feed `DashboardLayout`'s `hasUnsavedWork` ref
(`DashboardLayout.tsx:1847`) so `handleBackNav` (:1875) opens the in-app dialog
(`:3478-3517`). The wizard cannot do that. `frontend/src/app/[...view]/page.tsx:4098-4101`
returns it as an early return, `if (wizardMode) { return <LaunchWizard initialMode={wizardMode} />; }`,
under the comment "directly, same standalone-outside-DashboardLayout pattern", and
`frontend/src/app/workflow/create/page.tsx:48` does the same. So the wizard has no
`handleBackNav`, no `hasUnsavedWork` and no dialog, and a complete fix of ISS-371 and
[ISS-372](20260828-2141-ISS-372.md) leaves this Back untouched.

[ISS-786](20260922-1810-ISS-786.md) already changed this same handler from
`router.push(routes.home())` to `goBackOr(...)`, for history semantics only; it did not
address unsaved input.

## Expected vs actual (INFERRED)

**Expected:** with a typed brief or a template / design-system pick, Back opens the in-app
"Leave without saving?" dialog (Stay / Leave anyway). S-19-17 bans a native `confirm()`.

**Actual (inferred):** Back leaves at once and the picks are gone when the route is reopened.

## Fix placement

The gate has to live in the wizard, because the shared ref is not reachable from outside
`DashboardLayout`: a dirty flag (brief, template, design system, attachments or discovery
answers differ from the as-opened state, rebaselined when the `*.draft` seed is applied at
`:405-438` and when the template and design-system registries arrive) plus the same dialog.
The dialog markup is inline in `DashboardLayout.tsx:3478-3517`; extract it into a small shared
component as part of this fix rather than copying about forty lines. Do not do that extraction
for ISS-371 or ISS-372, which reuse the dialog where it is.

## What would settle it

Browser, `/create/prototype`: type a brief, click `[aria-label="Back to dashboard"]`, expect
immediate navigation with no `[role=dialog]`, then reopen the route and find the brief empty.
Test: an e2e in suite `03_launch_panels` using `L.BACK_TO_DASHBOARD`
(`tests/integration/e2e/framework/locators/launch_panels.py:20`), modelled on
`test_iss786_launch_wizard_back_loop.py`.

Same family, deliberately not filed: the `WorkflowView` Back (`WorkflowView.tsx:230`, route

## Analysis 2026-10-02 (QA-KB-058 analyzer) — root cause CONFIRMED

The INFERRED label at the top of this card is retired. The QA-KB-058 validator reproduced the defect 3/3 (section
above), and every line cited below was re-read in the working tree in this pass. **CONFIRMED** means a file:line read
here. **INFERRED** means a mechanism read from code whose visible effect nobody has observed, with what would settle it.

Line numbers are the uncommitted tree over HEAD `024c03ef8`. `LaunchWizard.tsx` has moved since this card was filed
(hunks from the [ISS-284](20260828-1906-ISS-284.md), [ISS-920](20261001-2221-ISS-920.md) and [ISS-189](20260828-1457-ISS-189.md) fixers; the Back is now `:1078`, not `:1063`). Re-grep before editing.

### Root cause — CONFIRMED, one mechanism

`LaunchWizard` is the one surface that holds typed input and has neither a Back guard nor a way to reach the shared one.

- **Back is a bare navigation.** `LaunchWizard.tsx:1078` `onClick={() => goBackOr(router, () => router.push(routes.home()))}`,
  `aria-label="Back to dashboard"` at `:1079`. `goBackOr` (`frontend/src/lib/navigation.ts:18-24`) is a history helper,
  `window.history.length > 1 ? router.back() : fallback()`. It knows nothing about input.
- **The input is component state and is never persisted.** `brief` `:256`, template `:252-253`, design system `:254-255`,
  `discoveryAnswers` `:257`, attachments `:259-272`, roster `:290`. The only `sessionStorage` writes in the file are the
  launch hand-off in `handleLaunch` (`:1044`, `:1049`, `:1052`). The `*.draft` key is read once at mount and removed
  (`:414`, `:447`). There is no `localStorage` use, and `grep -rn beforeunload frontend/src` is empty. A reopened route
  starts from the `useState` defaults, which is the validator's "brief empty".
- **The shared guard cannot reach it.** `[...view]/page.tsx:4117-4121` returns `<LaunchWizard initialMode={wizardMode} />`
  before the `DashboardLayout` return, and `workflow/create/page.tsx:48` mounts it directly. `DashboardLayout` never mounts
  it (its only `LaunchWizard` mentions are comments, `:1811`, `:2347`, `:2378`), so `hasUnsavedWork` (`DashboardLayout.tsx:1847`),
  `handleBackNav` (`:1875`) and the dialog (`:3479-3518`) are not in its tree.
- **Every other input surface reports to that guard; this one cannot.** `onUnsavedChange={handleUnsavedChange}` is wired at
  `DashboardLayout.tsx:3117` (AccountSettings, [FIX-704](20261002-0053-FIX-704.md)), `:3162` (IdeaInputPage,
  [FIX-702](20261002-0040-FIX-702.md)) and `:3216` (ComposerPage, [FIX-352](20260828-2346-FIX-352.md)). Those fixes left this Back untouched, as the
  section above predicted.

### Fix — where it belongs

Refines the "Fix placement" paragraph above; where they differ, this section is current.

In `LaunchWizard.tsx`. Both mounts render this one component, so a guard inside it covers every route, and nothing
changes in the pages or in `goBackOr`. Frontend only, so SC-001/INV-1 and the import-linter contracts are not in play; the
guard keys on edit state, never on `mode` or a workflow name.

1. **A "has unsaved input" signal, read at click time.** A `useRef(false)` latch plus a presence check, evaluated inside
   the Back handler. No effect and no new state, so no new `react-hooks/set-state-in-effect` debt (the file's
   suppression budget is 2, `frontend/eslint-suppressions.json`). `AccountSettings.tsx:615` `userHasEdited` is the
   in-repo latch precedent.
2. **A guard that takes the navigation:** `requestLeave(go)`. If unsaved, open the dialog and run `go` only on "Leave
   anyway"; otherwise run it at once. Back passes `() => goBackOr(router, () => router.push(routes.home()))`. Written this
   way, the second exit ([ISS-982](20261002-0427-ISS-982.md)) reuses it.
3. **The dialog: reuse, do not copy.** `frontend/src/components/ui/Modal.tsx` is the codebase's accessible dialog primitive
   (`role="dialog"`, `aria-modal`, focus trap, Escape, scroll lock, token-only styling), already used by
   `providers/ServiceBusyProvider.tsx:30` and `composer/CanvasConfigRail.tsx:49`. A small `ui/UnsavedChangesDialog`
   (`onStay`, `onLeave`) over it, with the shipped strings: title "Leave without saving?", body "You have unsaved changes.
   Leaving now will discard them.", buttons "Stay" and "Leave anyway" (Escape and a backdrop click are Stay). Put it in
   `components/ui`, so `workflow/` does not import from `layout/` (it does not today; `layout/` imports `workflow/`).
   Moving `DashboardLayout.tsx:3479-3518` onto it is optional for this fix, and that file is under concurrent edit.
4. **`handleLaunch` (`:1000`, navigates at `:1053`) stays unguarded.** The guard is on the Back click only.
5. **No native `confirm()`.** S-19-17 is a source scan of every non-test frontend file for a bare `confirm(`, `prompt(` or
   `alert(` (`tests/integration/e2e/suites/19_toasts_and_dialogs/test_toasts_and_dialogs.py:392-406`).

### Defining "unsaved": every writer, and the traps

The earlier notes name three programmatic writers. There are seven. A snapshot taken at mount, or rebaselined only on the
draft seed, reads each of them as a user edit and would prompt on an untouched wizard.

| state | programmatic writers (no user action) | user writers (these are edits) |
|---|---|---|
| `brief` | `chain.brief` `:408`; draft restore `:425` | textarea `:1213`; "Use template example" `:1277`; dictation, from an effect `:691-695` (Voice click `:1261`) |
| template | draft restore `:423`, `:427` | `handleSelectTemplate` `:770`, `handleSelectCustomTemplate` `:774`; Web/Deck toggle reset `:729-730` |
| design system | **[FIX-103](20260723-FIX-103.md) auto-select of "apple" `:678-682`** (fires when the registry lands, `mode === "prototype"` only); draft restore `:424`, `:426` | `handleSelectBuiltInDs` `:778`, `handleSelectCustomDs` `:782` |
| Discovery answers | none | `onChange={setDiscoveryAnswers}` `:1345` (every `DiscoveryForm` handler is user-driven) |
| attachments | none | `onFilesPicked` `:798` (visible entry set synchronously `:817`, content later `:840-855`), `removeFile` `:787`, image remove `:1237` |
| roster `pipelineAgents` | init `:290`; library re-seed `:469-474`; plan merge `:481-495`; override overlay `:568`; draft restore `:432` | `handleAddAgent` `:736`, `handleRemoveAgent` `:758`, `handleReorderAgents` `:762` (all from AgentsPopup); Web/Deck toggle `:731` |
| selections and gates | draft restore `:435-436`; override overlay `:569`; plan seed `:555` (display-only); ReviewGatesSection's mount report | ReviewGatesSection `toggle`; AgentsPopup edits |

1. **Do not latch inside `handleSelectionsChange` (`:348-351`).** It is the one writer for seeds and edits: draft restore
   `:435`, override overlay `:569`, `handleToggleOverride` `:593`, `:596`, `:607`, the Web/Deck toggle `:732` and the two
   children all call it. Latch at the two child props instead, `ReviewGatesSection` `:1364` and `AgentsPopup` `:1496`.
   Both children call it only from user actions (`ReviewGatesSection.tsx:180-192`; `AgentsPopup.tsx:2849`, and its Cancel
   re-emit `:2774`).
2. **`handleGatesChange` (`:766`, wired at `:1362`) fires on mount and on every roster change with `touched=false`,** and
   `touched` resets to false whenever the roster changes (`ReviewGatesSection.tsx:139-150`, `:173-178`). Latch only on a
   `true` report. Never read `gateSelectionRef.current.touched` as "ever edited".
3. **Dictation and "Use template example" write `brief` outside the textarea handler.** Latch there too: in the dictation
   effect only when `transcript` is non-empty (the Voice click can start with nothing recognised).
4. **Count attachments and Discovery by presence, synchronously.** `attachedFiles` is set at `:817`, before the async
   read, extract and stage resolve, so a Back click in that window already sees it. `!isDiscoveryEmpty(discoveryAnswers)`
   (`lib/launchDraft.ts:149`; the file already imports from that module) does the same for Discovery. Neither needs a latch.
5. **Save is asymmetric.** `handleSaveWorkflow` (`:916`) persists brief, template, design system, roster, selections and
   gates (`selections._wizard`). `handleSaveAsOverride` (`:964`) persists only the roster and selections plus a description
   string. Neither persists attachments or Discovery. Save keeps the page mounted ([ISS-371](20260828-2140-ISS-371.md)'s
   amendment (b)), so a just-saved workflow must not prompt: clear the latch after a successful `handleSaveWorkflow` only.
   Clearing it after Save as my version would hide a brief that is still unsaved.
6. **`handleToggleOverride` (`:582-627`) persists its choice server-side** (`setWorkflowOverrideEnabled`, `:601`, `:620`),
   so it need not set the latch.
7. **A latch cannot un-dirty.** Typing then clearing, or editing in Advanced then Cancel (AgentsPopup re-emits the pre-edit
   snapshot, `AgentsPopup.tsx:2770-2781`), leaves it set, so Back prompts on content that is back to the original. That is
   the safe direction. The alternative is [FIX-702](20261002-0040-FIX-702.md)'s shape, state baselines moved at every seed
   and every save: it handles those two cases but needs a rebaseline at all seven programmatic writers above. The latch is
   the smaller, more robust diff; either is acceptable if it passes the cold-load case below.
