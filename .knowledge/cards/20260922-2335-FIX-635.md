# FIX-635

Closes the half of [QA-SG-004](../../BUGS.md#qa-sg-004) that
[FIX-621](20260922-2009-FIX-621.md) left open: its own "What is deliberately
NOT changed" section says "The silent no-op's exact trigger is still not
proven", and [ISS-775](20260922-1330-ISS-775.md) marks it INFERRED and hands
its confirmation to the fixer. The silent no-op is the headline symptom — the
validator reproduced it 3/3 ("URL stayed on runC", no delayed recovery).

## What was wrong — the trigger, traced link by link

ISS-775 named the suspect: DashboardLayout's `pipelineState`-reactive push
superseding the switch's push. What it could not show is why that effect would
push the OLD run. The missing link is page.tsx's two URL-driven effects:

1. A click-driven switch (bell `onViewResults`, the header dropdown/badge via
   `onGoToPipeline`, History's `onOpenRun`) runs `handleSwitchToLiveRun` /
   `handleSelectWorkflowRun`, whose synchronous prelude sets
   `trackedRunIdRef.current = <new run>`, calls `runStore.switchViewTo` and
   `runConnection.attachRun` (`page.tsx:2795`, `:2816`, `:2830`; `:2955`).
2. `attachRun` replaces the sticky focus and re-materializes `liveRunIds`
   (`RunConnectionProvider.tsx:420-427`), and the context value is memoized on
   it (`:592-595`) — so `runConnection` changes identity. `switchViewTo`
   changes `runStore.viewed.pipelineState.pipelineRunId`. Both are deps of
   `handleSelectWorkflowRun` (`page.tsx:3414`).
3. T7 (`page.tsx:3487-3589`) and T11 (`page.tsx:3601-3804`) list
   `handleSelectWorkflowRun` in their deps, so they re-run — on the
   PRE-remount instance, where `usePathname()` still returns the OLD run's URL
   (the switch's `router.push` is a pending transition). `trackedRunIdRef`
   already names the new run, so the "already tracked" early return misses and
   the effect re-seeds the OLD run: `runStore.switchViewTo(runId)` on the
   liveRunIds fast path (`:3553` / `:3648`), or a full
   `handleSelectWorkflowRun({ id: runId })` (`:3577` / `:3795`).
4. DashboardLayout's pipelineState is `runStore.viewed.pipelineState`
   (`page.tsx:4181`, passed at `:4220`); its effect
   (`DashboardLayout.tsx:805-886`) re-fires on the `pipelineRunId` change and,
   the old run still `isRunning`, calls `router.push(routes.runStream(old))`
   (`:838`).
5. Next 16.2.4 lets a new navigation discard the pending one
   (`node_modules/next/dist/client/components/app-router-instance.js:143-153`,
   "Mark the pending action as discarded ... and start the navigation action
   immediately"). The push to the new run is dropped; the URL stays put.

This accounts for every observation in ISS-775's cycles: the FIRST click from
`/dashboard` always works (neither effect matches a non-run URL); every switch
FROM a run page fails; a retry click fails the same way; no console error; and
the "hybrid" render (title of the old run, Starting-point brief of the new
one) — the re-seed restores the old run's viewport at once, but its brief only
from `sessionStorage` (fast path) or after `getWorkflow` resolves (full
reopen), so `handleSwitchToLiveRun`'s `setSubmittedBrief(<new>)` shows through. `viewPathKey`'s own comment (`page.tsx:442-445`) states the intent
these re-runs violated: fire "only on an actual route change".

## What changed and why there

`frontend/src/app/[...view]/page.tsx` only:

- `:3486` — `const appliedRunViewKeyRef = useRef<string | null>(null);`, the
  path T7/T11 last applied, with the trace above as its comment.
- `:3492-3493` (T7) and `:3606-3607` (T11), right after each effect's
  `runId` check and before anything that can re-seed:
  `if (appliedRunViewKeyRef.current === viewPathKey) return;
  appliedRunViewKeyRef.current = viewPathKey;`

One guard at the one place every caller's fight originated, rather than a
guard per caller: it covers the bell panel (ISS-775), the dropdown and badge
([ISS-778](20260922-1600-ISS-778.md)), History reopens that go through
`handleSelectWorkflowRun` ([ISS-779](20260922-1602-ISS-779.md)), and a launch
or revision started from a run page, which move `trackedRunIdRef` the same way.
It also stops the stale re-run from re-claiming the OLD run's module-scope
switch generation, which would otherwise supersede the new switch's claim
([ISS-780](20260922-1604-ISS-780.md)'s guard, from FIX-621).

Per-mount is deliberate: a real navigation remounts page.tsx (`page.tsx`
T6/T11 comments, "confirmed live"), so the new instance starts at `null` and
applies its URL. Recording only the LAST applied path keeps shallow tab
switches and back/forward (A -> B -> A on one instance) working —
`runTabShallowNav.test.ts` still passes.

## What is deliberately NOT changed

- FIX-621's caller-side `await onSwitchToLiveRun(...)` stays: the test written
  for this bug pins it. With this guard in place the viewed run's reactive
  push (`DashboardLayout.tsx:838`) already navigates immediately when the
  target's store entry is already running (a run this tab has streamed or
  replayed); the await only delays the navigation for any other run. That residual cost is recorded as
  [ISS-851](20260922-2336-ISS-851.md), not changed here.
- DashboardLayout's reactive push is untouched — it is "the single funnel every
  launch path's pipelineRunId flows through" (its own comment); with the
  re-seed gone it no longer has an old run to push.
