## Description

Sibling of [ISS-689](20260918-ISS-689.md) (bug QA-KB-036), derived from its root cause rather than reported independently.

ISS-689 is about a source comment that cites [FIX-247](20260813-0205-FIX-247.md) for terminal-status reconciliation. FIX-247 is the frontend fix "Stop at the clarify gate cancelled the run, but the screen never repainted" (it changes `frontend/src/app/dashboard/page.tsx`); it has nothing to do with `_reconcile_terminal_status`. All four `FIX-247` citations in backend code come from one commit, `f23625911` (2026-09-11):

| site | text |
|---|---|
| `backend/app/api/run_commands.py:840` | `# FIX-247: the degraded verdict must track only the LATEST pipeline_complete ...` (the ISS-689 comment) |
| `backend/app/api/run_commands.py:1031` | `... (FIX-247: _reconcile_terminal_status needs to CLEAR a stale prior-attempt error ...)` above `_UNSET_ERROR` |
| `backend/tests/integration/agents/test_restart_resume_db.py:4380` | docstring of `test_reconcile_degraded_tracks_latest_completion_only`: `FIX-247 (run 4bdf9398): the degraded verdict must read off the LATEST ...` |
| `backend/tests/integration/agents/test_restart_resume_db.py:4422` | docstring of `test_reconcile_clears_stale_error_on_clean_completion`: `FIX-247: a tail that reconciles to completed must clear WorkflowRun.error ...` |

ISS-689's fix scope covers the two `run_commands.py` sites, so that `grep -n FIX-247 backend/app/api/run_commands.py` comes back empty (its own repro step 1). The two test docstrings are outside that file and outside that fix, so they are filed here.

The docstring at `:4380` also repeats ISS-689's second flaw: it says the verdict "must read off the LATEST `pipeline_complete` only", which is the dead last-by-seq mechanism. The live mechanism ([FIX-484](20260902-1600-FIX-484.md)) is "any degraded completion at or after the last attempt boundary (`run_resuming` / `pipeline_start`)". The test's four tails are consistent with both, which is why the docstring went unchallenged (see the test-gap sibling [ISS-886](20261001-2114-ISS-886.md)).

There is no correct card to cite instead. `grep -l f23625911 .knowledge/cards/*.md` matches only ISS-689, INDEX greps for `4bdf9398`, `_UNSET_ERROR` and `persist_resume_status` find nothing, and [FIX-563](20260918-FIX-563.md) covers only the resume-offset half of that commit. Do not invent an id for a docstring: cite run `4bdf9398` as the neighbouring comments do, or file a FIX card for the f23625911 reconcile change through book-keeping if a record is wanted.

## Why the root cause implies this

ISS-689 is a mis-cited explanatory comment left next to code whose behaviour moved on. The same commit wrote the same citation four times, and ISS-689's locked constraint ("A comment must cite the card that actually describes it") applies to each. Someone debugging a failing reconcile test reads `FIX-247` in the docstring and is sent to the frontend, the failure ISS-689 describes for the source comment.

## What would confirm or refute this

Confirmed statically by the analyzer: `grep -rn FIX-247 backend --include='*.py' --exclude-dir=.venv` returns exactly the four lines above (`evidence/qa-kb-036/02-analyze-fix-variants.txt`, section 7), and `git log -S` attributes all four to `f23625911`. The test-file sites have not been reproduced by the validator, so the card stays INFERRED on the line's scale; the impact (a debugger misdirected) is by analogy with ISS-689, not observed.

the LAST ATTEMPT only" and states the boundary rule with FIX-484. `test_reconcile_clears_stale_error_on_clean_completion`

ISS-689. `grep -rn FIX-247 backend --include='*.py' --exclude-dir=.venv` now returns nothing (it returned 4 lines
before). `-k reconcile` gave 22 passed, the same as before. The same test's inline parametrize comments and its
name still use the last-by-seq framing. This card did not name them, so they are filed as
