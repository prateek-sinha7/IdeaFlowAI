# ISS-797

**Register source:** `QA-PS-024` in root `LEDGER.md` / `BUGS.md` — filed by the fix pass
for [FIX-610](20260922-1830-FIX-610.md) as a found-but-not-fixed finding.
[ISS-764](20260922-1424-ISS-764.md) identified it and deliberately left it unfiled; this card
exists so it is not rediscovered from a transcript.

## What is wrong

`frontend/src/components/results/StepsOverviewSpine.tsx:459-463`:

```ts
const statusLabel = failed ? "Run failed" : isRunning ? "Running"
    // Task 11.5 (Req 20): "degraded" MUST NOT read as "Run complete". Both the
    // label text and the non-color indicator below differ from the success state.
    : (pipelineState?.degraded) ? "Run degraded"
    : "Run complete";
```

`cancelled` is one of the three terminal markers `useWorkflow.ts` stamps
(`TERMINAL_MARKER_BY_STATUS`, `useWorkflow.ts:378-389`) and the ternary never asks about
it. A run the user stopped therefore reads **"Run complete"** in the Steps tab's status
summary.

This is a missing branch, not a precedence error — the distinction
[ISS-764](20260922-1424-ISS-764.md) drew:

> Fixing ISS-701's line 408 (gating `failed` on `pipelineState?.failed` alone) does not
> touch this — it is a missing branch, not a precedence error, so it is a separate,
> pre-existing defect with a different required fix (add a `cancelled` arm to the ternary).

## How FIX-610 changed its visibility

Before [FIX-610](20260922-1830-FIX-610.md), a cancelled run that carried a pre-cancel
errored agent hit the `failed` branch and read "Run failed" (that was ISS-764's defect).
With the per-agent term removed from `failed`, that run no longer reads "Run failed" — it
now falls through to **"Run complete"**, joining the cleanly-cancelled case that already
did. FIX-610 did not introduce this branch gap and does not widen it in principle, but it
does mean every cancelled run now takes the fall-through, so the wrong label is uniform
rather than conditional on whether an agent errored.

`LaneRunHeader.tsx:121` does not have this gap — it checks `pipelineState?.cancelled`
ahead of the failed/degraded branch — so the two surfaces on the same page disagree for a
cancelled run.

## Why it was not fixed in the FIX-610 pass

Adding the arm requires choosing the label text and the indicator tone for a run the user
deliberately stopped ("Run cancelled"? "Run stopped"? amber, neutral, or its own token?),
and whether the `notRun` count, the "Not run" chips and the "Pipeline halted — reopen to
resume" banner should render for it. `LaneRunHeader` gives cancelled its own neutral
treatment, while the comment at `LaneRunHeader.tsx:124-126` shows degraded/failed tone
choices here are deliberate product calls, not mechanical ones. That is a product
decision, and neither ISS-701 nor ISS-764 carries it as a proposed fix.

## Evidence

- `frontend/src/components/results/StepsOverviewSpine.tsx:459-463` — the ternary, quoted
  above; no `cancelled` test anywhere in it.
- `frontend/src/hooks/useWorkflow.ts:378-389` — `TERMINAL_MARKER_BY_STATUS` maps
  `cancelled` to its own marker, mutually exclusive from `failed`/`degraded`.
- `frontend/src/hooks/useWorkflow.ts:1397` — `pipeline_cancelled` applies
  `terminalMarkers("cancelled")`; `pipelineState.failed` is never set on this path.
- `frontend/src/components/chat/LaneRunHeader.tsx:121` — the sibling surface that DOES
  check `pipelineState?.cancelled` first.
- `.knowledge/cards/20260922-1424-ISS-764.md` — the analysis that first identified this
  gap and scoped it out.

## What would settle it

A product answer on the label/tone for a cancelled run, then a test built like
`StepsOverviewSpine.cancelledErrorAgent.test.tsx` — render with
`pipelineState: { isRunning: false, cancelled: true }` and assert the chosen label instead
of the current "Run complete".
