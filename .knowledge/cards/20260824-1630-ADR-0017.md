# ADR-0017

## Decision

In the context of composed workflows, where a step has TWO identities — the authored
`instance_id` (`greet`) and the composed runtime id (`custom-agent:greet`) — we decided to
keep route targets authored in the bare form and give the engine a suffix fallback that
resolves them, to achieve manifests that read naturally, accepting that every OTHER
consumer must normalise before comparing.

**Area:** engine, workflow, composer

## Why this is written down

The dual identity is not itself a defect, but forgetting which space you are in is, and it
has now caused three separate failures — each of which looked like something else:

1. **`step_visit_counts` written bare, read composed.** The count was always 0, which
   silently disarmed the R-08 gate-key fold and the completion record. The symptom was a
   loop that appeared not to iterate.
2. **The canvas treating a bare target as a node id.** `routeTargets.has("custom-agent:done")`
   never matched `"done"`, so the branch target rendered as an ORPHAN and every route edge
   failed to resolve. The symptom was "the conditional gate isn't drawing".
3. **The composer keying selections on the bare id while the launch panel keyed on the
   composed id.** Two surfaces built agents differently from the same manifest.

None of these announced themselves as an identity problem. Each looked like a broken
feature until the ids were compared directly.

## The rule

- `depends_on` uses COMPOSED ids and does NOT get a fallback — a bare value there compiles
  and silently does nothing.
- `route.outcomes[*].target` with `trigger: step` uses BARE ids and DOES get the engine's
  fallback (`_route_index` / `_validate_route_targets`).
- `route.outcomes[*].target` with `trigger: workflow` is a WORKFLOW id, not a step id, and
  must never be normalised as one.
- `results[]` entries and `step_visit_counts` keys are COMPOSED.

A consumer that renders or matches steps outside the engine — the canvas, the composer,
any future graph view — must map bare → composed at the boundary, and must leave
`trigger: workflow` targets alone while doing it.
