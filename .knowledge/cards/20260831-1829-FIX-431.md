## Symptom

ppt agents repeatedly `ls`'d the skill mount point and got an empty list:

```
tool_call: ls args={'path': '/skills/html-ppt'}                              -> []
tool_call: ls args={'path': '/skills/html-ppt/templates/full-decks/pitch-deck'} -> []
```

`ppt-composer`'s own preamble read *"the filesystem paths in the SKILL.md don't exist."*
Not fatal — the deck still rendered off the template pipe — but every affected agent
burned turns on failed lookups and reasoned out loud about missing files.

The defect is not ppt-specific. Any catalog skill whose body points at a sibling
("See `root-cause-tracing.md` in this directory") hits it, because the agent resolves
that path SKILL-RELATIVE — at the staged copy's own directory — and nothing but
`SKILL.md` was ever written there.

## Root cause

`backend/app/agents/skill_staging.py:172` (pre-change) — `stage_skills` synthesized a
`SKILL.md` from the catalog entry's `content` and wrote exactly that one file:

    target = sandbox.path_for(f"skills/{skill_id}/SKILL.md")
    target.parent.mkdir(parents=True, exist_ok=True)
    if not (target.exists() and target.read_text(encoding="utf-8") == file_text):
        target.write_text(file_text)

`GlobalSkillEntry.content` is the SKILL.md BODY only — the catalog loader
(`skills_catalog._load_one`) never carries the rest of the skill folder, and
`backend/skills/global/systematic-debugging/` holds 9 further files
(`root-cause-tracing.md`, `condition-based-waiting.md`, `defense-in-depth.md`,
`find-polluter.sh`, ...) that the body names. [FIX-320](20260825-1600-FIX-320.md)
already flagged this in its "Note on scope" as a separate, unfixed limitation.

## Fix

Two files, both in `MOD-backend-app-agents`; `stage_skills` is the single function
every caller routes through (`agents/factory.py:308` is the only production call
site, and both the engine and the fan-out path reach staging only through it).

- `skills_catalog.py:96` — new public `skill_source_dir(skill_id) -> Path`. The
  `skills/global/<id>/` layout is the catalog module's knowledge, not the stager's;
  it is a helper rather than a `GlobalSkillEntry` field on purpose, because
  `app/api/skills.py:38` serialises entries with `asdict(e)` and a new field would
  leak an absolute host path into the API response.
- `skill_staging.py:180` — after the SKILL.md write, copy the rest of the catalog
  folder next to it:

      shutil.copytree(source_dir, target.parent,
                      ignore=shutil.ignore_patterns("SKILL.md"), dirs_exist_ok=True)

  `SKILL.md` is excluded so the synthesized frontmatter (which deepagents parses, and
  silently drops the skill without) always wins. The block sits AFTER
  `staged.append(skill_id)` in its own `try` — a reference-file failure records an
  error but must not unstage a skill whose SKILL.md landed. `copytree`'s default
  `copy2` preserves mtimes, so re-staging the same skill rewrites identical bytes
  with identical stamps and idempotence holds
  (`test_staging_twice_is_idempotent` green).

Nothing else moved: `sources`, `est_tokens` (`464 + 66 * len(staged)`) and the
`SkillsDelivery` shape are byte-identical, the [ADR-0006](20260811-ADR-0006.md) prune
runs before staging and keeps a re-attached skill's whole directory, and the
`^[A-Za-z0-9._-]+$` id guard already ran, so `_GLOBAL_SKILL_DIR / skill_id` cannot
traverse. A non-catalog id simply finds no source dir and copies nothing.

## Not fixed here

`backend/agents/workflows/ppt/workflow.yaml`'s header comment still describes the
mount-point mismatch and the manifest still deliberately attaches no skills, delivering
`html-ppt` through `injects: [template, template_example]` instead. That workaround was
left alone: `html-ppt` is not in `backend/skills/global/` on this branch, so there is no
catalog folder for this fix to copy from, and reverting the manifest would be a product
change the card does not ask for. The generic staging defect the card names is what is
closed here.
