# ISS-956

## What happened

INFERRED sibling of [BUG-024](20260827-BUG-024.md) (QA-KB-049). Not reproduced in a browser.

The report names `/runs/{id}/audit`, `/files` and `/steps`. The mechanism BUG-024 resolves to, the
`pipelineState.isRunning` funnel in `DashboardLayout.tsx`, contains no reference to the URL, so every other URL a
run can be opened at should be rewritten the same way while the run is live:

| URL | Screen (`frontend/src/lib/routes.ts`) | What the rewrite costs |
|---|---|---|
| `/runs/{id}` | `run-detail` (`:364`) | the route the user asked for is replaced by `/stream` |
| `/runs/{id}/steps/{agentId}` | `run-steps-agent` (`:395`) | the agent deep link ([ISS-277](20260828-1659-ISS-277.md)) is lost along with the tab |
| `/runs/{id}/workspace` | `run-workspace` (`:406`) | Workspace tab forced to Steps |
| `/runs/{id}/versions/{v}` and `/versions/{v}/{tab}` | `run-version` (`:377`) and the pinned tabs | the `/versions/{v}` pin is dropped as well |
| `/runs/{id}/preview/full` | `run-preview-full` (`:421`) | Preview tab forced to Steps |

Expected: the requested URL and tab survive a cold load while the run is generating (BUG-024's Expected).
Actual (INFERRED): `/runs/{id}/stream` with the Steps tab.

## Root cause (CONFIRMED by source read; the behaviour is INFERRED)

`frontend/src/components/layout/DashboardLayout.tsx:854-856`:

```ts
      if (incomingRunId) {
        router.push(routes.runStream(incomingRunId));
      }
```

`reopenedRunIdFor` (`frontend/src/app/[...view]/page.tsx:208-222`) returns the run id for exactly these screens
(`run-detail`, `run-steps`, `run-steps-agent`, `run-files`, `run-workspace`, `run-audit`, `run-version`,
`run-preview-full`), so T7 (`page.tsx:3462-3564`) runs the same `handleSelectWorkflowRun` replay for each one, and
that replay is what flips `isRunning` (see BUG-024). The three tabs in the report are three of eight screens, not a
property of those tabs.

## What settles it

A vitest over every screen: set the jsdom URL with `window.history.replaceState(null, "", "/runs/run-live/<suffix>")`,
render `DashboardLayout` with a `pipelineState` that is running with `pipelineRunId: "run-live"` (pattern:
`frontend/src/components/layout/DashboardLayout.iss656.test.tsx`), and assert `push` was not called with
`/runs/run-live/stream`.

Two fixes that look right fail it: one that whitelists `/audit|/files|/steps`, and one that tests
`pathname.startsWith("/runs/run-live/")`, which misses the bare `/runs/run-live` (no trailing slash).

The pinned form needs a decision as well as a test. `run-version`'s `runId` is the family ROOT, while the live run may
be a later member. If the live member differs from the id in the URL the push still happens, which is what
`PreviewPanel.tsx:911-913` does on purpose for a running member ("Follow it live instead").

## Fixed by the root fix?

Yes, if the guard compares `parseViewPath(location.pathname).runId` with the incoming run id (see BUG-024). This card
only adds the test matrix.

## TEST COVERAGE — ISS-956

## Fixed — QA-KB-049 (fixer, 2026-10-02): [FIX-712](20261002-1155-FIX-712.md)

The root fix landed as this card expected. The guard compares `parseViewPath(location.pathname).runId` with the
incoming run id, so it uses neither a whitelist nor `startsWith`. The matrix from "What settles it" is now
`frontend/src/components/layout/DashboardLayout.bug024.test.tsx`. It covers all eight screens plus the pinned `/versions/2/files`: 12 passed with the fix, and 9 failed |
3 passed with the guard removed. A URL that names a different run still pushes (the test's run-parent/run-child
control). So a pinned root URL whose live member differs still follows the live member, as `PreviewPanel.tsx:911-913`
intends. Not driven in a browser.
