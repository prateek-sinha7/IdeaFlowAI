# FIX-233

**Phase / trigger:** quick-260812-gsf

> No detail section exists in the register for this entry — only the
> summary-table row below. Nothing has been invented to fill the gap.

## Description

The Concierge was pre-fed the ENTIRE run through three unbounded read tools — one chat question re-fed 9,227,107 chars ≈ 2,306,776 tokens, on two runs 144% and 151% of everything the whole pipeline recorded — while its own model spend was discarded and therefore unmeasurable. Replaced the read surface with seven bounded, on-demand tools and made the spend a durable number. The issue row blamed the wrong event type, and that was load-bearing: the payload is 18 agent_input rows (7,290,638 chars, largest 479,605), NOT agent_chunk (max row 169 chars) — a chunk filter would have fixed almost nothing. Two further unbounded tools the row never mentioned: list_refs() projected artifact bodies inline (5,804,067 chars ≈ 1.45M tok in one call) and get_ref() returned bodies up to 389,651. Two security defects fixed alongside, each proven by a RED test: exclude_builtin_tools was never passed, so the model held write_file/edit_file/read_file/ls/glob/grep/write_todos — a filesystem WRITE surface on an app REST path, contradicting this module's own docstring; and ScopedStore.get_ref scopes by owner + visibility but never by run, so a prompt-injected ref_id could reach another run of the same owner.

## Root cause

(1) concierge.py:365 drained the runner with a bare if event["type"] != "chunk": continue, discarding every usage event; converse runs in a background task spawned AFTER the run settles, outside execute()'s lifetime, so neither aux_token_usage nor _apply_terminal_completion could ever see it. (2) concierge.py:434 called scoped_store.read_events(run_id, 0) — no LIMIT, no type filter — and the system prompt ORDERED the model to call it. (3) the runner defaults exclude_builtin_tools=False, excluding only the sub-agent tool.
