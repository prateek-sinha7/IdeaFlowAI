## What happened (INFERRED — not yet independently reproduced)

[ISS-322](20260828-2007-ISS-322.md) established that `handleSessionExpiry()`
(`frontend/src/lib/api.ts:175-180`) sends the browser to `routes.login({ expired: true })`
with no `redirect` param at all, for every one of its confirmed 13 call sites. Both routes the
2-validator actually drove through this failure (`/settings/ai-model`,
`/runs/<id>/workspace`) are bare pathnames with no query string of their own — the fix and its
regression tests have no evidence yet of what happens on a protected route that carries
meaningful state in its OWN query string.

`/analytics` is exactly that shape: `frontend/src/components/analytics/AnalyticsPage.tsx:134`
reads `searchParams.get("range")` and `:141` reads `searchParams.get("pipeline")` to seed
`dateFilter`/`pipelineFilter` on mount — so `/analytics?range=7d&pipeline=ppt` is a real,
reachable, protected URL whose filter state lives entirely in the query string, not the path.

## Why the root cause implies this

Two distinct but related consequences follow from the same mechanism:

1. **Today, under the unfixed bug**: since `handleSessionExpiry()` currently attaches no
   `redirect` at all, landing on `/dashboard` after re-login already discards `range`/`pipeline`
   exactly as it discards the path — this is not a new mechanism, just an unvalidated instance
   of ISS-322's own already-general claim ("every entry route hits the same bug").
2. **Once the proposed fix lands**: ISS-322's fix passes
   `window.location.pathname + window.location.search` as the new `redirect` value. That value
   must be nested safely inside `routes.login`'s OWN query string
   (`/login?expired=true&redirect=<...>`). `frontend/src/lib/routes.ts`'s `buildQueryString`
   (lines 7-19) already does this correctly today — `URLSearchParams.set()` percent-encodes the
   value, so a `redirect` containing its own `?range=7d&pipeline=ppt` cannot corrupt the outer
   query string. But `buildLoginRedirect()` in `frontend/src/lib/authRedirect.ts:43-49` (the
   already-working signed-out mechanism ISS-322 proposes mirroring) builds its URL by
   **string interpolation** (`` `/login?redirect=${encodeURIComponent(current)}` ``), not
   `buildQueryString`. If the fixer copies that pattern's *shape* into `routes.login` without
   also routing it back through the shared `URLSearchParams`-based builder — or hand-rolls the
   concatenation directly in `handleSessionExpiry()` instead of extending `routes.login` per
   `MOD-frontend-src-lib`'s own documented invariant ("routes.ts is the single source ... for
   both directions") — a query-string-bearing route is the one shape that would surface the
   mistake; a bare-pathname route would not.

## Expected vs actual (once ISS-322's fix lands)

- **Expected:** a mid-session expiry on `/analytics?range=7d&pipeline=ppt` preserves both the
  screen and its filters — `redirect=%2Fanalytics%3Frange%3D7d%26pipeline%3Dppt`, correctly
  nested, decoded back to the exact original URL by `resolveRedirectTarget` on arrival.
- **Actual (inferred, today):** discarded entirely, same as every other route (ISS-322's
  existing scope). **Risk (inferred, post-fix):** if the fix does not nest the value through
  `buildQueryString`/`URLSearchParams`, the original route's own `&pipeline=ppt` could leak out
  as a top-level `/login` param instead of staying part of `redirect`, silently truncating the
  return target to `/analytics?range=7d` or worse.

## What would settle it

Reproduce ISS-322's own steps (corrupt `auth_token`, trigger the 401 ladder) starting from
`/analytics?range=7d&pipeline=ppt` instead of the two routes already validated, both before and
after the fix lands — confirm the pre-fix loss, then confirm the post-fix `redirect` value
round-trips through `resolveRedirectTarget` without truncation.
