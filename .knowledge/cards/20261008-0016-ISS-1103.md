# ISS-1103

## Analysis (QA-KB-102, analyzer, 2026-10-08, HEAD 3bfff3990): CONFIRMED

This card began as an INFERRED lead from the QA-KB-097 analysis. Bug row `QA-KB-102` ("A user resume that dies before its first dispatch ends silently", Medium) is this card, and the question the lead left open (can a user reach a silent exit through `POST /api/runs/{id}/resume`?) is settled by running the real endpoint over the real engine, offline. The sections from `## Description` down are the original lead, kept as written; where this analysis disagrees with them it says so.

One correction to the bug report. It says the run ends with "no failed status". The row does end `failed` for a failed or degraded run (the reconcile's fail-safe; a cancelled run goes back to `cancelled`); what it lacks is a reason, a terminal event, and any signal to the user.

### Root cause: the resume tier has no failure channel

CONFIRMED by reading and by the probe.

- `_drive_resumed_stream`, the one funnel every resume driver reaches `_execute_impl` through, wraps the whole drive in `except Exception` and logs one WARNING (`engine.py:16030-16031`). It does not re-raise and emits no event.
- `resume_run` leaves through five bare `return`s (guards at `engine.py:15569`, `:15642`, `:15698`, `:15717`, `:15729`) and `_replay_clarify_run` through seven (guards at `:16108`, `:16154`, `:16178`, `:16194`, `:16206`, `:16223`, `:16238`), each after a WARNING and `_fire_resume_cleanup`.
- The launch entry is built the other way. `execute()` re-raises unchanged, "so every existing caller behavior (DB write, event emission) is untouched" (`engine.py:4255-4271`), and the launch driver's `except` writes an `error` frame, `status="failed"` and `.error=str(e)` (`run_commands.py:4368-4396`). The engine relies on that: its `finally` yields no terminal event for an unhandled exception (`engine.py:7619-7626`, `:7692-7697`), and a quarantined sandbox is a deliberate `RuntimeError` that must "propagate to abort the run" (`engine.py:4503-4524`). The resume funnel is the one caller that does not hold up its side.
- The app layer promised the other half and cannot keep it. `_drive_user_resume` flips the row back to `failed` with the reason only when `resume_run` raises (`run_commands.py:792-796`, T-50-06), and `resume_run` raises only from statements outside the swallow, for example its first `workflow_runs` read and `RunTrace(RunSandbox(...))` at `engine.py:15922-15928`. Whether a fault is recorded depends on which line it hits.
- `_reconcile_terminal_status` then reads an attempt with no events: no terminal event after the marker is the D2 fail-safe, `failed` (`run_commands.py:926-935`), and with nothing to derive a message from it "leave[s] the existing `.error` value untouched rather than invent one" (`:997-1000`).

### Settled: reachable through the endpoint

Real `resume_run_endpoint` and real `ExecutionEngine` armed with the `app/main.py:159-190` hooks, in-memory SQLite, no model call (`evidence/qa-kb-102/analysis-04-silent-resume-endpoint-probe.txt`, 9 passed in a scratch module outside the suite). Control: a valid composed manifest reaches `_drive_resumed_stream`.

| scenario | HTTP | `resume_run` | `_flip_back_to_failed` | durable tail after the marker | row after | live queue |
|---|---|---|---|---|---|---|
| A: persisted manifest no longer compiles, run `failed` | 200 | returned `None` | 0 calls | nothing | `failed`, `.error` = the previous attempt's text | `[None]` |
| A, run `cancelled` | 200 | `None` | 0 | nothing | `cancelled`, `.error` stale | `[None]` |
| A, run `degraded` | 200 | `None` | 0 | nothing | `failed`, `.error` stale | `[None]` |
| B2: roster empty and plan uncompilable (SIMULATED drift) | 200 | `None` | 0 | nothing | `failed` | `[None]` |
| C: `_execute_impl` raises before dispatch (sandbox reconciles to `quarantined`) | 200 | `None` | 0 | nothing | `failed` | `[None, None]` |
| G: fault before the funnel's `try` (control) | 200 | RAISED | 1 call | nothing | `failed`, `.error` = the fault | `[]`; done task and queue stay registered |
| D: restart auto-resume, no endpoint | n/a | `None` | n/a | one more marker per restart | `running` | n/a |
| B1: run type absent from the entitlement whitelist | 403 `tier_not_entitled` | not reached | | | | |

In every silent row the only trace is one server WARNING, for example `resume_run(..): persisted manifest failed to recompile (unknown deliverable 'no_such_deliverable_resolver' in workflow 'composed-three-step') - refusing to resume with a substitute roster`, or `resumed-stream drive(..) failed mid-drive: sandbox quarantined for run ..: repository is corrupt and requires operator action`. Scenario C's fault through `engine.execute()` raises `RuntimeError` to its caller, which is what the launch driver records.

So the lead's closing test is answered: the endpoint does not refuse earlier except for a pipeline id the tier whitelist does not know (B1: `_require_tier_entitlement` at `run_commands.py:700` calls `can_run_pipeline`, `entitlements.py:112-124`). A composed run whose manifest stops compiling, and any fault inside `_execute_impl` before the first event, pass every gate and end silently.

### What the user sees

CONFIRMED by source read; not driven in a browser. The click returns 200 and attaches the stream. The lane's "Restarting run…" indicator is cleared only by `pipeline_start` (`isPipelineRunning`) or a failed POST, and it is rendered before any failed or cancelled copy, so the owner sees an animated "Restarting run…" with no reason and no button until a reload ([ISS-1121](20261008-1450-ISS-1121.md)). After the reload the run reads `failed` (or `cancelled`) with the previous attempt's error text. Nothing tells them the resume was refused.

### How often (honest)

This is a latent defect in the data available here. The local dev DB holds 10 `run_resuming` markers and all 10 are followed by a `pipeline_start` (`analysis-01`). Of the 26 runs in a resumable status, 0 would end silently today: 24 would drive and 2 (type `user_stories_v2`, an id no checkout carries a manifest for) would be refused with 403 by the endpoint, or failed loudly by the restart classifier (`analysis-02`, `analysis-03`). None of the 57 dev runs carries a composed manifest: `manifest_json` is JSON `null` on 38 and SQL `NULL` on 19 (`analysis-06`), so the manifest exit has no instance in real data. The mechanism is reachable by construction: a persisted manifest that stops compiling after a registry or compiler change, a corrupt sandbox, a transient DB fault inside `_execute_impl`.

### Blast radius

- Callers of the funnel: `_drive_resumed_stream` is called from `resume_run` (`engine.py:15844`) and `_replay_clarify_run` (`:16282`) only. `resume_run` is reached from `_drive_user_resume` (`run_commands.py:792`), `_admitted_resume` (restart auto-resume, `engine.py:12868`, [ISS-1119](20261008-1450-ISS-1119.md)) and `_rearm_gate_run` (review gate, `:12999`); `_replay_clarify_run` from `_rearm_gate_run` (`:13006`, [ISS-1120](20261008-1450-ISS-1120.md)).
- What goes without a failure event: the reconcile (status, `.error`, [ISS-1122](20261008-1450-ISS-1122.md)), the SSE replay and the live queue, the history list, and the frontend lane ([ISS-1121](20261008-1450-ISS-1121.md)). The DB-only flip-back is the one recorder and tells nobody live ([ISS-1123](20261008-1450-ISS-1123.md)).
- No test asserts any of it ([ISS-1124](20261008-1450-ISS-1124.md)).

### Where the fix belongs

In the engine funnel, so every driver inherits it; nothing in the app layer is needed for the user path.

1. One private engine helper, called from the `except` in `_drive_resumed_stream` and from each failing early return of `resume_run` and `_replay_clarify_run`. It logs at ERROR with the reason; appends exactly one terminal `pipeline_failed` carrying the reason (inside the funnel through the loop's own stamp-persist-push block, outside it through `ScopedStore.append_event_at_or_after`, as `_stamp_resume_marker` does); transitions the state machine to `failed`, which persists `workflow_runs.status` and is what the restart drivers need because they have no app wrapper (every in-engine failure branch does the same, `engine.py:7514`, `:7553`, `:7579`, `:7603`); and pushes the frame to the live queue when one is registered. The exception itself is still not re-raised, which keeps the stated intent of the swallow ("a resume failure must not crash startup").
2. Inside the funnel, skip the synthesized event when the stream already yielded a terminal one (`pipeline_failed`, `pipeline_complete`, `pipeline_cancelled`, `pipeline_diverted`): [FIX-669](20261001-1918-FIX-669.md) locks "exactly one pipeline_failed".
3. Nothing for `_reconcile_terminal_status`: it already maps a `pipeline_failed` at or after the `run_resuming` boundary to `failed` and derives `.error` from its payload (`run_commands.py:986-998`). The DB-only flip-back ([ISS-1123](20261008-1450-ISS-1123.md)) and the lane ([ISS-1121](20261008-1450-ISS-1121.md)) need their own changes.

This supersedes the lead's hint that the early returns "could surface theirs" through `_flip_back_to_failed`: that function is app-layer (the engine may not import `app.*`) and runs only on a raise, and the restart and re-arm drivers have no wrapper to catch one.

### Not the fix

- Falling back to the registry roster so the resume "works". [FIX-576](20260901-0324-FIX-576.md) locks "Resume recompiles `workflow_runs.manifest_json` and FAILS CLOSED when it no longer compiles". The refusal stays; only its reporting changes.
- Raising from `_drive_resumed_stream`. The restart drivers would leave an unretrieved task exception and the same `running` row.
- Making `_reconcile_terminal_status` invent an error string. It cannot know the reason.
- Re-deriving this from [BUG-R01-resume](20260803-BUG-R01-resume.md): that fix resolved one trigger (the alias) and left the bail generic.

## Description

INFERRED sibling of [ISS-1101](20261008-0016-ISS-1101.md). The state-machine lock of [ISS-1101](20261008-0016-ISS-1101.md) reaches nobody as an error because the resume driver turns a drive that is dead on arrival into silence. The same silence applies to any other reason a resume cannot start, and for those the endpoint has no eviction step to prevent it.

What was observed (CONFIRMED, in the test harness): after a `_drive_user_resume` whose drive died on entry, the run row is `status='failed'` with `error=None` (the attempt recorded no reason), and the durable event tail ends `… 39:pipeline_failed, 40:run_resuming, 41:workflow_validated`: the marker of the attempt and one validation event, no `agent_error`, no `pipeline_failed`, no `pipeline_complete` (`evidence/qa-kb-097/analysis-plugins/kb097_dump.py` on `test_failed_run_resumes_skips_completed_tasks`, output in `evidence/qa-kb-097/analysis-15-swallowed-resume-durable-state.txt`; the same run with the state machine cleared continues `42:pipeline_start, 43:agent_start, …` to `completed`).

## Mechanism (CONFIRMED by reading)

- `_drive_resumed_stream` wraps the whole drive in `except Exception as exc:  # noqa: BLE001 — a resume failure must not crash startup` and only logs a WARNING (`engine.py:16030-16031`).
- `resume_run` itself returns silently, after a WARNING and `_fire_resume_cleanup`, in at least four places: no `workflow_runs` row (`:15569-15575`), a persisted manifest that no longer compiles ("refusing to resume with a substitute roster", `:15642-15653`), an unresolvable agent list (`:15698-15702`), an empty agent list (`:15729-15735`); a plan that cannot be compiled for an empty roster is a fifth (`:15717-15723`).
- `_drive_user_resume` (`run_commands.py:792-796`) only flips back to `failed` with a reason when `resume_run` RAISES, which it never does for the cases above. It goes on to `_reconcile_terminal_status`, which finds no event of this attempt, derives `failed`, and leaves `.error` untouched ("leave the existing ``.error`` value untouched rather than invent one", `run_commands.py:999-1000`); `_persist_resume_status` (`:1005`, def `:1021`) then stamps `completed_at`.

## What was INFERRED, and what settled it (settled 2026-10-08: see "Settled: reachable through the endpoint" above)

The endpoint evicts the state machine (`run_commands.py:745`), so the one trigger seen here cannot fire through `POST /api/runs/{id}/resume`. Whether a user can reach one of the other silent exits is not demonstrated. Settle it by resuming (through the endpoint, offline harness) a composed run whose persisted manifest no longer compiles: expect 200 `{run_id}`, `workflow_runs.status` back to `failed`, no new `agent_error` / `pipeline_failed` and an unchanged `error`. If that holds this is a minor-to-medium UX defect in the headline "reopen and fix" feature (the click appears to do nothing); if the endpoint refuses earlier it is a non-issue and this card closes as not-reproducible.

Fix direction, only once reproduced: no new event type is needed; `_flip_back_to_failed(run_id, reason)` (`run_commands.py:1008`) already persists a reason, and the early returns of `resume_run` could surface theirs the same way. That changes what a user sees after a refused resume, so it should be agreed before it is built.

## Resolution (5-fixer, QA-KB-102, 2026-10-08)
