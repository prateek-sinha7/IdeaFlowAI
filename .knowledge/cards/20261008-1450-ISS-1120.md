# ISS-1120

**Register source:** sibling derived during the `QA-KB-102` analysis on 2026-10-08 (root [ISS-1103](20261008-0016-ISS-1103.md)). Not its own bug row.

**Confidence:** INFERRED. The returns and the shared swallow are CONFIRMED by reading; the consequence for a parked run is read from the code and from a recorded earlier incident, not reproduced here. What would settle it: the restart harness (`tests/integration/agents/test_restart_resume_db.py`) with a composed run parked at an open Clarify gate whose manifest no longer compiles, then `restore_non_terminal_runs`, then `POST /api/runs/{id}/answers`. Expect 200 and no event after the answers.

## Condition

`restore_non_terminal_runs` branch (a) (`engine.py:12680-12808`) re-arms a `waiting_for_user` run: it recreates the store waiter and clears it ("armed", `:12749-12756`) BEFORE it spawns `_rearm_gate_run`. That driver calls `resume_run` for an open review gate (`:12998-12999`) or `_replay_clarify_run` for an open Clarify round (`:13006`). Either can leave without driving anything:

| exit in `_replay_clarify_run` | line |
|---|---|
| no `workflow_runs` row | `engine.py:16108` |
| persisted manifest no longer compiles | `:16154` |
| agent list cannot be resolved | `:16178` |
| plan cannot compile for an empty roster | `:16194` |
| empty agent list | `:16206` |
| no open questionnaire gate - "skipping" | `:16223` |
| open gate has no durable questions - "leaving parked" | `:16238` |

plus the five `resume_run` exits of [ISS-1103](20261008-0016-ISS-1103.md) for the review-gate case. Every one logs a WARNING, calls `_fire_resume_cleanup` and returns, and the funnel swallows anything `_execute_impl` raises (`:16030-16031`).

## Expected vs actual

Expected: a re-arm that cannot start either fails the run visibly (the WR-05 rule, `engine.py:12702-12712`, which already fails an uncompilable `waiting_for_user` run with a message) or parks it knowingly.

Actual: the status stays `waiting_for_user`, the waiter stays armed, no coroutine awaits it, and the answer or approval is accepted and does nothing. This is the shape [BUG-R01-resume](20260803-BUG-R01-resume.md) recorded live on 2026-07-19 (run 75979e2c: `_replay_clarify_run ... empty agent list - nothing to replay`, then `POST /answers` returned 200 `{"ok":true,"count":5}` and "0 new events after 40s+"). That fix resolved the alias before the roster lookup; `test_restart_resume_db.py:3779-3792` states the bail itself is "generic: any stored type whose roster comes back empty still black-holes the restart". The bail was never made loud.

Two of the seven are decisions rather than failures ("no open questionnaire gate", "open gate has no durable questions"). Whether those should surface is for the owner of the re-arm design; the other five are faults.

## Why the root cause implies it

`_replay_clarify_run` and `_rearm_gate_run` reach the same `_drive_resumed_stream` funnel and use the same log-and-return exits as `resume_run`. [ISS-1103](20261008-0016-ISS-1103.md)'s helper has to be called from them too, or the user-resume path is fixed and the restart paths are not.

## Resolution (5-fixer, QA-KB-102, 2026-10-08)

Resolved by [FIX-768](20261008-1540-FIX-768.md). The five fault exits of `_replay_clarify_run` (no row, manifest, agents, plan, empty roster) call `_fail_resume`, so the parked run ends `failed` with a `pipeline_failed`, and `_cleanup_pipeline` evicts its store waiter. The two decision exits ("no open questionnaire gate", "open gate has no durable questions") are unchanged and left to the re-arm owner.
