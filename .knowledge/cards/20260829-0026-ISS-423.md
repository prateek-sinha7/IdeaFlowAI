## Why this must also be broken

[ISS-312](20260828-1941-ISS-312.md)'s confirmed root cause is `handleFiles()` inside
`useBriefAttachments()` in `frontend/src/components/workflow/IdeaInputPage.tsx` (lines
512-523): the `isTextFile` branch does `content.slice(0, ATTACH_MAX_CHARS)` with no
truncation flag ever computed, while the sibling `isBinaryFile` branch (lines 524-535) calls
`extractFileText()` and appends a visible `[Content truncated to N chars]` note whenever
`res.truncated` is true.

`grep -rn "ATTACH_MAX_CHARS" frontend/src` returns exactly three hits: the constant's own
declaration in `frontend/src/lib/constants.ts`, `IdeaInputPage.tsx`, and
`LaunchWizard.tsx`. `LaunchWizard.tsx` is **not** a caller of `IdeaInputPage.tsx`'s
`handleFiles`/`useBriefAttachments` — `grep -rln "useBriefAttachments\|BriefAttachBox"
frontend/src` returns only `IdeaInputPage.tsx`, `AgentsPopup.tsx`, `ComposerPage.tsx` and
`CanvasView.tsx`; `LaunchWizard.tsx` is absent. It carries its own, independently-forked
`onFilesPicked` callback (lines 631-676) that reproduces the identical split byte-for-byte:

```tsx
// LaunchWizard.tsx:651-659

} else if (isBinaryFile) {

  //   setAttachedFileContents((p) => [...p, { name: res.filename, content: `${res.text}${truncNote}` }]);
```

Same asymmetry, same missing computation on the text side, same source file that already
proved (via [FIX-304](20260825-2115-FIX-304.md)) that `LaunchWizard`'s `MODE_CONFIG` is
typed `"prototype" | "ppt"` — it is the ONLY host for `/create/prototype` and `/create/ppt`;
every other built-in pipeline type renders `IdeaInputPage` instead. The chip render at
`LaunchWizard.tsx:935-946` shows only `file.name`, matching ISS-312's "no size, no
truncation state" finding — the same missing secondary signal.

The composed run message carries the identical marker format with no truncation note,
confirmed at `LaunchWizard.tsx:794-797`:

```tsx
const fileBlocks = attachedFileContents
  .map((f) => `\n\n=== Attached: ${f.name} ===\n${f.content}\n=== End: ${f.name} ===`)
  .join("");
if (fileBlocks) finalBrief = `${finalBrief}${fileBlocks}`;
```

`finalBrief` is the real payload sent to the run (not decorative) — the same mechanism ISS-312
reproduced on `/create/app`.

## Expected vs actual

**Expected:** attaching an oversized `.txt`/`.md`/`.json`/`.csv` file on `/create/ppt` or
`/create/prototype` shows the same visible truncation signal the binary path already
provides on those same two pages.

**Actual (INFERRED — not yet independently browser-reproduced):** the same silent slice
with zero indication should reproduce on `/create/ppt` and `/create/prototype`, since the
code is a byte-for-byte fork of the confirmed-broken branch, not a shared call into it.

## What would confirm or refute this

Repeat ISS-312's exact repro (a `.txt` file whose content exceeds 450,000 chars) on
`/create/prototype` and `/create/ppt` instead of `/create/app`; intercept the outgoing run
request the same way and check the body for a truncation marker.

## Where the fix belongs

**Not** the same file as ISS-312's eventual fix. Because `LaunchWizard.tsx`'s
`onFilesPicked` is a forked duplicate rather than a caller of `useBriefAttachments()`, a fix
inside `IdeaInputPage.tsx` alone does not reach this file. The two `isTextFile` branches
(`IdeaInputPage.tsx:514-523`, `LaunchWizard.tsx:653-659`) are textually identical, so the
smallest correct fix is one shared helper — e.g. exported from `frontend/src/lib/constants.ts`
alongside `ATTACH_MAX_CHARS`, something like `truncateAttachmentText(content): { content,
truncated }` — that both files' `isTextFile` branches call. One guard, two call sites, rather
than hand-patching each fork separately and risking a third drift later.
