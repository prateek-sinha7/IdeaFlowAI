# ISS-1087

Sibling of [ISS-1072](20261007-2125-ISS-1072.md), derived during the analysis of register entry **QA-KB-095** (`LEDGER.md`).
**Status: INFERRED.** Every link of the chain below was read or run on its own; no page load of a real family in this
state was observed, because the dev database holds none (scan of all 16 older members that carry a DB tag: 0 are in this
state, `evidence/qa-kb-095/07-analyze-tag-vs-sandbox-scan.txt`).

## Condition

A revision-family member that is NOT the family's last member, whose DB `git_tag` is set, opened at its own `/runs/{id}`,
while the sandbox is a LIVE one (it has files and a `.git`) whose tag list no longer contains that tag.

How a sandbox gets there is already documented: [ISS-697](20260922-1000-ISS-697.md) mechanism 2, confirmed with live rows on
2026-09-22. The directory is TTL-swept, a later revision re-creates it, `git_init_sandbox` builds a `.git` from nothing, and the
new revision tags only itself. In that family the DB said `v1`, `NULL`, `v3` and the sandbox listed `["v3"]`.

## Expected vs actual

- **Expected:** the older member's page asks for no ref the sandbox does not have, and shows its derived content from the run
  record. No 4xx.
- **Actual:** `PreviewPanel.tsx:890-891` still sets `displayRef` to the member's DB tag, so the header resolve
  (`:1502` `resolveRunDeliverable(..., displayRef ?? undefined)`), the Files row (`FilesTab.tsx:573-588`), the PDF preview and
  the header Download all request `?ref=v1`. The API is right to refuse it: `_validate_ref` (`run_files.py:872-883`) is
  fail-closed against the sandbox's real tag list, and a live sandbox is never "expired".

## Why the root cause implies it

[ISS-1072](20261007-2125-ISS-1072.md)'s root is one disagreement between two sources: the DB column says a snapshot exists,
the sandbox's git says it does not. On the reported run the sandbox is an empty husk, and the fix there is server-side
(an empty directory is an expired workspace). With a non-empty sandbox the server cannot call it expired, the 400 is the correct
answer, and the only party that can avoid the request is the page, which has the answer in hand: `RunHeader` already fetches
`GET /sandbox/refs` (`RunHeader.tsx:308-316`) and already reconciles it with `FamilyMember.git_tag` for the menu
(`RunHeader.tsx:327`, `latestReachableByTag`). `displayRef` is the one consumer that does not.

## What is confirmed, what is not

- CONFIRMED (read): `git_tag` is written only after `create_tag` returns (`engine.py:2637` then `:2653`), so a non-NULL column is a
  historical fact, never a statement about the sandbox now. The family endpoint returns the raw column (`runs.py:1766-1768`).
- CONFIRMED (run, offline): a live sandbox with files and a `.git` but no `v1` tag answers 400 on the listing, zip and file
  routes (`evidence/qa-kb-095/13-analyze-scratch-backend-run.txt`, the TAGLESS rows; the same fixture shape is pinned by
  `test_tagless_git_sandbox_rejects_ref_400`, ISS-724).
- CONFIRMED (render, offline): the real `PreviewPanel` asks for `ref=v1` whenever the member is not the newest and has a DB tag,
  with `getRunSandboxRefs` answering `[]` (`evidence/qa-kb-095/11-analyze-scratch-run.txt`, probe A). Nothing else feeds the value.
- NOT reproduced: the whole chain on a real family. That needs a family whose sandbox was swept and then revised.

## Fix direction, and the trap in it

One reconciliation in `PreviewPanel`, used by all three DB-tag derivations (this card covers `displayRef`; the other two are
[ISS-1090](20261007-2246-ISS-1090.md)): `usableTag(member) = member.git_tag if the sandbox lists it, else null`.

1. **Never map a lost tag to `undefined`.** `undefined` is the live tree, which is the NEWEST member's files ([FIX-717](20261002-1243-FIX-717.md)'s
   locked constraint). A lost tag is `null` ("no snapshot"), which FilesTab (`:573`), SandboxPdfPreview and the Figma path already
   read as "keep the fallback".
2. **The header Download is [ISS-1051](20261002-1242-ISS-1051.md)'s open call.** The header resolves with `displayRef ?? undefined`
   (`PreviewPanel.tsx:1496`, `:1502`), the live tree. Mapping the lost tag to `null` alone would turn today's accidental
   "Download disabled" (the 400 is swallowed at `:1505-1508`) into "Download hands over the newest member's file under the older
   member's name". Skip the header resolve for a lost tag so it stays disabled with no request, and leave ISS-1051's decision alone.
3. **Three states, not two.** The refs list is unknown while it loads and unknown again if the fetch fails, and `RunHeader`'s inner catch
   turns a failure into `[]` (`:313`). Treating that `[]` as "no tags" would drop good tags. Hold the ref-scoped reads until the list
   has loaded, and on a failed fetch keep today's behaviour.
4. **One list, one request.** `getRunSandboxRefs` uses `request()`, not `singleFlightGet` (`api.ts:1730-1739`), so a second caller
   is a second request. Lift the state `RunHeader` owns, or share it. `RunHeader.test.tsx` mocks the function, and ISS-1011 records
   PreviewPanel tests whose `@/lib/api` mock omits it: keep the dynamic-import-and-swallow idiom (`RunHeader.tsx:301-316`).
5. **Refresh it** when the family's tags change; a revision completing adds one.
