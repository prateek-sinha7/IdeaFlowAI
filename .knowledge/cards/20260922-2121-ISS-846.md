## Root cause (re-confirmed by direct read, 2026-09-22)

`handleWebSocketMessage` (`frontend/src/app/[...view]/page.tsx:1063`) is
subscribed to the live SSE fan-out unconditionally:

```ts
// page.tsx:2424-2434
const runSubscribe = runConnection.subscribe;
useEffect(() => {
  const unsubscribe = runSubscribe((m) =>
    handleWebSocketMessage({ type: m.type, data: m.data } as unknown as StreamMessage, m._sourceRunId),
  );
  return unsubscribe;
}, [runSubscribe, handleWebSocketMessage]);
```

No third argument is passed, so `isReplay` is `undefined` on every live
frame and `recentsToken()` (`page.tsx:1071`,
`= () => (isReplay ? null : getToken())`) behaves exactly like
`getToken()` — the durable-replay guard does not apply here, by design
(confirmed against its own card,
[FIX-624](20260922-2027-FIX-624.md): "Live SSE
(`page.tsx:2414`) passes nothing and is untouched"). Nine branches of
the same switch statement call `getWorkflows(token, { limit: 50 })`
(~37 KB) whenever their event fires on a LIVE run:

| Event | call site |
|---|---|
| `pipeline_complete` (immediate) | `page.tsx:1723` |
| `pipeline_complete` (KAN-120, 2s delayed) | `page.tsx:1752` |
| `pipeline_failed` | `page.tsx:1799` |
| `pipeline_diverted` | `page.tsx:1836` |
| `pipeline_cancelled` | `page.tsx:1885` |
| `questionnaire_ready` | `page.tsx:2122` |
| `questionnaire_complete` | `page.tsx:2147` |
| `review_gate_ready` | `page.tsx:2204` |
| `review_gate_approved` | `page.tsx:2240` |

This `useEffect` carries no `mainView`/screen condition. `page.tsx` is
the single catch-all behind `routes.ts`
([ADR-0018](20260824-1631-ADR-0018.md)) — every screen (`home`,
`history`, `library`, `execution`, `settings`, wizard routes, etc.) is a
mutually-exclusive `mainView === "<x>" && (...)` branch rendered by the
SAME mounted `DashboardLayout` instance (`DashboardLayout.tsx:2896-3200`),
and `page.tsx` already documents the same consequence for a DIFFERENT
fetch on [ISS-793](20260922-1826-ISS-793.md)'s card: "hooks run on every
render of this catch-all regardless of which branch it returns." The
MOUNT-time recents fetch is deliberately skipped in wizard mode
(`page.tsx:1030`, `if (wizardModeFor(parsedView)) return;`, added for
ISS-793) — but none of the nine live-event branches above has an
equivalent guard.

`RunConnectionProvider` delivers SSE frames for every run this browser
TAB has attached, regardless of which screen is open
(`frontend/src/providers/RunConnectionProvider.tsx:279-330`,
`attachRun`/`tab_launched_run_ids` in `sessionStorage`) — attachment
survives navigation because it lives in a provider mounted once in the
root layout, not in `page.tsx`'s per-route state.

## Expected vs actual

Expected: the recents-refresh cost QA-PS-047/ISS-842 measured (5-9
redundant `runs?limit=50` calls, 185-450+ KB, per run lifecycle) is paid
only while a user is actually looking at that run's stream page.

Actual (INFERRED from the code above): the identical cost is paid no
matter what the tab is showing — `/dashboard`, `/library`, `/create/ppt`
(a wizard route that never renders `recentRuns` at all and explicitly
opts OUT of the mount-time version of this same fetch), `/analytics` —
for as long as this tab has a background run attached. A user who
launches a build and browses elsewhere while it completes still pays
the full redundant traffic ISS-842 measured, off-screen where nobody is
watching the badge it's refreshing.

### What would confirm it

Launch a run, immediately navigate to `/library` (or any non-`/runs/*`
route), and watch Network while the backgrounded run fires a
`questionnaire_ready`/`review_gate_ready`/`pipeline_complete` event —
expect the same `runs?limit=50` pattern ISS-842 captured on
`/runs/{id}/stream`, on a screen with no visible use for it.

## Note on ISS-842's second-fetch attribution

ISS-842 attributes part of the observed 2x-per-event multiplier to
`frontend/src/components/history/WorkflowHistory.tsx:244-256`'s
`recentRunsRef`-keyed effect. Direct read here could not confirm that
component is mounted during the `/runs/{id}/stream` repro:
`<WorkflowHistory>` renders from exactly one production site
(`DashboardLayout.tsx:2957`; `grep -rn "<WorkflowHistory" frontend/src/`
finds no other JSX usage), gated `{mainView === "history" && (...)}`.
`routes.ts` parses the `stream` subpath to `{ screen: 'run-stream' }`
(`frontend/src/lib/routes.ts:393-396`), and `page.tsx`'s
`initialMainViewFor` maps `"run-stream"` to `"execution"`, never
`"history"` (`page.tsx:163-177`) — `mainView` is a single
`useState<MainView>` kept in sync with that mapping
(`DashboardLayout.tsx:558-588`). On a direct navigation to the stream
route this should leave `WorkflowHistory` unmounted, in tension with
ISS-842's attribution. Not asserting ISS-842 is wrong — flagging that
this one sub-claim needs a live check (a mount/unmount log on
`WorkflowHistory`, or a React DevTools snapshot during the repro) that
neither card has run yet. Whichever component the second call turns out
to be, it does not change the fix location below: the CONFIRMED
page.tsx mechanism above is already sufficient on its own to justify
the redundant traffic and its fix.

Also checked and deliberately NOT re-carding: the original QA-PS-047
report (`BUGS.md#qa-ps-047`, filed 2026-09-17) additionally named a
"Problem 2" — the home page/`HomeLaunchGrid` staying mounted underneath
the stream overlay. `mainView`'s single-value, mutually-exclusive render
(above) plus the `initialMainView` URL re-sync effect
(`DashboardLayout.tsx:579-588`, part of the 015-frontend-routing work)
look like they already prevent that; ISS-842's own 2026-09-22
revalidation does not reproduce or mention it either. Reading this as
resolved by the intervening routing fixes rather than re-carding it —
an inference from current code, not a live re-test of Problem 2
specifically.

## Where the fix belongs

Not nine patches (or ten, if `WorkflowHistory`'s effect is confirmed as
a real second caller). `handleWebSocketMessage`'s nine live-reachable
`getWorkflows({limit:50})` bindings should collapse into ONE coalesced
refresh: each branch sets a dirty flag/ref instead of calling
`getWorkflows` directly, drained by a single short-debounced effect (a
few hundred ms is enough to coalesce a burst like
`questionnaire_ready`+`questionnaire_complete`, or the KAN-120
immediate+delayed pair, into one network call).
[FIX-616](20260922-1923-FIX-616.md)'s
`inFlightWorkflows` map does not already cover this — it collapses calls
that are concurrently in-flight at the same instant, not sequential
calls seconds apart (confirmed by re-reading FIX-616's and
[FIX-624](20260922-2027-FIX-624.md)'s own scope
notes; neither claims to cover this event-driven path). Any other
confirmed live caller (`WorkflowHistory` or otherwise) should route
through the SAME dirty-flag/coalescing mechanism rather than keep an
independent effect, so every consumer of "did the recents list change"
shares one fetch regardless of which screen triggered it.
