Reproduced 3/3 from a cold start on `/workflows/ppt/canvas` (qa-admin, light theme, default
viewport). Every cycle: fresh navigation to `/dashboard`, confirm `auth_token` present, then
navigate directly to `http://localhost:3000/workflows/ppt/canvas` (lands on Canvas tab), read
the "Deliverable strategy" combobox's selected value via `el.value` / `el.options[el.selectedIndex].text`,
click "Simple", read the read-only "Deliverable type" field
(`[data-testid="composer-deliverable-type"]`).

| Cycle | Canvas combobox (selected) | Simple "Deliverable type" |
|---|---|---|
| 1 | `Streamed text — agent's raw output` | `Custom` |
| 2 | `ppt — declared by this workflow` (value `ppt`, a 4th option not present in cycle 1's option list) | `Custom` |
| 3 | `ppt — declared by this workflow` (value `ppt`) | `Custom` |

The two views never once agreed with each other. Ground truth via `GET /api/workflows/ppt`:
`deliverable.strategy` is `"ppt"`, `deliverable.name` is `"presentation.pptx"`.

**Refines BUG-20260828-073350-workflows-ppt-canvas's report**: the register entry describes
Canvas as consistently showing the wrong "Streamed text" option. Across this validation's 3
cycles, Canvas's combobox itself was non-deterministic — cycle 1 showed the wrong "Streamed
text" fallback (only 3 static options present), cycles 2 and 3 showed a correct, dynamically
injected 4th option `ppt — declared by this workflow` (`value="ppt"`). That variability appears
to be a separate timing/race condition inside `CanvasView.tsx`'s combobox population and was not
narrowed further here — it is out of scope for this card. What is constant, and what this card
covers, is that **Simple's label never varies and never agrees with whatever Canvas shows**: it
is hardcoded, not derived from the workflow's real deliverable.

## Root cause

`frontend/src/components/workflow/composer/ComposerPage.tsx:448`:

```ts
// Hardcoded ("Custom"), not derived from `workflowType`: this component only
// ever legitimately represents the "custom" pipeline, but `workflowType` is a
// shared mutable variable other screens can leave stale — that stale value
// was showing as "User Stories · Composer" in the header for a workflow that
// was never actually a User Stories run.
const deliverableLabel = PIPELINE_LABEL.custom;
```

This value is passed straight into `IdentityCard`'s `deliverableLabel` prop
(`ComposerPage.tsx:1157`), which renders it read-only at
`IdentityCard.tsx:49-63` (`data-testid="composer-deliverable-type"`). The prior fix that put this
comment in place (deliberately decoupling the label from the stale shared `workflowType`
variable) over-corrected: it replaced "sometimes wrong, derived" with "always wrong for
non-custom built-ins, constant". `CanvasView.tsx`'s "Deliverable strategy" combobox, by
contrast, independently derives its value from the workflow's actual `deliverable` config, so it
is the one component of the two that can ever show the true strategy — but the two components
never share that derivation, so nothing keeps their displayed labels consistent with each other.

## Expected vs actual

Expected: Simple and Canvas, showing the same unsaved, unmodified in-memory workflow, should
report the same deliverable type — ideally the real `ppt` strategy, or at minimum an identical
honest fallback.

Actual: Simple always renders the literal string "Custom" regardless of the real deliverable;
Canvas renders a value computed from the actual state (sometimes correct, sometimes falling back
incorrectly — see the non-determinism noted above, tracked separately). The two never match.

## Root cause (3-analyzer, 2026-08-29)

**CONFIRMED** — `frontend/src/components/workflow/composer/ComposerPage.tsx:478` (line drifted
from the validator's `:448`/`:1157` due to unrelated edits elsewhere in the file since that pass;
same statement, re-read at the current line):

```ts
const deliverableLabel = PIPELINE_LABEL.custom;
```

This is the ONLY place `deliverableLabel` is computed, and it is consumed exactly twice, both in
`ComposerPage.tsx` (`grep -rn "deliverableLabel\|<IdentityCard\b" frontend/src` confirms both
hits land in this one file):

- `:1195` — passed into `<IdentityCard deliverableLabel={deliverableLabel} .../>`. `IdentityCard`
  has exactly one call site in the whole frontend, and it is this one
  (`grep -rn "<IdentityCard\b" frontend/src` → one match). `IdentityCard.tsx:56-60` renders the
  value verbatim, read-only, `data-testid="composer-deliverable-type"` — the field this card's
  repro table reads.
- `:1020` — the shared header title: `` {builtinCanvasType ? `${initialName || builtinCanvasType} · copy` : `${deliverableLabel} · Composer`} ``.
  Only reached when `builtinCanvasType` is falsy, so it does not fire for this card's `ppt` repro
  (`builtinCanvasType` is truthy there) — see [ISS-580](20260829-0236-ISS-580.md) for the entry
  path where it does fire.

Neither read touches `runConfig`. Meanwhile `CanvasView.tsx:1574` — the sibling tab rendering the
SAME in-memory workflow — computes its own combobox value as
`runConfig?.deliverable?.strategy ?? "streamed_text"`: the real, already-fetched deliverable
config `ComposerPage` already holds in its own `runConfig` state
(`ComposerPage.tsx:410`, seeded at `:426-430` from `initialRunConfig`, itself wired as
`initialRunConfig={savedComposition?.runConfig}` at `DashboardLayout.tsx:3001`). `CanvasView` also
has a deliberate, commented fallback (`CanvasView.tsx:1594` `KNOWN_STRATEGIES = new
Set(["streamed_text", "single_file", "serialized_sandbox"])` — exactly the three
`user_allowed=True` resolvers per `ADR-0027` — and `:1712-1716`) for a strategy outside that set:
it injects a 4th, disabled `<option>` reading `"${strategy} — declared by this workflow"`. `ppt`'s
own manifest (`backend/agents/workflows/ppt/workflow.yaml:42-44`) declares `deliverable: {strategy:
ppt, name: presentation.pptx}` — not one of the 3 known strategies, which is exactly why Canvas's
honest fallback is the option this card's cycles 2-3 observed.

So the mechanism is exactly what the validator's original "Root cause" section already named,
re-confirmed at the current line: `IdentityCard`'s Simple-tab label is a component-scoped constant
that never reads `runConfig`, while `CanvasView`'s combobox already does — the two views share no
derivation, so nothing keeps them consistent, and Simple can only "accidentally" agree with Canvas
when a workflow's real strategy genuinely is the generic `custom`/`streamed_text` case (a
from-scratch composition that was never saved with a different strategy).

**INFERRED** (out of THIS card's scope, same boundary the validator already drew — not re-derived
here): the validator's own cycle-1-vs-2/3 table shows Canvas's combobox is itself
non-deterministic on cold load — cycle 1 fell back to the generic "Streamed text" option before
`runConfig` finished seeding, cycles 2-3 showed the correct dynamic `ppt` option once seeded. That
is a separate timing defect in the `runConfig` seeding race (adjacent to `ISS-196`'s save-side
seeding gap, a different symptom of a related mechanism), not in the Simple-tab label this card
covers — Simple is wrong 3/3 regardless of that race, since it never reads `runConfig` at all.

## Blast radius

`deliverableLabel` and `<IdentityCard>` each have exactly one call site, so this is not a
fan-out-of-callers problem — it is a fan-out-of-ROUTES problem. `ComposerPage`'s Simple tab is the
SAME component for every built-in: `builtinCanvasTypeFor()` (`frontend/src/app/[...view]/page.tsx:367`)
derives the type generically from the URL segment for `/workflows/<type>/canvas`, "no hardcoded
workflow list" (`frontend/src/lib/routes.ts:295,297`). Read every top-level built-in's own
declared `deliverable:` block directly (`backend/agents/workflows/<name>/workflow.yaml`):

| built-in | `deliverable.strategy` | Canvas would show | Simple always shows |
|---|---|---|---|
| `ppt` | `ppt` | dynamic "ppt — declared by this workflow" (this card's repro) | `Custom` |
| `ppt_v2` | `single_file` | "Single file — one file from the workspace" | `Custom` |
| `prototype` | `single_file` | "Single file — one file from the workspace" | `Custom` |
| `app_builder` | `serialized_sandbox` | "Serialized sandbox — zip the workspace" | `Custom` |
| `mulesoft_to_springboot` | `serialized_sandbox` | "Serialized sandbox — zip the workspace" | `Custom` |
| `dotnet_to_azure` | `serialized_sandbox` | "Serialized sandbox — zip the workspace" | `Custom` |
| `user_stories` | `streamed_text` | "Streamed text — agent's raw output" | `Custom` |

Every one of these disagrees with Canvas the identical way the reported `ppt` case does — `ppt`
is simply the one that got hunted and validated first. This is CONFIRMED by the code (the label
computation cannot vary by route param), though the other 6 routes were not independently clicked
through in a browser during this pass. A genuinely different entry CONDITION (not just a
different route param through the same code) is filed separately as
[ISS-580](20260829-0236-ISS-580.md) — a saved custom workflow, not a built-in.

## Proposed fix — and where it belongs

`ComposerPage.tsx:478` already has everything it needs in scope: `runConfig` (`:410`), the exact
same value `CanvasView` reads. The fix is to derive `deliverableLabel` from
`runConfig?.deliverable?.strategy` through a SHARED label lookup — not from `PIPELINE_LABEL` (a
different vocabulary: pipeline TYPE names like "Presentation"/"Prototype", not deliverable
STRATEGY names) and not by reverting to the stale `workflowType` the `:478` comment already
documents fixing away. Concretely: export one small
`deliverableStrategyLabel(strategy?: string): string` (mirroring `CanvasView`'s existing
`KNOWN_STRATEGIES` vocabulary — "Streamed text"/"Single file"/"Serialized sandbox", falling back
to an honest `"${strategy} — declared by this workflow"` for anything else, i.e. the same string
`CanvasView`'s dynamic option already renders) from ONE place both components import — e.g.
alongside `CanvasView`'s own `FORMAT_OPTIONS`/`KNOWN_STRATEGIES`, or hoisted next to
`PIPELINE_LABEL` in `AgentsPopup.tsx`. That is a smaller diff than teaching `IdentityCard` a second
copy of the same mapping, and it is the only way to guarantee Simple and Canvas cannot diverge
again — `CanvasView` already proves the derivation is possible from data `ComposerPage` already
holds in `runConfig`. This is a pure frontend rendering/label concern: it does not touch manifest
compilation, the registry, or the built-in-override write path (`ADR-0027`/`ADR-0033`), so no
engine or trust-boundary invariant is at risk from fixing it here.
