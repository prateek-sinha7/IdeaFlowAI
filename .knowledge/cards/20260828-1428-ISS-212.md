## Summary

**Sibling of [ISS-202](20260828-1409-ISS-202.md), derived from its root
cause — INFERRED, not yet reproduced on an actual in-progress run.**

ISS-202 established that `AuditTab.tsx`'s hook_runs merge loop
(`frontend/src/components/results/AuditTab.tsx:558-585`) unconditionally
assigns `category: "gate"` / `fineCategory: "gate"` to every
`hooksEnv.hook_runs` row — including ordinary `audit_logger` lifecycle
telemetry (`before_step`/`after_step`/`tool_call`/`tool_result`, always
`outcome: "continue"`) — because `deriveFineCategory("gate", hookName,
step)` (line 568, function at lines 281-295) only escalates to `"security"`
or `"behavioral"` on a regex match and otherwise falls back to
`source === "gate" ? "gate" : "validation"`, and the hook_runs loop always
passes `"gate"` as `source`.

That merge logic is triggered from a `useEffect` whose dependency array is
`[workflowRunId]` only (`AuditTab.tsx:451-597`, confirmed by direct read —
the effect body calls `getRunGateEvents` / `getRunValidationResults` /
`getRunExecRuns` / `getRunHookRuns` once per mount and never re-fetches on a
WS event or a timer). The component's `isRunning` prop (declared line 70,
destructured line 443) is referenced at exactly three call sites — lines
723, 812 and 849 — all of which are render-only (a "live" badge, an
"Elapsed … in progress" indicator, a violet monitoring banner). None of them
gate, filter, or alter the fetch/merge logic in any way.

**Implication:** the fabrication mechanism is state-independent by
construction. The moment a run in progress has completed at least one step
(so the default `audit_logger` hook — injected on every step of every
workflow, `backend/agents/workflows/compiler.py:818-830`,
`_DEFAULT_AUDIT_HOOKS = ["audit_logger", "secret_scan"]` — has written its
first `hook_runs` row), navigating to that run's Audit tab while it is still
`isRunning=true` should show the identical Governance-count inflation and
identical boilerplate detail panels that ISS-202 documents for a completed
run — just with a smaller row count so far, growing as the run continues
(each `AuditTab` mount is a fresh REST snapshot, not a live stream, so the
count would not visibly tick up without a re-navigation/remount).

## What would confirm or refute this

1. Start (or find already-running) a pipeline run.
2. While it is still in progress (`isRunning` banner visible), navigate to
   `/runs/{id}/audit`.
3. Confirm: Governance count > 0 with no corresponding `gate_events` rows,
   and every hook-run row bearing hook `audit_logger` expands to the same
   boilerplate `Action: allowed` / `Outcome: continue` text ISS-202
   documents for the completed-run case.
4. If the counts/behavior differ from ISS-202's completed-run reproduction
   in any way, this card is refuted and should be marked so.

## Expected vs Actual

**Expected:** if ISS-202's root cause is fixed at the shared merge/derive
site, both the completed-run and in-progress-run Audit tab should stop
fabricating Governance/Gate rows — there is only one code path, so there
should not be a run-state-dependent exception.

**Actual (predicted, unverified):** prior to that fix, an in-progress run's
Audit tab fabricates the same rows in real time, which is arguably more
misleading than the completed-run case — a user watching a "live" governance
count climb while a run executes has even stronger reason to believe real
policy gates are firing.
