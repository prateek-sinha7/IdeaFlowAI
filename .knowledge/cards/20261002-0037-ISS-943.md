## What is broken

Found by the QA-KB-011 fixer on 2026-10-02 while checking that [FIX-701](20261002-0037-FIX-701.md)'s
[ISS-920](20261001-2221-ISS-920.md) gate releases correctly. It was not reported and it was not fixed: no card
covered it and no test existed for it.

**Condition.** A saved prototype or ppt workflow (a `user_workflows` row, opened through `/workflows/{id}/run`)
whose roster has FEWER agents than the built-in's compiled plan, for example one agent removed in Advanced before
saving. `[...view]/page.tsx` stages the draft with `agentIds: saved.agent_ids` and mounts `LaunchWizard`
(see [ISS-920](20261001-2221-ISS-920.md)). LaunchWizard's override effect then fetches the built-in's detail
(`getWorkflowDetail(token, pipeline)`, `LaunchWizard.tsx:518`), not the saved row's.

**Expected.** Continue launches the saved roster, and every save from this screen persists it.

**Actual (CONFIRMED offline, component harness; never run end to end in a browser).** The launch draft carries
the plan's full roster. The probe `evidence/qa-kb-011/10-fix-scratch-plan-completion.test.tsx.txt` (two
`it`s, both pass on the 2026-10-02 working tree) restores a draft with `agentIds: ["prototype-plan"]` and resolves
`getWorkflowDetail` with the five prototype steps. In both cases the launch draft carries all five ids:

- E, cold (library empty at mount, lands after the detail): `["prototype-specify","prototype-plan","prototype-analyze","prototype-build","prototype-validate"]`
- F, warm (library preloaded, so there is no load window at all): the same five.

Control: with `steps: []` in the detail, the same restore launches `["prototype-plan"]`
(`evidence/qa-kb-011/09-fix-scratch-check.test.tsx.txt`, case D). So the plan merge is what replaces the roster.
Run outputs: `evidence/qa-kb-011/11-fix-test-runs.txt`.

## Mechanism (read at file:line)

- The draft restore sets the saved roster directly: `if (restored.length > 0) setPipelineAgents(restored);`
  (`LaunchWizard.tsx:432`).
- The spec-017 completion effect (`:481-495`, deps `[planAgents, libraryAgents]`) keeps `prev` only when
  `planAgents.length <= prev.length && !(planHasTree && !prevHasTree)` (`:492`); otherwise it returns
  `mergePlanWithLibrary(planAgents, libraryAgents)` (`:493`).
- Warm path: the restore runs first, the detail lands later, `setPlanAgents(planProj.agents)` (`:551`) re-runs the
  completion effect and the five-row plan beats the one-row saved roster.
- Cold path: the library landing re-runs the restore effect and then the completion effect in the same flush (both
  depend on `libraryAgents`). The completion's functional updater sees the restored roster as `prev` and replaces it.

The effect's own comment (`:476-480`) says it leaves "any lineup the user has edited or added to" alone. It does
not protect a lineup that is shorter because the user removed agents, and a restored saved roster is exactly that.
The guard was written to complete a PARTIAL LIBRARY roster (`ppt_v2` reuses ppt's steps, `:300-306`), not to
override a roster the user saved.

## Blast radius (INFERRED except the launch path)

- Continue / `handleLaunch` (`:1000-1058`): CONFIRMED offline above. `agentIds` are a subset selector at launch
  (`launch_run`'s `if agent_ids:` branch, per [ISS-920](20261001-2221-ISS-920.md)), so the run executes the
  full built-in roster while the header shows the saved workflow's name.
- AgentsPopup's footer "Save workflow" PATCHes the saved row when `userWorkflowId` is known (see
  [ISS-284](20260828-1906-ISS-284.md)'s blast radius), so opening a saved shorter workflow and saving from
  Advanced would write the plan roster over the saved one. INFERRED, not run; REFUTED by the Analysis below (`frontend/src/lib/api.ts:2648-2652`).
- Page-level "Save workflow" creates a new row with the plan roster, and "Save as my version" would UPSERT the
  plan roster as the override. INFERRED, not run.
- A user with an ENABLED override is not affected at launch (the server swaps in the override).

## Not decided here

The fix touches the spec-017 completion guard, which exists for partial library rosters. Whether a restored draft
roster should be exempt from completion, and how to tell it apart from a partial library roster, is analysis work.
[FIX-701](20261002-0037-FIX-701.md) did not touch this effect.

## Analysis (QA-KB-048, 3-analyzer, 2026-10-02)

**Claim status.** Root cause CONFIRMED: every link below was read in the working tree on top of `024c03ef8`, and the symptom was
reproduced 3/3 by the validator (`evidence/qa-kb-048/01..03-*.txt`). The recommended fix is INFERRED: it was not run, the 5-fixer
owns it. Verbatim quotes with line numbers: `evidence/qa-kb-048/04-analyze-code-quotes.txt`.

### Root cause (CONFIRMED)

One mechanism: the completion effect (`frontend/src/components/workflow/LaunchWizard.tsx:481-495`) decides whether a roster is
"partial" by LENGTH alone, and nothing records that the roster on screen came from a saved workflow.

1. The restore sets the saved roster with a plain `setPipelineAgents(restored)` (`:428-433`) and leaves no trace of where it came from.
2. The guard (`:492`) is `planAgents.length <= prev.length && !(planHasTree && !prevHasTree)`. A saved roster with fewer rows than the
   plan falls through to `return mergePlanWithLibrary(planAgents, libraryAgents)` (`:493`): it looks exactly like the partial LIBRARY
   roster the effect was written for. The effect's comment (`:476-480`) promises to leave "any lineup the user has edited or added to"
   alone, but only the "plan is not longer" half is implemented. The tree half would also replace a flat restored roster at EQUAL
   length whenever the plan carries children.
3. Both paths end there. Warm: the restore runs at mount and the plan lands later (`setPlanAgents`, `:551`, re-runs the effect). Cold:
   the library landing re-runs the restore and the completion in one flush, and the completion's updater reads the restored roster as `prev`.

It is the third effect in this component to overwrite a restored roster. [FIX-338](20260828-2221-FIX-338.md) made the default-derive effect (`:469-474`) a functional updater;
[FIX-701](20261002-0037-FIX-701.md) stopped Continue running before the restore. The completion effect (its comment first appears in commit `70665bbcb`, 2026-08-27) was never given the same rule.

### Where it is reachable

- What the wizard's `defaultAgentsFor(libraryAgents, mode)` yields per mode against the compiled plan (probe,
  `evidence/qa-kb-048/06-analyze-engine-seam-probe-output.txt`): prototype 5 of 5, ppt 3 of 3, ppt_v2 2 of 4, prototype_v2 0 of 11. So
  completion is a no-op on a fresh prototype or ppt open and does real work only for ppt_v2 (fills 2) and prototype_v2 (fills all 11).
- From the code read, a saved roster shorter than the plan can come out of the wizard UI only for ppt_v2 (INFERRED: the Remove button was not clicked, and rows can
  also arrive from the API or old data). The prototype and ppt core agents are LOCKED
  (`AgentsPopup.tsx:177-181`), but `getRole` (`:210-248`) returns "optional" for a pipeline with no entry in its table, and ppt_v2 and
  prototype_v2 have none, so `handleRemove` (`:2822-2826`) lets the user drop any ppt_v2 agent. prototype_v2's ids are `custom-agent:*`,
  which the library cannot resolve, so `restored` is empty there and this bug cannot fire. The validator's roster (one prototype agent)
  is something only an API call or an old row can produce: right for a regression test, not what a user does. The dev database holds no
  saved wizard rows to inspect (`evidence/qa-kb-048/07-analyze-saved-workflows-select.txt`, 0 rows in `workflows`).

### Correction to "Blast radius" above

The second bullet (AgentsPopup's footer "Save workflow" would write the plan roster over the saved row) is REFUTED. `saveUserWorkflow` drops
`agent_ids` and `base_pipeline_type` whenever `userWorkflowId` is set (`frontend/src/lib/api.ts:2648-2652`:
`const { base_pipeline_type: _bpt, agent_ids: _aids, ...updateBody } = body`), and `updateUserWorkflow` has no field for them
(`:2607-2617`, "composition is immutable after creation"). That footer save PATCHes name, description and `selections`, never the roster.
The first and third bullets are upgraded from INFERRED to CONFIRMED by reading (table above).

### Where the fix belongs

The completion effect, `LaunchWizard.tsx:481-495`. It is the one sink: every consumer above reads `pipelineAgents`. Do not patch the consumers,
`handleLaunch` / the `buildLaunchDraft` arguments (pinned by FIX-701's locked constraints, `LaunchWizard.test.tsx` and `launchDraft.parity.test.ts`),
the `page.tsx` staging or `DashboardLayout`.

Recommended (INFERRED, not run):

1. `const savedRosterRef = useRef(false)` beside `agentRestorePending` (`:298`).
2. Restore, `:432`: `if (restored.length > 0) { setPipelineAgents(restored); savedRosterRef.current = true; }`.
3. Completion updater, first line, before the length and tree tests: `if (savedRosterRef.current) return prev;`. A restored roster is the user's, so
   neither test may touch it; a fresh open (ref false) keeps completing ppt_v2's partial library roster. This holds on the cold path too: the ref is written
   inside the restore effect, which is declared before the completion effect, and a functional updater runs at the next render, so the flag is already true when the
   completion's updater reads it in that flush (INFERRED from React's ordering, not run).
4. `handleModeChange` (`:724-734`): `savedRosterRef.current = false`. The Web/Deck toggle re-sources the lineup from the library (`:731`) and the next plan
   must be allowed to complete it. With a stale `true`, restore then toggle web then deck leaves ppt_v2 on its 2-agent library default.

Alternative to evaluate: an identity-based guard instead of a flag, completing only a lineup that is empty or exactly the library default
(`defaultAgentsFor(libraryAgents, mode)`). It needs no reset and also protects a lineup the user edited, which the comment at `:476-480` already claims.
It also keeps completing a legacy ppt_v2 row saved while the 2-agent library default was on screen (possible before FIX-701 gated the save buttons); restored
without completion, `["ppt-deck-qa-v2","ppt-code-generator"]` would hit `launch_run`'s 422 `workflow_unsatisfiable` (`backend/app/api/run_commands.py:3563-3570`). Hazard:
do NOT add `mode` or `defaultAgentIds` to the effect's deps. On a toggle the effect would run once in the commit where `mode` changed, with the previous family's
`planAgents` still set and the new family's default as `prev`, and complete the wrong family's plan into the lineup.

### What this fix does not do

It makes the launch draft and every save carry the saved roster. It does not make the RUN execute it: for a satisfiable subset the engine re-expands it to the full plan,
and for an unsatisfiable one `launch_run` answers 422. That is a separate contract question needing an owner decision, carded as [ISS-966](20261002-0320-ISS-966.md). A different way a
restored roster loses agents (custom-pool ids dropped by the restore mapping) is [ISS-967](20261002-0320-ISS-967.md).

## Resolution (QA-KB-048, 5-fixer, 2026-10-02)

Resolved by [FIX-714](20261002-1159-FIX-714.md) in `frontend/src/components/workflow/LaunchWizard.tsx`. Steps 1, 3 and 4
of "Recommended" were applied as written: the `savedRosterRef` beside `agentRestorePending`, the guard as the
completion updater's first line, and the reset in `handleModeChange`. Step 2 was narrowed using the analysis's own
"Alternative to evaluate". The restore sets the ref only when the restored ids differ from
`defaultAgentsFor(libraryAgents, initialMode)`, so a restored exact copy of the library default is still completed.
The reason is checked offline: a ppt_v2 row equal to the 2-agent default is refused by `presort_specs`, which means a
launch_run 422 (`evidence/qa-kb-048/12-fix-presort-legacy-ppt_v2-row.txt`). The completion effect's deps are
unchanged. The card test `LaunchWizard.savedRoster.iss943.test.tsx` XPASSes 3/3, and the guards (a), (c) and the ppt_v2
3-of-4 case pass in a scratch run (`evidence/qa-kb-048/08..11`). The run still executing the full plan for a satisfiable
subset is [ISS-966](20261002-0320-ISS-966.md), which is open for an owner decision.
