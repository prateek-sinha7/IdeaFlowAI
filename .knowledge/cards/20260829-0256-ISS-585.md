## What happened (INFERRED — not yet reproduced live)

[ISS-355](20260828-2105-ISS-355.md) confirmed the root cause of
`BUG-20260828-080047-runs-id-steps`: `ToolCallsSection`'s collapsed one-line
tool-call preview (`frontend/src/components/results/AgentDetailPanel.tsx:412`)
coerces each `tc.args` value with bare `String(v)`, which yields
`[object Object]` for a plain object and `[object Object],[object Object],...`
(truncated to `[object Object],[object`) for an array of objects — e.g. the
`write_todos` tool's `todos` array. That confirmation (3/3, cold start every
cycle) was performed exclusively against one pre-existing **`completed`** run
(`/runs/b9feac1c-ec21-4531-8ba7-bb391786993e/steps`) — see ISS-355's
"Conditions" line: `run state completed (pre-existing run, populated with real
tool-call history — not a live/generating run)`.

Reading the render path that reaches `ToolCallsSection` shows nothing in it is
specific to a completed run:

- `AgentDetailPanel.tsx:1104` renders
  `{agent.toolCalls && agent.toolCalls.length > 0 && <ToolCallsSection toolCalls={agent.toolCalls} />}`
  — gated only on the array being non-empty, no `isRunning`/run-status check.
  Contrast this with the `ReasoningCard` block a few lines above it
  (`AgentDetailPanel.tsx:1063-1070`), which IS explicitly gated on
  `isRunning` (`live={isRunning && !outputStarted}` /
  `{isRunning && outputStarted && <ReasoningCard ... live ... />}`) — proving
  the component tree distinguishes live vs settled state elsewhere, just not
  for this section.
- `agent.toolCalls` is populated identically whether the run is live or
  completed. During a live run, `frontend/src/hooks/useWorkflow.ts:1057-1064`
  handles the `tool_call` SSE case and appends an entry with
  `args: (msg.args as Record<string, unknown>) || {}` taken straight from the
  backend message — the same `ToolCallEntry` shape
  (`frontend/src/types/index.ts:803-808`, `args: Record<string, unknown>`)
  that a completed run's stored `toolCalls` uses.
- The one live/done distinction that DOES exist inside `ToolCallsSection`
  (`tc.result != null ? "ok" : "…"`, line 414-415) only affects the status
  pill, not the `String(v)` args-preview expression on line 412.

So the same broken expression that ISS-355 confirmed against a completed
run's history should fire identically the moment a live run's agent issues a
tool call whose argument is an array or object (e.g. `write_todos` mid-run):
the "Tool calls" panel would show the garbled `[object Object]` preview in
real time, before the run reaches `completed` — not only when reviewing
history afterward.

## Why the root cause implies this

`ToolCallsSection` is one function with one call site
(`AgentDetailPanel.tsx:1104`), and that call site does not branch on run
status. A defect in the function's rendering logic is a property of the
function, not of the data source (completed-run fetch vs live SSE stream)
used to trigger it during validation, because both sources feed it the exact
same `ToolCallEntry[]` shape.

A `failed` run is not treated as a separate sibling here: once a run reaches
any terminal state its `toolCalls` are static, so `failed` renders through
the identical "settled" code path already covered by ISS-355's `completed`
repro — there is no distinct mechanism for `failed` the way there is for
`generating` (SSE-driven incremental updates).

## Expected vs actual

- **Expected:** the collapsed tool-call preview renders correctly regardless
  of whether the run is still generating or has already completed — the fix
  for ISS-355, once applied at `AgentDetailPanel.tsx:412`, should cover both
  without any additional state-specific change.
- **Actual (inferred, not directly observed):** watching a live run whose
  agent calls a tool with an array/object argument (e.g. `write_todos`)
  should show the same `[object Object]` / `[object Object],[object`
  collapsed text while the run is still in progress, before it reaches
  `completed`.

## What would confirm or refute this

Start a live run whose pipeline calls `write_todos` (or any tool with an
array/object argument) early, open the run's Steps/Thinking tab
(`tab-thinking` testid per `bug-hunter/velocity.json`) WHILE it is still
running, expand the agent row's "Tool calls" panel as soon as an SSE
`tool_call` event lands for that tool, and read the collapsed summary before
the run reaches `completed`. Garbled text confirms the shared mechanism; if
the panel instead shows nothing for an in-flight call, or some other
live-only code path intercepts first, that refutes it and this sibling should
be closed as not-reproduced.

## Disposition

Not independently fixed — the fix belongs in the same place as ISS-355's
(`AgentDetailPanel.tsx:412`, inside `ToolCallsSection`), since both the live
and completed paths route through that one expression. No separate code
change is expected once ISS-355 is fixed; this card exists to make sure the
5-fixer's/4-test-writer's coverage includes a live-run case, not only a
completed-run one, before this is marked resolved.

## Evidence

- `frontend/src/components/results/AgentDetailPanel.tsx:1104` — no
  `isRunning` gate on `ToolCallsSection`.
- `frontend/src/components/results/AgentDetailPanel.tsx:1063-1070` — contrast:
  `ReasoningCard` IS gated on `isRunning` a few lines above.
- `frontend/src/hooks/useWorkflow.ts:1057-1064` — `tool_call` SSE case sets
  `args` from `msg.args` unmodified, same shape as a completed run's data.
- `frontend/src/types/index.ts:803-808` — `ToolCallEntry.args:
  Record<string, unknown>`, state-independent.
