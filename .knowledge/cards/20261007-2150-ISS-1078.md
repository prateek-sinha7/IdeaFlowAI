# ISS-1078

INFERRED sibling of [ISS-897](20261001-2127-ISS-897.md) (bug report QA-KB-070), filed by the analyzer on 2026-10-07. The gap itself is CONFIRMED by a scratch mutation and a scratch drive, both below. What is still INFERRED is the path through the launch wizard in a browser, which I did not drive.

## Why the root cause implies it

ISS-897's root cause is that one half of the [ISS-131](20260812-2116-ISS-131.md) / [ISS-132](20260812-2116-ISS-132.md) pairing has no test: the call-site flag (`invocation_gated=False`) and the step-scope declaration (`runs_agent_inline = False`) must agree, and each is pinned or not strategy by strategy. Laying the pairing out per strategy and mutation-testing every cell (the matrix is in ISS-897's analysis addendum; raw runs in `evidence/qa-kb-070/04-analyze-output.txt`) found exactly two empty cells: task_loop's call site, which is ISS-897, and this one.

## The declaration

`backend/agents/capabilities/strategies/wave_scheduler.py:240-245`:

```python
    name = "wave_scheduler"

    # ISS-131: spawn-only, exactly like fanout_batch — every wave is dispatched
    # through ``run_fanout`` and the step's own agent is never run inline, so the
    # inline review gate never fires for it.
    runs_agent_inline = False
```

[FIX-424](20260831-1652-FIX-424.md) added it to `fanout_batch.py:71` and `wave_scheduler.py:245` in one edit. Its only new test, `backend/tests/agents/test_composed_fanout_declared_gate.py`, builds a composed `fanout_batch` step. FIX-424's own text says `wave_scheduler` "is cured by the same edit", so it was never exercised.

## What deleting it does (CONFIRMED by measurement)

The kernel reads the fact generically: `return bool(getattr(strategy, "runs_agent_inline", True))` (`engine.py:11522`), so an absent declaration reads `True`. `wave_scheduler` never runs the step's own agent: it dispatches every wave through `run_fanout` (`wave_scheduler.py:360-361`, `:383`), and each worker opts out of the inline gate with `invocation_gated=False` (`kernel_services.py:1311`). With the declaration gone the step-boundary dedupe predicts an inline gate that never opens: `inline_gated=self._should_gate(spec, ectx) and _runs_agent_inline` (`engine.py:6329` pre-step, `:6753` post-step) is true, and `_evaluate_gates` skips the declared gate (`engine.py:11750-11764`, logging "declared 'human' gate on step ... skipped - inline review gate already covers this agent (WR-02 dedupe)"). The step gets no gate, no event and no error. That is ISS-131's symptom, reached through a deleted line instead of a missing one.

`evidence/qa-kb-070/03-analyze-wave-declaration-drive.py` drives the real `ExecutionEngine.execute` over `sample_wave` (the ISS-097 harness from `test_restart_resume_db.py`) with what the wizard writes on a tick, `gate_agent_ids=["sample-wave-worker"]` plus `selections["sample-wave-worker"].gates=["human"]`, and counts entries into `_run_review_gate`:

| run | review-gate entries | pipeline |
|---|---|---|
| as shipped (`runs_agent_inline = False`) | 1 (`sample-wave-worker`) | complete, 0 errors |
| declaration deleted (in memory) | 0 | complete, 0 errors |

## Which tests notice: none (CONFIRMED by scratch mutation)

With `WaveSchedulerStrategy.runs_agent_inline` set back to the default `True` in memory (`MUTATE_UNDECLARE=wave_scheduler`, `evidence/qa-kb-070/mutate_task_loop.py`), these 13 offline files, run one at a time, give the same result as with no mutation: `tests/unit/agents/test_wave_scheduler.py` (13 passed), `tests/unit/agents/test_gates.py` (46), `tests/agents/test_conditional_human_gate_source_t26.py` (2), `tests/agents/test_composed_fanout_declared_gate.py` (1), `tests/integration/agents/test_composed_fanout.py` (6), `tests/integration/agents/test_sample_wave_workflow_db.py` (1 failed, 2 passed, the same failure with no mutation), `tests/integration/agents/test_restart_resume_db.py` (4 failed, 81 passed; the failed set is identical to the no-mutation run), `tests/unit/test_backlog_revision.py` (34), `tests/unit/agents/test_phase3_cutover_verify.py` (1 failed, 3 passed, the same failure with no mutation), `tests/unit/agents/test_fanout_cancel.py` (9), `tests/unit/agents/execution_engine/test_compiler.py` (35), `tests/integration/agents/test_step_raises_visibly.py` (3) and `tests/agents/test_wave_scheduler_cancel_row.py` (1).

Controls proving the harness can catch a missing declaration: the same mutation on `task_loop` fails `test_task_loop_declared_gate_iss132.py` (3 failed), and on `fanout_batch` fails `test_composed_fanout_declared_gate.py` (1 failed). `grep -rn runs_agent_inline backend/tests` finds the task_loop test file and nothing else.

## Expected vs actual

- **Expected:** deleting `wave_scheduler.py:245` makes a test fail.
- **Actual:** no test fails. A ticked wave step that declares a human gate silently loses it.

## Blast radius

Every step that resolves `wave_scheduler`: `backend/agents/workflows/backlog/workflow.yaml:195`, `backlog_revision/workflow.yaml:238`, `prototype_v2/workflow.yaml:118` and `:954`, `sample_wave/workflow.yaml:31`, and any composed workflow that selects the strategy. The wizard writes the declared gate on every tick (`ReviewGatesSection.tsx:89` `withHumanGate`, called from `toggle` at `:191`), so the combination is reachable from the UI, not only from a composed selection.

## Where a fix belongs

Test-only, no production change. The smallest pin reads the declaration through the kernel's own reader, as `test_task_loop_declares_not_inline` does (`backend/tests/unit/agents/test_task_loop_declared_gate_iss132.py:30-32`): `ExecutionEngine()._strategy_runs_agent_inline("wave_scheduler", CapabilityRegistry()) is False`. Parametrizing it over the three strategies that declare the fact (`task_loop`, `fanout_batch`, `wave_scheduler`) turns the pairing into one table. A behavioural pin is the heavier option: a ticked wave worker with a declared human gate enters the gate exactly once, built on the ISS-097 harness (`test_restart_resume_db.py:5510-5578`); the drive script above is the template.
