## Register entry

Filed against **QA-PS-030** (`LEDGER.md` / `BUGS.md`) after the validator's cold-load
reproduction (3/3): on the Arctic family (`e53d9b1f` v1 → `f7000bbd` v2 → `dfeb5949` v3),
selecting "v2" from the version dropdown fetches `GET /api/runs/e53d9b1f.../sandbox/file
?path=presentation.html&ref=v2`, gets **200**, and the iframe renders the literal `<h1>Arctic
Seed Vault Logistics</h1>` — v1's heading, dark, no color — instead of v2's "ARCTIC VAULT v2"
in red.

The dispatch brief's own prior analysis ("Defect A") already proved the OUTCOME from git alone:
all three tags exist and are healthy, `git show v1/v2/v3:presentation.html` returns identical
bytes, `git log -- presentation.html` shows exactly ONE commit (`98d9aa9 step: ppt-composer`,
from the v1 run), and the v2/v3 commits touched only `.chain/logs.jsonl`,
`.chain/presentation.pptx`, `.chain/summary.md`. This card traces the previously-undocumented
WHY.

## Root cause — CONFIRMED

**1. `presentation.html` is written by exactly one agent, exactly once, ever.**
`backend/agents/prompts/ppt-composer/AGENT.md:68` — "Write the complete deck to
`presentation.html` using the workspace write_file tool" (re-verified live at this exact line;
per [ISS-651](20260917-1200-ISS-651.md), which already traced this hardcoding for a different
symptom — the Files-tab filename). This agent runs ONLY on the base `ppt` pipeline's step 2
(`backend/agents/workflows/ppt/workflow.yaml`), i.e. only on the family's v1 run.
`ppt-composer`'s `tools:` frontmatter is `[workspace]` (`AGENT.md:23-24`) → native filesystem
tools bound (`agents/factory.py::_resolve_runner_tools`), so this write genuinely lands on disk.

**2. The revision agent never calls a filesystem tool at all.**
`backend/agents/workflows/ppt_revision/workflow.yaml` has exactly one step —
`agent: ppt-revision-agent, strategy: single_shot, gates: []` — no per-step `tools:` override
(contrast `prototype_revision`'s step 1, which explicitly declares
`tools: {read_files: true, write_files: true}`). `ppt-revision-agent`'s own `AGENT.md`
frontmatter is `tools: []`; per `agents/factory.py:1306-1352` (the R-22/D-07 "empty tool set"
rule, `if not spec.tools and not custom_keys: return ([], False)` at `:1349-1352`), that STILL
binds the NATIVE filesystem tools (`exclude_builtin=False`) — the backend's own `CLAUDE.md`
describes an OLDER, no-longer-accurate behavior here ("`tools: []` → exclude_builtin=True, no
tool chips") that disagrees with the current `factory.py`. So the tool IS available; the PROMPT
simply never asks for it. `ppt-revision-agent/AGENT.md`'s entire output contract is: *"Emit the
complete modified HTML file wrapped in `<artifact>` tags... One sentence before the artifact...
Nothing after `</artifact>`."* No `write_file`/`edit_file` instruction anywhere in the prompt.
The model complies with what it's asked: it prints the revised deck as chat-stream text and
touches no file.

**3. The engine's only materialization fallback for this deliverable strategy targets a
different, already-mismatched filename, and only inside a staging path that is never the live
tree.**
`backend/agents/execution_engine/engine.py:1364-1392` (`build_flat_payload`'s ppt-strategy
branch) fires whenever `_deliv_strategy == "ppt"` and the compiled deliverable's basename is not
yet a file at the sandbox root — true on every `ppt`/`ppt_revision` run, since `_output_basename`
(`:1293`) is `deliverable.name`, and both `backend/agents/workflows/ppt/workflow.yaml` and
`ppt_revision/workflow.yaml` declare `name: presentation.pptx` — a LITERAL STRING THAT NEVER
MATCHES `presentation.html`, the file `ppt-composer` actually writes (so this condition is true
even on v1's own run). This branch sanitizes `ectx.last_streamed` (the revision agent's
`<artifact>` text) into `_ppt_text`, which is then written (`:1441-1480`) to
`sandbox.root / ".chain.staging-<run_id>" / _output_basename` — a per-run STAGING directory,
later promoted into `.chain/` by the commit path (matching the dispatch brief's own observed
git diff: every revision's commit touches `.chain/presentation.pptx`, which is exactly HTML text
under a `.pptx`-suffixed name, not the file anything renders from). It never writes to the
sandbox ROOT, so `presentation.html` there is untouched.

**4. `git add -A` (`commit_in_sandbox`, `engine.py:435,546-547`) only stages what's actually
different on disk.** Since `presentation.html` never changes after v1, there is nothing to
stage for that path on any revision commit — so `create_tag(f"v{revision_ordinal}")`
(`engine.py:2349-2456`, per [ISS-697](20260922-1000-ISS-697.md)'s own trace of this step) tags a
commit whose `presentation.html` blob is byte-identical to v1's, every time.

**5. The backend and frontend are both innocent — confirmed by reading, not assumed.**
- Frontend: `runSandboxFileUrl(runId, path, ref)` (`frontend/src/lib/api.ts:1208-1211`) appends
  `&ref=${ref}` whenever a ref is supplied — the dispatch brief's own network capture already
  showed `ref=v2` on the wire; this is the client behaving correctly.
- Backend: `read_sandbox_file` (`backend/app/api/run_files.py:1080-1153`) validates `ref` via
  `_validate_ref` (`:821-858`, exact match against `list_tags()` — passes here, this family's
  tags are real and healthy, this is NOT [ISS-697](20260922-1000-ISS-697.md)'s Defect B), then
  calls `sandbox.read_file_at_ref(safe_ref, rel)` — i.e. `git show v2:presentation.html`. Git
  faithfully returns what is actually in that tree: v1's bytes. The 200 status and the byte
  content are both exactly correct given what's on disk; the disk is what's wrong.

## Mapping to the dispatch brief's known defects

**Confirms Defect A, does not overturn it.** The brief's hunch (A) is correct. This card adds
the previously-missing mechanism: not a vague "revision runs never write back," but the
specific, file:line reason — a text-only revision agent with no persistence instruction, plus
an engine fallback that targets a different (already-mismatched) filename and a different
(staging-only) location.

**Ruled out: Defect B1/B2.** Both require a missing or orphaned git TAG
([ISS-697](20260922-1000-ISS-697.md)'s mechanism). This family's tags are all present
(`git_tag` = `v1`/`v2`/`v3` in Postgres for `e53d9b1f`/`f7000bbd`/`dfeb5949`, confirmed live —
see Data below) and `ref=v2` returns **200**, not the 400 `_validate_ref` would raise for a
missing tag. The defect here is entirely about what's IN the (correctly tagged) tree, not
whether the tag exists.

## Scope correction: this is `ppt`/`ppt_revision`-specific, not "all workflow types"

The bug's own title (`LEDGER.md` QA-PS-030) says "all workflow types." Read against the code,
that is broader than what this mechanism actually reaches:

- `strategy: ppt` (`backend/agents/workflows/ppt/workflow.yaml`,
  `ppt_revision/workflow.yaml`) is used by NO other pipeline — this is the only deliverable
  strategy with the staging-only, mismatched-filename fallback traced above.
- `prototype`/`prototype_revision` (`strategy: single_file`, `name: prototype.html` — SAME
  name both sides) wires its revision step with an explicit
  `tools: {read_files: true, write_files: true}` override
  (`backend/agents/workflows/prototype_revision/workflow.yaml`) — the precedent this pipeline
  should have followed. [FIX-111](20260724-FIX-111.md) already fixed the SAME class of defect
  once before ("`prototype-build` ran under `single_shot` which never writes a sandbox file")
  for the base pipeline; `ppt_revision` is a NEW, unfixed instance of that same class.
- `custom_revision`/`app_builder_revision` (`strategy: serialized_sandbox`) bundle whatever is
  actually on disk after a write-tool-equipped builder agent runs (`custom-revision-builder`,
  `app-builder-revision-agent` both declare `tools: [workspace]`) — a fundamentally different,
  not-filename-pinned mechanism.
- `ppt_v2` (`strategy: single_file`, `name: presentation.html` — matching name, per its own
  workflow.yaml comment "`ppt-deck-qa-v2` is the ONE WRITER of `presentation.html`") has **no**
  revision pipeline at all today (`agents/registry.py`'s `REVISION_BASE_MAP` has no `ppt_v2`
  entry) — nothing to break yet.

**This is INFERRED, not exhaustively proven**: confirmed by reading each pipeline's
`workflow.yaml` + its revision agent's `tools:` declaration, not by reproducing each live. What
would fully settle it: reproduce the same ref=v2 check on a `prototype_revision` family and
confirm the heading DOES change (the expected-good contrast this card predicts).

## Fix direction (not applied — issue only)

**The single place**: `ppt-revision-agent` needs to actually persist its edit, the same way
`prototype-revision-agent` does for `prototype.html`
(`backend/agents/workflows/prototype_revision/workflow.yaml`'s step-level
`tools: {read_files: true, write_files: true}`, `edit_file`-only discipline documented in
`backend/CLAUDE.md`'s "`write_file` won't overwrite" note). Concretely, two things need to
change TOGETHER, or the fix just creates a third, still-orphaned file:

1. Resolve the `presentation.pptx` (`deliverable.name`) vs `presentation.html` (the literal
   string `ppt-composer` writes and everything UI-facing reads) naming split — either rename
   `deliverable.name` to `presentation.html` for `ppt`/`ppt_revision` (matching `ppt_v2`'s
   already-correct convention), or make `ppt-composer` write to whatever `deliverable.name`
   resolves to instead of the hardcoded literal. [ISS-651](20260917-1200-ISS-651.md) already
   covers the filename-facing half of this same split for a different symptom (Files-tab
   display name) — a fix should close both from the same naming decision, not separately.
2. Give `ppt-revision-agent` write access at the step level (mirroring
   `prototype_revision`'s workflow.yaml) and change its prompt from "emit an `<artifact>` block"
   to "read the current deck, then `edit_file` it in place" — `edit_file`, not `write_file`:
   the target file already exists in the shared family sandbox by the time any revision runs,
   and `write_file` is documented (`backend/CLAUDE.md`) not to overwrite an existing file.
3. **From [ISS-723](20260922-1245-ISS-723.md)'s independent, deeper trace**: even once (2) makes
   `ppt-revision-agent` write a fresh `presentation.html` to the sandbox ROOT, verify it is
   actually captured. The PER-STEP commit boundary (`engine.py:6141-6148`, a full `git add -A`)
   should pick it up for free — that is the intended capture point. `finalize_terminal_run`'s
   own terminal snapshot commit (`engine.py:2179-2189`) does NOT independently re-stage it: it
   passes `force_add=_built_payload.allowlist`, a hard 3-path `.chain/`-only allowlist
   (`payload_allowlist()`, `sandbox.py:268-291`, documented as a deliberate security/audit
   boundary — "these three exact paths and no others"). Do not widen that allowlist to include
   the root deliverable as a shortcut; that reopens a reviewed boundary. If the per-step commit
   is ever skipped or reordered for `ppt_revision`'s single-step manifest, the root write would
   silently go uncommitted again with a different mechanism than this card's own.

**What breaks if done carelessly**:
- Using `write_file` instead of `edit_file` on the second point reproduces the exact same
  no-op silently (matches the precedent this class of bug already has once —
  [FIX-111](20260724-FIX-111.md)).
- Changing `deliverable.name` without also updating `ppt-composer`'s hardcoded write target (or
  vice versa) just moves the mismatch instead of closing it.
- Any fix must keep routing new content through a real `commit_in_sandbox` call (`git add -A` +
  the mandatory secret scan) — not bypass into a non-versioned write — or `ref=vN` reads lose
  their "HEAD never moves" / tamper-evidence guarantee (Requirement 17/18).
- This fix is independent of [ISS-697](20260922-1000-ISS-697.md)'s Defect B fix direction (tag
  creation/durability) — do not conflate the two; both are needed, neither substitutes for the
  other.
- Must not regress the "Latest (live)" DB-read path that is CORRECT today — a fix that makes
  `presentation.html` on disk finally track the true content should only ever make the
  sandbox-file readers agree with what the DB-read path already shows, never the reverse.
