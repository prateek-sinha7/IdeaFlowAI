# ISS-932

Derived from the QA-KB-041 analysis of [BUG-104](20260829-1508-BUG-104.md). **Confidence: INFERRED** for real browsers.
The mechanism is CONFIRMED on the live source and reproduced offline in jsdom with ordinary clicks (below); nobody has run it
in a real browser. Unlike its four menu siblings this one does not depend on a Safari or Firefox quirk.

## Condition

`/workflows`, any browser, ordinary mouse flow: a card's "Workflow actions" menu, then Delete. The "Delete workflow"
confirmation (`role="dialog" aria-modal="true" aria-labelledby="delete-workflow-title"`) opens. Press Escape.

## Expected

The dialog closes, same as Cancel. The code intends it: the scrim carries
`onKeyDown={(e) => { if (e.key === "Escape") setDeleteRow(null); }}` (`SavedWorkflowsPage.tsx:421`).

## Actual

The dialog stays open. A keydown targets `document.activeElement`; the scrim's handler only sees events that start inside
the scrim. The flow guarantees focus is elsewhere:

```tsx
// SavedWorkflowsPage.tsx:355  (menu item Delete)
onDelete={() => { setOpenMenuId(null); setDeleteRow(row); }}
// SavedWorkflowsPage.tsx:417-421  (the confirmation)
{deleteRow && (
  <motion.div ... className="fixed inset-0 z-[80] ..."
    onClick={() => setDeleteRow(null)}
    onKeyDown={(e) => { if (e.key === "Escape") setDeleteRow(null); }}>
```

The menu item the user just clicked held focus; `setOpenMenuId(null)` unmounts the menu, so the focused element is
destroyed and focus falls back to BODY. The dialog never takes focus: the file has no `autoFocus`, no `.focus()` other than
the kebab trigger refocus (`:105`), and no `tabIndex` (`grep -n -E "autoFocus|\.focus\(|tabIndex"` returns `:105` only).

## Why the root cause implies it

Same shape as [BUG-104](20260829-1508-BUG-104.md): Escape bound by a React `onKeyDown` on a wrapper, no focus management.
The difference is the precondition. For the kebab it is a browser quirk (the click may not focus the trigger). Here it is
the flow itself: the element that held focus is removed by the click that opens the dialog, in every browser.

The History page has the same dialog done correctly. `DeleteModal` focuses its confirm button on open and listens on
`window` (`WorkflowHistory.tsx:1493-1500`: `confirmRef.current?.focus();` and `window.addEventListener("keydown", onKey);`),
so Escape works wherever focus is.

## Evidence (offline, jsdom; nothing under `frontend/src` was created or edited)

`evidence/qa-kb-041/08-analyze-probe-output.txt`, source `07-analyze-probe-saved.test.tsx.txt`, describe "Delete-confirm
scrim", plain `user.click` for both the kebab and the Delete item (no unfocused-click emulation):

```
[delete] dialog open; activeElement = BODY
[delete] after Escape: dialog still present = true
[delete] keydown fired ON the dialog node closes it (handler only sees events from inside)
```

The last line is the control: the same Escape aimed at a node inside the scrim does close it, so the handler works and the
event simply never reaches it.

No existing test presses Escape here: `SavedWorkflowsPage.test.tsx:252-269` walks the Delete flow and clicks the buttons.

## Reach (INFERRED)

Every browser, mouse path. jsdom applies the DOM rule that Chrome, Firefox and Safari also apply (a removed focused element
leaves `document.activeElement` on BODY); it has not been observed in a real browser. A user who tabs into the dialog first
would have focus inside it and Escape would work, which is why this goes unnoticed in keyboard-first checks.

## What would settle it

Chrome: `/workflows`, open "Workflow actions" on a card, click Delete, wait half a second, press Escape. Expected result if
the analysis holds: `document.activeElement` is BODY and the dialog is still open. Cancel the dialog by its button; never
confirm the delete.

## Fix direction

One line at the top level of `SavedWorkflowsPage`, using the shared hook from [FIX-388](20260829-0053-FIX-388.md)
(`frontend/src/hooks/useEscapeToClose.ts`): `useEscapeToClose(() => setDeleteRow(null), deleteRow !== null)`, and delete the
dead scrim `onKeyDown` (`:421`). Optionally also focus the primary button on open, as `WorkflowHistory`'s `DeleteModal` does
(`:1497`). This region (`:415-421`) is disjoint from the KebabMenu edit of [BUG-104](20260829-1508-BUG-104.md) (`:88-153`)
and from `cleanBrief` (`:59-73`), so the two can land together or apart.

Not the same defect, same page: the Rename modal (`NameWorkflowModal`) has no Escape binding at all. See the "Adjacent"
section of [BUG-104](20260829-1508-BUG-104.md).

## Resolution (QA-KB-041, fixer, 2026-10-02)

[FIX-710](20261002-0154-FIX-710.md) applies the "Fix direction" above as written. `SavedWorkflowsPage.tsx:172` now reads
`useEscapeToClose(() => setDeleteRow(null), deleteRow !== null);`, and the dead scrim `onKeyDown` is deleted (the scrim
keeps only `onClick` at `:421`). The optional confirm-button autofocus was not added.

**What the test shows.** On the fixed tree, the "ISS-932" case in `SavedWorkflowsPage.escape.test.tsx` reports "Expect
test to fail" in 3 of 3 runs. That is the pass signal, and the file was not edited. The marker is left for the verifier.
