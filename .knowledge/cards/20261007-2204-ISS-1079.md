## Condition

Anyone reading `test_resume_marker_seq_allocation.py`, or the DB-001 section of `test_resume_marker_workspace_db.py`, to learn how the
resume marker takes its seq.

## What the tests say (CONFIRMED, read)

- `backend/tests/agents/test_resume_marker_seq_allocation.py:3-9`, module docstring:

  > ``_stamp_resume_marker`` allocates its seq through ``ScopedStore.append_event_next_seq`` (FIX-240/DB-001), which fixed the
  > non-retrying append but NOT the read cost: that method still derives the next seq via ``read_events(run_id, after_seq=0)`` — an
  > unbounded read of every row for the run — instead of the bounded ``_max_event_seq`` aggregate ...

- `backend/tests/integration/agents/test_resume_marker_workspace_db.py:221-225`, the "(4) DB-001" section comment:

  > After the fix (routing through ``ScopedStore.append_event_next_seq``), every concurrent marker call survives with a distinct
  > seq — none are silently lost.

## What the code does (CONFIRMED, read and run)

- `backend/agents/execution_engine/engine.py:13104-13114`: `_stamp_resume_marker` calls
  `store.append_event_at_or_after(run_id, (await store._max_event_seq(run_id)) + 1, str(uuid.uuid4()), "run_resuming", {...})`. It has not
  called `append_event_next_seq` since [FIX-499](20260831-1641-FIX-499.md) ([ISS-125](20260812-1852-ISS-125.md)).
- `backend/agents/authz.py:556-575`: `append_event_next_seq` makes one keyed `event_id` lookup plus one `_max_event_seq` probe per
  attempt and no `read_events` call (FIX-688). Probe output: `evidence/qa-kb-074/02-probe-cost-of-append_event_next_seq.txt`.
- The first test passes today because the marker rides the bounded pair, as its assertion says, not because of anything in its
  docstring: `tests/agents/test_resume_marker_seq_allocation.py` is `1 passed` on this tree
  (`evidence/qa-kb-074/04-baseline-test_resume_marker_seq_allocation.txt`).

## Why the root cause implies it

It is the claim [ISS-901](20261001-2140-ISS-901.md) is about (a whole-log `read_events` as the cost of `append_event_next_seq`),
restated in a fourth place that the three-docstring report did not count, plus an allocator identity that changed earlier, under FIX-499.
ISS-901's harm statement applies unchanged: a reader who trusts the docstring takes `append_event_next_seq` for the whole-log allocator and
could re-file the cost FIX-688 removed. The stale-prose probe lists all sites: `evidence/qa-kb-074/03-probe-stale-prose-sites.txt`.

## Expected vs actual

- Expected: prose that describes the live allocation (bounded `_max_event_seq` probe plus `append_event_at_or_after`), or that is framed
  as the defect as originally filed ("ISS-125 found ...; fixed by FIX-499 / FIX-688").
- Actual: present tense, as if the marker still rode `append_event_next_seq` and that method still read the whole log.

## What would settle it

This repo has two habits for failing-first test docstrings. `tests/agents/test_resume_seed_bounded_aggregate.py:1-8` also narrates its
pre-fix defect in the present tense, but its first line names [ISS-639](20260831-1645-ISS-639.md) / [ISS-873](20261001-2110-ISS-873.md) / [ISS-874](20261001-2110-ISS-874.md), so it reads as
history and is not counted here.
[ISS-902](20261001-2144-ISS-902.md) / [FIX-733](20261007-1911-FIX-733.md) set the other precedent: test comments that explain a behaviour with
a dead rule are reworded. If the owner says narrated history is fine, close this as won't-fix; otherwise fix as below.

## Fix shape (comment-only, no behaviour change)

Reword in place; leave the test bodies and names alone.

- `:3-9`: for example, "ISS-125 found that `_stamp_resume_marker` allocated through `append_event_next_seq`, which then derived the next
  seq from `read_events(run_id, after_seq=0)`. The marker now uses the bounded `_max_event_seq` probe plus `append_event_at_or_after`
  (FIX-499), and `append_event_next_seq` no longer reads the log either (FIX-688). This test pins that the marker never calls
  `read_events`."
- `:221-225`: say which allocator the marker rides now (`_max_event_seq` + `append_event_at_or_after`, FIX-499), or mark the sentence as
  the DB-001 history.

Independent of [ISS-901](20261001-2140-ISS-901.md): different files, so the two can land in either order.
