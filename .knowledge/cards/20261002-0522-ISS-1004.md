# ISS-1004

INFERRED sibling of [ISS-684](20260918-ISS-684.md) (bug report QA-KB-065), filed by the analyzer on 2026-10-02. The mechanism below is CONFIRMED by lines I read and by an offline harness probe. What is still INFERRED is the path through the launch wizard, which I did not drive.

## Why the root cause implies it

ISS-684's root cause is that the engine treats a code step as a literal-keyed override applied AFTER the step's default `strategy` (`single_shot`) was already read. The `else` that resolves that default is the visible failure. The same stale default feeds a second consumer before the chain ever runs: the gate dedupe.

## The symptom

In the launch wizard, "Review gates" lists every agent of the workflow, Code steps included. Its text is "Checked agents pause the pipeline for your review after they finish" (`ReviewGatesSection.tsx:224`), and `agents.map` at `:226` has no filter. Ticking a Code step writes `human` into that step's gate list (`withHumanGate`, `:89-106`, called from `toggle` at `:191`) and puts its id in `gate_agent_ids` (`onChange(ordered, touched)`, `:176`). `_apply_selections` merges the selection's gates onto the compiled step (`engine.py:14196-14198`). The run then goes past that step with no review gate: no event, no error, and the wizard still says it pauses. This is the QA-KB-030 symptom ([ISS-132](20260812-2116-ISS-132.md), fixed by [FIX-680](20261001-2127-FIX-680.md)) for a step kind those fixes did not cover.

## Root cause (CONFIRMED)

Two facts have to agree and, for a Code step, they do not.

- The step-boundary dedupe predicts the inline gate: `inline_gated=self._should_gate(spec, ectx) and _runs_agent_inline` at `engine.py:6317` (pre-step) and `:6729` (post-step). `_evaluate_gates` then skips the declared `human` / `before-human` gate when `inline_gated` is true (`engine.py:11726-11740`, logging "declared 'human' gate on step ... skipped - inline review gate already covers this agent (WR-02 dedupe)").
- `_runs_agent_inline` is read off the registry strategy NAMED by `strategy_name` (`engine.py:6288-6290`; `_strategy_runs_agent_inline`, `:11477-11498`, `bool(getattr(strategy, "runs_agent_inline", True))`). For a Code step `strategy_name` is the default `"single_shot"` (`engine.py:6267-6269`, `compiler.py:901`, `plan.py:468`). `single_shot` declares nothing, so the kernel reads `True`.

But the strategy a Code step actually runs is the adapter the chain selects afterwards (`engine.py:6446-6496`), and none of the four adapters calls `ctx.runner.run_agent` (`publish_step.py:134-166`, `prototype_ui_extract.py:376-398`; `assemble_step.py` and `backlog_assemble.py` contain no `run_agent` or review-gate call). All three inline gate sites sit inside `_run_agent` (`engine.py:9186`; sites `:9271`, `:9430`, `:10928`). So the dedupe skips the declared gate for an inline gate that cannot open, and nothing replaces it. `runs_agent_inline` is declared only by `fanout_batch.py:71`, `task_loop.py:164` and `wave_scheduler.py:245` (`base.py:50-56` is the port); the adapters declare nothing, and could not be read anyway, because the flag is computed from the name before an adapter is chosen.

## Reproduction (offline harness, 2026-10-02)

In-process, scripted model, offline DB, no application source edited. The `ex_publish_step` fixture is driven through `tests/agents/_scripted_model._prepare_engine_run`, with `engine_mod.compile_for_run` wrapped to set `gates = ["human"]` on the publish step (on the harness's deep copy, as the wizard tick would), and `HumanGate.evaluate_stream` wrapped to record the steps it is entered for.

| run | `gate_agent_ids` | declared gate handler entered for | dedupe log line |
|---|---|---|---|
| unticked | `None` | `custom-agent:publish` (once) | none |
| ticked | `["custom-agent:publish"]` | nothing | "declared 'human' gate on step custom-agent:publish skipped - inline review gate already covers this agent (WR-02 dedupe)" |

In the ticked run the step's events were `agent_start`, `agent_chunk`, `agent_complete`: no review gate, and the run completed. The harness stubs `_run_review_gate`, so "a gate opened" shows up as the declared gate handler being entered, not as a `review_gate_ready` event.

## Expected vs actual

- **Expected:** a ticked Code step opens exactly one review gate after it finishes (and a declared `before-human` gate opens before it), like any other ticked step.
- **Actual:** no gate, no event, no error.

## Where a fix belongs

`backend/agents/execution_engine/engine.py`, at the one place `_runs_agent_inline` is computed (`:6288`). Both `inline_gated` reads reuse it, so one change covers the pre- and post-step paths.

- **Smallest:** `_runs_agent_inline` is `False` when `getattr(step, "mechanical", None)` is truthy, and the existing strategy read otherwise. It reads a step field, not a kind list, so it is generic.
- **Convention-aligned ([FIX-424](20260831-1652-FIX-424.md) / [FIX-680](20261001-2127-FIX-680.md)):** have each adapter declare `runs_agent_inline = False` and read the flag off the SELECTED strategy object. That needs the adapter selection (and the ISS-684 guard) moved above the pre-step gates, because the pre-step gates run first today. A side benefit: an unhandled kind then fails before a human is asked to review the step.

Do not add a kind-name list or a workflow or agent-id branch to the kernel, and do not remove the dedupe.
