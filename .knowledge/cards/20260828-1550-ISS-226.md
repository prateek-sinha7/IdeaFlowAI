## Reproduction (3/3, cold start each time)

Validated register entry `BUG-20260828-052800-create-ppt-r2` in `bug-hunter/ledger.md`.

1. Sign in as qa-admin, fresh navigate to `http://localhost:3000/create/ppt`.
2. Fill the brief textarea with distinct text, click a template card, then "Use this template"
   in the preview modal (confirmed selected — "Continue" becomes enabled).
3. Click "Save as my version". `POST /api/user-workflows` fires; inspect the request body.
4. Repeat from a fresh `/create/ppt` load with a different template and a different (or empty)
   brief.

Cycle 1: brief "VALIDATOR Cycle 1 brief for save-as-my-version persistence check", template
"8-Bit Orbit". Request body:
```json
{"name":"My presentation","description":"Your saved version of this workflow.",
 "base_pipeline_type":"ppt","agent_ids":["ppt-brief-analyst","ppt-composer","ppt-validator"],
 "manifest":{"steps":[...generic 3-step ppt pipeline, no template id, no brief text...]},
 "overrides_pipeline_type":"ppt"}
```
Response `201`, `id: da92b4a4-7eff-41b5-9b9a-205cfa1616d9`, `created_at: 2026-08-25T17:44:26...`
(unchanged from a prior record), `updated_at: 2026-08-28T05:25:27...`.

Cycle 2: brief "VALIDATOR Cycle 2 - a totally different brief about a safety and risk review deck
for the compliance team", template "Safety & Risk Review". Request body byte-for-byte identical
to cycle 1. Response identical, including `id`, `created_at`, AND `updated_at` — the
`updated_at` timestamp did not even advance despite the real wall-clock server time (per the
response `date` header) being ~10 hours later than the stored `updated_at` value, confirming the
saved record is fully static rather than merely losing fields on write.

Cycle 3: brief "VALIDATOR Cycle 3 - marketing pastel lifestyle brand refresh deck for Q4
launch", template "Pastel Lifestyle Deck". Request/response identical to cycles 1 and 2.

3/3 cold-start reproductions, deterministic on every attempt — no axis narrowing needed.
CONFIRMED.

## Conditions

- Tier: qa-admin, not tier-specific (payload-construction bug, same for any account).
- Entry path: fresh `/create/ppt` load each cycle (cold start), no prior /create/ppt visit in
  the session.
- Theme/viewport: not a factor — this is a request-body construction bug, not a render bug.
- Run state: n/a (save action only, never reaches launch).
- Trigger: clicking "Save as my version" itself, regardless of what brief text or template was
  set beforehand.

## Root cause

`frontend/src/components/workflow/LaunchWizard.tsx:727-753`, `handleSaveAsOverride`:

```js
const saved = await createUserWorkflow(jwt, {
  name: `My ${cfg.eyebrow.replace(/^New /, "")}`,
  description: "Your saved version of this workflow.",
  base_pipeline_type: pipeline,
  agent_ids: pipelineAgents.map((a) => a.id),
  manifest: buildWorkflowManifest(
    pipelineAgents,
    undefined,
    selectionsRef.current,
  ) as unknown as Record<string, unknown>,
  overrides_pipeline_type: pipeline,
});
```

`name` and `description` are hardcoded string literals (`cfg.eyebrow` for ppt mode always
resolves to the same "presentation" label, so `name` is always `"My presentation"`).
`buildWorkflowManifest` is called with `pipelineAgents` (the generic 3-agent lineup) and
`selectionsRef.current`, but never with `brief`, `selectedTemplateId`/`customTemplateBody`, or
`selectedDsId`/`customDsBody` — none of the state the component tracks for the wizard's own
"Continue" (launch) path.

Contrast with `handleLaunch` (line ~755), which DOES thread all of this through
`buildLaunchDraft(mode, { templateId: selectedTemplateId, designSystemId, brief: finalBrief,
customDsBody, customTemplateBody, ... })` — so the wizard's component state genuinely holds the
brief and template selection at the moment "Save as my version" is clicked; `handleSaveAsOverride`
simply never reads any of it into the payload it builds.

The identical `id`/`created_at` across all three trials (an "override" upsert keyed by pipeline
type per user, per the code comment at line ~1080: "bind this lineup to the built-in so it is
what THIS user gets whenever they open it") means every subsequent click of "Save as my version"
for this pipeline type overwrites the same one row — but even a single save never contained the
form state to begin with, so overwriting it with itself is indistinguishable from a no-op from
the user's perspective.

## Expected vs actual

**Expected:** "Save as my version" persists the user's actual current configuration — the
entered brief and the selected template (or design-system choice) — into the saved
override/workflow record.

**Actual:** the saved record's `name`, `description`, and `manifest` are always the same
hardcoded generic values from `handleSaveAsOverride`, regardless of what brief text or template
was on screen; the button reports success (`201 Created`, "Workflow saved to your catalogue")
with no indication that none of the user's input was captured.

causes in separate files.

## Blast radius (analyzer pass)

Root cause re-confirmed by independent read of `LaunchWizard.tsx:727-754` and `:756-804`
(`handleLaunch`, which DOES thread `templateId`/`designSystemId`/`brief`/`customDsBody`/
`customTemplateBody` via `buildLaunchDraft`).

Grepped every caller of `handleSaveAsOverride` and `createUserWorkflow` across
`frontend/src/`: the function is wired to exactly one `onClick` in its own file
(`LaunchWizard.tsx:1092`) and has exactly one other independent implementation in the whole
frontend, `IdeaInputPage.tsx:1460` — no third copy, no shared helper.

- `LaunchWizard.tsx`'s `handleSaveAsOverride` is unconditional on `mode` (`"prototype" | "ppt" |
  "ppt_v2"`, `MODE_CONFIG` at lines 96-137) and reachable at three URLs —
  `/create/ppt` (this bug, confirmed), `/create/prototype`, and `/create/ppt_v2` — all three
  rendering the identical component per `frontend/src/app/[...view]/page.tsx:287-302,3756-3760`.
  See sibling [ISS-279](20260828-1901-ISS-279.md).
- `IdeaInputPage.tsx`'s own `handleSaveAsOverride` (a separate implementation, not a shared call)
  has the same defect shape — hardcoded `description`, brief (`ideaInput`) never read — on every
  non-custom pipeline type that page serves. See sibling [ISS-280](20260828-1902-ISS-280.md),
  which is distinct from [ISS-225](20260828-1541-ISS-225.md)'s gates-only finding on that same
  function.

**Where the fix belongs:** inside `handleSaveAsOverride` in each file (or a shared helper the two
could call, since their save-payload shape is now near-identical) — not per-caller, since each
function has exactly one caller already. A structural note for the 5-fixer: the current
`WorkflowManifest`/`WorkflowCapabilities` TypeScript contract
(`frontend/src/types/index.ts:563-648`) has NO field for a template id, design-system id, or
brief text — only `steps`, `capabilities.internet`, `deliverable`, `planner`, `clarify`. Fixing
the hardcoded `name`/`description` strings needs no schema change; making the selected
template/design-system actually round-trip through a saved override likely does (a new manifest
field, both frontend type and backend model/compiler). This split is INFERRED — not verified
against `backend/agents/workflows/compiler.py` — and is the first thing the fix pass should
settle.
