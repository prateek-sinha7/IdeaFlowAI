## What was wrong

`frontend/src/components/history/WorkflowHistory.tsx` had four related bugs rooted in the same cause — `runs` state never grew past the initial 50-row fetch because `handleLoadMore` (already fully implemented at line ~316) was dead code with no trigger anywhere in the component:

1. **ISS-198 — header/chip mislabelling:** The `<p>{runs.length} runs</p>` header and `typeCounts.all = families.length` chip counter both used the capped array length instead of `totalRuns` (already populated from the API's `total` field). A 273-run account displayed "50 runs".

2. **ISS-207 — search false-negatives:** `matchesFilter` ran client-side over the capped `runs` array. Searching for a run title outside the loaded 50 returned "No runs match" — a false negative.

3. **ISS-208 — sort ranks wrong extremes:** `bucketAndSortFamilies` sorted over the same capped families. "Longest"/"Tokens" sort never surfaced the account's actual highest-usage run if it sat outside the loaded window.

4. **ISS-209 — delete desyncs totalRuns:** `handleDeleteConfirm` called `setRuns(filter)` but never `setTotalRuns`, leaving `totalRuns` one too high until the next full refetch. This would corrupt `handleLoadMore`'s offset math once the trigger was wired.

5. **ISS-213 — chip counts undercount:** `typeCounts` for all five per-type buckets was built from `families` (the capped array), so a type with zero first-page hits was hidden from the chip row entirely despite having entries in the account's full history.

The analysis addendum in ISS-198 confirmed this was a collateral regression from commit `ce08bf542` ("Revert 'Merge branch staging into dev'", 2026-08-17), which deleted a working Load More footer and reverted `typeCounts.all` from `totalRuns` — not an intentional removal of the feature.

## Root cause

`handleLoadMore` (line ~316) was correctly implemented — `offset: runs.length`, guard `runs.length >= totalRuns` — but had zero call sites. The component already held `totalRuns` from the API response; it just never displayed or acted on it.

## What changed and why there

All changes in one file: `frontend/src/components/history/WorkflowHistory.tsx`.

**ISS-198 — header and All chip:**
- Header text: `{runs.length} runs` → `{totalRuns} runs`
- `typeCounts.all = families.length` → `typeCounts.all = totalRuns`

This is option 2 from ISS-219's enumerated options: the header and All chip show run counts (`totalRuns` from `X-Total-Count`); the per-type chips show family-card counts derived from the loaded window. The tension between these two units is documented in ISS-219 and is a product decision — this fix picks the option that makes the header truthful without requiring a new backend aggregate endpoint.

**ISS-198 — Load More trigger (IntersectionObserver):**
- Added `loadMoreRef = useRef<HTMLDivElement>(null)` near the other refs
- Added a `useEffect` (placed after `handleLoadMore`'s declaration so tsc does not raise TS2448) that attaches an `IntersectionObserver` to the sentinel div — disconnects on unmount, re-observes whenever `handleLoadMore` identity changes (i.e. whenever `runs.length` / `totalRuns` / `loadingMore` change)
- Added a sentinel `<div ref={loadMoreRef}>` at the bottom of the sections map, rendered only when `runs.length < totalRuns`, showing a `Loader2` spinner while `loadingMore` is true and a "Load more" text label otherwise

This is the deleted footer pattern from the pre-revert commit, rewritten as an IntersectionObserver rather than an explicit button so scrolling loads pages automatically.

**ISS-209 — delete keeps totalRuns in sync:**
Inside `handleDeleteConfirm`, after `setRuns((prev) => prev.filter(...))`:
```ts
setTotalRuns((prev) => Math.max(0, prev - 1));
```
`Math.max(0, …)` guards against an already-zero count. No observable effect today (load more had no trigger before this fix), but becomes live the moment the IntersectionObserver fires.

**ISS-207/208/213 — partial-scope affordance:**
Added `const isPartiallyLoaded = runs.length < totalRuns` in the list-view derived values block, and rendered a notice beneath the search input when true:
```
Showing {runs.length} of {totalRuns} runs — scroll down to load more
```
This makes the scope of search, sort, and chip counts explicit rather than silently wrong. The approach is option 4/5 from ISS-198's Fix location notes: an explicit "counts reflect the loaded N of M" affordance rather than a backend aggregate or server-side search.
