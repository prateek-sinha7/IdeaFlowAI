# FIX-610

**Register source:** `QA-PS-024` in root `LEDGER.md` / `BUGS.md`.

## What was wrong

The Steps tab's status summary (`StepsOverviewSpine`) rendered the red X-circle
and the label **"Run failed"** for a run that was not failed:

- a TERMINAL `degraded` run holding at least one agent in `status: "error"`
  ([ISS-701](20260922-1030-ISS-701.md), reproduced 3/3 on cold starts against
  `/runs/353bb0af-590b-4acb-8fbb-6c280b39e192/steps`), and
- a TERMINAL `cancelled` run holding a pre-cancel errored agent
  ([ISS-764](20260922-1424-ISS-764.md), the inferred sibling).

The tell in ISS-701 is that the same panel rendered the correct "Run degraded"
for a sibling degraded run whose agents had all completed
(`ab2d555e-fa45-47c7-90da-a9f1adaba98a`) — the label varied by per-agent status
across two runs with the identical run-level terminal marker.

## Root cause

`frontend/src/components/results/StepsOverviewSpine.tsx:408` (pre-change):

```ts
const failed = !isRunning && (pipelineState?.failed || agents.some(a => a.status === "error"));
```

A per-agent status was being used as a run-level verdict. The three terminal
markers are mutually exclusive and are stamped by the shared
`terminalMarkers()` vocabulary in `useWorkflow.ts` (`TERMINAL_MARKER_BY_STATUS`
at `useWorkflow.ts:378-389`), so `degraded` and `cancelled` runs never carry
`pipelineState.failed`. The OR let `agents.some(...)` supply `failed` on its
own, and the label ternary tests `failed` first, so it steamrolled the correct
`pipelineState?.degraded` branch below it.

Both trigger states are normal persisted data, not staleness:

- `pipeline_complete` stamps `status: "error"` on every id in `agents_failed`
  and then applies `terminalMarkers("degraded")` (`useWorkflow.ts:1269`) — an
  `error` agent is what "degraded" MEANS.
- `pipeline_cancelled` (`useWorkflow.ts:1379-1382`) resets only
  `thinking`/`running` agents to `idle`; its own comment states that
  already-errored agents are left untouched, then `terminalMarkers("cancelled")`
  (`useWorkflow.ts:1397`).

[ISS-317](20260828-1755-ISS-317.md)/[FIX-379](20260829-0210-FIX-379.md) had
already found this OR and added the `!isRunning` guard, but that only covers
the mid-resume race it reproduced (a still-running pipeline carrying a stale
pre-resume `error`). For a genuinely terminal run, `!isRunning` is true and the
OR is still evaluated.

## What changed and why there

**One line, `frontend/src/components/results/StepsOverviewSpine.tsx:418`
(was :408):**

```ts
const failed = !isRunning && (pipelineState?.failed ?? false);
```

The `agents.some(a => a.status === "error")` term is gone; `!isRunning`
(FIX-379's guard) is kept. `?? false` matches the `pipelineState?.isRunning ??
false` idiom on the line above and keeps the flag typed `boolean`. The comment
above it was extended to record ISS-701/ISS-764 alongside the existing ISS-317
note, matching how this file documents each prior fix in place.

This is the single shared derivation every affected surface routes through, so
one guard cures the whole blast radius both cards named — all in this same
file, all downstream of this one `const`:

| line (post-change) | reader |
|---|---|
| `:459` | `statusLabel` — the "Run failed" text |
| `:468` | `phase` — the null-phase gate |
| `:494` | `notRun` — the idle-agent count |
| `:532` | the red X-circle status icon |
| `:695` | the per-row "Not run" chips |
| `:775` | the "Pipeline halted — reopen to resume" banner |

No per-caller patch is needed and none was made. Grepped the rest of the
frontend for the same pattern: no other component derives a run-level failed
flag from per-agent status (`RunChatLane.tsx:482,602`,
`AgentDetailPanel.tsx:1324`, `HandoffAgentPanel.tsx:51`, `AgentNode.tsx:187`
all render a single agent's own row; `DashboardLayout.tsx:889` uses `every(done
|| error)` for a completion check, a different question).

**Nothing lost on a genuine failure.** `pipelineState.failed` is stamped on
every path that reaches a failed run: live via `terminalMarkers("failed")` in
the `pipeline_error` handler (`useWorkflow.ts:1354`), and on cold-start
hydration via `applyTerminalStatus` (`useWorkflow.ts:453`), which applies the
same vocabulary from the server's persisted status.

## Deliberately NOT fixed here

The label ternary still has no `cancelled` arm
(`StepsOverviewSpine.tsx:459-463`), so a cancelled run now falls through to
**"Run complete"**. [ISS-764](20260922-1424-ISS-764.md) called this out as a
mechanically distinct, pre-existing defect — a missing branch, not a precedence
error — and scoped it out of its own verdict. This fix does not touch it, and
ISS-764's test asserts only the absence of "Run failed", which holds. Filed
as [ISS-797](20260922-1832-ISS-797.md) rather than fixed, because choosing the
label and tone a user-stopped run should show is a product decision, not a
mechanical one.

## Side observation (carried forward from ISS-701, not acted on)

`RunHeader.tsx:186` and `LaneRunHeader.tsx:121-128` both deliberately show
"Failed" for a degraded run — `LaneRunHeader`'s comment says degraded "shares
the failed token rather than get its own amber". That reads as a product
decision, so this fix leaves both alone; it makes `StepsOverviewSpine`
self-consistent (same label for any degraded run regardless of per-agent
status), which is the defect ISS-701 targeted. Note this means the original
`QA-PS-024` report's claim that the header badge shows amber "Degraded" is no
longer accurate for this revision.
