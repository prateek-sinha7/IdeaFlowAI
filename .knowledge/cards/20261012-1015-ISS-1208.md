# ISS-1208

**INFERRED** sibling of [ISS-1194](20261012-0735-ISS-1194.md) (register entry `QA-KB-123`). Every list below was read at HEAD and the Run History and Analytics-filter rows were computed against the dev database (SELECT only); what a user sees on screen for the other rows was not observed, and whether any of this is a defect is an open product question. This is a lead for the owner, not a defect report.

## Condition

An account with `prototype_v2` runs (admin has 16 roots and 12 revision runs that hang off them: `evidence/qa-kb-123/analysis-01-chip-bucket-replay.txt`). The same lists treat `ppt_v2`, `user_stories_v2` and `backlog` the same way by the same functions; only `prototype_v2` is measured here.

The History "Custom" chip and the Analytics "Custom" filter also disagree about what Custom is: History files every non-framework type there (`RevisionFamilyView.tsx:101-104`), Analytics matches only `custom` and `custom_revision` (`analytics.py:529`). Other surfaces already treat v2 as a Prototype with its own label: `savedworkflows/pipelineLabel.ts:16` maps `prototype_v2` to "Prototype" and `sidebar/Sidebar.tsx:45` labels it "Prototype v2", so History, Analytics and Preview are the outliers. The same pattern, on another surface, is [ISS-1195](20261012-0942-ISS-1195.md) / [ISS-1196](20261012-0942-ISS-1196.md) (Deliverable access omits the v2 workflows).

## Why the root cause implies it

[ISS-1194](20261012-0735-ISS-1194.md) asks why the Prototype chip is absent although the account has 28 prototype-family runs. The answer is that none is rooted at a type the chip counts, and that is this list. It also closes off the validator's second fix direction, "re-base the chip tests onto prototype_v2": that run set has no chip, and two of the three chip tests assert things only the first-party prototype renderer provides (a "Prototype" renderer mode, S-07-29; `View source` / `Open tweaks panel` controls, S-15-28).

One more consequence, INFERRED: S-10-12 (`test_analytics.py:252`, "defect as-is") passes today through `text.count("PROTOTYPE") > 1`, which the raw `PROTOTYPE_V2` rows satisfy as a substring; the duplicate-label defect it was written for (a `prototype` row and a `prototype_revision` row) no longer exists in this data.

## Open question (not for this card to decide)

Is `prototype_v2` meant to be a member of the Prototype family in Run History, Analytics and Preview, or a separate product that is deliberately "Custom" there? Evidence for "meant to be": [ADR-0054](20260925-1201-ADR-0054.md) made it the replacement for `pdf_to_prototype`, the catalog offers it as "Prototype from documents (Depth)" (enabled for hexaware, pro and enterprise per [ISS-1195](20261012-0942-ISS-1195.md)'s tier projection); two other surfaces label it "Prototype"; `ppt_v2` already got the equivalent normalization in Preview (`PreviewPanel.tsx:1084-1087`, spec 017) while `prototype_v2` did not. Evidence for "deliberate": `RevisionFamilyView.tsx:92-100` states that the four frameworks are fixed and everything else is custom by definition, and chips counting family roots only is ISS-219's open decision. If the owner says "meant to be", the change is one rule in each of the four places, ideally one shared type-to-family function; it would also change what 16 existing runs are called, so it needs a UI check of the History chips and the Analytics breakdown after it.

## What would settle it

The owner's answer. For the one INFERRED consequence: open a completed plain `prototype_v2` run (for example the admin's `0f62f7bc`) at `/runs/{id}` and read `[data-testid="renders-as-switch"]`; Auto / HTML / Markdown / Bundle confirms the generic channel, Auto / Prototype refutes it.

## For the test-writer

If the answer is "meant to be", the natural guard is offline and unit-level (vitest on `filterBucketFor` and on the analytics label map for `prototype_v2` and `ppt_v2`, one file at a time).
