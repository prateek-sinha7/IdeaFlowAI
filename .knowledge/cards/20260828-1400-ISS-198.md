## Reproduction — 3/3 cold starts, cycle 1

Reproduced on every cycle, cold navigation each time (never a soft re-click of the
same screen):

1. Cycle 1 — signed in as qa-admin, navigated directly to `http://localhost:3000/runs`
   from `/login`. Header read "Run History" / "50 runs"; the "All" filter chip read
   "All 50". `browser_network_requests` showed every `/api/runs` call from page load
   through filter/sort clicks carried `limit=50` and never `offset`.
2. Cycle 2 — navigated away to `/dashboard`, then cold-navigated to `/runs` again.
   Same "50 runs" / "All 50" labels.
3. Cycle 3 — navigated away to `/library`, then cold-navigated to `/runs` again. Same
   "50 runs" label, confirmed via `browser_find`.

All three cycles from a fresh navigation, same result — CONFIRMED, no axis variation
needed (3/3 on first pass).

## Root cause

`frontend/src/components/history/WorkflowHistory.tsx`:

- The mount effect (line ~204-213) calls `getWorkflows(token, { limit: 50 })`, and the
  response's `total` field IS captured into `totalRuns` state (`setTotalRuns(total)`,
  line 208) — the backend already tells the frontend the true count (273 for qa-admin).
- But the header text at line 973, `<p>{runs.length} runs</p>`, renders `runs.length`
  (always capped at the page size actually fetched — 50, or `Math.max(50, runs.length)`
  on refresh) instead of the `totalRuns` state that already holds the real total. The
  same `runs.length`-based count drives the "All" filter chip.
- `handleLoadMore` (line 289-299) is fully implemented — it correctly does
  `getWorkflows(token, { limit: 50, offset: runs.length })` and appends to `runs` — but
  it is dead code: `grep -n "handleLoadMore"` shows exactly one reference, its own
  definition. No button, no scroll listener, no `IntersectionObserver` calls it
  anywhere in the file (confirmed no `onScroll`/`IntersectionObserver` in the
  component). So scrolling the list's `.flex-1.overflow-y-auto` container to the
  bottom fires zero additional requests, matching BUG-20260828-011500-runs's evidence.

Net effect: the component already has everything it needs (`totalRuns` from the API,
a working `handleLoadMore`) but never displays the former or invokes the latter — this
reads as an incomplete wiring of an otherwise-finished pagination feature, not a
missing backend capability.

## Expected vs Actual

- Expected: header/chip show the true total (`totalRuns`, e.g. "273 runs" / "All 273"),
  and scrolling to the bottom (or a Load More affordance) fetches subsequent pages via
  `handleLoadMore` until `runs.length >= totalRuns`.
- Actual: header/chip always show `runs.length`, which never exceeds the most recent
  page fetched (50, or `Math.max(50, runs.length)` on manual/auto refresh); 223 of 273
  runs for the qa-admin account are permanently unreachable from `/runs`, and the UI
  represents the visible 50 as the complete total.

## Analysis addendum (3-analyzer, 2026-08-28)

**Historical confirmation — this is a collateral regression, not the original design.**
`git show ce08bf542 -- frontend/src/components/history/WorkflowHistory.tsx` (commit
`ce08bf542`, "Revert 'Merge branch staging into dev'", 2026-08-17) deletes a fully-working
footer block that was gated on `runs.length < totalRuns && !loading`, read "Showing
{runs.length} of {totalRuns} workflows", and had `onClick={handleLoadMore}` wired — and
in the same diff reverts `typeCounts.all` from `totalRuns` back to `families.length`.
Comparing against the pre-revert commit (`git show 6a2c84709:...WorkflowHistory.tsx`)
confirms both the working Load More footer and the `all: totalRuns` chip formula existed
immediately before this revert. The revert's stated purpose (per its diff to
`backend/app/api/runs.py`) was to remove a duplicated `WorkflowRunListResponse` class and
a duplicated `total = query.count()` block left over from a bad merge — the Load More
UI's removal reads as unintended collateral damage from that same commit, not an
intentional rollback of pagination.
**Caveat:** the header text bug (`{runs.length} runs`, line 973) is NOT part of this
regression — `git show 6a2c84709:...` shows that line already read `{runs.length} runs`
even in the pre-revert "good" commit. It has been wrong since `totalRuns` was first
introduced (commit `35b17ad1a`, "KAN-131", 2026-07-30) and was never fixed. So the fixer
should not treat "revert the revert" as a complete solution — it would restore the Load
More footer and the chip formula, but not the header text.

**Backend is not a blocker.** `backend/app/api/runs.py:315-365` (`list_runs`) currently
accepts `limit` (default 50, max 100) and `offset`, and sets `X-Total-Count` from
`query.count()`. The gap is entirely frontend-side.

**Blast radius — grepped every caller, ruled out siblings elsewhere.**
`grep -rln "getWorkflows(" frontend/src` (excluding tests) returns 6 files:
`WorkflowHistory.tsx`, `app/[...view]/page.tsx`, `providers/RunConnectionProvider.tsx`,
`components/results/AgentThinkingTab.tsx`, `store/slices/globalSlice.ts`,
`lib/api.ts` (the function itself). Every call site other than `WorkflowHistory.tsx`
fetches a small fixed `limit` (50 or 100) for a "recents"-style list and never claims to
represent the account's *total* run count — none of them capture `total` into state or
render it as a count, so none replicate this defect. A parallel grep of
`frontend/src/components/sidebar/*.tsx`, `catalog/*.tsx`, `savedworkflows/*.tsx` for a
similar "N items"-as-total label found none. **This defect is confined to
`WorkflowHistory.tsx` — no sibling caller elsewhere needs the same guard.**

Within `WorkflowHistory.tsx` itself, four more consequences of the same "`runs` never
grows past the fetched page" mechanism are filed as siblings below (INFERRED, not yet
reproduced): search (`matchesFilter`, line ~430) and sort (`bucketAndSortFamilies`, line
~950) both operate only on the capped `runs`/`families` array with no indication of
truncation ([ISS-207](20260828-1617-ISS-207.md), [ISS-208](20260828-1617-ISS-208.md));
`handleDeleteConfirm` (line ~408-421) updates `runs` but never `totalRuns`, desyncing
the offset bookkeeping `handleLoadMore` depends on ([ISS-209](20260828-1617-ISS-209.md));
and the per-type filter chips' `typeCounts` (line ~952-958) undercount and can vanish
entirely for a type with zero hits in the capped window ([ISS-213](20260828-1618-ISS-213.md)).

**Fix location.** Everything belongs inside `WorkflowHistory.tsx` — confirmed above that
no other component shares this code path, so there is no shared function to centralize
this in. Within that one file:
1. Header (line 973) and the `all` chip (line 952, `typeCounts.all = families.length`)
   need to read from `totalRuns` instead of the capped array — but note `totalRuns` counts
   raw runs while `families.length` counts grouped families; these are different units,
   and the pre-revert code's `all: totalRuns` compared a raw-run total against
   family-grouped per-type counts, an inconsistency of its own the fixer should resolve
   deliberately rather than restore blindly.
2. A pagination trigger needs to call `handleLoadMore` — the deleted footer (button gated
   on `runs.length < totalRuns`) is a ready-made reference, or an `IntersectionObserver`
   on `.flex-1.overflow-y-auto` for true infinite scroll.
3. `handleDeleteConfirm` needs a `setTotalRuns` decrement alongside its `setRuns` filter
   (ISS-209).
4. Search/sort (ISS-207/ISS-208) need a product decision — fetch-all-before-search,
   server-side search/sort (`list_runs` would need new query params), or an explicit
   "searching only the loaded N of M" affordance. Do not silently pick one.
5. Per-type chip counts (ISS-213) need the same kind of decision as item 4 — `totalRuns`
   has no per-type breakdown to read from, so either the backend grows a per-type count
   aggregate (`list_runs` or a new endpoint), or the chips gain a "counts reflect the
   loaded N of M" affordance instead of claiming exact per-type totals.

Do NOT blindly `git revert` `ce08bf542` wholesale — its backend diff also correctly
removed a duplicated `WorkflowRunListResponse` class and a duplicated `total =
query.count()` block (merge-conflict artifacts); only the frontend UI-wiring pieces
should be restored.
