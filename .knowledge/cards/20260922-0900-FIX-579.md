## The symptom

Pinning v2 of a run showed v3. `/runs/{id}/versions/N` resolves the pin by
INDEX into the family member list, so a member missing from that list shifts
every later version onto a different run — a wrong answer that looks like a
working feature.

## The root cause

[FIX-173](20260805-1853-FIX-173.md) added a guard dropping any child whose
canonical base type differed from the root's, to stop concurrent PPT and
prototype revisions contaminating each other's version dropdown.

It could not do the job it was written for. The contamination came from a
**write-path race**: `contentSourceRunId` transiently pointed at the wrong run
when `postRevision` fired, so the child's `parent_run_id` AND its
`source_run_id` were both written from the same wrong value. A read-path type
check cannot tell that row from a deliberate one — the comparison caught the
reported case by coincidence. Verified: no row in this database has the two
disagreeing.

Meanwhile it rejected two legitimate, shipped behaviours:

- A deliberate cross-type revision — a `custom` run whose deliverable is
  `prototype.html` routes through `handleRevisePrototype`, producing a
  `prototype_revision` child of a `custom` root.
- A divert. `ex_A3_divert` → `ex_A3_b_spanish` is a different pipeline BY
  DESIGN, so a base-type comparison can never admit a diverted child.

## What changed

The guard is removed. A cross-type child is admitted and **logged**, so a
genuine contamination stays observable instead of becoming indistinguishable
from a version that never existed.

`_compute_revision_ordinal`'s docstring is reconciled at the same time: it
never carried this guard and warned that the two counting rules could diverge.
They did — the git tag read `v3` where the API's `revision_index` said `2`.
Both now count every member.
