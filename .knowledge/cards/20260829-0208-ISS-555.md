## What happened

INFERRED sibling of [ISS-331](20260828-1840-ISS-331.md), derived from a
source-code read while analyzing that bug — not yet independently driven
live in a browser.

`SkillDetailModal` in `frontend/src/components/library/LibraryPage.tsx` is
the same-file, same-family modal as the reported `HookDetailModal` (both
render behind `/library` detail routes, both use the identical
`copied`/`handleCopy` idiom). Its `handleCopy` (`LibraryPage.tsx:201-205`)
is used by two separate buttons in the same modal: the header "Copy content"
button (`onClick={handleCopy}` at `LibraryPage.tsx:255`) and the "Copy"
button on the raw `SKILL.md content` block (`onClick={handleCopy}` at
`LibraryPage.tsx:315`).

## Root cause (same mechanism as ISS-331, confirmed by direct read of this file/lines)

```
const [copied, setCopied] = useState(false);
const handleCopy = async () => {
  await navigator.clipboard.writeText(skill.content);
  setCopied(true);
  setTimeout(() => setCopied(false), 2000);
};
```

No `try/catch`, no `.catch()`, no failure-state UI — identical shape to the
root cause ISS-331 confirms for `HookDetailModal`. Any rejection of the
`writeText` promise leaves both buttons stuck reading their default label
forever, with nothing surfaced to the user.

**What would confirm this live:** cold-navigate to a skill detail
(`/library` -> Skills tab -> any skill card), click either Copy button, and
check `document.body.innerText` / button `outerHTML` before and after, the
same protocol ISS-331 used for the hook detail page.
