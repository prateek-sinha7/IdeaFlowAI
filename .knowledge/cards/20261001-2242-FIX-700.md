## What was wrong

Bug report QA-KB-020. Two defects in `frontend/src/hooks/useRunChat.ts` share one premise: the chat transcript is
family-anchored, so frames of several runs fold into one array, but two pieces of hook state assumed a single run. The
root causes come from the analysis cards and are not re-derived here.

- [ISS-654](20260917-1250-ISS-654.md), the root card. `handleFrame`'s `case "review_gate_approved"`
  (`useRunChat.ts:569-584` before this edit) flipped "the last unresolved gate card" in `prev` by array position. The
  frame carries `pipeline_run_id` (`backend/agents/execution_engine/engine.py:12582-12590`), and every gate card carries
  its run as `runId` (`upsertNarratorMessage`, `useRunChat.ts:406-407`), but nothing compared them. With gate cards of
  two runs in one transcript, approving the EARLIER run flipped the later run's card and left its own card open. The
  validator reproduced this 3/3 cold (`evidence/qa-kb-020/01-validate-attempt{1,2,3}-vitest-output.txt`).
- [ISS-926](20261001-2223-ISS-926.md), the sibling. `lastSeqRef` was one scalar fed by frames of every family run
  (`useRunChat.ts:505-508` before this edit), but `run_events.seq` is per run (`backend/agents/authz.py:407-412`). After a
  family seed it held the highest seq of ANY member. Both after-seq fetches, the post-send re-fetch and the page's
  completion recovery through `getLastSeq`, then asked the viewed run for events above every row it has, and got none.

## What changed, and why there

Line numbers are as of this fix, in the uncommitted tree.

1. ISS-654, `useRunChat.ts:579-599`. The case now has braces, because it declares a `const` (`no-case-declarations`).
   It reads `rid = data.pipeline_run_id` (`:587`), and the `.find` predicate gains
   `(!rid || !m.runId || m.runId === rid)` (`:592`). So the newest unresolved gate card of the approved run flips. If
   either side has no run id, the old positional match applies. This is the agreed minimal fix from BUGS.md plus the
   analyzer's brace amendment. It lives in `handleFrame`, which every entry point folds through (the `subscribe`
   fan-out, `seedTranscript`, `appendFrames` and the post-send re-fetch), so one guard covers them all.
2. ISS-926, `useRunChat.ts:500`, `:509-518`, `:733`, `:754`. `lastSeqRef` is now a `Record<string, number>`. Its key is
   the frame's `pipeline_run_id ?? run_id`, falling back to the hook's `runId`, because `chatSubscribe` filters live
   frames to the viewed run (`page.tsx:2411-2428`). Every backend chat and proposal row stamps `pipeline_run_id` with
   the run it is stored under (`backend/app/api/run_commands.py:1223-1231`, `:2252-2259`, `:2382-2394`;
   `backend/app/agents/chat_narrator.py:255`), so the key names the seq space the row's `seq` belongs to. The post-send
   re-fetch reads the entry for `postRunId` (`:733`), and `seedTranscript` resets the whole map (`:754`).
3. ISS-926, the second reader. `getLastSeq` now takes the run it is asked about, typed
   `(runId: string | null) => number` (`useRunChat.ts:229`, `:824-826`). Its only caller is the completion recovery.
   That caller now passes the run it fetches, `getRunChatLastSeqRef.current?.(_completingRunId)` (`page.tsx:1672-1673`),
   and the ref's type follows (`page.tsx:2471`). Both edits are outside the other fixers' `page.tsx` hunks.

Known limit, not carded: a gate card without a `runId` still matches any approval, through the agreed fallback. Every
backend gate card stamps `pipeline_run_id` (`chat_narrator.py:255`), so only synthetic frames can reach that branch.
