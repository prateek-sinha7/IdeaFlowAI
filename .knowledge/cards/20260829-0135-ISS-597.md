## What is suspected

[ISS-383](20260828-2021-ISS-383.md) root-caused the bug to `SandboxTab.tsx`'s `CodeView`
(~line 492 onward): its own extensions list (`~675-701`) never sets
`EditorState.readOnly.of(true)` / `EditorView.editable.of(false)`, so `.cm-content` is
`contentEditable === true` with no visual read-only signal. Every reproduction in the register
entry and in ISS-383 exercised exactly one call site — the explicit "Code" toggle button, which
renders `<CodeView code={content} lang={extOf(active.path)} fill />` at `SandboxTab.tsx:1331`
(reached when `!rendered`, i.e. the toggle is in Code mode, per the render condition at
`:1326-1332`).

`CodeView` has a SECOND call site that was never toggled to and never tested: `SandboxTab.tsx:411`,
inside the `code:` override passed to `ReactMarkdown` as `MD_COMPONENTS.code`
(`:405-413`). Any fenced block (or any inline code long enough to contain a newline) inside a
markdown file's default, already-rendered **Preview** — the mode a user lands on by default,
before ever touching the Code/Preview toggle — renders through `<CodeView code={text...}
lang={lang} />`. This is the exact same function, same missing `readOnly`/`editable` config, same
missing lock icon / Save-Discard affordance. `CodeView`'s own doc comment (`:476-477`) even names
both surfaces as one component: "ONE component, both surfaces: the full-file view and every
fenced block inside a rendered markdown file" — so the code that ships already documents this
second surface exists; nobody exercised it during validation.

## Condition

- Open any run's Workspace tab and select a markdown file (`.md`) that contains at least one
  fenced code block (```` ``` ````-delimited or a language-tagged fence) — e.g. an agent-authored
  file with an embedded JSON/YAML/code snippet, a common shape for `PLANNER.md`-style agent notes.
- Stay on the default **Preview** mode — do NOT click the "Code" toggle button at all.
- Click into the rendered fenced block's text and type.

## Expected vs actual

- **Expected:** identical to ISS-383's ask — either the fenced block is genuinely inert (no
  `contentEditable`), or an explicit "editing" indication (lock icon / editing label / warning on
  navigation) appears, matching whatever disposition is chosen for the Code-toggle surface, since
  it is the same component.
- **Actual (predicted):** the fenced block accepts keystrokes exactly as the Code-toggle surface
  does — `.cm-content` under the fence is `contentEditable === true`, typed text inserts live at
  the cursor, and switching files silently discards it — with the added twist that the user never
  had to intentionally switch into "Code" mode at all; the editable surface is present in the
  page's DEFAULT view.

## Why the root cause implies this

`CodeView` is not conditioned on which call site invoked it — both `:411` and `:1331` construct
the identical `EditorView` from the identical extensions array (`:675-701`). A defect in "the
extensions array never sets readOnly/editable" cannot be scoped to one caller; it reproduces
identically at every call site of the function, and grep confirms there are exactly two
(`grep -n "<CodeView" frontend/src/components/results/SandboxTab.tsx` → `:411`, `:1331`) — both
inside this same file, `CodeView` is not exported.

**Marked INFERRED**: not independently reproduced in a browser (this pass is read-only). What
would confirm it: open a run's Workspace tab, pick a markdown file whose content includes a
fenced code block, stay on Preview (no toggle), click into the rendered code block, type, and
check `document.querySelectorAll('.cm-content')` for a `contentEditable === "true"` node under
the fence.

## Where the fix belongs

Same place ISS-383 already names: inside `CodeView`'s own extension list (`SandboxTab.tsx:675-701`),
not at either call site. One guard there closes both surfaces in the same edit — patching only
`:1331` (the reported path) leaves `:411`'s markdown-preview surface silently unguarded. Whatever
disposition is chosen for ISS-383 (true read-only vs. a visible "scratchpad, not saved" indication)
must be visible from both call sites, since they render the identical DOM.

Note for whoever fixes ISS-383: `frontend/src/components/results/SandboxTab.test.tsx:375-410`
("opens Find and Replace on the code view, and can actually replace") is an EXISTING, PASSING test
that explicitly asserts `.cm-content`'s `contenteditable` attribute is `"true"` and that CodeMirror's
Replace control is live — matching the inline comment at `SandboxTab.tsx:687-690` ("Replace has to
be able to write, so the doc is editable — but it is a SCRATCHPAD"). A naive
`EditorState.readOnly.of(true)` fix blocks ALL transactions, including the ones Replace dispatches,
and would fail this test. `EditorView.editable.of(false)` (DOM `contenteditable` off, but keymap
commands still dispatch) is the CodeMirror-6-idiomatic way to keep Replace working while removing
the plain-typing/paste surface this bug reports — but that still changes the assertion at `:403`
from `"true"` to `"false"`, so the test needs a deliberate update, not just a code change.
