## Description

The product could not tell you whether prompt caching was saving money or costing it — and the obvious version of this feature would have printed a catastrophic wrong number on day one. ISS-034 asked for "saved $Y (Z%)". That framing is refuted by the repo's own data and was NOT built. Re-derived read-only from backend/dev.db through the real shared estimate_cost_usd (0 reconciliation mismatches on all 11 rows): 6 of 11 persisted runs are strictly NEGATIVE (-4.98%..-8.86%), 1 exactly zero, 4 positive; the +80.34% aggregate is carried by two long prototype runs. A UI that can only say "saved" would be wrong on the MAJORITY of runs in the only dataset that exists. Shipped instead (owner decision D2): estimated_cost_full_usd — the as-if-UNCACHED counterfactual on the SAME token base — at BOTH cost sites, and a SIGNED Analytics line that branches on the sign of the data (positive -> "saved", negative -> "cost more" in amber because it is a config finding not an error, zero -> renders NOTHING, since a "0%" would imply caching ran and broke even). Every cited line number had drifted and was re-verified: the analysis said engine.py:2842-2855 / run_commands.py:2100-2115 and D2 said :2847-2854 / :2107-2114; actual at c05906c0 was :2873-2880 and :2171-2178. A THIRD estimate_cost_usd at run_commands.py:1574 — unmentioned by the analysis — is the Concierge chat_usage per-message writer (FIX-233) and was correctly left alone. The catastrophic-number trap was real and is closed: analytics.py:_num coerces an absent field to 0.0 and 0 of 11 existing rows carry the new key, so the naive sum(_num(usage.get(...))) was OBSERVED producing spend_full = $0.00 against spend = $15.00 -> "caching cost you the entire window more (-100%)". r_cost_full = _num(...) or r_cost makes a legacy row's delta exactly zero — never a fabricated $0 baseline — and metered_runs lets the UI state its coverage. Golden-neutral PROVEN BOTH WAYS, not assumed: key emitted AND stripped -> 10 passed with all 15 golden files byte-identical (SHA-256 compared); emitted and NOT stripped -> 5 event snapshots RED (the non-vacuity control). Zero regeneration; SNAPSHOT_UPDATE appears nowhere in the diff. D2's mandated footnote was stale and was corrected against the code: the Concierge IS metered per message now (concierge.py:578-609 -> ctx.usage; run_commands.py:1559-1583 writes a chat_usage event) but chat_usage has ZERO readers and Analytics reads only workflow_runs.token_usage, so chat spend is *recorded and excluded*, not unmetered; handoff is genuinely unmetered — app/services/handoff_pipeline.py has zero token metering and writes no WorkflowRun rows (the analysis grepped agents/execution_engine/handoff_pipeline.py, which does not exist). No migration (token_usage is an untyped JSON blob; every reader a tolerant json.loads) and no per-run badge — that would reverse the deliberate KAN-83 removal, revive 3 quarantined e2e cases, and put a precise dollar beside a run whose own total is not displayed. The global-cache-flag half is split out as ISS-120, not folded in.

## Root cause

The two cost sites priced only what was ACTUALLY paid, with no counterfactual, so the effect of BEDROCK_PROMPT_CACHE_ENABLED was unobservable anywhere in the product — and the one surface that shows dollars (Analytics) had no second term to compare against. The discriminator turns out to be run LENGTH, not workflow type: a run that writes cache entries it never re-reads pays the 1.25x cache_write_5m premium for nothing.
