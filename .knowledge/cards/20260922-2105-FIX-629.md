# FIX-629

Resolves [ISS-833](20260922-2002-ISS-833.md) and
[ISS-834](20260922-2003-ISS-834.md) (`BUGS.md#qa-ps-046` / `LEDGER.md`).

Does **not** close QA-PS-046: its root card
[ISS-832](20260922-2001-ISS-832.md) also names one remaining
`GET /api/runs?limit=50` on `/workflows/new`, which is consumed by the
always-mounted header and is escalated as a product decision —
`ESCALATIONS.md#qa-ps-046`.

## What was wrong

Two ways the 27 KB capability palette could still be fetched more than once,
both of them outside the reach of [FIX-617](20260922-1935-FIX-617.md)'s
`cachedGet()`:

- **[ISS-833](20260922-2002-ISS-833.md)** — `SHARED_GET_TTL_MS = 30_000`
  (`frontend/src/lib/api.ts`) is shorter than the gap the cache exists to
  bridge. `composer/CanvasView.tsx:304` fetches the palette on canvas mount;
  `composer/CanvasConfigRail.tsx:162` asks again only when the user opens an
  agent's config tab. FIX-617's own card justified the TTL with
  "`CanvasConfigRail` asks seconds after `CanvasView`'s fetch has already
  settled" — but naming a workflow, dragging agents in and reading their
  descriptions is a multi-MINUTE task, so past 30 s the entry was stale
  (`cachedGet`'s `Date.now() - hit.at < SHARED_GET_TTL_MS`) and the second
  call fell through to a real request for a byte-identical answer.
- **[ISS-834](20260922-2003-ISS-834.md)** — `capabilitiesApi.get`
  (`frontend/src/store/api/capabilities.ts:34-38`) is a second, axios-based
  implementation of the same endpoint on `store/api/http.ts`, which has no
  cache or dedupe of its own. It has zero callers today, so it contributed
  none of the reported duplication, but it is the surface `store/api/api.ts`'s
  own header comment ("Consolidated axios-based API client") steers new code
  toward — the next component wired to it reopens FIX-617's defect with no
  test watching.

## What changed and why there

**`frontend/src/lib/api.ts` — a per-path TTL on the shared GET cache.**
`SHARED_GET_TTL_MS` stays 30 s for everything; a new `ttlFor(path)` returns
`CATALOG_GET_TTL_MS` (30 min) for `/api/capabilities`. The change is in
`cachedGet`'s freshness check — the one place every capability caller already
routes through (`AgentsPopup.tsx:1128`, `AgentsPopup.tsx:1530-1549` via
`useAgentCapabilities`, `CanvasView.tsx:304`, `CanvasConfigRail.tsx:162`,
`AgentModelPicker.tsx:74`), so no call site needed touching.

A long entry is safe *for this path specifically*, which is why the TTL is
per-path rather than raised globally: `GET /api/capabilities` is a live
enumeration of the backend's capability registry plus the model catalog
(`backend/app/api/capabilities.py:130-140` — "Enumerates the registry live
(`_KNOWN` after `discover()`)"), auth-gated but carrying no per-user or
per-run field, so its body cannot change without a backend restart. The cache
is a module-level `Map`, so a page load starts it empty, and
`dropAccountReadsOnWrite` still clears the whole thing on any non-GET. The
30 s window is left in place for `/api/analytics/summary` and
`/api/settings/preferences`, whose bodies *do* move under the user.

**`frontend/src/store/api/capabilities.ts` — a single-flight guard.** The
axios twin now shares one open request between concurrent callers
(`inFlightPalette`, dropped in `.finally`), the same shape as
`inFlightWorkflows` in `lib/api.ts` (FIX-616). De-duplicates, does not cache:
a dead code path is not worth a second cache implementation next to the one
`lib/api.ts` already owns, and a session-length axios cache would outlive an
account switch that the `lib/api.ts` cache keys away. Deleting the dead
function was the card's other option and was NOT taken — pre-existing dead
code is left alone, and its test asserts the dedupe.
