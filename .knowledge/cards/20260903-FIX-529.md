## Related

## What was wrong

Reviewing run `faba87c9` (93m, completed), the Steps panel header read 93m 10s
while the rows summed to 38m 05s. `duration` was assigned per step id on every
`agent_complete`, so a step dispatched twice overwrote its own first number:
thirty executions rendered as seventeen rows, and the Task Planner's seven
spec-revision passes (17m 22s in total) reported 2m 23s. Separately, 28m 29s of
the run was spent parked at review gates — time that belongs to no step at all
and had nowhere to be counted.

## The fix (commit 3e6fcb93c)

- `passCount` counts every dispatch, not just the conditional loop-backs that
  `visit_count` sees.
- `cumulativeDuration` sums all passes; `duration` remains last-pass-only.
- A `busySeconds` / `waitingSeconds` split is folded from each event's own `ts`,
  so a reopened run accounts identically to a live one.
- `agent_complete` joins `ACCUMULATING_FRAME_TYPES` — it had been registered as
  idempotent-because-it-overwrites, which stops being true once a duration
  accumulates.

Pinned by replaying run `faba87c9`'s own durable log (90 frames distilled from
5.8 MB) through the reducer: busy 3878.4s + waiting 1709.4s + 1.7s dispatch
residual == the 5589.4s header.
