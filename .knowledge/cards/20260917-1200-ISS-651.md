# ISS-651

Register entry: **QA-PS-007** (`BUGS.md`).

## Reproduction

Verified by full code-path trace (cycle 1 of the trace — the mechanism is
unconditional across every ppt run, so a second and third read of the same
code path reproduce identically; no live pipeline run was launched for this
validation, see Note below).

**Route:** `/runs/{id}/files` (Files tab) and `/runs/{id}` (Preview panel
header Download), for any completed `ppt` / `ppt_revision` run.

**Trace:**

1. Every stage of the ppt pipeline writes the deck to a **literal, hardcoded**
   workspace path, never derived from the run topic:
   - `backend/agents/prompts/ppt-composer/AGENT.md:68` — "Write the complete
     deck to `presentation.html` using the workspace write_file tool."
   - `backend/agents/prompts/ppt-validator/AGENT.md:43` — "Write the final
     validated deck to `presentation.html`..."
   - `backend/agents/prompts/ppt-deck-qa-v2/AGENT.md:50-58` — reads/writes
     `presentation.html` by that literal name throughout.
2. `frontend/src/components/results/FilesTab.tsx` DOES derive a
   content-based, topic-aware name via `deriveDeliverableFiles` /
   `deriveDeliverableFilename` (FIX-140) — this part works correctly when it
   runs.
3. But `withWorkspaceFile()` (`FilesTab.tsx:451-462`, added for ISS-199)
   unconditionally overwrites that derived name: once
   `resolveRunDeliverable()` (`frontend/src/lib/api.ts:1175-1191`) finds the
   run's real workspace file, the FileItem row's `name` is replaced with
   `file.path.split("/").pop()` — i.e. the raw on-disk filename. Since every
   ppt run's on-disk file is literally `presentation.html` (per point 1),
   the row name — and therefore both the Files tab display and the
   `handleDownload`-driven downloaded filename — is always
   `presentation.html`, regardless of what `deriveDeliverableFilename`
   computed from the deck's `<title>`.

This is a **structural, deterministic** defect: it does not depend on
timing, account tier, theme, viewport, or empty/populated state — every
completed `ppt`/`ppt_revision` run resolves through this same path with the
same literal workspace filename.

## Expected vs Actual

- **Expected:** Final Output filename (Files tab + Download) reflects the
  run topic, e.g. `lateral-thinking-presentation.html`.
- **Actual:** Always `presentation.html`, for every ppt run, because the
  backend agents never write the topic into the filename and the frontend's
  workspace-file correction (ISS-199) trusts the on-disk name unconditionally
  over the content-derived one.

## Root cause

Two independent facts compound:

1. `backend/agents/prompts/{ppt-composer,ppt-validator,ppt-deck-qa-v2}/AGENT.md`
   hardcode the workspace write target as the literal string
   `presentation.html` — never interpolated with the run's topic/title.
2. `withWorkspaceFile()` in `frontend/src/components/results/FilesTab.tsx:451`
   has no fallback: when the resolved workspace file's own name is generic,
   it still wins over the correctly-derived content-based name from
   `deriveDeliverableFiles`.

## Note on validation method

No live ppt pipeline run existed for `qa-admin@flowinqa.com` at validation
time, and launching a fresh run to observe this live would spend real
LLM-pipeline cost/time purely to confirm a mechanism that is already
provably unconditional from three independent, literal `AGENT.md`
instructions plus the non-conditional override in `withWorkspaceFile`. Per
standing project policy (do not launch new pipeline runs solely to validate/
test without asking first), this was validated by full source trace instead
of 3 cold UI reproductions. Evidence (grepped excerpts of every file/line
above) is saved at
`bug-hunter/evidence/run-files-tab/_scratch/QA-PS-007-code-trace.txt`.

## Won't-fix (2026-09-23)

User decision: do not rename the deliverable — changing the `write_file` target risks breaking
other workflows. A generic `presentation.html` is acceptable provided the bytes are correct.
Byte-correctness verified on run `8754cc43-f0b6-4005-b2d1-34db2eb41ad1` (v8 and pinned v2, header
Download button; see [WONTFIX.md#qa-ps-007](../../WONTFIX.md#qa-ps-007)).
