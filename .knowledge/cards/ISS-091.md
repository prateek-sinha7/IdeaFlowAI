# ISS-091

## Title

Rejecting at a review gate does not STOP the pipeline: every remaining step still runs and the run ends on pipeline_complete. Measured at 99fcf4a2 — i.e. WITH FIX-227 and FIX-228 already landed, so FIX-227 does NOT cover this. Offline probe, a normal (non-resume) launch with an inline Human_Gate that rejects: BEFORE cancel: [... agent_complete, review_gate_ready] then AFTER cancel: [wave_started, subagent_spawned x2, subagent_result x2, merge_started, merge_completed, wave_completed, wave_started, subagent_spawned x2, subagent_result x2, merge_started, merge_completed, wave_completed, pipeline_complete] — the user rejects, the engine says pipeline_cancelled, and both remaining waves run to completion. ROOT CAUSE (proven, two parts). (a) _run_agent yields pipeline_cancelled and returns (engine.py:4448-4452 live gate, :3403 / :3510 re-entry + post-revision), but return only ends that step's generator. The consuming loop (engine.py:2513-2520) inspects only agent_error — it has no notion of a terminal event arriving through the stream — so the outer for i, spec in enumerate(ordered_agents) simply advances to the next step and falls through to the sole pipeline_complete emitter. (b) The step-boundary cancel check that WOULD stop it (engine.py:2371) reads cancel_event, and a gate rejection sets no cancel_event at all — which is precisely why FIX-227, whose whole mechanism is threading a real cancel_event into the resume path, is orthogonal to this. WHY IT IS NOT WORSE: _run_agent opens with a terminal-state guard (engine.py:3319-3320, self._state_machine.get_state(...)), and the rejection transitions the machine to cancelled — so every step routed through _run_agent (single_shot, and task_loop, which calls _run_agent per task) short-circuits. wave_scheduler does not route through _run_agent and has ZERO cancel/terminal checks (grep 'is_set()' wave_scheduler.py -> 0 hits), which is exactly the family the probe shows running. So the exposure is fan-out workflows, not the od_prototype build. SECOND, RELATED GAP in the same family: wave_scheduler.py has no cancel_event check either, so a Stop during an in-flight wave is only observed at the next step boundary — the residual FIX-227 explicitly deferred ("the four loops that read no cancel flag at all ... they belong with ISS-078"). Of those four, engine.py's outer per-step loop (:2371) and task_loop.py (:275, :376) do check; wave_scheduler.py is the one that genuinely has none. NOT an ISS-078 regression and older than all of it — the prior investigation reproduced a byte-identical tail at 3e80fcc4 (2026-07-19, the last-known-green commit). *That cross-commit reproduction is cited from the investigation, not re-run by me; everything else in this row I measured at 99fcf4a2.* COST — stated honestly, not inflated. Worker + merge cost of every wave after a rejected gate, on fan-out workflows only. NOT the 5-21M od_prototype figure: task_loop is protected by the _run_agent terminal guard. I did not measure this in tokens (the probe uses a scripted model, and the probe's own workers recorded no model calls and wrote no files — the fan-out machinery ran, but I cannot claim from it what a live wave would spend). RELATION TO FIX-229: FIX-229 stops the RECORD lying (the run is now cancelled, not completed). It does not and cannot stop the work — that is this issue. SUGGESTED FIX (not attempted): give the dispatch loop a terminal-event observation symmetric to its existing agent_error observation — break on pipeline_cancelled — and/or give wave_scheduler the terminal-state + cancel_event checks every other strategy already has. Blast radius is every workflow's termination path; needs its own task with golden re-verification.
