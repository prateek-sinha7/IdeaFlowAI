# ISS-128

## Title

**A gate REJECTION persists an audit record that says `action="approve"`.** `run_commands.py`'s reject branch calls `store.set_review_response(gate_key, approved=False, edited_content=...)` without passing `action=`, so the store's own default (`store.py:123`) stamps `action="approve"` on the durable record. Measured, not inferred — the same in-process probe that proved ISS-070 printed: `action='reject' → HTTP200 approved=False stored_action='approve'`. **Functionally inert**: the engine keys its terminal decision on `approved`, not `action` (`engine.py:5852`/`:5859`), so a reject still rejects. It is a **forensic** defect — the durable row misdescribes the user's decision, and anyone auditing "who approved this gate" from the store will count rejections as approvals. The same omission exists on the two sibling ingresses' reject branches (`:1101` region and `:1322` region).

## Severity / Tag / Status (original row)

- Sev: trivial
- Tag: api,validation
- Status: **OPEN** (filed 2026-08-12 during quick-260812-sgu, deliberately out of FIX-241's scope)

## Source / Evidence

Found by the ISS-070 investigation (quick-260812-sgu) while proving the fail-open. FIX-241 fixed the `else` branch's laundering — the approve branch now passes `action="approve"` explicitly and an unknown action is refused before any write — but **deliberately did not touch the reject branch**: changing what a rejection persists is a behaviour change to durable data with real blast radius on the declared-gate outcome computation (`agents/capabilities/gates/human.py:104-141` derives `GATE_BLOCK`/`GATE_WAIT_HUMAN`/`GATE_PASS` from the gate signals), and folding it in would have muddied the RED/GREEN proof of the discriminator change. Fix shape: pass `action="reject"` at all three reject branches, then re-check `human.py`'s outcome computation and any `get_review_response` reader before trusting it.

## Validation 2026-10-01 (QA-KB-006) - CONFIRMED 3/3

Reproduction mode: Test/static, no browser. Three cold runs of an in-process probe (AST scan of `backend/app/api/run_commands.py` plus a real `ArtifactStore().set_review_response("k", approved=False)`), identical each time:

- Reject-branch calls with no `action=` kwarg: `run_commands.py:325` (`store.set_review_response(gate_key, approved=False, edited_content=body.edited_content)`), `:1599` (`art_store.set_review_response(gate_key, approved=False)`), `:1965` (`art_store.set_review_response(_gk, approved=False)`).
- Persisted row: `{'approved': False, 'edited_content': None, 'action': 'approve', 'instructions': None}` (default at `backend/agents/artifact_store/store.py:142`, `action: str = "approve"`).
- Existing `backend/tests/unit/api/test_rest_gate_commands.py` passes 3/3 (2 passed) because it never asserts `action`; the card's earlier test path did not exist and is corrected above.
- Fix: add `action="reject"` at the three sites; assert `get_review_response(...)["action"] == "reject"`.

## Analysis 2026-10-01 (QA-KB-006) — ANALYZED

Read-only analyzer pass over `feat/user-stories-v2`. CONFIRMED means a `file:line` opened in this tree, or a probe that was run (the probe scripts live outside the repo; their printed output is quoted). Nothing here edits application source.

### Root cause — CONFIRMED

`ArtifactStore.set_review_response` takes two independent inputs, `approved` and `action`, and defaults `action` to `"approve"` whatever `approved` is (`backend/agents/artifact_store/store.py:138-144`; the default is at `:143`, one line below the `:142` in the validation note above). Three ingress reject branches pass only `approved=False`, so the default stamps `"approve"`. Every other branch states its action: redo and update_specs on all three ingresses, and approve on ingress 1.

| ingress | call that omits `action=` | file:line |
|---|---|---|
| 1 `POST /api/runs/{id}/gate` (the shipped UI's Reject click, `frontend/src/app/[...view]/page.tsx:4431-4435`) | `store.set_review_response(gate_key, approved=False, edited_content=body.edited_content)` | `backend/app/api/run_commands.py:325-327` |
| 2 `POST /api/runs/{id}/messages`, `CHANNEL_GATE` | `art_store.set_review_response(_gk, approved=False)` | `run_commands.py:1965` |
| 3 Concierge `gate_action` confirm | `art_store.set_review_response(gate_key, approved=False)` | `run_commands.py:1599` |

An AST scan of `run_commands.py` lists all 12 `set_review_response` calls: the 3 reject calls above omit `action=` (wrong); the approve calls at `:1601` and `:1967` also omit it (right only because the default happens to be `approve`); the other 7 pass it explicitly.

### CORRECTION to the Title paragraph: the record is not "durable"

The Title paragraph above, and BUGS.md, call the stored record a "durable audit row" and a "forensic" defect. The code says otherwise:

- `store.py:1` and `:12`: "in-memory HITL pause/resume registry", "per-process (single-asyncio-deployment) and intentionally NOT DB-backed". The record is `self._questionnaire_responses["review:{gate_key}"]`, a dict on the `ArtifactStore` singleton (`store.py:43`, written at `:157-164`).
- The only production reader is `engine.py:12457` (`_run_review_gate`), which reads it once, right after the event fires.
- The durable trail of a rejection is two other rows, both already correct. The `gate_events` row has `outcome='block'` (`backend/agents/capabilities/gates/human.py:143` sets `rejected = True`, `:179-180` maps it to `GATE_BLOCK`; the model `backend/app/models/gate_events.py` has an `outcome` column and no `action` column). And the `pipeline_cancelled` run event carries `"User rejected output from {spec.name}"` (`engine.py:9307`, `:9457`, `:10941`).
- `DOMAIN-hitl-gating.md:671` agrees: the review gate's wait is "an in-process `asyncio.Event` in artifact_store/store.py".

So the defect is a self-contradictory in-memory record, `{approved: False, action: "approve"}`: a latent trap for any future reader that keys on `action`, not a corrupted audit row. **Severity stays `trivial`**, as this card's own frontmatter says; the `High` in BUGS.md and LEDGER.md overstates it. The record also outlives its run, because `ArtifactStore.forget_run` does not pop review responses (see [ISS-868](20261001-2106-ISS-868.md)), but nothing ever reads it back.

- **Placement OVERRULED.** The flaw is the store's unconditional default, which three separate authors tripped over, and the call-site fix leaves the harness callers above and the next caller exposed. **Fix it at the shared seam**, one hunk in `store.py` `set_review_response`: default `action` to `None`, resolve `action = "approve" if approved else "reject"` when it is `None`, and update the docstring. Callers that state an action (redo, update_specs, ingress-1 approve) are untouched, and `run_commands.py` needs no edit; the three call-site edits should not be made on top of it. One authority for the label (INV-12) and a smaller diff than three call sites. If the fixer has a concrete reason to keep the call-site fix instead, every ingress-level test below passes either way, and only the store unit test is dropped.

## Fix (2026-10-01)

edit, and `run_commands.py` is untouched. The three ISS-128 strict xfails now report `XPASS(strict)`:

`test_gate_reject_action_persisted_api.py`. The bug line leaves the markers for the 6-verifier, which overrides the
"remove the xfail" constraint above. [ISS-868](20261001-2106-ISS-868.md) stays open.
