## Three failures, three different kinds of staleness

**S-18-05 — the transcript grew user turns.** The test asserted every
`data-message-id` starts `chat_reply:`, and its own docstring admitted the
scope: *"Seeded runs only ever produce `narrator` … until a user turn exists
there is nothing else to see."* Real user turns exist now:

```
a message id is not a chat_reply: {'role': 'user', 'id': 'client-1-97663a80-…'}
a message declares an unknown role: {'role': 'assistant', 'id': 'chat-reply:client-1-…'}
```

Three shapes, one per origin, and all three are STABLE across a cold load —
`upsertUserMessage` keys strictly on the frame's `message_id` and mints only
when the frame carries none (`useRunChat.ts`), so a reload re-renders the same
id. The `chat-reply:` (hyphen) form is the documented Issue-3 fallback at
`useRunChat.ts:397` for a reply frame with no `event_id`, derived from the user
turn it answers.

**S-05-07 — the assertion was inverted by its own fix.** The test required
agent IDs in the roster and forbade display names.
[ISS-327](20260828-2033-ISS-327.md) recorded the opposite: *"WorkflowDetailView
renders agentIds.map((id) => {id}) with no id-to-name lookup, unlike the
Library and Composer views for the same agents."* The raw id WAS the defect.
`WorkflowDetailView.tsx:45-47` resolves them now, and the file is byte-identical
between `feat/bug-hunter` and `feat/conditional-gates` — not a merge regression.

**S-03 launch panels — the gate defaults are gone.** Expected
`"1 agent|pause for review"`; [FIX-323](20260828-1629-FIX-323.md) removed
`gate: Human_Gate` from the prototype AGENT.md files, so the section renders
`"no gates"` when `gatedCount === 0` (`ReviewGatesSection.tsx:211-213`).
