# ISS-828

## Description

INFERRED sibling of [ISS-793](20260922-1826-ISS-793.md) (root cause card for
**QA-PS-045**, `/create/prototype`). ISS-793's mechanism 2 is
`LaunchWizard.tsx:617-654` calling `listPrototypeTemplates`,
`listPPTTemplates` **and** `listDesignSystems` unconditionally on mount,
regardless of `mode` — which is why a prototype-only page loads the PPT
template catalog. `LaunchWizard` is not prototype-specific: it is the single
shared component for **four** modes (`frontend/src/components/workflow/LaunchWizard.tsx:80`,
`STEPPER_MODE: Record<LaunchMode, "web" | "deck"> = { prototype: "web",
prototype_v2: "web", ppt: "deck", ppt_v2: "deck" }`), reached from four
distinct routes (`frontend/src/app/[...view]/page.tsx:322-337`,
`wizardModeFor`: `create-prototype` -> `prototype`, `create-ppt` -> `ppt`,
`create-workflow` with `pipelineType` `prototype_v2`/`ppt_v2` -> those two).
The same unconditional effect runs unchanged for all four, so the identical
defect — loading a template catalog the active mode never renders — applies
to the other three exactly as it does to `prototype`:

- `/create/ppt` (mode `ppt`, deck family): `listPrototypeTemplates` fires
  and is never read (`selectedWebTemplate`/`webTemplates` are only consulted
  when `isWeb`, i.e. `STEPPER_MODE[mode] === "web"` — `LaunchWizard.tsx:667-669`).
- `/create/prototype_v2` (mode `prototype_v2`, web family): `listPPTTemplates`
  fires and is never read, same as the original `prototype` finding.
- `/create/ppt_v2` (mode `ppt_v2`, deck family): same as `/create/ppt`.

This is the exact inverse of what ISS-793 found for `prototype`: not a new
mechanism, the same one applied to the three sibling modes nobody measured
yet.

## Why the root cause implies it

`LaunchWizard.tsx:617-654` branches on nothing — `authChecked` gates the
whole effect, but which of the three `listX` calls actually fires is not
conditioned on `mode`/`STEPPER_MODE[mode]` at all:

```tsx
// Load both template families + the design-system registry once authed.
useEffect(() => {
  if (!authChecked) return;
  const token = getToken();
  if (!token) return;
  let cancelled = false;

  listPrototypeTemplates(token)
    .then((t) => { if (!cancelled) setWebTemplates(t); })
    .catch(/* ... */);
  listPPTTemplates(token)
    .then((t) => { if (!cancelled) setDeckTemplates(t); })
    .catch(/* ... */);
  listDesignSystems(token)
    .then(/* ... */)
    .catch(/* ... */);

  return () => { cancelled = true; };
}, [authChecked, router]);
```

Because this is deterministic branch-free code with no `mode`/route
dependency, the same defect necessarily reproduces on every mode that reaches
this component — there is no code path by which `ppt`/`prototype_v2`/`ppt_v2`
could avoid firing the other family's fetch. The only reason this is
INFERRED rather than CONFIRMED is that nobody has captured a live
`performance.getEntriesByType('resource')` trace for these three routes the
way ISS-793 did for `prototype` — the mechanism is proven by source, not yet
by reproduction.

`listDesignSystems` is NOT part of this defect: `dsRequired = isDeck &&
selectedDeckTemplate?.design_system?.requires === true` and `dsVisible =
isWeb || dsRequired` (`LaunchWizard.tsx:676-677`) mean a deck template can
legitimately require a design-system pick, so fetching it unconditionally for
both families is arguably correct, not wasteful — unlike the two template
lists, which are read by exactly one family each.

## The correct pattern already exists in this codebase

`frontend/src/components/workflow/composer/DesignPickerModal.tsx:95-109`
fetches only the template family the active `designMode` needs:

```tsx
Promise.all([
  designMode === "deck" ? listPPTTemplates(token) : listPrototypeTemplates(token),
  listDesignSystems(token),
])
```

This is the same ternary-on-family shape `LaunchWizard.tsx:617-654` is
missing — confirming the omission is an oversight in one call site, not a
deliberate "load both, decide later" design. A fix at `LaunchWizard.tsx:617-654`
mirroring this exact ternary closes all four modes from the one place they
all already route through; no other caller of `listPrototypeTemplates`/
`listPPTTemplates` needs touching (`grep -rn "listPrototypeTemplates(\|listPPTTemplates("
frontend/src` — the only two callers are this effect and `DesignPickerModal.tsx`,
and the latter is already correct).

## Expected vs actual (predicted, not yet measured)

- Expected: `/create/ppt` and `/create/ppt_v2` fetch `listPPTTemplates` +
  `listDesignSystems` only; `/create/prototype_v2` fetches
  `listPrototypeTemplates` + `listDesignSystems` only.
- Actual (predicted from the shared code path): all three additionally fire
  the template-list call for the OTHER family, wasting one request and its
  payload per load — the same shape ISS-793 measured for `prototype` (a `GET
  /api/ppt/templates` load, 44.3 KB per the original BUGS.md QA-PS-045
  report).

## TEST COVERAGE — ISS-828

Manual verification only (no test suite exists for this wizard-mount fetch
path, same as ISS-793). Not yet reproduced — this card is filed INFERRED

## Resolution — [FIX-630](20260922-2115-FIX-630.md) (2026-09-22)

Fixed at the single predicted site, `LaunchWizard.tsx:617-647`, with the
`isWeb` ternary this card prescribed; `listDesignSystems` kept its
mode-independent once-per-mount effect exactly as this card argued it should.
The `ppt` leg is now proven live, not inferred:
`tests/integration/e2e/suites/03_launch_panels/test_qa_ps_045_wizard_wrong_template_family.py::test_ppt_wizard_does_not_fetch_prototype_templates`
XPASS(strict), and `frontend/src/components/workflow/LaunchWizard.iss837.test.tsx`
now fails with "Expect test to fail". `prototype_v2`/`ppt_v2` route through the
same branch and the same `STEPPER_MODE` lookup, so they are covered by
construction.
