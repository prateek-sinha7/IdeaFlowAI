# FIX-714

## What was wrong

This is bug QA-KB-048. A saved prototype or ppt workflow whose roster is shorter than the built-in's compiled plan is
opened through `/workflows/{id}/run`. On Continue, the launch draft carried the plan's full roster instead of the
saved one. The validator reproduced it 3/3 offline: a restored `["prototype-plan"]` launched all five prototype ids,
on both the cold path (library lands after the plan) and the warm path (library preloaded). The root card is
[ISS-943](20261002-0037-ISS-943.md). Its sibling [ISS-967](20261002-0320-ISS-967.md) is a second way a restored
roster lost agents: a saved custom-pool agent (AGENT.md `pipeline_type: custom`) was dropped by the restore mapping.

## Root cause (from the cards, re-checked in the working tree before editing)

- The spec-017 completion effect (`LaunchWizard.tsx:492-508` now) decided whether a roster was partial by length
  alone: `planAgents.length <= prev.length && !(planHasTree && !prevHasTree)`. Nothing recorded that the roster on
  screen came from a saved workflow, so a saved roster shorter than the plan looked exactly like ppt_v2's partial
  library roster and was replaced by `mergePlanWithLibrary(planAgents, libraryAgents)`.
- ISS-967: the restore mapped `d.agentIds` through `libraryAgents.find(...)` (`:435` now). `useAgentLibrary` builds
  `libraryAgents` without the custom pool (`useAgentLibrary.ts:33-36`), so a custom-pool id resolved to `undefined`
  and `.filter(Boolean)` dropped it without a trace.
- Blast radius, re-checked by grep: `setPipelineAgents` has 11 writers in the file and `mergePlanWithLibrary` and
  `planAgents` appear in no other component. Every consumer the card lists (`handleLaunch` `:1056`,
  `handleSaveWorkflow` `:955`, `handleSaveAsOverride` `:996`/`:997`, the Advanced count, ReviewGatesSection,
  AgentsPopup) reads `pipelineAgents`. One guard at the sink covers all of them, and no consumer was edited.

## What changed, and why there

All changes are in `frontend/src/components/workflow/LaunchWizard.tsx` (+19/-4 lines). The FIX-701 and ISS-189
hunks already uncommitted in the file were left exactly as they were.

| where (working tree) | change | card |
|---|---|---|
| `:218` | `const { libraryAgents, allAgents } = useAgentLibrary();` | ISS-967 |
| `:299-301` | `const savedRosterRef = useRef(false);` beside `agentRestorePending`, with a 2-line comment | ISS-943 |
| `:432-435` | the restore looks ids up in `allAgents.find(...)`, with a 2-line comment | ISS-967 |
| `:437-443` | after `setPipelineAgents(restored)`: `savedRosterRef.current = <restored ids> !== <defaultAgentsFor(libraryAgents, initialMode) ids>` | ISS-943 |
| `:461` | the restore effect's deps gain `allAgents` (it changes in the same render as `libraryAgents`, so no extra run) | ISS-967 |
| `:495-496` | first line of the completion updater: `if (savedRosterRef.current) return prev;` | ISS-943 |
| `:745-746` | `handleModeChange`: `savedRosterRef.current = false;` | ISS-943 |

- **One guard at the sink.** It covers the launch, both saves and every display. Because it is a ref read inside the
  functional updater, the cold path holds too. The restore effect is declared before the completion effect and
  writes the ref synchronously, and the completion updater runs at the next render. Both the cold and the warm
  card tests prove it.
- **Departure from the card's literal step 2, chosen from its own "Alternative to evaluate".** The card recommends
  `savedRosterRef.current = true` on every non-empty restore. It also warns that this stops completing a legacy
  ppt_v2 row that is exactly the 2-agent library default. I checked that offline: `presort_specs` refuses
  `["ppt-deck-qa-v2","ppt-code-generator"]` with "Agent 'ppt-deck-qa-v2' consumes 'ppt-composer' but no agent in the
  workflow produces it", which is launch_run's 422 `workflow_unsatisfiable`
  (`evidence/qa-kb-048/12-fix-presort-legacy-ppt_v2-row.txt`). Such a row can still be saved today. On a FAILED plan
  fetch, completion never runs and Save workflow stays enabled, which is FIX-701's locked constraint "Save workflow
  and Advanced need only not-loading". Before this fix that row launched the full plan, and with the bare `true` it
  would 422. So the ref is set only when the restored ids differ from `defaultAgentsFor(libraryAgents, initialMode)`.
  A restored exact copy of the library default cannot be told apart from the partial library roster spec 017
  completes, so it is still completed. Every roster that does differ is protected. This takes the alternative's one
  advantage without its hazard: the completion effect's deps are unchanged, so `mode` is not read there. The
  comparison is order-sensitive, so it exempts only a literal copy.
- **The reset on a Web/Deck toggle** is the card's step 4. The toggle re-sources the lineup from the library
  (`:744`), and the next plan must be able to complete it.
- **ISS-967 at the restore only.** `libraryAgents` still excludes the custom pool, so `defaultAgentsFor` (`:206-209`)
  and its other readers are unchanged. A custom-pool agent restored this way counts against the optional-agent
  budget, just as one added through the picker does.
- **Invariants.** There is no workflow-name branch (SC-001 / INV-1) and no backend, Python, import or migration
  change. `handleLaunch` and the `buildLaunchDraft` arguments are untouched (FIX-701). The completion write is still a
  functional updater and never reads `pipelineAgents` from the closure (FIX-338).

## Behaviour now

- A saved roster restored from the draft is what the screen shows, what Continue launches and what both saves
  persist, whether it is shorter than the plan or carries a custom-pool agent.
- A fresh open with no draft is unchanged. The ref stays false, so ppt_v2's 2-agent library roster is still
  completed to its 4-step plan (scratch guard a).
- A restore followed by a Web to Deck round trip completes the new family's library roster again (scratch guard c).

## Not fixed here (each has a card)

- [ISS-966](20261002-0320-ISS-966.md) is open and needs an owner decision. This fix makes the launch DRAFT carry the
  saved roster, but the server still decides on its own. A satisfiable strict subset is re-expanded to the full plan
  by the engine roster seam (`engine.py:5004-5007`), and an unsatisfiable one is refused with a 422 before the mint.
  So the user-visible "runs the full built-in roster" remains for satisfiable subsets until the owner picks option A,
  B or C. Its test `backend/tests/integration/agents/test_saved_subset_roster_iss966.py` stays xfailed (observed
  below). If the owner picks option B ("the plan is authoritative"), the card says ISS-943's expected value inverts
  and this fix would be reverted with it.
- [ISS-1044](20261002-1159-ISS-1044.md) is new and open. ISS-967 left one question explicitly undecided: a saved id
  that resolves to no agent at all (an agent retired since the save) is still dropped silently. With this fix the
  rest of that roster is no longer re-completed by the plan. Whether to drop it silently or tell the user is a
  product call.
