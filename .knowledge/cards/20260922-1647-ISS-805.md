INFERRED boundary/scale sibling of [ISS-785](20260922-1620-ISS-785.md) — not
independently reproduced against a family with 3+ revisions; ISS-785's own
evidence only captured a 2-member family (1 primary + 1 other member, the
"`/events` × 2" row). BUGS.md#qa-ps-038 itself labels the per-member full-log
fetch "by design for the revision transcript", so this card is the boundary
case that design choice does not cover, not a correctness defect. To confirm:
open a run with a 3+ member revision family from history and confirm
`GET /api/runs/{id}/events` count and total bytes scale with member count.

## Root cause — full event log fetched, then filtered client-side to 2 frame types, per family member

`handleSelectWorkflowRun`'s chat-transcript seeding (KAN-154 Gap 1) fetches
every OTHER revision-family member's complete durable event log in parallel:

```
page.tsx:3088   const memberFrameArrays = await Promise.allSettled(
page.tsx:3089     otherMembers.map((m: { id: string }) =>
page.tsx:3090       getRunEvents(currentToken, m.id),
page.tsx:3091     ),
page.tsx:3092   );
```

Each `getRunEvents` call returns the member's entire event log — the same
endpoint ISS-785 measured at 3,877 KB for a single large run. The result is
then filtered down to only 2 frame types before use:

```
page.tsx:3108   memberFramesByMemberId.set(
page.tsx:3109     m.id,
page.tsx:3110     result.value.filter(
page.tsx:3111       (f) => f.type === "chat_message" || f.type === "chat_reply",
                   ),
```

There is no server-side filter (no `?types=chat_message,chat_reply` or
equivalent) — the full payload crosses the network for every member, and
everything except two frame types is discarded client-side. For a 2-member
family this is the "7.7 MB total" ISS-785 already measured (its own text
calls it "by design," not a bug). For a family with N members, this same
unfiltered fetch repeats N-1 times in the same `Promise.allSettled`, so the
cost is linear in family size with no server-side mitigation — not evaluated
against any family this deep in the existing evidence.

## Expected vs actual

Expected: seeding the cross-member chat transcript costs roughly the size of
the chat frames actually shown, independent of how large each member's full
pipeline trace is.

Actual (read from code, not measured past a 2-member family): cost equals the
sum of every OTHER member's complete event log, unfiltered until after the
fetch, growing linearly with family size.
