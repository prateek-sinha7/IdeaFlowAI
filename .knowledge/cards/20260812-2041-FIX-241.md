## Description

A human-in-the-loop gate that fails OPEN: every near-miss of a DENIAL silently APPROVED (ISS-070). resolve_gate dispatched on action with else: # approve (default) as the fallback (run_commands.py:272), an exact, case-sensitive, unstripped match. Observed in-process against the real endpoint, not reasoned: 'Reject', 'REJECT', ' reject', 'reject\n', 'rejct', 'no', 'deny', 'Redo', 'redo ', 'update-specs' → all HTTP200 approved=True, gate resolved. The user believes they stopped the run; the run resumes and spends the remainder of a 5–21M-token od_prototype budget. Second, unfiled finding — the record was LAUNDERED: the else never passed action=, so store.set_review_response's own default (store.py:123) persisted action="approve" while resolve_gate:278 echoed the raw garbage back to the caller — response and durable audit row disagree, which is very likely why this never showed up in a live log. On the declared-gate path it compounds: an unknown action emits none of _gate_rejected/_gate_redo/_gate_update_specs, so human.py:104-141 resolves a formal GATE_PASS and writes an honest-looking audit row — the precise failure the in-file comment at human.py:52 says the _UPDATE_SPECS branch exists to prevent. The row's scope was OVER-GENERALISED and is corrected in place: only ONE of the three set_review_response ingresses is defective. /messages CHANNEL_GATE (:1322) is fenced by chat_router.py:234 — verified by reading BOTH Dispatch(channel=CHANNEL_GATE) construction sites (chat_router.py:244/:255), each requiring turn.action in GATE_ACTIONS; the Concierge confirm (:1101) is fenced by concierge.py:350 normalisation plus H1 (params are server-written, never client body). Those two are latent hazards, not live defects. Two layers, each independently sufficient — MUTATION-PROVED, not assumed. A (schema): GateCommand.action → Literal["approve","reject","redo","update_specs"], giving 422 at the wire and an enum in OpenAPI. The DEFAULT IS RETAINED — making the field required would break test_attach_replay_matrix.py:551's bare {"gate_key": ...} POST *and* the published contract ("default": "approve"); verified after the change that OpenAPI still reads required: ['gate_key']. B (dispatch): elif action == "approve" + an else raising 400 unknown_gate_action / recoverable: true. Mutation 1 (A reverted, B kept) → all ten variants HTTP400, nothing stored, gate armed; mutation 2 (B reverted, A kept) → all ten HTTP422, same. It REFUSES and must never degrade to a reject: FIX-232 makes a rejection terminal, so turning a typo into a denial would destroy the run — leaving the gate ARMED is the only degrade that preserves every legitimate option, mirroring the engine's own choice for an ineligible update_specs (engine.py:5830-5838). Layer C ships the same fail-closed shape at the two latent ingresses; chat_router.py is deliberately NOT touched — its :234 guard IS the ISS-119 routing contract and reconciling that is ISS-119's decision. The if/elif chain is NOT restructured — only the else branches changed — because test_rest_gate_commands.py:362 is a grep-ratchet asserting the literal source substring action == "redo"; a dict/match refactor turns it red. Retag api,auth → api,validation: verified NOT an authorization defect — resolve_gate:222 → run_engine.py:765 filters WorkflowRun.user_id == user_id, so a cross-owner caller 404s and nobody else can approve your gate; the affected principal is the run's own owner. Severity stays major: a safety gate fails open, invisibly, on the remainder of a multi-million-token budget. INV-12: chat_router.GATE_ACTIONS stays the ONE authority — Literal needs static values, so the two are pinned by a set-equality test rather than a fifth hand-written copy. Splits out ISS-127 (analysis_report has no length cap on its path to the composed prompt) rather than folding it in.

## Root cause

Nothing on the POST /gate path ever constrained what an action IS. GateCommand.action was a bare str with no enum, and the dispatch's terminal else treated "not one of the three strings I check for" as consent. Every other ingress had grown a validator in a different file (chat_router.py:59, concierge.py:80, the FE TS union at api.ts:694) — four allow-lists, none of them on this route — so the endpoint's safety depended entirely on clients volunteering to be well-behaved. The engine compounds it by keying its terminal decision on approved, not action (engine.py:5852/:5859), which makes the API layer the SOLE place that maps action → approved.
