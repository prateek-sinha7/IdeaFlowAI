# ISS-130

## Title

**`KernelServices.run_agent` mutates SHARED `ExecutionContext` scratch while N fan-out workers run concurrently.** `kernel_services.py:1254-1291` (now `:1267-1304`) sets and restores `build_task_number`, `build_task_total`, `current_task_block`, `current_prototype_skeleton` and `current_step` on the ONE per-run `ectx` — but under `run_fanout`'s parallel `asyncio.gather` those N coroutines share that single object, so the save/restore is a classic interleaving hazard: worker A's `finally` can restore values while worker B is still mid-flight. **Contamination was NOT observed** — across five instrumented runs every worker wrote its correct distinct file — and the believed reason is that `_run_agent` consumes the scratch before its first `await`, which would make the mutation atomic w.r.t. the event loop. **That was NOT verified**, and it is an undocumented, unenforced invariant: adding any `await` earlier in `_run_agent` would silently break every parallel fan-out with cross-contaminated task blocks.

## Re-check (4-test-writer, 2026-08-31)

The hazard is already closed in the current tree, upstream of this card — **not** by the
before-first-`await` argument the card asked to be proven, but by the architecturally
stronger fix: `ExecutionContext.scratch_lock` (`backend/agents/execution_engine/context.py:489`,
KRN-005) is now held for the **full** `run_agent` invocation
(`backend/agents/execution_engine/kernel_services.py:1677-1724`, `async with lock:` wraps
bind → `_run_agent` await → restore), so N fan-out children sharing one `ExecutionContext`
under `asyncio.gather` can no longer interleave their scratch bind/restore windows at all —
the atomicity no longer depends on `_run_agent` never awaiting before consuming the scratch.
Landed in commit `7a8530627` ("feat(agents): add coverage instrumentation, postgres
integration tests, and characterization golden files"), well after this card was filed.

`backend/tests/agents/test_scratch_lock_fanout_race.py` already pins exactly this invariant
from two angles — `test_concurrent_run_agent_calls_never_observe_each_others_task_block`
(no cross-worker scratch observation) and `test_scratch_lock_serializes_concurrent_bind_windows`
(mutual exclusion, `max_concurrent == 1`) — and both PASS today:

```
tests/agents/test_scratch_lock_fanout_race.py::test_concurrent_run_agent_calls_never_observe_each_others_task_block PASSED
tests/agents/test_scratch_lock_fanout_race.py::test_scratch_lock_serializes_concurrent_bind_windows PASSED
2 passed in 0.92s
```

No red state to pin a new test to — the correct-behaviour assertion the card asks for
already exists, already passes, and an `xfail(strict=True)` wrapper around it would XPASS
immediately, which is not what this phase is for. Recommend closing ISS-130 as already-fixed
(cite the existing test above) rather than writing a duplicate.

## Resolution

Verified fixed in the current code on 2026-10-01 (feat/user-stories-v2 @ 3b08b2ba8) by static review: a first-pass check and an independent adversarial re-check both found every claim of this card fixed. No tests were run for this closure.

**Fixed by:** 7a8530627 (KRN-005 scratch_lock) plus the later KRN-005 follow-up ectx_override per-worker shallow copy (commit sha not looked up)

**Evidence:** Card claims: run_agent binds/restores 5 scratch fields (build_task_number, build_task_total, current_task_block, current_prototype_skeleton, current_step) on the shared per-run ectx, so concurrent fan-out workers could interleave. Current code: kernel_services.py:1297 run_worker makes _worker_ectx = copy.copy(self._ectx) per worker and passes ectx_override=_worker_ectx (:1311). run_agent uses _ectx = ectx_override (:2022), so bind/restore (:2035-2073) hits the worker's private copy. The shared-ectx path (serial, no override) holds ectx.scratch_lock (context.py:580) via async with lock (:2030) across the whole _run_agent await. The card's lock-only fix applies only to the non-worker path.

**Left over (outside this card's claims):** No hazard remains. Notes: (1) The checker's mechanism is stale. Fan-out workers now skip the lock (_NULL_LOCK) and use private ectx copies. (2) The cited test sits at backend/tests/unit/agents/test_scratch_lock_fanout_race.py, not the card's tests/agents path. It only exercises the shared-ectx lock path, and no test pins the ectx_override isolation. (3) Card status is still "open" and should be closed.
