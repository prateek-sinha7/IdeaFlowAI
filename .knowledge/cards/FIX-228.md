## Description

"Request changes" (redo) at an agent's gate re-ran that agent with the user's instruction and WITHOUT the document the instruction was about, so the model wrote only the delta and the previous work was destroyed — the Task Planner asked to "add 2 more pages" came back with only 1 task, and every earlier task was lost. Measured live on run a0d17afa: task_list v1 → v2 = 12,542 → 3,495 chars, headings 7 → 1, 0 of 7 kept; the redo dispatch grew by exactly 106 bytes — the instruction alone. Broken for EVERY agent (no branch at the publish site; a second live run shows it at two agents; the offline repro fails for three agents across two pipelines).

## Root cause

A decision, not a mechanism. P23 modelled a re-run as a REGENERATION and minted a fresh :redo{N} checkpoint thread specifically to stop the model seeing its rejected output — then the UI shipped that action as "Request changes" with an instruction box, so users write a *delta* and the engine gives the model no subject. FIX-217 hit the identical fork on the update_specs revision path and resolved it by pairing the fresh thread with an explicit prior-artifact injection; P23 shipped only the fresh-thread half of that pair. All three other channels are closed by construction: self-consumption is structurally impossible (_filter_consumed_outputs breaks on upstream.id == spec.id), the :redo{N} thread kills checkpoint replay, and gated authoring agents declare tools: [].
