# ADR-0003: The compiled plan is the run's agent roster

## Context and Problem Statement

The engine built the roster twice, from two independently authored files:

| PLAN | MEMBERSHIP |
| --- | --- |
| `compile_for_run(pipeline_type).steps` | `get_pipeline_agents(compiled.id)` |
| `agents/workflows/<id>/workflow.yaml` | `pipeline_type:` + `order:` in each `AGENT.md` |

`agents` arrived as a parameter from the caller, sourced from the registry. The plan
was compiled separately at run entry. An assertion then required the two flattened id
lists to be identical, order included, or raised `RuntimeError`.

It was a real guard. Rename an agent folder without editing the manifest and the engine
would drive a different set of agents than the manifest describes; the assertion caught
that loudly at run start. `backend/CLAUDE.md` documents it, and
`.planning/phases/51-.../51-PATTERNS.md:117` still reads *"The membership assertion —
DO NOT BREAK"*.

It is also unsatisfiable for the workflow shape spec 012 exists to deliver. A composed
workflow's steps are instances of one template — `custom-agent:emoji`,
`custom-agent:fact`, … — and no `AGENT.md` declares them, so `get_pipeline_agents`
returns `[]`:

```
plan       = ['custom-agent:emoji', 'custom-agent:fact', 'custom-agent:joke', 'custom-agent:page']
membership = []
```

Four ids against nothing. Not drift — structurally impossible. The guard's short-circuit
excuses an empty **plan** (`if _compiled_agent_ids and …`) but never an empty
**membership**, which is exactly backwards for a template-instance workflow where empty
membership is the correct state. A user-composed workflow saved from the canvas has no
disk membership at all, ever.

So the guard did not detect a broken workflow. It made a whole category of workflow
unrunnable.

## Considered Options

1. **Special-case `custom-agent:` ids in the assertion.** Skip the check when any step
   id carries a colon.
2. **Give the template a synthetic registry entry** so membership is non-empty.
3. **Delete the second roster.** Build `agents` from `compiled.steps`; with one roster
   there is nothing left to compare.

## Decision Outcome

**Option 3.** Immediately after `compile_for_run`:

```python
if compiled.steps:
    from agents.loader import load_agent_spec
    agents = [load_agent_spec(s.agent_id) for s in compiled.steps]
```

and the assertion is removed. Two rosters that must always match is one roster too many;
the fix is to stop having two, not to teach the comparison about exceptions.

Option 1 was rejected as a permanent exception carved for one id prefix — the same class
of hardcoded-name-list reasoning SC-001 forbids. Option 2 was rejected because it
fabricates registry rows for agents that do not exist on disk, moving the lie one layer
down.

`load_agent_spec` already resolves a synthetic `<base>:<instance_id>` by loading the base
template and overlaying the full id, so no loader change was needed.

The `if compiled.steps:` guard preserves `reverse_engineer`, which compiles to an empty
step list with a legitimately empty roster.

### Why this is safe for existing pipelines

For all 14 file-backed pipelines, `[s.agent_id for s in compiled.steps]` is byte-identical
to the registry roster — the manifests were authored in registry order. The reassignment
is a literal no-op for every one of them, and the ten golden characterization tests
confirm it. Verified by script over every manifest; see
`specs/012-per-agent-skills-custom-agents/reports/plan-vs-membership-observed.md`.

## Consequences

**Positive.** Composed workflows run. One roster, so no drift is possible between the
plan and the thing the engine drives. `resume_run` and `_compute_resume_offset` get the
same plan-based source, so a resumed run cannot pick a different roster than the original.

**Negative — the drift guard is gone and nothing replaces it.** Renaming an agent folder
without editing the manifest now fails later and less clearly: `load_agent_spec` raises a
generic loader exception *after* a `WorkflowRun` row has already been minted, instead of a
named `RuntimeError` at run entry. Three consumers still read the registry roster
independently and will silently disagree with what runs — `GET /api/agents/pipelines/{type}`
(`app/api/agents.py:115`), the mint-time `agent_count` (`app/api/run_commands.py:1785`),
and the `model_overrides` allow-list (`app/api/run_engine.py:539`), whose own docstring
already warns about this (T-06-07).

**Negative — this contradicts a standing decision.** Phase 51 lists the assertion as
must-not-break, and no planning document records the reversal. This ADR is that record.
The reasoning has changed because the premise has: when Phase 51 was written, every agent
belonged to exactly one pipeline and every step had an `AGENT.md`. Template instances
break both, and the guard has no correct answer for them.

**Neutral.** `test_compiled_plan_runs.py::test_runs_from_compiled_plan` is now tautological
for 12 of 13 cases — the roster is built from `compiled.steps`, so `started == compiled_ids`
holds by construction.

## Confirmation

`tests/agents/test_manifest_coverage.py::test_all_load_compile` is the only surviving check
of plan/registry parity, and it is test-time only, not runtime.

**Required follow-up, not yet done:**

- A non-blocking runtime drift signal (log/warn, scoped to a non-empty
  `get_pipeline_agents(compiled.id)`) comparing plan against registry for file-backed
  pipelines. This restores the diagnostic without restoring the hard failure.
- Re-source `agent_count` and `GET /api/agents/pipelines/{type}` from `compile_for_run`.
- Re-scope `_validate_model_overrides`'s `run_agent_ids` to the plan roster.
- Update `backend/CLAUDE.md`, which still documents the deleted `RuntimeError` as active.
