# ISS-1183

**Register source:** sibling derived during the `QA-KB-124` analysis on 2026-10-09 (root [ISS-1156](20261009-1445-ISS-1156.md)). Not its own bug row. It is test and environment hygiene, filed because it decides whether a validate run sees the built-in or a stored copy.

**Confidence:** CONFIRMED for the rows, their origin and the absence of any cleanup (SELECTs and file reads, `evidence/qa-kb-124/analysis-06-override-rows-and-origin.txt`). INFERRED for what each of the other eight rows does at run time: only `ex_A1_loop` (fails) and `ex_A2_branch` (passes, by the reply happening to end in JSON) have a run on record.

## Condition

The e2e suite runs as the seeded `admin@velocity.ai`. `test_save_manifest_gates.py` opens `/create/<id>` for five route-declaring examples and clicks "Save as my version"; `test_save_as_my_version_discards_brief.py` and the ISS-226/279/280 probes do the same for user_stories, ppt, prototype and ppt_v2. The row it creates is enabled (`override_enabled` true), and `resolve_override` (`_workflow_override.py:47-56`) hands it to the launch of that built-in for that user from then on (`run_commands.py:3650-3690`).

Nine rows, all `admin@velocity.ai`, created 2026-10-09 07:37:12 to 07:39:17 UTC and still enabled at 17:00 CEST: My user_stories, My presentation, My prototype, My presentation + PowerPoint, My ex_A4_human_divert, My ex_A1_loop, My ex_A2_branch, My ex_A3_divert, My ex_A4_human_gate. Their `description` is the tests' brief text byte for byte ("Test brief for ex_A1_loop save"). No test deletes them, and the framework's cleanup fixture (`conftest.py:420`, `disposable_user`) is opt-in and covers accounts, not workflow rows. Its own docstring names the failure: "a test that mutates [a seeded user] poisons every later test of that role".

## Expected vs actual

Expected: a test that saves an override leaves the shared account as it found it. Actual: the account's nine most-used built-ins are shadowed. Validate and QA runs made as admin after 07:39 UTC execute the stored copies, which are lossy ([ISS-1128](20261008-2134-ISS-1128.md), [ISS-1181](20261009-1708-ISS-1181.md)).

## Why the root cause implies it

The root failure exists only because that row does. All six `ex_A1_loop` runs before 07:39:03 UTC completed (built-in plan: no delivery block, greeting pasted); all four after it that reached the `check` step failed (`analysis-02` section 1). The same hazard applies to every example the suite touched; `ex_A2_branch` happened to pass on Bedrock Haiku (run `41f50ae1`), `ex_A3_divert` and the two `ex_A4_*` have not been run from their rows.

## Fix direction (INFERRED, not applied)

- Data, the line's call and not the analyzer's: remove or disable the nine rows. `PATCH /api/user-workflows/{id}` with `{"override_enabled": false}` or `DELETE /api/user-workflows/{id}` (`user_workflows.py:1016`, `:1117`), as admin. `run_commands.py` logs `override: run launching <id> from user <uid>'s saved override <row>` for every affected launch.
- Tests: after the Save click, delete the row the response returned (a finalizer on the returned `id`), or run these tests as a `disposable_user`.
- Validate preflight: before a smoke run as admin, `SELECT id, overrides_pipeline_type FROM workflows WHERE overrides_pipeline_type IS NOT NULL AND override_enabled` should return no row for the workflow under test.
