# ISS-947

## Description

Observed while regression-testing [FIX-705](20261002-0107-FIX-705.md). The spec-016 override
round-trip suite (save an override of `ppt`, read it back, toggle it off via PATCH) does not run.

## Evidence (observed 2026-10-02, before FIX-705's edit, same tree)

`DATABASE_URL=sqlite:///:memory: backend/.venv/bin/python -m pytest tests/unit/test_workflow_override_e2e.py`
gives `7 errors`. Every test fails at fixture setup with
`tests.unit.conftest.UnitIsolationError: Unit test opened a real database connection. Move it to tests/integration/<mirror>/ ...`
(`tests/unit/conftest.py:81`): the `api` fixture builds its own `create_engine("sqlite://")`.

There is a second, hidden failure behind the first. The fixture overrides only `get_current_user`
(`:43`). `POST /api/user-workflows` has depended on `get_current_principal` since the Cognito
migration (`backend/app/api/user_workflows.py:674`), and FIX-705 moved `PATCH /{id}` onto it too
(`:951`). Once the isolation error is gone, every request would answer 401.

## Fix direction

Move the file to `tests/integration/api/` (where the hermetic SQLite fixtures live). Add
`app.dependency_overrides[get_current_principal] = lambda: (state["user"], principal_for(state["user"]))`
as `tests/integration/api/test_user_workflows_api.py:81-104` does. Test-harness change only.

## Analysis (QA-KB-088, 2026-10-07)

> Re-analysed because the ledger row was closed DUPLICATE in error: this card is the root, it is still open, and nothing has
> fixed it. Everything below was read or run at HEAD `33d55657`; the files cited are unchanged through `2254c5ef5`.
> Evidence: `evidence/qa-kb-088/04` to `10`. The diagnosis and fix direction above are correct and are now proven end to end.
> The fix is test-harness only: no application file changes.

### Root cause (CONFIRMED)

Two independent faults, stacked. The first hides the second.

1. **Placement.** `backend/tests/unit/test_workflow_override_e2e.py:34-37` builds `create_engine("sqlite://", ...)` and
   `Base.metadata.create_all(bind=engine)`. The unit suite's autouse `_unit_io_guard` (`backend/tests/unit/conftest.py:90-123`)
   listens on `Engine` `connect` and raises `UnitIsolationError` (`:81`) for every DBAPI connection, in-memory SQLite included.
   The guard's own test pins that (`backend/tests/unit/test_unit_io_guard.py:30-34`), so the guard is not the thing to change.
2. **Auth override drift.** The `api` fixture overrides only `get_current_user` (`test_workflow_override_e2e.py:43`).
   `POST /api/user-workflows` depends on `get_current_principal` (`backend/app/api/user_workflows.py:674`) and so does
   `PATCH /{id}` (`:955`). The real dependency reads `bearer_scheme`, which answers a missing header with 401
   (`backend/app/core/dependencies.py:30-57`, `:221-252`). All 7 tests call `_save_override` (a POST); one also PATCHes.

Timeline (git, this tree): the file arrived 2026-08-26 (`732adc245`, spec 016); `POST` moved to `get_current_principal`
2026-09-17 (`b2a621f84`, "Fix/cognito login (#8)"); the connect-layer guard arrived 2026-09-22 (`09270703b`, "Fix/testcases
(#9)"); `PATCH` joined on 2026-10-06 (`14a675db4`, FIX-705). So fault 2 is older than fault 1, and since 2026-09-22 the file
has errored at setup. INFERRED, not run at those commits: between 2026-09-17 and 2026-09-22 it failed with 401 instead.

There is no third fault: with both repairs the 7 tests pass against the unchanged application.

### A third hazard the fix must close: two tests pass without the feature

In V0, `test_workflow_level_fields_still_come_from_the_file` and `test_another_users_override_is_invisible` PASS while every save
is rejected with 401. Both discard `_save_override`'s result (`test_workflow_override_e2e.py:107` and `:160`) and compare
state that is identical when no override exists. A relocation that forgets the principal override would therefore report
"2 passed, 5 failed" and look half done, and a future dependency change would not turn those two red. This is why a bare
"move the file" is not a sufficient fix.

### Fix, and where it belongs

Test harness only. Nothing in `user_workflows.py`, `dependencies.py`, the guard or any router changes.

1. **Move** `backend/tests/unit/test_workflow_override_e2e.py` to `backend/tests/integration/api/`. Five files relocated for this
   same guard gained an `_api` suffix (`test_duplicate_context_guard_api.py`, `test_run_files_ref_family_scope_api.py`,
   `test_sandbox_ref_scoped_endpoints_api.py`, `test_settings_preferences_race_api.py`,
   `test_settings_api_key_whitespace_name_api.py`), so `test_workflow_override_e2e_api.py` follows precedent. No test enforces
   the suffix. The file builds its own engine and requests no Postgres fixture, so `tests/integration/conftest.py` does not get
   in the way.
2. **Add the principal override** in the `api` fixture, exactly as `tests/integration/api/test_user_workflows_api.py:88-104`:
   import `get_current_principal` from `app.core.dependencies` and `principal_for` from `tests.fakes.principal`, then
   `app.dependency_overrides[get_current_principal] = lambda: (state["user"], principal_for(state["user"]))`.
   `principal_for` (`backend/tests/fakes/principal.py:40`) derives the groups from `state["user"].tier`, and the lambda reads
   `state["user"]` lazily, so `test_another_users_override_is_invisible` still switches identity.
3. **Close the vacuous passes** (V2/V3 prove this is compatible): make `_save_override` assert `status_code == 201`; in
   `test_workflow_level_fields_still_come_from_the_file` assert `after["is_overridden"] is True` before comparing fields; in
   `test_another_users_override_is_invisible` assert the owner sees `is_overridden` before switching user.

### Invariants at risk for a naive fix

- **Reverting `POST`/`PATCH` to `get_current_user`** to make the old fixture pass would break [FIX-705](20261002-0107-FIX-705.md)'s
  locked constraint (every model id is checked with `effective_tier(user, principal)` at create, PATCH and launch) and the
  Cognito-only auth Decision 3 (tier read off the verified token, not `users.tier`).
- **`@pytest.mark.allow_io`** would make the file run in `tests/unit/`, but it is the guard's own named escape hatch for "a test
  that is not really a unit test", and it would not fix the 401.
- **Loosening `_deny_db_connect`** (for example exempting in-memory SQLite) fails `test_unit_io_guard.py:30-34` and reopens the
  hole the guard closed for about 45 files.
- The file must stay under a recognised suite folder: `tests/conftest.py::pytest_collection_modifyitems` raises
  `UsageError` for anything outside `tests/<suite>/`.

### Blast radius

- Fault 2 (missing principal override) has exactly ONE live instance. Eight routes depend on `get_current_principal`
  (`settings.py:336,361`; `run_commands.py:628,1780,3249,5538`; `user_workflows.py:674,955`). The only test file that mounts
  `app.api.user_workflows` without overriding it is this one; the five run_commands test files that override only
  `get_current_user` call `gate`, `cancel`, `answers`, `events/stream` and `user_message`, none principal-dependent
  (`evidence/qa-kb-088/10`). The other instance, `test_duplicate_context_guard_api.py`, was repaired under [ISS-905](20261001-2149-ISS-905.md).
- Fault 1 (SQLite engine in `tests/unit/`) has more instances, all reproduced one file at a time on 2026-10-07 and none tracked
  anywhere: see the siblings.
- Impact of the dead file itself: the override read-back (`GET /api/workflows/{id}` reporting `is_overridden`, `has_override`,
  `override_id`, the `?original=true` view, the listing) is exercised by no live test. The production code behind it is
  unchanged and the 7 tests pass against it once repaired, so this is a coverage hole, not a product defect.
- Stale prose noticed, not a card: the module docstring of `user_workflows.py` (line 10) still says "`Depends(get_current_user)`
  on every route", which stopped being true for POST and PATCH.
