Confirmed 3/3 from a cold start (fresh tab, direct navigation to
`/settings/profile`, cycle 3 used a brand-new browser tab — no soft
re-click). Every cycle produced the identical request pattern via
`mcp__lane2__browser_network_requests`:

- `GET /api/auth/me` — 3x
- `GET /api/settings/preferences` — 2x
- `GET /api/capabilities` — 2x
- `GET /api/workflows` — 2x (the actual workflow-catalog endpoint)
- `GET /api/runs?limit=50` — 2x
- `GET /api/runs?limit=6` — 1x

This is BUGS.md QA-PS-035. Evidence:
`evidence/qa-ps-035/01-validate-attempt1-settings-profile-loaded.png`,

## Root cause — two independent mechanisms

**Mechanism A — a naming bug makes a run-history fetch look unavoidable.**
`getWorkflows()` (`frontend/src/lib/api.ts:770-781`) does not call
`/api/workflows` despite its name — it builds `path = "/api/runs"` and
appends `limit`/`offset`/`type` query params. `RunConnectionProvider.tsx:289`
calls `getWorkflows(t, { limit: 50 })` inside `refreshLiveRuns`, which runs
on mount (`RunConnectionProvider.tsx:323-326`, `useEffect` boot). This
provider is not scoped to the run/dashboard routes — it wraps the entire app
in the root layout (`frontend/src/app/layout.tsx`, confirmed via
`grep -rln RunConnectionProvider frontend/src/app frontend/src/components`),
so every route including `/settings/*` pays for a 50-row run-history fetch
it never displays. The real `/api/workflows` catalog endpoint is fetched
separately elsewhere in the settings render tree (confirmed present 2x in
every cycle) and is equally unused on this page — matches BUGS.md's
"Problem 2".

**Mechanism B — no shared cache for auth/preferences/capabilities.**
`getMe`/`getPreferences`/`getCapabilities` (or their `/api/auth/me` equivalent)
are called independently by more than one component in the settings render
tree: `frontend/src/app/[...view]/page.tsx` (the route resolver, likely an
auth-gate check) and `frontend/src/components/settings/AccountSettings.tsx`
(the settings page itself) each hold their own call to these endpoints with
no shared provider/cache — matches BUGS.md's "Problem 1". (`grep -rln
"getMe(\|getPreferences(\|getCapabilities(" frontend/src --include=*.tsx
--include=*.ts` lists both files plus five more unrelated to this route.)

## Expected vs actual

Expected: settings page fires only `/api/me` (or `/api/auth/me`),
`/api/preferences`, `/api/capabilities` — once each. No `/api/runs`, no
`/api/workflows`.

Actual: 3x auth/me, 2x preferences, 2x capabilities, plus 2x runs?limit=50,
1x runs?limit=6, 2x workflows — all confirmed live against the running
backend on `/settings/profile`.

## Decision — 2026-09-23 (user, option a)

For **QA-PS-035** the user chose option (a) (`ESCALATIONS.md#qa-ps-035`, recorded
01:34): the app shell's one `GET /api/runs?limit=50` (AppHeader's "N Running"
badge, the SSE live-run re-attach) and one `GET /api/workflows` per page are
intended. This card's "No `/api/runs`, no `/api/workflows`" expectation (Problem 2) is superseded by that decision, and
`test_settings_profile_does_not_fetch_runs_or_workflows` now asserts at most
one of each. The waste that needed no decision — `runs?limit=6` preloaded on every
route, and a second owner of `runs?limit=50` — is removed by
[FIX-640](20260923-0207-FIX-640.md). Observed green on 2026-09-23 once the frontend was back on :3000: the
re-scoped test XPASSed (strict), its marker was removed, and a plain re-run
PASSED — `tests/integration/test-runs/2026-09-23T02-14-fix-640-qa-ps-035/`, then `2026-09-23T02-17-fix-640-qa-ps-035-plain/`.
