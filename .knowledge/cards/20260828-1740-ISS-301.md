## Reproduction

Confirmed **3/3 on 2026-08-28, cold start each cycle** (cycle 1: reload with route
interception installed; cycle 2: cleared cookies/localStorage + fresh `page.goto`; cycle 3: a
brand-new browser tab with no prior route/state):

1. Minted a real, owned handoff token via `POST /api/handoff/receive` (`X-Flowin-API-Key`),
   confirmed at `http://localhost:3000/handoff/{token}` it renders the real session ("One more
   step before this can run" / task description / repo URL) on a healthy network — proving the
   token and ownership are valid.
2. Installed a Playwright route handler aborting every `**/api/handoff/**` request
   (`route.abort('failed')`), then reloaded/re-navigated to the same real-token URL from a cold
   start each time.
3. All three cycles rendered `Handoff not found` / `Failed to fetch` / `Back to dashboard` —
   identical in shape to a genuinely nonexistent token — for a token that is real, owned, and
   unexpired the whole time.
4. Removing the route interception and reloading recovered the correct session render
   immediately, confirming the session itself was never invalid — this is a client-side
   error-handling gap only.

## Root cause

`frontend/src/components/handoff/HandoffWorkflow.tsx:73-148` (`fetchSession`) wraps the
`getHandoff` call in a single `try/catch` that sets `loadError` to `err.message` for **any**
thrown error — a real 404 from the backend and a network-layer `fetch` rejection (DNS failure,
aborted connection, backend unreachable) both land in the same `catch` block with no
discrimination.

The render branch at `HandoffWorkflow.tsx:216-233` then does:

```tsx
if (loadError || !session) {
  return (
    ...
    <h1>Handoff not found</h1>
    <p>{loadError ?? "This handoff token doesn't exist, has expired, or belongs to a different account."}</p>
    ...
```

The heading is unconditionally "Handoff not found" for *any* `loadError`, regardless of whether
the underlying failure was an HTTP 404 (token really doesn't exist) or a `TypeError: Failed to
fetch` (network never reached the server). The raw `err.message` ("Failed to fetch") is shown
verbatim as the secondary line, but nothing distinguishes the two cases to the user, and there is
no retry action — only "Back to dashboard".

## Expected vs actual

- **Expected:** a network/fetch failure (no HTTP response received) is distinguished from a
  confirmed 404 from the server — e.g. a "Couldn't reach VelocityAI — check your connection and
  retry" state with a retry action.
- **Actual:** any failed `GET /api/handoff/{token}` request, network-layer or a real 404, renders
  the identical "Handoff not found" surface, even for a token that is real, owned, and unexpired.

## Conditions

- **Page/route:** `/handoff/{token}` (`frontend/src/app/handoff/[token]/page.tsx` →
  `HandoffWorkflow.tsx`).
- **Tier:** qa-admin (enterprise) — not tier-specific; the gap is purely in error-branch logic
  before any tier-scoped rendering.
- **Trigger:** any client-side fetch failure on `GET /api/handoff/{token}` (backend unreachable,
  connection aborted, DNS failure) — reproduced deterministically via Playwright
  `route.abort('failed')` on every one of 3 cold-start cycles; not intermittent, not
  timing-dependent.
- **Entry path:** both a fresh cold navigation and a reload of an already-open handoff page
  trigger it identically once the network call fails.

## Blast radius and fix location (added by analyzer pass)

Confirmed by reading `frontend/src/lib/api-handoff.ts:61-92` (`authedJson`) — the single choke point
behind ALL EIGHT handoff API calls (`getHandoff`, `startHandoff`, `getGithubPatStatus`,
`saveGithubPat`, `deleteGithubPat`, `listApiKeys`, `createApiKey`, `revokeApiKey`): it wraps an HTTP
failure as a bare `throw new Error(message || \`HTTP ${resp.status}\`)` with no `status` field, and
does not catch the `fetch()` call itself — a network-layer rejection (e.g. a `TypeError: Failed to
fetch`) propagates unmodified. Neither case carries anything a caller could branch on.

This is exactly the class of bug `frontend/src/lib/api.ts:93-116` was already hardened against:
`ApiError` (a typed `Error` subclass carrying `status`) plus the exported `isNotFoundError(e)` helper
were built specifically because, per that file's own comment, "every `.catch()` in the app treated a
genuine 404 and a transient network/timeout blip identically" (ISS-374). `lib/api.ts`'s shared
`request()`/`fetchWithAuth()` path (`:327-370`) already throws `ApiError` for every HTTP failure and
wraps a timeout as `ApiError(0, ...)` (`:277-298`). `api-handoff.ts` has its own separate, parallel
`authedJson` implementation (needed for its own base URL / key header shape) that never adopted that
fix — it regressed back to the pre-`ApiError` behavior for the entire handoff feature's API surface.
`isNotFoundError` is already exported and used by production code elsewhere
(`frontend/src/components/workflow/IdeaInputPage.tsx`), so this is an established, reusable pattern,
not a new one to invent. Note `ApiError` itself is NOT exported from `lib/api.ts` today (only
`isNotFoundError`/`errorMessageFromDetail` are) — a fix that throws it from `api-handoff.ts` needs
that export added first.

**Where the fix belongs:** `authedJson` in `frontend/src/lib/api-handoff.ts` (`:61-92`) is the one
place all eight handoff calls already route through. Making it throw the same `ApiError`-shaped
failure `lib/api.ts` throws (status-bearing for an HTTP failure, and a wrapped/typed network-failure
case instead of letting a raw `fetch` rejection through unlabeled) is one guard, not eight — every
caller (`HandoffWorkflow.tsx`, `IntegrationsCard.tsx`) can then branch with the same
`isNotFoundError`-style check instead of each re-deriving its own heuristic on `err.message` text.
Patching only `HandoffWorkflow.tsx`'s render branch (`:216-233`) fixes the one reported symptom but
leaves every other handoff call site — see [ISS-411](20260828-2147-ISS-411.md) and
[ISS-409](20260828-2148-ISS-409.md) — exactly as broken.
