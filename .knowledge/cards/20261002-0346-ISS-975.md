# ISS-975

**INFERRED in the UI, CONFIRMED at the API.** Derived while analysing QA-KB-053 ([ISS-665](20260917-1311-ISS-665.md)). The 404 below was observed against the
live backend; that the click then does nothing is read from the code, not observed in a browser.

Line numbers are the working tree on 2026-10-02 (HEAD `024c03ef8`); `PreviewPanel.tsx`, `api.ts` and `run_files.py` carry uncommitted edits from other work, so their numbers can sit a few lines off HEAD. Real-data figures come from read-only GETs against the dev backend on :8000 (admin account), saved with their script in `evidence/qa-kb-053/`.

## Condition

A tagged older member whose deliverable sits at a different PATH in the live tree than at its own tag. Real data, backlog family
`78e185fb-c032-4154-8552-774781b6e5df` (v1-v8, declared `Backlog.pdf`): the live tree holds a ROOT `Backlog.pdf`, while the tagged trees v2-v8 do not list it and hold only `.chain/Backlog.pdf`
(force-added by the terminal snapshot, `backend/agents/execution_engine/engine.py:2404-2411` `force_add=_built_payload.allowlist`;
the engine's binary scan leaves binaries out of step commits, `engine.py:2380-2385`, the likely reason the root copy is untracked,
INFERRED). The `backlog` workflow declares the name at `backend/agents/workflows/backlog/workflow.yaml:79` (`name: Backlog.pdf`).

## Expected vs actual

Expected: Download on pinned v2 saves v2's own PDF (`.chain/Backlog.pdf` at ref v2, 23,010,668 B).

Actual: nothing visible happens. The request 404s and the error is swallowed.

## Mechanism (read, plus the API check)

- `PreviewPanel.tsx:1437` `resolveRunDeliverable(token, activeRunId, declared)` has no ref, so `api.ts:1621` lists the LIVE tree and
  `api.ts:1634` lets the ROOT candidate win outright: `deliverableFile = "Backlog.pdf"`.
- `PreviewPanel.tsx:1485-1487` ([FIX-603](20260922-1440-FIX-603.md) / [ISS-706](20260922-1035-ISS-706.md)) then reads that path AT the pinned ref:
  `getRunSandboxFileBlob(token, activeRunId, "Backlog.pdf", "v2")`. Observed: `GET /api/runs/80054fbc-71cc-42de-adeb-ae2db82eb2f2/sandbox/file?path=Backlog.pdf&ref=v2`
  returns HTTP 404 `{"detail":"File not found"}`, while `?path=.chain/Backlog.pdf&ref=v2` returns 200 (23,010,668 B) and the same path
  with no ref returns 200 (23,626,760 B, v8's). Output saved in `evidence/qa-kb-053/path-at-ref-probe.out.txt`.
- `api.ts:1685-1687` throws on a non-OK response, and the IIFE in `handleHeaderDownload` (`PreviewPanel.tsx:1473-1495`) has no
  try/catch, so the click ends in an unhandled promise rejection: no alert, the button stays enabled. `FilesTab.handleDownload`
  catches and alerts (`:745-746`).
- [FIX-603](20260922-1440-FIX-603.md) turned the old failure (wrong bytes, ISS-706) into this one (no bytes) because it made the bytes ref-aware and left the path
  resolution live. Preview twin: [ISS-677](20260917-1449-ISS-677.md) (the ref fetch at `:1459` for the same path rejects, so `refDeliverableContent` stays null and
  "Loading v2..." never ends).

## Why the root cause implies it

[ISS-665](20260917-1311-ISS-665.md): the resolver is ref-blind, so the path comes from one tree and the bytes from another. A ref-aware resolver at `:1437` would
resolve at ref v2, find `.chain/Backlog.pdf` through its `.chain/` pass (`api.ts:1635`), and the existing ref-aware read at `:1485` would
then succeed.

## Fix direction

- Pass `sandboxSelectedRef ?? undefined` at `:1437` and at the bundle listing `:1431` (a one-argument edit once [ISS-665](20260917-1311-ISS-665.md)'s resolver change
  lands; the effect already lists `sandboxSelectedRef` in its deps, `:1446`).
- Give `handleHeaderDownload` a catch with user-visible feedback, the same shape as `FilesTab.handleDownload`.
- Hazard: for a pinned member with no tag there is no ref; resolving live and reading live is today's behaviour. Decide whether that
  should disable the button instead ([ISS-697](20260922-1000-ISS-697.md)).

## What would confirm this

Pin v2 of `78e185fb-c032-4154-8552-774781b6e5df` (`/runs/78e185fb-c032-4154-8552-774781b6e5df/versions/2`), click the header Download: expect
no download and an unhandled rejection in the console (`404: could not download Backlog.pdf`). Test seam:
`PreviewPanel.refSurfaces.test.tsx` already mocks `resolveRunDeliverable` and `getRunSandboxFileBlob`; make the former return
`Backlog.pdf` for no ref and `.chain/Backlog.pdf` for `ref="v2"`, and the latter reject for a path absent at the ref.

## Resolved (2026-10-02, QA-KB-053)

Fixed by [FIX-717](20261002-1243-FIX-717.md).
- The header's resolve (`resolveRunDeliverable`) and its bundle listing now run at `displayRef`, the same ref its Download reads. At ref v2 the path found is therefore `.chain/Backlog.pdf`, not the live root `Backlog.pdf`.
- `handleHeaderDownload` gained a `.catch` that alerts "Could not download the deliverable."

Observed runs:
- `api.resolveRunDeliverableChainAtRef.test.ts` went from "1 expected fail" to "Error: Expect test to fail". The marker is left for the verifier.
- `PreviewPanel.memberRef.test.tsx` (the ISS-975 case) is green.

The tagless-member hazard is left as a decision: [ISS-1051](20261002-1242-ISS-1051.md).
