## What was wrong

`BUG-20260828-042900-handoff-invalid`: with a real, owned, unexpired handoff
token, aborting `GET /api/handoff/{token}` at the network layer rendered the
page as `Handoff not found` — identical in shape to a genuinely nonexistent
token, with the raw `Failed to fetch` shown verbatim underneath and no retry.
Reproduced 3/3 from a cold start; removing the interception recovered the real
session immediately, so the token was never invalid.

## Root cause

Two layers, one mechanism, neither carrying anything a caller could branch on.

1. `frontend/src/lib/api-handoff.ts:61-92` (`authedJson`) — the single choke
   point behind all eight handoff calls (`getHandoff`, `startHandoff`,
   `getGithubPatStatus`, `saveGithubPat`, `deleteGithubPat`, `listApiKeys`,
   `createApiKey`, `revokeApiKey`). It threw a bare
   `new Error(message || \`HTTP ${resp.status}\`)` for an HTTP failure — no
   `status` field — and did not wrap the `fetch()` call at all, so a
   network-layer rejection (`TypeError: Failed to fetch`) propagated unlabelled.
   `lib/api.ts` had already been hardened against exactly this class (`ApiError`
   + `isNotFoundError`, ISS-374); `api-handoff.ts`'s separate parallel helper
   never adopted it.
2. `frontend/src/components/handoff/HandoffWorkflow.tsx:143-145` — `fetchSession`
   collapsed every throw into one `loadError` string, and the render guard at
   `:216` was `if (loadError || !session)` under an unconditional
   `<h1>Handoff not found</h1>`.

## What changed and why there

**`frontend/src/lib/api-handoff.ts` — the guard belongs here, once.**

- `:66-86` — the `fetch()` call moves inside a `try`. A rejection is re-thrown
  as `new ApiError(0, err.message)`. `ApiError(0)` is not a new convention: it
  is what `lib/api.ts:292` already throws for an aborted/timed-out request, i.e.
  "no HTTP response was received".
- `:104` — the HTTP-failure throw becomes
  `new ApiError(resp.status, message || \`HTTP ${resp.status}\`)`. The message is
  computed by the same `errorMessageFromDetail(...)` line as before, so ISS-224's
  PAT-echo fix is untouched and every existing `err.message` reader sees the
  identical string; the error just carries `status` now.
- `ApiError` needed no new export — `lib/api.ts:648` already had
  `export { ApiError }` (the note on ISS-301 saying it did not was stale; the
  export is in HEAD, not a working-tree change).

Patching only `HandoffWorkflow.tsx`'s render branch would have left the other
seven callers exactly as broken, which is what the sibling cards predicted.

**`frontend/src/components/handoff/HandoffWorkflow.tsx` — consume it.**

- `:55-61` — `loadError` becomes `{ message, offline } | null` instead of a bare
  string.
- `:149-159` — the single shared `catch` (both `fetchSession` call sites route
  through it) sets `offline` from `err instanceof TypeError || err.status === 0`.
  The `TypeError` arm is not test scaffolding: `lib/api.ts`'s own `request()`
  path still lets a raw fetch rejection through unwrapped, so a bare `TypeError`
  is a shape this app genuinely produces.
- `:231-262` — the guard is now `if (!session)` and the heading branches:
  `Couldn't reach VelocityAI` + a `Retry` button calling `fetchSession()` when
  `offline`, otherwise the unchanged `Handoff not found` copy and message. The
  404 path is byte-identical to before.
- `:392-400` — a refresh failure over an already-loaded session renders a
  non-blocking amber notice instead of taking the page over.

The guard change and the notice are [ISS-411](20260828-2147-ISS-411.md), whose
own card asks the ISS-301 fixer to either make `!session` take priority or file
it as still open. It is the same JSX block and the same `loadError` state, so
splitting it across two passes would have meant re-editing lines written minutes
earlier. Its `verification` stays `manual`/`pending` — the code defect it names
is gone and readable in the diff, but the live reproduction its own "What would
settle it" section describes was not performed here.

**Still open, deliberately:** [ISS-409](20260828-2148-ISS-409.md) —
`IntegrationsCard.tsx:80-93`'s `refresh()` still has an EMPTY catch, so a failed
`getGithubPatStatus`/`listApiKeys` still renders as "No GitHub token saved yet."
This fix makes that error typed and branchable, but the component change is in a
file outside this card's globs and the sibling is INFERRED, never reproduced. It
stays on its own card.

Also noted, not touched, in no card: `HandoffWorkflow.tsx`'s `if (loading)`
branch still returns a full-page spinner during the post-completion re-fetch, so
the two-pane view flashes out for the duration of that request before returning.
