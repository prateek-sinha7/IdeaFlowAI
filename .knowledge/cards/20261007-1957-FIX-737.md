# FIX-737

Bug report QA-KB-080 ("ISS-098 Stop-mid-wave test dies on TypeError: fake run_fanout rejects event_queue kwarg"). The
root cause and blast radius come from the 2026-10-02 analysis on [ISS-908](20261001-2204-ISS-908.md) and its siblings
[ISS-1022](20261002-0638-ISS-1022.md), [ISS-1023](20261002-0638-ISS-1023.md) and [ISS-1024](20261002-0638-ISS-1024.md).
They were not re-derived. Every quoted line was re-read on the working tree (branch `feat/stale-bug-fixes`, HEAD `21191b09c`,
later `283089ec7`; the two commits in between touch only `LEDGER.md` and three unrelated test files) before anything was edited.
All five edited files were clean against HEAD when the fix started.

## What was wrong

One mechanism, on one seam. A hand-rolled double of a `KernelServices` method pinned the keywords of the day. The real
handle and its callers then grew a keyword. Every caller passes by keyword and receives the handle as `Any`, so nothing
flagged the drift statically.

- [ISS-908](20261001-2204-ISS-908.md) (root). `backend/tests/agents/test_wave_scheduler_cancel_row.py:40` declared
  `async def run_fanout(self, requests, ctx, *, step=None):`. `_fanout_wave_stream.py:71-73` calls
  `runner.run_fanout(requests, ctx, step=step, event_queue=child_events)`, and its only caller is `wave_scheduler.py:474`.
  The `TypeError` fires on the first `__anext__`. It is not a `CancelledError`, so it skips the
  `except asyncio.CancelledError` arm (`wave_scheduler.py:492-503`, [FIX-425](20260831-1804-FIX-425.md)) and lands in
  `except Exception` (`:504`). That arm flips the row `failed` and re-raises, and `pytest.raises(asyncio.CancelledError)` does
  not match. Result: `1 failed`. The FIX-425 arm had no running guard from merge `4ebd98e8f` (2026-09-16) until now.
- [ISS-1023](20261002-0638-ISS-1023.md) (sibling, the other half of the Stop guard set).
  `backend/tests/unit/agents/test_fanout_cancel.py:86` declared
  `async def teardown_isolated_workspace(self, base_workspace, worker_ws):`. Since `24f112706` the kernel calls
  `await teardown(base_workspace, ws, delete_branch=delete_branch)` (`fanout.py:1773`, in `_teardown_allocated`). Its
  best-effort `except Exception` (`:1776-1777`) logged
  `fan-out workspace teardown failed: _CancelRunner.teardown_isolated_workspace() got an unexpected keyword argument 'delete_branch'`
  once per workspace. The fake's `torn_down` list stayed empty, and five tests failed on their own teardown assertions:
  `5 failed, 4 passed`.
- [ISS-1024](20261002-0638-ISS-1024.md) and [ISS-1062](20261007-1927-ISS-1062.md) (prose). The `KernelServices.run_fanout`
  docstring said `event_queue` is "None for every other caller today (fanout_batch, wave_scheduler, ...)". The kernel
  `run_fanout` docstring said "None (every other caller today)". The side-channel comment said "None for every existing caller
  — dead branch, zero behavior change". And `_fanout_stream.py` said the wave merge "lives here once". All four have been false
  since `1e329e47b` made `wave_scheduler` a second caller that passes the queue. ISS-1024 traces the narrow fake in ISS-908 to
  exactly this prose.

## What changed, and why there

The defect is in the doubles, so the doubles were changed and the product was not. Both are test-only, one signature each:

- `test_wave_scheduler_cancel_row.py:40` is now `async def run_fanout(self, requests, ctx, *, step=None, event_queue=None):`.
  This is the shape of the real handle (`kernel_services.py:1161-1168`) and of the ten fakes that already complied.
- `test_fanout_cancel.py:86-88` is now `async def teardown_isolated_workspace(self, base_workspace, worker_ws, *, delete_branch=True):`,
  wrapped the way `ruff format` wraps it (the file was formatter-clean at HEAD). This is the real handle's shape
  (`kernel_services.py:919-921`) and that of the compliant fake at `tests/agents/test_cancel_paths_v3.py:385`.
  `reclaim_isolated_workspace` on the same fake still calls it positionally, and the default covers that.

The prose was corrected in place, with no behaviour change (ISS-1024 for the first three, ISS-1062 for the fourth):

- `kernel_services.py:1177-1182` now names `parallel_group` (via `_fanout_stream`) and `wave_scheduler` (via
  `_fanout_wave_stream`) as the callers that pass a queue on every fan-out. It names `fanout_batch` and the engine tool-result
  path as the ones that pass None.
- `fanout.py:354-359`: the same two callers, and the same two that pass None.
- `fanout.py:569-572`: the "dead branch, zero behavior change" line is replaced by the same statement. ISS-1062's own
  disposition was "do it whenever `fanout.py` is next edited for a real reason". ISS-1024's docstring edit three hundred lines
  above was that reason. Leaving the comment would have left the file contradicting itself.
- `_fanout_stream.py:10-12`: `parallel_group` uses this merge, and the wave scheduler keeps its own copy, with wave identity
  stamping, in `_fanout_wave_stream.py`. That matches `_fanout_wave_stream.py:10-16`.

## Not changed, on purpose

- `stream_wave_fanout` and `_teardown_allocated` keep passing their keywords (see locked constraints). The ISS-908 analysis
  rules out making the call tolerant of a narrow runner, since `KernelServices` is the only runner.
- `pytest.raises(asyncio.CancelledError)` was not loosened. Neither guard got an `xfail` marker. Each guard was its own red
  witness and had none, so the 6-verifier has no marker to remove.
- The optional tightening in ISS-908 (`runner.updated[-1][1] == "cancelled"` instead of `in ("failed", "cancelled")`) was NOT
  applied. The guard states [ISS-098](20260812-1153-ISS-098.md)'s contract (the row becomes terminal), which accepts either
  value. It was written that way by FIX-425 itself, and no code reads the difference: the scheduler only ever reads `completed`
  (`wave_scheduler.py:353`) and `running` (`:438`). The analysis marks the tightening "not required to close this card".
- The optional ISS-1023 extra, recording `delete_branch` on the fake to assert retain-on-cancel, was not added. That contract
  is already asserted against the real handle by
  `tests/agents/test_phase6_sandbox_versioning.py -k teardown_isolated_workspace_passes_delete_branch` (ISS-1023).

## Left open

- [ISS-1022](20261002-0638-ISS-1022.md) stays open, unchanged except for a disposition note. It is INFERRED, and nothing in it
  fails today. Its six narrow `run_fanout` fakes are driven only by callers that omit `event_queue` (`fanout_batch.py:127`,
  `engine.py:8656`). The test phase wrote no test for it (`verification.test_files: []`), and the card's own cheapest option
  is to do nothing until a short caller changes. The family-ending part is a bind guard over the runner handle, derived by AST
  from `kernel_services.py` the way the [FIX-231](20260812-1120-FIX-231.md) guard is derived from `engine.py`. It is a new
  test, and the six one-line widenings go with it. That remains the open work.
