## The symptom

`.knowledge/architecture/modules.json` (generated_at 2026-09-12) describes
`MOD-backend` as a ten-file module. Nine of those ten files are third-party
package internals:

```
backend/.venv312/lib/python3.12/site-packages/langsmith/env/{__init__,_git,_runtime_env}.py
backend/.venv312/lib/python3.12/site-packages/pip/_internal/operations/build/
    {__init__,build_tracker,metadata,metadata_editable,wheel,wheel_editable}.py
backend/init_db.py
```

Only the last line is VELOCITY source. `.knowledge/architecture/MOD-backend.md`,
generated by the same script, stamps `file_count: 1` and lists `init_db.py`
alone — so the generated JSON and the generated card disagree about the same
module, and the `source files covered` row in `status.py` can never reconcile
between checkouts that do or do not carry that venv.

## Root cause

`build_architecture.py:120-131` defines the filter as a set of literal
directory names:

```python
PY_EXCLUDE = {
    ".venv", "venv", "__pycache__", "node_modules", ".mypy_cache", ".pytest_cache",
    ...
    "tests", "runs",
}
```

and `:159` applies it as component membership:

```python
if PY_EXCLUDE & set(p.relative_to(REPO_ROOT).parts):
    continue
```

`.venv312` is not `.venv`. The set intersection is empty, every `.py` under it
survives the walk, and `MODULE_ROOTS` assigns them all to the `backend` root
because no deeper root claims them.

Two things that look like they should have caught this did not:

- **`.gitignore` is irrelevant.** `scan_source_files()` walks the disk with
  `rglob`, never git. The nine files are untracked (`git ls-files
  backend/.venv312` is empty) and still reached the map. `.gitignore` carries
  `venv/` and `.venv/` — the same exact-name blind spot — and the two paths
  above are ignored only by coincidence, via the unrelated `env/` and `build/`
  rules.
- **`__pycache__` masked the scale.** That entry *is* in `PY_EXCLUDE`, so the
  compiled-only remnants of the other ~130 packages under `site-packages/`
  contribute nothing.

## Why the blast radius is small today, and why that is luck

`backend/.venv312` in the main checkout is a partially-deleted venv: `find
backend/.venv312 -name '*.py'` returns exactly 9 files, exactly the 9 in
modules.json. A complete `site-packages` is tens of thousands of modules, all of
which would be assigned to `MOD-backend`, burying the real map and making every
`status.py` file-count row meaningless.

The pollution is already committed, so it survives in the knowledge base
regardless of whether that venv is ever deleted.

## Fix

Replace the venv entries' set-membership test with a prefix test — a part is a
venv if `part.startswith(".venv")` or `part == "venv"` — while leaving the
other `PY_EXCLUDE` entries (`__pycache__`, `tests`, `runs`, the caches) as exact
matches, since those names are deliberate and `tests`/`runs` must stay exact for
the reasons documented in the block comment. Then rebuild so modules.json and
`MOD-backend.md` agree again.
