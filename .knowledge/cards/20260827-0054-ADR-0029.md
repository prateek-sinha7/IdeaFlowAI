## Decision

`ppt` is named for PowerPoint and delivers HTML — nothing in it ever emits
PptxGenJS. `ppt_v2` adds a fourth step that authors that source and calls a tool
to build the file, so the WORKFLOW produces the pptx rather than a download path
trying to conjure one afterwards.

## Why the deliverable is still the HTML

`ppt` declares `strategy: ppt`, which resolves to `ctx.last_streamed` — the LAST
step's output. Adding a fourth step under that strategy would replace the deck
with JavaScript. `single_file` reads a NAMED FILE back off the run sandbox
instead, so the HTML deliverable is immune to step order, and if step 4 fails
outright the composer's presentation.html is still on disk and the run still
delivers a deck.

## Why the verifier lives inside render_pptx

A verdict delivered by a tool the agent CHOOSES to call is a verdict the agent
can argue with, and one did: handed a violation it judged spurious, it concluded
"the layout is clean and correct" and shipped a deck whose every headline printed
through its own body copy. A gate inside the build has nothing to overrule.
