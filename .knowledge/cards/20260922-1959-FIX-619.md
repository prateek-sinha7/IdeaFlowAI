# FIX-619

Resolves [ISS-757](20260922-1419-ISS-757.md) and
[ISS-771](20260922-1507-ISS-771.md), both from
[QA-SG-007](../../BUGS.md#qa-sg-007) ("changing workflow from the notification
tab sometimes fails to redirect" — validated as: the bell is empty, so there is
nothing to click).

## What was wrong

`frontend/src/components/layout/AppHeader.tsx:186` (pre-change):

```tsx
const hasServerData = recentRuns.length > 0;
const liveRuns = hasServerData ? liveRunsFromServer : null;
```

`recentRuns=[]` carries two different facts and the header could not tell them
apart: *the initial fetch has not come back yet* and *this account has no runs*.
On a full reload with a pipeline already in flight, the first is true — and the
documented fallback (`runningFromNotifs`, `AppHeader.tsx:181-183`) is empty for
the same window, structurally so per ISS-757's analysis (FIX-204 drops
`running`/`gate` entries at hydration, `useNotifications.ts:44`; SSE resume never
redelivers `pipeline_start` for a run whose cursor has moved past it). Both
sources agreed on a confidently wrong answer, and
`frontend/src/components/ui/NotificationPanel.tsx:306` stated it as fact: "No
notifications yet / Pipeline completions will appear here", while the same page's
"Jump back in" listed both runs as live (ISS-757 evidence,
`evidence/qa-sg-007/02-validate-attempt2-notif-panel-empty-despite-active-runs.png`).

The same array feeds two more render sites (ISS-771) — `AppHeader.tsx:304`
(`runningPipelines.length === 1`) and `:349` (`> 1`) — which during that window
render nothing at all.

## What changed and why there

All three affected surfaces read ONE derivation, so the signal is threaded to
that derivation once rather than patched per render site.

- **`frontend/src/app/[...view]/page.tsx`** — new `recentRunsLoaded` state
  (`:795`), flipped in a `.finally()` on the initial `getWorkflows(...)`
  (`:995-1003`). This component owns that fetch, so it is the only place that
  knows whether it is still in flight; "settled" deliberately includes the
  `.catch` path so a backend outage cannot pin the UI in a permanent loading
  state. Passed down as `recentRunsLoaded={recentRunsLoaded}` beside the existing
  `recentRuns` prop.
- **`frontend/src/components/layout/DashboardLayout.tsx`** — pass-through only
  (prop at `:113-117`, destructure `:458`, forwarded to `<AppHeader>` at `:2742`).
  `DashboardLayout` is the sole mount of `AppHeader` in the app.
- **`frontend/src/components/layout/AppHeader.tsx`** — `recentRunsLoaded` prop
  (defaults to `true`: a caller that does not fetch has nothing to wait for, which
  keeps every existing caller and test on today's behaviour). `hasServerData`
  (`:196`) now means what its name says — the fetch came back AND returned rows:
  `recentRunsLoaded && recentRuns.length > 0`. The `&&` form, not
  `recentRunsLoaded || recentRuns.length > 0`, is deliberate: the latter would
  make an empty-but-loaded `recentRuns` suppress the notification fallback, which
  is the path FIX-201 (KAN-168) relies on for a just-launched run that has not
  reached the run list yet. New `liveRunsPending` (`:237`) = no known live run and
  the server has not answered.
- **`frontend/src/components/ui/NotificationPanel.tsx`** — new `liveRunsPending`
  prop (default `false`). When the panel is empty *and* pending it renders
  "Checking for active pipelines…" with the existing `Loader2` spinner instead of
  the empty state (`:305-316`). The panel repopulates in place the moment
  `recentRuns` resolves — no close-and-reopen, which is what the reporter had to
  do.

ISS-771's badge/dropdown need no separate edit — its own card says so ("No
separate fix is expected ... shares ISS-757's fix location exactly"). They read
the now loaded-aware `runningPipelines`; a placeholder pill in the header would
fire on every single page load, including the common case where nothing is
running, so the confident-empty claim is corrected where it is actually *made*:
the bell's text.

## What is deliberately NOT changed

- The `useNotifications` fallback is still structurally unable to repopulate a
  backgrounded run after a reload. That is [ISS-680](20260917-1555-ISS-680.md)'s
  scope; ISS-757's analysis states the loading-state fix is sufficient for this
  symptom independent of it.
- Seeding `AppHeader` from `HomeLaunchGrid`'s synchronous `localStorage` cache
  (which is why "Jump back in" is unaffected) would shrink the window to zero but
  means exporting three private helpers out of a working file — ISS-757's analysis
  names it as the alternative it did not take.
- ISS-757's `BUGS.md` data-integrity note (the QA-SG-007 and QA-PS-022 section
  bodies are swapped) is untouched — `BUGS.md` is read-only for this line.
