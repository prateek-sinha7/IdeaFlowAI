## What happened

Validating BUG-20260828-085047-runs-id-stream (register: `bug-hunter/ledger.md`).
Launched a live run of the "Playwright Smoke Test" workflow (run id
`649e56cf-ce0f-4a0f-91fa-4e75a971a980`) and watched it complete in
`/runs/649e56cf-ce0f-4a0f-91fa-4e75a971a980/stream`. The run reaches
`status: "completed"`, the Preview tab fully renders the deliverable, and the
file explorer's own "Download ZIP" control works — but the toolbar's
top-level "Download the deliverable" button (`aria-label="Download the
deliverable"`) stays `[disabled]` indefinitely.

`GET /api/runs/649e56cf-ce0f-4a0f-91fa-4e75a971a980` shows why:
`deliverable_mimetype: "application/zip"` is set, but
`deliverable_filename: null`. For contrast, the seeded completed run
(`b9feac1c-ec21-4531-8ba7-bb391786993e`) has both `deliverable_mimetype:
"text/html"` and `deliverable_filename: "presentation.html"` populated, and
its toolbar Download button is enabled.

## Root cause

Per [FIX-318](20260827-0055-FIX-318.md) (`frontend/src/components/preview/PreviewPanel.tsx`),
the toolbar Download button's name comes from the workflow's own
`deliverable.name`, persisted server-side to `WorkflowRun.deliverable_filename`
on `pipeline_complete`, and the button is gated on that declared file existing
in the run's workspace listing — by design, so it can never offer bytes never
written to disk. That gate is correct, but it has no fallback when the
backend completes a run WITHOUT ever writing `deliverable_filename` (this
run's `deliverable_mimetype` was set, so the pipeline clearly emitted SOME
deliverable metadata, just not the filename): with no declared name to
resolve against the workspace listing, the button can never enable, even
though the deliverable content is fully present and independently
downloadable through the file explorer's own "Download ZIP" control. The
defect is the missing fallback/backend gap, not the FIX-318 gating logic
itself, which behaves exactly as designed given a null name.

## Reproduction (3/3, cold start every cycle)

Each cycle: fresh `page.goto('/dashboard')`, then fresh
`page.goto('/runs/649e56cf-ce0f-4a0f-91fa-4e75a971a980/stream')`, no soft
re-click. Identical result on cycles 1, 2, and 3 — deterministic, not a
race: toolbar "Download the deliverable" button always renders `[disabled]`.
Cross-checked via `GET /api/runs/649e56cf-ce0f-4a0f-91fa-4e75a971a980` on
cycle 1: `status: "completed"`, `deliverable_filename: null`,
`deliverable_mimetype: "application/zip"`.

## Expected vs actual

- **Expected:** A completed run with a fully rendered, viewable deliverable
  offers a working top-level Download button, matching the deliverable that
  is demonstrably downloadable via the file panel's "Download ZIP".
- **Actual:** The toolbar's primary "Download the deliverable" button is
  permanently disabled whenever the backend completes a run without
  populating `deliverable_filename`, with no error shown to the user and no
  fallback to the workspace's own deliverable-flagged file(s).

## Root cause — confirmed compile-time mechanism (analyzer pass, 2026-08-28)

Deepens the "Root cause" section above with WHERE the "missing fallback/backend
gap" actually is, traced file:line and CONFIRMED by direct read. Nothing above
is changed or contradicted — this only answers the "why" the validation pass
left open.

`backend/agents/workflows/compiler.py:1446-1451`
(`WorkflowCompiler._compile_deliverable`) builds
`DeliverableSpec(name=raw.get("name"), ...)` **verbatim from the manifest, with
no validation and no fallback** when a manifest declares `deliverable.strategy`
without `deliverable.name`. This is asymmetric with `mimetype`: when a manifest
omits `deliverable.mimetype`, `default_mimetype(strategy, name)`
(`backend/agents/capabilities/deliverables/_mimetype.py:49-65`) computes a
strategy-keyed default at EMISSION time (`serialized_sandbox` -> `application/zip`
— exactly why this run's `deliverable_mimetype` came back populated while
`deliverable_filename` did not). There is no equivalent per-strategy default for
`name` anywhere in the codebase.

Confirmed via a real YAML parse of every manifest (grep alone undercounts —
comment-padded `deliverable:` blocks push the `name:` key past a naive `-A`
window): of 26 `workflow.yaml` files, exactly 3 declare `deliverable.strategy`
with no `deliverable.name` — `playwright_smoke_test`, `sample_fanout`,
`sample_wave` — and `playwright_smoke_test` is the ONLY one of those three
marked `user_launchable: true`, i.e. the only one reachable through the normal
launch UI. That is exactly the manifest this bug's run
(`649e56cf-ce0f-4a0f-91fa-4e75a971a980`) launched
(`backend/agents/workflows/playwright_smoke_test/workflow.yaml:25-26`:
`deliverable: {strategy: serialized_sandbox}`, no `name:` key — the file's own
header comment calls this "THIS IS TEMPORARY", but the manifest is live and
user-launchable today).

At completion, `ectx.deliverable = compiled.deliverable` is bound once
(`backend/agents/execution_engine/engine.py:1742` / `:3628`) and never mutated
by the resolver that actually produces the bytes
(`backend/agents/capabilities/deliverables/serialized_sandbox.py:45-51`,
`SerializedSandboxResolver.resolve` returns only content, never touches
`.name`). `_deliverable_name = getattr(ectx.deliverable, "name", None)`
(`engine.py:3737`) is therefore `None`, emitted verbatim as
`"deliverable_filename": _deliverable_name` in the `pipeline_complete` payload
(`engine.py:3754`).

`backend/app/api/run_commands.py:3044-3051` is the SOLE writer of
`WorkflowRun.deliverable_filename` for the launch path, both resume entry
points, and the revision driver (per its own docstring,
`run_commands.py:2960-2976`): it reads `data.get("deliverable_filename")` and
only assigns `wr.deliverable_filename` `if deliverable_filename is not None` —
a deliberate, CORRECT guard (it is what keeps a resumed run's completion from
wiping a previously-set value), so the column is simply never written and
stays its column default `NULL` (`backend/app/models/workflow.py:79`). The
defect is entirely upstream of this guard, not in it.

**Fix location.** The compiler stays intentionally thin by design (INV-5,
`compiler.py`'s own comments), and the existing precedent for exactly this
kind of gap is `_mimetype.py`'s per-strategy default, computed at EMISSION
time, not in the compiler. The lowest-diff, most idiomatic fix is a sibling
`default_deliverable_name(strategy, ...)` next to `default_mimetype`, applied
at `engine.py:3737` (`_deliverable_name = getattr(ectx.deliverable, "name",
None) or default_deliverable_name(_effective_strategy, ...)`) — ONE place,
upstream of every consumer this analysis found (backend:
`chat_narrator.py:197`, `run_commands.py:3045`; frontend: `PreviewPanel.tsx`'s
toolbar Download gate, `frontend/src/lib/api.ts:1089` `resolveRunDeliverable`
and its callers, `RunChatLane.tsx`'s `DeliverableCard` gate — see
[ISS-434](20260828-2240-ISS-434.md)).

**A frontend-only fix would miss a caller.** `PreviewPanel.tsx`'s
toolbar-download effect (lines ~915-977, the code this card's original "Root
cause" section analyzes) duplicates `resolveRunDeliverable`'s
stem/extension sibling-preference logic INLINE instead of calling the shared
helper (`frontend/src/lib/api.ts:1089-1106`, whose own doc comment says it
exists so "the Files tab, its base-version section and the header Download
cannot answer the question differently" — `PreviewPanel.tsx` currently does
not go through it). A fix landed only inside `resolveRunDeliverable` would
repair `FilesTab.tsx` but silently leave this bug's own toolbar button broken.
The backend-side default above sidesteps this by fixing the shared upstream
field itself, once, for every consumer.

**Blast radius (every caller grepped, not just the reported one):**
- Backend: `backend/app/agents/chat_narrator.py:197` (chat milestone card —
  checked; its `deliverable:{anchor}` fallback is inert, see
  [ISS-434](20260828-2240-ISS-434.md) for why); `backend/app/api/run_commands.py:3045-3051`
  (the sole DB-column writer — guarded correctly, not itself broken);
  `backend/app/api/runs.py:110,166,344` (read-through API response fields,
  correctly pass the null through, not independently broken).
- Frontend: `PreviewPanel.tsx` (this card's own toolbar Download symptom),
  `RunChatLane.tsx` (chat lane `DeliverableCard`, see
  [ISS-434](20260828-2240-ISS-434.md)), `frontend/src/lib/api.ts:1089`
  `resolveRunDeliverable` (the shared resolver `FilesTab.tsx` calls),
  `WorkflowHistory.tsx:928` (has its own documented fallback — `undefined`
  degrades to a generic `deliverable.<ext>` name inside `FilesTab`, not gated
  all-or-nothing the way the two above are, not filed as a sibling).
