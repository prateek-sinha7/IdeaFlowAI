## Symptom

A step whose only real predecessor is expressed through `depends_on` — not
through array adjacency and not as a route target — receives no incoming edge
during layer assignment and therefore ranks at column 0, rendering back at the
start of the canvas beside `intake`.

Observed on a deliberately API-authored fixture ("EDGE 5-outcome fan + two
gates converging", `23a9ec7b-2ec0-4a98-8eaf-de816dec7d03`): `gate-b` declares
`depends_on: [custom-agent:w2]` and is a plain array successor of `gate-a`,
which branches away. `hasChainEdge` therefore correctly refuses a chain edge,
no route outcome points at `gate-b`, and it lands at column 0 next to `start`.

There is NO overlap and nothing renders incorrectly in isolation — the node is
simply in the wrong column.

## Root cause

`computeRootLayout` builds its edge set from exactly two sources: chain edges
where `hasChainEdge(i)` holds, and `trigger:"step"` route outcomes. A declared
`depends_on` is never read.

This is latent for canvas-authored workflows, where the composer keeps array
order aligned with the chain so `depends_on` and adjacency agree. It bites
workflows authored through the API or a hand-written `workflow.yaml`, where
array order is storage order and `depends_on` is the real graph — the same
class of assumption that produced [ISS-175](20260825-1115-ISS-175.md).

Note ADR-0004 already establishes that a declared `depends_on` OVERRIDES the
inferred DAG wherever the two disagree. The canvas layout does not honour that.

## Fix direction

Add declared `depends_on` as a third edge source in the phase 1/2 edge build,
normalising the composed `agent:instance` form to the node id the layout uses
(route targets are authored bare and resolved by suffix — ADR-0017 — so reuse
whatever normalisation the route-target path already applies). Treat a
`depends_on` edge exactly like a chain edge for ranking; direction handling
(backward => back-edge) is unchanged.

## Priority

Low for the product today — the composer cannot author this shape. Worth doing
before the canvas is used to VIEW workflows authored outside it, which is
already possible via `/workflows/{id}/edit` on any saved manifest.
