## What was wrong

The per-user Constitution was spliced verbatim into every governed agent's system
prompt on every run, with no length check, token budget or truncation marker
anywhere between the DB read and the composed prompt string. A user who pasted a
document into an editor that visually claims a 4000-char cap could silently
inflate every subsequent run's prompt for every agent in every pipeline — higher
token cost and context-window pressure whose cause traces back to a Settings save,
not to the pipeline that degraded. Full evidence in
[ISS-402](20260828-2121-ISS-402.md); the frontend half of the same defect is
[ISS-293](20260828-1924-ISS-293.md) / [FIX-364](20260829-0041-FIX-364.md).

## Root cause

`_inject_constitution` (`backend/agents/factory.py:673`, pre-change numbering)
returned the pre-warmed value unchanged:

- `backend/agents/factory.py:689-699` — `constitution = getattr(ctx, "prewarmed_constitution", None)`
  then straight into the f-string, no size branch.
- `backend/agents/factory.py:586` — `_compose_system_prompt` calls it
  unconditionally, so the block is assembled for every governed agent on every run.
- `backend/agents/execution_engine/engine.py:1821` — the run-entry pre-warm
  (`await get_workflow_memory().get_constitution(user.id)`) reads the full stored
  value; `WorkflowMemory.get_constitution` (`backend/agents/workflow_memory/memory.py:49`)
  truncates nothing on read, and `_set` only caps writes at 1,048,576
  (`memory.py:26,208-210`).

Nothing in that chain bounded the string, so the store's ~1 MiB ceiling was the
effective per-prompt ceiling.

## What changed and why there

**`backend/agents/factory.py`** — 27 added lines, no deletions, no new imports:

- `_CONSTITUTION_MAX_CHARS = 32_000`, a module-level constant declared directly
  above `_inject_constitution` (the file's existing style for `_GUARDRAILS_DIR`,
  `_DEFAULT_RUNTIME`, `_NO_TOOLS_PREAMBLE` — declared beside their use).
- A single size branch at the top of `_inject_constitution`, after the empty
  no-op return: over the ceiling, the body is cut to `_CONSTITUTION_MAX_CHARS`
  and a `[... Constitution truncated — N chars omitted ...]` marker is appended,
  with a `logger.warning` naming the ceiling and the omitted count so the
  inflation stops being invisible.
- Two docstring/comment lines recording that this is the one truncation point.

`_inject_constitution` is the whole blast radius, re-confirmed by grep before
editing: its only production caller is `_compose_system_prompt:586`, and
`prewarmed_constitution` is otherwise only *populated* (`engine.py:1821,4893`,
`execution_engine/context.py:190`) — nothing else composes a prompt from it. One
guard here covers every governed agent and every current and future workflow,
which is why it does not belong in any `AGENT.md` or manifest.

**Why 32,000.** It is 8x the Settings editor's 4000-char product ceiling
([FIX-364](20260829-0041-FIX-364.md)), so nothing a user can save today — nor the
over-limit values saved before that ceiling was enforced (BUG-078 reproduced 4515
and 6015 chars) — is trimmed, while a pathological paste is bounded to roughly 8k
tokens instead of the store's 1,048,576-char ceiling. This is a defensive guard,
not a third product limit: enforcing the product ceiling remains the frontend's
job.

### Deliberately NOT changed

- **The 1,048,576 store cap** (`ConstitutionRequest.content`,
  `backend/app/api/settings.py:355`; `WorkflowMemory._MAX_VALUE_LEN`,
  `backend/agents/workflow_memory/memory.py:26`) — that is the number FR-012
  specifies and [FIX-364](20260829-0041-FIX-364.md) locked as a constraint.
- **`WorkflowMemory.get_constitution`** — truncating on read would cap the value
  the Settings page displays and re-saves, silently shrinking the user's own
  content. The cap belongs at injection, not at retrieval.
- **`backend/agents/execution_engine/engine.py`** — the register lists ISS-402
  under the engine batch, but the card's own "Where the fix belongs" section puts
  it in `factory.py`, and the engine only pre-warms the value. No engine edit was
  needed, so SC-001 was never in play.
