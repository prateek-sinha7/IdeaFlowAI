## Source

Validated from register entry `BUG-20260828-081200-analytics` in `bug-hunter/ledger.md`.

## Reproduction (3/3, cold start)

Reproduced on **all 3 cycles**, each starting from a fresh navigation to `/dashboard` then a
new load of `/analytics` (no soft re-click of an already-open tab):

- Cycle 1: `page.goto('/analytics?range=all')`, baseline noted (Total Tokens 93.2M, Est. Cost
  $50.90, Total Runs 275 / 159 completed / 37 failed, Success Rate 58%), then selected
  "Prototype" via the `Filter by pipeline` combobox. URL became
  `?range=all&pipeline=prototype`; "By Pipeline Type" narrowed to the two Prototype rows
  (18 runs/$7.25 and 8 runs/$0.86); every other figure stayed byte-identical to baseline.
  `browser_network_requests` confirmed only the original `GET /api/analytics/summary?range=all`
  calls and a Next.js RSC navigation request fired — no `...&pipeline=prototype` request.
- Cycle 2: fresh `page.goto('/analytics?range=30d')`, then selected "User Stories". URL became
  `?pipeline=user_stories` (range dropped from the URL by the same interaction). "By Pipeline
  Type" narrowed to User Stories only; Total Runs tile still read 275 / 159 / 37.
- Cycle 3: fresh `page.goto('/analytics?range=all&pipeline=presentation')` — a cold **deep link**
  with the filter already applied via URL, not click-through. Total Runs tile still read 275 /
  159 / 37 even though "By Pipeline Type" rendered only Presentation. This rules out
  "interaction timing" as the trigger: the unfiltered KPI state is baked into the page's data
  flow regardless of how the `pipeline` query param is set.

## Page / route / component

- Page: Analytics.
- Route: `/analytics`.
- Component: `frontend/src/components/analytics/AnalyticsPage.tsx` — the pipeline-filter
  combobox re-filters the `by_pipeline_type` breakdown array locally but the KPI tiles, Daily
  Activity chart, Success Rate donut, and By Model panel continue reading fields from the single
  unfiltered `/api/analytics/summary` response object fetched once on mount/range-change.

## Exact conditions

qa-admin (enterprise tier), default light theme, reproduced regardless of entry path (click
selecting the filter vs cold deep-link with `?pipeline=` preset in the URL), regardless of
`range` value (`all`, `30d` both shown), and regardless of which pipeline type is selected
(Prototype, User Stories, Presentation all shown). None of these axes flip the result — the bug
is unconditional on this page.

## Expected vs actual

**Expected:** selecting a pipeline type should scope the entire page — KPI tiles, chart, success
rate, and model breakdown — to runs of that type, consistent with the already-filtered "By
Pipeline Type" list next to them.

**Actual:** only the "By Pipeline Type" list itself re-filters. Total Tokens, Est. Cost, Avg/Run,
Total Runs, the Daily Activity chart, Success Rate, and By Model all keep showing the unfiltered
all-pipelines totals (93.2M tokens / $50.90 / 275 runs / 58%), directly contradicting the
narrowed numbers shown in the list beneath them. No new `/api/analytics/summary` request with a
`pipeline` query param is ever issued.

## Root Cause (CONFIRMED)

`AnalyticsPage.tsx` fetches ONE unfiltered `AnalyticsSummary` object per date-range change and
never re-derives it for the pipeline/model filters:

- The data fetch (`frontend/src/components/analytics/AnalyticsPage.tsx:154-177`) is a `useEffect`
  whose dependency array is `[dateFilter]` only (line 177) and calls
  `getAnalyticsSummary(token, dateFilter)` (line 163) — `pipelineFilter`/`modelFilter` are never
  passed in and never trigger a re-fetch.
- `getAnalyticsSummary` (`frontend/src/lib/api.ts:789-797`) has no `pipeline`/`type` parameter at
  all — it only accepts `(token, range)` and calls
  `` `/api/analytics/summary?range=${range}` `` (line 794).
- The backend route (`backend/app/api/analytics.py:278-297`) accepts only `range: str` (line
  280); `_aggregate()` (lines 154-275) computes `kpis` (total/completed/failed/success_rate),
  `token_totals`, `spend`/`spend_full`, and `daily` as a SINGLE aggregate over every owner-scoped
  run in the date window — there is no per-`type` variant of `kpis`/`token_totals`/`daily`
  anywhere in the payload. `PipelineRollup` (lines 120-125) carries only `count`/`total_tokens`/
  `cost`/`avg_duration` per type — no completed/failed split, so a per-pipeline success rate
  cannot even be derived client-side from the current payload shape.
- Client-side derivation (`AnalyticsPage.tsx:193-242`): `kpis`, `tokenTotals`, `spend`,
  `totalTokens`, `completedCount`, `failedCount`, `totalCount`, `successRate` (line 226),
  `avgTokens`, and `dailyData` (lines 236-242) are all read straight off the unfiltered `summary`
  object — none of these expressions reference `pipelineFilter` or `modelFilter`.
- Only two derived values actually apply a filter: `pipelineRows` (lines 244-252,
  `.filter(p => pipelineFilter === "all" || normalizeType(p.type) === pipelineFilter)`) and
  `modelRows` (lines 258-267, `.filter(m => modelFilter === "all" || m.model_id === modelFilter)`)
  — each filters only against the ONE query param it owns, never the other.
- The module's own architecture card documents this as the (mis-)intended shape: "Only the date
  filter re-queries the server; pipeline/model filters narrow the already-fetched rollup arrays
  client-side" (`.knowledge/architecture/MOD-frontend-src-components-analytics.md`, `## Shape`) —
  i.e. the design never wired the filters past the two breakdown arrays to the KPI tiles, chart,
  or success-rate donut.

## Blast Radius (grepped every caller)

`getAnalyticsSummary` has exactly two call sites in the frontend
(`grep -rn "getAnalyticsSummary" frontend/src`):
- `frontend/src/components/analytics/AnalyticsPage.tsx:163` — the broken page (this bug).
- `frontend/src/components/catalog/HomeLaunchGrid.tsx:206` — calls
  `getAnalyticsSummary(token, "all")` with a hardcoded range and NO pipeline/model filter UI, so
  it cannot exhibit this symptom; not part of the blast radius.

`GET /api/analytics/summary` (`backend/app/api/analytics.py`) has exactly one router registration
and one caller path (`grep -rn "analytics/summary" backend/`) — `getAnalyticsSummary` above. No
other backend consumer of `_aggregate()` exists.

So the blast radius is contained to `AnalyticsPage.tsx`'s own derived state — but WITHIN that
component it is wider than the reported symptom: the same unfiltered-summary flaw also governs
the **model** filter (not just pipeline), and the two breakdown lists never cross-filter each
other. See the sibling cards below.

## Proposed Fix (where it belongs)

The reported symptom cannot be fully fixed client-side: `daily` has no per-type breakdown and
`PipelineRollup`/`ModelRollup` carry no completed/failed split, so a per-pipeline (or per-model)
Success Rate / Daily Activity chart cannot be derived from data the server never sends. The fix
belongs in the **same place `range` already lives** — the existing "SC-1 server recompute"
pattern (`AnalyticsPage.tsx:20-21`, `api.ts:785-787`) — extended so `pipeline`/`model` are
additional allow-listed query params on `GET /api/analytics/summary` that `_aggregate()` filters
on BEFORE rolling up (`backend/app/api/analytics.py:290-296`, alongside the existing `cutoff`
filter), with the `useEffect` at `AnalyticsPage.tsx:154-177` adding `pipelineFilter`/`modelFilter`
to its dependency array and passing them to `getAnalyticsSummary`. One change to the shared
aggregation endpoint (not one guard per derived value in the component) is what makes KPI tiles,
chart, success rate, and both breakdown lists agree — patching only `totalTokens`/`successRate`
in the component would still leave `dailyData` unfilterable (no per-type daily buckets exist) and
would still leave the model-filter and cross-filter siblings below broken.

## Resolution

Fixed by [FIX-339](20260828-2231-FIX-339.md): `GET /api/analytics/summary` gained `pipeline` /
`model` params filtered before `_aggregate()` (`backend/app/api/analytics.py:310-323`), and the
fetch effect now depends on all three filters
(`frontend/src/components/analytics/AnalyticsPage.tsx:186`). Proven by
`test_pipeline_filter_narrows_total_runs_strictly` — XPASS(strict), the pass signal, with the
xfail marker left in place for the verifier.
