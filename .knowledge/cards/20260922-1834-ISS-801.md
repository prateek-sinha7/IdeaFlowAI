# ISS-801

## Description

Root-cause completion for **QA-PS-035** (`LEDGER.md` / `BUGS.md#qa-ps-035`),
which is already reproduced 3/3 cold-start in
[ISS-781](20260922-1630-ISS-781.md): `/settings/profile` fires `GET
/api/auth/me` x3, `GET /api/settings/preferences` x2, `GET /api/capabilities`
x2. ISS-781's own Mechanism B attributed this to "more than one component...
each hold their own call... no shared provider/cache" — true for `getMe`
(two call sites), but that explanation alone cannot produce the x2 counts
for `preferences`/`capabilities`, which this repo has exactly ONE call site
for outside `AnalyticsPage.tsx`'s own separate instance (already tracked as
[ISS-782](20260922-1610-ISS-782.md)):

```
$ grep -rn "getPreferences(\|getCapabilities(" frontend/src --include="*.tsx" --include="*.ts" | grep -v "\.test\."
frontend/src/app/[...view]/page.tsx:894:    getMe(storedToken)          # getMe only, not preferences/capabilities
frontend/src/components/settings/AccountSettings.tsx:140: getPreferences(token),
frontend/src/components/settings/AccountSettings.tsx:141: getCapabilities(token).catch(() => null),
frontend/src/components/analytics/AnalyticsPage.tsx:210:    getPreferences(token)
frontend/src/components/analytics/AnalyticsPage.tsx:237:    getCapabilities(token)
```

A single call site firing twice means the effect itself re-runs — this card
identifies why.

## Root cause

`frontend/src/components/settings/AccountSettings.tsx:133-154`:

```tsx
useEffect(() => {
  const token = getToken();
  if (!token) return;
  setLoading(true);

  Promise.all([
    getMe(token),
    getPreferences(token),
    getCapabilities(token).catch(() => null),
  ])
    .then(([user, prefs, palette]) => { ... })
    .catch(() => {})
    .finally(() => setLoading(false));
}, []);
```

Empty deps, no `AbortController`, no in-flight/mounted ref, no cache check —
identical shape to the effect [ISS-794](20260922-1827-ISS-794.md) already
proved doubles under `next dev`: "`next dev` (Turbopack, confirmed via
running process) runs every effect mount -> unmount -> remount once."
Re-confirmed independently here for the primary tree:

```
$ ps aux | grep -i "next dev" | grep -v grep
bilala ... node .../VELOCITY-AI/frontend/node_modules/.bin/next dev
```

(No `-p` flag -> port 3000, the tree this bug and `BUGS.md` both target.) By
the same confirmed mechanism, `AccountSettings.tsx`'s effect mounts twice per
cold load, so `getPreferences`/`getCapabilities` (one call site each) fire
twice, and `getMe` compounds ON TOP of the doubling
[ISS-794](20260922-1827-ISS-794.md) already found for its OWN, separate call
site at `frontend/src/app/[...view]/page.tsx:894` (inside the effect
dispatching `signedIn`, which per ISS-794 also fires `fetchWorkflows`/
`fetchRecentRuns` through `frontend/src/store/listenerMiddleware.ts` on
every route, `/settings/*` included, explaining ISS-781's separately-listed
`GET /api/workflows` x2 and `GET /api/runs?limit=6` x1 — the SAME upstream
mechanism ISS-794 diagnosed for `/create/ppt`, confirmed here as a fourth
site (dashboard/ISS-784, `/create/prototype`/ISS-793, `/create/ppt`/ISS-794,
now `/settings/*`).

Two independently-doubling `getMe` call sites (page.tsx's and
AccountSettings.tsx's own) is consistent with the 3-4x range seen across
BUGS.md's original report (4x) and ISS-781's later 3/3 revalidation (3x) —
run-to-run variance matches the timing-sensitive race ISS-794 already
documented (the listener's effect reads Redux status before either thunk's
`pending` reducer commits), not a fixed deterministic count.

**Corroboration already committed in this exact file** —
`AccountSettings.tsx:589-594`, inside the separate `ConstitutionSection`
function's own mount effect:

```tsx
// ISS-581: React StrictMode double-invokes the mount effect, so the GET can
// fire twice. If the second response arrives AFTER the user has started
// typing, the unconditional setContent(loaded) overwrites their draft.
```

[ISS-581](20260829-0241-ISS-581.md) already named this exact double-fire
phenomenon for a THIRD independent effect in this same component, back in
2026-08-29 — well before the current QA-PS batch. Its fix
([FIX-421](20260831-FIX-421.md)) added a `userHasEdited` ref that guards only
against the late response overwriting a draft; it does not cancel or dedupe
the second request, so `GET /api/settings/constitution` still double-fires
today on that tab (see sibling [ISS-799](20260922-1835-ISS-799.md)).

## Expected vs actual

- Expected: `getPreferences`/`getCapabilities` each fire once per
  `/settings/*` load (single call site, no re-fire). `getMe` fires once
  (one shared, cached source), not from two independent uncoordinated call
  sites.
- Actual: `getPreferences` x2, `getCapabilities` x2 (ISS-781, 3/3 cold
  cycles), `getMe` x3-x4 (BUGS.md 4x; ISS-781 revalidation 3x) — both
  explained by AccountSettings.tsx's own unguarded effect doubling, stacked
  on page.tsx's already-confirmed doubling (ISS-794).

## Where the fix belongs

Not a per-page guard. Two shared choke points, matching the pattern this
repo already uses elsewhere (Redux Toolkit slice + status guard, as
`globalSlice.ts` already does for `workflows`/`recentRuns`):

1. `frontend/src/store/listenerMiddleware.ts`'s `signedIn` effect — close
   the race ISS-794 identified (mark status `"loading"` synchronously,
   before the async thunk starts) so a second `signedIn` in the same tick
   cannot slip past the guard. Fixes this bug's `/api/workflows` and
   `/api/runs?limit=6` waste AND ISS-784/793/794's, in one place.
2. `getMe`/`getPreferences`/`getCapabilities` — hoist into one guarded,
   cached source (e.g. a small slice + listener, mirroring
   `globalSlice.ts`/`listenerMiddleware.ts`'s own established pattern) that
   `frontend/src/app/[...view]/page.tsx`, `AccountSettings.tsx`,
   `AnalyticsPage.tsx` ([ISS-782](20260922-1610-ISS-782.md)),
   `frontend/src/app/admin/page.tsx`
   ([ISS-789](20260922-1818-ISS-789.md)) and `LaunchWizard.tsx` all read
   from, instead of each independently calling `lib/api.ts` on its own
   mount effect. No new dependency needed — this repo already has the
   Redux Toolkit + `listenerMiddleware` infrastructure this pattern needs.
