## Reproduction (3/3, cold start each cycle)

Reproduced on all 3 cycles, each from a cold start (`localStorage.clear()` +
`sessionStorage.clear()`, fresh navigation to `/login`, fresh sign-in, then a direct
navigation to `/create/prototype`):

1. Sign in as `qa-basic@flowinqa.com` / `flowin-e2e-pass` (tier: `basic`).
2. Navigate directly to `http://localhost:3000/create/prototype` (no click-through from
   `/dashboard`, whose catalog card for this deliverable IS correctly disabled/locked for this
   tier — confirmed the dashboard-side gating is fine and the gap is route-level only).
3. The full "Configure your prototype" wizard renders (`heading: Configure your prototype`),
   fully interactive — brief textarea, Attach file/Voice, template gallery — with no lock icon,
   no "Requires Pro plan" badge, and no upgrade prompt anywhere in the flow.
4. Typing a brief into the textarea (all 3 cycles) leaves the footer's "Continue" button
   `disabled: false` (verified via `document.querySelectorAll('button')` lookup each cycle) —
   a basic-tier account reaches a submit-ready wizard state for a pipeline type its own
   `/settings/usage` page says it cannot access.

No axis variation was needed — the condition reproduced identically cold-start on cycles 1, 2
and 3 with only a direct URL entry path.

## Root cause

`frontend/src/app/[...view]/page.tsx` fetches the user profile (including `tier`) at line ~832
for display purposes ("Fetch user profile (includes tier)") but never gates rendering of the
launch wizard on `can_run_pipeline`/tier entitlement — `grep -n "can_run_pipeline\|entitle\|tier"`
on the file turns up only the profile fetch and `userTier={user?.tier ?? "basic"}` passed straight
into `LaunchWizard` as a display prop, never as a gate. The dashboard catalog
(`frontend/src/components/catalog/HomeLaunchGrid.tsx` per the register's evidence) enforces the
same tier data correctly by disabling the card and showing "Requires Pro plan" — so the
entitlement data is available client-side, it is simply never consulted on the `/create/<type>`
route itself.

The backend is NOT affected: `backend/app/api/run_commands.py::_require_tier_entitlement` (calls
`can_run_pipeline`) still rejects the launch at actual run creation. This is a client-side-only
gap — a basic-tier user can invest real effort (write a brief, pick a template, click through
the wizard) before any rejection ever surfaces, contradicting what `/settings/usage` told the
same account about its own plan.

## Expected vs actual

- **Expected:** a route the dashboard already gates by tier (disabled card + "Requires Pro plan")
  should not be independently reachable and fully usable via direct URL for an unentitled tier —
  at minimum the composer should show the same locked/upgrade state the dashboard card does.
- **Actual:** `/create/prototype` performs no tier check at all: it loads and is fully
  interactive for a basic-tier account, reaching an enabled "Continue" state, with zero
  indication anywhere in the flow that the account is not entitled to this deliverable.

## Conditions established

- **Tier:** basic (`qa-basic@flowinqa.com`). Not yet re-tested against `pro` (which also lacks
  this deliverable per the entitlements table) — the mechanism (no client-side gate at all) would
  affect any under-entitled tier identically since the check is simply absent, not tier-specific.
- **Entry path:** direct URL navigation to `/create/prototype`, bypassing the (correctly gated)
  dashboard card. This is the entire mechanism of the bug — the gate exists exactly one place
  (`HomeLaunchGrid.tsx`) and nowhere else.
- **Route pattern:** likely generalizes to any tier-restricted `/create/<type>` since the gating
  gap is in the shared `[...view]/page.tsx` route handler, not something specific to `prototype`.
- **Theme/viewport:** not varied — 3/3 reproduced on the default light theme, default viewport;
  the trigger is entry path, not presentation state.
