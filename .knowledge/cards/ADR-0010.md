# ADR-0010: Skills attach to an agent, never to a run

## Status: accepted

## Context

Two mechanisms answered the question "which skills does this agent get".

**Run-level** (`attached_skills`): the user opened a "Skills & hooks" panel and
attached skills to the *workflow*. Every agent in the launch received the same
bag. It reached the model via `ctx.attached_skills`.

**Per-agent** (`Step.skills`, spec 012 / R-01): the user ticks skills on one
agent row. It reaches the model via `ctx.step_skills`.

Three separate panels wrote the run-level bag, and one of them —
`AgentCapabilitiesModal`'s "Skills" tab — was rendered *inside a single agent's
inspector drawer* while writing a workflow-wide value. Ticking a skill there
looked per-agent and behaved run-wide.

The two also collided by design. `factory.py:275`:

```python
_skills = _resolve_step_skills(ctx.step_skills) if ctx.step_skills else ctx.attached_skills
```

Per-step wins *when it is non-empty*. So attaching a skill to agent A per-step
silently discarded every run-level skill for A while leaving them applied to B.
Nothing surfaced that.

## Decision 1 — the per-agent picker is the only authoring surface

`composer/AgentSkillsPicker` is mounted by `CanvasConfigRail`, `AgentRow`, and
the agent inspector drawer. The run-level Skills section is deleted;
`SkillsHooksTab` is renamed `HooksTab`.

The drawer's **custom-skill editor** (author inline skill text, attach it to the
run) was NOT ported. `Step.skills` is a list of catalog skill *ids* and there is
nowhere to put ad-hoc `content`. Authoring a new skill is a skills-catalog
concern, not an agent-inspector one. This is a real capability removal, not a
relocation.

Mounts with nothing to write back to — the Library drawer (a catalog agent in no
pipeline) and the wizard popup (which persists via `onSelectionsChange`, a
channel with no skills field) — render the picker `readOnly`. Showing the real,
correctly-filtered list disabled is honest; live checkboxes that discard the
click are not.

## Decision 2 — hooks stay run-level

Only the skills half retires. There is no per-step hooks field in the manifest
(nothing analogous to `Step.skills`), so moving hooks would need a new compiler
surface first. `SkillsHooksProvider` keeps its name to avoid churning ~15 test
files; read it as "the run-level attachment context".

## Decision 3 — the RUN path needed a new carrier, and this is the crux

Retiring `attached_skills` broke skill delivery for composed runs, and the break
was silent. The reason is that **a saved workflow's `manifest_json` is never the
run plan**:

```mermaid
flowchart TD
    A[composer: tick a skill on agent] --> B[AgentDef.skills]
    B --> C[SAVE: buildWorkflowManifest → manifest_json.steps[].skills]
    B --> D[RUN: selections[agent].skills]
    C -. never read at run time .-> X[✗]
    D --> E[engine._apply_selections overlay]
    E --> F[Step.skills]
    F --> G[ectx.current_step.skills → ctx.step_skills]
    G --> H[factory._resolve_step_skills → stage_skills]
```

At run entry the engine compiles its own **file-backed** plan
(`compile_for_run`) and overlays the `selections` map on top. `manifest_json` is
only ever read back for reload/display. So save and run carry skills through
different channels, and only the second one reaches a model.

`skills` was not in `_synthesize_step`'s projection list and not in
`_apply_selections`'s merge list. A user could tick a skill, watch it persist,
reopen the workflow and see it still ticked — and the agent would never receive
it. Run-level `attached_skills` had been papering over this.

So `skills` is now projected in `agents/workflows/selections.py` and merged in
`engine._apply_selections`, and `ComposerPage.handleRunOnce` folds each agent's
skills into its selections entry. `skills` is a plain id list with no capability
reference, so it carries no `trust="user"` gate.

The merge is a **union** with the step's manifest-declared skills, matching
`injects`: the composer's picker may only ADD to what the workflow author
declared, never silently drop a skill the manifest requires.

## Decision 4 — unknown skill ids are dropped on the user path only

`factory._resolve_step_skills` **asserts** on an unresolvable id. Its docstring
claims the compiler validates ids at compile time; it does not — `compiler.py`
carries `skills` through verbatim.

That assert is correct for a file-backed manifest (a typo there is an author bug
worth failing loudly on). It is wrong for user-supplied ids, which go stale: a
workflow saved when skill `x` existed must not crash the run after `x` leaves
the catalog. `_apply_selections` therefore filters against the live catalog and
logs what it dropped. If the catalog itself is unreadable the ids pass through
untouched — filtering on an empty set would strip every skill, which is worse
than the crash it prevents.

## Decision 5 — the backend keeps accepting `attached_skills`

Not an oversight. Rows saved before this change still carry the column, and
`user_workflows._migrate_attached_skills_to_steps` fans those legacy values out
into per-step `skills` on first read — so a legacy workflow's skills arrive
through the manifest and show up on the agent rows. Nothing in the UI writes the
field any more. `DashboardLayout` no longer hydrates it either, for the same
reason: there is no run-level surface left to hydrate into.

## Consequences

**Positive.** One surface, one scope, one word. The per-agent path is now
exercised by every composed run rather than being the rarely-hit branch of the
`factory.py:275` ternary.

**Negative — and this is the accepted cost.** Runs with no per-agent UI can no
longer attach skills at all: revisions (`ppt_revision`, `prototype_revision`,
…), chained runs, and wizard launches. A revision is dispatched from a button
with no canvas. Previously these inherited whatever the run-level panel held.
Giving them skills again needs a per-agent surface on those paths.

Inline custom-skill authoring is gone (Decision 1).

**Neutral.** The `attached_skills` column, its migration, and the engine's
`ctx.attached_skills` fallback all remain live for legacy rows and API clients.

## Confirmation

`tests/agents/test_composer_skills_delivery.py` pins the run-path chain link by
link — projection, trust=user compile, overlay, union semantics, unknown-id
drop, empty-selections parity, Path B (an agent absent from the base manifest),
and final resolution to a payload with non-empty content. A broken link produces
a run that *succeeds while ignoring the user's skill*, which no other test
catches.

Frontend: `tsc --noEmit` clean, and a full-suite diff against clean HEAD shows
**284 failing tests before and after, with an identical failure set** — no
regression. (That pre-existing 284 is a broken test harness — ~43 files render
Redux-connected components with no `<Provider>` — not product breakage. Out of
scope here.)

Backend: 98 passed across the skills/user-workflow/staging suites; the 15
failures in the broad run all reproduce at clean HEAD.
