## What is suspected

[ISS-245](20260828-1631-ISS-245.md) established the mechanism: a control gated only by
`disabled={<reactState>}`, where the handler sets that state via `setX(true)` (a React state
update, not a synchronous DOM mutation) with no `useRef` lock, leaves a pre-commit window in
which rapid repeated clicks each independently invoke the handler. The Account Settings
"Security" panel's email-MFA on/off toggle has the identical shape:

```
frontend/src/components/settings/SecuritySection.tsx:316-320 (excerpt)
                onClick={() => onToggleEmail(!emailOn)}
                disabled={pending}
                ...
                {pending ? "Saving…" : emailOn ? "Turn off" : "Turn on"}
```

```
frontend/src/components/settings/SecuritySection.tsx:112-119,122,145 (excerpt)
  const toggleEmailMfa = useCallback(
    async (enable: boolean) => {
      ...
      setPending(true);
      setNotice(null);
      try {
        const result = enable ? await enableEmailMfa(token) : await disableEmailMfa(token);
        ...
      } finally {
        setPending(false);
      }
```

`setPending(true)` is a React state update with no accompanying ref-based synchronous lock, and
`onToggleEmail` reads the CURRENT `emailOn` value at click time (`!emailOn`) to decide which
request to send — so two clicks landing in the pre-commit window do not just duplicate one
request, they can each capture the SAME pre-toggle `emailOn` value and send the SAME direction
twice, or (if a state update from click 1 is visible to click 2's closure before commit) opposite
directions, racing two concurrent `enableEmailMfa`/`disableEmailMfa` calls against each other.

## Condition

On Account Settings → Security, with the email MFA factor in a known state (on or off), click the
"Turn on"/"Turn off" toggle synchronously multiple times before the first request resolves — same
reproduction shape as ISS-245 (`btn.click(); btn.click();` in one JS task).

## Expected vs actual

- **Expected:** the toggle disables itself the instant the first click starts the request, so a
  second click before the response arrives is ignored and exactly one
  `enable`/`disableEmailMfa` request is sent per interaction.
- **Actual (predicted):** two concurrent MFA-factor-change requests fire from one interaction.
  Because `setState` in the `.then`-style success handler (`SecuritySection.tsx:126-137`)
  unconditionally applies whichever response resolves last — not necessarily the one from the
  later-clicked (intended-final) request — the panel's displayed `enabled`/`factors` state can end
  up reflecting the FIRST request's outcome rather than the second, i.e. the UI can show MFA as
  off when the account's real last-requested state was on, or vice versa. This is security-state
  UI accuracy, not just an inert duplicate as in ISS-245's login case.

## Why the root cause implies this

Independently-implemented but structurally identical to `handleSubmit`/ISS-245: a local
`useState` pending flag, set synchronously-in-JS-but-not-synchronously-in-the-DOM at the top of an
async handler, with the toggle's only gate being that state's React-rendered `disabled` prop and no
ref-based mutex. The extra out-of-order-response risk here (beyond plain duplication) follows from
`toggleEmailMfa` also being the site that both fires the request AND applies its result to display
state with no request-identity/sequence check — whichever of the two in-flight requests resolves
last wins, regardless of click order.

**Marked INFERRED**: no double-click has actually been performed against this toggle; only the
code shape (button, handler, state-assignment ordering, and the unconditional last-response-wins
`setState`) has been read and confirmed. What would confirm it: perform ISS-245's synchronous
double-click on the toggle, then `GET` the account's MFA status server-side and diff it against
what the panel displays.
