## Description

**INFERRED — derived from ISS-188's root cause, not yet reproduced in the browser.**

ISS-188 (root, `BUG-20260827-234030-create`) proved that `HomeLaunchGrid`'s own
`sessionStorage` cache is not scoped per user. Reading the code one layer up shows the
exact same shape of defect — no per-user scoping, no invalidation on account switch — in
the Redux preload path that `HomeLaunchGrid` also reads from (`reduxRecentRuns`,
`allWorkflows`):

- `frontend/src/store/slices/authSlice.ts:24-28` — the `signedIn` reducer sets
  `state.token`/`state.user` unconditionally from the action payload. It never compares
  the incoming token/user against the previous one, so a second `signedIn` for a
  *different* account is indistinguishable, at the reducer level, from a remount of the
  *same* account.
- `frontend/src/store/listenerMiddleware.ts:17-47` — the `signedIn` listener that
  preloads `fetchWorkflows`/`fetchRecentRuns` (and, identically, `fetchAgentLibrary`/
  `fetchSkills`/`fetchHooks`) guards each fetch on `state.global.workflowsStatus`/
  `recentRunsStatus` (and the sibling slices' own status) being *not already*
  `"loading"`/`"succeeded"` — "guarded so remounts within the same session don't
  refetch" (line 16's own comment). That guard has no concept of *which user* the
  `"succeeded"` status belongs to.
- `frontend/src/store/listenerMiddleware.ts:49-57` — the ONLY code path that resets this
  state (`globalCleared()`, plus `agentsCleared`/`skillsCleared`/`hooksCleared`) is the
  `signedOut` listener.
- The only two app-code sites that actually change the token are:
  - `frontend/src/app/[...view]/page.tsx:3140-3144` (`handleLogout`) — explicitly
    `dispatch(signedOut())` **before** navigating, so this path is safe.
  - `frontend/src/lib/api.ts:144-149` (`handleSessionExpiry`) — clears the token and
    does `window.location.href = routes.login(...)`, a **hard** navigation that
    restarts the JS runtime and resets Redux to `initialState` incidentally (not by
    design — nothing here dispatches `signedOut()` either).
  - `frontend/src/app/[...view]/page.tsx:806-817` — the mount-time auth-check effect
    dispatches `signedIn` **unconditionally on every mount**, and separately, when
    `getToken()` returns falsy, does `router.replace(buildLoginRedirect())` — a **soft**
    (client-side) navigation, with no `signedOut()` dispatch anywhere on this branch.

So: whenever the stored token disappears or changes through anything other than
`handleLogout` or `handleSessionExpiry`'s hard reload — e.g. the exact
"corrupt-token/expiry recovery path" ISS-188's own repro simulated by hand
(`localStorage.removeItem('auth_token')` without a full reload) — the Redux store is
never cleared, `workflowsStatus`/`recentRunsStatus` (and the Library preload statuses)
remain `"succeeded"` from the FIRST account, and the next `signedIn` dispatch (now
carrying the SECOND account's token) causes `listenerMiddleware` to skip
`fetchRecentRuns()`/`fetchWorkflows()` entirely. `HomeLaunchGrid` would then read the
first account's `reduxRecentRuns`/`allWorkflows` directly — the identical leak ISS-188
proved via `sessionStorage`, now via the store itself, and broader (the whole workflow
catalog, plus whatever Library's agents/skills/hooks preload exposes) rather than just
the six most-recent runs.

## Why this is implied by the root cause (not imagined)

ISS-188's mechanism is "no per-user scope + no invalidation-on-switch" in ONE cache
(`sessionStorage`, `HomeLaunchGrid.tsx`). The same two missing properties are visible by
inspection in the OTHER cache `HomeLaunchGrid` reads from (Redux, `state.global`) one
layer up — this is the "other caller with the same flaw" case, not a different bug
class.

## Expected

Signing in as a second account in the same tab, after the first account's token was
cleared by any path other than an explicit log-out, should show ONLY the second
account's own recent runs/workflow catalog — Redux should refetch rather than silently
reuse the previous account's already-`"succeeded"` state.

## Actual (predicted — unreproduced)

`recentRunsStatus`/`workflowsStatus` staying `"succeeded"` across the swap causes
`listenerMiddleware`'s `signedIn` listener to skip the refetch, so `state.global.recentRuns`/
`workflows` keep serving the first account's data to the second account until an explicit
log-out or a hard page reload happens to occur.

## What would settle it

Reproduce ISS-188's steps 1-3 (sign in as qa-admin, clear only `localStorage.auth_token`,
sign in as qa-basic) **without navigating via a hard reload/`page.goto` between steps 2
and 3** (e.g. drive the login form via in-app client-side navigation throughout, the way
a real user clicking around would, rather than a fresh `page.goto('/login')`), then
inspect the Redux DevTools state (`state.global.recentRunsStatus`,
`state.global.recentRuns`) immediately after the qa-basic sign-in resolves, before any
manual reload.

## Root cause pointer

`frontend/src/store/listenerMiddleware.ts:17-47` (fetch guard keyed on status, not user
identity) + `frontend/src/store/slices/authSlice.ts:24-28` (`signedIn` sets state with no
prior-token comparison) + `frontend/src/app/[...view]/page.tsx:806-817` (unconditional
`signedIn` dispatch on every mount, no `signedOut()` on the token-missing branch).
