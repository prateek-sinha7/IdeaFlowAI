## What was wrong

Resolves [ISS-227](20260828-1554-ISS-227.md) and [ISS-281](20260828-1902-ISS-281.md).

`/workflow/create?mode=../admin` (and its percent-encoded twin
`?mode=%2e%2e%2fadmin`) redirected straight into the live `/admin` console —
an entry point whose only job is to pick a workflow-creation mode could
navigate anywhere in the app. Observed on the running dev server before the
change:

```
$ curl -sD - "http://localhost:3000/workflow/create?mode=../admin" -o /dev/null
HTTP/1.1 307 Temporary Redirect
location: /admin
```

[ISS-281](20260828-1902-ISS-281.md) is the same mechanism seen from the
authorization side: the proxy is edge middleware that redirects on an
unauthenticated read of a query string, so whatever gating exists is only
whatever the *destination* happens to do internally. `/admin`'s own gate
(`frontend/src/app/admin/page.tsx:170`,
`if (!user.is_admin) { router.replace(routes.dashboard()); return; }`) is
client-side and post-mount, so a qa-basic session's main frame genuinely
visited `/admin` before being bounced — `/admin` -> `/admin` -> `/dashboard`
in the `framenavigated` log the test-writer recorded.

## Root cause

`frontend/src/proxy.ts:10` built the redirect target by raw string
interpolation of the unsanitized `mode` query param:

```ts
return NextResponse.redirect(new URL(`/create/${mode}`, request.url));
```

`new URL()` performs RFC-3986 dot-segment normalization on the path it is
given, so `/create/../admin` collapses to `/admin` before the 307 is even
written. Nothing else in the file validates `mode`; the sibling client
component `frontend/src/app/workflow/create/page.tsx`'s `CreateRoute()`
allowlists (`raw === "ppt" || raw === "ppt_v2"`, else `prototype`), but that
code never runs — the middleware intercepts `/workflow/create` first.

Blast radius re-checked before editing, and it still holds: `proxy.ts:10` is
the only `new URL(` / `NextResponse.redirect` site in `frontend/src` fed by
untrusted data (`grep -rn "NextResponse.redirect\|new URL(" frontend/src` —
the other three hits are `CustomTemplateModal.tsx`'s hostname display and
`api.ts`'s path parse). All four in-app callers of
`routes.workflowCreateLegacy` (`CreationHub.tsx:31,35`,
`DashboardLayout.tsx:1547,1574`) pass the literals `"ppt"`/`"prototype"`, so
the exploit path is exclusively a crafted URL hitting the middleware.

## What changed and why there

**`frontend/src/proxy.ts`** — one expression: `mode` is encoded as a single
path segment before interpolation.

```ts
new URL(`/create/${encodeURIComponent(mode)}`, request.url)
```

Fixed at the interpolation, because that single site is where every caller
routes through — the middleware is the only thing that ever builds this
redirect, and there is no in-app caller to guard instead. `encodeURIComponent`
neutralizes `/` (and `\`, and a `//host` open-redirect prefix), so no
dot-segment survives for `new URL()` to resolve; percent-encoded input is
already decoded by `searchParams.get`, so both spellings land on the same
encoded target. This mirrors the two places in the app that already got this
right — `DashboardLayout.createRouteForType` (`/create/${encodeURIComponent(type)}`)
and `routes.workflowCanvas` — rather than inventing a third pattern.

An allowlist was NOT used, and no shared "known modes" helper was added to
`routes.ts`, even though [ISS-227](20260828-1554-ISS-227.md) floats it as the
more defensive option. Two reasons: the destination `/create/{type}` namespace
is deliberately open-ended — `parseViewPath` resolves any unknown segment to
`{ screen: 'create-workflow', pipelineType }` precisely so a catalog workflow
needs no route edit (SC-001) — so there is no closed set to check against; and
`frontend/src/lib/routes.ts` already carries another agent's uncommitted edits
in this working tree, making it a file-collision risk for a change that buys
nothing here. Recorded as still-open architectural debt below, not silently
dropped.

## Observed, NOT fixed, NOT mine

- `/create/..%2Fadmin` renders the same dead-end unknown-mode screen any
  unrecognised mode reaches. That is the already-filed
  `BUG-20260828-001720-workflow-create-prototype` (an unrecognised mode is
  treated as a workflow slug), unchanged by this fix and out of its scope.
- ADR-0018's "routes.ts is the single source for building every URL" is still
  violated by `proxy.ts` hand-building `/create/{mode}` and by
  `DashboardLayout.createRouteForType` doing the same — the traversal is
  closed, the architectural duplication is not. Neither file's mode set is a
  closed enumeration, so consolidating them is a design change, not a fix.
