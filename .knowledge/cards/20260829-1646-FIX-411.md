## What was wrong

`BUG-20260829-135100-runs-id-versions` (`bug-hunter/ledger.md`): cold-loading
`/runs/{root}/versions/1/steps` and `/runs/{root}/versions/2/steps` rendered
byte-identical Steps content ("Run complete · 5 / 5 agents · 1m 32s", the same
five agent rows) although the version-picker header read the correct version on
both loads and the pinned run's record was confirmed fetched over the wire.
Ground truth: root `77f74563-…` = 5 agents / 3164.1s / 8.57M tokens, revision
`ef86e750-…` = 2 agents / 371s / 2.39M tokens.

[FIX-334](20260828-2149-FIX-334.md) had already made the deliverable CONTENT
version-aware. This is the sibling gap it left: the pipeline DATA was never
given the same treatment.

## Root cause

`frontend/src/components/preview/PreviewPanel.tsx` — the version-pin override
kept only the fetched run's `.output`:
`setViewingVersion({ id, content: run.output })` at the Version-menu fetch
(`:586`) and the URL-pin effect (`:625`). From that one field it computed
`effUserStoryContent`/`effPptContent`/`effPrototypeContent` (`:656-658`) and
nothing else, so every surface fed by `agents` / `pipelineState` /
`agentOutputs` kept reading the raw props destructured at `:512` — the
live/root run, whatever the URL pinned:

- `:1422-1429` `<AgentThinkingTab agents={agents || []} pipelineState={pipelineState}>`
  — the Steps tab. `StepsOverviewSpine.tsx:340,367,383` derives the
  "N / N agents · duration" summary and the whole agent list from exactly
  these two ([ISS-606](20260829-1412-ISS-606.md)).
- `:1394` `<FilesTab … agentOutputs={agentOutputs}>` — the "Agent outputs"
  markdown list, on the same JSX line whose content props FIX-334 had already
  switched to `eff*` ([ISS-606](20260829-1412-ISS-606.md)).
- `:1466` `<AuditTab workflowRunId={pipelineState?.pipelineRunId}>` — worse
  than stale: `AuditTab.tsx:464-478` keys four of its OWN fetches
  (`gate-events`, `validation-results`, `exec-runs`, `hook-runs`) on this id,
  so a pinned Audit tab actively fetched the wrong run
  ([ISS-609](20260829-1420-ISS-609.md)).
- `:1085`, `:1160`, `:1186` `agentOutputs={agentOutputs}` on
  `AppBuilderIDEPreview` / `GenericDeliverablePreview`, and `:773-776`
  `agentNameById = {…, ...buildAgentNameById(pipelineState?.agents)}` consumed
  at `SandboxTab.tsx:1047` — the two surfaces whose PRIMARY content/runId was
  already pin-aware but whose secondary lookups were not
  ([ISS-608](20260829-1421-ISS-608.md)).

Blast radius re-checked before editing: `<PreviewPanel` still has exactly one
mount (`DashboardLayout.tsx:3127`), and all six call sites above are still at
the line numbers the cards recorded. `workspaceRunId` (`:753`) and
`activeRunId` (`:551`) were already pin-aware and are untouched.

## What changed and why there

**`frontend/src/components/preview/PreviewPanel.tsx` — one new projection, six
rewired props.** `versionViewFrom(run: WorkflowRun): VersionView` (module-level,
next to the other file-local helpers) turns the ALREADY-FETCHED pinned run
record into the three shapes the pipeline surfaces consume — `agents`
(`AgentRunState[]`), `pipelineState` (`PipelineRunState`) and `agentOutputs`
(`AgentOutputItem[]`) — alongside the `content` the override already carried.
Both fetch sites now store `versionViewFrom(run)`, and
`effAgents`/`effPipelineState`/`effAgentOutputs` sit directly under
`effPrototypeContent` with the same `?? raw prop` fallback, so an un-pinned
run is byte-identical to before.

Fixed at the PreviewPanel mount, not inside the child tabs, for the reason
FIX-334 recorded and its `locked_constraint` states: the override is state
PreviewPanel alone owns, and the six consumers are already reading from it for
content. One projection cures all three cards; guarding each child tab would
have been four diffs and a fourth copy of the version rules.

Two details worth keeping:

- **Rows are collapsed to the LAST one per `agent_id`.** A persisted
  `agent_outputs` row is one agent RUN, so a task-loop agent repeats — this
  family's root run has 17 rows for `agent_count: 5`. Last-row-per-id in
  first-appearance order is exactly what the live reducer holds after a durable
  replay, and it restores the run's own agent count (5 for v1, 2 for v2).
- **No per-agent status is invented.** A persisted row means a completed
  output, so rows map to `status: "done"`; run-level failure comes from the
  server's own `run.status === "failed"` on the synthesised `pipelineState`,
  never a client `empty == failed` guess (the ISS-017 rule).

`pipelineRunId` on the synthesised state is the pinned run's id, which is what
carries [ISS-609](20260829-1420-ISS-609.md): `AuditTab` reads
`effPipelineState?.pipelineRunId` and so fetches the pinned run's audit rows,
while an un-pinned run still gets `pipelineState.pipelineRunId` — the live id
that is available from the first frame (the same reason `workspaceRunId`
prefers it over `activeRunId`).

No new fetch, no new prop threaded through DashboardLayout, no backend change,
and no edit to any child tab.
