# ISS-772

## Description

INFERRED sibling of [ISS-730](20260922-1343-ISS-730.md) (bug QA-PS-028's root card) — not
reproduced live. Filed because the root cause implies it, not because it was observed.

ISS-730 traces QA-PS-028 to `backend/agents/prompts/backlog-compiler/AGENT.md`: a final step
told to `read_file` N upstream `.agents/*.md` files and "Include ALL epics and stories" with
no structural requirement to enumerate or account for every item it read. Three other agents
share the identical shape — same "Sandbox Reading Guide" phrasing, same final-step role, same
absence of a structural checklist — confirmed by reading all three `AGENT.md` files in full:

| Agent | Pipeline | Step | Upstream sources |
|---|---|---|---|
| `app-sdlc-governance` | `app_builder` | 15/15 (final) | 6 (`material-analyzer`, `app-system-design`, `app-security-architecture`, `app-code-compliance`, `app-devops`, `app-test-compliance`) |
| `dotnet-sdlc-governance` | `dotnet_to_azure` | 13/13 (final) | 5 (`dotnet-security-architecture`, `dotnet-azure-bicep`, `dotnet-code-compliance`, `dotnet-test-compliance`, `dotnet-validation`) |
| `mulesoft-sdlc-governance` | `mulesoft_to_springboot` | 13/13 (final) | 12 files listed in its own Sandbox Reading Guide (`.agents/01-mulesoft-inventory.md` … `.agents/12-mulesoft-validation.md`) |

All three declare `tools: []` in their own `AGENT.md` frontmatter (text-only, per the schema
default) but their workflow step declares no `tools:` override either — confirmed by reading
`backend/agents/workflows/app_builder/workflow.yaml:81-83`,
`backend/agents/workflows/dotnet_to_azure/workflow.yaml:64-66`,
`backend/agents/workflows/mulesoft_to_springboot/workflow.yaml:65-67` — which compiles to the
`ToolPermissions()` default (`read_files: bool = True`, confirmed directly at
`backend/agents/workflows/plan.py:65`; also already established by
[ISS-732](20260922-1352-ISS-732.md)). So, like `backlog-compiler`, all three genuinely have
`read_file` access to every listed source; nothing blocks them from reading everything, and
nothing checks whether they did.

Each is prompted with the same soft completeness language — `dotnet-sdlc-governance`: "Use
`read_file` to load the prior agents' outputs before compiling the governance and handover
artefacts"; `mulesoft-sdlc-governance`: "Reading is your own responsibility — the engine does
not inject these for you" (the exact phrase `backlog-compiler`'s own `AGENT.md` uses);
`app-sdlc-governance`: "Read the files above before writing anything," one line of an "OUTPUT
CONTRACT" that is otherwise about tool-call-syntax hygiene, not completeness. None of the
three requires the agent to enumerate what it read against what it wrote, and — per
[ISS-730](20260922-1343-ISS-730.md)'s own confirmed engine-side finding — nothing in
`_execute_impl`'s completion gate (`engine.py:7376-7457`) would catch a governance document
that quietly omits, say, the security-architecture agent's threat model while still reading as
a complete, well-formed handover package.

## Why the root cause implies this

The mechanism ISS-730 confirms is not `backlog-compiler`-specific: an LLM given N files to
read manually and a prose "cover it all" instruction, with no engine-side diff against what it
actually produced, is exposed to the same content-window/attention trade-off regardless of
which pipeline or how many files. The three agents above share the SAME shape (final step,
highest fan-in of any step in their own pipeline, `tools: []`/default `read_files=True`, one
soft completeness line) as the one already-confirmed instance.

## What would confirm or refute this

Not reproduced — this card is the hypothesis, not the observation. To settle it: run
`app_builder`/`dotnet_to_azure`/`mulesoft_to_springboot` to completion enough times to catch a
case where one of these three steps' `input_tokens` is markedly lower than its upstream
siblings (the same advance signal [ISS-730](20260922-1343-ISS-730.md) used for
`backlog-compiler`), then diff its output against the upstream agent it under-read for a
silently dropped ADR/runbook/SLO section.

## Fix

Same location as [ISS-730](20260922-1343-ISS-730.md)'s own fix direction — a
content-completeness signal added once to `_execute_impl`'s shared completion gate
(`engine.py:7376-7457`) covers all four agents (and any other agent of this shape) in one
place; no per-agent engine change needed. A prompt-side structural checklist on each of these
three `AGENT.md` files would help but, per ISS-730, is not a substitute for the engine-side
check.
