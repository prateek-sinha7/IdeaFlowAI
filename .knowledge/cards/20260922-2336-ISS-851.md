# ISS-851

Found while fixing [QA-SG-004](../../BUGS.md#qa-sg-004) under
[FIX-635](20260922-2335-FIX-635.md); recorded, not fixed.

## What is wrong

[FIX-621](20260922-2009-FIX-621.md) made every live-run switch caller await the
switch before navigating:

- `DashboardLayout.tsx:2816` — bell `onViewResults`:
  `await onSwitchToLiveRun(targetRunId); router.push(...)`
- `DashboardLayout.tsx:2749` — `onGoToPipeline` (dropdown + badge)
- `AppHeader.tsx:258` (`handleRunClick`), `AppHeader.tsx:354` (badge fallback)

The awaited promise is `handleSwitchToLiveRun` (`page.tsx:2778-2887`), which
resolves only after `await getRunEvents(switchToken, runId)` (`page.tsx:2848`)
and the full replay. `getRunEvents` goes through `fetchWithTimeout` with
`REQUEST_TIMEOUT_MS = 30_000` (`lib/api.ts:124`, `:283-289`). So:

1. **The URL moves one serial round trip late.** The new mount's T11 fetches
   the same events again after the remount (`page.tsx:3676`), so the user
   waits for two `getRunEvents` in series where HEAD `cae0c8adf` waited for
   one — for every switch whose target the reactive push below cannot move
   first. QA-SG-004's own report lists "long delay (several seconds)" as a
   symptom.
2. **Under connection-pool saturation the navigation waits up to 30 s.**
   INFERRED from the code, not observed live: REST and SSE share one origin
   (`frontend/.env.local` `NEXT_PUBLIC_API_URL=http://localhost:8000`), each
   live run holds its own streaming fetch (`RunConnectionProvider.tsx:599-611`,
   `useRunStream.ts:345-349`), and `RunConnectionProvider.tsx:45-52` (BUG-013)
   already documents that with 6+ streams "the next request to the origin ...
   has no free socket and hangs". Six actively-emitting runs this tab owns fill
   the pool, and the awaited `getRunEvents` then queues behind them.

FIX-621's card says the switch "never rejects ... so navigation cannot be
stranded" — true for a rejected fetch, not for a queued one.

## Why it is not fixed under FIX-635

`page.qaSg004.test.tsx` (the QA-SG-004 test) requires an in-flight guard AT
the caller — its `hasInFlightGuard` accepts `await onSwitchToLiveRun` — and
pins `router.push(routes.runStream(targetRunId))` to the call site. Removing
the await turns its ISS-775 and two ISS-778 tests red, and a fixer may not
edit a test to pass. FIX-635's T7/T11 guard makes the await unnecessary for
correctness (the page no longer fights the push), and DashboardLayout's
reactive push (`DashboardLayout.tsx:838`) navigates immediately when the
target's store entry is already running — so the cost now falls only on runs
this tab has not streamed or replayed.

## Decision needed (analysis/test phase)

Whether the ISS-775/ISS-778 tests' "guard at the caller" premise should be
restated so the callers can return to a synchronous `router.push` (HEAD
`cae0c8adf` shape) now that the fight is guarded inside page.tsx.
