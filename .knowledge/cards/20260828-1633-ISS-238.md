## What happened

Filed from `BUG-20260827-231407-register` in `bug-hunter/ledger.md`. For an
**authenticated** user, navigating (cold, full `page.goto`) to any nonexistent sub-path
under `/register` — `/register/anything`, `/register/abc123xyz`,
`/register/deep/nested/path` — leaves the address bar on that bogus URL while the
fully-rendered authenticated dashboard (heading "What would you like to build today?",
workflow catalog cards, "Jump back in" run history, header nav with Home active) renders
underneath it. No console errors; the dashboard's own API calls (`/api/runs`,
`/api/auth/me`, `/api/workflows`, `/api/analytics/summary`, etc.) all return 200,
confirming a genuine render, not a stale screenshot. Signed-out users hitting the same
URL correctly fall through to `/login?redirect=...` — the defect is specific to the
authenticated path.

## Reproduction (3/3, cold start each time)

Each attempt: `about:blank` -> fresh `page.goto` to a different `/register/<sub-path>`,
already authenticated as qa-admin (`auth_token` present).

1. Cycle 1: `http://localhost:3000/register/anything` -> `location.href` stayed
   `/register/anything`, `h1` read "What would you like to build today?".
2. Cycle 2: `http://localhost:3000/register/abc123xyz` -> same mismatch.
3. Cycle 3: `http://localhost:3000/register/deep/nested/path` -> same mismatch.

3/3 CONFIRMED — no variation needed; the trigger is simply "authenticated + any
`/register/<extra-segment(s)>` URL".

## Root cause

`frontend/src/lib/routes.ts:219-221`:

```ts
if (head === 'register') {
  return { screen: 'register' };
}
```

This matches on `segments[0] === 'register'` alone, with no check that
`segments.length === 1` — unlike the sibling `create` branch three cases below it, which
explicitly branches on `segments.length === 1` vs. deeper segments. So
`parseViewPath(['register', 'anything'])` returns `{ screen: 'register' }`, exactly the
same descriptor as the real, exact `/register` route.

The catch-all component, `frontend/src/app/[...view]/page.tsx`, only ever reaches this
code for **sub-paths** — the literal `/register` is served directly by
`frontend/src/app/register/page.tsx` (a real Next.js route, which wins over the catch-all
for an exact match and does its own `router.replace('/login')`). But
`[...view]/page.tsx` itself has **no branch anywhere that checks
`parsedView.screen === "register"`** — grepped the whole file, zero hits. Every
unhandled/unrecognized screen falls through the if-chain to the file's default render
path, which is the same `DashboardLayout`/catalog render used for `home`. Contrast with
`screen === "unknown"` (line ~3710), which explicitly calls `notFound()` — `register` gets
none of that handling because the parser never produces `unknown` for it in the first
place.

Distinct from [ISS-193](20260828-1554-ISS-193.md), which is about the **exact**
`/register` path's own `register/page.tsx` component redirecting an authenticated user
into `/login`'s missing guard — that bug lives entirely inside the real
`app/register/page.tsx` file and is already `status: resolved`. This issue is a
`parseViewPath` matching bug in the catch-all route parser, only reachable via sub-paths
that never hit `app/register/page.tsx` at all.

## Expected vs actual

- **Expected:** an authenticated user hitting a nonexistent sub-path under `/register`
  gets a 404/not-found (matching the `unknown` screen's existing behavior) or an actual
  redirect, with the URL and rendered content agreeing.
- **Actual:** the URL bar permanently shows the bogus `/register/<sub-path>` while the
  authenticated dashboard renders underneath it, stable across hard reloads.

## Fix direction (not applied — analysis/fix only)

Guard the `register` branch in `routes.ts` the same way `create` already is:
`if (head === 'register' && segments.length === 1) { return { screen: 'register' }; }`,
falling through to the existing `unknown` return otherwise (line ~284/346/409) so
`[...view]/page.tsx`'s existing `notFound()` handling for `screen === "unknown"` takes
over — no new branch needed in the page component itself.
