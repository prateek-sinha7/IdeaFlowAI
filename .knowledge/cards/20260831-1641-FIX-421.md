# FIX-421

**Phase / trigger:** bug-hunt domain 15 (backend·other), batch B4 — ISS-125

## Description

[FIX-240](20260812-1852-FIX-240.md) moved `_stamp_resume_marker` off its original
unretried `read-max(seq)+1-then-append_event` onto
`ScopedStore.append_event_next_seq`, which closed the lost-write race but kept the
READ cost: that allocator calls `read_events(run_id, after_seq=0)` **per attempt**,
materialising every `run_events` row for the run in order to derive one integer. The
local corpus holds a 26k-row and a 36k-row run — this is the exact cost profile that
already ruled `append_event_next_seq` out for the engine's own event sink, and it was
sitting on the in-process auto-resume path.

The marker also never needed anything `append_event_next_seq` uniquely provides: it
mints a fresh `event_id` (`uuid.uuid4()`) on every call, so its `(run_id, event_id)`
idempotent no-op branch can never fire.

The fix routes the marker through the same pair the engine sink
(`engine.py:448`) and the durable-cancel writer (`app/api/run_commands.py:445`)
already use — `_max_event_seq` (a bounded `func.max` aggregate over
`uq_run_events_scope_seq`) for the tail, then `append_event_at_or_after`, which
re-appends past a racing writer and only retries when the tail actually reached the
attempted seq. Collision safety is preserved; the full-log scan is gone.

## Root cause

`backend/agents/execution_engine/engine.py:7675` (pre-fix) called
`ScopedStore.append_event_next_seq`, whose allocation loop begins
`existing = await self.read_events(run_id, after_seq=0)`
(`backend/agents/authz.py:485`) — an unbounded read of every row for the run, per
retry attempt, to compute `max(seq) + 1`.

## What changed and why there

`backend/agents/execution_engine/engine.py` — `_stamp_resume_marker` only. One call
site, because that is where every caller of the marker converges: `engine.py:7411`
(the in-process restart auto-resume) and `app/api/run_commands.py:733` (the REST
resume endpoint) both reach the allocation through this one method, so no caller-side
guard was needed anywhere.

- allocation swapped to `(await store._max_event_seq(run_id)) + 1` +
  `append_event_at_or_after(...)`, matching `_record_cancellation_in_the_durable_tail`
  verbatim in shape (INV-12: one durable-audit-append idiom, not a third variant).
- the `except RuntimeError` branch was **removed** — it was orphaned by this change.
  `RuntimeError` is `append_event_next_seq`'s retry-exhaustion signal only;
  `append_event_at_or_after` re-raises the DB's own `IntegrityError` instead, and no
  discriminator distinguishes exhaustion from the non-retryable rejections (absent
  `workflow_runs` FK target in the offline harness, a `None` recovered workspace) that
  share it. Both now degrade through the existing best-effort `except Exception`
  warning, which is exactly what the sibling audit writer does. **Consequence to
  know:** an exhausted-retry conflict now logs at WARNING rather than ERROR. Nothing
  is swallowed — the allocator always raises — but the log level for that one path
  dropped.
- the `DB-001` docstring paragraph rewritten to describe the allocator actually in
  use; leaving it naming `append_event_next_seq` would have made the comment lie.

Deliberately NOT changed: the chat-lane callers of `append_event_next_seq`
(`app/api/run_commands.py`, `app/agents/chat_narrator.py`). They depend on its
`(run_id, event_id)` idempotent no-op for double-submitted `message_id`s — that is the
method's reason to exist, and ISS-125 scopes to the marker.

## Sibling cards this same edit touches

**[ISS-133](20260812-2148-ISS-133.md) — cured here, but NOT closed by me.** It is a
duplicate filing of the same call site (`_stamp_resume_marker`) from the collision
angle rather than the read-cost angle, and its prescribed fix is verbatim this one:
"swap `append_event` for `append_event_at_or_after(run_id, max+1, …)`". Its collision
half was already closed by DB-001 (the move to `append_event_next_seq`); this change
completes it. Left `status: open` because ISS-133 is an in-flight unit of a DIFFERENT
bug-hunt domain (14-backend-api, batch B2, status ANALYZED) whose register row is not
mine to write — its owner should verify against this card rather than re-fix the
function. Its second, self-described "unverified" impact (`_reconcile_terminal_status`
treating `run_resuming` as an attempt boundary, `run_commands.py:652-660`) is untouched
by this change and remains theirs.

**[ISS-639](20260831-1645-ISS-639.md) — filed, not fixed.** Sweeping the file for
ISS-125's idiom rather than patching only the named site turned up two more unbounded
`read_events(after_seq=0)` + `max(seq)+1` tail reads (`engine.py:10010` `resume_run`,
`engine.py:10377` `_replay_clarify_run`). They are seq SEEDS, not appends — no
lost-write exposure, read cost only — so they are a separate defect with a separate
proof obligation, not part of this diff.
