## Description

update_specs regenerated the spec from scratch instead of revising it, and every resumed run rebuilt its planning context from a 200-char stub — the degraded spec then drove the planner and the finished prototype, with no UI signal

## Root cause

Not data loss, a routing bug: spec v1, the planning_context row and the clarifications row were all in ectx.artifacts when the degraded prompt was composed. (D1) _run_spec_revision_sub_pipeline set only ectx.spec_revision_context = analysis_report; prototype-specify declares consumes: [] + tools: [], so it had neither a routing nor a filesystem channel to the spec the prompt told it to "preserve unchanged sections" of. (D2) a resumed run took skip_planner -> _default_planning_context (user_message[:200], every list empty): block collapsed 4,591 -> 291 chars across 16 of 18 dispatches. (D3) the revision reused the IDENTICAL checkpoint thread_id, so the only thing that had ever carried the prior spec was the LangGraph conversation — empty after a restart on sqlite's InMemorySaver.
