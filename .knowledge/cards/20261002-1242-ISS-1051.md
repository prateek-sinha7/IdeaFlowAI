# ISS-1051

**Deferred, not fixed.** [ISS-975](20261002-0346-ISS-975.md) flagged this as a hazard and left it open: "Decide whether
that should disable the button instead". [FIX-717](20261002-1243-FIX-717.md) kept the header's behaviour for this case
unchanged.

## Condition

An older family member whose `git_tag` is null. [ISS-697](20260922-1000-ISS-697.md) explains how that happens: tagging
is best-effort and can fail for a completed member. Real examples are `4eb1a2ea-b4be-400a-b53c-b63597cc52a0`
(cancelled) and `97b49f98-83bd-4ed6-8631-600bf9653905` (failed), both in family
`87e02c32-96a9-4e50-8ed0-79023d83540f`, per `evidence/qa-kb-053/family-probe.out.txt`. Neither of those two declares a
deliverable, so neither one reaches this path today.

## What happens (read)

- `PreviewPanel.tsx:874`: `displayRef` is `null` for such a member, because it has no snapshot to read.
- Since FIX-717, these consumers treat `null` as "keep the fallback":
  - FilesTab keeps the content-derived row (`FilesTab.tsx:573`);
  - SandboxPdfPreview renders its fallback;
  - the Figma export walks the member's own HTML on the client.
- The header does not. `:1455` resolves with `displayRef ?? undefined` (the live tree), and `:1506-1507` reads with the
  same value. So the header Download still hands over the newest member's file under this member's name. This is the
  behaviour from before FIX-717, kept on purpose because the choice is a UX decision.

## Decision needed

1. **(a)** Disable the header Download for a tagless older member, with a tooltip saying why.
2. **(b)** Keep serving the live file, which may be another member's bytes.

For (a), the code change is small: skip the resolution effect when `displayRef === null`, the same way FilesTab does.
