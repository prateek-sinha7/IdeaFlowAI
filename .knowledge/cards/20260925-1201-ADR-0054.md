## Decision

`pdf_to_prototype` and `prototype_v2` both built a prototype from uploaded
documents. `prototype_v2` is the one kept: it is entitled on every tier and is the
flow being demoed. `pdf_to_prototype` is deleted — folder, Enterprise rows in both
entitlement maps, its compile test and its entries in the parity/alias lists.

## What stays, and why

Capabilities only `pdf_to_prototype` used were checked one by one:

| Capability | Kept because |
|---|---|
| validators `journeys_coverage`, `html_element_floor`, `fragment_field_coverage` | registered `user_allowed=True` — offered on the Composer palette |
| input provider `pdf_pages` | `user_allowed=True`, and pairs with the `file-analyst` agent (spec 019) |
| skill `file-extraction` | lives in `backend/skills/global/` |
| `spec_plan_coverage`, `design_quality`, `prototype_emit_only`, mechanical publish | used elsewhere |

No DB-composed workflow and no run referenced any of them at deletion time. The
"PDF → Prototype" label in `pipelineLabel.ts` stays so historical runs keep a name.

## Related rename

`playwright_smoke_test` → `ex_playwright_smoke_test` (display name "Browser check"),
so the dashboard's `ex_` prefix rule files it under Engine examples.
