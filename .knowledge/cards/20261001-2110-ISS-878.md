# ISS-878

**Register source:** `QA-KB-034` in root `LEDGER.md` / `BUGS.md` (sibling, derived during its analysis on 2026-10-01).
**Root card:** [ISS-877](20261001-2110-ISS-877.md) holds the root cause (the engine's silent roster seam) and the fix location.
**Claim status:** INFERRED at the product level. REPRODUCED at the unit level, offline, for (A1) the roster the trigger path hands
`_launch_run_core` and (A2) the spec-overlay gap (probe below: `_launch_run_core` stubbed, no database, no run, no server). The persisted
`agent_count`, the user-visible effect of A2 and the `resume_run` log lines (B) are inferred from the code read; nothing was launched.

## Condition

A caller resolves a FILE-BACKED workflow's roster as `get_pipeline_agents(ref)` and falls back to the compiled plan only when that list
is EMPTY. Today that is wrong for the two workflows whose registry roster is a strict subset of their plan
(`prototype_v2_revision` 1 of 3, `prototype_v2_feature_revision` 1 of 5; [ISS-877](20261001-2110-ISS-877.md) shows why: their steps are
`custom-agent:*` template instances the registry skips on purpose). `launch_run` outgrew the empty-only rule; its twins did not.

## What is wrong

### A. The trigger path, `KernelServices.run_trigger_workflow`

`backend/agents/execution_engine/kernel_services.py:1594-1601` (file-backed branch):

```python
target_pipeline_type = workflow_ref
target_compiled = None
target_agents = get_pipeline_agents(workflow_ref)
if not target_agents:
    target_agents = [
        load_agent_spec(s.agent_id)
        for s in compile_for_run(workflow_ref).steps
    ]
```

The block's own comment (`:1584-1589`) says "Mirrors launch_run's LaunchSource.FILE_PIPELINE resolution ... with the compiled-plan
fallback launch_run already uses for a composed manifest whose custom-agent steps have no AGENT.md". That described the empty case
only, and `launch_run` has since gained the "incomplete, not just empty" rule below; the mirror is out of date. History: the trigger
block dates from `887ccfe96` (2026-08-21, spec 014); `bab17c0b9` (2026-08-27) added the `launch_run` rule and the engine's
`_roster_is_partial` clause together and did not touch this block. The result goes straight into `_launch_run_core(agents=target_agents,
compiled=target_compiled, ...)` (`kernel_services.py:1664-1674`), and `_launch_run_core` only counts and forwards it:
`run_commands.py:3004` `agent_count = len(compiled.steps) if compiled is not None else len(agents)`, then `:3201` `agents=agents`
into `_drive_launch_to_queue`. `launch_run`'s version of the same block (`run_commands.py:3604-3605`):

```python
if _plan is not None and _plan.steps and len(agents) < len(_plan.steps):
    agents = get_execution_engine()._specs_from_plan(_plan.steps)
```

**A1, partial roster (REPRODUCED at the unit level).** For `workflow_ref="prototype_v2_revision"` the core receives 1 agent and
`compiled=None`, so the run row is minted with `agent_count` 1 (INFERRED from `:3004`; the core was stubbed) for a 3-step plan; the
engine's seam then silently runs all 3. `launch_run`'s own comment (`run_commands.py:3590-3594`) records the user-visible symptom of
exactly this: "The run then minted with agent_count=2 for a four-step plan, and the progress chip read "0/2" for a run that executes
four." It was fixed in `launch_run` only.

**A2, the fallback bypasses the plan overlay (REPRODUCED at the unit level; effect INFERRED).** The empty-roster fallback builds raw
`load_agent_spec(step.agent_id)` specs, not `_specs_from_plan`. The engine documents why that matters (`engine.py:3991-4006`):
`_specs_from_plan` is "the single source for rebuilding `agents` from a compiled plan's steps ... which must agree or a resumed composed
run reports every step under its template's name ("Custom Agent")", and without the produces/consumes overlay "a manifest's declaration
is silently inert and every composed step gets `context_sources: []`". The raw roster has equal ids to the plan, so the engine's seam
does NOT rebuild it (`not agents` and `_roster_is_partial` are both false), and the engine runs the raw specs.

**A2 is not implied by [ISS-877](20261001-2110-ISS-877.md).** It sits in the same block and has the same fix, so it is filed here
rather than as a third card.

### B. `resume_run`'s own progress lines

`backend/agents/execution_engine/engine.py:15651-15662`:

```python
logger.info("resume_run(%s): resuming pipeline=%s at step offset %d/%d", run_id, pipeline_type, offset, len(agents))
if offset >= len(agents):
    # Every step already complete — finalize without re-driving any agent.
    logger.info("resume_run(%s): all steps complete — nothing to re-drive", run_id)
```

For a run with no persisted manifest `agents` is `get_pipeline_agents(resolve_alias(pipeline_type))` (`:15608`), i.e. 1 agent for
`prototype_v2_revision`, while `offset` is computed by `_compute_resume_offset` against the plan (`:16239-16249` rebuilds the roster
from `compile_for_run`, 3 steps). With offset 1 or 2 the denominator is 1 and the "all steps complete — nothing to re-drive" line is
false. The branch only logs and falls through, so execution is unaffected: `_drive_resumed_stream` passes the partial roster on and the
seam in `_execute_impl` expands it. The defect is the misleading text. After the ISS-877 fix the same resume would print
"all steps complete" and then "roster expanded from plan", a contradiction inside one incident log.

`_replay_clarify_run` has the same empty-only fallback (`:16079`, `:16086`) but no length-based output, so there is nothing visible.

## Why the root cause implies it

[ISS-877](20261001-2110-ISS-877.md)'s mechanism is that the engine reconciles a partial roster late and invisibly. Any caller that sizes
something from the UNRECONCILED roster therefore gets no signal that its numbers disagree with what runs. A1 and B are two such
callers. The one mismatch somebody noticed (`agent_count`, "0/2") was hand-fixed in `launch_run` and the twin copies were left behind,
which is the pattern a silent seam produces.

## Expected vs actual

- **A1.** `run_trigger_workflow(workflow_ref="prototype_v2_revision")` hands the core `len(agents) == 3` (the plan's step count), so
  `agent_count == 3`. Actual: 1. Same for `prototype_v2_feature_revision`: expected 5, actual 1.
- **A2.** For `prototype_v2` and `backlog` the roster equals `_specs_from_plan(plan.steps)`: display names, produces, consumes.
  Actual: raw specs, every name "Custom Agent", overlays absent.
- **B.** The denominator and the "all steps complete" test use the plan's step count. Actual: the registry roster's length.

## Fix

Make the trigger block do what `launch_run` does (`run_commands.py:3604-3605`): after `get_pipeline_agents(workflow_ref)`, compile the
plan and, when `len(target_agents) < len(plan.steps)`, rebuild with `self._engine._specs_from_plan(plan.steps)`. `KernelServices` already
holds the engine as `self._engine`, so there is no new import. That one edit fixes A1 and A2 together (the raw `load_agent_spec` list is
replaced by `_specs_from_plan`). For B, use the plan's step count for the denominator and the all-complete test in `resume_run`
(`_compute_resume_offset` already compiles the plan).

Optional single home, only if the fixer wants it: extract the three-line seam of ISS-877 into `ExecutionEngine._complete_roster(agents,
compiled)` and call it from the seam, the trigger path, `launch_run` and both resume seams, so the rule exists once. Neither card
requires it. The kernel stays workflow-agnostic (INV-1): the rule is set containment over the plan, never a name.

## Resolution (2026-10-02, QA-KB-034 fixer)

- **A1 and A2 are fixed by [FIX-707](20261002-0134-FIX-707.md).** The file-backed branch of
  `run_trigger_workflow` (`kernel_services.py:1584-1601`) now compiles the plan and rebuilds the
  roster with `_specs_from_plan(_plan.steps)` whenever it is shorter than the plan. That is the
  `launch_run` rule. The call goes through `get_execution_engine()`, `launch_run`'s own handle,
  rather than `self._engine`; FIX-707 gives the reasons.
  - `test_trigger_path_roster_matches_plan_size` is XPASS(strict).
  - Probe after the fix: `prototype_v2_revision` hands the core 3 agents (was 1),
    `prototype_v2_feature_revision` 5 (was 1). `prototype_v2` and `backlog` now carry the
    `_specs_from_plan` names, produces and consumes.
- **B (the `resume_run` progress line) is not fixed.** It is log-only and untested, and it moves
  to [ISS-950](20261002-0134-ISS-950.md) (open). This card is resolved for A1 and A2 only.
