## Reproduction

Confirmed 3/3 from a cold start (fresh navigation to `/dashboard` then `/workflows/new`
each cycle, prior composer state cleared) as qa-admin. Cycle 1 produced the failure first
and cycles 2-3 replicated it identically, including cycle 3 where the "Back" click was
fired immediately after Escape (no settle wait) — timing is not a factor, this is
unconditional.

Steps (each cycle):
1. Cold-navigate to `/workflows/new` (0 agents, "Untitled workflow" placeholder).
2. Type a name into the "Workflow name" textbox (e.g. "Bug Hunter Validator Draft C1").
3. Click "Add agent" → "+ Add" on "Domain Discovery Agent" in the library modal → Escape
   to close it. Header summary now reads "1 agents"; nothing has been saved ("Save
   workflow" never clicked).
4. Click the composer's own `button "Back"` (top-left, `aria-label="Back"`, next to the
   name field).
5. Observed: immediate navigation away (to `/dashboard` in this session, since that was
   the prior in-app history entry) with **zero confirmation dialog** of any kind — no
   native `confirm()`, no in-app "unsaved changes" modal, no `beforeunload` prompt.
6. Re-navigate to `/workflows/new`: composer is fully reset — "Untitled workflow"
   placeholder, "0 agents" — the name and the added agent are unrecoverable.

## Expected vs Actual

**Expected:** Leaving the composer via its own Back control while unsaved name/agent
state is present prompts a "You have unsaved changes — leave anyway?" confirmation (or
the composer persists a recoverable draft).

**Actual:** All unsaved composer state (name + every added agent) is discarded
instantly and silently. No warning, no draft.

## Root cause

`ComposerPage`'s Back button (`frontend/src/components/workflow/composer/ComposerPage.tsx:977-984`)
wires `onClick={onBack}` directly with `aria-label="Back"` — no dirty-check gate on the
click handler itself.

The `onBack` prop is `handleBackNav`
(`frontend/src/components/layout/DashboardLayout.tsx:1684-1695`), passed to `ComposerPage`
at `frontend/src/components/layout/DashboardLayout.tsx:2908`. `handleBackNav` unconditionally
calls `router.back()` (or `router.push(routes.home())` when there's no history) with no
check against the composer's own dirty state (name typed, `pipelineAgents`/manifest
non-empty, none of it persisted via "Save workflow"). `handleBackNav` is shared across
several `onBack` call sites (`WorkflowHistory`, `AccountSettings`, `AnalyticsPage`, the
composer's two mount points) so a fix belongs in this one shared function — or a
composer-specific wrapper that gates it — rather than patched per caller.

## Blast radius

`handleBackNav` (`DashboardLayout.tsx:1701-1712`) is passed as `onBack` to exactly 5
call sites (confirmed via `grep -rn "onBack=" frontend/src`, excluding `*.test.tsx`):
`WorkflowHistory` (:2767), `AccountSettings` (:2849), `AnalyticsPage` (:2863),
`IdeaInputPage` (:2893), `ComposerPage` (:2946, shared by both `/workflows/new` and
`/workflows/{id}/edit`). Every one wires its own Back button the same way — a raw
`onClick={onBack}` with no dirty-check at the call site either. `AnalyticsPage` is
read-only (no unsaved state, not at risk). The other three carry real not-yet-persisted
user input and are filed as their own INFERRED sibling cards below — not yet
independently reproduced.

## Fix should live in one place

Patching only `ComposerPage.tsx:979` leaves `IdeaInputPage`, `AccountSettings`, and the
`/workflows/{id}/edit` mount all still broken by the same mechanism. The guard belongs
in (or wrapping) `handleBackNav` itself — the one place all 5 callers already route
through — fed by a per-child "is this dirty" signal threaded down from each page,
rather than five separate `confirm()` calls sprinkled into five `onClick` handlers.

**Line-number note:** `DashboardLayout.tsx` is under concurrent edit by other work in
this pipeline (`git diff --stat` shows +48/-9 against this card's base commit at the
time of this note), so the original citations above (`:1684-1695`, `:2908`) have
drifted from where `handleBackNav` and the composer's `onBack` wiring sit on the

(see Blast radius above). Same function, same mechanism, same conclusion — only the
line numbers moved. Re-`grep` before editing rather than trusting either set of
