## Why this card exists

[ISS-198](20260828-1400-ISS-198.md)'s "Fix location" step 1 flags that `totalRuns`
counts raw runs while `families.length` counts grouped family cards, and tells the
fixer to "resolve it deliberately rather than restore blindly". Attempting that
resolution shows the two units are not merely inconsistent — under the *currently
green* scenario suite they are **mutually unsatisfiable**. No arrangement of header
text and chip counts passes both the new xfail tests and the existing ones. The
5-fixer changed no source; the decision belongs to a human.

## Contradiction 1 — units (runs vs family cards)

`tests/integration/screens/06-run-history.feature.md` @S-06-04 requires
*"the 'All' filter's count equals the total run count"* and *"the sum of the other
filters' counts equals the 'All' count"*; @S-06-05 requires *"the visible row count
equals the filter's own count"*. Rows are family cards — `RevisionFamilyView.tsx:539`
and `:593` are the only `aria-label="Open …"` nodes, one per family; expanded members
render as `Version N` (`:663`) and are not rows.

- Chips as **run** counts: All = 275 = header ✓ S-06-04, named sum 275 ✓ S-06-04,
  [ISS-213](20260828-1618-ISS-213.md) ✓ — but filtering to Presentation promises 31
  rows and the list draws 25 ✗ S-06-05 (fails for all five types).
- Chips as **family** counts: S-06-05 ✓, S-06-04's second line ✓ — but All = 232
  against a truthful header of 275 ✗ S-06-04's first line.
- Header as the family count: ✗ [ISS-198](20260828-1400-ISS-198.md)'s
  `test_header_count_reflects_the_true_total_not_the_capped_page`, which asserts the
  header equals `X-Total-Count`.

There is no third option: S-06-04 + S-06-05 + family grouping force
`families(type) == runs(type)`, which holds only inside today's 50-row window.

## Contradiction 2 — scope (capped list vs history-wide counts)

- `test_scrolling_to_the_bottom_loads_more_runs` asserts `len(rows) <= 50` at rest and
  more rows after a scroll — the list must be **capped** when the page settles.
- [ISS-213](20260828-1618-ISS-213.md) asserts the Custom chip reads ≥ 158, i.e. chip
  counts must be **history-wide**; S-06-05 then requires the list to draw that many
  rows (176 for Custom) — the list must be **uncapped**.
- Capping the *render* instead of the *fetch* also breaks
  [ISS-208](20260828-1617-ISS-208.md): the true highest-token run sits in the Older
  bucket, behind Today (2) + Earlier (190) cards, so a 50-row window never draws it —
  `bucketAndSortFamilies` (`RevisionFamilyView.tsx:298-329`) sorts *within* a date
  bucket, never across.

Server-side search/sort/count params do not escape this either: S-06-05 compares the
chip to the rendered rows, so any paginated render fails it for a type larger than
the page.

## Options for the human

1. **Card units win.** Header + All chip + named chips all count runs (275 / 195 / 31
   / …); re-base @S-06-05 and its test to "the visible cards represent that many
   runs". Keeps every ISS test; changes one spec line.
2. **List units win.** Header counts runs, chips keep counting cards; re-base
   @S-06-04's first line to "the 'All' filter's count equals the number of run cards".
   Keeps S-06-05/S-06-02 and satisfies ISS-198 t1, ISS-207, ISS-208, ISS-213; changes
   one spec line and needs `test_scrolling_to_the_bottom_loads_more_runs` re-based,
   because option 2 is only reachable by loading the whole history (no row cap).
3. **Keep the cap, pay for the backend.** `list_runs` grows `search`, `sort` and a
   per-bucket *distinct-root* count aggregate; the list stays paginated. Still fails
   S-06-05 for any type larger than a page, so it needs option 1 or 2 on top — the
   most work, the fewest tests satisfied.

Whichever is chosen, [ISS-209](20260828-1617-ISS-209.md) (decrement `totalRuns` in
`handleDeleteConfirm`, `WorkflowHistory.tsx:408-421`) is a one-line prerequisite: any
Load-More trigger that auto-chains on `runs.length < totalRuns` spins forever after a
delete without it.
