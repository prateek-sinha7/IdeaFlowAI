## Origin

Sibling of [ISS-678](20260917-1449-ISS-678.md), derived during the analysis of register entry
**QA-KB-064** (`LEDGER.md`). It **contradicts one of that card's statements**: "The engine's own
run path is NOT affected. At sandbox open, `engine.py:3983-3999` calls `git_init_sandbox` and flips
`sandbox.has_git = False` if init fails." The flip is at `engine.py:4412-4429` now, and it cannot
fire for a git failure. Status: mechanism **CONFIRMED** in-process (temp dir, a simulated init
failure); the real-world trigger (a `git init` that fails on a deployed host) is **INFERRED** and was
not observed.

## Condition

The engine opens the run's sandbox (`engine.py:4403-4404`) and `git init`, the seeding of
`.gitignore`, or the initial commit fails: `git` missing from `PATH`, a permission or disk error, a
failing global hook. Idempotent re-opens are unaffected, because `LocalWorkspace.git_init_sandbox`
returns at once when `.git` already exists (`local.py:711-712`).

## Expected vs actual

- **Expected** (the engine's own comments, `engine.py:4410-4411` and `:4422-4429`): "a git-init
  failure must NOT abort the run ... commits simply won't fire (has_git degrades to no-op)". The
  sandbox flips to `has_git=False`, so `commit_in_sandbox` returns `no_change=True` at
  `engine.py:599-602` and every git-gated step is skipped.
- **Actual:** `has_git` stays `True` with no `.git` on disk. Every step-boundary commit goes through
  `commit_in_sandbox`, whose staging step fails and returns `blocked=True,
  block_reason="staging_failed"` while setting `ectx.last_commit_blocked = True`
  (`engine.py:613-638`). The terminal path then forces the run to `degraded` with "The run's files
  could not be staged, so they were not saved to its history." (`engine.py:8079-8089`,
  `_COMMIT_BLOCK_REASONS` at `:343-344`), and the finalizer's tag step is skipped
  (`engine.py:2609-2613`).

## Mechanism (read, then probed)

1. `engine.py:4403`: `sandbox = RunSandbox(disk_principal, _chain_root_id)`, default `has_git=True`.
   The flag has to start `True`: `RunSandbox.git_init_sandbox` is itself gated on it
   (`sandbox.py:1045-1046`).
2. `engine.py:4412-4429`: `_git_init_fn()` is wrapped in `try / except Exception`, and the `except`
   sets `sandbox.has_git = False`.
3. `RunSandbox.git_init_sandbox` (`sandbox.py:1032-1064`) never raises. Its own
   `try: fn() / except Exception as exc: logger.warning(...)` (`:1056-1064`) swallows every failure
   from `LocalWorkspace.git_init_sandbox`. The only line that can reach the engine's `except` is
   `fn = getattr(self._ws(), "git_init_sandbox", None)` at `:1047`, which sits outside that `try`
   and raises only if building the workspace fails.
4. Nothing else writes `has_git` after construction, so the flag stays `True`.

## Evidence (probe, 2026-10-02)

`backend/.venv/bin/python` from `backend/`, temp `RUNS_ROOT`, `LocalWorkspace.git_init_sandbox`
patched to raise `CalledProcessError(128, ["git", "init"])`:

```
PASS F1 RunSandbox.git_init_sandbox SWALLOWS a failed git init  -> raised=None
PASS F2 after the failed init the sandbox STILL claims has_git=True with no .git
        -> has_git=True .git_exists=False
PASS F3 the engine's step-boundary commit then returns blocked/staging_failed and flags last_commit_blocked
        -> blocked=True reason=staging_failed ectx.last_commit_blocked=True
```

No test pins either behaviour: a search of `backend/tests` finds no test of the flip and none of the
"continuing without git" path.

## Fix direction, and the trap in it

Reconcile **inside the owner of the flag**: at the end of `RunSandbox.git_init_sandbox()`, and in
its `except`, set `self.has_git = False` when `not (self.root / ".git").exists()`, and mirror it onto
`self._workspace.has_git` if `_ws()` was already built. `LocalWorkspace.has_git` is a separate copy
snapshotted at build time (`local.py:328`, `sandbox.py:635-642`) and is what fan-out isolation reads
(`fanout.py:335`). Keep the change in `sandbox.py`: `engine.py` must not import `app.*` at module
level (import-linter contract, `engine.py:595-597`).

**Flipping the flag alone does not make the run `completed`.** `finalize_terminal_run` Step 8 is
gated on `_sandbox is not None and completed and not last_commit_blocked` (`engine.py:2609-2613`),
**not** on `has_git`. `RunSandbox.create_tag` raises `RuntimeError` when `has_git` is false
(`sandbox.py:914-917`), the `except` at `engine.py:2690` logs an ERROR and calls
`attempt.degrade("tag_creation_failed")`. The run would still publish `degraded`, only with a
different reason. Steps 1b (`:2176`), the snapshot commit (`:2402`), crash-replay (`:2479`) and the
run ref (`:2510`) are already gated on `has_git`; the tag step is the odd one out. Whether a run
that could not be versioned should end `completed` or `degraded` is a product call for whoever fixes
this; [ISS-697](20260922-1000-ISS-697.md) touches the same question from the tag side.

Do not derive `has_git` in `RunSandbox.__init__` instead: a derived `False` at construction would
make `git_init_sandbox()` a no-op, so no sandbox would ever get a `.git` and nothing would be
versioned.

## Test notes

Offline unit test: patch `app.agents.runtime.local.LocalWorkspace.git_init_sandbox` to raise, call
`RunSandbox.git_init_sandbox()` on a temp sandbox, assert `has_git is False` (today `True`), and
that `await commit_in_sandbox(...)` then returns `no_change=True` and leaves
`ectx.last_commit_blocked` false (today `blocked=True`). The `ectx` / `step` shapes are the
`SimpleNamespace` stubs `restore_version` builds (`runs.py:2535-2549`).
