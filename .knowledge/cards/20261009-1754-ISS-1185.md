# ISS-1185

Sibling of [ISS-1158](20261009-1510-ISS-1158.md) (register entry QA-KB-122). The register lists 12 tests that POST a password; these four post nothing, so they are not on its list. Filed 2026-10-09 by the analyzer.

## Condition

The admin "Create New User" dialog is invitation-only: no password input and the submit button reads "Send Invitation" (`frontend/src/app/admin/page.tsx:694-708`; the heading is still "Create New User", `:666`). Four e2e tests drive the old dialog (email, password, "Create User"):

| test | e2e site | stale locators | 2026-10-09 rerun |
|---|---|---|---|
| S-11-15 `test_adding_a_user_creates_an_account_at_the_chosen_tier` | `suites/11_admin/test_admin.py:350` fills `input[type="password"]`; `:352` clicks a button matching /create/i | password input; the button is now "Send Invitation" | `Page.fill: Timeout 30000ms exceeded ... waiting for locator("input[type=\"password\"]")` |
| ISS-577 `test_the_create_user_password_field_has_a_show_hide_toggle` | `test_admin.py:366-385` (`:382` `input[type="password"]`) | the field itself | `Locator expected to be visible ... element(s) not found` |
| ISS-295 `test_create_user_dialog_rejects_email_with_no_at_or_domain` | `test_create_user_email_validation.py:53` fill, `:55` `name="Create User"` | password input, button name | same `Page.fill` timeout |
| ISS-324 `test_duplicate_email_create_shows_an_error_toast` | `test_iss324_duplicate_email_toast.py:61,74` fill, `:65,79` `name="Create User"` | password input and button name, each twice | same `Page.fill` timeout |

All four are in the rerun's FAILED list (`rerun/11_admin.log:606,611,612,613`, quoted in `evidence/qa-kb-122/analysis-07-validate-bugs-log-excerpts.txt`), so the failure is CONFIRMED by a run and the cause by reading both sides (`evidence/qa-kb-122/analysis-05-drift-probe.txt`, section G6: the modal at `page.tsx:647-714` has no `type="password"` and no "Create User" button text; nine test lines still look for them).

## Why the root cause implies it

It is the same intentional change as the `disposable_user` POST body in [ISS-1158](20261009-1510-ISS-1158.md): `b2a621f84` removed the password from the API and, in the same commit, from the form ("Create-user form drops the password field entirely and shows an invitation notice instead"). Its unit twin `frontend/src/app/admin/admin.reskin.test.tsx` was updated; the e2e files were not. Three of the four tests carry TWO stale locators (password input and button name), so deleting the password fill alone leaves them red.

## Expected vs actual

Expected: fill the email (and tier), submit with "Send Invitation".
- ISS-295: the gate holds. The button is `disabled` unless `EMAIL_PATTERN.test(newEmail)` (`page.tsx:704`), so the malformed-email test should pass once its locators are right; [ISS-295](20260828-1726-ISS-295.md) is `resolved`, and the test regains the coverage it was written for.
- ISS-324: a duplicate email answers 409 (`backend/app/api/admin.py:444-449`) and the dialog shows an error toast. [ISS-324](20260828-1815-ISS-324.md) is `resolved`.
Actual: all four die on the missing input.

## Fix direction (test-side only)

- `tests/integration/e2e/framework/locators/admin.py` has no locator for the dialog, and three files re-type "Create User" and the password selector. Put the heading ("Create New User") and the submit button ("Send Invitation") there once.
- S-11-15, ISS-295, ISS-324: drop the password fill, click "Send Invitation". Keep each test's `_delete_by_email` cleanup.
- ISS-577 test: retire it. [ISS-577](20260829-0219-ISS-577.md) asked for a show/hide toggle on a field that no longer exists; the requirement is void and the card stays `resolved` as history. Do not put a password field back to satisfy it.
- Spec text: `tests/integration/screens/11-admin.feature.md:212-215` ("Adding a user creates an account at the chosen tier") and any step that names a password field.

## Traps

- S-11-15 and ISS-324 each create a real pool user, and each successful create asks Cognito to send an invitation email (`backend/app/core/cognito.py:421-423`, `DesiredDeliveryMediums=["EMAIL"]`) to a generated `@velocity.ai` address. The `finally` cleanup deletes the user, not the mail.
- Anything these tests create stays `is_admin=False` (the bug line's second-admin rule).
- ISS-324 needs its first create to succeed so the 409 on the second one races the first toast's timer; the toast selector (`.fixed.bottom-6.right-6`) is unverified against today's markup. INFERRED.

## Confidence

CONFIRMED: the four failures (rerun logs) and the cause on both sides (source). INFERRED, not run: that S-11-15 and ISS-324 pass once both locators are fixed. Settle with the live stack, one file at a time: `test_admin.py -k adding_a_user`, then `test_create_user_email_validation.py`, then `test_iss324_duplicate_email_toast.py`.
