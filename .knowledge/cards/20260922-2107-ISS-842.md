## What happened

Bug QA-PS-047 (see `BUGS.md#qa-ps-047`, `LEDGER.md`) reports the live run
stream page (`/runs/{id}/stream`) firing 49+ API requests, including
`GET /api/runs?limit=50` 8-9x, while a run is actively in progress — not
just on durable replay of a completed run (that's the separate, still-open
QA-PS-038).

Validated 3/3 from a cold start. Each cycle:

1. Sign in as `qa-admin@flowinqa.com`.
2. Launch "Build an interactive prototype" (`/create/prototype`) with a
   fresh brief, which lands the run on a questionnaire/clarify gate
   (`status: waiting_for_user`).
3. Cold-navigate to `/runs/{id}/stream`. `GET /api/runs?limit=50` fires
   once at mount (expected, request #68 in every cycle).
4. Click "Accept all recommended & continue"
   (`POST /api/runs/{id}/answers`) — a single live SSE event
   (`questionnaire_complete`).
5. Immediately after, **two more** `GET /api/runs?limit=50` calls fire
   (requests #90 and #91 in every cycle) — 3x total from one user action,
   not 1x.

Identical on all three cycles — same request numbers (68, then 90+91),
same trigger (the questionnaire-answer POST), same 2x multiplier. Cycle 1
alone was sufficient to confirm; cycles 2 and 3 reproduced it exactly.

## Root cause

Two independent effects both refetch the run list on the same live event:

- `frontend/src/app/[...view]/page.tsx` — `handleWebSocketMessage` has
  ~12 separate `getWorkflows(token, { limit: 50 })` call sites across its
  SSE event branches (gate-ready ~2196, gate-approved ~2232,
  questionnaire-complete ~2139, pipeline-complete, etc.). Each live event
  that touches `recentRuns` fires one of these directly.
- `frontend/src/components/history/WorkflowHistory.tsx:250` — a
  `useEffect` keyed on the `recentRuns` prop **reference** (via
  `recentRunsRef`, see comment at line 62-70 referencing "T38
  (014-conditional-gates, R-20 live case)") fires its OWN independent
  `getWorkflows(token, { limit: 50 })` whenever `page.tsx`'s
  `setRecentRuns` produces a new array reference — which every one of the
  call sites above does.

So every live SSE event that updates `recentRuns` produces 2x the
`runs?limit=50` traffic: one direct call from `page.tsx`, one cascaded
call from `WorkflowHistory`'s prop-reference effect. For a 15-minute run
with multiple gates and clarifications this compounds into the 8-12+
live fetches (300-450 KB) QA-PS-047 originally reported, on top of the
mount-time duplicates (`family` x2, `workflows` x3, `gate-events` x2 also
observed firing at mount in every cycle here).

## Expected vs actual

Expected: ~7 requests at mount (`runs/{id}`, `events?after=0`, `family`,
`sandbox/refs`, `runs?limit=50` once, `workflows`, `me`), then the SSE
stream carries all further updates with no more `runs?limit=50` calls.

Actual: 1 `runs?limit=50` at mount, then 2 more per live SSE event that
touches `recentRuns` — confirmed here specifically for
`questionnaire_complete`; QA-PS-047's own network trace additionally names
`review_gate_ready`, `review_gate_approved` and `pipeline_complete` as
other live events that trigger it.
