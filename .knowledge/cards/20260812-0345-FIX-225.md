## Description

Three defects on one reopen-replay path, two of them in the same expression — the "Spec Revision Cycle N" banner read 5 for a run with 2 revisions, and the reopened run's trace repainted as "0 / 5 agents" with every Steps row disabled. (a) ISS-080: agentStartCounts was a bare += 1 with NO identity key, so it counted DELIVERIES; a history reopen replays the durable log once over REST and again over SSE, and the trailing same-run pipeline_start fired resetReplayState mid-replay (24 783 event ids discarded, measured), voiding the CR-05 dedup that was the counter's only protection — {specify:6, plan:4, analyze:4} against a durable truth of {3,2,2}. (b) ISS-081: deriveSpecRevisionCount took max over ALL agents while a per-task agent loop restarts ONE step once per task — run 6e38b9a7 (one revision, 11 prototype-build starts) yields 10, and a live prototype build would show a revision banner having performed none. (c) ISS-075: a pipeline_start re-announcing the run on screen REBUILT every agent as idle and zeroed completedCount, which also made the FIX-222 version picker unreachable (StepsOverviewSpine gates navigation on status !== "idle").

## Root cause

One missing concept, three symptoms: the FE had no predicate for *"this pipeline_start re-announces the run I am already showing"*. FIX-221 introduced it for exactly ONE field (useWorkflow.ts:306-309) instead of promoting it, so the same trailing frame still wiped the dedup seen-set and still rebuilt the roster. Underneath that: two accumulators trusted an external guarantee instead of carrying their own identity — the restart history assumed "each frame arrives once", and the roster assumed the engine's resume_offset was a count of completed agents when it is the FIRST INCOMPLETE step (0 for a run parked at a gate on step 0).
