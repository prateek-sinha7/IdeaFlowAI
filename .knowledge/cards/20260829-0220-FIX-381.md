## What was wrong

BUG-20260828-085830-runs-cancelled (`bug-hunter/ledger.md`). Run
`a8dfa959-e233-4ddf-87ce-d9a942cefde3` was cancelled, then re-launched with "Run
Again"; the resumed pipeline genuinely failed (two `agent_error` rows, then
`pipeline_failed` at seq 29, all 4 agents `agents_failed`). `GET /api/runs/{id}`
kept returning `{"status": "cancelled", "error": null}` on every cold fetch, the
detail badge kept reading "Cancelled by you", and the `/runs` history list kept
tagging the run `cancelled` — while the body of that same detail page, derived
from the event stream rather than the status field, listed all four failed agents
directly under a "This run was cancelled" heading. A permanently wrong terminal
status, not a rendering glitch.

## Root cause

`_reconcile_terminal_status` (`backend/app/api/run_commands.py:748-838`) — the
sole place a resumed run's terminal `WorkflowRun.status` is persisted, as traced
in [ISS-316](20260828-1952-ISS-316.md). Its `resume_supersedes` flag
(`run_commands.py:811-818` pre-fix) was keyed **exclusively on `complete_seqs`**,
the list of non-degraded `pipeline_complete` seqs:

```python
resume_supersedes = (
    cancelled
    and complete_seqs
    and max(complete_seqs) > max(cancelled_seqs)
    and any(max(cancelled_seqs) < s < max(complete_seqs) for s in reattempt_seqs)
)
if cancelled and not resume_supersedes:
    new_status = "cancelled"
```

A resumed attempt that fails writes `pipeline_failed`, never `pipeline_complete`,
so `completes` — and therefore `complete_seqs` — stays empty. `resume_supersedes`
short-circuits `False` on the bare truthiness check, the first ladder branch fires
and re-persists `"cancelled"`. The `else: new_status = "failed"` fail-safe three
lines below is correct but unreachable for this tail: it needs `cancelled` to be
`False`, and the original cancellation is permanently in the durable tail.

[FIX-105](20260723-FIX-105.md) (KAN-120) introduced `resume_supersedes` for the
completed-resume case only; [FIX-229](20260812-0653-FIX-229.md) (ISS-078) added
the attempt-boundary guard to it. Neither covered the failed-resume case.

## What changed, and why there

`backend/app/api/run_commands.py:811-819` only — the file
[ISS-316](20260828-1952-ISS-316.md)'s `applies_to.globs` names. The supersede
check now takes its max over **every terminal outcome of a later attempt**, not
completions alone:

```python
terminal_seqs = complete_seqs + [e.seq for e in events
                                 if e.type == "pipeline_failed"]
resume_supersedes = (
    cancelled
    and terminal_seqs
    and max(terminal_seqs) > max(cancelled_seqs)
    and any(max(cancelled_seqs) < s < max(terminal_seqs) for s in reattempt_seqs)
)
```

The ladder below is untouched: once the cancellation is superseded, a tail with no
`completes` falls through `degraded` and `completes and not failed` to the existing
`else: new_status = "failed"`. This is the card's own proposed fix shape.

It belongs in the shared reconciler because both callers route through it —
`_drive_user_resume` (`run_commands.py:740`, the "Run Again" path that produced the
report) and `stop_run_driver` (`backend/app/api/run_shutdown.py:330-332`, the
`POST /cancel` escalation) — so one guard here fixes both. Every frontend consumer
of the status field (`RunDetailPage.tsx`, `WorkflowHistory.tsx:599`,
`PreviewPanel.tsx`, `RevisionFamilyView.tsx`, `NotificationPanel.tsx`) renders
correctly once the persisted field is correct; none needed a change.

### Why the attempt-boundary guard still holds

The guard is the reason this is three lines and not a rewrite. A cancellation and
a failure inside ONE attempt (a user rejecting at a re-entered gate, then the same
attempt erroring) have no `run_resuming` / `pipeline_start` row between them, so
`any(max(cancelled_seqs) < s < max(terminal_seqs))` is `False` and the rejection
still stands — the exact property [FIX-229](20260812-0653-FIX-229.md) added, now
extended to failures rather than weakened. Verified by the three pre-existing
`test_reconcile_supersedes_only_across_an_attempt_boundary` cases, all still green.

## Not fixed by this card

Three sibling defects in the same function stay **open** — each is a different
state combination with its own card, no failing test, and (for ISS-435) a design
question this card deliberately does not answer:

- [ISS-435](20260828-2253-ISS-435.md) — a resumed attempt ending in a **degraded**
  `pipeline_complete` is still stuck `"cancelled"`, because `complete_seqs` excludes
  degraded completions. Admitting them into `terminal_seqs` would reverse an
  explicit exclusion FIX-229 shipped; that is a decision, not a fix.
- [ISS-436](20260828-2253-ISS-436.md) — the `degraded` flag is a bare `any()` over
  the whole multi-attempt tail with no boundary scoping.
- [ISS-437](20260828-2253-ISS-437.md) — the `failed` flag is unscoped the same way,
  so a run resumed after an earlier failure that then cleanly completes still
  reports `"failed"`. This card does not change that either way: on such a tail
  `max(terminal_seqs)` is the completion's seq, exactly as `max(complete_seqs)`
  was, so the supersede decision and the resulting status are identical pre- and
  post-fix. ISS-437 owns the unscoped-flag fix that makes it `"completed"`.
