## Register entry

Root of register entry **QA-PS-008** (`LEDGER.md`) — "Version dropdown shows
inflated version list and preview fails for all non-live versions (/runs/{id})".
Replaces [ISS-652](20260917-1244-ISS-652.md) and [ISS-663](20260917-1310-ISS-663.md)
as the root card after the 5-fixer stage escalated ([ESCALATIONS.md#qa-ps-008](../../ESCALATIONS.md#qa-ps-008))
that both misidentified where the leaked tags come from. This card carries the
corrected mechanism and the full caller list.

## What this corrects

[ISS-652](20260917-1244-ISS-652.md)'s "Defect 1" said the leaked tags were the
sandbox's **own** git repo carrying deploy/release history no family member created,
and proposed filtering `list_tags()` against the family's `WorkflowRun.git_tag` values.
That is not what happens. The repro family's chain-root sandbox
(`runs/c6b9b61f-183d-4662-ae84-d7fd5a052571/2708dbf1-50d0-465d-9bed-56b651ea1abf/`) is an
**empty directory with no `.git` of its own**. Every git call in `LocalWorkspace` runs with
only `cwd` set, so git's normal upward repository search finds the enclosing checkout —
here, the Flowin/Velocity source tree itself, because `RUNS_ROOT=../runs`
(`backend/.env:8`) sits inside it. The seven "versions" QA saw are this project's own tags,
not a sandbox-repo artifact. [ISS-663](20260917-1310-ISS-663.md)'s mechanism claim (that
`_validate_ref` trusts the same `list_tags()` output as an allow-list) is correct and is
folded in below unchanged, but its "Actual" section understates the impact: the content
served at a leaked tag is the **host source checkout's own history**, not merely "sandbox
content at an unrelated tag."

Both `bug-hunter`/analysis history and `ESCALATIONS.md#qa-ps-008` document the correction
in detail; this card is the corrected replacement, not a duplicate investigation.

## Root cause — CONFIRMED, reproduced directly

### The git-search escape (the actual Defect 1)

`LocalWorkspace._git()`, the file's own designated "SINGLE git-subprocess owner"
(comment at `backend/app/agents/runtime/local.py:370`), sets only `cwd`:

```python
def _git(self, *args: str, env: dict[str, str] | None = None) -> str:
    result = subprocess.run(
        ["git", "-c", "user.name=Flowin Runtime", ..., *args],
        cwd=str(self._root),
        check=True,
        capture_output=True,
        text=True,
        env=env,  # None => inherit
    )
    return result.stdout
```

(`local.py:372-390`, read verbatim). No `GIT_CEILING_DIRECTORIES`, no check that
`self._root` itself contains a `.git`. `list_tags()` (`local.py:875-891`) calls
`self._git("tag", "--list")` through this helper. Three more git subprocess calls bypass
`_git()` entirely and have the identical gap — same `cwd`, no ceiling, no `env` argument at
all: `read_file_at_ref` (`local.py:1062-1067`, `git show <ref>:<relpath>`),
`list_files_at_ref` (`local.py:1080-1089`, `git ls-tree -r <ref> --name-only`), and
`archive_at_ref` (`local.py:1104-1108`, `git archive <ref> --format=zip`).

When `self._root` has no `.git`, git does what it always does absent a ceiling: it walks
up the directory tree until it finds one. Verified directly, read-only, in this
repository:

```
$ cd runs/c6b9b61f-183d-4662-ae84-d7fd5a052571/2708dbf1-50d0-465d-9bed-56b651ea1abf/
$ git rev-parse --show-toplevel
/Users/bilala/Developer/Projects/VELOCITY-AI
$ git tag --list
deploy-prod-20260603-012557
deploy-prod-20260603-014226
pre-fixes-reset
pre-rebase-safety
v0.0.1
v0.0.2
v0.2.0
```

Seven tags, byte-identical to what QA-PS-008's reproduction saw in the dropdown.

### Why `has_git=True` doesn't catch this

`RunSandbox.list_tags()` — the method every caller above actually invokes — checks only a
caller-supplied boolean, never reality:

```python
def list_tags(self) -> list[str]:
    if not self.has_git:
        return []
    fn = getattr(self._ws(), "list_tags", None)
    ...
```

(`backend/app/agents/sandbox.py:896`, read verbatim). `has_git` defaults `True`
(`sandbox.py:546`), and every read-path caller constructs `RunSandbox` without overriding
it: `GET /{run_id}/sandbox/refs` (`backend/app/api/run_files.py:663`),
`GET /{run_id}/sandbox` (`:698`), `GET /{run_id}/sandbox/zip` (`:792`),
`GET /{run_id}/sandbox/file` (`:889`) — all `RunSandbox(current_user.id, _chain_root_id,
runs_root=settings.RUNS_ROOT)`, no `has_git=` argument. So "does this sandbox have its own
git repo" is never actually asked; the flag is an assumption, and nothing before the git
subprocess call verifies it.

### Defect 2 — Preview hangs forever on a non-family tag (from ISS-652, re-verified, unchanged)

This half of ISS-652 was never in dispute and is independently re-confirmed by re-reading
the code: `RunHeader.tsx`'s `VersionMenu` renders whatever tags it is given with no
filtering (comment at `RunHeader.tsx:34-36` documents this — tags come straight from
`GET /api/runs/{id}/sandbox/refs`). Selecting a leaked tag runs
`handleVersionMenuSelect`'s no-match fallback (`PreviewPanel.tsx:819-823`): `member` is
`undefined` (no `FamilyMember.git_tag` equals the leaked tag), so only
`setSandboxSelectedRef(tag)` fires — `viewingVersion`/`activeRunId` never change. The
ref-scoped fetch is gated on `deliverableFile` (`PreviewPanel.tsx:1257`:
`if (!sandboxSelectedRef || !activeRunId || !deliverableFile) return;`), and
`deliverableFile` is resolved by a separate effect (`PreviewPanel.tsx:1188-1248`) against
the run's own live tree — structurally blind to `sandboxSelectedRef` except as a gating
condition (line 1197), never as an input to what it resolves. When that resolution comes
back empty, line 1257's effect never runs, no `getRunSandboxFile` request is ever issued,
and `RefVersionPreview`'s `Loading {tag}…` text has nothing to ever resolve it.

## Blast radius — every caller reading via the same unscoped git plumbing

All of these share the identical root cause (no ceiling directory on any sandbox git
subprocess) and are fixed together by one change:

1. **`GET /{run_id}/sandbox/refs`** (`run_files.py:644-669`) — the version dropdown feed.
   Original QA-PS-008 symptom.
2. **`GET /{run_id}/sandbox?ref=`**, **`/sandbox/zip?ref=`**, **`/sandbox/file?ref=`**
   (`run_files.py:704`, `:805`, `:905`) — all three gated by `_validate_ref`
   (`run_files.py:604-641`), which accepts any tag `list_tags()` returns. Since that list is
   the host checkout's tags when the sandbox has no `.git`, any authenticated owner of ANY
   run can list/zip/read the **host source checkout's own tree** at one of its real tags —
   this is ISS-663's mechanism, corrected: it is not "unrelated sandbox content," it is this
   project's own source at that tag. Not exercised against a live backend (see ISS-663's own
   "what would confirm this"; a safe offline probe against a throwaway nested outer repo,
   run in the scratchpad, reproduced the equivalent read: `list_tags()` returned the outer
   repo's tag and `read_file_at_ref` returned the outer repo's file bytes for a path outside
   the sandbox).
3. **`_validate_ref_against_tags`** (`sandbox.py:1846-1882`), used by
   `select_legacy_payload`'s legacy chain-context read path (`local.py:1837`, called from
   `backend/app/api/run_commands.py:4338-4368`). Narrower blast: `tag` here is a stored
   `WorkflowRun.git_tag` value, not raw user input, so the practical risk is a legacy chain
   payload resolving against the wrong repo rather than an attacker-chosen ref — same root
   cause, lower severity, no separate card.
4. **`engine.py:2351`** — a diagnostic-only `list_tags()` call inside the tag-creation
   failure logger (`finalize_terminal_run`). Worst case is a misleading "collision" flag in a
   log line; not a functional or security defect on its own.
5. **The restore/write path** — `POST /{run_id}/restore` accepts the same leaked tags and
   runs `git restore` + `git commit` with `cwd` inside the host checkout. Filed separately as
   [ISS-672](20260917-1350-ISS-672.md) (sibling) because the consequence class (a write into
   the host repository, not a read) is materially different and more severe.
6. **Frontend** — `RunHeader.tsx` / `PreviewPanel.tsx` (Defect 2 above) is a real,
   independent bug (a leaked tag with no matching `FamilyMember` should show an error, not
   hang), but it is not itself part of the git-search-escape root cause — it is the visible
   symptom once a non-family tag reaches the menu at all.

Two callers were investigated and found NOT to share this defect:
`frontend/src/lib/api.ts`'s `resolveRunDeliverable` has no `ref` parameter at all — an
unrelated defect, already filed as [ISS-665](20260917-1311-ISS-665.md) and unaffected by
this correction (its test is correct as written).

## Expected vs actual

- **Expected:** `refs` in `GET /api/runs/{id}/sandbox/refs` = only tags this run family
  created; every ref-scoped read/list/archive/restore call against a sandbox with no `.git`
  of its own fails closed ("not a git repository"), never silently resolving to whatever
  repo happens to enclose the sandbox directory on disk.
- **Actual:** any sandbox lacking its own `.git` transparently inherits the enclosing
  checkout's entire tag/object history for every git-backed sandbox operation.

## Fix direction (not applied — issue only)

The fix belongs in `LocalWorkspace`, which the file already documents as the single owner
of every sandbox git subprocess (`local.py:370` comment) — one change there covers every
caller in the blast radius above, rather than a guard duplicated in each of `run_files.py`,
`runs.py`, `sandbox.py`'s legacy path, and the engine diagnostic:

- Add `GIT_CEILING_DIRECTORIES=str(self._root.parent)` (or equivalent — e.g. resolving and
  caching `(self._root / ".git").is_dir()` once and short-circuiting before any subprocess
  call) to `_git()` (`local.py:372-390`) so its `env=` always carries the ceiling regardless
  of what the caller passes.
- Apply the identical `env=` to the three direct `subprocess.check_output` calls that
  bypass `_git()`: `read_file_at_ref` (`:1062`), `list_files_at_ref` (`:1081`),
  `archive_at_ref` (`:1104`).
- With the ceiling set, a sandbox with no `.git` gets git's own "not a git repository"
  failure on every one of these calls — which every caller already treats as fail-closed
  (`list_tags()` returns `[]` on exception; `_validate_ref`/`_validate_tag_for_restore`
  reject every ref against an empty allow-list). No caller-side change is needed once the
  ceiling is in place; the existing fail-closed handling starts working as its own
  docstrings already claim it does.
- `RunSandbox.has_git` (`sandbox.py:546`) staying a caller-supplied flag is a secondary gap
  worth closing too (it is currently just wrong for the 87 of 103 local `runs/` directories
  observed to have no `.git`), but the ceiling fix above is sufficient on its own to close
  every leak in this card and in [ISS-672](20260917-1350-ISS-672.md) — `has_git` accuracy is
  a robustness improvement, not required for this fix.
- Defect 2 (frontend hang) is independently worth a fallback error state in
  `handleVersionMenuSelect`'s no-match branch regardless of the backend fix, since any
  future non-family tag (not just a leaked host tag) would hit the same silent hang.

## Resolved by FIX-522 (2026-09-17)

[FIX-522](20260917-1449-FIX-522.md) applied this card's fix direction as written: `_git_env`
adds `GIT_CEILING_DIRECTORIES=<root parent>` to `_git()` and to the three direct
`check_output` readers in `backend/app/agents/runtime/local.py`. The test file was rewritten
to the fixture this card prescribes: a sandbox with no `.git`, nested in a tagged outer repo.
Pre-fix it fails for the stated mechanism: 3 xfailed, and `--runxfail` shows the leaked tag,
a 200 serving the outer repo's file, and a commit landing in the outer repo. Post-fix all 3
are XPASS(strict).

Two items in this card were not changed by FIX-522 and are carried forward as open cards:

- Defect 2 (the Preview `Loading {tag}…` hang) is now [ISS-677](20260917-1449-ISS-677.md).
- `has_git` accuracy is now [ISS-678](20260917-1449-ISS-678.md).
