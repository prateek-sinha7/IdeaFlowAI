# ISS-816

## What this completes

[ISS-789](20260922-1818-ISS-789.md) (validate phase) root-caused BUGS.md's
QA-PS-042 to `frontend/src/app/admin/page.tsx:177-198`'s mount effect,
reproduced 3/3 on a client-side (SPA) navigation into `/admin`, not on a
hard reload. This card (analyze phase) answers the two questions ISS-789
left open: blast radius (who else is affected) and where the fix belongs.

## Root cause — confirmed by direct read

`frontend/src/app/admin/page.tsx:177-198`:

```tsx
useEffect(() => {
  const token = getToken();
  if (!token) { router.replace(buildLoginRedirect()); return; }
  getMe(token).then(user => {
    if (!user.is_admin) { router.replace(routes.dashboard()); return; }
    setCurrentUserId(user.id);
    loadUsers(token);           // -> adminListUsers(t)
  }).catch(...);
}, [router, loadUsers]);
```

No `AbortController`, in-flight `useRef` guard, or cache — matches ISS-789.
`loadUsers` is itself `useCallback`-memoized on `[showToast]`, and
`showToast` on `[]`, so the effect's own dependency array is stable; the
double-fire comes from the mount itself running twice (dev StrictMode),
not from the effect re-running due to a changing dependency.

## Blast radius — confirmed by grep

`grep -rn "adminListUsers(" frontend/src --include="*.tsx" --include="*.ts"`
(excluding tests) returns exactly ONE call site: `admin/page.tsx:168`,
inside `loadUsers`, itself only invoked from the same mount effect above.
The reported `GET /api/admin/users` x2 has **no blast radius beyond this
one page** — it is entirely explained by that single effect firing twice.

`grep -rn "getMe(" frontend/src --include="*.tsx" --include="*.ts"` returns
five real call sites (`HomeLaunchGrid.tsx:45` is a comment, not code):

- `frontend/src/app/[...view]/page.tsx:894` — the shared catch-all's own
  auth-check effect, already root-caused as
  [ISS-794](20260922-1827-ISS-794.md) (`page.tsx:879-892`, no guard,
  doubles under StrictMode) for routes that resolve through that catch-all.
- `frontend/src/app/admin/page.tsx:183` — this bug (ISS-789, above).
- `frontend/src/components/settings/AccountSettings.tsx:139` — `/settings`,
  already covered by [ISS-781](20260922-1630-ISS-781.md) Mechanism B /
  [ISS-801](20260922-1834-ISS-801.md).
- `frontend/src/components/workflow/LaunchWizard.tsx:371` — **not covered
  by any existing card.** Filed as [ISS-817](20260922-1932-ISS-817.md).

## Why the fix cannot live in the catch-all (confirmed)

`find frontend/src/app -maxdepth 1 -type d` lists `[...view]`, `admin`,
`handoff`, `login`, `preview-fullscreen`, `register`, `workflow` — six
literal Next.js App Router route folders that sit ALONGSIDE the catch-all,
not behind it, despite CONTEXT.md's "every URL routes through routes.ts
behind one catch-all" framing of the common case. `admin/page.tsx` imports
neither `AppHeader` nor `DashboardLayout`
(`grep -n "AppHeader\|DashboardLayout" frontend/src/app/admin/page.tsx`
returns nothing) — so BUGS.md's own hypothesis that `AppHeader` (line 569)
is a second, independent `getMe` caller on this page is WRONG; there is
exactly one call site (`admin/page.tsx:183`), matching ISS-789. `/admin`
never runs `[...view]/page.tsx`'s auth-check effect at all, so a fix scoped
to that file (ISS-794's scope) would leave `/admin` — and
`/workflow/create`, `/login`, `/register`, `/handoff`,
`/preview-fullscreen` if any share the same call shape — still broken.

## Where the fix belongs (confirmed)

Both `getMe` (`api.ts:546-551`) and `adminListUsers` (`api.ts:1575-1580`)
call `request<T>()` (`api.ts:365-375`), which calls `fetchWithAuth()`
(`api.ts:332-363`) — the shared path every REST call in this file goes
through except a few functions documented as deliberate exceptions (raw
downloads, SSE/NDJSON streams). `fetchWithAuth`/`request` have exactly ONE
in-flight guard in the whole file: `inFlightRefresh`/`refreshOnce()`
(`api.ts:225-234`), and it exists solely to single-flight the token-refresh
call — there is no general keyed-by-URL in-flight dedupe for ordinary GETs
(confirmed by reading the full bodies of both functions; no other
`inFlight`/cache map exists in this file).

This is the same conclusion the sibling cards for QA-PS-037/039/041
([ISS-788](20260922-1816-ISS-788.md) and its neighbours) independently
reach for their own routes: **one guard in `request()`**, generalizing
`refreshOnce()`'s single-flight pattern to a URL-keyed map, closes every
caller at once — `admin/page.tsx`'s effect, `[...view]/page.tsx`'s effect
(ISS-794), `AccountSettings.tsx`'s effect (ISS-781/801), and
`LaunchWizard.tsx`'s effect (ISS-817) — regardless of whether the caller's
route goes through the catch-all or is a literal route folder. A
per-component `useRef`/`AbortController` guard (the shape ISS-789 diagnosed
for `admin/page.tsx` alone) would also close THIS bug, but leaves every
sibling caller — present and future — still unguarded.

## Confidence

CONFIRMED (read directly): the effect location and shape; the sole call
site for `adminListUsers`; the five `getMe` call sites; the absence of
`AppHeader`/`DashboardLayout` on `/admin`; the six literal route folders
alongside `[...view]`; the absence of any general GET dedupe in
`request()`/`fetchWithAuth()`.

INFERRED (already flagged as open by ISS-789 itself, not resolved further
here): the precise reason a hard reload does not double-fire while an SPA
navigation does. React 18 StrictMode's dev-only double-invoke is the
working theory across this whole card family and is consistent with
`frontend/next.config.ts` carrying no `reactStrictMode: false` override
(default is `true`, confirmed by reading the 46-line file), but the
hard-reload-vs-soft-nav asymmetry itself is not independently re-derived
here — settling it would need the same repro run against a production
build (`next build && next start`), where StrictMode's double-invoke does
not apply, to see whether the duplication survives.

## Resolution — [FIX-626](20260922-2045-FIX-626.md), 2026-09-22

Fixed, with one deliberate narrowing of the proposal above. The guard went
into `adminListUsers()` itself (`frontend/src/lib/api.ts:1671-1699`, a
token-keyed `inFlightAdminUsers` map mirroring `inFlightWorkflows`), NOT
into `request()`/`fetchWithAuth()` for all GETs.

Why: this card's own grep is what makes the broad version unnecessary —
`adminListUsers` has exactly one non-test call site (re-verified at fix
time), and `getMe`'s other four are already covered by `cachedGet()`
(ISS-801, landed after this card was written, which is why the body above
still describes `getMe` as unguarded). A blanket GET dedupe in `request()`
would also break the invariant `api.ts:394-404` documents in prose — run
and workflow lists deliberately are NOT deduped, because their callers
refetch precisely to observe a change.

Proven by `tests/integration/e2e/suites/11_admin/test_qa_ps_042_admin_duplicate_requests.py`
— `XPASS(strict)` after the fix (the assertion passes; the run fails only
on the xfail marker, which 6-verifier removes).
