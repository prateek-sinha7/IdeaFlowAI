# ISS-1159

Register entry QA-KB-120 (Low, finalizer, no UI route). Validated from the server logs: no browser is involved, and a fresh failing run costs real model money, so the occurrences already in the logs were used. 4 of 4 failed runs showed it (3 on :8000, 1 on :8001); the signature never appeared on a successful run.

## Reproduction (observed)

Run the `ex_A1_loop` style workflow so the conditional gate fails (QA-KB-124: `malformed route_decision JSON`, state `generating -> failed`) before `greeting.md` exists. In `/private/tmp/velocity-8000.log`:

- run c10a03ed (line 6743-6744), caa766dc (7085-7086), 1260b7ba (7307-7308): `build_flat_payload: output file not found ... basename='greeting.md'` then `WARN build_flat_payload: stage_exact failed` with a traceback ending `git ... add --force -- .chain/summary.md .chain/logs.jsonl .chain/greeting.md returned non-zero exit status 128`.
- :8001 run 9a931a7a: same sequence.
- Every time, finalization then succeeds: `build_metadata_only_snapshot ... reason='output_unmaterializable'`, `published=degraded candidate=failed`.

## Cause (code read)

`backend/agents/execution_engine/engine.py:1650` only `logger.debug`s "output file not found" and leaves `_allowlist` (built at :1554 from `_output_basename`) unchanged; `:1757` `sandbox.stage_exact(list(_allowlist))` then runs `git add --force -- <3 paths>` (`local.py:1433`), which is all-or-nothing and exits 128 (pathspec does not match) for the missing `.chain/greeting.md`. The sibling case for the text form already prunes (`engine.py:1674`, comment "not staged, so stage_exact never names a missing file"); the main output path lacks the same prune.

## Expected vs actual

Expected: a not-materialized output is a known, handled state (non-chainable `output_not_materialized`), so it should not produce an error traceback; summary.md and logs.jsonl should still stage. Actual: WARN plus traceback per failed run, and nothing staged by that call (the later snapshot path masks it).

## Fix direction

When `_materialized` is False, drop `.chain/<_output_basename>` from `_allowlist` before `stage_exact` (mirror :1674), or have stage_exact skip paths absent on disk.

Evidence: evidence/qa-kb-120/01-validate-log-occurrences.txt. Related: QA-KB-124 (the failing run that triggers it).

### Root cause (one mechanism)

`build_flat_payload` decides which files it will stage before it knows which it wrote, and for the declared output it never takes the entry back out.

1. `_allowlist = _payload_allowlist(_output_basename, _text_basename or None)` (`engine.py:1554`) returns `{.chain/logs.jsonl, .chain/summary.md, .chain/<output>[, .chain/<text form>]}` from the declared names alone (`sandbox.py:314-320`).
2. The output is then copied or materialized in one of four branches (`engine.py:1606-1647`: file on disk, `serialized_sandbox` bundle, `streamed_text`, `ppt`). When none yields bytes, or the copy raises, `_materialized` stays `False`. The only thing the `else` does is `logger.debug("output file not found ...")` (`engine.py:1648-1653`); `_allowlist` is untouched. `_payload_chainable` and `_non_chainable_reason = "output_not_materialized"` are derived from the flag (`engine.py:1689-1699`); the allowlist is not.
3. Only the text form is taken back out, with the comment that states the invariant: `except Exception:  # noqa: BLE001 — not staged, so stage_exact never names a missing file`, then `_allowlist = _allowlist - {f".chain/{_text_basename}"}` (`engine.py:1667-1674`).
4. `sandbox.stage_exact(list(_allowlist))` (`engine.py:1757`) goes through `RunSandbox.stage_exact` (`sandbox.py:1199-1215`) to `LocalWorkspace.stage_exact`, which is ONE `self._git("add", "--force", "--", *paths)` (`local.py:1426-1434`). `_git` runs `subprocess.run(..., check=True, capture_output=True)` (`local.py:385-404`), so a non-zero exit is a `CalledProcessError`.
5. Git exits 128 for a pathspec that matches nothing on disk and nothing in the index, and stages nothing (analysis-01, case A). When the family already tracks `.chain/<output>` from an earlier snapshot, `git add` accepts the path and stages its deletion instead, silently (analysis-01 case B; probe `[C]`). So the failure belongs to the first terminal pass of a family whose output never reached `.chain/`, which is every run in the register's evidence.
6. `build_flat_payload` catches it and logs `logger.warning("build_flat_payload: stage_exact failed for run=%s", run_id, exc_info=True)` (`engine.py:1761-1766`): a full traceback at WARN, above the production INFO threshold. The `DEBUG` line before it is dev-only.

### Why nothing is lost, and why it is still worth fixing

- `finalize_terminal_run` Step 5 calls `build_flat_payload` (`engine.py:2335`) and, because the payload is `built`, not `materialized` and the deliverable is declared, replaces it with `build_metadata_only_snapshot(..., "output_unmaterializable")` (`engine.py:2341-2353`). That function begins with `reset_index()` (`engine.py:1879-1889`), untracks every other `.chain/` path (`:1903-1926`) and stages `.chain/summary.md` alone (`:1977-1988`). Whatever `build_flat_payload` staged, or failed to stage, is discarded. Probe `[D]`: the finalizer record and the committed `.chain/` tree are identical with and without the prune.
- It is still a defect. A handled, designed state (`output_not_materialized`) produces an error traceback at WARN on the first terminal pass of every such run. The `Payload` it returns names a file it did not stage, while its docstring says "exactly three ... paths that were force-staged" (`engine.py:381-383`). And the same unreconciled allowlist is what makes [ISS-1178](20261009-1659-ISS-1178.md) possible.

### Blast radius

- Writer: `build_flat_payload` has one production caller, `finalize_terminal_run` Step 5 (`engine.py:2335`), which is reached from two places: the run-end `finally` (`engine.py:7676`) and the clarify-cancel branch (`engine.py:5635`). Other mentions are tests and a comment (`kernel_services.py:1955`). The legacy `_write_chain_payload` (`engine.py:1115`) has no caller outside tests and does not stage.
- Consumers of the allowlist. Inside the function: the stale reconciliation (`engine.py:1739`, it compares tracked paths with `_allowlist`), `stage_exact` (`:1757`) and the returned `Payload` (`:1769`). Outside it: the snapshot commit's `force_add=_built_payload.allowlist` (`engine.py:2423`, and the retry at `:2470`), which does one `git add --force` per path inside `commit_in_sandbox` and turns any failure into `blocked / staging_failed` (`engine.py:616-638`). That second consumer is not reached with the phantom output on this branch, because the metadata-only payload has replaced it; it is reached by the sibling.
- Every way the output can fail: file absent, copy raising, `streamed_text` with an empty stream, `ppt` with an empty stream, `serialized_sandbox` with nothing written. Probe `[F]`: all five warn today, and all five are cured by the same prune. That is why the prune must key on `_materialized`, after the whole `try / except`, and not sit in the `else` (the `except` path leaves `_materialized` False too).
- The other `stage_exact` caller, `build_metadata_only_snapshot` (`engine.py:1979`), stages only the file it has just written and returns early when that write fails: not affected.
- Environments: all (a WARN with `exc_info`); the dev data above.

### Where the fix belongs

In `build_flat_payload`, one reconcile keyed on the flag that already decides chainability, placed after the output-copy `try / except` (after `engine.py:1659`):

```python
if _output_basename and not _materialized:
    _allowlist = _allowlist - {f".chain/{_output_basename}"}
```

It is the only place that knows what was written, it mirrors the text-form precedent a few lines below it, and it repairs all three allowlist consumers at once. The stale reconciliation then untracks a previously tracked `.chain/<output>` (probe `[G]`: the same staged deletion `git add` produced in `[C]`). `stage_exact` is given only paths that exist. The returned `Payload.allowlist` is true. Probe `[B]`, `[D]`, `[F]` and `[G]` ran exactly this, in memory (the function's own source with the two lines inserted, `exec`'d into the engine module), with no source edited.

Shapes considered and why not:

- Make `stage_exact` skip absent paths: `RunSandbox.stage_exact` documents the opposite on purpose ("A staging failure must be visible", `sandbox.py:1203-1204`), and `commit_in_sandbox` depends on a failed add being `staging_failed` (`engine.py:625-638`). It would also hide the sibling.
- Skip the `stage_exact` call when the output is unmaterialized: leaves `Payload.allowlist` naming a file that is not there, and `build_flat_payload` stops staging the files it did write.
- Filter the whole allowlist by `is_file()` after the swap: also removes [ISS-1178](20261009-1659-ISS-1178.md)'s phantom entries, but turns "degraded / payload_blocked" into "completed, tagged, chainable payload with two of three files" for a logs or summary write failure, which is the owner's call (that card). Keep it out of this fix.

- Do not change the strings the finalizer keys on: `no_declared_output` is compared literally at `engine.py:2387`; `output_not_materialized` becomes `output_unmaterializable` through the metadata-only swap.
