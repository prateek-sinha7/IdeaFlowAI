## Bug

Validates `BUG-20260828-104200-workflows-nonexistent-r2` in `bug-hunter/ledger.md`.

## Reproduction (3/3, cycle 1 first showed it, identical on 2 and 3)

Every cycle from a cold start (fresh navigation, session already authenticated as `qa-admin`,
light theme, default viewport):

1. Navigate directly to `http://localhost:3000/workflows/<bad-id>/canvas` — tried both
   `00000000-0000-0000-0000-000000000000` (cycles 1, 2) and `totally-bogus-id-12345` (cycle 3);
   both dead-link id shapes reproduce identically.
2. Confirm the composer header reads "0 agents", "0 review gates", canvas shows only the
   "Brief" node — `GET /api/workflows/<bad-id>` 404s, so no real workflow was ever fetched.
3. Type any brief into "Brief description".
4. Click "Run once".
5. Observe: no error, no warning. The app navigates to `/runs/<new-id>/stream` and a real
   9-agent pipeline begins executing (Market Research Agent, Strategy Analysis Agent, Roadmap
   Planning Agent, Security Audit Agent, Test Strategy Agent, Performance Optimization Agent,
   Documentation Agent, Executive Reporting Agent, Task List Planner).
6. `GET /api/runs/<new-id>` confirms `agent_count: 9`, `type: "custom"`, `status: "generating"`/`"planning"`.

Validator run ids (all stopped immediately after confirming `agent_count: 9` via the API, to
limit Bedrock spend beyond what was needed to prove the defect):
- Cycle 1: `5ea741be-481d-45ff-af6d-3ab174d45378` — stopped after 1/9 agents, 30.4K tokens.
- Cycle 2: `e757c2a0-977e-4982-a2bb-11e2a9e3dd63` — stopped at `status: "planning"`, before any
  agent token spend.
- Cycle 3: `b5841a65-52c4-48f9-981f-11a02e542953` (via the `totally-bogus-id-12345` variant) —
  stopped at `status: "planning"`, before any agent token spend.

## Root cause

`handleRunOnce` in `frontend/src/components/workflow/composer/ComposerPage.tsx:786-944`
computes `currentIds = pipelineAgents.map((a) => a.id)` (line 920). On the dead-link canvas,
`pipelineAgents` is the empty array the composer initialized because
`GET /api/workflows/<bad-id>` 404'd, so `currentIds` is `[]`. `dispatchType` resolves to
`"custom"` (`resolveDispatchType(pipelineAgents, "custom")`, line 802 — the comment there notes
it short-circuits to the literal `"custom"` since ComposerPage never means anything else). The
call at line 939 is `onRun(dispatchType, brief, currentIds, extraParams)` — i.e. `onRun("custom",
brief, [], ...)`.

On the backend, `backend/app/api/run_commands.py:2692-2726` (the launch handler's
agent-resolution block):

```python
agent_ids = body.agent_ids
agents = None
if launch_source is not LaunchSource.USER_WORKFLOW_MANIFEST:
    if agent_ids:
        ...  # allow-list against the given ids
    else:
        agents = get_pipeline_agents(base_pipeline_type)
```

`agent_ids` arrives as `[]` (an empty JSON array), which is falsy in Python — so the `if
agent_ids:` branch is skipped and the `else` fires: `get_pipeline_agents(base_pipeline_type)`
with `base_pipeline_type == "custom"`. `PIPELINE_AGENTS["custom"]`
(`backend/agents/registry.py:115`, auto-discovered from every `AGENT.md` whose
`pipeline_type: custom`) is the full custom-agent utility pool — the same 9 agents seen firing
in every reproduction (Market Research Agent, Strategy Analysis Agent, Roadmap Planning Agent,
Security Audit Agent, Test Strategy Agent, Performance Optimization Agent, Documentation Agent,
Executive Reporting Agent, Task List Planner).

The `else` branch's intent is legitimate for a genuinely built-in pipeline launch (e.g. `ppt`,
`prototype`) where an empty `agent_ids` correctly means "use the registry's fixed membership for
this type" — that path is exercised correctly elsewhere. The bug is that the SAME fallback fires
for `pipeline_type: "custom"` when `agent_ids` is empty for the opposite reason: not because the
caller wants the type's default roster, but because the composer had **zero** agents to send.
Nothing distinguishes "custom with no agents configured" from "built-in with no agent_ids sent
by convention" at this call site — an empty list is structurally identical to "no roster given"
in both cases, so the composer's genuinely-empty 0-agent state is silently reinterpreted as "run
custom's full default pool."

## Expected vs actual

**Expected:** "Run once" with `pipelineAgents.length === 0` should either be disabled/blocked in
the composer before the request is even sent, or the backend should reject a `pipeline_type:
"custom"` launch with `agent_ids: []` (422/400 — no agents selected) rather than silently
substituting the full custom-agent pool.

**Actual:** `agent_ids: []` for `pipeline_type: "custom"` is indistinguishable, at
`run_commands.py:2695`, from "caller relies on registry default" and falls through to
`get_pipeline_agents("custom")`, launching all 9 custom-pool agents against real Bedrock with no
UI indication this would happen.
