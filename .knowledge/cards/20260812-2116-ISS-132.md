# ISS-132

## Title

**The task-loop sibling of ISS-097: ticking a task-loop agent opens ONE GATE PER TASK.** Same root cause — `_should_gate` is per-INVOCATION on `spec.id` while `gate_agent_ids` is a per-STEP selection — and the task loop is the other strategy that turns one step into N invocations of one agent id. Verified at `eb12bc7e`: `task_loop.py` calls `runner.run_agent(step, ctx, task_number=..., ...)` with NO `invocation_gated`, so it takes the default `True`, and unlike `run_fanout` it FORWARDS every event (`yield event`). **So this is the visible, answerable cousin, not a hang**: N sequential gates, all on the one gate key `f"{run_id}:{agent_id}"`, each surfacing properly on the wire and each requiring a human click. Annoying and almost certainly not what the user meant by ticking one box, but nothing is lost and nothing is invisible. Reachable on a live workflow: `prototype-build` is in the frontend agent library (`AgentLibraryData.ts:25`) with `gate: null`, so it is tickable in the launch wizard's gate picker. **FIX-242 deliberately left this alone.** The mechanism it added (`invocation_gated=False`) would close this in one line at the task-loop call site, but whether a per-task review gate should be offered AT ALL is a product decision — some users may genuinely want to review each task of a build — whereas the fan-out case had no defensible reading because the gates were unreachable. Note ISS-090 already records that FIX-228 handles the task-loop redo case defensively inside `_consume_redo`, so the interaction is partly known.

## Source / Evidence

Found 2026-08-12 by the ISS-097 investigation while sweeping for siblings of the invocation-vs-step confusion, and named in the FIX-242 plan's out-of-scope list. Fix shape, once the product question is answered: either pass `invocation_gated=False` at the `task_loop.py` `run_agent` call (suppress entirely, matching fan-out), or gate only the FINAL task, or leave as-is and change the gate picker's copy so "pauses after they finish" is not a promise the task loop breaks N times.

## Validation (QA-KB-030, 2026-10-01)

Reproduced 3/3 cold (Static check, no browser): `TaskLoopStrategy` declares no `runs_agent_inline` (`getattr(..., '<undeclared>')` printed `<undeclared>` each time). `engine.py:11474` defaults an undeclared strategy to `True`, so the step-boundary dedupe at `engine.py:6309` (`inline_gated=self._should_gate(...) and _runs_agent_inline`) predicts an inline gate. But `task_loop.py:360` passes `invocation_gated=False`, so the inline gate never fires and the step's declared `gates:[human]` is skipped: no gate at all. Siblings `fanout_batch.py:70` and `wave_scheduler.py:245` already declare `runs_agent_inline = False`. Fix: same class attribute on `TaskLoopStrategy` (`task_loop.py` ~line 149). Evidence: `evidence/qa-kb-030/01-validate-attempts-runs-agent-inline-undeclared.txt`.

## Analysis (QA-KB-030, 2026-10-01)

### Where this card stands

The "ONE GATE PER TASK" symptom in the body above was closed on 2026-09-04 by `ff37f777a` ("Option A" in the escalation register: `.kiro/bug-fix-workflow/escalated/README.md:26`, `escalated/15-backend-other.md:22-32`): `task_loop.py:360` now passes `invocation_gated=False`. This card stayed `open` and its summary went stale. What is still broken is the half of the fan-out fix that commit did not copy. This section is the live root cause; the history above is left as written.

### ROOT CAUSE (CONFIRMED)

`TaskLoopStrategy` opts every `run_agent` call out of the inline review gate but does not declare the matching step-scope fact. Two facts, kept in two places, have to agree and do not:

1. Invocation scope. `task_loop.py:360` `invocation_gated=False` -> `kernel_services.py:2064` -> `_run_agent` -> `_should_gate(spec, ectx, invocation_gated=False)` returns `invocation_gated and selected` = False (`engine.py:11451`) at the three inline gate sites (`engine.py:9263`, `:9422`, `:10904`). The inline gate never opens for a task-loop step.
2. Step scope. The step-boundary dedupe predicts the inline gate instead of observing it: `inline_gated = self._should_gate(spec, ectx) and _runs_agent_inline` (`engine.py:6309` pre-step, `:6721` post-step), where `_runs_agent_inline` comes from `_strategy_runs_agent_inline` as `getattr(strategy, "runs_agent_inline", True)` (`engine.py:11474`). `TaskLoopStrategy` declares nothing (class body `task_loop.py:149-162`), so the kernel reads `True`. `fanout_batch.py:70` and `wave_scheduler.py:245` declare `False`.

With the agent ticked in `gate_agent_ids`, `_should_gate(spec, ectx)` is True, so `inline_gated` is True and `_evaluate_gates` skips the declared `human` / `before-human` gate (WR-02 dedupe, `engine.py:11702-11716`, which logs "inline review gate already covers this agent" - false for a task-loop step). Net effect: zero review gates, no event, no error, and the wizard still says "1 agent pauses for review".

### How it slipped

- [FIX-424](20260831-1652-FIX-424.md) (2026-08-31, commit `835793a99`) added `runs_agent_inline` for fan-out and recorded task_loop as "genuinely does run the step's agent inline, so `runs_agent_inline` is `True` for it and nothing here changes it".
- `ff37f777a` (2026-09-04) then made that premise false by suppressing the inline gate per task. It mirrored only the call-site half of [ISS-097](20260812-1153-ISS-097.md) / [FIX-242](20260812-2116-FIX-242.md) ("engine.py not touched"), not the step-scope half FIX-424 had to add for fan-out ([ISS-131](20260812-2116-ISS-131.md) is the fan-out twin of this defect). No test pins either half for task_loop: `tests/unit/agents/test_strategies.py:168` `_FakeRunner.run_agent` accepts `invocation_gated` (`:177`) and drops it.

### Reachability (CONFIRMED by reading each hop; run level proven offline below)

Ticking "Build Agent" under Review gates in either wizard sends BOTH inputs the dedupe misreads. `ReviewGatesSection.tsx:180-191` (`toggle` -> `withHumanGate`, [ISS-247](20260828-1637-ISS-247.md)) writes `selections[agent].gates=["human"]` and reports the id into `gate_agent_ids`; it is mounted at `IdeaInputPage.tsx:2199` and `LaunchWizard.tsx:1342`, and the launch payload carries both (`IdeaInputPage.tsx:1622`, `:1624`). The engine merges the declared gate onto the manifest step by agent id (`engine.py:14173-14174`) and leaves the manifest's `strategy: task_loop` alone (`sel.get("strategy")` is falsy, `:14248`). The shipped `prototype`, `prototype_large_revision` and `prototype_feature_revision` workflows all run `prototype-build` on `task_loop` with `gates: []`; a composed `prototype-build` gets `task_loop` from `withPrototypeTaskLoop` (`IdeaInputPage.tsx:1609`); the composer also offers "One at a time - shared file" = `task_loop` (`CanvasConfigRail.tsx:1578`). The API layer is not affected: it reads armed gates (`run_commands.py:162` `_gate_is_pending`), not a prediction.

As shipped: 0 gates opened. With the declaration: 1 (once per step, not per task). `pipeline_complete=True` and 0 errors in both.

### BLAST RADIUS (CONFIRMED by grep)

- Readers of the flag: only `_strategy_runs_agent_inline` (`engine.py:11453-11474`) -> one local (`:6280`) -> two reads (`:6309`, `:6721`). One attribute covers pre-step `before-human` and post-step `human`.
- Strategies (all five registered): single_shot and parallel_group are correctly `True` (each calls `run_agent` once with the default gate; parallel_group's children are `run_fanout` workers). fanout_batch and wave_scheduler are correctly `False`. task_loop is the only wrong one. No other strategy passes `invocation_gated=False`: the only call sites are `task_loop.py:360`, `kernel_services.py:1125` (run_merge_agent) and `:1310` (run_worker), the latter two reachable only through `run_fanout`.
- Workflows on task_loop: `prototype`, `prototype_large_revision`, `prototype_feature_revision`, composed `prototype-build`, fixture `sc001_task_loop`. No name branch is involved, so one declaration covers them all.
- No existing test drives a ticked, declared-gate task_loop step (task_loop tests pass `gate_agent_ids=[]`; the `sample_wave*` resume tests are wave_scheduler), so the fix flips no current expectation. INV-3 holds: a step with no declared human gate, or an unticked agent, is byte-identical.

### FIX - the agreed minimal fix is ACCEPTED

Add `runs_agent_inline = False` to `TaskLoopStrategy` (`task_loop.py`, directly under `name = "task_loop"` at :157, same placement as `fanout_batch.py:70`), with a comment citing ISS-132 / `ff37f777a`. The comment must say why it is `False` although `run` calls `run_agent`: every call opts out of the inline gate, so the inline review gate can never cover the step and the declared gate has to run. No `engine.py` edit: the kernel already reads the flag generically off the resolved capability, which is what keeps INV-1 / SC-001 intact ([FIX-424](20260831-1652-FIX-424.md) locked constraint: "The kernel never infers inline-dispatch from a strategy NAME"). Optional companion, comment only: reword `capabilities/base.py:48-55` so the flag reads "can the inline review gate cover this step's own agent", since task_loop is the first strategy that dispatches inline yet declares `False`.

Why not the alternatives:
- Reverting `invocation_gated=False` brings back N gates per task; the recorded decision (Option A) chose to suppress them.
- Gating only the final task (this card's other option) would keep `runs_agent_inline=True` and make the INLINE gate the single review. Not what was decided, and not needed.
- A strategy-name branch in `_strategy_runs_agent_inline` or `_evaluate_gates` is exactly what the FIX-424 locked constraint forbids.

Result after the fix: ticking the build agent yields exactly one review, after the whole task loop, on the declared post-step `human` gate (payload `results[-1]["output"]`, refreshed at `engine.py:6564`), which is what the picker copy ("pause ... after they finish") promises.

Overlap with QA-KB-024 / [ISS-685](20260918-ISS-685.md): that fix edits `fanout_batch.py` (~L92 `parser.parse`) and the resume reconcilers in `engine.py` (~L14889, ~L14971, ~L15202). This fix edits only `task_loop.py` (one class attribute) and optionally the `base.py` comment; it needs no `engine.py` line and no `fanout_batch.py` line. The hunks are disjoint. Add the new tests as new functions or a new file rather than reshaping shared fixtures in `test_strategies.py`.
