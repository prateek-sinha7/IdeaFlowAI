## Symptom

```
TestCreateRevisionEventOrdering::test_create_revision_returns_run_id
  AssertionError: Expected 200, got 500:
TestTierToPipelineMapping::test_tier_drives_effective_target[small-prototype_output]
  Failed: Unexpected status 500:
… and 9 more, plus 10 × RuntimeError: This portal is not running
```

The 10 errors are anyio portal teardown after the failing request — fix the
500 and they should go with it. Treat this as **one** defect with 21 witnesses,
the largest single cluster in the backend suite.

## Provenance

Pre-existing on `feat/conditional-gates`. Running this file against
`602296cc8` in a detached worktree reproduces the identical count — the merge
did not cause it. It was invisible until
[FIX-414](20260831-0110-FIX-414.md) stopped 3734 tests erroring at setup.

## Root cause (5-fixer, 2026-08-31) — NOT an endpoint defect

Two stacked causes, neither of them a production fault:

1. **The 500 is the ISS-102 offline live-model guard.** `create_revision`
   (`backend/app/api/run_commands.py:3701`) calls `_classify_revision_tier`,
   which builds a real provider client at
   `backend/app/api/run_commands.py:3638`
   (`llm = build_model(model_id, max_tokens=256, disable_thinking=True)`).
   The autouse guard at `backend/tests/conftest.py:265` replaces
   `ChatBedrockConverse.__init__` and raises `LiveModelClientConstructed`,
   which derives from **`BaseException` on purpose** so no production
   `except Exception` can swallow it. `_classify_revision_tier`'s own
   `except Exception` arm (`run_commands.py:3657`) therefore does not catch it,
   it escapes the handler, Starlette returns 500 and the anyio portal dies —
   which is the 10 `This portal is not running` teardown errors.
   Observed traceback: `run_commands.py:3701` -> `:3638` ->
   `model_factory.py:220` -> `tests/conftest.py:265`.
   In production the same line constructs a real client and any failure is
   caught by that `except Exception`, degrading to tier `small` and returning
   200 — the endpoint has no 500 to fix. The guard's own message names the
   remedy: *"(a) patch the construction seam in the test"*.

2. **Seven of the eleven assertions encode a contract production deleted.**
   The file is written against the pre-`revision-pipeline-refactor` design in
   which the app layer called `app.agents.revision_analyzer.run_analyzer` and
   forwarded an `analyzer_solution` kwarg. That call is gone: `run_analyzer`
   has **zero production callers**
   (`grep -rn "run_analyzer" backend/app backend/agents --include="*.py"` hits
   only the comment at `run_commands.py:1446`, "no app-layer run_analyzer call
   needed here"), the kwarg was removed on purpose (`run_commands.py:3745`,
   "analyzer_solution kwarg removed — engine populates ectx.analyzer_solution
   via the produces_solution_plan post-step hook") and the analyzer is now
   manifest step 0 with `extra_agent_count=0` (`run_commands.py:3731`).
   Every `patch.object(ra, "run_analyzer", ...)` in this file is inert.

## Evidence — probe run, no application code changed

Stubbing only the construction seam the tests miss (an autouse fixture

## Why this was escalated instead of fixed

Nothing here is fixable from the application side:

- Widening `_classify_revision_tier` to `except BaseException` would swallow
  the ISS-102 guard (and `asyncio.CancelledError`) — the exact hole ISS-102 and
  `test_iss118_construct_only_exemptions.py` exist to keep closed.
- Adding the nodeids to `_CONSTRUCTS_BUT_NEVER_INVOKES` is barred by that same
  test — and would be false, the classifier does invoke.
- Making the remaining 7 green requires re-adding the app-layer `run_analyzer`
  call and the `analyzer_solution` kwarg, i.e. reverting
  `revision-pipeline-refactor` in production to match a stale test.

The resolution is a **test rewrite against the post-refactor contract** —
stub the `build_model`/classifier seam, and re-point or retire the 7
`run_analyzer` assertions onto the engine's `produces_solution_plan` step 0.
That is 4-test-writer work, and "the refactor is the intended end state" is a
product call this fixer will not make unilaterally, especially while
[ISS-631](20260831-0115-ISS-631.md) still reports roster/manifest drift across
all three revision pipelines.

**Related dead code (mentioned, not deleted):**
`backend/app/agents/revision_analyzer.py` (`run_analyzer`, 11 KB) now has no
production caller at all.
