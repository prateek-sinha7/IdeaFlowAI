## What was wrong

On a completed run's Preview tab (`/runs/b9feac1c-ec21-4531-8ba7-bb391786993e`),
every chat bubble's clock label re-derived itself to the browser's current time on
each page load. A message genuinely sent at 09:51 AM read 09:52 AM after one
reload and 09:56 AM after the next — validated 3/3 by
[ISS-358](20260828-2118-ISS-358.md) (09:15/09:16/09:17 PM across three cold
navigations), each reading exactly that reload's wall clock. Register entry
`BUG-20260828-095700-runs-id-chat-timestamp` (`bug-hunter/ledger.md`).

## Root cause

Two halves, one missing field.

**Frontend fold.** `frontend/src/hooks/useRunChat.ts` `upsertUserMessage` (`:354`
pre-change) and `upsertNarratorMessage` (`:393`) built the folded `ChatMessage`
with `createdAt: new Date().toISOString()` unconditionally. That is the "create"
branch EVERY replayed historical frame takes — `seedTranscript` (`:702-725`)
clears `seenRef`/`lastSeqRef` and resets `messages` to `[]` before folding, so no
prior bubble survives to merge into. `upsertNarratorMessage` additionally
clobbered an already-settled value on re-fold: its merge branch spread
`{ ...prev[idx], ...msg }` with `msg.createdAt` freshly minted.
`frontend/src/components/chat/MessageBubble.tsx:189` then rendered that fabricated
value, and is the ONLY consumer of `ChatMessage.createdAt` in the frontend
(re-confirmed by grep before editing: the other `.createdAt` reads are
`run.createdAt` / `pipelineState.createdAt` / `notification.createdAt`, different
types).

**Backend gap — and it was on BOTH transports.** There was no real send time to
prefer. `run_events.created_at` (`backend/app/models/run_event.py:72`) is NOT NULL
and stamped on every durable row, but neither durable reader projected it:
`GET /api/runs/{id}/events` (`backend/app/api/runs.py:1080-1093`) returned only
`{seq, event_id, type, payload_json}`, and the SSE attach replay
(`backend/app/api/run_stream.py:232-245`) yielded
`{**payload_json, event_id, seq}`. The app-layer chat writers persist no timestamp
in the payload either (`backend/app/api/run_commands.py:1050-1060`), so for a
`chat_message`/`chat_reply` the row column is the ONLY send time that exists.

Blast radius re-confirmed by grep before editing and still holds: the defective
fold is reached from every `seedRunChatTranscript` / `appendRunChatFrames` call
site in `frontend/src/app/[...view]/page.tsx` (`:1507`, `:2656`, `:3012`, `:3430`,
`:3451`, `:3466`) — cold reload of a completed run, history reopen, revision/family
reopen, and `handleSwitchToLiveRun`'s still-generating-run switch
([ISS-595](20260829-0120-ISS-595.md)) — plus the SSE tail, since `useRunChat` is
subscribed to the live frame stream (`page.tsx:2295`, `subscribe: chatSubscribe`)
and that stream replays the same durable rows on attach.

## What changed and why there

**`backend/app/api/runs.py`** — `get_run_events` projects `"created_at":
_iso_utc(r.created_at)`, and a module-level `_iso_utc` is added beside the response
models as the free-function twin of their `_serialize_dt` field serializer (for
plain-dict projections that have no Pydantic model to hang one on). Fixed at this
shared projection rather than per-consumer because it supplies a real timestamp for
EVERY event type replayed this way, past and future — the shape
[ISS-413](20260828-2357-ISS-413.md) already proposed as its option 1. UTC-promoted
for the KAN-113 reason [FIX-354](20260828-2357-FIX-354.md) promoted its own stamp:
a naive `isoformat()` is `Date.parse`'d as LOCAL time in the browser, which is the
very class of defect being fixed.

**`backend/app/api/run_stream.py`** — the SSE attach replay merges the same
`_iso_utc(r.created_at)` into the frame body. The file's own comment already
requires this loop to mirror "the REST twin ... so both durable readers key
identically"; projecting the column on one transport only would make a replayed
frame's shape depend on which transport delivered it, and the consumer is a single
reducer that cannot tell them apart. The value is merged FIRST, so a
payload-embedded timestamp still wins — this is what stops a resumed run's row
write time clobbering FIX-354's `pipeline_start` stamp of the RUN's `created_at`.
Imported deferred (inside the generator), matching this file's existing style for
`app.*` imports, so no new module-level edge is created.

**`frontend/src/lib/api.ts`** — `RunEventRow` gains an optional `created_at`, and
`getRunEvents` merges it into `DurableFrame.data` with the same first-position
fallback ordering as the SSE twin. `event_id`/`seq` keep their merged-LAST,
column-wins position (BUG-018) — unchanged.

**`frontend/src/hooks/useRunChat.ts`** — one new `foldedCreatedAt(data, existing?)`
helper: prefer `data.created_at`, then an existing bubble's already-settled value,
and only fall back to the clock for a genuinely live frame carrying neither (where
receipt time IS the send time). Both upserts call it. In `upsertNarratorMessage`
the `findIndex` is hoisted three lines above the message literal so the merge
branch can pass the existing value in — that is the whole of the reordering.

`MessageBubble.tsx:189` is untouched: once `createdAt` is a real ISO string it
renders correctly as-is.

## One test assertion widened (direction: test follows card, not code follows test)

`backend/tests/unit/test_sse_stream.py::TestReplay::test_replay_from_cursor_projects_seq_frames`
asserted the replayed body by exact dict equality against the OLD closed key set.
The card asks for a new key on that body, so the assertion was widened to include
it — it remains a strict exact-dict compare (it still fails if anything else
appears), and the expected `created_at` is read back off the row and promoted
explicitly rather than through the endpoint's own `_iso_utc`, so the tz half is
pinned independently rather than tautologically. No application behaviour was
changed to satisfy a test. The wire-parity guard (`assert_wire_parity`, the 29-01
projection contract) passed untouched, as did the other 52 tests in that file;
`created_at` is already in `_VOLATILE_STRIP_KEYS`
(`backend/tests/agents/characterization/_normalize.py`, added by FIX-354), which is
why the characterization goldens are unaffected.
