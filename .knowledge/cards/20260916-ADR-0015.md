# ADR-0015

## Decision

Split pull-request CI into an unprivileged evaluator and a trusted default-branch finalizer.
`ci.yml` evaluates pull-request source and emits SHA-bound evidence without secret-bearing or
status-writing permissions. `ci-authoritative.yml`, triggered from trusted default-branch content,
attests the evaluator run and exact head, uses PR source only as read-only scanner input, performs
secret-bearing Sonar analysis, and is the sole publisher of `ci-required`.

## Context

Pull-request source can be fork-controlled. Executing its workflow configuration, actions, or
scripts with Sonar credentials or a write-scoped token would let untrusted code influence a
protected status. Separately, a status published for a superseded SHA is misleading even if the
old run succeeded.

## Consequences

- Required-status rulesets must require the one finalizer-published context, not duplicate
  evaluator statuses.
- Missing, malformed, stale, or non-success evidence is a failed finalization, not a skipped
  signal.
- The finalizer must re-check that the evaluated SHA is still an open pull request head before it
  writes a status.
- CI policy belongs under `backend/tools/ci` and workflow support files, not the agent runtime.
