## Register entry

Root of register entry **QA-PS-008** (`LEDGER.md`) — "Version dropdown shows
inflated version list and preview fails for all non-live versions (/runs/{id})".

## Reproduction — 3/3, cycle 1

Reproduced on the FIRST cold-start attempt and again identically on cycles 2 and 3;
no narrowing was needed.

1. Sign in as `qa-admin@flowinqa.com` (enterprise/admin tier).
2. Cold-navigate directly to `/runs/23bd9c67-e239-4979-b14a-cb78222795e8` (a
   Prototype Revision run — v2, one revision on top of parent
   `2708dbf1-50d0-465d-9bed-56b651ea1abf`).
3. Click the version chip (`v1 ▾` in RunHeader — the chip itself mislabels the
   *live* run as `v1` even though this is the v2/revision run; a second, separate
   defect from the same header, not chased further here).
4. Open the "Select a version" listbox.

**Actual (cycle 1, repeated verbatim on cycles 2 and 3, and on both the parent
run and the revision run):**

```
Latest (live)
v0.2.0
v0.0.2
v0.0.1
pre-rebase-safety
pre-fixes-reset
deploy-prod-20260603-014226
deploy-prod-20260603-012557
```

Eight entries for a run family that has exactly two real members (v1 parent,
v2 revision). The six non-"Latest" entries are IDENTICAL on both runs tested —
they are not derived from either run's own history at all.

5. Select any tag other than "Latest (live)" (`v0.2.0` and `v0.0.1` both tried).

**Actual:** the header shows `Viewing <tag> · read-only` and the Preview panel
shows `Loading <tag>…` and never leaves that state (confirmed at 5-6s of
waiting on each of the three cycles). `browser_network_requests` shows
`GET /api/runs/{id}/sandbox/refs` and `GET /api/runs/{id}/sandbox` fire, but
**no** `GET /api/runs/{id}/sandbox/{file}?ref=<tag>` request is ever issued —
the ref-scoped fetch never even starts.

**Expected:** the dropdown lists only this run family's own versions (v1, v2 —
2 entries), and selecting any of them loads that version's deliverable in
Preview.

## Root cause — CONFIRMED, two independent defects in the same flow

### Defect 1 — inflated list: `list_tags()` is repo-wide, not family-scoped

`backend/app/api/run_files.py:644-669` (`GET /{run_id}/sandbox/refs`) calls
`sandbox.list_tags()` and returns the result verbatim as `refs`.

`LocalWorkspace.list_tags()` (`backend/app/agents/runtime/local.py:875-891`):

```python
def list_tags(self) -> list[str]:
    try:
        out = self._git("tag", "--list")
        tags = sorted(t.strip() for t in out.splitlines() if t.strip())
        return tags
    except Exception:
        return []
```

`git tag --list` returns **every tag reachable in the sandbox's git repository**,
not just tags this run family created via `create_tag()` (local.py:858-873).
Because the sandbox's working copy carries the deployment/release tag history
of the underlying repo (`v0.2.0`, `v0.0.2`, `v0.0.1`, `pre-rebase-safety`,
`pre-fixes-reset`, `deploy-prod-20260603-014226`, `deploy-prod-20260603-012557`),
every one of those leaks into the version picker of every run, verbatim and
identical run to run — confirmed by comparing the parent run and the revision
run, which returned byte-identical tag lists despite being different run
families.

### Defect 2 — Preview hangs forever on a leaked (non-family) tag

Frontend `RunHeader.tsx`'s `VersionMenu` renders whatever `tags` it is given
with no filtering against the run's actual `FamilyMember.git_tag` set — it
trusts the backend list completely (comment at RunHeader.tsx:34-36 documents
this: "the git tags fetched from GET /api/runs/{id}/sandbox/refs by the
caller").

Selecting a leaked tag routes through `PreviewPanel.tsx`'s
`handleVersionMenuSelect` → `FIX-516`'s fallback branch (no `FamilyMember`
matches the tag, since it isn't one): `intendedSandboxRef.current = null;
setSandboxSelectedRef(tag);` — this sets only the sandbox ref, never
`viewingVersion`.

The ref-scoped deliverable fetch that would show something in Preview is
gated on `deliverableFile` (`PreviewPanel.tsx:1257`:
`if (!sandboxSelectedRef || !activeRunId || !deliverableFile) return;`).
`deliverableFile` is resolved by a separate effect (`PreviewPanel.tsx:1190-1248`)
against the run's **own live-tree** deliverable name — it never even considers
the pinned ref. When that resolution comes back empty for whatever reason
(observed here: no request for the file ever fires), the ref-scoped effect at
line 1257 never runs, so `getRunSandboxFile` is never called — no network
request is issued at all — and `RefVersionPreview`'s `Loading {tag}…` text
(PreviewPanel.tsx:339) has nothing to ever resolve it. The code's own comment
at PreviewPanel.tsx:1219-1222 names this exact failure shape ("leaving
'Loading {tag}…' forever with no request ever issued") as a previously-seen
bug; this repro shows the fix at that comment does not cover the case of a
tag with no matching `FamilyMember` at all — which Defect 1 guarantees will
happen for every leaked repo tag.

## Expected vs actual

- **Expected:** `refs` in `GET /api/runs/{id}/sandbox/refs` = only tags this
  run family created (`create_tag()` calls for this family), and any listed
  tag resolves in Preview.
- **Actual:** `refs` = every tag in the sandbox git repo, and any tag not
  backed by a `FamilyMember` hangs Preview indefinitely with zero network
  activity.

## Fix direction (not applied — issue only)

Defect 1: scope `list_tags()` (or its caller) to tags this run family actually
created — e.g. a name-prefix convention checked at creation time in
`create_tag()`, or cross-referencing the returned tags against the family's
`FamilyMember.git_tag` column server-side before returning `refs`.

Defect 2 is a direct consequence of Defect 1 today (no non-family tag should
ever reach the menu), but is independently fragile: `handleVersionMenuSelect`'s
fallback path sets `sandboxSelectedRef` for a tag with no resolvable
deliverable and no user-visible error/timeout — worth a fallback error state
regardless of whether Defect 1 is fixed.

## Analysis missed (2026-09-17)

- This card blamed the sandbox's own git repo for holding deploy/release tags no family member
  created, and proposed filtering `list_tags()` against the family's `WorkflowRun.git_tag`
  values. That is not what happened.
- The repro family's chain-root sandbox is an empty directory with no `.git` of its own.
  `LocalWorkspace` runs git with only `cwd` set (`backend/app/agents/runtime/local.py:372-390`,
  `:1062`, `:1081`, `:1104`), so git searches upward and finds the Flowin source checkout itself
  (`RUNS_ROOT=../runs` is inside it) — the "versions" QA saw are the project repo's own tags.
- `RunSandbox.list_tags` (`sandbox.py:896`) checks only the `has_git` flag, never whether `.git`
  exists. See [ESCALATIONS.md#qa-ps-008](../../ESCALATIONS.md#qa-ps-008) for the full trace,
  caller list, and fix-location options.

**Superseded by [ISS-671](20260917-1345-ISS-671.md)**, which carries the corrected root
cause (git's upward repository search, not a sandbox-owned repo) and the full caller list.
Defect 2 (the Preview hang) was never wrong and is restated, re-verified, in ISS-671.
