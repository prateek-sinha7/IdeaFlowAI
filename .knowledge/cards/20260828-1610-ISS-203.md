## Why the root cause implies this

[ISS-206](20260828-1609-ISS-206.md)'s two mechanisms (`needsFullManifest()` never consulting
`runConfig`, and `runConfig` never resyncing after the built-in's async fetch resolves) are
generic to `ComposerPage.tsx` — nothing in either mechanism references `ppt` by name or by
strategy value. Any built-in opened via `/workflows/{type}/canvas`
(`DashboardLayout.tsx:1453-1459`, `handleOpenInCanvas`, reachable for every `WorkflowType` except
`custom` — the only member of `COMPOSER_ENABLED_TYPES`, `DashboardLayout.tsx:353-355`) whose
declared `deliverable` differs from the composer's hardcoded fallback
(`{strategy: "streamed_text", name: "output.md"}`) is exposed the same way.

Read every catalog built-in's `deliverable:` block directly:

| built-in | `backend/agents/workflows/<id>/workflow.yaml` | declared deliverable | differs from fallback? |
|---|---|---|---|
| `ppt` | `:42-44` | `strategy: ppt`, `name: presentation.pptx` | yes (the reported case) |
| `ppt_v2` | `:52-54` | `strategy: single_file`, `name: presentation.html` | yes |
| `prototype` | `:40-42` | `strategy: single_file`, `name: prototype.html` | yes |
| `app_builder` | `:27-29` | `strategy: serialized_sandbox`, `name: app` | yes |
| `dotnet_to_azure` | `:18-20` | `strategy: serialized_sandbox`, `name: azure-app` | yes |
| `mulesoft_to_springboot` | `:18-20` | `strategy: serialized_sandbox`, `name: springboot-app` | yes |
| `user_stories` | `:29-31` | `strategy: streamed_text`, `name: user_stories.md` | filename only |

`ppt_v2` is the sharpest case beyond the reported one: it also declares a genuinely non-default
tool grant on one step (`backend/agents/workflows/ppt_v2/workflow.yaml:77`,
`{read_files: true, write_files: false}`). Unlike `ppt` (whose steps all use the default
`true`/`true`, so no grant is actually lost even though the mechanism would drop a non-default one
— see ISS-206's "What is and is not actually lost"), copying `ppt_v2` via "Save as copy" would
silently upgrade that step back to `write_files: true` on top of losing the `single_file`/
`presentation.html` deliverable — a more severe, security-relevant regression than the reported
bug (a step that was supposed to be read-only gains write access in the copy).

`user_stories` is the mildest case: its strategy already matches the fallback (`streamed_text`),
so the Workflow tab would still show "Streamed text" (visually plausible, not obviously wrong) —
only the output filename (`user_stories.md` vs the fallback's `output.md`) and the empty-vs-real
manifest would differ, making this instance harder for a user to notice than `ppt`'s.

## Expected vs actual

**Expected:** "Save as copy" on any of these built-ins persists a `manifest` carrying the real
`deliverable` (and any non-default tool grants) declared in `backend/agents/workflows/<id>/workflow.yaml`.

**Actual (inferred, not yet reproduced):** the same `manifest: null` / generic-deliverable outcome
ISS-196 verified for `ppt`, once for each of `ppt_v2`, `prototype`, `app_builder`,
`dotnet_to_azure`, and `mulesoft_to_springboot` — plus a silently-restored write grant for
`ppt_v2` specifically.

## Status

**INFERRED.** The mechanism is confirmed by source (same code path, same gate, no per-workflow
branching) and the `deliverable`/`tools` declarations above were read directly from each
`workflow.yaml`, but no live click-through has been run for any built-in other than `ppt`
(ISS-196 owns that one). Settling this needs one repeat of ISS-196's reproduction steps
(`/workflows/<type>/canvas` → "Save as copy" → inspect the POST body and the copy's own edit
page) per row in the table above — cheapest to check first: `ppt_v2`, since it is the only one
with an independently-verifiable non-default-grant side effect.
