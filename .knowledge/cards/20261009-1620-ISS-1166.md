# ISS-1166

INFERRED sibling of [ISS-1155](20261009-1420-ISS-1155.md) (register QA-KB-119), derived from its root cause: the durable
log has one reader with no bounded form, and the REST endpoint is not its only caller. `backend/agents/authz.py:476-479`
names three users of that reader: "SSE resume, the events API and engine resume". This card is the SSE one.

## Condition

A client attaches `GET /api/runs/{id}/events/stream` with no `Last-Event-ID` (a fresh attach; a non-int header degrades
to the same, `backend/app/api/run_stream.py:684-689`) to a run with a large log. The code's own comment calls a fresh
attach "the common case" (`run_stream.py:480-481`), and `useRunStream` sends the header only once it holds a cursor
(`frontend/src/hooks/useRunStream.ts:346-347`; "worst case = full replay", `:18-20`).

## Expected vs actual

Expected: the replay is delivered in bounded pages, each released as it is sent, so the first frames arrive quickly and
memory stays flat. Actual: `_iter_sse_frames` calls `rows = await store.read_events(run_id, after_seq=after_seq)`
(`run_stream.py:413`) and starts yielding only after it returns (`:414`). One `.all()` holds every ORM row of the tail,
then 107,409 frames are yielded one by one, and `replayed_event_ids` (`:441`) keeps every id for the stream's lifetime.

## Why the root cause implies it

Same reader, same missing bound (`authz.py:412`: `return query.order_by(RunEvent.seq.asc()).all()`). The execution mode
differs: the SSE generator is fed a session-less store (`run_stream.py:667-670`, BUG-004), so `read_events` runs in a
worker thread (`authz.py:164-177`) and, unlike the REST path, does not freeze the loop. It does sit under
`_STORE_CALL_TIMEOUT_SECONDS = 10.0` (`authz.py:74`): a tail whose single read exceeds 10 s raises `StoreTimeout` out of
the generator instead of merely being slow.

## Measured (CONFIRMED) and INFERRED

CONFIRMED, `evidence/qa-kb-119/04-analysis-sse-probe.txt`: a fresh attach to run 78e185fb (completed, so replay,
`stream_attached`, close): 200, 49,998,763 B, 12.35 s total. `/health` during it: 192 of 198 probes answered within 10 ms,
worst 471 ms. The SSE twin is slow and heavy, not loop-freezing.

INFERRED, each with what settles it:

- **A log whose read exceeds 10 s fails the attach with `StoreTimeout`** instead of degrading. [ISS-639](20260831-1645-ISS-639.md)
  measured 2-7 s per `read_events` call at 37k-137k rows, so the ceiling sits within roughly 1.5-3x of the largest local
  run. Settle: in a scratch run (not in the tree) set `_STORE_CALL_TIMEOUT_SECONDS` to 1.0 and attach to 78e185fb with no
  cursor; expect `evt=authz.store_call_timeout method=read_events` in the log and a stream that closes with no
  `stream_attached` frame.
- **A late attach to a LIVE long run can evict itself.** The subscriber queue is registered before the replay
  (`run_stream.py:696-703`) but drained only in step 4 (`:505-509`). Live events accumulate for the whole replay (about 12 s
  here) in a queue of `SSE_SUBSCRIBER_QUEUE_MAXSIZE = 1000` (`backend/app/core/config.py:281`); a full queue is EVICTED
  (`backend/app/api/run_engine.py:351-353`, `_evict_subscriber` at `:286`, log reason `queue_full_on_dispatch`), the stream
  closes and the client must reconnect. That needs more than about 83 live frames per second during the replay, which a
  streaming run emitting `agent_thinking` deltas can do. Settle: attach with no cursor to a streaming run with a large log
  and look for `SSE subscriber evicted` in the backend log.
- **Per-attach memory** is the full tail as ORM rows before the first frame. Settle: RSS during the 12 s window.

## Fix location

Not in this function alone. Once [ISS-1155](20261009-1420-ISS-1155.md) adds a bounded forward reader
(`ScopedStore.read_events_page`), `_iter_sse_frames` step 1 loops over it page by page: yield the page's frames, advance
`replayed_through_seq`, add the ids to `replayed_event_ids`, drop the page, stop on a short page. Keep the C-06a dedup set
(`run_stream.py:394-410`), the `stream_attached` handshake after the replay, and the gate re-arm guard (`:492`) as they
are. Moving the subscription to AFTER the replay would trade the C-06a duplicate window for a loss window (events
committed between the last page and the subscribe), so do not take that shortcut; the eviction risk above is the price of
subscribing first, and paging the replay shortens it.

Trap: four tests fake the store with `async def read_events(self, run_id, after_seq=0)`
(`backend/tests/integration/api/test_sse_stream_api.py:971,1204,1440,1468`). Changing `read_events` itself, instead of
adding a sibling method, breaks them; a paged replay needs those fakes to grow the new method.

## Update (5-fixer, QA-KB-119, 2026-10-09)

Still open. [FIX-778](20261009-1653-FIX-778.md) fixed the REST endpoint only and added the bounded reader this card
asks for: `ScopedStore.read_events_page(run_id, after_seq, *, limit)` (`backend/agents/authz.py:416-438`), the same
filter and `_scope_owner_ws` scope as `read_events`, `ORDER BY seq ASC LIMIT :limit`. `_iter_sse_frames` still calls
`read_events` at `backend/app/api/run_stream.py:413`. Left for its own pass because this card is INFERRED, has no red
test, and the change sits on the live-run path; the fakes named above (and the stores the attach-replay matrix in
`backend/tests/integration/api/test_attach_replay_matrix_api.py` feeds `_iter_sse_frames`) would need the new method.
