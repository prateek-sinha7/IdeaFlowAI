# FIX-719

Register source: `QA-KB-054` in root `LEDGER.md` / `BUGS.md`. Resolves [ISS-687](20260918-ISS-687.md) (root),
[ISS-976](20261002-0405-ISS-976.md), [ISS-977](20261002-0405-ISS-977.md) and [ISS-978](20261002-0405-ISS-978.md).

## What was wrong

`POST /api/runs` for a file workflow built from `custom-agent` steps (`prototype_v2`, `backlog` and 15 others on
this branch) returned `400 invalid_agent_ids` whenever `agent_ids` carried the workflow's own compiled ids.
`POST /api/user-workflows` returned `422 agent_ids not allowed` for the same flat roster. The 400 also told the
user to repair a blank step in a saved override that did not exist.

## Root cause

- `backend/app/api/run_commands.py:3468-3470` allow-lists every supplied id against
  `allowed_custom_agent_ids(base_pipeline_type)`.
- `backend/agents/registry.py:438-447` builds that set from `PIPELINE_AGENTS`, i.e. from `AGENT.md` frontmatter. A
  `custom-agent:<instance_id>` step has no `AGENT.md`, so for these workflows the set is the `return set()` fallback
  (`:447`). Every non-empty `agent_ids` was rejected.
- `backend/app/api/user_workflows.py:720-722` ran the same predicate on save.
- FIX-438's message (`run_commands.py`, the `_stale` list) assumed any rejected `custom-agent:` id came from a saved
  override. For these workflows it is the plan's own step.

## What changed and why there

One shared predicate, called from the only two production call sites of `allowed_custom_agent_ids`. Re-grepped on
2026-10-07: `run_commands.py:3469` and `user_workflows.py:721`. No other sender needs a change.

- `backend/app/api/run_engine.py:807-825`, new `_own_plan_roster(pipeline_type)`. It returns every agent id of
  `compile_for_run(pipeline_type).steps` when any of them starts with `CUSTOM_AGENT_PREFIX`, and `set()` otherwise.
  That includes no manifest or a compile error. The registered step of a mixed plan (`prototype_v2_revision`)
  counts, so "the full roster" means the whole plan.
- `backend/app/api/run_commands.py:3459-3467`: if `set(agent_ids) == _own_plan_roster(base)`, the local `agent_ids`
  becomes `None`. The existing `else` branch (`:3549-3578`) then compiles the plan and builds the roster with
  `_specs_from_plan`, the same way a launch without ids does. `presort_specs` never runs on a file-backed plan (the
  CWF-001 D1 scope fence), and nothing downstream reads `body.agent_ids` again.
- `backend/app/api/run_commands.py:3479-3500` (ISS-978): the saved-override sentence now names only rejected
  `custom-agent:` ids that are NOT plan steps (`_stale`). Plan steps (`_own`) get a separate sentence: the workflow
  file fixes which steps run, so launch it with all of its steps, or use Advanced, Save as copy.
- `backend/app/api/user_workflows.py:48, 722-731` (ISS-976): save raises its 422 only when the list is not the
  plan roster. It goes through the app-layer helper, so `user_workflows.py` still has no direct
  `agents.execution_engine` import.

**Provenance, stated plainly.** These production lines were already in `HEAD` when this pass started. They landed
in commit `14a675db4` ("not_stable changes for stale fix cards") with no FIX card, the ledger row still `TESTED`
and all four ISS cards still `open`. This pass edited no production line. It checked the code line by line against

## Decision taken: an edited roster is rejected

[ISS-687](20260918-ISS-687.md) left one choice to the fixer, with a recommended default. The question: what happens
to a strict subset or superset of the plan? **Taken as recommended: reject it pre-mint.** Normalising it away would
run the FULL plan, so steps the caller removed would still run and spend Bedrock tokens. The full roster, which is
what every real sender produces, satisfies the bug's Expected.

The general question of whether a launch may run a strict SUBSET of a built-in's steps is
[ISS-966](20261002-0320-ISS-966.md), still open and waiting on an owner decision (options A/B/C). This fix fails
closed in the meantime. If the owner picks option A (honour subsets), custom-agent file workflows have to follow:
today they 400 on a subset, while registered built-ins silently run the full plan (ISS-966's finding).

## Test correction: the expected behaviour was misstated (explicit, test-only)

The 4-test-writer's `test_iss687_custom_agent_roster.py` sent a strict SUBSET and asserted success:
`["custom-agent:fi-planner", "custom-agent:fi-readers"]` is 2 of the 11 `prototype_v2` steps, and
`["custom-agent:us-planner"]` is 1 of the 20 `backlog` steps. Those ids were copied from the analyzer's probe, which
used them only to show the rejection. ISS-687's "For the test writer" section prescribes the full plan for the red
case (`agent_ids=[<every id in compile_for_run(...).steps>]`, expect 200 and one run). The same section lists
"an edited roster (plan minus one id) still rejected" under **Must stay green**. Against the in-tree fix the subset
tests therefore stayed xfail for a reason the card itself calls correct (`400 ... are steps of 'prototype_v2'
itself` / `422 agent_ids not allowed`). No production code was changed to make them pass.

The changes, all in that one test file:

- New helper `_plan(pipeline)` = every compiled step id. It replaces the `_PLAN` subset in the ISS-687 launch test
  and in both ISS-976 save parametrisations (each now parametrised on `pipeline` only).
- The ISS-687 launch test monkeypatches the harness `_RecordingEngine._specs_from_plan` to the real
  `ExecutionEngine._specs_from_plan`, which reads no engine state. This is the "harness gap" the card names: without
  it the success path dies with `AttributeError` (observed in a scratch probe, see below).
- New guard `test_edited_own_roster_is_still_rejected`, from the card's "Must stay green" list: plan minus one id →
  launch `400 invalid_agent_ids` with 0 runs, save `422`. It is not xfail because it holds before and after the fix.
- Unchanged: every assertion of the three red tests (`< 400` with `_run_count == 1`, and `== 201`), the ISS-978 test
  as a whole, and every `xfail(strict=True)` marker. The 6-verifier removes those.

The test-writer's original file is kept for the audit at
`evidence/qa-kb-054/fix-test_iss687_custom_agent_roster.py.orig`. The same diff is
`git diff -- backend/tests/integration/api/test_iss687_custom_agent_roster.py`, since the original is what
`14a675db4` committed.
