## What was wrong

This is register bug **QA-PS-004**. On a User Stories run with three review gates, the
concierge chat showed `Review approved — build continues` once per approved gate, word for
word. Scrolling back, you could not tell which approval belonged to which agent. The root
cause is recorded in [ISS-650](20260917-1130-ISS-650.md).

## Root cause

- `frontend/src/components/chat/ResultCard.tsx:141-142` (pre-fix): a resolved gate card
  rendered a hardcoded literal with no slot for an agent name.
- `frontend/src/hooks/useRunChat.ts:411-421` (pre-fix): `upsertNarratorMessage` built the gate
  `ChatMessage` without any agent field, and `ChatMessage` (`frontend/src/types/index.ts:85-115`)
  had no field to hold one.
- `backend/app/agents/chat_narrator.py:255-261` (pre-fix): nothing upstream could have supplied
  the name. `project_milestone_card` returned only `{pipeline_run_id, message_id, card_kind,
  text, deep_link}` and dropped `agent_name`, even though its source `review_gate_ready`
  carries it (`backend/agents/execution_engine/engine.py:10288-10292`). The durable rows of
  run `a7279a95-8af1-4b5d-b1d1-04c8625a9c89` show the whole chain. Seq 541 is a
  `review_gate_ready` with `agent_name: "Domain Discovery Agent"`. Seq 542 is the gate
  `chat_reply` with no name. Seq 543 is a `review_gate_approved` carrying `agent_id` only
  (`engine.py:10446-10452`). The same pattern repeats at 2591-2593 and 4635-4637.

[ISS-650](20260917-1130-ISS-650.md) put the plumbing gap on the `review_gate_approved` path (`useRunChat.ts:565`). That
event has no `agent_name` to plumb, so the name has to travel on the gate card itself.

## What changed, and why there

1. `chat_narrator.py:255-267`: `project_milestone_card` now adds `agent_name` to a gate card
   when the source event has one. Keyed on the generic `CARD_GATE` kind, never a workflow name.
2. `types/index.ts:110-115`: `ChatMessage.agentName?: string`, additive and optional.
3. `useRunChat.ts:421-424`: `upsertNarratorMessage` reads `data.agent_name` into `agentName`.
4. `ResultCard.tsx:142-145`: a resolved gate reads `<agentName> review approved — build
   continues`. With no `agentName` the old literal renders unchanged.

**Why the card and not the approval frame or a companion frame.** Every chat-lane path gets
the card's payload whole:

- the live yields spread `**_card` (`engine.py:3816-3829`, `:13496-13505`);
- both durable readers pass `payload_json` through untouched (`backend/app/api/runs.py:1509`
  for `GET /events`, `backend/app/api/run_stream.py:251` for the SSE replay).

A name taken from the companion `review_gate_ready` frame would not reach every transcript.
The page seeds family members, the revision reseed and the completion append with
`chat_message`/`chat_reply` frames only (`frontend/src/app/[...view]/page.tsx` filters at
`:1504`, `:2974`, `:3444`, `:3461`, `:3480` at time of writing). Those transcripts never see
that frame.

**Only new runs get named cards.** `chat_reply` rows are persisted at emit time. Runs recorded
before this change keep `Review approved — build continues`, because their stored gate cards
have no `agent_name`. That includes the repro run `a7279a95`. [FIX-517](20260917-1307-FIX-517.md) has the same property
for the same reason. To verify, use a gate card created after the backend reloaded this file.

Invariants: SC-001 holds. `grep "if pipeline_type ==\|if spec.id ==" backend/agents/execution_engine/`
returns 0. `chat_narrator.py` is app-layer, no import was added, and no migration was touched.

  confirmation before anyone fixes it, so it stays `open`. With this change, a mis-resolution
  would name the wrong agent as approved instead of reading generically.

  `ResultCard.tsx:146-147` still names no agent. That is not this bug, and its test has not been
  written and seen red yet. `ChatMessage.agentName` is the plumbing that card says it needs.
- [ISS-664](20260917-1310-ISS-664.md) (QA-PS-006 sibling): terminal reopen still flips every gate
  card to resolved, rejected gates included. Such a card now reads `<agent> review approved`.
