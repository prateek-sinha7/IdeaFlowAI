# ISS-745

## Description

**INFERRED sibling of [ISS-744](20260922-1409-ISS-744.md) — not reproduced live (no run was
launched for this analysis, per this task's constraints). Filed because ISS-744's own root cause
implies it, not because it was observed.**

ISS-744 establishes that `frontend/src/app/[...view]/page.tsx:1521` fires
`setContentSourceRunId(completingRunId)` for ANY `*_revision`-typed `pipeline_complete` this tab
is tracking, bypassing the `isForeignCompletion` guard whenever `isRevisionCompletion` is true.
ISS-744's reproduction path assumes the completing revision belongs to the SAME family as what is
on screen (the ordinary "I pinned an old version while my own revision finishes" case). This card
is the harder case: `isRevisionCompletion` (`page.tsx:1509`) is:

```tsx
const isRevisionCompletion = typeof completingPipelineType === "string" && completingPipelineType.endsWith("_revision");
```

— a check against the STRING SUFFIX of the completing run's own `pipeline_type` only. Nothing in
it, or in the `if (completingRunId && (!isForeignCompletion || isRevisionCompletion))` condition
that guards `setContentSourceRunId` at `:1521`, checks that `completingRunId`'s family (its
`parent_run_id` ancestry / `root_id`) has any relationship to `trackedRunIdRef.current` (the
family currently on screen). The inline comment at `:1501-1508` states the intended scope — "a
`*_revision` pipeline is intentionally dispatched FROM the currently-tracked run" — but the code
enforces only the type suffix, not the "FROM the currently-tracked run" half of that sentence.

## Why the root cause implies this

`RunConnectionProvider`'s own design explicitly supports one tab tracking SEVERAL of the user's
concurrently-running pipelines at once (`liveRunIds = union(autoIds, focusedRunId)`,
`RunConnectionProvider.tsx:255-271` — `autoIds` is every `AUTO_STREAM_STATUSES` run this tab has
itself launched in-session, restored from `sessionStorage`'s `tab_launched_run_ids`; this is the
same union that powers the "N running" notification badge, QA-PS-002/ISS-679's area). If a user,
in ONE tab, over one session:

1. Launches a revision on family A, then navigates away (Home, or straight to family B's run
   detail) before it finishes — family A's revision run id is now in this tab's `autoIdsRef` via
   `AUTO_STREAM_STATUSES`, so this tab keeps receiving its `pipeline_complete` regardless of what
   is currently rendered.
2. Opens family B's run detail page and pins an older member (or even just leaves it on
   "Latest (live)") while family A's revision is still generating.
3. Family A's revision finishes. `completingRunId` = family A's revision run id,
   `trackedRunIdRef.current` = family B's currently-viewed run id → `isForeignCompletion=true`.
   `completingPipelineType` ends with `_revision` → `isRevisionCompletion=true`. The OR-bypass at
   `:1521` fires regardless: `setContentSourceRunId(familyA_revision_id)`.
4. `DashboardLayout`'s family-fetch effect (`DashboardLayout.tsx:701-706`, keyed only on
   `[contentSourceRunId]`) now fetches family A's `runFamily`, and `liveRunId` becomes family A's
   run id. The screen the user was looking at — family B — is replaced with family A's content:
   not merely "reset to latest," but switched to an entirely different project the user was not
   even looking at, with no navigation of their own.

This is a strictly larger blast radius than ISS-744: ISS-744's user at least ends up back at
their OWN family's latest, which — however unwanted mid-review — is at least still their content.
This card's path can hand them someone else's (well, their own OTHER project's) run entirely.

## What would confirm or refute this

Not reproduced. To settle it: in one browser tab, launch a `*_revision` pipeline on family A and
immediately navigate to family B's run-detail page before A finishes (or use two concurrent
revisions across two unrelated families, both launched from the same tab in-session); observe
whether `contentSourceRunId`/the rendered content jumps to family A the moment its revision
completes while family B is on screen. A passing disproof would require finding an additional
guard between `page.tsx:1509` and `:1521` that this read missed — re-grep
`isRevisionCompletion`/`completingRunId` in the live file first, in case a later commit narrowed
it after this pass.

## Fix direction (not applied — issue only)

Same call site as ISS-744 or immediately upstream of it: `isRevisionCompletion` needs a lineage
check, not just a type-suffix check — e.g. confirm `completingRunId`'s `parent_run_id` (or its
resolved family root) matches the family currently in view before allowing the OR-bypass, not
merely that the string ends in `_revision`. If ISS-744's fix moves the pin-preservation guard
into `PreviewPanel`, this card's fix is still needed separately in `page.tsx` — ISS-744 stops the
symptom (pin loss) for same-family completions; this card stops `contentSourceRunId` from being
redirected to a DIFFERENT family's run id at all, which no downstream pin-guard can repair once
`runFamily` itself has been refetched for the wrong family.

## Analysis update — QA-KB-055 (2026-10-07)

Register bug QA-KB-055 ("Another family's finished revision hijacks the run-detail screen you are viewing") is this
card's defect. It was first closed as a DUPLICATE of this card and reopened, because this card is still open and nothing

### Verdict

The mechanism is **CONFIRMED by source read**; the card called it INFERRED. It has **not been observed end to end in a
browser**: QA-KB-055 is a static-repro entry and no run was launched (runs cost money). Every link below was opened at the
line given.

Line drift since filing: `page.tsx:1509` is now `:1617` (`isRevisionCompletion`), `:1521` is now `:1629` (the OR),
`:1497-1500` is now `:1605-1608` (`isForeignCompletion`), `DashboardLayout.tsx:701-706` is now `:741-746` (family fetch).

### The chain (CONFIRMED reads)

1. **Delivery.** A completion from a run the user is not looking at reaches the page handler, by two routes.
   - Sticky focus (no reload needed). Launching a revision calls `runConnection.attachRun(run_id)` (the `postRevision`
     `.then` blocks in `DashboardLayout.tsx`, `page.tsx:4340` for the `onStartPipeline` path), which makes that revision
     the single sticky focus (`RunConnectionProvider.tsx:464-471`). Opening another run only replaces the focus when that
     run is non-terminal: `page.tsx:2993` `if (!REOPEN_TERMINAL_STATUSES.has(fullRun.status)) { runConnection.attachRun(fullRun.id); }`.
     So opening a COMPLETED family B from History leaves the revision on family A focused and streaming. `detachRun` is
     called only for the completing and the cancelled run (`page.tsx:1636`, `:1867`), never on navigation.
   - Auto-attach. `RunConnectionProvider.tsx:336-357`: `refreshLiveRuns` attaches every run whose status is in
     `AUTO_STREAM_STATUSES` AND whose id is in `sessionStorage` `tab_launched_run_ids`, whatever is on screen. A revision
     row is minted with `status="revising"` (`backend/app/api/run_commands.py:4687`), which is in that set
     (`RunConnectionProvider.tsx:69-75`). `refreshLiveRuns` runs on boot, on tab-visibility wake and on `online` (`:372`,
     `:391`, `:396`); `reattach()` has no caller outside the provider. This route keeps the revision streaming even when the
     user then opens a non-terminal run, once the tab has been reloaded or refocused since the launch.
   - `page.tsx:1086-1088`: the handler "is subscribed to the app-wide SSE fan-out and carries no route guard".
     `pipeline_complete` is not agent-scoped (`frontend/src/lib/__tests__/wsRunScope.test.ts:152`), so nothing returns early
     for a foreign one.
2. **Decision.** `page.tsx:1605-1608` `isForeignCompletion` is `completingRunId !== trackedRunIdRef.current`; `:1617`
   `isRevisionCompletion = typeof completingPipelineType === "string" && completingPipelineType.endsWith("_revision")`;
   `:1629` `if (completingRunId && (!isForeignCompletion || isRevisionCompletion))` then `:1630`
   `setContentSourceRunId(completingRunId)`. The suffix test and the OR are the whole decision; family membership is never
   consulted, and the event cannot answer it: the payload built at `backend/agents/execution_engine/engine.py:7968-7979`
   carries `pipeline_type`, `pipeline_run_id` and totals, no `parent_run_id` and no root. A `degraded` completion takes the
   same path (`data.status` is not read before the set).
3. **Effect.** `contentSourceRunId` is read by: `DashboardLayout.tsx:741-746` (`getRunFamily(contentSourceRunId)` becomes
   `runFamily`), `:3423-3424` (`runFamily` and `liveRunId` go to `PreviewPanel`: chip, header, Preview), `:534-539` (the
   tab-click route map, so the next tab click `pushState`s to the other family's URL), `:1203-1325` and `:1922-1926`
   (revise and chain parent, see [ISS-1077](20261007-2142-ISS-1077.md)), and `page.tsx:2329-2331` (`trackedRunIdRef`
   follows it, so every later run-scope decision is made against the hijacked id). No effect reacts to it by pushing a
   route; only click handlers (tab click, chain, resume) read it and navigate. So the address bar keeps naming the viewed
   run until one of those is used (inferred from reading every consumer, not observed); a hard reload returns to it.
4. **Why page-local memory cannot carry the answer.** The page remounts on every `router.push` under `[...view]`
   (`page.tsx:3494-3499`), so anything recorded in a ref at launch is gone by the time the revision completes.

Precedent: [FIX-173](20260805-1853-FIX-173.md) Bug 1 (2026-08-04) records the same mechanism biting a user,
"`contentSourceRunId` could transiently point to a prototype run when a PPT revision's `postRevision` was called".

Precondition for QA: one revision per family at a time (`run_commands.py:4610-4616` rejects a second with 409
`revision_already_in_progress`), so the trigger needs a revision in flight on family A while family B is open.

### Why the OR exists, and what the fix must keep

[FIX-088](20260722-FIX-088.md) added the OR for the SAME-family case: the user is on the parent while its revision
finishes, `completingRunId !== trackedRunIdRef.current`, and without the OR the family never refetches and the chip stays
at v1. The un-pinned follow-to-latest is pinned by the GREEN control in `PreviewPanel.pinSurvival.test.tsx` and by
[ISS-744](20260922-1409-ISS-744.md)'s fix ([FIX-603](20260922-1440-FIX-603.md)). Both must survive. The OR is not dead code:
`handleRevisionLaunched` (`page.tsx:2862-2867`) and the `onStartPipeline` path (`:4380-4382`) point `trackedRunIdRef` at
the revision itself, but the user can open another member of the family afterwards and the revision then reads as foreign.

### Where the fix belongs

**One decision, three call sites**, all in `handleWebSocketMessage`'s `pipeline_complete` branch: `:1625` (the
background-notification bridge, which today excludes every revision), `:1629` (the content-source set) and `:1688-1731`
(the content slots, [ISS-1074](20261007-2140-ISS-1074.md)). A change at `:1629` alone leaves the other two disagreeing with
it. Put the predicate in `frontend/src/lib/wsReplayState.ts` beside `isForeignRunFrame`, the module's existing "ONE shared
predicate" for this class, which is unit-testable where the 4000-line page is not.

**What it must compare is the family root, not the tracked run.** `trackedRunIdRef` is the run on screen: it can be an
older member, or the revision itself. The triage sketch in BUGS.md ("completing run's parent equals `trackedRunIdRef`")
misclassifies a same-family revision whose parent is a middle member (viewing v1 while v3, a child of v2, completes) and
brings back FIX-088's stuck chip for that case. The sketch's parenthetical "or shares its family root" is the load-bearing
half.

**Where the lineage comes from** (none needs an API change; cheapest first):

- (a) Resolve both roots with the existing owner-scoped `GET /api/runs/{id}/family` (`getRunFamily`,
  `backend/app/api/runs.py:1835-1875`, returns `root_id`), only on the rare foreign-revision branch. It is async, so check
  `trackedRunIdRef` again when it resolves, and fail safe to the background branch on error.
- (b) Record `{revisionRunId: rootId}` at launch in BOTH launch paths. `handleRevisionLaunched` receives only the new id
  today (`:2862`); `onStartPipeline` knows `extraParams.source_workflow_run_id`. Capture it before `trackedRunIdRef` is
  overwritten and persist it in `sessionStorage` (see point 4 above). `WorkflowRun.rootRunId` (`types/index.ts:446`) is not
  enough alone: `handleRevisionLaunched` does not refresh `recentRuns`.
- (c) Add `parent_run_id` / `root_run_id` to the `pipeline_complete` payload at `engine.py:7968`. This is an additive
  SSE-contract change and also needs the key in `_VOLATILE_STRIP_KEYS`
  (`backend/tests/agents/characterization/_normalize.py`) to keep the five characterization goldens identical (INV-3),
  plus a note in `specs/001-ai-workflow-os/contracts/websocket-events.md`. [FIX-603](20260922-1440-FIX-603.md) called the
  payload route "a data/design decision"; (a) or (b) avoids having to make it.

Unresolved lineage must not switch the screen (treat it as background); the same-family case must still advance when it
does resolve.

### Not an escalation

No product decision is open. The intended behaviour is written down twice already ([BUG-011](20260803-BUG-011-sse.md):
a foreign run's completion must not re-point the VIEWED content-source; QA-KB-055's Expected), and options (a) and (b)
need no contract change.
