## Summary
Each saved-workflow card on `/workflows` has a `button[aria-label='Workflow actions']` that opens
a small dropdown menu (`Edit` / `Rename` / `Duplicate` / `Delete`). The menu is correctly
scoped per-card (opening it on "My presentation" only ever shows/affects "My presentation" —
verified separately) and it DOES close correctly when the page's invisible outside-click overlay
(`div.fixed.inset-0.z-10`, rendered behind the menu specifically to catch outside clicks) receives
a genuine mouse click. However, pressing the **Escape** key while the menu is open has no effect
at all: the trigger button's `aria-expanded` attribute stays `"true"` and the menu list stays
visually present and interactive. This was verified with real Playwright keyboard events
(`page.keyboard.press('Escape')`), not synthetic/no-op JS calls, and reproduced twice on two
different cards ("My presentation" and "My prototype"). This is a distinct component and route
from the already-filed `BUG-20260827-221400-dashboard` (Escape not closing the dashboard catalog
card's "Inspect details" modal, a full `role="dialog"` overlay with Context Providers/
Capabilities/Compaction sections on `/dashboard`) — here the affected control is a lightweight
per-card action dropdown on the My Workflows list, reachable only via `/workflows`, with a
completely different purpose (workflow management actions vs. a read-only info panel) and a
different close mechanism (an outside-click overlay that itself works fine, unlike the dashboard
modal's X-only close).

## Reproduction
1. Sign in as qa-admin, navigate to `/workflows`.
2. Locate the "My presentation" card and click its `button[aria-label='Workflow actions']`
   (scoped via the card's unique title text, per the definition's `deleteWorkflow` recipe
   approach). Observe the menu opens: `Edit`, `Rename`, `Duplicate`, `Delete`, and the trigger
   button's `aria-expanded` reads `"true"`.
3. Press the Escape key (`page.keyboard.press('Escape')`, a genuine keyboard event).
4. Observe: the menu is still fully visible and interactive; `aria-expanded` on the trigger button
   is still `"true"`.
5. For contrast, confirm the menu's own outside-click handling otherwise works: a genuine
   Playwright mouse click on the invisible `div.fixed.inset-0.z-10` overlay rendered behind the
   open menu correctly closes it (`aria-expanded` becomes `"false"`, no menu items visible).
6. Repeated steps 2-4 on a second, different card ("My prototype") — identical result: Escape has
   no effect, `aria-expanded` stays `"true"` after the key press.

## Expected
Pressing Escape while the "Workflow actions" dropdown is open should close it, consistent with
standard menu/dropdown dismissal behavior and with the fact that this same menu already responds
correctly to an outside click.

## Actual
Escape is not wired to the menu's close handler at all — the menu remains open indefinitely after
Escape, and only an outside click (or presumably selecting a menu item) dismisses it.

## Analysis (QA-KB-041, 2026-10-01) - ANALYZED

**Current verdict: CONFIRMED, named trigger.** This supersedes the 2026-08-28 UNREPRODUCIBLE line in the header list: that cold start
used real clicks, which focus the trigger in Chrome. The defect needs an opening click that leaves the trigger unfocused.
Frontmatter `status: open` is correct.

### Root cause - CONFIRMED (read at file:line, reproduced offline)

`KebabMenu` (`frontend/src/components/savedworkflows/SavedWorkflowsPage.tsx:88-153`) dismisses on Escape only through a React
`onKeyDown` bound to its wrapper `<div>`:

```tsx
// SavedWorkflowsPage.tsx:100-109
const triggerRef = useRef<HTMLButtonElement>(null);
const handleKeyDown = (e: React.KeyboardEvent) => {
  if (e.key === "Escape" && isOpen) {
    e.stopPropagation();
    onClose();
    triggerRef.current?.focus();
  }
};
return (
  <div className="relative" onClick={(e) => e.stopPropagation()} onKeyDown={handleKeyDown}>
```

A keydown is dispatched to `document.activeElement` and bubbles up from there, so the wrapper only sees Escape while the trigger
or a menu item holds focus. Nothing moves focus into the menu on open: the file's only `.focus()` is the trigger refocus inside
this handler (`:105`), and it has no `autoFocus` and no `tabIndex`. The whole behaviour therefore rides on the opening click
having focused the trigger. Safari and Firefox on macOS do not focus a `<button>` on click (INFERRED: platform behaviour; the
validator emulated it with a JS `.click()` in Chrome, which also leaves `activeElement` on BODY). Then Escape targets BODY,
never enters the wrapper, `onClose` never runs, and `aria-expanded` stays `"true"`. Outside click still works: it is a mouse event
on a real element (`:454`). The 2026-08-28 cycles and the validator's attempt 1 are the same fact from the other side: with a
focusing click the handler works.

**Reproduced offline** (`evidence/qa-kb-041/08-analyze-probe-output.txt`, source `07-analyze-probe-saved.test.tsx.txt`; jsdom,
with a stable-identity motion mock so nodes survive re-renders the way real motion's do; nothing under `frontend/src` touched):

| case | activeElement after the click | after Escape |
|---|---|---|
| CONTROL, `user.click(trigger)` (focuses, like Chrome) | the trigger | `aria-expanded="false"` |
| REPRO, `fireEvent.click(trigger)` (never focuses) | BODY | `aria-expanded="true"`, menu present |
| REPRO, Escape dispatched straight on `document.body` | BODY | `aria-expanded="true"` |
| SHAPE, Escape dispatched on the menu node (inside the wrapper) | n/a | closes: the handler is wrapper-scoped |

### Fix - where it belongs; accepted and overruled

**Accepted from the QA-KB-041 notes:** the mechanism (a document-level `keydown` listener that is active only while the menu is
open, and on Escape calls `onClose()` and refocuses the trigger) and the test shape (open without focusing the trigger via
`fireEvent.click`, keydown Escape on `document.body`, expect `aria-expanded="false"`).

**Overruled or refined:**

1. **Placement.** Do not hand-write another inline `useEffect` in `KebabMenu`. [FIX-388](20260829-0053-FIX-388.md) already put
   this exact listener in `frontend/src/hooks/useEscapeToClose.ts`: `useEscapeToClose(onClose, enabled = true)` registers
   `document.addEventListener("keydown", ...)` and calls `onClose()` on Escape, and its own card says it exists so "the next
   modal calls one hook instead of copy-pasting a fourth effect". The notes' inline effect would be the fifth copy. The hook
   lacks only the trigger refocus, which one closure at the call site supplies:

   ```tsx
   // KebabMenu: replaces :101-107 and the onKeyDown prop on :109
   useEscapeToClose(() => { onClose(); triggerRef.current?.focus(); }, isOpen);
   ```

   No hook edit is needed for this bug. If the four menu siblings land in the same change, give the hook an optional trailing
   `returnFocusTo?: React.RefObject<HTMLElement | null>` instead so each call site drops its closure (three lines, backward
   compatible with its three modal callers).
2. **Delete the wrapper handler** (`:101-107` and `onKeyDown={handleKeyDown}` on `:109`). Do not keep it "with stopPropagation"
   as the notes allow: two paths for one behaviour, and a test could not tell which one closed the menu.
3. **Keep the `isOpen` gate (the second argument).** `KebabMenu` renders once per card; an ungated document listener would run
   on every Escape anywhere on the page and every instance would call `triggerRef.current?.focus()`, leaving focus on the last
   card's trigger.
4. **No replacement for the old `e.stopPropagation()` is needed.** The two modals this page can open are mounted only after the
   menu has closed (`setOpenMenuId(null)` at `:353` and `:355`), so no other Escape listener is live while a menu is open.

**Region discipline (QA-KB-019):** the working tree already carries QA-KB-019's one-line `cleanBrief` change at `:64`
([ISS-882](20261001-2111-ISS-882.md)). This fix touches one new import line near `:16` and `KebabMenu` `:100-109`; the optional same-file Delete-confirm fix ([ISS-932](20261001-2224-ISS-932.md)) is
`:415-421`. All three regions are disjoint from `cleanBrief` (`:59-73`).

## Resolution (QA-KB-041, fixer, 2026-10-02)

[FIX-710](20261002-0154-FIX-710.md) implements the fix that "Fix - where it belongs" above specifies.
`SavedWorkflowsPage.tsx:105` now reads `useEscapeToClose(() => { onClose(); triggerRef.current?.focus(); }, isOpen);`.
The wrapper `handleKeyDown` and its `onKeyDown` prop are deleted (the wrapper is now `:107`), and the `isOpen` gate is
kept. The same change resolves the five siblings, each through the same hook and gated on its own open state. The
analysis line "Frontmatter `status: open` is correct" described the card before this fix.

**What the test shows.** On the fixed tree, `SavedWorkflowsPage.escape.test.tsx` reports "Expect test to fail" for all 3
`it.fails` cases, and it did so in 3 of 3 runs. That is the pass signal. This file was not edited: its stable motion mock
keeps the synchronous checks deterministic. The existing focused-trigger CONTROL test (`SavedWorkflowsPage.test.tsx`)
passes 9/9. The markers are left for the verifier, and so is the manual browser re-run of the QA-KB-041 reproduction.
