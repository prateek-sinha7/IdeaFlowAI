# ISS-1007

**INFERRED. Reproduced offline in jsdom only (cases R4 and R4 control), not in a browser.** Derived while analysing QA-KB-066 ([ISS-755](20260922-1415-ISS-755.md)); the root-cause analysis and
the offline proof are on that card ("Re-analysis (2026-10-02, QA-KB-066)") and in `evidence/qa-kb-066/`. An unreproduced
sibling is a lead, not a defect.

Line numbers are the working tree on 2026-10-02 (HEAD `024c03ef8`); `PreviewPanel.tsx`, `DashboardLayout.tsx` and
`useWorkflow.ts` carry uncommitted edits from other work (none touches clarifications), so HEAD numbers can sit a few lines off.

## Condition

The shell run is paused at a clarify gate (`clarifyQuestions` non-empty, `isRunning` true) and the user opens the Version menu,
which renders in EVERY run state once the run has a tag (`RunHeader.tsx:415-434`: "the interactive VersionMenu shows in EVERY
state (running/failed/settled)"), and picks an older terminal member. (A member that is still running is followed live instead,
`PreviewPanel.tsx:911-914`.) Revisions can reach this: `backend/agents/workflows/ppt_revision/workflow.yaml:10-13` and
`backend/agents/workflows/app_builder_revision/workflow.yaml:18-21` declare `clarify.mode: auto`.

## Expected vs actual

- **Expected:** read-only v1's Steps shows v1's own agent rows under the "Viewing v1 (read-only)" banner
  (`PreviewPanel.tsx:1700`); the live run's question stays where it already is, the lane composer
  (`DashboardLayout.tsx:3354` `onSubmitAnswers={handleLaneSubmitAnswers}`).
- **Actual** (offline proof R4 against its control, `evidence/qa-kb-066/analysis-proof-clarify-pin.out.txt`): the pinned v1 Steps
  renders the live run's pending question in the spine's awaiting card (`"liveAnswerFormShownUnderPin":true`) and ZERO agent rows
  (`"pinnedAgentRowsShown":0`). Control, same pin with the shell running but no pending question: 1 agent row.

## Why the root cause implies it

Same defect class as [ISS-755](20260922-1415-ISS-755.md) on the neighbouring props: `PreviewPanel` hands the Steps tab the SHELL run's raw
clarify inputs with no pin check. `PreviewPanel.tsx:1984-1985` forwards `clarifyQuestions` and `onSubmitClarify` (and `:1979-1987`
the gate, skip and cancel callbacks) straight from the page. `StepsOverviewSpine.tsx:470`
`hasClarify = !!(clarifyQuestions && clarifyQuestions.length > 0 && onSubmitClarify)` has neither a run-state nor a pin term, so:

- `:474` the status pill reads "CLARIFY / Waiting on your answers";
- `:597-602` the awaiting card mounts the live run's `InlineClarifyActions`;
- `:633` `{!hasClarify && agents.map(...)}` hides every agent row of the pinned version. The comment on that line calls a visible
  agent during a clarify pause "a concurrent background run that leaked into the viewport"; here the hidden ones are the pinned
  version's own.

The gate affordance is already safe under a pin, by accident: `gateActive` (`:471`) and `gateAwaiting` (`:653`) require
`isRunning`, read from `pipelineState` (`:409`), which is `effPipelineState` and so `isRunning: false` for a pinned view
(`versionViewFrom` `PreviewPanel.tsx:644`). Only the clarify form lacks that guard.

Submitting from that form answers the LIVE run (`handleLaneSubmitAnswers` `DashboardLayout.tsx:2720-2733` ->
`handleQuestionnaireSubmit` `:2111-2153` -> `activePipelineRunId`) from inside a view the banner calls read-only.

## Fix direction (not applied; INFERRED design, validated on a scratch copy)

At `PreviewPanel.tsx:1984-1985` pass `viewingVersion ? undefined : clarifyQuestions` and the same for `onSubmitClarify` (`hasClarify`
needs both). Scratch variant `evidence/qa-kb-066/patched/PreviewPanel.complete.tsx`: R4 passes. `PreviewPanel.tsx` only: leave
`StepsOverviewSpine` alone, it is also mounted by `WorkflowHistory` (through `AgentThinkingTab`).

Possible product question, answer INFERRED: should the live clarify form be reachable from a pinned older version? The lane composer
already carries it, so the expected answer is no. If the owner says yes, the fix is instead to restore the version's agent rows
(`:633` should not hide them) and label the form as belonging to the live run.

## What would settle it

Reach a clarify round on a family member that has an earlier tagged version (a `ppt_revision` / `app_builder_revision` run), leave
it unanswered, pick the earlier version from the Version menu, open Steps.

## Resolution — FIX-730 (2026-10-07)

Resolved by [FIX-730](20261007-1900-FIX-730.md), for register entry QA-KB-066, exactly as this card's fix direction
proposed. `clarifyQuestions` and `onSubmitClarify` reach AgentThinkingTab as `undefined` under a pin
(`PreviewPanel.tsx:2058-2059`), so `hasClarify` is false and the pinned version's agent rows render.
`StepsOverviewSpine` is untouched. The product question above (should the live form be reachable from a pinned
version?) was answered with the card's expected "no": the lane composer still carries it.
