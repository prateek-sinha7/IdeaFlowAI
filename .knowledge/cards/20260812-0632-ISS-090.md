# ISS-090

## Title

**`redoable` has no eligibility fence — unlike `update_specs_eligible` it is an inline `True` literal at all three gate call sites, so ANY agent named in a per-run `gate_agent_ids` gets a Redo button with no server-side rule.** `update_specs_eligible` is computed by the structural predicate `_update_specs_eligible(artifact_kind, ectx)` (engine.py), published on `review_gate_ready`, and **binding** — ISS-053 tracks the remaining ingress enforcement. `redoable=True` has no equivalent: it is hard-coded at `engine.py` gate call sites (the REQ-RESUME-17 re-entry, the post-revision re-open, and the live post-stream gate). Consequences are bounded but real: a run that gates a **task-loop** or **tool-bearing** agent advertises "Request changes" on a dispatch whose semantics differ (FIX-228 handles the task-loop case defensively in `_consume_redo` by withholding the injected subject when `build_task_number` is set — but that is the *engine* being careful, not the *affordance* being correct). The symmetric fix is a `_redoable(artifact_kind, spec, ectx)` predicate mirroring `_update_specs_eligible`, published and enforced at the same three sites. Not required for ISS-086 and not attempted: it changes which buttons users see, so it needs its own decision.
