# ISS-639

## Title

**Two resume-tier seq SEEDS still read the whole durable log.** Found while fixing
[ISS-125](20260812-1852-ISS-125.md), by sweeping the rest of the file for the idiom
that card names rather than patching only the site it named.

```python
existing = await tail_store.read_events(run_id, after_seq=0)
start = max((r.seq for r in existing), default=0) + 1
```

appears verbatim twice more:

- `backend/agents/execution_engine/engine.py:10010` — `resume_run`, seeding the
  resumed run's sink counter past the durable tail.
- `backend/agents/execution_engine/engine.py:10377` — `_replay_clarify_run`, the same
  seed for the CR-01 questionnaire re-emit.

Both materialise every `run_events` row for the run (the local corpus holds a 26k-row
and a 36k-row run) to derive one integer, which is the cost
[ISS-125](20260812-1852-ISS-125.md) is about and which
`ScopedStore._max_event_seq` — a bounded `func.max` aggregate over
`uq_run_events_scope_seq` — exists to avoid.

## Why this is NOT the ISS-125/ISS-133 defect

These two are **seeds, not appends**. Nothing is written at the derived seq here: the
value initialises the `_RunEventSink` counter, and every append that follows already
goes through the collision-safe `append_event_at_or_after`
([FIX-240](20260812-1852-FIX-240.md), `engine.py:448`). So there is **no lost-write
exposure** — this is purely the read-cost half, on a path that runs once per resume
rather than per event. That is why it is filed separately at `minor` instead of being
folded into [FIX-499](20260831-1641-FIX-499.md), whose diff is deliberately one
function.

## Fix shape

`start = (await tail_store._max_event_seq(run_id)) + 1` at both sites, keeping each
existing `except Exception → start = 1` offline degrade untouched. Note the scope
difference before assuming it is a pure swap: `read_events` and `_max_event_seq` apply
the SAME `_scope_owner_ws` filter, so the derived integer is identical — verify that on
a seeded fixture rather than by inspection.

### Root cause (CONFIRMED)

Both restart drivers seed the manual seq allocator of `_drive_resumed_stream` by deriving ONE integer from a whole-log read:

```python
# resume_run, engine.py:15681-15683   (_replay_clarify_run, engine.py:16151-16153, same with _tail_ws)
tail_store = ScopedStore(owner_id=owner_id, workspace_id=workspace_id)
existing = await tail_store.read_events(run_id, after_seq=0)
start = max((r.seq for r in existing), default=0) + 1
```

`ScopedStore.read_events` (`authz.py:401-414`) is `query.order_by(RunEvent.seq.asc()).all()`: every column of every row, JSON payloads included. `ScopedStore._max_event_seq` (`authz.py:580-599`) is `SELECT max(seq)` under the same `run_id =` and `_scope_owner_ws` filter. The bounded form is already used at `engine.py:13058` (`_stamp_resume_marker`, [FIX-499](20260831-1641-FIX-499.md)), `app/api/run_commands.py:465` and `authz.py:649`; these two seeds were left behind and filed here.

`start` has one consumer: `start_seq=start` (`engine.py:15757`, `16189`) becomes `next_seq` (`engine.py:15802`), and every append after it goes through `_RunEventSink.persist` then `append_event_at_or_after` (`engine.py:15882`, `3331`). So, as filed, there is no lost-write exposure; this is a read-cost defect.

### Cost (CONFIRMED, measured; files in `evidence/qa-kb-045/`)

The local Postgres now holds 50 runs and 756,178 `run_events` rows. The "26k / 36k" in the filing is stale: the largest runs are 136,890, 107,409, 68,374, 37,354 and 36,037 rows (48 MB of JSON payload in the largest). The real code paths, read-only, session-less (so through `_run_bounded`), two passes on an idle box:

| run | rows | `read_events` + `max` | `_max_event_seq` | derived `start` |
|---|---|---|---|---|
| 3976f8ce | 136,890 | 4.4-5.0 s | 0.02-0.05 s | 220390 (both) |
| 78e185fb | 107,409 | 6.2-7.0 s | 0.02-0.03 s | 107410 (both) |
| 2867387c | 68,374 | 5.5-6.9 s | 0.02-0.03 s | 68375 (both) |
| 9b6f1bfb | 37,354 | 2.2-4.0 s | 0.03-0.04 s | 37355 (both) |

`EXPLAIN ANALYZE` on the largest run: the aggregate is an Index Only Scan Backward on `uq_run_events_scope_seq`, 1.0 ms; the `read_events` equivalent is a parallel bitmap heap scan plus an external-merge sort spilling about 70 MB to disk, 444 ms DB-side. The rest of the 4.4-5.0 s wall time is the ORM materialising the rows (INFERRED from wall against DB-side). The app already logs `evt=authz.store_call_slow method=read_events` for these reads. No non-terminal run exists in this DB right now, so the boot-time population is empty today.

The read runs under `_run_bounded`'s 10 s bound (`authz.py:74`). A `StoreTimeout` is a `RuntimeError`, swallowed by the seeds' `except Exception` and logged at DEBUG (`engine.py:15684-15690`, `16154-16160`), degrading to `start = 1` (INFERRED to fire only on a slower box: measured 2.2-7.0 s idle). Even then nothing is lost: the first persisted event collides on `uq_run_events_scope_seq`, `append_event_at_or_after` re-appends at the tail, and `_drive_resumed_stream` re-stamps (`engine.py:15885-15888`). A wasted collision and a misleading seed, not corruption.

### The open obligation in "Fix shape" is settled (CONFIRMED by execution)

The card asked for scope equivalence to be verified on a seeded fixture rather than by inspection. Over 8 scope/run cases (own scope, a second workspace holding a higher seq, a second owner, `workspace_id=None`, unknown workspace, unknown owner, empty run, missing run), `max((r.seq for r in read_events(run, after_seq=0)), default=0) + 1` equals `(await _max_event_seq(run)) + 1` in every case (`evidence/qa-kb-045/01-analysis-equivalence-and-driver-read-counts.txt`). By construction too: both apply `_scope_owner_ws` (`authz.py:219-227`) and `run_id =`, `RunEvent.seq` is `nullable=False` (`run_event.py:74`), and the empty case is `max(default=0)` against `int(scalar() or 0)`, both 0.

Current driver behaviour, executed with the offline harness (same file): `resume_run` with the offset stubbed makes exactly one store call, `read_events(0)`; `_replay_clarify_run` makes two, `read_events(0)` twice (the content read at :16115 plus the seed). Both seed correctly (`start_seq` = tail + 1).

### Fix: accepted, with conditions

Accept the agreed minimal fix: at `engine.py:15682-15683` and `16152-16153` replace the two lines with `start = (await tail_store._max_event_seq(run_id)) + 1`. It belongs inside `resume_run` and `_replay_clarify_run`, the only convergence points of all four callers. Conditions:

1. Leave `start = 1` and the surrounding `except Exception` degrade (offline harness, SAFE-03) untouched.
2. Touch ONLY the two seeds. Do not swap `engine.py:12677`, `12931` or `16115`.
3. The optional test is required (notes below).
4. No new helper: a helper for two 4-line stanzas is a bigger diff than the fix, and the idiom already exists at `engine.py:13058`.
5. Expect a partial gain: after the fix `_replay_clarify_run` still reads the log once (the content read) and `resume_run` still reads it in `_first_incomplete_step` and others. The fix removes one whole-log materialisation per resume path, not all of them.

Run it as one file, offline: `cd backend && .venv/bin/python -m pytest tests/agents/test_resume_marker_seq_allocation.py -v`. ### Invariants at risk

None for a correct two-line swap: no workflow name is involved (SC-001 / INV-1), no new import (the engine already imports `ScopedStore`, and `_max_event_seq` is a method of it), and it keeps the single shared resume funnel (INV-12) instead of adding a third seed idiom. The naive-fix trap is swapping every `read_events(after_seq=0)`: that breaks `derive_open_gate` and the questionnaire replay.
