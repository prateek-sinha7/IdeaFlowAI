## What is suspected

ISS-315's reproduction and validation were both scoped to `/workflows/new` — a brand-new,
never-saved composition where `initialName` is never supplied, so `name` starts at `""`
(`ComposerPage.tsx:219`, `useState(initialName ?? "")`). But the Save button and its guard
(`ComposerPage.tsx:1108-1117`, current lines — confirmed by direct read; ISS-315 recorded this
same code at :1075-1082, an earlier line offset before other landed changes shifted the file)
render ONCE in one shared `ComposerPage`, reached from every route that mounts it — including two
others where `name` starts non-empty and the identical guard fires only once the user actively
clears the field:

- **Edit an existing saved workflow** (`/workflows/{id}/edit`): `DashboardLayout.tsx:2998` passes
  `initialName={savedComposition?.name}` into `ComposerPage` — the saved row's real name, always
  non-empty by construction (you cannot have saved it with an empty name in the first place). The
  name `<input>` (`ComposerPage.tsx:1024-1032`) has no `readOnly` guard, so a user who
  selects-all-and-deletes the name (e.g. mid-rename) and clicks Save hits the exact same silent
  block ISS-315 documented — but now on a workflow that may carry real, unsaved edits (added,
  removed, or reordered agents) the user believes are about to persist.
- **Save as copy of a built-in** (`builtinCanvasType` set; label switches to "Save as copy" at
  `ComposerPage.tsx:1135`): `ComposerPage.tsx:1020`'s own fallback expression —
  `` `${initialName || builtinCanvasType} · copy` `` — only falls back to `builtinCanvasType` when
  `initialName` is falsy, which implies `initialName` is not guaranteed to be populated on this
  route either. If it is empty on first load, the guard blocks the very first "Save as copy"
  click with no feedback, before the user has touched the name field at all.

## Condition

- Route A: `/workflows/{id}/edit` on any existing saved custom workflow — clear the pre-filled
  name field, click "Save workflow".
- Route B: a built-in's canvas/simple view reached via "Save as copy" — if its name field is ever
  empty on first load (unconfirmed — see below), click "Save as copy" without typing a name.

## Expected vs actual

- **Expected:** the same clear, observable validation signal ISS-315 asks for, regardless of
  which route reached this shared button.
- **Actual (predicted):** the identical silent no-op — no request, no toast, no red border, no
  inline message — reached via a route the original hunter/validator never drove.

## Why the root cause implies this

The guard at `ComposerPage.tsx:1108-1112` runs unconditionally before `handleSave` on every
route, keyed only on the live `name` state — nothing in the guard branches on create vs. update
or on which route supplied the initial value. ISS-315 proved the guard's feedback is broken for
the create case; the same code path necessarily produces the same break wherever this component
mounts with a name the user can clear. The edit-route consequence is materially worse than the
new-workflow case ISS-315 covers: an edit-route user has pre-existing state (agent selections,
descriptions) they may reasonably believe just saved, since the button gives no signal either
way — a false sense of "it saved" is a worse outcome than "nothing happened yet" on a workflow
that never existed to begin with.

**Marked INFERRED**: no live click-through has been performed on either route. The shared
component/guard code and both routes' prop wiring have been read and confirmed
(`ComposerPage.tsx:219`, `:1020`, `:1108-1117`, `:1135`; `DashboardLayout.tsx:2998`), but neither
`/workflows/{id}/edit` nor a built-in's copy route has actually been driven with an
empty/cleared name. What would confirm it: open an existing saved workflow, clear the name, click
Save, and check for the same no-request/no-feedback signature ISS-315 captured; separately, load
a built-in's canvas/simple view fresh and inspect whether its name field is empty or pre-filled
on first render.
