## The gap

FIX-545 (resolved) taught the task parsers to prefer the task file already on
disk over a reply that merely narrates it: `parse_preferring_target(reply_text,
sandbox=…, target=…)` tries `target`, then each `fallback_targets` entry, then
the reply.

Only two call sites adopted it, both guarded by the same feature probe:

- `strategies/task_loop.py:213-216`
- `strategies/wave_scheduler.py:228-231`

```python
if hasattr(parser, "parse_preferring_target"):
    tasks = parser.parse_preferring_target(plan_output, sandbox=sandbox, target=target)
else:
    tasks = parser.parse(plan_output)
```

Four call sites were not revisited and still call `parser.parse(...)`:

- `strategies/fanout_batch.py:92`
- `execution_engine/engine.py:13499` — task_loop boundary reconciler
- `execution_engine/engine.py:13579` — wave_scheduler orphan allowset
- `execution_engine/engine.py:13797` — fan-out completeness check

## Why the three engine ones are the serious half

Those three exist *precisely* to recompute the same content-addressed task keys
the strategy persisted — `compute_task_key(upstream_hash,
normalize_task_content(t), ordinal)` over the parsed task list. Recomputing keys
from a different input than the one that produced them cannot work.

Concrete failure: a `wave_scheduler` step with parser `json_tasks`. The strategy
builds its tasks from `build/tasks.json`. On resume, `engine.py:13579` builds
keys from the reply's fenced JSON — exactly the narrated / truncated / absent
case FIX-545 exists for — so the recomputed keys never match the completed keys.
Consequences by site:

- `:13579` — the wave orphan allowset for that agent is wrong or absent, and
  finished fragments look orphaned.
- `:13499` — `common_prefix_length(current_keys, done_ordered)` mis-sets the task
  boundary.
- `:13797` — a `ValueError` raised by the parser on narration is swallowed by the
  broad `except`, which returns `i` (fail-safe = re-enter). The run re-enters a
  *completed* fan-out step and re-pays for it.

## screen_plan is the worst case

`ScreenPlanParser.parse()` raises `ValueError` on anything that is not a
`screens.json` inventory (`screen_plan.py:165-172`) — and an Architect's reply is
always prose. So at `:13797` it is not "a different parse", it is a guaranteed
throw into the swallowing `except`.

Even a lucky parse would be wrong: `parse_preferring_target` (`:174` onward)
reads `build/screens.json` **and additionally inlines `spec.md` into every task
body**, while `parse()` builds bodies with an empty spec string. Different task
bodies mean different normalised content mean different keys.

## Fix

Give the four sites the same treatment the two strategies got: read
`step.task_source.target`, pass the sandbox, use `parse_preferring_target` behind
the `hasattr` probe. The engine reconcilers already have `step` in hand at each
site, so `task_source.target` is one `getattr` away; they need a sandbox handle
for the run being reconciled.

Commits: `1e329e47b` (FIX-545), `a692982df` (added `screen_plan` without
revisiting the call sites).

[FIX-545](20260904-FIX-545.md) (`1e329e47b`) gave `json_tasks` a second entry point, `parse_preferring_target(reply, sandbox=, target=)`, that reads the task file the producer wrote and falls back to its reply only if the file is absent. `screen_plan` (added in `a692982df`) carries the same entry point. FIX-545 then pasted a `hasattr` probe into two of the six places that resolve a `task_parser`; the other four still call `parser.parse(<producer reply>)`. A grep of every non-test `resolve("task_parser", ...)` in `agents/` and `app/` finds exactly these six, so the list is complete.

### Corrections to the write-up above

1. `fanout_batch.py:92` is a strategy, not a reconciler. It is the same missing probe, but its failure is a normal-run parse error, not a resume key mismatch.
2. The site the write-up calls the "fan-out completeness check" (`:13797`, now `:15202`) is the `task_loop` completeness check (`if strategy == "task_loop":` at `engine.py:15167`). "Re-enters a completed step and re-pays for it" is overstated: re-entry is confirmed, re-payment is not, because the strategy skips completed tasks by prefix.
3. `screen_plan` is wired only to `wave_scheduler` in shipped manifests (`prototype_v2/workflow.yaml:954-959`), so its live site is `:14971` (swallowed, gate off), not the `:15202` completeness check. The "different bodies mean different keys" half stands (S-B3).
4. Line numbers `13499/13579/13797` are now `14889/14971/15202` (already noted under Validation).

### The agreed minimal fix: accepted in intent, overruled in four details

Accepted: use the same probe the strategies use, and one test per site asserting keys come from the on-disk file. Overruled:

1. **Do not paste the probe four more times.** This bug is copy-paste drift. Put one helper where all six sites route (below).
2. **`ectx.runner.sandbox` is None at the `:15202` site.** `_first_incomplete_step` is called from `_compute_resume_offset` with a bare `ExecutionContext(run_id, owner_id, disk_principal)` (`engine.py:16225-16231`, `:16254`) and `context.py:109` defaults `runner` to `None` (S-C prints `runner = None`). The agreed fix would be a silent no-op there and its per-site test could not pass. At `:14889` and `:14971` the runner is bound (`engine.py:5800`, before `:6001`), so there the handle does work.
3. **The `custom_path` skip is required, not optional.** The shipped `blr-write` declares both `kind: custom_path` and `source_step` (`backlog_revision/workflow.yaml:238-243`), and the composer writes both (`CanvasConfigRail.tsx:1683-1689`), so the existing `if not source_step: continue` guard does not protect them; the reconciler would parse the producer reply instead of the declared path.
4. **`fanout_batch` needs a normal-run test, not a resume test**, because it computes no keys.

### Proposed fix (where it belongs)

1. One pure helper in `backend/agents/capabilities/task_identity.py`, the module `task_loop.py:75`, `wave_scheduler.py:41` and `engine.py:80` already import. It is legal under the import-linter contract that `agents.capabilities` must not import the kernel or `app` (`backend/pyproject.toml:389-393`) because it duck-types `sandbox`.

   ```python
   def parse_step_tasks(parser, reply_text, *, sandbox=None, target=None):
       if hasattr(parser, "parse_preferring_target"):
           return parser.parse_preferring_target(reply_text, sandbox=sandbox, target=target)
       return parser.parse(reply_text)
   ```

2. Route all six through it: replace the if/else at `task_loop.py:213-216` and the elif/else at `wave_scheduler.py:272-277` (the `custom_path` branch stays first); call it at `fanout_batch.py:92` with `sandbox=getattr(runner, "sandbox", None)` and `target=getattr(task_source, "target", None)` (`task_source` may be None); call it at the three engine sites.
3. Sandbox at the engine sites: add an optional `sandbox=None` keyword to the two reconcilers (pass the `sandbox` local that `execute()` already hands to `_rematerialize_artifacts_to_disk` at `:6027`; fall back to `ectx.runner.sandbox`) and to `_first_incomplete_step`. `_compute_resume_offset` builds it the way `resume_run` does at `engine.py:15579-15582`: `RunSandbox(user_id or "anon", _resolve_root_id(run_id, owner_id))`, whose constructor does no I/O (`app/agents/sandbox.py:683` puts `mkdir` in `ensure()`). Every existing caller passes three or four positional arguments and keeps working.
4. `_compute_wave_orphan_allowsets`: before the `source_step` guard add `if getattr(task_source, "kind", None) == "custom_path": continue`. Mirroring `read_custom_path` (`wave_scheduler.py:86-97`) is the upgrade if revision runs should get the orphan gate; moving it beside the helper keeps the engine from importing a strategy module.
5. Keep every `except Exception` fail-safe, and add a `logger.warning` naming the step and the error in each of the three (`:14917`, `:14984`, `:15213`). Today nothing is logged there, which is why the orphan gate has been off for every shipped wave step without anyone noticing.
6. Do not name a parser in the engine (INV-1 / SC-001; `test_sc001_reconcile.py` greps the engine package for name literals). The `hasattr` probe is name-agnostic.

Not required, optional later: the `occurrence_ordinals` then `compute_task_key` comprehension is also copied four times (`task_loop.py:243-256`, `wave_scheduler.py:307-313`, `engine.py:14893-14901`, `:14975-14983`); a `task_identity.task_keys(tasks, upstream_hash)` would remove it. A cleaner but larger alternative is a strategy-owned `derive_tasks` method so the kernel stops re-implementing strategy parsing; it changes the `ExecutionStrategy` port, so it is a separate decision.

### Limits and INFERRED items

- INFERRED: reconcilers 4 and 5 run before `_rematerialize_artifacts_to_disk` (`engine.py:6001` and `:6017` versus `:6027`; they are its inputs). The file is therefore visible to them only if the run's sandbox directory survived to resume (local dev, same host, inside the TTL). On a wiped sandbox the helper falls back to the reply, which is today's behaviour, so nothing regresses. Whether a wiped-sandbox strategy can read a single_shot planner's file at all is NOT established here: the only durable file capture found is the task_loop per-task sibling capture (`kernel_services.py:2254-2330`) and wave fragments (`kernel_services.py:952-1010`); nothing found captures `build/tasks.json`. What would settle it: resume a shipped wave run against an empty sandbox directory.
- INFERRED: how often a reply parses to a different list than the file (S-B2, S-A). Shipped planners reply with one line, so the live shipped behaviour is the swallowed-error path (S-B1); the data-loss path needs a composed planner that echoes a fenced list, or a gate edit of the reply.
- INFERRED, minor: `_first_incomplete_step` takes the LAST matching row of `store.tree()` (`engine.py:15194-15196`, ordered created_at, version, id at `authz.py:355-363`) while the strategy takes the max version across kinds (`engine.py:13958-13963`). Equal for a single-kind producer.
- No sibling cards were minted. Every adjacent finding above (`custom_path`, the sandbox-less `:15202` site, `fanout_batch`) is a site of this same defect and is fixed by the diff above. The wiped-sandbox question is unproven and belongs to a separate investigation if it is ever reproduced.

## Fix (2026-10-01)

Fixed by [FIX-693](20261001-2204-FIX-693.md), as the analysis prescribed: one helper,
`task_identity.parse_step_tasks` (`backend/agents/capabilities/task_identity.py:173`), now serves all six
`task_parser` consumers. The `custom_path` skip sits in `_compute_wave_orphan_allowsets` (`engine.py:14977`).
`_first_incomplete_step` takes `sandbox=` and falls back to `ectx.runner.sandbox`, and `_compute_resume_offset` passes
`RunSandbox(user_id or "anon", _resolve_root_id(run_id, owner_id))`. The three `except` arms log a warning. One
plumbing deviation: the two reconcilers read `ectx.runner.sandbox`, which is the same `sandbox` `execute()` gives
`KernelServices`, instead of taking a new keyword. Observed: `test_iss685_resume_parses_task_file.py` went from
`7 xfailed` to `7 failed`, every one `[XPASS(strict)]`, with the markers left for the 6-verifier. The baselines
`test_resume_mechanical_steps.py` (4 passed) and `test_json_tasks.py` (16 passed) are unchanged.
