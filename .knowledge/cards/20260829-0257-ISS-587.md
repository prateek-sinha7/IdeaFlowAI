## What happened

Sibling defect derived while analyzing `BUG-20260828-082706-runs-id-files` (root card
[ISS-351](20260828-2103-ISS-351.md)) — found by grepping every other `.length`-as-bytes site in
the frontend, NOT by live browser reproduction. **INFERRED**: the mechanism is confirmed by
reading the source below, but nobody has yet reproduced the user-visible symptom in a running
browser. What would settle it: open a prototype run whose generated HTML contains multi-byte
UTF-8 characters (this app's LLM output commonly uses em dashes `—` and arrows `→`), switch the
Prototype Preview to its source view ("index.html"), and compare the displayed "X KB" against
`wc -c`/`new Blob([renderedHtml]).size` on the same string.

## Root cause

Same mechanism as [ISS-351](20260828-2103-ISS-351.md): `String.prototype.length` counts UTF-16
code units, not UTF-8 bytes. `PrototypePreview.tsx:570`, in the source-view header:

```
{(renderedHtml.length / 1024).toFixed(1)} KB · {renderedHtml.split("\n").length} lines
```

`renderedHtml` is the prototype's rendered HTML text; dividing its `.length` by 1024 and
labelling the result "KB" repeats the identical arithmetic mistake ISS-351 found in
`FilesTab.tsx`'s `formatSize()` callers — an independent inline occurrence in a different
component, not a call into a shared, already-broken function.

## Expected vs actual

- **Expected:** the source-view "X KB" label reflects `renderedHtml`'s true UTF-8 byte size.
- **Actual:** the label reflects `renderedHtml.length` (UTF-16 code units), understating the size
  whenever the HTML contains multi-byte UTF-8 characters — the `· Y lines` half of the same label
  is unaffected (`.split("\n").length` is a genuine line count, not a size).
