## Summary

INFERRED sibling of [ISS-338](20260828-2050-ISS-338.md) (`BUG-20260828-050900-settings-profile`),
derived from its root cause rather than independently reproduced.

ISS-338's mechanism is that this codebase has no shared, reusable masked-password-input
component (`frontend/src/components/ui/` has no `PasswordInput` or equivalent) — every password
`<input>` in the app hand-rolls its own optional reveal toggle, so whether one exists depends
entirely on whether that call site's author wired it. The admin "Create New User" modal's single
Password field is a further instance of the same gap: `type="password"` hardcoded, no toggle, and
the file imports no `Eye`/`EyeOff` icon at all.

This one differs from [ISS-338](20260828-2050-ISS-338.md) and
[ISS-576](20260829-0218-ISS-576.md) in shape — there is only one password field here, not a
current/new/confirm group, so there is no "inconsistent with its sibling fields" angle. The
consequence is still real: an admin typing a password for someone else has no way to check what
they typed before submitting, and a typo here means the new user cannot sign in.

## Root cause (read from source, not yet browser-reproduced)

`frontend/src/app/admin/page.tsx`:
- L6-9: icon imports are `Users, Shield, ChevronDown, Search, Plus, Trash2, RefreshCw,
  CheckCircle2, AlertCircle, X, LogOut` — no `Eye`/`EyeOff`.
- L494-499: "Password" field in the "Create New User" modal (`id="new-user-password"`, L496) —
  `type="password"` hardcoded on the same line, no `show`/toggle state, no button anywhere in the
  surrounding block.

## Expected vs Actual

- **Expected:** consistent with a password field elsewhere getting a reveal affordance, or at
  minimum a way for the admin to verify what they typed before creating the account.
- **Actual:** the field can never be shown in plain text; no eye-icon control exists.

## Why the root cause implies this

Same inference as [ISS-576](20260829-0218-ISS-576.md): ISS-338 shows the reveal toggle is
implemented ad hoc per field with no shared primitive enforcing it, which predicts other
hand-rolled password fields are equally likely to be missing one. `grep -rn 'type="password"'
frontend/src` (outside `AccountSettings.tsx`) turned up this field as the second concrete
instance.

## What would confirm it

Cold-navigate to `/admin` as `qa-admin`, open "Create New User", and query the DOM:
`input#new-user-password ~ button` should resolve to `null`.
