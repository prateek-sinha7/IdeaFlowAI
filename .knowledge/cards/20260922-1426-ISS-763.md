# ISS-763

## Description

Sibling of [ISS-721](20260922-1242-ISS-721.md) (bug QA-PS-027,
`BUGS.md#qa-ps-027`), derived from its root cause rather than independently
reproduced.

`SerializedSandboxResolver.resolve` (`serialized_sandbox.py:45-51`) claims
the deliverable "iff the sandbox holds >=1 deliverable file":

```python
if runner.count_sandbox_deliverables(root) > 0:
    return runner.serialize_sandbox_deliverable(root)
return None
```

This is a file-COUNT gate, confirmed by direct read — it never inspects
what is IN those files. A code-gen (`app_builder`-style) agent that never
calls `write_file` but streams a conversational/placeholder response would
normally leave the sandbox empty and this resolver would return `None`
(falling through to `streamed_text`, ISS-721's already-documented gap). But
`_check_artifact_fallback` (`engine.py:8264-8340`, write at `:8333`:
`sandbox.write(filename, output or "")`) is the SAME mechanism ISS-721 cites
for the custom-agent case — the engine's "artifact guarantee" for a
`custom-agent:` step writes the model's raw streamed text to disk whenever
its declared file is missing. That write is exactly one sandbox file, so it
alone satisfies `count_sandbox_deliverables(root) > 0`, and the resolver
serializes it as a "successful" code-gen bundle — a single file holding an
apology, packaged and published as `"completed"`.

## Why the root cause implies this

ISS-721's root cause is that nothing between agent output and
`published_status` ever inspects content, only presence. `serialized_sandbox`
is a fourth, independently-read confirmation of the same pattern already
found in `single_file.py`, `streamed_text.py`, and `ppt.py` — all four
deliverable resolvers were read for ISS-721's "Root cause" section and all
four share the identical gap, each in its own way (verbatim read, verbatim
stream, verbatim stream, or here, count-only).

## What would confirm or refute this

A live `app_builder`/code-gen custom-agent step where the model streams
conversational text and never calls `write_file`, then checking whether
`_check_artifact_fallback` fires and whether the resulting single-file
sandbox is published `"completed"` by `serialized_sandbox`. Not attempted
by this card.
