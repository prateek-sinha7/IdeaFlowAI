# BUG-R04 — clarify-skip (`POST /answers {responses:


### BUG-R04 — clarify-skip (`POST /answers {responses:[], skip_clarification:true}`) returns 200 but the run stays `waiting_for_user` — the `skip_clarification` flag is CORRECTLY wired + consumed (NOT a dead field); the stays-waiting symptom is a pre-existing lost-wakeup race at `clarify_engine.py:284` reachable ONLY by a client that submits BEFORE `questionnaire_ready` (the QA harness, never the FE)  [severity 🟡 minor] [BY-DESIGN (flag) + FIXED ✅ (pre-arm race)]
- **Found by:** R-skip-clarify repro on 2026-07-19 · runs `feb0e17c-752b-4c15-9a09-b8f963d49c20` + `1386315d-a2e0-47b0-b7ff-62f7f6c1e346` (both `user_stories`, FRESH / never-crashed, parked at the clarify questionnaire)
- **Symptom:** `POST /api/runs/{id}/answers` with `{"responses":[], "skip_clarification":true}` returned HTTP 200 `{"ok":true,"count":0}` (accepted) but the run then sat at `waiting_for_user` for 30–100s+ with no new events / no log activity — it did NOT proceed to planner/agents. Reproduced twice. DISCRIMINATING CONTROL: on the SAME two runs, a subsequent NORMAL answer (`{"responses":[{question_id,answer}…]}`, count>0) advanced the run to `generating` immediately (`waiting_for_user`→`generating`). So a normal answer wakes the run's waiter; the empty-`skip_clarification` submit did not. NOT resume-related (fresh runs, no restart) and NOT the od_prototype id-alias class (BUG-R01/R02): `user_stories` is a real registry key.
- **Expected:** "Skip all & run directly" (`skip_clarification:true`) force-proceeds the clarify gate into planner→agents dispatch, per ISS-027.
- **Investigation (root cause, file:line + verdict):**
  - **`skip_clarification` is FULLY WIRED end-to-end — every site enumerated (NOT a dead/ignored field):**
    - **FE (does send it):** `DashboardLayout.tsx:1178-1182` `handleQuestionnaireSkip` → `onSubmitQuestionnaire(activePipelineRunId, [], true)` (wired to `onSkipClarify` at `:1806`/`:1874`); the KAN-90 "Cancel Workflow" path `:1223-1225` sends the identical `([], true)`. → `useWorkflow.ts:150-159` `submitQuestionnaire(…, skipClarification=true)` → `postAnswers({responses, skip_clarification})`. `api.ts:724-731` passthrough.
    - **HTTP handler:** `run_commands.py:116-127` `AnswersCommand.skip_clarification: bool = False`; `:252-277` `submit_answers` → `:274-276` `store.set_questionnaire_responses(run_id, responses, skip_clarification=bool(body.skip_clarification))`; returns `count=len(responses)` (=0 for the skip). The handler does NOT branch on skip beyond forwarding it to the store.
    - **Chat path (2nd caller of the same seam):** `run_commands.py:1025`/`1036` via `route_chat_turn`; `chat_router.py:135`/`160`/`215` threads `skip_clarification`.
    - **Store:** `store.py:44-48` `_questionnaire_force_proceed` dict; `:62-86` `set_questionnaire_responses` stores `responses` + `force_proceed` **AND** calls `event.set()` (`:80-81`) UNCONDITIONALLY (identical for skip and normal); `:95-105` `get_questionnaire_force_proceed`.
    - **Consumer:** `clarify_engine.py:307-309` reads `force_proceed` after `await event.wait()`; `:332-334` `if force_proceed: execution_gate="PROCEED"; return`.
    - **Tests (green offline):** `test_rest_answers_cancel.py:145-157` (HTTP stores `force_proceed=True`); `test_execution_engine.py:192-229` (`ClarifyEngine` force-proceeds: exactly 1 `questionnaire_ready`, no re-ask, PROCEED).
    - **Register lock:** `IMPLEMENTATION-REGISTER.md:3757` lists the `force_proceed` "Skip all" exit as one of "**three legitimate PROCEED exits**." ⇒ INTENDED and wired; the WS→HTTP move did NOT drop it (the HTTP handler calls the SAME `store.set_questionnaire_responses` seam the retired WS `submit_questionnaire` used — docstrings `run_commands.py:15`/`119`/`258`).
  - **Why "the flag is silently ignored" CANNOT be the cause:** `user_stories` compiles `effective_rounds=1` (`compiler.py:240` `rounds=int(clarify_raw.get("rounds",1) or 1)`, default 1; the `user_stories` manifest sets no `rounds`; clamp at `clarify_engine.py:258`). With ONE round the loop ALWAYS returns PROCEED after a SINGLE `event.wait()` return — via `:332` (force_proceed) OR, even if the flag were False, via `:337` (`missing_information` non-empty → fall through) → loop guard `round_num(1) < effective_rounds(1)` false → exit → `:342` `clarification_limit_reached` → `:352` PROCEED (this is exactly `test_clarify_engine_empty_submit_proceeds_after_one_round`, `test_execution_engine.py:233`). There is NO re-ask path for a 1-round pipeline. ∴ a fully-ignored flag would STILL proceed; "stays `waiting_for_user`" ⟺ the waiter never woke (`await event.wait()` at `clarify_engine.py:299` never returned).
  - **Why the waiter didn't wake — the LOST-WAKEUP race (ACTUAL root cause):** `get_artifact_store()` is a module singleton (`store.py:173-184`), so the HTTP handler and the engine share the SAME `_resume_events[run_id]`. The ONLY `clear()` of that clarify event is `clarify_engine.py:284`, and it runs AFTER **(a)** `engine.py:1870` transitions status→`waiting_for_user` and **(b)** the seconds-long LLM question generation at `clarify_engine.py:269` (`_generate_questions`). Reproducing sequence: status→`waiting_for_user` (`engine.py:1870`) fires BEFORE the questions exist → the harness (polling status) POSTs skip → `set_questionnaire_responses` stores `[]`+`force_proceed=True` AND `event.set()` (`store.py:81`) → `clarify.run` finishes generating, reaches `:284` `event.clear()` which **WIPES the set** → `:287` emits `questionnaire_ready` → `:299` `await event.wait()` blocks with nothing set → run sits at `waiting_for_user`. The later NORMAL answer (necessarily sent AFTER `questionnaire_ready`, since it carries real `question_id`s) sets the now-armed event → `:332`/`:337` → PROCEED → `generating`. This matches "skip stays, later normal advances, same run" exactly, and reproduces reliably because the wipe window is LLM-question-generation-wide (seconds). The clear-before-emit comment (`clarify_engine.py:279-282`) only guards a responder acting AFTER `questionnaire_ready`; it does NOT guard a submit that lands between the status flip (`engine.py:1870`) and the `clear()` (`:284`).
  - **FE-usage / severity check:** the FE Skip button is gated behind the RENDERED questionnaire — `laneClarifyOpen = questionnaireQuestions.length > 0` (`DashboardLayout.tsx:1361`), `onSkipClarify=handleQuestionnaireSkip` (`:1806`/`:1874`), and `questionnaireQuestions` is populated only from `questionnaire_ready`. So a real FE user CANNOT POST skip before `questionnaire_ready`; every FE-issued skip lands AFTER `:284`'s clear on the armed waiter → proceeds correctly. Only a client that submits PRE-`questionnaire_ready` (a QA harness firing skip on the first `waiting_for_user`) hits the race. ∴ **🟡 minor** — does not block the documented FE flow.
  - **Distinct from prior entries:** SSE **BUG-004** = `submit_answers` 500 under concurrent load (QueuePool connection leak); here skip returns 200, so different. SSE **BUG-005/010/012** = FE clarify state not bound to the viewed run (a rendering/observation defect). This is a BACKEND pre-arm lost-wakeup — a different mechanism. NOT BUG-R01/R02 (those are the `od_prototype` id-alias empty-roster bail; `user_stories` has a non-empty roster and does not bail).
  - **Classification — PRE-EXISTING, NOT v3.0.** `skip_clarification` is ISS-027; the clear-before-emit ordering (`clarify_engine.py:279-284`) and the status-flip-before-question-gen (`engine.py:1870` vs `clarify_engine.py:269`) are the ISS-027 / clarify-rounds (KAN-74 / T-v1f) design, all predating v3.0. The fresh-run clarify launch path is unchanged by v3.0/resume. (Contrast BUG-R01/R02 = Phase 49 regressions; BUG-R03 = resume output-column gap.)
- **Verdict:** `skip_clarification` handling on `POST /answers` is **BY-DESIGN correct and fully wired/consumed — NOT a silently-ignored flag** (FE→HTTP→store→clarify all present; register-locked as a legitimate PROCEED exit; unit-tested both layers). The observed "200 but stays waiting" is a **real but narrow, pre-existing lost-wakeup race at `clarify_engine.py:284`**, reachable ONLY by a client submitting before `questionnaire_ready` (the QA harness), never the FE. Honest residual: the secondhand repro does not pin the skip's wall-clock order vs `questionnaire_ready`; but the code proves (i) a skip landing AFTER `questionnaire_ready` proceeds, and (ii) a 1-round pipeline proceeds regardless of the flag — so the pre-arm race is the ONLY code path that yields "stays waiting," and the flag itself is not defective.
- **Fix (design only — NOT implemented here; 🟡, optional robustness hardening):** close the pre-arm race in `ClarifyEngine.run`: BEFORE `await event.wait()` (`clarify_engine.py:299`), re-check `await self._store.get_questionnaire_responses(pipeline_run_id) is not None` (an early submit already stored a list — `store.py:78` stores `[]`, NOT `None`, so it is detectable; `force_proceed=True` is already stored too); if present, skip the wait and fall straight into the existing read/merge/force_proceed at `:301-332`. Symmetric for an early NORMAL submit. Alternative: arm+clear the resume event ONCE before `engine.py:1870` flips status→`waiting_for_user` (and drop the `:284` clear), so no `set()` can be wiped after the run is claimable. Either is a small generic change — no workflow-name literal (INV-1/SC-001 safe), reuses the existing seam (INV-12). **Coverage:** RED→GREEN test that seeds `responses`+`force_proceed` in the store BEFORE calling `ClarifyEngine.run` (simulating a pre-`questionnaire_ready` submit) and asserts exactly one `questionnaire_ready` + `execution_gate=="PROCEED"` — currently RED (the waiter blocks on the wiped event). Deferred to its own gsd-quick if pursued (analysis only here).
