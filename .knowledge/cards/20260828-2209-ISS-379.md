## Source

Derived (analyzer pass) from the root-cause investigation of `BUG-20260828-010600-workflows-id-run`,
recorded on [ISS-273](20260828-1653-ISS-273.md). **INFERRED** — not independently reproduced in a
browser; filed from source reading alone. See "What would settle it" below.

## Root cause chain (from ISS-273)

ISS-273's analyzer pass found that `frontend/src/app/[...view]/page.tsx`'s cold-mount effect for
`/workflows/{id}/run` (`:3620-3713`) sets `workflowRunFailed = true` on any fetch failure (`:3706`)
but never routes that flag into `notFound()` — it only stops the loading-`null` return at the
render gate (`:3785-3791`) before falling through to the default `<DashboardLayout>` return.

## This sibling

`workflowRunFailed` (declared `:409`) has exactly one setter in the whole file —
`setWorkflowRunFailed(true)` at `:3706` — and it is never reset to `false` anywhere: not at the top
of the effect before a new fetch starts, and not on the effect's success path (`:3628-3691`).
Contrast the sibling flags in the SAME file that this effect otherwise mirrors:

- `workflowEditAccessDenied` — explicitly reset to `false` at the top of its effect, before the
  fetch fires (`:3480`, comment: "clear a prior denial before this fetch resolves — same reasoning
  as handleSelectWorkflowRun's ISS-017-style reset above").
- `workflowDetailFailed` — reset to `false` on its own success path (`:3546`).
- `runAccessDenied` — reset to `false` at `:2725` (the referenced "ISS-017-style reset").

`workflowRunFailed` has neither reset. Consequence: once a SPA session visits ANY
`/workflows/{id}/run` that fails (the ISS-273 scenario), `workflowRunFailed` stays `true` for the
rest of the session. The render gate at `:3785-3791` reads
`if (parsedView.screen === "workflow-run" && !workflowRunMainView && !workflowRunFailed) return null;`
— its whole purpose (per the comment at `:3777-3784`) is to render nothing while a `workflow-run`
fetch is in flight, "so a visit (or a hard refresh) ... no longer flashes the Dashboard/Home screen
before landing on Canvas or the launch panel." With `workflowRunFailed` stuck `true`, that condition
is false from the first render of a SECOND navigation onward, so the loading-suppression never
engages: the component falls straight through to `<DashboardLayout>` (a Dashboard-content flash)
while the SECOND, entirely valid, `/workflows/{id2}/run` fetch (`:3626`) is still resolving.

## Expected vs actual (INFERRED, needs live reproduction)

**Expected:** navigating in-SPA from a failed `/workflows/{badId}/run` to a valid
`/workflows/{goodId}/run` renders nothing (or a loading state) until the second fetch resolves,
then renders that workflow's launch panel — matching the documented intent of the `:3785-3791` gate.

**Actual (inferred from the missing reset):** the Dashboard flashes in between — or, if the second
fetch is slow enough to observe directly, persists visibly — because `workflowRunFailed` from the
FIRST (failed) visit is still `true` when the SECOND effect's render evaluates, defeating the
"render nothing while loading" guarantee the `:3777-3784` comment describes.

## What would settle it

Reproduce live: sign in, navigate to `/workflows/00000000-0000-0000-0000-000000000000/run` (fails,
per ISS-273), then client-side navigate (not a hard reload) to a real saved workflow's
`/workflows/{id}/run`. Compare against a cold, single-visit load of the same valid id: if the
in-session second visit shows a Dashboard flash the cold visit does not, this is confirmed.

## Fix

Same location as ISS-273's fix: `frontend/src/app/[...view]/page.tsx`'s `workflow-run` cold-mount
effect (`:3620-3713`). Add `setWorkflowRunFailed(false)` at the top of the effect, before the fetch
fires — mirroring `workflowEditAccessDenied`'s existing `:3480` reset — so a fresh attempt always
starts from a clean flag. This is the same effect ISS-273's fix already touches; there is no
separate call site.

## Resolution

Resolved by [FIX-355](20260828-2358-FIX-355.md): `setWorkflowRunFailed(false)` now runs at the top of the
cold-mount effect, before the fetch fires. **Verification stays `pending` on purpose** —
the shipped fix is covered only indirectly (FIX-355's regression run shows a valid id's
`/workflows/{id}/run` still reaching its launch panel); the in-SPA second-visit flash this
card infers was never reproduced live, so nothing observed proves it independently.
