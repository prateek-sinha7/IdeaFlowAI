## Description

Every completed revision run silently lost 7 WorkflowRun output columns — the fourth caller BUG-R03 never wired, and the row it defeated (get_token_usage, FIX-249) had shipped the SAME session (ISS-152). _drive_revision_to_queue (run_commands.py:2764) is the app-layer dispatch path for EVERY *_revision pipeline run — Concierge disposal, chat, and POST /{id}/revisions all funnel into it. Its _persist_terminal_status closure wrote ONLY status/completed_at; it never called _apply_terminal_output_columns (:2237), the function documented as "the SINGLE event→WorkflowRun output-column mapping" and already wired into the launch driver and both resume entry points. BUG-R03/QUICK-260719-hvn (commit d68b8b75) wired three of four callers — its own investigation cleared the revision driver by grepping it for .output/.agent_outputs READS and finding none, never checking whether it WROTE them. Verified against 8a970205-5892-466a-89b0-f613b9dd021d (the only revision that had ever completed in this database — rate 1/1): all 7 columns (output, agent_outputs, token_usage, duration, model_id, deliverable_mimetype, deliverable_filename) NULL despite a real deliverable existing. The engine was innocent: _handle_revision (engine.py:6360-6612) already forwards every event — including pipeline_complete's full payload — verbatim through the caller-supplied websocket_send_fn; the driver simply never accumulated what it already received. Blast radius: Analytics counted every revision as $0 cost AND, as a zero-duration-numerator completed row, actively dragged down avg_duration in the denominator (analytics.py:184-238); the Run Detail KPI strip hid entirely (GET /{id}/summary returned duration=None, token_usage={}, agents=[]); GET /{id}/chain-context returned an empty context block for anything chained off a revision; and it silently defeated FIX-249's get_token_usage tool for every revision run ({"available": false} whenever the column was NULL, which for a revision was always). Severity MAJOR (matches the originating investigation and the orchestrator's independent agreement — top of band, not critical: nothing destroyed, the live deliverable itself was always correct, and the data is fully recoverable from run_events). Fix, run_commands.py only, mirrors _drive_launch_to_queue byte-for-byte: _queue_send now accumulates raw_events unconditionally; monotonic_start = time.monotonic() captured before dispatch; _persist_terminal_status calls _apply_terminal_output_columns(swr, raw_events, model_id=getattr(user, "preferred_model", None) or None, duration_seconds=round(time.monotonic() - monotonic_start, 1)) inside its existing session before sdb.commit() — one session, one commit. Deliberately uses the driver's OWN monotonic clock, never pipeline_complete.total_duration, so ISS-150 (two disagreeing duration numbers) isn't made worse by a third source. _apply_terminal_output_columns's own docstring (which enumerates its callers) corrected to name the revision driver as the fourth. No engine change; _apply_terminal_output_columns itself untouched apart from its docstring — stays the sole writer, no second implementation (INV-3/INV-12). Two items surfaced, deliberately not performed here: the wr.error omission in the SAME function (filed ISS-153 — a failed revision gets no error message at all) and the one-row backfill of 8a970205's 7 columns from its own durable run_events (lossless per this fix's own investigation; left as an open owner decision, not silently performed). A genuine third finding surfaced during this fix's OWN live verification, NOT caused by this fix (filed ISS-154): switching the in-family version picker to an older, non-latest revision whose .output is still NULL shows a blank preview (PreviewPanel.tsx:528-543) — a code path structurally impossible to exercise before this session, since no family had 3 versions to switch between until this fix's own live test created one.

## Root cause

_drive_revision_to_queue's terminal-write closure (_persist_terminal_status) was never updated when BUG-R03 introduced _apply_terminal_output_columns and wired it into the launch driver and both resume entry points — the revision driver was the fourth caller that shipped without the wiring, because the prior fix's own investigation audited it only as a reader of the output columns, never as a writer.
