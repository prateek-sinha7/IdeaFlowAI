# ISS-127

## Title

**`GateCommand.analysis_report` has no length cap anywhere on its path into the composed prompt.** Traced end to end at `e6b24ae5`: `run_commands.py:115` (`analysis_report: str \| None`) → `resolve_gate:264` → `store.set_review_response(instructions=...)` → `engine.py:5788`/`:5840` → `_gate_update_specs` → `engine.py:5511`/`:5552` → `engine.py:5387` `ectx.spec_revision_context = analysis_report` → injected into the composed prompt at `engine.py:9096`. A `grep` for slicing / `MAX_*` / `len(...)` truncation over `agents/` + `app/` on that path returns nothing — so an owner-supplied string of arbitrary size is injected into **every** dispatch of the 3-agent spec-revision sub-pipeline, on a workflow whose measured token ceiling is 37.3M. The sibling field `MessageCommand.analysis_report` (`run_commands.py:698`) shares the gap. **Owner-scoped, so it is a cost-amplification gap rather than a cross-tenant one** (`resolve_gate:222` → `run_engine.py:765` filters on `WorkflowRun.user_id`).

## Source / Evidence

Found by the ISS-070 investigation and named in the ISS-070 row, but **deliberately NOT folded into FIX-241** — it is a different defect with a different fix (a cap plus a 422 at the schema, and an owner decision about what the cap should be), and including it would have obscured the RED/GREEN proof of the discriminator change. Fix shape: a `Field(max_length=...)` on both models plus a decision on the limit; note that unlike the ISS-070 fix this one IS a behaviour change for any client currently sending a long report, so check the FE's `analysis_report` producers first.
