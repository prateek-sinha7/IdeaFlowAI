# ISS-765

## Description

Sibling of the root cause analyzed on **[ISS-705](20260922-1050-ISS-705.md)** for
bug **QA-PS-025** (`BUGS.md#qa-ps-025`). ISS-705 names one UI surface —
`AgentsPopup.tsx`, the flat/"Simple" list composer — whose `StepSelection.strategy`
type (`"fanout_batch" | "wave_scheduler"`, `AgentsPopup.tsx:1397`) makes `task_loop`
unselectable. The custom composer has a SECOND, independent UI surface for the same
job: the node-graph "Canvas" view, whose per-node config panel lives in
`frontend/src/components/workflow/composer/CanvasConfigRail.tsx`. That file imports
the shared `StepSelection` type and the shared `applyLeverPatch` reducer from
`AgentsPopup.tsx` (so the underlying data shape is not duplicated), but its own JSX
— the actual "Fan out over a list" `Toggle` and the Batch/Waves `<select>` — is a
second, independently hand-written UI component that hardcodes the identical
two-value restriction. Fixing only `AgentsPopup.tsx` (type + Simple-view JSX) would
leave a user composing via the Canvas view with no way to pick `task_loop` either —
this is a second call site the root-cause fix must also touch, not a consequence
that disappears once the shared type is widened.

## Expected vs Actual

Expected: whatever lever `AgentsPopup.tsx` gains for connecting a planner to a
`task_loop` worker, `CanvasConfigRail.tsx` offers the same lever — the two composer
views are meant to write to the same `SelectionsMap` via the same shared reducer
(`CanvasConfigRail.tsx:18` imports `applyLeverPatch`), so neither should have less
capability than the other.

Actual: `CanvasConfigRail.tsx`'s own JSX only ever writes `strategy: "fanout_batch"`
(on enabling the toggle, line 1270) or `strategy: wave ? "wave_scheduler" :
"fanout_batch"` (the mode `<select>`, lines 1310/1325-1326) — there is no code path
in this file, independent of `AgentsPopup.tsx`, that can ever write `task_loop`.

## Evidence

- `frontend/src/components/workflow/composer/CanvasConfigRail.tsx:1258-1278` —
  the "Fan out over a list" `Toggle`'s `onToggle` writes
  `patch({ strategy: "fanout_batch", task_source: {...} })` on enable, `patch({
  strategy: undefined, task_source: undefined, fanout: undefined })` on disable.
- `frontend/src/components/workflow/composer/CanvasConfigRail.tsx:1291-1327` — the
  mode `<select>` offers exactly
  `<option value="fanout_batch">Batch — one pass</option>` and
  `<option value="wave_scheduler">Waves — dependency-ordered</option>`
  (lines 1325-1326); its `onChange` (lines 1297-1322) only ever assigns
  `strategy: wave ? "wave_scheduler" : "fanout_batch"`.
  `task_loop` is not a reachable value anywhere in this handler.
  Confirmed by direct read of the whole 1255-1330 block, matching what
  `AgentsPopup.tsx:2200-2327` does line-for-line for the Simple view (same pattern:
  `fanoutOn`/`waveOn` derivation, same two-option `<select>`).
- `frontend/src/components/workflow/composer/CanvasConfigRail.tsx:24` — imports
  `type StepSelection` from `../AgentsPopup` (the same restrictive union ISS-705
  names), and line 410 — `const fanoutOn = sel.strategy === "fanout_batch" ||
  waveOn;` — mirrors `AgentsPopup.tsx:2215` exactly.
- `frontend/src/components/workflow/composer/CanvasView.tsx` and
  `composer/ComposerPage.tsx` mount `CanvasConfigRail` as the Canvas view's config
  panel — confirmed via `grep -n "StepSelection" frontend/src/components/workflow/`,
  which shows `CanvasView.tsx`, `CanvasConfigRail.tsx` and `CanvasNode.tsx` all
  import the same `StepSelection`/`SelectionsMap` types the Simple view uses, i.e.
  this is a genuinely separate rendering path over the same underlying state, not a
  re-export of `AgentsPopup`'s own JSX.
