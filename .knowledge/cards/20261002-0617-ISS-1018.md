# ISS-1018

INFERRED sibling of [ISS-904](20261001-2149-ISS-904.md): the twin of [ISS-401](20260828-2121-ISS-401.md)'s guard. ISS-401 and [ISS-404](20260828-2120-ISS-404.md) came out of one bug-hunter entry (the false
"managed outside the application" claim, once in the admin 409, once in the Security-tab copy) and each got a test. ISS-904 is the
dead ISS-401 test; this card is the ISS-404 one. Same mechanism: `b2a621f84` (2026-09-17) removed the local/break-glass account
type, and a guard for it survived. What would settle it: run the two specs below in the live tier (Playwright against a running,
signed-in app). They were NOT run here, so every "would fail" below is read from code, not observed.

## What the specs assert against what the code does (INFERRED)

- `tests/integration/e2e/suites/09_settings/test_iss404_security_copy.py:50` asserts `status.get("supported") is False` for
  `admin@velocity.ai` ("expected to be break-glass/local"). `backend/app/api/auth.py:907-913` is the only constructor of
  `MfaStatusResponse` (`grep -rn "MfaStatusResponse(" backend/app`) and passes `supported=True` unconditionally; its docstring
  (`:888-890`) still promises `supported=false` for a break-glass account. The precondition cannot hold, so the spec fails before it
  reaches its UI assertions. `backend/app/core/identity.py:15-17`: "local bcrypt/HS256 authentication and the break-glass local-admin
  exemption have been removed entirely."
- `tests/integration/e2e/suites/09_settings/test_settings.py:685` (S-09-13) does `if mfa_status(page).get("supported"): pytest.skip(...)`,
  so it now always skips. Its header (`:6-11`) describes the old pool (the scenarios at `:701`, `:738`, `:756` skip when `not supported`,
  so with `supported` always true they stop skipping). Whether they pass is unknown.
- `tests/integration/e2e/framework/locators/settings_page.py:72-84` keeps `NOT_AVAILABLE`, `EXTERNALLY_MANAGED` and
  `LOCAL_ACCOUNT_NO_MFA`, the copy of an account type that no longer exists.

## The code under test is itself vestigial (CONFIRMED by grep)

- `frontend/src/components/settings/SecuritySection.tsx:241-254`: `if (!status.supported) {...}` renders "Not available for this account /
  This is a local account ... Its password is stored by this application and can be changed from the Profile tab." `supported` is read
  nowhere else (`grep -rn "supported" frontend/src`, non-test), and no frontend test feeds `supported: false`. Against the shipped backend
  the branch is unreachable. If it were reached the last sentence would be false: migration 0038's docstring
  (`backend/alembic/versions/0038_cognito_only_users.py:28-29`) says "No password is stored anywhere in this application after this migration".
- The same stale description sits in `frontend/src/lib/api.ts:742`, `backend/app/api/auth.py:888-890` and `backend/app/models/schemas.py:94-96`.

## Fix direction

The live spec and the dead UI branch are two halves of one thing, and one half is an API contract.

- Specs (test-only): retire `test_iss404_security_copy.py` (its subject, a false claim about a local account, has no account left), drop
  S-09-13 or leave it skipping with a pointer here, fix the `test_settings.py` header, drop the two dead locator constants.
- Product code: `supported` is part of the `GET /api/auth/mfa` response and of the `MfaStatus` type. Removing the field and the branch is
  an API/UX-contract change that belongs to the owner; the safe subset is correcting the three stale docstrings/comments. Do not remove
  the field as part of fixing the specs.
