## What happened

On `/library?tab=hooks`, typing into the "Search hooks" box and/or clicking a
category pill (e.g. "PostToolUse", "SessionStart") narrows the 8-card hook
grid and updates the URL with `?category=<name>`. Clicking a card opens its
full-screen detail view at `/library/hooks/<id>`. Closing that view with the
header's X button navigates back to the bare `/library?tab=hooks` — no
`category` query param, the search box empty, the "All" pill active, and all
8 hook cards visible again. The filter/search state the user had before
opening the detail view is not restored; it is discarded on the round trip.

## Reproduction (3/3, cycle 1)

Validating `BUG-20260828-093757-library-hooks-id` (`bug-hunter/ledger.md`).
Signed in as qa-admin, cold navigation (`/dashboard` → `/library?tab=hooks`,
fresh page load) on every cycle, lane3 Playwright session:

1. **Cycle 1** — search `session` + category pill `SessionStart` → grid
   narrows to 1 card ("Session Context Loader"), URL becomes
   `/library?tab=hooks&category=SessionStart`. Open the card
   (`/library/hooks/session-start`), click the dialog's X close button →
   lands on `/library?tab=hooks` with no `category` param, search box empty,
   "All" pill active, all 8 cards shown.
2. **Cycle 2** — same page reloaded cold; search `quality` + category pill
   `PostToolUse` → narrows to 2 cards, URL
   `/library?tab=hooks&category=PostToolUse`. Opened "Quality Gate"
   (`/library/hooks/post-quality-gate`), closed via X → same reset to bare
   `/library?tab=hooks`.
3. **Cycle 3** — cold reload again; search `config` + category pill
   `PreToolUse` → narrows to 1 card ("Config Protection"), URL
   `/library?tab=hooks&category=PreToolUse`. Opened
   (`/library/hooks/pre-config-protection`), closed via X → same reset.

Reproduced identically on all 3 cold-start cycles; no axis variation was
required. Default qa-admin tier, light theme, first visit to the route on
every attempt.

## Expected vs actual

Expected: closing the hook detail view returns the user to the Hooks tab
exactly as they left it — same search text, same active category pill, same
filtered card set — consistent with round-trip behaviour elsewhere in the app
where returning from a detail view preserves list context.

Actual: both the search text and the category filter are discarded every
time a hook detail view is closed; the tab always resets to its default
unfiltered "All" state, regardless of which search term or category pill was
active before opening the detail view.

## Analyzer confirmation (ANALYZED pass on BUG-20260828-093757-library-hooks-id)

**CONFIRMED, re-read at HEAD** (working tree, uncommitted — other bug-hunt agents are actively
editing `LibraryPage.tsx` in this same shared checkout; every line number below comes from one
unbroken grep+read pass taken together, not stitched across separate reads at different times).

**Root cause: the loss happens on OPEN, not on close.** `closeDetailModal` only round-trips
whatever filter/search state survives to the moment it runs — by the time the X is clicked, that
state is already gone:

1. `hookSearch`/`skillSearch`/`searchQuery` (`LibraryPage.tsx:539,537,522`) are plain
   `useState("")` with NO url-derivation anywhere in the file — nothing ever seeds them from a
   query param, on mount or otherwise.
2. `activeCategory`/`skillCategory`/`hookEvent` (`LibraryPage.tsx:521,536,538`) DO derive from the
   URL, but only via a one-shot `useState(urlCategory)` initializer (`urlCategory =
   searchParams.get("category") || "all"`, `:520`) — read once at mount, never resynced on a later
   URL change.
3. Clicking a hook card calls `router.push(routes.libraryHook(hook.id))`
   (`LibraryPage.tsx:1005`), and `routes.libraryHook`/`libraryAgent`/`librarySkill`
   (`frontend/src/lib/routes.ts:131,127,129`) each build a BARE path — e.g.
   `` `/library/hooks/${slug}` `` — carrying no query string at all. The tab/category/search the
   user had active is not encoded in the URL being navigated to. Contrast `routes.ts:121`'s
   `library()`, which DOES accept `{ tab, category }` — the detail-route builders never grew the
   same shape.
4. That `router.push` remounts the whole `DashboardPage` tree. This is not speculation about
   Next.js in general — it is this exact codebase's own confirmed, tested finding, documented at
   `frontend/src/app/[...view]/page.tsx:3238`: *"T9's router.push remounts THIS page component
   (Next.js does not preserve a dynamic-route page's own instance across a client-side navigation
   to a new URL under the same catch-all — confirmed live: a fresh render-instance id appears
   right after router.push...)"*. `LibraryPage` mounts beneath that same page with no key-based or
   storage-based survival mechanism of its own, so every `useState` in it — including all three
   search fields, and on this path the category ones too — reinitializes against the fresh mount's
   now-bare URL.
5. So the moment the hook card is clicked, the remount re-runs `LibraryPage`'s initializers
   against `/library/hooks/session-start`: `hookSearch` resets to `""` and `hookEvent` resets to
   `"all"`. The T15 `librarySlugAppliedRef` effect (`:587-627`) then finds the hook and opens the
   modal, correcting `mainTab` back to `"hooks"` — but nothing restores `hookEvent`/`hookSearch`.
6. `closeDetailModal` (`:635-641`) reads `mainTab === "hooks"` (correct) and `hookEvent === "all"`
   (already wrong) and pushes `routes.library({tab: "hooks", category: undefined})` →
   `/library?tab=hooks` — exactly the URL this card's own reproduction observed. The search box
   shows empty for the same reason: it was never in the URL to lose a second time.

`closeDetailModal`'s own category-threading logic (`:637-639`) is correct given its inputs — it is
a symptom carrier, not the defect. The defect is upstream, at the OPEN transition, in `routes.ts`'s
three bare detail-path builders plus the total absence of any URL param (or remount-surviving
store) for the three search fields.

**Blast radius — every caller of the three affected route builders, grepped, not assumed:**
`grep -rn "routes\.libraryAgent\|routes\.librarySkill\|routes\.libraryHook" frontend/src` returns
exactly 3 non-test call sites, all in `LibraryPage.tsx` — one per tab (`:828` agents, `:908`
skills, `:1005` hooks) — and all three funnel into the SAME `closeDetailModal`
(`onClose={closeDetailModal}` at `:1038`, `:1055`, `:1058`). The Hooks tab is the one this bug
report exercised; Agents and Skills share the identical shape and are filed as siblings, plus one
more for the browser Back button (which reaches the same already-lost state without ever calling
`closeDetailModal`) — all three INFERRED, not independently reproduced in a browser this pass:
- [ISS-592](20260829-0117-ISS-592.md) — Agents tab (`routes.libraryAgent`, `:828`)
- [ISS-593](20260829-0117-ISS-593.md) — Skills tab (`routes.librarySkill`, `:908`)
- [ISS-594](20260829-0117-ISS-594.md) — browser Back button, all three tabs (T16 effect,
  `:643-665`, never restores search/category)

**Where the fix belongs.** Not inside `closeDetailModal` — it already does the right thing with
what it's given. Two changes, both already-precedented patterns in this same file/module:
1. `routes.ts`'s `libraryAgent`/`librarySkill`/`libraryHook` need to accept and thread an optional
   `{ tab, category, search }` (mirroring `routes.library`'s own params shape), and the three
   `LibraryPage.tsx` open-handlers (`:828`, `:908`, `:1005`) need to pass the CURRENT
   tab/category/search through when pushing into a detail view — so the remount's fresh mount
   reads them back off the new URL, the same way `urlCategory` already does for category today.
2. `searchQuery`/`skillSearch`/`hookSearch` need the same one-shot URL-seed treatment
   `activeCategory`/`skillCategory`/`hookEvent` already get (`:520-521`) — today there is no
   `search`/`q` param anywhere in `routes.library`'s shape, so even a perfect fix to (1) alone
   cannot restore search text; the param has to be added, not merely threaded through.

One change to the three route builders plus one shared URL-seeding pattern extension, not three
separate per-tab patches — every open-handler and `closeDetailModal` already funnel through
`routes.ts` and this one component (ADR-0018: "Every URL in the app is built and parsed by
routes.ts, and all 34 screens render behind one required catch-all segment").

**Why not fully re-verified live in this pass.** This is a source read, not a fresh browser
session — the remount claim rests on the codebase's own documented, tested comment
(`page.tsx:3238`, originally written for the run-execution screen under the same catch-all)
rather than a new click-through of the Library screen specifically. Everything else in the chain
is a direct read (every state declaration, both route-builder sets, both call-site sets). What
would fully settle the one inferential hop: open `/library?tab=hooks`, filter, open a card, and
check whether `LibraryPage`'s own render-instance changes underneath the detail view (a
mount-logged value, or React DevTools' component-tree identity) — matching the "confirmed live"
method the `page.tsx:3238` comment itself used for the run-execution screen.

INVARIANTS AT RISK: none of SC-001 / the kernel-workflow-agnostic invariants — this is a
frontend-only client-routing/state defect, no backend or workflow-engine surface touched. The
one architectural rule the fix must respect is ADR-0018 (all URLs built/parsed through
`routes.ts`, behind the one catch-all) — the fix stays inside that contract, it does not bypass
it with a parallel state channel (e.g. a raw `window.history` call or a bespoke non-`routes.ts`
query string).
