## The symptom

Every reopen of a composed run restarted at step 0. A run that had failed at its
6th of 11 steps re-read four PDFs, re-answered a 37-question clarify gate and
re-ran the Analyst — roughly 25 minutes and several dollars per reopen — while
the product reported it as a resume.

## The root cause

FIX-522 and FIX-558 made resume recompile the run's persisted manifest, and
`resume_run` does exactly that. But `_compute_resume_offset` threw that plan
away and called `compile_for_run(pipeline_type)` itself. For a composed workflow
that call returns the GENERIC `custom` roster (market-research-agent,
swot-analyst, …), so the completeness scan walked step ids the run never had,
found no durable evidence for the first of them, and returned 0.

The comment defending this said the passed-in roster is empty for composed
workflows. That was true once and went stale the moment FIX-366 started
persisting the manifest — the exact kind of stale reassurance a future reader
trusts again.

`_replay_clarify_run`, the clarify-gate restart twin, carried the identical
defect and was worse: it never read `manifest_json` at all.

## What changed

`_compute_resume_offset` now takes the plan the caller already recompiled
(`compiled=`) and scans that. `compile_for_run(pipeline_type)` survives only as
the fallback for a file/registry pipeline with no persisted manifest — the one
case that ever needed it. Where `compiled.steps` is non-empty the roster is
rebuilt from the plan via `_specs_from_plan`, the same seam `execute()` uses,
so a composed workflow no longer validates an empty agent list.

`_replay_clarify_run` now mirrors `resume_run`: it reads `manifest_json`,
recompiles, and **fails closed** if the manifest no longer compiles. Substituting
the generic roster is strictly worse than not replaying — it runs the wrong
pipeline on the user's money.

Offset computation stays best-effort: any exception logs and returns 0. That is
still correct (completed steps are reused via the content-hash key), just
expensive, so it must never be the normal path.

## `_first_incomplete_step` and the R-11 ceiling

A wave index with a `completed` row stays complete even when a later
non-terminal row exists for the same index — that later row is an interrupted
resume re-entry, not evidence the wave never ran.

The documented limitation is not solved: a wave step revisited by a conditional
loop-back reuses `wave_index` from 0, so a first-visit completed row can mask an
interrupted second visit. More broadly, resume indexes by ORIGINAL array
position and assumes each step id appears at most once per run. That is R-11,
a v1 scope cut, still open.

## Verified

Live twice on run `4bdf9398`: offset 6/11 then 7/11, six ingestion steps and 23
of 25 builder tasks skipped, 15 minutes against the original 70. Three new tests
in `test_restart_resume.py`, each checked to fail against the pre-fix logic.

## Note on the recorded evidence

The sync brief placed `_compute_resume_offset`, `_replay_clarify_run` and
`_first_incomplete_step` in `backend/app/api/run_commands.py`. They are not
there and never were — all three are methods of `ExecutionEngine` in
`backend/agents/execution_engine/engine.py` (`:14754`, `:14550`, `:13597` at the
time of writing). `run_commands.py` owns the resume *endpoint*, not the offset.
