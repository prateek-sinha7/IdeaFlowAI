# No reduced-motion policy in the frontend (class-level sibling of QA-KB-001)

Sibling of QA-KB-001 and its root card [BUG-018-GROUNDED-CONTEXT](20260717-1903-BUG-018-GROUNDED-CONTEXT.md). The footer strip is one instance of a missing app-wide policy; the same root cause is why nothing else gates either.

**Evidence level:** CONFIRMED for the absence of any gate (grep below) and for how the installed `motion` 12.38.0 resolves the preference (observed on a stand-in panel; see the root card's analysis). INFERRED for how each listed component looks under the OS setting: none of them was run. What would settle it: Chrome DevTools > Rendering > "Emulate CSS media feature prefers-reduced-motion: reduce" and a walk through the listed screens.

## Condition

The OS or DevTools reports `prefers-reduced-motion: reduce`, on any page that renders one of the animations below.

## Expected vs actual

- Expected: positional motion (slides, scale, rotate, height/width reveals, ambient drift) is suppressed or instant; CSS animations and transitions are neutralised; nothing loops indefinitely.
- Actual: every animation plays as designed.

## Why the root cause implies it

`MotionConfigContext` defaults to `reducedMotion: "never"` (`framer-motion/dist/es/context/MotionConfigContext.mjs:10`), and the app never opts in:

```
$ grep -rn -i -E "prefers-reduced-motion|useReducedMotion|MotionConfig|reducedMotion|motion-safe|motion-reduce" frontend --exclude-dir=node_modules --exclude-dir=.next --exclude-dir=.git
(no output, exit 1)
```

BUG-018 Part B was the only place the requirement was ever written down, for one component, in a card, and no test enforces it (`grep -rln matchMedia frontend/src frontend/e2e` finds nothing, and no Playwright config sets `reducedMotion`).

## Instruments (CONFIRMED on the installed library; stand-in panel, OS preference stubbed to reduce)

1. One `<MotionConfig reducedMotion="user">` at the app root covers the first row for all 50 files. Observed: a numeric height jumped to 100px at the first sample while opacity still ramped 0.10 to 1.00 over ~214 ms. It does not cover opacity.
2. `<MotionConfig skipAnimations>` makes every value instant, opacity included (observed: opacity 1.00 at the first sample). It is not tied to the OS preference by itself (a provider would have to pass it the result of `useReducedMotion()`), and it freezes loading indicators outright.
3. One `@media (prefers-reduced-motion: reduce)` block in `globals.css` neutralising `animation` and `transition` covers the CSS rows. It cannot reach motion/react, which writes inline styles from JS.

Suggested shape: 1 plus 3 as the app policy, with a per-site `{ duration: 0 }` gate where the requirement is literally "instant" (QA-KB-001 and its live-panel sibling). Whether the infinite status pulses (RunChatLane's dots, TypingIndicator, `animate-pulse`) should freeze under reduce is a design call, since a frozen dot can read as stalled; decide it in the fix card rather than by default.

## Placement and hazards

- The root layout is `frontend/src/app/layout.tsx`, a server component composing `AuthSessionProvider > StoreProvider > ServiceBusyProvider > SkillsHooksProvider > RunConnectionProvider`; the other providers live in `frontend/src/providers/`. `frontend/AGENTS.md` says to read `node_modules/next/dist/docs/` before writing code against this Next version.
- 69 test files mock `motion/react` or `framer-motion` with factories. A root provider is not rendered by component tests, so it needs no mock changes. A per-component `useReducedMotion()` would hit them: observed on a scratch copy, one factory without `useReducedMotion` failed all 14 tests of `RunChatLane.fix192.test.tsx`.
