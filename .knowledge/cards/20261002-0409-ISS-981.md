# ISS-981

Found while analysing QA-KB-057 ([ISS-905](20261001-2149-ISS-905.md)). This is a sibling by adjacency, not the same
fault: ISS-905's two faults are in the TEST fixture. These two are behaviours of the guard itself, at the edges the
file's three scenarios never reach, so the 8 tests will not catch them once ISS-905 is repaired. Both were observed
with a throwaway harness replica that edits no repo file (`evidence/qa-kb-057/04-analyze-probe-output.txt`, scripts
`probe_seeds.py` and `probe_guard_edges.py` beside it, section 3).

## What happens (CONFIRMED, observed 2026-10-02)

The guard's happy path is fine and is what the 8 tests encode: brief plus legacy block plus an admissible
`source_workflow_run_id` gives HTTP 200, the persisted `WorkflowRun.input` is the bare brief, and exactly one
`legacy_context_block_stripped` row exists, backfilled with the minted run id (probe E2).

**A. A refused launch leaves an orphan audit row.** A request carrying brief plus legacy block plus a source run that
admission refuses (probe E1: HTTP 422 `source_payload_missing`) leaves two audit rows and no run:
`('legacy_context_block_stripped', run_id='pending', source_ref=<source>, outcome='stripped')` and
`('chain_refused', run_id=<source>, ...)`. The `pending` row can never be backfilled.

**B. A message that is only the legacy block is not stripped, but is audited twice as stripped.** With an admissible
source (probe E3: HTTP 200, `chain_v2_accepted: true`) the persisted `WorkflowRun.input` is the whole
`=== CONTEXT FROM PREVIOUS PIPELINE ===` block, so the v2 `.context/` payload and the legacy block both reach the run,
and TWO `legacy_context_block_stripped` rows (both `outcome='stripped'`) are written for that one run.

## Why (working-tree line numbers; HEAD 024c03ef8 in brackets)

1. The endpoint-level guard in `launch_run` (`backend/app/api/run_commands.py:3438-3472` [3421-3455]) persists the
   audit row at `:3446-3469` with `run_id="pending"`. It runs BEFORE the empty-brief gate (`:3490`), the tier gate
   (`:3510`), the capacity gate (`:3514`), the agent, template, model and image gates, and `admit_chain_launch`
   (`:3818`). The only place that replaces `pending` is `:3889-3914` [3849-], reached only after `_launch_run_core`
   returns. A refusal at the admission gate (observed) skips it. The same follows by code order for every other
   `_reject` between `:3472` and `:3863` (INFERRED: only the admission refusal was run).
2. When the text before the marker is empty, both guards fall back to the original content: `:3472`
   `content = _stripped if _stripped else content` and `:3016` `content = _stripped_content if _stripped_content else content`.
   The endpoint-level comment (`:3470-3471`) calls it "edge case: message IS the context block". Both then log
   `outcome="stripped"` unconditionally. Because the endpoint guard falls back to the ORIGINAL content, the marker is still present when
   `_launch_run_core`'s own guard (`:2978-3018` [2962-3000]) runs, so it writes the second row.
3. That core-level guard is otherwise unreachable. `_launch_run_core` has two callers: `launch_run` (`:3863`) and
   `run_trigger_workflow` (`backend/agents/execution_engine/kernel_services.py:1664`), which passes
   `source_workflow_run_id=None` (`:1679`) and no `request_source_workflow_run_id`, so `_strip_trigger_id` is falsy.
4. Nothing queries these rows. In `backend/` and `frontend/src` the string `legacy_context_block_stripped` appears in the two
   writers (`run_commands.py:3000`, `:3454`), a docstring (`backend/agents/capabilities/hooks/provenance_audit.py:37`) and a
   documentation constant (`frontend/src/lib/workflowChaining.ts:130`). `run_provenance_audits.run_id` has no foreign key
   (`backend/app/models/run_provenance_audit.py:39`), so the placeholder inserts silently on Postgres too. The damage is
   audit-trail accuracy, not a user-visible failure.

## What is a defect and what is a decision (INFERRED until the owner says)

- A is a defect by the table's own contract: a row whose `run_id` is a placeholder no query can resolve, claiming a
  strip for a launch that never minted. The refusal already has its own row (`chain_refused`).
- B has two parts. The audit rows claiming `stripped` when nothing was stripped, and the duplicate row, are plainly
  wrong. Whether the retained block is wrong is a product call: the endpoint comment keeps it deliberately
  (presumably so a block-only message does not trip the ISS-155 empty-brief gate at `:3490`; INFERRED, the comment does
  not say why), but the shipped contract text says "the two are never combined"
  (`frontend/src/lib/workflowChaining.ts:120-128`, Req 13 AC 11 / Req 21 AC 10). Settle it before changing behaviour.

## Proposed fix (not applied)

Write the strip audit once, after the outcome is known: only when the content actually changed, and with the real run
id (same transaction as the mint, or backfill-and-delete on refusal). Drop one of the two copies of the guard: the
endpoint-level one already covers every HTTP launch, and the `_launch_run_core` copy fires only as the second pass of
the block-only case, so it and its `request_source_workflow_run_id` parameter can go (that parameter is pinned by the
signature test at
`backend/tests/integration/api/test_rest_run_launch_api.py:1044-1077`, which would change with it). Then pin A, B and
the exactly-one-row happy path in `test_duplicate_context_guard_api.py`.
