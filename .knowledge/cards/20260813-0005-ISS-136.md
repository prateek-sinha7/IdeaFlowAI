# ISS-136

## Resolution (QA-KB-008, fixed 2026-10-01)

Resolved by [FIX-674](20261001-2114-FIX-674.md), which applies the recommended fix from the analysis below. The
`pipeline_reconnected` arm (`frontend/src/hooks/useWorkflow.ts:1505-1518`) no longer has a private list. It gates on
`TERMINAL_MARKER_BY_STATUS` and returns `applyTerminalStatus(prev, status)`. As a result, `degraded` now resolves the
run, and the phantom `"error"` member is gone. `npx vitest run src/hooks/useWorkflow.reconnect.test.ts` now reports
4 failed | 7 passed (11). All 4 failures are "Expect test to fail" on the `it.fails` cases, which is the XPASS signal.
The markers are left in place for the verifier.

## Analysis (QA-KB-008, analyzed 2026-10-01)

**Verdict.** Root cause CONFIRMED (read and run). It is narrower than this card's title: one reducer arm, not four lists.
And the symptom in the bug report (a degraded run stuck on "running" after reconnect) is NOT reachable in the shipped
product, because nothing emits the frame that arm handles. Effective severity is low and latent; the ledger's High
reflects the reported symptom, not reachability.

### Root cause (CONFIRMED)

`frontend/src/hooks/useWorkflow.ts:1505-1506`, inside `case "pipeline_reconnected"` (`:1469-1547`):

```ts
const TERMINAL_STATUSES = ["completed", "failed", "cancelled", "error", "diverted"];
if (status && TERMINAL_STATUSES.includes(status)) {
```

The arm owns a private terminal vocabulary instead of the one FIX-245 made canonical in the same file,
`TERMINAL_MARKER_BY_STATUS` (`:379-385`: completed, cancelled, failed, degraded, diverted). The private copy differs in
two members. It has `"error"`, which is not a run status anywhere (`WorkflowStatus`, `frontend/src/types/index.ts:405`;
backend `TERMINAL_RUN_STATUSES`, `backend/agents/execution_engine/engine.py:3393-3399`; the `WorkflowRun.status` comment,
`backend/app/models/workflow.py:50-56`). And it lacks `"degraded"`. A `{live:false, status:"degraded"}` frame fails the
`includes` at `:1506`, skips the terminal branch, and lands on the non-terminal tail `return true` at `:1546`: no
`setPipelineState` call, no `sessionStorage` clear.

Provenance (read-only git): the array was born in f5ee356fa (2026-06-11, "feat(12-08): handle pipeline_reconnected") as
`["completed","failed","cancelled","error"]`; 887ccfe96 (2026-08-21, spec 014) appended `"diverted"` to it and, again, not
`"degraded"`. It is the one copy nothing pins: `frontend/src/hooks/__tests__/terminalStatusReconcile.test.ts:132-155` pins
only `TERMINAL_MARKER_BY_STATUS` equal to `page.tsx`'s `REOPEN_TERMINAL_STATUSES`.

Census of terminal-status definitions in non-test `frontend/src` today (this card's original line numbers have moved):

| where | members | note |
|---|---|---|
| `page.tsx:85` `REOPEN_TERMINAL_STATUSES` | completed failed cancelled degraded diverted | canonical |

### Fix: accept the agreed floor, overrule it as the complete fix

The agreed minimal fix (add `"degraded"`, keep `"error"`, one test) is ACCEPTED as sufficient to close the reported
symptom. It is correct but incomplete, for two reasons.

1. The arm's terminal branch stays marker-less. After the floor, a `degraded` frame resolves `isRunning:false` with no
   `degraded` marker, which `StepsOverviewSpine.tsx:464-467` renders as "Run complete" (sibling
   [ISS-864](20261001-2103-ISS-864.md)). That is already true today for `failed` and `cancelled` (harness rows B and C below).
2. It keeps a fifth hand-edited list that has already drifted once (diverted added, degraded never): the INV-12 failure
   FIX-245 was written to stop. [ISS-142](20260813-0005-ISS-142.md) says the same about any future status handling
   on this path: "MUST route through the shared `terminalMarkers`/`applyTerminalStatus` rather than introducing a fresh
   status list".

Recommended fix, in the same arm (`useWorkflow.ts:1505-1533`): delete the private array and the hand-built patch, guard on
membership in the canonical map, and delegate to the shared one-way helper.

```ts
if (status && Object.prototype.hasOwnProperty.call(TERMINAL_MARKER_BY_STATUS, status)) {
  try { sessionStorage.removeItem("active_pipeline_run_id"); sessionStorage.removeItem("active_pipeline_type"); } catch { /* non-fatal */ }
  setPipelineState((prev) => applyTerminalStatus(prev, status));
  return true;
}
```

Why there: `applyTerminalStatus` (`:401-469`) is already the definition of what a terminal status does to run state for the
reopen path, and `terminalMarkers` (`:388`) for the live arms. This arm is the only terminal path that bypasses both.

Behaviour deltas the fixer must know:

- `"error"` stops being terminal in this arm. Nothing emits it. If the owner wants zero change on that unreachable path,
  keep an explicit `|| status === "error"` guard; no test pins it either way.
- `failed`, `cancelled` and `degraded` now stamp their marker (this is the sibling fix).
- Still-running/thinking agents go to idle on a failure terminal (today they are left as-is). The existing `failed` test
  seeds idle agents, so it is unaffected.

Checked in a scratch harness: `applyTerminalStatus` returns the results the existing `completed` and `failed` tests assert
(isRunning false; agents all done / all idle; completedCount 2) plus the marker, and returns its input untouched for
`running` and `error`. So ISS-137's worry that routing through the shared mapping "breaks a green suite" does not hold for
the existing 7 cases. INFERRED for the real suite until it is run after the fix.

An alternative that makes this bug moot is ISS-137's remedy: delete the dead arm, its two routing entries,
`useWorkflow.reconnect.test.ts`, and the e2e `reconnected()` helper plus TS-S-03. Not recommended inside this fix:
`mockSse.ts:305-307` retains the arm on purpose for the reconnect specs, so removal needs the owner's sign-off. It does not
block this bug.
