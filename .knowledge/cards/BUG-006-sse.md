### BUG-006 — Run-screen pipeline-type label shows the wrong (stale) type for a history-opened run  [🟡 minor] [FIXED ✅]
- **RESOLVED:** FIXED (quick 260716-lb6, 616d481a) — live-proven

- **Found:** 2026-07-16 · live Bedrock QA · surface run screen → left conversation lane header (`LaneRunHeader`, `data-testid="lane-run-type"`), on a **history/recents-opened COMPLETED app_builder run** ("A URL shortener web app", 15 app_builder agents, "app" deliverable — verified app_builder).
- **Symptom:** The small pipeline-type chip above the lane title read **"USER_STORIES"**, not the run's real type (app_builder → would render "APP_BUILDER"). Everything else on the screen is the OPENED run's correct data — the 15 app_builder agents, audit, and deliverable all render correctly; only the type LABEL is stale. Sibling of BUG-001 (the lane TITLE had the same "bound to the wrong run" defect, fixed today in quick 260716-j1u) and of BUG-003's L2 aggravator (the revise-handler selection, also fixed today) — here the third consumer of the same stale state: the displayed TYPE.
- **Root cause (investigation agent — read `.planning/SSE-QA-BUG-LOG.md` BUG-001/003 + the impl-register run-screen phases 32/39/44; grep-confirmed all 19 `setWorkflowType` writers + git-blamed the symptom line and both sibling fixes):**
  - **Symptom site → cause site.** The chip renders `{type}` at `frontend/src/components/chat/LaneRunHeader.tsx:231` (inside `data-testid="lane-run-type"`, `:228`; CSS `uppercase` at `:229` is why it shows "USER_STORIES" not "user_stories"). `type` = `runType || humanizeRunType(pipelineState?.pipeline_type)` (`LaneRunHeader.tsx:184`) — when `runType` is a truthy string it is used **verbatim** (the `humanizeRunType` fallback is only reached when `runType` is falsy). Feed chain: `frontend/src/components/layout/DashboardLayout.tsx:1745` `runType={workflowType || pipelineState?.pipeline_type}` → `frontend/src/components/chat/RunChatLane.tsx:641` (prop) → `:1172` `runType={runType}` (straight pass-through, no transform) → `LaneRunHeader`.
  - **The mechanism (`DashboardLayout.tsx:1745`).** The displayed type is bound to `workflowType` — DashboardLayout-internal state (`:250-256`, default `"user_stories"`) — which is **only** auto-synced from the live pipeline's declared type by the effect at `DashboardLayout.tsx:330`, gated on `if (pipelineState?.isRunning)` (`:331`, `setWorkflowType(normalised)` at `:345`). On a **completed** history/recents reopen `isRunning` is false → the sync effect never fires → `workflowType` stays stale (its `"user_stories"` default, or whatever the last launched/selected run set it to). The reopen path (`page.tsx handleSelectWorkflowRun`, reached via `onSelectWorkflowRun`/`onOpenRun` at `DashboardLayout.tsx:1505`/`:1539`) sets the viewed-run identity `contentSourceRunId` but **never** `workflowType` — verified: none of the 19 `setWorkflowType` writers (`:250`/`:345`/`:522`/`:531`/`:539`/`:551`/`:569`/`:583`/`:639`/`:688`/`:757`/`:839`/`:856`/`:937`/`:1042`/`:1542`/`:1553`/`:1562`/`:1571`) is on the history-reopen path; they are all launch/feature-select/revise/chain paths. Because `workflowType` is truthy, `workflowType || pipelineState?.pipeline_type` short-circuits to the stale value and never consults the viewed run's real type. The viewed run's type IS available and is exactly what the two sibling fixes already read — `recentRuns.find((r) => r.id === contentSourceRunId)?.type` (`:1250`, `:1351`).
  - **Same broken assumption as BUG-001/003 — "the on-screen run's type is `workflowType`."** That holds for the primary launch flow (the gated effect syncs `workflowType` while `isRunning`), but is false the moment a completed non-latest run is opened from history/recents. The assumption has **three** consumers in this component: (1) the lane TITLE, (2) the REVISE-handler selection, (3) the displayed TYPE chip. The quick-260716-j1u sweep fixed (1) and (2) but missed (3).
  - **PRE-EXISTING, and an unlogged miss in the BUG-001/003 sweep.** `git blame`: the buggy `runType={workflowType || pipelineState?.pipeline_type}` (`:1745`) = **`5003aca47` "feat(39-05): wire the lane Back-to-history + run metadata into the run shell" (imran-hex, 2026-07-11, Phase 39 / RUNUI-06)** — the SAME commit that introduced BUG-001's original always-`recents[0]` title mis-binding. The `isRunning` gate on the sync effect (`:331`) = `0590c2448` (2026-05-19), pre-existing. Today's quick-260716-j1u cluster rebound the two sibling consumers of the same stale `workflowType`: the lane TITLE (`cc2f98f74`, `viewedRun` at `:1349-1353`) and the REVISE-handler selection (`8b4e2eb7b`, `viewedRunType`/`effectiveReviseType` at `:1248-1252`), both keyed on `recentRuns.find(r => r.id === contentSourceRunId)`. It did **not** touch the DISPLAY-type prop at `:1745`, and j1u's `deferred-items.md` (DEF-BUG-002-generic-reopen + WARNING-2) does **not** log it — so BUG-006 is a genuine unlogged sibling that slipped the sweep (fable step 8). Notably the fix's input is already computed and in scope but unused by the display: `viewedRunType` (`:1248`) / `effectiveReviseType = viewedRunType ?? workflowType` (`:1252`). Same **"run-screen state not bound to the viewed run"** class as BUG-001 (title), BUG-002 (open path), BUG-003 (revise type), BUG-005 (clarify) — here the type LABEL.
- **Fix (PROPOSED — investigation only, NOT applied):** bind the displayed type to the VIEWED run, mirroring the two sibling fixes already in this component. Reuse the in-scope `effectiveReviseType` (= `viewedRunType ?? workflowType`, `:1252`), one contiguous edit at `DashboardLayout.tsx:1745`:
  ```
  - runType={workflowType || pipelineState?.pipeline_type}
  + runType={effectiveReviseType || pipelineState?.pipeline_type}
  ```
  (Equivalent, if decoupling from the revise-named const is preferred: `runType={(viewedRunType ?? workflowType) || pipelineState?.pipeline_type}` — identical value.) Both consts are in scope at `:1745` (proven: `activeReviseHandler`, built from `effectiveReviseType` at `:1253`, is consumed at `:1748`; `runHeaderTitle` at `:1354` is consumed at `:1744`). Behaviour by flow:
  - **Fresh launch / live** (`isRunning` true or `contentSourceRunId` null) → `viewedRunType` undefined → `workflowType` (kept correct by the gated sync effect) → **byte-identical to today, no regression**.
  - **Live-complete / history-reopen** (`isRunning` false, `contentSourceRunId` set) → `viewedRunType` = the viewed run's `type` → **correct label (bug fixed)**.
  - **Viewed run older than the recents window** (`find` → undefined) → falls back to `workflowType` → no worse than today (strictly no regression; label stale only for out-of-window runs, same caveat as BUG-001).
  - Minimal + SC-001-safe: one-line edit in a guarded component, keys only on generic run identity (`contentSourceRunId`/`run.id`/`run.type`), **zero** workflow-name literal added, no `page.tsx` change, no new state/prop. Rejected alternative: reorder to prefer `pipelineState?.pipeline_type` — depends on the DEF-44-12-4 durable seed populating `pipeline_type` on reopen (unverified) and diverges from the sibling fixes' proven `recentRuns.find` source.
  - **Optional polish (separate, pre-existing, out of scope):** the chip shows the type RAW (the `runType` branch bypasses `humanizeRunType`, `LaneRunHeader.tsx:184`) then CSS-uppercases it (`:229`), so it renders "APP_BUILDER", not "App Builder". Wrapping in `humanizeRunType(...)` would prettify but also changes the launch-flow formatting — a cosmetic decision unrelated to the wrong-TYPE defect; do not fold it into the minimal fix.
