## What happened

INFERRED sibling of [ISS-331](20260828-1840-ISS-331.md), derived from a
source-code read while analyzing that bug — not yet independently driven
live in a browser.

`frontend/src/components/preview/PrototypePreview.tsx`'s "Copy all" source
button shares ISS-331's exact failure mode (silent on rejection, not a false
positive like the other preview-surface siblings), because it gates
`setCopied(true)` on the promise settling — it just never handles the
rejection branch.

## Root cause (confirmed by direct read — same silent-on-failure mechanism as ISS-331)

`frontend/src/components/preview/PrototypePreview.tsx:391-398`:

```
const handleCopySource = useCallback(() => {
  if (!renderedHtml) return;
  navigator.clipboard.writeText(renderedHtml).then(() => {
    setCopied(true);
    if (copyTimeoutRef.current) clearTimeout(copyTimeoutRef.current);
    copyTimeoutRef.current = setTimeout(() => setCopied(false), 2000);
  });
}, [renderedHtml]);
```

Unlike the fire-and-forget siblings, this one DOES gate `setCopied(true)` on
the `.then()` callback, so it will not falsely report success. But there is
no `.catch()` on the chain: if `writeText` rejects, the `.then()` callback
never runs, the rejection is an unhandled promise rejection, and the button
is stuck reading its default state forever — the identical mechanism ISS-331
confirms for `HookDetailModal.handleCopy`, just written with `.then()`
instead of `await`.

**What would confirm this live:** open a prototype run's preview, click
"Copy all" in the source-view toolbar, and reproduce ISS-331's protocol
(check `document.body.innerText` / button state before and after) on a
condition where the write is known to reject.
