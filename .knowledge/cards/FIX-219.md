## Description

After FIX-216b, od_ppt runs triggered via the Concierge revision chip launched
`ppt_revision` (2 agents: Deck Revision + Deck Assembly) instead of
`od_ppt_revision` (1 agent).

## Root Cause

Two gaps:

**Gap 1 — FIX-216b over-broad map:** `_OD_BASE_MAP = {"od_prototype": "prototype", "od_ppt": "ppt"}`
was applied unconditionally for ALL tiers. `od_ppt_revision` is entitled on every
tier that can launch `od_ppt` (basic/pro/enterprise). The `od_ppt → ppt` remapping
was wrong — it should never apply because `od_ppt_revision` always has agents and is
always entitled when `od_ppt` itself is entitled.

**Gap 2 — Stale durable proposal rows:** Existing `concierge_proposal` DB rows
created before this fix stored `params.target = "ppt_output"` for od_ppt runs.
At confirm time, `_dispose_concierge_proposal` read `target = "ppt_output"` from
the durable row → `revision_pipeline_type = "ppt_revision"` → 2 agents.

## Fix

**Gap 1:** Remove `od_ppt` from `_OD_FALLBACK_MAP` entirely. Only
`od_prototype → prototype` fallback remains (for hexaware tier where
`od_prototype_revision` is not entitled).

**Gap 2:** After reading `target` from durable params, apply a stale-proposal
correction: if `wr_type` is `od_ppt` (or `od_ppt_revision`) AND `target == "ppt_output"`,
remap to `"od_ppt_output"`. This silently corrects any old proposals without
requiring the user to dismiss and re-request.
