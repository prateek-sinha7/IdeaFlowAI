## Summary

`AuditTab` (route `/runs/{id}/audit`) claims to render "every gate, scan,
validation and exec, attributed and exportable" from an "Immutable, owner- and
workspace-attributed log." For a completed run
(`b9feac1c-ec21-4531-8ba7-bb391786993e`) it shows "100 records" — "Governance
96," "Security 4," "Activity 0" — but the run's dedicated gate-events endpoint,
`GET /api/runs/{id}/gate-events`, returns `{"gate_events":[]}` (zero real gate
checkpoints), and the raw event stream (`GET /api/runs/{id}/events?after=0`,
9740 events) contains exactly one `gate_status` event. The 96 rows labelled
"Gate"/"Governance" instead correspond in count to ordinary `tool_call` (44) +
`tool_result` (44) + 8 before/after-step markers from `agent_start`/
`agent_complete` — none of which are governance gates.

**Root cause** — `frontend/src/components/results/AuditTab.tsx`, the loop over
`hooksEnv.hook_runs` (from `getRunHookRuns`, lines 558-585):

```
568: const fineCategory = deriveFineCategory("gate", hookName, step);
...
574:   category: "gate",
```

Every row returned by `getRunHookRuns` — including ones whose `hook` field is
literally `"audit logger"` with `event` values `before_step`/`after_step`/
`tool_call`/`tool_result` (ordinary pipeline telemetry, not policy
checkpoints) — is unconditionally assigned `category: "gate"` and fed
`"gate"` as the base category into `deriveFineCategory`. There is no branch
that routes non-gate hook names (anything not matching the `/secret|scan/`
regex used elsewhere in the same function, e.g. `buildHookLabel` line 143) to
the `"activity"` or `"behavioral"` fine categories that already exist in
`FINE_CATEGORY_META` (lines 220-264) for exactly this kind of lifecycle
event. The result: any `audit logger` hook_run row is indistinguishable from
a real governance gate in the UI's counts and filters.

Compounding this, `buildHookDetailRows` (lines 151-182) only produces
row-specific detail when `detail.detector`/`matched_keys`/`match`/`marker`/
`action`/`reason` are present. `audit logger` hook_run rows carry a non-null
but field-less `detail` object, so every one of them falls through to the
same fallback: `Action: allowed` (line 175's `fallbackAction` for a
non-block/non-warn `outcome`) and `Outcome: continue`, paired with the
`"gate"` fine category's static `whatIs` text (lines 233-235: "A governance
gate — a checkpoint where the run paused for a policy decision..."). Once
expanded, every one of the 96 rows shows byte-identical detail regardless of
its real label or timestamp — confirmed by expanding "audit logger — before
step" (01:50:11 PM) and "audit logger — tool call" (01:56:11 PM): both
produce the identical "What is this?" / `Action: allowed` / `Outcome:
continue` block.

## Reproduction — confirmed 3/3, cycle 1 (fully cold navigation each time)

1. Navigate fresh (full page load, not a soft nav) to
   `http://localhost:3000/dashboard`, then to
   `http://localhost:3000/runs/b9feac1c-ec21-4531-8ba7-bb391786993e/audit`,
   signed in as `qa-admin@flowinqa.com`.
2. Audit tab header reads "100 records" / "Governance 96" / "Security 4" /
   "Activity 0" — every cycle, deterministic.
3. `fetch(/api/runs/{id}/gate-events)` → `{"gate_events":[]}` (200 OK).
4. `fetch(/api/runs/{id}/events?after=0)` → 9740 events, `gate_status: 1`,
   `tool_call: 44`, `tool_result: 44` (matches the fabricated Governance
   count: 44+44+8=96).
5. Expand row "audit logger — before step — 01:50:11 PM" (Gate/Passed) and
   row "audit logger — tool call — 01:56:11 PM" (Gate/Passed, ~6 minutes
   later, different label) — both detail panels are byte-identical: "What is
   this? A governance gate — a checkpoint where the run paused for a policy
   decision or a human approval before it was allowed to continue." /
   `Action: allowed` / `Outcome: continue`.

Reproduced identically on cycles 2 and 3 (fresh `/dashboard` → `/runs/{id}/audit`
navigation each time, same 100/96/4/0 split). No axis variation was needed —
the discrepancy is deterministic on every load of this completed run, driven
by data shape (the run's `hook_runs` rows), not timing or account.

## Expected vs Actual

**Expected:** "Governance"/"Gate" rows reflect real gate-events / behavioral
checks; non-gate `hook_runs` telemetry (audit-logger step/tool markers) is
categorized as `"activity"` (the fine category that already exists for
exactly this), and detail panels show data specific to that row.

**Actual:** All `hook_runs` rows are force-categorized `"gate"` regardless of
`hook` name, inflating the Governance count from 0 real gates to 96, and the
generic per-row fallback in `buildHookDetailRows` makes every one of those 96
rows expand to identical, non-attributable boilerplate — directly
contradicting the tab's own "attributed" claim.
