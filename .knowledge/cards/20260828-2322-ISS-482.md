## Sibling of ISS-320 (INFERRED — not yet reproduced)

Filed while analyzing **BUG-20260828-095800-settings-constitution-r2** (root card
[ISS-320](20260828-1802-ISS-320.md)). ISS-320's own reproduction (cycle 3) established that
the Constitution editor holds an **unsaved draft** distinct from the persisted backend value —
typing into the textarea without clicking "Save constitution" leaves a local-only edit. This
card is about a second, different way that draft is lost with zero confirmation: not the
"Clear" button, but switching to a different settings tab.

This is NOT a duplicate of [ISS-372](20260828-2141-ISS-372.md) (already on file): ISS-372 is
scoped to the header **Back** button (`onClick={onBack}` at `AccountSettings.tsx:209`), which
routes through the shared `handleBackNav` and discards password-change fields and
`pendingModel`. It does not mention or cover the Constitution draft, and its trigger
(`handleBackNav`) is a completely different code path from the one below.

## Why the root cause implies this

`ConstitutionSection` is mounted conditionally, inline in `AccountSettings`'s render:

```
frontend/src/components/settings/AccountSettings.tsx:480-482
{section === "constitution" && (
  <ConstitutionSection />
)}
```

`ConstitutionSection`'s draft lives in its OWN local `useState("")` at
`AccountSettings.tsx:507` (`content`), not lifted to the parent. The active tab is switched by
the `Tabs` component's `onChange` handler:

```
frontend/src/components/settings/AccountSettings.tsx:230-234
onChange={id => {
  const next = id as SettingsSection;
  setSection(next);
  router.replace(SECTION_ROUTE[next]());
}}
```

This calls `setSection(next)` unconditionally — no check of whether `content` differs from
what was last loaded from the backend. When `section` changes away from `"constitution"`, the
`{section === "constitution" && (...)}` guard turns false and React unmounts
`ConstitutionSection`, which discards its local `content` (and `status`) state entirely, with
no warning. Navigating back to the Constitution tab remounts a fresh `ConstitutionSection`,
whose `useEffect` (`:514-527`) re-fetches from the backend — so the typed draft is gone, same
outcome ISS-320 flags for the persisted value, just reached by a different click.

## Expected vs actual

**Expected:** switching away from the Constitution tab while the textarea holds unsaved,
un-persisted text should warn before discarding it — consistent with the confirmation gap
ISS-320 and ISS-372 both flag for this page's other destructive/lossy actions.

**Actual (inferred, unverified):** clicking any other tab (Profile, AI Model, Usage & Limits,
Security) while on Constitution with unsaved draft text should silently unmount
`ConstitutionSection` and lose the draft with no prompt.

## What would settle it

Reproduce in the browser: open `/settings/constitution`, type draft text into the textarea
without clicking "Save constitution", click a different tab (e.g. "Profile"), then click back
to "Constitution" and confirm the draft is gone (only the last-saved backend value, or empty,
remains) with no confirmation ever having been shown.

## Where a fix belongs

If ISS-320's fix lifts a dirty-check/confirm gate onto `handleDelete`, the same dirty check
(`content` vs the last-fetched value) should also gate the `Tabs onChange` handler at
`AccountSettings.tsx:230-234` — otherwise the Clear button gets a guard while tab-switching
remains an equally silent way to lose the same draft.
