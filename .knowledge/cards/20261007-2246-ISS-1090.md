# ISS-1090

Sibling of [ISS-1072](20261007-2125-ISS-1072.md), derived during the analysis of register entry **QA-KB-095** (`LEDGER.md`).
**Status: INFERRED at the browser level.** Both halves were run separately: the endpoint answers 400 on the live server for
the reported run, and a scratch render of the real `PreviewPanel` + `SandboxTab` prints the error text in red. Nobody has driven
the pinned URL in a browser.

## Why the root cause implies it

[ISS-1072](20261007-2125-ISS-1072.md)'s root is that the page treats the DB column `FamilyMember.git_tag` as proof that the
sandbox holds that tag. `PreviewPanel` derives a ref from that column in THREE places, not one:

| derivation | line | feeds |
|---|---|---|
| `displayRef` | `PreviewPanel.tsx:890-891` | the header resolve and Download, the Files row, the PDF preview (root card and [ISS-1087](20261007-2244-ISS-1087.md)) |
| `pinnedMemberTag` | `PreviewPanel.tsx:1040`, applied at `:1052-1054` | `sandboxSelectedRef`, so the Workspace tab and the pinned preview |
| `activeParentGitTag` | `PreviewPanel.tsx:893` | FilesTab's "From v{n-1}" rows (`FilesTab.tsx:550-554`) |

A fix applied to `displayRef` alone, the path the report names, leaves the other two requesting refs the sandbox does not have.

## Condition

- **(a) URL pin.** `/runs/{id}/versions/{n}` where member n's DB tag is not in the sandbox. The route is written on every
  selection ([ISS-296](20260828-1724-ISS-296.md)) and survives a reload, so a bookmark, a reload while pinned or a chat deep link
  can carry it. The menu cannot create it for a lost tag: it lists only what `GET /sandbox/refs` returns. For the reported run:
  `/runs/0f62f7bc-d3a2-4748-8004-0b534e1741ae/versions/1`.
- **(b) Base rows.** A revision whose parent's DB tag is not in the sandbox, with the Files tab's "From v{n-1}" section opened.
  In the reported family that is the failed revision `b7bdf6a3-2ae9-48f6-867e-dbfb61b9f570`, whose parent tag is `v1`.

## Expected vs actual

- **(a) Expected:** an honest state for a version with no snapshot ("Workspace expired", or an explicit no-snapshot message), not an
  API error string. **Actual:** `SandboxTab` calls `getRunSandbox(token, runId, selectedRef)` (`SandboxTab.tsx:1170`), and its
  catch sets `setListError(err.message)` (`:1185`), rendered in red at `:1460`. Probe D prints `"invalid ref"` with class
  `px-1 py-2 text-[11px] text-status-failed` (`evidence/qa-kb-095/11-analyze-scratch-run.txt`). The live endpoint answers
  `400 {"detail":"invalid ref"}` for `?ref=v1` on the reported run (`evidence/qa-kb-095/06-analyze-live-probe-matrix.txt`).
- **(b) Expected:** no 4xx. **Actual:** `resolveRunDeliverable(..., parentGitTag)` (`FilesTab.tsx:551`) asks for the parent's tag, the
  API answers 400, and `catch { /* the derived rows stand */ }` (`:554`) swallows it. Network noise only; the rows are right.

## What the root card's fix does and does not cover

[ISS-1072](20261007-2125-ISS-1072.md)'s server-side fix (an empty directory counts as expired) cures both for a husk:
(a) becomes the "Workspace expired" empty state, (b) a 200 with no files. It cures neither for a live sandbox that lacks the tag
([ISS-1087](20261007-2244-ISS-1087.md)'s state), where the 400 is correct.

## Fix direction

Route all three derivations through the one reconciliation described in [ISS-1087](20261007-2244-ISS-1087.md) (a tag counts only if
the sandbox lists it; a lost tag is `null`, never `undefined`). For (a) the helper must also keep `pinnedMemberTag` from reaching
`setSandboxSelectedRef` (`:1052-1054`) and `intendedSandboxRef` (`:1053`).

**Open question, not blocking the root fix:** what a pinned Workspace tab should show when its tag is lost. Reading the live tree
would show the NEWEST member's files under an older label ([ISS-1050](20261002-1242-ISS-1050.md) asks the same thing for the unpinned
case); an explicit "no snapshot for this version" state is new copy. That is a product call for the owner of ISS-1050/ISS-1051.
