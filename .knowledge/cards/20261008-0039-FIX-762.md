# FIX-762

## What was wrong

This fix is for bug report QA-KB-097. The root cause is the 2026-10-08 analysis on [ISS-1101](20261008-0016-ISS-1101.md) and
[ISS-1102](20261008-0016-ISS-1102.md). It was not re-derived here.

**This is a test-only change. No application code changed for these cards. Audit it as a test edited to fit the app.** The
cards say the tests' premise is stale, not the engine. Since [FIX-669](20261001-1918-FIX-669.md) (`60bbe040d`), instance A's
scripted crash is a `StepRaised`. `_execute_impl` then moves the process-global `StateMachine` to terminal `failed`
(`engine.py:7599-7603`). Instance B is a second `ExecutionEngine()` in the same test process. It inherits that entry, so its
`transition(run_id, "generating")` (`engine.py:5739`) is refused by the terminal guard (`state_machine.py:92-97`).
`_drive_resumed_stream` then swallows the error (`engine.py:16030-16031`). In production this does not happen:

- The user resume endpoint evicts the entry first (`run_commands.py:745`, [FIX-105](20260723-FIX-105.md)).
- A restart starts with an empty machine.

The tests skip both, so they modelled "a new process" with the old process's state machine. That gave the report's
symptoms: wave-1 worker `c` never ran, and a user resume of a failed run stayed `failed`.

[ISS-1102](20261008-0016-ISS-1102.md) found a second effect in `test_cancel_stops_resumed_run_db.py`. The ISS-084 Stop test was
red on the same lock. Its re-adoption guard was vacuous: instance A left the row `failed`, so `adopted == []` held whatever the
cancel did. Under the ISS-084 mutant the guard stayed green.

## What changed, and why there

1. `test_restart_resume_db.py`, `_ResumeHarness.make_engine` (`:437`). It now sets
   `agents.execution_engine.state_machine._MACHINE = None` before `ExecutionEngine()`, with a comment that each engine instance
   stands for a new process. Every crash-then-resume test builds both instances through this one method, including the cancel
   file, which imports the harness. So one edit fixes all of them and every future test written this way. The card considered
   adding a `forget_run` call to each test instead and rejected it.
2. `test_cancel_stops_resumed_run_db.py`, `test_a_cancelled_resumed_run_is_not_re_adopted_by_auto_resume`. After instance A, the
   row is put back to `generating` (the pattern of `test_restart_resume_db.py:5367-5369`). A real crash, a process death, leaves
   it non-terminal. After `engine_b.resume_run`, the test now asserts `row.status == "cancelled"`. The docstring's "RED pre-fix"
   line now says what goes red today. The existing `adopted == []` assertion is unchanged.

Not done, per the cards: loosening the terminal guard, evicting inside `resume_run`, or special-casing the scripted crash in
`_guarded_step`. That would reopen the hole FIX-669 closed.
