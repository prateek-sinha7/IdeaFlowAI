# ISS-895

## What is broken

This was found while fixing QA-KB-029 ([FIX-679](20261001-2126-FIX-679.md)) and was not fixed there, because it is outside that bug's cards.

`frontend/src/components/results/AgentDetailPanel.artifactVersions.test.tsx` fails all 10 of its tests with one error:

```
Error: [vitest] No "getCapabilities" export is defined on the "@/lib/api" mock. Did you forget to return it from "vi.mock"?
 ❯ src/components/results/AgentDetailPanel.tsx:1325:5
```

- The test's mock factory (`AgentDetailPanel.artifactVersions.test.tsx:16-19`) returns only `getRunArtifacts` and `getToken`. vitest throws when code reads any other export of a factory mock.
- `AgentDetailPanel.tsx:26` imports `getCapabilities`. The mount effect at `:1321-1332` calls `getCapabilities(token)` whenever `getToken()` is truthy, and the mock's `getToken` returns "test-token". The `.catch(() => {})` there cannot help, because the throw happens on the property access, before any promise exists.
- `git blame` puts `:1325` in `3b4f02819` (2026-09-22, "feat(models): add GPT-5.6 on Bedrock and a per-step effort control"). The test file was last changed in `54d013f9d` (2026-08-12). It has been red since 2026-09-22.

Impact: no test runs the component-level coverage of per-artifact version viewing. That coverage includes:

- selecting v1 repaints the output;
- the read-only banner;
- Back to latest;
- the cards from [ISS-085](20260812-0505-ISS-085.md) and [ISS-087](20260812-0533-ISS-087.md), on top of [ISS-065](20260812-0005-ISS-065.md).

`ArtifactVersionPicker`'s own unit tests still run. Nothing exercises the picker mounted inside AgentDetailPanel.

## Evidence

- **Pre-existing, not caused by [FIX-679](20261001-2126-FIX-679.md):** at HEAD `024c03ef8` (a git-archive snapshot with no fix applied), the file fails 10/10 with the identical error. See `evidence/qa-kb-029/03-fix-before-head-024c03ef8.txt`. After the fix the result is the same. See `evidence/qa-kb-029/04-fix-after-working-tree.txt`.
- When measured, neither `AgentDetailPanel.tsx` nor the test file had uncommitted changes (`git status --short`).

## Proposed fix (test-only, not applied)

Give the factory the missing export. The sibling `AgentDetailPanel.modelChip.test.tsx:37-41` already does this: it spreads `importOriginal` and adds `getCapabilities: vi.fn(async () => ({ capabilities: [], model_catalog: CATALOG }))`. The smallest form adds one line to the existing factory: `getCapabilities: async () => ({ capabilities: [], model_catalog: [] }),`. After that, re-run the file to show whether its 10 assertions still hold against today's AgentDetailPanel. That has not been observed yet.

Nine test files in `frontend/src/components/results/` name AgentDetailPanel. Only this one and `modelChip` mock `@/lib/api`, and `modelChip` provides `getCapabilities`. The others use the real module, where `getToken()` returns nothing in jsdom, so the effect returns early.

## Analysis (QA-KB-069, analyzer run 2026-10-02)

Verdict: the root cause above is **CONFIRMED** against the working tree, and the open question in the proposed fix is now answered. With the one-line factory fix all 10 assertions pass, so none had drifted. The fix belongs in the test file only.

### Root cause (every line read)

- `frontend/src/components/results/AgentDetailPanel.tsx:26` imports `getCapabilities` from `@/lib/api`. The mount effect at `:1321-1332` calls it (`:1325`) as soon as `getToken()` returns a truthy value (`:1322-1323`).
- `frontend/src/components/results/AgentDetailPanel.artifactVersions.test.tsx:16-19` is a closed factory: `getRunArtifacts` and `getToken: () => "test-token"`, nothing else. Its `getToken` makes the effect fire. `getCapabilities` is absent, and the vitest module mock answers a read of any undefined export with a throw. The read is a property access on the module namespace, so it throws synchronously inside the effect, before the `.catch` at `:1330` exists.
- `getCapabilities` is an `export async function` (`frontend/src/lib/api.ts:2262`), so in production it cannot throw synchronously. Only the strict mock can. That is why no production guard is warranted.
- Introduced by `3b4f02819` (2026-09-22 18:03 +0200, per `git blame -L 1321,1332`). `git show --stat 3b4f02819` shows it changed `AgentDetailPanel.modelChip.test.tsx` (that factory now spreads `importOriginal` and stubs `getCapabilities`, `:37-41`) and `AnalyticsPage.test.tsx`, but not this file. This file was last changed by `54d013f9d` (2026-08-12). The CI job `frontend-vitest` runs the complete Vitest inventory (`.github/workflows/ci.yml:634-665`). Why a red file sat for ten days is not established here.
- Reproduced 2026-10-02 05:29 in this tree: `cd frontend && npx vitest run src/components/results/AgentDetailPanel.artifactVersions.test.tsx` gave `Test Files 1 failed (1)`, `Tests 10 failed (10)`, and the error at `AgentDetailPanel.tsx:1325:5`. `git status --short` showed no uncommitted change to the panel or to either test file.

### The open question, answered

Experiment on scratch copies outside the repo tree (alias import in place of `./AgentDetailPanel`, same vitest config otherwise):

|---|---|

| factory plus `getCapabilities: async () => ({ capabilities: [], model_catalog: [] }),` after `getToken:` | `Test Files 1 passed (1)`, `Tests 10 passed (10)`, 1.40 s |

### Blast radius (grepped, then run)

- **Production: no defect.** `getCapabilities` has 6 direct non-test callers (`AccountSettings.tsx:162`, `AgentDetailPanel.tsx:1325`, `AgentModelPicker.tsx:74`, `AgentsPopup.tsx:1141`, `WorkflowDialog.tsx:79`, `AnalyticsPage.tsx:237`) and 5 consumers of `useAgentCapabilities` (`AgentsPopup.tsx:1839` and `:2064`, `composer/AgentRow.tsx:83`, `composer/CanvasView.tsx:386`, `composer/CanvasConfigRail.tsx:227`), whose own call is `AgentsPopup.tsx:1657`. That is 11 in all. [ISS-839](20260922-2022-ISS-839.md) counted nine; the two it lacks, `AgentDetailPanel.tsx:1325` and `composer/AgentRow.tsx:83`, both came in with `3b4f02819` (`git blame`). Every one routes through the single `cachedGet`-backed function (`api.ts:2269`), so no production change is needed.
- **Tests, for `getCapabilities`: this file only.** 108 test files mock `@/lib/api`. An import-closure pass that honours each test's own `vi.mock` cuts found 13 whose component tree reaches a call site while the factory is closed and lacks `getCapabilities`. Each of the 12 others was run alone and none shows the `getCapabilities` error. Why each stays green was not established per file. The other 7 results-dir tests that name `AgentDetailPanel` do not mock `@/lib/api`.
- **Same flaw class, other export.** The remaining 95 mocking files were run one at a time (3 min 17 s). 90 exit 0. The missing-export signature appears in three more files, all for `getRunSandboxRefs`: [ISS-1011](20261002-0544-ISS-1011.md). Two of those files also carry an unrelated stale-assertion defect: [ISS-1012](20261002-0544-ISS-1012.md). Three other red files have no missing-export signature, so they are not this root cause: `AnalyticsPage.test.tsx` (5 failed), `SandboxTab.test.tsx` (4 failed), `LaunchWizard.test.tsx` (2 failed). `WorkflowHistory.test.tsx` (1 failed) is already [ISS-953](20261002-0154-ISS-953.md).

### Where the fix belongs

`frontend/src/components/results/AgentDetailPanel.artifactVersions.test.tsx:16-19`, one line inside the existing factory:

```
getCapabilities: async () => ({ capabilities: [], model_catalog: [] }),
```

Not `AgentDetailPanel.tsx` or `api.ts`: production is correct and cannot throw synchronously. Not an `importOriginal` spread: the real `getCapabilities` would then make a network request under `getToken: () => "test-token"`, so the stub is needed either way and the spread only adds weight. No shared mock helper: that would migrate 103 closed factories to fix a one-line bug.

Success check: the same command as above gives `Test Files 1 passed (1)` and `Tests 10 passed (10)`. The failing test for this card already exists; it is this file.

Invariants at risk: none. The change touches no kernel, registry or manifest surface.
