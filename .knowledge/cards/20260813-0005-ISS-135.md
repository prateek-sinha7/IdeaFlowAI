# ISS-135

## Title

**FIX-240 residual — `payload_json.seq` diverges from `run_events.seq` on a re-append.** `_RunEventSink.persist` re-stamps `data["seq"]` AFTER `append_event_at_or_after` returns, but the row was already serialised with the ORIGINAL value. Observed on real data: run `1ea6d262` row **248** carries `"seq": 247` in its payload. Replay yields `id: row.seq` (248) with `data.seq` = 247, while the live frame carried 248. **Harmless TODAY** because every de-dup keys on `event_id`, not `data.seq` — which is why it is filed rather than folded. It is a latent trap for anything that ever keys on `data.seq`. Fix shape: re-stamp before persist, or persist the re-stamped dict. **NOT a reason to touch FIX-240 otherwise.**

## Validation (QA-KB-007, 2026-10-01)

Reproduced 3/3 from cold start, offline (no browser): seed a row at seq=1, call `ScopedStore.append_event_at_or_after(run, 1, "b", "t", {"seq": 1})`. The collision retry lands the row at seq=2 but the stored `payload_json["seq"]` stays 1 (`LANDED 2 row.seq 2 payload.seq 1`). Cause is in `backend/agents/authz.py` `append_event_at_or_after`: the `except IntegrityError` branch sets `attempt_seq = tail + 1` without updating `payload_json`. Condition: any seq collision retry where payload carries a `seq` key. Evidence: `evidence/qa-kb-007/01-validate-repro-test-and-output.txt`. Severity raised to High by the QA-KB sweep.

## Analysis (QA-KB-007, 2026-10-01)

CONFIRMED = a `file:line` I read at HEAD (feat/user-stories-v2 @ 024c03ef8 plus working tree) or an output I produced. INFERRED = said so, with what would settle it. Evidence: `evidence/qa-kb-007/02-analyze-scratch-repro.py.txt`, `03-analyze-db-probes.py.txt`, `04-analyze-run-output.txt` (section letters below refer to the last file).

### Root cause (CONFIRMED)

One mechanism, three links.

1. **The engine stamps the REQUESTED seq into the very dict it then persists.** `execute()`: `data["seq"] = seq` (`backend/agents/execution_engine/engine.py:4192`), then `sink.persist(seq, event_id, type, data)` (`:4205`). The resume driver is a twin: `data["seq"] = seq` (`:15875`), `sink.persist(...)` (`:15882`). `data` is passed as the payload.
2. **`ScopedStore.append_event_at_or_after` relocates the row but never touches the payload.** In `backend/agents/authz.py:601-657` the `except IntegrityError` branch does `attempt_seq = tail + 1` (`:652`); the next loop turn calls `self.append_event(run_id, attempt_seq, event_id, type, payload_json)` (`:637-639`) with the ORIGINAL `payload_json`. `append_event` writes the `seq` column from its argument and `payload_json` as an unrelated value (`authz.py:385-394`) and commits before returning (`:396`); the column is a plain `JSON` with no mutation tracking (`backend/app/models/run_event.py:77`), serialised at flush.
3. **The re-stamp the docstring delegates to the caller arrives too late.** The docstring says "The caller MUST re-stamp the returned seq onto the event it is about to emit" (`authz.py:619`). The callers do (`engine.py:4208-4209`, `:15885-15886`: `data["seq"] = actual_seq`), but only on the in-memory dict, after the row committed. The live frame, the on-disk run trace (`_trace.observe` runs after the re-stamp, `:4212`) and `row.seq` all carry the landed seq; the stored `payload_json["seq"]` alone keeps the requested one.

Reproduced three ways on in-memory SQLite (section A, two cold runs, same result): store level `LANDED 2 row.seq 2 payload.seq 1`; sink level mimicking the loop `live frame seq=3 row.seq=3 stored payload.seq=2`; and through the real `ExecutionEngine.execute()` wrapper `[('review_gate_ready',1,1), ('chat_message',2,None), ('pipeline_cancelled',3,2), ('agent_chunk',4,4)]` as (type, row.seq, payload.seq) while the yielded frames read seq 1, 3, 4.

**Corrections to this card's original text (all CONFIRMED against HEAD):**
- It is the two drive loops, not `_RunEventSink.persist`, that re-stamp; `persist` only returns the landed seq (`engine.py:3315-3351`).
- "can lag the row's real seq by one" is wrong. The lag is however many foreign rows sit between the requested and the landed slot: 1 to 476 on real data, never negative (section G).
- "Replay yields `data.seq` = 247" is stale since [FIX-248](20260813-0357-FIX-248.md): SSE replay merges the row's `event_id`/`seq` columns LAST over the payload (`backend/app/api/run_stream.py:430-439`) and the FE reader does the same (`frontend/src/lib/api.ts:1487-1489`). Replay therefore masks the divergence, and the comment at `run_stream.py:417-421` ("for an engine-authored row this is a provable no-op") is false whenever a retry happened.
- The fix shape "re-stamp before persist" cannot be built: the landed seq is only decided inside the retry loop. "Persist the re-stamped dict" is only possible inside `append_event_at_or_after`.
- The sample run `1ea6d262` is not in the dev DB (section F), so that observation cannot be re-checked here; run `b09e4ae7` shows the same defect (below).

### Observed amplifier (not this bug's root cause, not carded)

CONFIRMED: in `b09e4ae7` the requested seq goes BACKWARDS 615 times in landing order (e.g. row 28056 requested 28056, the next row 28057 requested 28049; section E). One driver cannot do that: each loop stamps and persists one event at a time and its counter only ever increases (`engine.py:4189-4211`, `:15872-15888`). So at least two engine drivers were writing this one run, leapfrogging each other's counters; every retry lands past the other writer and keeps its stale payload seq. Two `run_resuming` markers 82 s apart (seq 27586 at 13:21:46, seq 28046 at 13:23:08) and three `pipeline_start` rows (seq 2, 27588, 28057) show the run was re-driven twice.

INFERRED: why two drivers overlapped. Likely a dev-server reload: [FIX-234](20260812-1312-FIX-234.md) records that `--reload` "leaves two stuck processes". What settles it: the backend log around 2026-09-25 13:21-13:24 showing two live driver tasks for this run id. If it turns out to be a product defect rather than a dev-environment artefact it needs its own card; none was minted because the cause is unverified. Relevance here: the retry path is exercised far more than this card assumed (745 of the 746 rows).

### Fix: the agreed minimal fix is ACCEPTED, with four constraints

Where: `ScopedStore.append_event_at_or_after`, immediately after `attempt_seq = tail + 1` (`authz.py:652`). It is the one function every affected caller routes through, so one 2-line change covers both drive loops and any future caller:

```python
if isinstance(payload_json, dict) and "seq" in payload_json:
    payload_json = {**payload_json, "seq": attempt_seq}
```

1. **Copy, never mutate in place.** The dict is the caller's live frame. On exhaustion the function re-raises (`:657`), `persist` returns `None`, and the loops' contract is "`None` means no re-stamp" (`engine.py:4203-4204`); mutating in place would leave the live frame on a seq the row never got. Scratch test G shows the copy leaves the caller's dict untouched.
2. **Re-stamp on every hop,** inside the `except` branch rather than once before the loop: a second collision moves the seq again. Scratch test E: stale first tail probe, 2 hops, landed 4, stored payload 4.
3. **Keep it after the `if tail < attempt_seq: raise` guard** (`authz.py:650-651`). The offline characterization harness (FK violation, empty tail) must keep re-raising untouched so goldens keep contiguous 1,2,3... seqs (SAFE-03 / INV-3). The agreed placement satisfies this; an earlier placement would not.
4. **Do not widen it.** Not into `append_event` (a dict copy on each of the ~36k writes of a long run, for a defect that only exists on the retry branch), and not by dropping `seq` from persisted payloads (changes the REST `/events` contract and the FIX-248 merge semantics). The shallow copy is O(number of keys), not O(bytes), so a 214 KB `agent_input` row is not duplicated.

Forward-only. The 746 rows already stored stay stale: nothing reads them (replay merges `row.seq`) and a backfill would UPDATE an append-only log. Not recommended, not required to close this bug.
