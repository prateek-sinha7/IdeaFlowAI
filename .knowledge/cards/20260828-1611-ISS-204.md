## Why the root cause implies this

[ISS-206](20260828-1609-ISS-206.md) Mechanism 1: `needsFullManifest(pipelineAgents)`
(`ComposerPage.tsx:51-60`) is a pure function of `pipelineAgents` — `isCustom` / `prompt` /
`skills.length` / `children.length` / `route.outcomes`. It has no way to see that `runConfig`
(the Workflow tab's deliverable/planner/clarify picker) was changed, because `runConfig` is a
completely separate piece of state never passed to it. This is true regardless of WHERE
`pipelineAgents` came from — a built-in's `initialManifestSteps` (the reported case, ISS-206/
ISS-196/ISS-203) is only one way to end up with an all-stock-agent, `needsFullManifest()===false`
composition. Two other, more common ones reach the identical gate:

1. **Fresh "Compose a custom workflow"** (`/workflows/new`, no `builtinCanvasType`, no
   `initialManifestSteps`): a user drags in only library agents (no custom prompt, no skill, no
   sub-agent, no conditional route on any of them) and changes ONLY the Workflow tab — e.g. sets
   Deliverable strategy to "Single file" / `report.html`. `pipelineAgents` still has zero
   customized agents, `needsFullManifest` is `false`, `selections` stays `{}` (nothing per-node
   was touched), so `selectionsBody` in `handleSave` (`ComposerPage.tsx:628-632`) resolves to
   `{}` and the chosen deliverable is never sent — Save silently reverts to the server's own
   default deliverable for a `custom` manifestless row.
2. **Re-saving (PATCH) an already-saved workflow** that happens to use only stock agents: the
   same `needsFullManifest(pipelineAgents)` check runs again on every save
   (`ComposerPage.tsx:641-657`, `saveUserWorkflow` → `updateUserWorkflow` when `userWorkflowId` is
   set). If the user opens an existing all-stock-agent saved workflow and changes only the
   Workflow tab before clicking Save again, the change is dropped the same way — this is not
   specific to first-time create.

Both are reachable through the SAME single gate ISS-206 names as the fix location
(`ComposerPage.tsx:628` and its `handleRunOnce` mirror at `:798`), so the fix ISS-206 proposes
(broadening the persist-full-manifest decision to also fire on a `runConfig` change) closes this
case too without any additional code — this card exists so the fix is validated against a
from-scratch/re-save scenario as well as a built-in-copy one, since it is easy to write a test
that only covers the built-in path and still leave this one broken.

## Expected vs actual

**Expected:** any Workflow-tab change (deliverable strategy, output name, planner, clarify mode)
survives Save, whether or not any individual agent was also customized.

**Actual (inferred, not yet reproduced):** for a composition with zero customized agents, the
Workflow-tab change is silently dropped on Save — both on first create and on a later re-save —
exactly as ISS-196 observed for the built-in-copy case, but reachable with no built-in involved
at all.

## Status

**INFERRED.** Derived directly from `needsFullManifest`'s definition and the two `handleSave`
call sites — no click-through attempted for the from-scratch or re-save path. Settling it: open
`/workflows/new`, add 2-3 stock library agents (no customization), set a non-default Deliverable
strategy in the Workflow tab, Save, and inspect the POST body for a `manifest` key the same way
ISS-196 did for the built-in case; repeat with a PATCH (re-save) of an existing all-stock-agent
saved workflow.
