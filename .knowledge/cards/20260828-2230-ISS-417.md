# ISS-417

## Title

`TokenUsageSummary` (`frontend/src/components/workflow/TokenUsageSummary.tsx`), mounted in the
Steps tab (`AgentThinkingTab.tsx`), destructures `totalTokens` / `totalInputTokens` /
`totalOutputTokens` / `cacheReadTokens` / `cacheWriteTokens` straight off the SAME
`pipelineState` object [ISS-304](20260828-1600-ISS-304.md) already found is corrupted by
`pipeline_complete.total_tokens` — so the Steps tab footer shows the same wrong 17.9K (not
10.4K) for the same run, in a second location the hunter never checked for this run.

## Mechanism (CONFIRMED by code read; NOT independently re-reproduced live this session)

`TokenUsageSummary.tsx:18-28`:

```ts
export function TokenUsageSummary({ pipelineState, modelId }: TokenUsageSummaryProps) {
  const { totalTokens, totalInputTokens, totalOutputTokens, cacheReadTokens, cacheWriteTokens } = pipelineState;
  ...
  if (!totalTokens && !totalInputTokens) return null;
  const input = totalInputTokens ?? 0;
  const output = totalOutputTokens ?? 0;
  const total = totalTokens ?? (input + output);
```

It reads the exact fields ISS-304 traced to `useWorkflow.ts`'s `pipeline_complete` case
(`totalTokens: (msg.total_tokens as number) || prev.totalTokens || 0`, line 796) — no
independent computation of its own.

`AgentThinkingTab.tsx:321` mounts it: `<TokenUsageSummary pipelineState={pipelineState}
modelId={pipelineState.modelId} />`. `AgentThinkingTab` receives `pipelineState` as a **prop**
(declared at line 24) — it does not call `useWorkflow()` itself. The run route
(`frontend/src/app/[...view]/page.tsx:2087`) makes the ONE `useWorkflow()` call for the page
(`const { pipelineState, ... } = useWorkflow();`) and that single object is what both
`RunChatLane` (owns `LaneRunHeader`, ISS-304's reported surface) and `PreviewPanel` → the
results tabs → `AgentThinkingTab` are fed from — so the Steps tab footer and the chat header
are two renderers of the identical `pipelineState.totalTokens` value for the same run, not two
independent computations.

**What would confirm this as a live symptom** (not done this session — scope was the reported
chat-header bug): open the Steps tab on the same run
(`/runs/a0693fcd-9451-4c19-a9e7-61474ea03516`) and read the footer's token figure; it should
show 17.9K, matching the chat header, both disagreeing with `token_usage.total_tokens` (10.4K).

**Not the already-fixed Steps-tab bug.** This is NOT
`BUG-20260828-012500-runs-id-steps` ([ISS-278](20260828-1700-ISS-278.md), status FIXED) — that
bug was a display-math error (uncached-input rendered beside a full total) inside this same
component, on a different run, already resolved. This card is the pipeline_complete-vs-
token_usage authority split (ISS-304's root cause) reaching the SAME component through its
`pipelineState` prop, independent of and unrelated to ISS-278/ISS-385's formula bug.

## Expected vs Actual

- Expected: the Steps tab's token footer agrees with `token_usage.total_tokens` (10.4K) and
  with the Run History list card and the chat header, once ISS-304 is fixed.
- Actual (inferred, unverified): the Steps tab footer shows 17.9K on the same run, for the same
  reason ISS-304's header does — both read `pipelineState.totalTokens`, which
  `useWorkflow.ts:796` sets from `pipeline_complete.total_tokens` verbatim.

## Fix

Belongs wherever ISS-304's fix lands. If the fix is applied at the backend source
(`_apply_terminal_output_columns`, `backend/app/api/run_commands.py`) so the persisted
`token_usage` and the live/replayed `pipeline_complete` event agree, this card resolves for
free — no separate frontend change needed, since both `LaneRunHeader` and `TokenUsageSummary`
already route through the one `pipelineState` object. A frontend-only patch to `LaneRunHeader`
alone would leave this component still wrong.
