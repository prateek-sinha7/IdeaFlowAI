# ISS-961

**INFERRED, not reproduced.** Derived while analysing QA-KB-050 ([BUG-025](20260827-BUG-025.md)). Every link below was
read in source; what has not happened is anyone driving the screen and reading the result. An unreproduced sibling is a
lead, not a defect.

Line numbers are the working tree on 2026-10-02 (HEAD `024c03ef8`). `ComposerPage.tsx`, `AgentsPopup.tsx`,
`DashboardLayout.tsx`, `page.tsx` and `SavedWorkflowsPage.tsx` carry uncommitted edits from other work, so their numbers
can be a few higher than at HEAD; `CanvasNode.tsx`, `AgentRow.tsx`, `CanvasView.tsx` and `AgentLibrary.tsx` are clean
against HEAD. The shared mechanism (the composer reads DashboardLayout's `workflowType`, which is `user_stories` on every
composer route except a built-in's canvas) is proved in [BUG-025](20260827-BUG-025.md)'s analysis section and in
`evidence/qa-kb-050/`; it is not repeated here.

## Condition

A saved workflow opened for editing whose composition holds a catalogue agent the composer's mistyped pipeline treats as
core. With the `user_stories` default that is domain-analyst and backlog-compiler (locked) and epic-architect,
story-estimator, nfr-specialist and backlog-reviewer (required). Three ways in, none of which supplies a type:

- **My Workflows > Edit.** `frontend/src/components/savedworkflows/SavedWorkflowsPage.tsx:220-223`: `handleEdit` is only
  `router.push(routes.workflowEdit(row.id))`. Nothing sets a workflow type.
- **A typed, refreshed or shared `/workflows/{id}/edit` link.** `frontend/src/app/[...view]/page.tsx:3782-3834` fetches the
  row and calls `setInitialSavedComposition({...})` (`:3799`); the object has no type field.
- **`/workflows/{id}/run` for a composer-built row.** `page.tsx:3927-4053`, `setWorkflowRunMainView(isComposerWorkflow(saved) ? "composer" : "input")`
  at `:4022`, same shape.

## Why the root cause implies it (each step read)

1. `ComposerPage.tsx:1430` and `:1629` feed `getRole` from the shared `workflowType` prop, whichever route mounted the
   composer ([BUG-025](20260827-BUG-025.md), mechanism steps 1-5).
2. `initialWorkflowTypeFor` returns `undefined` for `workflow-edit` and `workflow-run` (`page.tsx:386-397`; executed in
   `evidence/qa-kb-050/analysis-proof-initialWorkflowTypeFor.out.txt`), so `DashboardLayout.tsx:627-637` seeds `"user_stories"`.
3. My Workflows > Edit sets nothing (`handleEdit`, above). My Workflows > Run goes through `handleLaunchSaved`, which does set a
   type, `setWorkflowType(saved.base_pipeline_type)` (`DashboardLayout.tsx:1737-1738`), but then
   `router.push(routes.workflowRun(saved.id))` (`:1749`), and a push under the `[...view]` catch-all remounts the page
   (`DashboardLayout.tsx:540-550`; [ISS-916](20261001-2220-ISS-916.md) read Next's cache key for the same fact), so the seed is the
   same `undefined`. Even if the type survived it would be the row's
   `base_pipeline_type`, which `:1743-1745` says can be stale ("a row stamped with a stale type could never open in the
   Composer again"); a stale `user_stories` stamp is exactly as wrong as the default.
4. Save stamps `base_pipeline_type: "custom"` (`ComposerPage.tsx:931`), so nothing on the save path ever shows the author
   that the type they edited under was not `custom`.

## Expected vs actual

- **Expected:** every agent in a saved custom workflow can be removed; a lock appears only on a built-in's own canvas, with a
  matching Core badge.
- **Actual (derived):** the Canvas shows a Core badge and a dead, invisible Remove on domain-analyst and backlog-compiler,
  and a dead, invisible Remove with no badge on the four required agents. The author cannot take them out of a workflow
  they saved. In the Simple view the drag lock (`ComposerPage.tsx:669`, `AgentRow.tsx:117`) also blocks reordering the two
  locked ones.

## Why this is INFERRED, and what settles it

Read, not driven. The cold-load half (steps 1-2) needs no inference. The click-path half (step 3) rests on the remount
claim. Settle it by opening My Workflows, editing a saved workflow that contains `epic-architect`, and reading the
`disabled` attribute of `[aria-label="Remove ..."]`, or with the unit test below.

## Where the fix belongs

Nothing separate. The `canvasPipelineType = (builtinCanvasType ?? "custom") as WorkflowType` that [BUG-025](20260827-BUG-025.md)'s
analysis puts in `ComposerPage.tsx` closes this too, because for a saved workflow `builtinCanvasType` is undefined and
the type becomes `"custom"`. Fixing only `initialWorkflowTypeFor` for `workflow-new` would NOT close it. This card exists
so the fix is tested on the edit route as well as on `/workflows/new`.

## For the test-writer

Offline: mount `ComposerPage` as `renderComposer` does (`ComposerPage.test.tsx:152-181`; its default `workflowType` is
`"user_stories"`, which is what these routes supply) with `initialAgentIds: ["epic-architect", "story-estimator"]` and
`initialUserWorkflowId: "wf-1"`, no `builtinCanvasType`, Canvas view. Assert both `Remove ...` buttons are enabled and no
element reads `Core`. It fails today (both disabled). Live: `tests/integration/e2e/suites/05_saved_workflows/` is the home
for My Workflows > Edit; no case there reads a Remove control.
