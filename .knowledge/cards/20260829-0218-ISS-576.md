## Summary

INFERRED sibling of [ISS-338](20260828-2050-ISS-338.md) (`BUG-20260828-050900-settings-profile`),
derived from its root cause rather than independently reproduced — no validator cycle has run
against this page yet.

ISS-338's root cause is that `AccountSettings.tsx` hand-rolls a per-field `show`/toggle boolean
for each password `<input>` rather than using a shared, reusable masked-input component — so
whether any given password field gets a reveal affordance depends entirely on whether that one
call site remembered to wire it. `frontend/src/components/ui/` (the project's own primitives
folder — `Badge.tsx`, `Button.tsx`, `Card.tsx`, `Pill.tsx`, `Tabs.tsx`, …) has no `PasswordInput`
or equivalent. That absence means the same class of omission can recur anywhere else a password
field is hand-rolled, and it already has: the Cognito "set a new password" challenge form on the
login page hard-codes `type="password"` on both of its fields and never imports `Eye`/`EyeOff` at
all — a stricter version of the same gap (0 of 2 fields revealable, vs. AccountSettings' 2 of 3).

This form is reached via the `NEW_PASSWORD_REQUIRED` Cognito challenge (first sign-in / admin
password reset), and its second field is explicitly a retype-verification field ("Confirm
password" / `Re-enter your new password`) — the exact same purpose ISS-338 calls out for the
settings-page confirm field.

## Root cause (read from source, not yet browser-reproduced)

`frontend/src/app/login/page.tsx`:
- L6: `import { Mail, Lock } from "lucide-react";` — no `Eye`/`EyeOff` import anywhere in the file.
- L455-470: "New password" field (`id="new-password"`, L460) — `type="password"` hardcoded at
  L461, no `show`/toggle state, no button.
- L471-485: "Confirm password" field (`id="confirm-new-password"`, L476) — `type="password"`
  hardcoded at L477, same absence.

Both fields sit inside `ChallengeForm` (the shared shell for Cognito's `NEW_PASSWORD_REQUIRED` /
MFA challenges), rendered when `isNewPassword` is true.

## Expected vs Actual

- **Expected:** consistent with the product intent ISS-338 identifies — a password field whose
  purpose is to let the user verify a retyped value should be revealable, or at minimum should
  match whatever affordance exists elsewhere in the app for password fields.
- **Actual:** neither "New password" nor "Confirm password" on this form can ever be shown in
  plain text; there is no eye-icon control on either.

## Why the root cause implies this

ISS-338's mechanism is "no shared masked-input primitive exists, so each password field's
reveal toggle is opt-in per call site and easy to forget." That is an architectural gap, not a
one-off typo — it predicts other hand-rolled password fields in the app are equally exposed.
This card is the first of two such fields I located from that inference (`grep -rn
'type="password"' frontend/src` for occurrences outside `AccountSettings.tsx`); see also
[ISS-577](20260829-0219-ISS-577.md) for the second (Admin "Create New User" modal).

## What would confirm it

A cold-navigate to the login page with a Cognito account in the `NEW_PASSWORD_REQUIRED` state,
inspecting the DOM the same way ISS-338's validator did:
`input#new-password ~ button` and `input#confirm-new-password ~ button` should both resolve to
`null`.
