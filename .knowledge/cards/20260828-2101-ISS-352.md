## What is suspected

[ISS-245](20260828-1631-ISS-245.md) confirmed (3/3, reproduced) that `LoginForm.handleSubmit` in
`frontend/src/app/login/page.tsx` has no synchronous guard against rapid repeated clicks: the only
gate is `disabled={isLoading}` on the submit `<Button>`, and `isLoading` is a React state value
that does not reach the DOM's `disabled` attribute until React commits — a commit that lands on a
later tick than a same-task synchronous click. `handleChallengeSubmit` (`login/page.tsx:95-152`),
the handler for the MFA/new-password/OTP step rendered by `ChallengeForm`, has the identical shape:

```
frontend/src/app/login/page.tsx:122-124 (excerpt)
    setIsLoading(true);
    try {
      const result = await respondToLoginChallenge(email, challenge.session, challenge.challenge, {
```

and `ChallengeForm`'s submit button (`login/page.tsx:525`) reads the same
`disabled={isLoading}` prop, passed down from the same `LoginForm` state. There is no
`useRef`-based synchronous lock here either — `setIsLoading(true)` at line 123 is a state update,
not a DOM mutation, so it is exposed to exactly the same pre-commit window ISS-245 measured on the
base sign-in form.

## Condition

Reach the challenge step (any of: `NEW_PASSWORD_REQUIRED`, `SOFTWARE_TOKEN_MFA`, `EMAIL_OTP`,
`SELECT_MFA_TYPE` — not `MFA_SETUP`, which renders no submit control), fill the required field(s)
for that step, then click the "Continue" button synchronously multiple times before the first
`POST /api/auth/login/challenge` response returns — the same reproduction shape ISS-245 used
(`btn.click(); btn.click(); btn.click();` in one JS task) against the Continue button instead of
Sign in.

## Expected vs actual

- **Expected:** the "Continue" button disables itself the instant the first click starts the
  challenge-response request, so additional clicks before the response arrives are ignored and at
  most one `POST /api/auth/login/challenge` is sent per submission.
- **Actual (predicted):** each synchronous click before the commit lands independently invokes
  `handleChallengeSubmit`, each firing its own `respondToLoginChallenge` call — for
  `NEW_PASSWORD_REQUIRED` specifically, this means duplicate concurrent Cognito
  set-new-password attempts from a single interaction; for the MFA code paths, duplicate
  concurrent code-verification attempts (one of which risks consuming/invalidating a
  single-use OTP or triggering Cognito's attempt-throttling on a legitimate first try).

## Why the root cause implies this

Same file, same component tree, same `isLoading` state variable, same button-prop wiring, same
missing ref guard — `handleChallengeSubmit` is not a different mechanism from `handleSubmit`, it
is the same one written a second time three lines away. ISS-245's own "Proposed fix" section
already names this handler as needing the identical guard; this card exists to track it as its
own reproducible condition (a different user-visible surface — the challenge step, not the base
form — with a plausibly worse consequence given OTP/Cognito single-use semantics) rather than
leaving it as a parenthetical under the root card.

**Marked INFERRED**: only `handleSubmit` was actually triple-clicked and measured (ISS-245's
3 cycles). No cycle in that validation reached the challenge step. What would confirm it:
sign in with an account that returns `NEW_PASSWORD_REQUIRED` or a code challenge, fill the
step's fields, and repeat ISS-245's synchronous triple-click against the Continue button while
instrumenting `window.fetch` / `browser_network_requests` for `auth/login/challenge` call count.
