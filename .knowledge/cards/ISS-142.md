# ISS-142

## Title

The WS->SSE cutover DROPPED status from the reconnect ack, breaking parity with locked decision D-13. IMPLEMENTATION-REGISTER.md records for D-13/12-09 that the pipeline_reconnected reply carries live/status/replayed_through_seq. Its replacement, stream_attached (run_stream.py:215-227), is documented in that same file as "the new-transport replacement for the legacy pipeline_reconnected ack" — and emits only {pipeline_run_id, live, replayed_through_seq}. Restoring status is cheap and is PARITY, not invention: run_is_terminal/workflow_run.status is ALREADY computed in request scope for FIX-240's gate-re-arm guard, the handshake is synthesised per attach so it is NOT a durable run_events row (sidestepping both objections that killed the wire-synthesis option), and it reuses replayed_through_seq as its id: so Last-Event-ID is untouched. Evaluated during FIX-245 and NOT built, for two reasons. (1) It does not fix ISS-126 at all — a terminal run never opens an SSE stream (page.tsx:2171), so it cannot subsume the FE reconciliation. (2) The claim that it merely "revives an already-written handler" is inaccurate: useWorkflow.ts's handler is keyed on pipeline_reconnected, an event NOTHING emits (ISS-137), so this needs a NEW stream_attached handler — real work, not a one-field re-add. Its real value is the cases FIX-245 does not cover: a reload while the record is still non-terminal, and a cursored reattach. If built, it MUST route through the shared terminalMarkers/applyTerminalStatus added by FIX-245 rather than introducing a fresh status list (INV-12), and must keep the same one-way directionality.

## Source / evidence

Evaluated during quick-260812-wir per an explicit instruction to consider it as a possible substitute for the FE fix; rejected as a substitute on evidence (the symptom does not traverse the SSE path) and filed as an independent parity item rather than folded.
