## What was wrong

`GET /api/settings/preferences` (the per-model `allowed` flags) and `PUT /api/settings/preferences` (the 403 tier gate) decided
model entitlement from the advisory `users.tier` column. [ADR-0013](20260916-ADR-0013.md) makes `cognito:groups` the authority.
The column only matches the token when `refresh_projection_if_stale` rewrites it. It returns early when the token's `iat` is not
newer than `users.roles_synced_at` (`backend/app/core/provisioning.py:138-140`). Through the real dependency chain, a basic-groups
token over a pro column therefore got `allowed: true` and a 200 for Opus while `/api/auth/me` said basic. The mirror case refused a
pro-groups token (analyzer evidence `evidence/qa-kb-083/04-analyze-probe-real-chain-output.txt`).

## Root cause

`get_preferences` (`backend/app/api/settings.py:332` before this change) and `update_preferences` (`:353`) depended on
`get_current_user`. That dependency returns only the `User` and drops the `Principal`
(`backend/app/core/dependencies.py:255-282`). Without a principal the handlers could not call `effective_tier(user, principal)`
(`backend/app/core/identity.py:214-223`), so `:341`, `:374` and `:388` passed `user.tier` to `can_use_model`. Settings was the last
caller giving `can_use_model` a column. The other two, `run_engine.py:668` and `run_commands.py:2616`, already pass effective tiers.
That is why the fix belongs in this file and nothing shared changed.

## What changed, and why there

Only `backend/app/api/settings.py` changed in production code:

- It imports `get_current_principal` and `Principal, effective_tier`. `get_current_user` stays because nine other routes in the file
  still depend on it.
- Both handlers take `auth: tuple[User, Principal] = Depends(get_current_principal)`, the `user_workflows.py` create/update shape.
  Each unpacks `user, principal = auth` and computes `tier = effective_tier(user, principal)` once. The three former `user.tier`
  reads now use `tier`: `can_use_model(tier, ...)` at `:347`, `:386` and `:400`.
- In `update_preferences` the tier is computed before `commit()`/`refresh()`. The gate and the response flags can no longer be
  judged by different values. The 422-before-403 order ([FIX-361](20260829-0029-FIX-361.md)) and the validated-value response
  ([ISS-319](20260828-1804-ISS-319.md)) are unchanged.
- No line was added to `projection_read_allowlist.txt`. Its per-function key would also approve the gate read
  ([ISS-1029](20261002-0705-ISS-1029.md) gap 2). The T7 guard passes without one.
- Each new parameter carries the comment `create_user_workflow` uses ("get_current_principal, not get_current_user: ...").
  The comment explains why these routes differ from the rest of the file. It also keeps the API-contract generator
  (`tests/integration/capture/_api.py::auth_of`, a substring match on `current_user`) labelling both routes `user`. Without it they
  would read as `public`, which is the defect [ISS-1065](20261007-1940-ISS-1065.md) records for four other routes. Observed after
  the change: `_api.py --json` prints `GET` and `PUT /api/settings/preferences ... user`, the same as the committed snapshot.

One test-only edit follows the new signature. ISS-937 step 6 asked for it to be flagged for the verifier's direction check.
`backend/tests/unit/test_settings_preferences_race.py` is ISS-319's pin and the only direct caller of `update_preferences`. It moved
to `backend/tests/integration/api/test_settings_preferences_race_api.py`. The unit I/O guard had stopped it at setup. No assertion
changed. The diff against the original is exactly:

- `import uuid` and `from tests.fakes.principal import principal_for`;
- `cognito_sub=str(uuid.uuid4())` in the `User(...)` seed (the NOT NULL column from [ISS-1019](20261002-0617-ISS-1019.md), seeded the
  way [FIX-736](20261007-1940-FIX-736.md) seeded its siblings);
- the two `user=user_x` keyword calls became `auth=(user_x, principal_for(user_x))`.

That is ISS-1064 section 2. Section 1 (`backend/tests/unit/test_admin_privilege_race.py`, which needs boto3 mocks) is untouched,
so ISS-1064 stays open.
