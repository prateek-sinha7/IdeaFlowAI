## What was wrong

The composer edits ONE `SelectionsMap` (`ComposerPage.tsx:1113-1115` for Canvas,
`ComposerPage.tsx:1337-1344` for the Simple-view rows), and `StepSelection.tools`
is a normal field of it. Canvas view's rail wrote that field from its Tools tab;
Simple view had no Tools UI at all. So disabling "Write files" for a step in
Canvas produced real, shared, in-session state that Simple view neither displayed
nor could edit — its `Overrides` row read identically (`Validator Gate Retry
Skills`) for a restricted and an unrestricted agent, and its "Configure →" panel
contained no occurrence of "Tool grants" / "Read files" at all.

## Root cause

`frontend/src/components/workflow/composer/AgentRow.tsx:252` mounts
`AdvancedExpander` (`AgentsPopup.tsx`), and that component's JSX never read or
wrote `StepSelection.tools` — its per-agent block rendered Validator / Gate /
Model / Retry / fan-out only, matching its hardcoded `Validator · Gate · Model ·
Retry` subtitle. The three grant switches existed in exactly one place in the
frontend, `CanvasConfigRail.tsx` (the Tools tab), which also owned its own inline
copy of the grant list and its own `read_files ?? true` default computation.
Nothing shared: a grant added or defaulted differently in one surface could not
reach the other.

## What changed and why there

1. `frontend/src/components/workflow/AgentsPopup.tsx` — added, next to
   `applyLeverPatch` (the existing single writer of the selection shape), the
   shared definitions both lever surfaces now read: `TOOL_GRANT_LEVERS` (the
   author-editable grants with their labels/copy), `effectiveToolGrants(sel)`
   (the read+write-ON defaults) and `hasToolOverride(sel)`.
2. Same file, `AdvancedExpander` — a "Tool grants" block per agent, mapping
   `TOOL_GRANT_LEVERS` and writing through `updateLever(agent.id, { tools })`,
   i.e. the SAME `applyLeverPatch` reducer the Canvas rail patches through, so
   the two views cannot drift and a tools edit can never be clobbered by a
   sibling writer's stale snapshot. It renders OUTSIDE the collapsed
   `Advanced — <name>` disclosure deliberately: an existing restriction has to be
   visible the moment the config panel opens, which is the reported defect. `exec`
   keeps the Canvas rail's fixed-OFF disabled row (the untrusted cap zeroes it for
   db-trust manifests).
3. `frontend/src/components/workflow/composer/AgentRow.tsx` — a fifth `Tools`
   chip in the `Overrides` row, lit by `hasToolOverride(selection)`, so a
   restriction set in either view is flagged at a glance exactly like
   Validator/Gate/Retry/Skills.
4. `frontend/src/components/workflow/composer/CanvasConfigRail.tsx` — its inline
   grant-list literal and its local default computation replaced by the shared
   `TOOL_GRANT_LEVERS` / `effectiveToolGrants`. Its own markup (InfoHint +
   description + `role="switch"` Toggle) is untouched.

No backend, manifest or persistence change: `agentToManifestStep` and
`manifestStepsToGateSelections` already round-trip `tools`, and an untouched step
still emits no `tools` key.
