## Root cause

`frontend/src/lib/routes.ts:72-85` — every other run-tab builder (`runSteps`,
`runFiles`, `runWorkspace`, `runAudit`) takes an optional second `version`
parameter and builds `/runs/{id}/versions/{v}/{tab}` when it is supplied
(`routes.ts:72-73`, `:78-85`). `runStepsAgent` (`routes.ts:75-76`) takes only
`(id, agentId)` and always builds the un-pinned `/runs/${id}/steps/${agentId}`
— there is no way to ask this specific builder for a version-pinned form.

The parser side already accepts one: `parseViewPath` (`routes.ts:319-339`)
lifts a `/versions/{v}` segment ahead of the tab for every run route
including this one, and line 339 returns `{ screen: 'run-steps-agent',
runId, agentId, version }` — matching the `ParsedView` union member at
`routes.ts:184`, which declares `version?: string` on `run-steps-agent`
exactly like its sibling screens. So the type and the parser both model a
version-pinned per-agent URL; only the builder cannot produce one.

## Why this matters

[ADR-0018](20260824-1631-ADR-0018.md) makes `routes.ts` the single source
for building AND parsing every URL. This is that contract broken in one
direction for one screen: parsing a hand-typed
`/runs/{id}/versions/{v}/steps/{agentId}` works, but nothing in the app can
construct that same URL through the typed builder. A caller that later
wants to link to a specific agent's detail while a historical version is
pinned — the natural next step once [ISS-277](20260828-1659-ISS-277.md) is
fixed and an agent-detail link/copy-link affordance exists — will silently
drop the version pin, because the builder it would reach for has no
parameter to carry it.

## Confirmed vs inferred

**CONFIRMED** (read directly): the parameter asymmetry itself —
`routes.ts:72-89` (four sibling builders carry `version?`) vs `:75-76`
(`runStepsAgent` without it) — and that the parser already produces a
`version` field for this exact screen (`:184`, `:319-339`).

**INFERRED**: real-world impact. `routes.runStepsAgent` has zero production
callers today (`grep -rn "runStepsAgent" frontend/src/` matches only
`routes.ts` itself and `routes.test.ts`), so no live user path exercises
this parameter combination yet. It becomes live the moment ISS-277's fix
(or any future "link to this agent" affordance) is built, since a naive
implementation would reach for this exact builder. Confirming it further
means building that affordance and checking whether the version pin
survives — that is the fixer's job, not something to reproduce standalone.
