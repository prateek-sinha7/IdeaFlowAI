# ISS-1067

## Description

Found while choosing the sandbox tokens for [FIX-745](20261007-2030-FIX-745.md). FIX-745 implements
[ISS-1038](20261002-1117-ISS-1038.md), which showed that agent HTML served on the application origin can read
`auth_token` from `localStorage`. The share link is now sandboxed into an opaque origin. Two in-app viewers of the
same kind of content are not.

CONFIRMED, read:

- `frontend/src/components/preview/PrototypePreview.tsx:355-365` builds `URL.createObjectURL(new Blob([renderedHtml],
  { type: "text/html" }))`. A blob URL carries its creator's origin, which is the app's. `:607-610` loads it in an
  iframe with `sandbox="allow-scripts allow-same-origin"`. `:389` `handleOpenInNewTab` calls
  `window.open(blobUrl, "_blank")`, a top-level document on the app origin with no sandbox at all.
- `frontend/src/components/preview/PPTPreview.tsx:252` sets `sandbox={isOdPpt ? "allow-scripts allow-same-origin" :
  "allow-scripts"}` on a `srcDoc` iframe, and `:33` fixes `isOdPpt = true`. A srcdoc document with
  `allow-same-origin` inherits the parent's origin.
- `PreviewPanel.tsx:178-182` states the opposite rule for the generic renderer: same-origin agent HTML is
  "stored-XSS-adjacent (T-18-05)", and its `sandbox="allow-scripts"` with no `allow-same-origin` is "a BLOCKING
  security mitigation".

By the HTML sandbox semantics, `allow-scripts` together with `allow-same-origin` on same-origin content leaves the
script able to read the origin's storage and to remove its own sandbox. The FIX-745 probe shows the reverse case
(`evidence/qa-kb-089/fix-chrome-csp-sandbox-probe.txt`): without `allow-same-origin` the script sees origin `null`
and storage throws.

INFERRED, not driven: exploitability. It needs hostile script in a deliverable, and agent output is shaped by the
prompt and by uploaded documents. The viewer would be the run's owner, or an admin, signed in to the app. Why these
two components keep `allow-same-origin` is not established. `PPTPreview.tsx:223-245` sizes the iframe element from
the parent, which does not need it, so something else may. That has to be checked before any change.

## Disposition

Open; analyzed 2026-10-09 under QA-KB-125, see the Analysis below. FIX-745 did not touch it: these files are outside
its cards, and removing `allow-same-origin` may break in-app deck or prototype behaviour. The Analysis measures exactly
what it breaks and gives a replacement that does not. The owner approved fixing it on 2026-10-09 (BUGS.md, QA-KB-125),
so this is not a product decision.

## Analysis (QA-KB-125, 2026-10-09)

Everything marked CONFIRMED was read at the cited line or measured in real Google Chrome 151. The measurements are
scripts plus their output in `evidence/qa-kb-125/analysis-1..4-*` (a throwaway origin simulated with `page.route`, no
server started, the app untouched). INFERRED items say what would settle them.

### Root cause (CONFIRMED)

No single place decides how agent-authored HTML is framed or opened. Every viewer hand-types its own
`<iframe sandbox=...>` string, and every "Open in new tab" hand-rolls `new Blob` + `URL.createObjectURL` +
`window.open`. Two consequences.

1. **The iframe token was fixed once, regressed twice, and nothing noticed.** Commit `5db19e6db` (2026-05-12, "Phase B
   G1-H7") dropped `allow-same-origin` from both `PPTPreview.tsx` and `PrototypePreview.tsx` because "the combination with
   `allow-scripts` effectively disables the sandbox - the iframe could reach into parent localStorage and read the JWT".
   Commit `77228e567` (2026-05-20) put it back on `PrototypePreview` when it moved the iframe to a `blob:` URL. Commit
   `d2970ff7f` (2026-05-27) put it back on `PPTPreview` behind `isOdPpt` and deleted the explaining comment. None of the
   three touched a frontend test, and no test has ever asserted either component's sandbox: the June tests pin only the
   generic renderer (`PreviewPanel.genericDeliverable.test.tsx`, `WorkflowHistory.genericReopen.test.tsx`).
2. **The re-adding commit rests on a false premise.** `77228e567` says "Blob URLs have a null origin - allow-same-origin
   gives the iframe same-origin access to itself (null === null) but NOT to the parent ... JWT is safe". A `blob:` URL
   carries the origin of the page that created it. Measured (`analysis-1-origin-probe.txt`, variant A): a blob iframe
   with `allow-scripts allow-same-origin` reports origin `http://app.test` and reads `localStorage.auth_token`, the
   parent's title, and the parent's storage. The validator saw the same in the real UI, 3 of 3.

"Open in new tab" is the other half. `window.open(blobUrl)` always yields a top-level document on the creator's origin,
with `window.opener` intact (variant E), and a `<meta>` CSP `sandbox` is ignored (variant F). A top-level tab has no
attribute to set, so each copy needs a structural wrapper, and none has one.

### Why the author wanted `allow-same-origin`, and what a naive removal breaks (CONFIRMED)

The blob exists to make in-page navigation work (`77228e567`: "enabling the SPA hash router in the generated prototype
HTML"). Measured (`analysis-2-nav-probe.txt`, table in [ISS-1162](20261009-1553-ISS-1162.md)): a blob frame with
`allow-scripts` alone makes `<a href="#...">`, `location.hash =` and `hashchange` silent no-ops. A plain `srcdoc` frame
makes an anchor click load the parent URL into the frame, and `history.replaceState` throws. So "delete the token" breaks
prototypes, and "switch to srcdoc" breaks them differently.

What works (row H of `analysis-2` and `analysis-4`): `srcDoc` + `sandbox="allow-scripts"` + `<base href="about:srcdoc">`
injected first in `<head>`. The origin is `null`; anchors, `location.hash`, `hashchange`, `popstate`, `replaceState` and
`pushState` all behave as they do in today's same-origin blob.

The parent has no coupling that needs same-origin. `PrototypePreview.tsx` declares `iframeRef` (`:332`) and attaches it
(`:605`) but nothing dereferences it; Tweaks are injected into the HTML string (`injectTweaksIntoHtml`, `:290-318`);
`PPTPreview.tsx` only writes `iframe.style.*` (`:233-242`). A grep for `contentWindow`, `contentDocument`, `postMessage`
and `onLoad` finds nothing in `PrototypePreview.tsx`, `PPTPreview.tsx` or `TweaksPanel.tsx`.

### Fix: where it belongs

One new module in `frontend/src/lib/` (the name `agentHtml.ts` is a suggestion), with every site routed through it:

```ts
export const AGENT_HTML_SANDBOX = "allow-scripts";          // never combined with allow-same-origin
export function frameableAgentHtml(html: string): string;   // insert <base href="about:srcdoc"> first in <head>
export function openAgentHtmlInNewTab(html: string): void;  // script-free wrapper blob around the sandboxed srcdoc frame, noopener
```

- Iframes. `PrototypePreview.tsx` goes from `src={blobUrl}` to `srcDoc={frameableAgentHtml(renderedHtml)}` and loses the
  blob state and effect (`:324`, `:356-365`) and the dead `iframeRef`. `PPTPreview.tsx` deletes `isOdPpt` and the ternary.
  The already-correct sites use the constant.
- New tab. `PrototypePreview.tsx:389`, `PreviewPanel.tsx:1597` and `:2182`, `WorkflowHistory.tsx:1006` call
  `openAgentHtmlInNewTab`; `PPTPreview.tsx:208-213` is deleted. The wrapper must escape `&` and `"` when it embeds the
  document in the `srcdoc` attribute (the probe's `esc_attr`).
- Guard. A source test over `frontend/src/**` that fails on the string `allow-same-origin` (with the
  `DesignSystemDetailModal.tsx` allowance above) and on `window.open(` fed from `createObjectURL` outside the helper. The
  repo already pins wiring this way (`overrideAgentPool.source.test.ts`), and a source pin is exactly what was missing in
  May.

Not these, each measured: deleting the token from PrototypePreview and keeping the blob (navigation dead, row B); plain
srcdoc (anchors load the parent, History API throws, rows C and D); a `<meta>` CSP sandbox inside the blob (ignored,
variant F); `noopener` alone (drops the opener, not the origin). A backend route that answers with
`Content-Security-Policy: sandbox allow-scripts`, like the share link, also works (row I), but an iframe cannot send the
bearer token, so it needs new token plumbing and is a larger change than a client helper.

### Constraints the fix must respect

- **Remount, never mutate `srcDoc`.** `PreviewPanel.tsx:253-273` records that Chrome leaves a frame blank when its
  `srcdoc` attribute is rewritten after mount (measured there on run b0642e0f). PrototypePreview's Tweaks rebuild changes
  `renderedHtml` repeatedly (400 ms debounce, `:375-382`), and today `key={blobUrl}` (`:606`) forces the remount. Moving
  to srcDoc needs a `key` that changes with the content: a counter, not the multi-megabyte string.
- **[ISS-1066](20261007-2030-ISS-1066.md) bites harder after this.** Once the in-app prototype preview is an opaque
  origin, a prototype seeded from `live-dashboard/assets/template.html:413` (unguarded `localStorage`) aborts its script
  in-app, as ISS-1066 predicts for the share link. Skill and template files are the user's to edit, so the fixer must not
  touch it; flag it to the owner. The deck templates are already guarded (see [ISS-1160](20261009-1553-ISS-1160.md)).
- **Chrome only was measured.** Firefox and Safari behaviour of the `about:srcdoc` base is untested, as is whether
  `window.open(url, "_blank", "noopener,noreferrer")` still opens a tab rather than a popup window in every browser.
- **SC-001.** Dispatch stays keyed on `mimetype` and `filename`. The helper takes HTML and knows no workflow name. No
  `routes.ts` change: no new URL.

### Documentation that must change with the fix

- `.knowledge/architecture/MOD-frontend-src-components-preview.md`, "Why this shape": "Sandboxing is deliberately
  asymmetric by trust level. First-party HTML the platform itself generated (prototype output, `od_ppt` decks) renders with
  `sandbox="allow-scripts allow-same-origin"`". That records the vulnerability as design intent. The trust model is wrong
  (the platform's own agents write this HTML from prompts and uploaded documents, which is why `5db19e6db` removed the
  token), and a reader will cite it to close this bug as intended. The hand-authored section is for the fixer's
  book-keeping to correct.
- `PreviewPanel.tsx:179`, "reuses the PPTPreview non-od_ppt pattern": that arm is dead code.
- `run_files.py:752`, "The deck preview keeps rendering through the iframe's `srcdoc`, which is sandboxed": false for
  PPTPreview until the fix.

## Resolution (QA-KB-125, 2026-10-09)

(`AGENT_HTML_SANDBOX`, `frameableAgentHtml`, `openAgentHtmlInNewTab`), with every site in the blast radius routed
through it and the source guard in `frontend/src/lib/agentHtml.test.ts`. `PrototypePreview.sandbox.test.tsx` went from
2 expected fail to XPASS (both `it.fails` report "Expect test to fail"); the markers are left for the 6-verifier.
`DesignSystemDetailModal.tsx` is allow-listed in the guard with the reason given above. The real-Chrome check on run
`4f3ebe40-8384-467c-9255-322eaf0fc183` is still the verifier's.
