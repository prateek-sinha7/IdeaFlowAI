## What was wrong

Cold-navigating to `/workflows/{id}/run` with an id that cannot resolve to a saved
workflow rendered the full authenticated Dashboard catalog (`h1: "What would you like
to build today?"`, workflow cards, "Jump back in") while `location.href` stayed on the
original, unresolvable `/workflows/{id}/run` path indefinitely — a persistent
URL/content mismatch with no not-found state and no navigation. Validated 3/3 from cold
start against a well-formed-but-nonexistent UUID, a malformed id string, and a second
distinct nonexistent UUID ([ISS-273](20260828-1653-ISS-273.md),
`BUG-20260828-010600-workflows-id-run`).

## Root cause

`frontend/src/app/[...view]/page.tsx`, the one catch-all every URL in the app renders
behind (ADR-0018). Its `/workflows/{id}/run` cold-mount effect (`:3620-3713`
pre-change) calls `userWorkflowsApi.get(workflowId)`; the `.catch()` (`:3692-3707`)
handled 401 via `handleSessionExpiry()` and then did a bare
`setWorkflowRunFailed(true)` (`:3706`) — and nothing else. The only reader of that flag
was the loading gate at `:3785-3791`:

```tsx
if (parsedView.screen === "workflow-run" && !workflowRunMainView && !workflowRunFailed) {
  return null;
}
```

whose documented purpose (`:3777-3784`) is only to render nothing while the fetch is in
flight. Once `workflowRunFailed` flipped `true` the condition went false, that gate
stopped blocking, and execution fell through every render-time return below it to the
unconditional `return <DashboardLayout ... />` at `:3818`. `workflowRunMainView`,
`workflowRunWizardMode` and `initialSavedComposition` were all still unset (the success
branch never ran), so `DashboardLayout` rendered its default Home catalog. **No
`notFound()`, `router.push` or `router.replace` was ever called on this path** — which
is exactly why the URL never moved.

It is a structural omission relative to the 3 sibling identity-fetch-failure flags in
the same file, all of which do call `notFound()`:

| Route | Flag | Set at | Gated into `notFound()` |
|---|---|---|---|
| `/runs/{id}` reopened / live-stream | `runAccessDenied` | `:3099` | `:3734-3736` |
| `/workflows/{id}/edit` | `workflowEditAccessDenied` | `:3519` | `:3741-3743` |
| `/workflows/{id}` read view | `workflowDetailFailed` | `:3570` | `:3751-3753` |
| `/workflows/{id}/run` | `workflowRunFailed` | `:3706` | **never** |

Two sibling defects in the same catch, both filed off this root cause and both fixed
here because a partial fix would have regressed:
[ISS-379](20260828-2209-ISS-379.md) — the flag had exactly one setter and no reset
anywhere, so a stale `true` survived for the rest of the SPA session and defeated the
loading-`null` gate (and, post-fix, would have fired `notFound()`) on a later, valid
`/workflows/{id2}/run`. [ISS-380](20260828-2209-ISS-380.md) — the catch was unnarrowed,
so a transient 5xx/network blip on a real, owned workflow was indistinguishable from a
genuine 404; shipping the `notFound()` gate alone would have turned that blip into a
newly-introduced PERMANENT not-found.

Blast radius re-confirmed by grep before editing and still holds:
`grep -rn "userWorkflowsApi\.get(" frontend/src/` returns 3 call sites, all in this one
file (`:3482` edit view, `:3542` read view — both already correctly gated — and `:3627`,
this one). `grep -rn "workflowRunFailed" frontend/src/` returns only this file's
declaration (`:409`), its setter and its one gate. No other component fetches a saved
workflow by id; the click-through launch path (`DashboardLayout.handleLaunchSaved`)
already has the object in hand and never issues this fetch. There is no other caller to
route through.

## What changed and why there

All three changes land in the SAME effect and its render gate in
`frontend/src/app/[...view]/page.tsx` — the only place the failure is produced and the
only place it is consumed.

**Reset (ISS-379)** — `setWorkflowRunFailed(false)` added immediately before
`userWorkflowsApi.get(workflowId)` in the cold-mount effect, mirroring
`workflowEditAccessDenied`'s existing pre-fetch reset. Placed before the fetch rather
than on the success path so the clean slate exists while the request is in flight, which
is precisely the window the loading gate covers.

**Narrowing (ISS-380)** — the bare `setWorkflowRunFailed(true)` is now
`if (err instanceof ApiError && (err.status === 403 || err.status === 404))`, byte-for-byte
the same predicate `workflowEditAccessDenied` (`:3518`) and `workflowDetailFailed`
(`:3568`) already use after the F7 audit fix. Every other error keeps the
`console.error` log-and-continue above it, so a 5xx on a valid id leaves the loading gate
holding (renders nothing) instead of asserting a not-found — the identical degrade
`workflowDetailFailed`'s `if (!workflowDetail) return null;` already produces. Landed in
the same change as the gate, not a second pass, because the gate is what makes the
unnarrowed catch dangerous.

**The gate (ISS-273)** — `if (parsedView.screen === "workflow-run" && workflowRunFailed)
{ notFound(); }` added directly above the existing loading-`null` return, so a resolved
failure short-circuits before the fall-through to `<DashboardLayout>`. Placed here rather
than beside the other three `notFound()` blocks higher up to keep it adjacent to the gate
it corrects and inside the same commented `workflow-run` region.

The stale comments on the catch ("A 403/404 (or any other failure) still falls back to
Home, same as before this fix") and on the loading gate ("workflowRunFailed lets a genuine
fetch failure still fall through to Home") described the exact behaviour this change
removes, so both were rewritten. No other line in the file was touched.

Deliberately NOT done: the now-redundant `!workflowRunFailed` term still in the
loading-gate condition. `notFound()` throws above it, so the term can never be false
there any more — but removing it is a cosmetic edit no card asked for, and leaving it
keeps the diff to the three behavioural changes.
