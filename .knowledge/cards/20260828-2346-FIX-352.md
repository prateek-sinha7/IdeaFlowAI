## What was wrong

On `/workflows/new`, naming a workflow and adding an agent, then clicking the composer's
own Back control, navigated away instantly and threw every bit of that state away — no
confirmation, no `beforeunload`, no draft. Returning to `/workflows/new` showed a blank
"Untitled workflow" with 0 agents. Reproduced 3/3 (see
[ISS-275](20260828-1855-ISS-275.md), `BUG-20260828-003800-workflows-new`).

## Root cause

`ComposerPage`'s Back button wires `onClick={onBack}` raw
(`frontend/src/components/workflow/composer/ComposerPage.tsx:979` at the time of the
report). `onBack` is `handleBackNav`
(`frontend/src/components/layout/DashboardLayout.tsx:1701`), which called
`router.back()` / `router.push(routes.home())` unconditionally — it cleared its own
cross-cutting state (questionnaire, pending run) and had no visibility at all into any
mounted child's uncommitted state. The same handler is wired as `onBack` to all five of
`DashboardLayout`'s page mounts, so the gap was never composer-specific; the composer is
just where it was reproduced.

## What changed and why there

**`DashboardLayout.tsx` — the guard, in the one shared handler.**
A `hasUnsavedWork` ref plus a stable `handleUnsavedChange` callback sit directly above
`handleBackNav`, which now opens with:

```tsx
if (hasUnsavedWork.current && typeof window !== "undefined" &&
    !window.confirm("You have unsaved changes. Leave anyway? Your work will be lost."))
  return;
```

A ref, not state, so the live value is readable without re-creating the callback on every
keystroke in the child. Putting it here rather than on the composer's own button is the
whole point: the other four mounts (`IdeaInputPage`, `AccountSettings`, `AnalyticsPage`,
`WorkflowHistory`) reach the same guard the moment they start reporting a dirty signal —
no second `confirm()` anywhere.

**`ComposerPage.tsx` — the per-child signal.**
A new optional `onUnsavedChange?: (dirty: boolean) => void` prop, driven by a snapshot of
the workflow name plus the roster's `id:name` pairs (so add / remove / reorder / rename all
move it) compared against an `unsavedBaseline` ref. The baseline is `null` = "recapture on
the next commit", set at mount, again by the existing library re-seed effect (which
*replaces* the roster with the same saved composition, so the mount-time snapshot would
otherwise read as a user edit on `/workflows/{id}/edit`), and again after a successful
save. Unmount reports `false`, so no other page can inherit a stale dirty flag.

Known ceiling: per-node skill and prompt edits do not move the snapshot on their own —
only name and roster do, which is what the card scoped and what a discard visibly costs.

Not touched: `handleGoHome`, the sidebar and header nav, and a raw address-bar navigation.
The card scoped the Back control; a `beforeunload` guard is a separate decision.

## Deferred

[ISS-371](20260828-2140-ISS-371.md) (IdeaInputPage) and
[ISS-372](20260828-2141-ISS-372.md) (AccountSettings) stay open: the guard is now in
place for them, but neither page reports `onUnsavedChange` yet, so each still needs its
own one-line wiring plus its own definition of dirty.
[ISS-373](20260828-2142-ISS-373.md) (`/workflows/{id}/edit`) is mechanically covered —
same component, same snapshot, and the baseline is rebaselined off the library re-seed
precisely so a freshly opened saved workflow is not born dirty — but it has not been
independently exercised in a browser, so it stays open for its own verification.
