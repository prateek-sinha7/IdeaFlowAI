### BUG-013 — Reopening a clarify-paused run under ≥6 concurrent non-terminal runs hangs the reopen `GET /api/runs/{id}` (browser HTTP/1.1 connection-limit exhausted by per-run SSE streams) → empty IDLE lane, no clarify, stale "USER_STORIES" label  [🟠 major] [FIXED ✅]
- **RESOLVED:** FIXED (quick 260716-r7d, commits `aebff868`/`c35f73e6`) via the minimal+hardening fix. **Part A** (`RunConnectionProvider.tsx`): replaced `NON_TERMINAL_STATUSES` with `AUTO_STREAM_STATUSES`={running,planning,analyzing,generating,revising} — BACKGROUND parked runs (`waiting_for_user`/`clarifying`) no longer auto-open a stream (they emit nothing while parked); a single sticky `focusedRunId` (set by `attachRun`, new replaces prior) is unioned into `liveRunIds` behind the identity guard so the VIEWED/launched run still streams; the page `attachRun(fullRun.id)`s on reopen, gated to NON-terminal runs (`REOPEN_TERMINAL_STATUSES`) so a completed reopen never pins a dead-stream reconnect loop (plan-checker warning). **Part B** (`api.ts`): AbortController ~30s timeout on `request()` → a starved call rejects with a typed `ApiError` instead of hanging silently. RED→GREEN: 7 provider/timeout/source-lock tests (5 fail→7 pass); tsc clean; full vitest 742 pass / 8 known baseline reds; mocked SSE/reconnect/history/revision/clarify Playwright 32 pass/0 fail; at-risk 29/29; SC-001 clean. **LIVE-PROVEN** (screenshot `bug013-clarify-fixed.png`): with 6 parked runs present, dashboard auto-streams dropped **12 → 0**; the in-page `localhost:8000` fetch that hung 8s now returns **200 @113ms**; reopening the clarify-paused run renders lane state **"clarify"** with all **6 questions + options** on screen (was empty "idle"), and the reopen attaches exactly **1** stream (the focused run). Regression from Phase 44 SSE cutover + DEF-44-12-3; fixed here. Residual (separate, cosmetic) — **NOW FIXED** (quick 260716-sml, `d917d8c1`): the type LABEL read "USER_STORIES" for a non-terminal reopen because the BUG-012 `viewedRunType` binding (`DashboardLayout.tsx:1274`) was `!isPipelineRunning`-gated + the header pill (`:1475`) used raw `workflowType`. Fixed by un-gating `viewedRunType` (prefer the durable `contentSourceRunType`, which is set only on reopen, regardless of running state) + binding the header pill to `effectiveReviseType`. Launch→watch byte-identical (contentSourceRunType null on launch). RED→GREEN (DashboardLayout.laneTitle Test A/B); tsc clean; at-risk 23/23. **LIVE-PROVEN**: the same reopened clarify-paused prototype run now shows lane "OD_PROTOTYPE" + header "od_prototype" (was "USER_STORIES"/"User Stories"), clarify intact. Closes the entire stale-`workflowType` family (BUG-006 label / BUG-008 generic gate / BUG-012 typed dispatch / this = non-terminal reopens).
- **Found:** 2026-07-16 · live Bedrock QA (user had 6 `waiting_for_user` runs) · surface run screen reopen via Home recents, on an **`od_prototype` no-template clarify-paused** run `586f4ad4-bdc1-4b21-b295-ea262b0b609f` ("Build a prototype on apple products…", 6 questions ready). Screenshot `~/.claude/jobs/e660aea4/tmp/clarify-reopen.png` + `probe-clarify.png`.
- **Symptom:** Reopening the run from Home recents (fresh browser) renders the run screen's left lane **empty in `data-run-state="idle"`** — no clarify card, no questionnaire (the 6 real questions never appear), no Steps/pipeline trace, no chat — with the deliverable area showing "Output will appear here" and the neutral "Message the run…" composer. The lane type chip wrongly reads **"USER_STORIES"** for this od_prototype run. **NOT** BUG-005's "0/0 BUILDING + Steer" symptom (that was `building` + `isRunning` true; this is `idle` + `isRunning` false). Backend is CORRECT (durable events `workflow_validated, planner_start, planner_complete, gate_status, questionnaire_ready(6q, carries pipeline_run_id), chat_reply`; **no** `pipeline_start` — clarify is PRE-build; verified via `/events`).
- **Root cause (investigation agent — read `.planning/IMPLEMENTATION-REGISTER.md` run-screen/SSE sections + `SSE-QA-BUG-LOG.md` BUG-004/005/010/011/012 + traced the reopen + SSE transport in source; RUNTIME-PROVEN with a Playwright discriminator, not reasoned):** **the browser's HTTP/1.1 ~6-connections-per-origin limit is fully consumed by the 6 concurrent long-lived EventSource SSE streams that `refreshLiveRuns` auto-attaches (one per non-terminal run), so the reopen's same-origin `GET /api/runs/{id}` has no free connection slot and QUEUES INDEFINITELY** — the reopen `await` never resolves, so `contentSourceRunId`/`contentSourceRunType`/the durable-event replay never run, and the lane renders the initial idle state with the stale default `workflowType`.
  - **Chain (each link verified, clean-tree line numbers):**
    1. **Trigger:** `frontend/src/providers/RunConnectionProvider.tsx:222-244` `refreshLiveRuns` does `getWorkflows(t,{limit:50})` then `.filter((r) => NON_TERMINAL_STATUSES.has(r.status))` (`:232`) and mounts **one `RunStreamConnection` per id** — `liveRunIds.map((runId) => <RunStreamConnection>)` (`:358`), i.e. **one native EventSource SSE stream per run**. `NON_TERMINAL_STATUSES` (`:60-68`) includes `waiting_for_user` + `clarifying`. The 6 clarify-paused runs (`586f4ad4` od_prototype, `6c230eab` app_builder, `6af0a82d` user_stories, `8941d0f3`/`7cf6ddb8` od_prototype, `50e59943` user_stories) therefore open **6 concurrent long-lived streams to `localhost:8000`** — exactly Chromium's 6-per-origin HTTP/1.1 cap. (Backend is HTTP/1.1: `curl -I` → `HTTP/1.1 405`; h2 would multiplex and dodge the cap.)
    2. **The starved call:** reopen click → `page.tsx handleSelectWorkflowRun` (`:1228`) → `getToken()` OK (`:1242`) → `await getWorkflow(currentToken, run.id)` (`:1246`) → `frontend/src/lib/api.ts` `getWorkflow` (`:405`) → `request('/api/runs/586f4ad4', {GET})` → **bare `await fetch(url)` with NO timeout/retry/mutex** (`api.ts:85`), `url = BASE_URL + path`, `BASE_URL = ENV.API_URL` (`api.ts:18`) = **`http://localhost:8000`** in dev (`env.ts resolveApiUrl` → localhost branch). This is the SAME origin as the 6 streams → **no free connection → the request is issued but never gets a socket → hangs forever.**
    3. **Reopen aborts silently:** because the `await` at `page.tsx:1246` never settles, `setContentSourceRunId(fullRun.id)` (`:1250`), `setContentSourceRunType` (`:1253`), the `if (fullRun.id !== pipelineState.pipelineRunId)` durable-event replay (`:1264`) + `seedRunChatTranscript`, and the deliverable seed **all never execute**. No throw ⇒ the outer catch (`page.tsx:1375` "Failed to load workflow output") never fires either — consistent with the "no console errors captured" ground truth.
    4. **Render = initial idle + stale label.** With `contentSourceRunId` still `null`, `questionnaireData` `null`, `activePipelineRunId` `null`, `pipelineState` reset (`isRunning=false`, `agents=[]`): `laneClarifyOpen = questionnaireQuestions.length>0 && (…)` (`DashboardLayout.tsx:1355`) = **false**, `isPipelineRunning=false` ⇒ `runLaneState` (`:1358-1364`) falls all the way to **`"idle"`**. And `viewedRunType` (`:1274`) is gated `!isPipelineRunning && contentSourceRunId != null` → `true && false` → **undefined** → `effectiveReviseType = viewedRunType ?? workflowType` = the default `workflowType="user_stories"` → the type chip `runType={effectiveReviseType || pipelineState?.pipeline_type}` (`:1771`) renders **"USER_STORIES"**. So the stale label is a **downstream symptom of the same hang** (contentSourceRunId never set) — NOT the BUG-006/012 `isRunning`-gate mechanism (here `isRunning` is false) and NOT a separate seed gap.
  - **RUNTIME PROOF (discriminator, `~/.claude/jobs/e660aea4/tmp/probe-connlimit.mjs`, temporary probes in `page.tsx` since reverted — tree clean):** at reopen, probes fired `hsr-called` → `token=present` → `before-getWorkflow`, then **nothing** (no `after-getWorkflow`, no `outercatch`) for 35 s — the app's `GET http://localhost:8000/api/runs/586f4ad4` request was issued (`p.on('request')`) but received **no response/finished/failed** in 12 s. The clincher: two timed fetches to the **same endpoint** fired concurrently from the page — `sameOrigin http://localhost:8000` → **AbortError at 7002 ms (hung)**; `crossOrigin http://127.0.0.1:8000` → **200 in 8 ms**. Same backend, same URL path, same instant — only the ORIGIN differs (127.0.0.1 has its own un-saturated connection pool). `curl localhost:8000/api/runs/586f4ad4` also returns 200 in 3 ms. Backend/pool are healthy — this is purely a browser per-origin connection-queue starvation. (Ruled out: DB pool exhaustion — BUG-004 fix `d418b5a1`/`56deb5c4` IS present; getToken null — `token=present`; getWorkflow reject — no catch fired; replay throw — replay never runs.)
  - **Hypotheses (task) verdict:** **H1 (replay throws before `questionnaire_ready`) — REFUTED:** the replay loop never runs (hang precedes it); and the 4 pre-questionnaire reducer handlers (`useWorkflow.ts:710/731/754/795`) are pure scalar setters that don't touch `agents[]`, so they wouldn't throw on a missing `pipeline_start` anyway. **H2 (`questionnaireQuestions` effect timing, `DashboardLayout.tsx:597-602`) — REFUTED:** `questionnaireData` is never set, so the effect has nothing to copy; not a timing issue. **H3 (`activePipelineRunId` never set / cleared) — TRUE as a downstream symptom, not the cause:** the durable `questionnaire_ready` DOES carry `pipeline_run_id` (verified), so the replay WOULD set it — it's just never reached. **H4 (multi-run fan-out) — CORRECT as the TRIGGER, but via a DIFFERENT mechanism than hypothesized:** it is not a foreign `pipeline_start` poisoning global clarify state (that is BUG-005, already fixed `8eec694c`, and needs ≥1 *building* run — all 6 here are gate-paused and emit no `pipeline_start`); it is the 6 concurrent *streams* exhausting the browser connection pool.
  - **Launch vs reopen — SAME root, different starved call (reopen RUNTIME-PROVEN; launch REASONED):** the live "no-template prototype parks at clarify but never shows questions" path shares the identical connection-exhaustion root — with 6 streams already open, a fresh launch's same-origin `POST /api/runs` (`RunConnectionProvider.tsx:318-320` `sendCommand`) queues behind the streams (mint hangs/delays), and even once minted the launched run's own stream is a 7th connection that can't open → its clarify frames can't arrive → no questions. A **clean single-run launch (≤5 other non-terminal runs)** stays under the cap and shows clarify normally — i.e. the failure is conditional on ≥6 concurrent non-terminal runs, not on workflow type or no-template.
  - **REGRESSION — introduced by the SSE work, in two steps; NOT pre-existing and NOT from the BUG-005/DEF-44-12-4 state-binding quicks:** (1) **Phase 44 / 44-06 (`a931c066`/`f6ce1142`, 2026-07-15)** deleted the single multiplexed WebSocket transport and replaced it with **one SSE EventSource per run** — so N runs now = N browser connections (the file's own comment at `RunConnectionProvider.tsx:58` admits "the WS transport masked this because it reconnected by run-id, status-agnostic"). (2) **DEF-44-12-3 (`0563afad`, 2026-07-16 — THIS session)** authored the current `NON_TERMINAL_STATUSES` set INCLUDING `waiting_for_user`/`clarifying` (git-blame `:60-68` = `0563afad7`), so gate-paused runs — which stream nothing — now each HOLD a connection. The BUG-005 (`8eec694c`) and DEF-44-12-4 (`dhr`) work is orthogonal (reducer/clarify state binding, not transport) and neither caused nor fixes this.
- **Fix (PROPOSED — investigation only, NOT applied; this is a TRANSPORT-layer bug, so the deferred "systemic per-run subscriber scoping" from BUG-005 #2 / BUG-010 does NOT address it — that scopes which frames reach the reducer, not how many connections are open):**
  - **PRIMARY (minimal, directly removes the starvation): don't hold an SSE stream open for gate-paused runs.** A `waiting_for_user`/`clarifying` run emits NO further frames until the user acts, so its stream is pure connection-waste. Drop `"waiting_for_user"` + `"clarifying"` from `NON_TERMINAL_STATUSES` (`RunConnectionProvider.tsx:60-68`) so `refreshLiveRuns` attaches only genuinely-streaming states (`running`/`planning`/`analyzing`/`generating`/`revising`). The viewed clarify run is already seeded via the durable `getRunEvents` replay in `handleSelectWorkflowRun` (`page.tsx:1287`), not a live stream; **re-attach on demand** when the user submits the questionnaire/opens the run (`attachRun(id)` already exists, `:305`). This keeps concurrent streams well under 6 in the reported scenario. Caveat to verify: a clarify run advanced by ANOTHER tab won't auto-refresh its lane until re-attach — acceptable, and DEF-44-12-3's history-open attach can be preserved by attaching the *single* opened run.
  - **DURABLE (correct architecture, larger): a single multiplexed SSE connection for all runs** (one `GET /api/runs/events/stream?ids=…` fan-in) instead of one EventSource per run — restores the pre-44 single-connection model and removes the N-connection cap entirely. Backend adds a multiplexed endpoint; FE collapses `liveRunIds.map(<RunStreamConnection>)` into one stream. **OR** cap `refreshLiveRuns` to attach at most ~3 streams (prioritising the viewed/active/most-recent run) so REST always has free slots. Serving prod over HTTP/2 raises the cap to ~100 streams/connection but is not a real fix (still bounded, and dev stays broken).
  - **HARDENING (defense-in-depth, orthogonal): add an `AbortController` timeout to `request()` (`api.ts:80-95`)** so a starved fetch fails fast (→ the outer catch fires + a visible error) instead of hanging silently forever — turns this class of bug from an invisible idle screen into a surfaced error. Does not fix the starvation; makes it diagnosable.
- **Verify (fail-before / pass-after — proposed):**
  1. **Fail-before:** with ≥6 `waiting_for_user`/non-terminal runs (⇒ 6 auto-attached SSE streams to the app origin), reopen a clarify-paused run from Home recents → lane `data-run-state="idle"`, no clarify/questions, type chip "USER_STORIES"; the app's `GET /api/runs/{id}` stays pending indefinitely. (Reproduced live 2026-07-16 for `586f4ad4`; discriminator: same-origin fetch AbortError@7s vs cross-origin 200@8 ms — `probe-connlimit.mjs`.)
  2. **Pass-after (PRIMARY):** with clarify/`waiting_for_user` excluded from auto-attach (≤2 streams open), the same reopen resolves `getWorkflow` in <50 ms → `contentSourceRunId` set → durable replay runs → `questionnaire_ready` seeds the 6 questions → `runLaneState="clarify"`, questions render + answerable, chip = "OD_PROTOTYPE". Repeat with 8–10 concurrent non-terminal runs to confirm REST never starves.
  3. **No-regression:** a single live no-template od_prototype launch still shows clarify (≤ cap); answering clarify → build still streams (on-demand re-attach); ≤5-concurrent-run reopens unaffected; `tsc --noEmit` clean.
  4. **Unit:** a `RunConnectionProvider` vitest asserting `NON_TERMINAL_STATUSES` excludes `waiting_for_user`/`clarifying` and that `refreshLiveRuns` yields ≤ the cap; optionally an `api.request` test asserting an `AbortController` timeout rejects a hung fetch.
