## Root Cause

**CONFIRMED — backed by code read.**

### 1. `AgentRollup` backend model has no `pipeline_types` field

`backend/app/api/analytics.py` lines 142–157:

```python
class AgentRollup(BaseModel):
    agent_id: str
    agent_name: str
    count: int = 0
    total_tokens: int = 0
    input_tokens: int = 0
    output_tokens: int = 0
    cost: float = 0.0
```

No `pipeline_types` field exists. The `_aggregate` function (lines ~395–405)
builds each `AgentRollup` purely from `agents_acc`, which is keyed on
`agent_id` — it never reads `r.type` (the run-level pipeline type string)
during the per-agent accumulation pass.

### 2. The accumulator loop has `r.type` but never uses it per agent

`_aggregate` lines ~282–330: the per-agent loop walks `agent_list` parsed
from `r.agent_outputs`, but the outer `WorkflowRun` row `r` carries
`r.type` in full. The accumulator simply never reads it. `r.type` is the
pipeline type (`prototype`, `ppt`, `user_stories`, etc.) stored when the run
was created — it is the ground truth and requires no new column or migration.

### 3. `agent_outputs` JSON blob does not store `pipeline_type` per entry

`_apply_terminal_output_columns` in `run_commands.py` writes each agent
entry from `agent_start` events. The `agent_start` payload (engine.py line
~7831–7834) is:

```python
{"agent_id": spec.id, "name": spec.name, "role": spec.role,
 "icon": spec.icon, "index": index, "total": len(ordered_agents),
 "model_id": _start_model_id, ...}
```

No `pipeline_type` key. This is intentional (SC-001 — the engine is
workflow-agnostic), and **not where the fix belongs** — see Fix Approach below.

### 4. Frontend `agentRows` derivation drops all pipeline context

`AnalyticsPage.tsx` lines ~342–349:

```typescript
const agentRows = (summary?.agents ?? []).map((a) => ({
  id: a.agent_id,
  name: a.agent_name,
  runs: a.count,
  tokens: a.total_tokens,
  cost: a.cost,
}));
```

No `pipeline_types` in the mapped shape. The "By Agent" rendering at
lines ~614–647 shows `a.name` as the sole label chip — no secondary
workflow chip rendered.

## Fix Approach (3-layer, additive)

| Layer | File | Change |
|---|---|---|
| Backend model | `backend/app/api/analytics.py` | Add `pipeline_types: list[str]` to `AgentRollup`; in `agents_acc` track a per-agent `set[str]` of `r.type` values; serialize to `list` in `agent_rollups` |
| Frontend type | `frontend/src/lib/api.ts` (or wherever `AgentRollup` interface lives) | Add `pipeline_types: string[]` to the interface |
| Frontend render | `frontend/src/components/analytics/AnalyticsPage.tsx` | Map `pipeline_types` into `agentRows`; render a small chip per pipeline next to `a.name` using the existing `PIPELINE_LABELS` map (already present for the By Pipeline Type section) |

Notes:
- No new DB column, migration, API endpoint, or golden regeneration required.
  `r.type` is already on the `WorkflowRun` row read in `_aggregate`.
- The `PIPELINE_LABELS` dict in `AnalyticsPage.tsx` already maps every known
  pipeline type to its display label — the chip labels are ready to use.
- An agent can belong to multiple pipelines (ADR-0023: `AgentSpec.pipeline_type`
  is `str | list[str]`). At analytics time each agent occurrence is tied to
  exactly one `r.type`, so accumulating a set per `agent_id` across runs
  correctly collects all pipelines that agent has been invoked from.
- SC-001 / INV-1 are not violated: the accumulation keys on `r.type` generically
  and emits whatever pipeline strings are present — no workflow names in the kernel.
