## Why this must also be broken

[ISS-321](20260828-2002-ISS-321.md) root-caused `/create/prototype` (and `/create/ppt`) reaching a
fully interactive `LaunchWizard` for an unentitled tier because `frontend/src/app/[...view]/page.tsx`
fetches `user.tier` (line ~868) for display only and never calls `canRunPipeline`/`can_run_pipeline`
before the `wizardMode` render branch at lines 3833-3838.

That branch is not the only render path out of the same catch-all. `initialMainViewFor` (`page.tsx`
lines 124-131) maps the `create-app`, `create-user-stories`, and `create-workflow` (for any
catalog pipeline type other than `ppt_v2`) screens onto `MainView: "input"` — a completely
different code path from `wizardMode`. `DashboardLayout.tsx:2901-2930` renders `<IdeaInputPage>`
for `mainView === "input"` and passes it `workflowType`, `onRun`, `initialAgentIds`, etc. — **no**
`userTier` or any tier-shaped prop. Confirmed by reading `IdeaInputPage.tsx` in full: `grep -n
"tier\|entitle\|can_run_pipeline\|canRunPipeline"` returns exactly one hit, an unrelated comment
about "priority tier" ordering in an intent-matching list — the component has no tier awareness to
gate with even if it wanted to.

`DashboardLayout.tsx` DOES receive `userTier` as a prop (line 454, forwarded from
`page.tsx:4187`'s `userTier={user?.tier ?? "basic"}`), and DOES pass it onward — but only to
`AppHeader` (line 2574, cosmetic tier badge/upgrade button) and to `HomeLaunchGrid` (line 2750,
the one place that correctly calls `canRunPipeline(userTier, type)` to disable a catalog card).
Every other `mainView` branch, including `"input"`, ignores the prop entirely. This is the exact
same missing-check shape ISS-321 found, reproduced in a second component the catch-all also
renders unconditionally.

## Expected vs actual

**Expected:** a basic-tier account navigating to `/create/app` (or `/create/user-stories`, or any
`/create/<type>` whose composer is the Input panel rather than the wizard) sees the same
locked/upgrade state the dashboard catalog card shows for that type, consistent with
`/settings/usage`.

**Actual (INFERRED -- not yet independently reproduced):** `IdeaInputPage` should render fully
interactive -- brief textarea, agent picker, model overrides -- for a pipeline type the account's
tier does not include (e.g. `app_builder`, entitled only from `pro` up per
`backend/app/core/entitlements.py:24-31` / `frontend/src/lib/entitlements.ts:34-44`), with the
backend's `_require_tier_entitlement` (`run_commands.py:2202`) as the only actual rejection, same
as ISS-321's confirmed behavior for `prototype`.

## What would confirm or refute this

Sign in as `qa-basic@flowinqa.com`, navigate directly to
`http://localhost:3000/create/app` (basic tier excludes `app_builder`). Confirm the Input panel
renders fully interactive with no lock/upgrade indication, and that typing a brief + clicking Run
reaches the backend 403 rather than being blocked client-side. A miss (some other gate intercepts
first) would refute this card.

## Where the fix belongs

Same choke point ISS-321 already identifies: `frontend/src/app/[...view]/page.tsx` already knows
both `user.tier` and the resolved pipeline type (via `wizardModeFor`/`initialWorkflowTypeFor`) at
the exact point it decides what to render. A single guard placed there -- before the `wizardMode`
early return AND before `mainView` is allowed to resolve to `"input"`/`"composer"` for an
unentitled type -- covers this card, ISS-321, and [ISS-474](20260829-0112-ISS-474.md) in one
change, using the existing `canRunPipeline(tier, pipelineType)` from
`frontend/src/lib/entitlements.ts:94` (already the source of truth `HomeLaunchGrid` calls). Adding
the check separately inside `IdeaInputPage` and `LaunchWizard` would also work but duplicates the
call at every current and future render site instead of the one place all of them already route
through.

### Root cause (CONFIRMED)

The client-side entitlement check is wired into individual surfaces, not into the launch path, and this surface was never wired.

1. `canRunPipeline` / `getUpgradeTier` are called from exactly three components (evidence 2). `IdeaInputPage.tsx` (2,314 lines) imports neither and takes no tier prop (`IdeaInputPageProps`, `:775-827`; signature `:962`).
2. `DashboardLayout` has the value (`userTier`, `:267`, default `"basic"` at `:491`) but forwards it only to `AppHeader` and `HomeLaunchGrid`. The `mainView === "input"` branch renders `<IdeaInputPage ...>` at `:3159-3178` without it.
3. The Run path therefore tests nothing about the plan. `handleRun` opens with `if (!ideaInput.trim() || pipelineAgents.length === 0) return;` (`IdeaInputPage.tsx:1566-1567`); the Run button is
   `disabled={isSubmitting || !ideaInput.trim() || pipelineAgents.length === 0 || (isMigrationMeta && !migrationChoice)}` (`:2009`); and the brief box's shortcut calls the handler directly,
   `onSubmitShortcut={handleRun}` (`:1952`), so Cmd/Ctrl+Enter would bypass even a disabled button.
4. What `handleRun` dispatches is `resolveDispatchType(pipelineAgents, effectiveType).type` (`:1616`), and `resolveDispatchType` (`:450-471`) returns `baseType` unchanged unless it is `custom`. So the dispatched type equals
   `effectiveType` (`:988`: the migration sub-choice if one is made, else `workflowType`). That is the correct gate key.
5. `onRun` is `handleRunPipeline` (`DashboardLayout.tsx:1759`), which sets `setMainView("execution")` (`:1761`) before the POST, then calls `onStartPipeline` (`:1816`), `page.tsx:4256`, and `RunConnectionProvider.tsx:520-529` (throws `ApiError` on a non-2xx).
6. The only enforcement is the backend: `run_commands.py:3510`, `_require_tier_entitlement(current_user, principal, pipeline_type)` (`:2558-2601`), a 403 with code `tier_not_entitled` and the upgrade text. The reads that precede it are not tier gated:
   `GET /api/workflows/{id}` has no `can_run_pipeline` / `effective_tier` (evidence 6), and `GET /api/agents/library` has no entitlement check, so nothing upstream stops the panel from rendering fully usable.

The tier the client would use agrees with the server's: `GET /api/auth/me` returns `effective_tier(user, principal)` (`auth.py:699-704`), the same authority the gate uses.

### Blast radius

One render site, several ways in. `IdeaInputPage` is rendered once (`DashboardLayout.tsx:3159`); everything that sets `mainView = "input"` reaches the ungated panel:

- cold URL (typed, refreshed, shared): `/create/app`, `/create/backlog` and any `/create/<catalog type>`. `page.tsx:150-157` maps `create-app`, `create-user-stories`, `create-workflow` to `"input"`, and `initialWorkflowTypeFor` (`:386-397`) seeds `app_builder` / `user_stories` / `{type}` into `DashboardLayout.tsx:627-637`;
- `handleLaunchSaved` (`:1631-1750`, `setMainView` at `:1746-1748`): saved non-composer workflows, for example after a downgrade. My Workflows' "Run workflow" button (`SavedWorkflowsPage.tsx:395-398`) has no tier check;
- `handleEditBrief` (`:2367-2410`, `setMainView("input")` at `:2395`): "Edit brief and run again" on an older run;
- in-app `handleSelectFeature` (`:1569-1581`) is pre-gated at the catalog tile (`HomeLaunchGrid.tsx:246`). Its other caller, My Workflows' "New workflow" (`DashboardLayout.tsx:3145`, `SavedWorkflowsPage.tsx:270-275`, no tier check), passes `custom`, which opens the composer: [ISS-474](20260829-0112-ISS-474.md).

Types that can lock here (launchable, non-beta; evidence 7): `app_builder` for `basic` and `hexaware`; `backlog` for `basic`; the `ex_*` fixtures for everything below `enterprise`. `prototype*` and `ppt*` go to the wizard ([FIX-497](20260829-0242-FIX-497.md)). `user_stories` never locks.

Same flaw on neighbouring surfaces: `ComposerPage` ([ISS-474](20260829-0112-ISS-474.md)), the Save buttons ([ISS-968](20261002-0338-ISS-968.md)), and the unhandled refusal ([ISS-969](20261002-0338-ISS-969.md)).

### Where the fix belongs

**Inside `IdeaInputPage`**, mirroring FIX-497's placement for `LaunchWizard` (`LaunchWizard.tsx:910-911`, applied at `:1001`, `:1374-1381`, `:1437`). Not in `page.tsx` as this card first proposed: `handleLaunchSaved` and `handleEditBrief` write `mainView` directly in `DashboardLayout` state and never pass through
`initialMainViewFor`, so a page-level guard misses them; and `page.tsx` renders before `user` has loaded, so it would have to wait (blank render) or redirect instead of showing the locked state the bug asks for.

1. **Gate key:** `effectiveType` (not `workflowType`, which is `"migration"` until a sub-path is chosen). `locked = tier !== null && !canRunPipeline(tier, effectiveType)`; `upgradeTo = tier !== null ? getUpgradeTier(tier, effectiveType) : null`. Data-driven through `TIER_PIPELINES`, no per-workflow-name branch (SC-001 / INV-1).
2. **The tier source must be nullable. Do not pass DashboardLayout's `userTier` as it is.** It is `"basic"` until `getMe` resolves and stays `"basic"` if it fails: the default at `DashboardLayout.tsx:491`, `userTier={user?.tier ?? "basic"}` at `page.tsx:4488`, and
   `.catch(() => { /* Non-fatal — tier defaults to "basic" if fetch fails */ })` at `:957-959` (evidence 4). Used as is, an `enterprise` or `pro` account would get a locked Run on a cold `/create/app` while the profile request is in flight, and permanently if it fails.
   FIX-497 set the rule: unknown tier never locks, so a profile blip cannot brick an entitled user. Options, smallest first:
   (a) `useAppSelector((s) => s.auth.user?.tier ?? null)`: the profile is already dispatched into Redux at `page.tsx:955` (`authSlice.ts:29`), it is `null` until loaded, `IdeaInputPage` already reads Redux through `useAgentLibrary`, and the shared test store has the slice (`renderWithProviders`);
   (b) a new optional, nullable prop threaded from `page.tsx` through `DashboardLayout`; (c) its own `getMe`, like `LaunchWizard.tsx:380` (one extra request, and every `vi.mock("@/lib/api")` factory in the tests then needs `getMe`, as FIX-497 found).
3. **Apply `locked` in three places**, as FIX-497 did: `handleRun`'s early return (this also covers the shortcut at `:1952`), the Run button's `disabled` (`:2009`), and a lock banner with the same wording and classes as `LaunchWizard.tsx:1374-1381` / `HomeLaunchGrid.tsx:344-348`
   (`Requires {TIER_LABELS[upgradeTo]} plan`), shown instead of the "Run workflow" label. Save: [ISS-968](20261002-0338-ISS-968.md).
4. **Precondition:** [ISS-970](20261002-0339-ISS-970.md). The lock trusts the frontend `TIER_PIPELINES` mirror, which is one id short today (`sample_subagents_parallel`: beta, impact nil), and the test that pins it is red.

## Resolution 2026-10-02

Resolved by [FIX-716](20261002-1230-FIX-716.md). The fix went where the analysis above placed it: inside `IdeaInputPage`, keyed on `effectiveType`.
- The tier source is option (b), a nullable `userTier` prop. `DashboardLayout` fills it from the Redux profile (`s.auth.user?.tier ?? null`), so an unknown tier never locks.
- `locked` gates `handleRun` (and so Cmd/Ctrl+Enter), the Run button and a "Requires <tier> plan" banner. It also gates both Save buttons, the Input-panel half of [ISS-968](20261002-0338-ISS-968.md).
- `IdeaInputPage.iss472.test.tsx`: both `it.fails` cases now report "Expect test to fail". The marker is left for the verifier.
- The "Hazards" note about the stale `workflowType` on a cold `/workflows/{id}/run` is filed as [ISS-1048](20261002-1231-ISS-1048.md) (open, INFERRED).
