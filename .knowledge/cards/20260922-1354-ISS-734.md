# ISS-734

## Description

**INFERRED sibling of [ISS-733](20260922-1353-ISS-733.md) (QA-PS-021's root
card) — not reproduced. Filed because the root cause implies it, not because
it was observed.**

ISS-733 establishes that `_build_validation_target`
(`backend/agents/capabilities/gates/validation.py:158-217`) never checks
whether a specific upstream artifact a step depends on actually exists — it
only resolves the RUN's overall declared deliverable. That function is not
custom-workflow code: it backs the `validation` gate capability
(`ValidationGate.evaluate`, same file, lines 72-155), which is declared by
ten NATIVE workflow manifests, confirmed via
`grep -l gates: backend/agents/workflows/*/workflow.yaml | xargs grep -l validation`:

`dotnet_to_azure`, `ex_publish_step`, `mulesoft_to_springboot`,
`pdf_to_prototype`, `prototype_revision`, `ex_validation_retry`,
`prototype_v2`, `prototype_large_revision`, `prototype_feature_revision`,
`playwright_smoke_test`.

Every one of these pipelines is structurally exposed to the same class of
defect as QA-PS-021: a step wired to `gates: [validation]` runs its declared
validators against whatever `_build_validation_target` hands back, with no
check that the upstream step it depends on actually produced real content.
Today this is unobserved because these native pipelines DO get
`write_files` where their manifest declares it (they are not blocked by
QA-PS-019/[ISS-698](20260922-1001-ISS-698.md), which is scoped to
`custom`/`custom_revision`), so the happy path never exercises the gap.

## Why the root cause implies this and not just custom workflows

The absence of an upstream-artifact-exists check is in the SHARED gate
module, not in anything custom-workflow-specific. Any of these ten
pipelines would hit the identical silent-compensation pattern if an
upstream step's artifact were legitimately missing for a reason other than
a permissions gap — a Bedrock throttle that recovers with partial/empty
output, a wrong deliverable path, a race in a fan-out step, a
crash-recovery fallback that resumes past a step that never really
completed. Nothing in `_build_validation_target` or `ValidationGate` would
catch it; the validators would simply run against a stale or missing
target, or (per `_build_validation_target`'s graceful-degradation branches,
lines 200-216) silently fall back to the raw `ctx` on any factory error.

## What would confirm or refute this

Not reproduced — this card is the hypothesis, not the observation. To
settle it: on one of the ten listed pipelines, force an upstream step's
write to fail without raising (e.g. monkeypatch the sandbox write for that
step in a test, or replay a run where a step's tool call silently produced
no file) and observe whether the downstream `gates: [validation]` step
produces a `GATE_PASS` or `GATE_BLOCK` outcome that does not reflect the
missing upstream content, and whether `_unrecovered_agents` records the run
as anything other than a clean completion.

## Fixer note (2026-09-22) — NOT fixed, escalated: the test asserts a contract
## that does not exist and a return value that breaks the only caller

5-fixer did not apply a change here. Three findings, all verified by direct read:

1. **`ctx.produced_artifacts` exists nowhere in production.**
   `grep -rn "produced_artifacts" --include="*.py" backend/` returns ONLY the two
   lines inside `tests/agents/test_qa_ps_021_downstream_no_upstream_artifacts.py`
   (:145 and :152). The test invents the attribute its own guard would key off.

2. **`ctx.current_step` is a step-id STRING in production, not an object with
   `.consumes`.** The only two capability-layer readers treat it as a string:
   `agents/capabilities/context_pack/pack.py:174` and
   `agents/capabilities/repo_inventory/inventory.py:250`, both
   `producer_step=getattr(ctx, "current_step", None) or "<default>"`. The test
   passes `current_step=SimpleNamespace(consumes=[...])`.

3. **Returning `None` breaks the single caller.** `_build_validation_target` has
   exactly one production call site — `agents/capabilities/gates/validation.py:92`,
   inside `ValidationGate.evaluate` — and its return value goes straight to
   `issues = await validator.validate(target)` at :102. The test asserts
   `target is None`, which would hand `None` to every declared validator of every
   `gates: [validation]` step in all ten pipelines this card lists.

The card's underlying observation (no per-step upstream-artifact pre-check) still
stands and is unrefuted — it is the card's OWN "What would confirm or refute
this" experiment that has not been run. What a missing upstream artifact should
make the gate DO (GATE_BLOCK? a new outcome? a different target?) is an API
contract decision, and `None` is not a viable answer.

Decision needed: `ESCALATIONS.md#qa-ps-021`, question 2.

## Decision applied (2026-09-23): won't fix, decision 1a

`ESCALATIONS.md#qa-ps-021` recorded decision 1 = (a) at 2026-09-23 01:34: "Nothing,
retire ISS-734". The run-level signals [FIX-612](20260922-1838-FIX-612.md),
[FIX-615](20260922-1854-FIX-615.md) and [FIX-634](20260922-2235-FIX-634.md) already

This card is moved to `WONTFIX.md#qa-ps-021` with that rationale, and its status is set
to `wontfix`. No code change.

**Test rewritten to the decision.** The app was not changed to fit the old test. Its
`target is None` would have handed `None` to `validator.validate(target)` at
`validation.py:100`. The new test is
`test_missing_declared_upstream_is_caught_at_run_level_not_by_the_validation_gate`:

- `_build_validation_target` keeps a real run-level target
- `dropped_section_reason` flags a deliverable over 2000 characters whose declared
  upstream produced nothing

It is `[XPASS(strict)]` with no code change; see [FIX-639](20260923-0148-FIX-639.md).

**Consequence accepted with the decision.** A validator can still pass a step whose
real input never arrived. The run is what gets flagged, not the gate.
