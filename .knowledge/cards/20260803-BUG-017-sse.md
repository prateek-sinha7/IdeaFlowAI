- **Found:** 2026-07-17 (user-reported, live) · after a prototype COMPLETED, asking "what is the status" in the left chat produced no visible answer.
- **Root cause (deep-investigation agent, LIVE-REPRODUCED — Concierge POST measured 11.15s; the re-fetch measured firing at +0.34s):** a delivery RACE — NOT a missing or truncated reply. Two layers. (a) The reply IS complete and IS persisted: durable `chat_reply` via `backend/app/api/run_commands.py:988` `store.append_event_next_seq(run_id, event_id="chat-reply:{message_id}", type="chat_reply", text=answer)` — measured 1690 chars incl. a full Status Summary (refutes the earlier "only the opener persisted" premise; the "I'll check the status…" the user saw is just the visible PREFIX of a complete answer). It is persisted **durable-only, with NO live-queue push**, so the FE's sole delivery path is the DEF-44-12-2 re-fetch-after-send in `frontend/src/hooks/useRunChat.ts:365-375` (`await sendCommand(...)` then `fetchEvents(runId, lastSeq)` folded via `handleFrame`, idempotent on `event_id`). (b) THE BUG — `frontend/src/app/dashboard/page.tsx:1027-1029` wires `useRunChat`'s `sendCommand` as `(runId, payload) => { void runConnection.sendCommand(runId, payload); }`: it **`void`s the async POST promise and returns `undefined`**, so `await sendCommand(...)` awaits `undefined` and resolves IMMEDIATELY; the re-fetch fires at +0.34s — long before the POST completes at 11.15s and the reply persists. No `chat_reply` exists yet → nothing folds in; no second re-fetch is ever triggered → the reply NEVER renders (it only surfaces if the run is later reopened, whose `seedTranscript` re-fetches all durable events, `page.tsx:1319`). Defeats DEF-44-12-2's explicit "await the up-channel THEN re-fetch" contract (that ticket flagged "live proof pending B3/B5" — this IS that failure). BUG-015's `detachRun` is ORTHOGONAL (it only ensures there is no live stream on a completed run, which makes the durable-only re-fetch the sole path → the race guaranteed-fatal there). Timeout theory ruled out (the provider `sendCommand` uses a raw `fetch`, no `AbortController`, so the api.ts 30s timeout is not in this path). SECONDARY (separate, real, backend): the answer is factually mis-grounded — `backend/app/agents/chat/concierge.py:356` calls `read_events(run_id, 0)`, dumping all ~12,480 events oldest-first, so the model can call a COMPLETED run "IN PROGRESS" (it never weights the terminal `pipeline_complete` at the tail); this also drives the ~11s latency.
- **Fix (PROPOSED — NOT applied, awaiting user go / discussion):** PRIMARY (the delivery bug, FE-only, ONE edit at `frontend/src/app/dashboard/page.tsx:1027-1029`) — make the adapter await/return the promise instead of voiding it: `sendCommand: async (runId, payload) => { await runConnection.sendCommand(runId, payload); }`. Then `await sendCommand()` in `useRunChat` waits for the POST (which resolves only after the reply is persisted) → the re-fetch fires AFTER the reply exists → it folds + renders as its own turn. Type-correct (`Promise<void>`); the synchronous optimistic user bubble + `return messageId` are unaffected; the launch→attach path (`runId` null) is a separate call site not routed through `useRunChat.sendMessage`, so it is untouched. SECONDARY (recommended, independent, BACKEND) — bound the Concierge `read_events` window (`concierge.py:356`, currently seq 0 = all events) to a recent/terminal-biased slice: cuts the ~11s latency AND fixes the "completed reported as in-progress" mis-grounding. OPTIONAL (hardening) — show a pending/spinner state on the ASK turn so a multi-second Concierge reply is not a silent gap.
