## What happened

`test_sc001_nonprototype_task_loop_runs_with_app_py` asserted the run's deliverable
is the built `app.py`; it got the streamed text
`'Building task 1. Building task 2. Done.'` instead.

## Root cause

Not the resolver. The logs say it plainly:

```
tool 'write_file' DENIED at execution — not granted by this step's permissions
Validation: task 1/2 wrote no app.py — skipping validation
single_file: app.py not written by agent — falling back to streamed output
```

`backend/tests/agents/fixtures/sc001_task_loop/workflow.yaml` declared no `tools`
block on the `sc001-build` step, so it sat at the least-privilege default and could
not write. `single_file` then did exactly the right thing:
`runner.sandbox.read(filename)` returned nothing, and it fell back to
`last_streamed` (`backend/agents/capabilities/deliverables/single_file.py:72-105`).

The fixture now grants what the step needs:

```yaml
    tools:
      read_files: true
      write_files: true
      exec: false
```

## This closes ISS-184's open question

[ISS-184](20260825-2115-ISS-184.md) recorded that the `single_file` deliverable
surviving an override was UNPROVEN — the prototype override run had been
deliberately shortened, so no `prototype.html` was ever written and the fallback
fired. The conclusion drawn there ("not yet proven") was correct at the time but
pointed suspicion at the resolver. This run isolates it: the resolver reads the
sandbox correctly and its fallback is deliberate; what determines whether
`single_file` yields the real artifact is whether the producing step was granted
`write_files`.

The identical omission appeared independently in the composed fan-out fixture the
same day — three workers completed and wrote nothing, for the same reason
([FIX-308](20260826-0124-FIX-308.md)). Two unrelated fixtures hitting it suggests
the failure mode is easy to author, not that either fixture was careless: the
symptom (a plausible-looking deliverable made of streamed prose) does not point at
permissions.
