# ISS-972

**INFERRED, not reproduced in the UI.** Derived while analysing QA-KB-053 ([ISS-665](20260917-1311-ISS-665.md)). Every link in the mechanism was read in
source and the data it acts on was read from the live API (`evidence/qa-kb-053/family-probe.out.txt`); nobody has yet
opened the screen, expanded the section and read the row. An unreproduced sibling is a lead, not a defect.

Line numbers are the working tree on 2026-10-02 (HEAD `024c03ef8`); `PreviewPanel.tsx`, `api.ts` and `run_files.py` carry uncommitted edits from other work, so their numbers can sit a few lines off HEAD. Real-data figures come from read-only GETs against the dev backend on :8000 (admin account), saved with their script in `evidence/qa-kb-053/`.

## Condition

Any revision member's Files tab with the "From v{n-1}" section expanded, **pinned or not**. The section renders only when
`parentRunId` is non-null (`FilesTab.tsx:929`), i.e. only on revisions, and it reads the parent's workspace file through the
same ref-blind resolver as the current row. No pin is involved, which makes this wider than the pinned-version framing of
[ISS-665](20260917-1311-ISS-665.md): on the newest member (the page a family opens on) the parent is by definition NOT what the live tree holds.

The parent's type must be one `deriveDeliverableFiles` yields a row for (`FilesTab.tsx:408-467`: user_stories, custom,
ppt/ppt_v2/ppt_revision, prototype and its revision types); otherwise `rows.length` is 0 and `:534-536` never resolves.

## Expected vs actual

Expected: the row is the PARENT's own file (name, size, Download bytes from the parent's snapshot), as the section's own
caption promises ("Files from the previous version this revision was based on.", `FilesTab.tsx:950`).

Actual: name and size come from the NEWEST member's file, and Download returns the newest bytes under the parent's label.

## Mechanism (read)

- `FilesTab.tsx:510-545` `handleToggleBase`: `getWorkflow(parentRunId)`, then `:522` derived rows from `parentRun.output` (the
  parent's own content, correct), then `:535` `resolveRunDeliverable(getToken() || "", parentRunId, parentRun.deliverableFilename)`
  with no ref, which is `api.ts:1621` `getRunSandbox(token, runId)`, the chain root's live tree (`run_files.py:939-940`, `:982`).
  `:537` `withWorkspaceFile(rows[0], parentRunId, hit)` then overwrites the parent's own row with the live file's name and size
  and sets `workspace: { runId: parentRunId, path }` (`:486`); Download reads that path with no ref (`:740`). The ISS-215
  reconciliation is what swaps the parent's own `output` for a live-tree read.
- PreviewPanel hands FilesTab the parent's id but not its tag: `:862` `activeParentRunId = sortedMembers.find((m) => m.id ===
  activeRunId)?.parent_run_id ?? null` and `:1922` `parentRunId={activeParentRunId} parentVersionNumber={activeIdx}`. The tag is
  right there: `FamilyMember.git_tag` (`types/index.ts:492`) sits on every `sortedMembers` row and is read at `:950` and `:1007`.

## Real data (live API, read-only)

Family `463e6c0b-32de-4781-a113-6630627bd395` (prototype_v2, v1-v4, every member declares `prototype.html`). Newest v4 =
`6014bc97-e4cf-4676-b0a0-21a4da98925f`; its parent v3 = `dc60f462-a4ca-45c1-9683-72f2ab523c6e` (`prototype_v2_feature_revision`).

- `GET /api/runs/dc60f462-…/sandbox`, which is what `:535` asks: `prototype.html`, 93,131 B, sha256 `787e532059c3`. That is v4's file.
- `GET /api/runs/dc60f462-…/sandbox?ref=v3`, v3's own: `prototype.html`, 91,733 B, sha256 `ce9458abac31`.
- `formatSize` (`FilesTab.tsx:1250`) therefore renders 90.9 KB where 89.6 KB is right, and Download differs byte for byte.

## Why the root cause implies it

Same cause as [ISS-665](20260917-1311-ISS-665.md) (the resolver has no ref and the family shares one sandbox) but a DIFFERENT ref: the parent's tag, not
`sandboxSelectedRef`. The parent is never the displayed member, so threading `selectedRef` into FilesTab repairs `:563` and
leaves `:535` on the live tree; passing the displayed member's ref to `:535` would be worse, labelling the child's file as its base.

## Fix direction and hazards

- PreviewPanel computes `parentRef = sortedMembers.find((m) => m.id === activeParentRunId)?.git_tag ?? null` beside `:862` and
  passes it; `:535` becomes `resolveRunDeliverable(token, parentRunId, parentRun.deliverableFilename, parentRef)`.
- A parent with no tag (`git_tag` null, see [ISS-697](20260922-1000-ISS-697.md); real data: members `4eb1a2ea-b4be-400a-b53c-b63597cc52a0` cancelled and
  `97b49f98-83bd-4ed6-8631-600bf9653905` failed in family `87e02c32-96a9-4e50-8ed0-79023d83540f`) has nothing to scope to: skip the
  reconciliation and keep the derived rows (the parent's own `output`); never fall back to the live tree.
- Hazard on the same surface, different mechanism (not carded separately): `baseFetched` (`FilesTab.tsx:508`), `baseFiles` and
  `baseOpen` are never reset when `parentRunId` changes, and `<motion.div key="files">` (`PreviewPanel.tsx:1911`) does not remount on
  a version switch, so with the section open a switch can leave the previous parent's rows under the new "From v{n-1}" label.
  Reset them on `[parentRunId, parentRef]`, or the ref-aware rows go stale across a switch. INFERRED: not exercised.

## What would confirm this

Open `/runs/6014bc97-e4cf-4676-b0a0-21a4da98925f`, Files tab, expand "From v3": expect the row at 90.9 KB; Download it and
sha256 the file: expect `787e532059c3` (v4's) where v3's own is `ce9458abac31`. Test seam: `FilesTab.baseVersion.test.tsx` mocks
only `getToken`/`getWorkflow`, so `resolveRunDeliverable` is undefined there and the call throws into the `catch` at `:538`; add it
to the mock and assert the 4th argument.

## Resolved (2026-10-02, QA-KB-053)

Fixed by [FIX-717](20261002-1243-FIX-717.md).
- PreviewPanel passes the parent's own tag as `parentGitTag`, read from `sortedMembers[].git_tag`.
- The "From v{n-1}" rows resolve only at that tag. Without a tag, the parent's derived rows stand and the live tree is never read.
- FilesTab is keyed on the displayed member, so a version switch no longer keeps the previous parent's base rows. That was the hazard noted above.

Observed run: `FilesTab.baseVersionRef.test.tsx` went from "1 expected fail" to "Error: Expect test to fail". The marker is left for the verifier.
