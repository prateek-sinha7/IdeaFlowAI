## Per-step model selection never reached ModelResolver

**Symptom:** a per-agent model selection made in the launch wizard (`prototype-build`
set to Sonnet via the AgentsPopup per-step model picker) ran on Haiku throughout —
every `build_model: ChatBedrockConverse model=eu.anthropic.claude-haiku-4-5...` for the
build agent and every internal fix-loop retry, on a real local run
(`01fd07cb-3faf-4ad7-9085-20452887c104`).

**Root cause:** confirmed via the live DB row for that run —
`workflow_runs.selections_json` correctly held
`{"prototype-build": {"model": "eu.anthropic.claude-sonnet-4-5-20250929-v1:0"}}`, so
save/launch/validation (`_synthesize_step`, `WorkflowCompiler.compile(trust="user")`,
`_apply_selections`) all worked and correctly produced a compiled `Step.model`. The
break was one level deeper: `ExecutionEngine._resolve_model(ectx, spec, model_id)`
(`engine.py:4156`, pre-fix) called `ModelResolver.resolve(spec, step)` with
`step` defaulting to `None` — the call site never passed it, confirmed by the code's
own comment: *"step=None this plan (06-04 wires the compiled Step lookup)"*. With
`step=None`, `ModelResolver.resolve()`'s tier 2 (`model_policy.py:79-128`,
`step.model`) can never win — resolution silently falls through past it to tier 5
(session default / Haiku), for every run, on every agent, regardless of what
`selections_json` records. This is the single `_resolve_model()` call site in the
codebase, so the gap is universal, not specific to `prototype-build`.

`ectx.current_step` was already the correctly-bound compiled Step at this exact point
in the dispatch loop — read four lines below for `injects`/`skills`/`prompt`/`tools`
(`engine.py:4178-4227`) — so the fix is threading the same value into the model call.

**Fix:** [FIX-263](20260819-1726-FIX-263.md) adds `step=ectx.current_step` to the `_resolve_model()` call at
`engine.py:4156`. Byte-identical for every run with no per-step model selection (tier 2
stays `None` either way — the parity the removed comment already asserted).
