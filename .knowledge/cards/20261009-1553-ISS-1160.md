# ISS-1160

## Description

INFERRED sibling of [ISS-1067](20261007-2030-ISS-1067.md) (bug QA-KB-125), found while analysing it. The QA-KB-125
validation drove `PrototypePreview` only ("PPTPreview ... not driven"). This is the deck viewer. It has the same
sandbox flaw, and one thing the prototype viewer does not: the generic renderer dispatches a filename into it, and that
renderer's own header calls its sandbox "a BLOCKING security mitigation".

## Why the root cause implies it

The root cause in ISS-1067 is that no single place owns the sandbox decision, so each viewer types its own token string
and two of them regained `allow-same-origin` after being fixed. PPTPreview is the second of the two. Commit
`5db19e6db` (2026-05-12) dropped `allow-same-origin` from it with the reason "the iframe could reach into parent
localStorage and read the JWT". Commit `d2970ff7f` (2026-05-27) put it back behind `isOdPpt` and deleted that comment.

## Evidence

CONFIRMED, read:

- `frontend/src/components/preview/PPTPreview.tsx:33` is `const isOdPpt = true;`. The iframe at `:248-261` is
  `srcDoc={htmlContent}` with `sandbox={isOdPpt ? "allow-scripts allow-same-origin" : "allow-scripts"}` at `:252`.
  With the constant fixed at `true`, the `"allow-scripts"` arm is dead code and the value is always the same-origin one.
- `frontend/src/components/preview/PreviewPanel.tsx:246-248`, inside the `text/html` branch of
  `GenericDeliverablePreview`: `if (deliverable.filename === "presentation.html") { return <PPTPreview content={content}
  isStreaming={false} pipelineType="ppt" onRevise={undefined} />; }`. The header of that function (`:178-183`) says the
  `text/html` iframe is `sandbox="allow-scripts"`, "NO allow-same-origin", "a BLOCKING security mitigation" and that it
  "reuses the PPTPreview non-od_ppt pattern" (T-18-05). That pattern is the dead arm above. A custom workflow whose
  deliverable is named `presentation.html` is rendered same-origin: the one filename on which the contract does not hold.
- Every mount reaches it: `PreviewPanel.tsx:1638` (live ppt run), `:247` (generic path, which also serves the
  version-pinned views through `mimetypeForPath`, `:339-345`), `WorkflowHistory.tsx:1073` (`isGenericPpt`) and `:1112`
  (ppt in History).
- Real Chrome 151, `evidence/qa-kb-125/analysis-1-origin-probe.txt`, variant C (srcdoc with `allow-scripts
  allow-same-origin`): the child's origin is the app's, `localStorage.auth_token` is readable, and `parent.document.title`
  is readable. Variant D (srcdoc, `allow-scripts` only) shows origin `null` and every one of those reads throwing.
- Tests: `PreviewPanel.genericDeliverable.test.tsx` asserts exactly `allow-scripts` for `custom.html`, `out.html` and
  `reopen.html`, never for `presentation.html`. There is no `PPTPreview` test file, and the first-party dispatch test
  mocks the component behind a `ppt-preview` test id, so nothing renders the real iframe.

INFERRED, not driven in the app UI: that the four mounts behave as the probe's variant C does. What would settle it: open
a completed ppt run in the real UI and read `iframe.getAttribute("sandbox")` and
`iframe.contentWindow.localStorage.getItem("auth_token")`, the check the validator ran for the prototype viewer.

## Expected vs actual

- Expected: every deck, live or reopened, first-party or generic, renders with exactly `sandbox="allow-scripts"`, the
  contract T-18-05 states and the tests assert for every other HTML deliverable.
- Actual: `allow-scripts allow-same-origin` on all four mounts.

## What dropping it costs

CONFIRMED by reading: `PPTPreview.tsx:222-247` scales the iframe by writing `iframe.style.*` from outside, which needs no
same-origin. The file has no `contentWindow`, `contentDocument`, `postMessage` or `onLoad` (grep). The deck templates
guard their storage: `html-ppt/assets/runtime.js:620-626`, `simple-deck/assets/template.html:306,341-342`,
`replit-deck/assets/template.html:444,477` and `tweaks/assets/wrap.html:326-336` are all try/catch. The unguarded
storage reader is the prototype template in [ISS-1066](20261007-2030-ISS-1066.md), not a deck.

What does change: a deck with `<a href="#...">` navigation. In a srcdoc iframe that already loads the parent URL into the
frame today, with or without `allow-same-origin`. See [ISS-1162](20261009-1553-ISS-1162.md).

## Fix direction

Do not fix this in isolation. Use the shared constant and helper that [ISS-1067](20261007-2030-ISS-1067.md) puts in
`frontend/src/lib/`. In this file that means deleting `isOdPpt` and the ternary at `:252`, and the `isOdPpt`-only
`style`/`className` branches at `:253-260` (the file treats the flag as always true). `pipelineType` is already marked
`@deprecated` (`:16-18`), so no caller needs an edit.

## Test notes

Offline vitest, one file at a time. Render the real `PPTPreview` with a `<!DOCTYPE html>` string and expect
`iframe.getAttribute("sandbox")` to be exactly `allow-scripts`. Add a `PreviewPanel.genericDeliverable` case with
`filename: "presentation.html"` and the same expectation: it renders the same-origin iframe today, so it is red before the
fix. Keep `PreviewPanel.genericDeliverable.test.tsx:88,111,211,267` and `WorkflowHistory.genericReopen.test.tsx:163` green.

## Resolution (QA-KB-125, 2026-10-09)

Resolved by [FIX-775](20261009-1625-FIX-775.md) through the shared helper of [ISS-1067](20261007-2030-ISS-1067.md). `PPTPreview.tsx` lost `isOdPpt` and its ternaries; the deck iframe is `srcDoc={frameableAgentHtml(htmlContent)}` with `sandbox={AGENT_HTML_SANDBOX}`, so `presentation.html` from the generic path is sandboxed too. The guard case "no frame gets allow-same-origin" named `PPTPreview.tsx` at pre-fix HEAD 01777a107 and passes after.
