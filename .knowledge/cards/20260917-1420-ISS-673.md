# ISS-673

## Title

QA-PS-002's real mechanism, replacing [ISS-644](20260917-0930-ISS-644.md): the notification panel's live "X of N agents" / percentage — and the header's own running-pipelines badge/dropdown, which nobody had connected to this bug yet — read a value that is only ever as fresh as the LAST unrelated re-render of `page.tsx`, because the per-run store deliberately never re-renders on a write to a run that isn't the one currently being viewed.

## What was found (re-analysis, following [ISS-658](20260917-1302-ISS-658.md)'s escalation)

[ISS-658](20260917-1302-ISS-658.md) already showed that [ISS-644](20260917-0930-ISS-644.md) blamed the wrong data path (`updateProgress` / `DashboardLayout.tsx:937-941`, which sets `notification.agentsCompleted` — a field the panel never reads for a live run, since `NotificationPanel.tsx:212-214` filters running/gate items out of `notifications` before the terminal list is drawn) and proposed, as "likely, not verified," that the real `0` comes from the `?? 0` fallback on `runAgentsCompletedMap` at `AppHeader.tsx:200`. I read every file in that chain directly and confirmed the mechanism, plus a second render surface neither [ISS-644](20260917-0930-ISS-644.md) nor [ISS-658](20260917-1302-ISS-658.md) mentions.

### Confirmed data path (every line read)

1. `NotificationPanel.tsx:212-214` — `notifications = notificationsProp.filter(n => n.status !== "running" && n.status !== "gate")`. Every LIVE row (running or gate) is drawn only from the separate `liveRuns` prop (`NotificationPanel.tsx:312-319`), never from `notifications`.
2. `AppHeader.tsx:474,482` — `<NotificationPanel ... liveRuns={runningPipelines} />`.
3. `AppHeader.tsx:194-221` builds `runningPipelines` from `recentRuns` (server data). Per entry:
   `agentsCompleted: isActive ? pipelineAgentsCompleted : storeCompleted` (`:215`), where
   `storeCompleted = runAgentsCompletedMap?.[r.id] ?? 0` (`:204`) and
   `isActive = activePipelineRunId != null && r.id === activePipelineRunId` (`:199`).
4. `DashboardLayout.tsx:2639-2642` supplies those props from ITS OWN `pipelineState` (the VIEWED run) and from `runAgentsCompletedMap`:
   `pipelineAgentsCompleted={pipelineState?.completedCount ?? 0}`, `activePipelineRunId={pipelineState?.pipelineRunId ?? null}`, `runAgentsCompletedMap={runAgentsCompletedMap}`.
5. `page.tsx:3890` — `pipelineState` passed down is `runStore.viewed.pipelineState`: the ONE run currently projected to React. `page.tsx:3897-3903` builds the map fresh on every render:
   ```ts
   const runAgentsCompletedMap: Record<string, number> = {};
   for (const run of recentRuns) {
     const entry = runStore.get(run.id);
     if (entry) runAgentsCompletedMap[run.id] = entry.pipelineState.completedCount;
   }
   ```
6. `useRunStateStore.ts` — `storeRef` is a plain `useRef<Map>` (`:274`, "no re-render on writes to background runs" per the file's own architecture comment at `:260-271`). Every per-run mutator gates the ONLY re-render trigger (`project()` → `setViewedState`) behind `runId === viewedRunIdRef.current`:
   - `handleFrame` (`:360-482`, the entry point for EVERY SSE frame including `agent_complete`) — project only `if (runId === viewedRunIdRef.current)` at `:476`.
   - `update` (`:484-491`) — same guard at `:488`.
   - `updatePipelineState` (`:493-502`) — same guard at `:499` (implied, same pattern as 488/476).
   - `updateWaveGroups` (`:513-522`) and `initRun` (`:533-542`) — same guard.
   So `entry.pipelineState.completedCount` for a background run DOES update correctly and promptly inside the ref (confirmed: `page.tsx:1406-1408` routes every non-foreign frame — background or viewed — to `handleFrame` unconditionally, BEFORE the active-run check), but nothing tells React to re-render because of it.
7. Net effect: `runAgentsCompletedMap` is recomputed correctly on every `page.tsx` render, but `page.tsx` only re-renders for reasons unrelated to a background run's own progress (the viewed run's frames via `project()`, or an explicit `getWorkflows().then(setRecentRuns)` refetch tied to a handful of specific SSE types — see below). Sitting on `/dashboard` or any screen where none of the concurrent runs is the viewed one, with no terminal/gate event firing, means `page.tsx` never re-renders, so the map — and everything it feeds — stays frozen at whatever it held the moment the user last navigated there. That is typically all-zero, because the navigation away from a freshly-launched run (to start the next one, or to `/dashboard`) usually happens before that run's first `agent_complete` frame. This matches the QA report exactly: three concurrent runs, none of them the single "active" one at the moment the bell is checked, all frozen at 0% simultaneously — not merely delayed, but genuinely never refreshed for as long as no unrelated re-render happens.

### A second render surface — not identified in any prior card

`runningPipelines` (`AppHeader.tsx:194-221`) is not private to the notification panel. It ALSO drives the header's own inline running-pipeline indicator, reading the identical `agentsCompleted`/`agentsTotal` fields:
- `AppHeader.tsx:341-345` — the single-pipeline badge: `{runningPipelines[0].agentsCompleted ?? 0}/{runningPipelines[0].agentsTotal}`.
- `AppHeader.tsx:391,433-436` — the "N Running" dropdown (KAN-132), one row per pipeline: `{pipeline.agentsCompleted ?? 0}/{pipeline.agentsTotal}`.

Both read the exact same array as `NotificationPanel`'s `liveRuns`, so both show the identical frozen count. See [ISS-674](20260917-1420-ISS-674.md), filed separately because it is an independently-visible location a tester could report (or fail to notice) without ever opening the bell panel.

## Why ISS-644's fix target cannot work

[ISS-644](20260917-0930-ISS-644.md)'s proposed mechanism — `pipelineState` freezing once `DashboardLayout` is not showing the run's own stream page — is real code, but it feeds `updateProgress` → `notification.agentsCompleted` (`useNotifications.ts:151-155`), a field read only at `NotificationPanel.tsx:134-143` and `AppHeader.tsx:338,427` (all downstream of `notifications`, not `liveRuns`). Point 1 above shows that field is structurally unreachable for any notification whose `status` is `"running"` or `"gate"` — exactly the two states a still-executing pipeline is ever in. A fix at `DashboardLayout.tsx:937-941` would make `notification.agentsCompleted` correct, and it would still never be drawn. `ISS-644`'s test (`frontend/src/components/layout/DashboardLayout.iss644.test.tsx`) asserts against that same unreachable field, so it can be made to pass without changing what the user sees — the exact trap [ISS-658](20260917-1302-ISS-658.md) already flagged.

## Blast radius

- `frontend/src/components/ui/NotificationPanel.tsx:130-144` (`NotifRow`) — the originally-reported bell-panel progress bar/percentage. Every live row, regardless of status (`running` or `gate`).
- `frontend/src/components/layout/AppHeader.tsx:341-345` — header single-pipeline badge "X/N".
- `frontend/src/components/layout/AppHeader.tsx:433-436` — header multi-pipeline "N Running" dropdown, per-row "X/N" (see [ISS-674](20260917-1420-ISS-674.md)).
- NOT affected (checked and ruled out): `RunChatLane.tsx`/`LaneRunHeader.tsx`/`PipelineGraph.tsx` read `pipelineState.completedCount` directly as a prop scoped to whichever run's screen is actually mounted — they are only ever shown for the viewed run, which `project()` always keeps fresh. `useWorkflow.ts`'s own `completedCount` is the reducer that feeds the viewed run's `pipelineState` and is unaffected. Analytics' `completedCount` is a separate, backend-aggregated KPI.
- A background run's review-gate STATUS is NOT part of this blast radius: `page.tsx:2045-2051` (`review_gate_ready`) and `:2071-2077` (`review_gate_approved`) both call `getWorkflows().then(setRecentRuns)` unconditionally (not gated on viewed/foreign), so `recentRuns[i].status` — and therefore `AppHeader.tsx:210`'s `"gate"` mapping — updates correctly for a backgrounded run. Only the AGENT COUNT for that same row stays frozen. This refines [ISS-649](20260917-1105-ISS-649.md) — see the note added there.
- A background run's FAILURE/CANCELLATION status also refreshes correctly via the same mechanism (`page.tsx:1663-1686` for `pipeline_failed`, `:1741-1753` for `pipeline_cancelled`, both unconditional on `!isForeignFrame`, which is false for any run this tab launched) — so the run correctly drops out of the LIVE section. But its CLIENT-SIDE `notifications` entry never transitions out of `status: "running"` in the background (confirmed by [ISS-648](20260917-1100-ISS-648.md): `markFailed`/`markCancelled` only fire for `currentPipelineNotifId.current`), so it also never qualifies for the TERMINAL section. Net effect: the row disappears from the panel entirely rather than "stays running forever" — a refinement, not a retraction, of [ISS-648](20260917-1100-ISS-648.md); see the note added there.

## Fix — where it belongs

The data in the store's ref is already correct (point 6 above) — this is a missing re-render subscription, not a missing computation. Patching `page.tsx`'s inline `runAgentsCompletedMap` construction, or any one of the three render sites in the blast radius, would leave the other two broken and would still only refresh opportunistically. All three consumers already funnel through one shared source: `frontend/src/hooks/useRunStateStore.ts`. That is where a fix belongs — for example, a second, cheap piece of React state (a version counter, or a shallow `Record<string, number>` of completed-counts) updated alongside the existing ref write in `handleFrame`/`update`/`updatePipelineState` for the NON-viewed-run branch, returned from the hook, and used by `page.tsx` as a dependency so `runAgentsCompletedMap` (and thus every downstream reader) refreshes promptly instead of only on an unrelated render. The hook's own doc comment (`:260-271`) shows the silent-ref behavior for background runs was a deliberate perf/flicker decision (`FIX-224`), so the fix needs to add a narrow signal for progress counts specifically, not simply remove the guard and re-project full `pipelineState` for every background frame (that would reopen the flicker problem `FIX-224` fixed).

## What would further confirm this

This re-analysis is code-read only (no browser session was used). A live check — two or three concurrent runs launched in one tab, navigate to `/dashboard` before any of them completes an agent, wait, then open both the bell panel and the header's own running-pipelines control — would confirm both render surfaces freeze at the same wrong number at the same time, and that switching to view one of them (making it `activePipelineRunId`) immediately corrects only that one row.

## Resolution (2026-09-17, [FIX-521](20260917-1447-FIX-521.md))

Fixed where this card placed it, in the shared producer. `useRunStateStore.handleFrame` now bumps
a one-line state tick when a non-viewed run's `completedCount` changes. That re-renders page.tsx,
so `runAgentsCompletedMap` and all three surfaces refresh. No other background frame re-renders
(FIX-224 holds; a scratch render count recorded in FIX-521 measured it).

This card had no test, so the 5-fixer wrote
`frontend/src/hooks/useRunStateStore.iss673.test.tsx` before changing code. On the unfixed store it
failed at the on-screen assertion, with the store at 2 and the screen at "0". After the fix it
XPASSes, and the `{ fails: true }` marker is left for the 6-verifier.

Still open and out of this fix's reach: runs launched in another tab are never streamed here, so
they still fall back to `?? 0`. See [ISS-675](20260917-1447-ISS-675.md).

## Analysis missed (2026-09-17, reopen, 5-fixer)

[FIX-521](20260917-1447-FIX-521.md) made the change where this card said to, but the live panel
still reads "0 of 6 agents" (6-verifier, run `8ff57cca-3064-4a4a-8031-6576c785aee1`, after both a
client-side navigation to `/dashboard` and a cold reload; screenshots
`bug-hunter/evidence/notification-panel/_scratch/verify-qaps002-panel-0of6-after-fix.png` vs
`verify-qaps002-realprogress-after-fix.png`, 0/6 vs 5/6 at the same moment). This
card's premise fails on QA's own path. It says "the data in the store's ref is already correct —
this is a missing re-render subscription, not a missing computation" (point 6, "Fix — where it
belongs"). After the user navigates away, though, the store's count is 0 and never changes. A
re-render cannot show a count the store never computed.

- **The store is lost on navigation.** `useRunStateStore()` lives inside
  `app/[...view]/page.tsx`. Any `router.push` within the catch-all remounts that page, which
  loads it with a new, empty store (`page.tsx:3269-3273`, "confirmed live";
  `DashboardLayout.tsx:517-520`). That includes Home, which is `router.push(routes.home())` =
  `/dashboard` (`DashboardLayout.tsx:1739-1741`, `lib/routes.ts:57`).
- **The new store never gets the agent list.** The run's `pipeline_start` frame reached the
  previous store instance.
  - `RunConnectionProvider` sits above the router and keeps the stream open. It holds back only
    the frames that arrive during the sub-second gap when nothing is subscribed
    (`RunConnectionProvider.tsx:75-89, 351-393`).
  - A cold reload resumes from the saved `run_cursor:<id>`, sent as `Last-Event-ID`
    (`RunConnectionProvider.tsx:156, 214`; `useRunStream.ts:188-190, 342`). So `pipeline_start`
    is not replayed after a reload either.
- **Without the agent list, every `agent_complete` is dropped.**
  - `launchedRunIdsRef` is restored from sessionStorage (`page.tsx:638-651`), so later frames
    still reach `runStore.handleFrame` (`page.tsx:1411`).
  - `handleFrame` creates an entry with an empty `agents` list.
  - For an agent id it does not know, the `agent_complete` reducer returns `prev` unchanged
    (`useWorkflow.ts:694, 706`). `completedCount` stays 0.
  - FIX-521's tick fires only when `completedCount` changes (`useRunStateStore.ts:471, 488-489`),
    so it never fires.
  - `runAgentsCompletedMap[id]` is therefore 0 (`page.tsx:3912-3918`).
- **page.tsx already recovers from this loss, but only for the run in the URL.** T11
  (`page.tsx:3398-3420`) replays `getRunEvents` for that run and gives the reason in its comment:
  "useWorkflow's agent_start case is a no-op for any agent id not already in state … confirmed
  live". Nothing replays a live background run while the user is on `/dashboard`.
- **Why `useRunStateStore.iss673.test.tsx` still passes.** It sends `pipeline_start` and
  `agent_complete` to the same store instance, so it never simulates a remount.

Evidence (observed 2026-09-17 by the 5-fixer):

- Scratch vitest (run, then deleted):
  - Store A received `pipeline_start` (6 agents) and was then unmounted.
  - A new store B received `agent_start`/`agent_complete` for a1–a3.
  - Store B ended with `completedCount=0` and `agents=0`, and never re-rendered (its screen still
    showed the first render, "0|-1").
  - Control: the same frames sent to one store instance rendered "3|6".
  - Result: 2 passed.
- Current test results, one file at a time with `npx vitest run`:
  - iss644: "1 expected fail"
  - iss648: "1 passed"
  - iss649: "1 passed"
  - iss658: "1 expected fail"
  - iss673: "1 failed, Expect test to fail" (an unexpected pass)

For re-analysis (not decided here):

- **Rehydrate on mount.** For each live run in `launchedRunIdsRef` that the URL does not name,
  replay `getRunEvents` through `runStore.handleFrame` only, not the full page router, which has
  page-level side effects. Cost: one event-log fetch per live run on every route change.
- **Lift the store into a provider above the router.** The count would survive client navigation.
  A reload would still need the rehydrate option.
- **Add a completed-agent count to `GET /api/runs`.** This covers reloads and
  [ISS-675](20260917-1447-ISS-675.md). It changes an API contract (option b in
  [ESCALATIONS.md#qa-ps-002](../../ESCALATIONS.md#qa-ps-002)).
- **Whichever option is chosen**, its test must simulate a remount: a new store instance that
  never received `pipeline_start`. Otherwise the test will pass again while the live panel stays
  broken.

FIX-521's tick is still in the tree and does no harm. It updates a background run whose
`pipeline_start` reached the current page instance.

## Superseded (2026-09-17, 3-analyzer)

[ISS-679](20260917-1522-ISS-679.md) re-analyzed this card's own "For re-analysis" list above and
confirmed the mechanism: `useRunStateStore()` is called inside `page.tsx` (`page.tsx:2170`), so a
`router.push`/reload remount under `[...view]` destroys its `storeRef` entirely — this card's "the
data in the store's ref is already correct" is false once that happens, since `pipeline_start` (the
only thing that seeds `pipelineState.agents`) never reaches the new instance. FIX-521 remains a
correct, working fix for the sub-case this card actually diagnosed (a background run progressing
within one page.tsx mount); it just cannot reach the case that matters for QA's own repro. See
ISS-679 for the confirmed evidence and the recommended fix location.
