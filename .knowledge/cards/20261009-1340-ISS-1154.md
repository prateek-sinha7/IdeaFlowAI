### Root cause (one mechanism)

"Edit brief & run again" hands the brief to the composer through a channel that does not survive the navigation it triggers, for every destination except the four wizards.

1. `handleEditBrief` fetches the run and calls `openComposerWith(run?.input || submittedBrief || "")` (`DashboardLayout.tsx:2439-2441`). `getWorkflow` returns the full run with `input` (`api.ts:1132`, `:1344-1350`); the list endpoint omits it by design (`runs.py:750-756`), which is why this fetch exists ([FIX-582](20260922-0915-FIX-582.md)). So the brief is in hand and correct.
2. `openComposerWith` (`:2405-2429`) writes it to two places. `setPendingHomeBrief(editedBrief || undefined)` (`:2406`) is component state, declared `useState<string | undefined>(undefined)` with no initializer and no storage read (`:1594`). The `sessionStorage.setItem(draftKey, ...)` (`:2424-2426`) runs only if `draftKey` resolves, and the table has four entries: `prototype`, `prototype_v2`, `ppt`, `ppt_v2` (`:2422-2423`).
3. Then `setMainView("input"); router.push(createRouteForType(effectiveReviseType))` (`:2427-2428`): a route such as `/create/ex_A1_loop` that carries nothing about the brief (`:412-427`, `routes.ts:284-309`).
4. That push replaces the `DashboardLayout` instance. Next renders each route segment's subtree under `key={stateKey}` (`layout-router.js:673`), where `stateKey = createRouterCacheKey(segment)` and a dynamic segment's key includes its value, `view|<value>|c` (`create-router-cache-key.js:15-16`, `layout-router.js:549`). `runs/<id>` to `create/<type>` is a different key, so a new tree mounts. `next.config.ts` sets no `cacheComponents`, so the bfcache `<Activity>` branch (`layout-router.js:683-688`) is not taken. The repo records the same thing in `page.tsx:3547-3551` ("confirmed live: a fresh render-instance id appears right after router.push") and `DashboardLayout.tsx:551-557` (a push "REMOUNTS page.tsx ... wiping every page-local run state"), and the BUG-023 test takes it as its premise: "the remounted page can only recover the type from that URL" (`initialWorkflowType.bug023.source.test.ts:38-39`).
5. The new instance is built from the URL alone: `initialMainView` and `initialWorkflowType` come from `initialMainViewFor` / `initialWorkflowTypeFor` (`page.tsx:133-157`, `:386-397`, passed at `:4296-4305`). That is why the TYPE survives the push and the BRIEF does not: the type is in the URL, the brief is not. The new instance's `pendingHomeBrief` is `undefined`.
6. `IdeaInputPage` mounts with `initialInput={savedComposition?.brief ?? pendingHomeBrief}` (`DashboardLayout.tsx:3207`), which is `undefined`, and seeds `ideaInput` and `briefBaseline` once, at mount (`IdeaInputPage.tsx:970`, `:1031`). Empty textarea.

The four wizard types escape because `page.tsx` returns `<LaunchWizard>` above `DashboardLayout` (`page.tsx:4172-4177`), and the wizard restores `<mode>.draft` from sessionStorage on mount (`LaunchWizard.tsx:449-451`) and clears it once consumed (`:490-492`).

**Corroboration from the validator's screenshots.** `handleEditBrief` never calls `setWorkflowType` (none in `:2399-2442`), and the only effect that does is gated on `pipelineState?.isRunning` (`:842-856`), which is false for a failed run. An instance that survived the push would therefore show the `user_stories` default panel; probe `[A]` prints `workflowType=user_stories`. The screenshots show "Retry until it passes" (`ex_A1_loop`) and "Write backlog from prototype and documents" (`backlog`). The type was re-seeded from the URL by a new instance.

### Why the earlier fixes did not catch it

- [ISS-235](20260828-1830-ISS-235.md) argued "DashboardLayout is mounted once for the life of the SPA session ... route pushes do not remount it", from the absence of a `key` prop on the JSX call site. The key that matters is Next's segment key, which that card did not look at.
- [FIX-331](20260828-2056-FIX-331.md) (`d027f16bd`, 2026-08-29) verified live only on the two `ppt_v2` runs the e2e file named, where the destination is the wizard and `pendingHomeBrief` is irrelevant. It states the `pendingHomeBrief` half as true for "every other type" without clicking one. [FIX-582](20260922-0915-FIX-582.md) (`7f9be3d60`, 2026-09-22) fixed the fetch and the `prototype_v2` slot, with the same blind spot.
- The e2e file hard-coded two `ppt_v2` runs until `14ce62c59` (2026-09-22) made it discover the newest failed run with a brief at runtime. On this dataset that is an `ex_A1_loop` run (`analysis-03`). So the first non-wizard run the test ever clicked is the one that fails. This is not a regression of the code: the non-wizard hand-off never reached a composer in the real app. What changed is the mix of runs under test.
- [ISS-916](20261001-2220-ISS-916.md) saw it coming. Its step 3: `pendingHomeBrief` "is DashboardLayout state ... so the same remount would drop it for every non-wizard type. That would be a different root cause (state set before `router.push`) and needs its own card". This is that card.
- No unit test can see it. The DashboardLayout tests mock `useRouter()` as `{ push: vi.fn() }`, which cannot remount anything; the lane tests only check that the button calls `onEditBrief`.

### Blast radius

- Writer: `handleEditBrief` is the only code that hands a failed run's brief to a composer. Provider `DashboardLayout.tsx:3369`; the only consumer is `RunChatLane.tsx:1941-1942`, in the failed branch (`:1804`). The cancelled and degraded branches call `onRelaunch` (a resume), not this.
- Readers of the non-wizard channel: one, `DashboardLayout.tsx:3207`, then `IdeaInputPage.tsx:970` / `:1031`. `IdeaInputPage` has a single mount site (`DashboardLayout.tsx:3198`).
- Dev data (`analysis-03`): 16 failed runs. 11 are non-wizard and hit this (`ex_A1_loop` 5, `backlog` 2, `ex_A2_branch` 2, `ex_A4_human_gate` 1, `user_stories_v2` 1), 3 are `prototype_v2` and work, 2 are `prototype_revision` ([ISS-1171](20261009-1624-ISS-1171.md)).
- Same flaw in other callers, read and not filed. `handleHomeSelectFeature` (`:1652-1655`) sets `pendingHomeBrief` and then pushes, but `homeBrief` is always empty since FIX-181 removed the Home textarea (`HomeLaunchGrid.tsx:241-242`): unreachable. `handleLaunchSaved` is compensated: `page.tsx` re-fetches the saved row on mount and rebuilds the composition with its brief (`page.tsx:4057-4073`) and writes the wizard draft itself (`:4044`). The chain flows use sessionStorage for wizard targets and launch non-wizard targets directly, with no composer in between (`DashboardLayout.tsx:1948-1976`, `:2024-2039`).

### Where the fix belongs

One function and one initializer, not the callers.

- Write side: `handleEditBrief.openComposerWith` (`:2405-2429`). It is the only place that knows the brief and the destination, and it already owns the slot table.
- Read side: where the destination's first render gets its brief, which is the initial value of `pendingHomeBrief` (`:1594`), because `IdeaInputPage` takes it once at mount.
- Not in `RunChatLane` (a one-line click), not in `IdeaInputPage` (it cannot know where a brief came from), not in `page.tsx` (nothing to re-derive unless the URL carries the run id).

Candidate shape, probed with no source edited (`analysis-02`): (1) in `openComposerWith`, give the slot table a default for destinations with no wizard (`}[reviseBase] ?? "idea.draft"`); (2) initialize `pendingHomeBrief` from that key with a read-only initializer, and remove the key in a mount effect. Result in the probe: all five non-wizard types and the three revision types without a base key get their brief; the key is gone after the first mount and a later fresh visit is empty (`[G]`); it holds under StrictMode (`[H]`); the wizard rows are unchanged. It leaves the three wizard-base revision types empty, which is [ISS-1171](20261009-1624-ISS-1171.md).

Alternative, closer to [ADR-0014](20260824-1630-ADR-0014.md): name the source run in the URL (a `routes.ts` builder and its `parseViewPath` arm) and let the destination fetch `GET /api/runs/{id}` on mount, as `/workflows/{id}/run` already does. It survives a refresh and a shared link and cannot go stale. The cost is a `routes.ts` change (ADR-0018: no path literal outside it), `routes.test.ts`, and a render gate, because `IdeaInputPage` seeds once. Both satisfy the expected behaviour, so the choice is the fixer's, not an escalation.

### Traps for the fixer

- Setting the brief after the push, in an effect or a `.then`, lands on the instance that is already gone, and `IdeaInputPage` would ignore a late `initialInput` anyway.
- Initializers must be pure: StrictMode, the dev default, calls them twice. Read in the initializer, clear in an effect (probe `[H]`).
- One-shot, or it comes back. [ADR-0014](20260824-1630-ADR-0014.md) records a sessionStorage hand-off that re-applied itself on Back and survived a refresh. Consume it when the composer shows it, and never leave it for a surface that does not read it ([ISS-1171](20261009-1624-ISS-1171.md)).
- Derive the slot and the route from one destination decision ([FIX-582](20260922-0915-FIX-582.md)'s locked constraint).
- No workflow-name `if` in `DashboardLayout`: key it on "has a wizard slot", which is data (SC-001 in spirit; the file's own comments keep it that way).
- Keep the wizard path as it is. A staged draft already outranks ambient `chain.*` state (`LaunchWizard.tsx:408-415`, ISS-347 / ISS-1000).

## Resolution ([FIX-777](20261009-1651-FIX-777.md), 2026-10-09)

The "Where the fix belongs" shape, in `DashboardLayout.tsx` only. `openComposerWith` now stages every brief in sessionStorage: the
wizard slot for the four wizard types, `"idea.draft"` for every other destination (`:2432-2434`). `pendingHomeBrief`'s `useState`
reads `"idea.draft"` in a pure initializer and a mount effect removes it (`:1594-1602`), so the REMOUNTED instance on `/create/<type>`
hands the brief to `IdeaInputPage` at its first render, once. The card's test reports 7 XPASS + 2 green controls
(`evidence/qa-kb-110/fix-01-iss1154-test-xpass-after-fix.txt`). The e2e file is the 6-verifier's (browser). The four items under
"Observed while reading, not filed" are untouched by this fix.
