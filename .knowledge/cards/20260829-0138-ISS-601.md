## Source

Sibling of [ISS-370](20260828-2136-ISS-370.md), derived while analyzing
`BUG-20260828-103900-handoff-settings-r2` in `bug-hunter/ledger.md`.

## What is suspected

[ISS-370](20260828-2136-ISS-370.md) root-caused the API-key name bug to a two-part gap: the
frontend's untrimmed `||` fallback, AND the backend's `ApiKeyCreateRequest.name: str =
Field(default="Default", min_length=1, max_length=64)` (`backend/app/api/settings.py:77`), whose
`min_length` counts raw characters without stripping whitespace, so a whitespace-only string
satisfies it. `create_api_key` (`settings.py:229-255`) never calls `.strip()` on `payload.name`.

Grepping every other backend Pydantic model that accepts a user-supplied entity name with the
same `min_length=1`-only shape found a second instance with the identical gap:
`SaveUserWorkflowRequest.name: str = Field(min_length=1, max_length=120)`
(`backend/app/api/user_workflows.py:206`). Reading the whole file confirms no `.strip()` call
exists anywhere in it — `body.name` is used verbatim in the uniqueness check, the `WorkflowDefinition`
constructor (`name=body.name`, `create_user_workflow`, around line 682), and the PATCH handler
(`row.name = body.name`, `update_user_workflow`, around line 794). A whitespace-only name would
persist and render the same way the API-key bug does: a saved-workflow row with no visible name.

This is NOT a hypothetical anti-pattern reachable from imagination — it is the mechanically
identical schema shape (`Field(min_length=1, ...)`, no whitespace awareness) at a second call
site in the same API module family. Contrast the THIRD such field,
`UserAgentBody.name` (`backend/app/api/user_agents.py:66`): `create_user_agent` and
`update_user_agent` both already do `name = body.name.strip()` then `if not name: raise
HTTPException(422, "name must not be blank")` (`user_agents.py:179-184`, `:235-240`) — confirmed
NOT vulnerable, and it demonstrates the correct backend-side defense this codebase already knows
how to write elsewhere. `user_workflows.py` is the one file of the three missing it.

## Condition

No live in-app UI path reaches this today — every known frontend caller of
`POST /api/user-workflows` and `PATCH /api/user-workflows/{id}` already trims client-side before
sending:

- `ComposerPage.tsx:1109,1119` — the inline "Workflow name" header field: `if (!name.trim()) {
  setSaveError(...); return; }` then `handleSave(name.trim(), description.trim())`.
- The shared `NameWorkflowModal.tsx:39,107-108` (`canSave = name.trim().length > 0`, Save button
  `disabled={!canSave}`, `onSave(name.trim(), description.trim())`) — used for BOTH
  `SavedWorkflowsPage.tsx`'s "Rename workflow" action (via `renameUserWorkflow`) and
  `AgentsPopup.tsx:2434`'s "Save to catalogue" action (via `saveUserWorkflow`).

Confirmed via `grep -rn "saveUserWorkflow(\|renameUserWorkflow("` across `frontend/src`: exactly
these three call sites exist, and all three route through one of the two trim guards above. The
condition that WOULD reach the gap is a direct API call bypassing the browser UI entirely (curl,
a script, or any REST client holding a valid session credential) sending
`{"name": "   ", "base_pipeline_type": "custom", "agent_ids": [...]}` to
`POST /api/user-workflows`.

## Expected vs actual

**Expected:** the backend rejects or trims a whitespace-only `name` itself, the same way
`user_agents.py`'s create/update handlers already do — matching this codebase's own established
pattern for user-supplied entity names ("bounded input" is called out explicitly in
`user_agents.py`'s module docstring as a defended property).

**Actual (predicted, not yet reproduced):** `payload.name` is stored verbatim
(`user_workflows.py`, no `.strip()` anywhere in the file), so a direct API call with a
whitespace-only name would persist a saved workflow with no visible, human-readable name in "My
Workflows" — the same permanently-unidentifiable-row symptom [ISS-370](20260828-2136-ISS-370.md)
documents for API keys. Unlike API keys, a saved workflow DOES have a rename path
(`PATCH /api/user-workflows/{id}` via the "Rename workflow" menu action), so if this were ever
reproduced, it would at least be recoverable from the UI — a narrower consequence than ISS-370's
"permanent, unfixable" API-key case.

## Why the root cause implies this

ISS-370's mechanism is general, not API-key-specific: "a `Field(min_length=1, ...)` Pydantic
constraint counts raw string length, not trimmed content, so it does not by itself reject a
whitespace-only value; without an explicit `.strip()` in the handler, nothing else in the request
path does either." That mechanism is a property of the SCHEMA PATTERN, and
`SaveUserWorkflowRequest.name` uses the identical pattern. The only reason it does not manifest
as a live symptom today is that both known frontend callers happen to already guard it
client-side — a coincidence of current UI code, not a backend guarantee. `user_agents.py` shows
this codebase's intended fix (strip + reject-blank in the handler) is a known, already-applied
pattern one file over; `user_workflows.py` is the outlier that never received it.

**Marked INFERRED**: not reproduced this session — no browser or direct-API action was taken
against `POST /api/user-workflows` with a whitespace-only name. What would confirm it: call
`POST /api/user-workflows` directly (bypassing the UI) with
`{"name": "   ", "base_pipeline_type": "custom", "agent_ids": ["<valid-id>"]}` using a valid
session token, and check whether the created row's `name` is the literal whitespace string in
`GET /api/user-workflows`. What would refute it: a validator or dependency this reading missed
that also strips/rejects `name` somewhere in the FastAPI request pipeline before
`create_user_workflow` runs (e.g. a shared Pydantic base model with a `field_validator` this file
inherits from — not seen while reading `user_workflows.py`, but not exhaustively ruled out across
the whole `app/api` package).
