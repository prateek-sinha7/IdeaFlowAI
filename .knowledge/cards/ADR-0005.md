# ADR-0005: Supported workflow types are discovered from disk

## Context and Problem Statement

`SUPPORTED_PIPELINE_TYPES` was a hand-typed `frozenset` literal of 17 entries at the top
of `loader.py`. Adding a pipeline meant remembering to edit it; a forgotten edit silently
broke `list_agent_ids` and registry discovery for the new type, and `_build_spec` raised
`AgentSpecError` for any `pipeline_type` outside it.

It was introduced in `9374ac28` as a **schema/typo guard** — validating authored input.
No ADR, `.knowledge/` card or invariant frames it as a security control, and `git log -S`
shows only two commits ever touched it.

`.knowledge/INVARIANTS.md:22` says the opposite of what the frozenset does:

> **SC-001** | Launchability is keyed on the declared flag, never a hardcoded name list —
> a saved workflow is pure data, no new pipeline name

A second hardcoded list had grown beside it: the loader also carried a hand-maintained
set of template agent ids so `custom-agent` would be excluded from every roster.

## Considered Options

1. **Keep the literal**, accept the manual edit as the cost of an explicit allow-list.
2. **Derive from `agents/workflows/` only** — one source, simplest rule.
3. **Derive from three sources** — manifests, declared `pipeline_type` values, and an
   explicit alias set — and replace the template name list with a per-agent flag.

## Decision Outcome

**Option 3.** Computed once at import (`loader.py`, module footer):

```python
_ID_ALIAS_TYPES = frozenset({"od_prototype", "od_prototype_revision"})

def _discover_supported_pipeline_types() -> frozenset[str]:
    types = set()
    #  (a) authored workflow manifests
    #  (b) pipeline_type declared by any loadable AGENT.md
    #  (c) pure run-label aliases
    ...
```

Option 2 was tried and **regressed**: deriving keys from declared `pipeline_type` values
alone drops agentless workflows, turning `PIPELINE_AGENTS["reverse_engineer"]` from `[]`
into a `KeyError`. Both source (a) and source (b) are load-bearing —
(a) keeps manifest-backed workflows with no agents, (b) keeps `spec_kit`, whose agents
include `deep-planner`, the planner every pipeline runs.

Source (c) exists because `od_prototype` resolves to `prototype` before any manifest or
agent lookup, so it has no directory and no `AGENT.md` and is genuinely not derivable.

`AgentSpec.template: bool` replaces the template name list. Parsing is **strict** — a
non-bool raises rather than coercing, because a folder silently failing to mark itself a
template rejoins the roster and breaks its pipeline's membership. `list_agent_ids` filters
on the flag *after* loading, since the flag lives in the parsed spec, not the directory
name.

The `pipeline_type` allow-list check in `_build_spec` is removed: the set is now derived
partly from those same declarations, so validating against it would be circular.

## Consequences

**Positive.** Adding a workflow is adding a folder. SC-001 is satisfied rather than
contradicted. `TEMPLATE_AGENT_IDS_BY_FLAG` is precomputed at import, taking
`get_all_agents_flat` from 0.8ms to 0.018ms per warm call.

**Negative — the typo guard is gone.** A misspelled `pipeline_type` no longer raises. It
creates its own one-agent phantom type, silently removing the agent from its intended
pipeline's membership while producing an unlaunchable key with no manifest. The module
comment names a startup consistency check as the intended replacement; **it is not
implemented.**

**Negative — four fixture manifests become visible.** The set went 17 → 21, gaining
`sample_brownfield`, `sample_fanout`, `sample_subagents`, `sample_wave`.
`app/api/workflows.py::_discover_manifest_ids` filters on this set, so
`GET /api/workflows` now returns them, and two tests fail:
`test_workflows_api.py::test_sample_fixtures_are_not_exposed` and
`::test_list_carries_launchable_flags`.

Three of the four reference agents with no `AGENT.md` and are structurally unrunnable.

**Not a security regression.** Launch is gated independently by
`entitlements.py::TIER_PIPELINES` (`run_commands.py:1638`, `user_workflows.py:443`), an
unmodified allow-list with no entry for the three broken fixtures in any tier. Widening
the type set grants no access. The regression is catalog *visibility* only.

**The tests encode an accident, not a decision.** Those three were never *decided* to be
hidden — they were omitted from a hand-typed list, and a later test comment rationalized
the omission. `FANOUT-USER-FACING-SCOPE.md:30` records the original intent (*"carry NO
`user_launchable` key → default `False`"*), which is no longer true: all three declare
`user_launchable: true` at HEAD. And the failing test's own opening paragraph states the
SC-001 rule it then violates:

> *"launchability is a DECLARED manifest flag surfaced per row, never a hardcoded name
> list ... nothing is hidden from the catalog; incomplete pipelines are marked
> is_beta=true instead."*

**Import-time cost.** Discovery parses ~85 `AGENT.md` files on any `import agents.loader`
— bounded (tens of ms) but unconditional. If `_WORKFLOWS_DIR` is missing, source (a) is
silently skipped with no warning, unlike the per-agent logging in `iter_agent_specs`.
Paths are `__file__`-relative so CWD-independent, and the Dockerfile copies the whole
tree, so no deployment path resolves it empty.

## Confirmation

**Required follow-up, not yet done:**

- Fix the ISS-015 break the SC-001 way: set `user_launchable: false` on
  `sample_brownfield`, `sample_fanout`, `sample_wave` (pure data), and change the two
  assertions from "must be absent" to "must be `user_launchable: false`". Do **not**
  reintroduce a skip-list — that is the thing SC-001 forbids.
- Implement the startup consistency check the removed guard was traded for.
- `backend/CLAUDE.md`'s "Adding a Pipeline" Step 1 still instructs contributors to edit
  the frozenset literal that no longer exists.
- A dozen tests loop `for pt in sorted(SUPPORTED_PIPELINE_TYPES)`; any future directory
  under `agents/workflows/` silently joins all of them. Scope those loops to exclude
  fixture types.
- Cosmetic: `AgentSpec.template` versus the manifest's `is_beta`/`user_launchable`
  naming — either rename to `is_template` or document the divergence.
