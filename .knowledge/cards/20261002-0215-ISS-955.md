# ISS-955

## What happened

[ISS-938](20261001-2233-ISS-938.md) predicted this trade-off by reading the code. It was observed while
[FIX-711](20261002-0215-FIX-711.md) was being written. FIX-711 makes every URL pin change bump `selectGen`. When a menu
pick's URL write round-trips, the URL-pin effect therefore supersedes the handler and becomes the only applier for that
pick. On success nothing changes. On failure the handler's guarded `setViewingVersion(null)` is skipped, and the effect's
catch only logs (`PreviewPanel.tsx:1028-1032`):

```ts
} catch (err) {
  // Same contract as handleSelectVersion: best-effort, never throw into
  // the preview surface — an unresolvable pin leaves the live view up.
  console.warn("[revision-family] pinned version fetch failed", err);
}
```

That comment says live. The code leaves whatever view was already up, and that is live only when nothing was pinned
before.

## Observed (scratch probe, 2026-10-02, vitest 4.1.11, jsdom)

Setup: the harness of `PreviewPanel.staleVersionPick.test.tsx`, a 3-member family, `pinnedVersion` re-rendered to
simulate the URL. Steps: pick v1 and resolve it, round-trip the URL to `1`, pick v2, round-trip the URL to `2`, then
reject `getWorkflow(m2)`. Both runs used the same test body; no repo file was edited.

| implementation | read-only banner | chip | what is on screen |
|---|---|---|---|
| before FIX-711 (pre-edit copy) | none | `Viewing v2▾` | live (latest) content |
| after FIX-711 | `Viewing v1 (read-only)` | `Viewing v2▾` | v1 content |

Picking from live (nothing pinned) ends the same way in both: `viewingVersion` stays `null`.

## Expected vs actual

- **Expected:** a version that fails to load is never shown under a label that names it as loaded.
- **Actual:** the chip and the URL name the failed version. Before FIX-711 the content was live; now it is the version
  that was up before the pick. The read-only banner names what is actually shown.

## Decision needed (UX)

What should a failed version fetch show?

- (a) The effect's catch clears to live when not cancelled (`if (!cancelled) setViewingVersion(null)`). This is
  one line and restores the pre-FIX-711 result, but the chip still names the failed version.
- (b) An explicit error state ("Couldn't load v2", with a retry) and the chip still on v2.
- (c) Revert the chip and the URL to the version still on screen.

Severity is low: it needs `GET /api/runs/<member>` to fail for a family member that the family listing just returned.
