## What happened

Found by the QA-KB-012 / QA-KB-013 fixer while adding the [ISS-911](20261001-2220-ISS-911.md) arity checks in
[FIX-696](20261001-2235-FIX-696.md). ISS-911 covers segments AFTER a valid verb. These paths are the runs branch's
`/versions/{v}` lift, which no card covered, so FIX-696 left them unchanged. INFERRED as a live defect: the parser
output below was executed, but no render was reproduced in a browser.

## Root cause (CONFIRMED by source read and by running the parser)

`frontend/src/lib/routes.ts`, the ISS-230 versions lift in the `runs` branch (anchor on the text; `:374-380`
after FIX-696):

```ts
if (segments[2] === 'versions') {
  version = segments[3];
  if (segments.length <= 4) {
    return { screen: 'run-version', runId, version };
  }
```

`segments.length <= 4` also admits length 3, where `segments[3]` is undefined. `ParsedView` declares
`{ screen: 'run-version'; runId: string; version: string }` (`routes.ts:221`): `version` is required. The `run-stream`
and `run-preview-full` arms return without `version`, so a pinned form of either parses to the un-pinned screen.

Executed against the working-tree `routes.ts` after FIX-696 (Node 22.23.1, `--experimental-strip-types`, scratch
script outside the repo):

| input | `parseViewPath` result |
|---|---|
| `['runs','r1','versions']` | `{"screen":"run-version","runId":"r1"}` (no `version`) |
| `['runs','r1','versions','2','stream']` | `{"screen":"run-stream","runId":"r1"}` (pin dropped) |
| `['runs','r1','versions','2','preview','full']` | `{"screen":"run-preview-full","runId":"r1"}` (pin dropped) |

Downstream (read, not executed): `initialMainViewFor` maps `run-version` to `"execution"`
(`[...view]/page.tsx:175-177`) and `reopenedRunIdFor` returns its `runId` (`page.tsx:216-218`). So `/runs/{id}/versions`
should open the run with no pin under a `/versions` URL. That is a URL and content mismatch per
[ADR-0018](20260824-1631-ADR-0018.md), the inverse of the ISS-911 shape.

Reachability: no builder emits any of these. `routes.runVersion(id, v)` always passes `v`, and `routes.runStream` and
`routes.runPreviewFull` take no version. They are reachable only by a typed, shared or hand-edited URL.

## Fix direction (not applied)

In `parseViewPath` only, as with FIX-696:
- Return `run-version` only when `segments.length === 4`, and `unknown` for a bare `/runs/{id}/versions`.
- For `/versions/{v}/stream` and `/versions/{v}/preview/full`, either return `unknown` when `version` is set or carry
  the pin. Which one depends on whether a pinned stream or full-screen preview is meant to be a route. No builder
  makes one today, so `unknown` matches the current route table.

## Analysis (QA-KB-084, 3-analyzer, 2026-10-02)

Raised as bug QA-KB-084 (`BUGS.md#qa-kb-084`, Low, reproduction mode Static). The analyzer re-read every claim above
in the working tree and executed the parser again. Line numbers are the working tree, where `routes.ts` carries
[FIX-696](20261001-2235-FIX-696.md)'s uncommitted arity edit; anchor on the code text.

Provenance (`git show <sha>:frontend/src/lib/routes.ts`): the undefined `version` is original. Spec 015's first parser
(`887ccfe96`) had `if (subpath === 'versions') { const version = segments[3]; return { screen: 'run-version', runId,
version }; }` with no length check at all. The ISS-230 lift (`d027f16bd`, [FIX-328](20260828-2014-FIX-328.md)) kept the
hole as `segments.length <= 4`, and is also what made a pinned `/stream` or `/preview/full` parse to the un-pinned
screen: before it, any `/runs/{id}/versions/...` path was `run-version`, so the pin was at least carried.

### Root cause: one mechanism, CONFIRMED

The ISS-230 pin lift in `parseViewPath`'s `runs` branch trusts `segments[3]` as the pin, and two arms then discard it
(`frontend/src/lib/routes.ts`):

- `:374-380`: `version = segments[3]; if (segments.length <= 4) { return { screen: 'run-version', runId, version }; }`
  admits length 3, where `version` is `undefined`.
- `:415` (`subpath === 'stream' && tail.length === 3`) and `:420` (`subpath === 'preview' && tail[3] === 'full' &&
  tail.length === 4`) never look at the lifted `version`, and their `ParsedView` members (`:220`, `:222`) have no
  `version` field, so a pinned form parses to the un-pinned screen.

Why `tsc` does not catch it: `frontend/tsconfig.json` has `"strict": true` but not `noUncheckedIndexedAccess`, so
`segments[3]` is typed `string`, the assignment narrows `version` from `string | undefined` to `string`, and the
`run-version` literal satisfies the required `version: string` at `:221`. A reduced copy of that pattern compiled
clean under the repo's own `tsc --strict` (exit 0).

Executed against the working-tree `routes.ts` (node 22.23.1, `--experimental-strip-types`, scratch script in the
session scratchpad, repo untouched):

| input | result today | own keys |
|---|---|---|
| `['runs','r1','versions']` | `{"screen":"run-version","runId":"r1"}` | `screen,runId,version` (the key is present, value `undefined`) |
| `['runs','r1','versions','2','stream']` | `{"screen":"run-stream","runId":"r1"}` | `screen,runId` |
| `['runs','r1','versions','2','preview','full']` | `{"screen":"run-preview-full","runId":"r1"}` | `screen,runId` |
| `['runs','r1','versions','2']` | `run-version`, `version:"2"` | correct |
| `['runs','r1','versions','2','steps']`, `.../steps/a1`, `/files`, `/workspace`, `/audit` | each screen with `version:"2"` | correct |
| `['runs','r1','versions','2','preview']`, `['runs','r1','versions','2','versions','3']` | `unknown` | correct |

### Blast radius (CONFIRMED by grep and read)

`parseViewPath` has four production callers: `frontend/src/app/[...view]/page.tsx:437` (everything below),
`frontend/src/components/library/LibraryPage.tsx:465` (library screens only, unaffected), and
`frontend/src/app/error.tsx:24` plus `frontend/src/app/global-error.tsx:24` (`screenLabel()` for error telemetry
only: the label for these three URLs becomes `unknown`, nothing else changes). Tests that call it:
`routes.test.ts`, `routes.iss339.test.ts`, `initialWorkflowType.bug023.source.test.ts`; none exercises the three forms.

What `page.tsx` does with the three bad parses (all from the one parse, so one fix reaches all of it):

- `initialMainViewFor` (`:133-200`) maps all three to `"execution"`; `reopenedRunIdFor` (`:208-222`) returns the run id
  for `run-version` and `run-preview-full`; `liveStreamRunIdFor` (`:257-259`) does for `run-stream`.
- `pinnedVersionFor` (`:234-236`, `"version" in parsed ? parsed.version : undefined`) is `undefined` for all three, and
  `pinnedVersion={pinnedVersionFor(parsedView)}` (`:4255`) reaches `PreviewPanel`, where `:992`
  (`if (!pinnedVersion) { ... setViewingVersion(null); }`) and `:1005`
  (`pinnedMember = pinnedVersion ? ... : undefined`) mean the pin is never applied.
- The T7 effect (`:3462-3564`) and the T11 effect (`:3576-3779`) fetch or re-attach the plain run named by the URL's
  `{id}`; for `/versions/{v}/stream` on a still-running root that includes the live SSE attach.
- Nothing rewrites the path: the only code that changes it shallowly is `DashboardLayout.tsx:551` (a tab click);
  `AgentThinkingTab.tsx:454` and `:480` push `${pathname}?agent=...` and keep whatever pathname is current; and
  `router.replace` appears in `page.tsx` only for login redirects (`:936`, `:3439`). So the bogus URL stays until the
  first tab click, which builds its route from `pinnedVersion` (`DashboardLayout.tsx:523`, now `undefined`) and
  quietly lands on the un-pinned URL. That is the URL-and-content mismatch of
  [ADR-0018](20260824-1631-ADR-0018.md).
- `unknown` is the route that already does the right thing: `page.tsx:4064-4066` calls `notFound()`.

Reachability, so the severity stays honest: `routes.runStream` (`:115`) and `routes.runPreviewFull` (`:119`) take no
version, and `routes.runVersion` (`:117`) has no non-test caller (`routes.runDetail(id, v)` emits the same string).
Every `routes.runStream` call site (`DashboardLayout.tsx`, `page.tsx:2895`, `StepsOverviewSpine.tsx:52`) passes a run
id, the only `routes.runPreviewFull` caller is `preview-fullscreen/page.tsx:42`, and the backend emits none of these
URLs (`grep "/versions/" backend/`: one docstring, `backend/app/api/runs.py:1657`). Typed, shared or hand-edited URLs
only.

Adjacent state: for a GENERATING run, `DashboardLayout`'s `isRunning` funnel rewrites run URLs to `/stream`
([ISS-956](20261002-0316-ISS-956.md), INFERRED), so the stale-URL window described here is mostly a terminal run.

### Where the fix belongs

In `parseViewPath` only, as [FIX-696](20261001-2235-FIX-696.md) did and its locked constraints require ("Arity is
enforced inside parseViewPath ... never as a per-caller guard in page.tsx or DashboardLayout", and run-tab arity is
counted on `tail`). One guard in the shared function covers all four callers; a guard in `page.tsx` would leave the
error-boundary labels and any future caller wrong.

Candidate diff, three edits, validated on a scratch copy of `routes.ts` (the repo file is untouched):

```diff
-      if (segments.length <= 4) {
+      if (segments.length === 4) {
...
-    if (subpath === 'stream' && tail.length === 3) {
+    if (subpath === 'stream' && tail.length === 3 && version === undefined) {
...
-    if (subpath === 'preview' && tail[3] === 'full' && tail.length === 4) {
+    if (subpath === 'preview' && tail[3] === 'full' && tail.length === 4 && version === undefined) {
```

The first edit alone makes the bare form `unknown`: at length 3 the `tail` rebuild yields `['runs', id]`, `subpath` is
`undefined`, and control reaches the final `return { screen: 'unknown' }`. An explicit
`if (segments.length === 3) return { screen: 'unknown' };` above it is the more readable spelling and equally valid.
Its parse table on the scratch copy: bare `/versions`, pinned `/stream` and pinned `/preview/full` are `unknown`; every
other row of the table above is unchanged.

### Why this is not an escalation

The open question in "Fix direction" (return `unknown`, or carry the pin) has an answer in the existing contract:

- `specs/015-frontend-routing/contracts/route-map.md:37` lists `/runs/{id}/versions/{v}` as the only versioned run
  route, and the Runs table (`:27-38`) has no bare `/versions`, no pinned stream and no pinned preview/full.
  `data-model.md:75` gives the `run-version` row the params `runId, version`. The same file's `:38` row calls
  `/runs/{id}/preview/full` a "legacy alias of `/runs/{id}`" and its note says the route "survives only as the
  redirect target for old `/preview-fullscreen?runId=` bookmarked links", so a pinned alias of an alias is no route.
  Caveat: that table predates ISS-230 and does not list the pinned tab forms either, so it is supporting evidence,
  not proof on its own.
- No builder can emit them (signatures above), no backend code emits them, and no test or e2e step visits them (grep of
  `frontend/src` and `tests/`).
- [FIX-696](20261001-2235-FIX-696.md)'s locked constraint: "parseViewPath returns a real screen only at the exact
  arity of its route; any extra path segment yields { screen: 'unknown' }". Its text lists these forms as "unchanged
  on purpose" because "neither was in any card", not because they were intended.
- [ADR-0018](20260824-1631-ADR-0018.md)'s corollary ("an unrecognised path must resolve to a typed screen ... never
  fall through to `unknown`") is about the open-ended, catalog-driven `/create/{type}` set, as the ADR itself says, and
  `MOD-frontend-src-lib` (`:158-164`) describes the same single exception. The three forms here are a closed set that
  nothing builds, the case FIX-696 already sends to `unknown` -> `notFound()` for the other arity holes.
- QA-KB-084's Expected says `unknown`.

Carrying the pin instead would be a feature (`version?` on two builders and two `ParsedView` members, `pinnedVersionFor`,
PreviewPanel wiring) and would contradict `/stream`'s meaning, a live re-attach, against a pinned read-only snapshot.
