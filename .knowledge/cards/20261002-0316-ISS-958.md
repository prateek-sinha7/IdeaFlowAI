# ISS-958

## What happened

INFERRED sibling of [BUG-024](20260827-BUG-024.md) (QA-KB-049), the other callers of the same funnel. Not reproduced in
a browser. The report is a cold load; these are in-app navigations that arrive at the same effect.

1. **Version menu, a still-running family member.** `frontend/src/components/preview/PreviewPanel.tsx:911-913`:

   ```ts
   if (member && memberId !== unpinnedRunId && !TERMINAL_RUN_STATUSES.has(member.status) && onOpenLiveRun) {
     onOpenLiveRun(memberId, tab);
     return;
   }
   ```

   `tab` is the tab on screen: the comment at `PreviewPanel.tsx:889-891` says "picking a version never also changes
   which tab is showing". `DashboardLayout.tsx:556-562` (`handleOpenLiveRun`) turns it into a route and pushes it:
   `router.push((routeFor[tab] ?? routes.runDetail)(runId))`. The member's page mounts, T7 replays it, `isRunning` goes
   true, and the funnel at `DashboardLayout.tsx:854-856` pushes `/runs/{member}/stream`, so the tab the caller
   deliberately carried is lost.

2. **History and Home run rows.** `DashboardLayout.tsx:2993` (Home recents) and `:3053` (History) both do
   `router.push(routes.runDetail(run.id))`. For a running row that is also rewritten to `/stream`.

Expected: (1) the member opens live on the tab that was showing, as the code and its comments intend. (2) is a UX
call, see below.
Actual (INFERRED): `/runs/{id}/stream` with the Steps tab.

## Root cause (CONFIRMED by source read; the behaviour is INFERRED)

The same effect as BUG-024: `frontend/src/components/layout/DashboardLayout.tsx:854-856`,

```ts
      if (incomingRunId) {
        router.push(routes.runStream(incomingRunId));
      }
```

with no check that the URL already addresses `incomingRunId`. The callers above each push a run URL on purpose and then
race their own destination.

## UX call that the fix changes

After the root fix, a running row opened from History or Home stays on `/runs/{id}` instead of landing on `/stream`.
That agrees with BUG-024's Expected ("Only a fresh launch lands on /stream"), but it is a visible change: History also
has an explicit `onViewRunningPipeline` (`DashboardLayout.tsx:3038-3052`) that pushes `/stream` for a running run, and
that path is unaffected. QA should not report the row-click change as a regression.

## What settles it

Live tier, needs a revision family with a member in flight: on the Audit tab, open the Version menu and pick the live
member; the URL should end `/audit` and today (INFERRED) ends `/stream`. For the rows, open a generating run from
History and read the URL.

## Fixed by the root fix?

Yes. The pushed URL addresses the incoming run, so a guard keyed on the URL leaves it alone.

## TEST COVERAGE — ISS-958

## Fixed — QA-KB-049 (fixer, 2026-10-02): [FIX-712](20261002-1155-FIX-712.md)

`handleOpenLiveRun` and the History and Home rows push a URL that names the incoming run, so the funnel now leaves it
alone. `frontend/src/components/layout/DashboardLayout.bug024.test.tsx` covers `/runs/{id}` (the rows) and the `/steps`, `/files`, `/workspace` and `/audit` tabs (what
`handleOpenLiveRun` pushes). The UX change above applies: a running row opened from History or Home now stays on
`/runs/{id}`. History's explicit `onViewRunningPipeline` still pushes `/stream`. Not driven in a browser.
