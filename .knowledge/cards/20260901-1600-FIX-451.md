## What was wrong

`IntegrationsCard.tsx:80–93` (`refresh` callback) had a completely empty catch:

```tsx
} catch {
  /* dashboard auth already gated this surface */
}
```

On any failure — network blip, 5xx, stale token — `patStatus` and `keys` were left at their initial-mount state of `null`/`[]`. The backend route for "no PAT saved" returns a normal 200 `null` (never an error), so the catch fires only on genuine failures — but rendered identically to "nothing saved yet". A user with real credentials hitting a transient error saw "No GitHub token saved yet." and "No API keys yet." — a false negative with no way to distinguish it from a brand-new account.

## Root cause

Single-file defect: `IntegrationsCard.tsx`'s `refresh()` catch block, with an inline comment suggesting the failure was expected ("dashboard auth already gated this surface"). It was not a valid gate: a stale auth token would still produce a real credential-bearing screen on the backend, and the comment did not distinguish "auth gated — blank by design" from "network/5xx — blank by accident."

## What changed and why there

Added a `fetchError` state (`{ message: string; offline: boolean } | null`) mirroring FIX-370's `loadError` shape:

```tsx
const [fetchError, setFetchError] = useState<{ message: string; offline: boolean } | null>(null);
```

The catch now detects offline/unreachable errors (matching `err instanceof TypeError || err.status === 0`) and sets a human-readable message:

```tsx
} catch (err) {
  const offline =
    err instanceof TypeError ||
    (typeof err === "object" && err !== null && "status" in err &&
     (err as { status: number }).status === 0);
  setFetchError({
    message: offline
      ? "Couldn't reach the server — check your connection."
      : "Couldn't load your saved credentials. Try again.",
    offline,
  });
}
```

On a successful refresh `fetchError` is cleared (`setFetchError(null)`), so recovery is transparent.

The JSX renders an amber notice at the top of the card (above the GitHub PAT and API keys sections) when `fetchError` is set:

```tsx
{fetchError && (
  <div className="rounded-xl border border-amber-200 bg-amber-50 px-4 py-3 flex items-center justify-between gap-3">
    <div className="flex items-center gap-2 text-[12px] text-amber-800">
      <AlertCircle className="h-4 w-4 flex-none" />
      {fetchError.message}
    </div>
    <button onClick={() => void refresh()} className="text-[11px] font-medium text-amber-800 hover:underline flex-none">
      Retry
    </button>
  </div>
)}
```

This is the same amber-notice pattern used throughout the codebase for non-blocking fetch errors, and the same placement FIX-370 used for the HandoffWorkflow offline case.
