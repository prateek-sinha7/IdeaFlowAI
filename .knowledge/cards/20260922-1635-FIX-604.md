# FIX-604

QA-PS-058, a design change Bilal asked for directly rather than a defect report:
*"I still see latest on a done run, why is that? didn't we conclude it will be
only running workflow?"* Two frontend files changed
(`RunHeader.tsx`, `PreviewPanel.tsx`) plus the component's own spec file. No
backend file was touched.

## What was wrong

`VersionMenu` rendered `Latest (live)` unconditionally as option 0
(`RunHeader.tsx:99-112` pre-change) in every run state, on every family. On a
settled family whose newest member is tagged, the live working tree IS that
tag's bytes — the terminal snapshot commit is the last thing written to the
sandbox — so the menu offered the same content twice under two names. An entry
that sometimes means "work in progress" and sometimes means "the same thing as
v6" cannot be reasoned about, which is what made the version menu read as
confusing.

Not a data-correctness defect: `Latest (live)` resolved correctly every time.

## The rule now implemented — three branches

| State | Dropdown |
|---|---|
| a run in the family is in flight | `Latest (live)` first, then completed tags |
| all done, newest member reachable by tag | tags only, newest first — no `Latest (live)` |
| all done, newest member NOT reachable by tag | `Latest (live)` + "Never captured as a version — no tag to select instead." |

**The third branch is the load-bearing one.** Tag creation is best-effort
(`backend/agents/execution_engine/engine.py:2349-2456`): `WorkflowRun.git_tag`
is written only after a successful `create_tag`, so a COMPLETED run can carry
`git_tag = NULL` permanently, and a sandbox's `.git` can be rebuilt out from
under a tag that did land — both mechanisms documented and confirmed live in
[ISS-697](20260922-1000-ISS-697.md) on family
`2708dbf1-50d0-465d-9bed-56b651ea1abf` (DB rows claim v1/v2/v3, `git tag -l`
returns only `v3`). Where that happens there is no tag to select and the live
tree is the only route to the content. A two-branch implementation would have
turned a silent tagging failure into silent data loss, so the reachability test
is deliberately conservative and fails open.

## What changed and why there

**`RunHeader.tsx`** — the one place the option list is built, and the only
production consumer of the tag list, so the whole rule lives here:

- Two new optional props (`:247-254`): `latestVersionTag?: string | null` (the
  NEWEST family member's git tag; `null` = it finished without one; ABSENT = the
  caller has no family data) and `latestVersionInFlight?: boolean`.
- The rule itself (`:318-330`), computed beside the existing `hasTags` (`:317`):
  `latestReachableByTag = !!latestVersionTag && tags.includes(latestVersionTag)`,
  `inFlight = isRunning || latestVersionInFlight`,
  `showLatestLive = inFlight || !latestReachableByTag`,
  `neverCaptured = latestVersionTag !== undefined && !inFlight && !latestReachableByTag`.
  `isRunning` is the component's own existing `runState` discriminator
  (`:303`) — no new signal was threaded for the in-flight case beyond the
  family-row fact the caller already had.
- `VersionMenu` takes `showLatestLive` / `neverCaptured` and wraps the live
  option and its note in them (`:118-140`, `neverCaptured` at `:134`). Selecting a tag or the live entry is
  untouched — the same `onSelectVersion(tag | null)` contract.
- `markedRef` (`:87-91`): with the live entry dropped, nothing in the menu would
  be marked as the current selection while browsing un-pinned, so the tag equal
  to the chip's own label (the version actually on screen) carries `aria-selected`
  instead. `liveLabel` is the bare `vN` in exactly those states.

**`PreviewPanel.tsx`** — supplies the two facts from data it already holds
(`:1226-1235`), right beside `familyVersionCount` (`:1225`), with no new fetch:

```
const latestMember = sortedMembers.length > 0 ? sortedMembers[sortedMembers.length - 1] : undefined;
const latestVersionTag = latestMember ? (latestMember.git_tag ?? null) : undefined;
const latestVersionInFlight = !!latestMember && !latestMember.completed_at;
```

`sortedMembers` is the DB-authoritative family list (`GET /{id}/family`) already
driving the chip's label. `completed_at` is used rather than a status-string set
so no status enum is duplicated into this file (SC-001-shaped) — and it fails in
the safe direction: a member with no `completed_at` reads as in flight, which
only ever keeps `Latest (live)`.

**Why "in flight" is not its own new signal.** A member still running has no tag
by construction (tags are created in `finalize_terminal_run`), so the untagged
branch already keeps the live entry for it; `latestVersionInFlight` exists only
so the *note* does not claim a still-running version "was never captured".

## FIX-603 is untouched

All four of its behaviours in this file were re-read after the change and are
byte-identical: the pinned ref threaded into `handleHeaderDownload` + its
`useCallback` dep, `VersionView.runInput` / `effRunInput`, the `/versions/{n}`
URL-pin effect staging `intendedSandboxRef`, and the pin-clearing effect keyed on
`pinnedVersion`. This change adds three derivations and two JSX props and edits
nothing else in `PreviewPanel.tsx`.

## The pinned test, revised deliberately

`RunHeader.test.tsx:80` asserted *"Latest (live) is the first option, newest tag
next"* and `:102` that `options[0]` has text `Latest (live)`. That was correct
for the pre-QA-PS-058 behaviour and is wrong after it. It was **revised, not
deleted or weakened**: the same assertions (first option, newest tag next,
`aria-selected`, and the full `onSelectVersion("v1")` / `onSelectVersion(null)`
callback contract) now run under `runState="building"` + `latestVersionInFlight`,
and three new cases pin the other branches. No other assertion in any file was
relaxed.

## Not changed, deliberately

- **[ISS-697](20260922-1000-ISS-697.md) stays OPEN.** Its fix direction is that
  the menu should not be gated on `list_tags()` at all — it should list every
  `FamilyMember` from the DB, tagged or not. That is a bigger change to what the
  menu contains; this card only changes when the LIVE entry is offered, and it
  deliberately preserves the escape hatch ISS-697's mechanism needs until that
  card is fixed.
- **`hasTags` still gates whether the menu mounts** (`RunHeader.tsx:420`) — a
  family with no tags at all keeps today's static chip. Unchanged, and ISS-697's
  territory.
- **The `VersionSwitch.integration.test.tsx` harness passes no family info**, so
  it exercises the fail-open path (`latestVersionTag` absent → live entry kept)
  and was left exactly as it is — it still asserts what it always asserted.
