# ISS-125

## Title

_stamp_resume_marker still allocates its seq the slow, unprotected way. engine.py:6309-6311 reads the ENTIRE durable log (store.read_events(run_id, after_seq=0)) to compute max(seq)+1, then calls the non-retrying append_event at that fixed seq. Two consequences: (a) it materialises every row of the run — the local corpus holds a 26k-row and a 36k-row run — to derive one integer, which is the exact cost profile that ruled append_event_next_seq out for the engine sink; (b) it carries the same lost-write exposure ISS-121 describes, though the blast radius is far smaller (the marker is a best-effort audit row wrapped in its own try/except, and losing it degrades an audit trail, not run state). Fix shape: reuse the _max_event_seq index probe FIX-240 added, and append through append_event_at_or_after. Line numbers verified at commit 88521920.

## Source / evidence

Surfaced by the ISS-121 allocator sweep. Not folded into FIX-240 because the marker needs no seq RE-STAMP (it yields no frame), so it is a genuinely separate change with a separate proof obligation.
