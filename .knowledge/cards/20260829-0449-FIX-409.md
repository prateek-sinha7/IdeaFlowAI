## What was wrong

`BUG-20260828-013500-runs-id-workspace`. On a run's Workspace tab, opening any text file in
"Code" view rendered it inside a CodeMirror 6 instance whose `.cm-content` is
`contentEditable === true`. Clicking in and typing inserted characters live, and nothing on the
page said so — no lock icon, no "read-only" badge, no disabled styling, no Save/Discard control,
no warning. Opening a sibling file re-fetched the server's bytes and the typing vanished with no
indication anything had been lost. 3/3 cold-start reproductions across `PLANNER.md`,
`01-ppt-brief-analyst.md` and `.browser/deck-styles.json`; no `PUT`/`POST`/`PATCH` was ever
observed, so nothing was ever at risk server-side — the defect is entirely the unannounced
editable surface and its silent discard.

## Root cause

`frontend/src/components/results/SandboxTab.tsx`, `CodeView` (`:492`), whose `EditorView`
extensions array (`:675-701` pre-change) never sets `EditorState.readOnly.of(true)` or
`EditorView.editable.of(false)`.

The writable doc is **deliberate**, not an omission. The inline comment at `:687-690` states it
("⌘F opens Find AND Replace. Replace has to be able to write, so the doc is editable — but it is
a SCRATCHPAD"), and `frontend/src/components/results/SandboxTab.test.tsx:375-410` is an existing,
passing test that asserts `.cm-content`'s `contenteditable` is `"true"` and that the Replace
control is live. A blanket `EditorState.readOnly.of(true)` blocks every transaction including the
ones Replace dispatches, and would have failed that test.

What was actually wrong is that the pane never said any of this to the user, and the component's
own top-of-file doc comment (`:476-491`) asserted the opposite — "CodeMirror 6, **read-only**...
(autocomplete, linting, history, edit keymaps) is for EDITING **and is not pulled in**" — while
`commands.history()` and `commands.defaultKeymap` are both in the extensions list two hundred
lines below it. So the missing thing was the user-facing signal, and the stale thing was the doc
comment, not the implementation.

## What changed and why there

All of it inside `CodeView`, the one function both call sites route through
(`grep -n "<CodeView" SandboxTab.tsx` → `:411`, `:1339`; the component is not exported, so those
two are the whole blast radius):

1. **The strip** — one `<span>` appended after the editor host, reading
   `Read-only scratchpad — edits are not saved` behind a `Lock` glyph. Placed inside `CodeView`
   rather than at either call site precisely because there are two: the explicit Code toggle
   (`:1339`, the path the bug report exercised) and `MD_COMPONENTS.code` (`:411`), which feeds
   every fenced block of a markdown file's DEFAULT, un-toggled Preview through the identical
   editor. A guard at `:1339` alone would have left the surface a user reaches without clicking
   anything still silent ([ISS-597](20260829-0135-ISS-597.md)).
2. **The `fill` wrapper** — `h-full min-h-0` → `flex h-full min-h-0 flex-col`, and the editor host
   `h-full` → `min-h-0 flex-1`. The host used to be the only child claiming the full pane height;
   the strip needs a row under it.
3. **The doc comment** — dropped the false "read-only" claim and the false "edit keymaps... not
   pulled in" claim, and said instead what ships and why: the doc takes keystrokes because Replace
   writes, there is no save path, and the strip is how the user is told.
4. `Lock` added to the existing `lucide-react` import.

No `readOnly`/`editable` config was introduced, so the Find-and-Replace contract at
`SandboxTab.test.tsx:375-410` is untouched and still green.

**`PreviewPanel.tsx` was not modified.** [ISS-598](20260829-0136-ISS-598.md) named it in its
globs but its own "Where the fix belongs" section concludes no status prop needs threading: the
defect is status-blind by construction (`CodeView` receives only `code`, `lang`, `fill`), so the
same strip covers a still-generating run and a completed one identically. Confirmed by running
that card's test against an unchanged `PreviewPanel`.
