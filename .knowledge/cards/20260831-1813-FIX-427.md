# FIX-427

**Phase / trigger:** bug-hunt domain 15 (backend·other), batch B1 — ISS-120

## Description

`BEDROCK_PROMPT_CACHE_ENABLED` was the ONLY gate on Bedrock prompt caching, and it is
process-wide. A caller that knows its turn is short and single-shot — one that will
WRITE a cache entry nothing later re-reads, and so pay a pure 1.25x surcharge on that
content (`agents/capabilities/model_catalog.py:82`, `cache_write_5m = 1.25e-6` against
`input = 1e-6`) — had no way to decline. Its only lever was the global setting, which
would have turned caching off for every other concurrent call in the process too.

The fix is the per-call escape hatch: `cached_invoke(..., enable_cache=False)` suppresses
the `cache_control` kwarg on THAT call and nothing else. It is **opt-OUT only** —
`enable_cache=True` (the default) never re-enables caching the global flag has turned
off, so `BEDROCK_PROMPT_CACHE_ENABLED` remains the master kill switch and every existing
caller's behaviour is byte-identical.

Placed in `cached_invoke` itself, at the one line where the per-call `cache_control` is
computed, because all five direct-invoke callers route through it:
`agents/planner/smart_planner.py:405`, `agents/execution_engine/clarify_engine.py:554`,
`app/agents/handoff/classifier.py:50`, `app/agents/handoff/test_agent.py:143` and
`app/agents/handoff/compliance_agent.py:159`. One guard there covers all of them; a
guard per caller would have been five diffs and four future misses.

Deliberately NOT put inside `_bedrock_cache_control` (cached_invoke.py:60). That helper's
contract is "identical gating + payload to `_BedrockCachePointsMiddleware`" (INV-12: ONE
mechanism); giving it a per-call parameter the middleware does not have would have made
that claim false. The per-call policy belongs where the per-call argument arrives.

**The `_BedrockCachePointsMiddleware` half of ISS-120 is NOT closed by this card** — see
the deferred-findings note below.

## Root cause

`backend/app/agents/cached_invoke.py:176` (pre-fix) read the cache decision solely from
`_bedrock_cache_control(llm)`, whose only enable-gate is
`settings.BEDROCK_PROMPT_CACHE_ENABLED` (`cached_invoke.py:71`, default `True` from
`app/core/config.py:158`). No parameter, no per-step signal, nothing a caller could pass.
Caching was therefore all-or-nothing for the whole process, and on a short run that is a
MEASURED net cost increase (ISS-120: 6 of 11 persisted runs -4.98%..-8.86%).

## What changed

`backend/app/agents/cached_invoke.py` — three edits, all in `cached_invoke`:

- signature: `enable_cache: bool = True` added as a keyword-only parameter (`:129`);
- docstring: an `enable_cache` `Args:` entry stating the 1.25x rationale and the
  opt-out-only semantics;
- the gate itself (`:184`): `cc = _bedrock_cache_control(llm) if enable_cache else None`.

No new imports. No signature change to `_bedrock_cache_control`. No caller updated —
the default preserves today's behaviour exactly.

## Deferred (not fixed here)

The second flag-read site named by ISS-120,
`app/agents/deep_agent_runner.py:283` (`_BedrockCachePointsMiddleware._maybe_apply`),
still has no per-call override. It is constructed at exactly one place
(`deep_agent_runner.py:463`, `_BedrockCachePointsMiddleware()`) with no per-step signal
available to feed it, so wiring an override there IS ISS-120's candidate shape (b) — a
manifest-declared capability flag plus the plumbing to carry it to the runner. That is a
product/design decision the card explicitly leaves open (it lists three mutually
exclusive shapes and picks none), not a defect with one right answer, so it was not
decided here. ISS-120's middleware half remains open under the ISS card.
