## What was wrong

A cold load of `/create/user-stories` fired `GET /api/workflows/user_stories`
twice. `IdeaInputPage.tsx:1121`'s mount effect (`useEffect(..., [workflowId])`,
lines 1097-1302) guards only its own state update with a `cancelled` flag set
in the cleanup — it never aborts or de-duplicates the fetch — and React
StrictMode double-invokes that effect in dev (`frontend/next.config.ts` sets
no `reactStrictMode: false` override).

The same shape repeats on every surface that seeds itself from a workflow's
compiled plan. Re-grepped at fix time
(`grep -rn "getWorkflowDetail(" frontend/src`, 7 non-test call sites), which
confirms ISS-819's blast-radius table still holds at the current line numbers:

| Call site | Trigger | Card |
|---|---|---|
| `IdeaInputPage.tsx:1121` | mount effect, `[workflowId]` | [ISS-819](20260922-1940-ISS-819.md) (the reported path) |
| `LaunchWizard.tsx:508` | mount effect | [ISS-820](20260922-1941-ISS-820.md), [ISS-836](20260922-2018-ISS-836.md) |

`getWorkflowDetail()` itself was a bare `request()` call with no guard at all,
unlike `getWorkflows()` (`inFlightWorkflows`, [FIX-616](20260922-1923-FIX-616.md))
and `adminListUsers()` (`inFlightAdminUsers`, ISS-789/ISS-816) sitting in the
same file.

## What changed and why there

`frontend/src/lib/api.ts` — one private
`inFlightWorkflowDetail: Map<string, Promise<WorkflowDetail>>` above
`getWorkflowDetail()`, keyed by `` `${token}\n${path}` `` where `path` is the
already-resolved `/api/workflows/{id}[?original=true]`. A caller asking while
a request is still open gets that promise back instead of issuing a second
`request()`; the entry is deleted in `.finally()`.

This is the one place all seven call sites already route through, so it closes
the reported path and all four sibling cards in a single change — the same way
FIX-616 closed every `getWorkflows()` caller without touching
`WorkflowHistory.tsx`, `RunConnectionProvider.tsx` or `page.tsx` individually.
No per-component `useRef`/`AbortController` guard was added or wanted.

Two deliberate properties, both matching the `inFlightAdminUsers` precedent
three hundred lines above:

- **De-duplicates, does NOT cache.** The entry is dropped the moment the
  request settles, so the two `handleToggleOverride` read-backs
  (`IdeaInputPage.tsx:1705`, `LaunchWizard.tsx:590`) — each a sequential
  `await setWorkflowOverrideEnabled(...)` followed by
  `await getWorkflowDetail(...)` — still go to the network and still observe
  the row they just wrote. `cachedGet()`'s 30 s TTL would have been wrong here
  for exactly that reason.
- **The key includes the resolved path, not just the id**, so the spec-016
  "compare with original" read (`?original=true`) can never be served the
  override payload, and the token is in the key so two identities never share
  a plan.

`getWorkflowDetail` lost its `async` keyword (it now returns the shared
promise directly, like `getWorkflows` and `adminListUsers`); the declared
`Promise<WorkflowDetail>` return type and the signature are unchanged, so no
caller was touched.

  report's "not needed on a creation wizard" complaint is about the
  unconditional `[isAuthenticated]` effect in `page.tsx:985-1002`, which is
  ISS-808's territory (QA-PS-039), not this function's.
- **[ISS-836](20260922-2018-ISS-836.md) (QA-PS-044's root card) names this same
  function and is cured by this change**, but it belongs to another bug's row
  and its status was left untouched here — only a reciprocal reference edge was
  added to it.
- **[ISS-837](20260922-2018-ISS-837.md)** — `LaunchWizard`'s
  `listPrototypeTemplates`/`listPPTTemplates`/`listDesignSystems` calls go
  through `ppt-api.ts`/`prototype-api.ts`'s own `fetch()` wrappers and are out
  of this function's reach. Still open.
