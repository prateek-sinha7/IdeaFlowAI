# ISS-1134

**Register source:** sibling derived during the `QA-KB-107` analysis on 2026-10-09 (root [ISS-1133](20261009-0200-ISS-1133.md)). Not its own bug row.

**Confidence:** the mechanism is CONFIRMED twice. By source: `smart_planner.py:346-394` has no override rung. By an offline probe that replaced every chat-model
constructor with a recorder (`evidence/qa-kb-107/analysis-03-smartplanner-ignores-override.txt`): with `USE_LOCAL_OLLAMA=1` in the process environment,
`SmartPlanner()` reaches `ChatBedrockConverse` (with and without a bearer token) while `build_model()` reaches `ChatOllama`. INFERRED: what a real run does
with it. No run was started and no model was called.

What would settle it in a run: with the override on and a valid Bedrock token, launch `prototype` and read the planner's token usage and the backend log. Planner
tokens against a Bedrock model id while every agent step reports Ollama is the proof. Offline, the test under "Test notes" settles it.

## Condition

- `SmartPlanner.__init__` calls `self._build_llm()` (`backend/agents/planner/smart_planner.py:340`). `_build_llm` (`:346-394`) has three exits: `ChatAnthropic` when
  `ANTHROPIC_API_KEY` is set (`:350-363`), `ChatBedrockConverse` over a bearer-token session (`:376-387`), and `ChatBedrockConverse` over the default credential
  chain (`:389-394`). It never reads `USE_LOCAL_OLLAMA`, never reaches `ChatMistralAI`, and never calls `build_model`.
- `plan()` hands that instance to `cached_invoke(..., model=self._llm)` (`:530-534`). `cached_invoke` calls `build_model` only when `model` is a `str` or `None`
  (`backend/app/agents/cached_invoke.py:178-181`), so an instance skips the override. Every other one-shot (clarify, the handoff agents, the revision analyzer,
  `run_commands.py:5541`) goes through `build_model` and does honour it.
- The engine runs the planner for every manifest that declares `planner: run`: 14 of the 39 built-in `workflow.yaml` files, `prototype`, `user_stories` and
  `app_builder` among them. The other 25 say `planner: skip`, and a composed manifest defaults to skip (`kernel_services.py:1637`). Call chain: `engine.py:5443`
  -> `_run_planner` (`:8219`) -> `_invoke_planner` (`:8283-8299`).

## Expected vs actual

Expected: with the dev override on, every model call of a run goes to the local model. That is what the override's own banner says ("NOT the real configured
provider", `model_factory.py:357-364`) and what the `QA-KB-107` report assumes ("the run never touches Bedrock").

Actual: the planning call goes to Anthropic or Bedrock. Two outcomes:

- Valid token: one billed Bedrock call per planner run, and the plan JSON comes from a different model than the rest of the run.
- Expired token (the state of this dev machine, `evidence/qa-kb-107/analysis-01-live-config.txt`): `plan()` catches the exception and returns `_default_context`
  (`smart_planner.py:560-562`, `:564-585`) with `execution_gate: "CLARIFY_REQUIRED"` and `planner_fallback: True`. The run does not fail. It degrades to the canned,
  domain-generic clarify gate, with one warning line. `engine.py:8277-8281` is a second net, for a constructor failure.

## Why the root cause implies it

[ISS-1133](20261009-0200-ISS-1133.md) is the preflight's copy of the provider-selection chain, and it is too strict. This is the planner's copy, and it is too loose:
it follows the chain without its first rung. There are three working copies (`build_model`, the preflight, `SmartPlanner._build_llm`) and a fourth that only logs
(`main.py:96-114`). Fixing the preflight alone lets the launch through and then exposes this.

## Fix direction (INFERRED, not applied)

Make the planner honour the same decision. Smallest change: at the top of `_build_llm`, when the shared override helper from the [ISS-1133](20261009-0200-ISS-1133.md)
fix says the override is on, `return build_model(self.model_id, max_tokens=2048)`. Leave the Anthropic and Bedrock exits alone: INV-3 asks for byte-identical
requests, and routing them through `build_model` would add `temperature=1` and reasoning fields where the planner sends `temperature=0` (Anthropic) or neither
(Bedrock).

## Test notes

Offline unit test, no network: `monkeypatch.setenv("USE_LOCAL_OLLAMA", "1")`, replace `langchain_ollama.ChatOllama` and `langchain_aws.ChatBedrockConverse` with
`MagicMock`s, leave `settings.AWS_BEARER_TOKEN_BEDROCK` empty so no boto session is built, construct `SmartPlanner()`, and assert the Ollama recorder was called and
the Bedrock one was not. Today it is the other way round. The control (`USE_LOCAL_OLLAMA=0`) must still reach Bedrock. Pin the flag explicitly in both: left
unpinned the result depends on the local `backend/.env` ([ISS-1136](20261009-0258-ISS-1136.md)).
