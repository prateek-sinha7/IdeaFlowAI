# ISS-052

## Title

One "Update the Specs" click costs FOUR approvals: the re-run specify gate, the re-run plan gate, then the analyze gate RE-OPENS after the sub-pipeline returns. The doubled analyze gate is redundant and the two are visually identical, so the user cannot tell which one they are on. This is the real UX fix behind ISS-064.

## Severity / Tag / Status (original row)

- Sev: minor
- Tag: agents,product
- Status: **PARTIALLY FIXED — FIX-254 (ex-FIX-220) / quick-260812-1nz (2026-08-12). The ambiguity clause is CLOSED; the extra-approval clause is NOT — it is now ISS-072.** This row had two clauses and they have different answers. **(1) "the two are visually identical, so the user cannot tell which one they are on" — FIXED.** `review_gate_ready` now carries `revision_cycle` (which spec-revision cycle this FIRING belongs to, 0 = none) + `revision_in_flight` (is the pass still on the stack), `(0,False)/(1,True)/(1,False)` across `[0]/[1]/[2]` — the PAIR is unique per firing, which cycle alone is not. Both come from existing run scratch (`revision_high_water` / `revision_attempt`) through ONE resolver `_revision_stamp` with three callers: no new state, no migration, no workflow/agent literal. The FE names the cycle on the gate card and no longer claims "Accept & continue to build" at a firing where approving merely finishes the revision. It also closed an UNTESTED second harm the investigation found: `InlineGateActions` reset its one-action latch on `[output, gateKey]`, and NEITHER changes between `[1]` and `[2]`, so the re-opened gate rendered with every action disabled; the stamp is now in that dependency array, with a test seen failing first. **(2) "costs FOUR approvals" — NOT fixed, deliberately.** Suppressing `[2]` (what this row's text proposes) is disqualified on evidence: it is the ONLY firing with `update_specs_eligible=True`, so removing it deletes the sole entry to a second cycle and regresses ISS-064, closed the same day. The genuinely redundant firing is `[1]` — same bytes, strictly smaller action set, approval with no externally visible effect — and suppressing THAT is a different, larger change. Filed as **ISS-072**. **Also rejected outright, on measured evidence:** FE-side dedupe of "same gate_key + same output". It converts a redundant gate into a HANG (the engine is still blocked on `event.wait()`; swallowing the frame removes the only UI that can resolve it) and it would eat legitimate restart-resume re-opens, whose signature is identical — live-proven at `5ecb990f` seq 8402/8406 and `d5dbc9f2` seq 24788/24792, each preceded by `workflow_validated` + `pipeline_start`. **Residual (known, unfixed):** the chat-lane milestone card still reads "Paused — needs approval" for both firings (`chat_narrator.py:171-173`) — the data to disambiguate it now rides the event (SSE re-emits `payload_json` verbatim), so that is a pure render follow-up. NOTE `chat_narrator._revision_index` reads `spec_revision_attempt`/`revision_index`, NOT `revision_cycle` — verified, no collision, and the names were kept distinct deliberately so an in-revision gate card does not silently become a "Revising spec" card.
