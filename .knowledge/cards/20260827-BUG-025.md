## Why this is worse than a stuck button

The canvas is the only place the composition exists before it is saved. An
author who adds a wrong agent has no way back except reloading, which discards
every other thing configured on the canvas alongside it. The cost of the defect
scales with how much work preceded the mistake.

## The invisible-disabled compounding

`disabled:opacity-0` was presumably chosen so a locked control does not clutter
a canvas full of core steps. The effect on this path is that there is nothing
on screen to explain why removal does not work — the `title` attribute is
attached to an element with zero opacity, so the hover that would reveal it
never happens. Greying the control instead would at least make the lock legible
while the underlying source-of-truth bug is fixed.

## Analysis 2026-10-02 (QA-KB-050)

Re-analysed from the current tree (branch `feat/user-stories-v2`, HEAD `024c03ef8`, working tree). No browser was opened: the
report's reproduction mode is Static, and the symptom was already observed live in an earlier phase (D-30,
`tests/integration/DEFECTS-OBSERVED.md:709-739`, found by e2e `S-04-08`). This analysis explains it, corrects the triage sketch and
widens the blast radius.

Baseline for line numbers: the working tree on 2026-10-02. `ComposerPage.tsx`, `AgentsPopup.tsx`, `DashboardLayout.tsx`, `page.tsx`
and `SavedWorkflowsPage.tsx` carry uncommitted edits from other work (none inside `getRole`, `AgentsPopup.tsx:169-248`; in
`ComposerPage.tsx` the cited lines are 4 to 16 higher than at HEAD). `CanvasNode.tsx`, `AgentRow.tsx`, `CanvasView.tsx` and

### Root cause (CONFIRMED: one mechanism and two compounding defects)

**The mechanism: the composer decides what is core from a value it does not own.**

1. `ComposerPage` takes `workflowType` as a prop documented as "fixed at composer entry" (`ComposerPage.tsx:119-120`), and
   `DashboardLayout.tsx:3214` hands it DashboardLayout's own `workflowType` state. That state is written from 20 `setWorkflowType(`
   call sites (grep: `:835`, `:1206-1324`, `:1417`, `:1488`, `:1571`, `:1738`, `:1768`, `:1946`, `:2072`, `:3061-3093`) and seeded once at
   mount (`DashboardLayout.tsx:627-637`): `initialWorkflowType`, else a `prototype.pending` / `ppt.pending` latch, else `"user_stories"`.
2. For three of the four composer routes the seed is `undefined`. `initialWorkflowTypeFor` (`page.tsx:386-397`) maps only
   `create-app`, `create-user-stories` and `create-workflow`, and `page.tsx:4250` passes `initialWorkflowTypeFor(parsedView) ??
   builtinCanvasType` down. Executed on the real functions (`evidence/qa-kb-050/analysis-proof-initialWorkflowTypeFor.out.txt`):

   | URL | screen | seed DashboardLayout receives |
   | --- | --- | --- |
   | `/workflows/new` | workflow-new | undefined, so `"user_stories"` |
   | `/workflows/{id}/edit` | workflow-edit | undefined, so `"user_stories"` |
   | `/workflows/{id}/run` | workflow-run | undefined, so `"user_stories"` |
   | `/workflows/ppt/canvas` | workflow-canvas | `"ppt"` (from `builtinCanvasType`), the right one |

3. So a cold `/workflows/new` mounts the composer with `workflowType === "user_stories"`. (The in-app click, Home "Compose a custom
   workflow", calls `handleSelectFeature("custom")` (`DashboardLayout.tsx:1569-1581`): `setWorkflowType("custom")` and then
   `router.push(routes.workflowNew())`. A push under the `[...view]` catch-all remounts `page.tsx` (`DashboardLayout.tsx:540-550`;
   [ISS-916](20261001-2220-ISS-916.md) read Next's cache key for the same fact), which would discard that `"custom"`. INFERRED: nobody
   has clicked it.) This is the same family as [BUG-023](20260827-BUG-023.md), whose fix mapped `create-app` and `create-user-stories`
   and left the composer routes out.
4. The composer feeds that value to `getRole` through `ComposerPage.tsx:1430` (CanvasView, then every CanvasNode: `CanvasView.tsx:2374`
   root nodes and `:2417` sub-agent nodes), `:1629` (AgentRow) and `:669` (drag guard). `getRole(agentId, pipelineType)`
   (`AgentsPopup.tsx:210-248`) returns `"locked"` for domain-analyst and backlog-compiler and `"required"` for epic-architect,
   story-estimator, nfr-specialist and backlog-reviewer when the type is `user_stories`. For `"custom"` the native list is `[]`
   (`:241`), so everything is `"optional"`.

**Compounding defect 1: the badge and the lock read different predicates.** Both renderers compute `const locked = role === "locked"`
and `const removable = role === "optional"` (`CanvasNode.tsx:479-480`, `AgentRow.tsx:85-86`). The Core badge is `{locked && ...}`
(`CanvasNode.tsx:731`, `AgentRow.tsx:170`); Remove is `disabled={!removable}` (`CanvasNode.tsx:639`, `AgentRow.tsx:199`).
`"required"` is neither, so it gets no badge and a disabled Remove.

**Compounding defect 2: the dead control is invisible.** `CanvasNode.tsx:644` styles the disabled Remove `disabled:opacity-0`, so
`title="Core agents can't be removed"` (`:638`) sits on an element nobody can see. `AgentRow.tsx:201` greys the same control
(`disabled:text-line-faint`), so the Simple view is visible but unexplained.

**Executed, not just read.** The real `getRole` with the real LOCKED/REQUIRED sets, sliced out of `AgentsPopup.tsx`, and the two
predicates, which the script first asserts are still verbatim in both renderers
(`evidence/qa-kb-050/analysis-proof-getRole.out.txt`):

| agent | pipelineType `user_stories` (what the route supplies) | pipelineType `custom` (what it should supply) |
| --- | --- | --- |
| domain-analyst | locked: Core badge, Remove disabled | optional: no badge, Remove enabled |
| backlog-compiler | locked: Core badge, Remove disabled | optional |
| epic-architect | required: NO badge, Remove disabled | optional |
| story-estimator | required: NO badge, Remove disabled | optional |
| nfr-specialist | required: NO badge, Remove disabled | optional |

That is D-30's DOM to the letter when the three agents added are domain-analyst, epic-architect and story-estimator: one Core badge, three
disabled Removes, and the two non-core ones ("Estimation Agent", "Backlog Architecture Agent", the names in
`backend/agents/prompts/story-estimator/AGENT.md` and `epic-architect/AGENT.md`) are required, not locked, in the pipeline they came
from. Why those three: the Add-agent panel opens on the same stale tab and hides nothing ([ISS-962](20261002-0319-ISS-962.md), INFERRED).

**The guard is right where it applies.** `getRole(..., "ppt")` locks all three ppt steps and the badge agrees, which is why `S-04-03`
(`/workflows/ppt/canvas`, Core x3) passes. Do not touch `getRole`, `LOCKED_AGENT_IDS` or `REQUIRED_AGENT_IDS`.

**Origin.** Three faults, entered at different times:

- The two predicates and `disabled:opacity-0` are in the first commits of the two surfaces: `e1490fad2` (2026-07-13, Simple view) and
  `acb616be3` (2026-07-14, Canvas view; `git show acb616be3:frontend/src/components/workflow/composer/CanvasNode.tsx`, lines 21, 46-47,
  98, 104). Its header already says "optional agents only; Core agents can't be removed", and the disabled control is titled that for
  every non-optional role, so in the code's own vocabulary Core means "not optional" and the badge is the odd one out.
- The stale type: until `9cf42ca8e` (2026-08-21) the composer's roster was seeded from `workflowType`, so `getRole(..., workflowType)` was
  coherent. That commit made the composer start empty and hardened THREE reads to the literal `"custom"`, with comments saying
  `workflowType` "is a shared mutable variable other screens can leave stale": `pipelineLabel` (`ComposerPage.tsx:641`), the Save stamp
  (`:931`) and `resolveDispatchType(pipelineAgents, "custom")` (`:1044`). It left the other eight code reads alone. BUG-025
  (2026-08-27) is the residue.

### Fix: where it belongs, so every consumer routes through it

Frontend only; no backend, migration or restart. Three changes, in order of importance.

1. **`ComposerPage.tsx`: derive the composer's identity once and read only that.**

   ```ts
   // "custom" unless this canvas shows a built-in's own manifest. `workflowType` is DashboardLayout's shared
   // mutable state (default "user_stories") and is never the composer's identity.
   const canvasPipelineType = (builtinCanvasType ?? "custom") as WorkflowType;
   ```

   Use it at `:651`, `:669`/`:672`, `:793`, `:798`, `:1430`, `:1629`, `:1666`, `:1706`. Either stop destructuring the prop (and drop it from
   `DashboardLayout.tsx:3214` and the three test mounts) or keep it only for the log at `:298`. This is the generalisation of what
   `9cf42ca8e` did for three reads, and the one place that survives every source of staleness (the remount default, a saved row stamped with
   a stale base type `DashboardLayout.tsx:1743-1747`, any of the 20 writers), which a fix at the seed cannot. The triage sketch's
   `(builtinCanvasType as WorkflowType) ?? "custom"` casts before the fallback; cast the whole expression, because `WorkflowType` is a closed
   union (`types/index.ts:395`) and `builtinCanvasType` is a `string`.
2. **One predicate for the badge and the lock**, defined beside `getRole` (`AgentsPopup.tsx:210`) and called by `CanvasNode.tsx:479-480`,
   `AgentRow.tsx:85-86` and `AgentsPopup.handleRemove` (`:2823`): Core badge and Remove both read `role !== "optional"`. The drag guard
   stays `role !== "locked"`, so required steps stay reorderable. This is also the only change that fixes the built-in canvases and the
   modal ([ISS-963](20261002-0319-ISS-963.md)).
3. **`CanvasNode.tsx:644`: replace `disabled:opacity-0` with `AgentRow.tsx:201`'s `disabled:text-line-faint`**, so the lock is visible and its
   title reachable.

Optional, and not sufficient alone (same family as BUG-023 / FIX-699): `initialWorkflowTypeFor` could return `"custom"` for `workflow-new`.
It would not cover `/workflows/{id}/edit` and `/run` (no type exists until the fetch resolves) or a stale-stamped saved row, and it leaves
the shared variable mutable under the composer. Do not touch `getRole`, the id sets or `AgentLibrary`: each is right for the type it is given.

Invariants: no SC-001 / INV-1 / import-linter surface (a frontend screen mapping, no kernel); ADR-0018 untouched (no path literal). The one
thing a naive fix can break is locked constraint 2 (frontmatter): removing the guard, or hard-coding `"custom"` inside CanvasNode, would unlock
`/workflows/ppt/canvas`, which `S-04-03` expects to be Core x3.

### Corrections to the triage sketch (BUGS.md, QA-KB-050)

- Step 1 lists `:1430`, `:1629`, `:669/:672` only. Five more reads need the same value (`:651`, `:793`, `:798`, `:1666`, `:1706`), and `:1706`
  is the one that lets core agents onto the canvas in the first place.
- Step 3 asks for `AgentRow.tsx:200` to swap `disabled:opacity-0`; AgentRow has none (`:201` is already `disabled:text-line-faint`). Only
  `CanvasNode.tsx:644` is invisible.
- Step 2 is right (badge on `role !== "optional"`) and has a source in the code's own vocabulary (see Origin).
- Locked constraint 1 ("the Core BADGE is the one telling the truth"), and the same line in the D-30 fix sketch (`DEFECTS-OBSERVED.md:737-739`:
  the lock "should follow the same source the Core badge does"), hold only for `/workflows/new`, where nothing should be core. Read
  literally as "make the lock follow the badge" (`removable = !locked`) they would make `required` agents removable on every built-in canvas
  and in the launch modal, whose own guard is `getRole(agentId, pipelineType) !== "optional"` (`AgentsPopup.tsx:2823`). That changes the
  built-in contract, which is a product call and not part of this fix. The designed rule is "required means not removable" (the control has
  been titled "Core agents can't be removed" for every non-optional role since `acb616be3`), so the lock is right and the badge is the one
  that under-reports ([ISS-963](20261002-0319-ISS-963.md)). The type fix makes the question moot on `/workflows/new`: with `custom` there
  is no lock and no badge.
