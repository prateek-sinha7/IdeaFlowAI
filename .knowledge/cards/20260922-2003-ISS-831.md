## What is suspected

INFERRED — the least-settled part of [ISS-800](20260922-1633-ISS-800.md)'s
root cause. BUGS.md QA-PS-048's headline claim is `GET /api/runs/{id}` (the
full run record, 829 KB on the reporter's 2.2M-token run) fetched **3x** on
an Audit tab switch — "the most severe individual waste — 1.66 MB of
redundant data." [ISS-800](20260922-1633-ISS-800.md)'s own 3/3 validation
did **not** reproduce this: the bare run record fetched once per attempt on
a smaller (249K-token) run, while the four Audit-specific endpoints still
duplicated 2x independent of run size. This card investigates why the two
claims diverge and what would explain the ×3 specifically.

`getWorkflow` (`frontend/src/lib/api.ts:1003-1012`) has no dedupe — it
calls `request()` directly, not the `cachedGet()` TTL helper at
`api.ts:386-426`. Grepped call sites app-wide (`grep -rn "getWorkflow("
frontend/src`, excluding `getWorkflows`/`getWorkflowDetail`/comments):

- `frontend/src/app/[...view]/page.tsx:2918` — `handleSelectWorkflowRun`'s
  own fetch, the canonical "open a run" call. [BUG-030](20260826-1403-BUG-030.md)
  (resolved) already proved a tab click no longer remounts `page.tsx`
  (`window.history.pushState`, not `router.push`), so this specific call
  does not refire per tab click — ruled out as the tab-switch source.
- `frontend/src/components/layout/DashboardLayout.tsx:2345,2815,3368` —
  three further independent call sites.
- `frontend/src/components/preview/PreviewPanel.tsx:880,983,1380` — version
  pin (`handleSelectVersion`), pinned-member resolution
  (`useEffect([pinnedMemberId, pinnedMemberTag])`), and the
  deliverable-resolver effect this card's sibling
  [ISS-830](20260922-2002-ISS-830.md) also names — none keyed on
  `activeTab`, so none fire simply because the user switched tabs, but all
  three are individually unguarded.
- `frontend/src/components/results/AgentThinkingTab.tsx:226,235,243` —
  THREE calls in the Steps tab alone, for a diverted-run, the run itself,
  and its parent — conditional on the run having a `parentRunId` or a live
  divert, which a large multi-revision run (like the reporter's 2.2M-token
  one) plausibly has and the smaller validation run plausibly does not.
- `frontend/src/components/results/FilesTab.tsx:517` — parent-run lookup,
  same conditional shape.
- `frontend/src/components/results/StartingPointCard.tsx:95` — root-run
  lookup for the "Starting point" card, same conditional shape.
- `frontend/src/components/history/WorkflowHistory.tsx:372,393` — two more,
  inside `WorkflowHistory`'s own static detail view (a different `mainView`
  branch, not concurrently mounted with `PreviewPanel` per ISS-800's
  finding).

`getRunFamily` (`frontend/src/lib/api.ts:1016-1024`) has the same no-dedupe
shape and 4 call sites: `page.tsx:3098,3592`,
`DashboardLayout.tsx:708`, `WorkflowHistory.tsx:416`.
[ISS-800](20260922-1633-ISS-800.md)'s validation additionally observed
`GET /api/runs/<id>/family` duplicating 2x on the Audit tab open — "not
part of the original report but visible in every attempt" — consistent
with the same unguarded-effect-plus-Strict-Mode mechanism landing on one
of these four call sites.

## Condition

Opening a large, multi-revision run (parent/root/diverted relationships
populated) from history and clicking through tabs, under `next dev`'s
default Strict Mode.

## Expected vs actual

**Expected:** `GET /api/runs/{id}` fires once per run open (at
`handleSelectWorkflowRun`), not on every subsequent tab click, and
`GET /api/runs/{id}/family` fires once.

**Actual (predicted):** on a run whose parent/root/diverted lookups are
populated, `AgentThinkingTab`'s 3 conditional `getWorkflow` calls (Steps
tab) and/or `FilesTab`'s and `StartingPointCard`'s single calls each fire,
each doubled by Strict Mode, landing on a total higher than the single
clean fetch ISS-800 observed on its smaller run — consistent with, though
not yet proven to exactly equal, the reporter's ×3.

## Why the root cause implies this

Same mechanism [ISS-800](20260922-1633-ISS-800.md) confirmed for
`AuditTab`'s four endpoints — unguarded mount effect, `next dev` Strict
Mode double-invoke, no `cachedGet()` routing — reproduces by direct reading
at every `getWorkflow`/`getRunFamily` call site above. What is NOT yet
established is which specific combination of these 8+ / 4 sites, on a run
shaped like the original reporter's, adds up to exactly 3x/2x rather than
some other multiple — that requires a live repro this analysis pass did
not run.

## What would settle it

Reproduce on a run with a real parent/root/diverted relationship
(comparable to the reporter's 2.2M-token run), with DevTools Network
reset between each tab click rather than left running for the whole
session, to attribute each `GET /api/runs/{id}` and
`GET /api/runs/{id}/family` hit to its specific triggering component.
