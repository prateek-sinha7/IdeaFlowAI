## What was wrong

`/runs/{id}/audit` reported "100 records — Governance 96, Security 4,
Activity 0" for a run whose own `GET /api/runs/{id}/gate-events` returns
`{"gate_events":[]}`. The 96 "Gate" rows were ordinary `audit_logger`
telemetry — `before_step`/`after_step`/`tool_call`/`tool_result`, always
`outcome: "continue"` — relabelled as governance checkpoints, and every one of
them expanded to byte-identical detail (`Action: allowed` / `Outcome:
continue` under the "A governance gate…" explainer). The same rows were
serialized verbatim into the CSV/JSON compliance export.

## Root cause

`frontend/src/components/results/AuditTab.tsx` — the `hooksEnv.hook_runs`
merge loop:

- **`AuditTab.tsx:568`** `deriveFineCategory("gate", hookName, step)` — every
  hook_run passed `"gate"` as its source category, and
  `deriveFineCategory` (lines 281-295) ends in
  `return source === "gate" ? "gate" : "validation"`, so any hook name that
  did not match the `/secret|credential|\bscan\b|leak/` or
  `/behavio|guideline|\bhook\b/` regexes could never reach the `"activity"`
  fine category that already exists in `FINE_CATEGORY_META` for exactly this
  lifecycle telemetry.
- **`AuditTab.tsx:574`** `category: "gate"` — hardcoded on the merged row, so
  the coarse category the exporter writes was wrong too.
- **`AuditTab.tsx:151-182`** `buildHookDetailRows` only surfaced
  `detail.detector` / `matched_keys` / `match` / `marker` / `action` /
  `reason`. The `audit_logger` payload
  (`backend/agents/capabilities/hooks/audit_logger.py:88-98`,
  `backend/agents/execution_engine/engine.py:5215-5260`) carries none of
  those — it carries `agent_name`, `tool`, `summary` — so every row fell to
  the same `Action: allowed` / `Outcome: continue` fallback.

## What changed and why there

All three defects sit on the single merge site every hook_run row routes
through, so all three ISS cards are cured by one change in one file (the
helpers are module-local; their only call site is that loop, and the two
mounts — `PreviewPanel.tsx:1341` and `WorkflowHistory.tsx:901` — render the
same component).

1. `AuditCategory` gains `"hook"` — hook_runs is its own source, alongside
   gate-events / validation-results / exec-runs.
2. `deriveFineCategory` gains `if (source === "hook") return "activity";`
   **after** the security and behavioral checks, so a `secret_scan` row still
   resolves to `"security"` and a behavioral-guideline hook still resolves to
   `"behavioral"` (Governance) — only unsignalled lifecycle telemetry falls to
   Activity.
3. The merge loop passes `"hook"` as source and sets `category: "hook"`.
4. `buildHookDetailRows` emits `Agent` / `Tool` / `Summary` rows from the
   fields the real payload already carries, so two rows with different hooks,
   tools or agents no longer expand to identical text. Nothing is fabricated —
   each row is elided when its field is absent.
5. `exportRows()` now includes `fineCategory` alongside `category`. Required
   by ISS-211: the coarse `category` alone cannot carry the distinction, since
   a `secret_scan` hook row is `category: "hook"` / `fineCategory: "security"`
   while an `audit_logger` row is `category: "hook"` /
   `fineCategory: "activity"`. The exporters themselves
   (`frontend/src/lib/exporters/auditExporter.ts`) are unchanged — they were
   already correct generic serializers, as ISS-211 concluded.

ISS-212 needed no separate change: the fetch/merge effect has one code path
for both states, so fixing it at the merge site fixes the in-progress case;
the `isRunning` prop remains presentation-only.
