## What was wrong

A `prototype_revision` chained off a real parent run (`parent_run_id` set — the
normal "revise the prototype I just built" path) applied **no edit at all**.
The run completed, the fix-loop reported nothing, and the deliverable was the
**parent's** HTML, byte-for-byte:

```
tool_result  edit_file → "Error: String not found in file: '<h1>Dashboard</h1>'"
deliverable  <!doctype html><html><body><section data-page='dashboard'>hi</section></body></html>
```

The agent asked for the string the *user's* artifact contains; by the time it
ran, the sandbox file was somebody else's.

## Root cause — `backend/agents/capabilities/context_providers/previous_run.py:308`

`PreviousRunProvider.load` is **not** invoked once per run. The engine calls it
at run entry (`engine.py:2549`, `_seed_workflow_context`) *and* again for every
agent that declares an inject, inside the generic context injector
(`engine.py:10721`, `_compose_context_message`). So its side-effecting helper
`_seed_existing_artifact` ran once per STEP.

The first invocation does two things: it seeds the message-borne artifact into
the sandbox, and it **slims `runner.user_message`** — replacing the
`=== EXISTING PROTOTYPE HTML ===` block with a one-line file pointer
(`_slim_revision_message`). That mutation is permanent and shared.

The second invocation therefore reads a message with no markers and takes the
branch written for the *Concierge* path (`previous_run.py:322`, "no HTML markers
in user_message"), reading `prototype.html` out of the **parent run's** sandbox
and writing it over the child's — after the step before it had edited that file
in place. It also overwrote the stashed `ctx.revision_original_html`, so the
single_file fallback and the `revision_validation` fix-loop were both baselined
against the wrong artifact.

Observed in the log verbatim, one step after the entry seed:

```
previous_run: seeded prototype.html from parent sandbox harness-prototype-9096f8ed
              (no HTML markers in user_message — Concierge path)
```

This only became reachable once the revision pipelines grew a second step ahead
of the writer — `prototype-revision-analyzer` as step 0 (`e0f6beeed`). With one
step there was no second `load` to clobber anything.

## The change

One guard, at the top of the single helper both `load` call sites route
through (`previous_run.py:308`):

```python
if getattr(ctx, "revision_original_html", None):
    return
```

`revision_original_html` is set by **both** seed paths (message-borne and the
Concierge parent read), so its presence is exactly "this run already has its
editable artifact" — the seed becomes once-per-run and the parent read can no
longer fire behind a step's back. Nothing else moves: the first invocation is
byte-identical, the L16 ownership gate and `allow_parent_read` verdict are
untouched, and a genuine Concierge revision (markers never present) still seeds
from the parent on its first `load`.

Not fixed here, deliberately: the parent *reference* files (`spec.md`,
`design.md`, `tasks.md`) are still re-written from the parent on every
per-agent `load`. Same repetition, different files — nothing in this defect's
witness touches them, and they are read-only reference material today. Noted on
[ISS-638](20260831-0115-ISS-638.md).

## Blast radius

Seven manifests declare `context_providers: [previous_run]` —
`prototype_revision`, `prototype_large_revision`, `prototype_feature_revision`,
`app_builder_revision`, `ppt_revision`, `user_stories_revision`,
`custom_revision`. Every one of them loses the user's edit on a chained run
once it has a step ahead of its writer, which is why the guard belongs in the
provider and not in any one workflow.
