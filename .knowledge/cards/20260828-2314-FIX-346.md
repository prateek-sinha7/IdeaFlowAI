## What was wrong

On `/create/app` (and every other panel `IdeaInputPage` serves), checking an agent in the
top-level "Review gates" checklist updated that control's own pill — "Review gates — 1 agent
pause for review" — but the SAME agent's `Gate` combobox in the Advanced modal's per-agent
Config tab still read "No gate", in one page session with no save or submit between them
([ISS-247](20260828-1637-ISS-247.md), CONFIRMED 3/3 from a cold load).

## Root cause

Two disjoint stores backed "does this step pause for human review", with no path between them:

- `frontend/src/components/workflow/ReviewGatesSection.tsx:88-96` (`toggle`) wrote a local
  `checkedIds: Set<string>` and reported it upward through `onChange(ids, touched)`, which each
  caller parked in a ref (`IdeaInputPage.tsx:936-948`, `LaunchWizard.tsx:242-243`) read only at
  submit time as the top-level `gate_agent_ids` launch field.
- `frontend/src/components/workflow/composer/CanvasConfigRail.tsx:248-276` derives its `Gate`
  combobox from `sel.gates ?? []` and writes back through `patch()` → `onSelection(agent.id,
  next)` into the per-step `selections` map.

The structural half — the reason a one-line "also write the gate" would not have worked — is
that **`AgentsPopup` owned that selections map privately**: `AgentsPopup.tsx:2242` seeded
`liveSelections` in a `useState` INITIALIZER (mount-once, deliberately, which is why
`IdeaInputPage` keys the popup on whether the manifest fetch has landed). The popup is rendered
unconditionally and mounts with the page, so nothing that happened afterwards outside the modal
could reach the map the modal renders from.

## What changed and why there

Frontend only — the backend already honours both mechanisms and dedupes them (below). Four
files, one mechanism: the map moves up to the page, and the shared checklist writes into it.

- **`ReviewGatesSection.tsx`** — the shared component both launch panels route through, so the
  fix lands once for both. Two optional props (`selections`, `onSelectionsChange`) and a pure
  `withHumanGate()` helper; `toggle` now also emits `selections[id].gates` with `human`
  added/removed. Only `human` is filtered out and re-added, so `validation` (owned by the
  Validator lever), `conditional` and `before-human` are carried through untouched, and an
  emptied step is deleted from the map — the same rule `AgentsPopup.handleCanvasSelection`
  applies. The local `checkedIds` seed and the `onChange(ids, touched)` contract are UNCHANGED:
  they are what keeps `gate_agent_ids` byte-identical on an untouched run, and the 12 existing
  tests in `ReviewGatesSection.test.tsx` assert exactly that seeding behaviour.
- **`AgentsPopup.tsx`** — new optional `selections` prop; `liveSelections` is now
  `controlledSelections ?? ownSelections`. Four lines. Absent ⇒ the popup keeps its own
  mount-once copy, so `AgentsPopup.reskin.test.tsx` and any other uncontrolled mount are
  unaffected.
- **`IdeaInputPage.tsx`** — holds the live map as state seeded exactly where the popup's private
  seed came from (`cleanSelections`, plus a `useEffect` folding `manifestSelections` in UNDER it
  when the fetch lands, the same precedence `mergedInitialSelections` had). `handleSelectionsChange`
  — already the single writer the popup reported through — now writes the ref AND the state.
  `selectionsRef` stays the launch-payload source untouched, so an untouched run still omits
  `selections` (INV-3).
- **`LaunchWizard.tsx`** — same lift for the ppt/prototype panels
  ([ISS-361](20260828-2120-ISS-361.md)). Here the popup seeded from `selectionsRef.current`
  directly, so every one of the six writers (draft restore, saved-workflow projection, both
  override-toggle branches, the deliverable-family reset) now routes through
  `handleSelectionsChange`, which was moved up beside the state it owns. The ref and the
  rendered map can no longer drift.

**Why sending both is safe.** A step selected by `gate_agent_ids` AND declaring `gates:[human]`
does not double-prompt: `backend/agents/execution_engine/engine.py:6382-6405` (WR-02) skips the
declared `human` gate whenever the inline `_should_gate` path fires for that step — they share
one `gate_key` (`f"{run}:{agent_id}:{visit_count}"`, no gate name in it) and the engine already
guards it. That check is what made writing into `selections` the right store rather than a
second pause.

## Known flake in the verification test (test-side, not the fix)

`test_checking_a_review_gate_sets_that_agents_gate_in_the_advanced_modal` reads
`gate.input_value()` immediately after `expect(gate).to_be_visible()`. The `<select>` renders as
soon as the Config tab opens, but its `chosenGate` is derived from `gateOptions`, which
`useAgentCapabilities` fetches from `/api/capabilities`
(`CanvasConfigRail.tsx:118,250-253` — `gateChoices` is `[]` until it lands, so `chosenGate`
falls back to `""`). Under suite load the read beats the fetch and the assertion sees `""`.

Evidence this is a read race and not the fix: the failure screenshot that run wrote —
`tests/integration/test-runs/2026-08-28T23-05-fix-iss-247-regress4/03-launch_panels/UNMARKED-checking-a-review-gate-sets-that-agents-gate-in-the-advanced-modal/03-advanced-config-FAILED.png`
— shows Gate = **"Human gate"** for Domain Discovery Agent, taken milliseconds after the
assertion raised. Standalone the test XPASSes 6/6.

The test was NOT edited: `expect(gate).not_to_have_value("")` (auto-waiting) instead of the bare
`input_value()` read would settle it, but that is the verifier's call, not a change to make
while proving a fix.

## Not covered here

[ISS-362](20260828-2121-ISS-362.md) — the INVERSE direction — is untouched and stays open.
Setting `Gate: Human gate` in the Advanced modal still does not tick the Review-gates checklist,
because the checklist's own `checkedIds` remains seeded from `AgentDef.gate === "Human_Gate"`
rather than derived from `selections[id].gates`. Deriving it is the one-store end state, but it
would change the untouched-default seeding that `ReviewGatesSection.test.tsx` pins and that
`gate_agent_ids`' `touched` contract depends on — a design decision, not this fix.

[ISS-361](20260828-2120-ISS-361.md) (the LaunchWizard/ppt/prototype path) IS carried by this
change — the same shared component, the same lift — but it was an INFERRED card with
`verification: manual, not_run` and no test, and nobody drove `/create/ppt` or
`/create/prototype` through the checklist here. It is left open pending that manual check.
