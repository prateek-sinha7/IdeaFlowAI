# ISS-876

**Register source:** `QA-KB-021` in root `LEDGER.md` / `BUGS.md` (sibling, derived during its analysis on 2026-10-01).
**Root card:** [ISS-682](20260904-ISS-682.md) holds the root cause and the fix location.

**Claim status: INFERRED end to end; the payload gap is CONFIRMED by reading.** No copy has been saved and re-launched
to watch the budget trip.

## Why the root cause implies this

The agreed minimal fix for QA-KB-021 adds `manifest` to the two row-backed seeds in `page.tsx` and deliberately leaves
the built-in canvas seed alone ("copy-only"). That is right about identity: a built-in has no `WorkflowDefinition`
row, so the seed must carry no `id` ([ADR-0014](20260824-1630-ADR-0014.md) locked constraint). But the same seed
also carries no `manifest`, and unlike the row-backed seeds it cannot get one, because the payload it is built from has
no source for the top-level keys. It is the same loss class one level over: Save rebuilds `manifest_json` from Composer
state plus a passthrough source, and for the built-in canvas that source is `undefined` by construction.

- `frontend/src/app/[...view]/page.tsx:521-552` seeds `agentIds`, `manifestSteps: detail.manifest_steps`, and a
  `runConfig` mapped from the payload's `deliverable` / `planner` / `clarify_*` ([FIX-325](20260828-1645-FIX-325.md)
  added exactly that mapping). Nothing else.
- `WorkflowDetail` (`backend/app/api/workflows.py:226-254`) declares id, name, description, planner, clarify_mode,
  clarify_defaults, context_providers, deliverable, steps, manifest_steps and the override flags. It has no `limits`,
  `input_providers`, `seed_files` or `capabilities`. The handler already loads the whole manifest
  (`manifest = load_manifest(workflow_id, _WORKFLOWS_DIR)`, `:471-474`) but projects only its name, description and
  steps.
- Save on a built-in canvas always sends a full manifest (`ComposerPage.tsx:897-903`:
  `needsFullManifestOnSave(pipelineAgents, runConfig, builtinCanvasType, initialManifestSteps)` is true on
  `!!builtinCanvasType`, then `buildWorkflowManifest(..., initialManifest)` with `initialManifest` undefined), so the
  copy persists steps plus run config and nothing else.

Built-ins that declare top-level keys a copy would lose:

| built-in | key | where |
|---|---|---|
| prototype_v2 | `limits: {max_subagents: 200, max_depth: 2, wall_clock_seconds: 10800}` | `backend/agents/workflows/prototype_v2/workflow.yaml:32-35` |
| backlog | the same `limits` block | `backend/agents/workflows/backlog/workflow.yaml:84-87` |
| prototype | `input_providers: [run_images]` | `backend/agents/workflows/prototype/workflow.yaml:50-51` |

## Consequence (each hop read, none run)

The copy is a db row and launches at `trust="db"`, which is trusted since [ADR-0039](20260904-1424-ADR-0039.md)
(`compiler.py:228` `_TRUSTED_SOURCES = {"file", "builtin", "db"}`). With no `limits` it compiles to `Limits()` and the
budget falls back to `DEFAULT_MAX_SUBAGENTS = 8`, `DEFAULT_WALL_CLOCK_SECONDS = 900`
(`backend/agents/execution_engine/budget.py:43-46`, `:92-106`); a fan-out past eight raises
`BudgetExceeded("subagents")` (`budget.py:194-200`). That is the failure ADR-0039 exists to remove: "a
`wave_scheduler` build charging one subagent per task dies at task 9 under the untrusted ceiling, mid-run, with
earlier waves already written to disk". ADR-0039 lets a db row declare a raised ceiling; this path can never carry one
over from the built-in it was copied from. Losing `input_providers: [run_images]` likewise drops the image provider
from a copy of `prototype`.

## Where the fix would belong

Not in `page.tsx` alone — the data is not in the payload. Expose the manifest's non-step top-level keys on
`WorkflowDetail` (the handler has the parsed manifest in hand already), then have the `page.tsx:521` seed pass them as
`manifest` — still without `id`. When a per-user override is in force (`workflows.py:535-539` serves the override's
steps), the top-level keys still come from the file manifest, because an override only replaces `steps`
(`backend/app/api/_workflow_override.py:104-121`, `merge_override_steps`).

Open product question for whoever picks this up: should a copy of a built-in inherit its `limits` and
`input_providers`? ADR-0014 calls the surface "explore-and-fork", which reads as yes, but no card decides it. This card
is not escalated because the claim is still INFERRED.

## What would settle it

Static (done): `WorkflowDetail` has no such fields. End to end: open `/workflows/prototype_v2/canvas`, Save as copy,
then `GET /api/user-workflows/{id}` — the manifest should lack `limits`. Test: a backend test that
`GET /api/workflows/prototype_v2` carries the top-level keys, then a `page.tsx` source assertion that the canvas seed
passes `manifest` and still no `id`.

## Test (2026-10-01)

No test written. The fix is a design change (a backend payload change so GET /api/workflows/{id} exposes limits/input_providers, plus a canvas seed carrying them without an id per ADR-0014); there is no offline assertion until that contract is chosen.

## Fix phase (2026-10-01): not fixed, left open

[FIX-677](20261001-2119-FIX-677.md) fixed [ISS-682](20260904-ISS-682.md) and [ISS-875](20261001-2110-ISS-875.md)
but did not touch this card on purpose. The built-in canvas seed (`page.tsx:521`) still carries no `manifest` and no
`id`. The data is not in the payload: `WorkflowDetail` has no top-level keys. Fixing it needs a backend payload
change, plus a product answer to whether a copy of a built-in inherits `limits` and `input_providers`. Status stays
`open`.
