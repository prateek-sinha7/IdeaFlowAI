# ISS-1131

**Register source:** sibling derived during the `QA-KB-104` analysis on 2026-10-08 (root [ISS-1117](20261008-1444-ISS-1117.md)). Not its own bug row.

**Confidence:** every link below is CONFIRMED (a code read, or an offline probe with the run core stubbed). The whole chain is INFERRED, because no run was launched
(a run costs money and this line may not start one). What would settle it: one live run of a basic-tier row whose conditional gate answers the diverting outcome,
then `GET /api/runs/{id}` for `diverted_to_workflow` and a child run of the enterprise-only pipeline; or a scripted-model engine test that does the same.

## Condition

`can_run_pipeline` is a call placed by hand at each door that starts a run by pipeline name: `launch_run` (`run_commands.py:3469`, through
`_require_tier_entitlement`), resume (`:700`), revision (`:4671`) and `create_user_workflow` (`user_workflows.py:740`). The cross-workflow trigger (spec 014 R-12)
is one more door that starts a run by pipeline name, and it has no gate:

1. A saved row may carry a conditional gate whose outcome is `trigger: workflow` with a `target`. The compiler accepts any target other than `self` "as a SYNTACTIC
   reference only" (`compiler.py:1763-1788`). A save compiles at `trust="db"` (`user_workflows.py:117`), where every registered capability is allowed.
2. At the gate the engine calls `ectx.runner.run_trigger_workflow(step, ectx, workflow_ref=_route_target, ...)` (`engine.py:7170`, `:7186-7191`).
3. For a name in `SUPPORTED_PIPELINE_TYPES` that has a `workflow.yaml` (`_is_file_backed_workflow`, `kernel_services.py:70-93`), `run_trigger_workflow` sets
   `target_pipeline_type = workflow_ref` (`:1597`) and calls `_launch_run_core(... pipeline_type=target_pipeline_type ...)` with `user=SimpleNamespace(id=ectx.owner_id)`
   (`:1668-1698`). The only identity on this path is the owner id. There is no `Principal`, so there is no `effective_tier` to read.
4. `_launch_run_core` (`run_commands.py:2879-3253`) mentions no tier at all (0 matches for "tier" in those lines), and nothing in `backend/agents/` calls
   `can_run_pipeline`. `_launch_run_core` has exactly two callers: `launch_run` (`:3842`, gated at `:3469`) and this one.

The user controls every input: the row's prompts (a prompt that asks the gate step to answer `{"decision": "spanish"}` makes the outcome near-deterministic),
the outcome's `target`, and the row's `base_pipeline_type` (any type the tier may run, for example `ppt`).

## Evidence

`evidence/qa-kb-104/analysis-05-probe-workflow-trigger-door-no-tier-check.txt` (probe `analysis-plugins/test_probe_sync_entitlement.py::test_probe_E_workflow_trigger_door`,
in-memory SQLite, `_launch_run_core` stubbed so nothing is minted). For each target in `app_builder` (pro-only), `sample_subagents_parallel` and `custom` (both enterprise-only):

- a BASIC caller's `POST /api/user-workflows` (`base_pipeline_type: ppt`, a manifest whose gate has `trigger: workflow, target: <T>`) answers **201**;
  `can_run_pipeline("basic", T)` is `False`;
- `KernelServices.run_trigger_workflow(workflow_ref=T)` reaches `_launch_run_core` with `pipeline_type=T` and `user={'id': 'owner'}`.

Control from the root's probe C (`analysis-02`): the same caller launching `T` directly through `POST /api/runs` is refused, **403 `tier_not_entitled`**, and never reaches the mint.

## Expected vs actual

Expected: a pipeline the owner's tier may not run cannot be started by a workflow the owner saved, whichever door starts it; the save or the launch of the row is
refused, the way `launch_run` refuses the same pipeline. Actual: save 201, and the trigger mints the run.

## Why the root cause implies it

[ISS-1117](20261008-1444-ISS-1117.md) is a pipeline name reaching an action with no entitlement call because the gate was placed per door and this door never got one.
The trigger is the same shape with a more direct effect (it runs the pipeline rather than storing a copy). The domain card already records the class: "A new launch
endpoint that never calls `can_run_pipeline`. Nothing fails ... There is no CI gate, no import-linter contract and no test that asserts every launch path checks
entitlement" (`DOMAIN-auth-and-entitlements`, "What breaks if you get it wrong"). [ISS-055](20260812-0036-ISS-055.md) and [FIX-189](20260806-1335-FIX-189.md) are the earlier
two instances (launch, then resume and revision). [ISS-946](20261002-0107-ISS-946.md) found the same path missing the MODEL gate and stopped on the same blocker (no
principal inside a running run); this card is the pipeline half of that finding.

## Fix direction (INFERRED, not applied)

A `trigger: workflow` target is a static string in the manifest, so it can be checked where a principal exists and no tier needs to travel into the kernel:

- **Launch edge.** In `launch_run` Case 3, after `_WORKFLOW_COMPILER.compile`, walk `compiled.steps[*].route.outcomes[*]` for `trigger == "workflow"` targets that are
  file-backed pipelines and refuse (403, `tier_not_entitled`) when `can_run_pipeline(effective_tier(...), target)` is false. This also catches a row saved before the fix and
  an owner downgraded after saving. Resume replays the persisted manifest, so it needs the same walk.
- **Save edge.** `create_user_workflow`, the manifest branch of `update_user_workflow` and `sync-from-file` run the same walk before storing.
- One walker beside `_model_entitlement_error` (`run_engine.py:609`, same `(status, message) | None` shape), called from the three places, rather than three copies.
- The other route is [ISS-946](20261002-0107-ISS-946.md)'s: persist the launch tier on the run and gate inside `_launch_run_core`, which covers both mint doors at one point.
  It needs a new column or an `ExecutionContext` field (migrations are additive only) and a decision on the tier source; the edge walk needs neither.

Traps:

- The kernel (`backend/agents/`) must not gain an `app.*` import for this (import-linter "kernel imports only capability ports"; `lint-imports` was 3 kept / 2 broken at
  `d284eb258`, the 2 pre-existing). The edge walk lives in `app/api/`.
- No `if target == "<name>"` anywhere: the check is a `can_run_pipeline` table lookup, so INV-1 / SC-001 hold.
- Targets that are a saved `user_workflow_id` are resolved by `_owned` at trigger time (`kernel_services.py:1603-1646`). They are the owner's own rows, gated by their own base
  type at their own save; their content is [ISS-1114](20261008-1415-ISS-1114.md)'s question.
- An engineer-authored file workflow that triggers another file workflow (`ex_A3_divert` to `ex_A3_b_spanish`) must keep working: both are enterprise-only
  (`entitlements.py:82-83`), and the walk runs only against a saved row or an inline manifest (launch Case 3), never against a file plan (Case 1).

Test shape for the 4-test-writer (offline; harness of `test_iss1112_override_writers_trust.py` plus the `_get_db` and `_launch_run_core` patches of `analysis-05`): (1) basic
`POST /api/user-workflows` with a trigger to `app_builder` expects 403 (201 today); (2) a row stored through the ORM with the same manifest, launched by `user_workflow_id` as basic,
expects a refusal with `_launch_run_core` not reached (reached today); controls: target `self`, and target `ppt` for basic, still save and launch. The live divert is not
testable offline.
