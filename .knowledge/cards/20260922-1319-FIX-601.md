# FIX-601

Fixes **QA-PS-030** (root) and **QA-PS-031** (duplicate) — `LEDGER.md` / `BUGS.md`.

## What was wrong

Selecting any non-latest version of a PPT family rendered v1's deck. `ref=v2` and `ref=v3`
returned **200** with v1's bytes because that is genuinely what the tag holds: on the Arctic
family (`e53d9b1f` v1 → `f7000bbd` v2 → `dfeb5949` v3) `git log -- presentation.html` shows
exactly ONE commit (`98d9aa9 step: ppt-composer`), and every revision commit touched only
`.chain/logs.jsonl`, `.chain/presentation.pptx`, `.chain/summary.md`. The Postgres `output`
column was correct per run, which is why "Latest (live)" looked right and every `ref=vN` did not.

This is the exact inversion of the design contract recorded in `FIX-STATE.md`
("DESIGN INTENT FROM BILAL"): the canonical deliverable at the sandbox ROOT is the real
artifact and every revision must rewrite it; `.chain/` is a final copy step, never the target.

## Root cause — THREE mechanisms, all required

[ISS-727](20260922-1235-ISS-727.md) and [ISS-723](20260922-1245-ISS-723.md) independently
identified (1) and (3). Mechanism (2) is a **correction** both cards got wrong, found while
fixing and proved below.

**1. The prompt never asked for a write.**
`backend/agents/prompts/ppt-revision-agent/AGENT.md` (pre-fix) — the entire output contract was
*"Emit the complete modified HTML file wrapped in `<artifact>` tags … Nothing after
`</artifact>`."* It also told the agent to `read_file("presentation.pptx")`, a file that has
never existed at the sandbox root. The model complied with what it was asked and touched no file.

**2. CORRECTION to ISS-727/ISS-723: the agent did NOT have write tools at runtime.**
Both cards concluded from `agents/factory.py:1306-1352` (the R-22/D-07 empty-tool-set rule) that
`tools: []` still binds native `write_file`/`edit_file`, so this was "a prompt gap, not a
tool-binding one". That is true only at the factory layer. A step that declares no `tools:` block
compiles to the §8 least-privilege default (`compiler.py:1488-1489` →
`ToolPermissions()`, `workflows/plan.py:66` `write_files: bool = False`), and
`denied_tools()` (`workflows/permission_caps.py:134`) then excludes those tools inside
`DeepAgentRunner` (`app/agents/deep_agent_runner.py:783-784`). Measured on the compiled manifest:

```
BEFORE fix, denied: ['edit_file', 'execute', 'write_file']
AFTER  fix, denied: ['execute']
```

So the prompt fix alone would have produced a run of failed tool calls. Both changes are load-bearing.

**3. `deliverable.strategy: ppt` resolves from the stream, not the disk.**
`agents/capabilities/deliverables/ppt.py::PptResolver.resolve` returns
`unwrap_artifact(…(ctx.last_streamed))`, and `engine.py:1364-1392`'s materialization fallback
writes that text only into `.chain.staging-<run>/` → `.chain/`, under the declared
`presentation.pptx` — a name nothing at the sandbox root has ever carried. Fixing (1) and (2)
alone would have been **actively harmful**: the agent's stream becomes a one-line summary, so
`WorkflowRun.output` (the one surface that is correct today) would have become that summary.

## What changed, and why there

**`backend/agents/workflows/ppt_revision/workflow.yaml`**
- `deliverable.strategy: ppt` → `single_file`; `name: presentation.pptx` → `presentation.html`.
  `SingleFileResolver.resolve` (`capabilities/deliverables/single_file.py`) reads the named file
  off the sandbox, so the file the agent edits is what becomes `final_output`, what
  `build_flat_payload` copies into `.chain/` (a real `shutil.copy2` of the root file — the copy
  step Bilal's contract asks for), and what the per-step `git add -A`
  (`engine.py:6141-6148`) stages before `create_tag(f"v{n}")`.
- Step `ppt-revision-agent` gains `tools: {read_files: true, write_files: true}`.

Both mirror `backend/agents/workflows/prototype_revision/workflow.yaml` (step 1) and
`ppt_v2`'s manifest, the two working precedents for an in-place revision.

**`backend/agents/prompts/ppt-revision-agent/AGENT.md`** — output contract rewritten from
"emit an `<artifact>` block" to read `presentation.html`, `edit_file` it in place, re-read to
confirm the document is intact, and "Do **not** paste the HTML into your reply". `write_file` is
explicitly forbidden on that path: the file already exists in the shared family sandbox and
deepagents' `FilesystemBackend` does not overwrite (`backend/CLAUDE.md:185`) — the exact silent
no-op [FIX-111](20260724-FIX-111.md) already shipped once. The stale
`read_file("presentation.pptx")` instruction is corrected in the same pass.

**Test harness (`_scripted_model.py` + two derivations)** — the scripted `ppt-revision-agent`
turn encoded the OLD contract (`"Revised per instruction.\n<artifact>{deck}</artifact>"`) and two
test modules DERIVED their expected bytes by splitting that string on `<artifact>`. The turn now
streams narration plus a `write_file("presentation.html", …)` tool call, the same shape
`prototype-build` already uses in that file, and both modules derive the expected deck from the
tool-call args. **The assertions are byte-unchanged** (`final_output == EXPECTED_…_REVISED_DECK`)
— only the simulated agent behaviour moved, to the behaviour the cards prescribe. That assertion
is now the end-to-end proof: `final_output` equals the bytes the agent WROTE.

## Deliberately NOT changed

- **Base `ppt`** keeps `strategy: ppt` / `name: presentation.pptx`. It is pinned literally by
  `tests/unit/test_ppt_v2_manifest.py::test_ppt_is_byte_identical_to_its_own_manifest`
  ("ppt must not have moved"), by `test_workflow_override_e2e.py:110`, and by comments in
  `AgentsPopup.tsx:81` / `PreviewPanel.tsx:1217`. Its v1 root file is already correct — the
  staleness is purely a revision defect. `resolveRunDeliverable`
  (`frontend/src/lib/api.ts:1183-1200`) already resolves a declared `.pptx` to the sibling
  `presentation.html`, so a family whose v1 declares `.pptx` and whose v2+ declare `.html`
  resolves to the same file either way — no frontend change was needed. The remaining
  base-`ppt` half of the naming split stays with [ISS-651](20260917-1200-ISS-651.md).
- **`payload_allowlist`** (`app/agents/sandbox.py:268-291`) — untouched. The root write is
  captured by the per-STEP `git add -A`, exactly as [ISS-723](20260922-1245-ISS-723.md)'s Layer-1
  analysis predicted; its reviewed 3-path boundary was never widened.
- **`revises_existing`** stays `false`. Flipping it would seed the parent artifact and slim the
  message, but `tests/agents/test_revision_gating.py` asserts exactly one in-place revision
  (WR-04) — a classification change beyond this defect. Not needed: the family shares one
  sandbox, so `presentation.html` is already on disk, and the frontend still pastes the deck
  into the revision message (`DashboardLayout.tsx:1211`).

## Residual risk

This is a prompt change, so compliance is probabilistic. If the model does not call `edit_file`,
`SingleFileResolver` step (1) reads the file that IS on disk — the previous version's deck — so
the failure mode is "the revision silently does nothing" rather than "raw `<artifact>` text in
the deliverable". That is the same exposure `prototype_revision` has carried in production, and
it is strictly better than the pre-fix state, where that outcome was guaranteed. Also note the
`_deliv_strategy == "ppt"` mid-stream carousel sanitize (`engine.py:9607`) no longer fires for
this pipeline — matching `ppt_v2`/`prototype_revision`, which have never needed it because
`edit_file` mutates an already-sanitized deck.

## How to verify for real

A fresh `ppt_revision` run on an existing family should produce, in the family sandbox:

1. `git log -- presentation.html` gains a **second** commit (`step: ppt-revision-agent`), not
   just the original `ppt-composer` one.
2. `git show v<new>:presentation.html` differs from `git show v1:presentation.html` and carries
   the requested change.
3. `.chain/presentation.html` (note: `.html`, not `.pptx`) byte-equals the root file.
4. `workflow_runs.deliverable_filename` for the new run reads `presentation.html`.
5. `GET /api/runs/{root}/sandbox/file?path=presentation.html&ref=v<new>` renders the new deck,
   and `ref=v1` still renders v1 — i.e. the version selector finally distinguishes them.
6. `WorkflowRun.output` still holds the revised deck (the "Latest (live)" path must not regress).

**A backend restart is required before any of this**: `compile_for_run` is `lru_cache`d, so the
manifest change is invisible to a running process.
