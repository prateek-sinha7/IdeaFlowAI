# ISS-607

**BUG-ID:** BUG-20260829-140111-runs-id-steps-agent

## Reproduction (3/3, cold start each cycle — CONFIRMED on cycle 1, no narrowing needed)

Live pair: root run `636ff908-21d6-4c3a-9f00-0ea4f08060fc` (v1, 7 base agents incl.
"Documentation Agent") / revision run `2ac66bbd-8d76-4d59-9580-a29b1a4f6e74` (v2, 1 agent
"Backlog Revision Agent").

1. **Cycle 1** — cold nav `/dashboard` -> `page.goto` fresh to
   `http://localhost:3000/runs/636ff908-21d6-4c3a-9f00-0ea4f08060fc/steps` (base, unversioned
   route — what "Back to history" and every run-card link land on). Picker button read
   "Version v1". Opened the picker, clicked the "Version v2" option. Result: `window.location`
   unchanged (still `.../steps`, no `/versions/2` segment), picker button still reads
   "Version v1", agent list still v1's 7 base agents. 0 console errors/warnings, no network
   request for the revision run id.
2. **Cycle 2** — fresh cold nav `/dashboard` -> same base steps URL. Repeated the picker click.
   Identical no-op result.
3. **Cycle 3** — fresh cold nav `/dashboard` -> same base steps URL. Used the chat transcript's
   "Answer in Steps" button on the "Revision started" entry (`chat-result-card-link` testid)
   instead of the picker. Identical no-op: URL unchanged, picker still "Version v1", content
   unchanged.
4. **Contrast** — `page.goto` directly to the revision's own run id
   (`/runs/2ac66bbd-8d76-4d59-9580-a29b1a4f6e74/steps`) renders "Backlog Revision Agent"
   correctly with populated Reasoning / Full input prompt / Agent output / Context received —
   proves the revision's own data and `AgentDetailPanel` are fine; the defect is purely in
   reaching it from the root run's base Steps route.

## Page / route / component

- Page: Run detail — Steps tab.
- Route: `/runs/{rootRunId}/steps` (base, unversioned route).
- Components: `PreviewPanel.handleSelectVersion`
  (`frontend/src/components/preview/PreviewPanel.tsx:550-593`),
  `DashboardLayout.handlePreviewPanelTabSelect`

## Root cause (traced by code reading — two independent defects, both matching this BUG-ID)

**1. Version-picker no-op.** `PreviewPanel.tsx:550-551`:

```
const latestId = sortedMembers[sortedMembers.length - 1].id;   // newest family member — v2
const activeRunId = viewingVersion?.id ?? liveRunId ?? latestId;
```

On the base `/steps` route, `liveRunId` (passed down as `contentSourceRunId`, the ROOT run id,
v1) wins over `latestId`, so the panel actually renders v1 — but `latestId` is independently
computed as the newest member, v2. `handleSelectVersion` (`PreviewPanel.tsx:570-593`), on
selecting v2:

```
const memberIdx = sortedMembers.findIndex((m) => m.id === memberId);
onTabSelect?.(activeTab, memberId === latestId || memberIdx < 0 ? null : String(memberIdx + 1));
if (memberId === latestId) { setViewingVersion(null); return; }
```

Because the clicked v2's id equals `latestId`, the code treats the click as the "already on
latest, back-to-live" shortcut and passes `null` for the version pin instead of pinning v2. In
`DashboardLayout.handlePreviewPanelTabSelect` (`DashboardLayout.tsx:486-501`),
`pin = version === undefined ? pinnedVersion : (version ?? undefined)` resolves to `undefined`
for the explicit `null`, so `targetRoute = routes.runSteps(contentSourceRunId, undefined) =
"/runs/{id}/steps"` — identical to `window.location.pathname` — and the early-return guard
(`if (!targetRoute || targetRoute === window.location.pathname) return;`) fires, so
`window.history.pushState` never runs. `setViewingVersion(null)` leaves `activeRunId` still
resolving to `liveRunId` (v1). Net effect: `latestId` (newest family member) and the actually
*displayed* "live" run (the root run id) are two different things whenever a base Steps route
is showing the root instead of the family's newest member, and the `memberId === latestId`
equality check conflates them — so selecting the newest revision is silently swallowed as a
no-op.

**2. Chat "Answer in Steps" / "Open in Steps" no-op.** `ResultCard.tsx`
`onClick={() => onRequestOpenTab(tab)}` (lines 164, 175, 207) only ever passes a generic tab id
(`"thinking"`). There is no run-id or version parameter anywhere in this deep-link seam
(`onRequestOpenTab: (tab: string) => void`, `DashboardLayout.tsx:301`). Since the base Steps
route is already showing the "thinking" tab, requesting the same tab again is an inherent no-op
regardless of which run/revision the chat message actually refers to — the mechanism has no way
to target a different run in the family at all, only to switch tabs within whichever run is
currently mounted.

## Expected vs Actual

**Expected:** from the root run's base Steps URL, both the version picker's "Version v2" option
and the chat's "Answer in Steps" link on "Revision started" should navigate to (or otherwise
render) the revision's own Steps content, including its distinct agent list ("Backlog Revision
Agent"), matching what a direct `page.goto` to the revision's own run id already shows.

**Actual:** both affordances are silent no-ops from the base route — no URL change, no content
change, no console error, no network request for the revision run id. The revision's agent list
and populated Input/Output/Context panels are reachable only by knowing and directly navigating
to the revision's own run id, which no visible UI control exposes from the base Steps view.
