# ISS-1165

**Register source:** sibling derived during the `QA-KB-126` analysis on 2026-10-09 (root [ISS-1114](20261008-1415-ISS-1114.md)). Not its own bug row.

**Confidence:** INFERRED. The persisted trust is CONFIRMED by reading and by the launch probe (`evidence/qa-kb-126/analysis-01-probe-db-trust-doors-by-tier.txt`, block `[L]`: a basic launch hands the mint `manifest_json._trust == 'db'`). The resume recompile was read, not driven. What would settle it: call `ExecutionEngine.resume_run` offline, model stubbed, on a failed run row whose `manifest_json` is `{"steps": [<exec step>], "_trust": "db"}` with a basic owner, and read `resumed_compiled.steps[0].tools.exec`.

## Condition

`launch_run` Case 3 persists the trust it compiled with: `persisted_manifest["_trust"] = _trust` (`run_commands.py:3430-3431`), and `_trust` is `db` for any saved row that is not an override. The resume drivers read it back and recompile at it: `resume_run` (`engine.py:15698-15706`) and `_replay_clarify_run` (`engine.py:16257-16265`), `_trust = _mf.pop("_trust", "user") or "user"`. The resume endpoint's gates are `_require_tier_entitlement(wr.type)` (`run_commands.py:701`) and the trigger walker (`:702-709`); neither looks at `_trust`. A run is resumable when it is failed, degraded or cancelled (`:685-688`).

## Expected vs actual

Expected: a resume never runs with more privilege than a fresh launch by the same caller would get today. Actual: it runs with the privilege the launch had when the run began.

## Why the root cause implies it

[ISS-1114](20261008-1415-ISS-1114.md) is a trust decision taken at compile time with no tier. `_trust` on the run row is that decision frozen. After the root is fixed every new launch by a lower tier persists `user`, but a run persisted under the old rule keeps `db`, and the rule that protects it (the compile trust) is the one the fix changes only for new decisions. The population shrinks as old runs age out, which is why the severity is low.

## Fix direction (INFERRED, not applied)

Decide whether to grandfather or clamp, and say so in the root's change. To clamp, the resume endpoint holds the principal, so it can compare the persisted `_trust` with the answer of the root's shared helper for this caller and refuse (or lower it) before the engine re-reads the row. `_trust` is absent for every file-pipeline run and defaults to `user`, which is already fail-closed.

## Test notes

Offline, no live run: a `WorkflowRun` row with `status='failed'` and the manifest above, owner basic, `POST /api/runs/{id}/resume` with the engine singleton stubbed (harness of `evidence/qa-kb-104/fix-plugins/test_probe_fix_doors.py::test_R_resume`) shows the endpoint's gates; the recompile needs the real `resume_run` with a scripted model.

## Resolution ([FIX-776](20261009-1628-FIX-776.md), 2026-10-09)

Decided: clamp at the user's door, grandfather in-flight runs. `resume_run_endpoint` refuses (403 `tier_not_entitled`, before the status
flip and the queue registration) a run whose persisted `_trust` is `db` when `_saved_row_trust(effective_tier(current_user, principal))`
gives this caller `user`. New launches persist the tier-based answer, so the population only shrinks. The startup re-arm paths (`resume_run`
on a review re-entry, `_replay_clarify_run`) hold no principal and keep the trust a run already had: a restart is not a new grant. The dev DB
has no run carrying `_trust` (`evidence/qa-kb-126/fix-04-dev-db-readonly-queries.txt`). Observed: basic resume of a `_trust="db"` run 403,
status stays `failed`; basic `_trust="user"` / none and enterprise `_trust="db"` 200 (`fix-01` `[R]`). The test file above was red on a HEAD
copy (`200 == 403`) and is green with the change.
