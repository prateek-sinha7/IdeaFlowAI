## Why QA-PS-006's root cause implies this

ISS-653's confirmed mechanism is that `ResultCard.tsx`'s gate ternary
(`frontend/src/components/chat/ResultCard.tsx:140-145`) recognizes exactly TWO
states for a gate card, keyed only on the boolean `message.resolved`:

```tsx
// frontend/src/components/chat/ResultCard.tsx:140-145
const inlineText =
  kind === "gate" && message.resolved
    ? "Review approved — build continues"
    : kind === "gate"
    ? "Review required"
    : message.content;
```

There is no third rendering for "the gate was never actually approved, but the run
ended anyway" (rejected, crashed, diverted). Whether a gate card shows the approved
text depends entirely on how `resolved` gets set to `true` — and one of the two
places that happens conflates "the run reached ANY terminal status" with "this gate
was approved":

```ts
// frontend/src/hooks/useRunChat.ts:735-746
// Auto-resolve all gate cards when seeding a completed/terminal run.
// A gate in a completed run was necessarily approved — there is no pending
// review box to show. This covers history-reopen and family-seed paths
// where review_gate_approved may not be in the durable event log.
// Generic — keyed on cardKind, never on workflow/agent name (SC-001).
if (isTerminalRun) {
  setMessages((prev) =>
    prev.map((m) =>
      (m.cardKind === "gate" || m.cardKind === "clarify") && !m.resolved ? { ...m, resolved: true } : m
    )
  );
}
```

The comment's own premise — "a gate in a completed run was necessarily approved" —
is true for `completed`, but the caller passes `isTerminalRun` for four OTHER
statuses too:

```ts
// frontend/src/app/[...view]/page.tsx:86
const REOPEN_TERMINAL_STATUSES = new Set(["completed", "failed", "cancelled", "degraded", "diverted"]);
```

```ts
// frontend/src/app/[...view]/page.tsx:3023-3025
// Pass isTerminalRun=true for completed/failed/cancelled/degraded runs so
// gate chat_reply cards are auto-resolved (no pending review box).
seedRunChatTranscript(familyChatFrames, REOPEN_TERMINAL_STATUSES.has(fullRun.status));
```

`cancelled` is exactly the status a REJECTED gate produces. Rejecting a gate never
fires `review_gate_approved` — the backend only yields it on the approve path:

```python
# backend/agents/execution_engine/engine.py:10441-10446
if not approved:
    yield {"type": "_gate_rejected"}
    return

yield {
    "type": "review_gate_approved",
```

and the reject path transitions the run straight to `cancelled`:

```python
# backend/agents/execution_engine/engine.py:7653-7660
if gate_event.get("type") == "_gate_rejected":
    current = self._state_machine.get_state(pipeline_run_id)
    if current not in ("cancelled", "failed", "diverted"):
        self._state_machine.transition(pipeline_run_id, "cancelled")
    yield {"type": "pipeline_cancelled", "data": {
        "pipeline_run_id": pipeline_run_id,
        "reason": f"User rejected output from {spec.name}",
    }}
```

So within the live session, the rejected gate's card correctly stays
`resolved: false` (still reads "Review required") because nothing ever flips it.
But the FIRST time that now-`cancelled` run is reopened — cold nav, the `/runs`
history list, or a family reseed — `seedTranscript` runs with `isTerminalRun: true`
(since `"cancelled"` is in `REOPEN_TERMINAL_STATUSES`) and unconditionally flips
the still-pending gate card to `resolved: true`, which `ResultCard.tsx` then
renders as **"Review approved — build continues"** — the opposite of what actually
happened. The same blanket check equally mislabels a gate left dangling by a
`failed` or `diverted` run (nobody approved anything there either); `cancelled`
via an explicit reject is used here as the cleanest, most reliably
user-triggerable illustration.

## Expected (once reproduced)

A gate card's resolved rendering reflects the gate's ACTUAL outcome. A run that
ended via rejection, failure, or diversion without an actual approval for a given
gate should never render that gate as "Review approved — build continues" — at
minimum it should stay "Review required" (honest but stale), and ideally reflect
the real outcome (e.g. an inline note tied to the same "Cancelled by you" /
"What went wrong" pipeline card already shown for that run).

## Actual (inferred, not yet observed)

Rejecting a review gate, then reopening that run (cold `goto`, `/runs` history
list, or navigating away and back) is expected to show the gate's chat card as
"Review approved — build continues" — even though the pipeline was cancelled by
the user's rejection, not approved.

## What would confirm this

1. Launch a run with at least one review gate (e.g. a PPT run with "lateral
   thinking", or any pipeline with `gate: Human_Gate` agents).
2. When the gate opens, click **Reject** (not approve). Confirm the run reaches
   `cancelled` and the chat shows "Cancelled by you".
3. While still in the live session, confirm the gate's own card still reads
   "Review required" (it should, since `review_gate_approved` never fired).
4. Cold-reopen the same run: navigate to `/dashboard`, then a fresh `goto` of
   `/runs/{id}` (or open it from the `/runs` history list).
5. Scroll to the same gate card and check whether it now reads "Review approved —
   build continues" instead of "Review required".

## Fix-phase note (2026-09-17)

This card was left `open` when [FIX-520](20260917-1338-FIX-520.md) fixed ISS-653. It is still
unreproduced, and its test is not ready to drive a fix:

- **The test cannot see the fix this card describes.** The card blames the caller,
  `frontend/src/app/[...view]/page.tsx:3028`. The test (`frontend/src/hooks/useRunChat.test.ts:597`)
  calls `seedTranscript` directly with `true`, the same value a completed-run reopen passes.
  Narrowing the caller's flag cannot turn it green.
- **Passing it inside the hook needs a design decision.** The hook would have to leave a gate with
  no `review_gate_approved` frame pending on a terminal seed. That missing-approval case is what the
  auto-resolve exists for (`useRunChat.ts:739-742`); family members are seeded chat-only
  (`page.tsx:2974`). The options are listed in FIX-520's "Not fixed here".

Before fixing, reproduce this live, choose the design, and then decide where the test should assert.
