# ISS-1192

**Register source:** sibling derived during the re-analysis of `QA-KB-124` on 2026-10-09 (root [ISS-1156](20261009-1445-ISS-1156.md)). Not its own bug row.

**Confidence:** CONFIRMED for the mechanism (read, and run offline through the real engine, factory and deepagents backend). INFERRED for the consequence: no write-granted loop has reached pass 2 on record, because the four failing `ex_A1_loop` runs all died at pass 1's `check`. The refusal text itself names the way out ("Read and then make an edit, or write to a new path."), so a real model may recover with `edit_file`; whether Haiku does is unknown. What would settle it: after the [ISS-1156](20261009-1445-ISS-1156.md) fix, run a write-granted looping plan on Haiku (the stored `ex_A1_loop` override as admin, or a composed one) and read `run_events` for the `greet` pass-2 `write_file` tool_result and the calls after it.

## Condition

A custom-agent step that holds `write_files` and is re-dispatched by a conditional route (`loop_max_iterations`): the `greet` side of `ex_A1_loop` whenever its steps carry the grants the Composer defaults to (`frontend/src/store/api/userWorkflows.ts:336-339`) or that a saved override stored ([ISS-1181](20261009-1708-ISS-1181.md)). It cannot be seen today, because the run never gets past pass 1's decision step; it becomes the next failure once [ISS-1156](20261009-1445-ISS-1156.md) is fixed.

## Mechanism (CONFIRMED)

1. The delivery block names a fixed path. `artifact_name(instance_id, topic)` is `<instance_id>-<topic>.md` (`backend/agents/workflows/artifacts.py:87-117`), with no pass or visit component, and `factory.py:727-731` emits `Call write_file with path <that>` on every dispatch of the step.
2. deepagents refuses to overwrite: `FilesystemBackend.write` returns "Cannot write to <path> because it already exists. Read and then make an edit, or write to a new path." (`deepagents/backends/filesystem.py:451-453`, deepagents 0.6.7).
3. The artifact guarantee does not repair it. `_check_artifact_fallback` returns early when the step can write and the file exists (`engine.py:9185`, `if can_write and sandbox.read(filename) is not None: return None`). Its docstring (`engine.py:9156-9165`) reasons about looped steps only for a write-LESS step, where "exists" cannot mean "the model just wrote it". For a write-granted looped step "exists" can only mean pass 1.
4. Nothing clears the file between passes, and the roster points the next reader at the same path on every pass (`engine.py:9051-9053`).

Offline run (`evidence/qa-kb-124/analysis-09-loop-pass2-write-probe.txt`; `ex_A1_loop` edges with read+write grants, the ISS-1156 fix applied in a scratch copy, the repo tree untouched): `greet` pass 1 `write_file` returns "Updated file"; passes 2, 3 and 4 return the refusal; the file on disk after the run is still `Hello team!`; `check`, answering from the text it read, says `retry` four times; `budget_aborted`. The probe scripts `greet` to follow the block literally and not to recover. That scripting is the INFERRED part.

## Expected vs actual

Expected: every pass of a looped step lands its output at the path the next reader is pointed at. Actual (predicted for a model that follows the block verbatim): pass 1's text stays, the judge keeps re-reading it, and the loop runs to its budget and fails closed.

## Why the root cause implies it

It is the second half of the same contract. [ISS-1156](20261009-1445-ISS-1156.md) is the delivery block applied to a step whose REPLY the engine reads as its answer; this is the delivery block applied to a step the engine RE-RUNS. Both come from the block at `factory.py:727-731` being unconditional and path-fixed. The adjacent state of the same code is pass 1 versus pass N, and the built-in plan hides it for the same reason it hides the root: its steps are tool-free, so there is no block and no file.

## Fix direction (INFERRED, not applied)

Prompt first, per the standing rule: one added sentence in the delivery block, in the same edit as the root fix: "If that file already exists (a retry or a loop pass), replace its content with `edit_file`." No engine change.

Engine alternatives, each needing a yes: clear the step's delivery file when the step is re-dispatched (`ectx.step_visit_counts` already knows the visit), or make `_check_artifact_fallback` compare against a pre-step snapshot instead of testing existence, as the single_file readback already does with `_pre_step_deliverable` (`engine.py:10680`, ISS-683). Do not suffix the filename with the pass: [ADR-0011](20260813-ADR-0011.md) makes `artifact_name` the single authoritative name.
