## What is suspected

[ISS-337](20260828-1900-ISS-337.md) root-caused `LoginForm`'s failed-login error banner
(`frontend/src/app/login/page.tsx:271-279`) having no `role`/`aria-live` and never receiving
focus. Reading the same file in full (559 lines) shows the sibling `ChallengeForm` component
— rendered in place of `LoginForm` once `login()` returns a Cognito challenge instead of a
token (first-login "set a new password" step, or an MFA code/selection step) — has its own,
separately-authored error block with the identical gap:

```tsx
{error && (
  <div className="mb-5 rounded-[var(--radius-button)] border border-[var(--status-failed-border)] bg-[var(--status-failed-fill)] px-4 py-3 text-sm text-status-failed">
    {error}
  </div>
)}
```
— `frontend/src/app/login/page.tsx:446-450`. No `role`, no `aria-live`, and nothing in
`handleChallengeSubmit` (lines 102-162, read in full) moves focus to it either — the same
pair of `setError(...)` / no-focus-move as `handleSubmit`.

## Condition

Reached on any of: an invalid `NEW_PASSWORD_REQUIRED` submission (password too short —
`"New password must be at least 12 characters."`; or mismatched confirmation —
`"Passwords do not match."`), an empty `SELECT_MFA_TYPE` submission
(`"Choose how you'd like to receive your code."`), an empty MFA code field
(`"Enter the 6-digit code..."`), or any API failure surfaced through the same
`describeApiError()` helper `handleSubmit` uses (lines 70-78).

## Expected vs actual

**Expected:** same WCAG 4.1.3 requirement ISS-337 already established — a
programmatically-determinable status message so assistive technology announces the
validation/auth failure.

**Actual (predicted):** identical practical outcome to ISS-337's validated finding — the
error text renders visually with no live-region signal and no focus move, so a screen-reader
user submitting the challenge form gets no notification that their attempt failed.

## Why the root cause implies this — and why it is a distinct defect, not the same report

This is the exact same mechanism ISS-337 validated (a `setError(...)` call inside a
`FormEvent` handler triggers a conditional re-render, no navigation involved) on a
DIFFERENT component (`ChallengeForm`, not `LoginForm`) with its OWN independently-authored
JSX — fixing ISS-337's block does not touch this one; there is no shared component between
them (confirmed by reading both functions in full — `ChallengeForm` is a separate function
starting at line 378, not a shared subcomponent `LoginForm` also renders).

**Marked INFERRED**: not independently reproduced — reaching this step requires either a
test account requiring a first-login password reset, or one requiring MFA, and none was
driven through the challenge flow for this analysis. What is CONFIRMED (by reading
`frontend/src/app/login/page.tsx` lines 378-551 in full) is that the JSX carries no ARIA
live-region semantics. What would confirm or refute it: sign in with a test account that
returns `NEW_PASSWORD_REQUIRED` or an MFA challenge (this repo's standard QA accounts are
likely already past first-login, so this would need a Cognito test user forced into that
state, or a mocked `login()` response inside a component test — this file's existing
`login.reskin.test.tsx` already stubs `@/lib/api` via `vi.mock`, so a driven test does not
need real Cognito) and inspecting the rendered error node for `role`/`aria-live` the same
way ISS-337's own reproduction did.
