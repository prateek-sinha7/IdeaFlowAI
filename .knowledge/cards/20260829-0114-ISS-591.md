## Sibling of ISS-359 - the comparator itself is only partially correct

[ISS-359](20260828-1918-ISS-359.md) / `BUG-20260828-093400-library-skills-id-r2` calls
`/library/skills/<id>`'s rendering the correct baseline - "runs the same content through [a markdown
renderer]" - and cites confirmed `<h2>`/`<h3>` headings on four skills. That much holds. Reading
`LibraryPage.tsx`'s `SkillDetailModal` in full (the component behind that route) shows it is NOT
`react-markdown` (already a project dependency - `frontend/package.json`, used elsewhere by
`frontend/src/components/preview/MarkdownPreview.tsx`, `chat/MessageBubble.tsx`,
`results/SandboxTab.tsx`) - it is a bespoke line-by-line splitter that only recognizes a few
line-prefix constructs:

- `LibraryPage.tsx:212` - a line starting `"# "` becomes the section's heading, only when it is the
  very first line accumulated (`current.lines.length === 0 && !current.heading`).
- `LibraryPage.tsx:214` - a line starting `"## "` starts a new section, heading = that line.
- `LibraryPage.tsx:286-288` - within a section, a line is classified `isBullet`
  (starts `"- "`/`"* "`) or `isNumbered` (`/^\d+\.\s/`); the prefix is stripped and the REST OF THE
  LINE becomes `text` verbatim.
- `LibraryPage.tsx:294` / `:299` - that `text` is dropped straight into `<p>{text}</p>` (or a bullet
  row) with no further parsing.

No inline markdown token is interpreted anywhere in this path: `**bold**`, `` `inline code` ``,
`[link](url)`, `_em_`, and any heading deeper than `##` (`###`, `####`) all pass through as literal
characters inside the rendered paragraph - the same failure mode ISS-359 reports for the Composer
modal, just narrower in scope (line-prefix constructs work; everything else doesn't), and on the exact
page the bug report treats as the correctly-working reference.

## Expected vs actual

**Expected:** a skill's `content` (its `SKILL.md` body) renders as HTML wherever the app claims to
format it, including inline emphasis, inline code and links.

**Actual (inferred):** on `/library/skills/<id>` itself, any skill whose body contains `**bold**`,
`` `code` ``, `[text](url)`, or a `###`/`####` heading shows those markup characters literally inside
the "Formatted content" section - confirmed by reading `LibraryPage.tsx:207-221` and `:285-301` in
full; not yet checked against a live skill whose `SKILL.md` actually contains one of those tokens.

## Why this matters for ISS-359's fix

If `AgentSkillsPicker.tsx`'s `detailSkill` modal is "fixed" by copying this same line-splitter (rather
than routing both surfaces through the real `react-markdown` + `remark-gfm` pipeline
`MarkdownPreview.tsx` already uses, with its already-audited "no rehype-raw" security posture -
`MarkdownPreview.tsx:8-18`), the fix propagates this narrower parsing gap into a second component
instead of closing it. The shared surface belongs on the `react-markdown` path, not on this hand-rolled
one - one place both `AgentSkillsPicker.tsx` and `LibraryPage.tsx`'s `SkillDetailModal` route through.

## Why this is INFERRED, not CONFIRMED

The parsing gap is confirmed by reading `LibraryPage.tsx:195-340` (`SkillDetailModal`) in full - there
is no code anywhere in the function that touches `**`, `` ` ``, `[`, or `_` inside a line. What is NOT
yet verified is a live skill whose `SKILL.md` body actually contains one of those tokens, opened at
`/library/skills/<id>`, with the literal markup visible in the DOM (mirroring ISS-359's own
`querySelectorAll` method). None of the four skills ISS-359 tried (`windows-desktop-e2e`,
`.NET Backend Expert`, `Accessibility (WCAG 2.2)`, `html-deck-to-pptx`) were checked for this narrower
gap - the validator confirmed headings only.

## Evidence

Source-only at filing time - no screenshots. Confirm via: `LibraryPage.tsx:207-221` (section-splitting
loop), `:285-301` (line-to-JSX render, no inline parsing), `:321-323` (the raw `<pre>` block that DOES
still exist here as a fallback, unlike `AgentSkillsPicker.tsx`'s modal which has ONLY that), and
`frontend/src/components/preview/MarkdownPreview.tsx:69-131` (the `react-markdown` + `remark-gfm`
pipeline already used elsewhere in the app for the same job).
