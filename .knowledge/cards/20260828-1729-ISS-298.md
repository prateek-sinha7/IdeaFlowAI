## Summary

`frontend/src/app/preview-fullscreen/page.tsx` (`PreviewFullscreenPage`, inside its top-level
`useEffect`) checks `params.get("error") === "quota"` and, if true, calls `setState("quota")`
and `return`s immediately — before the component ever reads `sessionStorage["__app_preview__"]`.
The plain (no-query-param) route reached moments later in the same `useEffect` reads that exact
key and renders the full working IDE preview whenever it holds valid, parseable data.

Root cause (file:line): `frontend/src/app/preview-fullscreen/page.tsx`, the `if
(params.get("error") === "quota") { setState("quota"); return; }` block, which sits ahead of the
`setTimeout` that performs the `sessionStorage.getItem("__app_preview__")` read/parse used by the
no-param path a few lines below.

`AppBuilderPreview.handleFullscreen()` (`frontend/src/components/preview/AppBuilderPreview.tsx`)
opens the fullscreen tab via `window.open(..., "_blank")` deliberately **without** `"noopener"` so
the new tab shares the opener's browsing context and can read `__app_preview__` from
sessionStorage — the component's own comment confirms this is intentional sharing.
`sessionStorage.setItem` is atomic: a `QuotaExceededError` throw on a second, larger write leaves
whatever was written by an earlier, smaller, successful write untouched. So the realistic sequence
is: a user opens Full Screen once (a valid payload is now cached), then triggers a second Full
Screen attempt whose write is too large and throws quota-exceeded — the catch block opens a new
tab at `?error=quota`. That tab shares the same sessionStorage which still holds the earlier,
fully valid, renderable payload — yet the page shows only the generic "too large" dead end and
never consults or offers the cached preview it has direct read access to.

## Reproduction (3/3, cycle 1)

Reproduced deterministically on all 3 cold-start cycles — this is a pure client-side branch-order
bug with no timing/tier/theme dependency, confirmed CONFIRMED on the first cycle already:

1. Sign in as qa-admin, land on `/dashboard`. Seed sessionStorage directly:
   `sessionStorage.setItem('__app_preview__', JSON.stringify({files:[{path:'index.html',
   content:'<h1>hello</h1>'}], projectName:'Cycle1Project'}))`.
2. Navigate to `http://localhost:3000/preview-fullscreen` (no params). Title becomes
   `"Cycle1Project — IDE Preview"` — confirms the payload is valid and renderable.
3. Same tab, navigate to `http://localhost:3000/preview-fullscreen?error=quota`. Page shows
   "Project too large for full screen" / "The generated project exceeds the browser session
   storage limit (~5MB)..." instead of the preview.
4. In that same page load, `sessionStorage.getItem('__app_preview__')` is still non-null and
   `JSON.parse(...).files.length === 1` and `projectName === 'Cycle1Project'` — the exact seeded
   data, fully intact, never consulted by the quota branch.

Cycle 2 varied entry path (cold deep link straight to `?error=quota` with no prior plain-route
visit that session) — same result, with a second independent 2-file payload
(`Cycle2SecondRepro`) still verifiably present after the dead end rendered.

Cycle 3 repeated the full cold sequence (fresh `/dashboard` load, session cleared, re-seeded,
navigate to `?error=quota`) — same result.

## Expected

When `?error=quota` is present, the page should still check whether `__app_preview__` holds a
valid, parseable payload (the same check the plain route already performs a few lines later)
before giving up — either rendering that last-known-good preview, or at minimum indicating a
previous preview is still available — rather than unconditionally declaring the "too large" dead
end on every load of this URL regardless of what is actually sitting in the shared
sessionStorage the two tabs intentionally share.

## Actual

The `error === "quota"` branch returns unconditionally before any sessionStorage check, so a
tab that legitimately still holds a valid, viewable preview payload (from an earlier successful
Full Screen attempt in the same shared browsing context) is shown the generic, dead-end "too
large" message instead — discarding a working preview the app itself proves it can render, with
no path to reach it from this URL.
