# ISS-1144

**Register source:** QA-KB-108 (SMOKE-3), validated 2026-10-09.

## Reproduction (3/3, cold start each)

The live backend holds valid credentials now, so the failure was driven offline and deterministically: `evidence/qa-kb-108/01-validate-repro-script.py` builds the app's TestClient, patches `app.api.auth.cognito.admin_initiate_auth` to raise `botocore.exceptions.TokenRetrievalError("Token has expired and refresh failed")` (the exact exception in the live log) and POSTs `/api/auth/login` with `Origin: http://localhost:3000`. Three separate processes: attempts 1, 2, 3 each returned `500`, `access-control-allow-origin` absent, body `Internal Server Error` (`evidence/qa-kb-108/02-validate-attempts-1-3-output.txt`). The reporter's original occurrence: `/private/tmp/velocity-8000.log` line 16702 `auth.py", line 342, in login` ending `botocore.exceptions.TokenRetrievalError: Error when retrieving token from sso: Token has expired and refresh failed` (excerpt in `evidence/qa-kb-108/03-validate-backend-log-excerpt.txt`).

## Conditions

Any tier, any theme. Trigger: the AWS credentials that sign the Cognito `AdminInitiateAuth` call cannot be refreshed (expired SSO session). Valid credentials: login 200 with CORS headers (curl 2026-10-09).

## Expected vs actual

Expected: handled 503 ("Authentication service unavailable") with the normal CORS headers, as for any provider error. Actual: unhandled exception, Starlette's outer 500 handler answers outside CORSMiddleware, so the browser reports a CORS block and the login page shows "An unexpected error occurred. Please try again."

## Cause (read from source)

`backend/app/api/auth.py:341-367`: `except ClientError as exc:` is the only handler; its non-credential branch already returns the 503 `Authentication service unavailable`. `TokenRetrievalError` derives from `BotoCoreError`, not `ClientError`, and is raised in the signer before any HTTP call, so it skips the handler. The same applies to other `BotoCoreError`s (`NoCredentialsError`, `EndpointConnectionError`). Other `cognito.*` call sites in auth.py should be checked for the same narrow catch.

## Analysis (analyzer, 2026-10-09)

CONFIRMED means read at the cited file:line, and executed offline where an evidence file is named. INFERRED means derived, with what would settle it.

### Root cause: two independent gaps, one symptom

**1. The provider-failure handlers model one of botocore's two exception families (CONFIRMED).** botocore raises `ClientError` when the service answered with an error and `BotoCoreError` when the call never completed: credential or SSO-token resolution, endpoint, timeout. The two are disjoint (`evidence/qa-kb-108/07-analyze-source-excerpts.txt`, last section: `TokenRetrievalError > BotoCoreError > Exception`, `ClientError > Exception`). Credentials are resolved when botocore signs the request, inside `_client().admin_initiate_auth(...)` (`backend/app/core/cognito.py:253-263, 276`), so an unresolvable chain raises before any HTTP request. `backend/app/api/auth.py:343` catches `ClientError` only. The exception skips the whole block, including the 503 and the `LOGIN_FAILURE` audit event at `:357-367`.

**2. Nothing downstream turns the escape into a response the browser can read (CONFIRMED).** `backend/app/main.py:539` registers a handler for `RequestValidationError` and nothing else. An unhandled exception reaches Starlette's `ServerErrorMiddleware`, which wraps the entire stack including `CORSMiddleware` (`backend/.venv/lib/python3.13/site-packages/starlette/applications.py:62-71`), so the 500 carries no `access-control-allow-origin`. The browser blocks it, `fetch` rejects with a `TypeError`, and `frontend/src/app/login/page.tsx:73-81` prints its generic string for anything that is not an `ApiError`. That function prints the server's `detail` for an `ApiError`, which `fetchWithAuth` builds from the response body (`frontend/src/lib/api.ts:572-578`), so once the backend answers 503 with CORS headers the login page needs no change.

**Side effect at the same line (CONFIRMED by reading).** No `LOGIN_FAILURE` event is emitted, so the `auth_login_failure` log metric filter (`infra/terraform/modules/monitoring/main.tf:2118-2121`, feeding the `auth_login_failure_spike` alarm at `:2131-2143`, `treat_missing_data = "notBreaching"`) sees nothing while every sign-in is failing. An outage that stops all logins is invisible to the login-failure alarm.

**Not a laptop-only problem (INFERRED).** `backend/app/core/config.py:4-6` says production authenticates through the instance profile, so `CredentialRetrievalError`, IMDS timeouts and `NoCredentialsError` reach the same unhandled path. An incident log, or blocking IMDS on a staging host, would settle it; neither was done.

Which operations need credentials is not a guess: the installed botocore service model marks `ForgotPassword`, `ConfirmForgotPassword`, `ChangePassword`, `AssociateSoftwareToken`, `VerifySoftwareToken`, `SetUserMFAPreference` and `RevokeToken` as `auth_type='none'`, and every `Admin*` operation the backend uses as signed (`06-analyze-botocore-service-model-auth-types.txt`). A credential-free process confirms it: signed operations fail with `NoCredentialsError`, unsigned ones reach the network (`05-analyze-handler-placement-and-signing-output.txt`, part 2).

Already correct, and the in-repo precedent for this exact condition: `auth.py:588` (`except Exception`, comment "no creds / endpoint / DNS failure"), `:735`, `:903`, `:987`, `:1231`, and `provisioning.py:303`. `GET /mfa` answers 200 with CORS headers under the same fault (probe row C, last line).

Not affected: `enforce_admin_mfa` makes no Cognito call (`backend/app/core/identity.py:277-281`); token verification fetches the JWKS over httpx and raises `CognitoVerificationError`; engine model calls have their own classification (`backend/agents/execution_engine/engine.py:197`).

### Where the fix belongs

**Layer 1: translate at the Cognito call sites, through two shared symbols in `backend/app/core/cognito.py`**, the adapter and the one module that knows both exception families. `PROVIDER_ERRORS = (ClientError, BotoCoreError)` and `provider_error_code(exc) -> str` (the AWS error code for a `ClientError`, the class name otherwise). At the ten `auth.py` clauses and the ten `cognito_admin.py` clauses, `except ClientError as exc:` plus `exc.response.get("Error", {}).get("Code", "")` becomes `except PROVIDER_ERRORS as exc:` plus `provider_error_code(exc)`. The existing branching keeps working, because a `BotoCoreError`'s code (`TokenRetrievalError`) matches no special code and falls into the branch each site already has for "any other failure", which is the outcome its author documented: 503 in the `auth.py` handlers (and in `login` also `LOGIN_FAILURE` with `reason="provider_error:TokenRetrievalError"`, restoring the alarm signal with no new `AuthEvent` member), `ProviderUnavailableError` in `cognito_admin.py` (which `api/admin.py` already maps to 503, and must keep doing without importing botocore), the generic 202 in `forgot_password`, degrade-to-local in `is_last_admin`'s first read.

Zero-caller-edit alternative: translate once inside `_client()`, wrapping the boto3 client so a `BotoCoreError` is re-raised as a `ClientError` subclass whose code is the class name. It fixes every present and future caller, but needs a proxy that also wraps `get_paginator` (`list_users_in_group` and `list_pool_users` page lazily, `cognito.py:521-539, 726-739`) and re-expresses "could not reach the service" as a `ClientError`. Either satisfies the acceptance list below; the choice is the fixer's. Existing unit tests patch `cognito._client` with a `MagicMock` (`backend/tests/unit/api/test_cognito_refresh_secret_hash.py`), so a wrapper inside `_client()` is bypassed by them, not broken.

**Layer 2: the safety net in `backend/app/main.py`**, see [ISS-1150](20261009-0935-ISS-1150.md): `app.add_exception_handler(BotoCoreError, ...)`, a JSON 503, logging the exception. Keyed on the class, not on `Exception`.

Minimum that closes QA-KB-108 as reported: layer 2 plus layer 1 at `auth.py:343` with its audit event. The sibling cards check the rest.

### Acceptance (for the test writer)

1. `POST /api/auth/login` with `cognito.admin_initiate_auth` raising `TokenRetrievalError` and `Origin: http://localhost:3000` gives 503; `detail` is a non-empty string (the existing `Authentication service unavailable`); `access-control-allow-origin` is `http://localhost:3000`; exactly one `LOGIN_FAILURE` event with `provider="cognito"` and `reason="provider_error:TokenRetrievalError"`. Today: 500, no header, no event (3/3 for the validator, and again in `04-analyze-sibling-probes-output.txt`).
2. Controls that must not change: `ClientError(InternalErrorException)` gives the same 503 plus event `provider_error:InternalErrorException`; `ClientError(NotAuthorizedException)` gives 401 `Invalid credentials`. They stop a guard that swallows everything, or that turns a provider outage into "wrong password", from passing.
3. The same assertion for each endpoint in the sibling cards. Ready-made harnesses: `evidence/qa-kb-108/04-analyze-sibling-probes.py` and `08-analyze-admin-routes-probe.py` (from `backend/`: `PYTHONPATH=. .venv/bin/python <script>`; DB stubbed, every Cognito wrapper patched, no network).
4. One file at a time: `backend/tests/security/test_cognito_client_boundary.py` stays green.

### Traps

- `@app.exception_handler(Exception)` or `(500)` returns the 503 but still without a CORS header (`05-...-output.txt`, part 1). Only a handler keyed on `BotoCoreError` keeps it.
- `except BotoCoreError` in `api/admin.py` fails `test_admin_api_imports_no_raw_provider_sdk` (`backend/tests/security/test_cognito_client_boundary.py:152`). Translate in `cognito_admin.py`.
- Routing a `BotoCoreError` into the `NotAuthorizedException` branch tells users their password is wrong during an outage, and in `/refresh` would also mark accounts `disabled` ([ISS-1146](20261009-0935-ISS-1146.md)).
- No local fallback. [ADR-0013](20260916-ADR-0013.md): Cognito is the sole credential authority and an uncertain provider answer must fail closed where it grants authority. The right outcome at sign-in is a denial with a readable message.
- Do not add an `AuthEvent` member: the enum is a published interface for the Terraform metric filters (`backend/app/core/auth_events.py` docstring). Use a `reason` string, as `auth.py:253-261` documents. Keep passing `**audit_identity`.
- `/forgot-password` must stay a generic 202 ([ISS-1149](20261009-0935-ISS-1149.md)); a uniform "BotoCoreError becomes 503" rule would break it.
