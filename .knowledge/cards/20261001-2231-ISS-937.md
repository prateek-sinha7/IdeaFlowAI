# ISS-937

## Description

Sibling of [ISS-398](20260828-2106-ISS-398.md) (QA-KB-017), found because the obvious way to write the missing gate is to copy the one that exists. The only live caller of `can_use_model` is the settings page ([FIX-361](20260829-0029-FIX-361.md)), and it passes the raw `User.tier` column: `get_preferences` (`backend/app/api/settings.py:341`) and `update_preferences` (`:374`, `:388`) take `user: User = Depends(get_current_user)` (`:332`, `:353`) and call `can_use_model(user.tier, ...)`.

[ADR-0013](20260916-ADR-0013.md) locks the opposite: "Effective tier and admin status come from the verified `cognito:groups` claim; `User.tier` and `User.is_admin` are advisory projections only." The same rule is written into the code: `backend/app/core/identity.py:214-223` ("`cognito:groups` is ALWAYS authoritative -- never the DB column"), `backend/app/core/dependencies.py:190-195` (callers needing the effective tier "must call `core.identity.effective_tier` ... not read the column directly"), and `_require_tier_entitlement` (`backend/app/api/run_commands.py:2555-2598`), whose docstring says no gate may read the projection alone.

## Why the root cause implies it

Same helper, wrong tier source. If the QA-KB-017 gates are written in the shape the settings page uses, they inherit the same ADR-0013 violation on three more routes.

## Evidence

CONFIRMED, read: the lines cited above.

Mitigation, so the severity stays low: `_sync_role_projection` (`backend/app/core/dependencies.py:145`, called at `:215` and `:249`) refreshes `users.tier` from the token's groups before the handler runs whenever the token is newer than the last sync (`provisioning.py:112-150`), so in the ordinary case the column equals the effective tier at request time.

INFERRED, not driven: the residual window. A token older than the last sync that is still valid after a group change made outside the admin API (a Cognito console edit does not bump `tokens_valid_from`) would be gated on the newer column value instead of its own groups. What settles it: a request authenticated by a principal whose groups disagree with `user.tier`, against the settings routes.

## Expected vs actual

- Expected: every model-tier decision, on every route, reads `effective_tier(user, principal)`.
- Actual: the settings routes read `user.tier`.

## Fix direction

Move the three settings call sites onto the same `(user, principal)` helper the QA-KB-017 gates use (`get_current_principal` instead of `get_current_user` on those two routes). Do not copy the `user.tier` shape into the new gates.

## Test notes

Settings route tests live in `tests/integration/e2e/suites/09_settings/test_settings.py` ([FIX-361](20260829-0029-FIX-361.md)'s coverage). A unit-level check is enough here: override `get_current_principal` with a principal whose groups say basic while the fake user's `tier` column says pro, and assert the premium preference is refused.

## Analysis (QA-KB-083, analyzer, 2026-10-02, HEAD `024c03ef8`)

Root cause CONFIRMED by reading the code and by running it. Everything above stands. This section settles the INFERRED item in Evidence and adds the mechanism, blast radius, fix location and test guidance.

### Root cause

One mechanism. The two preference handlers depend on `get_current_user`, which hands back only the `User` row: `backend/app/core/dependencies.py:255-282` returns `user` from `get_current_user_with_payload` and drops the `Principal` (and the dict payload that carries its groups). A handler holding only a `User` cannot call `effective_tier(user, principal)` (`backend/app/core/identity.py:214-223`, which returns `resolve_tier_from_groups(principal.groups)` and `del`s `user`), so the only tier in scope is the advisory column, and `settings.py:341`, `:374` and `:388` pass it to `can_use_model`. `can_use_model(user_tier: str, ...)` (`backend/app/core/entitlements.py:144`) takes a bare string, so nothing in the call tells a column value from an effective one.

Why it was missed: the gate predates the Cognito-only cutover. `can_use_model(user.tier, ...)` landed in `d027f16bd` (2026-08-29, [FIX-361](20260829-0029-FIX-361.md)) and the GET `allowed` flags in `b87123e06` (2026-09-01, [ISS-430](20260829-0029-ISS-430.md)). The cutover `b2a621f84` (2026-09-17) moved `_require_tier_entitlement`, `user_workflows.py` and the other gates onto `effective_tier`, added the T7 guard, and left `settings.py` alone. The guard has been red on these reads since ([ISS-1029](20261002-0705-ISS-1029.md)).

### When the column and the token disagree (CONFIRMED by execution)

The window needs no console edit. It needs a valid token whose `iat` is not newer than `users.roles_synced_at`: `refresh_projection_if_stale` returns early on `token_iat <= int(synced_at.timestamp())` (`backend/app/core/provisioning.py:138-140`), so the column keeps whatever the last-syncing token wrote. The admin API closes the window for its own changes (`cognito_admin.change_tier` commits `tokens_valid_from` at `:434` before touching Cognito and signs the user out at `:453`); an out-of-band group change, or two tokens minted around a sync, does not.

Scratch probes, outside the repo, offline, in-memory SQLite, the real settings router and the real `can_use_model` (`evidence/qa-kb-083/01-` to `04-`). Both dependencies overridden, column and token groups set apart:

| `users.tier` | token groups | `GET` allowed[Opus 4.6] | `PUT` Opus 4.6 |
|---|---|---|---|
| pro | basic | True | 200, stored |
| basic | pro | False | 403 |
| basic | basic | False | 403 |
| pro | pro | True | 200, stored |

The same routes behind the REAL dependency chain, with only Cognito signature verification stubbed (`evidence/qa-kb-083/04-analyze-probe-real-chain-output.txt`):

1. Newer token (basic groups, `iat` after the last sync) with a pro column: `refresh_projection_if_stale` rewrites the column pro to basic, `/api/auth/me` says basic, `allowed` is False and `PUT` is 403. This is the ordinary case and the reason severity stays low.
2. Older-but-valid token (basic groups, `iat` before the last sync) with a pro column: `/api/auth/me` says basic while `GET /preferences` says `allowed: true` for Opus and `PUT` returns 200 and stores Opus. The column stays pro. One page, two tiers.
3. Mirror: older-but-valid pro token with a basic column: `/api/auth/me` says pro, `allowed` is False, `PUT` is 403. A false refusal, so the defect runs both ways and is not only over-permissive.

Still INFERRED: how often a live pool produces rows 2 and 3. Nothing here drove a real Cognito pool. What would settle it: a console-side group edit, then two tokens against the settings routes.

### Blast radius (grepped, not assumed)

- Producers of the wrong tier: three reads in two handlers, `settings.py:341`, `:374`, `:388`. `can_use_model` has five call sites: these three, `run_engine.py:668` (`_model_entitlement_error`, effective tier, [FIX-705](20261002-0107-FIX-705.md)) and `run_commands.py:2616` (`_entitled_user`, effective tier). Settings is the only caller that feeds it a column. No other `.tier` read decides anything in `backend/app` or `backend/agents` (grep of `.tier`, `.is_admin` and `getattr(..., "tier" | "is_admin")`); the one other decision read of a projection column is `run_commands.py:2655`, [ISS-1028](20261002-0705-ISS-1028.md).
- `PUT` consumers: `settings.py:378` is the only writer of `users.preferred_model`, and `run_commands.py` reads it at ten sites. The four front doors go through `_entitled_user(user, caller_tier)` (`:1643`, `:1791`, `:3784`, `:5635`, FIX-705), so a premium value stored through this hole is dropped at launch for an effective-basic token. The consequence is a preference the run silently ignores, not a premium-billing bypass.
- `GET` consumers: `frontend/src/components/settings/AccountSettings.tsx:415` (`disabled={m.allowed === false}` and the lock) through `getPreferences` (`frontend/src/lib/api.ts:1945`, the shared `cachedGet`). `AnalyticsPage.tsx:210` reads `preferred_model` only. The response shape does not change with the fix.
- Tests: `tests/security/test_no_projection_reads.py::test_no_projection_reads_in_decision_context` is red on `settings.py:341` and `:388` (1 failed, 1 passed, run 2026-10-02); it reports `update_preferences` once, at `:388`, so the `:374` gate read hides behind the same key. `backend/tests/unit/test_settings_preferences_race.py` is the only direct caller of `update_preferences` (keyword `user=`) and already errors at setup ([ISS-1019](20261002-0617-ISS-1019.md)). No offline HTTP-level test mounts the preference routes. The e2e `test_basic_tier_cannot_persist_a_powerful_model` cannot see this defect: a live login keeps column and groups equal.
- Not affected: `tests/security/test_route_contract.py` already counts `get_current_principal` as an auth dependency (`:47`), and import-linter sees `app.api` to `app.core`, the edge `user_workflows.py` already uses.

### Fix, and where it belongs

In `backend/app/api/settings.py`, on the two preference handlers only. `effective_tier` is already the one function every other gate calls, so settings is the last holdout and nothing shared needs to change. Making `can_use_model` take a `Principal` would touch three caller families that already pass effective tiers, for no gain.

1. Imports: `get_current_principal` from `app.core.dependencies`, `Principal` and `effective_tier` from `app.core.identity`. Keep the `get_current_user` import; nine other routes in the file use it.
2. `get_preferences` and `update_preferences`: replace `user: User = Depends(get_current_user)` with `auth: tuple[User, Principal] = Depends(get_current_principal)`, then `user, principal = auth` and `tier = effective_tier(user, principal)` once at the top. This is the shape of `user_workflows.py:674-682` and `:951-955`. The triage sketch's "add principal while keeping user" does not work as written: `get_current_principal` returns the `(user, principal)` tuple, and keeping `get_current_user` as well would verify the token twice.
3. Use `tier` at `:341`, `:374` and `:388`. Computing it once, before `commit()` and `refresh()`, also stops the response flags at `:388` (read after `db.refresh(user)`) from being judged by a different value than the gate at `:374`.
4. Keep what [ISS-319](20260828-1804-ISS-319.md) and [FIX-361](20260829-0029-FIX-361.md) locked: the 200 body reports the `model_id` this request validated, not a re-read of the row, and the 422 for an unknown id is checked before the 403 for a tier denial.
5. Do not allow-list the reads in `projection_read_allowlist.txt` to green the guard: its per-function key would approve the `:374` gate read too ([ISS-1029](20261002-0705-ISS-1029.md)). After this change the guard should pass with no new line.
6. `test_settings_preferences_race.py` calls `update_preferences(..., user=..., db=...)` twice. Once the file runs again ([ISS-1019](20261002-0617-ISS-1019.md)) those become `auth=(user_x, principal_for(user_x))`. That is a test-only edit following the signature; flag it for the verifier's direction check.
7. Out of scope for this card: [ISS-1028](20261002-0705-ISS-1028.md) (an open spec decision, D-02) and the guard rework in [ISS-1029](20261002-0705-ISS-1029.md). Fix this card first, as ISS-1029 says.
