# ISS-905

> Analysed 2026-10-02 for QA-KB-057: see "Analysis (QA-KB-057, 2026-10-02)" at the end. It keeps everything below and
> corrects three points: Fault 2 is refused by the legacy selector (not the v2 selector), FIX-504 B5 is not the trigger
> (`chains_from: true` on `user_stories` is), and the fix must also pin `RUNS_ROOT`.

Found during the QA-KB-027 fix ([FIX-691](20261001-2149-FIX-691.md)). This file was `backend/tests/unit/test_duplicate_context_guard.py`,
listed in the unit-tier row of the [ISS-891](20261001-2120-ISS-891.md) table. FIX-691 fixed the two faults the cards name: it moved the file
out of `tests/unit/`, whose `_unit_io_guard` refused its DB connection (8 errors), and swapped its
`password_hash="x"` seed for `cognito_sub`. Two more faults sit behind them. No card covers either.

## What the tests guard (live behaviour, currently unguarded)

The duplicate-context guard in `_launch_run_core`. When a launch carries both `source_workflow_run_id` and a legacy
`=== CONTEXT FROM PREVIOUS PIPELINE ===` block, the block is stripped and a `legacy_context_block_stripped` audit row is
written (`backend/app/api/run_commands.py:2937-2958`). The guard is still in the product. Only its tests are dead.

## Fault 1: the auth override (all 8 tests)

`launch_run` (`POST /api/runs`, `backend/app/api/run_commands.py:3236-3243`) takes
`auth: tuple[User, Principal] = Depends(get_current_principal)`. The fixture
(`test_duplicate_context_guard_api.py:101`) overrides only `get_current_user`, so every request is
`401 {"detail":"Not authenticated"}`. Observed: `8 failed` (`evidence/qa-kb-027/05-fix-after-test-runs.txt`).
The sibling launch fixture already does it right: `tests/integration/api/test_rest_run_launch_api.py:115-130` also
overrides `get_current_principal` with `(state["user"], principal_for(state["user"]))`.

## Fault 2: the source run has no committed payload (6 of 8)

With the principal override added in a transient probe (file restored byte-identical; output in
`evidence/qa-kb-027/07-duplicate-context-guard-probe.txt`): `6 failed, 2 passed`. The 6 are every test that passes
`source_workflow_run_id`; each gets
`422 {"code":"source_payload_missing","error":"Chain launch refused"}`. `_seed_source_run`
(`test_duplicate_context_guard_api.py:133-152`) adds a bare `WorkflowRun` row with no finalization ref, sandbox, tag or
`.chain/` payload. The v2 selector therefore refuses it at its first check (`run_commands.py:4930-4933`:
`ref = visible_tag or internal_ref` is `None`, so it raises `ChainRefused("source_payload_missing")`).
[FIX-504](20260915-FIX-504.md) made that a hard 422 on purpose ("B5 — `source_payload_missing` always raises HTTP
422"), so the fixture is stale. The product is not wrong.

## Fix (test only, proposed)

1. Add the `get_current_principal` override exactly as `test_rest_run_launch_api.py:115-130` does.
2. Make `_seed_source_run` a finalized v2 source: a sandbox with the flat `.chain/` payload committed, a tag or
   internal ref, and the finalization record the selector reads. Reuse whatever builder FIX-504's offline integration
   tests use rather than writing a new one.
3. Repoint the comment at `frontend/e2e/tests/ts-v2-chain-versioning.spec.ts:8`, which still names
   `backend/tests/unit/test_duplicate_context_guard.py`.

Do not relax the 422 or the principal dependency to make these pass.

## Analysis (QA-KB-057, 2026-10-02)

Verdict: **test-only, the product is correct, no product edit is needed.** Faults 1 and 2 above are real and are the only
two. Observed this session (`evidence/qa-kb-057/04-analyze-probe-output.txt`, scripts `probe_seeds.py` and
`probe_guard_edges.py` beside it; they edit no repo file): the shipped file gives `8 failed, 3 warnings in 1.39s`, all
`401 {"detail":"Not authenticated"}`; the 8 REAL test bodies replayed with the principal override, a throwaway `RUNS_ROOT`
and either admissible seed below give `passed=8 failed=0` each. The text above is left intact. This section corrects three
points in it, adds one constraint it misses, and records the blast radius.

### Corrections to the text above

1. **Fault 2 is refused by the LEGACY selector, not the v2 selector (CONFIRMED).** A bare `WorkflowRun` has no
   `run_finalizations` row, so `read_finalization_record` returns None (`backend/agents/execution_engine/finalization.py:335-371`),
   `is_legacy_source` returns True for `record is None` (`backend/app/api/run_commands.py:4931-4933` [HEAD 4891-4893]), and
   `select_source_payload` dispatches to `_select_legacy_payload_or_refuse` (`:5122-5125`). That raises
   `ChainRefused("source_payload_missing")` when `select_legacy_payload` finds neither `.chain-legacy/<id>/` nor `.chain/<id>/`
   (`:5075-5076` [5035-5036]; `backend/app/agents/sandbox.py:2188-2242`). `_select_v2_payload` and its
   `ref = visible_tag or internal_ref` (`:4974` [4934]) are never entered: the probe's selector trace for every failing case is
   `['_select_legacy_payload_or_refuse:enter', '_select_legacy_payload_or_refuse:raised:source_payload_missing']`. The 422 body
   (`:5333-5350`) is identical either way, which is why the card read it as v2.
2. **FIX-504 B5 is not the trigger (CONFIRMED).** B5 only made the `chain_policy == "degrade"` branch unreachable
   (`run_commands.py:5397-5412`, `if False:`). `user_stories` declares no `chain_policy`, so it has always been the compiler
   default `"refuse"` (`backend/agents/workflows/compiler.py:1647`, same default at `4a6e89933^`) and a missing payload has always
   refused. What switched the gate on for this file's pipeline type is `chains_from: true` at
   `backend/agents/workflows/user_stories/workflow.yaml:35` (commit `3241a99aa`, 2026-09-12).
3. **Line numbers moved, and the guard exists twice.** The working tree carries uncommitted edits to `run_commands.py`
   (`git diff --stat HEAD`: 101 insertions, 60 deletions; [ISS-949](20261002-0107-ISS-949.md) notes the same). Current numbers:
   `launch_run` dependency `:3263`; endpoint-level strip `:3426-3472`; `admit_chain_launch` call `:3818`; core-level strip
   `:2955-3018`. The file's header says it validates the guard "in _launch_run_core", but over HTTP the strip that runs is the
   endpoint-level one; the core copy fires only as a second pass in one boundary case (see [ISS-981](20261002-0409-ISS-981.md)).

### Fix constraints for the test-writer and fixer (verified; all test-side)

1. **Principal override**, as `tests/integration/api/test_rest_run_launch_api.py:114-130` does:
   `app.dependency_overrides[get_current_principal] = lambda: (state["user"], principal_for(state["user"]))`.
   `get_current_principal` (`backend/app/core/dependencies.py:221-252`) does not depend on `get_current_user`, so the existing
   override cannot cover it; the 401 text comes from `_BearerScheme` (`:30-57`).
2. **Pin `RUNS_ROOT` to `tmp_path` before the first request** (`monkeypatch.setattr(settings, "RUNS_ROOT", str(tmp_path / "runs"))`;
   precedent `tests/integration/api/test_sandbox_ref_scoped_endpoints_api.py:46`). The text above does not mention it and a
   two-fault fix alone would trip it. By code reading (not run, to avoid writing into the real `runs/`): `backend/.env:8` sets
   `RUNS_ROOT=../runs`, the repo-level `runs/`; `RunSandbox.__init__` resolves it (`sandbox.py:598`); and the admission gate's
   `ReadOnlySandbox.list_prefix` reaches `_ws()`, whose `ensure()` mkdirs the source sandbox (`sandbox.py:619-643, 681-690, 1787-1792`).
   So every launch that reaches admission would create `runs/<random-user>/<source-run>/`, and a v2 seed would also `git init` there.
   (INFERRED context: 334 top-level `runs/` dirs, each a random uuid holding one run, were touched between 2026-10-01 20:00 and
   2026-10-02 03:30, which looks like unpinned tests rather than the four seeded accounts.)
3. **Seed an admissible source.** Two shapes, both verified 8/8 (probe section 2). Either keeps the 422 and the principal
   dependency intact. Stubbing `admit_chain_launch` out of the test would presumably also pass (not run) but stops exercising the real
   gate; not recommended.
   - *Legacy-shaped (minimal: no git, no finalization row)*: after the bare row, `RunSandbox(user_id, run.id).write(f".chain/{run.id}/summary.md", f"run_id: {run.id}\n")`.
     Admitted through `_select_legacy_payload_or_refuse` (Requirement 7).
   - *v2-shaped (what the QA-KB-057 sketch asks for, about 12 lines)*: `RunSandbox(user_id, run.id)`, `ensure()`, `git_init_sandbox()`, write the three flat files
     (`.chain/summary.md` with `run_id:` and `output_filename:` lines, `.chain/logs.jsonl`, `.chain/user_stories.md`),
     `commit_all("snapshot", paths=[], force_add=frozenset(<the three>))`, `create_tag("v1")`, `create_run_ref(run.id)`, and add a
     `RunFinalization` row with `published_status`, `candidate_status`, `payload_chainable=True`, `commit_sha`, `internal_ref`
     (`refs/ideaflow/runs/<id>`), `git_tag="v1"`. Traps: `.chain/` is gitignored, so force-add is mandatory; pass `paths=[]`, not the
     list (a second, non-forced `git add` of an ignored path exits 1); `read_finalization_record` treats a row with any of
     `run_id, published_status, candidate_status, payload_chainable, commit_sha` NULL as absent (`finalization.py:145-154`);
     and `is_legacy_source` classes the source legacy unless `refs/ideaflow/runs/<id>` resolves (`run_commands.py:4937`).
   - There is NO reusable real-source builder. The two helpers the QA-KB-057 sketch names are mock-based:
     `tests/agents/test_chain_exact_ref.py` stubs the sandbox and `read_finalization_record` with `MagicMock` and `patch`, and
     `tests/agents/test_finalizer_v2.py` drives the finalizer with a `FakeSandbox` over a mock DB.
4. **Strengthen two assertions that are weaker than their names.** `test_run_minted_with_legacy_block_intact` (`:318-331`) only
   asserts `_RecordingEngine.invoked`; it never checks the block survived (probe E4: it does, the marker is in the persisted input).
   `test_legacy_block_not_stripped_without_source_run_id` (`:296-316`) asserts only the audit count. A guard that stripped
   unconditionally and silently would pass the first.
5. **Repoint the stale path** in the comment at `frontend/e2e/tests/ts-v2-chain-versioning.spec.ts:8` (confirmed still
   `backend/tests/unit/test_duplicate_context_guard.py`). Spec traceability tables name the old path too and count the guard as
   covered (`specs/019-sandbox-git-versioning/bugs/GIT_VERSIONING_GAP.md:272`,
   `.kiro/specs/sandbox-git-versioning-v2/gap-closure-review.md:140` and `:608`); they are dated snapshots, left alone.

### Blast radius

- **Fault 1 class** (fixture overrides only `get_current_user`; the route depends on `get_current_principal`). The principal-gated
  routes are `POST /api/runs`, `/{id}/resume`, `/{id}/messages`, `/{id}/revisions` (`run_commands.py:3263, 628, 1780, 5603`) and
  `POST` and `PATCH /api/user-workflows` (`user_workflows.py:674, 951`). A static cross-tab of the 40 backend test files that mention
  those URLs against their dependency overrides finds exactly two that override only `get_current_user` while calling a principal-gated
  route: this file and `tests/unit/test_workflow_override_e2e.py`, already carded as [ISS-947](20261002-0107-ISS-947.md) (QA-KB-088).
- **Fault 2 class** (a bare seeded source row sent as `source_workflow_run_id` to a workflow that declares `chains_from`: `backlog`,
  `ppt_v2`, `prototype`, `user_stories`). In the tests, only `tests/integration/api/test_rest_run_launch_api.py:835-896`: its foreign
  and unknown source tests send `pipeline_type="user_stories"` and expect 200 with the link dropped, but the gate answers 404 by design
  (`run_commands.py:5323-5328`, "IDOR by design, Requirement 6 AC 1"). That is the stale-test half of
  [ISS-949](20261002-0107-ISS-949.md) (QA-KB-061); the link is INFERRED, this analysis did not run that file.
- **Product callers of the broken thing: none.** `launch_run` is the only HTTP caller of `_launch_run_core`; the other caller,
  `run_trigger_workflow` (`backend/agents/execution_engine/kernel_services.py:1664`), passes no source id.
