# FIX-425

## What was wrong

Stop a fan-out run **while a wave is in flight** and that wave's `wave_runs` row
stayed at `status="running"` forever, for a run that was plainly terminal. Anyone
reading the table directly saw a live wave on a dead run. Full evidence in
[ISS-098](20260812-1153-ISS-098.md), which reached it from the
[ISS-091](20260812-0654-ISS-091.md) probe work (probe 3 confirmed Stop does raise
`CancelledError` through `run_fanout`) plus a code read.

Cosmetic rather than data-losing, which is why it stayed `trivial`: the WR-01
stale-row sweep (`wave_scheduler.py:304-313`, now `:310-319`) flips such rows
`superseded` on the next resume, so no resume decision is ever made on the stale
value and the durable record self-corrects.

## Root cause

`backend/agents/capabilities/strategies/wave_scheduler.py:345` (the card said
`:340`; the file has since gained the ISS-131 `runs_agent_inline` attribute above
it). The wave dispatch loop wraps its `async for event in runner.run_fanout(...)`
in a single `except Exception:` arm whose whole job is to flip the in-flight wave's
row terminal (`failed`) and emit `wave_failed` before re-raising.

`asyncio.CancelledError` has inherited from `BaseException`, **not** `Exception`,
since Python 3.8. A Stop-during-a-wave therefore skipped that arm entirely, the
`await runner.update_wave_run(row_id, ...)` never ran, and the row recorded by
`record_wave_run(..., status="running")` at `:320` was never updated. The
`completed` flip at `:352` is equally unreachable on that path — the row simply had
no writer at all after cancellation.

Single-site defect, confirmed by grep: the ONLY non-test writers of the flip are
`wave_scheduler.py:318` (WR-01 sweep), `:346` (failed) and `:352` (completed), all
inside this one loop. `fanout_batch` records no wave rows, so there is no sibling
caller to fix.

## What changed and why there

**`backend/agents/capabilities/strategies/wave_scheduler.py`** (+13, no deletions,
no behaviour moved):

- `import asyncio` added to the stdlib import block. Stdlib only — the module's
  import-purity comment (INV-13 / import-linter) is about `agents.execution_engine`
  and `app.*`, neither of which is touched.
- A new `except asyncio.CancelledError:` arm placed directly ABOVE the existing
  `except Exception:` arm, on the same `try`, so the fix sits at the one place every
  wave's row transition already routes through. It does exactly two things:
  `await runner.update_wave_run(row_id, status="cancelled")` and a bare `raise`.

Deliberately the narrow arm and **not** the one-token `except BaseException:` the
issue card offered as its first option. `yield event` lives inside the same `try`,
so the broad form would also catch the `GeneratorExit` thrown there whenever the
engine closes this generator early — and both awaiting and yielding inside a
`GeneratorExit` handler raise `RuntimeError: async generator ignored GeneratorExit`.
That would have traded a cosmetic stale row for a real teardown crash on every early
break.

`status="cancelled"` (over reusing `failed`) matches WR-01's precedent of a new
free-String status value and keeps the durable record honest about which way the
wave ended. `update_wave_run` on the kernel side
(`kernel_services.py:649-657`) is already best-effort — it no-ops without a scoped
store and swallows its own exceptions — so this adds no new failure mode to the
cancel path.

### Deliberately NOT changed

- **No `wave_failed` event on the cancel path.** The `except Exception:` arm yields
  one; a cancelled run's terminal event is `pipeline_cancelled` from the engine, and
  inventing a new wave-level event for it is beyond what
  [ISS-098](20260812-1153-ISS-098.md) asks for and would move the FE event surface.
- **The WR-01 stale-row sweep** (`:310-319`) — still correct and still the safety
  net for a hard crash (where no handler runs at all). This fix only removes its work
  on the graceful-cancel path.
- The `runs_agent_inline = False` attribute at `:166` is
  [FIX-424](20260831-1652-FIX-424.md)'s uncommitted change in the same file, left
  byte-untouched.

## Migrations

None. `wave_runs.status` is a free `String` column (no `sa.Enum`), so the new
`cancelled` value needs no schema change — the same argument WR-01 made for
`superseded`. No new dependency.
