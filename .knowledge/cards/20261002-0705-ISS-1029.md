# ISS-1029

## Description

Sibling of [ISS-937](20261001-2231-ISS-937.md) (QA-KB-083) and of [ISS-1028](20261002-0705-ISS-1028.md), found because ISS-937 is already detectable by a test nobody had seen fail. `backend/tests/security/test_no_projection_reads.py` ("T7") is the guard for [ADR-0013](20260916-ADR-0013.md): it AST-scans `backend/app` for reads of `users.tier` / `users.is_admin` and fails unless each one is declared display-only in `backend/tests/security/projection_read_allowlist.txt`.

At HEAD `024c03ef8`, run one file at a time from `backend/` (`DATABASE_URL=sqlite:///:memory: .venv/bin/python -m pytest tests/security/test_no_projection_reads.py -q`), it gives `1 failed, 1 passed`, and the failure names the ISS-937 reads:

```
app/api/settings.py::get_preferences::tier   (app/api/settings.py:341)
app/api/settings.py::update_preferences::tier   (app/api/settings.py:388)
```

The guard has three gaps of its own:

1. **It sees only attribute loads on `user` / `*_user` names.** `_findings` (`test_no_projection_reads.py:59-87`) accepts an `ast.Attribute` whose `.value` is an `ast.Name` that `_is_user_binding` approves (`:49-56`: `name == "user" or name.endswith("_user")`). `getattr(current_user, "is_admin", False)` is a `Call`, so `run_commands.py:2655` ([ISS-1028](20261002-0705-ISS-1028.md)) is never reported. Other receiver names (`u`, `created`, `row`, `request.user`) are skipped by construction; the ones in `admin.py` today are display or projection writes, which is why nobody noticed.
2. **Findings collapse per function.** The key is `path::scope::attr` (`:143`). `update_preferences` reads `user.tier` twice, at `:374` (the 403 gate) and `:388` (a response flag), and the guard reports one signature, at the later line. The tempting way to green the guard, `app/api/settings.py::update_preferences::tier  # response field`, would also pre-approve the gate read. The docstring of `test_allowlist_has_no_stale_entries` (`:166-172`) names this risk ("silently pre-approve a future read that happens to land in the same function"), and the key design allows it.
3. **The allow-list claims there is one decision-context read.** `projection_read_allowlist.txt:21`: "The ONE intentional decision-context read" (`cognito_admin.py::is_last_admin::is_admin`). [ISS-1028](20261002-0705-ISS-1028.md) is a second one, and gap 1 hides it.

## Why the root cause implies it

ISS-937 is the case the guard exists for: a gate that reads `user.tier` and that no functional test notices "because the column is usually right" (the guard's own module docstring). The two reads predate the guard's last rewrite (`b2a621f84`, 2026-09-17; the `can_use_model(user.tier, ...)` lines came from `d027f16bd` and `b87123e06`, 2026-08-29 and 2026-09-01), and no card, ledger row or report mentions the guard failing: INDEX.md, LEDGER.md, BUGS.md and `reports/` have no reference to it.

## Evidence

CONFIRMED, executed (2026-10-02): the test run above, and a one-off AST scan of `backend/app` (scratch script, not in the repo) listing every read of `.tier` / `.is_admin` with any receiver plus `getattr(..., "tier" | "is_admin")`. The guard's own receiver rule saw eight reads (`admin.py:224-225`, `auth.py:210-211`, `settings.py:341/374/388`, `cognito_admin.py:225`). Outside it: `request.*` payload fields, `created.*` / `u.*` reads in `admin.py` that are display or projection writes, `m.tier` (a model's display tier), and `run_commands.py:2655`, the only decision-context one.

CONFIRMED, read: `test_no_projection_reads.py:49-56, 59-87, 143, 166-172`; `projection_read_allowlist.txt:21`; `.github/workflows/ci.yml:336-337` runs `pytest tests -m "not live and not requires_api_key and not requires_postgres and not requires_postgres_populated_migration"`.

INFERRED, not driven: that CI is red on this file (it carries none of the excluded markers, but I did not see a CI run), and that it has been red since `b2a621f84` (not run at that commit).

## Expected vs actual

- Expected: a read of the projection in a decision context fails the guard whatever syntax it uses, and an allow-list line approves exactly the read it describes.
- Actual: red on the known reads, blind to `getattr` and to other receiver names, and one line can approve a whole function.

## Fix direction

Order matters. Fix [ISS-937](20261001-2231-ISS-937.md) first (and decide [ISS-1028](20261002-0705-ISS-1028.md)); otherwise the guard stays red on known violations and the fixer is tempted to allow-list them. Then:

- Make `_findings` also flag `getattr(<name>, "is_admin" | "tier", ...)` with a constant second argument, and decide whether to widen the receiver rule or to flag every `.tier` / `.is_admin` load in `backend/app` except an explicit list of safe receivers.
- Give each allow-list signature enough to tell two reads in one function apart (a per-function ordinal, or the source line text), so a display read cannot approve a gate read.
- Correct the "ONE intentional decision-context read" comment to match whatever ISS-1028 decides.

## Test notes

The guard is its own test. Add a case per gap: a source string containing `getattr(current_user, "is_admin", False)` must be reported; two reads of `user.tier` in one function with only one of them allow-listed must still report the other.
