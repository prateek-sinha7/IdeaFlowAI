# ISS-954

## What happened

[ISS-940](20261001-2233-ISS-940.md) (QA-KB-037 sibling) listed these two handlers under "Same shape, lower
plausibility, not carded separately" and gave no fix direction for them. [FIX-711](20261002-0215-FIX-711.md) fixed
ISS-940's version picker and resolved that card, so these two sites get their own card here. Otherwise the finding
would only survive inside a resolved card.

## Root cause (CONFIRMED by source read; the behaviour is INFERRED)

`frontend/src/components/layout/DashboardLayout.tsx:2903-2909` (notification panel, a run not already loaded):

```ts
const token = getToken();
if (token && onSelectWorkflowRun) {
  setMainView("execution");
  router.push(routes.runStream(runId));
  void getWorkflow(token, runId)
    .then((fetchedRun) => { onSelectWorkflowRun(fetchedRun); })
    .catch(() => { /* non-fatal */ });
```

`DashboardLayout.tsx:3460-3464` (completion toast, FIX-215 fallback when the run is not in `recentRuns`) has the same
`getWorkflow(token, toast.workflowRunId).then((fetchedRun) => { onSelectWorkflowRun(fetchedRun); })`.

Neither checks, when the response lands, that this open is still the latest. Two opens A then B, with responses
arriving B then A, call `onSelectWorkflowRun(A)` last, while the route is B's. ISS-940 explains why the page-level
guard cannot catch this: `handleSelectWorkflowRun` in `page.tsx` claims its switch generation at entry, which is
arrival order here, and it is handed a full record, so `isSwitchGenerationStale` has nothing to trip on.

## Why it was not fixed with FIX-711

ISS-940's fix direction covered only the History handler. Here the fix has to answer a question the card does not:
which navigations should supersede a pending notification or toast open? Only the next notification or toast, or any
route change (sidebar, History row, a direct URL)? A counter shared by these two handlers alone would miss the second
kind.

## What settles it

Write a vitest on `DashboardLayout` with two deferred `getWorkflow` promises: open notification A, open B, resolve B
then A, and assert the last `onSelectWorkflowRun` call is B. Severity is low: it needs two opens inside one fetch
window.
