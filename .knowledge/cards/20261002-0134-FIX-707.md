# FIX-707

## What was wrong

Bug QA-KB-034 is a static reproduction, validated 3/3 (see the validation section on
[ISS-634](20260831-0115-ISS-634.md)). The engine's roster seam replaced a strictly partial caller
roster with the compiled plan and recorded nothing. A caller that passed `agents=[spec]` got the
whole plan, and nothing in the logs said so.

- The root card is [ISS-877](20261001-2110-ISS-877.md).
- [ISS-878](20261001-2110-ISS-878.md) is its sibling. The trigger path sized a file-backed target
  from the unreconciled registry roster and completed it only when it was empty, using raw specs.

## Root cause (from the cards, re-checked before editing)

- **ISS-877.** In `backend/agents/execution_engine/engine.py:5004-5006`,
  `_roster_is_partial = bool(agents) and {a.id for a in agents} < _plan_ids` guards the rebind
  `agents = self._specs_from_plan(compiled.steps)` (now `:5015`). The branch had no logger call.
  The rebind overwrote the only reference to the caller's roster, and `pipeline_start` reports
  only the post-seam roster.
- **ISS-878 A1/A2.** At HEAD `024c03ef8`, `kernel_services.py:1594-1601` read
  `if not target_agents: target_agents = [load_agent_spec(s.agent_id) for s in compile_for_run(workflow_ref).steps]`.
  That has two effects:
  - A partial roster passed through, so `prototype_v2_revision` (1 of 3) and
    `prototype_v2_feature_revision` (1 of 5) minted `agent_count` 1.
  - The empty-roster fallback skipped the `display_name`/`produces`/`consumes` overlay, so every
    step of `prototype_v2` and `backlog` was named "Custom Agent".

Blast radius, re-checked by grep before editing:

- `_roster_is_partial` appears only at the seam.
- Every engine entry reaches the seam through `_execute_impl`, so one log line covers all of
  them: `execute()`, `_drive_resumed_stream` (used by `resume_run` and `_replay_clarify_run`),
  triggered runs and the test harnesses.
- `_specs_from_plan(` is called from `run_commands.py:3622` and `:3674`, and from `engine.py`
  `:5015`, `:13424`, `:15673`, `:15696`, `:16143`, `:16167` and `:16314`. The trigger block was
  the only file-backed roster resolver that still completed only an empty roster with raw
  `load_agent_spec` specs.

## What changed, and why there

1. **`engine.py:5007-5014`** (ISS-877). One INFO record is written inside the
   `_roster_is_partial` branch, before `_specs_from_plan`:
   `roster expanded from plan: run=%s pipeline=%s requested=%s plan=%s`. It logs the requested ids
   and the plan ids, plus the run id and `pipeline_type`. That follows the card's two amendments
   to the register's count-only proposal. Because it is written before the rebuild, the record
   survives a `load_agent_spec` failure inside `_specs_from_plan`. It sits at the seam because
   every route converges there. The `not agents` branch does not log.
2. **`kernel_services.py:1584-1601`** (ISS-878 A1+A2). The file-backed branch of
   `run_trigger_workflow` now compiles the plan. When `len(target_agents) < len(_plan.steps)`,
   it rebuilds the roster with `get_execution_engine()._specs_from_plan(_plan.steps)`. This is
   the rule and the call `launch_run` uses at `run_commands.py:3621-3622`. One edit fixes both
   A1 (the minted `agent_count` now equals the plan's step count) and A2 (the overlays are
   applied).
   - The `load_agent_spec` import was orphaned by this edit and is removed. Case 2 imports its
     own copy.
   - The block comment, which claims parity with `launch_run`, now describes the empty-or-
     incomplete rule.

### Where this differs from the card

- **The handle is `get_execution_engine()`, not the card's `self._engine`.** The card's
  instruction is to make the block do what `launch_run` does, and `run_commands.py:3622` uses
  `get_execution_engine()`. There are three more reasons:
  - `run_trigger_workflow` never reads `self._engine`. It resolves the target through
    module-level functions, and the child run is executed by `get_execution_engine()` inside
    `_launch_run_core`'s driver.
  - Every existing trigger test, and the card's own test, builds `KernelServices.__new__`
    without `_engine`. With `self._engine` the ISS-878 test would have failed on an
    `AttributeError` instead of reaching its assertion.
  - The result is the same either way. In production the only `ExecutionEngine` is the
    singleton (`engine.py:16917-16922`), `KernelServices` is built with `engine=self` at
    `engine.py:5808`, and `_specs_from_plan` reads no instance state.
- **The compile in the file-backed branch is now unconditional, with no `try/except`.** At HEAD
  an uncompilable target already raised here when the roster was empty. When the roster is not
  empty it now also raises, before the mint, instead of minting a run the engine cannot
  compile. `_is_file_backed_workflow` already requires a `workflow.yaml`, the engine compiles
  the same plan for the child, and `compile_for_run` is `lru_cache`d.

### Deliberately not changed

- **ISS-878 part B is not fixed.** In `resume_run`, the progress line and its
  `offset >= len(agents)` check (`engine.py:15718-15729`) still use the registry roster length.
  The change would be log-only, nothing tests it, and the card itself marks it INFERRED, so it
  moves to [ISS-950](20261002-0134-ISS-950.md) (open). The mismatch is no longer silent, though:
  that resume now goes on to print this fix's `roster expanded from plan` line, which names the
  requested ids and the plan ids.
- **`launch_run`'s own pre-expansion (`run_commands.py:3604-3622`) still does not log.** That
  branch is the normal path for 18 of 41 workflow types (ISS-877, rejected alternative b).
- **No SSE event and no `pipeline_start` field were added** (ISS-877, rejected alternative a).
- **The [ADR-0008](20260811-ADR-0008.md) wording drift is untouched.** Superseding an ADR is
  the architect's call.
- **[ISS-634](20260831-0115-ISS-634.md) stays open.** Its harness defect is a separate issue
  (ISS-877, "Why this is its own card").
