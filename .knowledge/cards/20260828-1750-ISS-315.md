## What happened

On `/workflows/new` (the blank custom-composer), with at least one agent added to the canvas but
the "Workflow name" field left empty (only the "Untitled workflow" placeholder showing), clicking
"Save workflow" does nothing observable: no `POST /api/user-workflows` (or any workflow-related)
request fires, no toast or banner appears, and the name field gets no visible error state — no
red border, no inline message. The button itself stays fully enabled and clickable throughout.
The only side effect is the name `<input>` silently regaining DOM focus, which is indistinguishable
from any unrelated stray focus change.

Confirmed **CONFIRMED, 3/3, cold start every cycle** — each cycle re-navigated fresh to
`/dashboard`, then to `/workflows/new`, added one agent (Domain Discovery Agent, via "Add agent" →
"+ Add" → Escape to close the modal, confirming "1 agents" in the header with the name field still
empty), then clicked "Save workflow". All three cycles produced identical results: no new network
request beyond the page's normal `GET /api/workflows`/`GET /api/capabilities` calls, no visible
DOM change other than the input's focus state, and `document.body.innerText` contained no error
text at any point (checked for "required"/"Name is"/"enter a name").

## Expected vs actual

- **Expected:** attempting to save with an empty name gives the user a clear, observable signal —
  an inline validation message near the field, a red border, a toast, or at minimum a visibly
  disabled "Save workflow" button — so the user understands why nothing was saved.
- **Actual:** the save action is silently blocked client-side with no user-visible indication
  whatsoever. The button remains enabled; the only trace is a refocus of the name input that looks
  identical to an accidental click.

## Conditions established

- Route: `/workflows/new` (blank custom composer, Canvas/Simple view — reproduced in the default
  view reached straight off "Add agent")
- Tier: qa-admin (not varied — reproduces 3/3 without needing another tier)
- Entry path: `/dashboard` → `/workflows/new` (fresh nav each cycle) → Add agent → Escape → Save
  workflow, name field never touched
- Run state / data: at least 1 agent on the canvas, 0 agents also produces the same silent no-op
  by the same code path (not separately re-tested — the guard is name-only, agent count is
  irrelevant to it)
- No timing variation needed: identical result on the very first click every cycle, and repeating
  the click (per the original hunter's step 5) produces the same silent no-op again.

## Root cause

`frontend/src/components/workflow/composer/ComposerPage.tsx:1073-1085`, the Save-workflow button:

```tsx
onClick={() => {
  if (!name.trim()) {
    nameInputRef.current?.focus();
    return;
  }
  setCanvasResetLayoutSignal((n) => n + 1);
  handleSave(name.trim(), description.trim());
}}
disabled={saving}
title={!name.trim() ? "Name the workflow first" : undefined}
```

The guard exists and is correct — it stops `handleSave` (and therefore the `POST`) from ever
firing on an empty name, which is why no request is observed. But the ONLY user-facing signal is:

1. a `title` attribute — a native browser tooltip that only appears on hover, never on click, and
   is not read by anything triggered by the click itself; and
2. `nameInputRef.current?.focus()` — a focus call with no accompanying visual treatment (no red
   border, no `aria-invalid`, no error text near the field).

`disabled={saving}` means the button's disabled state is driven only by the in-flight save
request, never by name-emptiness, so the button never visually communicates "you can't click this
yet." There is no `saveError`/toast path taken for this case either — `setSaveError` (used a few
lines below in `handleSave` for the detached-step case, `:646-651`) is never called for the
empty-name guard, since the guard returns before `handleSave` is even invoked.
