# ISS-1088

## Description

**INFERRED sibling of [ISS-909](20261001-2216-ISS-909.md)**, filed by the QA-KB-081 analysis (2026-10-07). ISS-909's mechanism is a
registry fetch that feeds a launch gate and whose failure is dropped. The wizard has a second one, one `if` away in the same
effect: the deck-template catalog. The deck wizard cannot continue without a template, exactly as the web wizard cannot continue
without a design system.

Every mechanism line below was read at the cited line, and the missing banner was reproduced at component level by the analyzer
probe (`evidence/qa-kb-081/04-analyze-ds-registry-probe.test.tsx.txt`, output in `06-...-output.txt`: the test "EXPECTED: deck
template fetch failure shows the same banner" fails with `[deck template reject] page text mentions banner: false`, while its
control "web template fetch failure shows the 'Couldn't load templates' banner" passes). Only the browser-level reachability, a
failing `GET /api/ppt/templates` against a live backend, is inferred. Nobody has driven it.

## Condition (INFERRED)

`GET /api/ppt/templates` (`listPPTTemplates`, `frontend/src/lib/ppt-api.ts:47`) rejects with a non-401 error (network failure,
5xx), or resolves `[]`.

The empty arm is reachable by reading: `od_loader._all_templates()` returns `[]` after `logger.error("Templates directory
missing: %s", ...)` when the OpenDesign templates directory is missing (`backend/app/services/od_loader.py:171-176`),
`backend/app/api/ppt_templates.py:61-63` serves that as HTTP 200, and `@lru_cache(maxsize=1)` (`od_loader.py:171`) keeps it for the
life of the process. `od_loader.py:43-45` records a past production regression of exactly this kind: a mis-resolved root
"returned an empty template gallery".

## Mechanism (CONFIRMED by reading and by the component probe)

1. `frontend/src/components/workflow/LaunchWizard.tsx:683-689` (web branch of the template effect): the catch ends in
   `setLoadError(err.message)`.
2. `LaunchWizard.tsx:691-696` (deck branch, the same effect): the catch is
   `.catch((err: Error) => { if (cancelled) return; if (err.message.startsWith("401")) { handleSessionExpiry(); } })`. Any other
   failure is dropped: nothing is stored and nothing is shown.
3. The banner that would show it, `LaunchWizard.tsx:1375-1379` ("Couldn't load templates: {loadError}"), is generic. It is not
   web-specific, so setting `loadError` from the deck branch would surface it with no further change.
4. `frontend/src/components/workflow/ppt/PPTTemplateGallery.tsx:177-180` renders "No templates match your search." whenever the
   filtered list and the custom list are both empty, which includes an empty catalog; the footer (`:203-209`) says "0 templates".
   `prototype/TemplateGallery.tsx:206-208` has the same string for the web gallery.
5. The deck gate needs a template: `LaunchWizard.tsx:958`
   `return Boolean(selectedTemplateId && hasBuildInput && (!dsRequired || selectedDsId));`, with the pill "Pick a template" at
   `:1459`.

Result: the user sees a gallery that says no template matches a search they never typed, no error, no retry, a disabled Continue
and a "Pick a template" pill. They can still use "Upload custom" (`PPTTemplateGallery.tsx:122-129`), so it is not a hard dead end.
Both catches were born in the unified wizard commit `cc1097213` (2026-07-10, plan 37-07): the web catch had `setLoadError` and the
deck catch did not, from the first version (`git show cc1097213:frontend/src/components/workflow/LaunchWizard.tsx`, lines 237-249).
Nothing regressed; there is no last good commit to bisect to.

## Where it bites

`ppt` and `ppt_v2` only (`/create/ppt`, `/create/ppt_v2`, `/workflow/create?mode=ppt|ppt_v2`, and `/workflows/{id}/run` for a saved
deck workflow). The web family reports the failure (control test) and its template is optional (blank canvas), so it is not blocked.

## Why the root cause implies it

ISS-909's root cause is not about design systems as such. It is a fetch that feeds a gate in `LaunchWizard`, with its failure
dropped and no explicit state for "failed". The template effect has the same shape for the deck family, and the repair for ISS-909
(an explicit load state next to the data) is the thing this fetch lacks too.

## Expected vs actual

- **Expected:** a failed deck-template fetch shows the same "Couldn't load templates: ..." banner the web family shows, and an
  empty catalog is not worded as a search miss.
- **Actual:** no banner; the gallery says "No templates match your search."; Continue disabled behind "Pick a template".

## What would settle it (INFERRED -> CONFIRMED)

Offline, one file: in `frontend/src/components/workflow/LaunchWizard.test.tsx` mock `listPPTTemplates` with
`mockRejectedValue(new Error("500 boom"))`, render with `initialMode="ppt"`, and assert `screen.getByText(/Couldn't load
templates/)`. The probe holds this test and it fails today. In a browser, on `/create/ppt`, make `GET /api/ppt/templates` return
500 and read the Template step.

## Fix direction (not decided here)

`LaunchWizard.tsx:693-696`: call `setLoadError(err.message)` after the 401 branch, as `:688` does. Smaller still, and it stops the
two copies drifting apart again: give the two `.catch` handlers one shared function. Two cautions for whoever lands it:

- `loadError` (`:251`) is one slot with no reset (`setLoadError(null)` is never called). ISS-909's fix needs its own state for the
  design-system registry so the two failures cannot overwrite each other, and a Retry on the template effect would have to clear it.
- The wording "No templates match your search." for an empty catalog (both galleries) is a separate, cosmetic decision for the
  gallery components; it is not needed to close this card.

Severity: Low (needs the PPT catalog endpoint alone to fail).
