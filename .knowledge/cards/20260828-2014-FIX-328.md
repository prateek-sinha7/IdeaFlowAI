## What was wrong

Opening `/runs/{rootId}/versions/2` and then clicking any non-Preview tab silently
dropped the version pin: the URL collapsed to `/runs/{rootId}/{tab}`, the network
re-fetched `GET /api/runs/{rootId}` + `/api/runs/{rootId}/sandbox` (the ROOT run =
v1), and the Files tab rendered v1's deliverable while the picker read "Version v1".
Nothing told the user the pin had been lost. Register entry:
**BUG-20260828-090732-runs-id-versions** (`bug-hunter/ledger.md`).

## Root cause — two links in one chain, not two bugs

**1. The URL dropped the pin** — `handlePreviewPanelTabSelect`,
`frontend/src/components/layout/DashboardLayout.tsx:471-498`. Every tab's target was
built from `routes.run*(contentSourceRunId)` alone, and none of the five builders
(`frontend/src/lib/routes.ts:65-76`) could express a `/versions/{v}` segment. The
shallow `window.history.pushState(null, "", targetRoute)` then wrote that
un-versioned path. Confirmed live before the change: clicking `tab-files` at
`/versions/2` left the URL at `/runs/77f74563-.../files`.

**2. The pin was never applied even when the URL carried it.** `parsed.version` was
parsed and then discarded — the deeper half of the same chain, recorded separately as
[ISS-294](20260828-1725-ISS-294.md). Measured mechanism, which differs from what
ISS-230's card inferred: the tab click does NOT drive the re-fetch through
`reopenedRunIdFor` (`frontend/src/app/[...view]/page.tsx:182-196` returns the same
root id, so that effect early-returns and never refetches). The fetch is
`PreviewPanel.tsx:847-910`, keyed on
`activeRunId = viewingVersion?.id ?? liveRunId ?? latestId`
(`PreviewPanel.tsx:530`). `liveRunId` is `contentSourceRunId` — the run the shell
opened, i.e. the family ROOT on a `/versions/{v}` deep link — and it wins over
`latestId`. With `viewingVersion` only ever set by RunHeader's Version menu, a
URL-borne pin could not reach `activeRunId` at all. That is why URL, fetches and
rendered data reverted together: all three hang off the same un-pinned path.

Observed baseline requests during the tab click (before the change):
`/api/runs/77f74563-… ×2`, `/api/runs/77f74563-…/sandbox ×2`; zero requests for
`ef86e750-…` (v2).

## What changed and why there

**`frontend/src/lib/routes.ts`** — `runDetail`/`runSteps`/`runFiles`/`runWorkspace`/
`runAudit` take the pin as an OPTIONAL second argument and emit
`/runs/{id}/versions/{v}/{tab}`; omitting it yields the byte-identical un-versioned
route they always returned. `parseViewPath` lifts a `versions/{v}` pair out from
BETWEEN the run id and the tab, then parses the remainder through the existing tab
arms — so `version` rides along on `run-detail`/`run-steps`/`run-steps-agent`/
`run-files`/`run-workspace`/`run-audit` and the bare `/runs/{id}/versions/{v}` form
still resolves to `run-version`, unchanged. This is why a refresh of
`/runs/{id}/versions/2/files` still lands on Files: `reopenTabFor` keys on the
screen, which is now `run-files` rather than `run-version`.

**`frontend/src/components/layout/DashboardLayout.tsx`** — the single chokepoint the
blast radius named. `pinnedVersion` (new optional prop) is passed to all five entries
of `routeMap`, so the pin survives every tab click, and forwarded to `PreviewPanel`.
`routes.runSteps/runFiles/runWorkspace/runAudit` have exactly one caller each, so
this one edit covers every tab — no per-caller guards.

**`frontend/src/app/[...view]/page.tsx`** — `pinnedVersionFor(parsedView)` stops
discarding `parsed.version` and threads it to `DashboardLayout`, the same way
`initialMainView`/`initialSettingsSection`/`initialWorkflowType` are already derived
from the parsed path. Deliberately NOT done by resolving the version to a member id
inside `reopenedRunIdFor`: that selector is synchronous and the number→id resolution
needs the run family, which is fetched one level down in `DashboardLayout` and
already threaded to `PreviewPanel`. Reading the URL a second time in
`DashboardLayout` (via `usePathname`) was tried and rejected — it added a router
dependency that three existing `DashboardLayout.*.test.tsx` mocks do not provide,
i.e. it would have meant editing tests to accommodate the app.

**`frontend/src/components/preview/PreviewPanel.tsx`** — resolves `pinnedVersion`
against `sortedMembers` (already computed there) and applies the member as
`viewingVersion`. Set directly rather than through `handleSelectVersion`, because
that function treats "the latest member" as the Version menu's back-to-live shortcut
and nulls the override — which is precisely the family under test, whose v2 IS the
latest. The effect is keyed on the RESOLVED member id alone, so a tab switch (which
changes neither the id nor the family) does not re-fetch or re-pin, and "Back to
latest" is not immediately undone. `isViewingOlder` still governs the read-only
banner, so pinning the newest version correctly shows no banner.

Deliberately one-directional: a URL with no pin never CLEARS a menu-selected one, so
the existing (unfixed) Version-menu behaviour — [ISS-296](20260828-1724-ISS-296.md),
the menu does not write the URL — keeps working exactly as it does today.
