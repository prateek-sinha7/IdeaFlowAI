# ISS-864

**Resolved 2026-10-01 by [FIX-674](20261001-2114-FIX-674.md)** with the same edit that resolves the root card. The arm's
terminal branch now returns `applyTerminalStatus(prev, status)`, so `failed`, `cancelled` and `degraded` take their
marker from `terminalMarkers()`. In `useWorkflow.reconnect.test.ts`, the three `ISS-864` `it.fails` cases now pass;
vitest reports them as "Expect test to fail".

**Register source:** `QA-KB-008` in root `LEDGER.md` / `BUGS.md` (sibling, derived during its analysis on 2026-10-01).
**Root card:** [ISS-136](20260813-0005-ISS-136.md) holds the root cause and the fix location; this card is the
adjacent-state defect that the root's reported repro (a `degraded` frame) does not exercise.

**Claim status: INFERRED at the product level, REPRODUCED at the unit level.** The state-level defect below was
reproduced in a throwaway vitest harness (output quoted under "Evidence"). It has NOT been seen in a browser, and
cannot be today: no backend path emits `pipeline_reconnected` ([ISS-137](20260813-0005-ISS-137.md)). It becomes
user-visible the moment something re-emits the frame (for example [ISS-142](20260813-0005-ISS-142.md) restoring
`status` on the SSE `stream_attached` ack).

## What is wrong

The `pipeline_reconnected` reducer arm (`frontend/src/hooks/useWorkflow.ts:1469-1547`) resolves a finished run with a
hand-built patch (`:1515-1531`):

```ts
setPipelineState((prev) => {
  // Mirror pipeline_complete's agent finalization on success; for
  // failed/cancelled/error leave agents as-is but still resolve.
  const updated = status === "completed" ? prev.agents.map(...) : prev.agents;
  return {
    ...prev,
    isRunning: false,
    agents: updated,
    completedCount: updated.filter((a) => a.status === "done").length,
  };
});
```

It clears `isRunning` and nothing else. It never stamps the run-level marker (`failed` / `cancelled` / `degraded`)
that every other terminal path stamps through the one shared mapping `terminalMarkers()`
(`useWorkflow.ts:388-391`): `pipeline_complete` (`:1300`), the live cancel/fail arms, and the reopen reconcile
`applyTerminalStatus` (`:401-469`). The arm's own comment says it "mirrors pipeline_complete" but it mirrors only the
agent finalization, not the markers.

## Why the root cause implies it

[ISS-136](20260813-0005-ISS-136.md)'s mechanism is "this arm privately re-implements what terminal looks like instead
of calling the single shared implementation". The status LIST is one half of that re-implementation (the QA-KB-008
symptom); the state PATCH is the other half. Fixing only the list (add `"degraded"`) makes a `degraded` frame take
exactly the branch a `failed` frame takes today, so the degraded run would resolve `isRunning:false` with no `degraded`
marker.

## Expected vs actual

For `{type:"pipeline_reconnected", live:false, status:S}` with S in `failed` | `cancelled` | `degraded`:

- Expected: `isRunning === false` and `state[S] === true` (what `applyTerminalStatus(prev, S)` returns).
- Actual: `isRunning === false`, `state[S] === undefined`.

## Who reads the missing marker (read, not run in a browser)

1. `frontend/src/components/results/StepsOverviewSpine.tsx:423` `const failed = !isRunning && (pipelineState?.failed ?? false);`
   and `:464-467` `statusLabel = failed ? "Run failed" : isRunning ? "Running" : (pipelineState?.degraded) ? "Run degraded" : "Run complete"`.
   Marker unset means "Run complete". The comment at `:416-422` states the contract this arm breaks: "The run-level
   markers are mutually exclusive and always stamped by terminalMarkers()".
2. `frontend/src/components/layout/DashboardLayout.tsx:2603`
   `(pipelineState?.failed || pipelineState?.cancelled || pipelineState?.degraded || pipelineState?.divertedTo) ? "terminal" : laneHasDeliverable ? "complete" : "idle"`.
   Marker unset means the lane state is "complete" or "idle", never "terminal".
3. `frontend/src/components/preview/PreviewPanel.tsx:1117-1131`
   `liveFailureSignal = !!(pipelineState?.failed || pipelineState?.degraded)`. Marker unset means a terminal run with
   no deliverable shows the neutral empty state instead of the failure affordance (ISS-017).

The wording of item 1 is the same family as the closed [ISS-701](20260922-1030-ISS-701.md) (a degraded run must not
read as complete/failed in the Steps panel); that fix made the label depend on the marker alone, which is exactly why
a marker-less terminal resolve now reads "Run complete".

## Evidence

Scratch harness, outside the repo (session scratchpad `qa-kb-008/`): `repro.test.ts` imports `handlePipelineMessage`
and `applyTerminalStatus` from `frontend/src/hooks/useWorkflow.ts`, seeds a mid-run state with two idle agents, and sends
the frame. Run with
`cd frontend && npx vitest run --config <scratchpad>/qa-kb-008/vitest.config.mts` (jsdom, same setup file as the repo).

```
A degraded   -> {"isRunning":true,"ss":"run-1"}      // the QA-KB-008 bug: not resolved, sessionStorage not cleared
B failed     -> {"isRunning":false,"ss":null}        // resolved, but `failed` is undefined   (expected true)
C cancelled  -> {"isRunning":false}                  // resolved, but `cancelled` is undefined (expected true)
D applyTerminalStatus(seed,"degraded") -> isRunning false, degraded true   (PASS - the shared mapping is right)
Tests 3 failed | 5 passed (8)   -> A, B, C fail as predicted; D-H pass
```

`degraded` has no row of its own here because it cannot be asserted until the root fix lets that frame resolve at all;
after the root fix the same assertion applies to it.

## Fix

Same change as the root card's recommended fix, not a second edit: route the arm's terminal branch through
`applyTerminalStatus(prev, status)` (`useWorkflow.ts:401`) instead of the hand-built patch, so the markers come from
`terminalMarkers()`. Both state containers that receive the frame (`useWorkflow.handleMessage` via
`page.tsx:1570`, and `useRunStateStore.ts:584`) call the same `handlePipelineMessage`, so one edit in the arm covers both.

If the fixer takes only the root card's one-token floor, this card stays open: the floor closes the QA-KB-008 symptom
but not this one.

## Test notes (for the test-writer)

Add to `frontend/src/hooks/useWorkflow.reconnect.test.ts`, reusing `makeHarness()` / `seedState()`: a table over
`failed`, `cancelled`, `degraded`, each sending `{type:"pipeline_reconnected", live:false, status, pipeline_run_id:"run-1"}`
and asserting `isRunning === false` AND `state[status] === true`. Add the converse for `completed` and `diverted`:
none of `failed`/`cancelled`/`degraded` is set. All the failure-marker rows fail today with `expected undefined to be true`.
The `degraded` row also covers the root card's symptom, so it needs the root fix to get as far as the marker.

## Not filed

Foreign-run bleed on this frame (a concurrent run's `pipeline_reconnected` resolving the viewed run) is real by design:
`frontend/src/lib/__tests__/wsRunScope.test.ts:144` pins `pipeline_reconnected` as an intentionally cross-run lifecycle
frame. It is not implied by this root cause and the frame is dead, so no card.
