# ISS-1114

**Register source:** sibling derived during the `QA-KB-100` analysis on 2026-10-08 (root [ISS-1092](20261007-2308-ISS-1092.md)). Not its own bug row, and not part of the root's fix.

**Confidence:** CONFIRMED for the save and the compile (`evidence/qa-kb-100/analysis-05` W0, W5). The live launch was not driven.

## Decision needed

Should the privileges [ADR-0039](20260904-1424-ADR-0039.md) gave to a saved row (exec, spawn_subagents, no CAP-03) stay reachable by a caller whose tier cannot run the Composer?

## Condition

The Composer is enterprise-only because its base pipeline is `custom`, and `custom` is an enterprise entitlement (`entitlements.py:67`). Nothing forces a manifest-backed row to use that base:

- `create_user_workflow` gates on `can_run_pipeline(tier, body.base_pipeline_type)` (`user_workflows.py:703`). The caller picks `base_pipeline_type`.
- Basic and pro may run `ppt` (`entitlements.py:11-16`, `:37-41`).
- `analysis-05` W5, basic-tier caller: `POST` with `base_pipeline_type: "ppt"`, no `overrides_pipeline_type`, and a manifest whose step has `tools.exec: true`, `gates: [security, approval]`, `validators: [code_test]` returns **201**; the launch Case 3 compile of that row at `trust="db"` gives `exec=True`. Control W0, the same caller with `base_pipeline_type: "custom"`, gets **403**.
- At launch the row dictates its own type (`run_commands.py:3404-3407`) and the tier gate runs on that type (`:3452`), so it passes.

This is not the override bug. No override flag is involved, so fixing `merge_override_steps` and the override writers leaves it open.

## Why the root cause implies it

Same family: authorization keyed on where the bytes live (`db`) rather than who wrote them, which is the point [ADR-0038](20260902-1321-ADR-0038.md) makes against the crude fix in ADR-0039. ADR-0039 accepted the exposure for composed workflows and paired it with an enterprise entitlement in the same commit; the entitlement keys on a field the caller supplies.

## Options

- **a) Make the entitlement follow the content.** Refuse (403) a manifest-backed row, at save and at launch, unless the caller's tier may run `custom` or the row carries no privileged grant and no non-user-allowed capability. Consequence: basic and pro keep manifest rows that use only user-allowed things; a stored privileged row from a lower tier stops launching.
- **b) Require the Composer base.** A manifest-backed row must have `base_pipeline_type == "custom"`. Consequence: override rows (which use the built-in's base) and any wizard-saved manifest row need an explicit exemption.
- **c) Accept ADR-0039 as written.** Consequence: any tier that can run a built-in can run host code (python, pytest, ruff behind a self-approval) by choosing that built-in as the base. ADR-0039's residual-risk list does not say so.
- **d) Build ADR-0038's per-owner `resource_policy`.** The largest change, and the only one that separates budget from tool tier.

Analyzer's view, not a decision: a) or b) before c). Option c) contradicts the premise of the `exec_command` docstring ("exec is engineer-only", `local.py:479`).

## After the decision

A human sets this card's `status`. For a) or b) a bug row is filed for the fixer; for c) ADR-0039 gets a residual-risk addendum and this card is closed as accepted; d) is a spec.

### Root cause (one mechanism)

A saved row's privilege and its entitlement come from two inputs that nothing connects.

1. **The privilege is the trust of the compile.** `_TRUSTED_SOURCES = {"file", "builtin", "db"}` (`compiler.py:228`); `trusted = trust in _TRUSTED_SOURCES` (`:324`). At `db`, `_check_trust` returns at once (`:506-507`), the exec/network/secrets/spawn rejection is skipped (`if not trusted`, `:1023`), the Limits ceiling is skipped (`:467`), and `apply_cap` resolves the trusted cap (`permission_caps.py:75`, `:80-103`: exec, spawn_subagents, git and the tool packs). Every plain saved row compiles at `db`, at three sites that are each given no tier: the save check (`user_workflows.py:121`), launch Case 3 (`run_commands.py:3374-3376`, `"user" if _inline or user_workflow_row.overrides_pipeline_type else "db"`) and the conditional-route trigger (`kernel_services.py:1616`).
2. **The entitlement is a label the caller chose.** The only tier check on a row is `can_run_pipeline(tier, body.base_pipeline_type)` at create (`user_workflows.py:744-748`), and at launch the same label read back from the row (`run_commands.py:3437-3438`, gate at `:3483`). The label need only be in `SUPPORTED_PIPELINE_TYPES` (`:728`). `custom` is the one enterprise-only label (`entitlements.py:67`); `ppt` is entitled to basic, pro and enterprise (`:14`).
3. The Composer is "enterprise-only" only because the Composer UI happens to send `custom` (`ComposerPage.tsx:944`). Another entitled label on the same manifest is never asked the Composer question.

History from git, so nobody reads this as a deliberate pairing. `custom` has been enterprise-only since `925121744` (2026-05-19) and the create-time gate since `9d733d543` (2026-06-14). Manifest rows launched from `24332e0c5` (2026-08-14) while `db` was UNTRUSTED, so the label did not matter. `ea2db4e02` (2026-09-04, [ADR-0039](20260904-1424-ADR-0039.md)) made `db` trusted; the entitlement change in that same commit entitled `pdf_to_prototype` and `sample_subagents_parallel` on the enterprise tier, which are two file pipelines and have nothing to do with the Composer. No rule tying `db` trust to the Composer entitlement was ever written.

### Where the fix belongs

Decide the trust of a saved row once, from the caller's entitlement, and give that one answer to every compile site. Two findings fix the shape.

- **It has to be the real compile, not a check in front of it.** Probe `[N]`: `tool_sets: [internet, pptx, spawn_subagents, ask_user, playwright]` compiles at `user` without an error and comes out as `['playwright']`; at `db` it comes out whole. The user cap narrows silently, so a dry-run gate ("does it compile at user?") or a walker beside `_model_entitlement_error` would pass the manifest while the real `db` compile still grants the packs. A walker would also be a second copy of the compiler's rules, while [ADR-0039](20260904-1424-ADR-0039.md)'s locked constraint names the compiler as "the SOLE enforcement point for manifest trust".
- **The compile trust is sufficient.** Mutation probe `analysis-04` (a monkeypatch of `WorkflowCompiler.compile`, no source edited) turns `db` into `user` for a caller who may not hold the Composer. Save is 422 for basic, hexaware and pro; the stored legacy row is refused at launch with the mint not reached; PATCH is 422 with the stored manifest unchanged; the trigger raises `CompilerError` before the mint; every row of the `[M]` table is refused or narrowed to nothing; benign controls still save and launch; the enterprise `custom` row still launches with `exec=True` and `_trust == 'db'`.

Proposed shape (INFERRED, not applied): one helper in `backend/app/api/run_engine.py` beside `_model_entitlement_error` (`:609`) and `_trigger_entitlement_error` (`:674`). That module is the app-layer home of entitlement helpers; it is already imported by `user_workflows.py` (`:48-52`) and `run_commands.py` (`:95-101`) and, lazily, from the kernel (`kernel_services.py:1604`). Its answer: `user` for an inline manifest or an override row; otherwise `db` only when `can_run_pipeline(effective_tier(user, principal), "custom")` holds, else `user`. Call sites:

1. `_compile_check_manifest` takes the trust (`user_workflows.py:84-140`); `_validated_manifest` passes it; POST insert, POST upsert and PATCH hold the principal.
2. Launch Case 3 uses it for `_trust` (`run_commands.py:3374-3376`). `caller_tier` is computed later today (`:3762`) and has to move above the compile. The persisted `_trust` (`:3431`) already carries the decision to resume.
3. The trigger cannot read a tier: clamp it, see [ISS-1164](20261009-1558-ISS-1164.md).

Why keyed on the live tier and not on the stamped label (option b): the frontend documents rows in the wild whose label is stale (`base_pipeline_type` is immutable and a Composer manifest sits inside; `frontend/src/store/api/userWorkflows.ts:858-869`, the shared-`workflowType` leak). A label rule would demote an entitled owner's rows; a tier rule demotes nobody who is entitled and promotes nobody who is not. The dev DB holds none (`analysis-02`: 2 plain manifest rows, both `custom`, both enterprise owners), which says nothing about production.

### Traps for the fixer

- Keep `db` trusted. Do not change `_TRUSTED_SOURCES` or `TRUSTED_TRUST_LEVELS` (ADR-0039 locked constraints; the enterprise Composer needs them) and do not flip `_compile_check_manifest` globally ([ISS-1092](20261007-2308-ISS-1092.md)). The inline manifest stays `user`.
- INV-1 and SC-001: no `custom` literal and no tier lookup under `backend/agents/`. The kernel only receives an answer or calls the app-side helper it already imports lazily; [FIX-771](20261009-0126-FIX-771.md) locks "no tier travels into the kernel and no kernel -> app import is added".
- Save must equal launch: the same helper at both, or a row saves that launch refuses (or the reverse).
- A verbatim copy of an entitled pipeline does not compile at `user` for 14 of the 30 pipelines some tier may run, even with the row's own built-in as the baseline (`analysis-03`): the workflow-level `context_provider: previous_run` of every `*_revision`, `limits.max_subagents: 200` of `backlog` and `prototype_v2`, `deliverable: ppt`, and `spawn_subagents` of `sample_subagents_parallel`. For basic that is `ppt`, `ppt_revision` and `user_stories_revision`. No frontend flow stores such a copy (the wizards save overrides, which take workflow-level fields from the file, and the Composer sends `custom`), but sync-from-file can, so a lower tier's synced row stops launching. Run the probe's `SELECT` (`analysis-plugins/query_saved_rows_by_shape.py`) on the real database first, and tell the owner if exemptions are wanted.
- A refused compile at the trigger raises mid-run and fails the parent run; at launch it is `invalid_workflow_manifest` (422).
- Stale text that states the premise this card removes: `engine.py:5910-5913` ("a user/db manifest can never provision the exec workspace"), `local.py:479` ("exec is engineer-only"), `run_commands.py:2523-2527` ("the identical manifest can already be POSTed ... so the same bytes were always reachable"). Update them with the change; the rest of the stale `user/db` wording is [ISS-1116](20261008-1444-ISS-1116.md), which asked to be settled after this card.
- A fixer that guards only exec and spawn leaves the rest of the `[M]` table open. The Expected names two grants; the closed set is the whole table.
