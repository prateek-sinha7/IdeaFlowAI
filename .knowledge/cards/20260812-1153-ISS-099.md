# ISS-099

## Title

**A retry-enabled step records a CANCELLED step as reusable.** When `step.retry.max_attempts > 0`, `_dispatch_step_with_retry` (`engine.py:7236-7274`) runs the strategy inside an attempt loop and, on normal completion of `strategy.run`, unconditionally yields `step_completed` carrying the step's `input_hash`. A gate rejection ends `strategy.run` normally (the producer yields `pipeline_cancelled` then returns), so the success branch fires anyway and the stream carries `pipeline_cancelled` followed by `step_completed`. That `step_completed` is exactly what `_find_reused_completion` matches on a later restart, so a step the user REJECTED would be skipped as already-done — the same "durable record of work that did not happen" family as ISS-091, one layer down. **Dormant, not theoretical:** `grep` finds no `retry:` key in any manifest under `agents/workflows/`, so `max_attempts` is 0 everywhere and the gate-TRUE branch never runs today. It is reachable in principle through `agents/workflows/selections.py`, which accepts a user-supplied `retry: {max_attempts: N}` on a composed workflow. FIX-232 deliberately did not fold this in: the dispatch-loop fix already stops the run at the step boundary, and suppressing events mid-stream is a different and riskier change than observing them. Suggested fix: do not yield `step_completed` when the attempt ended on a terminal event.
