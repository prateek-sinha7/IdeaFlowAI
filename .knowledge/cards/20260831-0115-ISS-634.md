## Symptom

```
test_split_tool_xml_untouched_for_tooluse_agent
  tool-using agent stream was perturbed by the sanitizer (must be…)
test_clean_stream_passes_through_unchanged_for_toolless_agent
  clean tool-less stream was perturbed (must be byte-identical…)
test_lone_lt_and_html_at_boundaries_chunk_identical_for_toolless_agent
  tool-less prose with a lone `<` / `<div>` / `a < b` at chunk…
test_benign_held_tail_survives_flush_no_content_loss
  a benign held tail was not flushed verbatim at stream end
```

## Why this ranks above the bigger clusters

Every one asserts that content survives the sanitizer unchanged. A sanitizer
that alters a CLEAN stream is dropping or rewriting text a user is reading —
and the last guard is explicitly about **content loss at flush**. Four tests is
a small number; the failure mode is not.

Pre-existing on `feat/conditional-gates`, verified at `602296cc8`.


## 5-fixer (2026-08-31): the root cause on this card is WRONG — escalated, no code changed

The sanitizer is NOT perturbing anything. Driving `_ChunkStreamSanitizer` directly
with the exact four inputs (real `_strip_fabricated_tool_xml` for the tool-less
cases, identity for the tool-using case) returns them **byte- and chunk-identical**:

```
clean    ['Domain analysis: ', 'the system manages tasks ', 'for a single user.']
lone<    ['Use the ', '<', 'div> wrapper and the ', '<', 'Input> field. Note a ', 'a < b', ' comparison.']
heldtail ['Result is ', 'x ', '<f']            # join == input join, tail flushed verbatim
tooluse  ['Here is the result. <function_calls><invoke name="read_', 'file">…</function_calls> Done analyzing.']
```

There is no content loss and no rewriting of a clean stream. The "Why this ranks
above the bigger clusters" section is arguing from a symptom that does not exist.

### What actually fails

`backend/tests/agents/test_chunk_sanitizer.py::_drive_single_agent` calls
`ExecutionEngine.execute(agents=[spec], …)` and documents itself as driving "a
single-agent pipeline". It does not. At
`backend/agents/execution_engine/engine.py:1720-1722`:

```python
_plan_ids = {s.agent_id for s in compiled.steps}
_roster_is_partial = bool(agents) and {a.id for a in agents} < _plan_ids
if compiled.steps and (not agents or _roster_is_partial):
    agents = self._specs_from_plan(compiled.steps)
```

A one-agent roster is a strict subset of the compiled plan, so the engine
**replaces it with the full plan** and runs every agent. The patched
`create_runner` gives each of them the same scripted model, so `emitted` is the
input deltas repeated once per agent — 6× for `user_stories`, 3× for
`prototype_revision`. Every `assert emitted == deltas` fails on length alone,
and each per-agent slice is exactly the expected list.

`test_split_tool_xml_untouched_for_tooluse_agent` shows the same thing: the
first `prototype_revision` agent is tool-less so its copy is (correctly)
stripped, and the two tool-using copies pass through untouched — the gate works.

### Why it is red now and was green before

`_roster_is_partial` was introduced 2026-08-27 by `bab17c0b9` ("ppt_v2 pipeline,
run sandbox API, pptx layout verification") to fill in a genuinely partial roster
(`ppt_v2` reuses agents authored for `ppt`). The test file predates it
(2026-06-13, `0a901b41e`). The production change is intentional and load-bearing;
it invalidated the harness's premise as a side effect.

### Why the 5-fixer did not fix it

* Fixing it in the engine means distinguishing "caller deliberately passed a
  subset" from "roster is partial because the agents live in another pipeline" —
  `ppt_v2` is also a strict subset, so there is no signal to key on. That is a
  design decision, not a fix, and no card covers it.
* Fixing it in the test means editing four red tests with **zero** production
  change, on a card that does not say the expected behaviour was misstated. That
  is the app-bent-to-test inversion in reverse; it needs an explicit decision.
* The viable test-only route, if that is the decision, is the existing
  `execute(compiled_override=…)` seam — hand the harness a one-step
  `CompiledWorkflow` instead of relying on `agents=[spec]` being honoured — or
  filter `emitted` to the target `agent_id`. Either is a 4-test-writer /
  3-analyzer call, not a fixer's.

Sibling observation, not carded here: the roster expansion at engine.py:1721 is
**silent** — a caller that passes a subset gets agents it never asked for with no
log line. Harmless today (every production caller passes the full roster from
`get_pipeline_agents`), but it is what made this take a full drive-and-diff to see.

## QA-KB-034 validation (2026-10-01, static, 3/3)

Register entry QA-KB-034 ("Silent roster expansion") is the sibling observation above. The code has moved: the expansion is now at `backend/agents/execution_engine/engine.py:5005-5007` (`_roster_is_partial = bool(agents) and {a.id for a in agents} < _plan_ids` / `if compiled.steps and (not agents or _roster_is_partial): agents = self._specs_from_plan(compiled.steps)`). Verification for this sibling: type static, status passed (reproduced).
