# ISS-1025

Sibling of [ISS-907](20261001-2200-ISS-907.md) (QA-KB-079), found while bounding its blast radius. Status: CONFIRMED by a mutant probe. It is a
regression-guard gap, not a product defect: the resume driver is correct today (the validated twin test below passes on the real source). No bug
report names it. Evidence: `evidence/qa-kb-079/04-analyze-mutant-plugin.py.txt` (mutants T and U), `06-analyze-proposed-case-resume-driver-twin.py.txt`,
`07-analyze-run-output.txt` sections 3, 4 and 6.

## Condition

`ExecutionEngine._drive_resumed_stream` (`backend/agents/execution_engine/engine.py:15832`) is the shared re-entry stream of every restart driver
(`resume_run`, `_rearm_gate_run`, `_replay_clarify_run`, the user `POST /resume` wrapper; its docstring `:15852-15866`). It is the second feeder of
`_RunEventSink.persist` with a seq-carrying payload, next to `execute()` (the ISS-135 blast-radius table lists both):

- it stamps the requested seq into the dict it is about to persist: `data["seq"] = seq` (`:15941`);
- it persists that same dict: `actual_seq = await sink.persist(seq, event_id, event.get("type", ""), data)` (`:15948-15950`);
- it re-stamps the landed seq and advances its allocator ONLY when `persist` reports one:
  `if actual_seq is not None and actual_seq != seq: data["seq"] = actual_seq; if actual_seq >= next_seq: next_seq = actual_seq + 1` (`:15951-15954`);
- the frame it pushes to `live_queue` (`:15965-15967`) is that same `data`; `run_stream` turns `data["seq"]` into the live SSE `id:` cursor
  (`backend/app/api/run_stream.py:553-558`) while replay uses `row.seq` (`:430-439`).

No test makes this path collide. A chat-lane row taking the seq the resumed engine's counter still owns is exactly the FIX-240 hazard, and the
resume comment says so (`:15943-15947`: "a resumed run is exactly as exposed to the chat lane's concurrent seq allocation as a launched one").

## Why the ISS-907 root cause implies it

The root cause in [ISS-907](20261001-2200-ISS-907.md) is that the FIX-692 regression guard only exercises one entry point, one hop. The "other caller"
leg of that gap is this driver: [FIX-692](20261001-2200-FIX-692.md)'s coverage block names `execute()` as the only wrapper-level guard, and
[FIX-240](20260812-1852-FIX-240.md) shipped its re-stamp tests for `execute()` only (`test_run_events_db.py:366`).

## Proof (CONFIRMED, observed 2026-10-02 on feat/user-stories-v2 @ 024c03ef8 plus working tree)

1. Hop counter. A scratch plugin counted the calls to `append_event_at_or_after` and the `except IntegrityError` retries that moved past a taken seq
   (`real_hops`) over a faithful copy of it (control R). The five resume-driver test files: `test_restart_resume_db.py` 544 calls, 0 hops;
   `test_resume_ws_bridge_db.py` 117 calls, 0 hops; `test_resume_marker_workspace_db.py` 66 calls, 0 hops; `test_cancel_stops_resumed_run_db.py`
   2 calls, 0 hops; `test_resume_marker_seq_allocation.py` 1 call, 0 hops (730 calls, 0 hops). The only files that reach a hop are
   `test_run_events_db.py` and `test_run_events_payload_seq_db.py` (2 each, both drive `execute()` or the sink) and one cancel-API test (1).
2. Mutant T deletes the re-stamp for this driver only (`persist` answers with the REQUESTED seq when its caller is `_drive_resumed_stream`, which is
   the effect of deleting `:15951-15954`). Failing SETS compared with control R, file by file: identical in all five resume files and in both
   run_events files. Nothing notices.
3. Mutant U does the same for `execute()` (`engine.py:4208-4211`). `test_run_events_db.py::test_execute_restamps_seq_onto_the_frame_it_yields`
   fails (1 failed, 8 passed). The execute() re-stamp is guarded; the resume one is not.
4. The twin test (below) passes on the real source (1 passed), is killed by mutant T and by mutant H (the ISS-135 bug, no store re-stamp), and
   passes under U and under the in-place mutant A (an in-place store mutation is masked on the success path by this very loop, `:15951-15952`).

The 6 failures in `test_restart_resume_db.py` ([ISS-1013](20261002-0547-ISS-1013.md) and others), the one in `test_resume_ws_bridge_db.py` and the one
in `test_cancel_stops_resumed_run_db.py` also fail WITHOUT the plugin, with identical failing sets under R, T and U; [FIX-688](20261001-2140-FIX-688.md)
records the last two as pre-existing. They are not this card.

## Expected vs actual

- Expected: a test fails when the resume driver stops re-stamping, so the live frame, the durable row and the stored payload cannot disagree after
  a collision on a resumed run.
- Actual: nothing fails. Mutant T survives every existing test.

## What a regression would do (INFERRED, not run end to end)

The resumed run's frames go out through `live_queue` to the WS bridge. If the re-stamp were lost, the live `id:` would carry the requested seq while the
durable row (and every replay) carries the landed one, and `next_seq` would not advance past it, so the next event would collide in turn. That is the
Last-Event-ID corruption [FIX-240](20260812-1852-FIX-240.md) names as worse than the drop it fixed. What would settle it: a browser reconnect on a
resumed run that took a chat turn mid-stream; the offline twin below settles the code path only.

## Fix direction (test-only; engine.py is correct and stays untouched)

Add one case beside `test_execute_restamps_seq_onto_the_frame_it_yields` (`backend/tests/integration/repositories/test_run_events_db.py:366`), driving
the real driver with the same scripted `_execute_impl` and the same chat-lane write as that test. The validated scratch version is
`evidence/qa-kb-079/06-analyze-proposed-case-resume-driver-twin.py.txt`. In outline:

```python
monkeypatch.setattr(ExecutionEngine, "_execute_impl", _scripted_impl)   # arms kwargs["_sink"], chat row lands between two engine events
queue = asyncio.Queue()
await ExecutionEngine()._drive_resumed_stream(
    "run-1", agents=[], user_message="", pipeline_type="prototype", user_id="alice",
    session_id=None, parent_run_id=None, selections=None, start_seq=1, live_queue=queue)
# drain `queue` (skip the None sentinel); assert the collision happened (chat row seq 2, pipeline_cancelled 3, agent_chunk 4), then for each
# engine event: live frame data["seq"] == row.seq == row.payload_json["seq"]
```

- No `xfail`: it passes on today's source by design (the tests are the fix). Observe red under mutant T (and H) with the plugin in
  `evidence/qa-kb-079/04-analyze-mutant-plugin.py.txt` (`KB079_MUTANT=T`), green under R.
- Set `RUNS_ROOT` to a scratch directory when running outside the repo's own tests: the driver builds a `RunTrace` under it.
- Marker `@pytest.mark.issue("ISS-1025")`. One file at a time: `cd backend && .venv/bin/python -m pytest tests/integration/repositories/test_run_events_db.py -q`.

## Resolution — FIX-734 (2026-10-07)

Resolved by [FIX-734](20261007-1923-FIX-734.md), for register entry QA-KB-079. The test phase had not added the twin, so the
fix phase did. It is `test_resume_driver_restamps_live_frame_and_stored_payload_after_a_collision`, at
`test_run_events_db.py:422-487`. The test is the scratch version above with four adaptations:
- it seeds the run with the file's `_seed_run`;
- it carries `@pytest.mark.asyncio`;
- its marker is `ISS-1025`;
- it sets `RUNS_ROOT` to `tmp_path` through monkeypatch.

`engine.py` is untouched. The re-stamp it guards is now at `:15975-15978`, a 24-line shift from the numbers above.

Observed results:
- Shipped code: 10 passed.
- The 9 tests that existed before (`evidence/qa-kb-079/fix-08`): T 9 passed (it survives), U 1 failed.
- With the twin (`fix-02`): T 1 failed (the twin, `assert 2 == 3`), H 1 failed (the twin, `assert 3 == 2`), U 1 failed (the
  `execute()` twin), A 10 passed (masked on the success path).
- The end-to-end reconnect consequence stays INFERRED. No run was started.
