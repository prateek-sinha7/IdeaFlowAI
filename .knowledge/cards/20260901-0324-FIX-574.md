## Related

## What was wrong

`KernelServices.run_agent` held `ExecutionContext.scratch_lock` for the full
invocation (KRN-005). Fan-out spawned N workers concurrently, but every one of
them queued on that lock, so the "parallel" reading group executed strictly one
reader at a time. ISS-130 had recorded the shared-scratch hazard; the lock that
masked it was also what made the fan-out sequential.

## The fix (commit 127b20a3d)

`kernel_services.py` mints each worker with `ectx_override=copy.copy(self._ectx)`:
scratch fields are private per worker, the substrate is shared by reference, and
no worker needs the run-wide lock. `budget.py` raises `DEFAULT_MAX_CONCURRENCY`
from 4 to 5 so a declared `max_parallel: 5` is no longer clamped to 4.

## How to verify

Five parallel readers in a composed run now overlap in the run log (start
timestamps interleave) instead of forming a chain. `test_fanout.py` /
`test_budget.py` cover the copy semantics and the concurrency default.
