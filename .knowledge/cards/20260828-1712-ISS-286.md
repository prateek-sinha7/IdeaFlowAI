# ISS-286

**BUG-ID:** BUG-20260828-020900-runs-id-versions

## Reproduction (3/3, cold start each time — CONFIRMED on cycle 1)

1. Signed in as qa-admin (pre-existing session; `!!localStorage.getItem('auth_token')` true).
2. **Cycle 1** — cold nav `/dashboard` -> direct nav to
   `http://localhost:3000/runs/77f74563-fa19-4f0b-84fd-d0224f89a54a/versions/2`. Waited 2s for
   settle. Version-picker button read "Version v1"; listbox showed "Version v1" `[active]` and
   "Version v2" unselected. Page body (chat transcript) showed the v2 revision text ("Replace
   every flat gray image placeholder (#e8e8e8 blocks)…", "luxury-asset-marketplace-jets-yachts-cars.html").
   Mislabel reproduced.
3. **Cycle 2** — cold nav `/dashboard` -> direct nav to the same `/versions/2` URL again (fresh
   navigation, not a re-click). Identical result: picker "Version v1", content is v2's.
4. **Cycle 3** — cold nav to `/versions/1` first, then a full navigation to `/versions/2`.
   Identical result: picker "Version v1", content is v2's.

Reproduced identically on **every cycle (3/3)** — no timing/entry-path variation needed to
surface it; this is not a race, it fires on the very first render of `/versions/2`.

## Page / route / component

- Page: Run detail pinned to an artifact version.
- Route: `/runs/{root_id}/versions/{n}` (`parseViewPath` in `frontend/src/lib/routes.ts:336-339`
  parses this into `{ screen: 'run-version', runId, version }`).
- Component: `RunHeader`'s `VersionMenu` (`frontend/src/components/preview/RunHeader.tsx:34-168`),
  fed `versionLabel`/`activeRunId` computed in `PreviewPanel.tsx:521-537,786-792`.

## Root cause (traced, not yet fixed)

`parseViewPath` captures the URL's version segment into `ParsedView.version`
(`frontend/src/lib/routes.ts:338`, `type: { screen: 'run-version'; runId: string; version: string }`),
but **nothing downstream ever reads `parsed.version`** — confirmed by
`grep -rn "parsedView.version\|parsed\.version" frontend/src` returning only the two
declaration sites in `routes.ts` itself.

`reopenedRunIdFor` (`frontend/src/app/[...view]/page.tsx:182-196`) treats `run-version` exactly
like `run-detail`: it returns `parsed.runId` (the family ROOT/v1 run id) and drops the version
number entirely. That id flows into `handleSelectWorkflowRun` -> `setContentSourceRunId` /
`setActivePipelineRunId`, which is what `PreviewPanel` uses as `liveRunId`. In `PreviewPanel.tsx:530`,
`activeRunId = viewingVersion?.id ?? liveRunId ?? latestId` — since `viewingVersion` is only ever
set by a manual picker click (`handleSelectVersion`, never by the URL), and `liveRunId` here is the
v1 root id, `activeRunId` resolves to v1. `activeIdx` (`findIndex` of `activeRunId` in the sorted
family, line 531) is therefore `0`, and `headerVersionLabel` (`PreviewPanel.tsx:789-792`) renders
`"v1"` — regardless of which version's content the page actually displays.

The content itself is correct (v2), so whatever surface resolves content already knows the real
version; only the label/selection path never consults `parsed.version`. The fix belongs where
`reopenedRunIdFor`/the cold-mount effect resolves `run-version` — it needs to either resolve
`parsed.version` to the matching family member's run id (via `getRunFamily`) and feed THAT into
`viewingVersion`/`liveRunId`, or otherwise thread the URL's version number into the same state
`headerVersionLabel` reads.

## Expected vs Actual

- **Expected:** On `/versions/2`, the picker button and its listbox option should read/select
  "Version v2", matching the URL and the content shown.
- **Actual:** Picker button and listbox both claim v1 is selected/current while the content on
  screen is v2's, on every cold load and after a full reload.

## Resolution — found already fixed by the analyzer (2026-08-28)

Independent re-read of the current source (uncommitted working tree, this checkout) shows this
card's mechanism is now fixed, as a side effect of [FIX-328](20260828-2014-FIX-328.md), filed
against the broader **BUG-20260828-090732-runs-id-versions** (`bug-hunter/ledger.md`,
Status: CLOSED — a materially worse variant of this same bug, found independently and fixed
before this card's own analysis pass).

- `pinnedVersionFor` (`frontend/src/app/[...view]/page.tsx:208-210`), a NEW function alongside
  the still-unchanged `reopenedRunIdFor` (`page.tsx:182-196`, still root-only by design — see its
  own doc comment at `page.tsx:198-206`), now reads `parsed.version` and is threaded into
  `DashboardLayout` as `pinnedVersion={pinnedVersionFor(parsedView)}` (`page.tsx:3897`).
- `DashboardLayout` forwards it unchanged into `PreviewPanel`: `pinnedVersion={pinnedVersion}`
  (`DashboardLayout.tsx:3134`).
- `PreviewPanel` resolves it against the sorted family and fetches that member as
  `viewingVersion` (`pinnedMemberId`/the effect at `PreviewPanel.tsx:604-621`), so
  `activeRunId` (`PreviewPanel.tsx:539`) and `activeIdx` (`PreviewPanel.tsx:540`) now resolve to
  the family member the URL names, not the root, and `headerVersionLabel`
  (`PreviewPanel.tsx:844`) follows. That label and `activeRunId` feed `RunHeader`'s
  `VersionMenu` (`PreviewPanel.tsx:1162-1163` -> `RunHeader.tsx:34-53,103,108,127`) — the exact
  button text, `aria-label`, and listbox `[active]` option this card's reproduction checked.
- Blast radius re-checked independently via
  `grep -rn "reopenedRunIdFor\|pinnedVersionFor\|pinnedVersion\|headerVersionLabel" frontend/src`:
  `reopenedRunIdFor`/`pinnedVersionFor` each have exactly one call site in `page.tsx`;
  `pinnedVersion` has exactly one further hop (`DashboardLayout.tsx` -> `PreviewPanel.tsx`);
  `headerVersionLabel` is read only inside `PreviewPanel.tsx` itself. No caller exists outside
  the chain [ISS-230](20260828-1805-ISS-230.md)/[ISS-294](20260828-1725-ISS-294.md) already
  mapped.
- This card's own root cause (`reopenedRunIdFor` discarding `parsed.version`, so `activeRunId`
  resolves to the root and `headerVersionLabel` renders "v1") is the byte-identical mechanism
  [ISS-294](20260828-1725-ISS-294.md) independently traced and [ISS-230](20260828-1805-ISS-230.md)
  generalized across every tab — not a coincidental overlap. No new sibling defect exists beyond
  what [ISS-230](20260828-1805-ISS-230.md), [ISS-294](20260828-1725-ISS-294.md),
  [ISS-296](20260828-1724-ISS-296.md) (inverse: menu write never reached the URL) and
  [ISS-300](20260828-1726-ISS-300.md) (adjacent state: Files tab) already cover — those four
  exhaust the axes this root cause implies (other tab consumers, the inverse write direction, the
  Files-tab adjacent state), and all four are `status: resolved`, `verification: passed`.

**Coverage gap (not a defect):** `test_iss_230_version_pin_survives_tab_switch.py` proves the URL,
network target and Files-tab content survive a pin, but no assertion in that suite reads
`RunHeader`'s visible "Version v{n}" button text or its listbox `[active]` option directly — this
card's own exact claim. The only recorded confirmation of the label itself is the 6-verifier's
manual re-check under BUG-20260828-090732 (`bug-hunter/ledger.md`, "Verified" entry, 2026-08-28):
"cold-loading `/runs/{rootId}/versions/2` now shows 'Version v2' immediately." A future pass
touching this area should add one assertion of the Version-menu button text against `RD.LANE`'s
pinned version to close that gap.

**Disposition:** register entry `BUG-20260828-020900-runs-id-versions` set to `DUPLICATE` — same
root cause as [ISS-230](20260828-1805-ISS-230.md)/[ISS-294](20260828-1725-ISS-294.md), already
fixed and verified under `BUG-20260828-090732-runs-id-versions` (CLOSED). No new fix needed; this
card stays as the record of the earlier, independent discovery.
