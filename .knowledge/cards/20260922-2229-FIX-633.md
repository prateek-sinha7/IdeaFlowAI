# FIX-633

Fixes **QA-PS-040** (`LEDGER.md` / `BUGS.md#qa-ps-040`) — the `/library` cold
load firing `GET /api/workflows` twice.

## What was wrong

[ISS-787](20260922-1815-ISS-787.md) reproduced the duplication 3/3 from cold
start on `/library`: `GET /api/workflows` x2 and `GET /api/runs?limit=50` x2,
with distinct `x-request-id` headers proving two real backend calls rather
than a devtools artifact.

## Root cause

Exactly as [ISS-844](20260922-2124-ISS-844.md) established, re-checked against
the tree before editing:

- `frontend/src/components/library/LibraryPage.tsx` issues no fetch of its
  own and there is no `/library` route folder — `/library` is served by the
  shared `[...view]` catch-all, so nothing Library-local exists to patch.
- `frontend/src/app/[...view]/page.tsx:939` (pre-fix) —
  `dispatch(signedIn({ token: storedToken }))` inside the mount-time
  auth-check effect, with no one-shot guard of any kind, while the sibling
  `recentRuns` effect in the SAME component already carried one
  (`recentRunsRequestedRef`, `page.tsx:843`, landed as
  [FIX-630](20260922-2115-FIX-630.md)). That asymmetry is the defect.
- `grep -rn "dispatch(signedIn(" frontend/src` — one match app-wide, that
  line. `grep -rn "dispatch(fetchWorkflows(" frontend/src` — one dispatch
  site app-wide, `store/listenerMiddleware.ts:52`, reached only from the
  `signedIn` listener. So every duplicate `/api/workflows` traces to that one
  effect running more than once.
- `fetchWorkflows()` (`globalSlice.ts:32-34`) calls `workflowsApi.list()`
  (`store/api/workflows.ts:78-81`) — a bare axios GET on the second HTTP
  client, outside `lib/api.ts`'s `cachedGet`/`inFlightWorkflows` entirely
  (`store/api/http.ts`'s own header comment says so), so nothing downstream
  collapses a second call.

## What changed, and why there

One file, `frontend/src/app/[...view]/page.tsx`, two hunks:

1. `const signedInDispatchedRef = useRef(false);` declared immediately above
   the auth-check effect, mirroring `recentRunsRequestedRef`.
2. The dispatch at the former `:939` is wrapped in
   `if (!signedInDispatchedRef.current) { signedInDispatchedRef.current = true; dispatch(signedIn(...)); }`
   — the claim set synchronously *before* the dispatch.

This is the choke point ISS-844 names: one guard in the single component every
route mounts through closes the duplicate for `/library`, `/dashboard`,
`/analytics`, `/settings/*`, `/workflows/new` and `/runs` at once, rather than
per-route.

**Only the dispatch is guarded, not the effect.** An early `return` at the top
would also skip `router.replace(buildLoginRedirect())`, `setToken`,
`setIsAuthenticated` and `getMe()` on a second invocation. Those are either
required on every invocation or already deduplicated
(`getMe()` is `cachedGet`-wrapped, `api.ts:630`, per
[FIX-618](20260922-1945-FIX-618.md)), so the narrow wrap is both smaller and
safer.

**Per-mount, deliberately not module-scope** — the opposite choice from
[FIX-632](20260922-2221-FIX-632.md)'s `recentRunsSnapshot`, and for a reason
the two cases do not share. `signedIn` is what tells
`listenerMiddleware.ts:22-66` an identity arrived; its ISS-200 branch compares
`getOriginalState().auth.token` against `action.payload.token` and clears the
previous account's preloads when they differ. A module-scope one-shot would
suppress that announcement for the life of the JS module and strand an account
switch on the previous user's cached catalog. A remount's repeat dispatch is
harmless by contrast: by then `state.global.workflowsStatus` is
`"loading"`/`"succeeded"` and the listener's own guard (`:47-56`) drops it —
which is precisely what two dispatches inside ONE mount can defeat.

## On [ISS-845](20260922-2125-ISS-845.md) — left open, deliberately

ISS-845 warns that the trigger for the doubling is unproven, and that a
`useRef` fix would not close a *genuine second mount* because that mount gets
a fresh ref. That caveat is answered, not ignored: a second mount is exactly
the case the listener's own `workflowsStatus` guard already absorbs (it runs
later in time, after `fetchWorkflows.pending` has committed), so the per-mount
ref is the right granularity for the case that guard cannot see.

What this fix does NOT do is settle *which* mechanism produced ISS-787's 3/3
capture. It cannot: the symptom no longer reproduces on demand (the
test-writer measured 0/5 then 0/1 on live cold `/library` loads, recorded on
ISS-844). **ISS-845 therefore stays `open`** — the instrumented capture it
asks for is still unwritten, and closing it on a fix that did not measure it
would be the exact mistake ISS-845 was filed to prevent.
