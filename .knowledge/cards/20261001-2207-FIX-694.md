# FIX-694

## What was wrong

Bug report QA-KB-019. The root cause and blast radius come from the analysis on [ISS-579](20260829-0234-ISS-579.md)
and its sibling [ISS-882](20261001-2111-ISS-882.md). They are not re-derived here.

- [ISS-579](20260829-0234-ISS-579.md) (root): the attach handler serialises names into free text with delimiters
  that are legal inside a filename (`WorkflowView.tsx:350-351`, names joined with `", "` inside `[Attached: ...]`).
  `stripAttachmentMarker` re-parsed that text with the same delimiters. `/(\n\n)?\[Attached: ([^\]]*)\]/g` ended
  the capture at the first `]`, `names.split(", ")` cut a name containing `, ` into pieces, and
  `if (at === -1) return match;` handed the text back unchanged. The chip went, the marker stayed, and `handleRun`
  forwarded it as the brief. [FIX-400](20260829-0402-FIX-400.md) had designed the helper against delimiter-free
  names.
- [ISS-882](20261001-2111-ISS-882.md) (sibling, reader side): `cleanBrief` (`SavedWorkflowsPage.tsx:64`) stripped
  legacy markers with `/\[Attached:[^\]]*\]/g`, so `idea\n\n[Attached: my].txt]` previewed as `idea\n\n.txt]`.

## What changed, and why there

- `frontend/src/components/workflow/WorkflowView.tsx`, `stripAttachmentMarker` (`:86-95`): the body is the
  implementation the [ISS-579](20260829-0234-ISS-579.md) analysis recommended. The filename is regex-escaped inline, since no escape helper
  exists in `frontend/src`. One non-global regex removes exactly one entry. Its three alternatives are all anchored
  on `[Attached: `: the sole entry together with its `\n\n` separator; a later entry (`, <name>` followed by `, `
  or `]`); or the first of several (`<name>, `). None of them looks for the closing `]`, which is ambiguous once a
  name may contain one. The helper has one caller, the chip remove handler (`:401`), so no call site changed:
  `handleRun` (`:172-178`), the Run gate and the textarea all read the corrected `ideaInput`. The writer
  (`:350-351`) is byte-identical, because `cleanBrief` and persisted legacy briefs read that format.
- `frontend/src/components/savedworkflows/SavedWorkflowsPage.tsx`, `cleanBrief` (`:64`): `[^\]]*\]` became
  `[^\n]*?\](?=\s|$)`, the [ISS-882](20261001-2111-ISS-882.md) fix direction. A marker now ends at a `]` followed by whitespace or the end of
  the text. It stays separate from the WorkflowView helper, as that card asks: a different consumer, display-only.

Not used, on purpose: the BUGS.md Notes' terminator guard `\[Attached: (.*?)\](?=\n\n|$)`. The [ISS-579](20260829-0234-ISS-579.md) analysis
overruled it because it leaves the marker in place when the user typed text after it on the same line (probe: 20 of
22 for that version, 22 of 22 for this one). Sanitising names at write time was not chosen either. The analysis
called it a fallback: it changes the forwarded brief and needs a sanitiser shared by writer and stripper.

Known limits, unchanged from the analysis: a name containing a newline, two markers typed onto one line, and a
marker the user edited by hand. In `cleanBrief`, a name containing `] ` still ends the match early (display-only,
accepted by [ISS-882](20261001-2111-ISS-882.md)). One more, measured here: the in-band format is ambiguous when one batch holds a name and
another name ending in `, <that name>`. With `a.txt` attached before `x, a.txt`, removing `a.txt` now leaves
`[Attached: a.txt, x]`, which a later removal of `x, a.txt` cannot match. The pre-fix split got that order right and
the mirror order (`a.txt, y` before `a.txt`) wrong; the new code is the reverse
(`evidence/qa-kb-019/08-fix-known-limit-ambiguous-tail.txt`). Reordering the alternatives only swaps which order
fails. Ending the ambiguity means composing the marker at submit time instead of in the textarea, which the [ISS-579](20260829-0234-ISS-579.md)
analysis left as a UX call.
