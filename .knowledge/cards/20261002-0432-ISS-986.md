# ISS-986

INFERRED sibling of [ISS-949](20261002-0107-ISS-949.md) (QA-KB-061), derived from its fix rather than from the defect
itself. Restoring the parent link on a REST-launched revision turns that run into a member of the revision family. Every
other way of minting a `*_revision` row guards family membership; this one does not. The behaviour below was observed
with an in-process probe that edits no repo file (`evidence/qa-kb-061/01-analyze-probe-output.txt`, probe S3 and S1b); the
race it implies was not run.

## What happens (CONFIRMED, observed)

Parent `P` is an owned completed run, and an active (`running`) revision child of `P` already exists.

- `POST /api/runs/{P}/revisions` answers `409 {"code":"revision_already_in_progress"}`.
- `POST /api/runs` with `pipeline_type="user_stories_revision"` and `source_workflow_run_id=P` answers `200`.
  At HEAD the new run is not in `P`'s family at all (ISS-949: `parent_run_id` is NULL). With the ISS-949 fix applied
  in-process it joins the family while the other revision is still `running` (family members: `running`, `completed`).
- That REST-launched child has `source_run_id = NULL` (probe S1b), where `_mint_revision_row` writes
  `source_run_id=parent_run_id`.

## Why (CONFIRMED by reading)

`_mint_revision_row` (`backend/app/api/run_commands.py:4604`) is the guarded mint. It resolves the family root first, and
that resolution 404s on a cycle, a cross-owner or a missing ancestor (`:4654`). Then, under `family_lock(user.id,
revision_root_id)` (`:4670`), it applies the `_has_active_chain_revision` 409 (`:4675-4681`) and writes
`source_run_id=parent_run_id` (`:4749`, "Requirement 22 AC1/AC2"). Its docstring says the single insertion covers "all 3
production call sites (create_revision, CHANNEL_REVISION in post_message, Concierge revision disposal)". `launch_run` ->
`_launch_run_core` (`:3256`, `:2868`) is a fourth way to mint a `*_revision` row and applies none of those four things:
`family_lock` and `_has_active_chain_revision` are used only inside `_mint_revision_row`. (Tier and "does this pipeline
exist" are not part of the gap: `launch_run` has its own gates for both, `_require_tier_entitlement` at `:3510` and the
`invalid_pipeline_type` / `no_agents` rejections.)

It is dormant at HEAD only because the parent link is dropped ([ISS-949](20261002-0107-ISS-949.md)), so a REST-launched
revision never joins a family. Once linked, the engine resolves the family root and shares its sandbox directory
(`backend/agents/execution_engine/engine.py:4392-4402`, "All revision runs in a family share the chain root's sandbox
directory"), so two such runs would write the same directory.

The frontend still launches revisions this way for user stories, prototype (v1) and app builder:
`DashboardLayout.tsx:1229`, `:1249`, `:1261` and the History callbacks `:3067-3097`. prototype_v2, backlog, custom and ppt
(from the run screen) go through `postRevision` -> `create_revision` -> `_mint_revision_row` instead.

## INFERRED, not run

Two tabs, or a double click on "Revise", launching two revisions of one parent through `POST /api/runs`: both would be
admitted and both would share the family sandbox. The engine stamps each run's `revision_ordinal` at start as "its 1-based
position among ALL family members" (`engine.py:4613-4631`) and the finalizer tags `vN` from it, so two overlapping runs
could take the same ordinal and collide on the tag. Needs two real engine runs, which this analysis did not start. Raise
the severity if it reproduces.

## Where the fix belongs

A design call for the fixer, not made here. Either (a) the REST launch path mints `*_revision` rows through
`_mint_revision_row`, so there is one guarded mint, or (b) the three legacy frontend handlers move to `postRevision` as
prototype_v2, backlog and custom already did, and the REST arm keeps only the ISS-949 parent link for API clients. Whichever
is chosen, the `source_run_id` question stays open: Requirement 6 AC 16 says a declaration-gated launch must not leak a
source edge (`run_commands.py:3835-3839`), while Requirement 22 AC1/AC2 says a revision's parent IS its chain source. The
ISS-949 fix deliberately leaves `source_run_id` alone.
