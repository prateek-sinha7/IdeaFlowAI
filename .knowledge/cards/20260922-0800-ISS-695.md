## What happened

On `/create/prototype` and `/create/ppt`, Template tab -> "Upload custom" -> "From URL" tab,
entering `https://hexaware.com/` (a valid, publicly reachable page) and clicking **Fetch**
fails. The modal shows:

```
Could not reach that URL. Check the address and try again.
```

and `GET /api/prototype/fetch-url?url=...` returns `502 Bad Gateway` with
`{"detail":"Could not reach that URL. Check the address and try again."}`. This is the
friendly message [FIX-396](20260829-0348-FIX-396.md) installed for the catch-all exception
handler — the leak it fixed is gone, but the underlying fetch genuinely fails for URLs that
are not actually unreachable.

## Reproduction — 3/3 from a cold start, register entry QA-PS-013

1. **Cycle 1** — `/create/prototype`, cold nav from `/login` through sign-in: Upload custom
   -> From URL -> `https://hexaware.com/` -> Fetch -> `502`, same message. Network request
   `GET /api/prototype/fetch-url?url=https%3A%2F%2Fhexaware.com%2F` -> `[502] Bad Gateway`.
2. **Cycle 2** — cold nav via `/dashboard` -> `/create/prototype`, modal reopened fresh ->
   identical `502` and message.
3. **Cycle 3** — cold nav via `/dashboard` -> `/create/ppt` (the sibling route) -> Upload
   custom -> From URL -> same URL -> Fetch -> `502`. Confirms both routes share the failure,
   and that the request still lands on `/api/prototype/fetch-url` even from the PPT wizard
   (same shared `CustomTemplateModal`, matching [ISS-343](20260828-2059-ISS-343.md)'s blast
   radius finding).

## Trigger — named, not hexaware.com-specific

Not narrowed by timing/tier/theme/viewport — reproduces identically every cycle. Narrowed
by **URL target** instead: called `fetch_url_for_template`'s own `httpx.AsyncClient` code
path directly, from this backend's Python environment (`backend/.venv`), against three
different, definitely-reachable hosts:

```
$ python3 -c "import httpx,asyncio; ..." (backend/.venv active)
https://example.com/     EXC ConnectError [SSL: CERTIFICATE_VERIFY_FAILED] certificate verify
                          failed: self-signed certificate in certificate chain (_ssl.c:1010)
https://hexaware.com/    EXC ConnectError [SSL: CERTIFICATE_VERIFY_FAILED] certificate verify
                          failed: self-signed certificate in certificate chain (_ssl.c:1010)
https://www.google.com/  EXC ConnectError [SSL: CERTIFICATE_VERIFY_FAILED] certificate verify
                          failed: self-signed certificate in certificate chain (_ssl.c:1010)
```

The same three hosts fetched via plain `curl` (which uses the OS trust store, not httpx's
bundled `certifi` bundle) succeed:

```
$ curl -s -o /dev/null -w "%{http_code}\n" --max-time 10 https://example.com/   -> 200
$ curl -s -o /dev/null -w "%{http_code}\n" --max-time 10 -A "Mozilla/5.0 ..." \
       https://hexaware.com/                                                    -> 200
```

**Named trigger: every `https://` URL fails identically**, because
`backend/app/api/prototype_templates.py:349` constructs `httpx.AsyncClient()` with default
TLS verification, which trusts only `certifi`'s bundled CA list. This environment sits
behind a TLS-intercepting proxy whose certificate is not in that bundle (it IS in the OS/
curl trust store), so every outbound `client.get(url, ...)` raises `httpx.ConnectError`
wrapping an `ssl.SSLCertVerificationError`, which the existing catch-all
(`prototype_templates.py:387-392`, installed by FIX-396) turns into the generic 502 seen in
the UI. The reported URL is not special — the reporter's repro (`hexaware.com`) happened to
be the first URL tried, but the fetcher fails for 100% of external targets in this
environment.

## Expected vs actual

- **Expected:** a syntactically valid, publicly reachable HTTPS URL is fetched successfully
  and used as the custom template's source HTML.
- **Actual:** every HTTPS URL 502s with "Could not reach that URL", because the backend's
  `httpx.AsyncClient` will not complete a TLS handshake through this environment's
  intercepting proxy — the CA it presents is outside `certifi`'s default trust store.

## Blast radius (analyzer pass, 2026-09-22)

Every backend call site building an `httpx` client for an OUTBOUND (non-localhost) HTTPS
request, found by `grep -rn "httpx\.AsyncClient(\|httpx\.Client(" backend --include="*.py" |
grep -v "/tests/"` plus one bare `httpx.get`:

- `backend/app/api/prototype_templates.py:349` — `fetch_url_for_template` — the reported
  path, this card.
- `backend/app/api/settings.py:130` — `upsert_github_pat` ("Save GitHub PAT"). Filed as
  [ISS-750](20260922-1403-ISS-750.md) — a worse failure mode than this bug: no catch-all
  wraps the call, so it would raise unhandled rather than show a friendly 502.
- `backend/app/services/handoff_github.py:292,334` — `get_repo_metadata` /
  `create_pull_request`, the handoff "push to GitHub" PR-creation flow. Filed as
  [ISS-751](20260922-1404-ISS-751.md).
- `backend/app/core/cognito.py:114` — `_fetch_jwks`, used to verify inbound JWTs. Filed as
  [ISS-738](20260922-1405-ISS-738.md), flagged uncertain: this session's own login succeeded
  against this backend, so whether this path is actually exercised here is unconfirmed — see
  that card.

All four share the identical mechanism: `httpx`'s default `verify=True` resolves to
`certifi`'s bundled CA list only, which does not include this environment's TLS-intercepting
proxy CA (present in the OS/curl trust store instead, per the Trigger section above). None of
the four pass a `verify=` override, so all four are expected to fail identically for any
external HTTPS host reached from this backend process. CONFIRMED by reading all four call
sites; the failure itself is CONFIRMED only for this card's own path (direct-interpreter
repro above) and INFERRED for the other three pending their own reproduction.

## Fix location (analyzer pass, 2026-09-22)

**Primary:** none of the five call sites shares a helper today — each constructs its own
`httpx.AsyncClient()` / `httpx.Client()` / `httpx.get()` ad hoc. The smallest diff that fixes
every current and future caller at once is a single shared HTTP-client factory (e.g.
`backend/app/core/http_client.py::build_http_client(**kwargs)`) that resolves `verify=`
once — trusting the OS/enterprise trust store (the stdlib `ssl` default context, or the
`truststore` package's `SSLContext`, either of which sees what `curl` already sees in this
environment) instead of `httpx`'s certifi-only default — and routing
`prototype_templates.py:349`, `settings.py:130`, `handoff_github.py:292,334` and
`cognito.py:114` through it. Patching only `prototype_templates.py` (this bug's reported
path) would leave all four siblings broken.

**Caution:** `_is_private_url` (`prototype_templates.py:305-318`) and the SSRF posture around
it are unrelated to this defect and must not be loosened while fixing TLS trust — the fix is
scoped to *which CAs are trusted*, not to relaxing what hosts may be fetched.

of host this proxy does intercept.

## Fix (fixer pass, 2026-09-22) — [FIX-607](20260922-1814-FIX-607.md)

`fetch_url_for_template` now builds its client with
`verify=default_ssl_context()` (`backend/app/core/http_client.py`), a cached
context trusting the union of the OS/enterprise trust store and certifi's
bundle — the CA set `curl` already sees. All four sibling call sites in the
blast radius were routed through the same helper. `_is_private_url` and the
SSRF posture were not touched.

Proven by calling the patched endpoint function in-process against the
reporter's own URL: `https://hexaware.com/` -> 169055 bytes of HTML,
`https://example.com/` -> 559 bytes, where the pre-fix path 502s. The e2e
test is still red because `:8000` runs a process started at 14:46:48 with no
`--reload` — it must be re-run after a backend restart. Full numbers in
[FIX-607](20260922-1814-FIX-607.md).
