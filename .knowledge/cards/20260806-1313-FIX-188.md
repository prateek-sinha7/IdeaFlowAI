# FIX-188

**Phase / trigger:** Phase 33 (D-05 proposals), Phase 43 (43-02 deferral), ISS-054

## Description

Concierge-held consequential proposals (`channel: "chain"`, `"gate_action"`, `"revision"`)
are durably persisted server-side but the confirm/reject chip never appears in the UI.

## Root Cause

Two simultaneous gaps:

**Gap 1 — Dead binding (`DashboardLayout.tsx:232-235,1514`)**
```ts
const RUN_CONCIERGE_PROPOSALS: LaneProposal[] = [];  // module-level frozen constant
const runConciergeProposals = RUN_CONCIERGE_PROPOSALS;  // plain alias, no setter
proposals={runConciergeProposals}  // always []
```
There is no `setRunConciergeProposals` anywhere. The `handleRejectProposal` was also a
documented no-op. This was a deliberate Phase 43 deferral that was never completed.

**Gap 2 — No `concierge_proposal` case in `handleFrame` (`useRunChat.ts:494`)**
```ts
default:
  // Every other frame leaves the transcript untouched
  break;
```
The durable `concierge_proposal` rows delivered by the existing post-send `fetchEvents`
re-fetch (DEF-44-12-2) silently fell to `default:` and were discarded.

## Fix

**`useRunChat.ts`:**
- Add `HeldProposal` interface (exported, structurally compatible with `LaneProposal`)
- Add `proposals: HeldProposal[]` state
- Add `"concierge_proposal"` case in `handleFrame`: upserts pending, removes resolved
- Add `dismissProposal(id)` callback (client-side only)
- Expose both in `UseRunChatReturn` and `return` statement

**`dashboard/page.tsx`:**
- Destructure `proposals: runChatProposals` and `dismissProposal: dismissRunChatProposal`
- Pass as `runChatProposals` and `onDismissRunChatProposal` to `<DashboardLayout>`

**`DashboardLayout.tsx`:**
- Add `runChatProposals?: LaneProposal[]` and `onDismissRunChatProposal?` to props
- Destructure both in component
- Replace dead binding: `const runConciergeProposals = runChatProposals ?? RUN_CONCIERGE_PROPOSALS`
- Fix no-op reject: `onDismissRunChatProposal?.(_id)`
- Update stale frozen constant comment and dead binding comment

## Invariants Verified

- **INV-1/SC-001** — new handleFrame case keyed on opaque `channel` string, no pipeline-type
  branch — ✅
- **INV-3** — frontend-only; 5 backend characterization goldens unaffected — ✅
- **INV-12** — single data delivery path (durable-row via existing `fetchEvents`); the thinner
  `chat_reply.data.proposals` shape explicitly NOT used — ✅
- **H1** — confirm execution unchanged; only chip visibility changes — ✅

## Known limitation

`chain` proposals never get a server-side "resolved" row (FIX-115 routes confirm through
`onSuggestion`, not `onConfirmProposal`). The pending durable row stays `"pending"` in the
DB. On hard reload, the chip re-appears. Accepted; this was the original design intent.
