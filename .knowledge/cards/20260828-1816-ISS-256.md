## What is suspected

[ISS-224](20260828-1735-ISS-224.md) names `authedJson` (`frontend/src/lib/api-handoff.ts`) as
the frontend half of the root cause. Fixing only that function leaves a **second, independently
written copy of the identical anti-pattern** untouched: `ApiError` in `frontend/src/lib/api.ts`,
the client every non-handoff page in the app uses via `request()`/`fetchWithAuth()`. Any page
that (a) hits a `request()`-backed endpoint returning FastAPI's list-shaped 422 `detail`, and
(b) renders `err.message` on-page, reproduces ISS-224's on-page-raw-JSON symptom through a path
`authedJson`'s fix cannot reach. **INFERRED** — the duplicate implementation and its render
sinks are confirmed by reading the code; a live 422 through this specific path has not been
triggered in the browser.

## Root cause — a second, independent implementation of the same idiom

**Confirmed by reading both files side by side:**

- `frontend/src/lib/api-handoff.ts:86-88` (`authedJson`, the mechanism ISS-224 names):
  ```ts
  const message =
    typeof body?.detail === "string" ? body.detail : JSON.stringify(body);
  ```
- `frontend/src/lib/api.ts:77-79` (`ApiError`'s constructor, the app-wide client):
  ```ts
  const message =
    typeof detail === "string" ? detail : JSON.stringify(detail);
  ```

These are two separate re-implementations of "only handle a plain-string `detail`, otherwise
stringify the whole thing" — not one shared function with two callers.
`grep -rln "JSON\.stringify(body)\|JSON\.stringify(detail)" frontend/src/lib/*.ts` returns
exactly these two files and no others, so this is the complete known duplication.

**Confirmed live render sinks**, both on `frontend/src/components/settings/AccountSettings.tsx`
(a real, non-handoff page), both fed through `api.ts`'s `request()`:

- `AccountSettings.tsx:166` calls `changePassword()` (-> `api.ts:1329`,
  `request("/api/auth/change-password", ...)`); its catch at `:169-170` sets
  `message.text = err.message`; rendered raw at `:314`.
- `AccountSettings.tsx:132-142` (model-preference save) calls `updatePreferences()` (->
  `api.ts:1361`, `request("/api/settings/preferences", ...)`); its catch sets
  `modelMessage.text = err.message`; rendered raw at `:417`.

**Not yet confirmed — the live trigger.** Neither `ChangePasswordRequest`
(`backend/app/api/auth.py:1222-1225`) nor `UserPreferencesUpdateRequest`
(`backend/app/api/settings.py:84-85`) currently declares a `min_length`/`max_length` constraint,
so no input on THIS page trips a list-shaped 422 today. The duplicate broken parser and its
raw-render sink are proven; the specific field that fires it on `AccountSettings.tsx` is not yet
localized. Elsewhere in the app, several other `request()`-routed fields DO carry a length
constraint with no confirmed client-side cap and would plausibly trigger it on their own pages,
e.g. `backend/app/api/user_workflows.py:206` (`name`, `max_length=120`, wired through
`api.ts:1726-1729`'s `getUserWorkflows` and its sibling create/rename calls) and
`backend/app/api/user_agents.py:66-70`. None were click-tested in this session.

## Why the root cause implies this

ISS-224's frontend root cause is the idiom itself, not one file. The idiom is duplicated, not
shared, so a fix that edits only `authedJson` structurally cannot reach `ApiError`'s callers —
and `ApiError`'s callers are most of the app, not just `/handoff/settings`.

## Expected vs actual (once a trigger is confirmed)

- **Expected:** a `request()`-backed 422 with list-shaped `detail` is parsed into a friendly
  message everywhere in the app, the same way the plain-string 400 case already is.
- **Actual (predicted):** `ApiError.message` is the full `JSON.stringify` of the response body,
  and at minimum `AccountSettings.tsx` renders it verbatim once a qualifying field exists.

## What would confirm or refute this

Find or exercise a `request()`-routed, length-constrained field reachable from the live UI with
no client-side cap (candidates above), submit an over-length value, and read the response body
plus the page snapshot the way ISS-224's reproduction did. Confirms if raw JSON renders;
refutes if every such field turns out to already have a client-side cap or its own
friendly-message handling.
