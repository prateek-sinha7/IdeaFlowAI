# ISS-1168

**Register source:** sibling derived during the `QA-KB-109` analysis on 2026-10-09 (root [ISS-1153](20261009-1340-ISS-1153.md)). Not its own bug row; the fix is part of the root's change.

**Confidence:** CONFIRMED offline. The real `AdminPage` was rendered in jsdom with a `getMe()` that returns the id of a listed admin, and each own-row control was clicked: `evidence/qa-kb-109/analysis-02-probe-own-row-today.txt`, blocks `[P1]`, `[P3]`, `[P4]`, `[P5]`. The server half was driven by calling the real handlers with actor == target (in-memory SQLite, Cognito mocked): `evidence/qa-kb-109/analysis-01-probe-admin-self-target-matrix.txt`, block `[S]`. NOT driven in a live browser, on purpose: a live click on the shared admin's own row is the thing the line must avoid (see the root's operational warning).

## Condition

Any signed-in admin looking at their own row of the `/admin` users table. `AdminPage` never keeps `getMe().id` ([ISS-1153](20261009-1340-ISS-1153.md)), so the row render (`frontend/src/app/admin/page.tsx:512-623`) cannot single the row out. Three controls are live on it besides Delete:

| control | where | what the click sends | server answer | history |
|---|---|---|---|---|
| Plan dropdown | `page.tsx:540-544` | `PATCH /api/admin/users/{id}/tier` | 400 "You cannot change your own tier. Ask another administrator." (`admin.py:301-305`) | never guarded in the UI, before or after `b2a621f84` |
| Role pill | `page.tsx:550-564` | `PATCH .../role` `is_admin=false` | 400 "You cannot remove your own admin access." (`admin.py:365-369`) | **guarded until `b2a621f84`**: `disabled={user.id === currentUserId && user.is_admin}` and a title "You cannot remove your own admin access" (pre-image lines 422-427) |
| Disable | `page.tsx:602-609` | `POST .../disable` | 400 "You cannot disable your own account." (`admin.py:566-570`) | added by `b2a621f84`, born unguarded |

The probe shows the own row carrying the same five controls as another admin's row, none disabled (`[P1]`), the role pill titled "Click to remove admin access" (`[P3]`), and each click sending the request for the admin's own id, answered by the server's own sentence in a toast.

## Expected vs actual

Expected: the own row offers no control the server will refuse. The role pill was disabled with an explanatory title for exactly this reason before `b2a621f84`; the other two have the same server rule and the same reason. Actual: all three are live, and each click ends in an error toast about the admin's own row.

## Why the root cause implies it

[ISS-1153](20261009-1340-ISS-1153.md) is "the page does not know which row is the signed-in admin". Delete is only the control the validator happened to look at. The role pill is the direct regression of the guard that went with `currentUserId`; Disable and the tier dropdown are the same missing branch on two more controls. A fix that hides only Delete, which is all the e2e test `test_an_admin_cannot_delete_their_own_account` asserts, leaves these two open.

## Fix direction (INFERRED, not applied)

The same change as the root, not a second mechanism: one `isSelf` per row, then Disable not rendered, the role pill disabled when the row is the admin's own and an admin (with its former title), the tier trigger disabled. The reference diff is `evidence/qa-kb-109/analysis-plugins/page.reference-fix.tsx` (13 changed lines; the contract test `[C2]` passes against it and the repo's own 16 admin tests stay green, `analysis-03`, `analysis-04`).

## Resolution

Resolved by [FIX-779](20261009-1659-FIX-779.md) (5-fixer, 2026-10-09), the root's change: on the own row the role pill is disabled with "You cannot remove your own admin access", the plan trigger is disabled with "You cannot change your own plan", and Disable is not rendered. The ISS-1168 case in `admin.iss1153.test.tsx` observed XPASS; marker left for the 6-verifier.
