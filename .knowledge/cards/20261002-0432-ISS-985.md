# ISS-985

INFERRED sibling of [ISS-949](20261002-0107-ISS-949.md) (QA-KB-061), derived from its root cause. `launch_run` hands
`_launch_run_core` ONE source-id parameter and fills it with the ADMITTED id, which is `None` whenever the target manifest
declares no `chains_from`. ISS-949's defect is the revision-parent link reading that parameter. This is a second reader of
it: the `chain_v2_accepted` flag in the launch response. Nothing here has been seen in a browser; both halves are
read, and the backend half was also observed with a probe.

## What happens

- **Backend half (CONFIRMED, observed).** `POST /api/runs` with `pipeline_type="user_stories_revision"` and an owned
  `source_workflow_run_id` answers `200 {"run_id": "<id>"}` with no `chain_v2_accepted` key. Probe S1 in
  `evidence/qa-kb-061/01-analyze-probe-output.txt` (scripts beside it; they edit no repo file), at HEAD and again with the
  [ISS-949](20261002-0107-ISS-949.md) fix applied in-process.
- **Frontend half (CONFIRMED by reading, render not observed).** `frontend/src/providers/RunConnectionProvider.tsx:613-617`:
  `launchedRunId && payload.source_workflow_run_id && !body?.chain_v2_accepted` fans out a synthetic
  `chain_context_unavailable` with `reason: "incompatible_backend"` (`:618-628`). The reducer stores it
  (`frontend/src/hooks/useWorkflow.ts:1976-1980`), `RunChatLane.tsx:2287-2291` mounts `RunEngineNotice`, and
  `RunEngineNotice.tsx:98` renders "Chain context unavailable: backend version mismatch ... Upgrade the backend", action
  "Wait for backend upgrade".

## Why

`backend/app/api/run_commands.py:3250-3252` [HEAD 3234-3236]: `if source_workflow_run_id: response_body["chain_v2_accepted"] = True`.
That parameter is the admitted id: `:3855-3857` [3815] sets `_admitted_source_id = _chain_admission.source_id`, and `:3872` [3832]
passes it as `source_workflow_run_id`. For a manifest without `chains_from`, `admit_chain_launch` returns
`ChainAdmission(active=False, refusal_reason="declaration_gate")` (`:5310-5312` [5270-5272]) and `source_id` keeps its default
`None` (`:4888`). The comment at `:3244-3249` says the flag means "the v2 chain mechanism processed a source_workflow_run_id"
so a new frontend can detect an OLDER backend. A current backend that evaluated the source and declined it by design is
indistinguishable from that older backend, because the flag is derived from the declined value.

## Who is affected (reading)

Every launch that sends `source_workflow_run_id` to a manifest with no `chains_from`:

- every REST-launched `*_revision`: `DashboardLayout.tsx:1229` (user stories), `:1249` (prototype), `:1261` (app builder), and
  the History callbacks `:3067`, `:3077`, `:3087`, `:3097` reach `POST /api/runs` through `useWorkflow.ts:122`
  (`Object.assign(payload, context)`) and `RunConnectionProvider.tsx:496`. All ten `*_revision` manifests lack `chains_from`.
- a chain into a workflow that does not declare it. Only `ppt_v2`, `backlog`, `prototype` and `user_stories` do
  (`backend/agents/workflows/*/workflow.yaml`); `ppt` says it deliberately does not (`ppt/workflow.yaml:45-52`).
  INFERRED which of these targets the wizard actually offers.

## Expected vs actual

Expected: no version-mismatch notice for a launch the current backend handled correctly. Actual: the run lane tells the
user the backend is out of date and to wait for an upgrade.

## Where the fix belongs, and what would settle it

At the one place the flag is written, `_launch_run_core:3251`: derive it from the request id
(`request_source_workflow_run_id or source_workflow_run_id`), the same pattern the duplicate-context strip already uses at
`:2982`. The frontend cannot tell the two cases apart. Product question for a chain INTO a non-chaining workflow: the user
did expect context there and gets none, so some notice may be wanted, but not with the `incompatible_backend` reason. The
fixer should decide that with the owner, not silently suppress it.

To settle the INFERRED half: launch a user-stories revision from History in the UI and look for the notice, or add a
`RunConnectionProvider` test that feeds a `200 {"run_id": ...}` answer for a revision launch. No backend test mentions
`chain_v2_accepted` today (`grep -rn chain_v2_accepted backend/tests` is empty), so add one beside
`test_rest_run_launch_api.py`.
