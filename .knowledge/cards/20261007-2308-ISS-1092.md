# ISS-1092

**Register source:** sibling derived during the analysis of `QA-KB-088` on 2026-10-07 (root [ISS-947](20261002-0107-ISS-947.md)). Found while
running the spec-016 piece-level file that [ISS-1091](20261007-2308-ISS-1091.md) covers. Not yet its own bug row.

**Confidence:** CONFIRMED for the behaviour (a failing test, a direct call and an HTTP round trip, all run on 2026-10-07 at
`33d55657`). **Not decided:** the code is not necessarily the wrong side. Two recorded statements contradict each other
and nothing here says which one wins. Evidence: `evidence/qa-kb-088/09-analyze-merge-override-trust-probe-output.txt`.

## Condition

`tests/unit/test_workflow_override.py::test_a_not_user_allowed_gate_is_rejected` (`:253-260`) is the only non-setup failure in
that file. It builds an override step with `gates: ["security"]` and asserts `merge_override_steps(...)` returns the file
plan unchanged. It returns a NEW plan instead. This is a real assertion failure, so it stays red after
[ISS-1091](20261007-2308-ISS-1091.md) relocates the file's DB-backed tests.

## Mechanism (CONFIRMED)

- `backend/agents/execution_engine/overrides.py:97-100` compiles the override's steps with
  `WorkflowCompiler().compile(parsed, registry, trust="db")`, with a comment that the row "is re-checked here because a row
  can be tampered with directly in the database".
- `backend/agents/workflows/compiler.py:228` is `_TRUSTED_SOURCES = frozenset({"file", "builtin", "db"})` (commit `ea2db4e02`,
  2026-09-04, "trust db manifests exactly as file manifests", recorded as [ADR-0039](20260904-1424-ADR-0039.md)). `_check_trust`
  (`compiler.py:488-509`) returns at `if trusted: return` (`:506-507`), so `user_allowed` is never consulted at `trust="db"`.
- Direct call: `merge_override_steps(ppt, [step with gates=['security']], registry)` returns a different object, the step
  `custom-agent:mine` carries `gates: ['security']`, while `is_user_allowed("gate", "security")` is `False`.
- Through HTTP (harness = the fixed e2e fixture): `POST /api/user-workflows` with `overrides_pipeline_type: "ppt"` and that step
  returns **201**; `GET /api/workflows/ppt` then reports `is_overridden: true` and serves `gates: [['security']]`. The save
  path also compiles at `trust="db"` (`user_workflows.py:117`), so the save check is no stricter than the merge.
- Both readers go through the one function: `workflows.py:322` (the served plan) and `run_commands.py:3628` (the launch),
  and the launch treats "returned the same object" as "refused" (`run_commands.py:3631-3633`).

## The contradiction

| says reject | says accept |
|---|---|
| `overrides.py:9` ("a user/db manifest is untrusted"), `:21` ("approval and security are not [user_allowed], and a row smuggling one is correctly rejected"), the test at `test_workflow_override.py:253-260`, `compiler.py:313-314` and `:499` (docstrings: "`user` or `db` are UNTRUSTED"), `run_commands.py:3631-3633` | `compiler.py:224-228` (comment and constant: only `user` is untrusted) and [ADR-0039](20260904-1424-ADR-0039.md) (`status: active`): "Only 'user' is untrusted", a saved row is trusted |

The spec-016 commit (`732adc245`, 2026-08-26) wrote the left column; `ea2db4e02` (2026-09-04) wrote the right one without
touching `overrides.py` or its test. [ADR-0039](20260904-1424-ADR-0039.md) names the saved Composer workflow, not an
override of a built-in, and its locked constraints do not mention overrides.

## Decision needed

For a user's override of a built-in workflow, must the compiler enforce `user_allowed` on its steps, or is an override row
trusted like any other saved row?

- **A. Enforce (spec 016 and the test win).** Compile the override steps at `trust="user"` in `merge_override_steps`
  (`overrides.py:100`, one place, both readers). The save path needs the same stricter check for rows that set
  `overrides_pipeline_type`; `_compile_check_manifest` is shared with ordinary composed workflows that ADR-0039 deliberately
  trusts, so it cannot simply be flipped. Consequence: the test passes unchanged; an already-stored privileged row degrades to
  the file plan at the next launch with the existing "failed to compile" warning.
- **B. Trust (ADR-0039 wins).** Rewrite or delete the test and correct the five stale statements above. Consequence: no
  behaviour change; an enterprise user's override of a built-in may carry `security`/`approval` gates and trusted tool grants,
  the same exposure ADR-0039 accepted for composed workflows.

ADR-0039's locked constraint "the compiler is the SOLE enforcement point for manifest trust" applies to either choice. Option A
only tightens; it does not widen `_TRUSTED_SOURCES`.

## Why the root cause implies it

It does not strictly. It is the same failure mode as [ISS-947](20261002-0107-ISS-947.md): a test that stayed behind while the code moved and
that nobody saw because the file's other tests failed at setup first. Found, not fixed, so it gets its own card.

## Re-analysis (QA-KB-100, 2026-10-08)

Bug row `QA-KB-100` (High, security) was raised from this card. The analysis was re-run at HEAD `f06129262`; the source files it cites are unchanged since `33d55657`. Everything above stands. This section narrows the decision and corrects the scope. Evidence: `evidence/qa-kb-100/analysis-01` to `-08`; probe scripts in `evidence/qa-kb-100/analysis-plugins/`.

**Severity.** `low` was too low. The gate in the failing test is the mildest of eleven things the same line lets through ([ISS-1111](20261008-1415-ISS-1111.md)): an override step can also carry `exec` and `spawn_subagents` grants, and a basic-tier caller can save it (201). The frontmatter `severity` is now `high`.

**The decision above is narrower than it looked.** It was framed as one record against one record. Counting them:

| says an override step is untrusted | says a saved row is trusted |
|---|---|
| spec 016 `spec.md:95-96`: "A not-user-allowed capability is refused. A stored row declaring `approval` or `security` fails the `trust="db"` compile; the run falls back to the file plan." And `plan.md:407`: "Capability trust: unchanged" | [ADR-0039](20260904-1424-ADR-0039.md) (`status: active`): "A manifest loaded from the database is trusted exactly as one loaded from disk." |
| [ADR-0027](20260825-2115-ADR-0027.md) (accepted): a refused override "returns the base plan unchanged" | |

Three further facts point the same way (`analysis-05`, `-06`):

1. ADR-0039 never mentions overrides. Its title, decision, consequences and residual risks all speak of "Composer/db workflows", and `overrides.py` is not in its globs. Commit `ea2db4e02` touched `compiler.py`, `permission_caps.py`, `entitlements.py` and two tests, and none of `overrides.py`, `user_workflows.py` or `run_commands.py`. When `overrides.py:100` was written (`732adc245`), `_TRUSTED_SOURCES` was `{file, builtin}`, so `trust="db"` meant "untrusted". The constant changed its meaning under the call.
2. The exposure ADR-0039 did accept (a saved row may carry exec and spawn) was paired, in the same commit, with an enterprise entitlement. The Composer's base `custom` is enterprise-only; an override of `ppt` is not. A basic caller is refused the Composer (403) and accepted for the override (201).
3. The guard ADR-0039 says "still cannot fire" is still dead (`security.py:127`), so the compiler is the only control, and the override path switches it off for every tier.

**Working conclusion (the analyzer's, not a ruling).** For override rows the code is the wrong side and the test is right: compile an override's steps at `trust="user"`. That is a scope clarification of ADR-0039, not a reversal of it: `_TRUSTED_SOURCES` and the Composer path do not change. What is left for a human: (1) annotate ADR-0039 with that scope (an ADR is corrected by supersession; none was edited here), and (2) the non-override shape of the same exposure, [ISS-1114](20261008-1415-ISS-1114.md), which is a real decision and is not part of this fix.

One locked constraint to name. ADR-0039's first reads: "An inline, client-authored manifest is the single remaining source that CAP-03 checks against user_allowed, and it must stay that way; widening trust to "user" would remove the last compile-time authorization boundary." The fix makes override steps a second checked source. I read "single remaining" as describing the state after ADR-0039 and "must stay that way" as "do not widen trust to `user`", and the fix leaves `_TRUSTED_SOURCES` alone. If the owner reads that constraint as a prohibition on checking any other source, this is the one place the working conclusion needs a human.

One shared steps-only check at `trust="user"` serves the merge and the writers. Traps: `_TRUSTED_SOURCES` must not change and `_compile_check_manifest` must not flip globally (both would break ADR-0039's Composer rows); a gate-name special case closes five of the eleven rows; a read-side-only fix leaves the four writers answering 201 or 200 and `GET` serving the raw steps (`analysis-08`).

**What the one-line fix does** (mutation probe, `analysis-07`: `trust="user"` at the merge call site only, nothing edited): `tests/unit/test_workflow_override.py` goes from `1 failed, 5 passed` to `6 passed`. `test_workflow_override_e2e_api.py` (7), `test_workflow_override_api.py` (17), `test_user_workflows_agent_count.py` (8) and `test_model_tier_gate_workflows_api.py` (21) are identical before and after.

**Regression surface of `trust="user"`** (`analysis-04`). Eight built-ins' own raw steps are refused at `user`: `app_builder` (`post_step: api_prefix_audit`); `prototype`, `prototype_feature_revision` and `prototype_large_revision` (`compaction: html_skeleton`); `prototype_revision` (`post_step: revision_validation`); `sample_fanout`, `sample_subagents_parallel` and `sample_wave` (`spawn_subagents`). Two routes can put such steps in an override. The wizard (`LaunchWizard.tsx:1054-1058`) sends library agent ids plus user-allowed selections and is not affected (INFERRED: the TypeScript builder was not run through the compiler). The canvas is different: `IdeaInputPage.tsx:1225` seeds from `manifest_steps`, and `agentToManifestStep` spreads every key it does not model back onto the step (`userWorkflows.ts:283-305`), engineer-only ones included. A canvas "Save as my version" of `app_builder` (user-launchable, no wizard surface) would therefore carry `post_step: api_prefix_audit`: refused with a 422 once the writers check, and an existing row of that shape falls back to the file plan, which is the same plan. Either the canvas strips engineer-only keys before it saves an override (a client change), or the 422 stands and `app_builder` cannot be overridden from the canvas. The 422 is the safe default; shipping the strip is a UX call for the owner and does not block the trust change. `tool_sets` outside `file_extract` and `playwright` are dropped from override steps, which is the contract [ADR-0044](20260901-0324-ADR-0044.md) locks.

**Adjacent, not filed** (INFERRED, not driven, not a security issue): a resumed run of a FILE_PIPELINE override rebuilds the file plan, because `resumed_compiled` exists only for a persisted Case 3 manifest (`engine.py:15626-15640`, `:15694-15705`), so an override does not survive a resume.
