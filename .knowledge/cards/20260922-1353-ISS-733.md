# ISS-733

## Description

Root-cause card for bug **QA-PS-021** (`BUGS.md#qa-ps-021`) — "Downstream
agents in a custom workflow receive no upstream artifacts and either
compensate by producing wrong content or emit diagnostic output instead of
the intended deliverable." (The bug's own section in `BUGS.md` is misaligned
with an adjacent entry — its Reproduction/Expected/Actual/Root-Cause/Files
content is filed one heading down, under the `QA-SG-007` anchor,
`BUGS.md:1146-1191`. Cross-checked against the bug's own metadata block at
`BUGS.md:1095-1100` — Page/Route/Severity/Found-by/Found-at all agree — and
against the ledger title at `LEDGER.md:81`; this is a `BUGS.md` filing defect,
not a different bug. Recorded here since `BUGS.md` is read-only to this
role.)

When a downstream step in a custom workflow can't find the upstream artifact
its prompt depends on, it does not fail — it compensates, in one of three
ways the report observed, and the engine never distinguishes any of them
from a clean completion:

1. **Self-narration** — the step explains its own missing input/tool instead
   of producing content. Reproduced 3/3 by [ISS-699](20260922-1220-ISS-699.md)
   (`documentation-agent`: *"Since I cannot use write_file, I'll compose them
   as responses to the user:"*).
2. **Unauthorized regeneration** — a validator/QA-role step (reporter's
   examples: `ppt-validator`, `prototype-validate`) detects the missing
   upstream build and redoes that work itself, so the deliverable is
   produced by the wrong agent, arrives with reasoning prose mixed in, and
   the run is marked `degraded` — or `completed` despite no real artifact
   ever landing.
3. **Silent drop** — a compiler/aggregator step (reporter's example:
   `backlog-compiler`) finds an upstream section missing and omits it from
   the final output with no flag.

All three trace to the trigger already root-caused in
[ISS-698](20260922-1001-ISS-698.md) (QA-PS-019): `_apply_selections`
(`backend/agents/execution_engine/engine.py:12767-12911`) never overlays a
`tools` patch onto the running step, so no custom-workflow step is ever
granted `write_file`/`edit_file`. Confirmed directly by re-reading the same
function: its `patch` dict branches cover `validators`/`gates`/`model`/
`retry`/`injects`/`skills`/`strategy`/`fanout`/`task_source` (lines
12851-12910), and the one comment mentioning `tools` (lines 12900-12904)
explains withholding `spawn_subagents`, not the `write_files`/`read_files`
omission. The base manifest (`backend/agents/workflows/custom/workflow.yaml`,
lines 23-57) declares `gates: []` on all 9 default steps, and no step
declares `produces`/`consumes` either (`grep -n 'produces\|consumes'
backend/agents/workflows/custom/workflow.yaml` returns nothing) — so the
newer typed-artifact routing path is ALSO inert here:
`_filter_consumed_outputs` (`engine.py:14824-14853`) returns `{}` immediately
when a spec's `consumes` is empty. A custom-workflow step has exactly zero
ways to receive real upstream context today, file-based or typed.

## Root cause — why the engine can't tell (CONFIRMED, file:line read directly)

What this card adds on top of QA-PS-019/ISS-698's trigger: the ENGINE has no
mechanism, anywhere, to catch a step that ran without its expected input and
produced something other than the intended deliverable.

- `backend/agents/execution_engine/engine.py:7375-7388` — `_unrecovered_agents`,
  the sole input to the run's `degraded`-vs-clean-`completed` decision, is
  built entirely from `ectx.failed_invocations` (populated only on an
  `agent_error`/exception) and `_failed_agent_ids`:
  ```python
  _completed_pairs = {(r.get("agent_id"), r.get("task_number", "") or "", r.get("visit_count", 0)) for r in results}
  _completed_agent_ids = {r.get("agent_id") for r in results}
  _unrecovered_agents = {
      agent_id
      for (agent_id, task_number, visit_count) in getattr(ectx, "failed_invocations", set())
      if (agent_id, task_number, visit_count) not in _completed_pairs
  }
  _unrecovered_agents |= (_failed_agent_ids - _completed_agent_ids)
  ```
  A step that completes WITHOUT raising — narrating, regenerating someone
  else's work, or dropping content — lands in `results` and counts as
  completed. There is no content/output inspection anywhere in this block.
  This is why the reporter's regeneration example shows a run marked
  `completed` despite producing no real deliverable, and the other
  regeneration example shows `degraded` only because that step ALSO
  happened to fail to persist its self-generated substitute to disk — not
  because the engine recognised the substitution itself.

- `backend/agents/capabilities/gates/validation.py:158-217` —
  `_build_validation_target` is the one place the engine builds a target for
  gate-driven content validation, and it resolves only the RUN's overall
  declared deliverable (`ctx.deliverable.name`) via
  `ctx.runner.deliverable_context(...)`; there is no per-step check for
  "does the specific upstream artifact this step's prompt depends on
  actually exist." Read in full: every branch (lines 180-216) either builds
  the run-level target or degrades to returning `ctx` unchanged on any
  failure — none of them look at what a PRIOR step wrote.

  **Scope correction against the original report's own technical notes:**
  none of the default `custom/workflow.yaml` steps declare
  `gates: [validation]` (confirmed: `gates: []` on all 9, lines 23-57), so
  this exact function is not literally on the call path for the reporter's
  examples unless a user opts a step into the `validation` gate via the
  composer (`_apply_selections` merges `user_step.gates` at
  `engine.py:12854-12856`). It is included here as confirming evidence that
  NO layer of the engine checks upstream-artifact presence — not as the
  direct mechanism behind the reporter's examples, which is model behaviour
  under a missing-context prompt (INFERRED which exact prompt logic fires
  each mode — not traced to one function; the three failure modes are
  prompt-driven improvisation, not a single shared code path).

## Fix direction (not applied by this card — analysis only)

Two independent layers; neither alone is sufficient:

1. **Trigger** — ISS-698's fix (add a `tools` branch to `_apply_selections`'s
   `patch` dict) closes the 100%-reliable custom-workflow case, but does
   nothing for a legitimately-missing upstream artifact elsewhere (a crash,
   a wrong path, a race).
2. **Detection, at the one choke point every caller already routes
   through** — extend `_unrecovered_agents`'s computation
   (`engine.py:7375-7388`) so a step whose declared `consumes` resolved to
   no content, or whose prompt-expected upstream file never appeared, is
   added to the unrecovered set even though it raised no exception. This is
   the single shared finalization block every pipeline reads, so one guard
   here covers `custom`, `custom_revision`, and every native pipeline in one
   place — a per-agent prompt patch would only cover the agents someone
   thought to fix, and the composer lets a user pick any of ~80.
