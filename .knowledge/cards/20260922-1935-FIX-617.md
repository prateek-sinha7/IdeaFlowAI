Resolves [ISS-796](20260922-1825-ISS-796.md) in full and the duplication half of
[ISS-782](20260922-1610-ISS-782.md) (BUGS.md QA-PS-036). ISS-782 stays **open**: its
"no `/api/runs`/`/api/workflows` on `/analytics`" expectation needs a product
decision, recorded in [ESCALATIONS.md#qa-ps-036](../../ESCALATIONS.md).

## What was wrong

A cold `/analytics` load fetched every shared payload twice —
`/api/analytics/summary?range=30d`, `/api/settings/preferences` and
`/api/capabilities`, the last of them 23.6 KB — and the workflow composer fetched
`/api/capabilities` once per `useAgentCapabilities` call site.

There is exactly **one** call site per endpoint on the analytics page
(`AnalyticsPage.tsx:184/210/237`), so this was never a second caller: it was the
absence of any request-level sharing. Each caller owned its own fetch, so

- React StrictMode's dev-mode mount→unmount→remount double-invoked each of those
  three effects with the same closure and the same args (which is why both
  `summary` calls carry the identical `?range=30d`), and
- two components that genuinely both need the catalog each paid for it.

`useAgentCapabilities` (`AgentsPopup.tsx:1525`) was written to be the shared
source and cannot be: a hook's `useState`/`useEffect` pair is per call site, so
its four call sites are four requests. `CanvasView.tsx:304` hoisted the call out
of the nodes precisely to stop per-node duplication ("so every CanvasNode's model
pill reads the SAME fetched catalog"), and then its own child
`CanvasConfigRail.tsx:162` called the same hook again, reintroducing it.

Two further calls on `/analytics` came from code whose result reached nothing:
`RunConnectionProvider.refreshLiveRuns` pulled a 50-row run list and then
discarded every row, and `page.tsx` pre-fetched the 22 KB workflow catalog into a
prop nobody reads.

## What changed and why there

**1. `frontend/src/lib/api.ts` — `cachedGet()` (new, next to `authHeaders`).**
A module-level `Map` keyed `${token}\0${path}`, holding the promise for
`SHARED_GET_TTL_MS` (30 s); failures are evicted so the next caller retries for
real. `getAnalyticsSummary`, `getPreferences` and `getCapabilities` now return
`cachedGet(...)` instead of `request(...)`. This is the one point every caller
routes through, so it closes all of them at once — `AnalyticsPage`,
`AccountSettings`, `AgentModelPicker`, `WorkflowDialog`,
`CapabilityPaletteSection` and all four `useAgentCapabilities` call sites — with
no edit to any call site, and it absorbs the StrictMode double-invoke as a side
effect rather than hiding it behind `reactStrictMode: false`.

It deliberately mirrors the `inFlightRefresh`/`refreshOnce()` single-flight idiom
already in the same file (`api.ts:225-233`), with one difference the cards
require: it keeps the **resolved** value for the TTL, not just the in-flight
promise. ISS-796's duplicate callers do not mount together — `CanvasConfigRail`
asks seconds after `CanvasView`'s fetch has already settled — so an
in-flight-only guard would not have caught it.

Scope is deliberate. Only idempotent catalog/summary GETs go through it;
`updatePreferences` evicts `/api/settings/preferences` on both sides of its PUT.
The run/workflow list fetchers are left alone: their callers refetch precisely to
observe a change (a cancel clearing the header's "N Running" pill, a gate
flipping a status), so caching them would break those refreshes. Concurrent
duplicate `/api/runs` calls are handled separately and differently by
[FIX-616](20260922-1923-FIX-616.md)'s in-flight-only guard.

**2. `frontend/src/providers/RunConnectionProvider.tsx` — read the tab-owned set
before querying.** `refreshLiveRuns` fetched `getWorkflows(t, { limit: 50 })` and
then filtered it with `tabOwnedIds.size === 0 ? false : tabOwnedIds.has(r.id)` —
so on any tab that has launched nothing, every row was dropped and the whole
fetch was waste. This provider wraps the app in the root layout
(`app/layout.tsx:51`), so it paid that on every route. The `sessionStorage` read
moved above the request and returns early when the set is empty, landing in the
same end state (`autoIdsRef = []`, `recomputeLiveRunIds()`, sticky focus still
unioned in). The now-unreachable arm of the filter ternary went with it.

**3. `frontend/src/app/[...view]/page.tsx` — dropped a dead prefetch.** The
mount effect called `getWorkflowDefinitions` into `homeWorkflows`, passed to
`DashboardLayout` — which destructures it at `:458` and never reads it again.
`HomeLaunchGrid` has since moved to Redux (`state.global.workflows`, preloaded by
`store/listenerMiddleware.ts`) and takes no such prop
(`DashboardLayout.tsx:2894-2903`). So this was a 22 KB `GET /api/workflows` fired
on every route — `[...view]` is the catch-all — whose result reached nothing. The
call, the `homeWorkflows` state, the prop pass and the two imports it orphaned
are gone; `DashboardLayout`'s optional prop declaration is left alone as
pre-existing.

## What this did NOT fix

`/analytics` still calls `/api/runs` twice and `/api/workflows` once. Those come
from the Redux sign-in preload (`store/listenerMiddleware.ts`, dispatched from
`page.tsx:892` on every route) and from `page.tsx`'s `recentRuns` fetch, and both
payloads are consumed on `/analytics` by the always-mounted `AppHeader`
(`:126` workflow labels, `:176` the live-run badge). Removing them is a product
decision — see [ESCALATIONS.md#qa-ps-036](../../ESCALATIONS.md).
