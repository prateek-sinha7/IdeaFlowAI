## What was wrong

The root cause is on [ISS-1137](20261009-0304-ISS-1137.md) and is not re-derived here. A launch's outcome had nowhere to go:

- **No message.** `onStartPipeline` (`page.tsx`) ended in `void Promise.resolve(startPipeline(...)).then(...).catch(...)` and was typed
  `=> void`. Its `.catch` only reset state and logged in development, so a refusal from any of the 17 `onStartPipeline(` call sites in
  `DashboardLayout.tsx` was silent.
- **Run stayed disabled.** The FIX-614 latch in `ComposerPage.handleRunOnce` and `IdeaInputPage.handleRun` had no release. It relied on
  the page unmounting at every launch, and that premise was false. A refused launch never gets a run id, so the view never leaves the
  canvas or `/create/<type>`, and Run stayed dead until a reload.

## What changed, and why there

Five frontend files changed. There is no backend, manifest, `AGENT.md`, skill, `.env` or dependency change.

1. **The outcome handler returns the outcome** (`page.tsx:4390-4485`).
   - `onStartPipeline` now `return`s its promise chain. The `.then` returns the run id (`:4458`).
   - A null run id now throws into the `.catch` (`:4460-4462`) instead of taking the old silent `else { launchPendingRef.current = false; }`.
     `sendCommand` returns null when there is no token or when a 2xx body has no run id, and the card counts a null id as a refusal.
   - The `.catch` keeps its two recovery lines (`launchPendingRef.current = false; resetPipeline();`). It then sets `launchError` from
     `launchRefusalMessage(err)` and resolves `null` (`:4479-4484`).
   - It never rejects, so the 16 call sites that ignore the promise cannot leak an unhandled rejection.
   - `setLaunchError(null)` at the start of every launch (`:4349-4350`) clears the previous refusal.

   This is one definition for all 17 call sites (INV-12), as the card asks.
2. **The text** comes from `launchRefusalMessage(err)` (`api.ts:325-337`):
   - `detail.error` for a `_reject` body;
   - `errorMessageFromDetail` for a string detail or a 422 list;
   - otherwise "The run could not be started. Please try again.";
   - `null` for `host_capacity_exhausted`, because `ServiceBusyProvider` already shows that one.

   It never uses `ApiError.message`, which is the raw JSON body. ISS-1137 corrected ISS-969 on this point. It branches on the error `code`
   only, never on a pipeline type or workflow name (SC-001 / INV-1).
3. **The banner** is a `role="status"` strip at `DashboardLayout.tsx:2818-2831`. It sits beside the existing connection banners, with the
   same placement and styling as "Connection lost.", and has a Dismiss button. It is fed by the props `launchError` and
   `onDismissLaunchError` (`:116-118`, `:473-474`). `onStartPipeline` is now typed `=> Promise<string | null>` (`:113-114`).
4. **The latch is released on refusal only, in the two panels that own one.**
   - The canvas `onRun` lambda (`DashboardLayout.tsx:3265-3270`) and `handleRunPipeline` (`:1846-1848`) return the outcome.
   - `ComposerPage.handleRunOnce` passes both of its `onRun(...)` calls through `releaseIfRefused` (`ComposerPage.tsx:1046-1052`, `:1223`,
     `:1232`).
   - `IdeaInputPage.handleRun` chains the same `.then` (`IdeaInputPage.tsx:1702-1711`).
   - The latch stays set on a run id, while the POST is pending, and when `onRun` returns nothing.
   - The release is not in a `finally`. `onRun` returns before the POST settles, so a `finally` would reopen FIX-614's double-click window.
     The release runs in a microtask after the POST settles. By then, any same-tick second click has already hit
     `if (submittingRef.current) return;`.
   - Both `onRun` props are typed `=> Promise<string | null> | void` (`ComposerPage.tsx:132-140`, `IdeaInputPage.tsx:792-794`).
5. **The three comments that said the page unmounts are corrected:** `ComposerPage.tsx:1037-1042`, `IdeaInputPage.tsx:1600-1608` and
   `DashboardLayout.tsx:3262-3264`.

### Where this differs from the cards, and why

- **One banner, without a second copy in the panels' `saveError` line.** ISS-1137 says "The message: once, at the outcome handler". It
  also says the panels should "release the latch + its existing inline banner (`saveError`)". The panels release the latch but do not
  repeat the text: the layout banner already shows it once on both surfaces, and a second copy of the same sentence is noise. It would
  also be a second match for the e2e's page-wide `get_by_text`.
- **React state and a prop, not a pub/sub in `api.ts`.** ISS-1137 cites `onCapacityRejected` as the house pattern for a single seam.
  That pattern exists because the capacity publisher, the `ApiError` constructor, has no React owner. Here the publisher is the `.catch`
  inside `page.tsx`, which already renders `DashboardLayout`, so a prop is the smaller channel.
- **Flag for the app-bent-to-test audit: the `.catch` dev log is now `console.warn`. It was `console.error`** (`page.tsx:4473-4478`).
  - Scope: development only (`process.env.NODE_ENV !== "production"`). Production behaviour is identical.
  - Why it changed: the Next 16 dev overlay patches only `console.error`, and it copies the error text into a hidden
    `#nextjs__container_errors_desc` node. With the banner showing the same text, the e2e's page-wide `page.get_by_text(text)` then
    resolves to two elements and Playwright strict mode fails (`evidence/qa-kb-106/fix-02-dev-overlay-strict-mode.txt`).
  - The change was found through the test. It also stands on its own: after this fix a refusal is a handled, user-visible outcome, and a
    dev-overlay "Issue" for it is the red "1 Issue" pill that ISS-1137 had to explain away as not product UI.
  - If the audit disagrees, the alternative is one line. Restore `console.error`, and have the test-writer scope the e2e locator to the
    banner (`page.get_by_role("status").filter(has_text=text)`), as the ad-hoc check below does. No test was edited.

## Behaviour changes a caller can see

- A refused launch from any of the 17 `onStartPipeline` call sites shows the backend's reason in a red banner at the top of the app. Dismiss
  clears it, and so does the next launch. A capacity refusal still shows only the busy modal.
- After a refusal, Composer "Run once" and the Input panel's "Run workflow" work again, including Cmd/Ctrl+Enter, and the brief stays.
- A 2xx launch response without a run id now counts as a refusal: a generic banner and `resetPipeline()`. It used to be a silent no-op.
- `DashboardLayoutProps.onStartPipeline` returns `Promise<string | null>`. The `vi.fn()` stubs in tests still type-check.
- In development only, the launch-failure log is a `console.warn`. Next's dev overlay no longer counts a handled refusal as an "Issue".
