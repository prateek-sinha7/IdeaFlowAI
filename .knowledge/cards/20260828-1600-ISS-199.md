## What happened

Validating BUG-20260828-012900-runs-id-files (register: `bug-hunter/ledger.md`).
On a completed `ppt_v2` run (`/runs/b9feac1c-ec21-4531-8ba7-bb391786993e/files`),
the Files tab's "Final output" hero shows `kindred-a-custombuilt-social-network-pla.html`
(53.2 KB) labeled HTML/validated. `GET /api/runs/<id>/sandbox` lists four
`deliverable:true` candidates on this run:

- `presentation.html` — 54,551 bytes (the backend's own `deliverable_filename` on
  `GET /api/runs/<id>`, per ADR-0029)
- `presentation.pptx` — 163,771 bytes, `kind:"binary"` (the actual PPTX this
  workflow's last agent, "PPTX Code Generator", produces)
- `tmp/kindred-pitch-deck.html` — 54,588 bytes (a scratch file the Deck Engineer
  agent wrote mid-pipeline into a `tmp/` working directory)
- `conversation_history/...ppt-code-generator.md` — 319,756 bytes

The size the UI shows (53.2 KB) matches `tmp/kindred-pitch-deck.html` (54,588 B ≈
53.31 KiB), not `presentation.html` (54,551 B ≈ 53.27 KiB) — a 37-byte difference
confirmed by both the register's original report and this validation. Neither
`presentation.pptx` nor `presentation.html` is ever listed, previewed, or
downloadable (individually or via "Download All").

## Root cause

`frontend/src/app/[...view]/page.tsx:1470` (live-stream path) and `:2985`
(reopen path) both route `pipelineType`/`fullRun.type` in
`{"ppt", "ppt_v2", "ppt_revision"}` into `setPptContent(finalOutput)` /
`setPptContent(fullRun.output)` — i.e. the run's raw `output` field, which is
`ctx.last_streamed`, the text the LAST agent in the pipeline actually streamed.
For `ppt_v2` that last agent is "PPTX Code Generator" (step 4), whose own
streamed text is not byte-identical to `presentation.html` (written by step 3,
only *read* by step 4 — see ADR-0029's "one writer per file" constraint) and
apparently matches the `tmp/` scratch file's content instead.

`FilesTab.tsx`'s `deriveDeliverableFiles` (~line 388) then builds the "Final
output" row straight from that `pptContent` string — deriving both the byte
size and a content-derived filename (`<title-or-h1>.html`) from it — with no
call back to the run workspace/sandbox listing to resolve the file the backend
actually named `deliverable_filename`. Neither `page.tsx` nor `FilesTab.tsx`
ever reads `presentation.pptx` or reconciles against `is_deliverable_relpath`
(FIX-316) at all — the PPTX binary is structurally unreachable from this
surface regardless of which HTML file wins.

Note: ADR-0029 intentionally keeps the DECLARED deliverable as
`presentation.html`, not the `.pptx` — that part is by design, not this bug.
The defect here is that the Files tab shows neither the declared HTML nor the
pptx, but a third, mid-pipeline scratch file, because of the `last_streamed`
derivation above.

## Reproduction (3/3, cold start every cycle)

Each cycle: fresh `page.goto('/dashboard')`, then fresh
`page.goto('/runs/b9feac1c-ec21-4531-8ba7-bb391786993e/files')`, 2s settle,
re-inspect. Identical result on cycles 1, 2, and 3 — deterministic, not a race:
"Final output" row always reads `kindred-a-custombuilt-social-network-pla.html`,
HTML (.html), 53.2 KB, validated; `presentation.pptx` never appears in the file
list on any cycle.

Cross-checked via `GET /api/runs/<id>/sandbox` (returns the correct listing
including both `presentation.pptx` and `presentation.html`, both
`deliverable:true`) and `GET /api/runs/<id>` (`deliverable_filename:
"presentation.html"`) — confirms the mismatch is purely client-side selection,
not a missing or failed fetch.

## Expected vs actual

- **Expected:** Files tab's "Final output" surfaces the backend's declared
  `deliverable_filename` (`presentation.html`) — or, given this workflow's
  purpose, offers the `presentation.pptx` binary — read from the run's
  workspace/sandbox listing.
- **Actual:** "Final output" is built from `ctx.last_streamed` text
  (`fullRun.output`), which for `ppt_v2` is neither of those — it renders a
  `tmp/`-directory scratch file's content, mislabeled as the final deliverable.
