## What is stale

Found while fixing QA-KB-036 ([FIX-689](20261001-2142-FIX-689.md)) and left alone, because no card named these lines.
[ISS-887](20261001-2114-ISS-887.md) corrected the docstring of
`test_reconcile_degraded_tracks_latest_completion_only` in
`backend/tests/integration/agents/test_restart_resume_db.py`. Its parametrize comments and its name still explain the
tails with the last-by-seq rule that [ISS-689](20260918-ISS-689.md) deleted from `_reconcile_terminal_status`:

| site | text |
|---|---|
| `:4318-4319` | `# ... The LATEST` / `# pipeline_complete must decide, not "was ANY completion ever degraded".` |
| `:4334-4335` | `# Reverse order: a clean completion, then a LATER degraded one — latest-wins cuts` / `# the other way too.` |
| `:4377` | `async def test_reconcile_degraded_tracks_latest_completion_only(` |

The live rule is the boundary scan of [FIX-484](20260902-1600-FIX-484.md). The two differ when an attempt fails
after an earlier degraded completion: the latest completion is degraded, but the verdict is `failed`
(tail T5 in [ISS-886](20261001-2114-ISS-886.md)). The four tails of this test cannot tell the two rules apart, so the
comments pass unchallenged. A reader who trusts them is misled in the way ISS-689 describes.

## Disposition

The comments need rewording, and the name could become, for example, `..._tracks_latest_attempt_only`. Renaming
changes `-k` selections and pytest ids that cards and ledger rows quote, so that is a decision for the analyzer, not a
blind rename. No behaviour is involved.

## What would confirm or refute this

on 2026-10-01 (working tree, `feat/user-stories-v2`) prints the lines quoted above. It was not reproduced by a
validator, so it is INFERRED on the line's scale.

### Root cause (CONFIRMED)

1. **The text is stale.** `backend/tests/integration/agents/test_restart_resume_db.py`:
   - `:4318-4319`: `# 13:13 — yet pre-fix the run still read "degraded" forever. The LATEST` then
     `# pipeline_complete must decide, not "was ANY completion ever degraded".`
   - `:4334-4335`: `# Reverse order: a clean completion, then a LATER degraded one — latest-wins cuts` then `# the other way too.`
   - `:4377`: `async def test_reconcile_degraded_tracks_latest_completion_only(`

   The docstring right below them (`:4380-4386`) is already correct, after ISS-887 / FIX-689: "the degraded verdict must read off the
   LAST ATTEMPT only".
2. **They were written for a rule that lost a merge.** `git blame` gives `f236259113` for all three sites (2026-09-11, "fix(engine):
   resume a DB workflow at the failed step, and stop reporting a finished run as failed"), the commit that added the last-by-seq
   `degraded` rule. [FIX-484](20260902-1600-FIX-484.md) (`18a733e68`, 2026-09-02) had put the boundary scan in the same function on an
   independent line: `git merge-base --is-ancestor 18a733e68 f23625911` exits 1. Merge `4ebd98e8f` (2026-09-16) has both as ancestors and
   kept FIX-484's ladder, so the rule these comments explain stopped running. [ISS-689](20260918-ISS-689.md) / [FIX-689](20261001-2142-FIX-689.md)
   deleted its dead production half and the mislabeled comments, and reworded the docstring.
3. **The live rule.** `backend/app/api/run_commands.py`, docstring `:805-808` ("a degraded ``pipeline_complete`` at or after the last
   attempt boundary (``run_resuming`` / ``pipeline_start``) → ``degraded``") and the ladder:
   ```python
   last_reattempt_seq = max(reattempt_seqs) if reattempt_seqs else 0                        # :915
   current_attempt_completes = [e for e in completes if e.seq >= last_reattempt_seq]        # :918-920
   degraded_current = any(... == "degraded" for e in current_attempt_completes)             # :921-925
   if degraded_current:                                                                     # :930
   elif current_attempt_completes and not failed_current:  new_status = "completed"         # :932
   else:                                                   new_status = "failed"            # :934-935
   ```
   `_latest_complete` (`:841-843`) survives only to source the degraded error text (`:970-974`). The verdict is `any()` over the
   completions at or after the boundary. It is not "the latest completion".
4. **Why FIX-689 left them.** Its card lists them under "Not changed (outside the cards' scope)": ISS-887 named two docstrings, so the
   inline comments and the name had no card until this one.
5. **Why nothing flags them (measured).** All four tails give the same verdict under the live rule and under the dead one. With the
   dead last-by-seq rule restored on a scratch copy (variant opt2), the file's `-k reconcile` selection is 2 failed, 20 passed, and
   the two failures are the FIX-689 locks `test_reconcile_fix484_boundary_scoping[T5-iss436-degraded-then-failed]` and
   `[T6-iss437-failed-then-clean]`. The four tails of this test stay green. Table and raw output:
   `evidence/qa-kb-075/02-variant-matrix.txt`, `03-repo-tests-under-variants.txt`; the same matrix is in [ISS-1016](20261002-0606-ISS-1016.md).
6. **How a reader is misled, concretely.** The comment says the latest `pipeline_complete` decides. Apply that to T5
   (`test_reconcile_fix484_boundary_scoping`, `:6109-6120`: a degraded completion at seq 2, then a resume that fails): the latest
   completion is the degraded one, so the comment predicts `degraded`, while the pinned expectation is `failed` (opt2 gives
   `degraded`). Two tests in one file contradict each other if both are trusted. [ISS-689](20260918-ISS-689.md) adds that the dead
   rule's own premise ("a run completes at most once per attempt, so last-by-seq IS the latest attempt's verdict") breaks when an
   attempt fails, because a failed attempt emits no `pipeline_complete`.

### Decision: keep the test name (the question the Disposition leaves open)

Keep `test_reconcile_degraded_tracks_latest_completion_only`, reword the two comments, and do not reopen it:

- **A rename orphans quoted ids.** `grep -rlF test_reconcile_degraded_tracks_latest_completion_only .knowledge` returned five cards
  before ISS-1016 was filed (ISS-689, ISS-886, ISS-887, FIX-689, ISS-902). Outside `.knowledge`, `grep -rnF` (excluding `.git`, `node_modules`, `.venv`, `.next`,
  `bug-hunter`) finds only the definition at `:4377` and four pytest-id lines in `evidence/qa-kb-036/02-analyze-fix-variants.txt`; CI
  config, scripts and docs do not select it by name. Cards are permanent records, so after a rename those five quoted ids would select
  zero tests.
- **The name is not false for what the test pins.** On all four tails the latest completion IS the last attempt's completion, or
  there is none. That is why the author chose it, and why the tails cannot tell the rules apart. The docstring states the live rule in
  its first sentence, so the name is the only residual.
- **The report scopes the fix to comments.** BUGS.md QA-KB-075 "Expected" is "Comments describe the live FIX-484 rule", and its triage
  sketch (not binding) also keeps the name.
- A rename would buy no behaviour and costs `-k` selections people already typed. If someone still wants it,
  `..._tracks_latest_attempt_only` is the accurate word: one line at `:4377` plus a supersession note on the five cards.
