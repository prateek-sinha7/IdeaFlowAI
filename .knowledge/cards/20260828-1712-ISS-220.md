# ISS-220

**Register source:** `BUG-20260828-015930-runs-cancelled` in `bug-hunter/ledger.md`.

## Symptom

Clicking "Run Again" on a cancelled `ppt_v2` run navigates to
`/runs/{id}/stream` and shows a live progress panel ("Running", "0/4 agents",
first agent "Starting…"). The backend resumes the pipeline and — in this
fixture family — fails almost immediately (`pipeline_failed` + `chat_reply`
land on the event stream ~3-4s after resume, confirmed via direct
`GET /api/runs/{id}/events` polling). The already-mounted `/stream` page does
not reliably reflect this: in 2 of 3 cold-start reproduction cycles it stayed
frozen on the pre-resume "Starting…"/mid-step state for 15+ seconds after the
backend had already terminated the run, with no error surfaced anywhere on
screen. A full manual reload (fresh `page.goto` to the same URL) always
recovers immediately, showing the correct terminal state (failed agents list,
correct duration, "What went wrong" chat card).

## Reproduction (cycle-by-cycle, all cold start — fresh nav to `/runs/{id}`, no prior UI state)

- **Cycle 1** — run `826d09f0-21b0-4b8f-a79f-843fc5c82adb` (ppt_v2): clicked
  "Run Again", checked the live page 12s later — it had already caught up to
  the correct "Failed" state (header badge, "What went wrong" panel, failed
  agents list all present) with no reload. **Not reproduced this cycle.**
- **Cycle 2** — run `d6e425b6-df0d-4f54-9bba-f4a771e33812` (ppt_v2): clicked
  "Run Again"; backend's `/events` showed `pipeline_failed` (seq 3814) and
  `chat_reply` (seq 3815) within ~5s. The live page, checked at +15s and again
  at +30s with **zero** interaction in between, still showed header "Running",
  "1/4 agents", tab-strip subtitle "Deck Engineer Agent · streaming / building
  step 2 of 4" — stale and self-contradicting the Steps panel body directly
  below it, which HAD picked up "Run failed · 1/4 agents". A manual reload to
  the same `/stream` URL immediately corrected the header to "Cancelled" (sic
  — `status` field on the run resource itself is never flipped to `failed`,
  a known side-issue already separately filed) and rendered the full
  "What went wrong" transcript. **Reproduced.**
- **Cycle 3** — run `30dc9b1f-d9f9-4f96-b260-9571d8d42083` (ppt_v2): clicked
  "Run Again"; backend `/events` showed `pipeline_failed`/`chat_reply` within
  ~4s (run `status` stayed `cancelled` throughout, matching cycle 2). The live
  page, checked at +16s with zero interaction, was an exact match to the
  original register report: header "Running", "0/4 agents", Steps tab
  "Pipeline running · 0/4 · BUILDING", "Presentation Strategist Agent ·
  Starting…" — completely unmoved from the instant the click fired, despite
  the backend having already terminated the run twelve-plus seconds earlier.
  A manual reload to the same URL immediately corrected it (duration "3s",
  "0/4 agents", full "What went wrong" chat transcript). **Reproduced.**

**Score: 2/3.** The named trigger is a timing race, not a hard 100% freeze:
whichever reconnect/backoff cycle the client's SSE session happens to run
after the resume-triggered remount either does or does not pick up the
terminal frames emitted ~3-5s after resume, before the client has finished
re-establishing its stream. Cycle 1's self-recovery at the 12s mark is
consistent with a delayed catch-up on the SAME race, just observed after it
had already resolved — not evidence of a different, unaffected code path.

## Conditions established

- **Tier:** qa-admin (enterprise) — not tier-specific, no cross-tier axis run.
- **Entry path:** deep link to `/runs/{id}` (cancelled run detail), then
  click "Run Again" in-page — matches the register's own repro path exactly.
- **Run state:** a cancelled `ppt_v2` run whose resume fails fast (this
  fixture family's failure path: "The model rejected this request", all 4
  agents in `agents_failed`).
- **Timing:** the freeze is observed reliably in the 15-30s window
  immediately after the backend's `pipeline_failed`; whether it later
  self-heals (as in cycle 1) was not characterized further — worth revisiting
  if a fix attempt needs a tighter reproduction window.

## Root cause (circumstantial, from code reading — not yet a confirmed fix)

`frontend/src/components/layout/DashboardLayout.tsx`'s `pipelineState.isRunning`
effect (~line 735) is the single funnel that pushes the browser to
`routes.runStream(incomingRunId)` (line 768) whenever a pipeline starts,
including a resume via `handleResumeRun` (line 2253) → `postResume` →
`runConnection.attachRun`. Unlike the three OTHER call sites in the same file
that push to `/stream` (lines 2527-2534, 2538-2551, 2575-2591), this effect
does **not** call `onSwitchToLiveRun` before the `router.push` — it relies
entirely on the page-level T11 `liveRunIds` fast path that
[FIX-298](20260825-FIX-298.md) added to `frontend/src/app/[...view]/page.tsx`
to re-seed state after the resulting remount.

`router.push` to a new URL under the `[...view]` catch-all remounts
`page.tsx`, wiping every `useState` including whatever the SSE hook was
tracking. The remount's re-attach (T11 fast path) has to win a race against
the backend, which — for this fixture family — emits its terminal events
only ~3-5s after resume. When the reattach loses that race, the newly
mounted page's SSE session starts its own event cursor from whatever the
durable-event replay handed it, and if `pipeline_failed`/`chat_reply` land in
the gap between the old session tearing down and the new one's first
successful poll/reconnect, the client-side render is not told the run is
already over — matching FIX-298's site (frozen live view after a remount)
but on the DASHBOARD-triggered push, not the page-level fast path FIX-298
already patched.

This has not been instrumented to a single `file:line` fix; it is offered as
the most plausible mechanism given the reproduction pattern (intermittent,
correlates with how fast the backend terminates relative to the remount) and
the precedent at [FIX-298](20260825-FIX-298.md), which fixed an adjacent but
distinct symptom (a permanently blank screen, not a stale-but-partially-alive
one) in the same remount-and-reattach seam.

## Root cause — confirmed (analyzer pass, 2026-08-28)

Added without altering the section above, which stays as the validator's original
record. This pass traced the mechanism the section above could not pin to a line, and
found the exact structural gap:

1. `DashboardLayout.tsx:735-769` (the `pipelineState?.isRunning` effect) — read in full.
   Line 767-769 is unconditional: `if (incomingRunId) { router.push(routes.runStream(incomingRunId)); }`,
   with no `onSwitchToLiveRun` call first — confirmed, unlike the three sibling
   `router.push(routes.runStream(...))` sites at lines 2526-2536, 2548-2552 and
   2558-2592, which all call `onSwitchToLiveRun`/an equivalent before pushing.
   `handleResumeRun` (line 2253-2311) does call `runConnection.attachRun(run_id)`
   itself (line 2273) as its own pre-registration, but `attachRun`
   (`RunConnectionProvider.tsx:363-370`) only adds the run id to the SSE-transport
   `liveRunIds` set — it does none of `handleSwitchToLiveRun`'s page-state work
   (`setContentSourceRunId`, `runStore.switchViewTo`, durable replay), which is why
   [FIX-298](20260825-FIX-298.md)'s T11 fast-path re-seed is what makes the shell
   render correctly (not blank) after the remount — but only as a one-shot snapshot.
2. `frontend/src/app/[...view]/page.tsx:2195-2206` — read in full. This page-local
   `useEffect` is the **sole** wiring between `RunConnectionProvider`'s SSE fan-out
   and this page's `pipelineState`/`runStore`: it calls `runConnection.subscribe(...)`
   on mount and returns `unsubscribe` on cleanup. Both `runSubscribe`
   (`RunConnectionProvider.tsx:345-350`, `useCallback(..., [])`) and
   `handleWebSocketMessage` (`page.tsx:935-2037`, `useCallback(..., [])`) are
   referentially stable, so this effect fires exactly once per page.tsx mount and
   once per unmount — i.e. only at a remount boundary, never on an ordinary re-render.
3. `frontend/src/providers/RunConnectionProvider.tsx:331-339` (`fanout`) — read in
   full: `subscribersRef.current.forEach((fn) => fn(msg))`, no buffering, no queue,
   no last-message cache. A message fanned out while the page's handler is not
   currently in `subscribersRef` — precisely the window between the OLD page.tsx
   instance's unmount cleanup and the NEW instance's mount effect — is delivered to
   that handler never. `RunStreamConnection`/`useRunStream` itself lives ABOVE the
   router (mounted inside the provider) and is untouched by the page remount, so the
   transport keeps receiving frames from the backend throughout; it is only the
   page-local subscriber wiring that drops out.
4. `page.tsx:3285-3419` (T11 `liveRunIds` fast path) — read in full. Its durable-event
   catch-up (`getRunEvents(...).then(...)`) is a single REST fetch taken once, at the
   moment the fast path runs (once per remount) — not a poll, never retried. It can
   only replay events already persisted in the backend's durable log at that instant;
   anything the backend emits after that snapshot request relies entirely on (2)/(3)
   above, which is exactly where the frame is lost.

**CONFIRMED:** the four mechanisms above, each read at the cited file:line — a page.tsx
remount has a real window in which the SSE fan-out has no listener for
`pipelineState`, the fan-out does not buffer for a late resubscriber, and the one
compensating snapshot fetch is one-shot and pre-dates any event the backend has not
yet emitted.

**INFERRED (not independently instrumented):** that the *specific* frames lost in the
2/3 reproduced cycles fell inside this exact window, rather than some other cause. What
would settle it: a timestamped log of (a) when `RunConnectionProvider.fanout` dispatches
`pipeline_failed`/`chat_reply` for the resumed run, versus (b) when the OLD page.tsx
instance's subscribe-effect cleanup and the NEW instance's subscribe-effect mount fire,
during a failing reproduction cycle.

**Blast radius (grepped, not assumed):** `handleResumeRun` is the single funnel for
every resume — `RunChatLane.tsx` wires the identical `onRelaunch` prop
(`DashboardLayout.tsx:3012`) to the cancelled terminal card's "Run Again"
(`RunChatLane.tsx:1699,1730` — this card's reproduced case), the failed terminal card's
"Reopen & fix from the failed step" (`RunChatLane.tsx:1816-1824`), and the degraded
terminal card's "Run again" (`RunChatLane.tsx:1845-1867`). Filed as siblings:
[ISS-236](20260828-1740-ISS-236.md) (failed-run reopen) and
[ISS-237](20260828-1741-ISS-237.md) (degraded-run relaunch) — both INFERRED, same code
path, not yet independently reproduced.

**Where the fix belongs:** the shared seam — either (a) make `RunConnectionProvider`'s
`fanout`/`subscribe` replay-safe across a resubscribe (track a per-run last-delivered
cursor and flush the gap to a newly (re)joining subscriber), or (b) give the T11
fast-path's durable replay a second, delayed pass (mirroring the `setTimeout` retry
pattern `handleResumeRun` already uses for its own 409 race at
`DashboardLayout.tsx:2291-2299`) so a frame lost to the subscribe gap is still picked up
shortly after without a manual reload. Not in `handleResumeRun` or any individual
relaunch button — that would leave the two sibling paths above, and any future caller of
the same `isRunning` effect, exposed to the identical race.

## Expected vs actual

- **Expected:** once the backend emits `pipeline_failed`, the live `/stream`
  view reflects it within the normal SSE latency (as it does when the freeze
  does not occur, e.g. cycle 1) — header badge, chat transcript, and Steps
  lane all update without requiring a reload.
- **Actual:** in 2 of 3 cold-start cycles, the view froze on a stale
  pre-termination state (header "Running", stale agent count, stale
  tab-strip subtitle) for 15-30+ seconds with zero self-recovery observed in
  that window, only correctable by a full manual reload.

## Side-observation (not filed separately here — already noted in the register)

Across all three test cycles, `GET /api/runs/{id}` continued to report
`"status": "cancelled"` even after the resumed pipeline had failed and
`completed_at`/duration had been updated — the run's own terminal `status`
field is never flipped to `failed` by the resume path. This is the same
side-issue the register's `BUG-20260828-085830-runs-cancelled` entry already
tracks separately; not re-filed here.
