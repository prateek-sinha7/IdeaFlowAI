## Why it matters

Four of these are load-bearing repo entry points, not scratch:

- `README.md` is what a new contributor (or GitLab's project page) opens first.
- `docker-compose.yml` / `docker-compose.prod.yml` are the documented local and
  production bring-up.
- `app.env.example` is the template every `.env` is copied from — and `.env`
  itself is gitignored, so this file is the only checked-in record of which
  variables the app expects.

The remaining files (`README.txt`, `STATUS-vel-proj-ctx-adr.md`,
`home-page.md`, `pre-commit-issue.md`, `dashboard.md`) read as working notes
and were plausibly meant to go.

## What is NOT claimed here

This is not a claim that the deletion was wrong. A cleanup commit removing
stale root-level clutter is reasonable, and several of these files clearly
were clutter. The issue is that the commit message names only the screenshots,
so the removal of the four entry-point files is invisible to anyone reading
`git log` — including to whoever next wonders where the compose files went.

## Suggested resolution

Decide per file, then either restore or record the decision:

    git show 215b911e0^:README.md > README.md            # etc.

If they are meant to stay deleted, say so in a follow-up commit message or
supersede this card with the rationale. If `app.env.example` in particular is
gone permanently, the expected environment variables need a home somewhere
else — it is currently the only checked-in list.
