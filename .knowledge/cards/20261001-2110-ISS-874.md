# ISS-874

> **INFERRED sibling** of [ISS-639](20260831-1645-ISS-639.md), derived during the QA-KB-045 analysis (2026-10-01). The mechanism was READ; the cost was measured only at the store level (`read_events` on the largest local runs), not through the chat lane end to end (see "What would settle it").

## Condition

Any `chat_message` POST, or narrator milestone card, written to a run whose durable `run_events` log is large.

Callers (`grep -rn append_event_next_seq backend/ --include='*.py'`, non-test): `app/api/run_commands.py:1236` (`_persist_chat_message`, one per chat message) and `:1526`, `:1546`, `:2106`, `:2253`, `:2292` (other chat-lane writers); `app/agents/chat_narrator.py:330` (`persist_milestone_card`, one per projectable milestone event, reached from `engine.py:4222` in `execute()` and `engine.py:15913` in `_drive_resumed_stream` through `_RunEventSink.emit_milestone_card`).

## Code (CONFIRMED, read)

`authz.py:556-563`:

```python
for _ in range(max(1, _max_attempts)):
    existing = await self.read_events(run_id, after_seq=0)
    for row in existing:
        if getattr(row, "event_id", None) == event_id:
            return False, int(getattr(row, "seq", 0) or 0)  # idempotent no-op
    next_seq = (
        max((int(getattr(r, "seq", 0) or 0) for r in existing), default=0) + 1
    )
```

Every attempt materialises the whole run log, to (a) find an `event_id` match and (b) derive the tail.

## Expected vs actual

- **Expected:** a keyed single-row `event_id` lookup (served by `uq_run_events_scope_event`) plus the bounded `_max_event_seq` tail probe per attempt, which is what `append_event_at_or_after` (`authz.py:601-657`) already does for the engine sink.
- **Actual:** one whole-log read per attempt. `read_events` took 2.2-7.0 s on the 37k-137k-row runs of the local corpus (two passes, idle box; evidence below), so each chat message or milestone card on such a run pays that before its row is written.

## Why the root cause implies it

This is the idiom [ISS-639](20260831-1645-ISS-639.md) is about, at its origin: `authz.py:561-563` is the same `max(... seq ...) + 1` over `read_events(run_id, after_seq=0)`. [FIX-499](20260831-1641-FIX-499.md) removed it from `_stamp_resume_marker`, calling it "the exact cost profile that already ruled `append_event_next_seq` out for the engine's own event sink" (and `authz.py:541-545` says the same in the method's docstring), and its "Deliberately NOT changed" paragraph left the chat-lane callers because they depend on the `(run_id, event_id)` idempotent no-op. That reason covers the semantics, not the cost, and no open card tracks the cost (`grep -i append_event_next_seq .knowledge/INDEX.md` returns only FIX-499).

## Why it is NOT folded into ISS-639's fix

It is not a pure swap to `_max_event_seq`: the method must keep its `(created, seq)` idempotency contract for double-submitted `message_id`s, and the Postgres concurrency test that exercises it is `requires_postgres` (per FIX-499), so it cannot be proved in the offline tier. Different proof obligation, so a separate card.

## Escalation condition (INFERRED)

`_RunEventSink.emit_milestone_card` swallows only `SQLAlchemyError` (`engine.py:3302-3313`: `if not isinstance(exc, SQLAlchemyError): raise`). A `StoreTimeout` (a `RuntimeError`, `authz.py:78`) from a read that crosses the 10 s bound (`authz.py:74`) would propagate out of the card write into the run's drive loop. Measured idle-box reads (2.2-7.0 s) are inside the bound, so this is not shown to fire; it would settle on a slower box or a larger run.

## Fix shape (design, not a one-liner)

Per attempt: one keyed `event_id` lookup for the idempotent no-op, `_max_event_seq` for the tail, then the existing IntegrityError retry. Preserve `(created, seq)` and the `append_event_at_or_after` re-stamp semantics. The fixer owns the design.

## What would settle it

- An offline counting test: wrap `ScopedStore.read_events`, call `append_event_next_seq` on a seeded run, assert the number of `read_events(after_seq=0)` calls (today at least 1 per call).
- A measurement of `persist_milestone_card` on a seeded 100k-row fixture (in-memory SQLite, never the live DB: this path writes).

## Evidence

QA-KB-045 analysis probes under `evidence/qa-kb-045/` (repo root): `03-analysis-read-vs-max-timing.txt` (cost of the real `read_events` path), `02-analysis-db-size-and-explain.txt` (corpus size).

## Fix (2026-10-01)

Fixed by [FIX-688](20261001-2140-FIX-688.md) with the design above (`authz.py:556-575`). Each attempt now runs one
keyed lookup through `_run_bounded` for the idempotent no-op, then `_max_event_seq(run_id) + 1` for the tail. The
lookup is `query(RunEvent.seq)` on `run_id`, `event_id`, `seq > 0` and `_scope_owner_ws`, served by
`uq_run_events_scope_event`. The IntegrityError rollback-and-retry and the 8-attempt bound are unchanged.

The `(created, seq)` contract was checked against the pre-fix loop, copied verbatim, in eight scenarios. They
include a concurrent writer committing the same `event_id` between the read and the insert, and a session-less
store. Results and final rows were identical (`evidence/qa-kb-045/04-fix-probe-degrade-and-equivalence.txt`).
`test_append_event_next_seq_does_not_read_whole_log` now reports `XPASS(strict)`, and the marker is left for the
6-verifier. The Postgres concurrency test (`tests/integration/db/test_db002_postgres_seq_concurrency.py`,
`requires_postgres`) was not run, because this line runs the offline tier only.

The escalation path is unchanged: `emit_milestone_card` (`engine.py:3302-3313`) still re-raises a non-SQLAlchemy
error. Its per-attempt reads are now index probes instead of a whole-log read.

**What the analysis missed.** The blast radius did not list
`backend/tests/integration/repositories/test_run_events_db.py::test_append_event_next_seq_retries_past_a_raced_seq`.
That test injected its stale snapshot through `read_events` and asserted at least two calls. The fix removes
`read_events` from this method, so the test went red at `:272`, while its behaviour assertions (`created is True`,
`seq == 2`) still held. Its injection point was moved to `_max_event_seq`, the tail source this card's Expected
names, and no assertion changed. A no-re-probe mutant still fails the moved test. Details are in FIX-688,
"One test seam moved".
