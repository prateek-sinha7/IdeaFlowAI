CONFIRMED by direct read — both call sites and the shared function definition
were opened; this is a deterministic double-fetch on every run open (not a
race), distinct from ISS-785's SSE-replay mechanism. It explains ISS-785's own
observed `/family` count of 2-3 per attempt (QA-PS-038's evidence table),
which ISS-785's "Root cause" section does not itself derive — it only
attributes the `runs?limit=50` storm.

## Root cause — no shared fetch/cache; two components each own their own `getRunFamily` call

`getRunFamily(token, runId)` (`frontend/src/lib/api.ts:915-922`) is a plain,
uncached fetch of `GET /api/runs/{id}/family` — no in-flight guard, no
memoization, unlike the `inFlightRefresh` single-flight pattern already used
elsewhere in the same file (`api.ts:224-233`).

Two independent places call it for the exact same `runId` whenever a run is
opened from history:

1. `frontend/src/app/[...view]/page.tsx:3080`, inside
   `handleSelectWorkflowRun`'s chat-transcript seeding logic (KAN-154 Gap 1):
   ```
   page.tsx:3080   const family = await getRunFamily(currentToken, fullRun.id);
   ```
   used only to resolve `otherMembers` so their chat frames can be merged into
   the transcript.

2. `frontend/src/components/layout/DashboardLayout.tsx:706-711`, a `useEffect`
   keyed on `contentSourceRunId` (B3/POR §5 D5), used to build the version
   dropdown/`PreviewPanel`'s revision-family UI:
   ```
   DashboardLayout.tsx:706   useEffect(() => {
   DashboardLayout.tsx:707     if (!contentSourceRunId) { setRunFamily(null); return; }
   DashboardLayout.tsx:708     getRunFamily(getToken() || "", contentSourceRunId)
   DashboardLayout.tsx:709       .then(setRunFamily)
   ```
   `handleSelectWorkflowRun` calls `setContentSourceRunId(run.id)` early in its
   body (synchronously, before either `getRunFamily` call), so this effect
   always fires for the same run id source 1 already fetches.

Neither site is aware of the other. This is the same systemic shape already
carded for `getWorkflows()` across QA-PS-035/036/037/039
([ISS-781](20260922-1630-ISS-781.md), [ISS-783](20260922-1615-ISS-783.md)):
independent components/effects each hold their own call to a shared-data
endpoint with no shared provider or cache — here the endpoint is
`getRunFamily` instead of `getWorkflows`, and the duplication is
deterministic (both call sites always fire on every history-reopen) rather
than StrictMode/mount-timing-dependent.

## Expected vs actual

Expected: opening a run's detail page fetches `GET /api/runs/{id}/family`
once, and both the chat-transcript seed and the version-dropdown UI read that
same result.

Actual: `GET /api/runs/{id}/family` fires twice per open — confirmed by
reading both call sites, matching the 2-3x `/family` count ISS-785 measured
3/3 live.
