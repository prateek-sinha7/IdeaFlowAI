# FIX-180

**Phase / trigger:** Phase 31 (REQ-CHATUI-01), follow-up to FIX-178

## Description

After gate approval the chat panel showed two messages:
1. "Review approved — build continues" — correct, from FIX-178's resolved-gate mechanism
2. "Approved — build continues" with an "Answer in Steps ↗" link — stale duplicate

## Root Cause

FIX-167b (commit `2d5b9fcc`) added a narrator projection for `review_gate_approved` that
called `persist_milestone_card` and wrote a durable `run_events` row:

```python
# pre-FIX-178 chat_narrator.py
if etype in _GATE_RESOLVED_EVENTS:
    ...
    text = "Approved — build continues"
    return CARD_CLARIFY, text, f"gate:{anchor}"
```

FIX-178 removed this narrator emission and replaced the mechanism with a frontend
`resolved` flag on the gate `ChatMessage`. However:

- Existing DB rows written by the old narrator were **not deleted**
- `getRunEvents` returns **all** event types — stale `chat_reply` rows included
- `seenRef` dedup cannot help: the stale row's `event_id` was never seen by the live SSE
  path, so it is treated as new on every `appendRunChatFrames` or `seedRunChatTranscript`
- The `isTerminalRun` auto-resolve in `seedTranscript` only targets `card_kind="gate"`;
  the stale row has `card_kind="clarify"`, so it passes through unmodified

Both `appendRunChatFrames` (FIX-172 path after pipeline_complete) and
`seedRunChatTranscript` (history reopen) replay the stale row into `handleFrame`,
where `upsertNarratorMessage` appends a new `clarify`-kind `ChatMessage` with
`content="Approved — build continues"`. `ResultCard` renders it as a plain text card
with the clarify link label "Answer in Steps ↗" — the second bubble the user sees.

## Fix

One-line tombstone guard in `useRunChat.ts` `handleFrame` case `"chat_reply"`:

```ts
case "chat_reply": {
  // FIX-180: drop stale pre-FIX-178 narrator cards persisted in run_events
  const deprecatedApproveCard =
    data.card_kind === "clarify" &&
    typeof data.text === "string" &&
    data.text === "Approved \u2014 build continues";
  if (deprecatedApproveCard) break;
  setMessages((prev) => upsertNarratorMessage(prev, data));
  // ... rest of case unchanged
  break;
}
```

The guard fires on the deprecated text string only — it never fires for new runs (which
produce no such row). Redo (`"Redo requested"`) and update_specs (`"Updating the specs"`)
narrator cards have different text and are unaffected.

- **INV-12** (no dual implementation): ✅ single guard in handleFrame, no new hook/state
