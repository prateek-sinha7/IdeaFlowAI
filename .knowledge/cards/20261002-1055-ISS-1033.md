# ISS-1033

## Source

INFERRED sibling of [ISS-923](20261001-2223-ISS-923.md), derived while analyzing QA-KB-060 (analyze phase, 2026-10-02).
ISS-923's root cause is that nothing on the `/workflows/{id}/edit` path represents "the saved row the URL names has not
loaded". That missing state has two producers: a fetch that FAILED (ISS-923) and a fetch that has not SETTLED yet (this
card), which is the adjacent loading state of the same code. Line numbers are the working tree on 2026-10-02 (branch
`feat/user-stories-v2`, HEAD `024c03ef`, dirty).

## What is suspected

Three facts, each read on the current tree:

1. **The composer is offered before the row arrives.** `workflow-edit` maps to `"composer"` synchronously
   (`frontend/src/app/[...view]/page.tsx:163-165`), DashboardLayout seeds `mainView` from it on its first render
   (`frontend/src/components/layout/DashboardLayout.tsx:568-573`), and page.tsx has no loading gate for this route: its only
   `/edit` gate is the 403/404 flag (`page.tsx:4081-4083`), unlike `/workflows/{id}` (`:4097-4105`) and
   `/workflows/{id}/run` (`:4137-4146`), which `return null` while their seeds load. So a blank composer, with an editable
   name box and canvas and an enabled "Save workflow", is on screen from the first authenticated render until
   `userWorkflowsApi.get(id)` settles (`page.tsx:3782-3834`).
2. **"Not settled" has no upper bound.** `http = axios.create({ baseURL: ENV.API_URL })` sets no `timeout`
   (`frontend/src/store/api/http.ts:17-19`) and nothing retries (`:32-54`), so a request that hangs keeps the window open
   until the browser or a proxy gives up the socket.
3. **When the seed does land, the composer is REMOUNTED, not updated.** `setInitialSavedComposition` (`page.tsx:3799`) ->
   DashboardLayout copies it (`DashboardLayout.tsx:1553-1557`) -> the key flips from `"new"` to the row id (`:3213`; the
   comment at `:3197-3212` states the intent: "Keying on the saved row's id forces a clean remount once it arrives"). The
   new ComposerPage instance builds name, description and `pipelineAgents` from `useState` initializers that read the props
   once at mount (`frontend/src/components/workflow/composer/ComposerPage.tsx:241-242`, `:296-326`), and the old instance's
   unmount reports "clean" to the Back guard (`:377-378`, `return () => onUnsavedChange?.(false)`). Whatever was typed in the
   window is dropped with no prompt.

## Condition

Open `/workflows/<owned-id>/edit` (typed URL, refresh, My Workflows "Edit" or the read view's Edit link) at a moment
`GET /api/user-workflows/<id>` takes long (hundreds of ms to never). Type a name and/or add an agent before the response
arrives, and optionally click "Save workflow".

## Expected vs actual

**Expected:** no savable composer is offered until the row has loaded (or the loading state is visible), and nothing the
user typed is silently replaced when the row arrives.

**Actual (predicted):**

- (a) A Save click in the window takes the create branch (`userWorkflowId` is undefined, `ComposerPage.tsx:919`,
  `frontend/src/lib/api.ts:2648-2654`) and POSTs a NEW row: 201 when the name differs from the saved one and at least one
  agent was hand-added, 422 on zero agents (`backend/app/api/user_workflows.py:214`), 409 on the saved row's own name
  (`:849-853`). Same server rules as ISS-923.
- (b) When the seed lands the composer remounts onto the ORIGINAL saved row: the typed name and agents are gone, and the new
  row from (a), if any, is not the one on screen. The user sees their workflow "unchanged" while My Workflows holds a stray
  copy; `setUserWorkflowId(resp.id)` (`ComposerPage.tsx:936`) acts on an instance that is about to be discarded, or that is
  already unmounted when the POST resolves.

## Why the root cause implies this

Same absent state, other producer. It matters for the FIX, not just the count: the closing mechanism proposed on
[ISS-923](20261001-2223-ISS-923.md) (hold Save while "a saved row was expected and none has arrived") closes (a), because the
gate holds while the GET is in flight as well as after it fails. It does NOT close (b): the discard is caused by the key-flip
remount, not by Save, so any Save-only gate leaves typed work to be replaced. Closing (b) needs the composer to be inert, or
not rendered, until the seed lands, which is the `/workflows/{id}/run` pattern (`page.tsx:4137-4146`).
[ISS-410](20260828-2344-ISS-410.md)'s analysis called that "a design call" because a page.tsx `return null` unmounts
DashboardLayout, which [ADR-0014](20260824-1630-ADR-0014.md) documents as the double-mount hazard. So the decision belongs to
whoever fixes ISS-923: gate Save only (cheap; leaves (b), which needs a multi-second GET to bite), or also hold the render
(closes (b), larger).

**Marked INFERRED**: not reproduced. Mechanism (3) is confirmed by reading the lines cited and the comment that states the
intent; the user-visible scenario was not run. What would confirm it: Playwright with
`page.route("**/api/user-workflows/<id>", r => setTimeout(() => r.continue(), 5000))`, open `/workflows/<id>/edit`, type into
`input[name="workflow-name"]` during the delay, then read the input once the seed lands (expect the saved name, not the typed
one). With a Save click in the window, `GET /api/user-workflows` shows an extra row; that needs enterprise tier (the POST is
gated by `can_run_pipeline`, `user_workflows.py:693-707`) and persists data, so use a throwaway name and delete it. What would
refute it: a loading state or an inert composer between mount and seed, which this read did not find (`page.tsx:4081-4083` is
the only `/edit` gate; `DashboardLayout.tsx:3187-3253` mounts ComposerPage unconditionally on `mainView === "composer"`).

## Partly closed by FIX-748 (QA-KB-060, fix phase, 2026-10-07)

(a) is closed. [FIX-748](20261007-2046-FIX-748.md) holds Save workflow while `/workflows/{id}/edit` names a row and
ComposerPage has no row id (`ComposerPage.tsx:1263-1265`). An in-flight GET and a failed GET give ComposerPage
identical props, so the same gate covers the loading window. **(b) stays open.** FIX-748 does not change the key-flip
remount that drops typed name and agents when the seed lands (`DashboardLayout.tsx:3226`). Closing (b) needs a
render-side hold for `/edit`. [ISS-923](20261001-2223-ISS-923.md) ("Not a substitute") records that as a design call
(a page.tsx `return null` unmounts DashboardLayout, the ADR-0014 double-mount hazard), so it was not done here. Status
stays `open`, still INFERRED and unreproduced.
