# ADR-0014

## Decision

Host-capacity monitoring is advisory and fail-open. A single lifespan poller collects CloudWatch
Agent CPU/memory readings and publishes a process-local immutable snapshot plus admission
decision. Request handlers only read that decision; no client request or admin matrix query calls
AWS.

Only when the feature is enabled and the decision is known and engaged does the system reject a
non-admin attempt to mint or dispatch new expensive work. A blind/stale/missing reading allows
work, and administrators remain exempt. Cancellation, gate and answer resolution, steering, and
SSE reconnect are never capacity-gated.

## Context

The product needs to avoid starting work during sustained host saturation without turning a
metrics outage into a total availability outage. The pure policy uses consecutive breaches,
hysteresis, and a minimum block duration to avoid flapping; the AWS adapter is isolated from the
policy and request path.

## Consequences

- New launch, resume, revision, Concierge, and handoff-start call sites must use the shared
  admission decision rather than introducing one-off CPU checks.
- The structured `host_capacity_exhausted` response and `Retry-After` are the common client
  contract; user interfaces should surface a recoverable busy state instead of endpoint-specific
  errors.
- The deployed default scope is the serving instance. A multi-instance/fleet policy requires an
  explicit coordination decision rather than assuming process-local state is fleet truth.
