## What was wrong — ISS-251

[FIX-327](20260828-1845-FIX-327.md) extracted the "which file is the deliverable"
rule into `resolveRunDeliverable` in `frontend/src/lib/api.ts` and routed the Files
tab and History surfaces through it. `PreviewPanel.tsx`'s header-Download
`useEffect` (the origin of the rule) was left on its own 60-line inline copy:
declaring name, calling `getWorkflow` if undeclared, calling `getRunSandbox`,
building the `stem`/`ext`/`candidates` array by hand.

Two implementations of one rule is how [ISS-214](20260828-1633-ISS-214.md) and
[ISS-215](20260828-1633-ISS-215.md) happened: a future change to the sibling
preference applied in `api.ts` and not here means the header Download and the Files
tab hand the user different files for the same run.

## What was wrong — ISS-599

`handleHeaderShare` in `PreviewPanel.tsx` fired
`void navigator.clipboard?.writeText(link)` — optional chaining with no `catch`.
A clipboard-permission denial or missing `navigator.clipboard` was silently
swallowed; the user got no feedback. This is one of the four sites
[ISS-599](20260829-0340-ISS-599.md) named that [FIX-395](20260829-0338-FIX-395.md)
missed (it grepped `navigator.clipboard.writeText`; the optional-chain pattern
`?.writeText` was not in the grep).

## Root cause (ISS-251)

`PreviewPanel.tsx:~1073-1125` (pre-change) — inline `try` block with the
`getWorkflow` + `getRunSandbox` + candidates logic that `resolveRunDeliverable`
already encapsulates verbatim. `resolveRunDeliverable` was not imported.

## Root cause (ISS-599)

`PreviewPanel.tsx:~1016` (pre-change) — `handleHeaderShare`:

```tsx
void navigator.clipboard?.writeText(link);
```

Fire-and-forget with optional chaining and no error handler. `useClipboardCopy`
existed (`FIX-395`) and was not imported.

## What changed and why there

**`frontend/src/components/preview/PreviewPanel.tsx`** — two targeted edits:

1. **Import line** — `resolveRunDeliverable` added to the `@/lib/api` import;
   `useClipboardCopy` imported from `@/hooks/useClipboardCopy`.

2. **ISS-251** — the `try` block inside the `useEffect` that gates the header
   Download button collapses from ~50 lines to ~10:
   - `declared = pipelineState?.deliverableFilename ?? null`
   - If `!declared` → ISS-313 bundle path (call `getRunSandbox`, check `.deliverable`
     flag) — unchanged, because `resolveRunDeliverable` returns `null` for no-name
     and leaves callers to decide; the bundle logic is caller-specific.
   - If `declared` → `resolveRunDeliverable(token, activeRunId, declared)` — single
     call that internally handles `getWorkflow` fallback + `getRunSandbox` + the
     `stem`/`ext`/`candidates` preference — the duplicate is gone.

3. **ISS-599** — `handleHeaderShare`:
   - `useClipboardCopy()` called at component level; `copy` destructured as
     `copyToClipboard`.
   - `void navigator.clipboard?.writeText(link)` replaced with
     `void copyToClipboard(link)`.
   - `copyToClipboard` added to `useCallback` deps array.

**`frontend/src/components/preview/PreviewPanel.test.tsx`** — mock updated:
The `vi.mock("@/lib/api", ...)` block gained a `resolveRunDeliverable` stub that
routes through the already-mocked `mockGetRunSandbox`, implementing the same
extension-keyed sibling logic inline in the test. This keeps all five existing
download assertions working unchanged — their `mockGetRunSandbox` stubs already
encode the expected sandbox states.
