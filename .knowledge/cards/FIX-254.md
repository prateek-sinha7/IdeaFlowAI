## Description

One "Update the Specs" click opened the analyze gate THREE times and nothing on the wire told the firings apart. gate_key is f"{run_id}:{agent_id}" — a gate SLOT, not a FIRING — so the analyze re-run INSIDE the revision sub-pipeline and the gate re-opened after that pass returned arrived with the same key AND byte-identical output (live run 5ecb990f seq 24652/24655: 11,974 chars, sha1 0136795fc392, 5 ms apart, zero events between) while carrying OPPOSITE affordances (update_specs_eligible False vs True). The user could not tell which gate they were on (84 s of hesitation on the duplicate, live), and the ambiguity produced a wrong major issue (ISS-062, closed as a misdiagnosis). Second, untested harm found by the investigation: InlineGateActions reset its one-action latch on [output, gateKey] and NEITHER changes between the two firings, so the second gate rendered with every action disabled.

## Root cause

A modelling gap, not a mechanism: the sub-pipeline was DESIGNED headless — its own comment says the review gate "is not expected during a revision cycle" (engine.py:5310-5313) — and the "re-open the gate afterwards" step (:5440 → :3463-3482) exists precisely to give the user the review the pass would not. But the pass re-runs each agent through the full _run_agent path for behaviour reuse (INV-12), so every one of them DOES gate. The re-open therefore re-presents a review that already happened, and the event vocabulary had no field that could distinguish a gate FIRING from a gate SLOT.
