# ISS-1073

Register bug QA-KB-096.

## Reproduction (3/3 settled, cold navigation via about:blank each time, admin@velocity.ai)
1. Run `78e185fb-c032-4154-8552-774781b6e5df` is completed, `deliverable_filename` = `Backlog.pdf`.
2. Open `/runs/78e185fb-c032-4154-8552-774781b6e5df` and wait for it to settle.
3. `GET /api/runs/78e185fb.../sandbox/file?path=Backlog.pdf&ref=v1` returns 404 `{"detail":"File not found"}` (11.1s, 11.4s, 10.9s after navigation in attempts 1-3). The same path without `ref` returns 200 (`%PDF-1.4`).
4. Preview pane shows "Backlog.pdf could not be loaded. It can be downloaded from the Files tab." (visible breakage, not only a console error).

## Conditions
Trigger: wait for the page to settle (this run loads slowly, 5.5M tokens). Captures that stop at ~6-12s often see no request, and the skeleton is still showing. Direct deep link, admin tier, default theme. Also fires on /steps and /files deep links per the reporter.

## Expected vs actual
Expected: deliverable resolves for the pinned version or the UI falls back to the unpinned file. Actual: 404 and Preview error state. Likely cause (unverified): PDF backfilled after the v1 ref was cut.

## Related
Sibling of [ISS-1072](20261007-2125-ISS-1072.md) (400 on /sandbox?ref=v1) and [ISS-975](20261002-0346-ISS-975.md).

## Analysis (QA-KB-096, 2026-10-07)

**Evidence status.** Root cause CONFIRMED four ways: a source read at HEAD `2005a0a6b`; read-only git on the family's sandbox
(`runs/2d626ad9-.../78e185fb-...`, no write, no checkout); read-only GETs against the running backend (`:8000`, admin account) for all seven tags; and an
offline render of the real `PreviewPanel`, `RunHeader`, `SandboxPdfPreview` and `api.ts` over a faked network that serves what the API returned (15 scratch
tests, all passing). No browser was driven. Two points are INFERRED and marked. Everything is in `evidence/qa-kb-096/10` to `16`.

### The chain (CONFIRMED)

1. **The row declares the PDF.** Every completed member of family `78e185fb` has `deliverable_filename = Backlog.pdf` and `deliverable_mimetype = application/pdf`
   (`11`).
2. **The page hands the declared name straight through.** On a reopen `page.tsx:3317-3323` sets
   `genericDeliverable = { mimetype, filename: fullRun.deliverableFilename, content: fullRun.output }`. The live path does the same from the `pipeline_complete`
   event (`page.tsx:1741-1746`).
3. **The page decides the run is an "older member" and pins its DB tag.** `PreviewPanel.tsx:889-891`:
   `const displayRef = sandboxSelectedRef ?? (activeMember && activeMember.id !== latestId ? activeMember.git_tag ?? null : undefined);`. Run `78e185fb` is v1 of
   8 and the newest is v8, so `displayRef = "v1"`. No pin is involved: `/runs/78e185fb-...` has no `/versions/{n}` segment.
4. **The generic preview forwards both.** `renderDeliverable()` (`:1735`) mounts `GenericDeliverablePreview` with `runId={activeRunId}` and
   `selectedRef={displayRef}`. For `application/pdf` (`:227-239`) it renders
   `<SandboxPdfPreview runId path={deliverable.filename} selectedRef fallback={... could not be loaded. It can be downloaded from the Files tab.}>`.
5. **The component asks the tag for the declared path.** `SandboxPdfPreview.tsx:27`:
   `getRunSandboxFileBlob(getToken() || "", runId, path, selectedRef)`, which `api.ts:1655-1658` turns into
   `GET /api/runs/78e185fb-.../sandbox/file?path=Backlog.pdf&ref=v1`.
6. **The endpoint reads that exact path at the tag.** `run_files.py:1165-1178`: `_validate_ref("v1")` passes (it is a tag), `read_file_at_ref(safe_ref, rel)`
   raises for a path that is not in the tree, and `except Exception` becomes `HTTPException(404, "File not found")`.
7. **The page swallows it.** `SandboxPdfPreview.tsx:34`, `.catch(() => { if (!cancelled) setState("missing"); })`, renders `fallback`. The 404 shows only
   in the network tab; the pane shows the fallback text.

### Why no tag holds `Backlog.pdf` at the root (CONFIRMED)

- The root file is kept out of git on purpose. `backlog_export.py:583-593` (`_keep_out_of_history`) adds `/Backlog.pdf` and `/Backlog.zip` to the sandbox
  `.gitignore`: "The run-history commit's binary scan refuses a PDF, and both files are rebuilt from the committed documents by every final assembly — so they
  stay out of git." The sandbox carries both lines (`git check-ignore -v Backlog.pdf` answers `.gitignore:12:/Backlog.pdf`; they arrived with step commit
  `6507f02`, 2026-09-30 16:34:38).
- The only tracked copy is `.chain/<name>`, force-added by the terminal snapshot: `engine.py:2416-2423` (`force_add=_built_payload.allowlist or None`), with the
  allowlist from `sandbox.py:272-320` (`payload_allowlist`).
- Per tag (`12`, `git ls-tree`): **v1 holds no PDF anywhere** (`.chain/backlog.md` and `backlog.md`). v2, v3, v4, v5, v7 and v8 hold `.chain/Backlog.pdf` only
  (23,010,668 / 23,553,059 / 23,558,186 / 23,558,181 / 23,593,271 / 23,626,760 B). HEAD, which is v8, tracks `.chain/Backlog.pdf`; the root `Backlog.pdf`
  (23,626,760 B, mtime 2026-10-01 18:26) is untracked and ignored.
- The API agrees (`11`): `?path=Backlog.pdf&ref=vN` is 404 for EVERY tag, v8 included; `?path=.chain/Backlog.pdf&ref=vN` is 200 for v2 to v8 and 404 for v1.

### Why v1 has no PDF at all (facts CONFIRMED, the row's history INFERRED)

- v1's own terminal payload says `output_filename: backlog.md` (`git show v1:.chain/summary.md`, written 2026-09-30T14:34:38Z) and holds `.chain/backlog.md`.
  v2's says `output_filename: Backlog.pdf`.
- The PDF existed on disk when v1 ended. v1's last step, `us-final`, logs "... Wrote Backlog.pdf and Backlog.zip." at 14:34:37Z (`.logs/78e185fb-....jsonl:2146`).
  The manifest only began declaring `name: Backlog.pdf` with `text_name: backlog.md` in `b88a0e74d` (2026-09-30 17:23, 49 minutes after v1's snapshot at 16:34:39;
  `workflow.yaml:77-80`). That commit also added `effective_deliverable` (`engine.py:1095-1112`) and "the chain payload carries both"
  ([FIX-664](20260930-1723-FIX-664.md)).
- So v1's tag was cut while the deliverable was still the text form. Tags are immutable (the tag-integrity guarantee, `engine.py:2536-2538`); nothing will ever
  add a PDF to v1.
- INFERRED: the v1 ROW's `Backlog.pdf` and `application/pdf` were written after v1 completed. The engine's own v1 record says `backlog.md`; the row value is
  `ectx.deliverable.name` at completion (`engine.py:7959`, `:7976`), its only writer is `run_commands.py:3979-3980`, and no repo code rewrites a row. The
  2026-10-02 probe already shows `declared=Backlog.pdf` for v1 (`evidence/qa-kb-053/family-probe.out.txt:53`). So the validator's "backfilled" is probably literal,
  for the row. What would settle it: the row's update history in Postgres. It does not change the fix: this run is proof that a run's declared name can differ from
  what its tag holds, and the code has to cope with that.

### The regression window (CONFIRMED)

`SandboxPdfPreview` shipped on 2026-09-30 17:23 (`8e846c782`) with no ref, reading the live tree, so an older member's page showed the NEWEST PDF
([ISS-973](20261002-0346-ISS-973.md): v2's request returned v8's 23,626,760 B). [FIX-717](20261002-1243-FIX-717.md) gave it `selectedRef={displayRef}` (it reached
git in `14a675db4`, 2026-10-06) and left `path` as the declared name. That turned "wrong bytes" into "no bytes", the same trade
[ISS-975](20261002-0346-ISS-975.md) records for the header Download after FIX-603. The header, the Files rows and the Download were fixed together because they all
go through `resolveRunDeliverable(..., ref)`; the PDF preview is the one reader that does not.

### What the page shows (CONFIRMED by offline render, `13` to `15`)

| page | the Preview asks for | result | header Download |
|---|---|---|---|
| v8, the newest (no ref) | `sandbox/file?path=Backlog.pdf` | 200, PDF frame | enabled |
| v2's own page (an older member) | `sandbox/file?path=Backlog.pdf&ref=v2` | 404, "Backlog.pdf could not be loaded. It can be downloaded from the Files tab." | **enabled** (the header resolve found `.chain/Backlog.pdf` at v2) |
| v1's own page (the validator's run) | `sandbox/file?path=Backlog.pdf&ref=v1` | 404, same fallback | disabled (nothing resolves at v1) |

So the visible breakage is wider than the report's v1. v2, v3, v4, v5 and v7 each HAVE a PDF at their tag, and the page tells the user it cannot be loaded beside a
Download that works. v1 has none. The validator's screenshot (`07-...png`) is the v1 row.

Why the request waits about 11 s is not part of the mechanism. `GET /family` answers in 0.11 s and `GET /sandbox/refs` in 0.11 s, while `GET /api/runs/{id}` is
6,585,601 bytes (`16`). `displayRef` needs only the family and the open member, so the request waits on the page reopening that record; the Preview shows
`RunDataSkeleton` until it lands (`PreviewPanel.tsx:1895-1906`). INFERRED; the validators' own note says captures before about 12 s see the skeleton and no request.

The three endpoints themselves are correct: listing, file and zip read exactly what a tag holds.

Which data is affected: only the `backlog` workflow declares a binary deliverable (`workflow.yaml:77-80`; `BINARY_MIMETYPES = {application/pdf}`,
`_mimetype.py:30`). The dev DB has 10 runs declaring `application/pdf`, in four families. Three have one member, the newest, which reads live. Family `78e185fb` has
eight; its six completed older members (v1, v2, v3, v4, v5, v7) take the ref path and fail; v6 was cancelled and has no tag, so it takes the `null` path (the
fallback, no request, correct).

### Fix, and where it belongs

One change, in `SandboxPdfPreview.tsx`: the component both callers use, and the one reader that skips the resolver.

- Resolve first: `resolveRunDeliverable(token, runId, path, selectedRef)` (`api.ts:1614-1647`). It lists the tree AT the ref, tries the declared name and then
  `.chain/<name>`, and answers null when neither is listed.
- Null: render `fallback` and send NO file request. That is v1: the 404 goes away and the honest end state stays.
- A hit: `getRunSandboxFileBlob(token, runId, hit.path, hit.ref ?? selectedRef)`. v2 then reads `.chain/Backlog.pdf` at v2.
- Keep two things as they are. `selectedRef === null` (an older member with no tag) renders the fallback and sends nothing ([FIX-717](20261002-1243-FIX-717.md)).
  `undefined` lists the live tree (the newest member), where a TTL-swept workspace answers `expired: true, files: []`, which resolves to null and the fallback, as the
  404 does today.
- The listing is the request the header already makes (`getRunSandbox(token, runId, ref)`, `api.ts:1630`), and `singleFlightGet` shares an open one
  (`api.ts:686-698`), so it costs nothing extra while they overlap.
- Proof the location is enough: a scratch prototype of exactly this change, rendered over the real family (`15`, probes F1 to F4). v2 at v2 sends the listing and
  then `path=.chain%2FBacklog.pdf&ref=v2` and shows the frame; v1 at v1 sends the listing and NO file request; the newest sends the live `Backlog.pdf` as today; a
  null ref sends nothing. The prototype lives in the scratchpad and in `13`, not in the application.
- Both callers then route through it: `PreviewPanel` and `WorkflowHistory`. History still passes no ref, so it still shows the newest PDF for an older member
  ([ISS-1049](20261002-1242-ISS-1049.md)); that is a separate, smaller change.
- No backend change.

### Why not the other candidates

- **"Fall back to the unpinned file"** (the report's second expectation). The ref-less read of `Backlog.pdf` is v8's 23,626,760 B, so v1 would show the newest PDF
  under its own label. [FIX-717](20261002-1243-FIX-717.md)'s locked constraint forbids it: "consumers keep their fallback rather than read another member's file".
- **Alias `.chain/` inside `/sandbox/file`.** It changes an exact-path contract that the Workspace tab, the zip and the archive routes rely on, and `?ref=v1` would
  still 404 because v1 has no PDF. `_validate_ref` is the Requirement-16 gate and stays fail-closed.
- **Un-ignore the root PDF, or add one to v1.** `backlog_export.py:583-593` keeps a 23 MB binary out of history on purpose (the commit binary scan refuses it),
  and tags are immutable.
- **Drop `?ref` for older members.** That reads the live tree, the newest member's files: the state FIX-717 removed.
- **Pass the header's `deliverableFile` down instead.** It is gated on `headerRunState` and the pin (`PreviewPanel.tsx:1457`), null means both "not yet" and
  "absent", and History has no such state.

### What a naive fix would get wrong

- Resolving without the ref. `resolveRunDeliverable` lists the LIVE tree when `ref` is undefined (`api.ts:1630`), finds the root `Backlog.pdf`, and the read at the
  tag 404s again. That is [ISS-975](20261002-0346-ISS-975.md)'s mechanism.
- Treating a null resolve as "retry without a ref".
- Existing frontend tests mock `@/lib/api` with only `getToken` and `getRunSandboxFileBlob` (`SandboxPdfPreview.test.tsx`, `SandboxPdfPreview.ref.test.tsx`).
  Routing through the resolver means those mocks gain `resolveRunDeliverable`. `SandboxPdfPreview.ref.test.tsx` asserts `calls[0][3] === "v2"`, which still holds when
  the resolver returns `{ path, ref: "v2" }`. That is a test-seam change, not the app bent to the test: the read at the member's ref is unchanged, only the path
  argument becomes the resolved one. `PreviewPanel.pdfDeliverable.test.tsx` stubs `SandboxPdfPreview` and is unaffected.
- Fixing the un-pinned path and stopping. The pinned branch reads the PDF as text ([ISS-1095](20261007-2347-ISS-1095.md)) and a pinned v1 never leaves "Loading"
  ([ISS-677](20260917-1449-ISS-677.md)).
