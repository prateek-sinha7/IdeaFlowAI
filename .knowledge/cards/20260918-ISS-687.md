## The symptom

Launching `prototype_v2` from the wizard returned a 400 with
`Invalid agent_ids for 'prototype_v2': ['custom-agent:fi-planner', ...]`.

## The root cause

`launch_run` (`backend/app/api/run_commands.py`, the `invalid_agent_ids` block)
allow-lists every supplied id:

    allowed_ids = allowed_custom_agent_ids(base_pipeline_type)
    rejected = [aid for aid in agent_ids if aid not in allowed_ids]

`allowed_custom_agent_ids` (`backend/agents/registry.py`) derives that set from
the registry, which is built from `AGENT.md` `pipeline_type` frontmatter. A file
workflow whose steps are `custom-agent` instances compiles to
`custom-agent:<instance_id>` ids that have **no AGENT.md on disk**. They can
therefore never be members of that set. Every launch that sends them is a
guaranteed rejection.

It stayed latent only because `prototype_v2` is the first such workflow wired to
a launch surface that sends a roster.

## Scope — 14 of 36

    grep -rln "agent: custom-agent" backend/agents/workflows/*/workflow.yaml

returns 14 of the 36 `workflow.yaml` files: `pdf_to_prototype`, `prototype_v2`,
the seven `ex_A*` fixtures (`ex_A1_loop`, `ex_A2_branch`, `ex_A3_b_spanish`,
`ex_A3_c_dutch`, `ex_A3_divert`, `ex_A4_human_divert`, `ex_A4_human_gate`), plus
`ex_publish_step`, `ex_test_loop_reachable_skip`, `ex_test_transitive_skip`,
`ex_validation_retry` and `sample_subagents_parallel`.

`prototype_v2/workflow.yaml` is 11 steps, every one `agent: custom-agent` with
an `instance_id` — `fi-planner`, `fi-readers`, `fi-synth`, `fi-gaps`,
`fi-close`, `pb-spec`, `pb-design`, `pb-build`, `pb-assemble`, `pb-validate`,
`pb-present`.

(The commit body of `73796dbd0` says "14 of the 35" — it counted before adding
`prototype_v2` itself. The current tree is 14 of 36.)

## Why the three existing cards do not close this

All three describe the **composer-override** instance of the same root cause,
and none of their remedies transfers to a file workflow:

- [FIX-306](20260825-2115-FIX-306.md) closed it by REMOVING the affordance — a
  blank custom-agent template nobody has to pick. A file workflow's steps are
  not an affordance anyone can withhold.
- [FIX-438](20260831-1954-FIX-438.md) only improved the rejection message at
  that site.
- [ADR-0016](20260824-1630-ADR-0016.md)'s inline-manifest escape hatch is
  unreachable from a request that is `agent_ids`-shaped.

Widening the allow-list was rejected again: `allowed_custom_agent_ids`' own
docstring carries the KAN-75 entitlement-bypass revert.

## What actually shipped, and what is still open

`73796dbd0` filters the ids out at ONE caller —
`frontend/src/components/workflow/LaunchWizard.tsx`:

    agentIds: pipelineAgents.map((a) => a.id).filter((id) => !id.startsWith(CUSTOM_AGENT_PREFIX)),

That is correct for the wizard (the compiled plan is the roster; `AgentsPopup`
edits per-step config, not membership) but it is a per-caller patch. The other
13 workflows and every other `agent_ids` sender still hit the same wall, and
nothing in the backend rejects or normalises the shape at source.
