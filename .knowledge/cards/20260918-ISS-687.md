## The symptom

Launching `prototype_v2` from the wizard returned a 400 with
`Invalid agent_ids for 'prototype_v2': ['custom-agent:fi-planner', ...]`.

## The root cause

`launch_run` (`backend/app/api/run_commands.py`, the `invalid_agent_ids` block)
allow-lists every supplied id:

    allowed_ids = allowed_custom_agent_ids(base_pipeline_type)
    rejected = [aid for aid in agent_ids if aid not in allowed_ids]

`allowed_custom_agent_ids` (`backend/agents/registry.py`) derives that set from
the registry, which is built from `AGENT.md` `pipeline_type` frontmatter. A file
workflow whose steps are `custom-agent` instances compiles to
`custom-agent:<instance_id>` ids that have **no AGENT.md on disk**. They can
therefore never be members of that set. Every launch that sends them is a
guaranteed rejection.

It stayed latent only because `prototype_v2` is the first such workflow wired to
a launch surface that sends a roster.

## Scope — 14 of 36

    grep -rln "agent: custom-agent" backend/agents/workflows/*/workflow.yaml

returns 14 of the 36 `workflow.yaml` files: `pdf_to_prototype`, `prototype_v2`,
the seven `ex_A*` fixtures (`ex_A1_loop`, `ex_A2_branch`, `ex_A3_b_spanish`,
`ex_A3_c_dutch`, `ex_A3_divert`, `ex_A4_human_divert`, `ex_A4_human_gate`), plus
`ex_publish_step`, `ex_test_loop_reachable_skip`, `ex_test_transitive_skip`,
`ex_validation_retry` and `sample_subagents_parallel`.

`prototype_v2/workflow.yaml` is 11 steps, every one `agent: custom-agent` with
an `instance_id` — `fi-planner`, `fi-readers`, `fi-synth`, `fi-gaps`,
`fi-close`, `pb-spec`, `pb-design`, `pb-build`, `pb-assemble`, `pb-validate`,
`pb-present`.

(The commit body of `73796dbd0` says "14 of the 35" — it counted before adding
`prototype_v2` itself. The current tree is 14 of 36.)

## Why the three existing cards do not close this

All three describe the **composer-override** instance of the same root cause,
and none of their remedies transfers to a file workflow:

- [FIX-306](20260825-2115-FIX-306.md) closed it by REMOVING the affordance — a
  blank custom-agent template nobody has to pick. A file workflow's steps are
  not an affordance anyone can withhold.
- [FIX-438](20260831-1954-FIX-438.md) only improved the rejection message at
  that site.
- [ADR-0016](20260824-1630-ADR-0016.md)'s inline-manifest escape hatch is
  unreachable from a request that is `agent_ids`-shaped.

Widening the allow-list was rejected again: `allowed_custom_agent_ids`' own
docstring carries the KAN-75 entitlement-bypass revert.

## What actually shipped, and what is still open

`73796dbd0` filters the ids out at ONE caller —
`frontend/src/components/workflow/LaunchWizard.tsx`:

    agentIds: pipelineAgents.map((a) => a.id).filter((id) => !id.startsWith(CUSTOM_AGENT_PREFIX)),

That is correct for the wizard (the compiled plan is the roster; `AgentsPopup`
edits per-step config, not membership) but it is a per-caller patch. The other
13 workflows and every other `agent_ids` sender still hit the same wall, and
nothing in the backend rejects or normalises the shape at source.

## Analysis — QA-KB-054 (2026-10-02, branch feat/user-stories-v2 @ 024c03ef8)

Evidence: `evidence/qa-kb-054/` (four probe scripts plus `output.txt`; read-only, in-process, no server, no
real run). Line numbers are the working tree on 2026-10-02; `run_commands.py` and the frontend files carry other
lanes' uncommitted edits, so they can sit a few lines off HEAD.

**CONFIRMED, reproduced through the real router.** `POST /api/runs` with `pipeline_type="prototype_v2"` (and
with `"backlog"`) and `agent_ids` set to a few of the workflow's own compiled ids returns `400 invalid_agent_ids`
and mints 0 runs. The same two requests with `agent_ids` omitted return `200 {"run_id": ...}` and mint 1 run.
The field is the only difference (`test_probe_launch.py`).

### The counts are tree-dependent

"14 of 36" is the count on the checkout this card was written against. On this branch it is **17 of 39**
`workflow.yaml` files: it adds `backlog`, `backlog_revision`, `prototype_v2_revision`,
`prototype_v2_feature_revision` and has no `pdf_to_prototype`. 15 are all-custom-agent; the two `prototype_v2_*`
revisions are mixed (one registered step, `prototype-revision-analyzer`). For all 17, `PIPELINE_AGENTS[wf] == []`
and `allowed_custom_agent_ids(wf) == set()` (executed, `probe_registry.py`).

### Mechanism (every line read)

1. `run_commands.py:3284`: `launch_source` defaults to `FILE_PIPELINE` (no `user_workflow_id`, no inline manifest).
2. `run_commands.py:3522-3525`: any non-manifest launch with non-empty `agent_ids` computes
   `allowed_ids = allowed_custom_agent_ids(base_pipeline_type)` and rejects every id outside it (`:3526-3549`).
3. `registry.py:438-447`: `base_agents = PIPELINE_AGENTS.get(pipeline_type); if base_agents: return ...; return set()`.
   A custom-agent file workflow has no `AGENT.md`, so its registry roster is `[]` and the answer is the security
   fallback `set()`. Every non-empty `agent_ids` is therefore rejected, including a legitimately registered id.
4. The spec-017 "own manifest steps" union (`registry.py:314-353`, `_own_manifest_step_agents`) cannot rescue it:
   it sits behind the same `if base_agents:` guard (`:439-444`), it returns the bare template name
   (`['custom-agent']`, executed) rather than `custom-agent:<instance_id>`, and `*_revision` pipelines return early
   with `set(PIPELINE_AGENTS.get(...))` (`:415-416`).
5. The roster the launch needs already exists: the `else` branch (`run_commands.py:3593-3622`) compiles the plan
   (`compile_for_run`) and builds specs with `get_execution_engine()._specs_from_plan(...)`. That is the branch the
   control request takes. Nothing after the allow-list block reads `body.agent_ids` again (the local `agent_ids`
   is used only inside the block, `:3520-3550`; everything downstream consumes `agents`).

### Blast radius

Backend: exactly two production call sites of `allowed_custom_agent_ids`.

- `launch_run`, `run_commands.py:3524` (reached by FILE_PIPELINE and USER_WORKFLOW_FLAT; `_launch_run_core` callers
  such as the cross-workflow trigger carry no `agent_ids`).
- `create_user_workflow`, `user_workflows.py:720-727`: the save-side twin ("save == launch") -> [ISS-976](20261002-0405-ISS-976.md).

Frontend: one transport, three private workarounds, several unprotected senders.

- Transport: `useWorkflow.startPipeline`, `useWorkflow.ts:91-93`, forwards `agentIds` verbatim as `payload.agent_ids`
  to `POST /api/runs` (`:128`). Nothing normalises it.
- Per-caller workarounds, each re-discovering this card: `LaunchWizard.tsx:1041` (prefix filter),
  `IdeaInputPage.tsx:1670-1681` (send `[]` when the roster equals the manifest roster),
  `ComposerPage.tsx:1178-1209` (send `[]` for an unmodified built-in).
- Unprotected: `IdeaInputPage.tsx:1678` sends the full `custom-agent:*` roster whenever it differs from the manifest
  roster (user edited it, an override is active, or `manifestAgents` has not loaded); the pass-throughs
  `page.tsx:1001/1043/2530/2613` (`agentIds: draft.agentIds`) and `DashboardLayout.tsx:1455/1520` are safe only
  because the wizard that writes the draft filters; any external API client.
- **Correction to the QA-KB-054 write-up:** `page.tsx:536` is not a launch sender. It seeds the
  `/workflows/{type}/canvas` composer (`setInitialSavedComposition({ agentIds: ... })`). The composer launches via
  `user_workflow_id` / an inline `manifest` (Case 3, no allow-list) or `[]` for an unmodified built-in, so it is
  unaffected. The statement "400s for every sender except LaunchWizard" is too broad; the defect is the backend
  contract that forces every sender to carry its own workaround.

### Where the fix belongs

Backend, at the single ingress every `agent_ids`-shaped launch routes through: the allow-list block in
`launch_run` (`run_commands.py:3516-3550`). It is a normalisation in front of the allow-list, not a widening of it.

- Compute the base pipeline's own plan, `compile_for_run(base_pipeline_type)` (`engine.py:3593-3594`, `@lru_cache`;
  imported elsewhere in this function at `:3612` and `:3720`, so it needs importing above the block), and
  `plan_custom = {s.agent_id for s in plan.steps if s.agent_id.startswith(CUSTOM_AGENT_PREFIX)}`.
- If `plan_custom` is non-empty and `set(agent_ids) == plan_custom`, the request carries nothing the plan does not
  already say: set the local `agent_ids = None` so the existing `else` branch (`:3593-3622`) supplies the roster.
- The discriminator is **plan identity**. It is data-driven (no workflow name, SC-001 / INV-1) and a no-op for every
  registered-agent pipeline, whose plan has no `custom-agent:` steps, so those launches stay byte-identical.
- Leave `allowed_custom_agent_ids` alone (KAN-75, and its many pinned tests). Keep the rejection pre-mint.
- Make the override sentence at `:3534-3544` fire only for `custom-agent:` ids that are NOT in `plan_custom`
  ([ISS-978](20261002-0405-ISS-978.md)).
- Apply the same predicate at `create_user_workflow` through one shared helper ([ISS-976](20261002-0405-ISS-976.md)).
- Optional once green: `LaunchWizard.tsx:1041`, `IdeaInputPage.tsx:1670-1681` and `ComposerPage.tsx:1178-1209`
  become redundant.

Decision with a recommended default, left to the fixer: a roster that is a strict subset or superset of the plan
(an edited roster). Recommendation: reject it, do not silently drop it. Dropping runs the FULL plan, so steps the
user removed would still run and spend Bedrock tokens. `set(agent_ids) == plan_custom` implements the
recommendation; the case every real sender produces (the full roster) satisfies the bug's Expected either way.

### What a naive fix breaks

The triage sketch in BUGS.md (strip `custom-agent:`-prefixed ids when `launch_source is FILE_PIPELINE`, set `None`
when empty) puts the discriminator on the wrong axis.

1. ISS-182 / FIX-438's regression test is a **FILE_PIPELINE** launch, not USER_WORKFLOW_FLAT: `pipeline_type="user_stories"`,
   `agent_ids=["custom-agent:legacy-stale-1", "domain-analyst"]`, no `user_workflow_id`
   (`test_iss182_stale_override_agent_ids.py:36-54`). A FILE_PIPELINE-wide prefix strip turns that 400 into a launch
   of `['domain-analyst']`. The behaviour holds today (`test_probe_iss182_guard_behaviour.py`:
   `400 invalid_agent_ids | override sentence present: True | runs: 0`) but its test no longer collects
   ([ISS-977](20261002-0405-ISS-977.md)), so nothing would go red.
2. Silent discard of roster edits (above): a blanket strip runs the unedited plan.
3. Widening `allowed_custom_agent_ids`, or letting the plan's ids fall into the `if agent_ids:` branch, would run
   `presort_specs` (`run_commands.py:3558-3564`), which the CWF-001 D1 scope fence (`:3551-3557`) forbids for
   file-backed manifests, and would build specs from `load_agent_spec('custom-agent:<id>')` (it succeeds, executed)
   instead of `_specs_from_plan`. It would also break the pinned allow-list tests
   (`test_registry_helpers.py`, `test_run_pipeline_validation.py`, `test_ppt_v2_manifest.py::test_the_allow_list_still_fails_closed`).

## Resolution (QA-KB-054, 5-fixer, 2026-10-07)

Resolved by [FIX-719](20261007-1754-FIX-719.md). The production change matches "Where the fix belongs" above:
`_own_plan_roster` (`backend/app/api/run_engine.py:807-825`) is called at `run_commands.py:3465-3467` and
`user_workflows.py:725-727`, and `allowed_custom_agent_ids` is untouched. It was already in `HEAD` (`14a675db4`)
when the fix phase ran. The edited-roster decision was taken as recommended: an edited roster is rejected, not run
as the full plan.

The test file's red cases had to be corrected, test-only. They sent a SUBSET of the plan (2 of 11 `prototype_v2`
ids, 1 of 20 `backlog` ids) and asserted success. The "For the test writer" section above asks for the full plan,
and its "Must stay green" list keeps an edited roster rejected. After the correction, on the in-tree code:
4 x XPASS(strict) plus a new edited-roster guard that passes. With `_own_plan_roster` switched off: 4 xfailed.
FIX-719 holds the exact runs.
