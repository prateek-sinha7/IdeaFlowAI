# ISS-836

## Description

Re-analysis of **QA-PS-044** (`LEDGER.md` / `BUGS.md#qa-ps-044`), dispatched
back to analyze after a TEST-WRITER pass (2026-09-22) could not reproduce
[ISS-794](20260922-1827-ISS-794.md)'s measured counts (`auth/me` x3,
`/api/workflows` x2, `/api/runs?limit=50` x2 — all now x1 across 3
independent measurements). This card verifies WHY that happened (three
unrelated sibling fixes closed it, not a mistaken original measurement) and
identifies what QA-PS-044's report still leaves unexplained: `GET /api/ppt`
x2 and `GET /api/templates` x2, neither of which ISS-794 ever measured.

## Part 1 — ISS-794's finding is closed, confirmed by direct read

All three mechanisms ISS-794 blamed are gone from the current tree:

1. **`getMe()` now cached.** `frontend/src/lib/api.ts:609-615`:
   ```tsx
   export async function getMe(token: string): Promise<User> {
     // ISS-801: shared-GET cached — `[...view]/page.tsx`, `AccountSettings`,
     // `admin/page.tsx` and `LaunchWizard` each fetch the profile for themselves...
     return cachedGet<User>("/api/auth/me", token);
   }
   ```
   `cachedGet()` (`api.ts:410-426`) is a 30s TTL cache keyed by `token+path`
   (`api.ts:386-407`), added for [ISS-801](20260922-1834-ISS-801.md). Any
   second `getMe()` call inside the TTL window — including page.tsx's own
   StrictMode-doubled call and `LaunchWizard.tsx`'s independent one — now
   shares the first call's promise instead of firing a new request.

2. **`getWorkflows()` (the `/api/runs` fetcher, despite its name) now
   single-flights.** `frontend/src/lib/api.ts:855-877`: a module-level
   `inFlightWorkflows` Map, added by [FIX-616](20260922-1923-FIX-616.md) for
   ISS-783/QA-PS-037, returns the SAME promise to a concurrent caller asking
   for the same `token+path`. `page.tsx`'s `[isAuthenticated]`-gated effect
   (currently at `page.tsx:1017-1039`) calls `getWorkflows(currentToken,
   { limit: 50 })` unconditionally on every route — StrictMode's mount
   double-invoke now collapses to one real fetch.

3. **The separate `/api/workflows` catalog pre-fetch is deleted, not
   deduped.** The same `page.tsx` effect used to also call
   `getWorkflowDefinitions()` directly. Reading the file now shows:
   ```tsx
   // ISS-782: the `getWorkflowDefinitions` pre-fetch that used to sit here is
   // gone. ... So this was a 22 KB GET /api/workflows fired on EVERY route
   // (this is the `[...view]` catch-all) whose result reached nothing.
   ```
   confirming [ISS-819](20260922-1940-ISS-819.md)'s identical finding for
   the `/create/user-stories` sibling. The one remaining `/api/workflows`
   source is the Redux `fetchWorkflows` thunk
   (`frontend/src/store/slices/globalSlice.ts:32`), dispatched once from
   `listenerMiddleware.ts`'s `signedIn` listener with a status guard.

This matches the TEST-WRITER's own 2026-09-22 note in `LEDGER.md` row
`QA-PS-044` (pytest network capture + live browser `browser_network_requests`,
3/3 measurements at `auth/me` x1 / `/api/workflows` x1 / `/api/runs?limit=50`
x1). [ISS-794](20260922-1827-ISS-794.md)'s `status` is set to `resolved` by
this card — its conclusion was correct when written; the code it described
has since changed.

## Part 2 — the still-open root cause

QA-PS-044's original report (`BUGS.md#qa-ps-044`) also recorded `GET
/api/ppt` x2 ("Wizard config fetched twice") and `GET /api/templates` x2.
[ISS-794](20260922-1827-ISS-794.md) never measured or explained either —
its 3-cycle capture only logged `auth/me`, `workflows`, `runs?limit=50`,
`runs?limit=6`, and the three `*/library` calls. Both remain unaddressed by
every fix that closed Part 1.

**Root cause:** `frontend/src/lib/api.ts:1809-1829`:

```tsx
export async function getWorkflowDetail(
  token: string,
  workflowId: string,
  opts?: { original?: boolean }
): Promise<WorkflowDetail> {
  const qs = opts?.original ? "?original=true" : "";
  return request<WorkflowDetail>(
    `/api/workflows/${encodeURIComponent(workflowId)}${qs}`,
    { method: "GET", headers: authHeaders(token) }
  );
}
```

A bare `request()` call — no `cachedGet()` wrapper, no in-flight Map, unlike
`getMe()`/`getWorkflows()` above. `/create/ppt` renders `LaunchWizard.tsx`,
whose own mount effect at `frontend/src/components/workflow/LaunchWizard.tsx:490-566`
calls this function at line 507:

```tsx
useEffect(() => {
  if (!authChecked) return;
  ...
  getWorkflowDetail(token, pipeline)          // :507 — pipeline="ppt" on /create/ppt,
    .then((detail) => {                       // i.e. the literal GET /api/workflows/ppt
      if (cancelled) return;
      ...
    });
  return () => { cancelled = true; };
}, [authChecked, mode, handleSelectionsChange]);
```

`cancelled` blocks a post-unmount STATE update, never the fetch. This is the
identical shape [ISS-819](20260922-1940-ISS-819.md) already proved doubles
`GET /api/workflows/user_stories` under React StrictMode for
`IdeaInputPage.tsx`'s sibling effect, and exactly the mechanism
[ISS-820](20260922-1941-ISS-820.md) already predicted for this exact file
and line — this card supplies the corroboration ISS-820 deferred to
"QA-PS-044's own analysis pass":

```
$ npx vitest --run src/lib/api.getWorkflowDetailDedup.test.ts
 Test Files  1 passed (1)
      Tests  1 expected fail (1)
```

`api.getWorkflowDetailDedup.test.ts` asserts two concurrent
`getWorkflowDetail()` calls for the same workflow id collapse to one fetch;
it is written `it.fails` (xfail-strict) and is STILL reporting "1 expected
fail" today — i.e., concurrent calls still produce 2 real fetches. This
proves the function-level gap is live right now, independent of which
caller triggers it.

**Confidence note:** the FUNCTION-level gap (`getWorkflowDetail()` has zero
dedup) is CONFIRMED by the direct read above plus the still-failing test.
Whether `LaunchWizard.tsx:507`'s specific mount-effect timing produces
exactly 2 real fetches on every `/create/ppt` cold load (as opposed to only
under specific entry paths) is NOT independently re-verified with a live
browser capture in this pass — this dispatch has no browser tool available.
That measurement is what would upgrade this from INFERRED reproduction to
CONFIRMED reproduction; see NOTE to the test-writer below.

non-double-invoked re-render triggered by that state flip. This is a
correction to this card's own Part 2/Confidence-note: the FUNCTION-level
gap (`getWorkflowDetail()` has no in-flight dedupe) is still confirmed
live and still red
(`api.getWorkflowDetailDedup.test.ts`, still "1 expected fail"), but
`LaunchWizard.tsx:507` specifically does NOT double-fire it on either cold
or SPA-nav entry to `/create/ppt` — some OTHER caller of `getWorkflowDetail`
(not this route) would be needed to observe the function-level gap
manifest as two real requests on the wire. The still-open `GET /api/ppt`
x2 in the original QA-PS-044 report is not explained by this file/line;
see ISS-837 for the template-family over-fetch this pass DID confirm.
