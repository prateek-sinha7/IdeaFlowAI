# ISS-1203

**Register source:** `QA-KB-112` (Medium, `/settings/security`), validated CONFIRMED 3/3 on 2026-10-09 (`evidence/qa-kb-112/01..03`: three cold starts, three different setup keys). It was escalated at validate as possibly intentional. **Owner decision 2026-10-09 (`BUGS.md`, section QA-KB-112): "option a, keep as is. /settings/security stays the TOTP enrollment page (b2a621f84). Test-only fix: update velocity.json (`/settings/security` no longer the tab-security route) and the 8 failing 09_settings e2e tests to the enrollment-page behaviour. No app change."** This card is the analysis the line re-entered with that decision. It explains why the tests and the browser map are wrong, and it keeps the fix inside that boundary.

**Confidence.** Root cause CONFIRMED: source read, an unauthenticated server-render probe of both dev frontends, and the 2026-10-09 e2e artifacts (read, not re-run). The three siblings are INFERRED; each says what was and was not observed.

## What happens (CONFIRMED)

1. A cold load of `/settings/security` shows a bare page: H1 "Two-factor authentication", "Admin access requires a second factor. Set up an authenticator app to continue.", an Account / Setup key / Setup link block, a code field and a disabled "Verify and enable". There is no header, no tab strip and no "Account Settings" heading (ARIA snapshot in `analysis-02`, screenshot `analysis-07`).
2. Every load shows a different key, because every mount calls `POST /api/auth/mfa/totp/associate`: `XNAGDTGH…`, `2QU32AL4…`, `AH2DMHYL…` (the validator's three cold starts), `PKG5DLFS…` and `BTN7KVTX…` (two cold loads inside the rerun).
3. The URL no longer reaches the Account Settings Security tab, and clicking that tab leaves the shell for this page too ([ISS-1204](20261012-0949-ISS-1204.md)).

## Root cause (CONFIRMED): one commit left two files owning one URL

**1. The static page wins the URL.** `b2a621f84` (Fix/cognito login (#8), 2026-09-17) added `frontend/src/app/settings/security/page.tsx`. A static App Router segment outranks the `[...view]` catch-all; `routes.ts:180` already relies on and documents the same rule for `/admin` ("static app/admin/page.tsx takes precedence over [...view] catch-all"). Observed rather than assumed: an unauthenticated `GET /settings/security` on :3000 and :3001 returns server HTML containing the enrolment heading and "Preparing your enrolment…"; `GET /settings/profile` does not (`analysis-03`).

**2. Everything that maps the URL to the tab was left standing.** The path has a history (`analysis-08`): `1b6ebe4f2` (2026-08-07) added it as the standalone Security page, `112244c9b` (same day) deleted it into `SecuritySection.tsx`, and `b2a621f84` re-created it as a different page. What still says "the URL is the tab":

- `routes.ts:170-174`: "The page is gone (dev's change, kept); the URL stays so the tab is addressable exactly like the other four" (written 2026-08-24, `7f269f37d`), and `routes.ts:492` `if (tab === 'security') return { screen: 'settings-security' }`.
- `[...view]/page.tsx:193` and `:312-313` (`settings-security` maps to `settings` and to `"security"`).
- `AccountSettings.tsx:61` `security: routes.settingsSecurity`, `:278-279` `setSection(next); router.replace(SECTION_ROUTE[next]())`, `:531-533` the only mount of `SecuritySection`.
- `SecuritySection.tsx:26-35`: "Lives as a TAB inside Account Settings rather than its own route: the standalone `/settings/security` page duplicated the chrome…".

The two designs contradict each other in source, and the later one, the page, wins at runtime.

**3. "A new secret on every visit" is the page working as written.** `page.tsx:35-54` `begin()` calls `associateTotp(token)` (`:43`), and `:56-61` runs it from a mount effect (a `setTimeout(0)` with a cleanup, so React's dev double-mount should not double-call; read, not measured). The page never reads MFA status (`getMfaStatus` is not imported, `:17`), so a blocked admin, an enrolled admin and a non-admin all get the same ceremony. `associateTotp` is `POST /api/auth/mfa/totp/associate` (`api.ts:918-923`); `auth.py:784-817` returns `cognito.associate_software_token(access_token)` (`cognito.py:626-633`): "The secret is returned ONCE and never stored server-side", one fresh Cognito `AssociateSoftwareToken` per call. The page tells the user so (`page.tsx:163-166`: "This key is shown once and is not stored. If you leave this page before finishing, start again."). A visit changes no account state: `cognito.py:587-594`, "a user who called AssociateSoftwareToken but never completed VerifySoftwareToken does NOT appear" among the confirmed factors.

**4. Nobody updated the consumers of the old contract.** `b2a621f84` is 788 files; none is under `tests/integration/` and `velocity.json` is not among them (`analysis-08`). The page's intended consumer works and is untouched by this bug: a blocked admin is sent there by `admin/page.tsx:190-196` (`router.replace('/settings/security?enroll=…')`) after the backend's `admin_mfa_required` 403 (`auth.py:479`, `admin.py:124`; `enroll_path` is the API path `/api/auth/mfa/totp/associate`, not this URL). The page's own docstring (`page.tsx:3-14`) states that purpose.

## Where the fix belongs (owner boundary: test-side only, no app change)

One fix, in the places where a single edit propagates:

1. **Spec first**, because `capture/_scenarios.py` links every test to a scenario id in both directions (baseline today: 511 scenarios, 511 implemented, 0 awaiting, 0 untagged). `09-settings.feature.md`: S-09-01 examples (drop the Security row), S-09-02 (keep the `tab-security` row and make its Then say it lands on the enrolment page), S-09-13..S-09-19 as the table proposes, the header (`:1-8`, "Five tabs behind `/settings/{tab}`, uniformly addressable") and the tab table (`:22`). Then the trackers.
2. **One locator module, one helper.** `settings_page.py` `TABS` is what S-09-01/02/19 iterate: keep it to the tabs that cold-load as Account Settings, give Security its own constant, and add the enrolment locators (`totp-secret`, `totp-otpauth-uri`, `name=totp-code`, the "Verify and enable" button, the H1). Add `open_enrolment(page)` beside `open_settings()` rather than loosening `open_settings`: its heading assertion is what catches a real tab regression. Drop the constants ISS-1018 lists as dead.
3. **The nodes.** The enrolment-page behaviour the owner asked for, as assertions: H1 present and no Account Settings chrome; `totp-secret` non-empty and equal to the `secret=` in `totp-otpauth-uri`; "Verify and enable" disabled until a code is typed; exactly one `POST /api/auth/mfa/totp/associate` per cold load; a second cold load shows a different secret (the behaviour the owner accepted); a wrong code (`000000`) shows the server's message and the page stays (`page.tsx:73-81`).
4. **`velocity.json`** (one file): `routes.settingsSecurity` keeps the URL but says what it is; `pages.settings.routes` drops `/settings/security`; `tabs` and `testids` keep Security and `tab-security` (the tab exists, and it leaves the shell); `selectors.settingsTab` gets the same caveat; add the enrolment page (heading, hooks, "a new secret per load", the safety rule below). Fix or flag the stale `note` separately; do not widen the fix.
5. **Optional drift guard**, the line's pattern for test-side fixes (QA-KB-122, `backend/tests/unit/test_e2e_tier_drift.py`, text parsing, no browser): while `frontend/src/app/settings/security/page.tsx` exists, no entry of `settings_page.TABS` may carry its route and `velocity.json` `pages.settings.routes` may not list it. Red today. A shape, not a decision; the 4-test-writer owns it.

**Do not:** edit `page.tsx`, `routes.ts`, `AccountSettings.tsx` or `SecuritySection.tsx` (owner: no app change; the stale comments belong to the decision in [ISS-1204](20261012-0949-ISS-1204.md)); move the enrolment page (`admin/page.tsx:190-196` and `security.test.tsx` depend on it); type another `/settings/security` literal anywhere (ADR-0018: path literals belong to `routes.ts`).

**Safety for every test and probe.** Never complete the ceremony with a valid code on `admin@velocity.ai` or any shared QA account. `associate` alone changes nothing; `verify` with the right code enrols a factor (`auth.py:820-867`) and changes every later sign-in of that account. A wrong code is safe (a 400, the page stays).
