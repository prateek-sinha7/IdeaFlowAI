# ISS-111

## Title

The spec_revision narrator card kind is unreachable end-to-end, and its branch OUTRANKS every other card kind. chat_narrator._classify evaluates attempt = _revision_index(data); if attempt > 0: at :151-159 — before the clarify/gate/pipeline/deliverable branches, and by its own comment "regardless of the carrying event". But _revision_index (:106-118) keys on spec_revision_attempt / revision_index, and nothing anywhere writes either key into an event payload: those two strings appear as quoted dict keys only at :112 and :114 — the reader itself. The engine holds spec_revision_attempt as a Python local (engine.py:3376, 3481, 3610, 4547, 7048) and passes revision_index= as a kwarg into _consume_update_specs / _run_spec_revision_sub_pipeline; the value reaches ectx.revision_attempt and is consumed at exactly three places — the :rev{N} checkpoint thread suffix and two in-flight booleans — and never enters an event data dict (agent_start's payload is fixed at {agent_id, name, role, icon, index, total}). So attempt is always 0, the branch never fires, and the card has never been emitted: measured over 232,023 durable run_events across 14 runs — including 52 rows mentioning update_specs, i.e. spec revisions demonstrably happened — persisted cards are gate 52 / clarify 43 / pipeline 17 / deliverable 12 / null 6 and spec_revision is ZERO. The danger is the precedence, not the dormancy. Because the branch runs first and ignores the carrying event type, ANY future change that adds revision_index or spec_revision_attempt to an event payload silently converts every card emitted during a revision pass into a spec_revision card — including the gate cards the user must approve. This was a near miss once already: IMPLEMENTATION-REGISTER.md:4214 records FIX-220 naming its keys revision_cycle / revision_in_flight specifically to avoid it. Decide, deliberately: arm the kind (and add a precedence guard so it cannot outrank gate), or delete it from both sides of the contract. Deleting is NOT a cleanup — the kind is declared and asserted in four places (chat_narrator.CARD_KINDS:44-46, types/index.ts:79, useRunChat.ts:297-303, test_chat_narrator.py:122 "all five card kinds are the documented set") and its dormancy is a locked decision, so it is an owner's call with its own brief. The family lesson to record with it: ISS-083 was the fifth dead counter here (ISS-039, FIX-164, FIX-163/ISS-063/FIX-221, FIX-225, ISS-083), and the generator is one design choice — *the frontend keeps re-deriving a number the backend already computed as a string*, which chat_narrator.py:157 has emitted since Phase 29. Three properties make it rot-prone: the authoritative value never reaches the FE as data; its correct value is 0 on most runs, so broken is indistinguishable from correct; and every incarnation had zero wiring coverage — *a test that supplies a component's input itself proves nothing about wiring*. The ending move (put the cycle on the wire and delete the FE derivation) is a real design change needing its own brief — arming _revision_index is precisely the landmine above — and must NOT be smuggled into a trivial fix. Related: app/api/runs.py reuses the name revision_index for the run-FAMILY v-number, a different concept; a rename would defuse the collision cheaply.
