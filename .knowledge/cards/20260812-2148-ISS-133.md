# ISS-133

## Title

**FIX-240 / ISS-121's collision-unsafe append idiom survives, unfixed, in the resume tier's double-drive guard.** `ExecutionEngine._stamp_resume_marker` (`engine.py:6309`) allocates its seq the naive way — `existing = await store.read_events(run_id, after_seq=0)` then `next_seq = max(seq)+1` then `store.append_event(...)` (`engine.py:6339-6352`) — and its outer `except Exception` (`:6353-6354`) degrades **any** failure to `logger.warning`. `IntegrityError` is one. So a `uq_run_events_scope_seq` rejection from the chat lane, which allocates from the SAME per-run seq space on every turn (`append_event_next_seq`), silently discards the `run_resuming` marker. That is the exact failure mode FIX-240 fixed for the engine's event sink by moving it to `append_event_at_or_after`; this call site was not swept. **What the marker is for, so the impact is not guessed:** it is the **double-drive guard** (T-12-03-DOUBLEDRIVE / Pitfall 3) — written BEFORE the driver task so a crash mid-resume is itself resumable and the run is never driven twice. Losing it weakens exactly that guarantee. A second, **unverified** impact: `_reconcile_terminal_status` treats `run_resuming` as an attempt boundary in its `resume_supersedes` test (`run_commands.py:652-660`), so a lost marker could record a successfully-resumed run as `cancelled` (the KAN-120 / ISS-078 symptom) — except the same test also accepts `pipeline_start`, and I did **not** verify whether a resumed run re-emits `pipeline_start`; if it does, this second impact is nil. **Reachability is narrow but real:** the boot-restore call site runs before any client is attached, but `_drive_user_resume` stamps the marker while the user is on the run screen and can chat. **Fix shape:** one-line — swap `append_event` for `append_event_at_or_after(run_id, max+1, …)`, the same edit FIX-240 made. Consider sweeping every remaining naive `read_events → max+1 → append_event` in one pass rather than one call site at a time.

## Test-writer note (2026-08-31)

The defect this card names — `_stamp_resume_marker`'s naive `read_events → max+1 →
append_event` seq allocation — is already fixed at HEAD. `engine.py:7694-7755` now
allocates via `store._max_event_seq(run_id)` + `append_event_at_or_after` (the
collision-safe retry pair), and the function's own docstring cites the fix: "ISS-125: it
now rides the SAME collision-safe pair the engine sink and the durable-cancel writer
use". `backend/tests/agents/test_resume_marker_seq_allocation.py` (marked `issue("ISS-125")`,
no xfail) already exercises this exact call site and passes at HEAD — ran it offline
(`python3.11 -m pytest tests/agents/test_resume_marker_seq_allocation.py -q`): 1 passed.
No `xfail(strict=True)` test can be written against ISS-133 without XPASSing
immediately (it would fail the suite for the wrong reason — a fixed defect, not a
selector/fixture error). The secondary "unverified impact" this card names
(`_reconcile_terminal_status`'s `resume_supersedes` check treating a lost marker as a
false `cancelled`) is now moot too, since the marker append no longer silently drops on
collision. ISS-133 is a stale duplicate of the already-shipped ISS-125 fix.
Recommend closing.
