## Condition

Inverse of [ISS-332](20260828-2041-ISS-332.md): that card is about a folder OVER-showing (staying
visible with zero matches); this is about a folder UNDER-showing — hiding a file that DOES match.

Read directly in `frontend/src/components/preview/AppBuilderPreview.tsx`:
- `FileTreeNode` only recurses into a folder's children when `isExpanded` is true
  (`{isExpanded && node.children?.map(child => <FileTreeNode .../>)}`, line 185) — a collapsed
  folder's descendants are never rendered, and therefore never reach the leaf `matchesSearch`
  check at all.
- `expandedPaths` (which folders are open) is set only by: the initial mount effect, which
  auto-expands solely the TOP-LEVEL path segment of each file (`topFolders.add(parts[0])`, lines
  346-358); manual `onToggle` clicks; or the "Expand all"/"Collapse all" button (lines 522-534).
- No effect in the component depends on `searchQuery` to adjust `expandedPaths`. Search state and
  expand state are fully decoupled.

## Expected vs actual

Expected: typing a query that matches a file nested inside a currently-collapsed, non-top-level
folder surfaces that match — at minimum by auto-expanding the containing folder, or some other
indication the match exists.

Actual (INFERRED, not yet reproduced in a browser): a match sitting inside a folder below the
auto-expanded top level is never rendered while that folder stays collapsed, and nothing about the
collapsed folder row itself changes to hint that it contains a hit. A query with a real match
several levels deep can appear to return nothing, unless the user has already manually expanded
the right folder before searching.

## Why the root cause implies it

Same missing wiring as ISS-332, just the other side of it: ISS-332 established that folder
rendering is fully independent of `searchQuery`; this card establishes that folder *expansion* is
too. Both are consequences of `searchQuery` never being read anywhere in the folder branch or in
`expandedPaths`'s state transitions.

## What would settle it

Repeat ISS-332's repro but do NOT pre-expand any subfolder (unlike its step 2, which explicitly
expands `src/styles` and `src/utils` first): seed the same 4-file payload, leave every folder at
its default (top-level-only) expand state, then search for `helper` (matches
`src/utils/helper.js`, which sits inside a non-top-level folder collapsed by default) and confirm
the match never appears without a manual expand.

## Resolution

Fixed by [FIX-394](20260829-0127-FIX-394.md). Its `ISS-501` case in
`AppBuilderPreview.searchFilter.test.tsx` XPASSes.
