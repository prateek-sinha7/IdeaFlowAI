## Sibling of ISS-360 — same remount, different trigger (no X click needed)

[ISS-360](20260828-1917-ISS-360.md)'s "Analyzer confirmation" section traces the search/category
reset to a page-level remount that fires on ANY `router.push` to a new pathname under the
`[...view]` catch-all — triggered when the detail view is OPENED
(`routes.libraryAgent`/`librarySkill`/`libraryHook` build bare paths with no query string), not
specifically by the X/scrim close button. The browser's own Back button reaches that identical
already-lost state by a route the X button never touches: `closeDetailModal` is never called at
all on a Back navigation. Not independently reproduced in a browser this pass (INFERRED).

## Mechanism

1. `frontend/src/components/library/LibraryPage.tsx:643-665` — the T16 effect ("when the URL
   changes, e.g. via browser back, close any modal that no longer matches the current URL") exists
   because Back is a real pathname change the app must react to. It clears
   `selectedAgent`/`selectedSkill`/`selectedHook` when `librarySlug` becomes null (`:647-651`),
   mirroring what `closeDetailModal` does for the X button.
2. That effect only clears the SELECTED-item state. It does nothing for, and cannot restore,
   `searchQuery`/`skillSearch`/`hookSearch`/`activeCategory`/`skillCategory`/`hookEvent` — and per
   [ISS-360](20260828-1917-ISS-360.md)'s finding, those were already reset to their `useState`
   defaults by the remount that happened when the detail view was OPENED, well before Back is
   ever pressed.
3. So whether the user leaves the detail view via the X button, the scrim click, or the browser's
   Back button, the search/category state is already gone by the time any of those three fire —
   Back only demonstrates that there is no surviving state to restore, not merely that
   `closeDetailModal`'s own URL-building is incomplete.

## Expected vs actual

Expected: pressing the browser's Back button from a Library detail view (any of the three tabs)
returns to the list with the same search text and category filter that were active before the
detail view was opened.

Actual (inferred, not yet reproduced live): identical reset to the X-button case — empty search
box, "All" category pill, full unfiltered grid — because the state was already lost at OPEN time,
before Back (or the X button) ever runs.

## Why this is INFERRED, not CONFIRMED

The T16 effect's scope (selected-item only, no search/category restoration) is confirmed by
reading `LibraryPage.tsx:643-665` in full. What is not yet verified is a live Back-button
reproduction (open a filtered Hooks tab, open a card, press the browser Back button instead of the
X, inspect the URL/search box/pill). [ISS-360](20260828-1917-ISS-360.md)'s validator reproduced
only the X-button path, 3/3 cycles.
