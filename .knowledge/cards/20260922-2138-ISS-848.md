# ISS-848

## Description

Root-cause completion for **QA-PS-051** (`LEDGER.md` / `BUGS.md#qa-ps-051`), analyze phase.
[ISS-843](20260922-2114-ISS-843.md)'s validate-phase reproduction (3/3 cold-start cycles,
`lane3` Chrome, `qa-admin@flowinqa.com`) already isolated the symptom to
`page.tsx:1021-1040`'s `recentRunsRequestedRef` guard and proposed a remount as the
explanation, but flagged it explicitly as "confirmed by evidence, not by reading a
remount-triggering line directly." This card closes that gap — the remount is read
directly, in a comment that already existed in the tree before this bug was filed — and
identifies the exact `router.push` call site that triggers it for a Library card click.

## Root cause (CONFIRMED — every citation read directly this session, 2026-09-22)

1. `frontend/src/components/library/LibraryPage.tsx:828` — clicking an agent card calls
   `router.push(routes.libraryAgent(agent.id, {...}))`. Same pattern at `:910` (skill) and
   `:1009` (hook) — the three library detail kinds QA-PS-051 names.

2. `frontend/src/app/[...view]/page.tsx:3494-3498` — a dated comment on an unrelated ref
   (`trackedRunIdRef`) states the general fact directly, "confirmed live":
   > "T6 (retry — V2 attempt 8 regression, FR-001/FR-003): T9's router.push remounts THIS
   > page component (Next.js does not preserve a dynamic-route page's own instance across
   > a client-side navigation to a new URL under the same catch-all — confirmed live: a
   > fresh render-instance id appears right after router.push, before
   > trackedRunIdRef.current even changes)."

3. `frontend/src/components/layout/DashboardLayout.tsx:543-548` corroborates independently
   and names the workaround this codebase already uses elsewhere:
   > "SHALLOW url update — deliberately NOT router.push. ... router.push changes the
   > [...view] catch-all params, which REMOUNTS page.tsx (see its T6/T7 comments —
   > "confirmed live"), wiping every page-local run state ... pushState keeps the URL
   > shareable/refreshable ... without touching the router tree, so nothing remounts and
   > nothing refetches."

   This is not a one-off: the same remount fact is independently established for a
   different ref by [FIX-493](20260907-1240-FIX-493.md) ("Both [router.push and
   router.back] are real Next.js router navigations, so both remounted the `[...view]`
   catch-all `page.tsx`") and for `useRunStateStore` by
   [ISS-679](20260917-1522-ISS-679.md)/[FIX-523](20260917-1555-FIX-523.md). Three
   independent prior investigations already hit this; this bug is a fourth.

   A FIFTH, older investigation hit the exact same `LibraryPage.tsx:828` call site
   already: [ISS-592](20260829-0117-ISS-592.md)/[ISS-593](20260829-0117-ISS-593.md)
   (2026-08-29) traced this identical `router.push(routes.libraryAgent/librarySkill(...))`
   remount to a DIFFERENT symptom — the Library tab's search text/category filter
   resetting — and it was closed by
   [FIX-407](20260829-0441-FIX-407.md). That fix deliberately did not stop the remount;
   it re-seeds `LibraryPage`'s filter state from URL query params carried on the new
   route (`routes.libraryAgent` etc. now take `{tab, category, search}`, per FIX-407's own
   locked constraint: "the restored state travels as query params ... not through a
   parallel history/storage channel"). Checked directly, not assumed: that workaround
   does not touch this bug, because `recentRunsRequestedRef` is a boolean "have I already
   fetched" flag with no meaningful URL representation to re-seed from — re-encoding
   "true" into the URL would not distinguish a real remount from a page the user
   deliberately reloaded to see fresh data. The fix has to preserve the GUARD itself
   across the remount, not re-derive it from the URL the way FIX-407 does for filter text.

4. `frontend/src/app/[...view]/page.tsx:828` — `const recentRunsRequestedRef = useRef(false);`,
   a component-instance-scoped ref, destroyed and recreated on every remount from point 2/3.

5. `frontend/src/app/[...view]/page.tsx:1022-1054` — the effect: skips the fetch only
   `if (recentRunsRequestedRef.current) return;` (line 1031), otherwise sets it `true` and
   calls `getWorkflows(currentToken, { limit: 50 })`. The guard is correct WITHIN one mount
   lifetime; a fresh mount gets a fresh `false` and refires the fetch.

6. `frontend/src/lib/api.ts:868-908` (`getWorkflows` / `inFlightWorkflows`) — the only
   dedupe is an in-flight-only `Map`, "dropped the moment the request settles" (its own
   doc comment). It cannot suppress a second call that starts after the first has already
   resolved, which is exactly what happens between the `/library` mount's fetch settling
   and the user's later click into a detail route.

7. `frontend/src/lib/api.ts:401-406` (`cachedGet()`'s own header comment) — run/workflow
   lists are deliberately excluded from the shared TTL cache: "their callers refetch
   precisely to observe a change (a cancel clearing the header's 'N Running' pill, a gate
   flipping a status)." This rules out the naive fix (wrap `getWorkflows` in `cachedGet`):
   it would reintroduce exactly the staleness `cachedGet` was deliberately kept away from
   this endpoint to avoid, for every OTHER caller of `getWorkflows` too (Run History's own
   pagination/filtering, the header's live-run pill).

**Net mechanism:** `recentRunsRequestedRef` is the one remaining "fetch once per session"
guard in `page.tsx` still implemented as a component-local ref. Every sibling mechanism
this codebase already hardened against the identical remount survives it because it was
moved somewhere that outlives `page.tsx`'s own instance — `auth/me`/capabilities/
preferences via `cachedGet` (a module-level TTL cache, confirmed at `api.ts:630` `getMe`
returns `cachedGet(...)`, which is also WHY `auth/me` measured as firing only once in
[ISS-843](20260922-2114-ISS-843.md)'s own reproduction even though the auth-check effect
that calls it, `page.tsx:912-934`, also re-runs on every remount — the effect refires, the
network call does not, because it is cache-backed); the agents/skills/hooks catalog fetch
via the Redux store's own `workflowsStatus` guard in `listenerMiddleware.ts`, which lives
above the router and survives remounts; `useRunStateStore`, moved to module scope by
FIX-523. This one call site was never moved.

## Blast radius (grepped, not just the reported path)

`grep -rl "router\.push(routes\." frontend/src` (excluding tests) returns 10 files:
`page.tsx` itself, `admin/page.tsx`, `workflow/page.tsx`, `CreationHub.tsx`,
`DashboardLayout.tsx`, `LibraryPage.tsx`, `StepsOverviewSpine.tsx`,
`SavedWorkflowsPage.tsx`, `LaunchWizard.tsx`, `RunConnectionProvider.tsx`. QA-PS-051
reported only the Library card-click path (3 of these call sites: agent/skill/hook). The
mechanism itself is keyed purely on "did `[...view]` remount," not on anything
Library-specific — see [ISS-849](20260922-2140-ISS-849.md) for the generalized claim
this implies.

`grep -n "useRef(false)" frontend/src/app/[...view]/page.tsx` finds exactly one other
candidate, `launchPendingRef` (`:806`). Read and ruled out as a sibling: it gates an
in-progress launch window, set and cleared entirely within one async launch flow
(`:4315`/`:4383`/`:4397`), not a "fetched once" guard — a remount cannot leave it in a
wrong state the way it does `recentRunsRequestedRef`.

## Expected vs actual

- Expected (per [ISS-843](20260922-2114-ISS-843.md)'s own framing, unchanged here):
  `GET /api/runs?limit=50` fires once total across a `/library` -> detail-view navigation,
  or never, since no library detail view renders run history.
- Actual: fires once per `[...view]` mount, so once on `/library` and again on every
  subsequent non-wizard navigation within the same tab.

## Where the fix belongs

Not in `LibraryPage.tsx` — a guard added there would cover only 3 of the ~10 navigation
call sites in the blast radius above, leaving every other route pair still broken. Not a
`cachedGet` TTL wrap on `getWorkflows()` itself — that would violate the documented
"must refetch to observe live changes" contract every other caller of that function
relies on (point 7 above). The fix belongs where every other "survive the remount" fix in
this codebase already landed: promote the GUARD (not the data) to a scope that outlives
`page.tsx`'s own instance. The smallest version of that is a module-level flag inside
`page.tsx` (mirroring the module-level `Map` pattern `inFlightWorkflows` already uses two
functions away in `api.ts`, keyed per-token so an account switch still gets a fresh
fetch) — a same-file, few-line change that does not touch `getWorkflows()`, so every
other caller's refetch-to-observe-changes behavior is untouched. This is a frontend-only
change; it does not touch SC-001/INV-1 or any import-linter-guarded port.
