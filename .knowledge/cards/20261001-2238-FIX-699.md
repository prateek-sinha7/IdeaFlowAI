# FIX-699

## What was wrong

This is bug report QA-KB-002. The root cause and blast radius come from the analysis on
[BUG-023](20260827-BUG-023.md) and are not re-derived here.

`parseViewPath` gives `/create/app` and `/create/user-stories` their own screens, with no `pipelineType`
(`frontend/src/lib/routes.ts:286-287`). `initialWorkflowTypeFor` returned a type for the generic screen only:

    return parsed.screen === "create-workflow" ? parsed.pipelineType : undefined;

So both named screens reached DashboardLayout's `workflowType` `useState` initializer with no type and fell through to
its `"user_stories"` default. `/create/app` rendered the user_stories workflow, and Run dispatched it.

## What changed, and why there

The change is in `frontend/src/app/[...view]/page.tsx`, inside `initialWorkflowTypeFor` only (now `:386-397`). The
edit was anchored on the quoted ternary:

    switch (parsed.screen) {
      case "create-app":
        return "app_builder";
      case "create-user-stories":
        return "user_stories";
      case "create-workflow":
        return parsed.pipelineType;
      default:
        return undefined;
    }

Its docblock (`:378-385`) was rewritten, as BUG-023 asked. The old one covered only "a generic `/create/{type}` cold
load". It also said the click path makes the type matter only on a cold mount, which
[ISS-916](20261001-2220-ISS-916.md) disputes.

**Why the fix goes here.** The function has one call site,
`initialWorkflowType={initialWorkflowTypeFor(parsedView) ?? builtinCanvasType}` (`page.tsx:4242` in the working tree,
`:4225` at HEAD). It has one consumer, the `workflowType` initializer (`DashboardLayout.tsx:627-637`). Every way onto
the two URLs therefore goes through it:
- a cold load
- the `/workflow/create?mode=app|user-stories` redirect
- the Home tile's `router.push`
- the "Edit brief & run again" `router.push`

I grepped again before editing and there is still one call site. The ids match line 1 of
`backend/agents/workflows/app_builder/workflow.yaml` and of `user_stories/workflow.yaml`. The style follows
`wizardModeFor` just above.

**Checked and left alone:**
- `routes.ts` and its `toEqual({ screen: 'create-app' })` round trips.
- `handleSelectFeature` and `createRouteForType` in DashboardLayout.

One consumer behaviour does change. `/create/app` and `/create/user-stories` now take priority over the
`prototype.pending` / `ppt.pending` sessionStorage fallback in that initializer, as `/create/{type}` already did. No
flow depends on that flag at these two URLs. The wizard sets the flag and then pushes `routes.home()`
(`LaunchWizard.tsx:1037-1038`), where `initialWorkflowTypeFor` still returns `undefined`.

## Tests and docs that encoded the defect, re-pointed

BUG-023's section "Tests and docs that encode the defect" names each of these as going red or stale with the fix, so
changing them is in scope. None of these edits loosens an assertion about correct behaviour.

1. **S-03-09 in `tests/integration/e2e/suites/03_launch_panels/test_launch_panels.py` (`:208-220`).** It was
   `@defect test_cold_loading_create_app_shows_the_user_stories_panel`, which asserted the bug (`SIMPLE_HEADING`, 6
   agents). Its own failure message said to rewrite it once D-01 was fixed. It is now
   `test_cold_loading_create_app_shows_the_app_builder_panel`, with `@defect` dropped. It asserts:
   - H1 "Describe the application" and eyebrow "Generate a full-stack application". This is app_builder's curated
     copy, `TYPE_CONFIG.app_builder` in `IdeaInputPage.tsx`, which the panel picks via
     `const curated = TYPE_CONFIG[effectiveType]`.
   - "Provide the brief" is absent, via `to_have_count(0)`, the suite's usual negative check.

   As BUG-023 asked, it does not assert an agent count, because admin@velocity.ai owns a 1-step "My app_builder"
   override. It does not assert "GENERATE APP BLUEPRINT" or "BUILD AN END-TO-END APPLICATION" either. The card's
   guard on the other screen already exists: S-03-07 asserts `SIMPLE_HEADING` on a cold `/create/user-stories`.
2. **The [ISS-247](20260828-1637-ISS-247.md) test in the same file (`:343-373`).** It loaded `/create/app` and clicked
   "Domain Discovery Agent" (`domain-analyst`). Only the user_stories roster has that agent
   (`backend/agents/workflows/user_stories/workflow.yaml:62`; app_builder has no match), so the test passed only
   because of D-01. It now loads `/create/user-stories`, with its assertions unchanged.
3. **The S-03-08 comment in the same file.** I dropped the sentence "It is the ONLY create route that resolves its
   type correctly on a cold load — see S-03-09", which the fix makes false. This is a comment-only change.
4. **S-03-09 in `tests/integration/screens/03-launch-panels.feature.md` (`:167-176`).** This is the spec half of the
   same scenario, rewritten to match: same id, `@defect` dropped, new title "Cold-loading /create/app shows the
   app-builder panel". Its old "CORRECT behaviour, once fixed" hint ("BUILD AN END-TO-END APPLICATION", "Advanced 1
   agents") named exactly what BUG-023 says not to assert, so it was removed. I dropped the matching S-03-08 sentence
   here as well.
5. **D-01 in `tests/integration/DEFECTS-OBSERVED.md`.** I added a RESOLVED line in the file's own convention (as on
   D-02 and D-18). It names BUG-023 instead of a SHA because nothing is committed. It also records that the second
   fix sketch, deleting the special cases, is unsound.
6. **`tests/integration/PAGES.md:52` (p10) and `tests/integration/MANIFEST.md:44` (`07`).** D-01 is marked resolved
   in both. The p10 and `07` screenshots predate the fix and show the user-stories panel until the next capture sweep.
7. **Not edited: `tests/integration/docs/PROGRESS.md:71`.** It still shows the old S-03-09 title. Its header says
   "Generated by `capture/_scenarios.py --ledger`. Do not hand-edit", and `scripts/run-all-offline.sh` rewrites it.
