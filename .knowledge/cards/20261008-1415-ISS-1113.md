# ISS-1113

**Register source:** sibling derived during the `QA-KB-100` analysis on 2026-10-08 (root [ISS-1092](20261007-2308-ISS-1092.md)). Not its own bug row.

**Confidence:** INFERRED. Read from the code, plus a compile probe on an equivalent row (`evidence/qa-kb-100/analysis-05` W5 runs the same compile call); `POST /api/runs` itself was not driven because it mints a run. What would settle it: a test that calls `launch_run` with the `user_workflow_id` of a row that has `overrides_pipeline_type` set, with the engine hand-off stubbed, and asserts which trust the compile used.

## Condition

An override is stored as an ordinary `WorkflowDefinition` row (`source="user"`, `manifest_json={"steps": [...]}`), so it has a second reader that never touches `merge_override_steps`:

- `launch_run` resolves `body.user_workflow_id` through `_owned` (`run_commands.py:3287`), which filters on owner and `source="user"` only (`user_workflows.py:507-517`), never on `overrides_pipeline_type`.
- A row whose `manifest_json` has `steps` becomes `LaunchSource.USER_WORKFLOW_MANIFEST` (`run_commands.py:3299-3303`), is compiled at `trust="db"` (`:3386-3390`: `"user" if _inline else "db"`), persists `_trust: "db"` for resume (`:3402`), and takes its pipeline type from the row, `ppt` (`:3404-3407`), which is what the tier gate then checks (`:3452`).
- The saved-workflows list returns every `source="user"` row, overrides included (`user_workflows.py:897-911`), so the override is offered as a runnable saved workflow (INFERRED for the page; the UI was not driven).
- Other `trust="db"` readers of a user row: the conditional-route trigger (`kernel_services.py:1640`, [ISS-946](20261002-0107-ISS-946.md)) and the resume recompile (`engine.py:15627-15640` uses the persisted `_trust`).

## Expected vs actual

Expected: the steps of an override row never run with more trust than `merge_override_steps` gives them, whichever door they come through. Actual: through this door they compile at `db`, so the whole table in [ISS-1111](20261008-1415-ISS-1111.md) applies and the root card's fix does not reach it.

## Why the root cause implies it

The fix proposed for the root closes one reader. A row has more than one, and this is the one left once the first is closed.

## Fix direction (INFERRED, not applied)

Compile a row that has `overrides_pipeline_type` at `trust="user"` in Case 3 and in the trigger path (the Case 3 row snapshot, `run_commands.py:3288-3297`, would need that column), or refuse to launch an override row by id and send the caller to the built-in. Either way, no fourth `LaunchSource` ([ADR-0020](20260824-1831-ADR-0020.md) locked constraint). A persisted `_trust: "db"` on runs minted before the fix is replayed at resume, which is acceptable only once the writers have stopped producing such rows ([ISS-1112](20261008-1415-ISS-1112.md)).

Not covered: a saved row that is not an override ([ISS-1114](20261008-1415-ISS-1114.md)).

## Resolved (QA-KB-100 fix, 2026-10-08)

The first option was taken, the one the test encodes. [FIX-766](20261008-1444-FIX-766.md) compiles an override row at `trust="user"` in Case 3 (`run_commands.py:3356-3358`, with `overrides_pipeline_type` added to the row snapshot at `:3296`) and persists that trust for resume (`:3408`). The trigger door does the same (`kernel_services.py:1616`, `:1644`). No fourth `LaunchSource`. `test_launching_an_override_row_by_id_compiles_below_db_trust` XPASSes (strict). A probe confirms that the trigger compiles at `user` for an override row and `db` for a plain row, and that Case 3 keeps `db` for a plain row (`evidence/qa-kb-100/fix-06` F6-F8b).
