# ISS-845

INFERRED sibling of [ISS-844](20260922-2124-ISS-844.md) (QA-PS-040), filed
because the existing explanation for the doubling ISS-844's Mechanism 1
depends on does not survive a second card's own scrutiny — a gap in the
knowledge base, not yet reproduced or resolved by anyone.

## The claim as it stands today

[ISS-794](20260922-1827-ISS-794.md) (root-caused for `/create/ppt`,
QA-PS-044) states: "the listener's `effect` runs async per action, so both
StrictMode-doubled `signedIn` dispatches can read `'idle'` before either
thunk's `pending` reducer has committed, racing past the guard and firing
`fetchWorkflows`/`fetchRecentRuns` twice." [ISS-832](20260922-2001-ISS-832.md)
(QA-PS-046) and, by extension,
[ISS-844](20260922-2124-ISS-844.md) (QA-PS-040) both cite this as the
mechanism and apply it "verbatim" to their own routes.

## Why that claim is already in doubt (CONFIRMED — a prior card said so)

[FIX-618](20260922-1945-FIX-618.md), analyzing the SAME listener on
`/settings/profile`, measured `GET /api/runs?limit=6` firing **x2** while
`GET /api/workflows` (dispatched from the same effect, one line below, under
the identically-shaped guard) fired only **x1** — the *inverse* asymmetry
`fetchWorkflows`-races-past-guard would predict if both thunks were racing
the same way. FIX-618's own text: "ISS-794 attributes the doubling to the
listener `effect` running 'async per action', but RTK invokes the effect
synchronously up to its first `await` — which here is after both
dispatches — so that stated mechanism does not explain the asymmetry. Left
for ISS-784/793/794's own line rather than patched on a guess."

That line is accurate as far as it goes: `frontend/src/store/listenerMiddleware.ts:47-56`
reads `state.global.workflowsStatus` / `state.global.recentRunsStatus`
(both plain synchronous `getState()` reads) and calls
`dispatch(fetchWorkflows())` / `dispatch(fetchRecentRuns())` — dispatching a
`createAsyncThunk` synchronously dispatches its `.pending` action before
returning — all **before** the effect's first genuine `await` (the trailing
`await Promise.all([...preloadHome, ...preloadLibrary])` at `:66`). If
`createListenerMiddleware` runs one `signedIn` listener invocation to
completion (or to its first await) before starting the next, as this
reading implies, the guard should NOT be racy: the second invocation should
observe `workflowsStatus === "loading"` and skip. Yet the doubling is
empirically real — ISS-794 measured it 3/3 live on `/create/ppt`, and
FIX-618 measured a version of it (the `limit=6`/asymmetry case) live on
`/settings/profile`. Something genuinely causes two real network calls;
"the listener effect races" is just not yet shown to be that something.

## What this means for ISS-844 (QA-PS-040) specifically

[ISS-844](20260922-2124-ISS-844.md)'s Mechanism 1 is CONFIRMED at the
structural level (exhaustive grep: one `dispatch(signedIn(` site, one
`dispatch(fetchWorkflows(` site, no cache in `workflowsApi.list()` — so any
doubling must trace to `page.tsx:924`'s effect firing more than once) and
CONFIRMED empirically at the observed-symptom level (ISS-787's live 2x
capture, and the same 2x shape reproduced on multiple sibling routes). What
is NOT confirmed anywhere in the corpus is the internal mechanics of *why*
firing that effect twice produces two real `fetchWorkflows` network calls
past a guard that reads synchronously-committed state. Two plausible
alternatives neither this card nor any other has tested:

- The `[...view]` catch-all is not just StrictMode-double-invoking one
  mount's effects, but genuinely double-*mounting* in some cases —
  [ISS-843](20260922-2114-ISS-843.md) found exactly this ("the `[...view]`
  catch-all component itself remounts when its segment array changes
  shape") for a *navigation* trigger; an analogous full-remount on a cold
  load (e.g. a hydration mismatch triggering a second client render) would
  bypass a `useRef` guard the same way a `useState`-initialized one would
  not, and would not be "racing the guard" at all — it would be a second,
  fully independent effect run with its own fresh closure.
- `createListenerMiddleware`'s actual scheduling of two rapid dispatches of
  the SAME action type may not serialize the way "synchronous up to first
  await" assumes — e.g. if it schedules each matching action's effect via
  its own independent `Promise.resolve().then()` rather than a shared
  per-listener queue, the two effect invocations could interleave at the
  microtask level in a way neither ISS-794 nor FIX-618 fully traced through
  Redux Toolkit's own source.

## Why this is worth its own card rather than folding into ISS-844

Whoever fixes ISS-844's Mechanism 1 needs to fix the ACTUAL cause, not the
described one — a `useRef` one-shot guard (the fix that worked for the
`recentRuns` effect, [FIX-630](20260922-2115-FIX-630.md)) only helps if the
trigger is StrictMode double-invoking a single mount's effect. If the real
trigger is a genuine second mount (first bullet above), the same `useRef`
fix would not close it, since a fresh mount gets a fresh ref. Landing a fix
that "should" work per the unproven theory, without checking which theory
is right, risks a repeat of exactly what FIX-618 already flagged once.

## What would settle it

A live instrumented capture: log `page.tsx`'s mount effect's own
invocation count (e.g. a `console.count` at the top of the auth-check
effect, before any early return) alongside the timestamps of both
`dispatch(signedIn(...))` calls and the `fetchWorkflows.pending`/
`.fulfilled` reducer timestamps, on one cold `/library` (or `/dashboard`)
load. That distinguishes "one mount, two effect invocations, guard raced"
from "two mounts, two independent effect invocations, no guard could have
caught it" — not yet done by any card in this corpus.

## NOTE — fixer phase (2026-09-22): a fix landed, this card stays OPEN

[FIX-633](20260922-2229-FIX-633.md) added the per-mount `signedInDispatchedRef` guard to
`page.tsx`'s auth-check effect. That answers this card's stated worry about
the *remount* alternative rather than ignoring it: a genuine second mount
happens later in time, after `fetchWorkflows.pending` has committed, so
`listenerMiddleware.ts:47-56`'s own `workflowsStatus` check already drops its
repeat dispatch — the case that guard cannot see is two dispatches inside ONE
mount, which is what the ref closes. Module scope was rejected on purpose: it
would suppress the `signedIn` announcement the ISS-200 account-switch branch
depends on.

What FIX-633 did NOT do is settle which mechanism produced ISS-787's 3/3
capture — the symptom no longer reproduces on demand (0/5 then 0/1 live
re-checks, recorded on [ISS-844](20260922-2124-ISS-844.md)), so the
instrumented capture this card specifies ("What would settle it") is still
unwritten. Closing this card on an unmeasured fix is the exact mistake it was
filed to prevent, so it remains `open`.
