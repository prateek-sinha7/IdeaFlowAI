# FIX-608

Bug **QA-PS-019** (`BUGS.md#qa-ps-019`) — the Custom-workflow composer's per-step
**Tools** tab had no runtime effect in either direction.

## What was wrong

"Write files" ON never granted `write_file`/`edit_file` ([ISS-698](20260922-1001-ISS-698.md),
reproduced live 3/3 — runs `aa2c0684-…`, `dfc27751-…`, `6829bdef-…`, the agents
naming the missing tool themselves), and "Read files" OFF never revoked
`read_file`/`ls`/`glob`/`grep` ([ISS-732](20260922-1352-ISS-732.md), the inverse
of the same gap). The selection saved, the UI showed it, the run ignored it.

## Root cause

`backend/agents/execution_engine/engine.py`, `ExecutionEngine._apply_selections`
(the single overlay seam; one production call site, `engine.py:4654`). It builds a
`patch` dict from one `if sel.get(...)` case per lever — `validators`, `gates`,
`model`, `retry`, `injects`, `skills`, `strategy`, `fanout`, `task_source` — and
had **no `tools` case at all**. Everything upstream already worked:
`selections.py`'s `_LEVER_KEYS` projects `tools` onto the synth step, and
`WorkflowCompiler.compile(trust="user")` turns it into a real `ToolPermissions` on
`user_step.tools` (pinned by this file's first, non-xfail test). Only the copy onto
the step that actually runs was missing, so `ectx.current_step.tools` kept whatever
`custom/workflow.yaml` declared — `tools: {read_files: true}` on 8 of 9 steps and no
`tools:` key on the ninth, i.e. `write_files=False` and `read_files=True` for every
step regardless of what the user picked. `factory.py:419-432`'s
`denied_tools(ctx.step_tools)` then stripped `write_file`/`edit_file` from every
custom-workflow agent.

The comment sitting where the branch should have been —

> "No `tools` overlay: the declarative fanout_batch path acquires no
> spawn_subagents grant (run_fanout does no permission check; trust=user forces
> tools.spawn_subagents OFF anyway)."

— only ever reasoned about `spawn_subagents`, but the absent branch dropped the
whole `ToolPermissions` object.

## What changed, and why there

One branch added to the same `patch` dict, `engine.py:12903-12926` (the stale
comment above the fan-out levers reworded, since the overlay now exists):

```python
if isinstance(sel.get("tools"), dict) and sel["tools"]:
    _slots = {f.name for f in dataclasses.fields(step.tools)}
    _named = {k: getattr(user_step.tools, k) for k in sel["tools"] if k in _slots}
    if _named:
        patch["tools"] = dataclasses.replace(step.tools, **_named)
```

Three decisions, each deliberate:

* **In `_apply_selections`, not at any caller.** It is the single seam every
  composed run routes through (`engine.py:4654`), and it is where the other eight
  levers already land. ISS-732's second observable — `_step_can_read_files` at
  `engine.py:15055-15063` reading the same un-overlaid field — self-corrects with
  no edit of its own.
* **Values come from `user_step.tools`, never from `sel`.** That object has already
  been through `compile(trust="user")` → `permission_caps.apply_cap`, so the
  untrusted cap has bounded it (`exec`/`spawn_subagents`/`network`/`git` OFF,
  `tool_sets` narrowed). The engine copies a decided permission; it still decides
  none — `permission_caps.py`'s "engine.py (nothing)" contract holds, and no import
  was added.
* **Named slots only, not a wholesale replace.** The composer exposes exactly two
  levers (`AgentsPopup.tsx:1484-1495` `TOOL_GRANT_LEVERS`), so replacing the whole
  object with an untrusted-capped one would silently drop an engineer-granted
  `exec`/`tool_sets` from a trusted base step the user merely re-modelled. Keyed off
  the selection's own keys, so it carries no permission literal (SC-001).
