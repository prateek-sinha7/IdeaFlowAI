# ISS-793

## Description

Opening `/create/prototype` (the prototype `LaunchWizard`) fires several API
calls it does not need — duplicate `GET /api/runs?limit=50` and `GET
/api/workflows`, three `GET /api/auth/me`, and a `GET /api/ppt/templates`
loading the PPT template catalog on a page that only renders prototype
templates. Confirmed for bug **QA-PS-045** (see `LEDGER.md` /
`BUGS.md#qa-ps-045`).

## Reproduction

3/3 cold-start cycles, every cycle: navigate to `about:blank`, then
`http://localhost:3000/create/prototype` (already signed in as
`qa-admin@flowinqa.com`), wait 2s to settle. Verified per-load with
`performance.getEntriesByType('resource')` filtered to
`fetch`/`xmlhttprequest` (the MCP network-request log does not reset across
same-origin navigations in this environment):

Every cycle produced the identical 15 fetch/xhr calls:
`GET /api/auth/me` ×3, `GET /api/runs?limit=50` ×2, `GET /api/workflows` ×2,
`GET /api/runs?limit=6` ×1, `GET /api/agents/library` ×1, `GET
/api/hooks/library` ×1, `GET /api/skills/library` ×1, `GET
/api/workflows/prototype` ×1, `GET /api/prototype/templates` ×1, `GET
/api/prototype/design-systems` ×1, `GET /api/ppt/templates` ×1.

100% reproducible, not intermittent — every cycle produced the identical
count and set, so this is CONFIRMED outright (no axis-narrowing needed).

Evidence: `evidence/qa-ps-045/01-validate-attempt1-prototype-wizard-loaded.png`,
`evidence/qa-ps-045/02-validate-attempt2-prototype-wizard-loaded.png`,
`evidence/qa-ps-045/03-validate-attempt3-prototype-wizard-loaded.png`.

## Discrepancy from the original report

The reporter's DevTools capture (2026-09-17) recorded 143 total requests /
3.6 MB and attributed the duplication to `DashboardPage`/`HomeLaunchGrid`
mounting underneath `LaunchWizard` as an overlay (citing `page.tsx:3868` and
`HomeLaunchGrid.tsx:223,288`). That theory is stale against the current
tree: `frontend/src/app/[...view]/page.tsx:4004-4009` (the
015-frontend-routing T6 fix, landed after the report) returns
`<LaunchWizard initialMode={wizardMode}>` standalone for `/create/prototype`
— it never reaches the `DashboardLayout`/`HomeLaunchGrid` render branch at
all. The 143-vs-15 gap is most likely the reporter's count including static
template-thumbnail assets alongside API calls, or a capture taken before T6
landed. The CORE defect — duplicate fetches and PPT templates loading on a
prototype-only page — still reproduces cleanly today, via two different and
more precise root causes than the report guessed:

## Root cause

1. `frontend/src/app/[...view]/page.tsx:990-1007`:

```tsx
useEffect(() => {
  if (!isAuthenticated) return;
  const currentToken = getToken();
  if (!currentToken) return;

  getWorkflows(currentToken, { limit: 50 })
    .then(({ runs }) => setRecentRuns(runs))
    .catch(() => { /* ... */ });

  getWorkflowDefinitions(currentToken)
    .then((rows) => setHomeWorkflows(rows.filter((w) => w.user_launchable)))
    .catch(() => { /* ... */ });
}, [isAuthenticated]);
```

This mount effect lives in the SAME top-level `page.tsx` component that
renders every route (dashboard, wizard, canvas, etc.) and is gated only on
`isAuthenticated`, never on which `MainView`/route this render cycle will
actually produce. React hooks run unconditionally on every render of this
component regardless of which JSX branch (`<LaunchWizard>` at line 4008 vs
`<DashboardLayout>` further down) the function eventually returns, so
`getWorkflows({limit:50})` (`GET /api/runs?limit=50`) and
`getWorkflowDefinitions` (`GET /api/workflows`) fire on `/create/prototype`
even though nothing on that route reads `recentRuns` or `homeWorkflows`.
This accounts for `runs?limit=50` firing at all on a page that should not
need run history, and contributes to the `/api/workflows` duplication
(this effect's call plus the wizard's own workflows fetch for its "5
agents" Advanced panel).

2. `frontend/src/components/workflow/LaunchWizard.tsx:617-654` (comment:
   "Load both template families + the design-system registry once authed"):

```tsx
useEffect(() => {
  if (!authChecked) return;
  const token = getToken();
  if (!token) return;
  let cancelled = false;

  listPrototypeTemplates(token)
    .then((t) => { if (!cancelled) setWebTemplates(t); })
    .catch(/* ... */);
  listPPTTemplates(token)
    .then((t) => { if (!cancelled) setDeckTemplates(t); })
    .catch(/* ... */);
  listDesignSystems(token)
    .then(/* ... */)
    .catch(/* ... */);

  return () => { cancelled = true; };
}, [authChecked, router]);
```

`LaunchWizard` calls **both** `listPrototypeTemplates` and
`listPPTTemplates` unconditionally on mount regardless of `mode` — it never
checks `mode === "prototype"` before fetching the PPT catalog (or vice
versa on `/create/ppt`). This is the actual, current source of "PPT
template assets load on a prototype page" — not a `DashboardPage`/
`HomeLaunchGrid` overlay as the original report guessed.

`GET /api/auth/me` ×3 and `GET /api/workflows` ×2 have more than one
caller — `page.tsx:894` (`getMe`), `LaunchWizard.tsx:371` (`getMe`), and a
further, not-yet-traced source (`HomeLaunchGrid.tsx` also defines a
`getMe` call, though per the current render path it should not be mounted
on this route) — left for the fix phase to fully isolate rather than
resolved here.

## Expected vs actual

- Expected: opening the prototype wizard fires only what the wizard needs —
  `GET /api/workflows/prototype` (wizard config), `GET
  /api/prototype/templates`, `GET /api/prototype/design-systems`, `GET
  /api/workflows` (for the "5 agents" Advanced count), `GET /api/auth/me` —
  roughly 5 requests, no PPT assets, no run history.
- Actual: 15 fetch/xhr calls including duplicated `auth/me` (×3),
  `runs?limit=50` (×2), `workflows` (×2), `prototype/templates`, plus
  `ppt/templates`, `agents/library`, `hooks/library`, `skills/library`, and
  `runs?limit=6` — none of which the prototype wizard uses.

## Impact

Wasted backend round trips on every wizard open (duplicate `auth/me` and
`workflows` calls, an unnecessary `runs?limit=50` fetch, and PPT template
payload the page never renders) — cosmetic/perf overhead, not a functional
break; the wizard still works.

## TEST COVERAGE — ISS-793

Manual verification only (no test suite exists for this wizard-mount fetch
path). Verified via `performance.getEntriesByType('resource')` across 3
independent cold-start cycles, all three showing an identical 15-call set
with the duplication and PPT-template-on-prototype-page symptom described
above.

## Resolution — [FIX-630](20260922-2115-FIX-630.md) (2026-09-22)

Both mechanisms closed. `LaunchWizard.tsx:617-647` now picks the family off
`isWeb` (`isWeb` added to the deps so the in-wizard toggle still loads what it
switches to) and `listDesignSystems` moved to its own once-per-mount effect;
`page.tsx:1017` returns early when `wizardModeFor(parsedView)` resolves, keyed
on `viewPathKey` with a `recentRunsRequestedRef` so it stays one fetch per
mount. Measured after the change on a cold `/create/prototype`:
`prototype/templates` 1, `prototype/design-systems` 1, `auth/me` 1,
`workflows` 1 — no `ppt/templates`, no `runs?limit=50`. The `/api/workflows`
duplication this card also listed belongs to
[ISS-781](20260922-1630-ISS-781.md) and stays open there; the `auth/me` ×3 and
`runs?limit=50` ×2 counts had already been closed by `cachedGet` (ISS-801) and
`inFlightWorkflows` (FIX-616) before this fix.
