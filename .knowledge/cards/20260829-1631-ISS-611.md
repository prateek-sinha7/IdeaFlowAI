# ISS-611

**BUG-ID:** BUG-20260829-140111-runs-id-steps-agent (sibling, derived by analysis — NOT independently reproduced this pass)

**Confidence: INFERRED** (per this Analyzer pass's own rule: unreproduced in a live browser this
pass). The mechanism itself is a complete, unambiguous code trace — every line below was read —
and the developer who last touched this exact function **already wrote down the same defect in
a comment** (see "Corroboration" below) without fixing it, which is materially stronger grounding
than a hypothesis.

## The inverse of ISS-607's defect #1 — same conflation, opposite direction

ISS-607 documents: starting from the UNPINNED base route (`liveRunId` = root = what's currently
shown) and picking the true latest member is a **no-op** (nothing navigates). This card documents
the mirror case: starting from a **pinned OLDER, non-latest** member (`/runs/{rootId}/versions/2/
...` in a 3-member family) and clicking "Back to latest" is **not a no-op** — it navigates, but
to the wrong place: the family ROOT, silently mislabeled as "latest".

## Root cause (traced by code reading)

`PreviewPanel.tsx:550-551`:
```
550  const latestId = sortedMembers.length > 0 ? sortedMembers[sortedMembers.length - 1].id : (liveRunId ?? null);
551  const activeRunId = viewingVersion?.id ?? liveRunId ?? latestId;
```
`liveRunId` is `contentSourceRunId` (`DashboardLayout.tsx:3153`, `liveRunId={contentSourceRunId
?? null}`) — the run id embedded in the URL's base segment. Every versioned route FIX-328 built
is shaped `/runs/{rootId}/versions/{v}/{tab}` (`frontend/src/lib/routes.ts` — the pin is always
the SECOND argument, the base run id the first), so for as long as a user is browsing a family
through that addressing scheme, `contentSourceRunId`/`liveRunId` stays pinned to the ROOT id that
first established the mount, never to whichever member is currently being viewed. `latestId`
(line 550) is independently computed as `sortedMembers`' last (newest-by-`revision_index`)
member. **For any family with 2+ members reached via its root URL, these two are structurally
different values** — `liveRunId` is the root, `latestId` is the newest revision.

`ReadOnlyVersionBanner.tsx:31-36` renders the literal button text `"Back to latest →"`,
wired at `PreviewPanel.tsx:1222` to `handleBackToLatest`:
```
597  const handleBackToLatest = useCallback(() => {
598    onTabSelect?.(activeTab, null);
599    setViewingVersion(null);
600  }, [onTabSelect, activeTab]);
```
`setViewingVersion(null)` means `activeRunId` (line 551) now resolves to `viewingVersion?.id
(null) ?? liveRunId` = **`liveRunId`, the ROOT** — not `latestId`. The same happens via
`handleSelectVersion`'s identical branch (`PreviewPanel.tsx:579-582`,
`if (memberId === latestId) { setViewingVersion(null); return; }`) if the picker's true-latest
option is clicked while a DIFFERENT older version is currently pinned. Both paths also call
`onTabSelect?.(activeTab, null)` (lines 578/598) which DOES navigate this time — unlike ISS-607's
no-op — because the URL currently carries a real pin (`/versions/2/...`) that differs from the
un-pinned target route, so `DashboardLayout.tsx:501`'s `targetRoute === window.location.pathname`
guard does NOT block it. The button visibly does something; what it does is wrong.

## Corroboration — the FIX-328 author already flagged this exact gap, unfixed

`PreviewPanel.tsx:605-615`, the comment on the URL-pin-applied effect that FIX-328 added:
```
609  // and would null the pin out for exactly the family
610  // whose newest member is the one pinned.
```
That comment describes precisely this conflation and explains why FIX-328 set `viewingVersion`
directly for a URL-borne pin instead of routing it through `handleSelectVersion` — but
`handleSelectVersion`'s own "latest → null → liveRunId" branch, and `handleBackToLatest`, were
left as they were. This card is that same acknowledged gap, for the USER-CLICKED path rather
than the cold-URL path FIX-328 worked around.

## Expected vs Actual (inferred, not yet re-driven through the browser)

**Expected:** in a 3-member family (v1 root, v2, v3-latest) opened via `/runs/{rootId}/steps`,
pinning to v2 (`/runs/{rootId}/versions/2/steps`) and clicking "Back to latest →" (or picking v3
in the picker) lands on **v3**'s content, matching the button's own label.

**Actual (inferred):** it lands on **v1** (the root) — `liveRunId`, not `latestId` — with the
picker/URL giving no indication that "latest" and "what's now on screen" have diverged.

## Fix direction

Same chokepoint as ISS-607/ISS-610: `handleSelectVersion`/`handleBackToLatest`
(`PreviewPanel.tsx:570-600`) need to resolve the "back to live/latest" shortcut against
`latestId` explicitly (pin to `latestId`'s member number) rather than assuming `liveRunId` and
`latestId` are interchangeable — they coincide only when the mount's own URL already names the
latest member (the ISS-607 "contrast" case: navigating directly to the revision's own run id).

## Evidence

Code reading only, this pass — every file:line above was opened and quoted. No independent
browser reproduction; a 3-member family fixture would be needed (the ISS-607 pair is only
2-member, root+1 revision, where `liveRunId` happens to equal `latestId` once you're ON the
revision's own URL — this defect needs a family where the user is pinned to a MIDDLE member).
