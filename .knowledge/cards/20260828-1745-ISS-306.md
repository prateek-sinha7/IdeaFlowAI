## What happened

On `/create/ex_A4_human_gate` (the seeded "Human Gate" fixture), the "Pick Language" step's
manifest declares `"gates": ["before-human", "conditional"]` per `GET
/api/workflows/ex_A4_human_gate`. On a completely fresh page load — zero user interaction —
neither of the two UI controls that are supposed to expose gate state reflects the
`before-human` half of that: the "Review gates" checklist popover pill reads "no gates" with
all 5 agent checkboxes unchecked (including Pick Language), and the Advanced modal's Config
tab for that same node renders the `Gate` combobox pre-set to "Conditional gate" only, with
no other indicator anywhere in that panel that the step also carries a human-review gate.

Reproduced 3/3 from independent cold navigations (`/dashboard` -> `/create/ex_A4_human_gate`
each time). Cycle 1 confirmed both controls (Review-gates checklist unchecked, Gate combobox
"Conditional gate" only via evaluated `checked` state on all 5 checkboxes). Cycle 2
re-confirmed both controls identically. Cycle 3 re-confirmed the Review-gates pill alone
("no gates") as a spot-check; no variation across cycles was needed — this reproduces on the
very first render, before any interaction, every time.

BUG-20260828-055300-create-ex-a2-branch in the bug-hunter register documents the original
find.

### One relevant discovery during validation

The `CanvasConfigRail` Config tab for this node also renders a separate "Declared
capabilities" panel that DOES list both `gate:before-human` and `gate:conditional` as
badges, and the `Gate` combobox itself carries a tooltip: "Gates pause or redirect the run
at this step. One gate per step — human-review gates share one durable slot." This confirms
the underlying data is present and reaches the client; the gap is specifically that the two
controls named in this bug (the Review-gates checklist and the Gate combobox's own selected
value) have no representation for a step carrying two gates simultaneously — the checklist
derives its checked state from a source that doesn't include `before-human` from this
manifest at all, and the combobox is a single-select bound to `chosenGate`, which picks one
value out of `sel.gates` and drops the other.

## Root cause (not yet fixed — filed as ISS)

Not fully traced to file:line in this validation pass (no code was modified). Two known
facts narrow it:
- `CanvasConfigRail.tsx`'s `Gate` combobox (see sibling ISS-247, same file) is a single
  `<select>` bound to one derived `chosenGate` value out of `sel.gates`/`agent.gates` — a
  step with `gates: ["before-human", "conditional"]` can only ever show one of the two in a
  single-select, and the observed behavior is that `conditional` wins, `before-human` is
  dropped from the visible selection entirely (not merely deprioritized — no fallback text,
  no secondary badge in the combobox row itself).
- `ReviewGatesSection.tsx`'s checklist (see ISS-247) is driven by its own local
  `checkedIds`/`gateAgentIds` state, which is unrelated to `agent.gates` — for this fixture
  it appears not to be seeded from the manifest's `before-human` declaration on initial
  load at all, hence "no gates" / all-unchecked even though the backend genuinely declares
  one.

## Root cause — CONFIRMED (3-analyzer, 2026-08-29)

Completes the trace the section above left open. No code was modified — this is a read-only
trace. Two independent, fully-confirmed mechanisms, one per broken control:

**Mechanism A — Review-gates checklist ("no gates" / all unchecked).**
`ReviewGatesSection.tsx:52` — `const isDefaultGated = (a: AgentDef): boolean => a.gate ===
"Human_Gate";` — and `:92-96`/`:103-114` — `checkedIds` seeds ONLY from the `initialGateIds`
prop (a saved run's flat `gate_agent_ids` list — absent on a fresh built-in load) or
`isDefaultGated` (the STATIC per-AGENT.md `gate` field). That field is populated from
`declared_gate=spec.gate if spec else None` (`backend/app/api/workflows.py:501`), i.e. the
`custom-agent` template's own AGENT.md frontmatter — which does not and cannot declare
`gate: Human_Gate` per-step, because the per-step human-review declaration for a composed step
lives exclusively in the manifest's `gates: [...]` array (the ADR-0013 vocabulary), a
completely different field `isDefaultGated`/`checkedIds`'s seed never reads. The `selections`
prop FIX-346 added to this component (`ReviewGatesSection.tsx:48`) is wired as a WRITE-only
target (`onSelectionsChange`, fired only from `toggle`, `:136-138`) — nothing reads
`selections`/`sel.gates` to compute the *initial* `checkedIds`. So a `custom-agent` step, which
has no AGENT.md and therefore no static `gate` field at all, can never render checked on load
no matter what its manifest declares — confirmed live: `pick-language`'s `AgentDef.gate` is
`null` (no library AGENT.md exists for `custom-agent` instances), so `isDefaultGated` is false
for all 5 steps in this fixture regardless of the real `gates: [before-human, conditional]`
declaration.

**Mechanism B — Gate combobox shows only "Conditional gate"; the Prompt User toggle (the
control actually built to represent `before-human`) never activates either.**
- B1 (by design, not itself a defect): `CanvasConfigRail.tsx:237,250-255` — `PROMPT_USER_GATE =
  "before-human"`; `gateChoices = gateOptions.filter((g) => g !== COUPLED_GATE && g !==
  PROMPT_USER_GATE)`; `chosenGate = gateChoices.find((g) => declared.includes(g)) ?? ""`.
  `before-human` is deliberately excluded from the combobox's own option set (comment at
  `:227-233`) — the combobox can only ever show `conditional` here. The intended representation
  is a separate "Prompt User" toggle in the Route section, not this control.
- B2 (the actual defect): that toggle's `promptUser` boolean
  (`CanvasConfigRail.tsx:730-734`) requires FOUR conditions, one of which is `route?.condition_agent
  === prev.id`. `prev.id` is always the normalized canvas-node-id form
  `"<agentBase>:<instance_id>"` (`custom-agent:ask` for the `ask` step — confirmed at
  `frontend/src/lib/manifestAgents.ts:114` and independently at
  `frontend/src/components/workflow/IdeaInputPage.tsx:1130`). But `route.condition_agent` is left
  as the manifest's RAW bare instance id (`"ask"`) because `normaliseRoute()` normalizes
  `outcomes[*].target` and `default_next` through `nodeIdOf` but never touches
  `condition_agent` — confirmed by reading BOTH copies of this function: the shared
  `frontend/src/lib/manifestAgents.ts:55-74`, and a still-live, un-migrated duplicate inside
  `frontend/src/components/workflow/IdeaInputPage.tsx:1100-1117`. The duplicate matters: it is
  the function that actually runs on THIS bug's exact repro path — `IdeaInputPage.tsx`'s primary
  manifest-fetch effect populates `manifestAgents`/`pipelineAgents` (which `ReviewGatesSection`
  and the canvas both render from) via its OWN local `normaliseRoute` at `:1100`, not the shared
  helper (the shared `agentsFromManifest` is only called from the `override` branch at `:1065`
  and a second effect at `:1469`). Either way, `"ask" !== "custom-agent:ask"`, so `promptUser` is
  always `false` and the Prompt User toggle never activates for any composed/custom-agent step
  using `condition_agent` — the one control designed to surface `before-human` is structurally
  broken by an id-format mismatch between the read (bare) and comparison (normalized) sides.

Manifest confirmation: `backend/agents/workflows/ex_A4_human_gate/workflow.yaml:104-115` —
`pick-language` declares `gates: [before-human, conditional]` and `route: {condition_agent: ask,
outcomes: {...}}`, `ask` being the bare instance id that both mechanisms above choke on.

Why the "Declared capabilities" panel (noted below) IS correct: it is built straight from
`detail.steps[].gates` — the compiled projection — at `IdeaInputPage.tsx:1040-1051`
(`setDeclaredCapabilities`), a THIRD, independent derivation that never touches `AgentDef.gate`,
`selections`, or `route.condition_agent`. This confirms the underlying data reaches the client
intact; all three purpose-built "does this step have a human gate" indicators are each broken by
a different narrow/stale source, not by a missing API field.

**Where the fix belongs:**
1. Mechanism A: land in `ReviewGatesSection.tsx`'s `checkedIds` initializer (`:92-96`) and re-seed
   effect (`:103-114`) — derive gated-state from `selections?.[a.id]?.gates` too, not just
   `initialGateIds`/`isDefaultGated`. This is the ONE shared component both `IdeaInputPage.tsx`
   and `LaunchWizard.tsx` render (both already thread a live `selections` prop into it post-
   FIX-346), so a fix here covers every caller without a per-page patch.
2. Mechanism B: `normaliseRoute()` needs to map `r.condition_agent` through `nodeIdOf` exactly
   like it already does for `outcomes[*].target`/`default_next` — but that one-line fix must land
   in BOTH the shared `manifestAgents.ts:55-74` copy AND the un-migrated `IdeaInputPage.tsx:1100-
   1117` duplicate, or fixing only the "obvious" shared helper leaves this exact route (and every
   other `/create/<built-in>` slug IdeaInputPage serves) still broken. The more durable fix is
   retiring the local duplicate in favor of the shared `agentsFromManifest()` call the rest of
   `manifestAgents.ts`'s own docblock says exists to prevent this drift — worth flagging to
   whoever fixes this, though the minimal correct fix is the parallel one-line patch.

**Invariants at risk for a naive fix:**
- ADR-0013 split `human` (post-step) from `before-human` (pre-step) as deliberately DIFFERENT
  gates, not aliases (`CanvasConfigRail.tsx:227-233`; `ReviewGatesSection.tsx:69-71`'s
  `withHumanGate` already carefully filters only `HUMAN_GATE = "human"`, carrying `before-human`
  through untouched). A Mechanism-A fix that makes the checklist show ANY declared gate as its
  one "human review" checkbox — without preserving that distinction — would silently re-merge
  what ADR-0013 split apart.
- FIX-346's own `locked_constraints`: "An untouched launch payload still omits `selections`
  entirely (INV-3) — the seed is display-only, only a user toggle writes." A Mechanism-A fix must
  stay a pure DISPLAY derivation from `selections`/`sel.gates` — it must not start writing into
  `gateSelectionRef`/`gate_agent_ids` as a side effect of merely rendering the seeded state, or an
  untouched run's launch payload stops being byte-identical.

## Expected vs actual

Expected: a step the backend manifest declares as carrying a `before-human` gate should
surface that fact in at least one of the two UI controls built to expose gate state — the
Review-gates checklist should show that agent checked, and/or the Gate combobox should
indicate the human-review gate is active in some way, rather than silently rendering as if
only the conditional gate exists.

Actual: both controls report the step as ungated for human review on first load. The
Review-gates checklist shows "no gates" / all unchecked; the Gate combobox shows only
"Conditional gate" selected, with no trace of `before-human` in either control (though a
separate "Declared capabilities" badge list on the same panel does show it).

## Related mechanism, but a distinct defect from ISS-247

[ISS-247](20260828-1637-ISS-247.md) documents that checking an agent in the Review-gates
checklist on `/create/app` does not sync to that same agent's Gate combobox in the Advanced
modal — a defect that requires a **user action** (checking a box) to trigger the desync.
This card (ISS-306) requires **zero interaction**: the seeded, already-gated fixture data on
`/create/ex_A4_human_gate` is misrepresented in both controls the instant the page loads,
and the Gate combobox's single-select model appears structurally unable to represent a step
that carries two gates simultaneously in the first place — there is no post-interaction
"desync" state to reach, because the correct state was never displayed to begin with.
