## What the decision actually is

Not "write integration tests". The decision is **how the suite is allowed to
report on itself**, and every rule below exists because a softer version of it
had already produced a false number.

The suite claimed 100% control coverage twice and measured 49% both times. The
response was not a bigger number but a gate: enumerate every addressable
control from source, link each to a scenario id, and fail the suite when the
enumeration and the scenario ledger disagree. A coverage figure that cannot
drift silently is worth more than a high one.

The same instinct produces the stub rule. 506 scenarios needed tests; one
function per scenario was generated so the spec-to-test link was complete from
day one — but every generated body carries `@pytest.mark.skip`. A stub that
passes is worse than no stub, because it converts an honest gap into a green
tick. `PROGRESS.md` therefore counts running, skipped and unwritten separately
and is regenerated, never edited.

## What it does not assert

Stated deliberately rather than left implied: this is an offline UI-contract
suite. It exercises real screens through a real browser against a real backend,
and it does not assert model output, deliverable quality, or anything requiring
a live provider call. The live tier is a separate gate.

## The costs accepted

- Generating 506 stubs means the repository carries 38 skipped tests at any
  time. That is the visible form of the honesty rule, not debt.
- Permanent scenario ids mean a deleted scenario leaves a hole in the
  numbering. Renumbering would break every cross-reference in the defect
  ledger, which is the more expensive failure.
