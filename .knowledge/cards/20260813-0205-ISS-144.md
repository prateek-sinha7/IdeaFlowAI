# ISS-144

## Title

**`POST /api/runs/{run_id}/answers` accepts a terminal run — no 409 guard, unlike `/gate`.** `backend/app/api/run_commands.py:327-352` (`submit_answers`) checks ownership (`_review_gate_owned_by`) before writing but has **NO terminal-run check**, unlike the sibling `POST /{id}/gate` (`:255-269`) which calls `_review_gate_run_is_terminal(gate_key)` and returns HTTP 409 `pipeline_not_running` — **that exact helper is already imported into the same module (`run_commands.py:82`) and simply not called on the `/answers` path.** Consequence: a clarify answer submitted against an already-cancelled run returns HTTP 200 `{"ok": true, ...}` and silently no-ops — the run does not resume (its queues, tasks and cancel-events were already torn down by `_cleanup_pipeline`), the user's answers vanish with no error shown, and `set_questionnaire_responses` re-creates a small dict entry plus a fresh `asyncio.Event` with no waiter and no eviction path per stray click — a minor per-click leak on a dead run. **Fix shape:** add the same `_review_gate_run_is_terminal(run_id)` -> 409 `pipeline_not_running` guard used by `/gate`, mirroring `run_commands.py:261-269`. **Open contract question, not yet decided:** should this endpoint 409 (matching `/gate`) or degrade some other way — 409 is recommended for consistency, but flag it as a product decision, not purely a bug.
