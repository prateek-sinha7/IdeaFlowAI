# ISS-872

**Register source:** `QA-KB-043` in root `LEDGER.md` / `BUGS.md` (sibling, derived during its analysis on 2026-10-01).
**Root card:** [ISS-105](20260812-1312-ISS-105.md) holds the root cause (nothing asserts how shutdown's snapshots and
counters behave when run state changes during its drain awaits). This card is the one product defect that missing test
would have exposed.

**Claim status: CONFIRMED by code read, REPRODUCED by an offline scratch probe, NOT yet by a repo test; impact INFERRED.**
The mechanism is read at the file:line below (line numbers at HEAD `024c03ef8`; the symbols are the stable handle). The
probe is `evidence/qa-kb-043/analyze-probe.py` (section 2; output in `analyze-probe-output.txt`). Impact is inferred:
the field is log-only (`app/main.py:419-420` logs the summary as JSON) and it over-counts, so anything sized from it
errs on the safe side.

## What is wrong

`shutdown_run_infrastructure()` builds its summary at entry, before any await (`backend/app/api/run_shutdown.py:79-96`):

```python
    summary: dict[str, Any] = {
        "event": "app_shutdown",
        "runs_in_flight": len(_PIPELINE_TASKS),
        ...
        "live_queues": len(_PIPELINE_QUEUES),
```

and, after every drain, derives the end-state figure from that entry-time number (`:218-224`):

```python
    # D9 measurability: runs left non-terminal here are exactly the set the next
    # boot's restore_non_terminal_runs will classify (branch b auto-resume /
    # branch c fail). This is the number the D9 semaphore must be sized against.
    summary["runs_left_for_boot_restore"] = (
        0 if settings.SHUTDOWN_STOP_RUNS else summary["runs_in_flight"]
    )
```

The comment says "left non-terminal here", which is an end-of-shutdown claim. Between the sample and the assignment the
function awaits up to 10 s (Concierge drain, `:105-107`) + 3 s (its cancel-and-wait, `:131-133`) + 3 s (pump drain,
`:170-172`) + 3 s (pump cancel-and-wait, `:183-185`) + 1 s (pool close, `:204`) = 20 s at the defaults
(`backend/app/core/config.py:318,321,326`). With `SHUTDOWN_STOP_RUNS` off (production) no driver is stopped or
cancelled in that window, so a run that completes naturally in it runs its driver `finally`
(`await event_queue.put(None)` then `_cleanup_pipeline(...)`: `_drive_launch_to_queue`, `run_commands.py:4422-4424`;
`_drive_revision_to_queue`, `:5845-5847`), which pops its `_PIPELINE_TASKS` entry, and the run goes terminal. It is
still counted as "left for boot restore".

The same entry-time sampling applies to `live_queues` (`:83`), `pump_tasks_in_flight` (`:91`), `cancel_events`,
`live_ectx` and `concierge_turns_in_flight`, but those are named for the entry state and are accurate as such. Only
`runs_left_for_boot_restore` claims an end state.

Second-order: `runs_in_flight` counts registry membership, not liveness. `_is_run_live` documents that a driver which
dies before its cleanup leaves a `done()` entry behind (`run_engine.py:147-165`), so even the entry count can include
finished tasks.

## Why the root cause implies it

[ISS-105](20260812-1312-ISS-105.md)'s mechanism is that shutdown reads the run registries and then awaits while drivers
and pumps keep running, and nothing asserts what the summary means under that interleaving. The registry snapshots were
made safe (no await between snapshot and use). The summary counters were never examined for the same time-of-sample
question. A test of the pre-snapshot window, which the root card now requires, is the first thing that would have shown
`runs_in_flight` and the end-state figure diverging.

## Expected vs actual

Seed four drivers, hold shutdown in step 1 with a pending Concierge task, let two drivers finish (`_cleanup_pipeline`)
and register one new queue, then release the Concierge task.

- Expected: `runs_left_for_boot_restore == 2` (the two drivers still registered).
- Actual: `runs_left_for_boot_restore == 4`.

## Evidence

Probe output (`evidence/qa-kb-043/analyze-probe-output.txt`, section 2; offline, `DATABASE_URL` pinned to throwaway
sqlite, `psycopg2 imported: False`):

```
summary: runs_in_flight=4 live_queues=4 queues_sentinelled=3 runs_left_for_boot_restore=4 concierge_persisted=1 errors=[]
drivers actually still registered after shutdown: ['run-a', 'run-c']
```

The two existing assertions on the field stay valid under the fix below: `backend/tests/unit/app/test_run_shutdown.py:190`
(`== 0`, stop-runs on) and `:214` (`== 1`, one pending driver, stop-runs off).

## Fix

One expression at `run_shutdown.py:222-224`: recompute at the end instead of reusing the entry sample, counting only
registry entries whose task is not finished, for example
`sum(1 for t in _PIPELINE_TASKS.values() if not getattr(t, "done", lambda: False)())`. `_PIPELINE_TASKS` is already
imported in that function. Keep `runs_in_flight` as the entry count and keep the `0 if settings.SHUTDOWN_STOP_RUNS`
branch. Treat anything not provably finished as left, the way `_is_run_live` does (`run_engine.py:182-190`).

## Fix (QA-KB-043, 2026-10-01, fixer)

Fixed by [FIX-682](20261001-2128-FIX-682.md). `backend/app/api/run_shutdown.py:222-232` now computes the field at
return: `0 if settings.SHUTDOWN_STOP_RUNS else` the count of `_PIPELINE_TASKS` entries that are not a `done()`
`asyncio.Task`. `runs_in_flight` stays the entry count. The count uses `isinstance(t, asyncio.Task)`, the same check
`stop_run_driver` uses in this file, rather than this card's `getattr` example: it cannot raise, and it keeps "not
provably finished counts as left". Observed with cwd `backend/`, running
`.venv/bin/python -m pytest tests/unit/app/test_run_shutdown.py -q -p no:cacheprovider`: before the edit,
12 passed and 1 xfailed. After it, 12 passed and 1 failed, the failure being `[XPASS(strict)] ISS-872 unfixed` on
this card's test, so the fix works. The xfail marker is left for the 6-verifier. Both existing assertions on the
field (`== 0` with stop-runs on, `== 1` for a pending driver with it off) still pass.
