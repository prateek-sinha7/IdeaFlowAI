## What happened

Bug QA-PS-028: the `backlog-compiler` agent (Delivery Compilation Agent, step 6 of
`user_stories`, prompt at `backend/agents/prompts/backlog-compiler/AGENT.md`) reads all prior
agents' outputs from `.agents/NN-agent-id.md` and compiles the final `user_stories.md`
deliverable. When it omits an entire epic present in `epic-architect`'s output, it never
mentions the omission — its own "Backlog Summary" totals (`Total Epics: N`) count only what it
included, and `pipeline_complete` still reports `agents_completed: 6/6` with no degraded state.
The run detail page shows "Done" / "Run complete 6/6 agents" with nothing indicating content
was dropped.

## Reproduction — 2 independent naturally-occurring cold instances (of 6 completed
`user_stories` runs examined in this DB), plus the reporter's own log-evidenced instance in
BUGS.md#qa-ps-028 (run `e2903536`, no longer present in this DB — rotated)

**Cycle 1 — run `a1a8c82a-8333-4fe8-8ea6-9d29ccfd01bc`** ("github dashboard user story")
- `epic-architect` output contains epic `# Epic: Customization & Sharing [P1]` with story
  "Create and Save Custom Dashboard Layouts" (verified via `GET /api/runs/a1a8c82a-.../
  agent_outputs`, and in the UI at `/runs/a1a8c82a-.../steps`).
- `backlog-compiler` output contains 0 occurrences of "Customization" anywhere.
- Its own `## Backlog Summary` states `**Total Epics:** 5` — the true upstream count was 3
  distinct epics in this run once merged/expanded, but the point is the summary counts only
  what shipped and gives no indication one architect-produced epic is missing.
- UI: `/runs/a1a8c82a-8333-4fe8-8ea6-9d29ccfd01bc` shows header status "Done", Steps tab shows
  "Run complete · 6 / 6 agents · 5m 35s" — no partial/degraded indicator anywhere.
- Evidence: `evidence/qa-ps-028/01-validate-attempt1-run-detail-loaded.png`,
  `evidence/qa-ps-028/02-validate-attempt1-backlog-summary-total-epics-5-no-omission-flag.png`,
  `evidence/qa-ps-028/03-validate-attempt1-steps-tab-run-complete-6of6.png`

**Cycle 2 — run `5efb67f9-1cc1-468b-befb-d205f1be0180`** ("github dashboard user story")
- `epic-architect` output contains `# Epic: Intelligent PR & Code Review Workflow [P0]` with
  story "Unified Code Review Queue".
- `backlog-compiler` output contains 0 occurrences of "Intelligent PR" anywhere.
- `backlog-compiler`'s `input_tokens` (28,853) is markedly lower than `nfr-specialist`'s
  (68,215) and `backlog-reviewer`'s (51,196) for the same run — the exact "not all upstream
  content was in context" signal the reporter's log evidence for `e2903536` already named.
- Its own `## Backlog Summary` states `**Total Epics:** 5`, again with no mention of the
  dropped epic.
- Evidence: `evidence/qa-ps-028/04-validate-attempt2-backlog-summary-total-epics-5-no-omission-flag.png`

**Cycle 3 — the reporter's own instance**, `e2903536` (BUGS.md#qa-ps-028): `epic-architect`
produced 4 epics including "SDK Integration Layer" (4 stories); `backlog-compiler` shipped only
3, said "I'll compile all the agent outputs," reported `Total Epics: 4, Total Stories: 18`
matching only what it kept, and `pipeline_complete.published_status` read `"completed"`.

Trigger: any time `backlog-compiler`'s context window does not carry the full content of one
or more upstream `.agents/NN-*.md` files — visible ahead of time as compiler `input_tokens`
well below the upstream agents that fed it — it silently omits the epic(s) it could not fit,
and nothing downstream (the compiler's own summary counter, or `pipeline_complete`) detects or
flags the gap. Out of 6 completed `user_stories` runs examined in this database, 2 exhibit the
drop — the trigger is intermittent/content-dependent, but when it fires the omission is never
flagged, which is the actual defect.

## Root cause

`backend/agents/prompts/backlog-compiler/AGENT.md` gives the agent a reading list
(`.agents/01-domain-analyst.md` … `.agents/05-backlog-reviewer.md`) and an output format, but
no structural requirement to enumerate and account for every epic id/title it read before
compiling — nothing tells it to cross-check its own output against the epic list it consumed,
and nothing forces it to report a count mismatch. The engine's `pipeline_complete` (see
`backend/app/models/run_finalization.py`, `backend/app/api/runs.py`) only checks that every
agent exited without raising — it has no post-completion diff between the compiler's declared
sources and its output, so `published_status` reads `"completed"` regardless of whether content
was dropped.

## Expected vs actual

Expected: the compiler either includes every upstream epic, or explicitly states what it
omitted and why, and the run's terminal status reflects a partial deliverable.

Actual: entire epics vanish from the final output with zero trace in the summary, the chat
transcript, or the run's terminal status — a user has no way to know content they were shown
mid-run (in `epic-architect`'s step output) did not make it into the deliverable they download.

## Root cause — engine-side gap (analyzer, file:line confirmed; corrects the citation above)

The validator's `## Root cause` above correctly identifies the agent-prompt half but cites
`backend/app/models/run_finalization.py` / `backend/app/api/runs.py` for the engine half —
read directly, neither contains a completeness check: `run_finalization.py` (60 lines, read in
full) is a passive SQLAlchemy model — it only declares the `published_status`/`candidate_status`
columns the finalizer writes into, no logic; `runs.py`'s `published_status` field (`:153-161`)
is a Pydantic response field mirroring the same DB column back out. The real mechanism is
elsewhere:

1. **Prompt-level (CONFIRMED, `backend/agents/prompts/backlog-compiler/AGENT.md` read in
   full).** The agent is told "Reading is your own responsibility — the engine does not inject
   these for you" and "Include ALL epics and stories from previous agents" — both are prose
   instructions to the model, never verified by anything. The five `.agents/NN-*.md` files it's
   told to read are always populated correctly regardless of what the compiler itself does:
   `write_agent_output` (`backend/app/agents/sandbox.py:1477`, called unconditionally from the
   shared per-step completion handler at `backend/agents/execution_engine/engine.py:9768`)
   persists every step's streamed output to `.agents/{NN}-{agent_id}.md` for every pipeline,
   independent of any `tools.write_files` grant. So the compiler always has the real upstream
   content on disk to read — whether it calls `read_file` on all five files, or reads them but
   drops content while composing, is a pure model-judgement choice with no engine-side check
   either way.

2. **Engine-level (CONFIRMED, read directly — the SAME block [ISS-721](20260922-1242-ISS-721.md)
   already root-causes for sibling bug QA-PS-027).** `_execute_impl`'s terminal completion gate,
   `backend/agents/execution_engine/engine.py:7376-7457`, is the ONE shared path every pipeline
   type funnels through (SC-001 — no `pipeline_type` branch anywhere in it). `_unrecovered_agents`
   (`:7381-7387`) is built only from `ectx.failed_invocations` (invocations that raised) minus
   completed `(agent_id, task_number, visit_count)` triples; `_pipeline_complete_data["status"]`
   becomes `"degraded"` only when that set is non-empty (`:7388-7390`), or on a budget-cap
   degrade (`:7415-7420`) or a blocked commit (`:7426-7427`) — `published_status` (`:7435-7457`)
   defaults to `"completed"` unless one of those three fired. A compiling step that returns
   normally after silently omitting an epic trips none of them.

## Scope correction — QA-PS-019 is not the trigger for this bug

`BUGS.md`'s own technical root-cause paragraph links the "compiler reads engine-reserved
`.agents/NN-agent-id.md` paths" behaviour to QA-PS-019 (the custom-workflow "Write files"
toggle granting nothing). That linkage does not hold for the cycles actually reproduced here:
all three (this card's two DB cycles plus the reporter's own) are `user_stories` runs — a
NATIVE pipeline. `_apply_selections`, QA-PS-019's own mechanism
([ISS-698](20260922-1001-ISS-698.md)), has exactly one call site
(`engine.py:4654`, inside `execute()`'s run-entry compile step) and
[ISS-733](20260922-1353-ISS-733.md)'s own blast-radius section confirms it is reached only by
`custom` and `custom_revision` runs — never `user_stories`. And per point 1 above,
`.agents/NN-*.md` files are populated by `write_agent_output` for every step of every pipeline
unconditionally, `tools.write_files` or not — reading from that path is simply how every
multi-step pipeline's downstream agents always work, not a QA-PS-019-driven fallback. This bug
reproduces identically whether or not QA-PS-019 is fixed.

## Blast radius

- **Prompt-pattern siblings** — grepped every `AGENT.md` whose frontmatter declares 3+
  `consumes` entries and is its pipeline's final (highest-`order`) step. Three share
  backlog-compiler's exact shape (a final "governance/handover" agent, manual `read_file`
  across every listed upstream `.agents/*.md` file, only a soft "cover everything" instruction,
  no structural checklist): `app-sdlc-governance` (`app_builder`, step 15/15, 6 upstream
  sources), `dotnet-sdlc-governance` (`dotnet_to_azure`, step 13/13, 5 upstream sources),
  `mulesoft-sdlc-governance` (`mulesoft_to_springboot`, step 13/13, 12 upstream sources, read
  directly — all three AGENT.md files quoted in full). See
  [ISS-772](20260922-1512-ISS-772.md).
- **Downstream propagation** — `user_stories_revision` is a real, reachable pipeline
  (`backend/agents/registry.py:147`, `REVISION_BASE_MAP["user_stories_revision"] =
  "user_stories"`) whose single step seeds the parent run's own `user_stories.md` verbatim
  (confirmed directly: `backend/agents/prompts/user-story-revision-agent/AGENT.md`, "The
  backlog under revision is seeded into your sandbox as `user_stories.md`") and is contracted
  to "PRESERVE every other epic, story... exactly as-is." A revision launched against a parent
  run this bug already hit inherits the gap with no new signal. See
  [ISS-773](20260922-1512-ISS-773.md).
- **The shared engine-side gap (point 2 above) is systemic** to every pipeline type and every
  `_revision` variant — already fully blast-radius'd by [ISS-721](20260922-1242-ISS-721.md)
  (its own [ISS-761](20260922-1424-ISS-761.md) native-pipeline and
  [ISS-762](20260922-1425-ISS-762.md) revision-pipeline siblings cover that ground; not
  re-derived here).
- Not re-scoped further: ~80 agent prompts exist in this repo; only the four highest-fan-in
  "final synthesis" roles were checked directly against backlog-compiler's exact pattern.

## Fix direction (not applied by this card — analysis only)

Two independent layers, neither alone sufficient:

1. **Detection — belongs in the same shared block ISS-721 already names**
   (`_execute_impl`'s completion gate, `engine.py:7376-7457`, beside the existing
   `budget_degraded_reasons`/`last_commit_blocked` signals). One guard here — e.g. a compiling
   step emits a machine-checkable manifest of the source items it accounted for, diffed against
   what its declared upstream sources actually produced — covers every pipeline and every
   compiler-shaped agent in one place, the same way the existing three signals already do.
   Whoever implements ISS-721's placeholder-detection fix should design it to also catch THIS
   shape of gap: QA-PS-028's own evidence (a 19,581-char, 5,093-output-token compiled document)
   shows a length/duration heuristic alone — ISS-721's own proposed default — would NOT flag a
   substantial document that is merely missing one section.
2. **Prompt-side, cheaper but partial** — give backlog-compiler and the
   [ISS-772](20260922-1512-ISS-772.md) sibling agents a structural self-check ("list every
   epic id/title read from each source file before writing the summary; Total Epics MUST equal
   that list's length"). Raises the bar on the model's own behaviour but verifies nothing —
   not a substitute for #1.
