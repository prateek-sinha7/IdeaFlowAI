## Description

Validated from bug register entry **BUG-20260828-074900-workflow-r2**. On `/workflow`
(the standalone legacy workflow builder rendered by `WorkflowView.tsx`, reached directly
via the `/workflow` route — distinct from the newer `/create/<type>` launch panel), the
"Attach file" control and its chip's remove ("x") button are asymmetric:

- **Attach** (`WorkflowView.tsx` file `<input>` `onChange`, ~line 328-343): pushes the
  file into `attachedFiles` state AND appends a literal `[Attached: <filename>]` marker
  into `ideaInput` (the brief textarea's backing state) via `setIdeaInput`.
- **Remove** (chip's `onClick`, ~line 388): only does
  `setAttachedFiles((prev) => prev.filter((_, i) => i !== idx))` — it never touches
  `ideaInput`, so the `[Attached: ...]` marker it had written stays in the textarea
  permanently after the visual chip is gone.

Because `handleRun`'s enable gate for the "Run Workflow" button reads only
`ideaInput.trim()` (the same field ISS-328 already flags as ignoring
`pipelineAgents.length`), the button stays enabled off this now-orphaned marker text
even though the attachment no longer exists and the workflow has 0 agents.

## Reproduction (validated 2026-08-28, 3/3 cold starts)

Each cycle from a cold start: fresh navigation `/dashboard` -> `/workflow` (qa-admin,
already-authenticated session; not a soft re-click of the same screen).

1. Navigate to `http://localhost:3000/workflow`. Textarea empty, "Run Workflow" disabled.
2. Click "Attach file (PDF, DOCX, PPTX, TXT)", upload a small `.txt` file. Direct DOM read
   of `textarea.value` confirms `[Attached: <filename>]`; a removable chip
   `<filename> (<size>)` renders below the field; `runButton.disabled` becomes `false`.
3. Click the chip's "x" button. The chip disappears from the DOM/snapshot.
4. Re-read `textarea.value` directly: still exactly `[Attached: <filename>]`.
   `runButton.disabled` is still `false` — enabled for a workflow with 0 agents and no
   attachment, keyed purely on the orphaned marker text.

Reproduced identically on all 3 cycles (cycle 1: `zz-hunt-r2-c1.txt`, cycle 2:
`zz-hunt-r2-c2.txt`, cycle 3: `zz-hunt-r2-c3.txt`), each from an independent cold
`/dashboard` -> `/workflow` navigation. No axis variation was needed — the trigger
reproduces unconditionally: any attach-then-remove cycle on this page.

## Expected vs Actual

Expected: removing an attachment via its chip's "x" reverses the attach action fully —
the `[Attached: ...]` marker it injected is also cleared (or, if the textarea has other
real user-typed content, only the marker segment is stripped) — and "Run Workflow"
reflects the workflow's real state.

Actual: the remove control deletes only the chip/array entry; the marker string stays in
`ideaInput`/`textarea.value` forever, misrepresenting the brief and keeping "Run Workflow"
enabled for a phantom attachment.

## Root cause

`frontend/src/components/workflow/WorkflowView.tsx`:
- Attach path (~line 337-340): `setAttachedFiles((prev) => [...prev, ...newFiles]);` then
  `setIdeaInput((prev) => prev ? \`${prev}\n\n[Attached: ${fileNames}]\` : \`[Attached: ${fileNames}]\`);`
- Remove path (~line 388): `onClick={() => setAttachedFiles((prev) => prev.filter((_, i) => i !== idx))}`
  — no corresponding `setIdeaInput` call to strip the marker it added.

The two paths mutate `ideaInput` and `attachedFiles` as if they were one linked state,
but only the add direction keeps them in sync.
