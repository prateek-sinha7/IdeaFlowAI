## What was wrong

Resolves [ISS-374](20260828-2146-ISS-374.md) and
[ISS-375](20260828-2147-ISS-375.md) — the register entry
`BUG-20260828-001720-workflow-create-prototype`.

`/workflow/create?mode=nonsense` redirects to `/create/nonsense`, which renders a
normal-looking "Provide the brief" screen whose Save workflow / Save as my version /
Run buttons are disabled forever, no matter what brief is typed. The only trace of
the failure was a console `GET /api/workflows/nonsense 404`. Observed on the running
dev server before the change, `document.body.innerText` on `/create/nonsense`
contained no "not found", "failed to load" or "error" text anywhere.

[ISS-375](20260828-2147-ISS-375.md) is the same screen reached from the other side:
a REAL workflow (`custom` — `GET /api/workflows/custom` returns 200 with 9 steps,
confirmed with a qa-admin bearer) whose one detail request fails transiently lands in
the identical silent dead end, because the catch never asked which failure it was.

## Root cause

`frontend/src/components/workflow/IdeaInputPage.tsx:1181-1190` (pre-change
`1172-1181`) — the manifest fetch's `.catch()` mapped every rejection to "nothing
declared":

```ts
.catch(() => {
  if (!cancelled) {
    setDeclaredCapabilities(undefined);
    setManifestAgents(undefined);
    setManifestSelections(undefined);
    setManifestRawSteps(undefined);
  }
});
```

That is correct for the SURF-03 capability strip it was written for, but the same
`manifestAgents` feeds the roster: at `IdeaInputPage.tsx:1259` the roster effect
computes `systemRoster = libraryIsComplete ? fromLibrary : (manifestAgents ?? fromLibrary)`,
which for a pipeline_type no `AGENT.md` declares is `undefined ?? []` = `[]`. Every
action is gated on `pipelineAgents.length === 0` (`IdeaInputPage.tsx:1658,1673,1684`),
so the screen disables itself permanently and says only "Add agents first".

Blast radius re-grepped before editing; [ISS-374](20260828-2146-ISS-374.md)'s table
still holds exactly — six real `getWorkflowDetail` call sites, unchanged in count and
location. `page.tsx:452-499` and `ComposerPage.tsx:410-439` were deliberately left
alone per that card's items 3 and 4 (the first belongs to
[ISS-299](20260828-1730-ISS-299.md), the second gates nothing).

## What changed and why there

**`frontend/src/lib/api.ts`** — one exported predicate beside the `ApiError` class
it reads:

```ts
export function isNotFoundError(e: unknown): boolean {
  return e instanceof ApiError && e.status === 404;
}
```

`ApiError` already carried `status` but is not exported, so no caller could tell
"does not exist" from "could not load right now" without re-deriving it. The
predicate is the shared piece [ISS-374](20260828-2146-ISS-374.md) asked for; it lives
in `api.ts` because that is the only module that can see the class.

**`frontend/src/components/workflow/IdeaInputPage.tsx`** — a `loadError` state
carrying WHICH failure it was (`"not-found" | "failed" | null`), cleared on the
effect's two early returns and on success, set in the existing catch via
`isNotFoundError(e)`, and rendered beside the disabled buttons next to the `saveError`
line the file already had:

```tsx
{loadError && pipelineAgents.length === 0 && !isMigrationMeta && (…)}
```

Fixed in the catch rather than at the route or in the roster effect because the catch
is where every failure of this fetch converges — the roster effect only sees the
`undefined` the catch left behind, and the route cannot know whether an id exists.
The state carries the case rather than being a boolean because
[ISS-375](20260828-2147-ISS-375.md) is precisely the distinction: a 404 has no useful
retry ("go back and pick one from the dashboard"), a transient failure does ("reload
the page to retry").

The render is gated on `pipelineAgents.length === 0` — [ISS-374](20260828-2146-ISS-374.md)'s
own condition, "the fetch failed AND there is no recovery path". `isMigrationMeta` is
excluded because `migration` is the single `WorkflowType` with no workflow of its own
(it 404s BY DESIGN — verified against `GET /api/workflows/{id}` for every member of the
union: only `migration` is not a real id) and its recovery is picking a sub-path, not
reloading. Without that clause the banner would have appeared on a perfectly healthy
screen.

`LaunchWizard.tsx:395`'s catch was NOT converted to the predicate even though
[ISS-374](20260828-2146-ISS-374.md) item 2 sweeps broadly: its `mode` is a closed
union, its fallback roster is always non-empty, and the card's own blast-radius table
marks it "not reachable in a broken state" — changing it would alter no behaviour and
is covered by no test.

## Observed, NOT fixed, NOT mine

- **The second test in each verification file asserts a different remedy from the one
  its card chose, and both still xfail.**
  `test_unrecognized_slug_does_not_permanently_disable_save_after_brief` and
  `test_transient_fetch_failure_on_real_workflow_does_not_dead_end` require
  `Save workflow` to become ENABLED. [ISS-374](20260828-2146-ISS-374.md) §Fix and
  [ISS-375](20260828-2147-ISS-375.md) §Fix both specify surfacing the error, not
  recovering a roster — [ISS-253](20260828-1646-ISS-253.md) framed it as an either/or
  ("surface an explicit error **or** fall back to a working default") and the analysis
  picked the first branch. Enabling Save for `/create/nonsense` would mean inventing a
  roster for a workflow that does not exist. For `/create/custom` it is impossible
  without breaking KAN-112: `IdeaInputPage.tsx:1246-1247` sets `pipelineAgents = []`
  for `effectiveType === "custom"` unconditionally, by design ("custom workflow starts
  blank — user picks agents themselves"), so that test's Save button is disabled on a
  fully successful fetch too. Neither test was edited. Choosing the fallback branch
  instead is a product decision, not a fix.
- The run button still reads "Add agents first" underneath the new banner. Correcting
  that label for the failed-load case is copy work no card asked for.
