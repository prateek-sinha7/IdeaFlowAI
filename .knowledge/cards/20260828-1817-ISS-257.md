## What is suspected

[ISS-224](20260828-1735-ISS-224.md)'s backend half is not specific to
`GithubPATRequest.pat` — it is the absence of ANY `RequestValidationError` handler in the
FastAPI app, which is a repo-wide gap, not a per-route one. **Confirmed:**
`grep -rn "RequestValidationError\|exception_handler" backend/app/` returns nothing, and
`backend/app/main.py` was read in full: it registers `CORSMiddleware` and one request-id
middleware (`:295-325`) and no `@app.exception_handler` of any kind. So Pydantic's default 422
handler — which embeds the complete rejected value in `detail[].input` — fires for **every**
length/pattern-constrained field across all 20 routers `main.py` includes, not only `settings.py`.
The one other field found in this pass that holds a genuine credential (rather than a name,
title or content blob) is `RegisterRequest.password`. **INFERRED** — no request was actually
sent to `/api/auth/register` in this session.

## Root cause — the same missing-handler gap, a second field

**Confirmed by file:line read:**

- `backend/app/models/schemas.py:16`: `password: str = Field(..., min_length=8)` on
  `RegisterRequest`.
- `backend/app/api/auth.py:74`:
  `def register(request: RegisterRequest, db: Session = Depends(get_db)):`. FastAPI validates
  the body against `RegisterRequest` **before** this function body runs, so the 422 (and the
  password echo) fires even though the handler itself unconditionally then returns 403
  "Self-registration is disabled" (`auth.py:74-89`) — the docstring explicitly keeps the
  Pydantic model bound to the route "so malformed bodies still 422 rather than 403, which is the
  more helpful failure mode for the client." Nothing in `main.py` intercepts that 422 to redact
  it, identically to ISS-224's `GithubPATRequest.pat` case.

**Reachability caveat, checked and worth recording honestly:** a search of `frontend/src/app`
and `frontend/src/components` in this session found no live caller of `register()`
(`frontend/src/lib/api.ts`), and per [ADR-0021](20260806-ADR-0021.md) auth moved to Amazon
Cognito — self-registration through the product's own UI may be fully retired. If so, the
exposure is to a direct API caller (a script, an old client, a proxy or log capturing the
request), not the product's own browser UI — still a real instance of the same "never echo a
rejected secret" gap ISS-224 raises, just reached by a different entry point than the browser.

## Why the root cause implies this

ISS-224 traces its backend leak to the *absence* of a custom `RequestValidationError` handler —
a property of `main.py`, not of `settings.py`. Any other `Field(..., min_length=...)` /
`max_length=...` constraint on a value that is itself sensitive inherits the identical leak the
moment a caller submits a value that violates it. A check of the three other password-shaped
models in the API (`ChangePasswordRequest`, `ResetPasswordRequest`,
`ConfirmForgotPasswordRequest` — `backend/app/api/auth.py` / `admin.py`) found none carries a
length constraint today, so only `RegisterRequest.password` currently trips this mechanism.

## Expected vs actual (once reproduced)

- **Expected:** a rejected password is never echoed back in any response body, mirroring the
  guarantee ISS-224 quotes for the PAT card.
- **Actual (predicted):** the full submitted password string appears verbatim in the `422`
  response body's `detail[].input`.

## What would confirm or refute this

`POST /api/auth/register` with a body like `{"email":"x@example.com","password":"short"}` (curl,
or the frontend `register()` call if a live caller is found) and read the response body for
`detail[].input`.
