## Description

Validated from bug register entry **BUG-20260828-053745-create-app-r2**. On
`/create/app` (renders the simple launch panel, "Provide the brief"), attaching a
plain-text-type file (`.txt`/`.md`/`.json`/`.csv`) whose content exceeds the
450,000-character `ATTACH_MAX_CHARS` limit (`frontend/src/lib/constants.ts`) has its
content silently sliced to that limit before being sent in the run payload, with no
indication anywhere in the UI (chip, toast, or the sent brief text itself) that
truncation occurred.

Root cause: `frontend/src/components/workflow/IdeaInputPage.tsx` `handleFiles()` has two
sibling branches for the same operation that diverge in observability. The `isTextFile`
branch (`.txt/.md/.json/.csv`, ~line 512-520) does `content.slice(0, ATTACH_MAX_CHARS)`
directly with no truncation flag or note. The `isBinaryFile` branch (`.pdf/.docx/.pptx`,
~line 524-530) calls `extractFileText()` server-side and appends
`` `\n[Content truncated to ${ATTACH_MAX_CHARS.toLocaleString()} chars]` `` to the content
block whenever `res.truncated` is true. Both paths hit the identical 450,000-char limit;
only the binary path tells anyone it happened. The file-chip render (~line 629) shows
only `file.name` for either path — no size, no truncation state — so there is no
secondary signal either.

## Reproduction (validated 2026-08-28, 3/3 cold starts — first cycle already reproduced it)

Each cycle from a cold start: fresh navigation `/dashboard` → `/create/app` (qa-admin,
already-authenticated session; no soft re-click of the same screen).

1. Navigate to `http://localhost:3000/create/app`.
2. Fill the brief textbox: "Summarize the attached notes into user stories."
3. Click "+ Attach file", upload a `.txt` file containing 500,000 `'a'` characters
   (`huge.txt`, well over the 450,000-char `ATTACH_MAX_CHARS` limit).
4. Screenshot the attachment chip: filename only, no size, no warning
   (`02-revalidation-cycle1-chip.png`, `03-revalidation-cycle3-chip.png`).
5. Click "Run workflow" with `page.route('**/api/runs')` installed to capture and abort
   the outgoing `POST /api/runs` request client-side (no real run created).
6. Inspect the captured body: length is exactly **450,236** characters (450,000 sliced
   file content + wrapper text), the string ends `...aaaa\n=== End: huge.txt ===` with no
   truncation marker anywhere, and `body.toLowerCase().includes('truncat')` is `false`.

Cycle 1: body length 450236, containsTrunc `false`. Cycle 2 (fresh `/dashboard` →
`/create/app` reload): identical, body length 450236, containsTrunc `false`. Cycle 3
(fresh reload again): identical, body length 450236, containsTrunc `false`. All three
cycles produced byte-identical results — deterministic, not a race; no axis variation was
needed.

## Expected

When a text-type attachment's content is cut to fit `ATTACH_MAX_CHARS`, the user should
see the same visible signal the binary (`.pdf`/`.docx`/`.pptx`) path already provides —
either a truncation note appended to the sent content, a visible warning near the file
chip, or outright rejection of files over the limit with a clear error.

## Actual

The content is silently sliced with `content.slice(0, ATTACH_MAX_CHARS)` and stored with
no truncation flag or note. The file chip shows only the filename. Nothing in the UI or
the payload sent to the agent indicates data was dropped.

## Root cause pointer

`frontend/src/components/workflow/IdeaInputPage.tsx` `handleFiles()`: `isTextFile` branch
(`.txt/.md/.json/.csv`) does `content.slice(0, ATTACH_MAX_CHARS)` with no truncation note;
`isBinaryFile` branch (`.pdf/.docx/.pptx`) calls `extractFileText()` and appends a visible
`[Content truncated to N chars]` note when `res.truncated` is true.
`ATTACH_MAX_CHARS = 450000` in `frontend/src/lib/constants.ts`.

## Blast radius (analyzer pass, 2026-08-29)

`handleFiles()` lives inside the exported `useBriefAttachments()` hook (`IdeaInputPage.tsx:476-572`),
whose own doc comment states it is shared so "BOTH IdeaInputPage and ComposerPage's Simple view
mount the SAME attach/extract logic (INV-3, no forked implementation)". Confirmed consumers —
`grep -rln "useBriefAttachments\|BriefAttachBox" frontend/src`:

- `IdeaInputPage.tsx` itself — reached not only at `/create/app` but at every other pipeline type
  that renders it: `/create/user_stories`, `/create/mulesoft_to_springboot`,
  `/create/dotnet_to_azure` (confirmed via [FIX-304](20260825-2115-FIX-304.md): `LaunchWizard`'s
  `MODE_CONFIG` only covers `"prototype" | "ppt"`, every other built-in renders `IdeaInputPage`).
- `frontend/src/components/workflow/composer/ComposerPage.tsx` — BOTH its Simple view
  (`BriefAttachBox` at :1213, `useBriefAttachments()` at :240) and its Canvas view (the same
  `briefAttachments`/`briefText` state passed into `CanvasView` at :1144-1175) — this is the
  workflow composer (`mainView === "composer"` in `DashboardLayout.tsx`), a different page than
  `/create/app`. One fix inside `handleFiles()`/`useBriefAttachments()` covers all of the above —
  they are all the SAME function instance, not separate implementations.
- `frontend/src/components/workflow/AgentsPopup.tsx:2325` also calls `useBriefAttachments()` for
  its embedded `CanvasView`'s Brief node, but that instance is explicitly documented as
  "decorative... local-only... never read or persisted from here" (:2319-2324) — its content is
  never sent, so while the same code path executes, there is no data-loss consequence. Lower
  priority; not carded separately.

**A second, un-shared implementation exists**, filed as its own sibling since it needs its own
fix: [ISS-423](20260829-0026-ISS-423.md) (`LaunchWizard.tsx`, serving `/create/ppt` and
`/create/prototype` — the two pipeline types `IdeaInputPage` does NOT cover).

**A third, adjacent implementation** in the concierge chat lane (`useChatAttachments.ts`) computes
a `truncated` flag correctly but drops it before it reaches the user or the backend prompt —
different mechanism, same symptom family: [ISS-422](20260829-0027-ISS-422.md).

**Where the fix belongs:** `IdeaInputPage.tsx`'s `isTextFile` branch (:514-523) needs its own
`content.length > ATTACH_MAX_CHARS` check and a note appended, mirroring the `isBinaryFile`
branch immediately below it — fixing this ONE spot covers `/create/app`, `/create/user_stories`,
`/create/mulesoft_to_springboot`, `/create/dotnet_to_azure`, and both ComposerPage views. Since
`LaunchWizard.tsx:653-659` has the textually identical branch, the smallest correct fix extracts
one shared helper (e.g. in `frontend/src/lib/constants.ts` next to `ATTACH_MAX_CHARS`) that both
files' `isTextFile` branches call, rather than hand-patching the logic twice.
