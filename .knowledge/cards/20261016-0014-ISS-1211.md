# ISS-1211

## Symptom

On the dev server the Admin → Machines tab listed the instance but showed no instance details: STATE `UNKNOWN`, GATE `BLIND`, CPU %, MEMORY % and READING AGE empty, TYPE `—`. No error was logged.

## Root cause

- `infra/scripts/reconcile-host-config.sh` (CW agent heredoc, `append_dimensions`) publishes every metric with `InstanceId` + `InstanceType` (and `cpu=cpu-total` for CPU). There was no `aggregation_dimensions`, so no `InstanceId`-only series existed.
- `backend/app/services/host_metrics.py` `collect_readings` queries `dims = [{"Name": "InstanceId", ...}]`. CloudWatch matches dimension sets exactly, so `GetMetricData` succeeded with zero datapoints, every reading was `None`, and `capacity_state` classified the host as unknown/blind (fail-open, by design).
- `host_metrics.py` hardcoded `instance_type=None`, so TYPE always rendered `—` even though the API and `CapacityMatrix.tsx` carry the field end to end.

Evidence (from `.agents/tasks/dev-machines-instance-blind-rca.md`): verified — `list-metrics` shows only the full-dimension series; a `get-metric-statistics` query with `InstanceId` alone returns no datapoints while the full set returns data. Inferred — the same mismatch affects every environment that runs this agent config.

## Side effect

The dev cpu-high, mem-high, disk-root-high and disk-data-high alarms in `infra/terraform/modules/monitoring/main.tf` (`:480-483`, `:505-508`, `:530-533`, `:556-559`) query `{InstanceId}` / `{InstanceId, path}` with `treat_missing_data = "breaching"`, so they sat in a false ALARM.

## Fix

- Agent rollup: `"aggregation_dimensions": [["InstanceId"], ["InstanceId", "path"]]` in the agent `metrics` section. Originals are still sent; about 20 extra custom metrics per instance. The list matches the alarm dimension sets exactly, so `main.tf` is unchanged.
- Instance types: from `DescribeInstances` (discovery, or the override cross-check, which now runs once per inventory TTL instead of every tick), with an IMDSv2 `instance-type` fallback for self.
- Observability: one WARNING per instance when `GetMetricData` succeeds but every series is empty, and one INFO when data resumes; no per-tick spam.

## Rejected option

Changing the app's query dimensions to the agent's full `append_dimensions` set: it couples the app to agent config (InstanceType, `cpu`) and leaves the alarms broken.

## Post-deploy verification

1. `aws cloudwatch get-metric-statistics --namespace VelocityAI/Dev --metric-name mem_used_percent --dimensions Name=InstanceId,Value=<id> ...` returns datapoints; `list-metrics` shows an `[InstanceId]`-only entry.
2. Machines tab shows TYPE (e.g. `m6i.xlarge`), STATE OK, real CPU/memory/reading age, GATE ALLOWING.
3. The dev cpu/mem/disk alarms return to OK.
4. Container logs do not show `host_metrics: GetMetricData returned zero datapoints`.

The "Disabled" badge is by design (`HOST_CAPACITY_GATE_ENABLED`).
