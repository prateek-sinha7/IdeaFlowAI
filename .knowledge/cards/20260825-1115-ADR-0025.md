## Decision

The composer canvas positions root nodes with a hand-rolled **Sugiyama layered
graph drawing** algorithm in
`frontend/src/components/workflow/composer/graphLayout.ts`
(`computeRootLayout`). The full contract lives in
`specs/014-conditional-gates/canvas-spine-fan-layout.md`.

## Why not a tree algorithm

`treeLayout.ts` implements Reingold-Tilford tidy-tree layout and is **correct
for the sub-agent tree**, which really is a tree. It must NOT be generalised to
the root graph, because the root graph is a **DAG with back-edges**:

- a node can have two parents — in a `gate -> deep -> refactor` shape,
  `refactor` is also the target of a later gate's `fail` loop;
- back-edges exist by design (spec 014 R-06/R-07 conditional loops).

An earlier revision of the layout spec told an implementer to apply
Reingold-Tilford to the root graph. That was wrong and was retracted.

## The model

**Spine** = the major axis the main chain runs along (horizontal today, left to
right). **Fan** = everything a gate opens, distributed perpendicular to it,
symmetric about the gate. A vertical spine is the same formula with the axes
swapped, so the transpose must stay a one-line change.

Sugiyama phases, and what each one owns:

| Phase | Owns | Technique |
|---|---|---|
| 1. Cycle removal | back-edges | reverse them so the graph is a DAG |
| 2. Layer assignment | DEPTH (column) | `col(n) = 1 + max(col(pred))`, longest-path |
| 3. Crossing reduction | BREADTH ORDER (a permutation) | barycenter/median, 2-4 sweeps |
| 4. Coordinate assignment | BREADTH COORDINATE | Brandes-Koepf median alignment + compaction |

Dummy nodes split any edge spanning more than one layer, one per intermediate
layer, so long edges stay straight instead of cutting diagonally.

Phase 4 is where fan centring and pitch come from, and they are
**consequences, not requirements**: a gate IS the median neighbour of its own
outcome group, so median alignment centres the fan on the gate automatically.
Do not add a post-hoc correction pass to enforce centring — every attempt to
do so in this module produced a worse layout (see
[FIX-297](20260825-1115-FIX-297.md)).

## The one deliberate deviation: size-aware separation

Textbook Sugiyama assumes uniform node sizes. Ours are not — a root step card
is ~243px tall as measured, an external workflow node is `EXTERNAL_NODE_H = 58`.
So layer-adjacent separation is:

```
sep(u, v) = (height(u) + height(v)) / 2 + ROW_GAP
```

`ROW_GAP = 64`. Dagre does the same thing (`nodesep` applies on top of
half-heights, never instead of them).

**Heights must be MEASURED, not estimated.** `ROOT_H_EST = 176` in
`treeLayout.ts` is explicitly "approximate ... exact height varies with
content" — a card grows with a ROUTE row or extra chips. `rowPortOffset * 2`
(CanvasView's `nodeCenterY` measuring effect) is the real height and is passed
into `computeRootLayout` as `cardH`; CanvasView then pushes that height onto
every root card as a min-height, so all root cards genuinely are `cardH` tall.
Using the estimate under-separates every fan by `cardH - ROOT_H_EST`.

## No new dependency

`treeLayout.ts:5-7` records that its algorithm was "reimplemented by hand so
the canvas stays dependency-free", and `specs/015-frontend-routing/plan.md:43`
generalises it: this codebase "prefers hand-rolled solutions over pulling in
libraries where avoidable". Honour that — do not add dagre, elkjs or d3-dag.

Hand-rolled does NOT mean invented. Implement the NAMED phases, keep the phase
boundaries visible, and cite the algorithm in comments so the next engineer
recognises it rather than re-deriving it. Justified simplifications are fine if
stated in a comment (longest-path instead of network simplex; median heuristic
with a few sweeps instead of optimal crossing minimisation).

## Invariants a layout change must preserve

- **I1** no two node boxes intersect, heights included
- **I2** no negative `x`/`y`; nothing outside the content area
- **I3** each fan is centred on its gate on the minor axis
- **I4** consecutive fan separation equals the `sep()` formula (uneven pitch is
  CORRECT when heights differ)
- **I5** no slack beyond the formula — no nudge loops
- **I6** fan members in declared outcome order
- **I7** deterministic: same graph in, identical coordinates out

Assert these over **computed layout values**. `jsdom` has no layout engine —
`getBoundingClientRect()` returns all zeros there, so assertions phrased on
real pixel geometry are vacuous.

## Auto-arrange

Auto-arrange IS this formula. Because it is also the DEFAULT layout, an opened
workflow is already arranged with no click and no flash-then-rearrange. The
button recomputes and may discard manual drag overrides; normal renders must
not discard `dragOverrides`.
