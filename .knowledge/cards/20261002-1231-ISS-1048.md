# ISS-1048

**INFERRED, not reproduced.** I read each link of the chain below in source on 2026-10-02 (working tree, branch `feat/user-stories-v2`). Nobody has opened such a URL and looked at the request it sends.

The analysis on [ISS-472](20260829-0110-ISS-472.md) first flagged this as a hazard ("Hazards for the fixer"). I filed it as its own card when [FIX-716](20261002-1230-FIX-716.md) resolved ISS-472, so the hazard is not lost with that card.

## Condition

A saved workflow that is neither a composer row nor a wizard type, opened at `/workflows/{id}/run` by URL (typed, refreshed or shared). Examples are a row with `base_pipeline_type` `app_builder`, `backlog` or `user_stories`. Composer rows and `prototype*`/`ppt*` rows take other branches.

## Why (each step read)

1. `initialWorkflowTypeFor` (`page.tsx:386-397`) maps only `create-app`, `create-user-stories` and `create-workflow`, so it returns `undefined` for `workflow-run`.
   - `page.tsx:4250` passes `initialWorkflowTypeFor(parsedView) ?? builtinCanvasType` down, which is also `undefined` on this route.
   - [BUG-025](20260827-BUG-025.md)'s route table recorded the same seed: `/workflows/{id}/run` gets "undefined, so `"user_stories"`".
2. `DashboardLayout`'s `workflowType` initializer (`DashboardLayout.tsx:632-642`) then falls back to `"user_stories"`. The only exceptions are a pending prototype or ppt staged in `sessionStorage`.
3. The cold-mount fetch for this route (`page.tsx:3929` onward) does not supply a type for the non-wizard branch. It sets `initialSavedComposition` (agent ids, brief, selections; `:4002`) and `setWorkflowRunMainView(isComposerWorkflow(saved) ? "composer" : "input")` (`:4022`), but never `saved.base_pipeline_type`.
   - A comment in the same function (`:3950-3955`) describes this outcome for an earlier variant: the generic brief panel "renders the user_stories copy ... for a saved PRESENTATION".
4. `IdeaInputPage` therefore mounts with `workflowType="user_stories"` and `workflowId="user_stories"` (`DashboardLayout.tsx:3185`, `workflowId={workflowType}`), plus the saved agent ids as `initialAgentIds`.
   - `effectiveType` is `user_stories`.
   - `handleRun` dispatches `resolveDispatchType(pipelineAgents, effectiveType).type`. That function returns its base type unchanged unless the type is `custom`, so the dispatch is `user_stories` with the saved row's agent ids.
5. [FIX-716](20261002-1230-FIX-716.md)'s tier lock uses the same `effectiveType`, and `user_stories` is entitled on every tier. On this route the lock never engages. This is not a regression: before FIX-716 there was no lock at all.

**Possibly reached by a click too (INFERRED).** My Workflows' "Run workflow" calls `handleLaunchSaved`. It sets `setWorkflowType(saved.base_pipeline_type)` (`DashboardLayout.tsx:1746`) and then calls `router.push(routes.workflowRun(saved.id))` (`:1757`). BUG-025 (point 3) and [ISS-916](20261001-2220-ISS-916.md) read that a push under the `[...view]` catch-all remounts `page.tsx`. If so, the type set before the push is discarded, and the click lands in the cold state above.

[FIX-713](20261002-1158-FIX-713.md) fixed this for `ComposerPage` only: the composer derives `builtinCanvasType || "custom"` itself. The Input panel still reads the shared `workflowType`.

## Expected vs actual

- **Expected:** the panel runs, gates and labels as the saved row's `base_pipeline_type`.
- **Actual (derived):** the panel shows the `user_stories` copy, the backend receives `pipeline_type: "user_stories"` with the saved agent ids, and the tier lock tests `user_stories`.
  - Not read: what the backend does with that pair. It might return 400 `invalid_agent_ids`, or run `user_stories` with foreign agents.

## What settles it

1. Sign in as `admin@velocity.ai` and save an `app_builder` workflow from `/create/app` ("Save workflow").
2. Open `/workflows/{its id}/run` by URL, type a brief and press Run.
3. Read the `POST /api/runs` body for `pipeline_type`.

An offline check is also possible: a page-level vitest that resolves `userWorkflowsApi.get` with an `app_builder` row and reads the `workflowType` passed to the Input panel.

## Where the fix probably belongs (not analysed)

`page.tsx`'s cold-mount fetch already holds `saved.base_pipeline_type`, as `handleLaunchSaved` does. `DashboardLayout`'s `workflowType` is a `useState` initializer, though, and the fetch resolves after mount. The type would therefore need the same sync-effect treatment `initialSavedComposition` gets (`DashboardLayout.tsx:1561-1565`). This is for the analyzer to confirm.
