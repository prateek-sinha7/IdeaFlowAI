# ISS-1112

**Register source:** sibling derived during the `QA-KB-100` analysis on 2026-10-08 (root [ISS-1092](20261007-2308-ISS-1092.md)). Not its own bug row.

**Confidence:** CONFIRMED. HTTP round trips against the real routers and an in-memory SQLite session, as a basic-tier caller (`evidence/qa-kb-100/analysis-05`, `analysis-08`). Nothing was launched.

## Condition

The inverse case of the root: if reading an override does not check trust, does saving one? No. An override row's `manifest_json` has four writers and none applies CAP-03 to it.

| writer | code | check on the steps | probe, basic-tier caller |
|---|---|---|---|
| `POST /api/user-workflows`, insert | `user_workflows.py:879` via `_validated_manifest` and `_compile_check_manifest` | `compile(..., trust="db")` at `:117` | W1: exec grant plus `security`, `approval` gates: **201** |
| `POST`, upsert of the same built-in | `:834`, same path | same | W2: `spawn_subagents` grant: **201** |
| `PATCH /api/user-workflows/{id}` with `manifest` | `:1026`, same path | same | W3: a benign row patched to the exec step: **200** |
| `POST /{id}/sync-from-file` | `:1057-1100` | none: `row.manifest_json = new_manifest` | W4: the steps of `sample_subagents_parallel` (enterprise-only) copied into the caller's `ppt` override: **200** |

After each, the read side applies the stored steps (`exec=True` or `spawn=True` in `analysis-05`).

## What a read-side-only fix leaves behind

`analysis-08` repeats the probe with `trust="user"` forced at the merge call site only (the root card's one-line fix):

- All four writers still answer 201 or 200. The stored row no longer applies, so the plan is the file plan: the security hole is closed.
- `GET /api/workflows/ppt` still reports `is_overridden=True` (`workflows.py:457`: a row exists and is enabled, not "the merge applied"), `steps` shows the file plan, and `manifest_steps` (`workflows.py:535-540`) serves the row's raw steps, `gates: [security, approval]` included. The wizard's Advanced roster is projected from `manifest_steps`, so the user sees a plan that is not the one that runs. [ADR-0033](20260825-2115-ADR-0033.md) records "saved and displayed while unlaunchable" as known-open by design; [ISS-181](20260825-2115-ISS-181.md) is the same class of mismatch.
- The promise in `user_workflows.py:94-95` ("a save can never pass a check the run would fail", and the module docstring at `:17-23`) stops being true for override rows.

## Expected vs actual

Expected: a save that sets `overrides_pipeline_type`, a PATCH of such a row, and a sync into such a row are refused with a 422 naming the capability, the way the selections path already is (`_compile_selections_trust_user`, `user_workflows.py:387`). Actual: all four accept.

## Why the root cause implies it

Save and read compile with the same literal, `trust="db"`, and the docstring at `:94` says that is deliberate ("matches the launch path too").

Adjacent, not implied by the root cause: `sync-from-file` also has no `can_run_pipeline` check on its source pipeline (W4 copied an enterprise-only workflow's steps into a basic caller's row). It shares this card's fix location, so it is recorded here rather than as its own card; split it if it should be tracked alone.

## Fix direction (INFERRED, not applied)

One shared steps-only check at `trust="user"`, called by `merge_override_steps` and by the four writers whenever the row is an override (`overrides_pipeline_type` set). Precedent for a check shared by save and launch: `agents/workflows/selections.py:196-230` with `_compile_selections_trust_user`, imported lazily inside the handler.

Traps:

- Do not flip `_compile_check_manifest` to `"user"` globally. It also saves ordinary Composer rows that [ADR-0039](20260904-1424-ADR-0039.md) deliberately trusts.
- Compile the steps only (the recipe at `overrides.py:87-100`), not the whole manifest. `sync-from-file` stores the entire file manifest, and `deliverable: ppt` and `context_providers: [opendesign]` are not user-allowed.
- Hardening POST alone leaves the upsert branch, PATCH and sync-from-file.
- The canvas saves an override from the built-in's raw `manifest_steps` and passes every step key it does not model straight back (`frontend/src/store/api/userWorkflows.ts:283-305`, `IdeaInputPage.tsx:1225`). For `app_builder` that includes `post_step: api_prefix_audit`, which `trust="user"` refuses (`evidence/qa-kb-100/analysis-04`). Once the writers check, that canvas save gets a 422. The 422 is the safe default; whether the canvas should strip engineer-only keys before saving an override is a UX call for the owner and does not block the trust change. The wizard path sends library agent ids and is not affected (INFERRED).
- `app/api/user_workflows.py` must not import `agents.execution_engine` at module level (its docstring). Put the helper where the selections helper lives, or import it lazily as `_compile_check_manifest` already does.

## Resolved (QA-KB-100 fix, 2026-10-08)

[FIX-766](20261008-1444-FIX-766.md) adds `_compile_check_override_steps` (`user_workflows.py:139-168`). It runs the shared `compile_override_steps` at `trust="user"` and answers 422. `_validated_manifest(..., override_of)` calls it for POST insert, POST upsert and PATCH, and sync-from-file calls it on the file's steps when the row is an override (`:1136-1142`). All three tests in `test_iss1112_override_writers_trust.py` XPASS (strict). PATCH and sync-from-file were also driven by probe (`evidence/qa-kb-100/fix-06`: 422, 422, with a 200 control). Split out: the missing `can_run_pipeline` check on sync-from-file ([ISS-1117](20261008-1444-ISS-1117.md)) and the canvas engineer-only-keys decision ([ISS-1118](20261008-1444-ISS-1118.md)).
