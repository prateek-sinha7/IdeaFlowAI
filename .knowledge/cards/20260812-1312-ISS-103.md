# ISS-103

## Title

**Ctrl-C already cancels in-flight runs — by an uncontrolled path that runs AFTER the checkpointer pool is closed — while `kill`/`docker stop` does not. The two signals take different teardown paths, and only one of them is the one the code reasons about.** `uvicorn/server.py:312-330`'s `capture_signals()` restores each signal's ORIGINAL disposition and then calls `signal.raise_signal(captured_signal)` — still inside `serve()`, i.e. still inside `asyncio.run(...)` (`server.py:64-66`). For **SIGTERM** the restored disposition is the default, so the process dies right there: `asyncio.run` never returns, `Runner.close()` → `_cancel_all_tasks(loop)` (`asyncio/runners.py:193-201`) never runs, and no pipeline driver is ever cancelled. For **SIGINT** the restored handler raises `KeyboardInterrupt` in Python, which unwinds through `asyncio.run` normally — so `_cancel_all_tasks` DOES run, every registered driver task is cancelled, and each one's `except asyncio.CancelledError` handler (`run_commands.py:2424-2435` launch, `:2654-2659` revision) writes `wr.status = "cancelled"`. **Consequences.** (a) A developer pressing Ctrl-C has always been cancelling their in-flight runs, regardless of `SHUTDOWN_STOP_RUNS` — undocumented anywhere. (b) That cancel happens AFTER the lifespan has completed, i.e. after `close_checkpointer()` has closed the pool, so any driver whose unwind path touches `get_checkpointer()` hits `RuntimeError` (`checkpointer.py:41-49`); the two handlers above use the sync SQLAlchemy session so this is a latent hazard rather than an observed crash, but nothing bounds what else runs there. (c) `_cancel_all_tasks` gathers with **no timeout** (`loop.run_until_complete(gather(...))`), so a driver that does not unwind promptly hangs the process past every documented budget — outside `stop_grace_period`'s accounting entirely. **Fix shape:** decide whether SIGINT should behave as SIGTERM does (bring the cancel inside the lifespan where its ordering is controlled) and document whichever is chosen; the `SHUTDOWN_STOP_RUNS=True` path already does this deterministically and in the right order.

## Source / Evidence

Settled empirically during quick-260812-hsx on a throwaway uvicorn (port 8099), not inferred: a probe modelling the driver task + handler recorded NO `driver_wrote_status_cancelled` / `driver_finally` under SIGTERM and BOTH under SIGINT; a no-uvicorn control (`isolate_cancel_all_tasks.py`) confirmed plain `asyncio.run` DOES run the handler (`cancelled: False`); and a variant stamping a marker after `server.run()` returns never wrote it, proving `server.run()` does not return. Mechanism then read in the installed `uvicorn==0.34.0` source. <br><br>**REASSESSED 2026-08-12 (quick-260812-tni). Three changes to this row.** **(1) The fix DIRECTION is now fixed and the row's wording no longer leaves the wrong door open: SIGINT must be made to match SIGTERM, never the reverse.** Making SIGTERM behave like SIGINT means every `docker stop` / ECS deploy cancels every in-flight run and writes it terminal — precisely the `SHUTDOWN_STOP_RUNS=True` semantics production rejects for two independent recorded reasons (`config.py:206-211`, `run_shutdown.py:26-36`): it destroys deploy-invisibility, which is the entire point of Phases 45-50, **and** it pushes the teardown budget from 24 s to 30 s, i.e. onto the SIGKILL line. **(2) Severity lowered to `minor`.** Production never sends SIGINT: `docker-entrypoint.sh` uses `exec uvicorn` so uvicorn is PID 1, `docker stop` / ECS send **SIGTERM**, and a repo-wide grep for `StopSignal` / `stopSignal` / `stop_signal` returns **zero** hits in any compose file, Dockerfile, entrypoint or deployment doc. And FIX-234 already defused it locally: with `ENV=development` resolving `SHUTDOWN_STOP_RUNS=True` (verified at HEAD: `settings.SHUTDOWN_STOP_RUNS is True`), step 3 of the lifespan cancels the drivers **cooperatively, inside the lifespan, in the right order**, so by the time the accidental `_cancel_all_tasks` runs the drivers are already done. The remaining window is SIGINT with the flag explicitly forced off, or a non-development `ENV` that somehow receives SIGINT. Latent-hazard + observability row, not a money row. **(3) Sub-claim (b) probed and answered: NO checkpoint is written on a driver's cancellation unwind.** A no-network, no-model probe (`scratchpad/batch2/probe/checkpoint_on_cancel_probe.py`) built a LangGraph `StateGraph` on a spy checkpointer, streamed it inside a task, cancelled mid-node and gathered with no timeout (the `asyncio.runners._cancel_all_tasks` shape). Result for BOTH `astream_events` and `ainvoke`: 5 checkpoint writes total, **0 after the cancel** — the timeline is `… aput, node_slow_start, cancel_requested, node_slow_cancelled, driver_cancelled_error_handler, driver_finally`. LangGraph's pregel loop checkpoints around node completion; a node cancelled mid-flight writes nothing on the way out. Combined with the fact that `get_checkpointer()` has exactly **one** non-test caller in the whole backend (`engine.py:1512`, the run ENTRY path, not the unwind path), sub-claim (b) stays **latent, and is now latent by measurement rather than by assumption**. Caveat: the probe used `InMemorySaver` and a plain async node, so it pins LangGraph's write SITES, not any hypothetical `finally` inside deepagents middleware. **Why the code change is DEFERRED and not simply unfinished.** The clean fix is "own the SIGINT disposition", and it is **not reachable from inside the application**. `uvicorn 0.34.0`'s `Server.capture_signals()` snapshots `original_handlers = {sig: signal.signal(sig, self.handle_exit) …}` and in its `finally` reinstalls exactly that snapshot before `signal.raise_signal(...)`. Any handler the app installs later is therefore **discarded** at that moment. And the snapshot is taken BEFORE our code exists: `serve()` is `with self.capture_signals(): await self._serve(sockets)`, and `_serve` is what calls `config.load()` — the call that imports `app.main`. So there is no in-process seam. The only clean alternative is to stop launching uvicorn from its CLI and run a `uvicorn.Server` we own, which changes the production start command, the PID-1 process and the plumbing of `--proxy-headers` / `--forwarded-allow-ips` / `--timeout-graceful-shutdown` — an outward-facing deployment change, not a clean one, and out of scope for a quick task. **Explicitly NOT done: no second terminal-write path was added beside `_drain_then_cancel` (`run_shutdown.py:222-259`), which remains deliberately the only escalation policy.** Sub-claim (c) — `_cancel_all_tasks` gathering with no timeout (`asyncio/runners.py:201`) — is unchanged and is the same defect as ISS-106's untimeouted `pool.close()`: the documented teardown budget is not a budget. Fix those two together.
