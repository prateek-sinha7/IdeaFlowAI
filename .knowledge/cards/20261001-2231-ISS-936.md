# ISS-936

## Description

Sibling of [ISS-398](20260828-2106-ISS-398.md) (QA-KB-017), in the adjacent state "entitlement changed after the value was saved". [FIX-361](20260829-0029-FIX-361.md) made `PUT /api/settings/preferences` refuse a premium `preferred_model` for a basic account and argued that every reader is therefore safe: "they can no longer observe an unauthorised value, because it is never stored". That holds only while the account's tier never drops. A pro account that selected Opus and is later demoted keeps the stored value, and every launch uses it.

The agreed minimal fix for QA-KB-017 calls this out for saved workflows ("a downgrade-after-save edge, out of scope here"); it applies equally to the account-wide preference, which is the more consequential of the two because it silently drives every run.

## Why the root cause implies it

Same root cause, other end of the pipe: the entitlement is enforced where a value is written and nowhere it is consumed.

## Evidence

CONFIRMED, read:
- The only writer of `users.preferred_model` is `backend/app/api/settings.py:378`. A tier change does not touch it: `refresh_projection_if_stale` writes `tier`, `is_admin` and `roles_synced_at` only (`backend/app/core/provisioning.py:112-150`), and `change_tier` (`backend/app/core/cognito_admin.py:397`, reached from `admin.py::update_user_tier`) has no reference to it. A grep for `preferred_model` across `backend/app` and `backend/agents` finds only `settings.py`, `models/user.py` and `run_commands.py`.
- Ten read sites in `backend/app/api/run_commands.py` (`:1683, :1696, :1879, :3750, :4208, :4351, :5603, :5616, :5759, :5773`), none checking the tier. `:4208` is the launch driver's `engine.execute(model_id=getattr(user, "preferred_model", None) or None, ...)`.
- The engine seeds it as the session model, tier 5a of the resolver (`backend/agents/model_policy.py:225`), used by every agent that has no override, step model or `AGENT.md` model.

CONFIRMED, executed offline (repo harness `backend/tests/integration/api/test_rest_run_launch_api.py`, stub engine): a `basic` caller whose `preferred_model` is `eu.anthropic.claude-opus-4-6-v1` launched `user_stories` and got 200 with one run minted; the engine's `execute()` received `model_id='eu.anthropic.claude-opus-4-6-v1'`. The stale value was set directly on the fake user, so the downgrade transition itself was not driven.

INFERRED, not driven: the real sequence (pro account selects Opus, admin demotes via `PUT /api/admin/users/{id}/tier` or a group change plus a fresh token, the next launch runs on Opus). What settles it: that sequence plus reading `agent_complete.model_id` on the run; no paid run was launched here.

## Expected vs actual

- Expected: after a downgrade, a launch no longer runs on a model the account's current tier cannot select.
- Actual: the stored premium preference keeps driving the session model.

## Fix direction

Gate where the value is used, not only where it is written. One helper that resolves the session model from `(user, principal)` and falls back to the system default when `can_use_model(effective_tier(user, principal), preferred_model)` is false, called from the read sites that reach the engine. That is authoritative under [ADR-0013](20260916-ADR-0013.md) (local fields are projections). Optionally also reset the stored value where a tier change lands locally (`refresh_projection_if_stale`, `change_tier`) so the settings page does not keep showing a model the account cannot use (the page already reports `allowed: false` per model, [ISS-430](20260829-0029-ISS-430.md)).

## Test notes

Launch harness as above: basic caller, `preferred_model` set to the premium id, expect the engine to receive no premium `model_id` (default or `None`) and the launch to succeed. Control: pro caller keeps the premium `model_id`.
