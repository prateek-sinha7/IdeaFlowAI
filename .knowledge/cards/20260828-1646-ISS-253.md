## Reproduction (3/3, cold start each time)

Register entry: **BUG-20260828-001720-workflow-create-prototype** in `bug-hunter/ledger.md`.

Reproduced on **all 3 cycles**, each from a fresh, independent navigation (not a soft re-click):

1. Navigate cold to `http://localhost:3000/dashboard`, confirm session (`auth_token` present),
   then cold-navigate to `http://localhost:3000/workflow/create?mode=nonsense`.
2. `location.href` settles on `http://localhost:3000/create/nonsense` — the mode/slug redirect
   fires (treating `nonsense` as a workflow id, not the special-cased `ppt`/`prototype` values).
3. Console shows `GET http://localhost:8000/api/workflows/nonsense` → `404 Not Found`, on every
   cycle.
4. The page renders a normal-looking "Provide the brief" / "Run a workflow" composer.
   `document.body.innerText` contains no "error", "not found", or "failed" text anywhere.
5. DOM read of the three action buttons (`Save workflow`, `Save as my version`,
   `Add agents first`) shows `disabled === true` on first render, and — after typing a full,
   valid, non-trivial brief into the "Brief description" textbox — **still `disabled === true`,
   unchanged**. There is no path to completion on this page.

Repeated as a fully independent cold navigation two more times (dashboard -> URL, dashboard ->
URL) with identical results each time: redirect fires, 404 in console, three buttons disabled
before and after filling the brief, no error text anywhere in the body.

Conditions established: qa-admin tier, light theme (default), first visit and revisit both
fail identically — tier/theme/session-age are not the trigger; the trigger is purely
**an unrecognized, non-empty `mode` value on `/workflow/create`**.

## Expected vs Actual

**Expected:** An unrecognized `mode`/workflow slug should either surface an explicit
"workflow not found" error with a way back to a valid start point, or fall back to a working
default — not present a normal-looking but permanently non-functional composer with zero
indication anything failed.

**Actual:** `/create/nonsense` renders indistinguishably from a real composer. Every action
(save, save-as, add agents) is permanently disabled regardless of user input, and the only
evidence anything is wrong is a console 404 no typical user will ever see.

## Root cause (read, not fixed)

`frontend/src/app/[...view]/page.tsx` routes `/create/{slug}` to the `create-workflow` screen,
carrying `slug` through as `pipelineType`/`workflowId` with no existence check — any string is
accepted and handed to `ComposerPage`.

`frontend/src/components/workflow/composer/ComposerPage.tsx:418-436` fetches
`getWorkflowDetail(jwt, workflowId)` (→ `GET /api/workflows/{workflowId}`) to populate
`declaredCapabilities` (the SURF-03 capability strip). On failure it does:

```ts
.catch(() => {
  if (!cancelled) setDeclaredCapabilities(undefined);
});
```

This swallow is intentional for SURF-03 ("nothing declared, strip doesn't render" — see the
comment at the `getWorkflowDetail` JSDoc in `frontend/src/lib/api.ts:1634-1640`, "An unknown id
raises 404 server-side (the caller treats that as 'nothing declared')"). But the SAME 404
also means the roster-seeding path (console-logged as `[wf] 4. roster for {slug}
{fromLibrary: 0, fromManifest: 0, using: manifest}`) finds zero agents for the unknown
pipeline type, so `pipelineAgents` stays empty. The three action buttons are gated on
`pipelineAgents.length > 0` (via `optionalCount`/`canAddMore` and the "Add agents first" label),
so with zero agents they are permanently disabled — and nothing on this code path ever surfaces
the 404 as a user-visible error, because the catch that would have been the natural place to do
so was written for a different, narrower purpose (an optional capability strip, not the
composer's core save/run affordances).
