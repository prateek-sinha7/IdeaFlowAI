## What happened (INFERRED sibling — not yet reproduced in the running app)

Derived from the root cause of [ISS-302](20260828-1734-ISS-302.md) (BUG-20260828-052400-workflows):
a delete-confirmation dialog that captures only the target row's **id** in local state at
click time, then renders fully static JSX with no lookup back into the loaded list to
interpolate identifying text. That exact shape recurs here, on the admin user-management
page — a higher-stakes surface, since the destructive action is deleting a user account and
"all their data."

## Root cause (CONFIRMED by direct read — the reproduction itself is not yet confirmed)

`frontend/src/app/admin/page.tsx`:

- `deleteConfirm` (line 126, `useState<string | null>`) stores only a user **id**.
- It is set at line 441: `onClick={() => setDeleteConfirm(user.id)}` — only `user.id` is
  captured, even though the full `user` row (with email/name) is in scope at the click site.
- The confirm dialog (lines 525-556) is fully static JSX: heading `"Delete user?"` (543),
  body `"This will permanently delete the user and all their data. This cannot be undone."`
  (544) — no email, username, or any other identifying field anywhere in the dialog.
- `handleDeleteUser(deleteConfirm)` (line 549) is called with only the id at confirm time —
  the identifying data is dropped at the point of capture, not lost later, exactly matching
  ISS-302's finding for `SavedWorkflowsPage.tsx`.

## Expected vs actual

- **Expected:** the confirmation states which user account will be deleted (e.g. their email
  or display name), so an admin can verify the correct account before an irreversible
  account + data deletion.
- **Actual:** dialog heading and body are fixed strings, identical regardless of which user
  row triggered them.

## Why the root cause implies it

Same mechanism as ISS-302: an id-only confirm-state variable (`useState<string | null>`) set
from a row click handler, feeding a dialog that renders static copy with no lookup back into
the loaded rows list. `admin/page.tsx` is a third, independent implementation of this same
shape (its own local state, its own inline dialog JSX — no shared component with
`SavedWorkflowsPage.tsx` or `WorkflowHistory.tsx`), which is why the fix cannot be a single
shared-function patch across all three call sites — each is a separate copy of the same
mistake.

## What would settle it

Reproduce in the running app on `/admin`: open the delete-confirm dialog for two different
users and diff the dialog's accessible text. **Not attempted in this pass** — `/admin` is a
sensitive surface (this repo's standing rule bars granting a second admin session, since it
401s every admin credential and needs a DB write to undo); a *reproduction* of an existing
dialog before cancelling is a different, lower-risk action than granting admin, but is left
for whoever validates this card to judge and perform deliberately, not attempted
incidentally here.
