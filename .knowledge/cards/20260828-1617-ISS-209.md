## Derivation (INFERRED — not yet reproduced; currently masked by ISS-198)

Sibling of [ISS-198](20260828-1400-ISS-198.md) — the inverse-case check ("if load is
broken, what about delete/create interacting with the same state?").

`frontend/src/components/history/WorkflowHistory.tsx`:
- `setTotalRuns` is called in exactly 3 places, all inside fetch effects: the mount
  effect (line 210), the `recentRuns`-change effect (line 231), and `refreshRuns` (line
  252) — confirmed via `grep -n "setTotalRuns"`.
- `handleDeleteConfirm` (line 408-421) calls `deleteWorkflow(token, deleteConfirmId)`
  then `setRuns((prev) => prev.filter((r) => r.id !== deleteConfirmId))` (line 415) — it
  never calls `setTotalRuns`. `totalRuns` is left exactly as it was before the delete,
  now one higher than the server's true count until the next fetch effect fires.
- `handleLoadMore`'s guard (line 291) is `runs.length >= totalRuns`, and its fetch (line
  293) uses `offset: runs.length`. Deleting a run that was inside the currently-loaded
  window shifts the server's true ordering (`ORDER BY created_at DESC` — the run
  previously just past the loaded window moves into it), so a subsequent `handleLoadMore`
  call computes `offset` against a `runs.length` that no longer matches the server's
  current position for "the next unseen row" — the following page can skip or duplicate
  one row relative to what the user has already seen.

**Currently masked**: because [ISS-198](20260828-1400-ISS-198.md) means `handleLoadMore`
is unreachable today, this drift has no visible effect yet. It becomes live the moment
[ISS-198](20260828-1400-ISS-198.md) is fixed by wiring a Load More/infinite-scroll
trigger — so it should be fixed in the same change, not discovered as a follow-up bug
after that fix ships.

## Expected vs Actual

- Expected: deleting a run keeps `totalRuns` (and the offset semantics `handleLoadMore`
  relies on) in sync with the server's true count — either by decrementing `totalRuns`
  locally or by re-fetching the count.
- Actual: `totalRuns` is frozen at its last-fetched value across any number of deletes;
  only a subsequent full refetch (manual refresh, auto-refresh, or a `recentRuns` change
  from the parent) corrects it.

## What would confirm or refute this

Reproduction (once a Load More/infinite-scroll trigger exists per the
[ISS-198](20260828-1400-ISS-198.md) fix): load the first page, delete a run from within
that loaded page, trigger Load More, and check the next-fetched page's `offset` request
against the server's actual remaining rows for an off-by-one skip or duplicate — compare
against `totalRuns` in React state (still showing the pre-delete count) vs. a fresh
`GET /api/runs?limit=1` call's `X-Total-Count` header (the true post-delete count).

## Why this is a sibling, not the same bug

[ISS-198](20260828-1400-ISS-198.md)'s root cause is "no trigger ever calls
`handleLoadMore`." This is a latent correctness bug IN `handleLoadMore`'s own
bookkeeping, on the delete path specifically, that today has no observable symptom only
because the trigger doesn't exist — fixing ISS-198 without also fixing this would trade
one invisible bug for a newly-visible one.
