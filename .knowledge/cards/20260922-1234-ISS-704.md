# ISS-704

## Title

Sibling of [ISS-720](20260922-1232-ISS-720.md): the ref-scoped workspace zip endpoint has no
size cap at all, for the same reason the ref-scoped listing has no size — git-tree plumbing
carries no blob-size data in this codebase, and nobody filled the gap on either endpoint.

## Status: CONFIRMED — the code path is unconditional, read directly in both branches

`backend/app/api/run_files.py`'s `download_sandbox_zip` (976-…) has two branches:

- **Ref branch** (`if ref is not None:`, line 1019): validates the ref, does
  `archive_fn = getattr(sandbox, "archive_at_ref", None)` (1023), gets
  `archive_bytes: bytes = archive_fn(safe_ref)` (1030) — raw `git archive` bytes — and
  **returns them directly at line 1036-1043**. No size is computed or compared anywhere in
  this branch.
- **Live branch** (falls through when `ref is None`): `files, _truncated = sandbox.list_files()`
  (1045), `total = sum(int(f.get("size", 0)) for f in files)` (1046),
  `if total > _SANDBOX_MAX_ZIP_BYTES: raise HTTPException(413, ...)` (1047-…).

Because the ref branch `return`s at line 1036, execution can **never** reach line 1045 onward
when `ref` is supplied. This is not a weakened check — it is structurally unreachable code for
every ref-scoped request.

## Why ISS-720's root cause implies this

The live branch can only compute `total` because `sandbox.list_files()` returns real per-file
`size` from `full.stat()` (`sandbox.py:793,796`). The ref branch has no equivalent: both
`list_files_at_ref` and `archive_at_ref` are built on git-tree plumbing (`git ls-tree
--name-only`, `git archive`) that — per [ISS-720](20260922-1232-ISS-720.md) — carries no
blob-size data anywhere in this codebase today. Whoever wrote this branch could not `sum()` a
size that was never fetched, so the cap check was omitted rather than computed — the identical
gap as ISS-720's `size: 0`, just consumed by a size LIMIT here instead of a size DISPLAY.

This also lapses a constraint already on record: FIX-316's card states "Sandbox reads are
capped at 8MB and the zip at 64MB; over the cap is a 413, never a truncated file presented as
whole" — asserted repo-wide, not "for the live branch only."

## Expected

`GET /{run_id}/sandbox/zip?ref=vN` for a workspace whose tree at that ref exceeds 64MB returns
`413`, same as the live path, per FIX-316's locked constraint.

## Actual

The ref branch returns `200` with the full `git archive` bytes regardless of size — no cap, no
413, at any size.

## What would confirm this live

Tag a sandbox whose tracked tree exceeds 64MB (or lower `_SANDBOX_MAX_ZIP_BYTES` in a test),
call `GET /{run_id}/sandbox/zip?ref=<tag>`, and confirm it returns 200 with the oversized
archive instead of 413. Not exercised by QA-PS-032's reproduction, which only hit the listing
endpoint, not the zip endpoint — the MECHANISM here is fully confirmed by static reading (a
`return` at line 1036 cannot reach lines 1045-1047, which is not a fact that needs a live run to
settle); only the "workspace this large actually occurs in practice" scenario is unverified.

## Fix — separate from ISS-720's, do not conflate

Needs either (a) sizing `archive_bytes` after generation
(`len(archive_bytes) > _SANDBOX_MAX_ZIP_BYTES` before returning — cheapest, and a fair proxy
since a compressed archive is never larger than the tree it holds) or (b) summing real blob
sizes from a `git ls-tree -r -l <ref>` before calling `archive_at_ref` (shares plumbing with
ISS-720's fix if that lands first). Either belongs inside `download_sandbox_zip`'s ref branch
(`run_files.py:1019-1043`) — the one place every ref-scoped zip request routes through, not in
a caller.
