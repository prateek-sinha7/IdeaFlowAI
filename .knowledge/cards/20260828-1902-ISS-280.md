## Why this must also be broken

`frontend/src/components/workflow/IdeaInputPage.tsx` has its own, separately-implemented
`handleSaveAsOverride` (line 1460-1488, confirmed read) — not the same function as
`LaunchWizard.tsx`'s, but the same defect SHAPE:

```js
const saved = await createUserWorkflow(jwt, {
  name: `My ${workflowId}`,
  description: "Your saved version of this workflow.",
  base_pipeline_type: workflowId,
  agent_ids: pipelineAgents.map((a) => a.id),
  manifest: buildWorkflowManifest(pipelineAgents, undefined, selectionsRef.current) as unknown as Record<string, unknown>,
  overrides_pipeline_type: workflowId,
});
```

`description` is the identical hardcoded literal `"Your saved version of this workflow."` found
in `LaunchWizard.tsx:735` (confirmed: `grep -n "Your saved version of this workflow\." frontend/src/`
returns exactly these two lines, nowhere else). Neither `name` nor `manifest` reads `ideaInput` —
the component's brief-textarea state (`const [ideaInput, setIdeaInput] = useState(...)`, line
855) — anywhere in the function body (confirmed: `grep -n "ideaInput" IdeaInputPage.tsx` lists 7
occurrences, none between lines 1460-1488).

This is not a hypothetical omission: `ideaInput` demonstrably IS live, meaningful state at save
time, because the sibling `handleSaveWorkflow` in the SAME file (line 1382-1418) already threads
it — `brief: ideaInput.trim()` at line 1396, inside the `wizardConfig` object it saves under
`selections._wizard`. The same page proves the brief is available and captured for one save
button and silently dropped for the other, the identical pattern
[ISS-226](20260828-1550-ISS-226.md) found in `LaunchWizard.tsx` (`handleLaunch` captures the
brief; `handleSaveAsOverride` does not).

`handleSaveAsOverride` is reachable for any non-custom seeded/built-in workflow, confirmed at
`IdeaInputPage.tsx:1661-1670`: the button renders whenever `effectiveType !== "custom" &&
workflowId`, unconditional on which pipeline type `workflowId` names — this includes
`user_stories`, `app_builder`, `mulesoft`, `dotnet`, and every `ex_A*` conditional-gate example
(the same set [ISS-254](20260828-1810-ISS-254.md) already enumerates for the gates-only defect).

## Relationship to ISS-225

[ISS-225](20260828-1541-ISS-225.md) traces the SAME function (`handleSaveAsOverride`,
`IdeaInputPage.tsx:1460`) but only the `selectionsRef.current`/`gates` mechanism — it 422s loudly
on a manifest that declares `route:` without `gates:`. That card's own root-cause section never
mentions `name`/`description` or `ideaInput`/brief at all. This card documents a SEPARATE,
independently-broken facet of the identical function: on any workflow whose manifest does NOT
declare a bare `route:` (so ISS-225's 422 never fires and the save silently succeeds with
`201`), the save still discards the brief and reports a generic hardcoded description — the same
silent-data-loss shape ISS-226 found in the sibling wizard, just never called out for this file.
Fixing ISS-225's gates gap alone would not fix this.

## Expected vs actual

**Expected:** "Save as my version" on any non-custom workflow through `IdeaInputPage.tsx`
persists a description/manifest that reflects what the user actually typed into the brief field,
the same expectation ISS-226 states for the wizard's brief/template.

**Actual (INFERRED — not yet independently reproduced with request/response capture for this
specific facet):** the saved record's `description` is always the static literal regardless of
`ideaInput`'s contents, and the persisted `manifest` carries no trace of the brief text — on any
non-custom workflow whose own manifest does not itself trip ISS-225's R-03 check.

## What would confirm or refute this

Reproduce on a non-custom, non-route-declaring workflow (e.g. `/create/user-stories` or
`/create/app`, sidestepping ISS-225's gates 422 entirely): type a distinctive brief into the idea
input, leave everything else default, click "Save as my version", and inspect the `POST
/api/user-workflows` request body — confirm `description` is the static literal and no field
carries the brief text. A response that DOES vary with the brief would refute this card.

## Where the fix belongs

Same class of fix as [ISS-226](20260828-1550-ISS-226.md)/[ISS-279](20260828-1901-ISS-279.md):
inside `handleSaveAsOverride` itself, reusing the pattern its own sibling `handleSaveWorkflow`
already proves works (`brief: ideaInput.trim()`). Since `WorkflowManifest` has no field for brief
text at all (`frontend/src/types/index.ts:642-648`) and a per-run brief arguably should not be
baked into a reusable per-pipeline-type override in the first place, the immediately-actionable
part of this fix is the misleading hardcoded `description` (and `LaunchWizard.tsx`'s `name`); the
5-fixer should confirm with the team whether brief capture belongs here at all before extending
the manifest schema for it — see ISS-279's note on the same open question for the wizard side.
