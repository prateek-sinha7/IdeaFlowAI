## What is suspected

[ISS-190](20260828-1501-ISS-190.md) root-caused the `/create/prototype` permanent-blank-page bug
to a specific anti-pattern in `frontend/src/app/[...view]/page.tsx`: a boolean (`mounted` /
`isAuthenticated`) that starts `false`, is flipped to `true` exactly once by a mount-only
`useEffect` (empty or effectively-static deps), and unconditionally gates 100% of the
component's render output until then — with nothing in the frontend listening for a
`pageshow`/bfcache-style restore to re-arm it.

That exact anti-pattern is NOT unique to `page.tsx`. It is independently re-implemented, byte-for-byte
the same shape, in two other files:

- `frontend/src/components/workflow/LaunchWizard.tsx:161` —
  `const [authChecked, setAuthChecked] = useState(false);`; `:259-270` — the auth-check
  `useEffect(() => { ...; setAuthChecked(true); ... }, [router])` (fires once, `router`'s identity
  is stable for the SPA session); `:806` — `if (!authChecked) { return <...Loading…></div>; }`,
  the sole gate on everything below it.
- `frontend/src/app/handoff/settings/page.tsx:21` — `const [authed, setAuthed] = useState(false);`;
  `:32` — `if (!authed) return null;`.

`LaunchWizard` is not a helper `page.tsx` merely calls into for `/create/prototype` — it is ALSO
mounted directly, standalone, by a genuinely separate route:
`frontend/src/app/workflow/create/page.tsx` (`/workflow/create?mode=ppt|prototype`, the legacy
unified launch route). That wrapper page's own comment (`:17-19`) says explicitly: "Auth is owned
by LaunchWizard... the duplicate getToken/redirect + loading gate here was a redundant second
gate [IN-07]" — i.e. `page.tsx`'s gate is deliberately NOT in front of `LaunchWizard` on this
path. `/workflow/create` is live and actively used, not dead code — confirmed call sites:
`frontend/src/components/home/CreationHub.tsx:31,35` and
`frontend/src/components/layout/DashboardLayout.tsx:1530,1557`.

## Condition

- Navigate to `/workflow/create?mode=prototype` (or `?mode=ppt`) directly, or via the Home
  screen's launch card / DashboardLayout's launch action.
- Browser Back to a prior route, then browser Forward back to `/workflow/create?mode=...`.
- (Lower-priority second instance, same pattern) the same sequence against
  `/flowin-handoff/settings` (`handoff/settings/page.tsx`).

## Expected vs actual

- **Expected:** Forward re-renders the launch wizard (or handoff settings page) exactly as a
  fresh visit does.
- **Actual (predicted):** `LaunchWizard`'s copy renders its `Loading…` placeholder
  (`:806-812`) forever instead of ISS-190's totally blank body — a different visible symptom
  (a permanent spinner, not a blank raw-RSC page) but the same underlying defect class: a
  mount-once effect whose flip never re-fires, with no bfcache/pageshow recovery.
  `handoff/settings/page.tsx` would show a blank body (`return null`), matching ISS-190's symptom
  more closely.

## Why the root cause implies this — and why it is a DISTINCT defect, not the same one

ISS-190's proposed fix lives in `page.tsx` because that file is the ONE shared catch-all every
one of the 34 `[...view]` screens routes through (ADR-0018) — fixing it there covers all of
them at once. `LaunchWizard.tsx` and `handoff/settings/page.tsx` are NOT reached through that
catch-all's gate on the routes named above, so a `page.tsx`-only fix, however correct, leaves
these two call sites with the identical unfixed defect. This has to be tracked and fixed
separately, in each file, or via a shared hook (e.g. `frontend/src/hooks/`) all three gates are
migrated onto — the exact "other callers with the same flaw, not covered by the shared-function
fix" case.

**Marked INFERRED**: neither file's Back-then-Forward behavior has actually been driven yet —
only the identical source-code shape has been confirmed by reading it. What would confirm it:
repeat ISS-190's Back-then-Forward repro against `/workflow/create?mode=prototype` and
`/flowin-handoff/settings`, 3 cycles each, cold start every cycle.
