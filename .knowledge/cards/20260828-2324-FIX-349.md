## What was wrong

On `/create/ex_A2_branch` ("Branch by Language"), opening "Advanced 5 agents", selecting the
"Pick Language" step and changing its `english` outcome's route Type from "Step" to "Workflow"
with target "Spanish Greeter" adds a "Spanish Greeter — Diverts run" node to the modal's canvas.
Clicking the modal's own **Cancel** closed it but kept the edit: reopening "Advanced" still
showed the divert node and still showed Type "Workflow" / Target "Spanish Greeter". Reproduced
3/3 by the validator, with `browser_network_requests` showing only background `GET`s throughout —
nothing was ever saved, so this was purely un-discarded client state. A full page reload did
reset it. Register entry `BUG-20260828-001100-create-ex-a2-branch`.

## Root cause

Confirmed on [ISS-363](20260828-2129-ISS-363.md) (which corrects
[ISS-258](20260828-1650-ISS-258.md)'s own attribution — see "Why ISS-258's mechanism was
superseded" below).

Every edit made inside the modal writes the **host page's** React state live, and nothing ever
snapshotted it:

- The route/outcome editor: `CanvasConfigRail.tsx:295` `onRouteChange?.(...)` →
  `CanvasView.tsx:748-751` `handleRouteChange` → `onTreeChange?.(next)` →
  `AgentsPopup.tsx:2462` `<CanvasView ... onTreeChange={onReorder} />` → the host's `onReorder`
  → `IdeaInputPage.tsx:1540-1542` `setPipelineAgents(reordered)` (and `LaunchWizard.tsx:577`,
  identically).
- `pipelineAgents` is the same array handed straight back down as `AgentsPopup`'s `agents` prop,
  so the divert node appears the instant the patch applies.
- The per-agent flat levers take a parallel route: `AgentsPopup.tsx:2255-2262`
  `handleSelectionsChange` → `onSelectionsChange` → the host's `selectionsRef.current` /
  `liveSelections`.

The Cancel button was `onClick={onClose}` and `onClose` is `() => setShowAgents(false)` in both
hosts (`IdeaInputPage.tsx:1882`, `LaunchWizard.tsx:1126`) — a visibility flag and nothing else.
The header X and the backdrop `onClick` were wired to the same bare `onClose`, so all three
dismiss affordances shared the defect.

## What changed, and why there

`frontend/src/components/workflow/AgentsPopup.tsx`, one file — +31 new lines (the snapshot block
plus a preceding blank) and 4 single-line edits (the `react` import and the three `onClick`s):

1. `useRef` added to the existing `react` import.
2. An open-edge snapshot, next to `handleSelectionsChange` where the other live-propagation
   wiring lives:
   ```tsx
   const openSnapshot = useRef<{ agents: AgentDef[]; selections: SelectionsMap } | null>(null);
   useEffect(() => {
     if (isOpen) openSnapshot.current = { agents, selections: liveSelections };
     // eslint-disable-next-line react-hooks/exhaustive-deps
   }, [isOpen]);
   ```
   `isOpen` alone is the dependency list on purpose — `agents`/`liveSelections` are what is being
   snapshotted, so re-running as they change would overwrite the snapshot with the very edit
   Cancel exists to undo. Same `eslint-disable-next-line react-hooks/exhaustive-deps` idiom the
   file's neighbours already use (`CanvasView.tsx:340`, `ReviewGatesSection.tsx:113`).
3. A `handleCancel` that restores before closing:
   ```tsx
   const handleCancel = useCallback(() => {
     const snapshot = openSnapshot.current;
     if (snapshot) {
       onReorder?.(snapshot.agents);
       handleSelectionsChange(snapshot.selections);
     }
     onClose();
   }, [onReorder, handleSelectionsChange, onClose]);
   ```
4. The three dismiss affordances re-pointed at it: the footer Cancel button (was `:2504`), the
   header X (was `:2404`) and the backdrop `onClick` (was `:2349`). The post-save `onClose()`
   inside `handleSaveWorkflow` is deliberately untouched — a save must keep what it saved.

**Why in `AgentsPopup` and not in either host.** `AgentsPopup` has exactly two production callers
(`grep -rn "<AgentsPopup" frontend/src/ --include="*.tsx"` → `IdeaInputPage.tsx:1870`,
`LaunchWizard.tsx:1112`; the only other four hits are render calls in the `.reskin.test.tsx`),
and neither has a bespoke path — both wire `onClose`/`onReorder`/`onSelectionsChange` to the same
shapes. Re-emitting the snapshot through `onReorder` rather than staging the tree locally is the
smaller change AND the safer one: staging every tree edit until "Save workflow" would stop an
unsaved composition from reaching the launch payload, which [ADR-0016](20260824-1630-ADR-0016.md)
(an unsaved composition is launched by sending its manifest inline) requires to keep working.
Restoring on dismiss fixes the reported bug without touching the live-edit path at all.

Restoring the ORIGINAL object identities makes an untouched session free: `setPipelineAgents(sameArray)`
and `setLiveSelections(sameMap)` both bail out on `===`, so opening and cancelling the modal
without editing forces no re-render. That is why there is no "did anything change" guard.

Because `<CanvasView>` renders inside `{isOpen && ...}`, it unmounts on close and re-derives
everything from the restored `agents` prop on reopen — no canvas-local copy of the tree needed
resetting.

## Why ISS-258's mechanism was superseded

[ISS-258](20260828-1650-ISS-258.md) named `handleSelectionsChange`/`onSelectionsChange`/
`selectionsRef` as what fires for a route edit. That chain is real and independently broken, but
it is wired to `ConfigLeversFlat`'s per-agent levers, not the canvas route editor —
[ISS-363](20260828-2129-ISS-363.md) carries the corrected trail, and
[ISS-364](20260828-2130-ISS-364.md) carries the lever chain as its own sibling. ISS-258's
reproduction, evidence and Cancel-button citation stand and are what this fix was verified
against. The fix restores BOTH stores, so the lever chain is covered by the same diff.

## Deferred finding — the test's final assertion has a value/label mismatch

Not an app defect and NOT fixed here (a fixer does not edit a test to make it pass). The
verification test's last line reads:

```python
expect(page.get_by_label("Type").first).to_have_value("Step", timeout=5_000)
```

`to_have_value` compares the `<select>`'s **value**, and the markup is
`<option value="step">Step</option>` (`CanvasConfigRail.tsx:843`) — so the observed value is
`step`, the label is `Step`. The assertion is therefore red on a WORKING fix. Playwright's
`select_option("Workflow")` earlier in the same test matches by value *or* label, which is why
only this one line trips. The behaviour the card asks for is confirmed by the same run's aria
snapshot: `combobox "Type": option "Step" [selected]`. Correcting the literal to `"step"` is a
one-token change that asserts the identical behaviour; it belongs to whoever owns the test, so
it is recorded here rather than applied.
