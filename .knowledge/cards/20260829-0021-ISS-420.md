## Why this must also be broken

ISS-311 traced the empty tab to `AgentLibrary.tsx`'s default-category line:

```tsx
// AgentLibrary.tsx:86
const [activeCategory, setActiveCategory] = useState(currentPipelineType || "all");
```

`IdeaInputPage.tsx` derives the meta-type for the migration launcher:

```tsx
// IdeaInputPage.tsx:877-879
const isMigrationMeta = workflowType === "migration";
const [migrationChoice, setMigrationChoice] = useState<WorkflowType | null>(null);
const effectiveType: WorkflowType = isMigrationMeta && migrationChoice ? migrationChoice : workflowType;
```

`migrationChoice` starts `null`, so before the user picks MuleSoft→Spring Boot or .NET→Azure,
`effectiveType === workflowType === "migration"`. The "Advanced" button that opens `AgentsPopup`
(and, inside it, `AgentLibrary`) carries no guard tied to this state:

```tsx
// IdeaInputPage.tsx:1900-1902
<button
  onClick={() => setShowAgents(true)}
  className="flex items-center gap-2 text-[12px] text-ink-400 hover:text-ink-700 transition-colors"
>
```

(no `disabled` attribute at all — contrast the Run/Continue buttons at `:1695`, `:1710`, `:1721`,
which DO gate on `isMigrationMeta && !migrationChoice`). So `AgentsPopup` mounts with
`pipelineType={effectiveType}` = `"migration"`, and `AgentLibrary` receives
`currentPipelineType="migration"`, defaulting `activeCategory` to that string.

`"migration"` is not a real catalog `pipeline_type` — only its two concrete children
(`mulesoft_to_springboot`, `dotnet_to_azure`) are declared on any `AGENT.md` — and it is absent
from `CATEGORIES_FALLBACK`/`CATEGORIES` (`AgentLibrary.tsx:52-61`, `89-99`), which only lists the
two concrete sub-types, never `"migration"` itself. Two consequences follow directly from
`AgentLibrary.tsx:104-105` (`matchesCategory = activeCategory === "all" || agentMatchesPipelineType(agent.pipeline_type, activeCategory)`)
and `:183` (`isActive = activeCategory === cat.id`):

- `filteredAgents` is empty regardless of `existingAgentIds` or search text — no catalog agent's
  `pipeline_type` ever equals `"migration"`.
- No sidebar category button renders as active — `activeCategory` (`"migration"`) matches no
  `cat.id` in the list at all, unlike ISS-311's case where the User Stories tab IS correctly
  highlighted, just empty.

## Expected vs actual

**Expected:** either the "Advanced" trigger is disabled until a migration sub-pipeline is chosen
(matching the Run/Continue buttons' existing guard), or `AgentLibrary` falls back to `"all"` when
handed a `currentPipelineType` that names no real category.

**Actual (INFERRED — not yet independently browser-reproduced):** derived from the code path
above, not yet clicked through live. The "No agents found" text would match ISS-311's reported
symptom, but the missing active-tab highlight would not — that visual difference is the fastest
way to tell the two apart during reproduction.

## What would confirm or refute this

Navigate to `/create/migration`, do NOT pick MuleSoft→Spring Boot or .NET→Azure, click
"Advanced", then "+ Add agent". Expected-per-this-card: the dialog opens with no sidebar category
button highlighted and "No agents found" showing. A highlighted tab (any tab) or a populated grid
would refute this card without affecting ISS-311 or [ISS-421](20260829-0020-ISS-421.md).

## Where the fix belongs

Same place as ISS-311 and [ISS-421](20260829-0020-ISS-421.md): inside `AgentLibrary.tsx`'s
default-category-selection logic (`:86`) — falling back to `"all"` when `currentPipelineType`
does not match any `CATEGORIES` id closes this for every caller at once. `IdeaInputPage.tsx`'s
missing guard on its own "Advanced" button (`:1900-1902`) is a second, independent half-fix worth
doing regardless (it also blocks opening the canvas with zero agents before a sub-pipeline is
picked), but does not by itself fix `AgentLibrary`'s default-selection blind spot for any other
caller that might pass an unrecognized type.
