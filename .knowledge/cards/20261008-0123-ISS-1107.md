# ISS-1107

## Description

INFERRED sibling of [ISS-1063](20261007-1940-ISS-1063.md) (QA-KB-098). The Playwright session registry (`playwright_session._SESSIONS`) is keyed by `run_id_from_sandbox(sandbox)`, which returns the LAST COMPONENT OF THE SANDBOX DIRECTORY (`playwright_session.py:435-446`, `return parts[-1]` at `:442`). For a revision that is the chain-root id, not the revision's id. The engine's release on every exit path calls `release(pipeline_run_id)` with the revision's own id (`engine.py:7641`), so `_SESSIONS.pop(<revision id>)` finds nothing (`playwright_session.py:478`) and the family's browser stays registered and running. The mismatch is CONFIRMED by a probe on the real functions; its consequences are not driven.

## Why the root cause of QA-KB-098 implies it

Same pattern as ISS-1063: a consumer written against an earlier shape of a thing was not migrated when the thing changed. `run_id_from_sandbox` arrived in `c98fb674a` (2026-08-27), when the sandbox directory name WAS the run id. The sandbox-git-versioning-v2 split (`e7305f9dd`, 2026-09-10; the helper's commit is an ancestor of it) made the directory the family root and the run id logical, and the helper still reads the directory. It was found while tracing which key the ISS-1063 test's `bind_sandbox` and `playwright_close` resolve to: that test is consistent only because registration and `playwright_close` (`playwright.py:502-509`) both go through the same helper, whereas the engine's release does not.

## Mechanism (CONFIRMED by reading, then by probe)

- Registration: every playwright tool calls `_get_run_id()` (`playwright.py:89-92`) which calls `run_id_from_sandbox(_SANDBOX_VAR.get())`; `pptx_tools.py:230` registers its browser work under the same helper, so both tool sets share the key.
- Release by the engine: `engine.py:7627-7641`, `await _release_playwright_session(pipeline_run_id)` in the `finally` that "every exit from this try crosses" (T7, spec 018 FR-009). `pipeline_run_id` is the logical id of the run being executed.
- Release by the agent (`playwright_close`, `playwright.py:487-509`) and by the idle timer (`_on_idle_timeout`, `playwright_session.py:370`; `_DEFAULT_IDLE_TIMEOUT_S = 300.0`, `:43`) both release the registration key, so they work. Only the engine's exit-time release is mismatched.

Probe (`evidence/qa-kb-098/analysis-06-probe-session-release-key.txt`, real `RunSandbox`, `run_id_from_sandbox`, `get_session`, `release`; no browser launched):

```
run_id_from_sandbox(root sandbox)     = 'root-aaa'
run_id_from_sandbox(revision sandbox) = 'root-aaa'   (revision's logical id is 'revision-bbb')
_SESSIONS keys after the revision's tool call: ['root-aaa']
_SESSIONS keys after engine-style release(revision id): ['root-aaa']   <- session SURVIVES
_SESSIONS keys after release(root id):                  []
```

## Expected vs actual

Expected (`engine.py:7627` comment): the finally "releases this run's Playwright session" on every exit path. Actual: for a root run the key equals `pipeline_run_id`, so it works; for a revision it is a no-op.

## Consequences (INFERRED, not driven)

1. The revision's Chromium (about 150 MB, `playwright_session.py:50`) outlives the run until the idle timer fires, up to 300 s after its last browser call, instead of at run exit.
2. A following run in the same family inside that window calls `get_session` with the SAME key and gets the SAME `PlaywrightSession`. Contexts are looked up by agent key (`playwright_session.py:90-124`) and `playwright_take_screenshot` reads `context.pages[0]` (`playwright.py:323`), so if the agent key repeats the later run's first page may be the earlier run's page.

## What settles the consequences

Drive two sequential revisions of one family with a playwright-granted step through the offline harness and assert `_SESSIONS` is empty after each run exits (today it still holds the family key), and for (2) that the second run starts with no pages. If the mismatch cannot be reached through a real run (for example if the engine never reaches the release with a revision id), this card closes as not reproducible.

## Fix direction (only once reproduced)

One derivation of the key, used on both ends. `run_id_from_sandbox` is the shared seam for the playwright and pptx tools, so the change belongs there or at the engine's single release call (`engine.py:7641`), not in individual tools. Two options:

- The engine releases with the same helper the tools register with (`release(run_id_from_sandbox(sandbox))`): a one-line change independent of [ISS-1106](20261008-0123-ISS-1106.md), but a revision's exit then closes a session keyed to the whole family, which is safe only while one run per family is active at a time.
- `run_id_from_sandbox` returns `sandbox.current_run_id`, so sessions are per run as the module docstring says ("Owns ONE browser for one run"). This only helps after [ISS-1106](20261008-0123-ISS-1106.md) gives the factory-built sandbox the revision id; today `current_run_id` there is the chain root, so this option alone changes nothing.

Decide it together with [ISS-1106](20261008-0123-ISS-1106.md).
