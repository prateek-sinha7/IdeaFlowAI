## The gap

`status.py` prints this, in one report, on HEAD `73796dbd0`:

```
source files covered           735         785   STALE
commits since sync              39           0   STALE
source files changed           287           0   STALE
domain prose                    14          14   OK
```

Three rows say the architecture map is 39 commits and 287 source files behind.
The fourth says all 14 DOMAIN cards' prose is current. They cannot both be true,
and the fourth is the one that is not.

## Why the row goes green when it should go red

The `domain prose` block (`status.py:303-332`) reads two frontmatter fields per
card with a regex and compares them:

```python
elif got["prose_signature"] != got["code_signature"]:
    stale_domains.append(card.stem)
...
"OK" if not (stale_domains or unauthored_domains) else "STALE",
```

It never touches the working tree. Both sides of that comparison are stamps, and
both stamps move only during a rebuild:

- `build_architecture.py:1183` writes `"code_signature": signature` for a
  DOMAIN card (`:861`, `file_signature(...)`, for a MOD card). These are the
  only sites that compute it, and both are inside the rebuild.
- `:1188` copies `prose_signature` forward verbatim from the prior card.

So the pair is frozen together at the last build. As soon as code changes
without a rebuild — the normal state between syncs — `code_signature` stops
describing the code, the two stamps stay equal for that reason alone, and the
row reports OK. The row is green *because* the rebuild is overdue, not despite
it. Once the rebuild runs, `code_signature` moves, the stamps diverge, and the
row correctly turns STALE. The check is inverted with respect to the thing a
reader wants to know.

Here that window is 39 commits wide: `modules.json` is `generated_at:
2026-09-12`, and 287 source files have changed since.

## Why this row in particular

`status.py`'s own comment block bills this as the durable signal — the one that
survives a GUI git client swallowing the pre-commit hook's handoff, "the signal
that survives not being watched". It is the row the design leans on for exactly
the unwatched case, and it is the row that goes green when the watching stops.

Under the standing rule that DOMAIN cards are the repo owner's alone to
re-author, a reader who sees `14 14 OK` has no way to know which cards actually
need attention, and no prompt to go looking.

## What it should do

Degrade rather than assert. When `source files covered` is STALE, the signature
comparison has no current input and the `domain prose` row should report
UNKNOWN (or inherit STALE) instead of OK. Computing a live signature in
`status.py` is the wrong answer — the block is deliberately frontmatter-only so
it costs a glob and no extractor.

## Analysis (QA-KB-026, analyzer, 2026-10-01)

### Root cause (CONFIRMED)

`tools/knowledge/status.py:329-333` derives the verdict from two lists only. `:318-327` fills them from a
frontmatter-only regex over each DOMAIN card:

```python
elif got["prose_signature"] != got["code_signature"]:                 # :326
    stale_domains.append(card.stem)
...
"OK" if not (stale_domains or unauthored_domains) else "STALE",       # :332
```

Neither side of that comparison is computed from the working tree, and neither moves except at a build or a stamp:

| stamp | written | when |
|---|---|---|
| `code_signature` (DOMAIN) | `build_architecture.py:1166-1169` digests the watched files, their symbols, `mods` and `ext`; `:1186` writes it | only inside a `build_architecture.py` run, from the tree as it stood at that moment |
| `prose_signature` (DOMAIN) | `:1191` carries the prior value forward; `--stamp` sets it equal to `code_signature` (`:1977-1978`) | only at a rebuild or a stamp |

`build_architecture.py:201-203` states the intent: `code_signature` is "recomputed here on every run". So
`prose == code` means "the prose matched the code when the last build ran". Between builds both stamps are frozen,
they stay equal, and the row says OK. That is this card's claim, and every line cited supports it.

The line references in this card's frontmatter have drifted by 3 since it was written, and `:861` corresponds to
what is now the per-file card site, not a MOD site. Current sites: per-file cards `:864` / `:865`, DOMAIN `:1186` /
`:1191`, MOD cards `:2140` / `:2144`. The claims themselves are unaffected.

Reference base: every `build_architecture.py` line number in this card and in its siblings is at HEAD 024c03ef.
The QA-KB-004 change ([BUG-129](20260918-BUG-129.md), in the working tree, not committed) adds 7 lines at `:132` and 1
at `:159`, so in a tree that has it add 8 to every `build_architecture.py` reference at or below `:160`. `status.py`
numbers are unaffected (the QA-KB-003 change is line-neutral).

The same class of trap was found and fixed once already, in the refresh gate. `refresh_affected`
(`build_architecture.py:1598-1617`) refuses to compare against the stored `symbols_signature` because "The build
refreshes that field from the current disk state ... stored and live are the same value by construction", and it
recomputes `symbols_digest(live_watch_set(...))` instead. `status.py` and `stale_prose_report` (`:312-346`) never got
that treatment.

### Fix: accept the shape and UNKNOWN, overrule the predicate

The agreed note (BUGS.md, QA-KB-026) is accepted in shape: degrade the verdict, do not recompute it. Two details are
overruled.

**1. Trigger.** The note keys on `source files covered` only. That row is a file count (`modules.json` `file_count`
summed against a disk scan, `status.py:182-191`), so it moves only when a file is added or removed. The case
`code_signature` exists to catch is a rename inside an existing file, which leaves the count equal
(`build_architecture.py:195-206`). S2 shows the agreed predicate still prints OK there. `status.py` already has its
own definition of "a rebuild is due": `needs_arch` at `:385` is `source files covered` OR `source files changed`, and
it prints the full-rebuild "Fix:" line from it. Use the same pair:

```python
        "STALE" if (stale_domains or unauthored_domains)
        else "UNKNOWN" if any(c[0] in ("source files covered", "source files changed") and c[3] == "STALE"
                              for c in checks)
        else "OK",
```

Only the verdict expression inside `checks.append((...))` (`:329-333`) changes. No new variable is needed, because both
rows are appended earlier (`:188`, `:252`) and `checks` already holds them. Harness result with this predicate: S1
UNKNOWN, S2 UNKNOWN, S0 and S4 unchanged. With the agreed predicate: S1 UNKNOWN, S2 still OK.

Cost of the wider trigger, stated plainly: `source files changed` is relative to the sync watermark (`git diff
sync..HEAD`, `:250`), not to the last architecture build. After a close that ran `build_architecture.py` but did not
re-sync, the row can read UNKNOWN when the truth is OK. That is the conservative direction. It is also the same state
in which the footer already prints "Fix: rebuild_knowledge.py", and a known-stale card still wins (STALE, named). If
the owner prefers zero such cases, keep the agreed `covered`-only predicate and drop the S2 test.

**2. UNKNOWN, not STALE.** Accepted, with evidence. A STALE row with no stale card would appear in the "N stale:" list
(`:378`) while the card-naming block (`:381`) stays silent, leaving a stale row with nothing to act on. UNKNOWN is never
alone: it needs a STALE `covered` or `changed` row beside it, so the stale count, the exit code and the `needs_arch`
Fix line are identical across variants (harness `stale_rows`: 1, 1, 1 for S1 and 2, 2, 2 for S2, across current,
agreed and amended). Both consumers that act on the row act only on a literal STALE, so UNKNOWN never triggers
`diagrams` before the rebuild has moved `code_signature`.

Text-mode output with the amended predicate, S1 (other rows omitted):

```
source files covered           935         974   STALE
domain prose                    16          16   UNKNOWN
1 stale: source files covered
Fix: python3 tools/knowledge/rebuild_knowledge.py
```

Rejected alternative, with evidence: recompute the signature live in `status.py`. The note under "What it should do"
above already rules it out on cost. It is also unavailable on correctness, see [ISS-884](20261001-2112-ISS-884.md):
`live_watch_set()` returns a smaller watch set than the build stamped for 6 of 16 DOMAIN cards on a clean tree, so a
live comparison would report 6 false STALEs today.

Residual limit (CONFIRMED by reading `:236-237` and `:250`): an uncommitted in-file edit with no file added or
removed trips neither `covered` nor `changed`, because `git diff sync..HEAD` sees commits only. Only a live recompute
sees it, and that is blocked on [ISS-884](20261001-2112-ISS-884.md).
