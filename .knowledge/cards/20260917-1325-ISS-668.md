# ISS-668

## Title

The Analytics Model Details panel shows "Thinking: Adaptive (effort: max)" for Claude Opus 4.5
and Opus 4.6, but the fragment tuple that actually selects "adaptive" thinking at runtime does
not include those models -- so the label is factually wrong for them. Found while tracing the
blast radius of QA-PS-009 (which reports the same row, correctly matching runtime behavior, for
Sonnet 5).

## Status: INFERRED -- mechanism confirmed by code trace, not yet reproduced live

The analyzer has no browser access. Every claim below is a direct file:line read, not a guess
by analogy -- but nobody has opened the live Model Details panel for an account with Opus
4.5/4.6 usage to watch the row actually render. See "What would confirm this" below.

## Why QA-PS-009's root cause implies this

QA-PS-009's mechanism ([ISS-667](20260917-1320-ISS-667.md)) is: `capabilities.py:189` sets
`thinking_supported=True` for any catalog model id matching one of the fragments in
`_THINKING_FRAGMENTS` (`capabilities.py:169`), and `AnalyticsPage.tsx:826-831` renders the SAME
hardcoded "Adaptive (effort: max)" string for every model where that flag is true -- the label
is not derived per-model, so it is only accurate as long as `_THINKING_FRAGMENTS` and
`model_factory.py`'s own thinking-type selector agree on every fragment. They do not:

- `backend/app/api/capabilities.py:169`:
  `_THINKING_FRAGMENTS = ("sonnet-5", "opus-5", "fable-5", "mythos-5", "opus-4")`
- `backend/app/agents/model_factory.py:123`:
  `_ADAPTIVE_THINKING_MODEL_FRAGMENTS = ("sonnet-5", "opus-5", "fable-5", "mythos-5")`

`capabilities.py:165-168` carries an explicit comment claiming these are kept in sync: "Models
whose id contains one of these fragments support adaptive thinking ... Mirrors the
`_ADAPTIVE_THINKING_MODEL_FRAGMENTS` tuple in `model_factory.py` -- kept in sync by grep rather
than a shared import." They are not in sync: `capabilities.py` carries one extra fragment,
`"opus-4"`, that `model_factory.py` does not have.

Two live catalog entries contain that exact substring:
- `backend/agents/capabilities/model_catalog.py:180` --
  `id="eu.anthropic.claude-opus-4-5-20251101-v1:0"` (Opus 4.5)
- `backend/agents/capabilities/model_catalog.py:192` --
  `id="eu.anthropic.claude-opus-4-6-v1"` (Opus 4.6)

For both:
- `capabilities.py:189` -> `thinking_supported=True` (matches `"opus-4"`) -> the panel shows
  the Thinking row.
- `model_factory.py:126` -> `_thinking_type(mid)` returns `"enabled"`, NOT `"adaptive"` (no
  fragment in `_ADAPTIVE_THINKING_MODEL_FRAGMENTS` matches `"opus-4"`) -> a real run on either
  Opus model, with thinking turned on, gets `thinking: {"type": "enabled", "budget_tokens": ...}`
  (`model_factory.py:139` / `196-199`), never `"adaptive"`.

Unlike the Sonnet 5 case in [ISS-667](20260917-1320-ISS-667.md), this is not a defensible
catalog classification choice -- it is `capabilities.py` and `model_factory.py` disagreeing
with EACH OTHER about the same two models, contradicting the comment that says they must match.

## Expected (once reproduced)

Either the row is not shown for Opus 4.5/4.6 at all (if "enabled" thinking should not surface
as an adaptive-effort note), or it shows text matching what the model actually gets ("Enabled" /
budget-based), not "Adaptive (effort: max)".

## Actual (inferred, not yet observed)

The Model Details panel shows the identical "Thinking: Adaptive (effort: max)" row for Opus 4.5
and Opus 4.6 as it does for Sonnet 5 and Opus 5, even though only the Sonnet-5/Opus-5 family
(per `model_factory.py`'s own tuple) actually gets adaptive-type thinking.

## What would confirm this

1. Sign in as `qa-admin@flowinqa.com`; run (or find existing analytics usage for) a pipeline on
   Claude Opus 4.5 or Opus 4.6.
2. Open `/analytics`, expand that model's card in Model Details.
3. If it shows "Thinking: Adaptive (effort: max)", this is confirmed -- the real thinking type
   `model_factory.py` would select for that model id is "enabled", not "adaptive".

## Where the fix belongs

Both tuples are hand-copied from each other across a layer boundary (the `capabilities.py`
comment says "by grep... not a shared import" because `model_factory.py` is app-layer and
`capabilities.py` sits on `agents.capabilities`, the kernel layer). `capabilities.py` already
imports `ModelCatalog` from `backend/agents/capabilities/model_catalog.py:51`; `model_factory.py`
does not import it today but is free to -- both are backend, and `model_catalog.py` is
explicitly kernel-pure data with no reverse dependency on either caller. The fix belongs as ONE
canonical fragment tuple/field in `model_catalog.py` (e.g. a `thinking_mode:
Literal["adaptive", "enabled", None]` per `ModelEntry`) that both `capabilities.py:189` and
`model_factory.py:126` read, instead of two literal tuples a comment cannot enforce. That also
lets the frontend (`AnalyticsPage.tsx:826-831`) render the real per-model type instead of a
hardcoded string, so a future new catalog entry cannot silently drift the same way a third time.

## Fixer finding (2026-09-17, 5-fixer): not fixed, escalated for a product decision

[FIX-524](20260917-1639-FIX-524.md) fixed only the ISS-667 label (`Adaptive (effort: max)` is now
`Adaptive`). This card stays open, its test stays red, and the decision request is
`ESCALATIONS.md#qa-ps-009`. No fix could be applied without a decision, for three reasons:

1. **The test cannot pass under this card's own fix.** The Sonnet 5 and Opus 4.5 fixtures in
   `frontend/src/components/analytics/AnalyticsPage.test.tsx:383-388` and `:397-402` have the same
   shape: `label`, `tier`, `context_window` and `thinking_supported: true`. Neither has a thinking
   type. If the frontend renders a backend-served per-model type, as "Where the fix belongs" above
   proposes, the field is missing in both fixtures, so one of the two tests fails whichever default
   is chosen. Only a model-id list on the frontend can tell the two ids apart. That list is exactly
   what [FIX-491](20260907-1239-FIX-491.md)'s locked constraint forbids: "model metadata must come
   from /api/capabilities live catalog (INV-12 single-source; SC-001 no hardcoded model-id list on
   frontend)".
2. **What the row should show is undecided.** "Expected" above offers two options: hide the row for
   Opus 4.5/4.6, or show "Enabled". The test picks "Enabled", but no decision is recorded.
3. **The blast radius is wider than Opus 4.5/4.6.** Every catalog model outside the adaptive
   fragments gets `enabled` thinking at runtime: `_thinking_type` returns `"enabled"`
   (`backend/app/agents/model_factory.py:126`), and the field is sent whenever
   `THINKING_BUDGET_TOKENS > 0` (`:115`; the default is 32767 at `backend/app/core/config.py:170`).
   That includes Haiku 4.5, Haiku 3.5, Sonnet 4.5, Sonnet 4.6 and Sonnet 4
   (`backend/agents/capabilities/model_catalog.py:74, 91, 103, 115, 168`). None of them shows a row,
   because none matches `_THINKING_FRAGMENTS`. `model_factory.py` is the only place that builds a
   `thinking` field. If "the row shows the runtime type" is the rule, those five models would show
   "Thinking: Enabled" too, which contradicts the reporter's "the Haiku 4.5 card does not show a
   Thinking row, which is correct" (`BUGS.md#qa-ps-009`). The other reading follows the stated
   intent of `_THINKING_FRAGMENTS` ("support adaptive thinking", `capabilities.py:165-168`). Under
   that reading, dropping `"opus-4"` is the one-token fix, but the ISS-667 decision says not to
   change `_THINKING_FRAGMENTS`.
