## What was wrong

This is bug report QA-KB-028. The test "coalesces concurrent 401s into a SINGLE refresh call" in
[frontend/src/lib/api.refreshRetry.test.ts](../../frontend/src/lib/api.refreshRetry.test.ts) is
the only test that runs the real `refreshOnce()` single-flight guard. It passed whether or not the
guard existed. With `if (!inFlightRefresh) {` changed to `if (true) {` (`api.ts:429`), the file
still reported `Tests 6 passed (6)` in three cold runs out of three (see the Validation section of
[ISS-824](20260922-1947-ISS-824.md)). Deleting the guard would have kept CI green.

## Root cause

[ISS-824](20260922-1947-ISS-824.md) has the full analysis. In short:

- The guard is `inFlightRefresh` / `refreshOnce()` at `frontend/src/lib/api.ts:426-434`.
  `fetchWithAuth` calls it at `api.ts:553` (`const fresh = await refreshOnce();`).
- `getMe` is `cachedGet<User>("/api/auth/me", token)` (`api.ts:941`). `cachedGet` keys on
  token plus path (`api.ts:639`) and returns the stored promise on a hit (`api.ts:641`).
- The old burst was three identical `getMe(STALE(5))` calls. They shared one promise, so one
  `/api/auth/me` request, one 401 and one `/api/auth/refresh` reached the guard. `refreshCalls`
  was 1 with or without the guard.

The application is correct. One `/api/auth/me` request for three identical calls is the intended
outcome of [FIX-618](20260922-1945-FIX-618.md), so `api.ts` stays unchanged.

## Change

The change is in the test only. The test writer replaced the body of the coalesce test exactly as
the ISS-824 analysis specified. This fixer changed no source file, and this bug changes no line
of `api.ts`. When the fix was checked, `git diff --stat -- frontend/src/lib/api.ts` was empty.
At 21:15 a fixer working on another bug edited the `ArtifactNode` interface (`api.ts:1494-1515`,
type-only). That interface is outside the refresh path: `refreshOnce`, `cachedGet` and `getMe`
still match HEAD.

- The import (`:2`) adds `getMfaStatus` and `getPreferences`.
- The burst (`:136-178`) is `getMe`, `getPreferences` and `getMfaStatus`, all called with
  `STALE(5)`. They use three different paths (`/api/auth/me`, `/api/settings/preferences`,
  `/api/auth/mfa`), so they get three different cache keys and produce three 401s.
- The fetch mock answers each replayed request with `{ path: url }`. The test asserts that each
  caller gets its own response back.
- The test first asserts a precondition: exactly three fetches carried `Bearer ${STALE(5)}`
  (`:172`). If an upstream cache or dedup collapses the burst again, the test fails at this point
  instead of passing vacuously.
- The original assertion stays: `refreshCalls` has length 1 (`:177`).

## Why there

The defect is in what the test proves, so the fix belongs in the test. The analysis rejected two
alternatives:

- Removing `getMe` from `cachedGet` would undo QA-PS-035 and would fix nothing the guard needs.
- Asserting only the `/api/auth/me` count would make the collapse visible, but it could not make
  the guard testable. The old burst makes three fetches whether the guard is on or off.

The burst has to go through `request()`/`fetchWithAuth`. Callers that use `authedFetch`, such as
`getRunSandboxZip`, never reach `refreshOnce()` (`api.ts:470-472`).

Two existing claims relied on this test. Both are now backed by a test that actually exercises
the guard:

- the "single-flighted refresh" decision in [ADR-0024](20260824-2100-ADR-0024.md), through its
  `verification.test_files`
- the `api.refreshRetry.test.ts` regression guard listed in [FIX-618](20260922-1945-FIX-618.md)

## Not addressed

ISS-824 records one more finding under "Also observed", and the analysis deliberately did not
open a card for it. The test header claims "three bounds" are pinned, but deleting
`path !== REFRESH_PATH &&` (`api.ts:550`) still leaves the file 6/6 green. That clause cannot be
reached today, so it is a defensive clause under an over-claiming comment, not a live defect.
This fix leaves the header untouched.
