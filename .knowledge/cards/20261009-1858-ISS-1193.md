# ISS-1193

**Register source:** found during the regression sweep for [FIX-783](20261009-1855-FIX-783.md) (QA-KB-124), 2026-10-09.
It is not caused by that fix: the failing id is identical on a copy of `backend/` that holds HEAD's `factory.py` and
`engine.py` (`evidence/qa-kb-124/fix-02-threaded-fix-runs.txt`, section D). Not analyzed. Only the observation is recorded here.

## Observed

The test was run one file at a time, offline, with `cd backend && .venv/bin/python -m pytest tests/agents/test_conditional_loop_budget_t24.py -q -p no:cacheprovider`.
The result was `1 failed`, both on the fixed tree and on the HEAD copy. The failing test is
`test_always_retry_stops_looping_but_completes_cleanly_with_a_warning`, and it fails at `test_conditional_loop_budget_t24.py:89`:

    AssertionError: a suppressed loop-cap convergence limit must not, by itself, degrade a run whose deliverable
    resolved cleanly: {... 'final_output': 'custom-agent:done default output.', 'deliverable_filename': 'greeting.md',
    'warnings': ["step 'greet' would be revisited 4 time(s), exceeding loop_max_iterations=3 (R-07) — stopped looping,
    continuing forward"], 'status': 'degraded', 'published_status': 'degraded', ...}

The payload has no `degraded_reason` key. The earlier assertions in the test pass: exactly one `budget_aborted` with
`dimension: loop_iterations`, and one `pipeline_complete`.

## Expected

The A14 contract, which landed in `1e329e47b` (2026-09-04) and is described in
`backend/tests/agents/test_loop_cap_warning_not_degraded.py`'s docstring: a tripped R-07 loop cap is a WARNING. A run
whose deliverable resolves and in which no agent failed completes cleanly, with a `warnings` entry. Only a capped run
that ends WITHOUT a deliverable stays `degraded`. That counter-case file passes today (`1 passed`).

## What would settle it

Find what sets `status`/`published_status` to `degraded` on this payload when there is no `degraded_reason`. Then decide
between two cases. If it is a regression of A14, fix the engine and keep the test. If a later intentional change made
any warning degrade the run, this test is stale and the change needs its own card. In that second case the decision is
the product owner's, and the test must not be edited to match the app until someone has made it.
