# ISS-753

## Register entry

Root-caused from the user's own report (relayed verbatim by the dispatch): "Another bug is on
Steps: on changing version it changes the agents in step, but starting point sometimes stuck at
v3 and showing that starting point, where each of the revision have different starting point."
No LEDGER row names this exact defect yet; the nearest neighbor, **QA-PS-033**, is a different
defect on a different precondition — see "Is this QA-PS-033?" below.

Investigated against a fresh, fully-healthy 6-member `ppt`/`ppt_revision` family (v1
`4d55165d…` … v6 `95351433…`, all six with real git tags) and two independent browser sweeps
(forward v1→v6 ×2 passes, then reverse v6→v1 + alternating far jumps) supplied by the dispatch.
No browser was driven in this pass — code and DB only, per the dispatch's own instruction.

## Root cause — CONFIRMED

**1. `VersionView` never captures the member run's own input.**
`PreviewPanel.tsx:536-549` declares the per-version snapshot type:
```ts
type VersionView = {
  id: string;
  content?: string;
  agents: AgentRunState[];
  pipelineState: PipelineRunState;
  agentOutputs: AgentOutputItem[];
  genericDeliverable?: GenericDeliverable;
};
```
There is no `runInput` (or brief/input) field. `versionViewFrom(run: WorkflowRun)`
(`PreviewPanel.tsx:551+`) builds `agents`/`pipelineState`/`agentOutputs`/`content`/
`genericDeliverable` from the fetched `run`, but never reads `run.input` — even though `run`
(fetched via `getWorkflow`, `PreviewPanel.tsx:830`/`:904`) carries that field, the same field
`page.tsx` reads at `fullRun.input`/`run.input` elsewhere (`page.tsx:2728`, `:2941`) to build a
clean brief.

**2. Both places that resolve a version go through this one function — and only this one.**
`versionViewFrom` has exactly two callers:
- `handleSelectVersion` (`PreviewPanel.tsx:808-838`, the in-panel version-dropdown chokepoint):
  `const run = await getWorkflow(token || "", memberId); setViewingVersion(versionViewFrom(run));`
  (`:830-831`).
- The `/versions/{n}` URL-pin deep-link effect (`PreviewPanel.tsx:899-913`): same shape,
  `setViewingVersion(versionViewFrom(run))` at `:905`.

Both correctly populate `viewingVersion`, proven by the fact that `effAgents`/`effPipelineState`/
`effAgentOutputs` (`PreviewPanel.tsx:950-952`, each `viewingVersion?.X ?? X`) DO correctly follow
the selected version — this is exactly why the sweep observed the Agents list updating correctly
on every single selection. There is simply no `effRunInput` in this list, because `VersionView`
never carries the data such a derivation would read from.

**3. The Steps tab is fed the raw, un-derived prop.**
`PreviewPanel.tsx:1783`: `runInput={runInput}` — passed straight into `AgentThinkingTab`, not
`viewingVersion?.runInput ?? runInput`. `AgentThinkingTab.tsx:97` destructures it and
`AgentThinkingTab.tsx:462-465` forwards it verbatim to `StartingPointCard`:
```tsx
<StartingPointCard
  input={runInput}
  originalBriefRootRunId={originalBriefRootRunId}
  revisionParentVersion={revisionParentVersion}
/>
```
(Note `originalBriefRootRunId`/`revisionParentVersion` ARE correctly version-aware — they derive
from `activeRunId` at `PreviewPanel.tsx:771/786-788`, which itself correctly tracks
`viewingVersion?.id ?? unpinnedRunId`. Only the `input` prop is wrong. This is the whole
defect in one line: two of `StartingPointCard`'s three props already follow the version; the
third does not, because it alone was never threaded through `VersionView`.)

**4. `runInput`'s real source is a page-level state variable that a version switch never touches.**
`PreviewPanel`'s `runInput` prop traces to `DashboardLayout.tsx:3313`: `runInput={submittedBrief}`.
`submittedBrief` (`page.tsx:2243`, `useState<string>("")`) is set in exactly two places, both
full page-level run-navigation events, neither of which is the in-panel version dropdown:
- `handleSelectWorkflowRun` — opening a run from History / a cold page load
  (`page.tsx:2936-2943`, comment at `:2936-2938`: *"Wire the VIEWED run's brief into the Steps
  surface (runInput=submittedBrief via DashboardLayout) so AgentThinkingTab's ... header reflect
  the opened run"*).
- `handleSwitchToLiveRun` — switching to a different LIVE running run via a header badge
  (`page.tsx:2724-2733`, comment: *"update submittedBrief to the new run's brief so the Steps
  panel 'Starting point' card shows the correct brief immediately"*).

Neither `handleVersionMenuSelect` (`PreviewPanel.tsx:849-870`) nor the URL-pin effect
(`:899-913`) calls back up into `page.tsx` to update `submittedBrief` — both are entirely local
state changes inside `PreviewPanel.tsx`. So no matter which family member the dropdown selects,
`submittedBrief`/`runInput` keeps whatever value it held from the last full-page run navigation.

## Why intermittent ("sometimes stuck at v3")

Not order-dependent and not distance-dependent — disproven directly by the sweep data: forward
(v1→v6 ×2), reverse (v6→v1), and alternating-far-jump (v1→v6→v2→v5→v3→v4) passes all produced
the IDENTICAL result, 10/10 and 10/10: "Starting point" showed `"Subsea Fibre Splice Operations"`
(v1's own brief) on every selection except v1 itself, regardless of direction or jump size.

It is **mount/navigation-dependent**: pinned to whichever run's `.input` `page.tsx` last captured
into `submittedBrief` via one of the two setters above. In THIS family the run screen was
entered at v1's own id (`4d55165d…` — the dispatch's own `sandbox: runs/.../4d55165d.../` path
names it), so `submittedBrief` was set to v1's brief once, on page load, and never again — hence
"always v1" in this sweep. The ORIGINAL reporter's "stuck at v3" is the same mechanism with a
different frozen value: on whatever occasion produced that report, the run last opened/switched-to
(via History, a chat "Answer in Steps" deep link, or a live-run badge) was v3's own run, freezing
`submittedBrief` at v3's brief instead — then every subsequent dropdown pick kept showing v3's
text because the dropdown never touches `submittedBrief` either way. Same bug, different frozen
value depending on entry point.

## Is this QA-PS-033?

**No — a distinct defect, on the opposite precondition.**

QA-PS-033's documented mechanism (`BUGS.md#qa-ps-033`): `handleVersionMenuSelect`'s
`sortedMembers.find((m) => m.git_tag === tag)` returns `undefined` when **no member has that
git_tag populated at all**; the `else` fallback then fires
(`setSandboxSelectedRef(tag)` only) and `handleSelectVersion` is **never called** — so
`viewingVersion` stays `null` and `effAgents`/`effPipelineState`/`effAgentOutputs` **all** fall
back to the live run's own props together. Under that mechanism, Agents and Starting point would
BOTH stay frozen on the live run.

This family's 6 members all have real git tags (confirmed by the sweep's own
`GET .../sandbox/refs` calls and by the version-dropdown offering all six). So `member` always
resolves, `handleSelectVersion` runs every time, and `viewingVersion` is correctly set — proven
by the Agents list tracking correctly on 10/10 selections in both sweep passes (the one exception
is a transient render-order race, a different bug — see [ISS-758](20260922-1421-ISS-758.md)).
QA-PS-033's fallback branch requires an **undefined** `member`; this bug requires a **defined**
`member` whose fetched run is simply missing one field from its client-side projection. The two
are mutually exclusive on any single selection.

Independent corroboration, from the opposite direction: the existing validator trace at
`UNREPRODUCIBLE.md#qa-ps-033` tested a tagged member (v3, its own "control" case) via the literal
dropdown-click path and found Steps correctly showed that version's own agents — noting *"This
matches FIX-516 ... which appears to already cover the general case."* That validation pass never
inspected the "Starting point" text specifically (its evidence table only covers agents / chip /
pipeline state), so it could not have caught this defect even on a path that was, in fact,
already exercising it.

**Conclusion**: QA-PS-033 should stay its own row — its own described mechanism (the
untagged-member fallback) is real code, but per that trace's own dropdown/`sandbox/refs`
evidence, it is not reachable via the UI as currently built. This card (ISS-753) is a new,
independent defect that only manifests on a **fully-tagged** family — precisely because
`handleSelectVersion` DOES run in that case, which is what exposes the missing `runInput`
derivation.

## Fix direction (not applied — issue only)

**The single shared place**: `VersionView` (`PreviewPanel.tsx:536-549`) and `versionViewFrom`
(`:551+`). Both call sites (`handleSelectVersion` and the `/versions/{n}` URL-pin effect) route
through this one function, so extending it once fixes the dropdown AND the deep-link path without
touching either caller.

1. Add a field to `VersionView` (e.g. `runInput?: string`), populated inside `versionViewFrom`
   from the fetched `run.input`.
2. Thread `viewingVersion?.runInput ?? runInput` at the two consumers that currently receive the
   raw prop: `PreviewPanel.tsx:1783` (Steps/`StartingPointCard`) and `PreviewPanel.tsx:1745`
   (Files tab — see [ISS-754](20260922-1414-ISS-754.md)).

**What breaks if done carelessly:**
- `StartingPointCard.tsx:33`'s own prop docstring says it expects *"The run's raw input string;
  parsed via C1 `parseRunInput`."* But `submittedBrief` (what `runInput` carries today on the
  live/reopen path) is already PARSED and first-line-trimmed
  (`page.tsx:2728-2730`/`:2941-2943`: `parseRunInput(...).revisionInstruction ?? .brief`, then
  `.split("\n")[0].trim()`). The new `VersionView.runInput` must be populated with the SAME
  shape — parsed and trimmed — not the raw `run.input`, or `StartingPointCard` renders two
  different shapes of text depending on whether a version is pinned. Mismatched parsing here is
  the exact class of bug FIX-130/KAN-116 already fixed once (marker-laden `===` blobs leaking
  into a title-like field).
- Do not touch `handleVersionMenuSelect`'s `else` fallback (`PreviewPanel.tsx:864-869`, the
  QA-PS-033 code path) while fixing this — its current behavior (Workspace ref flips, Steps
  stays live) is explicitly documented as correct for an untagged/in-progress member, and is a
  separate row.
- Frontend-only (React state derivation). No backend route, kernel, manifest, or
  `CapabilityRegistry` involvement — SC-001 and the registry invariant are not at risk.
