## What happened

INFERRED sibling of [ISS-331](20260828-1840-ISS-331.md), derived from a
source-code read while analyzing that bug — not yet independently driven
live in a browser.

`frontend/src/components/preview/MarkdownPreview.tsx` renders generic
markdown deliverables (user stories, docs) and carries TWO independent Copy
buttons, both sharing the same false-positive variant of ISS-331's mechanism.

## Root cause (confirmed by direct read — false-positive variant, two call sites)

`MarkdownPreview.handleCopyAll`, `MarkdownPreview.tsx:49-53` (header "Copy
All" button):

```
const handleCopyAll = () => {
  navigator.clipboard.writeText(content);
  setCopied(true);
  setTimeout(() => setCopied(false), 2000);
};
```

`CodeBlock.handleCopy`, `MarkdownPreview.tsx:174-178` (per-rendered-code-block
Copy button, a separate component/state instance mounted once per fenced
code block in the markdown output):

```
const handleCopy = () => {
  navigator.clipboard.writeText(code);
  setCopied(true);
  setTimeout(() => setCopied(false), 2000);
};
```

Both are fire-and-forget: `writeText` is not awaited, has no
`.then()`/`.catch()`, and `setCopied(true)` runs unconditionally on the next
line. Same missing-error-handling mechanism as
[ISS-331](20260828-1840-ISS-331.md), same false-positive shape as
[ISS-556](20260829-0208-ISS-556.md)/[ISS-557](20260829-0208-ISS-557.md): both
buttons claim "Copied"/"Copied!" even on a silently failed write.

**What would confirm this live:** open any markdown-rendered deliverable
(e.g. a user-stories or docs run), click "Copy All" and a per-code-block
Copy button, and verify with a clipboard write-interception whether content
actually lands when the write is made to fail.
