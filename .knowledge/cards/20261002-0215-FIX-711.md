# FIX-711

## What was wrong

The bug is QA-KB-037. On `/runs/{id}`, pick a version and then another before the first `GET /api/runs/<id>` returns.
When the older pick's response lands last it overwrites the newer pick, and the view stays wrong until the next
selection or a reload. Steps agents and tokens, Files, Preview, the chip and the read-only banner all show the abandoned
version while the URL names the new one. The validator reproduced it 3/3 in Chrome: v7 then v2 showed v7's 5 agents
and 112.4K tokens under `/versions/2/steps`. The root card is [ISS-758](20260922-1421-ISS-758.md). Two siblings share
the mechanism. In [ISS-938](20261001-2233-ISS-938.md), browser Back during a pending pick re-applies the abandoned
version over the one the URL names. In [ISS-940](20261001-2233-ISS-940.md), the History detail pane's version chips
apply in arrival order.

## Root cause (from the cards, re-checked before editing)

- `PreviewPanel.tsx` `handleSelectVersion` (HEAD 024c03ef8 `:884-921`, now `:892-930`) awaited `getWorkflow`, then
  called `setViewingVersion(versionViewFrom(run))` (and `setViewingVersion(null)` in its catch) without checking that
  the pick was still the latest. The blast radius was re-checked by grep before editing: four call sites, all in
  `PreviewPanel.tsx` (`handleVersionMenuSelect` null and tag paths, `handleBackToLatest`, the chat deep-link consumer),
  all routed through this one function.
- ISS-938: `viewingVersion` has two more writers, the no-pin branch of the `[pinnedVersion]` effect and the URL-pin
  effect. Both move with the URL, not with the handler, so a counter only the handler bumps cannot see a Back press.
- `WorkflowHistory.tsx` `handleSelectVersion` (`:389-407` at HEAD) called `onOpenRun(full)` / `setSelectedRun(full)`
  after its await, in arrival order. Its one caller is the `onSelectVersion` prop handed to `RunDetailPage` (now `:689`).

`PreviewPanel.tsx` gets 5 added lines and 3 edited lines, and `WorkflowHistory.tsx` gets 5 added lines. Nothing else in
either file changed. The QA-KB-044 / [ISS-154](20260813-0819-ISS-154.md) hunks already in `PreviewPanel.tsx` (`:28`,
`:575`, `:639`, `:1835`) were left as they were.

- **One guard in the shared handler.** It covers all four PreviewPanel callers. No caller changed, and neither did
  `versionViewFrom`, `api.ts`, `DashboardLayout` or `page.tsx`.
- **The counter is a ref.** It must not cause a re-render, and it must not live at module scope: PreviewPanel survives
  a version switch, because that switch is `window.history.pushState` with no remount.
- **No AbortController.** `getWorkflow` is single-flighted ([FIX-637](20260922-2358-FIX-637.md)). The handler and the
  URL-pin effect share one promise, so aborting would cancel the other consumer's request. The counter throws away the
  stale result and leaves the request alone.
- **No constraint the cards named was disturbed.** `handleVersionMenuSelect` still stages `intendedSandboxRef` before
  anything changes `activeRunId` ([FIX-603](20260922-1440-FIX-603.md)), and a discarded apply sets nothing.
  `onTabSelect` still writes the pin on every selection ([ISS-296](20260828-1724-ISS-296.md)). The `unpinnedRunId`
  shortcut is unchanged ([ISS-607](20260829-1450-ISS-607.md) / [FIX-412](20260829-1703-FIX-412.md)).
- **WorkflowHistory.** The stale call returns inside `try`, so its `finally { setLoadingDetail(false) }` still runs, as
  it did before.

## Behaviour now

- **Normal switching** is unchanged: the latest pick always passes the check. When the URL round-trips, the URL-pin
  effect bumps the counter and becomes the applier for that pick. It fetches the same member through the same
  single-flighted promise, so a successful pick ends exactly as before.
- **A failed pick behaves differently. ISS-938 named this trade-off, and it has now been observed.** The URL-pin effect
  supersedes the handler's guarded catch, and the effect's own catch (`PreviewPanel.tsx:1031`) only warns, so a failed
  pick no longer clears to live. A scratch probe pinned v1, picked v2, and rejected `getWorkflow(m2)` after the URL
  round-trip:
  - before this fix: `banner=[] chip=[Viewing v2▾]`, live content under a v2 chip;
  - after it: `banner=[Viewing v1 (read-only)] chip=[Viewing v2▾]`.

  Both are mislabelled. Which one is right is a UX question, carded as [ISS-955](20261002-0215-ISS-955.md).

## Not fixed here (each one has an open card)

- [ISS-939](20261001-2233-ISS-939.md) is still open. While a pick loads, Steps, Files and Audit still show the previous
  version under a chip that already names the new one. The card leaves this to a UX call between its options (a), (b)
  and (c). Its test stays `it.fails`. ISS-758's acceptance note says it is not a verification criterion for QA-KB-037.
  Whichever fix is chosen can reuse this `selectGen` counter.
- [ISS-954](20261002-0215-ISS-954.md) is new and open. ISS-940 named two more sites with the same arrival-order shape
  but gave no fix direction for them: the notification and completion-toast open handlers in `DashboardLayout.tsx`
  (`:2907-2909`, `:3462-3464`).
- **ISS-940's reachability claim was wrong.** Commit `dfd167387` ([FIX-584](20260922-0925-FIX-584.md), 2026-09-22, an
  ancestor of HEAD) deleted the row "Chain" action and `handleChainAffordance`. That was the only caller of
  `handleSelectRun(run, { forChain: true })`, and `grep forChain` in non-test source now finds only its definition.
  DashboardLayout always passes `onOpenRun` (`DashboardLayout.tsx:3053`), so `selectedRun` is never set. The History
  detail pane and its version chips therefore cannot be reached from any user path at HEAD. This guard covers the
  `!onOpenRun` branch, which the tests use and any future way back into that pane would use. `handleSelectRun`'s
  forChain post-await apply (`WorkflowHistory.tsx:371-377`) has no caller and was left alone.
