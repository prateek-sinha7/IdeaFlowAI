# ISS-1122

**Register source:** sibling derived during the `QA-KB-102` analysis on 2026-10-08 (root [ISS-1103](20261008-0016-ISS-1103.md)). Not its own bug row.

**Confidence:** CONFIRMED by the offline probe (`evidence/qa-kb-102/analysis-04-silent-resume-endpoint-probe.txt`, scenario A in three variants). The probe seeds the prior attempt's events by hand; a real earlier attempt writes more events, but `_reconcile_terminal_status` reads only the types the probe seeded.

## Condition

A user resume produces no event after its `run_resuming` marker (any path of [ISS-1103](20261008-0016-ISS-1103.md)), so `_drive_user_resume` goes on to `_reconcile_terminal_status` as if the attempt had run and finished.

## Expected vs actual

Observed in the probe, same refused resume, three prior states:

| status before | `.error` before | status after | `.error` after | `completed_at` |
|---|---|---|---|---|
| `failed` | `prior attempt: step a raised ValueError('boom')` | `failed` | unchanged: the previous attempt's text | overwritten |
| `cancelled` | the same text | `cancelled` | unchanged | overwritten |
| `degraded` | the same text | **`failed`** | unchanged | overwritten |

Why, in `run_commands.py`:

- `last_reattempt_seq` is the new marker, so `current_attempt_completes` is empty and `failed_current` is false; `degraded_current` is false; the branch at `:932-935` falls to `else: new_status = "failed"`. A `cancelled` run takes the earlier `if cancelled and not resume_supersedes` branch (`:905-906`) and goes back to `cancelled`.
- `this_attempt` is empty, so `derived` is `None` and the code "leave[s] the existing `.error` value untouched rather than invent one" (`:997-1000`). The row then names a step of the earlier attempt as the reason for this one. That is the shape the code itself calls out at `:944-947` (run 4bdf9398's header chip "kept naming a step that had since succeeded").
- `_persist_resume_status` sets `completed_at = now` on every call (`:1038`).

A degraded run holds partial results the owner chose to keep; a refused resume relabels it `failed`.

## Why the root cause implies it

With no failure event to read, the reconcile's D2 fail-safe cannot tell "ran and failed" from "never started". [ISS-1103](20261008-0016-ISS-1103.md)'s fix gives `.error` its reason, because `_reconcile_terminal_status` already derives it from a `pipeline_failed` after the marker (`:986-998`). It does not change the other two columns.

## Open question for the fixer (not an escalation)

After a refused resume, which status should a `degraded` run carry: `failed` with the reason (today, and what the root fix yields), or `degraded` with the reason? The expected result in the bug report is "marks the run failed", so the safe default is `failed`; this card only makes sure the relabel and the `completed_at` rewrite are chosen rather than inherited.

## Resolution (5-fixer, QA-KB-102, 2026-10-08)

Resolved by [FIX-768](20261008-1540-FIX-768.md). The refusal's own `pipeline_failed` now gives `.error` this attempt's reason. The open question is answered with the safe default: a refused resume of a `degraded` run reads `failed` (the bug's expected result), and `completed_at` is the refusal time. A refused resume of a `cancelled` run also reads `failed`, by the existing ISS-316 rule.
