## What was wrong

[FIX-328](20260828-2014-FIX-328.md) closed the URL/network half of
**BUG-20260828-090732-runs-id-versions** (`bug-hunter/ledger.md`): the
`/versions/{v}` segment now survives a tab click and the pinned member is
actually fetched. The bug was REOPENED because its own reproduction step 5
still failed — at `/runs/{rootId}/versions/2/files` the Files tab's "Final
output" reported **241.6 KB**, the ROOT run's v1 deliverable, not v2's
**83.5 KB**. Two mechanisms FIX-328 explicitly did not touch:

- [ISS-300](20260828-1726-ISS-300.md) — FilesTab was wired to the RAW content
  props, so no pin of any kind ever reached it.
- [ISS-296](20260828-1724-ISS-296.md) — the Version menu, the primary way a
  user pins, only set React state; `routes.runVersion` had zero application
  callers, so a pin was unshareable, lost on refresh, and invisible to the
  route FIX-328 had just taught to carry it.

## Root cause

**1. `frontend/src/components/preview/PreviewPanel.tsx:1319`** — the
`<FilesTab>` mount passed `userStoryContent={userStoryContent}
pptContent={pptContent} prototypeContent={prototypeContent}`: the live/root
values, never the version-aware `effUserStoryContent`/`effPptContent`/
`effPrototypeContent` the same component already computes at
`PreviewPanel.tsx:625-629` and renders on the Preview tab. `FilesTab` derives
its whole file list from those props —
`deriveDeliverableFiles(workflowType, {...})` at
`FilesTab.tsx:625`, with `size: formatSize(<prop>.length)` at
`FilesTab.tsx:389,397,414,422` — so the hero's name, size and downloadable
content were all the un-pinned run's. Confirmed against the API: run
`77f74563-…` (v1) `.output` is 247,394 chars → 241.6 KB, revision
`ef86e750-…` (v2) is 85,529 → 83.5 KB.

**2. `frontend/src/components/preview/PreviewPanel.tsx:555-570`** —
`handleSelectVersion` called only `setViewingVersion(...)`, and
`handleBackToLatest` only `setViewingVersion(null)`. Neither touched the URL,
and PreviewPanel has no router of its own. `DashboardLayout`'s
`handlePreviewPanelTabSelect` was the only code in the app that could build a
`/versions/{v}` route, and it read the pin exclusively from its
`pinnedVersion` prop — i.e. from the URL. A pin the URL did not already
carry could not be written by any user action.

## What changed and why there

**`frontend/src/components/layout/DashboardLayout.tsx`** —
`handlePreviewPanelTabSelect` takes an optional `version` second argument and
resolves the pin once, `const pin = version === undefined ? pinnedVersion :
(version ?? undefined)`, feeding all five `routeMap` entries. Three states in
one place: omitted keeps the URL's pin (every existing tab click, byte-
identical), a number pins, `null` clears. This is the same single chokepoint
ISS-230's blast radius identified — `routes.runSteps/runFiles/runWorkspace/
runAudit` still have exactly one caller each, so the Version menu gets
correct routes for all five tabs without a second route-building site.

**`frontend/src/components/preview/PreviewPanel.tsx`** —
`handleSelectVersion` and `handleBackToLatest` call
`onTabSelect?.(activeTab, …)`, routing the write through that chokepoint and
carrying the CURRENT tab, so picking a version never also changes which tab
is on screen. `null` is sent for the latest member, matching the menu's
existing back-to-live semantics (`memberId === latestId`), so the URL and the
local override agree in both directions. Local state is still set as well as
the URL — the menu keeps working in the renders that mount PreviewPanel
without `onTabSelect` (four `*.test.tsx` files do exactly that), and the
URL-driven pin effect FIX-328 added simply re-resolves the same member id.

**`frontend/src/components/preview/PreviewPanel.tsx:1319`** — `<FilesTab>` is
handed `effUserStoryContent`/`effPptContent`/`effPrototypeContent`. Fixed at
the mount, not inside FilesTab: the `eff*` values are the override that
PreviewPanel alone owns, and every other pinned-aware surface
(`renderDeliverable`, `activeContent`, `workspaceRunId`) already reads them —
FilesTab was the sole consumer that did not.

No new prop was threaded for the version write, and `usePathname` was
deliberately NOT introduced into `DashboardLayout` — the same rejection
FIX-328 recorded, for the same reason: three `DashboardLayout.*.test.tsx`
mocks do not provide a router, so it would have meant editing tests to
accommodate the app.
