# ISS-837

## Sibling of ISS-836 (QA-PS-044) — a second, unrelated no-guard fetch path

INFERRED — derived from reading the same `LaunchWizard.tsx` effect
[ISS-836](20260922-2018-ISS-836.md) traces `getWorkflowDetail` from, not
yet reproduced with a live capture.

QA-PS-044's original report (`BUGS.md#qa-ps-044`) also lists `GET
/api/templates` x2 and `GET /api/design-systems` (33.2 KB) among the
duplicate/unwanted calls on `/create/ppt`. Neither
[ISS-794](20260922-1827-ISS-794.md) nor
[ISS-836](20260922-2018-ISS-836.md) explains these — both are about
`frontend/src/lib/api.ts`'s `request()`-based functions, and the
template/design-system catalog is fetched through a COMPLETELY DIFFERENT,
bespoke code path.

## What was read

`frontend/src/components/workflow/LaunchWizard.tsx:617-654`:

```tsx
useEffect(() => {
  if (!authChecked) return;
  const token = getToken();
  if (!token) return;
  let cancelled = false;

  listPrototypeTemplates(token)          // :623 — GET /api/prototype/templates
    .then((t) => { if (!cancelled) setWebTemplates(t); })
    ...
  listPPTTemplates(token)                // :630 — GET /api/ppt/templates
    .then((t) => { if (!cancelled) setDeckTemplates(t); })
    ...
  listDesignSystems(token)               // :636 — GET /api/prototype/design-systems
    .then((s) => { ... })
    ...
  return () => { cancelled = true; };
}, [authChecked, router]);
```

Same `authChecked`-gated, `cancelled`-flag-only shape as the
`getWorkflowDetail` effect [ISS-836](20260922-2018-ISS-836.md) traces. But
`listPrototypeTemplates`/`listDesignSystems`
(`frontend/src/lib/prototype-api.ts:59-65`) and `listPPTTemplates`
(`frontend/src/lib/ppt-api.ts:47-49`) do NOT go through `lib/api.ts`'s
`request()` at all — each file has its OWN bespoke `fetch()` wrapper
(`authFetch()` in `prototype-api.ts:37-53`, `apiFetch()` in
`ppt-api.ts:29-40`), confirmed by direct read: neither calls `cachedGet()`,
neither touches `inFlightWorkflows`, neither imports from the same request
pipeline. Every dedup guard added for this whole QA-PS-04x batch
([ISS-801](20260922-1834-ISS-801.md)'s `cachedGet`,
[FIX-616](20260922-1923-FIX-616.md)'s `inFlightWorkflows`) lives inside
`lib/api.ts` and cannot reach these two files.

`/create/ppt` is a deck-only route, yet this effect unconditionally fetches
BOTH template families (`listPrototypeTemplates` — web — AND
`listPPTTemplates` — deck) plus `listDesignSystems`, regardless of `mode`.

## Why this is worth a card

Two independent, plausible explanations for the report's `GET /api/templates`
x2, both real per the code read above, not yet distinguished by a live
capture:

1. **Wasted fetch, not a true duplicate GET:** `listPrototypeTemplates`
   (`/api/prototype/templates`) and `listPPTTemplates`
   (`/api/ppt/templates`) are two DIFFERENT URLs, both fired on every
   `/create/ppt` load though the route only ever needs the deck family. A
   reporter without the exact endpoint names would reasonably describe two
   "template" requests as "the template list fetched twice."
2. **A genuine duplicate:** if this effect's mount timing double-invokes
   the same way [ISS-836](20260922-2018-ISS-836.md) predicts for the
   `getWorkflowDetail` effect two effects above it in the same component,
   any ONE of these three calls could also be firing twice for real.

Both stem from the same missing-guard root shape this whole card family
documents; distinguishing them needs a live network capture, which this
pass does not have tooling for (see NOTE).

## Expected vs actual (to be measured on `/create/ppt`)

- Expected: only `GET /api/ppt/templates` and `GET /api/prototype/design-systems`
  fire (the deck-only surface), each once.
- Actual (per the original report): a "templates" request counted twice —
  either `listPrototypeTemplates` firing unnecessarily alongside
  `listPPTTemplates` (over-fetch, not a dedup bug), or one of the three
  calls genuinely double-firing (same shape as ISS-836).

## Where the fix belongs

If mechanism 1: scope the effect to fetch only the template family
`mode`/`STEPPER_MODE[mode]` actually needs, the same way `dsRequired`/
`dsVisible` (`LaunchWizard.tsx:676-678`, a few lines below this effect)
already conditions other UI on deck-vs-web. If mechanism 2: the same
in-flight-Map pattern as [ISS-836](20260922-2018-ISS-836.md)'s fix, applied
inside `prototype-api.ts`'s `authFetch()` and `ppt-api.ts`'s `apiFetch()`
rather than `lib/api.ts` (these files do not share its request pipeline, so
the guard cannot live in one place for all five functions without first
unifying them — out of scope to decide here). Either way, not a
`LaunchWizard.tsx`-local guard.

## Resolution — 5-fixer, 2026-09-22 (QA-PS-044 line)

No new source change.

**Mechanism 1 (web family fetched on a deck-only open)** is fixed by
[FIX-630](20260922-2115-FIX-630.md): `LaunchWizard.tsx:629` `if (isWeb) {`
picks `listPrototypeTemplates` or `listPPTTemplates`, with deps
`[authChecked, router, isWeb]` at `:647`. Observed,
`npx vitest run src/components/workflow/LaunchWizard.iss837.test.tsx`
(2026-09-22 23:19): `Error: Expect test to fail`, `Tests 1 failed (1)`. That is
XPASS. The marker is left for the 6-verifier.

**Mechanism 2 (the same URL fetched twice through the unguarded
`authFetch()` at `prototype-api.ts:40` / `apiFetch()` at `ppt-api.ts:31`)**
has no trigger in the current tree, so no guard was added:

- Non-test callers (grep): `LaunchWizard.tsx:630/638/658` and
  `composer/DesignPickerModal.tsx:108-109`. DesignPickerModal is composer-only
  and fetches when the modal opens. `store/api/prototype.ts:46`'s
  `listDesignSystems` has zero callers.
- All three LaunchWizard fetch effects wait on `authChecked`. The auth effect
  sets it synchronously (`LaunchWizard.tsx:367` `setAuthChecked(true);`), so
  both StrictMode mount passes skip those effects. They run once, on the
  re-render that the state flip triggers. The test-writer's StrictMode render
  saw one call. FIX-630's cold live capture of the same component saw
  `prototype/templates 1, prototype/design-systems 1`.
- `app/[...view]/page.tsx:4126` renders `<LaunchWizard>` once, after the
  `!mounted || !isAuthenticated` null gate at `:4060`.

With no concurrent caller, a guard would be speculative. If a concurrent caller
is ever added, the fix location is still the one in "Where the fix belongs"
above. The 6-verifier's live `/create/ppt` capture is the check: a count above 1
for `ppt/templates` or `prototype/design-systems` reopens this card.
