# FIX-630

Closes **QA-PS-045** (`BUGS.md#qa-ps-045`) — the Create Prototype wizard loaded
the PPT template catalog and a run-history page it never renders.

## What was wrong

Opening `/create/prototype` fired `GET /api/ppt/templates` (44 KB of deck
templates a web-family wizard never shows) and `GET /api/runs?limit=50` (37 KB
of run history nothing on that route reads). The reporter blamed a
`DashboardPage`/`HomeLaunchGrid` overlay; [ISS-793](20260922-1826-ISS-793.md)
disproved that and found two independent unconditional mount effects instead.

## Root cause

1. `frontend/src/components/workflow/LaunchWizard.tsx:617-654` — one effect,
   commented "Load both template families + the design-system registry once
   authed", called `listPrototypeTemplates` **and** `listPPTTemplates` with no
   reference to `mode`. `LaunchWizard` is the single component behind all four
   launch modes (`STEPPER_MODE`, `LaunchWizard.tsx:81`), so every open of any
   mode fetched the family it cannot render:
   [ISS-828](20260922-1955-ISS-828.md) for `ppt`/`prototype_v2`/`ppt_v2`,
   [ISS-837](20260922-2018-ISS-837.md) for `/create/ppt` specifically.
2. `frontend/src/app/[...view]/page.tsx:1017` — an `isAuthenticated`-only mount
   effect calling `getWorkflows(token, { limit: 50 })`. Hooks run on every
   render of the `[...view]` catch-all regardless of which branch it returns, and
   `/create/ppt` + `/create/prototype` return `<LaunchWizard>` standalone
   (`page.tsx:4100-4104`), so the wizard routes paid for a run-history fetch no
   component on them consumes.

## What changed and why there

**`LaunchWizard.tsx:617-647`** — the template fetch now branches on `isWeb`
(`STEPPER_MODE[mode] === "web"`, already computed at `:236`) and `isWeb` joins
the dependency array so the in-wizard deliverable toggle (`handleModeChange`)
loads the family it switches to. This is the same family ternary
`composer/DesignPickerModal.tsx:108` has always used; that was the only other
caller of these two functions app-wide, and it was already correct. Fixing the
one shared effect closes all four modes at once — the sibling-card prediction —
rather than guarding each route.

`listDesignSystems` was deliberately split into its own effect
(`LaunchWizard.tsx:649-676`) keyed on `[authChecked, router]` only: both
families read the design-system registry (`dsVisible = isWeb || dsRequired`,
`:676-677`), and letting it re-run on a family toggle would re-fire FIX-103's
"apple" auto-select against a `selectedDsId` the user had cleared through
`handleSelectBuiltInDs(null)`.

**`page.tsx:1017-1052`** — the run-history prefetch returns early when
`wizardModeFor(parsedView)` resolves, and is keyed on `viewPathKey` so leaving
the wizard (client-side `router.push(routes.home())`, or the Back control)
still loads the history. `recentRunsRequestedRef` (`page.tsx:824`) keeps it at
one fetch per mount: the URL key alone would re-fetch on the shallow
`history.pushState` the run-detail tabs use, which changes `usePathname`
without remounting.
