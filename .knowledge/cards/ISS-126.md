# ISS-126

## Title

LOCUS AND SCOPE BOTH CORRECTED 2026-08-12 (FIX-245). (1) The stated locus is wrong and it changed the fix. A terminal run NEVER opens an SSE stream — page.tsx:2171 gates attachRun on non-terminal — so run_stream.py is never entered on this path. The frames come from GET /api/runs/{id}/events replayed at page.tsx:2234-2247. Both backend options rejected in this row were therefore aimed at a code path the symptom does not traverse; their rejection stands, but neither would have worked. (2) "Affects only runs corrupted BEFORE FIX-240" was FALSE — ISS-124s two app-layer driver terminals were still minting fresh corrupted runs until FIX-244 landed the same day, so ISS-124 was a prerequisite, not a sibling. FIX-240's data-repair guard only covers the CURSORED reattach; a fresh reopen of an already-corrupted run still renders an open gate. The guard added at run_stream.py:255 suppresses the D-14g gate re-arm when the persisted status is terminal — but that branch is reached only when after_seq > 0. Opening a run from history sends no Last-Event-ID, so after_seq == 0 and the symptom instead comes from step 1, the durable replay itself (run_stream.py:196-200), which faithfully yields the orphaned review_gate_ready row that is genuinely in the log. The FE rebuilds "Awaiting approval" + Stop from that frame. Deliberately not fixed here: filtering rows out of the durable replay would make the SSE stream disagree with the log it is replaying and break Last-Event-ID semantics, and synthesising a terminal frame on the wire would install the second source of truth INV-12 exists to prevent. The honest fix is front-end: dashboard/page.tsx already reads fullRun.status (:2399-2405) and already clears reviewGateData/activePipelineRunId on pipeline_cancelled` (:1192-1200, :1527-1561) — it should apply the same clearing when the fetched run status is terminal, regardless of what the replay contained. Affects only runs corrupted BEFORE FIX-240 (see ISS-123); new runs persist their terminal correctly.
