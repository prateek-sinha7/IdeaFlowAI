# ISS-088

## Title

**The local backend cannot be stopped by SIGTERM while any run is streaming, so `shutdown_run_infrastructure()` never executes locally at all — and even where it does execute it does not stop the runs.** Two independent facts, both verified 2026-08-12. (1) `docker-entrypoint.sh:35` passes `--timeout-graceful-shutdown 5`, but the local invocation does not: `ps -o command= -p 91032` → `python -m uvicorn app.main:app --host 127.0.0.1 --port 8010`. uvicorn's `timeout_graceful_shutdown` therefore defaults to `None`, and `H11Protocol.shutdown()` does NOT close a connection whose response is still streaming — so a live SSE stream never leaves `server_state.connections`, `_wait_tasks_to_complete()` spins forever, and `lifespan.shutdown()` is NEVER reached. `run_shutdown.py:8-13` documents exactly this and it is why `kill -9` was the only thing that worked on run `d5dbc9f2`. Consequence beyond the stuck stop: **no local shutdown behaviour is exercised the way production exercises it** — the Concierge drain, the pump teardown and `close_checkpointer()` have never run on a developer machine. (2) `SHUTDOWN_STOP_RUNS` defaults `False` (`config.py:215`, KAN-151 D8 §I11), so even a reachable shutdown deliberately leaves in-flight runs non-terminal for the next boot's auto-resume — meaning a deploy cannot stop a 21M-token build either. That default is a real trade (it is what keeps the Phase 45-50 resume tier working) and is a product decision, not a bug; the missing local flag is not. **Fix shape:** add `--timeout-graceful-shutdown 5` to the documented local run command so dev and prod exercise the same path; then re-open the `SHUTDOWN_STOP_RUNS` default as a product question with cost, not as an engineering default.

## Source / Evidence

Confirmed while fixing ISS-084 (quick-260812-7sk): `ps` on the live pid 91032, `docker-entrypoint.sh:35`, `config.py:203-215` and the `run_shutdown.py` module docstring — read, not inferred. Filed rather than fixed because it changes how the process is launched and how a deploy behaves, which is neither the engine defect ISS-084 named nor safe to bundle with it. **RESOLUTION.** Both facts in this row were verified exact at HEAD and the fix was demonstrated end-to-end on a throwaway server (port 8099; the owner's 8010 backend was never signalled). (1) Reachability: `--timeout-graceful-shutdown 5` added to the ten developer-facing documented commands and to both out-of-repo memory notes (`dev-runtime.md`, `local-run-bedrock.md`) — the ones agents actually read, so the fix takes effect in practice. Measured: no flag → alive at **31.25s** with ONLY `startup_complete` written, SIGKILL required; with the flag → exit in **5.82s** with the shutdown body completing. `--reload` was DROPPED rather than carried over (untreated it leaves TWO stuck processes — parent 96488 and child both alive after 20s — it masks crashes, and `watchfiles` is absent so it degrades to `StatReload` polling). Port kept at **8000**: the repo's committed default in `frontend/src/lib/env.ts:37`, `env-templates/.env.frontend:7` and `frontend/e2e/fixtures/live.ts:13`; 8010 is a per-machine override. Deliberately NOT edited: `docs/LOCALSTACK_SMOKE_REPORT.md` (a dated report), `frontend/src/data/skills.ts` + `skills/ecc/flox-environments` (seeded user-facing product content), `frontend/src/app/test-preview/page.tsx` (a preview fixture), and the `.planning/phases/**` / `.knowledge` point-in-time artifacts. (2) The `SHUTDOWN_STOP_RUNS` product question was decided as **environment-differentiated** (owner decision D3): ON for `ENV=development`, OFF for every other ENV, with an explicit env var winning in both directions. Two prerequisites landed FIRST, in the mandated order — the double `close_checkpointer()` (`main.py:302-307`, deleted; step 4 in `run_shutdown.py` is now the single site its docstring always claimed, INV-12), and the under-counting budget comment (it said "under 25s" while omitting both cancel-and-wait escalations AND the pump drain; the real figures are 24s off / 30s on against a 30s `stop_grace_period`, now asserted by a test that PARSES both numbers). (3) **The blocking open question is settled and the prior hypothesis is REVERSED:** `asyncio.run`'s loop teardown does NOT already mark in-flight runs `cancelled`. `capture_signals()` restores the original signal disposition and re-raises the captured signal INSIDE `serve()` (`uvicorn/server.py:326-330`), so under SIGTERM the process dies before `Runner.close()` → `_cancel_all_tasks` can run. Proven three ways: the driver markers are absent under SIGTERM and present under SIGINT; a no-uvicorn control shows plain asyncio DOES run the handler; and a marker stamped after `server.run()` returns never appears. Under SIGINT it does fire — see **ISS-103**. Goldens 10 passed / 0 moved, lint 4 kept / 0 broken, the 11 pre-existing reds unmoved, all vs `9df9c1c8`.
