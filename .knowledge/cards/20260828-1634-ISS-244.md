## Reproduction (3/3, cycle 1)

On `/settings/profile`, in the Password card:

1. Sign in as `qa-admin`, navigate (cold start, fresh nav each cycle) to `/settings/profile`.
2. Fill Current password with the real current password, New password with one value, Confirm
   new password with a **different** value.
3. Click "Change Password" — client-side validation correctly shows "New passwords do not
   match" (no network request fires; this guard itself is correct behaviour).
4. Without touching New password, edit Confirm new password so it becomes byte-for-byte
   identical to New password (verified via reading both `input[type=password]` DOM `.value`s
   directly).
5. **Actual:** the "New passwords do not match" banner remains on screen, unchanged.
6. **Expected:** the banner should clear (or at minimum stop asserting a mismatch that no
   longer exists) once the fields agree.

Reproduced on all 3 cold-start cycles (fresh `/dashboard` -> `/settings/profile` navigation each
time, cleared component state), each with different current/new/confirm value triples (including
one cycle using `pressSequentially`-style typing to rule out an event-wiring artifact — same
result). 3/3 — CONFIRMED, no narrowing needed.

## Root cause

`frontend/src/components/settings/AccountSettings.tsx`:

- `message` state (line 99, `useState<{type; text} | null>`) is written **only** inside
  `handleChangePassword` (lines 148-174) — once at the top (`setMessage(null)`, line 149, on
  submit) and again if a validation branch fails, e.g. `setMessage({type:"error", text:"New
  passwords do not match"})` at line 158-159.
- The `onChange` handlers for the New password field (line 295: `onChange={e =>
  setNewPassword(e.target.value)}`) and Confirm password field (line 306: `onChange={e =>
  setConfirmPassword(e.target.value)}`) update only their own field's state — **neither calls
  `setMessage(null)`**.
- Because `message` is set exclusively at submit time and never invalidated on subsequent
  keystrokes, once "New passwords do not match" is shown it is permanently stale until the user
  clicks "Change Password" again (successfully or not) — regardless of what the fields now
  contain.

## Expected vs actual

- Expected: mismatch validation state reflects the fields' current contents — clearing (or
  re-evaluating) as soon as New password and Confirm new password agree.
- Actual: the error is computed once per submit click and never recomputed/cleared on input,
  so a user who fixes their typo has no on-screen confirmation the form now agrees with them.
