## What happened

`/settings/constitution` (component: `AccountSettings.tsx`, section `"constitution"`)
displays a counter styled as a hard cap — `{content.length} / 4000 chars` (line 579) — and
page copy says the constitution "is prepended to every agent on every run." Nothing in the
save path enforces 4000 chars anywhere:

- The `<textarea>` (lines 586-593) has no `maxLength` attribute — confirmed via DOM read,
  `textarea.maxLength === -1`.
- The "Save constitution" button's `disabled` expression (line 627) is
  `saving || loading || !content.trim()` — no length check, so it never disables past 4000.
- The backend `ConstitutionRequest.content` field
  (`backend/app/api/settings.py:355`) is declared
  `Field(..., min_length=1, max_length=1_048_576)` — a 1 MiB cap, not 4000. `PUT
  /api/settings/constitution` (settings.py:372-388) validates against that 1 MiB limit only
  and persists whatever passes it verbatim via `memory.set_constitution`.

The "4000 chars" figure exists nowhere but the UI label — it is not read by any validation
on either tier.

## Reproduction — 3/3, cold start each cycle

Account: qa-admin (enterprise/admin tier — not tier-specific, this is a validation gap).
Reproduced identically on **cycle 1** (4518 chars: `"A".repeat(4500) + "MARKER-CYCLE1-4500"`),
**cycle 2** (5018 chars: `"B".repeat(5000) + "MARKER-CYCLE2-5000"`), and **cycle 3** (4318
chars: `"C".repeat(4300) + "MARKER-CYCLE3-4300"`). Each cycle was a fresh navigation
(`/dashboard` -> `/settings/constitution`), not a soft re-click:

1. Navigate to `/settings/constitution`.
2. Set the textarea's native value via the `HTMLTextAreaElement` value setter + `input`
   event dispatch (mimics real typing) to a string over 4000 chars.
3. Observe the counter update to e.g. `"4518 / 4000 chars"` — over the stated limit — and
   `Save constitution`'s `disabled` remain `false`.
4. Click Save. `PUT /api/settings/constitution` returns `200 OK`.
5. Navigate away (`/dashboard`) and back to `/settings/constitution` (cold reload of the
   route, not the same mounted component) — the textarea reloads the full over-limit
   content, counter still reads the over-limit value, confirming server-side persistence,
   not a client artifact.
6. `GET /api/settings/constitution` via `fetch` with the auth token independently confirms
   the full un-truncated `content` field (verified length and trailing marker text matched
   exactly what was sent, all three cycles).

Content restored to the pre-existing constitution
(`"E2E S-09-12: answer in exactly one sentence."`) after every cycle, verified via
`PUT`+reload, so no test data was left behind.

## Expected vs actual

**Expected:** either the client disables Save / rejects input past 4000 chars and the
server enforces the same 4000-char limit (422 on an over-limit payload), so the displayed
counter reflects a real constraint — or, if there is genuinely no limit, the counter should
not read "X / 4000 chars" implying a hard cap that does not exist.

**Actual:** content far beyond 4000 chars (tested 4318-5018) is accepted by both layers with
no truncation, warning, or rejection: `textarea.maxLength` is unset, `Save constitution`
never disables, and the backend's real cap is 1,048,576 chars, not 4000.
