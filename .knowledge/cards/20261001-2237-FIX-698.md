# FIX-698

## What was wrong

Bug report QA-KB-018. The root cause and blast radius are the analysis on
[ISS-410](20260828-2344-ISS-410.md) (CONFIRMED, reproduced 3/3 in the browser); they are not re-derived here.

`/workflows/{id}/canvas` mounts `ComposerPage` straight onto page.tsx's seed state, which is `null` while
`GET /api/workflows/{id}` is in flight and stays `null` when it fails for any reason other than 403/404
(`frontend/src/app/[...view]/page.tsx:564-575`: `setInitialSavedComposition(null)` first, then
`setBuiltinCanvasAccessDenied(true)` only for 403/404). ComposerPage keys copy mode on `builtinCanvasType` alone
(header `· copy`, label "Save as copy"), and its Save button was `disabled={saving}`, so a transient failure left a
live "Save as copy" over a blank composition. `handleSave` then POSTs a new `base_pipeline_type: "custom"` user
workflow: a 422 with zero agents (`agent_ids: list[str] = Field(min_length=1)`,
`backend/app/api/user_workflows.py:213`), a new row once the user hand-adds an agent.

[FIX-470](20260902-1200-FIX-470.md)'s `isSavingRef` (`ComposerPage.tsx:839-840`) blocks only a second concurrent
save, so its note that it "also closes ISS-410's ComposerPage-side consequence" did not hold: the validator
reproduced on a tree that already contained it. Its double-click mutex is untouched and still correct.

## What changed, and why there

`frontend/src/components/workflow/composer/ComposerPage.tsx`, two hunks, nothing else in the file:

1. `:1247-1251`, a derived flag above the component's `return`, with a three-line `// ISS-410` comment:

   ```
   const seedUnresolved =
     !!builtinCanvasType && !initialManifestSteps?.length && !initialAgentIds?.length;
   ```

2. `:1393-1400`, the Save button: `disabled={saving || seedUnresolved}`; the `title` keeps
   "Name the workflow first" first, then shows "This workflow has not loaded. Reload the page to retry."
   while `seedUnresolved`.

Why there: `handleSave` has exactly one call site, this button's `onClick` (`:1391`; `grep -n "handleSave\b"`
returns the definition, comments and that line), so the button is the single Save sink for every present path.
The seed reaches ComposerPage as props (`DashboardLayout.tsx:3229`, `:3236`), and DashboardLayout's key
`savedComposition?.id ?? "new"` (`:3212`) never changes for a built-in, so a prop-derived flag releases itself when
the seed lands; nothing has to remount. A loaded built-in always seeds at least one agent id (page.tsx maps
`detail.steps`, which `backend/app/api/workflows.py:487-529` builds from `compiled.steps`), so a healthy canvas is
never locked. The analysis rejected the alternatives and they were not
done: widening `builtinCanvasAccessDenied` (turns a blip into a permanent not-found, FIX-368), a retry inside
`getWorkflowDetail`, error or retry UI in page.tsx (outside the agreed scope), and IdeaInputPage's
`pipelineAgents.length` predicate (re-enables Save as copy the moment an agent is hand-added).

Not added: a second guard inside `handleSave`. Save has no other entry point today. If one is ever added (a
keyboard shortcut, say), the guard must sit before `isSavingRef.current = true` (`:840`) or release it on the
early return, as the detached and auth guards do.

  page.tsx and is forwarded by DashboardLayout. The page.tsx `/edit` and `/run` seed regions also carry other bugs'
  uncommitted hunks, so this was not a trivial edit. Stays open.
