## What happened

`/login` and `/login?expired=true` render the full sign-in form (and, for the `expired=true`
variant, the "Your session expired. Please sign in again." banner) for a user who is already
authenticated with a valid, working `auth_token` — no redirect to `/dashboard` ever fires, by any
entry path.

Confirmed **CONFIRMED, 3/3, cold start every cycle** — each cycle started from a fresh browser tab
with a fresh direct navigation (not a soft re-click of the same screen), using an `auth_token`
already proven valid by a prior successful sign-in:

- **Cycle 1:** fresh direct nav to `/login?expired=true` while authenticated → sign-in form and
  the stale "session expired" banner rendered; `GET /api/runs?limit=50` fired from the same page
  load returns `200 OK` with the stored token, proving the session is genuinely valid, not
  actually expired.
- **Cycle 2:** fresh direct nav to plain `/login` (no query string) while authenticated → sign-in
  form rendered (no banner, correctly, since `expired` param is absent) — same missing-guard
  failure on the base route, not just the `expired=true` variant.
- **Cycle 3:** new-tab fresh direct nav to `/login?expired=true` while authenticated → identical
  failure; waited 2.5s after load, no async redirect ever fires.

## Expected vs actual

- **Expected:** an authenticated user (valid `auth_token`, working API session) landing on
  `/login` or `/login?expired=true` by any navigation path is immediately redirected to
  `/dashboard`, mirroring the app's own logic that routes a signed-out user from `/` to `/login`
  and a signed-in user from `/` to `/dashboard`.
- **Actual:** `frontend/src/app/login/page.tsx` renders the sign-in form unconditionally, with no
  check for an existing valid token before rendering. There is no "already signed in, skip the
  form" guard on this route at all.

## Conditions established

- Route: `/login` and `/login?expired=true` (both fail identically for the form-shown symptom;
  the stale banner is specific to the `expired=true` query variant).
- Tier: qa-admin (register notes no tier dependency — the failure is a route-level missing guard,
  not tier-scoped logic).
- Theme/viewport: default (light theme, standard viewport) — not varied, not needed; 3/3 without
  variation.
- Entry path: reproduces via fresh direct navigation (address bar / new tab) AND via browser Back
  navigation after a successful sign-in (per the original register's step 4) — not entry-path
  specific.
- Session state: valid, non-expired `auth_token` in `localStorage` from a completed sign-in.
- Not timing-dependent: waited up to 2.5s after load in every cycle, no async redirect ever
  fires — this is a permanently missing guard, not a race.

## Root cause (CONFIRMED — 3-analyzer)

`frontend/src/app/login/page.tsx`'s `LoginForm` component (the only component this file
renders — `LoginPage` at line 523-529 just wraps it in `<Suspense>`) has **no mount-time
auth check at all**. Its React import line reads:

```
frontend/src/app/login/page.tsx:3
import { Suspense, useState, FormEvent } from "react";
```

`useEffect` is never imported, and grepping the full 530-line file confirms there is no
`useEffect` call anywhere in it — structurally, this component cannot run any check "on
mount." Execution goes straight from the two `useState` calls (lines 21-24) to the JSX
return of the full sign-in form (line 160 onward) on every render, unconditionally. The
existing `isExpired` flag (line 20, `searchParams.get("expired") === "true"`) only toggles
the stale-banner text at lines 231-239 — it never gates whether the form itself renders.

This is a **structural omission**, not a broken conditional: the guard other auth-aware
screens in this app all implement is simply absent here. Two comparison points prove the
pattern that is missing:

- `frontend/src/app/page.tsx:9-18` (full file) — the root route implements the exact
  inverse of what `/login` needs, in 10 lines: `useEffect` reads `getToken()`, and
  `router.replace(routes.home())` when a token exists, `routes.login()` when it doesn't.
  This is the template; `/login` has no counterpart of it for the signed-in case.
- `frontend/src/app/[...view]/page.tsx:805-811` — every protected screen behind the
  `[...view]` catch-all runs "Auth check on mount": `if (!storedToken)
  router.replace(buildLoginRedirect())`. This proves the app already enforces the
  opposite direction (unauthenticated → bounced to `/login`) correctly; only the
  signed-in-user-on-`/login` direction was never built.
- `frontend/src/lib/api.ts:26-33` — `getToken()` is the primitive both of the above read;
  it is `localStorage.getItem("auth_token")` guarded only for `localStorage` existing
  (`TOKEN_KEY = "auth_token"`, line 22). It answers "is a token present," which is exactly
  what the register's `GET /api/runs?limit=50` → `200 OK` in the reproduction evidence
  independently confirms was true and valid in every failing cycle — so a mount check
  using this same primitive would have caught it.

**The building blocks for the fix already exist inside this same file and are unused at
mount:** `resolveRedirectTarget` is imported at line 15 and `goToDestination()` (lines
39-46) already calls `router.push(resolveRedirectTarget(searchParams.get("redirect")))`
after a successful form submit — the identical call a mount-time guard needs, just never
invoked before the form renders.

## Blast radius

The broken component is `LoginForm` itself, not a shared function with many call sites —
every entry path funnels through the same unconditional render, which is why validation
cycles 1-3 above already reproduce it via three different routes to the same page (fresh
nav to `/login?expired=true`, fresh nav to plain `/login`, Back-navigation to
`/login?expired=true`). Grepping every code path in `frontend/src` that can land a browser
on `/login` (`routes.login()`, the literal string `"/login"`, `buildLoginRedirect()`) finds
one caller that reaches this same broken page **without validator coverage yet**:

- `frontend/src/app/register/page.tsx:12` — `useEffect(() => { router.replace("/login");
  }, [router]);` — unconditional, no `getToken()` check at all, unlike every other
  redirect-to-login call site in the codebase (`admin/page.tsx:165`,
  `handoff/settings/page.tsx:23-26`, `HandoffWorkflow.tsx:63-68`,
  `LaunchWizard.tsx:261`, `[...view]/page.tsx:807-809` all guard with `if (!token)`
  first). An authenticated user landing on the literal `/register` route is sent straight
  into this same missing-guard `/login` page. Filed as [ISS-193](20260828-1554-ISS-193.md)
  (INFERRED — not yet reproduced).

Every other `router.replace("/login")` / `buildLoginRedirect()` call site checked
(`admin/page.tsx:245` is a post-`logout()` redirect; the five others above all gate on
`!token` first) only fires when no token is present, so they do not independently
reproduce this symptom — they are correct callers of a page that is, itself, broken for
the one case none of them gate against.

## Proposed fix — where it belongs

`LoginForm` in `frontend/src/app/login/page.tsx` is the single render path every entry
point above funnels through, so one guard here — not one per caller — closes all of them,
including [ISS-193](20260828-1554-ISS-193.md). Add a mount-time check that reuses what the
file already imports rather than introducing a new abstraction:

- `useEffect(() => { if (getToken()) { router.replace(resolveRedirectTarget(searchParams.get("redirect"))); return; } setChecked(true); }, [router, searchParams])`
  — `getToken` (from `@/lib/api`, not yet imported here) and `resolveRedirectTarget`
  (already imported, line 15) are both already the primitives this file's own
  `goToDestination()` uses post-submit; this is the same call, just made at mount too.
- Gate the form's JSX return behind that `checked` state (`if (!checked) return null;`)
  rather than a bare effect with no render gate — `handoff/settings/page.tsx:21-32`
  (`authed` state, `if (!authed) return null`) is this app's own existing pattern for
  exactly this: without a render gate, the guard would still flash the full sign-in form
  for one paint before `useEffect` fires and redirects, since effects run after paint.
- This stays a per-page fix, matching the codebase's own established convention — six
  other files (`page.tsx`, `[...view]/page.tsx`, `admin/page.tsx`,
  `handoff/settings/page.tsx`, `HandoffWorkflow.tsx`, `LaunchWizard.tsx`) each already
  implement their own inline `getToken()`-gated `useEffect` rather than sharing one hook,
  so extracting a shared hook here would be a wider refactor than this bug calls for, not
  a requirement of the fix.
- No SC-001, registry, or backend involvement — this is frontend routing only, and
  `frontend/src/proxy.ts` (the one place ADR-0018 documents an edge-level check) cannot
  see `auth_token` since it lives in `localStorage`, not a cookie, so the check must stay
  client-side exactly where the existing pattern already puts it.
