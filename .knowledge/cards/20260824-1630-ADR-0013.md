# ADR-0013

## Decision

In the context of two human-review mechanisms that were spelled almost identically —
`gates: [human]` in a manifest and `gate: Human_Gate` in an `AGENT.md` — facing the fact
that they do OPPOSITE things (one reviews the PREVIOUS step's output before this step
generates, the other reviews this step's OWN output afterwards and supports redo), and
that which one ran was decided not by the manifest but by whether the step's agent
happened to have an `AGENT.md` on disk, we decided to put the phase in the name:
`human` now means POST-step and `before-human` means PRE-step, to achieve a manifest
that can be read literally, accepting a behaviour change to any manifest that already
declared `gates: [human]`.

**Area:** engine, gates, workflow

## Why this was not merely cosmetic

The old spelling was not ambiguous, it was *misleading*, and the tree proves it:
`backend/agents/workflows/prototype/workflow.yaml` declares `gates: [human]` on three
steps — `prototype-specify`, `prototype-plan`, `prototype-analyze` — and **all three were
dead lines**. Those agents carry `gate: Human_Gate` in their `AGENT.md`, so
`_should_gate` returned true, the `inline_gated` dedupe suppressed the declared gate, and
the inline (post-step) gate won every time. An engineer reading that manifest would
reasonably conclude those declarations cause the pauses. Deleting them would have changed
nothing.

## Alternatives rejected

**Redefine `human` as pre-step and leave the post-step case unnamed.** Rejected: the
post-step behaviour is the dominant real-world one — it is what every shipping pipeline
with human review actually gets, and what an author intends by "pause for review". Naming
the rare case and leaving the common one implicit inverts the usability.

**A flat multi-select of gate names in the UI.** Rejected while the names carried no
phase: a flat list makes a nonsense combination (two pre-step HITL pauses, which
double-prompt) exactly as easy to click as a sensible one. Once the names encode phase
this objection weakens, and the UI did move to grouped checkboxes — but grouped BY PHASE,
with within-phase exclusivity enforced.

**Put the gate name into `gate_key`.** This would allow a pre- and a post-step pause on
one step. Rejected as out of proportion: `gate_key` is load-bearing for durable resume,
and no fixture needs both. The compiler refuses the combination instead, which turns a
silent mis-resume into a compile error naming the step.

## The migration hazard this creates

Moving `human` into `_POST_STEP_GATES` makes prototype's three declarations LIVE for the
first time. They would then fire alongside the inline gate on the same agent and
double-prompt the user. The `inline_gated` dedupe was therefore moved with it — its guard
was `name == "human" and phase == "pre"`, which would never match once `human` became
post-step. Anyone revisiting that dedupe must keep it phase-agnostic across both HITL
names, or prototype regresses in a way only a live run reveals.
