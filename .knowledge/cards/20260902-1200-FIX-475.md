# FIX-475

## What was wrong

Two accumulators in `handlePipelineMessage`'s `pipeline_start` reducer lacked
a per-run boundary:

**ISS-108 — `clarifications`.**  
`retainClarifyRound` (`useWorkflow.ts:168`) appends to `clarifications` via a
direct UI call (not a frame), so ISS-082's frame-identity gate cannot reach it.
`startPipeline` explicitly resets it (`clarifications: []`, line ~69), but
`pipeline_start`'s `setPipelineState` return spread `...prev` and never cleared
it. A history reopen or chained run that bypasses `startPipeline` would carry
the prior run's Q&A rounds into the new run's state. Not observed live — flagged
by card ISS-108 during FIX-235 session.

**ISS-110 — `hookRuns`.**  
The `hook_run` case (`useWorkflow.ts:~1113`) does
`hookRuns: [...(prev.hookRuns || []), entry]` — a clean accumulator that is
already registered in `ACCUMULATING_FRAME_TYPES` and covered by ISS-082's
dedup gate. `pipeline_start` spread `...prev` and never cleared it, so one
run's audit log rows could survive into a subsequent run's `pipelineState`.
Same note: not observed, flagged as a one-line fix by ISS-110 which explicitly
cited that "the shape of the fix is already in place beside it" (the
`isSameRunReannounce` predicate).

## Root cause

`frontend/src/hooks/useWorkflow.ts` — the `pipeline_start` case's
`setPipelineState` return object: neither `clarifications` nor `hookRuns` was
named, so both inherited from `...prev` on every path, including genuinely
different-run frames.

## What changed and why there

Two lines added to the `pipeline_start` return object in
`frontend/src/hooks/useWorkflow.ts`, immediately after `protoPlannedTasks` (the
next accumulator with the identical reset pattern, KAN-120 BUG-3):

```ts
// ISS-108: preserve answered clarify rounds on a continuation; reset on a
// genuinely fresh run so the prior Q&A never leaks into the new run.
// Mirrors the protoCompletedTasks pattern on the same predicate.
clarifications: isContinuation ? (prev.clarifications ?? []) : [],
// ISS-110: preserve hookRuns on a continuation; reset on a fresh run so
// the prior run's audit log never leaks. hookRuns is in
// ACCUMULATING_FRAME_TYPES, so the dedup gate already covers it — only
// the per-run boundary was missing.
hookRuns: isContinuation ? (prev.hookRuns ?? []) : [],
```

`isContinuation` (`resumeOffset > 0 || isSameRunReannounce`) was already in
scope — the same predicate KAN-120 BUG-3 uses for `protoCompletedTasks` and
ISS-082 uses for the frame-identity cursor. No new variable, no new logic path.

**Why not in `retainClarifyRound`.** That function is the correct place for the
identity dedup if one were needed, but the per-run RESET belongs in the reducer,
not in a UI call — same reasoning as `protoCompletedTasks`: the reducer owns the
state lifecycle, and `retainClarifyRound` is a one-way push that should not
carry responsibility for deciding what "new run" means.
