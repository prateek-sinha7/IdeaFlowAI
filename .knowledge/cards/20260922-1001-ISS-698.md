# ISS-698

## Description

In the Custom Workflow composer (`/create/custom`, and any saved custom
workflow's `/workflows/{id}/run` editor), every step's **Tools** tab shows a
"Write files" switch that defaults to ON. Toggling it has zero effect at
runtime: the agent executing that step is never granted `write_file` or
`edit_file`, regardless of the switch state. This is bug **QA-PS-019**
(`BUGS.md#qa-ps-019`).

## Reproduction (3/3, cold start each cycle)

Verified live via `POST /api/runs` (`pipeline_type: "custom"`,
`agent_ids: ["market-research-agent"]` — the default `custom/workflow.yaml`'s
first step, per composer default "Write files" ON), skip-clarify, run to
completion, and reading `agent_outputs` for the step:

| Cycle | run_id | Agent's own words |
|---|---|---|
| 1 | `aa2c0684-ced0-4c19-b6d2-bab9e010966c` | "I don't have write_file available as a tool... no direct write capability in this interface." |
| 2 | `dfc27751-4e2d-4e89-9b64-a9501b0fd809` | "I don't have access to a `write_file` tool. The tools available to me are: `ls`, `read_file`, `glob`, `grep`, `write_todos`." |
| 3 | `6829bdef-1cf0-4b31-b347-24180f1330d8` | "I don't have access to a `write_file` tool in this step... no `write_file` or `edit_file`." |

Also confirmed in the UI (lane3, qa-admin): the Tools tab's "Write files"
switch is `checked` by default both on a fresh `/create/custom` canvas
(`market-research-agent` step) and on an existing saved workflow
(`ISS-580 deliverable check`, "Domain Discovery Agent" step) — the toggle
state itself is fine; only the runtime grant is missing.

Cascading effect observed in the same runs: every downstream step in the
9-agent default pipeline (swot-analyst onward) then reports the prior step's
`.agents/01-market-research-agent.md` as "corrupted"/"incomplete" — this is
QA-PS-020's symptom, same root cause.

## Root cause

`backend/agents/execution_engine/engine.py`, `_apply_selections` (~line
12767-12910). This function overlays the composer's per-step user
`selections` onto the file-compiled `Step` at run entry. It builds a `patch`
dict from individual `if sel.get(...)` branches for `validators`, `gates`,
`model`, `retry`, `injects`, `skills`, `strategy`, `fanout`, `task_source` —
**there is no `tools` branch**. The comment directly above the fan-out levers
(~line 12900-12904) says:

> "No `tools` overlay: the declarative fanout_batch path acquires no
> spawn_subagents grant (run_fanout does no permission check; trust=user
> forces tools.spawn_subagents OFF anyway)."

That justification only covers `spawn_subagents`; it does not license
dropping `write_files`/`read_files` from the overlay entirely, but the
missing `tools` case does exactly that — a step's `tools` are never patched,
so the running step keeps whatever `custom/workflow.yaml` declared.

`backend/agents/workflows/custom/workflow.yaml` (the base manifest) declares
`tools: {read_files: true}` on 8 of 9 steps and **no `tools:` key at all** on
`market-research-agent` (step 1) — none declare `write_files: true`. The
compiler's `_compile_tool_grant` (`compiler.py:1486`, called from line 1003)
compiles an absent/partial `tools:` block to `ToolPermissions(write_files=False)`
by default. `permission_caps.py`'s `PERMISSION_TOOLS["write_files"]` gates
exactly `{write_file, edit_file}` — consistent with the agents' own error
text.

So the chain UI -> `selections.tools` -> `synthesize_manifest` ->
`WorkflowCompiler.compile(trust="user")` produces a correctly-trust-compiled
`user_step.tools.write_files = True` (the untrusted cap allows it), but
`_apply_selections` never copies that field onto the step that actually
runs — the gap is purely in the missing overlay case, not the compiler or
the cap.

## Fix direction (not applied by this card — analysis only)

Add a `tools` branch to the `patch` dict in `_apply_selections`, mirroring
the existing `sel.get("validators")` / `sel.get("skills")` pattern: when
`sel.get("tools")` is present and `user_step.tools` is not None, patch
`tools=user_step.tools` (or a merged/capped variant, matching how `gates`
merges unconditionally today). Needs a decision on merge-vs-replace
semantics for a step whose base manifest already declares partial `tools:`.
