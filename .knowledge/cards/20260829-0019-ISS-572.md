## What happened

INFERRED sibling of [ISS-339](20260828-1850-ISS-339.md) (BUG-20260828-042311-settings) — same
mechanism, not yet reproduced live in a browser. Confirmed at the code level only.

`frontend/next.config.ts:6-31` defines exactly 4 server-only `redirects()` rules. ISS-339 covers
1 of them (`/settings` -> `/settings/profile`, lines 26-30). The other 3, all added in the same
array (lines 11-25), have the identical gap:

- `/library/agents` -> `/library` (next.config.ts:12-15)
- `/library/skills` -> `/library?tab=skills` (next.config.ts:16-20)
- `/library/hooks` -> `/library?tab=hooks` (next.config.ts:21-24)

`frontend/src/lib/routes.ts:377-399` (`parseViewPath`, `head === 'library'` branch) has no
client-side equivalent for any of the three. For a 2-segment path such as `['library',
'agents']`: `segments.length === 1` (line 385) is false, so it does not resolve to `{ screen:
'library' }`; `segments.length >= 3` (line 392) is also false, so the `type === 'agents' |
'skills' | 'hooks'` detail-route checks (lines 393-396) never execute either. Execution falls
through to the same terminal `return { screen: 'unknown' };` at line 399 that bare `/settings`
hits at line 408. `frontend/src/app/[...view]/page.tsx:3780-3782` renders `notFound()` for any
`screen: 'unknown'` — the identical shared gate ISS-339 hits.

The comment at `routes.ts:378-384` rests on the exact false premise ISS-339 disproved: "The
legacy 2-segment list shape (/library/agents, /library/skills, /library/hooks with no slug) is
intercepted by next.config.ts redirects before it ever reaches here." That is true only for a
cold/full navigation (SSR/document request) — Next.js's `redirects()` config never runs for a
client-side history transition (`pushState`/`popstate`, `router.push`, a plain `<a>`/`<Link>`
whose destination is same-origin), so such a transition reaches `parseViewPath` directly and
gets `unknown` -> 404, same as `/settings`.

This same false assumption is independently codified as a currently-PASSING test at
`frontend/src/lib/routes.test.ts:309-313`:

```ts
it('/library/{type} with no slug (legacy list shape) returns unknown — intercepted by next.config.ts before reaching parseViewPath', () => {
  expect(parseViewPath(['library', 'agents'])).toEqual({ screen: 'unknown' });
  expect(parseViewPath(['library', 'skills'])).toEqual({ screen: 'unknown' });
  expect(parseViewPath(['library', 'hooks'])).toEqual({ screen: 'unknown' });
});
```

The equivalent (also-wrong) settings assertion sits immediately below it at
`routes.test.ts:315-318` (`/settings without tab returns unknown`) — both encode the same
disproved premise as expected behavior.

## Why the root cause implies this

ISS-339's confirmed root cause is: a `next.config.ts` server-only `redirects()` rule has no
mirror in `routes.ts`'s `parseViewPath`, so any client-side transition to that bare path falls
through to `unknown` -> `notFound()`, while a cold/full load of the identical path redirects
correctly. `next.config.ts` declares exactly 4 such rules total; these are the other 3, defined
in the very same array literal, sharing the same file, the same parser, and the same rendering
gate. Nothing about the mechanism is settings-specific.

## Expected vs actual (INFERRED — pending reproduction)

Expected: a client-side transition to `/library/agents`, `/library/skills`, or `/library/hooks`
resolves to the same destination a cold load of the identical path reaches (`/library`,
`/library?tab=skills`, `/library?tab=hooks` respectively).

Actual (not yet reproduced live): client-side navigation is expected to render the 404 "Page not
found" screen and leave the URL frozen on the bare 2-segment path, mirroring ISS-339's confirmed
behavior for `/settings`.

## What would settle it

The same reproduction recipe validated for ISS-339, retargeted at the three library paths: from
a mounted screen, `window.history.pushState({}, '', '/library/agents');
window.dispatchEvent(new PopStateEvent('popstate'))` (repeat for `/library/skills`,
`/library/hooks`) and observe whether the 404 screen renders instead of the library list. This is
the ISS-339 recipe applied to a different `head`, not a different mechanism.

## Practical trigger note

Unlike some routing gaps, no in-app caller currently constructs a bare 2-segment library path or
a bare `/settings` path itself — `frontend/src/lib/routes.ts`'s own builder object only exposes
`library(params?)` (always emits `/library` plus query params, never `/library/agents` as a path
segment) and per-tab `settingsProfile()`/`settingsAiModel()`/etc. (never a bare `settings()`).
`frontend/src/components/layout/DashboardLayout.tsx:398` confirms in-app settings navigation
already goes through `routes.settingsProfile()`. So both this issue and ISS-339 are reachable
only via an external/historical link (the exact case `next.config.ts:7-10`'s comment names:
"old bookmarked/shared list URLs") landing as a client-side transition rather than a fresh
document load — not via any button currently in the app.
