## What was wrong

`IntegrationsCard.tsx` had no `window.confirm` gate anywhere in the file. Two independent destructive call sites fired their backend `DELETE` synchronously on a single click:

- `handleDeletePat` (`:123–139`) — called `deleteGithubPat(token)` without confirmation. Wired to the "Remove" button at `:245`.
- `handleRevoke` (`:161–176`) — called `revokeApiKey(token, id)` without confirmation. Wired to the "Revoke" button per API key row.

Both remove account-level credentials permanently and immediately. There was no opportunity to cancel.

## Root cause

Same anti-pattern as ISS-320 (Constitution) and ISS-480 (SkillManager): no `window.confirm`, no modal, no two-step gate. The app had exactly one existing confirmation gate in the entire frontend (`DashboardLayout.tsx:1717`) — a navigation guard — and none of the destructive data operations used it.

## What changed and why there

One early return at the top of each handler, before any state is touched and before the request is built, following FIX-385's exact shape:

**`handleDeletePat`:**
```tsx
if (
  !window.confirm(
    "Remove your GitHub token? This will disconnect Flowin from GitHub " +
      "until you save a new token.",
  )
) return;
```

**`handleRevoke`:**
```tsx
if (
  !window.confirm(
    "Revoke this API key? Any client using it will immediately lose access.",
  )
) return;
```

`window.confirm` over a new modal primitive: same rationale as FIX-385 — this is the gate the codebase already uses, it needs no new component, and the guard sits in the handler so callers inherit it.
