# ISS-764

**Register source:** `QA-PS-024` in root `LEDGER.md` / `BUGS.md` — filed as a sibling of
[ISS-701](20260922-1030-ISS-701.md) during root-cause analysis, not independently reproduced.

## What is suspected to be wrong

[ISS-701](20260922-1030-ISS-701.md) root-causes QA-PS-024 to
`StepsOverviewSpine.tsx:408`:

```ts
const failed = !isRunning && (pipelineState?.failed || agents.some(a => a.status === "error"));
```

which lets a per-agent `error` status override the run's real terminal marker whenever that
marker is not itself `pipelineState.failed`. ISS-701 reproduced this for `pipelineState.degraded`.
The identical OR has no dependency on which terminal marker is actually true — it fires off
`agents.some(...)` alone whenever `pipelineState?.failed` is falsy, regardless of whether the run
is `degraded`, `cancelled`, or (per the second finding below) anything else. `cancelled` is the
other terminal marker `useWorkflow.ts` sets independently of `failed`
(`terminalMarkers("cancelled")`, mutually exclusive from `failed`/`degraded` — confirmed at
`useWorkflow.ts:378-389`), and it is reachable with a leftover per-agent `error` status by
construction:

`frontend/src/hooks/useWorkflow.ts:1379-1382`, the `pipeline_cancelled` handler:

```ts
const updated: AgentRunState[] = prev.agents.map((a) =>
  a.status === "thinking" || a.status === "running"
    ? { ...a, status: "idle", thinking: "" }
    : a
);
```

Only `thinking`/`running` agents are reset to `idle`; the surrounding comment says explicitly
*"completed agents ('done') and already-errored agents are left untouched."* So a run where agent
2 of 4 already errored, and the user then clicks Stop on the still-running remainder, reaches
`pipeline_cancelled` with one agent still carrying `status: "error"` and
`pipelineState.cancelled = true` — `pipelineState.failed` is never set for this path.

## Why the root cause implies it

Tracing `StepsOverviewSpine.tsx:408` for that exact state: `isRunning` is `false` (terminal),
`pipelineState?.failed` is `undefined`/falsy (only `cancelled` was stamped), and
`agents.some(a => a.status === "error")` is `true` (the pre-cancel errored agent). The OR
evaluates the same way it does for ISS-701's degraded case: `failed` becomes `true` purely from
per-agent status, and the label ternary's first branch (`failed ? "Run failed" : ...`) wins over
whatever a correct cancelled-aware branch would say — exactly ISS-701's mechanism, substituting
`cancelled` for `degraded` as the marker that gets steamrolled. This is not a new bug pattern to
prove; it is the same line producing the same wrong precedence for a second terminal marker,
which is why it is filed as a sibling rather than a fresh investigation.

**A second, related but mechanically distinct gap, noted here and NOT folded into this card's
verdict:** the label ternary at `StepsOverviewSpine.tsx:449-453` has no `cancelled` branch at
all —

```ts
const statusLabel = failed ? "Run failed" : isRunning ? "Running"
    : (pipelineState?.degraded) ? "Run degraded"
    : "Run complete";
```

— so even a *cleanly* cancelled run (no agent ever errored) falls through to `"Run complete"`,
independent of the OR-precedence bug entirely (`failed` is correctly `false` there; the ternary
simply never asks about `pipelineState?.cancelled`). Fixing ISS-701's line 408 (gating `failed` on
`pipelineState?.failed` alone) does not touch this — it is a missing branch, not a precedence
error, so it is a separate, pre-existing defect with a different required fix (add a `cancelled`
arm to the ternary), not something "the root cause implies." Flagged for whoever next touches
this ternary; deliberately not filed as its own card by this pass to avoid padding this bug's
sibling set with a mechanism ISS-701's fix does not cover either way.

## Expected vs actual

- **Condition:** a run is stopped (`handleCancelWorkflow` / Stop button) after at least one agent
  has already reached `status: "error"`, and no further agent errors before the stop completes.
- **Expected:** the Steps panel status summary reflects a cancelled run (whatever label/tone the
  product intends for "stopped by the user with a partial failure already recorded" — at minimum,
  not the same red "Run failed" X-icon/banner a hard pipeline failure gets).
- **Actual (inferred, not yet driven in the browser):** `failed` evaluates `true`, so the panel
  shows the red X-circle, the "Run failed" label, the `notRun` idle-agent count, and — if any
  agent is still `idle` — the "Pipeline halted — reopen to resume" banner, none of which describe
  a run the user deliberately stopped.

## What would confirm or refute this

Reproduce live: launch a multi-agent run, wait for one agent to reach `status: "error"` (or force
it, e.g. via a security-gate block), then click Stop/Cancel while a later agent is still running.
Compare the Steps panel against `LaneRunHeader`'s cancelled handling
(`frontend/src/components/chat/LaneRunHeader.tsx` — checks `pipelineState?.cancelled` before the
failed/degraded branch, so it should NOT show this defect) for the same run. A test built the way
`StepsOverviewSpine.staleErrorLabel.test.tsx` (ISS-317) already does — render with
`pipelineState: { isRunning: false, cancelled: true, ... }` and one `agent({ status: "error" })` —
would settle it without a live run.

## Fix location

Same shared line as [ISS-701](20260922-1030-ISS-701.md): `StepsOverviewSpine.tsx:408`. ISS-701's
proposed direction — derive `failed` from `pipelineState?.failed` alone, matching how
`LaneRunHeader.tsx` keeps `failed`/`degraded`/`cancelled` as independent, non-overriding checks —
would cure this sibling as the same one-line fix, by construction: once `agents.some(status ===
"error")` is removed from the OR entirely, no per-agent status can flip `failed` true for any
terminal marker other than a genuine `pipelineState.failed`. The one guard at the shared
derivation is where all downstream readers (the label, the phase-null gate, the `notRun` count,
the X-icon, the "Not run" chips, and the "Pipeline halted" banner — all in this same file, all
downstream of the same `const failed`) route through; no per-caller patch is needed.
