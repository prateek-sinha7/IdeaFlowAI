# ISS-654

**Bug register entry:** derived from QA-PS-004 (`BUGS.md#qa-ps-004`, `LEDGER.md`) — root-cause card [ISS-650](20260917-1130-ISS-650.md)

## Status: CONFIRMED (offline hook repro, QA-KB-020, 2026-10-01)

Filed from the root-cause investigation of QA-PS-004, not from an independent
reproduction. Whoever picks this up should confirm it live before treating
it as a confirmed defect (see "What would confirm this" below).

## Reproduction (QA-KB-020, validated 2026-10-01, 3/3 cold runs)

**Browser repro substituted by an offline hook repro.** A UI repro needs two
family runs parked at live review gates, i.e. launching paid runs and leaving
them parked, which the line forbids. Orchestrator decision: drive the real
`useRunChat` hook (renderHook) with synthetic frames instead. Throwaway vitest
(deleted after; source kept at `evidence/qa-kb-020/00-validate-throwaway-vitest-source.ts.txt`):
two `chat_reply` gate cards (`card_kind: "gate"`, `pipeline_run_id` run-A then
run-B, both unresolved), then one `review_gate_approved` frame.

- Approve run-B (the later gate): `{run-A:false, run-B:true}` — correct, but only
  because B happens to be positionally last.
- Approve run-A (the EARLIER gate): `{run-A:false, run-B:true}` — WRONG. Run-B's
  gate is flipped to resolved, run-A's own gate stays open. Identical in all 3
  cold runs (`evidence/qa-kb-020/01-validate-attempt{1,2,3}-vitest-output.txt`).

Correction to the "What would confirm this" step 3 below: approving the
most-recently-opened gate resolves the right card; the defect fires when the
approval belongs to an EARLIER gate while a later run's gate is still open.
Trigger: >=2 unresolved gate cards from different runs in one family transcript
and an approval for any but the last. Maps to BUG QA-KB-020. The frame's
`pipeline_run_id` is available but ignored at `useRunChat.ts:574-583`.

## Why QA-PS-004's root cause implies this

ISS-650's confirmed mechanism is that a chat-lane gate card carries no
durable identity a *renderer* can use to show an agent name. This card is
the same gap on the *resolve* side: no identity for the *resolver* to match
against either.

`case "review_gate_approved"` in `useRunChat.ts` resolves a pending gate
card like this:

```ts
// frontend/src/hooks/useRunChat.ts:570-579
setMessages((prev) => {
  // Find the last unresolved gate card and flip it.
  const idx = prev.map((m, i) => ({ m, i }))
    .reverse()
    .find(({ m }) => m.cardKind === "gate" && !m.resolved)?.i;
  if (idx === undefined) return prev;
  const updated = [...prev];
  updated[idx] = { ...updated[idx], resolved: true };
  return updated;
});
```

This matches by ARRAY POSITION only ("the last unresolved gate card" in
`prev`) — no `runId`, `agentId`, or `gate_key` comparison against the
incoming event. The incoming `review_gate_approved` frame's own `data`
already carries fields that could disambiguate — `agent_id` and
`pipeline_run_id` (`backend/agents/execution_engine/engine.py:10447-10452`)
— but the handler never reads them.

`prev` is not guaranteed to hold only one run's turns. The transcript is
explicitly "family-anchored": `upsertNarratorMessage`'s own doc comment
states a family member's card carries ITS OWN run id and the merged
transcript stitches sibling/child-revision runs together
(`frontend/src/hooks/useRunChat.ts:400-407`), and FIX-178's contemporary
(FIX-167, same subsystem) established that a revision/child run's turns are
seeded into the SAME transcript array as the parent's (`seedRunChatTranscript`
fetches sibling/child runs via `getRunFamily`). So more than one `runId` can
coexist in `prev` by design, not as a corner case.

If a parent run's gate card is still unresolved while a revision/child run
in the same family ALSO opens — and later resolves — its own gate, the
child's `review_gate_approved` frame would flip whichever unresolved gate
card sits last in array order, which may be the PARENT's still-genuinely-
pending gate rather than the child's own. The visible effect: a gate card
renders "Review approved — build continues" for a gate the backend has not
actually resolved — the real pending approval is still blocking the OTHER
run.

## Expected (once reproduced)

An approval event only ever resolves the ONE gate card it actually
corresponds to (matched by run + agent/gate identity), regardless of how
many other runs' turns share the transcript array.

## Actual (inferred, not yet observed)

Approving a gate in one run of a family can flip a DIFFERENT run's
still-open gate card to the resolved rendering, while that other run's real
gate remains blocked server-side awaiting the user's actual response.

## What would confirm this

1. Start a run that opens a review gate and leave it pending
   (`waiting_for_user`).
2. From the same family, get a second gate open at the same time —
   e.g. a revision/child run that opens its own gate before the parent's is
   approved, or a redo/re-open sequence that leaves an older gate card
   marked unresolved while a newer one opens.
3. Approve the more-recently-opened gate and check whether the OTHER,
   still-genuinely-pending gate card also flips to "Review approved — build
   continues" in the shared transcript, while the backend still reports that
   run/agent blocked in `waiting_for_user`.

## Analysis (QA-KB-020 analyzer, 2026-10-01)

**Verdict.** The mechanism this card describes is correct and is now CONFIRMED (offline, 3/3,
above); its meaning stands. Only the line numbers had drifted: the handler is
`useRunChat.ts:569-584` (updater `:574-583`) and the producer is `engine.py:12565-12573`. The
BUGS.md repro has the direction reversed, see "Which approval goes wrong".

### Root cause (CONFIRMED, file:line read)

`handleFrame` pairs a `review_gate_approved` frame with a card by array position, not identity:

```ts
// frontend/src/hooks/useRunChat.ts:574-583
setMessages((prev) => {
  // Find the last unresolved gate card and flip it.
  const idx = prev.map((m, i) => ({ m, i }))
    .reverse()
    .find(({ m }) => m.cardKind === "gate" && !m.resolved)?.i;
  if (idx === undefined) return prev;
  const updated = [...prev];
  updated[idx] = { ...updated[idx], resolved: true };
  return updated;
});
```

Both halves of a usable key exist on every path and are never read:

- **The frame carries the run.** `engine.py:12565-12573` yields `review_gate_approved` with
  `pipeline_run_id` and `agent_id` (no `agent_name`, no `gate_key`). Both durable readers pass
  `payload_json` through (`runs.py:1568`, `run_stream.py:431-441`, `api.ts:1485-1490`), so replay
  and seed frames carry it too.
- **The card carries the run.** A gate card's `runId` is `data.run_id ?? data.pipeline_run_id`
  (`useRunChat.ts:406-407`, `:425`). The narrator card has `pipeline_run_id` and no `run_id`
  (`chat_narrator.py:255-261`; the live frame is `{**_card, seq, event_id}`, `engine.py:4228-4241`),
  so on every path (live, replay, family seed) `m.runId` is the run that opened that gate.
  `types/index.ts:123-125` documents `runId` as the family-anchoring field, and `:110-116`
  documents `resolved` as set "for the gate this card represents", which the positional code does
  not honour.

### Which approval goes wrong

"Last unresolved by position" is right whenever the approved gate's card is also the positionally
last unresolved one, so approving the LATER run's gate resolves the right card by luck (validator
S1). It is wrong when the approval belongs to an EARLIER run while a later run's gate card is
still unresolved: the later card flips and the earlier one stays open (validator S2, 3/3).
BUGS.md repro step 3 ("approve the child's gate") is therefore the working direction. The failing
one is approving the PARENT's gate while the child's card is in the transcript.

### Reachability: what must be true

1. The transcript holds gate cards of two runs and the approved run's card is not the last
   unresolved one.
2. Live frames cannot create that on their own: `chatSubscribe` drops frames whose `_sourceRunId`
   is not the viewed run (`page.tsx:2400-2417`). Other runs' cards enter through the family seeds,
   history reopen (`page.tsx:3139-3224`, order `[earlier members' chat, opened run's frames, later
   members' chat]`) and the revision remount (`page.tsx:3569-3698`). A seeded other-member gate
   card stays unresolved while the opened run is non-terminal, because its approval frame is
   filtered out of the seed ([ISS-925](20261001-2223-ISS-925.md)).
3. So the trigger is: the viewed run V has a gate genuinely pending, and a family member created
   AFTER V has a gate card. The backend REST path allows it: `create_revision` checks parent
   ownership only (`run_commands.py:5575-5585`), `_mint_revision_row` has no parent-status check
   (`:4560-4710`), and `_has_active_chain_revision` blocks only a second active DESCENDANT, the
   root excluded by design (`:4526`). The lane's own chat router cannot produce it: it emits
   `CHANNEL_REVISION` only for a terminal run (`chat_router.py:259-274`; a gate-paused run routes
   to the gate or Concierge channel, `:235-257`). The Concierge `revision` disposal
   (`run_commands.py:1635-1745`) has no status check inside the disposal; whether the Concierge ever
   proposes one on a gate-paused run was NOT read (INFERRED). Net: reachable through the API,
   narrow through the UI, so real-world frequency is low even though the defect is real.
4. Within ONE run, live frames cannot trigger it: the backend keeps one review gate open per run
   (`gate_pendency.py:167`, "one-gate-open-at-a-time"), so the open gate's card is always that
   run's newest.

### Impact

Chat-lane status text only. A gate card is inline text (`ResultCard.tsx:133-151`); the real
approve/reject surface is the Steps-panel gate, driven by the per-run store
(`page.tsx:2180-2188`), which is correct. Nothing is blocked server-side and the user can still
approve. The wrongly flipped card reads "<WrongAgent> review approved — build continues" (FIX-518
stamps `agentName`), while the pending gate's own card keeps "<Agent> review required" and
"Open in Steps".

### Blast radius (grepped)

- `resolved` is written in exactly two places in the frontend: this handler and the terminal
  auto-resolve at `useRunChat.ts:750-756` ([ISS-664](20260917-1310-ISS-664.md),
  [ISS-925](20261001-2223-ISS-925.md)). Nothing else selects a gate card positionally
  (`cardKind === "gate"` appears only in `ResultCard.tsx` rendering and those two writers).
- The other consumers of `review_gate_approved` are already run-scoped and not defective:
  `page.tsx:2170-2200` (uses `_sourceRunId`), `useWorkflow.ts:1196-1199` (one boolean on per-run
  state), `useRunStateStore.ts:555` (an allowlist entry).
- Producer: one site, `engine.py:12565`. No backend change is needed.
- Every entry point folds frames through `handleFrame`, so ONE guard covers all of them: the
  `subscribe` fan-out (`useRunChat.ts:632`), `seedTranscript` (`:744`; callers `page.tsx:2823,
  3224, 3677, 3698, 3713, 4292`), `appendFrames` (`:799`; `page.tsx:1669`) and the post-send
  re-fetch (`:719`).

### Fix: where it belongs, and the agreed minimal fix

It belongs in `case "review_gate_approved"` of `handleFrame` (`useRunChat.ts:569-584`). The agreed
minimal fix from BUGS.md (read `data.pipeline_run_id` as `rid`; add
`(!rid || !m.runId || m.runId === rid)` to the `.find` predicate) is ACCEPTED, with two
amendments:

1. Wrap the case body in braces (`case "review_gate_approved": { ... break; }`). The agreed text
   declares `const rid`, and a bare `case` trips `no-case-declarations`; `case "concierge_proposal": {`
   at `:585` already uses braces.
2. One test is not enough; see the test notes.

Why run identity and not "run + agent" as Expected asks: the card carries only `agent_name`
(`chat_narrator.py:265-266`) and the approval only `agent_id` (`engine.py:12569`), so there is no
shared agent key, and one open gate per run makes run identity sufficient for live approvals.
Agent-level matching would need an additive backend field on the card, which is not recommended.

Do not: match on `agent_name` or pipeline type (SC-001, and the frame has no name), "resolve the
first unresolved" (it inverts the bug), or touch the backend.

Known limit (INFERRED, no reachable path found, not carded): an approval replayed AFTER all of its
run's cards are already in the transcript would still pair with that run's newest card. Full-frame
seeds fold card then approval in seq order, and chat-only seeds are used for runs that have no
approvals yet.

- Fail-before (red offline, 3/3): two `chat_reply` gate cards with `card_kind: "gate"` and
  `pipeline_run_id` `"run-A"` then `"run-B"`, both unresolved; emit `review_gate_approved` with
  `pipeline_run_id: "run-A"`; assert A resolved and B not. The validated throwaway is
  `evidence/qa-kb-020/00-validate-throwaway-vitest-source.ts.txt` (it maps
  `Object.fromEntries(messages.map(m => [m.runId, !!m.resolved]))`).
- Guards: approving B resolves only B; an approval with no `pipeline_run_id` and one gate card
  still resolves it (fallback); an approval for a run with no card in the transcript resolves
  nothing (fail-before: it flips another run's card); two unresolved cards of the SAME run, the
  newest resolves.
- Run: `cd frontend && npx vitest --run src/hooks/useRunChat.test.ts` (one file, offline). The
  existing ISS-664 `it.fails` (`:573`) must stay an expected failure; its path (`seedTranscript`
  auto-resolve) is untouched.
