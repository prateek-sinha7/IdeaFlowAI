## What was wrong

The Composer's Simple tab reported a workflow's deliverable as the literal string
"Custom" for every workflow, while its Canvas tab — the sibling tab on the SAME in-memory
composition — showed the real strategy. Reproduced 3/3 on `/workflows/ppt/canvas`
([ISS-340](20260828-1856-ISS-340.md)): Simple `Custom`, Canvas `ppt — declared by this
workflow`. The same disagreement was reachable from every built-in canvas route and, via
the identical unconditional line, from a saved custom workflow reopened at
`/workflows/{id}/edit` ([ISS-580](20260829-0236-ISS-580.md)).

## Root cause

`frontend/src/components/workflow/composer/ComposerPage.tsx:478` (pre-fix):

```ts
const deliverableLabel = PIPELINE_LABEL.custom;
```

One variable carried TWO different vocabularies. `PIPELINE_LABEL` is pipeline-TYPE naming
("Presentation", "Prototype", "Custom") and was correct for the header eyebrow at `:1020`
(`${deliverableLabel} · Composer`), but the same value was also passed to
`<IdentityCard deliverableLabel=...>` at `:1195`, where the field is a deliverable
STRATEGY (`data-testid="composer-deliverable-type"`). Because the constant never read
`runConfig`, the Simple label could not vary by workflow, while `CanvasView.tsx:1574`
already derived its combobox from `runConfig?.deliverable?.strategy` off the same state.
Nothing shared a derivation between the two tabs, so they could only agree by accident.

## What changed and why there

- `frontend/src/components/workflow/composer/CanvasView.tsx` (module scope, above
  `CanvasView`) — added `DELIVERABLE_STRATEGY_LABEL` (the three `user_allowed=True`
  resolvers per [ADR-0027](20260825-2115-ADR-0027.md)) and
  `deliverableStrategyLabel(strategy?)`, which falls back to the honest
  `"${strategy} — declared by this workflow"` for a declared-but-not-grantable strategy
  (`ppt`). The rail's three `<option>` texts and its dynamic unofferable-strategy option
  now both render from that one source, so the label the Canvas shows and the label the
  Simple tab shows are the SAME string by construction — they cannot drift apart again.
- `frontend/src/components/workflow/composer/ComposerPage.tsx:479,485,1027,10` — split the
  conflated variable: `pipelineLabel = PIPELINE_LABEL.custom` keeps feeding the header
  eyebrow (`"Custom · Composer"`, which `ComposerPage.test.tsx:190` already asserts as
  intended behaviour and which is genuinely the composer's pipeline type), and
  `deliverableLabel = deliverableStrategyLabel(runConfig?.deliverable?.strategy)` feeds the
  identity card. Fixed at the single computation site, so every route through this one
  generic component — every `/workflows/<type>/canvas` built-in, `/workflows/new`, and
  `/workflows/{id}/edit` — is covered by the one edit.

Deliberately NOT changed: the header eyebrow does not become the deliverable sentence.
[ISS-580](20260829-0236-ISS-580.md) names `"Custom · Composer"` as a second symptom of the
same line, but [ISS-340](20260828-1856-ISS-340.md)'s own fix section is explicit that
`PIPELINE_LABEL` is a different vocabulary from a deliverable strategy; rendering
"Serialized sandbox — zip the workspace · Composer" as a breadcrumb would be wrong, and an
already-green assertion (`ComposerPage.test.tsx:190`) encodes the eyebrow's current text as
intended. The conflation itself was the defect; separating the two names is the fix.

## Known residual (not this fix's mechanism)

`test_simple_and_canvas_agree_on_ppt_deliverable_type` flakes roughly 1 run in 5 on a cold
load: observed 4/5 XPASS, and the one failure captured with `--runxfail` reads
`Simple shows 'ppt — declared by this workflow' but Canvas shows "Streamed text — agent's
raw output"`. Simple holds the TRUE value there; Canvas was READ before
`GET /api/workflows/ppt` seeded `runConfig` (`ComposerPage.tsx`'s `seededRunConfig` effect
adopting a late prop). That is the cold-load seeding race
[ISS-340](20260828-1856-ISS-340.md) already scopes out, filed here as
[ISS-604](20260829-0207-ISS-604.md). Re-run rather than treat a single `x` as a regression.
