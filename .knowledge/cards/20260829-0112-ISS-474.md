## Why this must also be broken

[ISS-321](20260828-2002-ISS-321.md) and [ISS-472](20260829-0110-ISS-472.md) each found a render
surface reached through `frontend/src/app/[...view]/page.tsx` with no tier check at the point the
catch-all decides what to render. A third one exists on the same pattern: `page.tsx:473` resolves
`builtinCanvasType` (via `builtinCanvasTypeFor(parsedView)`) for the `/workflows/{type}/canvas`
route -- per ADR-0014, "a built-in workflow opens on the canvas at its own URL and can only be
saved as a copy". `initialMainViewFor`'s `"workflow-canvas"` case (`page.tsx:135-136`) maps this
to `MainView: "composer"`, and `builtinCanvasType` is threaded into `initialWorkflowType`
(`page.tsx:3963`), which becomes `DashboardLayout`'s `workflowType` state
(`DashboardLayout.tsx:573-583`).

`DashboardLayout.tsx:2937-2946` renders `<ComposerPage>` for `mainView === "composer"` with props
`workflowType`, `onBack`, `onUnsavedChange`, etc. -- no `userTier` or tier-shaped prop, mirroring
exactly what ISS-472 found for `IdeaInputPage`. Confirmed by reading `ComposerPage.tsx`: `grep -n
"tier\|entitle\|can_run_pipeline\|canRunPipeline"` returns zero matches in the entire file -- the
component has no tier awareness anywhere, not even a partial or stale one.

As with the other two render surfaces, `userTier` reaches `DashboardLayout` as a prop
(`page.tsx:4187`) but is only ever forwarded to `AppHeader` (cosmetic) and `HomeLaunchGrid` (the
one correctly-gated consumer, `DashboardLayout.tsx:2750`) -- never to the `"composer"` branch.

## Expected vs actual

**Expected:** opening a built-in workflow's canvas for a pipeline type outside the account's tier
(e.g. `/workflows/prototype/canvas` as `basic`, which excludes `prototype` per
`TIER_PIPELINES["basic"]`) shows the same locked/upgrade state the dashboard catalog card would,
consistent with `/settings/usage` and with ISS-321's expectation for the wizard.

**Actual (INFERRED -- not yet independently reproduced):** the canvas should render fully
interactive -- the composed step DAG, agent picker, model overrides, and (per ADR-0014) a "Save as
copy" action -- for a basic-tier account, with no client-side indication the account cannot launch
this pipeline type. Whether `ComposerPage`'s own `Run once` action (if reachable from a built-in
canvas at all -- ADR-0014 says built-ins "can only be saved as a copy") reaches the backend launch
endpoint the same way ISS-321 confirmed `_require_tier_entitlement` catches, or whether "Save as
copy" alone has some other consequence for an unentitled tier, is not established here and would
need its own check.

## What would confirm or refute this

Sign in as `qa-basic@flowinqa.com`, navigate directly to
`http://localhost:3000/workflows/prototype/canvas` (a built-in `prototype` canvas; basic tier
excludes `prototype`). Confirm the composer renders fully interactive with no lock/upgrade
indication anywhere on the surface. If a "Run once" action is present and reachable, confirm
whether it 403s at the backend (mirroring ISS-321) or behaves differently. A miss (e.g. the route
itself redirects or renders not-found for a basic-tier session) would refute this card.

## Where the fix belongs

Same choke point as ISS-321 and ISS-472: `frontend/src/app/[...view]/page.tsx` already resolves
both `user.tier` and `builtinCanvasType` before `initialMainViewFor` decides `mainView ===
"composer"`. A single guard placed there -- gating `"workflow-canvas"` the same way as the
`wizardMode` and `"input"` cases -- closes this card alongside the other two in one change, via
the existing `canRunPipeline(tier, pipelineType)` from `frontend/src/lib/entitlements.ts:94`.

## Analysis 2026-10-02 (QA-KB-052)

Re-checked while analysing [ISS-472](20260829-0110-ISS-472.md) (the Input-panel twin of this card). Static read, no browser; line numbers are the working tree on 2026-10-02 (HEAD `024c03ef8`), with the same
caveat about uncommitted edits in `DashboardLayout.tsx` and `page.tsx`. Proof outputs: `evidence/qa-kb-052/analysis-proof.out.txt`. This card's `DashboardLayout.tsx:2946` is now `:3196-3253`. Status stays `open`; this note changes no claim above, it adds scope and corrects the fix location.

**Still CONFIRMED.** `ComposerPage.tsx` has zero references to tier, entitlement, `canRunPipeline` or upgrade (evidence 1), and the `<ComposerPage>` render block (`DashboardLayout.tsx:3196-3253`) carries no `userTier` (evidence 3b).
The card's open question, whether Run once is reachable from a built-in canvas and what it does, is answered: `handleRunOnce` (`ComposerPage.tsx:1003`) sends an **unmodified** built-in as itself, `onRun(builtinCanvasType, brief, [], ...)` (`:1202-1207`),
and anything else as `dispatchType` (`:1211-1216`), which `resolveDispatchType(pipelineAgents, "custom")` pins to `"custom"` (`:1044`). The button is `disabled={!onRun || isSubmitting}` (`:1357`) and the brief shortcut calls `handleRunOnce` directly (`:1505`). Both reach `POST /api/runs`,
where `run_commands.py:3510` returns a 403 `tier_not_entitled`, which the client then swallows ([ISS-969](20261002-0338-ISS-969.md)).

**The card's own "what would refute this" does not apply.** `page.tsx:572` and `:4088` render not-found when the canvas seed fetch returns 403/404, which could look like a tier gate. It is not one: `GET /api/workflows/{id}` has no tier check (`workflows.py:420-449`, evidence 6), so a basic account gets the manifest and the canvas.

**The scope is wider than the title.** The same component is mounted for four routes, and only one is the built-in canvas:

| route | type the composer dispatches / saves | locked for |
|---|---|---|
| `/workflows/{type}/canvas` | `builtinCanvasType` (e.g. `app_builder`) | tiers whose plan excludes that type |
| `/workflows/new` | `custom` (literal, `:1044`; save `base_pipeline_type: "custom"`, `:931`) | `basic`, `hexaware`, `pro` (only `enterprise` has `custom`, `backend/app/core/entitlements.py:67`) |
| `/workflows/{id}/edit`, `/workflows/{id}/run` (composer rows) | `custom` | same as above |

Reachable by a click, not only by URL: My Workflows' "New workflow" (`SavedWorkflowsPage.tsx:270-275`) calls `handleSelectFeature("custom")` (`DashboardLayout.tsx:3145`), which opens the composer for every tier with no tier check (INFERRED: nobody has clicked it as `basic`).
So a `basic` or `pro` account can compose a whole workflow whose Save and Run once both 403 ([ISS-968](20261002-0338-ISS-968.md) covers Save).

**Where the fix belongs (supersedes "page.tsx at the wizardMode resolution point").** Inside `ComposerPage`, the single component all four routes mount (one render site, `DashboardLayout.tsx:3196`), as in the Input-panel analysis on [ISS-472](20260829-0110-ISS-472.md)
and [FIX-497](20260829-0242-FIX-497.md). A `page.tsx` guard cannot see the saved-row routes or the in-app click, and `page.tsx` renders before the tier is known. Two traps specific to this surface:

- **Do not key the gate on the `workflowType` prop.** DashboardLayout's shared `workflowType` is `user_stories` on `/workflows/new`, `/edit` and `/run` ([BUG-025](20260827-BUG-025.md)); `user_stories` is entitled on every tier, so a gate keyed on it never locks.
  Key it on what the composer actually dispatches: `builtinCanvasType` when an unmodified built-in is on screen, otherwise `"custom"`.
- The tier source must be nullable (unknown never locks) for the reason given in the ISS-472 analysis: `DashboardLayout`'s `userTier` is `"basic"` while the profile loads or if it fails. Apply `locked` to `handleRunOnce` (covers `:1505`), the Run once button (`:1357`) and a lock banner.

**For the test-writer.** Offline: mount `ComposerPage` as the other composer tests do, with `auth.user.tier = "basic"` in the preloaded store and `builtinCanvasType="app_builder"` plus the unmodified built-in steps; assert Run once is disabled with the lock copy.
Control: `tier: "pro"` is enabled. A second case on `workflowType="user_stories"` with no `builtinCanvasType` and `basic` must also lock (it dispatches `custom`), which is what proves the gate does not read the prop.
