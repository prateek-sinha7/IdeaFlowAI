## What was wrong

`BUG-20260829-0090`: clicking "Run once" with a brief shorter than 3 characters
produced no visible feedback — the brief textarea regained focus (or the Canvas
Brief node was selected), but no banner, toast, `aria-invalid`, or red border
appeared. The button had an `opacity-60` visual treatment and a `title="Add a brief
first"` tooltip (hover-only), both of which were insufficient as click-time signals.

This is the exact pattern [ISS-315](20260828-1750-ISS-315.md) named for the Save
button's empty-name guard before [FIX-375](20260829-0151-FIX-375.md) fixed it:
a guard that correctly blocks the action but reports nothing observable on the click.

## Root cause

`frontend/src/components/workflow/composer/ComposerPage.tsx` — Run once button
`onClick` — the `briefText.trim().length < 3` branch returned after focusing
without calling `setSaveError`.

## What changed and why there

One `setSaveError` call added inside the `briefText.trim().length < 3` branch of
the Run once button's `onClick`, replicating FIX-375's pattern at the one matching
call site:

```tsx
if (briefText.trim().length < 3) {
  // ISS-431 — replicate FIX-375: report through the saveError banner.
  setSaveError("Add a brief of at least 3 characters before running.");
  if (view === "simple") {
    briefTextareaRef.current?.focus();
  } else {
    setBriefFocusSignal((n) => n + 1);
  }
  return;
}
```

The banner is cleared (`setSaveError(null)`) at the head of `handleSave` (the same
surface FIX-375 uses) and at the start of a successful `handleRunOnce` call, so a
prior error message does not persist once the user acts correctly. The focus/signal
behaviour is preserved unchanged alongside the new banner call.
