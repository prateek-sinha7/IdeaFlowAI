## What was wrong

On `/create/prototype` and `/create/ppt`, Upload custom -> From URL ->
`https://hexaware.com/` -> Fetch showed **"Could not reach that URL. Check the
address and try again."** and `GET /api/prototype/fetch-url` returned `502`.
The URL is publicly reachable — `curl` fetches it fine from the same machine.

## Root cause

`backend/app/api/prototype_templates.py:349` built its client with no `verify=`
override:

```python
async with httpx.AsyncClient(follow_redirects=True, timeout=10.0) as client:
```

`httpx`'s `verify=True` default resolves to **certifi's bundled CA list only**
— it never consults the OS/enterprise trust store. This environment sits
behind a TLS-intercepting proxy whose CA is installed in the OS store (which
is why `curl` works) but is absent from certifi's bundle, so every outbound
`https://` handshake raised `ssl.SSLCertVerificationError` wrapped in
`httpx.ConnectError`. The catch-all at `prototype_templates.py:387-392`
(installed by [FIX-396](20260829-0348-FIX-396.md)) turned that into the generic
502 the user sees. Nothing about `hexaware.com` was special — the fetcher
failed for 100% of intercepted hosts.

## What changed and why there

New shared helper `backend/app/core/http_client.py::default_ssl_context()`
(`lru_cache`d, built once per process):

```python
context = ssl.create_default_context()          # OS/enterprise store + SSL_CERT_FILE
context.load_verify_locations(cafile=certifi.where())
```

The **union** of both stores, deliberately: `create_default_context()` alone
would regress any deployment whose image ships no system CA bundle, and
certifi alone is the bug. Verification itself is untouched —
`verify_mode=CERT_REQUIRED`, `check_hostname=True`, observed on the built
context. `certifi` is not a new dependency: it is a hard requirement of
`httpx==0.28.1` (`importlib.metadata.requires('httpx')` -> `[... 'certifi' ...]`).

Routed through it — every outbound (non-localhost) httpx client in the
backend, the set found by
`grep -rn "httpx\.AsyncClient(\|httpx\.Client(\|httpx\.get(" backend --include="*.py" | grep -v /tests/`,
re-run at fix time and still exactly five:

- `app/api/prototype_templates.py:349` — `fetch_url_for_template`, the reported path ([ISS-695](20260922-0800-ISS-695.md))
- `app/api/settings.py:130` — `upsert_github_pat` ([ISS-750](20260922-1403-ISS-750.md))
- `app/services/handoff_github.py:292,334` — `get_repo_metadata` / `create_pull_request` ([ISS-751](20260922-1404-ISS-751.md))
- `app/core/cognito.py:114` — `_fetch_jwks` ([ISS-738](20260922-1405-ISS-738.md))

Fixing only `prototype_templates.py` would have left four call sites carrying
the identical defect. The three siblings do not reproduce **in this
environment** — the test-writer showed this proxy allowlists `api.github.com`
and `cognito-idp.*.amazonaws.com` while intercepting arbitrary domains — but
that is a property of the proxy's allowlist, not of the code: a GitHub
Enterprise `api_base`, a different proxy policy, or a different network brings
them straight back. The change at those four sites is one keyword argument
each and can only widen trust, never narrow it.

## Deliberately not changed

- `_is_private_url` (`prototype_templates.py:305-318`) and the SSRF posture
  around it — untouched, per ISS-695's explicit caution. This fix changes
  *which CAs are trusted*, never *which hosts may be fetched*.
- The catch-all 502 handler at `prototype_templates.py:387-392` — still the
  right behaviour for a genuinely unreachable URL.
- The `truststore` package that ISS-695 floated as an option — avoided; the
  stdlib context plus certifi does the same job with no new dependency.
