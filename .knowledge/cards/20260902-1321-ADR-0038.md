## Status

**Proposed — not decided.** The open questions in the last section must be
answered by a human before this is implemented. Nothing in the code has
changed.

## What is true today

Authorization is keyed on one string: where the manifest's bytes came from.

| Fact | Evidence |
|---|---|
| `_TRUSTED_SOURCES = frozenset({"file", "builtin"})` — everything else is untrusted | `backend/agents/workflows/compiler.py:205` |
| Untrusted ceiling is `{max_subagents: 8, max_depth: 2, wall_clock_seconds: 900}` | `compiler.py:220` |
| Declaring above the ceiling is a hard `CompilerError`, not a clamp — a 422 at save or at launch | `compiler.py:397-405`, surfaced at `app/api/user_workflows.py:115`, `app/api/run_commands.py:2672` |
| Trusted manifests have **no** upper bound — there is no ceiling constant, the rejection loop simply sits inside `if not trusted` | `compiler.py:397` |
| **No shipped file manifest declares `max_subagents` or `max_depth`.** Twelve declare `limits:` and every one sets only `wall_clock_seconds` (180-5400). So every workflow in the system today, file or DB, runs on `DEFAULT_MAX_SUBAGENTS = 8` | `grep -rn '^limits:' -A4 backend/agents/workflows/*/workflow.yaml`; `budget.py:43`, applied `budget.py:95` |
| The trusted/untrusted gap is exercised TODAY in exactly one dimension: `pdf_to_prototype` declares `wall_clock_seconds: 5400`, a raise above the 900 ceiling that is legal only because it is trusted. The same value in a DB row is a `CompilerError` | `backend/agents/workflows/pdf_to_prototype/workflow.yaml:70-71` |
| Capabilities are gated the same way (CAP-03) | `compiler.py:436-443` |
| `compaction: html_skeleton` is registered with no `user_allowed`, so it defaults to trusted-only | `backend/agents/capabilities/compaction/html_skeleton.py:29-33` |
| An untrusted step's `tools.tool_sets` grant is capped to `["file_extract", "playwright"]`; the trusted list includes `prototype` / `prototype_emit_only` | `backend/agents/workflows/permission_caps.py:104-112`, `:85-95` |
| Callers that compile untrusted: `trust="db"` for saved rows and overrides, `trust="user"` for inline manifests | `user_workflows.py:115`, `overrides.py:100`, `run_engine.py:739` |
| The budget object is built once per run from the compiled limits | `backend/agents/execution_engine/engine.py:1801` |
| `Step` has no `limits` field — there is no per-step escape hatch anywhere | `backend/agents/workflows/plan.py` |

**The asymmetry is a permission, not a number.** No engineer has yet raised
`max_subagents` anywhere, so the practical difference between a file and a DB
workflow today is one `wall_clock_seconds` value. That makes this decision
cheaper than it looks — almost nothing depends on the current behaviour — but
it also means the 8-subagent default, not the trust split, is what actually
blocks parallel work. Both need to move.

Two related constants are not policy at all, and are worth folding into this
decision rather than leaving behind:

- `DEFAULT_MAX_CONCURRENCY = 5` (`backend/agents/execution_engine/budget.py:44`)
  is a bare module constant. `_resolve_concurrency` clamps every declared
  `max_parallel` to it (`fanout.py:191-201`). **No manifest, setting or
  environment variable can raise it**, trusted or not.
- `max_subagents` is a **lifetime total**, incremented at `budget.py:215` and
  never decremented anywhere in the module; the check is
  `spent + n > max` at `budget.py:194`. It is not a concurrency cap, though it
  reads like one.

## The problem this produces

**1. The same steps get different budgets depending on where the bytes live.**
Move a 9-step workflow from `agents/workflows/<id>/workflow.yaml` into
`workflows.manifest_json` and it drops from unbounded to 8 subagents. Nothing
about the steps changed. `source` is a proxy for "a human reviewed this", and
it is being used to answer "how much may this cost" — two unrelated questions
on one axis.

**2. Parallel work is unreachable from the Composer, in practice.** Observed
while building the `pdf_to_prototype` v2 workflow (DB row
`f4994856-7b61-45d7-8c57-9e538f745e36`):

- A nested `subagents: {mode: parallel}` group compiles to `parallel_group`
  with a real `FanoutSpec` (`compiler.py:706-728`) and dispatches through
  `run_fanout` (`parallel_group.py:132`), so it **reserves**. The workflow's
  five PDF readers permanently spend 5 of the 8, leaving 3 for the entire rest
  of the run.
- `wave_scheduler` charges one subagent per task, cumulatively across waves
  (`wave_scheduler.py:267`, `:323`). A 20-task or 60-task wave build therefore
  dies at task 9 with `BudgetExceeded`, mid-run, with earlier waves' output
  already on disk.
- Consequence: a document-driven build of 60 screens **cannot** be expressed
  as a Composer workflow at all. The only way to buy the budget is to move the
  manifest to disk, where it is no longer user-editable.

**3. The one uncapped path is uncapped by accident, not by design.**
`task_loop` never enters `run_fanout` (`task_loop.py:274`, `:334` dispatch via
`runner.run_agent`), so it costs zero subagent budget, has no iteration cap, no
task-list truncation, and is never wall-clock checked. A DB workflow may
therefore run 60 sequential agents for hours — far more total spend than the
8-subagent fan-out it is forbidden — because the meter is attached to the
mechanism rather than to the consumption. **The cap does not measure what it
claims to measure.**

**4. The wall clock barely exists.** `note_wall_clock` is called from exactly
three sites, all inside `fanout.py` (`:571`, `:598`, `:690`). The step-dispatch
loop never consults the budget. A run whose only fan-out is early (the readers)
arms the deadline at `fanout.py:335` and is then never checked again — which is
why run `faba87c9` ran roughly three hours under a 5400s limit without
aborting. The 900s ceiling bites hard inside a wave build and not at all
elsewhere, so its practical effect is close to the opposite of its intent.

**5. Trusted-only capabilities are gated on maturity, not risk.**
`html_skeleton` is a compaction strategy — it cannot harm anyone. It is
trusted-only because it was written for the prototype shape and is unproven
elsewhere. Denying it to composed builds forces every per-task sub-agent to
re-read the whole growing `prototype.html`, which is a direct cause of late-task
drift and duplicated helpers.

**6. The existing workaround has a silent failure mode.** An override row
supplies `steps` only and inherits `limits` from the file manifest on every
resolve (`overrides.py:87-93`, `:122-125`). But its isolated compile still runs
at `trust="db"` (`overrides.py:100`), so trusted-only capabilities are still
refused — and on `CompilerError` the whole override is **discarded silently**
and the run falls back to the file plan (`overrides.py:101-107`). The user's
customisation vanishes with no error surfaced.

## Decision (proposed)

Replace the source-keyed trust check with a policy consulted for the
**owner** of the workflow.

```
resource_policy   (per workspace, or per plan tier — admin-editable)
    max_subagents           clamped by a hard code ceiling
    max_depth
    wall_clock_seconds
    max_concurrency         ← today a bare constant, not policy at all
    capability_tier         ← beta/unproven capabilities on/off
    tool_tier               ← SEPARATE axis, security-reviewed
```

- `compiler.compile(..., trust=...)` stops taking a source string and takes a
  resolved policy instead.
- `file` and `builtin` manifests resolve to a system tier — they ship through
  code review, which stays a stronger guarantee than any row.
- The capability trust check (`_check_trust`, `compiler.py:436`) splits: a
  *maturity* flag for things like `html_skeleton`, and the existing
  security-shaped gate for tool sets.
- `DEFAULT_MAX_CONCURRENCY` becomes a policy field, because leaving it a
  constant means waves stay pinned at 5-wide no matter what an admin sets.

## What it solves

- A Composer workflow can run a real wave build; the `pdf_to_prototype` v2
  shape stops needing a disk fork purely to buy budget.
- `html_skeleton` reaches composed per-task builds, removing a known cause of
  build drift.
- A custom builder agent can be granted the `prototype` tool set, so composed
  workflows are no longer forced to reuse the library `prototype-build` agent
  to obtain `report_task_complete`.
- Budget becomes tunable per customer, which is the actual product need behind
  every workaround above.
- The override-row hack and its silent-discard failure mode stop being the
  recommended path.

## What it costs, and the new risks it creates

**Risks**

- *Privilege creep through one toggle.* If budget and tool tier share an admin
  switch, "give this team more subagents" silently becomes "user workflows may
  now shell out". This is the failure this ADR most needs to prevent, and it is
  why `tool_tier` is a separate field with its own review.
- *Noisy neighbour.* Per-owner limits without a global backstop let one
  workspace exhaust shared capacity. A system ceiling in code is required, not
  optional.
- *Admin as a new attack surface.* The role gate becomes security-relevant; it
  needs an audit trail on policy changes.
- *A wrong policy is now a runtime failure with no compile-time warning.*
  Today an over-declared limit is refused at save. If limits move to policy, a
  workflow saved under a generous policy starts failing mid-run when the policy
  is later lowered. Some of the guarantee moves from save time to run time.

**Cost**

- Migration plus a `resource_policy` table (or columns on an existing tier).
- Every `trust=` call site threads a policy through: `user_workflows.py:115`,
  `overrides.py:100`, `run_engine.py:739`, `run_commands.py:2668-2672`, and
  `WorkflowCompiler.compile`'s signature.
- An admin surface (frontend + API + role check).
- `budget.py` gains a policy-sourced concurrency value; `_resolve_concurrency`
  (`fanout.py:191-201`) stops referencing a module constant.
- The existing untrusted-ceiling tests need rewriting; they currently assert
  the source-keyed behaviour this removes.

## Alternatives considered

| Alternative | Why not |
|---|---|
| Raise `_LIMITS_DEFAULT_CEILING` | Lifts the cap for every user at once and removes the guard entirely. |
| Give DB manifests a fixed fraction of the file allowance ("half") | Keeps the conceptual bug — policy still keyed on storage location — and adds a magic number. |
| Allow-list specific workflow ids as trusted | Two-line stopgap, viable for one internal workflow, but does not scale and hides the policy in code. |
| Keep using override rows | Inherits budget but not capabilities, cannot be created from the Composer UI today, and fails silently (`overrides.py:101-107`). |

## Open questions — these need a human decision

1. **Should an admin ever be able to grant `exec` / `network` / `git` /
   `secrets` to a user-authored workflow, or does that stay code-only?** This
   decides whether `tool_tier` exists at all or whether tool grants simply
   remain source-keyed while budget moves to policy.
2. Policy scope: per workspace, per plan tier, or per user?
3. Does the hard code ceiling apply to admins too, or only to non-admin
   policies?
4. Do `file`/`builtin` manifests keep unbounded limits, or does the system tier
   also get a finite number so nothing in the platform is truly uncapped?
5. Should lowering a policy invalidate already-saved workflows at save time, or
   only fail them at run time?
