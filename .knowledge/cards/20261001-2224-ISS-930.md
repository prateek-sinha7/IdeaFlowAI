# ISS-930

Derived from the QA-KB-041 analysis of [BUG-104](20260829-1508-BUG-104.md). **Confidence: INFERRED** for real browsers. The
mechanism is CONFIRMED on the live source and reproduced offline in jsdom (below); nobody has run it in Safari or Firefox.

## Condition

`/admin`, the per-user tier dropdown (`TierDropdown`, `aria-haspopup="menu"`, one per row in the users table), opened by a
click that does not focus the trigger (Safari and Firefox on macOS do not focus a `<button>` on click; a programmatic
`.click()` does not either), then Escape pressed. Admin-only page, so the audience is small.

## Expected

Escape closes the menu: `admin.reskin.test.tsx:161-176` is named "open menu has role=menu and closes on Escape".

## Actual

The menu stays open and `aria-expanded` stays `"true"`.

## Why the root cause implies it

[BUG-104](20260829-1508-BUG-104.md): Escape is bound with a React `onKeyDown` on the wrapper element, so it only counts
keydowns that start inside the wrapper. A keydown targets `document.activeElement`; with the trigger unfocused that is BODY.

```tsx
// admin/page.tsx:83-86
<div
  className="relative inline-block"
  onKeyDown={(e) => { if (e.key === "Escape" && open) { e.stopPropagation(); setOpen(false); } }}
>
```

There is no `.focus()` call and no `autoFocus` anywhere in `TierDropdown` (`:57-126`), so nothing moves focus into the menu
on open. Outside click works because the full-screen `div.fixed.inset-0.z-40` overlay (`:100`) takes the click.

## Evidence (offline, jsdom; nothing under `frontend/src` was created or edited)

`evidence/qa-kb-041/08-analyze-probe-output.txt`, source `07-analyze-probe-admin.test.tsx.txt` (mocks copied from
`admin.reskin.test.tsx`):

| case | activeElement after the click | after Escape |
|---|---|---|
| CONTROL, `user.click(trigger)` (focuses, like Chrome) | the trigger button | menu closes |
| REPRO, `fireEvent.click(trigger)` (never focuses) | BODY | `aria-expanded = true`, `role="menu"` still present |

Why existing coverage cannot see it: `admin.reskin.test.tsx:161-176` opens the menu with `user.click(trigger)`, which focuses
the button, so it only ever exercises the working case.

## Reach (INFERRED)

Safari and Firefox on macOS admins. Chrome on every OS and a menu opened from the keyboard are unaffected.

## What would settle it

Real Safari or Firefox (macOS): open a tier dropdown with the mouse, press Escape. Do not grant or change any account on
`/admin` while checking; opening and closing the menu is all that is needed.

## Fix direction

Same as [BUG-104](20260829-1508-BUG-104.md): drop the wrapper `onKeyDown` (`:85`) and call the shared hook from
[FIX-388](20260829-0053-FIX-388.md), gated on the menu being open:
`useEscapeToClose(() => setOpen(false), open)` (`frontend/src/hooks/useEscapeToClose.ts`). `TierDropdown` does not refocus
its trigger today; keep that parity unless a trigger ref is added on purpose. Keep the `enabled` argument: the users table
renders one `TierDropdown` per row, and an ungated listener would be registered N times.

## Resolution (QA-KB-041, fixer, 2026-10-02)

[FIX-710](20261002-0154-FIX-710.md) applies the "Fix direction" above as written. `admin/page.tsx:71` now reads
`useEscapeToClose(() => setOpen(false), open);`. The wrapper `onKeyDown` is deleted (the wrapper is now `:87-89`). The
trigger is not refocused, which keeps parity with the old handler.

**The test file was corrected, and that is disclosed in FIX-710.** `admin.escape.test.tsx` checked `queryByRole("menu")`
for null synchronously after Escape. The menu leaves through a 0.1s `AnimatePresence` exit (`:100-109`), so with the fix
in place the test still reported "1 expected fail". Straight after Escape, `aria-expanded` was `false` and the node was
still mounted.

The check now runs inside `waitFor`, matching `admin.reskin.test.tsx:175`, which this card cites as the expected
behaviour. Against the pre-fix page the corrected test is red: a `waitFor` timeout after about 1.03s. On the fixed tree it
XPASSes in 3 of 3 runs. The marker is left for the verifier.
