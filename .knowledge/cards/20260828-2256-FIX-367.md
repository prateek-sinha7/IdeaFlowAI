## What was wrong

Two static strings, both gated on the same condition, both describing that
condition wrongly — and in the one direction that matters on a security
surface, by understating this application's own responsibility for a
credential.

1. `frontend/src/components/settings/SecuritySection.tsx:236-239` — the
   `SecurityPanel` `!status.supported` branch told a break-glass/local admin
   *"This account's credentials are managed outside the application, so
   two-factor authentication is configured separately."*
2. `backend/app/api/admin.py:558-563` — `reset_user_password`'s 409 `detail`
   for `user.auth_provider != "cognito"` said *"This account's password is
   managed outside the application and cannot be reset here."*

## Root cause

`status.supported` comes from `GET /api/auth/mfa`
(`backend/app/api/auth.py:906-948`); the only branch that sets it false is
`auth.py:925-933`, `if user.auth_provider != "cognito"`. `auth_provider`
(`backend/app/models/user.py:55-57`) takes exactly two values — `"cognito"`
or `"local"` — so that condition means break-glass/local and nothing else in
this codebase today. For that account type this application **is** the
credential store: `password_hash` (`backend/app/models/user.py:28-33`) is a
column on the app's own `User` row, and `POST /api/auth/change-password`'s
`local` branch (`auth.py:1254-1269`) verifies and rewrites it in place — from
the Profile tab of the very settings shell that was denying it.

Both strings were written for a genuinely Cognito-backed account and reused
verbatim for the only account type the condition can actually select. In
`SecuritySection.tsx` the comment two lines above the branch (lines 231-232)
already stated the correct reason — *"A break-glass/local account has no
Cognito factors to manage"* — while the JSX beneath it said something else,
and something false.

## What changed, and why there

No shared function covers both sites: one is a React JSX branch, the other a
Python `HTTPException` detail, cross-tier with no common code path. Grepping
`"managed outside"` across `frontend/src` and `backend/app` returns exactly
those two hits (ISS-404's blast-radius check, re-run before editing and still
accurate), so two independent copy corrections is the complete fix, not a
per-caller patch.

- `SecuritySection.tsx:236-240` — now: *"This is a local account, so there are
  no second-factor methods to manage here. Its password is stored by this
  application and can be changed from the Profile tab."* Matches the comment
  above it and points at the path that actually owns the credential.
- `admin.py:558-564` — now: *"This is a local break-glass account and cannot
  be reset here. Its password is changed from the account's own profile
  settings, or through the break-glass runbook."* The 409 and its design
  rationale (comment at admin.py:553-557) are untouched; only the wording
  handed to the caller changed.

### Test assertions that encoded the defect

Three existing assertion sites asserted the OLD, false copy as correct — a
blast-radius gap in ISS-404, whose grep was scoped to `frontend/src` and
`backend/app` and so never reached the test tree. They were re-pointed at the
corrected copy; **no assertion was weakened, and no application code was
changed to satisfy a test.**

- `tests/integration/e2e/framework/locators/settings_page.py` — added
  `LOCAL_ACCOUNT_NO_MFA` (the corrected copy). `EXTERNALLY_MANAGED` keeps its
  old value with a comment explaining why: `test_iss404_security_copy.py:58`
  uses it as the needle that must now have count 0.
- `tests/integration/e2e/suites/09_settings/test_settings.py:478` (S-09-13) —
  `L.EXTERNALLY_MANAGED` -> `L.LOCAL_ACCOUNT_NO_MFA`. The scenario's name and
  `@pytest.mark.scenario("S-09-13")` marker are unchanged; renaming a scenario
  is a feature-file decision, not a fixer's. Its title ("...for an
  externally-managed account") is now inaccurate — flagged, not touched.
- `tests/integration/e2e/suites/11_admin/test_admin.py:402` — the needle
  `EXTERNALLY_MANAGED = "managed outside the application"` became
  `BREAK_GLASS_REFUSAL = "local break-glass account and cannot be reset here"`
  (2 uses, S-11-17 and S-11-18), and S-11-17's docstring quote of the 409 body
  was updated to the string it now returns.

## Not fixed here

`MfaStatusResponse` (`backend/app/models/schemas.py:80-98`) still carries only
a boolean `supported`, with no reason code or `auth_provider` echo. ISS-404
records this as a contributing factor, not the defect: no genuinely
external-IdP account type exists in this codebase today, so adding a reason
field would be building for a case that does not exist. If one is ever added,
that response needs enriching before this copy can be reused — the frontend
would otherwise be back to guessing from one boolean.
