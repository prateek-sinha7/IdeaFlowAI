# ISS-615

**BUG-ID:** BUG-20260829-140111-runs-id-steps-agent (deferred finding from FIX-412)

## The state after FIX-412

`test_back_to_latest_from_pinned_middle_version_reaches_true_latest` makes two
assertions. After [FIX-412](20260829-1703-FIX-412.md):

- `assert fetched_true_latest` — **passes.** Observed live on the 5-member
  fixture (root `b868a6b6-ed11-4ae9-a512-6df2b1c5ad4e`): clicking
  "Back to latest →" while pinned to v2 lands on
  `http://localhost:3000/runs/b868a6b6-.../versions/5/steps` and issues three
  `GET /api/runs/8ab0ca9e-03db-4a53-b040-67791a3da520` plus its `/gate-events`.
  That is exactly [ISS-611](20260829-1631-ISS-611.md)'s stated Expected.
- `assert not fetched_root_instead` — **fails**, and cannot pass.

## Why the second assertion is unsatisfiable

Exactly one request naming the root fires: a bare
`GET /api/runs/b868a6b6-ed11-4ae9-a512-6df2b1c5ad4e`. It is not the version
switch. Probed directly: performing a PLAIN older-pin change instead (picker
v2 -> v4, an interaction that was never part of this bug and worked before it)
emits the identical bare root request alongside the three v4 fetches. It is the
route-change side effect of the shell re-reading the run its path names —
`/runs/{rootId}/versions/{v}/{tab}` keeps the ROOT in the base segment by design
(`pinnedVersionFor`'s own doc comment, `frontend/src/app/[...view]/page.tsx:200-210`:
"the shell opens the run the path names and DashboardLayout fetches ITS family").

So "no request names the root" is a proxy for "the root's data is what got
rendered", and under this addressing contract the proxy is wrong: the root is
always fetched, and what is RENDERED is decided by the pin.

## Disposition

The test was deliberately left unedited — changing an assertion to match a fix is
the inversion this line guards against, and this is a verifier's call, not a
fixer's. Two options:

1. **Narrow the assertion** to what ISS-611 actually claims — assert the final
   URL ends `/versions/5/steps`, or that the rendered content is v5's, rather
   than that no root request exists.
2. **Change the addressing scheme** so a pin re-bases the URL onto the pinned
   member's own run id. That is a design decision touching FIX-328/ISS-230's
   whole contract and is out of scope for a bug fix.

Option 1 is almost certainly right; it needs an explicit ruling before anyone
touches the file.
