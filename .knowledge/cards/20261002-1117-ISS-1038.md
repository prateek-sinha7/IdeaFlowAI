# ISS-1038

## Description

INFERRED sibling of [ISS-948](20261002-0107-ISS-948.md). The allow-list line that fixes ISS-948 must carry a reason the route is safe to expose, and "serves the deliverable only" is true of what the route returns. Checking the rest of that claim against `view_shared_run` shows the response is narrow in what it contains and unprotected in how a browser may treat it.

`backend/app/main.py:664-665` says: "Content-Security-Policy: sandbox so the shared prototype cannot run arbitrary JS in the viewer's main browsing context." The dict that follows (`:666-672`) holds `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy` and `Cache-Control`, and no `Content-Security-Policy`. That string appears nowhere else in `backend/app` or `frontend/next.config.ts`, and the middleware stack (`main.py:474-520`: CORS, request id, slow-request log) adds none.

What the route returns for a text deliverable is HTML written by an agent (`return HTMLResponse(content=output, headers=share_headers)`, `main.py:691`), which for a prototype is interactive and runs script. The link the UI hands out is `${window.location.origin}${result.share_url}` (`frontend/src/components/preview/RunHeader.tsx:377`), the application's own origin, and the access token is stored in `localStorage` under `auth_token` (`frontend/src/lib/api.ts:21`, read by `getToken` at `:45-51`), which any script on that origin can read. Production nginx adds a server-level CSP (`infra/scripts/reconcile-host-config.sh:244`), but it is an application-wide policy, not a sandbox: it allows `script-src 'self' 'unsafe-inline' 'unsafe-eval'` and has no `sandbox` directive. Local dev has no nginx and so no CSP at all.

## Why the root cause implies it

ISS-948 exists because this route was never put through the contract that demands a stated reason it is safe to expose unauthenticated. The same missing review left a safety property that the code states in a comment and does not implement. The allow-list line the fix adds is an attestation of safety; this card is what that attestation does not cover.

## Evidence

CONFIRMED, read: `backend/app/main.py:664-672` (comment and header dict), `:691` (HTML returned as-is), `:474-520` (middleware); a case-insensitive search for `content-security-policy` over `backend/app`, `frontend/next.config.ts` and `infra` finds the comment at `main.py:664` and the nginx server-level policy at `reconcile-host-config.sh:244` only; `RunHeader.tsx:377`; `api.ts:21`, `:45-51`.

INFERRED, not driven: exploitability. It needs a deliverable carrying hostile script (agent output is shaped by the prompt and by uploaded documents) and a viewer who is signed in to the app in the same browser; the production `connect-src 'self'` limits exfiltration by `fetch` but not by navigation. Whether the link is reachable in production at all depends on [ISS-1037](20261002-1117-ISS-1037.md). What would settle it: a test that calls `view_shared_run` with patched dependencies (the pattern at `backend/tests/unit/app/test_binary_deliverable.py:132-139`) and asserts the response carries a `Content-Security-Policy` containing `sandbox`; today it has none.

## Expected vs actual

- Expected (the code comment's own intent): the shared response isolates its content from the application origin, for example `Content-Security-Policy: sandbox allow-scripts`. Scripts still run, in an opaque origin that cannot read the app's `localStorage` or call its API with the viewer's credentials. `allow-same-origin` must not be combined with `allow-scripts`, which cancels the sandbox.
- Actual: no `Content-Security-Policy` on the response.

## Fix direction

Add the header to `share_headers` at `main.py:666`. It is route-owned, so it holds in dev (no nginx) and in production, and it does not depend on any nginx location (an `add_header` in an nginx `/s/` location would discard the server-level headers, see [ISS-1037](20261002-1117-ISS-1037.md)). Use `sandbox allow-scripts` if shared prototypes must stay interactive, plain `sandbox` where script is not needed. Whether shared prototypes must run script is the owner's call; the comment's stated intent ("cannot run arbitrary JS in the viewer's main browsing context") is met by `allow-scripts` without `allow-same-origin`.

## Test notes

Offline unit test in the style of `test_share_of_a_pdf_deliverable_serves_the_file_bytes` (`test_binary_deliverable.py:132`): patch `app.api.runs.get_shared_run_by_token` to return a `SimpleNamespace` run with `deliverable_mimetype="text/html"`, call `main.view_shared_run("tok")` through `asyncio.run`, and assert `"sandbox"` appears in `resp.headers["Content-Security-Policy"]` and that the value never contains both `allow-scripts` and `allow-same-origin`. Run that one file from `backend/`.

## Fix (2026-10-07, QA-KB-089)

Fixed by [FIX-745](20261007-2030-FIX-745.md). `share_headers` (`main.py:667-668`) sends
`Content-Security-Policy: sandbox allow-scripts`, with no `allow-same-origin`. That is the token set of the in-app
generic renderer (`PreviewPanel.tsx:278`), so shared prototypes stay interactive. It applies to every branch. Real
Chrome 151 renders a PDF identically with and without the header, and HTML under it sees origin `null`, where
`localStorage` throws. Both results are in `evidence/qa-kb-089/`. The same exposure persists in-app and is filed as
[ISS-1067](20261007-2030-ISS-1067.md).
