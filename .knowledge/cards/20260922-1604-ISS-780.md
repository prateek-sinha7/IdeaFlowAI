# ISS-780

## Title

[ISS-657](20260917-1250-ISS-657.md) already named "two async requests, last-one-in wins" for
`handleSwitchToLiveRun` and was closed by a same-instance guard
(`trackedRunIdRef.current !== runId`, `page.tsx:2765`). [ISS-775](20260922-1330-ISS-775.md)'s
analysis of QA-SG-004 shows that guard is `useRef`-scoped to ONE mount of `page.tsx`, and a
live-to-live switch's own `router.push` remounts `page.tsx` (confirmed live,
`page.tsx:3374-3378`) — so a rapid double-click on two DIFFERENT live runs, where the remount lands
between the two clicks, gives the second click a completely fresh ref that has never heard of the
first click, and vice versa. ISS-657's fix does not, and structurally cannot, cover this case.

## Why ISS-775's root cause implies this

- `page.tsx:2765` — `if (trackedRunIdRef.current !== runId) return;` — reads the CURRENT
  component instance's own ref. This correctly drops a stale response when a second click lands
  on the SAME page instance (ISS-657's original case: dropdown click A, click B before A's fetch
  resolves, both handled by one still-mounted `page.tsx`).
- `page.tsx:3374-3378` (existing code comment, read directly) — "T9's router.push remounts THIS
  page component ... a fresh render-instance id appears right after router.push, before
  trackedRunIdRef.current even changes." A remount does not merely reset the ref's VALUE, it
  replaces the ref OBJECT itself (`useRef(null)` re-runs on the new instance) — the two clicks'
  closures, if the remount lands between them, are no longer even reading the same variable.
- Consequently: click A (live run A -> live run B) starts `handleSwitchToLiveRun("B")` on instance
  1, then `router.push` remounts to instance 2. If the user's retry/second click (a live run B ->
  live run C switch, e.g. after A's own click LOOKED like it failed — exactly the retry behaviour
  [ISS-647](20260917-1100-ISS-647.md)'s register report already named as the natural user
  reaction) fires from instance 2 before instance 1's superseded `getRunEvents("B")` resolves,
  instance 1's late write is graded against instance 1's OWN ref (still `"B"`, never told about
  "C") — the guard reports "not stale" and lets a B-replay through even though the user has since
  moved on to C. Instance 1's write is only actually voided by `mountedRef` becoming false
  (`useRunStateStore.ts:335`), a SEPARATE, coarser mechanism than trackedRunIdRef, and (per
  [ISS-775](20260922-1330-ISS-775.md)/[ISS-778](20260922-1600-ISS-778.md)) only reliably blocks a
  write that arrives AFTER the unmount completes — a write that lands in the narrow window before
  cleanup runs is not guaranteed to lose the race.

## Expected (once reproduced)

Two rapid clicks on two different live runs, in any order, leave the UI on the LAST one the user
actually clicked — the same guarantee ISS-657's own "Expected" section already states for the
single-instance case.

## Actual (inferred, not yet observed independently)

Because the guard cannot see across a remount, the outcome of two rapid live-to-live clicks is
determined by unmount/fetch timing rather than click order — the UI can settle on neither run
cleanly, or on the first-clicked run instead of the last, depending on which instance's write
lands after the other's `mountedRef` flips.

## What would confirm this

1. Start 3 concurrent live runs (A, B, C), viewing A.
2. Click B's notification/dropdown entry, then — without waiting for navigation to settle —
   immediately click C's entry (re-opening the panel/dropdown if it closed).
3. Throttle the network so B's `getRunEvents` resolves noticeably after C's, and check which run
   the app actually lands on and keeps showing after both settle — same method
   [ISS-657](20260917-1250-ISS-657.md) itself proposed, repeated here across a real remount instead
   of a single mounted instance.
