# ISS-089

## Title

A cancel is purely in-process, so a Stop that arrives when no driver is live is lost — and the next boot auto-resumes the run the owner just tried to stop. After FIX-227, POST /cancel on a run with no in-process driver answers honestly (accepted: false, status: "not_running") instead of lying — but the run is still running/generating in workflow_runs, still inside restore_non_terminal_runs' NON_TERMINAL set (engine.py:5710-5713), and the next startup adopts it and drives it to completion at the owner's expense. This is exactly the second half of what happened to d5dbc9f2: the process was killed at 03:03:36 and the replacement backend emitted pipeline_start two seconds later and billed 7.5M further tokens. The window is real in normal operation, not only after a kill -9: SHUTDOWN_STOP_RUNS=False means every deploy leaves its in-flight runs non-terminal by design, so a Stop pressed during a rolling restart lands on nothing. Fix shape (product decision, not technical): make the cancel DURABLE — a cancel_requested marker (an additive run_events row or a workflow_runs column) written by the endpoint regardless of liveness, and checked by restore_non_terminal_runs before it adopts a run, so the boot classifier fails the run terminal instead of resuming it. Note the ordering constraint: the check must run before _stamp_resume_marker, and the resulting status must be cancelled (terminal, outside NON_TERMINAL) rather than failed.

## Source / evidence

Identified while fixing ISS-084 (quick-260812-7sk) and recorded rather than silently left: FIX-227 makes every in-process cancel real and terminal, and makes the no-driver case honest, but it does not and cannot make an in-memory asyncio.Event survive the process that holds it. The analysis carried it as Open Question 1 (ISS-084-ANALYSIS.md §11).
