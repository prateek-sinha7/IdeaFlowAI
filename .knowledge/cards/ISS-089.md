# ISS-089

## Title

A cancel is purely in-process, so a Stop that arrives when no driver is live is lost — and the next boot auto-resumes the run the owner just tried to stop. After FIX-227, POST /cancel on a run with no in-process driver answers honestly (accepted: false, status: "not_running") instead of lying — but the run is still running/generating in workflow_runs, still inside restore_non_terminal_runs' NON_TERMINAL set (engine.py:5710-5713), and the next startup adopts it and drives it to completion at the owner's expense. This is exactly the second half of what happened to d5dbc9f2: the process was killed at 03:03:36 and the replacement backend emitted pipeline_start two seconds later and billed 7.5M further tokens. The window is real in normal operation, not only after a kill -9: SHUTDOWN_STOP_RUNS=False means every deploy leaves its in-flight runs non-terminal by design, so a Stop pressed during a rolling restart lands on nothing. Fix shape (product decision, not technical): make the cancel DURABLE — a cancel_requested marker (an additive run_events row or a workflow_runs column) written by the endpoint regardless of liveness, and checked by restore_non_terminal_runs before it adopts a run, so the boot classifier fails the run terminal instead of resuming it. Note the ordering constraint: the check must run before _stamp_resume_marker, and the resulting status must be cancelled (terminal, outside NON_TERMINAL) rather than failed.

## Source / evidence

Identified while fixing ISS-084 (quick-260812-7sk) and recorded rather than silently left: FIX-227 makes every in-process cancel real and terminal, and makes the no-driver case honest, but it does not and cannot make an in-memory asyncio.Event survive the process that holds it. The analysis carried it as Open Question 1 (ISS-084-ANALYSIS.md §11). RESOLVED — and the row's own proposed fix was the worse of the two. Two corrections to the row as filed. (1) The NON_TERMINAL citation engine.py:5710-5713 was wrong, as were the three other recorded values (:5263, :5838-5841, :5899-5902); at 2df5324b the tuple was an inline literal at engine.py:5921 — a fifth value in one week. It is now ONE module constant, NON_TERMINAL_RUN_STATUSES, imported by the endpoint and by scripts/cutover_legacy_runs.py (which held a second copy), pinned by an AST source guard that catches a copy under any name. (2) Option B — the cancel_requested marker checked inside restore_non_terminal_runs — was rejected. It needs a migration or a new event type; it edits the resume tier's most delicate three-branch classifier; it misses branch (a) (waiting_for_user spawns _rearm_gate_run without ever calling _stamp_resume_marker, so a marker checked before the stamp misses every gate-parked run — the row's own ordering constraint is true but insufficient); and it leaves the row lying running to history, analytics, /resume eligibility and the UI until the next boot, possibly forever. Shipped instead: write the terminal status at cancel time. One function. cancel_run's not-live branch reads the row; TERMINAL ⇒ the pre-existing not_running ack, byte-identical, no write; NON-TERMINAL ⇒ a durable pipeline_cancelled row via the collision-safe ScopedStore.append_event_at_or_after (best-effort audit/replay) + status="cancelled" + completed_at via _persist_resume_status (authoritative — a failure answers 500 cancel_not_persisted, it does NOT inherit _reconcile_terminal_status's degrade) + accepted:true, cancelled:true, status:"cancelled". No migration, no new table/column/event type, and no change to restore_non_terminal_runs at all — cancelled is already outside the non-terminal set and POST /resume already accepts it, so the boot scan consults the decision through the filter it already has and the run moves from AUTOMATIC to EXPLICIT, owner-authenticated resume. Proof is the boot scan's task count, not prose: at 2df5324b the same test observed ExecutionEngine.restore_non_terminal_runs.<locals>._admitted_resume spawned for a run whose Stop had just answered not_running. Cost framing corrected: the register's "5-21M tokens" understates the tokens and overstates the drama — measured ceiling on this corpus is 37.3M tokens / $7.07, the d5dbc9f2 incident cost $3.58 with ~$1.61 (45%) billed after the cancel, and all 14 metered runs together total $17.75. It is a correctness-and-trust defect first, a cost defect second on a Haiku workload — about an order of magnitude worse on an Opus-tier model, which is what the fix insures against. SCOPE — single-process only (→ ISS-134). _is_run_live is process-local; the deployment is single-process today (exec uvicorn, no --workers, no replicas) so "not live here" == "not live anywhere". Under the locked ECS Fargate to-be a Stop landing on instance B would mark a row cancelled while instance A kept billing. Do not later assume this fix is multi-instance-safe.
