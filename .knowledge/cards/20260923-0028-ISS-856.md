## Found while reconciling QA-PS-048's request count (see ISS-853's re-analysis)

Not on `AgentThinkingTab` — a different call chain with the identical root
pattern this whole re-analysis pass is about: a caller fetches the full run
record, hands off to another function, and that function refetches the same
run instead of trusting the data it was just given.

## What is wrong

`frontend/src/components/history/WorkflowHistory.tsx:388-405`
(`handleSelectVersion`, fired when a user picks a different revision from
the family/version picker):

```tsx
const handleSelectVersion = useCallback(async (memberId: string) => {
  ...
  const full = await getWorkflow(token, memberId);
  if (onOpenRun) {
    onOpenRun(full);
  } else {
    ...
```

`onOpenRun` is wired, in both `WorkflowHistory` mounts inside
`DashboardLayout.tsx:2925` and `:2985`:

```tsx
onOpenRun={(run) => { onSelectWorkflowRun?.(run); setMainView("execution"); router.push(routes.runDetail(run.id)); }}
```

`onSelectWorkflowRun` is bound at `frontend/src/app/[...view]/page.tsx:4434`
to `handleSelectWorkflowRun` — the same function [ISS-853](20260922-2359-ISS-853.md)
already names for the page-open fetch:

```tsx
// page.tsx:2999
const fullRun = await getWorkflow(currentToken, run.id);
```

So one version click does: `getWorkflow(token, memberId)` inside
`handleSelectVersion` (awaited to completion — `onOpenRun(full)` only runs
after it resolves, so this is NOT concurrent with what follows and
`singleFlightGet` has nothing to merge), THEN `handleSelectWorkflowRun`
receives `full` as its `run` argument and reads only `run.id` from it
(confirmed by the comment already at `page.tsx:2965-2967`: "the id is the
row the user clicked — already trusted enough... and `getWorkflow(token,
run.id)` can only give the same one back") before firing a SECOND
`getWorkflow(currentToken, run.id)` for data it was handed a moment earlier.

## Why this is a sibling, not a duplicate

Same "refetch instead of reuse" root cause as ISS-853, but neither the
component nor the call site ISS-853 is scoped to — this is the
version-switch path, not the Steps-tab-open path, and the two GETs here are
provably SEQUENTIAL (the second fires from inside the first's own resolved
callback), so no in-flight guard could ever have caught it. This is the
strongest CONFIRMED candidate for part of the ORIGINAL bug report's
"fetched 3x" figure (FIX-637 could not reproduce a 3x pattern on a plain tab
switch): a version click plus its page-level open accounts for 2 of those
fetches by itself, through a different mechanism than StrictMode.

## What would settle it

Open a run with 2+ revisions, DevTools Network reset, click a different
version in the History panel's family picker. Expect one `GET
/api/runs/{memberId}` if fixed. CONFIRMED by the code chain above (every
file:line read directly this pass); the live count has not been measured in
this analysis session (no browser access from this role).

## Suggested fix

`handleSelectWorkflowRun` (page.tsx) already accepts a `WorkflowRun` as its
`run` argument. Give it a way to accept an ALREADY-FULL record (e.g. an
`isAlreadyFull` flag on the call from `onOpenRun`, or skip the `:2999` fetch
whenever the passed-in `run` already carries the fields a "thin" list row
would not) so a caller that already awaited `getWorkflow` — `handleSelectVersion`
is the one found here — is not made to pay for it twice. The fix belongs in
`handleSelectWorkflowRun` itself, not in each caller, so every future caller
that already holds a full record benefits without adding its own guard.
