# ISS-755

## Register entry

Sibling of [ISS-753](20260922-1413-ISS-753.md) (root card, full mechanism there), filed from the
same investigation. No QA-PS row names this specific manifestation; not observed in either sweep
supplied by the dispatch (neither sweep's family had an active clarify round).

## Root cause — CONFIRMED mechanism, INFERRED manifestation frequency

- `PreviewPanel.tsx:1784` computes the `clarifications` prop it forwards to `AgentThinkingTab` as
  `clarifications ?? pipelineState?.clarifications`. The `pipelineState` used in THIS specific
  fallback is `PreviewPanel`'s own **raw top-level** prop — contrast `PreviewPanel.tsx:1781`,
  two lines above, which correctly passes `pipelineState={effPipelineState}` (the version-aware
  value) for the main `pipelineState` prop itself. The `clarifications` line does not reuse that
  already-correct `effPipelineState`.
- `PreviewPanel.tsx:1745` (the `FilesTab` call) repeats the identical shape:
  `clarifications={clarifications ?? pipelineState?.clarifications}`.
- The explicit `clarifications` prop is `PreviewPanel`'s own top-level prop, documented at
  `PreviewPanel.tsx:440-441` as *"the reopen override"* — set from page-level reopen state, not
  from `viewingVersion`, and never cleared or re-derived when the version dropdown changes
  `viewingVersion`. Because `??` prefers it whenever it is non-empty, a non-empty reopen-override
  value permanently shadows the fallback for the rest of that page mount, regardless of which
  version is subsequently selected.
- Inside `AgentThinkingTab.tsx:247`: `const resolvedClarifications = clarifications ??
  pipelineState?.clarifications;` — here `pipelineState` IS `effPipelineState` by the time it
  arrives (per `PreviewPanel.tsx:1781`), so if the explicit `clarifications` prop were absent,
  this fallback half would actually be correct and version-aware. The defect is specifically the
  explicit prop's un-derived precedence, not this inner fallback.
- `resolvedClarifications` feeds `StepsOverviewSpine`'s `clarifications` prop
  (`AgentThinkingTab.tsx:446`), which renders the actual clarify-round UI inside the Steps
  overview (`AgentThinkingTab.tsx:443-467` mounts `StepsOverviewSpine` with `StartingPointCard`
  as its `topSlot`).

## Confidence: INFERRED (manifestation), CONFIRMED (code shape)

The code shape matches [ISS-753](20260922-1413-ISS-753.md)'s pattern exactly: a raw top-level
override prop, never merged with `viewingVersion`. Whether this is currently VISIBLE to a user
depends on the top-level `clarifications` prop being non-empty at the time — which, per its own
"reopen override" comment, only happens in specific reopen/switch scenarios. Neither sweep
supplied by the dispatch exercised a clarify round, so this pass has no direct observation either
way. What would settle it: reopen (or view) a run whose own clarify history is non-empty, then
switch versions via the dropdown, and check whether the Steps clarify-rounds section still shows
the reopened run's rounds instead of the newly-selected version's own (or none, if that version
had no clarify round).

## Fix direction (not applied — issue only)

Same shared root as [ISS-753](20260922-1413-ISS-753.md): once a version is pinned
(`viewingVersion != null`), prefer `effPipelineState?.clarifications` over the raw `clarifications`
override at both `PreviewPanel.tsx:1745` and `:1784` — or, more uniformly, extend `VersionView`
to carry its own `clarifications` snapshot the same way [ISS-753](20260922-1413-ISS-753.md)
proposes for `runInput`, so every pinned-version-aware prop in this component follows the same
one derivation pattern.

## Re-analysis (2026-10-02, QA-KB-066)

Re-opened as bug QA-KB-066 (`LEDGER.md`, `BUGS.md#qa-kb-066`). The code shape filed above is **CONFIRMED and unchanged**: both
consumers read a raw shell value where a version-aware one belongs. What moved is the line numbers, the described mechanism (one
operand of the `??` is dead in production), and the scope (the Files tab shares the expression, and nothing anywhere loads a pinned
version's own rounds). Anchors are the working tree on 2026-10-02 (HEAD `024c03ef8`); `PreviewPanel.tsx`, `DashboardLayout.tsx` and
`useWorkflow.ts` carry uncommitted edits from other work (none touches clarifications), so HEAD numbers sit a few lines off (HEAD:
`effPipelineState` `:1065`, `effRunInput` `:1069`, FilesTab `:1894`, Steps `:1938`). This card stays `open`: nothing here is a fix.

3. **Where the raw rounds come from.** Not a reopen override (see 2): they are the rounds the shell run answered live in this page

### Fix placement (what a fixer should do)

One derived value in the `eff*` block, read by both JSX sites: the FIX-603 pattern (`effRunInput` closed
[ISS-753](20260922-1413-ISS-753.md) and [ISS-754](20260922-1414-ISS-754.md) with one const).

```ts
const effClarifications = viewingVersion
  ? viewingVersion.clarifications          // new optional field on VersionView; undefined = none
  : (clarifications ?? pipelineState?.clarifications);
```

then `clarifications={effClarifications}` at `:1922` and `:1966`. Key it on the PIN, not on the field: the nullish-chain form is the
`naive` variant and does not fix the bug. BUGS.md's two-word sketch also passes today, but only because the explicit override is
never wired; once [ISS-1008](20261002-0523-ISS-1008.md) wires it, `clarifications ?? effPipelineState?.clarifications` lets the shell's override shadow the
pinned version again. Nothing changes in `AgentThinkingTab`, `FilesTab`, `StepsOverviewSpine` or `ClarificationsCard` (all also
mounted by `WorkflowHistory`, which passes its own fetched rounds). Frontend-only; SC-001 and the registry and import-linter
invariants are not involved. This satisfies FIX-516's locked constraint (every pipeline prop a pinned-version-aware surface consumes
must be the `eff*` value).

Caveat (INFERRED): if a pin ever resolves to the shell's own run (the `/versions/{n}` effect can set `viewingVersion` for it,
`:1005-1035`) a pin-keyed value hides that run's live rounds. Not on the common path: the menu writes no pin for the shell run
(`:915`).

## Resolution — FIX-730 (2026-10-07)

Resolved by [FIX-730](20261007-1900-FIX-730.md), for register entry QA-KB-066. The re-analysis above stands, and the fix
is its "Fix placement" design:

- `effClarifications` is keyed on the pin (`PreviewPanel.tsx:1243`).
- `VersionView.clarifications` is new (`:598-600`).
- Both consumers read the one value: FilesTab `:1993` and AgentThinkingTab `:2037`.

The un-pinned branch also takes [ISS-1008](20261002-0523-ISS-1008.md)'s loaded rounds, so the expression is wider than
the three-line sketch. It is still pin-keyed, and the `naive` nullish chain was not used.

Tests: in `PreviewPanel.clarifyPin.test.tsx`, both ISS-755 cases (Steps, Files) now fail with "Expect test to fail",
which is the `it.fails` pass signal. The markers are left for the 6-verifier. The FIX-601..604 guards are unchanged:
pinSurvival, refSurfaces, versionRunInput and RunHeader (`evidence/qa-kb-066/fix-01`, `fix-03`).
