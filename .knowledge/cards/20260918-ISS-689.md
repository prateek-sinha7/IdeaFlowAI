## The gap

Two branches fixed the same defect independently and the merge kept both. The
verdict is now decided by one of them while the other's explanation sits above
it, dead and mislabelled.

`f23625911` (this branch) and [FIX-484](20260902-1600-FIX-484.md) both attacked
`_reconcile_terminal_status`'s unscoped degraded flag. Merge `4ebd98e8f` took
both.

## What is dead

`run_commands.py:815-819`:

```python
_latest_complete = max(completes, key=lambda e: e.seq) if completes else None
degraded = bool(
    _latest_complete is not None
    and isinstance(_latest_complete.payload_json, dict)
    and _latest_complete.payload_json.get("status") == "degraded"
)
```

`degraded` is assigned and never read. Verified by walking every `degraded`
occurrence in `run_commands.py` between `:819` and `:960`: after the assignment
the only names that appear are `degraded_complete_seqs`, `degraded_current`,
`degraded_agents`, `degraded_reason` and string literals `"degraded"`. The bare
local is never one of them.

## What actually decides the verdict

FIX-484's reattempt-boundary scan, at `:888-901`:

```python
last_reattempt_seq = max(reattempt_seqs) if reattempt_seqs else 0
current_attempt_completes = [e for e in completes if e.seq >= last_reattempt_seq]
degraded_current = any(... == "degraded" for e in current_attempt_completes)
...
if degraded_current:
    new_status = "degraded"
```

So the surviving semantics are "any degraded completion at or after the last
reattempt boundary" (ISS-436 / ISS-437 scoping), NOT "the latest completion by
seq".

## Why this bites

An 11-line comment block above the dead local explains the last-by-seq mechanism
in detail — the mechanism that no longer runs — and labels itself **FIX-247**.
[FIX-247](20260813-0205-FIX-247.md) is a real card, titled *"Stop at the clarify
gate cancelled the run, but the screen never repainted"*. It is about the live
terminal handler clearing legacy React state. It has nothing to do with terminal
status reconciliation.

So anyone debugging a wrong `degraded` verdict reads a confident explanation of
dead code, follows its card reference, and lands in the frontend.

## What to do

Either delete the dead local together with its comment, or keep it and delete
FIX-484's duplicate. Both are defensible; having both is not. The two must not
each claim to own the verdict.

### Root cause (CONFIRMED)

The degraded and failed verdicts were re-scoped twice, in two different hunks of one function, and a textual merge kept half of each. Git raised no conflict because the hunks are disjoint.

1. [FIX-484](20260902-1600-FIX-484.md) (`18a733e68`, 2026-09-02) replaced the status ladder's whole-tail flags with `degraded_current` / `failed_current`, but left the old whole-tail assignments behind and wrote the comment at :942-944 saying to keep them "for backwards-compat". AST scan of that commit's function: `failed` (line 782) and `degraded` (784) are Store-only, so `failed` has been dead since FIX-484. The `failed = any(...)` line itself dates from `70fc41e87e` (2026-07-19).
2. `f23625911` (2026-09-11), an independent line (`git merge-base --is-ancestor 18a733e68 f23625911` is false), re-scoped the same flag a different way: `_latest_complete` plus `degraded = bool(...)` (last completion by seq), with the 10-line comment labelled FIX-247, and reworded the docstring to "the LATEST `pipeline_complete`" (blame, :804). In that version the ladder read both flags (`elif degraded:` line 845, `elif completes and not failed:` line 847; AST: both Load), so there they were live.
3. Merge `4ebd98e8f` (2026-09-16) combined them. The ladder is FIX-484's, the definition hunk is f23625911's, so `degraded` lost its only reader. `_latest_complete` kept a reader because f23625911 also uses it in a third hunk, the degraded error text.

At HEAD (ruff F841 reports exactly the two dead locals and nothing else in the file):

| line | code | reads |
|---|---|---|
| 838 | `failed = any(e.type == "pipeline_failed" for e in events)` | none (F841) |
| 840-849 | `# FIX-247: the degraded verdict must track only the LATEST pipeline_complete ...` | 10 lines, not 11 |
| 850 | `_latest_complete = max(completes, key=lambda e: e.seq) if completes else None` | :852-854 (feeds the dead local) and **:986-987** (live) |
| 851-855 | `degraded = bool(_latest_complete is not None and ...)` | none (F841) |
| 945-950 | `if degraded_current:` / `elif current_attempt_completes and not failed_current:` / `else:` | the live ladder |
| 984-989 | `_payload = (_latest_complete.payload_json if isinstance(_latest_complete.payload_json, dict) else {})` | derives the degraded `WorkflowRun.error` |

The dead mechanism's explanation is wrong as well as dead. The comment says "A run completes at most once per attempt, so last-by-seq IS the latest attempt's verdict". The first half holds (one emitter: `backend/agents/execution_engine/engine.py:8178-8181`, an unconditional `yield` guarded against cancelled/failed/diverted), but an attempt that FAILS emits no `pipeline_complete`, so last-by-seq then returns a PRIOR attempt's verdict. That is [ISS-436](20260828-2253-ISS-436.md), and it is why FIX-484's boundary scan is the right mechanism (tail T5 in [ISS-886](20261001-2114-ISS-886.md)).
