# FIX-695

## What was wrong

Bug report QA-KB-010 (and its closed duplicate QA-PS-010). The root cause and blast radius are the analysis on
[ISS-189](20260828-1457-ISS-189.md); they are not re-derived here.

The deck wizard had a hard gate with no reachable affordance. `dsRequired`
(`LaunchWizard.tsx:698`, `isDeck && selectedDeckTemplate?.design_system?.requires === true`) gates `canContinue`
(`:889`) and shows the "Pick a design system" pill (now `:1375`). The only control that sets `selectedDsId` is
`DesignSystemPicker` inside `dsSlot`, and `WizardStepper` mounts `dsSlot` only when the active step id is
`"design-system"` (`WizardStepper.tsx:187`). `LaunchWizard.tsx:1298` passed
`steps={isDeck ? ["template"] : ["template", "design-system", "discovery"]}` ([FIX-065](20260721-1133-FIX-065.md),
widened from `mode === "ppt"` to `isDeck` by `70665bbcb`), so no deck ever had that step. The 3 of 55 deck templates
that declare `design_system.requires: true` (`ib-pitch-book`, `weekly-update`, `simple-deck`) could not be launched
in `ppt` or `ppt_v2`.

## What changed, and why there

`frontend/src/components/workflow/LaunchWizard.tsx:1298-1300`, the single expression that decides which steps exist
(anchored on its unique string, not a line number):

```
steps={isDeck ? (dsRequired ? ["template", "design-system"] : ["template"]) : ["template", "design-system", "discovery"]}
```

plus a two-line `// ISS-189:` comment above it, matching the file's existing comments between JSX props.

Why there: `WizardStepper` has exactly one non-test consumer (`LaunchWizard.tsx:1295`, grep), so every deck route
reaches this prop: `/create/ppt`, `/create/ppt_v2`, `/workflow/create?mode=ppt|ppt_v2` and `/workflows/{id}/run`
for a saved ppt/ppt_v2 workflow. `dsRequired` already drives the gate, the pill, `dsVisible`/`dsSlot` and the
draft's `designSystemId`, so keying the step list on it makes the gate and its picker agree by construction.
Non-DS decks keep FIX-065's one Template step. `WizardStepper.tsx:193` (`steps.length > 1`) shows Back/Next only in the
two-step case. `WizardStepper.tsx`, `buildLaunchDraft` and the Save/override regions of `LaunchWizard.tsx`
(QA-KB-011) are untouched.

Not done, per the analysis: extending [FIX-103](20260723-FIX-103.md)'s auto-select to decks (it runs at mount,
before any template is chosen, and would silently pick a DS nobody chose), hiding the 3 templates, and relaxing the
gate.

Left behind and not deleted: the `<StepNote>` "This deck template doesn't require a design system" branch of `dsSlot`
(`:1324`). It cannot render for decks any more, because the deck DS step now exists only when `dsRequired`.

## Still open

- [ISS-909](20261001-2216-ISS-909.md) (INFERRED sibling) is not fixed by this edit and stays open. Its deck exposure
  is now live: if `GET /api/prototype/design-systems` fails or returns `[]`, the new deck Design System step shows
  the endless `animate-pulse` skeleton (`:1313-1314`) while the pill and `canContinue` still ask for a DS.
- `LaunchWizard.test.tsx`'s `WizardStepper` stub still renders `ds-slot` whatever `steps` says (a deliberate
  test-writer choice, so the older tests that click `pick-ds` keep their shape). The ISS-189 tests prove the `steps`
  prop. That a user can actually reach the picker was proven with the real stepper in a scratch probe (evidence
  07/08), not by a repo test.
