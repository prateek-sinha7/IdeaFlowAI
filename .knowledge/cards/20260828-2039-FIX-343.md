## What was wrong

`BUG-20260828-104200-workflows-nonexistent-r2`: "Run once" on a composer showing
**0 agents** launched a real 9-agent pipeline against Bedrock. Validated 3/3;
`GET /api/runs/<id>` returned `agent_count: 9`, `type: "custom"` for a canvas whose
header read "0 agents, 0 review gates".

## Root cause

`backend/app/api/run_commands.py:2695` (`launch_run`, the sole `POST /api/runs`
handler):

```python
agent_ids = body.agent_ids
if agent_ids:
    ...  # allow-list the given ids
else:
    agents = get_pipeline_agents(base_pipeline_type)   # :2726
```

`if agent_ids:` is False for `[]` exactly as it is for `None`, so an explicitly
**empty** roster was indistinguishable from "no roster sent, use this type's
default membership". For `base_pipeline_type == "custom"` the `else` resolved
`custom/workflow.yaml`'s own nine steps (`agents/registry.py:108-115`,
`PIPELINE_AGENTS["custom"] = list_agent_ids("custom")`) — Market Research,
Strategy Analysis, Roadmap Planning, Security Audit, Test Strategy, Performance
Optimization, Documentation, Executive Reporting, Task List Planner — and minted
+ drove a run the caller never composed.

The fallback is correct for a genuinely built-in pipeline, whose roster is
registry/manifest-fixed. It has no legitimate meaning for `custom`, whose roster
IS whatever the client selected.

## What changed and why there

One `elif` in `launch_run`, between the allow-list branch and the registry
fallback (`backend/app/api/run_commands.py:2725`): when
`base_pipeline_type == "custom"` and `agent_ids` is falsy, reject with
`422 no_agents_selected` before the mint.

The guard sits at the **backend** seam rather than in the composer because that
is the one point every reachable trigger routes through, and it covers `None`
(what the browser actually sends — `frontend/src/hooks/useWorkflow.ts:88-90`
omits `agent_ids` entirely when the array is empty) and `[]` (what a direct API
caller sends) with one branch:

1. the reported dead-link `/workflows/<bad-id>/canvas` composer — [ISS-234](20260828-1628-ISS-234.md);
2. any other swallowed `getWorkflowDetail` failure on a REAL workflow, since the
   catch at `frontend/src/app/[...view]/page.tsx:494-496` is unconditional, not
   404-specific — [ISS-334](20260828-2045-ISS-334.md);
3. a brand-new "Compose a custom workflow" canvas, which starts at
   `pipelineAgents = []` by design — [ISS-333](20260828-2044-ISS-333.md);
4. a legacy `USER_WORKFLOW_FLAT` row with a NULL `agents` column, which
   `run_commands.py:2569-2571` turns into `agent_ids = []`. (New saves cannot
   create one — `SaveUserWorkflowRequest.agent_ids` carries `Field(min_length=1)`,
   `backend/app/api/user_workflows.py:212`, prior fix WR-02.)

Not touched: the sibling **UI** asks in [ISS-333](20260828-2044-ISS-333.md)
(disable "Run once" / early-return in `ComposerPage.handleRunOnce`, the way
`IdeaInputPage.handleRun` already does) and [ISS-334](20260828-2045-ISS-334.md)
(distinguish a transient fetch failure from "no such workflow"). Those remain
open on their own cards — this fix removes the expensive consequence, not the
missing UI affordance.

`base_pipeline_type` is the alias-collapsed value, and `custom_revision` is a
distinct key ending in `_revision`, so revision launches — which legitimately
send no `agent_ids` — are unaffected. `app/api/run_commands.py` is the API layer,
not `backend/agents/execution_engine/`, so SC-001 / INV-1's no-workflow-name-branch
fence is untouched; the file already carries the same shape at
`run_commands.py:2727` (`base_pipeline_type == "ppt"`), and `agents/registry.py:414`
keys `allowed_custom_agent_ids` on `custom` the same way.
