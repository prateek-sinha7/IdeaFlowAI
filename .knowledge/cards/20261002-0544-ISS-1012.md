# ISS-1012

Found with, not caused by, [ISS-895](20261001-2126-ISS-895.md) (QA-KB-069). Its root cause does not imply this defect. It surfaced while measuring [ISS-1011](20261002-0544-ISS-1011.md), the `getRunSandboxRefs` mock hole in the same two files, and it is filed so the red that remains after ISS-1011 is fixed has an owner. Confidence: **CONFIRMED** for the failure and its mechanism, **INFERRED** where marked.

## What is broken

Six tests fail on a label lookup that can never match the current `RunHeader`.

- `frontend/src/components/preview/PreviewPanel.versionChip.test.tsx` fails 5 of 5, observed 2026-10-02. The queries are `getByLabelText(/Version v3, choose version/)` (`:105`, `:174`), `getByLabelText(/Version v2, choose version/)` (`:170`), `getByLabelText(/Version v3/)` (`:119`, `:144`, `:180`) and `getByLabelText(/Version/)` (`:160`, `:163`). First error: `TestingLibraryElementError: Unable to find a label with the text of: /Version v3, choose version/`.
- `frontend/src/components/preview/PreviewPanel.test.tsx` fails 1 of 19: "mounts the run header and exactly ONE version affordance (INV-3) in the settled state". It asserts `getAllByLabelText(/choose version/)` has length 1 (`:152`) and `getByLabelText(/Version v2, choose version/)` (`:153`). Error: `Unable to find a label with the text of: /choose version/`.

## Mechanism (confirmed)

- The assertions were written in `8292e0a1a` (2026-07-11, "RunHeader — Version menu / Share / Download / status badge"), per `git blame` on `PreviewPanel.test.tsx:150-153` and `PreviewPanel.versionChip.test.tsx:105`.
- Commit `24f112706` (2026-09-09, "git-backed run versioning and run chaining", an ancestor of HEAD) removed the line `aria-label={`Version ${versionLabel}, choose version`}` from the `VersionMenu` trigger in `frontend/src/components/preview/RunHeader.tsx`. The same diff made the trigger conditional on `hasTags`.
- The trigger today (`RunHeader.tsx:99-110`) is a `<button>` with `aria-haspopup="listbox"` and `aria-expanded={open}` (`:101-102`), the visible text `{chipText}` (`:107`) and a `▾` glyph (`:109`). It has no `aria-label`. The listbox below it has `aria-label="Select a version"` (`:115`).
- Across all of `frontend/src`, the only non-test code containing "choose version" is `ArtifactVersionPicker.tsx:220`, which is a different control: the artifact picker in the Steps panel.
- The two test files were not updated after 2026-09-09. `PreviewPanel.versionChip.test.tsx` was last changed in `ec1ea70f5` (2026-08-19) and `PreviewPanel.test.tsx` only by the merge `4ebd98e8f` (2026-09-16), which left those lines as `8292e0a1a` wrote them.

## Independent of ISS-1011 (experiment)

Scratch copies outside the repo tree, factory plus `getRunSandboxRefs: async () => [],` (variant 1) or `getRunSandboxRefs: async () => ["v1","v2","v3"]` (variant 2). With the export supplied in either variant:

- `PreviewPanel.versionChip`: `Tests 5 failed (5)`, no `Errors`. The same 5 failures as the unpatched copy.
- `PreviewPanel.test`: `Tests 1 failed | 18 passed (19)`, no `Errors`. The same 1 failure.

Supplying tags does not help, because with tags the interactive `VersionMenu` mounts and its trigger still has no `aria-label`.

## Expected vs actual

- Expected: the version-selector tests drive the version affordance the app ships today.
- Actual: they look for an accessible name that no non-test code under `components/preview/` renders. Six tests are red. The label has been gone since `24f112706` (2026-09-09), so the tests have asserted a name that does not exist for that long; the date they first went red was not bisected.

## Not established (INFERRED)

- Whether the assertions behind the first failing line in each test still hold. The label lookup fails first, so the listbox option count, the read-only banner text and the keyboard-navigation expectations have never been exercised against the current `VersionMenu`. Expect more drift once the lookup is fixed.
- That the trigger's accessible name is currently its text content (about "v3 ▾" or "Viewing v1 ▾"). This is derived from the markup above, not measured with an accessibility tool.
- Whether a missing accessible name is acceptable. See the decision below.

## Decision for whoever fixes it

The tests encode the old accessibility contract: a labelled trigger with `aria-haspopup="listbox"`. The code dropped the label in a feature commit and the tests were not touched. Two readings:

1. **The tests are stale (default).** Rewrite the six lookups against the current trigger, for example `getByRole("button", { name: /v3/ })` or a query on `aria-haspopup="listbox"`. Supply tags through `getRunSandboxRefs` so the menu mounts at all (`RunHeader.tsx:426` mounts it only when `tags.length > 0`; otherwise a static `<span>` renders at `:420-424`). No production change.
2. **The label was dropped by accident.** Restore an `aria-label` on the trigger. That is a UX and accessibility contract change, which is a product decision, not a test fix.

Whoever picks this up should diff any non-test change separately and confirm its direction: the app must not be changed just to satisfy a stale test.
