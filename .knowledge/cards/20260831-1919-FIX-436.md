## What was wrong

Three cases, one cause:

```
test_agents_api_real_registry::…::test_prototype_endpoint_gate_values
  AssertionError: assert None == 'Human_Gate'
test_agents_api_real_registry::TestAgentLibraryEndpoint::test_library_returns_200_with_gate_and_real_prototype_ids
  AssertionError: assert None == 'Human_Gate'
test_phase6_frontend_consistency::…::test_gate_values_match_real_registry[prototype]
  prototype: gate values diverge between frontend and real registry
```

[FIX-323](20260828-1629-FIX-323.md) removed `gate: Human_Gate` from the
prototype `AGENT.md` files and set `gates: []` in the manifest — the user opts
in per run via `gate_agent_ids`. [FIX-415](20260831-0110-FIX-415.md) migrated
the gate-STREAMING tests to that path and explicitly left these three
([ISS-636](20260831-0115-ISS-636.md)).

The measured registry state confirms the production side is already correct:

```
get_pipeline_agents("prototype")
  prototype-specify None / prototype-plan None / prototype-analyze None
  prototype-build None / prototype-validate None
```

## Root cause — `frontend/src/components/workflow/AgentLibraryData.ts:38-40`

Only the third case had a production defect, and it is the one the ISS card
flagged: `AgentLibraryData.ts` is the generated mirror of the backend registry,
and FIX-323 changed the backend without regenerating it, so the file still
declared

```ts
{ id: "prototype-specify", …, gate: "Human_Gate" },
{ id: "prototype-plan",    …, gate: "Human_Gate" },
{ id: "prototype-analyze", …, gate: "Human_Gate" },
```

`test_gate_values_match_real_registry[prototype]` exists precisely to catch
that drift ("If someone edits a prototype/ppt agent's id, `gate` frontmatter,
or pipeline membership on the backend without regenerating
`AgentLibraryData.ts`…") and it was correctly red. The two API cases carry no
production defect at all — the endpoint serialises `AgentSpec.gate` faithfully;
the assertions were frozen literals of a value FIX-323 deleted.

## What changed and why there

**1. The generated data — `AgentLibraryData.ts:38-40`, `gate: "Human_Gate"` →
`gate: null`.** This is the only production edit. Blast radius checked before
editing: nothing imports the file (`grep -rn "AgentLibraryData\|LIBRARY_AGENTS"
frontend/src` finds only comments plus its own `ALL_LIBRARY_AGENTS` export —
`IdeaInputPage.tsx:854` takes the live library from `useAgentLibrary()`/Redux),
its own header declares it DEPRECATED and kept "for historical reference and
test fixtures only", and `ReviewGatesSection.tsx:73-86` (`isSeedGated`) already
reads gates ONLY from the manifest's `selections[id].gates`, never from a
static `AgentDef.gate`. So no rendered behaviour moves; the value was
documentation that had gone false, and the phase-6 test is what documents it.

**2. Two stale API assertions INVERTED, not deleted** — the
[FIX-415](20260831-0110-FIX-415.md) pattern, so the removed default cannot
silently return:

- `test_prototype_endpoint_gate_values` — was four per-id equalities (two
  `== "Human_Gate"`, two `is None`); now `all(g is None for g in
  gate_by_id.values())` over the whole pipeline, which also covers
  `prototype-analyze`, the id the original list predated.
- `test_library_returns_200_with_gate_and_real_prototype_ids` — its final
  `gate_by_id["prototype-specify"] == "Human_Gate"` is now `is None`. Every
  other assertion in that test (200, ids present, retired v1 ids gone, `gate`
  key on every entry) is untouched.

**3. One stale frontend-data pin re-pointed** —
`test_phase6_frontend_consistency.py::TestPrototypeAndPptSpecifics`. This is
the frozen twin of the parametrized equality above it: it asserted the
`.ts` file's literal `Human_Gate` values, so regenerating the data turned it
red. Its three `== "Human_Gate"` lines became one `all(g is None …)`; the id-set
assertion is unchanged. It was renamed
`test_prototype_real_ids_and_human_gate` → `test_prototype_real_ids_and_no_static_gate`
because the old name asserted the opposite of the contract (same reason
FIX-415 renamed `test_default_run_single_gate_per_agent_with_real_payload`).
A stale parenthetical in `test_ppt_and_prototype_counts_reconciled` describing
`prototype-analyze` as "Human_Gate" was corrected in the same file — it is the
exact claim this card retires.

Nothing under `backend/agents/` or `backend/app/` was touched: restoring the
static gate would have fixed all three reds in one line and was the wrong
direction — it reverts a deliberate product decision and would break
`test_declared_gate_streaming.py`, whose precondition FIX-415 inverted to
assert that no spec carries an inline gate.

## Adjacent, mentioned not touched

- `AgentLibraryData.ts` `order` values for the prototype family (1..5) are
  stale against the registry after [FIX-433](20260831-1859-FIX-433.md)
  re-spaced them (1, 3, 4, 5, 6). No test compares frontend `order` to the
  registry — `test_id_set_matches_real_registry` compares SETS — and no card
  covers it, so it was left alone. The file is unimported, so nothing renders
  from it.
- `ReviewGatesSection.test.tsx:6` still says "agents with gate === 'Human_Gate'
  start CHECKED" in its module docstring, while the tests below it correctly
  assert the opposite ("starts with NO checkboxes pre-checked"). The
  `Human_Gate` fixtures there are DELIBERATE — they prove the component ignores
  the static field — so only the docstring line is stale. Out of ISS-636's globs.
- `backend/tests/agents/test_phase8_live.py:425` describes `_DEFAULT_GATE_AGENT`
  as "those whose AGENT.md declares gate: Human_Gate". The dict is only ever
  used to pass an explicit `gate_agent_ids`, which is the correct post-FIX-323
  path, so the code is right and only the comment is history. Live tier, not run.
