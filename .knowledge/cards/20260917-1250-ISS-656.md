# ISS-656

## Title

`onViewRunningPipeline`, the callback `DashboardLayout` passes to `WorkflowHistory` for its "jump back to the currently running pipeline" affordance, duplicates the exact buggy shape of QA-PS-005's `onGoToPipeline` ([ISS-647](20260917-1100-ISS-647.md)) — same stale-state read, same silent-no-op exposure.

## Status: INFERRED — not yet reproduced

Filed from the root cause of QA-PS-005, not from an independent reproduction. Whoever picks this up should confirm it live before treating it as a confirmed defect (see "What would confirm this" below).

## Why QA-PS-005's root cause implies this

`frontend/src/components/layout/DashboardLayout.tsx:2859-2873`:

```tsx
onViewRunningPipeline={() => {
  const runId = pipelineState?.pipelineRunId;
  if (runId) {
    onSwitchToLiveRun?.(runId);
    setMainView("execution");
    router.push(routes.runStream(runId));
  }
}}
```

This is, line for line, the same pattern as the confirmed-buggy `onGoToPipeline`
(`DashboardLayout.tsx:2643-2653`, see [ISS-647](20260917-1100-ISS-647.md) § "Root cause —
second mechanism"): it reads `pipelineState?.pipelineRunId` at call time rather than being
handed a run id it can trust, and it calls `onSwitchToLiveRun` (itself async, see
`page.tsx:2592-2680`) and then navigates using the SAME stale value instead of waiting for
or being passed the resolved one.

The difference from the dropdown case is timing rather than mechanism: this button is
reached from the History page (`mainView === "history"`), so the user has typically been
away from the execution view for longer, making it MORE likely that `pipelineState` is
either unset or points at a different/older run than "the currently running pipeline" the
button's label promises — the same two failure shapes QA-PS-005 documents (no-op when
`pipelineRunId` is falsy; wrong-run navigation when it holds a stale value) apply here
without any list-reflow involved at all.

## Expected (once reproduced)

Clicking "view running pipeline" from the History page always switches to and navigates
into whichever pipeline is actually live server-side, every time.

## Actual (inferred, not yet observed)

The click can silently do nothing, or navigate to a previously-viewed run instead of the
actually-running one, depending on what `pipelineState.pipelineRunId` happened to hold
before the click — mirroring QA-PS-005's reported symptom exactly.

## What would confirm this

1. Start a pipeline run, then navigate to the History page (`/history` or the in-app
   History view) without revisiting the run's own stream page.
2. Locate and click the "view running pipeline" / resume affordance that
   `onViewRunningPipeline` backs.
3. Observe whether it navigates to the live run immediately, after a delay, or not at all
   on that click — and whether a second click behaves differently (per QA-PS-005's own
   "works on a subsequent click" observation).
