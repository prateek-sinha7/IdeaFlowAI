# ADR-0007: Custom-agent artifacts use a hyphen, not a dot

## Context and Problem Statement

Spec 012 R-12/R-20 give each custom-agent instance a deterministic artifact name so the
parent step can find what its children wrote. `artifact_name(instance_id, topic)` is the
single source of that name (F-06 — both the prompt preamble and the roster block must
call it rather than format the string themselves).

It produced `<instance_id>.<topic>.md`.

Observed on `qwen3.5:4b` during a live `sample_subagents` run: told to write
`joke.mountain.md`, the model created `/joke/mountain.md` — reading the dot as a path
separator. The failure did not stop there. The engine's artifact fallback then saved the
model's chat text (*"Written to `/joke/mountain.md`."*) as the artifact, so the downstream
`page` step read that sentence instead of the joke and rendered it into the deliverable.

One ambiguous character produced a silent data-corruption chain: wrong path → fallback
fires → prose stored as an artifact → downstream step consumes prose.

## Considered Options

1. **Harden the prompt** — tell the model the dot is not a directory.
2. **Change the separator to a hyphen.**
3. **Teach the artifact fallback to reject prose** that looks like a status message.

## Decision Outcome

**Option 2.** `f"{instance_id}-{topic}.md"`.

Option 1 was rejected as unreliable: it spends prompt budget on a small model to work
around a name we chose, and it fails silently when the instruction is not followed.
Option 3 is worth doing on its own merits — the fallback converting a visible failure into
corrupt downstream data is a real defect — but it treats the symptom, and the artifact
would still land at the wrong path.

A hyphen cannot be read as a path component. The remaining dot is the extension, which is
unambiguous.

### Blast radius, checked before the change

`artifacts.py` is shared, so every call site was verified to be `custom-agent:`-gated:

| call site | gate |
| --- | --- |
| `factory.py:559` | inside `if isinstance(spec.id, str) and spec.id.startswith("custom-agent:")` |
| `engine.py:3190` | under `if not dep_id.startswith("custom-agent:"): continue` |
| `engine.py:3233` | under `if not spec_id.startswith("custom-agent:"): return None` |

No non-custom-agent pipeline can reach it, so no existing artifact is renamed. The ten
golden characterization tests pass unchanged.

`artifact_name` also refuses any `instance_id` that is not a bare slug
(`^[a-z0-9][a-z0-9-]*$`) — it is the last point before a filename is built, so it rejects
rather than trusts. Passing an `agent_id` would otherwise yield
`custom-agent:research-a-topic.md`, and `../../etc/passwd` a traversal (F-02).

## Consequences

**Positive.** The observed failure chain is removed at its root. Names are still
deterministic and still derive from a single function.

**Negative.** `instance_id` and `topic` are both hyphen-slugs, so the name has three
kinds of hyphen in it — within the instance id, within the topic slug, and between them.
**The name is no longer mechanically splittable back into its parts.** Nothing parses it
today; anything that needs to must key on `instance_id` some other way rather than
splitting on `-`.

**Neutral.** This makes the convention diverge from any dotted-namespace convention used
elsewhere. Since the name is only ever produced and read whole by custom-agent steps,
the divergence is contained.

## Confirmation

`tests/agents/test_artifacts.py` covers `topic_slug` and `artifact_name`, including the
`ValueError` on a non-slug `instance_id`. The ten golden characterization tests confirm no
existing pipeline's artifacts changed.

**Related, still open:** the artifact fallback that turned this into corrupt data rather
than a visible failure is unfixed. It fires on three to four agents per run of
`sample_subagents` and silently stores chat text as the artifact. That is a separate
defect and a more dangerous one than the separator.
