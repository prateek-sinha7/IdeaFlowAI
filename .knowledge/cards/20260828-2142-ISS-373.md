## Sibling of ISS-275 — adjacent state (INFERRED — not yet reproduced)

Filed while analyzing `BUG-20260828-003800-workflows-new`. [ISS-275](20260828-1855-ISS-275.md)
reproduced the discard on `/workflows/new` — a brand-new, never-saved workflow. The SAME
component, at the SAME unguarded `onClick={onBack}` line, also mounts for
`/workflows/{id}/edit` — editing a workflow that was already saved once. This is the
"adjacent state" of the reported bug (editing an existing composition vs. authoring a
new one), not a different mechanism, so it is filed as its own card rather than folded
into the root: the fix's dirty-check has to cover BOTH mounts, and the impact differs
(here the user can lose edits to something that used to be a known-good persisted
workflow, with no way to tell after the fact that anything was even changed). Not
independently reproduced yet — a lead, not a confirmed defect.

## Why the root cause implies this

`DashboardLayout.tsx` mounts one `ComposerPage` for `mainView === "composer"`, keyed on
`savedComposition?.id ?? "new"` (`frontend/src/components/layout/DashboardLayout.tsx`,
composer mount block just above `onBack={handleBackNav}` at `:2946`) — the same
component instance serves both `routes.workflowNew()` (`/workflows/new`,
`frontend/src/lib/routes.ts:48`) and `routes.workflowEdit(id)` (`/workflows/{id}/edit`,
`frontend/src/lib/routes.ts:100`), differentiated only by whether `savedComposition` is
pre-populated. Its Back button is the identical unguarded wiring ISS-275 already
confirmed: `onClick={onBack}` at
`frontend/src/components/workflow/composer/ComposerPage.tsx:979`, and `onBack` is the
shared `handleBackNav` (`DashboardLayout.tsx:1701-1712`) that has no visibility into the
composer's dirty state either way.

Nothing in `ComposerPage` or `handleBackNav` distinguishes "editing an existing saved
workflow" from "authoring a new one" — the dirty-check gap ISS-275 found applies
identically to both mounts, because it is the same `onClick` on the same button.

## Expected vs Actual (to be confirmed by reproduction)

**Expected:** Opening `/workflows/{id}/edit` for an already-saved workflow, changing its
name/agents/steps, then clicking Back should prompt for confirmation before discarding
the edits (or preserve them), same as the fix expected for ISS-275 — and the guard must
cover this mount, not just `/workflows/new`.

**Actual (inferred, unverified):** Clicking Back after editing a saved workflow should
silently navigate away and discard every unsaved edit, with no warning and no way to
tell afterward that anything was changed — worse than ISS-275's case, since here there
was a known-good prior version to lose track of.

## What would settle it

Reproduce in the browser: open an existing saved workflow via "My Workflows" ->
edit (`/workflows/{id}/edit`), change the name or add/remove an agent, click the
composer's Back button, and confirm the change is silently gone with no confirmation
prompt (re-opening the same workflow should show it unchanged from its last save, with
no indication the edit was ever made).
