## What is suspected

[ISS-244](20260828-1634-ISS-244.md) root-caused the Settings > Profile stale "New passwords do
not match" banner to one exact mechanism in `frontend/src/components/settings/AccountSettings.tsx`:
a feedback-message `useState` written only inside the submit handler, with none of the relevant
fields' `onChange` handlers ever invalidating it — so a message that asserts something about the
current field values keeps asserting it after the values change and the assertion becomes false.

The identical mechanism, independently implemented, exists in
`frontend/src/app/login/page.tsx`, in the Cognito first-login/MFA challenge flow:

- `error` state — `const [error, setError] = useState("");` (line 24).
- Written **only** inside `handleChallengeSubmit` (lines 95-152): cleared once at its own top
  (`setError("");`, line 98), then re-set by whichever validation branch fires —
  `"New password must be at least 12 characters."` (lines 101-104), **`"Passwords do not
  match."`** (lines 105-108, the byte-for-byte same category of check as ISS-244 — a live
  predicate over two password fields), `"Choose how you'd like to receive your code."`
  (lines 109-113), or the code-empty message (lines 114-120).
- Rendered at lines 436-440: `{error && (<div>...{error}</div>)}` inside `ChallengeForm`.
- `ChallengeForm`'s four field `onChange` handlers each update only their own piece of state and
  never touch `error`:
  - `newPassword` — line 453: `onChange={(e) => setNewPassword(e.target.value)}`
  - `confirmNewPassword` — line 469: `onChange={(e) => setConfirmNewPassword(e.target.value)}`
  - `selectedFactor` (radio) — line 495: `onChange={(e) => setSelectedFactor(e.target.value)}`
  - `mfaCode` — line 514: `onChange={(e) => setMfaCode(e.target.value)}`
- The only other place `error` is cleared is `onCancel` (line 173, backs out of the challenge
  entirely) — there is no path that clears it on a mere field edit within the same step.

Grepped for the population of "password must match" checks across the whole frontend
(`do not match` / `confirmPassword` / `ConfirmPassword`) — these two files, ISS-244's and this
one, are the *only* two hits. No third instance exists.

## Condition

1. Sign in with an account whose Cognito state is `NEW_PASSWORD_REQUIRED` (temporary password),
   landing on the `ChallengeForm` "Set a new password" step.
2. Enter a New password and a Confirm password that differ; submit. Client-side validation shows
   "Passwords do not match." (`handleChallengeSubmit`, line 106) — correct at that instant.
3. Without touching New password, edit Confirm password so it becomes identical to New password.
4. **Predicted:** the "Passwords do not match." banner remains on screen, unchanged, even though
   the two fields now agree — same stale-assertion shape as ISS-244.

(Secondary, same handler/component, same fix location: the `SELECT_MFA_TYPE` "Choose how you'd
like to receive your code." and the OTP "Enter the 6-digit code…" messages are set the same way
and are equally never cleared by their own field's `onChange` — `selectedFactor` line 495,
`mfaCode` line 514.)

## Expected vs actual

- **Expected:** once the fields make the stated condition false (passwords agree; a factor is
  chosen; a code is entered), the error banner clears or re-evaluates, mirroring whatever fix
  lands for ISS-244.
- **Actual (predicted):** the banner is frozen at whatever `handleChallengeSubmit` last wrote,
  regardless of subsequent edits, until the user submits again or cancels the challenge.

## Why the root cause implies this — and why it is a DISTINCT defect, not the same one

ISS-244's fix belongs in `AccountSettings.tsx` — that component owns its own `message` state and
its own three password inputs; a fix there cannot reach `login/page.tsx`, which is a wholly
separate component tree with its own `error` state and its own four `ChallengeForm` inputs. Same
flaw, same shape, zero shared code between the two call sites — this is the "other caller with
the same flaw" case, not a duplicate of ISS-244 itself, and needs its own fix in `ChallengeForm`'s
`onChange` handlers (or a shared "clear validation message on edit" hook, if one is introduced to
fix both at once).

**Marked INFERRED**: the `NEW_PASSWORD_REQUIRED` challenge step has not actually been driven in
the browser for this defect — only the identical source-code shape has been confirmed by reading
`frontend/src/app/login/page.tsx` lines 24, 95-121, 173, 436-440, 453, 469, 495, 514. What would
confirm it: reach `ChallengeForm` with a `NEW_PASSWORD_REQUIRED` session (a QA account seeded with
a temporary password, or intercepting `/api/auth/login` to force the challenge shape), repeat the
mismatch-then-correct repro from ISS-244's Condition section, 3 cold-start cycles.
