## Summary

The "Create New User" dialog on `/admin` lets an admin submit an email that
already belongs to another user. The backend correctly rejects the request
with `409 Conflict` and body `{"detail":"A user with this email already
exists."}`, but nothing in the UI ever tells the admin the submission failed.
The modal stays open with the typed email/password still filled in, the
"Create User" button re-enables (no longer "Creating..."), and
`document.body.innerText` contains neither "already" nor "exists" at any
point after the request settles. The only observable trace is a browser
console network error and a `409` entry in the network panel — nothing a
non-technical admin would ever see.

This validates **BUG-20260828-103434-admin** in `bug-hunter/ledger.md`.

## Reproduction — confirmed 3/3, cycle 1 (fully cold navigation each time)

Each cycle: fresh navigation `http://localhost:3000/dashboard` →
`http://localhost:3000/admin` (full `page.goto`, not a soft nav), signed in
as `qa-admin@flowinqa.com`.

1. Click "Add user", fill Email `zz-hunt-dup-cN@flowinqa.com` / Password
   `zzhuntpass123`, Plan left at Basic, click "Create User" — succeeds (row
   count 4→5, modal closes).
2. Click "Add user" again, fill the SAME email with a different password,
   click "Create User".
3. Observe: `POST /api/admin/users` → `409 Conflict`,
   `{"detail":"A user with this email already exists."}` (confirmed via
   `browser_network_request` on every cycle). Console shows
   `Failed to load resource: ... 409 (Conflict)`. The modal remains open,
   email/password fields still populated, "Create User" button re-enabled
   (not "Creating..."). `document.body.innerText` and a full-DOM
   `textContent` scan for `already exists` / `Failed to create` both return
   zero matches — no toast element (`.bottom-6.right-6`, the toast's own
   class selector) exists in the DOM at all.
4. Cleanup each cycle: closed the dialog, deleted the throwaway user via its
   row's Delete action + confirm, verified the table returned to the
   original 4 seeded users before starting the next cycle.

Reproduced identically on cycles 1, 2 and 3 with distinct throwaway emails
(`zz-hunt-dup-c1/c2/c3@flowinqa.com`) to rule out any per-email caching. No
axis variation was needed — deterministic on every duplicate-email submit,
independent of timing (verified with an explicit wait after the button
re-enables, not just an immediate check) and independent of which cycle
created the original throwaway user.

## Root cause

`frontend/src/app/admin/page.tsx`, `handleCreateUser` (~L212-228):

```
try {
  const created = await adminCreateUser(token, newEmail, newPassword, newTier, newIsAdmin);
  ...
  showToast("success", `User ${created.email} created`);
} catch (err: unknown) {
  showToast("error", err instanceof Error ? err.message : "Failed to create user");
} finally {
  setCreating(false);
}
```

`adminCreateUser` → `request()` → `fetchWithAuth()` (`frontend/src/lib/api.ts`
L296-327) does correctly throw `ApiError(409, "A user with this email already
exists.")` on the non-OK response — confirmed no unhandled promise rejection
and no uncaught JS error fires (instrumented with `window.addEventListener('unhandledrejection'/'error')`
across a full duplicate-submit cycle: zero entries). `finally` running
(button re-enables) proves the catch block completes without throwing, i.e.
`showToast("error", msg)` is called. Yet the toast element the component
renders at L559-578 (`className="fixed bottom-6 right-6 z-50 ..."`, wrapped
in its own `<AnimatePresence>{toast && (...)}</AnimatePresence>`) never
mounts — a live DOM query for its own marker class (`.bottom-6.right-6`)
returns `NOT FOUND` at every point in the 3.5s window `showToast`'s
`setTimeout` would keep it visible. The state update that should make
`toast` truthy is not producing a render the DOM reflects. This needs
further investigation in a fix pass (candidate: a stale/duplicate `toast`
state batch, or the modal's own re-render on the same tick clobbering the
toast's mount) — not resolved here, validation only establishes the
observable defect and rules out a network/backend cause.

## Expected vs Actual

**Expected:** On a 409 (or any) rejection from `POST /api/admin/users`, the
dialog surfaces the server's message — the same toast pattern already used
for a successful create ("User X created") should fire with "A user with
this email already exists." — so the admin knows the create failed and why.

**Actual:** The rejection is caught, `creating` resets and the button
re-enables, but the toast intended to report it never appears anywhere in
the DOM. The admin cannot distinguish "still processing" from "silently
failed" without opening devtools.
