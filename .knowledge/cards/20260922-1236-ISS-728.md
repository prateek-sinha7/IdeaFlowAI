## Why ISS-727's root cause implies this

[ISS-727](20260922-1235-ISS-727.md) establishes, as CONFIRMED fact: the sandbox ROOT's
`presentation.html` is written exactly once, by v1's `ppt-composer`, and never again by any
`ppt_revision` run — not "stale relative to some other ref," but literally unwritten past v1
for the LIFE of the family. That is a statement about the LIVE/HEAD state of the file, not
merely about what a historical git tag captured.

Two callers read that live/HEAD file directly, with NO `ref` parameter — which is the textbook
CORRECT way to ask for "the current/latest content," not a bug in how they ask:

1. **`handleHeaderDownload`** (`frontend/src/components/preview/PreviewPanel.tsx:1343-1345`):
   ```tsx
   const blob = deliverableFile
     ? await getRunSandboxFileBlob(token, activeRunId, deliverableFile)   // no ref
     : await getRunSandboxZip(token, activeRunId);
   ```
2. **`handleDownload`** (`frontend/src/components/results/FilesTab.tsx:728-737`), for any row
   with `file.workspace` set:
   ```tsx
   const blob = await getRunSandboxFileBlob(getToken() || "", file.workspace.runId, file.workspace.path);
   ```
   — same shape, same missing 4th (`ref`) argument.

Both reach `read_sandbox_file` (`backend/app/api/run_files.py:1080-1153`) with `ref=None`,
which — per its own docstring, "Omitting `ref` is byte-identical to today" — falls straight to
`target = sandbox.path_for(rel)` / `data = target.read_bytes()` (`:1158-1180`): a plain
filesystem read of the CURRENT working tree. For a `ppt_revision` family, that working tree's
`presentation.html` is exactly the file [ISS-727](20260922-1235-ISS-727.md) proves never
changes. So clicking Download (or viewing the Files-tab row's content) on run `f7000bbd`
(v2) or `dfeb5949` (v3) — **as their own page, latest view, no dropdown touched** — should,
by this mechanism, still serve v1's "Arctic Seed Vault Logistics" deck, not "ARCTIC VAULT
v2"/"v3".

**Why the main Preview iframe is unaffected** (the dispatch brief's own proven fact: "Navigating
directly to the v3 run id... correctly showed 'ARCTIC VAULT v3' as its own run's live
content"): that surface reads `WorkflowRun.output` from Postgres, not the sandbox file — a
DIFFERENT source that [ISS-727](20260922-1235-ISS-727.md)'s Data section confirms IS correctly
populated per member. This card's claim is exactly that gap: two "give me the latest content"
code paths in the same app, reading two different backing stores, that silently agree everywhere
EXCEPT a `ppt_revision` family — because only for `strategy: ppt` does the sandbox-file store
stop tracking reality after v1.

## Not a duplicate

- **[ISS-706](20260922-1035-ISS-706.md)** (QA-PS-054, `handleHeaderDownload` omits
  `sandboxSelectedRef`) and **[ISS-665](20260917-1311-ISS-665.md)** (FilesTab resolves a pinned
  version from the live tree) are both about a caller FAILING TO ASK for an explicitly-pinned
  OLDER ref, and getting the live tree instead — the live tree is treated as the (wrong, for
  that moment) fallback. Fixing either makes the request carry the right `ref=vN`.
- This card is about a caller that asks for NOTHING (correctly, since it wants "latest") and
  still gets a wrong answer, because "latest" itself is broken for this pipeline type. Fixing
  ISS-706/665 does not touch this — there is no ref to thread on a run's OWN page; the bug is
  upstream, in what "live" means once [ISS-727](20260922-1235-ISS-727.md)'s mechanism has run.

## Expected vs Actual

- **Expected**: Clicking Download (or opening the Files-tab deliverable row) on `f7000bbd`
  (v2) or `dfeb5949` (v3) directly — their own run page, no version dropdown touched — returns
  that run's own real content ("ARCTIC VAULT v2"/"v3").
- **Actual (inferred)**: Both return v1's "Arctic Seed Vault Logistics" deck, identical to what
  the version-dropdown symptom already shows for an explicit `ref=v2` — except here no ref is
  involved at all; it is what "latest" resolves to.

## What would confirm this

Open run `f7000bbd-cf98-4748-b737-98b599874f08` (v2) directly (not via `e53d9b1f`'s version
dropdown) and click the Preview panel's header Download button (no version pinned). If the
downloaded file's `<h1>` reads "Arctic Seed Vault Logistics" instead of "ARCTIC VAULT v2", this
is confirmed. Repeat on the Files-tab row's own download affordance for the same run.

## Blast radius

Same two call sites traced above — any other future caller of
`getRunSandboxFile`/`getRunSandboxFileBlob` with no `ref` argument against a `ppt`/
`ppt_revision` run inherits the same gap, not just these two.

## Fix direction (not applied — issue only)

Not a separate fix from [ISS-727](20260922-1235-ISS-727.md)'s: once `ppt-revision-agent`
actually persists its edit to the real sandbox-root file (this card's dependency), the live/HEAD
tree itself becomes current, and both callers traced here start returning correct bytes with no
change of their own required. This card exists so that verification of ISS-727's eventual fix
checks a RUN'S OWN LATEST DOWNLOAD, not only the version-dropdown `ref=` case — the two are
easy to conflate and a fix could plausibly satisfy one check while leaving the other
unverified.
