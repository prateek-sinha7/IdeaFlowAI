## Description

The spec_revision chat card held a SECOND, contradicting copy of the revision-cycle number — and the register row's proposed fix would have made it a THIRD. ISS-083 asks for ResultCard's dormant cycle prop to be wired from runStore.viewed.specRevisionCount. REJECTED; nothing was wired. The prop is not a gap, it is a duplicate: the header rendered Revising spec — cycle ${cycle ?? 1} while the body rendered the backend narrator's own text (chat_narrator.py:157, f"Revising spec — cycle {attempt}"), so had the card ever mounted it would have printed "cycle 1" directly above "cycle 2". Deleted, not shadowed (INV-12): prop doc+decl (:96-100), destructure (:103 — the row misses this line), ternary (:117-120); the header falls back to the static CARD_SPECS.spec_revision.title. The row's cited 97-100,119 was stale at both ends. The card KIND is deliberately KEPT — cross-stack contract, parked on purpose; its unreachability is filed as ISS-111 rather than folded in.

## Root cause

The FE keeps re-deriving a number the backend already computed as a string. Three compounding facts, each re-verified here rather than inherited. (1) The kind is unreachable end-to-end: chat_narrator._revision_index (:106-118) keys on spec_revision_attempt/revision_index, and those two strings exist as quoted dict keys only at :112/:114 — the reader itself; the engine holds spec_revision_attempt as a Python local and passes revision_index= as a kwarg, and neither ever enters an event payload (agent_start's is fixed at {agent_id,name,role,icon,index,total}). attempt is therefore always 0 and the minting branch at :151-159 never fires — confirmed over 232,023 durable run_events across 14 runs, including 52 rows proving spec revisions demonstrably happened: cards are gate 52 / clarify 43 / pipeline 17 / deliverable 12 / null 6 and spec_revision is ZERO. (2) The dormancy is deliberate and LOCKED: IMPLEMENTATION-REGISTER.md:4214 records FIX-220 naming its keys revision_cycle/revision_in_flight *specifically* to avoid waking this reader, which "would have silently turned every in-revision gate card into a 'Revising spec - cycle N' card", and forbids inventing a third counter. (3) The store value is the wrong semantics anyway: specRevisionCount is the run's CURRENT count while a chat card is a HISTORICAL transcript entry, so a transcript holding a cycle-1 and a cycle-2 card would paint both with the live number — while the correct per-card value is already on the wire twice (text and deep_link.target). This is the fifth dead counter in the family (ISS-039, FIX-164, FIX-163/ISS-063/FIX-221, FIX-225, this), not the third the row claims.
