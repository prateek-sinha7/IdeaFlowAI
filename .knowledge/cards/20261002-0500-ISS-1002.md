# ISS-1002

## Description

INFERRED sibling of [ISS-347](20260828-2058-ISS-347.md) (root of QA-KB-062). The wizard half is
reproduced offline against the real `LaunchWizard`
(`evidence/qa-kb-062/analysis-proof-launchwizard-chain.out.txt`, case R3 plus the R3 control);
the writer half is read in code (CONFIRMED by file:line). Not reproduced live. Unlike ISS-347
and ISS-1000 it needs NO abandoned push: it is reachable in ordinary use.

Same family — the wizard treats `chain.*` sessionStorage as ambient state — with a different
writer and a different reader line.

**Writer.** `frontend/src/components/history/WorkflowHistory.tsx:829-842` (built-in targets) and
`:899-909` (saved-workflow targets): on every chain click for a non-success source run
(`isNonSuccess = selectedRun.status !== "completed"`, `canChain = !isNonSuccess ||
selectedRun.payloadChainable === true`, `:733-736`) it runs
`sessionStorage.setItem(CHAIN_SOURCE_STATUS_KEY, selectedRun.status)` BEFORE
`onChainPipeline(...)`, without knowing whether the target opens the wizard. That is decided
later, in `handleChainFromHistory` (`frontend/src/components/layout/DashboardLayout.tsx:2021-2048`)
through `selectWorkflowWizardPath` (`frontend/src/store/slices/globalSlice.ts:250-257`: only
`ppt`, `ppt_v2`, `prototype`). Every other target takes the non-wizard branch (`:2050-2100`),
which never reads or clears the key.

**Reader.** The wizard's pickup effect reads `chain.v2.source_status` whether or not
`chain.from` is set (`frontend/src/components/workflow/LaunchWizard.tsx:388-392`); `canContinue`
blocks on it (`:895`: `if (chainSourceStatus && !warningAcknowledged) return false;`); but the
only acknowledgement UI renders under `chainFrom && chainSourceStatus` (`:1164-1204`, the
checkbox's `setWarningAcknowledged` at `:1193`). With no `chain.from` the user is blocked and
has nothing to click.

**Observed offline.** R3: stale `chain.v2.source_status = "failed"`, the user types a brief and
picks a template and design system -> `{"continueDisabled":true,"ackCheckbox":false}`. R3
control, the same clicks without the key -> `continueDisabled:false`. The key is consumed by
that first read (`:391`), so a reload clears it — which is why this reads as a flaky wizard
rather than a bug.

**Second consequence (derived).** `handleChainPipeline` (`DashboardLayout.tsx:1893-2008`, the
chat lane's chain entry) never touches `CHAIN_SOURCE_STATUS_KEY`, so a stranded value also rides
into a later GENUINE chain started from the chat lane: the wizard then shows "Source run failed
— output may be incomplete" for the wrong run and holds Continue until it is acknowledged.

## Why the root cause implies it

ISS-347's root is that `chain.*` keys are read by the wizard with no tie to the navigation that
wrote them. Here the writer is even further from the navigation decision than the reader is, so
the key outlives its navigation in routine flows.

## Expected vs Actual

- **Expected:** `chain.v2.source_status` influences the wizard only when that wizard open IS the
  chain it describes; a warning that gates Continue always has a visible control to clear it.
- **Actual (R3):** Continue disabled, no checkbox, no explanation, until a reload.

## Where the fix belongs

Reader first: derive one predicate, `showSourceWarning = Boolean(chainFrom && chainSourceStatus)`,
and use it in BOTH `canContinue` (`:895`) and the JSX (`:1164`), so a gate and its remedy cannot
diverge. That alone removes the dead end. Writer second: write the key only for a wizard target;
the only place that knows is the wizard branch of `handleChainFromHistory`
(`DashboardLayout.tsx:2022-2048`). `WorkflowHistory.test.tsx` pins the writer to the history
side today (the `chain.v2.source_status` asserts around `:446` and `:470-472`), so that test
moves with the writer. Both are part of the same single-reader/scoping decision recorded on
[ISS-1001](20261002-0500-ISS-1001.md).

## Resolution: FIX-723 (2026-10-07), reader half

Resolved for the dead end by [FIX-723](20261007-1810-FIX-723.md).

- **What changed.** `showSourceWarning = chainFrom !== null && chainSourceStatus !== null` (`LaunchWizard.tsx:948`) is
  now the only condition for the `canContinue` gate (`:952`) and the warning/checkbox JSX (`:1233`). Continue can no
  longer be blocked with no checkbox on screen. A draft open also drops the key outright (`:403-410`).
- **Tests.** `LaunchWizard.chain.test.tsx` ISS-1002 case: the it.fails body now passes. Proof R3 shows Continue
  enabled. `LaunchWizard.test.tsx` SGV2 11.7 failed/degraded tests are unchanged and green.
- **Not done: the writer half.** `WorkflowHistory.tsx:837` / `:905` still write the key for non-wizard targets, and
  `handleChainPipeline` still does not clear it. A stranded value can still show the warning on a later GENUINE
  chat-lane chain, for the wrong run, though now always with its checkbox. As this card says, that belongs to the
  scoping decision on [ISS-1001](20261002-0500-ISS-1001.md).
