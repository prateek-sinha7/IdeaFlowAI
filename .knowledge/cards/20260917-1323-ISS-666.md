## What happened

Found by the 5-fixer while applying [FIX-519](20260917-1323-FIX-519.md) for register bug
**QA-PS-005**. Not fixed there because choosing between the options below is a design
decision the ISS cards did not cover.

## Mechanism

- `frontend/src/components/layout/AppHeader.tsx:229-245` `handleRunClick` (live branch) calls
  `onSwitchToLiveRun(run.id)` (`:233`). That is DashboardLayout's wrapper
  (`DashboardLayout.tsx:2657-2666`), which syncs `currentPipelineNotifId`/`currentPipelineNotifRunId`
  (FIX-201) and then calls the page's `handleSwitchToLiveRun`. Next, `handleRunClick` calls
  `onGoToPipeline?.(run.id)` (`:237`).
- The one `onGoToPipeline` implementation (`DashboardLayout.tsx:2643-2655`) calls
  `onSwitchToLiveRun?.(runId)` (`:2651`) again. This time it goes straight to the page's
  `handleSwitchToLiveRun`, and then it calls `router.push`.
- The single-badge fallback (`AppHeader.tsx:318-325`) has the same pairing.
- So each click runs `handleSwitchToLiveRun(sameId)` twice (`page.tsx:2592`): two `getRunEvents`
  round trips (`:2648`), two replays and two `seedRunChatTranscript` passes.

## Why it is harmless today, and why it is still recorded

- Both calls carry the same id, so the in-flight guard from [ISS-657](20260917-1250-ISS-657.md)
  (`page.tsx:2651`) lets both through. The reducer's identity gate refuses the duplicate frames
  (see the ISS-082 note at `page.tsx:2663`), and `seedRunChatTranscript` resets before it folds,
  so the end state is the same.
- The `router.push` right after the switch remounts `page.tsx` (see the T6 comment at `page.tsx:3255`).
  Both replays therefore usually finish inside the superseded instance, and the new instance
  restores the run again through `handleSelectWorkflowRun`. That is a third fetch.
- Before FIX-519, the second call either carried the stale `pipelineState.pipelineRunId` (the
  [ISS-647](20260917-1100-ISS-647.md) defect) or was skipped on a cold load. Now it always repeats the
  clicked id. The cost is wasted round trips; there is no visible defect.

## Options (not taken)

1. Remove `onSwitchToLiveRun(run.id)` from `handleRunClick` and the single badge, and let
   `onGoToPipeline(run.id)` do the switch. The implementation calls the page handler directly,
   so the wrapper's FIX-201 notification-ref sync would have to move into it.
2. Make the `onGoToPipeline` implementation skip its own switch when it is given a run id,
   because callers that pass an id have already switched. The legacy badge
   (`AppHeader.tsx:459`, bare call) keeps its switch.

## Expected vs actual

- **Expected:** one `getRunEvents` fetch per header run click.
- **Actual:** two from the pre-navigation instance, then the post-remount restore fetch.
