# ISS-866

## Description

**Observed, not inferred, but a DIFFERENT root cause from [ISS-863](20260929-1021-ISS-863.md).** Found while
running QA-KB-040's blast-radius check: every test file that references `waveWorkers`, run one at a time.
The reducer suite `useWorkflow.waveWorkers.test.ts` fails 2/10 (ISS-863: one defined `startedAt` key). This
file, in the same wave-worker stack, fails 2/29 for an unrelated reason. ISS-863 speaks of "two older
`toEqual` cases"; four tests across two files are red.

Command (cwd `frontend/`):
`./node_modules/.bin/vitest --run src/components/results/AgentDetailPanel.waveWorkerStatus.test.tsx`
gives `2 failed | 27 passed (29)`, identical on two runs on 2026-10-01 (HEAD `024c03ef8`; `git status
frontend/` clean, so nothing local is skewing it). Output kept in
`evidence/qa-kb-040/07-analyze-sibling-waveWorkerStatus-vitest-output.txt`.

The two failures, both `AssertionError: ... to contain 'Full input prompt'`:

- `AgentDetailPanel — a wave member's page carries the same sections > shows the member's own output, reasoning, input and context`
  at `AgentDetailPanel.waveWorkerStatus.test.tsx:288`
- `AgentDetailPanel — a member page is the step page, every section > renders every section a step page renders`
  at `:328-329` (the string sits in a `for` list)

The received page text in both contains
`Tool calls1read_filefile_path: xokTask messageContext loaded from files in .context/ ... →56 chars`:
the input section is rendered, under a different label.

## Mechanism (CONFIRMED, each line read)

- `frontend/src/components/results/AgentDetailPanel.tsx:524` is
  `const label = hasTwoSections ? "System prompt" : contextIsFileBased ? "Task message" : "Full input prompt";`
- `AgentDetailPanel.tsx:1562-1565` passes
  `contextIsFileBased={ !agent.systemPrompt && sources.some(s => s.type === "run_input" || s.type === "context_block") }`,
  where `sources` is `[...(agent.contextSources ?? []), ...attachedFileSources]` (`:1373`).
- Both fixtures give the member `contextSources: [{ type: "run_input", label: "prompt.md", size_chars: 60 }]`
  (`AgentDetailPanel.waveWorkerStatus.test.tsx:277` and `:315`) and no `systemPrompt`. So
  `contextIsFileBased` is true and the label is "Task message", with the subtitle
  "Context loaded from files in .context/" (`AgentDetailPanel.tsx:525-527`).

## Why it is red (CONFIRMED from git)

The test was created in `05b7bce54` (2026-09-10 21:26 +0200). That commit's message lists
"waveWorkerStatus (29)" among the vitest files it ran and says "tests pass at runtime". The tree of that
commit has no `contextIsFileBased` at all: `git show 05b7bce54:frontend/src/components/results/AgentDetailPanel.tsx
| grep -c contextIsFileBased` prints `0`, and `git merge-base --is-ancestor e7305f9dd 05b7bce54` answers
"no". `contextIsFileBased` was introduced by `e7305f9dd` ("sandbox-git-versioning-v2", 2026-09-10 17:40
+0530, Req 13 AC 9), the only commit that ever changed that identifier in `AgentDetailPanel.tsx`
(`git log -S contextIsFileBased`), on a parallel line of history. Neither commit's tests exercise the
other's behaviour, so the contradiction first appeared when the two lines merged. See
`evidence/qa-kb-040/08-analyze-git-history.txt`.

## Disposition: INFERRED, not decided

Probably a stale test. `AgentDetailPanel.tsx:500-504` says that when context is loaded from files the human
message is "legitimately short" and the section should read "Task message". A wave member's `inputPrompt`
is its `input_prompt` or, failing that, its `task_block` (`frontend/src/hooks/useWorkflow.ts:511-515`). If a
real member's context is file-based, as the fixture models it, that is exactly the case the comment
describes. If so the fix is test-side: expect "Task message", or give the fixture a `systemPrompt` so it
exercises the "System prompt" label.

What would settle it: (a) whether Req 13 AC 9 is meant to apply to wave-member pages at all; (b) opening a
real wave member page from an existing completed wave run and checking that its `contextSources` carry a
`run_input` entry. Neither needs a new run. Decide which side is wrong before editing either, as ISS-863
did for its own pair.

## Not caused by, and not fixed by, the QA-KB-040 change

The `toMatchObject` fix for ISS-863 touches only `useWorkflow.waveWorkers.test.ts`; it changes nothing in
this file or in `AgentDetailPanel.tsx`. The 27 passing tests here include the `wave member duration` block
(`AgentDetailPanel.waveWorkerStatus.test.tsx:359-396`), which is where the `startedAt` / `durationMs`
fallback of `upsertWaveWorker` is covered.
