## What was wrong

`/admin`'s "Create New User" dialog accepted `not-an-email` — no `@`, no
domain — and `POST /api/admin/users` persisted it verbatim. The resulting row
rendered normally in the admin table but could never sign in through
`/login`, so it sat as an orphaned account until an admin noticed and deleted
it by hand. Filed as `BUG-20260828-033400-admin`, root card
[ISS-295](20260828-1726-ISS-295.md), reproduced 3/3.

## Root cause

Two independent gaps, both on the email field only — password length and tier
ARE checked server-side, email was not:

- `backend/app/api/admin.py:131` — `CreateUserRequest.email: str`, a bare
  Pydantic `str`. The codebase's own established pattern is `EmailStr`
  (`backend/app/models/schemas.py:15` `RegisterRequest.email`, `:22`
  `LoginRequest.email`); this schema never adopted it. `create_user`
  (`admin.py:392-512`) checks duplicate → 409, tier allow-list → 400, password
  `len < 8` → 400, and nothing about email shape, so the string reached
  `User(email=request.email, ...)` unchanged on both the local-auth and
  Cognito paths.
- `frontend/src/app/admin/page.tsx:213` (`handleCreateUser`) and `:512` (the
  "Create User" button's `disabled` prop) gated on `!newEmail || !newPassword`
  — presence, never format. The Email `<input>` carries `type="email"`, but
  the modal is a `<motion.div>`, not a `<form>`, so no submit event fires and
  nothing calls `.checkValidity()`; the native HTML5 constraint was decorative.

## What changed and where

- `backend/app/api/admin.py` — `email: str` → `email: EmailStr` on
  `CreateUserRequest` (plus the `EmailStr` import). This is the authority:
  FastAPI/Pydantic rejects a malformed value with 422 before the handler body
  runs, so a direct API caller that skips the browser is blocked too.
  `AdminUserResponse.email` (`:112`) was deliberately left `str` — it is a
  response model, and tightening it would 500 on any already-persisted
  malformed row instead of rendering it for deletion.
- `frontend/src/app/admin/page.tsx` — one module-level `EMAIL_PATTERN`
  constant used by both the `handleCreateUser` guard and the button's
  `disabled` prop, so the button stays disabled on a malformed address rather
  than round-tripping a request that can only 422. A `<form>` wrapper was the
  other option the analysis offered; it would fire native validation on submit
  but leaves the button enabled, which is not the behaviour the test asserts.

No new dependency: `pydantic[email]==2.12.5` is already in
`backend/requirements.txt:11`.

## Blast radius checked

`CreateUserRequest` has exactly one consumer (`admin.py`'s own `create_user`);
`adminCreateUser` (`frontend/src/lib/api.ts:1487`) has exactly one production
caller (`admin/page.tsx:218`). Every other `POST /api/admin/users` caller in
the tree sends a well-formed address —
`tests/integration/e2e/conftest.py:381` (`e2e-<hex>@flowinqa.com`),
`tests/integration/e2e/suites/24_api_contract/test_api_contract.py:338`,
`backend/tests/integration/test_admin_authorization_matrix.py:241,257,270,311`
(`*@example.com`) — so none are newly rejected. Pydantic runs `EmailStr` with
`check_deliverability=False`, so no DNS lookup is introduced.

## Not fixed here

[ISS-405](20260828-2324-ISS-405.md)'s backend half is closed in passing —
`EmailStr` rejects `""` too, so an empty-string email can no longer be
persisted through the API. Its second half is NOT addressed: the unguarded
`user.email[0].toUpperCase()` at `frontend/src/app/admin/page.tsx:391` still
throws on any already-persisted empty-string row and still crashes the whole
`/admin` page through the root `error.tsx`. That card stays open.
