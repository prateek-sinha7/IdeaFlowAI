# ISS-138

## Title

**The FIX-201 legacy->store bridge overwrites the run store's `pipelineState` WHOLESALE, silently discarding any store-only correction.** `page.tsx:1663-1672` runs `runStore.updatePipelineState(runId, () => pipelineState)` — a total replacement, not a merge — whenever the legacy `useWorkflow.pipelineState` changes and the run is both viewed and actively-building. **This cost a real false-green during FIX-245:** the ISS-126 reconciliation was written to the store, the unit tests passed, and the fix was still INVISIBLE on screen because the bridge copied the stale legacy state over it a few hundred ms later. FIX-245 works around it by reconciling BOTH containers through the same helper, but the hazard remains for the next person who patches store state directly. Fix shape: make the bridge merge rather than replace, or make the store the sole owner of `pipelineState` and retire the legacy copy.

## Severity / Tag / Status (original row)

- Sev: major
- Tag: frontend
- Status: **FIXED** — FIX-256 (2026-08-13 dev merge, commit `d0dc1f49`). The bridge is terminality-preserving: the store's own verdict is re-applied through the SHARED one-way `applyTerminalStatus` (INV-12), keyed on the explicit `cancelled`/`failed`/`degraded` markers or the reopened run's persisted status — never inferred from `isRunning:false`, which a not-yet-started entry also carries. TEST-035 (11), seen RED first. **Live A/B vs a pre-fix frontend on :3001, same backend, 7 samples over 30s: IDENTICAL** — FIX-245's dual-container workaround already masked the symptom, so what this removes is the latent hazard this row named ("the hazard remains for the next person who patches store state directly"), and the live pass proves no regression.

## Source / Evidence

Root-caused in a live browser during quick-260812-wir by instrumenting the store — the store entry was observed flipping back to `isRunning:true` ~4s after being set false, with no `handleFrame` involved.
