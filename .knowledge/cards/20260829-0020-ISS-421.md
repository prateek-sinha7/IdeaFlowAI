## Why this must also be broken

[ISS-311](20260828-1740-ISS-311.md) confirmed the mechanism for `/create/user-stories`:
`AgentLibrary.tsx`'s `filteredAgents` (`:104-117`) excludes every agent already present in
`existingAgentIds`, and the tab defaults to the current pipeline's own category
(`activeCategory = currentPipelineType || "all"`, `:86`). That card's own root-cause section
already established the trigger is structural — every `user_stories`-tagged catalog agent is
pre-seeded into the default workflow — not a fetch or tagging bug specific to that one pipeline.

Reading the two hosts that feed `AgentLibrary` a real `currentPipelineType` confirms the same
structural guarantee holds for every OTHER non-custom pipeline type too, on two independent
surfaces:

**1. `IdeaInputPage.tsx` (`/create/<type>`, the reported route)**

```tsx
// IdeaInputPage.tsx:898-902
const type = isMigrationMeta && migrationChoice ? migrationChoice : workflowType;
if (type === "custom") return [];
return LIBRARY_AGENTS.filter((a) => agentMatchesPipelineType(a.pipeline_type, type)).sort((a, b) => a.order - b.order);
```

This is the `pipelineAgents` `useState` initializer — the FRESH-load seed (no `initialAgentIds`,
i.e. no restored/saved workflow). It filters the static catalog (`AgentLibraryData.ts`'s
`LIBRARY_AGENTS`) down to exactly the agents tagged for `type`, for every type except `"custom"`
(explicitly short-circuited to `[]` one line above). That result becomes both the "Advanced N
agents" canvas AND, via `AgentsPopup.tsx:2673`'s `existingAgentIds={collectAgentIds(agents)}`,
the `AgentLibrary` prop that drives `notAlreadyAdded`. Counted directly in `AgentLibraryData.ts`:
6 `user_stories` / 3 `ppt` / 5 `prototype` / 15 `app_builder` / 13 `mulesoft_to_springboot` /
13 `dotnet_to_azure` entries — every one of them lands in the fresh seed, so every one of those
6 tabs is empty on first open, the same way ISS-311 already reproduced for `user_stories`.

**2. `LaunchWizard.tsx` (`/workflows/<id>/run`, launching a built-in with no saved override)**

```tsx
// LaunchWizard.tsx:147-150
const defaultAgentsFor = (libraryAgents: AgentDef[], mode: LaunchMode): AgentDef[] =>
  libraryAgents.filter((a) => agentMatchesPipelineType(a.pipeline_type, MODE_CONFIG[mode].agentPipeline)).sort(
    (a, b) => a.order - b.order,
  );
```

Used as the `pipelineAgents` initializer (`:205`) and on every mode switch (`:567`) whenever no
saved override exists for that pipeline (`overrideAgents` only replaces it at `:452` when one
does). `libraryAgents` here comes from `useAgentLibrary()` — the SAME live,
`GET /api/agents/library`-backed Redux state `AgentLibrary.tsx`'s own `ALL_AGENTS` reads
(`useAgentLibrary.ts:24-33`) — so on this host the seed and the addable catalog are drawn from
the identical array, making the "every catalog agent for this type is already added" outcome
exact, not merely likely. `AgentsPopup.tsx:2673` receives the same `pipelineType`/`agents` shape
from this host too (`LaunchWizard.tsx:1174-1175`).

**Not affected:** `ComposerPage.tsx:1401` also passes a `currentPipelineType`, but its own mount
comment (`:284-288`) states `"custom"` is the only `workflowType` this component ever mounts for
(`DashboardLayout`'s `COMPOSER_ENABLED_TYPES`) — and `"custom"` is the one type both hosts above
explicitly start blank rather than fully-seeded, so this host's own category tab is not
guaranteed empty. `app/workflow/page.tsx:67` and `WorkflowView.tsx:556` pass neither
`currentPipelineType` nor `existingAgentIds` (`activeCategory` defaults to `"all"`) — also not
affected, and `/workflow` is a standalone route outside `routes.ts`'s catch-all (ADR-0018) with
no in-app link found, so likely unreached regardless.

## Expected vs actual

**Expected:** opening "Add agent" from a fresh `/create/ppt`, `/create/prototype`,
`/create/app_builder`, `/create/mulesoft_to_springboot`, `/create/dotnet_to_azure`, or from
`/workflows/<built-in-id>/run` with no saved override, and landing on that pipeline's own
category tab, should show the same "No agents found" empty state ISS-311 already reported for
`user_stories` — the identical code path, just a different `type` value.

**Actual (INFERRED — not yet independently browser-reproduced for these specific routes):** not
confirmed live for the other 5 types or the second host; confirmed only via the code paths above,
which are structurally identical to ISS-311's already-reproduced case.

## What would confirm or refute this

Open `/create/ppt` (or any of the other 4 non-custom, non-user_stories types) fresh, click
"Advanced", click "+ Add agent", and check whether the tab matching that page's own pipeline
opens on "No agents found" the same way ISS-311 documented for `/create/user-stories` — then
repeat once from `/workflows/<a built-in id with no saved override>/run`. A miss on any of these
(a non-empty own-category tab) would mean that type's catalog is NOT a strict match with its
default roster, refuting this card for that one type without affecting ISS-311 or the others.

## Where the fix belongs

Same place ISS-311 already located it: inside `AgentLibrary.tsx`'s own default-category-selection
/ empty-state logic (`:86` and `:229-232`), not in any of the 4 hosts that mount it — a guard
there closes this sibling for every pipeline type and both hosts at once, instead of patching
`IdeaInputPage.tsx` and `LaunchWizard.tsx` separately.
