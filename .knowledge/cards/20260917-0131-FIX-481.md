# FIX-481

## What changed

The frontend now owns browser-session expiry in one root-level
`AuthSessionProvider`. It schedules a shared Cognito refresh before access-token
expiry, retries at true expiry when an early refresh fails transiently, and clears
the browser credential before redirecting through the safe internal login-return
path when recovery is terminal.

`lib/api.ts` now distinguishes a terminal Bearer 401 from an ordinary
unauthenticated 401. A Bearer request refreshes once and replays once; a failed
refresh or replayed 401 emits the shared expiry signal. Login failures and refresh
endpoint failures are not redirected. SSE and the surviving handoff WebSocket reuse
the same signal instead of maintaining duplicate clear-and-redirect code.

## Root cause

Protected pages previously treated the presence of `localStorage.auth_token` as
authentication. `frontend/src/lib/api.ts` refreshed and replayed a 401 once, but
then surfaced a terminal `ApiError` without clearing the token or navigating.
`frontend/src/hooks/useRunStream.ts` also left a failed proactive refresh as a
no-op. Consequently, an idle protected page could retain a stale credential and
continue rendering authenticated UI after the Cognito session could no longer be
refreshed.

## Evidence

- `frontend/src/providers/AuthSessionProvider.tsx` owns pre-expiry refresh,
  visibility/online rescheduling, terminal cleanup, and safe login redirect.
- `frontend/src/lib/api.ts` only expires a session after a terminal 401 carrying a
  `Bearer` header, preserving wrong-password login behavior.
- `frontend/src/hooks/useRunStream.ts` and
  `frontend/src/hooks/useHandoffSocket.ts` route failed recovery through the same
  session-expiry path.
