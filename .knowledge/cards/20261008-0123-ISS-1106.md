# ISS-1106

## Description

INFERRED sibling of [ISS-1063](20261007-1940-ISS-1063.md) (QA-KB-098). In production the sandbox that a revision run gives its tools and its per-agent `RunLog` carries `current_run_id == the chain-root id`, not the revision's own id. Every per-run path (`.logs/{run}.jsonl`, `.verify/{run}/`, `.browser/{run}/`) is keyed on `current_run_id` (`sandbox.py:651`, `:664`, `:673`), so a revision writes into the ROOT run's slot. The `.logs` half was observed in an offline engine drive; the `.browser/` and `.verify/` halves are derived from the same constructor and the property definitions, not driven through a browser step.

## Why the root cause of QA-KB-098 implies it

The red test of ISS-1063 is the only writer-driven guard of `.browser/{run_id}/` per revision (Requirement 37 AC 3); its pptx twin guards `.verify/{run_id}/`. Both build their sandboxes BY HAND with `RunSandbox(user, root_id, current_run_id=rev_id, ...)` (`backend/tests/agents/test_per_run_paths_v3.py:294-297`, `:415-418`) and never go through the engine or the factory. So they can only ever prove the property of a sandbox somebody constructed correctly, they cannot see whether production constructs one, and while the ISS-1063 test is red even that is unguarded. Checking what the production path actually hands to the tools shows it never passes the revision id.

## Mechanism (CONFIRMED by reading, then by probe)

- `RunSandbox.__init__(user_id, sandbox_root_id, *, current_run_id=None)` defaults `current_run_id` to `sandbox_root_id` (`sandbox.py:578-595`); `self.run_id` is documented as the alias for the LOGICAL run id (`sandbox.py:582-590`).
- `engine.py:4415`: `sandbox = RunSandbox(disk_principal, _chain_root_id)` has no `current_run_id`. The same module's other construction, the run trace at `engine.py:4140-4144`, DOES pass `current_run_id=pipeline_run_id`, so the engine knows the distinction and applies it at one of its two sites.
- `engine.py:9779` passes `run_id=sandbox.run_id` into `AgentContext`. `AgentContext` has a single `run_id` field (`factory.py:73`, "create_runner roots the RunSandbox at <user>/<run>/") and nothing for the logical id. `factory.py:371` then rebuilds the sandbox as `RunSandbox(ctx.user_id or "anon", ctx.run_id or "adhoc")`, again without `current_run_id`. That object is what `playwright.bind_sandbox` (`factory.py:1285`), `pptx_tools.bind_sandbox` (`:1267`) and `file_extract_tools.bind_sandbox` (`:1304`) receive.
- Readers of the per-run paths: `playwright.py:303` (`_sb.browser_dir / filename`, default filename `screenshot.png`, `:271`), `pptx_tools.py:259` and `:329` (`browser_dir`), `pptx_tools.py:488` (`verify_dir`), and six `RunLog(getattr(sandbox, "run_log_path", None))` sites in `engine.py` (`:9633`, `:10592`, `:10830`, `:10879`, `:11111`, `:11143`), which use the engine's own sandbox from `:4415`.

## Observed (offline, scripted model, root + two revisions through the real engine, HEAD 165c40316)

- `factory.py:371` was reached 18 times: every construction has `current_run_id` equal to the chain-root id and a `browser_dir` leaf equal to the chain-root id; none carries a revision id (`evidence/qa-kb-098/analysis-04-probe-runsandbox-ctor-sites.txt`). `engine.py:4415` was reached 3 times, all chain-root, including during the two revisions. `engine.py:4140` is the only site that carried a revision id (twice).
- `.logs`: the chain root's file holds `step_start` x18 and `step_end` x18 (6 agents x 3 runs); the two revisions' own files hold 37 lines each with neither (`evidence/qa-kb-098/analysis-05-probe-logs-per-event.txt`).

## Expected vs actual

Expected (`sandbox.py:651-679` docstrings, `playwright.py:295-297` "Requirement 24 AC 3: ... every revision's screenshots land in .browser/{run_id}/ rather than the flat .browser/ root shared by all revisions in the family", the ISS-1063 test's own docstring): each run in a family keeps its own `.logs/{run}.jsonl`, `.verify/{run}/` and `.browser/{run}/`.

Actual: a revision's per-agent log entries are appended to the root's `.logs/<root>.jsonl` (observed). A revision's playwright screenshots and pptx verify evidence are written under `.browser/<root>/` and `.verify/<root>/` (derived): a repeated `screenshot.png` overwrites the root's file silently; pptx `attempt-NN.js` numbering continues after the root's and `report.txt` is appended to (`pptx_tools.py:493-519`), which is exactly the mixing the pptx test asserts against (`"revision report body" not in root_report.read_text()`).

## Trap for the fixer (CONFIRMED by probe)

Adding `current_run_id=pipeline_run_id` at `engine.py:4415` and nothing else changes `sandbox.run_id` to the revision id. `engine.py:9779` passes that as `AgentContext.run_id`, and `factory.py:371` uses it as the DIRECTORY key, so the revision's runner would root in `<RUNS_ROOT>/<user>/<revision_id>/`, a different physical directory from the family root. Probe: `naive fix: engine sandbox.run_id='revision-bbb'; factory sandbox dir leaf='revision-bbb'; shared with engine dir: False` (`evidence/qa-kb-098/analysis-07-probe-naive-fix-splits-sandbox.txt`). That breaks ADR-0040's one-sandbox-per-family. The comment at `engine.py:9773-9778` ("sandbox.run_id is the chain-root id") has been stale since the id split.

## What is INFERRED, and what settles it

The `.browser/` and `.verify/` consequences are derived, not driven. Settle by repeating the analysis-04 spy (`evidence/qa-kb-098/analysis-plugins/kb098_sandbox_ctor_spy.py`) while driving root + revision and asserting the sandbox constructed at the factory site carries the revision id, or by driving a revision whose step grants `playwright` and asserting its screenshot lands in `.browser/<revision id>/`. If the factory-site sandbox does carry the revision id on some path the probe did not take, this card closes as not reproducible.

## Fix direction (only once reproduced)

Fix at the seam where the factory re-derives the sandbox, not in each tool. The engine already owns a sandbox object and `create_runner` already accepts `run_sandbox=` (`factory.py:285`, `:366-369`): hand it the engine's sandbox, built with BOTH ids, for the main-step path instead of letting `factory.py:371` rebuild one from `ctx.run_id`, or give `AgentContext` separate `sandbox_root_id` and `current_run_id`. Then `engine.py:4415` takes `current_run_id=pipeline_run_id` and `engine.py:9779` stops treating `sandbox.run_id` as a directory key. All six `RunLog` sites and all tools follow with no per-caller change. Decide ISS-1107 (the browser session key) in the same change.
