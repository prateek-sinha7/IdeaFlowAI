## What was wrong

Bug report QA-KB-024. The root cause and blast radius are the analysis in [ISS-685](20260918-ISS-685.md); they are
not re-derived here. [FIX-545](20260904-FIX-545.md) gave `json_tasks` (and later `screen_plan`) a
`parse_preferring_target(reply, sandbox=, target=)` that reads the task file the producer wrote before falling back
to its reply. It then pasted a `hasattr` probe into two of the six `resolve("task_parser", ...)` consumers
(`task_loop.py`, `wave_scheduler.py`). The other four still called `parser.parse(<producer reply>)`:

- `engine.py` `_compute_cumulative_boundaries` (was `:14889`) and `_compute_wave_orphan_allowsets` (was `:14971`).
  These resume reconcilers recompute content-addressed task keys and compare them with the keys the strategy
  persisted, so keys built from a different input could not match. Every shipped wave planner replies with one
  line, so `parse` raised, the `except` swallowed it and the RESUME-16 orphan gate was silently off. A reply that
  parsed to a different list gave a wrong boundary or a wrong allow-set, which is silent data loss
  ([ISS-685](20260918-ISS-685.md) scenarios S-A, S-B2, S-B3).
- `engine.py` `_first_incomplete_step`, the task_loop total (was `:15202`): a narrating reply raised and the
  finished step was re-entered. Its caller `_compute_resume_offset` builds a temp `ExecutionContext` whose `runner`
  is `None` (`context.py:109`), so no sandbox handle was reachable there.
- `fanout_batch.py:92`: a normal-run `ValueError` on a narrating reply with a correct task file on disk.

Re-checked before editing: a grep of every `"task_parser"` resolve in `backend/agents` and `backend/app` still finds
exactly these six sites, so the card's blast radius held.

## What changed, and why there

One helper that all six route through, as [ISS-685](20260918-ISS-685.md) prescribed, instead of four more pasted
probes:

- `backend/agents/capabilities/task_identity.py:173`: `parse_step_tasks(parser, reply_text, *, sandbox=None,
  target=None)` is the [FIX-545](20260904-FIX-545.md) probe in one place. `task_loop.py`, `wave_scheduler.py` and `engine.py` already
  import `task_identity`. The helper duck-types `sandbox` and imports nothing, so the "agents.capabilities must not
  import the execution kernel or the web layer" contract is unaffected.
- `task_loop.py:220` and `wave_scheduler.py:273`: their copies of the probe are replaced by the helper. It is the
  same probe with the same arguments, so behaviour is identical. The `custom_path` branch stays first in
  `wave_scheduler.py` (`:271`).
- `fanout_batch.py:93`: the helper, with `sandbox=getattr(runner, "sandbox", None)` and
  `target=getattr(task_source, "target", None)`; import at `:27`. `heading_tasks` (shipped `sample_fanout`) has no
  `parse_preferring_target`, so it still parses the reply.
- `engine.py:14889` and `:14985` (the two reconcilers): the helper, with
  `sandbox=getattr(getattr(ectx, "runner", None), "sandbox", None)` and the step's `task_source.target`.
- `engine.py:14977`: `_compute_wave_orphan_allowsets` skips a `task_source.kind == "custom_path"` step before the
  `source_step` guard. The shipped `blr-write` declares both (`backlog_revision/workflow.yaml:237-242`), so the old
  guard did not protect it. Producing no allow-set gives the same fail-safe KEEP it got before, when `parse` raised;
  the difference is that no parse is attempted now.
- `engine.py:15013`: `_first_incomplete_step(..., *, sandbox=None)`. `:15044` falls back to `ectx.runner.sandbox`
  (through `getattr`, because offline callers pass a bare namespace with no `runner`), and `:15232` uses the helper
  for the task_loop total.
- `engine.py:16296-16302`: `_compute_resume_offset` passes
  `sandbox=RunSandbox(user_id or "anon", _resolve_root_id(run_id, owner_id))`, the same construction `resume_run`
  uses. Both names already live in `engine.py`, so there is no new import. `RunSandbox.__init__` does no I/O, and
  `read()` returns `None` for an absent file without creating the directory (`app/agents/sandbox.py:557-617`,
  `:735-744`). `_resolve_root_id` catches every error and degrades to `run_id` (`engine.py:3545-3590`).
- The three `except Exception` arms (`engine.py:14924`, `:15005`, `:15253`) keep their fail-safe direction and now
  log a warning naming the step and the error. Nothing was logged there before, which is how the orphan gate stayed
  off for every shipped wave step without anyone noticing.

The engine branches on no parser or workflow name (INV-1 / SC-001). The probe is `hasattr`, and the only new literal
is the task-source kind `"custom_path"`.

### One deviation from the card (plumbing only)

[ISS-685](20260918-ISS-685.md) also proposed an optional `sandbox=` keyword on the two reconcilers, fed from
`execute()`'s `sandbox` local.
It was not added. At their only call sites (`engine.py:6001`, `:6017`), `ectx.runner` is the `KernelServices` built
at `:5800-5803` with that same `sandbox` (stored as `self.sandbox`, `kernel_services.py:256`). `ectx.runner.sandbox`
is exactly the handle the strategies read (`getattr(runner, "sandbox", None)`), so reading it keeps parity by
construction and leaves the call sites untouched. `_first_incomplete_step` does take the keyword, because its
resume-offset caller has no runner.

### Not changed, on purpose

- The engine's existing parser-name defaults (`or "heading_tasks"`, `or "json_tasks"`).
- The `occurrence_ordinals` + `compute_task_key` comprehension that is copied four times, and a strategy-owned
  `derive_tasks` port. [ISS-685](20260918-ISS-685.md) marks both as optional and separate decisions.
- On a wiped sandbox the helper falls back to the reply, which is today's behaviour.
  [ISS-685](20260918-ISS-685.md)'s open question
  (whether anything durably captures `build/tasks.json` for a wiped-sandbox resume) is not touched by this fix.
- `ScreenPlanParser.parse_preferring_target` writes `build/screens.json` back when `apply_flow_backstop` adds a
  transition (`screen_plan.py:256`, `:273`). The wave reconciler now makes the same call the strategy makes on
  re-entry, against the same sandbox. The backstop skips a transition that already exists
  (`screen_inventory.py:388`), so once the strategy has written one back, the reconciler's call adds nothing and
  writes nothing.
- The seven strict `xfail` markers in the test file, left for the 6-verifier.
