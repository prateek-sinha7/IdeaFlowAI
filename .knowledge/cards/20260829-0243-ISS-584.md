## What this is

An INFERRED sibling of [ISS-343](20260828-2059-ISS-343.md) (root, CONFIRMED, `/create/prototype`),
derived from that card's root cause rather than from a separate reproduction.

## Why the root cause implies it

ISS-343's leak lives entirely inside `CustomTemplateModal`'s `handleFetchUrl`
(`frontend/src/components/workflow/prototype/CustomTemplateModal.tsx:94-131`) plus the
backend catch-all it calls (`backend/app/api/prototype_templates.py:387-389`). That
component is not exclusive to the prototype wizard:

- `frontend/src/components/workflow/prototype/TemplateGallery.tsx:88` renders it — the
  reported route, `/create/prototype`.
- `frontend/src/components/workflow/ppt/PPTTemplateGallery.tsx:7-11,88` **imports the same
  `CustomTemplateModal` from the `prototype/` folder** (`from
  "@/components/workflow/prototype/CustomTemplateModal"` — not a forked copy) and renders it
  identically at `:88`.

Both galleries are mounted as interchangeable step bodies by
`frontend/src/components/workflow/WizardStepper.tsx`, whose own doc comment (`:11-20`) states
the stepper is "CHROME ONLY" reusing "Web -> `<TemplateGallery>`" / "Deck ->
`<PPTTemplateGallery>`". `WizardStepper` is mounted by
`frontend/src/components/workflow/LaunchWizard.tsx`, whose `STEPPER_MODE` map (`:73`) is
`{ prototype: "web", ppt: "deck", ppt_v2: "deck" }`, and `LaunchWizard` itself is what renders
at `/create/prototype` and `/create/ppt` (`frontend/src/app/workflow/create/page.tsx:24`,
`frontend/src/app/[...view]/page.tsx:3837`).

Because it is the literal same component instance — not a reimplementation — the exact same
`handleFetchUrl` (same 94-131 lines, same `authedFetch` call to
`/api/prototype/fetch-url`, same `setUrlError(data.detail || ...)` at `:110`) executes
whether the modal is opened from the prototype gallery or the PPT/deck gallery. Any input
that reproduces ISS-343 (an unreachable domain) must reproduce identically here, because the
code path is indistinguishable past the point where `WizardStepper` picks which gallery to
render.

## Expected vs actual (predicted, not yet reproduced)

- **Expected:** identical to ISS-343 — a friendly, human-readable message instead of raw
  Python/OS exception text.
- **Actual (predicted):** on `/create/ppt`, Template step -> "Upload custom" -> "From URL"
  tab, entering a syntactically valid but unreachable domain and clicking "Fetch" should
  surface the same `URL fetch failed: [Errno 8] nodename nor servname provided, or not
  known` text ISS-343 documented for `/create/prototype`, since it is the same function.

## What would confirm or refute this

Repeat ISS-343's exact repro steps (an unreachable domain, e.g.
`http://example.invalid.nonexistent-domain-xyz123/`), but starting from `/create/ppt`'s
Template step instead of `/create/prototype`'s: open "Upload custom template" -> "From URL"
tab -> paste the domain -> click "Fetch". A byte-identical raw-errno message confirms this
card; anything else (e.g. a gate that blocks the modal entirely on the deck path, or a
different error) refutes it and the root cause needs revisiting.

## Fix

No separate fix is needed at this file if [ISS-343](20260828-2059-ISS-343.md)'s fix lands in
the shared chokepoint (`backend/app/api/prototype_templates.py:387-389` and/or
`CustomTemplateModal.tsx:110`) — fixing the shared function automatically covers both
routes. This card exists so the `/create/ppt` route gets its own verification pass rather
than being assumed fixed for free, and so the fixer/verifier know a second route needs a
repro check before this can close.
