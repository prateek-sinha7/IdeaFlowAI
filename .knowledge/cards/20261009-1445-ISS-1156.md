## Analysis (analyze stage, 2026-10-09)

**Answer to the open question.** These runs did not execute the built-in `ex_A1_loop`. They executed admin@velocity.ai's SAVED OVERRIDE "My ex_A1_loop" (`workflows.id = bdf009f2-8545-4579-81a3-96391402b713`, `override_enabled` true, created 2026-10-09 07:39:03 UTC by an e2e test, [ISS-1183](20261009-1708-ISS-1183.md)). A canvas Run once of an unmodified built-in sends only `pipeline_type` (`ComposerPage.tsx:1199-1230`; the run rows have `selections_json` and `manifest_json` = JSON null), and the launch then swaps in the caller's enabled override (`run_commands.py:3650-3690`; the :8001 log says `override: run launching ex_A1_loop from user 2d626ad9-... saved override bdf009f2-...` at 13:41:56, the reporter's run 9a931a7a). The prompt `check` received is therefore neither the canvas text nor the built-in's; and the "deliver via write_file" instruction the validator saw on `emoji` is the clue to everything below.

Both of the reporter's hypotheses are refuted. Haiku follows the prompt: in all four failing runs `check` made the CORRECT judgement, `{"decision": "retry"}`, and wrote it to a file. The canvas did not lose the prompt: the override carries it verbatim. A prompt edit cannot reach the failure either: the built-in already passes, and the stored row holds its own copy of the prompt.

### Root cause

1. **The stored plan is not the built-in.** `evidence/qa-kb-124/analysis-04-plan-comparison.txt` (compile + `merge_override_steps`): built-in steps are `read_files false, write_files false`, `greet produces [greeting]`, `check consumes [greeting]`, `done consumes [greeting]`, `depends_on` greet<-emoji, check<-greet, done<-check. The merged override has `read true, write true` on all four, and `produces`/`consumes` for `greeting` and the greet and done `depends_on` are gone. The merge replaces the file plan's steps wholesale (`overrides.py:219`, module docstring "an override row supplies `steps` and nothing else").
2. **A write grant switches on a delivery contract.** `factory._compose_system_prompt` appends `## How to deliver ... Call write_file with path <step>-<slug>.md. Its content is your answer - never this instruction.` to every custom-agent step with `has_write_access` (`factory.py:460`, `:727-731`). It never asks whether the step's reply IS a typed decision. The recorded system prompt of `check` in run c10a03ed ends with that block (`evidence/qa-kb-124/analysis-02-...txt` section 9).
3. **The gate reads only the reply.** The engine writes the typed `route_decision` artifact from the step output (`engine.py:10616`, `:10791-10801`), and `ConditionalGate._read_decision` parses that (`conditional.py:226-258`). The file the step wrote is never read.
4. **Haiku obeys the contract.** In all four failing runs `check` read the greeting with `read_file`, called `write_file("/check-<slug>.md", '{"decision": "retry"}')`, and replied with narration of 83, 84, 32 and 30 characters ("I need to read the greeting file first.Now I'll write my answer to the output file:" and the three prose lines in the table above). `analysis-02` section 3.
5. **No decision, no default_next, run ends.** `outcomes.get(None)` misses, the route declares no `default_next`, so `GATE_BLOCK` (`conditional.py:185-206`), and the engine's ISS-170 arm fails the run (`engine.py:6779-6784`): "Check's conditional gate had nowhere to route", `published_status` degraded.
6. **Control: the same model passes on the built-in plan.** Bedrock run `83001c0b` (2026-10-07 15:35 UTC, cache tokens > 0): `check` replied exactly `{"decision": "retry"}` and then `{"decision": "ok"}`, the gate routed retry -> greet pass 2 -> ok -> done (`analysis-02` sections 4-5). Built-in steps are tool-free, so there is no delivery block (`factory.py:727` guard), and `consumes: [greeting]` makes the engine paste the greeting because the step cannot read files (`engine.py:16747-16758`; the L4 regression that `test_consumes_delivery_v3.py` pins). The reporter's "completed on local Ollama" run `32bbde34` (07:18 UTC) predates the override row and shows cache tokens 0/0; the discriminator between pass and fail is the plan, not the provider.

Run `1260b7ba` adds one more symptom of the same cause: `greet` wrote its greeting to a file and replied with nothing (`output_length` 0), so any step that relies on a reply (`done`) sees an empty one.

### Where the fix belongs

1. **Runtime, in the one function every authoring path reaches:** `factory.py:727`. Do not append the delivery block when the step's reply is a typed decision: `"route_decision" in (getattr(spec, "produces", None) or [])`, the predicate `engine.py:10663` already uses to keep the single_file readback away from a decision step. `_specs_from_plan` overlays the step's `produces` onto the spec (`engine.py:4029-4032`), so it is available. `_check_artifact_fallback` still writes the reply to the artifact file when the model wrote none, so ADR-0011's filename contract holds. Optionally replace the block for such a step with one line telling it to answer in its reply, which is what the hand-written sentence in `ex_A2/A3/A4` prompts does today (INFERRED to be stronger). This is the prompt-first fix: the instruction that causes the failure is a prompt template in the factory.
2. **Writer:** `userWorkflows.ts:336-340`, `?? agent.tools?.read_files ?? true` ([ISS-1181](20261009-1708-ISS-1181.md)); then ISS-1128 for the dropped keys.
3. **Data and tests:** disable or delete the nine rows and make the e2e saves clean up ([ISS-1183](20261009-1708-ISS-1183.md)). Without item 1 this only hides the defect.
4. Optional parity: give `ex_A1_loop`'s `check` the sentence the other four fixtures carry. It changes nothing for the failing runs (they use the stored copy) and nothing for the built-in (no write tool).

Not these: a `default_next` on `check` (a correct `retry` would become `GATE_PASS`, advance to `done` and skip the loop: the ISS-170 mis-route, and the fixture's header says an unrecognised decision must terminate); making the gate read the sandbox file (the hazard `engine.py:10651-10660` describes; the gate has no sandbox access by design); stripping grants from an override at launch (silently changes the user's saved version).

## Re-analysis (QA-KB-124, 2026-10-09)

### The fixer's finding, confirmed

The step's declared `produces` lives in one place a run can see: the engine's own spec objects. `_specs_from_plan` overlays it (`engine.py:4034-4035`, `overlay["produces"] = list(s.produces)`) and the engine reads it from there for its own decisions: the single_file readback guard (`_is_decision_step`, `engine.py:10668`) and the typed `route_decision` write (`:10797`). The factory never receives that object. The engine calls `create_runner(spec.id, ctx, ...)` (`:9955`; the throttle retry reuses the same `ctx`, `:10501`) and `create_runner` reloads by id (`factory.py:350`). For `custom-agent:<id>` the loader returns the blank template with only the id swapped and caches it by id for the whole process (`loader.py:164-167`), and `prompts/custom-agent/AGENT.md:1-11` declares no `produces`. `AgentContext` (`factory.py:31-157`) has no such field, and the engine builds it at `engine.py:9749-9865`, threading `step_injects`, `step_skills`, `step_prompt`, `step_tools` and `deliverable_filename_override` off the compiled step but not `produces`. So at `factory.py:727`, `spec.produces` is `[]` for every composed step on every dispatch. The engine knows the fact; the factory is the one reader that cannot.

### Where the fix belongs (replaces item 1)

One seam, two files, the seam the other per-step inputs already use. The thing being changed is a prompt block (`factory.py:727-731`), so the standing prompt-before-code rule is honoured; items 1 and 2 are plumbing that lets the block depend on a fact only the engine holds, not new enforcement:

1. `backend/agents/execution_engine/engine.py:9852`, in the `AgentContext(...)` call next to `step_tools=`: `step_produces=list(getattr(spec, "produces", None) or [])`. It must read the SAME `spec` that `:10668` and `:10797` read, so the readback guard, the artifact kind and the prompt guard cannot disagree (the rule `_deliverable_filename_override`'s docstring records: two consumers of one fact, one definition). This is the only construction site a decision step passes through: serial dispatch, loop re-entry, resume (`_specs_from_plan` at `:15773`, `:15812`, `:16300`, `:16336`), the route trigger (`kernel_services.py:1602`) and fan-out workers all reach `_run_agent`. The other `AgentContext(` sites (`kernel_services.py:2134`, the validation fix-loop; `chat_runner.py:131`; `evals/minimal/run.py`) build contexts for steps that cannot be a gate's decision source and keep the default `[]`.
2. `backend/agents/factory.py`: a field `step_produces: list[str] = field(default_factory=list)` on `AgentContext`, and at `:727` `if has_write_access and "route_decision" not in <spec.produces + ctx.step_produces>:`. The union mirrors how `step_injects` merges with `spec.injects` at `:608-610`. Keyed on the declared artifact kind, never a workflow or agent name (SC-001, INV-1; `engine.py:10668` is the precedent). The marker cannot be dodged by omission: R-27 (`compiler.py:1851-1870`) refuses to compile a conditional route whose decision source does not declare `produces: ["route_decision"]`, so every compile-valid plan carries it, override, Composer row and inline manifest alike.
3. Optional, same edit, prompt-first: give such a step one sentence in place of the block, under a different heading, for example `## How to answer`: "Your reply is your answer: the next step reads your reply, not a file. Do not write it to a file." INFERRED to be stronger than omitting alone. The four shipped route fixtures carry that sentence in their step prompts, but always next to the block (run `41f50ae1`: the step wrote the file anyway and routed only because its reply also ended in the JSON), so the sentence has never been tried alone on a write-granted step.

The scratch diff is `evidence/qa-kb-124/analysis-07-candidate-fix.diff`: 11 added lines (5 of them comments), 1 removed.
