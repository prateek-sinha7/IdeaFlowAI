## What happened

Validated `BUG-20260828-050115-library` (bug-hunter/ledger.md) — reproduced **3/3, all cold
starts** (fresh navigation, no prior page state):

- Cycle 1: cold-loaded `http://localhost:3000/library/agents/dotnet-inventory` — full detail
  dialog `.NET Solution Inventory Agent details` opened with Overview/Skills/Hooks/Config tabs;
  Config tab shows live Model/Validator/Before-execute-gate/After-execute-gate/Retry controls, a
  Reset button, and an enabled "Save agent" button.
- Cycle 2: cold-loaded `http://localhost:3000/library/agents/mulesoft-springboot-scaffold`
  (a second, unrelated "Coming Soon" pipeline) — same result: full dialog opened
  (`h2` = "Spring Boot Scaffold Agent").
- Cycle 3: repeat of cycle 1 from a fresh `/dashboard` → direct-URL cold load — same result.

Evidence: `bug-hunter/evidence/library/_scratch/cycle1-01-dialog-open.png`,
`cycle1-02-config-tab.png` (Config tab with enabled "Save agent"),
`cycle2-01-second-agent.png`, `cycle3-01-agent1-repeat.png`.

Meanwhile the catalog grid itself correctly renders both agents as
`opacity-60 cursor-not-allowed` with a "Coming Soon" badge and no click target — confirmed by
reading the grid's own onClick guard.

## Root cause

`frontend/src/components/library/LibraryPage.tsx`:

- Line 27: `BETA_WORKFLOWS` is the set of unreleased pipeline ids (includes `dotnet_to_azure`,
  `mulesoft_to_springboot`, etc.).
- Line 742 (grid card `onClick`): correctly guards — `if
  (!BETA_WORKFLOWS.has(getPrimaryPipelineType(agent.pipeline_type))) { setSelectedAgent(...);
  router.push(...) }` — so clicking a Coming-Soon card is a no-op.
- **Line 518-526 (the T15 cold-mount URL-seed effect, added by spec 015-frontend-routing to open
  the detail modal directly from `/library/agents/{id}` on a cold load) has no equivalent guard**:
  ```
  useEffect(() => {
    if (!librarySlug || librarySlugAppliedRef.current) return;
    if (librarySlug.type === "agents" && agentsStatus === "succeeded") {
      const agent = ALL_AGENTS_COMBINED.find(a => a.id === librarySlug.slug);
      if (agent) {
        setMainTab("agents");
        setSelectedAgent({ agent, index: ALL_AGENTS_COMBINED.indexOf(agent) });
        librarySlugAppliedRef.current = true;
      }
    } ...
  ```
  It looks the agent up by id and opens the drawer unconditionally — it never checks
  `BETA_WORKFLOWS.has(getPrimaryPipelineType(agent.pipeline_type))`. Two independent entry paths
  into the same `setSelectedAgent` state (a click and a URL cold-load) enforce the gate in only
  one of them.

## Expected vs actual

Expected: an agent id inside `BETA_WORKFLOWS` should be unreachable by direct URL too (redirect
to `/library`, or render a locked/unavailable state), matching the card's own click-blocking.

Actual: the URL-seed effect opens the identical fully-interactive drawer — including a live,
enabled "Save agent" button on the Config tab — for any `BETA_WORKFLOWS` agent id, with nothing
in the drawer indicating the agent is unreleased.

## Reproduction conditions

- Tier: qa-admin (not tier-specific — the gate is per-agent-id, not per-account).
- Entry path: direct cold URL load to `/library/agents/{beta-agent-id}` (bookmark, shared link,
  browser history, or incrementing through `GET /api/agents/library`'s own payload).
- Confirmed on two unrelated beta pipelines (`.NET to Azure` and `MuleSoft to Spring Boot`), so
  the gap is systemic to the effect, not specific to one agent's data.

## Analyzer confirmation (ANALYZED pass on BUG-20260828-050115-library)

**CONFIRMED, re-read at HEAD.** The mechanism above still holds; only the line numbers moved
(intervening commits, e.g. `FIX-333`'s `CARD_KEYBOARD_PROPS`, shifted offsets). At the commit this
analysis was done from, the cold-mount effect is `LibraryPage.tsx:589-614` (agents branch
591-597), and the grid's `BETA_WORKFLOWS` guard is at `LibraryPage.tsx:815` (plus five more
`BETA_WORKFLOWS.has(getPrimaryPipelineType(...))` call sites in the same grid render:
lines 685-686, 826, 828, 842-843, 849). Re-reading the effect confirms it takes exactly one
`if`/`else if`/`else if` shape across agents/skills/hooks, one function, not three.

**Blast radius — every consumer of this gate, grepped, not assumed:**
- `frontend/src/components/library/LibraryPage.tsx` (this card, agents branch) — the reported bug.
- `frontend/src/components/library/LibraryPage.tsx` skills branch (`:598-604`) — **same missing
  check, sibling defect, filed as [ISS-416](20260828-2210-ISS-416.md)** (INFERRED — mechanism
  confirmed by code read, live reproduction currently blocked because no skill in this dataset
  has `isBeta: true`; see that card).
- `frontend/src/components/library/LibraryPage.tsx` hooks branch (`:605-611`) — checked and
  **ruled out**: the hooks grid applies no `isBeta` filter at all (`filteredHooks`, `:702-708`,
  rendered `:990-1022` with a real `onClick` on every card regardless of `isBeta`), so there is no
  click-gate for the URL path to bypass. Not a sibling of this defect.
- `frontend/src/components/workflow/AgentLibrary.tsx:68` — an **independently duplicated** copy of
  the same `BETA_WORKFLOWS` set, gating its own Info/+Add buttons via a real `disabled` attribute
  (`:239,250,258,295,297`). Checked and **ruled out** as a sibling: `grep -rln
  "useSearchParams\|useParams" frontend/src/components/workflow` returns nothing — this component
  has no URL-seed entry point at all (it only opens via local `isOpen` prop from its parent), so
  there is no direct-URL path into it to bypass. Worth noting as a DRY smell (`BETA_WORKFLOWS`
  hand-copied verbatim in two files that could drift), but not this bug's mechanism.

**Where the fix belongs.** Both broken branches (agents, skills) already live inside the ONE
`useEffect` (`LibraryPage.tsx:589-614`) that is the sole entry point for every direct-URL /
bookmark / shared-link / browser-history open of a Library detail item — the grid's `onClick`
handlers are a separate, already-correct path and don't need to change. The fix is two guard
conditions added inside that existing effect, not a new helper and not a change per caller:
- agents branch: `if (agent && !BETA_WORKFLOWS.has(getPrimaryPipelineType(agent.pipeline_type)))`
- skills branch: `if (skill && !skill.isBeta)`

**Open question for the fixer, not resolved here:** when the found item IS beta, simply not
setting `librarySlugAppliedRef.current = true` leaves the URL pointing at
`/library/agents/{beta-id}` while the bare catalog listing renders underneath with no feedback —
the same silent-fallback shape `ISS-232`/`FIX-340` already had to fix once for a different cause.
This card's own "Expected" already names the two acceptable outcomes (redirect, or a visible
locked state); `closeDetailModal` (`LibraryPage.tsx:622-628`) is the existing
`router.push(routes.library(...))` pattern to reuse for the redirect option if that's the direction
chosen.
