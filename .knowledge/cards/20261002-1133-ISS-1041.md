# ISS-1041

Sibling of [ISS-945](20261002-0053-ISS-945.md), found by the QA-KB-087 analysis on 2026-10-02 with the same scan as
[ISS-1039](20261002-1131-ISS-1039.md) (every `it.fails` file in `frontend/src` run with the marker removed, on copies outside the repo;
`evidence/qa-kb-087/07-analyze-itfails-scan.txt`). Confidence: CONFIRMED by that run and by two follow-up probes; no repo file was
edited. This one belongs to a bug that is already closed (QA-PS-049, [FIX-636](20260922-2352-FIX-636.md)), so nothing is stuck behind
it: it is a leftover that reports "expected fail" for a defect that no longer exists. A validator re-run is still pending.

## Why the root cause implies it

Same class as [ISS-945](20261002-0053-ISS-945.md): an `it.fails` case that never reaches the assertion it was written for, so it
cannot show the XPASS that marks its bug fixed. The channel it reads is a `vi.mock("@/lib/api")` spy on `getRunArtifacts`, but the
component loads the module with a dynamic `import("@/lib/api")` inside its effect (`ArtifactVersionPicker.tsx:123`), and under vitest
the second, concurrent import of a factory-mocked module resolves to the REAL module. The repo's own
`ArtifactVersionPicker.iss802.network.test.tsx` says so in its header and counts requests at `fetch` instead.

## Condition

Remove `it.fails` from the case (on a copy; the repo file stays) and run it. The case mounts the picker under `<React.StrictMode>`.

## Expected

The spy counts the list fetches per agent selection: 2 before [FIX-636](20260922-2352-FIX-636.md), 1 after.

## Actual

After FIX-636 (the shipped component, `if (cancelled) return;` at `:126`): `AssertionError: expected "vi.fn()" to be called at least once`
at the first `waitFor`, after about 1.03 s, with an empty DOM. A trace on a mirror-only copy of the component shows why: setup A,
cleanup A, setup B; A resumes with `cancelled = true` and bails; B resumes with `cancelled = false`, but its `await import("@/lib/api")`
returned the real module, so `getRunArtifacts` is the real one and throws `ApiError: Not authenticated` into the effect's `catch`. The
spy sees nothing (0 calls over 200 ms). A plain mount without StrictMode reads 1.

Before FIX-636 (the same component with the `:126` line removed) the case, marker removed, passes with the spy at 1 (61 ms), while two
requests went out. So the case was never red for the double fetch: it reads 1, then 0, never 2, and `it.fails` hides both.

## Evidence

`evidence/qa-kb-087/08-analyze-itfails-wrong-reason-probes.txt`, section S-C. The network test, run as a real copy against the pre-fix
effect, fails with both URLs (`expected [ ...(2) ] to have a length of 1 but got 2`) and passes in place against the shipped component
(1019 ms). The legacy file in place: `Tests 1 passed | 1 expected fail (2)` together with the network test.

## Fix direction

Test file only; `ArtifactVersionPicker.tsx` is correct and stays untouched.

1. Delete `frontend/src/components/results/ArtifactVersionPicker.iss802.test.tsx`. Its guard is
   `ArtifactVersionPicker.iss802.network.test.tsx`, which discriminates 2 from 1. Moving the legacy case to count at `fetch` would
   duplicate that test, and a spy on a factory-mocked `@/lib/api` cannot work here.
2. If the team would rather keep the file, the marker must still go and the assertion must move to `fetch`.

For the 4-test-writer: the red test is the file's existence, e.g. an `it.fails` case asserting
`existsSync(resolve(__dirname, "ArtifactVersionPicker.iss802.test.tsx"))` is false (it flips to XPASS when the file is deleted, and the
verifier then removes `.fails`). When this closes, append a one-line resolved note to ISS-802 and FIX-636; do not rewrite them.

## Status after the QA-KB-087 fix (2026-10-07): still open

[FIX-744](20261007-2029-FIX-744.md) fixed the three sibling harnesses and left this card open, with no repo file edited for it.
The 5-fixer re-ran the probes on scratch copies (`evidence/qa-kb-087/fix-06-probe-iss1041.txt`; scripts in `fix-probes/`).

**Holds.** The mechanism is right: the spy reads 1 on the pre-FIX-636 picker and 0 on the shipped one, never 2. The fix
direction also holds:

- The `.network` test passes on the shipped picker.
- It fails on the pre-fix picker with
  `["http://localhost:8000/api/runs/r1/artifacts","http://localhost:8000/api/runs/r1/artifacts"]: expected [ …(2) ] to have a length of 1 but got 2`.
- Deleting the legacy file loses no protection.

**Correction.** The title's "can be neither red nor green" and the line "`it.fails` hides both" do not hold for the file as
shipped. Under `it.fails`, a reading of 0 makes the body throw, which shows as `1 expected fail` on the shipped picker. A reading
of 1 makes the body complete, which shows as a red `Expect test to fail` on the pre-fix picker (`legacy_asshipped_*`). So the
legacy file is a live tripwire for an ISS-802 regression, but it trips for the wrong reason (a spy count of 1, not 2) and with a
misleading message. It is not inert. That strengthens the case for deleting it rather than weakening it.

**Also stale.** The `.network` test's header says the legacy file "reads 1 with or without the fix". It reads 0 on the
shipped picker.

**Why not deleted here.** The legacy file is tracked and indexed:

- `.knowledge/architecture/MOD-frontend-src-components-results.md:38` links to it, in the generated section.
- `.knowledge/architecture/files/frontend/src/components/results/ArtifactVersionPicker.iss802.test.tsx.md` exists for it.

Deleting the file leaves two dead links that only the architecture rebuild clears. That rebuild also rewrites every DOMAIN
card's generated half and `modules.json`, which is the user's sync to run, not a bug fix's.

**To close.** Delete the file and run the full rebuild in the same pass. Nothing is blocked meanwhile: QA-PS-049 is closed,
and the legacy file still reads `1 expected fail` in place (`evidence/qa-kb-087/fix-01-before.txt` B6).
