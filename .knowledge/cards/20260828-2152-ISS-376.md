## What is suspected

[ISS-250](20260828-1645-ISS-250.md) root-caused `/workflow/create` never canonicalizing for a
missing/empty `mode` to `frontend/src/proxy.ts:8`'s `if (mode)` — a truthy check that silently
passes `null`/`""` straight through to `frontend/src/app/workflow/create/page.tsx`'s
`CreateRoute()` with no fallback destination. That analysis also established, by reading both
files, that `CreateRoute()` itself carries **zero canonicalization logic of its own**:

```ts
const raw = searchParams.get("mode");
const mode: LaunchMode =
  raw === "ppt" || raw === "ppt_v2" ? raw : "prototype";
return <LaunchWizard initialMode={mode} />;
```

For ANY `raw` that is not exactly `"ppt"` or `"ppt_v2"` — not just `null`/`""`, but also a typo,
a stale/garbage value, or any future mode the edge layer doesn't yet recognize — this silently
renders the full "prototype" wizard in place, with no `router.replace`, no error state, and no
signal that the URL never canonicalized. The entire system currently canonicalizes correctly
only because `proxy.ts` intercepts and redirects every truthy `mode` before this component ever
mounts (confirmed live by [ISS-227](20260828-1554-ISS-227.md)'s browser reproduction). `page.tsx`
was never designed as a second line of defense — it is a passthrough content renderer for
whatever `proxy.ts` chooses not to redirect, and it has no way to tell "legitimately missing
mode" apart from "proxy.ts didn't run for this request."

## Condition

Any request that reaches `CreateRoute()` without first passing through `proxy.ts`'s redirect —
i.e. any gap where the edge middleware does not execute (or does not match) for a request whose
final rendered route is still `frontend/src/app/workflow/create/page.tsx`. Candidates, none yet
confirmed: a build/deploy topology where edge middleware is skipped for a given request class
(e.g. a cached/static response, a CDN layer in front of the Next.js server), or a future request
shape whose `pathname` fails `proxy.ts`'s exact-match `matcher: ["/workflow/create"]` (a trailing
slash, different casing) while still resolving to this same page route.

## Expected vs actual

**Expected:** `CreateRoute()` never silently renders full application content for a `mode` it
cannot resolve to a definite deliverable family — either it canonicalizes itself, or it fails
visibly, regardless of whether `proxy.ts` ran first.

**Actual (predicted):** for any `raw` value it cannot resolve, `CreateRoute()` defaults straight
to the "prototype" wizard with no navigation and no indication anything is unresolved — the same
observable defect as ISS-250 (URL never canonicalizes, silently renders live functional content
underneath the stale route), reachable independently of whether `proxy.ts`'s redirect fires.

## Why the root cause implies this — and why it is a distinct defect, not the same report

ISS-250 was reproduced and filed specifically against `proxy.ts:8`'s falsy branch, reached via a
normal direct navigation where the edge middleware DOES run (it always does for the two trigger
shapes ISS-250 tested — a bare URL and `?mode=`, both still hit by `proxy.ts` first and simply
fall through its own falsy branch by design). This card is about the layer beneath that: what
`CreateRoute()` does on its own, independent of `proxy.ts` running at all. The mechanism is the
same class of defect (a route with two independent "should I canonicalize" decision points, only
one of which has any logic in it) but it is a different code path — fixing `proxy.ts`'s falsy
branch (ISS-250's proposed fix location) closes the reported symptom without touching this gap,
since `CreateRoute()`'s own lack of a fallback is untouched by that fix.

**Marked INFERRED**: this has not been reproduced — no evidence has been gathered that `proxy.ts`
is ever actually bypassed for a live request to `/workflow/create` in this app's current
deployment. What is CONFIRMED (by reading `frontend/src/app/workflow/create/page.tsx` in full,
39 lines) is that `CreateRoute()` has no canonicalization logic of its own to fall back on if it
ever is. What would confirm or refute this as a live defect: a component-level test that renders
`CreateRoute()` directly (bypassing the dev server, and therefore `proxy.ts`, entirely — e.g.
React Testing Library rather than an E2E/Playwright test against the running app) with an
unrecognized `mode`, and checks whether the render is silent or errors/redirects; separately,
inspecting the production build's middleware manifest to confirm `proxy.ts`'s matcher is applied
to every deployed request path that can resolve to this page, not just the dev server used for
ISS-227's and ISS-250's browser reproductions.
