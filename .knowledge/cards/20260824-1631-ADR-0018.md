# ADR-0018

## Decision

In the context of ten screens that all lived at `/dashboard` with the current screen held
only in component state — so refresh lost your place and nothing could be bookmarked or
shared — we decided to give every screen a real URL, with `routes.ts` as the single source
of truth for both directions (typed builders out, `parseViewPath()` back in), and to render
all 34 screens behind ONE required catch-all segment, to achieve addressable screens
without splitting a 2,862-line page into per-route files, accepting that the page component
stays large.

**Area:** frontend, routing

## Why one catch-all rather than per-route segments

Splitting the shared page into per-route file segments was considered and explicitly
placed out of scope: the screens share a single layout and a large amount of live run
state, and fragmenting them would have multiplied that state across route boundaries for
no navigational gain. The catch-all keeps one tree while still giving each screen a URL.

The `[...view]` vs `[[...view]]` choice is not stylistic. The optional form conflicts with
the root `page.tsx` at the same specificity — a real bug hit early in this work.

## Why a single source of truth, enforced

Path literals scattered through components are how URL schemes rot: a rename fixes the
builder and misses six call sites. Treating a literal outside `routes.ts` as a defect was
enforced across every verification pass of this spec, and it is what makes
`parseViewPath()` trustworthy as the inverse — the two cannot drift if only one file
knows the shape.

The corollary matters for anyone adding a screen: an unrecognised path must resolve to a
typed screen (even a generic one), never fall through to `unknown`. A dynamic catalog type
falling through to `unknown` is precisely what made `/create/{type}` 404 on cold load
while working on click.

## Why the proxy exists alongside next.config redirects

`next.config.ts`'s static `redirects()` handles the simple cases (bare `/library` →
`/library/agents`). It genuinely cannot handle `/workflow/create?mode={t}` → `/create/{t}`
without leaking the query string onto the destination — a Next.js 16.2.4 limitation, not a
config mistake. That one case is why `proxy.ts` exists, and it must live inside
`src/` for this project's tsconfig layout. (It was `middleware.ts` until
1c98a7924 renamed it to Next.js 16's `proxy` convention — same file, same
job, new name.) It was deliberately left UNFIXED until
root-caused rather than forced with a workaround.
