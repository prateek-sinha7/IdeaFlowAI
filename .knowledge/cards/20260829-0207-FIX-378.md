## What was wrong

`BUG-20260828-084621-runs-id-preview-full`: on `/runs/{id}/preview/full` for a completed ppt run at
a 375px viewport, the Preview tab bar's action cluster — "Download" and "Full Screen"
(`title="Open in new tab"`) — rendered entirely to the right of the visible viewport. The validator
measured the Full Screen button at `left: 400.02, right: 493.38` against `window.innerWidth: 375`,
3/3 on cold navigation, with `document.documentElement.scrollWidth === clientWidth === 375` — no
horizontal scroll anywhere in the ancestor chain, so no pointer or touch could ever reach it.

## Root cause

`frontend/src/components/preview/PreviewPanel.tsx:1203` — the tab-bar row
(`flex items-center justify-between gap-2`) is a single non-wrapping flex line holding the `Tabs`
list on the left and the action cluster on the right. Neither that row, nor the right-cluster
wrapper at `:1221` (`flex items-center gap-2`), nor `PPTTabActions`' own row at `:1540`
(`flex items-center gap-1.5 flex-shrink-0`) sets `flex-wrap` or `overflow-x`, and `flex-shrink-0`
blocks the last of them from shrinking. At 375px the row's content box is 315px wide
(`px-[30px]`) while its content measures ~463px (`Tabs` ~258px + `gap-2` + actions ~197px), so
everything past the overflow point simply left the viewport with nowhere to go — as
[ISS-314](20260828-1946-ISS-314.md) recorded at `file:line`. Re-read against the working tree
before editing; the mechanism still held (line numbers had shifted from the card's original
1450/1474-1481 under later commits — same code).

## Blast radius, re-confirmed before editing

- `PPTTabActions` has exactly one render site: `PreviewPanel.tsx:1230`, inside the right cluster of
  that one row (`grep -rn "PPTTabActions" frontend/src`).
- `PreviewPanel` has exactly one production call site: `DashboardLayout.tsx:3127` (`grep -rn
  "<PreviewPanel" frontend/src` — every other hit is a `*.test.tsx`). That call site sits in a
  `flex flex-col md:flex-row` split that stacks to full width below `md`, so the same defect
  reproduced on the plain `/runs/{id}` route too. Both routes mount this one row, so one edit fixes
  both — there is no second toolbar to patch.
- `PreviewPanel.tsx` has exactly two flex rows in the toolbar chain (`:1203` and `:1540`); the fix
  is on the outer, shared one, so a future renderType's action cluster dropped into the right
  cluster inherits it without its own change.
- No test asserts the row's class string (`grep -rn "flex-none px-\[30px\]\|justify-between gap-2"`
  over `frontend/src` `*.test.tsx` → no matches).

## What changed and why there

One line. `frontend/src/components/preview/PreviewPanel.tsx:1203` gains `flex-wrap`:

```tsx
<div className="flex-none px-[30px] pt-4 flex flex-wrap items-center justify-between gap-2 border-b border-line-divider">
```

At 375px the `Tabs` list (~258px) still fits the 315px content box, so the action cluster wraps onto
a second line and Full Screen lands at a right edge of ~219px — inside the viewport, clickable,
with no scrollbar introduced. `gap-2` already supplies the 8px row gap the wrap needs. At every
width where both children fit on one line the rendering is byte-identical to before, which is why
the wrap went on the row rather than on `PPTTabActions`: shrinking or scrolling the action cluster
would have changed the desktop presentation and still left a future second cluster broken.

Nothing else changed. No backend file, no test file, no migration, no import edge.
