## Why this must also be broken

[ISS-293](20260828-1924-ISS-293.md) established that nothing enforces the UI's displayed "4000
chars" limit on Constitution content: the `<textarea>` has no `maxLength`, `Save constitution`
never disables past 4000, and the only enforcement anywhere is the backend's
`ConstitutionRequest.content` `Field(..., min_length=1, max_length=1_048_576)`
(`backend/app/api/settings.py:355`) — a completely different, ~1 MiB ceiling. That number is not
arbitrary: `specs/001-ai-workflow-os/spec.md:224-227` (FR-012) specifies "value: up to 1,048,576
chars" as the actual Workflow_Memory contract, and the implementing tasks T074a/T074b
(`specs/001-ai-workflow-os/tasks.md:208-209`) only ever asked for a "free-form textarea" — "4000"
appears in no spec, no task, and no backend code. It is a UI-only invented constant. ISS-293's own
scope stops at the Settings page; it does not follow the saved content to where it is actually
consumed.

That consumption is unconditional and equally unguarded. `_inject_constitution`
(`backend/agents/factory.py:673-699`) reads:

```python
def _inject_constitution(ctx: AgentContext) -> str:
    constitution = getattr(ctx, "prewarmed_constitution", None)
    if not constitution:
        return ""
    return (
        "## Constitution (Governing Principles — Supreme Authority)\n\n"
        f"{constitution}\n\n"
        "## End Constitution\n\n"
        "The above Constitution governs all your outputs. Any finding that "
        "conflicts with these principles is CRITICAL."
    )
```

and is called unconditionally inside `_compose_system_prompt` (`backend/agents/factory.py:586`)
— i.e. for every governed agent, on every pipeline run, for the owning user. `constitution` here
is the full, verbatim saved value: `ctx.prewarmed_constitution` is populated once per run by
`await get_workflow_memory().get_constitution(user.id)` (`backend/agents/execution_engine/engine.py:1821`),
and `WorkflowMemory.get_constitution` performs no truncation on read (only `_set` caps on write,
at the same 1,048,576 ceiling — `backend/agents/workflow_memory/memory.py:26,208-210`). Nothing
between the DB read and the composed prompt string applies a length check, a token budget, or a
truncation marker. Contrast with this codebase's own documented pattern for exactly this class of
problem elsewhere — `.planning/STATE.md:459` describes `od_context.get_example_html` /
`EXAMPLE_MAX_CHARS` as "the ONLY place example.html is capped," a deliberate single-truncation
point precisely because an unbounded injected block is a known failure mode here. Constitution has
no equivalent guard anywhere in its path.

## Expected vs actual

**Expected:** a per-user Constitution well over the size the UI implies (already proven saved up
to 6,015 chars in ISS-293's own reproduction, and acceptable up to 1,048,576 per the backend's real
cap) either gets bounded/summarized before injection, or the user is warned that an oversized
constitution will inflate every future run's prompt — not injected silently, in full, into every
agent, every run.

**Actual (INFERRED — not yet independently reproduced against a live run):** because the save path
enforces nothing close to 4000 and the injection path enforces nothing at all, a user who fills the
editor with content in the tens- or hundreds-of-thousands-of-characters range (a plausible accident
— pasting a document into a box that visually claims a 4000-char cap) gets that entire block
silently prepended to every agent's system prompt on every subsequent run: larger prompts, higher
token cost, and more context-window pressure for every agent in every pipeline, invisibly, until a
run degrades or fails for a reason that traces back to a Settings-page save, not to the pipeline
that actually failed.

## What would confirm or refute this

Save a constitution in the tens-of-thousands-of-characters range (mirroring ISS-293's oversized-
payload technique), launch any pipeline run for that user, and inspect either the composed prompt
size in the `agents.factory` DEBUG log (`compose_prompt %s: %d slots -> ~%d chars`,
`backend/agents/factory.py:666-669` — count/chars only, never the body) or the Thinking tab's "full
input prompt" (FR-015, `specs/001-ai-workflow-os/spec.md:235-236`). Expected-per-this-card: the
composed size scales up by roughly the saved Constitution's length with no cap. A miss — e.g. a
truncation marker appears, or composed size stays flat — would refute this card without affecting
[ISS-293](20260828-1924-ISS-293.md).

## Where the fix belongs

Two different fixes, two different places — this card's fix must NOT be folded into ISS-293's:

- ISS-293's fix (the fictitious counter) belongs in `ConstitutionSection`
  (`frontend/src/components/settings/AccountSettings.tsx`) — align the displayed number, the
  textarea's `maxLength`, and the Save-disable check to whichever real cap is chosen.
- This card's fix belongs downstream, in the injection path itself. `_inject_constitution`
  (`backend/agents/factory.py:673-699`) is the ONE place every governed agent's Constitution block
  is assembled, for every pipeline, with no `if pipeline_type` branch — a defensive size cap or
  truncation-with-marker belongs there, once, not copied into any of the ~80 `AGENT.md` prompts or
  any pipeline manifest. One guard in this shared function is a smaller diff than one in every
  agent, and it protects every current and future workflow the same way ISS-293's frontend fix
  protects only the Settings page.
