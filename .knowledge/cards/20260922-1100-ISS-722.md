# ISS-722

## Title

Run detail page's "Pipeline running · X / N" header shows N=0 (rendering "0 / 0") for a freshly-created run whose agent count is already known to be 5 elsewhere, because the header's total is derived from a different, still-empty data source than the notification panel's total. Corresponds to QA-SG-001.

## Reproduction — 3/3, cycle 1 (reproduced on every cold-start attempt, no narrowing needed)

1. Sign in as `qa-admin@flowinqa.com`.
2. Launch a prototype run via `/create/prototype` with a brief (5-agent pipeline). `POST` creates the run with `agent_count: 5` in the run record immediately (confirmed via `GET /api/runs?limit=1`).
3. Cold-navigate directly to `/runs/<id>` (fresh `page.goto`, not a soft in-app nav) while the run is in `planning`/early `generating` state.
4. On the run detail page, the "Pipeline running" header (`StepsOverviewSpine.tsx`) reads **"Pipeline running · 0 / 0"**.
5. Open the bell-icon Notifications panel (global, route-independent) — the SAME run's card reads **"0 of 5 agents / 0%"**.

Both surfaces are reading the SAME run, at the SAME wall-clock moment, and disagree on the total (0 vs 5).

## Root cause

Two independent sources feed "total agents" for the same run, and only one of them is populated this early:

- `StepsOverviewSpine.tsx:403` — `const total = agents.length;` — used at `:461` to build the label `` `Pipeline running · ${guardedCompletedCount} / ${total}` ``. The `agents` prop is the per-run roster array, which starts as `agents: []` in the run-state store (`useRunStateStore.ts:168`) and is populated only as `agent_start`/roster-building stream events arrive. During `planning`/early `generating`, before the first such event, `agents.length === 0`, so the header reads "0 / 0" even though the run's real agent count (5) is already known server-side.
- `AppHeader.tsx:216` — `agentsTotal: isActive ? (pipelineAgentsTotal || r.agentCount) : (r.agentCount ?? 0)` — falls back to `r.agentCount`, which is the run record's static `agent_count` field, already `5` at creation time (confirmed via `GET /api/runs`). This is what both the header's own running-pipelines badge/dropdown and the `NotificationPanel` (`liveRuns={runningPipelines}`) display, so they read the correct total immediately.

The mismatch window is exactly the gap between run creation (`agent_count` known) and the roster array being populated from live stream events (`agents.length` still 0). `StepsOverviewSpine` has no fallback to the known `agent_count` for this window; `AppHeader`/`NotificationPanel` do.

## Expected

The run detail page's "Pipeline running" header and the notification panel show the same total agent count for the same run at the same moment — either both show the true total (5) throughout, or both show an honest "counting…" state until the roster is known. Never 0/0 next to another surface's 0/5.

## Actual

During the `planning`/early-`generating` window, the notification panel correctly reads `run.agent_count` (5) while the run detail header falls back to the still-empty client roster (`agents.length === 0`), producing "0 / 0" — reproduced 3/3, cycles 1-3, evidence above.
