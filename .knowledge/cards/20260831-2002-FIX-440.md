## Symptom

Since the Phase-44 WS→SSE cutover made SSE the sole run-event transport, every live run-event
stream held one QueuePool connection that was never returned — reclaimed only by GC. With the
default `5 + 10 = 15` pool, EventSource auto-reconnects and a few open tabs exhausted it, after
which `submit_answers` → `_review_gate_owned_by` (`backend/app/api/run_engine.py:344`) blocked on
`pool_timeout` and 500-ed. That is [BUG-004-GROUNDED-CONTEXT](20260716-1231-BUG-004-GROUNDED-CONTEXT.md)
/ [BUG-004-sse](20260803-BUG-004-sse.md).

## Root cause

`backend/app/api/run_stream.py` — `stream_run_events` declared `db: Session = Depends(get_db)`
and built ONE `ScopedStore(..., session=db)` that it then handed to the streaming generator
`_iter_sse_frames`, which calls `read_events` for the durable replay and the D-14g gate re-arm.

FastAPI ≥ 0.106 (0.115.6 installed) tears `yield`-dependencies down **before** the streaming body
runs, so `get_db`'s `finally: db.close()` fires first. The generator's later query then
re-acquires a **fresh** pooled connection on that closed session, and `ScopedStore._acquire`
(`backend/agents/authz.py:95-99`) sees a caller-supplied session → `owned=False`, so
`read_events`'s `finally: if owned: session.close()` (`authz.py:328-330`) never releases it.

One leaked connection per live stream. The checkpointer is not involved (separate psycopg pool),
and `run_stream.py` was the only site with this shape.

## Decision and fix

**Primary — `backend/app/api/run_stream.py:465-468`.** A *second*, session-less
`ScopedStore(owner_id=..., workspace_id=...)` is built for the generator and passed as
`store=stream_store` at `:548`. With no injected session, `_acquire` takes `owned=True` and each
`read_events` opens and closes its own `SessionLocal`, so nothing is held across the idle
live-drain loop. This mirrors the already-safe `post_message` idiom in `run_commands.py`.

Fixed at the store construction rather than by wrapping the endpoint in `try/finally: db.close()`
— the wrapper still pins one connection idle for the whole stream, so it caps the leak instead of
closing it.

The request-session store above it (`:442-446`) is deliberately kept: it backs the two pre-stream
owner checks only, which is why the fence at `:447` still 404s a cross-owner reader.

**Secondary (defence-in-depth) — `backend/app/models/database.py:19-33`.** The engine now passes
explicit `pool_size=20, max_overflow=40, pool_timeout=30, pool_recycle=1800` on the non-SQLite
branch, keeping `pool_pre_ping=True`. Sizing alone does not fix the leak; it raises the exhaustion
ceiling for ordinary multi-run concurrency.
