# FIX-201

**Phase / trigger:** Phase 44 (DEF-44-12-4 concurrent run isolation), ISS-061 continued, KAN-168

## Description

Comprehensive fix for concurrent pipeline cross-contamination. Multiple concurrent runs
(PPT + User Stories + Prototype) shared a single `pipelineState` reducer and shared
`questionnaireData`/`reviewGateData` React state, causing each run's UI to show data
from other runs. Also fixes agent progress not updating after clarify question submission
and review gate approval, plus infinite re-render loop and duplicate toast keys.

## Root causes

### 1. Shared pipelineState reducer (primary contamination)
`useWorkflow()` maintained a SINGLE `pipelineState` React state. All concurrent SSE
streams fan-out into one `handlePipelineMsgRef.current` reducer. After switching between
runs via badge/notification, `activelyBuildingRunIdRef` pointed to the wrong run, causing
foreign run's agent frames to overwrite the viewed run's `pipelineState`.

**Fix:** `useRunStateStore` hook implementing the viewport pattern:
- `Map<runId, PerRunState>` stores per-run state (pipelineState, waveGroups, questionnaireData,
  reviewGateData)
- `handleFrame(runId, msg)` routes frames to correct run's state via `handlePipelineMessage`
  (fakeSetState pattern)
- `switchViewTo(runId)` atomically projects the run's state to React (`setViewedState`)
- Background runs update silently (no re-renders); only the viewed run triggers renders
- `project()` bails out when key references are unchanged (prevents infinite loops)

### 2. Shared questionnaireData / reviewGateData (secondary contamination)
`questionnaire_ready`, `questionnaire_complete`, `review_gate_ready` updated global React
state without per-run isolation. Concurrent runs' clarify questions and review gates leaked
into each other's UI.

**Fix:** All three event handlers now call `runStore.update(runId, {...})` which stores per-run
and only projects to `viewedState` when `runId === viewedRunIdRef.current`.

### 3. Agent progress not showing immediately
`launchPendingRef.current = true` (set during POST window) blocked `isForActiveRun` check,
preventing `handlePipelineMsgRef.current` from being called during the launch window.
After `pipeline_start` early-registration sets `activelyBuildingRunIdRef`, subsequent
`agent_start`/`agent_complete` frames need to reach the reducer.

**Fix:** Removed `launchPendingRef` from `isForActiveRun` computation. The
`activelyBuildingRunIdRef === frameRunId` guard is sufficient.

### 4. `pipeline_start` early-registration not switching store viewport
During the async POST window, `pipeline_start` arrives before `.then()` resolves.
The pre-registration block registers the run in `launchedRunIdsRef` and sets refs,
but `viewedRunIdRef` in the store was not updated, so `handleFrame` wouldn't project.

**Fix:** Pre-registration block now calls `runStoreSwitchViewToRef.current(incomingRunId)`
to immediately set the store viewport, enabling real-time agent progress projection.

### 5. `handleSelectWorkflowRun` (Jump Back In / Run History) not setting refs synchronously
`activelyBuildingRunIdRef` was only set deep inside the async `getWorkflow()` fetch,
causing a race where live SSE frames from other runs could contaminate `useWorkflow.pipelineState`
before the replayed run's `pipeline_start` set it correctly.

**Fix:** `activelyBuildingRunIdRef.current = run.id` and `trackedRunIdRef.current = run.id`
set synchronously at the very start of `handleSelectWorkflowRun`.

### 6. `handleSelectWorkflowRun` condition skipped replay with stale store state
The replay skip condition `fullRun.id !== runStore.viewed.pipelineState.pipelineRunId`
used the store's viewed state which could be stale from a previous visit. Replay was skipped
when store had old data, leaving 0/N agent count.

**Fix:** Condition changed to `fullRun.id !== pipelineState.pipelineRunId` (from `useWorkflow`,
always the actively-building run's authoritative state).

### 7. `displayedPipelineState` derivation for UI
Introduced `displayedPipelineState` computed value: uses `runStore.viewed.pipelineState`
as the single source of truth for the UI. Added `useEffect([pipelineState])` sync with
dual guard (`runId === activelyBuildingRunIdRef.current` AND `runId === runStore.viewedRunId`)
to ensure `useWorkflow.pipelineState` is reflected in the store after agent frame processing.

### 8. Infinite re-render loop (Maximum update depth exceeded)
`project()` in `useRunStateStore` called `setViewedState({ ...state })` unconditionally,
creating a new object reference on every SSE frame. Combined with `setCursor(seq)` in
`useRunStream`, this caused React to exceed maximum update depth.

**Fix:** `project()` now uses functional update with reference equality check: bails out
if `pipelineState`, `questionnaireData`, `reviewGateData`, `waveGroups`, and `runId` are
all reference-equal to previous state.

### 9. Duplicate toast key (Encountered two children with the same key)
`setToasts` in DashboardLayout's completion effect fired multiple times with the same
`notifId + "-toast"` key due to rapid state updates triggering the effect multiple times
before `currentPipelineNotifId.current = null` was seen.

**Fix:** `setToasts` now uses a functional updater with dedup guard:
`if (prev.some(t => t.id === notifId + "-toast")) return prev`.

### 10. AppHeader LIVE_STATUSES missing "analyzing"
`LIVE_STATUSES` in AppHeader.tsx didn't include `"analyzing"`, causing runs in that state
to silently disappear from the header badge while `DashboardLayout.LIVE_RUN_STATUSES`
correctly included it.

**Fix:** Added `"analyzing"` to `AppHeader.LIVE_STATUSES`.
