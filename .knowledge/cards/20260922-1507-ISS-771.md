## Bug report

Derived while analyzing [QA-SG-007](../../BUGS.md#qa-sg-007) — the same underlying defect as
[ISS-757](20260922-1419-ISS-757.md) (the notification bell), found by grepping every reader of
the array ISS-757's root cause already proved wrong, not from a new browser reproduction.

## Status: INFERRED — mechanism confirmed in code, not yet reproduced live

## Why ISS-757's root cause implies this

[ISS-757](20260922-1419-ISS-757.md) confirms that `AppHeader.tsx`'s `runningPipelines` (built at
`AppHeader.tsx:194-222` from `recentRuns`/`useNotifications`, empty for one render after any fresh
mount of `page.tsx` — reload, new tab, or re-auth — until the `recentRuns` fetch resolves) is
passed to `NotificationPanel` as `liveRuns` at `AppHeader.tsx:482`. But `runningPipelines` is read
by two MORE render branches in the same file, unconditionally, on every render:

- `AppHeader.tsx:304` — `{runningPipelines.length === 1 && (` — the single-pipeline badge next to
  the bell.
- `AppHeader.tsx:349` — `{runningPipelines.length > 1 && (` — the "N Running" dropdown (KAN-132).

Both conditions test `.length` against an exact count (`=== 1`, `> 1`). During ISS-757's race
window `runningPipelines` is `[]` (length 0), so BOTH conditions are false and NEITHER branch
renders anything — unlike the notification panel (which at least shows a, wrong, "No
notifications yet" message), the badge/dropdown region renders nothing: no badge, no dot, no
count. A user reloading with one or more pipelines already in flight sees zero visual indication
that anything is running, for the exact window ISS-757 already proved exists.

This is the same class of "one array, three render sites" fan-out
[ISS-674](20260917-1420-ISS-674.md) already documented for a different, now-resolved root cause
(frozen `agentsCompleted`) — same three sites, same file, this time triggered by ISS-757's race
instead of ISS-674's stale-map cause.

## Expected

The header's single-run badge / "N Running" dropdown appear as soon as the server confirms a
pipeline is live, independent of whether the client happens to mount mid-flight of an existing run
(reload, fresh tab, or re-login) — matching what `NotificationPanel` should also do per ISS-757.

## Actual (inferred, not yet observed)

During the race window, the badge/dropdown area is simply absent — no loading indicator, no
badge, no error, nothing to notice or screenshot. Once `recentRuns` resolves (the same fetch
ISS-757 depends on), the badge/dropdown appear correctly.

## What would confirm this live

1. Start one workflow run from a tab; wait until it is confirmed live server-side.
2. Full-page reload to `/dashboard`.
3. Before `recentRuns` resolves (a throttled network is more reliable than eyeballing), observe
   the header region right of the nav: expect no single-run badge.
4. Repeat with two-plus concurrent runs: expect no "N Running" dropdown.
5. This is the same repro ISS-757 already used (2026-09-22, browser lane3, qa-admin@flowinqa.com)
   — its cycle 2 is the one attempt that landed inside the race window and is the one to re-watch.

## Fix

Shares [ISS-757](20260922-1419-ISS-757.md)'s fix location exactly — the shared derivation at
`AppHeader.tsx:171-222`. See ISS-757's "Fix — where it belongs" section (its 2026-09-22 Analysis)
for the recommended shape: a `recentRunsLoaded` signal threaded down from `page.tsx`, the only
place that knows the fetch is in flight. No separate fix is expected; this card exists so the
test-writer asserts the header badge/dropdown surfaces too, not only the bell panel, and so these
two render sites are not rediscovered later as a "new" bug.
