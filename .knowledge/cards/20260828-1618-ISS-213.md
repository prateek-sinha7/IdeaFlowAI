## Derivation (INFERRED — not yet reproduced)

Sibling of [ISS-198](20260828-1400-ISS-198.md), same root mechanism as
[ISS-207](20260828-1617-ISS-207.md) (search) and [ISS-208](20260828-1617-ISS-208.md)
(sort), applied to the type-filter chip row instead.

`frontend/src/components/history/WorkflowHistory.tsx`:
- `families = groupRunsByFamily(runs)` (line 942) is built from the same capped `runs`
  array as every other consumer — `runs` never exceeds the fetched page because
  `handleLoadMore` is dead code (see [ISS-198](20260828-1400-ISS-198.md)'s root cause).
- `typeCounts` (lines 952-958) tallies EVERY filter chip, not just "all" (already flagged
  in [ISS-198](20260828-1400-ISS-198.md)'s own root cause) — each of the five per-type
  buckets (`user_stories`, `ppt`, `prototype`, `app_builder`, `custom`) is built by
  `families.forEach` (line 953) bucketing via `filterBucketFor(g.root.type)` (line 956,
  imported from `RevisionFamilyView.tsx`).
- The chip row render (lines 1023-1049) reads `typeCounts[type] || 0` (line 1024) for the
  badge number, and line 1025 — `if (type !== "all" && count === 0) return null;` — hides
  the chip completely whenever its count within the capped window is zero.

## Expected vs Actual

- Expected: each type-filter chip's count reflects the account's true total for that
  type, and a type with zero occurrences among the loaded rows but 1+ among the
  un-fetched remainder still appears (or the UI states counts are partial).
- Actual: every non-"all" chip count undercounts the true per-type total once an
  account's runs exceed the fetched page (50, e.g. qa-admin's 273 — see
  [ISS-198](20260828-1400-ISS-198.md)), and — more severely — a type with zero
  representation in the currently-loaded 50 rows disappears from the filter row
  entirely, even though runs of that type exist further back in the account's history.

## What would confirm or refute this

Reproduction: identify (via `GET /api/runs?limit=100&offset=100` or `offset=200` for
qa-admin) a run `type` value with zero occurrences in the first
`GET /api/runs?limit=50` page but 1+ occurrences beyond it; load `/runs` in the UI and
confirm that type's filter chip either shows a lower count than the API-derived true
count, or is missing from the chip row altogether.

## Why this is a sibling, not the same bug

[ISS-198](20260828-1400-ISS-198.md)'s own "Fix location" step 1 names only the header
and the "all" chip (`typeCounts.all = families.length`, line 952) as needing to read
from `totalRuns`; it does not address the other five per-type buckets built in the same
`typeCounts` loop (lines 953-958). Those buckets have no equivalent in `totalRuns` at
all — `totalRuns` is a single aggregate, not broken down by type — so fixing them needs
a different mechanism than the header/all-chip fix. And unlike
[ISS-207](20260828-1617-ISS-207.md) / [ISS-208](20260828-1617-ISS-208.md) (wrong
search/sort results over an otherwise-visible list), this defect can make an entire
filter option vanish from the UI, not just misreport a number.
