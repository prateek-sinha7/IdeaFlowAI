# ISS-160

## Title

**The Concierge is unreachable on a revision run.** The same question, same user, same endpoint: the PARENT run answers correctly (exact token/cost figures), while the REVISION run returns `{"error":"This pipeline is not available on your current plan.","code":"pipeline_not_entitled"}`. This makes FIX-249's benefit unreachable on precisely the run class FIX-250 had just repaired, and it blocked the last step of that fix's live verification.

## Severity / Tag / Status (original row)

- Sev: major
- Tag: backend,product
- Status: **OPEN** (filed 2026-08-13; found while attempting to live-verify FIX-249 on a revision run)

## Source / Evidence

Discriminating A/B run live on 2026-08-13: parent accepted (`"channel":"revision"` proposal minted), revision rejected with `pipeline_not_entitled`.

## Validation (QA-KB-009, 2026-10-01)

Confirmed statically, 3/3 fresh runs. The named test (`backend/tests/unit/test_v2_revision_routing.py::test_concierge_nested_v2_revision_parent_keeps_v2_base`) PASSES (6 passed x3) because it covers only the disposal path, which already derives `base_type` (`backend/app/api/run_commands.py:1640-1650`). The defect is in the sibling CHANNEL_REVISION branch: `backend/app/api/run_commands.py:2018` still reads `target_artifact_type = dispatch.target_artifact_type or f"{wr_type}_output"` with no base mapping. `_mint_revision_row` (`run_commands.py:4608`) then builds `f"{target.removesuffix('_output')}_revision"`.

Trigger: parent run whose type already ends in `_revision` (user_stories_revision, prototype_v2_feature_revision, prototype_v2_depth_revision) and the client omits `target_artifact_type`. Derived pipelines `user_stories_revision_revision`, `prototype_v2_feature_revision_revision` are absent from `TIER_PIPELINES` for every tier (`backend/app/core/entitlements.py:10`; checked with a script over basic/hexaware/pro/enterprise: all False) -> 403 pipeline_not_entitled.
No existing test exercises the CHANNEL_REVISION branch with a `_revision` parent.

## Analysis (QA-KB-009 analyzer, 2026-10-01)

Verdict: root cause CONFIRMED. The agreed minimal fix is ACCEPTED with the refinements below. Two details in this card and in the QA-KB-009 entry are stale on today's code (see Corrections). Three siblings filed: [ISS-879](20261001-2111-ISS-879.md) (`ppt_v2`), [ISS-880](20261001-2111-ISS-880.md) (tier classification), [ISS-881](20261001-2111-ISS-881.md) (`REVISION_BASE_MAP`).

### Root cause (CONFIRMED, every line below was read)

One mechanism: the revision target for a chat-turn revision is derived from the parent run's type by hand at two entry points, and only one of them maps a `*_revision` parent type to its base.

1. Routing. `chat_router.route_chat_turn` sends a turn on a terminal run to `CHANNEL_REVISION` unless it carries a gate action or `concierge: true` (`backend/app/api/chat_router.py:212`, `:259-274`). The target is `turn.target_artifact_type`, i.e. whatever the client sent.
2. The broken line. `backend/app/api/run_commands.py:2018` in `post_message`: `target_artifact_type = dispatch.target_artifact_type or f"{wr_type}_output"`, where `wr_type` is the parent's `WorkflowRun.type` (`:1826`). When the parent is itself a revision run, `wr_type` already ends in `_revision`, so the target is `<x>_revision_output`.
3. The consumers. `_mint_revision_row` (`run_commands.py:4608`) derives `revision_pipeline_type = f"{target_artifact_type.removesuffix('_output')}_revision"`, which is `<x>_revision_revision`. The driver (`run_commands.py:5696`) and the engine (`backend/agents/execution_engine/engine.py:13215`, `:13292`) each re-derive the pipeline from the same `target_artifact_type`, independently.
4. The copy that was already fixed. The Concierge disposal path has the base mapping (`run_commands.py:1640-1650`). [FIX-212](20260811-1519-FIX-212.md) records this exact failure ("`wr_type = "user_stories_revision"` -> revision target `user_stories_revision_output` -> pipeline_type `user_stories_revision_revision` not in TIER_PIPELINES") and its fix touched only the disposal path (the code comment at `run_commands.py:1629` labels it FIX-211; the card is FIX-212). `git log -S'f"{wr_type}_output"' -- backend/app/api/run_commands.py` shows the expression entering both places (`fd5104b99` for CHANNEL_REVISION, `8d8ed0c25` for the disposal path) and leaving only one (`5818cdcca`, FIX-210..212).

### Corrections to this card and to the QA-KB-009 entry

- The failure code is no longer 403 `pipeline_not_entitled`. `_mint_revision_row` runs an existence gate BEFORE the entitlement gate: `get_pipeline_agents(...)` / `_compiled_step_count(...)` (`run_commands.py:4660-4666`) raise HTTP 400 `revision_unsupported` ("Revisions aren't available for this workflow yet - 'user_stories_revision_revision' has no pipeline behind it. Launch a new run instead."). The entitlement gate (`:4679-4688`, 403 `pipeline_not_entitled`) is never reached for a `*_revision_revision` type. The existence gate arrived in `ec1ea70f5` (2026-08-19), after this card was filed (2026-08-13), which is why the filed symptom and the QA-KB-009 "Actual" no longer match; the mechanism is unchanged. OBSERVED: 10 of 10 revision-run parent types return HTTP 400 `revision_unsupported` at enterprise; `user_stories_revision`, `ppt_revision` and `prototype_revision` return the same at basic, hexaware and pro (sampled, not all 10 per tier). Tier does not matter by construction: the existence gate runs before the tier check and does not read the tier.
- The Validation section's `prototype_v2_depth_revision` is not a pipeline type (no manifest, no hit anywhere in `backend/` or `frontend/src`). The v2 Depth revision pipeline is `prototype_v2_feature_revision`.
- The Concierge ASK path is not affected. A turn with `concierge: true` goes to `CHANNEL_CONCIERGE` and never reaches `_mint_revision_row`; only a held revision proposal, once confirmed, reaches the (correct) disposal path. The failing path is a PLAIN turn: REST clients (ISS-161's `"channel":"revision"` response is this branch) and the UI lane's plain `sendMessage(effectiveText, attachments)` (`frontend/src/components/chat/RunChatLane.tsx:1368`), taken for lane states other than `complete`, `building` and `clarify` (the three `concierge: true` sends are at `:1334`, `:1348`, `:1361`), in practice `terminal` and `idle`. The frontend never sends `target_artifact_type` on `/messages`, so the fallback at `:2018` always applies to UI-originated turns. The title of this card ("The Concierge is unreachable") is therefore imprecise; it is left as filed.

### Fix: where it belongs, and the verdict on the agreed minimal fix

ACCEPTED in outline. Extract the base-type derivation (the block at `run_commands.py:1640-1650`) into one private helper in `run_commands.py` (the BUGS.md note suggests `_revision_base_type(wr_type)`) and call it from BOTH sites: `:2018` becomes `dispatch.target_artifact_type or f"{_revision_base_type(wr_type)}_output"`, and the disposal block collapses to `base_type = _revision_base_type(wr_type)`. Verified sufficient for the reported trigger: the disposal block, run unmodified for all 10 revision parents with no model `target`, derived an existing, entitled revision pipeline every time.

Refinements for the fixer:

1. Keep the generic `removesuffix("_revision")` fallback. The registry already has `REVISION_BASE_MAP` (`backend/agents/registry.py:145`), and a helper that is only `REVISION_BASE_MAP.get(wr_type, wr_type)` is shorter, but the map lacks `backlog_revision` ([ISS-881](20261001-2111-ISS-881.md)), so it would still double-suffix `backlog_revision` parents. Verbatim extraction leaves the disposal path byte-for-byte unchanged (it is pinned by the passing `tests/unit/test_v2_revision_routing.py`); a map-first helper is acceptable only with the generic fallback behind it.
2. Fix the TARGET upstream, not the pipeline type downstream. `_mint_revision_row` (`:4608`), the driver (`:5696`) and the engine (`engine.py:13215`, `:13292`) each re-derive the pipeline type from `target_artifact_type`. Normalizing only inside `_mint_revision_row` would make the persisted row type disagree with the pipeline the engine dispatches, and putting base-type knowledge in the engine would be a workflow-name branch in the kernel (INV-1 / SC-001).
3. Do not fold the siblings in silently. `ppt_v2` ([ISS-879](20261001-2111-ISS-879.md)) needs a deliberate `ppt_v2 -> ppt` mapping; tier selection ([ISS-880](20261001-2111-ISS-880.md)) is a product call; the map row ([ISS-881](20261001-2111-ISS-881.md)) is a registry and test change.
4. Not filed: a client- or model-supplied `*_revision_output` target would double-suffix the same way (CHANNEL_REVISION trusts `dispatch.target_artifact_type`; the disposal path trusts `params["target"]` once it ends in `_output`). No shipped caller sends one (the UI always posts a base target; the Concierge tool docstring examples are base targets, `backend/app/agents/chat/concierge.py:416`), so there is no evidence it is reachable and no card.
