# ISS-1146

**Register source:** sibling derived during the `QA-KB-108` analysis on 2026-10-09 (root [ISS-1144](20261009-0725-ISS-1144.md)). Not its own bug row.

**Confidence:** the backend mechanism is CONFIRMED offline, row B of `evidence/qa-kb-108/04-analyze-sibling-probes-output.txt` (`refresh_auth` patched to raise `TokenRetrievalError`: 500, no `access-control-allow-origin`; `ClientError` control: 503 with it). The frontend consequence is read from source (`api.ts:413-429`, `AuthSessionProvider.tsx:84-111`) and is INFERRED, not driven; it needs a live session whose access token ages out while the backend's SSO session is expired.

## Condition

- Any `POST /api/auth/refresh` while the backend's AWS credential chain cannot be resolved. `refresh_auth` is `_client().admin_initiate_auth(AuthFlow="REFRESH_TOKEN_AUTH")` (`backend/app/core/cognito.py:333`), a SigV4-signed operation, so credentials are resolved at call time and a `BotoCoreError` is raised before any request leaves the process.
- The handler at `backend/app/api/auth.py:667-681` catches `ClientError` only. The refresh token itself is valid and untouched.

## Expected vs actual

Expected: 503 `Authentication service unavailable` with CORS headers, a result `refreshAccessToken` can treat as "provider unavailable, try again". Actual: 500 with no CORS header; the browser blocks it and `fetch` rejects.

## Downstream effect (INFERRED from source)

`refreshAccessToken` returns `null` for any non-ok response and for any thrown fetch (`frontend/src/lib/api.ts:421,426`). `AuthSessionProvider.refreshOrExpire` retries once at true expiry and then calls `expireSession()` (`frontend/src/providers/AuthSessionProvider.tsx:93-110`). So while the server's SSO session is expired, every signed-in browser is sent to `/login?expired=true` when its 60-minute access token ages out, and cannot sign back in ([ISS-1144](20261009-0725-ISS-1144.md)).

Out of scope here, stated so it is not mistaken for part of this fix: the frontend treats a handled 503 and a 401 the same, so the 503 fix does not stop that forced sign-out. Whether a 5xx from refresh should end the session is a frontend design question; [FIX-481](20260917-0131-FIX-481.md) chose "retry once at true expiry, then terminate". Not escalated, because the backend fix does not depend on it.

## Why the root cause implies it

Same narrow `except ClientError` (`auth.py:669`), same signed-operation trigger, same missing safety net (`backend/app/main.py:539`).

## Fix direction (INFERRED, not applied)

Route `BotoCoreError` into the existing 503 fall-through at `auth.py:677-681`. Trap: do not route it into the `NotAuthorizedException` / `UserNotFoundException` branch at `:671-676`. That branch calls `_reconcile_status_on_refresh_rejection`, whose docstring (`:551-575`) explains that a wrongly persisted `disabled` status locks an account out until an operator intervenes. A provider outage is not evidence about the account.

## Test notes

Override `get_current_user_for_refresh` with a stub `(user, payload)`, patch `app.api.auth.decrypt_cognito_refresh_token` to return a string, patch `app.core.cognito.refresh_auth` with `side_effect=TokenRetrievalError(...)`, send `Authorization: Bearer x` and `Origin: http://localhost:3000`. Assert 503, a string `detail`, `access-control-allow-origin` present, and that `_reconcile_status_on_refresh_rejection` was not called (patch it and assert). Keep the `ClientError(InternalErrorException)` control green.
