# ISS-1053

## What is broken

Found while fixing QA-KB-062 ([FIX-723](20261007-1810-FIX-723.md)), and not fixed there. It is not that bug: these
tests were red before FIX-723 and are still red after it, with the same counts and the same errors. Five cards have
logged them only as "pre-existing" coverage notes: [FIX-562](20260918-FIX-562.md),
[FIX-695](20261001-2230-FIX-695.md), [FIX-701](20261002-0037-FIX-701.md), [FIX-721](20261007-1758-FIX-721.md) and
the ISS-347 analysis. None of them filed a card for it.

Two tests in `frontend/src/components/workflow/LaunchWizard.test.tsx` fail:

- `WR-07: chaining launch threads sourceRunId and clears the key (v2: context block no longer injected into brief)`
  (`:442-458`)
- `a genuine chain (chain.from + chain.source_run_id → isChaining=true) still threads the source id and clears the
  key` (`:486-501`)

Each one sets `chain.from` and `chain.source_run_id` with no `chain.brief`, picks a design system and clicks Continue.
It then reads `JSON.parse(sessionStorage.getItem("prototype.draft")!)` and fails with
`TypeError: Cannot read properties of null (reading 'brief')` and `(reading 'sourceRunId')`. Observed on HEAD
`0b5223f4c` and again after FIX-723 (`evidence/qa-kb-062/fix-03-regression.txt`).

## Mechanism (read in code, line numbers as of FIX-723)

1. `chain.from` arms `isChaining`, which removes the brief editor (`LaunchWizard.tsx:1276` `{!isChaining && (`), so
   the user cannot type a brief.
2. `canContinue` requires `hasBuildInput = Boolean(brief.trim() || chainContextBlock?.trim())` (`:943`).
   `chainContextBlock` is always null: `setChainContextBlock` (`:293`) has had no caller since `e7305f9dd` removed both
   reads of `chain.context_block`.
3. So with no non-empty `chain.brief`, Continue stays disabled. `handleLaunch` returns at
   `if (!canContinue || locked) return;` (`:1061`) and writes no draft. The "Add a brief" pill (`:1458`) shows, but
   the control it asks for is hidden.

The test file says as much in its own comment (`LaunchWizard.test.tsx:555-558`): "the pre-existing hasBuildInput/ISS-155
gate that WR-07 and 'genuine chain' above already document as broken for the chaining path".

**Reachable in the product (INFERRED, read only).** Both chain writers can store an empty brief:

- `handleChainPipeline`: `cleanBrief = rawBrief || ctxBriefFallback` (`DashboardLayout.tsx:1947-1949`)
- `handleChainFromHistory`: `(run.input || "").split(...)[0].trim()` (`:2052-2053`)

A genuine chain from a source run whose input is empty therefore opens a wizard with no brief editor and a Continue that
can never enable. Not reproduced live.

## Disposition

Open. The tests and the gate contradict each other.

- WR-07 and BUG-014 expect a briefless chained launch: `draft.brief === ""` with `sourceRunId` threaded.
- The ISS-155 / [FIX-255](20260813-1438-FIX-255.md) gate refuses a briefless launch on purpose, in the wizard
  (`hasBuildInput`) and at the backend ingress (`empty_brief`).

**Decision needed:** are the two tests stale, so their fixtures should carry a non-empty `chain.brief` (which is how
proof case R6 in `evidence/qa-kb-062/` drives a genuine chain green)? Or should a chained open with an empty brief show
the brief editor so the user can supply one? The first changes tests only. The second is a wizard change keyed on
`brief`, not on `isChaining`. Either way, do not fix it by relaxing `hasBuildInput`: that reopens FIX-255's empty-brief
launch.
