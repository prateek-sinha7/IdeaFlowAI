# ISS-819

## Description

Root-cause completion for **QA-PS-043** (`LEDGER.md` / `BUGS.md#qa-ps-043`),
whose root card [ISS-790](20260922-1821-ISS-790.md) re-validated the bug
2026-09-22 (3/3 cold starts) but explicitly deferred the mechanism: "Root
cause — not traced here (analyze phase)... This card's remaining piece —
`GET /api/workflows/user_stories` duplicated 2x — is specific to this wizard
and still needs its own call-site trace." This card supplies it, and — because
the codebase moved under this analysis (two sibling fixes landed on this same
branch while it was in progress) — also reports which parts of ISS-790's
9-request table are no longer current.

## Root cause (the part still broken)

`frontend/src/components/workflow/IdeaInputPage.tsx:1097-1302`:

```tsx
useEffect(() => {
  if (!workflowId) { /* reset state, return */ }
  let cancelled = false;
  const jwt = getToken();
  if (!jwt) { /* reset state, return */ }
  getWorkflowDetail(jwt, workflowId)          // :1116
    .then((detail) => { if (cancelled) return; /* ...setDeclaredCapabilities etc. */ })
    .catch((e) => { if (!cancelled) { /* ... */ } });
  return () => { cancelled = true; };
}, [workflowId]);
```

`cancelled` only blocks a STATE UPDATE after unmount — it does not stop the
fetch itself, and there is no in-flight guard, `AbortController`, or cache.
`getWorkflowDetail()` (`frontend/src/lib/api.ts:1934-1946`, verified at the
current line numbers) is a plain
`request<WorkflowDetail>('/api/workflows/${workflowId}', ...)` call, so this
IS the literal `GET /api/workflows/user_stories` request ISS-790's table
names (the route param `workflowId` here is `"user_stories"` for
`/create/user-stories`). React's dev-mode StrictMode double-invokes this
effect on first mount (confirmed: `frontend/next.config.ts` sets no
`reactStrictMode: false` override), which is the same doubling mechanism
already established across this family (ISS-782/784/794/801/808).

**This is the ONLY production call site that renders on this route.** Every
non-test caller of `getWorkflowDetail` was grepped
(`grep -rn "getWorkflowDetail(" frontend/src --include=*.tsx --include=*.ts`):

| Call site | Trigger | Renders on `/create/user-stories`? |
|---|---|---|
| `IdeaInputPage.tsx:1116` | mount effect, `[workflowId]` | **Yes** — this is the bug |
| `page.tsx:492` | mount effect, gated on `builtinCanvasType` | No — `builtinCanvasType` is only set for the `workflow-canvas` screen (`builtinCanvasTypeFor(parsedView)`); `create-user-stories` resolves to a different screen, so this effect returns before fetching |
| `LaunchWizard.tsx:507` | mount effect | No — `LaunchWizard` renders for `/create/ppt`/`/create/prototype`, a separate wizard path per `initialMainViewFor`'s own comment ("`/create/ppt`... routes to a separate wizard page") |
| `LaunchWizard.tsx:589` | `handleToggleOverride`, user click | No — user-triggered, not a mount fetch |
| `WorkflowDialog.tsx:79` | mount effect, gated on `open` | No — a modal, not part of this page |
| `IdeaInputPage.tsx:1682` | `handleToggleOverride`, user click | No — user-triggered, same shape as `LaunchWizard.tsx:589` |
| `ComposerPage.tsx:606` | mount effect | No — the composer/canvas route |

The other four mount-effect call sites share the identical no-guard shape
and are filed as siblings: [ISS-820](20260922-1941-ISS-820.md) (LaunchWizard),
[ISS-821](20260922-1941-ISS-821.md) (WorkflowDialog),
[ISS-822](20260922-1941-ISS-822.md) (composer surfaces).

## What ISS-790's table no longer reflects (verified against the CURRENT tree)

ISS-790 captured its 9-request table at 18:21. Two unrelated fixes for
sibling bugs in this same batch landed on this branch afterward and changed
the two other duplicates ISS-790 recorded:

- **`GET /api/runs?limit=50` x2 — likely already closed.** The producing
  effect, `frontend/src/app/[...view]/page.tsx:985-1002` (`[isAuthenticated]`,
  the same effect [ISS-808](20260922-1850-ISS-808.md) root-caused for
  QA-PS-039/`/dashboard`), is unchanged and still calls
  `getWorkflows(currentToken, { limit: 50 })` unconditionally on every route
  including this one. But `getWorkflows()` itself now single-flights
  identical concurrent requests — `inFlightWorkflows`, a
  `Map<token+path, Promise>` dropped on settle
  (`frontend/src/lib/api.ts:855-869`, added by
  [FIX-616](20260922-1923-FIX-616.md) for
  [ISS-783](20260922-1615-ISS-783.md)/QA-PS-037). A second call to
  `getWorkflows()` for the identical resolved path while the first is still
  open now returns the SAME promise instead of firing a second request. Not
  re-verified with a fresh browser capture by this card — the JS-level call
  still happens twice under StrictMode, so this needs a live re-check, not
  an assumption, before it is called closed.
- **`GET /api/workflows` x2 — closed, by deletion.** The same effect used to
  also call `getWorkflowDefinitions(currentToken)` right after the line
  above. Reading the file just now shows that call is gone, replaced with:
  > `// ISS-782: the getWorkflowDefinitions pre-fetch that used to sit here
  > is gone. It existed to seed HomeLaunchGrid's card grid through the
  > homeWorkflows prop, but HomeLaunchGrid now reads the catalog from Redux
  > ... and never consumed the prop ... So this was a 22 KB GET
  > /api/workflows fired on EVERY route ... whose result reached nothing.`

  This matches [ISS-807](20260922-1852-ISS-807.md)'s finding for QA-PS-039
  ("delete the call, don't dedupe it") already being applied. Confirmed by
  direct read of the current file — this piece of QA-PS-043 no longer
  reproduces.
- **`GET /api/runs?limit=6` x1 and the three `*/library` x1-each calls** —
  unaffected by either fix, and were never duplicated (see ISS-790's own
  text); not part of this bug's mechanism (see Impact below).

## Impact

Only the `workflows/user_stories` x2 duplicate is confirmed still live: one
extra ~2.9 KB request per cold load of `/create/user-stories`, plus whatever
latency the second round-trip adds before the wizard's capability strip /
manifest-step canvas can render (the effect's `.then` populates
`declaredCapabilities`/`manifestAgents`, both used to paint the roster).
Small in isolation; the same shape repeats on every other `getWorkflowDetail`
mount-effect surface (see the sibling cards), so the aggregate is not.

## Where the fix belongs

`frontend/src/lib/api.ts`, generalizing the exact pattern
[FIX-616](20260922-1923-FIX-616.md) already proved out for `getWorkflows()`
onto `getWorkflowDetail()`: a private `Map<string, Promise<WorkflowDetail>>`
keyed by `` `${token}\n${workflowId}\n${qs}` ``, returned to a concurrent
caller instead of issuing a second `request()`, and dropped in a `.finally`
once the first settles. That is the one place every caller in the table
above — `IdeaInputPage.tsx`, `page.tsx`, `LaunchWizard.tsx`,
`WorkflowDialog.tsx`, `ComposerPage.tsx` — already routes through, so the
fix closes this bug and all three sibling cards in one change, the same way
FIX-616 closed QA-PS-037 plus every other `getWorkflows()` caller without
touching `WorkflowHistory.tsx`, `RunConnectionProvider.tsx`, or `page.tsx`
individually. No per-component guard is needed or wanted.
