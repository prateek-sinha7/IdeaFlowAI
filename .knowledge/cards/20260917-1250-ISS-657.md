# ISS-657

## Title

Because [ISS-647](20260917-1100-ISS-647.md)'s root mechanism is an unguarded async race, retrying a click that appeared to do nothing — the exact recovery behaviour QA-PS-005's own report describes ("the same entry may work on a subsequent click") — can itself start a SECOND overlapping switch before the first has resolved, with no protection against the two finishing out of order.

## Status: INFERRED — not yet reproduced

Filed from the root cause of QA-PS-005, not from an independent reproduction. Whoever picks this up should confirm it live before treating it as a confirmed defect (see "What would confirm this" below).

## Why QA-PS-005's root cause implies this

`handleSwitchToLiveRun` (`frontend/src/app/[...view]/page.tsx:2592-2680`) is `async` and
takes a real network round trip (`await getRunEvents(...)`, line 2648, then replays each
frame via `handleWebSocketMessage`, lines 2651-2659) before `runStore.switchViewTo(runId)`'s
projection is fully populated. Nothing in this function — no ref flag, no
`AbortController`, no request token check — stops a second call from starting while a
first is still awaiting its fetch:

- Click run A (dropdown or badge) → `handleSwitchToLiveRun("A")` starts, sets
  `trackedRunIdRef.current = "A"` (line 2603) and begins `await getRunEvents(token, "A")`.
- Per QA-PS-005 ([ISS-647](20260917-1100-ISS-647.md)), this click's own `onGoToPipeline`
  read is stale and appears to do nothing — the exact reported trigger for a user to
  retry.
- User clicks run B before A's fetch resolves → `handleSwitchToLiveRun("B")` starts,
  overwrites `trackedRunIdRef.current = "B"` and `runStore.switchViewTo("B")` (line 2624)
  immediately — while A's in-flight `getRunEvents("A")` promise is still pending.
- Whichever `getRunEvents` call resolves LAST wins: if A's slower fetch resolves after
  B's, A's replay (`page.tsx:2651-2659`) runs after B's and calls `runStore.switchViewTo("A")`
  again (line 2673, inside the `try`), silently reverting the viewport to A even though
  the user's most recent, intentional click was B — with no run-id/generation check
  anywhere in this function to discard a stale in-flight response.

This is the standard "two async requests, last-one-in wins" race, and it sits directly on
top of the exact retry behaviour ([ISS-647](20260917-1100-ISS-647.md)'s own root cause)
that a user experiencing QA-PS-005 is likely to perform.

## Expected (once reproduced)

Clicking a second, different running pipeline before the first click's switch has settled
either queues cleanly or cancels the first — the UI always ends up on the LAST run the user
actually clicked.

## Actual (inferred, not yet observed)

The UI can end up showing whichever of the two switches' network fetches happened to
resolve last, which is not guaranteed to be the user's last click.

## What would confirm this

1. Start two concurrent pipeline runs (A and B) so the header dropdown shows both.
2. Open the dropdown, click A's entry, and — without waiting for navigation — immediately
   click B's entry (re-opening the dropdown if it closed).
3. Throttle the network (e.g. Chrome DevTools) so `getRunEvents` for A resolves noticeably
   after the one for B, and check which run's stream page the app actually lands on and
   keeps showing.
