# FIX-229

**Phase / trigger:** 7:pipeline_complete → completed. Before bac1e556 the reconcile prioritised cancelled unconditionally and the trailing event was absorbed; bac1e556 did not create the contradictory tail, it removed the thing that was hiding it. An attempt boundary is a run_resuming/pipeline_start` row, so a completion only supersedes a cancellation when one lies BETWEEN them.

## Description

A user who resumes a run parked at a review gate and then REJECTS at that gate had the run recorded in history as completed. The rejection was silently discarded from the record and the deliverable appeared accepted. Reachable by anyone using Resume / Run Again on a failed or cancelled run that stopped at a gate — every workflow, not a family-specific defect. Found as red #7 of ISS-078's seven test_restart_resume.py failures; the other six were test defects (see TEST-013).

## Root cause

A broken assumption in the reconcile, not in the engine. resume_supersedes (run_commands.py:602, added by bac1e556/KAN-120) asked *"is there a pipeline_complete at a HIGHER SEQ than the last pipeline_cancelled?"* and read the answer as *"a later attempt succeeded"* — two different questions. On a rejection both events belong to ONE attempt: the engine emits pipeline_cancelled, _run_agent returns, and the dispatch loop falls through to the run's single pipeline_complete emitter.
