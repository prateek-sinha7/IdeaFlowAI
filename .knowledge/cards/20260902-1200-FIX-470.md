## What was wrong

`BUG-20260829-0055`: on `/workflows/new`, a rapid double-click on "Save workflow"
before the first POST response returned created two rows in `user_workflows` with the
same name. The Save button's only gate was `disabled={saving}` (React state), which
is set via `setSaving(true)` — a React state update that is asynchronous relative to
the DOM click event. A second click landing before React re-rendered the button
(between the first click's synchronous JS execution and the next paint) bypassed the
`disabled` prop entirely and independently called `saveUserWorkflow(token, undefined,
...)` → `createUserWorkflow`, producing a second row.

This is structurally identical to the login-form race ISS-245 documents; here the
consequence is worse because `userWorkflowId` is only set AFTER the first response,
so both calls use the create (POST) path rather than the update (PATCH) path.

## Root cause

`frontend/src/components/workflow/composer/ComposerPage.tsx` — `handleSave` — no
synchronous re-entrancy guard; `isSavingRef` was absent.

## What changed and why there

Two additions:

1. **Ref declaration** (alongside other `useRef` calls):
   ```ts
   const isSavingRef = useRef(false);
   ```

2. **Guard at `handleSave` entry** (synchronous — checked before any async work):
   ```ts
   if (isSavingRef.current) return;
   isSavingRef.current = true;
   ```
   Cleared unconditionally in the `finally` block:
   ```ts
   finally {
     isSavingRef.current = false;
     setSaving(false);
   }
   ```

The `saving` state and `disabled={saving}` are kept intact — they drive the
loading-spinner UI. The ref is the correctness gate; the state is the visual gate.
Both are needed: the ref prevents the double-POST, the state prevents the button
flickering back to enabled between the ref set and the React re-render.

Also closes ISS-410's ComposerPage-side consequence: a transient fetch failure
landing before a Save click produces the same empty `userWorkflowId` / no
`initialSavedComposition` state, and the ref mutex now prevents a concurrent
second Save from creating a second row in that scenario too. The `page.tsx`
unconditional-catch root (domain 8) is escalated separately.
