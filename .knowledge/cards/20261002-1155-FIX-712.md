# FIX-712

## What was wrong

The bug is QA-KB-049. Cold-load `/runs/{id}/audit`, `/files` or `/steps` of a run that is still generating, and the
URL becomes `/runs/{id}/stream` with the Steps tab forced. The same URLs work once the run completes, so nobody can
share a link to a live run's audit trail or files. The root card is [BUG-024](20260827-BUG-024.md). Four siblings share
the mechanism:

- [ISS-956](20261002-0316-ISS-956.md): every other run screen is rewritten the same way (`/runs/{id}`,
  `/steps/{agentId}`, `/workspace`, `/versions/{v}`, `/preview/full`).
- [ISS-957](20261002-0316-ISS-957.md): planning, revising and gate-parked runs are rewritten too, because the trigger
  is `isRunning` and not the run's status.
- [ISS-958](20261002-0316-ISS-958.md): in-app opens of a live run (Version-menu member, History and Home rows) get
  overwritten as well.
- [ISS-959](20261002-0316-ISS-959.md): Back from the rewritten `/stream` bounces forward again.

## Root cause (from the cards, re-checked before editing)

The cause is the `pipelineState?.isRunning` effect in `frontend/src/components/layout/DashboardLayout.tsx` (`:822-903`).
Its own comment calls it "the single funnel every launch path's pipelineRunId flows through". At HEAD 024c03ef8 it
ended in

```ts
      if (incomingRunId) {
        router.push(routes.runStream(incomingRunId));
      }
```

at `:854-856`, which never reads the URL. On a cold load, T7 replays the run's durable log. `pipeline_start` or
`planner_start` sets `isRunning` and `pipelineRunId`, the effect pushes `/stream`, `page.tsx` remounts, and T7's pending
tab deep link dies with the old mount.

The line numbers and the push matched the card exactly. Before editing I grepped every `routes.runStream` push in
`DashboardLayout.tsx` again. The others (`:2818`, `:2839`, `:2885`, `:2901-2941`, `:3050`, `:3470`) are click
handlers, as BUG-024's "Ruled out" says. The funnel is still the only automatic push.

## What changed, and why there

| where (working tree) | change | card |
|---|---|---|
| `DashboardLayout.tsx:39` | `import { routes, parseViewPath } from "@/lib/routes";` (was `{ routes }`) | BUG-024 |
| `DashboardLayout.tsx:854-857` | 2 comment lines, then `const here = parseViewPath(window.location.pathname.split("/").filter(Boolean));` and the condition `if (incomingRunId && !("runId" in here && here.runId === incomingRunId))` | BUG-024 |

That is 3 added lines and 2 edited lines. Nothing else in the file changed. The other session's uncommitted
`onUnsavedChange={handleUnsavedChange}` hunks (now `:3120`, `:3165`) were already in the working tree and were left as
they were.

- **One guard, at the funnel.** All the producers in BUG-024's blast-radius table reach this one effect: T7 cold loads
  and reopens, the Version-menu `handleOpenLiveRun`, the History and Home rows, the Back remount, and resume. A guard in
  each caller would miss the others.
- **`parseViewPath`, not `startsWith("/runs/" + id + "/")`.** BUGS.md's triage sketch used a hand-written path
  literal, which [ADR-0018](20260824-1631-ADR-0018.md) calls a defect. It would also miss the bare `/runs/{id}`. The
  parse uses the same form as `frontend/src/app/error.tsx:24`.
- **No `decodeURIComponent`.** BUG-024's snippet decoded each segment. I left that out. `routes.runStream` and the other
  run builders do not encode the id (`routes.ts:92-121`), so nothing needs decoding. And `decodeURIComponent` throws
  `URIError` on a malformed `%` sequence, which would crash this effect on any such path.
- **`window.location.pathname`, not `usePathname()`.** The card explains why: the render tests mock `next/navigation`
  with `useRouter` only, and `pathname` follows the `pushState` tab switches.
- **The push was not removed and does not read status.** Launch, revision and resume still depend on it (FR-010).
  [ISS-957](20261002-0316-ISS-957.md) explains why a status-keyed guard would not work.

## Behaviour now

| producer | before | after |
|---|---|---|
| cold load or reopen of any `/runs/{id}/<screen>` of a live run (QA-KB-049, ISS-956, ISS-957) | rewritten to `/stream` | stays |
| Version-menu live member, History and Home row opens (ISS-958) | rewritten | stays on the pushed URL |
| Back after a cold load (ISS-959) | bounced forward | no push, so no extra history entry |
| fresh launch: URL names no run (`/dashboard`, `/create/*`, the wizard) | `/stream` | `/stream` (unchanged) |
| revision from a run page: URL names the parent, the new run id differs | `/stream` | `/stream` (unchanged) |
| Resume or Run Again of the same run from its own `/runs/{id}/<tab>` | `/stream` | **stays on that URL** |

The last row is the behaviour change BUG-024 asked verification to confirm. BUGS.md's Expected supports it ("Only a
fresh launch lands on /stream"). The live view still updates there: `handleResumeRun` calls
`runConnection.attachRun(run_id)` itself, and the page's fan-out subscriber lives for the whole mount. Because the page
no longer remounts on resume, the remount gap that [ISS-220](20260828-1712-ISS-220.md) and
[FIX-330](20260828-2047-FIX-330.md) dealt with is not opened on this path. If product wants resume to land on
`/stream`, BUG-024 gives the follow-up: a one-shot ref set in `handleResumeRun` that bypasses the guard.

## Not fixed here

- [ISS-960](20261002-0316-ISS-960.md) is still open, and its own card says the root fix does not cover it. Reload
  `/library`, `/runs` or `/dashboard` in a tab that owns a generating run, and `useRunStateStore.ts:455-457` adopts the
  replayed `pipeline_start` as the viewport. The URL names no run, so the guard still pushes `/stream`. The card offers
  two fixes and picks neither: a launch-origin ref set by the launch, resume and revision handlers, or not adopting a
  `pipeline_start` that arrives during replay. No test exists for it yet.
- INFERRED and not settled offline: that skipping the push also keeps the TAB, not only the URL. With no remount,
  T7's `.finally` deep link (`page.tsx:3560-3562`) lands on the same mount, and PreviewPanel's merged effect
  (`PreviewPanel.tsx:1262-1297`) lets a fresh deep-link nonce win over the state default. The render test mocks
  PreviewPanel, so the browser re-run is what proves this part.
