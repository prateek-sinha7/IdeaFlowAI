## Source

Found while analysing QA-KB-033 / [ISS-442](20260829-0106-ISS-442.md). That card's root
cause is a whole-file occurrence count used as a proxy for a per-site property, which
implies every other test of the same shape. This is the only other one that qualifies:
the remaining candidates were read and rejected, with reasons, in ISS-442's analysis.
Not fixed here; out of scope for QA-KB-033.

**Status: INFERRED.** The mechanism is demonstrated below on the real source (mutated in
memory only). No real change has tripped it yet, so this is a lead, not a live defect.

## What is broken (CONFIRMED by reading)

`frontend/src/app/[...view]/launchImageAndRecents.source.test.ts:31-34`:

```ts
  it("carries images in BOTH the prototype and ppt setters", () => {
    expect(
      dashboardPage.split("pending.images && pending.images.length > 0").length - 1,
    ).toBe(2);
```

`dashboardPage` (line 18) is `readFileSync(resolve(__dirname, "./page.tsx"))`, which from this
directory is `frontend/src/app/[...view]/page.tsx` (4,469 lines), not a separate dashboard page.

The claim is per setter ("BOTH"); the evidence is an aggregate over the whole file. The two real
sites in `page.tsx` are `setPendingOdProtoParams({` (line 2527) with its guarded spread at line
2542, and `setPendingOdPptParams({` (line 2611) with its spread at line 2626, one each. There
are exactly two launch-staging setters (`grep -nE 'setPendingOd[A-Za-z]*Params\('` also finds
only the two `onClearPendingOd*` call sites), so "2" is a closed-set claim.

## Why ISS-442's root cause implies it (demonstrated, not yet triggered)

Real `page.tsx` text, mutated in memory only; nothing was written to the repo:

| scenario | count | `toBe(2)` |
|---|---|---|
| HEAD as it is | 2 | pass |
| a legitimate third reader of `pending.images` with the same guard | 3 | FAIL, a false alarm |
| the ppt setter loses its images spread while an unrelated site gains the same guard | 2 | pass, so the exact regression this test exists for is missed |

Today the file is green: `npx vitest --run 'src/app/[...view]/launchImageAndRecents.source.test.ts'`
printed `Tests  3 passed (3)` (vitest 4.1.11, 2026-10-01).

Likelihood is much lower than for ISS-442. That pin broke twice in a month because the 403/404
idiom is meant to spread. This one only trips if a third reader of `pending.images` is added.

## Disposition

Open, low priority, **do not fix as part of QA-KB-033**. It is the same policy question as
ISS-442 (should an exact whole-file count stand in for a per-site check), so decide once.

If the policy is "per-site, not aggregate", the fix is small here because the two setters have
unique anchors: slice each setter call from `setPendingOdProtoParams({` / `setPendingOdPptParams({`
and assert each slice contains the length-guarded images spread, then drop the count.

## Resolution (QA-KB-033 fix, 2026-10-01)

Resolved by [FIX-678](20261001-2124-FIX-678.md). The Disposition above said "do not fix as part
of QA-KB-033" and "decide once". The line then put this card on QA-KB-033's ledger row, and the
dispatch applied the floor decision from [ISS-442](20260829-0106-ISS-442.md) to both cards.
`launchImageAndRecents.source.test.ts:40` is now `).toBeGreaterThanOrEqual(2);`. The `it` title is
now "keeps a floor of 2 length-guarded images spreads, one per launch setter (prototype + ppt)".
The old title claimed "BOTH", which a whole-file count cannot prove. The comment (`:31-41`) names
both setters. This fix did not edit `page.tsx`. At 21:20 another bug's fixer added five
unrelated lines, so the two spreads are now at `:2545` and `:2629`. Observed by the fixer (cwd
`frontend/`):

- `npx vitest run 'src/app/[...view]/launchImageAndRecents.source.test.ts'` gave
  `Tests 3 passed (3)` before the edit (21:17:31), after it (21:19:19), and again at 21:26:49
  after the unrelated `page.tsx` edit
- `evidence/qa-kb-033/fix-mirror.sh` ran the real test file against mutated copies of `page.tsx`,
  once on the committed test file and once on the fixed one. A third legitimate reader (count 3)
  was red before and is green after. The ppt setter dropping its spread (count 1) is red both
  times. The compensating case (count 2) is green both times. The per-setter slice form named in
  the Disposition would close that gap; it was not done.
