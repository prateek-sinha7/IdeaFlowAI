# ISS-984

**INFERRED sibling of [ISS-919](20261001-2221-ISS-919.md) (QA-KB-059), derived by the analyzer on 2026-10-02.** The client half (button state and payload) was run offline; the end-to-end loss of a real override was not. An unreproduced sibling is a lead, not a defect.

Line numbers are the working tree on 2026-10-02 (HEAD `024c03ef8`). `IdeaInputPage.tsx` carries uncommitted [FIX-702](20261002-0040-FIX-702.md) hunks, so its numbers sit about 24-33 above HEAD's.

## Condition

A user with an ENABLED override of a built-in that renders `IdeaInputPage` (`user_stories`, `app_builder`, ...) opens `/create/<type>` while `GET /api/workflows/<type>` fails (5xx, network, timeout; a 404 is a different case, below) and clicks "Save as my version".

## Expected vs actual

- **Expected:** "Save as my version" is disabled, with a `title` saying why (the wording `LaunchWizard.tsx:1425-1428` carries since [FIX-701](20261002-0037-FIX-701.md): "Couldn't check for your saved version of this workflow. Reload to try again."), because the page cannot know what it would overwrite. "Save workflow" stays enabled: it creates a new row and never touches the override.
- **Actual (OBSERVED OFFLINE, scratch T3, `evidence/qa-kb-059/03-analyze-scratch-run.txt`):** with `getWorkflowDetail` rejecting, `saveAsMyVersion.disabled=false errorBannerShown=false`.

## Why the root cause implies it (each step read)

[ISS-919](20261001-2221-ISS-919.md)'s cause is that nothing models "the roster is final". A failed fetch is the same missing state read by the same consumers:

1. The `.catch` (`IdeaInputPage.tsx:1329-1341`) clears the manifest state and sets `loadError` (`:1339`). Nothing re-seeds the roster: `manifestAgents` was already `undefined`, so the roster effect's dependencies (`:1437`) do not change and `pipelineAgents` stays the library roster (`:1001-1012`).
2. The buttons read `pipelineAgents.length === 0` only (`:1983`, `:1998`). The banner reads `loadError && pipelineAgents.length === 0 && !isMigrationMeta` (`:2029`), so with a non-empty library roster the failure is invisible. [FIX-351](20260828-2347-FIX-351.md) scoped the banner to the empty roster on purpose: its locked constraint is "A `getWorkflowDetail` failure that leaves the roster empty is surfaced on the screen".
3. A click sends the same payload as the pending case in [ISS-919](20261001-2221-ISS-919.md) (`overrides_pipeline_type: workflowId`, `agent_ids` = the library roster; observed in T2) and the server UPSERTs it over the real row (`backend/app/api/user_workflows.py:807-847`, no version or concurrency check).

## Why this is a card of its own

It rides ISS-919's fix (same state, same component), but a naive fix gets it wrong in BOTH directions, and each direction is a separate test:

- A settle flag set in `.finally`, or in both branches without a failure term, re-enables the UPSERT after a failed GET. That is this card.
- A flag set only on success and applied to BOTH buttons (what the QA-KB-059 triage sketch reads as written: "set true in the getWorkflowDetail .then ... success only") disables "Save workflow" for good after any settled failure. That includes `migration`: its GET 404s by design (`backend/app/api/workflows.py:445`, an id outside `_KNOWN_WORKFLOW_IDS`, which `_discover_manifest_ids()` builds at `:120` from `agents/workflows/<id>/workflow.yaml`; there is no `agents/workflows/migration/`; the page comment at `IdeaInputPage.tsx:2023-2028` says the same), and the effect depends on `[workflowId]` only (`:1345`), so it never re-fetches after the user picks a sub-path. Today "Save workflow" works there once a path is chosen (`:1983`), so success-only would regress it.

So the state must tell loading, ready and failed apart, as `LaunchWizard`'s `overrideLoad` does (`LaunchWizard.tsx:295`): "Save workflow" and "Advanced" need not-loading, "Save as my version" needs ready.

## What would settle it end to end

Browser, account with an enabled `user_stories` override (create one with "Save as my version" on `/create/user_stories` if the account has none; it is test data): `page.route('**/api/workflows/user_stories', r => r.fulfill({ status: 503, body: '{}' }))`, wait for "Advanced N agents" with N > 0, click "Save as my version", capture the POST `/api/user-workflows` and ABORT it (never let the write through). The defect is a captured body with `overrides_pipeline_type: "user_stories"` and the system roster, not the override's.
