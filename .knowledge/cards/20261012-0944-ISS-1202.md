# ISS-1202

**Register source:** sibling derived during the `QA-KB-121` analysis on 2026-10-12 (root [ISS-1199](20261012-0944-ISS-1199.md)). Not its own bug row.

**Confidence.** The string is CONFIRMED offline: it was built by the installed `anthropic` 0.125.0 client's own response-to-exception path and run through the REAL `_sanitize_agent_error` source
(`evidence/qa-kb-121/analysis-02-other-providers-probe.txt`). INFERRED: that the live Anthropic API answers a revoked key with exactly that body, and that the app behaves the same end to end (no run was started).

## Condition

`ANTHROPIC_API_KEY` is set. That is the first rung of `build_model` (`model_factory.py:433`), used by local dev, and a revoked or invalid key is rejected by the provider on the first model call.
The preflight cannot help: its docstring says Anthropic's and Mistral's keys "carry no equivalent structural signal" (`model_factory.py:128-131`), so, exactly as for the Bedrock key, the first model call is
the only place the rejection can be reported.

## What happens (offline-confirmed)

- The anthropic SDK raises `AuthenticationError` with `str(exc)` = `Error code: 401 - {'type': 'error', 'error': {'type': 'authentication_error', 'message': 'invalid x-api-key'}}`.
- `_is_transient_throttle` is False for it (401 is not in `_TRANSIENT_STATUS`, `backend/agents/model_policy.py:485`), so the runner swallows it into the `error` event and the engine calls
  `_sanitize_agent_error` (`engine.py:10429`).
- None of the 12 credential needles (`engine.py:233-244`: `credential`, `unauthoriz`, `access denied`, `expiredtoken`, `invalidclienttokenid`, `accessdenied`, `unrecognizedclient`,
  `authentication failed`, `security token`, `not authorized`, `forbidden`, `signature`) occurs in that text (`authentication_error` is not `authentication failed`; `x-api-key` is not `credential`).
  The function returns `_GENERIC_AGENT_ERROR_MESSAGE`, "The model rejected this request." (`engine.py:295`).
- Mistral's 401 is `Client error '401 Unauthorized' for url ...`; it is caught only by accident, through `unauthoriz`, and then gets the cloud-session sentence, which is wrong for a Mistral key too.

The generic sentence reads as if the request were wrong. The engine's own comment records that failure mode for provider 5xx: it "read as the request being wrong and could not be told apart from a
refusal" (`engine.py:248-249`). The chat path is not affected in the same way: `llm_errors.map_exception` already maps an Anthropic 401 or 403 to `auth_error` (`llm_errors.py:139-140`).

## Expected vs actual

Expected: a rejected API key is named as such, with the remedy, for every provider the chain can select. Actual: Bedrock gets the cloud-session sentence ([ISS-1199](20261012-0944-ISS-1199.md)); Anthropic gets
the generic one.

## Why the root cause implies it

Same closed substring table, vocabulary limited to AWS wording plus a few generic words. The owner's decision on [ISS-1199](20261012-0944-ISS-1199.md) is scoped to Bedrock, so a fix that adds only
Bedrock-shaped needles leaves this open. The cheapest fix is the same row: give the new "API key rejected" row the needles `authentication_error` and `invalid x-api-key` and a provider-neutral copy.

## Fix direction (INFERRED, not applied)

In the row [ISS-1199](20261012-0944-ISS-1199.md) adds above the credential row: add `"authentication_error"` and `"invalid x-api-key"` to the needles and keep the copy provider-neutral ("the provider's
API key ..."). A shared literal cannot name the right env var per provider, because the table matches on text and carries no provider name; either leave the env var out of the shared copy or keep a
separate Bedrock-only variant. Whether to widen beyond Bedrock is the owner's call; the conservative outcome is to record this as accepted for a dev-only key.

Traps: do not add the bare needle `401` or `error code` (matches too much, for example a 401 from a tool's HTTP call quoted in an error); keep every return a literal (WR-02).

## Test notes

Offline: `_sanitize_agent_error("Error code: 401 - {'type': 'error', 'error': {'type': 'authentication_error', 'message': 'invalid x-api-key'}}")` must not equal `_GENERIC_AGENT_ERROR_MESSAGE` (red today). Controls: the
Mistral 401 text keeps a credential-class message; `test_image_payload_guard.py:234-237` (unknown text stays generic) stays green.
