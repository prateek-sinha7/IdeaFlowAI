## What is suspected

[ISS-328](20260828-1834-ISS-328.md) root-caused the reported "Run Workflow enables with zero
agents, click does nothing" symptom to `WorkflowView.tsx`'s disabled gate (line 473, checks only
`ideaInput.trim()`) plus `handleRun` (lines 161-167), whose `if (onStartPipeline)` guard fails
silently because the component's one and only caller —
`frontend/src/app/workflow/page.tsx:58-62` — never passes `onStartPipeline`.

Reading `WorkflowView.tsx` further shows the same unwired-props gap reaches beyond the Run
button itself. The component also never receives `pipelineState`, `onResetPipeline`, or
`onViewResults` from that same one caller, and two more pieces of its own state machine depend
on those:

- `pipelineState` (lines 130-138) falls back to a static default whenever the optional
  `externalPipelineState` prop is absent:
  ```ts
  const pipelineState = externalPipelineState || {
    isRunning: false, pipeline_type: "", agents: [],
    currentAgentIndex: -1, totalDuration: null, completedCount: 0,
  };
  ```
  Since `app/workflow/page.tsx` never passes this prop, `pipelineState` is this exact static
  object on every render, forever.
- The step-transition effect (lines 141-148) is the *only* code in the file that ever calls
  `setStep("running")` or `setStep("complete")`, and both branches gate on that same
  permanently-static object: `pipelineState.isRunning` (always `false`) and
  `pipelineState.agents.length > 0` (always `0`, a literal empty array). Neither condition can
  ever be true on this route.
- `step` itself starts at `"build"` (line 96, `useState<WorkflowStep>("build")`), and nothing
  else in the file writes to it besides that effect and `handleSelectFeature` (which only ever
  sets `"build"`, never `"running"`/`"complete"`).

So on `/workflow`, `step` is provably frozen at `"build"` for the lifetime of the page: Step 3
(`"running"` — the live `PipelineGraph`, lines 484-500) and Step 4 (`"complete"` — the same
graph plus the "View Results" and "Run Another Pipeline" footer buttons, lines 524-553) are dead
code on this route — not merely hard to reach, but structurally unreachable given the current
caller.

## Condition

Given the current single caller (`app/workflow/page.tsx`) never supplies
`onStartPipeline` / `pipelineState` / `onResetPipeline` / `onViewResults`: on `/workflow`, no
sequence of clicks, the `Cmd+Enter` keyboard shortcut on the textarea (line 320, which calls the
identical `handleRun`), or Agent Library interactions can ever move `step` off `"build"`.

## Expected vs actual

**Expected:** if `WorkflowView` renders a 4-step flow (select -> build -> running -> complete)
with a live pipeline graph and post-run actions, a user on `/workflow` should be able to reach
all of it once a run starts — or, if this route is never meant to actually run anything, it
should not present a Run control and a graph/results UI that no interaction can ever surface.

**Actual (predicted):** Steps 3 and 4 — the running-pipeline graph, "View Results", and "Run
Another Pipeline" — are permanently dead code on `/workflow`; the page can only ever show Step 2
("build"), no matter what the user does, because nothing this component is ever given can flip
`pipelineState.isRunning` or populate `pipelineState.agents`.

## Why the root cause implies this

Same mechanism ISS-328 already names — `app/workflow/page.tsx` wiring only `pipelineType`,
`userMessage`, and `onClose`, and nothing else `WorkflowView` accepts — just followed one layer
further: ISS-328 shows the immediate click is a no-op; this shows why nothing downstream of a
successful run could ever render either, even if the click guard were bypassed some other way.
Both symptoms trace to the identical unwired-prop gap in the same one caller, so the fix belongs
in the same place ISS-328's fix does — either wire real callbacks/state into `<WorkflowView>` at
`app/workflow/page.tsx:58-62`, or retire this route. It structurally sits outside
[ADR-0018](20260824-1631-ADR-0018.md)'s "every URL is built and parsed by `routes.ts`, all
screens render behind one required `[...view]` catch-all" — `/workflow` is a hand-written
Next.js file route with no `routes.ts` builder — and its likely intended replacement,
`IdeaInputPage.tsx` (reachable via the catch-all), already implements this exact brief+agents+Run
flow correctly, guard included: `IdeaInputPage.tsx:1334` and `:1721` both check
`pipelineAgents.length === 0` where `WorkflowView.tsx:473` does not.

**Marked INFERRED**: confirmed entirely by reading `WorkflowView.tsx` (lines 96, 130-148, 161-167,
320, 484-553) and `app/workflow/page.tsx` (lines 58-62) — the unreachability is a direct, provable
consequence of that code, not a guess. Not independently browser-verified: nobody drove
`/workflow` this session specifically trying to reach Steps 3/4. What would settle it: attach a
breakpoint/log on `setStep` while exhaustively driving `/workflow`'s UI (attach file, add/remove
agent, voice input, Cmd+Enter, click Run) and confirm it is only ever called with
`"build"`/`"select"`, never `"running"`/`"complete"`.
