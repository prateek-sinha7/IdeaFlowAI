# ISS-1001

## Description

INFERRED sibling of [ISS-347](20260828-2058-ISS-347.md) (root of QA-KB-062). Half B1 is observed
offline against the real `LaunchWizard` (`evidence/qa-kb-062/analysis-proof-launchwizard-chain.out.txt`,
case R4, a characterisation); half B2 is derived from reading and cannot be reproduced until a
precedence fix exists. Not reproduced live: the trigger is an abandoned chain push.

Both hand-off channels the wizard reads on mount are plain sessionStorage keys:

- `chain.*`, written by `handleChainPipeline` (`frontend/src/components/layout/DashboardLayout.tsx:1922-1941`)
  and `handleChainFromHistory` (`:2024-2045`);
- `<mode>.draft`, written by `handleEditBrief` (`:2393`), `handleLaunchSaved` (`:1685`, `:1712`) and
  the cold `/workflows/{id}/run` effect (`frontend/src/app/[...view]/page.tsx:3989`).

Neither payload records which navigation wrote it or when. The reader can therefore only choose
by precedence, and precedence cannot tell a stale value from a fresh one on either side.

**B1 — draft-less open (observed, R4).** With no draft staged, a stale chain trio hijacks a
plain open. Entry points that stage nothing: the Home catalog
(`frontend/src/components/catalog/HomeLaunchGrid.tsx:247` -> `selectWorkflowWizardPath`),
`DashboardLayout.handleSelectFeature` (`:1577-1578`), a cold `/create/ppt` via `wizardModeFor`
(`page.tsx:349-364`). R4: stale `chain.from`/`chain.brief`/`chain.source_run_id`, fresh
`<LaunchWizard initialMode="prototype">` -> `{"briefEditorVisible":false,"continuingBanner":true}`;
the stale brief is pre-filled behind a hidden editor. The fix sketched in BUGS.md for QA-KB-062
("read the mode's draft key first; if a draft exists ignore chain.brief ...") does not touch this
case, because there is no draft to win.

**B2 — inverse (derived).** Once the reader prefers a draft, a STRANDED draft outranks — and,
per that sketch, deletes — a genuine chain hand-off written moments earlier: the user chains
from run X into ppt, `handleChainPipeline` writes `chain.*` and pushes, the wizard finds an old
`ppt.draft` first and drops the chain keys, so the user gets the old draft and no source
linkage. A draft can be stranded by: today's early return (R1: `draftKeyStillStored: true`); the
retention rule `LaunchWizard.tsx:446-447` (`if (!d.agentIds || d.agentIds.length === 0 ||
libraryAgents.length > 0) { removeItem(draftKey) }`), which keeps a draft that has `agentIds`
while the agent library is still empty, so an unmount before the library arrives strands it; or
a writer that stages a draft and then fails to navigate. Narrow once ISS-347's early return is
gone, but not empty.

## Why the root cause implies it

ISS-347's root is "ambient session state, no tie to a navigation". A precedence rule (chain
first today, draft first in the sketch) only picks a winner between two unverified values; it
does not make either value trustworthy. The second clause of QA-KB-062's Expected — "a chain
hand-off applies only to the navigation that wrote it" — is met only by scoping, which is also
what ISS-347's own Disposition asks for ("stamped with the target mode and dropped when it does
not match").

## Expected vs Actual

- **Expected:** a hand-off is consumed only by the navigation that wrote it, and, symmetrically,
  a staged draft applies only to the navigation that staged it.
- **Actual:** B1 (R4) a stale chain trio shapes a fresh open; B2 a stale draft would shape a
  genuine chain once draft-first precedence is introduced.

## Where the fix belongs

A design choice for the fixer; it is technical, not a product question. Options, cheapest first:

1. Stamp each payload with `{target mode, written-at}` and let the wizard accept only a stamp for
   its own mode that is a few seconds old. Writers to touch: the two chain writers, the four
   draft writers, and `WorkflowHistory`'s `chain.v2.source_status` (see
   [ISS-1002](20261002-0500-ISS-1002.md)); the reader stays the single decision point.
2. Each writer clears the other channel before writing, which makes draft-first precedence
   safe; B1 stays open unless the draft-less entry points also clear `chain.*`.
3. Carry the hand-off in the navigation itself (router state or query); any URL must come from
   `frontend/src/lib/routes.ts`, the single URL source.

Not required to close QA-KB-062 if the owner accepts "draft wins plus drop chain keys" as the
whole fix; record the decision either way so B1/B2 are not rediscovered.

## Decision recorded: FIX-723 (2026-10-07)

QA-KB-062 shipped the precedence fix, not scoping: [FIX-723](20261007-1810-FIX-723.md). It is "draft wins, drop every
chain key, never arm chainFrom", decided in `LaunchWizard`'s pickup effect. This card stays **open**. Both halves
above are still true:

- **B1 is unchanged.** Proof R4, re-run after FIX-723 (`evidence/qa-kb-062/fix-02-proof-r0-r6-after.txt`), still shows
  `{"briefEditorVisible":false,"continuingBanner":true}` and `chain.source_run_id` left for a draft-less open with a
  stale trio.
- **B2 is now live by construction.** A stranded `<mode>.draft` outranks and deletes a genuine chain hand-off. One
  stranding source is gone: ISS-347's early return, so the draft is now consumed. Others remain: the `agentIds`
  retention rule (`LaunchWizard.tsx:485-487`, the draft is kept while the agent library is empty) and a writer that
  stages a draft and then fails to navigate.
- **The [ISS-1002](20261002-0500-ISS-1002.md) writer half also lands here.** A stranded `chain.v2.source_status` can
  still ride into a later genuine chat-lane chain.

**Cheapest next step:** option 2 above. Each chain writer (`handleChainPipeline`, `handleChainFromHistory` in
`DashboardLayout.tsx`) would remove `ppt.draft` / `prototype.draft` and `chain.v2.source_status` before writing. That
closes B2 and the ISS-1002 residual, and leaves B1 to option 1 or 3. It was not done in QA-KB-062 for two reasons:
`DashboardLayout.tsx` and `[...view]/page.tsx` are in QA-KB-060's ([ISS-923](20261001-2223-ISS-923.md)) globs, which
were in flight on the same line, and this card's own text says the fix is not required to close QA-KB-062.
