# ISS-824

## Description

Deferred finding from [FIX-618](20260922-1945-FIX-618.md), which routed
`getMe` through `cachedGet` (`frontend/src/lib/api.ts:446`).

`frontend/src/lib/api.refreshRetry.test.ts` ends with:

```ts
it("coalesces concurrent 401s into a SINGLE refresh call", async () => {
  ...
  const [a, b, c] = await Promise.all([
    getMe(STALE(5)),
    getMe(STALE(5)),
    getMe(STALE(5)),
  ]);
  ...
  expect(refreshCalls).toHaveLength(1);
});
```

Its stated intent is in the file header: "The single-flight assertion matters
because a screen fires several calls at once, so one expiry produces a burst
of simultaneous 401s." It is the only test of `refreshOnce()`
(`api.ts:227-234`).

Now that `getMe` reads through the shared GET cache, the three calls share ONE
promise and produce ONE `/api/auth/me` request, so exactly one 401 and
therefore exactly one `/api/auth/refresh` is reached **whether or not
`refreshOnce()` single-flights at all**. The assertion still passes; it no
longer discriminates.

The test was left as-is by FIX-618 rather than rewritten — changing what a
test proves is not a fixer's call to make silently.

## Expected vs actual

- Expected: deleting the `inFlightRefresh` guard from `api.ts` makes this test
  go red.
- Actual (predicted, not yet run): it stays green, because the burst of
  concurrent 401s it needs can no longer originate from three `getMe` calls
  with the same bearer.

## What would settle it

Temporarily remove `refreshOnce()`'s memoisation (call `refreshAccessToken()`
directly) and run `npx vitest run src/lib/api.refreshRetry.test.ts`. A green
run confirms the test is vacuous.

## Where a fix belongs

Drive the concurrent burst from calls that are NOT shared-GET cached — e.g.
three different endpoints that all send the stale bearer, which is also closer
to the real "a screen fires several calls at once" scenario the header
describes — or assert on `/api/auth/me` call count alongside the refresh
count so the collapse is visible rather than silent.

## TEST COVERAGE — ISS-824

None. Found by reading, not by a failing run: the test is green today, which
is precisely the problem.

## Validation (QA-KB-028, 2026-10-01)

Reproduced 3/3 from cold start (Test mode, no browser). In `frontend/`, `api.ts` `refreshOnce()` memoization was disabled by changing `if (!inFlightRefresh) {` to `if (true) {` (api.ts ~L428), then `npx vitest run src/lib/api.refreshRetry.test.ts` was run three times. Each run reported `Tests 6 passed (6)`, including the coalesce test, so the test does not guard single-flight. The edit was reverted after the runs (`git diff` on api.ts is empty). Cause confirmed: `getMe` uses `cachedGet("/api/auth/me")` (api.ts:941), which collapses the three concurrent calls to one request and one 401. No conditions beyond this. Evidence is the command output above; no screenshots apply.

## Analysis (QA-KB-028, 2026-10-01)

**Decision: the defect is in the TEST. `api.ts` is correct and stays untouched.** The fix is one test
body in `frontend/src/lib/api.refreshRetry.test.ts`. One `/api/auth/me` request for three identical
`getMe` calls is the intended [FIX-618](20260922-1945-FIX-618.md) outcome (`/api/auth/me` 3-4 -> 1,
measured there); the guard itself works (the replacement below is green with it and red without it);
and exempting `getMe` from the cache would undo QA-PS-035 while fixing nothing the guard needs.

### Root cause (CONFIRMED: every line below was read in the tree; `api.ts` and the test are unmodified vs HEAD)

1. Guard: `inFlightRefresh` / `refreshOnce()` at `frontend/src/lib/api.ts:426-435`, entered from
   `fetchWithAuth` at `api.ts:553` (`const fresh = await refreshOnce();`).
2. Collapse: `getMe` is `cachedGet<User>("/api/auth/me", token)` (`api.ts:941`). `cachedGet` keys on
   `${token}\u0000${path}` (`api.ts:639`) and returns the stored promise on a hit (`api.ts:641`), so
   identical same-tick calls never become separate requests.
3. Test: `api.refreshRetry.test.ts:149-153` fires `getMe(STALE(5))` three times and asserts
   `refreshCalls` has length 1 (`:162`); its header (`:16-18`) says the point is that "a screen fires
   several calls at once". After the cache that is one call.
4. Origin: commit `fa559d08f` ("one owner per fetch") added the `getMe` -> `cachedGet` routing (the only
   commit a `git log -S` pickaxe finds) and, in the same commit, rewrote this test's bearers
   (`"stale.access.token"` -> `STALE(n)`), leaving the burst as three identical calls.
5. Mechanical proof, run in a scratch copy of `frontend/` (copied `api.ts` and test byte-identical to the
   tree per `diff`; the live tree was never edited). Fetch trace of the ORIGINAL burst, identical with the
   guard on or off: 3 fetches = `/api/auth/me [stale]` (401), `/api/auth/refresh`, `/api/auth/me [fresh]`.
   The unchanged test with `if (!inFlightRefresh) {` -> `if (true) {` (`api.ts:429`) gives
   `Tests 6 passed (6)`, matching the validator's 3/3 above.

### Fix: the replacement burst (VERIFIED in the scratch copy)

Import line becomes `import { getMe, getMfaStatus, getPreferences, login, setToken, getToken } from "@/lib/api";`
and the last-but-one `it` becomes:

```ts
  it("coalesces concurrent 401s into a SINGLE refresh call", async () => {
    // The burst must be three DIFFERENT requests sharing one stale bearer — what a
    // screen really fires. Three identical getMe(STALE(n)) calls collapse into one
    // shared-GET-cache request (ISS-801), so only ONE 401 reaches the guard and the
    // refresh count is 1 with or without it (ISS-824).
    fetchMock.mockImplementation((url: string, init?: RequestInit) => {
      if (String(url).includes("/api/auth/refresh")) {
        return Promise.resolve(okJson({ token: "fresh.access.token" }));
      }
      const bearer = new Headers(init?.headers as HeadersInit | undefined).get(
        "Authorization",
      );
      return Promise.resolve(
        bearer === "Bearer fresh.access.token"
          ? okJson({ path: String(url) })
          : unauthorized(),
      );
    });

    const [me, prefs, mfa] = await Promise.all([
      getMe(STALE(5)),
      getPreferences(STALE(5)),
      getMfaStatus(STALE(5)),
    ]);

    // Each caller got ITS OWN request replayed with the refreshed bearer.
    expect(me).toEqual({ path: expect.stringContaining("/api/auth/me") });
    expect(prefs).toEqual({ path: expect.stringContaining("/api/settings/preferences") });
    expect(mfa).toEqual({ path: expect.stringContaining("/api/auth/mfa") });

    const calls = fetchMock.mock.calls.map(([url, init]) => ({
      url: String(url),
      bearer: new Headers(init?.headers as HeadersInit | undefined).get("Authorization"),
    }));
    // Precondition: the burst really materialised. If an upstream cache or dedup
    // collapses these again this fails here instead of passing vacuously below.
    expect(calls.filter((c) => c.bearer === `Bearer ${STALE(5)}`)).toHaveLength(3);

    const refreshCalls = calls.filter((c) => c.url.includes("/api/auth/refresh"));
    // Without the single-flight guard this would be 3 — and the losers would
    // install a token a later refresh had already superseded.
    expect(refreshCalls).toHaveLength(1);
  });
```

Results (scratch copy, `npx vitest run src/lib/api.refreshRetry.test.ts`, one file, offline, ~1 s):

- ORIGINAL test, guard disabled: 6/6 pass (the bug).
- Replacement, guard intact, 3 cold runs: 6/6 each.
- Replacement, guard disabled, 3 cold runs: the coalesce test fails each time with
  `expected [ { ... } x3 ] to have a length of 1 but got 3` (trace: guard on = 7 fetches / 1 refresh,
  guard off = 9 fetches / 3 refreshes).
- Replacement re-collapsed to three identical `getMe`, guard intact: fails at the precondition,
  `expected [ { ... } ] to have a length of 3 but got 1`, so a future re-collapse is loud, not silent.
- `tsc --noEmit` on the copy: 13 errors, all in other `*.test.tsx` fixtures; none in this test or `api.ts`.

### The agreed minimal fix (BUGS.md QA-KB-028 Notes): accepted in direction, overruled in specifics

- ACCEPT: a burst of different requests sharing one stale bearer, per-URL response bodies, keep
  `refreshCalls` at length 1.
- ACCEPT, but MANDATORY (the note said "optionally"): assert that three requests carried the stale
  bearer. This bug is a test that passed for the wrong reason; that line stops it happening twice.
- OVERRULE "`getRunSandboxZip`-like": `getRunSandboxZip` (`api.ts:1693-1697`) goes through `authedFetch`,
  which "does NOT attempt the silent refresh" (`api.ts:470-472`). Its 401 calls `handleSessionExpiry()`
  and clears the token instead of joining the burst. Only `request()` / `fetchWithAuth` callers reach
  `refreshOnce()`.
- OVERRULE "uncached" as a requirement: three DIFFERENT paths suffice even when cache-backed (the
  replacement uses `getMe`, `getPreferences`, `getMfaStatus`, all `cachedGet`); what matters is distinct
  requests. `getChats` also works but needs an array body.
- This card's own alternative ("assert `/api/auth/me` call count alongside the refresh count") makes the
  collapse visible but cannot make the guard testable: the original burst is 3 fetches with the guard on
  or off. It is useful only as the precondition above.

### Blast radius

- `refreshOnce()` has four production callers, all depending on the one guard: `api.ts:553` (every REST
  call that sends a bearer), `providers/AuthSessionProvider.tsx:85` (app-wide proactive refresh),
  `hooks/useRunStream.ts:106` (SSE; its comment at `:100-101` states the contract: "The API client
  coalesces simultaneous refreshes from the app-wide session owner, REST requests, and SSE streams"),
  `hooks/useHandoffSocket.ts:164` (WebSocket close 4001).
- No test exercises the real guard except the vacuous one: `useRunStream.test.ts:28` and
  `useHandoffSocket.test.ts:15` replace `refreshOnce` with `vi.fn()`, and `api.refreshRetry.test.ts` is the
  only file under `frontend/src` that mentions `/api/auth/refresh`. Today the guard has zero effective
  coverage and deleting it keeps CI green.
- Claims resting on the vacuous test: [ADR-0024](20260824-2100-ADR-0024.md) `verification.test_files` for its
  "single-flighted refresh" decision, and [FIX-618](20260922-1945-FIX-618.md)'s "Regression guards" bullet for
  `api.refreshRetry.test.ts`.
- INFERRED (not reproduced against Cognito): a silently regressed guard would mint one refresh per
  concurrent 401 and the losers would install a superseded token (`api.ts:418-425`).
- Line numbers: this card's description cites `api.ts:446` (cachedGet) and `api.ts:227-234` (refreshOnce);
  they have drifted to `:636` and `:428-434`.

### Siblings: none minted

one test. Checked, not assumed: with each OTHER guard disabled in the scratch copy, its own test goes red:

inverse or adjacent-state defect to derive.

### Also observed (outside this root cause; no card minted)

The test header claims three bounds are pinned (`:14-16`). Disabling the retry bound, the bearer-only bound
or the null-refresh fallthrough each turns the matching test red, but deleting `path !== REFRESH_PATH &&`
(`api.ts:550`) leaves 6/6 green. That clause is unreachable today (`REFRESH_PATH` appears only at
`api.ts:334`, `:403`, `:550`; `refreshAccessToken` uses a raw `fetch`), so it is a defensive clause with an
over-claiming comment, not a live defect. Whoever edits the header can soften "three bounds" or add the case.
