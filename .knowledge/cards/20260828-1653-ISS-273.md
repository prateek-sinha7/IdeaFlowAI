## Source

Validated from register entry `BUG-20260828-010600-workflows-id-run` in
`bug-hunter/ledger.md`.

## Reproduction (3/3, cold start)

Reproduced on **all 3 cycles**, each a fresh navigation from `/dashboard` to a distinct
`/workflows/{id}/run` URL that cannot resolve to a saved workflow (no click-through, no soft
re-click of the same screen):

- Cycle 1: `http://localhost:3000/workflows/00000000-0000-0000-0000-000000000000/run`
  (well-formed but nonexistent UUID). Dashboard content rendered under the bogus URL.
- Cycle 2: `http://localhost:3000/workflows/not-a-valid-uuid/run` (syntactically malformed id).
  Identical mismatch.
- Cycle 3: `http://localhost:3000/workflows/11111111-1111-1111-1111-111111111111/run` (a third,
  distinct nonexistent UUID, from a fresh cold nav via `/dashboard`). Identical mismatch.

Confirmed on every cycle via direct `location.href` and `document.querySelector('h1').textContent`
reads (not screenshots alone):

```js
{ href: "http://localhost:3000/workflows/<id>/run", h1: "What would you like to build today?" }
```

Console on every cycle carries the matching pair:

```
[ERROR] Failed to load resource: 404 (Not Found) @ http://localhost:8000/api/user-workflows/<id>
[ERROR] cold-mount workflow-run fetch failed: <id> ApiError: Saved workflow not found
    at .../store/api/userWorkflows_ts_....js:415:26
```

The `cold-mount workflow-run fetch failed` log line and the stack pointing into
`store/api/userWorkflows.ts`'s `get` call confirm the 404 is caught, not uncaught — the page's own
error-handling path chooses to render Dashboard content rather than surface it.

## Page / route / component

- Page: saved workflow's launch panel.
- Route: `/workflows/{id}/run`, both a well-formed-but-nonexistent UUID and a malformed id string.
- Component: `frontend/src/components/workflow/LaunchWizard.tsx` — the cold-mount fetch effect
  that calls `GET /api/user-workflows/{id}` and, on 404, falls through to Dashboard content
  instead of a not-found state, without updating `location.href`.

## Exact conditions

qa-admin (enterprise tier), default light theme, deep-link/cold entry path (direct navigation to
the URL, not click-through). Reproduced identically for both id shapes and across three distinct
nonexistent ids, so id shape and entry path are not the trigger — the trigger is any 404 from
`GET /api/user-workflows/{id}` on cold mount of this route.

## Expected vs actual

**Expected:** an id that does not resolve to a real saved workflow produces an explicit not-found
state (e.g. "This workflow no longer exists" + a link back to `/workflows`) or an actual
navigation to a real destination, with the URL and rendered content agreeing.

**Actual:** the page renders the full Dashboard catalog (`h1: "What would you like to build
today?"`, workflow cards, "Jump back in") in place while `location.href` remains the original,
unresolvable `/workflows/{id}/run` path indefinitely — a persistent URL/content mismatch.

## Distinct from ISS-228

`ISS-228` covers the same route and component but a **valid, existing** workflow id
(`656ca387-...`, `GET /api/user-workflows/{id}` returns `200 OK`) where a parallel-fetch race
discards whichever of two successful responses resolves second, rendering the generic

## Root cause (analyzer pass, CONFIRMED via source read)

**Correction to the component/file attribution above.** The original validator pass attributed
this to `frontend/src/components/workflow/LaunchWizard.tsx`'s "cold-mount catch," reasoning from the
console stack trace (`store/api/userWorkflows_ts_....js:415:26`, inside the `.get()` call itself).
That stack trace shows where the FETCH throws, not where the FAILURE is HANDLED. Source reading
shows `LaunchWizard.tsx` is never even rendered on this path: the component only mounts when
`workflowRunWizardMode` is non-null, and that state is set **only on the fetch's success branch**
(`frontend/src/app/[...view]/page.tsx:3655`). The actual cold-mount fetch, its catch handler, and
the render gate that decides what to show on failure are ALL in
`frontend/src/app/[...view]/page.tsx` — `applies_to` above has been corrected accordingly.

**The mechanism**, read directly from `frontend/src/app/[...view]/page.tsx`:

- The `/workflows/{id}/run` cold-mount effect (`:3620-3713`) calls `userWorkflowsApi.get(workflowId)`.
  Its `.catch()` (`:3692-3707`) does `if (err instanceof ApiError && err.status === 401) {
  handleSessionExpiry(); return; } setWorkflowRunFailed(true);` — so a 404 (or any other non-401
  error) sets `workflowRunFailed = true` (`:3706`) and nothing else.
- The render gate at `:3785-3791` reads:
  ```
  if (parsedView.screen === "workflow-run" && !workflowRunMainView && !workflowRunFailed) {
    return null;
  }
  ```
  Its documented purpose (`:3777-3784`) is ONLY to render nothing while the fetch is in flight.
  Once `workflowRunFailed` flips to `true`, `!workflowRunFailed` is `false`, the whole condition is
  `false`, and this gate no longer blocks anything — execution falls through every wizard/composer
  render-time return below it and reaches the unconditional `return <DashboardLayout ... />` at
  `:3818`. Since none of `workflowRunMainView`/`wizardMode`/`initialSavedComposition` were ever set
  (the success branch never ran), `DashboardLayout` renders its default Home/Dashboard catalog
  content. **No `notFound()`, `router.push`, or `router.replace` is ever called on this path** —
  which is exactly why `location.href` stays on the bogus `/workflows/{id}/run` URL indefinitely
  while Dashboard content renders in its place.

**This is a documented, structural omission relative to 3 sibling identity-fetch-failure gates in
the exact same component**, all of which correctly call Next's `notFound()` on the analogous flag:

| Route | Failure flag | Set at | Gated into `notFound()` at |
|---|---|---|---|
| `/runs/{id}` reopened / live-stream | `runAccessDenied` | `:3099` | `:3734-3736` |
| `/workflows/{id}/edit` | `workflowEditAccessDenied` | `:3519` | `:3741-3743` |
| `/workflows/{id}` read view | `workflowDetailFailed` | `:3570` | `:3751-3753` |
| `/workflows/{id}/run` (this card) | `workflowRunFailed` | `:3706` | **never — only gates the loading-`null` return** |

## Blast radius (CONFIRMED via grep)

`userWorkflowsApi.get(id)` — the call whose 404 triggers this — has exactly 3 call sites in the
whole frontend, and all 3 are inside this one file:
`grep -rn "userWorkflowsApi\.get(" frontend/src/` returns only `page.tsx:3482` (`/workflows/{id}/edit`,
correctly gated), `page.tsx:3542` (`/workflows/{id}` read view, correctly gated), and `page.tsx:3627`
(`/workflows/{id}/run`, this card, not gated). No other component fetches a saved workflow by id —
the click-driven launch path (`DashboardLayout.tsx`'s `handleLaunchSaved`) already has the object in
hand from the list it was opened from and never hits this fetch at all, which is why a valid id's
`/run` panel (confirmed against `656ca387-...`) is unaffected. So the blast radius is fully internal
to this one file's `workflow-run` cold-mount effect and its render gate — there is no other caller
to fix. This also matches the routing invariant this repo enforces (`ADR-0018`, `CONTEXT.md` §1):
every URL renders behind the one catch-all in `frontend/src/app/[...view]/page.tsx`, so there is
architecturally nowhere else this logic could live.

## Fix — where it belongs

Entirely inside `frontend/src/app/[...view]/page.tsx`'s `workflow-run` cold-mount effect
(`:3620-3713`) and its render gate (`:3785-3791`) — the same file and the same effect ISS-379 and
ISS-380 below also touch, not a new call site:

1. Add a `notFound()` branch for `workflowRunFailed`, mirroring the 3 siblings in the table above
   (e.g. `if (parsedView.screen === "workflow-run" && workflowRunFailed) { notFound(); }`, checked
   before the existing loading-`null` gate).
2. Per [ISS-380](20260828-2209-ISS-380.md): narrow the catch to only 403/404 before setting
   `workflowRunFailed` (matching `workflowEditAccessDenied`'s `:3518` and `workflowDetailFailed`'s
   `:3568` narrowing) — otherwise step 1 alone turns a transient 5xx/network blip on a real,
   owned workflow into a newly-introduced permanent not-found, which is a regression the fix itself
   would cause.
3. Per [ISS-379](20260828-2209-ISS-379.md): reset `workflowRunFailed` to `false` at the top of the
   effect, before the fetch fires, mirroring `workflowEditAccessDenied`'s existing `:3480` reset —
   otherwise a stale `true` from an earlier failed visit in the same SPA session defeats the
   loading-`null` gate on a later, entirely valid `/workflows/{id2}/run`.

All three changes are one effect + one render gate in one file — there is nothing to route other
callers through, since none exist.
