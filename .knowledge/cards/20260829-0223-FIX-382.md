## What was wrong

BUG-20260828-094120-settings-ai-model-r2 (`bug-hunter/ledger.md`), validated
3/3 cold-start cycles. Two concurrent `PUT /api/settings/preferences` calls for
the same user with different `preferred_model` values both returned `200 OK`,
one write was silently lost, and — the part that makes it worse than an
ordinary last-write-wins race — the losing request's own `200` body reported
the OTHER request's model. The client that asked for Opus 4.6 was told, by its
own successful response, that Opus 4.6 was saved when Sonnet 4.5 had been
persisted. No error, no console warning, no network-level signal on either side.

The "losing" slot was not fixed to A or B across the three validator cycles,
which is what distinguishes a genuine backend race from a client-side ordering
artifact.

## Root cause

`backend/app/api/settings.py:345-353` (`update_preferences`), per
[ISS-319](20260828-1804-ISS-319.md):

```python
user.preferred_model = model_id
db.add(user)
db.commit()
db.refresh(user)

return UserPreferencesResponse(
    preferred_model=user.preferred_model,   # <-- re-read of the ROW, post-refresh
    available_models=AVAILABLE_MODELS,
)
```

The handler is a `sync def` endpoint, so FastAPI runs it in a threadpool worker;
each concurrent request gets its own `Session` via `Depends(get_db)` but they
share one `users` row. The response was built from `user.preferred_model` AFTER
`db.refresh(user)` — i.e. from the row's current DB state, not from the value
this request wrote. A second request's `commit()` landing in the window between
this request's own `commit()` and its `refresh()` therefore rewrote what this
request was about to report.

[FIX-361](20260829-0029-FIX-361.md)'s tier-entitlement check landed between the
card being written and the fix, shifting the handler from `316-342` to
`317-353`. It neither closes nor widens the race: it runs before the mutation
and touches no DB row, and a request that fails entitlement raises 403 and never
reaches `db.commit()`.

## What changed, and why there

`backend/app/api/settings.py` only — the one file
[ISS-319](20260828-1804-ISS-319.md)'s `applies_to.globs` names. One expression:
the response is now built from `model_id` (the local, already-validated value
this request itself committed, `settings.py:327`) instead of a post-`refresh`
re-read of `user.preferred_model`. A short `# ISS-319:` comment above the return
records why, matching the file's existing `# ISS-292:` convention, so the
re-read is not reintroduced as a "simplification" later.

This meets the register entry's own "Expected" bar verbatim: last-write-wins at
the DB stays acceptable UX, but a `200` body must never report a value the
request itself did not send. No locking, no version column, no migration, no
new dependency.

**No shared function was introduced.** As
[ISS-319](20260828-1804-ISS-319.md) § "Where the fix belongs" concluded, the
three sites carrying this shape inline three DIFFERENT response models; a helper
for three call sites that share no return type would be a bigger diff than the
three one-line changes. Re-grepped `db.refresh(` across `backend/app/api/` before
editing — the blast radius in the card still holds, and no shared
mutate-commit-respond wrapper has appeared since it was written.

**Downstream readers are unaffected.** The 8 sites in
`backend/app/api/run_commands.py` that read `user.preferred_model` to pick the
Bedrock model, and `get_preferences` (`settings.py:306-314`), all read the
persisted row and were never part of this defect — they inherit whichever value
won the race, which is the accepted last-write-wins behaviour. Nothing about
what gets PERSISTED changed here; only what gets REPORTED.

## Not fixed by this card

The two INFERRED siblings sharing the identical
commit-then-refresh-then-respond-from-the-refreshed-object shape stay **open**.
Neither is on this bug's fix assignment, neither has been validated, and neither
carries a test (`verification.type: manual`, `status: pending`), so there is
nothing here that could prove a change to them:

- [ISS-470](20260828-2310-ISS-470.md) — `upsert_github_pat`, same file
  (`settings.py:114-176`). Proposed fix: source `github_username`/`scopes` from
  the already-fetched local `gh_user`/`scopes_header`.
- [ISS-471](20260828-2310-ISS-471.md) — `admin.py`'s `update_user_tier` /
  `update_user_role`, whose `_to_response(user, db)` reads `user.tier` /
  `user.is_admin` post-refresh. These are privilege fields, so a confirmed
  instance there is materially more serious than this one. `admin.py` is outside
  this card's `applies_to.globs`.

If a fourth instance of this shape turns up, the shared-helper decision should be
revisited — three differently-shaped responses was the reason not to build one.
