# ADR-0011: The delivery block owns the artifact filename

## Context and Problem Statement

A composed step's system prompt can carry three filenames at once. Observed verbatim
in a live Writer prompt (run `44bb9a9d`, topic `cow`):

```
step prompt   "Read combined.md."  /  "Save the paragraph to paragraph.md."
roster        "Earlier steps produced:  - Brief Builder → 17ha47o-fozd8o-cow.md"
delivery      "Call `write_file` with path `17ha47o-2m9ig1-cow.md`."
```

`combined.md` does not exist — the upstream step was itself redirected to its artifact
name. `paragraph.md` is never written. The model resolves the contradiction differently
from run to run: obey the delivery block (`glasses`, `cow`), write both files
(`topic-sky`), or break the chain entirely (`Tea`, a 0-byte artifact).

The obvious reading is that the delivery block is a bug overriding the author's intent.
It is not.

## Decision

**`artifact_name(instance_id, topic)` is the only name that counts.** The delivery block
is emitted for every `custom-agent:` step and names that file. A filename appearing in a
step's authored prompt has no effect on what the engine writes or reads.

## Rationale

Three mechanisms must agree on one filename, and only a derived name can guarantee it:

| Mechanism | Where | Why it needs the name |
|---|---|---|
| Artifact guarantee | `engine.py::_check_artifact_fallback` | Writes the streamed text when the agent wrote nothing, so a step always has an artifact |
| Roster | `engine.py::_build_roster` | Tells the next step which files exist |
| Deliverable readback | `engine.py`, `single_file` | Reads the final step's artifact off disk |

A user-authored filename is known only to the prompt. The other three would have to parse
it back out of free text, and any disagreement produces a step that reports success while
its downstream reads nothing. The derived name is collision-free by construction
(`instance_id` is unique per step) and known at compile time, before the run has a topic.

Removal was trialled during the 2026-08-13 debugging session and **reverted**: the chain
did execute end to end, but the artifact guarantee then wrote empty files for steps that
had written their own, and the roster advertised 0-byte artifacts to the next step. The
bug was traded for a worse one.

## Consequences

**Positive.** One filename, three agreeing consumers. The deliverable is produced on every
run — verified byte-identical to the final step's artifact (`cow`: `output.html` 1011 B ==
`17ha47o-xb0x08-cow.md` 1011 B).

**Negative — authored filenames are silently ignored.** A prompt saying "save to
paragraph.md" produces no `paragraph.md`, no warning and no error. Authors reasonably
believe the instruction took effect, and the resulting file layout differs run to run
because the model resolves the contradiction differently each time.

**Handoff runs through the roster, not through names.** This is what makes ADR-0004's
`depends_on` derivation load-bearing rather than cosmetic: the roster is the only line in a
step's prompt naming a file that actually exists.

## Alternatives considered

**Honour the prompt's filename when it names one.** Rejected: it desynchronises the three
consumers above, and the failure is silent.

**Drop the delivery block.** Trialled and reverted — see Rationale.

**Constrain writes to the artifact name.** A real feature (the step may write only its own
artifact), not a fix. Not built; see ADR-0012 for why the adjacent `write_files` grant was
made fixed rather than enforced.

## Confirmation

The delivery block is asserted by `test_custom_agent_prompt.py` (composition order:
preamble → step prompt → roster → artifact instruction). The roster's
artifacts-that-exist rule is asserted by `test_artifact_fallback_and_roster.py`.

If this decision is revisited, the empty-artifact hazard must be closed first:
`_check_artifact_fallback` writes the streamed output even when it is empty, and
`_build_roster` advertises a file's existence without checking its content.
