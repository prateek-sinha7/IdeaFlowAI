## Summary

Derived while analyzing [ISS-298](20260828-1729-ISS-298.md) (`?error=quota` on
`/preview-fullscreen` shows a dead end even when a valid cached preview exists). ISS-298's own
root cause and its "Expected" resolution both center on `sessionStorage["__app_preview__"]`; this
card documents an independent property of that same key that any fix to ISS-298 inherits.

`AppBuilderPreview.handleFullscreen` (`frontend/src/components/preview/AppBuilderPreview.tsx:406-421`)
writes `JSON.stringify({ files, projectName })` to the single fixed string key `"__app_preview__"`
(line 410-412) — no run id, generation id, or timestamp is included. `handleFullscreen` is the ONE
function every `<AppBuilderPreview>` instance shares (it is defined once, inside the component, and
wired to the "Full Screen" button at line 477). Grepping every render site confirms three, all
funneling through the same key:

- `frontend/src/components/preview/PreviewPanel.tsx:163` — the live/current run's preview.
- `frontend/src/components/history/WorkflowHistory.tsx:833` — a reopened historical run's native
  IDE files.
- `frontend/src/components/history/WorkflowHistory.tsx:872` — a reopened historical run's generic
  bundle fallback.

CONFIRMED mechanism: `frontend/src/app/preview-fullscreen/page.tsx`'s plain-route branch (the
`setTimeout` at lines 52-76, read in full while analyzing ISS-298) re-reads and re-parses
`sessionStorage["__app_preview__"]` on every mount of the page, with no check that the payload
belongs to the run whose Full Screen click opened that particular tab. Concretely: open Full
Screen for Run A (tab A renders A's files) → return to the opener tab → open or reopen a
different Run B (via `PreviewPanel` or `WorkflowHistory`) and click Full Screen again, which
overwrites the shared key with B's payload → refresh tab A. Tab A's `useEffect` reruns, reads the
now-overwritten key, and would render Run B's files under a tab the user still believes is Run
A's — the URL stays plain `/preview-fullscreen` (no run id in the path) with nothing to indicate
the content switched.

The same lack of identity bears directly on whatever fixes ISS-298: if that fix mirrors the plain
route's read (render whatever is currently cached under `__app_preview__` when `error=quota` is
present), it can show a stale, unrelated run's files as if they belonged to the attempt that just
failed with quota-exceeded — the mirror-image failure of ISS-298 itself (there, valid same-run
data is wrongly discarded; here, a *different* run's stale data could be wrongly presented as
current).

## Why the root cause implies this

Confirming ISS-298's root cause required reading `preview-fullscreen/page.tsx`'s full `useEffect`
(lines 36-76) and `AppBuilderPreview.tsx`'s `handleFullscreen` (lines 406-421) in full. Both reads
surface the same fact: the cache key those two branches share carries no identity. This is the
"concurrent / adjacent state" derivation from ISS-298's mechanism, not a separate guess — the
exact key and exact read path ISS-298 turns on is what this card traces further.

## Confidence

INFERRED. CONFIRMED by direct file:line read: the write has no identity
(`AppBuilderPreview.tsx:410-412`), the key is shared across 3 render sites (grep, listed above),
and the plain route re-reads unconditionally on every mount with no staleness check
(`page.tsx:56-69`). NOT independently reproduced end-to-end in a browser this pass — no run of
"open A, switch to B, refresh A's tab" was executed. That reproduction is what would confirm this
as an observed defect rather than a design-level risk implied by the code.

## Reproduction (to run)

1. Sign in `qa-admin`, open an App Builder run A's preview, click Full Screen. Confirm tab A
   renders run A's files/`projectName`.
2. In the opener tab, switch to (or reopen via Workflow History) a different App Builder run B,
   click Full Screen. Confirm via `browser_evaluate` that `sessionStorage.__app_preview__` now
   holds B's payload.
3. Switch back to tab A and refresh (F5/reload). Expected: tab A still reflects run A, or at
   minimum signals it cannot verify freshness. Predicted actual: tab A's `useEffect` reruns,
   reads the overwritten key, and renders run B's files/`projectName` while the URL stays plain
   `/preview-fullscreen`.

## Where this bears on ISS-298's fix

The fixer should not treat "`__app_preview__` is present and parseable" as sufficient to render it
in the quota branch without also weighing whether it is stale relative to the attempt that
triggered `?error=quota`. This card does not mandate a specific solution (e.g. tagging the payload
with a run/generation id) — it flags the gap so ISS-298's fix does not trade a false-negative dead
end for a false-positive "wrong project silently shown as current."
