## What was wrong

`BUG-20260828-041815-login-expired-1` was REOPENED by the 6-verifier. The functional fix
([FIX-393](20260829-0325-FIX-393.md) — `role="alert"` on all three status banners in
`frontend/src/app/login/page.tsx`) was independently confirmed good and is untouched here.
What failed was a health check on the bug's other deliverable: `npx tsc --noEmit` reported

```
src/app/login/login.a11y.test.tsx(92,33): error TS2554: Expected 2 arguments, but got 1.
```

so the frontend did not build clean.

## Root cause

`frontend/src/app/login/login.a11y.test.tsx:92` constructed the rejection value as
`new ApiError(401)`. The name is imported from the real module
(`import { ApiError } from "@/lib/api"`, line 74), and the real class requires two arguments:

```ts
class ApiError extends Error {
  constructor(status: number, detail: unknown) {
```
— `frontend/src/lib/api.ts:93-96`, exported at `frontend/src/lib/api.ts:653`.

The discrepancy is that this file's own `vi.mock("@/lib/api")` factory redeclares the class
with `constructor(status: number, detail?: unknown)` — detail OPTIONAL
(`frontend/src/app/login/login.a11y.test.tsx:31-38`). That stub is what runs, but it is not
what TypeScript sees: `vi.mock` is a runtime substitution, so `tsc` resolves the import to
the real module's 2-argument signature. The call was therefore correct at runtime (vitest
does not type-check) and wrong at compile time — green tests over a red build.

## What changed and why there

One line, at the call site:

`frontend/src/app/login/login.a11y.test.tsx:92` — `new ApiError(401)` -> `new ApiError(401, null)`.

Fixed at the call site rather than by relaxing `detail` to optional in the real `ApiError`
(`frontend/src/lib/api.ts:96`): the production class genuinely needs the detail — its
constructor body derives the `Error` message from it via `errorMessageFromDetail(detail) ??
JSON.stringify(detail)` — and every one of the five real construction sites
(`lib/api.ts:297,359`, `lib/api-handoff.ts:83,105`, `store/api/http.ts:49`) already passes
two arguments. Widening the app's signature to accommodate a test would have been the app
bent to the test.

`null` was chosen over the asserted banner text deliberately. `describeApiError`
(`frontend/src/app/login/page.tsx:71-79`) returns "Invalid email or password." from its
`err.status === 401` branch and falls through to `typeof err.detail === "string" ? err.detail
: ...` otherwise; passing the asserted string as the detail would let the test still pass if
the 401 branch broke. With `null`, the assertion keeps proving the branch it was written to
prove. No assertion, expectation or test name was changed.
