# ISS-614

**BUG-ID:** BUG-20260829-140111-runs-id-steps-agent (deferred finding from FIX-412)

## What is still true after FIX-412

[ISS-612](20260829-1631-ISS-612.md) recorded that `DeepLinkTarget.anchor`
(`frontend/src/types/index.ts:75-90`) is parsed in full by
`useRunChat.parseDeepLink` (`useRunChat.ts:280-299`) and read nowhere in
`frontend/src`. [FIX-412](20260829-1703-FIX-412.md) fixed the user-visible
defect — the chat deep-link can now target a different family member — but did
NOT do it through `anchor`, so that statement is still literally true:
`grep -rn "\.anchor\b" frontend/src/` (excluding tests) still returns zero
application-code matches.

## Why anchor was not the right source

`_classify` (`backend/app/agents/chat_narrator.py:198-201`) targets a
DELIVERABLE card at its FILE, not its run:

```
target = f"deliverable:{filename}" if filename else f"deliverable:{anchor}"
```

Confirmed live against the ISS-607 fixture pair via `GET /api/runs/{id}/events`:
the revision run `2ac66bbd-8d76-4d59-9580-a29b1a4f6e74` emits
`"deep_link": {"target": "deliverable:user_stories.md", ...}` — no run id at all.
`ISS-612`'s own test exercises exactly that card kind, so an `anchor`-based fix
would have failed its own verification. Every `chat_reply` payload does carry
`pipeline_run_id` (`project_milestone_card`, `chat_narrator.py:249`), which is
present for every card kind, so FIX-412 uses that.

## Disposition

Cosmetic/structural, not user-visible. Either:
1. delete `anchor` from `DeepLinkTarget` and `parseDeepLink` as dead weight, or
2. give it its first real reader — a `deliverable:<filename>` anchor could select
   WHICH file the Files/Preview tab opens, which is the thing it actually names.

Neither is urgent, and the choice is a design call, not a bug fix.
