## The gap

One uploaded document is now three different things, and two of them disagree
about what the document says.

| representation | written by | fidelity |
|---|---|---|
| `.uploads/<name>` | ingest (`run_files.py`) | the real bytes |
| `.uploads/<name>.txt` | ingest, via `extract_upload_text` | flat text — pypdf / python-docx / python-pptx, **no page images, no annotations**, and nothing at all for `.xlsx` |
| `.extract/{format}/{slug}/document.md` + `pages/NN/image-N.png` | the `extract_text` tool | text in reading order plus render crops carrying the callout overlays |

The sidecar path is the original one and it still runs on every upload:
`run_files.py` calls `extract_upload_text(name, data)` for any extension in
`_EXTRACTABLE_EXTS` (`pdf`, `docx`, `pptx`), writes `{raw_rel}.txt`, and mirrors
it as a durable contribution. Nothing marks it superseded.

## It is still being pasted into agent messages

`uploaded_files._compose` is unchanged: for every manifest entry with
`has_text`, it reads the sidecar and emits

```
## Uploaded Files

### <name>
<flat text>
```

as an `uploaded_files_context` block, into the message of **every agent
declaring `injects: [uploaded_files]`**. Spec 019 §6 deliberately kept that
provider out of scope ("FR-024 governs the interaction by declaration, not by
modifying a shipped capability"), and commit `16b45d106` notes in its body that
this changes the brief content of workflows using that inject.

So an agent can be handed the lossy representation in its context **and** be
expected to go read the faithful one from disk.

## The only defence is prose

In `pdf_to_prototype`, all five reader steps carry the same paragraph:

> `.uploads/` is a folder of RAW FILES only. … A `.txt` sidecar next to a raw
> file there, and any document text already inlined into your context message,
> is NOT the document: it is a stale artifact of a different path, and you must
> never read it, quote it or write notes from it.

followed by an `IF EXTRACTION FAILS` paragraph telling the agent to write an
honest failure rather than fall back to either.

That is the whole enforcement mechanism in production. It is invisible to tests,
it does not transfer to any other workflow that declares
`injects: [uploaded_files]`, and it is one prompt edit away from gone.

## The sharpest part: an accepted ADR now contradicts the code

[ADR-0042](20260907-ADR-0042.md) is `accepted`, and its first locked constraint
reads:

> **NO agent receives pasted world state.** Uploaded documents, the design
> system, template text, upstream agent output and the planner's analysis all
> live in files the agent reads for itself.

Its input table names the decided shape for uploaded files as
`.uploads/<file>` + `.txt` sidecar — "the agent reads it".

That ADR predates `.extract/` entirely. Today the sidecar is *both* the shape it
names *and* the thing being pasted, and a third, better representation exists
that the ADR has never heard of. Nothing reconciles the two.

## What resolving this looks like

Whichever way it goes, it should be one decision, not two drifting ones: either
the sidecar stops being written and inlined for formats `.extract/` covers, or
ADR-0042 is amended to say which representation is authoritative and why the
other still exists. Until then, treat any workflow that does not carry
`pdf_to_prototype`'s paragraph as unprotected.
