## What happened

On a completed run's detail page, the left-lane header meta row (below the run title,
`data-testid="lane-run-meta"` area) shows a relative age for the run followed by duration and
token count, e.g. "just now · 18m 54s · 3.1M tokens". For run
`b9feac1c-ec21-4531-8ba7-bb391786993e` (`created_at: 2026-08-27T13:48:45Z`,
`completed_at: 2026-08-27T14:07:40Z` per `GET /api/runs/{id}`), the header reads "just now" no
matter how much real time has passed since completion. In the SAME header row, the "Version v1,
choose version" control computes and displays the correct age for the identical run/version — at
validation time this had advanced from "11h ago" (per the hunter's original report) to "1d ago"
(re-observed during this validation), tracking real elapsed time exactly as expected. The header's
duration ("18m 54s") and token count ("3.1M tokens") are each individually correct against the
API; only the relative-time segment is defective.

## Reproduction (validated 3/3, cold start every cycle)

Each cycle was a fresh, independent cold entry — never a soft re-click of an already-loaded page:

1. **Cycle 1** — direct cold navigation `http://localhost:3000/dashboard` → cold navigation to
   `http://localhost:3000/runs/b9feac1c-ec21-4531-8ba7-bb391786993e`. Header read "just now".
2. **Cycle 2** — cold navigation back through `/dashboard` again, then a fresh cold navigation to
   the same run URL. Header again read "just now"; opened the version picker in the same pass and
   confirmed it read "1d ago" for the identical run/version — the two labels on the same header
   row disagreed by over a day.
3. **Cycle 3** — cold navigation via a different entry path (`/dashboard` → `/runs` list route →
   cold navigation to the run detail URL, not a click-through). Header again read "just now".

All three cycles produced the identical result: **3/3 CONFIRMED**, no axis variation needed — the
defect is deterministic on every cold load of a completed run's detail page, not timing- or
entry-path-sensitive.

## Expected vs actual

- **Expected:** The header's relative timestamp reflects the same real elapsed time the version
  picker computes correctly for the identical run (e.g. "1d ago"), not a fixed/frozen value.
- **Actual:** The header is permanently stuck on "just now" regardless of the run's real age,
  while the version picker in the same row computes the correct age for the same run.

## Root cause (read, not fixed, during this validation pass)

`frontend/src/components/chat/LaneRunHeader.tsx`:

- `:42-58` — `formatRelativeAge(iso)` is a correct, standard relative-age formatter (`"just now"`
  below 45s, `Nm ago`, `Nh ago`, `Nd ago`, etc.) — the bug is not in this function's arithmetic.
- `:257` — the settled-state header meta row calls
  `formatRelativeAge(pipelineState?.createdAt)`, i.e. it derives the header's relative age from
  `pipelineState.createdAt`, not from the run's actual API `created_at`/`completed_at`.
- `frontend/src/hooks/useRunChat.ts:354,393,440,615,745` — every place in this codebase that
  stamps a `createdAt` field does so with `new Date().toISOString()` at the moment the object is
  constructed client-side (chat message send/receive time), not from a server-supplied timestamp.
  The consistent "just now" on every cold load — first paint, not a race that resolves — is
  explained by `pipelineState.createdAt` being populated the same way when a completed run's
  state is (re)constructed on page load: it gets stamped with the CLIENT'S current load/hydration
  time rather than carrying the run's real `completed_at`/`created_at` from the API response.
  This was not traced further into `useWorkflow.ts`'s state-hydration path (out of scope for
  validation) — the next stage should confirm exactly where `pipelineState.createdAt` is set when
  a completed run is loaded from `GET /api/runs/{id}` rather than from a live SSE stream, and feed
  it the run's real timestamp instead.
- By contrast, the version picker (elsewhere in the same component tree) derives its own
  "Version vN · Nh/Nd ago" label from the run/version's own persisted timestamp directly, which is
  why it is correct while the header is not — two different code paths computing the same
  semantic value from two different sources.
