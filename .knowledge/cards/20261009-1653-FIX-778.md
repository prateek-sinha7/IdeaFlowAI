## What was wrong

The root cause is on [ISS-1155](20261009-1420-ISS-1155.md) and is not re-derived here. `get_run_events` declared only `after`
and fed `ScopedStore.read_events` (an unbounded `.all()`) into one response. The endpoint's store carries the request session,
so `_run_bounded` runs the read in-line (`backend/agents/authz.py:161-162`) and FastAPI encodes the reply in-line too. One bare
call on run `78e185fb-c032-4154-8552-774781b6e5df` (107,409 events) built 52,909,786 bytes before sending byte one (TTFB 4.38 s,
total 4.40 s) and held a concurrent `/health` for 4,227 ms.

## What changed, and why there

The three places the card names. Every SPA consumer reaches the endpoint through `getRunEvents`, so the seven `page.tsx` sites
and `useRunChat` need no change.

1. `backend/agents/authz.py:416-438`: new `ScopedStore.read_events_page(run_id, after_seq, *, limit)`. It is `read_events` with
   `ORDER BY seq ASC LIMIT :limit`, the same `seq > after_seq` filter and `_scope_owner_ws` scope, through `_run_bounded`.
   `read_events` is untouched: [FIX-688](20261001-2140-FIX-688.md) locked it, and SSE resume and engine resume need it whole.
   `limit` is clamped at 0, because a negative LIMIT on SQLite means no limit.
2. `backend/app/api/runs.py:1522-1595` (`get_run_events`): `after: int = Query(0, ge=0)` and
   `limit: int = Query(1000, ge=1, le=5000)`, the idiom at `runs.py:745`. It reads `limit + 1` rows, so `has_more` costs no COUNT,
   and adds `has_more` and `next_after` (the last returned `seq`, or `after` when the page is empty). The ISS-358 `created_at`
   projection and every other key are unchanged.
3. `frontend/src/lib/api.ts:1451-1506`: `RunEventsResponse` gains optional `has_more` and `next_after`. `getRunEvents` requests
   `after=<next_after>&limit=5000` while `has_more` holds, collects the pages and maps `pages.flat()` exactly as before. A missing
   `has_more` ends the loop, which covers an old backend, the mock catch-all `{}` and the e2e fixtures
   (`frontend/e2e/fixtures/mockSse.ts`, `dashboard.ts`), none of which send it. The loop continues only when `next_after` is a number greater than the cursor, so a missing or
   stuck `next_after`, or a NaN cursor, also ends it.

## Behaviour changes a caller can see

- A bare GET returns at most 1,000 rows, where it returned all of them. A caller that wants the whole log follows `next_after`
  while `has_more` holds; the SPA does, inside `getRunEvents`. The manual scripts (`tools/api/endpoints/runs.http:295`,
  `tools/api/runs/run.*.http`, the Postman collections) now print the first page only.
- A negative `after`, and a `limit` outside 1..5000, answer 422. Before, a negative `after` answered 200 and `limit` was ignored.
- `getRunEvents` makes ceil(N / 5000) sequential requests for an N-row log (22 for the 107,409-event run), each under its own
  30 s client timeout, instead of one request under one timeout.
- The QA-KB-067 e2e (`test_qa_kb_067_history_click_reopens_once.py`) counts requests carrying `after=0`. Paging keeps that at one
  per reopen, because only the first page asks for `after=0`.
- Not changed, mentioned only: `frontend/src/store/api/runs.ts:121` (`runsApi.events`) and its own `RunEventsResponse` type have no
  non-test caller (ISS-1155 blast radius, row 8). They are dead code and still are.

## What this leaves open

- [ISS-1166](20261009-1620-ISS-1166.md), open. The SSE fresh attach still reads the whole tail in one `read_events`
  (`backend/app/api/run_stream.py:413`). `read_events_page` now exists for it, so its fix is the page loop the card describes.
  The four store fakes in `backend/tests/integration/api/test_sse_stream_api.py` and the stores fed to `_iter_sse_frames` in
  `test_attach_replay_matrix_api.py` would need the new method. Not done here: the card is INFERRED, has no red test, and it
  changes the live-run path.
- [ISS-1167](20261009-1620-ISS-1167.md), open. The browser still receives the whole log and replays it in one synchronous loop.
  The chat-only consumers and the replay loops are in `frontend/src/app/[...view]/page.tsx`, which QA-KB-110's cards
  (ISS-1154, ISS-1171) were changing in this tree at the same time, and whether a finished run needs its delta frames is a product
  question the card leaves open.
- Page size. At `limit=5000` a full walk keeps `/health` under 400 ms but not under 300 ms (5 of 25 probes over). At 1,000 it
  stays under 210 ms and takes 12.67 s instead of 6.68 s. The card specifies the max page; the trade-off is recorded on
  [ISS-1167](20261009-1620-ISS-1167.md), and changing it is one constant in `getRunEvents`.
