# ISS-1198

**INFERRED** sibling of [ISS-1195](20261012-0942-ISS-1195.md) (register entry `QA-KB-117`). The arithmetic is computed offline from source (`evidence/qa-kb-117/analysis-projection.out.txt`, the `modal` lines); the modal copy was not rendered.

## Condition

Any basic, pro or hexaware account opening the plan modal: "Manage plan" on `/settings/usage` (`AccountSettings.tsx:538`) or the header's basic-tier "Upgrade" link (`AppHeader.tsx:660`).

## Expected vs actual

Expected: the count is "the same rule as the Usage & Limits deliverable-access grid", which is what the code comment claims (`frontend/src/components/settings/UpgradePlanModal.tsx:35-36`, and [FIX-363](20260829-0043-FIX-363.md) says the same). Actual: the modal counts every non-revision id in the next tier's `TIER_PIPELINES` that the current tier lacks (`:37-41`), with no label filter, so it counts ids the grid does not show and ids the catalog does not enable.

| upgrade | modal copy (`:86-89`) | grid delta today | ids the modal counts and the grid does not |
|---|---|---|---|
| basic to pro | "unlocks 4 more deliverable types" | 2 | `backlog`, `prototype_v2` |
| pro to enterprise | "unlocks 13 more deliverable types" | 4 | the 8 Engine examples and `sample_subagents_parallel` (`is_beta`, Coming Soon) |
| hexaware to enterprise | "unlocks 16 more" | 6 | the 8 Engine examples, `ppt_v2`, `sample_subagents_parallel` |

## Why the root cause implies it

Same disease, a third projection of the entitlement list: the grid filters it through a hand-kept label map ([ISS-1195](20261012-0942-ISS-1195.md)), the modal does not filter it at all, and the catalog filters it through the live manifest rows. The three counts cannot agree. After ISS-1195 ships the grid will list the Engine examples, so the grid delta for pro to enterprise becomes 12 (examples-only fix: the 4 current tiles plus 8 examples) or 9 (fully catalog-driven: `custom` plus 8 examples), and the modal still says 13, because it also counts `sample_subagents_parallel` (beta) and, in the fully catalog-driven case, `migration` (no manifest), `mulesoft_to_springboot` and `dotnet_to_azure` (both beta). Fixing only the grid leaves this one wrong. Nothing pins the number: no test file mentions "more deliverable" (grep of `frontend/src` and `tests/integration/e2e`), and `test_iss291_manage_plan_button.py` only checks the button.

## Where the fix would belong

`UpgradePlanModal.tsx:37-41` `unlockedCount`, computed from the same shared derivation ISS-1195 proposes (entitled enabled catalog rows at the next tier minus those at the current tier). The modal is rendered from `AppHeader`, where the Redux store is available, so reading `state.global.workflows` there is straightforward.

## What would settle it

Open the modal as `basic@velocity.ai` and read the count, then read the grid delta between a basic and a pro account's Deliverable access; or a component test of `UpgradePlanModal` with `tier="pro"` that asserts the count equals the number of new tiles the grid would show.

## Fix (FIX-785, 5-fixer, 2026-10-12)

Resolved by the shared derivation in [FIX-785](20261012-1013-FIX-785.md) (`splitCatalog` / `catalogAccess` in `frontend/src/lib/entitlements.ts`). `UpgradePlanModal.tsx` `unlockedCount` counts the rows `catalogAccess(next)` lists that `current` cannot run. That is the grid's own derivation, applied in the one shared modal (FIX-363), so neither entry point changed. It falls back to the old count only while the catalog is empty. Case `ISS-1198` now reports "Expect test to fail" (XPASS). Raw output: `evidence/qa-kb-117/fix-01-vitest-runs.txt`.
