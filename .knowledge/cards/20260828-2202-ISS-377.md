## What is still broken

[FIX-336](20260828-2201-FIX-336.md) stopped "Save as my version" from
discarding the user's input — the `POST /api/user-workflows` body now carries
the brief, the template id and the design-system id in `description`. What it
did NOT do is make any of that come back: `description` is free text, nothing
parses it, so reopening `/create/ppt` (or `/create/prototype`,
`/create/ppt_v2`, or any simple panel) still shows an empty brief and no
template pre-selected even when an override exists.

The "Save workflow" button on the same screens does not have this problem —
it writes `selections._wizard` (`LaunchWizard.tsx:704`,
`IdeaInputPage.tsx:1410`), which `DashboardLayout.tsx:1583` and
`app/[...view]/page.tsx:3672` read back to prefill exactly these fields.

## Why it is a schema decision, not a fix

Both halves verified during the FIX-336 pass:

1. `backend/app/api/user_workflows.py:66` — `_reject_both` makes `manifest`
   and `selections` mutually exclusive on POST and PATCH; they write the one
   `workflows.manifest_json` column. An override save must send `manifest`
   (the override resolve reads `manifest_json["steps"]`), so the `_wizard` bag
   cannot be sent with it.
2. `backend/agents/workflows/manifest.py:266` — `build_manifest_from_dict`
   strict-key-rejects any top-level key outside `_ALLOWED_TOP_KEYS`
   (D-08 / INV-5), and `_validated_manifest` runs that parser at save time, so
   a `_wizard`/`brief`/`template` key inside the manifest 422s the save.

`frontend/src/types/index.ts:563-648` agrees: `WorkflowManifest` has `steps`,
`capabilities`, `deliverable`, `planner`, `clarify` and nothing else.

## The options, none of them a fixer's call

- Add a presentation-only top-level manifest key (the way `user_launchable` /
  `is_beta` / `icon` were added under Plan 20-01) and let it carry the wizard
  config. Touches `_ALLOWED_TOP_KEYS`, the frontend `WorkflowManifest` type and
  every reader.
- Let one row hold BOTH shapes — a real column split, so `_reject_both` stops
  being true. A migration, and additive-only makes it a new column.
- Decide a per-run brief does not belong on a reusable per-pipeline-type
  override at all (the position [ISS-280](20260828-1902-ISS-280.md) floats),
  persist only `templateId`/`designSystemId`, and leave the brief per-run.

[ISS-226](20260828-1550-ISS-226.md)'s stated expectation ("persists the entered
brief and the selected template … into the saved override record") is only
half-met until one of these is chosen.
