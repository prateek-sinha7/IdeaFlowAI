## What is left

[FIX-637](20260922-2358-FIX-637.md) resolved
[ISS-831](20260922-2003-ISS-831.md) by merging *concurrent* `getWorkflow`
calls into one request (`singleFlightGet`, `frontend/src/lib/api.ts:481-495`).
ISS-831's "Expected" section asks for more than that: the run record should
be fetched "once per run open ... not on every subsequent tab click". That
part is not met for the Steps tab.

`frontend/src/components/results/AgentThinkingTab.tsx:235`, inside the
divert-link effect keyed on `[runId, liveDivertedToRunId]`:

```tsx
const self = await getWorkflow(token, runId);
if (cancelled) return;
if (self.status === "diverted") {
  ...
} else if (self.parentRunId) {
  const parent = await getWorkflow(token, self.parentRunId);
```

PreviewPanel remounts the Steps tab on every tab switch
(`PreviewPanel.tsx:1878-1925`, `activeTab === "thinking"` inside
`AnimatePresence`). So every Steps open sends one `GET /api/runs/{id}` for
the full record: 829 KB on the QA-PS-048 reporter's run. The effect reads
only `status` and `parentRunId` from it. Before FIX-637 this was two
requests per open, because of Strict Mode. Now it is one. It cannot become
zero while each open issues a fresh read.

## Why FIX-637 did not take it

A TTL cache on `getWorkflow` would stop the repeat, but it is unsafe. The
run record changes while a run is live: its `status` flips at completion,
and the toast-click / reopen paths in `DashboardLayout.tsx` and `page.tsx`
read it again to see that. A cache would serve them the pre-completion row.
The fix has to be cheaper than that. Two candidates:

- read `status` / `parentRunId` from state the page already holds (the
  reopened run is loaded by `handleSelectWorkflowRun`, `page.tsx:2999`), or
- cache only runs in a terminal status.

Choosing between them is an analysis question, not done here.

## Condition

Any run whose Steps tab is opened more than once in a session, with no live
divert marker. Unconditional otherwise: `self` is fetched for every run, not
only for revisions. ISS-831 lists AgentThinkingTab's three calls as
conditional on a parent or divert, but that holds only for the `child` and
`parent` fetches.

## What would settle it

Open a completed run and reset DevTools Network. Click Steps → Preview →
Steps. Expect two `GET /api/runs/{id}` today (one per Steps open). The fix
target is zero after the first open.

## Re-analysis (2026-09-23): settled

Answers the 4 items the Fixer note above asked for.

### 1. Reconciled the count

The verifier's two `GET /api/runs/{id}` ~1s apart, on "a single click
straight to Steps", are NOT two StrictMode-doubled fires of the SAME call.
They are two DIFFERENT, unrelated call sites, both reading the same run:

- `frontend/src/app/[...view]/page.tsx:2999` (`handleSelectWorkflowRun`) —
  the run-OPEN fetch. Fires once per navigation to the run, regardless of
  which tab ends up active, because `PreviewPanel`'s default/initial tab
  selection and this fetch are independent of each other.
- `frontend/src/components/results/AgentThinkingTab.tsx:235` — this card's
  own subject. `PreviewPanel` mounts `AgentThinkingTab` only inside
  `{activeTab === "thinking" && (...)}` under `<AnimatePresence mode="wait">`
  (`PreviewPanel.tsx:1879-1925`), so its effect only starts once the user's
  click lands on Steps — necessarily after (or, if Steps is the landing tab,
  racing) the page-open fetch above.

Both go through `getWorkflow()` → `singleFlightGet()` (`api.ts:1051-1057`,
`:481-495`), which DOES merge two calls in flight AT THE SAME TIME — but
`.finally()` clears the map entry the MOMENT a request settles
(`api.ts:490-492`), so it merges nothing once the first call has already
returned. The page-open fetch has no reason to still be in flight by the
time a user clicks a tab a moment later; these two calls are sequential, not
concurrent, so `singleFlightGet` was never going to catch this pair
regardless of StrictMode.

This also means the original fixer-note hypothesis ("Both invocations
therefore reach `getWorkflow` within the same few ms, and the in-flight
guard should merge them") was answering a narrower, correct-but-insufficient
question: it shows `AgentThinkingTab`'s OWN StrictMode double collapses to
one network call (true, and still true), but that one call is still a
SECOND, independent fetch on top of the page-open fetch — exactly what this
card's original "It cannot become zero while each open issues a fresh read"
already said, just without identifying the other half of the pair.

CONFIRMED mechanism (every file:line above read this pass). The specific
claim "the verifier's two x-request-ids are these two exact call sites, not
some other pair" is INFERRED — a DevTools Initiator-column read on a fresh
repro would fully settle it; not available in this analysis pass (no
browser access from this role). [ISS-856](20260923-0028-ISS-856.md), found
during this same reconciliation, is a third, CONFIRMED (by code chain) way
two run-record GETs can stack for one user action — relevant to the
original report's "3x" figure, unrelated to this card's Steps-tab scope.

### 2. Catalog read

Filed separately as [ISS-854](20260923-0028-ISS-854.md):
`getWorkflowDefinitions` (`api.ts:1929-1936`) is a bare `request()` with NO
dedupe of any kind — worse than the run-record gap this card covers, which
at least gets `singleFlightGet` for concurrent calls.

### 3. Chosen fix

**Option (a) — read from state already held.** `DashboardLayout.tsx:714-720`
already fetches `runFamily` once per `contentSourceRunId` (via
`getRunFamily`, itself `singleFlightGet`-guarded) and passes it to
`PreviewPanel` as a prop; `PreviewPanel.tsx:810-828` already derives
`sortedMembers` / `activeParentRunId` from it for OTHER consumers
(`revisionParentVersion` / `originalBriefRootRunId`, both already threaded
into `AgentThinkingTab` at `PreviewPanel.tsx:1902-1903`). `AgentThinkingTab`
itself currently receives NO `runFamily`-derived prop at all (confirmed:
its full prop list at `PreviewPanel.tsx:1888-1920` has none) — that is the
gap to close, not a new fetch to invent.

Concretely: thread the active member's `status` and the matching
parent/child members' `id` / `type` / `title` / `status` from `runFamily`
into `AgentThinkingTab` as new prop(s), and have the effect's `self` /
`parent` lookups (`:235`, `:243`) read those instead of calling
`getWorkflow`. Fall back to today's fetch ONLY while `runFamily` is still
`null` (the `DashboardLayout` fetch is itself async and can still be in
flight on a fast first paint) — a silent "never fetch" would leave the
divert-link row absent until some later remount.

Option (b) — a TTL cache on `getWorkflow` — is confirmed still unsafe for
the reasons FIX-637 already gave (live status changes mid-run) and buys
nothing extra now that (a)'s data path is confirmed to already exist end to
end. Rejected, not re-argued further here.

[ISS-855](20260923-0028-ISS-855.md) (filed separately) is the same fix
applied to this effect's third branch (the diverted-FROM reverse scan).

## Resolution (2026-09-23)

Fixed by [FIX-638](20260923-0059-FIX-638.md) with option (a): `runFamily` is
now passed into `AgentThinkingTab`. It differs from "Re-analysis § 3" in one
place. When no family is held, the fallback fetches the family
(`getRunFamily`, single-flighted), not the old `getWorkflow(self)` chain.
That chain is exactly what this card's red test and ISS-855's forbid. Both
tests mount with no family, so the literal fallback left them red. The
`WorkflowHistory.tsx:1111` mount needed no change. It passes no
`pipelineState`, so `runId` is undefined and the effect never runs there.
