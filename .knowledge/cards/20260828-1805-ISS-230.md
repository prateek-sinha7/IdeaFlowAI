## Reproduction (3/3, cold start each time — cycles 1, 2 and 3 all failed)

Route under test: `http://localhost:3000/runs/77f74563-fa19-4f0b-84fd-d0224f89a54a/versions/2`
(root run `77f74563-...` = v1; revision `ef86e750-bbcd-404f-855a-fb0d5bee63f5` = v2 — a genuine
2-member revision family). Account: qa-admin (tier not implicated — nothing tier-specific in the
bug). Theme/viewport: default light, default viewport — not implicated by the mechanism (see
Root cause).

- **Cycle 1** — cold nav to `/runs/{rootId}/versions/2`, click the **Files** tab
  (`[data-testid="tab-files"]`). URL collapsed to `/runs/{rootId}/files`. Network fired
  `GET /api/runs/{rootId}` and `GET /api/runs/{rootId}/sandbox` — the ROOT run, never
  `ef86e750-...`. Files tab showed "Final output … 241.6 KB" (v1's size, not v2's ~83.5 KB).
  Version picker read "Version v1".
- **Cycle 2** — cold nav to `/runs/{rootId}/versions/2`, click the **Steps** tab
  (`[data-testid="tab-thinking"]`). URL collapsed to `/runs/{rootId}/steps`. Same shape.
- **Cycle 3** — cold nav to `/runs/{rootId}/versions/2`, click the **Workspace** tab
  (`[data-testid="tab-workspace"]`). URL collapsed to `/runs/{rootId}/workspace`. Same shape —
  confirms the defect is NOT scoped to Files/Steps as the original report suspected; it hits
  every non-Preview tab, generalizing beyond the two tabs BUG-20260828-090732-runs-id-versions
  named.

Every cycle reproduced identically — cold load each time, no timing/order dependency found or
needed to trigger it.

## Root cause

`frontend/src/components/layout/DashboardLayout.tsx:471-498`,
`handlePreviewPanelTabSelect`:

```ts
const routeMap: Record<string, string> = {
  "preview": routes.runDetail(contentSourceRunId),
  "thinking": routes.runSteps(contentSourceRunId),
  "files": routes.runFiles(contentSourceRunId),
  "workspace": routes.runWorkspace(contentSourceRunId),
  "audit": routes.runAudit(contentSourceRunId),
};
```

Every tab's target route is built purely from `routes.run*(contentSourceRunId)`
(`frontend/src/lib/routes.ts:65-76`) — none of the five route builders ever consult or preserve
a `/versions/<v>` segment, and `routes.runVersion(id, v)` (routes.ts:80) is never referenced
here at all. `contentSourceRunId` is the parent/root run id, not the pinned revision id, so the
moment any non-Preview tab is clicked, `window.history.pushState(null, "", targetRoute)`
(the deliberate shallow-nav path documented in the surrounding comment, chosen specifically to
avoid remounting `page.tsx`) writes an un-versioned URL. That pushState also drives the
subsequent fetch — the run-detail fetch effect keys off the URL/route it reads back, so it
re-fetches the root run (v1) instead of the pinned revision (`ef86e750-...`, v2). This is why
every downstream signal reverts together: URL, network target, and rendered data are all
downstream of the same un-versioned `targetRoute`, not three independent bugs.

## Expected vs actual

- **Expected:** switching tabs while pinned to `/versions/2` keeps the pin — the URL stays
  scoped under `/versions/2/<tab>` (or equivalent), the fetch targets `ef86e750-...`, and every
  tab (Files, Steps, Workspace, Audit) renders v2's real data.
- **Actual:** any non-Preview tab click silently drops the version segment, re-fetches the root
  run, and renders v1's data with no warning that the pin was lost.
