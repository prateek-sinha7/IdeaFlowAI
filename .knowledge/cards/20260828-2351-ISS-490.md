# ISS-490

## Title

INFERRED sibling of [ISS-327](20260828-2033-ISS-327.md): the obvious fix for the saved-workflow
detail view's raw-slug bug — resolve each `agent_ids` entry against the `useAgentLibrary()`
catalog — does not cover custom-agent instances, because their real display name was never part
of that catalog to begin with.

## Condition

A saved **custom** workflow that contains one or more instances of the reusable blank
`custom-agent` template (added via "+ Sub-agent"/"+ Add" in the Composer and given its own name,
e.g. two differently-named custom steps in the same workflow).

## Expected vs Actual (once ISS-327's catalog-lookup fix lands)

- **Expected:** `/workflows/{id}` shows each custom-agent instance's own user-given name (the same
  name the Composer canvas shows for that node), exactly as it already does for ordinary
  library/custom-catalog agents like `documentation-agent`.
- **Actual (predicted):** the instance still renders wrong. `agent_ids` stores these as
  `custom-agent:<instance_id>` (confirmed shape, see Evidence). A straightforward
  `useAgentLibrary().allAgents.find(a => a.id === id)` lookup — the exact mechanism ISS-327's fix
  is expected to add — MISSES for that id, because the catalog only carries the bare template
  entry `custom-agent`, never an instance-qualified one. Depending on how the miss is handled the
  row shows either the still-raw slug (`custom-agent:a1b2c3`) — ISS-327's original symptom,
  reappearing for a narrower input shape — or, if a fallback strips the suffix and matches the
  bare template instead, the generic placeholder `"New agent"` / `"Custom agent"` for every
  instance, silently discarding the name the user actually gave it.

## Why the root cause implies this

ISS-327's root cause is "no id-to-name lookup at all." The lookup that fixes it —
`useAgentLibrary()`'s `allAgents`, sourced from `GET /api/agents/library` — is a **static catalog
of template agents**, not a per-saved-workflow store. `frontend/src/store/api/userWorkflows.ts`
proves the app already treats custom-agent instances as a special case that catalog lookup cannot
serve:

- `instantiateIfTemplate` (`frontend/src/store/api/userWorkflows.ts:185-205`) mints a fresh
  `id: newId`/`instance_id: newId` shaped `custom-agent:<instance_id>` for every "+ Sub-agent" add
  of the blank template, and explicitly seeds it with placeholder `name: "New agent"`,
  `role: "Custom agent"` (lines 199-200) — the user's real name is typed in afterward and lives
  only on that instance, never added back to the catalog.
- `agentToManifestStep` (`frontend/src/store/api/userWorkflows.ts:207-213`) confirms what actually
  gets persisted for such a step: `{ agent: "custom-agent", instance_id: agent.instance_id ??
  agent.id, name: agent.name }` — the real name travels in the **manifest step**, not as a
  catalog-resolvable id.
- `manifestStepToAgent` (`frontend/src/store/api/userWorkflows.ts:428-447`) is the app's own
  reverse mapping, and it deliberately SKIPS the catalog for this case: `const base = !isCustom ?
  lookup?.(id) : undefined` (line 434), then falls through to `name: step.name ?? id` (line 439).
  `ComposerPage.tsx` uses exactly this path (`manifestStepsToAgents(initialManifestSteps, ...)`,
  `ComposerPage.tsx:272-276`) when reopening a saved workflow that has per-node
  skills/prompt/subagents — which is precisely how the Composer already shows the correct name for
  such a step while a catalog-only lookup would not.
- `UserWorkflowSummary` (`frontend/src/store/api/userWorkflows.ts:15-31`) confirms the data is
  available to fix this: it carries `manifest?: WorkflowManifest | null` alongside `agent_ids`,
  covering exactly the case where a saved workflow needed the full per-step shape (comment: "once a
  node carries a skill/prompt/subagents tree"). `WorkflowDetailView.tsx` reads neither `manifest`
  nor `selections` today — only `agent_ids` (confirmed, `WorkflowDetailView.tsx:29`) — so a fix
  that adds catalog lookup but still reads only `agent_ids` inherits this gap.

## Confidence

INFERRED. The mechanism is CONFIRMED by reading the four call sites above, but no saved workflow
with a custom-agent instance has been exercised live against a FIXED `WorkflowDetailView` (ISS-327
itself is not fixed yet, so there is nothing to reproduce this against today). What would settle
it: once ISS-327's fix lands, save a custom workflow with 2 instances of the blank template (each
renamed differently in the Composer), then cold-load `/workflows/{id}` and check whether the
detail view shows the two distinct user-given names or a raw slug / the generic "New agent" for
either row.

## Evidence

- `frontend/src/components/savedworkflows/WorkflowDetailView.tsx:29` — reads only
  `workflow.agent_ids`, never `workflow.manifest` or `workflow.selections`.
- `frontend/src/store/api/userWorkflows.ts:185-205` (`instantiateIfTemplate`),
  `:207-213` (`agentToManifestStep`), `:428-447` (`manifestStepToAgent`),
  `:15-31` (`UserWorkflowSummary`).
- `frontend/src/components/workflow/composer/ComposerPage.tsx:207` (`useAgentLibrary()` /
  `ALL_LIBRARY_AGENTS`), `:272-276` (`manifestStepsToAgents` branch for reopening a saved
  workflow).

## Proposed fix (for the 5-fixer, not applied here)

Belongs in `WorkflowDetailView.tsx` alongside ISS-327's fix, not as a separate change: after
resolving each id via `useAgentLibrary()`, for any id the catalog misses AND that starts with the
`custom-agent:` instance prefix, fall back to a name pulled from `workflow.manifest?.steps` (reuse
the existing exported `manifestStepsToAgents`/`manifestStepToAgent` from
`frontend/src/store/api/userWorkflows.ts` rather than re-deriving the walk) instead of the catalog.
Only the raw id remains as a last-resort fallback when neither source has it.
