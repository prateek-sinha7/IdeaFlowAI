# ISS-1148

**Register source:** sibling derived during the `QA-KB-108` analysis on 2026-10-09 (root [ISS-1144](20261009-0725-ISS-1144.md)). Not its own bug row.

**Confidence:** CONFIRMED offline at two levels. Layer: row E of `evidence/qa-kb-108/04-analyze-sibling-probes-output.txt` (with the Cognito wrapper patched to raise `TokenRetrievalError`, `is_last_admin`, `change_tier`, `invite_user` and `disable_user` raise `botocore.exceptions.TokenRetrievalError`; the `ClientError` control raises `ProviderUnavailableError`; `_raise_for(TokenRetrievalError)` re-raises it unchanged). HTTP: `evidence/qa-kb-108/08-analyze-admin-routes-probe-output.txt` (real app, only `require_admin` and `get_db` overridden): tier, role and reset-password give 503 with CORS headers for a `ClientError` and a CORS-less 500 for `TokenRetrievalError`; disable and delete give a CORS-less 500 for BOTH. Not driven: a real admin session. INFERRED: the partial-state cases below.

## Condition

- Any admin lifecycle action (`invite_user`, `change_tier`, `change_role`, `reset_password`, `disable_user`, `enable_user`, `delete_user`, the last-admin check) while the backend's AWS credential chain cannot be resolved. Every one of them calls a signed `Admin*` operation (`evidence/qa-kb-108/06-analyze-botocore-service-model-auth-types.txt`), so unlike some self-service endpoints (which call unsigned operations) they are ALL reachable by an expired SSO session.
- `backend/app/core/cognito_admin.py` has ten `except ClientError` clauses (`:130, :160, :211, :242, :332, :421, :455, :501, :606, :686`) and none that names `BotoCoreError`. The layer's own typed error is documented for this case: `ProviderUnavailableError` is "Cognito could not be reached, or returned a non-retryable server error" (`:112-113`).
- `backend/app/api/admin.py::_raise_for` maps only the four lifecycle error types and ends with `raise exc` for anything else, "UNCHANGED" by design (`:59-79`). The route-level 503 mappings that already exist (for example `admin.py:380-388` for `is_last_admin`) are therefore never reached by a `BotoCoreError`.

## Expected vs actual

Expected: 503 with the lifecycle layer's message ("Could not update tier at the identity provider." and so on) and CORS headers, which the admin UI can display. Actual: raw exception, Starlette 500 outside CORS, generic failure in the console.

## A second gap on the same routes, visible without any BotoCoreError (CONFIRMED)

`PATCH .../tier`, `PATCH .../role`, `POST .../reset-password`, `POST .../enable` and `POST /users` wrap their `cognito_admin` call in `except Exception: _raise_for(exc)` (`api/admin.py:320-323, :400-403, :459-464, :529-532, :635-638`). `POST .../disable` (`:600`) and `DELETE .../{id}` (`:712`) call `cognito_admin.disable_user` / `delete_user` bare. Their `ProviderUnavailableError` therefore escapes untranslated: the `ClientError` control already answers 500 with no CORS header (`08-...-output.txt`, last four rows). Consequence for the fix: converting `BotoCoreError` to `ProviderUnavailableError` inside `cognito_admin.py` turns tier, role, reset-password and enable green, and leaves disable and delete red until they get the same `_raise_for` wrapper. Without that, a test written for "every admin route answers 503" fails on those two rows and looks like an incomplete fix.

## Why the root cause implies it

The same assumption, one layer down: "the provider failed" is modelled as `ClientError` only. It has as many clauses as `auth.py` (ten against ten), all reachable by the reported trigger, and it sits behind a boundary test that dictates WHERE the fix goes: `test_admin_api_imports_no_raw_provider_sdk` (`backend/tests/security/test_cognito_client_boundary.py:152`) fails if `api/admin.py` imports botocore, and its docstring says provider failures are translated in the lifecycle layer so the route layer "only chooses a status code". A fix that adds `except BotoCoreError` to `_raise_for` breaks that test.

## Partial-state cases (INFERRED, narrow)

- `change_tier` and `change_role` commit `tokens_valid_from` BEFORE the Cognito writes by design (`cognito_admin.py:434-435, 483-484`). A `BotoCoreError` mid-sequence leaves the cutoff committed and the group membership possibly half-changed, exactly like a `ClientError` would, but the caller gets a 500 instead of the typed error the docstring promises ("Raises `ProviderUnavailableError` on any Cognito failure", `:407-409`). Needs credentials to lapse between two writes.
- `invite_user`'s compensation (`:364-381`) calls `_tolerate_missing("AdminDeleteUser", ...)`, which is also `ClientError`-only. If the credential failure persists, the compensating delete raises out of the `except` block and the new pool user is left without groups, against the "no acceptable partial state" rule in its docstring (`:316-321`). Needs the failure to hit between `AdminCreateUser` and `AdminAddUserToGroup`.
- `is_last_admin` is documented to degrade to the local projection when the provider cannot be read, "A provider outage therefore cannot silently drop the protection" (`:219-222`); a `BotoCoreError` on the first read (`:209-210`) skips that and raises instead.
- The delete flow loses its retry queue. `try_delete_pool_user` (`:674-691`) is documented as "purely queue a retry, never abort" and returns an error code instead of raising; its clause is `ClientError`-only, so a `BotoCoreError` raises. The route calls it AFTER the local row and dependents are deleted and committed (`api/admin.py:718-720, :724`) and BEFORE the `PendingCognitoDeletion` row is written (`:726-734`). Result: 500, the pool user stays (disabled by the earlier step), and nothing queues the retry that `backend/app/scripts/retry_cognito_deletions.py` drains, so the pool account is orphaned and the email cannot be re-invited (`UsernameExistsException`). Needs the failure to land between `AdminDisableUser` and `AdminDeleteUser`, or any network-level error on that last call.

## Fix direction (INFERRED, not applied)

In `cognito_admin.py`, treat `BotoCoreError` like the non-special `ClientError` in all ten clauses (shared symbols in [ISS-1144](20261009-0725-ISS-1144.md); the code for a `BotoCoreError` is its class name) so each site raises `ProviderUnavailableError`, or for `try_delete_pool_user` returns the class name as the retry code. `invite_user` has one more place that names the family without being an `except ClientError` clause: `isinstance(exc, ClientError)` at `:370`, which decides whether the compensating branch raises `ProviderUnavailableError` or re-raises raw. Leave `api/admin.py` botocore-free. `_retry_on_throttle` needs no change: it re-raises anything that is not a throttle `ClientError`, so the `BotoCoreError` reaches the caller's clause. Then give `disable_user` (`admin.py:600`) and `delete_user` (`:712`) the same `try / except Exception: _raise_for(exc)` the other five routes have; the `delete_user` wrapper must wrap only the `cognito_admin.delete_user` call, not the local transaction or the retry-queue write that follows.
