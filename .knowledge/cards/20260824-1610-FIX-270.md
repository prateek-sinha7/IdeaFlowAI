Four related display bugs in the run-history surface, all with the same root cause: no
mechanism existed to resolve a dynamic-catalog pipeline type (anything without a
hand-authored `TYPE_META` entry — every spec-014 `ex_A*` fixture) to its real name or
correct bucket.

1. **Agent count missing** on non-standard workflow types — `FamilyGroupCard`'s label
   only appended the agent-count suffix for known types. Fixed: always appended now
   (`` `${agentCount} agent${agentCount === 1 ? "" : "s"}` ``).
2. **Generic "Custom" instead of the real name** — no fallback existed past the hardcoded
   `TYPE_META` map. Fixed: new `selectWorkflowShortNameIndex` (`globalSlice.ts`) +
   `useWorkflowShortNames()` (`useWorkflowMetadata.ts`) + `resolveWorkflowTypeLabel(type,
   shortNameFor)` (`RevisionFamilyView.tsx`) — curated `TYPE_META` label if one exists,
   else the live catalog's `short_name`, else a humanized fallback
   (`ex_A4_human_gate` -> "Ex A4 Human Gate") for the pre-catalog-load render.
   **Own bug caught mid-fix**: first attempt's "does this type need the catalog lookup"
   check was `type === "custom"` (backwards) — `TYPE_META["custom"]` is a real, truthy
   key, so literal `"custom"` runs got the short-name treatment and every actually-unmapped
   type got the generic fallback, opposite of intent. Fixed with an explicit
   `needsCatalogLookup = type !== "custom" && !TYPE_META[type]` guard.
3. **"Custom" filter tab undercounted** (5 shown, ~44 expected) — `baseWorkflowType`
   bucketed only exact `"custom"` runs; every dynamic-catalog type matched no bucket at
   all and was invisible to every filter tab. Fixed: new `filterBucketFor(type)` — the 4
   known framework types keep their own bucket, everything else buckets as `"custom"`.
   Replaced `baseWorkflowType` at both call sites in `WorkflowHistory.tsx`
   (`matchesFilter`, tab-count computation).
4. **Divert-link breadcrumb showed message text + step id**, not the target workflow's
   name — `DivertBadge` now uses the same `resolveWorkflowTypeLabel` resolver; the
   `, step {stepId}` clause was dropped entirely (not just deferred) per explicit
   instruction.
