# FIX-725

## What was wrong

This fix is for bug report QA-KB-065. The root cause is from the 2026-10-02 analysis on
[ISS-684](20260918-ISS-684.md) and was not re-derived here. Every cited line was re-read before editing and the card
held. The chain had moved down by 12 lines since the analysis.

`_execute_impl` picks a code step's adapter with an if/elif over four literals: `publish`, `assemble_prototype`,
`assemble_backlog` and `extract_prototype_ui` (`engine.py:6458-6508`). Its `else` ran
`_registry.resolve("strategy", strategy_name)` without checking `step.mechanical`. For a code step, `strategy_name`
is the default `single_shot` (`engine.py:6279-6281`, `plan.py:468`, `compiler.py:901`). So if the registry and
compiler accepted a kind that the chain had no branch for, the step ran a model on its empty prompt and was billed for
it. The analysis's offline probe: 8 tokens, the run completed, no error. The defect is latent: today all four
registered kinds have branches.

Line numbers below are as of this fix, in the uncommitted tree.

## What changed, and why there

1. **`backend/agents/execution_engine/engine.py:6509-6520`.** A new `elif getattr(step, "mechanical", None):` sits
   between the last kind branch and the `else`. It logs at ERROR, naming the step and the kind. It then yields the
   step's `agent_error` (`recoverable: False`, error `Code step kind '<kind>' has no engine dispatch branch`) and
   raises `StepRaised(spec.id, msg)`. The existing `except StepRaised` in `_execute_impl` (`engine.py:7599`) marks the
   run failed and emits ONE `pipeline_failed` with `agents_failed: [step id]` and that error.

   Why this shape: ISS-684's Correction 2. A bare raise at selection time sits outside `_guarded_step`
   (`engine.py:14345`), which wraps only `strategy.run`. It would reach the REST driver's generic crash handler with
   no step id and no `pipeline_failed`. `StepRaised` lives in the kernel, so the guard stays in the engine, because
   `agents.capabilities` may not import the kernel.

   Why one place: the chain is the only place a code-step adapter is selected, and every driver (REST/SSE launch,
   panel revision, the NDJSON adapter, resume) runs through `_execute_impl`. This was re-grepped at fix time:
   - `resolve("strategy"` has two engine sites. One is `:6522`, this `else`. The other is `:11519`,
     `_strategy_runs_agent_inline`, which only reads a flag.
   - `_guarded_step(` has one caller (`:6527`).

   What did not change: the four handled kinds and every step with no `mechanical` value take the same code path as
   before.

2. **`backend/agents/workflows/plan.py:471-475` and `:488`, comments only.** They said `"publish"` was "the only
   value the compiler accepts today" and that the engine hook was "a separate proposal". Both were stale. Refreshed
   per ISS-684's fix item 4: any `_ALLOWED_MECHANICAL_KINDS` kind is allowed, each is dispatched by its own engine
   branch, and an unhandled kind fails.

## Deliberately not done

- **The kind-to-adapter table (ISS-684 fix item 2, marked optional).** The red test's parity half,
  `test_engine_dispatch_matches_registered_kinds`, collects the engine's kinds with the regex
  `getattr\(step, "mechanical", None\) == "([a-z_]+)"`. Collapsing the chain into a dict would leave that test
  reading an empty set. The test is the pinned contract, so the chain stays literal.
- **Failing before the pre-step gates, or a pre-flight over `compiled.steps` (ISS-684 Correction 3, optional
  hardening).** An unhandled kind still fails at its own step. By then the earlier steps have run, and so have the
  step's own pre-step gates and `before_step` hooks. [ISS-1004](20261002-0522-ISS-1004.md)'s convention-aligned fix
  would move the selection above the gates.
- **[ISS-1004](20261002-0522-ISS-1004.md) (a ticked Code step gets no review gate) and
  [ISS-1005](20261002-0522-ISS-1005.md) (the compiler never applies a code step's `user_allowed`).** Both stay open.
  Neither has a red test (`verification.test_files: []`), and this guard cures neither:
  - ISS-1004 sits at `_runs_agent_inline` (`engine.py:6300`).
  - ISS-1005 sits in `compiler.py`, and its own card says it may be intent: ADR-0045 calls `user_allowed`
    palette-only for code steps.
- **ADR-0045 itself is not edited.** Its recipe is restated below, as ISS-684 allows.

## ADR-0045's recipe, restated

[ADR-0045](20260918-ADR-0045.md) § "Adding a sixth code step" calls its step 4 (the engine `elif`) "the one that fails
silently if you skip it", and points at "ISS-646". Both are stale:

- Skipping step 4 now fails loudly twice. At test time, `test_engine_dispatch_matches_registered_kinds` fails because
  the engine's literals no longer equal the registry's and the compiler's kinds. At run time, the step fails with
  `agent_error` plus one `pipeline_failed` that names the kind. Either way, no model runs.
- The branch now goes in `engine.py:6458-6508`, above the ISS-684 guard, not at `:5977-5990`.
- The trap's card is [ISS-684](20260918-ISS-684.md). ISS-646 is unrelated.

The other steps are unchanged:

1. The adapter module with its `@register("mechanical", ...)` stub.
2. The registry's `discover()` list.
3. `compiler._ALLOWED_MECHANICAL_KINDS`, pinned by `test_compiler.py`.
4. The engine `elif`.
5. `_EXPECTED_NAMES` in `test_registry_capabilities.py`.
