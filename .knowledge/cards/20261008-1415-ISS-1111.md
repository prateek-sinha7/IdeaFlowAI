# ISS-1111

**Register source:** sibling derived during the `QA-KB-100` analysis on 2026-10-08 (root [ISS-1092](20261007-2308-ISS-1092.md)). Not its own bug row.

**Confidence:** CONFIRMED up to the compiled plan: an in-process probe against the real `merge_override_steps` and the real registry, and an HTTP round trip as a basic-tier caller. INFERRED beyond it: no run was launched (a run costs money and needs the approval click), so the last hop under "Reach at run time" follows from code read, not from an observed run. Evidence: `evidence/qa-kb-100/analysis-02` to `-08`.

## Condition

[ISS-1092](20261007-2308-ISS-1092.md) sampled one capability kind, the `security` gate. The call it blames, `overrides.py:100` (`trust="db"`), switches off three separate checks, not one:

1. CAP-03 `_check_trust` returns at `if trusted: return` (`compiler.py:506-507`). It guards gate, hook, validator, compaction, post_step, strategy, task_parser, mcp_server and context_provider references.
2. The grant-path rejection of `exec` / `network` / `secrets` / `spawn_subagents` sits under `if not trusted:` (`compiler.py:1023`).
3. The permission cap: `cap_key_for_trust("db")` is `"trusted"` (`permission_caps.py:75`, `:180`), so `exec` and `spawn_subagents` survive `apply_cap` and tool packs beyond `file_extract` and `playwright` survive.

20 override steps were compiled both ways (`analysis-03`). Eleven pass at `trust="db"` (shipped) and are refused at `trust="user"`:

| the override step carries | shipped (`db`) | `trust="user"` |
|---|---|---|
| `gates: [security]` | applied | refused, `('gate','security')` not user-allowed |
| `gates: [approval]` | applied | refused |
| `tools.exec` + `gates: [security, approval]` | applied, `Step.tools.exec=True` | refused |
| the same plus `validators: [code_test, code_lint]` | applied | refused |
| `tools.spawn_subagents` | applied, `Step.tools.spawn_subagents=True` | refused, "engineer-only" |
| `hooks: [provenance_audit]` | applied | refused |
| `compaction: html_skeleton` | applied | refused |
| `post_step: revision_validation` | applied | refused |
| `tools.mcp: [postgres.query]` + `security` gate + `secrets` grant | applied (effective `mcp` is capped to `[]`) | refused |
| `tools.network` | applied (effective `network` stays False) | refused |
| `tools.secrets` | applied (effective grant dropped) | refused |

Also: `tool_sets` of `spawn_subagents`, `pptx` and `ask_user` are accepted at both levels but survive only at `db`; [ADR-0044](20260901-0324-ADR-0044.md) locks the untrusted list to `file_extract` and `playwright` "regardless of what the composer UI offers". Controls pass at both levels: a benign step, `gates: [human]`, `validators: [code_test]`. Refused even at `db`: exec without both gates (D-01) and a powerful MCP server without `security` plus `secrets` (MCP-04).

## Reach at run time

CONFIRMED by reading:

- The merged plan is the plan that runs: `run_commands.py:3635` (`compiled = _merged`) feeds `compiled_override`, which `engine.py:4977-4981` adopts.
- `engine.py:5914-5925`: when any step has `tools.exec`, the engine calls `runtime_env.create_workspace(exec=True)`. No setting gates this (`backend/app/core/config.py` has no exec switch).
- `local.py:1713-1722` and `:235-238`: that workspace's policy allows `python`, `python3`, `pytest`, `ruff`, with 60 s CPU, 512 MB, 120 s wall and a scrubbed env.
- `code_test.py:90` runs `pytest -p no:cacheprovider -q .` in the run sandbox through that workspace. `code_test` is `user_allowed=True`, so a user may declare it; it is inert until the workspace has exec.
- The `approval` gate pauses for a human sign-off through the same review-gate mechanism as `human` (`approval.py:1-20`). INFERRED: the run's owner answers it from the run's own screen, so the approval is the caller approving themselves.
- The runtime second line of defence cannot fire: `security.py:127` reads `getattr(step, "trust", "file")` and `Step` (`plan.py:456`) has no `trust` field, so it always sees `"file"`. [ADR-0039](20260904-1424-ADR-0039.md) records this as residual risk 2.
- `local.py:476-480` accepts the residual that an allow-listed interpreter can still open sockets because "exec is engineer-only + `security`-gated".

INFERRED: an agent whose prompt the user wrote writes a `test_*.py` or `conftest.py`, and pytest executes it as the backend's OS user. What would settle it: one launched override run with an exec step and `code_test`, then reading the exec audit rows. Not done.

## Tier

`ppt` and `user_stories` are basic-tier (`entitlements.py:11-16`). `custom` (the Composer's base) and `sample_subagents_parallel` are enterprise-only (`entitlements.py:67`). In the probe a basic caller got **403** for the Composer row and **201** for the exec override (`analysis-05` W0, W1). The commit that widened trust (`ea2db4e02`) paired it with an enterprise entitlement ("Entitle pdf_to_prototype and sample_subagents_parallel on the enterprise tier; user_launchable: true alone does not entitle a pipeline"). The override path reaches the same grants with only the built-in's own entitlement.

## Expected vs actual

Expected: every row above is refused (422 at save, the file plan at read), the way `test_a_not_user_allowed_gate_is_rejected` expects for the gate. Actual: eleven are applied.

## Why the root cause implies it

It is the same line. A fix that special-cases the two gate names closes five rows (every row that names `security`; exec cannot compile without both gates, D-01) and leaves six open, among them `spawn_subagents` and the engineer-only hook, compaction and post_step. Moving the trust argument closes all eleven. The red test therefore has to be one row per kind, not one row.

## Fix direction (INFERRED, not applied)

The root card's fix. `analysis-07` shows that changing only the trust argument at the merge call site turns `test_workflow_override.py` from `1 failed, 5 passed` into `6 passed` and leaves four neighbouring override suites unchanged (7, 17, 8 and 21 passed, before and after).

The same change should correct the statements the trust widening left false: `engine.py:5910-5912`, `_exec_support.py:54-55`, `compiler.py:313-314`, `:367`, `:447`, `:499`, and `overrides.py:9`, `:18-21`, `:39-44`, `:97-99`.

Not covered here: the writers ([ISS-1112](20261008-1415-ISS-1112.md)), the second reader ([ISS-1113](20261008-1415-ISS-1113.md)) and the non-override shape ([ISS-1114](20261008-1415-ISS-1114.md)).
