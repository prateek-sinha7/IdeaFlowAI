# ISS-859

Found while implementing [FIX-640](20260923-0207-FIX-640.md). It is not a defect
under the user's 2026-09-23 option-(a) decision ("the app shell's single
`/api/runs?limit=50` … per page are intended"), so it is recorded rather than
fixed. It is **INFERRED from the code**, not measured: FIX-640's e2e runs cover
only the five header routes its bugs name, not `/create/*`, `/admin` or a tab wake.

## What happens

`RunConnectionProvider` is now the one owner of the run list, and it queries on
boot and on every `visibilitychange`-to-visible / `online` event, whether or not
anything on screen reads the rows:

1. **Routes with no header.** `/create/*` returns `<LaunchWizard>` standalone
   (`page.tsx`'s `wizardMode` early return) and `/admin` is its own route with
   no AppHeader. Before FIX-640, the one run-list call on a cold `/create/ppt` was
   the `signedIn` preload's `runs?limit=6` (**QA-PS-044**'s verification in
   `LEDGER.md` measured `runs?limit=6 x1` and no `limit=50`). Now it is the
   provider's `runs?limit=50`: the same count, about 32 KB more. QA-PS-044's
   title names "runs?limit=50 on a wizard page".
2. **Tab wakes.** A wake refetches the list on every route. That was HEAD's
   behaviour; FIX-617 removed it for tabs owning no runs only because the rows
   were discarded then. They now feed the badge, so the refresh has a reader on
   header routes, but not on the two above.
3. **`/runs` cascade.** Each wake refetch hands page.tsx a new `recentRuns`
   array, and `WorkflowHistory.tsx`'s T38 effect (`recentRunsRef`, "re-fetch
   whenever the parent's recentRuns changes reference") answers with its own
   `getWorkflows({ limit: 50 })`: two calls per tab focus on `/runs`.

## Disposition

Open, low severity. It needs a product call only if header-less-route bytes
matter.

## For the fixer

The considered alternative is to fetch only for a consumer: the provider
queries at boot only when this tab owns runs to re-attach, and otherwise waits
for page.tsx's `loadRecentRuns` (asked on header routes, not `/create/*`);
wakes refresh only a list someone asked for. The trap, per the locked
constraint above: if page.tsx stops asking on `/create/*`, a sign-in that lands
there skips the identity clear, and the first header route after it paints the
previous account's list for a frame. That frame is enough for HomeLaunchGrid to
cache those titles under the new account's key. So the wizard route still needs
an identity check that does not fetch. For item 3, the cheaper fix is to keep
the array identity when the refetched rows are unchanged.
