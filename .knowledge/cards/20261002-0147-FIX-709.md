# FIX-709

## What was wrong

Register entry QA-KB-044 (Low, `/runs/{id}`). A read-only PINNED version whose run has no stored
`output` showed the Preview tab's last-resort "Output will appear here". That is the same
future-tense copy a run gets before it has produced anything.

- The root card is [ISS-154](20260813-0819-ISS-154.md).
- [ISS-933](20261001-2231-ISS-933.md) is its sibling. A pinned version that ended failed,
  cancelled, degraded or diverted got no terminal affordance either.

The symptom is reached by pinning a TAGLESS member, through either of two routes:

- the `/runs/{root}/versions/{n}` URL (the pin effect);
- a chat result card (`handleSelectVersion`).

The Version menu lists only tagged members and routes to `RefVersionPreview`, so it never reaches
this branch (ISS-154, correction 1). Live rows: family `87e02c32-96a9-4e50-8ed0-79023d83540f`, v3
`cancelled` and v4 `failed`. Both have `output` NULL and `git_tag` NULL.

## Root cause (from the cards, re-checked before editing)

- At HEAD `024c03ef8`, `PreviewPanel.tsx:1825-1828` is the `!hasContent ? (...)` branch. It has
  one string, "Output will appear here", which is the only occurrence of that copy in
  `frontend/src`.
- Every branch ahead of it is keyed on the SHELL's props:
  - `isStillRunning`;
  - `showFailureAffordance` / `showDivertedAffordance`, from the raw `pipelineState` and
    `reopenedRunStatus`;
  - `isLoadingRunData`.
- `versionViewFrom` dropped the pinned run's `status`. Nothing in the panel could tell
  "settled, nothing stored" from "nothing yet".

Blast radius, re-grepped before editing:

- `versionViewFrom` (`:605`) is the only constructor of `VersionView`.
- It has two callers, `handleSelectVersion` (`:919`) and the URL-pin effect (`:1022`). Both feed
  the one `viewingVersion`, so a single render-site change covers both routes.
- The non-test importers of `PreviewPanel` are `DashboardLayout.tsx` and `RunDetailPage.tsx`.
  Neither builds a `VersionView`.

## What changed, and why there

Every change is in `frontend/src/components/preview/PreviewPanel.tsx`:

1. **`:28`.** `WorkflowStatus` joins the `@/types/index` type import.
2. **`:575-578`.** `VersionView` gains `status: WorkflowStatus` (ISS-154 amended fix, step 1).
3. **`:639`.** `versionViewFrom` returns `status: run.status` (step 2).
4. **`:1830-1847`.** A new branch sits directly ahead of the neutral one:
   `!hasContent && viewingVersion && TERMINAL_RUN_STATUSES.has(viewingVersion.status)`.
   - A `completed` version renders `No deliverable was saved for this version`, in the neutral
     branch's own `text-xs text-ink-400` line. This is ISS-154 step 3, with the copy as agreed.
   - A `failed`, `degraded`, `cancelled` or `diverted` version renders
     `<DegradedRunAffordance cancelled=... diverted=... />` (ISS-933).
     - There is no `onRetry` and no `failedAgents`.
     - The component already carries the copy the same run gets when it is opened directly:
       "This run was cancelled" or "This run did not complete successfully", plus the diverted
       detail line.
     - Without `onRetry` it shows "Open the Thinking tab to view details." instead of a retry
       button.

Why the render site:

- It is the one place every pin route converges.
- The branch sits after `isLoadingRunData`, so the loading skeleton still wins while a fetch is
  in flight.
- `TERMINAL_RUN_STATUSES` (`:398`) already existed.
- A pinned `running` member keeps the neutral copy, and so does a run record with no `status`.
  The running case is reachable only by a hand-typed URL, because the pin effect has no terminal
  guard.

### Where this differs from the card

- **The change is a separate branch, not a ternary inside the existing `!hasContent` branch.**
  ISS-154's amended fix used one ternary there and printed the new copy for every terminal
  status. ISS-933 is in the same file and uses the same test, and it replaces that copy with the
  affordance for the four statuses that ended badly. The test file records this: "The ISS-154 copy
  for these statuses is superseded by the affordance". The two cases render different elements,
  so they need separate branches.
- **ISS-933's product call was taken as the full affordance block, minus retry and the
  failed-agent list.** The card offered "status-specific copy only versus the full affordance
  block". The full block, without retry and the failed-agent list, is what the test asserts.
- **The four hunks come from an interrupted first attempt.** The first fixer for this bug was
  stopped by an API limit at 22:40 on 2026-10-01, after writing these four hunks. The
  `PreviewPanel.tsx` mtime is still `Oct 1 22:40:16`. Every hunk in `git diff` belongs to this
  bug, and nothing else had touched the file since. Each hunk was re-read against both cards,
  kept as written, and verified below.

### Deliberately not changed

- **Unpinned terminal-empty runs keep "Output will appear here".** This is ISS-154's locked
  constraint, and it is asserted by `PreviewPanel.degraded.test.tsx:177`/`:259` and by e2e
  TS-Q-05 and TS-R-03.
- **The shell signals are untouched:** `reopenedRunStatus`, `terminalFailure`,
  `terminalFailureNoDeliverable` and `defaultTabDiscriminator`. ISS-933 says feeding the pin into
  them drops the Preview tab and forces Audit for the whole panel.
- **The header run state of a pinned empty version is unchanged.** It still reads "idle"
  (ISS-154 blast radius, out of scope).
- **NULL `workflow_runs.output` rows are not backfilled** (ISS-154, rejected alternative).
- **One new finding is recorded, not fixed:** [ISS-952](20261002-0147-ISS-952.md) (open).
  - When the SHELL run itself ended cancelled, failed or diverted, its affordance branch sits
    ahead of this one.
  - A pinned empty version then shows the shell's status, or loses the Preview tab when the shell
    failed.
  - This is the reverse direction of ISS-933. It is outside both cards, and changing it would
    change shell tab visibility.
