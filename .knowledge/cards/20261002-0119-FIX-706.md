# FIX-706

## What was wrong

This is bug report QA-KB-025. The root cause, the blast radius and the agreed fix with its four amendments are the
analysis on [ISS-686](20260918-ISS-686.md). The Simple-view sibling is [ISS-918](20261001-2221-ISS-918.md). This card
does not re-derive either.

In short, the Canvas rail owned each parser's file as a two-entry literal, `PARSER_TARGET` (`CanvasConfigRail.tsx:70-73`
at HEAD `024c03ef8`). The "Task source type" `onChange` (`:1694` at HEAD) wrote
`PARSER_TARGET[parser] ?? sel.task_source?.target`. Any parser missing from the map, which today is `heading_tasks`
and tomorrow is any newly registered parser, took the PREVIOUS parser's file into the saved manifest. A parser that
honours `target` through `parse_preferring_target` tries that file before its own `fallback_targets`. The Simple view
(`AgentsPopup.tsx:2443` and `:2496` at HEAD) held a second copy of the same fact with a different value,
`target: "tasks.json"`.

## What changed, and why there

The registry's `_META` already projects `config_schema` through `describe` to `/api/capabilities`, and both composer
views read that payload through the one `useAgentCapabilities` hook. So the fact goes on the `@register`, and one
helper next to the hook reads it for every caller. No parser name was added anywhere.

1. `backend/agents/capabilities/task_parsers/json_tasks.py:49` adds `DEFAULT_TARGET = "build/tasks.json"`. `:102-111`
   gives `@register` a `config_schema` of `{"type": "object", "properties": {"target": {"type": "string",
   "description": ..., "default": DEFAULT_TARGET}}}`. `:229` makes `fallback_targets` default to `(DEFAULT_TARGET,)`.
   The registry-visible default and the runtime fallback are now one constant, as amendment 1b asked.
2. `backend/agents/capabilities/task_parsers/screen_plan.py:195-204` gives `@register` the same schema with
   `default: DEFAULT_TARGET`, the existing `"build/screens.json"` constant (`:40`). `heading_tasks.py` is unchanged:
   it reads the reply, so it declares no target.
3. `frontend/src/components/workflow/AgentsPopup.tsx`:
   - `:1621-1634` adds the exported pure `parserTarget(options, name)`. It returns
     `config_schema.properties.target.default` when that is a string, else `undefined`.
   - `:1640-1642` and `:1676`: `taskParserOptions` now carries `config_schema`, the projection `mechanicalOptions`
     already widens (correction 4). `CapabilityEntry.config_schema` was already typed `Record<string, unknown>`, so no
     new type.
   - `:2063-2067`: `AdvancedExpander` destructures `taskParserOptions` and computes `jsonTasksTarget`.
   - `:2508` and `:2561`: the two Simple-view seeds write `...(wave && jsonTasksTarget ? { target: jsonTasksTarget } :
     {})` in place of the literal "tasks.json" (ISS-918).
4. `frontend/src/components/workflow/composer/CanvasConfigRail.tsx`: `:26` imports `parserTarget`. `PARSER_TARGET` is
   deleted. `:1556` (fan-out mode), `:1609` (source agent) and `:1639` (the unknown-producer hint) read
   `parserTarget(taskParserOptions, parser)`. At `:1691` the parser `onChange` is now
   `const target = parserTarget(taskParserOptions, parser);`. The `?? sel.task_source?.target` carry-over is gone,
   and the existing `...(target ? { target } : {})` spread omits the key for a parser with no default.
5. Test fixture, not an assertion: `CanvasConfigRail.test.tsx:62-63`. The `screen_plan` palette entry now carries
   `config_schema.properties.target.default: "build/screens.json"`, the shape the backend serves. ISS-686's analysis
   step 5 asked for exactly this, because the rail now reads the default from the palette. The `:683` assertion
   (`target` is `"build/screens.json"`) is unchanged.
6. New guard: `backend/tests/unit/api/test_capabilities_api.py:263`, `test_task_parsers_declare_their_default_target`.
   `json_tasks` and `screen_plan` serve their default file in `config_schema`, and `heading_tasks` serves none.

This change was started by an earlier QA-KB-025 fixer that an API limit stopped part-way. This session read its
hunks, found them complete and correct against the cards, and kept them. The other hunks in `AgentsPopup.tsx` and
`CanvasConfigRail.tsx` (`withToolGrant`, the ConfigLeversFlat tool-grant rows, the `:773` comment) are
[FIX-703](20261002-0051-FIX-703.md)'s (QA-KB-016). They were left untouched.

## Accepted hazards (named in ISS-686, not changed)

- Loading window: `taskParserOptions` is empty until `/api/capabilities` returns. The fan-out mode and source selects
  are not `disabled={loading}`, so a switch inside that window saves no target. That is runtime-safe, because every
  file-reading parser has its own fallback, but it differs from the old always-seeded manifest.
- The palette gear: `AgentsPopup.tsx` shows a configuration affordance for any capability with a non-empty
  `config_schema`, so json_tasks and screen_plan now show one. Its field list renders top-level schema keys, which
  for this JSON-Schema shape are `type` / `properties`. The six schemas that were already populated
  (`wave_scheduler`, `task_loop`, ...) behave the same way. The analysis left this pre-existing rendering alone.
- Simple-view waves now seed `build/tasks.json`, not the root `tasks.json`. `parse_preferring_target` therefore tries
  `build/tasks.json` and then the reply. A planner that writes only a root `tasks.json` and narrates its reply is no
  longer found from a Simple-view-composed wave. ISS-918 prescribes this: the default belongs to the parser, and a
  step's authored target belongs to the step. Shipped manifests are unaffected, because they carry their own authored
  target.

## For verify (Browser)

The analysis gives this repro, and it needs no mock:

1. Open `/workflows/sample_wave/canvas` and click the `sample-wave-worker` node.
2. On the Config tab, set "Task source type" to "## Task headings".
3. Click Save as copy with the POST to `/api/user-workflows` aborted. The payload's `task_source` has no `target`.
4. Pick "JSON task list" and save the same way: `target` is `build/tasks.json`.

If you mock a fourth parser, use `config_schema.properties.target.default`. The validator's original flat
`config_schema.target.default` is not the shape the rail reads.
