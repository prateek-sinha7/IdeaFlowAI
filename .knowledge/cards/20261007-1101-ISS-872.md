## Root cause

CONFIRMED from code at `backend/app/api/run_commands.py`.

`_drive_launch_to_queue` (line ~4302) sets `wr.status = "degraded"` whenever the
engine emits a `pipeline_complete` event with `status == "degraded"`. This decision
trusts the event payload unconditionally.

The engine (in `_execute_impl`) sets `status="degraded"` when `_unrecovered_agents`
is non-empty. `_unrecovered_agents` is computed from `ectx.failed_invocations` using
`(agent_id, task_number, visit_count)` triples (ISS-028/R-08). In certain situations,
a visit_count mismatch between the recorded failure triple and the completion triple
can leave an agent in `_unrecovered_agents` even when that agent DID emit
`agent_complete` (i.e., it recovered):

- **R-08 visit_count divergence:** a step that errored at visit N and subsequently
  completed at visit N+1 would have failure triple `(agent_id, "", N)` not in
  `_completed_pairs` which holds `(agent_id, "", N+1)`.
- **Prior attempt bleed (ISS-437 pattern):** `ectx.failed_invocations` not scoped to
  the current attempt boundary in all code paths.

**Evidence:**
- All 6 agents in the User Stories run show green checkmarks — 6 `agent_complete`
  events confirmed in the SSE stream.
- `pipeline_complete.agents_completed = 5` and `status = "degraded"` — the engine
  incorrectly classified one agent as unrecovered.
- Clicking "Run again" (POST /resume, 0 new tokens, 0 s) immediately corrects to
  "Run complete 6/6 agents" — confirming all 6 `agent_complete` events were in the
  DB and `_reconcile_terminal_status` returned "completed" once a new clean
  `pipeline_complete` was emitted by the resumed zero-work pass.

## Blast radius

- Only runs where the **engine** produces a false-positive `status="degraded"` and
  ALL degraded_failed_agents also have `agent_complete` events.
- Genuine degraded runs (at least one agent with no `agent_complete`) are unaffected.
- `_drive_revision_to_queue` has the same structural gap (ISS-857) but is not changed
  here — scoped as a deferred finding to that existing issue.

## Resolution

[FIX-648](20261007-1101-FIX-648.md): added an R-09 safety net in `_drive_launch_to_queue`
that cross-checks `degraded_failed_agents` against the `agent_complete` events in
`raw_events` before committing the status. If every listed "failed" agent also completed,
the run is written as "completed" instead of "degraded".
