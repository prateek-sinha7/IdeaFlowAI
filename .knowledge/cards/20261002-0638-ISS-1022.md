# ISS-1022

INFERRED sibling of [ISS-908](20261001-2204-ISS-908.md) (QA-KB-080), derived from its root cause. Nothing below fails today: the lead is
that the same defect is one caller change away in six more places, and that nothing in the tree would say so before it happens.

## Why the root cause implies it

[ISS-908](20261001-2204-ISS-908.md)'s mechanism is a duck-typed test double whose `run_fanout` spells the keywords of the day, while the real handle
(`backend/agents/execution_engine/kernel_services.py:1161-1168`, `run_fanout(self, requests, ctx, *, step, event_queue=None)`) grew one.
Every consumer receives the handle as `Any` (`_fanout_wave_stream.py:37`, `runner: Any`), so no type checker sees the drift, and every call site passes by
keyword, so the first sign is a `TypeError` at run time, in the one test that happens to drive a caller that passes the new keyword.
That is true of every fake of this method, not only the one that broke.

## Condition (CONFIRMED by run and by `inspect.Signature.bind`)

Census of every `run_fanout` double under `backend/tests` (`evidence/qa-kb-080/analysis-run-fanout-fake-census.py`, output beside it): 17 fakes.
The real callers split in two:

- FULL call `(requests, ctx, step=..., event_queue=...)`: `_fanout_wave_stream.py:71-73` (via `wave_scheduler.py`) and `_fanout_stream.py:32-34` (via `parallel_group.py:132`).
- SHORT call `(requests, ctx, step=...)`: `fanout_batch.py:121` and `engine.py:8624` (`_derive_fanout`). Both are `HEAD 024c03ef8` numbers; the shared working tree carries
  [FIX-693](20261001-2204-FIX-693.md)'s uncommitted edits to both files, so the working tree reads `:127` and `:8632`.

Ten fakes accept the full call (`event_queue=None`). Seven reject it. One of the seven is driven by a FULL caller, which is [ISS-908](20261001-2204-ISS-908.md).
The other six are driven only by SHORT callers, so they are green today:

| `tests/unit/agents/test_fanout.py:320` (`_StratRunner`) | `fanout_batch` strategy | 31 passed |
| `tests/unit/agents/test_fanout.py:563` (`_Runner`) | `ExecutionEngine._derive_fanout` | same file |

| `tests/agents/test_fanout_parent_task_id.py:30` (`_Runner`) | `ExecutionEngine._derive_fanout` | 5 passed |

The newest of them, `test_iss685_resume_parses_task_file.py:173`, was written yesterday and copies the narrow shape: new narrow fakes are still being authored.

## Expected vs actual

- Expected: a change to the handle, or a new caller passing `event_queue`, fails ONE guard that names every non-conforming fake by `file:line` of its `def`.
- Actual: it fails whichever unrelated tests drive the changed call, after the fact, with a bare `TypeError`; and for the best-effort teardown path the kernel swallows
  the `TypeError` into a log line (see [ISS-1023](20261002-0638-ISS-1023.md)), so the symptom is a wrong assertion rather than an error.

## Trigger

Either of: `fanout_batch.py` or `_derive_fanout` starts passing `event_queue` (the natural way for `fanout_batch` to stream live worker events, as `parallel_group` and
the wave scheduler already do), which breaks the six together; or any new keyword lands on `KernelServices.run_fanout`, which breaks the narrow fakes behind whichever callers start passing it.
The runner-handle seam has moved three times in four weeks: `event_queue` added to `run_fanout` for `parallel_group` (`24332e0c5`, 2026-08-14), the wave scheduler became a second caller that passes it
(`1e329e47b`, 2026-09-04), and `delete_branch` was added to `teardown_isolated_workspace` (`24f112706`, 2026-09-09). The last two each broke a hand-rolled fake ([ISS-908](20261001-2204-ISS-908.md), [ISS-1023](20261002-0638-ISS-1023.md)).

## Prior art, and why it does not reach here

`backend/tests/unit/agents/test_gate_stub_signature_drift.py` ([FIX-231](20260812-1120-FIX-231.md)) is exactly this guard for `_run_review_gate`: it derives the real signature from
`engine.py` by AST, finds every stub, and asserts `inspect.Signature.bind` accepts the full keyword call. It is hard-wired to one method (`METHOD = "_run_review_gate"`, `ENGINE = ...engine.py`),
and its own docstring calls the drift "the fourth generation of one defect". [ISS-094](20260812-1120-ISS-094.md) already names the attribute-level variant as the family-ending move.

## Fix (proposed, not applied)

- Cheapest: do nothing to the six until a short caller changes. They are correct today.
- Family-ending: parametrise the FIX-231 guard (or add a sibling file) over the runner handle: derive `KernelServices.run_fanout` (and `teardown_isolated_workspace`, see
  [ISS-1023](20261002-0638-ISS-1023.md)) by AST from `kernel_services.py`, bind the FULL keyword call against every fake, and floor the census so a broken sweep fails loudly.
  The census script is a ready prototype (it is red today on exactly the seven narrow fakes). Widening the six fakes with `event_queue=None` goes in the same change, one line each, matching the ten that already comply.
- Not a fix: loosening the real signature, or giving the fakes `**kw` to swallow everything (it would hide the next real drift, which is what a bind guard exists to catch).

## What would settle it

Make a throwaway copy of `fanout_batch.py` pass `event_queue=` and run `tests/unit/agents/test_fanout.py` once: expect `TypeError` in the two fanout_batch-driven tests (`:320`, `:712`). Not run: it needs an
application-source edit, which analysis does not make. The census already proves the fakes reject the call; the only inference is that a short caller will one day send it.
