## What was wrong

`BUG-20260828-011000-workflow`: on the orphaned legacy builder at `/workflow`, typing any
non-empty text into "Describe your idea" enabled "Run Workflow" while "Workflow Agents (0)"
showed zero agents attached — the count rendered a few lines above the button was never
consulted. Validated 3/3 on cold cycles by the 2-validator; see
[ISS-328](20260828-1834-ISS-328.md).

## Root cause

Two gaps in `frontend/src/components/workflow/WorkflowView.tsx`, both named by
[ISS-328](20260828-1834-ISS-328.md):

- `:473` — `disabled={!ideaInput.trim()}` on the Run Workflow `motion.button` checked only the
  brief textarea, never `pipelineAgents.length`, even though `:406` renders
  `({pipelineAgents.length})` as "Workflow Agents (N)" immediately above it.
- `:161-167` — `handleRun` opened with `if (!ideaInput.trim()) return;` and carried no floor on
  `agentIds.length`, so it would forward a 0-agent roster to `onStartPipeline` unchallenged.

## What changed and why there

Both guards were added in `WorkflowView.tsx`, mirroring the identical pattern the replacement
screen already uses (`IdeaInputPage.tsx:1343` for the handler floor, `:1730` for the button):

- `:161` — `if (!ideaInput.trim() || pipelineAgents.length === 0) return;`
- `:473` — `disabled={!ideaInput.trim() || pipelineAgents.length === 0}`

**The handler guard is the root-cause fix, not a belt-and-braces duplicate.** `handleRun` has two
trigger paths and only one of them is a button: the `Cmd+Enter` shortcut on the textarea
(`:320`, `onKeyDown={(e) => { if (e.key === "Enter" && e.metaKey) handleRun(); }}`) invokes it
directly, and a `disabled` attribute does not intercept a keydown. Guarding only `:473` would
have left the keyboard path able to dispatch a 0-agent run the moment `onStartPipeline` is wired.
Both triggers route through `handleRun`, so the floor belongs there.

Blast radius re-confirmed at fix time with `grep -rn "WorkflowView" frontend/src`: exactly one
caller, `frontend/src/app/workflow/page.tsx:58` — no sibling caller to patch.

## Deliberately NOT fixed here

`onStartPipeline`/`pipelineState` callbacks into `<WorkflowView>` at `app/workflow/page.tsx:58-62`,
or retire the route the way `proxy.ts` already retires `/workflow/create` — are a route-lifecycle
decision this card does not settle, and the "wire" branch would stand up a second, independent
run-launch and run-state seam on an unlinked route, which is the fragmentation
[ADR-0018](20260824-1631-ADR-0018.md) explicitly refused. Escalated rather than chosen unilaterally.
