## Source

Derived by the analyzer from the root cause of `BUG-20260828-081200-analytics`
([ISS-229](20260828-1601-ISS-229.md)) — same mechanism, the sibling filter control. **Not yet
independently reproduced in a browser session** (the hunter/validator only exercised "Filter by
pipeline"); this card is INFERRED from a direct code read, filed so it does not go
rediscovered.

## Mechanism (CONFIRMED by code read, INFERRED as a live symptom)

`frontend/src/components/analytics/AnalyticsPage.tsx`:

- `modelFilter` (state declared line 147) is consumed in exactly three places: `modelRows`'s
  `.filter()` (line 259), `activeModelId` (line 270-272), and the "Model Details" panel (lines
  640-663, meta-only display, not a rollup).
- It is **never** referenced by `kpis`, `tokenTotals`, `spend`, `totalTokens`, `completedCount`,
  `failedCount`, `totalCount`, `successRate`, `avgTokens`, or `dailyData` (lines 193-242) — the
  identical unfiltered-derivation pattern documented as the root cause in ISS-229.
- The fetch `useEffect` (lines 154-177) depends on `[dateFilter]` only — changing `modelFilter`
  triggers no re-fetch, exactly as with `pipelineFilter`.
- The "Filter by model" `<select>` (lines 329-341) is only rendered when
  `availableModelIds.length > 1` — reproducing this needs a date range/account with 2+ distinct
  models represented (qa-admin's seeded runs mix Haiku/Sonnet per the ledger evidence, so this
  should be reachable).

## Expected vs actual (predicted from the mechanism above)

**Expected:** selecting a specific model in "Filter by model" should scope KPI tiles, the Daily
Activity chart, and Success Rate to that model's runs, consistent with the narrowed "By Model"
list.

**Actual (predicted, unverified):** only "By Model" narrows; Total Tokens, Est. Cost, Avg/Run,
Total Runs, the chart, and Success Rate should keep showing all-models totals — and "By Pipeline
Type" should also stay unfiltered by the model selection (same single-axis-only filtering as
ISS-229, mirrored onto the model axis).

## What would settle it

Reproduce live: `/analytics` as qa-admin on a range with 2+ models present, select a model in
"Filter by model", and compare KPI tiles/chart/Success Rate before vs after — same method ISS-229
used for the pipeline filter (`browser_network_requests` should show no new
`/api/analytics/summary?...&model=...` request, matching ISS-229's finding that no such param
exists server-side either).

## Fix

Same location as ISS-229 — this is not a second fix, it is the same server-recompute change
(`GET /api/analytics/summary` gaining an allow-listed `model` param alongside `pipeline`) covering
both filters in one pass, since both go through the identical single-`summary`-object flaw.


## Resolution

Fixed by [FIX-339](20260828-2231-FIX-339.md) — the same server-recompute change, covering both
filters in one pass as this card predicted. Proven by `test_model_filter_narrows_total_runs`:
TOTAL RUNS moved from 278 to 7, exactly the selected model's own breakdown row — XPASS(strict),
the pass signal, xfail marker left in place.
