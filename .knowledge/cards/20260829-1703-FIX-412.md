# FIX-412

**BUG-ID:** BUG-20260829-140111-runs-id-steps-agent

## What was wrong

From a run family's base, un-pinned route (`/runs/{rootId}/steps` — what "Back to
history" and every run-card link land on) a completed revision was unreachable
through any normal-user path. Both affordances built for it were silent no-ops:
the version picker's newest-member option, and the chat transcript's
"Answer/Open in Steps" link on the revision's own narrator card. The revision's
agent step ("Backlog Revision Agent") could only be reached by typing the
revision's own run id into the address bar, which no UI control exposes.

## Root cause — two independent defects, one seam each

**1. `latestId` and the run actually on screen were conflated**
(`frontend/src/components/preview/PreviewPanel.tsx:638-639`, pre-fix):

```
const latestId = sortedMembers[sortedMembers.length - 1].id;   // newest member
const activeRunId = viewingVersion?.id ?? liveRunId ?? latestId;
```

`liveRunId` is `contentSourceRunId` — the run id in the URL's BASE segment, which
for `/runs/{rootId}/versions/{v}/{tab}` is always the family ROOT. So on any base
route of a >=2-member family, `latestId` (newest member) and the run the panel
actually renders (`liveRunId`, the root) are structurally different values.
`handleSelectVersion` (`PreviewPanel.tsx:665-688`, pre-fix) keyed its
"already live, drop the pin" shortcut on `memberId === latestId`, so clicking the
newest member passed `null` for the pin. In
`DashboardLayout.handlePreviewPanelTabSelect` (`DashboardLayout.tsx:479-515`) a
`null` pin resolves `targetRoute` to the un-pinned route — identical to
`window.location.pathname` — and the guard at `DashboardLayout.tsx:501`
early-returns, so `window.history.pushState` never ran. Nothing navigated, nothing
re-rendered, no error. The same branch made `handleBackToLatest`
(`PreviewPanel.tsx:692-695`, pre-fix) resolve to `liveRunId` (the ROOT) rather than
the newest member — a wrong destination rather than a no-op — whenever the user
was pinned to a middle version of a longer family.

Nothing in either function reads `activeTab` as a branch condition, so the picker
no-op reproduced identically on all five tabs (one `PreviewPanel`/`RunHeader`
mount app-wide, `DashboardLayout.tsx:3127`) — [ISS-610](20260829-1631-ISS-610.md).

**2. The chat deep-link seam carried no run id at all.**
`ResultCard`'s `onClick={() => onRequestOpenTab(tab)}` (`ResultCard.tsx:164/175/207`)
passed a generic tab id only; `useTabDeepLink.requestOpenTab` was
`(tab, agentId?)`. Since the base Steps route already shows that tab, requesting
it again is inherently a no-op — the mechanism had no way to target a different
run in the family. The run id it needed was already on the wire but discarded:
`chat_narrator.project_milestone_card` (`backend/app/agents/chat_narrator.py:249`)
stamps `pipeline_run_id` on every `chat_reply` payload — a revision's card carries
the REVISION's id — and `useRunChat.upsertNarratorMessage` read only `data.run_id`,
which narrator payloads never carry, so `ChatMessage.runId` was always `undefined`
on a narrator turn.

Verified against the live fixture rather than assumed: `GET /api/runs/{id}/events`
shows the deliverable card's `deep_link.target` is `deliverable:user_stories.md`
— a FILENAME, no run id — so `DeepLinkTarget.anchor` (which
[ISS-612](20260829-1631-ISS-612.md) named as the source) cannot serve the
deliverable card kind its own test exercises. `pipeline_run_id` is present on
every card kind and is the field the type system already documents for this
("Family anchoring (D-02): the run/thread this turn belongs to",
`frontend/src/types/index.ts:118-119`), so it is the source used.

## What changed and why there

All three picker/banner defects are one chokepoint, so they are one change:

- `PreviewPanel.tsx:638-646` — new `unpinnedRunId = liveRunId ?? latestId`: the
  member the UN-pinned route renders. `activeRunId` now derives from it, so the
  two concepts have separate names and cannot be swapped by accident again.
- `PreviewPanel.tsx:665-698` — `handleSelectVersion` compares against
  `unpinnedRunId`, not `latestId`, in both the pin computation and the
  back-to-live early return. It also takes an optional `tab` (defaulting to the
  tab on screen) so the chat deep-link can switch run AND tab in one call.
- `PreviewPanel.tsx:700-706` — `handleBackToLatest` now routes through
  `handleSelectVersion(latestId)` instead of blindly nulling the pin, so the
  button pins exactly what its own label promises. Fixed at the chokepoint, not
  per-caller: `RunHeader`'s picker and `ReadOnlyVersionBanner`'s button now share
  one implementation.
- `PreviewPanel.tsx:952-970` (the merged deep-link/default-tab effect) — when a
  fresh deep-link target names a run that is a member of the mounted family and
  is not already active, it is handed to `handleSelectVersion`. Reuses the
  pin-and-navigate chokepoint above rather than building routes a second time.
- `useTabDeepLink.ts` — `TabDeepLinkTarget.runId` + `requestOpenTab(tab, agentId?, runId?)`,
  append-only so every existing URL-driven caller is unchanged.
- `MessageBubble.tsx:215` — binds the card to the run that MINTED it
  (`message.runId`). Bound here, one level above `ResultCard`, because this is
  where the transcript message is already adapted into the generic card and it
  keeps `ResultCard`'s prop a plain `(tab) => void`.
- `useRunChat.ts:407-414` — `runId` on a narrator turn falls back to the payload's
  `pipeline_run_id`. `chatSessionId` deliberately still derives from `run_id` only,
  so no existing anchoring changes.
- `ChatPanel.tsx` / `RunChatLane.tsx` / `DashboardLayout.tsx` — prop-type widening
  on `onRequestOpenTab` only; no behaviour.

## Not fixed here (deferred)

- **`DeepLinkTarget.anchor` still has zero readers** app-wide. This fix routes the
  run id through `pipeline_run_id` because `anchor` is a filename for deliverable
  cards, so `anchor` remains parsed-and-unread — recorded as
  [ISS-614](20260829-1704-ISS-614.md).
- **`ISS-611`'s second assertion.** `test_back_to_latest_from_pinned_middle_version_reaches_true_latest`
  asserts `not fetched_root_instead` — that NO request naming the family root
  fires. A bare `GET /api/runs/{rootId}` fires on ANY pin change (verified: a
  plain v2 -> v4 picker change, unrelated to this bug, emits the same request),
  because `/runs/{rootId}/versions/{v}/{tab}` keeps the root in the base segment
  and the shell re-reads the run its path names. That assertion cannot pass under
  the current addressing contract; it was left untouched rather than edited to
  match the fix — recorded as [ISS-615](20260829-1705-ISS-615.md).
