## Description

Validated from bug register entry **BUG-20260828-041815-login-expired-1**. On
`/login?expired=1` (DOM identical to plain `/login` — this is the same shared component,
confirmed against the `loginExpiredParamMustBeTrue` quirk which only affects the separate
session-expiry banner, not this error), submitting the sign-in form with invalid
credentials renders the visible text "Invalid email or password." inside a `motion.div`
at `frontend/src/app/login/page.tsx:261-268`. That element carries no `role="alert"`,
`role="status"`, or `aria-live` attribute of its own, and none of its ancestors up to
`<html>` carry one either — confirmed by walking the full ancestor chain via
`getAttribute('role')` / `getAttribute('aria-live')`, all `null`. `document.activeElement`
is never moved to the error text or back to a field; it stays on `<body>` (mouse-click
submit) or on the still-focused password `<input>` (Enter-key submit) — never anything
that would cause a screen reader to re-announce. The page's only genuine ARIA "alert"
role in the accessible tree is Next.js's built-in `next-route-announcer` (a shadow-DOM
element used only for route-change titles), which stays empty and is unrelated.

## Reproduction (validated 2026-08-28, 3/3 cold starts, all cycles — CONFIRMED on cycle 1)

Each cycle from a cold start: fresh `page.goto('http://localhost:3000/login?expired=1')`,
no reuse of prior page state.

1. **Cycle 1** (mouse-click submit, `wrong@flowinqa.com` / a wrong password): filled the
   form, clicked "Sign in". Evaluated the DOM: error `<div>` found with text "Invalid
   email or password.", `ownRole: null`, `ownAriaLive: null`, every ancestor up to
   `<html>` also `null`/`null`, `document.activeElement.tagName === 'BODY'`. Confirmed
   the defect on the first cold attempt.
2. **Cycle 2** (mouse-click submit, different invalid credentials
   `bad-user@flowinqa.com` / `totallywrong2`): identical result — `ownRole: null`,
   `ownAriaLive: null`, `closest('[aria-live], [role="alert"], [role="status"]')` is
   `false`, `activeElement` still `BODY`.
3. **Cycle 3** (varied entry path — Enter key from the password field instead of a
   button click, third distinct invalid pair `nope@flowinqa.com` / `wrongthing3`):
   identical result — `ownRole: null`, `ownAriaLive: null`, no live-region ancestor.
   `activeElement` this time is the still-focused password `INPUT` (expected, since
   Enter-submission never blurs the field) — still not the error text, so no
   re-announcement would occur either way.

Reproduced identically on all 3 cycles, deterministic across both entry paths (click vs
Enter) and three different invalid-credential pairs — no axis variation was needed beyond
what was already tried; the defect fires on every submit-with-invalid-credentials attempt.

## Expected

Per WCAG 4.1.3 (Status Messages), a programmatically-determinable status message —
`role="alert"`, `role="status"`, or `aria-live="polite"/"assertive"` on the error
container (or an ancestor) — should be present so assistive technology announces the
authentication failure without requiring a visual re-scan. Alternatively, focus should
move to the error text or back to a field with an accessible description referencing it.

## Actual

The error text at `frontend/src/app/login/page.tsx:261-268` is inserted as a plain,
non-live `motion.div` with no ARIA role and no `aria-live` attribute (own or inherited),
and focus is never moved to it. A screen-reader user who submits wrong credentials
receives no notification that anything happened; the failure is conveyed visually only.

## Root cause pointer

`frontend/src/app/login/page.tsx:261-268` — the `{error && (<motion.div ...>{error}</motion.div>)}`
block that renders "Invalid email or password." has no `role` or `aria-live` prop, and
nothing in `handleSubmit` moves focus to it or to an `aria-describedby`-linked field on
failure.

## Root cause — analyzer refinement (2026-08-29)

Confirmed by reading `frontend/src/app/login/page.tsx` in full (559 lines).

This card's own line citation above (261-268) is one block off: those lines are actually
the `isExpired` session-expiry banner (see [ISS-574](20260829-0220-ISS-574.md)), not the
failed-login `error` banner this card describes. The `error` block is:

```tsx
{error && (
  <motion.div
    initial={{ opacity: 0, y: -4 }}
    animate={{ opacity: 1, y: 0 }}
    className="mb-5 rounded-[var(--radius-button)] border border-[var(--status-failed-border)] bg-[var(--status-failed-fill)] px-4 py-3 text-sm text-status-failed"
  >
    {error}
  </motion.div>
)}
```
— `frontend/src/app/login/page.tsx:271-279`. The JSX shape and the "no role/aria-live"
finding this card already validated are both correct; only the line numbers needed
correcting.

The mechanism is not a broken shared function — it is hand-rolled inline JSX, and this
exact shape (a conditionally-rendered `motion.div`/`div` styled with `text-status-failed`,
no `role`, no `aria-live`) is duplicated **three** times in this one file, none of them
routed through a shared component. `frontend/src/components/ui/` (`Badge`, `Button`,
`Card`, `CompletionToast`, `ErrorBoundary`, `NotificationPanel`, `Pill`, `Tabs`) has no
generic alert/banner primitive this page could have used. The codebase already knows the
correct pattern elsewhere — `frontend/src/components/settings/SecuritySection.tsx:169` uses
`<div aria-live="polite" className="sr-only">` to announce a toggle's outcome, and
`frontend/src/components/workflow/AgentsPopup.tsx:2659` uses `<span role="alert">` for an
inline validation message — `login/page.tsx` simply never received the same treatment. See
[ISS-574](20260829-0220-ISS-574.md) (the `isExpired` banner) and
[ISS-575](20260829-0220-ISS-575.md) (`ChallengeForm`'s own error banner) for the other two
sites.

## Blast radius (analyzer pass, 2026-08-29)

`frontend/src/app/login/page.tsx` has `imported_by: []` per `MOD-frontend-src-app` — it is a
router leaf, nothing else in the frontend imports this JSX — and `register/page.tsx` renders
no form of its own (redirect-only shim, per the same module card). So the blast radius is
contained to this one file's three duplicate render sites; there is no cross-file "caller"
of a broken shared function to chase:

- **isExpired / session-expiry banner**, lines 261-269 — identical missing
  `role`/`aria-live`. Reached via `handleSessionExpiry()`
  (`frontend/src/lib/api.ts:175-179`, read in full), which does
  `window.location.href = routes.login({ expired: true })` — a full browser navigation, not
  an SPA push, so this banner is present at first paint rather than injected reactively.
  Filed as [ISS-574](20260829-0220-ISS-574.md).
- **`ChallengeForm`'s own error banner**, lines 446-450 — identical missing
  `role`/`aria-live`, and mechanistically IDENTICAL to this card's already-validated flow: a
  `setError(...)` call inside `handleChallengeSubmit` (client-side validation failures like
  "Passwords do not match." or an API failure) triggers a conditional re-render with no
  navigation at all — the exact same silent-to-AT mechanism this card validated for the main
  login form. Filed as [ISS-575](20260829-0220-ISS-575.md).

No tier/theme/viewport dependency — this is a static JSX/ARIA gap, not state- or
style-conditional.

## Fix location

Belongs inside `frontend/src/app/login/page.tsx` itself — not a new `components/ui/`
primitive. Three usages in one file is the "smaller diff in a shared place beats three
separate patches" case, but not enough repetition across files to justify a new
cross-cutting component: the smallest correct diff adds `role="alert"` to all three
existing blocks (lines 261-269, 271-279, 446-450), or factors them through one tiny local
wrapper inside this same file so a fourth banner, if ever added, inherits it too.
`role="alert"` implies `aria-live="assertive"` + `aria-atomic="true"` and is announced on
DOM insertion without requiring explicit focus management, so no `.focus()` calls are
strictly necessary to satisfy WCAG 4.1.3 for the two reactively-injected banners (this
card's `error` block and `ChallengeForm`'s). The `isExpired` banner is the one case worth a
focus-management alternative too, since it can be present at first paint of a
full-navigation load rather than injected after mount — `role="alert"` support for content
already in the DOM at parse time is less consistently announced across screen readers than
for content inserted after mount, and WCAG 4.1.3 offers moving focus as the explicit
alternative for exactly that case.
