## Source

Derived (analyzer pass) from the root-cause investigation of `BUG-20260828-042900-handoff-invalid`,
recorded on [ISS-301](20260828-1740-ISS-301.md). **INFERRED** — not independently reproduced in a
browser; filed from source reading alone (the component's own `refresh()` plus the backend route it
calls). See "What would settle it" below.

## This sibling

`IntegrationsCard.tsx`'s `refresh()` (`:80-93`):

```tsx
const refresh = useCallback(async () => {
  const token = getToken();
  if (!token) return;
  try {
    const [p, ks] = await Promise.all([
      getGithubPatStatus(token),
      listApiKeys(token),
    ]);
    setPatStatus(p);
    setKeys(ks);
  } catch {
    /* dashboard auth already gated this surface */
  }
}, []);
```

is the same `authedJson`-rooted call path ISS-301 traces, one layer up: `getGithubPatStatus`/
`listApiKeys` both route through `api-handoff.ts`'s `authedJson` (`:61-92`), which throws a bare
`Error` for an HTTP failure and lets a network-layer `fetch` rejection propagate unmodified — neither
carries a `status`. `refresh()`'s catch here is EMPTY: on ANY failure — network, 5xx, an aged token —
`patStatus`/`keys` are simply left at whatever they already were, which on first mount is their
declared initial state, `null`/`[]` (`:54`, `:60`).

Confirmed on the backend that "no PAT saved" is never an error in the first place:
`backend/app/api/settings.py:178-201` (`get_github_pat_status`) returns `None` — a normal 200 body,
not a 404/exception — when the `UserGithubCredential` row does not exist (`row is None: return None`
at `:188-189`). So the only way this `catch` fires at all is a genuine failure (network/5xx/stale
token), never the legitimate "nothing saved yet" outcome the inline comment implies it's guarding.

The resulting empty `patStatus`/`keys` state renders as:
- `:253-255` — the amber "No GitHub token saved yet." warning.
- `:335` — "No API keys yet." in the keys list.

Both are indistinguishable from a genuinely new user's screen. A user who HAS a saved PAT and keys,
hitting this component during a network blip, sees "No GitHub token saved yet" — a false negative on
a credential-bearing state, not just a confusing error message.

## Two surfaces, one mechanism

Both mount points share this exact `refresh()` — confirmed via `IntegrationsCard`'s own doc comment
(`:38-44`, "Used in two surfaces"):
- The standalone `/handoff/settings` route (`frontend/src/app/handoff/settings/page.tsx:54`).
- Inline as the onboarding state inside `HandoffWorkflow.tsx` (`:319`, the `showOnboarding` branch) —
  where a false "No GitHub token saved yet" could also mislead a user into re-pasting a PAT that was
  never actually lost.

## Expected vs actual (INFERRED, needs live reproduction)

**Expected:** a network/fetch failure while checking PAT/key status is distinguished from the
legitimate empty case — e.g. an inline "couldn't check your saved credentials, retry" notice — rather
than silently defaulting to "nothing saved."

**Actual (inferred):** any failure of `getGithubPatStatus`/`listApiKeys` is swallowed silently and
renders identically to a brand-new account with no PAT and no keys.

## What would settle it

Reproduce live: sign in as a user with a saved GitHub PAT and at least one API key, intercept
`GET /api/settings/github-pat` and/or `GET /api/settings/api-keys` to fail (Playwright
`route.abort('failed')`), then mount `/handoff/settings` (or a handoff page in the onboarding state)
and confirm it renders "No GitHub token saved yet." / "No API keys yet." despite both existing
server-side.

## Fix

`IntegrationsCard.tsx:80-93` (`refresh`) — the shared mount point for both surfaces. Should not
swallow the error: at minimum surface a retry/error state instead of silently defaulting to the
empty-state copy, and ideally route through the same `ApiError`/`isNotFoundError`-style
discrimination the root fix for ISS-301 introduces at the `authedJson` layer, so a real failure and a
real empty state are never rendered the same way.
