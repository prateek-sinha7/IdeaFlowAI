## Fixed (QA-KB-065, 2026-10-07)

Fixed by [FIX-725](20261007-1830-FIX-725.md), as fix item 1 and Correction 2 below prescribe. In `engine.py:6509-6520`,
an `elif getattr(step, "mechanical", None):` now sits before the `else`. It yields the step's `agent_error`
(`recoverable: False`) and raises `StepRaised`, so the run ends with one `pipeline_failed` naming the step and the
kind, and no model runs. The `plan.py` comments that called `"publish"` the only value were refreshed (fix item 4).
ADR-0045's recipe is restated in the fix card. Not done: the table refactor (the red test's parity regex reads the
literal chain) and failing before the pre-step gates (optional hardening). The siblings
[ISS-1004](20261002-0522-ISS-1004.md) and [ISS-1005](20261002-0522-ISS-1005.md) stay open: they have no test, and this
guard cures neither. The test shows XPASS(strict). Awaiting the 6-verifier.

## The symptom

You add a third code step. It compiles. It shows up in the composer's *Code step*
dropdown with its description. You run it. The step "runs", bills tokens, and
produces narration instead of the deterministic output you wrote. No compile
error, no engine error, nothing in the logs naming the problem.

## The root cause

`engine.py:5977-5990` selects the mechanical adapter from a hand-written if/elif
over two literal strings:

```python
if getattr(step, "mechanical", None) == "publish":
    strategy = MechanicalPublishStrategy(...)
elif getattr(step, "mechanical", None) == "assemble_prototype":
    strategy = MechanicalAssembleStrategy(...)
else:
    strategy = _registry.resolve("strategy", strategy_name)
```

The `else` is the trap. `strategy_name` came from
`getattr(step, "strategy", "single_shot")` at `engine.py:5804`, and
`Step.strategy` defaults to `"single_shot"` (`plan.py:435`). A mechanical step
serialises with no prompt and no tools (the composer returns early at
`userWorkflows.ts:305-308`), so the fall-through resolves `single_shot` and runs
an LLM against an empty prompt.

## Why nothing catches it

The *other* two parity surfaces are both pinned:

- `test_compiler.py:576-593` asserts
  `compiler._ALLOWED_MECHANICAL_KINDS == {name for kind, name in registry._KNOWN if kind == "mechanical"}`.
- `test_registry_capabilities.py:168` asserts `set(_KNOWN) == set(_EXPECTED_NAMES)`.

So registering a kind and forgetting the compiler set, or the expected-names
list, fails loudly. That is exactly what makes the engine gap dangerous: the
author gets a green run from the surfaces that *are* covered and reasonably
concludes the wiring is done.

Nothing asserts the engine side. Checking every test file that mentions
`mechanical`: `test_registry_capabilities.py:72-73` pins the enumeration,
`test_allowed_step_keys.py:61-62` pins the step key,
`test_mechanical_router.py` is the unrelated chat-intent router, and
`test_assemble_step.py` / `test_mechanical_publish_step.py` exercise the two
adapters directly — never the engine's *selection* of them.

Introduced by `a692982df`, when the second kind (`assemble_prototype`) was added
by copying the shape of the first rather than generalising it.

## The fix

Two parts, both small:

1. Replace the `else` with an explicit guard — if `step.mechanical` is truthy and
   matched no branch, raise naming the kind, instead of falling through to
   strategy resolution.
2. Add a parity test mirroring `test_compiler.py:576`: every
   `("mechanical", name)` in `registry._KNOWN` must have an engine dispatch
   branch.

ADR-0045 is the card that describes the whole recipe for adding a code step; this
is its step 4, and the only step in that recipe whose omission is silent.

Today nothing can reach the `else` with a code step. A probe printed the same four kinds from all three declarations and an empty difference in every direction:

| declaration | kinds |
|---|---|
| registry, `@register("mechanical", ...)` after `discover()` | assemble_backlog, assemble_prototype, extract_prototype_ui, publish |
| `compiler._ALLOWED_MECHANICAL_KINDS` (`compiler.py:206-208`) | the same four |
| engine literals `getattr(step, "mechanical", None) == "<kind>"` (`engine.py:6446`, `:6457`, `:6471`, `:6484`) | the same four |

That is why the first report of this card, QA-KB-023, ended UNREPRODUCIBLE: its claim that assemble_backlog and extract_prototype_ui have no engine branch is stale. It left the hardening itself open, and this report is that hardening. The day a fifth kind is registered and allowed, the engine runs it as a model step. The set grew from one kind to four in four weeks, each time by hand-editing the chain (publish, `1e329e47b`, 2026-09-04; assemble_prototype, `a692982df`, 2026-09-10; assemble_backlog and extract_prototype_ui together, `756f9bd8e`, 2026-09-29), and the next one is the one nothing checks.

### Root cause, with current lines (CONFIRMED)

- `engine.py:6446-6498`: an if/elif over four literals, then

  ```python
  else:
      strategy = _registry.resolve("strategy", strategy_name)
  ```

  The `else` has no `step.mechanical` check.
- `strategy_name` is the step's own strategy or the default (`engine.py:6267-6269`). `Step.strategy` defaults to `"single_shot"` (`plan.py:468`) and the compiler fills `raw.get("strategy", "single_shot")` for a code step too (`compiler.py:901`).
- `SingleShotStrategy.run` calls `ctx.runner.run_agent(step, ctx)` unconditionally (`single_shot.py:60`), and nothing on the agent path reads `step.mechanical`, so the step runs its agent once, with a model.
- "Empty prompt" is exact for every code step in the repo. All are `agent: custom-agent` with no `prompt` (`backlog/workflow.yaml:90-94`, `ex_publish_step/workflow.yaml:49-54`, the composer's `userWorkflows.ts:307-312`), so the blank custom agent runs against the run's user message.

### Corrections to this card and to the BUGS.md framing

1. **Lines and kind count.** The chain is `engine.py:6446-6498` with four branches (this card says `:5977-5990` and two). The registry drift guard is `test_registry_capabilities.py:222`, not `:168`, and its expected list names all four kinds (`:82-85`). [ADR-0045](20260918-ADR-0045.md)'s recipe step 4 and its pointer "recorded as ISS-646" are stale: the id of this card is ISS-684, and ISS-646 is an unrelated card.
2. **The triage sketch's bare `raise ValueError` is not "a single pipeline failure".** The chain sits inside `_execute_impl`'s `try` (`engine.py:6193`). Its handlers are CancelledError, BudgetExceeded, `(AssembleStepFailed, AssembleBacklogFailed)`, FanoutWorkerFailed and `StepRaised` (`:7449-7594`); there is no `except Exception`. `_guarded_step` (`:14321-14348`) turns a strategy's exception into `agent_error` plus `StepRaised`, but it wraps only `strategy.run` (`:6503`), which is after selection, so a raise at selection skips it. The exception leaves through the `finally` (`:7595`, which marks the run failed because the in-flight exception is an `Exception`, `:7638-7639`) and `execute()`'s observe-and-reraise (`:4243-4259`), and lands in the REST driver's defensive handler (`run_commands.py:4433-4461`): one generic `error` event, "Pipeline execution failed: ...", flagged `recoverable: True`, with no step id and no `pipeline_failed`. The run does fail, but through the crash path.
   The fix has to reach `StepRaised` (one `pipeline_failed` with `agents_failed: [step id]`, `:7575-7594`). Two ways: `yield` an `agent_error` (`recoverable: False`) and `raise StepRaised(spec.id, msg)` at the guard; or hand `_guarded_step` a strategy whose `run()` raises, which then logs at ERROR with the step id, emits the `agent_error` and raises `StepRaised` for you. `StepRaised` lives in `engine.py`, so the guard stays in the engine: `agents.capabilities` may not import the kernel (`backend/pyproject.toml:389-393`).
3. **Where it fails matters.** A guard at the chain fails at step N, after steps 1 to N-1 have billed and after the step's pre-step gates ran (a human could be asked to review a step that then errors). A pre-flight over `compiled.steps` before the first dispatch, or moving the selection above the pre-step gates, fails with zero spend. This is optional hardening; [ISS-1004](20261002-0522-ISS-1004.md) gives a second reason for the reorder.
4. **The composer is a live entry point.** `AgentsPopup.tsx:1678-1682` offers every `@register("mechanical", ..., user_allowed=True)` kind in the Code step dropdown, with no engine check, so the day a kind is registered a user can pick it and run it.

### Blast radius (grepped)

- **One dispatch site, every driver.** The chain is the only place that selects a mechanical adapter, and every run goes through `_execute_impl`: the REST/SSE launch driver (`run_commands.py:4242`), panel revision (`engine.py:13383`, via `execute`), the NDJSON adapter (`ndjson_adapter.py:64`) and every resume driver (`_execute_impl` at `engine.py:15898`). One guard covers all of them; no per-caller guard.
- **Other consumers of `step.mechanical`:** `engine.py:15304` (`complete_mechanical`, resume completeness: an `agent_complete` marks a code step done, so a billed fall-through also counts as complete) and the compiler (`compiler.py:915-927`, `:1187`). `registry.resolve("strategy", ...)` is called at only two engine sites: the `else` (`:6498`) and the `runs_agent_inline` read (`:11495`, see [ISS-1004](20261002-0522-ISS-1004.md)).
- **The declarations of the kind set**, which must agree: the `@register` per kind (the `_KNOWN` literal at `registry.py:223-227` still lists only two; the other two arrive at `discover()`), `compiler.py:206-208`, the engine chain, and `_EXPECTED_NAMES` (`test_registry_capabilities.py:82-85`). Pinned by a test: registry against compiler (`test_compiler.py:576-593`) and the registry list (`:222`). Pinned by nothing: the engine chain. Engine-level coverage of the chain exists for `publish` only (`test_mechanical_publish_step.py:265-301`, the `ex_publish_step` fixture); the other three kinds are tested through their adapters directly.
- **Frontend:** nothing hardcodes the kinds (the palette is live from `/api/capabilities`); `FRIENDLY_NAMES` degrades to `humanize()`.

### The fix, and where it belongs

Every caller shares the one chain, so the fix is one place: `backend/agents/execution_engine/engine.py`.

1. Replace the `else` with a guard for a code step the chain does not know: if `getattr(step, "mechanical", None)` is truthy, end the run through `StepRaised` as in Correction 2, naming the step and the kind (for example "Code step kind 'x' has no engine dispatch branch"); otherwise resolve the strategy as today. The four handled kinds and every non-mechanical step stay byte-identical (INV-3).
2. Optional, and recommended: collapse the four identical constructions into one table (kind to adapter class, with `spec`, `index`, `total` and `results` passed once). It makes "which kinds the engine handles" a set a test can read instead of source text. `publish_step` and `prototype_ui_extract` are imported lazily today (`assemble_step` and `backlog_assemble` are already imported at the top for their exception classes, `engine.py:90-93`); keep them lazy, a callable per entry, unless an import check shows no cycle.
3. Tests: see "For the test-writer".
4. When it closes, refresh what misleads the next author: `plan.py:469-475` and `:488` (they say `"publish"` is the only value), `engine.py:6438-6445`, and ADR-0045's recipe (supersede it or restate it in the fix card).

A structural alternative exists and is NOT part of this fix: register each adapter in the registry, have the engine `resolve("mechanical", kind)` and the compiler `is_registered` plus `_check_trust` against the same registry, so a kind is declared once and the compiler frozenset, the chain and the parity test all disappear. It also closes [ISS-1005](20261002-0522-ISS-1005.md). It contradicts ADR-0045's locked constraints (the registered class is a never-executed stub, and dispatch is the explicit chain), so it needs a decision and a superseding ADR first. The compiler cannot read the engine's table (`agents.workflows` may not import `agents.execution_engine`, `backend/pyproject.toml:383-387`); the neutral ground is the registry, or a test.
