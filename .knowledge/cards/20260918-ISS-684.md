## The symptom

You add a third code step. It compiles. It shows up in the composer's *Code step*
dropdown with its description. You run it. The step "runs", bills tokens, and
produces narration instead of the deterministic output you wrote. No compile
error, no engine error, nothing in the logs naming the problem.

## The root cause

`engine.py:5977-5990` selects the mechanical adapter from a hand-written if/elif
over two literal strings:

```python
if getattr(step, "mechanical", None) == "publish":
    strategy = MechanicalPublishStrategy(...)
elif getattr(step, "mechanical", None) == "assemble_prototype":
    strategy = MechanicalAssembleStrategy(...)
else:
    strategy = _registry.resolve("strategy", strategy_name)
```

The `else` is the trap. `strategy_name` came from
`getattr(step, "strategy", "single_shot")` at `engine.py:5804`, and
`Step.strategy` defaults to `"single_shot"` (`plan.py:435`). A mechanical step
serialises with no prompt and no tools (the composer returns early at
`userWorkflows.ts:305-308`), so the fall-through resolves `single_shot` and runs
an LLM against an empty prompt.

## Why nothing catches it

The *other* two parity surfaces are both pinned:

- `test_compiler.py:576-593` asserts
  `compiler._ALLOWED_MECHANICAL_KINDS == {name for kind, name in registry._KNOWN if kind == "mechanical"}`.
- `test_registry_capabilities.py:168` asserts `set(_KNOWN) == set(_EXPECTED_NAMES)`.

So registering a kind and forgetting the compiler set, or the expected-names
list, fails loudly. That is exactly what makes the engine gap dangerous: the
author gets a green run from the surfaces that *are* covered and reasonably
concludes the wiring is done.

Nothing asserts the engine side. Checking every test file that mentions
`mechanical`: `test_registry_capabilities.py:72-73` pins the enumeration,
`test_allowed_step_keys.py:61-62` pins the step key,
`test_mechanical_router.py` is the unrelated chat-intent router, and
`test_assemble_step.py` / `test_mechanical_publish_step.py` exercise the two
adapters directly — never the engine's *selection* of them.

Introduced by `a692982df`, when the second kind (`assemble_prototype`) was added
by copying the shape of the first rather than generalising it.

## The fix

Two parts, both small:

1. Replace the `else` with an explicit guard — if `step.mechanical` is truthy and
   matched no branch, raise naming the kind, instead of falling through to
   strategy resolution.
2. Add a parity test mirroring `test_compiler.py:576`: every
   `("mechanical", name)` in `registry._KNOWN` must have an engine dispatch
   branch.

ADR-0045 is the card that describes the whole recipe for adding a code step; this
is its step 4, and the only step in that recipe whose omission is silent.
