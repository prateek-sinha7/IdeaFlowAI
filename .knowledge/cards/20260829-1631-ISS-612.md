# ISS-612

**BUG-ID:** BUG-20260829-140111-runs-id-steps-agent (sibling, derived by analysis — NOT independently reproduced this pass)

**Confidence: INFERRED** for the user-visible generalization (not yet re-driven through a live
browser on a card kind other than "Revision started"). The underlying claim — that `anchor` is
parsed and then read nowhere — is CONFIRMED by an exhaustive grep, not a sample.

## Generalizes ISS-607's defect #2 beyond "Revision started"

ISS-607 root cause #2 found `ResultCard.tsx`'s `onClick={() => onRequestOpenTab(tab)}` (lines
164, 175, 207) passes only a generic tab id — no run id — for the specific "Revision started"
card it reproduced. Tracing the seam further shows this is not a gap specific to that one card
kind; it is the ENTIRE mechanism's design, and the run-id data it is missing already exists on
the message object, unread.

## Root cause (traced by code reading)

1. **The backend already emits a run reference on every milestone.** `_classify`
   (`backend/app/agents/chat_narrator.py:141-217`) sets `deep_link_target` to `f"run:{anchor}"`
   (or `clarify:`/`gate:`/`deliverable:`/`spec_revision:` — always `<kind>:<id>` shaped) for
   EVERY one of `CARD_CLARIFY`, `CARD_GATE`, `CARD_PIPELINE`, `CARD_DELIVERABLE`,
   `CARD_SPEC_REVISION` — e.g. line 210 (`"Revision started"`, the case ISS-607 exercised),
   but identically line 201 (`pipeline_complete` → deliverable), 211 (plain `pipeline_start`),
   213/215 (`pipeline_failed`/`pipeline_cancelled`), 169 (clarify), 173 (gate). `anchor` at
   line 149 is `run_id or "run"`, and `run_id` (`_run_id`, line 97-98) is the EVENT's own
   `pipeline_run_id`/`run_id` — for a revision's `pipeline_start`, that is the **revision's own,
   different** run id, not the run whose chat lane is currently mounted.

2. **The frontend parses that reference in full and stores it — `frontend/src/hooks/
   useRunChat.ts:280-299`, `parseDeepLink`:**
   ```
   293    const anchor = typeof r.target === "string" && r.target ? r.target : undefined;
   294    const tab = typeof r.tab === "string" && r.tab ? r.tab : undefined;
   ...
   298    ...(tab ? { tab } : {}),
   299    ...(anchor ? { anchor } : {}),
   ```
   `DeepLinkTarget.anchor` (`frontend/src/types/index.ts:75-90`) is typed and documented for
   exactly this: `"The narrator's milestone/artifact ANCHOR ... run:<id> / ... A semantic
   reference to WHAT the card reports"`.

3. **Nothing reads it.** `grep -rn "\.anchor\b" frontend/src/` (excluding tests) returns **zero
   matches** anywhere in application code. `ResultCard.tsx`'s `onRequestOpenTab: (tab: string) =>
   void` (line 97) has no parameter for it; `useTabDeepLink.ts`'s `requestOpenTab: (tab: string,
   agentId?: string) => void` (lines 45, 63-67) and its consumer effect
   (`PreviewPanel.tsx:833-845`, `setActiveTab(tab)` only) have no run-switching branch at all —
   the whole seam is scoped, by design (its own doc comment,
   `frontend/src/hooks/useTabDeepLink.ts:6-23`), to switching tabs WITHIN the currently-mounted
   run only ("A result card ... calls `requestOpenTab(tab)`; the Preview panel ... calls
   `setActiveTab`").

## Why this is broader than the "Revision started" case ISS-607 tested

Any narrator card whose `anchor`'s run id differs from `contentSourceRunId` (the currently
mounted run) hits the identical no-op, not just `pipeline_start` on a `*_revision` pipeline:
- A `deliverable` card ("Delivered — open in Preview →") for a **revision's own completion**,
  shown in the shared family chat transcript (`FIX-167`: `seedRunChatTranscript` fetches
  sibling/child revision runs via `getRunFamily`) while the root's base Steps/Preview route is
  still mounted — same missing-run-id defect, different `cardKind` (`deliverable` instead of
  `clarify`).
- `pipeline_complete`/`pipeline_failed`/`pipeline_cancelled` cards for the same reason, whenever
  they narrate a family member other than the one currently on screen.

`gate`/plain `clarify` cards are NOT implicated the same way — a gate/clarify pause happens on
the run currently being driven, so `anchor` there ordinarily already equals the mounted run;
listed here for completeness, not as part of this defect.

## Expected vs Actual (inferred beyond the one reproduced card kind)

**Expected:** any "Open in Steps/Preview" chat link whose milestone belongs to a sibling/child
run in the family navigates to that run's own content, not just switches tabs in place.

**Actual (inferred):** identical to ISS-607's "Revision started" reproduction — silent no-op —
for every other narrator card kind whose `anchor` names a different run than the one mounted,
because the run-id data the backend already sends is discarded at `parseDeepLink` read-time
(stored) but never consumed downstream.

## Fix direction

The single write-side chokepoint is `useTabDeepLink.requestOpenTab` (currently `(tab, agentId?)
=> void`) plus its one caller `ResultCard.tsx`'s `onClick` handlers — extend the signature to
carry the parsed `anchor`/run id through to `page.tsx`'s one consumer of `requestOpenTab`
(`frontend/src/app/[...view]/page.tsx:3933`), which already has everything needed to perform the
same kind of pin-and-navigate `handlePreviewPanelTabSelect` does for the version picker (ISS-607)
— reuse that, don't duplicate route-building logic in a second place.

## Evidence

`grep -rn "\.anchor\b" frontend/src/` (zero matches, confirmed this pass) plus every file:line
quoted above, all read directly. No new browser reproduction of a non-"Revision started" card
kind this pass.
