# ISS-1077

## Description

**INFERRED sibling of [ISS-745](20260922-1400-ISS-745.md) (register bug QA-KB-055). Every read below is CONFIRMED; the
end-to-end outcome (a wrongly parented revision row) is derived and not reproduced: the analysis was static and no run
was launched.**

ISS-745 shows that `setContentSourceRunId(completingRunId)` (`page.tsx:1629-1630`) can move `contentSourceRunId` to a run
in another family while the user is looking at the first one. `contentSourceRunId` is not only a display value; it is the
only input several write paths use to decide WHICH RUN TO ACT ON, and each reads it at click time:

| Where | What it does with it |
|---|---|
| `DashboardLayout.tsx:1203` (`handleRevisePpt`) | `postRevision(token, contentSourceRunId, { target_artifact_type: "ppt_output", ... })` |
| `DashboardLayout.tsx:1286`, `:1306`, `:1325` (custom, prototype_v2, backlog revise) | `postRevision(token, contentSourceRunId, ...)` |
| `DashboardLayout.tsx:1241`, `:1261`, `:1273` (user-stories, prototype, app_builder revise) | `onStartPipeline("..._revision", ..., { source_workflow_run_id: contentSourceRunId })` |
| `DashboardLayout.tsx:1922-1926` (`handleChainPipeline`) | `sourceRunId = contentSourceRunId ?? ...`, stored as `CHAIN_SOURCE_RUN_ID_KEY` for the chained launch. Its own comment states the invariant the hijack breaks: contentSourceRunId "always points at the run the user is CURRENTLY viewing". |

The server then trusts the id it is given. `create_revision` (`backend/app/api/run_commands.py:5550-5562`) resolves the
parent by id AND owner and nothing else (no check that it is the run the caller was looking at, none that the target type
fits it); `_mint_revision_row` (`:4672-4687`) writes the child with `parent_run_id=parent_run_id` and
`source_run_id=parent_run_id`, `status="revising"`. The family concurrency guard is keyed on that parent's family
(`:4610`), so the 409 "revision already in progress" check runs against the wrong family too.

### This has already happened once, and its only mitigation has since been removed

[FIX-173](20260805-1853-FIX-173.md) (Bug 1, 2026-08-04) records the live occurrence: with PPT and prototype revisions
running at once, `contentSourceRunId` "could transiently point to a prototype run when a PPT revision's `postRevision` was
called", so the new child was parented under the wrong family and appeared in the PPT version dropdown (7 entries
instead of 3). FIX-173 masked it on the read side with a base-type filter in `_owned_family_members`.

`backend/app/api/runs.py:1640-1665` now says that mask is gone and why: it "could not do the job it was written for"
because the corrupted row has `parent_run_id` AND `source_run_id` both written from the same wrong value, and it rejected
legitimate cross-type revisions and diverts. The docstring ends: "Contamination must be prevented where it is created, by
not writing a parent link from a transient id, not by filtering reads. Until that write-path hardening exists, a
cross-type child is admitted and logged". That hardening is not carded anywhere in `INDEX.md` (grepped for
`postRevision`, `wrong parent`, `transient`, `write-path hardening`, `cross-family`: only BUG-003-sse and FIX-170 match,
and neither is about this).

## Why the root cause implies this

The root cause (ISS-745) is a single piece of state, `contentSourceRunId`, that a background completion can move out
from under the user. Every consumer that reads it later inherits the move. The display consumers (family chip, header,
tab routes at `DashboardLayout.tsx:534-539`) show a wrong screen; these write consumers persist the error, and since the
read mask is gone nothing downstream will flag or hide it.

Fixing ISS-745 removes the usual trigger but not the exposure: the id is still read from mutable state at click time, so
any other way it goes stale (a completion arriving between the user typing a revise instruction and pressing send; a
future writer of `setContentSourceRunId`) reproduces it.

## Conditions

A user on family B's run detail; a revision launched earlier in the same tab on family A completes (ISS-745's trigger);
the user then revises or chains from what is on screen. The race variant needs no wrong screen: the completion lands
after the user began a revise instruction on B and before they press send.

## Expected vs actual

Expected: a revise or chain action's parent is the run the user is acting on (the run id in the URL / the viewed run), or
the action refuses when the viewed run and the parent it is about to send disagree.
Actual: the parent is whatever `contentSourceRunId` holds at click time; `create_revision` accepts any owned run.

## What would settle it (INFERRED until then)

A component test that mounts `DashboardLayout` with `contentSourceRunId` = A while the route names B, invokes a revise
handler, and asserts what `postRevision` receives. DashboardLayout is mountable (it has its own `*.test.tsx` files);
`page.tsx` is not. Backend side: a test that `POST /api/runs/{other_family_run}/revisions` succeeds today, which is the
documented behaviour and shows the server cannot catch it, so the guard has to be on the client or in the request
contract.

## Fix direction (not applied, issue only)

Frontend-only and in one place: derive the parent for the revise/chain handlers from the route-parsed run id
(`reopenedRunIdFor(parsedView)` / `parsedView` in `page.tsx`, already the source of truth for T7/T11) rather than from
mutable state, or compare the two and refuse on mismatch. Adding a request field the server validates (an expected family
root) would be an API-contract change, which is a product decision, not an analyzer call. Do not re-add a read-path type
filter in `_owned_family_members`: its docstring explains why it cannot work.

## Fixer note — escalated, not fixed (2026-10-07)

Left open. QA-KB-055 is ESCALATED on this card alone (`ESCALATIONS.md#qa-kb-055`). [FIX-752](20261007-2214-FIX-752.md)
fixed ISS-745 and ISS-1074 at their source. The only background writer of `contentSourceRunId` (the
`pipeline_complete` set) is now family-gated, so the trigger this card depends on is gone. Every remaining writer is
navigation or launch (`page.tsx:2801`, `:2940`, `:2980`, `:3528`, `:3623`, `:4307` at HEAD `e93aa40ed`).

What the analysis missed, and why a fixer cannot settle it:

- The test written for this card contradicts an existing one. `foreignRevisionHijack.qaKb055.source.test.ts:47-49`
  asserts `DashboardLayout.tsx` does NOT contain `postRevision(getToken() ?? "", contentSourceRunId,`.
  `revisionFamilyLinkage.source.test.ts:28` asserts it DOES. That test pins Revision Families B1, whose contract is
  the `DashboardLayout.tsx` prop note "Every revision launch path sources parent linkage from this". No code satisfies
  both.
- "Derive the parent from the route-parsed run id" conflicts with FIX-088's same-family advance, which FIX-752 keeps.
  Opening an older member, then letting a same-family revision finish, moves `contentSourceRunId` to the revision while
  the URL keeps naming the older member. A route-derived parent would revise the older member, not the content on
  screen.
- "Refuse on mismatch" is a new UX surface. A server-validated expected root is an API-contract change, which this
  card already called a product decision.

## Resolution (2026-10-09)

The owner chose option a (ESCALATIONS.md#qa-kb-055): keep the Revision Families B1 pin. The ISS-1077 case in `foreignRevisionHijack.qaKb055.source.test.ts` is retired, and this card is resolved as covered by FIX-752, which removed the completion-time trigger. Accepted consequence: there is no defence in depth against a future background writer of `contentSourceRunId`.
