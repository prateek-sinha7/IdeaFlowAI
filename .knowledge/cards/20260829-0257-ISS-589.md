## What happened

Sibling defect derived while analyzing `BUG-20260828-082706-runs-id-files` (root card
[ISS-351](20260828-2103-ISS-351.md)) — found by grepping every other `.length`-as-bytes site in
the frontend, NOT by live browser reproduction. **INFERRED**: the mechanism is confirmed by
reading the source below, but nobody has yet reproduced the user-visible symptom in a running
browser. What would settle it: upload/fetch an HTML custom template whose UTF-8 byte size sits
near or over 2 MB but whose character count is under it (e.g. a template dense with em dashes,
curly quotes, or non-Latin text), and check both (a) whether the "File is too large" gate fires
correctly and (b) whether the "Loaded X KB" / "Fetched X KB" label matches `wc -c` on the same
content.

## Root cause

Same mechanism as [ISS-351](20260828-2103-ISS-351.md): `String.prototype.length` counts UTF-16
code units, not UTF-8 bytes. `CustomTemplateModal.tsx` uses `htmlBody.length` for TWO distinct
purposes, both wrong:

- **Line 80** (`handleFileChange`, size-cap gate): `if (text.length > 2 * 1024 * 1024) { setFileError("File is too large (max 2 MB)."); return; }` — `text` is the string `FileReader.readAsText(file)` decoded. Since a UTF-16 code unit count is always ≤ the UTF-8 byte count for any content containing non-ASCII characters, this check UNDER-counts size and can WRONGLY ACCEPT a file whose true byte size exceeds 2 MB — this is a validation bypass, not just a cosmetic mislabel. The real byte size is already sitting unused on `file.size` (the `File` object at line 67) at the point this check runs; the code decodes to text first and checks the decoded string instead of the object it already has.
- **Line 232**: `Loaded {(htmlBody.length / 1024).toFixed(1)} KB` (file-upload success message).
- **Line 267**: `Fetched {(htmlBody.length / 1024).toFixed(1)} KB from {new URL(urlInput).hostname}` (URL-fetch success message, `htmlBody` here comes from `data.html` at line 113 — a backend-proxied fetch response with no `File` object behind it at all, so this site cannot fall back to a `.size` property the way line 80 could).

`formatSize`/`formatBytes`-style helpers are not used here at all — this is inline
`.length / 1024` arithmetic, an independent occurrence of the identical mistake ISS-351 found in
`FilesTab.tsx`'s `formatSize()` callers, not a shared function both files call into.

## Expected vs actual

- **Expected:** the 2 MB cap is enforced against the file's real byte size (`file.size` for the
  upload path; a UTF-8 byte computation of the fetched string for the URL path), and the
  "Loaded/Fetched X KB" labels match what `wc -c` reports on the same content.
- **Actual:** both the cap check and the two display labels are computed from
  `String.prototype.length` (UTF-16 code units) — a file/URL response with multi-byte UTF-8
  content will read smaller than it truly is, understating the label and, for the cap check,
  potentially admitting an over-cap file.
