# ISS-1095

Sibling of [ISS-1073](20261007-2135-ISS-1073.md) (QA-KB-096), filed by its analysis on 2026-10-07. **INFERRED.** The mechanism is read in source and was
rendered offline against the real components (`evidence/qa-kb-096/13` to `15`, probes D and H). Nobody has driven a browser to a pinned Backlog version.
An unreproduced sibling is a lead, not a defect.

## Condition

A completed, tagged member of a family whose deliverable is a binary (today only `backlog`: `Backlog.pdf`, `application/pdf`), viewed PINNED: the
`/runs/<root>/versions/N` URL, or a pick in the Version menu. Real data: family `78e185fb-c032-4154-8552-774781b6e5df`, versions 1 to 5 and 7.

## Why the root cause implies it

[ISS-1073](20261007-2135-ISS-1073.md)'s root cause is that the UN-pinned preview asks a tag for the declared path. A pinned version takes the OTHER preview
branch, and that branch was never taught about binaries. Fixing `SandboxPdfPreview` alone leaves every pinned version as it is now.

## Mechanism (read, then rendered)

- With `sandboxSelectedRef` set the Preview tab renders `RefVersionPreview` instead of `renderDeliverable()` (`PreviewPanel.tsx:1835-1852`).
- Its bytes come from the effect at `:1518-1532`: `getRunSandboxFile(token, activeRunId, deliverableFile, sandboxSelectedRef)`, the TEXT reader
  (`api.ts:1666-1679`, `res.text()`). `deliverableFile` is right: it is the header's ref-aware resolve (`.chain/Backlog.pdf` at v2). The read decodes a
  23 MB PDF as UTF-8.
- The text goes to `GenericDeliverablePreview` with no `runId` (`:390-393`), so the PDF branch (`:227`, `mimetype === "application/pdf" && runId &&
  deliverable.filename`) is skipped. The mimetype is `application/pdf`, so the html, markdown and zip branches do not match either, and the last block
  renders: "Deliverable ready ... This deliverable (application/pdf) can be downloaded from the Files tab." plus a "Download Backlog.pdf" button
  (`:301-329`).
- That button saves `new Blob([content], { type: ... })` (`:314`): the UTF-8-decoded text re-encoded, not the PDF's bytes. INFERRED from the code; not clicked.
- Pinned v1, the validator's run: the tag holds no PDF at all ([ISS-1073](20261007-2135-ISS-1073.md)), so the header resolve is null, `deliverableFile` stays
  null, the ref read at `:1520` never starts, `content` stays null and `RefVersionPreview` prints "Loading v1..." (`:385-388`). That is
  [ISS-677](20260917-1449-ISS-677.md)'s mechanism (open), reachable for run 78e185fb through the Version menu or `/versions/1`.
- The pinned URL also fires ISS-1073's request while the pin loads. Before `viewingVersion` arrives, `activeRunId` is the root and `displayRef` is `v1`
  (`PreviewPanel.tsx:890-891`), so `GET /sandbox/file?path=Backlog.pdf&ref=v1` goes out (404) beside the real read.

## Offline render (evidence 15, probes D and H)

The real PreviewPanel, RunHeader and api.ts over a faked network that serves the recorded listings.

- D, pinned v2 (`pinnedVersion="2"`): the requests are `sandbox/file?path=Backlog.pdf&ref=v1` (the root run, 404) and
  `sandbox/file?path=.chain%2FBacklog.pdf&ref=v2` (the text read). The PDF frame is absent. The card reads "This deliverable (application/pdf) can be
  downloaded from the Files tab." and the button reads "Download Backlog.pdf".
- H, pinned v1: after 700 ms the panel still shows "Loading v1...", no Deliverable card, header Download disabled.

## Expected vs actual

Expected: a pinned older version previews that version's own PDF in the PDF viewer, as the newest member's page does, and a pinned version whose tag holds
no PDF says so.
Actual: a "Deliverable ready" card whose copy points at a hidden tab ([ISS-1097](20261007-2347-ISS-1097.md)), and a download that is not the PDF; pinned v1
never leaves "Loading".

## Fix direction

Send the pinned branch through the component the un-pinned one uses. For a binary mimetype `RefVersionPreview` renders `SandboxPdfPreview` with
`runId={activeRunId}` and `selectedRef={sandboxSelectedRef}`, and the text read at `:1518` is skipped for it (no 23 MB `res.text()`). Once
[ISS-1073](20261007-2135-ISS-1073.md)'s fix is in, that component resolves the path and handles "absent at the ref" itself, which also gives pinned v1 an
honest end state. The "Loading forever" half stays [ISS-677](20260917-1449-ISS-677.md)'s.

## What would settle it

Open `/runs/78e185fb-c032-4154-8552-774781b6e5df/versions/2` cold: expect the "Deliverable ready" card instead of the PDF, and the file saved from it to
differ from `.chain/Backlog.pdf` at v2 (23,010,668 B). Then `/versions/1`: expect "Loading v1..." to persist. Test seam: probes D and H in evidence 13 mount the
real panel with `pinnedVersion`.
