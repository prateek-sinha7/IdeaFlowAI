## What was wrong

On a cold load of a completed run's detail page, the left-lane header meta row
(`data-testid="lane-run-meta"`) read `just now · 18m 54s · 3.1M tokens` for run
`b9feac1c-ec21-4531-8ba7-bb391786993e`, whose `created_at` is
`2026-08-27T13:48:45Z` — 11 hours old when first reported, over a day old at
validation. In the SAME header row the version picker computed the correct age
(`Version v1 · 1d ago`) for the identical run. Duration and token count beside
the frozen label were each correct against `GET /api/runs/{id}`; only the
relative-time segment was wrong. Validated 3/3 from cold entry, no axis
variation ([ISS-276](20260828-1700-ISS-276.md),
`BUG-20260828-011700-runs-id`).

## Root cause

`frontend/src/hooks/useWorkflow.ts:511` (pre-change):

```ts
createdAt: (msg.created_at as string) || prev.createdAt || new Date().toISOString(),
```

That reducer is the single writer of `PipelineRunState.createdAt`, and it is
fed by TWO transports: the live SSE stream, and the durable REST replay
(`frontend/src/app/[...view]/page.tsx:2599-2610` — `getRunEvents` → each frame
back through `handleWebSocketMessage` → the same reducer). The two frames are
byte-identical on the wire, so the reducer cannot tell a live start from the
replay of a day-old one.

The backend never put a timestamp on the frame:
`backend/agents/execution_engine/engine.py:2346-2363` (pre-change) emitted
`pipeline_start` with `pipeline_type`, `pipeline_run_id`, `agent_count`,
`agents` and `resume_offset` and nothing else, and
`GET /api/runs/{id}/events` (`backend/app/api/runs.py:1042-1092`) returns only
`seq`, `event_id`, `type`, `payload_json` — the `run_events.created_at` column
is never surfaced. So on a cold load of a settled run, `prev.createdAt` is
undefined (fresh per-run state) and `msg.created_at` is absent, and the
fallback stamped the client's wall clock at hydration time.

`frontend/src/components/chat/LaneRunHeader.tsx:257` then computes
`formatRelativeAge(pipelineState?.createdAt)` on the settled branch, always
sees an elapsed under 45s, and returns `"just now"`. The formatter itself
(`:42-58`) is correct. The version picker
(`frontend/src/components/preview/RunHeader.tsx:156`) calls the SAME helper
with `member.created_at` from the DB-backed `getRunFamily` endpoint, never
touching this reducer — which is exactly why the two labels disagreed.

Blast radius re-confirmed by grep before editing and still holds:
`pipelineState.createdAt` is written in exactly one place
(`useWorkflow.ts:511`) and read in exactly one place
(`LaneRunHeader.tsx:257`); `LaneRunHeader` mounts once
(`RunChatLane.tsx:2144`). The component is workflow-agnostic, so every
completed run of every workflow type hit this on every cold load. The other
`createdAt` assignments in `page.tsx` (`:1537,1623,1800,1853`) are `ChatMessage`
objects, a different field on a different type.

## What changed and why there

**`backend/agents/execution_engine/engine.py`** — the sole production emitter of
`pipeline_start` (grep: no other `"pipeline_start"` producer in `backend/`) now
reads the run's real `created_at` via `scoped_store.get_run(pipeline_run_id)`
and stamps it on the frame's `data`. UTC-promoted before `isoformat()` — the
same KAN-113 promotion `runs.py`'s `_serialize_dt` does, because a naive stamp
is `Date.parse`'d as LOCAL time in the browser and produces the wrong "Nh ago",
which is the very class of defect being fixed. The read is best-effort with a
`logger.warning` degrade, matching the workspace/capabilities persist directly
above it: the offline characterization harness has no `workflow_runs` row, so
the value is `None` there and the key rides as null. Fixed at the emitter, not
at the one consumer, because that is where the data is missing — the durable
row persisted from this frame is what every future replay reads back.

**`backend/tests/agents/characterization/_normalize.py`** — `"created_at"` added
to `_VOLATILE_STRIP_KEYS`. A per-run wall-clock stamp is the most volatile value
there is, `_REQUIRED_DATA_KEYS` has no `pipeline_start` entry at all, and the
snapshot compares whole canonical-JSON dicts — so without the strip a new key
would turn all 5 event goldens red. Same treatment its `resume_offset` sibling
got, and it keeps the golden files byte-untouched (INV-3). No golden currently
contains a `created_at` key on any event type, so nothing is de-pinned.

**`frontend/src/hooks/useWorkflow.ts:511`** — the `|| new Date().toISOString()`
fallback is deleted; the expression is now
`(msg.created_at as string) || prev.createdAt`. This is the half that repairs
runs whose durable `pipeline_start` row was already persisted without a
timestamp — the backend stamp cannot reach back into them. A frame with no
`created_at` now leaves the field unset, `formatRelativeAge(undefined)` returns
`""`, and the header's existing `metaParts.filter(Boolean)` drops it: a graceful
blank instead of a confident wrong value. Fixed in the reducer rather than in
`LaneRunHeader` so `pipelineState.createdAt` stops being a lie for any future
consumer, per the disposition on [ISS-276](20260828-1700-ISS-276.md).

Deliberately NOT done: surfacing `run_events.created_at` (the column exists,
`backend/app/models/run_event.py:72`) through `GET /api/runs/{id}/events` so
historical runs would render a real age instead of a blank. That is a new field
on a public API response plus a `DurableFrame` shape change — outside what
ISS-276 scoped, and a design call rather than a fix. Recorded as
[ISS-413](20260828-2357-ISS-413.md).
