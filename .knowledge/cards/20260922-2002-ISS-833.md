# ISS-833

Sibling of [ISS-832](20260922-2001-ISS-832.md), INFERRED — a boundary case in
the fix itself, not yet reproduced.

`frontend/src/lib/api.ts:407` sets `SHARED_GET_TTL_MS = 30_000` (30 seconds).
`cachedGet()` (`api.ts:410-426`) serves any caller within that window the
same resolved promise/value; past it, the cached entry is stale-but-present
(`hit && Date.now() - hit.at < SHARED_GET_TTL_MS` at `:415` evaluates false)
and the next caller falls through to a real `request()` call, which
repopulates the cache.

[FIX-617](20260922-1935-FIX-617.md)'s own card explains why a TTL was chosen
over an in-flight-only guard: "`CanvasConfigRail` asks seconds after
`CanvasView`'s fetch has already settled — an in-flight-only guard would not
have caught it." That framing — "seconds" — is the gap. `CanvasView.tsx:304`
fetches on the canvas's first mount; `CanvasConfigRail.tsx:162` only fetches
once the user clicks into an agent's config rail (confirmed: `CanvasConfigRail`
is the rail content mounted on that click, the same shape the existing
regression test exercises by clicking `L.RAIL_AGENT` and asserting
immediately — see
`tests/integration/e2e/suites/04_composer_canvas/test_iss796_capabilities_double_fetch.py`,
which asserts within `settings.SETTLE_MS` of the click). Composing a workflow
from scratch on `/workflows/new` — naming it, dragging in agents, reading
descriptions — is realistically a multi-minute task, not a multi-second one.
Once more than 30 seconds separate the canvas's mount from the first
agent-config click, the cache entry has expired and `CanvasConfigRail`
produces a second, real `/api/capabilities` fetch — the exact waste
[ISS-796](20260922-1825-ISS-796.md) was filed against, just outside the
window the existing test can see (it never waits).

Not yet reproduced — would need a live test that waits more than 30s between
canvas mount and opening the agent config rail. If confirmed, the fix is
either a longer TTL (weighed against staler catalog data across other
callers of the same cache) or making `useAgentCapabilities`'s two call sites
share one genuinely persistent fetch (e.g. a context/store both read) rather
than two independent hook instances racing a cache window.
