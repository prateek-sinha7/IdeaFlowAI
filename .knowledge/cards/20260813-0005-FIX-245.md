## Description

A reopened TERMINAL run rendered as if it were still live — header "Awaiting approval", an armed Stop button, armed gate cards (ISS-126). The register's stated locus was WRONG and it changed the fix: it put the symptom at the SSE durable replay, but a terminal run never opens an SSE stream (page.tsx:2171 gates attachRun on non-terminal), so run_stream.py is never entered on this path — the screen is fed entirely by GET /api/runs/{id}/events replayed at page.tsx:2234-2247. Both backend options previously rejected were therefore aimed at a code path the symptom does not traverse; their rejection stands, but neither would have worked. Fix (front-end, INV-12-REDUCING): terminalMarkers(status) becomes the SINGLE definition of what a terminal status does to run state, and the three live terminal event cases (pipeline_complete/pipeline_failed/pipeline_cancelled) route through it — so the number of places deciding "what terminal looks like" goes 3 → 1, and applyTerminalStatus is ONE-WAY (a non-terminal status returns prev unchanged, so a slow getWorkflow on a live run can never clear a legitimately open gate). The gate reuses the EXISTING REOPEN_TERMINAL_STATUSES, and a test pins the two sets equal so they cannot drift into the fifth divergent list INV-12 exists to prevent. TWO of the three pieces were found ONLY by driving a real browser, after the unit tests were already green — the live-verification lesson, paid again. (a) Patching the store is TRANSIENT: the FIX-201 bridge (page.tsx:1663-1672) copies the LEGACY useWorkflow.pipelineState into the store wholesale once the viewport switches, and that legacy state accumulated the same terminal-less replay, so it clobbered the store patch a few hundred ms later and the Stop button survived (filed as ISS-138). (b) Resolving isRunning is not sufficient: laneClarifyOpen is the ONE lane branch not AND-ed with isRunning — deliberately, since clarify precedes pipeline_start (on 808612bf: questionnaire_ready @5, pipeline_start @11), so gating it would break a LIVE clarify — and the header merely fell from "Awaiting approval" to "Clarifying" with Stop still armed; on that run the lingering panel is itself ISS-123 damage, its questionnaire_complete row being one of the 15 destroyed events. reviewGateData is deliberately NOT cleared — it is already masked by the gate branch's && isPipelineRunning, and clearing it alone is WORSE than nothing (runLaneState falls to "building" → header "Running", Stop still present). The fix is also not placed in the case "pipeline_cancelled": case "pipeline_failed": switch arm, which is verified dead code (ISS-139) and pinned as such by test.

## Root cause

Nothing in frontend/src derived the run-state terminal markers from the server's persisted workflow_runs.status; the run screen treated the terminal EVENT as the source of truth, inverting what every other consumer (boot restore scan, RunState fence, history badges, FIX-240's own SSE guard) already does.
