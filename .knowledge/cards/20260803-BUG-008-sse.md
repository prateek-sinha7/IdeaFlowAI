# BUG-008 — Reopened generic/custom deliverable renders empty on the shared run screen


### BUG-008 — Reopened generic/custom deliverable renders empty on the shared run screen  [🟠 major] [FIXED ✅]
- **RESOLVED:** FIXED (quick 260716-n2d, `3cce39df`) — decoupled `hasGenericDeliverable` (`PreviewPanel.tsx:577`) from the stale-`workflowType` gate via a `knownContentPresent` guard: a present generic deliverable now renders whenever the typed renderer for the (possibly-stale) `renderType` has nothing to show, so a terminal reopen no longer short-circuits to "Output will appear here". RED→GREEN unit (2 cases: `text/html`→P18 sandboxed iframe with no `allow-same-origin`; `text/markdown`→MarkdownPreview) + TS-T-04b un-`fixme`'d (real chromium History-tap of a `custom` completed HTML run → sandboxed Deliverable Preview iframe renders). tsc clean; `WorkflowHistory.genericReopen` + at-risk suites green; SC-001 clean (no workflow-name literal). **Offline-proven via the real-browser e2e** — a completed run's FE render gate is backend-agnostic (page.tsx seeds `genericDeliverable` from `fullRun.output` regardless of producer), so no live Bedrock custom run was required.

- **Tracks:** `DEF-BUG-002-generic-reopen` (deferred-items.md, quick 260716-j1u) · tracking test `e2e/tests/ts-t.history.spec.ts` TS-T-04b (`test.fixme`, :166).
- **Found:** 2026-07-16 · run-screen reopen of a `custom`/unknown-type deliverable · surface = shared run screen (execution view) PreviewPanel. Reached via BOTH the BUG-002 History-tap route (`onOpenRun`) and the pre-existing Home-recents route — both funnel through `page.tsx handleSelectWorkflowRun` → the single execution-view `<PreviewPanel>`.

- **Symptom:** Reopening a completed `custom`/unknown-type run whose `output` is HTML renders the run screen's Preview tab as the neutral empty state **"Output will appear here"** (`PreviewPanel.tsx:1018`) instead of the sandboxed `Deliverable Preview` iframe. The Files tab also loses its generic deliverable row. TYPED deliverables (user_stories/ppt/prototype/app_builder) render correctly. The OLD `RunDetailPage`/`WorkflowHistory` in-panel detail rendered the same generic deliverable fine (locked by `WorkflowHistory.genericReopen.test.tsx`).

- **Root cause — a DISPATCH/GATE gap keyed on a stale `workflowType`, NOT a data-loading gap. Pin: `PreviewPanel.tsx:577` (+ its upstream `:536`), fed a stale `workflowType` from `DashboardLayout.tsx:1825` because the binder at `DashboardLayout.tsx:330-368` is `isRunning`-gated (`:331`).**

  The surface hypothesis in `deferred-items.md` (page.tsx "does not repopulate `genericDeliverable` on this path") is **incorrect** — the data IS loaded and passed. Full chain:

  1. **Data IS seeded + passed (so this is NOT a data gap).** `handleSelectWorkflowRun` clears content (`page.tsx:1216`), then in the generic `else` branch — gated on `fullRun.output && isContentTerminal` (`:1293-1295`, completed/degraded) and a non-known type — DOES call `setGenericDeliverable({ mimetype: resolveReopenMimetype(...), filename, content: fullRun.output })` (`page.tsx:1311-1318`). For the TS-T-04b fixture (`type:"custom", status:"completed", output:"<!DOCTYPE html>…"`) this branch **fires**: `genericDeliverable.content` = the HTML, mimetype `text/html`. It is passed to `<DashboardLayout genericDeliverable={genericDeliverable}>` (`page.tsx:1428`) and on to `<PreviewPanel genericDeliverable={genericDeliverable}>` (`DashboardLayout.tsx:1823`). Verified present.

  2. **The gate suppresses it.** `PreviewPanel` decides "is there content to show" via `hasContent = !!(effUserStoryContent || effPptContent || effPrototypeContent || pptxCode || hasGenericDeliverable)` (`:579`), where `hasGenericDeliverable = !isKnownRenderType && !!genericDeliverable?.content` (`:577`) and `isKnownRenderType = KNOWN_RENDER_TYPES.includes(renderType)` (`:575-576`). `renderType` normalizes `detectedType = workflowType || (userStoryContent?…:…:"user_stories")` (`:536`). On a completed reopen the typed content is all empty, so `detectedType` collapses to the `workflowType` prop — and **`detectedType` never inspects `genericDeliverable`**, so it can only reach a non-known value if `workflowType` itself is non-known.

  3. **`workflowType` is stale on reopen.** The prop is `DashboardLayout`'s own `workflowType` state (`:1825`), default `"user_stories"` (`:250-256`). The effect that would rebind it to the viewed run's declared type (`:330-346`) is gated on `if (pipelineState?.isRunning)` (`:331`) and **never runs for a terminal reopen** (`isRunning` false). So `workflowType` stays `"user_stories"` → `renderType="user_stories"` → `isKnownRenderType=true` → `hasGenericDeliverable=false` → `hasContent=false`.

  4. **Empty state short-circuits before the renderer that WOULD have worked.** With `hasContent=false`, the preview tab takes the `!hasContent` branch (`:1016-1019` → "Output will appear here") and **never calls `renderDeliverable()`** — whose step-1 first-party lookup returns null (no typed content) and whose step-2 `if (genericDeliverable?.content) return <GenericDeliverablePreview …>` (`:890-891`) would have rendered the HTML in the P18 sandboxed iframe. The renderer is correct; the `hasContent`/`hasGenericDeliverable` gate (workflowType-dependent) starves it. `hasGenericDeliverable` also gates the Files-tab generic row (`:1081`), which is why the Files tab loses it too.

  **Why the OLD path (RunDetailPage/WorkflowHistory) renders it:** `WorkflowHistory` derives its type from the **actual reopened run** — `const workflowType = selectedRun.type` (`WorkflowHistory.tsx:377`) — so `isGeneric = !isUserStory && !isAppBuilder && !isPpt && !isPrototype` (`:401`) is correctly true for a `custom` run; it then resolves the mimetype straight from the output via the SAME `resolveReopenMimetype(selectedRun.deliverableMimetype, selectedOutput)` (`:403`) and renders HTML→sandboxed iframe (`:666-676`, `srcDoc`, `sandbox="allow-scripts"`, no `allow-same-origin`) / zip→bundle (`:682`) / else→MarkdownPreview (`:687`). It depends on the run's own type + output shape, **never** on a DashboardLayout-global `workflowType`. That is the exact difference: the OLD path self-detects; the execution-view PreviewPanel relies on a `workflowType` binding that the reopen path never establishes.

- **Pre-existing verdict — PRE-EXISTING; BUG-002 exposed it, did not introduce it.** All constituent lines predate the BUG-002 fix (`e8a22842`, 2026-07-16): the `isRunning`-gated binder `DashboardLayout.tsx:331` = `0590c2448` (imran-hex, 2026-05-19) — the SAME stale-`workflowType` root as BUG-003 L2 and BUG-006; the `workflowType={workflowType}` prop `:1825` = `4f7ec0898` (2026-05-07); the workflowType-gated `hasGenericDeliverable` `PreviewPanel.tsx:577` = `3ae121209` (imran-hex, 2026-06-13, Phase 18-03 — the generic-deliverable feature only ever rendered on the LIVE path, where `workflowType` is bound during `isRunning`); its folding into `hasContent` `:579` = `c5d8e4449` (2026-07-02); `detectedType` `:536` = `365b3a58f` (2026-05-06). BUG-002 (routing History taps into the execution view) merely made the custom-History-tap case reach this gate; the Home-recents route already shared it. Same "run-screen state not bound to the viewed run" class as BUG-001 (title)/BUG-003 (revise type)/BUG-005 (clarify)/BUG-006 (type label) — here the deliverable-render TYPE. NOT covered: `WorkflowHistory.genericReopen.test.tsx` renders `WorkflowHistory` directly (`:103`), never the execution-view PreviewPanel, so the run-screen generic reopen is genuinely untested (TS-T-04b `test.fixme` confirms).

- **Fix proposed (MINIMAL, not applied) — decouple the generic-deliverable "has content" signal from the stale-`workflowType` gate. Preferred: `PreviewPanel.tsx:577`.**
  Make a present generic deliverable count whenever the typed renderer for the (possibly-stale) `renderType` has nothing to show:
  ```
  // PreviewPanel.tsx:577 — before:
  const hasGenericDeliverable = !isKnownRenderType && !!genericDeliverable?.content;
  // after:
  const knownContentPresent = !!(effUserStoryContent || effPptContent || effPrototypeContent || pptxCode);
  const hasGenericDeliverable = !!genericDeliverable?.content && (!isKnownRenderType || !knownContentPresent);
  ```
  Effect: reopen custom (stale `workflowType="user_stories"`, no typed content) → `false || true` = true → `hasContent` true → `renderDeliverable()` runs → step-1 first-party returns null → step-2 renders the sandboxed iframe (and the Files-tab row via `:1081`). No regression: a live/first-party run with typed content has `knownContentPresent=true` + `isKnownRenderType=true` → `false || false` = false (and `genericDeliverable` is undefined there anyway); a live custom run is unchanged (`isKnownRenderType=false`); a terminal-FAILED run (status `failed`, not `completed`/`degraded`) never gets a `genericDeliverable` so `showFailureAffordance` (`:602`) is unaffected; a `degraded` run WITH a partial deliverable now renders it, which is the WR-01 intent. `renderDeliverable()` (`:868-895`) and `GenericDeliverablePreview` (the P18 `sandbox="allow-scripts"` / no `allow-same-origin` contract, `:178-215`) are untouched. Robust to runs outside `recentRuns` and to an empty/undefined `workflowType`. Preserves the launch/live flow byte-identically.

  **Alternative (pattern-consistent with BUG-003/006, but narrower):** at `DashboardLayout.tsx:1825` pass `workflowType={viewedRunType ?? workflowType}` (and `:1826` similarly), reusing the already-computed `viewedRunType` (`:1265-1268`). This binds `detectedType` to the viewed run's real type (`"custom"`) → `isKnownRenderType` false → renders. Caveat: `viewedRunType = recentRuns?.find(r => r.id === contentSourceRunId)?.type` is `undefined` when the reopened run is not in `recentRuns` (History surfaces runs beyond the recents window) → the bug persists for those. Prefer the PreviewPanel fix (no recentRuns dependency); the two are compatible if both are desired.
