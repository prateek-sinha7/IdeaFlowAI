`ComposerPage.tsx:653` sends `base_pipeline_type: "custom"` unconditionally. Its comment says this
is deliberate: `workflowType` is a shared mutable that other screens (history, revision, chaining)
also set, and trusting it once let a stale value be persisted as a saved workflow's permanent type.

Seven tests in `ComposerPage.test.tsx` assert the real type instead (`expected 'custom' to be
'user_stories'`). The suite has sat at **7 failed | 7 passed** since `c9ec0149c` — a documented
baseline, not a regression.

**Two consequences:**

1. The full canvas at `/workflows/{id}/canvas` cannot create an override — only the two launch
   surfaces can (see [FIX-304](20260825-2115-FIX-304.md)).
2. A permanently red suite trains people to ignore it.

**Disposition:** open, and it is a genuine design decision, not a bug to patch. Either the
composer gets a non-stale source for its entry type (an explicit prop rather than the shared
mutable), or the tests are wrong and should be rewritten to assert the hardcode. Deliberately not
resolved here — bending either side without deciding which is correct would hide the conflict.
