## Analysis (2026-10-01, QA-KB-015 analyzer): root cause CONFIRMED, agreed fix accepted with amendments

Line numbers in this section are the 2026-10-01 working tree, re-checked at 22:30:
`AccountSettings.tsx`, `DashboardLayout.tsx` and `IdeaInputPage.tsx` are unmodified against HEAD
(`LaunchWizard.tsx`, cited here only through ISS-917, now carries other work's uncommitted edits).
The numbers in the older sections below have drifted (Back is now `:232-237`, not `:209`).

### Root cause (CONFIRMED)

The Back guard exists and works; `AccountSettings` never feeds it. This card was filed before
[FIX-352](20260828-2346-FIX-352.md) put a dirty check into `handleBackNav`, and a later fix
([FIX-481](20260902-1530-FIX-481.md), the 2026-09-02 card; a second, unrelated card shares that
id) swapped its `window.confirm` for an in-app dialog. So "the same ungated handleBackNav" in the
summary and in the older sections below is stale: the handler is gated, this page just never
opens the gate.

- `frontend/src/components/layout/DashboardLayout.tsx:1875-1880`: `handleBackNav` opens the
  "Leave without saving?" dialog (`:3478-3517`) only `if (hasUnsavedWork.current)`.
- `DashboardLayout.tsx:1847-1850`: `hasUnsavedWork` is written only by `handleUnsavedChange`.
  Its one wired producer is the ComposerPage mount (`:3214-3215`); its one reader is `:1876`.
- `frontend/src/components/settings/AccountSettings.tsx:30-47,87`: the props are
  `{ onBack, initialSection }`. There is no `onUnsavedChange` and nothing ever calls one. The
  Back button (`:232-237`) is a bare `onClick={onBack}`.
- `DashboardLayout.tsx:3117`: the only mount passes `initialSection` and `onBack`, nothing else.

With Settings mounted the flag is permanently `false`, so Back takes the immediate `goBackOr`
branch (`:1885`). That is the validated reproduction (`evidence/qa-kb-015/01..06`).

### Not a product question

The page already names the state. The AI Model tab prints "Unsaved — currently using ..." on
`selectedModel !== pendingModel` (`AccountSettings.tsx:425`) and disables Save on the same test
(`:450`); the Constitution tab already confirms before discarding a draft on a tab switch
(`:249-256`, [ISS-482](20260828-2322-ISS-482.md)). Back is the one exit that skips all of it.

### Dirty sources on this page

1. Password fields: `currentPassword || newPassword || confirmPassword` (`:100-102`), cleared
   only by a successful change (`:192`). CONFIRMED and reproduced.
2. Model: `pendingModel !== selectedModel` (`:116-117`). Safe at start: both begin `null` and are
   set together from `prefs.preferred_model` in one `.then` (`:148-149`), and the select maps
   `""` to `null` (`:384`), so a pristine page is never dirty. CONFIRMED by reading; the
   reproduction typed a password, not a model pick.
3. Constitution draft: named by neither this card nor QA-KB-015, and
   [ISS-482](20260828-2322-ISS-482.md) says in terms that this card does not cover it. Filed
   separately as [ISS-921](20261001-2222-ISS-921.md), with the two false-prompt traps a naive
   check hits. INFERRED.

### Fix: the agreed minimal fix is ACCEPTED

Add `onUnsavedChange?: (dirty: boolean) => void` to the props (`:30`), destructure it (`:87`),
compute `dirty` from sources 1 and 2 (plus 3 per ISS-921) and report it with
`useEffect(() => { onUnsavedChange?.(dirty); return () => onUnsavedChange?.(false); }, [dirty, onUnsavedChange])`;
pass `onUnsavedChange={handleUnsavedChange}` at `DashboardLayout.tsx:3117`. That is the exact
shape of `ComposerPage.tsx:190,227,374-379` and keeps FIX-352's locked constraint: the check lives
in `handleBackNav`, never as a per-page `confirm()`. The guard itself must not change. The wiring
belongs on the page, not centrally: only the page knows its own dirty state, and the central
handler and dialog already exist. No baseline ref is needed (unlike ComposerPage and
IdeaInputPage): each value is compared with its own saved twin (`selectedModel`,
`constitutionLoadedValue`, or the empty string for the password fields), and the async loads set a
value and its twin in the same batched update, so a pristine page can never read as dirty.

Hazards for whoever fixes it:

- No `window.confirm`. S-19-17
  (`tests/integration/e2e/suites/19_toasts_and_dialogs/test_toasts_and_dialogs.py:392-393`) fails
  on any bare `confirm(` in non-test frontend source.
- Optional, one attribute: the Back button has no accessible name (`:232-237`; IdeaInputPage uses
  `aria-label="Back to dashboard"`, ComposerPage `aria-label="Back"`). That is why
  `tests/integration/e2e/framework/locators/settings_page.py` has no Back locator.
- Autofill (INFERRED, low): `PasswordInput` passes no `autoComplete`. If a browser autofills
  "Current password" on load, Back would prompt on an untouched page. What settles it: real
  Chrome with a saved credential for localhost:3000, open `/settings/profile`, read the field.

## Sibling of ISS-275 (formerly INFERRED, now reproduced: see Analysis above and Reproduction below)

Filed while analyzing `BUG-20260828-003800-workflows-new` (ComposerPage's Back button
silently discards unsaved workflow name/agents, root card [ISS-275](20260828-1855-ISS-275.md)).
`AccountSettings` is wired through the exact same shared, ungated navigation handler and
holds its own class of not-yet-persisted user input (an in-progress password change, and
a model preference picked but not yet saved). This has NOT been independently
reproduced in the browser; it is derived from reading the code path and is a lead, not a
confirmed defect.

## Why the root cause implies this

`ComposerPage`'s Back button calls `onBack` directly with no dirty-check
(`frontend/src/components/workflow/composer/ComposerPage.tsx:979`), and `onBack` is the
shared `handleBackNav` (`frontend/src/components/layout/DashboardLayout.tsx:1701-1712`),
which unconditionally does `router.back()` / `router.push(routes.home())` with zero
knowledge of any mounted child's own uncommitted state.

`handleBackNav` is passed as `onBack` to exactly 5 call sites in `DashboardLayout.tsx`
(confirmed via `grep -rn "onBack=" frontend/src`, excluding `*.test.tsx`):
`WorkflowHistory` (:2767), `AccountSettings` (:2849), `AnalyticsPage` (:2863),
`IdeaInputPage` (:2893), `ComposerPage` (:2946). `AccountSettings` wires its own Back
button the identical way — `onClick={onBack}`, no gate — at
`frontend/src/components/settings/AccountSettings.tsx:209`.

`AccountSettings` holds real, not-yet-saved user input in local `useState`, confirmed
present in the file:
- Password-change form: `currentPassword` / `newPassword` / `confirmPassword` —
  `AccountSettings.tsx:93-95` — cleared only on a successful `handleChangePassword()`
  call (`:168`), never on navigation.
- `pendingModel` — the AI-model dropdown value picked but not yet committed via
  `handleSaveModel` — `AccountSettings.tsx:105`, distinct from the already-saved
  `selectedModel` (`:104`).

None of this is persisted until the user explicitly clicks "Save"/"Change password".
Losing a typed password mid-entry (or a picked-but-unsaved model preference) with no
warning is the same shape of silent discard as the reported composer bug, on a
different screen behind the same shared handler.

## Expected vs Actual (to be confirmed by reproduction)

**Expected:** Leaving Account Settings via its own Back control while the password form
has typed content, or `pendingModel !== selectedModel`, should prompt for confirmation
before discarding, same as the fix expected for ISS-275.

**Actual (inferred, unverified):** Clicking Back should silently navigate away and
discard the typed password fields / pending model pick with no warning, by the same
mechanism as ISS-275.

## What would settle it

Reproduce in the browser: open Account Settings, type into the current/new/confirm
password fields (or pick a different AI model without clicking Save), click the header
Back button (`AccountSettings.tsx:209`), and confirm the fields are gone / the pick is
reverted with no confirmation prompt shown.

## Reproduction (BUG QA-KB-015, validated 2026-10-01)

Reproduced 3/3 from cold start (fresh /dashboard load, then deep link /settings/profile) as admin@velocity.ai, light theme, desktop viewport. Each cycle: typed a value into "Current password" (never submitted), clicked the header Back button (lucide arrow-left). Result each time: URL went /settings/profile -> /dashboard immediately, no modal ([role=dialog]/[role=alertdialog] count 0) and no native confirm; on returning to /settings/profile the field was empty. Code check: AccountSettings.tsx:87 props are only `{ onBack, initialSection }`, DashboardLayout.tsx:3117 passes no `onUnsavedChange` (it exists at :3215 for ComposerPage only). Note: /settings/security is the admin MFA enrollment page, not this form; password fields live on /settings/profile.
