## Root cause — a second, independent caller of the same unguarded replay path

[ISS-785](20260922-1620-ISS-785.md) root-causes QA-PS-038 to
`handleWebSocketMessage` (`frontend/src/app/[...view]/page.tsx:1016`) having
12 `getWorkflows(token, { limit: 50 })` call sites bound to SSE event types,
with no way to tell a replayed historical event from a live frame. Its
evidence is built entirely from the history-reopen path,
`handleSelectWorkflowRun` (`page.tsx:2993-3006` replays `getRunEvents`'s
result through `handleWebSocketMessage` unconditionally).

`handleSwitchToLiveRun` (`page.tsx:2716-2717`) is a **second, independent**
caller of the identical pattern:

```
page.tsx:2772   const durableFrames = await getRunEvents(switchToken, runId);
page.tsx:2777   for (const frame of durableFrames) {
page.tsx:2778     handleWebSocketMessage(
page.tsx:2779       { type: frame.type, data: frame.data } as unknown as StreamMessage,
                     ...
```

It fetches the run's full durable event log and replays every frame through
`handleWebSocketMessage` exactly like `handleSelectWorkflowRun` does — same
handler, same 12 unconditional `getWorkflows` bindings, same lack of a
replay-vs-live signal.

This function is reached from `AppHeader.tsx:225-235` and `:321-322`
(`onSwitchToLiveRun`, wired at `page.tsx:4299`) — the header's "N Running"
badge/dropdown, whose own comment states the branch is taken for "live/building
runs" (`AppHeader.tsx:225`). The badge's notion of "still running" comes from
`recentRuns`, itself only refreshed on specific SSE events (see
[ISS-143](20260813-0205-ISS-143.md): "the header 'N Running' pill goes stale
after a live cancel — no recentRuns refresh fires"). A run that finishes
between the badge's last refresh and the click is exactly the window where
`handleSwitchToLiveRun` fires this same full-log replay for a run that has,
in fact, already gone terminal — the run's status will never change again, so
none of the 12 refetches this replay triggers accomplish anything, same as
QA-PS-038.

## Expected vs actual

Expected: switching to a run via the header badge fires at most the requests
needed to attach its live state — no more `runs?limit=50` calls than the
number of SSE events that have genuinely fired since the badge last refreshed.

Actual (read from code, not yet clicked): every durable event in the target
run's log replays through the same 12 unconditional bindings ISS-785
documents, regardless of whether the run is still live or has already gone
terminal by the time of the click.

## Resolved by FIX-624 (2026-09-22)

[FIX-624](20260922-2027-FIX-624.md) put the guard on the shared router rather
than on either caller: `handleWebSocketMessage` now takes an `isReplay`
parameter, and all eight of its `getWorkflows(limit: 50)` bindings read a token
getter that returns null during replay. `handleSwitchToLiveRun`'s loop —
`page.tsx:2836-2843`, the one this card names — passes `true` alongside `runId`,
so the storm it would have fired can no longer happen.

Verified by construction plus measurement of the sibling loop rather than by the
badge click this card asked for: both loops call the same handler with the same
flag, and on `handleSelectWorkflowRun`'s loop the post-click `runs?limit=50`
count dropped 3 -> 1 with every `handleWebSocketMessage` frame gone from the
stacks (`evidence/qa-ps-038/07-fix-click-phase-before-after.txt`). The
narrow badge-timing repro this card describes (a run that goes terminal between
the badge's last refresh and the click) was NOT staged.
