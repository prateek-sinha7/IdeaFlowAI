# ISS-1205

**Register source:** sibling derived during the `QA-KB-112` analysis on 2026-10-12 (root [ISS-1203](20261012-0949-ISS-1203.md)). Not its own bug row. It also reopens the evidence behind [ISS-799](20260922-1835-ISS-799.md), whose card is `resolved` with this node as its `verification.test_files`.

**Confidence.** INFERRED sibling. The mechanism is certain from code (a substring match) and the pass is in the run record; nobody has printed the matched request.

## Condition

`test_qa_ps_035_settings_duplicate_requests.py::test_settings_security_tab_fetches_mfa_status_once` cold-loads `/settings/security` (`:82`), waits `SETTLE_MS`, counts the recorded requests whose URL contains `/api/auth/mfa` with `_count` (`:30-31`, `sum(1 for u in urls if path in u)`), and asserts the count is exactly 1 (`:85-89`). Its docstring claims it proves "the Security tab's mount effect (`SecuritySection.tsx`) must fetch `/api/auth/mfa` exactly once per cold load" (`:78-79`).

## What happens

- `GET /api/auth/mfa` has one client, `getMfaStatus` (`api.ts:859-862`), and one caller, `SecuritySection.tsx:82`. On `/settings/security` the static enrolment page owns the route ([ISS-1203](20261012-0949-ISS-1203.md)), `SecuritySection` never mounts, and that GET is never sent.
- The enrolment page sends one `POST /api/auth/mfa/totp/associate` per mount (`api.ts:918-923`). `"/api/auth/mfa" in "http://localhost:3001/api/auth/mfa/totp/associate"` is `True`, so the count is 1 and the assertion holds.
- Run record, full 09_settings run of 2026-10-09: `[5/39] UNMARKED ISS-799 — the Security tab's mount effect (SecuritySection.tsx)` `PASS 0 shots 5.2s`, in the same file where nine other nodes fail on this URL (`analysis-02`).

## Expected vs actual

Expected: green means `SecuritySection` sends one `GET /api/auth/mfa` on mount, which is ISS-799's claim. Actual: green means the enrolment page sent one `POST` to associate.

## Why the root cause implies it

It is the other consumer of the URL whose failure is silent: written for a tab, it cold-loads the same route, and its assertion is loose enough to be satisfied by the page that replaced the tab.

## Fix direction (test-side; belongs to the owner-decided fix of the root card)

The node can no longer reach `SecuritySection` by URL ([ISS-1204](20261012-0949-ISS-1204.md)). Either retire it from the e2e tier and move ISS-799's claim to the unit tier, where it can still be proved: the `initialSection="security"` case in `AccountSettings.render.test.tsx` (`:221-228`) asserts `mockGetMfaStatus` `toHaveBeenCalledWith("test-token")` but not how many times, so tightening it to exactly once is the faithful replacement. Or keep the e2e node and match method and exact path (`GET`, path equal to `/api/auth/mfa`), which turns it red on today's route table and documents that the tab is unreachable. The sibling Constitution node in the same file (`:92-107`) is unaffected: `/settings/constitution` is still served by the catch-all.

## What would settle it

Run the one node with `page.on("request", lambda r: print(r.method, r.url))` added: the only matching line is `POST .../api/auth/mfa/totp/associate`. The substring fact itself needs no browser.
