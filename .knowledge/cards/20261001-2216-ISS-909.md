# ISS-909

## Description

**INFERRED sibling of [ISS-189](20260828-1457-ISS-189.md)** (root card for QA-KB-010, the PPT
wizard "Pick a design system" dead end). Not reproduced. Every mechanism line below was read in
the code at the cited line; only the *reachability* (a failing or empty registry response) is
inferred.

ISS-189's invariant is: the wizard demands a design system the user has no way to supply.
ISS-189's own cause is an unmounted step. This card is the same invariant reached through a
different door: the picker step exists, but the registry that feeds it never arrives.

## Condition (INFERRED)

`GET /api/prototype/design-systems` (`listDesignSystems`, `frontend/src/lib/prototype-api.ts:64`)
rejects (network error, 5xx, expired token) or resolves `[]` (for example a mis-set `OD_ROOT`:
the backend lists `_OD_ROOT / "design-systems"`, `backend/app/services/od_loader.py:75`).

## Mechanism (CONFIRMED by reading)

1. `frontend/src/components/workflow/LaunchWizard.tsx:673` — the DS-registry effect ends in
   `.catch(() => { /* non-fatal — the picker stays empty */ })`. Nothing is stored or shown on
   failure, and there is no retry. Contrast the web-template effect in the same file, which does
   `setLoadError(err.message)` (`:635`) and renders it (`:1290-1294`).
2. `LaunchWizard.tsx:1311-1312` — `systems.length === 0 ? <div className="h-48 animate-pulse ..."/>
   : <DesignSystemPicker .../>`. An empty list is indistinguishable from "still loading", so the
   skeleton never resolves.
3. `LaunchWizard.tsx:886` (web: `Boolean(selectedDsId && hasBuildInput)`), `:889` (deck:
   `... && (!dsRequired || selectedDsId)`) and the `:1373` pill keep demanding a DS.
   `selectedDsId` can only come from the picker, a restored draft (`:416`) or FIX-103's
   auto-select (`:666-669`), and that auto-select sits inside the same `.then` that never runs.

Result: Continue disabled, "Pick a design system" pill showing, the DS tab an endless pulse, and
no message. The same dead end as ISS-189 with a different trigger.

## Where it bites

- `prototype` / `prototype_v2` wizard: today (a design system is always required for web,
  `:886`).
- Deck wizard (`ppt` / `ppt_v2`): only AFTER ISS-189's minimal fix lands. Today the deck wizard
  never mounts the picker, so this is masked; the three DS-requiring deck templates
  (`ib-pitch-book`, `weekly-update`, `simple-deck`) would then inherit this failure mode.
  **That condition is now met (2026-10-01):** [FIX-695](20261001-2230-FIX-695.md) mounted the deck
  Design System step, so the deck exposure is live. The edit did not touch the `:673` catch or the
  skeleton, which has moved to `:1313-1314`.

## Why the root cause implies it

ISS-189's fix makes the registry-fed `DesignSystemPicker` the ONLY way to satisfy `dsRequired`
for decks. That moves the question "can the user satisfy the gate?" from "is the step mounted?"
to "did the registry load?", and the wizard answers the second question by showing nothing. The
composer's `DesignPickerModal` already handles the same fetch correctly (`setError(...)` plus a
"Loading the catalog…" line, `composer/DesignPickerModal.tsx:117-120,275-277`), so the wizard is
the outlier, not the pattern.

## Expected vs actual

- **Expected:** a failed or empty registry fetch shows an explicit error (ideally with a retry)
  in the DS step, as the composer picker and the web-template effect do, and an empty list is
  distinguishable from loading.
- **Actual:** permanent skeleton, disabled Continue, no message.

## What would settle it (INFERRED -> CONFIRMED)

Offline, one file: in `frontend/src/components/workflow/LaunchWizard.test.tsx` mock
`listDesignSystems` to `mockRejectedValue(new Error("500"))` (and separately
`mockResolvedValue([])`), render with `initialMode="prototype"` and the real design-system slot,
and assert an error or empty message appears instead of the `animate-pulse` placeholder. Or, in a
browser on `/create/prototype`, block `/api/prototype/design-systems` and open the Design System
tab.

## Fix direction (not decided here)

Track a `systemsError` / `systemsLoaded` flag beside `setSystems` and render the message in the
`dsSlot` branch. Whether a deck template that merely declares `design_system.requires` may
proceed without a design system when the registry is empty is a product call (the backend
tolerates it: `backend/agents/execution_engine/od_context.py:323-324`). Severity: Low (needs the
design-system endpoint alone to fail).

### Root cause (CONFIRMED)

1. **One value stands for three states.** `LaunchWizard.tsx:250` declares `systems` initialised to `[]`. There is no loaded or error
   flag next to it (`grep -rn "systemsLoaded\|systemsError"` over `frontend/src` and `backend` finds nothing), so `[]` is at once "the
   request is in flight", "the request failed" and "the registry is empty".
2. **The failure channel is closed.** `:711-726`: `listDesignSystems(token).then(...)` stores `systems` and runs FIX-103's
   auto-select; its only `.catch` is `.catch(() => { /* non-fatal — the picker stays empty */ })`. A rejection (`authFetch` throws on
   any non-OK status, `prototype-api.ts:55`, and `fetch` itself rejects on a network error) stores nothing and shows nothing.
3. **The render reads the empty value as loading.** `:1396-1411`:
   `systems.length === 0 ? <div className="h-48 animate-pulse ..."/> : <DesignSystemPicker .../>`. `WizardStepper.tsx:187` mounts that
   slot whenever the active step is "design-system", so the step is a pulsing box for good.
4. **The gates do not care.** Web: `:955` needs `selectedDsId`, always. Deck: `:958` needs it once the chosen template declares
   `design_system.requires`, and since [FIX-695](20261001-2230-FIX-695.md) the deck wizard has the step that is meant to supply it.
   `selectedDsId` can only come from the picker (`:828-837`), a restored draft (`:455`) or FIX-103's auto-select (`:715-723`), which
   sits inside the `.then` that never runs.
5. **The one non-registry way out is hidden too.** `DesignSystemPicker` carries an "Upload custom" button
   (`DesignSystemPicker.tsx:197`) whose `onSelectCustom` is `handleSelectCustomDs` (`LaunchWizard.tsx:833-837`), which sets
   `selectedDsId` and `customDsBody` and so would satisfy the gate. The skeleton replaces the picker, so a user with an unavailable
   registry cannot reach it. The real picker copes with `systems=[]` (probe control "REAL DesignSystemPicker given systems=[] DOES
   offer 'Upload custom'" passes; its footer reads "0 design systems", `DesignSystemPicker.tsx:376`).
6. **It has been this way since the first version.** `git show cc1097213:frontend/src/components/workflow/LaunchWizard.tsx`
   (2026-07-10, the unified wizard, plan 37-07) has the same `.catch(() => { /* non-fatal — the picker stays empty */ })` at its line
   252 and the same `systems.length === 0` skeleton at its line 699. The comment records the assumption that a missing registry is
   cosmetic. That is false wherever a gate needs `selectedDsId`: the web wizard always, the deck wizard for DS-requiring templates
   (live since FIX-695). Nothing regressed, so there is no last good commit to bisect to.

### Reachability (the part this card called INFERRED)

- **Failed fetch: reproduced at component level.** The real `LaunchWizard` with `listDesignSystems` mocked to reject

  `<div class="h-48 animate-pulse rounded-[var(--radius-card)] bg-surface-white/60"></div>`, no text; Continue is disabled and the

  html: ...`; test "EXPECTED: registry REJECTS" fails, "OBSERVE: in the failed arm Continue stays disabled..." passes). What nobody
  has done is make a live backend fail; BUGS.md's reproduction is a unit test by design.
- **Empty list: CONFIRMED by reading and by the probe.** `od_loader.py:420-424`: `_all_design_systems()` is `@lru_cache(maxsize=1)`,
  logs "Design-systems directory missing" at ERROR and returns `[]` when `_DESIGN_SYSTEMS_DIR` is not a directory;
  `prototype_templates.py:192-198` returns it as HTTP 200; `_OD_ROOT` is resolved once at import (`od_loader.py:73`). The probe's
  `[empty arm]` output is the same skeleton. This is not hypothetical: `od_loader.py:43-45` records a production regression where a
  mis-resolved root "returned an empty template gallery".
- **Consequence for the fix.** A Retry can heal a transient failure. It cannot heal the empty list, because the backend serves the
  cached `[]` again until the process restarts. The two arms need different wording: an error with Retry, and a plain "no design
  systems are available" note.

### Fix, and where it belongs

`LaunchWizard.tsx` only, three hunks in one file. There is no shared function to route through: the other caller is already correct
and has a different lifecycle (fetch on modal open, together with the templates), so a shared hook would be a larger diff than the
bug.

1. **State.** Next to `systems` (`:250`), an explicit load state. This file already has the idiom: `overrideLoad` (`:308`) is
   `useState<"loading" | "ready" | "failed">("loading")`. Mirror it, plus the error message, rather than the two booleans in the
   triage sketch.
2. **Effect (`:705-729`).** `.then` marks ready, `.catch` marks failed and keeps `err.message`. Move the body into a `useCallback` so
   a Retry control can call it; the effect still calls it once, on the same deps.
3. **Render (`:1396-1411`).** Skeleton only while loading. Failed: an error line (`role="alert"`) and a Retry button. Ready and
   empty: a plain "no design systems are available" note; `StepNote` (`:1608`) is the in-file component for it. Recommended,
   though BUGS.md's Expected does not demand it: keep `DesignSystemPicker` mounted below the message in both non-ready arms so
   "Upload custom" stays reachable (root cause 5). That is the registry-level counterpart of FIX-695's locked constraint that the
   deck DS gate always has a mounted picker.

**What a naive fix would get wrong**

- Merging the registry fetch back into the template effect, or adding `isWeb` or `mode` to its deps.
  [FIX-630](20260922-2115-FIX-630.md) split it out on purpose and locked it: the design-system fetch stays mode-independent, because
  re-running it on a family toggle would re-apply FIX-103's "apple" auto-select over a selection the user had cleared.
- A Retry that reuses the effect body unchanged. The `.then` updater reads `mode` (`:721`) from the mount-time closure, because
  `mode` is not in the deps; a `useCallback` with `[]` keeps that. Decide it on purpose (a ref, or "only the first attempt
  auto-selects") and keep `if (prev !== null) return prev` so a Retry never overwrites a choice.
- Letting a stale response land. `cancelled` (`:709`) is local to the effect; with a callback, a double-clicked Retry or an unmount
  mid-flight needs a ref-based guard (a request counter), or a late failure can overwrite a successful reload.
- Reusing `loadError` (`:251`, banner at `:1375-1379` saying "Couldn't load templates"). The wording is wrong for design systems and
  it is one slot shared with the template effect, so the two failures would overwrite each other. Use separate state.
- Offering Retry as the remedy for an empty list. The backend caches `[]` per process (above); say "none available".
- Clearing the skeleton on `.then` and `.catch` but leaving `systems.length === 0 ? skeleton` in place. The empty arm would still
  pulse.
- Relaxing `canContinue` (`:955`, `:958`) so a missing registry stops blocking. Out of scope and a product call (see "Fix direction"
  above). The comment at `DesignPickerModal.tsx:144-145` says the backend raises `LookupError` for a web run with no design system;
  not re-verified here.
