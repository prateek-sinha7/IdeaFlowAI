# ISS-888

**Register source:** `QA-KB-042` in root `LEDGER.md` / `BUGS.md` (sibling, derived during its analysis on 2026-10-01).
**Root card:** [ISS-104](20260812-1312-ISS-104.md) holds the mechanism (a comment restates a fact about another file with nothing tying the two together). Here the restated fact is a **value**, not a position, so the line-number-to-symbol fix that closes ISS-104 does not close this.

**Claim status: INFERRED (sibling).** The analyzer read every line quoted below in the current tree; no validator has reproduced it, and QA-KB-042 did not report it. It is one day old, which is why nobody has hit it yet.

## What is wrong

`backend/app/agents/model_factory.py:509-515` builds the Bedrock client with `read_timeout=1800` and explains why in the comment above it: "1800 s covers ~100K output tokens (the old 600 s cut a call off at ~36K, below the 64K/128K caps)". That change landed in commit `390edbaa6` (2026-09-30) and is recorded as [FIX-657](20260930-1723-FIX-657.md) ("Bedrock `read_timeout` 600 s -> 1800 s").

Two comments in `backend/app/api/run_shutdown.py` still state the old value as fact:

- `:237-238`, the `_drain_then_cancel` docstring: "(``model_factory`` sets ``read_timeout=600``, so a per-chunk check can be up to ten minutes away)".
- `:283`, the `stop_pipeline_drivers` docstring: "``model_factory.py:112`` sets ``read_timeout=600``" (the line number is also stale, see ISS-104).

Two more mention "the Bedrock `read_timeout=600` config" only as a contrast to the host-capacity metrics client's deliberately tight timeouts: `backend/app/core/config.py:223` and `backend/app/services/host_metrics.py:56`. Those are ambiguous rather than wrong, because the planner's own client, `backend/agents/planner/smart_planner.py:371`, really does still use `read_timeout=600`.

Consequence: the "mid-model-call blind window" is what justifies the `task.cancel()` escalation in `_drain_then_cancel` (the per-chunk cooperative-cancel check only fires when a chunk arrives). A single silent read can now last 30 minutes, not ten (INFERRED: longer if botocore retries a timed-out read under `max_attempts=5`; not checked). The escalation design is unaffected; only the sizing narrative in the comments is wrong, by 3x.

## Why the root cause implies it

[ISS-104](20260812-1312-ISS-104.md)'s mechanism is that a comment copies a fact about another file and nothing re-checks it. FIX-657 changed the fact and could not have found the copies. A fixer converting `model_factory.py:112` into a symbol cite would naturally keep the rest of that sentence, "sets read_timeout=600", and ship a symbol-correct, value-wrong comment.

## Expected vs actual

- Expected: the comment names the symbol (`build_model`'s Bedrock `Config(read_timeout=...)` in `model_factory.py`) and either states 1800 s or states no number.
- Actual: both shutdown docstrings say 600 and "ten minutes".

## Fix

Do it in the SAME pass as ISS-104, on the same two sentences in `run_shutdown.py` (`:237-238` and `:283`): drop the literal, or write 1800 s, and cite `build_model`. A literal in prose cannot be unit-tested without re-reading the source, so prefer deleting it. `config.py:223` and `host_metrics.py:56`: disambiguate ("not the agent client's `read_timeout`") or leave.

## Test notes (for the test-writer)

No test needed; this is documentation. If ISS-104's guard asserts the anchor `read_timeout` appears in `model_factory.py` (it should, to catch a rename), that covers the symbol half; the value half is deliberately not asserted.

## Fix (QA-KB-042, 2026-10-01)

Resolved by [FIX-690](20261001-2145-FIX-690.md). The literal is gone from both `run_shutdown.py` docstrings.
`_drain_then_cancel` now says "a full Bedrock `read_timeout` away - see `build_model` in `model_factory.py`".
`stop_pipeline_drivers` says "`build_model` in `model_factory.py` sets a long Bedrock `read_timeout`". The
`config.py` metrics-adapter comment and the `host_metrics.py` `_client` docstring now read "NOT the Bedrock model
clients' long read_timeout" (the disambiguate option). The guard's
`test_shutdown_comment_read_timeout_matches_model_factory` now gives `[XPASS(strict)]`, because no
`read_timeout=N` is stated in `run_shutdown.py`.
