## What was wrong

A saved workflow's launch panel silently replaced the workflow's own agent roster with the
generic per-pipeline default roster. Reported as
`BUG-20260828-073900-workflows-id-run-r2` in `bug-hunter/ledger.md`; root-caused on
[ISS-228](20260828-1758-ISS-228.md) and its sibling [ISS-283](20260828-1905-ISS-283.md).

Not a network race between `GET /api/user-workflows/{id}` and `GET /api/workflows/{type}` — a
same-commit React effect-ordering bug inside one component.

## Root cause

`frontend/src/components/workflow/LaunchWizard.tsx:335-338` (pre-change numbering):

```js
useEffect(() => {
  if (libraryAgents.length === 0 || pipelineAgents.length > 0) return;
  setPipelineAgents(defaultAgentsFor(libraryAgents, mode));
}, [libraryAgents, mode]);
```

Two effects share the `libraryAgents` dependency, so both run in the same passive-effect flush
when the Redux agent library lands (`frontend/src/hooks/useAgentLibrary.ts:16-20` — populated by
`GET /api/agents/library` on app boot, so it is guaranteed empty on `LaunchWizard`'s first render
after a cold direct navigation):

- The draft-restore effect (`:278-324`) maps the draft's `agentIds` against the now-populated
  library and calls `setPipelineAgents(restored)` (`:303-307`) — the saved workflow's real roster.
- This effect, declared after it, read `pipelineAgents.length` from the SAME render's closure.
  React does not surface one effect's `setState` to a sibling within the same commit, so it always
  read `0`, always fired, and — enqueued last with a plain value — won.

Both call sites of the component route through it: the cold `/workflows/{id}/run` mount
(`frontend/src/app/[...view]/page.tsx:3771`, draft staged at `:3620-3699`) and the click-through
Run (`frontend/src/components/layout/DashboardLayout.tsx:1475-1558` →
`frontend/src/app/workflow/create/page.tsx:24`), which is [ISS-283](20260828-1905-ISS-283.md)'s
narrower window on the identical mechanism.

## What changed and why there

`frontend/src/components/workflow/LaunchWizard.tsx:343-348` — the emptiness test moved out of the
render closure and into a functional updater:

```js
useEffect(() => {
  if (libraryAgents.length === 0) return;
  setPipelineAgents((prev) =>
    prev.length > 0 ? prev : defaultAgentsFor(libraryAgents, mode),
  );
}, [libraryAgents, mode]);
```

`prev` is resolved against the queued update, so the sibling's `restored` roster is visible here
and left alone; when nothing was restored, `prev` is still the empty race-loss array and the
defaults apply exactly as before. The effect's original purpose (a fresh open with no draft must
not be stuck at 0 agents) and its guard against overwriting a user's deliberate removal of every
agent are both preserved.

One shared component, so both call sites are covered by the one change — neither
`[...view]/page.tsx` nor `DashboardLayout.tsx` was touched: both already write a correct draft.
Nothing else in the file changed; no imports were orphaned.

longer fire, but it was never observed firing and no test proves either direction.
