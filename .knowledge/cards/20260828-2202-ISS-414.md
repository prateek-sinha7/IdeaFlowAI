## What happened (INFERRED sibling — not yet reproduced in the running app)

Derived from the root cause of [ISS-302](20260828-1734-ISS-302.md) (BUG-20260828-052400-workflows):
a delete-confirmation dialog that captures only the target row's **id** in local state at
click time, then renders fully static JSX with no lookup back into the loaded list to
interpolate a name/title. That exact shape is independently duplicated here, for a
different entity (a workflow **run**, not a saved workflow) on a different page.

## Root cause (CONFIRMED by direct read — the reproduction itself is not yet confirmed)

`frontend/src/components/history/WorkflowHistory.tsx`:

- `deleteConfirmId` (line 179, `useState<string | null>`) stores only the run's id when a
  row's delete action is clicked — never a name/title.
- `handleDeleteConfirm` (lines 408-421) reads only `deleteConfirmId`, calls
  `deleteWorkflow(token, deleteConfirmId)` (line 414), and filters `runs` by that id (415) —
  never touches a name.
- The dialog itself is `DeleteModal`, a local function component (defined line 1237) whose
  entire prop signature is `{ onConfirm, onCancel, error }` — **no name/title/label prop
  exists to pass one even if the caller wanted to**. Its rendered text (lines 1270-1275) is
  100% static: heading `"Delete workflow"`, subtext `"This cannot be undone"`, body `"The
  workflow run and all its output will be permanently deleted."` — no run name, no run id,
  no pipeline type, nothing that distinguishes one run from another.
- `DeleteModal` is instantiated at two call sites (lines 945, 1226), both
  `{deleteConfirmId && <DeleteModal onConfirm={handleDeleteConfirm} onCancel={...} error={deleteError} />}`
  — neither passes anything identifying either.

## Expected vs actual

- **Expected:** the confirmation states which run will be deleted (e.g. the run's workflow
  name/title, or its started-at timestamp), so a user working through a long, similarly-named
  run history can verify the correct row before an irreversible delete.
- **Actual:** dialog heading and body are fixed strings, identical regardless of which run
  triggered them — structurally unable to show identifying info since `DeleteModal` accepts
  no such prop.

## Why the root cause implies it

Same mechanism as ISS-302, not a coincidence: an id-only confirm-state variable plus a
dialog component with zero identifying prop is precisely the shape that produces "generic
dialog, no matter which row you clicked." `WorkflowHistory.tsx` implements that shape a
second time, independently of `SavedWorkflowsPage.tsx` (separate component, separate state,
separate API call), which is why this is a sibling rather than a shared-function blast
radius of the same bug — there is no code path connecting the two today.

## What would settle it

Reproduce in the running app: open the run history view, trigger delete on two
similarly-named runs, and diff the dialog's accessible text across both (mirroring
ISS-302's reproduction). Not yet attempted here — this card is code-derived only.
