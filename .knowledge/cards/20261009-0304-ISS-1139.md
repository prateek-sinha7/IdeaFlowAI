# ISS-1139

**Register source:** sibling derived during the `QA-KB-106` analysis on 2026-10-09 (root [ISS-1137](20261009-0304-ISS-1137.md)). Not its own bug row. The report asked to "check
that the /create wizards use the same path". Answer: they reach the same `.catch`, and they are worse off than the panels with a Run button because they have no form left to
return to. **INFERRED:** the code is read end to end, the screen was not driven.

## Condition

Continue on the ppt, ppt_v2, prototype or prototype_v2 wizard (`LaunchWizard`), when `POST /api/runs` refuses the staged launch (503 `model_provider_unavailable`, 400 and 422
errors). A 403 is stopped earlier on the client: `if (!canContinue || locked) return;` (`LaunchWizard.tsx:1073`).

## Why the root cause implies it

1. `LaunchWizard.handleLaunch` (`:1072-1130`) does not launch. It writes the draft (`sessionStorage.setItem(draft.draftKey, ...)`, `:1116`), sets the pending flag (`:1124`) and
   calls `router.push(routes.home())` (`:1125`). The wizard unmounts and its in-memory state (brief, attachments, picks) goes with it.
2. Once the connection is ready, `page.tsx` consumes the draft before anything is sent: `sessionStorage.removeItem("prototype.pending")` and `("prototype.draft")`
   (`page.tsx:2568-2569`), `("ppt.pending")` and `("ppt.draft")` (`:2652-2653`), with the comment "FIX-005: clear stale draft so next fresh wizard open starts empty". Then
   `setPendingOdProtoParams(...)` (`:2581`) or `setPendingOdPptParams(...)` (`:2665`).
3. `DashboardLayout`'s launch effects fire `onStartPipeline` (`:1482`, `:1547`) after `setMainView("execution")` (`:1434`, `:1509`). A refusal goes to the `.catch`
   (`page.tsx:4454-4467`): state reset, nothing shown. The URL is `/dashboard` (`routes.ts:57`), whose view is `"home"` unless `hasPendingWizardRunRef` is true
   (`page.tsx:4293-4301`). That ref reads the pending flag once, at mount (`:505-507`), and its comment (`:498-504`) describes a fresh mount at `/dashboard` with the flag set, so
   the likely landing is an empty execution view; if the page instance persisted instead, the URL-sync effect (`DashboardLayout.tsx:603-607`) puts the user on Home.
4. Net, by reading: the user is on an empty execution view or on Home, sees nothing, and the draft they typed is gone from memory and from `sessionStorage`. The brief can only be
   re-typed. Which of the two screens it is does not change the fix.

## Expected vs actual

- **Expected:** a message, and a way back to the wizard with the brief intact (or the draft restored).
- **Actual (derived):** neither.

## What settles it

Playwright on `/create/ppt` with a POST-only stub of `/api/runs` returning 503 (let `GET /api/runs` through). Finish the wizard, press Continue, then read the page text and
`sessionStorage` (`ppt.draft` and `ppt.pending` absent). Repeat on `/create/prototype`.

## Where the fix belongs

The message comes from the same seam as the root. For the draft: remove it only once the launch is accepted (the `.then` with a run id), or put it back in the refusal path.
Today it is consumed at `page.tsx:2568-2569` and `:2652-2653` so that the next fresh wizard starts empty (FIX-005); keep that behaviour for the success path.

## After [FIX-773](20261009-0952-FIX-773.md) (2026-10-09): still open

The message half is covered: a refused wizard launch now reaches the `.catch`, and the layout banner shows the backend text. The draft
half is not covered. `page.tsx` still removes `ppt.draft` / `prototype.draft` before the POST, so there is nothing to retry from.
`onStartPipeline` now resolves the run id or `null`, and that outcome can drive a "remove on accept, restore on refusal" fix.
