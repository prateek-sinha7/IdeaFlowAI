## What happened

ISS-290 proved 5 of the app's 8 global hooks carry one or more `compatible_agents`
ids in their `HOOK.md` frontmatter that do not exist in the live 94-agent
roster (`html-prototype-builder`, `prototype-polisher`, `ppt-slide-architect`,
`requirements-analyst`). That same array — unfiltered, unvalidated — is not
only rendered as display chips (ISS-290's reported symptom); it also feeds an
**exact-match suggestion filter** in two other consumers of the same
`useHooksCatalog()` hook:

- `frontend/src/components/workflow/composer/CanvasConfigRail.tsx:379` —
  `const suggestedHooks = HOOKS.filter((h) => h.compatible_agents.includes(agent.id)).slice(0, 3);`,
  rendered as the "Suggested hooks" panel in the composer canvas's per-agent
  config rail ("hooks" tab), gated on `suggestedHooks.length > 0`
  (`CanvasConfigRail.tsx:473-485`).
- `frontend/src/components/workflow/AgentsPopup.tsx:593` — the identical
  expression, rendered in the standalone Agent Capabilities modal's hooks tab.

Both do a plain `Array.includes(agent.id)` with **no fallback** for a stale or
absent match. Contrast the equivalent skills-suggestion filter,
`frontend/src/components/workflow/composer/AgentSkillsPicker.tsx:71`:
`(s) => !s.compatible_agents?.length || s.compatible_agents.includes(agent.id)`
— skills explicitly treat a non-matching/empty list as "compatible with
everything" (R-33, "the safety default... never an invisible filter",
per `backend/tests/unit/test_skills_catalog_compatible_agents.py`). The two
hooks call sites have no equivalent fallback: once the only ids in a hook's
list are stale, that hook can never again appear in "Suggested hooks" for
*any* currently-real agent, including whichever agent now performs the role
the stale id used to name.

## Root cause

Same upstream mechanism as [ISS-290](20260828-1720-ISS-290.md):
`backend/app/agents/hooks_catalog.py:103` —
`compatible_agents=list(metadata.get("compatible_agents", []))` — loads the
HOOK.md frontmatter array with zero cross-validation against
`agents.registry.get_all_agents_flat()` / `backend/agents/prompts/`.
`frontend/src/hooks/useHooksCatalog.ts:29` forwards it unchanged to every
consumer. `LibraryPage.tsx` (ISS-290) only *displays* the array, so the
consequence there is a trust/cosmetic one. `CanvasConfigRail.tsx:379` and
`AgentsPopup.tsx:593` *filter by* the array, so the same stale data has a
functional consequence: a currently-real agent that inherited a stale id's
role (e.g. whichever agent now does what `html-prototype-builder`,
`prototype-polisher` or `ppt-slide-architect` used to do — confirmed retired,
see `backend/app/api/runs.py:713`'s own comment about the retired
"requirements-analyst" agent) receives zero suggested hooks for that role,
silently.

## Expected vs actual

**Expected:** opening the "hooks" tab for a currently-real agent surfaces
every hook whose declared `compatible_agents` covers that agent's role.

**Actual (INFERRED — not reproduced live in the browser; derived from a direct
code trace of both filter call sites and the confirmed-stale id set from
ISS-290):** for any agent that now performs the role a stale id used to name,
`post-design-quality`, `stop-console-log`, `stop-format-typecheck`,
`session-start`, and `stop-session-end` cannot appear in "Suggested hooks" in
either `CanvasConfigRail` or `AgentsPopup`, because none of their
`compatible_agents` entries resolve to that agent's real id.

## What would confirm or refute this

Open the composer canvas, select the agent that currently performs
prototype-build/polish or ppt-slide-authoring duties (whatever id replaced
`html-prototype-builder` / `prototype-polisher` / `ppt-slide-architect`), open
its "hooks" tab, and check whether the corresponding hook(s) appear under
"Suggested hooks". Absence, for a hook whose own description matches that
agent's role, confirms this card; presence (e.g. if a *different*, still-valid
id in the same hook's list already happens to cover that agent) refutes it for
that specific hook.
