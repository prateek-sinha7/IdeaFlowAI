# ADR-0004: Declared order wins over inferred order

## Context and Problem Statement

Two mechanisms can order a run, and they read disjoint inputs:

| | source | mechanism |
| --- | --- | --- |
| **INFERRED** | `produces:` / `consumes:` in each `AGENT.md` | `WorkflowResolver.validate()` → `validation.dag` |
| **DECLARED** | `subagents:` nesting in `workflow.yaml` | `WorkflowCompiler` synthesizes `depends_on`, topo-sorts |

`engine.py` used the inferred one unconditionally:

```python
ordered_agents = validation.dag or list(agents)
```

The resolver orders agents by contracts declared in their own `AGENT.md`. Every node of
a composed workflow loads the *same* file — `custom-agent/AGENT.md`, a template that
declares no `produces` and no `consumes`. The resolver therefore sees N identical
contract-free agents and has nothing to order them by. It cannot recover
`emoji → fact → joke → page`, because that order was never written in any `AGENT.md`.

It is written in the nesting, which the compiler already reads, already validates against
R-17/R-19, and already topo-sorts into `depends_on` edges. That work was being discarded.

Note this is an **ordering** problem only. Satisfiability validation
(`engine.py:1661`, cycles and unsatisfied `consumes`) runs before this line and is
untouched — a composed workflow consuming an artifact nobody produces still halts.

## Considered Options

1. **Merge `depends_on` into the resolver's graph** as additional edges and topo-sort
   once, so there is a single ordering path with two edge sources.
2. **Branch on the presence of `depends_on`**: trust the compiler's order when the plan
   declares edges, otherwise keep the resolver's.
3. **Give template instances synthetic `produces`/`consumes`** derived from their
   `instance_id`, so the resolver can order them.

## Decision Outcome

**Option 2**, as the minimum change that unblocks spec 012:

```python
if any(getattr(s, "depends_on", None) for s in compiled.steps):
    ordered_agents = list(agents)      # already topo-sorted by the compiler
else:
    ordered_agents = validation.dag or list(agents)
```

Zero file-backed manifests declare `depends_on` today — verified by grep across all 18 —
so the new branch is currently reachable only by manifests whose compiler synthesizes it
from `subagents:`. Every existing pipeline keeps the resolver path byte-identical.

Option 3 was rejected outright: one contract cannot describe N differently-purposed
instances, and populating it would make the template actively wrong rather than merely
empty.

**Option 1 is the better end state and is explicitly deferred, not rejected.** It removes
the branch entirely, makes a hand-written `depends_on` *add* a constraint rather than
*replace* contract ordering, and is the direction ADR-0009 argues for. It was not taken
here because it changes the resolver, and the goal of this change was to unblock spec 012
without touching a component every pipeline depends on.

## Consequences

**Positive.** Composed workflows execute in the order their nesting declares. Existing
pipelines are untouched — the branch is unreachable for them today.

**Negative — the discriminator is unsafe.** `depends_on` is already a legal step key
(`compiler.py:97`, "forward surface... consumed Phase 6/7") with no schema restriction
tying it to compiler-synthesized composition. And the test is `any(...)`: **one** step
carrying an edge flips ordering for the **entire** plan, not just that step.

Three production pipelines have `validation.dag` order that differs from manifest order —
`app_builder`, `dotnet_to_azure`, `mulesoft_to_springboot`. Adding a single `depends_on:`
line to any of them silently reverts execution to manifest order, with no error and no
test that would catch it.

Both orders are contract-valid in those cases. In `app_builder`, `app-test-compliance`
consumes `[app-test-implementation, app-code-compliance, app-security-architecture]` and
`app-devops` consumes `[material-analyzer, app-infra-generator, app-code-generator]` —
neither consumes what the other produces, so there is no edge between them and two
linearizations are equally correct. The divergence is tie-break, not correctness. That
makes the silent revert harder to notice, not less real.

**Negative — the resolver's ordering output is computed and then discarded** on the
declared-order path, which wastes nothing measurable but does mean two orderings exist in
memory with no assertion that they agree.

## Confirmation

`tests/unit/test_workflow_resolver.py` covers the resolver in isolation and never reaches
this branch. `tests/agents/test_compiler_subagents.py` covers `depends_on` synthesis and
never reaches `execute()`. `tests/agents/test_sample_wave_workflow.py` is the only test
driving a `depends_on`-bearing plan end to end, and it asserts only that the run
completes — it would pass identically on either branch.

**No test exercises the one case where the branches differ**: a plan with `depends_on`
present AND a resolver DAG that diverges from declared order. Untested because no fixture
builds it.

**Required follow-up, not yet done:**

- A regression test pinning `validation.dag` order for `app_builder`, `dotnet_to_azure`
  and `mulesoft_to_springboot` against manifest order, asserting the known divergence.
  This is the guardrail that would catch an accidental future `depends_on`.
- Either scope the override to the connected component that has edges, or execute
  Option 1 and delete the branch.
- A manifest lint rejecting hand-authored `depends_on` until then.
