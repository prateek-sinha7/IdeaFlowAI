## Sibling of ISS-853, the inverse-direction divert case

ISS-853 covers the effect's `self`/`parent` reads (`:235`, `:243`). This is
the third branch of the same effect — the one that fires when `self` itself
has ALREADY diverted, and the effect needs to find what it diverted TO.

## What is wrong

`frontend/src/components/results/AgentThinkingTab.tsx:236-241`:

```tsx
if (self.status === "diverted") {
  const { runs } = await getWorkflows(token, { limit: 100 });
  if (cancelled) return;
  const child = runs.find((r) => r.parentRunId === runId);
  setDivertLink(child ? { direction: "source", otherRunId: child.id, otherTitle: labelFor(child.type, child.title) } : null);
}
```

A flat `GET /api/runs?limit=100` reverse scan for the one run whose
`parentRunId === runId`. Two problems, not one:

1. **Wasteful.** `getWorkflows` already has its own in-flight guard
   (`inFlightWorkflows`, `api.ts:904-921`, ISS-783/QA-PS-037) so a StrictMode
   double is merged into one call — but that one call is still a 100-row run
   list fetched solely to find one id, on every Steps-tab open of a
   diverted run.
2. **Fragile.** `limit: 100` with no ordering guarantee tied to
   `parentRunId` means a user with 100+ runs created since the divert can
   have the child silently fall out of the window — `child` becomes
   `undefined`, `setDivertLink(null)`, and the "Diverted to X" row silently
   disappears. Nothing here paginates or retries.

`backend/app/api/runs.py:1564-1603`'s `_owned_family_members` (the function
behind `GET /api/runs/{id}/family`, i.e. `runFamily`) already performs this
exact lookup correctly: a BFS DOWN from the family root over owned children,
with a code comment stating explicitly "a divert ... a cross-type child is
admitted" — so a diverted child IS a member of `runFamily.members`, findable
by the same `parent_run_id === runId` test, with no separate fetch and no
100-row ceiling (the BFS is unbounded and owner-scoped, not `LIMIT`-clamped).

## Why this is a sibling, not a duplicate

Same root-cause pattern as ISS-853 (fetch instead of reading `runFamily`,
which PreviewPanel already holds) — but the REVERSE direction of ISS-853's
`self.parentRunId` case: ISS-853 is "find my parent", this is "find the
child I diverted to". Different call (`getWorkflows`, not `getWorkflow`),
different failure mode (silent data loss past 100 runs, not just an extra
request).

## What would settle it

Reproduce a diverted run whose child is NOT among the account's most recent
100 runs (needs 100+ runs created after the divert) and confirm the
"Diverted to X" row is missing where `runFamily.members` would have found
it. Absent that live repro this is INFERRED from the two code paths above,
both read directly this pass.

## Suggested fix

Same shape as ISS-853's option (a): once `AgentThinkingTab` receives
`runFamily` (or the specific fields it needs) as a prop, replace the
`getWorkflows({limit:100})` scan with `runFamily.members.find(m =>
m.parent_run_id === runId)`. This removes the 100-run ceiling as a side
effect, since the family walk is not `LIMIT`-clamped.
