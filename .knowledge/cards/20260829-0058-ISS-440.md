# ISS-440

**Register source:** analyzer pass on `BUG-20260828-085400-runs-failed` in
`bug-hunter/ledger.md` (root card [ISS-317](20260828-1755-ISS-317.md)).

## Why the root cause implies this

[ISS-317](20260828-1755-ISS-317.md)'s reproduction used a run that was `failed` (drifted
to `cancelled`) before the resume. The underlying mechanism — `useWorkflow.ts`'s
`pipeline_start` merge carrying an agent's stale `status: "error"` forward across a resume
unconditionally (`:457-458`, traced fully in [ISS-438](20260829-0056-ISS-438.md)) — does
not care WHICH terminal state preceded the resume; it fires on `isSameRunReannounce`
alone, true for any resume of the same `run_id`. [ISS-237](20260828-1741-ISS-237.md)
already establishes that a **degraded** ("completed with issues") run is resumable
through the identical `handleResumeRun` seam via RunChatLane's "Run again" button
(`RunChatLane.tsx:1845-1867`), confirmed by the backend's own eligibility message:
`"only failed, degraded, or cancelled runs are resumable"`.

Critically, a degraded run's completion is exactly the shape this bug needs to
reproduce — it always ends with at least one agent carrying `status: "error"` by
construction:

```ts
// useWorkflow.ts:757-758, 770-778 (case "pipeline_complete")
const isDegraded = (msg.status as string) === "degraded";
const degradedFailedIds = isDegraded ? ((msg.agents_failed as string[]) || []) : [];
...
const updated = prev.agents.map((a) => {
  if (degradedFailedIds.includes(a.id)) {
    return a.status === "error"
      ? a
      : { ...a, status: "error" as const, error: a.error || "Agent failed (run degraded)", thinking: "" };
  }
  ...
```

So every degraded run, by definition, leaves `pipelineState.agents` with one or more
`status: "error"` entries — then "Run again" (`handleResumeRun` → `pipeline_start`)
carries them forward unreset via the same `:457-458` merge ISS-317/ISS-438/ISS-439
already trace. This is the same defect through a third, distinct entry point (a
different SOURCE terminal state, not just a different consumer component like ISS-438/
ISS-439), which is why it is filed separately rather than folded into ISS-317's own
`failed`-run reproduction.

## Expected vs actual (predicted, not yet observed)

- **Expected:** clicking "Run again" on a degraded run's detail page and watching the
  Steps panel while the resume is confirmed `generating` shows a state consistent with
  "Running", the same as any other resume.
- **Predicted actual:** identical to [ISS-317](20260828-1755-ISS-317.md)'s observed
  behaviour — the Steps panel (and, per [ISS-438](20260829-0056-ISS-438.md)/
  [ISS-439](20260829-0057-ISS-439.md), the chat lane pip and the agent detail view) stays
  pinned on the failed/error presentation for the `agents_failed` agent(s) until their own
  `agent_start` events land.

## Status

**INFERRED — not independently reproduced.** Derived from source on both ends (the
degraded-completion stamp at `useWorkflow.ts:770-778` and the resume merge at `:457-458`),
plus [ISS-237](20260828-1741-ISS-237.md)'s already-confirmed entry point, not from a
browser repro cycle. What would confirm it: seed or find a `degraded` run, click "Run
again" from its detail page, confirm `generating` via `GET /api/runs/{id}`, and repeat
[ISS-317](20260828-1755-ISS-317.md)'s observation protocol on the Steps panel.

## Fix

Same shared seam as [ISS-317](20260828-1755-ISS-317.md), [ISS-438](20260829-0056-ISS-438.md)
and [ISS-439](20260829-0057-ISS-439.md) — `useWorkflow.ts`'s `pipeline_start` merge
(`:457-458`). Fixing it there covers this entry point automatically; a fix scoped only to
the `failed`-run reproduction path would leave this `degraded`-run path (and any future
resumable terminal state) exposed to the identical carry-over.
