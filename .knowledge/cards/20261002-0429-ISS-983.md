# ISS-983

**INFERRED sibling of [ISS-919](20261001-2221-ISS-919.md) (QA-KB-059), derived by the analyzer on 2026-10-02.** Facet (a) was run offline; facets (b) and (c) were read and never driven. An unreproduced sibling is a lead, not a defect.

Line numbers are the working tree on 2026-10-02 (HEAD `024c03ef8`). `IdeaInputPage.tsx` carries uncommitted [FIX-702](20261002-0040-FIX-702.md) hunks, so its numbers sit about 24-33 above HEAD's. `AgentsPopup.tsx` is shared by `IdeaInputPage` and `LaunchWizard`.

## Condition

`/create/<type>` for a built-in that renders `IdeaInputPage` (`user_stories`, `app_builder`, ...). The user opens "Advanced" before `GET /api/workflows/<type>` has settled, and edits the roster there, or saves or hands off from the popup.

## Expected vs actual

- **Expected:** the "Advanced" trigger is disabled until the fetch has settled, exactly like the two page-level Save buttons in [ISS-919](20261001-2221-ISS-919.md), so every edit starts from the final roster. `LaunchWizard` has done this since [FIX-701](20261002-0037-FIX-701.md) (`LaunchWizard.tsx:914`, `rosterSettling`; its amendment 3: the popup's footer Save is a third Save button).
- **Actual:** `IdeaInputPage.tsx:2188-2189` is `<button onClick={() => setShowAgents(true)} ...>` with no `disabled`. The popup is handed `agents={pipelineAgents}` (`:2279`), the unsettled roster.

## Why the root cause implies it (each step read)

[ISS-919](20261001-2221-ISS-919.md)'s cause: the roster is published as authoritative from the first render and every consumer is enabled before the async source that decides it has landed. "Advanced" is one more consumer. Three consequences:

**(a) An in-window edit is silently replaced (OBSERVED OFFLINE).** The roster effect (`:1367-1437`) re-seeds `pipelineAgents` with `seeded` (`:1430-1434`) whenever `manifestAgents`, `showOverride` or `overrideAgents` change, and never reads the previous roster; the fetch's `.then` writes those at `:1193-1195` and `:1263`. Scratch run T4 (`evidence/qa-kb-059/03-analyze-scratch-run.txt`, source `01-analyze-scratch-IdeaInputPage.test.tsx.txt`): a stub popup that edits through the host's `onReorder` (the callback the real popup uses) shows 4 agents, 3 after an in-window "drop last", and 4 again once the detail resolves: `edit survived the late overlay: false`. For an override user the same `.then` also replaces the per-agent levers, `selectionsRef.current = proj.selections` (`:1196`) (read, not run).

**(b) A popup Cancel can put the library roster back AFTER the fetch settled (INFERRED, read).** `AgentsPopup` stages its Cancel snapshot at the FIRST edit (`AgentsPopup.tsx:2739-2741`) and Cancel re-applies it through `onReorder` (`:2770-2773`), which the host wires to `handleReorderAgents` (`IdeaInputPage.tsx:2290`), whose body is `setPipelineAgents(reordered)` (`:1870-1872`). Sequence: open in the window, the first edit snapshots the PRE-overlay (library) roster, the late overlay re-seeds the override roster, Cancel writes the library roster back into `pipelineAgents`. A fix that gates only the two Save buttons then has "Save as my version" enabled on the library roster: the gate is bypassed. The popup is keyed on `manifestSelections` (`:2254`) and would remount, dropping the snapshot, if that flipped; but `user_stories` declares `gates: []` on all six steps (`backend/agents/workflows/user_stories/workflow.yaml:65-85`) and `:1259`/`:1262` leave `manifestSelections` undefined when no step declares a gate, so on the bug's own route the popup does NOT remount. Workflows whose manifest does declare gates were not checked.

**(c) The popup's own save and hand-off persist the unsettled roster (INFERRED, read).** The footer "Save workflow" (`AgentsPopup.tsx:3029-3044`, calling `handleSaveWorkflow` `:2783-2820`, `agent_ids: agents.map(...)` `:2801`) and "Open in full canvas" (`IdeaInputPage.tsx:2257-2278`: `agentIds: pipelineAgents.map(...)`, `manifestSteps: manifestRawSteps`, still `undefined` in the window) both carry the unsettled roster. Neither can UPSERT an override: `overrides_pipeline_type` is sent from exactly two places, `IdeaInputPage.tsx:1804` and `LaunchWizard.tsx:987` (`evidence/qa-kb-059/04-analyze-code-quotes.txt`, section 10). The harm is a new saved row, or a canvas seeded from the wrong roster, not the override loss in [ISS-919](20261001-2221-ISS-919.md).

## Where the fix belongs

The same state ISS-919's fix adds, in the same component: `disabled` on the trigger at `:2188` while the fetch is loading. Not in `AgentsPopup` (shared by both hosts; the [FIX-701](20261002-0037-FIX-701.md) card records the same reasoning). It should ride with ISS-919's fix, because gating only the two Save buttons leaves (b) as a bypass.

## For the test-writer

Offline, one file at a time. The harness is proven in `evidence/qa-kb-059/01-analyze-scratch-IdeaInputPage.test.tsx.txt` (T1 reads the trigger: today `advanced.disabled=false advancedLabel="Advanced4 agents · ~4m"`). Assert the trigger is disabled while the detail is pending and enabled after it resolves or rejects. Once the trigger is gated the in-window edit cannot be made at all, so (a) becomes a guard on the disabled trigger; (b) and (c) need the real popup, so assert them through the trigger, not through `AgentsPopup`.
