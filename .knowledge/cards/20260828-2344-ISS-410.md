## Source

## What is suspected

[ISS-334](20260828-2045-ISS-334.md) already showed that the cold-mount effect seeding the canvas
composer swallows a REAL workflow's transient fetch failure identically to a dead link, and traced
that shared precondition into [ISS-234](20260828-1628-ISS-234.md)'s Run once/9-agent-substitution
consequence. The same precondition reaches [ISS-299](20260828-1730-ISS-299.md)'s Save as copy
consequence just as directly, because both consequences are gated by the same swallow, not by
which button the user happens to click:

```ts
// frontend/src/app/[...view]/page.tsx:452-499
useEffect(() => {
  if (!isAuthenticated || !builtinCanvasType) return;
  ...
  try {
    const detail = await getWorkflowDetail(jwt, builtinCanvasType);
    ...
    setInitialSavedComposition({ ... });   // NO `id` — this is what puts the
                                            // composer in copy-only mode
  } catch {
    if (!cancelled) setInitialSavedComposition(null);
  }
  ...
}, [isAuthenticated, builtinCanvasType]);
```

The `catch` at lines 494-496 is unconditional — it does not inspect the thrown error at all, unlike
this SAME file's sibling cold-mount effect for `/workflows/{id}/edit`
(`workflowEditAccessDenied`, set only `if (err instanceof ApiError && (err.status === 403 ||
err.status === 404))`, `page.tsx:3506-3520`). `builtinCanvasType` itself is just the raw URL
segment (`builtinCanvasTypeFor`, `page.tsx:345-347`), so this effect cannot tell "this workflow
does not exist" apart from "this fetch failed for some other reason" — both collapse to the
identical `initialSavedComposition = null`.

Downstream, `ComposerPage`'s header (`` `${initialName || builtinCanvasType} · copy` ``,
`ComposerPage.tsx:1020`) and Save-button label (`"Save as copy"`, `ComposerPage.tsx:1135`) key off
the mere presence of `builtinCanvasType`, and the Save button's `disabled` state
(`ComposerPage.tsx:1116`, `disabled={saving}`) plus its `onClick` (`ComposerPage.tsx:1106-1115`,
name-empty guard only) never reference whether the manifest fetch actually succeeded — the same
absent existence gate [ISS-299](20260828-1730-ISS-299.md) already proved lets a dead-link save
complete. A **real, existing** built-in whose `GET /api/workflows/{id}` merely times out, 500s, or
is interrupted mid-request lands in the exact same `initialSavedComposition = null` / no
`userWorkflowId` state, so `handleSave` (`ComposerPage.tsx:663-762`) has nothing to PATCH and
mints a brand-new `POST /api/user-workflows` row via `saveUserWorkflow` — for a workflow that was
never dead.

## Condition

Load `/workflows/{id}/canvas` for an id that genuinely exists, at a moment `GET
/api/workflows/{id}` fails for any reason other than "not found" (network interruption, a
transient 5xx, a timeout) — then type a workflow name and click "Save as copy" before the fetch
has a chance to succeed on a retry.

## Expected vs actual

**Expected:** a transient fetch failure is distinguished from "no such workflow" (retried, or
surfaced as an explicit error/retry state) — and in neither case should "Save as copy" be
reachable while the source manifest is unresolved.

**Actual (predicted):** the identical unwanted-persisted-workflow outcome
[ISS-299](20260828-1730-ISS-299.md) documents for a dead link, triggered instead by ordinary fetch
flakiness against a workflow that is not dead at all — a fix scoped narrowly to "detect a 404 and
render not-found" would close ISS-299's reported path but leave this trigger, and this exact
consequence, unaddressed.

## Why the root cause implies this

[ISS-299](20260828-1730-ISS-299.md) and [ISS-334](20260828-2045-ISS-334.md) already established
that `page.tsx:494-496`'s catch cannot distinguish "this workflow does not exist" from "this fetch
failed for some other reason" — both collapse to the identical `initialSavedComposition = null`.
ISS-334 traced that ambiguity into the Run once/9-agent-substitution consequence for a real
workflow; this card is the same trace applied to the OTHER consequence the identical swallow
already produces on a dead link — Save as copy's unwanted persisted row. Both are properties of
the one unconditional catch, not of which affordance the user happens to use, so a fix that only
recognizes a genuine 403/404 (closing ISS-299's and ISS-234's reported paths, mirroring the
existing `workflowEditAccessDenied` pattern) would correctly leave a REAL workflow's transient
failure free to retry/degrade gracefully instead of masquerading as either "not found" or "start a
blank copy" — but until such a fix exists, this card records that the Save-as-copy trigger is not
"a dead link," it is "this catch ever firing for `workflow-canvas`," which is a strictly larger
set of conditions than ISS-299 alone reproduced.

**Marked INFERRED**: not reproduced this session — confirmed only by reading the unconditional
catch, the composer's copy-mode header/Save-button/`handleSave` logic (all keyed on
`builtinCanvasType`'s mere presence, none on fetch success), and tracing them into the same
`POST /api/user-workflows` path [ISS-299](20260828-1730-ISS-299.md) already proved returns `201
Created`. What would confirm it: force `GET /api/workflows/<real-id>` to fail transiently
(throttle/abort) for an id that exists, load `/workflows/<that-id>/canvas`, type a name, add an
agent, click "Save as copy", and check `GET /api/user-workflows` for the new duplicate row. What
would refute it: if `getWorkflowDetail` retries internally before this effect ever observes a
transient failure (not seen in the code read — same caveat ISS-334 already notes).

### ROOT CAUSE (CONFIRMED)

One mechanism made of three facts, all read on the current tree:

1. **page.tsx folds three states into one nullable value.**
   `useState<SavedComposition | null>(null)` (`page.tsx:441`) is `null` while the fetch is in flight,
   and the catch resolves every non-403/404 failure (5xx, timeout `ApiError(0)`, a raw network
   `TypeError`) to the same `setInitialSavedComposition(null)` (`page.tsx:553-555`, `:561-563`).
   "Loading", "failed" and "blank by design" are indistinguishable downstream. Unlike
   `/workflows/{id}` (`:4077-4085`) and `/workflows/{id}/run` (`:4120-4126`), the canvas route has no
   loading `return null` gate, so DashboardLayout and ComposerPage mount straight onto that `null`
   (`workflow-canvas` maps to "composer", `page.tsx:161-162`; only the denied flag is gated,
   `:4068-4070`).
2. **The conduit cannot repair it.** DashboardLayout copies a seed in only when it is non-null
   (`if (initialSavedComposition) { setSavedComposition(...) }`, `DashboardLayout.tsx:1553-1557`), and
   ComposerPage's key `savedComposition?.id ?? "new"` (`DashboardLayout.tsx:3212`) never changes for a
   built-in, which has no `id` by design ([ADR-0014](20260824-1630-ADR-0014.md)). So the composer is
   never remounted, in either direction.
3. **ComposerPage keys copy-mode on the URL, not on the seed.** The header (`:1261`) and the
   "Save as copy" label (`:1406`) read only `builtinCanvasType`; the button is `disabled={saving}`
   (`:1387`); `handleSave` guards only detached steps and auth (`:850-870`) and posts
   `agent_ids: pipelineAgents.map(a => a.id)` plus a full manifest (`needsFullManifestOnSave` is true
   whenever `builtinCanvasType` is set, `:104-116`) built from `runConfig`, which defaults to
   `DEFAULT_RUN_CONFIG` when `initialRunConfig` never arrived (`:450-452`). `handleSave` has exactly
   ONE call site, the button (`:1385`; `grep -n "handleSave\b" ComposerPage.tsx` returns the
   definition, comments and that line only).

| seed state | `initialSavedComposition` | today | after the agreed fix |
|---|---|---|---|
| loading (in flight) | `null` | live composer "ppt · copy", Save as copy enabled | Save disabled until the seed lands |
| **transient failure (5xx / timeout / network)** | `null` (`:555`) | identical to loading, forever | Save disabled, forever (tooltip only) |
| dead id (403/404) | `null` + `builtinCanvasAccessDenied` | not-found page (FIX-368) | unchanged |
| loaded | non-null, no `id` | seeded composer, Save as copy | enabled |

**Settled caveat from the original card:** "what would refute it: if `getWorkflowDetail` retries
internally". It does not. `getWorkflowDetail` only dedupes in-flight calls
(`frontend/src/lib/api.ts:2415-2440`) and `fetchWithAuth` replays once, on 401 only (`api.ts:536-566`).

### What actually reaches the server

- **Zero agents** (what the validator hit): `POST /api/user-workflows` with
  `agent_ids: []` is a 422, `agent_ids: list[str] = Field(min_length=1)`
  (`backend/app/api/user_workflows.py:213`). That schema rule is the ONLY thing between the click and
  a write; the page shows the backend's validation text through `saveError` (`:972-973`), which says
  nothing about the workflow having failed to load. CONFIRMED (validator, 3 attempts).
- **One or more hand-added agents** (the "unwanted duplicate" path): a manifest-bearing POST skips
  the allow-list (`user_workflows.py:719`), passes name uniqueness (409 only on an identical name,
  `:836-840`) and creates a `base_pipeline_type: "custom"` row holding the hand-built roster and the
  default `streamed_text` / `output.md` deliverable. INFERRED (not run: a 201 would persist data, and
  the validator aborted the POST); it is the same wrong-deliverable "copy" [ISS-196](20260828-1555-ISS-196.md)
  reported for `ppt`, reachable here with no bad URL. `evidence/qa-kb-018/06-validate-attempt3-named-save-as-copy-enabled.png`
  shows the state: header "PPT · COPY", 0 agents, an empty canvas, deliverable "Streamed text",

- **Tier:** the write also passes an entitlement gate (`can_run_pipeline`, commented "custom needs
  enterprise", `user_workflows.py:692-706`), so a lower tier presumably gets a 403 banner on the
  same click (INFERRED, not run). The live button is tier-independent.

### Fix: accept the agreed minimal fix

The two independent reviewers' fix stands: in `ComposerPage.tsx:1387` change `disabled={saving}` to
`disabled={saving || (!!builtinCanvasType && !initialManifestSteps?.length && !initialAgentIds?.length)}`.
Verified against the code, not just agreed with:

- **Right place.** ComposerPage is the single Save sink and `handleSave` has one call site, so a
  button gate closes every present path. The existence gate stays in page.tsx (FIX-368's locked
  constraint); this is a different question, "has the seed arrived", and belongs where the Save is.
- **Sound predicate.** `GET /api/workflows/{id}` mirrors `compiled.steps` and `manifest.steps`
  (`backend/app/api/workflows.py:476-529`), so a loaded built-in always has at least one step and
  the gate can never lock a healthy canvas. The seed arrives as props
  (`initialManifestSteps` / `initialAgentIds`, `DashboardLayout.tsx:3229-3236`), so the gate releases
  itself when it lands; no remount is needed.
- **SC-001-safe.** It tests `builtinCanvasType` truthiness, never a workflow name.
- **No test breaks.** Every existing built-in Save-as-copy test seeds `initialManifestSteps` first
  (`ComposerPage.manifestPersistence.test.tsx:88-191`).
- **Do NOT copy IdeaInputPage's predicate** (`pipelineAgents.length === 0`). On a failed canvas
  that re-enables Save the moment the user hand-adds one agent, which is the unwanted-copy path.
  The props-based predicate keeps it blocked.

Optional refinements, the fixer's call:

1. Derive it once (`const seedUnresolved = ...`) and reuse it for `disabled` and `title`. Keep the
   existing "Name the workflow first" title first; then something like "This workflow has not
   loaded. Reload the page to retry." Per the agreed scope there is no error UI and no retry in
   page.tsx.
2. If a guard is ALSO added inside `handleSave`, it must sit BEFORE `isSavingRef.current = true`
   (`:839-840`) or release it on the early return. (Precedent for guarding both places: Run once keeps
   its empty-roster guard in the handler and on the button, `:1007-1012` and `:1335-1338`, and the
   comment at `:1013-1019` says why: the Simple-view brief's Cmd/Ctrl+Enter shortcut bypasses the
   button. For Save there is no second entry point today.) The detached and auth guards do exactly that (`:862`, `:868`) because
   leaving it set once made every later Save a silent no-op (comment at `:857-861`).
3. Verifier: after the fix, Save as copy is DISABLED under the abort. Playwright `click()` on a
   disabled element waits for enablement and times out, so assert `isDisabled()` and zero
   `POST /api/user-workflows` instead of clicking.

Not a substitute: widening `builtinCanvasAccessDenied` to transient failures (turns a blip into a
permanent 404, FIX-368's locked constraint); a retry inside `getWorkflowDetail` (hides the failure
without gating Save during the retry window); giving the failed seed an `id` or switching to PATCH
([ADR-0014](20260824-1630-ADR-0014.md): a file-backed manifest has no row behind it). If page.tsx is
touched, keep all five narrowed-catch sites (`workflowDetailCatch.source.test.ts` asserts a floor of 5).
