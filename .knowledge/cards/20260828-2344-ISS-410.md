## What is suspected

[ISS-334](20260828-2045-ISS-334.md) already showed that the cold-mount effect seeding the canvas
composer swallows a REAL workflow's transient fetch failure identically to a dead link, and traced
that shared precondition into [ISS-234](20260828-1628-ISS-234.md)'s Run once/9-agent-substitution
consequence. The same precondition reaches [ISS-299](20260828-1730-ISS-299.md)'s Save as copy
consequence just as directly, because both consequences are gated by the same swallow, not by
which button the user happens to click:

```ts
// frontend/src/app/[...view]/page.tsx:452-499
useEffect(() => {
  if (!isAuthenticated || !builtinCanvasType) return;
  ...
  try {
    const detail = await getWorkflowDetail(jwt, builtinCanvasType);
    ...
    setInitialSavedComposition({ ... });   // NO `id` — this is what puts the
                                            // composer in copy-only mode
  } catch {
    if (!cancelled) setInitialSavedComposition(null);
  }
  ...
}, [isAuthenticated, builtinCanvasType]);
```

The `catch` at lines 494-496 is unconditional — it does not inspect the thrown error at all, unlike
this SAME file's sibling cold-mount effect for `/workflows/{id}/edit`
(`workflowEditAccessDenied`, set only `if (err instanceof ApiError && (err.status === 403 ||
err.status === 404))`, `page.tsx:3506-3520`). `builtinCanvasType` itself is just the raw URL
segment (`builtinCanvasTypeFor`, `page.tsx:345-347`), so this effect cannot tell "this workflow
does not exist" apart from "this fetch failed for some other reason" — both collapse to the
identical `initialSavedComposition = null`.

Downstream, `ComposerPage`'s header (`` `${initialName || builtinCanvasType} · copy` ``,
`ComposerPage.tsx:1020`) and Save-button label (`"Save as copy"`, `ComposerPage.tsx:1135`) key off
the mere presence of `builtinCanvasType`, and the Save button's `disabled` state
(`ComposerPage.tsx:1116`, `disabled={saving}`) plus its `onClick` (`ComposerPage.tsx:1106-1115`,
name-empty guard only) never reference whether the manifest fetch actually succeeded — the same
absent existence gate [ISS-299](20260828-1730-ISS-299.md) already proved lets a dead-link save
complete. A **real, existing** built-in whose `GET /api/workflows/{id}` merely times out, 500s, or
is interrupted mid-request lands in the exact same `initialSavedComposition = null` / no
`userWorkflowId` state, so `handleSave` (`ComposerPage.tsx:663-762`) has nothing to PATCH and
mints a brand-new `POST /api/user-workflows` row via `saveUserWorkflow` — for a workflow that was
never dead.

## Condition

Load `/workflows/{id}/canvas` for an id that genuinely exists, at a moment `GET
/api/workflows/{id}` fails for any reason other than "not found" (network interruption, a
transient 5xx, a timeout) — then type a workflow name and click "Save as copy" before the fetch
has a chance to succeed on a retry.

## Expected vs actual

**Expected:** a transient fetch failure is distinguished from "no such workflow" (retried, or
surfaced as an explicit error/retry state) — and in neither case should "Save as copy" be
reachable while the source manifest is unresolved.

**Actual (predicted):** the identical unwanted-persisted-workflow outcome
[ISS-299](20260828-1730-ISS-299.md) documents for a dead link, triggered instead by ordinary fetch
flakiness against a workflow that is not dead at all — a fix scoped narrowly to "detect a 404 and
render not-found" would close ISS-299's reported path but leave this trigger, and this exact
consequence, unaddressed.

## Why the root cause implies this

[ISS-299](20260828-1730-ISS-299.md) and [ISS-334](20260828-2045-ISS-334.md) already established
that `page.tsx:494-496`'s catch cannot distinguish "this workflow does not exist" from "this fetch
failed for some other reason" — both collapse to the identical `initialSavedComposition = null`.
ISS-334 traced that ambiguity into the Run once/9-agent-substitution consequence for a real
workflow; this card is the same trace applied to the OTHER consequence the identical swallow
already produces on a dead link — Save as copy's unwanted persisted row. Both are properties of
the one unconditional catch, not of which affordance the user happens to use, so a fix that only
recognizes a genuine 403/404 (closing ISS-299's and ISS-234's reported paths, mirroring the
existing `workflowEditAccessDenied` pattern) would correctly leave a REAL workflow's transient
failure free to retry/degrade gracefully instead of masquerading as either "not found" or "start a
blank copy" — but until such a fix exists, this card records that the Save-as-copy trigger is not
"a dead link," it is "this catch ever firing for `workflow-canvas`," which is a strictly larger
set of conditions than ISS-299 alone reproduced.

**Marked INFERRED**: not reproduced this session — confirmed only by reading the unconditional
catch, the composer's copy-mode header/Save-button/`handleSave` logic (all keyed on
`builtinCanvasType`'s mere presence, none on fetch success), and tracing them into the same
`POST /api/user-workflows` path [ISS-299](20260828-1730-ISS-299.md) already proved returns `201
Created`. What would confirm it: force `GET /api/workflows/<real-id>` to fail transiently
(throttle/abort) for an id that exists, load `/workflows/<that-id>/canvas`, type a name, add an
agent, click "Save as copy", and check `GET /api/user-workflows` for the new duplicate row. What
would refute it: if `getWorkflowDetail` retries internally before this effect ever observes a
transient failure (not seen in the code read — same caveat ISS-334 already notes).
