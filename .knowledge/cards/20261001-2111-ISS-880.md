# ISS-880

## Description

INFERRED sibling of [ISS-160](20260813-1300-ISS-160.md) (QA-KB-009). The three entry points that mint a revision child row through `_mint_revision_row` do not agree on how the pipeline tier is chosen for a prototype-family parent:

| entry point | location | tier selection |
|---|---|---|
| REST `POST /{id}/revisions` (`create_revision`) | `run_commands.py:5598-5630` | `_classify_revision_tier` (one LLM call) when the target is `prototype_output` or `prototype_v2_output` |
| Concierge disposal (`_dispose_concierge_proposal`) | `run_commands.py:1685-1710` | the same classifier |
| Chat-turn revision (`CHANNEL_REVISION` in `post_message`) | `run_commands.py:2010-2053` | none: the fallback target goes straight to `_mint_revision_row` |

CONFIRMED by an offline probe through the real `POST /api/runs/{id}/messages` endpoint (`env` fixture of `backend/tests/integration/api/test_chat_messages_endpoint_api.py`, `_drive_revision_to_queue` stubbed, `_classify_revision_tier` replaced by a counting stub that answers "large"): a `prototype` parent minted `prototype_revision` and a `prototype_v2` parent minted `prototype_v2_revision`, with 0 classifier calls. The tiers `prototype_large_revision`, `prototype_feature_revision` and `prototype_v2_feature_revision` (Depth) are unreachable from this channel.

## Why the root cause implies it

Same structural cause as ISS-160: the revision target and tier are resolved by hand, separately, at each entry point. The disposal path's own comment names the failure class: "the same revision succeeded from chat and failed from REST ... both entry points agree by construction" (`run_commands.py:1649-1657`). The `CHANNEL_REVISION` comment calls itself "the exact seam POST /{id}/revisions uses" (`run_commands.py:2015-2016`), but in the other two callers the classification runs BEFORE that seam, so this channel silently loses it.

## Consequence for the ISS-160 fix

Today a `prototype_large_revision`, `prototype_feature_revision` or `prototype_v2_feature_revision` parent fails outright on this channel (HTTP 400 `revision_unsupported`). After the agreed minimal fix those parents succeed, but their base is `prototype` / `prototype_v2`, so the child lands on `prototype_revision` / `prototype_v2_revision` (the smallest tier), even when the parent was a Depth run. The fixer should expect this and the test-writer should not pin a tier for those parents.

## What is not established

INFERRED, not demonstrated: whether the smallest tier is a quality problem for users, and whether the chat-turn channel is meant to be free of model calls. `chat_router.py:193` documents that `route_chat_turn` (the router) makes zero model calls, which is not the same statement as the endpoint that executes the dispatch making none. `_require_host_capacity` already gates this channel as new agent work (`run_commands.py:2014`).

## Decision needed

Either (a) accept and document that chat-turn revisions always use the smallest tier, or (b) run the same classification here. For (b), factor the "base type, target and tier" resolution into the helper ISS-160 introduces rather than pasting a third copy of the classification block.

## TEST COVERAGE - ISS-880

Not fixed, no test added. The probe was a scratch script (not committed).

## Fixer note (QA-KB-009, 2026-10-01): left open, product decision

Not fixed by [FIX-684](20261001-2129-FIX-684.md), deliberately. Since that fix, the consequence predicted above is live: on `CHANNEL_REVISION`, `prototype_large_revision` and `prototype_feature_revision` parents mint `prototype_revision`, and a `prototype_v2_feature_revision` (Depth) parent mints `prototype_v2_revision` (Fast), all without classification. Option (b) is not a mechanical fix, for three reasons:

- `_classify_revision_tier` makes a paid model call: `llm = build_model(model_id, max_tokens=256, disable_thinking=True)` then `await llm.ainvoke(...)` (`backend/app/api/run_commands.py`, inside `_classify_revision_tier`). The chat-turn channel makes no model call before minting today.
- With no parent `output` it returns `"large"` without calling the model (its comment: `Default to "large" (safer than "small" for an unknown request).`), so (b) would also move output-less prototype parents from the smallest tier to the large one.
- Intent is not recorded. The commit that added the classifier, `5ef66c6fa` (2026-08-20), scopes it to "(Concierge path + REST path)" and says nothing about `CHANNEL_REVISION`.

The decision belongs to the product owner: (a) document that chat-turn revisions use the smallest tier, or (b) classify here too. For (b), put the classification in one shared step after `_revision_base_type`, not a third copy. Test note: the parametrized `test_revision_of_revision_run_parent_mints_child` carries an ISS-880 marker but asserts only that a child is minted, not its tier, so its XPASS is not evidence for this card.
