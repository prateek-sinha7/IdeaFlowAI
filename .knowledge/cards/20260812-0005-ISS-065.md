# ISS-065

## Title

No UI surfaces PER-ARTIFACT versions inside a run. `artifact_refs` durably stores every version (run `d5dbc9f2` holds spec v1/v2/v3, task_list v1/v2, summary v1/v2) and `GET /api/runs/{id}/artifacts` already returns `version` per node, but the only FE caller is `WorkflowHistory.tsx:303`, hard-coded to `kind="clarifications"`. The "Version v1 ▾" chip users DO see is a different axis — the whole-RUN family via `getRunFamily()` (`parent_run_id`), so three in-run revision cycles change it not at all (verified live: `/family` returned 0 members, no `v2`/`v3` anywhere on the run screen). **This invisibility is why FIX-217 shipped undetected** — a spec was silently rewritten and nothing on screen said so. Data, API and the Concierge's `list_refs`/`get_ref` tools all already exist; this is wiring on an axis that is already there. Do NOT reuse the existing "Version" chip — two meanings on one control is what made this confusing. **CORRECTION (2026-08-12):** `/family` returns **1** member for `d5dbc9f2`, not 0 — itself, `revision_index: 1`, `parent_run_id: null`. That makes the point *worse*, not weaker: `RunHeader.tsx:62` hides the menu only below 1 member, so the "Version v1" chip DOES render, with a single option, while the spec is rewritten three times underneath — a control that actively teaches the wrong lesson. **Closed by a new `ArtifactVersionPicker` in the Steps L2 detail**, frontend-only: `?kind=X&include=content` already returns every version WITH its body, so no endpoint and no migration were needed. The "do NOT reuse the Version chip" instruction was honoured and is now backed by evidence — locked decision D2 (`IMPLEMENTATION-REGISTER.md:2531`) defines that chip's version as the family chronological index and says in terms it is NOT `artifact_refs.version`, and `handleSelectVersion` calls `getWorkflow(memberId)`, so feeding it an artifact-ref id would 404 into a dead control and corrupt the state behind FilesTab and StartingPointCard.
