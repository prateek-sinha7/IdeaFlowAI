## Decision

`agents/model_policy.py` keeps a process-local `_PROVEN_MODELS` set. A model id
joins it the moment a call on that id yields its first stream event —
`DeepAgentRunner.astream_events` calls `mark_model_proven(self.model_id)` inside
the `async for`, before `yielded_any` flips.

`_is_transient_throttle` gained an optional second parameter. When a permanent
error code arrives for a model that is already in that set, and the code is in
`_PROVABLY_TRANSIENT_CODES_CF` (today: `resourcenotfoundexception` alone), the
verdict flips to transient.

The reasoning is a plain contradiction: a permanent code means *genuinely our
fault* — a bad ARN, bad auth, bad input. That is true for an ARN that never
resolved. It is false for one that served traffic minutes ago in this same
process.

## Why the incident cost the whole step

Bedrock intermittently answers `ConverseStream` with

    ResourceNotFoundException: Inference Profile ARN not found

for a profile that is demonstrably present. Run `353bb0af` lost `pb-validate`
that way on `eu.anthropic.claude-sonnet-4-6` **after `pb-spec` and `pb-design`
had just completed on the SAME id**, and a direct probe seconds later returned
OK. Stream vs non-stream, tool use and a 310 KB payload were all ruled out.

The step died with no retry and no fallback, because this one predicate gates
three independent defences:

- the runner's same-model retry loop (`_MAX_MODEL_CALL_ATTEMPTS` attempts with
  backoff) — it only ever sees an exception that the re-raise below let out;
- the runner's re-raise at `deep_agent_runner.py:1291`, which is the ONLY thing
  that hands a model fault to the engine (`_astream_events_once` swallows
  everything else into an `{"type":"error"}` event);
- the engine's model-fallback chain in `_run_agent`.

That coupling is invisible from a manifest and from the function's own
docstring. A `retry:` or `fallback:` block would have changed nothing — both sit
downstream of this verdict.

## The narrowing, which must not be widened

Four deliberate limits, each with a test:

- **Only resource lookup flips.** `AccessDeniedException`,
  `ValidationException`, `UnrecognizedClientException`, `ExpiredTokenException`
  stay permanent forever. Proving a model must never launder a real
  configuration fault into a retry.
- **Proof is per model id.** Proving one id says nothing about another.
- **An unproven model still fails fast.** A genuinely wrong ARN is caught on the
  first call rather than burning three attempts.
- **Single-argument callers keep the old verdict.** Nothing else in the tree
  changed behaviour.

## What this did NOT re-arm — read before assuming a fallback fires

Only the runner's re-raise site passes a `model_id`. Both engine call sites
still classify with one argument:

- `engine.py:9396` — the model-fallback chain in `_run_agent`
- `engine.py:13026` — the declarative `step.retry` loop

So a proven-model `ResourceNotFoundException` that survives the runner's
same-model retries propagates to the engine, is classified **permanent** there,
and re-raises instead of advancing the fallback chain. What the change actually
buys is the runner's own same-model retry (which only engages when the fault
lands before the first token — exactly the shape of this Bedrock failure).
Threading `model_id` into those two engine sites is the open follow-up, not
something already done.
