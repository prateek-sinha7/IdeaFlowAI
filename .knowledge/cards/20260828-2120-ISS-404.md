## What happened

Root card for `BUG-20260828-032424-settings-security` (`bug-hunter/ledger.md`). On
`/settings/security` (rendered by `SecuritySection.tsx`, mounted as a tab of
`AccountSettings.tsx`), a break-glass/local account (e.g. `qa-admin`) sees:

> **Not available for this account**
> This account's credentials are managed outside the application, so two-factor
> authentication is configured separately.

That claim is false for this account. Its password is stored, verified and rewritten
entirely inside this application's own database.

## Root cause (CONFIRMED)

`frontend/src/components/settings/SecuritySection.tsx:233-243` — the `SecurityPanel`
component's `if (!status.supported)` branch renders the fixed "managed outside the
application" paragraph (lines 236-239) whenever the MFA-status API reports
`supported: false`. The comment immediately above the branch (lines 231-232) already
states the real reason correctly — `"A break-glass/local account has no Cognito
factors to manage. Say so plainly instead of rendering controls that would 501."` —
but the JSX text below it does not say that; it says something else, and something
false.

`status.supported` is populated from `GET /api/auth/mfa`
(`backend/app/api/auth.py:906-948`, `get_mfa_status`), whose docstring states plainly
(auth.py:912-914): *"Returns 200 with `supported=false` for a non-Cognito (break-glass)
account rather than an error."* The only branch that sets `supported=False` is
`auth.py:925-933`: `if user.auth_provider != "cognito": return
MfaStatusResponse(..., supported=False)`. `auth_provider` (`backend/app/models/user.py:55-57`)
takes exactly two values, `"cognito"` or `"local"` (default) — so today, `supported=false`
means break-glass/local and nothing else; there is no third, genuinely-external account
type in this codebase.

For that exact account type, this application IS the credential store:
`password_hash` (`backend/app/models/user.py:28-33`) is a column directly on the app's
own `User` row — *"Non-null ONLY for the single break-glass local-admin account
(auth_provider == 'local')"* — and `POST /api/auth/change-password`'s `local` branch
(`auth.py:1254-1269`) verifies `request.current_password` against that column and
writes the new bcrypt hash back into it, inside this application's own database, with
no external system involved. The `/settings/profile` tab's own "Change Password" form
calls exactly this endpoint for this exact account.

**Contributing factor (CONFIRMED, not the primary defect):** `MfaStatusResponse`
(`backend/app/models/schemas.py:80-98`) carries only a boolean `supported` field — no
reason code or `auth_provider` echo — so the frontend has no per-response signal to
build accurate copy from; it hardcodes one blanket explanation for the single boolean.
This does not excuse the copy (the comment two lines above it already knows the right
reason), but it is why a future genuinely-external-IdP account type would need a
richer response, not just a copy fix.

  defect, not (yet) a user-visible one — noted for triage/severity, not to excuse it.

## Fix — what changes, and where

Two independent, surgical copy corrections. No shared function covers both: the two
sites are cross-tier (a React JSX branch vs. a Python `HTTPException` `detail`
string) and share no code path today.

- `SecuritySection.tsx`'s `!status.supported` branch (~lines 233-243): replace the
  "managed outside the application" paragraph with copy that matches the comment
  directly above it — a local/break-glass account simply has no Cognito MFA factors
  to manage, not that a third party manages its credentials.
- `admin.py`'s `user.auth_provider != "cognito"` branch in `reset_user_password`
  (~lines 553-564): reword the 409 `detail` to state the actual constraint — this
  specific Cognito-admin-reset action cannot act on a break-glass account; the
  account's password changes through the local self-service path
  (`/settings/profile` → `POST /change-password`) or an out-of-band runbook instead —
  without claiming the credential itself lives outside the application.

If a genuinely external-IdP account type is ever added, `MfaStatusResponse` would
need a reason/provider field so the frontend stops re-guessing from one boolean.
Flagged only — no such account type exists today, so this is not part of the
minimal fix.
