## What is suspected

[ISS-234](20260828-1628-ISS-234.md) confirmed the mechanism: `ComposerPage.handleRunOnce`
(`frontend/src/components/workflow/composer/ComposerPage.tsx:786-944`) computes
`currentIds = pipelineAgents.map((a) => a.id)` (line 920) and, whenever the composer isn't an
`unmodifiedBuiltin`, dispatches `onRun(dispatchType, brief, currentIds, extraParams)`
unconditionally (line 939) — with **no check anywhere that `pipelineAgents.length > 0`** before
that call. ISS-234 reached `pipelineAgents = []` via the dead-link `/workflows/<bad-id>/canvas`
404 path specifically. Reading the same file shows that precondition is not unique to a dead
link — it is the **documented default state of a brand-new composition**:

```ts
// ComposerPage.tsx:275-280
// A brand-new "Compose a custom workflow" (no saved manifest, no saved
// agent ids) starts from a genuinely empty canvas — not a hardcoded
// library template. "custom" is the only workflowType this component
// ever mounts for (DashboardLayout's COMPOSER_ENABLED_TYPES), so there is
// no other case this fallback needs to serve.
return [];
```

Opening "Compose a custom workflow" from `CreationHub.tsx` (the `{ id: "custom", type: "custom",
label: "Compose a custom workflow", ... }` tile) mounts `ComposerPage` with no
`initialManifestSteps`/`initialAgentIds`/`builtinCanvasType`, so `pipelineAgents` lazy-initializes
to `[]` — identical in shape to the dead-link canvas's empty state, but reached with zero errors,
zero bad URLs, and zero fetches involved.

The composer's own "ready" indicator does not gate on agent count either — confirmed at
`frontend/src/components/workflow/composer/CanvasView.tsx:2282-2285`:

```tsx
{briefText.trim().length < 3
  ? `${3 - briefText.trim().length} more character${... } to enable Run`
  : "Ready to run."}
```

and the "Run once" button itself is `disabled={!onRun}` only (`ComposerPage.tsx:1058`) — no
`pipelineAgents.length` term anywhere in either condition. Compare `IdeaInputPage.handleRun`,
which explicitly guards the same shared `resolveDispatchType` call:

```ts
// IdeaInputPage.tsx:1301-1302
const handleRun = () => {
  if (!ideaInput.trim() || pipelineAgents.length === 0) return;
  ...
```

and its Run button: `disabled={!ideaInput.trim() || pipelineAgents.length === 0 || ...}`
(`IdeaInputPage.tsx:1675`). `ComposerPage.handleRunOnce` has no equivalent of either guard.

## Condition

Open "Compose a custom workflow" (fresh, no saved id, no manifest) → type any brief 3+ characters
long → click "Run once" **before adding a single agent**. No dead link, malformed id, or fetch
failure of any kind is required.

## Expected vs actual

**Expected:** "Run once" is disabled (or `handleRunOnce` early-returns) whenever
`pipelineAgents.length === 0`, the same way `IdeaInputPage.handleRun` already behaves for the
sibling simple-launch surface.

**Actual (predicted):** the identical full custom-agent-pool substitution ISS-234 documents —
`onRun("custom", brief, [], extraParams)` → `useWorkflow.ts` omits `agent_ids` from the POST body
entirely since `agentIds.length === 0` (`useWorkflow.ts:88-90`) → `run_commands.py:2695`'s
`if agent_ids:` is False → `get_pipeline_agents("custom")` (`run_commands.py:2726`,
`registry.py:108-115`) returns the full 9-agent pool — fires from the plain "start a new custom
workflow" entry point, with no bad link involved.

## Why the root cause implies this

ISS-234's root cause is that the launch endpoint cannot distinguish "a genuinely empty roster"
from "no roster given, use the default" at the one place both meanings collapse to the same
falsy `agent_ids`. That ambiguity is a property of the **backend fallback and the missing
frontend guard**, not of *how* the composer ended up with zero agents. The dead-link canvas is
one way to reach `pipelineAgents.length === 0`; a fresh, never-populated composition is another,
and — per `ComposerPage.tsx:275-280`'s own comment — the more common one, since it is the normal
first-open state of every custom composition before the user adds anything.

**Marked INFERRED**: not yet click-tested this session — confirmed only by reading
`handleRunOnce`, the mount-state initializer, the "Ready to run" gate, and the Run button's
`disabled` prop, none of which reference `pipelineAgents.length`. What would confirm it: open
"Compose a custom workflow," type a 3+ character brief, click "Run once" with 0 agents added, and
check the resulting run via `GET /api/runs/<id>` for `agent_count: 9`. What would refute it: a
gate elsewhere (e.g. a route-level guard on the `custom` composer specifically) that this reading
missed and that blocks reaching `handleRunOnce` with an empty roster.
