# ISS-897

## Description

This finding was deferred from [FIX-680](20261001-2127-FIX-680.md) (bug report QA-KB-030).
[ISS-132](20260812-2116-ISS-132.md) has two halves that must agree:

- **Call-site half.** `invocation_gated=False` on every per-task `runner.run_agent` call, at
  `backend/agents/capabilities/strategies/task_loop.py:367`, added by commit `ff37f777a`.
- **Step-scope half.** `runs_agent_inline = False` on `TaskLoopStrategy`, added by FIX-680.

`backend/tests/unit/agents/test_task_loop_declared_gate_iss132.py` now pins the step-scope half.
Nothing pins the call-site half:

- `_FakeRunner.run_agent` in `backend/tests/unit/agents/test_strategies.py:168-177` takes
  `invocation_gated=True` as a keyword argument and never records it.
- Only two files under `backend/tests` name both `invocation_gated` and `task_loop`: that one and
  the ISS-132 test file. The ISS-132 file mentions the flag only in its docstring.

## Expected vs actual

- **Expected:** removing `invocation_gated=False` at `task_loop.py:367` makes a test fail.
- **Actual:** no test fails. With FIX-680 in place, that revert would open the inline review
  gate once per task and also run the declared step gate. An N-task step would get N+1 gates:
  the original ISS-132 symptom plus one more gate.

## Where a fix belongs

The fix is test-only, with no production change. It follows ISS-132's "Notes for the test writer",
items 3 and 4:

- Make `_FakeRunner.run_agent` record `invocation_gated`, and assert it is `False` for every task.
- Optional: add a pairing guard, so that any strategy module that passes `invocation_gated=False`
  must also declare `runs_agent_inline = False`.

## Severity

Low. No current defect. This is a gap in the regression guard.

## Analysis addendum (QA-KB-070, analyzer, 2026-10-07)

Everything below is CONFIRMED unless marked INFERRED. No repo file was edited. Each "mutation" is applied in memory by `evidence/qa-kb-070/mutate_task_loop.py` (a pytest plugin) or by the probe and drive scripts beside it, and every run was one offline test file. `evidence/qa-kb-070/04-analyze-output.txt` has the full tables and the command shapes.

### Where the lines are now

The call site is `backend/agents/capabilities/strategies/task_loop.py:364`, the `invocation_gated=False,` keyword of the one and only `runner.run_agent(...)` call in the file (`:357-365`). The `runs_agent_inline = False` declaration is `:164`. The `:367` above was true when this card was filed; the file has since moved by three lines.

### The revert is invisible (CONFIRMED)

With the keyword deleted in memory (`TaskLoopStrategy.run` re-compiled without that line), nine offline files give the same result as with no mutation: `tests/unit/agents/test_strategies.py` (11 passed), `test_task_loop_declared_gate_iss132.py` (3), `tests/integration/agents/test_sc001_nonprototype_task_loop.py` (3), the three `tests/contract/agents/test_characterization_prototype*.py` goldens (2, 4 and 2), `tests/integration/agents/test_routing_parity.py` (5), `test_sc001_reconcile.py` (3), and `test_engine_runner_error_arm.py` (5 passed, 1 failed; the same test fails identically with no mutation, see the last section). The cause is structural, not an oversight in one file: every test that reaches the real task_loop passes `gate_agent_ids=[]` and a no-op gate, and the one ticked build-agent test (`test_task_loop_declared_gate_iss132.py:38`) calls `_evaluate_gates` directly and never `run_agent`.

### What the revert does to a real run (CONFIRMED by measurement)

`evidence/qa-kb-070/02-analyze-gate-count-drive.py` drives the real `ExecutionEngine.execute` over the 2-task `sc001_task_loop` fixture with the launch shape the wizard produces, `gate_agent_ids=[agent]` plus `selections[agent].gates=["human"]`, and a recording `_run_review_gate`:

| `invocation_gated=False,` deleted | 3 (two inline, one per task, plus the declared gate) | complete, 0 errors |

So "N tasks, N+1 gates" is measured, not derived.

### The proposed pin catches it (CONFIRMED)

`evidence/qa-kb-070/01-analyze-pin-probe.py` runs the real `TaskLoopStrategy.run` over a 3-task plan against a fake whose `run_agent` records `invocation_gated` with default `True`. As shipped it records `[False, False, False]`, so the pin passes. With the keyword deleted it records `[True, True, True]`, so the pin fails.

### Where the fix belongs

Test-only, in `backend/tests/unit/agents/test_strategies.py`, and nowhere else:

1. `_FakeRunner.run_agent` (`:168-188`): add `"invocation_gated": invocation_gated` to the dict appended to `run_agent_calls`. **Keep the parameter default `True`.** It mirrors `KernelServices.run_agent` (`kernel_services.py:1964`) and is what makes a deleted keyword read as `True`; a `False` default would make the pin pass vacuously.
2. Assert `all(c["invocation_gated"] is False for c in runner.run_agent_calls)` in `test_task_loop_parses_two_tasks_one_run_agent_each` (`:367-384`, the existing multi-task test), or in a test beside it.

No production line changes and no kernel line changes, so INV-1 / SC-001 are untouched. Do not "fix" this by changing the default of `invocation_gated` at `kernel_services.py:1964` or `engine.py:9227`: that would un-gate every step-shaped invocation, and `test_selecting_a_non_fanout_agent_still_opens_its_inline_gate` (`test_restart_resume_db.py:5582`) pins the default for exactly that reason.

For the test-writer: no red test exists against correct production code, except through the fake. Until step 1 lands, the new assertion raises `KeyError: 'invocation_gated'`, which is the red for a strict-xfail `@pytest.mark.issue("ISS-897")`. The real acceptance is a mutation check: with `task_loop.py:364` deleted (cwd `backend/`, `MUTATE_TASK_LOOP=1 PYTHONPATH=../evidence/qa-kb-070 .venv/bin/python -m pytest tests/unit/agents/test_strategies.py -q -p no:cacheprovider -p mutate_task_loop`) the new test must fail, and with no mutation it must pass.
