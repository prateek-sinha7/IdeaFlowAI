## What was wrong

Bug report QA-KB-026. `python3 tools/knowledge/status.py` printed `domain prose 16 16 OK` directly under
`source files covered 935 940 STALE`. This was observed live in this tree on 2026-10-01, before the change. The row
claimed every DOMAIN card's prose was current at exactly the moment the architecture map was known to be behind.

A second case came from the same block ([ISS-883](20261001-2112-ISS-883.md)). A DOMAIN card with no
`code_signature` was skipped by the loop but still counted in `found`, so a card the build had never stamped read
as verified.

## Root cause

Taken from the cards, not re-derived. [ISS-693](20260918-ISS-693.md): `prose_signature` and `code_signature` are both
stamps, and neither one moves between architecture builds. `build_architecture.py` writes `code_signature` only
inside a build, and it carries `prose_signature` forward or sets it with `--stamp`. Equal stamps therefore mean "the
prose matched the code at the last build", not "the prose matches the code now". The verdict at `status.py:332`
(pre-change numbering) was `"OK" if not (stale_domains or unauthored_domains) else "STALE"`, with no input that could
tell it the build was behind. [ISS-883](20261001-2112-ISS-883.md): `:322-323` did `continue` on a missing
`code_signature`, and `:330` computed `found` as `n_domains - len(stale) - len(unauthored)`, so the skipped card
landed in `found`.

## Change

All in `tools/knowledge/status.py`, inside the domain-prose block and its naming lines:

- `:317`: a third list, `unbuilt_domains`.
- `:322-324`: a card with no `code_signature` is appended to `unbuilt_domains` before the `continue`.
- `:330-340`: `found` also subtracts `unbuilt_domains`. The verdict is now the expression the ISS-693 analysis
  prescribed, with the third list added to the STALE branch:
  `"STALE" if (stale_domains or unauthored_domains or unbuilt_domains) else "UNKNOWN" if any(c[0] in ("source files
  covered", "source files changed") and c[3] == "STALE" for c in checks) else "OK"`. Both rows are already in `checks`
  at that point (`:188`, `:252`).
- `:388-389`: `unbuilt_domains` joins `named`, so an unbuilt card is named under "domain cards needing a pass". The
  Fix line beside it is `/velocity diagrams`, whose step 3 runs the architecture build that writes
  `code_signature`.

`skills/velocity/status.md`: added the `domain prose` row to "What it checks", including what UNKNOWN means. This is
the canonical copy, as the ISS-693 blast-radius table asked. The rsync mirrors (`.claude/skills/velocity/`,
`.kiro/skills/velocity/`, see `build_architecture.py:1328-1329`) and the separate `skills/velocity-win/` variants were
not edited. They pick the row up at the next mirror sync.

FIX-670 ([BUG-128](20260918-BUG-128.md)) owns `:319` and `:321` of the same loop (`head` renamed to `text`). Both
lines are untouched, and `backend/tests/unit/test_status_head_sha.py` still passes (2 passed).

## Why there

The trigger is the pair that `status.py` already uses for its own "a full rebuild is due" decision (`needs_arch`,
`:392`). The ISS-693 analysis widened the agreed `covered`-only predicate to this pair because a symbol rename inside
an existing file leaves the file count equal. UNKNOWN rather than STALE: a STALE row with no card to name would sit in
"N stale:" with nothing to act on. UNKNOWN is never alone, because it needs a STALE covered/changed row beside it,
and that row already drives the full-rebuild Fix line. The two consumers that act on this row, `prime.md:53` (five
copies) and `7-closer.md:71` (two copies), act on a literal STALE only, so UNKNOWN triggers neither. An unbuilt card
has to be STALE, not UNKNOWN. On an otherwise current tree, UNKNOWN would never reach the naming block, because the
report returns at "Everything current" first.

Not changed, and recorded on the cards: `stale_prose_report` (`--stale-prose`) has the same skip, but `diagrams.md`
labels its output "known-stale" (ISS-693, ISS-883). An uncommitted in-file edit with no file added or removed still
trips neither row, because `git diff sync..HEAD` sees commits only. Closing that needs a live recompute, which is
blocked on ISS-884.

## Not fixed: ISS-884 (left open)

[ISS-884](20261001-2112-ISS-884.md) is not caused by this bug's root cause. The analysis found it while ruling out a
live recompute. Its card assigns the fix design to the owner. A read-only probe from this phase settles the card's
INFERRED cause. For each DOMAIN card it compared the stamped `watched_files`, today's `live_watch_set()`, and
`domain_watch_set(..., prefer=members | Depends on | Depended on by)`, with the edges read from each member's
per-file card. Script: `scratchpad/kb026_884_seam_probe.py`; output: `scratchpad/kb026_884_seam_probe.out`.

```
live==stamped 10/16; seam==stamped 16/16
DOMAIN-auth-and-entitlements 31/30/31, context-assembly 28/27/28, deliverables-and-artifacts 30/29/30,
execution-strategies 20/19/20, hitl-gating 20/19/20, workspace-isolation 20/19/20   (stamped/live/seam)
```

The fix is known. Where `live_watch_set` gets the seam from is the owner's decision:

- (a) Persist `link_scope` (or the watch list) in the DOMAIN frontmatter. This changes the generated card schema and
  takes effect only after an architecture rebuild. The new key must sit after the signature keys, because
  `status.py` and `read_signatures` read only the first 2000 characters.
- (b) Rebuild `link_scope` at read time from the per-file cards' Depends on / Depended on by blocks, as the probe did.
  This needs no rebuild, but it makes `live_watch_set` depend on the generated body format of the `files/` tier.

Its test, `test_live_watch_set_passes_prefer_seam`, stays XFAIL. It asserts only `prefer is not None`.
`prefer=set(members)`, which equals today's default, would satisfy it without changing behaviour, so whoever fixes
ISS-884 should assert the stamped count instead.
