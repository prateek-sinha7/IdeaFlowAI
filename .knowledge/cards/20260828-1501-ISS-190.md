## What happened

`/create/prototype` (the legacy prototype wizard shell — tabs, template gallery, Back/Next)
renders correctly on a fresh visit. But: land on `/create/prototype` normally → press browser
**Back** (goes to `/dashboard`, renders fine) → press browser **Forward** (URL returns to
`/create/prototype`, title is correct) → the page body is completely empty. No header, no tabs,
no template gallery — just the page background. The state does not resolve after a 2+ second
wait; only a full `page.goto` reload recovers it.

Confirmed **CONFIRMED, 3/3, cold start every cycle** — each cycle re-navigated fresh to
`/dashboard`, then to `/create/prototype`, then `goBack()`, then `goForward()`, using real
Playwright `page.goBack()`/`page.goForward()` (not scripted `history.forward()`). All three
cycles produced identical results:

| cycle | body.innerText length after Forward | body.innerHTML length | blank |
|---|---|---|---|
| 1 | 0 | ~24000 (raw RSC payload) | yes |
| 2 | 0 | ~24000 | yes |
| 3 | 0 | ~24000 | yes |

`document.body.innerHTML` in the failure state is ~24000 characters of literal, un-executed
Next.js RSC streaming script/text payload — not rendered markup. `location.href` correctly reads
`http://localhost:3000/create/prototype` throughout, `auth_token` stays valid the whole time, and
every API the page needs (`/api/workflows/prototype`, `/api/prototype/templates`,
`/api/prototype/design-systems`, `/api/agents/library`, etc.) returns 200 OK — this is a
client-side hydration failure, not a data-fetch or auth failure.

## Expected vs actual

- **Expected:** Forward navigation back to `/create/prototype` renders the wizard shell exactly
  as a fresh visit does.
- **Actual:** The page silently renders nothing — an empty, contentless body holding only the raw
  un-hydrated RSC stream, no error, no loading indicator, no self-recovery, requiring a full
  reload.

## Conditions established

- Route: `/create/prototype` (the legacy-wizard route family per
  `bug-hunter/velocity.json` note at line 204 — `/create/ppt` and `/create/prototype` render the
  tabbed wizard shell, not the simple launch panel used by `/create/app` etc.)
- Tier: qa-admin (not varied — reproduces at 3/3 without needing to test other tiers)
- Entry path: `/dashboard` → `/create/prototype` (fresh nav) → browser Back → browser Forward
- Trigger is the Back-then-Forward sequence specifically — a fresh direct nav to
  `/create/prototype` (no Back/Forward involved) renders correctly every time.
- No timing variation needed: reproduced identically on the very first Forward click and after a
  2-second settle wait; the blank state is stable, not a race that resolves.

## Root cause (3-analyzer, 2026-08-28)

**CONFIRMED** (`frontend/src/app/[...view]/page.tsx`, the sole catch-all `DashboardPage`
component ADR-0018 requires every one of the app's 34 screens to render behind):

- `:416` — `const [mounted, setMounted] = useState(false);`
- `:490-492` — `useEffect(() => { setMounted(true); }, []);` — empty deps, fires exactly once
  per component lifetime.
- `:431` — `const [isAuthenticated, setIsAuthenticated] = useState(false);`
- `:806-827` — the "Auth check on mount" effect, deps `[router, dispatch]` (both stable
  references for the life of the SPA session) — the ONLY place `setIsAuthenticated(true)` is
  called; also effectively fires once.
- `:3701-3706` — `if (!mounted || !isAuthenticated) { return null; }`. Read every top-level
  `if`/`return` in the component from its start (`:344`) through this line: this is the FIRST
  render-level return in the whole 4107-line file — every route (all 34 screens) hits this exact
  gate before anything else renders.
- `:349-359` (comment, on why `usePathname()` is used instead of `useParams()`) confirms the
  page's own design explicitly assumes it is NEVER remounted by in-app navigation: "a run tab
  click updates the URL shallowly... router.push would remount this whole page and refetch the
  run." `mounted`/`isAuthenticated` being mount-once state is safe ONLY under that assumption.
- `grep -rln "pageshow\|popstate\|bfcache\|back_forward\|BackForward" frontend/src` returns
  **zero matches** — nothing anywhere in the frontend detects or recovers from a browser
  back/forward-cache-style restore.

So the mechanism is: `mounted` and `isAuthenticated` are each set exactly once, by effects whose
dependency arrays never change again, and the ONLY render path renders `null` until both are
true. Landing on `/create/prototype` fresh runs those effects and renders fine. Back to
`/dashboard` re-renders the SAME live component with new route params — `mounted`/
`isAuthenticated` are untouched, so it renders fine too (consistent with the validator's finding
that Back alone never reproduces this). Forward is the step that reproduces it 3/3, which is
only possible if, contrary to the code's own assumption, that specific navigation produces a
component instance whose `mounted`/`isAuthenticated` are back at their `false` initial values —
and whose mount-effects then never get a chance to re-run and flip them.

**INFERRED** (Next.js 16.2.4 App Router / browser internals, not this repo's code, so not
directly provable by reading it):
- Two mechanisms both fit the confirmed evidence and the reported DOM signature (`body.innerHTML`
  holds raw, un-executed `self.__next_f.push(...)` RSC stream chunks; `body.innerText` is empty):
  (a) Next's client-side Router Cache entry for `/create/prototype` had expired/missed by the
  time Forward fired, so the router performed a fresh RSC fetch and reconciled it as a NEW
  component instance rather than reusing the live one, landing back at the initial `false`/`false`
  gate before any mount effect re-runs; or (b) a genuine browser bfcache restore of a DOM/JS state
  captured before Next's client runtime had attached to that particular history entry. (b) fits
  the symptom less well than (a): the validator's own screenshots show `/create/prototype` fully
  rendered (tabs, gallery) immediately before Back is pressed, so a frozen-heap bfcache restore
  ought to resume that SAME rendered state, not a pre-hydration one.
- **What would settle it** (for 4-test-writer / 5-fixer, before picking a fix strategy): during
  the exact Back-then-Forward repro, log `performance.getEntriesByType('navigation')[0]?.type`
  and register `window.addEventListener('pageshow', e => console.log('persisted', e.persisted))`.
  `type === 'back_forward'` + `persisted: true` confirms browser bfcache (mechanism b);
  anything else points at Next's own Router Cache / soft-navigation path (mechanism a).

## Blast radius

- **Every one of the 34 screens `[...view]/page.tsx` renders**, not just `/create/prototype` —
  the `mounted`/`isAuthenticated` gate at `:3701` is upstream of every screen-specific branch, so
  a Back-then-Forward sequence to `/dashboard`, `/library`, `/settings/*`, etc. is exposed to the
  identical failure. Filed separately as [ISS-195](20260828-1558-ISS-195.md) since it is a
  distinct, independently-testable condition (different route, same mechanism).
- **An independently-implemented copy of the identical anti-pattern** — a mount-only
  `useState`/`useEffect` pair gating 100% of a component's render with no bfcache/pageshow
  recovery — exists separately in `frontend/src/components/workflow/LaunchWizard.tsx` (`:161`,
  `:259-270`, `:806`) and in `frontend/src/app/handoff/settings/page.tsx` (`:21`, `:32`).
  `LaunchWizard`'s copy guards the actively-used legacy route `/workflow/create?mode=ppt|prototype`
  (call sites: `frontend/src/components/home/CreationHub.tsx:31,35`,
  `frontend/src/components/layout/DashboardLayout.tsx:1530,1557`), which bypasses this page's
  gate entirely (`frontend/src/app/workflow/create/page.tsx:17-19`: "Auth is owned by
  LaunchWizard... the duplicate getToken/redirect + loading gate here was a redundant second
  gate [IN-07]"). A fix scoped only to `page.tsx` will NOT cover this route. Filed separately as
  [ISS-197](20260828-1559-ISS-197.md).

## Proposed fix — and where it belongs

`page.tsx` is the ONE catch-all every screen already routes through (ADR-0018), so the fix for
the 34-screen blast radius belongs there, once — not duplicated per-route. Two candidate
directions, pending the diagnostic above to pick between them:

1. **Blunt, mechanism-agnostic:** near the top of `DashboardPage`, register
   `window.addEventListener('pageshow', ...)` once and force `window.location.reload()` when
   `event.persisted` is true or `performance.getEntriesByType('navigation')[0]?.type ===
   'back_forward'` fires on an already-mounted instance. This matches the recovery path already
   confirmed 100% reliable by hand (a fresh `page.goto`/reload always recovers).
2. **Root-fix the gate:** stop deferring `mounted`/`isAuthenticated` to a `useEffect`; derive them
   synchronously (e.g. a lazy `useState(() => typeof window !== "undefined" && !!getToken())`
   initializer) so any fresh mount — the original SSR/hydration pass or a later remount — renders
   correctly on its first pass without waiting on a post-commit effect. This changes the
   SSR-hydration-mismatch tradeoff `:413`'s own comment says the current code deliberately chose,
   so it needs care.

`LaunchWizard.tsx`'s independent `authChecked` gate ([ISS-197](20260828-1559-ISS-197.md)) needs
the SAME fix applied separately — it is not reached through `page.tsx`'s gate, so fixing only
`page.tsx` leaves `/workflow/create?mode=...` broken. If a shared recovery hook is warranted, it
belongs in `frontend/src/hooks/` (`MOD-frontend-src-hooks`) so both gates — and any future one —
route through one place instead of a third copy-paste.
