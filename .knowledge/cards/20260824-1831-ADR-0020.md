# ADR-0020

## Decision

In the context of a `POST /api/runs` launch needing to source its pipeline type,
agent roster, and step tree from up to three different places (the request body, a
saved-but-flat `WorkflowDefinition` row, or a saved-or-inline Composer manifest tree),
facing the fact that these three shapes need materially different validation
(an `agent_ids` allow-list makes sense for two of them and not the third) and different
downstream data (`agents: list[AgentSpec]` vs a full `CompiledWorkflow`), the backend
already resolved this — as a literal three-member `LaunchSource(str, Enum)` — with the
shape detected exactly once, near the top of `launch_run`, and every branch
reconverging at exactly one mint+execute call. This ADR **records** that existing,
undocumented decision under a name a future search will actually find, rather than
introducing a new one.

**Area:** backend, run launch, workflow composition

## The three shapes, verbatim

From `backend/app/api/run_commands.py:2152-2179` (`class LaunchSource(str, Enum)`):

| Enum member | Plain-English name | Trigger |
|---|---|---|
| `FILE_PIPELINE = "file_pipeline"` | **File Based** | No `user_workflow_id` at all — a fresh built-in pipeline launch, or an ad-hoc `pipeline_type="custom"` + `agent_ids` picked straight from the library with no saved row behind it. |
| `USER_WORKFLOW_FLAT = "user_workflow_flat"` | **File Based, overridden in DB** | `user_workflow_id` present, and the referenced row's `manifest_json` is null/absent. A saved workflow that is still a flat `agent_ids` list (e.g. "Hello Poet": `hello_html` + attached hooks/skills on the row). Composition stays `agent_ids`-shaped; only the *source* of `pipeline_type`/`agent_ids`/hooks/skills changes — the row, not the client body. |
| `USER_WORKFLOW_MANIFEST = "user_workflow_manifest"` | **DB Based** | `user_workflow_id` present AND the row's `manifest_json` has a `"steps"` key — OR no `user_workflow_id` but the request body carries an inline `manifest.steps` (an unsaved Composer tree). The manifest tree **is** the composition; there is no file behind `base_pipeline_type`, and the `agent_ids` allow-list does not apply (nothing to check it against). |

Detection is inline in `launch_run`, not a separately named function (the enum's own
docstring says "see `_detect_launch_source`", which is aspirational — read it as
"the block below", `run_commands.py:2561-2595`):

```python
launch_source = LaunchSource.FILE_PIPELINE        # default
if body.user_workflow_id is not None:
    ...                                            # load + snapshot the row
    if user_workflow_row.manifest_json and "steps" in user_workflow_row.manifest_json:
        launch_source = LaunchSource.USER_WORKFLOW_MANIFEST
    else:
        launch_source = LaunchSource.USER_WORKFLOW_FLAT
elif body.manifest and "steps" in body.manifest:
    launch_source = LaunchSource.USER_WORKFLOW_MANIFEST
```

Each shape then takes its own short branch (`run_commands.py:2597-2624+`): Case 1 is a
no-op (nothing to overwrite); Case 2 overwrites `body.pipeline_type`/`body.agent_ids`/
hooks/skills/model_overrides from the row and falls through into the *existing*
`agent_ids` allow-list path unchanged; Case 3 synthesizes the top-level fields
`build_manifest_from_dict` requires (a DB-composed `manifest_json` never carries them)
and compiles with `trust="db"` — the compiler's own step-by-step capability checks are
the real security boundary for this shape, not an allow-list.

## Where the three shapes reconverge

All three branches funnel into **one** mint+execute call — `_launch_run_core`
(`run_commands.py:2417+`, its own `# ═══ JOIN POINT ═══` marker at line 2451; called
from `launch_run` itself at line 2883 with the comment *"All 3 LaunchSource branches
reconverge HERE"*). Everything above that call is launch-shape-specific ingress
validation; everything from that call downward runs identically regardless of shape.

One line inside `_launch_run_core` is the cleanest illustration of how little the three
shapes actually share once compiled:

```python
# `compiled` is only non-None for Case 3 (USER_WORKFLOW_MANIFEST) — CompiledWorkflow.steps
# is already FLAT (the compiler flattens the tree; parent/child is encoded per-step via
# `dispatched_by`, not nesting), so counting it needs no recursion.
agent_count = len(compiled.steps) if compiled is not None else len(agents)
```

Cases 1 and 2 carry a flat `agents: list[AgentSpec]`; only Case 3 carries a full
`compiled: CompiledWorkflow`. A change that reads one and forgets the other is exactly
the kind of bug this taxonomy exists to make legible.

## Why this shape

**Three cases, not two, because the security boundary genuinely differs.** Case 2 is
still validated against `registry.allowed_custom_agent_ids` (an `agent_ids` allow-list —
there is a flat, checkable list of ids). Case 3 has no such list to check against — a
Composer manifest's steps are `custom-agent:<instance_id>` synthetic ids with no
`AGENT.md` behind them — so its security boundary is the compiler's own per-step
`trust="db"` capability checks instead (see
[DOMAIN-workflow-compilation.md](../architecture/DOMAIN-workflow-compilation.md)). Collapsing Case 2 and
Case 3 into one "has a `user_workflow_id`" case would either apply an allow-list check
that Case 3 cannot satisfy, or skip it for Case 2 where it is the actual guard —
correctness requires the split.

**One detection point, one reconvergence point — not either alone.** Detecting once
(rather than re-inspecting `body`/the row at every downstream check) is what makes the
"never re-decide the shape mid-flight" half of the constraint enforceable; reconverging
once (`_launch_run_core`) is what makes the "every shape ends up minting a `WorkflowRun`
the same way" half enforceable. Either without the other would let a shape silently skip
validation or silently skip minting consistently.
