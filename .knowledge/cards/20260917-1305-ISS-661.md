# ISS-661

## Title

QA-PS-007's own card ([ISS-651](20260917-1200-ISS-651.md)) lists its Route as covering both
"the Files tab" and "the Preview panel header Download", but its Trace only follows the Files
tab mechanism (`withWorkspaceFile` in `FilesTab.tsx`). The header Download button is a
**separate, independent** code path with its own copy of the same flawed logic — this card
exists so the fix does not stop at `FilesTab.tsx` and silently leave this button broken.

## Status: INFERRED — not yet reproduced live

The code mechanism below was read directly (file:line), not merely hypothesized, but per
project policy this has not been confirmed by an actual browser click-through, so it is filed
as an unreproduced sibling like the others.

## Why QA-PS-007's root cause implies this

QA-PS-007's root cause is "trust the raw on-disk basename over the content-derived name."
That pattern is implemented **twice**, in two unrelated functions, in two different files:

1. `frontend/src/components/results/FilesTab.tsx:451-462` — `withWorkspaceFile()`, the
   function QA-PS-007 traced.
2. `frontend/src/components/preview/PreviewPanel.tsx:1272-1293` — `handleHeaderDownload`, a
   **separate, inline** implementation that never calls `withWorkspaceFile` at all:
   ```tsx
   const name = deliverableFile
     ? deliverableFile.split("/").pop() || deliverableFile
     : `workspace-${activeRunId.slice(0, 8)}.zip`;
   downloadBlob(url, name, blob.type);
   ```
   (`PreviewPanel.tsx:1287-1290`). `deliverableFile` is set at line 1241
   (`if (hit) setDeliverableFile(hit.path);`) from `resolveRunDeliverable`
   (`frontend/src/lib/api.ts:1175-1191`) — the same resolver QA-PS-007's trace already
   implicates. For a ppt run, `hit.path` resolves to the literal on-disk `presentation.html`
   (per [ISS-651](20260917-1200-ISS-651.md)'s backend evidence), so `name` here is
   deterministically `presentation.html` too — via a code path `withWorkspaceFile` never
   touches.

Meanwhile `PreviewPanel.tsx:1301` (`previewFilename`, the URL-bar name) and
`DashboardLayout.tsx:2470` (`laneDerivedFilename`, the chat lane's "Run summary" card) both
call `deriveDeliverableFilename` **directly**, bypassing `resolveRunDeliverable`/
`withWorkspaceFile` entirely — those two surfaces already show the correct, content-derived,
topic-based name for the same run. That existing correct path is the evidence for where the
fix's target behavior already lives in this codebase; the header Download button and the
Files tab row are the two surfaces that resolve the name from the workspace file instead and
both need to stop doing that unconditionally.

## Fix-location note (not a fix — for the fixer)

Because the same flaw is implemented independently in two files, a guard added only inside
`withWorkspaceFile()` fixes the Files tab but leaves this button emitting the generic name.
The smaller, root-cause diff is one shared helper (e.g. exported from `FilesTab.tsx` or a
lib module) that both `withWorkspaceFile()` (`FilesTab.tsx:451`, 2 call sites) and
`handleHeaderDownload` (`PreviewPanel.tsx:1287`) call, so all three call sites route through
one place.

## Expected (once reproduced)

Clicking the header Download button on a completed ppt (or prototype, per
[ISS-659](20260917-1305-ISS-659.md)) run saves a file named after the run's topic, matching
the Files tab's own (once fixed) filename.

## Actual (inferred, not yet observed)

The header Download button saves the file as the generic on-disk name (`presentation.html` /
`prototype.html`), independently of whatever QA-PS-007's fix does to the Files tab, unless
that fix also touches this code path.

## What would confirm this

1. Sign in as `qa-admin@flowinqa.com`, open a completed ppt run.
2. Click the Download affordance in the Preview panel header (not the Files tab row).
3. Check the saved filename — if it is `presentation.html` regardless of topic, this is
   confirmed.

## Won't-fix (2026-09-23) — confirmed live, resolves the escalation

Reproduced live: run `8754cc43-f0b6-4005-b2d1-34db2eb41ad1` ("Subsea Fibre Splice Operations",
`ppt_revision`), header Download button saved `presentation.html` for both the latest version
(v8) and a pinned older version (v2) — exactly the mechanism this card describes. But the
[ESCALATIONS.md#qa-ps-007](../../ESCALATIONS.md#qa-ps-007) decision this card raised is now
answered: don't rename the deliverable (`FIX-STATE.md`, 2026-09-22). That is effectively
option (a) — the declared/on-disk name is the name of record, no frontend fallback needed —
and the header Download button already does that correctly (matches the pinned
`PreviewPanel.test.tsx:269` assertion). Byte comparison (sha256) confirmed the header Download
served the right bytes for the version on screen in both cases; see
[WONTFIX.md#qa-ps-007](../../WONTFIX.md#qa-ps-007).
