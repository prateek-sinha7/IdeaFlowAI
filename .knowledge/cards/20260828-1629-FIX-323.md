## What was wrong

An authenticated user (valid `auth_token`, working API session) who landed on `/login` or
`/login?expired=true` — by direct navigation, browser Back, or the `/register` stub's
redirect — was shown the full sign-in form, and for the `expired=true` variant the stale
"Your session expired. Please sign in again." banner. No redirect to `/dashboard` ever
fired, by any entry path.

## Root cause

`frontend/src/app/login/page.tsx:3` — `LoginForm` never imported `useEffect` and had no
mount-time auth check anywhere in its 530 lines. Execution went straight from the
`useState` calls to the JSX return of the sign-in form on every render, unconditionally.
The `isExpired` flag (`searchParams.get("expired") === "true"`) only toggled banner text;
it never gated whether the form rendered.

The inverse guard already existed everywhere else in the app — `frontend/src/app/page.tsx:9-18`
branches `/` on `getToken()`, and `frontend/src/app/[...view]/page.tsx:805-811` bounces every
protected screen when no token is stored. Only the signed-in-user-on-`/login` direction was
never built.

## What changed and why there

`frontend/src/app/login/page.tsx` only — one guard in the single render path every entry
point funnels through, rather than one check per caller:

- A mount-time `useEffect` that calls `getToken()` and, when a token exists,
  `router.replace(resolveRedirectTarget(searchParams.get("redirect")))` — the identical
  call the file's own `goToDestination()` already makes after a successful submit.
  `resolveRedirectTarget` was already imported (line 15); `getToken` was added to the
  existing `@/lib/api` import.
- A `checked` state with `if (!checked) return null;` before the render branches. Effects
  run after paint, so without the render gate the sign-in form would flash for one frame
  before the redirect. This mirrors `frontend/src/app/handoff/settings/page.tsx:21-32`
  (`authed` state, `if (!authed) return null`), the app's own existing pattern.
- `frontend/src/app/login/login.reskin.test.tsx`'s `@/lib/api` mock gained a
  `getToken: () => null` stub, because the module mock must now expose the symbol the page
  imports. Every test in that file drives the sign-in form itself, so "anonymous" is the
  correct stub answer — no assertion was changed.

No `register/page.tsx` change was needed: with `/login` redirecting a signed-in visitor
onward itself, the `/register` -> `/login` hop becomes a harmless intermediate step.
[ISS-193](20260828-1554-ISS-193.md) — filed as INFERRED and never reproduced — is resolved
by this single-file fix, confirmed by direct observation below.

**No redirect loop.** `handleSessionExpiry()` (`frontend/src/lib/api.ts:144-149`) calls
`clearToken()` *before* `window.location.href = routes.login({ expired: true })`, so a
genuinely expired session arrives with no token and still lands on the form.

## Noted, not changed

`frontend/src/app/admin/page.tsx:182` bounces to `buildLoginRedirect()` when `getMe()` fails
with a *non*-401 error while a token is still stored. With this guard in place, `/login`
sends that user straight back to `/admin`, so a persistently failing `getMe()` can ping-pong
where it previously parked on the sign-in form. Unreachable in a healthy backend, outside
both cards' scope, and not touched here.
