## Decision

A finished run leaves a payload; the next run reads it as files.

`.chain/` holds the output side — `summary.md`, `logs.jsonl`, and the
deliverable — flat, committed, written on every terminal status. `.context/`
holds the input side of the receiving run. A chained run starts a **new
family** with its own sandbox; it does not join the source's history.

The copy takes bytes from the source's **immutable internal ref**, not its
working tree. That is the whole point: the source can be revised afterwards
and the chained run still holds what it was actually given.

**Admission is fail-closed and happens at launch.** A source that is still
running, not finalized, not chainable, or whose payload tripped the secret
scan is refused with a reason the interface can render. Degrading to an empty
context is reserved for one case — the payload is genuinely absent — and only
when the workflow asked for that policy.

## Why this shape

The previous design inlined the parent's context into the child's input text.
[ISS-159] recorded the consequence: no lineage was persisted, so nothing could
be traced, and the payload was whatever happened to be in a prompt. Files that
are committed and addressable by ref fix both halves.

Nesting per run id was tried first and dropped — a chained run wants *a*
payload, not an archive, and flat paths mean the receiving agent's reading
guide can name them literally.

## Consequences

- Every terminal status leaves a payload, so a cancelled run is still a usable
  source if a human decides it is.
- A workflow only chains if it declares `chains_from` AND actually writes its
  deliverable to disk. The two must be checked together; the flag alone
  compiles and then silently never admits.
- A copy failure after admission is swallowed into an "unavailable" flag and
  the run proceeds with an empty `.context/`. Whether it should refuse instead
  is an open owner decision (tracked as bug B5 on `feat/git-versioning`).
