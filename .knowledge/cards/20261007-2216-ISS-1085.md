# ISS-1085

**Register source:** `QA-KB-076` in root `LEDGER.md` / `BUGS.md` (sibling, derived during its analysis on 2026-10-07).
**Root card:** [ISS-903](20261001-2145-ISS-903.md) holds the mechanism (the guard enforces a narrower rule than the convention it exists for). This card is the inverse case: the guard polices the bad form (a line number) and does nothing for the good form (a symbol name).

**Claim status: INFERRED (sibling).** The missing assertions are CONFIRMED by reading the guard. That a rename would go unnoticed follows from that and is not reproduced as a failing test. Every anchor I looked up still resolves today, so nothing is broken yet.

## What is wrong

The convention [FIX-690](20261001-2145-FIX-690.md) installed has two halves. Its `locked_constraints` say shutdown-path comments "locate code by symbol (function, class, quoted anchor phrase), never by file:line". So a comment must not carry a line number, and the symbol it names must exist.

[ISS-104](20260812-1312-ISS-104.md)'s analysis put both halves into the guard it asked for: "assert that each ANCHOR the comments now name exists in the cited file ... A rename then fails a test instead of rotting. This is the idiom `tests/unit/services/test_shutdown_reachability.py` already uses." The guard that shipped, in commit `14a675db4` (2026-10-06, which replaced the three line-pinned `xfail` tests), has two tests:

- `test_no_line_number_cites_in_shutdown_path_files` (`test_run_shutdown_stale_citations.py:33-42`): the lint, half one only.
- `test_shutdown_comment_read_timeout_matches_model_factory` (`:46-56`): the `read_timeout=N` agreement from [ISS-888](20261001-2114-ISS-888.md).

Neither asserts that any named anchor exists.

State today, CONFIRMED: I looked up 34 names taken from FIX-690's change list and the ISS-104 inventory (`post_message`, `_drive_launch_to_queue`, `_drive_revision_to_queue`, `_run_agent`, `_execute_impl`, `_run_review_gate`, `_run_validation_fix_loop`, `_run_spec_revision_sub_pipeline`, `_drain_then_cancel`, `shutdown_run_infrastructure`, `close_checkpointer`, `restore_non_terminal_runs`, `stream_run_events`, `build_model`, `ScopedStore.assert_owns`, and the rest of that list). All resolve (`evidence/qa-kb-076/07-analyze-anchor-existence.txt`). One is not a `def`: `runs_left_for_boot_restore` is a dict key at `run_shutdown.py:227`, so the check has to be a plain "name occurs in the file text" test, not an AST definition lookup.

## Why the root cause implies it

[ISS-903](20261001-2145-ISS-903.md) is a guard narrower than its convention. This is the same gap on the other side of the convention. Replacing a number with a name moves the coupling problem from "the file grew" to "the symbol was renamed", and nothing watches that either. The original ISS-104 failure (a comment that points at code that moved away) can recur by a rename.

## Expected vs actual

- Expected: renaming or removing a symbol a shutdown-path comment names fails a unit test that names the comment's file and the missing anchor.
- Actual: the guard stays green and the comment points at nothing.

## Fix

In `backend/tests/unit/test_run_shutdown_stale_citations.py`, add a small table of `{path: [anchor, ...]}` and one test asserting each anchor string occurs in the cited file's text, which is the idiom ISS-104 specified. Plain `in` checks, no `ast`, no `app.*` import. ponytail: a hand-kept list, and the ceiling is that it drifts from the comments. If keeping it in step becomes a chore, derive the anchors from the backticked identifiers in the scanned comments.

- The anchor table should include the one non-`def` anchor above, so the test pins the plain-text approach.
