# ISS-1101

## Description

Three of the four tests behind [ISS-1061](20261007-1914-ISS-1061.md) fail with one mechanism, and it sits in the tests, not in the resume engine:

| test | red at | message |
|---|---|---|
| `test_midwave_resume_does_not_reinvoke_completed_workers` (`:514`) | `:590` | `wave-1 workers did not run on resume: {'b': 2, 'a': 2}` (`'c'` is never called) |
| `test_failed_run_resumes_skips_completed_tasks` (`:3595`) | `:3654` | the same message |
| `test_user_resume_persists_output_columns` (`:4543`) | `:4595` | `status must reconcile to completed: 'failed'` |

All three log `resumed-stream drive(<run>) failed mid-drive: Cannot transition run '<run>' from terminal state 'failed' to 'generating'.` (`engine.py:16031`) and nothing else about the resume: no wave-1 worker, no file, no `pipeline_complete`.

## Cause (CONFIRMED, every link read at HEAD)

1. Instance A's scripted crash is a `RuntimeError` raised inside `KernelServices.run_fanout` (`test_restart_resume_db.py:375-386`, `raise_on_fanout_call=2`). Since `60bbe040d`, `_guarded_step` (`engine.py:14343-14370`) turns any exception a step's strategy raises into `StepRaised`, and `_execute_impl` handles that with `self._state_machine.transition(pipeline_run_id, "failed")` (`engine.py:7599-7603`). Before it, the exception escaped `_execute_impl` and the state machine stayed at `generating`; the comment in `_execute_impl`'s `finally` still says so ("An unhandled one … never moves the state machine off "generating"", `engine.py:7620-7623`), and the tests' own comments encode the old premise: "leaves the run non-terminal" (`:530-534`).
2. `StateMachine` is a process-wide singleton (`state_machine.py:155-163`) and its guard reads that dict, not the database: `current = self._states.get(run_id)` then `if current in TERMINAL_STATES: raise StateMachineError("Cannot transition run … from terminal state …")` (`:92-97`). Instance A and instance B are two `ExecutionEngine()` objects in ONE test process, so B inherits A's `failed`.
3. Resume re-enters `_execute_impl`, skips only the `planning` transition (`_resuming`, `engine.py:5377-5379`) and then runs `self._state_machine.transition(pipeline_run_id, "generating")` (`engine.py:5739`). It raises.
4. `_drive_resumed_stream` catches it: `except Exception as exc:  # noqa: BLE001 — a resume failure must not crash startup`, then `logger.warning("resumed-stream drive(%s) failed mid-drive: %s", run_id, exc)` (`engine.py:16030-16031`). `resume_run` returns normally having emitted nothing.
5. `_drive_user_resume` (`run_commands.py:792-793`) then runs `_reconcile_terminal_status`, finds no `pipeline_complete` after the last attempt boundary and writes `failed` (test 3's assertion and the status half of test 2). Test 1 calls `resume_run` directly and sees only the missing worker calls.

## Why production is not affected (CONFIRMED by reading)

The in-process re-entries each get an empty or cleared machine. `restore_non_terminal_runs` → `resume_run` runs in a freshly started process (`engine.py:12630`, `:12868`). `resume_run_endpoint` clears the entry before it spawns the drive: step 6b, `get_state_machine().forget_run(run_id)` at `run_commands.py:745`. Its comment states the contract (`run_commands.py:735-741`): "Clear the in-memory state machine entry so _execute_impl's transition(run_id, "generating") does not hit the terminal-state guard. A cancelled run resumed in the SAME process session has "cancelled" locked; a failed run resumed after a restart has no entry (new process)". The eviction came with [FIX-105](20260723-FIX-105.md) (KAN-120, "Run Again"). A second, earlier eviction exists too: the app's run-end `_cleanup_pipeline` calls `get_state_machine().forget_run(pipeline_run_id)` (`run_engine.py:88`, `:142`; KAN-139 D4/D5) after every driver, failed runs included; the tests call `engine.execute()` / `_execute_impl` directly and never pass through that app-layer cleanup. The tests drive `_drive_user_resume` (the endpoint's thin wrapper, which by design does not repeat the endpoint's steps) or `resume_run` directly, so they skip the eviction the endpoint owns and model "a new process" with the old process's state machine. The one test in the file that models the restart properly is `test_rejected_run_resumes_and_still_produces_its_deliverable`, which calls `get_state_machine().forget_run(run_id)` at `:5365` and puts the row back to `generating` at `:5367-5369`.

So the user-visible claims of the report ("a wave worker is skipped", "a failed run can't resume") do not reproduce through `POST /api/runs/{id}/resume`; they reproduce only in a harness that skips the endpoint's eviction.

## Fix (test-only)

`_ResumeHarness.make_engine` (`test_restart_resume_db.py:437`): before `ExecutionEngine()`, reset the process-global machine (`import agents.execution_engine.state_machine as sm; sm._MACHINE = None`), with a comment that each engine instance stands for a new process. One edit fixes all three tests, [ISS-1102](20261008-0016-ISS-1102.md)'s file (it imports the same harness) and every future crash-then-resume test. The alternative, one `get_state_machine().forget_run(run_id)` per test as at `:5365`, is five lines in two files and has to be remembered by the next author.

No product change is needed. What a naive fix would break:
- Loosening the guard (`state_machine.py:92-97`) or letting `transition` leave a terminal state: terminal states are final (`:51-52`), and `_guarded_step` itself relies on `get_state(run_id) in TERMINAL_STATES` to recognise "a cancel racing the step" (`engine.py:14361`).
- Moving the eviction into `resume_run` "so the tests pass": production already evicts at the endpoint and restarts start empty, so it changes the engine for the sake of a harness, and a stray second `resume_run` on a live run would silently clear its guard. If someone wants it anyway it is a design change with its own card, not this fix.
- Deleting or xfail-ing the tests: they are the only coverage of the mid-wave skip and of the user-resume reconcile.

Scheduling: this edit and [ISS-1104](20261008-0016-ISS-1104.md)'s are in the same file; they do not overlap; run them serially.
