# ISS-894

INFERRED sibling of [ISS-683](20260904-ISS-683.md) (QA-KB-022). It is INFERRED for the real fix because that fix is not in the tree yet; the behaviour below was observed against the guard applied in memory only.

## What this card is for

The agreed fix for ISS-683 scopes the `single_file` readback (`backend/agents/execution_engine/engine.py:10621-10636`) to a step that CHANGED the declared deliverable (the file now differs from the file as it was before the step). That separates a step that only reads from one that writes. It cannot separate the two kinds of step that both write: a build step whose reply is a tool confirmation (substituting the file is wanted there) and an editor whose reply is a report (it is not). Both change the file, so both keep being replaced.

This card records that remainder so "ISS-683 fixed" is not read as "every post-build step keeps its own reply".

## Who is in the second group

`prototype_v2` ("Prototype from documents (Depth)", `backend/agents/workflows/prototype_v2/workflow.yaml`), after the mechanical `pb-assemble` (step 9) has written `prototype.html`:

- step 10 `pb-validate`, `write_files: true`. Its prompt: "Then you FIX what you found, in the prototype", `edit_file` with an exact old string for changes, and "Phase 6 - Record  build/bugs.json, then one line".
- step 11 `pb-present`, `write_files: true`. Its prompt: "Phase 4 - Finalize  fix the presentation, never the content", then "Phase 5 - Report".

The legacy `prototype` workflow's `prototype-validate` is in the same group (`write_files: true`; `agents/prompts/prototype-validate/AGENT.md:153-155` tell it to `edit_file` prototype.html).

So the two shipped prototype_v2 victims of ISS-683 are repaired by that guard only on a run where they find nothing to change.

## Observed (offline; nothing launched; nothing in the tree edited)

Scratch harness: the scripted `prototype` run (`tests/agents/_scripted_model._drive`) with `prototype-validate` scripted to call `edit_file(prototype.html, ">hi<" -> ">hello<")` and then reply "Validation passed after 1 fix.", run against an in-memory copy of `engine.py` carrying the ISS-683 guard:

- the validator's `agent_complete.output_length` is 87 (the whole file) while its streamed reply is 47 characters;
- `.agents/05-prototype-validate.md` is `# Validation Agent` plus the whole HTML;
- the run record's `agent_outputs` is untouched (it is built from `agent_chunk` events, `backend/app/api/run_commands.py:3986-3988`), so the Steps tab still shows the reply.

The same run against the unguarded tree gives the same numbers: the guard changes nothing for an editing step.

## Expected / actual

Expected (the QA-KB-022 report): "Each agent's output is its own streamed result." Actual after the guard: an editing step's recorded output (results, typed artifacts, `.agents/NN-*.md`, the inline review-gate card, `output_length`) is the file.

## Why the root cause implies it

The readback decides on file state, never on what the reply is. Writing the file and reporting on it are not exclusive, so a file-state test cannot isolate the one case the readback exists for (a reply that is only a tool confirmation).

## Options (nothing is decided here)

a. Accept. An editing step is a producer of the deliverable, so the file is its output. In prototype_v2 the Validator hands over through `build/bugs.json` (pb-present Phase 1, step 3), not through its transcript, so nothing downstream reads the wrong thing today. Recommended default: note it on ISS-683 and leave this open only until a transcript reader of an editor appears.
b. Never substitute; typed-write the file as an `html_file` artifact instead. This changes more than this card: `agent_complete.output_length` for the build steps (the PARITY-09 goldens), the inline human review card for a gated build step (it would show a confirmation, not the HTML), and the IN-05 lineage walk (`engine.py:7846`, which matches typed content to the final output). Needs an owner decision.
c. Declare the writer in the manifest (a per-step flag the compiler validates). New schema; no shipped workflow needs it yet.

## Verification note for ISS-683

Verify the ISS-683 fix with a NON-editing post-build step (a reviewer that only reads), as the QA-KB-022 report describes. Calling an editing step's replaced reply a failure of that fix would be a false negative; it is this card.
