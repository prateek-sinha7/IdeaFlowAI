# FIX-748

## What was wrong

Bug report QA-KB-060. The root cause and blast radius come from the analysis on
[ISS-923](20261001-2223-ISS-923.md) (CONFIRMED by a code read; the sink half was run offline). They are not re-derived here.

The `/workflows/{id}/edit` seed effect (`frontend/src/app/[...view]/page.tsx:3784-3834`) writes the seed only in its
`.then`. Its `.catch` handles 401 (session expiry) and 403/404 (not-found) and nothing else. A 5xx, a timeout or a
network failure leaves `initialSavedComposition` at `null`. The composer mounts anyway, because `workflow-edit` maps
to `"composer"` synchronously. DashboardLayout keeps the key `"new"` and passes `initialUserWorkflowId={undefined}`
(`DashboardLayout.tsx:3226`, `:3265`). ComposerPage could not tell this state from a legitimately blank
`/workflows/new`. FIX-698's `seedUnresolved` reads `builtinCanvasType`, which is undefined on `/edit`. So Save
workflow stayed live, and `handleSave` called `saveUserWorkflow(token, undefined, ...)`
(`ComposerPage.tsx:930`). That is the create branch (`frontend/src/lib/api.ts:2644-2654`): `POST /api/user-workflows`, a new
row, never a PATCH of the row being edited. The same props reach ComposerPage while the GET is still in flight
(the loading half, [ISS-1033](20261002-1055-ISS-1033.md) (a)).

## What changed, and why there

There are three small hunks. All follow the card's "Fix: where it belongs", and none is inside the `/edit` effect:

1. `frontend/src/app/[...view]/page.tsx:4255-4256`. One prop beside `builtinCanvasType`:
   `expectedUserWorkflowId={workflowEditIdFor(parsedView)}`. Only page.tsx knows that the URL names a saved row.
2. `frontend/src/components/layout/DashboardLayout.tsx:356-358` (optional prop), `:513` (destructure) and `:3253`
   (forwarded to ComposerPage next to `builtinCanvasType`).
3. `frontend/src/components/workflow/composer/ComposerPage.tsx:163-165` (optional prop), `:225` (destructure), and the
   ONE existing predicate extended at `:1261-1265`:

   ```ts
   const seedUnresolved =
     (!!builtinCanvasType && !initialManifestSteps?.length && !initialAgentIds?.length) ||
     (!!expectedUserWorkflowId && !userWorkflowId);
   ```

   The existing `disabled={saving || seedUnresolved}` (`:1407`) and its tooltip (`:1412`, "This workflow has not loaded.
   Reload the page to retry.") now also cover `/edit`.

Why there: ComposerPage is the single Save sink. `handleSave` has one call site, the Save button. One entry point
(`SavedWorkflowsPage.tsx:222`), one link (`WorkflowDetailView.tsx:80`) and every typed, refreshed or shared URL all
converge on the one effect and the one button. `grep` confirms that DashboardLayout has one mount site (`page.tsx:4176`)
and ComposerPage has one (`DashboardLayout.tsx:3205`). The gate releases itself. A successful seed flips the
DashboardLayout key, which remounts ComposerPage with `userWorkflowId` set. `/workflows/new` gets no
`expectedUserWorkflowId` and keeps a live Save. `AgentsPopup.tsx:2797`, the other `saveUserWorkflow` caller, takes its
id from a sessionStorage hand-off and is not affected.

The card names these alternatives as non-substitutes, and none was done: widening `workflowEditAccessDenied`, a retry
in `userWorkflowsApi.get` or `http.ts`, PATCHing by the URL id on a failed seed (destructive), a guard only inside
`handleSave`, per-entry-point guards, and a page.tsx `return null` loading gate (an ADR-0014 design call).

## Test change, made on the card's instruction (an assertion was NOT changed)

The test-writer's over-blocking guard ("Save workflow is enabled once the row id arrives",
`ComposerPage.iss923.test.tsx:61-66`) delivered the late seed with a plain `rerender`. ISS-923's own test recipe
(step 2) says that test needs a `key`: "a plain rerender does not re-run `useState` initializers, and DashboardLayout's
key flip is what delivers the seed in the app". With the card's predicate the unkeyed form went red
(`expect(element).toBeEnabled()`). A probe shows the unkeyed state is a real bug, not over-blocking (probe A, below).
After a plain rerender, the id `handleSave` sends is still `undefined`, so an enabled Save there would POST a new row.
The only test edit adds `key: "wf-123"` to that rerender, plus a one-line comment saying why. `toBeEnabled()` is
unchanged. No application line was shaped to the test. The obvious way to turn the unkeyed form green was to gate on
the `initialUserWorkflowId` prop or to sync state from the prop in an effect, and both were rejected. The first
releases Save while the create branch is still armed. The second adds behaviour no card asked for.

## Not fixed here

- [ISS-1033](20261002-1055-ISS-1033.md) (b), still open. A seed that lands after the user typed remounts ComposerPage
  through the key flip and silently drops what was typed. This gate closes the Save half, (a), because an in-flight GET
  and a failed GET give ComposerPage identical props. It does not touch the remount. Closing (b) needs a render-side
  hold for `/edit` (the `/run` `return null` pattern). ISS-923 calls that a design call because it unmounts
  DashboardLayout (ADR-0014 double-mount hazard), and it is not needed to close QA-KB-060.
- The tooltip copy says "has not loaded. Reload the page to retry." during a normal in-flight load as well. It is
  FIX-698's existing text, it shows on hover only, and the card adopted it deliberately. It is unchanged.
