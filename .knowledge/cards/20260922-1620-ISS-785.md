## Root cause

`frontend/src/app/[...view]/page.tsx`'s `handleWebSocketMessage` has 12
`getWorkflows(token, { limit: 50 })` call sites bound to SSE event types
(`pipeline_complete`, `questionnaire_ready`, `questionnaire_complete`,
`review_gate_ready`, `review_gate_approved`, `pipeline_failed`,
`pipeline_diverted`, `pipeline_cancelled`, etc). These exist to refresh the
recents list when a **live** run's status genuinely changes.

`handleSelectWorkflowRun` (page.tsx, opening a run from history) replays the
completed run's entire durable event log through this same
`handleWebSocketMessage` handler — the handler has no way to distinguish a
replayed historical event from a live SSE frame, so every matching event in
the log still fires its `runs?limit=50` refetch. A run with plan -> clarify ->
gate -> approve -> complete fires 5-6 of these bindings.

Each `setRecentRuns(newArray)` call creates a new array reference, which
`frontend/src/components/history/WorkflowHistory.tsx:248`'s
`useEffect([recentRuns])` picks up and fires a **second, independent**
`getWorkflows(token, { limit: 50 })` for — doubling every page.tsx refetch.

Additional unconditional sources compound the count: `page.tsx:968` (auth
mount), `store/listenerMiddleware.ts:55` (`signedIn` -> `fetchRecentRuns`),
and `RunConnectionProvider.tsx:289` (`refreshLiveRuns` on boot, plus
`RunConnectionProvider.tsx:336` on every `visibilitychange`/`online`).

`getRunEvents` is called once for the primary run and once per revision-family
member in `Promise.allSettled` (page.tsx ~2968); combined with the page.tsx
mount fetch and the replay path, the events/family endpoints are each hit
2x-4x per run open.

## Expected vs actual

Expected: opening a completed run fires ~4-6 requests (`runs/{id}` once,
`runs/{id}/events` once, `runs/{id}/family` once, `runs?limit=50` once at
mount).

Actual: 8-14 `runs?limit=50` calls and 3-4x duplicated `/family`/`/events`
calls per completed-run open, all three cycles.

## Status after FIX-624 (2026-09-22)

The replay half of this card is **fixed** by
[FIX-624](20260922-2027-FIX-624.md): `handleWebSocketMessage` took an
`isReplay` parameter and all eight of its `getWorkflows(limit: 50)` bindings now
read `recentsToken()`, which is null during a replay. Measured on this card's
own attempt-1 run (`8088430c-…`): `runs?limit=50` calls made by the CLICK went
3 -> 1, and the one that remains is `DashboardPage.useEffect`, not
`handleWebSocketMessage`
(`evidence/qa-ps-038/07-fix-click-phase-before-after.txt`).

This card stays **open** because its "Expected" is not reached and cannot be
reached from the files in its own `globs`:

- the residual `runs?limit=50` / `runs?limit=6` calls are the app-shell mount
  fetches (`store/listenerMiddleware.ts`'s sign-in preload and `page.tsx`'s
  `recentRuns` fetch that feeds the header badge) — the pending product decision
  in [ESCALATIONS.md#qa-ps-035](../../ESCALATIONS.md#qa-ps-035), whose own text
  says the same answer applies to QA-PS-036 and QA-PS-037;
- the `/events` x2 and `/family` x2-4 counts measured here are
  [ISS-840](20260922-2030-ISS-840.md) (the reopen runs twice per click) plus
  [ISS-804](20260922-1646-ISS-804.md), not the SSE-replay mechanism this card
  root-causes.

Correction to this card's own text, confirmed by stack trace rather than
reasoning: the "doubled by `WorkflowHistory`'s `useEffect([recentRuns])`" claim
did not show up in any post-click capture — not one `runs?limit=50` came from
`WorkflowHistory` after the click, with or without the fix.

## Decision — 2026-09-23 (user, option a)

For **QA-PS-038** the user chose option (a) (`ESCALATIONS.md#qa-ps-038`, recorded
01:34): the app shell's one `GET /api/runs?limit=50` (AppHeader's "N Running"
badge, the SSE live-run re-attach) and one `GET /api/workflows` per page are
intended. Counting the shell's per-document run-list fetches against this bug's budget is superseded by that decision, and
`test_qa_ps_038_run_detail_duplicate_requests.py` now counts only the reopen
click (collection starts once `/runs` has settled) and asserts at most one; the
`/events` and `/family` expectations stay with ISS-840 and ISS-804. The waste that needed no decision — `runs?limit=6` preloaded on every
route, and a second owner of `runs?limit=50` — is removed by
[FIX-640](20260923-0207-FIX-640.md). Observed green on 2026-09-23 once the frontend was back on :3000: the
re-scoped test XPASSed (strict), its marker was removed, and a plain re-run
PASSED — `tests/integration/test-runs/2026-09-23T02-15-fix-640-qa-ps-038/`, then `2026-09-23T02-17-fix-640-qa-ps-038-plain/`.
