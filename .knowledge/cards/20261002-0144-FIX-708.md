## What was wrong

Register entry QA-KB-035. The root cause and blast radius come from [ISS-676](20260917-1447-ISS-676.md)
(root) and [ISS-927](20261001-2224-ISS-927.md) (sibling). They are not re-derived here.

The live terminal block in `frontend/src/app/[...view]/page.tsx` (working tree `:1833-1879`) is the
only handler of `pipeline_cancelled` and `pipeline_failed`. Its page-level writes sat behind
`if (!isForeignFrame)`, which only asks whether this tab launched the run. Every run this tab
launched passes that check, including a background run that is not on screen. A background run's
terminal frame therefore ran `setReviewGateData(null)`, `setQuestionnaireData(null)` and
`setActivePipelineRunId(null)`, and on cancel also `setLastCancelledRunId(<BG>)`. All four slots
belong to the run on screen (`trackedRunIdRef`).

Per ISS-676's analysis, the first three are masked today: the lane reads the per-run store, and the
chat run id is held by `planner_start`. `setLastCancelledRunId` has a live reader.
`handleResumeRun` (`DashboardLayout.tsx:2530`) ranks it first, so "Run again" and "Reopen & fix"
could resume the cancelled background run (ISS-927).

## What changed, and why there

One hunk in the terminal block, the single place every caller of `handleWebSocketMessage` routes
through (the live SSE subscription and the three replays). The guard reuses the shared predicate
already imported at `page.tsx:22`, `isForeignRunFrame` (`frontend/src/lib/wsReplayState.ts:80-86`).
That predicate is false unless both ids are known and differ.

```ts
if (frameRunId) runStore.update(frameRunId, { questionnaireData: null });
const isBackgroundFrame = isForeignRunFrame(frameRunId, trackedRunIdRef.current);   // :1852
if (!isBackgroundFrame) {
  setReviewGateData(null);
  setQuestionnaireData(null);
  setActivePipelineRunId(null);
}
...
if (cancelledId) {
  if (!isBackgroundFrame) setLastCancelledRunId(cancelledId);                       // :1866
  detachRunRef.current?.(cancelledId);
}
```

These stay unconditional, as both cards require:
- `setBackgroundRunTransition`, which already has its own `frameRunId !== trackedRunIdRef.current` check (ISS-648).
- The per-run `runStore.update(frameRunId, ...)`.
- `detachRunRef`.
- `patchRecentRunStatus`.

The literal `if (!isForeignFrame)` wrapper is kept, so the source locks in `liveRunSwitch.fix201.test.ts` and
`terminalReopenReconcile.source.test.ts` still find it. No six-space `return;` was added inside the
block, so their slice end is unchanged.

The three replays point `trackedRunIdRef` at the replayed run before replaying, so for them
`frameRunId === tracked` and nothing changes. The hunk is saved at
`evidence/qa-kb-035/08-fix-page-tsx-hunk.diff`.

## Not changed (residuals named by the analysis)

- With `trackedRunIdRef.current === null` (the remount window) or a frame that has no run id, the
  predicate is conservative and behaviour is the same as before. ISS-676 records both as residual.
- The `pipeline_failed` chat bubble (`setMessages` under `!isForeignFrame`) has the same guard shape.
  Its page-level `messages` is never rendered (`DashboardLayout.tsx:3283`, `runChatMessages ?? messages`),
  so neither card asks for a change there.
- `lastCancelledRunId` is only ever cleared by a non-foreign `pipeline_start`. ISS-927 records this as an
  independent staleness question that the ISS-676 root cause does not imply.
- Not reproduced in a browser. Per ISS-676, the lane symptom is masked and a faithful repro needs two
  concurrent paid runs. All proof is the offline slice above.
