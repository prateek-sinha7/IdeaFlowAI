## What happened

On the run-history list, a run reached by a divert shows a
`← Continued from {X}` breadcrumb. T41/T42 persisted `diverted_at_step_id` and
threaded it all the way to the UI so the badge could name the step — and the badge
never printed it.

## Root cause

`frontend/src/components/history/RevisionFamilyView.tsx:472`. `DivertBadge` built
its text from the label alone:

```js
const text = link.direction === "source"
  ? `Diverted to ${otherLabel} →`
  : `← Continued from ${otherLabel}`;
```

The data was all present and covered: `buildDivertLinks` sets
`stepId: run.divertedAtStepId ?? undefined` (`RevisionFamilyView.tsx:255`), and its
own unit tests assert that — they pass. Only the render dropped it, which is why
nothing else caught it. The surrounding code comment explains a DIFFERENT,
deliberate change (the breadcrumb names the other run's WORKFLOW, not its title)
and says nothing about the clause, so this reads as collateral in that edit rather
than an intent.

## The fix

```js
const stepClause = link.stepId ? `, step ${link.stepId}` : "";
const text = link.direction === "source"
  ? `Diverted to ${otherLabel} →`
  : `← Continued from ${otherLabel}${stepClause}`;
```

Omitted when genuinely absent — a pre-migration historical row has no
`divertedAtStepId`, and the test pins that case separately.

## Test expectation that legitimately moved

The same three render tests also expected the badge to name the RUN
(`"Diverted to Run B →"`). It names the WORKFLOW (`"Diverted to Prototype →"`), and
that IS deliberate — `RevisionFamilyView.tsx:465-468`: a run's own title already
identifies it on its own row, so the breadcrumb's job is to say what the link goes
TO. Expectations updated to the workflow label; the step clause was restored in the
component instead, because there the data and its tests said the render was wrong.
