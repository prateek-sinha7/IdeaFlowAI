## What was wrong

`DashboardLayout.tsx` had two consumers that tested `effectiveReviseType` for deck
runs but only matched `"ppt"` and `"ppt_revision"`:

1. **`activeReviseHandler`** — the conditional chain that resolves which revise
   callback to surface in the lane header. A `ppt_v2` run matched none of the
   arms and resolved to `undefined`, so the Revise affordance was absent.

2. **`laneActiveContent`** — the content slot selector for the chat lane's
   DeliverableCard filename derivation. A `ppt_v2` run fell through to
   `userStoryContent` (the final `else` branch), causing
   `deriveDeliverableFilename` to be handed the wrong content slot AND a type
   string its own `ppt` branch never matched — producing the generic fallback
   label `"deliverable"` instead of the correct deck filename.

Root cause: `ppt_v2` is a deck pipeline (spec 017) that produces the same HTML
deliverable as `ppt` (it also emits a real `.pptx`). `page.tsx` already routes
`ppt_v2` output to `setPptContent` (`pipeline_complete` handler line ~1534).
The two consumers in DashboardLayout just never included the type string.

## What changed and why there

**`activeReviseHandler`** — added `|| effectiveReviseType === "ppt_v2"` to the
first arm's condition alongside `"ppt"` and `"ppt_revision"`. `handleRevisePpt`
is the correct handler because the revise path (REST POST /revisions) is
type-agnostic and `ppt_v2` runs are revised the same way as `ppt`.

**`laneActiveContent`** — added `|| effectiveReviseType === "ppt_v2"` to the
first arm's condition so `pptContent` is selected (the content slot `page.tsx`
already populates for `ppt_v2`).

Both changes are surgical single-condition additions. No other logic touched.
SC-001-safe: keyed on the pipeline type string from `effectiveReviseType` (a
server-derived value, not a workflow-name branch added to a guarded component —
`DashboardLayout` is not under the SC-001 name-free kernel ban).
