## Root cause (CONFIRMED by source read, INFERRED as a live defect pending repro)

`frontend/src/lib/routes.ts:224-229`:

```ts
if (head === 'login') {
  return { screen: 'login' };
}
```

Matches on `segments[0] === 'login'` alone — no `segments.length === 1` check, the identical
shape ISS-238 documents for the `register` branch seven lines below it. `parseViewPath(['login',
'anything'])` returns `{ screen: 'login' }`, indistinguishable from the exact `/login` path.

Like `register`, the literal `/login` is served by its own static Next.js route
(`frontend/src/app/login/page.tsx`) — Next's App Router only lets a literal segment folder
intercept its own EXACT path, so any deeper sub-path (`/login/anything`) is not matched there and
falls through to the root `[...view]` catch-all instead.

Grepped `frontend/src/app/[...view]/page.tsx` for `screen === "login"` / `'login'` (both quote
styles) and the literal token `'login'`/`"login"` anywhere in the file: **zero hits** — the same
result ISS-238 reports for `register`. No switch arm or if-branch anywhere handles `screen:
'login'`. Specifically, `initialMainViewFor` (page.tsx:107-174) has no `case "login":`, so it
falls to `default: return undefined;` (line 171-172).

Traced one hop further than ISS-238's own writeup: that `undefined` becomes the `initialMainView`
prop passed to `DashboardLayout` (page.tsx:3883-3891). `DashboardLayout.tsx:515-530`'s
`useState<MainView>` initializer reads `if (initialMainView) return initialMainView;` — false —
then checks a pending-wizard `sessionStorage` flag — also false — and falls to `return "home";`.
That is the literal line that renders dashboard content under the bogus `/login/<sub-path>` URL.
This is the same final mechanism ISS-238's fix direction targets; this card adds the
`DashboardLayout.tsx:515-530` confirmation for the record.

`routes.login()` (`routes.ts:25-27`) only ever builds `/login${queryString}` — no in-app
navigation ever constructs a deeper `/login/*` path — so, like `register`, this is reachable only
via a typed, shared, or otherwise hand-built URL, never through the app's own UI.

## Expected vs actual

- **Expected:** an authenticated user hitting a nonexistent sub-path under `/login` gets a
  404/not-found (the existing `if (parsedView.screen === "unknown") { notFound(); }` gate at
  page.tsx:3724), or an actual redirect — URL and content should agree.
- **Actual (INFERRED, not yet reproduced):** by the same mechanism ISS-238 confirmed 3/3 for
  `/register/<sub-path>`, `/login/<sub-path>` should leave the address bar on the bogus URL while
  the dashboard silently renders underneath it.

## Why the root cause implies this

ISS-238's root cause is "a `parseViewPath` head-only match with no depth guard, for a screen
`[...view]/page.tsx` has zero branches for." That description is not specific to `register` — it
is the literal shape of the `login` branch seven lines above it in the same function, verified by
the same zero-grep-hits result in page.tsx and the same `initialMainViewFor` default fallthrough.
Filed as a separate card because it fires on a distinct URL prefix and is a separately
reproducible symptom, not a rewording of ISS-238.
