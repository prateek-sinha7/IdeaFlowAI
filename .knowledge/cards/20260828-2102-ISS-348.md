## Root cause (CONFIRMED by source read, INFERRED as a live defect pending repro)

`frontend/src/lib/routes.ts:224-229`:

```ts
if (head === 'login') {
  return { screen: 'login' };
}
```

Matches on `segments[0] === 'login'` alone — no `segments.length === 1` check, the identical
shape ISS-238 documents for the `register` branch seven lines below it. `parseViewPath(['login',
'anything'])` returns `{ screen: 'login' }`, indistinguishable from the exact `/login` path.

Like `register`, the literal `/login` is served by its own static Next.js route
(`frontend/src/app/login/page.tsx`) — Next's App Router only lets a literal segment folder
intercept its own EXACT path, so any deeper sub-path (`/login/anything`) is not matched there and
falls through to the root `[...view]` catch-all instead.

Grepped `frontend/src/app/[...view]/page.tsx` for `screen === "login"` / `'login'` (both quote
styles) and the literal token `'login'`/`"login"` anywhere in the file: **zero hits** — the same
result ISS-238 reports for `register`. No switch arm or if-branch anywhere handles `screen:
'login'`. Specifically, `initialMainViewFor` (page.tsx:107-174) has no `case "login":`, so it
falls to `default: return undefined;` (line 171-172).

Traced one hop further than ISS-238's own writeup: that `undefined` becomes the `initialMainView`
prop passed to `DashboardLayout` (page.tsx:3883-3891). `DashboardLayout.tsx:515-530`'s
`useState<MainView>` initializer reads `if (initialMainView) return initialMainView;` — false —
then checks a pending-wizard `sessionStorage` flag — also false — and falls to `return "home";`.
That is the literal line that renders dashboard content under the bogus `/login/<sub-path>` URL.
This is the same final mechanism ISS-238's fix direction targets; this card adds the
`DashboardLayout.tsx:515-530` confirmation for the record.

`routes.login()` (`routes.ts:25-27`) only ever builds `/login${queryString}` — no in-app
navigation ever constructs a deeper `/login/*` path — so, like `register`, this is reachable only
via a typed, shared, or otherwise hand-built URL, never through the app's own UI.

## Expected vs actual

- **Expected:** an authenticated user hitting a nonexistent sub-path under `/login` gets a
  404/not-found (the existing `if (parsedView.screen === "unknown") { notFound(); }` gate at

- **Actual (INFERRED, not yet reproduced):** by the same mechanism ISS-238 confirmed 3/3 for
  `/register/<sub-path>`, `/login/<sub-path>` should leave the address bar on the bogus URL while
  the dashboard silently renders underneath it.

## Re-analysis (QA-KB-012 analyzer, 2026-10-01)

**Verdict.** The root cause above is CONFIRMED and its meaning is unchanged, so this is an in-place

### Root cause (CONFIRMED)

`parseViewPath` returns `{ screen: 'login' }` for any path whose first segment is `login`, because
the branch has no `segments.length === 1` check (`frontend/src/lib/routes.ts:256-261`):

```ts
if (head === 'login') {
  // Extract query params from the URL if they exist
  // Note: parseViewPath only receives segments, not query params directly
  // Query params must be handled at the call site using useSearchParams
  return { screen: 'login' };
}
```

The causal chain, each link read in source:

1. `app/login/page.tsx` owns only the exact `/login`; `app/login/` has no children (app tree
   listing), so `/login/<x>` reaches the root `[...view]` catch-all.
2. `page.tsx:425-426` builds `viewSegments = pathname.split("/").filter(Boolean).map(decodeURIComponent)`
   and calls `parseViewPath`. It gets `{ screen: 'login' }`.
3. No code consumes that screen: a grep of `frontend/src` (non-test `.ts`/`.tsx`) for
   `screen === 'login'|'admin'|'register'` and `case 'login'|'admin'|'register'` returns nothing.
   `initialMainViewFor` (`page.tsx:133-199`) has no `login` case and ends `default: return undefined;`
   (`page.tsx:197-198`).
4. `DashboardLayout`'s `useState<MainView>` initializer (`DashboardLayout.tsx:568-584`) skips
   `if (initialMainView)`, skips the pending-wizard `sessionStorage` check, and returns `"home"`
   (`DashboardLayout.tsx:583`). That paints the dashboard under the bogus URL.
5. The only hard-404 gate, `if (parsedView.screen === "unknown") { notFound(); }`
   (`page.tsx:4044-4046`), is never reached because the parser never returns `unknown` for this path.

Executed, not just read: a copy of the current `routes.ts` run under Node type-stripping (scratch script
outside the repo):

### Adjacent states (CONFIRMED by reading, not newly reproduced)

- **Unauthenticated:** `page.tsx:922-927` sends a no-token visitor to `buildLoginRedirect()`, here
  `/login?redirect=%2Flogin%2Fanything` (`lib/authRedirect.ts`). The render gate at `page.tsx:4035`
  returns null before the `unknown` gate, so after the fix they still redirect and never see the 404 first.
- **Post-login replay:** `login/page.tsx:70` pushes `resolveRedirectTarget(...)`, and
  `isSafeRedirectPath('/login/anything')` is true. Today signing in lands on the bogus URL with the
  dashboard; after the fix it lands on the 404 page, which is already how every unknown redirect target
  behaves.
- **Exact `/login`, authenticated:** served by `app/login/page.tsx`, which does
  `router.replace(resolveRedirectTarget(...))` (`login/page.tsx:57-58`), never by the catch-all. The
  guard cannot affect it.
- **Trailing slash / empty segments:** `.filter(Boolean)` (`page.tsx:425`) drops empties, so `/login/`
  yields `['login']`, and `next.config.ts` sets no `trailingSlash`. Unaffected.
- **State- or style-dependent?** No. The parser is a pure function; theme, viewport and tier cannot
  change the result. Concurrency (two tabs, double submit) does not apply.

### Fix: accept the agreed minimal fix, with two corrections

Accept `if (head === 'login' && segments.length === 1) {` plus a short ISS-348 comment mirroring the
register one (`routes.ts:263-266`). It is the same one-conjunct shape as
[FIX-344](20260828-2046-FIX-344.md) (register) and [FIX-462](20260901-2100-FIX-462.md) (analytics),
keyed on `segments.length === 1` rather than an enumeration of sub-paths. It belongs in `parseViewPath`
because every consumer routes through it. A `notFound()` for `login` in `page.tsx` would add a second
URL-interpretation site against [ADR-0018](20260824-1631-ADR-0018.md) and leave the telemetry label
wrong. `DashboardLayout`'s "home" fallback is deliberate for screens with no MainView
(`DashboardLayout.tsx:337-343`), so it must not change.

1. **Stale anchor.** The notes' `routes.ts:224` is wrong; use the code text (line 256).
2. **Apply with QA-KB-013.** The `admin` guard (`routes.ts:480`, [ISS-349](20260828-2102-ISS-349.md))
   is the same function and the same test file. FIX-344 recorded that these guards edit one file and
   must not run concurrently, so one fixer pass or strictly serialized.

Rejected alternative: deleting the `login` / `admin` branches. It would break the round-trip tests
above and contradict the documented route table, which lists `/login` and `/admin` as routes
(`specs/015-frontend-routing/contracts/route-map.md:13` and `:87`) and defines no sub-paths for either.

### Invariants at risk (for a naive fix)

- [ADR-0018](20260824-1631-ADR-0018.md): `routes.ts` is the single place URLs are parsed. A fix in
  `page.tsx` or `DashboardLayout` breaks that. Its corollary, "an unrecognised path must resolve to a
  typed screen, never fall through to `unknown`", concerns app-generated catalog URLs such as
  `/create/{type}`. `routes.login()` and `routes.admin()` only ever emit the exact path, so a hand-typed
  `/login/<x>` is not covered by it.
- The `unknown` -> `notFound()` gate at `page.tsx:4044` is the project's one hard 404 and the family
  fixes rely on it. Do not add a second 404 branch.
- SC-001 and the import-linter contracts: not involved (frontend only; the contracts govern backend
  Python packages).
