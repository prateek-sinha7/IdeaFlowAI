# FIX-697

Resolves [ISS-683](20260904-ISS-683.md) (bug line QA-KB-022). The analysis on that card was applied
as written; nothing here re-derives it.

## What was wrong

After a `single_file` build step wrote the declared deliverable, every LATER step whose reply was
shorter than the file (a validator, reviewer or reporter) had its recorded output replaced by the
file: its `results[]` entry, its typed artifacts, its `.agents/NN-*.md` transcript,
`agent_complete.output_length` and the inline review card. The committed prototype goldens pinned
it: `prototype-validate` `output_length` 84, the length of the scripted `prototype.html`, while its
reply is 32 characters.

## Root cause (from ISS-683, confirmed by the failing test before the edit)

`backend/agents/execution_engine/engine.py`, `ExecutionEngine._run_agent`, the single_file readback
(engine.py:10626-10636 before this change):

```python
_deliv_name = getattr(_deliv, "name", None) or "prototype.html"
file_from_disk = sandbox.read(_deliv_name)
if file_from_disk and len(file_from_disk) > len(output):
    ...
    output = file_from_disk
```

The swap depended on the file's state only, never on whether THIS step produced the file.

## What changed, and why there

Two hunks in `engine.py`; no other production file:

1. engine.py:10025-10035, directly above `output_chunks: list[str] = []` inside the redo loop's
   `try`: `_pre_step_deliverable`, the declared file read before the step streams. Read only when
   `deliverable.strategy == "single_file"`; a read failure leaves it `None` (strict-UTF-8 reads must
   not fail the step). Same idiom as `task_loop.py:383-387` (WR-05 `pre_fix_html`). Being inside the
   loop, every redo, loop-back revisit and `task_loop` task takes its own snapshot.
2. engine.py:10640-10644: the readback condition gains `file_from_disk != _pre_step_deliverable`.
   Every existing conjunct is kept verbatim (`len(file_from_disk) > len(output)`,
   `not _is_decision_step`, `not is_revision_workflow`), so the source slice in
   `tests/agents/test_deliverable_readback_gate.py` still holds.

Why there: every step runs through `ExecutionEngine._run_agent`, re-grepped on 2026-10-01:
`single_shot.py:60`, `parallel_group.py:139` and `task_loop.py:357` via `KernelServices.run_agent`
(`kernel_services.py:2049`); fan-out workers and merge agents (`kernel_services.py:1113`, `:1301`);
the spec-revision sub-pipeline (`engine.py:12066`). The block is the only copy (`file_from_disk`
appears nowhere else under `agents/` or `app/`), so one guard covers every caller. No workflow or
agent name, no new import, no migration.

## Test correction: card-justified, stated explicitly

`backend/tests/unit/agents/test_deliverable_readback_scope.py` asserted
`not any("<!doctype" in repr(t).lower() for t in typed[1:])`. `typed` records EVERY
`_dual_write_artifact` call, and `prototype-build` makes two: its declared `html_file` and its own
step artifact. So `typed[1:]` includes the writer's own artifact, which ISS-683 requires to be the
file ("the writer keeps the file"), as does the same test's first assertion,
`results[0]["output"] == BIG_HTML`. That assertion could not pass on any engine. Per-assertion probe
(scratch, engine swapped in memory, nothing written):

| assertion | pre-edit engine | fixed engine |
|---|---|---|
| writer `results[0]` is the file | pass | pass |
| reviewer `results[1]` is its findings | FAIL | pass |
| reviewer transcript has no HTML | FAIL | pass |
| `typed[1:]` has no HTML (as written) | FAIL | FAIL (writer's own artifact) |
| reviewer's typed writes non-empty, no HTML | FAIL | pass |
| last `output_length` == len(findings) | FAIL | pass |

The ISS-683 "For the test-writer" section asks for the REVIEWER's typed contents, so that one
assertion now selects `producer_agent == "prototype-validate"` and requires the set to be non-empty.
It still fails on the pre-edit engine (both reviewer artifacts were the HTML), so it still catches
the defect. No other line of the test changed, and the strict xfail marker stays for the 6-verifier.
The application was not changed to suit the test.

- `prototype.events.json:246`, `prototype.wsframes.json:287`: `prototype-build` task 2

  absent before it ran) still records the file (84). The build loop does not read that value:
  `task_loop.py:371-377` calls `persist_task_html` after every task, which re-reads the file
  (`kernel_services.py:2241`) and typed-writes it as `html_file` (`kernel_services.py:2244-2249`).

ISS-683's cheaper check, run first-hand on the scripted offline pipeline (`_drive("prototype")`):
`prototype-validate` `output_length` 32 and `.agents/05-prototype-validate.md` holds no HTML;
`04-prototype-build-t1.md` still holds the file.

## What this leaves

- [ISS-894](20261001-2123-ISS-894.md) stays open: a post-build step that EDITS the file (prototype_v2
  `pb-validate` and `pb-present`, legacy `prototype-validate` when it edits) changes the file, so it
  is still replaced. Options a/b/c there are a product decision.
- Two concurrent steps writing the declared file on one sandbox could be misattributed to each
  other. No shipped manifest has two concurrent writers of it; ISS-683 chose not to file this.
- A writer whose reply is longer than the file keeps its reply (the length conjunct is unchanged).
- If the pre-step read fails, `_pre_step_deliverable` is `None` and the step falls back to the old
  behaviour (replaced when the file is longer).
