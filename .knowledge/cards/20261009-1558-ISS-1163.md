# ISS-1163

**Register source:** sibling derived during the `QA-KB-126` analysis on 2026-10-09 (root [ISS-1114](20261008-1415-ISS-1114.md)). Not its own bug row; the fix is part of the root's change.

**Confidence:** CONFIRMED by an offline probe that drives the real `PATCH` and `POST /api/runs` handlers (in-memory SQLite, only `_launch_run_core` stubbed, so nothing was minted or spent): `evidence/qa-kb-126/analysis-01-probe-db-trust-doors-by-tier.txt`, block `[P]`. INFERRED: a run that executes the granted step. None was launched.

## Condition

`update_user_workflow` (`user_workflows.py:998-1093`) is the second writer of a plain row's manifest. It runs the model gate (`:1011-1018`) and the trigger gate (`:1021-1025`), then
`row.manifest_json = _validated_manifest(body.manifest, f"workflow:{row.id}", row.overrides_pipeline_type)` (`:1078-1083`). That compile is hard-coded `trust="db"` (`:121`). `can_run_pipeline` is called twice in the module, at create (`:744`) and at sync-from-file (`:1151`), and never here. The module docstring promises that a saved row "can never carry something launch would reject" (`:16-24`) and lists PATCH only "when `model_overrides` changes".

A row's `base_pipeline_type` is fixed at create (`UpdateUserWorkflowRequest` has no such field), so create's label gate cannot see what a later PATCH stores. The probe, as a `basic` caller:

1. `POST /api/user-workflows` with `base_pipeline_type: "ppt"` and `agent_ids: ["ppt-brief-analyst"]`, no manifest: 201. Nothing privileged yet.
2. `PATCH /api/user-workflows/{id}` with a manifest whose step has `tools.exec: true`, `gates: [security, approval]`: 200.
3. `POST /api/runs` with that `user_workflow_id`: 200; the plan handed to the mint holds `exec=True` and `gates=['security', 'approval']`.

## Expected vs actual

Expected: PATCH refuses what create and launch refuse; a basic-tier user cannot store an exec or spawn_subagents grant through any door. Actual: 200, and the stored row launches with the grant.

## Why the root cause implies it

[ISS-1114](20261008-1415-ISS-1114.md) is "the privilege comes from the compile trust, the entitlement from a label the caller chose". PATCH shows the label is not the only gap: this writer has no entitlement call at all, and nothing in the handler compares what it stores with the caller's tier. The obvious fix for the root, a stricter check on `body.base_pipeline_type` in create, never touches this handler. It is also the door a downgraded owner uses, because create's gate ran once, under the old tier.

## Fix direction (INFERRED, not applied)

The same change as the root, not a second mechanism. `update_user_workflow` already holds the principal, so it passes `_validated_manifest` the trust that the one shared helper returns for that caller, and `_validated_manifest` hands it to `_compile_check_manifest`. The `selections` branch (`:1063-1076`) already compiles at `user` and needs nothing.

## Resolution ([FIX-776](20261009-1628-FIX-776.md), 2026-10-09)

Resolved by the root's change, as the fix direction above says. `update_user_workflow` passes
`_saved_row_trust(effective_tier(current_user, principal))` to `_validated_manifest`, so a basic PATCH of an exec manifest onto a `ppt` row is
the compiler's 422 and `manifest_json` stays unchanged (`evidence/qa-kb-126/fix-01-probe-doors-after-fix.txt` `[P1]`; controls `[P2]` benign
PATCH 200 and `[P3]` enterprise PATCH onto a `custom` row 200). Proven by `test_patch_cannot_put_exec_manifest_on_basic_row` in the test
file above.
