## Status: CONFIRMED — read directly in source, and independently re-verified live (git + Postgres), not just taken from the task brief

The task brief handed me "Defect A" as already-proven. I re-proved it myself rather than
trusting the claim, and went one layer deeper: the brief describes the SYMPTOM ("revision runs
never write the deliverable back into the sandbox") correctly, but the deliverable in fact IS
written back correctly on every revision — just to the wrong path, which nothing downstream
consults. That refinement is what makes the fix location precise instead of a guess.

### Correction (self-identified, cross-checked against ISS-727 which independently found the same thing)

My first pass here claimed `ppt-revision-agent` has "no declared `tools:` that grant native
filesystem write." **That is wrong, and I verified the correction myself by reading
`backend/agents/factory.py:1306-1352` directly** (not by trusting `backend/CLAUDE.md`'s Tool
Sets table, which is stale on this exact point): the R-22/D-07 "empty tool set" rule —
`if not spec.tools and not custom_keys: return ([], False)` (`factory.py:1349-1352`) — means
`tools: []` STILL binds the native filesystem tools (`exclude_builtin=False`). The comment right
above it says so explicitly: *"filesystem read+write is bound for EVERY agent regardless of the
declared tool set."* So `ppt-revision-agent` genuinely HAS `write_file`/`edit_file` available.
The real gap (Layer 2, corrected below) is that its `AGENT.md` prompt never instructs it to use
them — a prompt-engineering gap, not a tool-binding one. This is a materially easier, more
surgical fix than "grant the agent a tool it's missing," and it is exactly what
[ISS-727](20260922-1235-ISS-727.md) already proposes.

## Root cause — CONFIRMED, two layers

### Layer 1 (universal, workflow-agnostic): the terminal commit can never re-stage a sandbox-root file

`backend/agents/execution_engine/engine.py:2179-2189` (`finalize_terminal_run`, "Step 6"):

```python
_snap_result = await commit_in_sandbox(
    _sandbox, _commit_msg, ectx, _snap_step,
    audit_operation="snapshot_commit",
    paths=[],          # already staged by build_flat_payload
    force_add=_built_payload.allowlist or None,
    ...
)
```

`force_add` is `_built_payload.allowlist`, and `payload_allowlist()` (`backend/app/agents/sandbox.py:268-291`)
is documented, in its own docstring, as: *"Return the exact three normalized paths that the
engine may force-stage... the ONLY exception to `RESERVED_PATHS`... these three exact paths and
no others."* Those three are always `.chain/logs.jsonl`, `.chain/<output_basename>`,
`.chain/summary.md`. **No code path ever re-stages a sandbox-root deliverable file at finalize
time, for any workflow, by deliberate design** (a reviewed security/audit boundary — Requirement
4 AC 11/14, V2-Q7 per the docstring at `sandbox.py:271-276`).

This alone would not matter if the per-STEP commit already captured a fresh root-level write —
and for a *file-writing* agent it does: `commit_in_sandbox`'s step-boundary call
(`engine.py:6141-6148`) stages via a full `git add -A` (docstring at `:6116`, "1. stage all
changes"). So Layer 1 only bites when Layer 2 is also true.

### Layer 2 (workflow-specific, CORRECTED): the revision agent HAS write access but is never prompted to use it

`backend/agents/workflows/ppt_revision/workflow.yaml:17-18` declares `deliverable.strategy: ppt`,
`name: presentation.pptx`. Under that strategy, `build_flat_payload` (`engine.py:1364-1392`)
sanitizes `ectx.last_streamed` into `_ppt_text` and materializes it ONLY at
`.chain.staging-{run}/presentation.pptx` → `.chain/presentation.pptx` (`:1470-1480`) — never at
`sandbox.root / "presentation.pptx"`. The revision agent itself never calls `write_file` for any
deliverable path — **not** because it lacks the tool (see "Correction" above: `tools: []` still
binds native fs tools, `factory.py:1306-1352`), but because `ppt-revision-agent/AGENT.md`'s
entire output contract asks it to *"Emit the complete modified HTML file wrapped in `<artifact>`
tags"* — a chat-stream instruction with no `write_file`/`edit_file` step anywhere in the prompt
([ISS-727](20260922-1235-ISS-727.md) quotes the exact prompt text). The model complies with what
it is asked; it has the tool and simply is never told to call it. So the per-step `git add -A`
(Layer 1's escape hatch) finds nothing to stage either — not because the tool was withheld, but
because nothing on disk ever changed. Confirmed live:

```
$ git -C runs/c6b9b61f…/e53d9b1f… log --stat --all
290ced1 chore: terminal snapshot run=dfeb5949…(v3)   .chain/logs.jsonl .chain/presentation.pptx .chain/summary.md
c4db0f7 step: ppt-revision-agent                     PLANNER.md only
ff04dee chore: terminal snapshot run=f7000bbd…(v2)   .chain/logs.jsonl .chain/presentation.pptx .chain/summary.md
0eaaae2 step: ppt-revision-agent                     PLANNER.md only
db8a748 chore: terminal snapshot run=e53d9b1f…(v1)   .chain/logs.jsonl .chain/presentation.pptx .chain/summary.md
98d9aa9 step: ppt-composer                           presentation.html (THE ONLY commit ever to touch this path)
```

`.chain/presentation.pptx` DOES change correctly on every revision (confirmed: v2 and v3 each
show a real diff there) — the revision's actual output IS produced and versioned correctly.
It is simply never at the path anything reads. `presentation.html` at sandbox root exists at all
only because `ppt-composer` (a *different*, file-writing agent, v1 only) hardcodes
`write_file("presentation.html", …)` directly — already carded as
[ISS-651](20260917-1200-ISS-651.md) (that card is about the FILENAME being generic, not
version-stale; this card is the first to explain the CONTENT staleness). Independently verified:
`git show v1:presentation.html`, `v2:…`, `v3:…` are byte-identical
(`<h1>Arctic Seed Vault Logistics</h1>` in all three); working tree is clean
(`git status --short` empty) and `git diff v1 -- presentation.html` empty — the file was never
even MODIFIED since v1, let alone committed.

### Why the frontend asks for `presentation.html` when the DB declares `presentation.pptx`

`resolveRunDeliverable` (`frontend/src/lib/api.ts:1183-1200`) takes the declared name
(Postgres-confirmed `deliverable_filename='presentation.pptx'` for all three runs in this
family), builds sibling candidates by swapping the extension (`.pptx` declared →
`[name, "<stem>.html"]`), and picks the first candidate present in the LIVE, unversioned
`getRunSandbox(token, runId)` listing. `presentation.pptx` never exists at sandbox root (only
inside `.chain/`, invisible to this candidate search), so the resolver falls through to
`presentation.html` — landing on exactly the one frozen, off-mechanism artifact. This explains,
for the first time, the task brief's own "unexplained… `deliverable_filename=presentation.pptx`
while the UI fetches `presentation.html`" footnote.

## mapsToKnownDefect: A (confirmed, refined — not overturned, not a new top-level defect)

The task brief's Defect A hunch is correct at the symptom level. This card and
[ISS-727](20260922-1235-ISS-727.md) — filed independently, concurrently, against sibling bugs
QA-PS-031 and QA-PS-030 respectively — converge on the same refined mechanism: not "never
written back" but "the revision agent has the write tool and never uses it, because its prompt
never asks it to." ISS-727's reading of the tool-binding question (`factory.py:1306-1352`) is the
more precise of the two and is what this card now cites (see "Correction" above, self-identified
and independently re-verified against source, not merely deferred to). This card's remaining
distinct value: the Layer-1 finding above is a genuine, separate caution about ONE possible fix
path (the engine-fallback route) that ISS-727's own recommended fix (agent prompt + tools,
matching `prototype_revision`'s precedent) does not need to worry about at all — see "Fix
location" below for which path avoids the trap.

## Fix location — primary recommendation, plus one alternative and its trap

**Primary (matches [ISS-727](20260922-1235-ISS-727.md)'s independently-derived recommendation,
which has real precedent — [FIX-111](20260724-FIX-111.md) already fixed the same CLASS of bug
this way for the base `prototype` pipeline):**

1. Give `ppt-revision-agent` a step-level write grant mirroring `prototype_revision`'s own
   `tools: {read_files: true, write_files: true}` override, and change its prompt from "emit an
   `<artifact>` block" to "read the current deck, then `edit_file` it in place" —
   `edit_file`, **not** `write_file`: the target already exists in the shared family sandbox, and
   `write_file` is documented (`backend/CLAUDE.md`) not to overwrite an existing file.
2. Resolve the `presentation.pptx` (declared `deliverable.name`) vs `presentation.html` (the
   literal string `ppt-composer` actually writes) naming split — either rename the declared name
   to match, or teach `resolveRunDeliverable` (`frontend/src/lib/api.ts:1183-1200`) about the
   mismatch. Needed either way, independent of which fix path is taken.

**Alternative considered (this card's own original proposal) — has a trap the primary path
avoids:** materializing `ectx.last_streamed` to `sandbox.root / _output_basename` inside
`build_flat_payload` (`engine.py:1313-1392`) instead of only `.chain/`. This is a smaller diff on
paper but hits Layer 1 directly: the terminal-snapshot commit that follows
(`engine.py:2179-2189`) passes `paths=[]` and relies ENTIRELY on `force_add=_built_payload.allowlist`
— and `payload_allowlist()`'s own docstring (`sandbox.py:268-291`) is explicit that its three
`.chain/` paths are "the ONLY exception to `RESERVED_PATHS`... and no others." A sandbox-root
write from `build_flat_payload` would NOT be captured by that specific commit call — it would
need EITHER a prior, separate commit (so the per-step `git add -A` catches it first, which is
exactly what the primary path already gets by construction) OR a deliberate widening of
`payload_allowlist`'s reviewed security boundary. **Do not widen `payload_allowlist`** — if this
alternative is chosen anyway, route the write through a step-boundary commit, not the
finalize-only one.

## Fix risk — what breaks if done carelessly

- Using `write_file` instead of `edit_file` on the primary path's point 1 reproduces the exact
  same no-op silently — this project already has one precedent for that exact mistake
  ([FIX-111](20260724-FIX-111.md)).
- Changing `deliverable.name` without also updating `ppt-composer`'s hardcoded write target (or
  vice versa) just moves the mismatch instead of closing it — see
  [ISS-651](20260917-1200-ISS-651.md), which already covers the filename-facing half of this
  same split for a different symptom (Files-tab display name); a fix should close both from one
  naming decision.
- `payload_allowlist`'s "exactly three, no others" contract is a reviewed security/audit
  boundary (own docstring: Requirement 4 AC 11/14, V2-Q7) — see the alternative's trap above; do
  not widen it as a shortcut.
- `create_tag_fn` (`engine.py:2374-2377`) tags whatever commit is HEAD after Step 6 — any fix's
  write has to land and get staged BEFORE that step-boundary commit, or the tag still points at a
  commit predating the file.
- Must not regress the "Latest (live)" DB-read path (`WorkflowRun.output`), which is CORRECT
  today — a fix should only ever make the sandbox-file readers agree with what that path already
  shows, never the reverse.
