## Related

## What was wrong

Fan-out workers were spawned concurrently (run_worker called in a gather loop) but
executed one at a time because each invocation acquired the run-wide `scratch_lock`
and held it through the entire `run_agent` call. Five parallel readers therefore
serialised and took 5× longer than necessary. Separately, DEFAULT_MAX_CONCURRENCY
was capped at 4, silently rejecting any max_parallel=5 declaration.

## The fix (commit 127b20a3d)

- Each worker call now receives `ectx_override=_copy.copy(self._ectx)` — a shallow
  copy isolating the worker's own scratch fields (current_step, build_task_number
  and friends) while keeping substrate objects (artifact graph, budget, sandbox,
  queues, completed_tasks) shared by reference.
- The worker's invocation skips the scratch_lock entirely (lock becomes `_NULL_LOCK`
  when ectx_override is supplied), so parallel workers can run concurrently without
  queuing on each other.
- `run_agent` branches: if ectx_override is provided, use it and skip the lock; else
  use self._ectx and acquire scratch_lock as before. Byte-identical for the
  non-fan-out path (no override supplied).
- DEFAULT_MAX_CONCURRENCY raised from 4 to 5 in backend/agents/execution_engine/budget.py.
