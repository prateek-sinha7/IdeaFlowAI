## Summary

INFERRED sibling of [ISS-319](20260828-1804-ISS-319.md), the root cause card for register
entry `BUG-20260828-094120-settings-ai-model-r2`. `PUT /api/settings/github-pat`
(`upsert_github_pat`, `backend/app/api/settings.py:114-176`) mutates a different per-user
singleton row but follows the IDENTICAL shape that produces ISS-319's false-success response:
mutate the row -> `db.commit()` -> `db.refresh(row)` -> build the response by reading fields
back OFF the just-refreshed object, instead of from values this request itself already holds.

Not reproduced — no test has fired two concurrent `PUT /api/settings/github-pat` requests. Filed
from the code-shape match alone; mark as INFERRED until reproduced.

## Why the root cause implies this

ISS-319's mechanism: two concurrent requests each get their own `Session` (both resolve
`Depends(get_db)` independently per request), race on one shared row's `commit()`, and whichever
request's `db.refresh()` executes AFTER the OTHER's `commit()` reports that OTHER request's
persisted values in its own "successful" response. `upsert_github_pat` has every precondition
that mechanism needs:

- A per-user singleton row, matched by owner id alone with no version/lock:
  `db.query(UserGithubCredential).filter(UserGithubCredential.user_id == user.id).first()`
  (`settings.py:149-153`) — same shape as `update_preferences`' `user` row.
- `db.commit()` then `db.refresh(row)` with no `with_for_update()`, no version column, no
  re-check in between (`settings.py:168-169`).
- The response reads `row.github_username` / `row.scopes` (`settings.py:171-172`) from the
  POST-refresh object — the exact "read-after-write, not the value this request itself sent"
  pattern that produces ISS-319's false-success.

Concretely: two concurrent `PUT /api/settings/github-pat` requests with different PATs (e.g. the
user re-pasting a corrected token right after a first submit, or two tabs) could cause the
losing request's `200` response to report the WINNING request's `github_username`/`scopes`
instead of its own — while that request's own PAT silently never reaches the DB. Note `last_4`
in the response (`settings.py:173`) is sourced from the LOCAL `pat` variable, not from `row`, so
it would NOT be wrong — a partially-correct, partially-fabricated response, arguably more
confusing than ISS-319's fully-fabricated one (a right last-4 digits paired with a wrong
username/scopes reads as "half saved").

## What would confirm or refute it

Fire two concurrent `PUT /api/settings/github-pat` requests with different PAT values
(`Promise.all`, the same pattern the ISS-319 validator used) and check whether the losing
response's `github_username`/`scopes` fields report the other request's GitHub account instead
of its own, and whether `GET /api/settings/github-pat` afterward shows one PAT silently
discarded with no error surfaced anywhere.

## Suggested fix (same shape as ISS-319)

Build the response's `github_username`/`scopes` from the LOCAL `gh_user`/`scopes_header`
variables already computed at `settings.py:145-146` (this request's own validated GitHub API
response), not from `row.github_username`/`row.scopes` post-refresh — mirrors whatever fix lands
for ISS-319's `update_preferences`.
