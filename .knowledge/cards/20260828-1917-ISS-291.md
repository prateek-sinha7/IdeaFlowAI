## Summary

On `/settings/usage` (Settings → Usage & Limits), the "Manage plan" button next to the
plan-name heading (`AccountSettings.tsx:448-457`) is rendered as an enabled, styled
`<Button variant="secondary" size="sm" className="... text-brand">Manage plan</Button>`
with **no `onClick` prop supplied at all** — line 454-456:

```tsx
<Button variant="secondary" size="sm" className="flex-shrink-0 px-3.5 py-2 text-brand">
  Manage plan
</Button>
```

This is not a handler that fails silently or an async call that errors — the component
simply never received a click callback, so nothing is wired to fire on click. For a
basic-tier account this leaves no in-app path to the backend's already-modelled
`UPGRADE_PATH: basic -> pro` (`backend/app/core/entitlements.py`), even though the
page's own copy promises one ("Your plan determines which deliverables you can run...
Manage plan").

## Reproduction (3/3, cycle 1 of 3 — no narrowing needed)

Register entry: **BUG-20260828-031600-settings-usage**.

- **Cycle 1** — qa-admin (enterprise tier), warm session, direct nav to `/settings/usage`.
  Clicked "Manage plan": `document.body.innerText.length` unchanged (472 before/after),
  `browser_network_requests` list identical before/after (no request fired), React fiber
  props inspection shows `typeof btn[reactPropsKey].onClick === 'undefined'`.
- **Cycle 2** — cold start: `localStorage.clear()` + fresh `/login`, signed in as
  `qa-basic@flowinqa.com`, fresh nav to `/settings/usage` ("Basic plan" heading, only 2 of
  8 deliverable types listed). Clicked "Manage plan": `innerText.length` unchanged
  (364 before/after), no new network request in the 59-75 request window.
  Screenshot: `bug-hunter/evidence/settings-usage/_scratch/cycle2-basic-after-click.png`.
- **Cycle 3** — same basic-tier session, hard nav to `/dashboard` then back to
  `/settings/usage` (fresh page load, not a soft re-click). `onClick` re-checked as
  `undefined` on the freshly-mounted button; clicked again, same no-op.
  Screenshot: `bug-hunter/evidence/settings-usage/_scratch/cycle3-basic-reload-after-click.png`.

3/3 reproduced identically across both tiers (enterprise admin, basic) and across warm
session / cold login / fresh reload entry paths — the defect is unconditional, not
axis-dependent. Root cause confirmed by direct source read:
`frontend/src/components/settings/AccountSettings.tsx:454-456` — the `<Button>` JSX has no
`onClick` attribute in the source, matching the runtime fiber-props finding exactly.

## Expected vs Actual

- **Expected:** clicking "Manage plan" opens some plan-management/upgrade affordance
  (modal, dedicated page, or at minimum a "contact sales" flow), giving a basic-tier
  account an in-app path toward the backend's real `basic -> pro` upgrade path.
- **Actual:** the button is a static, styled no-op for every tier — no network request,
  no DOM change, no navigation, no handler bound in the JSX at all.

## Analyzer findings — root cause, blast radius, fix location

Current source line numbers have drifted slightly (`AccountSettings.tsx:457-459`, not
454-456 — same JSX, same missing `onClick`; re-confirmed by direct read on 2026-08-28).

**Root cause (CONFIRMED):** this is not a wiring gap where a handler exists elsewhere and
was simply never attached — no such handler, modal, or page exists anywhere in the
codebase to attach. Confirmed by exhaustive grep:
- Frontend-wide, `"Manage plan"` occurs exactly once (`AccountSettings.tsx:458`) — no
  modal/dialog component, no second render site.
- `backend/app/api/` has no `billing`/`subscription`/`stripe` endpoint of any kind (grepped
  all matches; the only `plan`/`billing`/`subscription` hits are unrelated — workflow
  *execution* plans and run-cancellation-vs-billing races).
- All five `<Button>` elements in `AccountSettings.tsx` were checked individually
  (lines 321, 425, 457, 618, 627) — only the "Manage plan" button at 457 lacks `onClick`;
  the other four (Change Password, Save model, Clear/Save constitution) are correctly
  wired. This is an isolated omission, not a copy-paste pattern repeated across the file.
- `<AccountSettings>` has exactly one render site app-wide:
  `DashboardLayout.tsx:2849` (`frontend/src/app/handoff/settings/page.tsx` only mentions
  it in a comment, does not render it) — so the broken button exists at one runtime
  location regardless of entry route.

This is a missing feature, not a broken connection: the button was shipped as a visual
promise (styled, enabled, sits next to real plan-tier copy) with nothing built behind it.

**Blast radius (CONFIRMED):** `AppHeader.tsx:519-526` renders a second, independently-coded
"Upgrade" CTA in the account-menu dropdown for `userTier === "basic"`, whose `onClick`
calls `onNavigate("settings")` — landing the user back in this same `AccountSettings`
component, on its default section (not `routes.settingsUsage()` specifically), where the
only further "upgrade" affordance is this card's inert "Manage plan" button. `AppHeader` is
the persistent app shell (`MOD-frontend-src-components-layout`, mounted by `DashboardLayout`
on every screen), so every basic-tier user meets this promise repeatedly, not just on
Settings. Filed as [ISS-397](20260828-2105-ISS-397.md) (sibling, INFERRED pending live
click-through — the navigation itself is confirmed by source read, not yet driven in the
browser).

Two adjacent surfaces were checked and ruled OUT as siblings because they behave correctly:
`HomeLaunchGrid.tsx:288` and `CreationHub.tsx:81` both gate locked-tier workflow cards with
a real `disabled={!allowed}` plus a "Requires `<Tier>` plan" label and lock icon — inert by
design and clearly signaled as such, unlike "Manage plan" which is enabled, hover-styled,
and makes no visual distinction from a working control.

**Where the fix belongs:** not a bespoke `onClick` added only at line 457-459. Two
independent call sites (`AccountSettings.tsx:457-459` and `AppHeader.tsx:519-526`, via its
navigation target) both terminate at "no upgrade capability exists" — the smaller, root-cause
diff is one shared component (e.g. an `UpgradePlanModal`/`ContactSalesModal`, no new route
needed per ADR-0018 if it is a modal rather than a page) that both call sites open, rather
than each growing its own inline logic. A real billing/tier-change backend is out of scope
for this bug (`UPGRADE_PATH` in `backend/app/core/entitlements.py` only labels the next
tier, it does not action a change) — the achievable fix is an in-app acknowledgement of the
promise already made by both buttons' copy: at minimum a "contact your admin" / "request
upgrade" flow, consistent with what this card's own Expected section already named.
