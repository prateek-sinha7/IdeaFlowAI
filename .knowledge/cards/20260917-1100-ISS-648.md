# ISS-648

## Title

Background/non-viewed run's failure or cancellation is never reflected in its notification (stays `status: "running"` indefinitely), the same class of defect as QA-PS-002 ([ISS-644](20260917-0930-ISS-644.md)) applied to the failed/cancelled terminal states instead of the progress count.

## Status: INFERRED — not yet reproduced

Filed from the root cause of QA-PS-002, not from an independent reproduction. Whoever picks this up should confirm it live before treating it as a confirmed defect (see "What would confirm this" below).

## Why QA-PS-002's root cause implies this

QA-PS-002's confirmed mechanism ([ISS-644](20260917-0930-ISS-644.md)) is: `DashboardLayout`'s notification-updating effects are gated on `pipelineState` / `currentPipelineNotifId.current`, and both of those are scoped to whichever run is `runStore.viewed` — i.e. exactly one run at a time (`frontend/src/app/[...view]/page.tsx:3887`, `const displayedPipelineState = runStore.viewed.pipelineState;`, passed to `DashboardLayout` as the `pipelineState` prop at `:3926`). Any run that is not currently the viewed one never reaches an effect keyed only on that prop.

The SAME `currentPipelineNotifId.current`-only gating exists on the terminal failure/cancellation effect, and it has never been given the background-run bridge that the *completion* transition already received:

- `frontend/src/components/layout/DashboardLayout.tsx:905-917` — the ONLY place `markFailed`/`markCancelled` are called (`useNotifications.ts:166` and `:175`), gated by `if (currentPipelineNotifId.current)` alone — the viewed-run ref documented at `DashboardLayout.tsx:658-659` ("currentPipelineNotifId tracks the CURRENTLY VIEWED run's notif").
- Contrast with the *completed* transition: `frontend/src/components/layout/DashboardLayout.tsx:694-696` states in-code, "pipelineState only reflects the VIEWED run, so the standard completion effect... never fires for background runs" — and FIX-203 (`.knowledge/cards/20260807-1929-FIX-203.md`) closed exactly that gap by adding `backgroundCompletedRunId` state in `page.tsx` (`frontend/src/app/[...view]/page.tsx:788`) plus a dedicated effect in `DashboardLayout.tsx:701-729` that looks the matching notification up by `workflowRunId`/id pattern and calls `markCompleted` for a run that is NOT the tracked/viewed one.
- No equivalent `backgroundFailedRunId` / `backgroundCancelledRunId` exists anywhere in either file (confirmed absent: `grep -rn "backgroundFailedRunId\|backgroundCancelledRunId" frontend/src/` returns nothing).
- The SSE handler itself skips failure/cancellation bookkeeping for background runs at the source: `frontend/src/app/[...view]/page.tsx:1647` — `if (msg.type === "pipeline_failed" && msg.data && !isForeignFrame)` — and `:1718-1719` — `if (msg.type === "pipeline_cancelled" || msg.type === "pipeline_failed") { if (!isForeignFrame) { ... } }`. `isForeignFrame` (defined `page.tsx:1366`) is true precisely for a frame belonging to a run this tab is not actively tracking/viewing — the same axis as `runStore.viewed`. Both blocks are explicitly gated to skip exactly that case.

So the mechanism is confirmed by code (not merely guessed): a `pipeline_failed`/`pipeline_cancelled` SSE frame for a run that is not the viewed one is deliberately excluded from this handling, and there is no second path (unlike completion) that later reconciles the notification. The notification created for that run at launch (`agentsCompleted: 0`, `status: "running"`, `useNotifications.ts:138-147`) would keep showing a spinning/running state after the run has actually failed or been cancelled server-side.

## Expected (once reproduced)

A backgrounded or navigated-away-from run that fails or is cancelled shows the matching notification transition to a failed/cancelled state (mirroring how `markCompleted` already does for background completions via FIX-203).

## Actual (inferred, not yet observed)

The notification is expected to remain `status: "running"` indefinitely for a background run that fails or is cancelled, with no toast and no panel status change — because no code path calls `markFailed`/`markCancelled` for a non-viewed run.

## What would confirm this

1. Launch two concurrent runs (e.g. two prototype runs), leave run A viewed.
2. Force run B (backgrounded) to fail or cancel it (e.g. via the cancel action while run A is the viewed one, or trigger a real failure).
3. Open the notification panel and check whether run B's entry ever leaves `status: "running"`.
   Alternative repro matching QA-PS-002's own reproduction shape: launch one run, navigate away from its `/runs/<id>` page before it fails/is cancelled, then check the panel.

## Correction (re-analysis, 2026-09-17 — see [ISS-673](20260917-1420-ISS-673.md))

The "stays running forever" prediction is refined, not retracted. Read directly: `page.tsx:1663-1686` (`pipeline_failed`) and `:1741-1753` (`pipeline_cancelled`) both call `getWorkflows().then(setRecentRuns)` unconditionally whenever `!isForeignFrame` — which is false for any run this tab launched, background or not — so `recentRuns[i].status` DOES update to `"failed"`/`"cancelled"` for a backgrounded run, and it correctly drops out of `AppHeader`'s `liveRunsFromServer` (`LIVE_STATUSES` no longer matches). So the row does NOT keep showing a spinning "running" badge indefinitely as originally predicted.

But this card's core diagnosis — `markFailed`/`markCancelled` are only ever called for `currentPipelineNotifId.current` — is still correct code, and still matters: because the notification's OWN `status` field never leaves `"running"` for a background run, it never qualifies for `NotificationPanel`'s terminal list either (`n.status !== "running"` fails). Net effect: the run's row disappears from the panel entirely once it fails or is cancelled in the background — no live row (server says it's terminal), no failed/cancelled row either (client notification object never transitioned) — rather than staying visibly "running". The missing background bridge this card identifies is still the fix target; only the observed symptom shape changes from "stuck running" to "vanishes".

## Resolution (2026-09-17, [FIX-521](20260917-1447-FIX-521.md))

The bridge is added in FIX-203's shape. In the `pipeline_failed`/`pipeline_cancelled` block,
page.tsx sets `backgroundRunTransition = { runId, to: "failed" | "cancelled" }` for a run that is
not `trackedRunIdRef.current` (`page.tsx:1724-1728`). An effect beside FIX-203's
(`DashboardLayout.tsx:738-752`) finds that run's `running`/`gate` notification and calls
`markFailed`/`markCancelled`. The notification now reaches the panel's terminal list instead of
vanishing.

- `DashboardLayout.iss648.test.tsx` went from "1 expected fail" to XPASS; its marker is left for
  the 6-verifier.
- That test inspects source text only. FIX-521 records the behavioural check:
  - a scratch DashboardLayout render showed failed and cancelled notifications transitioning;
  - it went red with the effect disabled.
