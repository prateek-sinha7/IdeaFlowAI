# FIX-618

Resolves [ISS-801](20260922-1834-ISS-801.md) and
[ISS-799](20260922-1835-ISS-799.md) (both `BUGS.md#qa-ps-035`).
[ISS-781](20260922-1630-ISS-781.md) is **partly** addressed and stays open —
see "What is deliberately NOT fixed" below.

## What was wrong

A cold `/settings/profile` load fetched the same account data several times:
`GET /api/auth/me` x3-4, `GET /api/settings/preferences` x2,
`GET /api/capabilities` x2, and — on the other two tabs —
`GET /api/auth/mfa` x2 and `GET /api/settings/constitution` x2. None of it can
change between the duplicates; `/api/capabilities` alone is 23.6 KB a copy.

Two mechanisms, both producing the same symptom:

- **Two call sites that never meet.** `getMe` is called by
  `frontend/src/app/[...view]/page.tsx:894` (the route resolver's auth check)
  AND by `frontend/src/components/settings/AccountSettings.tsx:139`'s own
  `Promise.all` mount effect. `AccountSettings` mounts in a LATER commit than
  page.tsx's effect — it only renders once `setIsAuthenticated(true)` has
  landed — so an in-flight-only guard of the kind
  [FIX-616](20260922-1923-FIX-616.md) added for `getWorkflows` cannot catch
  this pair.
- **`next dev` double-invoking each mount effect.** The single call sites for
  `/api/auth/mfa` (`SecuritySection.tsx:103-105`) and
  `/api/settings/constitution` (`AccountSettings.tsx`'s `ConstitutionSection`,
  mount effect at :597) each fired twice. The constitution one was already
  named in [ISS-581](20260829-0241-ISS-581.md); `FIX-421` added a
  `userHasEdited` ref that stops the late response clobbering a draft but
  never removed the duplicate request itself.

## What changed and why there

**`frontend/src/lib/api.ts`** — three getters now read through `cachedGet`
(`api.ts:446`), the shared URL+token GET cache that landed in the same file
for [ISS-782](20260922-1610-ISS-782.md):

- `getMfaStatus` → `cachedGet<MfaStatus>("/api/auth/mfa", token)`
- `getMe` → `cachedGet<User>("/api/auth/me", token)`
- new `getConstitution(token)` →
  `cachedGet<{ content?: string | null }>("/api/settings/constitution", token)`

`getPreferences` and `getCapabilities` were already routed there by ISS-782's
fix; this change adds the three that QA-PS-035 also covers, so all five reads
share ONE source instead of each component owning its own fetch. That is the
choke point every caller already passes through — one guard there also closes
`admin/page.tsx:183`, `LaunchWizard.tsx:371`, `AnalyticsPage.tsx` and
`AgentModelPicker.tsx:74` without a per-caller edit.

Also in `api.ts`, a new `dropAccountReadsOnWrite()` (next to
`invalidateCachedGet`) is called at the top of BOTH shared request paths —
`fetchWithAuth` and `authedFetch`. Any non-GET clears the whole cache.
`updatePreferences` could call `invalidateCachedGet` by hand because its PUT
sits beside the GET it shadows; the constitution editor's PUT/DELETE
(`AccountSettings.tsx`, via `authedFetch`) and the MFA enable/disable POSTs do
not, and a cached read that outlives its own write is a wrong answer rather
than a slow one. Clearing on every write makes that unconditional, which is
what makes caching `/api/auth/mfa` and `/api/settings/constitution` safe at
all.

**`frontend/src/components/settings/AccountSettings.tsx`** — the
`ConstitutionSection` mount effect calls `getConstitution(token)` instead of
hand-rolling `authedFetch(`${ENV.API_URL}/api/settings/constitution`)`. Two
mount invocations had nothing to share while the request was built at the call
site. Still FR-015-safe: the shared path handles the 401 that this effect's
`.catch(() => {})` would otherwise swallow, and `authedFetch` is still used
for the section's own PUT and DELETE.

## What is deliberately NOT fixed

[ISS-781](20260922-1630-ISS-781.md)'s "Problem 2" — that `/settings/*` should
fetch NO run history and NO workflow catalog at all — is **not** fixed, and
its test is still `xfail`. Measured after this change on `/settings/profile`:
`GET /api/runs?limit=6` x2, `GET /api/runs?limit=50` x2,
`GET /api/workflows` x1.

Removing them is a product decision, not a fix, and is escalated in
`ESCALATIONS.md#qa-ps-035`:

- `frontend/src/components/layout/DashboardLayout.tsx:2715` renders
  `<AppHeader ... recentRuns={recentRuns} ...>` (the prop is passed at :2741)
  UNCONDITIONALLY, above the `mainView === "settings"` branch at :3013. The
  header's "N Running" badge and its dropdown resolve their run from that list
  (`AppHeader.tsx:328`, `:371`). So `/api/runs?limit=50` IS consumed by UI
  rendered on `/settings/*` — ISS-781's "a 50-row run-history fetch it never
  displays" does not hold for the header.
- `/api/workflows` and `/api/runs?limit=6` come from the `signedIn` warm-cache
  preload in `frontend/src/store/listenerMiddleware.ts:18-21`, whose own
  comment (ISS-232) states the app-wide intent.
  [ISS-794](20260922-1827-ISS-794.md) already classes that preload as
  "likely-intentional behaviour ... a product decision, not covered here".

Note that neither ISS-781's nor ISS-801's own "where the fix belongs" section
asks for removal — both prescribe de-duplication. The zero-request assertion
comes from the test only.

Two further findings recorded rather than patched:

- `GET /api/runs?limit=50` is still x2 because `RunConnectionProvider`'s boot
  fetch and `page.tsx:995`'s mount effect are ticks apart, and FIX-616's
  in-flight guard is deliberately in-flight-only. `cachedGet`'s own header
  comment rules run/workflow lists out of the cache on purpose ("their callers
  refetch precisely to observe a change — a cancel clearing the header's 'N
  Running' pill"). Overriding that is a design decision, not this fix.
- `GET /api/runs?limit=6` is x2 even though `listenerMiddleware.ts:54-56`
  guards `fetchRecentRuns` on `recentRunsStatus`, and `/api/workflows` next to
  it under the same guard is x1. ISS-794 attributes the doubling to the
  listener `effect` running "async per action", but RTK invokes the effect
  synchronously up to its first `await` — which here is after both dispatches
  — so that stated mechanism does not explain the asymmetry. Left for
  ISS-784/793/794's own line rather than patched on a guess.

## Test-file changes, and why they are not "fixing the test"

Two test files were edited. Neither assertion changed.

- `src/components/settings/AccountSettings.render.test.tsx` mocks `@/lib/api`
  wholesale with a factory, so the component's new `getConstitution` dependency
  resolved to `undefined`. The factory gains a `getConstitution` shim that
  delegates to the same stubbed global `fetch` — exactly the pattern the file's
  own comment records from the last time this read moved (bare `fetch` →
  `authedFetch` under FR-015), and the `expect(fetch).toHaveBeenCalledWith(...
  /api/settings/constitution ...)` assertion is untouched.
- `src/lib/api.refreshRetry.test.ts` reused the literal bearer
  `"stale.access.token"` in six `it` blocks. With `getMe` cached by URL+token,
  the first test's resolved user was served to the three later ones, which then
  never reached the ladder under test. Each block now uses its own stale bearer
  — the same isolation `api.sharedGetCache.test.ts` already uses
  (`"caps-a"`/`"caps-b"`). Assertions unchanged. The coverage this weakens is
  recorded as [ISS-824](20260922-1947-ISS-824.md), not hidden.
