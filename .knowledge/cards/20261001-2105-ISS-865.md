# ISS-865

**Evidence status.** The mechanism is REPRODUCED in-process by the QA-KB-006 analyzer (probe table below, 2026-10-01). User-facing exposure is INFERRED: the shipped frontend never sends this pair (`frontend/src/app/[...view]/page.tsx:4420-4425` sends `approved: true` only with `action: "approve"`; `:4431-4435` sends `approved: false` only with `action: "reject"`), so only a scripted or legacy client can reach it. Whether `approved: false` under `action: "approve"` is an intended legacy spelling of a rejection is stated nowhere; the fix below does not depend on the answer.

## Condition

`POST /api/runs/{run_id}/gate` with a body whose `action` is `"approve"` (or absent, which is the schema default, `backend/app/api/run_commands.py:136`) and `approved: false`.

## Expected vs actual

- Expected: the stored gate response describes the decision that will be enforced. The engine enforces a rejection, because it keys its terminal decision on `approved` (`backend/agents/execution_engine/engine.py:12561-12563`), so the record should say `action: "reject"`.
- Actual: `{'approved': False, 'edited_content': None, 'action': 'approve', 'instructions': None}`. The record contradicts itself.

## Why the root cause implies it

[ISS-128](20260812-2046-ISS-128.md)'s root cause is that the stored `action` label is whatever the calling branch hardcodes (or the store defaults), not a function of the final `approved`. The three-site fix (`action="reject"` on the reject branches) closes the cases where the branch itself is reject. This path is an approve branch whose `approved` is overridden by the request body: `run_commands.py:329` computes `approved = True if body.approved is None else bool(body.approved)`, then `:330-335` passes `approved=approved` together with the literal `action="approve"`.

## Reproduction (probe, scratchpad, offline)

`POST /api/runs/{id}/gate` against the real `ArtifactStore`, in-memory SQLite, same harness as `backend/tests/integration/api/test_update_specs_ingress_fence_api.py`. Stored record per request body:

| body | HTTP | stored |
|---|---|---|
| `{"action":"approve","approved":false}` | 200 | `{'approved': False, ..., 'action': 'approve'}` |
| `{"approved":false}` (action defaulted) | 200 | `{'approved': False, ..., 'action': 'approve'}` |
| `{"action":"approve","approved":true}` | 200 | `{'approved': True, ..., 'action': 'approve'}` (correct) |
| `{"action":"reject","approved":true}` | 200 | `{'approved': False, ..., 'action': 'approve'}` (the ISS-128 bug itself; the reject branch rightly ignores the client's `approved`) |

## Fix

One line in the approve branch of `resolve_gate` (`run_commands.py:330-335`): pass `action="approve" if approved else "reject"`. It only relabels the record to the decision already being enforced, so no response code, schema or engine behaviour changes and no API-contract decision is needed. The alternative that does change the contract (refuse the contradictory pair with 422) is only for the product owner to choose.

Keep `resolve_gate`'s `if action == "redo"` / `elif` chain shape: `backend/tests/unit/api/test_rest_gate_commands.py:48-72` greps its source for the literal `action == "redo"` and for ownership-check-before-write order.

This is independent of the store-level default recommended in ISS-128. A store that derives an OMITTED `action` from `approved` does not help here, because this branch passes `action` explicitly.

## Test notes

One test in `backend/tests/integration/api/test_rest_gate_commands_api.py`, beside `test_reject_persists_reject_action_not_approve`: POST `{"gate_key": ..., "action": "approve", "approved": false}`, then assert the recorded dict has `approved is False` and `action == "reject"`. Written first, it is red today. Offline, about 2 s.

## Blast radius

Writers: `run_commands.py:329-335` only. The other two ingresses hardcode `approved=True` on their approve branches (`:1601`, `:1967`), and `ChatTurn` has no `approved` field (`run_commands.py:1915-1925`), so neither can carry a client override. Reader: `engine.py:12457-12461`, which compares `action` only against `redo` and `update_specs`, so no run behaves differently.

## Fix (2026-10-01)

Fixed by [FIX-687](20261001-2130-FIX-687.md) in the store, not by the call-site line proposed above.
`set_review_response` derives the `"approve"` / `"reject"` label from `approved` even when a caller passes it
(`backend/agents/artifact_store/store.py:160-161`). The approve branch's hardcoded `action="approve"` with a client
`approved: false` is therefore stored as `"reject"`. `run_commands.py:330-335` is unchanged, which kept this fix out
of a file that QA-KB-009 and QA-KB-036 are editing. No response code, schema or engine behaviour changed, as the Fix
section above requires. `test_rest_gate_commands_api.py::test_approve_action_with_approved_false_persists_reject`
now reports `XPASS(strict)`. The marker is left for the 6-verifier.
