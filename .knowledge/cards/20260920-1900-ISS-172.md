## The three prototype revision manifests declare a leading analyzer step the registry cannot see

`compile_for_run(<pipeline>).steps` and the legacy registry roster
(`get_pipeline_agents(<pipeline>)`) disagree for all three prototype revision pipelines,
by exactly one leading step:

| pipeline | compiled plan | registry roster |
|---|---|---|
| `prototype_revision` | `prototype-revision-analyzer`, `prototype-revision-agent`, `prototype-validate` | `prototype-revision-agent`, `prototype-validate` |
| `prototype_feature_revision` | `prototype-revision-analyzer`, `prototype-revision-feature-specify`, `prototype-plan`, `prototype-build`, `prototype-validate` | `prototype-revision-feature-specify`, `prototype-plan`, `prototype-build`, `prototype-validate` |
| `prototype_large_revision` | `prototype-revision-analyzer`, `prototype-revision-planner`, `prototype-build`, `prototype-validate` | `prototype-revision-planner`, `prototype-build`, `prototype-validate` |

In each case the registry roster is a strict suffix of the compiled plan; nothing appears
in the registry that the manifest lacks.

**Mechanism.** `backend/agents/prompts/prototype-revision-analyzer/AGENT.md` declares
`pipeline_type: prototype_revision_analyzer` — its own private label, not any of the three
pipelines that declare it as a step. `get_pipeline_agents("prototype_revision")` filters
prompts by `pipeline_type`, so the analyzer is structurally invisible to the roster while
being the FIRST step of the compiled plan.

**Why it surfaced now.** The guard
(`test_id_alias_resolver.py::test_compiled_agent_sequence_matches_registry_order`)
parametrizes over manifest-backed pipeline ids discovered by walking
`agents/workflows/`. An earlier test-move left that directory root pointing one level too
high, so the list was EMPTY and the guard collected zero cases — vacuous green in CI, not
passing. Batch 6 repaired the root and all three cases went red immediately.

**Decision needed** (deliberately NOT taken here — this is a product/ownership question):

1. If the compiled plan is authoritative (the project's own direction: manifests drive the
   kernel, ADR-0003 already deleted the engine's run-entry roster assertion), then the
   analyzer's `pipeline_type` is the defect — or the parity guard is comparing against a
   source that can no longer answer the question, and should be retired for these three.
2. If the registry roster is authoritative for these pipelines, the manifests should not
   declare a step the roster omits.

Until then the three cases carry `@pytest.mark.xfail(strict=True, reason="ISS-172 …")`, so
CI is honest: green while the drift stands, and it FAILS the moment the drift is fixed
without removing the marker.
