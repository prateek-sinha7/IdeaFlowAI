# ISS-1174

**Register source:** found by the `QA-KB-126` 5-fixer on 2026-10-09 while writing [FIX-776](20261009-1628-FIX-776.md). Not its own
bug row, and not fixed there.

**Confidence:** CONFIRMED by reading for the missing argument; INFERRED for the resume outcome (no triggered child was resumed).

## Condition

`KernelServices.run_trigger_workflow` resolves a saved row with a `steps` manifest (Case 3), compiles it, and mints the child with
`_launch_run_core(...)` (`kernel_services.py:1677-1707`). It passes `compiled=target_compiled` but no `manifest_json`, so the parameter's
default `None` (`run_commands.py:2923`) is what the child's `WorkflowRun.manifest_json` stores. `launch_run` passes
`manifest_json=persisted_manifest` (the raw manifest plus `_trust` and `_overrides`) for the same shape (`run_commands.py:3447-3450`,
`:3902`).

Two consequences:

1. **Resume.** `resume_run` recompiles a composed run from its persisted manifest (`engine.py:15692-15721`, migration 0040). With none it
   falls to the registry branch, which rebuilds the roster from the run's `type`, the row's `base_pipeline_type`. For a Composer row
   (`custom`) that is the generic `custom` roster, the failure migration 0040 was written for ("a crashed composed run auto-resumed as a
   completely different pipeline", the engine comment above that block). `_replay_clarify_run` (`engine.py:16251-16270`) has the same
   branch.
2. **The next trigger hop.** [FIX-776](20261009-1628-FIX-776.md) holds a triggered row to the `_trust` persisted on the run that fires it
   (`_parent_run_trust`, `run_engine.py:731-745`). A triggered child persists none, so a row it triggers in turn compiles at `user`, even
   when the chain started from an enterprise Composer run at `db`. That is the fail-closed ceiling FIX-776 chose (the `ponytail:` comment at
   `run_engine.py:740`).

## Expected vs actual

Expected: a triggered composed child is a first-class composed run. It persists the manifest it ran, at the trust it was compiled at, so
resume runs the same workflow and the next hop reads that trust. Actual: it persists nothing, so resume picks a roster from the type and
the next hop gets `user`.

## Fix direction (INFERRED, not applied)

In `run_trigger_workflow`'s Case 3 branch, build the persisted manifest as `launch_run` does (`raw_manifest` plus `_trust: row_trust` and
`_overrides: row_overrides` when set) and pass it as `manifest_json=` to `_launch_run_core`. That reuses the existing column and the existing
resume reader, with no migration and no tier in the kernel. A file-backed or override-merged parent still persists no `_trust` and stays
`user` for a row it triggers. Check the resume endpoint's gates read the new value as intended ([ISS-1165](20261009-1558-ISS-1165.md):
a `db` child resumes only for a Composer-entitled caller).

## Test notes

Offline, harness of `backend/tests/integration/api/test_iss1164_1165_trigger_resume_trust.py`: fire `run_trigger_workflow` at a stored
Case 3 row from a run persisted at `_trust="db"` with `_launch_run_core` stubbed, and assert the stub received `manifest_json` with the
row's steps and `_trust == "db"`. For the second hop: insert the child run the stub saw and trigger a privileged row from it; today it
raises `CompilerError`.

`kernel_services.py:1677-1707` (the call, no `manifest_json`), `run_commands.py:2923` (`manifest_json: dict | None = None`),
`engine.py:15692-15721` (resume reads it). FIX-776's probe `evidence/qa-kb-126/fix-01-probe-doors-after-fix.txt` `[T]` shows the clamp
the second hop meets.
