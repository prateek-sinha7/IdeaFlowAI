## What was wrong

`BUG-20260828-053745-create-app-r2`: on `/create/app`, attaching a `.txt`/`.md`/`.json`/`.csv`
file whose content exceeds the 450,000-character `ATTACH_MAX_CHARS` limit had its content cut to
that limit and sent with **zero** indication anywhere — not in the chip (filename only), not in a
toast, not in the brief text itself. The validator's 3/3 cold-start repro captured a `POST
/api/runs` body of exactly 450,236 chars ending `...aaaa\n=== End: huge.txt ===`, with
`body.toLowerCase().includes('truncat') === false`. Attaching a `.pdf`/`.docx`/`.pptx` of the same
size on the same screen produced a visible note, because that branch already had one.

## Root cause

`frontend/src/components/workflow/IdeaInputPage.tsx:512-546` — `handleFiles()` inside the exported
`useBriefAttachments()` hook has two sibling branches for the same operation that diverge in
observability:

- `isTextFile` (`.txt/.md/.json/.csv`, `:514-523`) read the file client-side and stored
  `content.slice(0, ATTACH_MAX_CHARS)` — the truncation flag was never computed, so nothing
  downstream could surface it.
- `isBinaryFile` (`.pdf/.docx/.pptx`, `:524-541`) calls `extractFileText()` and appends
  `` `\n[Content truncated to ${ATTACH_MAX_CHARS.toLocaleString()} chars]` `` whenever
  `res.truncated` is true.

Same 450,000-char ceiling on both; only one side told anyone it was hit. The chip render shows
only `file.name`, so there was no secondary signal either.

Blast radius re-confirmed before editing (`grep -rln "useBriefAttachments\|BriefAttachBox"
frontend/src`): `IdeaInputPage.tsx`, `AgentsPopup.tsx`, `composer/ComposerPage.tsx`,
`composer/CanvasView.tsx` — all mount the SAME hook instance, so `/create/app`,
`/create/user_stories`, `/create/mulesoft_to_springboot`, `/create/dotnet_to_azure` and both
ComposerPage views (Simple + Canvas) were all reached by the one defect and are all covered by
the one hunk.

## What changed and why there

Two files, two hunks, both prescribed by [ISS-312](20260828-1941-ISS-312.md)'s "where the fix
belongs":

1. `frontend/src/lib/constants.ts` — new `truncateAttachmentText(content: string): string`
   exported next to `ATTACH_MAX_CHARS`: returns `content` untouched when it fits, otherwise
   `slice(0, ATTACH_MAX_CHARS)` plus the binary branch's existing note verbatim. The helper
   exists rather than an inline four-line patch because `LaunchWizard.tsx:653-659` carries a
   byte-for-byte fork of the same branch ([ISS-423](20260829-0026-ISS-423.md)) — one guard, two
   call sites, instead of the same logic hand-written twice and free to drift a third time.
2. `frontend/src/components/workflow/IdeaInputPage.tsx:520` — the `isTextFile` branch now stores
   `truncateAttachmentText(content)` instead of `content.slice(0, ATTACH_MAX_CHARS)`; the import
   on `:19` picks up the helper. `ATTACH_MAX_CHARS` stays imported — the binary branch (`:530`)
   still uses it directly.

Nothing else changed. The note (rather than a chip badge or an outright rejection) is the option
the card's own "Expected" lists first and the only one the failing test asserts; a chip-level
warning would be a second, unasked-for surface.
