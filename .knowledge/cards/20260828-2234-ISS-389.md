## Summary

Boundary case of [ISS-285](20260828-1745-ISS-285.md) (root: BUG-20260828-014416-runs-id-preview-full).
ISS-285 confirmed `/preview/full` silently auto-selects Audit for a terminal-failed run with no
deliverable, reproduced against a run carrying a populated (8-32 record) audit trail — the
substituted content was at least visibly *something*. This card is the zero-data boundary of the
identical mechanism: a run that failed before any gate/hook fired (no `hook_runs` rows at all)
hits the same silent Audit substitution, but `AuditTab.tsx` renders its own **"No audit records
yet"** empty state (`frontend/src/components/results/AuditTab.tsx:701`) into that substituted
tab — compounding one honesty gap on top of another.

## Mechanism (INFERRED from source; not independently re-driven in a browser)

`PreviewPanel.tsx:812,830-831` forces `activeTab` to `"audit"` for any `terminalFailureNoDeliverable`
run regardless of what that tab actually contains (ISS-285's confirmed root cause — unchanged
here). `AuditTab.tsx:701` independently renders `"No audit records yet"` whenever its own record
set is empty — confirmed via `grep` at that line; this is AuditTab's OWN, correctly-behaving empty
state for a genuinely-empty audit trail, not a defect in AuditTab itself. The compounding problem
is that the CALLER (PreviewPanel's silent substitution) gives the user zero context before AuditTab
ever renders anything: for the populated case the user at least sees real audit content and might
infer "well, this isn't a Preview, but it's something"; for the zero-record case the user gets a
tab labeled "Audit" reading "No audit records yet" with **no visible connection to the Preview they
actually asked for and no indication a failed run with no deliverable is why they're looking at an
empty audit trail instead**. It reads as a generic empty-audit-trail run, not as "the deliverable
you asked for doesn't exist."

## Expected vs actual

- **Expected:** the same honest "no deliverable was produced" affordance ISS-285's proposed fix
  would render for the populated-audit case, taking priority over AuditTab's own generic empty
  state — the substitution message should never let a viewer land on "No audit records yet" while
  thinking they asked to preview a deliverable.
- **Actual (inferred, not yet reproduced in a browser session):** `/preview/full` on a
  zero-audit-record failed run would render Audit's own "No audit records yet" text with the same
  complete absence of Preview-related context ISS-285 documents for the populated case.

## Why the root cause implies this

ISS-285's fix must render its honest empty-state check BEFORE falling into Audit content at all
(see ISS-285's proposed fix location, `PreviewPanel.tsx`'s deep-link/default-tab effect and
tab-content switch) — a fix that only special-cases "Audit has content" would still leave this
zero-record boundary rendering an uninformative, unrelated empty string. This is the "boundary and
empty" instance of the identical substitution defect, not a new mechanism.

**Status: INFERRED.** Not independently reproduced in a browser this pass — flagging what would
settle it: find or seed a `failed` run with zero `hook_runs` rows, cold-navigate to its
`/preview/full`, and confirm the rendered Audit pane reads "No audit records yet" with no
Preview-related messaging.
