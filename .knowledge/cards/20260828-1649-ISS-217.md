## Why this card exists

[ISS-190](20260828-1501-ISS-190.md) attributes the permanently blank
`/create/prototype` page after browser Back-then-Forward to the mount-once gate at
`frontend/src/app/[...view]/page.tsx:3701`
(`if (!mounted || !isAuthenticated) { return null; }`), and proposes two fixes inside
`DashboardPage`: a `pageshow`/`event.persisted` recovery listener, or a synchronous
`useState` initializer for the gate flags. [ISS-197](20260828-1559-ISS-197.md) predicts
`LaunchWizard.tsx`'s `authChecked` copy of that gate would hold its `Loading…` placeholder
forever on the same sequence.

The card itself names the diagnostic that would settle its INFERRED half
(`performance.getEntriesByType('navigation')[0].type` plus a `pageshow` listener). That
diagnostic was run before touching any source. **It disproves the stated root cause**, and
both proposed fixes are inoperable for a reason the reading-only analysis could not see. No
code change was made; the bug is escalated instead.

## What was measured

Six probe runs, real Google Chrome (`channel="chrome"`), against the running dev servers
(`localhost:3000` / `localhost:8000`), signed in as `qa-admin@flowinqa.com`, using real
`page.go_back()` / `page.go_forward()`.

**1. The blank is not route-specific and not gate-specific.** The same Back-then-Forward
sequence blanks every route tried, including one with no auth gate of any kind:

| route pair | fresh (innerText len) | after Back | after Forward |
|---|---|---|---|
| `/dashboard` ↔ `/create/prototype` | 2739 / 1481 | 0 | 0 |
| `/dashboard` ↔ `/workflow/create?mode=prototype` | 2739 / 1481 | 0 | 0 |
| `/dashboard` ↔ `/handoff/settings` | 2739 / 3728 | 0 | 0 |
| `/login` ↔ `/register` (anonymous, no session) | 381 / 381 | 0 | 0 |

`frontend/src/app/login/page.tsx` has no `mounted` flag, no `isAuthenticated` flag and no
auth gate — it renders its markup unconditionally — and it blanks identically. A defect
whose symptom is unchanged on a page that does not contain the accused code is not caused by
that code.

**Back is blank too**, on every pair above. ISS-190 states Back renders fine and treats
"Forward is the only step that reproduces" as load-bearing evidence for the remount theory;
that is not what a probe taken 4s after `go_back()` shows.

**2. React never hydrates, so no component-level fix can run.** After the back/forward load:

- `Object.keys(document).filter(k => k.startsWith('__react'))` → `[]` (fresh load:
  `["__reactContainer$…", "__reactResources$…"]`)
- `Object.keys(document.body).filter(k => k.startsWith('__reactFiber'))` → `[]` (fresh load:
  one key)
- no page errors, no console errors; the Next dev-overlay React root still mounts, so the
  runtime itself is alive — only the app root never attaches.

`DashboardPage`, `LaunchWizard` and `HandoffSettingsPage` are never mounted in the failure
state. A `pageshow` listener registered inside `DashboardPage` (ISS-190 fix 1) and a lazy
`useState` initializer for its gate flags (ISS-190 fix 2) both live in a component that does
not run — neither can execute, so neither can fix this.

**3. It is not bfcache.** `pageshow` fires with `persisted: false`;
`performance.getEntriesByType('navigation')[0].type === "back_forward"` with
`transferSize: 0` and `encodedBodySize`/`decodedBodySize` identical to the fresh load
(`/login`: 18826 bytes, matching `curl http://localhost:3000/login | wc -c` = 18826). The
complete document is replayed out of Chrome's HTTP cache and re-parsed; the resulting DOM
holds React's streaming-suspense placeholders unfilled —
`<div hidden=""><!--$--><!--/$--></div>` plus the inline flight scripts, `innerText.length
== 0`. ISS-190's `event.persisted` branch would never fire.

**4. With the back/forward cache ENABLED, the bug does not occur.** Playwright's default
Chromium args include `--disable-back-forward-cache`; removing it
(`ignore_default_args=["--disable-back-forward-cache"]`) and re-running the identical
sequence:

| step | url | innerText len | `pageshow.persisted` |
|---|---|---|---|
| fresh | `/create/prototype` | 1481 | false |
| Back | `/dashboard` | 2749 | **true** |
| Forward | `/create/prototype` | **1481** | **true** |

A browser with bfcache available restores the live, rendered page — which is what a human
pressing Back/Forward gets. The repro therefore depends on the harness disabling bfcache,
not on anything the prototype wizard or the gate does. (The app's open WebSocket does not
block eligibility here — `persisted: true` was observed on `/dashboard`.)

**5. ISS-197's premise does not hold on its own route.** `/workflow/create?mode=prototype`
redirects to `/create/prototype` — the URL after a fresh navigation is `/create/prototype`,
not the legacy route — so that path does not bypass `page.tsx`'s gate as the card assumes.
And the predicted symptom is wrong: it blanks, it does not sit on `LaunchWizard`'s
`Loading…` placeholder, because `LaunchWizard` never mounts either.

## What is and is not corrected

- [ISS-190](20260828-1501-ISS-190.md) — root cause **disproven**; superseded by this card.
  Its reproduction and its symptom description are accurate and stand.
- [ISS-195](20260828-1558-ISS-195.md) — its prediction (every screen, not just
  `/create/prototype`) is **confirmed**, but its scope is understated and its stated cause is
  wrong: routes outside the `[...view]` catch-all (`/handoff/settings`, `/login`) blank too,
  so the shared gate is not what they have in common.
- [ISS-197](20260828-1559-ISS-197.md) — its prediction is **disproven** (see 5 above); the
  duplicated mount-once gates it documents in `LaunchWizard.tsx:161/259-270/806` and
  `handoff/settings/page.tsx:21/32` are real as source-code observations, they are simply not
  the mechanism behind this bug.

## Disposition — needs a human ruling

Two questions this card deliberately does not answer alone:

1. **Is this a product defect at all?** It requires the back/forward cache to be
   unavailable. It is reproducible 3/3 under the bug-hunter harness and 0/3 with bfcache on.
   Real exposure is whatever makes a real browser skip bfcache for these documents (the dev
   server sends `Cache-Control: no-cache, must-revalidate`; a `no-store` document is
   bfcache-ineligible in Chrome). That has not been measured against a production build.
2. **If it is in scope, where does the fix belong?** Nowhere inside a React component — the
   app root does not hydrate in the failure state. It is an SSR/hydration-under-cache-replay
   or a response-header concern, and picking between those is a design decision, not a
   surgical fix. Whether the harness should simply keep bfcache enabled (matching a real
   browser) is the cheaper alternative and belongs in the same ruling.

`tests/integration/e2e/suites/12_shell_nav/test_shell_nav.py::test_forward_navigation_to_prototype_wizard_rehydrates`
was left exactly as 4-test-writer wrote it, `@pytest.mark.xfail(strict=True)` intact. It was
observed XFAIL (1 xfailed) before and after this investigation; nothing was edited to make it
pass.
