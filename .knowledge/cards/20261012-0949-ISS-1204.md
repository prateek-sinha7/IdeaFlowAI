# ISS-1204

**Register source:** sibling derived during the `QA-KB-112` analysis on 2026-10-12 (root [ISS-1203](20261012-0949-ISS-1203.md)). Not its own bug row.

**Confidence.** INFERRED sibling, with a reproduction artifact for the first case: the admin click is in the 2026-10-09 e2e run (S-09-02 on `tab-security`; screenshot and `steps.json` copied to `analysis-05` and `analysis-06`), not re-run by the analyzer. Other tiers, an already-enrolled account and the history effect are read from code.

## Condition

Any signed-in user on `/settings/profile`, `/settings/ai-model`, `/settings/usage` or `/settings/constitution` clicks the Security tab (`data-testid="tab-security"`), or confirms the "Discard unsaved changes?" dialog on the way to it (`AccountSettings.tsx:146` runs the same `router.replace`).

## What happens

`AccountSettings.tsx:278-279`: `setSection(next); router.replace(SECTION_ROUTE[next]());`, with `SECTION_ROUTE.security = routes.settingsSecurity` (`:61`), that is `/settings/security`. That URL belongs to the static enrolment page ([ISS-1203](20261012-0949-ISS-1203.md)), so Next swaps the `[...view]` page, which hosts `AccountSettings`, for it. The e2e screenshot taken right after the click shows the result: "Two-factor authentication / Admin access requires a second factor… / Preparing your enrolment…" on an empty page with no header and no tab strip, and `steps.json` records the URL settling on `/settings/security` (`analysis-05`, `analysis-06`; the same run's Profile page before the click is `analysis-05b`).

Consequences, in order of certainty:

1. **`SecuritySection` is unreachable (CONFIRMED by code).** Its only mount is `AccountSettings.tsx:531-533` (`section === "security"`). `section` becomes `"security"` in three ways: the tab click, which navigates away in the same handler; `initialSection="security"`, which `initialSettingsSectionFor` (`[...view]/page.tsx:312-313`) produces only when `[...view]` renders `/settings/security`, which the static page pre-empts; and `DashboardLayout.handleNavigate(..., { settingsSection })` (`:2326-2338`), which no caller passes (`AppHeader.tsx:582` is `onNavigate("settings")`; outside tests, `grep -rn settingsSection frontend/src` finds only the type and that handler). So the email-code toggle, the On/Off status, "Your role requires a second factor…" and the recovery note are dead UI.
2. **Every user gets the admin copy (CONFIRMED by code).** The page reads neither role nor MFA status (`page.tsx:17` imports no `getMfaStatus`; the copy at `:93-96` is fixed), so a non-admin who clicks the tab sees "Admin access requires a second factor" and gets a freshly minted secret.
3. **An enrolled account gets the same ceremony (INFERRED).** For an account that already holds a confirmed TOTP the click offers "set up"; completing it would register a new device (Cognito semantics not run, and it must not be tried on a shared account).
4. **Back skips the settings page (INFERRED, standard Next semantics).** `router.replace` overwrites the Account Settings history entry.
5. **The tab contradicts itself (CONFIRMED by code).** `SecuritySection.tsx:344` says "Set-up is handled by your administrator" while the page behind the same tab lets any signed-in user enrol; `SecuritySection.tsx:26-35` says the standalone page was removed.

## Why nothing noticed

S-09-02 asserts only `page.url.endswith(route)` (`test_settings.py:114`), so it is green on the enrolment page. The unit tests mount `AccountSettings` with `useRouter` mocked to a stub singleton (`AccountSettings.render.test.tsx:71-81`), so the navigation never happens, and the `initialSection="security"` case (`:221-228`) renders `SecuritySection` in isolation. Only a real browser on the real route table can see it.

## Expected vs actual

Expected: a tab click either shows the panel in place (the design `SecuritySection.tsx:26-35` and `AccountSettings.tsx:224-226` describe) or the tab is honest about being a link to a separate enrolment page. Actual: the tab reads like a panel and acts like a link to a bare page, and its panel can never be seen.

## Why the root cause implies it

[ISS-1203](20261012-0949-ISS-1203.md) is "the URL has two owners". `SECTION_ROUTE` is the in-app producer of that URL, so it is the first caller to inherit the collision; the cold-load e2e nodes are the second.

## Decision needed (owner)

`QA-KB-112`'s decision kept the URL as the enrolment page; it did not speak about the tab inside Account Settings.

1. **Keep it as a doorway.** The Security tab is a link to the enrolment page. `SecuritySection`, its `initialSection="security"` plumbing, the `settings-security` parse branch, the `[...view]` cases and the stale comments are then dead and should go, and the tab should say where it leads. App change.
2. **Show the tab in place and move the enrolment page** to its own URL (for example `/settings/security/enroll`, built through `routes.ts` per ADR-0018 and used by `admin/page.tsx:193`). Restores `SecuritySection` and makes S-09-01 and S-09-13..19 valid again. An app change the owner excluded for `QA-KB-112`.
3. **One URL, conditional page** (panel when enrolled, ceremony when not): the option the owner declined.

## What would settle the INFERRED parts

One browser cycle, no mutation: sign in as `pro@velocity.ai` (non-admin), open `/settings/profile`, click Security, read the H1 and the copy, press Back. Do not complete Verify on a shared account.

## Fix direction

None applied. Do not write a red test for the app behaviour until the owner chooses between 1 and 2: a test asserting the panel stays in place would encode the option the owner declined for the URL.
