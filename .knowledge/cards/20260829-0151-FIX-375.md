## What was wrong

`BUG-20260828-060700-workflows-new-r2`: on `/workflows/new`, with at least one agent on the
canvas and the "Workflow name" field left empty, clicking **Save workflow** did nothing
observable — no `POST /api/user-workflows`, no toast, no banner, no red border, no
`aria-invalid`, and the button stayed fully enabled. The only side effect was the name `<input>`
silently regaining DOM focus, which is indistinguishable from a stray click. Validated 3/3, cold
start every cycle ([ISS-315](20260828-1750-ISS-315.md)).

## Root cause

`frontend/src/components/workflow/composer/ComposerPage.tsx:1108-1112` (pre-fix), the Save
button's `onClick`:

```tsx
if (!name.trim()) {
  nameInputRef.current?.focus();
  return;
}
```

The guard itself is correct — it is why no request fires — but its only user-facing signals were
a `title="Name the workflow first"` (a native tooltip that appears on hover, never on click) and
a bare `.focus()` with no visual treatment. `disabled={saving}` is driven by the in-flight save
only, so the button never communicates "not yet". The component already owns a visible error
surface — `saveError` (`:227`), rendered at `:1400` in a `text-status-failed` div — and
`handleSave`'s own detached-step (`:676-681`) and not-authenticated (`:685-686`) branches already
use it; the empty-name guard returned before `handleSave` was ever invoked, so it reached none of
that plumbing.

## What changed and why there

One call added inside the guard, at the single choke point:

```tsx
if (!name.trim()) {
  // The title tooltip is hover-only, so a click on an unnamed
  // workflow used to be a silent no-op. Report it through the same
  // saveError banner the detached-step / not-authenticated guards
  // in handleSave already use.
  setSaveError("Name the workflow first, then save.");
  nameInputRef.current?.focus();
  return;
}
```

Placed in the guard rather than in each route's page because `ComposerPage` is one shared
component and `:1114` is its only `handleSave` call site (`grep -n handleSave` returns the
definition at `:663`, a comment at `:811`, and that one call). That covers `/workflows/new`,
`/workflows/{id}/edit` (`DashboardLayout.tsx:2998` seeds `initialName` but the user can clear it)
and the built-in save-as-copy canvas in one edit — the routes
[ISS-432](20260829-0039-ISS-432.md) predicts. No new state, no new component: the banner and its
clearing (`setSaveError(null)` at the head of `handleSave`) already existed.

Deliberately NOT changed: the `title` attribute (still accurate on hover), `disabled={saving}`
(disabling on an empty name would hide the message the fix exists to show), and the "Run once"
brief guard ~30 lines above — that is a different condition with no banner near it, tracked
separately as [ISS-431](20260829-0038-ISS-431.md).

## Known ceiling

The banner text persists while the user then types a name — it is cleared on the next save
attempt by `setSaveError(null)` at `handleSave`'s head, not on keystroke. Clearing it in the name
input's `onChange` was not done: no card asks for it, and the message is superseded the moment
the user saves again.
