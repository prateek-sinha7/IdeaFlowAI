## What is broken

`frontend/src/app/[...view]/workflowDetailCatch.source.test.ts:84`:

```ts
const occurrences = pageSource.split(narrowedPattern).length - 1;
expect(occurrences).toBe(3);
```

`narrowedPattern` is the shared narrowing idiom
`if (err instanceof ApiError && (err.status === 403 || err.status === 404)) {`.
The test's other four assertions are correctly scoped — they slice the T30
effect out of the source and assert *within* it. Only this last one counts
occurrences across the whole 3,900-line file, so it is a lock on "nobody may
ever add a fourth call site", which is the opposite of what the F7 audit that
wrote it wanted: that audit's finding was that MORE catches should adopt the
idiom, not fewer.

## How it went red

`git show HEAD:'frontend/src/app/[...view]/page.tsx'` has 3 occurrences and
the test passes. In the current working tree there are 5:

- +1 from the in-tree ISS-380 fix, which narrowed the `/workflows/{id}/run`
  catch to `setWorkflowRunFailed(true)` only on 403/404;
- +1 from [FIX-368](20260829-0106-FIX-368.md), which narrowed the
  `/workflows/{type}/canvas` catch the same way.

Both are correct uses of the idiom, and neither changes the T30 read-view
behaviour this file exists to lock. `vitest --run 'src/app/[...view]'` reports
89 passed / 1 failed, and this is the one.

## Disposition

Deferred, needs a decision this pass did not own:

1. **Delete the count assertion.** The four preceding assertions already lock
   the T30 effect's narrowing; the count adds no behavioural coverage and
   becomes wrong on every future adoption of the idiom.
2. **Bump `toBe(3)` to the current count.** Cheapest, but re-breaks the next
   time any catch is narrowed, and is wrong again if either in-tree fix is
   reverted before it lands.
3. **Re-scope it** to count occurrences inside the sliced effects it actually
   cares about, matching the pattern the rest of the file already uses.

Whoever takes it should note the file is shared with the ISS-380 fix — the
correct count depends on which of the two in-tree changes are committed.

## Analysis (QA-KB-033, 2026-10-01)

**Card status.** Still open and still valid. The mechanism in "What is broken" is CONFIRMED at HEAD:
`page.tsx` in the working tree is byte-identical to `git show HEAD:` and holds 5 occurrences. Only
the numbers moved. Option 2 (bump) landed in `809bb7b5b` (2026-08-31, recorded in
[ISS-621](20260831-0110-ISS-621.md)), so the test now reads `toBe(5)` and is green
(`npx vitest --run 'src/app/[...view]/workflowDetailCatch.source.test.ts'` printed 5 passed). The
"3" in this card's title is historical. The meaning has not changed, so the card is not superseded.

### Root cause (CONFIRMED)

`frontend/src/app/[...view]/workflowDetailCatch.source.test.ts:86-87`:

```ts
const occurrences = pageSource.split(narrowedPattern).length - 1;
expect(occurrences).toBe(5);
```

The test measures an **aggregate** (text occurrences across the whole 4,469-line file) as a
stand-in for a **per-site** property ("each of these catches is narrowed to 403/404"). An
aggregate is wrong in both directions:

- **Over-sensitive.** Any new correct use of the idiom fails it. That already happened twice
  (ISS-380 and FIX-368 each added one, 3 to 5). It fails `npm test`
  (`frontend/package.json:12`, `vitest --run --coverage`) and the CI job `frontend-vitest`
  (`.github/workflows/ci.yml:640`, `npx vitest --run` at line 669), with a message ("expected 6 to
  be 5") that names no site.
- **Under-sensitive.** A regression at one site plus an unrelated addition elsewhere nets to the
  same count and stays green.

It is not demanded by the spec: `specs/015-frontend-routing/tasks.md:98` (the F7 row) asks only
that T30's catch be narrowed "matching the sibling patterns" and names this test. No count is
required; the count is the test author's addition (comment at test lines 81-85).

### The five sites (CONFIRMED, `page.tsx` at HEAD)

|---|---|---|---|
| 561 | `/workflows/{type}/canvas` seed fetch | `setBuiltinCanvasAccessDenied` (562) | ISS-299 / FIX-368 |
| 3321 | run-detail fetch in `handleSelectWorkflowRun` | `setRunAccessDenied` (3353, after the F14 retry) | T24 |
| 3801 | `/workflows/{id}/edit` cold-mount | `setWorkflowEditAccessDenied` (3802) | T8 |

| 4019 | `/workflows/{id}/run` cold-mount | `setWorkflowRunFailed` (4020) | ISS-380 |

The file has 20 `catch (` / `.catch(` handlers; 5 use the idiom. Each flag has exactly one
`(true)` call site, all inside the gated block.

### What each assertion form does (CONFIRMED by simulation)

Real `page.tsx` text, mutated in memory only. Script `evidence/qa-kb-033/sim.js`, captured output
`evidence/qa-kb-033/sim.out.txt`. "pass" means the test would stay green.

| scenario | `toBe(5)` today | `>= 3` (agreed fix) | `>= 5` | per-setter |
|---|---|---|---|---|
| HEAD (5 sites) | pass | pass | pass | pass |
| S1: +1 legitimate new narrowed site | FAIL (the bug) | pass | pass | pass |
| S4: 1 sibling reverted to swallow-all | FAIL (caught) | pass (MISSED) | FAIL (caught) | FAIL (caught) |
| S2: 2 siblings reverted (ISS-380 and FIX-368 undone) | FAIL (caught) | pass (MISSED) | FAIL (caught) | FAIL (caught) |

"per-setter" means: for each of the five flags above, the text from the nearest preceding `catch`
header to the `set...(true)` call must contain the idiom.

### Blast radius (CONFIRMED by grep)

- **One assertion, one consumer chain:** `npm test` and CI `frontend-vitest`. Nothing else reads
  the count.
- **This count is the only source-level lock on four of the five sites.** A grep over
  `frontend/src` tests for `builtinCanvasAccessDenied|workflowEditAccessDenied|workflowRunFailed|runAccessDenied`
  returns nothing; only `workflowDetailFailed` appears, in this file. The live e2e tests that touch
  these routes (`tests/integration/e2e/suites/13_errors/test_errors.py:160-177` and
  `.../05_saved_workflows/test_iss273_run_panel_bogus_id_dead_end.py`) cover only the positive path
  (a bad id shows the 404), never the path the idiom exists for (a 5xx must NOT show not-found).
  Deleting the count would leave T24, T8, FIX-368 and ISS-380 with no lock at all.
- **T30's own site is locked separately and is correctly scoped:** the slice at test lines 30-37
  spans `page.tsx` lines 3812-3863 and holds exactly one idiom occurrence and only its own setter.

### Fix decision: accept the direction, overrule the constant and the "delete" alternative

BUGS.md records an agreed minimal fix: `toBeGreaterThanOrEqual(3)`, or delete the test.

- **Accept** replacing the equality with a floor. It removes the false alarm, and
  `freshLaunchTranscriptReset.source.test.ts:84` already uses a `>=` floor in this directory for
  the same reason.
- **Overrule the constant 3.** It is the pre-ISS-380, pre-FIX-368 count. At HEAD there are 5, so a
  floor of 3 lets two sites silently revert to swallowing every error, which is the one thing the
  comment at test lines 84-85 says the assertion is for ("a DROP means a catch block went back to
  swallowing every error"). The matrix shows `>= 3` misses S4 and S2, which `toBe(5)` catches
  today: it trades a false alarm for a missed regression, and the proposed replacement comment
  ("keeps the guard") would not be true.
- **Overrule "delete".** Its premise, that the `t30Effect`-scoped assertions already lock T30, is
  true but covers one site of five (see blast radius).
- **Recommended change**, one assertion in `workflowDetailCatch.source.test.ts:78-88`:
  `expect(occurrences).toBeGreaterThanOrEqual(5);` plus a rewritten comment and `it(...)` title that
  say it is a floor. The present title ("matches the exact narrowed pattern ... (no drift)") promises
  equality; a title that says "exact" over a `>=` assertion is how
  `freshLaunchTranscriptReset.source.test.ts:77` came to mislead. The comment should name the five
  sites and say: raise the floor when you add a site so the new site is protected, lower it only when a
  site is deliberately removed, never to turn a regression green.
- **Trade-off to accept knowingly.** A floor is no longer forced upward, so protection decays if
  nobody raises it. That is the price of not failing on every addition, and it matches the test's
  own words, "only ever goes UP by inspection". The stronger option is the per-setter form: it closes
  S3 and its failure names the site, at about 10 lines plus a setter list kept in step with the file.
  It is optional and not needed to close this bug.

**Is this a product decision?** No. No user-visible behaviour, API or UX is involved.
[ISS-621](20260831-0110-ISS-621.md) records the team's stance on count pins ("Each of these exists
so an unnoticed addition is impossible. Each fired correctly") for registry-size pins, where an
addition has follow-through elsewhere (docs, pricing, UI). This pin is different: its own comment
says only a drop matters, so that stance does not carry over. That reading is INFERRED; if the owner
prefers an equality tripwire here, the cost is the recurring one-line bump this card describes.

### For the test-writer

This is a test-brittleness defect. The production assertion reads `page.tsx` from disk, so a repo
test cannot drive it red without mutating the source; the reproduction is the in-memory matrix above.
Recipe from the real file text: `IDIOM = "if (err instanceof ApiError && (err.status === 403 || err.status === 404)) {"`;
S1 is `src + "\n" + IDIOM` (6 sites); S4 replaces the 3rd occurrence with `if (true) {` (4 sites).
After the fix: S1 green, S4 and S2 red, HEAD green (5 passed). If a vitest artefact is wanted,
factor the count into a local `countNarrowed(src)` used by both the assertion and a small
meta-test, so the meta-test exercises the same predicate the assertion uses.

No invariant (SC-001, import-linter contract) is at risk: test-only change, frontend, no engine or
contract surface.
