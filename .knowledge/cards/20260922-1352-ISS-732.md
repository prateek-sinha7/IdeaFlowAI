# ISS-732

Sibling of [ISS-698](20260922-1001-ISS-698.md) (bug **QA-PS-019**,
`BUGS.md#qa-ps-019`), filed by the 3-analyzer while deriving QA-PS-019's
blast radius.

## What happened

ISS-698 traces QA-PS-019 ("Write files" toggle has no effect) to
`_apply_selections` (`backend/agents/execution_engine/engine.py:12767`)
having no `tools` branch in the patch dict it builds from the user's
composer selections — `validators`, `gates`, `model`, `retry`, `injects`,
`skills`, `strategy`, `fanout`, `task_source` each get a `sel.get(...)`
case; `tools` gets none. That is a gap in the whole `ToolPermissions`
object, not something specific to `write_files`. The composer exposes
exactly two author-editable tool levers —
`frontend/src/components/workflow/AgentsPopup.tsx:1484-1495`
(`TOOL_GRANT_LEVERS`): `read_files` and `write_files`. Both selections
travel through the identical `sel.tools` -> `synthesize_manifest` ->
`WorkflowCompiler.compile(trust="user")` path and land on the same
`user_step.tools` the missing branch never copies onto the running step.
So a user who explicitly switches "Read files" OFF for a step gets the
same silent no-op ISS-698 documents for "Write files" ON — just in the
opposite direction: the restriction never takes effect and the agent keeps
more access than the user asked for, not less.

## Root cause

Mechanism — CONFIRMED by direct read (same function ISS-698 already reads,
re-verified independently for this ticket). Live reproduction — INFERRED,
not yet exercised in a browser or via a run.

`backend/agents/execution_engine/engine.py:12900-12904`, the comment
directly above the fan-out levers:

> "No `tools` overlay: the declarative fanout_batch path acquires no
> spawn_subagents grant (run_fanout does no permission check; trust=user
> forces tools.spawn_subagents OFF anyway)."

That comment only reasons about `spawn_subagents`. The actual code has no
`if sel.get("tools")` branch at all (confirmed by reading the full `patch`
dict construction, lines 12850-12910), so EVERY key inside a step's `tools`
selection is dropped identically — `read_files` along with `write_files`.
The running step (`ectx.current_step`, read at `engine.py:8893-8895`) keeps
whatever `backend/agents/workflows/custom/workflow.yaml` declared, which is
`tools: {read_files: true}` on 8 of 9 steps and no `tools:` key on the
ninth (compiles to the `ToolPermissions()` default, also `read_files=True`
— `backend/agents/workflows/plan.py:65`). Both are `True`, so an explicit
composer selection of `read_files: false` can never be observed at runtime
regardless of which base step it targets.

`backend/agents/workflows/permission_caps.py:132-135`
(`PERMISSION_TOOLS["read_files"] = {read_file, ls, glob, grep}`) is the
same enforcement seam ISS-698 traces for `write_files`
(`factory.py:419-432`'s `denied_tools = permission_caps.denied_tools(ctx.step_tools)`,
carried from the SAME un-overlaid `ectx.current_step.tools` at
`engine.py:8893-8895`) — so an agent whose step the user meant to sandbox
to "no reads" keeps full `read_file`/`ls`/`glob`/`grep` access to every
file another agent in the same run has written, including any upstream
agent's output the user did not intend this step to see.

A second, independent observable of the same gap: `engine.py:15055-15063`
computes `_step_can_read_files` off the identical un-overlaid
`ectx.current_step.tools.read_files` to decide whether to inline a
disk-substitute of a `consumes:`-typed upstream output directly into the
step's context message (the fallback path for a step that cannot
`read_file` its own dependency). Because the value is always `True` for
every custom-workflow step regardless of the user's selection, this
fallback never fires for a step the user explicitly marked read-disabled —
so a step that (correctly, per the fix) would end up with no read access
also never gets the compensating inline delivery, leaving it with neither
mechanism.

## Why this is INFERRED, not CONFIRMED

The missing-branch mechanism and both consumers above were read directly
from source with file:line. What is NOT yet done is a live run: launch a
custom workflow, toggle "Read files" OFF for one step in the Tools tab,
run it, and confirm from `.logs/*.jsonl` or the agent's own words that
`read_file`/`ls`/`glob`/`grep` were still available (mirroring ISS-698's
own 3-cycle live confirmation for the write_files direction). Settle this
the same way ISS-698 did: `POST /api/runs` with a `selections` map
carrying `{"tools": {"read_files": false}}` for one step, then inspect
`agent_outputs` for a tool_call event naming `read_file`/`ls`/`glob`/`grep`.

## Expected vs actual

- **Expected:** toggling "Read files" OFF for a composer step denies that
  step `read_file`, `ls`, `glob`, and `grep` at runtime.
- **Actual (inferred from code, not yet run live):** the step keeps
  whatever the base manifest declared (`read_files: true` on every
  existing custom-workflow step), so the restriction is silently ignored —
  the inverse of ISS-698's symptom on the same lever pair.

## Fix

Belongs in the exact same place ISS-698 already names: add a `tools`
branch to the `patch` dict in `_apply_selections`
(`engine.py:12850-12910`), copying `sel.get("tools")` onto the step the
same way the other levers are patched. A single fix there closes both
directions — `write_files` never granted (ISS-698) and `read_files` never
revoked (this card) — since both flow through the one missing branch. No
separate fix needed for the `_step_can_read_files` fallback at
`engine.py:15059-15063`; it reads the same field and self-corrects once the
overlay is applied.
