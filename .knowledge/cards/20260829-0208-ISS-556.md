## What happened

INFERRED sibling of [ISS-331](20260828-1840-ISS-331.md), derived from a
source-code read while analyzing that bug — not yet independently driven
live in a browser.

`InputPromptSection` (a step's "Full input prompt" expandable panel) in
`frontend/src/components/results/AgentDetailPanel.tsx` has its own Copy
button, independent of `HookDetailModal`, with a worse variant of the same
underlying defect class.

## Root cause (confirmed by direct read — worse variant: false-positive, not just silent)

`frontend/src/components/results/AgentDetailPanel.tsx:446-450`:

```
const handleCopy = () => {
  navigator.clipboard.writeText(prompt);
  setCopied(true);
  setTimeout(() => setCopied(false), 1500);
};
```

This is not even `async`/`await` — `navigator.clipboard.writeText(prompt)` is
fired and forgotten, and `setCopied(true)` runs on the very next line
unconditionally, regardless of whether the write promise ever resolves. Where
[ISS-331](20260828-1840-ISS-331.md)'s `HookDetailModal` gives zero feedback
on failure, this button gives **false positive** feedback: the UI claims
"Copied" even when the underlying clipboard write silently rejected. Same
missing-error-handling root cause as ISS-331 (no `try/catch`, no `.catch()`,
no failure path), one step further from the truth because success isn't even
gated on the promise.

**What would confirm this live:** open any run's Steps tab, expand an agent's
"Full input prompt" panel, click Copy, and verify (via
`navigator.clipboard.readText()` or a `page.evaluate` write-interception)
whether the clipboard actually received the prompt on a run where the write
is known to fail — the button will read "Copied" regardless.
