## What was wrong

Bug report QA-KB-045. The root cause and blast radius come from the analysis cards; they are not re-derived here.

- [ISS-639](20260831-1645-ISS-639.md) (root): the two restart drivers seeded `_drive_resumed_stream`'s seq counter
  by reading every `run_events` row of the run to derive one integer. Pre-change `engine.py:15682-15683`
  (`resume_run`) and `:16152-16153` (`_replay_clarify_run`):

  ```python
  existing = await tail_store.read_events(run_id, after_seq=0)
  start = max((r.seq for r in existing), default=0) + 1
  ```

- [ISS-873](20261001-2110-ISS-873.md): `_is_resumable_in_flight` asked the same whole-log read for a boolean, once
  per non-terminal run at boot. Pre-change `engine.py:12997`: `if await store.read_events(wr.id, after_seq=0):`.
- [ISS-874](20261001-2110-ISS-874.md): `ScopedStore.append_event_next_seq` re-read the whole log on every attempt
  to find an `event_id` match and the tail, for every chat message and narrator milestone card. Pre-change
  `authz.py:557-563`.

`ScopedStore.read_events` (`authz.py:401-414`) is `ORDER BY seq` plus `.all()` over every column. The ISS-639
analysis measured 2.2-7.0 s per call on the 37k-137k-row local runs, against 0.02-0.05 s for
`ScopedStore._max_event_seq` (`evidence/qa-kb-045/03-analysis-read-vs-max-timing.txt`).

## What changed, and why there

- `backend/agents/execution_engine/engine.py:15682` (`resume_run`) and `:16151` (`_replay_clarify_run`):
  `start = (await tail_store._max_event_seq(run_id)) + 1`. This is the agreed swap and the idiom
  [FIX-499](20260831-1641-FIX-499.md) already uses at `engine.py:13058`. The fix sits inside the two drivers
  because they are the convergence points of all four callers: `app/api/run_commands.py:791`, `engine.py:12820`,
  `:12951` (`resume_run`) and `:12958` (`_replay_clarify_run`). The `start = 1` default and the
  `except Exception` degrade around each seed are untouched.
- `engine.py:12997` (`_is_resumable_in_flight`): `if (await store._max_event_seq(wr.id)) > 0:`. The two-line
  comment above it described the replaced call and was updated with it. The `except Exception: return False`
  degrade is untouched.
- `backend/agents/authz.py:556-575` (`append_event_next_seq`): each attempt now runs one keyed lookup through
  `_run_bounded` for the idempotent no-op, then `_max_event_seq(run_id) + 1` for the tail. The lookup is
  `session.query(RunEvent.seq)` filtered on `run_id`, `event_id`, `seq > 0` and `_scope_owner_ws`, served by
  `uq_run_events_scope_event`. The IntegrityError rollback-and-retry loop and its 8-attempt bound are unchanged.
  The docstring's "(that would materialise the whole log per event)" became false and now reads "(that would add
  two index probes per event)" (`authz.py:542`).

Why the substitutions are exact:

- All three keep the scope filter of `read_events`: the same `run_id =` and `_scope_owner_ws`.
- `bool(read_events(after_seq=0))` is true iff some in-scope row has `seq > 0`, which holds iff `max(seq) > 0`.
- The keyed lookup keeps the old scan's `seq > 0` filter, and `uq_run_events_scope_event` makes the hit unique,
  so `.first()` returns the same row the seq-ascending scan returned first.
- The lookup and the tail probe are now two snapshots instead of one. A writer landing between them is resolved by
  the same IntegrityError retry as before (scenario S8 below).

Not changed, on purpose:

- The content readers `engine.py:12677`, `:12931`, `:16114` (`derive_open_gate`, questionnaire payloads) and
  `:6064`, `:14571`, `:15038`, `:15394`, as the ISS-639 analysis required. The gain is therefore partial, as that
  card predicted: `_replay_clarify_run` still reads the log once for its questions, and `resume_run` still reads it
  in `_first_incomplete_step`.
- `append_event_at_or_after` (`authz.py:613` onward), which QA-KB-007 is editing.
- The strict `xfail` markers, left for the 6-verifier.

## One test seam moved (no assertion changed)

`backend/tests/integration/repositories/test_run_events_db.py::test_append_event_next_seq_retries_past_a_raced_seq`
simulated the race by patching `store.read_events` to return a stale empty snapshot on its first call, then
asserted `calls["n"] >= 2`. After the fix the method no longer calls `read_events`, so the race was never provoked.
The test failed at `:272` ("a seq collision must have forced a re-read (retry)"), while `created is True` and
`seq == 2` still held.

The ISS-874 card's Expected section names the per-attempt mechanism: a keyed `event_id` lookup plus the bounded
`_max_event_seq` tail probe. The test's seam encoded the old mechanism, which that card names as the defect. The
stale snapshot is therefore now injected through `store._max_event_seq`, which returns 0 once. That is the seam
`backend/tests/integration/api/test_rest_answers_cancel_api.py:555-568` already uses for the same race. Every
assertion and the docstring are unchanged.

The moved seam still catches a broken retry. A scratch `-p` plugin swapped in a mutant that probes the tail once
and never re-probes after a collision. The test fails on it (`RuntimeError: mutant: exhausted`) and passes on the
fix. The ISS-874 analysis did not list this test in its blast radius; that note is now on the card.

- **ISS-874 equivalence.** The pre-fix loop, copied verbatim, and the fixed method return the same
  `(created, seq)` and leave the same rows in eight scenarios:
  - an empty run
  - a tail of 3

  - the same `event_id` under another workspace
  - higher seqs in another scope
  - a session-less store (the `_run_bounded` thread path)
  - a concurrent writer committing our `event_id` between the read and the insert (S8)
