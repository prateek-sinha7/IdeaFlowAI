## What is suspected

[ISS-315](20260828-1750-ISS-315.md) established the mechanism on the *Save workflow* button: a
client-side guard blocks the handler and returns early, and the ONLY user-facing signal is a
`title` attribute (a hover-only native tooltip that never appears on click) plus a bare
`.focus()` call with no accompanying visual treatment — no toast, no red border, no
`aria-invalid`, no inline message. The *Run once* button, in the same header block, ~30 lines
above the Save button, has the identical shape (confirmed by direct read):

```tsx
// frontend/src/components/workflow/composer/ComposerPage.tsx:1076-1097 (current)
onClick={() => {
  if (briefText.trim().length < 3) {
    if (view === "simple") {
      briefTextareaRef.current?.focus();
    } else {
      setBriefFocusSignal((n) => n + 1);
    }
    return;
  }
  handleRunOnce(briefText);
}}
disabled={!onRun}
title={
  !onRun
    ? "Run wiring lands in 41-06"
    : briefText.trim().length < 3
      ? "Add a brief first"
      : undefined
}
```

`briefFocusSignal` only selects the Brief node in Canvas view or plain-focuses the textarea in
Simple view (comment at `ComposerPage.tsx:233-234`: "bumps on every Run click while the brief is
too short; CanvasView watches it to select the Brief node and focus its textarea") — neither path
sets any error/invalid state, shows a message, or changes the field's styling. `disabled={!onRun}`
only covers the unrelated "run wiring not attached yet" case; when `onRun` is present and the
brief is merely too short, the button stays fully enabled and clickable, exactly like ISS-315's
Save case. A repo-wide grep of this file confirms `saveError` (the one existing visible-error
mechanism, rendered at `ComposerPage.tsx:1394-1398`) is never referenced anywhere near this
guard, so — unlike ISS-315's sibling fix, which can reuse that banner — this guard has no
existing visible-error plumbing to reuse at all.

## Condition

On any composer route (`/workflows/new`, an edit route, or a built-in canvas), leave the Brief
field empty or under 3 characters and click "Run once" while `onRun` is wired (button enabled).

## Expected vs actual

- **Expected:** attempting to run with an insufficient brief gives an observable signal — an
  inline message, a red border/`aria-invalid` on the brief field, or a toast — not just a hover
  tooltip.
- **Actual (predicted):** the click is silently absorbed; only a focus/selection change occurs,
  indistinguishable from a stray click, identical in kind to ISS-315's Save case.

## Why the root cause implies this

ISS-315's root cause is not "the Save button specifically is broken" — it is that this header's
inline validate-and-return guards signal failure only via a hover-only `title` attribute and a
bare focus call, with no visible error state wired up anywhere near the field. That exact
mechanism is duplicated (different condition, same shape) on the very next button in the same
JSX block. Nothing about the Run once guard differs in kind from the Save guard ISS-315 already
documents.

**Marked INFERRED**: no live click-through has been performed against this button; only the code
shape (guard, focus/signal-bump, `title`, absence of any error-state styling) has been read and
confirmed. What would confirm it: type 1-2 characters into the brief field, click "Run once", and
inspect `document.body.innerText` / DOM classes for any error text, red border, or `aria-invalid`
— the same check ISS-315's evidence ran for the Save case.
