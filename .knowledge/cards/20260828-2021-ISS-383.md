## What happened

On a completed, immutable run's Workspace tab (`/runs/<id>/workspace`), the "Code" view of any
text file (`.json`, `.md`) renders inside a live, freely-typeable CodeMirror 6 instance. The file
pane gives no indication anywhere — no lock icon, no "read-only" badge, no disabled/greyed
styling, no Save/Discard control, no warning — that what looks like a passive file-preview surface
actually accepts and inserts arbitrary keystrokes at the cursor position. Navigating to a
different file and back silently discards the typed text (the original bytes are re-fetched from
`GET /api/runs/{id}/sandbox/file?path=...`) with zero indication anything was lost.

## Reproduction (3/3, cold start, different file each cycle)

Route: `/runs/b9feac1c-ec21-4531-8ba7-bb391786993e/workspace` (a "Done"/completed "Ppt V2" run),
signed in as qa-admin.

- **Cycle 1** — cold nav to `/dashboard` then `/runs/<id>/workspace`, opened `PLANNER.md` (Run
  notes), toggled to "Code" view, `document.querySelector('.cm-content').isContentEditable` ===
  `true`, typed `CYCLE1_EDIT_TEST` — inserted live, confirmed via `.cm-content.textContent`.
- **Cycle 2** — cold nav (fresh `/dashboard` → `/runs/<id>/workspace`), opened
  `01-ppt-brief-analyst.md` (Agent outputs), same result: `isContentEditable === true`, typed
  `CYCLE2_EDIT_TEST`, inserted live.
- **Cycle 3** — cold nav, "All files" tab, expanded `.browser`, opened `deck-styles.json` (a
  different file type, JSON), same result: `isContentEditable === true`, typed
  `CYCLE3_EDIT_TEST`, inserted live.

3/3 cold-start reproductions, three different files, two file types, both entry paths (Artifacts
tree and the "All files" tree). No `PUT`/`POST`/`PATCH` request was ever observed after typing in
any cycle — only the original `GET .../sandbox/file` calls — so the defect is purely the
unguarded client-side editable state and its silent-discard UX, not data loss on the server.

## Root cause

`frontend/src/components/results/SandboxTab.tsx`, function `CodeView` (~line 491 onward).

The function's own doc comment (line 476) states the component is:

> "CodeMirror 6, **read-only**, and LAZILY imported... Everything else CodeMirror ships
> (autocomplete, linting, history, edit keymaps) is for EDITING **and is not pulled in**."

But the actual `EditorView` construction (~line 675) never sets `EditorState.readOnly.of(true)` or
`EditorView.editable.of(false)` anywhere in the file (`grep -n "readOnly\|editable"` on the file
matches only the extensions list, not a config call), and DOES include `commands.history()` and
`commands.defaultKeymap` — the exact "edit keymaps" the doc comment says are excluded. A second,
later inline comment at line 687-690 rationalizes this as deliberate ("Replace has to be able to
write, so the doc is editable — but it is a SCRATCHPAD... nothing you do here can alter what
shipped"), directly contradicting the function's own top-of-file doc comment one line above it.

The two comments disagree with each other and the implementation matches only the second, later
one — the component's own documented contract ("read-only") is not what ships. Whether the
original intent was truly read-only and a later Find&Replace change silently dropped the
`readOnly` config (most likely, since `search.search({ top: true })` does not itself require full
document write access — CodeMirror's search-replace can be scoped without `defaultKeymap`), or the
top-of-file comment is simply stale, the current state is an inconsistency between the component's
declared contract and its behavior, with no user-facing signal either way.

## Expected vs actual

- **Expected:** A file-preview pane for a completed, immutable run's workspace renders content
  read-only (`isContentEditable !== true`, or an explicit read-only CodeMirror configuration), or
  if editing is intentional, it is clearly indicated (an "editing" label, a visible Save/Discard
  affordance, a warning before a switched-away edit is discarded).
- **Actual:** The pane is a fully live, keystroke-accepting editor with no read-only enforcement,
  no visual indication of (in)tended immutability, and no warning that typed edits are silently
  discarded on navigating to a different file — while the component's own doc comment claims it
  is read-only.

## Note on a prior WONTFIX candidacy

`bug-hunter/wontfix-candidates.md` already carries an entry for this same register bug, filed by
an earlier validator pass that found only the line 687-690 inline comment and concluded the
editability might be intentional-by-design (for CodeMirror's built-in Find&Replace) and therefore
deferred to a human ruling. That entry did not have visibility into the CONTRADICTING top-of-file
doc comment (line 476: "CodeMirror 6, read-only... edit keymaps... not pulled in") found during
this pass, which shows the component's own stated contract is "read-only" and the implementation
does not honor it — i.e. this is not simply an intentional design tradeoff with no counter-signal,
it is a component whose documented invariant its own code violates. This card documents that
finding as a genuine defect; the `bug-hunter/wontfix-candidates.md` entry should be treated as
superseded context, not the final disposition.
