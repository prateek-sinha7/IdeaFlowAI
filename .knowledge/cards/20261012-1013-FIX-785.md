# FIX-785

Register entry `QA-KB-117` ("Deliverable access hides 'Branch on a decision'"). This change implements the owner decision of 2026-10-09 recorded in `BUGS.md`: "every example workflow that delivers something is listed under Deliverable access ... driven by the same entitlement list as the home catalog rather than a hand-kept map, so the two surfaces agree. Update e2e S-17-08". The root cause was taken from [ISS-1195](20261012-0942-ISS-1195.md) and not re-derived.

## What was wrong

Three surfaces each made their own projection of the same entitlement list:

- **Deliverable access** (`/settings/usage`). Before this change, `AccountSettings.tsx:85-88` `getBasePipelines` kept `TIER_PIPELINES[tier]` ids only when they had a key in the 8-entry `PIPELINE_DISPLAY` map (`:65-74`). Every entitled workflow without a key was dropped: "Branch on a decision" and the other Engine examples ([ISS-1195](20261012-0942-ISS-1195.md)), and `ppt_v2`, `prototype_v2` and `backlog` ([ISS-1196](20261012-0942-ISS-1196.md)). Ids that had a key were listed even when the catalog did not enable them: `mulesoft_to_springboot` and `dotnet_to_azure` (Coming Soon), and `migration` (no manifest) ([ISS-1197](20261012-0942-ISS-1197.md)).
- **The plan modal.** `UpgradePlanModal.tsx:37-41` `unlockedCount` counted `TIER_PIPELINES` with no catalog filter at all, so it showed 4, 13 and 16 ([ISS-1198](20261012-0942-ISS-1198.md)).
- **The home catalog** (`HomeLaunchGrid.tsx`) read the live rows (`GET /api/workflows`): `user_launchable`, `is_beta`, the example prefix and `canRunPipeline`.

## Change (where every caller routes through it)

- **`frontend/src/lib/entitlements.ts`.** New code goes after `canRunPipeline`, below the `TIER_PIPELINES` block the parity test parses.
  - `EXAMPLE_ID_PREFIX` and `isExampleWorkflow` move here from `HomeLaunchGrid.tsx`, which keeps the comment and the classifier from [FIX-645](20260925-1201-FIX-645.md).
  - `splitCatalog(workflows)` returns the catalog's launchable `productRows`, `exampleRows` and `betaRows`; beta wins over the prefix.
  - `catalogAccess(workflows, tier)` keeps the product and example rows that `canRunPipeline(tier, id)` allows.
- **`HomeLaunchGrid.tsx`.** Its three inline filters became `splitCatalog(workflows)`. `isExampleWorkflow` is re-exported, so `HomeLaunchGrid.categories.test.ts` still imports it from there.
- **`AccountSettings.tsx`.** A new `DeliverableAccessGrid` mounts only on the Usage & Limits tab.
  - It lists `catalogAccess(state.global.workflows, tier)`: product rows first, then an always-open "Engine examples" group. The group is not a collapsed `<details>`, so `innerText` and the e2e checks can read it.
  - Labels: a tile uses `PIPELINE_DISPLAY[id].label` when that exists. This keeps "Product Requirements", "Presentation", "Interactive Prototype", "App Builder" and "Custom Workflow", so no label call is made that the owner did not make. Otherwise the tile uses `display_name ?? getWorkflowLabel(id)`, exactly as the catalog does.
  - While the store has no catalog rows (a cold load before `GET /api/workflows` returns, or after it fails), the grid shows the old `getBasePipelines` tiles, per ISS-1195 hazard 2.
- **`UpgradePlanModal.tsx`.** `unlockedCount` now counts the rows `catalogAccess(next)` lists that `current` cannot run. It falls back to the old `TIER_PIPELINES` count only while the catalog is empty. Both entry points, `AccountSettings` and `AppHeader`, use this one component ([FIX-363](20260829-0043-FIX-363.md)). Neither entry point changed.
- **e2e S-17-08.** The owner asked for this update. The file is in ISS-1195's globs.
  - `@pytest.mark.defect` is dropped, and the test is renamed `test_deliverable_access_lists_the_examples_the_catalog_offers`.
  - It opens the catalog's Engine examples, reads every card title, and asserts each one appears after DELIVERABLE ACCESS on `/settings/usage`.
  - The expected set comes from the live catalog and is not hard-coded (ISS-1195 hazard 4: there are eight examples, not seven).
  - The S-17-08 scenario in `17-theme-and-tiers.feature.md` and its per-tier "Deliverable access" paragraph were rewritten to match.

No backend file, API contract or migration changed. `GET /api/workflows` already carries `user_launchable`, `is_beta` and `display_name`.

## Visible effect (derived from the manifests and `TIER_PIPELINES`, not rendered here)

| tier | Deliverable access lists |
|---|---|
| basic | Product Requirements, Presentation, Pitch an idea (Depth) |
| hexaware | Product Requirements, Interactive Prototype, Prototype from documents (Depth), Write backlog from prototype and documents |
| pro | the four above plus Presentation, Pitch an idea (Depth), App Builder |
| enterprise | pro's seven plus Custom Workflow, then "Engine examples": all 8 (incl. Branch on a decision, Browser check) |

Platform Workflows, Mulesoft Migration and .NET Migration no longer appear for enterprise. The catalog files the last two under Coming Soon and has no card for the first. This is the ISS-1197 case the test pins. The plan modal now reads 4 (basic to pro), 9 (pro to enterprise) and 12 (hexaware to enterprise).
