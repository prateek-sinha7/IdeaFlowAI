# ISS-1145

**Register source:** sibling derived during the `QA-KB-108` analysis on 2026-10-09 (root [ISS-1144](20261009-0725-ISS-1144.md)). Not its own bug row.

**Confidence:** the mechanism is CONFIRMED offline, row A of `evidence/qa-kb-108/04-analyze-sibling-probes-output.txt` (`admin_respond_to_auth_challenge` patched to raise `TokenRetrievalError`: status 500, no `access-control-allow-origin`; the `ClientError` control: 503 with it). INFERRED: the real expired-SSO trigger on this step, and the on-screen result (browser not driven).

## Condition

- Any `POST /api/auth/login/challenge` (NEW_PASSWORD_REQUIRED, SOFTWARE_TOKEN_MFA, EMAIL_OTP, SELECT_MFA_TYPE) made while the backend's AWS credential chain cannot be resolved.
- `AdminRespondToAuthChallenge` is a SigV4-signed operation (`evidence/qa-kb-108/06-analyze-botocore-service-model-auth-types.txt`: `auth_type=None` is the default, signed). botocore resolves credentials when it signs, so it raises a `BotoCoreError` subclass (`TokenRetrievalError` for an expired SSO session, `NoCredentialsError`, `CredentialRetrievalError` for an unreachable instance profile) before any HTTP request. `backend/app/api/auth.py:488-511` catches `ClientError` only.
- Reach: the caller holds a `Session` from a successful `/login` moments earlier, so during a steady outage `/login` ([ISS-1144](20261009-0725-ISS-1144.md)) fails first. This card is the case where credentials lapse between the two calls, and the reason a fix that patches only `/login` is incomplete: this handler is the same code.

## Expected vs actual

Expected: 503 `Authentication service unavailable` with the normal CORS headers; `ChallengeForm` renders `err.detail` through `describeApiError` (`frontend/src/app/login/page.tsx:73-81`, used at `:165`). Actual: 500, no CORS header, `fetch` rejects with a `TypeError` instead of an `ApiError`, and the form shows "An unexpected error occurred. Please try again."

## Why the root cause implies it

Same narrow `except ClientError` (`auth.py:492`), same signed-operation trigger, same absence of a safety net (`backend/app/main.py:539` registers only `RequestValidationError`). The 503 fall-through that already exists at `auth.py:507-511` is all that is missing for a `BotoCoreError`.

## Fix direction (INFERRED, not applied)

Route `BotoCoreError` into the existing fall-through at `:507-511` using the shared symbols recommended in [ISS-1144](20261009-0725-ISS-1144.md). Do not add it to the 401 or 400 branches at `:494-506`: they key on Cognito error codes a `BotoCoreError` never carries.
