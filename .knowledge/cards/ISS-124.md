# ISS-124

## Title

SEVERITY WAS UNDERSTATED — this was not minor. Beyond the durable hole, stop_run_driver runs _reconcile_terminal_status once the driver is provably gone, and that decides from the durable tail ALONE: with no pipeline_cancelled row it computes cancelled=[]/completes=[]/failed=[] -> the D2 fail-safe "failed", written through an UNCONDITIONAL _persist_resume_status that OVERWRITES the "cancelled" the driver had just set. So the owners Stop was recorded as a FAILURE. Observed directly as assert 'failed' == 'cancelled'. Two app-layer synthesised pipeline_cancelled frames never persist a durable row at all — a different cause with the same reopen symptom as ISS-121. run_commands.py:2435 (_drive_launch_to_queue) and :2666 (_drive_revision_to_queue) push a terminal frame straight onto the SSE queue with no seq, no event_id and no run_events write. They fire only on a genuine destructive task.cancel() where the engine did not already emit a terminal, so the frequency is low — but a run terminated that way has the same durable hole, and FIX-240 does not touch it (FIX-240 fixes the ENGINE sink; these bypass the engine entirely). Both line numbers re-verified at commit 88521920. Fix shape: give both sites an additive append_event_next_seq` write, which is the allocator an app-layer writer should already be using.

## Source / evidence

Enumerated by the ISS-121 emitter audit (8 engine emitters all persist; these two are the only non-persisting terminals). Filed rather than folded, so a durable-write change to the REST drivers is not smuggled into an engine-sink fix. FIXED 2026-08-12 (FIX-244): both branches now append through _record_cancellation_in_the_durable_tail — FIX-243s collision-safe writer — EXTENDED with a reason parameter rather than copied (INV-12: one durable-terminal writer, three callers); the default keeps FIX-243s payload byte-identical. No duplicate-suppression guard, deliberately: the pipeline_cancelled FRAME is already emitted unconditionally on both branches, so this only makes the row agree with the frame that already ships, and every verified consumer is any()/max()-shaped. 4 new tests in test_rest_answers_cancel.py (20 -> 24), all seen RED. The discriminating one drives a REAL task.cancel(), because the append sits inside an except asyncio.CancelledError block and had to be OBSERVED completing under genuine cancellation — that test also corrected a wrong assumption of mine (the driver deliberately CONVERTS the cancellation into a terminal instead of re-raising).
