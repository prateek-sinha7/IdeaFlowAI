# ISS-124

## Title

Two app-layer synthesised pipeline_cancelled frames never persist a durable row at all — a different cause with the same reopen symptom as ISS-121. run_commands.py:2435 (_drive_launch_to_queue) and :2666 (_drive_revision_to_queue) push a terminal frame straight onto the SSE queue with no seq, no event_id and no run_events write. They fire only on a genuine destructive task.cancel() where the engine did not already emit a terminal, so the frequency is low — but a run terminated that way has the same durable hole, and FIX-240 does not touch it (FIX-240 fixes the ENGINE sink; these bypass the engine entirely). Both line numbers re-verified at commit 88521920. Fix shape: give both sites an additive append_event_next_seq write, which is the allocator an app-layer writer should already be using.

## Source / evidence

Enumerated by the ISS-121 emitter audit (8 engine emitters all persist; these two are the only non-persisting terminals). Filed rather than folded, so a durable-write change to the REST drivers is not smuggled into an engine-sink fix.
