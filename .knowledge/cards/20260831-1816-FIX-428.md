# FIX-428

## What was wrong

The graceful-shutdown budget documented in `config.py` was bounded only in its drain
steps. `shutdown_run_infrastructure()` spends up to 24s in steps 1-3 (uvicorn's 5s
graceful window + the Concierge drain + both cancel-and-wait escalations + the pump
drain), then reaches step 4 — `close_checkpointer()` — which awaited
`pool_to_close.close()` with **no timeout**. A Postgres pool that is slow to close (an
in-flight statement, a wedged socket, a server that stopped answering) therefore sat on
top of the 24s with nothing capping it, pushed teardown past the container's stop grace
period, and got the process SIGKILLed mid-shutdown — the exact failure the budget exists
to prevent, with the shutdown summary never logged.

The guard could not see it either: `_teardown_budget_seconds()` in
`tests/unit/test_shutdown_reachability.py` sums the *configured* drains, and this wait
had no knob to appear in. Full evidence in [ISS-106](20260812-1315-ISS-106.md), recorded
during quick-260812-hsx by [FIX-234](20260812-1312-FIX-234.md) — which corrected the
budget comment but deliberately did not change the production shutdown path.
[ISS-103](20260812-1312-ISS-103.md) names the same class of defect for
`asyncio.runners._cancel_all_tasks`' untimeouted gather; that half is NOT addressed here
and stays open.

## Root cause

`backend/app/agents/checkpointer.py:140-144` (pre-change numbering, exactly as the card
said):

```python
    if pool_to_close is not None:
        try:
            await pool_to_close.close()
        except Exception as exc:
            logger.warning("close_checkpointer: pool.close() raised (non-fatal): %s", exc)
```

The `except` arm made a *raising* close safe, so the failure mode everyone had thought
about was covered; a close that simply never returns was not. `psycopg_pool` 3.3.1's own
`AsyncConnectionPool.close(timeout=5.0)` bounds only the worker gather — the
`await self._close_connection(conn)` loop that follows it is unbounded on a wedged
socket, so the pool cannot be relied on to bound itself.

Blast radius re-checked at fix time rather than taken from the card: `close_checkpointer`
has exactly one non-test caller, `backend/app/api/run_shutdown.py:198` (step 4), plus
`tests/conftest.py` and `tests/agents/_resume_child.py`. All of them route through the
one function, so the timeout belongs in the function.

## What changed and why there

| File | Change | Why |
|---|---|---|
| `backend/app/agents/checkpointer.py` | Module-level `import asyncio`; `pool_to_close.close()` wrapped in `asyncio.wait_for(..., timeout=settings.SHUTDOWN_CHECKPOINTER_CLOSE_SECONDS)`; a new `except asyncio.TimeoutError` arm ahead of the existing `except Exception` logs the abandoned close; docstring point 5 records the bound | The shared function every caller routes through; the D7 latch/null ordering above it is what makes abandoning the close safe |
| `backend/app/core/config.py` | New `SHUTDOWN_CHECKPOINTER_CLOSE_SECONDS: float = 1.0`; the budget comment gains the `1  checkpointer pool close` row (total 24 → 25 with stop-runs off, 31 with it on) and drops the "true worst case is unbounded — ISS-106" paragraph | The other two shutdown waits are settings here; the arithmetic the card asks the guard to cover is this comment's |
| `backend/tests/unit/test_shutdown_reachability.py` | `_teardown_budget_seconds()` adds the `SHUTDOWN_CHECKPOINTER_CLOSE_SECONDS` term; its docstring no longer says the worst case is invisible | The card's fix shape: "include that setting in the arithmetic guard, so the budget test covers the whole path rather than the part that happens to be configurable" |

**Why 1.0s.** The card leaves the value open. A healthy close of a `max_size=10`
autocommit pool is milliseconds, so 1s is generous for the good path and cheap on the bad
one, and it keeps the documented worst case at 25s against a 30s ceiling (5s of headroom)
rather than eating it. Operators can raise it; the point is that the wait is now
*counted*.
