# ISS-1206

**Register source:** sibling derived during the `QA-KB-112` analysis on 2026-10-12 (root [ISS-1203](20261012-0949-ISS-1203.md)). Not its own bug row.

**Confidence.** INFERRED sibling. Observed in two screenshots (the validator's `02-validate-attempt2-…png` and the e2e failure shot `analysis-07`): the light-theme legibility. Read from code, not run: the no-token behaviour and the missing exit controls. Not checked: the dark theme.

## Why the root cause implies it

The Security tab lived inside `[...view]`, `DashboardLayout` and `AccountSettings`, which supply the sign-in redirect, the header with back and the account menu, and the design tokens. The replacement is a bare static route under a root layout that supplies none of that (`layout.tsx:38-72`: providers and a body, no header). Whatever the shell used to give the page it now has to give itself, and it re-implements none of it. The page's primary audience, a blocked admin sent there by `admin/page.tsx:190-196`, meets all three gaps.

## Condition and what happens

1. **No sign-in redirect for a visitor with no stored token (read from code).** `page.tsx:37-41` sets the error "Please sign in again to continue." and `:110-116` offers "Try again", which re-runs `begin()` and fails the same way. Compare `[...view]/page.tsx:937-940` (`router.replace(buildLoginRedirect())`) and `SecuritySection.tsx:75-80`, which redirected a token-less user to login. An expired token is covered app-wide: `AuthSessionProvider` ends the session through the same safe login redirect on a terminal bearer failure (`providers/AuthSessionProvider.tsx:1-12`), so the gap is the never-signed-in or signed-out case.
2. **No way out, including the step the page demands (CONFIRMED by code).** After a successful verify the page says "Sign out and sign back in to finish… admin pages will keep refusing until you sign in again" (`page.tsx:203-219`) and renders no sign-out control, no link, no back button. The account menu is part of the shell, which is not on this route. The only exits are the browser's Back or typing a URL.
3. **Unreadable on the light theme (observed).** The page is styled for a dark background: `text-slate-100` on the H1 (`:90`), `bg-slate-900/60` on the key block (`:133`), `bg-slate-950` on the code field (`:185`). The app's light paper is `#F0EEE7` (`styles/globals.css:99`; dark is `#0D0D0D`, `:256`; the theme comes from `localStorage['velocity-theme']`, `layout.tsx:41-43`). In both screenshots the H1, both step headings and the three labels (ACCOUNT, SETUP KEY, SETUP LINK) are washed out against the paper, and the code field is a black box. INFERRED: legible when the dark theme is on.

## Expected vs actual

Expected: the page a blocked admin is redirected to is readable in the default theme, lets a signed-out visitor sign in, and gives the user a way to sign out when it tells them to. Actual: none of the three.

## Decision needed (owner)

This is a UI change, outside `QA-KB-112`'s test-side boundary. If wanted: use the design tokens and `Card`/`Button` (as `SecuritySection.tsx` does) instead of fixed slate classes; add the no-token redirect the catch-all has; give the page one exit (a sign-out action or a link back to the app). Which shell the page should live in is the same question as [ISS-1204](20261012-0949-ISS-1204.md).

## What would settle it

Set `localStorage['velocity-theme']='dark'` and cold-load `/settings/security` (legible?); clear `auth_token` and cold-load it (stuck on the message, no redirect?); read the "enrolled" state in the unit harness (`security.test.tsx` already renders it) for the missing control. No mutation, no valid code.
