## What was wrong

BUG-20260828-085047-runs-id-stream (`bug-hunter/ledger.md`). On a completed run
of `playwright_smoke_test` (`649e56cf-ce0f-4a0f-91fa-4e75a971a980`) the Preview
toolbar's "Download the deliverable" button was `[disabled]` forever, while the
deliverable was fully rendered and downloadable from the file panel's own
"Download ZIP". `GET /api/runs/{id}` returned `deliverable_mimetype:
"application/zip"` with `deliverable_filename: null`.

## Root cause

As traced in [ISS-313](20260828-1946-ISS-313.md): a manifest may declare
`deliverable.strategy` with no `deliverable.name`
(`backend/agents/workflows/playwright_smoke_test/workflow.yaml:25-26`).
`WorkflowCompiler._compile_deliverable` (`backend/agents/workflows/compiler.py:1446-1451`)
copies that `None` through by design (INV-5 — no defaulting in the compiler),
`engine.py:3737`/`:3754` emit it verbatim as
`pipeline_complete.deliverable_filename`, and `run_commands.py:3050-3051`'s
correct `is not None` guard leaves `WorkflowRun.deliverable_filename` NULL.

The button then never enables: `PreviewPanel.tsx`'s toolbar-download effect
returned early on a falsy `declared` name (`if (!declared || cancelled) return;`),
so `deliverableFile` stayed `null` and `canHeaderDownload` stayed `false`.

## What changed, and why there

`frontend/src/components/preview/PreviewPanel.tsx` only — the file this card's
issue scopes (`applies_to.globs`). The effect now fetches the workspace listing
before branching, and when **nothing was declared** it arms a new
`deliverableBundle` flag from `listing.files.some((f) => f.deliverable)`; the
handler then serves `getRunSandboxZip` under `workspace-<run8>.zip` instead of a
single workspace file. The declared-name path — including FIX-318's
extension-keyed `.html`/`.pptx` sibling preference and its "declared but not on
disk stays disabled" rule — is untouched.

### Why NOT the backend default the ISS-313 analysis proposed

[ISS-313](20260828-1946-ISS-313.md)'s appended analysis proposes a
`default_deliverable_name(strategy, ...)` sibling to `default_mimetype`, applied
at `engine.py:3737`. That cannot work here, and it is recorded so nobody retries it:

- All three name-less manifests (`playwright_smoke_test`, `sample_fanout`,
  `sample_wave`) declare `serialized_sandbox`, whose deliverable is the WHOLE
  workspace serialized into `filename:` blocks
  (`backend/agents/capabilities/deliverables/serialized_sandbox.py:45-51`). There
  is no single file to name, and no zip on disk — the archive is synthesized on
  demand by `GET /api/runs/{id}/sandbox/zip` (`backend/app/api/run_files.py:566`).
- So any static default (`deliverable.zip`) names a file absent from the
  workspace listing. The FE gate is presence in that listing
  (`listing.files.find((f) => f.path === c)`), so the button would still be
  disabled — verified against the live listing for
  `649e56cf-ce0f-4a0f-91fa-4e75a971a980`, which holds
  `.agents/01-playwright-smoke-test.md`, `.browser/smoke.png` and `index.html`
  (`deliverable: true`) and nothing else.
- Worse, it would write a fabricated name into `WorkflowRun.deliverable_filename`,
  which every other consumer DISPLAYS (`RunChatLane.tsx`'s `DeliverableCard`
  badge and its "open in Preview" target, `PreviewPanel`'s URL bar,
  `WorkflowHistory.tsx:928`) — reintroducing exactly the mislabelled-deliverable
  problem [FIX-318](20260827-0055-FIX-318.md) exists to prevent.

The fix therefore lands at the gate itself, which is where ISS-313's own
`applies_to.globs` and its "Expected" already pointed ("matching the deliverable
that is demonstrably downloadable via the file panel's 'Download ZIP'").

## Not fixed by this card

[ISS-434](20260828-2240-ISS-434.md) — `RunChatLane.tsx`'s `DeliverableCard`
gates on the raw `deliverable_filename`, not on this resolver, so it is
untouched here and stays open. It needs its own decision: show the run summary's
deliverable row for a bundle deliverable that has no filename.
