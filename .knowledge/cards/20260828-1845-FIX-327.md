## What was wrong

On `/runs/b9feac1c-ec21-4531-8ba7-bb391786993e/files` — a completed `ppt_v2`
run whose last agent is literally "PPTX Code Generator" — the Files tab's
"Final output" hero read `kindred-a-custombuilt-social-network-pla.html`,
HTML (.html), 53.2 KB. That is `tmp/kindred-pitch-deck.html` (54,588 B), a
mid-pipeline scratch file the Deck Engineer wrote into a `tmp/` working
directory. Neither the backend-declared `presentation.html` nor the real
`presentation.pptx` (163,771 B, `kind:"binary"`, `deliverable:true`) was
listed, previewable or downloadable — not individually, not via "Download
All" — even though `GET /api/runs/{id}/sandbox` returns both.

The same derivation, reached through two other callers, failed differently:
the History browser's own detail Files tab dropped a `ppt_v2` run into the
generic branch entirely (BUG-20260828-012900-runs-id-files, register
`bug-hunter/ledger.md`), and the "From v{n-1}" base-version section rendered
zero rows for a `ppt_v2` parent.

## Root cause

One mechanism, three callers.

1. **`FilesTab.tsx:390-400` (`deriveDeliverableFiles`)** built the deliverable
   row's NAME and SIZE by regex-parsing the content string it was handed
   (`<title>` / `<h1>`, then `formatSize(content.length)`), and its bytes were
   that same string. The string is `run.output` = `ctx.last_streamed` — the
   text the LAST agent streamed. For `ppt_v2` that is step 4 (PPTX Code
   Generator), which only *reads* `presentation.html` (written by step 3 — the
   one-writer-per-file rule of [ADR-0029](20260827-0054-ADR-0029.md)), so the
   streamed text matched the `tmp/` scratch file instead. Nothing in this path
   ever called back to the workspace listing or to `deliverable_filename`,
   which is precisely what [FIX-318](20260827-0055-FIX-318.md) had already
   built for the header Download button — but left INLINED in
   `PreviewPanel.tsx:846-910`, so no second surface could reach it.
2. **`FilesTab.tsx:392`** matched the literal strings `"ppt"` / `"ppt_revision"`
   only. `PreviewPanel.tsx:578`'s `renderType` folds `ppt_v2` into `"ppt"`, so
   the MAIN call site smuggled a normalized type in and looked fine — while
   `FilesTab.tsx:436-440`'s base-version fetch passes `parentRun.type` RAW, so
   a `ppt_v2` parent matched no branch and returned `[]`, and that call site has
   no generic fallback at all (ISS-215).
3. **`WorkflowHistory.tsx:542`** carries a SECOND, independently-maintained
   `isPpt` that never gained the `ppt_v2` normalization either, so a reopened
   deck got `pptContent: undefined`, `isGeneric: true`, and a
   `genericDeliverable` whose `filename` was hardcoded `undefined`
   (`WorkflowHistory.tsx:911`) even though `selectedRun.deliverableFilename`
   sat on the same object (ISS-214).

## What changed and why there

**`frontend/src/lib/api.ts`** — new exported `resolveRunDeliverable(token,
runId, declared?)`. It is [FIX-318](20260827-0055-FIX-318.md)'s rule, now
callable: read the declared `deliverable_filename` (off the run row when the
caller does not have it), list the workspace, and return the `SandboxFile`
that exists — preferring `<stem>.pptx` when the declaration is `.html`, and
`<stem>.html` when it is `.pptx`. Keyed on the declared EXTENSION, never a
workflow name (SC-001). `null` when nothing is declared or neither candidate is
on disk, so a surface never names a file it has not seen. It lives beside
`getRunSandbox` / `getRunSandboxFileBlob` because that is the one module every
Files-tab caller can already reach.

**`frontend/src/components/results/FilesTab.tsx`** — the fix sits in the
component, not in its callers, because BOTH `<FilesTab>` render sites and the
base-version section route through it:

- One settled-run effect (`runId` present, `isRunning` false) calls
  `resolveRunDeliverable`; `withWorkspaceFile` then re-stamps the derived row
  with the resolved file's name, its real byte size and a `workspace: {runId,
  path}` marker. Format comes from the resolved extension (`PPTX (.pptx)`), so
  the row cannot claim HTML while serving a binary.
- `handleDownload` gains a FIRST branch for a `workspace` row: bytes via
  `getRunSandboxFileBlob`, the same reader the Workspace tab and header
  Download use. This deliberately steps around the dead
  `file.id === "presentation-pptx"` handler (`:611`), which would re-convert
  the deck HTML through `POST /api/runs/export-pptx` rather than fetch the
  binary the run actually produced. That handler is left untouched and still
  unreachable — `deriveDeliverableFiles` never emits that id.
- Scoped to `deriveDeliverableFiles`' rows only: the `app_builder` ZIP is
  assembled client-side from parsed code blocks and has no single file on disk
  to reconcile against, and the generic row still fires only when nothing was
  derived.
- The base-version section runs the SAME resolver against `parentRunId`, in its
  own `try` so an expired parent workspace leaves the derived rows standing
  instead of emptying the section.
- `ppt_v2` joins the ppt branch of `deriveDeliverableFiles`, which is what the
  raw-type call sites need.

**`frontend/src/components/history/WorkflowHistory.tsx`** — `isPpt` gains
`ppt_v2` (matching `PreviewPanel.tsx:578`, which also restores PPTPreview for a
reopened deck), the Files tab now receives `runId={selectedRun.id}` so the same
resolver runs on this surface, and the generic row's `filename` reads
`selectedRun.deliverableFilename` instead of the hardcoded `undefined`.

`PreviewPanel.tsx` was NOT converted to the shared function: its five FIX-318
specs mock `@/lib/api` wholesale and assert on `getRunSandbox` /
`getRunSandboxFileBlob` being called, so moving the logic behind a new export
would blank that coverage and force those tests to be rewritten. Recorded as
[ISS-251](20260828-1846-ISS-251.md) rather than done quietly here.

**One assertion left red on purpose.** The second
`WorkflowHistory.pptV2Files.test.tsx` guard asserts that a `ppt_v2` run's
`genericDeliverable.filename` is not undefined. Once `ppt_v2` is normalized
into the ppt slot — which the FIRST guard in the same file requires — the run
correctly never reaches the generic-deliverable branch, so that prop is
`undefined` by design, exactly as it is on the main run screen
(`PreviewPanel.tsx:624`'s `hasGenericDeliverable` excludes a known render type
that has content). The defect the card names — `filename: undefined` hardcoded
at `WorkflowHistory.tsx:911` — IS fixed and is observable on a genuinely
generic run. The assertion was not edited.
