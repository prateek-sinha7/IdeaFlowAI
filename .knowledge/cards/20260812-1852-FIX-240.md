# FIX-240

## Description

Every chat turn during a live run silently destroyed one engine event from the durable log (ISS-121). The register row's own root cause was WRONG and is corrected in place. It claimed pipeline_cancelled is NEVER WRITTEN to run_events and prescribed "make the reopen path consult the run record". Every MEASUREMENT in that row is right; the causal claim on top of them is not. pipeline_cancelled IS written by all eight engine terminal emitters — on run 808612bf the INSERT was attempted, rejected by uq_run_events_scope_seq, and silently swallowed. Two writers shared ONE per-run seq space with TWO algorithms: ScopedStore.append_event_next_seq takes max(seq)+1 and retries past IntegrityError, while _RunEventSink.persist used a fixed in-memory counter and swallowed the collision — it catches SQLAlchemyError, IntegrityError is one, so a production seq collision took the branch written for "the offline harness has no schema" and was indistinguishable in the logs. authz.py:462-465 documented this as an accepted trade-off calling the collision "rare"; it fires on every chat turn during a live run, and the victim is whatever the engine emits next. At a gate the engine is idle, so the victim is deterministically the terminal frame — which is exactly why the symptom looked like "cancelled is never persisted". The fingerprint: the log does not end at review_gate_ready (278) — seq 281 is a narrator card reading "Cancelled by you", projected from the very event whose row is missing; a milestone card whose preceding row is a chat_message is structurally impossible otherwise. Also corrected: the rejection came through POST /messages (the only one of the three gate-adjacent endpoints that writes a durable row), not POST /gate. Fix: ScopedStore.append_event_at_or_after re-appends past the racing writer and returns the seq the row actually landed on; both engine drive loops (execute() and the resume driver) re-stamp data["seq"] with it and advance the allocator past it. The re-stamp is mandatory, not cosmetic — run_stream.py:198 renders the SSE id: cursor from row.seq on replay and :264 from data["seq"] live, so a retry without a re-stamp would corrupt Last-Event-ID resumption: a worse bug than the one being fixed. The obvious retry was REJECTED on cost: calling append_event_next_seq per engine event materialises the whole log per write and the corpus holds a 36k-row run; _max_event_seq is a bounded index probe on uq_run_events_scope_seq instead. The discriminator is the load-bearing part: a rejection is retried ONLY when the tail actually reaches the attempted seq. It does not in the characterization harness — measured, not assumed: the harness's persist failure is a sqlite3.IntegrityError FOREIGN KEY violation (the workflow_runs parent row is absent), so a naive "retry on IntegrityError" would have spun 8 attempts per event across every golden and re-stamped data["seq"], breaking assert_seq_contiguous, which pins seq DELTAS at exactly 1 on the RAW pre-normalize stream. The claimed INV-3 hazard was refuted before the design was chosen and replaced with the real one: goldens snapshot the YIELDED stream with seq/event_id stripped and no DB at all, and contain zero review_gate_ready / zero pipeline_cancelled (gate_agent_ids=[]) — so they are the neutrality gate, never the detection gate. Part (b) is data repair only and deliberately small: the D-14g SSE gate re-arm now consults the persisted WorkflowRun.status (reusing the exported TERMINAL_STATUSES, not a third copy). gate_pendency stays PURE — the import-linter contract forbids agents.capabilities importing app.*, so the status check lives at the app boundary. No synthetic event is back-filled: fabricating durable rows with no event_id provenance would make the log lie, and consulting the run record as a general substitute would install the second source of truth for terminal state that INV-12 exists to prevent. Why it shipped: test_append_event_next_seq_retries_past_a_raced_seq proved only that the chat writer WINS the race and never asked what happened to the loser — that missing half is TEST-024. All 3 new tests assert the durable ROW, never the yielded frame (the live stream is intact on every path, which is why three earlier offline probes for ISS-091 missed this entirely), were seen RED at 9e3dc9b0, and fail on their OWN assertions under retry-disabled / guard-removed mutations. FIX-232 is untouched and its money-stopping behaviour is preserved. Files ISS-123 (up to 29 already-destroyed events, not retroactively recoverable), ISS-124 (two app-layer terminals that never persist at all), ISS-125 (_stamp_resume_marker's full-log scan), ISS-126 (a fresh reopen still replays the dangling gate row).

## Root cause

Two run_events writers allocated from ONE per-run seq space with TWO algorithms; the engine's _RunEventSink.persist caught SQLAlchemyError (which IntegrityError subclasses) and degraded a real uniqueness collision through the branch meant for the schema-less offline harness, discarding the row.
