## Why this must also be broken (derived from the ISS-378 root cause)

[ISS-378](20260828-2006-ISS-378.md)'s root cause is that the `tools` lever is hand-copied per
authoring surface: the only things shared are the reducer `applyLeverPatch` and the grant list
`TOOL_GRANT_LEVERS` / `effectiveToolGrants`. Nothing shares the WRITER. The agreed minimal fix for
ISS-378 adds a third hand-copied writer, so the question "is the copied write correct?" has to be
answered first, and it is not: both existing copies have the same flaw.

## Mechanism (read; the reducer behaviour also re-run offline)

`effectiveToolGrants` returns exactly two keys, whatever `sel.tools` holds
(`frontend/src/components/workflow/AgentsPopup.tsx:1529-1536`):

```ts
return {
  read_files: sel?.tools?.read_files ?? true,
  write_files: sel?.tools?.write_files ?? true,
};
```

`applyLeverPatch` assigns each patched key whole (`AgentsPopup.tsx:1484-1491`, `cur[key] = v`), so a
`tools` patch REPLACES `sel.tools`. Both existing grant writers pass a fresh two-key object:

- `frontend/src/components/workflow/composer/CanvasConfigRail.tsx:929` —
  `onToggle={() => patch({ tools: { ...toolGrants, [key]: !toolGrants[key] } })}` where
  `toolGrants = effectiveToolGrants(sel)` (`CanvasConfigRail.tsx:465`).
- `frontend/src/components/workflow/AgentsPopup.tsx:2117-2121` (AdvancedExpander, Simple view's
  Configure panel) — `updateLever(agent.id, { tools: { ...grants, [key]: e.target.checked } })`,
  `grants = effectiveToolGrants(sel)` (`:2063`).

`StepSelection.tools` also carries `tool_sets` (the named tool packs, `frontend/src/types/index.ts:615-624`),
which the rail reads back from the same object (`CanvasConfigRail.tsx:475`,
`const toolPacks = sel.tools?.tool_sets ?? [];`) and writes through `toggleToolPack`
(`CanvasConfigRail.tsx:476-486`, which does preserve the grants). The composer stores a step's
selection by plain replace (`ComposerPage.tsx:764-774`, `next[agentId] = sel`), so nothing merges
`tool_sets` back in.

Offline check (scratchpad, the two reducers copied verbatim, `node` run, no app involved):

```
existing pattern  -> {"tools":{"read_files":true,"write_files":false}}
amended pattern   -> {"tools":{"read_files":true,"write_files":false,"tool_sets":["playwright"]}}
```

for `sel = { tools: { read_files: true, write_files: true, tool_sets: ["playwright"] } }` and the write
`{ tools: { ...grants, write_files: false } }` versus `{ tools: { ...sel.tools, ...grants, write_files: false } }`.

## Expected vs actual

- **Expected:** switching one grant changes only that grant; the step's tool packs are untouched.
- **Actual:** the first grant toggle after a pack is on removes the pack from the selection. On the
  rail the pack switch (`on={toolPacks.includes(pack)}`, `CanvasConfigRail.tsx:979-983`) re-reads OFF
  immediately. Simple view has no pack control at all (see [ISS-913](20261001-2218-ISS-913.md)), so
  there the loss is invisible.

## Why this is INFERRED, not CONFIRMED

The code path above is certain; what is not settled is the persisted outcome, which depends on the
save path. `agentToManifestStep` spreads the loaded `agent.tools` FIRST and emits `tool_sets` from
the selection only when non-empty (`frontend/src/store/api/userWorkflows.ts:335-345`;
`agent.tools` is captured whole at load, `:730`). So, by reading:

- a pack ticked in-session on a step that had none is lost at save once a grant is toggled;
- a pack already present in the loaded manifest is re-supplied by `...agent.tools` and survives.

No test covers it (`grep -rn tool_sets frontend/src --include='*.test.*'` returns nothing; only
manifest fixtures mention the key). A browser repro (Canvas, step -> Tools tab, switch "Playwright
browser" on, then switch "Write files" off, watch the pack switch revert) or the unit test below settles it.

Adjacent lead, not filed: the same `...agent.tools` spread means un-ticking a pack that was loaded
from a saved manifest may not remove it at save (the selection loses `tool_sets`, `agent.tools`
re-adds it). Unverified; an `agentToManifestStep` unit test would settle it.

## Where the fix belongs

One writer next to the reader, so every caller routes through it — not a patch in each handler. In
`AgentsPopup.tsx` beside `effectiveToolGrants` (`:1529`), e.g.
`withToolGrant(sel, key, on) => ({ ...sel?.tools, ...effectiveToolGrants(sel), [key]: on })`, called by
the rail (`:929`), AdvancedExpander (`:2119`) and the new ISS-378 rows. Leaving `...sel?.tools` first
keeps `tool_sets` and any other key; the grants still win. Frontend only; no backend change.

## Fixed (2026-10-02, QA-KB-016 fixer): [FIX-703](20261002-0051-FIX-703.md)

`withToolGrant(sel, key, on)` now sits beside `effectiveToolGrants` (`AgentsPopup.tsx:1538-1548`) and returns
`{ ...sel?.tools, ...effectiveToolGrants(sel), [key]: on }`. Every grant control calls it: the rail
(`CanvasConfigRail.tsx:926`), AdvancedExpander (`AgentsPopup.tsx:2184`) and the new `ConfigLeversFlat` rows.
A grant toggle therefore keeps `tool_sets`. `AgentDrawer.toolGrants.test.tsx`'s ISS-912 case XPASSes: the payload
keeps `tool_sets: ["playwright"]`. The `agentToManifestStep` lead on un-ticking a loaded pack was not touched. It is
still unverified, as this card says.
