## Reproduction (3/3, confirmed on every cycle — cold start each time)

Page/route: `/preview-fullscreen`, ready state (App Builder IDE full-screen preview), reached via
a valid `sessionStorage['__app_preview__']` payload matching the `PreviewPayload`/`ParsedFile`
shape (`{projectName, files: [{path, name, ext, content, language}]}`) that
`frontend/src/app/preview-fullscreen/page.tsx` expects.

Each of 3 cycles: fresh navigation to `/dashboard`, clear+reseed `sessionStorage`, cold navigate
to `/preview-fullscreen`, expand `src/styles` and `src/utils`, then type a query into the
"Search files" box that matches exactly one nested file and leaves at least one sibling folder
with zero matching descendants:

- Cycle 1 — query `app` (matches `src/app.js`): `styles/` and `utils/` folders both remain
  visible and expandable; expanding `styles` renders nothing under it. Footer stays "4 files ·
  0.1 KB total".
- Cycle 2 — query `helper` (matches `src/utils/helper.js`): `styles/` folder (zero matches)
  remains visible. Footer unchanged, still "4 files · 0.1 KB total".
- Cycle 3 — query `main` (matches `src/styles/main.css`): `utils/` folder (zero matches) remains
  visible. Footer unchanged, still "4 files · 0.1 KB total".

Conditions established by the repro: tier qa-admin, single-tab session, default light theme,
default viewport — none of those needed to be varied since the defect reproduced on every cold
cycle with no narrowing required.

## Root cause

`frontend/src/components/preview/AppBuilderPreview.tsx`, `FileTreeNode` (search predicate around
line 202):

```ts
const matchesSearch = !searchQuery || node.name.toLowerCase().includes(searchQuery.toLowerCase());
if (!matchesSearch) return null;
```

This guard sits only in the `file`-type branch (the folder branch returns unconditionally at the
top of the function, before this check is ever reached for folders). A folder is rendered and
expandable regardless of whether any descendant file matches `searchQuery` — the filter is never
propagated down into folder nodes, so a folder with zero matching children still renders a header
that expands to an empty list.

Separately, the sidebar footer stat line (`{files.length} files · {...} KB total`, ~line 556)
reads the full, unfiltered `files` array directly — it has no dependency on `searchQuery` at all,
so it never updates while a search is active, and visibly contradicts the filtered file list
above it.

## Expected vs actual

Expected: a folder with zero descendants matching the active search query is hidden along with
non-matching files, mirroring the existing leaf-file filter; the footer file/size summary
reflects the currently visible (filtered) set while a search is active.

Actual: folders are never filtered — any folder containing at least one non-matching file (even
zero matching files) stays visible and expands to an empty branch; the footer is hardcoded to the
unfiltered total and never changes with the search query.

## Blast radius

`FileTreeNode` and the footer live entirely inside the shared
`frontend/src/components/preview/AppBuilderPreview.tsx` component. Grepping every consumer
(`grep -rn "AppBuilderPreview" frontend/src`) finds four real (non-test) mount points, all
rendering the identical, unmodified component:

- `frontend/src/app/preview-fullscreen/page.tsx:118` — the reported path.
- `frontend/src/components/preview/PreviewPanel.tsx:163`, inside `AppBuilderIDEPreview` — the
  embedded, non-fullscreen "Preview" tab for a live/completed `app_builder` run.
- `frontend/src/components/history/WorkflowHistory.tsx:838` — the `isAppBuilder` branch of the
  reopen-run modal (`ideFiles`).
- `frontend/src/components/history/WorkflowHistory.tsx:877` — the `isGenericBundle` branch of the
  same reopen-run modal (`genericBundleFiles`).

Sibling [ISS-500](20260829-0006-ISS-500.md) tracks the other three (not yet independently
reproduced there). [ISS-501](20260829-0006-ISS-501.md) and [ISS-502](20260829-0006-ISS-502.md)
are further consequences of the same missing `searchQuery` wiring (a collapsed folder hiding a
real match, and a zero-match query with no empty-state).

## Fix — where it belongs

Both fixes belong inside `AppBuilderPreview.tsx` itself, not in any caller — all four mount points
route through this one component, so a guard added here fixes every one of them at once:

1. Give the folder branch (~line 169) the same kind of gate the file branch already has: compute
   whether the folder has ANY matching descendant (recursively) and `return null` when it does
   not, mirroring `if (!matchesSearch) return null;` at line 203.
2. Derive the footer's count/size (line 556) from the currently-visible (filtered) file set when
   `searchQuery` is non-empty, instead of reading the raw `files` prop unconditionally.

## Resolution

Fixed by [FIX-394](20260829-0127-FIX-394.md) — `hasMatchingDescendant` now gates `FileTreeNode`'s
folder branch and a `visibleFiles` memo drives the footer stats. Both
