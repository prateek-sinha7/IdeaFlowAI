# ISS-877

**Register source:** `QA-KB-034` in root `LEDGER.md` / `BUGS.md` (root card). Tree: `feat/user-stories-v2`, working tree on top of `024c03ef8`.
**Claim status:** CONFIRMED by reading the code and by offline throwaway probes (no product run, no server, no DB). Anything not
confirmed is marked INFERRED inline.

## Why this is its own card and not ISS-634

[ISS-634](20260831-0115-ISS-634.md) was the card the register entry was logged from. It does not cover this defect:

1. **It disclaims it in its own words.** The last paragraph of its 5-fixer section reads: "Sibling observation, not carded here: the
   roster expansion at engine.py:1721 is **silent** ... a caller that passes a subset gets agents it never asked for with no log line.
   Harmless today (every production caller passes the full roster from `get_pipeline_agents`), but it is what made this take a full
   drive-and-diff to see." This card is that observation, carded.
2. **Different subject and different code.** ISS-634 is a test-harness card (title: the chunk sanitizer; `applies_to.globs` and
   `verification.test_files`: `backend/tests/agents/test_chunk_sanitizer.py`, a path that has since moved to
   `backend/tests/integration/agents/`). This defect lives in `backend/agents/execution_engine/engine.py`, which ISS-634 does not list.
3. **ISS-634's own defect is already addressed in the code, independently of this one.** The harness no longer passes
   `agents=[spec]`: `backend/tests/integration/agents/test_chunk_sanitizer.py:132-158` builds a one-step `compiled_override` and passes
   `agents=[]` (commit `ff37f777a`, 2026-09-04). I read it; I did not run it. So closing this card must not be taken as closing ISS-634,
   and ISS-634 must not be closed on the strength of a log line.
4. **Findability.** ISS-634's index line says nothing about rosters or logging; a search for "roster" does not return it, so a future
   agent debugging a silently enlarged roster would never reach the fix location through it.
5. **Its premise has expired.** "Harmless today" was written 2026-08-31. On 2026-10-01 commit `05204d4f4` ("prototype v2 quick-change and
   feature revisions (spec 022)") added two workflows whose registry roster is a strict subset of their plan, so the seam's partial
   branch is now a live production path, not a test-only one (see "Blast radius").

## Root cause (CONFIRMED)

`ExecutionEngine._execute_impl` (starts `engine.py:4278`) contains the roster seam. The comment (`:4984-5003`) documents the intent;
the code is `engine.py:5004-5007`:

```python
_plan_ids = {s.agent_id for s in compiled.steps}
_roster_is_partial = bool(agents) and {a.id for a in agents} < _plan_ids
if compiled.steps and (not agents or _roster_is_partial):
    agents = self._specs_from_plan(compiled.steps)
```

- **No record is made.** The branch contains no `logger.*` call, no emitted event, no trace entry. `grep -n "_roster_is_partial\|roster expanded"
  backend/agents/execution_engine/engine.py` returns only `:5005` and `:5006`; `git log -S"roster expanded" -- backend/agents/execution_engine/engine.py`
  is empty, so a log line was never there and later removed. The clause was introduced by `bab17c0b9` (2026-08-27, "ppt_v2 pipeline ...").
- **The requested roster is destroyed.** Between the `_execute_impl` signature (`:4278`) and the seam, the variable `agents` is never
  read: the word appears only in the docstring and in one `agents.capabilities...` import path (`:4856`). The rebind at `:5007`
  overwrites the only reference, so nothing after it can reconstruct what the caller passed.
- **The executed roster is the only thing ever reported.** The `pipeline_start` event (`engine.py:5745`) carries `agent_count` and `agents`
  built from `ordered_agents`, i.e. the post-seam roster. A reader sees "6 agents" and has no way to learn that the caller asked for 2.
- **The documented contract points the other way.** [ADR-0008](20260811-ADR-0008.md)'s decision says "the plan FILLS IN rather than
  OVERRULES — the caller's list wins whenever it has one". The strict-subset clause that makes the plan overrule a caller's non-empty list
  was added 16 days after the ADR, and I found no ADR recording it (an `INDEX.md` search for roster / strict subset / fill in matches only
  ADR-0003 and ADR-0008). A reader who trusts the ADR expects `agents=[spec]` to be honoured, which is exactly the surprise below.

Why it matters is demonstrated, not hypothetical: three separate investigations had to rediscover the seam by driving a harness and
diffing ([ISS-634](20260831-0115-ISS-634.md) says so in its own words: "a full drive-and-diff to see"), namely
[ISS-632](20260831-0115-ISS-632.md) (7 tests), [ISS-634](20260831-0115-ISS-634.md) (4 tests) and
[ISS-638](20260831-0115-ISS-638.md) (the `text_only_prompt_hygiene` fixture), and at least four test files carry a workaround and a
comment about it: `test_chunk_sanitizer.py:132-158`, `test_text_only_prompt_hygiene_db.py:80-81` and `:86`,
`test_engine_runner_error_arm.py:56-57` and `:70-71`, `test_phase3_wip_commit.py:651` (all under `backend/tests/`).

(`engine.py:15832`, the shared re-entry stream of `resume_run`, `_replay_clarify_run` and the other resume drivers). One log line at the
seam therefore covers all of them. What each caller hands the seam (all read):

| `ndjson_adapter.py:64` | `get_pipeline_agents("prototype")`, 5 of 5 | inert |

| `kernel_services.run_trigger_workflow` (`kernel_services.py:1596`) | `get_pipeline_agents(workflow_ref)`, plan fallback only when empty | **partial** for the two workflows below (see [ISS-878](20261001-2110-ISS-878.md)) |
| test harnesses | `agents=[spec]`, `[:2]` | partial -> silently expanded (ISS-632 / 634 / 638) |

**Today's partial rosters** (offline probe: `get_pipeline_agents(wf)` ids vs `compile_for_run(wf).steps` ids over all 41 supported
pipeline types: 19 equal, 18 empty registry roster, 2 strict subset, 2 with no `workflow.yaml`):

```
prototype_v2_revision          registry=['prototype-revision-analyzer']  plan=['prototype-revision-analyzer','custom-agent:v2-fix','custom-agent:v2-validate']
prototype_v2_feature_revision  registry=['prototype-revision-analyzer']  plan=['prototype-revision-analyzer','custom-agent:v2-specify','custom-agent:v2-plan','custom-agent:v2-build','custom-agent:v2-validate']
```

The gap is structural, not a bug in the registry: those plan steps are `custom-agent:*` template instances and
`backend/agents/registry.py:206-213` skips them on purpose ("`template: true` marks a folder that exists to be INSTANTIATED ... never to
be a pipeline member"). `resolve_alias` is the identity for both (`engine.py:3530`; evaluated). So for these two workflows the registry
roster will always be 1 agent and the seam's partial branch is the designed completion mechanism. The 18 empty-roster workflows
(`backlog`, `prototype_v2`, the `ex_*` and `sample_*` fixtures ...) take the `not agents` branch, which is also normal.

## Expected vs actual

- **Expected** (register entry): when `execute()` expands a partial roster to the full plan, a log line records the expansion: agent ids
  requested vs agent ids executed.
- **Actual:** nothing is recorded; the caller's ids are gone after `engine.py:5007`.

## The agreed minimal fix: ACCEPTED, with two amendments

The register notes agree on a single `logger.info(...)` inside the branch, only when `_roster_is_partial` is true, never for
`not agents`. I accept the placement, the level and the guard. Amendments:

1. **Log ids, not counts.** The proposed `passed=%d plan=%d` cannot say which agent the caller asked for, and the incident class
   (ISS-632/634/638) is "I passed `[spec]` and five other agents ran". The register's own Expected text asks for agent ids. Under a
   strict-subset roster the lists are bounded by the plan size (5 steps in the largest case today), so ids cost nothing.
2. **Add `pipeline_type`.** The run id alone makes the reader look the run up to learn which workflow it was.

Name the second list `plan=`, not `executed=`: the DAG resolver may still reorder the roster afterwards, and `pipeline_start` is the
authority on execution order.

```python
if compiled.steps and (not agents or _roster_is_partial):
    if _roster_is_partial:  # `not agents` is the normal path; never log it
        logger.info(
            "roster expanded from plan: run=%s pipeline=%s requested=%s plan=%s",
            pipeline_run_id,
            pipeline_type,
            [a.id for a in agents],
            [s.agent_id for s in compiled.steps],
        )
    agents = self._specs_from_plan(compiled.steps)
```

The log is emitted BEFORE `_specs_from_plan`, so it survives a failure inside it (`load_agent_spec` raises for a plan step with no
`AGENT.md`). It names no workflow or agent: ids are data, the guard is set containment, so INV-1 holds.

**Level, and a visibility ceiling (INFERRED for production).** The logger is `agents.execution_engine.engine` (`engine.py:128`);
`backend/app/core/logging.py:315` sets the whole `agents` package to `LOG_LEVEL_APP`, which is INFO when unset and `DEBUG` in a local
`backend/.env`. `env-templates/.env.production.example:28` ships `LOG_LEVEL_APP=WARNING`, so a deployment that follows the template
will not show an INFO line. I recommend keeping INFO anyway: the expansion is by design on the two v2 revision workflows and must not
page anyone, and the goal is dev, CI and incident reproduction. Whether a real deployment pins WARNING is not in the repo (INFERRED);
the register's own Expected text says "debug", so INFO is already the more visible of the two.

**Rejected alternatives.** (a) A new SSE event or a `requested_agents` field on `pipeline_start`: durable, but it changes the event
vocabulary the frontend consumes for a diagnostics-only need. (b) Logging in `launch_run`'s pre-expansion at `run_commands.py:3604-3605`
too: that branch is the normal path for every manifest-only workflow (18 empty-roster types), so a per-launch line there is noise.

## Where the fix belongs

Inside `_execute_impl` at the seam, one block. Do not add it per caller: all of the routes in the table converge here, and the callers
that do their own pre-expansion (`launch_run`) intentionally hand the engine a complete roster. The adjacent defects found while
tracing the callers are not part of this fix; they are carded as [ISS-878](20261001-2110-ISS-878.md).

## Resolution (2026-10-02, QA-KB-034 fixer)

`logger.info("roster expanded from plan: run=%s pipeline=%s requested=%s plan=%s", ...)` sits
inside the `_roster_is_partial` branch (`engine.py:5007-5014`), before `_specs_from_plan`
(`:5015`). The `not agents` path does not log.
`backend/tests/integration/agents/test_roster_seam_log.py::test_partial_roster_expansion_logs_info`
is XPASS(strict), and the empty and full guards pass. [ISS-634](20260831-0115-ISS-634.md) is not
closed by this fix.
