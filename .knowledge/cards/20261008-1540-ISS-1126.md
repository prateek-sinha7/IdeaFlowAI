# ISS-1126

**Register source:** found by the 5-fixer while fixing `QA-KB-102` ([FIX-768](20261008-1540-FIX-768.md)), 2026-10-08. Not fixed there:
the cards scoped the restart-path fix to the status and the terminal event, and writing `.error` from the kernel for every restart-path
failure is a wider change than this bug. Not its own bug row.

**Line numbers** are the working tree with FIX-768 applied (HEAD `2461935f5` + FIX-768).

## What happens (OBSERVED offline, after FIX-768)

`evidence/qa-kb-102/fix-02-end-state-probe.txt`, scenario D: a `running` composed run whose persisted manifest no longer compiles, two
`restore_non_terminal_runs` scans of the real engine.

```
== D restart scan 1: status='failed' error="prior attempt: step a raised ValueError('boom')"
   tail: [(1, 'pipeline_start', None), (2, 'agent_start', None), (3, 'run_resuming', None), (4, 'pipeline_failed', "Resume refused: the workflow this run was launched with no longer compiles (...)")]
== D restart scan 2: status='failed' error="prior attempt: step a raised ValueError('boom')"
```

FIX-768 ended the ghost ([ISS-1119](20261008-1450-ISS-1119.md)): the row is `failed`, one `pipeline_failed` carries the reason, and the
second scan adds no marker. But `.error` is whatever the row held before (the probe seeds an old string; a real `running` row usually holds
NULL). The history row and the run header read `.error`, so they show no reason, or a stale one.

## Why (CONFIRMED by reading)

- The status reaches the row through the state machine: `StateMachine._persist` writes `wr.status = new_state` and nothing else
  (`backend/agents/execution_engine/state_machine.py:109-129`, the write at `:126`). FIX-768's `_fail_resume` and every in-engine failure
  branch (`StepRaised` & co.) take that path.
- The restart drivers (`_admitted_resume`, `_rearm_gate_run`) have no app wrapper. The one app hook they reach, the output persister
  (`engine.py:16167` → `persist_resume_output_columns`, `backend/app/api/run_commands.py:4090`), goes through
  `_apply_terminal_output_columns`, which "writes NO ``status`` / ``error``" (`run_commands.py:3885`).
- The user path is covered: `_reconcile_terminal_status` derives `.error` from the attempt's `pipeline_failed` (`run_commands.py:997-1011`).

So this is not specific to a refused resume: every restart-resumed run that fails (a step raising, a fan-out failure, a budget abort) ends
`failed` with no reason on the row.

## Fix direction (INFERRED, not applied)

Give the restart path the user path's reconcile: call the app's `.error` derivation from the injected output persister (it already reads
the owner-scoped tail after the drive), or add `.error` to what the persister maps from a `pipeline_failed` / `agent_error` in the tail. The
kernel stays out of app columns (SC-001, the persister is keyed on run_id only). Red test: scenario D, assert `.error` is the
`pipeline_failed` reason.
