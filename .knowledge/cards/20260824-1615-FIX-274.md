`ex_A1_loop`'s `check` step must judge the greeting `greet` produced. It was being shown
only the run brief, and asked to judge something it had never seen.

## Root cause, in two halves

1. `consumes` was absent from the compiler's `_ALLOWED_STEP_KEYS` and from the `Step`
   dataclass. Authoring it in a manifest was silently ignored, so
   `_filter_consumed_outputs` intersected against an empty set for every manifest-declared
   step. `produces` existed; its counterpart had never been added.
2. Adding it there was not enough. A composed step's runtime `AgentSpec` is
   `replace(base_spec, id=...)` built from `custom-agent/AGENT.md`, which declares neither
   `produces` nor `consumes` — so the runtime spec still carried empty sets even once the
   compiled `Step` was correct.

## Fix (R-29)

`consumes` added to `_ALLOWED_STEP_KEYS` and to `Step`; `_specs_from_plan` now overlays
both `produces` and `consumes` from the compiled step onto the runtime `AgentSpec`
alongside the existing `display_name` overlay.

## Watch out

Declaring `consumes` gives the DAG resolver a real edge, and it will REORDER the manifest
around it — that is how `ex_A4_human_gate` came to run its branch targets before the gated
step. Pin the sequence with explicit `depends_on` when adding `consumes` to a fixture
(ADR-0004).
