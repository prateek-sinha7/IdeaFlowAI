## Related

**Depends on:** [ADR-0013](20260824-1630-ADR-0013.md)

<!-- /RELATED -->

Found while verifying the `dev` merge. Six failures share one signature — a gate
evaluating twice:

```
test_gates                    assert ['block','block'] == ['block']
test_gates                    assert 'pass' in []
test_declared_gate_streaming  duplicate review_gate_ready for already-approved
test_declared_gate_streaming  expected exactly one review_gate_ready per gated agent
test_declared_gate_streaming  test_declared_gate_rejection_cancels_the_run
test_restart_resume           WR-03 regressed: rejection must end the run
```

## Why it is suspicious

None of those files were touched by EITHER side of the merge. The prime suspect is this
branch's own HITL split ([ADR-0013](20260824-1630-ADR-0013.md)): `_POST_STEP_GATES` now
contains `"human"`, and `human` / `before-human` are registered on one `HumanGate` class
under two names. A gate evaluating in both the pre- and post-step loop would look exactly
like this.

## Why it is still OPEN rather than assigned

No full backend suite was ever run on `c9ec0149c`, so "did the merge cause this" is
currently unanswerable. 33 other failures looked merge-caused and were traced and PROVEN
pre-existing, so the prior favours pre-existing — but that is a prior, not evidence.

**To settle it:** `git worktree add /tmp/premerge c9ec0149c`, run
`pytest tests/agents tests/unit tests/integration`, diff the failure sets. Two collection
blockers must be patched in the worktree first or pytest aborts and runs nothing — see
`specs/015-frontend-routing/post-merge-backlog.md` §1.1.


## Resolution — 2026-08-25

**Attributed, and the suspicion recorded above is WRONG.** `_POST_STEP_GATES` causing
double EVALUATION is impossible: `_evaluate_gates`' phase filter is mutually exclusive, so
a gate cannot run in both loops. The real cause is two omissions at the POST-step call
site, both dormant until [ADR-0013](20260824-1630-ADR-0013.md) moved `human` into it:

| | PRE-step loop (:2733) | POST-step loop (:2938) |
|---|---|---|
| `inline_gated=` | present since the 13-review fix | **absent** — WR-02 dedupe key missing |
| `cancel` arm | present since the 13-review fix | **absent** — WR-03 rejection ignored |

Without `inline_gated`, an inline-gated step opened the SAME review on the SAME `gate_key`
twice — once via `_should_gate` -> `_run_review_gate` inside `_run_agent`, once via the
declared gate. Without the `cancel` arm, a Reject yielded its gate event and fell through:
downstream steps kept executing and the run terminated as a completion with the state
machine stranded in `waiting_for_user`.

Baseline proof of attribution: at be1533e11 with the fix reverted,
`test_declared_gate_streaming.py` fails 3/3 with exactly the signatures listed above; with
the fix, 3 passed.

### Two stale tests repaired, and a third latent defect exposed

- `test_raising_hitl_gate_blocks_and_stops_gate_evaluation` paired `["human", "security"]`
  at `phase="pre"`. After ADR-0013 those sit in DIFFERENT phases, so `human` was filtered
  out and `security` answered alone — its `gate_blocked` event plus the WR-04 terminal
  sentinel giving `["block","block"]`. Two outcomes from ONE gate, which reads like a
  double evaluation but is not. Re-paired with `validation` (both post-step, validator
  registered to block) so the short-circuit is exercised again.
- `test_engine_sentinel_carries_human_gate_edit_detail` needed `phase="post"`; what it
  pins is phase-agnostic, only the label was stale.
- Once the dedupe removed the duplicate, `test_declared_human_gate_streams_ready_before_approval_and_resumes`
  ran further and died on `RuntimeError: coroutine raised StopIteration`. Its
  post-conditions did `gate_key.split(":", 1)[1]`, but `gate_key` is
  `f"{run}:{agent_id}:{visit_count}"` — THREE parts (the trailing count is ISS-052's
  per-firing discriminator). It looked up `"prototype-specify:0"` and matched nothing. The
  format did not change on this branch; the parse was always wrong and merely unreachable.
  Fixed with `rsplit` (a composed custom-agent id carries its own interior colon) and both
  bare `next()` calls given defaults so a future miss names the agent.

### Blast radius — 6 steps, two disjoint halves

`gates:[human]` is declared in exactly 3 manifests. Cross-referenced against which agents
carry `gate: Human_Gate` in AGENT.md (what `_should_gate` reads):

| step | inline? | which half bites |
|---|---|---|
| prototype / prototype-specify | yes | dedupe |
| prototype / prototype-plan | yes | dedupe |
| prototype / prototype-analyze | yes | dedupe |
| prototype_feature_revision / prototype-plan | yes | dedupe |
| prototype_feature_revision / …-feature-specify | no | cancel arm |
| sc001-test-fixture / sc001-fixture-analyze | no | cancel arm |

No overlap, full coverage. `gate_agent_ids` on the launch payload can move steps between
the columns at runtime; behaviour is correct either way. `security` and `approval` have
ZERO declarations anywhere, so the fail-closed gates are untouched.
