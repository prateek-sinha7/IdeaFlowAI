## Related

Found while verifying the `dev` merge. Six failures share one signature — a gate
evaluating twice:

```
test_gates                    assert ['block','block'] == ['block']
test_gates                    assert 'pass' in []
test_declared_gate_streaming  duplicate review_gate_ready for already-approved
test_declared_gate_streaming  expected exactly one review_gate_ready per gated agent
test_declared_gate_streaming  test_declared_gate_rejection_cancels_the_run
test_restart_resume           WR-03 regressed: rejection must end the run
```

## Why it is suspicious

None of those files were touched by EITHER side of the merge. The prime suspect is this
branch's own HITL split ([ADR-0013](20260824-1630-ADR-0013.md)): `_POST_STEP_GATES` now
contains `"human"`, and `human` / `before-human` are registered on one `HumanGate` class
under two names. A gate evaluating in both the pre- and post-step loop would look exactly
like this.

## Why it is still OPEN rather than assigned

No full backend suite was ever run on `c9ec0149c`, so "did the merge cause this" is
currently unanswerable. 33 other failures looked merge-caused and were traced and PROVEN
pre-existing, so the prior favours pre-existing — but that is a prior, not evidence.

**To settle it:** `git worktree add /tmp/premerge c9ec0149c`, run
`pytest tests/agents tests/unit tests/integration`, diff the failure sets. Two collection
blockers must be patched in the worktree first or pytest aborts and runs nothing — see
`specs/015-frontend-routing/post-merge-backlog.md` §1.1.
