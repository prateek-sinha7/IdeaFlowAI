## What was wrong

`alembic check` against a database built from the migration chain reported a
pending operation:

```
AutogenerateDiffsDetected: New upgrade operations detected:
  [('remove_index', Index('uq_workflow_runs_share_token',
     Column('share_token', VARCHAR(), table=<workflow_runs>), unique=True))]
```

**`remove_index`, not `add_index` — the direction matters and the register
entry had it backwards.** The migration is not the half that is missing.
`backend/alembic/versions/0040_workflow_run_share_token.py:44-51` *does*
create the index, as a sparse unique index with a
`share_token IS NOT NULL` WHERE clause on both SQLite and Postgres. What
never existed was the **model** declaration: `WorkflowRun.__table_args__`
(`backend/app/models/workflow.py:17-23`) listed only
`ix_workflow_runs_parent` and `ix_workflow_runs_user_created`.

So `Base.metadata` did not know about an index that every deployed database
has, and autogenerate — whose job is to make the DB match the metadata —
correctly proposed dropping it. Anyone who ran
`alembic revision --autogenerate` and committed the output would have
deleted the index that keeps `GET /s/{token}` an O(log n) lookup instead of
a full scan of `workflow_runs`.

## Root cause

`backend/app/models/workflow.py:132` — `share_token` was added to the model
as a bare `Column(String, nullable=True)` when migration 0040 landed. The
file already carries the correct pattern one field group up: the KAN-131
index for migration 0030 is declared in `__table_args__` with the comment
*"Declared here so `alembic check` / test_alembic.py see the model and the
migration agree."* 0040 simply did not follow it.

## What changed and why there

`backend/app/models/workflow.py` only — a third `Index(...)` entry in
`WorkflowRun.__table_args__`, mirroring migration 0040 exactly including
both dialect WHERE clauses, plus `text` added to the existing
`from sqlalchemy import ...` line to express them.

**No migration was added or altered.** A new migration would be the wrong
fix twice over: the index already exists in every database built from the
chain, so creating it again is a no-op at best and an error at worst, and
dropping it (the other direction autogenerate offered) would remove a
load-bearing lookup index. The model was the side that was wrong, so the
model is where the change belongs — `__table_args__` is the single place
every consumer routes through, both `alembic check` (via `Base.metadata`)
and the ~20 test fixtures that build their schema with
`Base.metadata.create_all`.
