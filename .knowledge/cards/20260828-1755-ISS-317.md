# ISS-317

**Register source:** `BUG-20260828-085400-runs-failed` in `bug-hunter/ledger.md`.

## Reproduction (validated 3/3, cold starts)

Route: `http://localhost:3000/runs/d6e425b6-df0d-4f54-9bba-f4a771e33812` (seeded
"Ppt V2" run, terminal state; observed as `failed` at report time, drifted to
`cancelled` under concurrent bug-hunt traffic by validation time — the mechanism
is identical for either terminal-with-errored-agents entry state, see Conditions
below). Account: qa-admin. Each cycle from a fresh `page.goto` to the run detail
route (not a soft re-click), the resume button clicked (`Reopen & fix from the
failed step` when the run showed `failed`; `Run Again` when it showed `cancelled`
— both wire to the same `handleResumeRun`, confirmed by [ISS-236](20260828-1740-ISS-236.md)),
then the Steps tab observed while the run was confirmed `generating` via
`GET /api/runs/{id}`.

- **Cycle 1:** cold load → Run Again → confirmed `status: "generating"` via API →
  header showed "Running", sub-header showed "Deck Engineer Agent · streaming",
  agent chips in the pipeline strip advanced (Presentation Strategist Agent done,
  Deck Engineer Agent "Starting…" then streaming) → Steps tab status summary
  showed **"Run failed · 1 / 4 agents · 3s"** the entire time, unchanged after
  ~10s of confirmed live progress. Reproduced.
- **Cycle 2:** navigated back to `/dashboard`, cold `page.goto` to the run route
  again, clicked Run Again → identical: header "Running", Steps panel "Run
  failed · 1 / 4 agents". Reproduced.
- **Cycle 3:** same cold-start protocol a third time → identical result.
  Reproduced.

Deterministic — no axis variation needed to trigger it; it fires on every resume
of this run regardless of whether the previous terminal state was `failed` or
`cancelled`.

Each cycle's run was stopped via the "Stop" control afterward to return the
fixture to a terminal state for the next cycle, not left abandoned.

## Root cause

`frontend/src/components/results/StepsOverviewSpine.tsx:365-367`:

```ts
const isRunning = pipelineState?.isRunning ?? false;
const failed = pipelineState?.failed || agents.some(a => a.status === "error");
...
const statusLabel = failed ? "Run failed" : isRunning ? "Running" : "Run complete";
```

`statusLabel` checks `failed` **before** `isRunning`, and `failed` is true if
*any* agent in the `agents` array currently has `status === "error"` — not
scoped to the current live attempt. When a run is reopened/resumed, the agents
that errored in the previous (pre-resume) attempt are not reset to `idle`
before the new attempt's events start arriving; their `status` stays `"error"`
in the array `StepsOverviewSpine` receives via `AgentThinkingTab`
(`frontend/src/components/results/AgentThinkingTab.tsx:283,291-292`). So even
though `pipelineState.isRunning` is `true` and the header/sub-header correctly
read live stream state, this one label keeps evaluating `agents.some(a =>
a.status === "error")` to `true` off the stale pre-resume agents and never
falls through to the `isRunning` branch.

## Expected vs actual

- **Expected:** while a run is actively `generating` (confirmed by
  `pipelineState.isRunning` / the API), the Steps panel status summary reads a
  state consistent with "Running", matching the header badge and the streaming
  sub-header rendered on the same screen.
- **Actual:** the summary is pinned on "Run failed" (with a stale `1 / 4 agents
  · 3s` count) for the run's entire live-progress duration, because the
  `failed` boolean is computed from leftover per-agent error status from before
  the resume rather than being cleared or gated by `isRunning`.

## Conditions

- Route: `/runs/{id}` → resume button → `/runs/{id}/stream`.
- Component: `StepsOverviewSpine` (Steps tab, `tab-thinking`), fed by
  `AgentThinkingTab`.
- Trigger: resuming *any* run whose `agents` array already contains an entry
  with `status === "error"` from a prior attempt — reachable via both the
  failed-run "Reopen & fix from the failed step" button and the cancelled-run
  "Run Again" button (both call `handleResumeRun`).
- Tier: qa-admin, default theme/viewport — not tier/theme/viewport dependent;
  the defect is data-shape dependent (stale agent error status), not
  environment dependent.

## Fix direction

Gate `failed` (or reorder the `statusLabel` ternary) so a currently-`isRunning`
pipeline never shows "Run failed" regardless of leftover per-agent error status
— e.g. `const failed = !isRunning && (pipelineState?.failed || agents.some(a =>
a.status === "error"))`, or reset stale `error` statuses to `idle` on the
agents that will re-run when a resume is initiated (same seam as
[ISS-236](20260828-1740-ISS-236.md)'s `handleResumeRun`).
