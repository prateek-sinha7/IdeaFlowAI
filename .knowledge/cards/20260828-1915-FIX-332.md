# FIX-332

Register source: `BUG-20260828-034200-handoff-settings` in `bug-hunter/ledger.md`.

## What was wrong

Submitting a >512-character GitHub PAT on `/handoff/settings` produced a `422`
whose body contained the **complete submitted string**, and the page rendered
that whole raw JSON blob — secret included — as visible text under the PAT
field, directly contradicting the card's own "Encrypted at rest, never returned
by any API."

Two independent defects compounded, and each had siblings the reported path did
not name:

1. **Backend** — `backend/app/main.py` registered no `RequestValidationError`
   handler, so FastAPI's default 422 handler serialised Pydantic's error shape
   verbatim, and that shape carries `input`: the entire rejected value. Not a
   property of `settings.py:64` (`GithubPATRequest.pat`) — a property of the
   app, so every length/pattern-constrained field on all 20 routers inherited
   it, including `RegisterRequest.password` (`app/models/schemas.py:16`,
   [ISS-257](20260828-1817-ISS-257.md)).
2. **Frontend** — the same "only a plain-string `detail` gets a friendly
   message, everything else is `JSON.stringify`" idiom was written **twice**,
   independently: `authedJson` (`frontend/src/lib/api-handoff.ts:86-88`,
   `/handoff/settings`' shared error path — [ISS-264](20260828-1815-ISS-264.md)
   reaches it through `createApiKey`) and `ApiError`'s constructor
   (`frontend/src/lib/api.ts:77-79`, the client every non-handoff page uses via
   `request()` — [ISS-256](20260828-1816-ISS-256.md)). FastAPI always sends a
   **list** for a 422 `detail`, so both fell straight through to the raw dump.

Confirmed empirically that this cannot be fixed at the model layer: a
`SecretStr` field failing `min_length` still reports
`{'type': 'too_short', ..., 'input': 'short7!'}` — Pydantic does not redact it.

## What changed and why there

- `backend/app/main.py` (after the request-id middleware, before the routers) —
  one `@app.exception_handler(RequestValidationError)` that rebuilds each error
  entry without `input` and returns the otherwise-identical body. One guard
  where every route's validation failure already converges, rather than a
  per-field or per-router redaction that the next constrained field would miss.
  `loc`/`msg`/`type`/`ctx` are untouched, so the 422 still says exactly what was
  wrong and where.
- `frontend/src/lib/api.ts` — new exported `errorMessageFromDetail(detail)`:
  string `detail` passes through unchanged; a **list** `detail` becomes its
  `msg` fields joined; anything else returns `null` so the caller keeps its
  existing fallback (object-shaped `detail` from `run_commands.py` / `admin.py`
  behaves exactly as before). `ApiError`'s constructor now calls it.
- `frontend/src/lib/api-handoff.ts` — `authedJson` calls the same function
  (`api-handoff.ts` already imported from `@/lib/api`), so the duplicate
  [ISS-256](20260828-1816-ISS-256.md) names is now one function with two
  callers rather than two copies of one bug.

Not changed: no `maxLength` was added to the PAT or key-name inputs — no card
asks for it, and a client-side cap would only hide the server-side leak.
