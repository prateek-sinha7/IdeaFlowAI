# ISS-1121

**Register source:** sibling derived during the `QA-KB-102` analysis on 2026-10-08 (root [ISS-1103](20261008-0016-ISS-1103.md)). Not its own bug row.

**Confidence:** CONFIRMED by source read: every reference to `runRestarting` in `frontend/src` was enumerated by grep (below). Not driven in a browser and not covered by a vitest render. What would settle the render: mount `RunChatLane` with `runLaneState` terminal, `runRestarting` true, and a stream that delivers no `pipeline_start`.

## Condition

The owner clicks "Reopen & fix" (failed run) or "Run Again" (cancelled run). `handleResumeRun` (`DashboardLayout.tsx:2534-2592`) sets `runRestarting` true (`:2550`), POSTs `/resume`, and on a 200 attaches the stream (`:2553-2555`). The attempt then ends without a `pipeline_start`: every path of [ISS-1103](20261008-0016-ISS-1103.md), whether the backend sends no frame (today) or, after the root fix, sends a `pipeline_failed` with no `pipeline_start` before it.

## Expected vs actual

Expected: the lane returns to its terminal view with the reason and the button, so the owner can retry or give up.

Actual: the lane stays on an animated "Restarting run…" for as long as the page lives.

- `runRestarting` is local state (`useState(false)`, `DashboardLayout.tsx:661`).
- It is set at `:2550`. It is cleared in exactly two places: the effect at `:1148-1154`, which fires when `isPipelineRunning` becomes true (that is `pipelineState.isRunning`, set by `pipeline_start` and the agent frames), and the POST error branch at `:2589`, which a 200 never reaches. No timeout, no other effect.
- `RunChatLane.tsx:1726-1747`: in the `terminal` case, `if (runRestarting) { return <... Restarting run…> }` comes before every failed, cancelled and degraded branch, so the terminal copy, the reason and the `chat-relaunch` button are all hidden.
- Nothing on the stream clears it: `stream_attached` is early-returned (`app/[...view]/page.tsx:1170-1177`) and no non-test file in `frontend/src` handles `run_resuming`.
- The stream itself closes quietly. A live attach that ends on the sentinel is treated as a drop and reconnects once (`useRunStream.ts:418-430`); the reconnect is a non-live attach and settles. The owner sees at most a flash of "Connection lost. Reconnecting…".
- A reload clears it (the state is not persisted) and shows the same terminal run with the same button.

The FE was written on the assumption that a resume always starts: `RunConnectionProvider.tsx:77-89` describes "the `pipeline_failed` a fast-failing resume emits ~3-5s later", i.e. after `pipeline_start`.

## Why the root cause implies it

The backend fix of [ISS-1103](20261008-0016-ISS-1103.md) delivers a `pipeline_failed` with no preceding `pipeline_start`. The effect at `:1148` keys only on `isRunning`, so the frame lands on a lane that never leaves "Restarting run…". Fixing the backend alone does not tell the user.

## Fix direction (INFERRED, not applied)

Clear `runRestarting` when a terminal frame newer than the click arrives, not only on `isRunning`. The terminal flags (`failed`, `cancelled`, `degraded`) are already true at click time, so the condition cannot be "failed is true": it needs the cursor or seq at click, or a new-terminal marker. The choice is the fixer's. The red test is a vitest render of `DashboardLayout` or `RunChatLane`: click, POST resolves, stream delivers `pipeline_failed` with no `pipeline_start`, expect the indicator gone and the failure copy and button back.

## Resolution (5-fixer, QA-KB-102, 2026-10-08)

Resolved by [FIX-768](20261008-1540-FIX-768.md). `DashboardLayout` keeps the `agents` array the click saw and clears `runRestarting` once the run is not running and `agents` has changed. The terminal reducer cases rebuild `agents`; `workflow_validated`, the one frame a starting resume sends before `pipeline_start`, does not. `RunChatLane.tsx` is unchanged.
