# ISS-418

## Title

Every KPI tile, daily chart, and per-pipeline/per-model breakdown on the Analytics page
undercounts real token/cost spend for any run that invoked the SmartPlanner, a clarify
one-shot, or the validation fix-loop sub-agent — the SAME root cause [ISS-304](20260828-1600-ISS-304.md)
found, observed from the opposite side: not "the header shows too MUCH", but "the aggregate
shows too LITTLE", because Analytics is wired to the number that structurally EXCLUDES that
spend, system-wide, not just on the one run the hunter checked.

## Mechanism (CONFIRMED by code read; NOT independently re-reproduced live this session)

`backend/app/api/analytics.py:188-195` builds every run-level total from the persisted column:

```python
for r in runs:
    usage = _parse_token_usage(r.token_usage)
    r_in = int(_num(usage.get("total_input_tokens")))
    r_out = int(_num(usage.get("total_output_tokens")))
    r_total = int(_num(usage.get("total_tokens"))) or (r_in + r_out)
```

`r.token_usage` is written solely by `_apply_terminal_output_columns`
(`backend/app/api/run_commands.py:2953-2977`, "the SOLE writer of these columns" per its own
docstring, shared by launch/both-resume-paths/revision). Per [ISS-304](20260828-1600-ISS-304.md)'s
root-cause read, that function's `pipeline_complete` branch (`run_commands.py:3042-3045`) reads
only `final_output`/`deliverable_mimetype`/`deliverable_filename` off the event and ignores its
own `total_input_tokens`/`total_output_tokens`/`total_tokens` fields; a few lines later
(`run_commands.py:3057-3065`) it independently re-derives the persisted totals by re-summing
`agent_outputs_collector` — i.e. `agent_complete` events only. The engine's live/replayed
`pipeline_complete` event (`backend/agents/execution_engine/engine.py:3712-3757`) additionally
folds in `aux_token_usage` — tokens from the SmartPlanner (`usage_sink=aux_token_usage.append`
at `engine.py:2122`), a clarify one-shot (`engine.py:2265`), and the validation fix-loop
sub-agent (`engine.py:2443`) — none of which ever appear in `agent_outputs_collector`, since
none of them fire an `agent_complete` event. That aux spend is real (ISS-033's own comment says
it exists precisely "so their tokens are COUNTED in the run totals instead of being silently
dropped") but it only reaches the LIVE/replayed SSE event, never the persisted `token_usage`
column Analytics reads.

On the confirmed run `a0693fcd-...`: `token_usage.total_tokens` = 10,428;
`pipeline_complete.total_tokens` = 17,931 — a ~7,503-token gap that Analytics' KPI
tiles/daily/per-pipeline/per-model breakdowns never see, for THIS run and every other run whose
pipeline used the planner, a clarify round, or the fix-loop.

**What would confirm this as a live symptom** (not done this session — scope was the reported
run-detail bug): sum `pipeline_complete.total_tokens` across a sample of completed runs from
their durable event logs and compare against the same runs' Analytics contribution; the
Analytics total should read lower by the aggregate aux-token gap.

## Expected vs Actual

- Expected: Analytics' token/cost figures for a run equal the run's actual total spend,
  including planner/clarify/validation-fix-loop tokens.
- Actual (inferred, unverified): Analytics reads `token_usage`, which structurally excludes
  that spend — the same data gap ISS-304 found, in the opposite direction (undercounts
  aggregates rather than overstating one header).

## Fix

Same fix location as [ISS-304](20260828-1600-ISS-304.md): `_apply_terminal_output_columns`
(`backend/app/api/run_commands.py`) is the single funnel `token_usage` is written through for
every completion path. Whatever direction ISS-304's fix takes (fold aux costs into the
persisted total, or strip them from the live event), doing it there — rather than patching
Analytics separately — is what keeps Analytics, the Run History card, `GET /api/runs/{id}`, and
the frontend's `pipeline_complete`-driven state all reading the same number.
