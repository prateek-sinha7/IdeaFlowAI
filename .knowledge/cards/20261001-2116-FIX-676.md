## What was wrong

Bug report QA-KB-040. Four tests in the wave-worker stack were red, in two files, for two different
reasons. In both files the application was right and the test expectation was stale. Both verdicts
come from the analysis and test phases and were not re-derived here:

- [ISS-863](20260929-1021-ISS-863.md), the root card. `useWorkflow.waveWorkers.test.ts:37` and `:52` (pre-change lines)
  asserted a reducer-built wave-worker row with `toEqual`. The row carries one defined key the test
  never listed: `startedAt: prior?.startedAt ?? Date.now()` at `frontend/src/hooks/useWorkflow.ts:536`,
  added on purpose by `05b7bce54` (2026-09-10) after the test was written. `toEqual` ignores the 24
  `undefined` keys of the 30-key row, so the "30 properties" in the report are a red herring; the
  clock value alone fails the match.
- [ISS-866](20261001-2105-ISS-866.md), the sibling. `AgentDetailPanel.waveWorkerStatus.test.tsx:288`
  and `:328` (pre-change lines) expected the label "Full input prompt" on a wave member page. The fixtures model a
  file-based member (`contextSources: [{ type: "run_input", ... }]`, no `systemPrompt`, at `:277` and
  `:317`), so `contextIsFileBased` is true (`AgentDetailPanel.tsx:1562-1565`) and
  `AgentDetailPanel.tsx:524` labels the section "Task message", as Req 13 AC 9 intends
  (comment at `:500-504`). The test came from `05b7bce54`, the label from `e7305f9dd` on a parallel
  line of history; the contradiction appeared when the two merged.

## What changed, and why there

Test files only. No application file was touched, and no assertion was loosened beyond what the cards
prescribed.

1. `frontend/src/hooks/useWorkflow.waveWorkers.test.ts`: `.toEqual([` became `.toMatchObject([` at the
   two row assertions (now `:39` and `:55`), with an ISS-863 comment above each. The expected objects keep all five fields
   (`taskId`, `status`, `workerIndex`, `waveIndex`, `waveTotal`). `toMatchObject` on an array still
   enforces the array length and every listed value (the analyzer's experiment,
   `evidence/qa-kb-040/04-analyze-matcher-experiment-output.txt`). It just stops pinning a clock value
   these nesting tests are not about.
2. `frontend/src/components/results/AgentDetailPanel.waveWorkerStatus.test.tsx`: "Full input prompt"
   became "Task message" in both tests (now `:290` and `:332`), with an ISS-866 comment above each. The new assertion is just as
   strong as the old one. Outside comments, the text "Task message" is rendered only by
   `InputPromptSection` (`AgentDetailPanel.tsx:524` label, `:565` secondary header), and that component
   is mounted only at `:1559`. So a page without its input section still fails. The other fix the card
   offered was to give the fixture a `systemPrompt`. It was not taken because it would change what the
   fixture models (a file-based member) and move the test onto the "System prompt" path. The test's own
   header says a member page is the step page. A step with this data says "Task message", so the member
   must too.

There is no shared function to guard. ISS-863's blast radius has no production caller and no other
whole-row equality assertion. ISS-866 has no other expectation of "Full input prompt" on a file-based page.
