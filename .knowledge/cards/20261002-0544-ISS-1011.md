# ISS-1011

Sibling of [ISS-895](20261001-2126-ISS-895.md) (QA-KB-069). Confidence: **CONFIRMED**. Every number below comes from a run the analyzer observed on 2026-10-02 in this tree; nothing was inferred.

## What is broken

[ISS-895](20261001-2126-ISS-895.md) is a test whose `vi.mock("@/lib/api", () => ({ ... }))` factory is a closed set, while production code on a mounted component reads an export the set does not contain. This is the same flaw with a different export, in three more files. The blast-radius sweep for ISS-895 found it.

| test file | factory | result (vitest 4.1.11) |
|---|---|---|
| `frontend/src/components/preview/PreviewPanel.revisionChip.test.tsx` | `:20-24` | `Tests 2 passed (2)`, `Errors 2 errors`, **exit code 1** |
| `frontend/src/components/preview/PreviewPanel.test.tsx` | `:21-47` | `Tests 1 failed \| 18 passed (19)`, `Errors 8 errors`, exit 1 |
| `frontend/src/components/preview/PreviewPanel.versionChip.test.tsx` | `:19-23` | `Tests 5 failed (5)`, `Errors 5 errors`, exit 1 |

Each prints `Error: [vitest] No "getRunSandboxRefs" export is defined on the "@/lib/api" mock` under "Unhandled Rejection", with the stack frame `src/components/preview/RunHeader.tsx:308:43`. `PreviewPanel.revisionChip` is the sharp case: both its tests pass, and the file still exits 1.

## Mechanism (confirmed by reading `RunHeader.tsx`)

- `RunHeader.tsx:308` is `import("@/lib/api").then(({ getToken, getRunSandboxRefs }) => {`. The destructuring reads `getRunSandboxRefs` off the module namespace. A closed factory mock answers a read of an undefined export with a throw.
- That throw happens inside the `.then` callback, so it rejects the promise `.then` returns. The only `.catch` is at `:313`, and it hangs off the inner `getRunSandboxRefs(token, activeRunId)` chain. Nothing is attached to the outer chain at `:308-314`, so the rejection is unhandled. vitest records an unhandled rejection as an error and turns it into a non-zero exit even when every test case passes.
- The comment at `RunHeader.tsx:301-303` says the opposite: "a caller whose @/lib/api test mock omits getRunSandboxRefs gets a swallowed rejection here rather than a thrown, test-failing render-effect error." The code does not swallow it. `git blame -L 306,316` attributes every line of the effect to `e4eecb705` (2026-09-12, "one version selector for the whole run", task U1).
- `getRunSandboxRefs` is defined at `frontend/src/lib/api.ts:1720` and has exactly one non-test consumer, `RunHeader.tsx:308-311` (grep over `frontend/src`).

## Why the root cause of ISS-895 implies it

ISS-895's mechanism is: a closed `@/lib/api` factory plus a production read of an export it lacks. The only thing that differs here is the export and the date. The `RunHeader` effect landed on 2026-09-12, ten days before `getCapabilities` landed in `AgentDetailPanel`, so this hole is older than the one in ISS-895. The sweep of every test that mocks `@/lib/api` (108 files, each run alone) found the missing-export signature in exactly four files: `AgentDetailPanel.artifactVersions.test.tsx` (`getCapabilities`, ISS-895) and the three above (`getRunSandboxRefs`). A sweep only sees holes on code paths a test actually exercises, so this is a floor, not a ceiling.

## Expected vs actual

- Expected: a test file whose assertions pass exits 0 and prints no `Errors` line.
- Actual: all three files report unhandled rejections (2 + 8 + 5) and exit 1. `PreviewPanel.revisionChip` reads as green in the summary line and fails the run. The `frontend-vitest` job (`.github/workflows/ci.yml:634-676`) runs `npx vitest --run --coverage ...` directly under `set -euo pipefail` with no `|| true`, so a non-zero exit from the run fails that step.

## Experiment: how much of the red is this card

Scratch copies of the three files, outside the repo tree (alias imports, same vitest config otherwise). Each factory got `getRunSandboxRefs: async () => [],`. A second variant returned `["v1","v2","v3"]`.

| file | control (unpatched copy) | with the export |
|---|---|---|
| `PreviewPanel.revisionChip` | `2 passed`, `Errors 2 errors`, exit 1 | `Tests 2 passed (2)`, no Errors, **exit 0** |
| `PreviewPanel.versionChip` | `5 failed`, `Errors 5 errors` | `Tests 5 failed (5)`, no Errors |
| `PreviewPanel.test` | `1 failed \| 18 passed`, `Errors 8 errors` | `Tests 1 failed \| 18 passed (19)`, no Errors |

So the mock hole is the whole defect only for `PreviewPanel.revisionChip`. In the other two files the same 5 and 1 assertions fail with or without the export, which is a second, independent defect: [ISS-1012](20261002-0544-ISS-1012.md). A fixer who adds the export and expects those two files to go green will be wrong.

## Proposed fix (not applied)

Pick one place; no product decision is involved.

1. **Production, one line (recommended).** Append `.catch(() => {})` to the outer chain at `RunHeader.tsx:314` so the promise chain has a terminal handler, which makes the comment at `:301-303` true. One line instead of three, and it also covers any future closed-factory test that mounts `RunHeader`. Trade-offs: it hides future mock holes in this one effect, tags stay `[]` so the static chip renders, and a test that wants the interactive `VersionMenu` must still supply tags (it mounts only when `tags.length > 0`, `RunHeader.tsx:426`). This changes a non-test file, so the reviewer should check the direction: the app is being aligned to its own written contract, not bent to a test.
2. **Tests, three lines.** Add `getRunSandboxRefs: async () => [],` to the three factories, the same shape as the ISS-895 fix. Zero production risk. If chosen, edit or delete the false comment at `RunHeader.tsx:301-303`.

Either way, the success check is `cd frontend && npx vitest run src/components/preview/PreviewPanel.revisionChip.test.tsx` giving `Tests 2 passed (2)`, no `Errors` line, exit 0, and the other two files losing their `Errors` lines.
