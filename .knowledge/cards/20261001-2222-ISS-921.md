## Sibling of ISS-372 (INFERRED: read from code, not reproduced in a browser)

Found while analysing QA-KB-015 ([ISS-372](20260828-2141-ISS-372.md): AccountSettings never
reports unsaved work to the shared Back guard). AccountSettings holds three kinds of
typed-but-unsaved input: the password fields, the model pick and the Constitution draft.
ISS-372 names the first two. [ISS-482](20260828-2322-ISS-482.md) says in terms that ISS-372
"does not mention or cover the Constitution draft", and fixes only the TAB-SWITCH exit
([FIX-386](20260831-1020-FIX-386.md)). The third exit, the Back button, is covered by neither
card, which is why it is filed on its own instead of being folded into ISS-372's scope.

## What I read (CONFIRMED, files unmodified against HEAD on 2026-10-01)

- The draft is parent state: `constitutionContent` / `constitutionLoadedValue`
  (`frontend/src/components/settings/AccountSettings.tsx:110-111`), written by
  `ConstitutionSection` through `setContent` / `setLoadedValue` (`:500-506`). The textarea
  stores the raw text (`:713`), the cap is 4000 characters (`:571`), and the section is mounted
  only while the Constitution tab is open. It is the longest and least reproducible input on
  the page.
- The only reader of the dirty comparison is the tab-switch guard (`:249-256`,
  `constitutionContent !== constitutionLoadedValue`). The Back button (`:232-237`) is
  `onClick={onBack}` and signals nothing to `DashboardLayout` (root cause as in ISS-372:
  `AccountSettings.tsx:30-47,87`; `DashboardLayout.tsx:3117`).
- Nothing persists the draft elsewhere: no autosave (`handleSave` runs only on the Save click)
  and no `beforeunload` handler anywhere in `frontend/src`. Back unmounts AccountSettings and
  the draft is gone.

## What is inferred

That the user sees the draft vanish. What would settle it: open `/settings/constitution`, type
into `textarea[name="constitution"]` without saving, click the header Back button (no
`[role=dialog]` appears, as in the validated ISS-372 reproduction), then reopen the tab; the
editor shows the last saved value. Every step of the mechanism was read; the outcome was not
observed.

## Why the root cause implies it

Same root as ISS-372: an AccountSettings that emits no `onUnsavedChange` leaves every dirty
source unguarded on Back. The Constitution draft is a source the product already treats as
worth a confirmation (the ISS-482 tab guard at `AccountSettings.tsx:249-256`), so Back is the
one exit that skips it.

## Expected vs actual

**Expected:** Back while `constitutionContent` differs from what was last loaded or saved opens
the shared "Leave without saving?" dialog (`DashboardLayout.tsx:3478-3517`).

**Actual (inferred):** navigates away at once and discards the draft.

## Where the fix belongs, and two traps

The same edit as ISS-372: one more term in the `dirty` expression that feeds
`onUnsavedChange`. It must land WITH ISS-372, or the guard has a hole in the highest-value
input on the page. Do not copy the tab guard's comparison unchanged. It has two flaws that a
Back guard would inherit as false prompts:

1. After a successful Save. `handleSave` stores `content.trim()` as `constitutionLoadedValue`
   (`:633`) but leaves `constitutionContent` untrimmed (`:713`), so a draft with leading or
   trailing whitespace still reads as dirty after Save. The tab guard already misfires on it.
   Define a single `constitutionDirty` that compares trimmed values and use it in both places.
2. After "Discard". `commitDiscardConstitution` (`:121-126`) switches the tab but leaves the
   discarded draft in `constitutionContent`, so Back would then ask about a draft the user
   already threw away. Reset it there: `setConstitutionContent(constitutionLoadedValue)`.

Neither trap is reproduced; both are read from the lines cited. The e2e test for the tab guard
(`tests/integration/e2e/suites/09_settings/test_settings.py:559`) exercises the Cancel path
only, so the Discard path has no test at all.
