# BUG-008 + BUG-011 — grounded fix spec (FE run-screen viewed-run binding, continued)

> Two frontend fixes, both the "run-screen state not bound to the viewed run / not run-scoped" class (same family as BUG-001/005/006). Root-caused to file:line by investigation agents. Full detail: `.planning/SSE-QA-BUG-LOG.md` → BUG-008 / BUG-011 (READ THEM). Executable spec for a `gsd-quick --validate`. Frontend-only.

## BUG-008 🟠 — reopened generic/custom deliverable renders empty (a 4th stale-`workflowType` consumer)
- **Cause:** on a terminal reopen, `PreviewPanel.tsx:579` `hasContent` is starved because `hasGenericDeliverable` (`:577`) = `!isKnownRenderType && !!genericDeliverable?.content`, and `isKnownRenderType` comes from `detectedType ← workflowType` (`:536`) — which is the **stale `"user_stories"`** default (the binder at `DashboardLayout.tsx:330-346` is `isRunning`-gated, never fires for a terminal reopen). So `isKnownRenderType=true` → `hasGenericDeliverable=false` → the Preview short-circuits to "Output will appear here" (`:1016-1019`) and never calls `renderDeliverable()` (whose step-2 `:890` would render the HTML in the P18 sandboxed iframe). The data IS loaded + passed (`page.tsx:1311-1318` seeds `genericDeliverable`) — it's a dispatch/gate gap, not a data gap.
- **Fix (PREFERRED — decouple the signal from the stale `workflowType`):** `frontend/src/components/preview/PreviewPanel.tsx:577`
  ```
  // before:
  const hasGenericDeliverable = !isKnownRenderType && !!genericDeliverable?.content;
  // after:
  const knownContentPresent = !!(effUserStoryContent || effPptContent || effPrototypeContent || pptxCode);
  const hasGenericDeliverable = !!genericDeliverable?.content && (!isKnownRenderType || !knownContentPresent);
  ```
  A present generic deliverable renders whenever the typed renderer for the (possibly-stale) `renderType` has nothing to show. No live/first-party regression (typed content → `knownContentPresent=true` + `isKnownRenderType=true` → `false`; live custom run → `isKnownRenderType=false` → unchanged); `renderDeliverable()`/`GenericDeliverablePreview` + the P18 `sandbox="allow-scripts"` (no `allow-same-origin`) contract untouched; robust to runs outside `recentRuns`. (Do NOT use the `workflowType={viewedRunType}` alternative alone — it has a recentRuns-membership gap.)

## BUG-011 🟡 — `pipeline_complete` not run-scoped: a background run completing hijacks the VIEWED content-source
- **Cause:** the page subscriber's `pipeline_complete` branch runs `setContentSourceRunId(data.pipeline_run_id)` (`frontend/src/app/dashboard/page.tsx:530`) with **no run-identity guard** — any attached run's completion re-points the viewed content-source. The BUG-005 fix run-scoped the `pipeline_start` reset via `trackedRunIdRef` (page.tsx ~:156/:941/:1489/:480-491); `pipeline_complete` was not covered.
- **Fix:** guard the `setContentSourceRunId` at `page.tsx:530` by the tracked run id — only re-point when the completing run IS the tracked/launched run, e.g. `if (data.pipeline_run_id === trackedRunIdRef.current) setContentSourceRunId(data.pipeline_run_id)` (reuse the existing `trackedRunIdRef` from the BUG-005 fix; verify its value at `pipeline_complete` time equals the launched/active run). **MUST preserve the launch flow:** when the run you launched/are-watching completes, it still becomes the content-source (the tracked ref == that run). Only a FOREIGN concurrent run's completion is ignored. Confirm the tracked ref is correct at complete-time (it's synced from `activePipelineRunId ?? contentSourceRunId` + set to the launched id) — if the launched run cleared `activePipelineRunId` on its own `pipeline_start`, ensure the ref still holds the launched id at completion (it's set at launch `:1489` and only re-set on a new launch), so the guard passes for the launched run's completion.
