## Why this must also be broken

[ISS-226](20260828-1550-ISS-226.md) root-caused `/create/ppt`'s "Save as my version" to
`handleSaveAsOverride` in `frontend/src/components/workflow/LaunchWizard.tsx:727-754` (confirmed
by independent re-read): it hardcodes `name`/`description` and calls
`buildWorkflowManifest(pipelineAgents, undefined, selectionsRef.current)` with no `capabilities`/
`runConfig` argument — so `selectedTemplateId`, `customTemplateBody`, `selectedDsId`,
`customDsBody`, and the brief text never reach the request body, even though the sibling
`handleLaunch` (lines 756-804) reads every one of those same pieces of state into
`buildLaunchDraft` at the moment of its own click.

That function is not `/create/ppt`-specific. `LaunchWizard` is a single component parameterized
by `mode: LaunchMode = "prototype" | "ppt" | "ppt_v2"` (`LaunchWizard.tsx:96-137`,
`MODE_CONFIG`), and `handleSaveAsOverride`'s only mode-dependent read is
`MODE_CONFIG[mode].savePipeline` (line 731, which pipeline id to bind the override to) and
`cfg.eyebrow` (line 734, cosmetic `name` prefix only) — every other line of the function,
including the `buildWorkflowManifest` call that omits template/brief/design-system, is identical
across all three modes. The "Save as my version" button itself (line 1090-1098) is rendered
unconditionally, not gated on `mode`.

All three modes are independently reachable at their own URL, confirmed via
`frontend/src/app/[...view]/page.tsx:287-302` (`wizardModeFor`: `create-ppt` -> `"ppt"`,
`create-prototype` -> `"prototype"`, `create-workflow` with `pipelineType === "ppt_v2"` ->
`"ppt_v2"`) and `frontend/src/lib/routes.ts:236-237,250` (`/create/ppt` ->
`{screen:"create-ppt"}`, `/create/prototype` -> `{screen:"create-prototype"}`, `/create/ppt_v2`
falls through the `mode` switch to `{screen:"create-workflow", pipelineType:"ppt_v2"}`), all
three rendering `<LaunchWizard initialMode={...}>` (`page.tsx:3759-3760`). `ppt_v2` is a real,
shipped pipeline (`ls backend/agents/workflows/` lists `ppt`, `ppt_revision`, `ppt_v2`), not a
placeholder id.

## Expected vs actual

**Expected:** "Save as my version" on `/create/prototype` and `/create/ppt_v2` persists the
user's actual on-screen configuration (brief, selected template, selected design system), the
same expectation [ISS-226](20260828-1550-ISS-226.md) states for `/create/ppt`.

**Actual (INFERRED — not yet independently reproduced per mode):** the same static-payload
symptom ISS-226 documented for ppt — hardcoded `description`, a `name` that only reflects
`cfg.eyebrow` (mode label) and never the brief/template, and a `manifest` with no template or
design-system id anywhere in it — should reproduce identically on `/create/prototype` and
`/create/ppt_v2`, since the broken function is the same one in the same file, not a per-mode
branch.

## What would confirm or refute this

Repeat ISS-226's exact reproduction (`bug-hunter/ledger.md` `BUG-20260828-052800-create-ppt-r2`,
steps 1-4) against `/create/prototype` (fill brief, pick a web template + design system) and
`/create/ppt_v2` (fill brief, pick a deck template) in turn: click "Save as my version", inspect
the `POST /api/user-workflows` request body. A miss on either (a payload that DOES vary with the
on-screen state) would mean that mode diverges from `ppt`'s code path in a way not accounted for
here and would refute this card for that mode specifically.

## Where the fix belongs

Same place as ISS-226: inside `handleSaveAsOverride` itself (or a small shared helper it and
`handleLaunch` both call), since all three modes share this one function — a guard or payload fix
placed there covers `/create/ppt`, `/create/prototype`, and `/create/ppt_v2` in one change, rather
than three per-mode patches. Any fix must also account for the fact that the current
`WorkflowManifest`/`WorkflowCapabilities` TypeScript contract
(`frontend/src/types/index.ts:563-648`) has no field for a template id, design-system id, or
brief text at all — only `steps`, `capabilities.internet`, `deliverable`, `planner`, `clarify` —
so threading `selectedTemplateId`/`selectedDsId` through to a persisted, reloadable override may
need a schema addition (frontend type + backend manifest/model), not just a values-are-available
plumbing fix. This is INFERRED scope, not confirmed against the backend compiler; the 5-fixer
should check `backend/agents/workflows/compiler.py` and the `user_workflows` manifest model
before committing to an approach.
