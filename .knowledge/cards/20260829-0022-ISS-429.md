## What happened (inferred from confirmed code, not yet reproduced against a ppt/prototype fixture)

[ISS-306](20260828-1745-ISS-306.md) confirmed two mechanisms on `/create/ex_A4_human_gate`
(served by `IdeaInputPage.tsx`) that make a seeded `before-human` gate invisible on a
completely fresh page load, zero interaction required:

- Mechanism A: `ReviewGatesSection.tsx:52,92-96,103-114` — `checkedIds` seeds only from
  `initialGateIds` or `isDefaultGated` (`agent.gate === "Human_Gate"`), never from the
  manifest's per-step `gates` array.
- Mechanism B: `CanvasConfigRail.tsx:730-734`'s "Prompt User" toggle requires
  `route?.condition_agent === prev.id`, but `normaliseRoute()` never normalizes
  `condition_agent` to the canvas node-id form `prev.id` uses, so the comparison is always
  false for any composed step using `condition_agent`.

Both mechanisms live in code shared by a SECOND caller, confirmed by direct read:

- `LaunchWizard.tsx:1072-1077` renders the identical `<ReviewGatesSection agents={pipelineAgents}
  onChange={handleGatesChange} selections={liveSelections}
  onSelectionsChange={handleSelectionsChange} />` — no `initialGateIds` passed at all, so
  `checkedIds` falls straight to `isDefaultGated`, exactly like the `IdeaInputPage.tsx` path
  Mechanism A describes.
- `LaunchWizard.tsx:415,422,460` builds `pipelineAgents` via the SHARED
  `agentsFromManifest()` (`frontend/src/lib/manifestAgents.ts:76-143`), whose `normaliseRoute()`
  (`:55-74`) has the identical `condition_agent`-not-normalized gap Mechanism B root-caused —
  this is the ACTUAL shared helper (not `IdeaInputPage.tsx`'s local duplicate), so any
  `/create/ppt` or `/create/prototype` step declaring both `gates: [before-human, ...]` and a
  `route.condition_agent` hits it identically.

This is a DIFFERENT symptom shape from [ISS-361](20260828-2120-ISS-361.md), which already
covers `LaunchWizard.tsx` for ISS-247's mechanism — but ISS-361 is framed entirely around a
USER ACTION ("checking an agent in the checklist... then viewing the Advanced modal"), the same
way ISS-247 itself required a checkbox click before the desync appeared. This card, mirroring
the distinction ISS-306 itself draws against ISS-247, requires NO interaction: a `/create/ppt`
or `/create/prototype` workflow whose manifest already declares a step's `before-human`/`human`
gate would misrepresent it in both controls the instant the page loads, before any checkbox is
ever clicked.

## Why the root cause implies this

ISS-306's own text states both mechanisms live in the shared component/helper the CALLER
renders, not in `IdeaInputPage.tsx`-specific glue: `ReviewGatesSection`'s seed logic and
`manifestAgents.ts`'s `normaliseRoute()` are identical code regardless of which page mounts
them. `LaunchWizard.tsx` mounts both unmodified (confirmed above), so a step reachable through
it with the same gate/route shape as `ex_A4_human_gate`'s `pick-language` step must fail
identically — there is no caller-specific patch in `LaunchWizard.tsx` that would make either
mechanism behave differently there.

## Expected vs actual (predicted)

Expected: a fresh `/create/ppt` or `/create/prototype` load of a workflow whose manifest
declares a step with `gates: [before-human, ...]` and a matching `route.condition_agent` should
surface that gate in the Review-gates checklist and/or the Prompt User toggle, with zero
interaction.

Actual (predicted, unverified): identical to ISS-306 — the checklist shows that step unchecked,
and the Prompt User toggle never activates, on the very first render.

## What would confirm or refute this

Find or construct a `ppt`/`prototype`-reachable fixture (or a saved/overridden workflow) whose
manifest declares a step with `before-human` + `condition_agent`, load `/create/ppt` or
`/create/prototype` fresh, and inspect the Review-gates checklist and the Advanced modal's
Config tab for that step with zero prior interaction. Both showing the gate refutes this card;
both silently omitting it (as ISS-306 found) confirms it.
