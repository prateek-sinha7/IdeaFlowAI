## Sibling of ISS-274 — INFERRED, not yet reproduced in the browser

[ISS-274](20260828-1854-ISS-274.md) established the root cause for the Composer Simple
view's "Configure →" panel: it opens `AdvancedExpander`
(`frontend/src/components/workflow/AgentsPopup.tsx:1774-2184`), whose subtitle is hardcoded
`Validator · Gate · Model · Retry` (`AgentsPopup.tsx:1883`) — no Tools row — even though
`StepSelection.tools` (the shared field Canvas view's `CanvasConfigRail` writes through) is
present in the exact same `SelectionsMap` shape. A whole-file grep for `"Tool grants"`,
`"Read files"`, `"Write files"`, `"Execute commands"` in `AgentsPopup.tsx` returns no match
at all (re-confirmed for this card).

Grepping every other renderer of that shared shape (`validatorOn`/`retryOn`/`gateOn`,
`applyLeverPatch`) turns up a SECOND, independent per-agent lever surface with the
identical gap: `ConfigLeversFlat` (`frontend/src/components/workflow/AgentsPopup.tsx:1620-1772`),
which backs the "Config" tab of `AgentCapabilitiesModal`
(`AgentsPopup.tsx:476-872`). Its own tab body is introduced by the comment "Config tab —
per-agent configuration levers (Model · Validator · Gate · Retry) shown FLAT" (`AgentsPopup.tsx:732-735`)
and its JSX (`AgentsPopup.tsx:1700-1771`) renders exactly four lever rows — Model,
Validator, Gate (pre/post checkboxes), Retry — and nothing for Tools. `ConfigLeversFlat`
shares the same `applyLeverPatch` reducer `AdvancedExpander` and `CanvasConfigRail` use
(`AgentsPopup.tsx:1640-1647`), so a `tools` value already present on the incoming
`SelectionsMap` would survive edits to the other levers (the reducer spreads `current`
before applying the patch) — it is just never rendered or offered for editing here either.

`AgentCapabilitiesModal` is mounted from two call sites, confirmed by grep:
- `frontend/src/components/library/LibraryPage.tsx:1001` — the Library page's per-agent
  detail drawer. Here `initialSelections`/`onSelectionsChange` ARE wired
  (`LibraryPage.tsx:1010-1013`), but only to a page-local `useRef`
  (`savedSelectionsRef`, `LibraryPage.tsx:637`) that never round-trips into any saved
  workflow — so today this call site cannot yet hide a REAL persisted override the way
  ISS-274's Composer case does.
- `frontend/src/components/workflow/AgentLibrary.tsx:335` — the "Add agent" picker modal
  used across Composer/LaunchWizard/IdeaInputPage. Here `onSelectionsChange` is not even
  passed (only `onSkillsChange`), so the Config tab's lever edits are entirely local and
  discarded when the modal closes, Tools or not.

## Expected vs actual

- **Expected:** if a per-agent config surface exposes Validator/Gate/Retry as editable
  levers over the shared `StepSelection` shape, it should expose Tools the same way Canvas
  view's rail does — or the surface should make clear Tools grants live elsewhere.
- **Actual:** `ConfigLeversFlat` renders the same four levers as `AdvancedExpander` and
  omits Tools identically, confirmed by reading its full JSX body
  (`AgentsPopup.tsx:1700-1771`) — no Tools row, tab, or reference to `sel.tools` anywhere
  in the component.

## Why this is INFERRED, not CONFIRMED

The missing Tools UI itself is confirmed by reading the component's source in full — there
is no Tools-rendering code to find. What is NOT yet verified is a live-browser repro
demonstrating a REAL persisted override being hidden through this specific surface today,
given the caller-wiring nuance above (neither current call site round-trips a `tools`
value into a saved workflow). This is filed as a lead for the next validation cycle: open
`AgentCapabilitiesModal`'s Config tab (via the Library page's agent detail drawer, or the
"Add agent" modal) and confirm no Tools section is offered, matching ISS-274's own
Reproduction steps 3-5 adapted to this surface.

## Analysis (QA-KB-016, analyzer, 2026-10-01)

**Verdict: unintended drift, a defect to fix. Not a deliberate exclusion, so not WONTFIX and not an
escalation.** Strictly it is not a regression either: `ConfigLeversFlat` has never had a Tools row. It
is the part of [FIX-350](20260828-2340-FIX-350.md) that was named and left open. The line numbers in
the sections above (`1700-1771`, `1620-1772`) are stale; current ones are used below. The browser
reproduction above stands (3/3; screenshot `evidence/qa-kb-016/02-validate-attempt1-config-tab-no-tool-grants.png`
shows System Prompt, Model, Validator, Before/After-execute gates, Retry, Reset / Save agent, no Tool grants).

### Root cause (CONFIRMED, every line read)

1. `ConfigLeversFlat` (`frontend/src/components/workflow/AgentsPopup.tsx:1797-1974`) renders Model
   (`:1879`), Effort (`:1893-1912`), Validator (`:1914-1922`), the Before/After-execute gate checkboxes
   (`:1926-1961`) and Retry (`:1963-1971`), then closes at `:1972`. No line in `1797-1974` matches
   `tools|TOOL_GRANT|effectiveToolGrants|hasToolOverride|Tool grants|Read files|Write files|Execute`.
2. The per-agent levers are hand-copied across three renderers of one `StepSelection`: the Canvas rail
   (`composer/CanvasConfigRail.tsx`), the Simple-view expander (`AdvancedExpander`, `AgentsPopup.tsx:1976`)
   and this flat list. Shared: the reducer `applyLeverPatch` (`:1479`) and, since FIX-350,
   `TOOL_GRANT_LEVERS` (`:1511`), `effectiveToolGrants` (`:1529`), `hasToolOverride` (`:1540`). Their
   consumers: rail `CanvasConfigRail.tsx:465,913`; expander `AgentsPopup.tsx:2063,2100`; chips
   `composer/AgentRow.tsx:97` and `composer/CanvasNode.tsx:496`. `ConfigLeversFlat` consumes none.
3. Nothing forces parity. No test renders one lever on more than one surface: tool-grant strings appear
   in a single test file (`composer/AgentRow.toolsVisibility.test.tsx`, Simple view), and Effort, whose
   comments say "present on BOTH authoring surfaces by design" (`:1889-1892`, `:2272-2275`), is tested on
   the rail only (`composer/CanvasConfigRail.effort.test.tsx`).
4. The write path is already generic: `updateLever` (`:1817-1824`) -> `applyLeverPatch` -> `setLocalSel`
   plus `onSelectionsChange`. A `tools` patch flows with no plumbing change; only the rows are missing.

### Blast radius (CONFIRMED by grep)

- `ConfigLeversFlat` has one call site, `AgentsPopup.tsx:788`, inside `AgentCapabilitiesModal` (`:507`).
  That modal has two mounts: `components/library/LibraryPage.tsx:1039` (the drawer: `/library` card
  click-through and the `/library/agents/<slug>` deep link) and `components/workflow/AgentLibrary.tsx:364`
  (the Add-agent picker, mounted by `composer/ComposerPage.tsx:1677`, `WorkflowView.tsx:570`,
  `AgentsPopup.tsx:2995`, `app/workflow/page.tsx:113`). One fix in `ConfigLeversFlat` covers every entry
  point; no caller changes.
- UI parity only. The drawer's `onSelectionsChange` writes a page-local ref (`LibraryPage.tsx:1045-1048`,
  `savedSelectionsRef`) and the Add-agent mount passes none (`AgentLibrary.tsx:364-369`), so a Tool grants
  toggle here is exactly as non-durable as Model/Validator/Gate/Retry
  ([ISS-392](20260828-2250-ISS-392.md), [ISS-393](20260828-2251-ISS-393.md),
  [BUG-073](20260829-1508-BUG-073.md)). No backend or run-time effect: these selections never reach
  `_apply_selections`.
- Adjacent states. Reset (`AgentsPopup.tsx:801-808`) clears `localSelections` and remounts via
  `resetKey`, so new rows reset with the rest. Save agent (`:815-825`) forwards `localSelections`, so
  grants ride along. `initialSelections` seeds `localSel` (`:1813`), so a stored grant renders on reopen.
  The rows do not depend on the capabilities fetch (`:1841-1844`); the `error` early return
  (`:1834-1840`) hides them with the other levers, as AdvancedExpander does.

### Fix: where it belongs

`ConfigLeversFlat` in `AgentsPopup.tsx`, after the Retry row (`:1963-1971`) and before the closing
`</div>` (`:1972`). Everything it needs is already defined above it in the same file
(`TOOL_GRANT_LEVERS`, `effectiveToolGrants`). Frontend only.

The agreed minimal fix (BUGS.md Notes) is **accepted in substance and placement**, with three amendments:

1. Write `tools: { ...sel.tools, ...grants, [key]: checked }`, not `{ ...grants, [key]: checked }`.
   `effectiveToolGrants` returns only read/write and `applyLeverPatch` replaces `tools` wholesale, so the
   agreed form is a third copy of [ISS-912](20261001-2218-ISS-912.md) (it drops `tool_sets`). It cannot
   bite on this surface today (nothing here can set a pack) but costs one token to avoid. Preferred: one
   `withToolGrant` writer beside `effectiveToolGrants`, shared with the two existing sites, as ISS-912
   describes. Checked offline by running the verbatim reducers under `node`.
2. Row markup: use this component's own patterns, `ConfigLeverRow` (`:1692`; its `description` is the
   `desc` that `TOOL_GRANT_LEVERS` already carries) with a checkbox child, or the gate rows' wrapping
   `<label>` (`:1942-1956`). Both avoid the `region` id prefix the agreed fix needs, so no duplicate-id
   risk. Keep `aria-label={`${label} for ${agentName}`}`, identical to AdvancedExpander (`:2115`), so one
   set of test queries fits both. The disabled, unchecked "Execute commands" row stays ("Not available to
   custom workflows.").
3. Update the Config-tab comment (`:773-776`, "Model · Validator · Gate · Retry"): it already omits
   Effort and would otherwise be read as the intended lever list.

Not recommended: one shared `<ToolGrantRows>` for all three surfaces. The data is already shared, the
markup differs by surface on purpose (FIX-350 left the rail's markup untouched), and three rows do not
earn a component. A test per surface is the cheaper guard. Nothing in the agreed fix was overruled.
