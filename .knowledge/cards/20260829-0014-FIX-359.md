## What was wrong

A cold navigation, reload or bookmark of `/runs/{id}/steps/{agentId}` selected the
Steps tab but rendered the bare, unfiltered lane list — no breadcrumb, no detail —
identically for a real agent id, a different real agent id, or a nonexistent one.
Only a manual row click opened the detail, and that click never wrote the URL, so
the state it produced could not be reloaded, shared or bookmarked.

## Root cause

The `agentId` was parsed and then dropped: nothing downstream of the parser had a
field to carry it.

- `frontend/src/lib/routes.ts:341-343` — `parseViewPath` correctly returns
  `{ screen: 'run-steps-agent', runId, agentId, version }`. The parse was never the
  problem.
- `frontend/src/app/[...view]/page.tsx` — `reopenTabFor(screen)` maps both
  `run-steps` and `run-steps-agent` to the same `"thinking"` string, and that string
  alone was handed to `runTabDeepLink.requestOpenTab(...)` at BOTH producer call
  sites (the already-tracked/shallow-nav branch and the cold-mount `.finally()`),
  even though the whole `parsedView` was in scope at each.
- `frontend/src/hooks/useTabDeepLink.ts:28-39` — `TabDeepLinkTarget` was `{tab,
  nonce}` and `requestOpenTab` was `(tab: string) => void`: no field existed to
  carry an agent id even one layer downstream.
- `frontend/src/components/preview/PreviewPanel.tsx:814-837` — the merged
  deep-link/default-tab effect read only `.tab`, and `<AgentThinkingTab>` was
  invoked with no agent-id-shaped prop.
- `frontend/src/components/results/AgentThinkingTab.tsx:84` — `selectedAgentId` was
  `useState<string | null>(null)`, unconditionally null on every mount regardless of
  the URL.

## What changed and why there

The fix is one new optional field on the ONE seam every deep-link producer already
routes through, rather than a second parallel channel from `page.tsx` to the Steps
tab (which would have left the chat "Open in Steps" CTAs on a different mechanism).

1. `frontend/src/hooks/useTabDeepLink.ts` — `TabDeepLinkTarget` gains an optional
   `agentId`; `requestOpenTab(tab, agentId?)` mints it into the target alongside the
   existing nonce. Every existing caller (`ResultCard`'s CTAs via
   `onRequestOpenTab: (tab: string) => void`) is unaffected — the argument is
   optional and those requests name no agent.
2. `frontend/src/app/[...view]/page.tsx:214-223` — new `deepLinkAgentIdFor(parsed)`,
   a narrow selector off the parsed view that mirrors the existing
   `pinnedVersionFor` idiom (`"agentId" in parsed`, which only `run-steps-agent`
   satisfies). Passed at BOTH producer call sites (`:3220` shallow-nav/back-forward
   branch, `:3293` cold-mount `.finally()`), not just the cold one the bug report
   named — they are the same mechanism and the shallow branch is the only one a run
   tab click and the back/forward after it reach.
3. `frontend/src/components/preview/PreviewPanel.tsx` — forwards
   `initialAgentId={deepLinkTarget?.agentId}` to `<AgentThinkingTab>`.
4. `frontend/src/components/results/AgentThinkingTab.tsx` — new optional
   `initialAgentId` prop seeds `selectedAgentId`'s initial value (so the deep-linked
   mount paints the detail directly, with no flash of the overview spine) and an
   effect keyed on that id re-applies it for a deep link arriving while the tab is
   ALREADY mounted (shallow run-tab nav / back-forward). Keyed on the id, so an
   in-pane "Back" is never re-stomped. The id — not a resolved agent object — is
   what is held, so a deep link that lands before `agents` arrives still opens the
   detail the moment it does (`selectedAgent` is resolved from the id every render).

SC-001: the id travels as an opaque run-scoped string, matched only against the
run's own `agents[].id`. No branch anywhere keys on a workflow or agent NAME, and
`reopenTabFor`'s screen→tab mapping is unchanged.

## Test edit — disclosed deliberately

`frontend/src/app/[...view]/runTabShallowNav.test.ts:62` (BUG-030's guard) asserts
by exact SOURCE-TEXT substring that the already-tracked branch mints the deep link.
Widening `requestOpenTab` — which ISS-277's own fix section calls for — lengthens
the call it pins, so the literal was updated to
`"runTabDeepLink.requestOpenTab(openTab, deepLinkAgentIdFor(parsedView))"`. The
guard's INTENT is unchanged (that branch must still mint the deep link for the
URL's tab) and the new literal is strictly stronger — it now also pins this fix in
the shallow-nav branch. No assertion was weakened or removed to turn a red test
green.

## Not fixed here (still open, by design)

- [ISS-387](20260828-2228-ISS-387.md) — the REVERSE direction: an in-pane agent/task
  selection still never calls `router.push`/`replace`, so the URL does not follow
  the selection and Back skips the Steps list. Untouched: it is its own card with
  its own globs, and a history push belongs with that card's history semantics, not
  smuggled into this one.
- [ISS-386](20260828-2228-ISS-386.md) — `routes.runStepsAgent` still takes no
  `version` parameter. Untouched here; the parser already accepts the pinned form,
  so this fix works for `/runs/{id}/versions/{v}/steps/{agentId}` too, but the
  builder still cannot construct it.
