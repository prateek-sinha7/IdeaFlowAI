# ISS-850

## Description

Residual finding from re-analyzing **QA-PS-021** (`BUGS.md#qa-ps-021`) after two of the
three compensation modes [ISS-733](20260922-1353-ISS-733.md) (this bug's root card)
originally described were independently closed by fixes filed under different bugs:

- Mode 1 (self-narration) — [ISS-699](20260922-1220-ISS-699.md), resolved: `FIX-608`
  (`20260922-1820-FIX-608.md`) closed the trigger (composer `write_files` grants now
  actually reach the compiled step) and `FIX-612`
  (`20260922-1838-FIX-612.md`, filed under QA-PS-027/[ISS-721](20260922-1242-ISS-721.md))
  added a backing `placeholder_narration_reason` signal regardless.
- Mode 3 (silent drop) — QA-PS-028's [ISS-730](20260922-1343-ISS-730.md), resolved by
  `FIX-615` (`20260922-1854-FIX-615.md`)'s `dropped_section_reason` signal.
- Confirmed live on this tree today:
  `cd backend && python3.11 -m pytest tests/agents/test_qa_ps_021_downstream_no_upstream_artifacts.py -q -p no:randomly`
  → `1 failed, 3 xfailed`; the failure is
  `test_apply_selections_carries_write_files_grant_onto_compiled_step` (ISS-699) now
  `XPASS(strict)` — i.e. passing, proving the grant is wired correctly.

**This card is INFERRED — not reproduced live.** It follows directly from reading the two
existing detection functions and finding neither can see the shape mode 2 takes; settling
it needs a live custom-workflow run where a builder step IS granted `write_files` (now
honoured per FIX-608) but a downstream validator-role step's declared dependency is not
satisfied — either because no step was told to produce it, or because the model chose not
to call the tool despite having it — and reading whether that step's raw completion
payload still gets treated as content-clean.

## What remains open (CONFIRMED by direct code read, 2026-09-22)

Mode 2 (the reporter's `ppt-validator`/`prototype-validate` examples, `BUGS.md#qa-ps-021`):
a validator/QA-role step that finds no upstream artifact to validate does not narrate the
absence and does not produce a partial copy of an existing document — it regenerates the
FULL deliverable itself, under its own attribution instead of the builder's. Neither
signal the shared completion gate gained since ISS-733 was filed can see this:

- `backend/agents/capabilities/deliverables/_placeholder.py:57-73` —
  `placeholder_narration_reason` requires BOTH the text to be short
  (`len(text) > _MAX_NARRATION_CHARS` — 2000, line 68 — returns `None`) AND to contain one
  of 12 literal first-person markers (`_NARRATION_MARKERS`, lines 26-40: `"i can't "`,
  `"i'm unable to"`, `"unable to complete"`, etc.). A validator's full self-generated
  substitute deliverable is long-form HTML/markdown/prose by construction and need
  contain none of them — read in full, the module's own docstring states the design
  intent explicitly: "a short, literal marker list and NOT a general output-quality
  judgement... a false positive is worse than a miss."
- `backend/agents/capabilities/deliverables/_coverage.py:75-93` —
  `dropped_section_reason` only fires when the deliverable verbatim-reproduces at least
  `_MIN_KEPT_NUM/_MIN_KEPT_DEN` (2/3, lines 38-39) of an upstream SOURCE's
  `_MIN_SECTIONS` (>= 3, line 35) top-level headings while omitting one. When the
  upstream artifact never existed at all — mode 2's own trigger — the loop's
  `_top_level_titles(sources[agent_id] or "")` returns `[]` for that agent,
  `len(titles) < _MIN_SECTIONS` is true, the entry is `continue`d (line 88), and the
  function returns `None`: there is nothing to diff the regenerated content against, so
  nothing is flagged.
- `backend/agents/execution_engine/engine.py:7456-7490` wires both signals into the same
  `_execute_impl` completion block (confirmed by direct read) and adds no third check
  anywhere keyed on "did this step's content actually come from the role its
  prompt/the deliverable declares."

## Why the root cause still implies this

[ISS-733](20260922-1353-ISS-733.md)'s central claim — "no engine mechanism catches a step
that ran without its expected input and produced something other than the intended
deliverable" — is still true for exactly this one shape, and remains reachable without any
ISS-698/699-class bug: a user simply not selecting "Write files" for the builder step in
the composer is an ordinary configuration choice, not a defect (FIX-608 only makes that
toggle work correctly — it does not require every workflow to grant it), and leaves a
downstream validator-role step's declared dependency legitimately missing. ISS-733's own
"Fix direction" section flagged this exact gap before FIX-608/612/615 existed: a
trigger-side fix "does nothing for a legitimately-missing upstream artifact elsewhere — a
crash, a wrong path, a race."

## Blast radius

Same shared block as [ISS-721](20260922-1242-ISS-721.md) (QA-PS-027) and
[ISS-730](20260922-1343-ISS-730.md) (QA-PS-028) — pipeline-agnostic by design (no
`pipeline_type` branch in `_execute_impl`, the kernel's name-branch ban), so a fix here
covers:

- `custom` / `custom_revision` runs (this bug) — any composer-selected validator-role step
  downstream of a builder step the user did not grant `write_files`.
- Per [ISS-734](20260922-1354-ISS-734.md), every native `gates:[validation]` pipeline
  (`dotnet_to_azure`, `ex_publish_step`, `mulesoft_to_springboot`, `pdf_to_prototype`,
  `prototype_revision`, `ex_validation_retry`, `prototype_v2`,
  `prototype_large_revision`, `prototype_feature_revision`, `playwright_smoke_test`)
  whenever ITS upstream artifact is legitimately missing (crash/race) rather than the
  always-denied case ISS-698 closed — those pipelines grant `write_files` by manifest
  design, so this is a narrower, rarer trigger for them than for `custom`.

## Fix direction (analysis only, not applied)

Belongs in the SAME shared block, `engine.py:7456-7490`, as a third signal alongside
`placeholder_narration_reason`/`dropped_section_reason` — not a per-pipeline or
per-resolver patch (mirrors how FIX-612 and FIX-615 were each a single addition to this
one block). Both existing signals are deliberately narrow, by their own documented
design, because a false positive flips a user-visible success badge; a reliable
"wrong role produced this" signal needs an attribution check — e.g. the completing step
is not the declared producer for what a downstream `consumes` was supposed to feed, yet
emitted substantial content anyway — rather than a text-shape heuristic. That design
tradeoff (how to detect "wrong role" without false-flagging a legitimately thorough
validator) is the fixer's call, not this card's.

## Test note (for 4-test-writer)

[ISS-733](20260922-1353-ISS-733.md)'s own existing test,
`test_custom_workflow_with_no_written_artifact_is_not_reported_clean` in
`backend/tests/agents/test_qa_ps_021_downstream_no_upstream_artifacts.py`, drives the
BARE `custom` manifest with zero tool grants selected. That is not this card's defect:
`backend/agents/workflows/custom/workflow.yaml:17-19` declares
`deliverable: {strategy: streamed_text, name: output.md}` — zero file writes IS the
declared happy path for that manifest (confirmed by direct read), and a 9/9-agent
offline drive completes cleanly with no file ever written, by design. A red test for
this card's mode-2 gap needs a step actually granted `write_files` (now honoured per
FIX-608) whose declared downstream consumer never finds real content from it — not the
default no-write configuration the existing xfail test drives.

## Fixed 2026-09-22 by [FIX-634](20260922-2235-FIX-634.md)

Applied in `backend/agents/capabilities/deliverables/_coverage.py`, not as a fourth call
in the gate: `dropped_section_reason` already receives exactly the two inputs this card's
own fix direction names — the deliverable, and the compiling step's DECLARED upstream
sources keyed by producer agent id (`engine.py:7477-7490` builds that map from the
`produces`∩`consumes` registry routing). The attribution check is therefore a second
branch of the same pass: a declared source that contributed NOTHING, under a deliverable
longer than `_MIN_UNSOURCED_CHARS` (2000, kept equal to `_placeholder.py`'s
`_MAX_NARRATION_CHARS` so the two signals partition the range), returns a reason and the
shared gate degrades `status` / `degraded_reason` / `published_status` as it already does
for the other two signals. `engine.py` was NOT edited — SC-001 holds trivially.

Observed: `cd backend && python3.11 -m pytest tests/agents/test_qa_ps_021_downstream_no_upstream_artifacts.py -q -p no:randomly`
→ `2 failed, 3 xfailed` (was `1 failed, 4 xfailed`); the new failure is this card's own
`test_wrong_attribution_full_regeneration_is_flagged_when_upstream_missing`
`[XPASS(strict)] ISS-850 unfixed` — the pass signal. Marker left for 6-verifier.

Known ceiling, stated on the FIX card: an upstream step that streamed prose but never
wrote its FILE still records that prose as its output, so its source entry is non-empty
and this signal stays quiet. That shape is FIX-612's (narration) and FIX-609's (raw prose
reaching the deliverable). A declared producer that never ran at all is absent from
`results` and deliberately not flagged — conditional routing legitimately skips steps.
