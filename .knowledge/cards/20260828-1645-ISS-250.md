## Reproduction (3/3, cold start each cycle)

Validated against register entry `BUG-20260828-001420-workflow-create-ppt`.

- **Cycle 1** — fresh `page.goto('http://localhost:3000/workflow/create')` (bare, no query
  string) after a cold navigate from `/dashboard`. `location.href` stayed at
  `/workflow/create` after a 2s settle; `document.querySelector('h1').textContent` read
  "Configure your prototype".
- **Cycle 2** — fresh `page.goto('http://localhost:3000/workflow/create?mode=')` (mode key
  present, empty value) from a cold `/dashboard` navigate. Identical result: URL never
  changed, same wizard rendered.
- **Cycle 3** — repeat of cycle 1 (bare URL) from another cold `/dashboard` navigate.
  Identical result, confirmed via `page.evaluate(() => ({url: location.href, h1:
  document.querySelector('h1')?.textContent}))` → `{url: "http://localhost:3000/workflow/create",
  h1: "Configure your prototype"}`.

3/3 — no narrowing needed. No axis variation was required; the defect is deterministic on both
trigger shapes (missing key vs. present-but-empty key).

## Root cause

`frontend/src/app/workflow/create/page.tsx`, `CreateRoute()`:

```ts
const raw = searchParams.get("mode");
const mode: LaunchMode =
  raw === "ppt" || raw === "ppt_v2" ? raw : "prototype";
return <LaunchWizard initialMode={mode} />;
```

This is not a redirect stub at all for the missing/empty case — it never calls
`router.replace`/`router.push`. It resolves a local `mode` variable (defaulting to
`"prototype"` for any `raw` that isn't `"ppt"`/`"ppt_v2"`, which includes `null` and `""`)
and renders `LaunchWizard` directly in place, under whatever URL the browser already has.
`LaunchWizard.tsx` itself has no route-canonicalization logic either — its only
`router.replace` calls are for the login redirect and Web/Deck in-wizard mode toggle (line
1143 `router.push(\`/workflows/${...}/canvas\`)` on save-as-copy, not on mount). So a genuine
canonicalizing redirect only happens for the two explicitly recognized values; missing/empty
`mode` silently falls into the same "render the prototype wizard" branch with no navigation
at all, leaving `/workflow/create` (and `/workflow/create?mode=`) as permanently live,
functional, un-canonicalized aliases into the current app.

## Root cause — analyzer refinement (2026-08-28)

Confirmed by reading `frontend/src/proxy.ts` in full (its own `matcher` scopes it to exactly
this route):

```ts
export function proxy(request: NextRequest) {
  if (request.nextUrl.pathname === "/workflow/create") {
    const mode = request.nextUrl.searchParams.get("mode");
    if (mode) {
      return NextResponse.redirect(new URL(`/create/${mode}`, request.url));
    }
    // If mode is missing, pass the request through unchanged
  }
  return NextResponse.next();
}
export const config = { matcher: ["/workflow/create"] };
```

This — not `page.tsx` — is the actual canonicalization layer for `/workflow/create`.
[ISS-227](20260828-1554-ISS-227.md)'s browser reproduction already proved this exact
`NextResponse.redirect` fires and lands `location.href` on `/create/<mode>` for any truthy
`mode` (that reproduction used a malicious `mode=../admin`, but the same code path is why
`?mode=ppt`/`?mode=prototype` genuinely do canonicalize, resolving the open question this
card's original "Root cause" section left implicit). The bug is `proxy.ts:8`'s `if (mode)`
— a plain JS truthy check on `URLSearchParams.get("mode")`, which returns either `null`
(key absent) or a `string` (key present), falsy only when that string is `""`. Both `null`
and `""` take the same silent-passthrough branch — line 12's own comment ("If mode is
missing, pass the request through unchanged") — with **no fallback destination at all**.

`page.tsx`'s `CreateRoute()` (quoted above) is therefore not itself a broken redirect stub;
it was never the canonicalization layer. It is the passthrough content renderer for whatever
`proxy.ts` chooses not to redirect. In current shipped behavior it never actually receives a
truthy `raw` — any truthy `mode` is intercepted by `proxy.ts` before this component renders
— so its own `raw === "ppt" || raw === "ppt_v2"` branch is effectively unreachable today.
`LaunchWizard.tsx`'s `router.replace`/`push` calls (lines 261, 799, 820, 1143, already
checked for this card) remain unrelated (login guard, cancel-to-home, save-as-copy) — none
fire on mount.

## Blast radius (analyzer pass, 2026-08-28)

- **Every reachable trigger of `proxy.ts:8`'s falsy branch**: `searchParams.get("mode")`
  returns `null` for a bare `/workflow/create` and for any misspelled/miscased key
  (`?Mode=ppt`); it returns `""` for `?mode=` and for `?mode=&mode=ppt` (`.get()` returns
  the first occurrence). All collapse to the two shapes already reproduced above (null,
  empty string) — no third trigger shape exists for this check.
- **In-app callers of `/workflow/create`** — grepped `workflow/create` across
  `frontend/src/`:
  - `frontend/src/components/home/CreationHub.tsx:31,35` —
    `router.push(routes.workflowCreateLegacy("prototype"|"ppt"))`
  - `frontend/src/components/layout/DashboardLayout.tsx:1547,1574` — same, hardcoded
  - `frontend/src/store/slices/globalSlice.ts:220-222,250-252` — `WIZARD_ROUTES`/
    `wizard_path` table, values always `ppt`/`ppt_v2`/`prototype`

  Every one of these passes a hardcoded, always-truthy mode string — **none can trigger the
  falsy branch**. The only route into it is external: a bookmark, hand-typed URL, or link
  predating the `?mode=` convention. This matches the hunter's own repro method (direct
  `page.goto`, not a UI click path) — there is no in-app caller currently capable of hitting
  this.
- `frontend/src/app/[...view]/page.tsx` mentions `/workflow/create` only in comments (lines
  296, 3586, 3766); one (3583-3592) attributes the canonicalizing redirect to "next.config.ts's
  T17 redirect" — **that is stale documentation**, not a functional issue: `next.config.ts`
  (read in full) carries no `/workflow/create` rule; the redirect has always lived in
  `proxy.ts`. Worth flagging so a fixer doesn't go looking in the wrong file.
- **Inverse direction checked, and it's fine**: `/create/{mode}` does not redirect back
  through `workflowCreateLegacy` — `[...view]/page.tsx:3773-3774` renders `LaunchWizard`
  directly, a deliberate choice (its own comment: avoids a bounce loop against this same
  `proxy.ts` redirect). Not a defect.
- **Axis check**: tier/theme/viewport are irrelevant — `proxy.ts` runs at the edge, before
  auth/session/rendering, matching the hunter's "no axis narrowing needed."

## Fix location

Belongs in **`frontend/src/proxy.ts`**, not `page.tsx`. `proxy.ts` is already the single
choke point for this route (`matcher: ["/workflow/create"]`) and already performs the
canonicalizing redirect for every truthy `mode` — the smallest diff extends the SAME
mechanism to the falsy case (e.g. default the mode before building the destination) rather
than adding a second, divergent redirect path inside the React component `page.tsx` renders.
A page-level fix would leave two different canonicalization mechanisms for one route
(edge-redirect for truthy, client-render-then-maybe-navigate for falsy) and would still paint
one full page under the uncanonicalized URL before correcting it, unlike every other `mode`
value today. See [ISS-227](20260828-1554-ISS-227.md) for the neighboring defect in this same
function (the truthy branch's destination is unsanitized) — a fix here should default `mode`
without reintroducing that gap.

## Expected vs actual

- **Expected:** every reachable variant of the `/workflow/create` redirect stub
  canonicalizes to a real target URL (or fails explicitly), per the file's own doc comment
  ("`/workflow/create` — the ONE unified deliverable-launch route... Replaces the retired
  `/workflow/prototype/templates` + `/workflow/ppt/templates` pages").
- **Actual:** `raw === "ppt" || raw === "ppt_v2"` is the only branch that gets a canonical
  target; every other `raw` (including `null`/`""`) renders the prototype wizard in place
  with zero navigation, so the legacy URL never disappears for those inputs.
