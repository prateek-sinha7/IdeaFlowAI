## The gap (as filed 2026-09-04)

FIX-535 made step objects survive a Composer load/save round trip.
`buildWorkflowManifest` gained a `sourceManifest` parameter to do the same for
the manifest's own top-level keys, but no caller supplies it. `id`,
`display_name`, `limits`, `input_providers` and `seed_files` are therefore still
dropped on save.

Recorded by the fixing commit itself (`00b61ff93`) as a known, deliberate gap.

## Reproduction (QA-KB-021, validated 2026-10-01, Static/Test mode, no browser)

Three cold runs, 3/3 reproduce the gap (conditions: any saved workflow opened via the
`/workflows/{id}/edit` or `/workflows/{id}/run` cold mount, then Saved).

1. `frontend/src/components/workflow/composer/ComposerPage.tsx:903` passes
   `initialManifest` as 5th arg of `buildWorkflowManifest`; it is fed from
   `DashboardLayout.tsx:3237` `initialManifest={savedComposition?.manifest}`.
2. The click-through path sets it: `DashboardLayout.tsx:1720`
   `manifest: (saved.manifest as Record<string, unknown> | undefined) ?? null,`.
3. Both cold-mount `setInitialSavedComposition` literals in
   `frontend/src/app/[...view]/page.tsx` (line 3776 edit, line 3978 run) set `manifestSteps:
   saved.manifest?.steps` and `runConfig` but NO `manifest`, so `savedComposition?.manifest` is
   undefined and `manifestTopLevelExtra(undefined)` returns `{}`
   (`userWorkflows.ts:~620`): `limits`, `input_providers`, `seed_files` etc. are dropped on save.
4. `npx vitest run src/store/api/pdfToPrototypeManifestRoundTrip.test.ts` x3: 5/5 pass each time,
   so the existing test does not cover the cold-mount wiring (it calls buildWorkflowManifest directly).

Agreed minimal fix: add `manifest: (saved.manifest as Record<string, unknown> | undefined) ?? null,`
to the two literals; leave the built-in canvas call (~521) alone. Tracked as QA-KB-021.

## Analysis — QA-KB-021 (analyzer, 2026-10-01, tree feat/user-stories-v2)

**Verdict: root cause CONFIRMED (every line below was opened and read). The agreed minimal fix is ACCEPTED, with the
refinements under "Fix".** Line numbers are as of this analysis; the quoted anchors survive edits.

### Root cause (CONFIRMED)

`SavedComposition` — the shape that carries a saved row into the Composer (`DashboardLayout.tsx:56-83`) — is built by
hand-copied object literals at four sites. `manifest` was added to the type and to one of the four.

| # | site | seeds | carries `manifest`? |
|---|---|---|---|
| 1 | `DashboardLayout.tsx:1717-1736` (`handleLaunchSaved`) | click-driven open | yes, `:1720` |
| 2 | `page.tsx:3776-3787` | `/workflows/{id}/edit` | **no** |
| 3 | `page.tsx:3978-3993` | `/workflows/{id}/run` (composer and input branches) | **no** |
| 4 | `page.tsx:521-552` | `/workflows/{type}/canvas` (built-in, no row) | no, and no source for it — see [ISS-876](20261001-2110-ISS-876.md) |

A static slice of `page.tsx` agrees: three `setInitialSavedComposition({` literals, none with a `manifest:` key
(`manifestSteps:` is the only key that starts with the word).

History, from `git log -S`: `00b61ff93` (2026-09-04) added `buildWorkflowManifest(..., sourceManifest)` with no caller.
`f23625911` (2026-09-11, titled "fix(engine): resume a DB workflow at the failed step ...", with frontend changes riding
along) wired the consumer half: `SavedComposition.manifest` (`DashboardLayout.tsx:62-66`), site 1, the
`initialManifest={savedComposition?.manifest}` prop (`DashboardLayout.tsx:3237`) and the call
`buildWorkflowManifest(pipelineAgents, capabilities, selections, runConfig, initialManifest)` (`ComposerPage.tsx:903`).
It did not touch sites 2 or 3.

Chain from there: sites 2 and 3 leave `savedComposition.manifest` undefined, so `ComposerPage.initialManifest` is
undefined and `manifestTopLevelExtra(undefined)` returns `{}` (`userWorkflows.ts:617-618`). The PATCH body's `manifest`
then carries only `steps` plus the modeled keys, and the server replaces the column outright
(`backend/app/api/user_workflows.py:994-997`, `row.manifest_json = _validated_manifest(body.manifest, ...)`;
`_validated_manifest`, `:138-`, checks steps only). Every top-level key outside `MODELED_MANIFEST_KEYS`
(`userWorkflows.ts:606-614`) is gone from the row: `limits`, `input_providers`, `seed_files`, `id`, `display_name`,
`icon`, `description`, `version`, `user_launchable`, `is_beta`, `chat`, and the rest of the allow-list
(`backend/agents/workflows/manifest.py:172-204`). `GET` returns the whole column (`_project`,
`user_workflows.py:446-449` and `:495`), so the seed had everything it needed.

Why it hurts (CONFIRMED by reading): a launch from the saved row compiles the stored column
(`backend/app/api/run_commands.py:3347-3349`), `seed_files` is read from it at launch (`:2817`), and a missing `limits`
compiles to `Limits()`, so the budget falls back to `DEFAULT_MAX_SUBAGENTS = 8` and `DEFAULT_WALL_CLOCK_SECONDS = 900`
(`backend/agents/execution_engine/budget.py:43-46`, `:92-106`). A fan-out past eight raises
`BudgetExceeded("subagents")` (`budget.py:194-200`). [ADR-0039](20260904-1424-ADR-0039.md) made db rows trusted
precisely so a Composer workflow could carry a raised ceiling ("dies at task 9 ... mid-run, with earlier waves already
written to disk"); this save strips it. `input_providers` is what binds image / PDF input (`backend/CLAUDE.md`: "the
image half ALSO needs a workflow-level `input_providers: [pdf_pages]`").

### What this card's original text got wrong (corrected in place)

"no caller passes it" has been false since 2026-09-11. That is why the title, `compact_summary` and `applies_to` above
were rewritten; the defect itself is unchanged.

The validator's note, "the click-through path sets it", is also weaker than it reads: the click path is not a working
escape hatch, because it is not what a user's click ends on.

- My Workflows, row menu, Edit: `handleEdit` is `router.push(routes.workflowEdit(row.id))`
  (`SavedWorkflowsPage.tsx:219-222`). It never calls `handleLaunchSaved`. Seed = site 2. **CONFIRMED.**
- WorkflowDetailView Edit and Run links (`WorkflowDetailView.tsx:79-90`), deep links, refresh: sites 2 and 3
  directly. **CONFIRMED.**
- My Workflows, Run workflow: `onLaunchSaved(row)` (`SavedWorkflowsPage.tsx:394`) calls `handleLaunchSaved`, which
  sets site 1's composition and then `router.push(routes.workflowRun(saved.id))` (`DashboardLayout.tsx:1749`). The
  `/run` effect (`page.tsx:3903-4028`) fetches the row again and seeds site 3's manifest-less literal, which
  `DashboardLayout` copies over its own state (`:1553-1557`). Until it lands, `page.tsx:4115-4121` returns `null`
  (`parsedView.screen === "workflow-run" && !workflowRunMainView && !workflowRunFailed`), and `page.tsx:3469-3473`
  plus [ADR-0014](20260824-1630-ADR-0014.md) record that a `router.push` under the shared catch-all remounts the page
  ("In-memory state does not survive that"). So site 1's `manifest` is discarded and the Composer ends up seeded by
  site 3. **INFERRED**: every hop is read, but the remount is documented in the code and the ADR, not re-observed here.
  One browser pass settles it: Run workflow on a row whose manifest has `limits`, Save in the Composer, then
  `GET /api/user-workflows/{id}`.

### Blast radius (grepped, not assumed)

- Seeds of `SavedComposition`: exactly the four above (`grep -rn "setInitialSavedComposition\|setSavedComposition"
  frontend/src`). The single `<ComposerPage` mount (`DashboardLayout.tsx:3195`) is fed only by `savedComposition`.
- Writers of a saved row's `manifest_json` that start from a loaded row: only `ComposerPage.handleSave`
  (`ComposerPage.tsx:897-931`). The other `buildWorkflowManifest(` callers, `IdeaInputPage.tsx:1769` and
  `LaunchWizard.tsx:967`, also pass no source **but are not affected**: they write override rows, and an override
  contributes only its `steps` (`backend/app/api/_workflow_override.py:104-121`, then `merge_override_steps`); the
  top-level keys come from the file manifest at run time.
- Entry points that end on sites 2 and 3: the Edit menu, the Run workflow button, the WorkflowDetailView links, deep
  links, refresh, and client navigation to either URL.
- Downstream: the first Save after the open, then every launch of that row (a saved Composer row launches from the
  stored column, `ComposerPage.tsx:1129` `{ user_workflow_id: userWorkflowId }`).
- A restoration route already exists: `POST /api/user-workflows/{id}/sync-from-file`
  (`user_workflows.py:1027`) rewrites the column from the source `workflow.yaml`, so the backend already
  acknowledges that a canvas save drifts from the file.

### Fix — accept the agreed minimal fix, with refinements

**Accept:** add `manifest: (saved.manifest as Record<string, unknown> | undefined) ?? null,` next to `manifestSteps:`
in the literals at `page.tsx:3776` and `:3978`. It type-checks exactly as `DashboardLayout.tsx:1720` does
(`userWorkflowsApi.get` returns `UserWorkflowSummary`, whose `manifest` is `WorkflowManifest | null | undefined`,
`lib/api.ts:~2490`). Nothing else reads `savedComposition.manifest` (`DashboardLayout.tsx:3237` only), so
`IdeaInputPage` is unaffected, and rows without a manifest behave as before (`?? null`).

Refinements:

1. Leave site 4 (`page.tsx:521`) alone, and never add an `id` to it ([ADR-0014](20260824-1630-ADR-0014.md) locked
   constraint). Its gap is a different fix: [ISS-876](20261001-2110-ISS-876.md).
2. Site 1's `manifest` (`:1720`) is now redundant in practice. Leave it; removing it is out of scope.
3. Optional hygiene, not required: `ComposerPage.tsx:975-985` lists `initialManifestSteps` but not `initialManifest` in
   `handleSave`'s deps although `:903` reads it. Harmless today, because `DashboardLayout.tsx:3212`
   (`key={savedComposition?.id ?? "new"}`) remounts `ComposerPage` when the row arrives and the manifest and its steps
   always arrive together.
4. Not recommended now: replacing the hand-copied literals with a shared builder. The `runConfigFromManifest` comment
   (`userWorkflows.ts:663-667`) shows this exact drift was cured for one field that way, but `SavedComposition` lives in
   `DashboardLayout.tsx`, so a builder under `store/api` would have to pull a component-layer type down or move it, and
   `page.tsx` is a hot file in a shared tree. The two-line diff is the smaller, safer one.

Still lost after this fix: `capabilities` ([ISS-875](20261001-2110-ISS-875.md)).

  repo's idiom is a source-lock test beside `workflowDetailCatch.source.test.ts`, for example
  `frontend/src/app/[...view]/savedCompositionManifest.source.test.ts`. Read `page.tsx`, slice the `/edit` effect (from
  `const workflowId = workflowEditIdFor(parsedView);` to `const workflowId = workflowDetailIdFor(parsedView);`) and
  the `/run` effect (from `const workflowId = workflowRunIdFor(parsedView);` to
  `setWorkflowRunMainView(isComposerWorkflow(saved) ? "composer" : "input");`), and assert each slice contains
  `manifest: (saved.manifest as Record<string, unknown> | undefined) ?? null`. All four anchors occur exactly once
  today. It fails now and passes with the fix. Do not pin a whole-file literal count: QA-KB-033
  ([ISS-442](20260829-0106-ISS-442.md)) is exactly that fragility.
- The behavioral half already exists and passes: `ComposerPage.test.tsx`, "a re-saved workflow keeps its limits

- `pdfToPrototypeManifestRoundTrip.test.ts` is green before and after and cannot see this bug: it builds the `source`

- One file at a time, offline tier only. A true end-to-end check belongs in the live tier

## Fix (2026-10-01)
