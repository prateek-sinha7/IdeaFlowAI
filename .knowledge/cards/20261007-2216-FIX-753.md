# FIX-753

Fixes QA-KB-067 (register `LEDGER.md`, detail `BUGS.md#qa-kb-067`). Resolves the root card
[ISS-840](20260922-2030-ISS-840.md) and its T11 sibling [ISS-1076](20261007-2141-ISS-1076.md), both with one
change at the hand-off they share. The version-picker sibling [ISS-1075](20261007-2141-ISS-1075.md) stays open,
for the reason under "Not changed" below.

## What was wrong

A history click on a completed run ran the whole reopen twice. The validator measured
`GET /api/runs/{id}` x2, `events?after=0` x2 and `/family` x2-3, 3 of 3 attempts. The baseline run for this fix,
before any edit, measured `events?after=0 x2` (`GET /api/runs/{id}` came to 1 that time, because `singleFlightGet`
coalesced the two overlapping calls).

## Root cause (ISS-840's analysis, re-checked on this tree before editing)

Every run-open surface in `DashboardLayout.tsx` calls `onSelectWorkflowRun?.(run)` and then `router.push`es a run
URL. Those surfaces are the History row and Home "Jump back in" (`onOpenRun`, pushing `runDetail`), the header run
list, the bell's completed branch and the completion toast (pushing `runStream`). `page.tsx` wired that prop to
`handleSelectWorkflowRun`, the full networked reopen. The push remounts `page.tsx`, so:

- the click-time call (instance A) fetched the run, its event log and its family into a page that was about to
  unmount, and every write it made landed nowhere (`useRunStateStore.ts:399` hands an unmounted page a throwaway
  entry);
- the remounted page's T7 effect (`/runs/{id}`) or T11 effect (`/runs/{id}/stream`) read a fresh `null`
  `trackedRunIdRef`. A terminal run is never in `runConnection.liveRunIds`, so the effect called
  `handleSelectWorkflowRun({ id: runId })` again. That second call is the one whose writes reach the screen.

The blast radius was re-grepped before the edit. `page.tsx` hands `onSelectWorkflowRun` to `DashboardLayout` at
exactly one site. All 8 `DashboardLayout` call sites (2848, 2911, the bell's uncached fetch-then-open, 2943, 2997,
3057, 3465, and the toast's uncached fetch-then-open) call it and then push a run URL. `AppHeader.handleRunClick`
reaches it only through its terminal branch.

## What changed, and why there

This is fix shape 1 from ISS-840's "Where the fix belongs". The duplicate is the click's call, and every surface
routes through one prop, so the change sits at that hand-off rather than in the T7/T11 guards:

1. `page.tsx`: new `primeRunOpen` (declared after `handleSelectWorkflowRun`), passed as `onSelectWorkflowRun`.
   It is synchronous and makes no fetch. It claims the switch (`beginSwitchGeneration(run.id)`, the same claim
   the old click-time call made, so an older in-flight reopen still drops), switches the store viewport, and sets
   `isLoadingRunData`, which keeps the FIX-606 skeleton on screen during the navigation. The remounted page claims
   the same run, keeps the same generation, and does the one reopen.
   - It does not set `contentSourceRunId`, which would cost one `/family` in the doomed instance, or
     `trackedRunIdRef`. Leaving the ref alone means T7/T11 still reopen if a push ever fails to remount.
   - It returns early when the current URL already names the run, using the same `parseViewPath(window.location...)`
     check DashboardLayout's BUG-024 push guard uses. A push to the URL already on screen does not remount, so a
     loading flag set there would never clear. The run is already displayed, so nothing is lost.
2. `DashboardLayout.tsx`: the two fetch-then-open variants (bell, run outside the recents window; toast, same
   case) lost their `getWorkflow(...).then(onSelectWorkflowRun)`. That fetch existed only to feed the click-time
   reopen, and on the bell it ran after the push, into the doomed instance. The remounted T11 fetches the run.

No import was orphaned: `getWorkflow` and `getToken` have other uses in `DashboardLayout.tsx`.

## Where the change landed in git, and the cached-toast question

The user's commits split this fix in two:

- `94a79a439` "fix(QA-KB-067)" carries only the `DashboardLayout.tsx` half. Its message says the open paths "no
  longer ... call onSelectWorkflowRun", which is not what changed: they still call it.
- The `page.tsx` half was committed inside `cb73a6dc6` "fix(QA-KB-055)", because that file also held FIX-752's
  edits. It is the part that makes `onSelectWorkflowRun` stop fetching: `primeRunOpen` (`page.tsx:3434-3440` at
  HEAD 33d556571) and `onSelectWorkflowRun={primeRunOpen}` (`:4478`).

The verify note added to `BUGS.md#qa-kb-067` (commit `33d556571`) says the completion toast's cached branch
"still calls `onSelectWorkflowRun(completedRun)` ... so the remounted page's T11 effect opens the run a second
time". The call is still there, by design: `DashboardLayout.tsx:3465` `onSelectWorkflowRun?.(completedRun);`. That
prop is now `primeRunOpen`, which never fetches, so T11's reopen is the only one. The bell's cached branch has the
same call shape (`DashboardLayout.tsx:2911` `onSelectWorkflowRun?.(cached);` and then `router.push(routes.runStream(...))`),
and it was measured at 1 / 1 / 2. The toast itself was not driven, because a toast needs a run that completes
during the session.

## Behaviour notes for the verifier

- Clicking the run that is already open, at the URL the click pushes (for example the toast "View results" or a
  bell entry for the run being watched on `/runs/{id}/stream`), no longer re-runs the reopen. Measured: 0 / 0 / 0
  requests, and the deliverable stays on screen. Before, that click re-fetched and re-seeded the same run in
  place. The live `pipeline_complete` path has already put the deliverable on screen.
- A header, bell or toast click made from another run's screen no longer blanks that screen at click time. The
  previous run stays visible until the new page mounts and shows its skeleton. From `/runs` and `/dashboard` the
  skeleton shows at click time, as before.

## Not changed

- [ISS-1075](20261007-2141-ISS-1075.md) (the History version picker) is left open. Its entry point,
  `WorkflowHistory.handleSelectVersion`, is reached only from the `RunDetailPage` that `WorkflowHistory` mounts
  when `selectedRun` is set. In production `selectedRun` is never set, for two reasons:
  - `handleSelectRun` returns early through `onOpenRun` unless `opts.forChain` is set, and `DashboardLayout` always
    passes `onOpenRun`;
  - no caller passes `forChain` since FIX-584 removed the Chain item (`grep -rn forChain frontend/src` outside
    tests returns only the `WorkflowHistory.tsx:341/354/358` definition).

  That path cannot be reached in production, so this fix left `WorkflowHistory.tsx` alone. Changing it would also
  have meant editing `page.iss856.test.tsx`'s sanity assertions. After this fix the path runs one reopen; the
  picker's own pre-fetch remains. The note on the card has the details.
- `handleSelectWorkflowRun` keeps ISS-856's `if (run.input === undefined)` guard. Every caller now passes a
  `{ id }` stub, so the guard always fetches. It is harmless, and `page.iss856.test.tsx` source-locks it. Its
  comment still names the toast and notification fetch-then-open as callers that hand over a full record; neither
  does any longer. That comment was left as it is.
- The T7 comment "Skipping here is what keeps a client-side nav from /runs from double-fetching (AC3)" was already
  inaccurate before this change (ISS-840) and was not edited.
