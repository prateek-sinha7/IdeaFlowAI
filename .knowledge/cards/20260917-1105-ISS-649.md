# ISS-649

## Title

Background/non-viewed run's review-gate opening (pause) or resolving (resume) is never reflected in its notification, the same class of defect as QA-PS-002 ([ISS-644](20260917-0930-ISS-644.md)) applied to the gate-pause/resume state instead of the progress count.

## Status: INFERRED — not yet reproduced

Filed from the root cause of QA-PS-002, not from an independent reproduction. Confirm live before treating as a defect (see "What would confirm this" below).

## Why QA-PS-002's root cause implies this

QA-PS-002's confirmed mechanism ([ISS-644](20260917-0930-ISS-644.md)): any `DashboardLayout` effect gated on the single-run `pipelineState`/`currentPipelineNotifId.current` pair only ever fires for whichever run is currently `runStore.viewed` (`frontend/src/app/[...view]/page.tsx:3887,3926`). The gate pause/resume effect has exactly the same gating and no background bridge:

- `frontend/src/components/layout/DashboardLayout.tsx:926-934`:
  ```ts
  useEffect(() => {
    if (!currentPipelineNotifId.current || !pipelineState?.isRunning) return;
    if (reviewGateData) {
      markGatePaused(currentPipelineNotifId.current);
    } else {
      markGateResumed(currentPipelineNotifId.current);
    }
  }, [reviewGateData, pipelineState?.isRunning]);
  ```
  Both `pipelineState` and `reviewGateData` are viewed-run-only props: `reviewGateData={runStore.viewed.reviewGateData}` (`frontend/src/app/[...view]/page.tsx:4149`), the same `runStore.viewed` projection as `pipelineState`.
- The underlying per-run data IS captured correctly regardless of which run is viewed — `runStore.update(gateRunId, { reviewGateData: gateData })` (`frontend/src/app/[...view]/page.tsx:2040`, inside the `review_gate_ready` handler at `:2019`) stores the gate for whichever run it belongs to — but nothing ever reads that per-run map to update a BACKGROUND run's notification the way `runAgentsCompletedMap` does for `AppHeader`'s progress display (FIX-208) or `backgroundCompletedRunId` does for completion (FIX-203).
- No `backgroundGate*` state/bridge exists anywhere in `page.tsx` or `DashboardLayout.tsx` (confirmed absent: `grep -rn "backgroundGate" frontend/src/` returns nothing), unlike the completion case which got exactly this treatment.

So a run that hits a review gate while it is NOT the viewed run has its `reviewGateData` correctly stored in `runStore`, but `markGatePaused`/`markGateResumed` (`useNotifications.ts:187`, `:200`) are never called for it — the notification stays in whatever state it was already in (most likely spinning "running") instead of showing paused, and never shows the resume either.

## Expected (once reproduced)

A backgrounded run whose review gate opens shows its notification transition to a paused/gate state, and resuming (approval) shows it return to running — mirroring the viewed-run behavior this effect already gives you when the gated run happens to be the one on screen.

## Actual (inferred, not yet observed)

The notification for a non-viewed run is expected to show no visible change when that run's review gate opens or resolves, because `markGatePaused`/`markGateResumed` are only ever invoked for `currentPipelineNotifId.current` (the viewed run).

## What would confirm this

1. Launch two concurrent runs that both reach a review gate (e.g. two Prototype runs), keep run A viewed.
2. Let run B (backgrounded) hit its review gate.
3. Check whether run B's notification-panel entry shows any paused/gate indicator, then approve run B's gate from wherever that's possible while backgrounded and check whether it resumes visibly.
   Alternative: reproduce QA-PS-002's own "navigate away" shape — start a run, navigate to `/dashboard` before its gate opens, and check the panel when the gate fires.

## Correction (re-analysis, 2026-09-17 — see [ISS-673](20260917-1420-ISS-673.md)): this card's central prediction is refuted for the live row's STATUS

Read directly: `page.tsx:2045-2051` (`review_gate_ready` handler) and `:2071-2077` (`review_gate_approved` handler) both call `getWorkflows().then(setRecentRuns)` **unconditionally** — not gated on `isForeignFrame`, `activelyBuildingRunIdRef`, or viewed status — specifically "so the badge shows 'WAITING FOR YOU' when gate fires" (page.tsx:2045's own comment) and "so badge shows resumed status after gate approval" (:2071). `AppHeader`'s live row status comes from the server's `r.status` (`AppHeader.tsx:206-214`, mapping `waiting_for_user` → `"gate"`), which this refetch keeps correct for EVERY run this tab launched, viewed or not. So a backgrounded run's gate open/resolve IS visibly reflected in the live row's status label — this card's "Actual (inferred)" does not hold.

What is still real: the SAME row's agent-progress count (`agentsCompleted`/`agentsTotal`, the [ISS-673](20260917-1420-ISS-673.md) defect) stays frozen regardless of the correctly-updating status — a backgrounded run paused at a gate shows the right "GATE" label next to a stale "0/N". That is [ISS-673](20260917-1420-ISS-673.md)'s bug, not a distinct gate-specific one.

Not addressed either way by this correction: whether the notification's `unreadCount`/toast (via `markGatePaused`/`markGateResumed`, `useNotifications.ts:187,200`) fires for a background run — those are only called for `currentPipelineNotifId.current` per this card's original citation, so the bell's unread badge may still fail to increment for a backgrounded gate even though the panel row itself, once opened, shows the right status. That narrower claim (badge count, not row content) is unverified either way and is what remains open in this card.

## Resolution (2026-09-17, [FIX-521](20260917-1447-FIX-521.md))

The narrowed claim holds in code. `unreadCount` is
`notifications.filter(n => !n.read && n.status !== "running")` (`useNotifications.ts:258`), and a
background run's notification never left `"running"`, so a background run waiting at a gate never
raised the bell's unread badge.

FIX-521 reuses the ISS-648 bridge:
- `review_gate_ready` for a non-tracked run sets `{ runId, to: "gate" }` (`page.tsx:2051-2052`).
- `review_gate_approved` sets `{ runId, to: "running" }` (`:2080-2083`).
- The DashboardLayout effect calls `markGatePaused`/`markGateResumed`.
- The state is an object, so a run's second gate re-fires the effect.
