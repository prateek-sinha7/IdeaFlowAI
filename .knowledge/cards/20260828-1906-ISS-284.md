## What is suspected

[ISS-228](20260828-1758-ISS-228.md) confirmed that opening a saved workflow's launch panel can
silently populate `pipelineAgents` with the generic per-pipeline default roster instead of the
saved override's real roster (`LaunchWizard.tsx:335-338` overwriting `:278-324`'s correct
restore — see that card for the full mechanism). `pipelineAgents` is not read-only display
state: it is the literal source of truth both save paths in the same file persist back to the
server:

- `handleSave` ("Save workflow", `LaunchWizard.tsx:699-705`) sends
  `agent_ids: pipelineAgents.map((a) => a.id)` (`:703`) when creating a new saved-workflow row.
- `handleSaveAsOverride` ("Save as my version", `LaunchWizard.tsx:727-754`) sends
  `agent_ids: pipelineAgents.map((a) => a.id)` (`:737`) AND builds the `manifest` from
  `pipelineAgents` (`:738-742`) — and per its own doc comment (`:717-719`), "the server UPSERTS on
  it — so saving twice updates the SAME row." This is the row the user is trying to preserve.

Neither handler re-fetches or re-derives the roster at save time — both trust whatever
`pipelineAgents` currently holds in state. If ISS-228's race has already fired (which, per that
card, is deterministic on every cold mount of `/workflows/{id}/run` in this environment), the
roster in state at the moment "Save" or "Save as my version" is clicked is the wrong generic
default set, not the workflow's real override.

## Condition

Open a saved prototype/ppt workflow's launch panel via any path that triggers ISS-228's race
(confirmed: cold `/workflows/{id}/run`; suspected: [ISS-283](20260828-1905-ISS-283.md)'s
click-through Run), then click "Save as my version" (or "Save workflow") without first noticing
the "Advanced N agents" roster is wrong — there is no error state and no visual cue that anything
is amiss, per ISS-228's own reproduction, so a user has no reason to suspect the click is
destructive.

## Expected vs actual

**Expected:** saving from the launch panel persists the agent roster the user actually sees and
intended to keep (or explicitly edited), or the save flow fails loudly if the panel's own state is
known to be unreliable.

**Actual (predicted):** the save silently UPSERTS the user's real saved override with the generic
default roster's `agent_ids` and a `manifest` built from that same wrong roster, permanently
replacing the data ISS-228's render bug merely misdisplayed — turning a transient render defect
into persisted data loss, with the same "no error, no indication anything is wrong" character as
the parent bug.

## Why the root cause implies this — and why it is a distinct defect from ISS-228

This is the inverse-direction case ISS-228 does not itself cover: that card is about a LOAD
(render) being wrong; this is what happens when the wrong LOAD feeds a SAVE. ISS-228's root cause
is a state race that leaves `pipelineAgents` wrong in memory — nothing about that mechanism
touches the server. It is `handleSave`/`handleSaveAsOverride` specifically, by trusting
`pipelineAgents` as ground truth with no re-validation against the fetched override, that turns
the in-memory defect into a persisted one. Fixing ISS-228's effect race prevents this too (the
state would never be wrong in the first place), but until it is fixed, this is the
highest-severity consequence in the family — data loss, not just a wrong render — and is worth
tracking and testing independently, so a fix verification checks "does Save reflect the true
override" and not just "does the initial render."

**Marked INFERRED**: no save has actually been triggered mid-race and diffed against the
pre-race override row server-side — only the shared `pipelineAgents` source, read directly from
`handleSave`/`handleSaveAsOverride`, has been confirmed. What would confirm it: reproduce ISS-228's
race (delay `GET /api/user-workflows/{id}` or cold-mount `/workflows/{id}/run`), click "Save as my
version", then `GET /api/user-workflows/{id}` again and diff `agent_ids`/`manifest` against the
pre-save values.

## Test-writer follow-up (2026-08-28) — the predicted mechanism does not reproduce

Did exactly the confirming steps above: cold-mounted `/workflows/{id}/run` for the
`656ca387-e69c-474d-b7ff-5fd9eb017cc0` ("My prototype") fixture, clicked "Save as my version" as
the very next action (both manually via `browser_run_code_unsafe` and as an automated Playwright
assertion run with `--runxfail`), and diffed `GET /api/user-workflows/{id}` before and after. In
both checks the POST body and the persisted `agent_ids`/`manifest` stayed exactly
`["documentation-agent", "prototype-specify"]` — the save is correct, not clobbered. The `Advanced`
modal's own roster (`canvas-node-wrap-*` testids) also read `documentation-agent`/
`prototype-specify` after the same cold mount, and separately clicking the Advanced modal's own
"Save workflow" issued a `PATCH /api/user-workflows/{id}` (in-place update, correct `userWorkflowId`
binding) rather than creating a duplicate.

This does not necessarily mean ISS-228's underlying race is fixed — the visible "generic
NEW PROTOTYPE / no template selected" symptom ISS-228 describes still reproduces — but the specific
data-loss claim this card makes (that `pipelineAgents` ends up wrong at save time) was not
observed in three independent live checks. No test is shipped against this card for that reason:
see `tests/integration/e2e/suites/05_saved_workflows/test_iss228_launch_panel_override_binding.py`'s
module docstring. Recommend re-validating this card's mechanism before the 5-fixer spends time on
it specifically.
