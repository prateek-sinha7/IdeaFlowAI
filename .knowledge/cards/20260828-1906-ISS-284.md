## Reproduction (QA-KB-011, validated 2026-10-01, 3/3 cold)

Browser lane3, admin@velocity.ai, /create/prototype. Held the workflow-detail GET (`/api/workflows/<pipeline>`) with page.route so the override/agent load never resolved, clicked "Save as my version" (button not disabled: `isDisabled()` false in all 3 attempts; LaunchWizard.tsx:1403-1411 has no `disabled` prop), and aborted the resulting POST /api/user-workflows (nothing persisted). The captured body had `base_pipeline_type: "prototype"` and `agent_ids: []` — handleSaveAsOverride (LaunchWizard.tsx:949) sends `pipelineAgents.map(a => a.id)` without waiting for getWorkflowDetail (:508). Nuance: with the fetch held entirely the roster is empty, not the default roster; a partial load window would give the default roster. Either way an unloaded roster is persisted over the real override.

Evidence: evidence/qa-kb-011/01..06-validate-attempt{1,2,3}-*.png

## Analysis (QA-KB-011, 2026-10-01, analyzer)

**Verdict.** Real and unfixed at HEAD `024c03ef8`. `LaunchWizard` enables its save buttons from first paint, before the
async sources that decide the roster have landed, and the override save is destructive. The fix belongs in
`LaunchWizard.tsx` only (one shared component for all four modes and both routes); no backend change.

### Root cause (CONFIRMED: every line below was read)

One mechanism: `pipelineAgents` is treated as the authoritative roster from the first render, nothing models "the
roster is final", and every consumer of it is enabled from the first render.

1. The first roster is whatever the Redux agent library holds. `LaunchWizard.tsx:290`:
   `useState<AgentDef[]>(() => defaultAgentsFor(libraryAgents, initialMode))`. On a cold navigation the library is
   empty (its preload is dispatched on `signedIn`, `frontend/src/store/listenerMiddleware.ts:25-26`, `:59-61`), so the
   first roster is `[]`; on an in-app navigation it is the library default.
2. The real roster arrives later, from independent async sources: the override/plan overlay (`:491-567`;
   `getWorkflowDetail(token, pipeline)` at `:508`; the override roster is applied at `:552-558`,
   `if (proj.agents.length > 0) setPipelineAgents(proj.agents);`; the plan roster by the effect at `:472-486`) and the
   library-gated draft restore (`:395-441`; agents only `if (... && libraryAgents.length > 0)`, `:420`).
3. The consumers are enabled from first paint. "Save workflow" (`:1389-1397`) and "Save as my version"
   (`:1403-1411`) have no `disabled` prop; "Advanced" (`:1276-1285`) neither. Continue is
   `disabled={!canContinue || locked}` (`:1415`): brief and design system, not roster state.
4. The save handlers read the roster from React state at click time with no readiness check. `handleSaveWorkflow`:
   `agent_ids: pipelineAgents.map((a) => a.id)` (`:925`). `handleSaveAsOverride`: the same (`:966`), a `manifest`
   built from it (`:967-971`) and `overrides_pipeline_type: pipeline` (`:972`).
5. The server UPSERTS on that field and replaces the user's real row: `backend/app/api/user_workflows.py:794-834`
   (`prior.agents = json.dumps(sorted_ids)` `:813`, `prior.manifest_json = ...` `:816`,
   `prior.override_enabled = True` `:827`). There is no version or concurrency check.

So a click on "Save as my version" after the library has loaded but before the `getWorkflowDetail` overlay has landed
writes the system roster over the user's override. That is the destructive case.

### What the validator captured is not that payload (CONFIRMED by schema read and an offline run)

The validator's body had `agent_ids: []`. With the fetch held the library had not loaded either: the screenshots show
"Advanced 0 agents" and the global "Loading workspace..." toast
(`evidence/qa-kb-011/01-validate-attempt1-prototype-wizard-detail-get-held.png`, `02-...`).
`agent_ids: list[str] = Field(min_length=1)` (`user_workflows.py:213`, comment WR-02) rejects that body before any
handler runs. Run offline (`evidence/qa-kb-011/08-analyze-schema-empty-roster.txt`): `agent_ids=[]` is rejected
(422, "List should have at least 1 item"), a non-empty default roster is accepted and reaches the UPSERT. The
validator's POST was aborted, so its response was never seen; the schema says it would have been a 422 error banner,
not a saved row.

What the 3/3 reproduction proves: the buttons are clickable before the fetch settles. What it did not hit: the
destructive window (library loaded, detail still pending). Both are the same defect; the test must target the
destructive one.

### Why FIX-338 did not close it (CONFIRMED)

[FIX-338](20260828-2221-FIX-338.md) moved the emptiness test in the library effect (`:460-465`) into a functional
updater, which removed the same-commit ordering race between two effects. It did not add, and could not add, a
"settled" signal: it changes which write wins, not whether a click can observe a roster that is not yet final. Its own
card leaves this one "open and untested".

### The agreed minimal fix: accepted in shape, amended in three places

Accepted: a settle state owned by the `getWorkflowDetail` effect (reset where that effect resets its other state,
`:499-506`); both page-level save buttons disabled until it flips; the optional early returns in the two handlers
(cheap, and they cover any caller that is not the button).

Amended:

1. **Settle on SUCCESS for "Save as my version", not in `.finally`.** The effect's `.catch` (`:561-565`) swallows every
   failure and "degrades to no override", leaving the library roster on screen, which for a user who HAS an override is
   the wrong roster. A `.finally` would flip the flag after a failed GET and re-enable the UPSERT on a roster known to
   be unreliable: the same loss through a failed fetch instead of a slow one. Use a tri-state
   (`loading | ready | failed`) or two booleans. "Save as my version" needs `ready`; "Save workflow" (it creates a new
   row and never touches the override) needs only not-`loading`. On `failed` the override button stays disabled with a
   `title` saying why; a reload retries. The no-token early return at `:494` needs no special case (`authChecked` was
   set from a token one effect earlier, and a missing one means `handleSessionExpiry` is already redirecting); one line
   to set the state there is fine if the fixer prefers it.
2. **Also require `pipelineAgents.length > 0` on both save buttons.** `IdeaInputPage` already does (`:1950`, `:1965`).
   It closes the empty window (the validator's `[]`) on the client instead of leaving it to the server's 422 banner.
3. **Gate the "Advanced" trigger (`:1276-1285`) on the same state.** Otherwise the popup's footer "Save workflow"
   (`AgentsPopup.tsx:2964-2979` calling `handleSaveWorkflow` `:2718-2755`, `agent_ids: agents.map(...)` `:2736`) is a
   third Save button reachable before the flag flips, which keeps the bug title true through the popup. It also stops
   two INFERRED consequences of opening the popup early: the late overlay (`:557`) silently replacing an edit made in
   the window, and a stale Cancel snapshot (`AgentsPopup.tsx:2673-2680`: `stageEdit` snapshots the pre-overlay roster
   at the first in-popup edit; `:2705-2716`: Cancel re-applies it through `onReorder`, which is `handleReorderAgents`,
   `:750-752`) putting the default roster back after the flag has flipped, at which point the now-enabled "Save as my
   version" would persist it. [FIX-365](20260829-0045-FIX-365.md) is precedent that this window is reachable: its test
   opened Advanced 352 ms after `page.goto` and hit it in 2 of 3 runs.

Not part of this fix, deliberately: Continue. Gating it here would touch the launch path whose payload is pinned byte
for byte (`LaunchWizard.test.tsx` golden, `launchDraft.parity.test.ts`), and the override case is server-protected.
The draft-restore window (agents restore waits for the library, `:420`) is a separate async source with its own
consumer: [ISS-920](20261001-2221-ISS-920.md).

### Where the fix belongs

`frontend/src/components/workflow/LaunchWizard.tsx`, nothing else: one shared component, both call sites
(`[...view]/page.tsx:4101`, `workflow/create/page.tsx:48`), all four modes. Not `AgentsPopup` (shared with
`IdeaInputPage`; one gated trigger is a smaller diff than a prop threaded through two hosts). Not the backend:
UPSERT-by-built-in is the specified behaviour (spec 016) and the server cannot know the client was unsettled. The
change is generic and branches on no workflow or mode name (SC-001 / INV-1; the component header `:69-75` says so).

## Fixed (2026-10-02, QA-KB-011 fixer): [FIX-701](20261002-0037-FIX-701.md)
