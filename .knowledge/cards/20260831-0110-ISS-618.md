## What happened

`suites/21_run_families_and_versions` failed with its own message:

```
AssertionError: a family row appeared: 'Open Generate a small backlog for a
simple bookmark manager app: (latest version), completed'. Revised runs now
exist — write S-21-01, S-21-02 and S-21-03 against them.
```

This is not a defect. The module's docstring declared the premise and planted
the tripwire:

> **Every run in this database is a family of one.** … S-21-04 and S-21-11
> fail the day a family of two appears, which is the signal that the rest of
> this module can be written properly.

The [ISS-230](20260828-1805-ISS-230.md) fixture (root `77f74563`, one revision)
made it false, so the tripwire fired exactly as designed.

## What it broke, and why each one

- **S-21-04 / S-21-11** — the tripwires themselves.
- **S-21-05** — `chip_count` waited 30s for a `Presentation` chip that is not
  rendered at all: `WorkflowHistory.tsx` drops a type chip whose count is zero
  (`if (type !== "all" && count === 0) return null`). An absent chip IS a count
  of zero, not a broken selector.
- **`a_run()`** — picks the first completed row, which is now the family root;
  that row opens the family's LATEST member, which has a version timeline. That
  answers a different question from the one S-21-10/S-21-11 ask.

## Still open

The same discovery reaches six more tests in suites 04, 06, 07 and 13 — logged
as T3-01..T3-06 in `bug-hunter/open-bugs.md`. They were not fixed in this pass.

A separate finding, deliberately left open: the `"Workflow versions"` region
S-21-07/08/09 specify lives in `RunDetailPage`, which no user path mounts
(`WorkflowHistory.handleSelectRun` routes every tap to the shared run screen,
BUG-002; retiring the internal detail is the open INV-3 follow-up). Those three
scenarios are skipped with that reason recorded rather than written against a
surface the app never renders. Logged as T5-03.
