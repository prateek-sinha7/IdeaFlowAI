## What was wrong

The App Builder file explorer listed a markdown subheading from a generated README
(`### Via Node.js`, followed by a fenced JS sample) as a standalone project file: it appeared
in the Explorer tree, in the "N files" footer, in the code viewer with a bogus `js` highlight,
and it downloaded — individually and inside "Download ZIP" — as an extensionless file literally
named `Via Node.js`. Register entry `BUG-20260828-105300-preview-fullscreen-r2`, reproduced
3/3 cold-start cycles against the real `__app_preview__` payload.

## Root cause

`frontend/src/components/preview/PreviewPanel.tsx:92` — Format 2 of `parseAppBuilderFilesForIDE`:

```ts
const headerRegex = /###\s+([\w./\-@][^\n]*\.\w+)\s*\n```[^\n]*\n([\s\S]*?)```/g;
```

`[^\n]*` spans spaces and any other character, so a prose heading whose text merely contains a
dot-plus-word-chars substring ("Node.js") matches exactly as well as a real `### src/app.js`
path heading. Format 3's `boldRegex` (`PreviewPanel.tsx:99`) carries the identical character
class. The only file-shaped check downstream was `addFile`'s `hasDot = name.includes(".")`
(`PreviewPanel.tsx:66` pre-fix), which `"Via Node.js"` passes because of the dot in "Node.js",
not because it is a plausible path. The unvalidated entry then flowed verbatim into
`AppBuilderPreview.buildTree`, `CodeViewer.handleDownload` (`a.download = file.name`) and
`handleDownloadZip`.

The same parser exists as three independent, byte-for-byte forks — `PreviewPanel.tsx:46-105`
(`parseAppBuilderFilesForIDE`), `FilesTab.tsx:196-258` (`parseCodeFiles`, feeds the Results/Files
tab `project.zip`) and `WorkflowHistory.tsx:74-105` (`parseFilesForIDE`, feeds the reopened-run
IDE preview) — each with the same regexes and the same weak guard, so the defect was reachable
from three unrelated UI surfaces.

## What changed and why there

New leaf module `frontend/src/lib/parsers/filePath.ts`:

```ts
export function isPlausibleFilePath(path: string): boolean {
  return !/\s/.test(path);
}
```

A generated file path never contains whitespace; a prose heading nearly always does — the one
cheap signal that separates `src/app.js` from `Via Node.js`, and the guard the analysis
prescribed.

It is called from the ONE funnel each fork already had — the `addFile`/`add` closure that all
three formats (1: ```` ```filename: ````, 2: `###` heading, 3: `**bold**`) route through — so a
single line per fork covers every format and every downstream consumer (Explorer tree, footer
count, code viewer, per-file download, ZIP):

- `frontend/src/components/preview/PreviewPanel.tsx:66` (ISS-323, ISS-485)
- `frontend/src/components/results/FilesTab.tsx:224` (ISS-483, ISS-485)
- `frontend/src/components/history/WorkflowHistory.tsx:91` (ISS-484, ISS-485)

Guarding the shared `addFile` rather than tightening `headerRegex` also fixes Format 3, which
was never exercised by the hunted reproduction. The three forks were NOT consolidated into one
parser — their output shapes differ (`ParsedFile` with `language` vs. `FileItem` with icon/mime),
and that refactor is outside this fix's blast radius; the shared guard is the part that must not
diverge again.

## Note for the verifier

The 4-test-writer's fixture contained ONLY the phantom-producing markdown, so a correct fix left
zero files and `AppBuilderPreview` rendered its "No files generated yet" empty state — which broke
the test's own scaffolding assertion `getByText(/files$/)` at line 86, before the bug assertion was
ever reached. The FIXTURE (not any assertion) was extended with one real `### src/app.js` file
heading, restoring fidelity to the hunted deliverable, which listed three genuine `.md` files
alongside the phantom ("4 files" in the footer). Both original assertions are untouched.
