# FIX-636

Resolves [ISS-802](20260922-1638-ISS-802.md) (`BUGS.md#qa-ps-049` / `LEDGER.md`).

## What was wrong

Opening any agent in a run's Steps tab (`/runs/{id}/steps/{agentId}`) sent
`GET /api/runs/{id}/artifacts` twice, back to back, with identical 13.4 KB
responses.

## Root cause

`frontend/src/components/results/ArtifactVersionPicker.tsx:108-132`, the list-fetch
effect. Its `cancelled` flag was checked only after the response came back, so it
stopped a late `setVersions` but never stopped the request itself.

`next dev` runs React StrictMode, which mounts every new component, cleans it up,
and mounts it again, all in one synchronous block. In Next's bundled react-dom,
`commitPassiveMountOnFiber(...)` is followed directly by
`commitDoubleInvokeEffectsInDEV(priority)`
(`frontend/node_modules/next/dist/compiled/react-dom/cjs/react-dom-client.development.js:19946-19953`).
Each mount started its own async IIFE, both got past `await import("@/lib/api")`,
and both called `getRunArtifacts`.

## What changed and why there

One guard, `ArtifactVersionPicker.tsx:120`, directly after the dynamic import:

```tsx
const { getRunArtifacts, getToken } = await import("@/lib/api");
// ISS-802: StrictMode's dev remount runs this cleanup before the import
// resolves — bail here, or both mounts fetch the same list.
if (cancelled) return;
```

This works every time, not just most of the time. `await` always yields, and
React finishes the mount, cleanup and remount before any awaited code resumes. So
the discarded first mount always sees `cancelled === true` and returns before it
fetches. The second mount fetches once. Production builds have no double mount,
the flag is `false`, and nothing changes. As a bonus, a picker that unmounts
before its import settles (for example, when the user clicks quickly through
agents) no longer sends a request that would have been thrown away.

**Why here and not in `getRunArtifacts` (`frontend/src/lib/api.ts:1216`).** That
function has two production callers
(`grep -rn "getRunArtifacts" frontend/src`, excluding tests). The only other mount
effect that calls it is `WorkflowHistory.tsx:434-445`'s clarify-rounds effect, which
[ISS-835](20260922-2011-ISS-835.md) predicted would also fetch twice. The test-writer
disproved that, and I checked it again for this fix (see ISS-835's fixer section).
That effect runs on a later update, never on the first mount, so StrictMode's double
call does not happen there. The branch that triggers it also cannot be reached in the
running app. That leaves this effect as the only caller with the defect, and it is
the file ISS-802's `applies_to.globs` names. A single-flight map in `getRunArtifacts`
(the [FIX-616](20260922-1923-FIX-616.md) `inFlightWorkflows` pattern) would guard a
caller that already fetches once. It would also mean editing `api.ts`, which
QA-PS-048's cards ([ISS-800](20260922-1633-ISS-800.md),
[ISS-831](20260922-2003-ISS-831.md)) also cover, and another fixer may be editing it.

`ArtifactVersionPicker.tsx:152`'s click-driven `select()` fetch did not change. It
runs when the user clicks, not when the component mounts, and its own
`contentCache` ref already stops it from fetching twice.

## A test that points the wrong way — [ISS-852](20260922-2352-ISS-852.md)

The test-writer's `frontend/src/components/results/ArtifactVersionPicker.iss802.test.tsx`
can't catch this bug, and its result points the wrong way. It counts calls on a
`vi.mock("@/lib/api")` factory spy. Under vitest, the second concurrent dynamic
import of that module resolved to the **real** module, so the spy never saw the
second request. Before the fix it reported `Error: Expect test to fail` (the spy
counted 1 while 2 requests went out). After the fix it reports `1 expected fail`
(the spy counts 0 while 1 request goes out). **Do not remove its `.fails`.** If it
runs as a plain test, it fails against the fixed code. I did not edit it, and it is
not in any card's `test_files`. The test that does catch the bug is the new
`ArtifactVersionPicker.iss802.network.test.tsx`, which counts requests at `fetch`.
Details and the five always-failing `debug802*.test.tsx` probes are in
[ISS-852](20260922-2352-ISS-852.md).
