## Source

Derived (analyzer pass) from the root-cause investigation of `BUG-20260828-042900-handoff-invalid`,
recorded on [ISS-301](20260828-1740-ISS-301.md). **INFERRED** — not independently reproduced in a
browser; filed from source reading alone (tracing both call sites of `fetchSession` and the render
guard they share). See "What would settle it" below.

## This sibling

`fetchSession` (`frontend/src/components/handoff/HandoffWorkflow.tsx:73-148`) is invoked from TWO
effects, not one:

- The initial-mount effect (`:150-152`): `if (authToken && handoffToken) void fetchSession();` — runs
  once auth resolves, while `session` is still `null`.
- The post-completion re-fetch (`:186-192`): once the WS-driven pipeline reducer reports `state.done`,
  a `reFetchedRef`-guarded effect calls `fetchSession()` again "to pick up persisted state."

Both share the exact catch ISS-301 describes (`:143-145`):

```tsx
} catch (err) {
  setLoadError(err instanceof Error ? err.message : "Failed to load handoff");
} finally {
  setLoading(false);
}
```

`session` is only ever written on the SUCCESS path (`setSession(sess)` at `:79`) — nothing resets it
to `null` in the catch. So after the initial fetch has already succeeded (the agent panel, diff, and
PR strip are already on screen for a real running or just-finished pipeline), a transient failure on
the SECOND fetch still sets `loadError`, and the render guard at `:216` is:

```tsx
if (loadError || !session) {
```

an OR, not `!session` alone. A truthy `loadError` is sufficient by itself to enter this branch even
though `session` is still the valid, populated object from the first fetch — so the whole two-pane
running/completed view is replaced by the "Handoff not found" full-page state, discarding a session
that demonstrably still exists.

## Post-fix risk

A fix to ISS-301 that only changes what renders INSIDE the `if (loadError || !session)` block (e.g.
branching on error type to show "not found" vs. "couldn't reach the server, retry") does **not** fix
this sibling — the guard still fires on the second fetch's failure and still discards the in-progress
view. Both need the same change: the guard has to stop treating a REFRESH failure on an
already-loaded session as equivalent to a COLD-LOAD failure with no session yet. Whoever fixes
ISS-301's render branch should confirm `!session` takes priority over a stale `loadError` left over
from a later refresh, or file this as a still-open gap explicitly rather than assume the two are the
same fix.

## Expected vs actual (INFERRED, needs live reproduction)

**Expected:** once a handoff session has successfully loaded once, a later refresh failure (e.g. the
post-completion re-fetch hitting a network blip) should not discard the already-rendered agent
panel/diff/PR-strip view — at most a non-blocking retry affordance for the refresh itself.

**Actual (inferred):** the render guard treats ANY `loadError`, regardless of source, as sufficient to
replace the entire view with "Handoff not found," even when `session` is still populated from an
earlier successful fetch.

## What would settle it

Reproduce live: load a real handoff token to a running or just-completed state (so `session` is
populated and the two-pane view renders), then intercept `GET /api/handoff/{token}` to fail
(Playwright `route.abort('failed')`) right as `state.done` flips true (or by manually re-triggering
the re-fetch), and confirm the already-rendered view is replaced by "Handoff not found" rather than
staying on screen or showing a lesser inline notice.

## Fix

Same file as [ISS-301](20260828-1740-ISS-301.md), same render guard (`HandoffWorkflow.tsx:216`) —
not a separate call site. The guard should key off `!session` for the full-page not-found/network
state, and treat a `loadError` from a REFRESH where `session` is already populated as a non-blocking,
dismissible notice instead.
