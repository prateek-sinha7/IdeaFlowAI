# ISS-960

## What happened

INFERRED sibling of [BUG-024](20260827-BUG-024.md) (QA-KB-049): the same funnel, reached by a different producer. Not
reproduced in a browser.

BUG-024 is a cold load of a run URL. The funnel effect has no URL check at all, so it should also fire when the cold
load is of a route that is not a run, if something makes a generating run the VIEWED run. One thing does:

1. The tab owns the run. `page.tsx` seeds `launchedRunIdsRef` from `sessionStorage["tab_launched_run_ids"]`
   (`frontend/src/app/[...view]/page.tsx:694-705`), and every launch (`:4341`) and every reopened run (`:3052-3055`)
   adds its id and persists it.
2. On a reload, `refreshLiveRuns` auto-attaches every run in `AUTO_STREAM_STATUSES` that the tab owns
   (`frontend/src/providers/RunConnectionProvider.tsx:352-358`), and a first attach replays the whole durable log
   (`frontend/src/hooks/useRunStream.ts:77-79`, "Absent → full replay"), including `pipeline_start`.
3. `isForeignFrame` is false for a tab-owned id (`page.tsx:1539-1546`), so the frame reaches the store
   (`page.tsx:1579-1581`, `runStoreHandleFrameRef.current(frameRunId, msg)`).
4. `frontend/src/hooks/useRunStateStore.ts:455-457` adopts it as the viewport because nothing is viewed yet:

   ```ts
   if (msg.type === "pipeline_start" && viewedRunIdRef.current === null) {
     setViewedRun(runId);
   }
   ```

   and `:598-602` then projects it, so `displayedPipelineState` (`page.tsx:4158`) is a running state with a
   `pipelineRunId`.
5. The funnel fires: `DashboardLayout.tsx:830-832` sets `mainView` to `"execution"`, and `:854-856` pushes
   `/runs/{id}/stream`. The effect's own comment (`:847-849`) says it is "Kept unconditional (not gated behind the
   mainView check above)".

Condition: the same tab launched or opened run `R` earlier, `R` is still `running`, `planning`, `analyzing`,
`generating` or `revising`, and the tab is then reloaded on a route that is not a run URL.
Expected: `FR-003` and `SC-002` of spec 015 (`specs/015-frontend-routing/spec.md:130-131`, `:224-225`), reloading any
screen's URL restores that screen.
Actual (INFERRED): the reload lands on `/runs/R/stream`.

## Root cause (CONFIRMED by source read; the behaviour is INFERRED)

Two links. The funnel at `DashboardLayout.tsx:854-856` is the same one as BUG-024. The new link is the store's viewport
auto-set at `useRunStateStore.ts:455-457`, whose comment justifies it by "the very first run of the session" and the
async launch window, and which cannot tell a replayed `pipeline_start` from a live one.

## Not fixed by the root fix

The URL guard that fixes BUG-024 compares the incoming run with the run the URL names. On `/library` the URL names no
run, so the push still happens. This card needs its own decision, for example:

- push only for a launch, resume or revision started from this page instance (a ref set by those handlers), or
- stop `handleFrame` adopting a pipeline_start that arrives during the stream's `replaying` phase.

Either has to keep a fresh launch landing on `/stream` (FR-010) and the launch-window pre-registration at
`page.tsx:1425-1446` working.

## What settles it

Live tier: launch a run in a tab, then reload that tab on `/library` while the run is generating, and read the URL.
Offline alternative: a page-level vitest in the style of `frontend/src/app/[...view]/page.qaSg004.test.tsx` that seeds
`sessionStorage["tab_launched_run_ids"]`, mounts at `/library`, delivers a `pipeline_start` through the mocked provider,
and asserts `push` is not called with a `/stream` URL.

## After FIX-712 (2026-10-02)

[FIX-712](20261002-1155-FIX-712.md) added the URL guard at `DashboardLayout.tsx:854-857`. As this card says, the guard does not cover this producer.
On `/library`, `/runs` or `/dashboard` the URL names no run, so the guard still pushes. The card is still open. It
needs one of the two options above, and it has no test yet.
