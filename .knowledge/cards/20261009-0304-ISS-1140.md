# ISS-1140

**Register source:** sibling derived during the `QA-KB-106` analysis on 2026-10-09 (root [ISS-1137](20261009-0304-ISS-1137.md)). Not its own bug row. **INFERRED:** the code is
read, the screen was not driven. The last step of the chain below is the weakest link.

## Condition

A refused launch from a handler that registers a notification before the POST: `handleRunPipeline` (`DashboardLayout.tsx:1821`), the staged ppt and prototype launches
(`:1479`, `:1544`), chain (`:2024`), history re-run (`:2117`) and the clarify relaunches (`:2207`, `:2247`). Composer Run once and the revision handlers register none, so they are
not affected by this card.

## Why the root cause implies it

1. Each of those handlers sets `currentPipelineNotifId.current = notifId` (`:1477`, `:1542`, `:1809`, `:2019`, `:2112`, `:2203`, `:2243`) and calls `addRunningNotification(...)`
   before `onStartPipeline(...)`, for example `:1808-1821` then `:1841`.
2. The refusal reaches only the `page.tsx` `.catch`, which resets `pipelineState` and `launchPendingRef` (`page.tsx:4462-4463`). Nothing marks the notification: `markFailed`
   has two callers, the background-run transition (`DashboardLayout.tsx:803`, which needs a run id) and the terminal effect (`:988-992`, inside `if (... pipelineState.agents.length
   > 0)` at `:924`; a reset state has no agents).
3. Effects, by reading:
   - The notification stays `"running"`. `AppHeader.tsx:190-192` lists running notifications whenever the server list is not available (`hasServerData = recentRunsLoaded &&
     recentRuns.length > 0`, `:197`), so an account with no run history sees a pipeline running until a reload (`useNotifications.ts:44` drops running ones on hydration). The
     bell list itself filters running ones out (`DashboardLayout.tsx:2867`).
   - `currentPipelineNotifId.current` still points at it. The next run to start from a path that registers no notification of its own (composer Run once, revisions) is back-filled
     onto it (`:900-902`, `:1034-1045`), and the terminal effect then marks that id completed (`:954-961`) with the title of the refused brief: a completion toast naming the wrong
     run. This is the weakest link; it depends on the order of three effects that were read, not run.

## Expected vs actual

- **Expected:** a refused launch leaves no "running" notification (or a failed one), and no later run is attributed to it.
- **Actual (derived):** it stays running, and may be reused.

## What settles it

In a browser with a POST-only `/api/runs` stub: refuse a launch from `/create/user-stories`, then check the header's running badge on an account with an empty run history. Then
remove the stub, launch a Run once on a canvas and compare the completion toast's title with the refused brief.

## Where the fix belongs

In the refusal path of the same outcome handler as the root: mark failed (or remove) the notification the launching handler created, whose id is `currentPipelineNotifId.current`
at that moment, and clear the ref and its companion `currentPipelineNotifRunId`. Not in each of the seven launching handlers.

## After [FIX-773](20261009-0952-FIX-773.md) (2026-10-09): still open

[FIX-773](20261009-0952-FIX-773.md) does not touch the notification. The refusal now shows a banner, but the running notification and `currentPipelineNotifId` are
left as this card describes. `onStartPipeline` now resolves the run id or `null` and never rejects, so a launching handler can now see
the refusal and mark its own notification failed.
