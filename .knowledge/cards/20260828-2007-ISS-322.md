## What happened

The app has a working return-path mechanism: a **signed-out** user deep-linking a protected
route is sent to `/login?redirect=%2F<path>` and, after signing in, correctly returned to that
exact route (`routes.login`/`resolveRedirectTarget` in `frontend/src/app/login/page.tsx`). But
when a session expires **mid-session** on a protected route — the 401 ladder auto-redirecting an
already-signed-in user — that mechanism is bypassed entirely: no `redirect` param is ever
attached, and after signing back in the user unconditionally lands on `/dashboard`, losing the
page they were actually on.

Confirmed **CONFIRMED, 3/3, cold start every cycle** (fresh navigation to
`/settings/ai-model`, `auth_token` corrupted in `localStorage`, then a fresh re-navigation to the
same URL to trigger the 401 ladder — not a soft re-click):

- **Cycle 1:** fresh nav to `/settings/ai-model` (loads normally) -> corrupt `auth_token` ->
  fresh re-nav to `/settings/ai-model` -> redirected to `/login?expired=true`, no `redirect`
  param -> signed in as qa-admin -> landed on `/dashboard`, not `/settings/ai-model`.
- **Cycle 2:** identical steps, fresh browser navigation each time, same corrupted-token value
  varied per cycle -> same `/login?expired=true` with no `redirect` param -> same `/dashboard`
  landing after re-login.
- **Cycle 3:** identical steps again -> same failure. Screenshot captured:
  `bug-hunter/evidence/login-expired-true/BUG-20260828-101500-login-expired-true-r2/_scratch/cycle3-expired-no-redirect.png`.

## Expected vs actual

- **Expected:** a mid-session expiry on a protected route preserves that route the same way the
  signed-out deep-link guard does (`?redirect=%2F<path>`), so re-authenticating returns the user
  to what they were doing.
- **Actual:** the 401-triggered redirect to `/login?expired=true` never attaches a `redirect`
  param. Signing back in always lands on `/dashboard`, discarding the original route, even though
  the identical `resolveRedirectTarget`/`?redirect=` mechanism on the very same login page works
  correctly when the user was signed out to begin with.

## Root cause

`frontend/src/lib/api.ts:147` — the shared "session genuinely expired" side effect (documented at
lines 131-142 as reused by the API 401 handler, the fetch-based handler, and the WebSocket
JWT-expired close handler) does:

```ts
window.location.href = routes.login({ expired: true });
```

`routes.login` (`frontend/src/lib/routes.ts:25-27`) only ever accepts `{ expired?: boolean }` — it
has no parameter for the current path, so it can never build a `redirect` query string. Contrast
with the signed-out guard (`frontend/src/app/[...view]/page.tsx`'s auth-check-on-mount, per
ISS-191's investigation) which builds `?redirect=%2F<path>` before sending an unauthenticated user
to `/login`. `login/page.tsx` itself already reads and uses `redirect` correctly on arrival
(`resolveRedirectTarget(searchParams.get("redirect"))`, lines 51 and 63) — the login page is not
the broken half; the call site in `api.ts` that never supplies the param is.

Because the redirect is a hard `window.location.href` navigation (not a router push), the current
path is still available in `window.location.pathname` at the moment this line runs — it is simply
never read and forwarded.

## Blast radius

Single call site: `frontend/src/lib/api.ts:147` is the one place `routes.login({ expired: true })`
is invoked for the mid-session-expiry path (shared by the API 401 handler, fetch handler, and
WebSocket JWT-expired close handler per the comment at lines 131-142), so every entry route hits
the same bug — confirmed here on `/settings/ai-model`, and the underlying register entry also
confirms it independently on `/runs/<id>/workspace`.

## Proposed fix — where it belongs

Extend `routes.login` to optionally accept a `redirect` param (mirroring the signed-out guard's
own `?redirect=%2F<path>` construction), and have `frontend/src/lib/api.ts:147` pass
`window.location.pathname + window.location.search` as that param when it builds the expired-login
URL. This is a one-line addition at the single call site plus a signature extension to an
already-shared route builder — no new abstraction, reusing the exact `resolveRedirectTarget`
mechanism `login/page.tsx` already implements and trusts (internal-path allowlist, open-redirect
guarded).
