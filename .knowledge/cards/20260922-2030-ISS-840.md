## Root cause — a remount-proof guard built out of a useRef

`frontend/src/app/[...view]/page.tsx:3453-3552` is the deep-link reopen effect:
for any `/runs/{id}*` URL it calls `handleSelectWorkflowRun({ id: runId })`,
which fetches the run, its full durable event log and (for the chat seed) its
revision family. It is supposed to skip that work when the run is already open:

```
page.tsx:3457   // Already loaded/loading — a click-driven open (once T9 lands), a live
page.tsx:3461   // client-side nav from /runs from double-fetching (AC3).
page.tsx:3462   if (runId === trackedRunIdRef.current) {
```

`trackedRunIdRef` is a `useRef` **owned by this page component**, and the click
that opened the run ends in `router.push("/runs/{id}")`, which remounts that
component. The file states this itself, 20 lines further down:

```
page.tsx:3480   // T6 (retry — V2 attempt 8 regression, FR-001/FR-003): T9's router.push
page.tsx:3481   // remounts THIS page component (Next.js does not preserve a dynamic-route
page.tsx:3485   // The remount wipes the local trackedRunIdRef back to null even though
page.tsx:3488   // this exact run is already being actively driven by this tab.
```

So on a history click the guard is evaluated against a fresh `null` ref and
always misses. The `runConnection.liveRunIds` branch at `:3499` — the one thing
that does survive the remount — only covers runs this tab is streaming, and it
deliberately falls through to the full `handleSelectWorkflowRun` anyway
(`:3505` "do NOT return early here", FIX-298c). A **completed** run opened from
history is in neither set, so the entire reopen runs a second time.

Measured after the click, per mechanism (FIX-624 already in place):

| request | count | why |
|---|---|---|
| `GET /api/runs/{id}` | 2 | one per `handleSelectWorkflowRun` invocation |
| `GET /api/runs/{id}/events?after=0` | 2 | same |
| `GET /api/runs/{id}/family` | 4 | 2 call sites ([ISS-804](20260922-1646-ISS-804.md)) x 2 invocations |
| `GET /api/runs/{id}/events?after=150` | 2 | the post-replay catch-up, once per invocation |

This is the multiplier behind [BUGS.md#qa-ps-038](../../BUGS.md#qa-ps-038)'s
"`/events` x2 — 7.7 MB" row, which ISS-785 attributes to the revision-family
seed alone.

## Fix direction (not applied — needs the 3-analyzer's blast radius)

[ISS-780](20260922-1604-ISS-780.md) already hit and solved the identical
problem for the *switch* path: "the in-flight guard for a run switch cannot live
in a useRef ... these two live at module scope — outside the component — so a
claim survives the remount the switch causes" (`page.tsx:96-121`,

ISS-779/780's stale-switch checks) and must not be re-derived from this card
alone.

## Analysis 2026-10-07 (3-analyzer, QA-KB-067)

Line numbers are the current tree; `page.tsx` has grown since the sections above
were written (the T7 guard is now `:3474`, its reopen `:3554`). CONFIRMED means a
line I opened; INFERRED says what would settle it.

### The duplicate to remove is the click's, not the effect's

CONFIRMED. The first half of the root cause above stands: the effect's guard reads
a fresh `null` after the push remounts the page (`page.tsx:3474`; remount stated
at `:3494-3499`), and a terminal run is never in `runConnection.liveRunIds`
(`handleSelectWorkflowRun` attaches only non-terminal runs, `:2993`; the set is
`union(autoIds, focusedRunId)`, `RunConnectionProvider.tsx:276-298`), so the
effect falls through to `handleSelectWorkflowRun({ id: runId })` (`:3554`).

What the sections above do not say is which of the two reopens is the redundant
one. It is the **click-time** one:

- Instance A, the page that handled the click, runs `onSelectWorkflowRun?.(run)`
  un-awaited and then `router.push(...)` in the same tick (`DashboardLayout.tsx:3005`,
  `:3065`). A's call starts its fetch chain; A is then unmounted.
- Nothing A writes afterwards lands. Every output of `handleSelectWorkflowRun` is a
  page-local setter (`setContentSourceRunId` `:2940`, `setUserStoryContent` to
  `setGenericDeliverable` `:2943-2946`, `setSubmittedBrief` `:3034`,
  `seedRunChatTranscript` `:3244`), and the run store hands an unmounted page a
  throwaway entry: `useRunStateStore.ts:399`
  `if (!mountedRef.current) return makeInitialRunState(runId);`, under the comment
  "A reopen click starts a replay here and then router.push remounts; the new page
  replays the same run" (`:395-398`). On unmount the store also deletes every
  finished run's entry (`:337-347`: "A finished run is rebuilt from its durable log
  when reopened").
- Instance B, the remounted page, runs the effect's call, and it is the only one
  whose writes reach the screen.

So the sketch in BUGS.md (a module-scope `reopenClaimRunId`, the effect returning
early when it matches) is wrong: it would make B skip its reopen and leave the new
page with empty state, the failure T6/T7/T11 exist to prevent (`:3631-3639`) and
the lesson [FIX-632](20260922-2221-FIX-632.md) recorded for this same remount:
"the guard and its data move together". INFERRED (not run) that the visible result
is a run shell with no data.

### Why nothing downstream collapses the two calls

CONFIRMED. `getWorkflow` and `getRunFamily` use `singleFlightGet`
(`api.ts:686-698`), whose entry is deleted when the request settles
(`.finally(() => inFlightGets.delete(key))`), so the click-time call and the
post-remount call, separated by Next's navigation latency, both reach the network.
That is why the validator still sees `GET /api/runs/{id}` x2 after ISS-830/831.
`getRunEvents` has no dedupe at all (`api.ts:1463-1471`).
`beginSwitchGeneration` returns the same generation for a re-claim of the same run
(`page.tsx:105-116`), so neither call is stale against the other and both run to
completion (`:2976`, `:3073`).

### Blast radius

| `:3471-3484` | completion toast (cached or fetch-then-open) | `runStream` | T11 |

The validator's reproduction (`evidence/qa-kb-067/01..03`, header "Back to runs") is
the `:3065` row through T7. The BUGS.md repro steps cite `:2848` (header, T11), a
different effect with the same flaw, filed as [ISS-1076](20261007-2141-ISS-1076.md).
The version-picker variant, where [ISS-856](20260923-0028-ISS-856.md)'s record
hand-over reaches only the destroyed instance, is
[ISS-1075](20261007-2141-ISS-1075.md).

Non-terminal runs are doubled too: T7's `liveRunIds` branch deliberately falls
through to the full reopen (`:3513-3534`, FIX-298c) and T11's fast path replays
events and family itself (`:3653`, `:3687`). The second pass is required there,
because the remount wiped page state; the duplicate is again the click-time one.

Not affected: cold mount or hard refresh of `/runs/{id}*` (one call, B's); shallow
tab clicks and back/forward on one instance (T7's early return `:3474-3492` is right
for those and must stay); live switches that `await onSwitchToLiveRun` before
pushing ([FIX-621](20260922-2009-FIX-621.md)).

### Where the fix belongs

The click-to-push hand-off, not T7/T11's guards (they are correct for the
same-instance cases they were built for). `handleSelectWorkflowRun` stays the single
networked opener, called from the effects (`:3554`, `:3772`) and its own retry
(`:3369`); a click that pushes a remounting URL must stop calling it.

1. Smallest: hand DashboardLayout a click-time function that does not fetch instead
   of `handleSelectWorkflowRun` (`page.tsx:4428`), and drop the two fetch-then-open
   variants (`DashboardLayout.tsx:2916-2924`, `:3475-3478`), whose `getWorkflow`
   exists only to feed the click-time call. Or delete `onSelectWorkflowRun?.(run)`
   at the sites above. A sync-only prime (viewport switch plus loading flag) keeps
   the skeleton [FIX-606](20260922-1811-FIX-606.md) shows during navigation; it must
   not set `contentSourceRunId`, because that fires DashboardLayout's family effect
   (`:741-746`) in the doomed instance and costs one `/family`.
2. If the click-time head start must stay: carry the fetched data across the
   remount in a module-scope, token- and run-keyed memo beside `switchGeneration`
   (`page.tsx:102-103`), the FIX-632 pattern. Larger diff: it rewrites fetch points
   that `page.qaSg004.test.tsx` and `page.iss856.test.tsx` source-lock, and it is
   what [ISS-1075](20261007-2141-ISS-1075.md) needs.

Do not: (a) the BUGS.md sketch above; (b) make `appliedRunViewKeyRef` module-scope
(`runViewEffects.qaSg004.source.test.ts` locks it per-mount, [FIX-635](20260922-2335-FIX-635.md));
(c) special-case "completed runs only", since live runs are doubled too; (d) bump
the switch generation on unmount: under StrictMode the simulated unmount would stale
the first cold-mount reopen while `appliedRunViewKeyRef` makes the second effect run
bail (INFERRED); (e) put a TTL on `getWorkflow` or `getRunEvents` in `api.ts`: other
callers refetch to watch a live run (`api.ts:674-683`).

## Fix 2026-10-07 (5-fixer, QA-KB-067)

Fixed by [FIX-753](20261007-2216-FIX-753.md), using fix shape 1 above. `page.tsx` now passes
`DashboardLayout` a synchronous `primeRunOpen` as `onSelectWorkflowRun`, in place of `handleSelectWorkflowRun`.
`primeRunOpen` makes no fetch: it claims the switch generation, switches the viewport and sets the loading flag.
The two fetch-then-open variants in `DashboardLayout.tsx` (bell, toast) lost their `getWorkflow`. The remounted T7
or T11 effect does the one reopen. The analysis above held on re-check; no part of it was re-derived.

One case it did not cover: a push to the URL already on screen does not remount. For that case `primeRunOpen`
returns early when the URL already names the run, because a loading flag set there would never clear.

Observed after the fix: `test_qa_kb_067_history_click_reopens_once.py` reported XPASS(strict), and 1 passed under
`--runxfail`. A probe measured 1 / 1 / 2 (`GET /api/runs/{id}` / `events?after=0` / `/family`) for the History
row. Evidence: `evidence/qa-kb-067/04-fix-after-*.png`. The full numbers are in FIX-753.
