# ISS-1147

**Register source:** sibling derived during the `QA-KB-108` analysis on 2026-10-09 (root [ISS-1144](20261009-0725-ISS-1144.md)). Not its own bug row.

**Confidence:** the mechanism is CONFIRMED offline, row C of `evidence/qa-kb-108/04-analyze-sibling-probes-output.txt`: for all three endpoints `app.core.cognito.admin_get_user` patched to raise `TokenRetrievalError` gives 500 with no `access-control-allow-origin`, and the `ClientError` control gives 503 with it. INFERRED: the on-screen result (browser not driven) and the half-enrolled state described under "Condition".

## Condition

- `POST /api/auth/mfa/totp/verify`, `POST /api/auth/mfa/email/enable`, `POST /api/auth/mfa/email/disable` while the backend's AWS credential chain cannot be resolved.
- Why these three and not the other MFA calls: their last step, `apply_mfa_preference` (`backend/app/core/cognito.py:630-701`), begins with `current = get_confirmed_mfa_factors(email)` (`:666`), which is `admin_get_user(email)` (`:579`), a SigV4-signed operation. The write that follows, `set_user_mfa_preference`, is unsigned (`evidence/qa-kb-108/06-analyze-botocore-service-model-auth-types.txt`: `auth_type='none'`). So the credential failure arrives from the read, inside handlers that catch `ClientError` only (`auth.py:849`, `:947`, `:1014`).
- `verify_totp` (`auth.py:835-860`) runs the unsigned `verify_software_token` first and `apply_mfa_preference` second in one `try`. With an expired session the code is accepted, the preference write never happens, and the user sees an error. Per the endpoint's own docstring (`:827-833`) a verified device is not used at sign-in until it is set preferred, so this leaves a verified-but-unused device (INFERRED; the same applies to a `ClientError` at that step, but there the user at least gets the 503).

## Expected vs actual

Expected: 503 `Authentication service unavailable` with CORS headers; `SecuritySection.describeError` prefers a string `err.detail` (`frontend/src/components/settings/SecuritySection.tsx:50-62`). Actual: 500 with no CORS header, `fetch` rejects with a non-`ApiError`, and the section falls back to its generic string.

## Why the root cause implies it

Same narrow `except ClientError`, and a signed call hidden one layer below the handler, which is why this is easy to miss when reading `auth.py` alone. The same file already shows the right behaviour for the same condition: `GET /mfa` wraps `get_confirmed_mfa_factors` in `except Exception` and degrades (`:901-905`; probe row C last line: 200 with CORS headers), and `disable_email_mfa` wraps `has_confirmed_totp` in `except Exception` and answers 503 (`:985-1000`).

The admin MFA gate is not affected: `enforce_admin_mfa` makes no Cognito call (`backend/app/core/identity.py:277-281`).

## Fix direction (INFERRED, not applied)

Route `BotoCoreError` into the existing 503 fall-through of each handler (shared symbols in [ISS-1144](20261009-0725-ISS-1144.md)). Keep `verify_totp`'s two failure meanings apart: `CodeMismatchException` and `EnableSoftwareTokenMFAException` stay 400.

## Test notes

Patch `app.core.cognito.admin_get_user` (not the `auth` module's name; `get_confirmed_mfa_factors` looks it up in `cognito`'s globals) with `side_effect=TokenRetrievalError(...)`. For `totp/verify` also patch `verify_software_token` to return `"SUCCESS"`. For `email/enable` set `settings.AUTH_EMAIL_MFA_ENABLED = True` or it answers 409 first. Override `get_current_user_with_payload`; send `Authorization: Bearer x` and an `Origin`. Assert 503 + string `detail` + CORS header, plus the `ClientError` control. Runnable form: `evidence/qa-kb-108/04-analyze-sibling-probes.py`.
