## Symptom

Sibling branches of one gate are laid out END TO END along x instead of side by
side. Each branch starts where the previous finished, so the canvas is roughly
2.4x wider than needed and nothing aligns by depth.

Measured on the 14-node / 5-gate case
(`/workflows/dc8ecf6a-5ca2-4f9c-bef7-ac0ddee56279/edit`):

```
x=314  t1, m1, l1, DUTCH   <- triage's fan, correct
x=417  t2                  <- tiny branch
x=520  t3
x=624  mgate               <- should share x=417 (m1's successor, same depth as t2)
x=830  lgate               <- should also share x=417
x=933  sgate, lm
x=1037 sa, sb, DUTCH
```

## Root cause

`graphLayout.ts:49`, "Add chain edges (each agent routes to the next)":

```js
for (let i = 0; i < pipelineAgents.length - 1; i++) {
  outEdges.get(pipelineAgents[i].id).add(pipelineAgents[i + 1].id);
}
```

Array neighbours are NOT necessarily connected. With steps stored as
`[intake, triage, quick-fix, done-simple, analyze, depth, ...]`,
`done-simple -> analyze` is fabricated — `analyze` is a route target of
`triage`, reached by the `complex` outcome. That invented spine forces rank to
increase monotonically along the array, which reproduces exactly the
"column = array index" behaviour Sugiyama phase 2 is supposed to eliminate
(see [ADR-0025](20260825-1115-ADR-0025.md)).

`hasOutcomesAt` (`graphLayout.ts:133`) is a SECOND hack layered on top: it
bumps every node at any rank a gate's outcomes occupy, which is why two nodes
at the same graph depth end up in different columns.

## Fix direction

Feed layer assignment the REAL edge set. The predicate already exists in
`CanvasView.tsx` — `hasChainEdge(i)` already knows a chain edge is absent when
the node is detached, is a route target, or its predecessor branches away. Use
that plus the route outcomes, and `hasOutcomesAt` should delete itself:
correct ranks then fall out of longest-path with no compensation.

This needs no product decision — the correct edge set is fully determined by
existing code.

## Note

Fixing this will move every coordinate, so the no-overlap invariant must be
re-verified live afterwards (see [FIX-297](20260825-1115-FIX-297.md) for the
measurement method). Overlap-freedom today does not predict overlap-freedom
after a rank change.

## Resolution (2026-08-25)

Three changes in `graphLayout.ts`, all verified live:

1. **Real edge set.** Chain edges are added only where `hasChainEdge(i)` holds
   — the predicate mirrors CanvasView's, so the drawing and the ranking agree
   by construction. Array adjacency alone is no longer treated as an edge.
2. **`hasOutcomesAt` deleted.** It only ever compensated for the fabricated
   edges. Column is now the topological rank directly.
3. **Two ordering fixes surfaced by the above**, both genuine gaps rather than
   regressions:
   - non-fan nodes inherit their chain predecessor's row, so each branch keeps
     its own lane (degenerate median alignment — one neighbour IS the median).
     Without it every non-fan node kept `row: 0` and the branches collapsed
     onto one lane once the ranks were right;
   - **Sugiyama phase-4 compaction per layer**: fans are placed per-gate, which
     guarantees no collision INSIDE a fan but says nothing about two gates
     whose fans share a column. One ordered top-to-bottom sweep per column
     enforces `top(i) >= top(i-1) + h(i-1) + ROW_GAP`. Pushes down only, single
     pass — not a nudge-until-clear loop.

Fan placement also had to move to RANK order: a gate's fan centres on the
gate's own row, which may itself be inherited, so array order placed fans
against the `row: 0` default.

Result on the 14-node / 5-gate case: columns are now true depth
(`t1,m1,l1` share one, `t2,mgate,lgate` share the next), width fell from ~2250
to 938, and overlaps went 9 -> 6 -> 2 -> **0**.
