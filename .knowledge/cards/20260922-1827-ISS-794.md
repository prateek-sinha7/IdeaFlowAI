# ISS-794

## Description

Confirmed for bug **QA-PS-044** (see `LEDGER.md` / `BUGS.md#qa-ps-044`).
Every cold load of `/create/ppt` fires duplicate API GETs: `GET
/api/auth/me` ×3, `GET /api/workflows` ×2, `GET /api/runs?limit=50` ×2 —
plus an app-wide preload of `/api/agents/library`, `/api/skills/library`,
`/api/hooks/library`, and `/api/runs?limit=6` that has nothing to do with
the PPT wizard.

## Reproduction (3/3, cycle 1)

3/3 cold-start cycles, each: navigate to `about:blank`, then
`http://localhost:3000/create/ppt` (already signed in as
`qa-admin@flowinqa.com`), wait 3s, read
`performance.getEntriesByType('resource')` (the MCP network-request log does
not reset across same-origin navigations in this environment — same
constraint noted in ISS-784).

- Cycle 1: 87 resource entries, `auth/me` ×3, `workflows` ×2, `runs?limit=50`
  ×2, `runs?limit=6` ×1, `agents/library` ×1, `skills/library` ×1,
  `hooks/library` ×1
- Cycle 2: 88 entries, identical duplicate pattern
- Cycle 3: 89 entries, identical duplicate pattern

100% reproducible, not intermittent — every cycle produced the same
duplication, so no axis-narrowing was needed.

Evidence: `evidence/qa-ps-044/01-validate-attempt1-create-ppt-loaded.png`,
`evidence/qa-ps-044/02-validate-attempt2-create-ppt-loaded.png`,
`evidence/qa-ps-044/03-validate-attempt3-create-ppt-loaded.png`.

## Root cause

`frontend/src/app/[...view]/page.tsx:879-892`:

```tsx
useEffect(() => {
  const storedToken = getToken();
  if (!storedToken) {
    router.replace(buildLoginRedirect());
    return;
  }
  setToken(storedToken);
  setIsAuthenticated(true);
  dispatch(signedIn({ token: storedToken }));
  getMe(storedToken)
    .then((u) => { setUser(u); dispatch(userLoaded(u)); })
    .catch(() => { /* tier defaults to "basic" */ });
  ...
```

A mount-only effect with no StrictMode double-invoke guard, matching the
pattern already documented in ISS-784. `next dev` (Turbopack, confirmed via
running process) runs every effect mount → unmount → remount once, so
`dispatch(signedIn(...))` and `getMe(storedToken)` each fire twice per cold
load. `getMe` doubling explains 2 of the 3 `auth/me` calls; the third comes
from `LaunchWizard`'s own independent tier/auth fetch (the wizard is a
standalone component, not a DashboardLayout child — see below — so it does
not share the page-level `user` state and fetches its own copy).

The doubled `signedIn` dispatch reaches
`frontend/src/store/listenerMiddleware.ts:22-66`, whose `signedIn` listener
guards on `state.global.workflowsStatus !== "loading" && !== "succeeded"`
before dispatching `fetchWorkflows`/`fetchRecentRuns` — but the listener's
`effect` runs async per action, so both StrictMode-doubled `signedIn`
dispatches can read `"idle"` before either thunk's `pending` reducer has
committed, racing past the guard and firing `fetchWorkflows` /
`fetchRecentRuns` twice. This is the same race shape as ISS-784, but that
card scoped its evidence and globs to `/dashboard` and blamed
`HomeLaunchGrid.tsx`'s own `analytics/summary` effect specifically. The
mechanism found here is upstream of that: `page.tsx`'s auth-check effect is
the ONE place `signedIn` is dispatched
(`frontend/src/app/[...view]/page.tsx:892` — the only call site, verified by
`grep -rn "dispatch(signedIn" frontend/src`), and it runs on every route
`[...view]/page.tsx` handles, `/create/ppt` included — this is broader than
ISS-784's dashboard-only framing, so it is filed as its own card rather than
folded into ISS-784.

The `agents/library`, `skills/library`, `hooks/library` and `runs?limit=6`
calls are a SEPARATE, likely-intentional behaviour, not part of the
duplication defect: `listenerMiddleware.ts:18-21`'s own comment says the
`signedIn` preload exists so "agents/skills/workflows are already in the
store by the time the user opens the Library or catalog tabs" — an
app-wide warm-cache decision (referenced as ISS-232 in that file), not
scoped to `/dashboard`. It fires on `/create/ppt` because `signedIn` is
dispatched from the shared `[...view]/page.tsx`, not because any
home/dashboard component is mounted underneath the wizard.

## Reporter's theory investigated and NOT confirmed

QA-PS-044 attributed the extra traffic to `DashboardPage` /
`HomeLaunchGrid` mounting underneath `LaunchWizard` and claimed 228 total
requests / 8.9 MB. Neither reproduced:

- `frontend/src/app/[...view]/page.tsx:4008` returns `<LaunchWizard
  initialMode={wizardMode} />` as a bare, standalone return — the
  surrounding comment (T6, spec 015-frontend-routing) states this is
  deliberately "outside DashboardLayout", the fix for the exact
  dual-mount failure mode the reporter describes.
- DOM check after each of the 3 cycles: `document.querySelectorAll('div.cursor-pointer.p-4').length === 0`
  (the card selector `velocity.json` documents for the home/library grid) —
  zero home-page cards ever render under `/create/ppt`.
- Measured totals across all 3 cycles: 87-89 `performance.getEntriesByType('resource')`
  entries, 1.7-2.7 MB `encodedBodySize` — not 228 requests / 8.9 MB.

The reporter's DevTools capture likely accumulated across more than one
load or interaction (the same caveat ISS-784 recorded for its own report's
4× vs the validated 2×). The real defect is the duplicate-GET pattern
above, not a structural dual-page mount.

## Expected vs actual

- Expected: `auth/me`, `workflows`, `runs?limit=50` each fire once per
  `/create/ppt` load; `agents/library`/`skills/library`/`hooks/library`/
  `runs?limit=6` are either accepted as intentional warm-cache preloads or
  scoped away from wizard-only routes (product decision, not covered here).
- Actual: `auth/me` ×3, `workflows` ×2, `runs?limit=50` ×2, every load.

## TEST COVERAGE — ISS-794

Manual verification only (no test suite exists for this mount-fetch path).
Verified via `performance.getEntriesByType('resource')` across 3
independent cold-start cycles, all three showing identical duplication.
