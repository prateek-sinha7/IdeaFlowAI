# ISS-1118

**Register source:** a consequence of [FIX-766](20261008-1444-FIX-766.md) (QA-KB-100) that the analysis predicted
([ISS-1092](20261007-2308-ISS-1092.md) re-analysis, "Regression surface"; [ISS-1112](20261008-1415-ISS-1112.md) "Traps"). It is
recorded so the UX decision is not lost when those cards close.

**Confidence:** CONFIRMED for the backend refusal. The eight built-ins' own raw steps are refused at `trust="user"`
(`evidence/qa-kb-100/analysis-04`), and since FIX-766 every override writer runs that check. INFERRED for the client: the canvas
was not driven. Its serializer was read.

## Condition

- `IdeaInputPage.tsx:1225` seeds the canvas from the built-in's `manifest_steps`. `agentToManifestStep`
  (`frontend/src/store/api/userWorkflows.ts:291` onwards) spreads `agent.extra` first, which holds every step key the canvas does
  not model, and then `...agent.tools`. So "Save as my version" (`IdeaInputPage.tsx:1826`, `overrides_pipeline_type: workflowId`)
  sends those keys back unchanged.
- Under `trust="user"`, `analysis-04` refuses the raw steps of `app_builder` (`post_step: api_prefix_audit`); `prototype`,
  `prototype_feature_revision` and `prototype_large_revision` (`compaction: html_skeleton`); `prototype_revision`
  (`post_step: revision_validation`); and `sample_fanout`, `sample_subagents_parallel` and `sample_wave` (`spawn_subagents`).
- Before FIX-766 such a save answered 201 and the override ran those engineer-only capabilities at `trust="db"`. Since FIX-766 the
  save answers 422 `invalid workflow override (...): capability ('post_step', 'api_prefix_audit') is not user-allowed ...`.
  An already-stored row of that shape runs the file plan, and its customisations stop applying. A read-only SELECT on the dev DB
  found 0 override rows (`evidence/qa-kb-100/fix-12`).
- The wizard's override save (`LaunchWizard.tsx:1036-1062`) uses the same `buildWorkflowManifest`. The analysis INFERRED that its
  `pipelineAgents` are library agents without `extra`, so it is not affected. Not driven.

## Decision needed

For a built-in whose own steps use engineer-only capabilities, what should "Save as my version" on the canvas do?

- **a) Strip.** The canvas drops the keys that are not user-allowed (`post_step`, `compaction`, `hooks` outside the allow-list,
  privileged `tools` grants) before an override save, and tells the user what was dropped. Consequence: the save succeeds, and the
  user's version runs without those capabilities. For `prototype` that means no `html_skeleton` compaction, which may change
  build quality.
- **b) Keep the 422.** Those built-ins cannot be overridden from the canvas. Consequence: no silent capability loss; the user
  sees the compiler's reason. This is the safe default FIX-766 ships.
- **c) Mark per capability.** Register specific capabilities `user_allowed=True` if they are safe for user-authored steps (for
  example `html_skeleton` compaction). Consequence: a registry change, reviewed one capability at a time against
  [ADR-0044](20260901-0324-ADR-0044.md).

## After the decision

a) is a frontend change in `agentToManifestStep`, or in a filter used only by the override save, with a Vitest case. b) closes
this card as accepted. c) is a registry change per capability, with the unit matrix in `tests/unit/test_workflow_override.py`
extended.

## Analysis (QA-KB-103, 2026-10-08, analyzer, worktree HEAD 135e6ea9b)

Bug row `QA-KB-103` (High) was raised from this card. Everything above stands except the four corrections below. Evidence:
`evidence/qa-kb-103/analysis-01` to `-07`, the probe scripts in `evidence/qa-kb-103/analysis-plugins/`, and the validator's screenshots in the
same directory. Nothing was launched, nothing was written to the app or the DB; the probes only GET from :8000 and run the real functions.

**Confidence.** The root cause is CONFIRMED: read in source, and reproduced by running the REAL canvas serializer (`buildWorkflowManifest`,
`agentsFromManifest`, through a vite `ssrLoadModule`) against the live `GET /api/workflows/{id}?original=true` and `GET /api/agents/library`, then
feeding its output to the real `compile_override_steps`. Which roster seed a browser reaches at a given moment is INFERRED from the code plus the
validator's 3/3 cold-start observation.

### Root cause (CONFIRMED)

One mechanism: a `trust="user"` check with no baseline, behind a client that returns the baseline on purpose.

- `compile_override_steps` (`backend/agents/execution_engine/overrides.py:50-71`) compiles the posted `steps` alone and ends
  `return WorkflowCompiler().compile(parsed, registry, trust="user")` (`:71`). It never looks at the built-in the row overrides, so every
  capability reference in the list counts as user-authored. `_check_trust` (`compiler.py:488-512`, `:506-508`) refuses any `(kind, name)` not
  registered `user_allowed`; the grant rejection (`compiler.py:1023-1042`) refuses `spawn_subagents`.
- The canvas sends the built-in's own references back unchanged. `agentToManifestStep` spreads `agent.extra` first
  (`frontend/src/store/api/userWorkflows.ts:301-306`) and the whole `agent.tools` (`:336-337`). `extra` is filled from the built-in's raw step by
  `manifestStepToAgent` (`:734`, `captureStepExtra` `:283-289`, `MODELED_STEP_KEYS` `:266-278`), and `agentsFromManifest` projects every
  built-in through it (`frontend/src/lib/manifestAgents.ts:157`). That round trip was made lossless on purpose in `00b61ff93` (2026-09-04) and is
  pinned by `userWorkflows.roundtrip.test.ts` ("an untouched load -> save loses no key and changes no value").

For an UNCHANGED plan-seeded save, the refused set is exactly the references the built-in's own file step declares (`analysis-03`); removing
exactly those makes every payload pass:

| built-in | refused reference | on step |
|---|---|---|
| app_builder | `post_step: api_prefix_audit` | app-infra-generator |
| prototype | `compaction: html_skeleton` | prototype-build |
| prototype_feature_revision, prototype_large_revision | `compaction: html_skeleton` and `post_step: revision_validation` | prototype-build |
| prototype_revision | `post_step: revision_validation` | prototype-revision-agent |
| sample_fanout, sample_subagents_parallel, sample_wave | `tools.spawn_subagents` | sample-fanout-worker, custom-agent, sample-wave-worker |

The three non-grant references are registered with the default `user_allowed=False`
(`capabilities/compaction/html_skeleton.py:29-33`, `post_steps/api_prefix_audit.py:50-55`, `post_steps/revision_validation.py:40-45`).
Across all 39 built-ins the plan-seeded payload is refused for exactly these eight and passes for the other 31 (`analysis-07`).

4. Options a) to c) omit the one the register row states (d, below).

### Decision status

The register row (`BUGS.md` QA-KB-103, logged in `716ccbb2a`) states the expected behaviour: an unchanged or lightly edited override of a built-in
saves, and the trust="user" check still refuses an engineer-only key the user added or changed. That is option **d) inherit by baseline**. This
analysis proceeds on it and does not escalate; if the owner prefers a), b) or c), only the next section changes. Why d) over the others:

- a) strip in the client: ends the lossless round trip of `00b61ff93` for override saves (and breaks its seven tests if done in `agentToManifestStep`
  itself), cannot cover an API client, cannot heal a row stored
  before FIX-766, and is what the library seed already does by accident ([ISS-1128](20261008-2134-ISS-1128.md)): the user's version runs without
  `html_skeleton` compaction and, on that seed, without the task loop.
- b) keep the 422: leaves the register's Expected unmet and the plan-seeded prototype save refused.
- c) mark `html_skeleton`, `api_prefix_audit`, `revision_validation` user_allowed: widens the palette for every user-authored manifest, not just
  inherited use ([ADR-0039](20260904-1424-ADR-0039.md) locked constraint), and does not cover the spawn trio.

### Where the fix belongs (PROPOSED, not applied)

One baseline-aware decision in the shared check, then the two doors that bypass it routed through it. Smallest correct diff, all callers covered:

1. `overrides.py:50-71` `compile_override_steps(workflow_id, steps, registry)`: take the override TARGET's own plan as the baseline (the merge already
   holds it as `compiled`; the writers can call `compile_for_run`, as `workflows.py` does). A not-user-allowed reference of kind `compaction` or
   `post_step` is admitted iff the SAME step identity in the baseline declares the identical `(kind, name)`. Everything else is refused exactly as
   today: any grant (exec, network, secrets, spawn_subagents), the security and approval gates, hooks, tool_sets outside the allow-list, a reference
   the baseline step does not carry, and one the user moved to another step. Compare references, not whole keys: the canvas adds `exec: false` to
   `tools`.
2. Seam: pass the admitted set into `WorkflowCompiler.compile` so `_check_trust` stays the single enforcement point (ADR-0039), or strip, compare
   and re-attach inside `overrides.py`. Pass data in; `agents/workflows` must not import the kernel.
3. Case 3 (`run_commands.py:3367-3407`) and the trigger (`kernel_services.py:1616-1645`) compile an override row's whole manifest at user trust
   themselves, not through the shared function (the FIX-766 locked constraint is not literally true of them): [ISS-1129](20261008-2134-ISS-1129.md).
4. No client change is needed for the 422. Do not strip in `buildWorkflowManifest`.

Traps:

- The baseline is the override TARGET's file plan (`row.overrides_pipeline_type`), never the `pipeline_type` of a sync-from-file body and never the
  previously stored row (a smuggled key would grandfather itself). `compile_for_run` resolves aliases; a raw `load_manifest` does not.
- Identity is the `agent` id, plus `instance_id` for `custom-agent`; nested `subagents.steps` share the namespace.
- Keep the spawn trio refused. Even if the check admitted the grant, the user-trust cap zeroes it (`compiler.py:1062-1068` `apply_cap`;
  `permission_caps.py:115` `spawn_subagents=False` in the untrusted cap), so the override would run those samples without fan-out. Document them
  as the exception (beta samples).
- Never let an engineer-only grant ride on a `custom-agent` step whose `prompt` the user changed.
- `merge_override_steps` replaces the steps wholesale (`overrides.py:140`), so what the writers store is what runs; both use the same function.
  If the built-in's own value later changes, a stored copy stops equalling the baseline and the merge falls back to the file plan with a warning
  (the ADR-0033 known-open display mismatch). Prefer re-attaching from the baseline at merge time over trusting the stored copy.
- Import-linter: `agents.workflows` must not import `agents.execution_engine` or `app`; `agents.execution_engine.engine` must not import `app.api`
  (`backend/pyproject.toml`). SC-001/INV-1: no workflow-name branch in the kernel; the baseline is looked up by `workflow_id` as data.
- FIX-766 locked constraints stay: `_TRUSTED_SOURCES` and `_compile_check_manifest` unchanged; a new override door calls the shared function.

## Fix (QA-KB-103, 2026-10-09, fixer)

Resolved by [FIX-769](20261009-0059-FIX-769.md), as proposed above (option d, the seam "strip, compare and re-attach inside
`overrides.py`"): `compile_with_baseline` admits a `compaction`/`post_step` reference iff the same `agent` step of
`compile_for_run(<override target>)` declares the identical name, and every compile of an override row goes through it (writers
and merge via `compile_override_steps`, Case 3, the trigger, both resume recompiles). No client change. The analysis held; nothing
in it was corrected. One deliberate narrowing of "identity": a `custom-agent` step never inherits (no built-in declares either key
on one). `test_iss1118_override_baseline_refs.py`: 5 XPASS(strict) + 1 passed, observed; the xfail marker is left for the verifier.
[ISS-1128](20261008-2134-ISS-1128.md) and [ISS-1130](20261008-2134-ISS-1130.md) stay open.
