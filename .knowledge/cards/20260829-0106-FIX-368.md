## What was wrong

`BUG-20260828-040400-workflows-nonexistent`: cold-loading
`/workflows/<bad-id>/canvas` (all-zeros uuid, all-f's uuid, or an arbitrary
string — 3/3, id shape irrelevant) rendered a fully interactive "copy"
composer instead of the app's generic 404. The composer was not inert: its
"Save as copy" button stayed enabled and `POST /api/user-workflows` returned
`201 Created`, so a literally dead link could originate a real, persisted
workflow.

Its two sibling routes for the same bad id — the bare `/workflows/{id}` read
view and `/workflows/{id}/edit` — already rendered not-found correctly.

## Root cause

`frontend/src/app/[...view]/page.tsx`, the `workflow-canvas` cold-mount effect
(pre-change lines 452-499). Its `catch` was unconditional:

```ts
} catch {
  if (!cancelled) setInitialSavedComposition(null);
}
```

`initialSavedComposition = null` is indistinguishable from that state's own
blank-composer default (`useState<SavedComposition | null>(null)`, line 413),
so nothing downstream could tell "this workflow does not exist" from "the
composer has not been seeded". Unlike this same file's sibling cold-mount
effects — `workflowEditAccessDenied` for `/workflows/{id}/edit`
(`page.tsx:3547`) and `workflowDetailFailed` for the bare `/workflows/{id}`
(`page.tsx:3597`), both gated by `notFound()` — `workflow-canvas` had no
companion "not found" state and no `notFound()` gate anywhere in the file.

`ComposerPage.tsx` then keys its header (`:1020`) and "Save as copy" label
(`:1135`) purely on the URL-derived `builtinCanvasType` string, and the Save
button's `disabled` (`:1116`, `saving` only) and `handleSave` (`:663-762`)
check neither workflow existence nor agent count — so the save always
completed.

## What changed and why there

Three hunks, all in `frontend/src/app/[...view]/page.tsx`, mirroring the
`workflowEditAccessDenied` pattern already in the same file:

1. `:472-476` — a companion state `builtinCanvasAccessDenied`, declared
   beside the `builtinCanvasType` const it belongs to.
2. `:521-529` — the catch takes `(err)` and, after the existing
   `setInitialSavedComposition(null)`, sets the new state only when
   `err instanceof ApiError && (err.status === 403 || err.status === 404)` —
   character-for-character the check the `/workflows/{id}/edit` catch uses.
   Every other failure keeps the old blank-seed behaviour, so a transient 5xx
   or a network blip is not converted into a permanent not-found.
3. `:3801-3807` — a fourth `notFound()` gate alongside the existing three,
   keyed on `builtinCanvasType && builtinCanvasAccessDenied`.

The gate belongs in `page.tsx` because that is the one catch-all component
every URL already routes through (ADR-0018) and the only place `notFound()`
is reachable; `ComposerPage.tsx` has no route awareness and was deliberately
left untouched. `DashboardLayout.tsx` forwards `builtinCanvasType` with no
logic of its own, so no passthrough change was needed.

Blast radius re-checked before editing: `getWorkflowDetail` has five call
sites in `frontend/src/` (`page.tsx:482`, `IdeaInputPage.tsx:1032,1468`,
`WorkflowDialog.tsx:73`, `LaunchWizard.tsx:395,459`, `ComposerPage.tsx:448`),
and only `page.tsx:482` feeds `initialSavedComposition` for the canvas route
— `WorkflowDialog` surfaces its error, `ComposerPage:448` is the optional
SURF-03 capability strip whose swallow is intentional, and `LaunchWizard`
fetches a fixed non-URL-derived pipeline type.

Not fixed here, and unchanged: [ISS-410](20260828-2344-ISS-410.md) — a
transient (non-403/404) failure against a REAL workflow still lands in the
blank-seed state. That is deliberate per its own card: narrowing to 403/404
is what keeps a network blip from masquerading as "not found". It stays open
on its own card.
