## What fails

`cd backend && ./.venv/bin/python -m pytest tests/agents/test_declared_gate_redo.py -q` reports
`FAILED tests/agents/test_declared_gate_redo.py::test_non_redoable_declared_gate_unaffected_by_redo_action`. The
error is `asyncio.exceptions.CancelledError` at `agents/execution_engine/engine.py:12455`, the `await event.wait()`
in `_run_review_gate`. It is raised when the `_drive` helper's
`asyncio.wait_for(gen.__anext__(), timeout=_EVENT_TIMEOUT_S)` expires (`test_declared_gate_redo.py:125`, with
`_EVENT_TIMEOUT_S = 60.0` at `:30`). The other test in the file passes.

## Mechanism

- The test builds a step with `redoable=False` (`test_declared_gate_redo.py:198`). It answers the gate's only
  `review_gate_ready` with `set_review_response(gate_key, approved=False, action="redo", instructions="ignored")`
  (`:209-211`) and never sends a second response. It then expects one `agent_start` and one ready (`:219-220`).
- `_run_review_gate` refuses a redo at a firing that published `redoable=False`. It logs "Review gate redo REFUSED
  ... gate stays open (ISS-090)", calls `event.clear()` and `continue`s waiting (`engine.py:12482-12490`). The
  comment above that block says the degrade is deliberately KEEP WAITING: approving would fail open on a HITL gate,
  and rejecting would cancel the user's run.
- Nothing unblocks the gate, so the drive times out.

## Disposition (INFERRED): stale test

The keep-waiting degrade is a deliberate fail-closed decision ([ISS-090](20260812-0632-ISS-090.md)). Two sibling
tests already drive the same shape correctly. Each posts the refused action, waits until
`store.review_event_pending(gate_key)` shows the gate re-armed, then approves so the drive ends:

- `backend/tests/agents/test_redoable_eligibility_fence.py:129-135`
- `backend/tests/unit/agents/test_update_specs_enforcement.py:108-115`

The likely fix is test-only: do the same here and keep the existing assertions. QA-KB-006 did not do it, because it
was out of scope.

### Mechanism (CONFIRMED, read)

1. `HumanGate` calls `run_human_gate(step, output=...)` (`human.py:140`), which forwards `redoable=bool(getattr(step, "redoable", False))`
   (`kernel_services.py:1475`). The test's step has `redoable=False` (`test_declared_gate_redo.py:198-199`).
2. The primitive publishes `review_gate_ready` with `redoable: False` (`engine.py:12455`) and yields it. `_drive` awaits `_on_ready` inline
   (`test_declared_gate_redo.py:129-130`). **While `_on_ready` runs, the engine generator is suspended at that `yield`.** An async generator
   advances only when `__anext__` is called again (`:125`), so nothing the engine does in reaction to a response can happen during `_on_ready`.
3. `_on_ready` stores a redo (`:209-211`) and returns. `_drive` resumes the generator. `event.wait()` returns at once because the store set
   the event (`store.py:171-172`). The primitive reads `action == "redo"` (`engine.py:12518`), sees `not redoable` (`:12530`), logs, clears the
   event and `continue`s (`:12537-12538`). It yields nothing, so no second `review_gate_ready` is emitted.
4. The loop reaches `await event.wait()` again (`:12503`). Nobody stores another response, so after 60 s (`_EVENT_TIMEOUT_S`, `:30`)
   `wait_for` cancels the pending `__anext__`.

### The trap in the bug report's fix sketch (CONFIRMED, run in a scratch copy of the tree)

BUGS.md sketches: after `set_review_response(..., action="redo")` in `_on_ready`, poll `store.review_event_pending(gate_key)` until the gate
re-arms, then approve. Mechanism step 2 says why that cannot work: the engine cannot re-arm while `_on_ready` is awaited. Three variants, each
run in a throwaway copy of `backend/` outside the repo (`evidence/qa-kb-072/06-analyze-scratch-variants-output.txt`; source in
`07-analyze-scratch-variants-test.py.txt`; drive timeout cut to 6 s; `3 passed in 12.47s`):

| variant | result |
|---|---|
| inline poll, approve only if the poll saw the re-arm (the sketch, literally) | hangs: the poll sees False, nothing approves, `TimeoutError` |
| inline poll, approve whatever the poll saw | green but **vacuous**: trace `rearm_seen_inline=False` and no "REFUSED" log. The approve overwrote the redo (`store.py:163-170` keeps one slot per gate) before the engine read it, so the refusal path never ran |
| `_on_ready` posts the redo and hands the approve to a concurrent task | correct: `rearm_seen_bg=True`, "REFUSED" logged, events end `review_gate_ready, review_gate_approved, pipeline_complete`, one `agent_start`, one ready |

### Fix, and where it belongs

**One place: `backend/tests/agents/test_declared_gate_redo.py::test_non_redoable_declared_gate_unaffected_by_redo_action` (`:193-220`).** No
application file changes, and there is no shared function to guard: the refusal lives once, in `_run_review_gate`, and every caller already
routes through it. Keep the redo, the `redoable is False` assertion and the existing `agent_start == 1` / `len(readies) == 1` assertions.
Replace the single inline answer with a redo plus a concurrent approver. This shape is the one the scratch run verified:

```python
rearmed = False
approver: list[asyncio.Task] = []

async def _on_ready(ev):
    readies.append(ev)
    store = harness.engine._store
    gate_key = ev["data"]["gate_key"]
    assert ev["data"]["redoable"] is False
    await store.set_review_response(gate_key, approved=False, action="redo", instructions="ignored")

    async def _approve_once_rearmed():
        nonlocal rearmed
        # the refusal clears the event: armed and unset == the engine consumed the redo and kept waiting
        rearmed = await _wait_until(lambda: store.review_event_pending(gate_key), timeout=5.0)
        if rearmed:
            await store.set_review_response(gate_key, approved=True)

    approver.append(asyncio.create_task(_approve_once_rearmed()))   # do NOT await it here
```

After `_drive` returns, assert `rearmed`, `"review_gate_approved" in types` and `"pipeline_complete" in types`, and `await` the task in a
`finally` so a failed drive cannot leak it. `_wait_until` is eight lines; the sibling tests each carry a private copy
(`test_redoable_eligibility_fence.py:104-111`), so copy it rather than import a private helper across test files. The `rearmed` flag is the
non-vacuity check and does not depend on log text. Update the docstring and the trailing comment that narrate the old route
(`:195-197`, `:218`: "the redo action was consumed, not honoured").

### What a naive fix would get wrong

- Polling inside `_on_ready` (the sketch): it hangs, and with an unconditional approve it passes without ever exercising the refusal.
- Approving instead of redoing, or approving first: removes the thing the test is about.
- Making the engine end the drive on a refused redo (approve, reject, or a new outcome): reverses [ISS-090](20260812-0632-ISS-090.md) and
  [FIX-500](20260831-1644-FIX-500.md), which `test_redoable_eligibility_fence.py` and `test_gate_redo_enforcement.py` pin.
- Raising `_EVENT_TIMEOUT_S` or deleting the test. Deleting loses the one end-to-end check that the manifest default `redoable: false` reaches
  the primitive through `HumanGate` and `run_human_gate`; the primitive-level tests do not cover that chain.
- Asserting on `caplog` alone: it works (`redo REFUSED` is logged), but it couples the test to a log string.
