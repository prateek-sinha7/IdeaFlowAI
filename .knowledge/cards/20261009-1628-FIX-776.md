# FIX-776

**Register source:** `QA-KB-126` (`LEDGER.md`), 5-fixer, 2026-10-09. Resolves [ISS-1114](20261008-1415-ISS-1114.md) (root) and its
three siblings: [ISS-1163](20261009-1558-ISS-1163.md) (PATCH), [ISS-1164](20261009-1558-ISS-1164.md) (route trigger) and
[ISS-1165](20261009-1558-ISS-1165.md) (resume). The owner approved fixing it on 2026-10-09 (`BUGS.md`, QA-KB-126), which took option c)
("accept ADR-0039 as written") off the table. Base is HEAD `01777a107`; line numbers below are that HEAD plus this change. The whole
change is `evidence/qa-kb-126/fix-05-change.patch`.

## What was wrong

The root cause is on [ISS-1114](20261008-1415-ISS-1114.md) and is not re-derived here. A saved row's privilege and its entitlement came
from two inputs that nothing connected:

- The privilege is the trust of the compile. Every plain saved row compiled at `trust="db"` (trusted since
  [ADR-0039](20260904-1424-ADR-0039.md): exec, spawn_subagents, CAP-03 gates and hooks, raised Limits, every tool pack), at sites that
  had no tier: the save check (`user_workflows.py:121` at HEAD, hard-coded `"db"`), launch Case 3 (`run_commands.py:3374-3376`),
  the route trigger (`kernel_services.py:1616`), and resume, which recompiles at the `_trust` launch persisted.
- The entitlement was a label the caller chose: `can_run_pipeline(tier, body.base_pipeline_type)` at create. The Composer is
  enterprise-only only because the Composer UI sends `custom`; any label the tier may run (basic: `ppt`) saved the same manifest, and
  PATCH stored one with no entitlement call at all.

## What changed, and why there

The fix is the card's proposed shape: decide the trust of a saved row once, from the caller's effective tier, and give that answer to
every compile site. The compile is the enforcement point, so nothing narrows or refuses beside it (ISS-1114 probe `[N]`: a dry-run gate
would pass a `tool_sets` request the real db compile grants).

1. **The one decision**, `_saved_row_trust(tier)` in `backend/app/api/run_engine.py:715-728`, beside `_model_entitlement_error` and
   `_trigger_entitlement_error`: `"db"` when `can_run_pipeline(tier, "custom")` holds, else `"user"`. `tier` is
   `effective_tier(current_user, principal)` at every caller (the token, Decision 3), and it has no default. The `custom` literal lives
   in `app/api`, never under `backend/agents/` (INV-1).
2. **Save, three writers** (`backend/app/api/user_workflows.py`). `_compile_check_manifest` takes the trust (`:85`, compile `:123`) and
   `_validated_manifest` takes a required keyword `trust` (`:177-183`) that it hands on for a plain row (`:244`). POST insert (`:944`),
   POST upsert (`:894`) and PATCH (`:1103`, the [ISS-1163](20261009-1558-ISS-1163.md) door, which had no entitlement call) pass
   `_saved_row_trust(effective_tier(current_user, principal))`. A basic, hexaware or pro save of an exec, spawn, CAP-03, Limits or
   engineer-hook manifest is now the compiler's own 422; `tool_sets` and `git` requests are accepted and narrowed exactly as an inline
   manifest is.
3. **Launch by id, Case 3** (`backend/app/api/run_commands.py:3383-3393`): `_trust` is `"user"` for an inline manifest or an override row
   (unchanged), else `_saved_row_trust(effective_tier(current_user, principal))`. The persisted `_trust` (`:3448`) now carries that
   answer to resume. A row stored before this fix by a non-Composer owner is refused at launch (`invalid_workflow_manifest`, 422, the
   mint not reached) or compiled with nothing privileged.
4. **Route trigger** ([ISS-1164](20261009-1558-ISS-1164.md) option 1; `kernel_services.py:1604-1622` and `run_engine.py:731-745`). The
   kernel has no principal, so it asks the app-side `_parent_run_trust(db, ectx.run_id)` through the lazy `app.api.run_engine` import it
   already had: a plain row gets at most the `_trust` launch persisted on the run that fires the trigger; a run with none gives `"user"`.
   Override rows stay `"user"`. A refused compile raises `CompilerError` before the mint, the posture [FIX-769](20261009-0059-FIX-769.md)
   verified for override rows.
5. **Resume** ([ISS-1165](20261009-1558-ISS-1165.md), decided: clamp at the user's door). `resume_run_endpoint` refuses a run persisted at
   `_trust == "db"` when `_saved_row_trust` gives this caller `"user"` (`run_commands.py:711-722`, 403 `tier_not_entitled`, before the
   status flip and the queue registration).
6. **Stale premise text the card named** (comments only): `engine.py:5910-5914` ("a user/db manifest can never provision the exec
   workspace"), `local.py:479-481` ("exec is engineer-only"), `run_commands.py:2536-2541` (inline "STRICTER than the saved row's
   trust=db"), and the `_compile_check_manifest` docstring (`user_workflows.py:99-101`).

### Where this differs from the cards, and why

- **The helper takes only the tier.** ISS-1114 sketched one helper that also returns `"user"` for inline and override rows. Those two
  conditions stay where they were, at launch (`_inline or overrides_pipeline_type`) and at the trigger (`overrides_pipeline_type`),
  because the save check must NOT give an override row `"user"`: `_compile_check_manifest` compiles without the override baseline, so a
  "Save as my version" carrying its built-in's `compaction` / `post_step` ([ISS-1118](20261008-1444-ISS-1118.md)) would 422. Override saves
  keep their `"db"` validation plus `compile_override_steps` at `"user"`, exactly as before.
- **Trigger, absent `_trust` gives `"user"`, not "today's behaviour".** ISS-1164 option 1 said a file-backed parent has no `_trust` and
  would keep today's row-only answer (`"db"`). Two user-authored parents also persist none: a built-in run with an enabled override (its
  steps can carry a route) and a triggered child (`run_trigger_workflow` mints with `manifest_json=None`). Keeping `"db"` for them left
  the basic-tier door open through an override parent or a second hop, so a missing `_trust` fails closed, as resume already reads it
  (`_mf.pop("_trust", "user") or "user"`). The cost is in "Behaviour changes" below; the upgrade path is [ISS-1174](20261009-1628-ISS-1174.md).
- **Resume: user door clamped, in-flight runs grandfathered.** The startup re-arm paths (`resume_run` on a review re-entry,
  `_replay_clarify_run`, `engine.py:15700`, `:16259`) have no principal and keep the trust a run already held; a restart is not a new
  grant. Every new launch persists the tier-based answer, so that population does not grow. The dev DB has no run carrying `_trust` at all
  (`fix-04`).
- **Tests for the siblings.** ISS-1163 is covered by the root's test file (PATCH case). ISS-1164 and ISS-1165 had no test, so this fix adds
  `test_iss1164_1165_trigger_resume_trust.py` (no xfail). It was observed red on an archive copy of HEAD for the bug's reasons (trigger
  "DID NOT RAISE", resume `200 == 403`) and green with the change (`fix-02` sections 3, 4, 7).

## Behaviour changes a caller can see

- basic, hexaware and pro: saving (POST or PATCH) a manifest row that holds anything only `db` admits is a 422 naming the capability,
  exactly what the same bytes sent inline get. `tool_sets` and `git` requests save and run narrowed.
- A row stored before this fix by such an owner, or by an owner downgraded since, launches at `user`: 422 if it holds a privileged grant.
- **A lower tier's verbatim file copy can stop launching.** ISS-1114 ("Traps", `analysis-03`): 14 of 30 entitled pipelines do not compile
  at `user` verbatim (for basic: `ppt`, `ppt_revision`, `user_stories_revision`). No frontend flow stores one (no frontend caller of
  sync-from-file), but sync-from-file can. The dev DB holds no such row (`fix-04`: the only plain manifest rows are 2 enterprise `custom`
  rows); production was not queried. The owner should say whether exemptions are wanted.
- Resume: a failed, degraded or cancelled run persisted at `_trust="db"` resumes only for a caller who may run the Composer (403
  `tier_not_entitled` otherwise).
- Route trigger naming a saved row id: the row compiles at most at the `_trust` of the run that fires it. Enterprise sees a change in
  three cases, each refused with `CompilerError` (the firing run fails) when the target row needs `db`: an unsaved (inline) Composer run,
  a built-in run with an enabled override, and a second trigger hop (a triggered child persists no `_trust`). The dev DB has no saved row
  whose route targets a saved row id (`fix-04` (b)). [ISS-1174](20261009-1628-ISS-1174.md) holds the upgrade path.
