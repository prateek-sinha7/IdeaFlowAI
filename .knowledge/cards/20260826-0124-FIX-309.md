## What happened

`PreviousRunProvider.load` seeded the existing artifact BEFORE running the L16
ownership gate. A stale code comment still justified that order:

> "Works off the user message (independent of a parent_run_id), so it runs BEFORE
> the parent-seed gate."

That was true when written. It stopped being true when the Concierge revision
fallback was added to `_seed_existing_artifact`
(`backend/agents/capabilities/context_providers/previous_run.py:259-265`):

```python
if not existing:
    parent_run_id = getattr(ctx, "parent_run_id", None)
    if parent_run_id and hasattr(runner, "read_parent_file"):
        existing = runner.read_parent_file(parent_run_id, artifact_name_inner) or ""
```

That reads the PARENT run's sandbox, keyed on `parent_run_id` — so the helper was
no longer parent-independent, and the ordering its own comment relied on had become
the wrong way round.

## Severity

**Defence-in-depth broken; no proven open hole.** The main API path resolves the
parent through `_resolve_owned_parent_run_id(db, source_workflow_run_id, user.id)`
(`backend/app/api/run_commands.py:2473`), so `parent_run_id` reaching ctx is already
owner-checked there. The in-provider `assert_owns` is the second fence, and L16 /
AUTHZ-02 / INV-8 state it explicitly — the guard existed precisely to keep this
ordering, and it was the thing that caught the drift.

## The fix

The gate moves above `_seed_existing_artifact`, and its verdict is threaded in as
`allow_parent_read`:

- `parent_ok` is computed first: `PermissionError` still propagates (never
  swallowed, L16); any other store error still fails CLOSED.
- `_seed_existing_artifact(ctx, *, allow_parent_read: bool = False)` gates ONLY the
  parent-read fallback on it. The default is False so a future caller is
  fail-closed by construction.
- On the fail-closed branch the message-only seed still runs — the user's own
  message is not the parent's data, so refusing the parent must not also discard it.
- `scoped_store is None` keeps its historic meaning (no store to check against →
  proceed), so no behaviour changes for a ctx that never carried one.

## Test expectations that legitimately moved

`test_declared_revision_with_parent_seeds_after_assert_owns` pinned
`runner.reads == ["spec.md", "design.md", "tasks.md"]`, from before the Concierge
fallback existed. That read of `prototype.html` is a real feature, and after this
fix it lands AFTER the gate — which is the whole point. Expectations updated to
`["prototype.html", "spec.md", "design.md", "tasks.md"]` for reads and the same
order for writes, with the reason recorded in the test.
