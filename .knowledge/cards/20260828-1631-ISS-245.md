## What happened

On `/login`, filling in valid credentials and clicking the "Sign in" button three times in
rapid succession — synchronous programmatic clicks with no delay between them — fires **three
separate** `POST /api/auth/login` requests instead of being reduced to one. The button's
`disabled` attribute and its label text are both unchanged (`disabled: false`,
`text: "Sign in"`) both immediately before and immediately after the triple click, even though
`handleSubmit` calls `setIsLoading(true)` synchronously on the first click.

Confirmed **CONFIRMED, 3/3, cold start every cycle** — each cycle started from a fresh
`localStorage.clear()` + fresh direct navigation to `/login`, not a soft re-click of the same
screen:

- **Cycle 1:** filled valid `qa-admin@flowinqa.com` / `flowin-e2e-pass`, triple-clicked the
  "Sign in" button synchronously. `button.disabled` read `false` before and after the three
  clicks. `window.fetch` instrumented to count `/auth/login` calls: **3**. Confirmed via
  `browser_network_requests` filtered to `auth/login`: three `POST` requests, all `200 OK`.
- **Cycle 2:** identical repro from a fresh cold start (cleared storage, fresh nav) — same
  result: `disabled` stays `false` throughout, 3 login calls fired.
- **Cycle 3:** identical repro from a third fresh cold start — same result: 3 login calls
  fired, button never disables.

## Expected vs actual

- **Expected:** the "Sign in" button disables itself (and/or shows a loading state) the
  instant the first click starts the login request, so additional clicks before the response
  arrives are ignored and at most one `POST /api/auth/login` is sent per submission attempt.
- **Actual:** three synchronous clicks each independently invoke `handleSubmit`, each of which
  calls `login(email, password)` (an async fetch), because the `disabled={isLoading}` prop on
  the `<Button>` only takes effect once React commits the `setIsLoading(true)` state update
  and re-renders — a commit that has not happened yet when a second and third synchronous click
  event dispatch inside the same task. The DOM's actual `disabled` attribute is provably still
  `false` at both click 2 and click 3.

## Conditions established

- Route: `/login`, base sign-in form only (not the challenge/MFA sub-form).
- Tier: qa-admin — not tier-specific; the form and its submit handler have no tier branching.
- Trigger: **rapid repeated clicks on "Sign in" before the pending login request resolves** —
  reproduced here via synchronous `btn.click(); btn.click(); btn.click();` in one JS task,
  which is the sharpest form of the same race a very fast human double/triple click can also
  hit, since React's state commit is not synchronous with the click handler.
- Not timing-window-dependent in the sense of needing a slow network — the backend responded
  `200 OK` to all three requests every cycle; the bug is the button failing to gate the *second
  and third click*, not a slow first response exposing a gap.
- Session/theme/viewport: default, not varied — 3/3 without variation, no need to sweep further
  axes.

## Root cause (CONFIRMED)

`frontend/src/app/login/page.tsx`'s `LoginForm.handleSubmit` (lines 76-93) does set
`isLoading` synchronously at the top of the handler:

```
frontend/src/app/login/page.tsx:76-93
async function handleSubmit(e: FormEvent<HTMLFormElement>) {
  e.preventDefault();
  setError("");
  setIsLoading(true);
  try {
    const result = await login(email, password);
    ...
```

and the submit `<Button>` (lines 306-313) does read `disabled={isLoading}`. The mechanism is
correctly wired for the *ordinary* case (one click, wait, response). It fails for *rapid
repeated clicks* because `setIsLoading` is a React state update, not a synchronous DOM
mutation: the button's `disabled` HTML attribute only flips after React re-renders and commits,
which happens on a later tick than the click event itself. A second (and third) click that
lands before that commit finds the DOM button still enabled and still fires its own
`handleSubmit` call, each starting its own independent `login()` request. There is no
synchronous guard (a ref flag, or disabling the DOM node directly in the click handler before
any `await`) to close this window — the only guard is the React state round-trip, which is too
slow for back-to-back clicks in the same or adjacent tasks.

## Proposed fix — where it belongs

`handleSubmit` in `frontend/src/app/login/page.tsx` is the single place every "Sign in" click
funnels through, so a synchronous guard added here (not per-caller, there is only one caller)
closes the whole class of duplicate submissions:

- Add an early-return synchronous guard at the very top of `handleSubmit`, before
  `setIsLoading(true)`, e.g. a `useRef<boolean>` flag checked and set synchronously
  (`if (submittingRef.current) return; submittingRef.current = true;`), cleared in the
  `finally` block alongside the existing `setIsLoading(false)`. A ref mutation is synchronous
  and does not depend on a React re-render, unlike state, so it closes the exact gap the
  `disabled={isLoading}` prop cannot close on its own.
- `ChallengeForm`'s `handleChallengeSubmit` (lines 95-152) has the identical shape
  (`setIsLoading(true)` after validation, `disabled={isLoading}` on its submit button) and is
  exposed to the same race for the MFA/new-password code path — the same ref guard pattern
  should cover both handlers in this file, since both funnel through the same component.
- No backend change needed: the backend already answers all three duplicate requests
  correctly (`200 OK` each); this is a frontend-only submission-debouncing gap.
