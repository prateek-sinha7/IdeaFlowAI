# ISS-1036

Sibling of [ISS-945](20261002-0053-ISS-945.md), found by the QA-KB-087 analysis on 2026-10-02. Confidence: the gap is CONFIRMED by
mutation on scratch copies (no repo file was edited; `evidence/qa-kb-087/`). The user-visible consequence of the mutation is INFERRED:
read from code, not observed in a browser. A validator re-run is still pending. Today's app is correct: `AccountSettings.tsx:635`
sets both sides, so this is a regression-guard gap, not a live defect.

## Why the root cause implies it

[ISS-945](20261002-0053-ISS-945.md)'s root cause is that the file's `@/lib/api` mock does not model the real Constitution load.
`AccountSettings.iss372.test.tsx:16` resolves `getConstitution` in memory, so the `:83` wait on `fetch` can never be satisfied. The
same line has a second effect that the first one hides: it resolves `{ content: "" }`, so the saved value the guard compares
against is `""` in every case.

The ISS-921 case is titled "(not before it loads)", and `AccountSettings.tsx:124-128` states the property it pins: "the loads set
both sides together, so a pristine page never reads as dirty". With `""` on both sides of `constitutionDirty` (`:129`) that property
holds whether or not the load sets both sides, so no case can notice. [FIX-704](20261002-0053-FIX-704.md)'s own sources file
(`AccountSettings.iss372.sources.test.tsx:14`) mocks the same empty payload, and FIX-704's mutants were "no model term, no trim, no
Discard reset": none of them touched the load.

## Condition

A returning user with a saved Constitution (any non-empty value) opens the Constitution tab and types nothing, while the load stops
setting `constitutionLoadedValue`. The scratch mutant is the one-line deletion of `setLoadedValue(loaded);` at
`AccountSettings.tsx:635` (`evidence/qa-kb-087/scratch/AccountSettingsMutant.tsx.txt`).

## Expected

At least one guard case fails: `constitutionContent` ("saved rules") then differs from `constitutionLoadedValue` (`""`), so
`hasUnsavedWork` is true and the page reports dirty without a keystroke.

## Actual

Both guard files stay green on the mutant. INFERRED real-app effect: every returning user with a saved Constitution would get the
"Leave without saving?" dialog on Back from a pristine Constitution tab, and no test would have said so.

## Evidence

All in `evidence/qa-kb-087/` (`02-analyze-scratch-runs.txt`, `03-analyze-mutant-kill-rate-and-act-flush.txt`):

- Run E: the mutant, the ISS-921 case fixed as [ISS-945](20261002-0053-ISS-945.md) proposes, the file's own empty mock: `Tests 4 passed (4)`.
- Run G: the FIX-704 sources file against the same mutant: `Tests 3 passed (3)`; against the real component (run H) also 3 passed.
- Run F: the same mutant with a saved value of "saved rules": the case fails with `expected "vi.fn()" to not be called with arguments: [ true ]`.
  Caught in 59 of 62 runs; the other 3 let the mutant through (one run alone, two of the parallel runs).
- The 3 misses: the negative assertion runs right after `findByRole("textbox")`, and the `true` report comes from the parent's `useEffect`
  (`AccountSettings.tsx:134-137`), which React flushes on its own schedule. INFERRED mechanism, measured effect: with
  `await act(async () => {})` between the two, the mutant was caught in 40 of 40 runs, and the same case on the real component passed
  32 of 32.

## Fix direction

Test-side only, in the same two files [ISS-945](20261002-0053-ISS-945.md) already opens. Do not edit `AccountSettings.tsx`.

1. Give the guard a non-empty saved Constitution. Cheapest: resolve `{ content: "saved rules" }` at `AccountSettings.iss372.test.tsx:16`.
   ISS-372 cases 1-3 never mount ConstitutionSection, so they are unaffected (scratch variant d1: `Tests 4 passed (4)`), and the ISS-921
   case still passes on the real component. Or add a "returning user" case to the sources file, which already renders onto the
   Constitution tab; its `vi.mock` factory returns a plain arrow, so a per-case value needs the factory to expose a `vi.fn`.
2. Flush effects before the negative assertion: `await act(async () => {})` between `findByRole("textbox")` and
   `expect(onUnsavedChange).not.toHaveBeenCalledWith(true)`. The idiom exists at `LaunchWizard.savedRoster.iss943.test.tsx:166`.
3. For the 4-test-writer: the in-repo precedent for a red test about a test is a source meta-lock
   (`frontend/src/app/[...view]/terminalReopenReconcileLock.meta.test.ts`, QA-KB-071), here asserting that a guard file's
   `getConstitution` mock resolves non-empty `content`.

## Resolution (QA-KB-087 fix, 2026-10-07)

Fixed test-only by [FIX-744](20261007-2029-FIX-744.md), with option 1 of the fix direction above. In
`AccountSettings.iss372.test.tsx`, `:16` now resolves `{ content: "saved rules" }`, and `await act(async () => {});` sits between
`findByRole("textbox")` and the negative assertion. The sources file and `AccountSettings.tsx` are untouched.

Observed on scratch copies (`evidence/qa-kb-087/fix-03-mutant-probe-iss945-iss1036.txt`):

- The `setLoadedValue(loaded)` mutant is caught at `:84` with `expected "vi.fn()" to not be called with arguments: [ true ]`.
- ISS-945's edits alone let the same mutant pass.
- Stability: 16 of 16 runs caught the mutant, and 16 of 16 runs passed on the real component (8-way parallel, twice each).
- The official file reads `4 passed` in place.
