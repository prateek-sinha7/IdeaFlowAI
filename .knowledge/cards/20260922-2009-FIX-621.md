# FIX-621

Resolves [ISS-775](20260922-1330-ISS-775.md) (root),
[ISS-778](20260922-1600-ISS-778.md), [ISS-779](20260922-1602-ISS-779.md) and
[ISS-780](20260922-1604-ISS-780.md), all from
[QA-SG-004](../../BUGS.md#qa-sg-004) — "Switching between parallel workflow
runs from notification bar is unreliable, sometimes fails or delayed".

## What was wrong

Every surface that switches to a different live run fired the switch WITHOUT
awaiting it and then pushed the run's stream URL unconditionally:

```tsx
onSwitchToLiveRun(targetRunId);            // async — starts a durable replay
setMainView("execution");
router.push(routes.runStream(targetRunId)); // remounts page.tsx immediately
```

`handleSwitchToLiveRun` (`frontend/src/app/[...view]/page.tsx:2745-2846`) runs
a synchronous prelude and then `await getRunEvents(...)` before replaying the
run's durable frames. `router.push` remounts this page under the `[...view]`
catch-all — not an inference, an existing dated code comment at
`page.tsx:3433-3437` ("a fresh render-instance id appears right after
router.push") — and that remount runs `useRunStateStore`'s unmount cleanup,
flipping `mountedRef` to false (`frontend/src/hooks/useRunStateStore.ts:335`).
From that moment `getOrCreate`/`getAgentStartTimes` hand the still-running
replay a throwaway object (`useRunStateStore.ts:392-397, 404-410`), so the
replay the click paid for writes nothing. Recovery falls entirely to the fresh
instance's T11 effect, which issues a SECOND `getRunEvents` for data the first
instance already fetched and discarded — the multi-second delay in the report,
and why "the same entry may work on a subsequent click".

Two guard gaps sat underneath it:

- [ISS-780](20260922-1604-ISS-780.md) — [ISS-657](20260917-1250-ISS-657.md)'s
  `if (trackedRunIdRef.current !== runId) return;` is a `useRef`, so the
  remount does not just reset its value, it replaces the ref OBJECT. Two rapid
  clicks on different runs land on two different page instances, and neither
  guard can see the other.
- [ISS-779](20260922-1602-ISS-779.md) — `handleSelectWorkflowRun`
  (`page.tsx:2905-3392`, the general "reopen this run" path behind History's
  row click) has the same two-phase async shape and, grepped in full, had ZERO
  stale-response checks anywhere in its ~440 lines.

## What changed and why there

**1. The callers await the switch before navigating** (the four call sites
[ISS-775](20260922-1330-ISS-775.md)/[ISS-778](20260922-1600-ISS-778.md) name).
Awaiting is what makes the pre-remount replay land in the REAL module-scope
store instead of a throwaway: the remount now happens after the replay, not
during it. `handleSwitchToLiveRun` wraps all of its async work in
`try/catch` and swallows its own fetch errors, so the awaited promise always
resolves — awaiting it can never strand the navigation.

- `DashboardLayout.tsx:2816` — the bell panel's `onViewResults` live/gate
  branch (ISS-775's own subject). The trailing
  `if (targetRunId) { router.push(...) }` moved inside the awaited block.
- `DashboardLayout.tsx:2749` — `onGoToPipeline`, the implementation behind
  BOTH the "N Running" dropdown entry and the single-run badge.
- `DashboardLayout.tsx:2766` — the `onSwitchToLiveRun` wrapper DashboardLayout
  passes to `AppHeader` now `return`s the page's promise; without that the
  header would await `undefined` and the fix would be a no-op there.
- `AppHeader.tsx:258` (`handleRunClick`) and `AppHeader.tsx:354` (the single
  badge's not-yet-in-recentRuns fallback) — `await onSwitchToLiveRun(...)`
  before `onGoToPipeline?.(...)`, inside a `void (async () => { … })()` so the
  handler's own signature (and FIX-519's ISS-647/ISS-655 contract that the
  clicked run's id is the one passed on) is unchanged.
- The prop type on both components widened to
  `(runId: string) => void | Promise<void>` — the implementation was always
  async; the type had flattened it to `void`.

**2. The in-flight guard moved to module scope** (`page.tsx:96-122`):

```ts
let switchGeneration = 0;
let switchGenerationRunId: string | null = null;

function beginSwitchGeneration(runId: string): number { … }   // claim
function isSwitchGenerationStale(generation: number): boolean { … }
```

Re-claiming the run already claimed keeps its generation, so the several
handlers ONE click runs through (`handleSwitchToLiveRun`, then T11's replay on
the instance the push created) share a single generation, while a claim for a
DIFFERENT run supersedes every older one. Claimed and checked at:

- `page.tsx:2757` / `:2824` — `handleSwitchToLiveRun`. ISS-657's
  `trackedRunIdRef.current !== runId` check is KEPT and OR-ed with the new one:
  the ref half catches a newer switch on the same instance, the generation half
  catches one made after the remount ([ISS-780](20260922-1604-ISS-780.md)).
- `page.tsx:2917` / `:2972` / `:3069` — `handleSelectWorkflowRun`, which had no
  guard at all ([ISS-779](20260922-1602-ISS-779.md)). Checked after
  `await getWorkflow(...)` and again after `await getRunEvents(...)`, the fetch
  that actually repaints the run. Deliberately NOT keyed on
  `trackedRunIdRef.current`: that ref is also written by a frame handler
  (`page.tsx:1371`) and by the contentSourceRunId sync effect (`:2331`), so it
  would drop legitimate reopens; the generation is the precise signal.
- `page.tsx:3581` / `:3631` — T11's `liveRunIds` fast-path replay, the
  instance that recovers the switch after the remount. It re-claims (same run,
  same generation) and drops its own replay if the user moves on mid-fetch.

## What is deliberately NOT changed

- **`handleSwitchToLiveRun` keeps its durable replay.** ISS-775's fix section
  floated deleting it and letting T11 own the replay; `liveRunSwitch.fix201.test.ts`
  locks "the single deduped replay through the page router stays"
  (`expect(body).toContain("handleWebSocketMessage(")`), so that option would
  have required editing an existing lock test.
- **The push was NOT centralised inside `handleSwitchToLiveRun`** (ISS-775's
  other option). Four callers would then have to stop passing their own target,
  which is exactly the stale-closure shape FIX-519 fixed; the test written for
  this bug also asserts the push stays at the call site it belongs to.
- **`onViewRunningPipeline` (`DashboardLayout.tsx:2985`) is untouched.** It is
  reached only when the clicked History row IS the run already being viewed
  (`WorkflowHistory.tsx:343-344`), so it is not a live-to-live switch and the
  defect does not apply. `DashboardLayout.iss656.test.tsx` also asserts its push
  synchronously.
- **`onSelectWorkflowRun` / `onOpenRun` call sites do not await.**
  `handleSelectWorkflowRun` runs `getWorkflow` + `getRunEvents` + a family walk;
  awaiting all of that before navigating would trade this bug's delay for a
  worse one. ISS-779's ask — the missing guard — is fixed inside the function.
- **The silent no-op's exact trigger is still not proven.** ISS-775 marks it
  INFERRED and names `DashboardLayout.tsx:823-824`'s `pipelineState`-reactive
  `router.push` as the suspect. Guarding that effect risks blocking the push
  for a NEWLY LAUNCHED run (its own comment calls it "the single funnel every
  launch path's pipelineRunId flows through"), so it was left alone rather than
  fixed on a theory. What this fix removes is the confirmed half: the orphaned
  replay, the duplicate fetch behind the delay, and the two guard gaps.
