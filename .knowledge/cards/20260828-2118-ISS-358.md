## Summary

On a completed run's Preview tab (`/runs/<id>`), a chat message's displayed
timestamp is not the time it was actually sent — it is the current wall-clock
time at whatever moment the page happens to load. Every full-page reload
recomputes it to a new "now", so the same historical message shows a
different, always-just-reloaded time on every visit.

Register entry: `BUG-20260828-095700-runs-id-chat-timestamp`
(`bug-hunter/ledger.md`).

## Reproduction (validated 3/3, cold start every cycle)

Route: `/runs/b9feac1c-ec21-4531-8ba7-bb391786993e` (completed run "Ppt V2"),
Preview tab, chat transcript (`RunChatLane` → `MessageBubble`). Account
`qa-admin` (no tier/theme/viewport dependency — none of those axes were
varied because 3/3 reproduced immediately).

For each cycle: navigate away to `/dashboard`, wait 65-130s, then cold
navigate back to the run route (a genuine remount, not a soft re-click):

- Cycle 1: message timestamp read 09:13 PM at send; after the cold reload it
  read **09:15 PM**.
- Cycle 2: after the next cold reload it read **09:16 PM**.
- Cycle 3: after the next cold reload it read **09:17 PM**.

Each reload's displayed timestamp exactly matched that reload's browser
wall-clock time (`new Date()`), never the original send time. Trigger is
simply: any full page reload / cold navigation to the run route — no timing,
entry-path, tier, theme or viewport variance needed.

This matches the hunter's original evidence: sent at 09:51 AM, read 09:52 AM
after one reload, then 09:56 AM after a ~5-minute-later reload.

## Root cause

`frontend/src/hooks/useRunChat.ts`:

- `upsertUserMessage` (~line 354) and `upsertNarratorMessage` (~line 393)
  both build the folded `ChatMessage` with `createdAt: new Date().toISOString()`
  unconditionally, every time a `chat_message` / `chat_reply` event frame is
  folded into the transcript.
- This same fold path runs for BOTH a freshly-sent live message and for
  historical events replayed from `GET /api/runs/{id}/events?after=N` on page
  load/reload.
- The backend event payload carries no `created_at`/timestamp field at all
  (confirmed via network inspection: `events?after=N` responses for
  `chat_message`/`chat_reply` have no timestamp key), so there is no real
  send time available to prefer — the code falls back to "now" on every
  fold, including replays.
- `frontend/src/components/chat/MessageBubble.tsx:189` then renders that
  fabricated value: `new Date(message.createdAt).toLocaleTimeString(undefined,
  { hour: "2-digit", minute: "2-digit" })`.

## Expected vs actual

- Expected: a message's displayed timestamp reflects when it was actually
  sent and stays fixed across reloads.
- Actual: the timestamp recomputes to the browser's current time on every
  page load, so a historical message appears to have been sent "just now"
  on every single visit.

## Distinction from ISS-276

Not the same defect as [ISS-276](20260828-1700-ISS-276.md) (`LaneRunHeader`
"stuck on just now" — a single frozen/wrong value fed by a hydration-time
stamp instead of `completed_at`, `LaneRunHeader.tsx:257`). That one never
updates once wrong. This one is never frozen — it changes to a new, always-
wrong "now" on every reload, in a different component (`MessageBubble` via
`useRunChat`), driven by a missing backend field rather than a wrong field
selection.

## Fix direction

- Backend should persist and return `created_at` on `chat_message` /
  `chat_reply` events.
- Frontend `upsertUserMessage` / `upsertNarratorMessage` should prefer
  `data.created_at` when present, and when merging/replaying an existing
  message should reuse the EXISTING message's `createdAt` rather than
  minting a fresh `Date.now()`.
