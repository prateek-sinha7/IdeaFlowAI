## Reproduction (QA-PS-048)

Validated 3/3 on 2026-09-16, cycle 1 — reproduces every time, no special
condition needed.

Steps:
1. Sign in as `qa-admin@flowinqa.com`, land on `/dashboard`.
2. Navigate directly (cold, fresh page load) to `/runs/<id>` for a completed
   run.
3. Click the **Audit** tab.
4. Inspect network requests to `/api/runs/<id>/*`.

Observed on every attempt, across two different completed run ids
(`8088430c-32aa-4551-ad24-f5fd806e872b` and
`8091de6b-3350-41fa-9ae1-b19c6ca422a9`):

- `GET /api/runs/<id>/gate-events` — 2x
- `GET /api/runs/<id>/validation-results` — 2x
- `GET /api/runs/<id>/exec-runs` — 2x
- `GET /api/runs/<id>/hook-runs` — 2x
- `GET /api/runs/<id>/family` — 2x (also duplicated, not part of the original
  report but visible in every attempt)

Expected: each of these endpoints fires once per Audit tab open.

### Attempts

| Cycle | Run id | Cold start | gate-events | validation-results | exec-runs | hook-runs |
|---|---|---|---|---|---|---|
| 1 | 8088430c-... | fresh nav to /runs/<id>, then click Audit | 2x | 2x | 2x | 2x |
| 2 | 8088430c-... (same run, fresh nav repeated) | fresh nav, then click Audit | 2x | 2x | 2x | 2x |
| 3 | 8091de6b-... (different run) | fresh nav, then click Audit | 2x | 2x | 2x | 2x |

The original report (BUGS.md#qa-ps-048) additionally claims the full
`GET /api/runs/{id}` record is fetched 3x on Audit tab switch. That specific
3x count for the bare run record was NOT observed in this validation — the
bare run record fetch fired once per attempt here (a much smaller run than
the reporter's 2.2M-token run: 249K tokens vs 2.2M tokens). The 2x duplication
of the four Audit-specific endpoints (`gate-events`, `validation-results`,
`exec-runs`, `hook-runs`) IS confirmed 3/3, independent of run size. This
narrower reproduction is what this card records; analyze should investigate
whether the run-record 3x scales with run size / payload before assuming it
is the same mechanism as the 2x endpoint duplication.

### Files

`frontend/src/components/results/AuditTab.tsx` has exactly one `useEffect`
issuing `Promise.all([getRunGateEvents, getRunValidationResults,
getRunExecRuns, getRunHookRuns])` keyed on `workflowRunId` — so a single
mounted `AuditTab` does not self-duplicate its own fetches. `AuditTab` is
imported and rendered from three places:
`frontend/src/components/preview/PreviewPanel.tsx:1935` (conditional on
`activeTab === "audit"` inside `AnimatePresence`), and
`frontend/src/components/history/WorkflowHistory.tsx:1121` (conditional on
`detailTab === "audit"`, a separate history/detail-panel context) — each
site renders `AuditTab` singly in its own ternary/conditional, not paired.
Root cause for why the SAME endpoint fires twice per open — a double mount
(e.g. React effect re-run, or two components independently importing the
same fetch helpers) versus a genuine double-render from `AnimatePresence`
transition overlap — is not established here; this is a validate-phase card,
not an analyze-phase one. Next investigation should trace whether
`AuditTab` itself mounts twice (React DevTools profiler / component tree)
or whether `PreviewPanel.tsx` and `WorkflowHistory.tsx` are BOTH mounted at
once on `/runs/<id>`.

## Root cause (ANALYZE PHASE — QA-PS-048)

`frontend/src/components/results/AuditTab.tsx:463-609`:

```tsx
useEffect(() => {
    if (!workflowRunId) return;
    const token = getToken();
    if (!token) return;
    let cancelled = false;
    setLoading(true);
    Promise.all([
      getRunGateEvents(token, workflowRunId),
      getRunValidationResults(token, workflowRunId),
      getRunExecRuns(token, workflowRunId),
      getRunHookRuns(token, workflowRunId).catch(() => ({ hook_runs: [] })),
    ])
      .then(([gates, validations, execs, hooksEnv]) => {
        if (cancelled) return;
        ...
      })
    ...
  }, [workflowRunId]);
```

One effect, keyed only on `workflowRunId`. `cancelled` blocks the `.then()`
state writes, never the fetch calls themselves — there is no in-flight or
StrictMode guard of any kind. `frontend/next.config.ts` (read in full: only
`devIndicators`, `output`, `rewrites`, `redirects` are set) carries no
`reactStrictMode: false` override, and this repo is on Next 16.2.4 (App
Router), where Strict Mode defaults to `true`. `next dev` mounts every
component twice (mount → cleanup → mount), so this one effect's four-way
`Promise.all` fires each endpoint twice per Audit tab open — exactly this
card's own 3/3 validation result (`gate-events`, `validation-results`,
`exec-runs`, `hook-runs`, and `family` all observed x2).

None of the four fetchers use this file's own existing dedupe helper.
`frontend/src/lib/api.ts:386-426` (`cachedGet()`) is a TTL-cached GET
wrapper whose own comment says it exists to "absorb React StrictMode's
mount->unmount->remount double-invoke in dev" (citing ISS-782) -- it already
backs `getAnalyticsSummary` and the capability-catalog/preferences reads.
`getRunGateEvents` (`api.ts:2379`), `getRunValidationResults` (`api.ts:2400`),
`getRunExecRuns` (`api.ts:2422`) and `getRunHookRuns` (`api.ts:2296`) all
call the bare `request()` (`api.ts:367`) directly instead. `request()` /
`fetchWithAuth()` has exactly one in-flight guard in the whole file --
`refreshOnce()` (`api.ts:225-234`), scoped to token refresh only -- plus a
second, narrowly-scoped `inFlightWorkflows` map (`api.ts:871`) that covers
only `getWorkflows()` (added by [FIX-616](20260922-1923-FIX-616.md) for a
different bug). Every other GET, including all four Audit endpoints, is
unguarded.

**This is answered: not two components racing.** `AuditTab` has exactly two
mount sites -- `PreviewPanel.tsx:1935` (`activeTab === "audit"`) and
`WorkflowHistory.tsx:1121` (`detailTab === "audit"`) -- but they are gated by
mutually exclusive `mainView` branches in `DashboardLayout.tsx`
(`mainView === "execution"` vs `mainView === "history"`, confirmed by
reading `DashboardLayout.tsx:2936` for `mainView === "history"` vs
`DashboardLayout.tsx:3168` for `mainView === "execution"`, whose own
`<PreviewPanel>` mount is at `DashboardLayout.tsx:3303`): on the cold-nav ->
click-Audit path this card's own reproduction used, only the `execution`
branch (`PreviewPanel`) is ever mounted, so only ONE `AuditTab` instance
exists. The 2x is Strict Mode re-invoking that one instance's effect, not a
second component mounting alongside it.

**Not confined to the Audit tab** -- the identical no-guard shape reproduces
in the other tabs this bug (QA-PS-048) reports:

- Steps tab: `AgentThinkingTab.tsx:167-180` independently calls
  `getRunGateEvents` AGAIN (its own "gate strip" UI, comment tag RUNUI-06),
  keyed on `[runId]` where `runId = pipelineState?.pipelineRunId` -- a
  second, separate caller of the same endpoint AuditTab already fetches.
- Workspace tab: `SandboxTab.tsx:1035-1066` independently calls
  `getRunSandbox`, keyed on `[runId, selectedRef, setMedia]`.
- Every tab, mount-time (not tab-keyed): `PreviewPanel.tsx:1341-1401`'s
  download-button-resolution effect ALSO calls `getRunSandbox` (when
  `pipelineState?.deliverableFilename` is falsy -- true for a reopened
  completed run with no live pipeline state, exactly this bug's own repro
  step "open a completed run from history") and conditionally `getWorkflow`,
  keyed on `[activeRunId, headerRunState, sandboxSelectedRef,
  pipelineState?.deliverableFilename]` -- independent of `SandboxTab`'s own
  fetch. Two unguarded `getRunSandbox` callers x Strict Mode's 2x each =
  4 -- matching BUGS.md's reported `sandbox x 4` exactly.

`getWorkflow` (`api.ts:1003-1012`, the function behind the reported
"829 KB full run record") has at least 8 distinct unguarded call sites
app-wide: `page.tsx:2918`, `DashboardLayout.tsx:2345,2815,3368`,
`PreviewPanel.tsx:880,983,1380`, `AgentThinkingTab.tsx:226,235,243`,
`FilesTab.tsx:517`, `StartingPointCard.tsx:95`, `WorkflowHistory.tsx:372,393`
-- none behind `cachedGet()` or any dedupe. [BUG-030](20260826-1403-BUG-030.md)
(resolved) already ruled out the most obvious repeat-fetch source for a tab
click specifically: a tab click is `window.history.pushState`, not
`router.push`, so `page.tsx` no longer remounts and
`handleSelectWorkflowRun`'s own `getWorkflow` call does not refire per tab
click. The reported "x3" on the full run record does NOT reproduce with a
single clean mechanism on this card's own validation run (fired 1x, not 3x,
on a smaller run -- see "Attempts" above) -- it is inferred to be the same
defect class landing on a different subset of these 8+ call sites depending
on which tabs get visited and whether the open run carries a
`parentRunId`/pinned-version relationship (the original report's run was
2.2M tokens, large enough to plausibly exercise `AgentThinkingTab`'s
parent/self/diverted-run lookups or `StartingPointCard`'s root-run lookup,
neither of which fires on the smaller validation run). Settling the exact
multiplier needs a live repro on a comparably large multi-revision run with
the network panel reset between EACH tab click, isolating which call
site(s) fire -- not yet done here; filed as [ISS-831](20260922-2003-ISS-831.md).

**Fix belongs in one place.** Route the read-only GETs above through the
existing `cachedGet()` helper (`api.ts:386-426`) the way `getAnalyticsSummary`
already does, or generalize an equivalent GET-scoped in-flight/TTL map
directly into `request()`/`fetchWithAuth()` so it covers all of Audit's 4 +
sandbox's 2 + `getWorkflow`'s 8+ + `getRunFamily`'s 4 call sites at once. A
guard added only inside `AuditTab.tsx`'s own effect would leave
`AgentThinkingTab.tsx`, `SandboxTab.tsx`, `PreviewPanel.tsx`'s own effect,
and every `getWorkflow`/`getRunFamily` caller still unguarded -- the same
"fix in the shared layer, not per-component" conclusion independently
reached the same day for the sibling routes analyzed for QA-PS-041
([ISS-788](20260922-1816-ISS-788.md)), QA-PS-042
([ISS-816](20260922-1931-ISS-816.md)), QA-PS-043
([ISS-819](20260922-1940-ISS-819.md)) and QA-PS-044
([ISS-794](20260922-1827-ISS-794.md)).
