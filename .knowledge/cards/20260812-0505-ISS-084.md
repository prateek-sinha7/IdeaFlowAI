# ISS-084

## Title

**Stop / cancel does not stop a building run. `POST /api/runs/{id}/cancel` returns `HTTP 200 {"ok":true,"cancelled":true}` and the run keeps generating.** Confirmed twice, independently: the owner clicked **Stop** in the UI on run `d5dbc9f2` and it did not stop; I then called the REST endpoint directly and got a success response while the event stream kept flowing — **109 new `agent_chunk` events in the following 20 seconds**, and 311 more after that. **Zero `pipeline_cancelled` events were ever emitted** for the run, so nothing downstream (UI, DB status, cost accounting) is told either. The run row stays `generating` forever. Escalation path measured: `SIGTERM` to the uvicorn process was ALSO ignored — the process stayed alive and kept driving the run; only `kill -9` stopped it. So there is currently **no working way for a user to stop a run that has entered the build task-loop**, and each un-stoppable prototype build is a 5-21M-token spend. Related but NOT the same as the known clarify-gate Stop no-op fixed in quick-260720-ec4 (that one was at a clarify/declared gate; this is mid-build). Suspected same family as the finding in the ISS-078 investigation that the dispatch loop (`engine.py:2492-2499`) does not `break` on `pipeline_cancelled` — that would explain a cancel flag being set while the loop keeps dispatching. **Do not fold into ISS-078**; that row is about resume, this is about cancel.

## Severity / Tag / Status (original row)

- Sev: **CRITICAL** (raised from major)
- Tag: product,api,engine
- Status: **FIXED — FIX-227 / TEST-011 (quick-260812-7sk), commit `ebf83005`, 2026-08-12. Offline-proven end-to-end (real resume drive, real durable store, scripted model); deliberately NOT live-proven — this defect was found because a resumed build burned 16.5M tokens, so no run was launched, resumed or gate-approved to verify it.** Original report follows. **ROOT CAUSE (proven, offline-reproduced):** `ExecutionEngine._drive_resumed_stream` (`engine.py:8274-8332`) takes **no `cancel_event` parameter and passes none** to `_execute_impl`, whose default is `None` (`engine.py:1096`). Every kernel guard reads `if cancel_event and cancel_event.is_set()`, so with `None` **all 12 short-circuit**. Separately, `run_engine._register_resume_task` (`:520-521`) and `run_commands.py:436` mint an **orphan `asyncio.Event` into `_CANCEL_EVENTS`** for exactly these runs — so `cancel_run` (`run_commands.py:335-338`) finds one, sets it, and returns `cancelled: true`. **Nobody reads it.** The false ack is a second, separate defect: the API asserts success for something it never verified. **CORRECTED FORENSICS — my first reading was wrong and the truth is worse.** I reported this run as "orphaned at `generating`". It is not: it reads **`completed`**, having run to `pipeline_complete` at 03:08:21 and billed **16,530,718 tokens total, of which 7,510,082 (45%) were billed AFTER the API returned `cancelled: true`**. **Zero `pipeline_cancelled` events exist on the run**; the entire database contains exactly ONE such event ever, and its payload shows it came from a destructive `task.cancel()`, not a cooperative Stop. **The escalation ladder is broken at every rung:** (1) UI Stop — no effect; (2) `POST /cancel` — returns 200 `cancelled:true`, no effect; (3) `SIGTERM` — ignored, because local uvicorn runs without `--timeout-graceful-shutdown` (only `docker-entrypoint.sh:35` passes it) so it waits forever on the live SSE stream and `lifespan.shutdown()` never runs (documented verbatim at `run_shutdown.py:8-13`), and `SHUTDOWN_STOP_RUNS` defaults **False** so it would not stop drivers anyway; (4) `kill -9` — stops that process, **but the next startup AUTO-RESUMES the run** (`restore_non_terminal_runs`, `main.py:203`, `run_engine.py:482+`) and drives it to completion. Measured exactly that: the replacement backend started 03:03:36 and emitted `pipeline_start` at 03:03:38, then ran the build to completion. **So restarting the backend to stop a run causes the run to finish.** **REGRESSION, not always-broken:** the gap dates to `83cfff4c` (2026-06-11), but `849e536d` / KAN-88 (2026-06-30) **removed the working destructive fallback** (`elif … current_pipeline_task.cancel()` in the old WS handler) on a false premise stated in its own comment — that `resume_run` checks the event. Phase 44's REST port then dropped the fallback entirely. **FIX (one change covers every loop):** all four resume drivers funnel through `_drive_resumed_stream`; thread the signal there via an injected hook wired in `main.py` (keeping the kernel free of `app.api`, per Ports & Adapters), make `_CANCEL_EVENTS[run_id]` the **same object** the engine reads, make the ack honest, and reuse `stop_pipeline_drivers`' bounded escalation as fallback. **Rejected hack:** unconditional `task.cancel()` — reintroduces the ISS-007 race and leaves the row non-terminal. **ISS-078's hypothesis is REFUTED as the cause** — `engine.py:2492-2499` does lack a break (real, but bounded by `_run_agent`'s terminal guard at `:3299`); ISS-084 originates upstream of every loop. **Why tests missed it:** `tests/unit/test_rest_answers_cancel.py:210-224` seeds `_CANCEL_EVENTS` itself and asserts only that the endpoint set it — it asserts the one thing that still works. No test asserts that a drive observes the event, that `pipeline_cancelled` is emitted, or that the run status flips. Fix is additive, all-default-`None`, offline-testable, needs no live run.

## Source / Evidence

Found live 2026-08-12: owner clicked Stop in the UI (reported: "i tried to stop visually and it didnt stop that run"); I reproduced via `POST /api/runs/{run}/cancel` with a valid owner token — `HTTP 200 cancelled:true`, then measured `MAX(seq)` twice 20s apart (33638 → 33747, still climbing). Backend restart with SIGTERM did not stop it; `kill -9` on pid 63746 did. Final run state: status stuck at `generating`, orphaned, 0 `pipeline_cancelled` rows. **RESOLVED 2026-08-12 (FIX-227 / TEST-011, commit `ebf83005`, branch `bugfix/spec-revision-context-loss`, NOT pushed):** the signal now reaches the kernel. `_drive_resumed_stream` — the ONE funnel all four resume drivers pass through — resolves the run's cooperative Event via a new INJECTED hook (`engine._resume_cancel_event`, wired once in `main.py` beside the five existing resume hooks, so the kernel still imports no `app.api`; lint-imports 4 kept / 0 broken) and hands it to `_execute_impl`, lighting all twelve armed boundaries at once. `run_engine._resume_cancel_event` is now the ONLY resume-path mint site (get-or-create), so `_CANCEL_EVENTS[run_id]` **is** the object the engine reads — the orphan is superseded, not left alongside (INV-12), and asserted by an object-**identity** test. `cancel_run` no longer reports registry mutation as cancellation: liveness (`_is_run_live`, the driver task) is the truth condition and the answer is `accepted`/`status: "stopping"`, never an unearned `cancelled: true`. `stop_pipeline_drivers`' drain-then-`task.cancel()` body was extracted to `_drain_then_cancel` and reused by a new per-run `stop_run_driver` — one escalation policy, not two — which afterwards calls the existing `_reconcile_terminal_status` so a force-cancelled run cannot be left non-terminal. **The 4-rung ladder is closed except rung 3** (see ISS-088 for the SIGTERM half, which is operational, not engine). **Terminal-state proof, the part that makes the difference:** the offline end-to-end test asserts the cancelled resume dispatches ZERO agents, persists exactly one `pipeline_cancelled` to `run_events`, and leaves `WorkflowRun.status = "cancelled"`; a separate test then runs a fresh `restore_non_terminal_runs()` and asserts it adopts nothing. Both were seen RED by mutating the one root-cause line back, reproducing the production symptom verbatim — *"a cancelled resume kept dispatching agents: {'a': 2, 'b': 2} -> {'a': 4, 'b': 4, 'c': 2, 'd': 2}"* and *"the next boot re-adopted a run the owner paid to stop"*. Goldens **10/10** and lint-imports **4 kept / 0 broken**, both identical to `1ed94666`, no golden regenerated; `test_restart_resume.py` held at its 7 failed / 48 passed ISS-078 baseline. **Not fixed here, deliberately:** the four loops that read no cancel flag at all (`engine.py:2492` forwarding, `:3318` redo, `task_loop.py:492` validator, the fan-out family) — one variable at a time, they belong with ISS-078; and a cancel is still purely in-process (ISS-089 territory — a Stop that arrives with no live driver returns `accepted:false` honestly, but the next boot still auto-resumes the run).
