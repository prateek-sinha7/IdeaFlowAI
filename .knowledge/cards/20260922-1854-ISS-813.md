# ISS-813

## Description

INFERRED sibling of **QA-PS-041** ([ISS-788](20260922-1816-ISS-788.md)). ISS-788
proved the My Workflows LIST page (`SavedWorkflowsPage.tsx`) duplicates its
`GET /api/user-workflows` fetch because its mount effect carries no
StrictMode/in-flight guard. The same catch-all page (`[...view]/page.tsx`)
hosts two more mount effects, for the two other screens the "My Workflows"
feature routes to, built on the identical shape. Not yet reproduced or
measured — filed as a lead, not a confirmed defect.

## Why the root cause implies this

`frontend/src/app/[...view]/page.tsx` has two more effects that each fetch a
single saved-workflow row, both with the same `let cancelled = false` /
cleanup-only guard already shown (by ISS-788, ISS-794) to be insufficient
against a doubled mount:

- `/workflows/{id}/edit` — lines 3671-3722, `userWorkflowsApi.get(workflowId)`,
  deps `[viewPathKey, isAuthenticated]`. The comment at line 3670 ("T8 ...
  same shape as T7") is the code's own admission this is a copy of another
  unguarded fetch effect.
- `/workflows/{id}` (read-only detail view) — lines 3730-3773, the same
  `userWorkflowsApi.get(workflowId)` call, same deps.

Both re-run on `isAuthenticated`, the exact flag ISS-794 already proved flips
through a doubled mount: `page.tsx:881-902`'s auth-check effect (`dispatch
(signedIn(...))` + `getMe(storedToken)`, read directly and confirmed
line-for-line against ISS-794's own citation) fires twice per load under
`next dev`'s StrictMode remount, with no dedupe guard of its own. Since these
two workflow-row effects key off the same flag and carry no request-level
dedupe either, the identical doubling ISS-788 measured for `getUserWorkflows()`
on the list page plausibly reproduces here for `userWorkflowsApi.get()` on the
two single-row screens.

## Where the fix would belong (if confirmed)

Not the same choke point as `getUserWorkflows()` / `getWorkflows()` / `getMe()`.
Those three all go through `lib/api.ts`'s `request()`, which already has one
dedupe precedent to mirror (`inFlightRefresh`, `lib/api.ts:225-233`).
`userWorkflowsApi.get()` (`frontend/src/store/api/userWorkflows.ts:862-865`)
goes through a SEPARATE client — `store/api/http.ts`'s axios instance,
confirmed by page.tsx's own comment at line 3705 ("unlike
handleSelectWorkflowRun's fetch (lib/api.ts's request()), userWorkflowsApi.get()
goes through store/api/http.ts's axios pipeline") — and `store/api/http.ts`
has no dedupe/cache mechanism at all (`grep -n "cache\|inFlight\|dedup"
frontend/src/store/api/http.ts` returns nothing). A fix here cannot just
mirror `lib/api.ts`'s pattern onto a different file; it needs either a new
in-flight-promise guard added to `userWorkflowsApi.get()` itself (keyed by
`workflowId`, so two DIFFERENT ids in flight don't collide with each other),
or a ref-guarded mount effect in `page.tsx`, the same shape ISS-794 proposes
for the auth-check effect itself.

## Expected vs actual (to be measured)

Expected: `GET /api/user-workflows/{id}` fires once per cold or client-side
load of `/workflows/{id}` or `/workflows/{id}/edit`.

Actual: unmeasured — this card is a lead. Settling it needs a `next dev`
network capture on both routes, the same method ISS-788 used
(`performance.getEntriesByType('resource')` across 3 cold-start cycles).

## Related

Sibling of [ISS-228](20260828-1758-ISS-228.md) — the third `/workflows/{id}`
sub-route (`/run`) already has its own filed issue (LaunchWizard fires two
GETs in parallel, an ordering problem). This card is about request COUNT on
the other two sub-routes, not ordering, so it is a distinct finding rather
than a duplicate.

## Update — 2026-09-22 (5-fixer): measured, does not reproduce

The capture this card asks for is in [ISS-841](20260922-2050-ISS-841.md). Both
routes fetch their row **once** per cold load, with and without the guard this
card prescribes, so the guard was built, measured and reverted — nothing under
`frontend/src/store/api/` changed. The client-side-nav entry path is still
uncovered, which is why this card is left open rather than superseded. Note the
blast radius is now THREE effects, not two: `page.tsx:3777` (`/edit`), `:3833`
(`/workflows/{id}`) and `:3923` (`/workflows/{id}/run`).
