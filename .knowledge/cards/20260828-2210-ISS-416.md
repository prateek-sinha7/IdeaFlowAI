## What happened (sibling, derived from ISS-303's root cause — analyzer pass on BUG-20260828-050115-library)

[ISS-303](20260828-1935-ISS-303.md) confirmed that `LibraryPage.tsx`'s cold-mount URL-seed effect
opens the agent detail drawer for a `BETA_WORKFLOWS` ("Coming Soon") agent id with no membership
check, even though the grid's own `onClick` correctly blocks the click. Re-reading the same effect
in full (`frontend/src/components/library/LibraryPage.tsx:589-614`) shows it has THREE branches —
agents, skills, hooks — sharing one `useEffect`. The skills branch has the identical shape as the
already-confirmed agents branch, and the identical omission:

```ts
} else if (librarySlug.type === "skills" && skillsStatus === "succeeded") {
  const skill = SKILLS.find(s => s.id === librarySlug.slug);
  if (skill) {
    setMainTab("skills");
    setSelectedSkill(skill);
    librarySlugAppliedRef.current = true;
  }
}
```
(`LibraryPage.tsx:598-604`) — `SKILLS` (line 498, `useSkillsCatalog()`) is the full, unfiltered
catalog array, so `SKILLS.find` matches a beta skill's id exactly as readily as a released one, and
nothing here checks `skill.isBeta` before calling `setSelectedSkill`.

## Root cause

CONFIRMED by direct read — the Skills tab has its own "Coming Soon" click-gate, structurally
identical to the agents grid's `BETA_WORKFLOWS` gate ISS-303 already documents:

- `LibraryPage.tsx:699-700`: `const activeSkills = filteredSkills.filter(s => !s.isBeta); const
  betaSkills = filteredSkills.filter(s => s.isBeta);`
- `LibraryPage.tsx:897-927` (active skills grid): each `Card` carries `onClick={() => {
  setSelectedSkill(skill); router.push(routes.librarySkill(skill.id)); }}`.
- `LibraryPage.tsx:939-961` (the "Coming Soon" section, confirmed rendered only when `betaSkills.length
  > 0`, line 932): each `Card` has **no `onClick` prop at all** — genuinely inert, exactly like
  [ISS-271](20260828-1851-ISS-271.md) already documented for this same grid from the keyboard-access
  angle ("beta/Coming-Soon skill cards are unaffected (no onClick)").
- `SkillDetailModal` (`LibraryPage.tsx:197`) takes only `{ skill, onClose }` — no `isBeta` prop at
  all — so even if it wanted to render a locked/unavailable state for a beta skill, it has no signal
  to do so with.

So the same two-path shape ISS-303 found for agents (a real click-gate in the grid; zero gate in the
URL-seed effect) exists for skills too, in the very same effect, one `else if` branch below the
agents one.

## Expected vs actual

Expected (mirrors ISS-303): a skill id inside `betaSkills` (i.e. `skill.isBeta === true`) should be
unreachable by direct URL to `/library/skills/{id}`, matching the grid's own click-blocking — or at
minimum the detail view should communicate the unavailable state, which it structurally cannot today
since `SkillDetailModal` is never told `isBeta`.

Actual (INFERRED from the code, not yet reproduced live — see below): a direct cold load of
`/library/skills/{beta-skill-id}` would open the identical, fully-rendered `SkillDetailModal`
(full markdown content, working Copy button) for a skill the catalog is displaying as `opacity-60
cursor-not-allowed` / "Coming Soon" in the same grid.

## Confidence and what would confirm or refute this

**CONFIRMED — the mechanism.** Both branches of the one effect, and both grids' click-gate shapes,
were read directly at the lines cited above; the agents/skills asymmetry with the URL-seed effect is
not inferred, it's the same code pattern twice.

**INFERRED — that this is live today.** Live reproduction is currently blocked, not just undone:
`grep -rl "isBeta:\s*true" backend/skills/global/*/SKILL.md` returns zero of the 186 skill folders
(only 52 even carry an explicit `isBeta: false`; the rest default to `False` via
`skills_catalog.py:113`, `metadata.get("isBeta", False)`). So `betaSkills` is an empty array in this
environment right now, the "Coming Soon" skills section never renders, and there is no live skill id
to cold-load and prove the drawer opens. This is a latent defect in shipped code behind a feature flag
with no current instance, not a guess about behavior that might not exist — the `isBeta` plumbing
is real end-to-end (`SkillDef.isBeta` in `frontend/src/store/api/skills.ts:12,28`, `HookDef.isBeta`
likewise, `useSkillsCatalog.ts:23` normalizing it, and the whole "Coming Soon" section keyed on it),
just currently zero-instance.

**Settle it**: set `isBeta: true` in any one `backend/skills/global/{id}/SKILL.md`'s frontmatter (or
add a temporary fixture skill), restart/re-scan the catalog cache, cold-load
`/library/skills/{that-id}`, and confirm whether `SkillDetailModal` opens. Same evidence shape ISS-303
already produced for agents.

## Scope note — hooks are NOT a sibling of this

The third branch of the same effect (`librarySlug.type === "hooks"`, `LibraryPage.tsx:605-611`) was
checked too. `HookDef` also carries an `isBeta?: boolean` field
(`frontend/src/store/api/hooks.ts:14`), but `LibraryPage.tsx`'s hooks grid (`filteredHooks`,
lines 702-708, rendered 990-1022) applies no `isBeta` filter anywhere — every hook, beta or not,
renders as a fully clickable card with a working `onClick`. There is no click-gate for hooks to
begin with, so there is nothing for the URL-seed effect to bypass. Not filed as a sibling.
