## Why this must also be broken (derived from [ISS-607](20260829-1450-ISS-607.md)'s root cause)

ISS-607 root cause #1 traced the version-picker no-op to `handleSelectVersion`
(`frontend/src/components/preview/PreviewPanel.tsx:570-593`), reproduced by the hunter/validator
starting from the **Steps** tab specifically. Reading the function shows nothing in its logic is
Steps-specific:

```
570  const handleSelectVersion = useCallback(async (memberId: string) => {
...
577    const memberIdx = sortedMembers.findIndex((m) => m.id === memberId);
578    onTabSelect?.(activeTab, memberId === latestId || memberIdx < 0 ? null : String(memberIdx + 1));
579    if (memberId === latestId) {
580      setViewingVersion(null); // back to live
581      return;
582    }
```

`activeTab` (line 578) is read from whatever tab happens to be mounted — `RunHeader`, which owns
the version-picker button (`RunHeader.tsx:38-73` wires `onSelectVersion` straight to this
function), is rendered once per `PreviewPanel` mount and is visible identically on every tab
(Preview/Steps/Files/Workspace/Audit all share the one `PreviewPanel` instance —
`DashboardLayout.tsx:3127` is the only mount site app-wide). The `memberId === latestId` branch
that swallows the click (ISS-607's defect #1) does not read `activeTab` at all — it fires
whenever the clicked member equals the newest family member, regardless of which tab initiated
the click. `DashboardLayout.handlePreviewPanelTabSelect` (`DashboardLayout.tsx:479-515`), the
consumer, builds its `routeMap` (lines 492-497) with one entry per tab and applies the identical
`pin`/`targetRoute===window.location.pathname` guard (line 501) to all five — nothing there
special-cases Steps either.

## Reproduction condition (not yet re-driven through the browser)

Same live pair as ISS-607 (root `636ff908-...` v1 / revision `2ac66bbd-...` v2), but starting
from `/runs/636ff908.../files` (or `/preview`, `/workspace`, `/audit`) instead of `/steps`.
Expect the identical failure: clicking "Version v2" in the picker leaves `window.location`
unchanged, the picker still reads "Version v1", and the tab's content stays on v1.

## Expected vs Actual

**Expected:** the version picker works the same on every tab — selecting the newest family
member from any of Preview/Steps/Files/Workspace/Audit navigates to that revision's content.

**Actual (inferred):** the no-op ISS-607 documented for Steps reproduces identically on the
other four tabs, since `handleSelectVersion`/`handlePreviewPanelTabSelect` treat `activeTab` as
an opaque pass-through, not a branch condition.

## Fix direction

Not a separate fix from ISS-607 — the correct fix for ISS-607's defect #1 (stop conflating
"clicked member equals the newest family member" with "the currently-live run is already that
member" — see ISS-607's root cause) lives in `handleSelectVersion` itself, the one chokepoint
every tab's picker click already routes through. Fixing it there closes this card for free; no
per-tab guard is needed or wanted.
