## What happened

On `/workflows` (Saved workflows / "My Workflows" list), clicking "Workflow actions" ->
"Delete" on any saved-workflow card opens a confirmation dialog whose text is
static and generic — heading "Delete workflow", subtext "This cannot be undone", body
"The saved workflow will be permanently removed from your saved workflows." — with
**no workflow title, id, or any other identifying detail**, confirmed via the full
accessibility tree (not just the screenshot). The list routinely contains many
near-identical rows (four "Signoff Stop-Resume Test…" cards, four "Signoff Composer
Test (API)…" cards distinguished only by a trailing numeric suffix, etc.), so a user
who opens the menu on the wrong lookalike card has zero disambiguating evidence in the
dialog before confirming an irreversible delete.

Register entry: BUG-20260828-052400-workflows.

## Reproduction (3/3, cold start each time, no narrowing needed)

Deterministic on every attempt — same generic dialog text regardless of which card
triggered it:

- **Cycle 1** — cold nav to `/workflows`, opened "Workflow actions" on the "Revision
  Verify Test" card, clicked Delete. Dialog: `heading "Delete workflow"` /
  `"This cannot be undone"` / `"The saved workflow will be permanently removed from
  your saved workflows."` — no card title anywhere in the a11y tree.
- **Cycle 2** — cold nav to `/workflows` again, opened "Hello Multi-Agent Test" card's
  menu, clicked Delete. Byte-identical dialog text to cycle 1.
- **Cycle 3** — cold nav to `/workflows` again, opened "SpecKit Clone" card's menu,
  clicked Delete. Byte-identical dialog text to cycles 1 and 2.

All three cancelled; no deletion performed.

## Root cause

`frontend/src/components/savedworkflows/SavedWorkflowsPage.tsx`:

- `deleteConfirmId` (line 166, `useState<string | null>`) stores only the workflow's
  **id** when a card's Delete menuitem is clicked, never its `name`.
- The confirm dialog (lines 408-444) renders purely static JSX for the heading (425),
  subtext (426) and body (429-431) — it never looks up the row matching
  `deleteConfirmId` in the workflows list to interpolate a name/title, unlike
  `handleRenameSave`'s sibling modal (`NameWorkflowModal`, line 402) which is passed
  `initialName={renameRow.name}` from a full row object (`renameRow`), not just an id.
- `handleDeleteConfirm` (lines 217-218) reads only `deleteConfirmId` and never
  references a name either — the identifying data is dropped at the point the menu
  click sets state, not lost later.

## Expected vs actual

- **Expected:** the confirmation states which workflow will be deleted, e.g.
  `Delete "<workflow title>"?` or the title/id present somewhere in the dialog body,
  so a user can verify the correct row before an irreversible action — especially
  given the list's many near-duplicate names.
- **Actual:** dialog heading and body are fixed strings, identical regardless of
  which card triggered them.

## Blast radius

Grepped every caller of `deleteUserWorkflow` (`frontend/src/lib/api.ts:1911`) in
`frontend/src/`: exactly one production call site,
`SavedWorkflowsPage.tsx:221` (`HomeLaunchGrid.test.tsx` /
`HomeLaunchGrid.crossAccountLeak.test.tsx` mock the whole `@/lib/api` module and never
actually call it — `HomeLaunchGrid.tsx` has no delete affordance). This bug is fully
contained to this one component for the "delete a saved workflow" feature.

The same defect **shape** — an id-only `useState<string | null>` confirm variable set from
a row-click handler, feeding a dialog that renders fully static text with no lookup back
into the loaded rows for a name/label — recurs independently (grepped via `deleteConfirmId`
/ `deleteConfirm` state plus the `"cannot be undone"` / `"permanently"` dialog strings) in
two other, unrelated components with no shared code path to this one:
[ISS-414](20260828-2202-ISS-414.md) (`WorkflowHistory.tsx`'s run-delete `DeleteModal`) and
[ISS-415](20260828-2202-ISS-415.md) (`admin/page.tsx`'s delete-user dialog). Both are
INFERRED/unreproduced — see those cards.

## Fix — where it belongs

The **minimal, in-scope fix** for this card is entirely local to
`SavedWorkflowsPage.tsx` and mirrors a pattern already correct in the same file: the sibling
`onRename` handler (line 346) captures the **whole row** (`setRenameRow(row)`), not just an
id, and `NameWorkflowModal` (line 402) is passed `initialName={renameRow.name}`. Applying
the same shape to delete — store the row (or at minimum its `name`) instead of only
`deleteConfirmId`, then interpolate that name into the heading/body at lines 425 and
429-431 — closes this card without introducing a new abstraction.

Because [ISS-414](20260828-2202-ISS-414.md) and [ISS-415](20260828-2202-ISS-415.md) show
the identical gap already copy-pasted into two more places, a **shared** confirmation-dialog
component (taking a subject label/name prop) that all three routes through would prevent a
fourth copy — flagged here for whoever scopes the fix, not required to close this card alone
since today there is no single function all three already route through.
