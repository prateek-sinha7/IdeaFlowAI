# ISS-950

## Description

This is part B of [ISS-878](20261001-2110-ISS-878.md). [FIX-707](20261002-0134-FIX-707.md) fixed
that card's trigger-path parts (A1, A2) and deferred this part, so it is recorded here and was not
rediscovered. Claim status when filed: **INFERRED**, read from the code and not run. Nothing was resumed.
**Update 2026-10-02 (QA-KB-090 analysis): CONFIRMED**, by reading and by an offline run of the real
`resume_run`. See "Analysis" at the foot of this card.

In `backend/agents/execution_engine/engine.py`, `resume_run` builds its roster for a run with no
persisted manifest as `get_pipeline_agents(resolve_alias(pipeline_type))` (`:15675`). It completes
the roster from the plan only when that list is EMPTY (`:15681-15696`). For
`prototype_v2_revision` the registry roster is 1 agent, while the plan has 3 steps (the
`custom-agent:*` steps are templates the registry skips; see
[ISS-877](20261001-2110-ISS-877.md)).

`_compute_resume_offset` (`:16262`) rebuilds the roster from the plan before it counts
(`:16314`). The offset is therefore relative to 3 steps, but the progress line divides it by
`len(agents)`:

```python
logger.info("resume_run(%s): resuming pipeline=%s at step offset %d/%d", run_id, pipeline_type, offset, len(agents))   # :15718-15724
if offset >= len(agents):                                                                                                # :15725
    logger.info("resume_run(%s): all steps complete — nothing to re-drive", run_id)                                      # :15727-15729
```

An offset of 1 or 2 therefore prints `1/1` or `2/1` and "all steps complete" while steps remain.
The branch only logs. Execution is unaffected: `_drive_resumed_stream` passes the partial roster on
and the `_execute_impl` seam expands it. Since FIX-707 the seam then logs
`roster expanded from plan: ... requested=['prototype-revision-analyzer'] plan=[...3 ids]`, so the
mismatch is visible in the same incident log, but the first two lines are still wrong.
`prototype_v2_feature_revision` (1 of 5) has the same shape. `_replay_clarify_run` has the same
empty-only fallback (`:16145`), but it prints no length-based output.

## Why deferred

- Only log text is wrong.
- The test-writer marked a test for it optional and wrote none.
- The card's claim is INFERRED: no resume of these workflow types was observed.

FIX-707 changed only the two paths that had failing tests.

## Fix (as ISS-878 proposed it)

Use the plan's step count for the denominator and for the all-complete test. `compile_for_run` is
`lru_cache`d, and `_compute_resume_offset` has just compiled the same plan. Wrap the compile so a
failure keeps `len(agents)`, because the line must never abort a resume.

An alternative is to complete a partial roster in `resume_run`'s own seam (`:15681`) with the
`launch_run` rule (`len(agents) < len(plan.steps)`). That also fixes the denominator, and the
engine seam would then not need to expand the roster on resume. Either way the guard is a length
or set comparison, never a workflow name (INV-1).

## Test notes

Drive `resume_run` for a `workflow_runs` row of type `prototype_v2_revision` with no
`manifest_json`. Seed a durable state that yields offset 1, using the `_patch_db` pattern
(`backend/tests/agents/test_phase3_wip_commit.py:255`). Stop the drive after the offset log. Then
assert with `caplog` that the line reads `1/3` and that no "all steps complete" record is emitted.

## Analysis (QA-KB-090, analyzer, 2026-10-02)

**Claim status: CONFIRMED.** The mechanism is read at file:line below, and the symptom was reproduced
offline against the REAL `ExecutionEngine.resume_run`: temp sqlite, in-memory `workflow_runs`, no
Bedrock, no Postgres, no server, no run, `_drive_resumed_stream` stubbed. Evidence is in
`evidence/qa-kb-090/` (`01` source quotes, `02` the probe, `03` its output). Re-run from the repo root:
`backend/.venv/bin/python evidence/qa-kb-090/02-analyze-resume-log-probe.py.txt`.
Tree: working tree on top of `024c03ef8`. Line numbers are that tree's, and other lanes are editing
`engine.py`, so re-find each by function name.

### Root cause (one mechanism, CONFIRMED)

`resume_run` puts two coordinate systems on one line.

- **The roster is the registry's.** For a run with no persisted manifest,
  `agents = get_pipeline_agents(resolve_alias(pipeline_type))` (`engine.py:15675`). The plan completes
  it only when it is EMPTY (`:15681`, `if not agents:`). The registry skips the `custom-agent`
  template (`registry.py:207-213`), so for `prototype_v2_revision` the roster is 1 agent and is never
  empty.
- **The offset is the plan's.** `_compute_resume_offset` (`:16262`) rebuilds its own roster from the
  plan (`:16313-16314`, `if compiled.steps: agents = self._specs_from_plan(compiled.steps)`).
  `_first_incomplete_step` indexes that list, and returns `len(ordered_agents)`, the plan length,
  when every step is done (`:15316`).
- **The line mixes them.** `:15718-15729` prints `offset` over `len(agents)` and tests
  `offset >= len(agents)`.

Observed (probe Q3: the real `_compute_resume_offset`, durable `step_completed` + `agent_complete`
events seeded for `prototype_v2_revision`, plan of 3):

| steps durably complete | real offset | roster handed to the drive | records logged |
|---|---|---|---|
| 0 | 0 | 1 | `at step offset 0/1` |
| 1 | 1 | 1 | `at step offset 1/1`, `all steps complete — nothing to re-drive` |
| 2 | 2 | 1 | `at step offset 2/1`, `all steps complete — nothing to re-drive` |
| 3 | 3 | 1 | `at step offset 3/1`, `all steps complete — nothing to re-drive` (the only true claim) |

`prototype_v2_feature_revision` (1 of 5) prints `0/1`, `1/1`, `4/1`, `5/1` the same way (probe Q2).
The controls read correctly: `user_stories` (6 of 6) prints `2/6`, and `prototype_v2` (empty registry
roster, so the `:15681` fallback completes it) prints `5/11`.

### What is NOT broken, so the fix stays small (CONFIRMED by reading)

- **Execution.** The all-complete branch has no `return`; it only logs. `_drive_resumed_stream`
  (`:15832`) never reads `len(agents)`. `_execute_impl`'s roster seam (`:5004-5015`) expands the
  1-agent roster to the plan before dispatch, and `pipeline_start` reports
  `agent_count: len(ordered_agents)` and `resume_offset` in plan coordinates (`:5752-5775`). So the
  SSE stream, the UI and the dispatch loop are right. Only the two log records are wrong.
- **A DB-manifest resume.** `resumed_compiled` is set, the roster is
  `_specs_from_plan(resumed_compiled.steps)` (`:15672-15673`), and `len(agents)` is already the plan
  length.
- **Fresh launches.** `launch_run` (`run_commands.py:3621-3622`), the trigger path (FIX-707) and
  `_mint_revision_row` (`max(len(_rev_agents), _plan_step_count)`) all size from the plan already.

### Blast radius (every route into the broken lines, grepped)

Production callers of `resume_run`; all reach `:15718-15729`:

1. `restore_non_terminal_runs` branch (b), `engine.py:12844`: auto-resume of an in-flight run after a
   restart.
2. `_rearm_gate_run` review re-entry, `engine.py:12975`: a run parked at a review gate across a
   restart.
3. User `POST /api/runs/{id}/resume`, `_drive_user_resume`, `run_commands.py:792`: resume of a failed
   run. This is the worst reading, because the user pressed Resume and the log says "nothing to
   re-drive".

Workflows affected today (probe Q1 over all 41 supported types): exactly 2, the manifest-less runs of
`prototype_v2_revision` (1 of 3) and `prototype_v2_feature_revision` (1 of 5). Of the other 39, 18
have a registry roster equal to the plan, 19 have an empty roster and take the `:15681` fallback, and
2 (`file_analyst`, `spec_kit`) have no `workflow.yaml`; none is a superset or has drifted. The
condition is structural, not a registry bug: a workflow whose plan mixes `custom-agent:*` template
steps with at least one authored agent, or that reuses another pipeline's agents, gets a non-empty
partial roster (ISS-877).

Nothing parses the two log lines (grep of `backend`, `frontend/src`, `scripts`, `tools`). Their readers
are operators, and the manual resume QA procedure in `.planning/RESUME-QA-TEST-SHEET.md` uses
`at step offset N/M` as its oracle, so a QA run of either workflow would read "all steps complete" on
a run that is about to re-drive steps.

### Where the fix belongs

Complete the roster in `resume_run`'s own seam (`:15681`), not only the denominator.

1. It is the one place all three production callers share.
2. The roster is what executes. Completing it makes the numerator, the denominator and the
   all-complete test agree by construction, and it removes resume's silent dependence on
   `_execute_impl`'s seam to expand a roster that resume itself built (ISS-877, FIX-707). That
   dependence is not guaranteed: [ISS-966](20261002-0320-ISS-966.md) is deciding whether a
   strict-subset roster may run as given, and the seam is where one is re-expanded today. INFERRED,
   conditional on that seam changing: this log-only defect would then become a resume that drives only
   the 1-agent roster it was handed (the offset still counts plan steps, so it would skip straight
   past the fixer and the validator).
3. A denominator-only patch (ISS-878's first sketch) leaves the 1-agent roster in place and needs a
   second compile on the log path.

Rules for the edit (INV-1 / SC-001: a set or length comparison, never a workflow name):

- Use the SEAM's predicate, `{a.id for a in agents} < {s.agent_id for s in compiled.steps}` or an
  empty roster. The QA-KB-090 triage sketch suggests `launch_run`'s `len(agents) < len(plan.steps)`.
  The two agree on all 41 types today and differ only when a registry roster is not a subset of its
  plan (drift): the seam keeps that roster and the length rule would replace it. Matching the seam
  keeps "roster before the seam equals roster after it", so the later expansion becomes a no-op.
- Only when `resumed_compiled is None`; a DB-manifest resume already equals its plan.
- A compile failure with a NON-empty roster must not abort the resume. `file_analyst` and `spec_kit`
  have a roster and no `workflow.yaml` today, and they currently flow into
  `_compute_resume_offset`'s own catch (offset 0, a warning). The abort at `:15690-15694` stays for
  the empty roster only.
- `compile_for_run` is `lru_cache`d (`:3593`), so the extra call costs nothing.
- Edit `_replay_clarify_run` (`:16152-16167`) in the same change. It has the identical empty-only
  fallback and hands the same partial roster to the same drive. It prints nothing length-based, and
  the two partial workflows cannot reach it: both declare `clarify: mode: skip`, and skip mode never
  invokes the ClarifyEngine (`engine.py:5446-5456`), so no `questionnaire_ready` is ever parked. So
  it is not carded as a sibling ([ISS-878](20261001-2110-ISS-878.md) reached the same conclusion),
  but the two resume seams must agree, as `_specs_from_plan`'s own docstring says (`:3995-3997`).
- Optional single home, if the fixer wants one: ISS-878's `ExecutionEngine._complete_roster(agents,
  compiled)`. The same rule now has five spellings: the engine seam (set containment), `launch_run`
  (length), the trigger path (length), `resume_run` (empty only), `_replay_clarify_run` (empty only,
  manifest-less). This card does not require it.

Expected side effect: once `resume_run` completes the roster, the INFO line `roster expanded from
plan` ([FIX-707](20261002-0134-FIX-707.md), `engine.py:5007`) no longer prints on a resume of these two
workflows, because nothing is left to expand. FIX-707 relies on that line to make the mismatch
visible; after this fix there is no mismatch. `test_roster_seam_log.py` drives `execute()`, not
`resume_run`, so no test pins it.
