# FIX-606

Fixes QA-PS-014 (register: `LEDGER.md`, detail: `BUGS.md#qa-ps-014`).
Resolves [ISS-739](20260922-1407-ISS-739.md) (root cause),
[ISS-740](20260922-1408-ISS-740.md) (failed/cancelled/diverted sibling) and
[ISS-752](20260922-1409-ISS-752.md) (Steps tab sibling) — one flag cures all
three, because all three are the same missing signal read by three different
gates.

## What was wrong

Opening a completed run from the history list (`/runs/{id}`) rendered a blank
Preview panel reading **"Output will appear here"** for the several seconds the
run's data took to arrive, with no spinner, skeleton or any other indication
that content was on the way. The blank state was pixel-identical to a
genuinely empty or failed run. The Steps tab was worse during the same window:
its EmptyState told the user to **"Start a pipeline"** for a pipeline that had
already finished running.

## Root cause

`frontend/src/app/[...view]/page.tsx` — `initialMainViewFor` maps all nine
reopened route forms (`run-detail`, `-steps`, `-steps-agent`, `-files`,
`-workspace`, `-audit`, `-stream`, `-version`, `-preview-full`) to
`MainView: "execution"` synchronously off the parsed URL, while the content is
filled in later by `handleSelectWorkflowRun`'s async fetch. No state anywhere
said that fetch was running, so every downstream gate defaulted to its
"nothing here" branch:

- `PreviewPanel.tsx:1055` — `isStillRunning = !!(isStreaming || pipelineState?.isRunning)`
  is `false` for the whole window on a reopened TERMINAL run (no stream is
  attached for a terminal status, and `resetPipeline()` clears `isRunning` at
  fetch start), and `hasContent` (`:1044`) is false until the fetch resolves →
  the neutral `!hasContent` branch fires (ISS-739).
- `PreviewPanel.tsx:1062-1079` — `reopenedRunStatus` is reset to `undefined` at
  fetch start and only set on resolve, so `reopenFailureSignal` /
  `isDivertedTerminal` are false BY CONSTRUCTION and a run about to resolve
  failed/cancelled/diverted shows the same success-shaped neutral copy first
  (ISS-740).
- `AgentThinkingTab.tsx:259-261` — `hasAnyData` is false for the same window
  (empty `agents`, no `runInput` yet) → `EmptyState` with its "Start a
  pipeline" copy (ISS-752).

## What changed and why there

ONE new boolean, `isLoadingRunData`, owned by the fetcher and threaded down the
existing `reopenedRunStatus` path — the same four files that prop already
crosses, in the same positions:

1. `frontend/src/app/[...view]/page.tsx`
   - new `useState(false)` beside the other reopen state;
   - `setIsLoadingRunData(true)` immediately before `handleSelectWorkflowRun`'s
     `try`, and a new `finally { setIsLoadingRunData(false) }` on its existing
     try/catch — so it clears on resolve, on error, and on the bounded
     403/404 retry's early `return` (the retry re-enters the same function and
     sets it again);
   - passed to `<DashboardLayout isLoadingRunData={...}>`.
2. `frontend/src/components/layout/DashboardLayout.tsx` — prop + pure
   passthrough to the single production `<PreviewPanel>` mount.
3. `frontend/src/components/preview/PreviewPanel.tsx` — prop, a new
   `RunDataSkeleton` (the in-repo `shimmer-effect` + `bg-surface-warm` idiom
   already used by `LibraryPage`/`HomeLaunchGrid`), and ONE new branch in the
   preview cascade sitting directly ahead of `!hasContent`; the same prop is
   handed to its `<AgentThinkingTab>` mount.
4. `frontend/src/components/results/AgentThinkingTab.tsx` — prop, and
   `EmptyState` gained a `loading` variant (shimmer + `aria-busy` + copy that
   says the trace is loading); `if (!hasAnyData) return <EmptyState loading={isLoadingRunData} />`.

**Why there, not at the call sites.** Blast radius re-verified at fix time, not
taken on trust: `grep -rn "<PreviewPanel" frontend/src` returns exactly ONE
production mount (`DashboardLayout.tsx:3285`), and `grep -n
"handleSelectWorkflowRun" frontend/src/app/[...view]/page.tsx` shows all four
call sites (`:3271` retry, `:3434` and `:3639` cold deep-link restores, `:4275`
`onSelectWorkflowRun`) funnel through the one fetch. Setting the flag inside
that fetch therefore covers every one of the nine reopened route forms with no
per-route and no per-tab patch.

Ordering note: the branch sits AFTER the failure/diverted affordances and
`isStillRunning`, and BEFORE `!hasContent`. That placement is what makes ISS-740
fall out for free — during the fetch the affordances cannot fire, so the loading
branch is the first one that can, and once the fetch resolves the real
affordance wins on the very next render.

## Deliberately not changed

- `WorkflowHistory.tsx:1111`'s `<AgentThinkingTab>` mount (the in-list embedded
  preview) is a different surface with its own loading flag in
  `RunDetailPage.tsx:75-76`. The new prop is optional, so that mount is
  untouched and behaves exactly as before.
- No header/tab-set changes. `headerRunState` and `visibleTabs` still flip when
  the fetch resolves; no card asked for that and changing it would alter the
  ISS-017/Phase 42-03 failed-run tab contract.
- Pre-existing lint errors in both edited React files (`react-hooks/immutability`,
  `react-hooks/refs`) and a pre-existing failure in
  `PreviewPanel.test.tsx` ("mounts the run header and exactly ONE version
  affordance") are untouched. The latter is caused by
  `RunHeader.tsx`'s `getRunSandboxRefs` call missing from that test file's
  `vi.mock("@/lib/api")` factory (`PreviewPanel.test.tsx:21-30`) — an unmodified
  file and an unrelated mock gap; mentioned, not fixed.
