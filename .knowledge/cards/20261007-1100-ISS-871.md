## Root cause

CONFIRMED from code at `frontend/src/app/[...view]/page.tsx` and `frontend/src/lib/api.ts`.

When a user clicks a **completed** run from the history list, two code paths both
execute the full event-loading sequence for the same run:

**Path A — `handleSelectWorkflowRun` (the history click handler, page.tsx ~line 2883):**
1. Calls `getRunEvents(currentToken, fullRun.id)` — CALL 1 (main run)
2. Calls `getRunFamily(currentToken, fullRun.id)` — FAMILY CALL 1
3. For each revision sibling calls `getRunEvents(currentToken, m.id)` — CALL 2 (sibling)
4. Calls `router.push(routes.runDetail(run.id))` to navigate

**Path B — T11 cold-mount effect (page.tsx ~line 3546):**
The `router.push` in Path A causes the `[...view]/page.tsx` component to **remount**.
On remount, the T11 cold-mount `useEffect` fires. For a **terminal** run (not in
`liveRunIds`), the guard at `trackedRunIdRef.current` is reset to null by the remount,
so the early-return does not fire. The effect falls through to call
`handleSelectWorkflowRun` **again**:
1. Calls `getRunEvents(currentToken, fullRun.id)` — CALL 3 (same main run, CONCURRENT)
2. Calls `getRunFamily(currentToken, fullRun.id)` — FAMILY CALL 2
3. For each sibling calls `getRunEvents(currentToken, m.id)` — CALL 4 (sibling again)

`getRunEvents` used a plain `request()` with no in-flight deduplication. Both Path A and
Path B fire concurrently (Path B fires while Path A's 27 s `events?after=0` is still in
flight), so the browser issues two separate 2.5 MB requests instead of sharing the first.

**Why `family x3`:** a third `getRunFamily` is fired from within the
`handleSwitchToLiveRun` path (triggered by another remount-related code path).

**Why only `events?after=0` x3 (not x4):** the `singleFlightGet`-backed `getRunFamily`
returns the same sibling list to both paths. One of the four calls is therefore not seen
as a duplicate — the net observed count is three, matching the bug report.

## Blast radius

- Only the **history-reopen path for completed runs with revision family members** is
  affected. Live runs (in `liveRunIds`) take a different T11 branch.
- The duplication wastes ~20 MB of bandwidth and adds 200+ seconds of blocking wait per
  open (the main-run events payload alone is 2.5 MB at 27 s).
- No data corruption — both paths decode the same events, and `handleWebSocketMessage`'s
  `seenEventIdsRef` dedup absorbs the duplicate frames on the second replay.

## Resolution

[FIX-647](20261007-1100-FIX-647.md): `getRunEvents` in `api.ts` now uses
`singleFlightGet` instead of plain `request()`. Concurrent identical calls (same token +
same URL including afterSeq fragment) share one in-flight promise. Because both Path A
and Path B issue the SAME `events?after=0` URL while the first request is still in
flight, the second call receives the first call's promise instead of launching a new
network request.
