## Summary

On `/create/user-stories`, opening Advanced -> Agents -> any "+ Add agent" canvas placeholder
opens the `AgentLibrary` dialog (`frontend/src/components/workflow/AgentLibrary.tsx`) defaulted
to the **"User Stories"** category tab (`activeCategory = currentPipelineType || "all"`, line 86).
That tab renders "No agents found" immediately on open, with no interaction needed, and stays
empty even with the maximally generic search term `agent`. Every other category tab (PPT,
Prototype, App Builder, MuleSoft to Spring Boot, .NET to Azure, Custom, All) renders a populated
list.

Reproduced 3/3 from a cold start (fresh `/dashboard` -> `/create/user-stories` navigation each
cycle, not a soft re-click): cycle 1, cycle 2, and cycle 3 all showed the same empty state on
first dialog open. No timing, entry-path, or session-age variation was needed — this is
deterministic, not flaky.

## Root cause

`AgentLibrary.filteredAgents` (AgentLibrary.tsx:104-117) filters `ALL_AGENTS` by
`matchesCategory` (agent's `pipeline_type` includes `activeCategory`) AND `notAlreadyAdded`
(`!existingAgentIds.includes(agent.id)`, unless it is the reusable custom-agent template).

Queried the live catalog via `GET /api/agents/library` (94 total agents): exactly 6 are tagged
`user_stories` — `domain-analyst`, `epic-architect`, `story-estimator`, `nfr-specialist`,
`backlog-reviewer`, `backlog-compiler`. The default `/create/user-stories` launch workflow ships
with 7 steps (the panel reads "Advanced 7 agents") that already include all 6 of these catalog
agents as pre-seeded steps, plus one non-catalog/custom step (observed node: "Delivery
Compilation Agent"). Because every `user_stories`-tagged catalog agent is already an
`existingAgentIds` member of the default workflow, `notAlreadyAdded` excludes all 6, leaving
`filteredAgents` empty for that category specifically — by construction, not by a missing tag or
a failed fetch. The search box narrows an already-empty set, so a broad search term cannot
surface anything either; this rules out a filter-string bug, matching the register's own
observation.

This is functionally correct (you cannot re-add an agent already on the canvas) but is a real UX
defect: the dialog **defaults to** the one category tab that is guaranteed to be empty for this
pipeline's own default workflow, with no messaging distinguishing "this category has zero
catalog entries" from "everything in this category is already on your canvas."

## Blast radius (analyzer pass, 2026-08-29)

Re-confirmed the root cause by reading `AgentLibrary.tsx` directly: the default-category line
(`:86`, `useState(currentPipelineType || "all")`), the filter (`:104-117`, correctly using the
`agentMatchesPipelineType` helper per ADR-0023 — not a bare `===`), and the empty-state message
(`:229-232`, `"No agents found"`, unconditional on `filteredAgents.length === 0`).

- **`AgentLibrary` render call sites** (`grep -rn "<AgentLibrary\b" frontend/src/ --include="*.tsx"`,
  4 production, none in tests): `frontend/src/app/workflow/page.tsx:67` and
  `frontend/src/components/workflow/WorkflowView.tsx:556` pass NEITHER `currentPipelineType` NOR
  `existingAgentIds` — `activeCategory` defaults to `"all"`, not this bug's trigger; `/workflow`
  is also a standalone top-level route outside `routes.ts`'s catch-all (ADR-0018) with no in-app
  link found, likely unreached regardless. `composer/ComposerPage.tsx:1401` passes
  `currentPipelineType={workflowType}`, but its own mount comment (`:284-288`) states `"custom"`
  is the only `workflowType` this component ever mounts for (`DashboardLayout`'s
  `COMPOSER_ENABLED_TYPES`) — the one category both affected hosts below explicitly start blank,
  so this host is not affected. `AgentsPopup.tsx:2673` (inside `export function AgentsPopup`)
  passes `currentPipelineType={pipelineType}` / `existingAgentIds={collectAgentIds(agents)}`
  straight through from ITS OWN caller — it carries the bug into `AgentLibrary`, but the defect
  is not `AgentsPopup`'s own.
- **`AgentsPopup` render call sites** (`grep -rn "<AgentsPopup\b" frontend/src/ --include="*.tsx"`,
  2 production): both feed `AgentLibrary` the identical structural pattern that produces this
  bug — `IdeaInputPage.tsx:1936` (`/create/<type>`, the reported route; fresh seed
  `LIBRARY_AGENTS.filter(agentMatchesPipelineType(...))` at `:902`, 100% of the static catalog for
  every type except `"custom"`) and `LaunchWizard.tsx:1143` (`/workflows/<id>/run` with no saved
  override; `defaultAgentsFor` at `:147-148` filters the SAME live `useAgentLibrary()` catalog
  `AgentLibrary.tsx`'s own `ALL_AGENTS` reads). Neither host is user_stories-specific — this
  reproduces (INFERRED, not yet independently browser-verified for these routes) on every
  non-custom pipeline type from either host. Filed as [ISS-421](20260829-0020-ISS-421.md).
- **A second, distinct trigger on the same defaulting line**: `IdeaInputPage.tsx`'s "Advanced"
  button (`:1900-1902`) carries no guard against the `"migration"` meta-type (unlike its
  Run/Continue buttons, which do gate on `isMigrationMeta && !migrationChoice`), so opening it
  before a migration sub-pipeline is chosen passes `currentPipelineType="migration"` — a value
  absent from both the catalog's real `pipeline_type`s and `AgentLibrary`'s own `CATEGORIES`
  list, so no sidebar tab highlights at all (worse than this card's case, where the User Stories
  tab correctly highlights, just empty). Filed as [ISS-420](20260829-0021-ISS-420.md).

Both siblings confirm the fix belongs where this card already located it: inside
`AgentLibrary.tsx`'s own default-category-selection / empty-state logic, not in any of its 4
hosts.

## Expected vs Actual

- **Expected:** The "Add agent" library's category tab matching the current pipeline (User
  Stories) should either list any addable (not-yet-added) User-Stories-tagged agents, or — when
  every catalog agent in that category is already present on the canvas — say so explicitly
  ("All User Stories agents are already on your canvas") rather than the generic empty-catalog
  message "No agents found", which reads as if the category has no agents at all.
- **Actual:** The tab shows "No agents found" unconditionally on open and on every reselection,
  with or without a search term, because all 6 `user_stories`-tagged catalog agents are
  pre-seeded into the default workflow's existing steps.

## Reproduction (cycle 1 of 3, representative)

2. Navigate `/dashboard` -> `/create/user-stories` (cold load each cycle).

5. Accessibility-tree snapshot (not screenshot alone) confirms `paragraph: "No agents found"`
   present immediately under the default-active tab, each cycle.
