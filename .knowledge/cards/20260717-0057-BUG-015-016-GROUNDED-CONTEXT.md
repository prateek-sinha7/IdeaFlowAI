# BUG-015 + BUG-016 — grounded fix spec (SSE reconnect bugs exposed by the parser fix)

> Two fixes: BUG-015 = **frontend** (completed run reconnect-loop), BUG-016 = **backend** (review-gate approve wrongly closes the live stream). Root causes runtime-proven by deep-investigation agents + orchestrator curl/source spot-checks. Executable spec for a `gsd-quick --validate`. **The backend change (BUG-016) requires a backend restart to take effect** (user accepted; it fails in-flight parked runs).

## BUG-015 (FRONTEND) — a completed, still-viewed run reconnects forever
**Cause (verified):** when a launched run goes terminal it stays the FE's focused/attached run; the backend closes a terminal run's stream after replay (`stream_attached{live:false}` then close — curl-verified, no `event: done`); `useRunStream` reconnects on ANY close with no terminal check → re-replay ~13,928 events + close → loop → the phase-driven "Reconnecting…" banner flaps.

**Fix (frontend only):**
1. **PRIMARY — `frontend/src/hooks/useRunStream.ts`: don't reconnect after a non-live stream closes.** Track the last `stream_attached` liveness per connection: in `dispatchBlock` (~`:255-268`) where `stream_attached` is handled, record `sawNonLiveAttachRef.current = (data.live !== true)` (a `useRef`, initialized false, **reset to false at the top of each `connect()`** so a genuine live-stream drop still reconnects). In the response-ended/close branch (`:370-372`), change `if (!stoppedRef.current && !controller.signal.aborted)` to ALSO require `&& !sawNonLiveAttachRef.current`; when that ref is true, do NOT `scheduleReconnect()` — instead settle to a quiescent phase (`setPhase("disconnected")` or a new terminal phase; do NOT set an error banner). This is localized to the hook and covers every path that attaches a terminal run.
2. **COMPLEMENTARY — release the focus on completion so the dead stream unmounts.** Add `detachRun(runId: string)` to `frontend/src/providers/RunConnectionProvider.tsx` (mirror `attachRun` :331-338): `if (focusedRunIdRef.current === runId) { focusedRunIdRef.current = null; recomputeLiveRunIds(); }`; expose it on the context value (`:381-382`) + the context type + the default stub (`:114`). Then in `frontend/src/app/dashboard/page.tsx` `pipeline_complete` handler (`:537-554`, where `completingRunId` + the `isForeignCompletion`/`trackedRunIdRef` check already exist) call `runConnection.detachRun(completingRunId)` for the tracked (non-foreign) completing run. This unmounts the completed run's `RunStreamConnection` (no reconnect, no ~14k re-replay). It does NOT remove the rendered preview/content (that's already in state).

**Do NOT** change the backend for BUG-015 (closing a finished stream is correct).

## BUG-016 (BACKEND) — approving a review gate wrongly closes the live stream
**Cause (verified):** the live-drain loop treats `review_gate_approved` as a stream terminal. `backend/app/api/run_stream.py:198` `if event.get("type") in _GATE_RESOLUTION_TYPES: return`, and `_GATE_RESOLUTION_TYPES` (`:68-77`) lists `review_gate_approved` (`:70`) with the true terminals. But approve RESUMES the run (engine keeps building on the same queue → `generating`). So the stream closes on approve → the FE reconnects. (Clarify does NOT do this — confirmed live; clarify resumes to `pipeline_start`, not in the set.)

**Fix (backend, ~2 lines) — `backend/app/api/run_stream.py`:**
- Define `_STREAM_TERMINAL_TYPES = _GATE_RESOLUTION_TYPES - frozenset({"review_gate_approved"})` (= `pipeline_complete`, `pipeline_cancelled`, `pipeline_failed`, `budget_aborted`, `error`) near `:68-77`.
- Change the drain-loop check at `:198` from `_GATE_RESOLUTION_TYPES` to `_STREAM_TERMINAL_TYPES`.
- **Leave `_GATE_RESOLUTION_TYPES` unchanged** at `:121` (`_dangling_review_gate` correctly treats approve as gate-resolved). Effect: after approve the open stream keeps delivering the post-approve `generating` frames — no close, no reconnect. Genuine terminals still close.
