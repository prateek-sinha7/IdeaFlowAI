# ISS-879

## Description

Sibling of [ISS-160](20260813-1300-ISS-160.md) (QA-KB-009), found while tracing its blast radius. ISS-160's root cause is that the revision target for a chat-turn revision is derived from the parent run's type by hand at each entry point, and only one entry point maps the parent type to its base. That derivation has a second gap, for a parent type that is NOT a `*_revision` type: `ppt_v2`.

A `ppt_v2` deck run has no revision pipeline of its own. `backend/agents/workflows/` holds `ppt`, `ppt_revision` and `ppt_v2` but no `ppt_v2_revision`, and `TIER_PIPELINES` (`backend/app/core/entitlements.py:15`, `:38`, `:56`) lists `ppt_v2` but no `ppt_v2_revision`. The product revises a `ppt_v2` deck through the `ppt` revision pipeline: `DashboardLayout.tsx:2415` routes `effectiveReviseType === "ppt_v2"` to `handleRevisePpt`, which posts `target_artifact_type: "ppt_output"` (`DashboardLayout.tsx:1192`), and [FIX-480](20260902-1530-FIX-480.md) records the intent: "`ppt_v2` runs are revised the same way as `ppt`".

Both server-side fallbacks take the run type verbatim instead:

- Chat-turn revision (`CHANNEL_REVISION` in `post_message`): `run_commands.py:2018`, `dispatch.target_artifact_type or f"{wr_type}_output"` gives `ppt_v2_output`.
- Concierge disposal when the model supplies no `target`: `run_commands.py:1640-1658`. `ppt_v2` does not end in `_revision`, so `base_type = wr_type`, and `target = f"{base_type}_output"` is `ppt_v2_output`.

`_mint_revision_row` (`run_commands.py:4608`) then derives `ppt_v2_revision`, which fails the existence gate (`run_commands.py:4660-4666`) with HTTP 400 `revision_unsupported`: "Revisions aren't available for this workflow yet - 'ppt_v2_revision' has no pipeline behind it."

## Why the root cause implies it

Same function, same flaw, different input. The fallback assumes the revision pipeline is named after the parent's type (or after its base once `_revision` is stripped). That holds for the 7 base types and, once ISS-160 is fixed, for all 10 revision types. It does not hold for `ppt_v2`, whose revision pipeline is `ppt_revision`. Fixing only the `*_revision` parents (the agreed minimal fix for ISS-160) leaves this gap open on both entry points.

## Evidence

Reproduced offline, not in a browser.

- CONFIRMED, chat-turn channel through the real endpoint. Harness: the `env` fixture of `backend/tests/integration/api/test_chat_messages_endpoint_api.py` (TestClient, in-memory SQLite, `_drive_revision_to_queue` stubbed so no model call happens). A `completed` run of type `ppt_v2`, then `POST /api/runs/{id}/messages` with `{"text": ..., "message_id": ...}` and no `concierge` / `target_artifact_type`: `http=400 code=revision_unsupported`, message names `'ppt_v2_revision'` (enterprise tier). The same probe on a `ppt` parent minted a `ppt_revision` child.
- CONFIRMED, Concierge disposal. `_dispose_concierge_proposal` driven with the `wired` stubs of `backend/tests/unit/test_v2_revision_routing.py` and `params` without `target`: `wr_type=ppt_v2` gives `target_artifact_type=ppt_v2_output`, derived pipeline `ppt_v2_revision`, which has neither agents nor a manifest. Every other base parent (`user_stories`, `prototype`, `prototype_v2`, `backlog`, `ppt`, `app_builder`, `custom`) derived an existing pipeline.
- INFERRED, the user-facing expectation. That a chat turn on a completed `ppt_v2` deck should revise it rests on FIX-480 and the UI routing above, not on a live run. A Concierge revision proposal that carries `target: "ppt_output"` (the tool docstring's own example, `backend/app/agents/chat/concierge.py:416`) is unaffected; the failure needs the model to omit `target`.

## Expected vs actual

- Expected: a plain chat turn (or a Concierge revision with no `target`) on a completed `ppt_v2` run mints a `ppt_revision` child, as the UI's own revise path does.
- Actual: HTTP 400 `revision_unsupported` naming `ppt_v2_revision`.

## Fix direction

Map `ppt_v2` to `ppt` in the same helper ISS-160 introduces, so both fallbacks agree with the UI by construction. Do not add a `ppt_v2_revision` manifest or a `TIER_PIPELINES` row: the UI already reuses `ppt_revision`, and a new manifest would be a second revision pipeline for the same deliverable.

## TEST COVERAGE - ISS-879

Not fixed, no test added. The probe results above came from scratch scripts that are not committed. A regression test belongs next to the ISS-160 test in `backend/tests/integration/api/test_chat_messages_endpoint_api.py` (`TestRouting`): parent type `ppt_v2` -> child type `ppt_revision`.

## Resolution (QA-KB-009 fixer, 2026-10-01)

Resolved by [FIX-684](20261001-2129-FIX-684.md): `_revision_base_type` maps `ppt_v2` to `ppt` (`backend/app/api/run_commands.py:1494-1497`), and both fallbacks call it (Concierge disposal `:1658`, `CHANNEL_REVISION` `:2028-2030`). No `ppt_v2_revision` manifest or `TIER_PIPELINES` row was added. Regression test added by the fixer, as this card's TEST COVERAGE asked: `backend/tests/integration/api/test_chat_messages_endpoint_api.py::TestRouting::test_ppt_v2_parent_revises_through_ppt_revision` (strict xfail). Observed red before the source change (400 `revision_unsupported` naming `'ppt_v2_revision'`), XPASS(strict) after it: the child row is `ppt_revision`.
