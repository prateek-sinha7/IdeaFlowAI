# ISS-097

## Title

**Gating a fan-out step's agent parks the run at a review gate NOBODY CAN SEE, DISCOVER OR RESOLVE.** `_should_gate` (`engine.py:4908-4925`, predicate at `:4922-4925`) is a per-INVOCATION predicate on `spec.id`, but `gate_agent_ids` is a per-STEP selection — the UI's own words are "Checked agents pause the pipeline for your review after they finish" (`ReviewGatesSection.tsx:128-129`). Those readings were identical for every workflow that existed when the selector shipped, because every step invoked its agent exactly once. Fan-out (Phase 11) broke that equivalence — `fanout.py:95-96` resolves `agent: self` to `step.agent_id`, so every worker runs the SAME `spec.id` as its parent step and every one independently reaches `_should_gate → True`. **The row as originally filed predicted "N simultaneous review gates, each awaiting a human". That is WRONG, in the direction that matters — it is worse.** Every worker's `review_gate_ready` is consumed and DISCARDED by `fanout.py:414-429`, whose loop body reads only `agent_complete` for token accounting and forwards nothing. So **zero** gate frames reach the SSE stream, **zero** rows reach durable `run_events`, `derive_open_gate` (`gate_pendency.py:68-108`) returns `(None, None)`, and the run stops dead at a HITL pause with `workflow_runs.status` reading `waiting_for_user` indefinitely. All N workers share ONE gate key `f"{run_id}:{agent_id}"` (`engine.py:5705`), so they are N arms of one slot, not N gates. **MEASURED offline at `eb12bc7e`** (`sample_wave`, single-wave plan, 4 workers, `gate_agent_ids=["sample-wave-worker"]`): `_should_gate` True 5/5, `_run_review_gate` entered **4×**, **1** distinct gate key, **0** `review_gate_ready` on the wire, **0** in `run_events`, outcome **HUNG** (20 s timeout). Control with `[]` completes cleanly. The same hang reproduces on the builder-composed fan-out fixture. **The gate is resolvable but undiscoverable** — `store.review_event_pending(gate_key)` returns True and `_gate_is_pending` would accept a resolution, so a user who GUESSES the predictable key can free the run by API. That is an expert escape hatch, not a product behaviour. It does not compound across restarts (`restore_non_terminal_runs` needs `derive_open_gate` to return a gate before re-arming, so the run parks harmlessly) but it leaves a permanently orphaned run row plus every worker's workspace allocated and every `subagent_runs` row `running` forever, because `run_fanout`'s `finally` teardown never runs. **SEVERITY RAISED major → critical**: an invisible, unresolvable hang on a shipped user-facing feature. Reachability is real, not theoretical — the gate picker (`ReviewGatesSection.tsx:131`) lists EVERY pipeline agent with no filter, the composer's fan-out toggle (`CanvasConfigRail.tsx:284-295`) is one click away in the SAME launch UI, and a saved workflow replays `gateAgentIds` on every subsequent launch (`DashboardLayout.tsx:1227-1228`), so it is sticky rather than one-off. **FIXED by FIX-242** with one keyword-only invocation-scope flag `invocation_gated`, threaded from the two kernel sites that create non-step invocations (`run_worker`, `run_merge_agent`) through `run_agent` into `_run_agent`, folded into the EXISTING predicate in place (INV-12). Default `True` ⇒ every step-shaped invocation byte-unchanged. **Three designs were evaluated and REJECTED** — do not retry them: (a) making `_should_gate` read `step.gates` CANNOT work, because `kernel_services.py:992-993` reuses the PARENT step object, gates included, whenever the worker is `agent: self` with no isolated workspace; (b) parking the flag on `ExecutionContext` races, because N workers share ONE `ectx` under `asyncio.gather`; (c) renaming worker agent ids breaks `_spec_for`, `allowed_workers`, fragment provenance and the wave resume cursor. **Residual, deliberately NOT folded:** `engine.py:2470` still passes `inline_gated=self._should_gate(spec, ectx)` at the step boundary, so a fan-out step that BOTH declares `gates:[human]` AND has its agent ticked now dedupes its declared gate against an inline gate that no longer fires — filed as **ISS-131**. Pre-fix that same combination hung; post-fix it silently has no gate. No manifest declares gates on a fan-out step today (verified across `agents/workflows/`); it is reachable only through composed selections.

## Source / Evidence

Found 2026-08-12 during quick-260812-g1c while enumerating the ISS-091 blast radius; nominated "Q2" by the ISS-091 investigation and deliberately filed rather than folded. **All four file:line citations in the original row had DRIFTED and are corrected above** (worker step view `kernel_services.py:971-984`→`:995-1008` with `gates=[]` at `:1001`; `_should_gate` `engine.py:4861-4864`→`:4908-4925`). The original row's suggested first step — "count `review_gate_ready` events; 1 is correct, N is the bug" — would have MEASURED ZERO and read as a pass, because the events never reach the stream; the working assertion counts `_run_review_gate` ENTRIES and asserts the run terminates. **Method trap that nearly buried this twice:** `tests/agents/test_restart_resume.py:365` (`make_engine`) assigns an empty async generator to `engine._run_review_gate` as an INSTANCE attribute, silently shadowing the real bound method; the first investigation run showed zero gates and nearly filed "not reachable". `del engine._run_review_gate` is what makes the defect visible — measured: without the `del` the very same test passes GREEN in 1.07 s against a live 4-arm hang. Any future gate assertion on that harness must un-shadow first.
