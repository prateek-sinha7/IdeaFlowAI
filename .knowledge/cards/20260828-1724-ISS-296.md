## Relationship to the root bug

Sibling of [ISS-230](20260828-1805-ISS-230.md), derived from its root cause — the INVERSE
case. ISS-230 shows that switching tabs while the URL already carries `/versions/<v>` drops
that segment. This card shows the segment is essentially never WRITTEN by the primary user
action in the first place: clicking a version in RunHeader's "Version ▾" menu.

## Root cause (INFERRED from static reading — not yet re-driven through the browser this pass)

- `VersionMenu.select` (`frontend/src/components/preview/RunHeader.tsx:72-76`) calls only
  `onSelectVersion(memberId)`, then closes the menu:
  ```ts
  const select = (memberId: string) => {
    onSelectVersion(memberId);
    setOpen(false);
    buttonRef.current?.focus();
  };
  ```
- That prop is `PreviewPanel`'s `handleSelectVersion` (`frontend/src/components/preview/PreviewPanel.tsx:549-564`),
  which calls only `setViewingVersion({...})` / `setViewingVersion(null)` — pure local React
  state. Neither this function nor its caller ever calls `router.push`, `router.replace`, or
  `window.history.pushState`.
- `routes.runVersion(id, v)` (`frontend/src/lib/routes.ts:80`) is the only builder that can
  produce a `/runs/{id}/versions/{v}` URL. A repo-wide search
  (`grep -rn "routes\.runVersion\|runVersion(" frontend/src`) finds exactly one match outside
  its own definition: `frontend/src/lib/routes.test.ts:127`, a unit round-trip test. No
  application code calls it.
- Net effect: picking an older version through the UI changes what the Preview tab renders,
  but the address bar, browser history, and any copied/shared link stay on whatever route was
  already showing — the pin lives only in one component's in-memory state, invisible to a
  reload, a shared link, or back/forward.

## Expected vs actual

- **Expected:** selecting a version in the Version menu updates the URL to reflect the pin
  (a `routes.runVersion`-shaped route or equivalent), so refresh/share/back-forward preserve
  it.
- **Actual:** the URL never changes when a version is picked through the UI; `routes.runVersion`
  is dead code reachable only by hand-typing the URL.

## Why this matters together with ISS-230 / ISS-294

A fix to `handlePreviewPanelTabSelect`'s routeMap (ISS-230) only preserves a `/versions/<v>`
segment that is ALREADY in the URL. Because nothing writes that segment from the real user
interaction, ISS-230's fix alone does not make the primary "pin a version via the menu, then
browse other tabs" journey work end to end — the write side needs wiring too, most naturally
in the same place `routes.ts` / `handleSelectVersion` already exist, so tab-router
(`DashboardLayout.tsx`), cold-mount fetch (`page.tsx`, see [ISS-294](20260828-1725-ISS-294.md)),
and the Version-menu write path all resolve `(rootId, version)` through one shared place.

## Fix direction (not applied — analysis/fix only)

`handleSelectVersion` should push the pinned version into the URL (via `routes.runVersion` or
an extended builder that also carries the active tab), rather than only setting local state —
matching ADR-0018's invariant that every navigation goes through a `routes.*` builder.

## Evidence

Derived from code reading only; no independent browser reproduction performed by this pass.
To confirm: pin an older version via the Version ▾ menu on a 2+-member run and check
`location.pathname` / `window.history` stay unchanged.
