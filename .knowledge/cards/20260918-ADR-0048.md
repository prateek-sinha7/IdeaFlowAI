## Decision

`extract_text` materialises a document into `.extract/{format}/{slug}/pages/NN/`,
one directory per page holding `text.md` plus `image-N.png` crops in reading
order. Four choices inside that shape look like obvious simplifications waiting
to happen, and each one is load-bearing.

## The image is a crop of the render, never the embedded image

`_crop_box_for_image` takes a `pdfplumber` image bbox in PDF points and scales it
into pixel coordinates of the `pypdfium2` render (`_RENDER_SCALE = 2.0`), and the
crop is taken from the render.

Extracting the embedded image object directly would be less code and lose the
feature. A documentation screenshot carrying callout arrows, rings and
highlighting is **the picture PLUS separate vector overlays drawn on top of it**.
Embedded-image extraction returns the picture alone — the annotation, which is
the part a reader actually needs, is dropped. Only a render has both.

The same finding drives ADR-0049's rejection of native Office extractors: there
the overlay is DrawingML instead of PDF vector, and the loss is identical.

Fragments are merged first (`_merge_image_fragments`, `_FRAGMENT_MERGE_GAP = 2.0`
points), so one visually contiguous picture split across several PDF image
objects becomes one crop. The placeholder records the audit trail inline:
`@[[image-1.png]]  <!-- 1240x780, 3 source objects -->`.

## The page directory is the state

A page is built into `pages/.tmp-NN-<uuid>/` and moved into place with a single
`os.rename`. The rename is atomic, so `pages/NN/` exists **if and only if** that
page is complete.

That single fact removes an entire class of machinery. There is no cache file, no
progress record, no partial-state marker and nothing to keep in sync with the
disk. Resume is:

```
set(range(1, page_count + 1)) − {existing page directories}
```

Stray `.tmp-` directories from a crashed prior run are swept on open — they were
never renamed, so they hold no completed page and are safe to discard.

Staleness is handled the same blunt way. `source_sha256` hashes the **uploaded**
bytes (the `.docx`, never the PDF derived from it), and a mismatch under the same
filename `rmtree`s the whole folder rather than trying to reconcile it. Uploads
dedupe by filename, so the same name really can carry different content. This
check must run **before** the conversion cache is consulted, or a stale
`source.pdf` is reused for the new document.

## Parallelism is processes or nothing

Above `_PARALLEL_PAGE_THRESHOLD = 30` pages, work fans out across
`_PARALLEL_WORKER_COUNT = 4` `ProcessPoolExecutor` workers, each taking one
contiguous page range and opening both documents once for the whole range.

**Threads were tried and are fatal.** Two measurements:

- `pdfplumber` on four threads: **0.99x** — pure Python, GIL-bound, no gain.
- `pypdfium2` rendering across threads: **crashes the process**, exit 133,
  SIGTRAP, no traceback. PDFium is not thread-safe. In the backend that kills the
  worker and every concurrent run on it.

FIX-561 states that the large-document branch uses processes; it does not say
threads were tried and are lethal. Without this card, "simplify this to a
ThreadPoolExecutor, it is the same thing and cheaper to spawn" survives a reading
of every card in the store. It does not survive a run.

The same non-thread-safety is why the sequential path holds `_PDFIUM_LOCK` around
its in-process rendering: five parallel tool callers rendering at once crashed
the same way.

`_materialize_parallel_sync` blocks on `future.result()` on purpose. The runtime
already runs these sync tools in a worker thread, so blocking here never touches
the run's event loop. Wrapping it in `asyncio.run()` would not add that
guarantee — it would remove it, because `asyncio.run` raises inside a thread that
already owns a loop, and the parallel branch would return an error having
materialised nothing.

## Image dedupe was priced and rejected

Not deferred — rejected (`research.md` R-01, which also deleted FR-005b and
RISK-02 from the spec).

The measurement: 50 crops, 18,569 image tokens on disk; perfect dedupe of every
repeat would save **541 tokens — about 2% of image tokens, 2.4% of the document's
total**. Against that, every exact-match method collapses the same base
screenshot bearing *different* annotations into one copy, which deletes exactly
the signal the render-crop decision above exists to keep.

The consequence is visible in the manifest: `totals.unique` equals
`totals.after_merge` by construction, because every merged picture is unique by
definition when nothing is deduped. A future reader should not take that field as
evidence dedupe ran.

## What a future author must do

Do not switch the process pool to threads. Do not add a resume/progress file
beside the page directories. Do not swap the render crop for embedded-image
extraction "to save a render". Do not add dedupe without re-running R-01's
pricing against a document whose repeats carry different annotations.
