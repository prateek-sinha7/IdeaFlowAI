## What happened

Deferred finding from [FIX-395](20260829-0338-FIX-395.md). Three of that fix's nine
`it.fails` guards stay red-as-expected after a correct fix, because of defects in the test
harness itself, not in the application. No test file was edited — this card records what each
one needs.

## 1. `LibraryPage.copyFeedback.test.tsx` — both tests (ISS-331, ISS-555)

The file mocks `next/navigation` with `useParams: () => ({})` and a no-op `router.push`.
`LibraryPage` reads its detail-modal selection from the URL
(`frontend/src/components/library/LibraryPage.tsx:488-494`: `useParams<{view?: string[]}>()`
-> `parseViewPath` -> `librarySlug`), and the T16 effect at `LibraryPage.tsx:643-665` opens
with:

```
if (!librarySlug) {
  setSelectedAgent(null); setSelectedSkill(null); setSelectedHook(null);
}
```

Clicking a card calls `setSelectedHook(hook)` AND `router.push(...)`; with `push` mocked the
URL never changes, `librarySlug` stays `null`, and the very next run of that effect closes the
modal it just opened. Measured directly (throwaway copy of the test, since deleted):

```
before=false after=false calls=0   # copy button detached, writeText never called
```

`findByRole` resolves against the transiently-mounted modal, but by the time the click is
dispatched the node is detached from React's tree, so the handler never runs. The assertion
then fails for a reason that has nothing to do with the button's behaviour, and no application
change can turn it green.

**Fix:** mock the URL the way the live repro actually entered the page — a deep link:

```ts
useParams: () => ({ view: ["library", "hooks", MOCK_HOOK.id] }),
```

(`["library", "skills", MOCK_SKILL.id]` for the skill test), and drop the tab/card clicks.
Verified: with that one change and FIX-395 applied, the same two assertions report
`Tests 2 passed (2)`.

## 2. `IntegrationsCard.copyFeedback.test.tsx` — the API-key "copy now" test (ISS-561)

```ts
const copyButtons = screen.getAllByRole("button").filter((b) => !b.textContent?.trim());
fireEvent.click(copyButtons[0]);
```

The GitHub PAT card renders before the API keys card, and its show/hide password toggle
(`IntegrationsCard.tsx:266-273`, an icon-only `<button type="button">`) is therefore the FIRST
text-free button in the DOM. Probed, both text-free buttons dumped:

```
COUNT=2
[0] <button type="button" class="absolute right-2 top-1/2 -translate-y-1/2 …>   # PAT eye toggle
[1] <button class="flex items-center gap-1 rounded-md px-2 py-1 text-blue-700 …> # key copy
```

So the test toggles password visibility and never touches the clipboard.

**Fix:** select the copy button by its position in the minted-key row rather than by index
over the whole page — e.g. `within(screen.getByText("New key — copy now").closest("div")!)`,
or give the button an `aria-label`.

The application side of that call site IS fixed and was verified by probe against
`copyButtons[1]`: rejecting clipboard -> button text `"Copy failed"`, resolving clipboard ->
`"Copied"` (it had no feedback at all before FIX-395).
