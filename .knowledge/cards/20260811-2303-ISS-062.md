# ISS-062

## Title

A/B measured across two live Bedrock runs: PRE-si4 run `5ecb990f` reported `eligible=True` at every analyze gate including both re-opens (seq 9572/24652/24655); POST-si4 run `d5dbc9f2` reports `True` at the original gate (seq 9283) but **False** at the re-opened one (seq 20360). So FIX-218 traded one broken behaviour for another: before, the button was VISIBLE and did nothing (ISS-064); now the action WORKS but the button is HIDDEN, so a user still cannot run a second cycle from the UI. The `update_specs_eligible` fence added by FIX-218 OVER-FIRES at the re-opened analyze gate. Measured live on run `d5dbc9f2` (2026-08-11): original analyze gate seq 9283 `eligible=True`, RE-OPENED analyze gate seq 20360 `eligible=False` — the plan's design intent was True/False/True across outer / in-pass / re-opened, so `ectx.revision_attempt` is still truthy when the re-opened gate is armed. Consequence: `InlineGateActions.tsx:130` computes `canUpdateSpecs = !!onUpdateSpecs && !!updateSpecsEligible` and `:258` renders the button only when true, so the user CANNOT see "Update the Specs" at the one gate where a second cycle is offered. ISS-064's engine half works (a POST does run a real cycle — spec v3, 40,052 chars) but is unreachable from the UI.

Run `d5dbc9f2` has only TWO analyze gates and **never reached a re-opened one** — the gate was consumed by a second `update_specs` POST 6s later (the ISS-053 path, since the button was hidden). A HEAD probe returns `eligible=True` at the genuine re-opened gate. **Do NOT relax `_update_specs_eligible` to "fix" this** — that re-opens the nesting recursion ISS-051 closed (measured +3 stack frames per level). The real, valid substance of this row — that the in-pass and re-opened analyze gates are byte-identical to the user yet carry opposite affordances, which is what made the tester misread the run — is transferred to **ISS-052**.
