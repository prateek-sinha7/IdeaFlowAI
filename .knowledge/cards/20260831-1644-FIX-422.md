# FIX-422

## What was wrong

`review_gate_ready` carries two generic affordance flags. One of them was a rule and the
other was a decoration. `update_specs_eligible` is computed by the structural predicate
`_update_specs_eligible(artifact_kind, ectx)`, published, and then ENFORCED — the gate
refuses an `update_specs` action the firing never advertised (ISS-053). `redoable` was the
literal `True`, typed out three times, at the three inline gate call sites.

Two consequences, both of them the same missing fence seen from opposite ends:

1. **No rule on the way out.** Any agent a user ticks into a per-run `gate_agent_ids` got
   a "Request changes" button, including the per-task dispatches of a `task_loop` step
   (one gate per task — [ISS-132](20260812-2116-ISS-132.md)). That dispatch already carries
   a COMPACTED view of the deliverable, which is exactly why
   [FIX-228](20260812-0617-FIX-228.md) had to withhold the injected subject inside
   `_consume_redo` when `build_task_number` is set. The engine was being careful about a
   promise the button should not have made.
2. **No rule on the way in.** `_run_review_gate` acted on `action == "redo"` unconditionally,
   never reading the `redoable` it had just published. A declared/user `gate:human` step
   publishes `redoable=False` and the FE renders no Redo control there, yet a replayed or
   scripted response still re-ran an agent. `HumanGate` caught it one layer up (REDO-GATE
   F1a maps a stray `_gate_redo` to `GATE_WAIT_HUMAN`), so the shared primitive — the layer
   ISS-053's comment in `agents/capabilities/gates/human.py:47` already says is the one that
   must never abstain — was the fail-open half.

## Root cause

`backend/agents/execution_engine/engine.py:4520`, `:4642`, `:5783` — the RESUME-17 restart
re-entry gate, the gate re-opened after a revision pass, and the live post-stream gate —
each passed `redoable=True` verbatim. There was no predicate to call: the symmetric
`_redoable` never existed, so there was no single place a rule could be stated and no value
for `_run_review_gate:7159` to enforce against.

## What changed and why there

**`engine.py:8340`** — `_redoable(self, ectx) -> bool`, placed directly beside its mirror
`_update_specs_eligible` (`:8301`):

```python
return not (getattr(ectx, "build_task_number", "") or "")
```

`build_task_number` is generic scratch that `KernelServices.run_agent`
(`kernel_services.py:1694-1720`) binds around exactly one per-task `_run_agent` invocation
and restores in a `finally`, so it is non-empty for precisely that dispatch's duration.
That is the same idiom condition 2 of `_update_specs_eligible` uses on `revision_attempt`
("an already-published field doubles as the in-flight signal"), so this invents no parallel
state (INV-12) and names no workflow and no agent id (INV-1 / SC-001).

**`engine.py:4520`, `:4642`, `:5783`** — the three call sites now pass
`redoable=self._redoable(ectx)`. Stated once, consumed three times; a future condition is a
one-line edit rather than three.

**`engine.py:7171`** — the enforcement half, inside the existing `if action == "redo":`
branch and modelled line-for-line on the `update_specs` refusal 30 lines below it:

```python
if not redoable:
    logger.warning(... "gate stays open (ISS-090)" ...)
    event.clear()
    continue
```

The degrade is KEEP WAITING for the reason ISS-053 records: approving would be fail-open on
a HITL gate, rejecting would cancel the user's run, and re-arming leaves every legitimate
action available. `gate_key` names a gate SLOT and not a firing, so a replayed earlier click
lands on whichever firing is armed now — no crafting required.

Four comments and one docstring paragraph that asserted "redoable is an inline True" were
corrected in the same pass (`:4627`, `:5761`, `:5767`, `:7030`, `:7093`); they became false
the moment the literal went away.

## What was deliberately NOT changed

[ISS-090](20260812-0632-ISS-090.md) sketched the signature as
`_redoable(artifact_kind, spec, ectx)`. It takes `ectx` alone: the rule reads one field and
there is no second condition for `artifact_kind` or `spec` to serve. **Flagged deviation** —
adding parameters no branch consumes would make the predicate look like it fences more than
it does.

The card also names **tool-bearing** agents beside task-loop ones. Not fenced. The only
structural spelling of "tool-bearing" available here is
`set(spec.tools) & {"prototype_emit_only", "prototype"}` (`engine.py:10822`), and the
builder gate is precisely where "request changes to my prototype" is the point of the
button. Withdrawing it there is a product decision, not a defect fix. The task-loop case is
the one the card substantiates (with FIX-228 as evidence) and the one that got fenced.

**No frontend change.** `frontend/src/types/index.ts:137-150` already documents `redoable`
as an optional server-set discriminator that the FE renders the Redo control IFF — the
flag's meaning is untouched, only its value on one dispatch shape.

**No new eligible-kinds set.** `_UPDATE_SPECS_ELIGIBLE_KINDS` has a mirror-shaped hole next
to it; nothing in the card asks for one and inventing an artifact-kind whitelist for redo
would withdraw the button from every gate this fix leaves alone.

## Blast radius

Behaviour changes on exactly one path: a `task_loop` step whose agent a user ticked into
`gate_agent_ids` (the static default set is `clarify-agent` alone — the only AGENT.md in
the tree declaring `gate: Human_Gate` — and it runs no task loop). Those per-task gates lose
the Redo button and, if a response arrives with `action: "redo"` anyway, stay open instead
of re-running the task. Every other firing is byte-identical (INV-3); `redoable` is in
`_VOLATILE_STRIP_KEYS`, so the goldens never saw it either way.
