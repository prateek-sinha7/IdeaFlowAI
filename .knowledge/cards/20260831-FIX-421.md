## ISS-581 — ConstitutionSection mount-GET overwrites in-flight draft

### What was wrong

`ConstitutionSection`'s mount `useEffect` called `setContent(loaded)` unconditionally when
the GET `/api/settings/constitution` response arrived. React StrictMode double-invokes the
effect, so two requests fire. If the second response landed after the user had started typing,
`setContent` silently replaced the draft with the backend's stored value, discarding the
edit with no warning. The same narrow window exists in production (single invocation) if the
user types before the first response lands.

### What changed

**`frontend/src/components/settings/AccountSettings.tsx`** — `ConstitutionSection`:

1. Added `useRef` to the React import at the top of the file.
2. Inside `ConstitutionSection`, added `const userHasEdited = useRef(false)` before the
   mount `useEffect`.
3. In the `useEffect`'s `.then` callback, wrapped the `setContent(loaded)` call:
   ```tsx
   if (!userHasEdited.current) {
     setContent(loaded);
   }
   setLoadedValue(loaded);   // always update the baseline for dirty-check
   ```
   `setLoadedValue` is NOT gated — the dirty-check (`constitutionContent !== constitutionLoadedValue`)
   always needs the real backend value to be accurate, regardless of whether the editor was
   touched.
4. In the textarea's `onChange` handler, added `userHasEdited.current = true` before
   `setContent(e.target.value)`.

### Why here, not elsewhere

The race is specific to `ConstitutionSection`'s local `userHasEdited` lifecycle — no other
settings section has a mount GET that writes directly into an editor the user may be typing in
simultaneously.

## ISS-581 (test half) — duplicate dialog handlers causing "already handled" errors

### What was wrong

Two places in `tests/integration/e2e/suites/09_settings/test_settings.py` registered a second
dialog handler alongside the autouse `dismiss_native_dialogs` fixture in `conftest.py`. Playwright
invokes ALL registered handlers; the second one raised
`Error: Dialog.dismiss: Cannot dismiss dialog which is already handled!`, failing the test
outright on some runs.

### What changed

**`tests/integration/e2e/suites/09_settings/test_settings.py`**:

1. `test_clear_constitution_requires_confirmation_before_deleting` — removed the redundant
   `page.on("dialog", lambda dialog: dialog.dismiss())` line. The autouse fixture already
   dismisses every dialog and the test verifies via a backend `GET` that nothing was deleted.

2. `test_switching_tabs_away_from_constitution_requires_confirmation_for_unsaved_draft` —
   removed the `page.once("dialog", _capture_and_dismiss)` handler and its helper closure.
   The test now slices `page.native_dialogs` (the autouse fixture's seen-list, set on the page
   object by conftest) before and after the click to capture the messages:
   ```python
   dialogs_before = len(page.native_dialogs)
   page.click(L.tab("tab-profile"))
   page.wait_for_timeout(settings.SETTLE_MS)
   dialogs_captured = page.native_dialogs[dialogs_before:]
   ```
   The assertions on `dialogs_captured` are otherwise unchanged.

## ISS-430 — AI Model selector offers non-entitled models with no lock

### What was wrong

`GET /api/settings/preferences` returned the full `AVAILABLE_MODELS` catalog to every tier
with no per-model entitlement flag. The frontend rendered every option unconditionally. A
basic-tier user's first signal that they could not use Opus was a 403 banner after clicking
Save — not a disabled option before it.

### What changed

**`backend/app/api/settings.py`** — both `get_preferences` and `update_preferences`:

```python
models = [
    {**m, "allowed": can_use_model(user.tier, m["id"])[0]}
    for m in AVAILABLE_MODELS
]
```

`AVAILABLE_MODELS` (the module-level constant) is unchanged — `test_available_models_is_projection`
asserts its key set stays `{id, name, description, tier}` and continues to pass.

**`frontend/src/lib/api.ts`** — added `allowed?: boolean` to `ModelOption`:
```typescript
/** ISS-430: true when the current account's tier may select this model. */
allowed?: boolean;
```

**`frontend/src/components/settings/AccountSettings.tsx`** — model `<select>`:
```tsx
<option key={m.id} value={m.id} disabled={m.allowed === false}>
  {m.allowed === false ? "🔒 " : ""}{m.name} · {m.tier}
</option>
```
`m.allowed === false` (strict) leaves options with `allowed: undefined` — i.e. an API
that has not yet been updated — enabled, so the change is safe against a stale backend.

**`tests/integration/e2e/suites/09_settings/test_settings.py`** — `test_basic_tier_cannot_persist_a_powerful_model`:
- Updated `evaluate_all` to also collect `disabled` property.
- Added assertion that the Opus option IS present but IS disabled (the ISS-430 affordance).
- Replaced `page.select_option(opus["value"])` (which now raises `error:optionnotenabled`)
  with a JS force-set + `dispatch_event("change")` to verify the backend 403 also fires.
- Docstring updated to describe the new affordance semantics.
