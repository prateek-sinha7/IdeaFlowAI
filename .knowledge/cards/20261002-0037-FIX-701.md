# FIX-701

## What was wrong

Bug report QA-KB-011. The root cause, blast radius and the agreed fix with its three amendments are the analysis on
[ISS-284](20260828-1906-ISS-284.md); the Continue window is [ISS-920](20261001-2221-ISS-920.md). They are not
re-derived here.

In short: `pipelineAgents` had no readiness state, so "Save workflow", "Save as my version" and the "Advanced"
trigger (whose popup has its own footer Save) were enabled from first paint, before `getWorkflowDetail` had decided
the roster. "Save as my version" sends `overrides_pipeline_type`, and the server UPSERTs on it
(`backend/app/api/user_workflows.py:794-834`), so a click in the library-loaded, detail-pending window wrote the
system roster over the user's real override. Separately, Continue was enabled while a saved workflow's draft
`agentIds` waited for the agent library, so the launch carried `[]` or the plan roster.
[FIX-338](20260828-2221-FIX-338.md) had closed the effect-ordering race only; it added no settled signal.

## What changed, and why there

`frontend/src/components/workflow/LaunchWizard.tsx`, the one component behind every mode and both mounts
(`[...view]/page.tsx` and `app/workflow/create/page.tsx`). Nothing else in the application changed.

1. `:291-298`, two states with `// ISS-284` and `// ISS-920` comments:
   `overrideLoad: "loading" | "ready" | "failed"` (initial `"loading"`) and `agentRestorePending` (initial `false`).
2. `:434`, in the draft-restore effect: `setAgentRestorePending(Boolean(d.agentIds && d.agentIds.length > 0) && libraryAgents.length === 0)`.
   True while a draft with agentIds waits for the library (the draft stays in sessionStorage, `:446`), false on the
   pass that restores it.
3. `:514`, `:521`, `:576`, in the `getWorkflowDetail` effect: reset to `"loading"` with its other state; `"ready"`
   first thing in `.then` after the `cancelled` check (React batches it with the override roster write at `:568`,
   so no render shows `ready` with the pre-override roster); `"failed"` in the `.catch` when not cancelled.
   Amendment 1: settle on success, never in a `.finally`.
4. `:912-914`, `rosterSettling = overrideLoad === "loading" || agentRestorePending`.
5. `:1295-1296`, Advanced: `disabled={rosterSettling}` (amendment 3; the popup's footer Save is a third Save).
6. `:1410-1412`, Save workflow: `disabled={rosterSettling || pipelineAgents.length === 0}` (amendment 2).
7. `:1425-1429`, Save as my version: `disabled={overrideLoad !== "ready" || agentRestorePending || pipelineAgents.length === 0}`,
   and on `"failed"` the `title` reads "Couldn't check for your saved version of this workflow. Reload to try again."
8. `:1437`, Continue: `disabled={!canContinue || locked || agentRestorePending}` (ISS-920's prescribed change,
   the button only).

The three gated buttons gain `disabled:cursor-not-allowed disabled:opacity-30`, the disabled styling
IdeaInputPage's own Save buttons already use, so a disabled button does not look clickable.

Why there: the two save handlers have one entry each (the button, and for Save workflow the NameWorkflowModal it
opens), and nothing re-arms `"loading"` while that modal covers the stepper, so the buttons are the single sink.
The optional early returns inside the handlers were not added for that reason. AgentsPopup was not touched (it is
shared with IdeaInputPage); gating its trigger is the smaller diff, as the analysis said.

### One existing test changed (recorded, not an assertion change)

`LaunchWizard.test.tsx` WR-05 (`:307-327`) rendered with an EMPTY agent library and clicked "Save workflow". Under
amendment 2 an empty roster disables that button, which is the behaviour the card specifies, so WR-05's fixture
now preloads `createTestAgents()` exactly as its neighbour at `:288-290` does, with a one-line `// ISS-284` comment
(`:309`). Its assertions (chrome and save-modal title follow the live mode) are unchanged. Without the fixture it
fails at the save-modal-title lookup (`:323` in the original file, `:326` now: "Unable to find an element by:
[data-testid="save-modal-title"]"), observed. No `waitFor` was needed: 25/27 three runs in a row.
