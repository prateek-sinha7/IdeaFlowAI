## Condition

Sibling of [ISS-340](20260828-1856-ISS-340.md), derived from its root cause rather than
independently reproduced in a browser — **INFERRED**, needs a live repro to confirm.

`ISS-340` covers a BUILT-IN opened via `/workflows/<type>/canvas` (`builtinCanvasType` set). This
card covers the OTHER entry path into the exact same `ComposerPage` component: a user's own
**saved custom workflow**, opened from "My Workflows" (`userWorkflowId` set, `builtinCanvasType`
undefined) — one whose own manifest declares (or was edited on the Canvas tab and saved with) a
deliverable strategy other than the generic `custom`/`streamed_text` default, e.g. `single_file`
or `serialized_sandbox`.

## Why the root cause implies it

`ComposerPage.tsx:478`'s `const deliverableLabel = PIPELINE_LABEL.custom;` is unconditional — it
does not branch on `builtinCanvasType`, `userWorkflowId`, or `runConfig` at all, so nothing in the
broken line distinguishes a built-in canvas from a saved custom workflow. Both entry paths feed
the SAME `runConfig` state through the SAME prop wiring
(`initialRunConfig={savedComposition?.runConfig}` at `DashboardLayout.tsx:3001`;
`ComposerPage.tsx:410`, seeded at `:426-430`), and the SAME `CanvasView.tsx:1574` combobox
correctly reads `runConfig?.deliverable?.strategy` regardless of which path populated it. Since
the fix ISS-340 proposes lives at exactly this unconditional line, a saved custom workflow with a
non-generic declared strategy should reproduce the identical Simple-vs-Canvas disagreement
ISS-340 documents for `ppt` — plus a SECOND, distinct visible symptom `ISS-340`'s own `ppt` repro
never reaches: the shared header title at `ComposerPage.tsx:1020` also reads `deliverableLabel`,
but its ternary only takes that branch when `builtinCanvasType` is falsy — exactly this card's
condition — so the title bar itself would read `"Custom · Composer"` even when the workflow's true
saved strategy is not custom.

## Expected vs actual

- **Expected:** A saved custom workflow's Simple tab and Canvas tab agree on its declared
  deliverable strategy — the same expectation ISS-340 states for a built-in.
- **Actual (expected from the code, not yet observed live):** Simple's "Deliverable type" field
  AND the header title both read "Custom" regardless of the workflow's real saved strategy;
  Canvas's combobox shows the true strategy (or its own honest "declared by this workflow"
  fallback for one outside `KNOWN_STRATEGIES`).

## What would confirm it

In "My Workflows", open (or first save via Canvas's Deliverable-strategy dropdown, then reopen) a
custom workflow whose manifest declares `deliverable.strategy` as `single_file` or
`serialized_sandbox`; read `[data-testid="composer-deliverable-type"]` on Simple and the header
title text, compare against Canvas's "Deliverable strategy" combobox value/selected-option text on
the same load, with no save/reload between the two reads — mirroring ISS-340's own reproduction
steps exactly, just on a saved custom workflow instead of a built-in.
