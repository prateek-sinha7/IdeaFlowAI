## What is broken

On the "simple launch panel" shell (`/create/user-stories`, `/create/app`, and
any `/create/<workflow_type>` other than `ppt`/`prototype` — see
`velocity.json` routes note), the **Run workflow** button never disables or
shows a loading state after being clicked. A second click landing before the
client-side route push to `/runs/<id>/stream` completes re-invokes
`handleRun` and fires a second, fully independent `POST /api/runs` — two
simultaneous runs from one user action.

Root cause: `frontend/src/components/workflow/IdeaInputPage.tsx:1480-1481`

```
const handleRun = () => {
  if (!ideaInput.trim() || pipelineAgents.length === 0) return;
```

`handleRun` never sets an in-flight/submitting flag anywhere in its body. The
button's `disabled` prop, `frontend/src/components/workflow/IdeaInputPage.tsx:1888`:

```
disabled={!ideaInput.trim() || pipelineAgents.length === 0 || (isMigrationMeta && !migrationChoice)}
```

only re-evaluates field validity (brief text, agent roster, migration
choice) — nothing there reflects "a run is currently being submitted". Since
nothing disables the DOM node between the first click and the SPA
navigation, a second click in the same window re-enters `handleRun` and
issues a second POST.

Signed in as `qa-admin@flowinqa.com`. Bug: QA-SG-002 (`LEDGER.md` /
`BUGS.md#qa-sg-002`).

- **Attempt 1** (cycle 1, single click): cold navigate to
  `http://localhost:3000/create/user-stories`, filled
  `textarea[name='brief']`, single `.click()` on "Run workflow". Checked
  `button.disabled` immediately after the click event handler ran — still
  `false`. Page routed to `/runs/7d946590-86cb-4ee1-99cc-d99709fbe029/stream`.
  Only 1 `POST /api/runs` fired (only 1 click made), but confirms the
  reporter's "no visual change — no disabled state, no loading indicator"
  observation.
- **Attempt 2** (cycle 2, double click): cold navigate again, refilled the
  brief, fired two synchronous `.click()` calls on the same button reference
  inside one `page.evaluate()`. After the first click, `button.disabled` was
  still `false` and the node was still in the DOM, so the second `.click()`
  fired too. Network log showed **two** `POST http://localhost:8000/api/runs`
  calls, returning two distinct `run_id`s:
  `e76d1416-d01a-4a6d-86da-80e224585405` and
  `17abafce-bdc7-4de1-a4bc-67e0ef7a36c0`.
- **Attempt 3** (cycle 3, double click): same recipe from a fresh cold
  navigate — same result, `button.disabled` stayed `false` after the first
  click, second click fired, two `POST /api/runs`, landed on
  `/runs/d7daa6f1-0072-4da1-bc9b-6f7eac22317c/stream`.

**Named trigger:** a second click on "Run workflow" landing before the SPA
route push to `/runs/<id>/stream` resolves. The button gives no disabled or
loading feedback in that window, so the click handler is fully re-entrant.

**Expected:** the button disables immediately on click (grayed out,
unclickable) and stays disabled until navigation/submission completes.

**Actual:** `button.disabled` remains `false` through and after the click;
a second click creates a second, independent run with its own `run_id`.

## Blast radius — ANALYZED 2026-09-22

`handleRun` has exactly one caller — this file's own "Run workflow" button
(`IdeaInputPage.tsx:1887`) — so it is not a shared function other pages route
through, and "blast radius" here means every OTHER launch handler that
duplicates its shape, not every caller of one function. `grep -rln
"IdeaInputPage" frontend/src` turns up `AgentsPopup.tsx`, `LaunchWizard.tsx`,
`CanvasView.tsx`, `ComposerPage.tsx`, `CanvasConfigRail.tsx` — none render
`<IdeaInputPage>` itself, they only import shared helpers
(`BriefAttachBox`/`useBriefAttachments`/`orderedStagedUploadIds`).
`grep -n "<IdeaInputPage" frontend/src -r` resolves to exactly one mount,
`DashboardLayout.tsx:3062`. So each of the other pages has its OWN
independent run-launch implementation, and each was checked directly for
the same missing-guard shape:

- **`ComposerPage.tsx` `handleRunOnce`** (`ComposerPage.tsx:984`, invoked
  from the "Run once" button's `onClick` — `ComposerPage.tsx:1313` — AND the
  brief textarea's Cmd/Ctrl+Enter shortcut — `ComposerPage.tsx:1457`, same
  unguarded function, two entry points). Read directly: no
  `submittingRef`/`isSubmitting` anywhere in the function or the file. The
  button's only `disabled` condition is `disabled={!onRun}`
  (`ComposerPage.tsx:1315`) — never re-evaluated for an in-flight
  submission. `DashboardLayout.tsx` wires this `onRun` straight to
  `onStartPipeline` with no guard either. Same consequence as this card:
  two back-to-back invocations both reach `onRun` and fire two independent
  `POST /api/runs`. CONFIRMED by direct file read that the guard is absent;
  INFERRED (not live-reproduced) that it double-fires the same way — filed
  as [ISS-767](20260922-1445-ISS-767.md).
- **`LaunchWizard.tsx` `handleLaunch`** (`LaunchWizard.tsx:963`, serves
  `/create/ppt` and `/create/prototype` per
  `frontend/src/app/[...view]/page.tsx:3987-3988`) — also has no
  `submittingRef` and its own button shows no loading state either, but the
  mechanism differs enough to rule out as a sibling of THIS defect:
  `handleLaunch` never calls `onRun`/POST directly. It writes a draft to
  `sessionStorage` (`draft.draftKey`/`draft.pendingKey`, per the
  `MODE_KEYS` map at `frontend/src/lib/launchDraft.ts:87-93`) and calls
  `router.push(routes.home())`. The actual run start happens once, from a
  `useState` lazy initializer in `DashboardLayout.tsx:544-606` that reads
  `sessionStorage.getItem("prototype.pending")`/`"ppt.pending"` on
  DashboardLayout's own first mount — a React lazy initializer runs exactly
  once per mount, so a double-click here re-writes the same sessionStorage
  key and pushes to the same route twice, not two independent runs. Checked,
  not filed as a sibling.
- **`WorkflowView.tsx`** (the Run button covered by
  [ISS-328](20260828-1834-ISS-328.md)/[FIX-391](20260829-0305-FIX-391.md)) —
  `grep -rn "<WorkflowView" frontend/src` resolves only to
  `frontend/src/app/workflow/page.tsx:96`, a bare (non-catch-all) Next.js
  route. `grep -n "'/workflow'" frontend/src/lib/routes.ts` returns nothing
  — `routes.ts` never generates a link to it — and the sibling
  `frontend/src/app/workflow/create/page.tsx` is explicitly called "the
  legacy `/workflow/create?mode=` page" in
  `frontend/src/app/[...view]/page.tsx:3980`'s own comment. Both are
  orphaned pre-catch-all routes, unreachable through normal in-app
  navigation (CONTEXT.md's invariant: the frontend routes every URL through
  `routes.ts` behind one catch-all). Not filed — dead code, not a live
  sibling.

## Fix — where it belongs

`handleRun` and its button are both in `IdeaInputPage.tsx`, and `handleRun`
has exactly one call site (its own button's `onClick`) — there is no shared
function to centralize this in. The already-proven pattern in this codebase
for this exact flaw class is [FIX-345](20260828-2250-FIX-345.md)'s
`submittingRef`, since replicated by [FIX-420](20260831-FIX-420.md)
(`togglingRef`) and [FIX-470](20260902-1200-FIX-470.md) (Composer Save
mutex):

- `const submittingRef = useRef(false)` in `IdeaInputPage`'s component body.
- In `handleRun` (`IdeaInputPage.tsx:1480`), set the guard AFTER the
  existing validity/design-picker early-returns (`ideaInput.trim()`,
  `pipelineAgents.length`, `isMigrationMeta`, `designMissing` —
  `IdeaInputPage.tsx:1481-1489`), not before: `if (submittingRef.current)
  return; submittingRef.current = true;` immediately before building
  `finalMessage` and calling `onRun(...)` (`IdeaInputPage.tsx:1561`). FIX-345
  placed its own guard after its equivalent early-returns for the same
  reason — a ref set at the very top and never released on an early return
  wedges the button permanently.
- `onRun` triggers an SPA route push (`handleRunPipeline` ->
  `setMainView("execution")`, `DashboardLayout.tsx:1691`) that unmounts
  `IdeaInputPage`, so unlike the login form there is no success path that
  needs the ref cleared. `onRun`'s type is `() => void`
  (`IdeaInputPage.tsx:756`) — it surfaces no rejection to this component
  today, so there is no `finally` to clear it against; note this if that
  contract ever changes.
- Thread the same intent into the button's `disabled`
  (`IdeaInputPage.tsx:1888`) via a `useState` companion (e.g.
  `isSubmitting`) purely for the VISIBLE disabled/loading state — a ref
  mutation alone does not trigger a re-render. Pair it exactly as FIX-345
  paired `disabled={isLoading}` with `submittingRef`: the ref stops the
  double POST, the state fixes the reporter's "no visual change, no loading
  indicator" complaint.

Apply the identical pattern to [ISS-767](20260922-1445-ISS-767.md)
(`ComposerPage.handleRunOnce`) in the same pass — same shape, same fix,
different file — rather than as a follow-up.
