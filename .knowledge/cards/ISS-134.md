# ISS-134

## Title

No cancel path in the system is multi-instance-safe, and FIX-243 makes that boundary load-bearing rather than academic. Liveness is decided by _is_run_live (run_engine.py:143), which reads the process-local _PIPELINE_TASKS / _PIPELINE_QUEUES dicts. Today that is sound: the deployment is single-process — docker-entrypoint.sh runs exec uvicorn with no --workers, and there are no replicas — so "not live in this process" == "not live anywhere". The locked to-be architecture is ECS Fargate (see to-be-architecture.html / the migration playbook), where it stops being sound in two directions at once: a Stop landing on instance B for a run driven on instance A would (i) take FIX-243's not-live branch and write status="cancelled" while instance A keeps billing, and (ii) be overwritten later by A's own terminal write — so the owner sees a cancelled run that was not cancelled, then a completed one they had stopped. The pre-FIX-243 behaviour was not better (the Stop reached nothing and the run finished anyway); the difference is that the wrong answer is now written down. Neither ISS-089 option fixes this — Option B's durable marker would not stop instance A either. What it actually needs: a cross-process liveness fact — a run lease / heartbeat row that instance A renews and instance B can read, plus a durable cancel signal A polls at its cooperative boundary. That is a design item for the migration, not a patch. Do not let FIX-243 be mistaken for multi-instance-safe; the constraint is recorded in _cancel_run_without_a_live_driver's docstring as well as here.

## Source / evidence

Recorded as an explicit scope note during FIX-243 rather than discovered as a failure — nothing multi-instance exists to fail yet. Single-process claim verified at HEAD: exec uvicorn in docker-entrypoint.sh with no --workers flag, no replicas key in docker-compose.yml.
