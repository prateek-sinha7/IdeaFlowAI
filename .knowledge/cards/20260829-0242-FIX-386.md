## What was wrong

BUG-20260828-094937-settings-usage-r2 (`bug-hunter/ledger.md`), validated 3/3
cold-start cycles as [ISS-321](20260828-2002-ISS-321.md). A basic-tier session
(`qa-basic@flowinqa.com`) that navigated straight to `/create/prototype` got the
identical, fully interactive "Configure your prototype" wizard a Pro/Enterprise
account gets — brief textarea, Attach file/Voice, the whole template gallery,
Design System and Discovery tabs — and, after typing a brief, an **enabled**
"Continue" button. No lock, no upgrade prompt, nothing anywhere in the flow.

`/settings/usage` tells that same account, correctly, that its plan covers only
Product Requirements and Presentation, and the dashboard catalog card for
"Build an interactive prototype" is already rendered `disabled` with a
"Requires Pro plan" badge. The gate existed in exactly one place — the catalog
card — and the URL the card would have opened was not gated at all.

## Root cause

`frontend/src/components/workflow/LaunchWizard.tsx` had **zero** tier awareness:
`grep -n "tier\|entitle\|canRunPipeline"` over the whole 1235-line file returned
nothing. Neither render site supplied it either —
`frontend/src/app/[...view]/page.tsx:3837` returns
`<LaunchWizard initialMode={wizardMode} />` with no tier prop (its
`userTier={user?.tier ?? "basic"}` at `:4187` goes to `DashboardLayout`, which
forwards it only to `AppHeader` and `HomeLaunchGrid`), and
`frontend/src/app/workflow/create/page.tsx:24` renders the same component from a
separate Next.js route that has no access to the profile at all.

So `canContinue` (`LaunchWizard.tsx:689-696` pre-change) was purely a
form-completeness test — brief present, design system / template picked — and
the Continue button's `disabled={!canContinue}` was the only thing standing
between an unentitled tier and a staged launch. The backend was never affected:
`backend/app/api/run_commands.py::_require_tier_entitlement` still rejects the
run at creation. This was a client-side-only gap, but a real one — the user
invests the whole brief-and-template effort before anything says no.

## What changed, and why there

One file: `frontend/src/components/workflow/LaunchWizard.tsx`.

- The existing mount-time auth effect (`:277-289`) now also calls
  `getMe(token)` and stores `u.tier`. Non-fatal `.catch(() => {})`, mirroring
  the same call's treatment in `[...view]/page.tsx:869-877`.
- A derived pair next to `canContinue` (`:706-714`):
  `const launchPipeline = MODE_CONFIG[mode].savePipeline;`
  `const locked = tier !== null && !canRunPipeline(tier, launchPipeline);`
  plus `upgradeTo` from `getUpgradeTier` for the badge copy.
- `locked` is applied in three places: the Continue button's
  `disabled={!canContinue || locked}`, `handleLaunch`'s existing early return
  (`if (!canContinue || locked) return;`), and a lock banner that renders in
  place of the "what's still missing" pills — `Requires {TIER_LABELS[upgradeTo]}
  plan`, the same wording and the same `border-brand/20 bg-brand-fill text-brand`
  treatment `HomeLaunchGrid.tsx:317-320` uses on the locked catalog card.

**Why in the component, not in the page.** Both cards that name a fix location
([ISS-321](20260828-2002-ISS-321.md) and
[ISS-473](20260829-0111-ISS-473.md)) reach the same conclusion: `LaunchWizard` is
the component both render sites mount, so a guard there closes every current and
future caller in one change. Re-grepped `LaunchWizard` across `frontend/src`
before editing — still exactly two render sites, so the blast radius in the card
holds. A guard placed in `[...view]/page.tsx` instead would have left
`/workflow/create?mode=prototype` — which `DashboardLayout.tsx:1547,1574` and
`CreationHub.tsx:31,35` actively `router.push` to — completely ungated, and the
T17 redirect a comment in `page.tsx:3628` claims neutralises that route does not
exist in `frontend/next.config.ts`.

The wizard owns the tier lookup rather than taking it as a prop for the same
reason: only one of the two render sites has `user.tier` in scope, so a prop
would have gated one route and not the other. The cost is one extra
`GET /api/auth/me` on a page that already fires the agent library, both template
registries, the design-system registry and the workflow-detail override probe.

**One test file was touched, and no assertion in it changed.**
`frontend/src/components/workflow/LaunchWizard.test.tsx` replaces `@/lib/api`
wholesale with a `vi.mock` factory, so a newly imported export must be listed
there or every test in the file dies on the import rather than on its own
assertion. `getMe` was added to that factory, resolving an `enterprise` user —
the entitled path those 19 tests were written against. Nothing else in the file
was edited.

## Not fixed by this card

The three INFERRED siblings stay **open**. None is on this bug's fix assignment,
none has been reproduced live, and each carries `verification.type: manual`,
`status: pending` with no test — there is nothing here that could prove a change
to them, and two of them name files outside this card's `applies_to.globs`:

- [ISS-472](20260829-0110-ISS-472.md) — `IdeaInputPage` (`mainView === "input"`,
  i.e. `/create/app`, `/create/user-stories`) gets no `userTier` prop from
  `DashboardLayout.tsx:2901-2930` and has no tier awareness of its own.
- [ISS-473](20260829-0111-ISS-473.md) — the standalone `/workflow/create` route.
  Its `<LaunchWizard>` render **is** covered by this fix (that is the point of
  putting the guard in the component), but the card's other half — that the
  route bypasses the ADR-0018 catch-all and that the T17 redirect it cites is
  absent from `next.config.ts` — is untouched and still stands.
- [ISS-474](20260829-0112-ISS-474.md) — `ComposerPage` for the built-in
  `/workflows/{type}/canvas` route, likewise rendered with no tier prop.

Also noted, not changed: "Save workflow" and "Save as my version" remain enabled
for a locked tier. They create a catalogue row rather than a run, no card covers
them, and the register's Expected is specifically about reaching a submit-ready
launch.
