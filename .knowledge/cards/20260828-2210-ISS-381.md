## What was found

While fixing [ISS-225](20260828-1541-ISS-225.md) / [ISS-254](20260828-1810-ISS-254.md)
([FIX-337](20260828-2210-FIX-337.md)), the sibling card
[ISS-263](20260828-1811-ISS-263.md) was checked against the running app rather
than inferred. Its central factual claim does not hold.

ISS-263 states, marked INFERRED and with "request/response not yet captured":

> **Actual:** "Save workflow" reports success (201 ...) while persisting
> `selections: {_wizard: {...brief}}` with no per-step data at all ... no 422.

Observed instead, `/create/ex_A4_human_divert`, brief typed, Advanced untouched,
"Save workflow" -> name -> Save:

```
POST http://localhost:8000/api/user-workflows -> 422
```

Reproduced directly against the API with the exact body the button sends:

```
{"base_pipeline_type":"ex_A4_human_divert",
 "agent_ids":["custom-agent:ask","custom-agent:pick-language","custom-agent:a-english"],
 "selections":{"_wizard":{"brief":"probe"}}}
-> 422 {"detail":"agent_ids not allowed for 'ex_A4_human_divert':
        ['custom-agent:ask', 'custom-agent:pick-language', 'custom-agent:a-english']"}
```

The rejection comes from the roster check at
`backend/app/api/user_workflows.py:562`, and it fires BEFORE
`_compile_selections_trust_user` (`:349-395`) is ever reached. So the
selections-map mechanism ISS-263 traced is not what the user hits: the button
fails loudly on the workflow's OWN composed step ids, which the roster validator
does not accept for a non-`custom` `base_pipeline_type`. Pre-existing —
`user_workflows.py` carries no uncommitted change (last touched by `732adc245`).

## Why ISS-263's proposed merge must not be applied as written

ISS-263 (and the register's own "pending ISS-263" note) proposes merging
`manifestSelections` into `handleSaveWorkflow`'s outgoing `selections:` map.
Measured against the real synth + compiler, that converts the failure rather than
removing it:

- `synthesize_manifest` builds each step from scratch and projects `route` NOWHERE
  — it is absent from `_LEVER_KEYS` (`backend/agents/workflows/selections.py:43-49`)
  and from the verbatim-projection loop (`:149-153`). So a merged
  `gates: ["before-human", "conditional"]` synthesises a step with a conditional
  gate and no route, and R-03 fires from the OTHER direction:

  ```
  step 'custom-agent:pick-language' declares gates: [conditional] but has no route
  (or route.outcomes is empty) — route: is required when gates: [conditional] is
  declared (R-03)
  ```

  Verified for all five route-declaring examples (`ex_A1_loop`, `ex_A2_branch`,
  `ex_A3_divert`, `ex_A4_human_divert`, `ex_A4_human_gate`); the other 25 built-ins
  either carry no gates (short-circuit on `has_selections`) or compile clean
  (`prototype`, `prototype_revision`, `prototype_feature_revision`,
  `sc001-test-fixture`).

- Making the merged map compile needs the selections map to carry AUTHORING
  structure, not just levers: `route` (with `outcomes[].target` AND
  `condition_agent` normalised to composed node ids — `ex_A4_human_gate` declares
  `condition_agent: ask`, and the synth's steps have no `instance_id` for the dual
  lookup to fall back on) plus `produces: ["route_decision"]` on the resolved
  decision source for R-27. Confirmed by probe: `gates + route` alone still fails
  R-27; `gates + route + produces` compiles.

That is a contract change to the persisted compact selections map, which
`selections.py`'s own docstring describes as a per-step LEVER map. It also buys
nothing at run time: `engine._apply_selections`
(`backend/agents/execution_engine/engine.py:8507-8690`) patches only
`validators / gates / model / retry / injects / skills / strategy / fanout /
task_source` onto the file-compiled step — there is no `route` overlay, so the
engine keeps compiling the base file-backed plan regardless.

## Answer to ISS-263's own open question

ISS-263 left open whether a "Save workflow"-created row loses the routing at
launch. It does not: `_apply_selections` never applies `route`, so the run plan
comes from the base workflow's file-backed manifest either way. By ISS-263's own
wording that narrows its finding to "the persisted `selections` row is
misleading/incomplete" — except that, per the observation above, the save never
succeeds in the first place.

## What would settle the disposition

A decision on which of the two is wanted, since they are different fixes:

1. **Make "Save workflow" work on a seeded example at all** — the roster
   validator at `user_workflows.py:562` must accept a built-in's own composed
   `custom-agent:<instance_id>` step ids when `base_pipeline_type` is that
   built-in. This is the defect the user actually meets, and it is not what any
   of ISS-225/254/263 describes.
2. **Make the compact selections map able to represent a conditional step** —
   project `route` + `produces` through `_synthesize_step` and have the FE emit
   both with normalised ids. Larger, needs an ADR (it widens what a selections
   map is), and is inert at run time.

Until one is chosen, `test_save_workflow_captures_the_routed_steps_gates`
(the ISS-263 test) stays xfail. It was NOT edited — it asserts the card's stated
Expected, and the card, not the test, is what is out of date.
