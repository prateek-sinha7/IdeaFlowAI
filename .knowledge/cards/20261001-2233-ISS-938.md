# ISS-938

## What happened

Derived while analysing QA-KB-037 (root card [ISS-758](20260922-1421-ISS-758.md)). ISS-758's agreed
minimal fix is a generation counter (`selectGen`) bumped by every `handleSelectVersion` call, which makes a
SECOND PICK supersede a first. It cannot see the other two writers of `viewingVersion`, which are driven by
the URL pin rather than by the handler:

| writer of `viewingVersion` | where (HEAD 024c03ef8) | bumps `selectGen`? |
|---|---|---|
| pin dropped from the URL, `setViewingVersion(null)` | `PreviewPanel.tsx:983` | no |
| pinned member resolved from the URL, fetch, `setViewingVersion(versionViewFrom(run))` | `PreviewPanel.tsx:999-1025`, guarded only against ITSELF by `cancelled` (`:1013`, `:1024`) | no |

So when the URL pin moves by any route other than a menu pick while a pick's fetch is in flight, the
abandoned pick's continuation (`PreviewPanel.tsx:914`) still passes `gen === selectGen.current` and applies.
The reachable route is the browser Back/Forward button: every pick pushes a history entry
(`window.history.pushState`, `DashboardLayout.tsx:551`), so Back is the natural "wrong one, undo" gesture.

## Root cause (CONFIRMED by source read and by execution at component level)

Same root cause as ISS-758: the handler's post-`await` apply trusts only its own call sequence, not the pin
actually in force. ISS-758's agreed fix narrows that to "no newer handler call"; the URL is the pin's source
of truth (a locked constraint of [FIX-603](20260922-1440-FIX-603.md): `pinnedVersion` is the read-only pin's
source of truth), so a URL change that is not a pick has to supersede the pick too.

Executed 2026-10-01 in jsdom (scratchpad harness, no repo file touched, vitest 4.1.11) against (1) the
unmodified `PreviewPanel.tsx` and (2) a scratchpad COPY carrying exactly the ISS-758 agreed fix:

- **S1.** Render with `pinnedVersion="1"` (applies v1), pick v2 from the menu (`getWorkflow(member-2)` held
  pending), re-render `pinnedVersion="2"` (the URL write round-tripping), re-render `pinnedVersion="1"` (Back),
  then resolve v2. URL pin is `1`; panel after: banner `Viewing v2 (read-only)`. RED on both (1) and (2).
- **S1b.** Same, but the final URL carries no pin (Back to the base `/runs/{id}` URL): v2 is re-applied under
  an un-pinned URL. RED on both (1) and (2).

## Expected vs actual

- **Expected:** after Back the panel shows what the URL names (v1, or live) and the abandoned pick leaves no
  trace.
- **Actual:** the abandoned pick's response lands last and the panel shows v2 (chip, banner, Steps, Preview,
  Workspace flip, same blast radius as ISS-758) while the address bar says v1 or names no version.

## Why the root cause implies it

`viewingVersion` has three writers (table above). ISS-758's counter closes handler-versus-handler only; the
handler's continuation stays unguarded against the other two.

## Fix direction (not applied)

Verified on a second scratchpad copy: ISS-758's fix PLUS two `selectGen.current++` lines in the existing
effects, one in the no-pin branch of the `[pinnedVersion]` effect (`:983`) and one in the URL-pin effect right
after its `if (!pinnedMemberId) return;` (`:1000`). Result: S1 and S1b green; ISS-758's scenarios A
(out-of-order), B (live-return), C (late failure), D (sequential control) and E (a normal pick whose URL
round-trip arrives before the response) stay green; the 17 existing `PreviewPanel*.test.tsx` files give
results identical to the unpatched copy.

Trade-off to weigh (by reading, not executed): with the bumps a handler fetch is superseded whenever the URL
moves, so the URL-pin effect becomes the applier for that pick (it fetches the same member; `getWorkflow` is
single-flighted, `api.ts:686-698`, [FIX-637](20260922-2358-FIX-637.md)). If that fetch FAILS, only the
effect's `catch` runs (`:1018-1022`, warn-only) instead of the handler's `setViewingVersion(null)`, so a failed
pick leaves the previous view up rather than clearing to live. Apply together with, or after, ISS-758's fix:
both edit the same counter.

## Status

`pinnedVersionFor(parsedView)` in `page.tsx` hands down after `handlePreviewPanelTabSelect` pushes the route,
`DashboardLayout.tsx:516-552`); a real Back press through Next's patched history was not driven. What settles
it: the validator's delayed-route recipe from the ISS-758 card (hold the first `GET /api/runs/<uuid>` for 5 s),

## Fixed — QA-KB-037 (fixer, 2026-10-02): [FIX-711](20261002-0215-FIX-711.md)

The fix direction above was applied as written, together with ISS-758's counter:

- `selectGen.current++` in the no-pin branch of the `[pinnedVersion]` effect (`PreviewPanel.tsx:992`);
- `selectGen.current++` right after `if (!pinnedMemberId) return;` in the URL-pin effect (`:1010`).

Observed: `PreviewPanel.staleVersionPick.test.tsx` "ISS-938" XPASS on 3 of 3 runs. The same body as a plain `it`:
before the edit it failed with `expected 'Viewing v2 (read-only)' to match /Viewing v1/`; after the edit it passes.

The trade-off named above was then executed instead of only read. A scratch probe pinned v1, picked v2, and rejected
`getWorkflow(m2)` after the URL round-trip:

- before the fix: `banner=[] chip=[Viewing v2▾]`;
- after the fix: `banner=[Viewing v1 (read-only)] chip=[Viewing v2▾]`.

Both mislabel the failed version, so this is not a regression in kind. It is carded for a UX decision as
[ISS-955](20261002-0215-ISS-955.md). A real browser Back press is still not driven, as the Status section above notes.
