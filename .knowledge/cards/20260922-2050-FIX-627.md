## What was wrong

**1. The saved-workflows list was fetched twice per page view.**
`GET /api/user-workflows` fired 2x on a cold `/workflows` load and 4x on a
client-side nav into it (ISS-788's own 3-cycle capture). Every one of those
calls goes through a single function — `getUserWorkflows()`
(`frontend/src/lib/api.ts:2032` before this change) — from a single production
call site, `SavedWorkflowsPage.tsx:170`'s mount effect. It is guarded only by a
`let cancelled = false` flag, which blocks the state update, not the request,
so React StrictMode's dev double-invoke and an SPA remount each pay for the
list again. `getMe` was the same shape and is already closed by
[FIX-618](20260922-1945-FIX-618.md)'s `cachedGet()`; `getWorkflows` by
[FIX-616](20260922-1923-FIX-616.md)'s `inFlightWorkflows`. This list was the
one left.

**2. "Duplicate" could POST twice for one intent.**
`handleDuplicate` (`SavedWorkflowsPage.tsx:195-206`) called `setOpenMenuId(null)`,
which closes the dropdown PANEL only — the kebab TRIGGER
(`SavedWorkflowsPage.tsx:110-119`) stays mounted and enabled for the whole
`await createUserWorkflow(...)`. Reopening that menu and clicking Duplicate
again mid-request created a second saved-workflow row server-side (the POST is
not idempotent). `handleRenameSave` and `handleDeleteConfirm` are immune for
free — both close their modal synchronously before the await, so their button
is gone by the time the request starts — and are deliberately untouched here.

## What changed and why there

**`frontend/src/lib/api.ts`** — `getUserWorkflows()` keeps its signature and
consults a module-level `inFlightUserWorkflows` Map keyed by `token` before
starting a request; a caller arriving while an identical request is open gets
that same promise, and the key is deleted in `.finally()`. This is the request
layer every caller routes through, so the one guard covers the mount effect,
its StrictMode twin, and any future caller — not one page. It deliberately
mirrors `inFlightWorkflows` (`api.ts:871`) and `refreshOnce()` (`api.ts:225-233`)
in the same file.

It de-duplicates and does **not** cache: the entry is dropped the moment the
request settles, so a mount after a rename/duplicate/delete still sees the
server's copy. `cachedGet()`'s 30s TTL would have been the wrong tool — its own
comment (`api.ts:404-406`) scopes it away from run/workflow lists for exactly
this reason, and this list is mutated from the page that reads it.

**`frontend/src/components/savedworkflows/SavedWorkflowsPage.tsx`** — a
`duplicatingRef` holding a `Set<string>` of row ids whose POST is still open,
checked at the top of `handleDuplicate` and cleared in a `finally`. A ref, not
state, because it gates the handler rather than the render; a Set keyed by row
id, so duplicating a *different* row meanwhile is unaffected. This is the one
handler in the file that needs it, per ISS-815's read of all three.

A concurrent, uncommitted change to `api.ts` for ISS-789/ISS-816 (QA-PS-042)
added an `inFlightAdminUsers` guard of the same shape in the admin section of
the file. Both changes coexist; neither overwrote the other. Line numbers here
are the working tree at the time of writing (`getUserWorkflows` at `api.ts:2054`).
