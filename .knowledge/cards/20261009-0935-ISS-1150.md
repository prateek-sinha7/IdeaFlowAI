# ISS-1150

**Register source:** sibling derived during the `QA-KB-108` analysis on 2026-10-09 (root [ISS-1144](20261009-0725-ISS-1144.md)). Not its own bug row.

**Confidence:** the placement rule is CONFIRMED twice: by reading Starlette (`backend/.venv/lib/python3.13/site-packages/starlette/applications.py:62-71`) and by executing a throwaway app that mirrors `main.py`'s middleware order (`evidence/qa-kb-108/05-analyze-handler-placement-and-signing-output.txt`, part 1). INFERRED: that any exception OTHER than a `BotoCoreError` (for example a database `OperationalError`) behaves the same on the real app; the mechanism says it must, but it was not probed.

## Condition

- Any exception that no route handler converts to an `HTTPException`, on any of the 25 routers `main.py` mounts (`app.include_router`, `:560-602`). The only registered handler is `RequestValidationError` (`backend/app/main.py:539`).
- Starlette sorts handlers when it builds the stack: `if key in (500, Exception): error_handler = value` goes to `ServerErrorMiddleware`, the OUTERMOST layer; every other key goes to `ExceptionMiddleware`, the INNERMOST (`applications.py:62-71`). `CORSMiddleware` sits between them (`main.py:474`), so the outer 500 is produced after the exception has already left it, and nothing adds `access-control-allow-origin`. `fetch` then rejects with a `TypeError`, not an `ApiError`, and the login page prints its generic string (`frontend/src/app/login/page.tsx:73-81`).
- Adjacent case with the same shape (INFERRED): `login` runs `db.query(User)...first()` before any Cognito call (`auth.py:332`); a database outage there is the same CORS-less 500.

## Expected vs actual

Expected: a provider-credential or network failure surfaces as a 503 the browser can read, whichever route raised it. Actual (probe, throwaway app, no handler): 500, no ACAO.

| handler registered for | status | ACAO |
|---|---|---|
| none (today) | 500 | absent |
| `Exception` | 503 | absent |
| `500` | 503 | absent |
| `BotoCoreError` | 503 | present |

## Why the root cause implies it

The second half of the reported symptom ("no CORS header") does not depend on boto at all. Fix every Cognito handler and the next unhandled exception reproduces the CORS-less 500; fix only this and the audit event and per-endpoint semantics listed below are still wrong.

## Fix direction (INFERRED, not applied)

- Register the handler for the CLASS: `app.add_exception_handler(BotoCoreError, ...)` returning a JSON 503 with a `detail` string. Lookup walks the exception's MRO (`starlette/_exception_handler.py:16-20`), so `TokenRetrievalError`, `NoCredentialsError` and `EndpointConnectionError` all find it. The obvious `@app.exception_handler(Exception)` does NOT work: the table above shows it still has no CORS header.
- Log the exception inside the handler (`logger.error(..., exc_info=exc)`). A handled exception no longer reaches Starlette's default error logging, and the traceback in the backend log is how this whole family was diagnosed.
- Message: the existing `Authentication service unavailable` is right for the auth routes; the request-path boto callers found are the Cognito ones (`cognito.py`, `cognito_admin.py`, `provisioning.py`, `auth.py`) and the host-metrics adapter, which already swallows its own credential and endpoint errors (`except Exception` at `backend/app/services/host_metrics.py:132, :173, :210, :312`, pinned by `backend/tests/unit/app/test_host_metrics_adapter.py:280-298`). A single message is therefore acceptable; a neutral wording is the fixer's call.
- Treat it as the safety net, not the fix. It cannot emit `LOGIN_FAILURE` with `provider_error:<class>` (`auth.py:358-363`), which feeds the `login_failure` log metric filter (`infra/terraform/modules/monitoring/main.tf:2118-2121`), and it would turn `/forgot-password` into a state oracle where its contract says it must stay a generic 202. Both need the per-route handling in [ISS-1144](20261009-0725-ISS-1144.md).
- Not in scope: a catch-all for every `Exception` that also stamps CORS headers. That changes behaviour for all routes and is a separate hardening decision.

## Test notes

Do not test this against a copy of the app; the placement rule is exactly what a copy would hide. Mount a throwaway route that raises `TokenRetrievalError` on the real `app` (and remove it afterwards), call it with `TestClient(app, raise_server_exceptions=False)` and an `Origin` header, assert 503, a string `detail`, and `access-control-allow-origin` present. A second assertion that a plain `RuntimeError` route still gives the existing 500 keeps the scope honest.
