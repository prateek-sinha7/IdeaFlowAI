## Summary

Derived while analyzing **BUG-20260828-031600-settings-usage** / [ISS-291](20260828-1917-ISS-291.md)
(the "Manage plan" button on `/settings/usage` has no `onClick` at all). That card's root
cause is broader than one missing prop — no plan-management/upgrade capability exists
**anywhere** in the codebase: confirmed by grepping `backend/app/api/` for
`billing`/`subscription`/`stripe` (no matches beyond unrelated "run kept billing" comments)
and the frontend for `"Manage plan"` (exactly one occurrence, in `AccountSettings.tsx`).

`AppHeader.tsx` — the persistent app shell, mounted by `DashboardLayout` on every screen —
renders a second, independently-coded affordance making the same promise. In the
account-menu dropdown's identity block, a basic-tier user sees their plan and an "Upgrade"
link:

```tsx
{userTier === "basic" && (
  <button
    onClick={() => { setProfileOpen(false); onNavigate("settings"); }}
    className="text-[11px] font-semibold text-brand hover:underline leading-none"
  >
    Upgrade
  </button>
)}
```

(`frontend/src/components/layout/AppHeader.tsx:519-526`)

Unlike ISS-291's button, this one genuinely fires an `onClick` — but the destination it
navigates to is `AccountSettings`' default section (`onNavigate("settings")` passes no
section argument; `SECTION_ROUTE.limits` → `routes.settingsUsage()` exists but is never
selected here), where the user must still find the Usage & Limits tab and click "Manage
plan" — the exact button ISS-291 already proved does nothing. The label "Upgrade" is kept by
a control that cannot itself upgrade anything, and whose destination cannot either.

## Why the root cause implies this

ISS-291's root cause, once generalized past its one line of JSX, is "no upgrade capability
exists in this app, frontend or backend." Any other UI surface using the word "Upgrade" as
an apparent call-to-action necessarily terminates at that same missing capability — there is
nowhere else for it to go. A frontend-wide grep for `Upgrade` (excluding tests) found exactly
one other match: `AgentsPopup.tsx:1214`, which is a source comment describing a **deliberately
unimplemented** "Upgrade to use" copy variant for a different (engineer-only lock) feature —
explicitly not live, and not a match for this pattern. `AppHeader.tsx:519-526` is the only
other real, rendered "Upgrade" control in the app.

## Expected vs Actual

- **Expected:** the account-menu "Upgrade" CTA either lands a basic-tier user somewhere that
  can action an upgrade (or clearly explain why not — e.g. "contact your admin"), or at
  minimum deep-links straight to `/settings/usage` where the plan context is visible.
- **Actual:** it navigates into `AccountSettings`' default (profile) section — not even
  `/settings/usage` — where the only further "upgrade" control anywhere in the app is the
  "Manage plan" button from ISS-291, which has no handler bound to it at all.

## Confidence: INFERRED

Confirmed by source read (`AppHeader.tsx:519-526`, `AccountSettings.tsx:457-459`, and a
codebase-wide grep for `stripe|subscription|billing|Manage plan|Upgrade`) — not yet
reproduced live in the browser. What would settle it: sign in as `qa-basic@flowinqa.com`,
open the account-menu dropdown, click "Upgrade", confirm it lands on `/settings` rather than
`/settings/usage`, then confirm (per ISS-291) that no in-app control from there can complete
an upgrade.

## Where the fix belongs

Same place as ISS-291's: one shared component (e.g. an upgrade/contact-sales modal) that
both `AccountSettings.tsx:457-459` and this button's `onClick` open directly, rather than
this button continuing to just relocate the user to a page whose own CTA is equally inert.
A modal avoids adding a new route (no `routes.ts` / ADR-0018 change needed); if a dedicated
page is chosen instead, it must be registered through `routes.ts` per ADR-0018 rather than
linked ad hoc.
