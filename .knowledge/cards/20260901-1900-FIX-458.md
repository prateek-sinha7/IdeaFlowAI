## What was wrong

`LibraryPage.skillMarkdown.test.tsx`'s second assertion:

```tsx
expect(/\*\*bold\*\*/.test(dialog.textContent ?? "")).toBe(false);
```

scanned the entire `[role=dialog]` — which contains two sibling sections:
1. The "Formatted content" block (react-markdown rendered — no literal `**bold**`).
2. The "SKILL.md content" block — a deliberate raw `<pre>{skill.content}</pre>` source
   view that always contains literal `**bold**` by design.

FIX-403 correctly routed the formatted section through react-markdown, so assertion 1
(`dialog.querySelector("strong, b") !== null`) passed, but assertion 2 scanned the
whole dialog and always found `**bold**` in the raw `<pre>` — making it unsatisfiable
without removing the deliberately-endorsed raw-source affordance. The card
[ISS-605](20260829-0216-ISS-605.md) documented this exactly.

## What changed and why there

**`LibraryPage.tsx`** — added `data-testid="skill-formatted-content"` to the `<div>`
wrapping `<SkillMarkdown content={skill.content} />`. The raw `<pre>` block below it
is untouched (correct, endorsed by ISS-591's own evidence section).

**`LibraryPage.skillMarkdown.test.tsx`** — three changes:
1. Removed `it.fails` marker (FIX-403 already landed the real fix; the marker was
   only keeping this test artificially xfail while the assertion was wrong).
2. Assertion 1 now queries within `formattedContent` for `strong, b`.
3. Assertion 2 now checks `formattedContent!.textContent` — the formatted section
   only, which must not contain literal `**bold**` after react-markdown renders it.

Both changes are test-side only per ISS-605's "What to change" section. The
production code change (`data-testid`) is the minimum anchor the test needs.
