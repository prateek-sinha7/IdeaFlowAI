## Status: INFERRED — not yet independently reproduced

Filed while analyzing `BUG-20260828-091300-library-skills-r2` (skills detail route falls back to
the Library listing for every skill id, hyphenated or not — see
[ISS-232](20260828-1627-ISS-232.md), the root card for that bug). This card is a same-shape
prediction derived from the shared code path, not a fresh browser reproduction — mark it
INFERRED until someone drives `/library/hooks/<id>` and confirms or refutes it.

## Why the root cause implies this

`frontend/src/components/library/LibraryPage.tsx` opens all three detail types (agent/skill/hook)
through the SAME cold-mount/URL-seed effect ("T15", lines 518-543) and the SAME URL-close effect
("T16", lines 562-581) — one `if`/`else if` chain per type, not three separate mechanisms. Two
facts I confirmed by reading the source, applied to the Hooks branch specifically:

1. **CONFIRMED — every navigation between two `/library/{type}/{slug}` URLs remounts the whole
   page**, throwing away local `useState`. `frontend/src/app/[...view]/page.tsx:3195-3199`
   documents this as a verified Next.js behavior in THIS repo ("Next.js does not preserve a
   dynamic-route page's own instance across a client-side navigation to a new URL under the same
   catch-all — confirmed live: a fresh render-instance id appears right after router.push"), and
   `FIX-298` (`.knowledge/cards/20260825-FIX-298.md`) already had to patch around the identical
   remount for the run-stream route ("Next.js does not preserve a catch-all page's own instance
   across a client-side navigation to a new URL under the same catch-all. Every useState in the
   page resets."). This means the Hooks tab's own card `onClick` handler
   (`LibraryPage.tsx:915-919`: `setSelectedHook(hook); router.push(routes.libraryHook(hook.id));`)
   has its direct `setSelectedHook` call thrown away by the remount its own `router.push` call
   triggers — the identical dead-state pattern ISS-232 already established for the Skills tab's
   card click (`LibraryPage.tsx:822-824`). Click-through entry and cold URL entry both reduce to
   ONE mechanism: the T15 effect's hooks branch, `HOOKS.find(h => h.id === librarySlug.slug)` at
   `LibraryPage.tsx:535`, followed by `setSelectedHook(hook)` at line 538.

2. **CONFIRMED — `frontend/src/hooks/useHooksCatalog.ts:23-31` has the identical unmemoized-array
   shape as `useSkillsCatalog.ts:17-26`** (ISS-232's own suspected culprit for skills): a fresh
   `reduxHooks.map(...)` built on every render, with no `useMemo`. Contrast
   `frontend/src/hooks/useAgentLibrary.ts:29-38`, which explicitly memoizes its arrays with
   `useMemo` and documents why in its own comment: "without this, every render produced two fresh
   .filter() arrays, and a consumer effect keyed on libraryAgents would loop forever." `ISS-303`
   (`.knowledge/cards/20260828-1935-ISS-303.md`), filed after this bug's 09:13 UTC window,
   independently confirmed the AGENTS branch of this same T15 effect DOES open correctly on a
   cold URL (a "Coming Soon" agent's full detail dialog opened 3/3) — the one branch backed by
   `useAgentLibrary`'s memoized array. `useHooksCatalog` shares skills' unmemoized shape, not
   agents' memoized one.

Both the shared remount mechanism and the shared unmemoized-catalog shape are structurally
identical between the Skills and Hooks branches of the same effect, so a hook id is expected to
reproduce the same symptom ISS-232 documents for skills: the URL updates to
`/library/hooks/<id>` correctly, but the rendered content is the full Library catalog listing,
with no console error and no per-hook network request ever fired.

## What would confirm or refute this

- Navigate to `/library/hooks/<any-hook-id>` (both a cold `about:blank` load and a genuine
  Hooks-tab card click), the same two-axis repro `BUG-20260828-091300-library-skills-r2` used for
  skills, and check whether `HookDetailModal` opens or the listing renders instead.
- Cheaper and deterministic without a browser: a colocated RTL test mounting `<LibraryPage />`
  with hooks preloaded into the store and a URL parseable to
  `{screen: 'library-hook', slug: <real hook id>}`, asserting `selectedHook` becomes non-null.
