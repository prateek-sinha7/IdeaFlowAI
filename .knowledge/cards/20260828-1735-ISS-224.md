# ISS-224

**Register source:** `BUG-20260828-034200-handoff-settings` in `bug-hunter/ledger.md`.

## Symptom

The "GitHub access token" card on `/handoff/settings` states: "Needs `repo`
scope. Encrypted at rest, never returned by any API." The PAT `<input>` has no
client-side `maxlength`, so a value over the backend's 512-character limit can
be typed/set and submitted. The backend correctly rejects it with
`422 Unprocessable Entity`, but the response body's `detail[].input` field
contains the **complete, untruncated string that was submitted** — the
rejected "secret" round-trips back from the server in plaintext. The frontend
has no handling for this particular error shape (a FastAPI/Pydantic
list-of-errors `detail`), so it falls back to rendering the entire raw JSON
string — including the embedded `input` value — as visible page text
directly under the PAT field, and it is also present verbatim in the Network
tab response body.

## Root cause

Two independent defects compound:

1. **Backend** — `backend/app/api/settings.py:64`:
   `pat: str = Field(..., min_length=10, max_length=512)` on
   `GithubPATRequest`. There is no custom exception handler for
   `RequestValidationError` on this route (or globally, for this field), so
   FastAPI/Pydantic's default 422 handler serializes its standard error
   shape, which for a `string_too_long` violation includes `"input"`: the
   *entire* value that failed validation, unredacted and untruncated,
   regardless of the field's semantic sensitivity.
2. **Frontend** — `frontend/src/lib/api-handoff.ts:86-88`, inside
   `authedJson`:
   ```ts
   const message =
     typeof body?.detail === "string" ? body.detail : JSON.stringify(body);
   throw new Error(message || `HTTP ${resp.status}`);
   ```
   This only extracts a friendly message when `detail` is a plain string
   (the shape used by the 400 "GitHub rejected the PAT" case). FastAPI 422
   validation errors always send `detail` as a **list** of error objects, so
   this branch falls through to `JSON.stringify(body)` — the whole raw
   payload, echoed value included. `frontend/src/components/handoff/IntegrationsCard.tsx:113-117`
   (`handleSavePat`'s catch block) then sets `patMessage.text` to
   `err.message` and renders it directly under the PAT field as page text —
   no parsing, no redaction.

## Reproduction (3/3, each from a cold start — fresh `page.goto` to `/handoff/settings`, no prior UI state)

- **Cycle 1**: cold nav to `/handoff/settings` as qa-admin, set the PAT input
  to `"ghp_" + "A".repeat(5000)` (5004 chars, via the native input value
  setter + `input` event to bypass any client cap — there is none), clicked
  "Save". `PUT /api/settings/github-pat` → `422`. Response body's `input`
  field: the full 5004-char string, byte-for-byte identical to what was
  typed. Page snapshot confirmed the literal JSON string
  (`{"detail":[{"type":"string_too_long",...,"input":"ghp_AAAA...`, full
  value included) rendered as plain text under the PAT field. **Reproduced.**
- **Cycle 2**: fresh cold nav (through `/dashboard` then `/handoff/settings`
  again), different synthetic value: `"github_pat_" + "Z".repeat(600)` (611
  chars). `PUT` → `422`, `input` field = the full 611-char string verbatim.
  Page again rendered the raw JSON (with the embedded value) as text.
  **Reproduced.**
- **Cycle 3**: fresh cold nav again, third distinct value:
  `"ghp_" + "Q".repeat(800)` (804 chars). Same result: `422`, `input` =
  full 804-char string verbatim, raw JSON rendered on-page.
  **Reproduced.**

**Score: 3/3 — CONFIRMED.** No axis variation was needed; the defect is
deterministic on any submission over 512 chars, independent of the exact
value or entry timing. No PAT was ever actually persisted — every attempt
was rejected by validation, so `GET /api/settings/github-pat` continued to
report "No GitHub token saved yet." throughout and after.

## Conditions

- **Tier:** qa-admin (enterprise); not tier-specific — the same `GithubPATRequest`
  validator applies to every account.
- **Entry path:** cold nav directly to `/handoff/settings` in every cycle.
- **Trigger:** submitting any PAT value >512 characters via "Save" on
  `/handoff/settings`'s GitHub access token card. Deterministic, not timing
  or session-dependent.

## Expected vs actual

- **Expected:** per the card's own guarantee, a rejected PAT — including one
  rejected purely for length — is never echoed back in any response body,
  and the frontend surfaces a friendly, generic message ("Token is too long
  (max 512 characters)") the same way it already does for the 400
  GitHub-rejection case.
- **Actual:** the full submitted PAT is present verbatim in the `422`
  response body's `input` field, and the frontend renders that entire raw
  JSON blob — value included — as visible page text, violating the
  "never returned by any API" claim on the same card.
