## Summary

INFERRED sibling of [ISS-319](20260828-1804-ISS-319.md), the root cause card for register entry
`BUG-20260828-094120-settings-ai-model-r2`. `PATCH /api/admin/users/{user_id}/tier`
(`update_user_tier`, `backend/app/api/admin.py:210-324`) and
`PATCH /api/admin/users/{user_id}/role` (`update_user_role`, `backend/app/api/admin.py:328-389`)
both follow the identical shape: mutate a single field on the target `User` row -> `db.commit()`
-> `db.refresh(user)` -> build the response via `_to_response(user, db)` (`admin.py:158-166`),
which reads `user.tier` / `user.is_admin` straight off the just-refreshed object.

Not reproduced — filed from the code-shape match alone. Not tested live: this run's standing
rule is never to grant a second admin on `/admin` (it 401s every admin credential and needs a
database write to undo), so no concurrent-write probe was attempted against a real admin
account.

## Why the root cause implies this

Same three preconditions as ISS-319:

- A shared, identity-keyed row (`db.query(User).filter(User.id == user_id).first()`,
  `admin.py:346`, or the caller's own `user` resolved by the admin-auth dependency chain)
  mutated directly from the request's own field, with no version column and no
  `with_for_update()`.
- `user.tier = request.tier` (`admin.py:313`) / `user.is_admin = request.is_admin`
  (`admin.py:376`) -> `db.commit()` (314 / 377) -> `db.refresh(user)` (315 / 378), with no
  re-check in the gap between commit and refresh.
- The response is built by `_to_response(user, db)` (called at `admin.py:324` / `admin.py:389`),
  which reads `user.tier` and `user.is_admin` off the object AFTER refresh — not from
  `request.tier` / `request.is_admin`, the values THIS specific admin call actually asked for.

Two admins (or one admin double-submitting, e.g. a slow network retry) changing the SAME target
user's tier or role concurrently would hit the identical failure: the losing call's `200`
response would report the OTHER call's tier/role instead of the one it itself set, while its own
write silently never reaches the DB. This is a materially more serious instance than ISS-319
because `tier`/`is_admin` are privilege fields — a misleading "granted admin" or "set to
enterprise" response body compounds the underlying lost update with a false confirmation of a
security-relevant change.

## What would confirm or refute it

Fire two concurrent `PATCH /api/admin/users/{id}/tier` (or `/role`) requests with different
values against the SAME target user (a throwaway non-admin test account, never against a real
admin credential per this run's standing constraint) and check whether the losing response's
`tier`/`is_admin` field reports the other call's value instead of its own, and whether the DB
ends up matching neither call's naive "last request sent wins" expectation — the same
non-deterministic "losing slot varies" signature ISS-319 reproduced 3/3.

## Suggested fix (same shape as ISS-319)

Build the response's `tier` / `is_admin` fields from `request.tier` / `request.is_admin` (the
value this call itself validated and just committed), not from the post-`db.refresh()` `user`
object — mirrors whatever fix lands for `update_preferences`.
