## What happened

`TestSignatureIntegrity::test_tampered_signature_is_rejected` failed
intermittently with `DID NOT RAISE CognitoVerificationError`. Measured: 1 failure
in 5 consecutive runs, then 8/8 green after the fix.

This is the test that proves a forged JWT signature is refused, so an intermittent
pass is the bad direction — the guard was silently not guarding on some runs.

## Root cause

The fixture flipped the LAST character of the signature:

```python
forged = f"{header}.{payload}.{signature[:-1]}{'A' if signature[-1] != 'A' else 'B'}"
```

base64url packs 6 bits per character. A 256-byte RSA signature is 2048 bits and
needs 343 characters = 2058 bits — 10 bits of the tail are padding that decode to
nothing. So flipping the final character can leave the DECODED signature bytes
byte-identical, in which case the token is not forged at all and verification
correctly succeeds. `make_token` mints a fresh signature per run, which is why it
came and went rather than failing outright.

## The fix

Tamper a middle character, which always lands on real signature bytes:

```python
mid = len(signature) // 2
flipped = "A" if signature[mid] != "A" else "B"
forged = f"{header}.{payload}.{signature[:mid]}{flipped}{signature[mid + 1:]}"
```

## How it surfaced

It did NOT appear in the first full-suite sweep — that run recorded
`26 passed`. It appeared only in the confirmation sweep afterwards, which is
exactly the shape of a flake and is why it was initially suspected to be a
regression from this session's `HTTPBearer` change ([FIX-311](20260826-0124-FIX-311.md)).
Running the single test five times settled it: 4 passed, 1 failed, with
`app/core/cognito.py` and the test file both untouched in the working tree.
