## What was wrong

Loading `/runs/940ca699-b21b-4666-8e44-3370a08a4561/workspace` — a run whose server status is
`diverted`, with `output: null` and `deliverable_filename: null` — showed the "Workspace
expired" empty state with the body copy "Run workspaces are cleared after a retention period.
The deliverable is still on the Preview and Files tabs — only the raw working files are gone."
No deliverable was ever produced: the Preview tab shows the empty placeholder, the Files tab
lists only agent intermediates plus the run input, and "Download the deliverable" is disabled.
The message therefore told a user who had not yet checked those tabs that output existed which
never did. BUG-20260828-090219-runs-diverted, 3/3 cold starts across two independent runs.

## Root cause

`frontend/src/components/results/SandboxTab.tsx:1044-1051` — the `if (expired)` branch
hardcoded the deliverable sentence with no check on the run's deliverable or status. The deeper
cause, per [ISS-586](20260829-0258-ISS-586.md): `SandboxTabProps` (`:842-849`) was never GIVEN
such a signal — it accepted only `runId` and `agentNameById`, and its sole expiry input,
`res.expired` (`:915`), is a directory-existence flag on the backend
(`backend/app/api/run_files.py:534`, `expired = not sandbox.root.is_dir()`) that is
status-agnostic by construction. So the branch could not distinguish a completed run whose
deliverable is genuinely still on Preview/Files from a diverted / failed / cancelled / degraded
run that never produced one — the same false claim reaches every terminal, deliverable-less run
once its workspace passes `RUN_DIR_TTL_HOURS` (`backend/app/core/config.py:308-311`), not only
a diverted one.

Blast radius re-grepped before editing (`grep -rn "<SandboxTab" --include="*.tsx" frontend/src`):
exactly one production caller, `frontend/src/components/preview/PreviewPanel.tsx:1406` — the
cards still held, and no line numbers had drifted.

## What changed and why there

`frontend/src/components/results/SandboxTab.tsx` — `SandboxTabProps` gains an optional
`hasDeliverable?: boolean`, and the `expired` branch renders the retention sentence
unconditionally with the deliverable clause appended only when that prop is true:

```tsx
Run workspaces are cleared after a retention period.
{hasDeliverable &&
  " The deliverable is still on the Preview and Files tabs — only the raw working files are gone."}
```

This is the single point every state routes through — the component has one `expired` branch, so
one guard covers diverted (ISS-356) and every other no-deliverable terminal status (ISS-586)
without a status literal anywhere in the component. The claim is **opt-in**: absent or false, the
copy simply does not mention a deliverable. A missing prop can then never produce a false
statement, and the transient window on a cold `/workspace` load — where a completed run's output
has not resolved yet — under-claims instead of over-claiming.

`frontend/src/components/preview/PreviewPanel.tsx:1406` — the one caller passes
`hasDeliverable={hasContent}`, the boolean it already computes at `:690` for exactly this
question (the signal [FIX-357](20260828-2210-FIX-357.md) threads into the other terminal-state
surfaces). Wiring only; no new computation.

**Not changed, and deliberately.** ISS-586 offers the richer alternative of threading
`isDivertedTerminal` / `isCancelledTerminal` / `terminalFailureNoDeliverable` and writing
per-status copy. Skipped, per the same card's own conclusion ("there is no reason to special-case
per-status inside `SandboxTab.tsx` itself"): the branch only ever needs to answer "is there a
deliverable to point at", and four status props would put a status vocabulary into a file-tree
component that has none today. Scenario `S-07-22` in `tests/integration/screens/07-run-detail.feature.md`
("An expired workspace says where the deliverable still is", whose Given includes "the Preview tab
still renders the deliverable") remains satisfied for the run it describes — that scenario's run
has a deliverable, so `hasContent` is true and the copy is unchanged for it. The feature file's
state table at `:114` now describes only the `hasDeliverable` case; not edited here — the screens
specs are the test-writer's surface, and this is noted for 6-verifier rather than silently rewritten.
