## What is suspected

[ISS-404](20260828-2120-ISS-404.md) established the mechanism: this codebase's copy
conflates "this app's own local/break-glass credential path" with "credentials
managed by an external system," when `password_hash` (`backend/app/models/user.py:33`)
is in fact a column on the app's own `User` row for exactly that account type.

`backend/app/api/admin.py:553-564`, inside `reset_user_password`
(`POST /api/admin/users/{user_id}/reset-password`, decorated at admin.py:513-514),
has the identical shape:

```
backend/app/api/admin.py:553-564 (excerpt)
    if user.auth_provider != "cognito":
        # The break-glass account is administered out-of-band from a secret
        # store, by design (plan §5.6). Letting it be reset through the ordinary
        # admin API would put the one credential that must survive a Cognito
        # outage back inside the system that outage would take down.
        raise HTTPException(
            status_code=status.HTTP_409_CONFLICT,
            detail=(
                "This account's password is managed outside the application and "
                "cannot be reset here."
            ),
        )
```

The code comment (553-557) gives the real, legitimate design reason for the REFUSAL
— the break-glass credential must stay changeable independent of a Cognito outage, so
this Cognito-only admin-reset path deliberately does not touch it — but the `detail`
string handed back to the caller asserts something broader and false: that the
password is managed *outside the application*. It is not; `POST
/api/auth/change-password`'s `"local"` branch (`auth.py:1254-1269`, cited in ISS-404)
changes this exact same account's password entirely inside this application's own
database. The refusal is correct by design; the wording that explains it is wrong,
for the same reason ISS-404's Security-tab copy is wrong.

## Condition

An authenticated admin calls `POST /api/admin/users/{user_id}/reset-password` where
the target `user.auth_provider != "cognito"` (i.e. the break-glass/local account).

## Expected vs actual

- **Expected:** the 409 explains the actual constraint — this Cognito-admin-reset
  action cannot act on a break-glass account; use the account's local
  self-service change-password path (or an out-of-band runbook) instead.
- **Actual:** the 409 `detail` says *"This account's password is managed outside the
  application and cannot be reset here"* — the same false external-management claim
  as [ISS-404](20260828-2120-ISS-404.md), for the same reason: `auth_provider !=
  "cognito"` only ever means break-glass/local in this codebase today, and that
  account's credential lives inside the application, not outside it.

## Why the root cause implies this

Grepping `"managed outside"` across `frontend/src` and `backend/app`
([ISS-404](20260828-2120-ISS-404.md)'s blast-radius check) returns exactly two hits;
this is the second. Both are static strings gated on the same condition
(`auth_provider != "cognito"` / `!status.supported`, which is driven by the same
field) and both describe it the same wrong way. This is "another caller with the same
flaw," not a coincidence of wording.

**Reachability differs from ISS-404, which is why this is filed separately rather
than folded into it:** `grep -rln "adminResetUserPassword\|reset-password"
frontend/src` finds only the wrapper's own definition
(`frontend/src/lib/api.ts:1459-1473`) — no component in `/admin` or anywhere else
calls it. The endpoint is live and callable (direct API use, a test, or a future "Reset
Password" button would all reach it), but today no UI path surfaces this 409 to a
user. Confirmed via grep; not exercised end-to-end.

**Marked INFERRED:** the code shape and the false claim are read and confirmed
verbatim (`admin.py:558-564`); what has NOT been done is an actual HTTP call
reproducing the 409 response body. What would confirm it: sign in as an admin, `POST
/api/admin/users/{break-glass-user-id}/reset-password` with a valid new password, and
read the `detail` field of the resulting 409 response.
