## What is suspected

[ISS-606](20260829-1412-ISS-606.md) root-caused the Steps tab / FilesTab agent-outputs symptom
(`BUG-20260829-135100-runs-id-versions` in `bug-hunter/ledger.md`) to `PreviewPanel.tsx` never
computing a version-aware override for `agents`/`pipelineState`/`agentOutputs`, unlike the
`effUserStoryContent`/`effPptContent`/`effPrototypeContent` it already computes for the
deliverable content (`PreviewPanel.tsx:656-658`). Reading the adjacent Audit tab mount
(`PreviewPanel.tsx:1464-1468`) shows a related but structurally different instance of the same
class of bug:

```
<AuditTab
  hookRuns={pipelineState?.hookRuns}
  workflowRunId={pipelineState?.pipelineRunId}
  isRunning={isStillRunning}
/>
```

`hookRuns` is dead on arrival — `AuditTabProps` declares it (`AuditTab.tsx:51`) but the
component's own destructuring signature never reads it
(`AuditTab.tsx:455`: `export function AuditTab({ workflowRunId, runMeta, isRunning }: AuditTabProps)`),
so that particular prop has no effect either way. `workflowRunId` is the live wire: `AuditTab`
uses it to drive FOUR of its own fetches on mount/change (`AuditTab.tsx:464-478`:
`getRunGateEvents`, `getRunValidationResults`, `getRunExecRuns`, `getRunHookRuns`, all keyed on
`workflowRunId`).

`PreviewPanel.tsx` already computes a version-pin-aware run id for exactly this purpose —
`activeRunId` (line 551: `viewingVersion?.id ?? liveRunId ?? latestId`) — and uses it for
`FilesTab`'s `runId` prop (line 1394) and, via the same `viewingVersion?.id ?? …` precedence,
for `SandboxTab`'s `workspaceRunId` (line 753: `viewingVersion?.id ?? pipelineState?.pipelineRunId
?? activeRunId ?? null`). `AuditTab`'s mount is the one tab that instead reads
`pipelineState?.pipelineRunId` directly, which `viewingVersion`/`pinnedVersion` never touch. So
when a version is pinned, the Audit tab does not merely render stale pre-fetched data (as
Steps/Files-agentOutputs do per ISS-606) — it actively fetches the WRONG run's gate/validation/
exec/hook-run rows, because it is handed the live run's id, not the pinned one.

## Condition

On a `/runs/{id}/versions/{v}/audit` URL for any `v` that is not the live/root run, whether
reached by cold navigation or by a tab click while already pinned.

## Expected vs actual

**Expected:** the Audit tab should fetch and display the PINNED version's own gate events,
validation results, exec runs and hook runs — matching `activeRunId`, the same id `FilesTab`
and `SandboxTab` already use.

**Actual (predicted):** the Audit tab fetches and displays the LIVE/root run's audit trail
regardless of which version is pinned, because `workflowRunId={pipelineState?.pipelineRunId}`
at `PreviewPanel.tsx:1466` never resolves through `viewingVersion`.

## Why the root cause implies this

Same mechanism ISS-606 names — `PreviewPanel.tsx`'s version-pin override
(`viewingVersion`/`overrideActive`/`effUserStoryContent` et al., lines 525-658) covers only the
three deliverable-content props — reached one tab further. The fix ISS-606 implies (compute an
`eff`-prefixed override once in `PreviewPanel` and thread it to every consumer) has to cover
this call site too: either feed `AuditTab`'s `workflowRunId` prop from `activeRunId` directly,
or compute one shared `effRunId` that the Steps/Files/Audit/Workspace mounts all read from the
same place.

**Marked INFERRED**: confirmed entirely by reading `PreviewPanel.tsx:1464-1468`,
`AuditTab.tsx:45-52,455,464-478`, and the `activeRunId`/`workspaceRunId` precedents at
`PreviewPanel.tsx:551,753`. Not independently browser-verified: nobody has cold-navigated to a
pinned-version `/audit` URL this session and compared the rendered rows against
`GET /api/runs/{pinnedId}`. What would settle it: repeat this bug's own reproduction (cold
`page.goto` to `/versions/1/audit` and `/versions/2/audit` on the same two-member family,
`77f74563-...`/`ef86e750-...`) and confirm whether the rendered gate/validation/exec/hook rows
differ between the two loads, or are identical the way Steps content was.
