## What is open

The seven conditional-gate fixtures written for spec 014 are indistinguishable from
product pipelines at the catalog layer:

| surface | state |
|---|---|
| `backend/agents/workflows/ex_A*/workflow.yaml` | `user_launchable: true` — all 7 |
| `backend/app/core/entitlements.py:47-53` | listed in the `enterprise` tier |
| `frontend/src/lib/entitlements.ts:63-69` | listed in the `enterprise` tier |

`ex_A1_loop`, `ex_A2_branch`, `ex_A3_divert`, `ex_A3_b_spanish`, `ex_A3_c_dutch`,
`ex_A4_human_gate`, `ex_A4_human_divert`.

An enterprise-tier user opening the catalog is offered all seven as runnable
workflows. Nothing marks them as fixtures.

## How it got here

Both entitlement entries were added as bug fixes, each correct in isolation:

- The backend comment reads "spec-014 conditional-gates integration: QA found these 5
  were not entitled to any tier despite `user_launchable: true`."
- The frontend comment reads "Launchable, non-beta and entitled on the backend, but
  absent here — so the catalog rendered the cards locked behind an upgrade prompt that
  no tier could satisfy."

Each fix took `user_launchable: true` as the given and closed the gap it created. The
premise itself — that QA fixtures should be user-launchable at all — was never
examined. `test_entitlement_parity` then locks the two sides together, so neither can
now be changed alone.

## Why it is an issue and not a fix

Which way this resolves is a product decision, not a defect with a correct answer:

- **If the fixtures are meant to be demos**, this is working as intended and the card
  closes — but they should probably carry titles and descriptions that say so.
- **If they are QA-only**, the fix is `user_launchable: false` on all seven manifests
  plus removal from BOTH entitlement tables (the parity test forces both), and spec
  014's fixtures need another dispatch route for their tests.

Recorded rather than acted on, per `b24bda25b`'s own framing.
