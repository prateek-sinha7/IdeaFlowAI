# ISS-1009

Sibling of [ISS-898](20261001-2128-ISS-898.md), found by the QA-KB-071 analysis on 2026-10-02. Confidence: CONFIRMED. The mechanism was run on
a scratch copy, not inferred; the repo test file and `page.tsx` were not edited. A validator re-run is still pending.

## Why the root cause implies it

[ISS-898](20261001-2128-ISS-898.md)'s stale anchor `applyTerminalStatus(prev, fullRun.status)` is read five times in the test file, and the
five readers fail in three different ways. `toContain` fails (cases 2 and 3 of the block). `indexOf(...)` followed by
`toBeGreaterThan(-1)` fails (cases 6, 7 and 8). `indexOf(...)` followed by `slice(call, call + 1600)` does not fail at
all (case 5, this card). The bug report's "5 failed | 4 passed" therefore overstates the protection: of the 4 passing
cases in the ISS-126 block only 3 assert anything.

## Condition

Run `frontend/src/app/[...view]/terminalReopenReconcile.source.test.ts` alone, from `frontend/`, with
`./node_modules/.bin/vitest --run <file> --reporter=verbose`. The case is
`does NOT clear reviewGateData — that would erase the historical gate card` (test lines 59-63 at analysis time):

```ts
const call = pageSource.indexOf("applyTerminalStatus(prev, fullRun.status)");
const windowAfter = pageSource.slice(call, call + 1600);
expect(windowAfter).not.toContain("reviewGateData: null");
```

## Expected

With the anchor absent from `page.tsx`, the case fails, like the five cases built on the same anchor. A source lock that
cannot find the code it guards must not pass.

## Actual

The case is green (`✓ ... does NOT clear reviewGateData — that would erase the historical gate card 0ms`) while
`call === -1`. `pageSource.slice(-1, 1599)` on the 250,512-character `page.tsx` has start index `length - 1`, which is past
the end index 1599, so the window is `""`, and `expect("").not.toContain("reviewGateData: null")` is trivially true.
Since `7f9be3d60` (2026-09-22) the ISS-126 rule "a reopened terminal run must not clear `reviewGateData`" has had no
working guard, while the file reported it as green.

## Evidence

- `evidence/qa-kb-071/02-analyze-scratch-ab.out.txt` run 0: the repo file run in place gives `Tests 5 failed | 5 passed (10)`
  with this case marked `✓`. Section 5 of the same file: `indexOf(stale anchor): -1 | window length: 0 | window === "": true`.
- After the [ISS-898](20261001-2128-ISS-898.md) re-anchor the window is real and the case still passes: the 1600 characters after
  `page.tsx:3130` hold one mention of `reviewGateData`, inside a comment, and the next literal `reviewGateData: null` is
  75,416 characters further on (line 4452). So the app is not hiding a defect here. The hole is only in the test.

## Fix direction

Same edit as [ISS-898](20261001-2128-ISS-898.md), same file: add `expect(call).toBeGreaterThan(-1);` between the `indexOf` and the
`slice`. Validated on a scratch copy (run 4a: `Tests 10 passed (10)` with the re-anchor plus this guard). Do not rely on
the re-anchor alone: it makes the case real today but leaves the same hole open for the next drift.

## Resolution — FIX-731 (2026-10-07)

Resolved by [FIX-731](20261007-1908-FIX-731.md). `expect(call).toBeGreaterThan(-1)` now sits between the `indexOf` and
the `slice` (`terminalReopenReconcile.source.test.ts:65`). The meta-lock's ISS-1009 `it.fails` case now fails with
"Expect test to fail", which is the pass signal. The marker is left for the 6-verifier (`evidence/qa-kb-071/fix-05`).
