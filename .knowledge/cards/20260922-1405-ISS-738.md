## What happened (inferred — not yet reproduced, reachability uncertain)

[ISS-695](20260922-0800-ISS-695.md) confirmed that `httpx` calls built with default TLS
verification fail every outbound HTTPS call in this environment (a TLS-intercepting proxy
whose CA sits outside certifi's bundle). `backend/app/core/cognito.py`'s `_fetch_jwks`
(`:109-124`) makes the same kind of call, synchronously:

```python
resp = httpx.get(_jwks_url(), timeout=5.0)
```

(`:114`), with no `verify=` override, to fetch the Cognito user pool's JWKS used to verify
inbound JWT signatures (`_get_signing_key`, `:127+`, caches the result in `_jwks_cache`).

## Why the root cause implies it — and the open question

Same construction pattern (bare `httpx.get`, default `verify=True`) against a public HTTPS
host — the exact shape ISS-695 proved broken for three unrelated hosts in this environment.
**But** this session signed in as `qa-admin@flowinqa.com` successfully against this same
backend, which is hard to reconcile with a broken JWKS fetch if Cognito verification sits on
that login's path. Two readings, neither settled by reading this card's files alone:

- This environment's auth does not actually call `_fetch_jwks` on the login path used here (a
  non-Cognito/local auth provider, or a pre-warmed/cached JWKS from before the proxy was in
  place) — dormant code sharing the defect but not currently exercised, or
- It does call it, and any request needing fresh verification would fail; a successful login
  does not by itself prove a live JWKS fetch succeeded (a cached key or a bypass elsewhere
  could mask it).

## Expected vs actual (expected on reproduction)

- **Expected:** `_fetch_jwks` retrieves the pool's signing keys over HTTPS.
- **Actual (predicted, if this path is live):** `httpx.get` raises `ConnectError` /
  `SSLCertVerificationError` on both retry attempts (`:112-124`), surfacing as
  `CognitoVerificationError(f"JWKS unavailable: {last_exc}")` — an auth failure, not a
  template-upload failure, making this the highest-severity sibling if it is reachable.

## Evidence

- `backend/app/core/cognito.py:114` — `resp = httpx.get(_jwks_url(), timeout=5.0)` (read
  directly; no `verify=` argument)
- `backend/app/core/cognito.py:109-124` — `_fetch_jwks`'s bounded 2-attempt retry, wrapping
  the raw exception into `CognitoVerificationError`
- [ISS-695](20260922-0800-ISS-695.md)'s direct-interpreter reproduction is the proof this
  construction pattern fails in this environment when it IS reached

## What would settle it

Confirm which auth provider this backend is actually configured against and whether
`_fetch_jwks` has been called successfully (or at all) since this environment's proxy was
introduced — e.g. a "JWKS fetch attempt" log line or a cache-hit trace. Out of scope for this
analysis pass (auth configuration, not template upload).

## Test (test-writer pass, 2026-09-22) — refuted on two independent grounds

1. **Reachability question this card itself raised, settled:** `backend/app/core/config.py`
   `AUTH_PROVIDER` defaults to `"local"` (`config.py:419`) and no `COGNITO_*` env var is set
   in this environment (`backend/.env` has none), so `_fetch_jwks` is never reached by this
   environment's login path — the "dormant code" reading in this card's own "Why the root
   cause implies it" section is the correct one here, not the "live and would fail" reading.
2. **Even called directly, it does not fail on TLS:** monkeypatched a real region/pool shape
   (`COGNITO_REGION="us-east-1"`, `COGNITO_USER_POOL_ID="us-east-1_fakepool00"`) and called
   `_fetch_jwks()` directly:
   ```
   CognitoVerificationError (handled): JWKS unavailable: Client error '404 Not Found' for
   url 'https://cognito-idp.us-east-1.amazonaws.com/us-east-1_fakepool00/.well-known/jwks.json'
   ```
   A clean 404 (fake pool id), not an SSL/TLS error — `cognito-idp.us-east-1.amazonaws.com`
   is reachable cleanly through this environment's proxy, same pattern as
   [ISS-750](20260922-1403-ISS-750.md)/[ISS-751](20260922-1404-ISS-751.md)'s `api.github.com`
   (see [ISS-695](20260922-0800-ISS-695.md)'s "Test" section for the host comparison). No
   test written; there is no defect here to assert against today, on either ground.

## Fix (fixer pass, 2026-09-22) — [FIX-607](20260922-1814-FIX-607.md)

Fixed with the root card, not separately: `_fetch_jwks` (`backend/app/core/cognito.py:114`) now passes
`verify=default_ssl_context()` (`backend/app/core/http_client.py`), the same
shared context ISS-695's own call site uses. One keyword argument per call
site; the context can only widen the trusted-CA set, never narrow it.

Still `verification.status: not_reproducible` — the test-writer's refutation
stands (this environment's proxy does not intercept `cognito-idp.us-east-1.amazonaws.com`, so
the failure never surfaced here). The call site is fixed anyway because the
mechanism is identical and the exemption is a property of this proxy's
allowlist, not of the code.
