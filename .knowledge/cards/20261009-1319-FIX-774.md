## What was wrong

The root causes are on the cards and are not re-derived here. botocore raises `ClientError` when Cognito answered with an error and
`BotoCoreError` when the call never completed. An expired SSO session is a `BotoCoreError` (`TokenRetrievalError`), raised while signing,
before any request. The two families are disjoint, and every provider-failure handler modelled only `ClientError`: ten in `auth.py`, and
nine clauses plus one `isinstance` in `cognito_admin.py`. The escape reached Starlette's outermost 500, built outside `CORSMiddleware`,
so the browser reported a CORS block and the login page showed its generic string. `/login` also skipped its `LOGIN_FAILURE` event, which
feeds the `auth_login_failure` alarm. Two admin routes, `POST .../disable` and `DELETE /users/{id}`, never translated even a
`ProviderUnavailableError`.

## What changed, and why there

1. **Two shared symbols in the adapter** (`cognito.py:254-271`), the one module that knows both families:
   `PROVIDER_ERRORS = (ClientError, BotoCoreError)`, and `provider_error_code(exc)`, which returns the service code of a `ClientError` and
   otherwise the exception's class name. `botocore.exceptions` is imported at module top (`:33`). That needs no credentials; `boto3` itself
   stays lazy in `_client()`.
2. **The ten `auth.py` handlers** (`:343` login, `:492` login/challenge, `:669` refresh, `:803` totp/associate, `:849` totp/verify, `:947`
   email/enable, `:1014` email/disable, `:1084` forgot-password, `:1129` forgot-password/confirm, `:1202` change-password). In each,
   `except ClientError` plus the `exc.response` read becomes `except cognito.PROVIDER_ERRORS` plus `cognito.provider_error_code(exc)`. No
   branch changed. A class-name code matches none of the special codes, so it takes the branch each author wrote for "any other failure".
   `/login` therefore emits `LOGIN_FAILURE` with `reason="provider_error:TokenRetrievalError"` and answers 503 `Authentication service
   unavailable`, with no new `AuthEvent` member. `/forgot-password` returns its generic 202 (ISS-1149).
3. **The lifecycle layer** (`cognito_admin.py:160, :211, :242, :332, :370, :421, :455, :501, :606, :686`) gets the same substitution, so
   every site raises `ProviderUnavailableError` with `code=<class name>`. `is_last_admin`'s first read degrades to the local projection, as
   documented. `try_delete_pool_user` returns the class name as its retry code, so the delete route queues its `PendingCognitoDeletion`
   row. At `:370` the compensation branch tests `isinstance(exc, cognito.PROVIDER_ERRORS)`. I corrected the comment above it, at `:368`,
   because it named the old check.
4. **The two bare admin routes** (`admin.py:600-603` disable, `:715-718` delete) get the `try / except Exception: _raise_for(exc)` the
   other five routes already have. The delete wrapper covers only `cognito_admin.delete_user`, not the local transaction or the retry-queue
   write after it. `api/admin.py` still imports no botocore.
5. **The safety net** (`main.py:560-580`): `@app.exception_handler(BotoCoreError)` returns a JSON 503 and logs the traceback (`exc_info`),
   because a handled exception no longer reaches Starlette's own error log. It is keyed on the class, not on `Exception` or `500`, so Starlette
   serves it inside `CORSMiddleware`.

### Where this differs from the cards, and why

- **Per-site translation, not the `_client()` proxy.** ISS-1144 left the choice to the fixer. The test-writer's test patches
  `cognito.admin_initiate_auth` itself, which bypasses any wrapper inside `_client()`. Under the proxy, the `provider_error:TokenRetrievalError`
  event the test asserts would never fire. The proxy would also have to wrap the lazy paginators, and would present "could not reach the
  service" as a `ClientError`.
- **Two `ClientError` clauses stay.** `cognito_admin.py:130` (`_retry_on_throttle`) already re-raises anything that is not a throttle
  `ClientError`, as ISS-1148 says. `auth.py:578` (`_reconcile_status_on_refresh_rejection`) is followed by an `except Exception`, and
  ISS-1144 lists it as already correct.
- **Safety-net wording.** ISS-1150 left the message to the fixer. The handler covers every route, not only auth, so it says `A cloud
  service is unavailable. Please try again.` The auth routes keep `Authentication service unavailable` from their own handlers.
- **Decorator form.** The card names `app.add_exception_handler`. I used `@app.exception_handler`, which is equivalent and matches the
  file's existing `RequestValidationError` handler.
- **No new test files.** ISS-1145 to ISS-1150 are `manual` verification cards, and the test-writer wrote only ISS-1144's file. I verified
  the siblings by re-running the analyzer's own harnesses, `04` and `08`, after the change, plus one supplemental probe for the cases those
  two do not reach (below).

## Behaviour changes a caller can see

- When the backend's AWS session is expired or unreachable, every Cognito-backed route answers 503 with CORS headers and a readable
  `detail`. Before, it was a 500 the browser blocked. The login page shows `Authentication service unavailable` instead of `An unexpected
  error occurred`.
- `LOGIN_FAILURE` with `reason="provider_error:<botocore class>"` is emitted again during such an outage, so the `auth_login_failure`
  alarm can see it.
- `POST /api/admin/users/{id}/disable` and `DELETE /api/admin/users/{id}` answer 503 for any provider failure, including a plain
  `ClientError`, instead of 500.
- A delete whose final `AdminDeleteUser` hits a `BotoCoreError` now writes its `PendingCognitoDeletion` row and answers 202.
- Any other untranslated `BotoCoreError` on any route is a 503 `A cloud service is unavailable. Please try again.`, logged with its
  traceback. Valid credentials: no change.

## What this leaves open (recorded on the cards, not fixed here)

- [ISS-1146](20261009-0935-ISS-1146.md)'s frontend half. `refreshAccessToken` treats the new 503 like a 401, so during an outage a session
  still ends at its true expiry ([FIX-481](20260917-0131-FIX-481.md)'s design). The card puts this out of scope.
- [ISS-1148](20261009-0935-ISS-1148.md)'s partial states. If the outage starts between `AdminCreateUser` and `AdminAddUserToGroup` and
  persists, `invite_user`'s compensating delete cannot reach the pool either. The half-created pool user remains, now behind a typed 503
  rather than a raw 500, as with a `ClientError` today. The cutoff-first order in `change_tier` and `change_role` is by design.
- [ISS-1149](20261009-0935-ISS-1149.md)'s "Not covered here". `_client()` builds the boto3 client with botocore's default timeouts, so a
  blackholed endpoint can outlast the frontend's 30 s abort.
- [ISS-1144](20261009-0725-ISS-1144.md)'s "Adjacent". `app/agents/llm_errors.py::map_exception` does not list `TokenRetrievalError`, so a
  chat call over an expired session offers a retry.
- `_raise_for`'s docstring in `admin.py` says "(currently six) call sites". There are now seven; there were five before this change.
- Probe `04`, section E, does not patch `list_users_in_group`. After this fix, `is_last_admin` degrades past its first read and that probe
  makes one real, read-only `ListUsersInGroup` call (the `Loading cached SSO token` line in `fix-02`). `fix-04` patches both reads.
