# FIX-682

Register entry **QA-KB-043** (root `LEDGER.md` / `BUGS.md`). The root card is [ISS-105](20260812-1312-ISS-105.md)
and the sibling is [ISS-872](20261001-2110-ISS-872.md). Root causes come from those cards and were not re-derived;
the code was re-read at the cited lines before editing. Line numbers are post-change unless marked.

## What was wrong

- [ISS-105](20260812-1312-ISS-105.md): there was no runtime defect, only a missing test. Step 2 of
  `shutdown_run_infrastructure` (`backend/app/api/run_shutdown.py:146-154`) iterates
  `list(_PIPELINE_QUEUES.keys())` and has no `await` before each guarded `put_nowait`, so it tolerates concurrent
  teardown by construction. Nothing asserted that while a driver finishes (`_cleanup_pipeline`) or a subscriber
  detaches (`_unsubscribe`) during shutdown's drain.
- [ISS-872](20261001-2110-ISS-872.md): `runs_left_for_boot_restore` was
  `0 if settings.SHUTDOWN_STOP_RUNS else summary["runs_in_flight"]` (`:222-224` pre-change). `runs_in_flight` is
  `len(_PIPELINE_TASKS)` sampled at entry (`:81`), before up to about 20 s of awaits (the Concierge drain, the pump
  drain and the pool close). A driver that finishes in that window pops its own entry (`_cleanup_pipeline`,
  `backend/app/api/run_engine.py:121`), but it was still reported as left for the next boot. The field is
  log-only (`backend/app/main.py:419-420`).

## What changed, and why there

1. **ISS-105, test only.** The fix is the test-writer's regression lock in
   `backend/tests/unit/app/test_run_shutdown.py`. `_open_step1_window` parks shutdown in step 1 with a pending task in
   `_CONCIERGE_STREAM_TASKS`, which is the only `await` before step 2. `TestShutdownSnapshotUnderConcurrentTeardown`
   mutates the registries in that window: two `_cleanup_pipeline` calls, one `_get_or_create_queue`, and one
   `_unsubscribe` after 0 or 1 loop turns. It then repeats the mutations as continuous churn for the whole call. The
   ISS-105 Test section records the mutation proof: an `await asyncio.sleep(0)` injected before step 2's
   `put_nowait` fails the churn test. The optional comment above step 2 was declined, per ISS-105 analysis item 4.
2. **ISS-872, `run_shutdown.py:222-232`.** The field is now counted at return:

   ```python
   summary["runs_left_for_boot_restore"] = (
       0
       if settings.SHUTDOWN_STOP_RUNS
       else sum(
           1
           for t in _PIPELINE_TASKS.values()
           if not (isinstance(t, asyncio.Task) and t.done())
       )
   )
   ```

   A two-line comment above it says why. This is the field's only producer, and its only consumer is the shutdown
   log line. As the card asks, `runs_in_flight` stays the entry count and the `SHUTDOWN_STOP_RUNS` branch is
   unchanged.

   The card's example used `getattr(t, "done", lambda: False)()`. I used the `isinstance(task, asyncio.Task)` test
   that `stop_run_driver` already uses in this file (`:333`), for two reasons. It cannot raise, and the function's
   contract is "Never raises". It also keeps the card's rule that anything not provably finished counts as left. On
   real entries the two forms agree: every assignment into `_PIPELINE_TASKS` stores an `asyncio.create_task(...)`
   result (`run_commands.py:753, 1766, 2045, 3226, 5668`, and `run_engine.py:535` via `_register_resume_task`, whose
   two engine call sites pass `create_task` results). No import was added, since `asyncio` and `_PIPELINE_TASKS` are
   already in scope.

Known limit: an entry whose task is `done()` but was never popped (the stale case `_is_run_live` documents,
`run_engine.py:150-165`) is now not counted. On the paths read here, such a run is already terminal.
`_drive_user_resume` flips any `Exception` to `failed` (`run_commands.py:793-795`), and `stop_run_driver` reconciles
a cancelled driver. A stale engine-side resume task whose row is still non-terminal would be under-counted by one.
That case was not observed and not chased.

Line shift: every line of `run_shutdown.py` below `:221` moved down 8. `_drain_then_cancel` is now at `:236`,
`stop_pipeline_drivers` at `:276` and `stop_run_driver` at `:306`. Older cards that cite those regions by line,
ISS-105's blast radius among them, now read 8 low. No assertion depends on those numbers: the run_shutdown citations
in `test_run_shutdown_stale_citations.py` and `test_shutdown_reachability.py` are docstring prose.

## Not fixed

[ISS-896](20261001-2127-ISS-896.md) is open. Running the shutdown test callers that ISS-105 names showed that
`test_shutdown_reachability.py::test_sigterm_reaches_the_lifespan_shutdown_half_while_a_stream_is_live` dies on the
unit I/O guard (`UnitIsolationError`, `tests/unit/conftest.py:129`) at its own `subprocess.Popen`, before any
shutdown code runs. That is unrelated to this change.
