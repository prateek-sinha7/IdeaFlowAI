# ISS-924

## Source

INFERRED sibling of [ISS-410](20260828-2344-ISS-410.md), derived while analyzing QA-KB-018
(analyze phase, 2026-10-01), and the INVERSE case of it. ISS-410's root cause is that page.tsx's
cold-mount seed fetches have no state for "failed, but not a dead id". On the canvas route the
blank initial state is an interactive composer, so the symptom is a live Save. On the two routes
below the blank initial state is a `return null`, so the symptom is a page that never appears.

## What is suspected

Two more page.tsx seed effects end exactly like the canvas one, and their render gates wait on
state that only the success path or the 403/404 branch ever sets.

`/workflows/{id}` (read view): the catch logs at `page.tsx:3837` and handles only 401 and 403/404
(`setWorkflowDetailFailed(true)`, `:3857`). The gate is

```ts
// frontend/src/app/[...view]/page.tsx:4077-4085
if (parsedView.screen === "workflow") {
  if (workflowDetailFailed) { notFound(); }
  if (!workflowDetail) { return null; }
  return <WorkflowDetailView workflow={workflowDetail} />;
}
```

`/workflows/{id}/run`: the catch logs at `:4006` and handles only 401 and 403/404
(`setWorkflowRunFailed(true)`, `:4025`). The gate is

```ts
// frontend/src/app/[...view]/page.tsx:4120-4126
if (parsedView.screen === "workflow-run" && !workflowRunMainView && !workflowRunFailed) {
  return null;
}
```

A 5xx, timeout or network failure sets neither `workflowDetail` / `workflowRunMainView` nor the
failed flags, so page.tsx returns `null` on every later render: a blank page with no message and
no retry until the user reloads. The code names the choice ("falls through to the log-and-continue
behavior", `page.tsx:3847-3854` and `:4017-4023`) but nothing continues to anything: no render path
exists for it.

[ISS-380](20260828-2209-ISS-380.md) (resolved) narrowed these catches on the stated expectation that
"a 5xx or network failure logs and lets the panel retry or show a transient-error state, same as
workflowEditAccessDenied/workflowDetailFailed already do" (its Expected section). Read against the
current tree that state does not exist for any of the cold-mount seeds: there is no retry in
`getWorkflowDetail` / `fetchWithAuth` (`frontend/src/lib/api.ts:2415-2440`, `:536-566`) nor in the
axios client behind `userWorkflowsApi` (`frontend/src/store/api/http.ts:17-54`).

## Condition

Open `/workflows/<existing-id>` or `/workflows/<existing-id>/run` for a workflow the user owns at a
moment `GET /api/user-workflows/<id>` fails for any reason other than 401/403/404.

## Expected vs actual

**Expected:** a transient failure shows an explicit error with a retry or reload affordance, the
way `IdeaInputPage` already does for its own fetch (`loadError`, `IdeaInputPage.tsx:1114`, copy
"Failed to load this workflow. Reload the page to retry." at `:1996-2001`).

**Actual (predicted):** an empty white page under a valid URL. No console error beyond the
`console.error` line, nothing on screen.

## Why the root cause implies this

Same absent state, opposite consumer. ISS-410's fix (a seeded-ness gate inside ComposerPage) does
not touch these routes, and neither does ISS-410's sibling for `/edit`. If page.tsx ever grows a
single seed status (loading / failed / ready) for its cold-mount effects, this is the consumer that
turns "failed" into something visible. Fixing only the 403/404 narrowing, as ISS-273 and ISS-380
did, is what leaves this state without a render path.

**Marked INFERRED**: not reproduced; confirmed only by reading the lines cited above. What would
confirm it: abort `GET /api/user-workflows/<id>` with `page.route`, open
`/workflows/<id>/run` and `/workflows/<id>`, and check that the body stays empty after load. What
would refute it: any other render path that releases the `null`, such as a timeout fallback, which
this read did not find (`page.tsx:4077-4085` and `:4120-4126` are the only returns on these
screens before DashboardLayout).

## Not closed by FIX-696 (QA-KB-018 fix phase, 2026-10-01)

Still open. [FIX-698](20261001-2237-FIX-698.md) is a ComposerPage Save gate and does not touch these two routes.
The cure here is a failure render path (error plus reload or retry) in page.tsx, which is the error UI QA-KB-018's
agreed scope explicitly excluded ("Do not retry or add error UI in page.tsx"), so it was left for its own fix.
