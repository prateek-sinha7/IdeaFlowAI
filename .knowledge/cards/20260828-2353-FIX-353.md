## What was wrong

On a completed run's Steps tab the "TOKEN USAGE" footer read
`3.1M total · 141.3K input · 192.8K output` — its own two visible parts summed to 334.1K
against a stated 3.1M total. `GET /api/runs/{id}` returns `total_input_tokens: 2,915,058`,
`total_output_tokens: 190,220`, `total_tokens: 3,105,278`, which do reconcile; only the
rendered "input" label was wrong. Reproduced 3/3 from a cold navigation
([ISS-278](20260828-1700-ISS-278.md), `BUG-20260828-012500-runs-id-steps`).

## Root cause

`frontend/src/components/workflow/TokenUsageSummary.tsx:56` (pre-change) rendered
`formatTokens(hasCaching ? uncachedInput : input)` as the unqualified `input` label, where
`uncachedInput` (`:32`) is `input - cacheRead - cacheWrite` — the newly-billed prompt tokens
only. The `total` beside it (`:26`) is `totalTokens`, i.e. derived from the FULL gross input.
So the moment a run used prompt caching (`hasCaching`, `:33` — true here with
`cacheRead=2,443,873`, `cacheWrite=332,250`) the two figures were drawn from different bases
and could not add up. The element's own `title` (`:54`) already carried the correct gross
figure, which is why the tooltip said 2.9M while the label said 141.3K.

`frontend/src/components/chat/ChatTokenWidget.tsx:93-124` carried an independently
hand-rolled copy of the identical formula (its docstring says it "Mirrors `TokenUsageSummary`"):
same `uncachedInput`, same `hasCaching` gate, same "gross value hidden in the `title`, uncached
value as the visible `in` label" shape ([ISS-385](20260828-2225-ISS-385.md)). Not reachable in
the UI today — `RunChatLane.tsx:67-71` imports only `composedContextUsage` /
`COMPACT_THRESHOLD_PCT` / `ComposedContextTelemetry` from that module, never the component —
but it would have reproduced the same defect the day the widget is mounted.

## What changed and why there

**`TokenUsageSummary.tsx`** — the label is now `{formatTokens(input)} input`, the same gross
value `total` is derived from, so `input + output` reconstructs the stated total. The `title`
is untouched (`Total context sent: 2.9M (2.4M cached)`) and still carries the cached share.
The `uncachedInput` local, orphaned by that change, is deleted; `hasCaching` stays because the
tooltip is gated on it. The header comment that described the removed branch is rewritten.

**`ChatTokenWidget.tsx`** — the `in` segment is now unconditional and renders the same gross
`input`; only the amber `⚡ N cached (P%)` segment stays behind `hasCaching`. `uncachedInput`
and the duplicated `title` are deleted with it. Fixed here rather than left dormant because
this is the second, independent copy of the exact formula the bug came from — patching only
the reported file would leave the identical defect queued behind the widget's first mount.

Deliberately NOT done: the shared `{total, uncachedInput, cacheRead, cacheWrite, hasCaching}`
helper both cards proposed. After the fix there is no shared arithmetic left to extract — the
subtraction is gone from both files and what remains in each is `?? 0` coalescing, so a new
module would be an abstraction over nothing. The goal the proposal existed to serve (no
dormant duplicate left to reintroduce the bug) is met by fixing both call sites in this pass.

`AnalyticsPage.tsx:224-232,604-619` — the third implementation of the same arithmetic — is
untouched: it already labels the value "New Input" inside a 4-segment breakdown that
reconciles to the total, and is the precedent this fix follows.
