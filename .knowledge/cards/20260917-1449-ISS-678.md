## Origin

Split out of [ISS-671](20260917-1345-ISS-671.md) when [FIX-522](20260917-1449-FIX-522.md) resolved
it. ISS-671 called this "a secondary gap worth closing too ... a robustness improvement, not
required for this fix". FIX-522 did not change it, so it is recorded here as an open item.

## What is wrong

- `RunSandbox.__init__` defaults `has_git=True` (`backend/app/agents/sandbox.py:546`).
- Every read-path API caller builds `RunSandbox(user_id, chain_root_id, runs_root=...)` with no
  `has_git=` argument: `backend/app/api/run_files.py:663, 698, 792, 889`, and the restore endpoint
  at `backend/app/api/runs.py:2427`.
- `RunSandbox.list_tags` (`sandbox.py:896`) and the other git-backed delegations gate only on the
  flag, never on `(self.root / ".git").is_dir()`.

ISS-671 counted 87 of 103 local `runs/` directories with no `.git`. Every API-built sandbox over
one of them is still treated as a git repo.

## Impact after FIX-522

With the ceiling, a git call on such a sandbox now fails closed ("not a git repository") rather
than reaching the enclosing checkout, so there is no data exposure and no host write. What is left
is confined to the API construction sites listed above:

- git subprocesses are spawned that cannot succeed;
- a `RunSandbox.commit_all` reached from them (restore, `runs.py:2443` onward) raises a raw
  `CalledProcessError` from `git add -A` rather than taking its documented "sandbox is not a git
  repo" warning branch.

The engine's own run path is NOT affected. At sandbox open, `engine.py:3983-3999` calls
`git_init_sandbox` and flips `sandbox.has_git = False` if init fails, so fan-out isolation (keyed on
`has_git`) sees an accurate flag there.

Not reproduced; traced by reading.

## Disposition

Open, low severity. Derive `has_git` from the real `.git` at construction, or check it at the
delegation seam, then add a test.
