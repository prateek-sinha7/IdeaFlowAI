# ADR-0001: Terminal frames mark the connection non-reconnecting

## Context and Problem Statement

`useRunStream` reconnects when the SSE stream closes, which is right for a dropped
live stream and wrong when the backend closed the stream *on purpose*. Three
separate defects were the same bug wearing different clothes:

- **BUG-015** — a completed run, still being viewed, reconnected forever.
- **FIX-121 / FIX-122** — clicking Stop produced a yellow "Reconnecting…" banner and
  made the Stop button look dead, because the stream closed right after
  `pipeline_cancelled` arrived.

The distinguishing signal is *intent*: did this stream end because the work is over,
or because the transport failed? Only the frames carry that.

The failure is a **race, not a missing case**. FIX-121 released the sticky stream
focus with `detachRunRef.current?.(cancelledId)` from the `pipeline_cancelled`
branch. But that schedules React state work, and React state updates are
asynchronous, while the reader loop is not:

1. `pipeline_cancelled` dispatched inside `useRunStream`'s async reader loop
2. `onMessage` → `setLiveRunIds` **scheduled**, not applied
3. loop continues immediately: `await reader.read()` → backend closes → `{done: true}`
4. `stoppedRef.current` still `false` — the unmount has not happened
5. `sawNonLiveAttachRef.current` still `false`
6. → `scheduleReconnect()` → `phase = "reconnecting"` → yellow banner

Anything that has to survive to the next `await` cannot live in React state.

## Considered Options

1. **Set the non-reconnect ref synchronously in the frame dispatcher.**
2. **Unmount the connection component on cancel** (FIX-121's `detachRun`).
3. **Suppress the banner in the UI** while a cancel is in flight.

## Decision Outcome

**Option 1.** `sawNonLiveAttachRef.current = true` is set directly inside
`dispatchBlock` when `pipeline_cancelled` or `pipeline_failed` arrives. That runs in
the same microtask as the frame, so it is guaranteed to land before the next
`await reader.read()`. When the close follows, the ref is already `true` and the hook
settles to `disconnected` quietly.

This is the same mechanism `stream_attached{live:false}` already used for BUG-015.
Terminal events are the same category: intentional ends, after which the backend
closes the stream. `pipeline_failed` is included for symmetry — a hard failure is
also an intentional end.

Option 2 is kept as **additive insurance only** — it still guarantees the component
eventually unmounts — but it is explicitly not the mechanism. Option 3 was rejected:
it hides the symptom and leaves the reconnect loop running underneath.

### Consequences

- **Positive** — one rule now covers every intentional stream end; the fix cannot
  race the render cycle; the mechanism matches the existing BUG-015 precedent.
- **Negative** — the terminal-frame list is maintained by hand. A new terminal frame
  type that is not added to that branch reintroduces the banner, and the symptom will
  look like a UI bug rather than a dispatcher omission.
- **Neutral** — `detachRun` stays, so there are two overlapping mechanisms. Anyone
  removing the "redundant" one must remove the *right* one.

### Confirmation

`frontend/src/hooks/useRunStream.test.ts` covers the BUG-015 half:
A1 asserts a non-live attach that closes settles `disconnected`; A2 is the control,
asserting a genuine live drop still reconnects.

**Coverage gap — the cancel path this ADR was written for is not yet tested.** No
case drives `pipeline_cancelled` or `pipeline_failed` through `dispatchBlock` and
then closes the stream. The regression FIX-122 fixed would not be caught today.
Closing that gap means one test per terminal frame type, mirroring A1.
