## What was wrong

Two backlog runs on the same uploaded prototype (`prototype__1_.html`) produced a
first screen that the reader could not read. Run `3cbc1b38` wrote this in
`file-synthesis/prototype-1/shards/prototype-1-s01/gaps.md`: "Page 01 image-1
screenshot too small to read". The same 189 px wide image appears in runs
`feaa1a06` and `7372962a`. Run `f755b22b` had the opposite failure earlier. Its
first screen was a 4,105,323-byte PNG (5,473,764 characters as base64), and the
provider rejected the request on the next model call.

## Root cause (at base 09ec5146c)

- `backend/app/agents/tools/html_extract.py:516` `_fit_screenshot` scaled every
  screen element screenshot to a 7,900 px longest side and 3.5 MB. A 1008 x 35,113 px
  element therefore became 188 x 6,553 px. A tall screen cannot be both accepted by
  the provider and readable at one picture.
- `html_extract.py:541` set the side-cap scale and `html_extract.py:546` then
  multiplied a byte factor onto it. The scale was applied twice, so each side came out
  about 17% smaller than the cap required. Workflow evidence: a 4000 x 40 test
  image with a 200,000-byte cap came out about 1162 px wide where the side cap
  alone allows 2000 px.
- `html_extract.py:234` reused any extract folder whose `source_sha256` matched.
  Folders built by older code were therefore never rebuilt.
- `backend/app/agents/deep_agent_runner.py:335-343` described the failing PNG as
  5,473,764 bytes. That figure is the base64 length. The file was 4,105,323 bytes.
- `backend/app/api/run_figma_frames.py:63` allowed Figma PNG/JPG frames up to 4 MB,
  above the 3.75 MB that the model accepts as base64. The guard then replaced such frames
  with a placeholder. Frames of 1440 x 10000 px had no dimension check and were sent whole.
- The guard in `deep_agent_runner.py` checked byte size only. No side-length check
  existed, so an image over 8000 px per side would still fail the whole request.
- `backend/agents/capabilities/prototype_ui_extract.py:264` `build_navigation` recorded
  only `image-1.png`. Once screens were tiled, the backlog `ui.md` would have shown
  only the top slice of a tall screen. Review caught this in `ae52d4fbf`.

## The fix

Commits on branch `fix/image-size`, local only and not pushed:
`17f4f4f5d` (issues 1-6) and `ae52d4fbf` (review finding B1).

- **Screen tiling.** `_tile_screenshot` and `_encode_tile` replace `_fit_screenshot`.
  A screenshot within the limits (`_MAX_TILE_SIDE = 2_000`, `_MAX_SCREENSHOT_BYTES =
  3_500_000`) is one unchanged tile. A larger one is cut into full-width slices, each
  at most 2000 px tall, overlapping by `_TILE_OVERLAP = 40` px, with at most
  `_MAX_TILES = 20`. Rows past the twentieth slice are left out, not shrunk.
- **Byte factor.** Applied only when an encoded attempt is still over the byte cap, and
  computed from that attempt's own size.
- **Folder versioning.** `_FORMAT_VERSION = 2` is written to the manifest as
  `format_version`. Reuse requires it to match together with `source_sha256`.
- **Side-length guard.** `deep_agent_runner.py` adds `_largest_media_side`, which reads
  the image header from the first `_IMAGE_HEADER_PROBE_B64_CHARS = 262_144` base64
  characters with Pillow. A side over 8000 px is replaced with
  `_OVERSIZED_SIDE_PLACEHOLDER`. An undecodable header keeps the block. A decompression
  bomb counts as over the limit. The byte-size branch and the FIX-550 duplicate and
  budget logic are unchanged.
- **Figma frames.** `run_figma_frames.py` `_frame_parts` splits a PNG or JPEG frame
  that exceeds the tile limits. Parts are named `frame-N-part-K.png`, and the manifest
  entry gains `parts` and `parts_note`. `backend/agents/prompts/design-ingestor/AGENT.md`
  tells the ingestor to read the parts in order and copy those two fields into
  `frames.json`. Frames uploaded before this change are not rewritten (see ISS-1214).
- **Backlog navigation.** `build_navigation` gives each screen a `screenshots` list in
  numeric order and keeps `screenshot`. The UI/UX Writer's `## Screens` step in
  `backend/agents/workflows/backlog/workflow.yaml` embeds every part. No reader
  prompt changed.
- **Spec.** `specs/021-backlog/spec.md` FR-011 now says a screen too tall for one
  picture references `image-1.png` through `image-N.png`, top to bottom.

## Known limits (decided, not deferred)

- A screen taller than 20 slices (about 39,000 px) loses the rows past the cut. `text.md`
  says so, and the text sections still carry those fields.
- The static route (no Chromium) still takes no screenshots.

## Correction to the design basis

The 2,000 px slice side came from secondary write-ups of the Anthropic limit for requests
with more than 20 images. The vision documentation (platform.claude.com, fetched
2026-11-02) names 3,000 px as the stricter per-side limit. 2,000 px is the
conservative choice and meets both figures.

## Deferred findings

- [ISS-1213](20261102-0136-ISS-1213.md): requests with more than 20 images are not checked
  against the stricter per-side limit. The guard checks only 8000 px.
- [ISS-1214](20261102-0136-ISS-1214.md): Figma frames uploaded before this fix are never re-tiled.
