## Summary

This is the analyzer pass on **BUG-20260828-103434-admin** / **ISS-324**,
which confirmed the duplicate-email 409's toast never mounts but left the
mechanism as "needs further investigation" with two candidates. This card
records the CONFIRMED mechanism and the ISS-324 root cause is scoped one
call site too narrowly — the defect is in the single `showToast` function
every admin action on this page shares, not something specific to
create-user's error path.

## Root cause — CONFIRMED

`frontend/src/app/admin/page.tsx:141-144`:

```ts
const showToast = useCallback((type: "success" | "error", text: string) => {
  setToast({ type, text });
  setTimeout(() => setToast(null), 3500);
}, []);
```

There is no `useRef` tracking the pending timer and no `clearTimeout`
anywhere in the file (`grep -n "clearTimeout\|useRef" admin/page.tsx` —
zero matches). Every call to `showToast` schedules its own **independent**
3.5s timer with nothing that cancels a still-pending timer from an earlier
call. `toast` state can only become falsy two ways: (a) a later
`showToast` call's own timer, correctly, after ITS 3.5s, or (b) an
EARLIER call's timer, which was never told a newer toast replaced it. Path
(b) is the bug: if a second `showToast` fires less than 3.5s after a
first, the first call's timer will null `toast` mid-way through (or, if the
gap between the two calls is itself close to 3.5s, almost immediately
after) the second toast's own intended display window — a stale-timer
race, not a rendering defect.

This is confirmed as a real, reproducible-in-isolation code defect from
reading the function in full — independent of which specific pair of
actions triggers it. `showToast` is not exported/shared
(`grep -rln "showToast" frontend/src` returns only this one file), so the
defect and its fix are both scoped entirely to this one function.

### Why this explains ISS-324's specific finding

ISS-324's repro is: (1) create a throwaway user — `showToast("success", ...)`
fires, scheduling timer A at T+3.5s; (2) reopen the dialog, resubmit the
SAME email, get a 409 — `showToast("error", ...)` fires at some T+Δ,
scheduling timer B at T+Δ+3.5s. For a browser-automation-driven repro
(click, fill, click, await a local-backend round trip), Δ is very plausibly
a low number of seconds — well inside timer A's 3.5s window — so timer A
fires shortly after the error toast is set and clears it early. A short
enough Δ (which a **scripted**, consistently-paced repro would produce
**deterministically**, matching ISS-324's "3/3, no timing axis needed"
finding) leaves the error toast visible for a sub-second window that an
"explicit wait after the button re-enables" DOM check, itself taking some
time to execute, can easily land after.

### What is still INFERRED, not proven by me

I have no browser tool in this pass, so I could not independently measure
Δ or add render-commit logging. What would settle it precisely: re-run
ISS-324's repro with a `console.log(Date.now())` at the top of `showToast`
(or read the two requests' timestamps out of the existing
`bug-hunter/evidence/admin/BUG-20260828-103434-admin/network.log`) to
confirm Δ < 3.5s, or write a component test that fires two `showToast`
calls with a controlled sub-3.5s delay and asserts the second toast's text
is still present past the first call's original 3.5s mark. Either settles
whether the race is the *complete* explanation or one contributing factor
among others.

### Ruled out

ISS-324's second candidate — "the modal's own re-render on the same tick
clobbering the toast's mount" — does not hold up in the code. The
create-user modal (`{showCreate && (...)}`, L465-526) and the toast
(`{toast && (...)}`, L567-583) are separate `<AnimatePresence>` trees,
siblings in the same return statement, each gated on its own independent
state. Reading the full 587-line file found no code path that lets
`showCreate` touch `toast` (or vice versa). Ruling this out narrows the fix
to `showToast` alone rather than anything modal-related.

## Expected vs Actual (the sibling scenario)

**Expected:** any admin action's success/error toast stays visible for its
full 3.5s, regardless of what other action preceded it.

**Actual (INFERRED — mechanically identical code path, not independently
reproduced for these specific pairs):** any two of the nine actions above,
performed within roughly 3.5s of each other, race the same stale timer —
e.g. two consecutive tier changes, a role toggle immediately followed by a
delete, or a failed load immediately followed by any other action. The
earlier action's toast (or, depending on the exact gap, the later one) can
be cut short or never effectively seen. Marked **INFERRED / status:
pending** per the sibling-derivation rule — nobody has reproduced any pair
other than create-success-then-create-duplicate (ISS-324) yet.

## Proposed fix (where it belongs)

In `showToast` itself (`admin/page.tsx:141-144`) — the one place all nine
callers already route through. Hold the pending timer id in a
`useRef<ReturnType<typeof setTimeout> | null>`; on each call, `clearTimeout`
the previous ref value if set, then `setToast(...)` and store the new
timer id. One guard in the shared function fixes every caller; patching
only `handleCreateUser`'s error path would leave the other eight
call sites — and the create-user SUCCESS toast itself, if it ever lands
within 3.5s of another action — still exposed to the identical race.

Not applied here — analysis only, per the analyzer's read-only boundary.
