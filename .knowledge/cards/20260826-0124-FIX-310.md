## What happened

`PATCH /api/admin/users/{user_id}/tier` let an admin set their OWN tier. The
endpoint validated the tier value and looked the user up, then proceeded — there
was no check that the target was somebody else.

## Root cause

Never implemented, not regressed: `git log -S'own tier' -- backend/app/api/admin.py`
returns nothing. The requirement was written (the test cites "Requirement 5.9,
admin self-action policy on tier changes") and the test with it, but the guard
was not added to this one route.

Its two siblings in the same file have it:

| endpoint | line | guard |
|---|---|---|
| `update_user_role` | `admin.py:329` | `if user_id == admin.id and not request.is_admin:` — cannot remove own admin access |
| `delete_user` | `admin.py:616` | `if user_id == admin.id:` — cannot delete own account |
| `update_user_tier` | `admin.py:209` | **none** |

## The fix

Three lines at the top of `update_user_tier`, matching the siblings' shape and
400 status:

```python
if user_id == admin.id:
    raise HTTPException(
        status_code=status.HTTP_400_BAD_REQUEST,
        detail="You cannot change your own tier.",
    )
```

The rationale recorded in the code: an admin changing their own tier is a
privilege mutation with no second pair of eyes — the same account authorises and
receives it — and a downgrade also strips the entitlements needed to undo it.
