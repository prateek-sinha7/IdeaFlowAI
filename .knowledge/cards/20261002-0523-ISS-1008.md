# ISS-1008

**INFERRED. Static read only: nothing below was run, in a browser or in jsdom.** Derived while analysing QA-KB-066 ([ISS-755](20260922-1415-ISS-755.md)); the root-cause analysis and
the offline proof are on that card ("Re-analysis (2026-10-02, QA-KB-066)") and in `evidence/qa-kb-066/`. An unreproduced
sibling is a lead, not a defect.

Line numbers are the working tree on 2026-10-02 (HEAD `024c03ef8`); `PreviewPanel.tsx`, `DashboardLayout.tsx` and
`useWorkflow.ts` carry uncommitted edits from other work (none touches clarifications), so HEAD numbers can sit a few lines off.

## Condition

Open a COMPLETED run that answered one or more clarify rounds on the run screen: from Run History or Home recents
(`handleSelectWorkflowRun`, `page.tsx:2903`), or a cold load / refresh of `/runs/{id}/steps`. Runs with `clarify.mode: auto`
(`ppt_v2`, `ppt_revision`, `app_builder_revision`, ...) are the ones that have rounds.

## Expected vs actual

- **Expected** (INFERRED from the design comments, not from a spec): a reopened run's Steps overview shows the
  "Clarifications, n questions" card and Files offers `clarifications.md`, as the History detail view does
  (`WorkflowHistory.tsx:1131`, `:1166`). `PreviewPanel.tsx:476-481` documents the hook for it: "the explicit `clarifications` prop
  is the reopen override".
- **Actual** (static): the rounds are empty for every reopened run, so Steps renders no card (`ClarificationsCard.tsx:32`
  `if (!loading && !hasRounds) return null`) and Files has no `clarifications.md` row (`FilesTab.tsx:108`).

## Why the root cause implies it

Finding where [ISS-755](20260922-1415-ISS-755.md)'s leaked raw rounds come from showed they exist only for rounds answered LIVE in the current page
mount:

- `useWorkflow.ts` writes `clarifications` in four places only: the initial state (`:49`, `INITIAL_STATE` `:42-50`), `startPipeline`
  (`:82`), `retainClarifyRound` (`:167-171`) and the `pipeline_start` per-run boundary (`:821`). The only clarify case in the
  reducer is `clarification_limit_reached` (`:1840`); no case rebuilds rounds from replayed events.
- Reopen calls `resetPipeline()` (`page.tsx:3046`, state := `INITIAL_STATE`, `useWorkflow.ts:133-137`) and replays the durable
  frames through the page router; nothing in that path reads `kind="clarifications"` artifacts.
- The explicit override prop is never passed: the only `<PreviewPanel` (`DashboardLayout.tsx:3383-3437`) wires `runInput`
  (`:3412`) but no `clarifications`. `git log -S"clarifications={" -- frontend/src/app frontend/src/components/layout` finds no
  commit that ever did; 18581c422 (2026-07-03) added the prop and wired only `WorkflowHistory`.
- The one fetcher of the persisted rounds is `WorkflowHistory.tsx:446`, a different surface from the run screen.

So the "reopen" half of the C2 design was only ever connected to History's own detail view.

## Fix direction (not applied)

Wire the override: fetch `getRunArtifacts(token, id, { kind: "clarifications", includeContent: true })` +
`parseClarificationArtifacts` for the viewed run, keyed on `contentSourceRunId` and only when the run is not the live one, and pass
the result as `PreviewPanel`'s `clarifications` prop. Share one `loadRunClarifications(token, runId)` helper (home:
`lib/clarifications.ts`) with [ISS-1006](20261002-0523-ISS-1006.md), which wants the same data for a pinned version.

Interaction with [ISS-755](20260922-1415-ISS-755.md)'s fix: the pin-keyed `effClarifications` ignores the override while a version is pinned,
which is correct (the override describes the shell run). The two-word alternative `clarifications ?? effPipelineState?.clarifications`
would let this wired override shadow a pinned version again, which is why ISS-755 recommends the pin-keyed form.

This is a different fix site from ISS-755 and [ISS-1006](20261002-0523-ISS-1006.md) (DashboardLayout / page level, not the pin paths), so it is filed apart.

## What would settle it

Open a completed run that answered a clarify round in a fresh tab at `/runs/{id}/steps` and look for the card; then
`GET /api/runs/{id}/artifacts?kind=clarifications&include=content` to confirm the rounds are persisted for it.

## Resolution — FIX-730 (2026-10-07)

Resolved by [FIX-730](20261007-1900-FIX-730.md), for register entry QA-KB-066. The diagnosis above stands. The fix
differs from "Fix direction" in three ways, each argued on FIX-730:

- **Where.** `PreviewPanel` loads the rounds itself (`PreviewPanel.tsx:1222-1238`). DashboardLayout does not pass the
  prop. This card's test mounts `PreviewPanel` alone, with no prop.
- **The key.** It is `workspaceRunId`, not `contentSourceRunId`. `contentSourceRunId` still names the parent while a
  revision runs, and after one fails (`page.tsx:4303`, `:1630`, `:1772-1794`).
- **Precedence.** Non-empty live rounds win over the loaded ones.

The load runs only for a settled run with no live rounds.

Test: the ISS-1008 case now fails with "Expect test to fail" (the `it.fails` pass signal). The marker is left for the
6-verifier.

Residual, filed as [ISS-1059](20261007-1900-ISS-1059.md) (open, INFERRED): a run reopened while it is still running gets
no loaded rounds until it settles.
