# ISS-051

## Title

A nested revision reaches depth 2 with BOTH levels computing revision_index=1, so two passes collide on the same :rev1 checkpoint thread (measured: 7 dispatches, only 4 unique thread ids). The inner finally (engine.py:5325) also resets ectx.revision_attempt to 0 AND wipes ectx.spec_revision_context while the outer pass is still on the stack. Reachable TODAY, independent of ISS-064: the analyze re-run inside the sub-pipeline opens its own gate with update_specs_eligible=True.

## Source / evidence

Observed by the 260811-mxg verifier via instrumentation; reproduced offline by the si4 planner. Duplicate ids + counter reset confirmed; a resulting bad spec NOT observed. RESOLVED (FIX-218 / quick-260811-si4): the sub-pipeline is now properly re-entrant. ExecutionContext.revision_high_water is a monotone per-run mark that is never cleared or restored, and the effective index derives from it, so no two passes at any depth can mint the same :rev{N} (7 of 7 unique, was 4 of 7). The finally RESTORES the three scratch fields instead of clearing them, so an inner pass cannot strip the outer's index or analysis report mid-flight. A companion affordance fence (_update_specs_eligible, now and not ectx.revision_attempt) stops the UI OFFERING the nesting route at all. Guarded by test_nested_revision_keeps_distinct_threads_and_restores_the_outer_pass + test_update_specs_not_offered_while_a_revision_is_in_flight.
