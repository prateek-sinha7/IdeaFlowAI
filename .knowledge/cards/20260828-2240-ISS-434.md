## What happened (derived, not yet reproduced)

Analyzing BUG-20260828-085047-runs-id-stream (register: `bug-hunter/ledger.md`),
root-caused in [ISS-313](20260828-1946-ISS-313.md): the toolbar's "Download the
deliverable" button stays permanently disabled whenever a run completes without
`WorkflowRun.deliverable_filename` populated. The same null value feeds a SECOND,
independent gate in the concierge chat lane that nobody has checked in-browser yet.

## Why the root cause implies this

`RunChatLane.tsx`'s settled-transcript footer computes
`dFilename = deliverableFilename ?? pipelineState?.deliverableFilename`
(`frontend/src/components/chat/RunChatLane.tsx:1919`) and renders the "Run
summary" strip's deliverable row only conditionally:

```
{dFilename && (
  <DeliverableCard filename={dFilename} version={dVersion} onOpen={goPreview} />
)}
```
(`RunChatLane.tsx:814-820`)

`dFilename` traces back to the exact same source ISS-313 already confirmed is
`null` for this run — `WorkflowRun.deliverable_filename` / the live
`pipeline_complete.deliverable_filename` — because the launched manifest
(`backend/agents/workflows/playwright_smoke_test/workflow.yaml:25-26`) declares
`deliverable.strategy: serialized_sandbox` with no `deliverable.name`, and the
compiler (`backend/agents/workflows/compiler.py:1446-1451`) copies that `None`
through with no validation or fallback (see the deepened root-cause section
appended to ISS-313 for the full compile-to-emission chain). When `dFilename`
is falsy, `DeliverableCard` is never rendered here — no filename badge in the
collapsed "Run summary" meta line (`metaBits`, `RunChatLane.tsx:771`), and no
expandable deliverable row with an "open in Preview" affordance, for a run
whose deliverable is fully present and independently downloadable via the file
panel.

Also checked and ruled OUT as a sibling: `chat_narrator.py:194-200` falls its
`pipeline_complete` deep-link `target` back from `deliverable:{filename}` to
`deliverable:{anchor}` when `filename` is falsy, but this fallback is inert —
the frontend's `deep_link.target` is a dedup/reference key, never parsed for a
filename (`ResultCard.tsx:108-113`: the actual navigation tab comes from a
separate `deepLink.tab` field). Noted here only so the next investigator does
not re-walk the same dead end.

## Expected vs actual (INFERRED — needs a live repro to confirm)

- **Expected:** the chat lane's "Run summary" strip shows a `DeliverableCard`
  for any completed run with a rendered deliverable, the same way it does for
  a run whose manifest declares a name.
- **Actual (predicted from the code path above, not yet observed in-browser):**
  on the run ISS-313 reproduced against
  (`649e56cf-ce0f-4a0f-91fa-4e75a971a980`, `playwright_smoke_test`), the "Run
  summary" strip's meta line should omit the filename bit and the expandable
  panel should never show a `DeliverableCard` row — the chat lane silently
  offering no path to the deliverable at all, same failure shape as the
  toolbar button, different surface.

## What would settle it

Reopen `/runs/649e56cf-ce0f-4a0f-91fa-4e75a971a980/stream` (or launch a fresh
`playwright_smoke_test` run), open the chat lane's "Run summary" strip, and
check whether a `DeliverableCard` row is present. `agents.length` is 1 for
this run, so the strip itself should still render (the `!dFilename`
early-return at `RunChatLane.tsx:1921` only suppresses the WHOLE strip when
there are also zero agents and zero clarifications) — the missing piece to
look for is specifically the `DeliverableCard` row, isolating this from
ISS-313's already-confirmed toolbar symptom.
