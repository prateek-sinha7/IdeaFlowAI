# ISS-132

## Title

The task-loop sibling of ISS-097: ticking a task-loop agent opens ONE GATE PER TASK. Same root cause — _should_gate is per-INVOCATION on spec.id while gate_agent_ids is a per-STEP selection — and the task loop is the other strategy that turns one step into N invocations of one agent id. Verified at eb12bc7e: task_loop.py calls runner.run_agent(step, ctx, task_number=..., ...) with NO invocation_gated, so it takes the default True, and unlike run_fanout it FORWARDS every event (yield event). So this is the visible, answerable cousin, not a hang: N sequential gates, all on the one gate key f"{run_id}:{agent_id}", each surfacing properly on the wire and each requiring a human click. Annoying and almost certainly not what the user meant by ticking one box, but nothing is lost and nothing is invisible. Reachable on a live workflow: prototype-build is in the frontend agent library (AgentLibraryData.ts:25) with gate: null, so it is tickable in the launch wizard's gate picker. FIX-242 deliberately left this alone. The mechanism it added (invocation_gated=False) would close this in one line at the task-loop call site, but whether a per-task review gate should be offered AT ALL is a product decision — some users may genuinely want to review each task of a build — whereas the fan-out case had no defensible reading because the gates were unreachable. Note ISS-090 already records that FIX-228 handles the task-loop redo case defensively inside _consume_redo, so the interaction is partly known.

## Source / evidence

Found 2026-08-12 by the ISS-097 investigation while sweeping for siblings of the invocation-vs-step confusion, and named in the FIX-242 plan's out-of-scope list. Fix shape, once the product question is answered: either pass invocation_gated=False at the task_loop.py run_agent call (suppress entirely, matching fan-out), or gate only the FINAL task, or leave as-is and change the gate picker's copy so "pauses after they finish" is not a promise the task loop breaks N times.
