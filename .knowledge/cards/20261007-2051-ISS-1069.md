# ISS-1069

## Provenance

The QA-KB-091 analyzer found this and recorded it in [ISS-1031](20261002-1040-ISS-1031.md), section
"Reverse direction (found, NOT fixed by the same change)", as a design call. The QA-KB-091 fixer
resolved ISS-1031's own claim with [FIX-749](20261007-2051-FIX-749.md) and moved this finding to its own
card, so it is not buried in a resolved one. Nobody reported it.

- **CONFIRMED offline** (jsdom, the real `PreviewPanel`): probe rows G7 in
  `evidence/qa-kb-091/04-analyze-probes-real-tree-and-fix-variants.txt`, re-run on 2026-10-07 in
  `evidence/qa-kb-091/fix-05-probes-before-after.txt`. Identical before and after FIX-749:
  - pinned `failed` or `degraded` WITH content, healthy shell:
    `header={"runFailed":false,"partialChip":false,"shareBtn":true,"downloadBtn":true}`;
  - the same kind of run UNPINNED (shell `failed`, with content):
    `header={"runFailed":true,"partialChip":true,"shareBtn":false,"downloadBtn":false}`.
- **INFERRED in the browser.** Nothing was driven, and no live row (a failed or degraded member with a
  stored output) was looked for. A failed run usually stores no output; a degraded one may.

## Mechanism (read)

- `PreviewPanel.tsx:1277` `const headerFailed = terminalFailure && !isCancelledTerminal;`.
  `terminalFailure` is built only from shell signals (`:1170-1179`), and since FIX-749 those are off
  for a foreign pin. Nothing in the header derivation reads `viewingVersion.status`, which is read only
  at the empty-body pinned branch (`:1907`).
- `headerRunState` (`:1278`) then falls to `hasContent ? "complete"`, so `RunHeader` shows Share and the
  settled Download (`RunHeader.tsx` `isFailed = failed || runState === "terminal"`).
- The badge reason would need the pin's failed agents. `VersionView` carries no `error` or failed-agent
  list.

## Reach widened by FIX-749 (INFERRED, code read)

While a revision runs and after it fails, `liveRunId` still names its PARENT (`PreviewPanel.tsx:1231`,
the ISS-1008 note). Before FIX-749, pinning that just-failed revision itself (a chat card ->
`handleSelectVersion`, which pins any terminal member) kept the live `pipelineState.failed` in force,
because the shell's live signal happened to describe the pin. FIX-749 gates the live signal on
`viewingVersion.id === unpinnedRunId`, which is the parent, so that pin now gets the same surface as
every other pinned failed version:

- Preview kept, with "did not complete successfully";
- a header without "Run failed".

## Decision needed

Should a pinned version's header say "Run failed" when the pinned run itself failed or degraded?

- **Yes:** add a header-only `pinFailed` derived from `viewingVersion.status`, OR-ed into `headerFailed`
  for the header only. The badge reason stays absent until `VersionView` carries an `error`. Tabs,
  Preview and `terminalFailure` must stay untouched (locked constraint above).
- **No:** a pinned version is read-only history. Its failure shows in the Preview copy (FIX-709) and in
  Steps, and the header stays settled. Close this card as intended.
