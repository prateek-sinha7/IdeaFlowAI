## Description

The two app-layer driver terminals wrote no durable row at all, so the owner's Stop was recorded as a FAILURE and fresh corrupted runs were still being minted (ISS-124). _drive_launch_to_queue and _drive_revision_to_queue both catch asyncio.CancelledError — the branch stop_run_driver escalates to when a driver cannot observe the cooperative cancel_event in bounded time — push a pipeline_cancelled FRAME onto the queue, set status="cancelled", and write NOTHING to run_events. The register filed this as minor; it is not. Two live consequences, both pinned by tests seen RED first. (1) The run's durable log ends on whatever preceded the cancel; when that is a review_gate_ready, a fresh reopen replays a dangling gate — i.e. this path was still MINTING the corrupted runs ISS-126 has to render, which also disproves ISS-126's "affects only runs corrupted BEFORE FIX-240". (2) stop_run_driver then calls _reconcile_terminal_status, which decides from the durable tail ALONE: no pipeline_cancelled row → cancelled=[]/completes=[]/failed=[] → the D2 fail-safe "failed", written through an unconditional _persist_resume_status that overwrites the "cancelled" the driver set moments earlier. Observed directly as assert 'failed' == 'cancelled'. Fix: both branches append through _record_cancellation_in_the_durable_tail, FIX-243's collision-safe writer (ScopedStore.append_event_at_or_after — FIX-240/ISS-121's failure mode), EXTENDED with a reason parameter rather than copied (INV-12: one durable-terminal writer, three callers); the default keeps FIX-243's no-live-driver payload byte-identical, the drivers pass "driver_task_cancelled". No duplicate-suppression guard, deliberately: the pipeline_cancelled frame is already emitted unconditionally on both branches, so this only makes the row agree with the frame that already ships, and every verified consumer is any()/max()-shaped. The discriminating test drives a REAL task.cancel() because the append sits inside an except asyncio.CancelledError block and had to be OBSERVED completing under genuine cancellation rather than assumed — writing it also corrected a wrong assumption of mine: the driver deliberately CONVERTS the cancellation into a terminal instead of re-raising, so an earlier version of that test asserting a re-raise was wrong and was fixed against observed behaviour.

## Root cause

Two app-layer drivers owned a terminal transition but only ever wrote the transport frame and the status column, never the durable event — while _reconcile_terminal_status, which runs immediately afterwards on the same path, derives status exclusively from that missing durable event.
