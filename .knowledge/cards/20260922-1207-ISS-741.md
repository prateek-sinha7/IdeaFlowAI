## What happened

Reported as QA-SG-003 (`BUGS.md#qa-sg-003`, `LEDGER.md` row). From a run detail
page (`/runs/{id}`), clicking "Back to history" (or "Back", same control,
aria-label "Back to history") lands on `/runs` as expected. Clicking the Run
History page's own Back arrow-left icon button then does NOT go further back
(e.g. to `/dashboard`) — it lands on the SAME run detail page again. Clicking
"Back to history" again returns to `/runs`. The two pages loop; the user can
never navigate past the point where they opened the run.

## Reproduction — 3/3 from cold start, cycle 1

Each attempt: fresh nav to `/dashboard`, then `/runs` (cold, not a soft
re-click), click a different run row, click "Back to history", click the Run
History page's Back icon.

| # | Run | Status | Result |
|---|---|---|---|
| 1 | `95351433-0825-4a33-a9c3-0dfad4b748ec` (ppt_revision) | completed | looped back to `/runs/95351433-…` |
| 2 | `dfeb5949-6ad6-496e-ba19-fe7ff5d1fbe1` (presentation) | completed | looped back to `/runs/dfeb5949-…` |
| 3 | `5ef6d95c-77b3-4e4d-8017-816359d37c8c` (presentation) | failed | looped back to `/runs/5ef6d95c-…` |

Varying the run and its terminal status ruled out a state-specific trigger —

## Root cause

`frontend/src/components/layout/DashboardLayout.tsx` — the execution shell's
`onBackToHistory` handler (~line 3210, two identical mounts at the same
location for the RunChatLane props) is:

```tsx
onBackToHistory={() => {
  setMainView("history");
  router.push(routes.runHistory());
}}
```

This **pushes** a new `/runs` entry onto browser history instead of popping
back to the `/runs` entry that already exists (from the row click that pushed
`/runs/{id}` — see `onOpenRun={(run) => { ...; router.push(routes.runDetail(run.id)); }}`
at DashboardLayout.tsx:2896/2956). So the stack becomes
`[..., /runs, /runs/{id}, /runs]` instead of `[..., /runs]`.

By contrast, the Run History page's own Back arrow-left button
(`frontend/src/components/history/WorkflowHistory.tsx:~1201`, wired to
`DashboardLayout.tsx`'s `handleBackNav`, `~line 1806`) is implemented
correctly with `router.back()`. When the user clicks it after the loop above,
it legitimately pops to the PREVIOUS history entry — which is the
just-repushed `/runs/{id}` — producing the observed loop. The bug is entirely
in `onBackToHistory`'s use of `router.push` where `router.back()` (mirroring
`handleBackNav`'s own pattern, which already falls back to
`router.push(routes.home())` only when there is no history to pop) belongs.

The default `onBackToHistory` in `frontend/src/components/chat/LaneRunHeader.tsx:299-305`
(`window.history.back()`) is correct and is NOT the bug — it is overridden by
DashboardLayout's buggy prop whenever DashboardLayout mounts the lane, which
is every real run-detail render.

## Fix direction (not applied — analysis/validation only)

Change `onBackToHistory` at DashboardLayout.tsx:~3210 to call `router.back()`
when `window.history.length > 1` (matching `handleBackNav`'s existing
fallback shape), instead of unconditionally `router.push(routes.runHistory())`.

## Fixed by FIX-620

[FIX-620](20260922-2006-FIX-620.md) applied the prescribed fix: the guard now
lives in `frontend/src/lib/navigation.ts` (`goBackOr`), and
`DashboardLayout.tsx:3251`'s `onBackToHistory` calls it instead of
`router.push(routes.runHistory())`. `handleBackNav` (`:1828`) and
`commitBackNav` (`:1808`) route through the same helper, so the app holds one
copy of the guard rather than three.
