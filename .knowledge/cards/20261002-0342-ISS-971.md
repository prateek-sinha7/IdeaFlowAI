# ISS-971

**CONFIRMED in a sandbox copy, not in the live tree.** Derived while analysing QA-KB-051 ([BUG-127](20260918-BUG-127.md)). It is the
same root mechanism (a stage that fails after `index` leaves `index`'s writes behind, with no rollback) but a different artifact and
a different consumer, so it needs its own fix and its own test. The analyzer reproduced it in a throwaway copy of `tools/knowledge/` +
`.knowledge/`; running it against the live tree would have meant really moving the live sync watermark.

Line numbers are the working tree on 2026-10-02 (HEAD `024c03ef8`); `rebuild_knowledge.py`, `build_index.py`, `build_context.py` are
clean against HEAD.

## Condition

`rebuild_knowledge.py --skip-architecture --set-sync-point`, the sync-point stamp (`skills/velocity/cli.md:17`), when any stage after
`index` fails. It is the closing action of `/velocity sync` (`skills/velocity/sync.md:116-126`) and of the bug line's Close pass
(`.claude/agents/7-closer.md:127-128`), and the `sync.md:39-47` "re-baseline" path. Today the trigger is [BUG-127](20260918-BUG-127.md)'s
`TypeError` in `context`; a `MissingInput` from `build_context.load_modules()` (a missing or unreadable `modules.json`,
`build_context.py:201-226`) trips it the same way.

## Why the root cause implies it (each step read)

- `rebuild_knowledge.py:324`: `extra = ["--set-sync-point"] if (name == "index" and args.set_sync_point) else None`. The flag is handed
  to the index stage and to no other.
- `build_index.py:375-377`: `if args.set_sync_point: state["last_sync_commit"] = commit` and `state["last_sync_date"] = ...strftime("%Y-%m-%d")`,
  persisted by `write_if_changed(STATE_PATH, ...)` at `:378-381`. That all happens inside stage 1 of the cards-only run, before `context`
  (stage 2) and `validate` (stage 3) exist as far as the process is concerned.
- `rebuild_knowledge.py:325-327`: a failing stage prints `Aborted at stage 'context'. Nothing further was run.` and returns 1. Nothing
  restores `state.yaml`; `skills/velocity/cli.md:67-76` says so outright ("There is no rollback").
- `build_index.py:356-362` defines the field: "`last_sync_commit` means 'the commit `sync` last reconciled against', and only `sync` may
  move it." A run that exits 1 has still moved it.

## Expected vs actual

- **Expected:** a stamp that reports FAILED leaves `last_sync_commit` and `last_sync_date` exactly where they were. The watermark moves
  once the artifact stages (`index`, `context`) have succeeded.
- **Actual:** the stamp moves both in stage 1, then fails in stage 2 with exit 1.

## What was reproduced

`evidence/qa-kb-051/analysis-sandbox-repro.sh`, step 4 (whole transcript in `analysis-sandbox-repro.out.txt`). Sandbox = copy of
`tools/knowledge/` and `.knowledge/`, one dummy card added, run under `/usr/bin/python3` 3.9.6:

```
before: last_sync_commit: 3b08b2ba84575d405b6e97f8006f053ca6b5b30d   last_sync_date: '2026-10-01'
  ! TypeError: write_text() got an unexpected keyword argument 'newline'
  FAILED (exit 1)
Aborted at stage 'context'. Nothing further was run.            exit=1
after:  last_sync_commit: ''                                      last_sync_date: '2026-10-02'
CONTEXT.md still: cards_indexed: 1698
```

The sandbox has no commits, so `git rev-parse HEAD` returns nothing and `last_sync_commit` becomes `''`; the date moved. INFERRED, from
`build_index.py:346-349`: in the real repo the commit becomes HEAD's sha.

## How much it matters (low)

Recovery is a re-run: the stages are idempotent and the re-run stamps the same HEAD. `skills/velocity/sync.md` makes the stamp the last
step, after the proposals are applied, so the reconciliation it records has already happened. What is wrong is the contradictory
outcome, and two readers of it:

- `status.py` derives `commits since sync` and `source files changed` only from `last_sync_commit` (`status.py:231-255`). After the failed
  stamp both read OK. `CONTEXT.md cards` is a pure count compare (`status.py:215-220`), so a stale pack whose card count did not change is
  not flagged either (INFERRED from the code; not executed).
- The closer's own rule ("Stamping past unreconciled commits drops them from every future sync window, permanently",
  `7-closer.md:129-130`) and the re-baseline path (`sync.md:39-47`) treat the watermark as the one irreversible field. In the documented
  flows the stamp runs only after reconciling, or on an explicit re-baseline, so no commit is lost today. What is left is a stamp that
  reports FAILED yet has moved the field, so an operator who stops there holds a watermark they were told did not move.

## Where the fix belongs

`rebuild_knowledge.py:main()` (`:322-331`), the single owner of stage order. Every caller of the stamp routes through it, and
`hook_mode()` phase 3 re-enters it (`:255`).

1. Stop forwarding `--set-sync-point` to the index stage. After `context` has succeeded, run the index stage once more with
   `--set-sync-point`, or give `build_index.py` a watermark-only entry. The second index run is idempotent: `write_if_changed`
   (`build_index.py:32-47`) rewrites `INDEX.md` only if its bytes differ, so only `state.yaml`'s two keys move, and the whole cards-only
   rebuild costs about 1.6 s (`.pre-commit-config.yaml:154`). `validate` stays last and its failure stays non-fatal for the watermark (the
   third `locked_constraints` entry); tying the watermark to `validate` would let any unrelated broken link block `sync`.
2. `build_index.py:355-362` keeps "preserve unless the flag is passed", and `sync.md` step 7 keeps its one command.

Alternative that also closes the ordering half of [BUG-127](20260918-BUG-127.md): run `context` before `index`. `build_context.py:372`
(`state = load_state()`) is the only use of `state` in `main()`; its value is never read, so `context` needs `state.yaml` to exist but
not what is in it. Then a `context` failure leaves `INDEX.md`, `state.yaml` and the watermark untouched. It costs doc ripple (the
`architecture -> index -> context -> validate` diagram at `cli.md:58-60`, `7-closer.md:88`, the comment at `rebuild_knowledge.py:15-18`)
and relaxes the precondition at `build_context.py:163-198`. INFERRED that nothing else depends on the order; the fixer should check.

## For the test-writer

Hermetic, the way `backend/tests/unit/test_status_domain_prose_unknown.py` drives `status.py`: importlib-load the script, work in a
temporary tree, never read the live counts. The scripts derive `ROOT` from `__file__` (`rebuild_knowledge.py:51`, `build_context.py:32`)
and `build_index.py` / `validate_links.py` resolve it with `git rev-parse --show-toplevel`, so copy `tools/knowledge/` into a temp
directory and `git init` it (no commit is needed: `build_index.py:346-352` handles an empty HEAD). Replace `build_context.py` in the copy
with a stub that exits 1, run `rebuild_knowledge.main()` with `sys.argv = ["rebuild_knowledge.py", "--skip-architecture", "--set-sync-point"]`
and assert `state.yaml`'s `last_sync_commit` and `last_sync_date` equal their pre-run values. They have moved today. Add the passing
case too: with a working `context` stub the watermark must move. Offline tier only, one file at a time.
