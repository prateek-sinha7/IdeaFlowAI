## Source

Derived by the analyzer from the root cause of `BUG-20260828-081200-analytics`
([ISS-229](20260828-1601-ISS-229.md)) — the cross-filter interaction implied by the same two
lines that prove ISS-229's mechanism. **Not yet independently reproduced in a browser session**;
filed from a direct code read.

## Mechanism (CONFIRMED by code read, INFERRED as a live symptom)

`frontend/src/components/analytics/AnalyticsPage.tsx`:

- `pipelineRows` (lines 244-252): `.filter(p => pipelineFilter === "all" || normalizeType(p.type)
  === pipelineFilter)` — checks `pipelineFilter` only. `modelFilter` is never read here.
- `modelRows` (lines 258-267): `.filter(m => modelFilter === "all" || m.model_id ===
  modelFilter)` — checks `modelFilter` only. `pipelineFilter` is never read here.
- Both selects are independently changeable (lines 313-327 pipeline `<select>`, lines 329-341
  model `<select>`, shown together whenever `availableModelIds.length > 1`), so a user can set
  both simultaneously.

## Expected vs actual (predicted from the mechanism above)

**Expected:** with both a pipeline type AND a model selected, "By Pipeline Type" and "By Model"
should each show figures scoped to the INTERSECTION (that pipeline's runs on that model), so the
two panels agree with each other.

**Actual (predicted, unverified):** "By Pipeline Type" shows the selected pipeline's totals across
ALL models (ignoring the model filter), while "By Model" shows the selected model's totals across
ALL pipelines (ignoring the pipeline filter) — the two panels can each be internally consistent
with the URL yet mutually contradictory, on top of ISS-229's already-broken KPI tiles/chart/
success-rate.

## What would settle it

Reproduce live: `/analytics` as qa-admin on a range with 2+ pipeline types AND 2+ models, select
one of each, and compare the "By Pipeline Type" and "By Model" figures against a manually
computed intersection from `GET /api/runs` for the same window.

## Fix

Same location as ISS-229/ISS-288 — extend the proposed server-side `pipeline`/`model` query
params so `_aggregate()` filters the run set on BOTH before rolling up
(`backend/app/api/analytics.py:290-296`), and have `pipelineRows`/`modelRows` read from that
already-intersected payload instead of each running its own single-axis client-side `.filter()`.
A per-list guard (making `pipelineRows` also check `modelFilter` and vice versa) would only
patch the two breakdown lists and leave KPI tiles/chart/success-rate on the wrong data still —
the shared server-side fix is what makes every section on the page agree at once.


## Resolution

Fixed by [FIX-339](20260828-2231-FIX-339.md): both breakdowns now render an
already-intersected payload — `pipelineRows` / `modelRows` no longer run their own single-axis
`.filter()` (`frontend/src/components/analytics/AnalyticsPage.tsx:254`, `:267`).

`verification.status` stays **pending**, not passed:
`test_pipeline_breakdown_respects_the_model_filter_too` SKIPPED on this seed data — "only one
model present in this range — the model filter is not rendered". Every Prototype run belonging
to qa-admin has a null `model_id`, so the pipeline-scoped payload holds one model bucket and the
select is not offered. The mechanism was confirmed at the endpoint instead:
`?range=all&pipeline=prototype&model=<haiku>` returns the INTERSECTION (0 runs, both lists
empty) where the two axes previously reported 26 and 7 independently. Re-running the browser
assertion needs seed data with a prototype run on a named model.
