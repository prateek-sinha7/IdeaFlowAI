## What happened (derived, not yet reproduced)

[ISS-246](20260828-1657-ISS-246.md) documents six Workflow-tab controls in the Advanced modal's
right rail that render permanently `disabled` — via `!onRunConfigChange`/`!onCapabilitiesChange`
— with no lock icon, tooltip, or copy explaining why. Reading the surrounding code for this
analysis (`frontend/src/components/workflow/composer/CanvasView.tsx:2215-2255`, the same right
rail that hosts those six controls) turned up a **seventh** control gated by the identical
mechanism that the hunter/validator's DOM sweep did not include in its checklist: the "Reset to
default" button in the Workflow-tab header.

```tsx
// CanvasView.tsx:2238-2253
{railTab === "workflow" && (
  <button
    type="button"
    onClick={() => {
      onRunConfigChange?.({ ... });
      onCapabilitiesChange?.({ ...capabilities, internet: false });
    }}
    disabled={!onRunConfigChange && !onCapabilitiesChange}
    className="... disabled:opacity-40"
  >
    Reset to default
  </button>
)}
```

Under the exact same condition ISS-246 documents — the LaunchWizard → `AgentsPopup` entry path,
where `AgentsPopupProps` has no `onRunConfigChange`/`onCapabilitiesChange` field at all (see
`AgentsPopup.tsx:43-146`; the comment at lines 71-80 documents this as deliberate) — this button
is also unconditionally disabled. It gets only `disabled:opacity-40` styling (a dim, not a
lock icon), no `title` attribute, and no adjacent copy of any kind. A user has no way to tell
whether "Reset to default" is unavailable on purpose or broken.

## Root cause

Same mechanism as ISS-246: `CanvasView.tsx`'s Workflow-tab UI treats the presence of
`onRunConfigChange`/`onCapabilitiesChange` as the sole signal for both "is this editable" and
"should the user be told why not" — and only wires the first. This button sits in the same
right-rail block (`railTab === "workflow"`, `CanvasView.tsx:2215-2289`) as the six controls
ISS-246 already covers, immediately above `workflowSettingsSection`, so a fix placed in
`workflowSettingsSection` alone (the natural fix site for ISS-246) will not reach it — this
button is rendered separately, in the tab header at line 2238, not inside
`workflowSettingsSection`.

## Reproduction (NOT yet performed — this is why `verification.status` is `pending`)

1. Sign in as qa-admin, cold nav to `/create/user-stories` (or any built-in `/create/<mode>`).
2. Open the "Advanced" modal, leave no agent node selected (default Workflow tab).
3. `document.querySelector('button')` matching text "Reset to default" (or
   `[...document.querySelectorAll('button')].find(b => b.textContent.trim() === "Reset to default")`)
   → read `.disabled`.
4. Expected per this analysis: `true`, with no `title` attribute and no adjacent explanatory
   text — the same defect class as ISS-246's six controls, on a seventh, previously-unchecked
   control.

## Expected vs actual

**Expected:** Same standard ISS-246 sets for the other six controls — either editable, or a
visible reason if intentionally locked.

**Actual (inferred, pending confirmation):** Silently disabled, indistinguishable from broken.

## Why this is a separate card and not folded into ISS-246

ISS-246's own reproduction section enumerates exactly six controls verified via DOM read; this
button was not one of them, so it is not covered by that card's verified claim even though the
mechanism is identical. Filing separately keeps ISS-246's verified scope accurate and gives the
fixer a discrete checklist item so the shared fix (wherever it lands — `workflowSettingsSection`
covers the six controls but not the tab-header Reset button; the fixer should confirm the fix
location's reach covers both) does not silently miss this button the way the original DOM sweep
did.
