## Register entry

Filed against **QA-PS-008** (`LEDGER.md`, closed) while investigating Bilal's report "the
versioning issue where version information or tag is not showing proper version in the run
detail". Re-examines FIX-522's own closing verification evidence on the SAME repro family
(`23bd9c67-e239-4979-b14a-cb78222795e8`, chain root `2708dbf1-50d0-465d-9bed-56b651ea1abf`) and
finds a second, previously-undocumented mechanism behind it: not leaked tags (QA-PS-008's
original defect, correctly fixed), but **missing real ones**.

## What populates the chip and the dropdown — two independent sources

- **The chip's LABEL** (`v1`, `v2`, …) is DB-derived and correct by construction:
  `PreviewPanel.tsx:760` builds `sortedMembers` from the `runFamily` prop (itself
  `GET /{id}/family`, i.e. `_owned_family_members`, `backend/app/api/runs.py:1563-1710` — a
  `parent_run_id` BFS walk with a 1-based `revision_index` at `:1694`, independent of git
  entirely). `activeIdx` (`PreviewPanel.tsx:772`) is that member's position, and
  `headerVersionLabel = "v${derivedVersionNumber}"` (`PreviewPanel.tsx:1174-1177`) is passed to
  `RunHeader` as `versionLabel`.
- **Whether the interactive dropdown mounts at all, and what fills it**, is a SEPARATE, git-only
  source: `RunHeader.tsx:266-277` fetches `GET /{run}/sandbox/refs`
  (`backend/app/api/run_files.py:861-885`, `RunSandbox.list_tags()` →
  `backend/app/agents/sandbox.py:923-941` → `git tag --list` in the sandbox root).
  `hasTags = tags.length > 0` (`RunHeader.tsx:279`) decides the branch: `hasTags` false keeps
  "today's static chip" (`RunHeader.tsx:369`, `!hasTags && versionLabel`); only `hasTags` true
  mounts `VersionMenu` (comment at `RunHeader.tsx:41`: "When no tags exist yet the caller keeps
  today's static chip instead of mounting this component at all"). Clicking a listed tag is then
  matched back to a family member by `sortedMembers.find((m) => m.git_tag === tag)`
  (`PreviewPanel.tsx:858`) — an exact-string match against the DB's OWN `git_tag` column
  (`runs.py:1698`), not against `revision_index`.

These two sources normally agree because tag creation is *supposed* to mirror `revision_index`
1:1. They are not kept in sync, and nothing reconciles them when they drift.

## Root cause — CONFIRMED

**1. Tag creation is best-effort, per-run, and can silently not happen for a real, completed
revision.** `finalize_terminal_run`'s "Step 8" (`backend/agents/execution_engine/engine.py:2349-2456`)
only attempts `sandbox.create_tag(f"v{revision_ordinal}")`
(`engine.py:2361-2363` guard, `:2377` the call) when `_sandbox is not None`,
`_effective_status == "completed"`, and `not last_commit_blocked`. `RunSandbox.create_tag`
(`backend/app/agents/sandbox.py:900-920`) raises if `self.has_git` is false (`:914-917`, e.g. the
run's own `git_init_sandbox()` — called at `engine.py:4098` — failed earlier in the SAME run) or
on any other git failure. When it raises, the outer `except` at `engine.py:2436` calls
`attempt.degrade("tag_creation_failed")` — but critically, the DB write
`_tag_row.git_tag = _tag_name_to_create` (`engine.py:2392`) only happens AFTER `create_tag`
returns successfully (`:2377-2392`), so a tag-creation failure leaves `WorkflowRun.git_tag` at
its default `NULL` while the run can still finish and stay `status="completed"` if the failure
happened somewhere degrade doesn't force it terminal. The column comment already documents this
as expected: `git_tag=getattr(r, "git_tag", None)  # task 6.4 — nullable; None when run pre-dates
git versioning` (`runs.py:1698`) — but the frontend menu treats "nullable" as "does not exist",
not "exists but isn't taggable right now."

**2. A sandbox's `.git` is not durable across the family's lifetime, so even a tag that WAS
created can vanish from what `list_tags()` reports later — with no error, and no way to tell
from the DB.** Confirmed directly, read-only, against the exact sandbox
[ISS-671](20260917-1345-ISS-671.md) used for its own repro:

```
$ git -C runs/c6b9b61f-183d-4662-ae84-d7fd5a052571/2708dbf1-50d0-465d-9bed-56b651ea1abf log --oneline --all --decorate
d0c6e5e (HEAD -> main, tag: v3) chore: terminal snapshot run=3839720c-0287-48c0-90cb-4385d910f460 status=completed
41f7f97 step: custom-revision-planner
73f3699 chore: initialise sandbox
$ git -C runs/c6b9b61f-183d-4662-ae84-d7fd5a052571/2708dbf1-50d0-465d-9bed-56b651ea1abf tag --list
v3
```

Three commits total, all dated **2026-09-21** — the day the family's THIRD member ran. The first
commit is literally `"chore: initialise sandbox"` (`git_init_sandbox`'s own message,
`backend/app/agents/runtime/local.py:678-707`), which only fires when `(self._root /
".git").exists()` is false (`local.py:698`) — i.e. this `.git` was built from nothing that day.
There is zero trace of the family's first two members (created **2026-09-16**, five days
earlier). This matches [ISS-671](20260917-1345-ISS-671.md)'s own 2026-09-17 finding that this
exact directory was "an empty directory with no `.git` of its own" at that time — between the
first member completing (which the database shows DID get tagged, see Data below) and ISS-671's
check the next day, this sandbox's `.git` was lost outright, then rebuilt from scratch (no
ancestry) when the third revision ran. **Provenance of the loss is INFERRED, not settled** — it
happened in a live dev/QA environment mid-investigation of QA-PS-008 itself, and no reconciliation
or backfill mechanism exists to notice or repair it either way (confirmed absent by reading:
`create_tag`/`list_tags` are the only tag-facing operations in `sandbox.py`; nothing compares
`git_tag` on `WorkflowRun` rows against `list_tags()` output).

Either mechanism (1) or (2) lands on the same observable defect: `WorkflowRun.git_tag` and the
sandbox's actual git tags can disagree for a real, completed, DB-visible family member, and
`RunHeader`/`PreviewPanel` have no fallback when they do — the member simply cannot be reached
through the version affordance.

## Is QA-PS-008's fix (FIX-522) implicated?

**Partly.** FIX-522 is correct and should not be reverted — it closed a real security/data leak
(host checkout tags and content reachable through any sandbox lacking its own `.git`). It did not
create either mechanism above; both are independent of the `GIT_CEILING_DIRECTORIES` change (a
sandbox with its own `.git` "behaves exactly as before" per FIX-522's own card). What FIX-522
changed was the FAILURE MODE on this exact family, at that exact moment: before it, a family
whose sandbox lacked `.git` showed a garbage-but-open dropdown (6 leaked host tags) that hung on
selection ([ISS-671](20260917-1345-ISS-671.md) Defect 2 / [ISS-677](20260917-1449-ISS-677.md));
after it, `refs` correctly went empty and the SAME family showed a static, non-interactive chip
with no dropdown at all — which FIX-522's own verification read as "the Preview-hang path is
unreachable," i.e. success. It was success, narrowly — but it retired the visible symptom of the
git-tag layer's unreliability rather than the layer's unreliability itself, and it is that
underlying layer (tag creation, and tag durability) that this card traces, independent of the
ceiling fix, still open today.

## Blast radius

Every caller gated on `list_tags()`/`GET /sandbox/refs` inherits this gap for any family member
with a missing or lost tag — same list [ISS-671](20260917-1345-ISS-671.md) already established,
now confirmed to bite in the "real version, no/lost tag" direction rather than only the
"leaked/fake tag" direction:

- `frontend/src/components/preview/RunHeader.tsx:266-382` — the version chip/menu itself (this
  card's primary finding).
- `_validate_ref` (`backend/app/api/run_files.py:820-856`, exact text not re-quoted here) gates
  `GET /sandbox`, `/sandbox/zip`, `/sandbox/file` with `?ref=`. A `ref=v2` request for this exact
  family would 400 "invalid ref" today — `v2` is not in `list_tags()` even though `v2`
  (`23bd9c67`) is a real, completed member.
- `PreviewPanel.tsx:858`'s `git_tag === tag` match — moot for an untagged member since it never
  reaches the menu to be clicked, but confirms the same DB column is trusted for both the
  existence check (list) and the identity check (select).
- Restore's `_validate_tag_for_restore` (`backend/app/api/runs.py`, per
  [FIX-522](20260917-1449-FIX-522.md)'s own caller list) — same allow-list, same gap, opposite
  direction of severity (restore REFUSING an untagged real version is fail-safe, not
  fail-dangerous).

## Fix direction (not applied — issue only)

The dropdown's EXISTENCE and CONTENTS should not be gated on `list_tags()` at all — `runFamily
.members` (already fetched, already correct, already what drives the chip's label) is the
authoritative version list. Concretely:

- `RunHeader`'s `hasTags`/`VersionMenu` gate (`RunHeader.tsx:279,369,376`) should key off
  `runFamily.members.length > 1` (threaded down from `PreviewPanel`, which already has it),
  not off `tags.length`.
- The menu should list every `FamilyMember` (by `revision_index`), independent of whether it has
  a `git_tag`. A member with a tag resolves ref-scoped content as today; a member without one
  falls back to whatever non-git snapshot exists (or shows an explicit "no snapshot for this
  version" state) instead of being silently omitted.
- Separately and regardless of the above: `finalize_terminal_run`'s tag step
  (`engine.py:2349-2456`) already distinguishes failure from success carefully (the "no orphan
  tags" design) — the gap is that nothing LATER notices or heals a member whose tag never landed
  or whose sandbox `.git` was rebuilt out from under it. A reconciliation pass (or at minimum a
  loud operator-visible signal, mirroring the existing `logger.error` at `engine.py:2440-2449` for
  same-run failures) would make mechanism (2) detectable instead of silent.
