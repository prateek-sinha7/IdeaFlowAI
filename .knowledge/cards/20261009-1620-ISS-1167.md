# ISS-1167

INFERRED sibling of [ISS-1155](20261009-1420-ISS-1155.md) (register QA-KB-119), derived from its root cause: the endpoint
hands the browser the whole durable log, and the browser has no way to cope with a log this size. Fixing the server side
alone (paging) leaves most of this cost in place, which is why it is its own card.

## Condition

A run whose `run_events` log is very large. The local corpus has one: run `78e185fb-c032-4154-8552-774781b6e5df`
(type `backlog`, completed, root of an 8-run revision family), 107,409 events, 52.9 MB.

- Opening that run from history: `handleSelectWorkflowRun` fetches the whole log (`frontend/src/app/[...view]/page.tsx:3103`)
  and replays it frame by frame in one synchronous loop (`:3108-3121`, `handleWebSocketMessage(..., true)`).
- Opening ANY of its 7 revisions: the family seed fetches every other member's whole log (`page.tsx:3205`; the launch
  remount path does the same, sequentially, at `:3765`) and then keeps only `chat_message` / `chat_reply` (`:3223-3225`, `:3767`).
  For this family that is 14 events, 4,581 B, out of 52.9 MB (`evidence/qa-kb-119/03-analysis-event-shape.txt`).

## Expected vs actual

Expected: the cost of reopening a completed run tracks what the screen shows, and a consumer that wants chat frames pays
for chat frames. Actual: every consumer pays for the whole log, and the primary replay pushes 107,409 frames through the
reducer without yielding to the browser.

## Why the root cause implies it

Same unbounded response. After [ISS-1155](20261009-1420-ISS-1155.md) pages the server, `getRunEvents` still concatenates
the entire trace and returns one array, and the chat-only consumers still receive every event type. So the client half of
the cost survives the server fix.

## Read from code (CONFIRMED)

- One buffered body: `request<T>` ends in `return response.json()` (`frontend/src/lib/api.ts:593`); `getRunEvents`
  then maps every row into a new object spreading its payload (`api.ts:1486-1505`).
- Frame mix on the large run (`03-analysis-event-shape.txt`): `agent_thinking` 87,073 + `agent_chunk` 18,640 =
  105,713 of 107,409 events (98.4%) and 83.2% of payload bytes. These are streaming deltas.
- Per-frame reducer work: `case "agent_thinking"` calls `setPipelineState((prev) => ...)` and copies `prev.agents` for
  every frame (`frontend/src/hooks/useWorkflow.ts:1044-1066`).
- The client gives up after 30 s: `REQUEST_TIMEOUT_MS = 30_000` (`api.ts:345`), enforced by an `AbortController` that is
  cleared once `fetch()` resolves (`api.ts:501-522`). For this endpoint the headers arrive only after the whole body is
  built (TTFB 4.38 s vs total 4.40 s), so the server's compute time counts against that budget.
- Related and already filed: the per-member chat-only fetch is [ISS-805](20260922-1647-ISS-805.md) (INFERRED there, never
  measured past 2 members); the replay-triggered refetch cascade was [ISS-785](20260922-1620-ISS-785.md).

## INFERRED, with what settles each

- **A multi-second main-thread task and a large JS heap** when the root is opened: `JSON.parse` of 53 MB, a 107k-row map,
  then 107k synchronous reducer calls, all in one task. Settle: real Google Chrome (not Chrome for Testing), Performance
  panel, open `/runs/78e185fb-c032-4154-8552-774781b6e5df`; record the longest task and the heap peak. Repeat on revision
  `b40eabd0-d7e2-4bc2-bc42-99ef6a147bff` (download, parse and map of the root, no reducer replay) to split the cost.
- **A larger log, or the same one under load, trips the 30 s client abort while the server keeps going.** The abort
  rejects with `Request timeout after 30000ms (aborted)` (`api.ts:515-517`), but the in-line server work cannot be
  cancelled ([ISS-1155](20261009-1420-ISS-1155.md) root cause, step 3), so a retry queues a second stall behind the first.
  Settle: the REST time scales linearly (4.4 s at 107k events), so a log about 7x larger, or this one with the loop busy,
  should show the abort.
- **Whether a completed run's reopen needs the delta frames at all** is a product/UX call (does the Steps tab have to show
  the full thinking text of a finished run?). Not decided here.

## Fix location

1. Chat-only consumers (`page.tsx:3205`, `:3765`, `:1691`): a server-side type filter on the same endpoint
   (`?types=chat_message,chat_reply`) turns 52.9 MB into 4.6 KB for this family. It belongs in the same change as
   [ISS-1155](20261009-1420-ISS-1155.md)'s `limit`, so the response shape is touched once. `ScopedStore.read_events_of_types`
   (`backend/agents/authz.py:461-509`) is the precedent, but its `limit` keeps the LAST n rows, so a forward-paged
   typed variant is needed, with the same `_scope_owner_ws` filter.
2. The two full-trace replay loops (`page.tsx:3108-3121` and the remount replay near `:3706`): yield to the browser between
   chunks of frames (an `await` of a macrotask every few thousand frames), so no single task spans the whole log.
3. If the delta frames are not needed for a terminal run (the product question above), exclude them server-side instead,
   which also removes 83% of the bytes.

## Update (5-fixer, QA-KB-119, 2026-10-09)

Still open. [FIX-778](20261009-1653-FIX-778.md) paged the server: `getRunEvents` now walks `after=<next_after>&limit=5000`
and still returns the whole log as one array, so every cost on this card remains on the client. Not done there because the
consumers and replay loops are in `frontend/src/app/[...view]/page.tsx`, which QA-KB-110's cards were changing in the same
tree, and the delta-frame question above is a product call.

Measured for the page size, run 78e185fb, `evidence/qa-kb-119/fix-02-paged-walk-probe.txt`: a full walk at `limit=5000`
is 22 requests in 6.68 s with `/health` worst 392 ms (5 of 25 probes over 300 ms); at `limit=1000` it is 108 requests in
12.67 s with `/health` worst 208 ms. Lowering the client page is one constant in `getRunEvents` if the 300 ms bar should
hold during a reopen too.
