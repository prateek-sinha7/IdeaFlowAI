# ISS-778

## Title

[ISS-775](20260922-1330-ISS-775.md)'s confirmed root cause for QA-SG-004 (the Notifications bell
panel) is not specific to that panel: the header's own "N Running" dropdown entries and the
single-run badge reach the exact same unguarded code, so a second live-to-live switch from either
of them, starting from an already-viewed live run's own `/runs/<id>/stream` page, should fail or
delay the identical way.

## Why ISS-775's root cause implies this

[ISS-775](20260922-1330-ISS-775.md) traced the bell panel's `onViewResults` handler
(`DashboardLayout.tsx:2757-2791`) to a shared shape: call `onSwitchToLiveRun(targetRunId)`
without awaiting it, then unconditionally `router.push(routes.runStream(targetRunId))`, which
remounts `page.tsx` (confirmed live, `page.tsx:3374-3378`) and races `handleSwitchToLiveRun`'s own
in-flight `getRunEvents` replay — once the pre-remount instance's `mountedRef` flips to `false`
(`useRunStateStore.ts:335`), `getOrCreate`/`getAgentStartTimes` hand that replay a throwaway object
instead of the real module-scope map (`useRunStateStore.ts:392-397, 404-410`), so recovery depends
entirely on the fresh instance's own independent replay (T11, `page.tsx:3458-3608`).

The header exercises the identical implementation, confirmed by direct reads, not inference:

- `AppHeader.tsx:391-401` — the "N Running" dropdown row `onClick` calls `handleRunClick(serverRun)`
  when the run is already in `recentRuns`, and falls back to `onViewResults?.(pipeline)` at `:404`
  otherwise — i.e. the dropdown can land in [ISS-775](20260922-1330-ISS-775.md)'s own call path
  directly.
- `AppHeader.tsx:313-326` — the single-run badge `onClick` has the same two-branch shape:
  `handleRunClick(serverRun)` at `:316`, or a direct `onSwitchToLiveRun(runId)` +
  `onGoToPipeline?.(runId)` pair at `:321-324` when `serverRun` is not yet resolved.
- `AppHeader.tsx:229-245` (`handleRunClick`) — both surfaces funnel into this one handler:
  `onSwitchToLiveRun(run.id)` then `onGoToPipeline?.(run.id)`, with no await between them and no
  check of what page is currently mounted.
- `DashboardLayout.tsx:2723-2735` (`onGoToPipeline`, the one implementation FIX-519 already patched
  for the stale-closure/reflow defects) — `onSwitchToLiveRun?.(runId); setMainView("execution");
  router.push(routes.runStream(runId));` — the exact same "fire, then push, unconditionally" shape
  `onViewResults` has, now confirmed to matter because of the remount, which is a DIFFERENT hazard
  than the one FIX-519 fixed.

FIX-519's own regression suite (`AppHeader.iss647.test.tsx`,
`AppHeader.runningDropdownSnapshot.test.tsx`) is unit-level React Testing Library coverage: it
asserts which `runId` a callback receives, never a real Next.js client-side navigation, so it
cannot observe a `page.tsx` remount and never exercised this mechanism at all. The header paths
were not verified against it, they were simply never asked the question.

## Expected (once reproduced)

Clicking a second, different live run's dropdown entry or badge, while already viewing a different
live run's own stream page, navigates there immediately and reliably — the same guarantee
[ISS-775](20260922-1330-ISS-775.md) expects of the bell panel.

## Actual (inferred, not yet observed independently)

The same silent no-op (URL and content stuck on the previously-viewed run) or multi-second delay
[ISS-775](20260922-1330-ISS-775.md) reproduced 3/3 for the bell panel, since both surfaces call the
identical `onSwitchToLiveRun` + unconditional `router.push` pair with no re-entrancy guard.

## What would confirm this

1. Launch 2+ concurrent live runs. Click one to view it (first click, `/dashboard` -> live run —
   per [ISS-775](20260922-1330-ISS-775.md) this always works).
2. From that run's own `/runs/<id>/stream` page, open the header's "N Running" dropdown (or, with
   exactly one other run live, use the single badge) and click a DIFFERENT live run.
3. Compare against [ISS-775](20260922-1330-ISS-775.md)'s own repro cycles: does the URL/content
   stay stuck, or does it lag several seconds before correcting?
