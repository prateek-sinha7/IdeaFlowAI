# ISS-1000

## Description

INFERRED sibling of [ISS-347](20260828-2058-ISS-347.md) (root of QA-KB-062). The mechanism is
read in code (CONFIRMED by file:line) and reproduced offline against the real `LaunchWizard`
(`evidence/qa-kb-062/analysis-proof-launchwizard-chain.out.txt`, case R2). It is not reproduced
live: the trigger is a chain hand-off that no wizard mount consumed (an abandoned chain push).

ISS-347 is about WHICH brief the wizard shows. This is the second consequence of the same
unscoped read, and it decides what the launch DOES: the wizard arms "chaining mode" from a
leftover `chain.from`. The pickup effect reads it on every mount, in a different effect from
the one that reads the draft (`frontend/src/components/workflow/LaunchWizard.tsx:381-385`):

```ts
const from = sessionStorage.getItem("chain.from");
if (from) {
  setChainFrom(from);
  sessionStorage.removeItem("chain.from");
}
```

`isChaining = Boolean(chainFrom)` (`:369`) then changes an open that is not a chain:

1. The brief editor is not rendered (`{!isChaining && (` at `:1207`) and the banner
   "Continuing from your ... — your brief is pre-filled." is (`:1147-1153`): the user can
   neither see nor edit the brief.
2. `handleLaunch` reads the leftover `chain.source_run_id` (`:1002`):
   `const sourceRunId = isChaining ? (sessionStorage.getItem(CHAIN_SOURCE_RUN_ID_KEY) ?? undefined) : undefined;`
3. That id travels `buildLaunchDraft` (`frontend/src/lib/launchDraft.ts:125`), then
   `frontend/src/app/[...view]/page.tsx:2524`/`:2558` (prototype) and `:2607`/`:2642` (ppt),
   then `frontend/src/components/layout/DashboardLayout.tsx:1429` (prototype) / `:1500` (ppt),
   and leaves as `source_workflow_run_id` on the launch request.

Backend (read, not exercised): `admit_chain_launch` (`backend/app/api/run_commands.py:5310-5372`)
acts on the id only for a workflow whose manifest declares `deliverable.chains_from: true` —
`prototype` (`backend/agents/workflows/prototype/workflow.yaml:46`), `ppt_v2` (`:60`), plus
`backlog` and `user_stories`. A leftover id is then looked up by owner: deleted or foreign ->
404 "Workflow run not found"; still running -> 422 `source_running`; non-chainable -> 422
`source_non_chainable`; otherwise ADMITTED, and the unrelated new run is minted with
`source_run_id = <stale id>` (`run_commands.py:3081`) and the stale source's payload is
installed into `.context/` before agent 1 (`:3234-3238`,
`backend/agents/capabilities/context_providers/chain_context.py:163`). `ppt`
(`workflow.yaml:45-52`, deliberately undeclared) and `prototype_v2` (no declaration) are zeroed
by the declaration gate (`run_commands.py:5310-5312`), so only the UI half applies to them.

This is the LIVE replacement for the half of ISS-347 that no longer holds: its
`chain.context_block` appended to the next run was removed from the wizard in `e7305f9dd`
(2026-09-10) — see the Analysis section on ISS-347.
[BUG-014-GROUNDED-CONTEXT](20260716-2156-BUG-014-GROUNDED-CONTEXT.md) closed the same leak by
gating the `chain.source_run_id` read on `isChaining`; a leftover `chain.from` re-arms exactly
that gate. [FIX-003b](20260616-FIX-003b.md) is the earlier "stale chain.from hides the brief
textarea" instance. (BUG-014's "hidden child run via parent_run_id" is no longer the backend
behaviour: a chained run gets `source_run_id`, not `parent_run_id`, `run_commands.py:3027-3031`.)

## Why the root cause implies it

ISS-347's root is that every `chain.*` key is ambient session state with no tie to the
navigation that wrote it. `chain.from` is one of four such keys and the only one that switches
the wizard into a different mode. Fixing only the `chain.brief` early return leaves it armed:
offline, with the draft applied and no `chain.brief` present, the editor is still hidden and
`sourceRunId` still launches (case R2).

## Expected vs Actual

- **Expected:** a wizard open that is not the target of a chain push behaves as a plain open —
  brief editor visible, no chaining banner, no `source_workflow_run_id` on the launch.
- **Actual (R2, executed):** `{"briefEditorVisible":false,"continuingBanner":true}` and the
  launch draft carries `"sourceRunId":"stale-run-id"` although the caller staged only `{ brief }`.

## Where the fix belongs

The wizard reader, in the same decision as ISS-347 — not in the callers. `chainFrom` must be
set only when the chain hand-off is the one being applied. A fix confined to the restore effect
(`:403-450`) cannot undo it, because the pickup effect (`:372-395`) runs first and has already
armed `isChaining`. The backend gate is correct to refuse a bad source and stays as is.

## Resolution: FIX-723 (2026-10-07)

Resolved by [FIX-723](20261007-1810-FIX-723.md), in the same decision as ISS-347.

- **What changed.** When the caller staged a draft for this mode, the pickup effect removes `chain.from` and
  `chain.source_run_id` before reading `chain.from` (`LaunchWizard.tsx:403-410`). `isChaining` therefore never arms,
  the brief editor shows, and `handleLaunch` sends no `sourceRunId`.
- **Tests.** `LaunchWizard.chain.test.tsx` ISS-1000 case: the it.fails body now passes. Proof R2 is green.
- **Still open: ISS-1001 B1.** A stale `chain.from` on a DRAFT-LESS open (proof R4) still arms chaining. With no draft
  to win, the reader cannot tell it apart from a genuine chain. That case is
  [ISS-1001](20261002-0500-ISS-1001.md) B1 and needs writer-side scoping.
