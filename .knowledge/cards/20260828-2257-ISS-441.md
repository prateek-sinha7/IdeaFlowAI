## Why this must also be broken

[ISS-318](20260828-1956-ISS-318.md) (root of `BUG-20260828-092630-library-agents-id`) established that
`AgentCapabilitiesModal` (`frontend/src/components/workflow/AgentsPopup.tsx`) renders the Library
agent-detail drawer for a catalog agent that has "nowhere to write back" — a description that applies
just as much to the drawer's **Hooks** tab, one tab over from the Skills tab this bug reports on, as
to the Skills tab itself. Tracing that adjacent tab shows it is broken by a different, and in one way
worse, mechanism.

### Root cause (CONFIRMED — every line below was read)

`AgentCapabilitiesModal`'s props include an explicit pass-through pair for hooks:

```tsx
// AgentsPopup.tsx:485-490
export function AgentCapabilitiesModal({
  agent, agentIndex, onClose,
  attachedHooks: propHooks,
  onAttachHook: propAttachHook,
  onSkillsChange,
  ...
```

but two lines later they are unconditionally shadowed:

```tsx
// AgentsPopup.tsx:526-532
const { hooks: HOOKS, events: HOOK_EVENTS } = useHooksCatalog();
// Always use context — works from Library page, Add agent modal, and AgentsPopup.
// HOOKS ONLY since ADR-0010; skills come from `agent.skills` and are written
// back through `onSkillsChange`, not through this context.
const ctx = useSkillsHooks();
const attachedHooks = ctx.attachedHooks;
const onAttachHook = ctx.attachHook;
```

`propHooks`/`propAttachHook` are destructured and typed (`AgentsPopup.tsx:497-498`) but never read again
anywhere in the file (`grep -n "propHooks\|propAttachHook" AgentsPopup.tsx` — no hits past the
destructuring) — dead parameters. Every mount of `AgentCapabilitiesModal`, **regardless of caller**,
reads and writes the one shared `useSkillsHooks()` context. Unlike the Skills tab, there is no
`readOnly`-equivalent flag anywhere in the Hooks tab's render (`AgentsPopup.tsx:809-856`, the whole
`drawerTab === "hooks"` block) — the "Attach" button is always enabled:

```tsx
// AgentsPopup.tsx:830-840
<button
  onClick={() => handleAttachHook(hook)}
  disabled={attached}
  ...
>
  {attached ? <><Check className="h-2.5 w-2.5" /> Added</> : <><Plus className="h-2.5 w-2.5" /> Attach</>}
</button>
```

`handleAttachHook` / `isHookAttached` (`AgentsPopup.tsx:595-603`):

```tsx
const isHookAttached = (id: string) => attachedHooks.some(h => h.id === id);
const handleAttachHook = (hook: HookDef) => {
  if (isHookAttached(hook.id)) return;
  onAttachHook?.({
    id: hook.id, name: hook.name, event: hook.event, trigger: hook.trigger,
    description: hook.description,
  });
};
```

The object written into `attachedHooks` carries no `agentId` (or any field identifying which agent's
drawer the click came from), and `isHookAttached` matches on `hook.id` alone, globally. The sink itself,
`SkillsHooksContext.tsx:41-54`, is a plain `useState<AttachedHook[]>([])` inside `SkillsHooksProvider`,
which is mounted once at `frontend/src/app/layout.tsx:44` — **above the router**, wrapping the entire
app for the lifetime of the browser tab. The context's own doc comment confirms the intent
(`SkillsHooksContext.tsx:20-24`): "HOOKS ARE DELIBERATELY UNCHANGED and remain run-level... read it as
'the run-level attachment context'" — i.e. a bag meant to be read by `startPipeline` when an actual
pipeline is launched, not a per-catalog-agent preview store. `LibraryPage.tsx`'s
`AgentCapabilitiesModal` mount (`LibraryPage.tsx:1030-1050`, the same one ISS-318 covers) passes neither
`attachedHooks` nor `onAttachHook`, so it falls straight into this shared context exactly like every
other caller.

## Expected vs actual

**Expected:** either "Attach" in a catalog-browse drawer (an agent belonging to no pipeline, same
framing ISS-392 uses for the Config tab) does not present as if it durably and specifically attaches
the hook to *this* agent, or the attachment is real, scoped to the agent, and correctly gated the same
way the Skills tab is supposed to be (`readOnly={!onSkillsChange}`, ISS-318's fix target) when there is
nowhere to write it.

**Actual (INFERRED — not yet independently reproduced in a browser):** clicking "Attach" on any
Suggested Hook in the Library agent-detail drawer flips that hook to a disabled "✓ Added" state
immediately — the same convincing, badge-like success signal the Skills tab gives — but the write lands
in one global list with no per-agent key. Opening a **different** agent's Library detail drawer should
show the same hook already "✓ Added" there too, never having been attached to that agent specifically.
Because `SkillsHooksProvider` sits above the router, this should survive client-side navigation to other
pages within the same tab (unlike Skills' `savedSkillsRef`, which is scoped to `LibraryPage`'s own mount
lifetime) but — being a plain `useState` with no persistence backing — should still be lost on a hard
reload, matching this bug's core "convincing feedback, nothing durable" shape. It also means a hook
casually previewed from the catalog page could ride into whatever pipeline the composer/wizard is
separately reading `useSkillsHooks()` for (`AgentsPopup.tsx:899`, `:2310` are two other readers of the
same context).

## What would confirm or refute this

Open `/library/agents/<agentId>` for two different agents in the same tab (no reload between). On
agent A's Hooks tab, click "Attach" on a suggested hook; close the drawer; open agent B's Hooks tab and
check whether that same hook (if also suggested for B) already shows "✓ Added" with no click. A miss —
each agent's Hooks tab shows only what was actually attached to it — would mean some per-agent
filtering exists that this read did not find, refuting this card without affecting
[ISS-318](20260828-1956-ISS-318.md).

## Where the fix belongs

Same shared component the whole family already points at —
`AgentCapabilitiesModal` (`AgentsPopup.tsx`) — once. The dead `propHooks`/`propAttachHook` parameters
suggest per-agent/per-caller hook scoping was intended but never wired through; either restore that
(thread real per-agent props instead of the shadowed context reads) or gate the Hooks tab's "Attach"
control behind the same kind of "nowhere to write back" check the Skills tab documents but currently
fails to enforce correctly (ISS-318). A guard here closes it for both production callers
(`LibraryPage.tsx:1030`, `AgentLibrary.tsx:335`) at once, matching the "fix once, where all callers
route through" shape [ISS-392](20260828-2250-ISS-392.md) and
[ISS-393](20260828-2251-ISS-393.md) already established for the Config tab on this same drawer.
