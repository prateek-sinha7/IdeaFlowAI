# FIX-379

**Register source:** `BUG-20260828-085400-runs-failed` in `bug-hunter/ledger.md`.

## What was wrong

Reopening a terminal run ("Reopen & fix from the failed step" on a failed run,
"Run Again" on a cancelled one — both `handleResumeRun`) genuinely resumes it:
`GET /api/runs/{id}` flips to `generating`, the header badge reads "Running" and
the sub-header streams. The Steps tab's status summary, a few pixels away on the
same screen, stayed pinned on **"Run failed · 1 / 4 agents · 3s"** for the whole
live run. Reproduced 3/3 on cold starts by the validator.

## Root cause

`frontend/src/hooks/useWorkflow.ts:458` — the `pipeline_start` reducer's
same-run re-announce branch merged each carried agent as
`{ ...existing, ...identity }`, spreading `status` and `error` forward
unconditionally from the pre-resume attempt. The resume supersedes that
evidence, but nothing cleared it: only that specific agent's own `agent_start`
event (`useWorkflow.ts:573-594`, pre-change numbering) ever reset it, which is
tens of seconds into the resume when earlier agents run first — matching the
~20s window observed.

Every reader of the resulting polluted `pipelineState.agents` array showed the
re-running agent as failed. `StepsOverviewSpine.tsx:342` is only where the
reported symptom surfaced:

```ts
const failed = pipelineState?.failed || agents.some(a => a.status === "error");
const statusLabel = failed ? "Run failed" : isRunning ? "Running" : "Run complete";
```

`failed` is evaluated before `isRunning`, so the label never fell through to the
"Running" branch.

## What changed and why there

**1. `frontend/src/hooks/useWorkflow.ts:458` — the shared reducer (root cause).**
When a carried agent's `status` is `"error"`, it is reset to the same rule the
non-carried roster branch already uses (`status: idx < resumeOffset ? "done" :
"idle"`, `error: null`) instead of being spread verbatim. This is the treatment
the top-level `cancelled`/`failed`/`degraded` markers already get a few lines
below. Everything else about the carried agent (its output, thinking, duration)
is still carried — ISS-075's merge semantics are untouched, and a non-errored
agent takes the byte-identical old path.

One guard there is where all callers route through, and it covers the whole
blast radius the analyzer grepped: `StepsOverviewSpine`'s other three read sites
(`:385` failedAgent, `:429` progress-bar segment, `:487` per-row style),
`RunChatLane.tsx:579` (PipelineMini's live pip, [ISS-438](20260829-0056-ISS-438.md)),
`AgentDetailPanel.tsx:947` (`isError`, [ISS-439](20260829-0057-ISS-439.md)), and
the degraded-run entry path ([ISS-440](20260829-0058-ISS-440.md)) whose
`pipeline_complete` stamps `status: "error"` on every `agents_failed` id and then
hits this same merge.

**2. `frontend/src/components/results/StepsOverviewSpine.tsx:342` — the label's
own guard.** `failed` is now `!isRunning && (pipelineState?.failed ||
agents.some(a => a.status === "error"))`. This is [ISS-317](20260828-1755-ISS-317.md)'s
first-named fix direction and the invariant the regression test asserts: a
pipeline that is actively running is never "failed", whatever per-agent status
the array happens to hold. It also stops the "Pipeline halted" banner (`:584`),
the "Not run" chips (`:532`) and the X-circle status icon (`:401`) — all derived
from the same flag — appearing mid-run.

`DashboardLayout.tsx:845`'s completion effect reads the same pattern but is
already gated behind `!pipelineState.isRunning` (`:837`), so it was correct
before and is unchanged.
