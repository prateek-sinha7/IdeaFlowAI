# ISS-080

## Title

The revision banner back-fills but over-counts: it renders "Spec Revision Cycle 5" on a run that had 2 revision cycles. FIX-221 fixed the right half of ISS-063 — the banner now appears on a fresh load, where before it never appeared at all — but the derived number is wrong, which is the same over-counting class FIX-164 originally existed to fix ("Cycle 6 after one click"). Ground truth for run d5dbc9f2-dbe8-480f-8b13-788794a6788e: agent_start counts are prototype-specify 3, prototype-plan 2, prototype-analyze 2, and artifact_refs holds spec v1/v2/v3 — so the correct derived value is 3 − 1 = 2. The UI shows 5, which is exactly (3 × 2) − 1. Hypothesis (to be confirmed, not yet proven): every durable frame reaches the reducer TWICE on a reopen — the REST replay in dashboard/page.tsx and the SSE replay from seq = 0 both deliver it — so useRunStateStore.handleFrame's accumulate-restarts derivation is not idempotent under double delivery, despite FIX-221's claim that it is a pure function of accumulated frames. If that holds, the fix is to dedupe by event seq (or derive from a set of unique seqs / the artifact_refs version count) rather than to accumulate. Do NOT revert FIX-221 — the back-fill half is correct and was the substance of ISS-063; only the derivation is wrong. Note the lesson: FIX-221 shipped with 15 green tests and still over-counts live, because no test replays the same frame twice.

## Source / evidence

Observed by me in a live headless-browser pass on 2026-08-12 against the running stack (backend :8010 on current code, frontend :3000), reopening the run from Run History on a fresh load. Screenshots live-03-run.png / live-05-agent-detail.png; driver scripts live-verify.mjs / live-picker.mjs. Counts read directly from backend/dev.db run_events. ROOT CAUSE PROVEN 2026-08-12 — the hypothesis above is confirmed. useWorkflow.ts:369-376 does agentStartCounts[agentId] += 1 with no identity key, so it counts *events*, not *distinct* events; deriveSpecRevisionCount (useWorkflow.ts:213-219) is then max − 1. On reopen the same durable event reaches the router twice (REST replay + SSE replay). A dedupe seen-set exists and should have stopped the second copy, but the trailing same-run pipeline_start fires resetReplayState (page.tsx:774) which wipes the seen-set mid-replay — measured at 24,783 discarded ids, exactly 24791 − 9 + 1. Replaying the real log through the real reducer gives 2 for one pass and 5 for two, reproducing the screen exactly. Fix: key the counter on event_id as a set, never += 1 — that is immune to any multiplicity. The artifact_refs-derived alternative was considered and rejected (extra fetch, workflow-specific kind, SC-001). Shares its trigger with ISS-075 and must ship with it, plus the shared "skip resetReplayState for a same-run frame" predicate. See also ISS-081, a second and independent defect in the same expression. CLOSED 2026-08-12 by FIX-225 (commit c46c8160), with BOTH halves the investigation recommended. (1) Identity: agentStartCounts (a bare += 1) is REPLACED by agentStartEventIds: Record<agentId, string[]> — a SET of durable event identities (event_id, else seq; unstamped legacy frames stay un-deduped exactly as shouldApplyEvent treats them), so the value is a function of the SET of events and immune to ANY multiplicity from ANY transport. (2) Class: page.tsx no longer calls resetReplayState for a pipeline_start naming the run this tab is already tracking, so the seen-set is not wiped mid-replay and the SSE pass is fully deduped against the REST pass. The predicate is captured BEFORE the launch-window block re-points trackedRunIdRef, or a fresh launch would misread as "same run"; the four sibling clears (reviewGateData / questionnaireData / activePipelineRunId / lastCancelledRunId) are deliberately left running. LIVE PROOF: the banner now reads "Spec Revision Cycle 2" (was 5) on run d5dbc9f2. Pinned by 3 new cases (double + triple delivery + the per-agent tally), all seen RED at 5 / 8 / {6,4,4}. The page.tsx:837-841 contradiction flagged as unresolved in the investigation is now EXPLAINED: the REST-replayed agent_* frames really cannot reach the store directly (the inner frameRunId const shadows the function parameter and is undefined for them), but they DO reach useWorkflow.pipelineState via handlePipelineMsgRef at :897 (isForActiveRun is true precisely because that id is undefined) — and the FIX-201 bridge effect at page.tsx:1640-1649 then pushes that whole state object into the store wholesale (runStore.updatePipelineState(runId, () => pipelineState)). The SSE pass increments on top of the copied base. That is the transfer step; no third delivery path exists.
