# ISS-705

## Description

This is bug **QA-PS-025** (`BUGS.md#qa-ps-025`, ledger title: "Custom workflow
agents that require task_loop strategy receive no task injection — runs as
single_shot with no task context, produces placeholder output").

`backend/agents/workflows/prototype/workflow.yaml` wires `prototype-build`
with `strategy: task_loop` and `task_source: {source_step: prototype-plan,
parser: heading_tasks}` — this is what lets a worker consume a planner's
`## Task N:` headings one at a time, appending to a single persisted file
across calls. When a user replicates that same planner->worker shape inside
the custom composer (`/create/custom`), the composer offers exactly one
connector lever, "Fan out over a list" (`frontend/src/components/workflow/AgentsPopup.tsx`
~line 1392-1398), whose `strategy` field is typed
`"fanout_batch" | "wave_scheduler"` — `task_loop` is not a member of that
union and is never sent in `selections`. Downstream,
`backend/agents/execution_engine/engine.py` `_apply_selections` only overlays
`strategy`/`task_source` when `sel.get("strategy")` is truthy
(`if sel.get("strategy") and user_step.strategy: patch["strategy"] = ...`),
so even though the overlay mechanism itself is generic and would happily
carry `task_loop` through, nothing in the composer UI can ever produce that
selection. The composer cannot auto-infer the connection either — the base
`custom/workflow.yaml` template has no task-consuming step at all (its 9
fixed steps are all `single_shot`, and the one step that emits tasks,
`task-list-planner`, is deliberately last with no downstream consumer).

## Reproduction (3/3, cold start each cycle)

**Cycle 1 (full live run, run id `3ba6bf05-430e-4d0e-bdcf-d3eadf3da756`).**
Cold nav to `/workflows/new` -> composed Spec Writer Agent (`prototype-specify`)
-> Task Planner Agent (`prototype-plan`) -> Build Agent (`prototype-build`,
added as sub-agent of the planner). Selected the Build Agent node, opened its
Config tab: the ONLY lever offered to connect it to the planner's task list
is "Fan out over a list" (toggling it reveals `Fan-out mode: Batch — one pass
| Waves — dependency-ordered`, and `Task source agent: Task Planner Agent`,
`Task source type: ## Task headings`) — no `task_loop` option exists anywhere
in the panel. Ran the composed workflow (brief: coffee-subscription landing
page). Task Planner correctly emitted 6 `## Task N:` headings and the fan-out
wiring correctly targeted them (`prototype-plan → Build Agent` shown in the
Steps panel). But because `fanout_batch` spawns independent workers per task
rather than task_loop's single continuously-appended-file worker, and none of
those workers had `write_file` (ISS-698), the final task's worker ("Task 6:
Final Wiring & Validation") could not find `prototype.html`/`spec.md` from
earlier tasks, narrated its own confusion ("the previous tasks haven't been
completed or the files were not persisted... write_file is not available"),
and then fabricated a "Task 6 Complete" checklist claiming a fully-built,
validated prototype that was never written anywhere. That fabricated
narration became the run's `output.md` deliverable — exactly the "no task
context, placeholder output" symptom QA-PS-025 describes, just one layer
down: the worker DOES receive per-task text (fanout_batch's task_source
works), but the missing task_loop continuity + missing write_file combine to
make its output indistinguishable from a placeholder.

**Cycles 2 and 3 (fresh cold nav to `/workflows/new` each time, no run
needed — the gap is a static UI/type fact, not a run-to-run variable).**
Rebuilt the identical Spec Writer -> Task Planner -> Build Agent composition
from scratch each time and reopened the Build Agent's Config tab: both times,
"Fan out over a list" (`Batch — one pass` / `Waves — dependency-ordered`) was
still the only connector lever offered — `task_loop` never appears as an
option, confirming the gap is deterministic (a TS union in
`AgentsPopup.tsx`), not timing- or data-dependent.

## Expected vs Actual

Expected: the composer either exposes `task_loop` as a selectable strategy
(with `task_source`) for a step downstream of a task-emitting agent, or
auto-infers it when the user connects a planner to a worker — matching what
the native `prototype` pipeline does.

Actual: the composer can only wire `fanout_batch`/`wave_scheduler`, which
runs each task as an independent worker with no shared incremental state,
producing broken/fabricated output on any planner->worker pair that expects
task_loop's single-file continuity (e.g. any composer replica of the
`prototype-plan` -> `prototype-build` shape).

  (`if sel.get("strategy") and user_step.strategy: patch["strategy"] = ...`)
  — confirms the overlay is generic but gated entirely on the FE ever sending
  a `strategy` value, which it cannot do for `task_loop`.
- `backend/agents/workflows/prototype/workflow.yaml:68-76` — the native
  `prototype-build` step's `strategy: task_loop` / `task_source:
  {source_step: prototype-plan, parser: heading_tasks}` declaration that the
  composer has no equivalent for.
- `backend/agents/workflows/custom/workflow.yaml` — the base custom template:
  9 steps, all `single_shot`, no task_loop step, `task-list-planner` last
  with no consumer.
- Live run `3ba6bf05-430e-4d0e-bdcf-d3eadf3da756` (qa-admin, 2026-09-22): Task
  Planner step output has a correctly-parsed 6-item task plan; Build Agent's
  final fan-out worker output (visible on the Preview tab, deliverable
  `output.md`) opens with "Reading the current state of the prototype and
  running final validation checks... It seems there's confusion about the
  file structure... write_file is not available... let me report task
  completion" followed by a fabricated "Task 6 Complete" checklist.
- `evidence/qa-ps-025/` — browser snapshots from all 3 cold-start cycles.
