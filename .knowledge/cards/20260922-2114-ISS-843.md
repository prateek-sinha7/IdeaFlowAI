Validated QA-PS-051 (LEDGER.md / BUGS.md#qa-ps-051). Confirmed 3/3 from cold
start in `lane3` Chrome as `qa-admin@flowinqa.com`.

### Reproduction that worked (all 3 cycles identical, no axis variance needed)

1. Cold navigate to `/library`.
2. Wait for the catalog to render, click a library card (e.g. "Architecture
   Agent", agent id `material-analyzer`) to open its detail route
   (`/library/agents/material-analyzer`).
3. Capture `mcp__lane3__browser_network_requests` filtered to
   `runs\?limit=50|auth/me`.

Every one of the 3 cycles showed the identical shape:

```
GET /api/auth/me          — index 65 — fired ONCE (on /library mount)
GET /api/runs?limit=50    — index 67 — fired on /library mount
GET /api/workflows        — index 68
GET /api/agents/library   — index 69
GET /api/skills/library   — index 70
GET /api/hooks/library    — index 71
GET /api/runs?limit=50    — index 73 — fired AGAIN on the detail-route mount
```

Also reproduced on a skill detail (`/library/skills/accessibility`) with the
identical two-call shape.

### Named trigger

**Entry path matters.** A cold, direct deep-link straight to
`/library/agents/<id>` (no prior `/library` visit in the tab) fires
`GET /api/runs?limit=50` only ONCE — there is no prior list-page mount to
already own the fetch. The duplication requires: `/library` list mounts
first (fetching `runs?limit=50`), THEN a client-side navigation into any
`/library/agents|skills|hooks/<id>` detail route re-fires the same fetch.

### Root cause

`frontend/src/app/[...view]/page.tsx:1021-1040` — the `getWorkflows(token,
{ limit: 50 })` effect is guarded by a `useRef` (`recentRunsRequestedRef`,
declared line 828) intended to fire "once per mount" per its own ISS-793
comment (line 1023-1029). No dedicated `/library` route folder exists —
`find frontend/src/app -maxdepth 4 -type d` shows only `[...view]`, `admin`,
`handoff`, `login`, `register`, `workflow` — so this catch-all page is the
only place `runs?limit=50` can originate for any library route.

The observed behaviour (ref resets between `/library` and
`/library/agents/<id>`) means the `[...view]` catch-all component itself
remounts when its segment array changes shape
(`["library"]` -> `["library","agents","<id>"]`), even though this is a
client-side navigation with no full page reload. Confirmed by evidence, not
by reading a remount-triggering line directly — the fix owner should verify
via React DevTools "Highlight updates" or a mount-count console log whether
this is a `key`-prop remount, a Suspense boundary reset, or something else
in how the catch-all resolves distinct segment arrays.

### Expected vs actual

- Expected: `GET /api/runs?limit=50` fires once total across a
  `/library` -> detail-view navigation (or never, since run history is not
  rendered on any library detail view).
- Actual: fires twice, 74 KB of run history the detail view never displays.

### Not reproduced as originally reported

`GET /api/capabilities` and `GET /api/me` are each called exactly ONCE per
navigation in the current codebase — no duplication observed on any of the
3 cycles. `/api/capabilities` is not even in the request set until the
Config tab is clicked, and fires once there. Only `GET /api/runs?limit=50`
duplicates. The original report's "capabilities×2, me×2, runs×2" appears
stale against HEAD — only the runs×2 / unneeded-run-history claim holds
today.
