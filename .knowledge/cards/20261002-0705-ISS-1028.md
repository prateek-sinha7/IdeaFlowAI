# ISS-1028

## Description

Sibling of [ISS-937](20261001-2231-ISS-937.md) (QA-KB-083), found by asking where else a gate is handed only a `User` row and so can only read the advisory projection. `_require_host_capacity(current_user: User)` (`backend/app/api/run_commands.py:2621`) takes no `Principal`, and decides the admin exemption from the column:

```python
decision = should_block_new_work(is_admin=getattr(current_user, "is_admin", False))   # run_commands.py:2655
```

[ADR-0013](20260916-ADR-0013.md) locks the opposite: "Effective tier and admin status come from the verified `cognito:groups` claim; `User.tier` and `User.is_admin` are advisory projections only." The handoff twin of the same gate already follows it: `backend/app/api/handoff.py:313` calls `should_block_new_work(is_admin=effective_is_admin(user, principal))`. The same decision is therefore made from two different sources depending on which door the request came through.

## Why the root cause implies it

Same flaw as ISS-937: an admission decision made from `users.*` because the helper never receives the token. The rationale written into the function is the part that went stale. Its docstring (`run_commands.py:2639-2642`) says the exemption "reads the advisory ``is_admin`` DB column, the same staleness window ``_require_tier_entitlement`` above already accepts for ``tier``". `_require_tier_entitlement` stopped accepting that window in Phase 2 of the Cognito migration (`run_commands.py:2571-2591`: "That argument did not hold up"), so the sentence now points at a window that no longer exists.

## Evidence

CONFIRMED, read:
- `run_commands.py:2621` signature `(current_user: User)`; `:2655` the `getattr` read; `:2639-2642` the docstring premise.
- `backend/app/services/capacity_state.py:382`: `should_block_new_work(*, is_admin: bool)` takes a plain bool, so passing `effective_is_admin(...)` needs no change there.
- `handoff.py:313`, the effective-flag twin.
- Seven call sites (AST map of `run_commands.py`): `launch_run :3514`, `create_revision :5634`, `resume_run_endpoint :704` and `post_message :2011` / `:2132` sit in handlers that already depend on `get_current_principal`. `_dispose_concierge_proposal :1642` is a helper that already receives `caller_tier` and would take an `is_admin` the same way. `user_message_shim :5957` depends on `get_current_user` only.
- Spec 014 records the column read as a decision, not an oversight. `specs/014-host-capacity-monitoring/plan.md:346-358` (D-02): "The exemption reads `current_user.is_admin` (the advisory DB column), not a live `cognito:groups` read, for one reason: the launch handlers take `Depends(get_current_user)` and threading `get_current_principal` through them would change signatures that ~25 existing tests override ... The exemption is a throttle bypass, not a privilege ... Upgrading to a live principal read is recorded as follow-up hardening". Both premises have moved: five of the seven sites now take the principal, and `_require_tier_entitlement` no longer reads the column.
- No guard can see it. `backend/tests/security/test_no_projection_reads.py` matches attribute reads only and this is a `getattr` call ([ISS-1029](20261002-0705-ISS-1029.md)). A one-off AST scan of `backend/app` for every read of `.tier` / `.is_admin` with any receiver found it to be the only decision-context read the guard cannot see; the others outside the guard's rule are `request.*` payload fields, `created.*` / `u.*` display or projection-write reads in `admin.py`, and a model's own `m.tier`.

INFERRED, not driven: the stale window itself. A token older than the last projection sync, still valid after an out-of-band group change, makes the exemption follow the newer column instead of its own groups. A column that is too high lets a non-admin token skip a capacity refusal (503 `host_capacity_exhausted`); one that is too low refuses an admin token. What settles it: a request whose principal's groups disagree with `user.is_admin`, with `HOST_CAPACITY_GATE_ENABLED` on and an engaged decision published.

## Expected vs actual

- Expected: every admin decision, on every door, reads `effective_is_admin(user, principal)`, as `handoff.py:313` does.
- Actual: `launch_run`, `create_revision`, `resume_run_endpoint`, `post_message` and `user_message_shim` ask the column.

## Fix direction

Decide first, because D-02 is a recorded decision: either reverse D-02 (the change below), or keep it and say so where the guard can see it (an allow-list line with a reason, and a corrected docstring).

To reverse it: give `_require_host_capacity` a `principal` (or an `is_admin: bool`) argument and pass `effective_is_admin(current_user, principal)`. The five handlers already hold `auth`; `_dispose_concierge_proposal` needs the flag threaded like `caller_tier`; `user_message_shim` needs `get_current_principal`. Six unit tests call `_require_host_capacity(<user>)` with one argument (`backend/tests/unit/api/test_capacity_gate_endpoints.py:78-134`, including a `_BareUser` with no `is_admin`), so they change with the signature. The integration file (`backend/tests/integration/api/test_capacity_gate_endpoints_api.py`) already overrides both dependencies through `principal_for`.

## Test notes

Make the two sources disagree, as `backend/tests/integration/api/test_entitlement_authority_api.py` does for tier: `principal_for(user, groups=[...])` with `groups` holding or omitting `ADMIN_GROUP` against a `user.is_admin` that says the opposite, an engaged decision published, then launch.
