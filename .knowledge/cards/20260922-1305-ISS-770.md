# ISS-770

## Title

A custom workflow's composer ("Compose a custom workflow", `/workflows/new`) exposes an
"Output format" selector (Markdown (.md) / HTML (.html)). Selecting HTML changes only the
deliverable's *filename* extension — the file's *content* is always raw markdown produced
by the last agent's streamed text, never actual HTML markup. The app's own Files tab
labels the file "Markdown (.md)" while showing the filename "output.html", and the run
record's `deliverable_mimetype` is `text/markdown` regardless of the selected format.

Validates **QA-SG-014** (`BUGS.md#qa-sg-014` / `LEDGER.md`) — the bug report itself
describes this defect under its "QA-PS-026" section header (BUGS.md content for
QA-SG-014 and QA-PS-026 is cross-mislabeled: QA-SG-014's own header is followed by
QA-PS-026's task_loop/planner-worker content, and vice versa — a pre-existing
BUGS.md data problem, not something this validation pass corrected, since BUGS.md is
read-only for this role). The title used here ("markdown instead of selected format,
always produces .md files") is the LEDGER.md row title, which is what this card was
dispatched against.

## Reproduction — CONFIRMED 3/3, cycle 2 first produced the decisive proof

All three from a cold `/workflows/new` (or "Run workflow" from a freshly saved
workflow) with `qa-admin@flowinqa.com`:

1. **Cycle 1** (run `fa216d19-79a1-4207-8e7d-268c4d4dd69c`): composer with Output
   format = HTML, brief only, "Run once" clicked with 0 explicit agents added.
   Auto-cancelled mid-run by an unrelated navigation event before completion —
   inconclusive on its own, but it exercised the same underlying pipeline (all runs
   under `base_pipeline_type: "custom"` execute the fixed 9-step
   `custom/workflow.yaml` pipeline regardless of `agent_ids` sent) and set the
   correct deliverable target `output.html` per the composer's own tooltip.
2. **Cycle 2** (run `e49b91e6-f2fe-479c-a941-75da2b53c05d`, completed, 3m23s):
   saved a workflow (`da58b66d-50cf-4cd8-bb5b-1727f8c2c1a0`, "QA-SG-014 format
   check") with Output format = HTML and 1 agent (Documentation Agent). The launch
   POST to `/api/runs` correctly included
   `selections: {"__deliverable__": {"strategy": "streamed_text", "name": "output.html"}}`.
   Run completed: `deliverable_filename: "output.html"`,
   **`deliverable_mimetype: "text/markdown"`**. `.chain/output.html`'s actual bytes
   are a raw `## Task 1: ... ## Task 2: ...` markdown task list (416 B) — no HTML
   tag anywhere. The Files tab (`/runs/e49b91e6.../files`) itself displays
   "output.html" / **"Markdown (.md) · 416 B · validated"**.
3. **Cycle 3** (run `0d7e68f3-edcd-40f9-9991-4a76a630d32c`, completed, 9m1s, re-run
   of the same saved workflow from `/workflows`): identical result —
   `deliverable_filename: "output.html"`, `deliverable_mimetype: "text/markdown"`,
   13.2 KB of raw markdown (`## Task 1: ... ## Task 18: ...`) with the Files tab
   again labeling it "Markdown (.md)".

**Trigger:** every `base_pipeline_type: "custom"` run, unconditionally — no axis
(agent count, brief, format selection, cold vs warm) changes the outcome. The
mismatch is 100% reproducible, not intermittent.

## Expected vs Actual

- Expected: selecting "HTML (.html)" in the composer's Output format dropdown
  produces a deliverable whose *content* is HTML markup, matching the file's `.html`
  extension and the `deliverable_mimetype` the API/UI report.
- Actual: only the *filename* changes. `deliverable_mimetype` is always
  `text/markdown`, and the bytes are the last agent's raw markdown/task-plan text
  with zero HTML tags, for every custom-workflow run regardless of the composer's
  Output format selection.

## Root cause (file:line, with the quoted mechanism)

1. **`backend/agents/execution_engine/engine.py:12920-12946`** — `_apply_selections`
   DOES correctly read `selections["__deliverable__"]` and patch the compiled
   plan's `deliverable` spec:
   ```python
   _deliverable_override = (selections or {}).get("__deliverable__")
   if _deliverable_override and isinstance(_deliverable_override, dict):
       from agents.workflows.plan import DeliverableSpec
       try:
           patched_deliverable = DeliverableSpec(**_deliverable_override)
           ...
           return dataclasses.replace(compiled, steps=new_steps,
               deliverable=patched_deliverable, clarify=patched_clarify), _user_by_agent
   ```
   This patches only the **`DeliverableSpec`** (strategy + output filename) — it
   does not, and structurally cannot, change *what the last agent's output looks
   like*. `strategy: streamed_text` still means "use the last step's raw streamed
   text verbatim" (`engine.py:1328-1348`, the `streamed_text` branch of
   `build_flat_payload`), so the override only renames the file the raw text gets
   written to.

2. **`backend/agents/workflows/custom/workflow.yaml:18-19`** hardcodes
   `strategy: streamed_text` / `name: output.md` for the file-backed `custom`
   pipeline's own deliverable — the 9-step pipeline that actually runs
   (Market Research → Strategy Analysis → Roadmap Planning → Security Audit →
   Test Strategy → Performance Optimization → Documentation → Executive Reporting
   → Task List Planner) never renders or converts its last step's output into
   HTML; there is no HTML-formatting agent or post-processing step in the file
   plan at all.

3. **`backend/agents/workflows/selections.py:196-206`** (`synthesize_manifest`
   docstring) confirms the composer's per-run `manifest.deliverable` field (which
   the FE populates correctly, e.g. `{"strategy":"streamed_text","name":"output.html"}`
   captured live in the `POST /api/user-workflows` request body) is a decoy used
   only for the trust=user compile-target check and "is NOT the engine's run
   plan" — the real override must travel via `selections.__deliverable__`, which
   the composer's "Run once"/"Run workflow" launch DOES send correctly (verified
   in the captured `POST /api/runs` body). So the FE→BE wiring for the *filename*
   is fully correct; the gap is structural: nothing in the engine ever transforms
   markdown content into HTML when `__deliverable__.name` ends in `.html`.

In short: `__deliverable__` is a **rename-only** lever (it changes `DeliverableSpec.name`
and can pick between `streamed_text` / `single_file` / `serialized_sandbox`
*strategies*, per `engine.py:12914`'s own comment "the FE stores it under the
reserved `__deliverable__` key ... Generic, name-free (SC-001): the caller decides
the shape, the engine just carries it"), never a **format-conversion** lever. The
composer UI's "Output format: HTML (.html)" control promises content conversion it
cannot deliver — no step in the compiled plan (fixed `custom/workflow.yaml`, or any
`agent_ids` subset of it) ever produces HTML markup.

## Notes

- The composer's default catalog for `base_pipeline_type: "custom"` always compiles
  the fixed 9-agent `custom/workflow.yaml` step list — the `agent_ids` sent by the
  composer UI (e.g. `["documentation-agent"]`) do not reduce which steps run. This
  is a separate observation, not this card's claim; flagging it here only because
  it explains why cycle 1/2/3's "1-agent" workflows all show "9 agents" in their
  run summary.
- Distinct from **ISS-021** (`.knowledge/cards/20260613-1711-ISS-021.md`, status
  `done`): that card was about an HTML deliverable existing on disk but being
  unreachable from Preview/Files (a UI-visibility gap, fixed 2026-08-14). This
  card is the opposite: the file IS reachable and correctly named, but its
  *content* was never HTML to begin with.
