## Description

Root-cause completion for **QA-PS-059** (`LEDGER.md` / `BUGS.md#qa-ps-059`),
whose validate-phase card [ISS-812](20260922-1853-ISS-812.md) traced the
Config-tab `capabilities` double-fire to `AgentsPopup.tsx`'s
`ConfigLeversFlat`/`useAgentCapabilities` and proposed the fix ("give
`getCapabilities` in `frontend/src/lib/api.ts` a shared in-flight-request
cache") but recorded it as "not applied (validation only)" — ISS-812 was
validated at 18:53, before any of today's fixes landed. This card confirms,
against the CURRENT source tree (20:22), that the fix has since shipped, and
separates what is now closed from what QA-PS-059 shares with an
already-tracked, still-open mechanism elsewhere.

## Root cause (confirmed, matches ISS-812)

`useAgentCapabilities` (`frontend/src/components/workflow/AgentsPopup.tsx:1530`)
runs a plain `useEffect(..., [token])` (`:1540-1544`) that calls
`fetchCapabilities(jwt)` — `getCapabilities` aliased at `AgentsPopup.tsx:24`
— with no request-level cache of its own; a React hook's state is per call
site, not shared. `ConfigLeversFlat` (`AgentsPopup.tsx:1717`) has exactly one
call site of this hook (`:1731`), so the doubling ISS-812 measured (2x
`GET /api/capabilities` on Config-tab open, 3/3 cold starts) is React 18 dev
StrictMode double-invoking that single mount effect — confirmed unchanged by
reading the current file.

## Now confirmed CLOSED

`getCapabilities` (`frontend/src/lib/api.ts:1815-1822`) no longer calls
`request()` directly — it now returns
`cachedGet<CapabilitiesPalette>("/api/capabilities", token)` (`cachedGet`,
`api.ts:410-426`: a module-level `Map` keyed `` `${token}\u0000${path}` ``,
30s TTL, entry evicted on failure so a real error still retries). This
shipped as [FIX-617](20260922-1935-FIX-617.md), landed 19:35 — after ISS-812's
18:53 validation. Confirmed two ways this session:

1. **Static** — direct read of `api.ts:1815-1822` and `:410-426` today.
2. **Dynamic** — ran `frontend/src/lib/api.sharedGetCache.test.ts`:
   `Test Files  1 passed (1)`, `Tests  6 passed | 1 expected fail (7)`,
   including "coalesces concurrent callers of the same endpoint into one
   fetch" — the exact StrictMode shape this bug exhibits.

**Blast radius, grepped fresh** this session
(`grep -rn 'getCapabilities(\|fetchCapabilities(\|useAgentCapabilities('
frontend/src --include='*.ts' --include='*.tsx'`, excluding tests and the
`api.ts` definitions): 9 non-test call sites, ALL routed through the one
fixed function, none bypassing it —

No caller bypasses `cachedGet`. The separate axios-based `capabilitiesApi`

([ISS-834](20260922-2003-ISS-834.md), re-confirmed by the same grep this
session). **No further sibling ISS card is warranted for the capabilities
mechanism**: the fix is the one shared function every caller already routes
through, and every caller is enumerated above — filing a per-caller sibling
would describe an already-closed path, not a new one.

## Still OPEN — not this card's mechanism, already tracked elsewhere

QA-PS-059's other two claims are the SAME defect the ledger row already
attributes to [ISS-787](20260922-1815-ISS-787.md) (validated via QA-PS-051,
`Status: DUPLICATE`), not a mechanism this card needs to re-derive:

- **`GET /api/runs?limit=50` x2** — INFERRED, not re-measured live on
  `/library/agents/*` this session. [FIX-616](20260922-1923-FIX-616.md) added
  an in-flight `Map` to `getWorkflows()` (`api.ts:871-895`), but
  [FIX-618](20260922-1945-FIX-618.md) measured this SAME pair
  (`RunConnectionProvider`'s boot fetch and `page.tsx:995`'s mount effect)
  still firing x2 on `/settings/profile` because the two calls are "ticks
  apart" — outside the in-flight window — and documents that as a deliberate
  non-fix ("Overriding that is a design decision, not this fix"; run/workflow
  lists are excluded from `cachedGet` on purpose per its own header comment).
  `RunConnectionProvider` mounts app-wide (`app/layout.tsx:51`) and
  `page.tsx`'s effect fires on every route via the single catch-all, so the
  same timing gap applies to `/library/agents/*` identically — this is a
  design tradeoff already recorded, not an unreported defect.
- **`GET /api/workflows` x2** — INFERRED. [ISS-782](20260922-1610-ISS-782.md)'s
  "Partial resolution" section traced the remaining source to
  `store/listenerMiddleware.ts`'s `signedIn` listener (dispatched from
  `page.tsx:892`, the same catch-all), whose possible StrictMode-driven
  double-dispatch is an open question explicitly left to
  [ISS-794](20260922-1827-ISS-794.md), "not patched on a guess." Per
  QA-PS-051's own "Expected" section (`ISS-787`'s sibling report), ONE
  `/api/workflows` call IS legitimate on a Library detail view (pipeline
  context) — this is the same open over-count QA-PS-051 already described,
  not a Library-specific mechanism.
- **`GET /api/auth/me` x2`** — does not reproduce. ISS-812 already measured
  it 1x, 3/3 cold starts; nothing in this analysis changes that finding.

## Where the fix belongs

For the part this bug uniquely contributed — capabilities×2 on the Config
tab — the fix is already applied, in `frontend/src/lib/api.ts`'s
`cachedGet()`; no further code change is needed. For the remainder, there is
no new fix location to propose here: it is the same shared
`getWorkflows()`/`listenerMiddleware.ts` territory
[ISS-787](20260922-1815-ISS-787.md)/[ISS-781](20260922-1630-ISS-781.md)/[ISS-794](20260922-1827-ISS-794.md)
already own, and re-patching it under this card would duplicate that work
rather than keep one guard per shared function.
