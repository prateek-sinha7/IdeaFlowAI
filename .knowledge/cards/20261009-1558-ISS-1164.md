# ISS-1164

**Register source:** sibling derived during the `QA-KB-126` analysis on 2026-10-09 (root [ISS-1114](20261008-1415-ISS-1114.md)). Not its own bug row.

**Confidence:** CONFIRMED for the compile and the call into the mint (offline probe, in-memory SQLite, `_launch_run_core` stubbed, `evidence/qa-kb-126/analysis-01-probe-db-trust-doors-by-tier.txt`, block `[T]`). INFERRED end to end: no conditional gate was fired in a live run (it needs a model that answers the routing decision). What would settle it: a scripted-model engine test whose gate answers the `trigger: workflow` outcome that names the row id, then `GET /api/runs/{id}` for `diverted_to_workflow` and a child run whose plan holds the grant.

## Condition

`run_trigger_workflow` (`kernel_services.py:1603-1650`) resolves a `workflow_ref` that is not `self` and not a file pipeline as a saved row: `_owned(db, workflow_ref, SimpleNamespace(id=ectx.owner_id))`, then `row_trust = "user" if row.overrides_pipeline_type else "db"` (`:1616`), then `compile_with_baseline(..., trust=row_trust, overrides=row_overrides)` (`:1643-1648`), then `_launch_run_core(... user=SimpleNamespace(id=ectx.owner_id) ...)` (`:1671-1685`). There is no `Principal`, tier or `can_run_pipeline` on the path ([ISS-946](20261002-0107-ISS-946.md) is the same blocker for the model gate).

[FIX-771](20261009-0126-FIX-771.md) gates the trigger targets that are file pipelines and lets a saved row id pass (`_trigger_entitlement_error`, `run_engine.py:674-712`: "`self` and a saved `user_workflow_id` are not pipeline names and pass"). [ISS-1131](20261008-2216-ISS-1131.md) records the row's content as the root's question.

Probe `[T]`, owner `basic`: a row with `base_pipeline_type: ppt` and an exec step as `workflow_ref`: the mint is reached with `pipeline_type='ppt'`, `user={'id': 'owner'}` and a plan holding `exec=True`, `gates=['security', 'approval']`.

## Expected vs actual

Expected: a row the owner's entitlement cannot hold at `db` is not compiled at `db` by any door that starts it. Actual: the trigger decides from the row alone, whoever the owner is.

## Why the root cause implies it, and why it needs its own fix

[ISS-1114](20261008-1415-ISS-1114.md) is three compile sites that each pick the trust without the tier (save `user_workflows.py:121`, launch Case 3 `run_commands.py:3374-3376`, this one). A fix that decides the trust from the caller's tier reaches the first two, which hold a principal. It cannot reach this one: the kernel has no tier, and [FIX-771](20261009-0126-FIX-771.md) locks "no tier travels into the kernel and no kernel -> app import is added". It is not only a leftover for old rows. A lower tier's save compiles at `user`, which accepts and narrows `tool_sets` and `git` instead of refusing them (probe `[N]`), so such a row can legitimately be stored; this door's `db` compile then returns them whole.

## Fix direction (INFERRED, not applied)

Three tier-free options for the fixer; the first is the smallest.

1. Clamp the child to the parent run's persisted `_trust`. Every Case 3 launch writes `persisted_manifest["_trust"]` onto the parent's `WorkflowRun.manifest_json` (`run_commands.py:3430-3431`); this door already opens a DB session (`:1604-1620`) and `ectx.run_id` names the parent. No tier and no workflow-name literal (INV-1). A file-backed parent has no `_trust`, which is today's behaviour.
2. [ISS-946](20261002-0107-ISS-946.md)'s route: persist the launch tier on the run or `ExecutionContext` and decide in `_launch_run_core`. It needs a column or a context field and covers both mint doors.
3. Derive the trust from the row's `base_pipeline_type`. Tier-free, but it demotes legacy Composer rows stamped with a stale label (the frontend documents that they exist, `frontend/src/store/api/userWorkflows.ts:858-869`).

A refused compile raises `CompilerError` out of `run_trigger_workflow`; the engine call is a bare `await` (`engine.py:7186-7191`), so the parent run fails. That is the same posture [FIX-769](20261009-0059-FIX-769.md) verified for override rows (`evidence/qa-kb-103/fix-02-doors-case3-trigger-resume-inline.txt`, line 9).

## Resolution ([FIX-776](20261009-1628-FIX-776.md), 2026-10-09)

Option 1, the parent clamp, with one change: a firing run that persisted no `_trust` gives `user`, not today's row-only `db`. A built-in run
with an enabled override (whose steps can carry a route) and a triggered child persist none too, and keeping `db` for them left the
basic-tier door open through either. `run_trigger_workflow` now takes `row_trust = "user" if row.overrides_pipeline_type else
_parent_run_trust(db, ectx.run_id)` through its existing lazy `app.api.run_engine` import (no tier in the kernel, no new module edge). Observed:
a stored exec row triggered from a run with no `_trust` or `_trust="user"` raises `CompilerError` before the mint; from a run at `db` it is
minted with `exec=True` (`evidence/qa-kb-126/fix-01-probe-doors-after-fix.txt` `[T]`). The test file above was red on a HEAD copy ("DID NOT
RAISE") and is green with the change. Enterprise cost and upgrade path: [FIX-776](20261009-1628-FIX-776.md) "Behaviour changes" and [ISS-1174](20261009-1628-ISS-1174.md).
