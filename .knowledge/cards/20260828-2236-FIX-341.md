## What was wrong

On `/settings/profile`, the Password card's "New passwords do not match" error
stayed on screen after the user corrected the Confirm field to agree with New
password. Reproduced 3/3 by the validator with the two `input[type=password]`
DOM values read directly and confirmed byte-identical while the banner still
claimed they differed.

## Root cause

`frontend/src/components/settings/AccountSettings.tsx:99` — the feedback
`message` state was written **only** inside `handleChangePassword`
(`:148-174`): cleared once on entry (`:149`), then set by whichever validation
branch fails, e.g. `"New passwords do not match"` at `:158-159`.

Every one of those texts asserts something about the *current* contents of the
three password fields ("All fields are required", "New password must be at
least 8 characters", "New passwords do not match", "Password changed
successfully"), but the three field `onChange` handlers — Current `:284`, New
`:296`, Confirm `:307` — each updated only their own field's state and never
touched `message`. So the banner was computed once per submit click and stayed
until the next one, regardless of what the fields then contained.

## What changed and why there

One file, three handlers plus a comment on the state declaration:

```
onChange={e => { setConfirmPassword(e.target.value); setMessage(null); }}
```

added to Current (`:284`), New (`:296`) and Confirm (`:307`).

The report named only the New/Confirm pair, but the mechanism is the state, not
the field: the same submit-time `message` also carries "All fields are
required" (falsified by typing into Current) and "Password changed
successfully" (falsified by starting a second change). Fixing only the two
fields the repro used would have left the Current field's identical staleness in
place, so all three edit paths into `message` now invalidate it. Nothing else
writes `message`, and `handleChangePassword`'s own `setMessage(null)` on entry
is untouched, so the submit-time validation is unchanged — the banner is simply
no longer allowed to outlive the values it describes.

Clearing (rather than live re-validating on every keystroke) is the behaviour
[ISS-244](20260828-1634-ISS-244.md) asks for and the behaviour the test asserts:
a message that can no longer be true disappears instead of nagging.
