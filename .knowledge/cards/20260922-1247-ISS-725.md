# ISS-725

Register entry: **QA-PS-031** (`BUGS.md`), filed as a sibling of [ISS-723](20260922-1245-ISS-723.md)
— the inverse (write-back) case of a read-side defect.

## Why the root cause implies this

[ISS-723](20260922-1245-ISS-723.md)'s instruction set explicitly asks: "if save is broken, is
load? if create, is delete?" The analogous check here is the inverse of Preview's READ: does
anything WRITE from the same frozen tag tree, and if so, does it inherit the same staleness —
except now as a mutation, not a display bug?

`POST /{run_id}/restore` (`backend/app/api/runs.py:2352-2530`) does exactly this. Its own
docstring states the contract plainly:

> "Restore the run's sandbox to a previous version tag. Creates a **forward commit**
> materializing the tracked tree at `tag`... Every existing commit and tag survives."

Step 9 of its own documented sequence: *"Materialize the tracked tree at the tag without moving
HEAD"* — `sandbox.materialize_tree_at_ref(safe_tag)` (`runs.py:2530`). This writes the WORKING
TREE to match whatever `git` has recorded for every tracked path at that tag — including
`presentation.html`, which [ISS-723](20260922-1245-ISS-723.md) proves is byte-identical to v1
at every tag (`v1`, `v2`, `v3`) for any streamed-strategy revision workflow, because nothing
ever re-commits it. `materialize_tree_at_ref` cannot distinguish "this path is genuinely v2's
content" from "this path was never updated past v1 and the tag just happens to point at it" — it
trusts the tree.

After materializing, `restore_version` commits the result through `commit_in_sandbox` (audited
as `operation="restore"`) and persists a `run_provenance_audits` row with the idempotency key
(`runs.py:2375-2378,2381-2384`) — i.e. the system records this as a **successful, correct**
restore to v2. There is no content comparison anywhere in the sequence (`runs.py:2352-2530`) that
would notice the "restored" `presentation.html` is actually v1's.

## Expected vs actual

- **Expected**: `POST /{run}/restore {tag: "v2"}` makes the live sandbox's `presentation.html`
  match what v2's revision agent actually produced (the "ARCTIC VAULT v2" content, per Postgres'
  `output` column for that run).
- **Actual**: it makes `presentation.html` match v1's original, unrevised content — silently. The
  restore reports success; the audit row says "restored to v2"; the bytes say v1. A user who
  restores an intermediate revision to recover from a bad LATER edit would get the ORIGINAL,
  pre-revision content back, not the revision they asked for — and would have no way to tell
  short of opening the file and comparing by eye.

## Severity rationale (high, not medium)

Unlike the read-side siblings (Preview/Workspace, which only MISDISPLAY), restore MUTATES the
live sandbox and writes a permanent, audited commit asserting correctness. There is no
"reload and see the real value" recovery the way there is for a misdisplaying read — the wrong
content becomes the new HEAD.

## What would confirm this live (not exercised here — restore is a write, out of this task's
read-only remit)

1. `POST /api/runs/{f7000bbd-…}/restore` with `{"tag": "v2", "idempotency_key": "<uuid>"}` against
   the Arctic Vault family (a healthy-git, `git_tag` fully populated family, so `_validate_tag_for_restore`
   passes cleanly — isolates this from Defect B).
2. Read `presentation.html` at the new HEAD afterward; compare its `<h1>` against the DB `output`
   column for `f7000bbd-…` (`ARCTIC VAULT v2`, already confirmed present in Postgres).
3. A mismatch (h1 reads "Arctic Seed Vault Logistics" instead) confirms this card exactly as
   described. Not run here: restore is a genuine mutation and this task's remit is read-only.

## Fix location

Same as [ISS-723](20260922-1245-ISS-723.md)'s Piece 1 — once a revision's deliverable is
actually written to sandbox root and captured in that revision's own commit, `materialize_tree_at_ref`
reconstructs the CORRECT tree automatically, with zero change needed inside `restore_version`
itself. This card exists to make sure the restore path is verified once that fix lands, not to
propose a second, independent fix.

## Fix risk

None specific to this card beyond [ISS-723](20260922-1245-ISS-723.md)'s own (the restore code
path is not itself buggy — it faithfully materializes what git has recorded; the defect is
entirely upstream, in what git was ever given to record).
