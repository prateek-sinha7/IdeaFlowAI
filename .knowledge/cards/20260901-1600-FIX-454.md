## What was wrong

`useRunStateStore.ts:420–440` (approx) defines `pipelineFrameTypes` — the allowlist for which SSE frame types are forwarded to `handlePipelineMessage`. An explicit `if (!pipelineFrameTypes.includes(msg.type)) return;` guard follows, silently dropping any unrecognised type.

Three validation frame types were absent from the list: `validator_result`, `gate_passed`, `gate_blocked`. All three rehydrate the `validationPassed` / `validationIssues` fields on `AgentRunState` via `handlePipelineMessage`'s existing cases.

`ValidationResultCard` in `AgentDetailPanel.tsx:839` self-gates on `passed === undefined`:
```tsx
if (passed === undefined && (!issues || issues.length === 0)) return null;
```

Because the replay path never called those reducer cases, `validationPassed` was always `undefined` on any run reopened from Run History — the card rendered nothing, and gate verdicts were permanently invisible after a page reload.

## Root cause

The allowlist was built incrementally as new frame types were added to the engine. The `validator_result` / `gate_passed` / `gate_blocked` types were added without a corresponding allowlist update.

## What changed and why there

Three entries appended to `pipelineFrameTypes` in `useRunStateStore.ts`, with an explanatory comment:

```ts
// ISS-117: validator_result / gate_passed / gate_blocked were omitted from
// the allowlist, so the early-return at the `if (!pipelineFrameTypes.includes
// (msg.type)) return;` guard below silently dropped them on replay.
// ValidationResultCard in AgentDetailPanel gates on `passed === undefined`
// and renders nothing — so no run reopened from history ever showed a gate
// verdict. These three types rehydrate `validationPassed` / `validationIssues`
// via handlePipelineMessage's existing cases; no new reducer needed.
"validator_result", "gate_passed", "gate_blocked",
```
