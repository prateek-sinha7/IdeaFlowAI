# FIX-730

## What was wrong

This fix is for bug report QA-KB-066 ("Steps/Files clarify rounds stay on the page run's rounds after pinning a different
version"). The root cause comes from the 2026-10-02 re-analysis on [ISS-755](20260922-1415-ISS-755.md) and its three
siblings. It was not re-derived here. Every cited line was re-read before editing, at HEAD `154e326b6`, where
`PreviewPanel.tsx` is unmodified since `14a675db4`.

`PreviewPanel` derives every pin-aware value from `viewingVersion` (`effAgents`, `effPipelineState`, `effRunInput`, ...).
Clarify rounds were not part of that:

- **[ISS-755](20260922-1415-ISS-755.md).** The FilesTab mount (old `:1950`) and the AgentThinkingTab mount (old `:1994`)
  both passed `clarifications ?? pipelineState?.clarifications`. That is the raw prop and then the raw shell
  `pipelineState`. The run screen never passes the prop (`DashboardLayout.tsx:3392-3440`), so a pinned v1 showed the
  rounds the shell run (v2) had answered live.
- **[ISS-1006](20261002-0523-ISS-1006.md).** `VersionView` had no `clarifications` field, and neither pin path fetched
  rounds. Only `getWorkflow` ran. A pinned version that did ask questions could only ever show none.
- **[ISS-1007](20261002-0523-ISS-1007.md).** `clarifyQuestions` and `onSubmitClarify` went to the Steps tab raw.
  `StepsOverviewSpine`'s `hasClarify` has no pin term, so pinning v1 while the shell waited on clarify rendered the live
  answer form inside the read-only v1. It also hid v1's agent rows.
- **[ISS-1008](20261002-0523-ISS-1008.md).** A run reopened or cold-loaded after it settled starts from
  `resetPipeline()`'s empty list. No reducer case rebuilds rounds from replayed frames: `questionnaire_complete` only
  clears the form (`page.tsx:2117-2132`). Nothing passes the "reopen override" prop either. Such a run showed no rounds
  at all.

## What changed, and why there

All changes are in `frontend/src/components/preview/PreviewPanel.tsx`. Line numbers are the new file.

- **`:31`, `:35`.** Two imports added: `getRunArtifacts` and `parseClarificationArtifacts`.
- **`:598-600`.** `VersionView.clarifications?` added (ISS-1006).
- **`:613-623`.** `loadRunClarifications(token, runId)`. It is the same `getRunArtifacts(kind="clarifications",
  includeContent)` call plus `parseClarificationArtifacts` that the History detail view makes
  (`WorkflowHistory.tsx:446-448`). It wraps them in try/catch and returns `[]` on failure.
- **`:955-956` (`handleSelectVersion`) and `:1060-1061` (the `/versions/{n}` effect).** The version's rounds are
  awaited in one `Promise.all` with `getWorkflow` and stored on the view (ISS-1006). The ISS-758 guards are unchanged.
- **`:1222-1238`.** The ISS-1008 load. When nothing is pinned, the run is not running, and it has no live rounds, the
  persisted rounds are loaded for `workspaceRunId`. They are stored as `{runId, rounds}`, so a stale answer never
  attaches to another run.
- **`:1239-1245`. `effClarifications`, the one value both consumers read.** It is pin-keyed (ISS-755):
  - With a pin, it is the version's own rounds.
  - Without a pin, it is the explicit prop, then the loaded rounds of the settled run, then the live
    `pipelineState.clarifications`.
- **`:1993` (FilesTab) and `:2037` (AgentThinkingTab).** Both now read `clarifications={effClarifications}`.
- **`:2055-2059`.** `clarifyQuestions` and `onSubmitClarify` are `undefined` under a pin (ISS-1007). This is the card's
  fix: the lane composer still carries the live run's form. `StepsOverviewSpine` is untouched.

One derived value read by both JSX sites follows the FIX-603 pattern. It covers the only production mount
(`DashboardLayout.tsx:3392`). No other reader of the prop exists.

### Where this differs from the cards, and why

1. **The ISS-1008 load sits in `PreviewPanel`, not in `DashboardLayout`.** The card proposed a fetch in
   DashboardLayout/page that passes the `clarifications` prop. The 4-test-writer's ISS-1008 case mounts `PreviewPanel`
   alone with no such prop, so a DashboardLayout-only fix would leave the test red. `PreviewPanel.tsx` is in the card's
   globs, and `PreviewPanel` is the component whose props document the "reopen override" (`:481-484`).
2. **The ISS-1008 load is keyed on `workspaceRunId`, not `contentSourceRunId`.** The card said "keyed on
   contentSourceRunId", which is `PreviewPanel`'s `liveRunId`. That id still names the parent in two cases:
   - `page.tsx` clears it only for a non-revision launch (`:4303`), so it keeps the parent while a revision runs.
   - It is advanced only by `pipeline_complete` (`:1630`). The `pipeline_failed` path (`:1772-1794`) never sets it.

   So a failed revision whose own `pipelineState` is on screen would have shown its parent's rounds.
   `workspaceRunId` (`pipelineState.pipelineRunId ?? activeRunId`) is the run whose pipeline is displayed. The file
   already argues the same at `:1204-1215`.
3. **Live rounds win when non-empty.** The card had the fetched override shadow them. The card also said "only when
   the run is not the live one", and a run with live rounds is exactly that case. This choice keeps the live path
   rendering exactly as before, and it skips the fetch whenever the live list already has rounds.
4. **The helper lives beside `versionViewFrom`, not in `lib/clarifications.ts`.** ISS-1008 suggested the lib as the
   shared home. Both callers ended up in `PreviewPanel.tsx`, and that lib documents itself as "Pure, side-effect-free"
   while this helper fetches. ISS-1006 suggested this location.

## Deliberately not done

- **[ISS-1059](20261007-1900-ISS-1059.md) (new, open, INFERRED).** A run reopened while it is still running gets no
  persisted rounds until it settles, because the load is gated on `!isStillRunning`. A round answered after such a
  reopen then wins over the persisted set. This is a residual of ISS-1008's gap, kept out because the card asked for
  no load on the live run.
- **ISS-755's unfiled blast-radius note.** FilesTab still gets raw `isRunning={isStillRunning}` and
  `buildingFilename={pipelineState?.deliverableFilename}` under a pin. The analyzer marked it "left alone, not
  verified, not filed". The Files tab is reachable only through a legacy `/files` deep link.
- **The header under a pin.** Neither `RunHeader`'s `clarifyCount` nor the header run state changed. That is the open
  product question in [ISS-1031](20261002-1040-ISS-1031.md).
