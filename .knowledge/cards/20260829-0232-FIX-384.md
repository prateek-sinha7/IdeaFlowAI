## What was wrong

BUG-20260828-101500-login-expired-true-r2 (`bug-hunter/ledger.md`), validated
3/3 cold-start cycles. The app already has a working return-path mechanism: a
**signed-out** user deep-linking a protected route is sent to
`/login?redirect=%2F<path>` and, after signing in, correctly returned to that
exact route. But when a session expired **mid-session** on a protected route —
the 401 ladder auto-redirecting an already-signed-in user — that mechanism was
bypassed entirely. No `redirect` param was ever attached, and after signing back
in the user unconditionally landed on `/dashboard`, losing the page they were
actually on. Confirmed on two distinct routes (`/settings/ai-model`,
`/runs/<id>/workspace`).

The read half was never broken. `login/page.tsx:55` and `:67` already consume
`searchParams.get("redirect")` via `resolveRedirectTarget` whenever the param is
present — the write half simply never supplied one.

## Root cause

Two lines, per [ISS-322](20260828-2007-ISS-322.md), and the second is the
reason the first could not be fixed locally:

`frontend/src/lib/api.ts:178` (`handleSessionExpiry`, the ONE "session genuinely
expired" side effect the whole 401 ladder funnels through):

```ts
window.location.href = routes.login({ expired: true });
```

`frontend/src/lib/routes.ts:25-27` — `routes.login`'s parameter type was
`{ expired?: boolean }` and nothing else. It had **no `redirect` field at all**,
so the mid-session-expiry path could not have attached one even if the call site
had wanted to. That is why this is not a missing argument but a missing part of
a shared builder's contract.

Because the redirect is a hard `window.location.href` navigation (not a router
push), the current path was still sitting in `window.location` at the moment
that line ran — it was simply never read and forwarded.

## What changed, and why there

Two files, both named in [ISS-322](20260828-2007-ISS-322.md)'s
`applies_to.globs`. No new file, no new helper, no new dependency.

1. **`frontend/src/lib/routes.ts:31`** — `login`'s param type gains
   `redirect?: string`. The body is untouched: `buildQueryString(params)`
   already percent-encodes every value through `URLSearchParams.set()`, and
   already drops `undefined`/`''`, so no other route builder or caller changes.
   A `// ISS-322:` comment above it records why the field exists and that it
   must keep going through `buildQueryString`.

2. **`frontend/src/lib/api.ts:178-183`** — `handleSessionExpiry()` now reads
   `const { pathname, search } = window.location` inside the existing
   `typeof window !== "undefined"` guard and passes `` `${pathname}${search}` ``
   as `redirect`.

**Fixed at the funnel, not at the reported path.** Re-grepped
`handleSessionExpiry` across `frontend/src` before editing — the card's blast
radius still holds exactly. All 13 call sites (`api.ts`'s own `fetchWithAuth`
401 branch and `authedFetch`, `store/api/http.ts`'s axios interceptor,
`useHandoffSocket.ts`'s JWT-expired 4001 close handler, `useRunStream.ts`,
`prototype-api.ts`, `ppt-api.ts`, `api-handoff.ts`, `LaunchWizard.tsx` x2,
`[...view]/page.tsx` x3) call the same void function and none of them passes an
argument, so the one change inside it covers every entry route. Not one caller
needed editing, and no caller could have been fixed on its own.

**The open-redirect guard is deliberately NOT duplicated here.** `redirect` is
validated on arrival by `resolveRedirectTarget` (`authRedirect.ts:32-34`) at
both login-page read sites, which is the same guard the already-working
signed-out flow relies on. Adding a second `isSafeRedirectPath` call on the
write side would import a guard for a value (`window.location.pathname`) the
browser guarantees is `/`-rooted, and would fork one allowlist into two places
that can drift.

**`buildLoginRedirect()` (`authRedirect.ts:43-49`) was intentionally not
reused.** It cannot carry `expired=true`, and it builds its URL by string
interpolation — the exact pattern [ISS-486](20260828-2335-ISS-486.md) warns
must not be propagated. Routing through `routes.login`/`buildQueryString`
instead is what makes a query-string-bearing target safe; verified directly
with the shape ISS-486 names:

```
/login?expired=true&redirect=%2Fanalytics%3Frange%3D7d%26pipeline%3Dppt
round-trip redirect = /analytics?range=7d&pipeline=ppt
```

`buildLoginRedirect` and its 8 call sites are untouched — the signed-out guard
already worked and is out of this card's scope.

## Not fixed by this card

- [ISS-486](20260828-2335-ISS-486.md) stays **open**. Its post-fix risk (a
  nested query string leaking out as top-level `/login` params) is structurally
  closed by routing through `buildQueryString`, and the round-trip above shows
  it, but its own `## What would settle it` asks for a live browser repro from
  `/analytics?range=7d&pipeline=ppt` both before and after the fix. That card is
  `verification.type: manual, status: pending`, it is not on this fix
  assignment, and a node-level round-trip is not the browser evidence it asked
  for. Closing it belongs to whoever drives that repro.
- A 401 that fires while the user is already sitting on `/login` now produces
  `redirect=%2Flogin`, which costs one extra client-side hop after sign-in
  (`/login` -> mount guard sees a token and no `redirect` -> `/dashboard`)
  rather than looping. `/api/auth/login` is already in
  `SESSION_EXPIRY_EXEMPT_PATHS`, so the sign-in POST itself never reaches this
  path. Left alone deliberately: it is not a regression (the destination is
  `/dashboard` either way, exactly as before), and a `/login`-specific carve-out
  is a behaviour change no card asked for.
