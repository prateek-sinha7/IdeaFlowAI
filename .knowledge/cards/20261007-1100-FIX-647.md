## What changed

**File:** `frontend/src/lib/api.ts`

`getRunEvents` was rewritten to use `singleFlightGet` instead of the bare `request()`
call:

```typescript
// BEFORE
const res = await request<RunEventsResponse>(
  `/api/runs/${encodeURIComponent(runId)}/events?after=${afterSeq}`,
  { method: "GET", headers: authHeaders(token) },
);

// AFTER (ISS-871 / FIX-647)
const res = await singleFlightGet<RunEventsResponse>(
  `/api/runs/${encodeURIComponent(runId)}/events?after=${afterSeq}`,
  token,
);
```

`singleFlightGet` (already in api.ts, introduced by FIX-637 for `getWorkflow` /
`getRunFamily` / `getRunSandbox`) keys on `token + URL` and returns the in-flight
promise to any second caller that arrives before the first call settles. Because
the cold-mount T11 effect fires while `handleSelectWorkflowRun`'s `events?after=0`
request is still in flight (27 s for the large run), the second call is absorbed into
the first instead of launching a fresh 2.5 MB HTTP request.

The `afterSeq` value is part of the URL fragment, so a cursor-advancing call
(`afterSeq > 0`, used by FIX-172's chat-frame recovery path) uses a different key and
is never merged with the full-history call (`afterSeq == 0`).

## Why this pattern is correct

`singleFlightGet` drops the cached entry the moment the request settles, so:
- A later independent call (e.g., a tab opened 5 minutes after the first one closes)
  always makes a fresh network request.
- The only calls that coalesce are **concurrent** ones — which is exactly the T11
  remount scenario where two identical requests would otherwise be useless duplicates.

This mirrors the existing `getRunFamily` and `getWorkflow` patterns, keeping the
dedup strategy consistent across all large run-detail reads.
