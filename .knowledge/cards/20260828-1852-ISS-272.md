## What happened (adjacent state to ISS-222's root cause)

Filed while analyzing `BUG-20260828-025521-library-hooks`. [ISS-222](20260828-1534-ISS-222.md)'s
root cause is that the cards which open a hook's/skill's detail are unreachable by keyboard. This
card covers the *next* state of the same interaction: once a detail modal is open — by whatever
path, including a direct URL, since "Modal state mirrors the URL" per
`.knowledge/architecture/MOD-frontend-src-components-library.md` — the modal itself has no
keyboard-dismiss path and no dialog semantics.

`grep -n "Escape\|addEventListener\|keydown\|KeyboardEvent\|role=\"dialog\"\|aria-modal\|focus()"
frontend/src/components/library/LibraryPage.tsx` returns **zero matches** across the whole
978-line file — there is no Escape handling, no focus trap, and no ARIA dialog role anywhere in
it.

Both in-file modals share one copy-pasted shell:
- `SkillDetailModal` (defined `LibraryPage.tsx:138`): scrim
  `<motion.div onClick={onClose} className="fixed inset-0 z-[80] ...">` (lines 164-168), inner
  panel `<div onClick={e => e.stopPropagation()} ...>` (169-172), Close button
  `<button onClick={onClose}>...<X .../></button>` (199-200).
- `HookDetailModal` (defined `LibraryPage.tsx:280`): identical shape — scrim `onClick={onClose}`
  (300-303), inner panel stopPropagation (305-307), Close button (335-336).

Neither scrim has an `onKeyDown` for Escape; neither the scrim nor the panel carries
`role="dialog"` / `aria-modal="true"`; neither modal moves focus onto itself (or its first
focusable control) on mount. The Copy and Close `<button>` elements inside ARE real buttons, so a
keyboard user already focused inside the modal can reach and activate them by continuing to Tab —
but nothing places focus there on open, nothing traps Tab inside the dialog, and Escape does
nothing at all.

**Scope note — `AgentCapabilitiesModal` is explicitly NOT part of this claim.** The Agents tab's
detail surface is a different, separate component (`AgentsPopup.tsx`, module
`MOD-frontend-src-components-workflow`, used well beyond the Library page) and it DOES declare
`role="dialog"` / `aria-modal="true"` (`AgentsPopup.tsx:606-607`), even though a grep for
`Escape` there also finds no explicit handler. Auditing that component is a separate
investigation with a much larger blast radius and is out of scope for this bug.

## Why the root cause implies this

ISS-222 establishes that `LibraryPage.tsx` systematically omits keyboard affordances on its
interactive surfaces — the same gap repeats for the Agents grid
([ISS-270](20260828-1850-ISS-270.md)) and the Skills grid
([ISS-271](20260828-1851-ISS-271.md)). The two in-file detail modals are the surface a
keyboard/AT user reaches immediately after a card, once those are fixed — if the modal itself has
no Escape handler and no focus management, fixing only the trigger cards leaves the "view a
hook's/skill's capabilities" flow still not fully keyboard-operable; the gap just moves one step
later in the same journey.

## Confidence

CONFIRMED mechanism — the grep above is a direct, complete check over the whole file, not a
sample, and both modals' scrim/panel/button blocks were read directly. INFERRED as a live defect:
not reproduced with a real keyboard or screen-reader session. Settling it: open a hook or skill
detail modal (mouse is fine to get there), press Escape (expect: nothing happens), then reload
directly on a detail URL and Tab from page load to confirm focus is never programmatically placed
inside the dialog.
