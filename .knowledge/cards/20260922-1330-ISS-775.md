# ISS-775

## Title

Register bug **QA-SG-004** (`BUGS.md#qa-sg-004`, "Switching between parallel workflow runs from
notification bar is unreliable, sometimes fails or delayed").

## Reproduction — 3/3 cold-start cycles, all producing the SAME failure on the SECOND click

Each cycle: cold `page.goto('/dashboard')`, launch/reuse 6+ concurrent live runs (10-21 parallel
`waiting_for_user`/`planning` runs were live throughout this sweep — well above the reported "6+"
threshold), open the bell icon Notifications panel, click a live-run entry.

- **Cycle 1:** From `/dashboard`, clicked notification entry for run `012788d4…` ("runC") — worked,
  navigated instantly to `/runs/012788d4…/stream`. Re-opened the bell, clicked a DIFFERENT live
  entry ("runB", `b072c373…`) — **the URL stayed on `012788d4…`**, and the page rendered a
  two-run hybrid: the header/title still said "runC" but the Steps panel's "Starting point" card
  showed runB's brief. A second retry click on the same runB entry also did nothing (confirmed
  after a 3s wait — no delayed recovery).
- **Cycle 2:** From `/dashboard`, clicked "runA" (`7eae539a…`) — worked, navigated correctly.
  Re-opened the bell, clicked "runC" (`012788d4…`) — **URL stayed on `7eae539a…`** (runA); no
  navigation, no console error.
- **Cycle 3:** From `/dashboard`, clicked "runB" (`b072c373…`) — worked, navigated correctly.
  Re-opened the bell, clicked "runA" (`7eae539a…`) — **URL stayed on `b072c373…`** (runB); no
  navigation, no console error.

**Named trigger:** the FIRST click of a session (cold `/dashboard` -> a live run) always
navigates correctly (3/3). The SECOND click — switching from an already-open live run's
`/runs/<id>/stream` page to a DIFFERENT live run via the same bell panel — fails silently every
time (3/3). No exception is thrown in either failure; the click event fires (Playwright reports
no interception/timeout) but the route and rendered content simply do not change.

## Expected vs actual

- **Expected:** clicking any live-run entry in the Notifications bell panel navigates to that
  run's detail page immediately, every time, regardless of which run is currently being viewed.
- **Actual:** the first switch away from `/dashboard` works; every subsequent switch to a
  different live run via the bell panel silently no-ops — URL and displayed content stay on
  the previously-viewed run.

## Why this is not [ISS-647](20260917-1100-ISS-647.md)/[FIX-519](20260917-1323-FIX-519.md)

FIX-519 fixed the header's "N Running" **dropdown** (`AppHeader.tsx` `handleRunClick` +
`onGoToPipeline`), the single-run **badge**, and the History **resume button**
(`onViewRunningPipeline`). Its own "Not fixed here" note only flags a harmless double-fetch
(ISS-666). Nothing in FIX-519 touches `NotificationPanel.tsx`'s `onRowClick` -> `onViewResults`
call path (`DashboardLayout.tsx:2757-2789`), which is a separate handler with its own
`targetRunId` resolution and its own (unguarded) call into `onSwitchToLiveRun` +
`router.push`. This card's repro exercises exactly that bell-panel path, not the dropdown FIX-519
patched.

Also unlike ISS-647's reflow-under-cursor mechanism, the panel was freshly re-opened before each
failing click (not held open across a background list change), and `router.push` is called
synchronously right after `onSwitchToLiveRun(targetRunId)` in the `onViewResults` handler
(`DashboardLayout.tsx:2782-2785`) with a `targetRunId` that should always be defined (`liveRuns`
items always carry `workflowRunId: r.id`, confirmed at `AppHeader.tsx:204`). The failure profile
(silent no-op, no console error, `router.push` apparently not taking effect once already on a
`/runs/<id>` route) points at a downstream guard or a reactive effect that reverts/ignores the
second push while `trackedRunIdRef`/`pipelineState` from the previously-viewed run is still
settling — the same general shape ISS-647 named for the dropdown ("only the reactive effect...
eventually navigated... or never if the replay failed") but on a different call site. Root cause
was not traced further here (out of scope for validation); whoever picks up analysis should start
at `DashboardLayout.tsx:2757-2789` (`onViewResults`) and page.tsx's `handleSwitchToLiveRun`
guard usage when the SOURCE route is already `/runs/<id>`.

## Root cause (analysis phase, CONFIRMED by direct code read)

The validation phase pointed at `DashboardLayout.tsx:2757-2789` (`onViewResults`) and at
`handleSwitchToLiveRun`'s guard "when the SOURCE route is already `/runs/<id>`." Both lines
still match the current tree exactly.

**The click handler itself (confirmed, `DashboardLayout.tsx:2757-2791`).** For a live/gate
notification, `onViewResults` resolves `targetRunId = n.workflowRunId ?? recentRuns?.find(...)`.
`n.workflowRunId` is always populated for a server-sourced `liveRuns` entry —
`AppHeader.tsx:194-220` builds every entry with `workflowRunId: r.id` (`:207`) whenever
`recentRuns` has data, which it does by the time of a SECOND click (the first click already
succeeded). So `targetRunId` resolves. The handler then calls `onSwitchToLiveRun(targetRunId)`
— **without `await`** — and unconditionally calls `router.push(routes.runStream(targetRunId))`
right after. There is no guard here comparing the target to the run currently being viewed, and
no check for a switch already in flight.

**`onSwitchToLiveRun` is `page.tsx`'s `handleSwitchToLiveRun` directly** (`page.tsx:4276`,
`onSwitchToLiveRun={handleSwitchToLiveRun}`). Its body (`page.tsx:2706-2797`) runs a SYNCHRONOUS
prelude — `trackedRunIdRef.current = runId`, `runStore.switchViewTo(runId)`,
`runConnection.attachRun(runId)`, `setContentSourceRunId(runId)`, `setActivePipelineRunId(runId)`,
`setSubmittedBrief(...)` — all of which take effect immediately, in the same tick as the click
(this is exactly what makes the "Starting point" card in the reproduction above show runB's brief
even when the URL stayed on runC: that card reads `submittedBrief` state, mutated directly).
ONLY AFTER that prelude does it `await getRunEvents(...)` (`:2762`) and replay each durable frame,
guarded by `if (trackedRunIdRef.current !== runId) return;` (`:2765`) — the
[ISS-657](20260917-1250-ISS-657.md) fix, which protects against a SECOND click landing on the
SAME `page.tsx` instance while the first is still in flight.

**`router.push` remounts `page.tsx` under the shared `[...view]` catch-all — this is not an
inference, it is an existing, dated code comment, read directly at `page.tsx:3374-3378`:**
"T9's router.push remounts THIS page component (Next.js does not preserve a dynamic-route page's
own instance across a client-side navigation to a new URL under the same catch-all — confirmed
live: a fresh render-instance id appears right after router.push...)." `DashboardLayout.tsx:529`
states the same fact independently. A remount does not just reset `trackedRunIdRef`'s VALUE, it
replaces the ref OBJECT (`useRef(null)` re-runs on the new instance) — so the guard at
`page.tsx:2765` is blind to a switch that a remount interrupts: it only ever sees the SAME
instance's own ref.

**The remount races `handleSwitchToLiveRun`'s own in-flight replay, and the replay usually loses.**
`useRunStateStore.ts:392-397` (`getOrCreate`) and `:404-410` (`getAgentStartTimes`) both start
`if (!mountedRef.current) return <throwaway>`. `mountedRef.current` flips to `false` in this
hook's unmount cleanup (`:335`) — which fires as part of the SAME remount that just replaced
`trackedRunIdRef`. Since `router.push` happens essentially immediately after the click while
`getRunEvents` is a real network round trip, the pre-remount instance's replay (`page.tsx:2762-
2794`) very often resolves AFTER its own `mountedRef` has gone false, so every write that replay
makes — including its final `runStore.switchViewTo(runId)` at `:2790` — lands in a throwaway
object instead of the real (module-scope since FIX-523) map. The comment at
`useRunStateStore.ts:393-396` independently documents this exact hazard ("an unmounted page's
leftover async work writes to a throwaway entry... A reopen click starts a replay here and then
router.push remounts; the new page replays the same run") for a different caller
(`handleSelectWorkflowRun`'s history-reopen path); the mechanism is identical for this card's
live-to-live switch.

**Recovery depends entirely on the freshly-mounted instance's own T11 effect**
(`page.tsx:3458-3608`, gated on `liveStreamRunIdFor(parsedView)` for a `/stream` URL). On the
fresh mount, `trackedRunIdRef.current` is `null`, so the "already loaded" fast path
(`:3466`) misses; `runConnection.liveRunIds.includes(runId)` is true (the pre-remount instance's
`attachRun(runId)` ran synchronously before the push, and `RunConnectionProvider` lives above the
router — confirmed at `page.tsx:3472-3474`), so T11 re-seeds the refs and runs its OWN
`getRunEvents` + `handleWebSocketMessage` replay (`:3523-3608`) — a SECOND, independent fetch for
data the pre-remount instance already fetched and threw away. This is a genuine, confirmed,
wasteful race, and it directly explains two of the three symptoms in the register report: the
multi-second delay (T11's own fetch is a real round trip nobody needed to pay twice), and "the
same entry may work on a subsequent click" (a retry gives the freshly-mounted T11 path another
chance to land) — the same general shape already named for the sibling dropdown bug
([ISS-647](20260917-1100-ISS-647.md)'s "only the reactive effect... eventually navigated... or
never if the replay failed", [ISS-657](20260917-1250-ISS-657.md)'s "two async requests,
last-one-in wins").

**INFERRED, not settled by a code read — the SILENT, no-recovery-at-all failure.** The above
explains delay and eventual recovery. It does not, by itself, explain why the URL sometimes never
changes at all even after a 3s wait with no retry (this card's own Cycles 1-3). The observed
"hybrid" render — old title/URL, but `submittedBrief` already showing the new run — is only
possible if NO remount happened for that specific click: a real remount tears down the whole
subtree, so a stale title next to a fresh Starting-point card on the SAME render is inconsistent
with the confirmed remount mechanism above, and more consistent with `router.push` having been
invoked but never actually committing a navigation (title/URL-driven data stayed on the old run
because nothing route-keyed ever re-ran; `submittedBrief` updated because that write happens
synchronously in the SAME still-mounted instance regardless of whether the push later commits).
No file:line read here proves why `router.push` would fail to commit. What would confirm it:
temporarily logging every `router.push` call plus every `pipelineState.pipelineRunId`/URL
transition during a live reproduction of the silent-failure case (Chrome DevTools or a
console.trace patch on `router.push`), to see whether the call fires at all, whether it
throws/rejects unobserved, or whether a competing call (e.g. `DashboardLayout.tsx:823-824`'s own
`pipelineState`-reactive `router.push(routes.runStream(incomingRunId))`, which re-fires on every
`pipelineState.pipelineRunId` change while `isRunning` is true) supersedes it before it commits.

## Fix (where it belongs)

All of the callers above already funnel through ONE shared implementation,
`handleSwitchToLiveRun` (`page.tsx:2706-2797`) — the right existing chokepoint, and where FIX-519
already established the precedent ("one guard in that one implementation... rather than N
per-caller patches"). Two changes belong there, not in the callers:

1. **Move the `router.push` call itself inside `handleSwitchToLiveRun`.** Today all four callers
   duplicate `onSwitchToLiveRun(id); ...; router.push(routes.runStream(id))` independently
   (`DashboardLayout.tsx:2733, 2750, 2790, 2953`). Centralizing the push is what lets a single
   guard refuse to re-push while a prior switch's remount is still resolving, instead of every
   caller having to remember to check. Must keep passing the caller's already-resolved `runId`
   explicitly (never re-derive from `pipelineState`) — that is FIX-519's own locked constraint and
   the reason the stale-closure bug does not reappear.
2. **Stop paying for `handleSwitchToLiveRun`'s own `getRunEvents` replay (`page.tsx:2759-2794`)
   when it is immediately followed by a push.** FIX-523's own `mountedRef` guard already proves
   that work is thrown away whenever the remount wins the race (the common case, per the timing
   argument above). T11 (`page.tsx:3458-3608`) already exists to replay a live run's durable log
   after a `/stream` mount — let it be the SINGLE owner of that job instead of two uncoordinated
   fetches racing for the same data. This is the change that would also close
   [ISS-780](20260922-1604-ISS-780.md) (the cross-remount double-click) for free, since there
   would be only one instance ever attempting the replay.

Neither change is decided here — that is the 5-fixer's call, informed by which shape produces the
smaller diff once the exact silent-failure trigger (still INFERRED above) is confirmed live. Any
fix must preserve FIX-519's locked constraints (`onGoToPipeline(runId?)` navigates to the id its
caller passes; `handleSwitchToLiveRun` drops a response once superseded) and FIX-523's locked
constraints (module-scope maps, running-only survival across unmount, per-JWT-sub scoping) — none
of those invariants are in question here, only where the navigation trigger and the replay work
live.

## Fixer addendum — the INFERRED silent-failure trigger, confirmed by code read

The competing push named above is real, and the missing link is page.tsx's
own URL-driven effects: T7/T11 re-run whenever `handleSelectWorkflowRun`
changes identity (every switch's `attachRun`/`switchViewTo` causes it), see
the OLD run's URL on the pre-remount instance with `trackedRunIdRef` already
on the new run, and re-seed the old run — whose `pipelineRunId` change makes
`DashboardLayout.tsx:838` push the old URL, and Next discards the pending
push. Full trace and fix: [FIX-635](20260922-2335-FIX-635.md).
