## What was wrong

The read-only saved-workflow screen `/workflows/{id}` rendered its agent roster as the raw
internal ids — `documentation-agent`, `prototype-specify` — while every sibling surface showed
friendly names for the identical ids: the Library page ("Documentation Agent" / "API & Technical
Writing") and this same workflow's own Composer at `/workflows/{id}/edit` ("Documentation",
"Spec Writer"). Register entry `BUG-20260828-004300-workflows-id`, reproduced 3/3 cold-start
cycles; `GET /api/user-workflows/656ca387-e69c-474d-b7ff-5fd9eb017cc0` returns
`agent_ids: ["documentation-agent", "prototype-specify"]` verbatim, so the gap was in the
component, not the API.

## Root cause

`frontend/src/components/savedworkflows/WorkflowDetailView.tsx:29` read `workflow.agent_ids`
straight off `UserWorkflowSummary` and `:52-56` rendered `<li>{id}</li>` — no id-to-name lookup
step of any kind. The component never called `useAgentLibrary()`, unlike
`ComposerPage.tsx:207,272-281` and `LibraryPage.tsx:497`, which both resolve the same ids through
`allAgents` (Redux, populated from `GET /api/agents/library`).

A catalog-only lookup would still have been wrong for composed steps (ISS-490): a "+ Sub-agent"
add mints an instance via `instantiateIfTemplate` (`frontend/src/store/api/userWorkflows.ts:186-204`)
whose real, user-typed name is persisted on the manifest step by `agentToManifestStep` (`:207-213`),
never added back to the catalog — so `allAgents.find(a => a.id === id)` misses for
`custom-agent:<instance_id>` and the row would have fallen back to the raw slug again, or to the
template's placeholder `"New agent"`.

## What changed and why there

One file, `frontend/src/components/savedworkflows/WorkflowDetailView.tsx` — its only call site is
`frontend/src/app/[...view]/page.tsx:3820`, and a grep of all 34 `agent_ids` consumers in
`frontend/src` confirms it was the only renderer of raw id strings (`SavedWorkflowsPage.tsx:255,329,380`
and `CanvasNode.tsx:126` read the field for a count only).

```tsx
const displayName = (id: string) => {
  const bare = id.startsWith(CUSTOM_AGENT_PREFIX) ? id.slice(CUSTOM_AGENT_PREFIX.length) : id;
  return (allAgents.find((a) => a.id === id) ?? findAgentInTree(manifestAgents, bare))?.name ?? id;
};
```

- Catalog first (`useAgentLibrary().allAgents`) — the established pattern, and ISS-327's fix.
- Then the workflow's own manifest: `manifestStepsToAgents(workflow.manifest?.steps ?? [], ...)`
  reconstructs the saved node tree exactly as `ComposerPage` does on reopen, and the existing
  exported `findAgentInTree` walks it, so a step nested under a parent resolves too. Reusing the
  three existing exports rather than re-deriving the walk is what ISS-490's proposed fix asked for.
- `CUSTOM_AGENT_PREFIX` de-prefixing is what bridges the two id shapes: `manifestStepToAgent`
  (`userWorkflows.ts:428-447`) keys a custom step on its bare `instance_id`, while `agent_ids`
  can carry the backend form `custom-agent:<instance_id>`. Stripping the prefix before the tree
  lookup covers BOTH persisted shapes with one expression and no name branching.
- The raw id survives only as the last-resort fallback, e.g. before Redux has loaded the library.

Deliberately NOT done: the role/subtitle line the ISS-327 card lists as "ideally". When the
catalog has not loaded, `manifestStepToAgent` sets `role: id` for a built-in step, so rendering
the role would print the raw slug back as a subtitle — the exact symptom this fix removes. Name
only; no test asserts the role, and the roster pill's single-line layout is unchanged.
