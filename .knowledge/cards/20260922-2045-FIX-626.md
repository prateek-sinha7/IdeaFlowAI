# FIX-626

Closes `BUGS.md#qa-ps-042` — "Admin page calls GET /api/me twice and
GET /api/users twice".

## What was wrong

Reaching `/admin` through an in-app (SPA) navigation — account menu →
"Admin Dashboard" — fetched `GET /api/auth/me` and `GET /api/admin/users`
twice each. A cold reload fetched each once.
[ISS-789](20260922-1818-ISS-789.md) reproduced the SPA path 3/3 and the
cold path 0/3; [ISS-816](20260922-1931-ISS-816.md) completed the root cause
and the blast radius.

`GET /api/auth/me` was **already closed before this fix** by
[ISS-801](20260922-1834-ISS-801.md)'s `cachedGet()` on `getMe()`
(`frontend/src/lib/api.ts:609-615`) — verified by direct read, not assumed.
Only the user list was still doubling, which is why the shipped test asserts
on `/api/admin/users` alone.

BUGS.md's own hypothesis — that `AppHeader` is a second, independent `getMe`
caller on this page — is wrong and stays wrong; ISS-816 proved
`admin/page.tsx` renders neither `AppHeader` nor `DashboardLayout`.

## Root cause

`frontend/src/app/admin/page.tsx:177-198` — the boot effect has no
`AbortController`, no in-flight `useRef` and no cache:

```tsx
getMe(token).then(user => {
  if (!user.is_admin) { router.replace(routes.dashboard()); return; }
  setCurrentUserId(user.id);
  loadUsers(token);           // -> adminListUsers(t)
}).catch(...);
```

React 18 StrictMode double-invokes that mount in `next dev`
(`frontend/next.config.ts` carries no `reactStrictMode: false`), so both
fetches ran twice. `adminListUsers()`
(`frontend/src/lib/api.ts:1671`, pre-fix) was a bare `request()` call with
zero dedupe — unlike `getWorkflows()` (`inFlightWorkflows`, FIX-616) or
`getMe()` (`cachedGet`, ISS-801).

## What changed, and why there

**1. `frontend/src/lib/api.ts` — single-flight `adminListUsers()`
(ISS-789 + ISS-816).** A token-keyed `inFlightAdminUsers` map, a structural
copy of `inFlightWorkflows` (FIX-616) sitting a few hundred lines above it.
Concurrent callers share one open request; the entry is dropped the moment
it settles, so any later refetch still goes to the network.

The fix lives in `lib/api.ts`, not in `admin/page.tsx`, for ISS-816's
reason: `/admin` is a literal Next.js route folder alongside the `[...view]`
catch-all, so a catch-all-scoped guard cannot reach it, and a per-component
`useRef` would leave every future caller unguarded.

**Where this deviates from ISS-816's literal proposal, and why.** ISS-816
proposes generalizing the guard into `request()`/`fetchWithAuth()` for ALL
GETs. That was deliberately not done, and the narrower per-function guard
was used instead:

- ISS-816's own grep is what makes the broad version unnecessary here:
  `adminListUsers` has exactly ONE non-test call site
  (`admin/page.tsx:168`) — re-verified at fix time, still one — and
  `getMe`'s four other call sites are already covered
  (`cachedGet`, ISS-801). There is no third caller for a blanket guard to
  reach.
- `api.ts:394-404`'s own comment documents the invariant a blanket guard
  would break: run/workflow lists "deliberately do NOT" get deduped,
  because their callers refetch precisely to observe a change. A GET issued
  11 ms after a mutation, while an unrelated identical GET is still open,
  would be served the pre-mutation response.

Same root cause, same file, same choke point; only the radius is narrower
than the card's sketch. Noted here rather than silently.

**2. `frontend/src/app/admin/page.tsx` — re-entrancy guards on Delete and
the admin-role toggle ([ISS-818](20260922-1933-ISS-818.md)).** A separate
mechanism in the same file: `handleDeleteUser` (`page.tsx:244`) and
`handleUpdateRole` (`page.tsx:213`) had no in-flight guard, unlike their own
siblings `handleCreateUser` (`disabled={creating}`, `page.tsx:530`) and
`TierDropdown` (`disabled={loading}`, `page.tsx:86`), so a fast double-click
fired two concurrent mutations — the second `DELETE` 404-ing after the first
landed and flashing "Failed to delete user" on a deletion that succeeded.
Added `deleting` (boolean — one confirm modal at a time) and `rolePending`
(a list of user ids — separate rows are independent actions and must not
block each other), mirroring the guards already in the file. Per ISS-818
this one belongs locally, NOT in `lib/api.ts`: two rapid genuine deletes of
DIFFERENT users must never be coalesced.
