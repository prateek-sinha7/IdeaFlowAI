## Why the root cause implies it

Same mechanism as the rest of [ISS-1158](20261009-1510-ISS-1158.md): a literal copy of a fact that changed underneath it, here the database instead of the app. `14ce62c59` (2026-09-22) named this exact shape ("FIXTURES PINNED BY RUN ID. Six scenarios named a UUID that had been pruned OR - worse - reassigned by a reseed") and converted six scenarios to runtime discovery. It also edited these same six files for other reasons (`test_iss285` 6 lines, `test_iss313` 7, `test_iss390` 6, `test_iss_606_609` 85, `test_iss_607_610_611_612` 195, `test_iss228` 1) and left their ids pinned, because the ids still existed that day; the dev database's oldest run is dated 2026-09-24. The register's own file says it was a known debt: "These rot whenever the database is pruned; the durable fix is runtime discovery via a_run_with_status(page, "completed")" (`test_iss_230_version_pin_survives_tab_switch.py:20-21`). `suites/07_run_detail/test_iss314_preview_toolbar_fullscreen_offscreen.py:15-18` shows the pattern to copy ("The run is discovered rather than pinned").

## What is wrong beyond "the ids are gone"

1. Two tests pass without exercising anything. S-285 asserts the Audit tab is NOT selected and S-390 asserts the Preview tab IS selected, on a run that does not exist. INFERRED mechanism (what the shell renders for an unknown id was not measured); CONFIRMED that the runs are absent and the tests passed.
2. `test_iss228` can never flip. It is `xfail(strict=True)` on [ISS-228](20260828-1758-ISS-228.md), which is still `open`, and it now fails for a 404, so a fix for ISS-228 would not be noticed. The other test in that file finds the workflow by name and works.
3. Pointing suite 21 at a live family will not turn it green. QA-KB-111 is REOPENED-VALIDATE (High): on a live family (78e185fb, v2 80054fbc) the Steps and Audit tabs ignore the pin on a cold load (`BUGS.md` QA-KB-111, "Reopened 2026-10-09"). After discovery these tests exercise that defect; expect red for that reason, and mark them `xfail(strict=True)` citing the QA-KB-111 card only once they are seen failing for it.
4. The three `run-header ... button[aria-haspopup='listbox']` timeouts QA-KB-111 asks to separate from the app are not selector drift: `frontend/src/components/preview/RunHeader.tsx:101` still renders `aria-haspopup="listbox"` and `framework/locators/run_detail.py:39` still has the testid. The likely cause is the missing run. INFERRED.

## Fix direction (test-side only)

- Replace every literal with discovery, skipping with a precise reason when the dataset cannot supply one (the `14ce62c59` rule). Helpers already exist per suite: `a_run()` (`suites/21_.../test_run_families_and_versions.py:144`), `a_run_with_status` (`suites/14_.../test_run_states.py:35`, `suites/18_.../test_chat_lane.py:83`, duplicated). A family of two or more can be found from `GET /api/runs?limit=100` (rows carry `root_run_id`, `backend/app/api/runs.py:140`) and confirmed with `/api/runs/{id}/family`, as `a_run()` does for a family of one.
- Do not seed the database with the old ids. The data owner is QA-KB-123 ("e2e test data lacks a v1 prototype run"); a dataset change belongs there.
