## Thread ectx.current_step into the engine's per-agent model resolution

Fixes [ISS-164](20260819-1726-ISS-164.md) — see that card for the root cause.

**Change** (`backend/agents/execution_engine/engine.py:4156`, one line):

```python
# before
model=self._resolve_model(ectx, spec, model_id),
# after
model=self._resolve_model(ectx, spec, model_id, step=ectx.current_step),
```

`ectx.current_step` was already the correctly-bound compiled Step at this exact point
in the dispatch loop (read a few lines below for `injects`/`skills`/`prompt`/`tools`),
so this reuses an existing, proven seam rather than introducing a new one.

**Parity:** for any run with no per-step `model` selection, `step.model` is `None` and
tier 2 is skipped exactly as before — byte-identical to pre-fix behavior (the removed
comment's own "06-04... unchanged" note). Behavior only changes when a `selections`
overlay actually sets a per-step model — which is exactly the case that was silently
broken.

**Known coverage gap (disclosed, not closed by this fix):** no test exercises this
exact call site end-to-end (a full `_run_agent` dispatch with a `selections` overlay
asserting the resulting `ctx.model`). `test_model_resolver.py` proves `ModelResolver
.resolve()`'s tier-2 logic is correct in isolation, calling it directly with an
explicit `step` — it does not prove the engine actually passes one. A future regression
reverting this kwarg would not be caught by any existing automated test. Recorded here
rather than closed silently; an integration test is future work if wanted.
