## Related

This branch added `handleSessionExpiry()` (FR-015): a 401 clears the token and sends the
browser to `/login?expired=true`, except on exempt paths. `dev` independently added a
Cognito 401 refresh-and-replay. Both were splitting the SAME base `request()`, so the
merge had to choose an order — neither parent contains this code.

```
401 ──► can we refresh?          (Cognito)
         │ yes → replay once with the fresh bearer, retryOn401 = false
         │ no  → the session really has ended   (FR-015)
         └────► handleSessionExpiry(), unless the path is exempt
```

## Why refresh comes first

Cognito access tokens live ~60 minutes, so a mid-session 401 is usually just an aged
token. Firing `handleSessionExpiry()` on that first 401 — which the FR-015 half did alone
— would log every user out about hourly. Refreshing first is the whole reason the two
halves compose rather than conflict.

The refresh is single-flighted (`refreshOnce`): a screen fires several requests at once,
so one expiry produces a burst of 401s, and without the guard each would mint its own
refresh with the losers installing a superseded token.
