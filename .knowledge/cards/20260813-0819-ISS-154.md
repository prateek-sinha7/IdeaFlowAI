# ISS-154

## Title

**Switching the in-family version picker to an OLDER, non-latest revision whose `.output` is NULL shows a blank "Output will appear here" preview instead of the deliverable, or any explanatory message.** `frontend/src/components/preview/PreviewPanel.tsx:528-543`, `handleSelectVersion`: `const run = await getWorkflow(token, memberId); setViewingVersion({ id: memberId, content: run.output })` — no fallback for a null `.output`. Reproduced live: opened the `SSEPROOFDROP` family (parent `a5d059e1...`) after FIX-250's live test added a v3 revision, making the pre-existing, deliberately-not-backfilled v2 (`8a970205-5892-466a-89b0-f613b9dd021d`) non-latest for the first time; explicitly selecting "Version v2" in the picker showed the read-only banner correctly but an EMPTY preview pane, while the left-column chat/KPI header stayed stuck on the v3 numbers. This is a DIFFERENT code path from the one already verified working (opening a family whose target revision IS still the latest, which uses different, richer content props supplied at mount) — not a contradiction of that finding, an addition to it. Confirmed NOT introduced by FIX-250: FIX-250's diff is 100% backend (`run_commands.py`), touches no frontend file, and `8a970205`'s own data is byte-unchanged before/after (`GET /api/runs/8a970205...` still returns `token_usage: None` both times). Blast radius bounded going forward: every NEW revision now gets a real `.output` (FIX-250), so the trigger condition (a completed revision with NULL `.output`) will not recur except for the small, fixed, already-existing set of pre-FIX-250 rows — a shrinking, historical-only exposure. Proper fix: `handleSelectVersion` should fall back to a distinct empty/degraded-state message (not the generic "no content yet" placeholder, which reads as if the run never produced anything) when `run.output` is null for a terminal, non-degraded run — or the backfill decision (surfaced, not performed, alongside FIX-250) would also close this for the one existing affected row.

### Root cause (CONFIRMED)

`PreviewPanel.tsx:1825-1828` is the Preview tab's last-resort branch and carries exactly one string:

```tsx
) : !hasContent ? (
  <div className="flex items-center justify-center h-full">
    <p className="text-xs text-ink-400">Output will appear here</p>
```

It is the only occurrence of that copy in `frontend/src` (grep), so every "nothing to show" state that survives the branches above it gets this future-tense "waiting" text.

For a read-only pinned version (`viewingVersion != null`, `overrideActive` at `:1056`; set only after `getWorkflow` resolved, at `:914` for `handleSelectVersion` and `:1017` for the URL-pin effect), `hasContent` (`:1109`) is false when the fetched run has no stored output: `versionViewFrom` maps `content: run.output` (`:635`) and `genericDeliverable: run.output ? {...} : undefined` (`:665`). No branch ahead of `:1825` looks at the pinned run. Each is keyed on the SHELL's props:

- `isStillRunning = !!(isStreaming || pipelineState?.isRunning)` (`:1120`);
- `liveFailureSignal` from the raw `pipelineState.failed/.degraded` (`:1122`), `reopenFailureSignal` / `isCancelledTerminal` / `isDivertedTerminal` from `reopenedRunStatus` (`:1127-1143`), hence `showFailureAffordance` (`:1132`) and `showDivertedAffordance` (`:1144`);
- `isLoadingRunData` (`:1813`), the shell's own reopen fetch.

And `versionViewFrom` drops the pinned run's `status` (only `failed: run.status === "failed"` survives, `:655`, inside a `pipelineState` that only the Steps tab reads). So the panel cannot tell "settled, nothing stored" from "nothing yet".
