# FIX-757

## What was wrong

Bug report QA-KB-081 (Low). The root cause and blast radius come from the 2026-10-07 analysis on
[ISS-909](20261001-2216-ISS-909.md) and its sibling [ISS-1088](20261007-2245-ISS-1088.md). They were not re-derived
here. Every quoted line was re-read in the working tree before editing (HEAD `2005a0a6b`, `LaunchWizard.tsx` blob
`42fa4728d`, unmodified).

- **[ISS-909](20261001-2216-ISS-909.md), the root.**
  - The registry had one state, the array: `const [systems, setSystems] = useState<DesignSystemListItem[]>([]);`.
    So `[]` meant loading, failed and "loaded, none" all at once.
  - The fetch ended in `.catch(() => { /* non-fatal — the picker stays empty */ });`. A failure was dropped.
  - `dsSlot` rendered `systems.length === 0 ? <div className="h-48 animate-pulse ..."/> : <DesignSystemPicker/>`.
    An empty value was always shown as loading.
  - The result was a pulsing box that never resolved, with no message. Continue stayed disabled and the
    "Pick a design system" pill stayed up. The skeleton also hid the picker's "Upload custom" button, the one way
    past the gate that does not use the registry.
- **[ISS-1088](20261007-2245-ISS-1088.md), the sibling.**
  - The deck branch of the template effect had
    `.catch((err: Error) => { if (cancelled) return; if (err.message.startsWith("401")) { handleSessionExpiry(); } })`.
  - The web branch also calls `setLoadError(err.message)`. The deck branch did not, so a non-401 failure was
    dropped. The deck gallery then said "No templates match your search." and showed no banner.

## What changed, and why there

One file, `frontend/src/components/workflow/LaunchWizard.tsx`, 4 hunks. The full diff is in
`evidence/qa-kb-081/11-fix-diff.txt`. There is no shared function to route through: the other caller of
`listDesignSystems`, `composer/DesignPickerModal.tsx`, already handles a failure correctly (the ISS-909 blast radius
says so).

1. **State (`:250-255`).** Added `systemsLoad` (`"loading" | "ready" | "failed"`, the same idiom as `overrideLoad`),
   `systemsError`, and `systemsAttempt` (the Retry counter). They sit next to `systems`.
2. **DS effect (`:707-741`).**
   - `.then` now also sets `systemsLoad` to `"ready"`.
   - The empty `.catch` now keeps `err.message` and sets `"failed"`. It still honours the effect's `cancelled` flag.
   - The deps went from `[authChecked, router]` to `[authChecked, router, systemsAttempt]`.
   - FIX-103's auto-select is untouched, including its `if (prev !== null) return prev` guard.
3. **`dsSlot` render (`:1408-1448`).**
   - The skeleton now renders only while `systemsLoad === "loading"`.
   - **Failed:** a `role="alert"` box ("Couldn't load design systems: {message}") with a Retry button.
   - **Ready but empty:** the same box in neutral StepNote styling, saying "No design systems are available.", with
     a Retry button.
   - `DesignSystemPicker` renders under the box in both of those states, and alone once the list loads.
   - Retry sets `"loading"` and bumps `systemsAttempt`. That re-runs the effect, and its cleanup cancels any older
     request.
4. **Deck template catch (`:698-702`, ISS-1088).** Changed `{ handleSessionExpiry(); }` to
   `{ handleSessionExpiry(); return; }` and added `setLoadError(err.message);`, so it now matches the web branch
   (`:690-694`) line for line. The existing generic banner (`Couldn't load templates: {loadError}`) shows it.

### Two places this differs from the card's sketch, on purpose

- **Retry uses a counter in the deps, not a `useCallback` plus a request-counter ref.**
  - The analysis said a callback would need a ref-based guard against stale responses. A counter in the deps
    re-runs the same effect, so its existing `cancelled` flag is that guard: a newer Retry, or an unmount, cancels
    the older request.
  - The FIX-630 constraint still holds. The new dep changes only when the user clicks Retry, never on a family
    toggle.
  - Retry sets `"loading"` in the click handler, not inside the effect, so there is no new
    `react-hooks/set-state-in-effect` error. The eslint set did not change.
  - Decided on purpose: a successful Retry runs FIX-103's auto-select with the `mode` currently on screen. The
    `prev !== null` guard means it can never replace an existing choice. Checked both ways: a fresh prototype gets
    "apple", and a restored draft keeps "midnight" (evidence 09, scratch tests).
- **The empty state also has a Retry button.**
  - The card warns against "offering Retry as the remedy for an empty list", because the backend caches `[]` until
    it restarts.
  - BUGS.md's Expected asks for "an explicit error (with a retry)" for both failed and empty. The test-writer's
    test asserts a Retry button in both arms. Neither was edited.
  - So the empty arm follows the card's wording: a neutral "No design systems are available." note, no error
    styling, no `role="alert"`. It keeps the Retry button, which does help once the backend is restarted with the
    directory in place.
  - If the owner wants no Retry in the empty arm, the test-writer's empty-arm assertion has to change first.

### Not done, per the analysis

- Relaxing `canContinue` (`:967`, `:970`) or the pill (`:1497`) when the registry is missing. That is a product call.
- Changing the backend's `200 []` for a missing OpenDesign directory (`od_loader.py`). That is an API-contract
  decision.
- The gallery wording "No templates match your search." for an empty deck catalog. The ISS-1088 card calls it a
  separate cosmetic decision that is not needed to close.
- Resetting `loadError`. No path can clear it today, because the Web/Deck toggle is hidden.

### Known edge, not filed

A Retry clicked after the token has gone, for example after signing out in another tab, hits the effect's
existing `if (!token) return;`, so the skeleton stays. The code before this fix had the same early return and no
Retry at all. Every other action in that tab gets a 401 and goes through `handleSessionExpiry`. The user is not
stuck, so no card was minted for it.
