## What is suspected

[ISS-345](20260828-1900-ISS-345.md) root-caused the reported symptom (removing an attachment
chip never strips the `[Attached: <filename>]` marker it wrote into `ideaInput`, so the
textarea stays keyed to a phantom attachment) purely in terms of its UI-visible effect: the
"Run Workflow" button's `disabled` gate reads the same stale `ideaInput`.

`ideaInput` has a SECOND reader in the same file — `handleRun` (`WorkflowView.tsx:161-166`):

```ts
const handleRun = () => {
  if (!ideaInput.trim()) return;
  if (onStartPipeline) {
    const agentIds = pipelineAgents.map((a) => a.id);
    onStartPipeline(selectedType, ideaInput.trim(), agentIds);
  }
};
```

This passes `ideaInput.trim()` straight through as the run's message/brief. Nothing here (or
anywhere else in the file) strips an orphaned marker before forwarding it, and `attachedFiles`
itself is never forwarded into `onStartPipeline` at all — only `selectedType`, the trimmed idea
text, and `agentIds` are passed.

Today this reader is unreachable: [ISS-328](20260828-1834-ISS-328.md) established (3/3,
`browser_network_requests` diffed) that `onStartPipeline` is `undefined` on `/workflow`'s sole
production mount, `app/workflow/page.tsx:58-62`, so `handleRun`'s `if (onStartPipeline)` guard
fails silently and 0 network requests fire. [ISS-492](20260829-0150-ISS-492.md) independently
confirmed the same caller also never supplies `pipelineState`/`onResetPipeline`/`onViewResults`.

## Condition

Given ISS-345's marker-persists mechanism, AND a caller of `<WorkflowView>` that supplies a
real `onStartPipeline` (which requires [ISS-492](20260829-0150-ISS-492.md)'s unwired-prop gap
to be closed first, since no caller does today): attach a file, remove it (marker persists per
ISS-345), then click "Run Workflow".

## Expected vs actual

**Expected:** a run launched after the user removed an attachment should carry a brief that
matches what is actually attached — no reference to a file the user explicitly removed.

**Actual (INFERRED):** once `onStartPipeline` is wired, `handleRun` forwards
`ideaInput.trim()` — which can contain ISS-345's orphaned `[Attached: <filename>]` string —
as the literal run brief. The pipeline/agent receiving that brief is told an attachment exists
that the run payload does not actually carry (since `attachedFiles` itself is never sent), which
is a run-DATA-integrity defect distinct from ISS-345's UI-only symptom (button stays enabled)
and from ISS-328's silent no-op (no request fires at all today).

## Why the root cause implies this

Same broken invariant [ISS-345](20260828-1900-ISS-345.md) already names — the remove handler
(`WorkflowView.tsx:388`) never reconciles `ideaInput` — observed through a second, independent
reader of that same field. The disabled-button check is one consumer of `ideaInput`; `handleRun`'s
payload construction (line 165) is another. A fix that patches only the `disabled` check (or
only the button's own read) would leave this second reader still forwarding the same corrupted
text the moment ISS-492's wiring gap closes. This is why the fix belongs where `ideaInput` is
actually mutated — the remove handler at line 388 — rather than in either reader: patch the
write site once and every present and future reader of `ideaInput` (button gate, `handleRun`, or
anything else added later) inherits the correction for free.

**Marked INFERRED in full**: not independently reproducible via the current UI — ISS-328
empirically confirmed 0 network requests fire from this route's Run button, and ISS-492's static
analysis shows `step` can never leave `"build"` because `onStartPipeline`/`pipelineState` are
never supplied by the one production caller. What would settle it: a unit test that mounts
`<WorkflowView>` with a mocked `onStartPipeline`, attaches a file, removes it, clicks Run, and
asserts the mock's second argument (the message) does not contain the substring `[Attached:`.

## Analysis (QA-KB-019, analyzer, 2026-10-01)

**Verdict.** This card's invariant stands: a run launched after the user removed an attachment must not carry that file's
marker. What breaks it today is narrower than the mechanism the card was written about.
[FIX-400](20260829-0402-FIX-400.md) closed "the remove handler never touches `ideaInput`" by adding `stripAttachmentMarker`,
but that helper is not the inverse of the writer for a filename containing `]` or `, `. Not superseding this card: its meaning
(a stale marker reaches `handleRun`) is unchanged; this section records the mechanism that is left. **Root cause CONFIRMED**:
every line below was read in the working tree, and the live function was run (probe below).

### Root cause (CONFIRMED)

The attach handler serialises names into free text using delimiters that are legal inside a filename, and the remove path
re-parses that text with the same delimiters.

- Write, `frontend/src/components/workflow/WorkflowView.tsx:353-354`:
  ``const fileNames = newFiles.map((f) => f.name).join(", ");`` then
  ``setIdeaInput((prev) => prev ? `${prev}\n\n[Attached: ${fileNames}]` : `[Attached: ${fileNames}]`);``
- Parse, `WorkflowView.tsx:88`: `.replace(/(\n\n)?\[Attached: ([^\]]*)\]/g, ...`. The class `[^\]]*` ends the capture at the
  FIRST `]`. For `[Attached: my].txt]` the captured names are `my`, not `my].txt`.
- Split, `WorkflowView.tsx:90`: `const remaining = names.split(", ");`. A name containing `, ` is cut into pieces.
- Both halves end the same way: `remaining.indexOf(filename)` is `-1`, and `WorkflowView.tsx:92`
  (`if (at === -1) return match;`) hands the text back unchanged.
- The helper has exactly one caller, the chip's remove handler, `WorkflowView.tsx:403-404`:
  `setAttachedFiles((prev) => prev.filter((_, i) => i !== idx));`
  `setIdeaInput((prev) => stripAttachmentMarker(prev, file.name));`
  The chip goes and the marker stays, which is [ISS-345](20260828-1900-ISS-345.md)'s symptom again, now only for names
  containing `]` or `, `.

Why it was missed: [FIX-400](20260829-0402-FIX-400.md) designed the helper against delimiter-free names, and the tests it
shipped use `zz-hunt-*.txt` (`WorkflowView.attachmentRemove.test.tsx:63,79,115`).

### Where the fix belongs

In `WorkflowView.tsx`, in the helper that undoes the writer's format (`:85-98`). The writer (`:354`) and that helper are the only
two places in the component that touch the format, and the helper has one caller, so no call site changes: the handler at `:404`
and `handleRun` stay as they are, and every reader of `ideaInput` inherits the correction, which is the argument this card
already made. Keep the writer byte-identical: `cleanBrief` and persisted legacy briefs read this exact format.

### The agreed minimal fix (BUGS.md Notes): accepted in part, overruled in part

- ACCEPTED: match the literal filename instead of splitting the block's contents. That is what cures both halves.
- OVERRULED as written: the terminator guard `\[Attached: (.*?)\](?=\n\n|$)`. The textarea is free text and the user can type
  straight after the `]` (`[Attached: a.txt] more words`). The current code handles that; the guarded regex does not, so the
  fix would trade this stale-marker bug for another. Probe: `current` passes "typed text right after marker (same line)", the
  Notes' version fails it (marker left in place), and both fail `[Attached: my].txt] more` (text after, name with `]`). Overall the
  Notes' version passes 20 of 22. With a name that may contain `]`, the end of the marker is inherently ambiguous, so do not try
  to find it; anchor on where the name can sit (right after `[Attached: ` or `, `, right before `, ` or `]`).
- ALTERNATIVE in the Notes (replace `]` and `,` in names at write time): a workable fallback, not recommended. It makes the
  marker diverge from `file.name` and rewrites what text is forwarded as the brief, and the stripper must then apply the same
  sanitiser, so two places must agree. If chosen, use one shared helper in writer and stripper.
- ACCEPTED and extended: add a test case with a name like `a, b].txt` (see the handoff below).
- Not a product decision, so not escalated. (Dropping the in-band marker altogether and composing it at submit time would end
  the whole class, [ISS-345](20260828-1900-ISS-345.md), [ISS-583](20260829-0234-ISS-583.md), this card and QA-KB-019, but it
  changes what the textarea shows and contradicts the assertions at `WorkflowView.attachmentRemove.test.tsx:66,90`. That is a UX
  call, not needed to close this bug.)

### Recommended implementation (sketch; the analyzer does not edit source)

```ts
// WorkflowView.tsx, replaces :85-98. The writer at :354 stays as is.
function stripAttachmentMarker(text: string, filename: string): string {
  const n = filename.replace(/[.*+?^${}()|[\]\\]/g, "\\$&");
  return text
    .replace(
      // sole entry | later entry | first of several; each anchored on "[Attached: ", none looks for the closing "]"
      new RegExp(`(\\n\\n)?\\[Attached: ${n}\\]|(\\[Attached: [^\\n]*?), ${n}(?=, |\\])|(\\[Attached: )${n}, `),
      (_m, _sep, keepMid, keepHead) => keepMid ?? keepHead ?? "",
    )
    .trim();
}
```

Non-global on purpose: one entry per call, as today (a file attached twice loses one entry per chip removed). Probe result:
22 of 22, including `]` and `, ` in one name, two batches, two files in one block with the odd name first or second, text typed
after the marker on the same line, a name that is a prefix or suffix of another, and user prose that mentions the same
filename before the marker. No regex-escape helper exists in `frontend/src` to reuse (searched), so the escape is inline.
Known limits: a name containing a newline; two markers typed onto one line; a marker the user hand-edited (same as today).
