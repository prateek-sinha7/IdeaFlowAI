- **Found:** 2026-07-17 (user asked whether the reply lands in the correct sequence). After BUG-017 made the reply render, the reply REPLACES the user's question in-place — they never coexist (the optimistic question bubble shows ~11s while pending, then vanishes the instant the reply lands), AND the reply is not the last item (the `PIPELINE · 6 AGENTS` mini + `user_stories.md` deliverable footer cards render below it). Verified LIVE 3 ways (DOM child-order dump; per-500ms temporal probe U1A5 → U0A6 at t=11.6s; screenshot pair) + in code + on the wire.
- **Root cause (orchestrator-verified in DB + code):** TWO issues. (1) OVERWRITE (the real bug): the durable `chat_reply` is persisted with a DISTINCT `event_id` COLUMN (`chat-reply:{message_id}`) but its `payload_json` contains NO `event_id` key — only `message_id`, which EQUALS the paired user `chat_message`'s `message_id` (both `client-1-…`; verified in `run_events`). `frontend/src/lib/api.ts::getRunEvents` (:562-564) maps each row to `{type, data: row.payload_json}` — it DROPS `row.event_id` (and `row.seq`). So on the FE re-fetch path `data.event_id` is undefined → `upsertNarratorMessage` (`frontend/src/hooks/useRunChat.ts:239-244`) falls back to `data.message_id` → `findIndex` matches the existing USER turn (same id) → `:261` overwrites it in place with `role:"assistant"`. The DEF-44-12-2 de-collision (which keys the reply on its distinct event_id) is DEFEATED because getRunEvents never surfaces event_id into the frame. PRE-EXISTING latent bug, EXPOSED by the BUG-017 fix (before, the reply never folded in at all, so the collision never fired). (2) NOT-LAST: `frontend/src/components/chat/ChatPanel.tsx` renders `{messages}` then `{transcriptFooter}` then the scroll anchor; `RunChatLane.renderTranscriptFooter` (`RunChatLane.tsx:1021-1051`) returns the pipeline-mini + deliverable cards for a `complete` run — always the last DOM children — so any newly-appended reply sits ABOVE them (by design; a UX call, not a data bug).
- **Fix (PROPOSED, FE-only, NOT applied — awaiting user go):** (1) OVERWRITE — in `getRunEvents` surface the row's distinct id + seq into the frame data: `data: { ...(row.payload_json ?? {}), event_id: row.event_id, seq: row.seq }` (matches the getRunEvents docstring intent that consumers key on `event_id`/`seq` INSIDE the frame). Then `data.event_id` = `chat-reply:{message_id}` (distinct) → the reply appends as its OWN turn BELOW the question (the intended behavior), and `data.seq` correctly advances the re-fetch cursor. RED→GREEN: a `useRunChat` test where a chat_reply frame with event_id `chat-reply:X` + message_id `X` (== a prior user turn `X`) appends as a SECOND turn and does NOT overwrite the user turn. (2) NOT-LAST — design decision for the user: keep the run-summary footer pinned below the chat (current), or let the latest reply be the true last item.
- **Relationship to BUG-017:** BUG-017's DELIVERY is genuinely fixed (the reply now renders; before, nothing appeared). BUG-018 is the presentation bug that fix EXPOSED. Distinct fix (getRunEvents), distinct file.
