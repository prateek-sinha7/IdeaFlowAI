## The symptom

Two runs died long after the real mistake, on artifacts nobody checked at the
moment they were produced.

**One stray `]`.** A 90 KB `tasks.json` was written with a single bracket out of
place. The write tool reported success. 279 seconds of correct planning later,
the next agent read it, and the run died with a JSON error carrying no trace of
the write that caused it.

**A short first fence.** `json_tasks` read only the FIRST fenced block in the
agent's reply and trusted whatever count it found. A run wrote 11 tasks where
the plan had 58, and the wave shipped a fifth of the work with no error
anywhere.

## The root cause

Not two bugs — one seam. A model-written artifact was accepted as bytes and only
interpreted much later, by something that had no way to say *who* produced it or
*when*. A write tool that reports success on any bytes moves every malformed-file
error one or more steps downstream.

Prompting harder had already been tried. That is why these runs existed.

## What changed

**`ValidatingFilesystemBackend`** (`app/agents/validating_backend.py`, 141 lines,
new). A `FilesystemBackend` subclass that wraps `write()` and `edit()`: any path
ending `.json` must parse before the write commits. Three details are
load-bearing:

- The path check is `file_path.rstrip().lower().endswith(".json")` — the
  `rstrip` stops `"tasks.json "` slipping past.
- On failure the file is left **byte-identical**. The prior content is read with
  `newline=""` so CRLF stays CRLF, and the restore is reported rather than
  swallowed when it itself fails.
- The parse error goes in the **tool result**, precise enough for the agent to
  repair it in the same turn.

Files are opened with `O_NOFOLLOW` where the platform has it.

**`json_tasks`** (`agents/capabilities/task_parsers/json_tasks.py`, +48).
`_strip_json_fence` now treats EVERY fence in the text as a candidate, in order,
keeping the first that actually parses — falling back to the first fence's
content so nothing that used to work stops working. A reply that opens with some
other fenced block no longer hides the plan sitting further down it.

And a wrapper object may now carry `contract.task_count`; when present it must
equal the parsed task count, otherwise `parse` refuses with
`"json_tasks: plan incomplete - contract.task_count=N …"`. Backward-compatible:
a plan with no `contract` dict is unchanged, so a short fence can still ship
silently for a plan that declares no count. If you want the guarantee, declare
the count.

## Why this card exists

`validating_backend.py`'s architecture file card is auto-generated and carries
nothing but a dependency graph. This is the only written rationale that module
will have: **validate at the tool layer, leave the file byte-identical on
refusal, put the reason in the tool result.** The two instances above are
examples; the seam is the point.
