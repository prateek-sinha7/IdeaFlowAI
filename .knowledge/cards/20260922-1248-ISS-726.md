# ISS-726

Register entry: **QA-PS-031** (`BUGS.md`), filed as a sibling of [ISS-723](20260922-1245-ISS-723.md)
— "the same code on a[nother] workflow" category.

## Status: INFERRED — mechanism confirmed by code, live symptom not yet observed

Filed from [ISS-723](20260922-1245-ISS-723.md)'s CORRECTED mechanism (see that card's own
"Correction" section, cross-confirmed by the independently-filed [ISS-727](20260922-1235-ISS-727.md)
against QA-PS-030), applied to a second workflow by the same reasoning, not from an independent
live reproduction. See "What would confirm this" below — this is a lead for the validator/hunt
line, not a closed defect.

## Why the root cause implies this

[ISS-723](20260922-1245-ISS-723.md) (as corrected) draws the real boundary precisely: the defect
bites any revision workflow whose agent (a) is on a deliverable strategy that only ever
materializes into `.chain/` (`ppt`, `streamed_text`, `serialized_sandbox` — the three branches
inside `build_flat_payload`, `engine.py:1313-1392`) AND (b) has a PROMPT that never instructs a
file write — regardless of whether the agent's `tools:` declaration is empty, since
`backend/agents/factory.py:1306-1352` (the R-22/D-07 "empty tool set" rule) binds native
filesystem tools for EVERY agent, `tools: []` included. `prototype_revision` is the counter-example
both ISS-723 and ISS-727 independently flag as LIKELY UNAFFECTED — not because of its `tools:
[workspace]` declaration alone, but because its `workflow.yaml` ALSO carries an explicit
step-level `tools: {read_files: true, write_files: true}` override AND its prompt actually
instructs `edit_file` use, genuinely rewriting `prototype.html` on disk every run (captured for
free by the per-step `git add -A`, `engine.py:6141-6148`).

`user_stories_revision` lands on the SAME side of that boundary as `ppt_revision`, checked
directly:

- `backend/agents/workflows/user_stories_revision/workflow.yaml:26` — `deliverable.strategy:
  streamed_text`, `name: user_stories.md`. `streamed_text` is handled by the SAME
  `build_flat_payload` branch shape as `ppt` (`engine.py:1328-1348`, immediately above the `ppt`
  branch ISS-723 cites) — materializes `ectx.last_streamed` only into
  `.chain/user_stories.md`, never `sandbox.root / "user_stories.md"`.
- `backend/agents/workflows/user_stories_revision/workflow.yaml:31-33` — the pipeline's only
  step is `user-story-revision-agent`.
- `backend/agents/prompts/user-story-revision-agent/AGENT.md:16` — `tools: []`. **Not** "no
  filesystem access" — `backend/agents/factory.py:1306-1352` binds native fs tools for every
  agent with an empty tool set (`exclude_builtin=False`), so `write_file`/`edit_file` ARE
  available to this agent at the runtime level (`backend/CLAUDE.md`'s Tool Sets table is stale on
  this exact point — verified directly against the current `factory.py`, not taken on the
  table's word).
- **CONFIRMED by reading the full prompt body** (`AGENT.md:21-80`): it tells the agent to
  `read_file` the seeded `user_stories.md` (`:25`), but its "OUTPUT CONTRACT" (`:34-36`,
  reinforced at `:79-80`) is unambiguous — *"Output ONLY the complete updated Markdown document.
  No preamble, no explanation."* There is no `write_file`/`edit_file` instruction anywhere in the
  prompt. This is the exact same shape as `ppt-revision-agent`'s `<artifact>`-wrapped stream
  contract: read the file for context, then answer in the chat stream, never touch disk. The tool
  is available; the prompt asks for a stream instead.

Both conditions now CONFIRMED to match `ppt_revision`'s corrected shape (tool available, prompt
never invokes it) exactly, not merely by analogy. The predicted symptom: `GET
/api/runs/{id}/sandbox/file?path=user_stories.md&ref=v2` on a completed `user_stories_revision`
run returns whatever `user_stories.md` held at the LAST commit that ever wrote that path (the
base `user_stories` run, if that pipeline's OWN deliverable strategy ever puts a real file at
sandbox root — itself unverified, see below) — not v2's revised backlog.

## What is NOT yet confirmed (why this is INFERRED, not CONFIRMED)

- No completed `user_stories_revision` run with a populated `git_tag` exists in this Postgres
  instance (`flowin_local_pdf`) at analysis time — queried and confirmed empty. There is no live
  sandbox to `git show` against, unlike [ISS-723](20260922-1245-ISS-723.md)'s directly-inspected
  Arctic Vault family.
- The BASE `user_stories` pipeline's own deliverable strategy is ALSO `streamed_text` (unverified
  whether any first-party agent in that pipeline holds a filesystem-write tool the way
  `ppt-composer` unexpectedly does for `ppt`/`ppt_revision` — ISS-723's Layer-2 exception that
  makes `presentation.html` exist at sandbox root at all despite the declared strategy). If NO
  agent in the `user_stories`/`user_stories_revision` family ever writes to sandbox root, the
  predicted symptom is not "frozen at v1" but "404 for every version, including v1" — the
  QA-PS-029 shape, not the QA-PS-031 shape. Which of the two this actually is depends on a fact
  not checked here (whether some `user_stories` agent has an ISS-651-style hardcoded write) and
  is exactly what live confirmation would settle.

## What would confirm this

1. Launch (or find) one completed `user_stories_revision` run with a healthy, populated
   `git_tag`.
2. `git log --oneline -- user_stories.md` in its sandbox: zero commits confirms the "always 404"
   shape (QA-PS-029-adjacent); exactly one, non-matching-the-latest-revision commit confirms this
   card's predicted "frozen at an earlier version" shape (QA-PS-031-adjacent), matching ISS-723
   exactly.
3. Either outcome is a real, previously-unconfirmed defect for this workflow — this card should
   be updated (not re-filed) once one is observed.

## Fix location

Same shape as [ISS-723](20260922-1245-ISS-723.md)'s primary recommendation: give
`user-story-revision-agent` a persistence instruction (`edit_file` the already-seeded
`user_stories.md` in place, matching how the prompt already tells it to `read_file` that same
path) instead of streaming the whole document back as chat text. No tool grant needs to change —
it already has one (see "Correction" trail above). The `streamed_text` branch in
`build_flat_payload` (`engine.py:1328-1348`, next to the `ppt` branch) is the ENGINE-side fallback
this card's mechanism goes through when nothing is written; it is not itself the fix location,
same caution as [ISS-723](20260922-1245-ISS-723.md)'s "Fix risk" section (the finalize commit
cannot re-stage a root file regardless).
