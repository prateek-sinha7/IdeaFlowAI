## What was wrong

Clicking "Save as my version" on `/create/ppt` fired a `POST /api/user-workflows`
whose body was byte-for-byte identical no matter what the user had typed or
picked — [ISS-226](20260828-1550-ISS-226.md) recorded three cold-start cycles
with three different briefs and three different templates producing the same
`name`, the same `description` and the same generic 3-step manifest, and the
same row `id`/`created_at` back (the endpoint UPSERTs on
`overrides_pipeline_type`). The save returned `201` and a "Workflow saved to
your catalogue" banner, so nothing on screen said the input had been dropped.

## Root cause

Two separately-implemented copies of `handleSaveAsOverride`, both building the
payload from literals and `pipelineAgents`/`selectionsRef` only:

- `frontend/src/components/workflow/LaunchWizard.tsx:735` — `description:
  "Your saved version of this workflow."`. The wizard shell is one component
  parameterised by `mode` (`MODE_CONFIG`, lines 96-137), so this one function
  serves `/create/ppt`, `/create/prototype` and `/create/ppt_v2` — the sibling
  [ISS-279](20260828-1901-ISS-279.md). Its own `handleLaunch` (line ~756) reads
  `brief`, `selectedTemplateId` and `selectedDsId` into `buildLaunchDraft` on
  the very same render, so the state is unambiguously live at save time.
- `frontend/src/components/workflow/IdeaInputPage.tsx:1467` — the identical
  literal, and `ideaInput` never read, on every non-custom workflow that shell
  serves ([ISS-280](20260828-1902-ISS-280.md)). Its own `handleSaveWorkflow`
  (line ~1396) already persists `brief: ideaInput.trim()`.

Blast radius re-checked before editing and it still holds: `grep -rn
"handleSaveAsOverride" frontend/src` returns exactly these two definitions and
their one `onClick` each (`LaunchWizard.tsx:1092`,
`IdeaInputPage.tsx:1663`) — no third copy, no shared helper, so the fix has to
land in the two functions (or in something they both call), never per-caller.

### The schema question ISS-226 left open, now settled

ISS-226's blast-radius section flagged as INFERRED that making the selected
template actually round-trip "likely needs a schema change" and told the fix
pass to settle it first. It does, and both halves of the lock were verified in
this pass:

1. `backend/app/api/user_workflows.py:66` (`_reject_both`) — `manifest` and
   `selections` are mutually exclusive on both POST and PATCH, because they
   write the same `workflows.manifest_json` column. An override save MUST send
   `manifest` (the override resolve reads `manifest_json["steps"]`), so the
   `_wizard` bag that carries `brief`/`templateId`/`designSystemId` for "Save
   workflow" **cannot** be sent alongside it.
2. `backend/agents/workflows/manifest.py:266` — `build_manifest_from_dict`
   rejects any top-level key outside `_ALLOWED_TOP_KEYS` (D-08 / INV-5), and
   `_validated_manifest` runs that parser at save time, so a `_wizard` (or
   `brief`, or `template`) key **inside** the manifest 422s the save.

That leaves `description` (`str | None`, `max_length=2000`) as the only
free-text field on the request that can carry what was on screen without a
schema addition — which is exactly the split ISS-280 called "the
immediately-actionable part".

## What changed and why there

**`frontend/src/store/api/userWorkflows.ts`** — one new exported helper,
`overrideDescription({ brief, templateId, designSystemId })`, next to
`buildWorkflowManifest` which both callers already import from this module. It
joins the non-empty parts and falls back to the old literal when there is
nothing on screen to describe, and `.slice(0, 2000)` caps it at the column's
`max_length` so a long brief cannot turn a silent data loss into a loud 422.

One helper rather than two inline blocks because the literal already existed in
exactly two places (`grep -n "Your saved version of this workflow\."` returned
those two lines and nothing else) and the two payloads are otherwise
near-identical — the shape [ISS-279](20260828-1901-ISS-279.md) proposed.

**`frontend/src/components/workflow/LaunchWizard.tsx`** — `handleSaveAsOverride`
calls it with the same three pieces of state `handleLaunch` reads, resolving
the design system exactly the way the sibling `handleSaveWorkflow` does
(`isDeck ? (dsRequired ? selectedDsId : null) : selectedDsId`) rather than
inventing a second rule. `useCallback` deps extended to match what the body now
reads — without that the closure would keep saving the first render's brief,
which is the same class of bug one layer down.

**`frontend/src/components/workflow/IdeaInputPage.tsx`** — same call with
`{ brief: ideaInput }`; that shell has no template or design-system picker.
Deps extended with `ideaInput` for the same reason.

`name` was deliberately NOT changed. The row is an UPSERT keyed on
`(user_id, overrides_pipeline_type)` — one row per user per built-in — so its
name is the identity label for "my version of the presentation workflow", not a
description of one save's content. Making it vary per click would rename the
same row on every save. ISS-226 listed it beside `description` as hardcoded;
it is hardcoded on purpose, and this is the reason, recorded rather than
silently skipped.

No backend file was touched: the payload was always accepted, it just never
carried anything.

## Observed, NOT fixed, NOT mine

- A saved override still cannot RESTORE the brief/template/design-system when
  the user reopens `/create/<type>`: the description is free text nothing
  parses back. Closing that needs a manifest schema addition, which is a
  design decision, not a fix — filed as
  [ISS-377](20260828-2202-ISS-377.md).
- `IdeaInputPage.tsx:1465` names the row `My ${workflowId}` — the raw pipeline
  id, so a user sees "My user_stories" rather than a display name. Pre-existing,
  cosmetic, untouched.
- [ISS-225](20260828-1541-ISS-225.md)'s separate gates facet of
  `IdeaInputPage.handleSaveAsOverride` (a 422 when the manifest declares
  `route:` without `gates:`) is a different mechanism in the same function and
  is NOT addressed here.
