## What was wrong

`/settings/constitution` renders a counter styled as a hard cap —
`{content.length} / 4000 chars` — under copy that says the constitution is
"prepended to every agent on every run". Nothing enforced the 4000. The
validator reproduced 3/3 from a cold start: 4318-5018 char payloads all saved
`200 OK` and survived a cold reload at full length. Register entry
`BUG-20260828-031900-settings-constitution`; full evidence in
[ISS-293](20260828-1924-ISS-293.md).

## Root cause

The `4000` was a UI-only literal with no backing anywhere in the save path:

- `frontend/src/components/settings/AccountSettings.tsx:582` — the counter, a
  hard-coded `4000` in JSX text and the only occurrence of the number in
  `frontend/src` (`grep -rn 4000 frontend/src`).
- `AccountSettings.tsx:586-593` — the `<textarea>` carried no `maxLength`
  (`textarea.maxLength === -1` in the DOM), so typing and pasting past 4000
  were both unconstrained.
- `AccountSettings.tsx:630` — `disabled={saving || loading || !content.trim()}`
  never looked at length, so Save stayed enabled at any size.

The only real enforcement is the backend's
`ConstitutionRequest.content = Field(..., min_length=1, max_length=1_048_576)`
(`backend/app/api/settings.py:355`), independently mirrored by
`WorkflowMemory._set`'s `_MAX_VALUE_LEN = 1_048_576`
(`backend/agents/workflow_memory/memory.py:26,208-210`). Both agree with
FR-012 (`specs/001-ai-workflow-os/spec.md:224-227`), which specifies 1,048,576
— so the backend is spec-compliant and the frontend display was the lie.

## What changed and why there

**`frontend/src/components/settings/AccountSettings.tsx`** — one module-level
`const CONSTITUTION_MAX_CHARS = 4000;` declared beside `ConstitutionSection`,
then read in the three places the analysis named:

- the counter (`{content.length} / {CONSTITUTION_MAX_CHARS} chars`) — the
  displayed number can no longer drift from what is enforced;
- `maxLength={CONSTITUTION_MAX_CHARS}` on the `<textarea>` — Blink's
  `HandleBeforeTextInsertedEvent` clamps typing and paste alike, so React's
  `content` state can never exceed the ceiling from user input;
- `disabled={saving || loading || !content.trim() || content.length > CONSTITUTION_MAX_CHARS}`
  on Save — covers the one path `maxLength` cannot, an account whose stored
  constitution is ALREADY over-limit from before this fix: that content loads
  into the textarea programmatically (`maxLength` does not truncate an
  assigned value), and Save now refuses to re-persist it until the user edits
  it down or clears it.

`ConstitutionSection` is the whole live blast radius: it is the only reachable
UI for this endpoint (`grep -rn "settings/constitution" frontend/src`), and
`handleSave` is its single save path, so the disable check sits where every
caller routes through.

### Deliberately NOT changed

- **The backend cap stays 1,048,576.** ISS-293's "Expected" offered a
  server-side 4000-char 422 as one option; the analysis on the register entry
  rules it out — 1,048,576 is what FR-012 specifies and what both backend
  layers already agree on. 4000 is a UI product ceiling, and every value the
  client can now send is well inside the server's limit.
- **The counter still reads 4000, not 1048576.** Raising the displayed number
  to the backend cap would make the on-screen figure honest but useless, and
  would break the passing S-09-11 scenario, which asserts the counter against
  `framework/locators/settings_page.py:67` `CONSTITUTION_CEILING = 4000`.
- **`settingsApi.getConstitution/updateConstitution/deleteConstitution`
  (`frontend/src/store/api/settings.ts:61-75`) is untouched** — the same
  unguarded PUT, but with zero consumers anywhere in `frontend/src`. Dead code
  today; ISS-293 explicitly does not file it as a live sibling.
- **`_inject_constitution` (`backend/agents/factory.py:673-699`) is
  untouched** — the downstream half, where saved content is spliced verbatim
  into every governed agent's system prompt with no size guard. That is
  sibling [ISS-402](20260828-2121-ISS-402.md), owned by a different card.

### A reload-step flake the 6-verifier will meet

The ISS-293 test was run four times: XPASS, XPASS, and twice a 30s timeout on
`page.wait_for_function(... value.length > 50)` inside the "And I reload the
page" block. Both timeouts landed immediately after a write to
`AccountSettings.tsx` — the first after this change, the second after a
concurrent fixer's `UpgradePlanModal` binding in the same file — so the reload
hit the Next.js dev server mid-recompile: the SSR'd textarea is visible (the
preceding `expect` passes) while hydration, and therefore the mount-effect
fetch that fills it, has not run. On a quiescent tree the same step completes
in 0.6s and the test XPASSes. It is a dev-server timing artifact of two agents
sharing one file, not the fix — re-run once the tree settles.
