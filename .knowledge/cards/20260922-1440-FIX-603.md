# FIX-603

Four defects, four distinct mechanisms, one file. Grouped into one card because
they share a single symptom class — *a surface that ignores the version pin* —
and one test run. `frontend/src/components/preview/PreviewPanel.tsx` is the only
production file changed. No backend file was touched.

## 1. QA-PS-057 / ISS-753 + ISS-754 — Steps "Starting point" never followed the dropdown

**Wrong:** `VersionView` (`PreviewPanel.tsx:536-549` pre-change) carried
`agents` / `pipelineState` / `agentOutputs` / `content` / `genericDeliverable`
but had no `runInput`, even though the `WorkflowRun` `versionViewFrom()` is built
from has `.input`. Both version-resolution paths route through that one function,
so neither could produce a version-aware brief. `effAgents` / `effPipelineState` /
`effAgentOutputs` tracked the selection correctly while `runInput={runInput}` at
the Steps and Files consumers was the raw prop, tracing to
`DashboardLayout.tsx:3313` → `submittedBrief` (`page.tsx:2243`), which only
`handleSelectWorkflowRun` and `handleSwitchToLiveRun` ever set. Reproduced 20/20
in the version-matrix audit.

**Changed:** `runInput?: string` added to `VersionView` (`:552`); populated in
`versionViewFrom` (`:600`) as `brief || run.title`; `effRunInput` added beside the
other `eff*` values (`:1004`); both consumers now read it (`:1805` FilesTab,
`:1843` AgentThinkingTab). This is exactly what
[ISS-753](20260922-1413-ISS-753.md) asked for — it names the missing `effRunInput`
and cites FIX-516's locked_constraint ("every pipeline prop a pinned-version-aware
surface consumes must be the `eff*` value") as the thing being violated — and the
single `effRunInput` also closes [ISS-754](20260922-1414-ISS-754.md), the FilesTab
`runInputFileRows` sibling, because both consumers chokepoint through it.

**Shape chosen: PARSED, not raw** — the risk the bug report flagged.
`StartingPointCard.tsx:33` documents its `input` prop as raw, but the live value
that has always flowed into it is `submittedBrief`, which `page.tsx:2728-2730` /
`:2941-2942` already reduce to `(parsed.revisionInstruction ?? parsed.brief ??
"").split("\n")[0].trim()`. `versionViewFrom` reproduces that line verbatim
(`:598-599`) so the two cannot drift. Feeding raw here would have made a pinned
revision render "Revision request" + the full marker-laden instruction while the
live view of that same run renders "Starting point" + one line, and would have
changed FilesTab's `prompt.md` row shape between pinned and live — the FIX-130
class of divergence.

## 2. QA-PS-054 / ISS-706 — header Download ignored the pinned ref

**Wrong:** `handleHeaderDownload` called `getRunSandboxFileBlob`/`getRunSandboxZip`
with no `ref`, while the sibling preview effect ~20 lines above already threads
`sandboxSelectedRef`. `run_files.py`'s handler gates its whole `git show <ref>:<path>`
branch on `ref is not None`, so a ref-less request falls through to a live
working-tree read and serves the newest bytes under the "Viewing v{n} (read-only)"
banner. The backend is correct and was not changed.

**Changed:** both calls take `sandboxSelectedRef ?? undefined` (`:1401-1402`), and
`sandboxSelectedRef` was added to the `useCallback` deps (`:1414`) — the second
half is not optional, because `deliverableFile` is usually the same string across
versions, so without it the callback is not rebuilt when only the ref changes and
the closure serves a stale ref.

## 3. QA-PS-056 — Workspace tab served latest content under a v1 banner

**The card's stated cause is WRONG and was not applied.** BUGS.md QA-PS-056 and
the dispatch brief both say "the Workspace file viewer never passes the selected
ref". It does. `SandboxTab.tsx` threads `selectedRef ?? undefined` through every
one of its reads — `:1046` listing, `:1085-1086` open-file text/blob, `:1106`
file download, `:1119` zip — and
`PreviewPanel.sandboxRef.test.tsx:161` ("the Workspace tab's file list and file
read carry ref=v1 while v1 is selected") passes against unmodified code. Adding a
ref there would have been a no-op.

**The real mechanism, traced:** `sandboxSelectedRef` is null while `viewingVersion`
is set, because the `ReadOnlyVersionBanner` keys on `isViewingOlder`
(`viewingVersion`) and not on the sandbox ref. The version MENU path stages
`intendedSandboxRef` (FIX-516) and is fine; the `/versions/{n}` URL-pin effect set
`viewingVersion` alone, so the `activeRunId`-change reset found nothing staged, took
its `else` branch, and nulled `sandboxSelectedRef`. That path is reached by a
`/versions/{n}` deep link, a reload while pinned, and any remount after the menu
wrote that segment (`handleSelectVersion` → `onTabSelect` → `DashboardLayout:502-539`
→ `pushState`).

**Changed:** `pinnedMember` is now destructured for both its id and its `git_tag`
(`:930-932`); when the tag exists the effect stages `intendedSandboxRef` and sets
`sandboxSelectedRef` before the fetch (`:946-950`), mirroring
`handleVersionMenuSelect` exactly; deps widened to `[pinnedMemberId, pinnedMemberTag]`
(`:962`).

## 4. QA-PS-055 / ISS-744 — a completing revision silently cleared the pin

**Wrong:** `useEffect(() => { setViewingVersion(null); }, [liveRunId])`. That prop
moves on navigation (what the effect was written for) but also on every tracked
`*_revision` completion, because `page.tsx:1521`'s `isRevisionCompletion` bypasses
the foreign-run guard and fires `setContentSourceRunId(completingRunId)`. Clearing
`viewingVersion` recomputed `activeRunId`, which fired the `:792-803` reset and
nulled `sandboxSelectedRef` too — both halves of the pin collapsed in one render.

**Changed:** re-keyed to `pinnedVersion` — `useEffect(() => { if (!pinnedVersion)
setViewingVersion(null); }, [pinnedVersion])` (`:920`). The `/versions/{n}` URL
segment is the pin's real source of truth ([ISS-296](20260828-1724-ISS-296.md) made `handleSelectVersion` write
it on every selection; dropping the pin drops it; navigating to another run drops
it), so the effect still supersedes in every case the old comment meant and in none
of the ones it did not.

**FIX-088 is preserved, not reverted.** `page.tsx` was not touched: it still
advances `contentSourceRunId` on every revision completion, so the chip and family
still tick v2 → v3 and the "stuck at v1" symptom FIX-088 fixed does not return.
With nothing pinned the new effect is a no-op — proved by the GREEN control test
that asserts the un-pinned advance still follows to latest.

## Deliberately NOT fixed

- **[ISS-745](20260922-1400-ISS-745.md) stays open.** Its test is still red, and
  correctly so. With the pin now surviving, the foreign-family case fails on the
  banner LABEL, not on pin loss: `AssertionError: expected 'Viewing v0
  (read-only)...' to match /Viewing v1/`. `versionNumber={activeIdx + 1}` and
  `activeIdx = sortedMembers.findIndex(m => m.id === activeRunId)` returns -1
  once `runFamily` has been swapped to a family the pinned member is not in. That
  is ISS-745's own stated position — "no downstream pin-guard can repair [this]
  once runFamily itself has been refetched for the wrong family" — so the fix is a
  lineage check on `page.tsx:1509`'s `isRevisionCompletion`, which needs the
  completing run's ancestry on the SSE payload. That is a data/design decision the
  card does not settle, and it was not attempted here.
- **[ISS-665](20260917-1311-ISS-665.md) stays open.** `FilesTab.tsx:737`'s row
  download has the same ref omission as defect 2 above, but that card's scope is
  broader ("ref-blind resolution", not one argument), it owns a different file, and
  no test covers it here.
- **[ISS-755](20260922-1415-ISS-755.md) stays open.** It is the prop immediately
  beside the two `runInput` consumers this card changed —
  `clarifications={clarifications ?? pipelineState?.clarifications}` reads the raw
  `pipelineState`, not `effPipelineState` — and it is the same "raw prop where an
  `eff*` belongs" class. Left alone deliberately: it has its own card and its own
  semantics (a live clarify round shadowing the pinned member's), and no test here
  covers it. The change it wants looks like one word (`pipelineState` →
  `effPipelineState`) on `PreviewPanel.tsx:1806` and `:1844`.
- **[ISS-758](20260922-1421-ISS-758.md) stays open.** `handleSelectVersion`'s async
  `getWorkflow` sets `viewingVersion` with no `cancelled` guard, unlike the
  `pinnedMemberId` effect beside it — the transient one-behind agent list the QA
  sweep caught on a v6→v2 jump, and the "Second, separate finding" on QA-PS-057's
  own `BUGS.md` entry. A different mechanism (a race, not a missing field), and it
  self-heals; not attempted here.
