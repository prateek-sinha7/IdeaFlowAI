# ISS-679

## Title

[ISS-673](20260917-1420-ISS-673.md)'s "Analysis missed" section (added by the 5-fixer after
[FIX-521](20260917-1447-FIX-521.md) still showed "0 of 6 agents" live) proposed, but did not
decide between, three fix shapes. This card is the re-analysis it asked for: every line of the
proposed mechanism read and confirmed directly, plus the exact reason `useRunStateStore.ts`
(ISS-673's own fix location) cannot be patched in isolation, plus a recommended fix location.

## Confirmed mechanism (every line read fresh, 2026-09-17)

1. **The store lives inside the component that gets destroyed.** `runStore = useRunStateStore()`
   is called directly in the page component's body (`page.tsx:2170`). `useRunStateStore`'s only
   backing store is `const storeRef = useRef<Map<string, PerRunState>>(new Map())`
   (`useRunStateStore.ts:274`) — a plain `useRef`, scoped to one hook call, i.e. one mount of
   `page.tsx`.
2. **That component really does remount on client-side navigation, not just re-render.** This is
   not an inference — it is an existing, dated code comment from an earlier, unrelated regression
   fix, read directly at `page.tsx:3269-3273`: *"T9's router.push remounts THIS page component
   (Next.js does not preserve a dynamic-route page's own instance across a client-side navigation
   to a new URL under the same catch-all — confirmed live: a fresh render-instance id appears right
   after router.push...)."* `DashboardLayout.tsx:515-520` independently states the same fact from
   the other side ("router.push ... REMOUNTS page.tsx ... wiping every page-local run state").
   A full reload has the identical effect for a different reason (below).
3. **The roster is seeded exactly once, by `pipeline_start`, and by nothing else.**
   `useWorkflow.ts:404-410` builds `agentStates`/`prev.agents` only inside `case "pipeline_start"`.
   `INITIAL_PIPELINE_STATE.agents = []` (`useRunStateStore.ts:148-156`) is what every fresh
   `getOrCreate` entry starts from (`useRunStateStore.ts:322-327`). A `pipeline_start` that fired
   before the remount reached the OLD, now-discarded store instance; the NEW instance's entry for
   that run is `agents: []` until something re-seeds it.
4. **Frames for the backgrounded run keep arriving after the remount, and reach the new, empty
   store — they just can't do anything with it.** `launchedRunIdsRef` is a `useRef` re-seeded from
   `sessionStorage` on every mount (`page.tsx:638-651`), so it survives the remount. Every
   non-foreign frame with a `frameRunId` is routed to `runStore.handleFrame` unconditionally,
   before any viewed/active check (`page.tsx:1410-1412`). But `useWorkflow.ts`'s per-event
   reducers all gate on the agent already being in the roster —
   `agent_start`: `const agentIdx = prev.agents.findIndex(...); if (agentIdx === -1) return prev;`
   (`useWorkflow.ts:586-587`); `agent_complete`: identical guard (`useWorkflow.ts:705-706`). With
   `prev.agents === []`, every single one of these is a silent no-op. `completedCount` is only
   ever recomputed at `useWorkflow.ts:724`, a line the `agent_complete` case never reaches for this
   run. This is a **missing computation**, not a stale render — confirming, not merely repeating,
   what ISS-673's "Analysis missed" section already concluded.
5. **[FIX-521](20260917-1447-FIX-521.md)'s tick cannot fire on a value that never changes.** The
   tick is `else if (entry.pipelineState.completedCount !== completedBefore) setBackgroundProgressTick(t => t + 1)`
   (`useRunStateStore.ts:488-489`), read inside `handleFrame` immediately after the reducer runs.
   Since the reducer returns `prev` unchanged (point 4), `completedBefore === completedCount`
   always, so the tick never bumps. FIX-521 is not wrong — it correctly re-renders page.tsx
   whenever a background run's count genuinely moves *within one store instance's lifetime* (its
   own test, `useRunStateStore.iss673.test.tsx`, sends `pipeline_start` then `agent_complete` to
   the *same* instance and passes). It just cannot recompute a count the reducer already dropped
   on the floor.
6. **A cold reload triggers the identical defect for an independent reason.** SSE resume is
   sequence-based, not from-scratch: `RunConnectionProvider.tsx:210-216` passes
   `afterSeq: readCursor(runId)` into `useRunStream`, and `readCursor`/`writeCursor` persist a
   `run_cursor:<id>` sequence number in `sessionStorage` (`RunConnectionProvider.tsx:152-164`). A
   reconnect after `pipeline_start` (sequence 0) has already been seen resumes strictly after it,
   so `pipeline_start` is not redelivered over SSE on a reload either. Client nav and reload are
   two different triggers for the exact same effect: the roster is gone and nothing re-seeds it
   for a run that is not the one named in the URL.
7. **A rehydration path already exists in this codebase for exactly this failure — but it is
   scoped to the run named in the URL only.** `page.tsx`'s `reopenedRunIdFor(parsedView)` effect
   fetches `getRunEvents(token, runId)` and replays every durable frame through
   `handleWebSocketMessage` (`page.tsx:3418-3427`), rebuilding the roster from scratch — its own
   comment (`page.tsx:3398-3417`) documents this was built for the *viewed* run hitting the same
   "empty roster after remount" symptom (T11, a prior regression). `handleSwitchToLiveRun`
   (the notification-panel / header-dropdown "switch to this run" handler, `page.tsx:2607-2696`)
   does the same replay before switching viewport. Neither path runs for a run that stays
   backgrounded — there is no third path that rehydrates a run nobody has clicked into.

## Why the fix cannot be "patch `useRunStateStore.ts` again"

[ISS-673](20260917-1420-ISS-673.md)'s "Fix — where it belongs" is correct that `useRunStateStore.ts`
is the one producer all three render surfaces (panel, header badge, "N Running" dropdown) share for
the *re-render* half of this bug, and [FIX-521](20260917-1447-FIX-521.md) is a real, working fix for
that half — it is not being reverted or called wrong. But its premise, *"the data in the store's ref
is already correct — this is a missing re-render subscription, not a missing computation"*
(ISS-673's own words), is false once a remount has happened: the ref genuinely holds `agents: []`,
and no signal `useRunStateStore.ts` could raise about "this changed" would matter, because nothing
inside that file ever gets the roster back. The fix cannot live purely inside the reducer/store —
it needs an actor that knows about REST replay (`getRunEvents`) and about which runs are
backgrounded, and today that logic lives in `page.tsx`, not in the hook.

## Fix — where it belongs (recommendation, not decided here)

Two shapes were already named as options in ISS-673's "For re-analysis" list; having now traced
every line, here is which is smaller and why.

- **Recommended: lift `useRunStateStore()` above the router**, next to `RunConnectionProvider`
  (`frontend/src/providers/`), which already sits above `app/[...view]/page.tsx` in
  `app/layout.tsx` specifically *because* it must survive this exact remount (its own doc comment,
  cited at `page.tsx:3281`, says so). If the store's `storeRef`/`viewedState` live in a provider
  instead of inside the page component, `router.push` never destroys them, `pipeline_start` is
  never lost for a backgrounded run, and the whole class of "per-run state vanishes on navigation"
  closes in one place — not just `completedCount`, and not just for whatever the next symptom
  report happens to be. `page.tsx`'s own `reopenedRunIdFor`/T11 replay-on-mount code (point 7
  above) becomes redundant for any run already known to the provider, though a genuinely cold
  reload still needs a one-time replay (the provider is itself remounted then, at the app root).
  This is not a data-shape change, and it is confined to the frontend, so it does not touch
  SC-001/INV-1 or any import-linter contract.
- **Smaller-footprint alternative: extend the existing per-run replay to every backgrounded run,
  not only the URL's own.** On mount (or on the same effect that already does this for the URL's
  run), iterate `launchedRunIdsRef.current`/`recentRuns` for entries that are still live and whose
  `runStore.get(id)` has an empty roster, and call the same `getRunEvents` + replay
  `handleWebSocketMessage` loop `handleSwitchToLiveRun` already uses. Cheaper to review, but it
  pays an event-log fetch per backgrounded run on every remount (not just once), and it has to be
  built carefully against the dedupe/race issues `handleSwitchToLiveRun`'s own comments already
  flag for the single-run case (ISS-082's note on a previously-deleted undeduped second replay
  pass) — now multiplied across N runs instead of one.

Either way, this is an implementation/placement choice for engineering, not a product or API
decision — nothing here changes a contract or user-facing behavior beyond "the number is now
right," so it does not need [ESCALATIONS.md#qa-ps-002](../../ESCALATIONS.md#qa-ps-002) reopened.

## Blast radius (re-checked, not just the reported path)

`grep -rn "runStore\.get(\|runStore\.has(" frontend/src/` (excluding tests) returns exactly two
production call sites: `page.tsx:1266` (an unrelated same-mount clarify-gate check with no remount
involved) and `page.tsx:3914` (the `runAgentsCompletedMap` construction ISS-673/674 already cover).
No other consumer of a backgrounded run's `pipelineState` exists, so the three render surfaces
[ISS-673](20260917-1420-ISS-673.md)/[ISS-674](20260917-1420-ISS-674.md) already named — notification
panel live rows, the header single-pipeline badge, the "N Running" dropdown — remain the complete
list. Two plausible extra siblings were checked directly and ruled out, not assumed:

- **A background run finishing (not just progressing) after losing its roster still leaves the
  live list correctly.** `pipeline_complete`'s reducer (`useWorkflow.ts:801-825`) does not gate on
  the roster — it maps `prev.agents` (empty is fine) and unconditionally sets the terminal
  markers. Separately, `page.tsx:1582-1619` unconditionally refetches `getWorkflows()`/
  `setRecentRuns` inside the same `pipeline_complete` handler, which is what actually drives a run
  out of `AppHeader`'s `LIVE_STATUSES` filter. So a background run that completes while its roster
  is empty disappears from the live section the same way [ISS-648](20260917-1100-ISS-648.md)
  already documented for fail/cancel — not a new symptom shape.
- **The URL's own run (the "inverse" of a backgrounded one) is not at risk.** It already gets its
  own mount-time replay (point 7 above), which is exactly what T11 was fixing before this bug
  existed. Nothing here regresses that path; it's cited as evidence the pattern works, not as
  something newly broken.

No further sibling is filed from this card: [ISS-675](20260917-1447-ISS-675.md) (another tab's run,
never streamed here at all) and [ISS-676](20260917-1447-ISS-676.md) (a background fail/cancel wrongly
resetting the *viewed* run's state) are different triggers/mechanisms already carrying their own
cards, not duplicates of this one.

## What would confirm this live

1. Launch 2-3 concurrent runs from one tab (matches the original QA repro).
2. Navigate to `/dashboard` (a `router.push`, not a tab click) before any of them finishes an
   agent, or reload the page instead.
3. Open the bell panel / header badge — expect "0 of N" exactly as QA reported, unchanged by
   FIX-521.
4. Click one run's row (`onViewResults` → `handleSwitchToLiveRun`, which DOES replay) and confirm
   only that run's number corrects itself; the others, still un-clicked, stay at 0.

The 5-fixer's own scratch vitest check (recorded in ISS-673's "Analysis missed" evidence: store A
seeded with `pipeline_start` then unmounted, a fresh store B fed `agent_start`/`agent_complete` for
the same agents, ending at `completedCount=0`) already reproduces the mechanism outside the
browser and is the shape any regression test for this card should follow — it is the one thing
`useRunStateStore.iss673.test.tsx` does not do (it never unmounts/remounts the hook between
`pipeline_start` and the completion frames).

## Resolution (2026-09-17, [FIX-523](20260917-1555-FIX-523.md))

The recommended shape was taken. The store moved above the router as module-scope maps, not a
provider: the lifetime is the same, and ISS-658's test renders the hook without one. The change is
confined to `useRunStateStore.ts`, and page.tsx is untouched.

Moving the store out of the page broke three things page.tsx relied on, so FIX-523 adds a guard
for each:

- Only running entries survive an unmount. A finished run replayed into its old entry reads
  revision count 0; the reducer defect is [ISS-681](20260917-1555-ISS-681.md).
- A dead page's late replay writes to a throwaway entry.
- The maps are cleared when the JWT `sub` changes.

Point 6, the cold reload, is **not** fixed and is split out to [ISS-680](20260917-1555-ISS-680.md).
Rehydrating through `handleFrame` would make the first replayed run the viewed one on `/dashboard`,
and DashboardLayout would then navigate to it.

Locked constraint 1 holds: FIX-521's tick is untouched. Locked constraint 2 holds: the URL run's
T7/T11 replay is unchanged, and replaying into a surviving running entry was observed to be
idempotent.
