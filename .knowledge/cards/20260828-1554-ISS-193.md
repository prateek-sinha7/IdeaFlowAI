## What happened (INFERRED — not yet reproduced)

Filed from the root-cause investigation of
[ISS-191](20260828-1330-ISS-191.md), not from an independent repro. Read directly:

`frontend/src/app/register/page.tsx:1-14` (full file):

```tsx
export default function RegisterPage() {
  const router = useRouter();
  useEffect(() => { router.replace("/login"); }, [router]);
  ...
}
```

This `useEffect` redirects to `/login` **unconditionally** — there is no `getToken()` (or
any other auth-state) check before the redirect fires. Every other
`router.replace`-to-login call site in this codebase gates on `!token` first
(`admin/page.tsx:165`, `handoff/settings/page.tsx:23-26`,
`components/handoff/HandoffWorkflow.tsx:63-68`,
`components/workflow/LaunchWizard.tsx:261`, `[...view]/page.tsx:807-809`, all read via
ISS-191's investigation) — `register/page.tsx` is the one exception.

Since `/login` itself has no guard for an already-authenticated visitor (ISS-191's
CONFIRMED root cause — `frontend/src/app/login/page.tsx` never imports `useEffect` and
has no mount-time check at all), the two gaps compose: an authenticated user who lands on
the literal `/register` route is sent to `/login` and then hits the identical missing
guard, staying on the sign-in form instead of reaching `/dashboard`.

## Expected vs actual

- **Expected:** an authenticated user (valid `auth_token`) who navigates to `/register`
  ends up on `/dashboard` — either directly, or via a `/login` hop that itself redirects
  onward once ISS-191 is fixed.
- **Actual (inferred):** the user is redirected to `/login`, which today renders the full
  sign-in form for them (ISS-191), so they appear stuck rather than reaching
  `/dashboard`.

## Why the root cause implies this

`register/page.tsx`'s redirect is a "caller" of `/login` in the same sense ISS-191's Blast
radius section uses the word — a code path that lands a browser on the broken page. It is
the one caller found that does **not** already gate on token absence, so it is the one
caller that can reproduce ISS-191's symptom through a second URL. This card exists so a
fix scoped only to `/login` (the correct, minimal fix per ISS-191) is verified against
this path too, and so nobody re-discovers this exact combination as a "new" bug later.

**Fixing ISS-191 alone is expected to resolve this card with no change to
`register/page.tsx`** — once `/login` redirects a signed-in visitor onward itself, the
extra `/register` → `/login` hop becomes a harmless intermediate step instead of a dead
end. The 6-verifier should still exercise this path explicitly, since it was never
independently reproduced here.

## Distinct from

`BUG-20260827-231407-register` (`bug-hunter/ledger.md`, not yet an ISS card as of this
writing) is a different defect: unmatched `/register/<sub-path>` URLs (e.g.
`/register/anything`) have no static file to match, so Next.js falls through to the
`[...view]` catch-all, which silently renders Dashboard content under the wrong URL for an
authenticated user. That is a route-resolution defect in the catch-all. This card is about
the literal `/register` route — served by `frontend/src/app/register/page.tsx`, which
Next.js resolves ahead of the catch-all for its own exact path — whose unconditional
redirect exposes ISS-191's missing guard rather than any catch-all fallback behavior. The
two never share a code path: `/register` never reaches `[...view]`.

## Settling this

Not yet reproduced. Would be settled by: sign in as qa-admin, confirm
`localStorage.getItem('auth_token')` is set and valid (e.g. `/dashboard` loads), then
navigate directly to `http://localhost:3000/register` (no sub-path) and observe whether
the sign-in form renders instead of an immediate bounce to `/dashboard`.

**SETTLED 2026-08-28 by [FIX-323](20260828-1629-FIX-323.md).** That exact procedure was
