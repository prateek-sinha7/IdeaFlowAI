# FIX-613

## What was wrong

Bug register `QA-SG-001`. Cold-navigating to `/runs/<id>` while a freshly
launched 5-agent run was still in `planning` / early `generating` showed
**"Pipeline running · 0 / 0"** in the run detail header, while the bell-icon
notification panel — the same run, the same wall-clock moment — showed
**"0 of 5 agents"**. Validator reproduced 3/3 from cold start
([ISS-722](20260922-1100-ISS-722.md)).

## Root cause

Two independent sources feed "total agents", and only one of them is
populated that early:

- `frontend/src/components/results/StepsOverviewSpine.tsx:403` —
  `const total = agents.length;` (label built at `:461`). `agents` is the
  client-built roster, seeded `[]` in `useRunStateStore.ts` and filled only
  as roster/`agent_start` frames arrive, so it is `0` for the whole window
  between run creation and the first frame.
- `frontend/src/components/layout/AppHeader.tsx:216` —
  `agentsTotal: isActive ? (pipelineAgentsTotal || r.agentCount) : (r.agentCount ?? 0)`
  — the notification/dropdown path falls back to the run record's static
  `agent_count`, already `5` at creation, which is why that surface is right.

[ISS-769](20260922-1443-ISS-769.md) found the same unguarded read on a third
surface: `AppHeader.tsx:464`'s legacy single-run badge renders the raw
`pipelineAgentsTotal` prop, which `DashboardLayout.tsx:2720` computed as
`pipelineState?.agents?.length ?? 0` — no `agentCount` fallback anywhere on
that path. Because that badge gates on `pipelineAgentsTotal > 0` it does not
print "0/0"; it silently omits the count instead. Same mechanism, milder
symptom.

## What changed, and why there

The fallback the notification path already had is now expressed ONCE, as a
field on the per-run pipeline state, and read by both unguarded surfaces:

1. `frontend/src/types/index.ts` — `PipelineRunState.agentCount?: number`,
   additive and optional: the run record's own `agent_count`, the only honest
   total available before the roster exists.
2. `frontend/src/app/[...view]/page.tsx` — the producer, seeded into the run
   store in BOTH paths that open a run and then replay its durable log:
   `handleSelectWorkflowRun` (deep-link `/runs/<id>` + history reopen) from
   `fullRun.agentCount`, and `handleSwitchToLiveRun` (notification/badge
   switch) from the `recentRuns` record. The store has no data source of its
   own — it is event-driven — so the seed belongs at the call sites that
   already hold the fetched run. Both reducers return `prev` unchanged when
   the value already matches, so no extra projection/re-render.
3. `frontend/src/components/results/StepsOverviewSpine.tsx:403` —
   `const total = agents.length || (pipelineState?.agentCount ?? 0);`
4. `frontend/src/components/layout/DashboardLayout.tsx:2720` —
   `pipelineAgentsTotal={pipelineState?.agents?.length || pipelineState?.agentCount || 0}`

`agents.length` still wins the moment the roster exists, so once the first
roster frame lands the live count is authoritative again and the seed is
harmlessly dropped by the FIX-201 legacy→store bridge (`page.tsx:2344`),
which by then carries a non-empty roster.

`DashboardLayout.tsx:1070`'s `const agentCount = pipelineState?.agents?.length ?? 0`
was deliberately left alone: it is guarded by `if (agentCount > 0)` and only
ever raises a notification's total, so it never writes the wrong number.
