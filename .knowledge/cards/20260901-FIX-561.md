## Related

## What was wrong

The extract_text materialiser is CPU/subprocess-heavy and synchronous. Running it on
the event loop starved every API route (observed live: four concurrent extract_text
calls froze the entire server for 10+ minutes). Even with proper threading, pdfium
is not thread-safe, and five parallel readers would crash the server with SIGBUS
inside FPDF_RenderPageBitmap.

## The fix (commit 127b20a3d)

- Rename the original implementations to `_extract_text_sync` and `_file_page_image_sync`.
- Create async wrappers `extract_text` and `file_page_image` that delegate via
  `asyncio.to_thread(_locked_call, sync_fn, ...)`.
- Introduce `_PDFIUM_LOCK` (threading.Lock) to serialize all pdfium/pdfplumber calls.
- `_locked_call(fn, *args)` acquires the lock, calls fn(*args), and releases it.
- This keeps the event loop breathing (asyncio.to_thread) while protecting pdfium
  from concurrent FPDF_* calls.
- The >30-page branch (separate processes) is unaffected; each process has its own
  pdfium instance.
