# ISS-1005

INFERRED sibling of [ISS-684](20260918-ISS-684.md) (bug report QA-KB-065), filed by the analyzer on 2026-10-02. The gap is CONFIRMED by lines I read and by an in-process probe with a throwaway kind. It is INFERRED that it is a defect rather than intent: [ADR-0045](20260918-ADR-0045.md) says a code step registers "for palette visibility only", and no privileged code step exists yet.

## Why the root cause implies it

ISS-684's root cause is that "which code steps exist" is declared in several places that nothing ties together (registry, compiler frozenset, engine chain). The registry holds one more per-kind fact, `user_allowed`, and the compiler never reads it for a code step, because it validates `mechanical` against its own frozenset instead of asking the registry.

## The gap (CONFIRMED)

- `compiler.py:915-927` checks `mechanical` against `_ALLOWED_MECHANICAL_KINDS` and rejects a `tools:` grant. It makes no `_check_trust` call.
- `_check_trust` (`compiler.py:488-512`) is called for every other kind a manifest can name: context_provider (`:344`), input_provider (`:351`), strategy (`:904`), gate (`:933`), hook (`:976`), validator (`:982`), compaction (`:990`), post_step (`:996`), task_parser (`:1253`) and deliverable (`:1623`). For a trust source outside `{file, builtin, db}` (`compiler.py:228`, so `user`) it raises when the capability is not `user_allowed`.
- For a code step the flag is read only by the palette: `AgentsPopup.tsx:1680` filters `c.kind === "mechanical" && c.user_allowed`. A body-supplied manifest for an unsaved composition is compiled at `trust="user"` ([ADR-0016](20260824-1630-ADR-0016.md), [FIX-282](20260824-1618-FIX-282.md)), so an API caller is not limited by the palette.

## Reproduction (in-process, 2026-10-02)

Throwaway capabilities registered in memory, `compiler._ALLOWED_MECHANICAL_KINDS` extended the way a developer adding a kind would, no application source edited. One-step manifest as in `test_mechanical_publish_step.py:36-48`.

| capability (all `user_allowed=False`) | trust | result |
|---|---|---|
| `validators: ["zz_priv_val"]` (control) | user | CompilerError: capability ('validator', 'zz_priv_val') is not user-allowed ... (CAP-03) |
| `validators: ["zz_priv_val"]` (control) | db | compiles (db is a trusted source, by design) |
| `mechanical: "zz_priv"` | user | **compiles** |
| `mechanical: "zz_priv"` | db, file | compiles (trusted, by design) |

## Exposure today

None. All four shipped code steps register `user_allowed=True` (probe: publish, assemble_prototype, assemble_backlog and extract_prototype_ui all read `True`). It matters the day someone registers a code step that must stay off the user palette (the recipe in ADR-0045 shows `user_allowed=True` as the template, so the flag is easy to get wrong in both directions).

## Expected vs actual

- **Expected:** at `trust="user"`, `mechanical: <kind>` for a kind registered `user_allowed=False` raises a CompilerError naming `('mechanical', kind)`, like every other kind. Trusted manifests are untouched.
- **Actual:** it compiles.

## Where a fix belongs

`backend/agents/workflows/compiler.py`, directly after the membership check at `:917-921`: one `self._check_trust(registry, "mechanical", mechanical, trusted, where)`. `_check_trust` returns at once for a trusted manifest, so file, builtin and db manifests, including every shipped workflow, are unchanged. For `trust="user"` it asks `registry.is_user_allowed`, which runs `discover()` lazily (`registry.py:484-494`), as it already does for every other kind under `user`. The structural alternative in ISS-684's analysis (the compiler asking the registry whether a code step exists at all) would give this check for free, but needs a decision first.

If the owners read `user_allowed` as palette-only for code steps (ADR-0045's wording), close this as won't-fix.

## For the test-writer

Red test, offline, next to the other compile-time mechanical tests (`backend/tests/agents/test_mechanical_publish_step.py`):

1. Use the `_clean_registry` idiom (`backend/tests/unit/agents/test_registry_capabilities.py:274-304`; it does not restore `_META`, so restore that too) and register a throwaway `("mechanical", "zz_priv")` with `user_allowed=False`.
2. `monkeypatch.setattr` `compiler._ALLOWED_MECHANICAL_KINDS` to include it.
3. Compile `_manifest_one_step({"agent": "custom-agent", "instance_id": "a", "mechanical": "zz_priv"})` with `trust="user"` and expect `CompilerError` mentioning `zz_priv` and "user-allowed". Today it compiles.
4. Controls: the same at `trust="file"` and `"db"` compiles; each of the four real kinds compiles at `trust="user"`.

Mark the test `@pytest.mark.issue("ISS-1005")`.
