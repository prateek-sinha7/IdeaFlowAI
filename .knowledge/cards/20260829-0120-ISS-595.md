## Summary

Sibling of [ISS-358](20260828-2118-ISS-358.md), derived from its root cause
rather than independently reproduced. [ISS-358](20260828-2118-ISS-358.md)
validated the "chat timestamp resets to now" defect only against a
**completed** run's cold reload. The same fold mechanism is also reachable
through a **second, distinct entry point** that attaches to a run while it is
still **generating** — untested by that validation. Register entry for the
bug this analysis is for:
`BUG-20260828-095700-runs-id-chat-timestamp` (`bug-hunter/ledger.md`).

## Root cause (CONFIRMED — same mechanism as ISS-358, different trigger)

`frontend/src/app/[...view]/page.tsx:2579-2666` (`handleSwitchToLiveRun`) is
the handler wired to `AppHeader`'s running-pipeline badge/dropdown
(`frontend/src/components/layout/AppHeader.tsx:220,227-228,316-317` — "live/
building runs → onSwitchToLiveRun (no reset); terminal → onSelectWorkflowRun")
and to two call sites in `DashboardLayout.tsx` (history sidebar switch,
`DashboardLayout.tsx:2589,2603,2644,2799`). Clicking a currently-running
pipeline from either surface calls:

```
page.tsx:2635  const durableFrames = await getRunEvents(switchToken, runId);
page.tsx:2656  seedRunChatTranscript(durableFrames, false);
```

`seedRunChatTranscript` (`useRunChat.ts:702-725`) clears `seenRef`/
`lastSeqRef`, resets `messages` to `[]`, then folds every durable frame
through the SAME `handleFrame` switch ISS-358 already traced —
`upsertUserMessage` (`useRunChat.ts:322-360`, fallback at `:354`) for
`chat_message` and `upsertNarratorMessage` (`:366-406`, fallback at `:393`)
for `chat_reply`. Because `messages` was just reset to `[]`, every prior
turn takes the `idx < 0` "create" branch and stamps
`createdAt: new Date().toISOString()` — the exact fallback ISS-358's root
cause documents, for the exact same reason (the backend's `chat_message`/
`chat_reply` payload carries no `created_at` to prefer instead, confirmed at
`backend/app/api/run_commands.py:1050-1060` and the projection gap at
`backend/app/api/runs.py:1080-1093`).

So: a user who sends a chat/steering message on a run that is still
generating, then later (same session or a fresh tab) switches to that live
run via the header's running-pipeline dropdown or the history sidebar's
"still running" row, will see that earlier message's timestamp read the
switch-time "now" — not its real send time — even though the run never
finished and no full page reload occurred. This is a state ISS-358's own
validation (`## Reproduction`, explicitly "a completed run") did not
exercise, and its mechanism (`handleSwitchToLiveRun`) is a different function
from the terminal-run cold-load path ISS-358 traced.

INFERRED (not yet browser-verified): that this is actually user-visible in
the running app exactly as described. CONFIRMED is the code path itself —
every line cited above was read directly, and the fold functions are
identical to the ones ISS-358 already proved defective. What would settle
it: send a chat message on a run, let it keep generating for >60s, switch
away (e.g. to Home) without reloading, then click that run's badge in
`AppHeader`'s running-pipeline dropdown and read the message's displayed
time against the actual send time.

## Expected vs actual

- Expected: a chat message's displayed time is stable regardless of whether
  the run is reached by a full reload, a history reopen, or a live-run
  switch — and regardless of whether the run has finished yet.
- Actual (inferred from the shared code path): switching to a still-running
  run re-derives "now" for every prior turn, the same way a completed run's
  reload does.

## Fix direction

No separate fix — this closes automatically once
[ISS-358](20260828-2118-ISS-358.md)'s fix direction lands, since it is the
exact same `upsertUserMessage`/`upsertNarratorMessage` code and the exact
same missing backend field. Filed separately only so the generating-run
state gets its own explicit test coverage rather than being assumed covered
by a completed-run repro. See [ISS-413](20260828-2357-ISS-413.md) for the
generic backend-side shape of the missing piece: adding `created_at` to the
`get_run_events` projection (`backend/app/api/runs.py:1080-1093`) and merging
it into `DurableFrame.data` the same way `event_id`/`seq` already are
(`frontend/src/lib/api.ts:983`, the BUG-018 precedent) would supply a real
timestamp to prefer for every event type replayed this way — `pipeline_start`
(ISS-413's own scope), `chat_message`/`chat_reply` (ISS-358 and this card),
and any future type — fixed once in the shared projection rather than
per-consumer.
