# ISS-105

## Title

**`lifespan.shutdown()` is entered BEFORE the SSE request generators finish unwinding, so `shutdown_run_infrastructure()` snapshots `_PIPELINE_QUEUES` / `_PUMP_TASKS` while stream teardown is still in flight.** `uvicorn/server.py:287-292` cancels `server_state.tasks` when the graceful window expires and then calls `await self.lifespan.shutdown()` **without awaiting the cancelled tasks**. Reproduced twice on the throwaway probe: `lifespan_shutdown_entered` is stamped ~0.4 ms BEFORE `sse_generator_finally` (t=1786531398.0193348 vs 1786531398.019713, and again at 1786531538.125244 vs 1786531538.126372). In the real app the SSE generator's `finally` (`run_stream.py:413-419`) only logs, so no harm is expected — but the full subscriber-detach path has NOT been traced under concurrent teardown, and step 2/2b of `shutdown_run_infrastructure` reason about exactly those registries. **Fix shape:** either await the cancelled connection tasks before the lifespan (not ours to change — it is uvicorn), or make the step 2/2b snapshot tolerant of concurrent mutation and assert that tolerance in a test.

## Analysis (QA-KB-043, 2026-10-01, analyzer)

**Verdict: no runtime defect; the defect is the missing test this card itself asked for** ("assert that tolerance in a
test", Title above). Line numbers are at HEAD `024c03ef8`; the symbols are the stable handle (see
[ISS-104](20260812-1312-ISS-104.md) for what happens to line citations). Re-checkable proof is under
`evidence/qa-kb-043/` (`analyze-probe.py`, `analyze-probe-output.txt`; offline, `DATABASE_URL` pinned to throwaway sqlite).

### Root cause (CONFIRMED: each item read at the cited line)

1. **The ordering premise is real.** uvicorn 0.34.0 (`backend/.venv/lib/python3.13/site-packages/uvicorn/server.py:287-292`;
   `backend/requirements-prod.txt:27` pins the same version) cancels `server_state.tasks` on graceful timeout and then runs
   `await self.lifespan.shutdown()` without awaiting them, so a cancelled SSE request's `finally` and
   `shutdown_run_infrastructure()` (`app/main.py:419`) interleave on one loop.
2. **The step 2 / 2b snapshots are tolerant by construction, not by test.** Step 2 (`run_shutdown.py:146-154`) iterates
   `list(_PIPELINE_QUEUES.keys())` and its loop body has no `await`, so on one loop thread nothing can mutate the registry
   between snapshot and use; each item is guarded (`:151-152`) and the whole step is guarded (`:153-154`, writes
   `queue_sentinel: ...` to `summary["errors"]`). Step 2b (`:167-189`) takes `{task for task, _generation in
   _PUMP_TASKS.values()}` (`:168`) before its only await (`:170`), inside `try/except` (`:187-189`, `pump_drain: ...`).
   Probe section 5: a queue whose `put_nowait` raises is skipped with `errors == []`; a registry whose `keys()` raises gives
   `errors == ['queue_sentinel: dictionary changed size during iteration']` with `checkpointer_closed` still True.
3. **A subscriber detach does not touch these registries.** The SSE generator's `finally` is `run_stream.py:583-589` (this
   card's `:413-419` no longer points at it; I did not check history for whether it once only logged). It awaits
   `_unsubscribe(run_id, live_queue)` (`run_engine.py:265-281`), which rewrites `_SUBSCRIBERS[run_id]` under
   `_SUBSCRIBERS_LOCK` and nothing else. Probe section 4: across a detach `_PIPELINE_QUEUES` and `_PUMP_TASKS` are
   unchanged, only `_SUBSCRIBERS` changes. `shutdown_run_infrastructure()` never reads `_SUBSCRIBERS`. Detach meets shutdown
   in one place, the pump's sentinel fan-out (`_dispatch_sentinel_to_subscribers`, `run_engine.py:354-373`); probe section 3
   sweeps a detach across N = 0..5 loop turns: `errors == []`, `pump_tasks_drained == 1`, `pump_tasks_cancelled == 0`,
   `_PUMP_TASKS` emptied, and the surviving subscriber always receives `None`. N = 0 (detached before the pump forwards)
   and N >= 1 (after) are the only two distinct orderings.
4. **What does mutate those registries** (all on the loop thread; the only `to_thread` in these modules is the revocation DB
   check, `run_stream.py:264`, which touches no registry): `_cleanup_pipeline` (`run_engine.py:88-144`, pops at `:120-122`)
   from the launch and revision driver `finally` blocks (`_drive_launch_to_queue`, `run_commands.py:4422-4424`;
   `_drive_revision_to_queue`, `:5845-5847`), from the engine's injected `_resume_cleanup` hook (`app/main.py:161`), and from
   the self-heal in `_is_run_live` (`run_engine.py:209`, reached from the SSE attach `run_stream.py:699` and from
   `run_commands.py:584`, `:711`); `_get_or_create_queue` (`run_engine.py:81-85`; callers `run_commands.py:727, 1754, 2033,
   3196, 5653` and `_register_resume_queue`, `run_engine.py:501`); the pump's own `finally` (`run_engine.py:436-444`) and
   `_ensure_pump` (`:447-477`) for `_PUMP_TASKS`.

### Why no test exists (CONFIRMED)

`shutdown_run_infrastructure()` is await-free through steps 1 and 2 unless a Concierge task is registered: the step-1 await
sits behind a conditional expression (`run_shutdown.py:104-110`). Probe section 0: with only queues seeded, other tasks get
0 event-loop turns during the whole call; with one pump, 3 turns (step 2b); with a Concierge task, many. So the one real
overlap is already covered (`test_pump_that_finishes_promptly_is_drained_not_cancelled`: the pump exits on its sentinel and
pops its own `_PUMP_TASKS` entry while step 2b waits), but no test can land a mutation BEFORE the step-2 snapshot, because
none opens the only window that precedes it. `_CONCIERGE_STREAM_TASKS` appears in the tests only as the fixture's `.clear()`
(`test_run_shutdown.py:55`, `:78`), so step 1 and its M-14 cancel path (`run_shutdown.py:121-133`) have no unit coverage at
all, and `queues_sentinelled` is asserted nowhere (`grep -rn queues_sentinelled backend/tests` returns 0 hits).

### Blast radius

- One production caller: `app/main.py:419`. Test callers: `backend/tests/unit/app/test_run_shutdown.py` (9 tests, 9 passed
  at baseline in 1.86 s: `cd backend && .venv/bin/python -m pytest tests/unit/app/test_run_shutdown.py -q`),
  `tests/unit/services/test_shutdown_reachability.py`, `tests/unit/test_checkpointer_shutdown_budget.py`.
- Same snapshot pattern, same missing concurrency test: step 3 `stop_pipeline_drivers` (`run_shutdown.py:289`, `:292`) and
  `stop_run_driver` (`:322`). The same harness extends to them; no separate card (one file, one fix).
- Latent exposure the test should guard: a future `await` inside the step-2 loop (for example awaiting a put on a bounded
  queue, which `_cleanup_pipeline`'s docstring already anticipates) would make the `list()` snapshot stale mid-loop. A key
  popped during that await raises `KeyError`, which the per-item guard swallows with no entry in `summary["errors"]`, so
  the only visible effect is a lower `queues_sentinelled`. A mutator that fires once in step 1's window cannot see this; one
  that fires on every loop turn can (see "Optional hardening" below).

### Fix: where it belongs, what I accept and what I overrule

Accepted: a test-only change, no application code. One new async test class in
`backend/tests/unit/app/test_run_shutdown.py` after `TestShutdownDrainsPumpTasks`, reusing the autouse
`_isolate_registries` fixture. It passes today (it is a regression lock, not a failing repro).

Overruled or sharpened, because the agreed fix as written would pass vacuously or assert something false:

1. **The mutator must run in step 1's window.** With only queues seeded, `asyncio.gather(shutdown(), mutator())` runs
   shutdown to completion first (probe section 1: `order: ['shutdown_done', 'mutator_start...']`), so the race never touches
   the snapshot and the test passes whether or not the snapshot is tolerant. Open the window with a controllable Concierge
   task: add a task that waits on an `asyncio.Event` to `run_commands._CONCIERGE_STREAM_TASKS` (a `set`,
   `run_commands.py:1273`), start shutdown as a task, `await asyncio.sleep(0)` so it parks in step 1, mutate, then set the
   event (or monkeypatch `SHUTDOWN_CONCIERGE_DRAIN_SECONDS`, default 10.0, `config.py:318`, or the test waits the full
   drain and trips the M-14 cancel).
2. **`_cleanup_pipeline` is the driver-completion teardown, not what a detaching subscriber triggers.** Use it for the
   registry race (a driver finishing). Use `run_engine._unsubscribe(run_id, q)` for the literal detach, parametrized over
   N = 0 and 1 `await asyncio.sleep(0)` turns before it.
3. **Assert only what is invariant.** Pick numbers so pre- and post-drain counts differ (probe section 2: four queues,
   finish two, register one): `errors == []`; `queues_sentinelled` equals the keys registered at snapshot time (3), not
   `live_queues` (4, sampled at entry, `:83`); every queue, including the ones `_cleanup_pipeline` popped, ends holding
   exactly one `None`; `checkpointer_closed is True`. Do NOT assert `runs_left_for_boot_restore` against the post-mutation
   driver count: it reuses the entry-time `runs_in_flight` (`:81`, `:222-224`) and would report 4 against 2 remaining,
   which is the sibling [ISS-872](20261001-2110-ISS-872.md).
4. **Decline the optional comment above `run_shutdown.py:147`.** Its suggested wording ("safe against concurrent detach")
   would be wrong (detach does not touch these registries; the safety is "no await between snapshot and use" plus the
   per-item guard), a comment cannot fail CI, and [ISS-104](20260812-1312-ISS-104.md) (QA-KB-042) is rewriting comments in
   the same file, so a second editor there is a collision for no gain. If a comment is wanted later, cite symbols, never
   line numbers.

Optional and cheap, same file, mirroring the existing `_BoomDict` test (`test_run_shutdown.py:138-153`): the step-2 guards
(probe section 5). A queue whose `put_nowait` raises leaves the others sentinelled with `errors == []`; a registry whose
`keys()` raises yields one `queue_sentinel:` entry and `checkpointer_closed` stays True.

Optional hardening, same file: make the mutator a background task that does one `_cleanup_pipeline` /
`_get_or_create_queue` per `await asyncio.sleep(0)` for the whole call, and have the registry record what it held when
step 2 read it (a `dict` subclass whose `keys()` stores `set(self)`, patched over `run_engine._PIPELINE_QUEUES` the way the
existing `_BoomDict` test patches `_PUMP_TASKS`; `run_shutdown` imports the registry at call time, `:72-77`, so the patch is
seen). Then `queues_sentinelled` must equal the size of that recorded set. Today the churn can only land in steps 1 and 2b,
so this costs nothing; it starts landing inside step 2 the day someone adds an `await` there, and the count stops matching.
Proved in probe section 6 by running the same churn against the real function (`queues_sentinelled=6`, recorded 6, match)
and against an in-memory copy with `await asyncio.sleep(0)` injected before the `put_nowait` (`queues_sentinelled=5`,
recorded 6, `errors=[]`): the regression is silent in `errors` and visible only in the count.
