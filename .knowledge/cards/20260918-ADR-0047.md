## Decision

An agent can ask the user a question in the middle of a run.

The `ask_user` tool emits a clarification request; the engine derives a
questionnaire round from it, runs the existing `ClarifyEngine` to put it to the
user, and merges the answers into `clarify/answers.json`.

This is a **second HITL surface**, alongside the pre-run questionnaire. Every
existing clarify card in this store describes the pre-run `ClarifyEngine` gate,
which is compiled into the plan up front and asked before any agent runs.
`ask_user` inverts that: the agent decides mid-run that it needs an answer.

## The tool asks nothing and blocks nothing

`ask_user(questions)` returns `json.dumps({"clarify_request": [...]})` and
nothing else. It imports no store, no event and no engine module — the same
store-free request-emitter shape `spawn_subagents` uses (FANOUT-01).

The ENGINE reads the request off the tool's result event and decides whether to
act on it. This is deliberate: the request is an **untrusted request from the
model**, and the kernel — not the tool — owns the pause. A tool that could halt a
run for a human by returning a string would be a tool that can halt a run for a
human by hallucinating a string.

Each question is an object the clarify UI already renders: `id`, `question`,
`answerType`, `options`, `recommendedAnswer`, `recommendedReasoning`,
`impactLevel`.

## Granting

`user_allowed=False`, exactly as `spawn_subagents`. Pausing a run for a human is
privileged, so it stays off the user palette in the composer; only a file
manifest can grant it. The only other `user_allowed` cards in this store are
about deliverables and context providers, so the tool case had no precedent to
read — hence writing it down here.

The capability provider (`capabilities/tools/providers.py`) imports NO concrete
tool. It returns `([TOOL_ASK_USER], False)` — a string key — and the factory
resolves it (`factory.py:1188`). Same shape as spec 017's pptx set and spec
018's playwright set, and the reason `agents/` stays import-clean of `app.*`.

It also needs its own entry in `workflows/permission_caps.py`; a tool the caps
table does not know about is not grantable at all.

## Rounds merge, they do not replace

`_derive_clarify` turns the request into a questionnaire round.
`_merge_clarify_rounds` folds that round into what earlier rounds wrote, and the
artifact store clears the previous round's responses
(`store.clear_questionnaire_responses`).

Merging is not an optimisation. An agent may call `ask_user` more than once in a
turn — that is how a long gap list reaches the user in batches instead of as one
wall of questions — and every call lands in the same `clarify/answers.json`. A
plain write would leave only the LAST batch on disk and every answer from an
earlier round would be gone before the folding step read the file.

The merge rules:

- keyed by question `id`, **newer wins** — re-asking a question is a correction,
  not a duplicate;
- order follows first appearance, so the file reads in the order the user was
  asked;
- `rounds` counts the calls;
- `clarified_topics` and `explicit_constraints` are unioned.

## What a future author must do

Anyone touching the clarify path will find the pre-run gate first — it is bigger,
older and has 34 cards. Check whether the change also affects `_derive_clarify` /
`_merge_clarify_rounds`. The two surfaces share `ClarifyEngine`, the answers file
and the frontend (`InlineClarifyActions`), and only one of them is documented
anywhere else.
