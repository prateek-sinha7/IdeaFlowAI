# ISS-101

## Title

context_provider:conversation still materialises a whole run's event log server-side to keep six chat turns. agents/capabilities/context_providers/conversation.py:99 calls scoped_store.read_events(run_id, 0) and then filters to chat_message/chat_reply in Python — on the worst run in the local corpus that is 12,123 rows / ~9.2 MB to render a ≤6,000-char transcript. This is not a token cost and not a regression: the model never sees it, and before FIX-233 the deleted read_events tool triggered the identical read (the prompt ordered the model to call it). But FIX-233 wired the provider into every Concierge turn, so the read is now UNCONDITIONAL rather than dependent on the model choosing to call a tool. The bounded counterpart already exists — ScopedStore.read_events_of_types(run_id, types, limit=…), added by FIX-233 — so the fix is a one-line swap. Deliberately not taken in FIX-233: conversation.py is shared kernel capability code with its own contract and unit tests, and narrowing its read from 'all chat rows' to 'the last N chat rows' is a behaviour change to a capability outside that issue's scope; its degrade-to-{} error path would also hide the change from any duck-typed store fake that lacks the new method.

## Source / evidence

Found 2026-08-12 while wiring the multi-turn replacement in quick-260812-gsf. Row counts measured read-only against backend/dev.db.
