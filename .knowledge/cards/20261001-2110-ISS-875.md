# ISS-875

**Register source:** `QA-KB-021` in root `LEDGER.md` / `BUGS.md` (sibling, derived during its analysis on 2026-10-01).
**Root card:** [ISS-682](20260904-ISS-682.md) holds the root cause and the fix location.

**Claim status: INFERRED.** Every hop below was read in the current tree, but no run or test has exercised it end to
end. What would settle it is under "What would settle it".

## Why the root cause implies this

The fix for QA-KB-021 makes `ComposerPage` receive the saved row's whole manifest (`initialManifest`) so
`buildWorkflowManifest` can pass through every top-level key the canvas does NOT model. The complementary half of that
design is the keys the canvas DOES model. `manifestTopLevelExtra` skips them
(`frontend/src/store/api/userWorkflows.ts:606-624`, `MODELED_MANIFEST_KEYS` = steps, capabilities, deliverable,
planner, clarify, context_providers, design_mode) on the premise that Composer state recomputes them on Save. That
premise holds only if each modeled key is hydrated on load. Checked one by one:

| modeled key | hydrated on load by | verdict |
|---|---|---|
| steps | `initialManifestSteps` | ok |
| deliverable, planner, clarify | `runConfigFromManifest` -> `initialRunConfig` (`userWorkflows.ts:668-680`, called by both `page.tsx` row seeds) | ok |
| context_providers (entry 0), design_mode | same helper | ok for the one provider the Composer can declare (`ContextProviderName` is `"opendesign"` only, `types/index.ts:748`) |
| **capabilities** | **nothing** | **not hydrated** |

The `capabilities` state is `const [capabilities, setCapabilities] = useState<WorkflowCapabilities>({});`
(`ComposerPage.tsx:442`). Its only writer is the toggle: `onCapabilitiesChange={setCapabilities}` (`:1435`), fed by
`CanvasView.tsx:2014-2019` (`on={!!capabilities?.internet}` / `onCapabilitiesChange?.({ ...capabilities, internet: !capabilities?.internet })`).
`WorkflowRunConfig` (`types/index.ts:727-741`) has no capabilities field, so `runConfigFromManifest` cannot carry it,
and `initialManifest` is read in exactly one place (`ComposerPage.tsx:903`, as the 5th argument to
`buildWorkflowManifest`), where `capabilities` is excluded by `manifestTopLevelExtra`.

On Save `buildWorkflowManifest` writes the key only when the state is non-empty
(`userWorkflows.ts:647-649`: `if (capabilities && Object.keys(capabilities).length > 0) manifest.capabilities = capabilities;`).
So a workflow saved with `capabilities: {internet: true}` reopens with the Internet toggle off and its next Save
persists a manifest with no `capabilities` at all. This survives ISS-682's fix, because that passthrough excludes the
key on purpose.

Run-time consequence: `backend/agents/factory.py:1401` (`if ctx.capabilities.get("internet"):`) binds the internet
tool, and a launch from a saved row falls back to the stored value
(`backend/app/api/run_commands.py:3371-3373`: `body.capabilities or raw_manifest.get("capabilities") or {}`) — the value
the re-save has just erased. The UI shows Internet off, so nothing signals the loss.

## Why the existing test does not catch it

`frontend/src/store/api/pdfToPrototypeManifestRoundTrip.test.ts:45` hands `source.capabilities` straight to
`buildWorkflowManifest`. The real `ComposerPage` passes its own `{}` state, so the test models a hydration that does not
exist.

## Expected vs actual

Expected: reopening a workflow saved with Internet on shows it on, and a re-save keeps `capabilities.internet: true`.
Actual (INFERRED): the toggle reopens off and a re-save omits `capabilities`.

## Where the fix would belong

`ComposerPage`: initialise `capabilities` from `initialManifest?.capabilities`. A `useState` initializer is enough for
a saved row, because `DashboardLayout.tsx:3212` (`key={savedComposition?.id ?? "new"}`) remounts `ComposerPage` once
the row arrives, so the initializer sees it on first mount. It depends on ISS-682's fix, since `initialManifest` is
undefined on both cold-mount seeds today. Do NOT add `capabilities` to the passthrough: it would override the user's
own toggle.

## What would settle it

A `ComposerPage` unit test next to the existing "a re-saved workflow keeps its limits block" case in
`frontend/src/components/workflow/composer/ComposerPage.test.tsx`: render with
`initialManifest: { steps, capabilities: { internet: true } }`, click Save, assert
`payload.manifest.capabilities` equals `{ internet: true }`. Expected to fail today even though `initialManifest` is
supplied. Run it as a single file.

## Test (2026-10-01)

`it.fails` "a re-saved workflow keeps its capabilities block (ISS-875)" in ComposerPage.test.tsx; observed red: `expected undefined to deeply equal { internet: true }`. Remove `.fails` when fixed.

## Fix (2026-10-01)

Fixed by [FIX-677](20261001-2119-FIX-677.md). `ComposerPage.tsx:444-446` now seeds the state with
`useState<WorkflowCapabilities>((initialManifest?.capabilities as WorkflowCapabilities | undefined) ?? {})`.
`capabilities` was not added to the passthrough. The `it.fails` now reports "Expect test to fail", which means the
inner assertion passes. The marker is left for the 6-verifier.
