# ISS-735

## Description

**INFERRED sibling of [ISS-733](20260922-1353-ISS-733.md) (QA-PS-021's root
card) — not reproduced. Filed because the root cause implies it, not because
it was observed.**

`backend/agents/registry.py:152` declares
`REVISION_BASE_MAP["custom_revision"] = "custom"`, and
`backend/agents/workflows/custom_revision/` is a real, separate manifest
directory (not just a dangling map entry) — so a custom workflow run can be
revised, the same way `prototype_revision` revises a `prototype` run. Per
`backend/CLAUDE.md`'s "Prototype build" section, a revision pipeline seeds
from the parent run's own output (`parent_run_id`).

ISS-733 establishes that nothing in the engine marks a run's persisted
`pipeline_complete` payload with "this step's content was a compensation
substitute" — the only status signals are `status`/`degraded_reason`/
`agents_failed` (`engine.py`, the `_pipeline_complete_data` block around
lines 7338-7390), none of which are set by any of the three compensation
modes when the compensating step itself completes without raising (the
`completed`-despite-no-real-deliverable case from ISS-733's Root Cause
section is exactly this: no exception, so no flag).

## Why the root cause implies this

If a parent `custom` run's deliverable was actually produced by one of
QA-PS-021's three compensation modes — a validator-role step regenerating
the missing upstream work under its own attribution, a compiler step that
silently dropped a section, or a step's raw narration text passed through
as the `streamed_text` deliverable (ISS-700) — a `custom_revision` run
launched from it has no way to know its seed was degraded. It reads the
parent's persisted output the same way it would read a clean one and
proceeds to revise content that was never the intended deliverable in the
first place, compounding the original defect one generation forward with no
new signal at the revision layer either.

## What would confirm or refute this

Not reproduced — this card is the hypothesis, not the observation. To
settle it: complete a `custom` run known to have hit one of ISS-733's three
compensation modes (e.g. reuse one of [ISS-699](20260922-1220-ISS-699.md)'s
run ids once QA-PS-019 is fixed enough for the run to reach a
`pipeline_complete`, or force the condition directly), launch a
`custom_revision` against it via `parent_run_id`, and inspect the revision
agent's seeded context for the compensated content, unflagged.

## Fixer note (2026-09-22) — NOT fixed, escalated: the test requires a schema
## change this card never proposed

5-fixer did not apply a change here.
`test_workflow_run_has_compensated_content_flag_for_revision_seeding` asserts

```python
columns = {c.name for c in WorkflowRun.__table__.columns}
flagged = columns & {"compensated", "content_compensated", "compensated_content"}
assert flagged
```

Satisfying it means adding a column to `backend/app/models/workflow.py`'s
`WorkflowRun` (`__tablename__ = "workflow_runs"`, :16) plus a new alembic
revision — the store is at `backend/alembic/versions/0047_run_manifest_json.py`,
so this would be `0048`. A schema change is explicitly outside 5-fixer's remit.

The card itself proposes no fix: its only forward-looking section is "What would
confirm or refute this", and it opens "**INFERRED sibling … not reproduced.
Filed because the root cause implies it, not because it was observed.**" There is
no card-authorised design for the flag — what sets it, what values it takes, how
a revision seed reacts — so the column shape would be invented at fix time.

Note also that the precedent in this seam runs the other way: `_apply_selections`
carries the composer's deliverable override under a reserved `__deliverable__`
key in the existing selections map precisely to avoid a column — "no new column,
no migration" (`engine.py`, the Option B / KAN-112 comment). Whether this flag
earns a column or belongs in an existing JSON payload is a design decision.

Decision needed: `ESCALATIONS.md#qa-ps-021`, question 3.

persisted `pipeline_complete` payload or the `WorkflowRun` row marks a run's content as

`agents_failed`, none of which are set by a compensating step that completes without
raising."* **Two of the three compensation modes now DO set exactly those signals**,
landed after this card was written (13:55; the fixes landed 18:38 and 18:54):

- `backend/agents/execution_engine/engine.py:7456-7459` — self-narration (mode 1) sets
  `_pipeline_complete_data["status"] = "degraded"` **and**
  `["degraded_reason"] = _placeholder_reason` ([FIX-612](20260922-1838-FIX-612.md)).
- `backend/agents/execution_engine/engine.py:7477-7490` — silent drop (mode 3) sets the
  same two keys from `dropped_section_reason`
  ([FIX-615](20260922-1854-FIX-615.md), which this card is already
  **Referenced by** via [ISS-773](20260922-1512-ISS-773.md)).
- `backend/agents/execution_engine/engine.py:7511-7513` — both escalate
  `published_status` to `degraded`, and `backend/app/api/run_commands.py:769` reconciles
  *"the LATEST `pipeline_complete` carrying `status=="degraded"` → `degraded`"* onto the
  persisted row. `WorkflowRun.status` already carries `degraded` in its declared
  vocabulary (`backend/app/models/workflow.py:41-45`), and `WorkflowRun.error` is
  derived from `degraded_reason_msg` (`run_commands.py:775-779`).

So a `custom_revision` seeded via `parent_run_id` **can** today tell that its parent was
degraded, and why, without any new column — which is also the direction the
counter-precedent in this seam points (`engine.py`'s Option B / KAN-112 comment: *"no
new column, no migration"*).

**What re-analysis must settle:** whether any residual gap remains once the parent's
`status`/`error` are read at revision-seed time — and if one does, whether it is mode 2
(unauthorized regeneration, whose trigger [FIX-608](20260922-1820-FIX-608.md) removed)
and whether it earns a column at all. Until that is answered the test
(`test_workflow_run_has_compensated_content_flag_for_revision_seeding`, which asserts a
`compensated`/`content_compensated`/`compensated_content` column exists) is asserting a
design that no card has chosen.

## Fixer note (2026-09-23): resolved by FIX-639 (decision 2a, no new column)

Decision 2 = (a): read the parent's existing `status` / `degraded_reason`, after
checking whether the seed path already reads them.

**Checked: it did not.** Every revision launch path reaches one seam: all three go
through `_drive_revision_to_queue` to `_handle_revision` (`engine.py:11915`). That seam
composed the seed from the parent's artifact refs only. It never read the parent's
`WorkflowRun` row. For `custom_revision` this block is the only seed. The
`previous_run` provider is a no-op there, because `is_revision_workflow` is False.

This was observed before the change. The rewritten test, run with `--runxfail`, failed,
and the seed carried no status.

**Fixed in [FIX-639](20260923-0148-FIX-639.md)**, at `engine.py:12064-12084`:

- After `assert_owns`, the parent row is read with
  `ScopedStore(owner_id, workspace_id=original.workspace_id).get_run(parent_run_id)`.
- When `status == "degraded"`, a `=== PARENT RUN STATUS ===` block is appended. It
  carries `WorkflowRun.error`, which is where the launch driver stores
  `degraded_reason`.
- No column, no migration, no model change.

**Test.** The old test asserted a `compensated` column, which was rejected. It is
replaced by `test_custom_revision_seed_carries_the_degraded_parent_status`. That test
was red before the change and is `[XPASS(strict)]` after.

**Residual, filed as [ISS-857](20260923-0148-ISS-857.md).** A degraded revision parent
has no `WorkflowRun.error`, so its flag reads "no reason recorded".
