# ISS-667

## Title

The Analytics Model Details panel shows "Thinking: Adaptive (effort: max)" for Claude Sonnet 5
because this app's own model catalog classifies every `sonnet-5` model id as adaptive-thinking
capable in BOTH the display path and the real Bedrock/Anthropic call path -- the two already
agree with each other. This is a deliberate catalog/product classification, not a
display-computation defect (QA-PS-009).

## Reproduction

Verified by full code-path trace. The flag is a static per-model catalog fact computed the same
way on every render, so a second/third read of the same code reproduces it identically -- this
matches the validator's own 3/3 cold-start reproduction already on record
(`WONTFIX.md#qa-ps-009`). Re-derived here from a fresh code read, not copied from that writeup.

**Route:** `/analytics` -> Model Details panel -> expand "Claude Sonnet 5 (US)" or
"Claude Sonnet 5 (EU)".

## Trace

1. `backend/agents/capabilities/model_catalog.py:134` and `:152` -- the catalog carries two
   Sonnet 5 entries, `us.anthropic.claude-sonnet-5` and `eu.anthropic.claude-sonnet-5`
   (region-routed by `model_policy.py`).
2. `backend/app/api/capabilities.py:169` --
   `_THINKING_FRAGMENTS = ("sonnet-5", "opus-5", "fable-5", "mythos-5", "opus-4")`; line 189
   sets `thinking_supported=any(frag in m.id for frag in _THINKING_FRAGMENTS)` on every
   `ModelCatalogEntry` the `/api/capabilities` endpoint returns. Both Sonnet 5 ids contain
   `"sonnet-5"`, so `thinking_supported=True` for both.
3. `frontend/src/components/analytics/AnalyticsPage.tsx:826-831` -- renders a hardcoded
   `Thinking` / `Adaptive (effort: max)` row whenever `entry.thinking_supported` is true. The
   text is the same literal string for every flagged model; nothing model-specific is derived.
4. `backend/app/agents/model_factory.py:123` --
   `_ADAPTIVE_THINKING_MODEL_FRAGMENTS = ("sonnet-5", "opus-5", "fable-5", "mythos-5")`, the
   tuple that actually selects `thinking.type="adaptive"` (`:126`, used at `:139` and `:196-199`)
   for a REAL Anthropic/Bedrock call. `"sonnet-5"` is in this tuple too, so a real pipeline run
   on either Sonnet 5 catalog entry, with thinking turned on
   (`settings.THINKING_BUDGET_TOKENS > 0`), does in fact get `thinking.type="adaptive"` --
   matching exactly what the panel displays.
5. `.knowledge/cards/20260907-1239-FIX-491.md` (the card that built this panel) documents
   `thinking_supported: True for sonnet-5/opus-4/opus-5 fragments` as the intended value, not a
   bug, and locks in "model metadata must come from the live `/api/capabilities` catalog" as a
   constraint.

This is a **structural, deterministic** flag: it does not depend on timing, account tier,
theme, viewport, or empty/populated analytics data -- every Sonnet 5 catalog entry resolves
through this same path with the same result.

## Expected vs Actual (as filed in `BUGS.md#qa-ps-009`)

- **Expected (reporter):** Sonnet 5 shows no Thinking row, because the reporter's real-world
  reference model does not support extended thinking.
- **Actual:** The row is shown, and it is shown because this app's catalog deliberately -- and
  consistently, across both the display path and the real activation path -- models
  `sonnet-5` as an adaptive-thinking-capable model.

## Root cause

Not a code defect: `thinking_supported` (`capabilities.py:189`) and the adaptive-thinking
selector (`model_factory.py:126`) agree with each other for `sonnet-5` -- the display is an
accurate report of a deliberate catalog classification, already locked by FIX-491. Whether that
classification should change is a product decision: changing it would also change real run
behavior for every Sonnet 5 invocation (turning adaptive thinking off), not just a UI label, so
this analysis cannot resolve it unilaterally.

## Disposition -- needs a human decision

This independently confirms the validator's `WONTFIX.md#qa-ps-009` reasoning from a fresh code
read. See `ESCALATIONS.md#qa-ps-009` for the decision needed and the options.

## Blast radius / sibling found

Grepping every consumer of `_THINKING_FRAGMENTS` / `_ADAPTIVE_THINKING_MODEL_FRAGMENTS` /
`thinking_supported` -- the blast-radius work this report's own Sonnet-5 symptom did not need,
since Sonnet 5 turned out self-consistent -- surfaced a genuine, separate drift affecting a
DIFFERENT model tier: [ISS-668](20260917-1325-ISS-668.md) (Opus 4.5 / Opus 4.6 show the same
"Adaptive (effort: max)" label, but their real thinking type is "enabled", not "adaptive").

## Product decision (2026-09-17, user)

Scope is the LABEL only. Sonnet 5 does run with adaptive thinking (`model_factory.py:139` sends
`{"type": "adaptive", "budget_tokens": 32767}`; `THINKING_BUDGET_TOKENS=32767`), so the Thinking row
STAYS. The app never sends an `effort` parameter, so "effort: max" is false.
Fix: `frontend/src/components/analytics/AnalyticsPage.tsx:829` — render `Adaptive`, not
`Adaptive (effort: max)`. Do NOT remove the row, do NOT change `_THINKING_FRAGMENTS` /
`_ADAPTIVE_THINKING_MODEL_FRAGMENTS`, do NOT add an effort parameter. The reporter's "row should not
show" is superseded by this decision. Evidence: WONTFIX.md#qa-ps-009 § Evidence trace.

## Resolution (2026-09-17, 5-fixer)

Resolved by [FIX-524](20260917-1639-FIX-524.md): `AnalyticsPage.tsx:829` now renders `Adaptive`, as the
decision above requires. Its test (`AnalyticsPage.test.tsx`, "ISS-667 — Sonnet 5 shows 'Adaptive' with no
fabricated effort qualifier") failed before the edit and passes after it. The 6-verifier still has to re-run
the `/analytics` reproduction in the browser.
