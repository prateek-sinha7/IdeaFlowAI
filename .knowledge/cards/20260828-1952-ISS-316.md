# ISS-316

## Reproduction (3/3, cycle 1)

Confirmed on 3/3 cold-start attempts, each producing the identical result on
attempt 1 — no narrowing needed.

1. Sign in as `qa-admin`. Load `http://localhost:3000/runs/a8dfa959-e233-4ddf-87ce-d9a942cefde3`
   (a fresh page load / full navigation each time, never a soft re-click).
2. The header badge reads "Cancelled" / "Cancelled by you"; the result panel shows
   "This run was cancelled — The run was stopped before producing a deliverable." directly
   above a "Failed agents" list naming all 4 pipeline agents (Presentation Strategist Agent,
   PPTX Code Generator, Deck Engineer Agent, Deck QA Agent).
3. `GET /api/runs/a8dfa959-e233-4ddf-87ce-d9a942cefde3` (called from the page via
   `fetch` with the stored `auth_token`) returns `{"status": "cancelled", "error": null}`
   on every one of the 3 cold loads.
4. `http://localhost:3000/runs` (Run History list) shows the same run's card tagged
   "cancelled".
5. `GET /api/runs/{id}/events` tail: two `agent_error` events, then `pipeline_failed` at
   seq 29, then a `chat_reply` "What went wrong" at seq 30 — no `pipeline_complete` anywhere
   in the resumed attempt's tail. All 4 agents ended in `agents_failed`.

Register entry: **BUG-20260828-085830-runs-cancelled**.

## Root cause

`backend/app/api/run_commands.py`, `_reconcile_terminal_status` (~line 748-838), the
function the "Run Again" / user-resume drive path (`_drive_user_resume`, line 709-745) calls
at line 740 to persist the resumed run's terminal status from the durable `run_events` tail.

The function computes a `resume_supersedes` flag (line 811-818) meant to let a resume's
own outcome override the run's earlier `pipeline_cancelled`:

```python
complete_seqs = [e.seq for e in completes
                 if not (isinstance(e.payload_json, dict)
                         and e.payload_json.get("status") == "degraded")]
...
resume_supersedes = (
    cancelled
    and complete_seqs
    and max(complete_seqs) > max(cancelled_seqs)
    and any(
        max(cancelled_seqs) < s < max(complete_seqs) for s in reattempt_seqs
    )
)
if cancelled and not resume_supersedes:
    new_status = "cancelled"
elif degraded:
    new_status = "degraded"
elif completes and not failed:
    new_status = "completed"
else:
    new_status = "failed"
```

`resume_supersedes` is keyed **exclusively on `complete_seqs`** — a `pipeline_complete`
event. When a resumed pipeline genuinely fails, the durable tail carries `pipeline_failed`
instead of `pipeline_complete`, so `completes` (and therefore `complete_seqs`) is empty.
`resume_supersedes` short-circuits to `False` on the `complete_seqs` truthiness check, so
the very first branch (`if cancelled and not resume_supersedes`) fires and
**unconditionally re-persists `"cancelled"`**, even though the resumed attempt is a later,
more recent outcome that genuinely failed. The `else: new_status = "failed"` D2 fail-safe
three lines below is correct in isolation but is unreachable for this exact case — it can
only be reached when `cancelled` is `False`, which it never is here (the run's original
seed status carries a `pipeline_cancelled` event in its earlier attempt).

This is the resume tier's mirror-image gap to what ISS-124/FIX-244 fixed on the launch/
revision drivers (a cancellation not being durably recorded at all); here the durable
`pipeline_cancelled` record from the *original* cancellation is recorded correctly, but the
reconciler has no code path that lets a *later* `pipeline_failed` supersede it the same way
a later `pipeline_complete` does. FIX-105/KAN-120 (the card that introduced
`resume_supersedes`) only handled the completed-resume case; the failed-resume case was
never covered.

## Expected vs Actual

**Expected:** once a resumed run's pipeline genuinely fails (`pipeline_failed` at a seq
later than the original cancellation, inside a new attempt bounded by a `run_resuming`/
`pipeline_start` row), `_reconcile_terminal_status` should persist `status="failed"` —
matching what the same page's body already renders ("Failed agents") — the same way it
already lets a later `pipeline_complete` supersede the cancellation.

**Actual:** `status` is durably and permanently stuck at `"cancelled"`. Every surface that
reads it — the `/runs/{id}` detail badge, the `/runs` history list, and the raw API
response — misreports the run indefinitely, while the very same detail page's body
independently derives and shows the correct "Failed agents" outcome from the event stream.

## Fix shape (not applied — validator scope is confirm-only)

Extend `resume_supersedes` (or add a parallel `resume_fails` flag) to also treat a
later-attempt `pipeline_failed` seq (or the D2 fail-safe conditions generally) as superseding
the earlier `cancelled`, using the same `reattempt_seqs` attempt-boundary guard FIX-229/
ISS-078 already established for the completed case — so the status ladder becomes
"latest attempt's outcome wins" symmetrically for both completion and failure, not just
completion.
