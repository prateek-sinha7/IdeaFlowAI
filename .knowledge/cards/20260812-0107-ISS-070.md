# ISS-070

## Title

**The gate-action discriminator is unvalidated, and an unknown action silently APPROVES.** `run_commands.py` `resolve_gate` dispatches on `action` with `else: # approve` as the fallback, so any unrecognised string — a typo, a stale client, a probe — resolves the HITL gate as approved. `GateCommand.action` is a bare `str` with no enum (live OpenAPI confirms `{"type": "string", "default": "approve"}`) while the frontend declares the closed union `"approve" \| "reject" \| "redo" \| "update_specs"` (`frontend/src/lib/api.ts:690`). The endpoint also contradicts its own sibling: the Concierge disposal takes the opposite, safer default and says so in-code — "M1: a MISSING action must NEVER silently approve a gate". Sibling gap on the same model: `GateCommand.analysis_report` is `str \| None` with **no length cap**, and it is injected into every re-dispatched prompt.

## Source / Evidence

Found 2026-08-12 by the ISS-053 investigation + fix (quick-260812-12t). **Deliberately NOT fixed there** — it is a distinct defect from the eligibility gap and folding it in would have been scope creep; ISS-053's fence is orthogonal (it constrains one action, this constrains which strings are actions at all). Fix shape: promote `action` to a `Literal[...]` so FastAPI rejects garbage at the boundary, and make the fallback deny rather than approve. Note the fix is NOT purely additive — a client today relying on the lenient default would start getting 422s, so check the FE and any scripted callers first. **CLOSED 2026-08-12 by FIX-241 — and this row was corrected on three points before it was.** **(1) Scope was over-generalised.** Only ONE of the three `set_review_response` ingresses was defective: `resolve_gate`'s `else` at `run_commands.py:272`. `/messages` `CHANNEL_GATE` (`:1322`) is fenced by `chat_router.py:234` — verified by reading BOTH `Dispatch(channel=CHANNEL_GATE)` construction sites (`chat_router.py:244`/`:255`), each of which requires `turn.action in GATE_ACTIONS`; the Concierge confirm (`:1101`) is fenced by `concierge.py:350` normalisation plus H1 (params are server-written, never client body). Both were hardened to the same fail-closed shape, but as hardening, not as the fix. **(2) Retagged `api,auth` → `api,validation`.** This is NOT an authorization defect: `resolve_gate:222` → `run_engine.py:765` filters `WorkflowRun.user_id == user_id`, so a cross-owner caller gets a non-revealing 404 and nobody else can approve your gate. The affected principal is the run's own owner. Severity stays **major** — a HITL safety gate fails open, invisibly, on the remainder of a 5–21M-token budget. **(3) The row understated it: the audit record was LAUNDERED.** The `else` never passed `action=`, so `store.set_review_response`'s own default (`store.py:123`) persisted `action="approve"` while `resolve_gate:278` echoed the garbage string back to the caller — measured directly: `action='rejct' → HTTP200 approved=True stored_action='approve'`. That is very likely why this was never noticed in a live log. On the declared-gate path an unknown action also resolves a formal `GATE_PASS` (`human.py:104-141`). **Fix:** `action` → `Literal["approve","reject","redo","update_specs"]` **with the default retained** (making it required would break `test_attach_replay_matrix.py:551`'s bare POST and the published OpenAPI contract), plus a fail-closed dispatch `else` raising 400 `unknown_gate_action`/`recoverable:true`. It REFUSES and never degrades to a reject — FIX-232 makes rejection terminal, so a typo must not destroy the run. Both layers mutation-proved independently. The `analysis_report` length-cap half of this row is split out as **ISS-127**, not folded in.
