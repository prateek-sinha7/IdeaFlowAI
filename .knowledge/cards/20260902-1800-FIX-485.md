## Symptom

On Windows, `pytest tests/unit/test_skill_staging.py::test_staged_skill_carries_its_referenced_sibling_files`
failed with:

```
AssertionError: assert [] == ['systematic-debugging']
```

The warning line in the log:

```
WARNING  app.agents.skill_staging:skill_staging.py:217 skill staging:
systematic-debugging: failed to stage ('charmap' codec can't encode
character '\u2192' in position 1737: character maps to <undefined>)
```

The `systematic-debugging` global catalog skill contains a `→` character (U+2192).
The staging code writes the synthesized `SKILL.md` with `target.write_text(file_text)`
(no encoding argument). On Linux Python defaults to UTF-8, so this never surfaced.
On Windows Python defaults to the active code page — `cp1252` in the test environment —
which cannot encode U+2192 and raises a `UnicodeEncodeError`. The `try/except` block
around the write caught the exception, appended an error string, and `continue`d past
`staged.append(skill_id)`, so `result.staged` came back `[]` instead of
`["systematic-debugging"]`.

The `read_text` call on the same line already had `encoding="utf-8"` — the `write_text`
call was simply missing it.

## Root cause

`backend/app/agents/skill_staging.py` line 183 (pre-fix):

```python
if not (target.exists() and target.read_text(encoding="utf-8") == file_text):
    target.write_text(file_text)    # ← missing encoding="utf-8"
```

## Fix

One argument added, `skill_staging.py:183`:

```python
if not (target.exists() and target.read_text(encoding="utf-8") == file_text):
    target.write_text(file_text, encoding="utf-8")
```

No logic change. The write now uses the same codec as the read.
