## Why the status dependence is the diagnostic

The routes themselves are fine — every one of them resolves correctly against a
completed run. So this is not a missing route or a broken parser; something on
the live-run path overrides the requested tab after resolution. That narrows
the search to whatever the `generating` status branch does on cold mount, and
rules out the routing contract itself.

## The user-visible cost

"Look at the audit trail of this running job" is not expressible as a link.
Every share of a live run lands the recipient on Steps, which is both the wrong
screen and indistinguishable from the sender having sent the wrong URL.

## Root cause (QA-KB-049 analysis, 2026-10-02)

CONFIRMED by source read unless a line says INFERRED. Nothing was executed: no browser, no test run.

The status dependence above is real, but the switch is not the run's status. It is `pipelineState.isRunning` of the
VIEWED run, and what acts on it is one effect in `DashboardLayout.tsx`, not anything on the `page.tsx` cold-mount path
(so the card's first guess, a status branch on cold mount, is half right: the status only matters through `isRunning`).

### The mechanism

1. `frontend/src/components/layout/DashboardLayout.tsx:822-903` is the effect its own comment calls "the single funnel
   every launch path's pipelineRunId flows through" (`:843-846`). `:823` gates on `pipelineState?.isRunning`, and
   `:854-856` then does

   ```ts
         if (incomingRunId) {
           router.push(routes.runStream(incomingRunId));
         }
   ```

   with no read of the current URL. Its deps are
   `[pipelineState?.isRunning, pipelineState?.pipeline_type, pipelineState?.pipelineRunId]` (`:903`). The push arrived
   with spec 015 (commit 887ccfe96, 2026-08-21).

2. How a cold load reaches it. `/runs/{id}/audit` parses to `run-audit` (`frontend/src/lib/routes.ts:411`). T7
   (`frontend/src/app/[...view]/page.tsx:3462-3564`) calls `handleSelectWorkflowRun({ id })` (`:3552`), which switches
   the store viewport to the run (`:2922`), attaches the stream when the run is not terminal (`:2993`), and replays the
   durable log through `handleWebSocketMessage` (`:3074-3087`). The replayed `pipeline_start`, or `planner_start`, sets
   `isRunning: true` and `pipelineRunId` (`frontend/src/hooks/useWorkflow.ts:797-799`, `:1707-1712`). The store
   projects it because the run is the viewed one (`frontend/src/hooks/useRunStateStore.ts:598-602`), and
   `displayedPipelineState = runStore.viewed.pipelineState` (`page.tsx:4158`) is passed to DashboardLayout (`:4197`).
   The effect's deps change and it pushes `/runs/{id}/stream`.

3. Why the TAB is lost and not only the URL. The push changes the `[...view]` params and remounts `page.tsx`
   ([FIX-298](20260825-FIX-298.md)). T7's pending deep link,
   `.finally(() => { if (tab) runTabDeepLink.requestOpenTab(...) })` (`page.tsx:3560-3562`), belongs to the unmounted
   instance. The new mount is `/stream`, whose screen carries no tab (`reopenTabFor`, `page.tsx:274-292`, has no
   `run-stream` case), so PreviewPanel's state-keyed default picks Steps for a building run
   (`frontend/src/components/preview/PreviewPanel.tsx:1288-1295`).

4. Why it depends on status. The effect acts only while `isRunning` is true (`:823`). A terminal run's replay ends in
   a terminal frame or in `reconcileTerminalStatus` (`page.tsx:3111-3131`) inside the same synchronous batch, so
   `isRunning` is already false when React commits and nothing is pushed. The batching part is INFERRED; the report's
   own control, a completed run keeps its URL, and the offline-tier scenario `S-14-08`
   (`tests/integration/e2e/suites/14_run_states/test_run_states.py:154-171`) agree with it. The scenario written for
   this bug, `S-14-07` (same file, `:146-151`), is a skipped live-tier stub.

5. Seen in a real browser before this analysis: `tests/integration/DEFECTS-OBSERVED.md` D-06 and
   `tests/integration/capture/46-live-run-tab-deeplink.json`
   (`{"url": ".../runs/72e2f445-.../stream", "selected": ["Steps"], "status": "Running"}`).

Ruled out. No other automatic `routes.runStream` push exists: the rest are click handlers
(`DashboardLayout.tsx:2818`, `:2839`, `:2885`, `:2901-2941`, `:3050`, `:3470`; `page.tsx:2895`;
`StepsOverviewSpine.tsx:52`). There is no `location.replace` or `location.assign` in the run path, and `proxy.ts` and
`next.config.ts` carry no run rules.

### Where the fix belongs

At the funnel, once: `DashboardLayout.tsx:854-856`. Every caller above arrives there, so a guard in each caller would
leave the rest. Skip the push when the URL already addresses `incomingRunId`:

```ts
const here = parseViewPath(window.location.pathname.split("/").filter(Boolean).map(decodeURIComponent));
if (incomingRunId && !("runId" in here && here.runId === incomingRunId)) {
  router.push(routes.runStream(incomingRunId));
}
```

with `parseViewPath` added to the existing `routes` import (`DashboardLayout.tsx:39`). Notes for the fixer:

- Use `parseViewPath`, not `pathname.startsWith("/runs/" + id + "/")` as the triage sketch in BUGS.md does. That is a
  hand-written path literal, which [ADR-0018](20260824-1631-ADR-0018.md) calls a defect, and it misses the bare
  `/runs/{id}` (no trailing slash). `frontend/src/app/error.tsx:24` already parses a pathname this way outside page.tsx.
- Use `window.location.pathname`, not `usePathname()`. All seven test files that render `<DashboardLayout`
  (`components/DashboardLayout.chain.test.tsx` and `components/layout/DashboardLayout.{catalogHome,iss644,iss656,launchLatch,laneTitle,revisionRouting}.test.tsx`)
  mock `next/navigation` with `useRouter` only, so a `usePathname` call would throw in each. `window.location.pathname` is
  already read in this file (`:538`, `:603`) and follows the `pushState` tab switches.
- Do not delete the push. Launch, revision and resume depend on it (FR-010; the FIX-298d note at `page.tsx:3769`; the
  comment at `DashboardLayout.tsx:843-853`).
- Do not key it on `status`: see [ISS-957](20261002-0316-ISS-957.md).
- Behaviour change to confirm in verification: Resume or Run Again from `/runs/{id}/<tab>` stays on that URL instead of
  landing on `/stream`. The Expected in BUGS.md ("Only a fresh launch lands on /stream") supports it; if it is not wanted,
  have `handleResumeRun` set a one-shot ref that bypasses the guard.
- INFERRED, to settle in a test or the browser: that skipping the push alone also keeps the tab. T7's `.finally` deep
  link lands after the replay (`page.tsx:3560-3562`) and PreviewPanel's merged effect lets a fresh deep link win over the
  state default (`PreviewPanel.tsx:1262-1286`), so Audit should win after a brief Steps flash. Nothing read proves it.

Left alone: `appliedRunViewKeyRef` stays per-mount ([FIX-635](20260922-2335-FIX-635.md)), tab clicks stay `pushState`,
and T11 still attaches only on `/stream`.

## Fixed — QA-KB-049 (fixer, 2026-10-02): [FIX-712](20261002-1155-FIX-712.md)

The fix went in where "Where the fix belongs" above puts it, at the funnel (now `DashboardLayout.tsx:854-858`). The
effect parses `window.location.pathname.split("/").filter(Boolean)` with `parseViewPath` and skips the push when that
`runId` equals `incomingRunId`. It differs from the snippet above in one way: there is no `decodeURIComponent`. The run
builders do not encode ids, and a malformed `%` sequence would throw inside the effect. Resume of the same run from its
own run URL now stays on that URL, which is the behaviour change flagged above.
