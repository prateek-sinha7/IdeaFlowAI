# ISS-674

## Title

The header's own inline running-pipeline indicator — the single-run badge next to the bell, and the "N Running" dropdown (KAN-132) when more than one pipeline is active — shows the identical frozen agent-progress count the notification panel shows, because both read the same array.

## Status: INFERRED — not yet reproduced live

Derived from [ISS-673](20260917-1420-ISS-673.md)'s confirmed root cause, not from an independent browser reproduction. The code path is read and cited below; confirm live before treating as a defect distinct in remediation (it shares its fix with [ISS-673](20260917-1420-ISS-673.md)).

## Why ISS-673's root cause implies this

[ISS-673](20260917-1420-ISS-673.md) confirms that `AppHeader.tsx`'s `runningPipelines` array (built at `AppHeader.tsx:194-221` from `recentRuns` + the render-stale `runAgentsCompletedMap`) is passed to `NotificationPanel` as `liveRuns` (`AppHeader.tsx:482`) — that is the reported symptom. But `runningPipelines` is a single array read by THREE places in the same file, not one:

- `AppHeader.tsx:341-345` — when exactly one pipeline is running, the header shows a badge next to the bell: `{runningPipelines[0].agentsCompleted ?? 0}/{runningPipelines[0].agentsTotal}`.
- `AppHeader.tsx:391,433-436` — when more than one pipeline is running, a "N Running" dropdown lists each: `{pipeline.agentsCompleted ?? 0}/{pipeline.agentsTotal}` per row (`:433-436`).
- `AppHeader.tsx:474,482` — the same array passed to `NotificationPanel` as `liveRuns`.

All three read `agentsCompleted`/`agentsTotal` off the exact same object references in `runningPipelines`. Since [ISS-673](20260917-1420-ISS-673.md) shows that array's `agentsCompleted` field for any non-`activePipelineRunId` entry is frozen at the value `runAgentsCompletedMap` held at the last unrelated re-render of `page.tsx` (not live), the badge and dropdown are wrong for exactly the same runs, at exactly the same moments, as the notification panel — they cannot be right while the panel is wrong, because they are reading the same value.

## Expected (once reproduced)

The header's single-run badge and the "N Running" dropdown show each background pipeline's real, currently-completed agent count, matching that run's own `/runs/<id>` stream page at the same moment.

## Actual (inferred, not yet observed)

Expected to show "0/N" (or whatever stale count was captured at the last unrelated render) for every pipeline that is not the one currently being viewed, identically to the notification panel — including the multi-pipeline case from the original QA report (three concurrent runs), where the dropdown would list all three rows wrong simultaneously.

## What would confirm this

1. Launch two or more concurrent runs in one tab (matches the original QA repro).
2. Navigate to `/dashboard` (none of them is `activePipelineRunId`).
3. Open the "N Running" dropdown (or, with exactly one still running, look at the single badge) and compare its "X/N" per pipeline against that same run's own `/runs/<id>` stream page checked at the same moment.
4. Switch to view one of the runs (making it `activePipelineRunId`) and confirm only that one row/badge corrects itself immediately, while the others stay frozen — this specifically confirms the `isActive` branch (`AppHeader.tsx:215`) is what separates "correct" from "frozen," not something specific to the notification panel's own rendering.

## Fix

Shares [ISS-673](20260917-1420-ISS-673.md)'s fix location exactly (`frontend/src/hooks/useRunStateStore.ts` — the shared producer of the data both surfaces read). No separate fix is expected; this card exists so the test-writer asserts the header surfaces too, not only the bell panel, and so this location isn't rediscovered later as if it were a new bug.

## Resolution (2026-09-17, [FIX-521](20260917-1447-FIX-521.md))

Fixed by ISS-673's change to the shared producer, as predicted. There was no separate edit.
Verification covers the shared producer only: `useRunStateStore.iss673.test.tsx` proves a
background completion re-renders the store's consumer. No test renders `AppHeader` itself. The
single badge (`AppHeader.tsx:343`) and the "N Running" dropdown rows (`:435`) read the same
`runningPipelines` array the panel does, so the live check should look at those two surfaces
alongside the bell panel. One known limit: while the dropdown is open it shows the snapshot taken
when it opened (FIX-519), so its counts refresh only after it closes and reopens.

## Reopened (2026-09-17, 5-fixer)

This card shares its cause and fix with [ISS-673](20260917-1420-ISS-673.md), and that card has
been reopened. The resolution above does not hold live. After a remount of page.tsx (navigating
to `/dashboard`, or a reload), a background run's store entry has no agent list, so
`completedCount` stays 0. The single badge and the "N Running" dropdown show the same 0 as the
panel. See ISS-673's "Analysis missed" section.

## Re-analyzed (2026-09-17, 3-analyzer)

[ISS-673](20260917-1420-ISS-673.md)'s own fix location has moved — see
[ISS-679](20260917-1522-ISS-679.md), which confirms the shared cause is a `page.tsx` remount
wiping `useRunStateStore`'s per-run map, not merely a missing re-render. This card's own claim
("shares ISS-673's fix location exactly") still holds: whatever ISS-679 recommends fixes this
card's two render sites too, with no separate edit expected, same as before.

## Resolution (2026-09-17, [FIX-523](20260917-1555-FIX-523.md))

Fixed by the same change as [ISS-679](20260917-1522-ISS-679.md), with no separate edit, as this card
predicted. After a client-side navigation, a background run keeps its roster, so `completedCount`
advances. The single badge (`AppHeader.tsx:343`) and the dropdown rows (`:435`) read that count
through `runningPipelines`.

No test renders `AppHeader`. The live check should look at these two surfaces beside the bell
panel, after a Home click, not after a reload ([ISS-680](20260917-1555-ISS-680.md)). The
dropdown's open-time snapshot (FIX-519) still applies.
