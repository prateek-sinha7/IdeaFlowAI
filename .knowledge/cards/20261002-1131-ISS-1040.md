# ISS-1040

Sibling of [ISS-945](20261002-0053-ISS-945.md), found by the QA-KB-087 analysis on 2026-10-02 with the same scan as
[ISS-1039](20261002-1131-ISS-1039.md) (every `it.fails` file in `frontend/src` run with the marker removed, on copies outside the repo;
`evidence/qa-kb-087/07-analyze-itfails-scan.txt`). Confidence: CONFIRMED by that run; no repo file was edited. A validator re-run is
still pending.

## Why the root cause implies it

Same class as [ISS-945](20261002-0053-ISS-945.md): an `it.fails` case that throws before its behavioural assertion, so it can never show
the XPASS that marks its bug fixed. Here the thrown error is a lookup in the case's own scoping.
[ISS-600](20260829-0341-ISS-600.md) found that the first text-free button on the page is the PAT eye toggle, not the key copy button,
and suggested scoping to the key banner with `within(screen.getByText("New key — copy now").closest("div")!)`.
[FIX-453](20260901-1600-FIX-453.md) applied that verbatim (`:94-95`). But `getByText` returns the title element itself,
`<div class="font-semibold mb-1">New key — copy now</div>` (`IntegrationsCard.tsx:383`), and `Element.closest` starts at the element, so
`.closest("div")` is the title div. The copy button sits in its sibling row (`:384-404`), outside it.

## Condition

Remove `it.fails` from the "API-key 'copy now' button" case (on a copy; the repo file stays) and run it.

## Expected

The case clicks the key copy button and reaches `expect(screen.queryByText(/copied|fail|error/i)).toBeInTheDocument()`, which passes:
the button now renders "Copied" or "Copy failed" (`keyCopied` / `keyFailed`, `IntegrationsCard.tsx:87-88`, `:390-398`) since
[FIX-395](20260829-0338-FIX-395.md). [ISS-561](20260829-0208-ISS-561.md) is resolved.

## Actual

`TestingLibraryElementError: Unable to find an accessible element with the role "button". There are no accessible roles.`, with the
searched DOM being only the title div, at `:96:21` (`getAllInBanner("button")`), about 30 ms into the case (`keyBanner` is `:94`). Under `it.fails` it reads "expected
fail" (the shipped file, run in place, is green), so the API-key copy feedback has no working regression guard. The case's fallback
`?? copyButtons[copyButtons.length - 1]` never runs, because `getAllByRole` throws on zero matches instead of returning an empty list.

## Evidence

`evidence/qa-kb-087/08-analyze-itfails-wrong-reason-probes.txt`, section S-B: marker removed gives the error above; with
`.closest("div")` replaced by `.parentElement` the file reports `Tests 2 passed (2)`.

## Fix direction

Test file only; `IntegrationsCard.tsx` is correct and stays untouched.

1. `:94`: `.closest("div")!` to `.parentElement!` (the banner container, `IntegrationsCard.tsx:382`).
2. `:72`: `it.fails(` to `it(`.

For the 4-test-writer: a source meta-lock as for QA-KB-071 (`frontend/src/app/[...view]/terminalReopenReconcileLock.meta.test.ts`): the
file must not scope `within()` to `.closest("div")` of the title element, and no `it.fails(` may remain on the case. When this closes,
append a one-line resolved note to FIX-453 and ISS-600; do not rewrite them.

## Resolution (QA-KB-087 fix, 2026-10-07)

Fixed test-only by [FIX-744](20261007-2029-FIX-744.md), as the fix direction above prescribes. `:94` now uses `.parentElement!`
(the banner container, `IntegrationsCard.tsx:382`), and `it.fails(` became `it(` on `:72`. `IntegrationsCard.tsx` is untouched.

- Marker off at HEAD: no button at `:96:21`.
