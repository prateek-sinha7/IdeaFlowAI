## What was wrong

On `/handoff/settings` (and the same card mounted inline at `/flowin-handoff`), typing three
spaces into "API key name" and clicking "Create key" minted a key whose name was the literal
three-space string. It rendered as a completely blank row in the "VelocityAI API keys" list —
every other row shows `Default`, `e2e-handoff-fixture` etc. before the token-prefix line. There
is no PATCH/PUT for `/api-keys`, so the blank name was permanent: revoking only swapped in a
"revoked" badge and left the row still nameless. Names exist so a user can tell which key to
revoke, so a nameless row is permanently unidentifiable.

Register entry: **BUG-20260828-103900-handoff-settings-r2** in `bug-hunter/ledger.md`,
3/3 in the browser.

## Root cause

Two layers, both required to explain the persisted blank name — and one general mechanism
behind both.

1. `frontend/src/components/handoff/IntegrationsCard.tsx:154` —
   `await createApiKey(token, keyName || "Default")` tested the RAW `keyName` state
   (`onChange={(e) => setKeyName(e.target.value)}`, never trimmed). `"   "` is a truthy JS
   string, so the `||` fallback never fired and the whitespace went out verbatim.
2. `backend/app/api/settings.py:77` — `ApiKeyCreateRequest.name: str = Field(default="Default",
   min_length=1, max_length=64)`. **`min_length` counts RAW characters, not trimmed content**, so
   `"   "` satisfies it, and `create_api_key` (`settings.py:229-255`) passed `payload.name`
   straight into `UserApiKey(...)` at line 237 with no `.strip()` — unlike its own sibling
   handler `upsert_github_pat` in the same file (`settings.py:126-128`), which already strips and
   422s on blank-after-strip.

That mechanism is a property of the schema pattern, not of API keys. [ISS-601](20260829-0138-ISS-601.md)
found the identical shape at `SaveUserWorkflowRequest.name`
(`backend/app/api/user_workflows.py:206`, `Field(min_length=1, max_length=120)`) — no `.strip()`
anywhere in that file, `body.name` used verbatim in the uniqueness query (`:616`), the
`WorkflowDefinition` constructor (`:682`) and the PATCH rename (`:794`). Not reachable from the
UI today only because all three frontend callers happen to trim client-side; a direct API call
would persist a nameless saved workflow the same way.

## What changed and why there

- **`backend/app/api/settings.py`, `create_api_key`** — `name = payload.name.strip() or "Default"`
  before constructing `UserApiKey`. This is the choke point: it is the sole handler that builds a
  `UserApiKey` row, so it closes the defect for the live caller AND for
  `frontend/src/store/api/settings.ts:41` (a second, currently unwired `createApiKey` hitting the
  same endpoint with the same missing-trim shape). `"Default"` — not a 422 — because that is the
  value the schema already declares as its default; a blank submission and a whitespace
  submission now land on the same name.
- **`frontend/src/components/handoff/IntegrationsCard.tsx:154`** — `keyName.trim() || "Default"`.
  One caller, two mount points (`app/handoff/settings/page.tsx:54` and
  `HandoffWorkflow.tsx:352`) share this `handleCreateKey`, so both are covered. Kept because this
  codebase guards both layers and it saves a pointless round trip; the backend line is what
  actually closes the defect.
- **`backend/app/api/user_workflows.py`** — a `field_validator("name")` on
  `SaveUserWorkflowRequest` and on `UpdateUserWorkflowRequest` that strips and raises on
  blank-after-strip (FastAPI turns that into the same 422 `user_agents.py:179-184,235-240` raises
  by hand). Put on the SCHEMA rather than in the two handlers because `body.name` is read at eight
  places across create/upsert-override/rename — validating once means the uniqueness check, the
  stored row and the 409 message all see the same normalised value. `UpdateUserWorkflowRequest.name`
  is optional, so the validator passes `None` through untouched.

No engine file, no migration, no new dependency.

## What was NOT changed

- `frontend/src/store/api/settings.ts:41` — a structurally identical `createApiKey` with the same
  missing client-side trim, but grepping every consumer of `settingsApi`/`api.settings` in
  `frontend/src` finds zero call sites. Dead/unwired today, and the backend strip covers it the
  moment it is wired up. Left alone rather than edited speculatively.
- `backend/app/api/user_agents.py` — already correct (`body.name.strip()` + 422 on blank in both
  create and update). It is the pattern the two changes above copy.
