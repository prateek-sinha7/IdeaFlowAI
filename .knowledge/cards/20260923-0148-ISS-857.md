# ISS-857

Found while writing [FIX-639](20260923-0148-FIX-639.md). Not fixed there: it is a
different writer, and QA-PS-021 did not ask for it.

## What is wrong

The two terminal-status writers treat a degraded completion differently.

- **Launch driver.** `backend/app/api/run_commands.py:3990-4001` sets
  `wr.status = "degraded"`. It also sets
  `wr.error = first_agent_error_msg or degraded_reason_msg or "degraded: agent(s) failed: …"`.
- **Revision driver.** `_drive_revision_to_queue` sees the degraded
  `pipeline_complete` at `run_commands.py:5274-5275` (`degraded_seen = True`). Its
  `_persist_terminal_status` (`:5280`) then sets only `swr.status`
  (`:5285`), `completed_at` and the shared output columns. It never sets `swr.error`,
  and `_apply_terminal_output_columns` writes no status and no error by design.

The result: a revision whose completion gate degraded it is persisted as
`degraded` with `error = NULL`. The `degraded_reason` from the event is lost from
the row. The event itself still sits in `run_events`.

## Why it matters

- FIX-639's seed flag reads `WorkflowRun.error`. When the parent is itself a
  degraded revision, the flag says "no reason recorded" instead of the reason.
- Any surface that shows `WorkflowRun.error` for a degraded run (the run header's
  error chip, history) shows nothing for a degraded revision. For a degraded launch
  run it shows the reason.

## Direction (not applied)

Mirror the launch driver in `_drive_revision_to_queue`: capture `degraded_reason`
from the degraded `pipeline_complete`, and write it to `swr.error` in the
`"degraded"` branch of `_persist_terminal_status`. This touches app code only, with no
schema change. A test belongs next to `tests/unit/test_rest_revisions.py::test_driver_degraded_completion_records_degraded`
(`:403`), which already drives a degraded revision completion and asserts only
`row.status`.
