# FIX-611

**Register source:** `QA-PS-025` in root `LEDGER.md` / `BUGS.md`.

## What was wrong

A worker agent placed downstream of a planner agent in the custom composer ran
as `single_shot` with no task context and answered *"I'm ready to help. What
would you like me to do?"*. The composer offered exactly one connector lever —
"Fan out over a list" — and that lever could only ever author `fanout_batch` or
`wave_scheduler`, never `task_loop`, the strategy the native `prototype`
manifest gives `prototype-build`
(`backend/agents/workflows/prototype/workflow.yaml:68-76`).

## Root cause

The same two-value restriction was hand-written **three** times, in three files
that do not share a type, plus a fourth gap on the launch path:

- `frontend/src/components/workflow/AgentsPopup.tsx:1397` —
  `strategy?: "fanout_batch" | "wave_scheduler";`, the Simple view's
  `StepSelection` ([ISS-705](20260922-1050-ISS-705.md)).
- `frontend/src/components/workflow/composer/CanvasConfigRail.tsx:1258-1327` —
  the Canvas node-graph view's own JSX: `onToggle` writes
  `strategy: "fanout_batch"`, and the mode `<select>` offered two `<option>`s
  ([ISS-765](20260922-1428-ISS-765.md)).
- `frontend/src/store/api/userWorkflows.ts:21` and `:793` — a third,
  independently declared `StepSelectionWire`, and a
  `manifestStepsToGateSelections` leaf branch gated on the two literal strings,
  so a saved `task_loop` step reopened with no strategy and no `task_source`
  ([ISS-760](20260922-1423-ISS-760.md)).
- `IdeaInputPage.tsx` / `composer/ComposerPage.tsx` —
  [FIX-111](20260724-FIX-111.md)'s targeted injection of
  `"prototype-build": {strategy: "task_loop"}` no longer existed in either of
  today's two launch paths ([ISS-766](20260922-1429-ISS-766.md)).

Nothing was wrong below the frontend. `task_loop` is registered
`user_allowed=True` (`backend/agents/capabilities/strategies/task_loop.py:126-130`),
`_synthesize_step` emits any string strategy verbatim
(`backend/agents/workflows/selections.py:106-107`), and the
`_apply_selections` overlay is generic — the value simply never arrived.

## What changed and why there

All four edits sit at the point every caller already routes through, so no
sibling surface is left behind:

1. **`AgentsPopup.tsx`** — `StepSelection.strategy` gains `| "task_loop"` (the
   one type both composer views and the shared `applyLeverPatch` reducer read),
   `fanoutOn` now also derives from `loopOn` so a saved `task_loop` step renders
   its lever ON, and the mode `<select>` gained a third option, *"One at a time —
   shared file"*. Its `onChange` now assigns `strategy: mode` instead of a
   two-way ternary; the parser/`fanout`/`on_conflict` branches are untouched, so
   `task_loop` gets `heading_tasks` and no wave-only keys — the exact shape the
   native manifest declares.
2. **`CanvasConfigRail.tsx`** — the same three changes in the Canvas view's own
   hand-written lever. It keeps using the shared `StepSelection` type and the
   shared `PARSER_TARGET`/`KNOWN_PRODUCERS` tables; only the mode is widened.
3. **`userWorkflows.ts`** — the wire type and the leaf reverse-mapping branch
   both recognise `task_loop`, so a saved step round-trips. The SAVE side needed
   no change: `agentToManifestStep`'s leaf branch (`:378-380`) already writes
   `step.strategy = selStrategy` for any value.
4. **`IdeaInputPage.tsx` + `ComposerPage.tsx`** — FIX-111's rule is back, as ONE
   exported helper `withPrototypeTaskLoop(selections, agents, deliverableName)`
   that both launch paths call, next to the `resolveDispatchType` the two
   already share ("INV-12 — single source, no duplication"). It fills a gap
   only: an explicit composer selection for `prototype-build` always wins, and
   it fires only for the agent set that already resolves to the `prototype.html`
   deliverable.

## Known limits (deliberate)

- `agentToManifestStep`'s PARENT branch (`userWorkflows.ts:350`,
  `selFanout === "fanout_batch" || "wave_scheduler"` -> `subagents.mode`) was
  left alone on purpose: `task_loop` is a LEAF strategy that spawns its own
  per-task sub-agents and carries no `subagents` block in the native manifest,
  so treating it as a parent fan-out mode would be wrong. Selecting `task_loop`
  on a composer node that has children is therefore still dropped on save.
- The `task_source` written for `task_loop` carries no `target`, so
  `heading_tasks` parses the planner's reply — the path ISS-705's live run
  `3ba6bf05-430e-4d0e-bdcf-d3eadf3da756` already proved parses correctly. The
  native manifest additionally names `target: tasks.md` as a sandbox preference.
