## What is suspected

[ISS-345](20260828-1900-ISS-345.md) root-caused the reported single-file symptom: the chip
remove button (`WorkflowView.tsx:388`) only does
`setAttachedFiles((prev) => prev.filter((_, i) => i !== idx))` and never touches `ideaInput`,
so the `[Attached: <filename>]` marker the attach handler wrote survives removal.

Reading the attach handler (`WorkflowView.tsx:330-343`) further shows the marker construction
itself is not one-string-per-session — it is one-or-more blocks depending on HOW files were
attached:

```ts
const newFiles = Array.from(files).map((f) => ({ name: f.name, size: ... }));
setAttachedFiles((prev) => [...prev, ...newFiles]);
const fileNames = newFiles.map((f) => f.name).join(", ");          // line 339
setIdeaInput((prev) => prev
  ? `${prev}\n\n[Attached: ${fileNames}]`
  : `[Attached: ${fileNames}]`);                                    // line 340
```

- A single multi-select (the `<input type="file" multiple>` at line 326-327) joins every
  filename from that ONE `onChange` event into ONE marker: `[Attached: a.txt, b.txt]`.
- A SECOND, separate attach action (re-opening the picker) appends a brand-new
  `\n\n[Attached: ...]` block regardless of whether a marker already exists — the ternary at
  line 340 only checks whether `prev` (the whole textarea) is non-empty, not whether it already
  contains a marker. Two separate attach events therefore produce TWO independent marker blocks
  in the same textarea.

The remove handler (line 388) is unconditional on file count: it filters `attachedFiles` by
index only, in every case, however the marker text was built.

## Condition

Either of:
1. Attach 2 files in one multi-select, then remove only ONE of the two resulting chips.
2. Attach one file, attach a second file in a SEPARATE picker invocation (two marker blocks
   now present), then remove either one chip.

## Expected vs actual

**Expected:** after a partial removal, `ideaInput`/`textarea.value` should reflect exactly the
files still attached — the marker for a removed file gone, the marker for a file that is still
attached intact and unchanged.

**Actual (INFERRED — reasoned from the code above, not independently re-driven through the
browser this session; the validated repro in ISS-345 used exactly one file per cycle):**
- Case 1: removing one chip from a joined `[Attached: a.txt, b.txt]` marker leaves the FULL
  joined string untouched — it still claims a.txt is attached (false) and does not name only
  b.txt (misleading either way).
- Case 2: removing either chip leaves BOTH separate blocks untouched — the marker for the
  removed file becomes indistinguishable, in the DOM, from the marker for the file that is
  genuinely still attached.

## Why the root cause implies this — and what it changes about the fix

This is not "the same bug reproduces again with more files" — it changes what a CORRECT fix has
to do. A naive fix that reacts to ISS-345 by having remove blank out "the" marker text (e.g.
strip everything matching `/\[Attached:.*\]/` or clear from the last `\n\n[Attached:` onward)
would, under Case 1 or Case 2 with one file still attached, also destroy the reference to the
file that was NOT removed — trading one bug for another. The fix belongs where [ISS-345](20260828-1900-ISS-345.md)
already locates it (the remove handler, keyed to whichever attach-time marker(s) contain the
removed filename specifically), not as a blanket clear — this card exists so that constraint is
recorded before the fix is written, not discovered after.

**Marked INFERRED**: the three code facts cited (multi-select join at line 339, unconditional
per-event append at line 340, index-only filter at line 388) were read directly and are
CONFIRMED. The resulting DOM string for N>1 files is INFERRED — reasoned from that code, not
independently re-driven through the browser this session. What would settle it: attach 2 files
via one multi-select, remove one chip, read `textarea.value` directly (settles Case 1);
separately, attach one file, reopen the picker and attach a second, remove one chip, read
`textarea.value` (settles Case 2 — expect two distinct `[Attached: ...]` blocks, only one of
which corresponds to a still-attached file).
