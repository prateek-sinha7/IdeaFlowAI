# FIX-769

Resolves [ISS-1118](20261008-1444-ISS-1118.md) (QA-KB-103, root) and its sibling [ISS-1129](20261008-2134-ISS-1129.md)
(the doors that compile an override row outside the shared function). It does NOT resolve
[ISS-1128](20261008-2134-ISS-1128.md) (a library- or hand-rolled-seeded save still stores a degraded plan; client-side, open) or
[ISS-1130](20261008-2134-ISS-1130.md) (inline Run once of an edited built-in; needs a decision, deliberately left refused).
It refines the second locked constraint of [FIX-766](20261008-1444-FIX-766.md), which Case 3 and the trigger did not literally meet.

## What was wrong

"Save as my version" on the canvas of `app_builder`, `prototype`, `prototype_feature_revision`, `prototype_large_revision` and
`prototype_revision` answered 422 `invalid workflow override (...): capability ('compaction', 'html_skeleton') is not user-allowed`
(or `('post_step', 'api_prefix_audit' | 'revision_validation')`) whenever the roster was plan-seeded, which an unchanged save is.

## Root cause

- `compile_override_steps` (`backend/agents/execution_engine/overrides.py:50-71` before this change) compiled the posted steps
  alone and ended `return WorkflowCompiler().compile(parsed, registry, trust="user")`. It never looked at the built-in the row
  overrides, so the built-in's OWN references counted as user-authored, and `_check_trust` (`compiler.py:488-512`) refused
  every one registered without `user_allowed` (`html_skeleton`, `api_prefix_audit`, `revision_validation`).
- The canvas returns those references unchanged on purpose: `agentToManifestStep` spreads `agent.extra` and `agent.tools`
  (`frontend/src/store/api/userWorkflows.ts:301-306`, `:336-337`), the lossless round trip of `00b61ff93`.
- Case 3 (`backend/app/api/run_commands.py:3367-3407`) and the route trigger (`backend/agents/execution_engine/kernel_services.py:1616-1645`)
  compiled an override row's whole manifest at `trust="user"` themselves, and both resume recompiles
  (`backend/agents/execution_engine/engine.py`, `resume_run` and `_replay_clarify_run`) recompile Case 3's persisted manifest at
  its `_trust`. A fix confined to `compile_override_steps` would have left all three refusing a row the writers accept
  ([ISS-1129](20261008-2134-ISS-1129.md)).

## What changed, and why there

One decision, in the module every override compile already belonged to (card seam option "strip, compare and re-attach inside
`overrides.py`", so `_check_trust` stays the single place any refusal comes from and `agents/workflows/compiler.py` is untouched):

1. `overrides.py`: `_split_inherited(overrides, steps)` deep-copies the steps and takes off a `compaction` / `post_step` value iff
   the step with the same `agent` id in `compile_for_run(overrides)` (the target's file plan; aliases resolve; nested
   `subagents.steps` share the namespace) declares the identical name. `compile_with_baseline(manifest, registry, *, trust, overrides)`
   compiles what is left at `trust` and puts each taken-off value back on its compiled `Step` with `dataclasses.replace` (the
   lru_cached plan is never touched). `overrides=None` is a plain compile. The baseline is loaded only when a step carries one of
   the two keys; `FileNotFoundError` (a pipeline type with no manifest) means nothing is inherited. `compile_override_steps` now
   returns `compile_with_baseline(parsed, registry, trust="user", overrides=workflow_id)`, so the four writers
   (`user_workflows.py` `_compile_check_override_steps`) and the merge (`merge_override_steps`) need no edit.
2. `run_commands.py` Case 3: compiles through `compile_with_baseline` with `overrides = None if _inline else row.overrides_pipeline_type`,
   and persists `_overrides` beside `_trust` (only when set) so the resume recompile makes the same decision.
3. `kernel_services.py` trigger: the same call with `overrides=row.overrides_pipeline_type`.
4. `engine.py` `resume_run` and `_replay_clarify_run`: pop `_overrides` with `_trust` and pass it. A manifest persisted before this
   change has no `_overrides` and compiles exactly as before.

Unchanged on purpose: grants are never inherited, so the spawn trio (`sample_fanout`, `sample_subagents_parallel`, `sample_wave`)
stays refused (the user-trust cap would zero the grant anyway); inline launches get no baseline ([ISS-1130](20261008-2134-ISS-1130.md));
no client strip ([ISS-1118](20261008-1444-ISS-1118.md) "Where the fix belongs" 4); `_TRUSTED_SOURCES`, `_compile_check_manifest`
and every registry `user_allowed` flag ([ADR-0039](20260904-1424-ADR-0039.md)) untouched.

Known ceiling (`ponytail:` comment in `_split_inherited`): the match is on the raw `agent` id, so a `custom-agent` step (compiled as
`custom-agent:<instance_id>`) never inherits. No built-in declares either key on one: the only file declarations are
`app_builder/workflow.yaml:66`, `prototype/workflow.yaml:82`, `prototype_feature_revision/workflow.yaml:63-64`,
`prototype_large_revision/workflow.yaml:53-54` and `prototype_revision/workflow.yaml:56`, all on built-in agents. Map the
`instance_id` identity when a built-in first does.

Another stored value of the same reference stays refused: if a built-in later changes its own `compaction`/`post_step`, an override
saved earlier no longer equals the baseline and the merge falls back to the file plan with a warning (the known-open
[ADR-0033](20260825-2115-ADR-0033.md) display mismatch the card names; not changed here).
