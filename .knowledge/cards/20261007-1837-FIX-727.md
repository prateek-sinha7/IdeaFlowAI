# FIX-727

## What was wrong

This fix is for bug report QA-KB-064. The root cause comes from the 2026-10-02 analysis on
[ISS-678](20260917-1449-ISS-678.md) and was not re-derived here. Every cited line was re-read before editing.

`RunSandbox.has_git` is set by the caller and never checked against the disk. `__init__` defaults it to `True` and
stores it unchanged (`sandbox.py:564`, `:614`), and no API construction site passes it. Before this fix,
`RunSandbox.list_tags` trusted the flag alone. On a sandbox with no `.git` it did two things:

- It built the workspace. `_ws()` calls `ensure()` (`sandbox.py:634`), which mkdirs a TTL-swept sandbox and re-points
  `.latest`. That is [ISS-996](20261002-0500-ISS-996.md): the Files tab loses "Workspace expired".
- It ran `git tag --list`. That cannot succeed under FIX-522's ceiling (`local.py:375-384`), and the failure was
  swallowed into `[]` (`local.py:907-912`).

Every version path goes through `list_tags`:

- `GET /sandbox/refs` (`run_files.py:906-908`).
- `_validate_ref` (`run_files.py:872-874`). It gates `/sandbox`, `/sandbox/zip` and `/sandbox/file` (`:949`, `:1056`,
  `:1166`) and the Figma export (`run_figma_export.py:751`).
- The restore gate `_validate_tag_for_restore` (`runs.py:2392-2412`, called at `:2527`).

The restore endpoint never raised `CalledProcessError`, because its tag gate answers 400 first. That is ISS-678's
correction 3.

## What changed, and why there

**`backend/app/agents/sandbox.py:935-939`.** `list_tags` now returns `[]` when `has_git` is false **or**
`(self.root / ".git")` does not exist, before `_ws()` is built. The docstring now says the same. Nothing else in
production code changed.

### Why not the analysis's suggested location

ISS-678's analysis suggested a `RunSandbox.for_existing(...)` constructor that derives the flag from disk, used "at
exactly the five sites" (`run_files.py:905, :940, :1043, :1155`; `runs.py:2511`). This fix uses the other option the
card's own Disposition names instead: "check it at the delegation seam". There are three reasons, and each was
checked:

1. **The card's own red test cannot pass with `for_existing`.** `test_restore_tag_gate_spawns_no_git_without_dot_git`
   builds the sandbox with the bare `RunSandbox(...)` constructor, the way the restore endpoint builds it today. It
   then calls `_validate_tag_for_restore` directly, which encodes the analysis's "implementation-agnostic" test note.
   A helper used only at the call sites leaves that sandbox at `has_git=True`, so the test would stay red. With the
   guard in `list_tags`, both tests in the file XPASS.
2. **The blast radius has moved since 2026-10-02.** The analysis listed `run_figma_export.py:744` as a site that never
   reaches git. It now calls `_validate_ref` (ISS-974, `:751`), so a sixth API site reaches `list_tags`. A helper
   applied at five sites would have missed it. A guard in the shared function covers every caller, including future
   ones.
3. **The guard keeps every constraint the analysis set:**
   - `__init__` and its default are unchanged, so the engine's `git_init_sandbox` and the INV-3 goldens are
     unaffected.
   - `commit_all` and `materialize_tree_at_ref` still raise, so the FIX-522 guard stays green.
   - `ReadOnlySandbox`'s flag is untouched, so legacy `list_prefix` reads still work (the trap in ISS-992).
   - No `engine.py` edit and no new import.

**What `for_existing` would have done that this does not:** an API-built sandbox's `has_git` attribute still reads
`True` when there is no `.git`. Nothing at those sites reads it on that path:

- `list_files` and `path_for` are not gated on the flag.
- Every git-backed call at those sites sits behind the `list_tags` gate, which now answers `[]`, so the route answers
  400. Those calls are `list_files_at_ref`, `file_sizes_at_ref`, `read_file_at_ref`, `archive_at_ref`,
  `detect_persistent_git_state`, `materialize_tree_at_ref` and `commit_in_sandbox`.

If a future API path reaches a `has_git`-gated call without going through the tag gate, derive the flag at that point.

### Callers whose behaviour changed

Each caller returns the same value as before. Only the side effects are gone.

- The refs feed and `_validate_ref` in `run_files.py` (four routes), and the Figma export's `?ref`: no git subprocess,
  no mkdir.
- The restore gate in `runs.py`: no git subprocess.
- The chain exact-ref check (`sandbox.py:1964`). `ReadOnlySandbox.list_tags` (`sandbox.py:1817-1822`) delegates here,
  so on a legacy or swept source the check now returns `[]` with no git call and no mkdir. That closes one of the three
  re-creation paths in [ISS-992](20261002-0458-ISS-992.md) Part 1. `list_prefix` and `resolve_ref_commit` still
  re-create a missing source root, so ISS-992 stays open.
- The engine finalizer's tag numbering (`engine.py:2712-2714`). On a run whose git init failed, it gets `[]` with no
  git call, the same value as before.

## Deliberately not done

- **`RunSandbox.for_existing`** was not added. See above.
- **[ISS-997](20261002-0500-ISS-997.md)** stays open and untouched. It is the case where a failed git init leaves
  `has_git=True` and step commits come back `blocked` / `staging_failed`. Its mechanism is in
  `RunSandbox.git_init_sandbox`, it has no red test, and its card names a product decision: should a run that could
  not be versioned end `completed` or `degraded`?
- **[ISS-992](20261002-0458-ISS-992.md)** stays open, as above. Its card asks for a real-disk legacy test before
  anything changes near `ReadOnlySandbox`'s flag. This fix did not change the flag.

- **One existing test no longer reaches the code it targets:**
  `test_phase4_tagging.py::TestRunSandboxTagDelegation::test_list_tags_returns_empty_on_workspace_error`.

    exercises the `except` branch.
  - It was not edited, because no card asks for that. Adding `(tmp_path / ".git").mkdir()` to it would restore its
    reach. Filed as [ISS-1056](20261007-1840-ISS-1056.md).
