# ISS-218

## Description

On a FAILED run's detail page (`/runs/{id}`), the "Resume options" panel's secondary
button, "Edit brief & run again," is expected — by its own label — to open the composer
with the run's original brief pre-filled so the user can make a targeted edit and
resubmit. It instead performs a client-side route change to a brand-new, completely
empty composer at `/create/<type>` (observed as `/create/ppt_v2`), with no query
parameter referencing the source run and no brief text carried across. The user's only
recourse is to manually copy the brief from the run detail page before clicking.

Corresponds to register entry **BUG-20260828-015500-runs-failed** in
`bug-hunter/ledger.md`.

## Reproduction (3/3, cycle 1)

Reproduced on every one of 3 cold-start attempts, no variance needed:

1. Sign in as qa-admin (existing session), navigate directly (fresh page load, not a
   soft nav) to a FAILED `ppt_v2` run detail: `/runs/72e2f445-2149-4623-b39b-f85d42f24f6a`
   (seeded failed run, brief: "Create a pitch deck to propose a bespoke facebook for a
   client...", confirmed via `GET /api/runs/{id}`).
2. In the "Resume options" panel, click the button with `data-testid=chat-relaunch-secondary`
   ("Edit brief & run again").
3. Observe: `location.href` becomes exactly `http://localhost:3000/create/ppt_v2` — no
   `?from=`/`?runId=`/`?brief=` or any other query string. `document.querySelector('textarea').value`
   is the empty string `""`.
4. Repeated the full cold navigate -> click -> inspect cycle two more times (each a fresh
   `page.goto` to the run URL, not a re-click on the same loaded page); identical result
   all 3 times.

No axis needed varying — the defect is unconditional given a FAILED run and this button.

## Expected vs Actual

- **Expected:** clicking "Edit brief & run again" opens the composer with the failed
  run's original brief text pre-filled in the textarea (ideally the same
  template/config too), so the user edits and resubmits.
- **Actual:** the composer opens completely blank, indistinguishable from a fresh "New
  presentation" flow, with the original brief discarded and no reference back to the
  source run.

## Root cause

`frontend/src/components/layout/DashboardLayout.tsx:2151` — `handleEditBrief`:

```ts
const handleEditBrief = useCallback(() => {
  if (!isPipelineRunning && onResetPipeline) onResetPipeline();
  setResumeError(null);
  setQuestionnaireQuestions([]);
  setMainView("input");
  router.push(createRouteForType(effectiveReviseType));
}, [isPipelineRunning, onResetPipeline, effectiveReviseType, router]);
```

`createRouteForType(effectiveReviseType)` builds a bare route (e.g. `/create/ppt_v2`)
with no query parameter, and nothing here seeds the target composer's brief/textarea
state (no `?brief=`/`?from=` query param, no sessionStorage/localStorage handoff, no
prefill fetch on the composer side keyed by a source run id). `RunChatLane.tsx:1828`
wires the button (`data-testid="chat-relaunch-secondary"`) straight to this
`onEditBrief` prop:

```ts
onClick={() => (onEditBrief ?? onRelaunch)?.()}
```

so the click path is a pure route change with zero payload — matching what was observed
in the network log (no brief-fetch/prefill request fires).

This is a distinct defect from [FIX-125](20260727-1557-FIX-125.md), which fixed the
secondary button calling the SAME handler as the primary "Reopen & fix" button (both
resumed instead of navigating) and added the separate `onEditBrief` prop/`handleEditBrief`
routing seen above. FIX-125 made the button navigate to the input view at all — it never
addressed carrying the brief text across that navigation, which is this issue.
