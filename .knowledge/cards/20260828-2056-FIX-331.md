# FIX-331

## What was wrong

On a FAILED run's detail page the "Resume options" panel's secondary button,
"Edit brief & run again" (`data-testid="chat-relaunch-secondary"`,
`frontend/src/components/chat/RunChatLane.tsx:1828`), opened a brand-new,
completely blank composer. The run's own brief — the whole point of an "edit
the brief" action — was discarded, so the only way to edit it was to retype it.

Register entry **BUG-20260828-015500-runs-failed** in `bug-hunter/ledger.md`.

## Root cause

`handleEditBrief`, `frontend/src/components/layout/DashboardLayout.tsx:2162`:

```ts
const handleEditBrief = useCallback(() => {
  if (!isPipelineRunning && onResetPipeline) onResetPipeline();
  setResumeError(null);
  setQuestionnaireQuestions([]);
  setMainView("input");
  router.push(createRouteForType(effectiveReviseType));
}, [isPipelineRunning, onResetPipeline, effectiveReviseType, router]);
```

A bare client-side route change with **zero payload**: no query parameter, no
storage hand-off, no prefill fetch. Whatever the destination composer's own
prefill slot already held is what surfaced — nothing (blank,
[ISS-218](20260828-1700-ISS-218.md)) or a stale value from an earlier
navigation ([ISS-235](20260828-1830-ISS-235.md)). Its own preceding comment
(`:2155-2156`) already claimed it "Pre-fills the brief from submittedBrief when
available"; the body never referenced `submittedBrief`.

### Correction to the issue cards' proposed fix

Both cards named `pendingHomeBrief` -> `IdeaInputPage`'s `initialInput`
(`DashboardLayout.tsx:2871`) as "the composer's only textarea-seeding
mechanism" on this path. **That is wrong for the reproduced case, and the
one-line fix they proposed is a no-op there** — verified live, not inferred:
applying `setPendingHomeBrief(viewedRun?.input || submittedBrief)` alone left
both tests red with `textarea == ''`, and a console probe showed the state
being set correctly and never reaching a textarea.

`createRouteForType` has **two** possible destinations, and the reported one is
not `IdeaInputPage`:

- `ppt` / `ppt_v2` / `prototype` -> `/create/{type}` is matched by
  `wizardModeFor` (`frontend/src/app/[...view]/page.tsx:301-316`) and returns
  `<LaunchWizard initialMode={...} />` at `page.tsx:3773-3775` — an early
  return **above** `DashboardLayout`, which therefore unmounts. `IdeaInputPage`
  and `pendingHomeBrief` are not on screen at all. The reported run is
  `ppt_v2`, so this is the path the bug was filed against.
- every other type stays inside `DashboardLayout`'s `mainView === "input"`,
  where `IdeaInputPage`'s `initialInput` does read `pendingHomeBrief`.

The cards' *fix location* (`handleEditBrief`) and *diagnosis* (nothing is
carried across the navigation) both hold — only the seeding channel was
misidentified.

## What changed and why there

One function, `frontend/src/components/layout/DashboardLayout.tsx:2162-2190`.
It seeds the brief for **both** destinations before pushing, so the fix covers
the reported `ppt_v2` path and every sibling type the same button reaches:

```ts
const editedBrief =
  recentRuns?.find((r) => r.id === contentSourceRunId)?.input || submittedBrief || "";
setPendingHomeBrief(editedBrief || undefined);
const reviseBase = baseWorkflowType(effectiveReviseType);
if (selectWorkflowWizardPath(reviseBase)) {
  sessionStorage.setItem(
    reviseBase === "prototype" ? "prototype.draft" : "ppt.draft",
    JSON.stringify({ brief: editedBrief }),
  );
}
```

- The wizard branch reuses the app's own existing hand-off: LaunchWizard
  restores `prototype.draft` / `ppt.draft` and clears it in the same effect
  (`frontend/src/components/workflow/LaunchWizard.tsx:277-322`, one-shot per
  FIX-005), which is the same channel `handleLaunchSaved` writes at
  `DashboardLayout.tsx:1542` / `:1569`. Key derivation mirrors the wizard's own
  (`initialMode === "prototype" ? … : "ppt.draft"` — `ppt_v2` shares `ppt`'s).
  Deliberately NOT the `chain.*` keys: those flip the wizard into chaining mode
  (`isChaining`, the "Continuing from your …" banner), and this is a fresh run.
- `pendingHomeBrief` is set unconditionally, as
  [ISS-235](20260828-1830-ISS-235.md) asks, so any stale value in that slot is
  overwritten rather than inherited.
- Source is `viewedRun.input || submittedBrief`, the same expression
  `runHeaderTitleFull` uses at `:2409`, inlined rather than referencing
  `viewedRun` (declared 200 lines below — naming it in the dependency array
  would be a TDZ `ReferenceError` at render time).

No URL change, so ADR-0018 (routes.ts owns every URL) is untouched; no backend,
migration or capability surface involved.
