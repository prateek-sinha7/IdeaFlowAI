# FIX-620

Resolves [ISS-741](20260922-1207-ISS-741.md) (root) and
[ISS-786](20260922-1810-ISS-786.md) (sibling), both from
[QA-SG-003](../../BUGS.md#qa-sg-003) — "Back button navigation loops between
run detail and run history pages".

## What was wrong

A control labelled "Back" that calls `router.push(<fixed route>)` does not go
back: it leaves the screen being left on the history stack and adds a second
copy of the destination on top. The next Back — the browser's own, or a
correctly implemented in-app one on the destination — then walks straight back
into the screen the user was trying to leave.

`frontend/src/components/layout/DashboardLayout.tsx` (pre-change, at the sole
`<RunChatLane>` mount):

```tsx
onBackToHistory={() => {
  setMainView("history");
  router.push(routes.runHistory());
}}
```

Opening a run from `/runs` already pushed `/runs/{id}`
(`DashboardLayout.tsx` `onOpenRun`), so this made the stack
`[…, /runs, /runs/{id}, /runs]`. Run History's own Back arrow is correct —
`handleBackNav`, which has always been `window.history.length > 1 ?
router.back() : push(home)` — so it legitimately popped to the *just-repushed*
`/runs/{id}`, and the two screens oscillated with no escape through the in-app
buttons (ISS-741 reproduced it 3/3 from cold;
`evidence/qa-sg-003/03-validate-attempt1-back-button-loops-to-run-detail.png`).

The same anti-pattern existed in two "Back" controls that mount outside
`DashboardLayout` and so cannot call its private `handleBackNav`
(ISS-786):

- `frontend/src/components/workflow/LaunchWizard.tsx` —
  `onClick={() => router.push(routes.home())}`, `aria-label="Back to
  dashboard"`.
- `frontend/src/app/workflow/page.tsx` —
  `onClose={() => router.push(routes.dashboard())}`, the prop behind
  `WorkflowView.tsx:176-178`'s `handleBack` (the `aria-label="Back"` icon at
  `WorkflowView.tsx:236-238`). The unconditional push lives on the prop, not in
  `WorkflowView`, which holds no router — so that is where it is fixed, and
  `WorkflowView.tsx` itself is untouched.

ISS-786 was filed as INFERRED, not reproduced. **It reproduces.** It is live on
`/create/prototype`, not the `/workflow/create` path the card's reachability
narrative names: the Home launch card routes to `/create/prototype`, and
`frontend/src/app/[...view]/page.tsx:4034` renders
`<LaunchWizard initialMode={wizardMode} />` there — same component, same
button. Observed on the real app, both directions (see TEST COVERAGE §3 and
`evidence/qa-sg-003/12-fix-test-output.txt`).

## What changed and why there

**New — `frontend/src/lib/navigation.ts`** (24 lines, one export):

```ts
export function goBackOr(router: { back: () => void }, fallback: () => void): void {
  if (typeof window !== "undefined" && window.history.length > 1) {
    router.back();
    return;
  }
  fallback();
}
```

This is the guard `handleBackNav` already carried, lifted to one place, exactly
as ISS-786 prescribes ("the guard belongs in one small shared helper … so
ISS-741's fix and this one land in the same place instead of three
independently-maintained copies"). It takes only `{ back }` — the fallback does
its own navigation, which is what lets the two `DashboardLayout` handlers keep
their `setMainView(...)` in the no-history branch without the helper knowing
anything about views.

Five call sites now route through it; no other behaviour changed at any of
them:

- **`DashboardLayout.tsx:3251`** (`onBackToHistory`, ISS-741 — the bug) —
  `goBackOr(router, () => { setMainView("history"); router.push(routes.runHistory()); })`.
  `setMainView` stays only on the fallback: when the pop happens, the
  `initialMainView` re-sync effect (`DashboardLayout.tsx:576-579`) picks the view
  up from the new URL, which is precisely how `handleBackNav` has always behaved.
- **`DashboardLayout.tsx:1828`** (`handleBackNav`) and **`:1808`**
  (`commitBackNav`, its unsaved-changes twin) — the two verbatim copies of the
  guard, replaced by the call. Semantics identical; this is what stops the
  helper from being a fourth copy.
- **`LaunchWizard.tsx:1042`** — `goBackOr(router, () => router.push(routes.home()))`.
- **`app/workflow/page.tsx:103`** —
  `goBackOr(router, () => router.push(routes.dashboard()))`.

## What is deliberately NOT changed

- **`WorkflowView.tsx` is untouched.** Adding `useRouter` to it would put a
  `next/navigation` dependency into a component whose two unit test files
  (`WorkflowView.attachmentRemove.test.tsx`, `WorkflowView.zeroAgents.test.tsx`)
  render it with no router mock, and there is no global mock in
  `frontend/vitest.setup.ts`. The push it ends in is on the prop, so the prop is
  where it is guarded.
- `app/workflow/page.tsx`'s `onClose` is also `handleRunAnother`'s exit
  (`WorkflowView.tsx:191`). It now pops rather than pushing a duplicate
  `/dashboard` — same intent (return whence you came), and it can no longer
  leave `/workflow` on the stack either.
- `LaneRunHeader.tsx:299-305`'s default `window.history.back()` was already
  correct and is untouched; it is overridden by the (now fixed) DashboardLayout
  prop on every real run-detail render.
- The nine other `router.push(routes.*)` calls in `DashboardLayout` are forward
  navigations, not "Back" controls. Out of scope for both cards.

## The ISS-786 test is broken — it was NOT edited

`tests/integration/e2e/suites/03_launch_panels/test_iss786_launch_wizard_back_loop.py`
fails upstream of its assertion, so it can neither confirm nor refute this fix.
Two defects, both in the test:

1. `page.get_by_role("button", name="Build an interactive prototype")` — Playwright
   matches the accessible name by *substring* by default, so on `/dashboard` it
   resolves to 6 elements (the launch card, its "Inspect …" button, two sibling
   prototype cards and two recent-run cards) and raises a strict-mode violation.
   The repo's own browser brief documents this class of trap ("+ Add" and
   "Workflow actions" repeat per card, so scope with clickNear).
2. It waits for `"/workflow/create" in url`, but that Home card navigates to
   `/create/prototype` (`app/[...view]/page.tsx:4034` renders `LaunchWizard`
   there). Observed: `TimeoutError … navigated to
   "http://localhost:3000/create/prototype"`.

A working version differs from the card's file in three strings — the launch-card
locator and the two route literals — with the assertion byte-identical:

```python
page.get_by_role("heading", name="Build an interactive prototype", exact=True).click()
page.wait_for_url(lambda url: "/create/prototype" in url)
...
assert "/create/prototype" not in page.url
```

That version PASSES with this fix and FAILS with `LaunchWizard.tsx:1042`
reverted. The repair is the 6-verifier's call, not this agent's: a 5-fixer does
not edit a test.
