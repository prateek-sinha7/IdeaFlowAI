# ISS-908

Found while verifying the QA-KB-024 fix ([FIX-693](20261001-2204-FIX-693.md)). That fix did not cause it: the pre-fix tree fails
the same way.

## Condition

- `backend/tests/agents/test_wave_scheduler_cancel_row.py:40`, the fake runner:
  `async def run_fanout(self, requests, ctx, *, step=None):`
- `backend/agents/capabilities/strategies/_fanout_wave_stream.py:71-73` calls it with a fourth keyword:
  `runner.run_fanout(requests, ctx, step=step, event_queue=child_events)`. The real
  `KernelServices.run_fanout` accepts `event_queue` (`backend/agents/execution_engine/kernel_services.py:1161-1167`).
- `git log -S "event_queue=child_events" -- backend/agents/capabilities/strategies/_fanout_wave_stream.py` returns
  `1e329e47b`. The test was last touched in `3e0c40f14` (2026-09-23). Both files are clean against HEAD `024c03ef8`,
  so this is committed drift, not an in-flight edit.

## Effect

`test_cancelled_error_mid_wave_marks_row_terminal` fails with
`TypeError: _CancelMidWaveRunner.run_fanout() got an unexpected keyword argument 'event_queue'`, raised at
`_fanout_wave_stream.py:71`, before the `asyncio.CancelledError` the test injects. The guard for
[ISS-098](20260812-1153-ISS-098.md) (a Stop during a wave must flip the in-flight `wave_runs` row terminal) therefore
exercises nothing. This card does not establish whether the product path still holds.

## Evidence

- `.venv/bin/python -m pytest tests/agents/test_wave_scheduler_cancel_row.py -q -p no:cacheprovider`, run alone from
  `backend/`: `1 failed` on the live tree, and `1 failed` with the same `TypeError` on a pre-fix copy (the five
  QA-KB-024 files restored from their pre-edit snapshot).

## Fix (proposed, not applied)

Test-only: give the fake's `run_fanout` an `event_queue=None` keyword. It was not applied during QA-KB-024 because
the file is outside that bug's card scope.

## Analysis (5-analyzer, 2026-10-02): CONFIRMED, test-only

Checked at HEAD `024c03ef8` on `feat/user-stories-v2`. Line numbers are HEAD's. The shared working tree carries other bugs' uncommitted edits: [FIX-693](20261001-2204-FIX-693.md)'s in
`wave_scheduler.py`, `fanout_batch.py`, `engine.py` and `task_loop.py`, and a separate change in `kernel_services.py` near `:1586`. They shift a few cites (in the working tree the cancel arm reads
`wave_scheduler.py:492-503`, `fanout_batch.py:127`, `engine.py:8632`) and touch neither the cancel arm, the dispatch call, nor any line cited from `kernel_services.py`. Every probe below ran against that working tree.

### Root cause (CONFIRMED: file:line read, failure reproduced, fix hypothesis run)

One mechanism. The ISS-098 guard's hand-rolled runner pins the two-keyword shape of `run_fanout`; the wave strategy now makes a three-keyword call.

- Call: `_fanout_wave_stream.py:71-73`, `runner.run_fanout(requests, ctx, step=step, event_queue=child_events)`. Its only caller is `wave_scheduler.py:476`
  (`async for event in stream_wave_fanout(...)` inside `_dispatch_wave`, driven at `:492`).
- Fake: `test_wave_scheduler_cancel_row.py:40`, `async def run_fanout(self, requests, ctx, *, step=None):`. No `event_queue`, no `**kw`.
- Real: `kernel_services.py:1161-1168` and the kernel `fanout.py:340-346` both take `event_queue: asyncio.Queue | None = None`.
- Where the error goes: an `async def` generator binds its arguments at the call, so the `TypeError` fires at `_fanout_wave_stream.py:71` on the first `__anext__`. It is not a `CancelledError`, so the dispatch `try`
  in `wave_scheduler.py` skips the `except asyncio.CancelledError` arm (`:494-505`) and lands in `except Exception` (`:506-516`), which flips the row `failed`, yields `wave_failed` and re-raises
  (`evidence/qa-kb-080/analysis-probe-where-the-typeerror-goes.out.txt`: events `['agent_start', 'wave_started', 'wave_failed']`, flips `[('row-0', 'failed')]`).
  The test's `pytest.raises(asyncio.CancelledError)` does not match a `TypeError`, so it fails there. The `CancelledError` the fake was written to raise is never reached.
- Reproduced today: `1 failed in 1.16s`, the same `TypeError` the validator saw three times (`evidence/qa-kb-080/01..03-validate-attempt*-pytest-output.txt`).

### How it got here (CONFIRMED by git): a semantic merge conflict

- `835793a99` (2026-08-31) added the `except asyncio.CancelledError` arm ([FIX-425](20260831-1804-FIX-425.md)) and this test together. Its fake matched the call the strategy made that day,
  `runner.run_fanout(requests, ctx, step=step)`; the real handle already accepted `event_queue` (`24332e0c5`, 2026-08-14), but no wave caller passed it yet.
- `1e329e47b` (2026-09-04) created `_fanout_wave_stream.py` and routed `wave_scheduler` through it, which is what adds `event_queue=child_events`. It widened the wave fakes that existed on its own line
  (`tests/agents/test_wave_scheduler.py` and `test_subagent_runs.py`: `-async def run_fanout(self, requests, ctx, *, step=None)` became `+... step=None, event_queue=None`).
  This test did not exist there (`git cat-file -e 1e329e47b:backend/tests/agents/test_wave_scheduler_cancel_row.py` fails), and neither commit is an ancestor of the other.
- The first tree holding both halves is merge `4ebd98e8f` (2026-09-16, "Merge branch 'feat/git-versioning' into feat/file-extract-tools"): parent `66bf725ba` has the stream and no test, parent `36617b824` has the test
  and no stream. In the merged tree `test_wave_scheduler_cancel_row.py:40` reads `*, step=None` and `_fanout_wave_stream.py:72` reads `event_queue=child_events`. The two edits touch different files, so the merge was
  textually clean and each side's suite was green on its own: nothing could fail before the lines met.
- Red on this lineage since 2026-09-16, and listed at `UNIT-TESTS.md:109` (row 76, `dev` at `3e0c40f14`, 2026-09-23). [FIX-693](20261001-2204-FIX-693.md) did not cause it (its probe on the pre-fix tree fails the same way).
  The card's own pointer to `1e329e47b` names the change that made the call, not the moment the test went red.

### The product path holds (CONFIRMED; this settles the question the Effect section left open)

No source and no test file was edited; every probe changes the fake or a copy of `wave_scheduler.py` in memory (`evidence/qa-kb-080/`).

1. Under the repo's own runner (`pytest` + `pytest-asyncio`, conftest hooks) with ONLY the fake's signature widened by a throwaway plugin (`analysis_pytest_probe_plugin.py`): `1 passed`
   (`analysis-pytest-probe-plugin.out.txt`). So the `except asyncio.CancelledError` arm at `wave_scheduler.py:494-505` flips the row `cancelled` and re-raises, as [FIX-425](20260831-1804-FIX-425.md) built it, through the real `stream_wave_fanout`.
2. The same widened fake against an in-memory copy of `wave_scheduler.py` with that arm cut: `AssertionError: wave_runs row was never flipped off 'running' after a mid-wave CancelledError`
   (`analysis-probe-widened-fake-and-mutant.out.txt`). Once unblocked the guard discriminates; it is not a vacuous pass.

### Blast radius (every caller and consumer grepped)

- `stream_wave_fanout`: one caller, `wave_scheduler.py:476`.
- `runner.run_fanout(...)` call sites in `backend/agents`: `_fanout_wave_stream.py:71` and `_fanout_stream.py:32` (`parallel_group.py:132`) pass `event_queue`; `fanout_batch.py:121` and `engine.py:8624`
  (`_derive_fanout`) do not. The real handle accepts it, so no production caller is affected. No `Protocol` declares `run_fanout` (the handle is `Any` everywhere), which is why nothing statically flags a stale double.
- Test doubles: 17 `run_fanout` fakes (`analysis-run-fanout-fake-census.py`, output beside it). Ten accept the full call. Seven reject it: this one, the only red one because a FULL caller drives it, and six that only
  SHORT callers drive, green today ([ISS-1022](20261002-0638-ISS-1022.md)).
- This is the ONLY test that drives a `CancelledError` through the wave strategy: the five other files that drive `WaveSchedulerStrategy` / `ParallelGroupStrategy` contain one `CancelledError` hit, an unrelated
  docstring in `test_restart_resume_db.py:1389`. So the [FIX-425](20260831-1804-FIX-425.md) arm has had no live guard since the two lines met.
- Adjacent, same mechanism on another method of the same handle and the other half of the same Stop guard set: [ISS-1023](20261002-0638-ISS-1023.md), five red tests in `test_fanout_cancel.py` (CONFIRMED by run).
- Prose that still describes the pre-wave world: [ISS-1024](20261002-0638-ISS-1024.md).

### Where the fix belongs

- In the test: `test_wave_scheduler_cancel_row.py:40` becomes `async def run_fanout(self, requests, ctx, *, step=None, event_queue=None):`, the shape of the ten fakes that already comply and of the real handle.
  After it: `1 passed` (probe 1). Baselined today, one file at a time and unaffected by it: `tests/unit/agents/test_wave_scheduler.py` 13 passed, `test_parallel_group_strategy.py` 7 passed.
- Not in production. `stream_wave_fanout` must keep passing the queue: it is how worker events reach the wave UI, and `_stamp_queued` (`_fanout_wave_stream.py:59-68`) layers `wave_index` / `step` / `wave_total` onto them
  ([FIX-541](20260904-FIX-541.md)). Making the call tolerant of a narrow runner would add a compatibility path nothing needs, since `KernelServices` is the only runner, and `_fanout_wave_stream.py` is import-pure
  (INV-13: stdlib and typing only).
- Fix in place. The file sits in the legacy `tests/agents/` suite folder (`tests/conftest.py`: "legacy, to be removed in Batch 6"); relocating it is a separate concern.

### Do not

- Do not loosen `pytest.raises(asyncio.CancelledError)` to `Exception` or `BaseException`. With the narrow fake the `TypeError` already flips the row `failed` through the WRONG arm, so the guard's last assertion
  (`runner.updated[-1][1] in ("failed", "cancelled")`) would pass without ever testing the cancel arm.
- Optional, same edit: tighten that assertion to `== "cancelled"`, the contract [FIX-425](20260831-1804-FIX-425.md) locks (`wave_scheduler.py:504`). Not required to close this card.
- Do not mark the test `xfail` or delete it: it is the only guard of that arm.

## Resolution (QA-KB-080 fix, 2026-10-07)

Fixed by [FIX-737](20261007-1957-FIX-737.md), as the analysis above proposed: test-only, one signature line.
`test_wave_scheduler_cancel_row.py:40` is now `async def run_fanout(self, requests, ctx, *, step=None, event_queue=None):`.

- Observed: `1 failed` before (`TypeError ... 'event_queue'` at `_fanout_wave_stream.py:71`) and `1 passed` after
  (`evidence/qa-kb-080/fix-01-before-cancel-row.txt`, `fix-03-after-cancel-row.txt`). The analyzer's mutant probe, re-run on
  the fixed file, still fails the guard with its own ISS-098 message when the cancel arm is cut from an in-memory copy of
  `wave_scheduler.py` (`fix-05-mutant-probe-on-fixed-file.txt`).
- Not done, as directed: `pytest.raises(asyncio.CancelledError)` was not loosened, no `xfail` was added, and
  `stream_wave_fanout` was not touched. The optional tightening to `== "cancelled"` was not applied. The guard keeps
  [ISS-098](20260812-1153-ISS-098.md)'s "terminal" contract, as FIX-425 wrote it, and no code reads `cancelled` vs `failed`
  on a wave row (`wave_scheduler.py` reads only `completed` at `:353` and `running` at `:438`).
- Siblings: [ISS-1023](20261002-0638-ISS-1023.md) and [ISS-1024](20261002-0638-ISS-1024.md) were resolved by the same fix.
  [ISS-1022](20261002-0638-ISS-1022.md) stays open (latent fakes, plus the bind guard that would end the family).
