## Why this must also be broken

`ex_A4_human_divert` renders TWO save buttons side by side on the same unmodified page
(`frontend/src/components/workflow/IdeaInputPage.tsx:1647-1670`, confirmed read): "Save workflow"
(`handleSaveWorkflow`, line 1382-1418, triggers `setShowSaveModal(true)` at line 1648) and "Save
as my version" (`handleSaveAsOverride`, ISS-225's subject) — both visible whenever
`effectiveType !== "custom" && workflowId`, exactly the condition this bug's page satisfies.

"Save workflow" reads the SAME unseeded ref ISS-225 documented — `const selections =
selectionsRef.current` (line 1391) — but sends it differently: `selections: { ...selections,
_wizard: wizardConfig }` (lines 1408-1411), never `manifest:`. That routes through a DIFFERENT
backend check than the one ISS-225 hits:

- `handleSaveAsOverride` sends `manifest:` → `_validated_manifest` →
  `_compile_check_manifest` (`backend/app/api/user_workflows.py:78-133`, read in full) compiles
  the CLIENT-SUPPLIED manifest as-is with `trust="db"` — no server-side merge with the base
  workflow's own file-backed manifest. This is what 422s on R-03.
- "Save workflow" sends `selections:` only →
  `_compile_selections_trust_user` (`backend/app/api/user_workflows.py:349-395`, read in full).
  `_wizard` is stripped at line 367; the remaining map is empty for an untouched page, so
  `has_selections(compile_selections)` is false and the function returns at line 377-378 —
  **no manifest synthesis, no compile, no validation runs at all.** The POST succeeds (201).

So "Save workflow" does not error — but it also never captures the step's `route:`. Even
setting aside the empty-selections short-circuit: `synthesize_manifest`
(`backend/agents/workflows/selections.py:158-199`, read in full) builds every step from
scratch via `_synthesize_step(agent_id, sel)` (lines 81-155), which sets only `agent` +
`strategy` plus whatever keys are present in `_LEVER_KEYS` (lines 43-49) or the generic
verbatim-projection loop (lines 149-153) — `route` is in NEITHER set. `synthesize_manifest` has
no way to emit a `route:` block under any input, because nothing in this module knows how to
project one. (Its docstring, lines 173-178, notes the synthesized manifest is a throw-away
validation artifact, not the persisted or run manifest — so whether an eventual LAUNCH of a
"Save workflow"-created row actually loses the routing, or re-derives it by compiling
`base_pipeline_type`'s own file-backed `workflow.yaml` at run entry per `run_commands.py`'s
`USER_WORKFLOW_MANIFEST` branch, was NOT traced here and is the open question below.)

## Expected vs actual

**Expected:** "Save workflow" on an unmodified seeded conditional-gate example either captures
the declared route/gates faithfully, or refuses the save the same way "Save as my version" does
— either way, the user is not left with a silently degraded save.

**Actual (INFERRED — request/response not yet captured):** "Save workflow" reports success
(201, "Saved" confirmation per the UI's `savedConfirm` state, line 1413) while persisting
`selections: {_wizard: {...brief}}` with no per-step data at all for the routed step — no 422,
no user-visible indication that the example's branching structure was not represented in the
selections it captured.

## What would confirm or refute this

1. Reproduce: `/create/ex_A4_human_divert`, type a brief, leave Advanced untouched, click "Save
   workflow" (not "Save as my version"), name it, save. Inspect the `POST /api/user-workflows`
   request/response — confirm `selections` carries no `pick-language`/routed-step key and the
   response is `201` (would confirm the silent-success half).
2. The open question this card does NOT resolve: launch the newly-saved workflow and observe
   whether it still asks the human/routes correctly, or silently runs as a linear pipeline. That
   determines whether this is "harmless because launch recompiles the base file-backed
   manifest" or "a second, quieter data-loss bug" — trace `backend/app/api/run_commands.py`'s
   handling of a `USER_WORKFLOW_MANIFEST`-sourced row with an empty `selections` map and a
   `base_pipeline_type` that is itself a route-declaring example, to settle it without a live run.

## Where the fix belongs

If confirmed harmful at launch: the fix is upstream of both save buttons, in the same place
ISS-225 and [ISS-254](20260828-1810-ISS-254.md) point at — `selectionsRef` never carrying the
manifest's declared gates is the common defect underneath all three symptoms (loud 422, quiet
drop here, and the four other examples). If launch turns out to safely fall back to the
file-backed base manifest regardless, this card's finding narrows to "the persisted `selections`
row is misleading/incomplete," a lower-severity UX gap rather than a functional break.
