# ISS-236

**Register source:** sibling derived while analyzing `BUG-20260828-015930-runs-cancelled`
(root card [ISS-220](20260828-1712-ISS-220.md)) in `bug-hunter/ledger.md`.

## Why the root cause implies this

[ISS-220](20260828-1712-ISS-220.md)'s confirmed mechanism (see that card's analyzer-pass
section) is: `handleResumeRun` (`frontend/src/components/layout/DashboardLayout.tsx:2253`)
calls `runConnection.attachRun(run_id)` (line 2273) on a successful `postResume`, which
starts the pipeline; `DashboardLayout`'s `pipelineState?.isRunning` effect
(`DashboardLayout.tsx:735-769`) reacts by unconditionally calling
`router.push(routes.runStream(incomingRunId))` (line 768) whenever `incomingRunId` is
set — with **no** call to `onSwitchToLiveRun` / `handleSwitchToLiveRun` first, unlike the
three other `router.push(routes.runStream(...))` call sites in the same file
(`onGoToPipeline` line 2526-2536, `onSelectWorkflowRun` line 2548-2552, `onViewResults`
line 2558-2592). That push remounts `frontend/src/app/[...view]/page.tsx` (established
mechanism, [FIX-298](20260825-FIX-298.md)/`BUG-030`), which tears down and rebuilds the
page-local `useEffect` at `page.tsx:2196-2206` that is the **sole** wiring between
`RunConnectionProvider`'s SSE fan-out and this page's `pipelineState`/`runStore`. The
fan-out itself (`frontend/src/providers/RunConnectionProvider.tsx:331-339`,
`:345-350`) is a plain `subscribersRef.current.forEach(fn => fn(msg))` with **no
buffering** — any frame fanned out while the page's handler is not currently in
`subscribersRef` (the exact state during the unmount-old/mount-new transition) is lost
for good. The one compensating mechanism, the T11 `liveRunIds` fast path's durable-event
replay (`page.tsx:3285-3419`), is a **single, non-retried** `getRunEvents` REST snapshot
taken at mount time — it cannot recover an event the backend emits after that snapshot
request, which is exactly the shape of a pipeline that fails a few seconds into the
resumed run.

This entire chain is reachable from **any** caller of `handleResumeRun`, not only the
cancelled-run "Run Again" button ISS-220 reproduced. `frontend/src/components/chat/RunChatLane.tsx`
wires the identical `onRelaunch` prop (from `DashboardLayout.tsx:3012`,
`onRelaunch={handleResumeRun}`) to:

- the **cancelled** terminal card's "Run Again" button (`RunChatLane.tsx:1699,1730`) —
  the case ISS-220 already reproduced 2/3 cycles, and
- the **failed** terminal card's "Reopen & fix from the failed step" button
  (`RunChatLane.tsx:1816-1824`, `onClick={() => onRelaunch?.()}`, same `data-testid="chat-relaunch"`).

Both buttons call the exact same function with the exact same downstream effects — there
is no branch inside `handleResumeRun` (`DashboardLayout.tsx:2253-2311`) that treats a
failed-run resume differently from a cancelled-run resume; it resolves `runId` from
`lastCancelledRunId ?? pipelineState?.pipelineRunId ?? contentSourceRunId ??
activePipelineRunId` regardless of which terminal card triggered it. If the mechanism
holds for cancelled, it structurally holds for failed too.

## Expected vs actual (predicted, not yet observed)

- **Expected:** clicking "Reopen & fix from the failed step" on a failed run's detail
  page resumes the pipeline and the live `/stream` view tracks the backend's events in
  near-real-time, same as any other resume.
- **Predicted actual:** on the same class of fast backend failure ISS-220 reproduced
  (~3-5s), the live view has a timing-dependent chance of freezing on the initial
  "Running / 0/N agents / Starting…" state, recoverable only by a manual reload — the
  same shape as ISS-220, same root cause, different entry button.

## Status

**INFERRED — not reproduced.** This card is derived from the shared-code argument above,
not from an independent repro cycle. What would confirm it: repeat ISS-220's cold-start
reproduction protocol (`bug-hunter/evidence/runs-cancelled/_scratch/` style) against a
seeded **failed** (not cancelled) run whose resume fails fast, and check whether the live
`/stream` view freezes the same way.

## Fix

Belongs in the same shared seam as ISS-220's fix, not in `handleResumeRun` or either
button individually — see [ISS-220](20260828-1712-ISS-220.md) for the proposed direction
(making the T11 durable-replay recover from the subscribe gap, or eliminating the gap by
moving frame delivery above the router). A fix scoped to "the cancelled case" alone (e.g.
inside `handleResumeRun`'s cancelled branch) would leave this failed-run path — and any
future caller of the same `isRunning` effect — exposed to the identical race.
