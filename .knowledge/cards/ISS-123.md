# ISS-123

## Title

FIX-240 stops NEW losses; it cannot recover the rows already destroyed. The pre-fix defect ran for as long as the chat lane has shared the engine's seq space, and a dropped run_events row has no provenance to reconstruct from. Corpus-wide upper bound measured read-only over backend/dev.db: 29 seq-stealing app-layer rows across 10 runs (chat_message 19, concierge chat_reply 8, chat_usage 2) against 233,325 rows in 16 runs — i.e. up to 29 silently destroyed engine events. Three identified by name: questionnaire_complete in runs 808612bf and f36ab26c, one pipeline_cancelled (808612bf), and an agent_chunk in ec7fb984 (seq 3581). Consumers that silently mis-read a holed log: SSE durable replay, derive_open_gate, _reconcile_terminal_status (a dropped terminal makes a user-resume fall through to new_status="failed"), _apply_terminal_output_columns, the conversation context provider, the Concierge, and GET /runs/{id}/events. Deliberately NOT fixed: back-filling synthetic terminal rows was considered and REJECTED — fabricating durable events with no event_id provenance is worse than the hole, and it would make the log lie about what the engine actually emitted. Money is NOT exposed: the startup restore scan filters on WorkflowRun.status, which is correct, so a holed cancelled run is never re-driven.

## Source / evidence

Measured by the ISS-121 root-cause investigation (read-only SQL, mode=ro). Candidate disposition: accept as historical data loss and record it, or write a one-off read-only audit that lists affected runs so support can recognise them.
