# ISS-892

Register entry: **QA-KB-027** (`BUGS.md`). Sibling of [ISS-724](20260922-1246-ISS-724.md) (root): the same two
faults, in the one existing test file that covers the "sandbox with no git of its own" edge the bug lists as
"fresh sandbox edge case unverified". Derived from the root cause, then **CONFIRMED by running it** (2026-10-01).

## Condition

`backend/tests/unit/test_run_files_ref_family_scope.py` lives under `tests/unit/`, where the autouse
`_unit_io_guard` (`backend/tests/unit/conftest.py:90-179`) refuses a real DB connection, a subprocess and a socket
unless the test carries `allow_io`. This file has no marker and needs all three of the first two.

Observed, `backend/`, `.venv/bin/python -m pytest tests/unit/test_run_files_ref_family_scope.py`:

```
EEF  — 2 errors, 1 failed
ERROR  test_refs_is_empty_for_a_sandbox_with_no_git_of_its_own   UnitIsolationError: Unit test opened a real database connection
ERROR  test_an_enclosing_repo_tag_is_rejected                    UnitIsolationError: Unit test opened a real database connection
FAILED test_materialize_and_commit_fail_closed_without_touching_the_outer_repo
       UnitIsolationError: Unit test spawned a subprocess: ['git', '-c', 'user.name=Host', ... 'init']
```

The third test needs no database at all: `_outer_git` (`:131-136`) calls `subprocess.run(["git", ...])`, so placement
alone kills it. Behind the guard, `_seed_user` (`:93`) also passes the removed `password_hash` kwarg
(see [ISS-891](20261001-2120-ISS-891.md) and the root card).

## What the three tests guard (why this is more than test hygiene)

`LocalWorkspace` git calls used to run with only `cwd` set, so a sandbox with no `.git` of its own adopted whatever
repository enclosed `RUNS_ROOT` (QA-PS-008: the Flowin source checkout). [FIX-522](20260917-1449-FIX-522.md) set
`GIT_CEILING_DIRECTORIES=<root.parent>` in `_git_env` (`backend/app/agents/runtime/local.py:382`). The tests pin it:

1. `GET /{run_id}/sandbox/refs` on a git-less sandbox is `[]`, not the enclosing checkout's tags
   ([ISS-671](20260917-1345-ISS-671.md)).
2. `_validate_ref` rejects a tag that exists only in the enclosing repo: `GET /sandbox/file?ref=deploy-prod-leaked`
   is 400, not the host checkout's file served at its own tag ([ISS-671](20260917-1345-ISS-671.md); an
   information-disclosure shape).
3. `materialize_tree_at_ref` and `commit_all` on a git-less sandbox raise and leave the outer repo's HEAD and
   uncommitted files untouched ([ISS-672](20260917-1350-ISS-672.md): restore was committing into the host repo).

[FIX-522](20260917-1449-FIX-522.md), [ISS-671](20260917-1345-ISS-671.md) and
[ISS-672](20260917-1350-ISS-672.md) each name exactly this file as `verification.test_files` with `status: passed`
(ISS-672 is severity critical: restore was committing into the host checkout). Those three claims no longer hold
while the file cannot run, which is why this sibling is rated high rather than as test hygiene.

## Why the root cause implies this

Same two faults as [ISS-724](20260922-1246-ISS-724.md): a real in-memory SQLite engine plus real `git` in
`tests/unit/` (README rules 7 and 8, `backend/tests/README.md:74-81`, send these to `tests/integration/`), and the
stale `User(password_hash=...)` seed. The bug's "fresh sandbox edge case unverified" is partly an existing-but-dead
test, not a missing one: tests 1 and 2 are the git-less-sandbox-under-a-ref case.

## Probe — the product is fine, only the guard is dead

A scratch pytest plugin outside the repo (adds `allow_io` to this file's tests and swaps `_seed_user` for a
`cognito_sub` seed; no repo file touched) takes the file from `2 errors, 1 failed` to **`3 passed`**. ISS-671 and
ISS-672 have not regressed.

## Fix — where it belongs

Relocate the whole file (its three tests share `_make_tagged_outer_repo` and `_assert_nearest_repo_is`) to
`backend/tests/integration/api/test_run_files_ref_family_scope_api.py` (README rules 7 and 8; precedent
`tests/integration/api/test_run_files_upload_api.py`), and fix the seed as in [ISS-891](20261001-2120-ISS-891.md). Keep
`_assert_nearest_repo_is`: it is the safety check that every git call lands in the throwaway outer repo, never the
real checkout. The file has no `__file__`-relative path, so there is nothing to recompute on the move.
