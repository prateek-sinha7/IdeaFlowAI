# ISS-931

Derived from the QA-KB-041 analysis of [BUG-104](20260829-1508-BUG-104.md). **Confidence: INFERRED** for real browsers. The
mechanism is CONFIRMED on the live source and reproduced offline in jsdom (below); nobody has run it in Safari or Firefox.

## Condition

`/runs` (Run History), the per-row overflow menu (`button[aria-label="Run actions"]`, `aria-haspopup="menu"`, component
`RowMenu`, one per run row and one per expanded version row), opened by a click that does not focus the trigger (Safari
and Firefox on macOS do not focus a `<button>` on click; a programmatic `.click()` does not either), then Escape pressed.

## Expected

Escape closes the menu. The code says so: `// a11y: Escape closes the open menu`.

## Actual

The menu stays open and `aria-expanded` stays `"true"`.

## Why the root cause implies it

[BUG-104](20260829-1508-BUG-104.md): Escape is bound with a React `onKeyDown` on the wrapper element, so it only counts
keydowns that start inside the wrapper. A keydown targets `document.activeElement`; with the trigger unfocused that is BODY.

```tsx
// RevisionFamilyView.tsx:446-452
<div
  className="relative"
  onKeyDown={(e) => {
    // a11y: Escape closes the open menu (toggling the same row closes it).
    if (e.key === "Escape" && isOpen) { e.stopPropagation(); onToggleMenu(runId); }
  }}
>
```

No `.focus()` or `autoFocus` anywhere in `RowMenu` (`:436-487`), so nothing moves focus into the menu on open. Outside click
works because `WorkflowHistory.tsx:1486-1488` renders a full-screen `div.fixed.inset-0.z-10` while `openMenuId` is set.

## Evidence (offline, jsdom; nothing under `frontend/src` was created or edited)

`evidence/qa-kb-041/08-analyze-probe-output.txt`, source `07-analyze-probe-rowmenu.test.tsx.txt` (renders the exported
`FamilyGroupCard` with the same `openMenuId` / `onToggleMenu` wiring as `WorkflowHistory.tsx:1455-1456`):

| case | activeElement after the click | after Escape |
|---|---|---|
| CONTROL, `user.click(trigger)` (focuses, like Chrome) | "Run actions" | `aria-expanded` back to `"false"` |
| REPRO, `fireEvent.click(trigger)` (never focuses) | BODY | `aria-expanded = true`, `role="menu"` still present |

No existing test covers Escape on this menu at all (`grep -i escape frontend/src/components/history/*.test.tsx` finds one
unrelated comment).

## Reach (INFERRED)

Safari and Firefox on macOS. Chrome on every OS and a menu opened from the keyboard are unaffected.

## What would settle it

Real Safari or Firefox (macOS): `/runs`, open "Run actions" on any row with the mouse, press Escape. Do not choose Delete.

## Fix direction

Same as [BUG-104](20260829-1508-BUG-104.md): drop the wrapper `onKeyDown` (`:448-451`) and call the shared hook from
[FIX-388](20260829-0053-FIX-388.md): `useEscapeToClose(() => onToggleMenu(runId), isOpen)`
(`frontend/src/hooks/useEscapeToClose.ts`).

**The `isOpen` gate is mandatory here, not tidiness.** `RowMenu` renders once per row, and the History page's
`onToggleMenu` is a toggle (`setOpenMenuId(openMenuId === id ? null : id)`, `WorkflowHistory.tsx:1456`). An ungated listener
would register on every row, and each Escape would call the toggle for every row that is not open, which opens a menu.

## Resolution (QA-KB-041, fixer, 2026-10-02)

[FIX-710](20261002-0154-FIX-710.md) applies the "Fix direction" above as written. `RevisionFamilyView.tsx:449` now reads
`useEscapeToClose(() => onToggleMenu(runId), isOpen);`. The `isOpen` gate is kept, and the wrapper `onKeyDown` is deleted
(the wrapper is now `:451-453`).

An expanded family renders the root's RowMenu twice, so two listeners fire on one Escape. Both still close the menu,
because `WorkflowHistory.tsx:1456` toggles from its render closure, not from a functional update.

**The test file was corrected, and that is disclosed in FIX-710.** `RevisionFamilyView.escape.test.tsx` checked
`queryByRole("menu")` for null synchronously after the `aria-expanded` check. The menu leaves through a 0.1s
`AnimatePresence` exit (`:464-471`), so the null check reported "1 expected fail" in 4 of 4 runs, even though
`aria-expanded` was already `false`.

The null check now runs inside `waitFor`, matching the CONTROL in this card's own probe
(`07-analyze-probe-rowmenu.test.tsx.txt:41`). The `aria-expanded` assertion is unchanged. Against the pre-fix RowMenu the
corrected test is red: `aria-expanded` is still `"true"`. On the fixed tree it XPASSes in 3 of 3 runs. The marker is left
for the verifier.
