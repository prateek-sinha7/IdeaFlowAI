## What was wrong

Selecting a pipeline type on `/analytics` narrowed the "By Pipeline Type" list and nothing
else. Total Tokens, Est. Cost, Avg/Run, Total Runs, the Daily Activity chart, Success Rate and
the By Model panel all kept reporting the unfiltered window, so the page contradicted itself —
the tiles said 278 runs / $52.82 while the list directly beneath said Prototype was 18 + 8 runs.
The model filter had the identical shape (ISS-288), and the two breakdown lists ignored each
other's filter (ISS-289).

## Root cause

One unfiltered `AnalyticsSummary` per date range, narrowed in the browser at two leaf points:

- `backend/app/api/analytics.py:278-297` (pre-change) — `GET /api/analytics/summary` accepted
  `range` alone. `_aggregate()` rolls `kpis` / `token_totals` / `spend` / `daily` up over every
  owner-scoped row in the window, and neither `PipelineRollup` nor `ModelRollup` carries a
  completed/failed split — so a per-pipeline Success Rate or Daily Activity chart could not be
  derived client-side from what the server sent, at any price.
- `frontend/src/lib/api.ts:789-797` (pre-change) — `getAnalyticsSummary(token, range)` had no
  pipeline/model parameter to pass even if the component had wanted one.
- `frontend/src/components/analytics/AnalyticsPage.tsx:177` (pre-change) — the fetch effect's
  dependency array was `[dateFilter]`; changing either other filter fired no request.
- `AnalyticsPage.tsx:245` / `:259` (pre-change) — the only two places a filter was read:
  `pipelineRows.filter(pipelineFilter)` and `modelRows.filter(modelFilter)`, each on its own
  axis, neither reaching the tiles, the chart, the donut or each other.

## What changed, and why there

The filter moved to where `range` already lives — one place every caller routes through, rather
than a guard per derived value:

- `backend/app/api/analytics.py:283-325` — `get_analytics_summary` gains `pipeline` and `model`,
  applied to the query BEFORE `_aggregate()`, alongside the existing `cutoff`. Both are generic
  column comparisons on `type` / `model_id`, never a workflow-name branch (SC-001): `pipeline`
  matches the base type and its `_revision` variant (mirroring the frontend's `normalizeType`,
  so the breakdown keeps listing both rows), and `model` honours the `"unknown"` bucket key the
  same module hands the caller back for a null `model_id` — now the shared `_UNKNOWN_MODEL`
  constant (`analytics.py:49`, used at `:237`), so selecting that option cannot return an empty
  page. An absent param changes nothing, so the unfiltered payload is byte-identical.
- `frontend/src/lib/api.ts:811-826` — `getAnalyticsSummary(token, range, pipeline?, model?)`,
  built with `URLSearchParams`; a filter set to "all" is omitted.
- `frontend/src/components/analytics/AnalyticsPage.tsx:186` — the fetch effect depends on
  `[dateFilter, pipelineFilter, modelFilter]` and passes all three; the two client-side
  `.filter()` calls at `:254` and `:267` are gone, because the payload arrives already scoped on
  both axes.
- `AnalyticsPage.tsx:340` — the model `<select>` also renders while `modelFilter !== "all"`. The
  scoped payload reports only the selected model, which would otherwise hide the control that is
  still applying the filter, with no way back to "All models".

`getAnalyticsSummary`'s only other caller, `HomeLaunchGrid.tsx:206`, passes `range="all"` and no
filters — unchanged behaviour, verified green.
