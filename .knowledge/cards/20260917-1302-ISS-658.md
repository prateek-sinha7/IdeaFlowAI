# ISS-658

## Title

The 5-fixer escalated QA-PS-002 without changing any code. [ISS-644](20260917-0930-ISS-644.md) names a data path the notification panel never draws, and the test written for it (`frontend/src/components/layout/DashboardLayout.iss644.test.tsx`) checks that same hidden data. A change that turns the test green would leave the panel showing "0 of N agents".

ISS-644 is **not** marked superseded here. Deciding that belongs to re-analysis or the user.

## Confirmed by reading the code

1. The panel draws live rows only from its `liveRuns` prop (`NotificationPanel.tsx:312-319`). It drops running and gate items from `notifications` at `NotificationPanel.tsx:212-214`.
2. `liveRuns` is AppHeader's `runningPipelines` (`AppHeader.tsx:474`), built at `AppHeader.tsx:190-217` from the server's `recentRuns`:
   - `agentsCompleted: isActive ? pipelineAgentsCompleted : storeCompleted` (`:211`)
   - `storeCompleted = runAgentsCompletedMap?.[r.id] ?? 0` (`:200`)
   - `agentsTotal` comes from `r.agentCount` (`:212`)
   - `LIVE_STATUSES` includes `generating` (`:46-48`), so the repro run lands here.
3. AppHeader's fallback, `runningFromNotifs` (`AppHeader.tsx:177-183`, used only when `recentRuns` is empty), is always empty. `DashboardLayout.tsx:2670` gives AppHeader only `notifications.filter(n => n.status !== "running" && n.status !== "gate")`.
4. As a result, the `useNotifications` notification that ISS-644 names is never drawn while its run is live. That is the object whose `agentsCompleted` gets set by `updateProgress` (`DashboardLayout.tsx:937-941`, `useNotifications.ts:151-155`). `agentsCompleted` is read only at `NotificationPanel.tsx:134-143` and `AppHeader.tsx:338,427`, and all three read `runningPipelines`.
5. On a page reload, `useNotifications.ts:37-44` (FIX-204) drops running notifications while restoring saved state. So in ISS-644's "cold navigation" repro, the notification ISS-644 is about does not exist at all. The panel row still appears, because it comes from `recentRuns`.
6. In step 3 the test passes `runAgentsCompletedMap: { [runId]: 5 }` with an idle `pipelineState`. With those inputs, a live run in `recentRuns` is not active, so AppHeader already shows "5 of N" (`AppHeader.tsx:195,200,211`). The test sets up a state where the bug does not happen, then checks a field nothing shows. (The test passes no `recentRuns`, so its panel draws no live row at all.)

## Likely cause of the 0 (not verified, for re-analysis)

The "0" most likely comes from the `?? 0` fallback at `AppHeader.tsx:200`:

- `runAgentsCompletedMap` is rebuilt on every page render from `runStore.get(run.id)` (`page.tsx:3894-3900`). The store is held in a ref (`useRunStateStore.ts:273-274`). It only has an entry for a run whose live-stream (SSE) messages reached this tab (`getOrCreate`, `useRunStateStore.ts:361`).
- `RunConnectionProvider.tsx:307-315` reconnects automatically only to runs listed in this tab's `sessionStorage.tab_launched_run_ids`. A run started in another tab or an earlier session never gets a store entry.
- A message for a background run does not re-render page.tsx; only the viewed run's messages update the screen (`useRunStateStore.ts:476-481`). Even an existing entry is only as fresh as the last unrelated re-render.
- The server's run list gives only `agentCount` (`WorkflowRun` in `types/index.ts`, `lib/api.ts:754`). It has no completed-agent count to fall back on.

The QA report says three concurrent runs "all show 0%". That matches a missing store entry. ISS-644's theory (a count frozen after leaving the run's page) would keep the last count, not reset it to 0.

## Options (design decisions, not a fixer call)

- **A.** Re-analyze QA-PS-002 against `AppHeader.tsx:190-217` and `page.tsx:3894-3900`. Rewrite the test to render the panel with `recentRuns` and check the "X of N agents" text it actually shows. Then mark ISS-644 superseded.
- **B.** Server side: add a completed-agent count to `GET /api/runs` and use it as AppHeader's fallback. This changes the API contract and the backend serializer.
- **C.** Client side: re-render the map's consumer when a background run's message arrives (for example, a version counter in `useRunStateStore`), and/or connect to streams for every live run. This only helps runs this tab can stream, so it does not cover runs launched elsewhere.

## Fixer note (2026-09-17, [FIX-521](20260917-1447-FIX-521.md)): this card's own test asserts the wrong mechanism

The panel defect this card traced is fixed by FIX-521 at ISS-673's location. This card stays
**open** because of its test, and the test was **not edited**.

`frontend/src/components/ui/NotificationPanel.iss658.test.tsx` passes the panel a
`status: "running"` notification carrying `agentsCompleted: 5` beside a stale `liveRuns` row, and
expects "5 of 6 agents". Three problems with that:

- **The panel forbids it.** It drops running and gate items on purpose
  (`NotificationPanel.tsx:212-214`: "only show terminal notifications here — live runs come via
  liveRuns").
- **Production never sends one.** DashboardLayout never passes a running notification
  (`DashboardLayout.tsx:2695`).
- **The field is the stale one.** That `agentsCompleted` is the `updateProgress` field this card's
  own "Confirmed by reading the code" section shows is only updated for the viewed run.

Turning the test green would mean merging notification counts into live rows at one render site.
That is the per-site patch [ISS-673](20260917-1420-ISS-673.md) rules out, it would be unreachable in
production, and it would read ISS-644's stale field. It is the same trap this card flagged in
`DashboardLayout.iss644.test.tsx`.

After FIX-521 it still reports "1 expected fail", unchanged from before. The test-writer needs to
retire it or re-point it at ISS-673's mechanism; the fix's own evidence is
`useRunStateStore.iss673.test.tsx`. This card's "Likely cause of the 0" also named the cross-tab
case, which FIX-521 does not reach and which is now [ISS-675](20260917-1447-ISS-675.md).

## Test-writer note (2026-09-17)

Re-pointed per this card's own ask. `NotificationPanel.iss658.test.tsx` is retired (`it.skip`,

covering the same defect [ISS-679](20260917-1522-ISS-679.md) names; it stays filed under this
card because ISS-679 is not in this bug's assigned card set.

module scope, so a `page.tsx` remount no longer drops a background run's roster.

- `useRunStateStore.iss658.test.tsx` went from "1 expected fail" to XPASS ("Expect test to fail"). Its

  JWT `sub`.
- A full page reload still starts the store empty. That trigger is
  [ISS-680](20260917-1555-ISS-680.md), deferred.
