# ISS-1064

What is left of [ISS-1019](20261002-0617-ISS-1019.md) after [FIX-736](20261007-1940-FIX-736.md). ISS-1019 listed seven test files
that seed `User` without the NOT NULL `cognito_sub`. FIX-736 revived five. These two were probed first and deliberately left
alone. Both still sit in `tests/unit/`, where the I/O guard stops them at setup. That guard is what keeps the first one off
the network today.

Probe: copies with only the seed edit, run outside `tests/unit` (`-c /dev/null`, `DATABASE_URL=sqlite:///:memory:`).
Evidence: `evidence/qa-kb-077/fix-06-unit-race-pins-probe.txt`.

## 1. `backend/tests/unit/test_admin_privilege_race.py` (ISS-471): reviving it reaches the real identity provider

- As shipped: `2 xfailed`, but only because setup errors (`UnitIsolationError`, then NOT NULL beneath). Both tests carry
  `@pytest.mark.xfail(reason="ISS-471 unfixed", strict=True)`. [ISS-471](20260828-2310-ISS-471.md) is `resolved`, so the
  marker is stale too.
- Seed fixed, outside the guard, `--runxfail`:
  `botocore.errorfactory.UserNotFoundException: ... when calling the AdminListGroupsForUser operation: User does not exist.`,
  then `app.core.cognito_admin.ProviderUnavailableError: Could not read current group membership at the identity provider.`
- Why: `update_user_tier` / `update_user_role` (`backend/app/api/admin.py`) now call `cognito_admin`. That is the P1 atomicity
  fix, and `tests/integration/api/test_admin_privilege_atomicity_api.py` tests it with boto3 mocked. This race test predates
  it and mocks nothing. `backend/.env` sets `COGNITO_USER_POOL_ID`, and no conftest guards boto3, so the call went out.
- Disclosure: the probe made one read-only `AdminListGroupsForUser` call for `target@example.com`, which does not exist in
  the pool. Nothing was mutated. With an email that did exist, the same path would go on to change that account's groups.
- Hazard: the queued eviction of guard-tripping unit files (`backend/tests/README.md`, "63 files / 599 tests") would do
  exactly this to the file if it moved it mechanically. Fixing the seed in place would remove the NOT NULL failure that
  currently stops it first, which is why FIX-736 did not do even that.
- Needs: boto3 mocks (the atomicity file's pattern), the seed, the move to `tests/integration/api/`, then a check of what the
  race pins actually say now that ISS-471 is resolved.

## 2. `backend/tests/unit/test_settings_preferences_race.py` (ISS-319): moves with ISS-937's fix

- As shipped: `1 error` (`UnitIsolationError`). Seed fixed, outside the guard: `1 passed` against today's `update_preferences`.
- Left alone because [ISS-937](20261001-2231-ISS-937.md) (QA-KB-083) names this file in its globs. Its fix changes
  `update_preferences` to take the principal, and this file is the only direct caller (`user=` keyword), so that fix has to
  edit it anyway. Two fixers editing one file lose each other's edits. The seed (`cognito_sub=str(uuid.uuid4())`) and the move
  to `tests/integration/api/` belong in that same edit.

[FIX-738](20261007-1958-FIX-738.md) did section 2 in ISS-937's edit. The file is now

Section 1 (`test_admin_privilege_race.py`) is untouched, so this card stays open for it.
