## The symptom

`tools/knowledge/status.py` prints a header line that is supposed to say which
commit and which checkout the report describes. It says this instead:

```
tree:   /Users/bilala/Developer/Projects/VELOCITY-AI-worktrees/feat-pdf-workflow
branch: feat/pdf-workflow @ ---
id:    last sync 2026-09-15 (4a6e8993)
```

The sha is `---` and the next line begins with a stray `id:`. `--json` shows
what is actually in the field: roughly 2000 characters of
`DOMAIN-workspace-isolation` frontmatter and generated body, sitting where an
8-character sha belongs.

Reproduced on HEAD `73796dbd0`, both output modes.

## Root cause

One name, two meanings, twenty lines apart.

`status.py:144` binds the report's identity:

```python
head = git("rev-parse", "HEAD")
```

`status.py:319`, inside `for card in sorted(arch_dir.glob("DOMAIN-*.md"))`,
rebinds it as a scratch buffer for the card text the signature regex scans:

```python
head = card.read_text(encoding="utf-8", errors="replace")[:2000]
```

Python has no block scope, so the loop variable *is* the module-level one. Both
consumers run after the loop and both get the last DOMAIN card read — `:342`
emits it as the JSON `"head"`, `:355` slices `[:8]` off it and prints `---`
(the opening frontmatter delimiter) plus whatever the rest of the line held.

The shadowing arrived with the domain-prose block in `70d4d63b2`. That commit
added the loop; it did not touch line 144, so nothing in the diff looked wrong.

## Why it matters

The header line is the only thing distinguishing one checkout's report from
another's, and `status.py` deliberately prints a `NOTE: N other checkout(s) of
this repo exist` block right below it so a reader can tell genuine drift from a
different branch. Without a real sha, that whole comparison is guesswork.

The JSON field is worse: anything reading `head` programmatically gets 2KB of
markdown where it expects a sha, with no error to notice.

## Fix

Rename the loop variable at `:319` (and its two uses at `:321`). Nothing else
moves.

## Analysis (QA-KB-003, 2026-10-01)

Diagnosis above is **CONFIRMED** against `tools/knowledge/status.py` on HEAD 024c03ef (branch

### Root cause (CONFIRMED)

One local name, two meanings, inside `main()` (`status.py:140-390`):

- `:144` `head = git("rev-parse", "HEAD")` -- the report's identity.
- `:318` `for card in sorted(arch_dir.glob("DOMAIN-*.md")) if arch_dir.is_dir() else []:` then
  `:319` `head = card.read_text(encoding="utf-8", errors="replace")[:2000]` -- rebinds it at the
  top of EVERY iteration. This runs before the `continue` at `:323`, so a DOMAIN card with no
  `code_signature` clobbers it too.
- `:320-321` `re.findall(r"^(prose_signature|code_signature):\s*(\S+)\s*$", head, re.M)` -- the
  only reader of the scratch value. Nothing from `:322` to the end of the loop reads `head`.
- `:342` `"head": head,` (JSON) and `:355` `@ {(head or '?')[:8]}` (header) -- both run after the
  loop and see the last DOMAIN card in `sorted()` order, `DOMAIN-workspace-isolation.md` of 16.

Observed 2026-10-01: header `branch: feat/user-stories-v2 @ ---` then `id:    last sync ...`;
`--json` `head` is 2000 chars starting `---\nid: DOMAIN-workspace-isolation\ntype: architecture-domain`
while `git rev-parse HEAD` is `024c03ef82e54cc3688222b23fe9a830a1d76131`. The `other_checkouts[].head`
values in the same JSON are correct 40-hex shas: they come from `worktrees()` (`:94`), a different
variable. That contrast is the quickest tell.

Precision fixes to the prose above (meaning unchanged):
1. The rename touches ONE use at `:321`, not two.
2. The 8 chars printed are `---\nid: ` (the newline is the 4th), which is where the orphan `id:` line comes from.
3. `head` is local to `main()`, not module-level; Python having no block scope is still the mechanism.
4. The bug is dormant only when `.knowledge/architecture/` has zero DOMAIN cards (loop never runs).
   Otherwise it is always on: no dependence on card content, flags, tier or theme. It also hides a
   failed `git rev-parse` -- an empty `head` would print `?`, but the loop overwrites it with card text.

### Fix (agreed minimal fix ACCEPTED, not overruled)

`status.py:319` `head = card.read_text(...)[:2000]` becomes `text = ...`, and `status.py:321`
`..., head, re.M))` becomes `..., text, re.M))`. Leave `:144`, `:342`, `:355` alone. `text` collides with
nothing in `main()` (the only `text` token in the file is the `text=True` kwarg at `:37`, inside
`git()`). The fix belongs at the clobbering assignment: it repairs both consumers at once, while
recomputing the sha at `:342`/`:355` would leave `head` poisoned for any future reader and bury the
cause. Extracting the loop into a helper is a larger diff in a function that QA-KB-026
([ISS-693](20260918-ISS-693.md)) also edits at `:329-335`; the in-place rename changes no line count,
so the two fixes can land in either order.

Proved without touching the tree: a scratch copy of `status.py` with exactly those two edits (ROOT
pointed at this tree) prints `branch: feat/user-stories-v2 @ 024c03ef   last sync 2026-10-01 (3b08b2ba)`
and its `--json` `head` equals `git rev-parse HEAD`; the table rows are unchanged.
