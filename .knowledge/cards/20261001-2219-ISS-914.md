## What happened

Found on 2026-10-01 by the 3-analyzer while checking the premise ISS-349's source comment rests on ("static
app/admin/page.tsx takes precedence over [...view] catch-all for /admin path"). The premise still holds for `/admin`
and `/login`; it no longer holds for `/register`. This is an adjacent finding rather than a second instance of the
missing depth guard: the trigger is the EXACT `/register` path, not a sub-path. INFERRED: every link below is read
from code or git, except the final render, which needs one signed-in browser cycle.

## Root cause (CONFIRMED by source read, INFERRED as a live defect)

1. `frontend/src/app/register/page.tsx` no longer exists. `git ls-tree -r HEAD --name-only | grep
   'frontend/src/app/register'` prints nothing, and `git show --stat b2a621f84 -- frontend/src/app/register` shows
   `frontend/src/app/register/page.tsx | 18 ------------------` (commit "Fix/cognito login (#8)", 2026-09-17, the
   Cognito-only authentication change).
2. `frontend/src/lib/routes.ts:267-269` still parses the path:

```ts
if (head === 'register' && segments.length === 1) {
  return { screen: 'register' };
}
```

   and `routes.ts:52` still builds it (`register: (): string => '/register'`; no caller outside tests).
   `parseViewPath(['register'])` -> `{"screen":"register"}` (probe, current code).
3. Nothing renders that screen. `[...view]/page.tsx` has no register branch (every case-insensitive hit for
   "register" in the file is an unrelated run-launch comment), `initialMainViewFor` falls to `default: return
   undefined` (`page.tsx:197-198`), and `DashboardLayout.tsx:568-584` defaults `useState<MainView>` to `"home"`
   (:583), the same fallthrough ISS-349 traces.
4. So `/register`, now served by `[...view]` like any unrecognised first segment, paints Home under `/register` for
   a signed-in user.

Premises written while the stub still existed, now stale: [FIX-344](20260828-2046-FIX-344.md) ("the exact
`/register` path never reaches this code"), [BUG-056](20260829-1508-BUG-056.md) ("Exact `/register`
(authenticated) still redirects to `/dashboard`", verified 2026-08-28), `test_auth.py:162-163` ("register/page.tsx
keeps the route alive rather than 404ing so cached external links land somewhere sensible. It is a stub, not a
screen."), and `MOD-frontend-src-app.md:88-89` (still lists `register/page.tsx`).

## Why S-01-08 does not catch it

`tests/integration/e2e/suites/01_auth/test_auth.py:155-163` (S-01-08) cold-loads `/register` and expects a `/login`
URL plus the sign-in heading. That is the signed-out case: `[...view]` renders null (`page.tsx:4035-4040`) while its
mount effect sends a token-less user to the login redirect (`page.tsx:922-927`, `router.replace(buildLoginRedirect())`;
BUG-056 recorded the same for signed-out `/register/<sub-path>`), so the test still passes. Nothing exercises the
signed-in case. (INFERRED: the e2e suite was not run here.)

## Expected vs actual

- **Expected:** a retired, cached self-registration link lands somewhere sensible for a signed-in user too (the
  intent S-01-08's comment states): a redirect to the sign-in or dashboard destination, or not-found.
- **Actual (INFERRED):** the address bar stays on `/register` while the dashboard renders.

## Why ISS-349's root cause implies it

The depth-guard siblings are carded separately and are not this: [ISS-348](20260828-2102-ISS-348.md) (`login`),
[ISS-910](20261001-2220-ISS-910.md) (`dashboard`), [ISS-911](20261001-2220-ISS-911.md) (trailing segments).

Not the depth guard: the shared amplifier. `[...view]/page.tsx` renders the dashboard for any parsed screen it has no
branch for, so every descriptor `parseViewPath` can return without a renderer (`login`, `register`, `admin`) is one
stale assumption away from painting Home. For `admin` and `login` the static route still shields the exact path; for
`register` the shield is gone.

## What would settle it

Sign in, cold-load `/register`, read `location.pathname` and the `h1`. If it redirects, close this card.

## Fix direction (decision needed, not applied)

Pick the intended landing for retired self-registration links, then implement it in one place:
(a) restore a stub `app/register/page.tsx` that redirects; (b) add `{ source: "/register", destination: "/login" }` to
`next.config.ts` `redirects()` (the `/settings` rule there is the model; mirror it in `parseViewPath` too if
client-side transitions matter, per ISS-339); or (c) drop the `register` branch so the path parses to `unknown` ->
`notFound()` (then `routes.register()` and its round-trip test at `routes.test.ts:45` go with it). (c) contradicts the
S-01-08 intent; (a) and (b) honour it.

## Fixer note (QA-KB-013, fixer, 2026-10-01): not closed

The QA-KB-013 fix dispatch asked for this card to be closed as not-a-defect on the premise "/register is already
guarded". That premise does not hold for this card's trigger, so the card stays `open` and its meaning is unchanged:

- The only register guard is FIX-344's depth guard, `if (head === 'register' && segments.length === 1) {`
  (`frontend/src/lib/routes.ts:271` after [FIX-696](20261001-2235-FIX-696.md)). It rejects `/register/<sub-path>`
  and ADMITS the bare `/register`, which is exactly the path this card is about. `parseViewPath(['register'])` still
  returns `{"screen":"register"}` (probe, `evidence/qa-kb-012/05-fix-parser-probe-head-vs-worktree.txt`).
- Nothing else intercepts exact `/register`:
  - `frontend/src/app/register/` does not exist (`ls` fails; `git ls-files frontend/src/app/register` is empty).
  - `frontend/next.config.ts` `redirects()` has only these sources: `/library/agents`, `/library/skills`,
    `/library/hooks`, `/settings`.
  - `frontend/src/proxy.ts` matches only `/workflow/create`.
  - `[...view]/page.tsx` has no register branch. Its only `router.replace` calls are the no-token login redirect
    (`:936`) and logout (`:3431`).

FIX-696 does not change this path. What still settles it: one signed-in browser cycle at exact `/register`, then the
product decision under "Fix direction" above.
