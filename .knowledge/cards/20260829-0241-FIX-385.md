## What was wrong

`/settings/constitution` renders "Clear" directly beside "Save constitution".
It reads as a draft reset — the textarea never auto-saves, so nothing on the
screen suggests the two buttons write to different places. It was in fact a
one-click, irreversible, account-wide delete of the standing instructions the
same page says are "prepended to every agent on every run": the click fired
`DELETE /api/settings/constitution` synchronously, and the backend delete
(`backend/app/api/settings.py:405-410`) is a hard delete with no soft-delete
and no versioning, so the click was the only safeguard that could exist.

## Root cause

`frontend/src/components/settings/AccountSettings.tsx` — `ConstitutionSection`'s
`handleDelete` (now :547) was wired straight to the "Clear" button's `onClick`
(now :629) with no intermediate gate: no `window.confirm`, no modal, no
two-step "are you sure". `handleDelete` is a local closure with exactly one
call site, so the whole defect and the whole fix live in that one handler.

## What changed and why there

One early return at the top of `handleDelete`, before any state is touched and
before the request is built:

```tsx
if (!window.confirm(
  "Clear your constitution? This permanently deletes the saved instructions "
  + "prepended to every agent on every run."
)) return;
```

`window.confirm` rather than a new `ConfirmDialog` primitive: it is the gate
this codebase already uses for destructive-by-navigation work
(`frontend/src/components/layout/DashboardLayout.tsx:1717`), it needs no new
component, and the e2e test written for [ISS-320](20260828-1802-ISS-320.md)
expects the confirmation to surface as a native dialog. The guard sits in the
handler, not the button, so every future caller of `handleDelete` inherits it.

**Not fixed here, deliberately:** the same unguarded-destroy shape in
`SkillManager.tsx` ([ISS-480](20260828-2320-ISS-480.md)),
`IntegrationsCard.tsx` ([ISS-481](20260828-2321-ISS-481.md)) and the
tab-switch draft loss ([ISS-482](20260828-2322-ISS-482.md)). Those are
separate components with their own cards and their own owners — nothing routes
through `handleDelete`, so there is no shared function to fix once.

## Verification

Direct observation against the running app (Playwright, real Chrome, qa-admin),
constitution restored afterwards:

```
E. dialog seen          : ['Clear your constitution? This permanently deletes …']
F. GET after DISMISS    : {"content":"E2E S-09-12: answer in exactly one sentence."}
G. dialog seen (accept) : ['Clear your constitution? This permanently deletes …']
H. GET after ACCEPT     : {"content":null}
```

Dismiss leaves the persisted value untouched; accept still deletes. Before this
change the same click produced `{"content": null}` with no dialog at all, 3/3
(see [ISS-320](20260828-1802-ISS-320.md)).

The card's e2e test still reports `xfail`, and **not because the fix is
missing** — in all 3 runs the post-click `GET` returned the saved constitution
rather than `null`, i.e. the DELETE never fired. The test cannot reach its
assertion for two reasons of its own, both recorded in
[ISS-581](20260829-0241-ISS-581.md):

1. its setup's `editor.fill(marker)` + Save persists the OLD value, so the
   assertion compares the surviving constitution against a marker that was
   never saved;
2. it registers its own `page.on("dialog", … dismiss())` on top of the autouse
   `dismiss_native_dialogs` fixture (`tests/integration/e2e/conftest.py:279`),
   and the second dismiss raises `Dialog.dismiss: Cannot dismiss dialog which
   is already handled` — a hard FAILED, seen on run 2 of 3.

The test was left exactly as written; repairing it is the test author's call,
not this fix's.

## Consequence for the e2e suite

`conftest.py`'s autouse `dismiss_native_dialogs` dismisses every native dialog,
so from now on **"Clear" is a no-op in every e2e test** unless that test
accepts the dialog itself. Two restore paths click Clear expecting it to work
(`test_settings.py:436` and `:539`); both only execute when the account starts
with an EMPTY constitution, which is not the current pool state, so neither is
reachable today — but they will need an `accept()` when it is.
