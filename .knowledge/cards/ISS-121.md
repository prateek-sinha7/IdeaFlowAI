# ISS-121

## Title

A gate-rejected run reopens from history looking ALIVE: header "Awaiting approval", a "Stop" button, and the stale clarify line "The run is paused and waiting for you to answer clarification questions". The run is genuinely finished — DB workflow_runs.status = 'cancelled', and only 1 of 6 agents ever started. ROOT CAUSE — CORRECTED IN PLACE 2026-08-12. THE ORIGINAL DIAGNOSIS IN THIS ROW WAS WRONG. It read: *"pipeline_cancelled is NEVER WRITTEN to the durable run_events log … the fix is to make the reopen path consult GET /api/runs/{id}"*. Every MEASUREMENT below is correct; the causal claim built on top of them was not. pipeline_cancelled IS written on every one of the engine's eight terminal emitters. On this run the INSERT was attempted, rejected by the uq_run_events_scope_seq UNIQUE constraint, and silently swallowed. The real defect is general, not gate-specific: every app-layer run_events row written while a run is live destroyed exactly one subsequent engine event. Two writers shared ONE per-run seq space with TWO algorithms — ScopedStore.append_event_next_seq (agents/authz.py:433) allocates max(seq)+1 and retries past IntegrityError, while the engine's _RunEventSink.persist (engine.py:429-462) used a fixed in-memory counter and swallowed the collision: it catches SQLAlchemyError, IntegrityError is one, so a production seq collision took the branch written for "the offline harness has no schema" and was indistinguishable in the logs. At a gate the engine is idle, so the victim is deterministically the terminal frame — which is exactly why the symptom LOOKED like "cancelled is never persisted". authz.py:462-465 documented this as an accepted trade-off and called the collision "rare"; it fires on every chat turn during a live run. MEASUREMENTS (unchanged, all verified): full type tally for live run 808612bf-777a-4ab1-b188-6561a23eb12a (user_stories, gate on domain-analyst, rejected): agent_chunk 262, chat_reply 6, chat_message 2, workflow_validated 1, review_gate_ready 1, questionnaire_ready 1, planner_start 1, planner_complete 1, pipeline_start 1, gate_status 1, chat_usage 1, agent_start 1, agent_input 1, agent_complete 1 — no pipeline_cancelled, no pipeline_complete. The fingerprint that broke it open: the log does NOT end at review_gate_ready (seq 278) — seq 279 is a narrator chat_reply card, 280 the user's chat_message "Not what I wanted — stop.", and 281 is a chat_reply milestone card reading "Cancelled by you" — the card projected FROM the very pipeline_cancelled event whose row is missing. A milestone card whose preceding row is a chat_message is structurally impossible unless the engine event that produced it was dropped. Also corrected: the rejection arrived through POST /api/runs/{id}/messages (the chat lane, the only one of the three that writes a durable row), NOT POST /gate; POST /gate and POST /cancel write none and never reproduced it. FIX (FIX-240): ScopedStore.append_event_at_or_after re-appends past the racing writer and returns the seq the row actually landed on; both engine drive loops re-stamp data["seq"] with it (mandatory — run_stream.py:198 renders the SSE id: cursor from row.seq on replay and :264 from data["seq"] live, so a divergence corrupts Last-Event-ID). The rejected "consult the run record instead" option was correctly identified as insufficient AND as an INV-12 second source of truth for terminal state; it survives only as a narrow app-boundary guard on the SSE gate re-arm. RELATION TO FIX-232 — unchanged and still honest: FIX-232 is CORRECT and untouched; it did not create the durability gap, it changed which wrong thing the user saw. Residual, NOT fixed by FIX-240: ISS-123 (rows already destroyed are not retroactively recoverable) and ISS-126 (a fresh reopen still replays the dangling gate row).
