# FIX-622

Register entry: **QA-SG-013** (`BUGS.md`) — "Download button is disabled on user story run
detail page, cannot download deliverable". Resolves [ISS-768](20260922-1500-ISS-768.md) (base
`user_stories`) and its confirmed sibling [ISS-774](20260922-1530-ISS-774.md) (`custom`) with
one change in the shared resolver, because both cards trace to the same mechanism and ISS-774
exists precisely to forbid a `user_stories`-only guard.

## What was wrong

On every completed run of a workflow whose `deliverable.strategy` gives the declared filename a
NOMINAL rather than an on-disk meaning, the header "Download the deliverable" button was
disabled permanently — not a timing, tier, theme or version-pinning effect. ISS-768 reproduced
it 3/3 against base `user_stories` runs; ISS-774 confirmed it live on `custom` run
`e49b91e6-f2fe-479c-a941-75da2b53c05d`, where 22 completed/degraded `custom` runs existed.

## Root cause

Two halves that disagree about where the deliverable lives.

**Backend (correct, by design).** `build_flat_payload` in
`backend/agents/execution_engine/engine.py:1328-1348` documents the `streamed_text` contract
verbatim — *"the declared name is NOMINAL, not a file (S8) … `chat` (chat.md), `custom`
(output.md), `user_stories` (user_stories.md) and `reverse_engineer` (analysis.md) declare a
nominal filename whose bytes live in `ectx.last_streamed` … never on disk"*. The
materialization at `engine.py:1462-1466` therefore writes those bytes to
`_staging_abs / _output_basename`, and `engine.py:1536` atomically replaces that staging dir
onto `sandbox.root / ".chain"`. The result is canonical and durable, not scratch:
`backend/app/agents/sandbox.py:309` stages `f".chain/{output_basename}"` into the payload
allowlist, `sandbox.py:255` keeps `.chain/` in `_LISTING_VISIBLE`, and
`backend/app/api/run_files.py:708-711` refuses only `.uploads/`, `.logs/` and `.chain-legacy/`
— so `.chain/<name>` is both listed by `GET /{run_id}/sandbox` and served by
`GET /{run_id}/sandbox/file`. The same is true of the `serialized_sandbox` and `ppt` branches
above and below it, which share the identical "nominal name" comment and the identical staging
write.

**Frontend (the defect).** `resolveRunDeliverable` (`frontend/src/lib/api.ts`) ended with a
single exact-path match against that listing:

```ts
return candidates.map((c) => listing.files.find((f) => f.path === c)).find(Boolean) ?? null;
```

`candidates` only ever holds bare basenames (`user_stories.md`, `output.html`,
`<stem>.pptx`/`<stem>.html`), so the comparison `f.path === c` can only ever hit a file at
sandbox ROOT. For a nominal-name strategy nothing is ever at root, the resolver returned
`null`, `deliverableFile` in `PreviewPanel.tsx` stayed `null`, and
`canHeaderDownload = !!deliverableFile || deliverableBundle` (`PreviewPanel.tsx:1424`) was
`false`. The ISS-313 bundle fallback could not cover it either: that branch fires only when
`declared` is falsy, and here `deliverable_filename` is populated.

## What changed, and why there

`frontend/src/lib/api.ts:1300-1315` — the resolver now runs the candidate list twice, root
first, `.chain/` second:

```ts
return candidates.map(at).find(Boolean)
  ?? candidates.map((c) => at(`.chain/${c}`)).find(Boolean)
  ?? null;
```

This is the one place all callers route through — `PreviewPanel.tsx:1392` (header Download) and
`FilesTab.tsx:533,561` (the deliverable row and its "From v{n-1}" sibling) both call it, and
ISS-774 makes the shared location a requirement rather than a preference. It is also location-
keyed, not name-keyed, so it cures `streamed_text`, `serialized_sandbox` and `ppt` together
without a workflow-name branch anywhere (SC-001 holds; nothing under
`backend/agents/execution_engine/` was edited at all).

Two properties make it safe rather than merely small:

- **Root wins outright.** The `.chain/` pass is reached only after every root candidate has
  missed, so no run that resolves today resolves differently — `ppt_v2`'s real root
  `<stem>.pptx` still beats a chained `<stem>.html`. The change can only turn a `null` into a
  hit.
- **Callers already basename the path.** `PreviewPanel.tsx:1446` uses
  `deliverableFile.split("/").pop()` for the saved filename and `:1732` for the displayed one;
  `FilesTab.tsx:476` does `file.path.split("/").pop()` in `withWorkspaceFile`. A
  `.chain/user_stories.md` hit therefore downloads and displays as `user_stories.md`, with no
  consumer change needed.

## Deliberately NOT done

The cards offered an alternative (a): give one agent per `streamed_text` pipeline a real
`write_file` to sandbox root, as FIX-601 did for `ppt-revision-agent`. Rejected here — it is
per-workflow prompt surgery repeated for every current and future `streamed_text` pipeline,
which is exactly the sibling-breakage shape ISS-774 was filed to prevent, and it would also
contradict `engine.py:1328`'s stated design that the name is nominal.

[ISS-726](20260922-1248-ISS-726.md) (`user_stories_revision`) shares this mechanism and its
Download button is fixed by the same change, but its own card claims a DIFFERENT symptom —
ref-scoped reads frozen at an earlier version — which this fix does not address. Its status is
deliberately left `open` for its own row rather than closed on this fix.
