Line numbers are HEAD `c0f0a2abd` plus this change. The backend tree had no other uncommitted change while this was made, so the whole

## What was wrong

The root causes are on the two cards and are not re-derived here.

- [ISS-1117](20261008-1444-ISS-1117.md): `sync_user_workflow_from_file` authenticated with `get_current_user`, so it had no principal and never
  called `can_run_pipeline`. Any tier could copy any file pipeline's manifest into a row it owns. A plain row launches under its own
  `base_pipeline_type` at `trust="db"`, so the copy ran.
- [ISS-1131](20261008-2216-ISS-1131.md): a conditional gate's `trigger: workflow` target is a pipeline name. `run_trigger_workflow`
  (`kernel_services.py:1584-1602`) mints it mid-run through `_launch_run_core`, where no principal and no tier exist. No door checked the
  target, so a basic-tier row could start an enterprise-only run.

## What changed, and why there

1. **One walker, beside `_model_entitlement_error`.** `_trigger_entitlement_error(tier, manifest)` in `backend/app/api/run_engine.py:674-712`.
   It has the same `(status, message) | None` shape and walks the manifest the same way: `steps`, then each step's `subagents`. That
   recursion matters. The compiler flattens `subagents` children into the plan (`compiler.py` `_expand_step`), so a route on a nested step
   fires like a top-level one. For each `route.outcomes` entry with `trigger: workflow`, a target that `_is_file_backed_workflow` accepts must
   pass `can_run_pipeline(tier, target)`. Otherwise the answer is `(403, "conditional gate triggers '<target>': <reason>")`.
   `_is_file_backed_workflow` is the exact predicate `run_trigger_workflow` uses to mint by name, so the gate cannot drift from the door.
   `self`, a saved `user_workflow_id`, and a supported type with no `workflow.yaml` (`spec_kit`) are not minted by name, so they pass.
   `can_run_pipeline` fails closed on an unknown name, so walking every target would have refused every row-id trigger.
2. **Save edge, three doors** in `backend/app/api/user_workflows.py`. "Save == launch validation" is the module's own rule (docstring
   T-21-02), so all three refuse what launch now refuses:
   - `create_user_workflow`, right after the model gate (`:801-806`).
   - `update_user_workflow`, right after the model gate, on `body.manifest` (`:1020-1025`).
   - `sync_user_workflow_from_file`, on the file's manifest after it is read and before it is stored (`:1167-1172`).
3. **ISS-1117's gate on sync** (`user_workflows.py:1118`, `:1138`, `:1148-1155`). The dependency is now `get_current_principal`. After the
   `SUPPORTED_PIPELINE_TYPES` check and before `_owned` and the file read, sync refuses when
   `can_run_pipeline(effective_tier(current_user, principal), body.pipeline_type)` is false (403, create's own message). The handler docstring
   now names the two 403s (`:1132-1136`). It gates on the raw `body.pipeline_type`, as launch does (`resolve_alias` is the identity).
4. **Launch edge** (`run_commands.py:3775-3784`). This sits right after the model gate and walks the SAME argument,
   `persisted_manifest or {"steps": _ov_steps}`. That covers Case 3 for a saved row and for an inline manifest (`_inline`, `trust="user"`;
   `conditional` is `user_allowed=True`). It also covers an enabled spec-016 override, whose steps `merge_override_steps` compiles and runs
   (their routes are live). The refusal is `_reject("tier_not_entitled", ..., 403)`, the code `_require_tier_entitlement` uses. This also
   catches a row saved before this fix and an owner downgraded since.
5. **Resume edge** (`run_commands.py:702-709`). Right after `_require_tier_entitlement(wr.type)`, the walker reads the persisted
   `wr.manifest_json`, before the status flip and the queue registration. This is the ISS-1131 card's "Resume replays the persisted
   manifest, so it needs the same walk".

Imports: `_trigger_entitlement_error` is added to the existing `app.api.run_engine` import blocks in `user_workflows.py:48-52` and
`run_commands.py:101`. The walker imports `_is_file_backed_workflow` and `can_run_pipeline` lazily, as its sibling does.

### Where this differs from the cards, and why

- **ISS-1131 placed the launch walk "in Case 3, after `_WORKFLOW_COMPILER.compile`".** It sits after the model gate instead, still after the
  compile and still before the mint, and it walks the model gate's argument. The difference is that override steps are covered too. An
  override row is a workflow the owner saved, and the card's Expected is "whichever door starts it". One side effect: if
  `merge_override_steps` refuses an override (so the file plan runs and the trigger never fires), the walk still refuses it. The model gate
  has the same posture. A save can no longer create such a row.
- **The walk reads the raw manifest dict, not `compiled.steps`.** The save doors have no compiled plan to hand. The dict shape is exact,
  because `_compile_route` accepts only a mapping of mappings whose `trigger` is exactly `step` or `workflow`. Any other shape is a 422 at
  compile, and every door compiles the manifest.
- **No refactor of create's inline `can_run_pipeline` block into a helper.** ISS-1117 calls that optional.

## Behaviour changes a caller can see

- sync-from-file: 403 for a pipeline the tier may not run. That includes the 10 types no tier may run (`chat`, `sample_fanout`, ...), so
  enterprise now gets 403 where it got 200 before. This matches create and launch. `spec_kit` and `file_analyst` change from 422 to 403 for a
  tier that may not run them, because the gate now runs before the file read (ISS-1117 "Traps").
- A save, launch or resume whose manifest has a conditional gate that triggers a file pipeline the tier may not run: 403. Launch and resume
  use code `tier_not_entitled`. The message names the target.
- sync-from-file now depends on `get_current_principal`. A fixture that overrides only `get_current_user` gets a 401 (the
  [ISS-905](20261001-2149-ISS-905.md) shape). No test outside the card's file calls this endpoint.

## What this leaves open (recorded on existing cards, no new card needed)

- **[ISS-1114](20261008-1415-ISS-1114.md), open.** A plain row still compiles at `trust="db"` and launches under its own base type. A
  hand-written copy of an enterprise-only workflow's steps, sent through POST or PATCH, still runs. This change makes the sync door
  consistent and removes the byte-exact copy. It does not add a content-following gate. That is ISS-1114's decision.
- **Row-id trigger targets.** `run_trigger_workflow` resolves a saved row named by id (`kernel_services.py:1603-1646`) and mints it with no
  gate. The row's own trigger targets were walked at its save, which is the case from now on. A row saved before this fix, or an owner
  downgraded since, is not walked again at trigger time. ISS-1131 ("Traps") records this as ISS-1114's question.
- **Rows already stored.** For a real database, the ISS-1117 card's `SELECT` finds filled-from-file rows. The dev DB held 0 rows in
  `workflows` (`analysis-03`).

Noticed, not changed: the `user_workflows.py` module docstring still says every route uses `Depends(get_current_user)`. That was already
untrue for create and PATCH, and is now untrue for sync too. No card asked for a change there.
