## Change

Backend (60bbe040d). A finished backlog run can be revised in place. The `backlog_revision` manifest runs five steps: an Analyst writes `revisions/<n>/revision-spec.md` behind a human gate; a Planner turns it into `revisions/<n>/tasks.json`; writers apply the tasks in parallel waves; a Reviewer checks every change; the existing mechanical assembly rebuilds `backlog.md`, the CSV/JSON and `Backlog.pdf`.

- `task_source` kind `custom_path`: a wave step reads exactly one file, whose path may hold `{revision_n}`, with no fallback to the parent run's `build/tasks.json`.
- E1/E2: the revision request reaches the Analyst as a workspace message instead of re-pasting the ~1 MB backlog, and declared gates are honoured.
- E3: opt-in step key `reply: last_message` keeps only a step's final message, so narration between tool calls never reaches the review card.
- The chain payload carries a binary deliverable's text form (`backlog.md` beside `Backlog.pdf`).
- Entitlements allow the revision; `GET /workflows` returns `task_source.path`.

Verified live on backlog 78e185fb: revisions 1-5 pass, 4 and 5 clean end to end.

Composer (887ff01fc). Waves mode's Task source type gains a fourth option, "Custom path", with a path box defaulting to `revisions/{revision_n}/tasks.json`. The path survives save and reopen, and changing the source agent keeps it.

87903ab3b later set the revision workflows `user_launchable: false`: a revision starts from a finished run's chat, never from the catalog.
