# ISS-974

**INFERRED, not reproduced.** Derived while analysing QA-KB-053 ([ISS-665](20260917-1311-ISS-665.md)). Both halves of the mechanism were read in source;
the route itself was NOT called (it is a POST that launches Chromium). The per-version file sizes it would render come from the
read-only probe in `evidence/qa-kb-053/family-probe.out.txt`.

Line numbers are the working tree on 2026-10-02 (HEAD `024c03ef8`); `PreviewPanel.tsx`, `api.ts` and `run_files.py` carry uncommitted edits from other work, so their numbers can sit a few lines off HEAD. Real-data figures come from read-only GETs against the dev backend on :8000 (admin account), saved with their script in `evidence/qa-kb-053/`.

## Condition

The Files tab of a prototype-type member that is not the newest (pinned older, or opened at its own URL, see [ISS-973](20261002-0346-ISS-973.md)). The second
row, `<name>-figma.json`, exists whenever `isPrototype && prototypeContent` (`FilesTab.tsx:452-462`). Download, then confirm in the
guide modal.

## Expected vs actual

Expected: the exported Figma JSON describes that version's prototype.

Actual: it describes the newest member's `prototype.html`, because the server renders the working tree.

## Mechanism (read)

- `FilesTab.tsx:832-860` (`prototype-figma-json` branch of `handleDownload`): `html = prototypeContent || ""` (the member's own content,
  correct), then `:854` `figmaRunIdRef.current = runId ?? null`; the modal's `onConfirm` (`:1237-1240`) calls
  `exportFigmaZip(figmaHtmlRef.current, figmaStemRef.current, figmaRunIdRef.current)`.
- `frontend/src/lib/exporters/figmaExporter.ts:35-47`: with a `runId` the payload comes from `POST /api/runs/${runId}/figma-export`;
  the client-side DOM walk of the member's own `htmlContent` (`:63-67`) runs only after a 503/404/exception. So the right bytes are
  already in hand and are used only as the fallback.
- `backend/app/api/run_figma_export.py:717-749`: the signature is `(run_id, current_user)` with no `ref`;
  `chain_root_id = _resolve_chain_root_or_404(...)`, `sandbox = RunSandbox(current_user.id, chain_root_id, ...)`,
  `html_path = sandbox.path_for("prototype.html")`, rendered via `html_path.as_uri()` (`:763`). That is the working tree, the NEWEST
  member's file, for any member id in the path ([ADR-0052](20260921-ADR-0052.md) moved the export server-side).
- Secondary read, same flaw: `FilesTab.tsx:839-842` fetches `getRunSandboxFile(getToken() || "", runId, "prototype.html")` with no ref
  when `prototypeContent` is empty.

## Real data (what the route would render, read-only)

Family `463e6c0b-32de-4781-a113-6630627bd395`, member v2 `86e6bcf8-0d88-45ad-a049-d385a8bb0eeb` (`prototype_v2_revision`): its own
`prototype.html` is 86,812 B (sha256 `6a9ab9c074f3`); the working tree the route renders is 93,131 B (`787e532059c3`, v4's).

## Why the root cause implies it

Same cause as [ISS-665](20260917-1311-ISS-665.md) (a family shares one sandbox and every read defaults to the live tree) but the backend half has no ref concept
at all, so a frontend-only [ISS-665](20260917-1311-ISS-665.md) fix cannot reach it.

## Fix direction

- Backend: give the route an optional `ref`, validated with `_validate_ref` (`run_files.py:846`), read `sandbox.read_file_at_ref(safe_ref,
  "prototype.html")` and render that (Chromium needs a `file://` URI, so a temp file inside the sandbox's own scratch, removed after).
- Frontend: `exportFigmaZip(html, stem, runId, ref)` and a ref captured when the guide modal opens; the secondary read at `:842` takes
  the same ref.
- A member with no tag: skip the server path and use the client-side DOM walk of the member's own `htmlContent` (the existing
  fallback), never the live file.

## What would confirm this

Pin v2 of `463e6c0b-32de-4781-a113-6630627bd395`, Files tab, Figma row, confirm the modal, unzip the download and compare the
screens to `git show v2:prototype.html` in that sandbox; expect them to match v4's file instead. Test seam: backend unit test that
monkeypatches `_run_playwright_extraction` and asserts the file it is handed matches the requested ref; frontend test on
`figmaExporter.ts` asserting the request carries the ref.

## Resolved (2026-10-02, QA-KB-053)

Fixed by [FIX-717](20261002-1243-FIX-717.md).
- `POST /api/runs/{id}/figma-export` takes an optional `ref`, validated by `_validate_ref`.
- With a ref, the route renders `read_file_at_ref(ref, "prototype.html")` from a temp file in the sandbox's git-ignored `.browser/` scratch, and removes the file in a `finally`.
- `exportFigmaZip` sends `?ref=`. FilesTab captures the ref when the guide modal opens.
- A member with no tag skips the server path and walks its own HTML on the client.

Observed runs:
- `test_figma_export_ref_iss974.py` went from "1 xfailed" to `[XPASS(strict)]`. The marker is left for the verifier.
- The new `test_figma_export_ref_render_iss974.py` passes 3 of 3.
