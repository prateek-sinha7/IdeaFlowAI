INFERRED sibling of ISS-783 (QA-PS-037's root card), NOT yet reproduced by
clicking — found by reading the code ISS-783's fix will touch, not by a
browser repro. To confirm: open `/runs`, wait for the cold-load fetches to
settle, then click "Refresh" twice in quick succession and check DevTools
Network for two overlapping `GET /api/runs?limit=...` requests.

## Root cause — the manual refresh path is the one call site in this file with no in-flight guard

`refreshRuns` (`WorkflowHistory.tsx:267-283`) calls `setIsRefreshingRuns(true)`
and fires `getWorkflows(token, { limit: Math.max(50, runs.length) })`
unconditionally on every call — it never checks `isRefreshingRuns` on entry.
The button handler, `handleManualRefreshRuns` (`:284-287`), calls
`refreshRuns()` directly with no debounce of its own either.

Contrast with the auto-refresh timer effect a few lines below it
(`:305-309`):
```
if (runsRefreshMs && runsSecondsLeft === 0 && !isRefreshingRuns) {
  refreshRuns();
}
```
That call site DOES check `!isRefreshingRuns` before calling the same
function. The guard already exists in this file, next to this code — it
simply was never applied to the manual button's call site.

This is the same missing-dedup defect ISS-783 root-causes for this page's
mount effects (no shared cache or in-flight-request guard on `getWorkflows`
calls), reached through a different trigger: a user-initiated double-click
instead of a cold-mount effect stack. A fix that adds request
dedup/in-flight tracking inside `getWorkflows()` itself (see ISS-783's
proposed fix location, mirroring the existing `inFlightRefresh` pattern at
`frontend/src/lib/api.ts:225-233`) would close this call site too, with no
separate per-caller guard needed.

## Expected vs actual

Expected: clicking "Refresh" while a refresh is already in flight either
no-ops or reuses the in-flight request — one `GET /api/runs` per refresh
cycle.

Actual (read from code, not yet clicked): `refreshRuns` has no re-entry
guard, so two rapid clicks (or one click landing while StrictMode's
mount-time fetch is still in flight) can produce two concurrent
`GET /api/runs?limit=...` calls.

## Resolution — [FIX-616](20260922-1923-FIX-616.md)

Closed by the shared-function guard this card predicted, with no per-caller
change: `getWorkflows()` (`frontend/src/lib/api.ts:770`) single-flights
concurrent identical requests, and two rapid clicks on Refresh resolve to the
same key (`limit: Math.max(50, runs.length)` does not change between them), so
the second click joins the first request instead of opening a new one.
`refreshRuns` itself is untouched — it still has no `isRefreshingRuns` entry
check, which is now a style inconsistency rather than a duplicate-request
defect. Proven by the concurrent-call assertion in
`frontend/src/lib/api.getWorkflowsDedup.test.ts`; the browser double-click
repro described above was never run.
