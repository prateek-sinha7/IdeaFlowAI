# ISS-923

## Source

INFERRED sibling of [ISS-410](20260828-2344-ISS-410.md), derived while analyzing QA-KB-018
(analyze phase, 2026-10-01). ISS-410's root cause is that page.tsx's cold-mount seed fetch has no
state for "failed, but not a dead id": a transient failure silently leaves the page on its blank
initial state while a live Save sits on top of it. The `/workflows/{type}/canvas` effect is one of
three seed effects built on that shape. This card is the one whose consumer is, again, a live Save.

## What is suspected

`/workflows/{id}/edit` seeds the SAME `ComposerPage` from `userWorkflowsApi.get(id)` and ends its
catch like this:

```ts
// frontend/src/app/[...view]/page.tsx:3793-3808
.catch((err) => {
  if (cancelled) return;
  console.error("cold-mount workflow fetch failed:", workflowId, err);
  if (err instanceof ApiError && err.status === 401) { handleSessionExpiry(); return; }
  if (err instanceof ApiError && (err.status === 403 || err.status === 404)) {
    setWorkflowEditAccessDenied(true);
  }
});
```

A 5xx, a timeout, or a network failure satisfies none of the three branches (a response-less axios
failure is passed through as a raw `AxiosError`, not an `ApiError`: `frontend/src/store/api/http.ts:47-52`).
`initialSavedComposition` therefore stays `null` and:

- `ComposerPage` is already mounted blank (`workflow-edit` maps to "composer" synchronously,
  `page.tsx:163-165`) and is never remounted: DashboardLayout's key is
  `savedComposition?.id ?? "new"` (`DashboardLayout.tsx:3212`) and stays `"new"`.
- `initialUserWorkflowId={savedComposition?.id}` is `undefined` (`DashboardLayout.tsx:3250`), so
  ComposerPage's `userWorkflowId` is `undefined` (`ComposerPage.tsx:238-240`).
- `builtinCanvasType` is undefined, so the button reads "Save workflow" (`ComposerPage.tsx:1406`)
  and `disabled={saving}` (`:1387`) leaves it enabled.
- `handleSave` calls `saveUserWorkflow(token, undefined, ...)` (`:919`), which takes the create
  branch (`frontend/src/lib/api.ts:2648-2654`): `POST /api/user-workflows`, never the PATCH of the
  row being edited.

## Condition

Open `/workflows/<existing-id>/edit` for a workflow the user owns at a moment
`GET /api/user-workflows/<id>` fails for any reason other than 401/403/404, type a name, add at
least one agent, click "Save workflow".

## Expected vs actual

**Expected:** the failure is surfaced (error or retry), or Save is unreachable until the row has
loaded; in no case does "Save workflow" create a different row than the one being edited.

**Actual (predicted):** a new workflow is created. Two backend rules limit the damage but do not
prevent it: zero agents is a 422 (`agent_ids: list[str] = Field(min_length=1)`,
`backend/app/api/user_workflows.py:213`), and re-typing the edited row's own name is a 409
(`user_workflows.py:836-840`). A different name plus one hand-added agent returns 201.

## Why the root cause implies this

Same swallow, same live Save, different route. It matters for the FIX, not just the count:
ISS-410's agreed minimal fix (disable Save as copy while `builtinCanvasType` is set and nothing
seeded it) does NOT reach here, because on `/edit` ComposerPage has no signal that a seed was
expected. `/workflows/new` (legitimately blank, Save must stay live), a failed
`/workflows/{id}/edit` and a loaded one all mount the same "composer" view (`page.tsx:163-165`).
Only page.tsx knows `workflowEditIdFor(parsedView)` is set (`page.tsx:325-326`), so closing this
needs a signal that originates there: a seed status, or a `seedPending` prop DashboardLayout
forwards. The same signal would give both routes a visible "failed to load, reload" message of the
kind `IdeaInputPage` already shows (`loadError`, `IdeaInputPage.tsx:1114`, banner `:1996-2001`).
Design note: if a seed status is introduced, flip "ready" on SUCCESS only, never in a `.finally`:
a failed fetch must not re-enable Save. [ISS-284](20260828-1906-ISS-284.md)'s analysis reaches the
same rule for LaunchWizard (its amendment 1).

**Marked INFERRED**: not reproduced; confirmed only by reading the lines cited above. What would
confirm it: abort `GET /api/user-workflows/<id>` with `page.route`, open
`/workflows/<id>/edit`, name the workflow, add an agent, click "Save workflow", and watch for
`POST /api/user-workflows` (create) instead of a `PATCH`. What would refute it: a retry or an
error state between the fetch and the composer, which this read did not find
(`store/api/http.ts:17-54` has no retry; `page.tsx:3793-3808` has no transient branch).

### ROOT CAUSE (CONFIRMED)

One mechanism made of four facts, all read on the current tree:

1. **page.tsx has no state for "the row the URL names has not loaded".** The `/edit` effect (`page.tsx:3782-3834`) writes the
   seed in exactly one place, the `.then` (`:3799-3811`). Its `.catch` (`:3813-3828`) logs, then has two branches: 401 ->
   `handleSessionExpiry()` (`:3821-3824`) and 403/404 -> `setWorkflowEditAccessDenied(true)` (`:3825-3827`). A 5xx reaches it as
   `ApiError(5xx)` and a response-less failure as a raw `AxiosError` (`frontend/src/store/api/http.ts:47-52`); neither matches, so
   nothing is set and `initialSavedComposition` keeps its initial `null` (`page.tsx:452`). The render side is no better:
   `workflow-edit` maps to `"composer"` synchronously (`:163-165`) and the only `/edit` gate is the denied flag (`:4081-4083`);
   unlike `/workflows/{id}` (`:4097-4105`) and `/run` (`:4137-4146`) there is no loading `return null`, so DashboardLayout and
   ComposerPage mount straight onto the `null`.
2. **The conduit cannot repair it.** DashboardLayout copies a seed only when it is non-null
   (`if (initialSavedComposition) { setSavedComposition(...) }`, `DashboardLayout.tsx:1553-1557`); ComposerPage's key
   `savedComposition?.id ?? "new"` (`:3213`) stays `"new"`; `initialUserWorkflowId={savedComposition?.id}` (`:3251`) is `undefined`.
3. **ComposerPage has no signal that an edit was expected.** `userWorkflowId` starts as `initialUserWorkflowId`
   (`ComposerPage.tsx:238-240`). FIX-698's `seedUnresolved` (`:1250-1251`) is keyed on `builtinCanvasType`, so the Save button is
   `disabled={saving || seedUnresolved}` (`:1393`), which is enabled, labelled "Save workflow" (`:1418`), and its `onClick`
   guards only an empty name (`:1380-1389`). A failed `/edit` and a legitimately blank `/workflows/new` mount the same props
   (`workflow-new` and `workflow-edit` share one `"composer"` mapping, `page.tsx:163-165`), so ComposerPage alone cannot tell
   them apart.
4. **The sink takes the create branch.** `handleSave` (`:832-989`, ONE call site, the Save button, `:1391`) calls
   `saveUserWorkflow(token, userWorkflowId, ...)` (`:919`); with `userWorkflowId` undefined, `saveUserWorkflow` falls through to
   `createUserWorkflow` (`frontend/src/lib/api.ts:2648-2654`), `POST /api/user-workflows` (`:2592-2596`). Nothing in the
   request names the row being edited.

| seed state | `initialSavedComposition` | Save today | after the fix below |
|---|---|---|---|
| loading (in flight) | `null` | live, create branch | held until the row arrives |
| **transient failure (5xx, network, hung)** | `null` | live, create branch, forever | held, forever |
| dead id (403/404) | `null` + `workflowEditAccessDenied` | not-found page | unchanged |
| loaded | non-null, with `id` | PATCH of that row | enabled |
| `/workflows/new` (no id in the URL) | `null` by design | live, create | unchanged, must stay live |

### What reaches the server

The backend cannot tell this save from an intended create, so nothing there stops it. Zero agents is a 422
(`agent_ids: list[str] = Field(min_length=1)`, `backend/app/api/user_workflows.py:214`); the edited row's own name is a 409
(duplicate check `:789-797`, raise `:849-853`); a different name plus at least one hand-added agent is a 201 and a NEW row
(`:855-889`). The original row is untouched and the user is left believing otherwise; afterwards `setUserWorkflowId(resp.id)`
(`ComposerPage.tsx:936`) makes the next Save PATCH the NEW row. The create is entitlement-gated (`can_run_pipeline`, "custom
needs enterprise", `user_workflows.py:693-707`), so a lower tier presumably gets a 403 in the banner on the same click (INFERRED,
not run); the live button is tier-independent. The 201 itself is INFERRED (not run: it persists data).

### Fix: where it belongs

ComposerPage is the single Save sink and FIX-698 already put the seed gate there; what is missing is the SIGNAL, which only
page.tsx has (`workflowEditIdFor(parsedView)`, `page.tsx:325-327`). Thread it exactly like `builtinCanvasType`, and extend the ONE
existing predicate so both URL-seeded routes share it. Three small hunks, none inside the `/edit` effect:

1. `page.tsx`, one JSX line beside `builtinCanvasType={builtinCanvasType}` (`:4252`):
   `expectedUserWorkflowId={workflowEditIdFor(parsedView)}`.
2. `DashboardLayout.tsx`: optional prop `expectedUserWorkflowId?: string` (interface beside `builtinCanvasType`, `:354`; destructure
   `:508`), forwarded to ComposerPage next to `builtinCanvasType` (`:3239`).
3. `ComposerPage.tsx`: the same optional prop, and extend `seedUnresolved` (`:1250-1251`):

   ```ts
   const seedUnresolved =
     (!!builtinCanvasType && !initialManifestSteps?.length && !initialAgentIds?.length) ||
     (!!expectedUserWorkflowId && !userWorkflowId);
   ```

   The existing `disabled={saving || seedUnresolved}` and tooltip (`:1393-1400`, "This workflow has not loaded. Reload the page
   to retry.") then cover `/edit` too.

Why this shape: "ready" is DERIVED from the data landing (a row id), so a failure can never flip it and there is no `.finally` to get
wrong; it releases itself when the seed arrives (the key flip remounts ComposerPage with `initialUserWorkflowId` set);
`/workflows/new` has no `expectedUserWorkflowId` and keeps a live Save; and it reads `userWorkflowId` truthiness, never a workflow
name (SC-001 / INV-1). Prefer `!userWorkflowId` over `userWorkflowId !== expectedUserWorkflowId`: the row id is an exact-match
string (`WorkflowDefinition.id` is `Column(String)`, `_owned` filters `id == workflow_id`, `user_workflows.py:507-523`), so on
success they are equal and the extra comparison buys nothing.

The bug's triage sketch (a `loading|ready|failed` status set inside the `/edit` effect, forwarded as `seedPending` /
`seedFailed`) also works, and is the form to use if a VISIBLE "failed to load, reload" message that tells failed from loading is
wanted (precedent: IdeaInputPage's `loadError`, `IdeaInputPage.tsx:1138`, banner `:2029-2035`, copy "Failed to load this
workflow. Reload the page to retry."). It is not needed to meet the
Expected ("the load failure is shown (error or retry), OR Save is unavailable until the row has loaded"), it edits the effect
region that carries ISS-682's uncommitted `manifest:` hunk (`git diff` hunk `@@ -3778`), and it adds state that has to be kept
consistent with the data it describes. If it is done anyway, set "failed" ONLY in the `.catch` fall-through after the 401 and
403/404 branches and "ready" ONLY in the `.then`; never in a `.finally` (a failed fetch must not re-enable Save; same rule as
[ISS-284](20260828-1906-ISS-284.md)).

**Not a substitute:**

- Widening `workflowEditAccessDenied` to transient failures: turns a blip into a permanent 404, and
  `workflowDetailCatch.source.test.ts` keeps a floor of five narrowed 403/404 catches. Keep the `/edit` catch in its narrowed form.
- A retry in `userWorkflowsApi.get` or `http.ts`: hides the failure without gating the load window; none exists today
  (`http.ts:32-54`, `store/api/userWorkflows.ts:887-890`).
- **Giving the failed seed the URL id so that Save PATCHes it.** Destructive: `update_user_workflow` replaces `manifest_json`
  outright (`backend/app/api/user_workflows.py:1019-1022`) and renames the row, so a blank or hand-typed composition would
  OVERWRITE the saved workflow, which is strictly worse than the stray row this bug creates.
- A guard only inside `handleSave`, or disabling Save on `!userWorkflowId` alone: without the URL-derived signal ComposerPage
  cannot tell a failed `/edit` from `/workflows/new`, whose Save must stay live.
- A per-entry-point guard (My Workflows Edit, the read view's Edit link, a typed URL): all three converge on the one effect and
  the one button.
- A page.tsx `return null` loading gate for `/edit` (the `/run` pattern): would also remove the key-flip discard described in
  [ISS-1033](20261002-1055-ISS-1033.md), but unmounts DashboardLayout, the double-mount the built-in canvas ADR-0014
  ([20260824-1630-ADR-0014](20260824-1630-ADR-0014.md)) documents. A design call, not needed to close this bug.

## Fix (QA-KB-060, fix phase, 2026-10-07)
