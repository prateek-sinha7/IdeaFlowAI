## What was wrong

Every file-size label the Files tab renders was a character count wearing a byte unit.
Confirmed 3/3 from cold starts on `/runs/b9feac1c-ec21-4531-8ba7-bb391786993e/files`
([ISS-351](20260828-2103-ISS-351.md)): `prompt.md` declared "620 B" against 626 real bytes,
`01-presentation-strategist-agent.md` "9.5 KB" against 9845 bytes, `02-deck-engineer-agent.md`
56398 against 56564, `04-pptx-code-generator.md` 29459 against 29584. The declared numbers
matched the content's UTF-16 code-unit count exactly; the Download button delivered the larger,
true file. This pipeline's LLM output routinely carries em dashes (`—`) and arrows (`→`) — 3 UTF-8
bytes, 1 UTF-16 unit each — so the understatement is the normal case, not an edge case.

Three sibling surfaces made the identical arithmetic mistake inline, found by grepping the
pattern rather than by call-graph (none of them calls `formatSize`):
[ISS-587](20260829-0257-ISS-587.md) the Prototype Preview source-view "X KB",
[ISS-588](20260829-0257-ISS-588.md) the App Builder file-explorer "X KB total" (a SUM, so the
error compounds with file count), and [ISS-589](20260829-0257-ISS-589.md) the custom-template
loader — which is worse than cosmetic: its "max 2 MB" upload gate was tested against the decoded
string's `.length`, and a UTF-16 unit count is always ≤ the UTF-8 byte count, so an over-cap file
was wrongly ACCEPTED. That one is a validation bypass, not a mislabel.

## Root cause

`String.prototype.length` counts UTF-16 code units, not UTF-8 bytes. Every site fed that number
to something that means bytes.

`frontend/src/components/results/FilesTab.tsx` — `formatSize` itself (`:1121`) is a correct
bytes→`B`/`KB`/`MB` formatter; all 11 of its callers passed a character count:

```ts
size: formatSize(agent.output.length),   // :546 (pre-fix)
```

Call sites (pre-fix line numbers): 103, 116, 236, 393, 401, 418, 426, 546, 572, 616, 649. The
twelfth call, `formatSize(file.size)` at `:447`, was already correct — `file.size` is the
backend's real `SandboxFile` byte count — and it self-corrected exactly ONE row
(`derivedFiles[0]`, the Final-output row) and only when `resolveRunDeliverable` matched a
workspace file. Every other row had no such correction.

The three siblings were independent inline occurrences, not callers of the broken function:
`PrototypePreview.tsx:565`, `AppBuilderPreview.tsx:570`, and `CustomTemplateModal.tsx:80` (the
cap gate) / `:232` / `:267`.

## What changed and why there

Fifteen sites, one mechanism — so the fix is one function, not fifteen expressions. New
`frontend/src/lib/byteSize.ts`:

```ts
const encoder = new TextEncoder();

export function utf8Bytes(text: string): number {
  return encoder.encode(text).length;
}
```

No such helper existed under `frontend/src/lib/` (nearest precedent was `resizeImage.ts`'s
`approxBase64Bytes`, which is base64-specific). Every offending site now calls it:

- `FilesTab.tsx` — all 11 `formatSize(x.length)` → `formatSize(utf8Bytes(x))`. `:448`'s
  `formatSize(file.size)` deliberately untouched: it already carries real API bytes, and wrapping
  it would be wrong.
- `PrototypePreview.tsx:566` — `(utf8Bytes(renderedHtml) / 1024).toFixed(1)` KB. The
  `· N lines` half of the same label is a genuine line count and was left alone.
- `AppBuilderPreview.tsx:571` — the footer reduce sums `utf8Bytes(f.content)`. `{visibleFiles.length}
  files` is a file count, untouched.
- `CustomTemplateModal.tsx:233,268` — both "Loaded/Fetched X KB" labels use `utf8Bytes(htmlBody)`.
- `CustomTemplateModal.tsx:81` — the cap gate now reads the `File` object's own byte size,
  `if (file.size > 2 * 1024 * 1024)`, rather than re-measuring the decoded string. `file` is
  already in closure scope at that point; the authoritative byte count was sitting unused one
  variable away. This is the ISS-589 validation bypass, closed at the trust boundary.

Deliberately NOT changed: `AccountSettings.tsx` and `StartingPointCard.tsx` label `.length` as
"chars", which is correct as written; `SandboxTab.tsx`, `ChatAttachments.tsx` and
`useChatAttachments.ts` already use real byte sources.
