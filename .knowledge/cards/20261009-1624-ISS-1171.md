# ISS-1171

**Register source:** sibling derived during the `QA-KB-110` analysis on 2026-10-09 (root [ISS-1154](20261009-1340-ISS-1154.md)). Not its own bug row; it is a second consequence of the same hand-off in `handleEditBrief`, so it is fixed in the same function.

**Confidence.** CONFIRMED offline up to the staging: probe `[E]` in `evidence/qa-kb-110/analysis-01-probe-remount-loses-pendinghomebrief.txt` drives the real `DashboardLayout.handleEditBrief` and the real `parseViewPath`, and records what is staged and where the push lands. INFERRED: the leak itself (a later wizard open restoring the orphan), and what a user sees on the revision's own panel. Nobody clicked it live.

## Condition

A failed run whose `type` ends in `_revision`. The failed lane does not look at the type (`RunChatLane.tsx:1804`, `if (pipelineState?.failed)`), so the same two buttons render; the secondary one calls `handleEditBrief` (`RunChatLane.tsx:1941-1942`). The dev database holds two such runs, both `prototype_revision`: `b7bdf6a3-2ae9-48f6-867e-dbfb61b9f570` (parent `0f62f7bc-d3a2-4748-8004-0b534e1741ae`) and `97b49f98-83bd-4ed6-8631-600bf9653905` (parent `87e02c32-96a9-4e50-8ed0-79023d83540f`), `evidence/qa-kb-110/analysis-03-dev-runs-failed-by-type-and-e2e-fixture-pick.txt`.

Inside `handleEditBrief` (`DashboardLayout.tsx:2399-2442`) two decisions are made from two different keys:

1. The wizard slot comes from the BASE type: `const reviseBase = baseWorkflowType(effectiveReviseType)` (`:2404`), and `baseWorkflowType` only strips a trailing `_revision` (`workflowChaining.ts:24-27`). For `prototype_revision` that is `prototype`, so `draftKey` resolves to `"prototype.draft"` (`:2422-2423`) and the brief is written there (`:2424-2426`).
2. The route comes from the FULL type: `router.push(createRouteForType(effectiveReviseType))` (`:2428`), here `/create/prototype_revision`.

That URL parses to `{ screen: 'create-workflow', pipelineType: 'prototype_revision' }` (`routes.ts:309`), and `wizardModeFor` returns a mode only for the exact ids `ppt_v2` and `prototype_v2` plus the two named screens (`page.tsx:349-366`). So the push renders the plain brief panel (IdeaInputPage inside DashboardLayout), not the wizard that owns `prototype.draft`.

## What the probe shows

Block `[E]` of the default run (HEAD `01777a107`):

| failed run type | pushed to | staged in sessionStorage | wizard? | remounted brief |
|---|---|---|---|---|
| `ppt_revision` | `/create/ppt_revision` | `ppt.draft` | no | empty |
| `prototype_revision` | `/create/prototype_revision` | `prototype.draft` | no | empty |
| `prototype_v2_revision` | `/create/prototype_v2_revision` | `prototype.draft` | no | empty |
| `prototype_v2_feature_revision` | `/create/prototype_v2_feature_revision` | nothing (base `prototype_v2_feature` is not in the table) | no | empty |
| `backlog_revision`, `user_stories_revision` | `/create/<type>` | nothing | no | empty |

The first three rows are the finding: a draft is written for a destination that does not read it. The mutation run (`analysis-02`) applies the candidate fix of the root card, which adds a default slot, and leaves exactly these three rows empty, because the slot is still chosen from the base type.

## Expected vs actual

Expected: whatever "Edit brief & run again" means on a revision run, the brief goes to the surface the push actually lands on, and nothing is left behind for a surface the user did not open. Actual: the brief is staged for a wizard, the user is sent somewhere else, and `ppt.draft` or `prototype.draft` stays in `sessionStorage` until some wizard mounts.

## Why the root cause implies it

[ISS-1154](20261009-1340-ISS-1154.md) is "the hand-off channel is chosen without reference to where the push lands". This is the same sentence for the wizard half: the slot table and the route are computed separately, and [FIX-582](20260922-0915-FIX-582.md) already named that drift as the cause of the first blank composer ("the two tables drifting apart"). It fixed `prototype_v2` and left the `_revision` spelling, which `baseWorkflowType` folds into the base for the slot and nobody folds for the route.

## The INFERRED part, and what would settle it

LaunchWizard's restore effect reads `draftKeyFor(initialMode)` on every mount, applies `brief` (`LaunchWizard.tsx:449-451`, `:461`) and removes the key only after it has processed the draft (`:490-492`). Nothing ties the draft to the navigation that wrote it. So the next fresh open of the ppt or prototype wizard, from the Home tile or `/create/prototype`, should show the revision run's brief. To settle it: open the failed `prototype_revision` run `b7bdf6a3-...`, click "Edit brief & run again", then open Home and "Build a prototype", and read the brief field. No run is launched by either step.

Second, separate question, not decided here: `GET /api/workflows` lists every `*_revision` workflow as `user_launchable: False, is_beta: True` (`evidence/qa-kb-110/analysis-05-workflows-user-launchable-flags.txt`), so `/create/<x>_revision` is a launch panel for a workflow the catalog does not offer. Whether "Edit brief & run again" belongs on a failed revision at all, and what it should open, is the owner's to say. It does not block the root fix.

## Fix direction (INFERRED, not applied)

Compute the destination once and derive both the slot and the route from it. The slot must exist only when the route is the wizard that reads it, which is the data `wizardModeFor` and `LaunchWizard`'s `STEPPER_MODE` already hold; no new workflow-name branch. Whether a revision run opens its base composer or something else is the product question above; the minimum is that no draft is staged for a destination that will not consume it.

## Resolution ([FIX-777](20261009-1651-FIX-777.md), 2026-10-09)

The "Fix direction" minimum, in the root's function. The slot table in `openComposerWith` is indexed by `effectiveReviseType`, the same
value `createRouteForType` builds the route from, instead of `baseWorkflowType(effectiveReviseType)`, and a type with no wizard slot
falls back to `"idea.draft"` (`DashboardLayout.tsx:2432-2434`). So `ppt_revision`, `prototype_revision` and `prototype_v2_revision`
stage `"idea.draft"`, which the remounted `/create/<x>_revision` panel reads and clears; no `ppt.draft` / `prototype.draft` is left for a
later wizard. The card's three ISS-1171 cases XPASS; the probe on the fixed source shows the brief on every revision type's panel
(`evidence/qa-kb-110/fix-01`, `fix-02`). The route itself is unchanged: the "Second, separate question" above (should a failed revision
offer this button, and open what) is still the owner's and is NOT answered by this fix.
