## Source

Validated from register entry `BUG-20260828-073900-workflows-id-run-r2` in
`bug-hunter/ledger.md`.

## Reproduction (3/3, cold start)

Reproduced on **all 3 cycles**, each a fresh navigation to
`http://localhost:3000/workflows/656ca387-e69c-474d-b7ff-5fd9eb017cc0/run` (deep-link entry, not
click-through):

- Cycle 1: plain `page.goto` to the route with no interception. Generic wizard rendered.
- Cycle 2: repeat plain `page.goto`, same result.
- Cycle 3: `localStorage`/`sessionStorage` fully cleared (re-seeding only `auth_token`), then
  navigated to `/dashboard` and to the route again. Same result.

No artificial network delay (`page.route` + `waitForTimeout`) was needed to reproduce in this
environment — the race is deterministic on a plain load/reload of this URL. The hunter's original
report used an artificial delay to make the causal mechanism explicit; this validation pass
confirms it reproduces without one too.

Confirmed via `browser_network_requests` on cycles 1 and 3 that
`GET http://localhost:8000/api/user-workflows/656ca387-e69c-474d-b7ff-5fd9eb017cc0` returned
`200 OK` on every cycle (also confirmed directly via `curl` with a fresh qa-admin JWT, returning
`name: "My prototype"`, `agent_ids: ["documentation-agent","prototype-specify"]`,
`overrides_pipeline_type: "prototype"`). `GET /api/workflows/prototype` (the generic base type)
fires alongside it. No console errors on any cycle.

## Page / route / component

- Page: saved workflow's launch panel.
- Route: `/workflows/{id}/run`.
- Component: `frontend/src/components/workflow/LaunchWizard.tsx` — the spec-016 override-fetch
  `useEffect` (around line 357, "fetch this user's override of the built-in, if any"), rendered
  through `frontend/src/app/[...view]/page.tsx`.

## Exact conditions

qa-admin (enterprise tier), default light theme, deep-link entry path (direct navigation/reload
to the URL rather than click-through from another screen), no run in progress — this is the
launch/configure screen prior to any run starting. Conditions were not what flipped the repro
here: it reproduced identically across cold, warm-storage-cleared, and repeat-visit variants.

## Expected vs actual

**Expected:** the panel applies the override response whenever it resolves (or waits for it)
regardless of which of the two parallel fetches (`GET /api/user-workflows/{id}` vs
`GET /api/workflows/{base_pipeline_type}`) settles first — rendering "My prototype"'s name,
description, and saved template/agent configuration.

**Actual:** whichever of the two parallel fetches is *not* first to resolve is discarded. The
panel renders h1 "Configure your prototype" under a "NEW PROTOTYPE" heading, with "No template" /
Blank Canvas selected — no trace of "My prototype", its description, or its saved
template/agent binding anywhere in `document.body.innerText` — and this binding never
self-corrects even after the override response is confirmed to have arrived successfully.

## Distinct from ISS-183

`ISS-183` covers `ComposerPage.tsx` hardcoding `base_pipeline_type: "custom"` on the full-canvas
editor at `/workflows/{id}/canvas` — a deliberate design tradeoff around a shared mutable. This
card is a different component (`LaunchWizard.tsx`, the two launch surfaces, not the composer) and
a different symptom: a render-binding race that silently discards a successfully-fetched override
response, not a hardcoded outbound field on save.

## Root cause (analyzer pass, CONFIRMED via source read)

The mechanism is NOT a network fetch race between the two observed GET requests (their arrival
order is not what decides the outcome — the original framing above, "the non-first-to-resolve
response is discarded," describes the observed symptom accurately but not the true cause). It is
a synchronous same-commit React effect-ordering bug entirely internal to
`frontend/src/components/workflow/LaunchWizard.tsx`, which is why it reproduces deterministically
with no artificial delay:

- `LaunchWizard.tsx:278-324` ("restore session draft") reads the `{mode}.draft` sessionStorage
  payload the caller wrote (from `GET /api/user-workflows/{id}`, staged by
  `frontend/src/app/[...view]/page.tsx:3606-3699`'s cold-mount effect) and, once
  `libraryAgents.length > 0`, maps `d.agentIds` to `AgentDef`s and calls
  `setPipelineAgents(restored)` (`:303-307`) — this is what actually applies the saved override's
  real agent roster.
- `LaunchWizard.tsx:335-338` ("re-derive once real agents arrive") fires on the SAME
  `libraryAgents` transition (it shares that dependency) and reads `pipelineAgents.length` from
  the SAME render's closure — i.e. the value from BEFORE the effect above applied its update
  (React does not let one effect observe a sibling effect's `setState` call within the same
  commit). It therefore always sees `0` and unconditionally calls
  `setPipelineAgents(defaultAgentsFor(libraryAgents, mode))` (`:337`) — the generic per-pipeline
  library roster.

Both effects issue a plain-value `setState` (not a functional updater), and the second effect is
declared — and therefore always runs — after the first, in the same passive-effect flush. Its
call is enqueued last and wins, silently discarding the just-restored override roster every time.
`frontend/src/hooks/useAgentLibrary.ts:16-20` documents `libraryAgents` as Redux state "populated
by GET /api/agents/library via the listenerMiddleware on app boot," starting from an empty array —
so on a cold direct navigation to `/workflows/{id}/run` (as opposed to in-SPA click-through) it is
guaranteed to be empty on `LaunchWizard`'s first render, guaranteeing this exact race fires on
every cold mount. This also explains the "Advanced 2 agents" coincidence noted in the bug report:
`defaultAgentsFor` (`:147-149`) filters the FULL agent library down to the `prototype` pipeline's
default roster, which happens to also be 2 agents, but not `documentation-agent` /
`prototype-specify`.

**Fix belongs in `LaunchWizard.tsx`, not either caller**: both `frontend/src/app/[...view]/page.tsx`
and `frontend/src/components/layout/DashboardLayout.tsx` (see [ISS-283](20260828-1905-ISS-283.md))
already write a correct draft: the defect is entirely in having two independent effects race to
set the same state off the same trigger. The smallest correct fix is to fold `:335-338`'s recovery
logic into the same effect as `:278-324` (single source of truth for "was pipelineAgents actually
restored"), not to special-case either caller.

See [ISS-283](20260828-1905-ISS-283.md) (same race, reached via click-through Run) and
[ISS-284](20260828-1906-ISS-284.md) (Save/Save-as-override persisting the clobbered roster back to
the server) for the derived blast radius.

## Fixer pass (2026-08-28) — root cause fixed, card left open

[FIX-338](20260828-2221-FIX-338.md) closes the effect race described above:
`LaunchWizard.tsx`'s "re-derive once real agents arrive" effect now tests emptiness inside
`setPipelineAgents((prev) => ...)`, so it observes the draft-restore effect's queued update
instead of the stale render closure and stops clobbering the restored roster.

This card is NOT marked resolved: its own verification test still fails. Both scenarios in
`tests/integration/e2e/suites/05_saved_workflows/test_iss228_launch_panel_override_binding.py`
assert `'My prototype' in document.body.innerText`, and after the fix they still fail on exactly
that assertion and nothing else — because the panel never renders a saved workflow's name at all,
race or no race. That half of this card's **Expected** is a separate presentation gap, now filed
as [ISS-384](20260828-2221-ISS-384.md), and closing it is a UI decision no card covers.
