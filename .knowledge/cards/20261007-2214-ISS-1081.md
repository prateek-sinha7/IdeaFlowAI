# ISS-1081

> **INFERRED sibling** of [ISS-899](20261001-2129-ISS-899.md), derived during the QA-KB-072 analysis (2026-10-07). Every code fact below
> was READ on the working tree (branch `feat/stale-bug-fixes`, HEAD `e93aa40ed`, no `backend/` edits against HEAD) and is CONFIRMED. The
> INFERRED parts are the user-visible effect (nothing in the UI changes after the call) and whether this is a defect at all. The 200 is
> pinned by an existing test, so this is a lead for the owner, not a regression.

## Condition

A client posts `action: "redo"` for a review gate whose firing published `redoable: false`. That is any declared `gates: [human]` step
without `redoable: true` (the manifest default), and any per-task build dispatch ([FIX-500](20260831-1644-FIX-500.md)'s case). The FE
never offers the button there, so the callers that can still send one are the Concierge (`propose_gate_action("request_changes")`, mapped
to `redo`), the chat-message route and a scripted client.

## What the code does (CONFIRMED, read)

- **Engine.** `engine.py:12530-12538`: with `redoable=False` the primitive logs "Review gate redo REFUSED ... gate stays open (ISS-090)",
  calls `event.clear()` and `continue`s. It yields nothing, so no event reaches the wire. The only trace is a WARNING log line.
- **The three ingresses write the redo response and report success without asking whether the gate offered redo.**
  - `run_commands.py:307-310`, POST /gate: `if action == "redo": await store.set_review_response(...)`, then
    `return {"ok": True, "action": action, "gate_key": gate_key}` (`:343`).
  - `run_commands.py:1598-1601`, the Concierge `gate_action` disposal. `request_changes` is mapped to `redo` by
    `_CONCIERGE_GATE_ACTION_MAP` (`:1246`, used at `:1596`). It replies `{"channel": ..., "disposed": "gate", "action": "redo"}` (`:1622`).
  - `run_commands.py:1946-1949`, POST /messages with `CHANNEL_GATE`.
- **The `update_specs` branch of the same three chains has a fence.** `_review_gate_advertises_update_specs(gate_key)` raises a 409
  (`run_commands.py:316-317`, `:1604-1605`, `:1953-1954`; the helper is `run_engine.py:887`). Its docstring gives the purpose:
  "so an ingress can answer a caller with a 409 instead of a silently-ignored 200" (`run_engine.py:893-894`). The deny helper says
  "Raised by ALL THREE set_review_response ingresses so no channel is privileged" (`run_commands.py:192-194`). The engine comment calls
  that layer the "caller feedback" and its own refusal "the LAST line of defence" (`engine.py:12568-12572`).
- **Redo has no counterpart.** `grep -rn "_review_gate_advertises" backend/app` lists only the `update_specs` helper and its three uses.
- **The Concierge cannot tell.** `_derive_progress` records only `open_gate = "review"` from the event type (`concierge.py:258-259`),
  `_gate_intent` accepts `request_changes` for any gate and degrades an unrecognised action to it (`concierge.py:80`, `:369-377`), and the
  open-gate prompt text mentions only approval (`concierge.py:1299-1304`).
- **The 200 is pinned.** `tests/integration/test_gate_redo_enforcement.py:205-210` asserts `actions == ["redo", "approve"]` and that
  every POST returns 200. Observed on this tree: `2 passed in 0.96s` (`evidence/qa-kb-072/08-analyze-anchor-tests.txt`).

## Why the root cause implies it

[ISS-899](20261001-2129-ISS-899.md)'s test hung because a refused redo gives its caller no signal: the test assumed the redo ended the
interaction, and the gate silently stayed open. The ingresses are the production callers of that same silent refusal. ISS-090 explained
the absence of an ingress layer with "The FE never offers Redo when the flag is False, so nothing legitimate arrives here"
(`engine.py:12522-12523`). The Concierge and a scripted client reach the engine without the FE button, so that premise does not hold
for them. [ISS-053](20260811-2101-ISS-053.md) judged the same silence unacceptable for `update_specs` and fenced all three ingresses.

## Expected vs actual

- Expected (INFERRED, the owner decides): the caller learns the redo was not honoured, as it does for an ineligible `update_specs`, or
  the Concierge does not propose `request_changes` at a gate that did not offer it.
- Actual: a success reply, no event, no state change. The user stays at an open gate and can still approve or reject, so the failure is
  closed and nothing is lost. The Concierge disposal reply reports `"disposed": "gate"` (`run_commands.py:1622`). What the FE shows the
  user for that reply was not read, which is part of why this is INFERRED.

## What would settle it

- The `/gate` half is already observed (`test_gate_redo_enforcement.py`). The other two ingresses can be driven the same way: use
  `_drive_gate_over_http`'s shape with a `redoable=False` gate and POST the `/messages` route and the Concierge disposal. Assert a 200
  and that no new event follows while `store.review_event_pending(gate_key)` stays True.
- User-visible effect: at a declared `gates: [human]` step with `redoable` absent, ask the Concierge for changes, confirm the chip, and
  watch the run. INFERRED prediction: it stays paused with no new event. Not run, because the analysis phase drives no browser.
- Whether it is a defect: the owner's call. If the log-only refusal is the intended contract, close this as won't-fix.

## Fix shape and the decision it needs (not binding)

Options, each with its consequence:

1. **Mirror the `update_specs` fence.** Add `_review_gate_advertises_redo(gate_key)` beside `run_engine.py:887`, reading `redoable` off the
   same `review_gate_ready` row (abstain True when the row or key is missing, as the existing helper does), and raise a 409
   `redo_not_offered` from the three ingresses. Consequence: this changes the contract `test_gate_redo_enforcement.py:209-210` pins, so
   that test must expect the 409 on the first POST, and any client that posts redo blind starts getting errors.
2. **Keep the 200, make the refusal visible.** Add a field to the reply or an event. Consequence: a contract addition on all three
   channels.
3. **Fix the Concierge only.** Carry the published `redoable` into its run context and withhold `request_changes` at a gate that did not
   offer it. Consequence: scripted clients stay silent; the Concierge stops proposing a dead action.
4. **Leave it.** The FE hides the button and the engine fails closed.

Land [ISS-899](20261001-2129-ISS-899.md) first. It is test-only and independent of this card.
