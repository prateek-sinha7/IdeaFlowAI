# ISS-1016

## Description

Sibling of [ISS-902](20261001-2144-ISS-902.md) (bug QA-KB-075), derived from its root cause rather than reported independently.

ISS-902's root cause is a blind spot. The four tails of `test_reconcile_degraded_tracks_latest_completion_only` read the same
under the live rule and the dead one, so a comment can describe the wrong rule and nothing fails. [ISS-886](20261001-2114-ISS-886.md)
set the standard that closes such a gap: each FIX-484 scoping needs a tail that goes red when only that scoping is reverted.
[FIX-689](20261001-2142-FIX-689.md) added T5-T7 for ISS-436, ISS-437 and ISS-435. [FIX-484](20260902-1600-FIX-484.md) scoped one
more place, the `completed` rung of the ladder, and nothing locks it.

**Condition.** A durable tail where an EARLIER attempt reached a terminal `pipeline_complete` (degraded or clean) and the LATEST
attempt, after the last `run_resuming` / `pipeline_start`, ended without any terminal event:

`pipeline_start 1, pipeline_complete{degraded} 2, run_resuming 3, pipeline_start 4, agent_start 5` (T8; T9 is the same with a clean
completion at 2).

**Expected.** `failed`. The docstring (`backend/app/api/run_commands.py:805-809`) says a `pipeline_complete` at or after the last
boundary with no `pipeline_failed` at or after it is `completed`, and "anything else / no clean terminal → ``failed`` (the D2
fail-safe)". `backend/app/api/run_shutdown.py:330-333` relies on it: "no clean terminal → ``failed`` — either way TERMINAL, so no boot
re-adopts it."

**Actual.** The live code gives `failed` (measured below), so there is no product defect today. What is missing is a guard: no
existing test goes red if the rung is reverted, and the reverted rung reads `completed` for the condition above.

## Why the root cause implies it

- It is the same blind spot as ISS-902, one rung over: the tails in this function's tests do not discriminate the scoped rule from the
  un-scoped one on this dimension.
- The comment above tail 4 (`test_restart_resume_db.py:4362-4363`) names the scenario: "No pipeline_complete at all — a resume that
  stopped again before producing any new terminal event." Tail 4 is `[("pipeline_start", 1, {}), ("agent_start", 2, {"agent_id": "w"})]`
  (`:4365`): one attempt and no earlier terminal event, so "new" has nothing to be new relative to. The tail reads `failed` under the
  un-scoped rung too (T4 column), so the comment promises coverage the tail does not deliver. T8 and T9 build the scenario the
  comment describes.

## Why it is reachable (INFERRED for the exact production sequence; the tail itself is measured)

- A degraded run is resumable. The incident behind this test file was exactly that: run 4bdf9398 failed, a resume degraded on
  credential expiry, the next resume completed (`test_restart_resume_db.py:4316-4318`).
- `stop_run_driver` runs the reconcile once it has cancelled the driver (`run_shutdown.py:351-353`), and `run_commands.py:4405-4412`
  ([ISS-124](20260812-1852-ISS-124.md)) records that the D2 fail-safe is what that path lands on when the tail has no terminal event
  ("took its D2 fail-safe → the owner's Stop was recorded as ``failed``"). On a resumed run whose first attempt completed, the
  un-scoped rung would record `completed` for an interrupted attempt. No run was started to reproduce that sequence.
