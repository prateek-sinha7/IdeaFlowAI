# ISS-681

## Status: found by the 5-fixer, mechanism observed in a scratch test, not fixed

Found while making the run store outlive a page remount
([FIX-523](20260917-1555-FIX-523.md)). FIX-523 keeps the defect from reaching users across a
remount. It does not change the reducer, so the defect is still there inside a single page mount.

## Mechanism (`useWorkflow.ts`, line numbers as of FIX-523)

A full durable replay into an entry that already holds a finished run does this:

1. The replayed `pipeline_start` names the same run, so it counts as a re-announcement
   (`isSameRunReannounce`).
2. `agentStartEventIds` is carried only when `prev.isRunning` is true (`:557`, FIX-222). A
   finished run has `isRunning: false`, so the restart history is reset to `{}`.
3. `lastAppliedSeq` is carried for any re-announcement (`:563`, ISS-082).
4. `isRedelivery` (`:274-279`) now treats every replayed `agent_start` (seq at or below the
   cursor) as already applied and skips it.
5. `agentStartEventIds` stays empty, so `deriveSpecRevisionCount` returns 0 and the "Spec Revision
   Cycle" banner (ISS-063) disappears.

Observed on the pre-FIX-523 store with a scratch vitest (run once, then deleted): one store
instance, a finished run with one revision replayed twice. The count was 1 after the first replay
and 0 after the second. The same double replay of a still-running run left every field identical.

## Reachability

- **Across a remount:** closed by FIX-523. Finished entries are dropped on unmount, and an
  unmounted page's late replay writes to a throwaway entry. The
  `useRunStateStore.remountLifetime.test.tsx` cases fail without those guards.
- **Within one mount:** only a second full replay of an already-finished run, with no remount in
  between, reaches it. Every reopen click this fixer read calls `router.push`, which remounts
  (`DashboardLayout.tsx:2691, 2745, 2839, 2899`). The remaining case is a race: a live run's
  `pipeline_complete` lands before a replay of that same run that is already in flight.

## Fix direction (not decided)

Treat a `pipeline_start` whose `seq` is at or below `prev.lastAppliedSeq` as a re-delivery. Keep
the restart history in that case, and apply FIX-222's reset only to a genuinely new
`pipeline_start` (a resume). This changes the reducer's re-announce contract (ISS-063/080/082,
FIX-222), so it needs its own tests.
