## What was wrong

`BUG-20260828-005700-workflows-ppt-canvas`: opening the `ppt` built-in at `/workflows/ppt/canvas`
showed "Streamed text — agent's raw output" in the Workflow tab even though
`GET /api/workflows/ppt` declares `deliverable: {"strategy":"ppt","name":"presentation.pptx"}`,
and "Save as copy" then POSTed a body with **no `manifest` key at all**, so
`workflows.manifest_json` persisted `NULL` — the copy of a PPTX-producing workflow became a
generic streamed-text/markdown one, with no in-UI signal anything was lost.

## Root cause

Two coupled defects in `frontend/src/components/workflow/composer/ComposerPage.tsx`, both named by
[ISS-206](20260828-1609-ISS-206.md):

1. **The save gate could not see the Workflow tab.** `needsFullManifest(agents)`
   (`ComposerPage.tsx:51-60` pre-fix) is a pure function of the NODE list —
   `isCustom`/`prompt`/`skills`/`children`/`route.outcomes` — and it is the sole decision at
   `ComposerPage.tsx:628` for whether `handleSave` sends
   `{manifest: buildWorkflowManifest(pipelineAgents, capabilities, selections, runConfig)}`.
   `buildWorkflowManifest` (`frontend/src/store/api/userWorkflows.ts:397-399`) is the ONLY place
   `runConfig.deliverable`/`planner`/`clarify` is folded into a save. A built-in's three stock
   agents fail every node check and `selections` is `{}`, so the body resolved to `{}` and the
   deliverable never reached the wire — regardless of what the Workflow tab held.
2. **`runConfig` had no resync effect.** It was seeded once by a plain `useState` initializer
   (`ComposerPage.tsx:335-341` pre-fix) falling back to `{streamed_text, output.md, planner:skip,
   clarify:skip}`. Its siblings `pipelineAgents` and `selections` each carry a dedicated
   re-derive effect for exactly this race (`:250-269`, `:305-329`); `runConfig` never got one.
   For a built-in the race is real: `frontend/src/app/[...view]/page.tsx:437-485` fetches the
   real manifest asynchronously and builds `savedComposition.runConfig` from `detail.deliverable`,
   but `page.tsx:448-451` deliberately omits `id` (a built-in has no `WorkflowDefinition` row), so
   `DashboardLayout.tsx:2906`'s `key={savedComposition?.id ?? "new"}` remount never fires and the
   correct `initialRunConfig` (`DashboardLayout.tsx:2943`) never reached state.

Fixing only one leaves the bug half-alive: (2) alone corrects the display while Save still omits
`manifest`; (1) alone serialises a `runConfig` still stuck on the wrong default.

## What changed and why there

All three edits are in `ComposerPage.tsx` — the single component every affected path
(built-in copy, from-scratch save, re-save, Run once) already routes through:

- **`DEFAULT_RUN_CONFIG` + `runConfigIsFromScratchDefault` + `needsFullManifestOnSave(agents,
  runConfig, builtinCanvasType, initialManifestSteps)`** (new, beside `needsFullManifest`).
  The save gate now also fires when the canvas was seeded from a real manifest (a built-in via
  `/workflows/{type}/canvas`, or a saved row's `initialManifestSteps`) or when the Workflow tab
  differs from the from-scratch default. `needsFullManifest` is unchanged and still used for the
  node-shape question it actually answers. The hardcoded default literal now exists once, so the
  state seed and the comparison cannot drift.
- **`handleSave`** calls the new gate; `builtinCanvasType`/`initialManifestSteps` added to its
  `useCallback` deps.
- **`seededRunConfig` effect** — mirrors `seededFromManifest`: adopt the first real
  `initialRunConfig` that arrives, once, after which the user's own Workflow-tab edits own the
  state. This is what cures [ISS-205](20260828-1612-ISS-205.md) too, since Run-once's
  fallthrough reads `runConfig?.deliverable` (`ComposerPage.tsx:759` pre-fix) once a reorder has
  flipped `unmodifiedBuiltin` to false.

**Deliberately NOT changed:** the second `needsFullManifest` call site inside `handleRunOnce`
(the steps/`user_workflow_id` decision). ISS-206's fix note suggests widening both sites "so the
two can't drift", but that site answers a different question — Run already sends
`deliverable`/`planner`/`clarify` unconditionally as top-level `extraParams`, so the Workflow tab
has no bearing on it, and ISS-205 states the run defect is "purely the VALUE that is wrong, not
whether it is sent". Widening it would make a reopened saved workflow launch from its stored
manifest (`user_workflow_id`, trust="db") and silently ignore roster edits the user had not saved
yet — a new defect. An in-code comment at that site records the reasoning.

## Known edge introduced

A composition with **zero** agents and a non-default Workflow tab now sends
`manifest: {steps: []}`, which `backend/app/api/user_workflows.py::_validated_manifest` rejects
with a 422 ("'steps' must be a non-empty list") rendered inline as `saveError`. Previously such a
save silently created an empty, manifestless row. Saving an empty composition was already
meaningless; the new failure is loud rather than silent, and no card asked for a node-count guard.
