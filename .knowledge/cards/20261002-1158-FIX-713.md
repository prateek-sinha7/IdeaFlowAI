# FIX-713

## What was wrong

This is bug report QA-KB-050. The root cause and blast radius come from the analysis on
[BUG-025](20260827-BUG-025.md) and are not re-derived here.

`ComposerPage` handed `getRole` (and six other reads) the `workflowType` prop, which is DashboardLayout's
shared, mutable state. On `/workflows/new`, `/workflows/{id}/edit` and `/workflows/{id}/run`,
`initialWorkflowTypeFor` supplies no type, so it is the `"user_stories"` default. `getRole(id, "user_stories")`
returns `locked` for domain-analyst and backlog-compiler and `required` for four more. Both renderers then
badged `role === "locked"` but locked Remove on `role !== "optional"`, so a `required` agent had a disabled
Remove and no badge. On the Canvas that dead control was also invisible (`disabled:opacity-0`).

## What changed, and why there

Line numbers are the working tree after the change.

1. **`ComposerPage.tsx:650-655`: the composer derives its own type once.**

       const canvasPipelineType = (builtinCanvasType || "custom") as WorkflowType;

   All eight code reads of `workflowType` now read it:
   - `:658` `defaultAgentIds`, the root-agent cap exemption ([ISS-965](20261002-0319-ISS-965.md))
   - `:676`, `:679` the Simple-view drag guard
   - `:800`, `:805` brief recommendations and the companion banner ([ISS-964](20261002-0319-ISS-964.md))
   - `:1437` CanvasView, then every CanvasNode (BUG-025, [ISS-961](20261002-0319-ISS-961.md))
   - `:1636` AgentRow
   - `:1673` HooksTab (accepted there, never read)
   - `:1713` AgentLibrary `currentPipelineType`, its default tab and the HIDDEN_FROM_CUSTOM filter
     ([ISS-962](20261002-0319-ISS-962.md))

   The prop stays, and is read only by the mount log (`:298`). Its doc (`:119-121`) now says so, so nobody
   reaches for it as the composer's identity again. `DashboardLayout.tsx` and the test mounts are untouched.

   **Why here.** Every composer route mounts this one component. Deriving the type here covers every source of
   staleness: the remount default, a saved row stamped with a stale base type, and any of DashboardLayout's 20
   `setWorkflowType` writers. A seed fix in `initialWorkflowTypeFor` covers none of `/edit`, `/run` or a stale row.

   **`||`, not the card's `??`.** The file tests `builtinCanvasType` by truthiness everywhere else
   (`!!builtinCanvasType` at `:112`, `:1190`, `:1258`), so `||` keeps `""` "not a built-in" here too. Every real
   value gives the same result either way.
2. **`CanvasNode.tsx:732` and `AgentRow.tsx:171`: the Core badge reads `!removable`** (`role !== "optional"`), the
   predicate the Remove lock already used (`CanvasNode.tsx:639`, `AgentRow.tsx:200`). `locked`
   (`role === "locked"`) still drives the avatar tint and AgentRow's `draggable` (`:117`, `:125`), so required
   steps stay reorderable, as the card asked.

   **Placement differs from the card's sketch.** [ISS-963](20261002-0319-ISS-963.md) proposed one exported
   predicate beside `getRole` in `AgentsPopup.tsx`, also called from `AgentsPopup.handleRemove` (`:2823`). I left
   it out for two reasons. `handleRemove` already reads `getRole(...) !== "optional"`, so the helper changes no
   behaviour there. And `AgentsPopup.tsx` is in the globs of [ISS-966](20261002-0320-ISS-966.md) (QA-KB-048,
   TESTED in the same wave), so editing it risked a concurrent lost edit. The rule the card asks for holds: badge
   and lock read the same predicate in both renderers. The modal's embedded canvas renders CanvasNode
   (`AgentsPopup.tsx:2983`), so it is covered with no AgentsPopup edit.
3. **`CanvasNode.tsx:644`: `disabled:opacity-0` is now `disabled:text-line-faint`**, AgentRow's greyed state
   (`AgentRow.tsx:202`). A locked control and its title "Core agents can't be removed" are visible.

**Not touched:** `getRole`, `LOCKED_AGENT_IDS`, `REQUIRED_AGENT_IDS`, `AgentLibrary.tsx`, `DashboardLayout.tsx` and
`page.tsx`. On `/workflows/ppt/canvas`, `canvasPipelineType` is `ppt` and `getRole` locks every ppt step, so the guard
stays: Core x3 with disabled Removes (BUG-025 constraint 2, `S-04-03`).

## Tests and docs that encoded the defect, re-pointed

BUG-025's section "Tests and docs that encode the defect" names each of these as going red or stale with the fix, so
changing them is in scope. None of these edits loosens an assertion about correct behaviour.

1. **`ComposerPage.test.tsx`, the row case "each agent row renders ... Core badge (getRole) ..." (`:243-256`).** It
   mounted the `/workflows/new` shape (`workflowType` `user_stories`, no `builtinCanvasType`) and asserted a Core
   badge on domain-analyst. I saw it go red after the source change ("Unable to find an element with the text:
   /^Core$/"). It now mounts `builtinCanvasType: "user_stories"`, and every assertion is unchanged.
2. **`S-04-08` in `tests/integration/e2e/suites/04_composer_canvas/test_composer_canvas.py` (`:198-230`).** It was
   `@defect` and asserted all three Removes disabled with fewer Core badges than Removes. Its own failure message
   said to rewrite it once D-30 was fixed. `@defect` is dropped, and the three adds are as before. It now asserts
   three enabled Removes and zero Core badges. It then removes one and asserts two Remove controls and a header
   summary of 2 agents, which is `screens/04-composer-canvas.feature.md` S-04-08.
   - **Not run**: browser tier.
   - With the fix, the Add-agent panel opens on the Custom tab ([ISS-962](20261002-0319-ISS-962.md)). The three
     adds are therefore whatever that tab lists first, most likely the reusable `custom-agent` template
     (`backend/agents/prompts/custom-agent/AGENT.md`, `pipeline_type: custom`), not user_stories agents. That is
     why the new asserts count controls rather than names.
3. **D-30 in `tests/integration/DEFECTS-OBSERVED.md`.** I added a RESOLVED line in the file's convention (as on D-01).
   It also records that the old fix sketch ("the lock should follow the badge") is unsound read literally.
