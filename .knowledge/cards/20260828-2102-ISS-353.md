## What is suspected

[ISS-245](20260828-1631-ISS-245.md) established the mechanism: a submit control gated only by
`disabled={<reactState>}`, where the handler sets that state via `setX(true)` (a React state
update, not a synchronous DOM mutation) with no `useRef` lock, leaves a pre-commit window in
which rapid repeated clicks each independently invoke the handler. `ComposerPage`'s "Save
workflow" button has the identical shape:

```
frontend/src/components/workflow/composer/ComposerPage.tsx:1073-1083 (excerpt)
        <button
          type="button"
          onClick={() => {
            if (!name.trim()) { nameInputRef.current?.focus(); return; }
            setCanvasResetLayoutSignal((n) => n + 1);
            handleSave(name.trim(), description.trim());
          }}
          disabled={saving}
```

```
frontend/src/components/workflow/composer/ComposerPage.tsx:633,658 (excerpt)
  const handleSave = useCallback(
    async (wfName: string, wfDescription: string) => {
      ...
      setSaving(true);
      try {
        const resp = await saveUserWorkflow(token, userWorkflowId, { ... });
        setUserWorkflowId(resp.id);   // :723 — only set AFTER the response
```

`saveUserWorkflow` (`frontend/src/lib/api.ts:1828-1849`) dispatches purely on whether
`userWorkflowId` is set: `if (userWorkflowId) { ...update... } return createUserWorkflow(token,
body);`. For a brand-new, never-saved composition, `userWorkflowId` is `undefined` for the
entire in-flight duration of the first save — it is only assigned from `resp.id` at line 723,
after `await` resolves.

## Condition

On `/workflows/new` (or any composer session that has never been saved, so `userWorkflowId` is
still `undefined`), fill in a valid name and add at least one agent (satisfying the guards ISS-315
already documented for the empty-name case), then click "Save workflow" synchronously multiple
times before the first `POST` response returns — same reproduction shape as ISS-245
(`btn.click(); btn.click();` in one JS task).

## Expected vs actual

- **Expected:** the Save button disables itself the instant the first click starts the save
  request, so a second click before the response arrives is ignored and exactly one
  `POST /api/user-workflows` fires, creating exactly one row.
- **Actual (predicted):** because `userWorkflowId` stays `undefined` until the response lands,
  every click that lands inside the pre-commit window independently calls
  `saveUserWorkflow(token, undefined, ...)` → `createUserWorkflow`, so two clicks produce two
  separate `POST /api/user-workflows` requests and two separate persisted rows for what the user
  experienced as one "Save" action — a duplicate entry in "My Workflows", not merely a duplicate
  in-flight request. This is a materially worse consequence than ISS-245's login case, where the
  backend answers all duplicate requests without creating duplicate data.

## Why the root cause implies this

Independently-implemented but structurally identical to `handleSubmit`/ISS-245: local
`useState` loading flag, set synchronously-in-JS-but-not-synchronously-in-the-DOM at the top of an
async handler, with the submit control's only gate being that state's React-rendered `disabled`
prop and no ref-based mutex. The consequence differs (login's duplicate POSTs are inert; this one
persists a duplicate row) precisely because `userWorkflowId` — the value that would turn a second
`createUserWorkflow` into a `updateUserWorkflow` — is never available until after the very request
whose duplication this bug is about.

**Marked INFERRED**: no double-click has actually been performed against a live composer save;
only the code shape (button, handler, state-assignment ordering, and the create/update dispatch
in `saveUserWorkflow`) has been read and confirmed. What would confirm it: perform ISS-245's
synchronous double-click on the Save button of a never-saved composition, then
`GET /api/user-workflows` and check for two rows with the same name/timestamp.
