## What happened

On `/create/prototype`, Template tab, "Upload custom" -> "From URL" tab: entering a
syntactically valid but unreachable/unresolvable URL and clicking "Fetch" renders the
backend's raw Python socket exception text verbatim as the on-page inline error:

```
URL fetch failed: [Errno 8] nodename nor servname provided, or not known
```

`GET /api/prototype/fetch-url?url=...` returns `502 Bad Gateway` with body
`{"detail":"URL fetch failed: [Errno 8] nodename nor servname provided, or not known"}`,
and `CustomTemplateModal.tsx` renders that `detail` string unmodified as the field's error
message. This is a distinct code path from client-side URL-format validation (typing
`not-a-valid-url` correctly shows the app-authored "URL must start with http:// or https://"
message), proving the modal has a friendly-message path and simply falls back to the raw
backend exception string when the failure originates from the network fetch itself (DNS
resolution failure surfaced via Python's `socket.gaierror`/`OSError` errno 8) rather than
client-side input validation.

## Reproduction — 3/3, deterministic, no axis variation needed

Reproduced 3/3 from a cold start (fresh navigation to `/dashboard` then `/create/prototype`,
modal re-opened each cycle, no warm state carried between cycles), signed in as `qa-admin`:

1. **Cycle 1** — `http://example.invalid.nonexistent-domain-xyz123/` -> `502`, same errno text.
2. **Cycle 2** — different domain, `https://another-totally-fake-domain-abc987.invalid/` ->
   `502`, byte-identical errno text.
3. **Cycle 3** — third domain, `https://third-unreachable-domain-qqq111.invalid/` -> `502`
   confirmed via `GET http://localhost:8000/api/prototype/fetch-url?url=...` returning
   `[502] Bad Gateway`, byte-identical errno text rendered in the modal.

Steps per cycle: navigate to `/create/prototype` (Template tab) -> click "Upload custom" ->
click the "From URL" tab -> fill the Template URL textbox with an unreachable domain -> click
"Fetch" -> the inline error paragraph shows the raw errno text. Cancelled the modal after each
cycle; no template was created, wizard left clean. No entry-path, timing, tier or theme
variation was needed — deterministic on every cold-start cycle.

## Expected vs actual

- **Expected:** a network-level fetch failure (unresolvable domain, connection refused,
  timeout) is translated into a friendly, human-readable message (e.g. "Could not reach that
  URL — check the address and try again"), consistent with the modal's existing client-side
  validation path.
- **Actual:** the modal renders the backend's raw internal exception string unmodified,
  leaking the backend's runtime/OS detail (`[Errno 8] nodename nor servname provided, or not
  known`) with no actionable guidance for the user.

## Root cause (mechanism, not yet fixed)

`backend/app/api/prototype_templates.py`'s `fetch-url` endpoint catches the outbound fetch's
`OSError`/`socket.gaierror` and re-raises it into a `502` response whose `detail` is
`str(exception)` (or equivalent) rather than a fixed, user-safe message. The frontend
(`CustomTemplateModal.tsx` via `frontend/src/store/api/prototype.ts`) then displays
`error.detail` verbatim in the inline error paragraph with no server-side or client-side
message translation for this failure class, unlike the sibling client-validation path that
does have an app-authored string.

## Root cause (analyzer pass, 2026-08-29 — CONFIRMED)

**Backend** — `backend/app/api/prototype_templates.py`, `fetch_url_for_template`
(`:325-389`). The handler's final exception clause (`:387-389`):

```python
except Exception as exc:
    logger.warning("fetch-url failed for %s: %s", url, exc)
    raise HTTPException(status_code=502, detail=f"URL fetch failed: {exc}")
```

interpolates `str(exc)` straight into the HTTP `detail` with no translation. It sits after
two narrower, already-safe handlers — `httpx.TimeoutException` (`:380-381`, fixed message)
and `httpx.HTTPStatusError` (`:382-386`, interpolates only the numeric status code) — so it
is the catch-all for everything else `client.get(url, ...)` (`:349-353`) can raise. A DNS
resolution failure surfaces there as an `httpx.ConnectError` wrapping the OS resolver's
`socket.gaierror`, whose `str()` is exactly the `"[Errno 8] nodename nor servname
provided, or not known"` text observed in the repro. `_is_private_url` (`:305-318`) is not
the source — it swallows its own resolution errors and returns `False` ("let httpx handle
the error", `:317-318`), so nothing from that helper ever reaches this handler.
CONFIRMED: the interpolation itself, by reading `:387-389`. INFERRED: the exact exception
class name (`httpx.ConnectError`) — not verified by running the code, only by elimination
(not `HTTPException`, no timeout occurred, no HTTP response was ever received) and the
byte-identical error text.

**Frontend** — `frontend/src/components/workflow/prototype/CustomTemplateModal.tsx`,
`handleFetchUrl` (`:94-131`). Line 110:

```tsx
if (!res.ok || data.error) {
  setUrlError(data.detail || data.error || "Failed to fetch URL.");
  return;
}
```

renders the backend's `detail` field completely unmodified into `urlError`, which is then
painted verbatim at `:258-263`. There is no message-translation layer for a network-origin
failure on this path, unlike the malformed-URL case (backend `:339-340`, a fixed
app-authored string) which never reaches this branch. CONFIRMED by direct read.

## Fix location (analyzer pass, 2026-08-29)

**Primary, and sufficient on its own:** `backend/app/api/prototype_templates.py:387-389`.
Replace `detail=f"URL fetch failed: {exc}"` with a fixed, safe message (e.g. "Could not
reach that URL — check the address and try again."), keeping `logger.warning(..., exc)` so
the raw detail stays available server-side for debugging. This is the correct chokepoint:
every live caller (`CustomTemplateModal.tsx` from both routes) and the one dead-code caller
(`prototypeApi.fetchUrl`) all terminate in this one function, so the fix protects every
current and future caller without touching the frontend at all.

**Secondary, optional, defense-in-depth:** `CustomTemplateModal.tsx:110` trusts `data.detail`
for any error shape with no vetting. Not required to close this specific bug once the
backend catch-all stops emitting raw text, but worth a one-line note for whoever fixes this.
