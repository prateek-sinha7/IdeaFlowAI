## What happened

On the hook detail view at `/library/hooks/<hook-id>` (a real route rendering
`HookDetailModal` in `frontend/src/components/library/LibraryPage.tsx`),
clicking the "Copy" button in the modal header gives no observable feedback:
the button's text stays "Copy" (never "Copied!"), its icon stays the
`lucide-copy` glyph (never swaps to the green `Check` state the component
code defines), and `document.body.innerText` gains no "Copied" text anywhere
on the page. The only visible change is the transient `:active` state from
the click itself.

## Reproduction (3/3, cold start every cycle)

Each cycle: fresh navigation (either `/dashboard` -> deep link, or a hard
reload of the route), not a soft re-click of an already-open modal.

- **Cycle 1:** cold navigate to `http://localhost:3000/library/hooks/post-design-quality`,
  click "Copy" — `document.body.innerText.includes('Copied')` is `false`
  immediately after the click; button still reads "Copy".
- **Cycle 2:** cold navigate (via `/dashboard` first) to
  `http://localhost:3000/library/hooks/post-quality-gate` (a different hook) —
  identical result, `false`, button still "Copy".
- **Cycle 3:** cold navigate again to
  `http://localhost:3000/library/hooks/post-design-quality` (repeat of cycle
  1's hook, confirming it is not a first-visit-only condition) — identical
  result, `false`, button still "Copy".

No axis variation was needed to reproduce — it fails identically across two
different hooks, repeat and fresh visits, deep-link and click-through entry,
qa-admin tier, default theme/viewport. `navigator.clipboard.writeText` itself
works fine in this session when called directly via `page.evaluate` (returns
`'ok'`, no permission error), so the write is not the blocked part — the
button's own `copied` state simply never flips visibly in these attempts.

## Expected vs actual

**Expected:** per the component's own code, clicking "Copy" should flip
`copied` to `true`, swapping the button to a green `Check` icon + "Copied!"
label for 2000ms (`setTimeout(() => setCopied(false), 2000)`).

**Actual:** the swap never happens in any of the 3 cold-start cycles tested;
the button is visually and textually indistinguishable from its unclicked
state.

## Root cause (confirmed — file:line read)

`frontend/src/components/library/LibraryPage.tsx:351-355`, `HookDetailModal`:

```
const [copied, setCopied] = useState(false);
const handleCopy = async () => {
  await navigator.clipboard.writeText(copyText);
  setCopied(true);
  setTimeout(() => setCopied(false), 2000);
};
```

CONFIRMED: `handleCopy` has no `try/catch` around
`await navigator.clipboard.writeText`, no `.catch()`, and no failure-state UI
of any kind. If that promise rejects for ANY reason, `setCopied(true)` is
never reached; the rejection becomes an unhandled promise rejection (visible
only in devtools, never to the user); and the button is stuck reporting
"Copy" forever — exactly the reported symptom, on every hook, every cycle.

CONFIRMED (ruled out): the mount site (`LibraryPage.tsx:1070-1072`,
`<AnimatePresence>{selectedHook && <HookDetailModal .../>}</AnimatePresence>`)
carries no `key` prop and `selectedHook` only flips falsy->truthy on open, so
the component instance is not remounted while the modal is open. `copied` is
ordinary local `useState`, so a stale-closure/remount explanation (the
alternative this card originally flagged) does not hold — read directly, not
inferred.

INFERRED (not settled — what would confirm it): which specific condition
trips the rejection in the browser session that reproduced this 3/3.
Candidates: `document.hasFocus()` false at click time, the Async Clipboard
API's transient-user-activation requirement not being satisfied by a
synthetic/automation-dispatched click, or a Permissions-Policy restriction on
this route. A fixer/test-writer can settle this by adding `.catch((err) =>
...)` and logging `err.name`/`err.message` on the next repro — the fix itself
(show a failure state) does not depend on knowing which one it is.

## Fix belongs

In one shared helper (e.g. `copyToClipboard(text): Promise<boolean>` or a
`useClipboardCopy()` hook) under `frontend/src/hooks/` or `frontend/src/lib/`,
wrapping `navigator.clipboard.writeText` in a `try/catch` and returning/
setting an explicit failure flag instead of leaving the rejection unhandled.
All 12 call sites — both modals in `LibraryPage.tsx`, and the 8 others listed
above (including the 2 that already catch-and-log) — should route through it
and render a failure state using the exact same inline icon/label-swap idiom
each already uses for `copied`. One guard in the shared function is a smaller
diff than patching 12 call sites individually, and patching only
`HookDetailModal` leaves every sibling above silently carrying the same
defect.
