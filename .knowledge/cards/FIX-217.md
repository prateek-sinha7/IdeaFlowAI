## Description

When chaining from a revision run (e.g. prototype_revision v2 → PPT),
the chain context was empty because `get_chain_context` in `runs.py` only
walked ONE level up the ancestor chain. A revision-of-revision stopped at
v1 (also `prototype_revision`, no spec output) → empty `context_block`.

Additionally:
- Stale `chain.context_block` from a previous chain session leaked into new chains
- `chain.brief` was written BEFORE awaiting `getChainContext` — both sessionStorage
  keys not settled before router.push triggered wizard mount
- History-reopened / Concierge-surfaced runs had stale/empty `workflowInput`
- Direct chain path lacked `setMainView('execution')` synchronously

FIX-216c: `od_prototype`/`od_ppt` pending-run staging had a `!draft.brief` guard
that blocked wizard-chained launches where the context block IS the brief.

## Root Cause

`get_chain_context` in `runs.py` used a single-level parent walk:
```python
parent = await store.get_run(run.parent_run_id)
```
For a chain `prototype_revision (v2) → PPT`:
- v2 is `prototype_revision` → walks to v1 (also `prototype_revision`) → no spec → empty
- Should walk to `od_prototype` (root) → has spec output

## Fix

**Backend (`runs.py`):** Replace single-level parent walk with a loop
that walks ancestor chain until finding a non-`*_revision` base run
(capped at 20 hops to prevent infinite loops on malformed ancestry).

**Frontend (`DashboardLayout.tsx`):**
- Clear `chain.context_block` from sessionStorage before each chain call
- Await `getChainContext` before writing `chain.brief`
- Fall back to `ctx.brief` (source run DB input) when `workflowInput` is stale/empty
- Add `setMainView('execution')` synchronously before `onStartPipeline` on direct chain path

**Frontend (`page.tsx`, FIX-216c):**
- Remove `!draft.brief` guard from `od_prototype`/`od_ppt` pending-run staging
  so wizard-chained launches with empty `brief` field fire correctly
