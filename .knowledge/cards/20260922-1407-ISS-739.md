## QA-PS-014 — analyzer root cause (supersedes ISS-696's mechanism, keeps its reproduction)

Bug register: [QA-PS-014](../../BUGS.md#qa-ps-014).

[ISS-696](20260922-0948-ISS-696.md) (the 2-validator's confirmation card) reproduced the bug
correctly (3/3, cold start each time — see its own Evidence) and its `hasContent`/`!hasContent`
citations (`PreviewPanel.tsx:992`, `:1676-1679`) are CONFIRMED correct and reused below unchanged.
Its third root-cause bullet — `RunDetailPage.tsx:76,186` — is factually wrong for this route and
is corrected here rather than edited in place (book-keeping.md `## Corrections`): `RunDetailPage`
is never mounted for a cold `/runs/{id}*` load. ISS-696's `status` is set to `superseded` by this
card; nothing in its body was altered.

### Root cause (all CONFIRMED — file:line read)

1. **`RunDetailPage` is not on this route.** `grep -rn "<PreviewPanel" frontend/src` returns
   exactly ONE production JSX use: `DashboardLayout.tsx:3285`. `grep -rl RunDetailPage
   frontend/src` shows it is imported/mounted only inside `WorkflowHistory.tsx:36,674` (the
   in-list embedded preview) — a different surface `[...view]/page.tsx`'s `run-detail` case never
   renders. Read `DashboardLayout.tsx:3159-3330`: the `mainView === "execution"` branch mounts
   `RunChatLane` (left) + `<PreviewPanel>` (right) only; there is no `RunDetailPage` anywhere in
   it. `RunDetailPage.tsx:75-76` (`useState<RunSummary|null>(null)` / `useState(true)` loading
   flag, fed by `GET /api/runs/{id}/summary`) is itself a correctly-built pattern — just for
   `WorkflowHistory`'s embedded preview, not this route.

2. **No loading flag exists on the real path.** `frontend/src/app/[...view]/page.tsx`:
   `initialMainViewFor` (`:142-151`) maps every `run-*` screen (`run-detail`, `run-steps`,
   `run-steps-agent`, `run-files`, `run-workspace`, `run-audit`, `run-stream`, `run-version`,
   `run-preview-full`) to `MainView: "execution"` synchronously off the parsed URL, before any
   fetch starts. The actual content — `userStoryContent`/`pptContent`/`prototypeContent`/
   `pipelineState.agents`/`reopenedRunStatus` — is populated by `handleSelectWorkflowRun`
   (`page.tsx:2846` on, `async`: `getWorkflow` → `getRunEvents` → replay via
   `handleWebSocketMessage`). `grep -n "setLoading\|isLoadingRun\|isFetchingRun\|loadingRun"
   frontend/src/app/[...view]/page.tsx frontend/src/components/layout/DashboardLayout.tsx`
   returns ZERO matches in either file — no state anywhere signals "this reopen fetch is in
   flight."

3. **`PreviewPanel`'s only in-progress signal is blind to this gap.**
   `PreviewPanel.tsx:1003`: `isStillRunning = !!(isStreaming || pipelineState?.isRunning)`.
   For a reopened TERMINAL run, `isStreaming` never becomes true — `page.tsx` (~`:2915`) only
   calls `runConnection.attachRun` `if (!REOPEN_TERMINAL_STATUSES.has(fullRun.status))` — and
   `pipelineState.isRunning` is reset false by the same function's `resetPipeline()` call
   (`:2955`) at the START of the fetch. So `isStillRunning` is `false` for the entire fetch
   window on exactly the class of run the bug reports ("any completed workflow run"). With
   `isStillRunning` false, `hasContent` (`:992`, unpopulated until the fetch resolves) is the
   only remaining gate, and the neutral branch (`:1676-1679`, `!hasContent ? <p>Output will
   appear here</p>`) fires — identical to a genuinely-empty terminal run.

4. **The "Loading workspace…" toast some cycles showed is unrelated.**
   `frontend/src/store/GlobalPreloadIndicator.tsx:12-30` — a GLOBAL, post-sign-in background
   preload indicator for the agents/skills/workflows Redux slices, explicitly documented
   ("never blocks the dashboard itself, since none of today's dashboard content depends on this
   data being ready"). It has no relationship to a run's own content fetch, which is exactly why
   ISS-696's cycle 3 (click-through, global preload already settled) never showed it while cycles
   1-2 (cold direct navigation, right after sign-in) did — coincidence of timing, not a reopen
   loading signal.

### Blast radius

`PreviewPanel` has exactly one production mount (`DashboardLayout.tsx:3285`), reached whenever
`mainView === "execution"` — which `initialMainViewFor`/`reopenedRunIdFor`
(`page.tsx:142-151`, `:182-196`) map from ALL NINE reopened route forms, not just the literally
reported `/runs/{id}`: `run-detail`, `run-steps`, `run-steps-agent`, `run-files`, `run-workspace`,
`run-audit`, `run-stream`, `run-version`, `run-preview-full`. Every one funnels through the same
ungated `handleSelectWorkflowRun` fetch, so a cold load of or direct link to any of them hits the
identical gap. Within that one gap, every PreviewPanel-derived signal it feeds is affected the
same way — see [ISS-740](20260922-1408-ISS-740.md) (failure/cancelled/diverted affordance) and
[ISS-752](20260922-1409-ISS-752.md) (Steps tab).

### Fix — where it belongs

ONE loading flag in `page.tsx`, set `true` when `handleSelectWorkflowRun`'s reopen fetch starts
and cleared in a `finally`, threaded down through `DashboardLayout` into the single `<PreviewPanel>`
mount (`:3285`) as a new prop (e.g. `isLoadingRunData`). Inside `PreviewPanel`, ONE new branch
ahead of the existing `!hasContent` check (`:1676`) renders a skeleton/spinner while that flag is
true. Because `PreviewPanel` has only the one production mount and all 9 route forms share the
one fetch, this single guard closes the gap for every sibling automatically — no per-tab
patching needed. `RunDetailPage.tsx:75-76`'s existing `loading`/skeleton pattern and
[FIX-004b](20260622-FIX-004b.md) ("WorkflowCatalog's tiny 'Loading workflows...' text ... replaced
with a 5-row animated skeleton") are both already-in-repo precedents to mirror. See this card's
`locked_constraints`: the new flag must stay a distinct "fetch in flight" boolean and must not be
inferred from `terminal && !content` — that exact shortcut was already rejected for the
failure-affordance signal (`PreviewPanel.tsx:996-999`, ISS-017).
