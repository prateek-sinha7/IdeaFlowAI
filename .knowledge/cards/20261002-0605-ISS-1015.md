# ISS-1015

Same failure class as [ISS-906](20261001-2200-ISS-906.md) (bug QA-KB-078): a characterization golden was not re-pinned when
the characterized stream changed. Found by running the other golden-backed files in that family one at a time. The cause
is independent of `sandbox.py:68` and so is the fix. Confidence: **CONFIRMED** for the symptom and the diff, **INFERRED**
for which commit introduced which key (marked below).

## Condition

`backend/tests/agents/test_characterization_sample_subagents_parallel.py::test_sample_subagents_parallel_event_snapshot`
fails at HEAD `024c03ef8` (`1 failed, 1 passed in 3.09s`; the byte snapshot passes). First diff at index 0: a
`subagent_spawned` event now carries `'task_id': None, 'task_author_id': None`.

Read-only re-derivation (`_drive("sample_subagents_parallel")` -> `_canonical_order(_normalize(...))` vs the committed
golden, nothing written): both streams are 35 events; 66 differing leaves, and every one is a key ADDED since the golden:
24 x `task_author_id`, 24 x `task_id`, 18 x `worker_index`. Per event type: `task_id` and `task_author_id` on
`subagent_spawned`, `subagent_result`, `agent_start`, `agent_input`, `agent_skills`, `agent_chunk`, `agent_complete`,
`artifact_fallback` (3 each, one per worker); `worker_index` on the six worker-side types (not on the two `subagent_*`
lifecycle events).

## Cause

- CONFIRMED. `fanout.py:769-770` and `:790-791` put `"task_id": worker.get("task_id"), "task_author_id":
  worker.get("task_author_id")` on every `subagent_spawned`, and `:717-718` put the same two keys on every
  `subagent_result`; `fanout.py:574-579` copies each child event onto the `event_queue` with `worker_index`, `task_id` and
  `task_author_id` stamped. `parallel_group.py:132` calls `stream_fanout`, which passes `event_queue=child_events` for every
  parallel fan-out (`_fanout_stream.py:33`), so the stamp reaches every worker event of this pipeline, with `None` values
  because these workers carry no task identity.
- CONFIRMED. The comment at `fanout.py:568-570` still reads "additive, default-off ... None for every existing caller - dead
  branch, zero behavior change". `stream_fanout` is a caller that always supplies the queue, so the claim no longer holds.
- CONFIRMED order. The golden was last written at `bd3ca6e68` (2026-09-12). `git blame` puts the `subagent_spawned` and
  `subagent_result` lines at `1d95275b4` (2026-09-23, "Merge origin/dev into feat/stable") and the stamping lines at
  `390edbaa6` (2026-09-30). The golden-sweep close-out recorded all 9 golden-backed files green on 2026-09-14
  (`specs/019-sandbox-git-versioning/bugs/GIT_VERSIONING_BUGS.md:57`, B12), so the drift arrived after that.
- INFERRED. Blame shows the last touch, not the first introduction (`git log -S'"worker_index"'` also lists `1e329e47b`,
  2026-09-04). Which commit alone accounts for which key was not bisected; it does not change the fix.

## Disposition

Open, decision pending. Two ways to make the golden and the code agree, and the choice is not made here:

1. Re-pin, if worker identity on every fan-out event is the intended wire (the `_fanout_wave_stream.py:18` docstring says
   "Worker identity (`worker_index` / `task_id`) is carried on the wire", but it says it for wave workers, so it does not
   settle the non-wave case):
   `cd backend && SNAPSHOT_UPDATE=1 .venv/bin/python -m pytest tests/agents/test_characterization_sample_subagents_parallel.py -k event_snapshot -p no:cacheprovider`,
   then review that the 66 added leaves are exactly the keys listed above.
2. Keep non-wave fan-out byte-identical by stamping a key only when its value is not `None`, the precedent set by
   [FIX-277](20260824-1616-FIX-277.md) ("emitted only when non-zero so the characterization goldens stay byte-identical").
   That changes `fanout.py`, so it needs the picker-up to confirm no consumer relies on a present-but-`None` key.

Do not regenerate this golden together with the `app_builder` ones: it is a different decision and a different review.

Evidence: run of the file (1 failed, 1 passed, 3.09 s); the read-only leaf diff above; `fanout.py:568-579`, `:717-718`,
`:769-770`, `:790-791`; `_fanout_stream.py:33`; `parallel_group.py:132`.

## Resolution — FIX-735 (2026-10-07)

Resolved by [FIX-735](20261007-1927-FIX-735.md) with **option 1 (re-pin)**. The golden was regenerated by its own
`-k event_snapshot` invocation and reviewed apart from the app_builder goldens. The review found 35 events with an
identical type sequence. Exactly 66 leaves were added and none removed or changed: 24 `task_author_id` and 24 `task_id`
(all `None`), and 18 `worker_index` (all `int`). Option 2 was not taken. `fanout.py:576` stamps
`worker_index = idx`, which is never `None`, so a None-skip would still leave 18 added leaves and a re-pin anyway.
`useWorkflow.ts` reads `task_id` by truthiness (`:896`, `:1091`, `:1124`), so a present `null` and an absent key look
the same to it. Correction to the INFERRED bullet above: `git log -S` puts the `worker_index` stamp at `1e329e47b` and
`task_author_id` at `5af898322` / `05b7bce54`. None of them is an ancestor of `bd3ca6e68`, and they arrived through merge
`1d95275b4`. `390edbaa6` only re-indented the lines. The stale comment at `fanout.py:568-570` is carded as
[ISS-1062](20261007-1927-ISS-1062.md). The file now reports 1 failed (`[XPASS(strict)] ISS-1015 unfixed`) and 1 passed;
with `--runxfail` it reports 2 passed. Evidence: `evidence/qa-kb-078/fix-04`, `fix-07`, `fix-08`, `fix-14`.
