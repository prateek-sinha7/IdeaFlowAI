# FIX-724

## What was wrong

This fix is for bug report QA-KB-059. The root cause comes from the 2026-10-02 analysis on
[ISS-919](20261001-2221-ISS-919.md) and its siblings [ISS-983](20261002-0429-ISS-983.md) and
[ISS-984](20261002-0429-ISS-984.md). It was not re-derived here. Every cited line was re-read before editing and the
card held. The line numbers had moved by 9-21 since the analysis, because the QA-KB-052 tier lock (`locked ||`)
landed on the same `disabled` expressions.

`IdeaInputPage` had no state saying that the roster is final:

- The first roster is the library's. It comes from the `pipelineAgents` lazy initialiser (`IdeaInputPage.tsx:1010`)
  and the roster effect (`setPipelineAgents(seeded)`, `:1456`).
- The real roster arrives later, from `getWorkflowDetail(jwt, workflowId)` (`:1179`). Its `.then` writes
  `overrideAgents`, `showOverride` and `manifestAgents`, and the roster effect then re-seeds `pipelineAgents`.
- "Save workflow" and "Save as my version" were gated on `locked || pipelineAgents.length === 0 || (isMigrationMeta &&
  !migrationChoice)` only. The "Advanced" trigger had no gate at all.
- `handleSaveAsOverride` (`:1795`) sends `agent_ids: pipelineAgents.map(...)` (`:1818`) with
  `overrides_pipeline_type: workflowId` (`:1826`). `POST /api/user-workflows` UPSERTs that over the user's override
  row (`backend/app/api/user_workflows.py:811-847`) with no concurrency check.

So a click while the GET was pending, or after it had failed, replaced a saved override with the library roster
([ISS-919](20261001-2221-ISS-919.md), [ISS-984](20261002-0429-ISS-984.md)). Advanced also let an edit land in that
window, and the late overlay then re-seeded it away ([ISS-983](20261002-0429-ISS-983.md)).

Line numbers below are as of this fix, in the uncommitted tree.

## What changed, and why there

Only `frontend/src/components/workflow/IdeaInputPage.tsx` changed, as the card prescribes: the state sits next to
`loadError`, the fetch effect writes it, and the three consumers read it. The other candidates were ruled out:

- `LaunchWizard`: it has its own fetch effect, already fixed by [FIX-701](20261002-0037-FIX-701.md).
- `AgentsPopup`: it is shared by both hosts.
- The backend: UPSERT by built-in is spec 016 behaviour, and a concurrency token would be an API-contract change.

1. `:1148-1155` adds `overrideLoad: "loading" | "ready" | "failed"`, the same tri-state LaunchWizard uses. Its lazy
   initialiser is `workflowId ? "loading" : "ready"`, so a page with no workflow id never paints a disabled Save.
2. The fetch effect writes it:
   - `"ready"` in both early returns (no `workflowId` `:1164`, no jwt `:1175`);
   - `"loading"` before the request (`:1178`), so a `workflowId` change re-gates;
   - `"ready"` first in the `.then`, after the `cancelled` check (`:1182`);
   - `"failed"` in the `.catch`, under `!cancelled` (`:1361`).

   There is no `.finally`.
3. The three consumers:
   - **"Save workflow"** (`:2005`) adds `overrideLoad === "loading"`. It creates a new row and never touches the
     override, so a settled failure leaves it usable. That matters for `migration`, whose GET 404s by design.
   - **"Save as my version"** (`:2020`) adds `overrideLoad !== "ready"`. On a failure it shows the `title` from [FIX-701](20261002-0037-FIX-701.md)
     (`:2022-2024`): "Couldn't check for your saved version of this workflow. Reload to try again."
   - **"Advanced"** (`:2225-2226`) gets `disabled={overrideLoad === "loading"}`, plus the `disabled:` styling the two
     Save buttons already carry. It is the only way into `AgentsPopup` (`setShowAgents(true)` has one caller), so
     every popup path in [ISS-983](20261002-0429-ISS-983.md) (a)-(c) now starts from the final roster: edits, the footer Save, "Open in full
     canvas", and the stale-Cancel chain.

The existing `locked`, `length === 0` and migration terms are kept.

Disabling "Save as my version" on `migration` removes nothing that worked. `migration` is not in
`SUPPORTED_PIPELINE_TYPES`: run from `backend/`, `.venv/bin/python -c "from agents.loader import
SUPPORTED_PIPELINE_TYPES as S; print('migration' in S)"` printed `False`. So the server 422s an override of it
(`user_workflows.py:813-817`).

## The test file: two changes, both traced to a card

`IdeaInputPage.iss919.test.tsx` is the analyzer's scratch run, copied in with `it.fails`. The original is kept at
`evidence/qa-kb-059/fix-IdeaInputPage.iss919.test.tsx.orig`. It has two edits.

**1. T4 rewritten, because its card says it asserted the wrong thing.**

- **What the old T4 did.** It made its edit through the stub popup's `onReorder`. The stub ignores `isOpen`, so the
  edit went around the Advanced trigger. It then asserted that the edit survives the late overlay. No card prescribes
  that behaviour.
- **What [ISS-983](20261002-0429-ISS-983.md) says instead.** Its "Expected" reads: "the Advanced trigger is disabled until the fetch has
  settled". Its "For the test-writer" reads: "Assert the trigger is disabled while the detail is pending and enabled
  after it resolves or rejects. Once the trigger is gated the in-window edit cannot be made at all, so (a) becomes a
  guard on the disabled trigger".
- **What the old T4 showed under this fix.** It stayed `expected fail` (`edit survived the late overlay: false`,
  `fix-02`). The 6-verifier would have taken the marker off a test that is still red.
- **What T4 asserts now.** The trigger is disabled while the GET is pending and enabled once the detail lands. It is
  still `it.fails`. Against HEAD's component it is red (`pending=false`, `fix-03`).

**2. Five plain controls added**, the ones the [ISS-919](20261001-2221-ISS-919.md) analysis says "belong in the file":

- resolved with no override: all three buttons enabled;
- rejected 503, and rejected 404: Save as my version disabled with the reason, Save workflow and Advanced enabled;
- empty library with `steps: []`: both Save buttons disabled;
- no `workflowId`: Save workflow enabled, and no fetch.

Without them the file passed a broken fix. The triage sketch's success-only flag on every consumer (`mutantA` in
`fix-09`) flips T1-T4 exactly as this fix does, yet it disables Save workflow for good after migration's 404. The two
"rejected" controls go red on it.

T1-T3 are unchanged, apart from the shared mock's `isNotFoundError`. It now reads a `vi.fn` that defaults to `false`
and is reset in `beforeEach`.

## Not fixed

- **A one-commit window, accepted by the card.** `"ready"` commits in the same render as `overrideAgents` and
  `manifestAgents`, but the roster effect re-seeds `pipelineAgents` one commit later. For that commit "Save as my
  version" is enabled with the pre-overlay roster in its closure. A click is practically unable to land there, and
  the tests await the enabled state. Closing the window fully means moving the override seed out of the effect,
  which is a larger change than the card asks for.
- **The "Failed to load this workflow" banner** still shows only for an empty roster
  (`loadError && pipelineAgents.length === 0`), the scope [FIX-351](20260828-2347-FIX-351.md) locked. When the roster is not empty, the Save as
  my version `title` is the only explanation of a failure, which is what [ISS-984](20261002-0429-ISS-984.md) expects.
- **No browser re-run.** The fixer does not drive the UI. For the 6-verifier:
  - On `/create/user_stories`, hold `**/api/workflows/user_stories` with `page.route` and leave
    `/api/agents/library` alone.
  - While it is held, Save workflow, Save as my version and Advanced are disabled, and no `POST /api/user-workflows`
    fires. All three enable on release.
  - E2E S-05-13 (`tests/integration/e2e/suites/05_saved_workflows/test_saved_workflows.py:393-415`) clicks Advanced
    right after render. Playwright waits for an enabled button, so the gate is compatible.
