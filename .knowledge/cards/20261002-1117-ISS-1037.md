# ISS-1037

## Description

INFERRED sibling of [ISS-948](20261002-0107-ISS-948.md), found by grepping every place that enumerates the application's public paths after ISS-948 showed that `GET /s/{token}` ([ADR-0035](20260828-0644-ADR-0035.md)) was missing from the one in the test suite. From what the repository contains, the share link works in local development and cannot reach FastAPI in a production deployment. Two hops have to forward it, and neither does.

1. **nginx never sends `/s/` to the backend.** The HTTPS server block of the production site template declares these locations (`infra/scripts/reconcile-host-config.sh:249-364`): `/api/auth/login`, `/api/auth/register`, `/api/auth/change-password`, `/api/auth/refresh`, the SSE regex, `/api/`, `= /health`, `= /openapi.json`, `= /docs` and `= /redoc` (both 404), `/ws/chat`, `/ws/handoff/`, `/mcp/`, `/install/`, `/` and `/_next/static/`. None matches `/s/`, so the request falls to `location /` and is proxied to the frontend (`:353-354`).
2. **The Next.js rewrite collapses to a self-rewrite.** `frontend/next.config.ts:14-15`:
   `source: "/s/:token", destination: \`${process.env.NEXT_PUBLIC_API_URL ?? "http://localhost:8000"}/s/:token\``.
   `??` falls through only for `null` / `undefined`. The production image is built with the variable set to the empty string (`frontend/Dockerfile:49-50` `ARG NEXT_PUBLIC_API_URL=""` / `ENV ...`; `.github/workflows/deploy.yml:525-527` "No NEXT_PUBLIC_* build args (D-4)"; `backend/tests/unit/tools/ci/test_container_contracts.py:83` pins `build_args={"NEXT_PUBLIC_API_URL": "", ...}`), so the destination is `/s/:token`: the same path, served by the frontend itself. There is no `frontend/src/app/s` route, so the frontend's own routing handles the path (most likely the `[...view]` catch-all) and it never reaches FastAPI. `frontend/src/lib/env.ts:31-32` handles the same empty value correctly with `if (explicit)`; the rewrite does not.

The comment at `next.config.ts:7-12` records the assumption that fails: "In production both are behind the same reverse proxy, so the rewrite is only needed for local dev". The reverse proxy has no rule for the path.

## Why the root cause implies it

ISS-948 is a new public path registered in one of the places that must know about it (the Next rewrite, which the author's own dev setup needed) and not in the others. The contract allow-list is one missing entry; the nginx location map is another. The nginx template has a test, `backend/tests/unit/app/test_nginx_site_template.py`, but it pins the SSE location and the rate limits, not the set of backend-owned paths, so nothing compares the template with the routes FastAPI serves.

## Evidence

CONFIRMED, read: `reconcile-host-config.sh:249-364` (the location list above, `grep -n "^\s*location "` over the file); `next.config.ts:7-15`; `frontend/Dockerfile:45-50`; `deploy.yml:525-527`; `test_container_contracts.py:83`; `frontend/src/lib/env.ts:31-32`; `ls frontend/src/app` has no `s` directory.

CONFIRMED, executed (2026-10-02, side-effect free): the rewrite expression evaluated by Node.
`NEXT_PUBLIC_API_URL="" node -e '...'` printed `"/s/:token"`. With the variable unset it printed `"http://localhost:8000/s/:token"`.

INFERRED, not driven: that nothing outside this repository (a CDN or load balancer in front of nginx) routes `/s/*` to the backend; what the `[...view]` catch-all renders for an unknown path. What would settle it: `curl -i https://<host>/s/does-not-exist` against a deployed host. FastAPI answers `404 {"detail":"Share not found or expired."}` (`backend/app/main.py:649`); the frontend answers HTML. Or build the image with the Dockerfile default and read the `/s/:token` entry in `.next/routes-manifest.json`.

## Expected vs actual

- Expected: a share link minted by `POST /api/runs/{id}/share` opens the deliverable for an anonymous visitor in production, as it does in dev.
- Actual (from the configuration): the request never reaches the backend; the visitor gets the frontend's response for an unknown path.

## Fix direction

Route it where the other backend-owned paths are routed: add a `location /s/ { proxy_pass http://velocityai_backend; include /etc/nginx/snippets/velocityai-proxy-headers.conf; }` to the site template in `reconcile-host-config.sh`. **Do not put an `add_header` in it.** nginx discards every inherited `add_header` once a location declares one of its own, which is what `test_sse_location_declares_no_add_header` (`test_nginx_site_template.py:135-148`) pins for the SSE location; a header added here would drop the server-level HSTS, nosniff and CSP headers from share responses. Then make the Next rewrite stop pretending: for a build whose `NEXT_PUBLIC_API_URL` is empty it must not produce a destination equal to its source (drop the rewrite for that case, or test for the empty string the way `env.ts` does). Keep the dev path working. The security header for the shared response belongs in the route itself, see [ISS-1038](20261002-1117-ISS-1038.md).

## Test notes

Both checks are offline and need no browser.

- Extend `test_nginx_site_template.py` with a directive-level check, using the same heredoc extraction as its SSE tests (`:34`): a `location /s/` exists, proxies to `velocityai_backend`, and declares no `add_header`.
- A frontend unit test that stubs `NEXT_PUBLIC_API_URL` to `""`, awaits `nextConfig.rewrites()` (the template literal is evaluated at call time) and asserts the `/s/:token` destination does not equal its source.

## Fix (2026-10-07, QA-KB-089)

Fixed by [FIX-745](20261007-2030-FIX-745.md), both halves. `reconcile-host-config.sh` gains `location /s/` with
`proxy_pass http://velocityai_backend`, the proxy-headers include, and no `add_header`. `next.config.ts:15` changes
`??` to `||`, so an empty build value resolves like an unset one. The first test-notes item was missing, so the fixer
added it as `test_nginx_site_template.py::test_share_link_location_proxies_to_the_backend`, watched it fail first,
and then saw 7 passed. The second item (the frontend unit test) was not written. The static guard in
`test_share_route_hardening.py` (XPASS strict) stands in for it, together with a node evaluation of `rewrites()`:
`""` → `http://localhost:8000/s/:token`.
