# ISS-1125

**Register source:** found by the 5-fixer while fixing `QA-KB-102` ([FIX-768](20261008-1540-FIX-768.md)), 2026-10-08. Not fixed there: neither
[ISS-1103](20261008-0016-ISS-1103.md) nor its siblings name this exit, and the fix it needs is a design call (below). Not its own bug row.

**Line numbers** are the working tree with FIX-768 applied (HEAD `2461935f5` + FIX-768).

**Confidence:** the mechanism is CONFIRMED by reading. The consequences are INFERRED from the code; nothing here was probed.

## Mechanism (CONFIRMED by reading)

`_execute_impl` validates the DAG and, when it is not satisfiable, yields one `error` frame and returns
(`backend/agents/execution_engine/engine.py:5239-5249`):

```python
        if not validation.satisfiable:
            yield {
                "type": "error",
                "data": {
                    "error": "Workflow DAG is unsatisfiable: "
                    + "; ".join(validation.errors),
                    "code": "workflow_unsatisfiable",
                    "recoverable": False,
                },
            }
            return
```

That exit sits before the run's main `try` (`engine.py:6205`, whose `finally` at `:7619` runs the finalizer) and before the first
state-machine transition (`:5379` `planning`, `:5739` `generating`). Driven through `_drive_resumed_stream`, the stream ends NORMALLY:
no exception, so FIX-768's swallow branch (`engine.py:16118-16122`) never runs, and no `pipeline_failed` / `pipeline_complete` /
`pipeline_cancelled` / `pipeline_diverted`, so nothing ends the attempt. The `error` frame itself is persisted and pushed live like every
other event.

## Consequences (INFERRED, not probed)

- Restart auto-resume: the row keeps the status it had (`running` / `generating`), no driver is left, and the next boot adopts it again
  with one more `run_resuming` marker. The [ISS-1119](20261008-1450-ISS-1119.md) shape, by a different exit.
- User resume: `_reconcile_terminal_status` finds no `pipeline_failed` after the marker, takes the D2 fail-safe `failed`, and keeps the
  previous attempt's `.error` (`backend/app/api/run_commands.py:997-1011` derive it from `agent_error` / `pipeline_failed` only, never
  from an `error` frame). The [ISS-1122](20261008-1450-ISS-1122.md) shape.
- Lane: the frontend `error` case only sets `pipelineError` (`frontend/src/hooks/useWorkflow.ts:1357-1362`). It does not rebuild
  `agents`, so FIX-768's `DashboardLayout` clear does not fire and "Restarting run…" stays. The [ISS-1121](20261008-1450-ISS-1121.md) shape.

## How often

Latent. The plan was satisfiable at launch; a resume recompiles it (registry roster or persisted manifest), so it turns unsatisfiable only
when an agent's `produces` / `consumes` contract changed between launch and resume. Same class as the manifest exit FIX-768 covers.

## Fix direction (INFERRED, not applied)

In `_drive_resumed_stream`, after the `async for` ends normally with no terminal seen, route through `_fail_resume` with the `error`
frame's text. First check every normal-return path of `_execute_impl` on a resume (a gate park waits inside the generator; Stop yields
`pipeline_cancelled`; the all-steps-complete offset path), so a legitimate terminal-less return is not turned into a failure. The red test
would resume a run whose roster no longer satisfies its DAG and assert one `pipeline_failed` after the marker and a `failed` row.

## Analysis (QA-KB-105 analyzer, 2026-10-08, HEAD c9c4c630a)

This card is now bug `QA-KB-105` (`LEDGER.md`). Everything above stays as filed. This section confirms the mechanism on the current tree,
upgrades what was INFERRED to OBSERVED where an offline probe could settle it, corrects one claim, and names where the fix belongs.

Probe: `evidence/qa-kb-105/analysis-plugins/kb105_probe_test.py`, a scratch module outside the suite that reuses the harness of
`test_qa_kb_102_silent_resume.py` and `test_restart_resume_db.py`. The DAG is forced unsatisfiable by patching `WorkflowResolver.validate`
(the call at `engine.py:5215`); SQLite in memory, no model call, no live DB. Output:
`evidence/qa-kb-105/analysis-01-unsatisfiable-resume-probe.txt`.

### Root cause (CONFIRMED by reading)

`_drive_resumed_stream` recognises a failed attempt by exception only. `_terminal_seen` is set in the loop (`engine.py:16047-16053`) but
read only inside the `except` (`:16121`), so a stream that ends without raising counts as a finished attempt whatever it yielded.
`_execute_impl` has exactly one exit that ends a stream without raising and without a terminal event: the unsatisfiable-DAG return
(`engine.py:5239-5249`). It yields the generic `error` frame and returns before the first state-machine transition (`:5379` planning,
skipped on a resume; `:5739` generating) and before the main `try/finally` (`:6205`, `:7619`).

I read every other exit of `_execute_impl`. Its 18 other `return` statements (`:5659`, `:6238`, `:6265`, `:6361`, `:6423`, `:6561`, `:6584`,
`:6829`, `:7251`, `:7279`, `:7396`, `:7426`, `:7502`, `:7546`, `:7568`, `:7598`, `:7618`, `:7782`) and its natural end (`:8210-8213`) either
yield a terminal first (directly, or through `_pending_terminal_event`, which the `finally` emits at `:7702-7726`) or follow one the stream
has already carried (`:6238` and `:8179`, whose comments say the terminal went out at the point of cancellation or failure). `engine.py:5241`
is also the only place the engine itself yields a generic `error` frame (`:4267` only feeds the run trace). So no legitimate terminal-less
return exists today for a guard to misread.

The launch tier handles the same frame. CWF-001 D2 maps a stream that ends on a generic `error` to `failed`, with its text as `.error`
(`backend/app/api/run_commands.py:4270-4277`, `:4326-4338`; test `test_driver_generic_error_records_failed` in
`backend/tests/integration/api/test_rest_run_launch_api.py`). The resume tier never got that mapping, and its restart drivers have no app
wrapper that could host one.

| R1, R2 restart auto-resume of a `running` run, two boots | row `running` after both; `run_resuming` 2, `error` 2, `pipeline_failed` 0 | no terminal; `completed_at` SET and `duration` 4.2 on the `running` row after boot 1 |
| G1, G2 restart re-arm of a gate-parked run | row `waiting_for_user` | see [ISS-1127](20261008-2132-ISS-1127.md) |
| C control, same user resume, DAG left satisfiable | row `completed`, tail ends `pipeline_complete` | nothing: the harness is sound |

### Corrections and additions to the Consequences section above

- "User resume ... takes the D2 fail-safe `failed`" holds for a `failed` or `degraded` previous attempt (U1, U3) but not a `cancelled` one.
  `_reconcile_terminal_status` keeps `cancelled` unless a `pipeline_failed` or `pipeline_complete` follows the cancellation with an attempt
  boundary between them (`run_commands.py:903-917`). U2 ends `cancelled`.
- Restart auto-resume: the status is observed as stated, plus an effect the card did not name. The funnel's `finally` still calls the output
  persister (`engine.py:16167-16169`), and `_apply_terminal_output_columns` stamps `completed_at` and `duration` when they are unset
  (`run_commands.py:4033-4036`), so a row that stays `running` carries a completion time. Both guards (`not wr.completed_at`, `not wr.duration`)
  then keep the premature values.
- Lane: still INFERRED (the frontend was not probed). The reconnect path keeps `isRunning` true for a non-terminal status
  (`frontend/src/hooks/useWorkflow.ts:1531-1542`), so the restart ghost reads as running on the lane indefinitely.
- "How often": the card ties the trigger to a changed `produces`/`consumes` contract. `WorkflowResolver.validate` is also order-sensitive
  (`resolver.py:141-142`, only a producer declared before the consumer counts) while a resume rebuilds its roster from the registry or the
  recompiled plan (`engine.py:15764-15766`), not from the launch roster. Whether the two orders can differ is INFERRED; diffing the launch
  roster against `resume_run`'s for a composed run would settle it.

  (`:12868`, restart branch b), `_rearm_gate_run` (`:12999` review, `:13006` clarify) and `_drive_user_resume` (`run_commands.py:793`). All four

- Readers of the durable `error` event it leaves: `derive_open_gate` (`gate_pendency.py:47`, `:60`, see ISS-1127), `_reconcile_terminal_status`
  (ignores it), `_apply_terminal_output_columns` (ignores it, stamps `completed_at`).

### Where the fix belongs

`_drive_resumed_stream`, which the engine's own comment calls "the ONE funnel every resume driver ... reaches `_execute_impl` through"
(`engine.py:15979-15983`). Keep the last `error` frame's text next to `_terminal_seen`, and give the `try` an `else:` so the exception path
is not handled twice:

```python
else:  # the stream ended without raising
    if not _terminal_seen:
        await self._fail_resume(run_id, f"Resume failed: {_stream_error or 'the run ended without a terminal event'}", live_queue)
```

One guard in the shared funnel gives all four drivers the FIX-768 outcome (one `pipeline_failed`, the state machine `failed`, a live frame)
and covers any future terminal-less return. It runs before the `finally`, so the output persister then reads a tail that ends in
`pipeline_failed`. `_fail_resume` never raises (`engine.py:15539`).

Rejected: a guard in `_drive_user_resume` (the thin wrapper, INV-12 fence, and the restart drivers have no wrapper); a change to
`_reconcile_terminal_status` (cannot help the restart path and would re-derive what `_fail_resume` already records); filtering `error` out of
`derive_open_gate` (a separate vocabulary decision, moot once the attempt ends `failed`).

Optional complement, not needed for this bug: make the exit at `engine.py:5239-5249` yield a `pipeline_failed` after the `error` frame, like the
other in-engine failure branches. It would also give the launch and revision tiers a durable terminal, but it changes their event contract, so
it is a separate change.

### Risks for the fixer

- Four existing tests drive `_drive_resumed_stream` with a scripted `_execute_impl` that ends WITHOUT a terminal: three in

  `backend/tests/agents/test_run_trace.py` (`:302`). After the guard they reach `_fail_resume`, which moves the process-wide state machine for

- `.error` on the restart path is [ISS-1126](20261008-1540-ISS-1126.md)'s. Assert status and the single `pipeline_failed` there, and `.error`
  only on the user path.
