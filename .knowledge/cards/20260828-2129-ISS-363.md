## Correction

[ISS-258](20260828-1650-ISS-258.md) established the bug (BUG-20260828-001100-create-ex-a2-branch,
3/3 reproduced, confirmed no network request fires) and correctly identified the Cancel button's
wiring (`AgentsPopup.tsx:2492-2493` → `onClose` → `IdeaInputPage.tsx:1882`
`() => setShowAgents(false)`, which only toggles visibility). Its Root Cause section, however,
names `AgentsPopup.tsx:2238-2247`'s `handleSelectionsChange`/`onSelectionsChange`/
`selectionsRef.current` as what fires "on every route-editor edit inside the modal." Reading the
actual outcome-editor code shows that chain is not what runs for a route/outcome Type or Target
edit — a **different** prop chain does, writing a **different** piece of parent state
(`pipelineAgents`, not `selectionsRef`). This card carries the corrected mechanism; ISS-258's
repro, evidence and Cancel-button citation stand and are not disputed.

## Root cause (CONFIRMED — every line below was read)

The conditional-gate route/outcome editor (the "Route N outcomes" pill's Type/Target controls the
bug's repro exercises) lives in `frontend/src/components/workflow/composer/CanvasConfigRail.tsx`,
not in `AgentsPopup.tsx` itself. Its per-outcome edit handler:

```tsx
// CanvasConfigRail.tsx:295
onRouteChange?.(agent.id, applyOutcomePatch(route, key, patch));
```

`onRouteChange` is wired, in the canvas embedded inside the modal, to
`frontend/src/components/workflow/composer/CanvasView.tsx:2302`
(`onRouteChange={handleRouteChange}`), whose handler is:

```tsx
// CanvasView.tsx:748-751
const handleRouteChange = (id: string, route: AgentDef["route"]) => {
  const next = reconcileDetached(mapAgentInTree(pipelineAgents, id, (a) => ({ ...a, route })));
  onTreeChange?.(next);
};
```

`CanvasView.tsx:688-692` documents this explicitly in a comment: "the route-editor write-through
... round-trips through `onTreeChange` into the SAME `pipelineAgents` state Save persists." Inside
`AgentsPopup.tsx`, the embedded `<CanvasView>` forwards its own `onReorder` prop straight through
as `onTreeChange`:

```tsx
// AgentsPopup.tsx:2462
<CanvasView ... onTreeChange={onReorder} ... />
```

`onReorder` is supplied by whichever page hosts the modal. Both confirmed hosts wire it to a
handler that writes directly into REACT STATE with no staging:

```tsx
// IdeaInputPage.tsx:1540-1542 (onReorder={handleReorderAgents} at :1912)
const handleReorderAgents = useCallback((reordered: AgentDef[]) => {
  setPipelineAgents(reordered);
}, []);
```
```tsx
// LaunchWizard.tsx:577 (onReorder={handleReorderAgents} at :1156)
setPipelineAgents(reordered);
```

`pipelineAgents` is the state array that both the modal's embedded canvas AND the host page's
own background canvas render from (`AgentsPopup` receives it as its `agents` prop —
`IdeaInputPage.tsx` passes `agents={pipelineAgents}` at its `<AgentsPopup>` call site) — so the
instant the outcome's Type/Target patch is applied, the new "Diverts run" divert node appears,
exactly as the bug report observed.

The modal's Cancel button never touches any of this:

```tsx
// AgentsPopup.tsx:2492-2493
<button onClick={onClose} ...>Cancel</button>
```

`onClose` is `() => setShowAgents(false)` in both hosts (`IdeaInputPage.tsx:1882`,
`LaunchWizard.tsx:1126`) — a visibility flag only. No code path snapshots `pipelineAgents` when
the modal opens, and no code path restores it when Cancel (or backdrop-click, which reuses the
same `onClose`) fires. Confirmed no rescue exists elsewhere either: `showAgents` has exactly one
setter call site per host (the toggle) and is read by no `useEffect` in either file (`grep -n
"showAgents" IdeaInputPage.tsx LaunchWizard.tsx` — 2 matches per file, declaration + toggle,
nothing else). The docstring at `IdeaInputPage.tsx:1871-1880` confirms `AgentsPopup` is rendered
**unconditionally** — `isOpen` never unmounts it — so there is no mount/unmount boundary that
could incidentally reset state either.

## Why ISS-258's attribution was imprecise

`AgentsPopup.tsx:2242-2248`'s `handleSelectionsChange`/`onSelectionsChange`/`selectionsRef` chain
is real code and independently exhibits the identical defect shape (live-propagate on edit, no
restore on Cancel) — but it is wired to `ConfigLeversFlat.tsx:1640-1647`'s `updateLever`, the FLAT
per-agent levers (validators/gates/model/retry), a sibling UI surface in the same "Config tab",
not the canvas's route/outcome editor the bug's repro actually drives. See
[ISS-364](20260828-2130-ISS-364.md) for that chain as its own, not-yet-reproduced sibling.

## Expected vs actual

Expected: Cancel restores `pipelineAgents` (and every other modal-local edit) to the snapshot
that existed when the modal opened, before calling `onClose`.

Actual: Cancel calls only `onClose`; `pipelineAgents` was already mutated the instant the outcome
patch applied, and nothing ever reverts it.

## Where the fix belongs

Inside `AgentsPopup.tsx`, once — not in `IdeaInputPage.tsx` or `LaunchWizard.tsx`, and not by
patching `handleSelectionsChange` alone (that would fix nothing here; it is not the path this bug
exercises). `AgentsPopup` already takes a one-time mount snapshot for `liveSelections`
(`AgentsPopup.tsx:2233-2241`, `useState(() => initialSelections ?? {})`); the same pattern needs
to exist for `agents`/`pipelineAgents` — held as `AgentsPopup`'s OWN staged copy, edited locally
by the embedded canvas, and propagated to the host's `onReorder`/`onAddAgent`/`onRemoveAgent`
only from the "Save workflow" footer button (`AgentsPopup.tsx:2495-2510`) — with the Cancel
button (`:2492-2493`) resetting that local copy (and re-emitting it to the host via `onReorder` so
the host's `pipelineAgents` un-does any already-live-propagated edit) before calling `onClose`.
Doing this once in `AgentsPopup` fixes both hosts (`IdeaInputPage.tsx`, `LaunchWizard.tsx`) and
every edit surface (route editor, add/remove/reorder — see [ISS-365](20260828-2131-ISS-365.md);
second host — see [ISS-366](20260828-2132-ISS-366.md)) in one diff, since none of them have a
bespoke code path — they all route through this one shared modal component.
