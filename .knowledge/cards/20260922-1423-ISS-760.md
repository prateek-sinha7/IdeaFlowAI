# ISS-760

## Description

Sibling of the root cause analyzed on **[ISS-705](20260922-1050-ISS-705.md)** for
bug **QA-PS-025** (`BUGS.md#qa-ps-025`) — the inverse (load) side of the same
`fanout_batch`/`wave_scheduler`-only restriction. ISS-705 and
[ISS-765](20260922-1428-ISS-765.md) show the COMPOSE-time gap: neither composer UI
can ever construct a `task_loop` selection. This card shows the same restriction
lives a THIRD time, independently, in the save/load (persisted "My Workflows")
layer — so even if a future fix lets the compose-time UI construct
`strategy: "task_loop"` for a step, saving that workflow and reopening it will not
round-trip correctly, because the wire type and the reverse-mapping function that
rehydrate a saved manifest back into the composer's in-memory selections map both
predate that fix and only know about the two fan-out values.

`frontend/src/store/api/userWorkflows.ts` declares its OWN `StepSelectionWire` type
(not imported from `AgentsPopup.tsx` — its own comment at lines 12-16 explains it is
declared separately to avoid a store->component dependency) with the identical
`strategy?: "fanout_batch" | "wave_scheduler"` restriction. That same comment
documents this exact bug CLASS already happening once before, for `wave_scheduler`:
"[the type] appeared inline in six signatures, which is how `wave_scheduler` came to
be authorable in the composer but unrepresentable here" — i.e. the composer UI grew
a `wave_scheduler` lever before this wire type was updated to carry it, and the type
had to be fixed up after the fact. `task_loop` needs the same fix-up, proactively.

The concrete failure lives in `manifestStepsToGateSelections`, the function that
turns a saved workflow's compiled `ManifestStep[]` back into the composer's
`Record<string, StepSelectionWire>` selections map when a user reopens it. Its
leaf-fan-out branch (`:793`) is a hard equality check against the two known
strategy strings; a step whose `strategy` is `"task_loop"` fails it silently — no
error, no warning, `entry.strategy` (and therefore `entry.task_source`) is simply
never set for that step.

## Expected vs Actual

Expected: reopening a saved workflow reconstructs every step's fan-out/task-loop
configuration exactly as it was saved, symmetric with however it was originally
authored (matching the file's own stated intent for the fan-out reverse-mapping
block, lines 771-790/791-810).

Actual: a saved step with `strategy: "task_loop"` reopens with no strategy and no
task_source in the composer's selections state — the UI would show the "Fan out
over a list" toggle OFF and the task-loop configuration would appear lost, even
though the backend's stored manifest/selections still has it intact. A user who
edits and re-saves that reopened workflow would silently strip the `task_loop`
strategy from the persisted row.

## Evidence

- `frontend/src/store/api/userWorkflows.ts:12-32` — `StepSelectionWire` type
  declaration and its own comment: "Named once because it appeared inline in six
  signatures, which is how `wave_scheduler` came to be authorable in the composer
  but unrepresentable here." Line 21: `strategy?: "fanout_batch" | "wave_scheduler";`
  — no `task_loop` member, mirroring `AgentsPopup.tsx:1397` and
  `CanvasConfigRail.tsx`'s restriction but as a THIRD, independently-typed
  declaration.
- `frontend/src/store/api/userWorkflows.ts:791-810` (`manifestStepsToGateSelections`,
  leaf-fan-out branch) — quoted exactly:
  `if (!isNested && !step.subagents && (step.strategy === "fanout_batch" ||
  step.strategy === "wave_scheduler")) { entry.strategy = step.strategy as
  "fanout_batch" | "wave_scheduler"; ... }` (lines 793-794). A `step.strategy ===
  "task_loop"` never satisfies this condition.
- `frontend/src/store/api/userWorkflows.ts:344-354` (`agentToManifestStep`, the SAVE
  direction, parent/isParent branch) — `const selFanout = selStrategy ===
  "fanout_batch" || selStrategy === "wave_scheduler";` (line 350) — the same
  restriction on the save side for a parent (fan-out-group) step, confirming the
  gap is symmetric: save and load both only understand the two fan-out strategies.
