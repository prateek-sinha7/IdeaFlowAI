- **Root cause (investigation agent — read `.planning/IMPLEMENTATION-REGISTER.md` (797 KB, targeted: SSE/run-screen sections) + `.planning/SSE-QA-BUG-LOG.md` BUG-004/005/013 to EOF; traced the SSE transport end-to-end in source; RUNTIME-PROVEN with temporary `console.log` instrumentation + a real reopen driving the live stream, plus a `\r`-strip fail-before/pass-after experiment; all instrumentation reverted, tree clean):**
  - **THE BUG — the live SSE frame-boundary split never matches the backend's line endings, so NO live frame is ever dispatched.** `frontend/src/hooks/useRunStream.ts` reads the fetch-stream body and extracts frames with **`while ((idx = buf.indexOf("\n\n")) !== -1) { … buf.slice(idx + 2) … dispatchBlock(rawBlock) }` (`useRunStream.ts:343`/`:345`)** — i.e. it splits SSE frames on a **LF-LF (`\n\n`)** blank-line boundary. But the backend serves SSE via **`sse-starlette==3.0.2`, whose `DEFAULT_SEPARATOR = "\r\n"`** (`backend/requirements.txt:103`; the endpoint `run_stream.py:279 EventSourceResponse(...)` does not override `sep`), so every frame is terminated `\r\n` and the blank-line frame separator on the wire is **`\r\n\r\n`**. `"\r\n\r\n".indexOf("\n\n") === -1` (the two `\n`s are separated by a `\r`), so the `while` loop **never executes**, `dispatchBlock` is **never called**, and the trailing flush `if (buf.trim()) dispatchBlock(buf)` (`:350`) only fires on stream **close** (`done`) — which never happens for a held-open live stream (parked/replaying). Net: the fetch reader receives every byte, the phase reaches `replaying`, but **not a single frame is ever parsed or delivered to the page.**
  - **RUNTIME PROOF (reverted instrumentation + a reopen that ALSO attaches the live stream — no extra launch):** reopening the parked run drove `attachRun(1d109223)` → a `RunStreamConnection` mounted and `useRunStream.connect()` fired; instrumentation captured **`[B014-FETCH-RES] {status:200, hasBody:true}` → phase `replaying`**, then **ZERO `[B014-DISPATCH]` for 30 s** (buffer accumulates `\r\n\r\n` frames, boundary split never matches). The clarify still rendered — but ONLY from the REST replay path (below), NOT the stream. **Fail-before/pass-after discriminator:** a one-line temp change appending `.replace(/\r/g,"")` to the decoded chunk (so `\r\n\r\n`→`\n\n`) flipped `[B014-DISPATCH]` from **0 → 9** frames immediately (`workflow_validated…questionnaire_ready…stream_attached` + sse-starlette pings) — proving the CR/LF boundary mismatch is exactly what starves the dispatcher. Raw wire confirmed byte-for-byte (`curl … /events/stream`): `id: 1\r\ndata: {…}\r\n\r\nid: 2…`; the captured file contains **7× `\r\n\r\n` and 0× `\n\n`** (hexdump at the first boundary: `ted"}\r\n\r\nid:`).
  - **SECONDARY defect (latent behind the primary; would surface the moment the split is fixed) — the frame `type` is read from an `event:` line the backend never emits.** `dispatchBlock` derives the type via **`else if (line.startsWith("event:")) typeLine = …` (`:224`) → `const type = typeLine ?? "" ` (`:227`)**, and treats the parsed `data:` JSON as the whole payload. - **Fix (PROPOSED — investigation only, NOT applied):** repair the FE SSE parser so it matches the backend's ACTUAL (sse-starlette-standard, `run_stream.py`-documented) wire; the backend wire is correct and should NOT change. Two coupled edits in `frontend/src/hooks/useRunStream.ts dispatchBlock`, both required:
  1. **Frame boundary — tolerate `\r\n\r\n` (primary).** Normalize CR before/at the split so a `\r\n`-terminated stream frames correctly — e.g. strip `\r` from each decoded chunk (`buf += decoder.decode(value,{stream:true}).replace(/\r/g,"")`) so the existing `\n\n` split + `slice(idx+2)` + per-line `startsWith` parsing all work unchanged; or split on a boundary regex matching `\r?\n\r?\n` and advance by the matched length. (Proven sufficient: the `\r`-strip experiment restored dispatch 0→9.)
  2. **Type/data envelope — derive from the parsed `data:` JSON, not an `event:` line (secondary, mandatory).** The backend puts `{type, data}` in the `data:` body (mirroring the old WS `{type,data}` message) and emits no `event:` line, so parse `const parsed = JSON.parse(dataLine)` and dispatch `{ type: parsed.type ?? typeLine ?? "", data: (parsed.data ?? parsed) as Record<string,unknown> }`. Keep the `event:`-line read as a fallback for wire that does carry it. This restores `msg.type`/`msg.data.event_id`/`msg.data.seq` so dedup + the pipeline/switch routing bind. (Without this, a boundary-only fix still yields `type=""` and nothing routes — runtime-proven.)
  - **Mock parity (required, or the fix silently regresses e2e):** `frontend/e2e/fixtures/mockSse.ts:439` currently emits the FE-parser's wrong shape (`event:` line, flat `data:`, `\n\n`). Either make `dispatchBlock` tolerant of BOTH shapes (least-disruptive; keep the mock) OR update the mock to emit the REAL backend shape (`\r\n\r\n`, no `event:` line, nested `{type,data}`) so the suite actually exercises the live contract (durable fix — the mock/real divergence is what let this ship). Recommend tolerant parsing + a NEW e2e fixture asserting the real `\r\n`/nested wire.
  - **Do NOT** change the backend to emit `event:` lines / flat data / `\n` separators — that diverges from the sse-starlette default and the `_sse_projection` characterization parity; the FE parser is the side that regressed.
