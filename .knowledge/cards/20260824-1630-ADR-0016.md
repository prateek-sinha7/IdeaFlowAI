# ADR-0016

## Decision

In the context of "Run once" on a composition the user has edited but not saved, facing
the fact that such a composition's steps are dynamically generated
`custom-agent:<instance_id>` instances whose bare ids can never appear in the static
allow-list `agent_ids` is checked against, we decided to accept the manifest inline in the
launch body and compile it at `trust="user"`, to achieve explore-edit-run without forcing
a save first, accepting one more shape the launch endpoint must understand.

**Area:** api, launch, composer, security

## Why this is not a new trust surface

The identical manifest can already be POSTed to `/api/user_workflows` and then launched
via `user_workflow_id`. The same bytes were always reachable; the only thing that changed
is that they no longer have to be persisted first. And the inline path is compiled at a
STRICTER level than the saved path — `trust="user"` versus a saved row's `trust="db"` —
so the compiler's per-step capability checks, which reject privileged grants for a
non-file manifest, remain the security boundary exactly as before.

## What it replaced

Before this, the composer's own code carried the limitation as a comment: *"an unsaved
Case-3 composition still runs via the pre-existing flat path until the user saves."* In
practice that path 400s with `invalid_agent_ids`, so Run once on an edited composition
simply failed, and the user's only recourse was to save a workflow they may not have
wanted to keep.

## The narrower case is still preferred where it applies

An UNMODIFIED built-in opened on the canvas does not use this path. It launches by its own
`pipeline_type` with NO `agent_ids`, letting the backend source the roster from the
compiled plan — the same shape the `.http` runners use. That keeps the manifest's own
deliverable, planner and clarify settings, which an inline steps-only manifest would
replace with composer defaults.
