## Context

Characterization goldens pin the normalized event stream of a run. They are
regenerated on purpose with `SNAPSHOT_UPDATE=1`, and the harness prints the
instruction itself: *"If intentional (sanctioned 0C change), regenerate ... and
review the diff (SAFE-02)."*

The review step is the whole safeguard, and it is the step that gets skipped —
because a red golden after an intentional change looks exactly like a red golden
after an environmental failure.

## What went wrong

`backend/tests/agents/characterization/golden/prototype_revision.events.json`
carried this as EXPECTED output:

```
type: gate_blocked
data.gate: validation
data.issues[0].validator: html_render
data.issues[0].severity: CRITICAL
data.issues[0].message: "uncaught exception: render harness error:
                         Browser.new_page: Target page, context or browser has been closed"
```

That message is [FIX-307](20260826-0124-FIX-307.md) — the render validator was
dead, every call raised inside its own harness, and the failure was captured as a
CRITICAL validation issue. Someone regenerated the golden while that was true, so
the corpus asserted that a broken browser harness IS the correct behaviour of this
pipeline. The guard then defended the bug: fixing `render_check` made the golden
go red, which reads as "your fix broke characterization".

It was not one file. The same event was about to be written into
`prototype_revision.wsframes.json` in this session, and was caught only because the
regeneration diff was read line by line and the added event was an ERROR event.

## Decision

**A regeneration diff is read before it is kept, and a new failure/error event in
it blocks the regeneration until the failure is explained.**

Concretely:

1. Diff the regenerated golden and classify every added and removed event, not
   just the counts. Equal counts on both sides mean reformatting; the signal is
   the events that appear on ONE side only.
2. If the diff ADDS a `gate_blocked`, an `error`, a `pipeline_failed`, or any
   payload containing "harness error" / "unavailable" / "could not", stop. Explain
   that event first. It is far more often a broken local environment than a real
   behaviour change.
3. Regenerate only from an environment you have confirmed healthy. In this session
   the browser was verified independently (a bare `chromium.launch` + `new_page`
   worked) BEFORE any golden was rewritten, which is what separated "the harness is
   broken" from "playwright is not installed".
4. If a golden is already contaminated, the fix is a new regeneration once the
   environment is sound — plus a card explaining the contamination, so the next
   red golden is not mistaken for a regression again.

## Consequence

A golden is a record of what the system does, so it faithfully records a broken
dependency too. That is the cost of characterization testing and it is accepted —
the mitigation is procedural, not structural, because a golden that filtered out
"suspicious" events would stop being a faithful record.

The practical tell: goldens are the one artifact where a test going RED after a
fix is evidence FOR the fix. Read the diff before believing the colour.
