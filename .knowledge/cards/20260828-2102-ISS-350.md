## What happened

INFERRED sibling, not yet reproduced in-browser. Distinct downstream consequence from
[ISS-348](20260828-2102-ISS-348.md) (login) and [ISS-349](20260828-2102-ISS-349.md) (admin): the
parser flaw is identical, but this one does NOT fall through to the dashboard.

## Root cause (CONFIRMED by source read, INFERRED as a live defect pending repro)

`frontend/src/lib/routes.ts:418-420`:

```ts
if (head === 'analytics') {
  return { screen: 'analytics' };
}
```

Same missing-depth-guard shape as `register`/`login`/`admin` — matches `segments[0] ===
'analytics'` alone, no `segments.length === 1` check, so `parseViewPath(['analytics',
'anything'])` returns `{ screen: 'analytics' }` just as readily as the bare `/analytics` path.
Unlike `register`/`login`/`admin`, there is no separate static Next.js route for `/analytics` —
it is served entirely by the `[...view]` catch-all, and `initialMainViewFor` (page.tsx:169-170)
DOES carry `case "analytics": return "analytics";`. So a bogus `/analytics/<sub-path>` resolves to
a real, explicit `MainView` and `DashboardLayout` renders the genuine Analytics page — not the
dashboard fallback ISS-238/348/349 describe.

The `AnalyticsPage`'s own params (`range`, `pipeline`) are read from the query string via
`useSearchParams` (per the `ParsedView` type comment at routes.ts:204 and the sibling
`login`/`runHistory` screens' handling) — `parseViewPath` only ever sees path segments, so
whatever extra segment follows `/analytics/` is parsed, discarded, and never validated or
rendered. The address bar and the rendered page diverge exactly as ADR-0018 says they must not:
"all 34 screens render behind one required catch-all segment" implies every URL that segment
parses to something either renders the matching screen or 404s — a URL that parses to a real
screen it was never meant to name is the same class of violation as one that parses to no screen
at all.

`routes.analytics()` (`routes.ts:144-146`) only ever builds `/analytics${queryString}` — no
in-app navigation constructs a deeper `/analytics/*` path — so this is reachable only via a typed
or shared URL.

## Expected vs actual

- **Expected:** an authenticated user hitting a nonexistent sub-path under `/analytics` gets a
  404/not-found (the existing `screen === "unknown"` -> `notFound()` gate at page.tsx:3724), or an
  actual redirect — matching how every other unrecognized deeper path is meant to behave.
- **Actual (INFERRED, not yet reproduced):** the address bar stays on the bogus
  `/analytics/<sub-path>` while the real, fully-functional Analytics page renders underneath it —
  a URL/content mismatch, just with a legitimate screen instead of the dashboard.

## Why the root cause implies this

ISS-238's root cause is the missing `segments.length === 1` guard on a single-condition `head ===
X` branch in `parseViewPath`. `analytics` has that exact same missing guard, verified by reading
the same function. The only reason its symptom differs from `register`/`login`/`admin` is that
`initialMainViewFor` happens to enumerate `analytics` explicitly while it omits the other three —
that is a downstream branching difference, not a different root cause. Filed as its own card
because "renders the wrong-but-real screen" is a materially different observable defect than
"renders the dashboard," and because it is a separately reproducible symptom on its own URL
prefix.
