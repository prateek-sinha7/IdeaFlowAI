# ISS-834

Sibling of [ISS-832](20260922-2001-ISS-832.md), INFERRED — a latent hazard,
not a currently-reproducing defect.

`frontend/src/store/api/capabilities.ts:34-38` defines `capabilitiesApi.get`,
a second implementation of `GET /api/capabilities` built on the axios `http`
client (`store/api/http.ts`) instead of `lib/api.ts`'s `fetch`-based
`request()`. `frontend/src/store/api/http.ts` has no cache/dedupe/in-flight
logic anywhere — confirmed:
`grep -n "cache\|dedupe\|dedup\|inFlight\|TTL" frontend/src/store/api/http.ts`
returns nothing. Every `store/api/*.ts` fetcher built on it, including this
one, is exactly as uncached today as `getCapabilities`/`getWorkflows`/`getMe`
were before FIX-617/FIX-616/ISS-801 wrapped them in `lib/api.ts`.

`capabilitiesApi.get` is re-exported through `store/api/api.ts:11,29,48` as
`api.capabilities.get` / `capabilitiesApi`; that file's own header comment
describes it as the "Consolidated axios-based API client" — the surface new
code is steered toward. A repo-wide grep
(`grep -rn "capabilitiesApi\.get\|\.capabilities\.get(" frontend/src`) finds
**zero** callers — it is dead code today, so it contributes none of
QA-PS-046's observed duplication (this corrects
[ISS-798](20260922-1631-ISS-798.md)'s implication that it does — see
[ISS-832](20260922-2001-ISS-832.md)).

Same shape [ISS-813](20260922-1854-ISS-813.md) already confirmed for
`userWorkflowsApi.get`: a second, axios-based, uncached implementation of an
endpoint `lib/api.ts` also serves, that a `lib/api.ts`-only fix (FIX-617,
FIX-616) cannot reach. There the hazard was already live (two real callers
found). Here it is not yet live, but the shape is identical and the trap is
the same: the next component that reaches for `api.capabilities.get()` — the
path the codebase's own comment steers new code toward — silently
reintroduces the exact duplication FIX-617 just closed, with no test or card
watching that file for it.

Not filed as reproducing today. Would be confirmed the moment any new caller
is added to `capabilitiesApi.get` / `api.capabilities.get`; until then the
fix is either deleting the dead duplicate or routing it through the same
`cachedGet()` so it can never regress silently.
