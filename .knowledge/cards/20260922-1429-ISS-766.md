# ISS-766

## Description

Sibling of the root cause analyzed on **[ISS-705](20260922-1050-ISS-705.md)** for
bug **QA-PS-025** (`BUGS.md#qa-ps-025`) — a regression check on the one prior fix
that targeted this exact symptom for one narrow case.
**[FIX-111](20260724-FIX-111.md)** (2026-07-24) fixed the identical
"`prototype-build` runs `single_shot`, never writes `prototype.html`" failure for
ONE specific scenario: a user replicating the native prototype pipeline's own
`prototype-specify -> prototype-plan -> prototype-build` agents through the custom
composer with the `prototype.html` deliverable selected. Its fix was a targeted
hack in `frontend/src/components/workflow/IdeaInputPage.tsx`: whenever
`deliverableOverride.name === "prototype.html"` AND `prototype-build` was in the
composed agent list, it injected `"prototype-build": { strategy: "task_loop" }`
into `mergedSelections` before launch — bypassing the need for any composer lever
at all, for that one literal agent id.

Reading both of today's composer launch entry points shows that mechanism no
longer exists in either of them. `IdeaInputPage.tsx`'s current `mergedSelections`
construction (lines 1520-1526) is a plain conditional merge of `__deliverable__`
onto the raw `selections` map — no `prototype-build` string, no `task_loop`
string, appears anywhere in the file (`grep -c "task_loop"
IdeaInputPage.tsx` → 0). The custom composer has also grown a second, newer entry
point since FIX-111 was written — `frontend/src/components/workflow/composer/ComposerPage.tsx`
— whose `mergedSelections` construction (lines 1048-1051) is the same shape of
plain merge and likewise contains no `prototype-build`/`task_loop` special case.
Whether this is a straight regression (the block was deleted when the composer
selections mechanism was generalized for ADR-0010/skills-folding) or the mechanism
simply never migrated when `ComposerPage.tsx` was introduced as a newer entry
point is not determined by this read alone — either way, the effect today is the
same: the one scenario FIX-111 shipped a fix for is unprotected again.

## Expected vs Actual

Expected: composing the native `prototype-specify -> prototype-plan ->
prototype-build` triple through either current composer entry point, with the
`prototype.html` deliverable selected, launches `prototype-build` under
`task_loop` (matching FIX-111's verified behavior and the native `prototype`
pipeline it replicates).

Actual: neither `IdeaInputPage.tsx` nor `ComposerPage.tsx` contains any code path
that inspects the deliverable override and the composed agent list together to
inject `strategy: "task_loop"` for `prototype-build`. That scenario now depends
entirely on the general composer lever ISS-705/[ISS-765](20260922-1428-ISS-765.md)
describe as missing — and today there is no lever, general OR
`prototype-build`-specific, that can produce it.

## Evidence

- `.knowledge/cards/20260724-FIX-111.md` — the original fix: "When
  `deliverableOverride.name === "prototype.html"` AND `prototype-build` is in the
  agent list, inject `"prototype-build": { strategy: "task_loop" }` into
  `mergedSelections`" in `frontend/src/components/workflow/IdeaInputPage.tsx`.
- `frontend/src/components/workflow/IdeaInputPage.tsx:1520-1526` (current) —
  `const mergedSelections = deliverableOverride ? { ...selections, __deliverable__:
  deliverableOverride } : selections;` — no conditional on `prototype-build` or
  `task_loop` anywhere nearby or elsewhere in the file.
  `grep -n "task_loop" frontend/src/components/workflow/IdeaInputPage.tsx` returns
  no matches.
- `frontend/src/components/workflow/composer/ComposerPage.tsx:1048-1051` (current) —
  `const effectiveDeliverable = runConfig?.deliverable ?? deliverableOverride; const
  mergedSelections = effectiveDeliverable ? { ...withSkills, __deliverable__:
  effectiveDeliverable } : withSkills;` — same plain-merge shape, same absence of a
  `prototype-build`/`task_loop` special case.
  `grep -rln "prototypeStepOverrides" frontend/src/` (the local variable name
  FIX-111's card implies for the injected overrides) returns zero files anywhere in
  the frontend tree.
