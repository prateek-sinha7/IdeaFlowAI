# ADR-0002: `workflow` is the only vocabulary

## Context and Problem Statement

One concept has two names, split by which subsystem you are reading:

| `workflow`                     | `pipeline`                            |
| ------------------------------ | ------------------------------------- |
| `agents/workflows/<id>/workflow.yaml` | `pipeline_type`                |
| `WorkflowCompiler`             | `PIPELINE_AGENTS`                     |
| `CompiledWorkflow`             | `get_pipeline_agents()`               |
| `workflow_runs` (DB table)     | `run_pipeline` (WS message)           |
| `WorkflowResolver`             | `pipeline_complete` (event)           |

This is not an unresolved disagreement. It was decided in
`specs/003-workflow-engine-decoupling/plan.md:40`:

> **Q1. Vocabulary: should we rename `pipeline/pipeline_type` to `workflow`
> everywhere?**
> **Answer:** Unify on **`workflow`** as the primary term. Keep `pipeline_type`
> only as a temporary migration alias until callers move.

`workflow` won. The callers never moved. The alias was never removed, and every
subsequent change was written against whichever term was already local to the
file being edited. The "temporary" side is now the larger one — roughly 3,300
occurrences across 207 backend Python files and 3,400 across 226 frontend
TS/TSX files.

Two things kept it alive, and both must be closed or it will stall a second
time:

- **The decision was invisible.** It sits at line 40 of a thousand-line plan
  document for a different refactor. There was no ADR, nothing enforcing it,
  and no reason for anyone reading `engine.py` to know it existed.
- **`backend/CLAUDE.md` taught the retired term as current.** The architecture
  guide new work is written against documents "Adding a Pipeline",
  `PIPELINE_AGENTS`, and `compile_for_run(pipeline_type)`. A guide that
  contradicts the decision reintroduces the term faster than a rename removes
  it.

The cost is not only aesthetic. The two vocabularies mark a real seam: the
registry (`pipeline_type` → which agents belong) and the manifest
(`workflow.yaml` → how they run) are two sources of truth for one workflow,
and the shared string is the only thing coupling them. Reasoning about that
seam while the two halves are named differently is materially harder.

## Decision

`workflow` is the only vocabulary the system knows. `pipeline` is **removed**,
not deprecated — no alias survives the migration, because the previous attempt
failed precisely by leaving one.

The rename lands in three tiers, in order, each independently shippable:

- **Tier 1 — internal Python.** Identifiers that are never serialized:
  `PIPELINE_AGENTS` → `WORKFLOW_AGENTS`, `get_pipeline_agents` →
  `get_workflow_agents`, `SUPPORTED_PIPELINE_TYPES` →
  `SUPPORTED_WORKFLOW_TYPES`, `_INTERNAL_PIPELINES` → `_INTERNAL_WORKFLOWS`,
  plus local variables and internal parameters. No contract changes; the
  existing suite is the full verification.
- **Tier 2 — the wire.** `run_pipeline` → `run_workflow`, `pipeline_complete`
  → `workflow_complete`, `pipeline_run_id` → `workflow_run_id`,
  `pipeline_type` → `workflow_type`. Breaking, and therefore backend and
  frontend in one coordinated change. Ingress accepts both key spellings for
  one release so an in-flight run or a stale browser tab does not break
  mid-stream; egress emits only the new names. The golden characterization
  snapshots under `tests/agents/characterization/golden/` assert these keys
  byte-for-byte and are regenerated as part of this tier.
- **Tier 3 — the database.** Two columns:
  `workflow_definitions.base_pipeline_type` and `handoffs.pipeline_output`.
  The `workflow_runs` table is already correctly named and its
  `pipeline_run_id` column was dropped in migration 0012, so this tier is the
  smallest.

## Why this is deferred, not scheduled

The rename touches ~433 files (207 backend Python, 226 frontend TS/TSX). A
change of that width conflicts with **every** branch open at the time it
lands, and the cost is paid by whoever has to rebase — not by the change
itself. That makes the merge window, not the work, the binding constraint.

This is not a disagreement with the decision. `workflow` is still the right
term and `pipeline` is still debt. It means the rename needs a moment when few
branches are open, and it should land as one atomic change at that moment
rather than as an incremental drip that keeps the conflict surface permanently
open.

Until then the two vocabularies coexist knowingly. The table above is the
translation key; `pipeline_type` and `workflow.yaml` name the same thing.

## Consequences

**Accepted costs.** Tier 2 is a breaking protocol change requiring a
coordinated release. Regenerating the golden snapshots temporarily removes the
protection they exist to provide — the regeneration diff must be reviewed as
a rename-only change, not accepted wholesale. Tier 1 touches nearly every test
file, so it must land as one atomic change rather than a drip.

**Enforcement.** A grep gate fails CI when a `pipeline` identifier appears
outside the allowed set. Without it this ADR is another line 40 in another
document. The gate carries an explicit, shrinking allow-list for anything a
tier has not yet reached, so the remaining debt is visible and countable
rather than assumed gone.

**Out of scope.** `Pipeline` in its ordinary English sense (a CI pipeline, a
data pipeline in a comment) is untouched. The gate matches identifiers, not
prose.
