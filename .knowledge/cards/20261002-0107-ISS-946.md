# ISS-946

## Description

Found while fixing QA-KB-017 ([FIX-705](20261002-0107-FIX-705.md)) and left open on purpose.
FIX-705 gates every user-supplied model id at create, PATCH and the HTTP launch. The launch gate
re-reads a saved row's manifest, which also catches an account downgraded after it saved a premium
step model. A run started by a spec-014 conditional route does not pass through that launch:
`run_trigger_workflow` mints it directly.

## Evidence (read, not driven)

- `backend/agents/execution_engine/kernel_services.py:1486` defines `run_trigger_workflow`. For a
  user row (`workflow_ref` that is not a file manifest) it loads `manifest_json` through `_owned`.
  When the row has `steps` it compiles at `trust="db"` (`:1640`). Then it calls
  `_launch_run_core` (`:1662`) with `model_overrides={}` (`:1677`) and
  `user=SimpleNamespace(id=ectx.owner_id)` (`:1678`).
- Nothing on that path calls `_model_entitlement_error` (`backend/app/api/run_engine.py:609`) or
  `can_use_model`. The step models reach the resolver as tier 2, which checks catalog membership
  only (`backend/agents/model_policy.py:249-258`).
- The session model is safe on this path: the namespace user has no `preferred_model`.

Exposure is narrow. Since FIX-705, a save with a premium model is refused for basic, so the row
must have been saved before FIX-705, or while the owner was on a paid tier. It must also be the
target of a conditional route.

## Why it was not fixed in FIX-705

The gate needs the caller's tier, and the tier comes from `effective_tier(user, principal)` on a
request's verified token (ADR-0013). A trigger fires inside a running run, so there is no request
and no principal. Picking a tier source is a design decision, not a mechanical extension. The
options are the tier the parent run was launched under (which would have to be persisted on the
run) or a projection read (forbidden by ADR-0013). The kernel side also cannot import the gate
beyond the lazy `app.api.run_commands` import it already carries.

## Fix direction

Persist the launch-time effective tier on the parent run, or on `ExecutionContext`, and have the
app side of the trigger (`_launch_run_core` or a thin wrapper around it) run
`_model_entitlement_error(tier, manifest=row.manifest_json)` before minting.
