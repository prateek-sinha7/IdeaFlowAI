## Description

Console error "Maximum update depth exceeded" occurring 26+ times per SSE frame
during active pipeline runs, causing degraded performance.

## Root Cause

`useEffect([pipelineState])` at page.tsx syncs `useWorkflow.pipelineState` into
the run store for the live build path (FIX-201 bridge):

```typescript
useEffect(() => {
  runStore.updatePipelineState(runId, () => pipelineState);
}, [pipelineState]);
```

The loop:
1. SSE frame → `handlePipelineMessage` → `setPipelineState(new obj)` → `pipelineState` changes
2. Effect fires → `updatePipelineState` → `project` → `setViewedState(new obj)` → re-render
3. Re-render: `pipelineState` from `useWorkflow` is still the same new object → BUT React sees the dep changed → effect fires again
4. Each SSE frame triggers 26+ re-renders before React's depth detector stops it

## Fix

Coalesce the `updatePipelineState` calls via `requestAnimationFrame`:

```typescript
const syncRafRef = useRef<number | null>(null);
useEffect(() => {
  // ... guards ...
  if (syncRafRef.current !== null) cancelAnimationFrame(syncRafRef.current);
  const snapshot = pipelineState;
  syncRafRef.current = requestAnimationFrame(() => {
    syncRafRef.current = null;
    runStore.updatePipelineState(runId, () => snapshot);
  });
  return () => { /* cleanup */ };
}, [pipelineState]);
```

Each SSE frame cancels the pending rAF and schedules a new one with the latest
snapshot. Only one `updatePipelineState` call fires per ~16ms animation frame
instead of 26× per frame.

Also added `syncPipelineStateOnly` to `useRunStateStore` — a no-project variant
of `updatePipelineState` that updates `entry.pipelineState` without calling
`setViewedState`, for use when the UI projection is already handled by another path.
