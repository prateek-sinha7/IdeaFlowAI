# ISS-935

## Description

Sibling of [ISS-398](20260828-2106-ISS-398.md) (QA-KB-017). A workflow whose steps are a manifest (`{"steps": [...]}`) can name a model per step (`steps[i].model = {model, fallback, effort, ...}`). Nothing on the save path or the launch path looks at that id, and the launch path additionally forwards the request body's override maps without validating them at all.

Basic accounts can reach this shape. The built-in canvas "save my version" posts a `manifest` for `user_stories` and `ppt` (`frontend/src/components/workflow/IdeaInputPage.tsx:1769-1774`, `LaunchWizard.tsx:972`, spec 016 override), and the Composer's full-manifest save and inline "Run once" do the same (`ComposerPage.tsx:901-919`, `:1140`). The Canvas Model lever is serialised into `steps[i].model` by `frontend/src/store/api/userWorkflows.ts:359-368`.

## Why the root cause implies it

Same missing tier check, plus a missing catalog check, in the shape the Canvas uses for full saves. [ISS-398](20260828-2106-ISS-398.md)'s "the three downstream routes inherit the fix" does not hold: Case 3 never reaches `_validate_model_overrides`.

## Evidence

CONFIRMED, read:
- `backend/agents/workflows/compiler.py:1404-1449` (`_compile_model_policy`) records `model` and `fallback` as given; the only checks are key names and `effort`. No catalog membership, no tier.
- Save: `backend/app/api/user_workflows.py:138-198` (`_validated_manifest`) checks `instance_id` and compiles at `trust="db"`; it persists at `:816-820` (override upsert) and `:861-865` (insert), and PATCH at `:997`.
- Override replay: `backend/agents/execution_engine/overrides.py:87-130` compiles the saved steps at `trust="db"` and takes `.steps` as they are.
- Launch, Case 3: `backend/app/api/run_commands.py:3722-3733` skips `_validate_model_overrides` and the selections re-validation for `USER_WORKFLOW_MANIFEST`, justified by "the compiler's own trust=db checks ... a stricter, per-step equivalent, not a gap". The compiler's trust checks cover capabilities, not model ids (see the first bullet). `model_overrides = body.model_overrides or {}` (`:3727`) is still forwarded to `_launch_run_core` (`:3826`, with `selections=body.selections` at `:3833`) and on to `engine.execute`. Only Case 2 replaces the body's map with the saved row's (`:3319-3320`), so in Case 3 the request body's map is what runs.
- The resolver trusts tier-1 overrides outright (`backend/agents/model_policy.py:215-227`); only tier 2 and 3 get an `is_allowed` re-check (`:249-271`), and explicit `fallback` entries are catalog-checked only (`:317-323`).
- An inline manifest takes `pipeline_type` from the request (`run_commands.py:3397-3401`), and the entitlement gate keys on that (`:3489`).

CONFIRMED, executed offline (scratch probes; stub engine; nothing written to the repo):
- `WorkflowCompiler._compile_model_policy({"model": "evil.attacker/unknown:latest"}, ...)` returns a `ModelPolicy` carrying that string; `ModelResolver(model_overrides={"custom-agent:x": "evil.attacker/unknown:latest"}).resolve(...)` returns the same string.
- Save (harness `test_user_workflows_api.py`, basic): `POST /api/user-workflows` with `base_pipeline_type=user_stories`, `manifest={"steps":[{"agent":"domain-analyst","model":{"model":<opus-4-6>}}]}`, `overrides_pipeline_type="user_stories"` returned 201 and stored the Opus step model (pro: 201).
- Launch (harness `test_rest_run_launch_api.py`, basic, `pipeline_type=user_stories`): an inline manifest with one step carrying Opus returned 200, one run minted, and the engine's compiled plan had `custom-agent:a1` on Opus. A Case 3 launch with `model_overrides={"custom-agent:a1": "evil.attacker/unknown:latest"}` returned 200, one run minted, and the engine received the unknown id.

INFERRED, not driven: that an unknown id then fails only at the provider call after the run was minted; that a saved Case 3 row replays the same way (same code path, saved row compiled at `trust="db"`); and that `run_trigger_workflow` (`backend/agents/execution_engine/kernel_services.py:1486`) can replay a user row's manifest without ever passing launch ingress (it passes `model_overrides={}`, `:1677`, so only the manifest steps matter).

## Expected vs actual

- Expected: a basic account saving or launching a manifest whose steps name a premium model is rejected (403); an unknown id is rejected (422) at save rather than failing mid-run.
- Actual: accepted and persisted or run; the body maps of a Case 3 launch are not validated at all.

## Fix direction

The gate described on [ISS-398](20260828-2106-ISS-398.md), applied to this shape:
- Save: walk `manifest["steps"]` (recursing `subagents.steps`) for `model.model` and each `model.fallback` entry, checking catalog (422) then tier (403). `_validated_manifest` has no tier today, so the tier has to be passed in from create and PATCH.
- Launch: for Case 3, check `body.model_overrides`, `body.selections` and the compiled plan's user-authored step models. Do not walk the compiled plan of a file-backed built-in (Case 1): its manifest and `AGENT.md` may declare premium models for every tier on purpose; gate only user-authored sources (saved manifest rows, inline manifests, an enabled override's steps, the body maps).
- Correct the skip comment at `run_commands.py:3722-3726`, which is wrong for model ids.
- Reading the stored manifest at launch also closes the downgrade-after-save edge the agreed minimal fix left out of scope.
