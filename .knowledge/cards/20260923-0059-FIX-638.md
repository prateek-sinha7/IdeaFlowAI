# FIX-638

This fixes what was left of `BUGS.md#qa-ps-048` after
[FIX-637](20260922-2358-FIX-637.md). The 6-verifier reopened the bug on the
report's line "No re-fetching of the full run data (829 KB) on every tab
switch". It resolves [ISS-853](20260922-2359-ISS-853.md) (the root) and its
siblings [ISS-854](20260923-0028-ISS-854.md),
[ISS-855](20260923-0028-ISS-855.md) and [ISS-856](20260923-0028-ISS-856.md).

## What was wrong

- **The Steps tab.** Before this fix, the divert-link effect in
  `AgentThinkingTab.tsx:201-258` was keyed on `[runId, liveDivertedToRunId]`.
  Every mount made these requests, in this order:
  1. `getWorkflowDefinitions`, unconditionally. That is `GET /api/workflows`,
     about 30 KB, with no dedupe.
  2. `getWorkflow(token, runId)`, to read only `status` and `parentRunId`.
     That is the full run record: 829 KB on the reporter's run.
  3. For a diverted run, a `getWorkflows({ limit: 100 })` reverse scan. For a
     revision, `getWorkflow` on the parent instead.

  PreviewPanel mounts the Steps tab fresh on every switch (`activeTab ===
  "thinking"` inside `AnimatePresence`). Tab opens happen one after another,
  so FIX-637's in-flight `singleFlightGet` could never merge them.
- **The version switch.** `WorkflowHistory.handleSelectVersion` awaits
  `getWorkflow(token, memberId)`. It then hands `full` through `onOpenRun` to
  `handleSelectWorkflowRun` in `page.tsx`. Before this fix, that function
  fetched the same record again at `page.tsx:2999`. Two more callers did the
  same, by calling `getWorkflow(...).then(onSelectWorkflowRun)`:
  `DashboardLayout.tsx:2840` (notification) and `:3403` (toast).

## Root cause (from the cards, not re-derived)

- **ISS-853.** The effect refetched data the page already held.
  `DashboardLayout.tsx:714-720` fetches `runFamily` once per
  `contentSourceRunId` and hands it to PreviewPanel (prop at `:443`).
  AgentThinkingTab received no family-derived prop.
- **ISS-855.** The 100-run reverse scan dropped the link silently once the
  child fell outside the newest 100 runs. The family walk
  (`backend/app/api/runs.py:1563`, `_owned_family_members`) already includes
  divert children.
- **ISS-854.** `getWorkflowDefinitions` was a bare `request()` call, made
  before the effect knew whether there was any link to label.
- **ISS-856.** `handleSelectWorkflowRun` reads only `run.id` and always
  refetched the record.

I re-ran the blast-radius grep at fix time. It holds, with one correction to
the card:

- **AgentThinkingTab is mounted in two places.**
  - `PreviewPanel.tsx:1888`: the only mount that has a run id.
  - `WorkflowHistory.tsx:1111`: passes no `pipelineState`, so `runId` is
    `undefined` and the effect returns on its first line. ISS-853 said this
    mount "would need a family or the current fetch as a fallback". It needs
    neither.
- **PreviewPanel is mounted once**, at `DashboardLayout.tsx:3324`. That mount
  always passes `runFamily`, which is `null` while the family loads or when
  the read fails.
- **`getWorkflowDefinitions` has two callers:** AgentThinkingTab and
  `CanvasNode.tsx:105`. CanvasNode keeps its own module-wide promise, so a
  single-flight wrapper makes no difference to it.
- **`handleSelectWorkflowRun` has these callers:**
  - The T7 route effect, which passes a `{ id }` stub.
  - The `recentRuns` rows from AppHeader and DashboardLayout.
  - The list rows from `WorkflowHistory.handleSelectRun`.
  - Three callers that pass a record they have just fetched:
    `handleSelectVersion`, `DashboardLayout.tsx:2840` and `:3403`.

## What changed and why there

**1. `AgentThinkingTab.tsx`: new optional prop `runFamily`, and a rewritten
divert-link effect.**

- **When `runFamily` contains this run,** the effect reads this run, its
  parent and its divert child straight from the family, with no request.
  - Source link: when this run's status is `diverted`, the link goes to the
    member whose `parent_run_id` is this run.
  - Target link: when this run's parent is `diverted`, the link goes to that
    parent.

  These are the same rules as the old chain. The backend sets the root's
  `parent_run_id` to null, because the root's parent is outside the family.
  The old chain fetched that outside parent, got a 404, and showed no link.
  The result is the same.
- **When the family is not held,** the effect calls `getRunFamily(token,
  runId)`. "Not held" means `null`, absent, or a family that belongs to a
  different run. This read is small and single-flighted, so on a first paint
  it merges with DashboardLayout's own family read if that is still in flight.
- **The catalog is fetched only once a link is found.** `loadDefs()` runs just
  before `setDivertLink`.
- **The live-divert path is unchanged,** apart from the deferred catalog read.
- **`runFamily` is added to the effect's deps.** When DashboardLayout's family
  arrives after a fallback read, the effect reads it again from the prop.

**2. `PreviewPanel.tsx`: passes `runFamily={runFamily}` to the Steps tab.**
This is one prop and nothing else.

**3. `api.ts`: `getWorkflowDefinitions` now goes through `singleFlightGet`.**
This follows FIX-637's precedent. ISS-854 offered `cachedGet` or
`singleFlightGet`. I picked single-flight, which only merges requests that
are in flight together, because a TTL cache would hide a newly saved workflow
for its whole lifetime.

**4. `page.tsx` `handleSelectWorkflowRun`: fetches only when needed.** It now
reads `let fullRun = run; if (run.input === undefined) fullRun = await
getWorkflow(...)`. `input` tells a full record from a slim one:

- The full record always carries it: `WorkflowRunResponse.input: str`
  (`runs.py:111`), and the column is `nullable=False` (`workflow.py:46`).
- A list row never carries it: `WorkflowRunListResponse` (`runs.py:202`)
  leaves it out on purpose (KAN-131). A `{ id }` stub has no `input` either.

The guard sits inside `handleSelectWorkflowRun`, so every caller that passes
a full record benefits without adding a guard of its own. Slim callers still
fetch, so they still get the 403/404 access check. A caller that passes a
full record has already passed that check.

**Deviation from ISS-853's fallback.** ISS-853 chose to "fall back to today's
fetch ONLY while `runFamily` is still `null`". Today's fetch is the 829 KB
`getWorkflow(self)` call plus the 100-run scan. The three red tests assert
that neither ever happens, and they mount with no family held. With the
literal fallback, the ISS-853 and ISS-855 tests stay red. This fix's fallback
fetches the family instead, which is better on three counts:

- It answers the same three questions: this run's status, its parent and its
  divert child.
- It keeps the card's reason for having a fallback at all: the row must not
  go missing while DashboardLayout's read is still in flight, or after it
  fails.
- It meets every sibling card in every state.

A missing prop falls back exactly like `null`. The tests do not pass by
treating "absent" as "skip".

## What this does NOT cover

- **[ISS-840](20260922-2030-ISS-840.md) (open, under QA-PS-038).** A
  click-driven open ends in a `router.push`, which remounts `page.tsx`. The
  new instance has a null `trackedRunIdRef`, so the T7 route effect runs the
  reopen again, including `GET /api/runs/{id}`. None of these four cards
  covers this. If the verifier counts two GETs on a history or version click,
  this is the cause.
- **Staleness.** The held family is read once per `contentSourceRunId`
  (`DashboardLayout.tsx:714-720`). Suppose a parent's `diverted` status lands
  after that read. The child's "Continued from" row then shows up at the next
  family read, meaning the next open or a reload. Before this fix it showed
  up at the next Steps remount. For the run being watched, the live path
  (`pipeline_diverted` → `liveDivertedToRunId`) still shows the row at once.
- **No live network counts.** No browser was used in this phase. Measuring
  the requests after the fix is the 6-verifier's manual re-run.
