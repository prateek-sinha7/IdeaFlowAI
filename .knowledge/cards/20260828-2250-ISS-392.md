## Correction

[ISS-287](20260828-1712-ISS-287.md) established the bug for
`BUG-20260828-025950-library-agents-id` (3/3 reproduced, confirmed no network request fires,
confirmed the Model reverts to "Default" on re-open) and correctly identified the Save-agent
button's `onClick` (`AgentsPopup.tsx:772-793`) as calling only `onSelectionsChange?.(localSelections)`
with no API call. Its Root Cause section, however, claims **"LibraryPage mounts AgentsPopup
[`AgentCapabilitiesModal`] WITHOUT an `onSelectionsChange` prop."** Reading the actual current
call site shows this is factually wrong: `LibraryPage.tsx` DOES pass `onSelectionsChange`. The
real defect is one level deeper — even when the prop IS wired, it only ever reaches a
non-durable in-memory ref, because **no caller of `AgentCapabilitiesModal`, anywhere in the
codebase, has a real backend endpoint to call for this data.** ISS-287's reproduction, evidence
and screenshots are unaffected and remain the basis for the bug's confirmed status; this card
corrects only the ROOT CAUSE mechanism, the same way [ISS-363](20260828-2129-ISS-363.md)
corrected [ISS-258](20260828-1650-ISS-258.md) for a sibling component.

## Root cause (CONFIRMED — every line below was read)

`LibraryPage.tsx:1030-1043` (the drawer opened for `/library/agents/<agentId>`):

```tsx
<AgentCapabilitiesModal
  agent={{ ...selectedAgent.agent, skills: selectedAgent.savedSkills ?? selectedAgent.agent.skills }}
  agentIndex={selectedAgent.index}
  onClose={closeDetailModal}
  asDrawer
  initialSelections={selectedAgent.savedSelections ?? {}}
  onSelectionsChange={(next) => {
    // Persist the selections for this agent so reopening restores them.
    savedSelectionsRef.current[selectedAgent.agent.id] = next;
  }}
  ...
```

`onSelectionsChange` IS supplied — contra ISS-287. It writes into `savedSelectionsRef`, declared
at `LibraryPage.tsx:657` as a plain `useRef<Record<string, SelectionsMap>>({})`, with its own
comment at `LibraryPage.tsx:654-657` stating the actual (limited) intent: **"Persist per-agent
Config-tab selections across drawer open/close cycles ... surviving the drawer unmount"** — a
same-session cache, never claimed to survive a reload.

Inside `AgentsPopup.tsx`, `AgentCapabilitiesModal`'s Save-agent handler
(`AgentsPopup.tsx:772-793`):

```tsx
onClick={() => {
  // Persist the current selections to the parent (e.g. LibraryPage
  // savedSelectionsRef) so reopening the drawer restores them.
  onSelectionsChange?.(localSelections);
  setSaved(true);
  setTimeout(() => { setSaved(false); onClose(); }, 900);
}}
```

fires `onSelectionsChange?.(localSelections)` — which DOES reach `savedSelectionsRef` here — then
unconditionally shows a "✓ Saved" flash and closes, regardless of whether anything durable
happened. **Grepping the entire file for any network call confirms there is none**
(`grep -n "fetch(\|await api\.\|apiClient\.\|axios\.\|/api/agents\|PATCH\|PUT\b"
AgentsPopup.tsx` — every hit is a *comment* naming the ONE PUT/DELETE endpoint that exists in
this file, `/api/agents/{id}/prompt`, and each says it is explicitly NOT wired here):

- `AgentsPopup.tsx:265-269` (System Prompt section): "the Agent-drawer Config tab mounts this
  with `surfaceOnly` so the override PERSISTENCE is DEFERRED ... no durable write path is
  reachable from the drawer."
- `AgentsPopup.tsx:399-401`: "the drawer Config tab passes `surfaceOnly` ... so no durable
  override PUT/DELETE is reachable."
- `AgentsPopup.tsx:732-735` (directly above the Model/Validator/Gate/Retry levers): "durable
  override persistence is DEFERRED (no PUT/DELETE path reachable)."

So the Model/Validator/Gate/Retry levers in the Config tab have **no backend endpoint to call at
all** — not a missing prop, a missing API. `savedSelectionsRef` is the only sink that exists, and
it is `useRef({})`, reset to empty on every fresh mount of `LibraryPage`.

**The deep-link/cold-mount path never even attempts to seed it.** `LibraryPage.tsx:589-597` (the
`T15` effect that opens the drawer when the URL is `/library/agents/<id>` on first load):

```tsx
setSelectedAgent({ agent, index: ALL_AGENTS_COMBINED.indexOf(agent) });
```

— omits the `savedSkills`/`savedSelections` fields entirely (unlike the click-through path at
`LibraryPage.tsx:816-822`, which explicitly does `savedSelections: savedSelectionsRef.current[agent.id]`).
So `selectedAgent.savedSelections` is `undefined` on a cold/deep-link open, `initialSelections={selectedAgent.savedSelections ?? {}}`
(`LibraryPage.tsx:1039`) resolves to `{}`, and the Model shows "Default" — exactly the symptom
ISS-287 reproduced, and exactly what a validator's "cold load" reproduction cycle
(ISS-287 cycles 1 and 3 were both explicitly cold loads) will always hit, independent of whether
`onSelectionsChange` is wired.

## Why ISS-287's attribution was imprecise

The comment ISS-287 cites (`AgentsPopup.tsx:531-534`, real and accurately quoted: "Local per-agent
selections state for the Config tab when the caller does not supply `onSelectionsChange` (e.g.
LibraryPage drawer)") describes the GENERAL shape of the fallback code, using LibraryPage as an
illustrative example of "a caller that might not supply it" — but it is not a live description of
LibraryPage's actual current call site, which does supply it. Trusting the comment over the
call site produced the wrong specific claim.

## Expected vs actual

**Expected:** either the override is actually persisted (a network call fires and the value
survives a fresh navigation/reload), or the Library's agent-detail view does not present editable
Model/Validator/Gate/Retry controls behind a "Save agent" button that implies the change takes
effect — the same treatment already given to the System Prompt section (`surfaceOnly`) and to the
Skills tab when `onSkillsChange` is absent (`AgentsPopup.tsx:490-496`: "renders read-only rather
than offering controls that discard the click").

**Actual:** `onSelectionsChange` — wired or not — never reaches any backend endpoint; the only
sink is a same-session React ref that a cold/deep-link mount never even reads from.

## Where the fix belongs

Inside `AgentCapabilitiesModal` (`AgentsPopup.tsx:476`), once — not in `LibraryPage.tsx`, and not
by adding a per-caller workaround. It is the ONE shared component both production callers
(`LibraryPage.tsx:1030`, `AgentLibrary.tsx:332` — see [ISS-393](20260828-2251-ISS-393.md)) route
through, and neither has (or can be given, without a new backend endpoint) a durable sink. The
precedent for the honest fix already exists twice in this same file: `AgentPromptSection`'s
`surfaceOnly` gate and the Skills tab's `onSkillsChange`-presence gate both turn an
unpersistable control read-only instead of pretending to save it — though
[ISS-318](20260828-1956-ISS-318.md) shows the Skills-tab gate is itself wired wrong for this
exact `LibraryPage` mount (it supplies `onSkillsChange`, defeating its own `readOnly` contract),
the same class of defect one tab over. The Model/Validator/Gate/Retry levers and the "Save agent"
button need the same treatment — or, if durable per-agent overrides
are wanted as a real feature, a backend endpoint plus wiring `effectiveOnSelectionsChange` through
it, added once here so both callers inherit it.

`MOD-frontend-src-components-library`'s own `## Purpose`/`## Shape` documents `LibraryPage` as
having "no server state (everything is a static catalog import)" and delegating agent detail
straight to `AgentCapabilitiesModal` — the read-only-when-unpersistable direction is the one that
matches this module's own documented design intent; inventing new backend persistence for a
catalog-browsing surface would be the larger, less-proportionate change.
