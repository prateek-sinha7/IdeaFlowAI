# ISS-967

**Register source:** `QA-KB-048` in root `LEDGER.md` / `BUGS.md` (adjacent finding on the same restore path, found during its analysis on 2026-10-02).
**Root card:** [ISS-943](20261002-0037-ISS-943.md). This is NOT the same mechanism: ISS-943 is the plan-completion effect, this is the restore mapping.
**Claim status:** INFERRED. Every link below was read in the working tree on top of `024c03ef8`; nothing was run.

## What is broken

**Condition.** A saved prototype / ppt / ppt_v2 workflow whose roster contains an agent whose AGENT.md `pipeline_type` is `custom`
(the custom-utility pool). The wizard lets a user add one: the Advanced popup's picker reads `allAgents`
(`frontend/src/components/workflow/AgentLibrary.tsx:83`, `const { allAgents: ALL_AGENTS } = useAgentLibrary();`), which includes
custom agents, and `launch_run` accepts them (`registry.allowed_custom_agent_ids` is the pipeline's own agents plus
`PIPELINE_AGENTS["custom"]`). Such a roster is saved by `handleSaveWorkflow` (`LaunchWizard.tsx:940`).

**Expected.** Reopening the saved workflow shows, and Continue launches, the same roster that was saved.

**Actual (read, not run).** The draft restore resolves each saved id against `libraryAgents` and discards what it cannot find
(`LaunchWizard.tsx:428-433`):

```ts
const restored = d.agentIds
  .map((id) => libraryAgents.find((a) => a.id === id))
  .filter(Boolean) as AgentDef[];
if (restored.length > 0) setPipelineAgents(restored);
```

and `useAgentLibrary` builds `libraryAgents` WITHOUT custom agents (`frontend/src/hooks/useAgentLibrary.ts:33-36`:
`reduxAgents.filter((a) => !agentMatchesPipelineType(a.pipeline_type, "custom"))`). The custom-pool id resolves to `undefined`
and is dropped with no marker, while `restored.length > 0` stays true for the other agents. The screen, the launch draft
(`:1041`) and the next Save workflow (`:940`) then all lack that agent.

## Relation to the root cause

The drop happens today, independent of [ISS-943](20261002-0037-ISS-943.md): the plan never contains a custom-pool agent, so plan completion cannot bring one back. ISS-943's fix
makes a restored roster authoritative (exempt from completion), so after it the dropped agent stays dropped and the next Save workflow persists the loss. That makes this the
other way a restored roster silently differs from the saved one, which is why it is carded with ISS-943 and not left in a transcript. Unknown ids (an agent retired since the
save) are dropped the same way, where the launch would otherwise fail loudly with `invalid_agent_ids`.

## Fix direction

Resolve the restore through `allAgents` (the hook already returns it), in the restore effect only. Leave `libraryAgents` alone:
`defaultAgentsFor` (`LaunchWizard.tsx:206-209`) and other consumers rely on it excluding the custom pool. Whether an id that
resolves to nothing should be dropped silently or surfaced is a product call, not decided here.

## What settles it

An offline vitest in `LaunchWizard.test.tsx`'s harness: `preloadedState.agents` holding the five prototype agents plus one agent with
`pipeline_type: "custom"`, a `prototype.draft` whose `agentIds` includes that agent, click Continue, read the `prototype.draft` it
writes. Today its `agentIds` omit the custom agent.

## Resolution (QA-KB-048, 5-fixer, 2026-10-02)

Resolved by [FIX-714](20261002-1159-FIX-714.md). The restore now looks saved ids up in `allAgents`
(`LaunchWizard.tsx:435`), and the effect's deps gained `allAgents`. `libraryAgents` and `useAgentLibrary.ts` are
unchanged. The ISS-967 case in `LaunchWizard.savedRoster.iss943.test.tsx` XPASSes. The question this card left
undecided (an id that resolves to no agent at all is still dropped silently) moved to
[ISS-1044](20261002-1159-ISS-1044.md), which is open.
