# ISS-815

## Description

INFERRED sibling of **QA-PS-041** ([ISS-788](20260922-1816-ISS-788.md)). QA-PS-041's
root cause is that nothing in `SavedWorkflowsPage.tsx` guards an async trigger
against firing more than once (the mount-effect fetch at line 170). A "no
dedupe anywhere in this component" root cause implies the write side is worth
checking too, not just the read side that QA-PS-041 reported — so all three
kebab-menu mutation handlers were read directly.

## What was checked, and the result

- `handleRenameSave` (`SavedWorkflowsPage.tsx:185-193`) — `setRenameRow(null)`
  runs synchronously BEFORE the `await renameUserWorkflow(...)` call, so the
  modal (and its Save button) unmounts in the same tick the handler runs.
  **Self-guarded** — there is no button left to double-click.
- `handleDeleteConfirm` (`SavedWorkflowsPage.tsx:213-220`) — identical shape:
  `setDeleteRow(null)` runs before the `await deleteUserWorkflow(...)`.
  **Self-guarded**, same reason.
- `handleDuplicate` (`SavedWorkflowsPage.tsx:195-206`) — `setOpenMenuId(null)`
  closes the dropdown PANEL only. The kebab TRIGGER button
  (`SavedWorkflowsPage.tsx:110-119`, rendered unconditionally inside
  `KebabMenu`) stays in the DOM and stays enabled throughout the `await
  createUserWorkflow(...)` call (`SavedWorkflowsPage.tsx:199-203`). A user can
  reopen the same row's menu and click "Duplicate" again while the first
  request is still in flight — nothing in the handler or the button disables
  that path. **Not guarded.**

## Why this is worth a card

Two overlapping clicks fire two real `POST /api/user-workflows` calls (not
idempotent), creating two duplicate saved-workflow rows server-side for one
intended action — a visible, confusing defect if it fires, not just wasted
bandwidth. Filed as INFERRED: the CODE gap (no guard) is confirmed by direct
read; the user-facing CONSEQUENCE (an actual double row) is not yet
reproduced, since it needs a fast reopen-and-reclick or a throttled network
to trigger.

## Where the fix belongs

In `handleDuplicate` itself (`SavedWorkflowsPage.tsx:195`) — a local
in-flight guard (e.g. track the row id currently duplicating, checked at the
top of the handler and cleared in a `finally`) mirroring the synchronous-close
protection `handleRenameSave`/`handleDeleteConfirm` already get for free from
closing their modal before the await. This is the one handler in the file
that needs an explicit guard; the other two do not, and should not be
touched.

## Expected vs actual (to be measured)

Expected: reopening the menu and clicking Duplicate again while the first
duplicate is still saving either no-ops or queues behind it, but never issues
two `POST /api/user-workflows` calls for one logical "duplicate this row"
intent.

Actual: unmeasured — needs a throttled-network repro (e.g. Chrome DevTools
"Slow 3G" + two fast clicks reopening the menu) to confirm the row actually
duplicates twice.

## Related

Scoped to one file, one handler — no further links beyond the Depends-on
edge above.

## Resolved — 2026-09-22

[FIX-627](20260922-2050-FIX-627.md) added exactly the guard this card asks for:
a `duplicatingRef` `Set<string>` of row ids, checked at the top of
`handleDuplicate` and cleared in a `finally`. `handleRenameSave` and
`handleDeleteConfirm` were left alone, as this card prescribes.

The CONSEQUENCE this card filed as unmeasured is now measured. A/B with the
same steps, the POST held open 2s by a route handler that does not block the
Playwright driver (async API):

```
guard reverted (git stash) → POSTs: 2   ← the duplicate row, reproduced
guard in place             → POSTs: 1
```

The bug's own e2e test still reads 2 because its throttle is a `time.sleep(2)`
inside a SYNC route handler, which blocks the driver so the two clicks never
overlap — written up in [ISS-841](20260922-2050-ISS-841.md), not fixed by
editing the test.
