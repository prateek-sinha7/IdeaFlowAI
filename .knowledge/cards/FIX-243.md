## Description

The owner's Stop was thrown away whenever no in-process driver was live — and the next boot re-adopted the run and finished it at the owner's expense (ISS-089). POST /api/runs/{id}/cancel wrote no status at all in the not-live branch (run_commands.py:414-418 at 2df5324b): it set an in-memory asyncio.Event and armed an in-process escalation task, both of which die with the process. So after a restart, a deploy, or any resumed run whose Event was an orphan, the row stayed running/generating — inside restore_non_terminal_runs' non-terminal filter — and the next startup drove it to completion. This is the second half of the d5dbc9f2 incident: a 16,530,718-token run, $3.58, of which ≈$1.61 (~45%) was billed AFTER the API answered cancelled: true. Measured ceiling on this corpus is 37.3M tokens / $7.07 for one od_prototype build; all 14 metered runs, all time, total $17.75. Cache reads dominate, so this is a correctness-and-trust defect first and a cost defect second on a Haiku workload — roughly an order of magnitude worse on an Opus-tier model, which is what the fix insures against.

## Root cause

WorkflowRun.status is a projection of an in-process asyncio task's lifetime, never a durable record of what the system was asked to do. Every terminal-status write in the codebase executes inside a task (launch/revision driver CancelledError handlers, _reconcile_terminal_status, the restore branches); the HTTP command layer wrote none. A truth no task was alive to record simply was not recorded. The row's own proposed fix (Option B — a durable cancel_requested marker checked inside restore_non_terminal_runs) was REJECTED: it needs a migration or a new event type, edits the resume tier's most delicate three-branch classifier, misses branch (a) (waiting_for_user spawns _rearm_gate_run without ever calling _stamp_resume_marker, so a marker checked before the stamp would miss every gate-parked run), and leaves the row reading running to history/analytics//resume/the UI until the next boot — possibly forever. Option A writes the terminal status at cancel time: one function, no migration, no new vocabulary, and no change to restore_non_terminal_runs at all, because cancelled is already outside the non-terminal set and POST /resume already accepts it. The run moves from AUTOMATIC resume to EXPLICIT, owner-authenticated resume — which is what a Stop should mean.
