QA-PS-036 (see `LEDGER.md` / `BUGS.md#qa-ps-036`). Validated CONFIRMED 3/3, cold
navigation `/dashboard` → `/analytics` each cycle, `qa-admin@flowinqa.com`
(enterprise/admin), light theme. Every cycle produced the identical multiset of
`/api/*` calls (captured via `performance.getEntriesByType('resource')` right
after each fresh navigation, so no cumulative-log artifact):

- `GET /api/analytics/summary?range=30d` x2
- `GET /api/settings/preferences` x2
- `GET /api/capabilities` x2
- `GET /api/runs?limit=50` x2 — not displayed on `/analytics`
- `GET /api/workflows` x2 — not displayed on `/analytics`
- `GET /api/agents/library`, `/api/skills/library`, `/api/hooks/library` x1 each — not displayed on `/analytics`
- `GET /api/runs?limit=6` x1 — not displayed on `/analytics`
- `GET /api/auth/me` x1 (expected)

Same pattern on all 3 cycles — no timing/entry-path/session-age trigger needed,
it fires on every route mount.

## Root cause

Two independent defects compound:

1. **Duplicate fetches of shared data.** `AnalyticsPage.tsx:210` calls
   `getPreferences(token)` and `AnalyticsPage.tsx:237` calls
   `getCapabilities(token)` directly, instead of reading either from a shared
   cached provider. A second call to each of `/api/settings/preferences`,
   `/api/capabilities` and `/api/analytics/summary` comes from elsewhere in the
   always-mounted layout tree (not yet isolated to one file — see Note below).

2. **Off-page fetches from a globally-mounted layout.** `DashboardLayout.tsx`
   statically imports every page component (`AnalyticsPage`, `HomeLaunchGrid`,
   `LibraryPage`, `WorkflowHistory`, `AccountSettings`, `ComposerPage`, ...)
   and switches between them client-side rather than per-route code-splitting,
   so layout-level providers mount and fetch regardless of the active route.
   `RunConnectionProvider.tsx:289` (`refreshLiveRuns`) calls
   `getWorkflows(t, { limit: 50 })`, which hits `GET /api/runs?limit=50`,
   unconditionally on mount — this is the un-displayed runs fetch. The library
   (`agents/skills/hooks`) and `runs?limit=6` calls trace to the same
   always-mounted layout tree, not to `AnalyticsPage` itself.

## Note for analysis

The bug's original report (2026-09-17) measured 17 requests with
summary/preferences/capabilities each x4 and totalling 204 KB. This validation
(2026-09-22) measured the same defect shape but at x2, not x4, plus three
extra always-present calls (`agents/library`, `skills/library`,
`hooks/library`) the original report did not list. Two explanations, neither
ruled out: (a) Next.js React StrictMode double-invokes mount effects in the
dev server (no `reactStrictMode: false` found in `frontend/next.config.*`),
so whatever the true per-mount call count is gets doubled in this dev
environment — if the report's "4x" was also StrictMode-doubled, the
underlying defect is 2 independent call sites per endpoint, unchanged; or (b)
an intervening change (e.g. `FIX-524` touched `AnalyticsPage.tsx`, unverified
whether it removed a duplicate call site) reduced one of two duplicate call
sites between the two dates. Confirm the true production (non-StrictMode)
call count before treating the count delta as a partial fix.

### Resolved by analysis (QA-PS-036, 2026-09-22)

**(a) is correct; (b) is ruled out.** `grep -rn "getAnalyticsSummary(\|getPreferences(\|getCapabilities("
frontend/src --include="*.tsx" --include="*.ts"` (excluding tests and the
`lib/api.ts` definitions themselves) returns exactly one caller of each inside
`AnalyticsPage.tsx` — `:184` (`getAnalyticsSummary`, deps
`[dateFilter, pipelineFilter, modelFilter]`), `:210` (`getPreferences`, deps
`[]`), `:237` (`getCapabilities`, deps `[]`) — and no second call site
anywhere in the always-mounted layout tree (`DashboardLayout.tsx`,
`RunConnectionProvider.tsx`, `app/[...view]/page.tsx`, `app/layout.tsx`).
`DashboardLayout.tsx:3030-3039` also confirms `AnalyticsPage` is rendered
behind `{mainView === "analytics" && (...)}`, not kept mounted alongside
`HomeLaunchGrid` or any sibling page — so a second, concurrently-mounted page
component cannot be the source either. `frontend/next.config.ts` sets no
`reactStrictMode` key, so Next's default (`true`) applies under `next dev`,
which mount→unmount→remounts every component once, double-invoking all three
`useEffect`s with the SAME closure/args — this is why both duplicates of
`analytics/summary?range=30d` carry the identical query string rather than
two different ranges. `FIX-524` (`AnalyticsPage.tsx:829`, the hardcoded
"Adaptive (effort: max)" row label) never touched these three effects, so (b)
is not the explanation. Net: the underlying defect is exactly ONE call site
per endpoint plus zero request-level dedupe — not two independent call sites
— consistent with the reporter's higher "4x" count being the DevTools Network
panel accumulating more than one load/interaction rather than a genuinely
different per-mount shape (same caveat already logged on
[ISS-784](20260922-1812-ISS-784.md) for `/dashboard`).

**Third source of the unused `runs`/`workflows` fetches, isolated.**
Root cause mechanism 2 above named only `RunConnectionProvider.tsx:289`
(mounted app-wide via `app/layout.tsx:51`, above the router). A second,
independent source exists: `frontend/src/app/[...view]/page.tsx`'s own
mount effect (`:990-1006`, deps `[isAuthenticated]`) unconditionally calls
BOTH `getWorkflows(currentToken, { limit: 50 })` (→ `GET /api/runs?limit=50`)
AND `getWorkflowDefinitions(currentToken)` (→ `GET /api/workflows`), with an
inline comment stating the reason: `"Pre-fetch the user-launchable workflow
catalog so HomeLaunchGrid can seed its card grid instantly from state instead
of making its own fetch."` `[...view]/page.tsx` is the one catch-all route
component for every path in the app (frontend invariant — see
`.knowledge/CONTEXT.md`), so this HomeLaunchGrid-only optimization fires on
every authenticated route, `/analytics` included, regardless of whether
`HomeLaunchGrid` is even mounted. This corroborates
[ISS-785](20260922-1620-ISS-785.md)'s looser "`page.tsx:968` (auth mount)"
attribution with the exact mechanism and its own justification comment — it
is a second, RunConnectionProvider-independent source of the same two unused
calls, not a duplicate of mechanism 2, and StrictMode doubles this effect too
(same missing-guard shape as `HomeLaunchGrid.tsx` in
[ISS-784](20260922-1812-ISS-784.md)).

**Fix implication:** a request-deduping/caching layer that every caller
(page components AND `page.tsx`'s own pre-fetch) routes through would collapse
BOTH the cross-component duplication (mechanism 1) and the StrictMode
double-invoke duplication in one mechanism — a double-invoked effect that
hits an in-flight/cached promise reuses it instead of firing a second
request. Do not "fix" the StrictMode symptom by disabling it
(`reactStrictMode: false`) — that hides the dev signal without touching the
underlying missing-cache defect, which still wastes bandwidth in production
every time two of these callers mount on the same page.

## Partial resolution + what the analysis missed (5-fixer, 2026-09-22)

**Mechanism 1 is fixed** by [FIX-617](20260922-1935-FIX-617.md), measured on a
cold `/analytics` load against the live tree: `/api/analytics/summary?range=30d`,
`/api/settings/preferences` and `/api/capabilities` now fire exactly ONCE each
(the test's first assertion passes), where this card's validation measured each
at x2. Total `/api/` requests on the load: 10, down from the 15 recorded in
Evidence above. The fix is the "Fix implication" note's own prescription —
`cachedGet()` in `frontend/src/lib/api.ts`, URL+token keyed — with one
correction: it has to keep the RESOLVED value, not just the in-flight promise,
or [ISS-796](20260922-1825-ISS-796.md)'s later-mounting caller is missed.

**Mechanism 2 is NOT fixed, and this card's source list for it is incomplete.**
Two of its calls were removable with no behaviour change and are gone —
`RunConnectionProvider.tsx:289` no longer queries a run list it then discards
(its `tabOwnedIds.size === 0 ? false` filter dropped every row on any tab that
has launched nothing), and `page.tsx`'s `getWorkflowDefinitions` prefetch is
deleted (its `homeWorkflows` prop is destructured at `DashboardLayout.tsx:458`
and never read; `HomeLaunchGrid` moved to Redux and takes no such prop). What
remains is `/api/runs` x2 and `/api/workflows` x1, and it comes from a THIRD
source this card never examined:

- `frontend/src/store/listenerMiddleware.ts` — a `signedIn` listener dispatching
  `fetchWorkflows()` (`GET /api/workflows`), `fetchRecentRuns()`
  (`GET /api/runs?limit=6`, `globalSlice.ts:7` `RECENT_RUNS_LIMIT = 6`) and the
  three `/api/*/library` preloads. Its own comment claims `signedIn` "fires only
  from the dashboard/home page's mount-time auth check", but it is dispatched at
  `frontend/src/app/[...view]/page.tsx:892`, the catch-all for EVERY route. This
  is the exact multiset of off-page calls this card's Evidence block could not
  attribute, `/api/runs?limit=6` included.

**And this card's "Expected" cannot be met without a product decision.** Its
premise — that run history and the workflow catalog are "not displayed on
`/analytics`" — does not hold for the app shell: `<AppHeader` renders at
`DashboardLayout.tsx:2715`, ABOVE the `mainView === "analytics"` branch at
`:3030`, and consumes both payloads (`AppHeader.tsx:126` `useWorkflowLabels()`
← `state.global.workflows` ← `GET /api/workflows`; `AppHeader.tsx:176`
`recentRuns.filter(r => LIVE_STATUSES.has(r.status))` ← `GET /api/runs?limit=50`).
Escalated with options and consequences in
[ESCALATIONS.md#qa-ps-036](../../ESCALATIONS.md).
