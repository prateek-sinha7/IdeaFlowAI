## What happened

```
test_picking_a_version_in_the_menu_writes_the_pin_into_the_url
  AssertionError: the Version menu did not write the pin into the URL —
  url is 'http://localhost:3000/runs/77f74563-fa19-4f0b-84fd-d0224f89a54a'
```

## The app is right, the test was wrong

`PreviewPanel.tsx:645` — `const unpinnedRunId = liveRunId ?? latestId;` — and
`handleSelectVersion` passes a `null` pin when the picked member IS
`unpinnedRunId`. A pinned deep link opens the family ROOT in the shell
(`contentSourceRunId` → `liveRunId`), so on `/runs/{root}/versions/2` the root
is `unpinnedRunId`, and picking `Version v1` resolves to "no pin needed": the
bare `/runs/{root}` already renders v1.

Nothing [ISS-296](20260828-1724-ISS-296.md) asked for is lost — that URL is
shareable, survives a refresh, and carries the version across tabs. And keying
the shortcut on `unpinnedRunId` rather than on `latestId` is precisely what
ISS-607/610/611 needed; their tests pass. Two contracts collided and only the
older test was wrong.

Why it went unnoticed: in the 2-member ISS-230 family the only version
reachable from v2 is v1 — which is the shortcut case. That fixture cannot
distinguish "the pin was written" from "the pin was lost".
