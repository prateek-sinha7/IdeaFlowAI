# FIX-426

## What was wrong

`context_provider:conversation` built its ≤6,000-char, six-turn transcript by
materialising the run's **entire** `run_events` log server-side and filtering it in
Python. On the worst run in the local corpus that is 12,123 rows / ~9.2 MB to render a
block the model reads a few hundred tokens of. Full evidence in
[ISS-101](20260812-1232-ISS-101.md).

Not a token cost and not a regression — the model never sees the discarded rows, and
before [FIX-233](20260812-1232-FIX-233.md) the deleted `read_events` tool triggered the
identical read because the system prompt ordered the model to call it. What FIX-233
changed is the **frequency**: it wired this provider into `_load_conversation_context`
(`concierge.py:663`) on every Concierge turn, so the drain went from
"whenever the model chose to call a tool" to unconditional.

## Root cause

`backend/agents/capabilities/context_providers/conversation.py:99` —
`ConversationProvider._read_chat_events` called `scoped_store.read_events(run_id, 0)`,
the **unbounded replay primitive** (`agents/authz.py:315`, the one behind SSE resume,
the events API, engine resume and `append_event_next_seq`'s seq allocation), then
`_render_transcript` dropped everything that was not `chat_message` / `chat_reply`.

The bounded counterpart already existed and needed no new code:
`ScopedStore.read_events_of_types(run_id, types, *, limit, after_seq=0)`
(`agents/authz.py:380`), added by FIX-233 precisely so bounded READERS stop slicing a
whole log in Python. Its own docstring names this case: "On the worst run in the local
corpus that is 20 rows instead of 12,123 (9.2 MB)."

## What changed and why there

**`backend/agents/capabilities/context_providers/conversation.py`** — the fix is inside
`_read_chat_events`, the single chokepoint every caller routes through. Both live
callers of the provider (the engine's `injects:[conversation]` context assembly and the
Concierge's `_load_conversation_context`) reach the store only through
`ConversationProvider.load` → `_read_chat_events`, so one edit covers both; grepped and
confirmed there is no sibling caller doing its own chat-transcript read.

- `_MAX_CHAT_ROWS = 200` added beside the existing `_DEFAULT_BUDGET` / `_DEFAULT_KEEP_RECENT`
  module defaults. Chosen so the cap can never truncate a transcript the budget would
  have kept: 200 turns is already 30 chars/turn at the 6,000-char default budget. It
  mirrors `concierge.py`'s `_PROGRESS_SCAN_LIMIT = 200`.
- The read became
  `await scoped_store.read_events_of_types(run_id, _CHAT_TYPES, limit=_MAX_CHAT_ROWS)`.
  `_CHAT_TYPES` is the frozenset the module already declared for the Python-side filter,
  so the type allow-list is now pushed into the SQL `IN` list and the row cap into
  `LIMIT` — the same rows, selected in the database instead of in the process.
- The `except` arm and its warning kept, method renamed in the message only. Two stale
  docstring lines naming `read_events` updated to the bounded method.

`_render_transcript` keeps its own `etype not in _CHAT_TYPES` filter — untouched, and
now defence in depth rather than the only filter.

### The sibling test fake, and why editing it is not bending the app to the test

`tests/agents/test_conversation_provider.py`'s `_FakeScopedStore` exposed **only**
`read_events`, so after the swap it hit the provider's degrade path and two of its nine
tests went red on an `AttributeError` — exactly the trap [ISS-101](20260812-1232-ISS-101.md)
flagged in advance ("its degrade-to-`{}` error path would also hide the change from any
duck-typed store fake that lacks the new method").

The failure was in the **double**, not the assertions: a real `ScopedStore` has had
`read_events_of_types` since FIX-233, so the fake had drifted from the collaborator it
stands in for. `read_events_of_types` was **added** to it (honouring the same
`raises=True` error simulation) and `read_events` left in place, because production has
both. **No assertion, no expected value and no test name was changed.**

### Deliberately NOT changed

- **`read_events` itself** — it stays unbounded on purpose (`authz.py:391`): it is the
  replay primitive, and capping it would silently truncate SSE/engine resume.
- **No `hasattr` fallback to `read_events`.** It would be dead code in production (the
  real store always has both) and would keep alive the dependency the new test exists to
  prove gone (INV-12: nothing may shadow its replacement).
- **`conversation_keep_recent`** — read at `conversation.py:144`, still set by nobody.
  Left as-is; a keep-recent above 200 could not fit the char budget anyway.
- The other unbounded `read_events(run_id, 0)` call sites (`engine.py` ×7,
  `run_commands.py` ×3) are outside this card's globs and carry their own cards
  (e.g. [ISS-125](20260812-1852-ISS-125.md) for `_stamp_resume_marker`).
