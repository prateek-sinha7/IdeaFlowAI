## What is suspected

INFERRED sibling of [ISS-800](20260922-1633-ISS-800.md) (QA-PS-048's root
cause), derived from reading — not yet browser-reproduced independently.

Two separate, unrelated effects both call `getRunSandbox` for the same run:

**1. `SandboxTab.tsx:1035-1066`** (the Workspace tab's own file listing):

```tsx
useEffect(() => {
  if (!runId) return;
  const token = getToken();
  if (!token) return;
  let cancelled = false;
  setListLoading(true);
  ...
  getRunSandbox(token, runId, selectedRef ?? undefined)
    .then((res) => { if (cancelled) return; ... })
    .catch((err: Error) => { if (!cancelled) setListError(err.message); })
    .finally(() => { if (!cancelled) setListLoading(false); });
  return () => { cancelled = true; };
}, [runId, selectedRef, setMedia]);
```

**2. `PreviewPanel.tsx:1341-1401`** (the header Download button's
deliverable-file resolver, fires on EVERY tab, not just Workspace, whenever
`pipelineState?.deliverableFilename` is falsy — true for a reopened
completed run with no live pipeline state, exactly this bug's own repro
step):

```tsx
useEffect(() => {
  setDeliverableFile(null);
  setDeliverableBundle(false);
  if (!activeRunId || (headerRunState !== "complete" && !sandboxSelectedRef)) return;
  let cancelled = false;
  void (async () => {
    ...
    let declared = pipelineState?.deliverableFilename ?? null;
    if (!declared) {
      const run = await getWorkflow(token, activeRunId);
      if (cancelled) return;
      declared = run.deliverableFilename ?? null;
    }
    if (!declared) {
      const listing = await getRunSandbox(token, activeRunId);
      if (cancelled) return;
      setDeliverableBundle(listing.files.some((f) => f.deliverable));
      return;
    }
    ...
  })();
  return () => { cancelled = true; };
}, [activeRunId, headerRunState, sandboxSelectedRef, pipelineState?.deliverableFilename]);
```

Both are `useEffect`s with no in-flight guard — `cancelled` blocks only the
post-resolution `setState`s, not the fetch calls — and `getRunSandbox`
(`api.ts`) has no dedupe of its own, same as every other fetcher ISS-800
named.

## Condition

Opening the Workspace tab on a completed run that declares no
`pipelineState?.deliverableFilename` (a reopened run with no live pipeline
state — this bug's own repro: "Open any completed run from history").

## Expected vs actual

**Expected:** `GET /api/runs/{id}/sandbox` fires once, when the Workspace
tab is opened (or not at all if the declared deliverable file is already
known).

**Actual (predicted):** two independent callers (`SandboxTab`'s own mount
effect, `PreviewPanel`'s download-resolver effect) each fire once, each
doubled by `next dev`'s Strict Mode = 4 total — matching BUGS.md's
originally reported `GET /api/runs/{id}/sandbox × 4` exactly.

## Why the root cause implies this

[ISS-800](20260922-1633-ISS-800.md) established the mechanism (unguarded
mount effect + Strict Mode double-invoke + no `cachedGet()` routing) and
that it is not confined to `AuditTab`. `SandboxTab.tsx` and
`PreviewPanel.tsx`'s own effect are two more direct instances of the exact
same shape, confirmed by reading both file:line ranges above — what is not
yet confirmed is the live count, hence INFERRED.

## What would settle it

Cold-navigate to a reopened completed run with no declared deliverable
filename, open DevTools Network filtered to `/sandbox`, click the
Workspace tab, and count requests — repeat 3x per this line's own
validation convention.
