## What happened

On a completed run's Steps tab (`/runs/{id}/steps`), the bottom-left "TOKEN USAGE" footer shows
`3.1M total · 141.3K input · 192.8K output`. `141.3K + 192.8K = 334.1K`, roughly 9x smaller than
the stated `3.1M total` — the footer's own two visible parts cannot reconstruct the total it
states. Cross-checked against `GET /api/runs/{id}` (`token_usage`): `total_input_tokens:
2,915,058`, `total_output_tokens: 190,220`, `total_tokens: 3,105,278` — the API's `input + output`
correctly sums to `total`; only the rendered "input" label is wrong. The same footer element's own
`title` attribute reads "Total context sent: 2.9M (2.4M cached)" — the component holds the correct
2.9M value and shows it in its own tooltip, but renders a different, much smaller number as the
primary visible label.

Confirmed **CONFIRMED, 3/3, cold start every cycle** — each cycle re-navigated fresh
(`/dashboard` → `page.goto` the steps URL) and read the footer via direct DOM `innerText`, not
just a screenshot:

| cycle | footer text | matches ledger's originally reported values |
|---|---|---|
| 1 | `TOKEN USAGE\n3.1M total\n·\n141.3K input\n·\n192.8K output` | yes |
| 2 | identical | yes |
| 3 | identical | yes |

Deterministic, not a race — identical after a full reload each time.

## Expected vs actual

- **Expected:** the visible "input" figure should either show the real total input tokens (2.9M,
  matching the API and the element's own tooltip) so `input + output ≈ total`, or, if the intent
  is to show only non-cached "new" input tokens, the label should say so explicitly (e.g. "141.3K
  new input") instead of appearing unqualified beside a total it cannot reconstruct.
- **Actual:** the footer shows `3.1M total · 141.3K input · 192.8K output` — self-contradictory,
  and the tooltip on the same element already contains the correct 2.9M figure it doesn't show.

## Root cause

`frontend/src/components/workflow/TokenUsageSummary.tsx`:

- `:26` — `total = totalTokens ?? (input + output)`, where `input` (`:24`) is the FULL
  `totalInputTokens` (gross, includes cache read/write per the file's own comment at `:31`).
- `:32` — `uncachedInput = Math.max(0, input - cacheRead - cacheWrite)` — deliberately computed
  to represent only the newly-billed prompt tokens.
- `:56` — `{formatTokens(hasCaching ? uncachedInput : input)} input` — when caching is active
  (true for this run: `cacheRead=2,443,873`, `cacheWrite=332,250`), the visible label renders
  `uncachedInput` (≈138,935 → "141.3K" after rounding) unqualified as `"input"`, right next to a
  `total` computed from the FULL `input` value at `:26`. The component's own `title` attribute at
  `:54` already carries the correct full `input` figure ("Total context sent: 2.9M... "), proving
  the right value is available in scope — it's just not the one rendered as the primary label.

This is a labeling/consistency defect, not a data-fetch bug: every underlying number
(`total`, `input`, `cacheRead`, `cacheWrite`) is correct and present in the component; only the
choice of which value to show as "input" next to a full "total" is wrong.

## Conditions established

- Route: `/runs/b9feac1c-ec21-4531-8ba7-bb391786993e/steps` (completed 4-agent PPT run with
  active prompt caching — `cacheRead`/`cacheWrite` both nonzero)
- Tier: qa-admin (not varied — reproduces at 3/3 without needing other tiers)
- Entry path: cold `page.goto` to `/dashboard` then to the steps URL, and a bare reload of the
  steps URL directly — both reproduce identically
- No timing dependency: read immediately after the DOM settles each cycle, all three identical
- Trigger condition (from reading the code, not narrowing): any completed run where prompt
  caching was used (`cacheReadTokens > 0` or `cacheWriteTokens > 0`) hits the `hasCaching` branch
  at `:56` and shows the mismatched figure. A run with zero cache activity would show the full
  `input` value and NOT reproduce this — not tested here since this run has caching, but follows
  directly from the code at `:33` (`hasCaching = cacheRead > 0 || cacheWrite > 0`).
