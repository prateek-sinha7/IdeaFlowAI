# ADR-0014

## Decision

In the context of opening a built-in (file-backed) workflow on the full-page composer,
facing the fact that such a workflow has no `WorkflowDefinition` row to write back to, we
decided to give it its own URL — `/workflows/{pipelineType}/canvas` — and to run the
surface copy-only: Run works on your edits, Save creates a NEW workflow you own, to
achieve an explore-and-fork surface, accepting that unsaved edits made in the Advanced
modal do not travel to the full canvas.

**Area:** frontend, routing, composer

## The load-bearing part is the URL, not the label

Before this, "Open in full canvas" pushed `/workflows/new` and carried the composition in
memory. That failed repeatedly and in ways that took a browser to see:

- `ComposerPage` seeds its state from `useState` INITIALIZERS, and it renders in the same
  pass `DashboardLayout` first mounts — so a composition set by an effect arrives too late.
- `page.tsx` briefly renders `null` through one of its cold-mount gates after a
  `router.push`, which UNMOUNTS `DashboardLayout`. In-memory state does not survive that;
  the composer mounted twice and the second, blank mount was the one that stuck.
- The `key={savedComposition?.id ?? "new"}` remount that rescues the saved-workflow path
  never fires here, because a built-in has no id — the key stays `"new"`.

A `sessionStorage` handoff was tried and made things worse: going BACK from the canvas
re-applied that composition to the launch panel, whose `initialAgentIds` restore resolves
ids against `ALL_LIBRARY_AGENTS`. A composed step (`custom-agent:emoji`) has no library
entry, so every id was dropped and the panel showed "0 agents" — surviving a refresh via
the TTL.

Naming the workflow in the URL removes the whole class: the composer refetches
`GET /api/workflows/{type}` on any mount, so a remount, a refresh and a shared link are
all the same code path. The handoff was deleted rather than hardened.

## Alternative rejected

**A separate namespace — `/workflows/built-in/{type}/canvas`.** Rejected: it encodes
*where a workflow came from* into the URL, which is a data property, not a navigation
one, and is the same origin-branching SC-001 warns against. It would also require two link
builders and two parsers forever. Deriving instead is safe by construction — a saved
workflow is addressed by UUID, which can never collide with a manifest directory name, the
same disjointness argument `run_trigger_workflow` already relies on for
`user_workflow_id` vs a file-backed pipeline id.
