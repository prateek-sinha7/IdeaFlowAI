## What was wrong

QA-PS-047 (`BUGS.md#qa-ps-047`, `LEDGER.md`): opening a live run's stream page
fired 49+ requests / 10+ MB, with `GET /api/runs?limit=50` (37 KB) firing 8-9
times and growing as the run progressed. [ISS-842](20260922-2107-ISS-842.md)
reproduced it 3/3 from cold: one user action (answering a clarify gate) produced
**three** run-list fetches, not one. [ISS-846](20260922-2121-ISS-846.md) showed
the same mechanism carries no route guard at all, so the cost is paid on every
screen a tab is showing while a backgrounded run emits frames — including wizard
routes that explicitly opt OUT of the equivalent mount-time fetch
(`page.tsx:1030`, ISS-793).

## Root cause

`handleWebSocketMessage` (`frontend/src/app/[...view]/page.tsx:1063`) is
subscribed to the app-wide SSE fan-out with no screen condition
(`page.tsx:2424-2434`, no `isReplay` argument — so
[FIX-624](20260922-2027-FIX-624.md)'s replay guard correctly does not apply to
live frames). Nine of its branches each called
`getWorkflows(token, { limit: 50 })` directly to learn a status the frame had
already stated:

| Event | old call site |
|---|---|
| `pipeline_complete` (immediate) | `page.tsx:1723` |
| `pipeline_complete` (KAN-120, 2 s delayed) | `page.tsx:1752` |
| `pipeline_failed` | `page.tsx:1799` |
| `pipeline_diverted` | `page.tsx:1836` |
| `pipeline_cancelled` | `page.tsx:1885` |
| `questionnaire_ready` | `page.tsx:2122` |
| `questionnaire_complete` | `page.tsx:2147` |
| `review_gate_ready` | `page.tsx:2204` |
| `review_gate_approved` | `page.tsx:2240` |

[FIX-616](20260922-1923-FIX-616.md)'s `inFlightWorkflows` map does not reach
this: it collapses calls that are concurrently open, not sequential calls
seconds apart. Each of these also handed `setRecentRuns` a **fresh array**, which
is the change-signal `WorkflowHistory`'s `recentRuns`-reference effect (T38,
`WorkflowHistory.tsx:244-256`) re-fetches on — the second multiplier ISS-842
measured.

## What changed and why there

One helper beside `recentsToken()`, at the single point all nine branches route
through (`page.tsx:1088`):

```ts
const patchRecentRunStatus = (runId: string | null | undefined, status: WorkflowStatus) => {
  if (isReplay || !runId) return;
  setRecentRuns((prev) => {
    const at = prev.findIndex((r) => r.id === runId);
    if (at < 0 || prev[at].status === status) return prev;
    const next = [...prev];
    next[at] = { ...next[at], status };
    return next;
  });
};
```

Eight of the nine branches now call it instead of fetching. The status each one
writes is the status the backend has already persisted, read off the engine:

- `questionnaire_ready` / `review_gate_ready` → `waiting_for_user`
  (`engine.py:5168`, `engine.py:8038`, `engine.py:11261`).
- `questionnaire_complete` → `generating` (`engine.py:5292` after
  `clarify.run()`; the mid-run path's `prior_state = "generating"` at
  `engine.py:8037`/`8069`).
- `review_gate_approved` → `generating` (`engine.py:11409-11411`; a REJECT goes
  to cancelled and arrives as its own `pipeline_cancelled` frame).
- `pipeline_failed` → `failed`, `pipeline_cancelled` → `cancelled`.
- `pipeline_complete` → `data.status || "completed"` — the SAME field
  `_reconcile_terminal_status` (`backend/app/api/run_commands.py:762-820`) reads
  off the durable tail to decide degraded-vs-completed.

`recentRuns` exists to drive AppHeader's "N Running" badge and the notification
panel, and both read `status` (`AppHeader.tsx:45-48`, `LIVE_STATUSES`), so the
badge stays live with no network at all. Returning `prev` unchanged when nothing
moved also stops the reference churn that fed `WorkflowHistory`'s T38 effect;
when the panel IS open (`mainView === "history"`), a real transition still
signals it, which is the one screen where re-reading the list is the point.

Two pieces of machinery went with the list replace they existed to protect
against, not as a side refactor:

- **KAN-120's second, 2 s-delayed refetch** raced `_reconcile_terminal_status`.
  Patching from the frame's own `status` lands on the reconciler's verdict
  instead of racing it.
- **KAN-125 / FIX-136's per-row "preserve running" maps** (×3) only ever existed
  because REPLACING all 50 rows let a concurrent run's freshly-written DB status
  overtake its own `pipeline_complete`. A single-row patch cannot touch another
  run, so there is nothing left to preserve. `launchedRunIdsRef` itself is
  untouched and still used by the foreign-frame guards.

### The one branch that still fetches — deliberate

`pipeline_diverted` (`page.tsx:1790-1804`) keeps its `getWorkflows` call. It is
the only live branch where a row is **added** rather than changed: the frame
carries `diverted_to_run_id` as a bare pointer
(`contracts/sse-pipeline-diverted.md`, guarantee 3 — "a pointer, not an inline
continuation"), so the new run's row genuinely does not exist client-side and
cannot be patched in. It fires at most once per run, on the rare
conditional-gate route, not per gate/clarify/completion frame.

### Known narrowing

`patchRecentRunStatus` no-ops when the run is not already in `recentRuns`
(`at < 0`), where a full refetch would have surfaced it. `RunConnectionProvider`
only fans frames out for runs this tab launched or focused
(`RunConnectionProvider.tsx:279-330`, `tab_launched_run_ids`), and both paths put
the row in the list first (launch refreshes it at `page.tsx:4390`, FIX-195
Fix-A), so no reachable case loses a row.
