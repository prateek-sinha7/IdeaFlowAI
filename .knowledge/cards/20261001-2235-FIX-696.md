# FIX-696

## What was wrong

Bug reports QA-KB-012 (`/login/<sub-path>`) and QA-KB-013 (`/admin/<sub-path>`). The root cause and blast radius are
the analyses on [ISS-348](20260828-2102-ISS-348.md) and [ISS-349](20260828-2102-ISS-349.md); they are not re-derived
here. Both were validated 3/3 in the browser (`evidence/qa-kb-012/01-03`, `evidence/qa-kb-013/01-03`).

`parseViewPath` (`frontend/src/lib/routes.ts`) matched a route as soon as the segment it cared about matched, without
checking that nothing followed it. For `login` and `admin`, a static route owns the exact path, so only the sub-path
reached the `[...view]` catch-all. There it parsed to a screen nothing renders, `initialMainViewFor` returned
`undefined`, and `DashboardLayout` fell back to `"home"`: the dashboard painted under the bogus URL. `dashboard`
([ISS-910](20261001-2220-ISS-910.md)) and the multi-segment branches ([ISS-911](20261001-2220-ISS-911.md): create,
workflows, runs, library, settings) had the same flaw one step later and rendered a real screen under a bogus URL.
This is the same family as [FIX-344](20260828-2046-FIX-344.md) (register) and [FIX-462](20260901-2100-FIX-462.md)
(analytics).

## What changed, and why there

All in `parseViewPath`, the one function every consumer routes through (`[...view]/page.tsx:437`,
`LibraryPage.tsx:465`, `error.tsx:24`, `global-error.tsx:24`; `DashboardLayout.tsx` and `AccountSettings.tsx` only
mention it in comments). Fixing it there fixes the render, the library detail seed and the error-telemetry label at
once. Anchor on the code text; the numbers are from the working tree after this change.

- ISS-348: `if (head === 'login' && segments.length === 1) {` (`:260`), plus a 4-line ISS-348 comment mirroring the
  register one.
- ISS-910: `if (head === 'dashboard' && segments.length === 1) {` (`:280`).
- ISS-349: `if (head === 'admin' && segments.length === 1) {` (`:509`). The stale "Intentionally unreachable dead
  code" comment above it was replaced with an ISS-349 comment, as the card asked. The same stale comment on the
  `routes.admin()` builder (`:180`) was not part of any card and is untouched.
- ISS-911, one arity check per branch:
  - create: `if (segments.length > 2) return { screen: 'unknown' }` after the bare `/create` case (`:289-292`).
  - workflows: `new` returns `workflow-new` only at length 2 (`:320`), and `segments.length > 3` is `unknown` before
    the `canvas`/`edit`/`run` arms (`:329-332`).
  - runs: per-arm `tail.length === 3` on files, workspace, audit and stream (`:400-418`); `tail.length === 4` on
    `steps/{agentId}` (`:393`) and `preview/full` (`:420`).
  - library: `segments.length >= 3` became `=== 3` (`:456`).
  - settings: `segments.length > 2` is `unknown` before the tab arms (`:479-482`).

The ISS-911 arms are safe for every path the app builds, which was checked before editing. The `routes.*` builders
emit nothing deeper. `proxy.ts:21`, `DashboardLayout.tsx:418` and `LaunchWizard.tsx:1458` encode their one variable
segment. `routes.runStepsAgent` has no non-test caller. Library slugs are folder names
(`skills_catalog.py:104`, `hooks_catalog.py`) or `user-agent:<uuid>` (`app/api/agents.py:204`), never containing `/`.
`page.tsx` reads no raw `viewSegments` beyond the parser. Every deep page path the e2e suites visit fits the new
arities (grep of `tests/integration/e2e`), and so does the one `useParams` mock (`LibraryPage.copyFeedback.test.tsx`,
3 segments).

Unchanged on purpose: `/runs/{id}/versions` (no `{v}`) still parses to `run-version` with `version` undefined, and
`/runs/{id}/versions/{v}/stream` and `.../preview/full` still drop the pin. Neither was in any card; both are now
recorded, open, as [ISS-941](20261001-2240-ISS-941.md).

## Not fixed here

[ISS-914](20261001-2219-ISS-914.md) (exact `/register` for a signed-in user) stays **open**. The dispatch asked for it
to be closed as not-a-defect because "/register is already guarded", but the only register guard is the FIX-344 depth
guard `if (head === 'register' && segments.length === 1) {` (`routes.ts:271`). It admits the bare path, which is
exactly the path ISS-914 is about. Nothing else intercepts it: `frontend/src/app/register/` does not exist (`ls`
fails, `git ls-files frontend/src/app/register` is empty), `next.config.ts` `redirects()` has no `/register` source,
`proxy.ts` matches only `/workflow/create`, and `page.tsx`'s only redirects are no-token to login (`:936`) and logout
(`:3431`). Its fix needs a product decision (stub redirect, `next.config.ts` redirect, or drop the branch), recorded
on the card.
