# ISS-769

**Register source:** `QA-SG-001` in root `LEDGER.md` / `BUGS.md` — sibling
filed during the Analyzer pass over [ISS-722](20260922-1100-ISS-722.md), the
confirmed root-cause card for this bug.

## What is suspected — INFERRED, not yet reproduced

[ISS-722](20260922-1100-ISS-722.md) established that
`StepsOverviewSpine.tsx:403`'s `total = agents.length` reads the client-built
per-run roster (`pipelineState.agents`; `useRunStateStore.ts:168` seeds it
`[]`), which stays empty until the first roster-building SSE event lands —
while `AppHeader.tsx:216`'s
`` agentsTotal: isActive ? (pipelineAgentsTotal || r.agentCount) : (r.agentCount ?? 0) ``
avoids the gap with a fallback to the run record's already-known
`agent_count`.

`AppHeader.tsx` has a SECOND render path that does not carry this fallback:
the "legacy" single-run badge.

```tsx
// AppHeader.tsx:450-469
{/* Legacy: fall back to old scalar props if notifications don't carry
    a running entry but pipelineState says running (edge case on first render) */}
{runningPipelines.length === 0 && isPipelineRunning && pipelineType && (
  <motion.button ...>
    <span className="h-1.5 w-1.5 rounded-full bg-white animate-pulse flex-shrink-0" />
    <span className="max-w-[120px] truncate">{getWorkflowLabel(pipelineType)}</span>
    {pipelineAgentsTotal > 0 && (
      <span className="text-white/60 flex-shrink-0">
        {pipelineAgentsCompleted}/{pipelineAgentsTotal}
      </span>
    )}
  </motion.button>
)}
```

`pipelineAgentsTotal` is a plain prop here (default `0`, `AppHeader.tsx:111`),
not the mapped-and-guarded `agentsTotal` field the dropdown/notification
paths use. Its value is set by the caller:

```tsx
// DashboardLayout.tsx:2719-2720
pipelineAgentsCompleted={pipelineState?.completedCount ?? 0}
pipelineAgentsTotal={pipelineState?.agents?.length ?? 0}
```

Same unguarded `pipelineState.agents.length` read as
`StepsOverviewSpine.tsx:403` — no `|| agentCount` fallback anywhere on this
path.

**Where this differs from ISS-722, and why it still matters:** the badge
gates its count on `pipelineAgentsTotal > 0` (line 464), so during the
empty-roster window it does not render a visible "0/0" — it just omits the
count entirely, alongside the workflow label. That is a milder symptom than
ISS-722's literal "0/0", but it is the same mechanism (an unguarded
`agents.length` read, no fallback to the known `agent_count`) reachable on a
third UI surface, and it means a fix that only patches the one reported call
site would still leave this path silently wrong.

**Trigger condition (per the code's own comment):** `runningPipelines.length
=== 0 && isPipelineRunning && pipelineType` — "edge case on first render,"
i.e. the same run-just-launched window ISS-722 reproduces, before the run
has been promoted into the `liveRuns`/notifications list.

## Why the root cause implies this

ISS-722's root cause is "two independent sources feed 'total agents' for the
same run, and only one of them is populated this early." The fallback that
closes that gap lives in exactly one of `AppHeader.tsx`'s three render
branches (`agentsTotal` at line 216) — not all of them. The legacy branch
(line 464) was written against the older, unguarded `pipelineAgentsTotal`
prop and never picked up the fallback added at line 216. Same file, same
component, same missing guard, different branch: a textbook sibling caller
of the broken pattern ISS-722 named.

## What would confirm or refute it

Drive a run to the exact edge case the code comment names — a fresh launch
where the client reaches `isPipelineRunning: true` before the run has been
added to `recentRuns`/notifications (e.g. throttle the runs-list poll, or
catch the very first paint after the launch `POST` returns) — and check
whether the header badge briefly shows the workflow label with NO count,
while the bell icon (reachable at the same instant) already shows a nonzero
total. If `runningPipelines.length` is never actually `0` in practice (e.g.
the notification is always created synchronously before this badge can
paint), close this card as unreproducible rather than fix it.
