# BUG-005 — Prototype launched with no template: clarify never renders (UI stuck at "Running 0/0 BUILDING")


### BUG-005 — Prototype launched with no template: clarify never renders (UI stuck at "Running 0/0 BUILDING")  [🟠 major] [FIXED ✅]
- **RESOLVED:** FIXED (quick 260716-j1u, 8eec694c) — live-proven

- **Found:** 2026-07-16 · live Bedrock QA (heavy concurrent load — same session as BUG-004's ~10+ simultaneous runs) · surface run screen → clarify-gate rendering, on an **`od_prototype` no-template launch** (KAN-87), brief "a website that mimics apple.com". Runs `afb5de91-7017-422e-a1c9-6872109b49f9` + `bea8b22d-4e0d-44f1-a32e-c5b63b6bb41f`.
- **Symptom:** The run screen shows **"Pipeline running · 0/0 · BUILDING"** with ONLY the "Starting point" card and a **"Steer the run"** (building-mode) composer — **no clarifying questions render, nothing progresses, it looks stuck** — even though the run is server-side paused at the clarify gate (`status=waiting_for_user`) with a well-formed 6-question questionnaire ready.
  - **Task-brief premises corrected against the live API (the user/agent capture was stale):** the run `type` is **`od_prototype`** (not `prototype`); `agent_count` is **5** (not 0) with a valid 5-agent DAG (`prototype-specify/plan/analyze/build/validate`); and it carries a **spurious `parent_run_id`/`root_run_id` = `c530695f`** (a completed *user_stories* "Task Manager" run) — a revision-family mis-link from a stale `sourceRunId` in the wizard draft (`page.tsx:984` → `DashboardLayout.tsx:643` `source_workflow_run_id`), the BUG-001/002/003 stale-viewed-run class, but NOT the cause of the stuck clarify.
  - **"0/0 agents" is a red herring.** Agents reach the FE only in the **`pipeline_start`** event, which fires *after* `questionnaire_complete` (verified: completed `ab90f5f4`/`4cd2f478` both emit `pipeline_start{agent_count,agents}` only post-clarify). So *every* workflow shows 0/0 agents while paused at the clarify gate — user_stories included. The bug is the **missing questions**, not the agent count.
- **Root cause (investigation agent — read `.planning/IMPLEMENTATION-REGISTER.md` global + Phase 07 prototype-as-manifest, Phase 25 run-inputs/ClarificationsCard, Phase 28/29 chat+SSE backbone, Phase 31/32/39/42 run-screen/clarify FE; curled the live run detail + `/events` + `/events/stream`; grep-confirmed the launch guard in `run_commands.py`):**
  - **Backend + SSE wire are CORRECT — do not "fix" them.** `GET /api/runs/afb5de91/events/stream` delivers a well-formed live frame `id:5` = `{"data":{questions:[6 …],"round":1,…},"type":"questionnaire_ready"}`; `planner_complete` carries `"no_template_mode": true`. The **`missing_template_context` guard (`run_commands.py:1176-1188`) correctly did NOT fire** — it only rejects when a resolved agent declares `template` in `injects` AND `_needs_template` AND `not od_context.no_template`; the no-template prototype is a **supported KAN-87 feature** (`page.tsx:975-978`, `templateId ?? ""`), so `no_template` exempts it. **So the launch should NOT be rejected pre-mint** (task option (a) = NO) and the compile is **not empty** (5 agents; task option (c) = N/A).
  - **The FE bug (primary, deterministic under concurrency) — a foreign run's `pipeline_start` WIPES the viewed run's clarify.** The run-screen clarify state is a **single, global, page-level React state** (`page.tsx:157` `questionnaireData` → effect `DashboardLayout.tsx:585-589` → `questionnaireQuestions`), and `runLaneState` derives clarify **purely** from it: `laneClarifyOpen = questionnaireQuestions.length>0 && (…activePipelineRunId)` → `runLaneState = … : laneClarifyOpen ? "clarify" : isPipelineRunning ? "building" : …` (`DashboardLayout.tsx:1308-1317`). It is **not bound to the viewed run**. It is fed by the SSE provider's **NON-run-scoped fan-out** — `RunConnectionProvider.tsx:275-283` fans *every frame from every attached run* to the *single* subscriber `handleWebSocketMessage`, and `refreshLiveRuns` (`:226-244`) auto-attaches **all** non-terminal runs on boot (`attachRun` `:305-308` appends more). The `pipeline_start` branch of that one subscriber (`page.tsx:462-482`) then runs **unconditionally, with no run-identity guard**: `resetReplayState(…)` clears the global seen-set (`:463`), `setQuestionnaireData(null)` (`:481`), `setActivePipelineRunId(null)` (`:482`). So the moment **ANY** concurrently-attached run enters its build phase and emits `pipeline_start`, that foreign frame **clears the clarify questionnaire of the run the user is viewing** → `questionnaireQuestions` empties → `runLaneState` falls through `clarify`→`building` → "Pipeline running · 0/0 · BUILDING", no questions, "Steer the run" composer. (The comment at `:477-480` intends this clear only for a *previous* run in the same tab — but the non-run-scoped fan-out makes it fire for *concurrent* runs too.)
  - **Why it hit here and not the "working" user_stories clarify.** Not type-specific: user_stories at clarify is equally vulnerable. Two factors made od_prototype the victim: (1) the od_prototype **planner is slow** (~23s to `questionnaire_ready`: `workflow_validated` 10:30:45.9 → `planner_complete` 10:30:56.5 → `questionnaire_ready` 10:31:08.7), so its clarify gate stays open long enough to be wiped; (2) it was hit under **heavy concurrent load** — the two od_prototype runs were even minted **120ms apart** (`created_at` 10:30:45.246 & .368 — a double-mint), and BUG-004 documents ~10+ simultaneous runs, several *building*. Any of those building runs' `pipeline_start` wipes the clarify. user_stories clarify "worked" because it was exercised in isolation (no concurrent build to wipe it). The two clarify runs alone do NOT self-wipe (neither emits `pipeline_start`); the wipe requires ≥1 concurrent building run — guaranteed under the QA's load.
  - **Sibling cross-run poisoning (same seam, `:463`).** `resetReplayState` on a *foreign* `pipeline_start` also **clears the global `seenEventIdsRef` dedup set** shared by all attached runs, so the viewed run's already-applied events can double-apply / its next reconnect after_seq is wrong — a second facet of the same "one global reducer serving N runs" defect.
  - **PRE-EXISTING — not introduced by the recent DEF-44 SSE work.** `git blame`: the unconditional `setQuestionnaireData(null)`/`setActivePipelineRunId(null)` on `pipeline_start` = `7d95409cf` **Prateek Sinha 2026-06-30** (WR-03 per-run reset, written for the single-run-per-tab assumption); the non-run-scoped fan-out = `1cc8e92ab` **imran-hex 2026-07-08** (Phase 29 SSE backbone); `laneClarifyOpen`/`runLaneState` = `368bc5229` **imran-hex 2026-07-08** (Phase 32 run-screen). All predate the feat/ui-2 DEF-44 campaign. Same **"run-screen live state not bound to the viewed run"** class as BUG-001 (title), BUG-002 (open path), BUG-003 (revise type) — here the **clarify questionnaire**.
- **Fix (PROPOSED — investigation only, not applied):** task option **(b)** — bind the clarify state to the viewed/active run so a foreign run's `pipeline_start` can't wipe it. Minimal + SC-001-safe (keys only on the generic `pipeline_run_id`, zero workflow-name literal):
  1. **`page.tsx:462`** — run-scope the `pipeline_start` reset block: only run `resetReplayState` + `setReviewGateData(null)` + `setQuestionnaireData(null)` + `setActivePipelineRunId(null)` when the incoming frame's `pipeline_run_id` is the run this consumer is tracking — i.e. gate on `data.pipeline_run_id === (activePipelineRunId ?? contentSourceRunId ?? pipelineState.pipelineRunId)` (or the just-launched run id), so a **concurrent foreign** `pipeline_start` is ignored. Preserves the intended "new run in this tab clears the old questionnaire" behavior; drops the cross-run wipe.
  2. **Systemic (recommended) — run-scope the page subscriber itself.** At `page.tsx:909-912` (the `runSubscribe` → `handleWebSocketMessage` bridge) drop frames whose `data.pipeline_run_id` ≠ the viewed/active run before they reach the single global reducer/clarify state, so the non-run-scoped fan-out (`RunConnectionProvider.tsx:276`) can't bleed one run's frames (agents, gate, clarify, seen-set) into another's view. This is the durable fix the BUG-001/002/003 "viewed-run binding" class points to; #1 is the minimal subset that stops *this* symptom.
  - **Secondary (separate, lower-priority): the double-mint.** Two `od_prototype` runs minted 120ms apart = the staged wizard launch (`page.tsx:959` effect, deps `[effectiveConnectionStatus]`) or the launch button firing twice (non-idempotent). Guard the launch so one user action mints one run. Not required to fix the stuck-clarify symptom, but it doubles the concurrent-run count that triggers it.
  - **Do NOT:** reject the no-template launch (KAN-87 supported; guard already exempts), touch the backend clarify/planner, or "fix" the compile (5 agents present).
- **Verify (fail-before / pass-after — proposed):**
  1. **Fail-before:** pause run A at the clarify gate (any workflow); while A is viewed, launch/attach run B and let B reach its build phase (`pipeline_start`). Observe A's clarify questionnaire vanish and A's screen fall to "Pipeline running · N/M · BUILDING" with the "Steer the run" composer and no questions. (Reproduced live: two `od_prototype` clarify runs `afb5de91`/`bea8b22d` under concurrent build load.)
  2. **Pass-after:** same sequence with the reset run-scoped (#1) and/or the subscriber run-scoped (#2) → B's `pipeline_start` no longer clears A's clarify; A's 6 questions stay and are answerable; `submit_questionnaire` advances A. user_stories + od_prototype clarify both survive a concurrent build.
  3. **No-regression:** a fresh single-run od_prototype no-template launch still shows clarify (already correct at the wire); reopening a clarify-paused run from recents/history still replays `questionnaire_ready` → clarify (`handleSelectWorkflowRun` durable seed, `page.tsx:1222`); answering clarify → build still clears the questionnaire for the SAME run.
  4. **Unit:** a `page.tsx`/reducer vitest — a `pipeline_start` whose `pipeline_run_id` ≠ the active run does NOT null `questionnaireData`/`activePipelineRunId` nor clear the seen-set; a matching `pipeline_start` still does. `tsc --noEmit` clean.
