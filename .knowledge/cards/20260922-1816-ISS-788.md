Confirmed 3/3 from a cold start via `mcp__lane1__browser_network_requests` /
`performance.getEntriesByType('resource')`:

- Attempt 1 (cold hard nav, direct `goto('http://localhost:3000/workflows')`
  from `about:blank`): `GET /api/user-workflows` 2x, `GET /api/workflows` 2x,
  `GET /api/runs?limit=50` 2x, `GET /api/runs?limit=6` 1x, `GET /api/auth/me` 1x.
- Attempt 2 (repeat of attempt 1, identical entry path): identical counts —
  reproducible, not flaky on this axis.
- Attempt 3 (cold session on `/dashboard`, then client-side SPA navigation by
  clicking the "My Workflows" nav button — entry-path axis): `GET
  /api/user-workflows` **4x**, `GET /api/auth/me` **2x**, `GET
  /api/workflows` 1x, `GET /api/runs?limit=50` 1x — this is the exact
  magnitude BUGS.md QA-PS-041 reports.

Named trigger: **entry path**. A client-side (in-app) navigation to
`/workflows` doubles the duplicate-fetch count versus a cold hard URL load —
the SPA route change lets the destination page's own data-fetching mount
(`SavedWorkflowsPage.tsx`) stack on top of layout/nav components that were
already mounted from the previous route, whereas a hard reload only pays for
one full mount cycle. The unnecessary `/api/runs?limit=50` fetch and at least
one duplicate `/api/user-workflows` call are present on **every** entry path
(3/3), so the core defect holds regardless of trigger; the trigger only
explains why the reporter counted 4x/2x rather than 2x/1x.

This is BUGS.md QA-PS-041. Evidence:
`evidence/qa-ps-041/01-validate-attempt1-workflows-page-loaded.png`,
`evidence/qa-ps-041/02-validate-attempt3-clickthrough-workflows-page.png`,
`evidence/qa-ps-041/03-network-requests-summary.txt`.

## Root cause — same two mechanisms as ISS-781 (QA-PS-035)

**Mechanism A — the unused runs fetch.** `getWorkflows()`
(`frontend/src/lib/api.ts:770-781`) despite its name builds
`path = "/api/runs"` with `limit`/`offset` query params — it is a run-history
fetcher, not a workflow-catalog fetcher. `RunConnectionProvider.tsx:289`
calls `getWorkflows(t, { limit: 50 })` inside `refreshLiveRuns` on mount.
This provider wraps the whole app (confirmed earlier for ISS-781 via `grep
-rln RunConnectionProvider frontend/src/app frontend/src/components`), so
every route pays for a 50-row run-history fetch — including `/workflows`,
where My Workflows renders only saved-workflow cards with no run history,
recents, or "Jump back in" section.

**Mechanism B — no shared cache for the saved-workflows list / identity.**
`getUserWorkflows` has exactly one call site inside the page itself
(`frontend/src/components/savedworkflows/SavedWorkflowsPage.tsx:170`,
confirmed via `grep -rln getUserWorkflows frontend/src`), so the 2x-4x
duplication is not two page components racing each other — it is the same
mount effect firing more than once per page view as the SPA layout/nav shell
(`frontend/src/app/[...view]/page.tsx`) and the destination page each drive
their own auth/list fetch with no shared provider or cache, the same shape
documented for ISS-781/ISS-783/ISS-785 on their own routes.

## Expected vs actual

Expected: `/workflows` fires `GET /api/user-workflows` once, `GET
/api/workflows` once (the catalog, for per-card agent counts), and `GET
/api/auth/me` once. No `/api/runs`.

Actual (worst observed, cycle 3 — client-side nav): `GET /api/user-workflows`
4x, `GET /api/auth/me` 2x, `GET /api/runs?limit=50` 1x unused, `GET
/api/workflows` 1x. Even the best observed case (cycles 1-2, hard nav) still
duplicates `/api/user-workflows` 2x and fetches the unused
`/api/runs?limit=50` 2x.

## Update — 2026-09-22 (5-fixer): Mechanism B fixed, Mechanism A escalated

**Mechanism B is closed** by [FIX-627](20260922-2050-FIX-627.md): an in-flight
Map in `getUserWorkflows()` (`frontend/src/lib/api.ts`). Measured on the bug's
own test, `--runxfail`, cold `/workflows` load — `user-workflows` **2x → 1x**.
`/api/auth/me` is already 1x here, closed earlier by
[FIX-618](20260922-1945-FIX-618.md)'s `cachedGet()`, so this card's
identity-duplication claim no longer reproduces either.

**Mechanism A is not a code change.** This card's premise — that `/workflows`
"pays for a 50-row run-history fetch it never displays" — does not hold for the
shell this route renders inside. `SavedWorkflowsPage` mounts at
`frontend/src/components/layout/DashboardLayout.tsx:3077`, under
`mainView === "saved-workflows"` (`:3068`), which is BELOW `<AppHeader`
(`:2720`) and its `recentRuns={recentRuns}` (`:2754`) — the header's
"N Running" badge consumes exactly that list. It is the identical situation
[QA-PS-035](../../ESCALATIONS.md#qa-ps-035) escalated over, and QA-PS-041 is the
fifth bug waiting on that one decision. Remaining on a cold load: `/api/runs?limit=6`
1x (the ISS-232 sign-in preload) and `/api/runs?limit=50` 1x.

The test written from this card asserts `uw_count == 1 AND not runs_calls` in
one assertion, so it stays red on the second half alone.
