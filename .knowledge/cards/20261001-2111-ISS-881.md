# ISS-881

## Description

Adjacent defect found while analyzing [ISS-160](20260813-1300-ISS-160.md) (QA-KB-009). `REVISION_BASE_MAP` (`backend/agents/registry.py:145-155`), documented as "maps revision pipeline types to their base types", has 9 entries and no `backlog_revision`. There are 10 revision pipelines: the nine mapped ones plus `backlog_revision`, which has a manifest (`compile_for_run("backlog_revision")` gives 5 steps), an empty `PIPELINE_AGENTS` roster, and `TIER_PIPELINES` rows for hexaware, pro and enterprise (`backend/app/core/entitlements.py`).

CONFIRMED by running the one test that asserts it: `backend/tests/unit/test_backlog_revision.py::test_backlog_revision_base_is_backlog` fails, `KeyError: 'backlog_revision'` at `test_backlog_revision.py:284` (`assert REVISION_BASE_MAP["backlog_revision"] == "backlog"`), 1 failed. The test was committed with the backlog revision workflow in `60bbe040d` (2026-10-01, spec 022 section 11); the commit added the manifest, tier rows and the test, but not the map row.

No runtime code reads the map. `grep -rn REVISION_BASE_MAP` over `*.py`, `*.ts`, `*.tsx` and `*.yaml` finds only tests and two comments: `registry.py:413` and the `_dispose_concierge_proposal` docstring at `run_commands.py:1506`, which says the revision channel "Reuses `REVISION_BASE_MAP` (via `_mint_revision_row`)". That is not true: `_mint_revision_row` derives the pipeline type by string (`run_commands.py:4608`) and never touches the map. So the user-visible impact today is nil; the cost is a red committed test and a map that cannot be trusted as the registry's source of truth.

## Why the root cause implies it

ISS-160's root cause is that "revision type -> base" is hand-rolled at each entry point. There are three copies of that knowledge: this map (9 of 10, missing `backlog_revision`), the inline block in the Concierge disposal path (`run_commands.py:1640-1650`, complete for all 10: observed offline), and a log-only `_canonical_base` in `runs.py:1682`. The natural instinct when fixing ISS-160 is to reuse the registry map as the single source. Done as a bare lookup (`REVISION_BASE_MAP.get(wr_type, wr_type)`), that fix still double-suffixes `backlog_revision` parents: the offline `CHANNEL_REVISION` probe showed `backlog_revision` among the ten parents that return HTTP 400 `revision_unsupported` today, and a map-only fix would leave it there.

## Ripple to know about before adding the row

INFERRED from reading, not run: `backend/tests/unit/agents/test_registry_helpers.py:101-103` builds `_AGREEING_REVISION_PIPELINES = set(REVISION_BASE_MAP.keys()) - _COMPOSED_REVISION_PIPELINES`, and `test_revision_allow_list_is_own_agents_only` (`:152-160`) asserts a non-empty `PIPELINE_AGENTS` roster for each entry. `backlog_revision` has an empty roster, like the two v2 composed revisions already excluded in `_COMPOSED_REVISION_PIPELINES` (`:98-100`), so it would need the same exclusion. What settles it: add the row in a scratch copy and run that one test file.

## Fix direction

Add `"backlog_revision": "backlog"` to `REVISION_BASE_MAP` and `backlog_revision` to `_COMPOSED_REVISION_PIPELINES` in `test_registry_helpers.py`, and correct the `run_commands.py:1506` docstring. Independent of ISS-160's fix: whichever helper ISS-160 introduces must keep the generic `removesuffix("_revision")` fallback so it works whether or not this row exists.

## TEST COVERAGE - ISS-881

Observed by the analyzer: `backend/tests/unit/test_backlog_revision.py::test_backlog_revision_base_is_backlog` run alone, 1 failed (`KeyError: 'backlog_revision'`). Not re-baselined at an earlier commit; the failure follows directly from the registry source (the key is absent), not from any other state. No fix, no test added.

## Resolution (QA-KB-009 fixer, 2026-10-01)

Resolved by [FIX-684](20261001-2129-FIX-684.md): `"backlog_revision": "backlog"` added to `REVISION_BASE_MAP` (`backend/agents/registry.py:155`); `backlog_revision` added to `_COMPOSED_REVISION_PIPELINES` (`backend/tests/unit/agents/test_registry_helpers.py:99`); the `run_commands.py` docstring (now `:1535`) names `_revision_base_type` instead of the map. The predicted ripple was observed: with the map row alone, `test_revision_allow_list_is_own_agents_only[backlog_revision]` failed ("expected a non-empty allow-list"); with the composed classification the file is 30 passed. `test_backlog_revision_base_is_backlog`: XPASS(strict). `_revision_base_type` keeps the `removesuffix("_revision")` fallback and does not read the map.
