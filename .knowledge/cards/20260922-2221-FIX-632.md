# FIX-632

Fixes **QA-PS-051** (`LEDGER.md` / `BUGS.md#qa-ps-051`).

## What was wrong

`GET /api/runs?limit=50` — 37 KB of run history — fired once on the `/library`
mount and a second time on the client-side navigation into
`/library/agents|skills|hooks/<id>`, a view that renders no run history at all.
[ISS-843](20260922-2114-ISS-843.md) reproduced it 3/3 from cold start.

## Root cause

Exactly as [ISS-848](20260922-2138-ISS-848.md) established, re-checked against
the tree before editing:

- `frontend/src/app/[...view]/page.tsx:828` — `recentRunsRequestedRef` is a
  `useRef`, so it lives and dies with one component instance.
- A `router.push` under the `[...view]` catch-all remounts that component — the
  file states this as confirmed-live fact in its own T6 comment (`page.tsx:3494-3498`),
  and `DashboardLayout.tsx:543-548` names the same fact when explaining why it
  uses a shallow `pushState` instead.
- `LibraryPage.tsx:828/910/1009` are the three `router.push(routes.libraryAgent/
  librarySkill/libraryHook(...))` call sites QA-PS-051 walks through.
- `getWorkflows` (`api.ts:868-908`) dedupes in-flight requests only, and run
  lists are deliberately kept out of `cachedGet`'s TTL cache (`api.ts:401-406`),
  so the second mount's fresh `false` guard went straight to the network.

## What changed, and why there

One file, `frontend/src/app/[...view]/page.tsx`, three hunks:

1. **`let recentRunsSnapshot: { token: string; runs: WorkflowRun[] } | null`** at
   module scope, beside the existing `switchGeneration` pair that ISS-780 put
   there for this same remount. Module scope is the only scope that outlives the
   remount, and it is where every other "survive the remount" fix in this
   codebase already landed (`cachedGet` for `auth/me`, the Redux store for the
   catalog, FIX-523's module-level `useRunStateStore`).

2. **The mount effect seeds from the snapshot instead of refetching** when the
   snapshot's token matches the current one, and the successful fetch writes it.

3. **A mirror effect keeps the snapshot current** from every other path that
   updates the list (the post-cancel/divert refetch, the launch refresh, the SSE
   status patches), so the next remount seeds today's statuses rather than
   whatever the first fetch returned.

**Why the guard could not move alone.** [ISS-848](20260922-2138-ISS-848.md)
prescribed promoting "the GUARD (not the data)". Taken literally that ships a
second defect: `recentRuns` (`page.tsx:818`) is component state and dies on the
identical remount, so suppressing the refetch without carrying the rows across
would hand the new mount an empty list — blanking AppHeader's "N Running" pill
and the notification panel (`AppHeader.tsx:200,241`, the surface ISS-757's
`recentRunsLoaded` gate exists to protect). The guard and its data move together
for that reason; the card's prescribed location, scope and token keying are
unchanged.

**Deliberately not done:** no TTL wrap on `getWorkflows()` itself
(`api.ts:401-406` keeps run lists out of that cache because its other callers
refetch precisely to observe a change), and no per-caller patch in
`LibraryPage.tsx` (that would cover 3 of the ~10 `router.push(routes.*)` call
sites and leave every other route pair broken — the point of
[ISS-849](20260922-2140-ISS-849.md)).

## Scope note on [ISS-849](20260922-2140-ISS-849.md)

ISS-849 is the INFERRED generalization — the same remount refetch on any
non-wizard `[...view]` route pair, not only Library. The fix is at the mechanism,
not at the Library path, so it removes that refetch for every route pair by
construction. This is resolved **by mechanism, not by a red-to-green test**:
ISS-849 was never reproduced deterministically on any non-Library path, and its
two tests ship as green regression guards. Both still pass after the change.
