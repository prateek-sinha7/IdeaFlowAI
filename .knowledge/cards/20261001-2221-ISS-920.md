## What is broken (INFERRED: every link below was read, none was run)

Found while analysing QA-KB-011 (2026-10-01). [ISS-284](20260828-1906-ISS-284.md) is about the window in which the
override/plan overlay (`getWorkflowDetail`) has not landed. This is the OTHER async source that decides the roster in
the same component, the library-gated draft restore, and the OTHER consumer of the roster, Continue. It is not covered
by ISS-284's fix (a settle flag on the `getWorkflowDetail` effect) and it has a different harm: a launch, not a save.

**Condition.** Cold open of `/workflows/{id}/run` for a SAVED prototype/ppt workflow (a `user_workflows` row, not an
override) whose roster differs from the built-in default. `[...view]/page.tsx:3918-3971` stages the draft with
`agentIds: saved.agent_ids` (`:3964`) and mounts `LaunchWizard`. The agent library is Redux state filled by a preload
dispatched on `signedIn` (`frontend/src/store/listenerMiddleware.ts:25-26`, `:59-61`), so on a cold navigation it is
empty on the wizard's first render (the same fact [FIX-338](20260828-2221-FIX-338.md) records). The saved-workflow GET
resolves before `GET /api/agents/library`, and Continue is clicked in the gap.

**Expected.** Continue launches the saved roster, or stays disabled until it has been restored.

**Actual.**

- The draft-restore effect (`LaunchWizard.tsx:395-441`) sets the brief, template and design system on its first pass
  (`:415-419`) but restores `agentIds` only `if (d.agentIds && d.agentIds.length > 0 && libraryAgents.length > 0)`
  (`:420`), and it keeps the draft in sessionStorage until the library arrives (`:437-439`).
- `canContinue` (`:881-890`) needs only a design system and a brief, both of which the first pass has just restored.
  Continue is `disabled={!canContinue || locked}` (`:1415`), so it is enabled.
- `pipelineAgents` at that moment is `[]` (library empty, `:290`) or the built-in plan roster (once
  `getWorkflowDetail` lands, effect `:472-486`), never the saved roster.
- `handleLaunch` (`:985-1043`) writes `agentIds: pipelineAgents.map(...)` (`:1026`) into a NEW `prototype.draft` /
  `ppt.draft` (`:1029`), overwriting the unrestored one, and routes home. Those `agentIds` reach the launch:
  `[...view]/page.tsx:2510` copies them into the pending params (omitted when empty, `:2544`) and
  `DashboardLayout.tsx:1455-1457` calls `onStartPipeline(webPipeline, brief, agentIds, ...)` with
  `pendingOdProtoParams.agentIds ?? []`. The draft carries no saved-workflow id, so the server cannot recover the saved roster:
  with `agent_ids` empty, `launch_run` takes the `else` branch and runs `agents = get_pipeline_agents(base_pipeline_type)`
  (`backend/app/api/run_commands.py` at HEAD 024c03ef8, `:3577`; the `if agent_ids:` branch is `:3506`).
- Result: a paid run of the built-in default agents for a workflow the user saved with a different roster, with the
  header still showing the saved workflow's name and only the "Advanced N agents" count hinting at it.

**Why the root cause implies it.** Same flaw as [ISS-284](20260828-1906-ISS-284.md): `pipelineAgents` has no
readiness state, so every consumer of it is enabled from first paint. ISS-284 covers the save buttons and the
`getWorkflowDetail` source; this card covers the launch button and the draft-restore source. The Save buttons share
this window too.

### Not affected

A user with an ENABLED override of the built-in: the server resolves the override for the caller and replaces the
roster the client sent (`run_commands.py` at HEAD, `:3630-3657`: `compiled = _merged` `:3656`,
`agents = get_execution_engine()._specs_from_plan(_merged.steps)` `:3657`), so Continue runs the override whatever
`agentIds` carried. That is why ISS-284 does not need to gate Continue for the override case.

### What would settle it

- Browser: cold `page.goto('/workflows/<id>/run')` for a saved prototype workflow with a non-default roster;
  `page.route('**/api/agents/library', hold)`; wait until the brief is pre-filled and Continue is enabled; click it and
  capture the launch request, then ABORT it (the hard limit is no paid run). If the defect exists `agent_ids` is
  absent or empty or built-in-sized, not the saved ids.
- Offline: vitest in `LaunchWizard.test.tsx`'s harness with `preloadedState.agents` EMPTY and a `prototype.draft`
  holding `agentIds` of the saved roster; Continue is enabled after the brief and design system restore; click and
  read the `prototype.draft` it writes. Pre-fix its `agentIds` is `[]`.

### Fix

Gate the Continue BUTTON, nothing else, on "no draft agent restore pending". Track it with one state set in the
restore effect (true when a draft with `agentIds` is seen while `libraryAgents.length === 0`, false once
`setPipelineAgents(restored)` has run) and add it to the `disabled` expression at `:1415`. Do not change
`handleLaunch` or the `buildLaunchDraft` arguments: the draft payload is pinned byte for byte by
`LaunchWizard.test.tsx` and `launchDraft.parity.test.ts`, and the new term is false in every flow without a
pending draft, so those tests are unaffected. The same state belongs in the readiness predicate that
[ISS-284](20260828-1906-ISS-284.md)'s fix adds for the Save buttons if the fixer wants the two windows closed by one
predicate.

## Fixed (2026-10-02, QA-KB-011 fixer): [FIX-701](20261002-0037-FIX-701.md)

As prescribed: `agentRestorePending`, set in the draft-restore effect, is added to Continue's `disabled` only
(`handleLaunch` and `buildLaunchDraft` untouched) and to the shared save/Advanced readiness predicate. Offline:
Continue is disabled while the library is empty and the draft carries agentIds, and enables when the library lands,
launching the saved `["prototype-plan"]` (`evidence/qa-kb-011/09-fix-scratch-check.test.tsx.txt`, case D).

What this card's analysis did not cover: once the restore has run, the spec-017 plan-completion effect
(`LaunchWizard.tsx:481-495`) replaces a restored roster that is SHORTER than the built-in plan, warm or cold, so a
saved workflow with removed agents still launches the full roster. That is a different mechanism from the load
window, it was observed offline, and it is carded as [ISS-943](20261002-0037-ISS-943.md) (open).
