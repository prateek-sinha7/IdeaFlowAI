## Description

Stop at the clarify gate cancelled the run, but the screen never repainted — the live terminal handler cleared only legacy React state, never the run store the lane actually reads (ISS-140), and the one piece of code that did it correctly sat in a switch arm that could never execute (ISS-139). The lane stayed on "Clarifying" with Stop still armed and the clarify questionnaire still submittable, on a run the backend had genuinely already cancelled. The live pipeline_cancelled/pipeline_failed handler is the if (pipelineTypes.includes(msg.type)) block, NOT the switch below it — both message types are members of pipelineTypes, whose branch always returns first, so the case "pipeline_cancelled": case "pipeline_failed": arm at the old page.tsx:1527-1562 was 36 lines of unreachable code that nonetheless contained the mechanically correct runStore.update(..., {questionnaireData: null}). Two source-lock tests had pinned that dead arm and were GREEN while pinning code that had never once executed — a lock satisfied only by unreachable code proves nothing. What shipped: the reachable live block now does if (frameRunId) runStore.update(frameRunId, { questionnaireData: null }) inside the existing run-scoping if (!isForeignFrame) guard (page.tsx:1206); the dead arm is DELETED; and the arm's two genuinely live-relevant effects — setLastCancelledRunId and detachRunRef.current?.() — are rescued onto the reachable path, the first time either has ever executed on a live cancel. Both source-lock files were reconciled, TIGHTER not relaxed: liveRunSwitch.fix201.test.ts (an unanticipated SECOND lock on the same dead string, found mid-execution) now also asserts the write stays inside if (!isForeignFrame). reviewGateData is deliberately NOT added to the store patch: that half really IS masked, by the gate branch's own && isPipelineRunning, and clearing it would erase the historical gate card from a reopened transcript — which terminalReopenReconcile.source.test.ts already locks against. Live-proven on Bedrock with two fresh cheap user_stories runs, each sampled at t+3s/8s/15s/25s after Stop: FIXPROBE (clarify armed, 15 chips / 4 questions) and GATEPROBE (review gate armed, the regression control this fix does not touch) both settle to "Cancelled" with no Stop, no clarify submit, no gate actions, a terminal-cancelled card and API status cancelled.

## Root cause

laneClarifyOpen (DashboardLayout.tsx:1862) is the ONE branch of the runLaneState ternary (DashboardLayout.tsx:1864-1871) NOT AND-ed with isRunning — deliberately, because clarify precedes pipeline_start — and it is evaluated BEFORE the terminal branch. So a lingering store questionnaireData OUTRANKED the terminal markers the same cancelled frame had already applied correctly. The lane reads the STORE (page.tsx:2731, questionnaireData={runStore.viewed.questionnaireData}); the three legacy setters the handler did call (setReviewGateData, setQuestionnaireData, setActivePipelineRunId) are invisible to it. ISS-140's filed text was WRONG and is corrected by this fix: it claimed the defect was "MASKED by the isRunning conjunct ... not user-visible today". laneClarifyOpen has no isRunning conjunct at all; the masking claim only ever held for the reviewGateData half of that row, never for the questionnaireData half, which was the live, user-visible cause all along. Disproven twice — once by source reading, once by live browser reproduction — hence that row's severity is raised minor -> major.
