# FIX-768

**Register source:** `QA-KB-102` (`LEDGER.md`), 5-fixer, 2026-10-08. Resolves [ISS-1103](20261008-0016-ISS-1103.md) (root) and its
siblings [ISS-1119](20261008-1450-ISS-1119.md), [ISS-1120](20261008-1450-ISS-1120.md), [ISS-1121](20261008-1450-ISS-1121.md),
[ISS-1122](20261008-1450-ISS-1122.md), [ISS-1123](20261008-1450-ISS-1123.md), [ISS-1124](20261008-1450-ISS-1124.md). Two findings left
open: [ISS-1125](20261008-1540-ISS-1125.md), [ISS-1126](20261008-1540-ISS-1126.md).

Line numbers are the working tree with this fix applied, on HEAD `2461935f5`.

## What was wrong

The root cause is on [ISS-1103](20261008-0016-ISS-1103.md) and is not re-derived here. The resume tier had no failure channel:
`_drive_resumed_stream` swallowed whatever `_execute_impl` raised with one WARNING, and `resume_run` / `_replay_clarify_run` left through
twelve WARNING-plus-bare-`return` exits. A refused or crashed resume left no terminal event, no new `.error` and no live frame. A user
resume was reconciled `failed` with the previous attempt's error (a degraded run relabelled, a cancelled run left `cancelled`), a restart
auto-resume left a `running` row with no driver that every boot adopted again, the app wrapper's flip-back was database-only, and the run
lane stayed on "Restarting run…".

## What changed, and why there

1. **One failure channel in the engine.** `ExecutionEngine._fail_resume(run_id, reason, live_queue=None)`
   (`backend/agents/execution_engine/engine.py:15525-15586`). It logs ERROR, appends ONE `pipeline_failed` carrying the reason, moves the
   state machine to `failed` (that persists `workflow_runs.status`, which the restart drivers need because they have no app wrapper), and
   puts the frame on the live queue. It never raises. `_reconcile_terminal_status` already derives `.error` from that event on the user path
   (`backend/app/api/run_commands.py:997-1011`), so the reconcile is unchanged.
2. **Called where every driver routes.** The five fault returns of `resume_run` (`engine.py:15636`, `:15716`, `:15769`, `:15794`, `:15808`),
   the same five in `_replay_clarify_run` (`:16203`, `:16256`, `:16279`, `:16299`, `:16313`), and the funnel's `except` (`:16118-16122`)
   unless the stream already yielded a terminal (`_terminal_seen`, `:16009`, `:16047-16053`). The two decision exits of
   `_replay_clarify_run` ("no open questionnaire gate", "open gate has no durable questions") are left alone: ISS-1120 puts them with the
   re-arm owner. The existing WARNING lines stay; the reason strings ("Resume refused: the workflow this run was launched with no longer
   compiles (…)", "Resume failed: <exc>", …) become the user path's `.error`.
3. **The wrapper tells the live client** ([ISS-1123](20261008-1450-ISS-1123.md)). `_drive_user_resume`'s `except` now puts one
   `pipeline_failed` frame on the run's queue, flips back as before, then calls `_cleanup_pipeline` (`run_commands.py:795-807`).
4. **The lane leaves "Restarting run…"** ([ISS-1121](20261008-1450-ISS-1121.md)). `DashboardLayout` keeps the `agents` array the click
   saw (`restartAgentsRef`, `frontend/src/components/layout/DashboardLayout.tsx:662-666`, set at `:2563`), and a new effect clears
   `runRestarting` once the run is not running and `agents` has changed (`:1161-1167`).
5. **Docs only.** The `resume_run` docstring no longer says a refused resume "logs and returns (the run stays in its prior state)", and
   `_drive_user_resume`'s docstring names the frame and the cleanup. On the stub test `test_resume_arm_failure_flips_back_to_failed`
   (`backend/tests/integration/api/test_rest_resume_api.py`) the docstring now says it proves only "a raise is recorded", not that the real
   engine raises ([ISS-1124](20261008-1450-ISS-1124.md) asked for this). No assertion was touched.

### Where this differs from the cards' proposals, and why

- **The funnel's synthesized event is appended through `ScopedStore.append_event_at_or_after`, not the loop's own
  stamp-persist-push block.** `_RunEventSink` is armed only at `engine.py:4932`, after the sandbox quarantine raise at `:4509`. For the
  card's own scenario C, persisting through the loop's sink would have been a silent no-op. One write path serves both the funnel and the
  early returns. The workspace is the one `_stamp_resume_marker` recovers, or the row's `workspace_id` when the run has no durable row yet
  (the clarify replay of ISS-1120).
- **The wrapper's frame is a `pipeline_failed`, not the launch driver's `error` frame** that ISS-1123's inferred direction suggested. The
  frontend `error` case only sets `pipelineError` (`frontend/src/hooks/useWorkflow.ts:1357-1362`) and does not end the restart indicator,
  and every engine-side resume failure now sends `pipeline_failed`, so the client gets one vocabulary. The frame is live-only, like the
  launch driver's: the row already carries the reason through `_flip_back_to_failed`.
- **The wrapper does not call `_fail_resume`** (ISS-1123's preferred "one writer"). That would tie the app wrapper to a new private engine
  method. `test_rest_resume_api.py`'s `_StubEngine` has no such method, so T-50-06's test would break. The faults that reach this
  `except` are raised before the funnel (the row read, `RunTrace(RunSandbox(...))`), mostly database faults, where a durable append would
  fail too.
- **ISS-1121 signal.** The terminal reducer cases rebuild `agents` (`pipeline_failed` at `useWorkflow.ts:1364`, `pipeline_cancelled` at
  `:1408`, both via `prev.agents.map`). `workflow_validated`, the one frame a starting resume sends before `pipeline_start`
  (`engine.py:5217` comes before `:5765`), only spreads `prev` (`useWorkflow.ts:1856-1862`). Rejected: comparing the `pipelineState`
  object (it would clear on `workflow_validated` and flash the old failure copy mid-restart), `timelineTs` (no backend event carries the
  `ts` that `advanceTimeline` needs), and the chat `messages` (tied to the message text format).

### Choices the cards left open

- [ISS-1122](20261008-1450-ISS-1122.md): a refused resume of a `degraded` run now reads `failed`, with the refusal as its reason. That
  matches the bug's expected result ("marks the run failed"). The partial results stay in the event log and the deliverable columns.
  `completed_at` is the refusal time: the attempt ended then. A refused resume of a `cancelled` run also reads `failed`, by the existing
  ISS-316 rule (a later attempt that fails supersedes the cancellation).
- Invariants kept: no workflow-name branch in the kernel (SC-001); the only new kernel imports are `app.models.database` and
  `app.models.workflow`, inside `_fail_resume`, as `resume_run` already does; no migration;
  [FIX-576](20260901-0324-FIX-576.md) still fails closed; one `pipeline_failed` per attempt ([FIX-669](20261001-1918-FIX-669.md));
  the success path is unchanged (the control run's tail is identical before and after, below).
