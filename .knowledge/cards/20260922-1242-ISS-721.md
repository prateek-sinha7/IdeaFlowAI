# ISS-721

## Description

Bug QA-PS-027 (`BUGS.md#qa-ps-027`). A custom-workflow run whose agents never
received the tools/context they needed (root cause: ISS-698, the composer's
"Write files" toggle grants nothing) still shows the header badge **"Done"**
(green) and the chat transcript's Deliverable line as **"Delivered — open in
Preview →"**, even though the actual agent outputs are the agents narrating
their own confusion, not the requested work product.

## Reproduction — 3/3, cold start each

Each attempt is an independent run, freshly navigated to (not a re-click of
the same page):

1. **Cycle A** — run `aa2c0684-ced0-4c19-b6d2-bab9e010966c`
   (`http://localhost:3000/runs/aa2c0684-ced0-4c19-b6d2-bab9e010966c`, brief
   "write a one-line note into a file named result.md"). Header badge: **Done**.
   Deliverable `output.md` (9 agents). Final agent (Task List Planner) output
   opens: *"The file appears corrupted... This suggests the pipeline may have
   failed or the files were not properly generated"* — then re-describes the
   original one-line-note task as three decomposed "tasks" instead of doing it.
   Screenshot: `evidence/qa-ps-027/cycle1-aa2c0684-header.png`.
2. **Cycle B** — run `dfc27751-4e2d-4e89-9b64-a9501b0fd809`, same brief.
   Header badge: **Done**. First agent's own output: *"I don't have access to
   a `write_file` tool"* — the requested file was never written. Every
   downstream agent re-reads the same missing/incomplete upstream file and
   produces more meta-commentary. Final deliverable `output.md` is the Task
   List Planner explaining what *should* happen, not a written note.
   Screenshot: `evidence/qa-ps-027/cycle2-dfc27751-header.png`.
3. **Cycle C** — run `6829bdef-1cf0-4b31-b347-24180f1330d8`, same brief.
   Header badge: **Done** (confirmed via `browser_find`).
   Screenshot: `evidence/qa-ps-027/cycle3-6829bdef-header.png`.

All three runs: `status: "completed"` from `GET /api/runs/<id>`, 9/9 agents
completed without exception, badge and Preview both signal success. No axis
variation needed — 3/3 cold-start reproduction, same trigger every time:
**an agent chain that never gets real tool access/context still completes
"cleanly" (no exception), so the run-level status and UI badge report full
success regardless of what the agents actually produced.**

## Expected vs Actual

Expected: when every/most agents in the chain produce only
meta-commentary/placeholder output (no real deliverable content), the run
should surface as degraded/failed, not "Done".

Actual: header badge and deliverable status are driven purely by whether
agents raised exceptions, not by what they produced. All three cold-start
cycles show a green "Done" badge and "Delivered" deliverable status for
output that is entirely agents describing why they couldn't do the work.

## Note

This card records the run-level "Done despite placeholder content" symptom
only (QA-PS-027). The upstream cause of *why* the agents had no real tools/
context is ISS-698 (QA-PS-019, the Write-files toggle bug) and ISS-705
(QA-PS-025, task_loop injection bug) — both already confirmed. QA-PS-022
("agent with no context/tools produces a placeholder response, engine treats
it as a successful step") is the adjacent sibling bug and is still `Open` in
the register; it was not re-validated here.

## Root cause

**CONFIRMED** by direct read — the engine's terminal completion gate never
inspects agent OUTPUT CONTENT anywhere; every signal it checks is
presence/absence (an exception raised, or a file existing on disk), never
meaningfulness:

- `_execute_impl` (`engine.py:7376-7390`) builds `_unrecovered_agents`
  solely from `ectx.failed_invocations` (invocations that raised) minus the
  completed `(agent_id, task_number, visit_count)` pairs. An agent that
  streams "I'm ready to help" and returns normally IS a completion, not a
  failure — it is never added to `failed_invocations`, so it can never make
  `_unrecovered_agents` non-empty.
- `published_status` (`engine.py:7435-7457`) is computed once, at the tail
  of that SAME pipeline-agnostic `_execute_impl` — the one shared kernel
  path for every pipeline type (SC-001: no `if pipeline_type == "custom"`
  branch exists anywhere in it). `_s5_pub` (`:7438-7442`) defaults to
  `_pipeline_complete_data.get("status", "completed")` — `"completed"`
  unless exactly one of four EXPLICIT signals fired: an unrecovered agent
  (above), a budget-cap degrade (`ectx.budget_degraded_reasons`,
  `:7415-7420`), a blocked last commit (`ectx.last_commit_blocked`,
  `:7426-7427`), or a finalizer-level non-chainable reason from
  `finalize_terminal_run` (read back at `:7439-7441`). None of the four
  inspects deliverable bytes.
- The finalizer's own closest thing to a "did it really produce output"
  check, the `output_unmaterializable` trigger (`engine.py:2107-2122`),
  only verifies `_built_payload.materialized` — that a declared deliverable
  FILE EXISTS on disk — never that its content is meaningful. A file
  holding one sentence of agent narration satisfies it identically to a
  real deliverable.
- `_check_artifact_fallback` (`engine.py:8264-8340`; the write itself is
  `:8333`: `sandbox.write(filename, output or "")`) is the mechanism that
  PUTS placeholder/conversational text on disk in the first place: when a
  custom-agent step's declared file is missing, the engine writes whatever
  the model streamed — verbatim, no length or content check — to the
  declared filename. The "artifact guarantee" that exists (per its own
  docstring) precisely to prevent a silently-empty deliverable is what
  turns a one-line apology into a file the resolvers then treat as real.
- Every deliverable resolver inherits the same gap, confirmed by reading
  all four: `single_file.py:131-134` (`built = sandbox.read(filename); if
  built: return built` — any non-empty read wins), `streamed_text.py:46-48`
  (`return unwrap_artifact(last_streamed)`, unconditional — this is
  `custom/workflow.yaml`'s own declared strategy,
  `deliverable: {strategy: streamed_text, name: output.md}`),
  `ppt.py:67-78` (same shape — transforms `last_streamed` but never checks
  whether it IS a deck), `serialized_sandbox.py:45-51`
  (`count_sandbox_deliverables(root) > 0` — a file-COUNT gate, never a
  content gate; see [ISS-763](20260922-1426-ISS-763.md)).

**Filename/mimetype mismatch — also CONFIRMED, same root defect, secondary
symptom (example 2 in the bug report, `output.html` + `text/markdown`):**
`engine.py:7286-7293` computes `_deliverable_mimetype` from
`_effective_strategy` — the resolver that ACTUALLY produced the bytes,
reassigned from the declared strategy to `"streamed_text"` at `:7193` when
the declared resolver returns `None` (a deliberate WR-01 choice, per the
comment at `:7181-7186`: "so the emitted deliverable_mimetype... always
matches the bytes"). But `_deliverable_name` (`:7286`) is read once from the
DECLARED spec and is never re-derived when the effective strategy falls
back — only the mimetype half of the pair is corrected to track reality,
the filename half is not.

**INFERRED (not settled by this card):** the bug report's own suggested
signal — per-agent "5-10s, 100-300 tokens" — is a plausible heuristic a fix
could use to flag a suspiciously short completion, but nothing in the code
just cited reads `input_tokens` / `output_tokens` / duration per-agent as a
quality gate today. Whether duration/tokens alone reliably distinguish a
placeholder from a legitimately terse agent (vs. false-positiving on it) is
a design question for whoever implements the fix, not something confirmable
by reading the current code.

## Blast radius

Grepped every consumer of the engine's completion signal, not just the
`/create/custom` path the bug report and this card's own reproduction used:

- **Every pipeline type, not only `custom`.** The completion-gate block
  above lives in `_execute_impl` (`engine.py:3961`), the ONE shared
  execution path for ALL pipeline types (SC-001). A native (non-composer)
  `prototype`, `ppt`, or `user_stories` run is exposed to the identical gap
  the moment one of its agents streams conversational/placeholder text
  without raising. See [ISS-761](20260922-1424-ISS-761.md) (INFERRED
  sibling).
- **Every `_revision` pipeline.** `backend/app/api/run_commands.py` has
  THREE independent consumers of the SAME unaware `pipeline_complete.status`
  / `published_status` fields: `_reconcile_terminal_status` (`:762-890`),
  `_drive_launch_to_queue` (`:3818-4011`), and `_drive_revision_to_queue`
  (`:5221-5327`). All three key off `status == "degraded"` / its absence
  with no additional content awareness — `ppt_revision`,
  `prototype_revision`, `user_stories_revision`, and `custom_revision` runs
  are exposed identically. See [ISS-762](20260922-1425-ISS-762.md)
  (INFERRED sibling).
- **`serialized_sandbox` (code-gen / app_builder) pipelines.** Confirmed by
  direct read (`serialized_sandbox.py:45-51`): the resolver's only gate is
  `count_sandbox_deliverables(root) > 0`, a file-count check, never
  content — and `_check_artifact_fallback` above is exactly the mechanism
  that can plant the one file satisfying that count. See
  [ISS-763](20260922-1426-ISS-763.md) (INFERRED sibling).
- **The frontend is NOT implicated — ruled out, not a finding.**
  `frontend/src/components/chat/LaneRunHeader.tsx`'s `laneStatus`
  (`:94-138`) renders `"Done"` only for `runState === "complete"` and
  correctly, distinctly renders `"Failed"` for
  `pipelineState?.degraded`/`.failed` (`:127-128`) — it is a faithful
  renderer of whatever status the backend sends. The wrong status is
  decided entirely server-side before it ever reaches this component.
- **`cancelled` / `failed` / `diverted` runs are unaffected — ruled out, not
  a finding.** They skip the `pipeline_complete` block entirely
  (`engine.py:7435`'s guard) and emit their own distinct terminal event, so
  this defect cannot masquerade as one of those states — only the
  "completed" vs. "degraded" fork is wrong.

## Fix direction (not applied by this card — analysis only)

Belongs in the ONE shared completion-gate block in `_execute_impl`
(`engine.py:7376-7457`), alongside the existing `budget_degraded_reasons` /
`last_commit_blocked` degrade signals (`:7415-7427`) — that block is already
where every pipeline type's terminal status converges, so one additional
signal there covers every resolver and every pipeline type (including every
`_revision` variant, which runs the identical `_execute_impl`) without
touching any of the four resolvers or the three `run_commands.py` consumers
individually. Do NOT duplicate a content check into each resolver —
`single_file.py`, `streamed_text.py`, `ppt.py`, and `serialized_sandbox.py`
would each need the same logic maintained four times, and a fifth resolver
added later would silently inherit the gap again. Left open for whoever
implements the fix: what signal counts as "placeholder" (output length, a
denylist of hedging phrases, the token/duration heuristic the bug report
suggests, or some combination) — a judgment call this card does not make.
