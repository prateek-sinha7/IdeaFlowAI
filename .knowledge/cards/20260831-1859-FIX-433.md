## What was wrong

`prototype-revision-analyzer` runs as **step 0** of all three revision
manifests — `prototype_revision`, `prototype_large_revision` and
`prototype_feature_revision` — but was absent from the registry roster for
every one of them:

```
list_agent_ids("prototype_revision")
  → ['prototype-revision-agent', 'prototype-validate']        # 2
workflow.yaml steps
  → ['prototype-revision-analyzer', 'prototype-revision-agent',
     'prototype-validate']                                    # 3
```

14 xfail-marked cases across 5 files witnessed it: roster-vs-YAML equality and
roster-completeness in `test_registry.py` (6), compiled-vs-registry order in
`test_manifest_coverage.py` (3) and `test_id_alias_resolver.py` (3), plus the
`prototype_revision` wire-parity and characterization snapshots (2), which had
been recorded against the 2-agent roster. A 15th, unmarked red —
`test_get_pipeline_agents_returns_agent_specs_sorted_by_order` — failed with
`orders=[1, 1, 2, 4, 5]`: `get_pipeline_agents` DID pull the analyzer in from
the manifest (via `_own_manifest_step_agents`, the spec-017 reuse completion),
but at a colliding `order: 1`.

## Root cause — `backend/agents/prompts/prototype-revision-analyzer/AGENT.md:13`

The analyzer began life as an **app-layer pre-pipeline** agent and was given
its own private, manifest-less pipeline type so it would deliberately stay out
of the rosters:

```yaml
pipeline_type: prototype_revision_analyzer     # ← the whole defect
```

`revision-pipeline-refactor` (e0f6beeed) then promoted it to manifest step 0 of
all three pipelines and **left that line alone**, working around the resulting
roster gap instead of closing it. The workaround is still commented in
production, and names the root cause verbatim:

```python
# backend/agents/execution_engine/engine.py:7942
# This is required because prototype-revision-analyzer declares
# pipeline_type: prototype_revision_analyzer (its own private type) and is
# therefore NOT in PIPELINE_AGENTS["prototype_revision"] — passing the
# registry list silently skips step 0 of the manifest.
```

`PIPELINE_AGENTS` is derived from each `AGENT.md`'s own `pipeline_type` +
`order` (`agents/registry.py:_discover_pipeline_agents` → `agents/loader.py:184
list_agent_ids`), so the frontmatter IS the membership declaration. A step in
the manifest that no `AGENT.md` claims is invisible to every roster consumer:
the agent library, `allowed_custom_agent_ids`, the DAG resolver's `consumes`
validation and the API's step count.

The two `prototype_revision` goldens are a **second, independent** casualty.
e0f6beeed regenerated them correctly (`agent_count: 3`); `732adc245` — which is
**not** a descendant of e0f6beeed — regenerated them on a tree where the
analyzer was not yet a step (`agent_count: 2`), and the merge `5d9885150`
resolved the conflict onto that side. The `large`/`feature` goldens only
survived because they did not exist on the other branch.

## What changed and why there

**Membership, in the one place membership is declared** —
`prototype-revision-analyzer/AGENT.md`:

```yaml
pipeline_type:
- prototype_revision
- prototype_large_revision
- prototype_feature_revision
```

`pipeline_type` has accepted a list since the multi-pipeline case was added
(`loader.py:465 _parse_pipeline_type`); `prototype-validate` and
`prototype-build` already use it. Nothing in the loader, the registry or the
engine changed — the fix is data, which is exactly the SC-001 shape (a workflow
is a manifest plus an `AGENT.md`, with zero engine edits).

**Order re-spacing, because `order` is a single scalar per agent.**
`list_agent_ids` sorts the roster by `order` and rejects duplicates, so the
analyzer has to sort ahead of each pipeline's former first step. `order` is
constrained to `>= 1` (`loader.py:325`), so `0` was not available and the tail
of the prototype family had to shift up by one to open a slot at 2:

| agent | before | after |
|---|---|---|
| `prototype-revision-analyzer` | 1 | 1 (unchanged) |
| `prototype-revision-agent` | 1 | 2 |
| `prototype-revision-planner` | 1 | 2 |
| `prototype-revision-feature-specify` | 1 | 2 |
| `prototype-plan` | 2 | 3 |
| `prototype-analyze` | 3 | 4 |
| `prototype-build` | 4 | 5 |
| `prototype-validate` | 5 | 6 |

`prototype-specify` stays at 1. Every relative order — in the base `prototype`
pipeline and in all three revisions — is byte-identical to before; only the
numbers moved. That is safe because nothing reads `order` as an index: it is
the sort key in `list_agent_ids`/`get_pipeline_agents` and in the four frontend
`a.order - b.order` comparators (`LibraryPage.tsx:682`, `AgentLibrary.tsx:129`,
`IdeaInputPage.tsx:1274`, `LaunchWizard.tsx:151`).

`prototype_revision_analyzer` disappears from `SUPPORTED_PIPELINE_TYPES` with
this change. It was a phantom type — no `agents/workflows/` dir, so it was
already excluded from `_MANIFEST_BACKED_IDS` and unlaunchable; every production
use of the frozenset is a gate, so losing it only tightens.

**Goldens regenerated** with `SNAPSHOT_UPDATE=1`, then restored to the CRLF
line endings the committed `*.events.json` files carry, so the diffs show only
the semantic change (a whole-file LF rewrite otherwise buried 1 changed entry
in 1,146 changed lines). Semantic delta, measured entry-by-entry:

- `prototype.events.json`, `prototype.wsframes.json`,
  `prototype_large_revision.events.json`,
  `prototype_feature_revision.events.json` — **exactly one** entry each, the
  `pipeline_start` agents list, carrying the new `order` numbers.
- `prototype_revision.events.json` (16 → 21 entries) and
  `.wsframes.json` — the analyzer's step-0 events restored and the downstream
  `index`/`total` shifted `0/2 → 1/3`, i.e. e0f6beeed's recording put back.

  production caller — already recorded on
  [ISS-630](20260831-0115-ISS-630.md), not deleted here.

  shared agent. This fix works because the numbers happen to line up; the next
  manifest that reuses an agent at a different position will need
  `list_agent_ids` to read manifest order instead. Not carded — no defect
  exists today.
