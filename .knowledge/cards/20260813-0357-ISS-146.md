# ISS-146

## Title

**The narrator's "Delivered — open in Preview" chat card rendered TWICE after a mid-run SSE reconnect.** `GET /api/runs/{id}/events` (`api.ts:583-590`) merges a durable row's `event_id`/`seq` COLUMNS over `payload_json`; the SSE endpoint's durable-replay step (`run_stream.py:202`) discarded those columns and served `payload_json` RAW. Four app-layer event types (`chat_reply`/`chat_message`/`chat_usage`/`run_resuming`) persist NO identity inside their own payload, so for those rows the columns were the only identity that existed — and the narrator's real durable key (`chat_reply:{source_event_id}`, underscore) can never be reproduced by the frontend's fallback (`` chat-reply:${message_id} ``, hyphen), so a card delivered once live and once via a replayed reconnect rendered as two differently-keyed bubbles. Live-reproduced twice on Bedrock (`c706162e` no-drop control = 1 card; `8b0989d0` dropped+reconnected = 2 cards) before the fix shipped. **FIXED 2026-08-13 (FIX-248):** one line at `run_stream.py:202` merges the row's `event_id`/`seq` columns over `payload_json` on replay, mirroring the REST twin's own convention — no frontend file touched. Proven by a new backend unit test (RED: `event_id` absent → GREEN: 44 passed/0 failed) and a new mounted-browser e2e (`TS-SSE-RESILIENCE-06`, RED: 2 cards → GREEN: 1 card). **Live re-proof deferred** — see FIX-248's Status column; blocked by an unrelated AWS SSO token issue, not by this fix.
