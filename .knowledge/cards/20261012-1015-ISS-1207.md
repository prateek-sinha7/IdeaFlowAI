# ISS-1207

**INFERRED** sibling of [ISS-1194](20261012-0735-ISS-1194.md) (register entry `QA-KB-123`). The mechanism is replayed offline on a recorded capture and read from the JSX; the live DOM text of the filtered breakdown was not re-captured, which is what keeps this INFERRED (see "What would settle it").

## Condition

Any caller of `runs_by_pipeline(page)` (`tests/integration/e2e/framework/locators/analytics.py:103-129`): ISS-289 `test_pipeline_breakdown_respects_the_model_filter_too` (`test_analytics.py:388` and `:402`) and S-10-10 `test_the_pipeline_breakdown_sums_to_the_totals` (`:194`). It returns shifted pairs for any card with two or more rows and nothing for a one-row card; the `.get("PROTOTYPE")` lookups work only when two rows happen to share that label.

## Expected vs actual

Expected: `runs_by_pipeline` returns `{label: runs}` for each row of the By Pipeline Type card, whatever the number of rows. Actual: it returns the previous row's count under each label, never reads the last row, skips any row whose label does not start with A-Z (`.NET MIGRATION`) together with the previous row's count, and returns `{}` for a one-row card.

Replay (`evidence/qa-kb-123/analysis-02-analytics-filter-and-locator.txt`, Part C; the regex is copied from `analytics.py:125-128`):

| input text | true content | `runs_by_pipeline` result |
|---|---|---|
| recorded `tests/integration/capture/35-analytics.json` (19 pipeline rows, label first) | APP BUILDER 3, PROTOTYPE 12, CUSTOM 24, ..., PROTOTYPE 8; the 19 rows sum to 221 | 16 labels summing to 171: `'PROTOTYPE': 3.0, 'CUSTOM': 12.0, ...` (APP BUILDER's count under PROTOTYPE); CUSTOM's 24 appears nowhere and `.NET MIGRATION` is never a key |
| `?pipeline=prototype` on today's data: one `prototype_revision` row | PROTOTYPE 6 | `{}` |
| the D-11 era: a `prototype` row and a `prototype_revision` row, one label | PROTOTYPE 12, PROTOTYPE 8 | `{'PROTOTYPE': 12.0}` (row 1's count, row 2's label) |
| D-11 fixed: one merged row | PROTOTYPE 20 | `{}` |

## Why the root cause implies it

The register counts ISS-289 as the fourth test that "needs a v1 prototype run" ([ISS-1194](20261012-0735-ISS-1194.md)). It fails with `Prototype not found in the By Pipeline Type breakdown / assert None` (`first_errors.txt:20`, `triage.txt:16` in `evidence/qa-kb-123/analysis-03-validate-bugs-log-excerpts.txt`), which is exactly the parser returning `{}`. The breakdown is one row today because the Analytics "Prototype" filter is `type IN ('prototype','prototype_revision')` (`backend/app/api/analytics.py:529`) and the admin history holds no `prototype` row, only 6 `prototype_revision` rows (`analysis-02` Q1). With a v1 `prototype` run present the card has two rows that both read PROTOTYPE (`AnalyticsPage.tsx:319`: `PIPELINE_LABELS[normalizeType(type)]` maps both types to "Prototype"), and the regex happens to find a label after the first row's figures. So the data gap exposed a parser that only worked because of D-11's duplicate label: providing the missing run would have hidden this, and fixing D-11 would bring it back.

## Why the pairing is wrong (CONFIRMED by reading)

- The row JSX is label first, figures second: `AnalyticsPage.tsx:559` `<span ...>{p.label}</span>` then `:560-563` `<div ...><span>{p.runs} run...</span>` and the dot, tokens and cost spans. `innerText` therefore reads `LABEL`, `<n> runs`, `·`, `<tokens>`, `<cost>`, then the next row's `LABEL` (the recorded capture shows exactly this order).
- The helper's docstring says the opposite (`analytics.py:111-112`: "Rows read `<n> runs · <tokens> <cost> <TYPE>` — the label follows its figures"), and its regex (`:125-126`) takes a count, skips up to three lines, then takes the next all-caps line as the label.

## Where the fix belongs

`framework/locators/analytics.py:103-129`, the only parser. Read each row as label-then-figures; that fixes all three call sites at once. Keep the "first occurrence wins" behaviour deliberately or sum duplicates deliberately: with D-11's duplicate label `setdefault` currently keeps row 1 and silently drops row 2's count, and S-10-10's total check would want the sum. Correct the docstring at `:111-112`. Extracting the text-to-dict step into a pure function makes it testable offline (the module imports only `re`).

After the parser is right, ISS-289 will not go green on today's data: the six `prototype_revision` runs carry one model (`eu.anthropic.claude-haiku-4-5-20251001-v1:0` in every `agent_outputs`, `model_id` NULL on the run rows; `analysis-02` Q1b and Q1c), so the model `<select>` is not rendered (`AnalyticsPage.tsx:425`, `availableModelIds.length > 1`) and the test skips at `test_analytics.py:392-393`. That skip is the designed outcome; the scenario only executes when the Prototype-filtered window lists two or more models.

## What would settle it

`document.body.innerText` of the By Pipeline Type card at `/analytics?range=All&pipeline=prototype` on the live stack. If it reads `By Pipeline Type\nPROTOTYPE\n6 runs\n...`, the replay above is exactly what the test sees. A card whose label came after its figures would refute this.
