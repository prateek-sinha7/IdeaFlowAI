# ISS-976

**CONFIRMED at the HTTP layer, INFERRED in the UI.** Derived while analysing QA-KB-054 ([ISS-687](20260918-ISS-687.md)). The 422 below was produced by driving the real router in-process (`evidence/qa-kb-054/test_probe_save_side.py`, output in `evidence/qa-kb-054/output.txt`). That a given button sends this body was read from the code, not clicked.

## Condition

Save a workflow whose `base_pipeline_type` is one of the custom-agent file workflows (17 of 39 on this branch: `prototype_v2`, `backlog`, the `ex_A*` fixtures, ...) with a flat `agent_ids` roster of its compiled `custom-agent:<instance_id>` ids and **no `manifest`**.

## Expected / actual

Expected: save accepts what launch accepts. `user_workflows.py` docstring: "Save == launch validation ... A saved row can never carry something launch would reject." ISS-687's fix makes launch accept a workflow's own roster, so save must not reject it.

Actual (executed): `422 {"detail": "agent_ids not allowed for 'prototype_v2': ['custom-agent:fi-planner', 'custom-agent:fi-readers']"}`, and the same for `backlog` with `['custom-agent:us-planner']`.

## Why the root cause implies it

`create_user_workflow` re-uses the launch predicate verbatim, `backend/app/api/user_workflows.py:720-722`:

    if body.manifest is None:
        allowed_ids = allowed_custom_agent_ids(body.base_pipeline_type)
        rejected = [aid for aid in body.agent_ids if aid not in allowed_ids]

and `allowed_custom_agent_ids(<custom-agent file workflow>)` is the empty set (`registry.py:446-447`; `PIPELINE_AGENTS[wf] == []`, see ISS-687). Only the manifest-backed shape skips the check (`user_workflows.py:709-719`), which is why the Composer is unaffected.

This is the second and last production call site of `allowed_custom_agent_ids` (`grep -rn allowed_custom_agent_ids backend --include=*.py`: `run_commands.py:3524` and `user_workflows.py:721`).

## Callers that send the failing shape (read, not clicked)

- `LaunchWizard.handleSaveWorkflow`, `LaunchWizard.tsx:936-942`: `createUserWorkflow(jwt, { base_pipeline_type: MODE_CONFIG[mode].savePipeline, agent_ids: pipelineAgents.map((a) => a.id), selections })` with no `manifest`. `savePipeline` is `"prototype_v2"` for the "New prototype from documents" mode (`LaunchWizard.tsx:136`). Unlike this wizard's launch path (`LaunchWizard.tsx:1041` filters the `custom-agent:` ids) the save path has no filter.
- `AgentsPopup.handleSaveWorkflow`, `AgentsPopup.tsx:2797-2810` -> `saveUserWorkflow` -> `createUserWorkflow` (`frontend/src/lib/api.ts`): `agent_ids: agents.map((a) => a.id)`, no `manifest`.
- `IdeaInputPage.handleSaveWorkflow`, `IdeaInputPage.tsx:1710-1722`: same shape, `base_pipeline_type: effectiveType`.
- NOT affected: `LaunchWizard.handleSaveAsOverride` (`LaunchWizard.tsx:970-988` sends `manifest`) and ComposerPage (hard-codes `base_pipeline_type: "custom"`, `ComposerPage.tsx:931`).

## What would settle the UI half

Open the `prototype_v2` wizard (or a custom-agent file workflow in the launch panel), press Save workflow, and read the save modal's error line. Expect the 422 text above.

## Fix guidance

Apply the same predicate as launch through ONE shared helper (do not write two copies). Leave `allowed_custom_agent_ids` untouched. Sequence with ISS-687: land the launch normalisation first, then call it from `create_user_workflow`.
