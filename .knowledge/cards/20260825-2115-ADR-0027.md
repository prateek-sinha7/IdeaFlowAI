## Decision

A user's override of a built-in workflow stores **only the step list**. Every workflow-level
field is read from the file manifest on every run, override or not.

## Why

A full user manifest **cannot compile** for `ppt`. `WorkflowCompiler._check_trust`
(`backend/agents/workflows/compiler.py:417`) rejects any capability not registered
`user_allowed=True`, and `registry.is_user_allowed` **defaults to False**. Both
`deliverable/ppt` and `context_provider/opendesign` lack the flag, so a DB-sourced ppt manifest
is refused at `trust="db"`.

The alternatives were to make those capabilities user-grantable — widening the trust surface for
every user manifest, not just overrides — or to special-case ppt. Overlaying `steps` alone needs
neither: the file manifest keeps supplying everything the trust model protects.

## What it locks in

- A user can change **which agents run and how each is configured**. They cannot change what the
  workflow *delivers*.
- `merge_override_steps` compiles the row's steps alone (with placeholder deliverable/planner/
  clarify that are discarded), takes `.steps`, and returns
  `dataclasses.replace(compiled, steps=...)`. It must never mutate `compiled` — `compile_for_run`
  is `@lru_cache(maxsize=None)` and hands the same object to every user and run.
- A refused override (malformed row, not-user-allowed capability) returns the base plan unchanged,
  so the run proceeds on the file plan rather than failing.

## Consequence discovered later

Because the deliverable stays file-owned, a workflow whose strategy is last-streamed (`ppt`,
`streamed_text`) has its deliverable produced by whichever step runs LAST. An override that
appends a step therefore replaces the deliverable — see [FIX-305](20260825-2115-FIX-305.md).
