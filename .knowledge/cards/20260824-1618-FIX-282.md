Two related failures on the composer's "Run once":

1. An UNMODIFIED built-in opened on the canvas sent
   `pipeline_type: "custom"` plus bare `agent_ids: ["emoji","language",…]` → 400.
2. A MODIFIED composition had no launchable shape at all.

## Root cause

`agent_ids` are allow-listed against `allowed_custom_agent_ids(base)`, which is registry
membership (`PIPELINE_AGENTS[base] | PIPELINE_AGENTS["custom"]`). A composed workflow's
nodes are dynamically generated `custom-agent:<instance_id>` instances whose bare ids can
never appear there. `ComposerPage`'s own comment documented the limitation: the only
escape was `user_workflow_id`, which requires saving first.

## Fix, in two parts

**Unmodified built-in** — launches by its own `pipeline_type` with NO `agent_ids`, so the
backend sources the roster from the compiled plan. This is exactly the payload the
`.http` runners use, and it preserves the manifest's own deliverable/planner/clarify,
which an inline steps-only manifest would replace with composer defaults.

**Modified composition** — the launch body now accepts an inline `manifest`, compiled at
`trust="user"`. See [ADR-0016](20260824-1630-ADR-0016.md) for why that is not a new trust
surface.

Verified live: unmodified `ex_A2_branch` ran from the canvas as `type: ex_A2_branch` and
routed to `say-hola` on Spanish input; a modified composition (a branch target removed,
with its route outcome) ran as `type: custom` and still routed correctly. A modification
that leaves a DANGLING route target is correctly refused with a precise R-10 message.
