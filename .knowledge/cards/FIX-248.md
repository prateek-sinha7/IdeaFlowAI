## Description

The narrator's "Delivered — open in Preview" milestone card rendered TWICE in the run chat lane after a mid-run SSE reconnect (ISS-146). Two endpoints project the SAME durable run_events row differently: GET /api/runs/{id}/events (api.ts:583-590, since the BUG-018 fix) merges the row's event_id/seq COLUMNS over payload_json; the SSE endpoint's durable-replay step (run_stream.py:202) discarded the columns and served payload_json RAW. Harmless for engine-authored events — the engine stamps identity INTO the payload itself before persisting (engine.py:1085-1086) — but four app-layer types (chat_reply, chat_message, chat_usage, run_resuming) persist with NO identity embedded, so for those rows the columns are the ONLY identity that exists. The narrator's card is one such row (chat_narrator.persist_milestone_card); its real durable key (chat_reply:{source_event_id}, UNDERSCORE, keyed on the source milestone's own uuid) can never be reproduced by the frontend's fallback ( chat-reply:${message_id} , HYPHEN) — so a card delivered once live (real key) and once via a replayed reconnect (anonymous, pre-fix) renders as two differently-keyed bubbles. The production trigger is more specific than "any reconnect," and was traced end to end, not assumed: pipeline_complete IS a member of the SSE endpoint's own _STREAM_TERMINAL_TYPES (run_stream.py:79), so the live drain returns the instant it is drained — the narrator card, queued by the engine immediately AFTER pipeline_complete (engine.py:1104-1132), is never delivered live on that connection at all. useRunStream.ts:301 does not treat pipeline_complete as a non-live close (a separate, deliberately unfixed gap — see ISS-147), so the client reconnects, carrying Last-Event-ID = <completeSeq>; the server replays the card off the durable tail (pre-fix, anonymous) — racing the completion backfill (page.tsx → getRunEvents) that independently fetches the SAME row, WITH identity, via detachRun's FIX-172 "additive insurance" (page.tsx:967-980). That insurance is defeated whenever the run's id is ALSO in RunConnectionProvider's autoIdsRef (armed by an online/visibilitychange wake firing WHILE the run is still active — exactly what a mid-run network blip does), because detachRun only clears the sticky-focus half of liveRunIds = union(autoIdsRef, focusedRunIdRef). Fix (Option A, one line, server-side): merge the row's event_id/seq columns over payload_json at the replay yield, adopting the convention the REST twin already used — yield _sse_frame(r.seq, r.type, {**(r.payload_json or {}), "event_id": r.event_id, "seq": r.seq}). No frontend file touched; the frontend's keying/dedup logic was already correct, it simply never received the identity to key on.

## Root cause

run_stream.py:202's durable-replay yield served r.payload_json raw instead of merging the row's event_id/seq COLUMNS — the sole identity source for the 4 app-layer event types that embed none in their own payload.
