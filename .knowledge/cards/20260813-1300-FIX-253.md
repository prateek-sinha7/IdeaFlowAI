## Description

update_specs_eligible was advertised but never enforced — the review gate ran the spec-revision sub-pipeline at firings that had published the affordance as unavailable, and gate_key names a gate SLOT rather than a FIRING so REPLAYING a legitimate earlier click was enough (no crafting). Harm was corruption and cost, not redundancy: at the two DEFAULT-gated agents (index < 2) it revised nothing yet blanked the agent's output and re-opened the gate empty; at a build/validate gate it re-ran the build (~$3.68 vs ~$0.03, no rate limiting). Live-observed on run d5dbc9f2 (gate advertised eligible=0, action accepted 6.05s later). The declared gates:[human]/[approval] path also had NO _gate_update_specs branch, so the signal leaked to the SSE wire AND fell through to GATE_PASS — a silent approve.

## Root cause

A modelling decision, not a mechanism: KAN-101 modelled update_specs_eligible on redoable, but redoable is genuinely advisory (a redo re-runs the same agent, always meaningful) while update_specs dispatches a sub-pipeline whose targets are chosen POSITIONALLY from the gated agent's index — so the same action means "re-run specify/plan/analyze" at one gate and "re-run plan/analyze/build" at the next. The flag that encodes WHICH gate is which was classified as cosmetic and discarded: it was a parameter of _run_review_gate (engine.py:5450), stamped onto the outbound event (:5516), then never read again — the branch at :5576 keyed purely on the client-supplied action string.
