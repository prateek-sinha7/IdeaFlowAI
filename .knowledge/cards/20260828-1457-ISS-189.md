## Page / route / component

- Page: PPT wizard shell (New presentation)
- Route: `/create/ppt`
- Component: `frontend/src/components/workflow/LaunchWizard.tsx` (shared launch wizard shell
  used by prototype and PPT modes)

## Root cause

The template preview modal for "Investment Banking Pitch Book" shows an "Uses design system"
badge, and selecting it sets a requirement that the wizard's unmet-requirements pill row
renders as "Pick a design system". However, `LaunchWizard.tsx`'s design-system auto-select
logic (added in [FIX-103](20260723-FIX-103.md)) only default-selects a design system when
`prev === null && mode === "prototype"` — it is scoped exclusively to prototype mode. In PPT
mode, `selectedDsId` is never initialized for a template that declares a design-system
requirement, and no design-system picker UI is rendered anywhere in the PPT wizard for the user
to satisfy the requirement manually. The pill is thus permanently unmet and `Continue` stays
`disabled === true` regardless of a valid template + non-empty brief.

## Analysis (QA-KB-010, analyzer, 2026-10-01)

**Verdict.** Root cause CONFIRMED and sharpened. The "Root cause" section above states two true
facts but frames the defect as a missing auto-select. The mechanism that makes the wizard a dead
end is that the design-system STEP is never mounted for decks. The agreed minimal fix is accepted
(the auto-select is rejected, see Alternatives). No product decision is needed.

### ROOT CAUSE (CONFIRMED, every line below was read)

One contradiction inside `frontend/src/components/workflow/LaunchWizard.tsx`: a hard gate with no
reachable affordance.

- **Gate.** `dsRequired = isDeck && selectedDeckTemplate?.design_system?.requires === true`
  (`:698`) feeds `canContinue` (`:889`:
  `Boolean(selectedTemplateId && hasBuildInput && (!dsRequired || selectedDsId))`) and the pill
  (`:1373`: `(isWeb || dsRequired) && !selectedDsId && <Pill label="Pick a design system" />`).
- **Affordance.** The only user-facing control that sets `selectedDsId` is `DesignSystemPicker`
  inside `dsSlot` (`:1309-1324`). `dsSlot` is already built for decks (`dsVisible = isWeb ||
  dsRequired`, `:699`).
- **Why it never shows.** `WizardStepper` mounts `dsSlot` only when the active step id is
  `"design-system"` (`WizardStepper.tsx:187`), and the active step id comes from the `steps` prop
  (`:128`). `LaunchWizard.tsx:1298` passes
  `steps={isDeck ? ["template"] : ["template", "design-system", "discovery"]}`, so no deck ever
  has a design-system step.
- **No other writer of `selectedDsId`:** the picker handlers (`:766-773`), draft restore (`:416`),
  and FIX-103's auto-select (`:666-669`, prototype only). The deck draft carries
  `designSystemId: null` unless `dsRequired` (`:998`), so a restored draft supplies none either.

**Regression history** (read-only git). The 37-07 wizard `cc1097213` (2026-07-10) passed no
`steps` prop (default: three steps) and set `dsVisible = mode === "prototype" || dsRequired`, so a
design-system-requiring deck could reach the picker. [FIX-065](20260721-1133-FIX-065.md)
(`95bc44bf6`, 2026-07-21) added `steps={mode === "ppt" ? ["template"] : [...]}` to drop the
DS/Discovery tabs for PPT. That is right for the 52 of 55 deck templates that need no design
system, but it left the gate and pill untouched, so the 3 that do became unlaunchable.
`70665bbcb` (2026-08-27) generalised `mode === "ppt"` to `isDeck`, which extended the clamp to
`ppt_v2`.

**Why auto-select is not the fix.** FIX-103's effect runs once at mount (`:652-676`), before any
template is chosen, so it cannot know `dsRequired`. Extended to decks it would preselect "apple"
for every deck and silently discard it for the 52 that need none (`:998`), and with no picker the
user could never change it: an Investment Banking deck would be styled by a design system nobody
chose.

### Test escape (CONFIRMED)

`LaunchWizard.test.tsx:78-108` stubs `WizardStepper` and renders `props.dsSlot` unconditionally;
the stub's prop type does not even declare `steps`. The deck tests at `:233-247` and `:282-299`
pick the design-system-requiring template `pitch` (`:67`) and then click `pick-ds`, which exists
only because the stub ignores the step list. They pass while the real wizard is unlaunchable.
`WizardStepper.test.tsx` never exercises `steps` either, so the decision at `:1298` has no
coverage at any layer.

### BLAST RADIUS (CONFIRMED by grep)

- **One call site.** `WizardStepper` has exactly one non-test consumer (`LaunchWizard.tsx:1295`),
  and every `dsRequired` consumer is in that file (`:698, :889, :910, :963, :998, :1373`, plus
  dependency arrays).
- **Modes and URLs.** `isDeck` is true for `ppt` and `ppt_v2` (`STEPPER_MODE`, `:81`):
  `/create/ppt`, `/create/ppt_v2` (`wizardModeFor`, `[...view]/page.tsx:349-361`),
  `/workflow/create?mode=ppt|ppt_v2`, and `/workflows/{id}/run` for a saved ppt/ppt_v2 workflow
  (`[...view]/page.tsx:4089-4101`).
- **Templates.** Of the 55 deck/slides templates from `od_loader.list_ppt_templates()` exactly 3
  declare `design_system.requires: true`: `ib-pitch-book` (Investment Banking Pitch Book),
  `weekly-update` (Weekly Team Update) and `simple-deck` (Clean Slide Deck, named in neither
  QA-KB-010 nor QA-PS-010). That also answers QA-PS-010's "there may be others" audit request.
- **Not affected.** Web wizards (DS step present); custom/uploaded deck templates
  (`selectedDeckTemplate` is null, so `dsRequired` is false, test `:263-278`); the composer
  (`DesignPickerModal` always offers its DS tab and `designMissing` does not require a DS for
  decks, `ComposerPage.tsx:476-478`); the dashboard launch (`[...view]/page.tsx:2579-2582` only
  requires `templateId` and passes `designSystemId ?? null`).
- **Downstream use of a picked DS (so the picker is not a placebo).** `designSystemId` ->
  `buildLaunchDraft` (`launchDraft.ts:119-122`) -> `ppt.draft` -> `load_ppt_od_context`
  (`backend/app/api/launch_context.py:448`, `backend/agents/execution_engine/od_context.py:299-324`)
  -> `ppt-composer` declares `injects: [template, design_system, template_example]`
  (`backend/agents/prompts/ppt-composer/AGENT.md:11-14`).

### FIX (accepted as agreed) and where it belongs

One place, the single expression that decides which steps exist, `LaunchWizard.tsx:1298`:

```
steps={isDeck ? (dsRequired ? ["template", "design-system"] : ["template"]) : ["template", "design-system", "discovery"]}
```

All callers (ppt, ppt_v2, every route above) funnel through this one prop, and `dsRequired` is
already the shared predicate for the gate, the pill and `dsSlot`, so keying the step list on it
makes the gate and its affordance agree by construction. FIX-065's goal (no DS/Discovery tabs for
the 52 non-DS decks) is kept, and FIX-096's `steps.length > 1` guard (`WizardStepper.tsx:193`)
means the Back/Next row appears only in the 3 two-step cases. The expression is keyed on data
(`isDeck`, the template's own `design_system.requires`), never on a workflow or template name, so
SC-001 / INV-1 hold; `buildLaunchDraft` is untouched, so the launch-contract parity gate (INV-3)
is unaffected. Anchor the edit on the unique string `steps={isDeck ? ["template"] :`, not on a
line number.

Walk-through with the real stepper (CONFIRMED by reading, not run): select a DS-requiring
template -> `dsRequired` true -> steps `["template","design-system"]` -> a "Design System" tab and
Back/Next appear and the pill still shows -> the user opens the tab -> `dsSlot` ->
`DesignSystemPicker` -> `handleSelectBuiltInDs` sets `selectedDsId` -> pill clears -> Continue
enables -> `designSystemId` is written to `ppt.draft`. Choosing a non-DS template shrinks the steps
back to one; the template step is index 0 and `WizardStepper.tsx:128` falls back to `"template"`
for an out-of-range index, so no tab is stranded.

Left behind, harmless: the `<StepNote>` "doesn't require a design system" branch (`:1322`) becomes
unreachable for decks, because the DS step now exists only when `dsRequired`.

### Alternatives considered

- **Extend FIX-103's auto-select to decks (`:668`).** Rejected, see above (and the BUGS.md note).
- **Hide the DS-requiring templates from the deck gallery** (QA-PS-010's stated expectation,
  logged 2026-09-17, closed DUPLICATE of this card). Not chosen: it removes 3 of 55 templates, and
  QA-PS-010's underlying concern (a pipeline that cannot complete correctly) is met by the picker
  instead. A product owner may still prefer it; it would be a catalog filter in
  `od_loader.list_ppt_templates`, not a wizard change.
- **Relax the gate so Continue works with no DS.** Not chosen. The backend tolerates it
  (`od_context.py:323-324` sets `is_design_system_required = False`), but the deck then runs
  without the tokens the template declares it needs (`sections: [color, typography, layout,
  components]`), contradicting the documented rule (`LaunchWizard.tsx:693`, `:888`; composer copy
  "Required - supplies the colour, type and spacing tokens", `DesignPickerModal.tsx:309-311`).
- **Always include the DS step for decks.** Not chosen: it reverts FIX-065 for the 52 templates
  that need no design system.
