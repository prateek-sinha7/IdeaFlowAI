# ISS-934

## Description

Sibling of [ISS-398](20260828-2106-ISS-398.md) (QA-KB-017), found while mapping its blast radius. ISS-398 is about the `model_overrides` map, and its fix paragraph assumes every model id a user supplies passes through `_validate_model_overrides`. The per-agent model the product UI sends today does not.

The Canvas Model lever (`frontend/src/components/workflow/composer/CanvasConfigRail.tsx:1035-1066`, `aria-label="Model"`, options = the whole catalog, no tier filter) writes `selections[agentId].model`. `AgentsPopup.tsx:2737-2744` says so outright ("per-agent model lives in `selections[id].model` ... No separate `model_overrides` key") and `IdeaInputPage.tsx:1624` posts `selections: launchSelections` when a run starts. `AgentModelPicker`, the component that used to emit `model_overrides`, is mounted nowhere any more; only comments mention it. So a fix confined to `_validate_model_overrides` closes an API door the UI does not use and leaves open the one it does.

On the server a per-step model inside `selections` is validated by a different function, which also has no tier input.

## Why the root cause implies it

Same flaw as ISS-398, in a second validator: a model id is accepted on catalog membership alone. `backend/agents/workflows/selections.py:249-254` documents that `selections` "takes a DIFFERENT route than the `model_overrides` map", so ISS-398's "all callers inherit the fix" cannot hold for it.

## Evidence

CONFIRMED, read:
- `backend/agents/workflows/selections.py:245-276`: `validate_selection_model_ids(selections)` loops `sel.get("model")` and rejects only `not catalog.is_allowed(model)`. `is_allowed` is "known and `user_allowed`", the CAP-03 trust flag, which is a different axis from subscription tier (`model_catalog.py:440-443`).
- Save callers: `backend/app/api/user_workflows.py:420` inside `_compile_selections_trust_user` (`:386`), reached from create (`:739`) and PATCH (`:987`).
- Launch caller: `backend/app/api/run_engine.py:726` inside `_revalidate_selections_trust_user` (`:693`), reached from `backend/app/api/run_commands.py:3736`, and only when `launch_source is not USER_WORKFLOW_MANIFEST` (`:3728`).
- The engine applies the value as tier-2 `step.model` (`backend/agents/model_policy.py:216-227`); [ISS-168](20260819-1834-ISS-168.md) traced live that a Canvas-selected model reaches Bedrock as `modelId`.
- The function lives under `agents.workflows`, which import-linter forbids from importing `app` (`backend/pyproject.toml:383-387`), so the tier check cannot be added inside it.

CONFIRMED, executed offline (scratch probes outside the repo; no database, no network, stub engine, nothing written to the repo):
- `validate_selection_model_ids({"domain-analyst": {"model": "eu.anthropic.claude-opus-4-6-v1"}})` returns `None` (accepted). `can_use_model("basic", <same id>)` returns `(False, "This model requires Pro or higher. Upgrade your plan to unlock it.")`.
- Save, repo harness `backend/tests/integration/api/test_user_workflows_api.py` (`api` fixture, `_FakeUser(tier="basic")`): `POST /api/user-workflows` with `base_pipeline_type=user_stories`, `agent_ids=["domain-analyst"]`, `selections={"domain-analyst": {"model": <opus-4-6>}}` returned 201 (pro: 201).
- Launch, repo harness `backend/tests/integration/api/test_rest_run_launch_api.py` (`env` fixture, recording stub engine, `user.tier = "basic"`): `POST /api/runs` with `pipeline_type=user_stories` and the same selections returned 200, one WorkflowRun minted, and the engine's `execute()` received `selections={'domain-analyst': {'model': 'eu.anthropic.claude-opus-4-6-v1'}}`.

INFERRED, not driven: a real browser session as `basic@velocity.ai` using the Canvas Model lever, and a live run on Bedrock (no run was launched; hard limit). What settles it: the QA-KB-017 verifier setting the lever to Opus on `/workflows/user_stories/canvas` as basic and reading the Save response.

## Expected vs actual

- Expected: a basic account's save or launch carrying a premium `selections[*].model` is rejected before any row or run exists.
- Actual: accepted (201 on save, 200 on launch with a run minted).

## Fix direction

One tier check for this door at the app layer, keyed on `effective_tier(user, principal)` ([ADR-0013](20260916-ADR-0013.md)), over every `sel["model"]`, called from both wrappers or from the single shared helper described on [ISS-398](20260828-2106-ISS-398.md). `validate_selection_model_ids` keeps its catalog job and stays kernel-pure. Tier denial is 403 ([FIX-361](20260829-0029-FIX-361.md)'s locked constraint), catalog stays 422. PATCH needs a principal first: `update_user_workflow` depends on `get_current_user` only (`user_workflows.py:937`).

## Test notes
