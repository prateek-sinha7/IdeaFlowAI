## Analysis (QA-KB-040, 2026-10-01, analyzer)

**Verdict: stale test expectation. Change the two assertions; touch no application file.** CONFIRMED.

### Root cause (CONFIRMED, every line below was read)

1. `frontend/src/hooks/useWorkflow.ts:476-556`: `upsertWaveWorker` builds every wave-worker child row as one
   object literal of 30 keys (`:493-550`). Most are carried forward from `prior`, so on a fresh row 24 of
   them are `undefined`.
2. One key is never undefined: `useWorkflow.ts:536`, `startedAt: prior?.startedAt ?? Date.now(),`
   (comment at `:534-535`: "Start the clock on the FIRST event for this member"). It is the clock base for the
   measured-duration fallback at `:543-549`. Typed at `frontend/src/types/index.ts:1042` (`startedAt?: number`).
3. `frontend/src/hooks/useWorkflow.waveWorkers.test.ts:37-39` and `:52-54` assert the row with
   `toEqual([{ taskId, status, workerIndex, waveIndex, waveTotal }])`.
4. `toEqual` ignores `undefined`-valued keys but not a defined one. The only defined key beyond the five
   asserted is `startedAt`, a millisecond epoch the test can neither predict nor list, so both assertions
   fail. Vitest prints every extra key with a `+` (`evidence/qa-kb-040/01-...txt`), which makes it look as
   if the 30-key count is the problem. It is not.

### Proof that `startedAt` alone is the cause (CONFIRMED by run)

Run from a scratch root outside the repo (no repo file touched), importing the real reducer and
`reducerHarness` by absolute path. `evidence/qa-kb-040/04-analyze-matcher-experiment*`:

- the row has 30 keys; the defined ones are exactly `startedAt, status, taskId, waveIndex, waveTotal, workerIndex`
- `toEqual` as the test is written: fails
- `toEqual` after deleting `startedAt` from the received row: passes, so the 24 undefined keys are ignored
- `toEqual` with `startedAt: expect.any(Number)`: passes
- `toMatchObject` with the five asserted fields: passes
- `toMatchObject` still fails on an extra row (array length is enforced) and on a wrong `status`

And on a scratch copy of the REAL test file with only lines 37 and 52 changed to `toMatchObject`: `Tests 10
passed (10)`. Control, the unmodified copy in the same harness: `2 failed | 8 passed (10)`, identical to the
repo. `evidence/qa-kb-040/05-analyze-proposed-fix-proof.txt`.

### Why this is a stale test and not an app regression (CONFIRMED from git and source)

- `startedAt` was added on purpose. Commit `05b7bce54` (2026-09-10, "wave-worker identity and UI") added it
  with 16 other fields of the row, the explanatory comments (`useWorkflow.ts:534-535`, `:537-542`), the type
  member (`types/index.ts:1042`) and tests for the behaviour it enables
  (`AgentDetailPanel.waveWorkerStatus.test.tsx:359-396`, the `wave member duration` block).
- The test file is older: created 2026-09-04 in `1e329e47b`. `05b7bce54` did not touch it, and the "Tests:"
  paragraph of its message does not name it (`useWorkflow` occurs 0 times in that paragraph), so the file went
  red on 2026-09-10 unnoticed. `a56c90506` (2026-09-29) appended three field-level cases to it
  (`waveWorkers?.[0].modelId ... .toBe(HAIKU)`) and left the two failing `toEqual` cases alone;
  [FIX-653](20260929-1021-FIX-653.md) records them as already failing. `evidence/qa-kb-040/08-analyze-git-history.txt`.
- The value is wall-clock time taken inside the reducer, like the other `Date.now()` uses in the same file
  (`useWorkflow.ts:586`). Nothing renders it: outside tests `frontend/src` mentions `startedAt` for a wave
  member only at `useWorkflow.ts:536`, `:546`, `:547`, `:586` and the type at `types/index.ts:1042`
  (`AuditTab.tsx` has an unrelated run-level field of the same name). There is no user-visible behaviour to
  have regressed.

### Correction to the report

BUGS.md and the validation note above put it as "`toEqual` requires exact equality but the objects have 30
properties, the expectations 5". The count is a red herring: `toEqual` ignores `undefined` keys, so 24 of the
30 are irrelevant and ONE defined key matters. The direction (a test-side fix) is unchanged. What it changes is
the choice of fix: stripping or normalising undefined keys would do nothing, and the stricter alternative below
only has to name `startedAt`.

### Blast radius (CONFIRMED by grep and by running each file alone, 2026-10-01, HEAD `024c03ef8`, `git status frontend/` clean)

- Production: none. `upsertWaveWorker` is called at `useWorkflow.ts:901` (running), `:1118` (done) and
  `:1214` (failed); `startedAt` is read only inside the reducer. No production file needs to change.
- Tests that assert equality on a reducer-built wave-worker row: exactly two, `useWorkflow.waveWorkers.test.ts:37`
  and `:52`. The file's other `toEqual`s (`:137` `waveSkipped`, `:148` `waveRepair`) are exact small objects and pass.
- The only suites that feed `task_id`-stamped (wave) frames through the reducer are this file,
  `useWorkflow.waveTokens.test.ts` (2/2 pass) and `AgentDetailPanel.waveWorkerStatus.test.tsx`
  (27 pass, 2 fail for a different reason, filed as [ISS-866](20261001-2105-ISS-866.md)).
- Other suites that reach the reducer through `reducerHarness` all pass: `useWorkflow.accumulators` 46/46,
  `runAccounting` 8/8, `specRevisionCount` 21/21. Component suites that mention `waveWorkers`:
  `AgentDetailPanel.waveWorkers` 7/7, `StepsOverviewSpine.wave` 6/6, `AgentThinkingTab` 9/9,
  `TokenUsageSummary.cache` 4/4.

### Fix (the agreed minimal fix is accepted; nothing is overruled)

Test-only. In `frontend/src/hooks/useWorkflow.waveWorkers.test.ts`, change `.toEqual([` to `.toMatchObject([`
on lines 37 and 52. Keep the expected objects as they are (`taskId`, `status`, `workerIndex`, `waveIndex`,
`waveTotal`).

Why this strength is right: the file header (`:1-10`) says these tests are about nesting, one parent row, one
child row per `task_id`, status transitions. `toMatchObject` on an array still enforces the array length and
every listed field's value (proved above), and stops pinning a clock value. The stricter alternative,
`toEqual` with `startedAt: expect.any(Number)` added, also passes, but it re-pins the tests to a field they
are not about, and the next always-defined field breaks them again.

Where it belongs: there is no shared function to guard and no other caller (blast radius above), so the two
lines in the test are the whole fix.
