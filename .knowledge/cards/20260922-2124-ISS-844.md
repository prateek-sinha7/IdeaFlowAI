## LibraryPage.tsx makes no fetch of its own (CONFIRMED)

`frontend/src/components/library/LibraryPage.tsx` has five `useEffect`s
(`:74`, `:78`, `:531`, `:570`, `:648`) — all local UI-state seeding (focus,
Escape-key handling, URL tab/slug sync). None calls `fetch`, `axios`, or any
`lib/api.ts`/`store/api/*` function (confirmed by direct read of each). Its
data comes entirely from Redux selectors: `state.agents.status`,
`state.skills.status`, `state.hooks.status` (`:477-479`) and
`state.global.workflows` (`:482`, used at `:485` to build `agentCategories`
and at `:816` to look up each agent's workflow-type label — a real,
non-dead use). All four of those slices are populated by
`store/listenerMiddleware.ts`'s `signedIn` listener, not by Library itself.
There is also no dedicated `/library` route folder — `find frontend/src/app
-maxdepth 2 -type d` lists only `[...view]`, `admin`, `handoff`, `login`,
`register`, `workflow`, `preview-fullscreen` — so `/library` is served
entirely by the shared catch-all. Every mechanism below is therefore
cross-route infrastructure, not a Library-specific defect.

## Mechanism 1 — `/api/workflows` doubling (CONFIRMED structure, OPEN, actionable)

1. `frontend/src/app/[...view]/page.tsx:913-934` — the auth-check mount
   effect — unconditionally calls `dispatch(signedIn({ token: storedToken
   }))` (`:924`) with **no** StrictMode-remount guard (confirmed by direct
   read of the current file: no ref/lock of any kind in this effect, unlike
   its sibling effect below).
2. `grep -rn "dispatch(signedIn(" frontend/src` returns exactly one line,
   `page.tsx:924` — the only place this action is ever dispatched app-wide.
3. `frontend/src/store/listenerMiddleware.ts:22-66`'s `signedIn` listener is
   its only consumer. It reads `state.global.workflowsStatus` (`:47`) and
   dispatches `fetchWorkflows()` (`:52`) only when that status is not
   `"loading"`/`"succeeded"`.
4. `grep -rn "dispatch(fetchWorkflows(\|fetchWorkflows()" frontend/src`
   returns exactly two lines app-wide: the thunk's own definition
   (`globalSlice.ts:32`) and this one dispatch site
   (`listenerMiddleware.ts:52`) — no other caller exists.
5. `fetchWorkflows()` (`globalSlice.ts:32-34`) calls `workflowsApi.list()`
   (`store/api/workflows.ts:78-81`) — a bare `axios http.get("/api/workflows")`
   with no cache and no in-flight guard of its own (confirmed by direct
   read; this is a wholly separate HTTP client from `lib/api.ts`'s
   `cachedGet()`-covered functions, per `store/api/http.ts`'s own header
   comment: "a second shared request path... bypassing `lib/api.ts`'s
   `fetchWithAuth` entirely").

Steps 2 and 4 (exhaustive grep, single call site each) leave no candidate
source for a second `/api/workflows` call other than step 1's effect firing
twice. `next dev`'s React 18 StrictMode mounts every component's effects
twice in development (mount → cleanup → remount); this exact effect, on the
structurally identical `/create/ppt` route, was already measured doing this
3/3 live ([ISS-794](20260922-1827-ISS-794.md): `workflows` x2, `auth/me`
x3), and [ISS-832](20260922-2001-ISS-832.md) confirmed by direct read that
it "applies verbatim" to `/workflows/new` — same shared component, same
effect, no route-specific code in between. Nothing about `/library` is
different: same catch-all, same unguarded effect.

**What is INFERRED, not re-confirmed live for `/library` by this card:**
the exact count today. Settling it needs a fresh cold `/library` capture
(`performance.getEntriesByType('resource')` or the MCP browser
network-request tool) filtered to `/api/workflows`, the same method
[ISS-843](20260922-2114-ISS-843.md) used for the sibling Library-detail bug.

**The "why does the guard fail" mechanism is itself unresolved** — see
[ISS-845](20260922-2125-ISS-845.md), filed alongside this card.

## Mechanism 2 — `/api/runs?limit=50` can still double (OPEN, but a known cross-route gap, not new)

- `page.tsx:1017-1044`'s own `recentRuns` effect (`getWorkflows(currentToken,
  {limit:50})` → `setRecentRuns`) now carries a `recentRunsRequestedRef`
  guard (declared `:824`, checked `:1031`, set `:1034`) — confirmed by
  `git blame -L 1022,1046 -- "frontend/src/app/[...view]/page.tsx"` to be
  the newest, still-uncommitted edit to this file (2026-09-22 21:17:35
  +0200), layered on [FIX-630](20260922-2115-FIX-630.md) (21:15). This
  effect's own contribution to the doubling is therefore now closed, for
  every route including Library.
- `frontend/src/providers/RunConnectionProvider.tsx:279-331`'s
  `refreshLiveRuns` (mounted app-wide via `app/layout.tsx:51`, above the
  router) independently calls the same `getWorkflows(t, {limit:50})`
  *unless* this tab's `sessionStorage.tab_launched_run_ids` is empty
  (`:296-316`, the early-return [FIX-617](20260922-1935-FIX-617.md) added).
  A tab that has already launched or viewed a run this session — which the
  browser this bug-fixing line shares across many bugs will have, by the
  time it reaches `/library` — still fires this second, independent call.
  [FIX-616](20260922-1923-FIX-616.md)'s `inFlightWorkflows` map
  (`api.ts:887`) only collapses genuinely *concurrent* calls; these two
  effects fire from different components a few ticks apart, outside that
  window. [FIX-618](20260922-1945-FIX-618.md) already measured and
  explicitly left this exact pair unfixed on `/settings/profile`
  ("Overriding that is a design decision, not this fix") — the same gap,
  unchanged, applies to every route sharing these two components.
- Both eventual consumers are real, not dead code: `AppHeader.tsx:188,200`
  (mounted at `DashboardLayout.tsx:2720`, `recentRuns` passed at `:2754`,
  **above** the `mainView === "library"` branch at `:2934` that renders
  `<LibraryPage />` at `:2951`) drives the header's "N Running" badge;
  `RunConnectionProvider` uses its own copy to auto-reattach this tab's SSE
  connections. Neither is "unused" the way the original bug report assumed.

This is the identical fact already established for `/settings/*`
([FIX-618](20260922-1945-FIX-618.md)), `/analytics`
([ISS-782](20260922-1610-ISS-782.md)), `/dashboard`
([ISS-808](20260922-1850-ISS-808.md) /

## Where the fix belongs

Both open mechanisms live in the ONE shared component every route —
including `/library` — mounts through,
`frontend/src/app/[...view]/page.tsx`, plus the two app-wide singletons it
feeds (`listenerMiddleware.ts`, `RunConnectionProvider.tsx`).
`LibraryPage.tsx` has nothing to fix; it fetches nothing.

- **Mechanism 1**: give the auth-check effect (`page.tsx:913-934`) the same
  one-shot guard its sibling `recentRuns` effect just received
  (`recentRunsRequestedRef` at `:1017`), or make the `fetchWorkflows`/
  `fetchRecentRuns` dispatch itself idempotent (e.g. a module-level
  in-flight/one-shot lock in `globalSlice.ts` or `listenerMiddleware.ts`,
  mirroring `api.ts`'s `inFlightWorkflows`/`cachedGet`). One guard at this
  choke point closes it for every route sharing the effect — `/dashboard`,
  `/analytics`, `/settings/*`, `/workflows/new`, `/runs`, `/workflows`,
  `/library` — not just this one. A Library-local patch would have nothing
  to attach to, since Library issues no fetch of its own.
- **Mechanism 2** is the same already-escalated AppHeader-consumption
  question tracked for QA-PS-035/036/037/038/041/046
  (`ESCALATIONS.md#qa-ps-035`); no new escalation is filed by this card
  beyond noting Library belongs on that list. Collapsing
  `RunConnectionProvider`'s and `page.tsx`'s independent callers into one
  shared fetch (rather than removing either) would close the duplication
  without touching what either consumer needs — that is a code fix, not a
  product decision, and is open regardless of how the escalation resolves.

### Why 3/3 (ISS-787, 18:15) then 0/5 (test-writer's later re-check) doesn't refute Mechanism 1 — INFERRED

Both measurements are consistent with an unresolved race condition rather
than a closed guard: a race's defining signature is that it does not
reproduce at a fixed rate across separate sessions — dev-server HMR/compile
state, React 18 StrictMode's double-invoke timing, and backend response
latency all differ between an 18:15 run and a later one, and any of them can
widen or close the window in which a second `dispatch(signedIn(...))` reads
stale state. A guard that reliably closed the window would read 0/N
consistently; this reads 3/3 then 0/5 — inconsistent in both directions,
which a stably-fixed or a stably-broken path would not produce. This is
INFERRED reasoning, not a re-confirmed mechanism: it does not by itself
decide between ISS-845's two candidate triggers (StrictMode double-invoking
one mount's effects vs. a genuine second mount of the `[...view]` catch-all,
per [ISS-843](20260922-2114-ISS-843.md)'s precedent for the latter). Settling
that still needs the instrumented capture ISS-845 already specifies
(mount-effect invocation count alongside dispatch/reducer timestamps on one
live cold load) — not attempted by this note.

### For the fixer

The fix this card already names does not require knowing which of ISS-845's
two mechanisms is correct: a one-shot guard on `page.tsx:912-933` itself,
mirroring `recentRunsRequestedRef`, closes this effect's own contribution to
the race regardless of trigger — exactly as
[FIX-630](20260922-2115-FIX-630.md) already did for the sibling effect in
the same component. It does not touch Mechanism 2
(`runs?limit=50`'s cross-component duplication between `page.tsx` and
`RunConnectionProvider`), which stays the separate, already-escalated
product question at `ESCALATIONS.md#qa-ps-035`.
