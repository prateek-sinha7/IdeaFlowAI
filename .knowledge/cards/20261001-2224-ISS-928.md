# ISS-928

Derived from the QA-KB-041 analysis of [BUG-104](20260829-1508-BUG-104.md). **Confidence: INFERRED** for real browsers. The
mechanism is CONFIRMED on the live source and reproduced offline in jsdom (below); nobody has run it in Safari or Firefox.

## Condition

The account menu in the app header (`button[aria-label="Account menu"]`, rendered by `AppHeader` on every page), opened by
a click that does not focus the trigger button (Safari and Firefox on macOS do not focus a `<button>` on click; a
programmatic `.click()` does not either), then Escape pressed.

## Expected

Escape closes the menu and returns focus to the trigger. The code comment and the test both promise it
(`AppHeader.tsx:174-175`, `AppHeader.a11y.test.tsx:147-158`).

## Actual

The menu stays open and `aria-expanded` stays `"true"`.

## Why the root cause implies it

[BUG-104](20260829-1508-BUG-104.md): Escape is bound with a React `onKeyDown` on the wrapper element, so it only counts
keydowns that start inside that wrapper. A keydown targets `document.activeElement`; with the trigger unfocused that is
BODY, which is not inside the wrapper. The profile menu has exactly that shape:

```tsx
// AppHeader.tsx:174-182
// a11y: Escape closes the menu and refocuses the trigger. Bound on the wrapper
// so it fires whether focus is on the trigger button or a menu item.
const handleMenuKeyDown = (e: React.KeyboardEvent) => {
  if (e.key === "Escape" && profileOpen) {
    e.stopPropagation();
    setProfileOpen(false);
    triggerRef.current?.focus();
  }
};
// AppHeader.tsx:529
<div className="relative" ref={dropdownRef} onKeyDown={handleMenuKeyDown}>
```

The comment's "fires whether focus is on the trigger or a menu item" assumes one of the two holds focus. Nothing moves focus
into the menu on open: the only `.focus()` call in the file is the trigger refocus inside this handler (`:180`). Outside
click works because it is a document `mousedown` listener (`:153-161`), independent of focus.

## Evidence (offline, jsdom; nothing under `frontend/src` was created or edited)

`evidence/qa-kb-041/08-analyze-probe-output.txt`, source `07-analyze-probe-notif-header.test.tsx.txt`:

| case | activeElement after the click | after Escape |
|---|---|---|
| CONTROL, `user.click(trigger)` (focuses, like Chrome) | trigger | menu closes, trigger focused |
| REPRO, `fireEvent.click(trigger)` (never focuses) | BODY | `aria-expanded = true`, menu present |

Why existing coverage cannot see it: `AppHeader.a11y.test.tsx:147-158` opens the menu with `user.click(trigger)`, which focuses
the button, so it only ever exercises the working case.

## Reach (INFERRED)

Safari and Firefox on macOS, and any input path that opens the menu without focusing the trigger. Chrome on every OS and a
menu opened from the keyboard (Enter or Space on the focused trigger) are unaffected. The header is on every page, so the
surface is wide, but the cost is one extra click outside the menu.

## What would settle it

Real Safari or Firefox (macOS): open the account menu with the mouse, press Escape. Or in Chrome DevTools:
`document.querySelector('[aria-label="Account menu"]').click()`, then press Escape (the validator used the same trick for
BUG-104, `evidence/qa-kb-041/03-validate-attempt2-jsclick-menu-open.png`).

## Fix direction

Same as [BUG-104](20260829-1508-BUG-104.md): drop the wrapper handler (`:174-182` and the `onKeyDown` prop at `:529`) and
call the shared hook from [FIX-388](20260829-0053-FIX-388.md), gated on the menu being open:
`useEscapeToClose(() => { setProfileOpen(false); triggerRef.current?.focus(); }, profileOpen)`
(`frontend/src/hooks/useEscapeToClose.ts`). Keep the `enabled` argument: an ungated listener would run on every Escape on
every page. Do not hand-roll another inline effect.

Not the same defect, same file: the "N Running" dropdown (`AppHeader.tsx:404-419`, `aria-haspopup="menu"`) has no Escape
binding at all. See the "Adjacent" section of [BUG-104](20260829-1508-BUG-104.md).

## Resolution (QA-KB-041, fixer, 2026-10-02)

[FIX-710](20261002-0154-FIX-710.md) applies the "Fix direction" above as written.
`AppHeader.tsx:178` now reads
`useEscapeToClose(() => { setProfileOpen(false); triggerRef.current?.focus(); }, profileOpen);`.
`handleMenuKeyDown` is deleted, and the wrapper at `:525` no longer carries `onKeyDown`.

**The test file was corrected, and that is disclosed in FIX-710.** `AppHeader.escape.test.tsx` checked
`queryByRole("menu")` for null synchronously after Escape. The menu leaves through a 0.12s `AnimatePresence` exit
(`:543-550`), so that check raced the animation. On an unchanged tree it gave XPASS, then expected fail, then XPASS.

The check now runs inside `waitFor`, matching `AppHeader.a11y.test.tsx:154-156`, which this card cites as the expected
behaviour. Against the pre-fix AppHeader the corrected test is red: a `waitFor` timeout, with the menu still present. On
the fixed tree it XPASSes in 3 of 3 runs. The marker is left for the verifier.
