## Condition

A run opened from a surface that calls `onSelectWorkflowRun` and then pushes
`routes.runStream(id)` (`/runs/{id}/stream`, `routes.ts:115`, parsed to
`run-stream` at `routes.ts:418`):

| `DashboardLayout.tsx` | surface |
|---|---|
| `:2848-2852` | header run list, terminal branch of `AppHeader.handleRunClick` (`AppHeader.tsx:265-266`) |
| `:2911-2913` | bell panel, completed notification, run found in `recentRuns` |
| `:2916-2924` | same, run not cached: pushes first, then `getWorkflow(...).then(onSelectWorkflowRun)` |
| `:2951-2953` | bell panel, old notification matched by title/type |
| `:3471-3484` | completion toast, cached or fetch-then-open |

## Expected vs actual

Expected: one reopen per click: one `GET /api/runs/{id}`, one `events?after=0`,
one family seed.

Actual (inferred): two of each. On the fetch-then-open variants the click-time
call is made by the handler's own `getWorkflow(...).then(...)` after the push, so
it runs on a page instance that is already gone, or about to be.

## Why ISS-840's root cause implies it

`page.tsx:3578-3781` is T11, the `/runs/{id}/stream` twin of the T7 effect
ISS-840 describes. It carries both parts of the flaw:

- the skip guard `if (runId === trackedRunIdRef.current) return;` (`:3589`),
  which reads the freshly mounted page's `null` ref once the push has remounted
  the page (`:3494-3499`);
- the same fall-through `void handleSelectWorkflowRun({ id: runId } as
  WorkflowRun)` (`:3772`), reached for every run that is not in
  `runConnection.liveRunIds`. A terminal run never is, because
  `handleSelectWorkflowRun` attaches only non-terminal runs (`:2993`).

The click-time call is the wasted one for the reason ISS-840 gives
(`useRunStateStore.ts:399` hands an unmounted page a throwaway entry); the
effect's call is the one that lands. A fix applied to T7 only leaves this path.

## Non-terminal variant (same sites, same cause)

For a run this tab has attached, T11 takes its `liveRunIds` fast path
(`:3601-3767`), which replays `getRunEvents` (`:3653`) and `getRunFamily`
(`:3687`) itself. That replay is required, because the remount wiped the page's
state, so the duplicate is the click-time reopen. A fix that special-cases
`!liveRunIds` ("terminal runs only") leaves this variant behind.

## Fix location

Same as ISS-840: the click-to-push hand-off, not T11's guard. Do not make
`appliedRunViewKeyRef` module-scope; `runViewEffects.qaSg004.source.test.ts`
locks it per-mount.

## What would settle it

Playwright as admin: open the bell panel, click a completed notification whose
run is outside the recents window, and count `GET /api/runs/{id}` and
`events?after=0` after the click. Two of each today if the inference holds, one
of each after the ISS-840 fix.

## Fix 2026-10-07 (5-fixer, QA-KB-067)

Fixed by [FIX-753](20261007-2216-FIX-753.md), the same change that fixes ISS-840, made at the hand-off both share.
The header list, bell and toast call `onSelectWorkflowRun`, which `page.tsx` now wires to `primeRunOpen`
(no fetch) instead of `handleSelectWorkflowRun`. The two fetch-then-open variants this card lists
(`DashboardLayout.tsx` bell uncached, toast uncached) lost their `getWorkflow(...).then(onSelectWorkflowRun)`.
T11's guard is unchanged.

Manual verification after the fix used a Playwright probe as admin, with no run launched. The bell entries were
seeded through `flowin.notifications.v3`. Counts are `GET /api/runs/{id}` / `events?after=0` / `/family`:

| Path | Run | Result |
|---|---|---|
| Bell, run inside the recents window | `38db40af` | 1 / 1 / 2, deliverable rendered |
| Bell, run outside the recents window (the dropped fetch-then-open) | `417e3c59` | 1 / 1 / 2, deliverable rendered |
| Bell, for the run already open at that URL | `38db40af` | 0 / 0 / 0, deliverable still rendered |

Screenshots: `evidence/qa-kb-067/04-fix-after-{2-bell-cached,3-bell-uncached,4-bell-same-url}.png`.

The "before" counts on this path were never measured, so the doubling stays INFERRED from the shared mechanism.
The header-list and toast paths were not driven, because both need a live run. They call the same prop.
