# ADR-0009: The wave surface is compiler-derived, and waving requires declared edges

## Status: partial

The scheduling **surface** is built and verified. The **dispatcher** is not. See
"What is not built" — do not read this card as "step concurrency shipped".

## Context and Problem Statement

`ExecutionEngine.execute()` runs steps strictly serially. Measured on
`sample_subagents`, where `joke` declares `depends_on: []` and is independent of
`fact`:

```
emoji  03:50:11.856 -> 03:50:43.424
fact   03:50:43.438 -> 03:51:04.635
joke   03:51:04.652 -> 03:51:25.074   started 11ms after fact ENDED
page   03:51:25.089 -> 03:52:20.891
```

Zero overlap. `subagents: mode: parallel` compiles to zero DAG edges between
siblings — the freedom is expressed and then ignored.

Task-level fan-out already exists (Phase 11 `run_fanout`, Phase 12
`build_waves`). Both parallelize *inside* one step. Step-level concurrency was
never designed — no evidence of it anywhere in `.planning/` or `.knowledge/`.

`build_waves` (`capabilities/strategies/wave_scheduler.py:58`) is a pure Kahn-levels
partitioner with conflict-key splitting. It reads exactly four attributes off each
item: `id`, `depends_on`, `conflict_keys`, `targets`. `Task` declares all four;
`Step` declared only `depends_on`.

## Decision 1 — the wave surface is compiler-derived, not authored

`Step` gains `conflict_keys` and `targets`, and an `id` property aliasing
`agent_id`. With those, `build_waves` runs against a list of `Step` **completely
unmodified** — verified.

Neither field is added to `_ALLOWED_STEP_KEYS`, so no manifest author can write
them and **INV-5 ("no DSL — control-flow keys stay rejected") is untouched.** The
compiler fills `conflict_keys` from a fact it already has:

```python
conflict_keys=[instance_id] if instance_id else [],
```

`instance_id` is a complete stand-in for the step's output file, because
`artifact_name` (`workflows/artifacts.py`) keys the on-disk filename on
`instance_id` **alone** — so the conflict key is knowable at compile time without
the run's topic slug, which is not.

`id` is a **property**, not a field: a real field would duplicate `agent_id` in
every `asdict()`, manifest round-trip and equality check, and the two could then
disagree.

## Decision 2 — waving requires declared `depends_on`

This came out of running the new surface against real plans, and it is the
important half of this card:

```
sample_subagents:
   wave 0: ['custom-agent:emoji', 'custom-agent:joke']
   wave 1: ['custom-agent:fact']
   wave 2: ['custom-agent:page']

prototype:
   wave 0: [ALL FIVE STEPS]

app_builder:
   wave 0: [ALL FIFTEEN STEPS]
```

`prototype` and `app_builder` collapse to a single wave — because their step
order comes from the **resolver DAG** (`produces`/`consumes` on each `AGENT.md`),
not from declared `depends_on`, and the compiler cannot see it. To `build_waves`
they are fifteen unrelated steps.

A dispatcher naively driven by `build_waves(compiled.steps)` would therefore run
every `app_builder` agent concurrently, against one shared sandbox, in a pipeline
that is strictly sequential in reality. That is data corruption, not a
performance regression.

**So eligibility is: the plan must carry declared `depends_on` edges.** Same
discriminator as the ordering branch (ADR-0004). For a plan without them every
wave is size 1 and the loop is exactly today's. This is not a safety net bolted
on — it is the only correct reading: absent declared edges, the compiler does not
know the ordering, and "no edges" must mean "assume sequential", never "assume
independent".

The longer-term fix is ADR-0004's Option 1 — merge `depends_on` into the
resolver's graph so there is one edge set — after which every plan has real edges
and this restriction dissolves.

## Decision 3 — opt-in is a settings flag, not a manifest key

A new `parallel:`/`wave:` step key would be a manifest-declared control-flow key
— INV-5 rejects it. A process-level setting (e.g.
`settings.ENABLE_STEP_WAVE_CONCURRENCY`, default **off**) instead:

- never reaches `_ALLOWED_STEP_KEYS`, so INV-5 is untouched
- gates a branch **inside the existing loop**, so INV-12 (*"single
  `_execute_impl`/`run_fanout` dispatch path; never a third launch-driver copy"*,
  `.planning/ROADMAP.md:1198`) is satisfied — wave-of-1 is the literal existing
  code path
- does not silently change `sample_subagents` the day the code merges, which a
  DAG-shape-implied trigger would

`compiler.py`'s existing rejection of `max_parallel` under `mode: parallel` stays
a rejection. It is orthogonal — an author-declared numeric cap the engine still
has no field for — and repurposing it as the opt-in signal would be a silent
manifest-semantics change.

## What is NOT built

Everything that actually makes steps run concurrently:

1. **Per-step `ExecutionContext` scoping** — the highest-risk item. At least
   eight single-slot fields mean "the one step running now": `current_step`,
   `last_streamed`, `redo_directive`, `steering_notes`, `pending_turn_images` /
   `turn_images_once`, `current_task_block` / `build_task_number` /
   `build_task_total`, and `ectx.depth` (bumped and restored in `fanout.py`, a
   mutation site outside `context.py` that the first audit missed). Plus the
   `results[-1]` idiom at twelve read sites and two append sites. Wrong scoping
   raises nothing and fails no golden — the goldens are order-canonical
   multisets — so the failure mode is silent cross-step corruption seen first in
   production.
2. **The wave dispatcher** — `asyncio.Queue` fan-in inside the same loop.
3. **`skill_staging` wave-union prune** — it currently prunes against ONE step's
   attached skills, so two concurrent steps delete each other's (ADR-0006). A
   lock does not fix it; the prune set must become the wave's union.
4. **Cancellation** cancel-and-drain, **gates** at wave boundary, **resume** for a
   partially-complete wave (Phase 12's D-07 deliberately avoided a step-status
   table; reusing `wave_runs` at step level is the candidate).

## Consequences

**Positive.** `build_waves` is reusable as-is — no fork, no second entry point.
The surface is inert: `conflict_keys` is empty on every non-custom-agent step and
nothing calls `build_waves` on steps yet, so this change is a no-op at runtime.
Verified: 116 compiler/plan/resolver tests and all 17 golden characterization and
wire-parity tests pass unchanged.

**Negative.** A partially-built feature is a hazard if mistaken for a finished
one — hence `status: partial` and this section. `Step` now carries two fields
nothing reads, which is dead weight until item 2 lands.

**Neutral.** Built-in steps get no conflict key, which is correct only while
nothing waves them. Whoever enables waving for built-ins must give them real
write targets first, or two steps writing `prototype.html` could co-schedule. The
compiler comment says this at the assignment site.

## Confirmation

Verified by direct execution against real compiled plans (see Decision 2 output).
116 tests across `test_compiler.py`, `test_compiler_subagents.py`,
`test_manifest_coverage.py`, `test_allowed_step_keys.py`,
`test_workflow_resolver.py` pass; 17 golden tests pass.

**No test covers the wave partition itself yet** — a unit test asserting the
three-wave shape for `sample_subagents` and the single-wave collapse for
`app_builder` should land with the dispatcher, since the second is the safety
property that matters.

The overlap test, when the dispatcher exists, must be **deterministic, not
timing-based**: have each of two scripted models block until it observes the
other has started. Concurrent execution proceeds; serial execution deadlocks and
the test times out. A wall-clock assertion would be flaky.
