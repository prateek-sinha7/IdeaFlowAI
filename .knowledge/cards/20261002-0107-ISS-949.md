### A. A REST-launched revision loses `parent_run_id` (CONFIRMED)

The route is `POST /api/runs`, `launch_run` (`backend/app/api/run_commands.py:3256`). The report's `/api/runs/launch` is not a route.

1. **The admission gate declines the source.** `launch_run` calls `admit_chain_launch` (`:3818` [HEAD 3778]). When the manifest
   does not declare `deliverable.chains_from` (default False: `backend/agents/workflows/plan.py:369`, `compiler.py:1645`) it
   returns `ChainAdmission(active=False, refusal_reason="declaration_gate")` (`:5310-5312` [5270-5272]), and `source_id` keeps
   its default `None` (`:4888`). All ten `*_revision` manifests lack `chains_from` (`grep -c chains_from` is 0 in each
   `backend/agents/workflows/<x>_revision/workflow.yaml`: app_builder, backlog, custom, ppt, prototype, prototype_feature,
   prototype_large, prototype_v2, prototype_v2_feature, user_stories). Only `ppt_v2`, `backlog`, `prototype` and
   `user_stories` declare it.
2. **Only the admitted id is handed on.** `:3855-3857` [3815]: `_admitted_source_id = _chain_admission.source_id`; `:3872` [3832]:
   `source_workflow_run_id=_admitted_source_id`.
3. **`_launch_run_core` links the revision parent from that same parameter** (`:3033-3041` [3017-3025]):
   `_resolve_owned_parent_run_id(db, source_workflow_run_id, user.id) if pipeline_type.endswith("_revision") else None`. With `None`
   the resolver returns `None` without a query (`backend/app/api/run_engine.py:986-987`), so `WorkflowRun.parent_run_id` is NULL.
4. **The raw body id is passed down too**, as `request_source_workflow_run_id` (`:3886` [3846]; parameter `:2896`), but only the
   duplicate-context strip reads it (`:2982`). The parent link (`:3037`), `source_run_id` (`:3081`), the audit row (`:3092`) and
   the response flag (`:3251`) all read the admitted one.
5. **History (CONFIRMED from git).** `e7305f9dd` (2026-09-10, sandbox-git-versioning-v2) replaced
   `source_workflow_run_id=body.source_workflow_run_id,` with `source_workflow_run_id=_admitted_source_id,` and added
   `request_source_workflow_run_id` for the strip only (`git show e7305f9dd -- backend/app/api/run_commands.py`). The intent it
   broke is KAN-116 / [FIX-087](20260722-FIX-087.md) (the parent link is for `_revision` types only, so a chain stays out of
   the family) and the `LaunchCommand` docstring (`:2487-2488`), which calls the field "the (owner-checked) revision/chaining
   parent link". The same commit meant `source_run_id` to stay NULL for a gated launch (Requirement 6 AC 16, `:3835-3839`);
   nothing in it weighs the parent link. The test file's two parent-link tests were not touched then, and moved from
   `tests/unit/` to `tests/integration/api/` in `09270703b` (2026-09-22).

Consequences of a NULL parent (CONFIRMED by reading the engine; no live row shows them, see below):

- the run gets its own sandbox, not the family's: `_resolve_root_id(pipeline_run_id, owner_id)` returns the run's own id when
  `parent_run_id` is NULL (`backend/agents/execution_engine/engine.py:4392-4402`);
- for the types that declare `revises_existing` (`prototype_revision`, `prototype_large_revision`, `prototype_feature_revision`,
  `prototype_v2_revision`, `prototype_v2_feature_revision`, `backlog_revision`) the `previous_run` provider seeds nothing, because
  `ctx.parent_run_id` is None (`backend/agents/capabilities/context_providers/previous_run.py:267`); the other four
  (`user_stories_`, `app_builder_`, `ppt_`, `custom_revision`) do not use it, so for them only the family, sandbox and
  ordinal consequences apply;
- `revision_ordinal` keeps its default 1 (`engine.py:4630`, `if parent_run_id:`);
- the History family walk, keyed on `parent_run_id`, lists the run as a separate root.

**Who launches a revision this way:** the frontend, for user stories, prototype (v1) and app builder.
`frontend/src/components/layout/DashboardLayout.tsx:1229`, `:1249`, `:1261` and the History callbacks `:3067`, `:3077`, `:3087`,
`:3097` call `onStartPipeline("<x>_revision", ..., { source_workflow_run_id })`, with the comments "Revision Families (B1): link the
parent so the backend assembles the family" (`:1228`) and "history revisions previously sent NO parent -> orphan runs" (`:3065`).
That reaches `POST /api/runs` through `useWorkflow.ts:122` (`Object.assign(payload, context)`) and `RunConnectionProvider.tsx:496`.
These handlers are the active ones for those types (`DashboardLayout.tsx:2416`, `:2424`, `:2425`). prototype_v2, backlog, custom and
ppt (run screen) use `postRevision` -> `create_revision` -> `_mint_revision_row`, which writes the link itself (`:4742-4749`), so
they are not affected.

**Live data.** Read-only, against the dev Postgres: `SELECT type, COUNT(*) AS n, SUM(CASE WHEN parent_run_id IS NULL THEN 1 ELSE 0
END) AS parent_null, SUM(CASE WHEN source_run_id IS NULL THEN 1 ELSE 0 END) AS source_null, MIN(created_at), MAX(created_at) FROM
workflow_runs WHERE type LIKE '%\_revision' ESCAPE '\' GROUP BY type ORDER BY type` returned 19 rows: `backlog_revision` 7,
`prototype_large_revision` 1, `prototype_revision` 6, `prototype_v2_feature_revision` 3, `prototype_v2_revision` 2, every one with
`parent_null = 0` and `source_null = 0`. Both columns set is what `_mint_revision_row` writes (`:4742-4749`) and what the REST path
cannot produce at HEAD (its `source_run_id` stays NULL), and every row is dated 2026-09-28 or later, after `e7305f9dd`, so these
came from `_mint_revision_row` (INFERRED from that, not traced per row). No row looks like a REST launch (there is no
user_stories, ppt or app_builder revision at all), so the symptom is shown by the offline test and probe only, not by live data.

**Fix, and where it belongs.** One place: the parent resolution in `_launch_run_core` (`:3033-3041`). Resolve it from the raw
request id and fall back to the admitted one:

```python
_resolve_owned_parent_run_id(db, request_source_workflow_run_id or source_workflow_run_id, user.id)
```

Verified in-process (probe fix A): `test_owned_source_links_the_child` passes, and the launch file goes from 5 failed to 4
failed (the other four are B and C). It belongs in `_launch_run_core` because that is the join point for every launch and already
owns this resolution. Its two callers are `launch_run` (`:3863`) and `run_trigger_workflow`
(`backend/agents/execution_engine/kernel_services.py:1664`), which passes `parent_run_id_override=ectx.run_id` and no request id,
so it is unaffected.

Regression check of fix A on the other files that touch the source-id paths, one file at a time, identical with and without it:
`tests/agents/test_conditional_divert_v4_validation.py` 1 passed, `test_b3_saved_workflow_chain_launch.py` 8 passed,
`test_chain_context_v3.py` 1 failed and 14 passed (the failure is [ISS-987](20261002-0440-ISS-987.md), not this),
`test_duplicate_context_guard_api.py` 8 xfailed, `test_duplicate_context_guard_audit_api.py` 2 xfailed.

What a naive fix would break:

- Reverting `:3872` to `body.source_workflow_run_id` leaks a stray id into `source_run_id` (`:3081`) and `chain_source_run_id`
  (`:3238`) for every declaration-gated launch, against Requirement 6 AC 16.
- Dropping the `endswith("_revision")` guard puts chained runs into the source's revision family (KAN-116 / FIX-087).
- Adding a parameter to `_launch_run_core` fails `test_launch_run_core_is_plain_async_function_decoupled_from_fastapi`
  (`test_rest_run_launch_api.py:1044-1077` pins the exact parameter set). `request_source_workflow_run_id` is already in it.
- Bypassing `_resolve_owned_parent_run_id` drops the owner check, and a foreign parent link would leak another owner's run
  metadata through the family read (the resolver's own docstring, `run_engine.py:971-979`).
- SC-001 / INV-1: keep the generic suffix test; no workflow-name branch.

### B. Two stale tests: a foreign or unknown source on a chaining workflow (CONFIRMED)

`test_foreign_source_drops_the_link_but_still_launches` (`test_rest_run_launch_api.py:861-880`) and
`test_unknown_source_drops_the_link_but_still_launches` (`:883-896`) post `pipeline_type="user_stories"`, which declares
`chains_from: true` (`user_stories/workflow.yaml:35`). `admit_chain_launch` therefore reaches its owned-row fetch and answers
`404 {"detail":"Workflow run not found"}` (`run_commands.py:5323-5328`), which is the spec: "missing or cross-owner sources SHALL
return 404" (`.kiro/specs/sandbox-git-versioning-v2/requirements.md:570-572`, Requirement 6 AC 1). Observed: both answer 404 and
mint nothing (probe B1, B2). The tests encode the pre-v2 contract, "drop the link, never reject" (header comment `:795-807`, which
also cites `run_commands.py:1204`).

The tests bend to the app, and do not relax the 404. The old contract still holds, and is worth keeping, for a non-chaining
`_revision` pipeline: probes B3 and B4 (`user_stories_revision` plus a foreign or an unknown source) answer 200 with
`parent_run_id` None, at HEAD and with fix A. Re-point these two tests at `pipeline_type="user_stories_revision"`, so they
exercise the resolver for real once A lands, and add 404 cases for `user_stories` that assert no new `WorkflowRun`.

### C. Stale driver fixtures: no `agent_id` after `agent_start` (CONFIRMED)

`test_driver_persists_full_agent_history_like_ws` (`test_rest_run_launch_api.py:543`),
`test_driver_persists_model_id_and_prices_non_circular` (`:907`) and
`test_rest_revisions_api.py::test_driver_happy_path_persists_output_columns` (`:349`) raise `TypeError: the JSON object must be
str, bytes or bytearray, not NoneType`. `_apply_terminal_output_columns` (`run_commands.py:3919`) opens one row per
`(agent_id, task_id)` (`:3949-3981`) and appends a closed row only `if row.get("agent_id")` (`:4028`, `:4033`). The stubs send
`agent_id` on `agent_start` only. Their `agent_input`, `agent_thinking`, `tool_*`, `agent_chunk` and `agent_complete` events carry
none, so they land on a `(None, "")` row that is dropped, and `agent_outputs` and `token_usage` are never written.

The keying arrived in `77b52bb3d` (2026-09-29, "per-model pricing and the cache split in run usage"; `git log -S'open_agents'`).
The real engine puts `agent_id` on every one of those events (`engine.py:9955` agent_input, `:10192` agent_chunk, `:10205`
agent_thinking, `:10238` tool_call, `:10288` tool_result, `:10886` agent_complete), so the product is right and the stubs are
stale. That settles the question [ISS-900](20261001-2132-ISS-900.md) left open ("stale stub or collector regression"): stale stub.

Fix: add `"agent_id": "a1"` (the id on that test's `agent_start`) to the events after `agent_start`: launch file `:567-593` and
`:961-969`, revisions file `:373-384`. Probe fix C (events inherit the open agent_id): launch file 3 failed and 22 passed (A and
B remain), revisions file 25 passed. The revisions-file test belongs to QA-KB-073 / ISS-900 as well: fix it once, in whichever
bug's fix reaches it first, and do not have both edit it.
