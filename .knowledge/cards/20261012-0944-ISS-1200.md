# ISS-1200

**Register source:** sibling derived during the `QA-KB-121` analysis on 2026-10-12 (root [ISS-1199](20261012-0944-ISS-1199.md)). Not its own bug row.

**Confidence.** The mechanism is CONFIRMED by source read (every line below was opened). The user-visible effect is INFERRED: no run was started, because a launch costs
real money and the root card's evidence already settles what the later step says. What would settle it: one launch of a `planner: run` workflow with a key the provider rejects.

## Condition

- A workflow whose manifest declares `planner: run`: 14 of the 39 manifests under `backend/agents/workflows/` (`chat`, `custom`, `app_builder`, `prototype`, `ppt`, `ppt_v2`, `user_stories`,
  `dotnet_to_azure`, `mulesoft_to_springboot`, `reverse_engineer`, `sample_brownfield`, `sample_fanout`, `sample_wave`, `sc001-test-fixture`).
- 13 of those 14 declare `clarify.mode: auto` (always clarify); `sc001-test-fixture` is `disabled`.
- Provider is the Bedrock bearer-token rung (no `ANTHROPIC_API_KEY`, no `USE_LOCAL_OLLAMA`), and the provider rejects the key although the preflight passed it (the root card's case).

## What happens (mechanism CONFIRMED, effect INFERRED)

1. `engine.py:5448` runs the planner first. `SmartPlanner.plan` wraps its model call in `except Exception as exc: logger.warning("SmartPlanner failed: %s — using default context", exc); return self._default_context(...)`
   (`smart_planner.py:566-568`). The default context carries `"execution_gate": "CLARIFY_REQUIRED"` (`:581`) and `"planner_fallback": True` (`:590`).
2. Nothing reads `planner_fallback` (the only hit in `backend/` and `frontend/src/` is its definition). The engine logs `planner_complete` and emits the planner events as for a success
   (`engine.py:5557-5566`). The UI has a handler for a `planner_error` event (`useWorkflow.ts:1754-1757`, sets `plannerStatus: "error"`), but the backend never emits that event: the only
   `planner_error` in `backend/` is a dict key set in `_run_planner`'s own except branch (`engine.py:8283-8287`), which `SmartPlanner`'s swallow makes unreachable for a model error.
3. `clarify.mode: auto` forces the gate to CLARIFY_REQUIRED anyway (`engine.py:5478-5483`). The run transitions to `clarifying` and `waiting_for_user` (`engine.py:5570-5590`). The question
   generator `ClarifyEngine._generate_questions_via_llm` (`clarify_engine.py:423`) calls the model through `cached_invoke` inside `try: ... except Exception as exc: logger.warning("ClarifyEngine LLM generation failed: %s — falling back to static library", exc); return None`
   (`:654-659`), so the user is shown the STATIC question library.
4. Only after the user answers does the first agent step call the model, fail, and report the message that [ISS-1199](20261012-0944-ISS-1199.md) is about.

## Expected vs actual

Expected: a provider rejection of the key at the planner or clarify call is not hidden. Either the run ends there through the same funnel and message as an agent step, or at least a
visible warning (the `planner_error` frame the UI already handles) is emitted. Actual: both calls degrade silently, the key rejection exists only in two server log lines, and the user
spends a human round trip on a questionnaire built from canned defaults before the run fails.

## Why the root cause implies it

The owner's decision for [ISS-1199](20261012-0944-ISS-1199.md) moves the whole burden of reporting a revoked key onto "the first model call". For these workflows the first model calls are
the planner and the clarify generator, and both are written to degrade on ANY exception, so the improved message does not appear at the first call; it appears one human round trip later.

## Fix direction (INFERRED, not applied)

In `SmartPlanner.plan` and `_generate_questions_via_llm`, treat a credential-class provider rejection differently from a timeout or a parse failure: re-raise it (or return a flagged result) so the
engine ends the run through the existing funnel. The kernel already has the permanent-code predicate for this: `_PERMANENT_ERROR_CODES` in `backend/agents/model_policy.py:448-458` (a kernel-side
leaf, no new import direction). Every non-credential failure keeps today's fallback unchanged.

Traps: `_default_planning_context` says "DO NOT add keys: this dict is serialized verbatim into the planner event and the characterization normalizer does not recurse into it, so a new key
breaks INV-3" (`engine.py:8310-8311`); keep the goldens' timeout and parse fallbacks byte-identical. The owner asked for a small, dev-friendly change on [ISS-1199](20261012-0944-ISS-1199.md);
closing this as accepted for a dev-only key is a legitimate outcome and is the owner's call.

## Test notes

Offline: a scripted chat model whose `ainvoke` raises a `botocore.exceptions.ClientError` with code `AccessDeniedException`, passed as `SmartPlanner(model_id=...)._llm` (the instance path in
`cached_invoke` skips `build_model`). Today `plan()` returns the default context with `planner_fallback` True (the swallow). The clarify twin: the same exception through
`_generate_questions_via_llm` returns `None` today. A control with a timeout or malformed JSON must keep the fallback.
