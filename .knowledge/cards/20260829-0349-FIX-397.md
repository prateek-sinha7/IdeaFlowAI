## What was wrong

`frontend/next.config.ts:6-30` declares exactly 4 `redirects()` rules —
`/library/agents` -> `/library`, `/library/skills` -> `/library?tab=skills`,
`/library/hooks` -> `/library?tab=hooks`, `/settings` -> `/settings/profile`. Next.js
applies `redirects()` only to a full/document navigation. A client-side history transition
to the identical path (`pushState` + `popstate`, `router.push`, a same-origin `<Link>`)
never reaches the server, so it landed in the client parser directly, resolved to
`{ screen: 'unknown' }`, and `frontend/src/app/[...view]/page.tsx:3780-3782` rendered the
honest 404 with the URL frozen on the bare path. Same URL, two destinations, decided by how
it was reached — reproduced 3/3 for `/settings` (BUG-20260828-042311-settings), code-confirmed
for the three library paths.

## Root cause

`frontend/src/lib/routes.ts:401-403` (settings, ISS-339) and
`frontend/src/lib/routes.ts:392-399` (library legacy 2-segment shape, ISS-572) — neither
branch mirrored its `next.config.ts` rule, both fell through to the shared terminal
`return { screen: 'unknown' }`. Both carried an inline comment asserting the redirect made
the client case unreachable, which holds only for a cold load.

## What changed and why there

`frontend/src/lib/routes.ts` — `parseViewPath` is the single function every routing consumer
goes through (`[...view]/page.tsx:398`, `LibraryPage.tsx:489`, `error.tsx:24`,
`global-error.tsx:24`), so one mirror per branch fixes all four callers at once:

- `head === 'settings'`, `segments.length === 1` now returns `{ screen: 'settings-profile' }`.
- `head === 'library'`, `segments.length === 2` with `type` in `agents|skills|hooks` now
  returns `{ screen: 'library' }`.

Both destinations are screens the parser already produced for `/settings/profile` and
`/library`, so no consumer gains an unexercised code path — `initialSettingsSectionFor`
(`page.tsx:276`) maps `settings-profile` -> `"profile"` unchanged, and `librarySlug`
(`LibraryPage.tsx:490-495`) stays `null` for `{ screen: 'library' }` exactly as it did for
`unknown`. The stale comment at `routes.ts:388-390` stating the redirect intercepts the
library shape before the parser is removed with it.

`frontend/src/lib/routes.test.ts:309-318` — the two assertions that codified the disproved
premise (`/library/{type}` and bare `/settings` return `unknown`) now assert the mirrored
destinations. This is a card-sanctioned correction: [ISS-572](20260829-0019-ISS-572.md) names
both blocks as encoding an expectation its analysis disproved, and lists `routes.test.ts` in
its `applies_to.globs`.

## Residual, deliberately not fixed here

- The URL bar stays on the bare path after a client transition (the parser resolves the
  screen; it does not rewrite history). A cold load still canonicalises via `next.config.ts`.
- `/library/skills` and `/library/hooks` land on the library screen's default agents tab —
  the `?tab=` half of those two destinations is a query param, which `parseViewPath`
  structurally never sees (documented convention at `routes.ts:384-388`, shared with
  login/runHistory/analytics). Changing that would require a new field on `ParsedView`.

Neither is reachable from any in-app control today: `routes`' own builders emit
`/library` + query params and per-tab `settingsProfile()`/`settingsAiModel()`/etc., never a
bare `settings()` or a 2-segment library path (see
[ISS-572](20260829-0019-ISS-572.md)'s trigger note). Both paths are reachable only from an
external/historical link arriving as a client-side transition.
