## What was wrong

`PreviewPanel.tsx:~1593` (pre-change) mounted `AuditTab` with:

```tsx
<AuditTab
  hookRuns={pipelineState?.hookRuns}
  workflowRunId={effPipelineState?.pipelineRunId}
  isRunning={isStillRunning}
/>
```

`effPipelineState` resolves to `viewingVersion?.pipelineState ?? pipelineState` —
this was intended to carry the pinned run's id. However, `versionViewFrom` fills
`pipelineState.pipelineRunId` with `run.id` (the pinned member's id), making
`effPipelineState?.pipelineRunId` the right value **after** `versionViewFrom` is
called.

The bug: `AuditTab` uses `workflowRunId` to drive **four live fetches** on mount
(`getRunGateEvents`, `getRunValidationResults`, `getRunExecRuns`, `getRunHookRuns`)
— not just for rendering pre-fetched data as Steps/FilesTab do. The e2e test
(`test_audit_tab_fetches_the_pinned_versions_own_run_id`) reproduced the card's
mechanism exactly: Audit tab pinned to v2 fetched the ROOT run's gate-events
(`77f74563-...`) instead of the pinned revision's, because `pipelineRunId` on
`effPipelineState` was the live (root) run id.

The card was **reopened 2026-08-31** after a premature close: observed still
failing in the post-merge integration sweep at merge commit `90ec542a0`.

## Root cause

`activeRunId` at `PreviewPanel.tsx:646` is already the correct version-aware id:

```ts
const activeRunId = viewingVersion?.id ?? unpinnedRunId;
```

`FilesTab` uses `runId={activeRunId}` (line 1394). `SandboxTab` uses
`workspaceRunId` which resolves `viewingVersion?.id` first. `AuditTab` was the
one tab that instead read `effPipelineState?.pipelineRunId` — an indirection that
depended on `versionViewFrom` having populated `pipelineState.pipelineRunId` on the
override object, which proved not to hold in all re-render orderings.

## What changed and why there

One prop at `AuditTab`'s mount site in `PreviewPanel.tsx`:

```tsx
// Before
workflowRunId={effPipelineState?.pipelineRunId}

// After
workflowRunId={activeRunId ?? undefined}
```

`activeRunId` is `string | null`; `AuditTabProps.workflowRunId` is
`string | undefined`, hence `?? undefined` to satisfy TypeScript without widening
the type. The semantics are identical: when `activeRunId` is null (no run id yet),
`AuditTab` gets `undefined` and its own `if (!workflowRunId) return` guard skips
all fetches — the same short-circuit `effPipelineState?.pipelineRunId` triggered
when the pipeline state was absent.

No other file changed. The `pipelineRunId` field added to `versionViewFrom`'s
return in `PreviewPanel.tsx:499` (the prior attempt) is now unused for this
purpose but is harmless and left in place — it may still be consumed by other
callers.
