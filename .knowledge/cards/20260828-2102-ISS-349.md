## Root cause (CONFIRMED by source read, INFERRED as a live defect pending repro)

`frontend/src/lib/routes.ts:422-425`:

```ts
// Intentionally unreachable dead code: static app/admin/page.tsx takes precedence over [...view] catch-all for /admin path; kept for parseViewPath documentation.
if (head === 'admin') {
  return { screen: 'admin' };
}
```

The comment's "intentionally unreachable" claim holds only for the **exact** `/admin` path, where
`frontend/src/app/admin/page.tsx` (confirmed on disk: `admin/page.tsx`, no catch-all child under
`admin/`) wins over the root `[...view]` catch-all. It does NOT cover `/admin/<sub-path>` — Next's
App Router only lets a literal segment folder intercept its own exact path, and there is no
`app/admin/[...]/page.tsx`, so a deeper path has no more specific match and falls through to
`[...view]` exactly like `register` and `login` do. Once there, this branch has the same shape as
both: `head === 'admin'` alone, no `segments.length === 1` guard, so
`parseViewPath(['admin','anything'])` returns `{ screen: 'admin' }`.

Grepped `frontend/src/app/[...view]/page.tsx` for `screen === "admin"` / `'admin'` (both quote
styles) and the literal token anywhere in the file: **zero hits**, same as `register` and
`login`. `initialMainViewFor` (page.tsx:107-174) has no `case "admin":`, falls to `default:
return undefined;` (line 171-172) — the same `undefined` `initialMainView` prop that
`DashboardLayout.tsx:515-530`'s `useState<MainView>` initializer defaults to `"home"` for (no
`initialMainView`, no pending-wizard sessionStorage flag).

`routes.admin()` (`routes.ts:149`) only ever builds the bare `/admin` — no in-app navigation
constructs a deeper `/admin/*` path — so this is reachable only via a typed or shared URL, never
through the app's own UI, same as `register`/`login`.

## Expected vs actual

- **Expected:** an authenticated user hitting a nonexistent sub-path under `/admin` gets a
  404/not-found (the existing `screen === "unknown"` -> `notFound()` gate at page.tsx:3724), or an
  actual redirect.
- **Actual (INFERRED, not yet reproduced):** by the same mechanism ISS-238 confirmed 3/3 for
  `/register/<sub-path>`, `/admin/<sub-path>` should leave the address bar on the bogus URL while
  the dashboard silently renders underneath it. Whatever admin-role gate the real
  `app/admin/page.tsx` applies is irrelevant here — that component is never reached for a
  sub-path, so this is a routing defect independent of authorization.

## Why the root cause implies this

Same `parseViewPath` head-only-match-with-no-depth-guard shape ISS-238 documents for `register`,
confirmed by the identical zero-grep-hits result in page.tsx and the identical
`initialMainViewFor` default fallthrough into `DashboardLayout`'s "home" default. Filed
separately because it is a distinct URL prefix and a separately reproducible symptom.

## Analysis (QA-KB-013 analyzer, 2026-10-01)

**Verdict.** Root cause CONFIRMED. This card's meaning is unchanged, so this is an in-place update, not a
supersession; its "INFERRED" status above is closed by the validator's 3/3 browser reproduction and by the executed
parser check below. The shared-root note above is confirmed: one mechanism (a head-only `parseViewPath` branch with no
`segments.length === 1` guard, for a screen the catch-all never renders), two independent defects, so neither QA-KB-012
nor QA-KB-013 is a DUPLICATE. They differ in URL prefix and reporter symptom, in the branch (`login` at
`routes.ts:256`, `admin` at `routes.ts:480`), in their validated reproductions (`evidence/qa-kb-012/`,
`evidence/qa-kb-013/`) and in their root cards, and an admin-only guard leaves `parseViewPath(['login','x'])` returning
`{ screen: 'login' }`: fixing one does not fix the other.

### ROOT CAUSE (CONFIRMED, each link read at the cited line)

1. `frontend/src/lib/routes.ts:479-482`:

   ```ts
   // Intentionally unreachable dead code: static app/admin/page.tsx takes precedence over [...view] catch-all for /admin path; kept for parseViewPath documentation.
   if (head === 'admin') {
     return { screen: 'admin' };
   }
   ```

   No `segments.length === 1` conjunct, unlike `register` (`routes.ts:267`, FIX-344) and `analytics` (`routes.ts:475`,
   FIX-462). The comment is true only for the exact path: `app/admin/` holds `page.tsx` and two test files, no catch-all
   child, so `/admin/<sub-path>` has no static match and reaches `[...view]`.
2. `[...view]/page.tsx:424-426` derives the segments from `usePathname()` and calls `parseViewPath`, which returns
   `{ screen: 'admin' }`. Nothing consumes that screen (grep below), `initialMainViewFor` has no `admin` case and ends
   `default: return undefined` (`page.tsx:197-198`), and the one hard-404 gate keyed on the parser,
   `screen === "unknown"` -> `notFound()` (`page.tsx:4044-4046`), is never reached.
3. `DashboardLayout.tsx:568-584`: `initialMainView` is undefined and no pending-wizard flag is set, so the
   `useState<MainView>` initializer returns `"home"` (`:583`). Nothing rewrites the URL, so Home renders under
   `/admin/<sub-path>`.

Executed against the current `routes.ts` (`cd frontend && node --experimental-strip-types --input-type=module -e
"import('./src/lib/routes.ts').then(m => console.log(JSON.stringify(m.parseViewPath(['admin','nonexistent']))))"`):

| input | result |
|---|---|
| `['admin']` | `{"screen":"admin"}` (exact path: correct, and must stay) |
| `['admin','nonexistent']`, `['admin','foo','bar']`, `['admin','zzz']` (the validator's three URLs) | `{"screen":"admin"}` (the bug) |
| `['register','anything']`, `['analytics','anything']` (controls) | `{"screen":"unknown"}` |

No authorization angle: the view painted is the ordinary signed-in Home, not the admin console. `app/admin/page.tsx`
(and its `is_admin` gate) never mounts for a sub-path. Signed-out visitors never get that far: the mount effect sends a
token-less user to the login redirect (`page.tsx:922-927`), as it does for `/register/<sub-path>`.

### BLAST RADIUS (grep of `backend/` and `frontend/src/`)

- Callers of `parseViewPath`: `[...view]/page.tsx:426` (the only render consumer), `error.tsx:24` and
  `global-error.tsx:24` (`screenLabel(...)`, telemetry only; after the fix `/admin/<sub-path>` is labelled `unknown`,
  which is accurate), `LibraryPage.tsx:465` (library-scoped, unaffected). Tests: `routes.test.ts`,
  `routes.iss339.test.ts`. Nothing in `backend/`.
- Consumers of `{ screen: 'admin' }`: none. `grep -rn "screen === ['\"]admin['\"]\|screen: ['\"]admin['\"]\|case ['\"]admin['\"]"
  frontend/src` finds only the type member (`routes.ts:237`), the branch (`routes.ts:481`) and the round-trip test
  (`routes.test.ts:308`). The guard has no runtime consumer to break.
- Builders of `/admin*`: `routes.admin()` (`routes.ts:181`) has no caller and `AppHeader.tsx:611` pushes the literal
  `/admin`. Nothing in the app constructs `/admin/<sub-path>`, so it is reachable only through a typed, shared or
  bookmarked URL. Severity read: a cosmetic URL/content mismatch with no data exposure (BUG-056, the `register`
  analogue, was rated Medium; the ledger has High).
- Exact `/admin` is served by the static `app/admin/page.tsx` and does not pass through the catch-all at runtime; the
  guard keeps `['admin']` -> `{ screen: 'admin' }` (round trip at `routes.test.ts:308`, and the telemetry label for a
  crash on `/admin`).

### FIX: where it belongs, and the agreed minimal fix is ACCEPTED

`parseViewPath` is the single function every consumer routes through, so the guard belongs there and nowhere else (same
site as FIX-344 / FIX-462; one conjunct in the shared function is a smaller diff than a guard in each caller):

```ts
// ISS-349: exact /admin is served by the static app/admin/page.tsx, so only /admin/<sub-path>
// reaches this parser (via [...view]). Without the guard it resolved to { screen: 'admin' }, which
// nothing renders, and fell through to the default dashboard instead of `unknown` -> notFound().
if (head === 'admin' && segments.length === 1) {
  return { screen: 'admin' };
}
```

Replace the stale "Intentionally unreachable dead code" comment at `routes.ts:479` rather than leaving it above the guarded
branch. Considered and rejected: deleting the branch (breaks the `routes.test.ts:308` round trip and the telemetry
label); an explicit `admin` case or guard in `page.tsx` / `DashboardLayout` (per-caller, leaves the telemetry label
wrong); a central "no render path -> 404" rule in `page.tsx` (not every `initialMainViewFor` `undefined` is unrenderable:
the wizard and workflow screens render through earlier standalone branches, `page.tsx:4077-4102`). No overrule of the
BUGS.md note.
