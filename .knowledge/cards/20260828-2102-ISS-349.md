## Root cause (CONFIRMED by source read, INFERRED as a live defect pending repro)

`frontend/src/lib/routes.ts:422-425`:

```ts
// Intentionally unreachable dead code: static app/admin/page.tsx takes precedence over [...view] catch-all for /admin path; kept for parseViewPath documentation.
if (head === 'admin') {
  return { screen: 'admin' };
}
```

The comment's "intentionally unreachable" claim holds only for the **exact** `/admin` path, where
`frontend/src/app/admin/page.tsx` (confirmed on disk: `admin/page.tsx`, no catch-all child under
`admin/`) wins over the root `[...view]` catch-all. It does NOT cover `/admin/<sub-path>` — Next's
App Router only lets a literal segment folder intercept its own exact path, and there is no
`app/admin/[...]/page.tsx`, so a deeper path has no more specific match and falls through to
`[...view]` exactly like `register` and `login` do. Once there, this branch has the same shape as
both: `head === 'admin'` alone, no `segments.length === 1` guard, so
`parseViewPath(['admin','anything'])` returns `{ screen: 'admin' }`.

Grepped `frontend/src/app/[...view]/page.tsx` for `screen === "admin"` / `'admin'` (both quote
styles) and the literal token anywhere in the file: **zero hits**, same as `register` and
`login`. `initialMainViewFor` (page.tsx:107-174) has no `case "admin":`, falls to `default:
return undefined;` (line 171-172) — the same `undefined` `initialMainView` prop that
`DashboardLayout.tsx:515-530`'s `useState<MainView>` initializer defaults to `"home"` for (no
`initialMainView`, no pending-wizard sessionStorage flag).

`routes.admin()` (`routes.ts:149`) only ever builds the bare `/admin` — no in-app navigation
constructs a deeper `/admin/*` path — so this is reachable only via a typed or shared URL, never
through the app's own UI, same as `register`/`login`.

## Expected vs actual

- **Expected:** an authenticated user hitting a nonexistent sub-path under `/admin` gets a
  404/not-found (the existing `screen === "unknown"` -> `notFound()` gate at page.tsx:3724), or an
  actual redirect.
- **Actual (INFERRED, not yet reproduced):** by the same mechanism ISS-238 confirmed 3/3 for
  `/register/<sub-path>`, `/admin/<sub-path>` should leave the address bar on the bogus URL while
  the dashboard silently renders underneath it. Whatever admin-role gate the real
  `app/admin/page.tsx` applies is irrelevant here — that component is never reached for a
  sub-path, so this is a routing defect independent of authorization.

## Why the root cause implies this

Same `parseViewPath` head-only-match-with-no-depth-guard shape ISS-238 documents for `register`,
confirmed by the identical zero-grep-hits result in page.tsx and the identical
`initialMainViewFor` default fallthrough into `DashboardLayout`'s "home" default. Filed
separately because it is a distinct URL prefix and a separately reproducible symptom.
