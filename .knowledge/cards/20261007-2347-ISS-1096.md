# ISS-1096

Sibling of [ISS-1073](20261007-2135-ISS-1073.md) (QA-KB-096), filed by its analysis on 2026-10-07. **INFERRED.** The mechanism is read in source and the
two byte counts below are real (`evidence/qa-kb-096/11`, `12`). It is not reproduced, because a share is a state change (`POST`) and the analysis was
read-only. An unreproduced sibling is a lead, not a defect.

## Condition

A public share link (`POST /api/runs/{id}/share`, then `GET /s/{token}`, no auth) for a member of a family whose deliverable is a binary, other than the
newest member. Real data: family `78e185fb-c032-4154-8552-774781b6e5df`. The live root `Backlog.pdf` is 23,626,760 B (v8's). v2's own copy is
`.chain/Backlog.pdf` at tag v2, 23,010,668 B.

## Why the root cause implies it

[ISS-1073](20261007-2135-ISS-1073.md): the declared name is a gitignored ROOT file that every final assembly rewrites (`backlog_export.py:583-593`), so it only
ever holds the NEWEST member's bytes, and any reader that takes it without a ref gets those bytes. The share route is the server-side reader of that path.
It was added by [FIX-664](20260930-1723-FIX-664.md) the same day as the PDF preview, before any ref existed.

## Mechanism (read)

- `get_shared_run_by_token` returns the shared run row (`runs.py:2323-2352`).
- `view_shared_run` takes `run.deliverable_filename` and, for a binary mimetype, reads
  `RunSandbox(run.user_id, root_id, runs_root=settings.RUNS_ROOT).path_for(run.deliverable_filename).read_bytes()` (`main.py:678-690`): the working-tree file in the
  FAMILY ROOT's directory.
- There is no ref, no `.chain/` candidate and no tag. The row carries its own tag (`models/workflow.py:172`, `git_tag`) and it is not consulted.
- The read happens at serve time. A link minted while v2 was the newest changes under the recipient: it serves v3's bytes once v3 completes.
- For the newest member, or a single-member family, the read is right. `backend/tests/unit/app/test_binary_deliverable.py:128`
  (`test_share_of_a_pdf_deliverable_serves_the_file_bytes`) covers only that case.

## Expected vs actual

Expected: a share link serves the member it was minted for.
Actual (INFERRED): the newest member's PDF, under the older member's link.

## Fix direction

In `view_shared_run`, read at the run's own tag when the row has one (`RunSandbox.read_file_at_ref`), with the same candidate order as the frontend resolver
(root, then `.chain/<name>`; `api.ts:1643-1645`), and read the live file only for a run with no tag. A tag that is no longer in the sandbox answers 404, as the
other routes do for an expired workspace. Keep `share_headers` unchanged. Do not make `/sandbox/file` alias `.chain/`.

## What would settle it

As admin: `POST /api/runs/80054fbc-71cc-42de-adeb-ae2db82eb2f2/share`, `GET /s/<token>`, and compare its size with
`GET /api/runs/80054fbc-71cc-42de-adeb-ae2db82eb2f2/sandbox/file?path=.chain/Backlog.pdf&ref=v2` (23,010,668 B) against the ref-less read (23,626,760 B).
Test seam: the share test in `test_binary_deliverable.py`, with a two-member family and a tag on the older run.
