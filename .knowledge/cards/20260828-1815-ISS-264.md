## What is suspected

[ISS-224](20260828-1735-ISS-224.md) root-caused the GitHub-PAT case to a compound of two defects:
a backend 422 that echoes the full rejected value, and a frontend helper (`authedJson`) that
falls back to dumping the whole raw JSON body on-page when `detail` isn't a plain string. That
frontend helper is not PAT-specific — it is `IntegrationsCard`'s **shared** error path for every
form on `/handoff/settings`, including "Create API key". This card is that same mechanism,
reached through a different field, predicted but **not yet reproduced** in the browser.

## Root cause — the identical `authedJson` call chain, a second caller

**Confirmed by reading the full call chain, file:line:**

1. `frontend/src/components/handoff/IntegrationsCard.tsx:147` — `handleCreateKey` calls
   `createApiKey(token, keyName || "Default")`.
2. `frontend/src/lib/api-handoff.ts:151-156` — `createApiKey` calls the shared `authedJson`,
   whose fallback (`api-handoff.ts:86-88`, the exact code ISS-224 names as the frontend root
   cause) is:
   ```ts
   const message =
     typeof body?.detail === "string" ? body.detail : JSON.stringify(body);
   ```
3. `IntegrationsCard.tsx:151-155` — `handleCreateKey`'s catch block:
   `setKeyMessage({ type: "error", text: err instanceof Error ? err.message : "Failed to create key" })`.
4. `IntegrationsCard.tsx:390-393` — `{keyMessage && (<div>...{keyMessage.text}</div>)}` renders
   it raw and unparsed — the same sink as `patMessage.text` at `:295`, which ISS-224's evidence
   already screenshotted rendering raw JSON.

Backend side: `ApiKeyCreateRequest.name` (`backend/app/api/settings.py:76`) is
`Field(default="Default", min_length=1, max_length=64)`. The `keyName` `<input>`
(`IntegrationsCard.tsx:376`) carries no `maxLength` attribute — confirmed absent by reading the
whole file, the same gap ISS-224 found on the PAT input.

**Not yet confirmed:** no browser action was taken in this pass; the 422 was not actually
triggered. `ApiKeyCreateRequest.name` is a label, not a credential, so unlike ISS-224's PAT this
sibling is not itself a secret leak — its value is proving the frontend half of the defect is a
property of the shared helper and its render sink, not of the PAT field specifically.

## Why the root cause implies this

`authedJson`'s bug is "only a plain-string `detail` gets a friendly message; every FastAPI 422
sends a list, so everything else falls through to `JSON.stringify(body)`." `createApiKey` is
just another caller of that same function with its own length-validated field. No new
hypothesis is needed — the same fallback and the same raw-render sink apply mechanically to any
`authedJson` caller with a rejectable field, and `createApiKey` is one.

## Expected vs actual (once reproduced)

- **Expected:** a >64-character key name is rejected with a friendly, generic message ("Name is
  too long (max 64 characters)"), the same way the PAT field's 400 case is already handled.
- **Actual (predicted):** the raw `{"detail":[{"type":"string_too_long",...}]}` body renders as
  plain page text under the API-keys section, mirroring ISS-224's PAT screenshot.

## What would confirm or refute this

On `/handoff/settings`, type a 65+ character string into the "Create API key" Name field and
click "Create key"; read the `POST /api/settings/api-keys` response body and the page snapshot
the same way ISS-224's reproduction did for the PAT field.
