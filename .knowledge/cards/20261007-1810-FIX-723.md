# FIX-723

## What was wrong

This fix is for bug report QA-KB-062. The root cause is the 2026-10-02 analysis on
[ISS-347](20260828-2058-ISS-347.md), with its siblings [ISS-1000](20261002-0500-ISS-1000.md) and
[ISS-1002](20261002-0500-ISS-1002.md). It was not re-derived here. Every cited line was re-read on HEAD `0b5223f4c`
(`LaunchWizard.tsx` blob `3353604b7`) before editing, and the card held. The four traps in its "Where the fix belongs"
section shaped the change.

`LaunchWizard` treats the `chain.*` sessionStorage keys as ambient state. Nothing ties them to the navigation that wrote
them. Two effects consumed them independently:

- **Pickup** (HEAD `LaunchWizard.tsx:391-414`). On every mount it read `chain.from`, which arms `isChaining`: the brief
  editor is hidden, the "Continuing from your ..." banner shows, and `handleLaunch` sends `chain.source_run_id`. It also
  read `chain.v2.source_status`.
- **Restore** (HEAD `:422-477`). It applied `chain.brief` and `return`ed (`:425-431`) before it ever read
  `ppt.draft` / `prototype.draft`.

So a leftover hand-off beat the draft that `handleEditBrief`, `handleLaunchSaved` or the cold `/workflows/{id}/run`
effect had just staged. The staged draft was never applied, never cleared, and the stale source id launched. That is
ISS-347 and ISS-1000 (cases R1, R2).

Separately, `canContinue` blocked on `chainSourceStatus` alone (HEAD `:935`), but the acknowledgement checkbox only
renders under `chainFrom && chainSourceStatus` (HEAD `:1216`). A stranded `chain.v2.source_status` therefore left
Continue disabled with nothing to click. That is ISS-1002 (case R3).

## What changed, and why there

Everything is in `frontend/src/components/workflow/LaunchWizard.tsx`, the single reader. The writers are unchanged, as
ISS-347's Disposition says. Line numbers are as of this fix.

1. `:86` adds `draftKeyFor(mode)`, the `STEPPER_MODE` ternary the restore effect already used. The restore effect now
   calls it too (`:444`), so the two effects cannot disagree on the draft key.
2. `:403-410`, in the pickup effect, before the `chain.from` read: if `sessionStorage.getItem(draftKeyFor(initialMode))
   !== null`, remove `chain.from`, `chain.brief`, `CHAIN_SOURCE_RUN_ID_KEY` and `CHAIN_SOURCE_STATUS_KEY`. Placing it
   here, not in the restore effect, is trap 1: the restore effect runs after `setChainFrom` and cannot disarm it. The
   removal does not depend on the key's value, so an empty `chain.brief` goes too (trap 2). Deleting the keys is what
   makes the restore effect's `libraryAgents` re-run see the same inputs (trap 3, R5). The effect's deps gain
   `initialMode` (`:425`), which it now reads.
3. `:438`: the restore effect's `if (chainBrief)` becomes `if (chainBrief !== null)`. On a genuine chain, an empty
   `chain.brief` is now consumed with the rest of the hand-off instead of lingering for the next open (trap 2). With no
   draft present, the `return` skips nothing.
4. `:948` adds `showSourceWarning = chainFrom !== null && chainSourceStatus !== null`. It is used by `canContinue`
   (`:952`, deps `:959`) and by the warning JSX (`:1233`, which was `chainFrom && chainSourceStatus`). This is
   ISS-1002's "reader first" fix: a gate and its remedy now share one condition. Both setters store only truthy
   strings, so `!== null` reads the same as the old truthiness check, and it also narrows `chainFrom` for
   `CHAIN_SOURCE_LABEL[chainFrom]` (tsc is clean).

Constraints kept:

- [FIX-331](20260828-2056-FIX-331.md)'s seeded-brief constraint: the "Edit brief" draft now wins.
- The [FIX-005](20260616-FIX-005.md) one-shot draft: the restore and its clear are unchanged.
- The [BUG-014-GROUNDED-CONTEXT](20260716-2156-BUG-014-GROUNDED-CONTEXT.md) guard: `sourceRunId` is still read only
  when `isChaining`.
