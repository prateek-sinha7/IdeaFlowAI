# ISS-1153

**Register source:** `QA-KB-109` (validate stage, 2026-10-09).

## Reproduction (3/3, cold)
Signed in as admin@velocity.ai (admin, enterprise), lane2, real Chrome. Each attempt: `about:blank`, then fresh `goto http://localhost:3000/admin`, wait for the users table.
Every attempt (cycles 1, 2, 3) listed `Delete admin@velocity.ai`, `Delete enterprise@velocity.ai`, `Delete pro@velocity.ai`, `Delete basic@velocity.ai`. The own row (admin@velocity.ai) carries a Delete button.

Route note: the users table lives at `/admin`; `/admin/users` returns 200 and is the same surface.

## Expected vs actual
Expected (velocity.json `selfGuard`): the signed-in admin's own row has NO delete control.
Actual: the control renders and opens the delete confirm. The server refuses with 400 (self-delete guard, see FIX-310), so the defect is UI-only: a dead-end control.

## Cause
`frontend/src/app/admin/page.tsx:611-620` renders the Delete button unconditionally for every row:
`onClick={() => setDeleteConfirm({ id: user.id, email: user.email })} aria-label={`Delete ${user.email}`}`.
Commit b2a621f84 (Cognito sole-auth) removed `const [currentUserId, ...]` and the `disabled={user.id === currentUserId && user.is_admin}` guard on the role button; nothing replaced it. `getMe(token)` is still called at page.tsx:222, so the current user is available.

## Conditions
No tier, theme or timing dependence observed; present on every load.

### Root cause (one mechanism)

The page never keeps the signed-in admin's id, so its row renderer cannot tell the own row from any other.

1. `getMe(token)` is called at `page.tsx:222`. Its callback uses the result for the gate (`:223`) and then calls `loadUsers(token)` (`:224`); `user.id` is dropped and there is no state to hold it. Before `b2a621f84` there was: `const [currentUserId, setCurrentUserId] = useState<string | null>(null)` (pre-image line 122), set by `setCurrentUserId(user.id)` (pre-image line 178).
2. The row map (`page.tsx:512-623`) has no self branch. Every per-row control is rendered from `user` alone: tier dropdown `:540-544`, role pill `:550-564` (its only condition is `disabled={rolePending.includes(user.id)}`), Reset password `:584-591`, Disable/Enable `:592-610`, Delete `:611-618`.
3. What `b2a621f84` ("Fix/cognito login (#8)", 2026-09-17, Cognito Phase 5, unit tests tagged T14) removed, read from `git show b2a621f84^:frontend/src/app/admin/page.tsx`:
   - the `currentUserId` state, its setter call and the role pill's `disabled={user.id === currentUserId && user.is_admin}` plus its title "You cannot remove your own admin access" (pre-image lines 122, 178, 422-427). That was the ONLY use of `currentUserId`.
   - the `{!user.is_admin && (` wrapper around the Delete button (pre-image line 449): a coarser rule, no Delete on ANY admin row, which is what kept the own row Delete-free. The same commit rebuilt the Actions cell as an unconditional group and added Reset password and Disable/Enable to it with no guard.
   Delete's guard therefore never depended on `currentUserId`; see Corrections.
4. On the server the refusal is the only guard left: `admin.py:301-305` (tier), `:365-369` (role demote), `:566-570` (disable) and `:686-690` (delete) answer 400 for the admin's own id. `reset_user_password` (`:501-546`) has no such check ([ISS-1170](20261009-1621-ISS-1170.md)).
5. `getMe().id` and the list's `id` are the same value: `/api/auth/me` returns `id=user.id` (`backend/app/api/auth.py:688-702`), the list returns `id=u.id` (`admin.py:259-267`), and `User.id` is typed on the frontend (`frontend/src/types/index.ts:36-41`). The e2e helper relies on the same equality (`test_admin.py:131-141`).

### Blast radius

- Frontend: `AdminPage` is the only consumer. `git grep` over `frontend/src`: `adminListUsers`, `adminUpdateTier`, `adminUpdateRole`, `adminResetUserPassword`, `adminCreateUser`, `adminDeleteUser`, `adminDisableUser` and `adminEnableUser` are defined at `lib/api.ts:2032-2165` and called only from `admin/page.tsx`. The second client, `store/api/admin.ts`, is aggregated in `store/api/api.ts:23,41,60` and nothing calls it. Nothing else lists users, so no other screen shows an own row.
- Backend: all of `admin.py` (list, tier, role, create, reset, disable, enable, delete). Tier, role, disable and delete refuse self; reset does not.
- Specs and tests that name the contract: `tests/integration/screens/11-admin.feature.md:44-46,117-123`, `velocity.json:604`, `test_admin.py:113-128` (S-11-04, needs the own Delete ABSENT), `tests/integration/e2e/suites/19_toasts_and_dialogs/test_toasts_and_dialogs.py:337-356` (S-19-14, accepts absent or disabled), the T14 unit tests (`admin.actions.test.tsx:169-185`, `admin.reskin.test.tsx:224-231`) and [FIX-310](20260826-0124-FIX-310.md).
- Not affected: the other callers of `getMe` (`[...view]/page.tsx`, AccountSettings, LaunchWizard). The fix reads a value the page already fetches.

### Where the fix belongs

One file for the root: `frontend/src/app/admin/page.tsx`, the single row render. Keep the id from the `getMe` call the page already makes (no new fetch: `getMe` is a shared-GET cache, `lib/api.ts:950-955`), set it in the same `.then` before `loadUsers(token)` so no row renders without it, compute `const isSelf = user.id === currentUserId` once per row, then:

- Delete, Disable and Reset password are not rendered on the own row (the spec wants Delete absent, count 0);
- the role pill is disabled when the row is the admin's own and an admin, with its former title;
- the tier trigger is disabled (a `disabled` prop on `TierDropdown`).

The reference change, 13 changed lines marked `[QA-KB-109]` (plus a header comment and a probe sentinel that a real fix would not carry), is `evidence/qa-kb-109/analysis-plugins/page.reference-fix.tsx`. It is a copy and was never applied. Against it the contract tests pass, the controls stay green, and the repo's own 16 admin tests pass unchanged (`analysis-03`, `analysis-04`).

Alternative considered and not recommended: have the server flag the own row in `AdminUserResponse`. It would change an API contract and add a backend change for a value the client holds already. Rule rejected: hiding by `is_admin`, the pre-`b2a621f84` rule. It contradicts T14 and removes controls on other admins that an admin may legitimately use, with last-admin left to the server.

### Traps for the fixer

- Own row only. Another admin's row keeps every control (`[P7]`). With `currentUserId === null`, or a `getMe()` carrying no `id` as in the T14 mocks, nothing counts as the own row (`[P8]`), so the existing tests need no edit.
- Do not add a second `/api/auth/me` call; the page's duplicate-fetch history is why `getMe` and `adminListUsers` are cached and single-flighted.
- Keep the accessible names: the e2e locators and the unit tests query `Delete <email>`, `Disable <email>`, `Reset password for <email>` and `Remove admin access from <email>`.
- Hiding Delete alone fixes this card and leaves [ISS-1168](20261009-1621-ISS-1168.md) and [ISS-1170](20261009-1621-ISS-1170.md) open. The server guard in [ISS-1170](20261009-1621-ISS-1170.md) is a separate backend change.
- `velocity.json` `admin.columns` still lists six columns and no STATUS (stale since `b2a621f84`); that is the test harness's descriptor, not part of this fix.

### Operational warning for the line

Until [ISS-1170](20261009-1621-ISS-1170.md) is fixed, no browser lane may click the Key (Reset password) on `admin@velocity.ai`'s own row, and none may call that endpoint with the admin's own id: it is accepted and revokes the shared admin's session. The own-row Delete, Disable, role and tier controls are harmless to click (400), only pointless.

### Corrections to the earlier text of this card

- "removed `const [currentUserId, ...]` and the `disabled=...` guard on the role button; nothing replaced it" is right for the role pill, but `currentUserId` never guarded Delete. - The Delete button spans `page.tsx:611-618` at HEAD; the card's `611-620` is within two lines.

## Resolution
