# FIX-703

## What was wrong

This is bug report QA-KB-016. The root cause, blast radius and agreed fix, with its three amendments, are the
analysis on [ISS-378](20260828-2006-ISS-378.md). The writer defect is [ISS-912](20261001-2218-ISS-912.md). This card
does not re-derive either.

In short, `ConfigLeversFlat` backs the Config tab of `AgentCapabilitiesModal`, which is the `/library` agent drawer and
the Add-agent picker. It rendered Model, Effort, Validator, the Before/After-execute gates and Retry, and nothing for
`StepSelection.tools`. [FIX-350](20260828-2340-FIX-350.md) gave the Simple-view expander the shared grant rows and
named this surface as still open.

Separately, both existing grant writers built a new two-key object, `{ ...effectiveToolGrants(sel), [key]: on }`.
These were the rail (`CanvasConfigRail.tsx:925` before this change) and AdvancedExpander (`AgentsPopup.tsx:2139`
before). `applyLeverPatch` replaces `tools` whole, so the first grant toggle dropped the step's `tool_sets` packs.

## What changed, and why there

All changes are in the frontend. No backend, manifest or persistence code changed.

1. `frontend/src/components/workflow/AgentsPopup.tsx:1538-1548` adds the exported `withToolGrant(sel, key, on)`
   next to `effectiveToolGrants`. It returns `{ ...sel?.tools, ...effectiveToolGrants(sel), [key]: on }`: the step's
   other keys (`tool_sets`) are spread first and survive, and the grants still win. This is the one writer that
   ISS-912 asked for, and the "Preferred" form of ISS-378's amendment 1. It goes here because every grant control
   already imports its reader, `effectiveToolGrants`, from this spot.
2. Same file, `ConfigLeversFlat`:
   - `:1904` adds `const grants = effectiveToolGrants(sel);`.
   - `:2001-2032` adds the "Tool grants" group after the Retry row. It maps `TOOL_GRANT_LEVERS` to checkbox rows with
     `aria-label={`${label} for ${agentName}`}`, the same name AdvancedExpander uses, and `title={desc}`. Each row
     writes `updateLever({ tools: withToolGrant(sel, key, checked) })`. The group ends with the disabled, unchecked
     "Execute commands" row, titled "Not available to custom workflows.".
   - Amendment 2: the markup is this component's own gate-row pattern, a wrapping `<label>` under a small uppercase
     group title. So there is no `region` id prefix and no duplicate-id risk.
3. Same file, `:773-774`: the Config-tab comment now lists "Model · Effort · Validator · Gate · Retry · Tool grants"
   (amendment 3).
4. Same file, `:2184`, AdvancedExpander: the grant checkbox writes `withToolGrant(sel, key, e.target.checked)`
   (ISS-912).
5. `frontend/src/components/workflow/composer/CanvasConfigRail.tsx:29` imports `withToolGrant`. `:926`: the Tools-tab
   grant toggle writes `withToolGrant(sel, key, !toolGrants[key])` (ISS-912). The rail's markup and its
   `toggleToolPack` are unchanged, because `toggleToolPack` already spreads the grants.

Why one writer and not three guards: grep `tools: {` over `frontend/src` (non-test) finds exactly three writers of
`tools`. These are the two grant toggles above and the rail's `toggleToolPack`, which already preserves the grants.
All grant writes now go through the one function, so a fourth surface cannot reintroduce the drop.

`ConfigLeversFlat` has a single call site, `AgentsPopup.tsx:788` in `AgentCapabilitiesModal`. Both mounts of that
modal therefore pick up the change with no caller edits: `LibraryPage.tsx` (the drawer and `/library/agents/<slug>`)
and `AgentLibrary.tsx` (the Add-agent picker). Reset remounts the component through `resetKey`, so the new rows reset
with the other levers. Save agent forwards `localSelections`, so the grants go with it. Durability is unchanged, and
it is exactly as non-durable as the other levers on this surface: [ISS-392](20260828-2250-ISS-392.md) and
[ISS-393](20260828-2251-ISS-393.md).
