## Why this must also be broken

[ISS-225](20260828-1541-ISS-225.md) traced the root cause to
`frontend/src/components/workflow/IdeaInputPage.tsx`: `selectionsRef` (line 936) is seeded ONLY
from `cleanSelections` and mutated only by explicit user edits (`handleSelectionsChange`,
lines 937-942) or the override-toggle path (lines 1428-1440). It is never assigned from
`manifestSelections` — the per-step `gates` the manifest-fetch `useEffect` derives from the
opened workflow's own raw steps (built at lines 1098-1105, merged only into the DISPLAY-only
`mergedInitialSelections` at lines 1190-1196, and passed only as `initialSelections` to the
`AgentsPopup` canvas at line 1917).

`handleSaveAsOverride` (line 1460-1478) unconditionally builds the save manifest as
`buildWorkflowManifest(pipelineAgents, undefined, selectionsRef.current)` — `pipelineAgents`
carries `route:` (correctly sourced from the manifest), but `selectionsRef.current` carries no
`gates` for any step the user has not touched. The backend's R-03 cross-field check
(`backend/agents/workflows/compiler.py:967-971`) then rejects any step with `route:` but
without `gates: [conditional]`.

This mechanism has nothing to do with `ex_A4_human_divert` specifically — it fires for ANY
workflow opened through this same page/button whose OWN manifest declares `route:` on a step,
since the bug is that `selectionsRef` never learns about a manifest's declared gates at all,
regardless of which built-in is open. Four other shipped example workflows declare `route:` in
their own `workflow.yaml` (confirmed via `grep -rl "route:" backend/agents/workflows/*/workflow.yaml`):

- `backend/agents/workflows/ex_A1_loop/workflow.yaml`
- `backend/agents/workflows/ex_A2_branch/workflow.yaml`
- `backend/agents/workflows/ex_A3_divert/workflow.yaml`
- `backend/agents/workflows/ex_A4_human_gate/workflow.yaml`

Each is reachable at `/create/<id>` through the identical `IdeaInputPage.tsx` shell (confirmed:
`effectiveType !== "custom" && workflowId` at line 1661 renders the same "Save as my version"
button for any non-custom `workflowId`), and each necessarily satisfies R-03 in its OWN source
manifest (a manifest declaring `route:` without `gates: [conditional]` could not compile at all,
so it could never have shipped). Clicking "Save as my version" unmodified on any of the four
should therefore 422 with the identical R-03 message, just naming a different step/workflow id.

## Expected vs actual

**Expected:** an unmodified seeded example whose own manifest already satisfies R-03 saves
successfully, on any of the five `ex_A*` conditional-gate examples alike.

**Actual (INFERRED — not yet independently reproduced per example):** the same 422 ISS-225
documented for `ex_A4_human_divert` should reproduce on `ex_A1_loop`, `ex_A2_branch`,
`ex_A3_divert` and `ex_A4_human_gate` — the broken code path is shared, not per-workflow.

## What would confirm or refute this

Repeat ISS-225's exact reproduction (`bug-hunter/ledger.md` `BUG-20260828-051530-create`, steps
1-3) against `/create/ex_A1_loop`, `/create/ex_A2_branch`, `/create/ex_A3_divert` and
`/create/ex_A4_human_gate` in turn: sign in, type a brief, leave Advanced untouched, click
"Save as my version", and confirm each 422s with an R-03 message naming that workflow's own
routed step. A miss on any of the four (a 201 instead) would mean that example's manifest
differs from `ex_A4_human_divert`'s shape in a way not yet accounted for here, and would refute
the "same code path, any route-declaring manifest" claim for that one workflow specifically.

## Where the fix belongs

Same place as ISS-225: a single merge of `manifestSelections` into the outgoing save manifest at
`handleSaveAsOverride`'s `buildWorkflowManifest(...)` call (or a small shared local helper in
`IdeaInputPage.tsx` used by every save call site there) fixes this for all five examples at once,
since none of them get a bespoke code path — they all render through the same component and the
same button.
