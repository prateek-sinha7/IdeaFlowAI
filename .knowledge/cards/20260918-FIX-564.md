## The symptom

One transient Bedrock fault ended a whole 25-worker wave.

Bedrock accepted a builder's request, streamed 1173 thinking deltas over 98
seconds, then put an error frame on the still-open `ConverseStream`:
`internalServerException` — "Try your request again". Nothing retried it, the
worker failed, and because fan-out is fail-closed (see FIX-566) the failed
worker ended the run.

## The root cause

Three independent chances to classify that exception as transient, all missed on
a capital letter.

1. The transient whitelist was PascalCase and compared case-sensitively.
   Botocore surfaces an event-stream error frame with a LOWER-camel
   `:exception-type` code, so `internalServerException` matched nothing.
2. The HTTP-status fallback had nothing to read. Botocore's event-stream parser
   never attaches `ResponseMetadata`/`HTTPStatusCode` to an `EventStreamError`,
   so the status branch could not fire.
3. `_TRANSIENT_SUBSTRINGS` had no `internal server` token, so the last-resort
   message match missed too.

The structural fault underneath all three: the predicate was **fail-closed**. An
unrecognised code meant "not transient", and the set of codes a mid-stream
provider fault can carry is not enumerable from the outside.

## What changed

`_is_transient_throttle` now **fails open**. Classification order, all
comparisons casefolded on both sides:

1. An explicit PERMANENT code → `False` immediately. The set is
   `AccessDeniedException`, `UnauthorizedException`,
   `UnrecognizedClientException`, `ExpiredTokenException`,
   `InvalidSignatureException`, `ValidationException`,
   `ResourceNotFoundException` — genuinely our fault (bad auth, signature, ARN
   or input), never worth a retry.
2. A known transient code → `True`.
3. A botocore-shaped response dict whose `HTTPStatusCode` is in
   {429, 500, 503, 529} → `True`.
4. A `status_code` / `http_status` attribute in that set → `True`.
5. `exc` is a `botocore.exceptions.EventStreamError` not caught by step 1 →
   `True`. A mid-stream fault is by construction something that happened on
   Bedrock's side of an already-accepted request; fail OPEN for the one family
   this predicate cannot enumerate exhaustively.
6. Type name or stringified message contains a transient substring →  `True`.
7. Otherwise `False`, so the caller re-raises and does not switch models.

`DeepAgentRunner.astream_events` gained a bounded **same-model** retry:
`_MAX_MODEL_CALL_ATTEMPTS = 3` (1 initial + 2 retries), full-jitter exponential
backoff — `random.uniform(0, min(30.0, 2.0 * 2**attempt))`. The engine's own
model-fallback loop only ever ADVANCES TO A CHEAPER MODEL and has no sleep; for
a `cost_class="cheap"` model (the builders' Haiku) the tier-descent chain is
empty, so it exhausts on attempt 1. Only the runner, which owns the model call,
can do what "try your request again" actually asks for. The jitter is what stops
25 concurrent workers waking in lockstep.

## The known ceiling

The retry is scoped to failures **before anything has been yielded downstream**:

```python
if yielded_any or attempt >= _MAX_MODEL_CALL_ATTEMPTS:
    raise
```

An in-place retry after chunks have already reached the consumer would duplicate
them, and the runner has no vocabulary for telling the engine to discard a
partial stream. So this retry would **not** have saved the incident above, which
failed after 1173 deltas. Closing that gap needs an engine-side reset signal the
fallback chain currently emits only for a model switch.

## The proven-model exception

`ea620c42c` added one narrow escape from the permanent set.
`ResourceNotFoundException` ("Inference Profile ARN not found") is a genuine
provider lie when the same model id served traffic minutes ago — run `353bb0af`
lost `pb-validate` on `eu.anthropic.claude-sonnet-4-6` while `pb-spec` and
`pb-design` had just used it successfully, and a direct probe right after
returned OK. A model that has streamed successfully in this process is recorded
in `_PROVEN_MODELS`, and only `resourcenotfoundexception` flips transient for it.
Auth, validation and signature codes stay permanent forever — a proven model
must never launder them into a retry.

This matters because the predicate is the single gate for three defences at
once: the runner's same-model retry, the runner's re-raise, and the engine's
model-fallback loop. One permanent verdict kills all three.

## Why this is load-bearing

Fail-closed waves (FIX-566) make the classifier the difference between one
unlucky worker and a dead run. The two changes should be read together.
