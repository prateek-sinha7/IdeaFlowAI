# ISS-744

## Title

Filed from a direct investigation of two questions Bilal asked about the run-detail version UI:
(1) why does "Latest (live)" exist alongside v1..vN, and (2) why does a run-detail screen update
when a revision is running "on another screen." This card answers (2)'s BUG half. Question (1)'s
answer (redundant only in a fully-settled family; load-bearing whenever a run completes untagged)
is not a new defect — it is already explained by the existing [ISS-697](20260922-1000-ISS-697.md)
(best-effort tagging) and [ISS-725](20260922-1247-ISS-725.md) (restore rewrites live HEAD) cards,
corroborated live in this pass (see "Live evidence" below).

## What is broken

Pin an older version from the RunHeader `VersionMenu` (e.g. "v2" while the family's newest is
v6) on a run-detail screen. While that pin is up, let ANY revision this browser tab is tracking
reach `pipeline_complete` — the SAME family's own in-flight revision that was already running
when you arrived on the page, or a completely different run this tab is also subscribed to for
the "N running" notification badge. The instant it lands, the pinned view is silently discarded:
the chip, Steps tab, agent list, agent-output cards, Preview and Workspace tab all snap back to
"Latest (live)" — no confirmation, no toast, no way to tell the pin was dropped except that the
content changed under the user.

## Root cause — CONFIRMED

Two pieces, each independently confirmed by direct read of the current file, that chain together.

**Piece 1 — `frontend/src/app/[...view]/page.tsx:1495-1522`:**

```tsx
const completingRunId = data.pipeline_run_id as string | undefined;
const completingPipelineType = data.pipeline_type as string | undefined;
const isForeignCompletion =
  !!completingRunId &&
  !!trackedRunIdRef.current &&
  completingRunId !== trackedRunIdRef.current;
...
const isRevisionCompletion = typeof completingPipelineType === "string" && completingPipelineType.endsWith("_revision");
...
if (completingRunId && (!isForeignCompletion || isRevisionCompletion)) {
  setContentSourceRunId(completingRunId);
```

The `isRevisionCompletion` clause is an unconditional OR against the foreign-completion guard:
**any** `*_revision`-typed pipeline this tab is subscribed to advances `contentSourceRunId` to
that run's id, whether or not it is the run the user is currently looking at. The comment
directly above (`:1501-1508`) states the assumption this leans on — "a `*_revision` pipeline is
intentionally dispatched FROM the currently-tracked run" — but nothing in the condition checks
that; it only checks the type-name suffix. `contentSourceRunId` is the prop `DashboardLayout`
threads into `PreviewPanel` as `liveRunId` (`DashboardLayout.tsx:3311`,
`liveRunId={contentSourceRunId ?? null}`).

**This bypass is deliberate, dated, and documented — [FIX-088](20260722-FIX-088.md) (2026-07-22).**
Before FIX-088, `isForeignCompletion` blocked `setContentSourceRunId` for EVERY revision
completion (a revision's id is never `trackedRunIdRef.current`, which stays on the PARENT run's
id for the whole duration the revision runs), so the version chip stayed stuck at "v1" forever
after the first revision. FIX-088's own reasoning — "the user is revising a run they were already
viewing, so the revision completion should advance the content source" — is correct for the
un-pinned case and was verified only for it (its own Verification section walks through "v1,
no pin" -> revise -> "v2, no pin"). It does not mention `viewingVersion`/pinning at all. The
bypass this card is reporting is not a bug FIX-088 introduced by accident so much as a case FIX-088
never had to consider: **a fix for this card must keep FIX-088's outcome (the chip/family DOES
advance) while additionally not tearing down an explicit pin that post-dates the revision's
launch.** Simply reverting FIX-088 re-opens the original "stuck at v1" symptom — see "Fix
direction" below.

**Piece 2 — `frontend/src/components/preview/PreviewPanel.tsx:883` and `:792-803`:**

```tsx
// A new live run supersedes any active read-only view.
useEffect(() => { setViewingVersion(null); }, [liveRunId]);
```

```tsx
useEffect(() => {
  if (intendedSandboxRef.current !== null) {
    setSandboxSelectedRef(intendedSandboxRef.current);
    intendedSandboxRef.current = null;
  } else {
    setSandboxSelectedRef(null);
  }
}, [activeRunId]);
```

`activeRunId = viewingVersion?.id ?? unpinnedRunId` (`:771`), and `unpinnedRunId = liveRunId ??
latestId` (`:770`). When Piece 1 changes `liveRunId`, the `:883` effect unconditionally nulls
`viewingVersion` — which recomputes `activeRunId` to the new `unpinnedRunId` — which changes the
`:792-803` effect's dependency, and since nothing staged `intendedSandboxRef` for this path (that
ref is only ever set inside `handleVersionMenuSelect`, a completely different call path — see
"Relationship to FIX-516" below), the `else` branch runs and `sandboxSelectedRef` is ALSO nulled.
Both halves of the pin — the DB-projected `viewingVersion` (Steps/agents/outputs/Preview content)
and the git-ref `sandboxSelectedRef` (Workspace tab, ref-scoped file reads) — collapse to "live"
in the same render pass. Neither effect inspects whether a pin was active before clearing it.

## Reproduction path (traced, not yet browser-observed — see Confidence)

1. Open a run-detail page for a family that has an in-flight `*_revision` run (or one this tab
   is otherwise subscribed to for the notification badge).
2. Use the `VersionMenu` to pin an older member, e.g. v2 — `handleSelectVersion` fires,
   `viewingVersion` and `sandboxSelectedRef` are both set to v2 (`PreviewPanel.tsx:808-840`,
   confirmed correct — this part already works).
3. Wait for the tracked revision to finish. `pipeline_complete` arrives over this tab's own SSE
   connection (it was already subscribed — pinning is pure frontend state, it never calls
   `detachRun`/changes `RunConnectionProvider`'s `liveRunIds`).
4. `page.tsx:1522` fires `setContentSourceRunId(completingRunId)`. `liveRunId` changes value.
   `PreviewPanel.tsx:883` fires. The v2 pin (both halves) is gone; the screen now shows the
   completed revision as "Latest (live)" with no prompt.

## Relationship to FIX-516 — this is a NEW path into the same reset effect, not a regression of it

[FIX-516](20260915-1420-FIX-516.md) added `intendedSandboxRef` specifically so that
`handleSelectVersion`'s OWN side effect (it changes `viewingVersion`, which changes `activeRunId`,
which fires the `:792-803` reset) does not immediately erase the `sandboxSelectedRef` the SAME
call just set. That guard only covers the reset firing from INSIDE the version-pinning call
chain. It has no way to cover the reset firing from an EXTERNAL cause — `liveRunId` itself
changing because a different piece of state (`contentSourceRunId`, owned by `page.tsx`, several
components away) moved out from under it. FIX-516's own locked_constraint ("intendedSandboxRef
... must be set before `handleSelectVersion` is called") is upheld correctly by this defect — the
ref is legitimately `null` on this path, because nothing pinning-related asked for this reset at
all.

## Live evidence for Q1 (not a new defect — corroborates existing cards)

Verified directly in Postgres (`flowin_local_pdf`) and the shared sandbox on disk, read-only, no
browser or run launched:

- Family root `4d55165d-59b5-4571-b5ac-1ce7aebc3cbf` (`ppt` → 5 `ppt_revision`s, v1..v6, all
  `status=completed`, all `git_tag` populated) — its sandbox
  (`runs/c6b9b61f-183d-4662-ae84-d7fd5a052571/4d55165d-.../`) has `HEAD` and tag `v6` at the
  IDENTICAL sha `a7fbc59d45bebd4e6c3f95a6009813c9513d5f65`, clean working tree (`git status
  --short` empty). For this settled family, "Latest (live)" and the top `vN` tag are byte-for-byte
  the same thing today — this is very likely the exact family Bilal was looking at when he asked
  "why do we have latest (live)?", and the observation is correct: once every revision tags
  cleanly and nothing has written since, the two options ARE redundant.
- Family root `2708dbf1-50d0-465d-9bed-56b651ea1abf` (the [ISS-697](20260922-1000-ISS-697.md)
  family) — right now its sandbox's `git tag --list` returns only `v3`; the DB says the root's
  own `git_tag='v1'` but no `v1` tag exists on disk at all. `GET /sandbox/refs` for this family
  today returns `{"refs":["v3"]}` — the dropdown cannot even offer "v1", but "Latest (live)"
  still resolves (to v3's content, `HEAD == v3`'s sha here too). This is ISS-697's mechanism,
  live and current, not a new finding — it is the concrete case where "Latest (live)" is NOT
  redundant: it is reachable even where a real, DB-recorded version has become unreachable by
  ref.

## Blast radius

- `frontend/src/components/preview/PreviewPanel.tsx:883` and `:792-803` — the two effects that
  fire; both halves of the pin (`viewingVersion`, `sandboxSelectedRef`) collapse together, so
  every pin-aware child (Steps/agents via `effAgents`/`effPipelineState`/`effAgentOutputs`,
  Preview via `effUserStoryContent`/`effPptContent`/`effPrototypeContent`/`effGenericDeliverable`,
  Workspace/`SandboxTab` via `selectedRef`, the `VersionMenu` chip/selection itself) is affected
  identically — this is not four separate bugs, it is one state collapse consumed in four places.
- `frontend/src/app/[...view]/page.tsx:1521-1522` — `grep -n "setContentSourceRunId("` shows 7
  call sites total; this is the only one gated by `isRevisionCompletion`, i.e. the only one that
  can fire for a run the viewer did not just launch/select. The other 6 (`:2748`, `:2877`,
  `:2902`, `:3408`, `:3495`, `:4167`) are direct user actions (select/reopen/launch/reset) and are
  not implicated — a pin is not expected to survive the user explicitly navigating away anyway.
- Not implicated: the `pinnedMemberId` effect (`PreviewPanel.tsx:896-913`, the `/versions/{v}`
  URL deep-link path) — it only ever SETS `viewingVersion`, never clears it, and does not touch
  `sandboxSelectedRef` at all (confirmed by direct read; this was the specific path flagged for
  checking and it is not the mechanism — the sibling `:883` effect is).

## Fix direction (not applied — issue only)

Belongs in `PreviewPanel.tsx`, not in `page.tsx` — `page.tsx`'s job of tracking which run just
completed is legitimate and correct; the bug is that `PreviewPanel` reacts to that tracking
change unconditionally. The `:883` effect (and, by extension via `activeRunId`, the `:792-803`
one) needs to check whether a pin is currently intentional before clearing it — e.g. only auto-
clear `viewingVersion` on a `liveRunId` change when `viewingVersion` is null OR when
`viewingVersion.id === previous liveRunId` (i.e. the view WAS following live and a new live run
superseded it — the legitimate case the comment at `:882` describes), never when the user
explicitly pinned a DIFFERENT, older member via `handleSelectVersion`. One guard here covers
Steps/agents/Preview/Workspace at once — no per-tab patch needed, matching how `effAgents` etc.
already chokepoint through this same `viewingVersion` state.

**Do not revert [FIX-088](20260722-FIX-088.md)'s `page.tsx` bypass as "the fix" for this card** —
that resurrects its original symptom (chip/family stuck at v1 forever after the first revision).
`page.tsx` should keep advancing `contentSourceRunId`/refetching the family on every revision
completion; `PreviewPanel` is where the pin needs to survive that advance.
