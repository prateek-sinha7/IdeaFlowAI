## What was wrong

`page.tsx` `handleWebSocketMessage`'s `pipeline_cancelled` arm (inside the
`pipelineTypes` fast-path block) called `setLastCancelledRunId`,
`detachRunRef.current(cancelledId)`, and cleared questionnaire/gate state — but
never refreshed `recentRuns` from the server. `AppHeader` derives its "N
Running" badge and dropdown from `recentRuns` filtered by `LIVE_STATUSES`
(`AppHeader.tsx:46-49`). After a cancel the backend immediately writes
`status: "cancelled"` to the `workflow_runs` table, but the stale `recentRuns`
snapshot still listed the run as `running` — so the badge kept showing the
cancelled run as in-flight until the next unrelated `recentRuns` refresh
(pipeline_complete of a different run, page focus/online event, etc.).

The `pipeline_failed` handler (immediately above the cancelled block) and the
`pipeline_diverted` handler (below it) both refresh:

```ts
getWorkflows(currentToken, { limit: 50 })
  .then(({ runs }) => setRecentRuns(runs))
  .catch(() => {});
```

The `pipeline_cancelled` arm was the only missing case.

## What changed and why there

Added the same `getWorkflows` → `setRecentRuns` pattern to the
`pipeline_cancelled` sub-block, immediately after `detachRunRef.current(cancelledId)`:

```ts
// ISS-143: refresh recentRuns so AppHeader's "N Running" pill clears
// immediately after a cancel.
const cancelToken = getToken();
if (cancelToken) {
  getWorkflows(cancelToken, { limit: 50 })
    .then(({ runs }) => setRecentRuns(runs))
    .catch(() => {});
}
```

`getToken()` is safe here because cancellation requires an authenticated
interaction. No KAN-125 "preserve still-building runs" protection is needed:
unlike `pipeline_complete` (which can race with other running runs being
incorrectly marked complete), a `pipeline_cancelled` frame means exactly one
run changed status; the rest of the list is unaffected.

`getWorkflows` is already imported at the top of `page.tsx`. No new
dependencies introduced.
