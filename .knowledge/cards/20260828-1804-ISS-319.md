## Summary

`PUT /api/settings/preferences` (`/settings/ai-model` page, `backend/app/api/settings.py:316-342`
`update_preferences`) is not safe under two concurrent writes from the same user. Confirmed via
`bug-hunter/ledger.md` entry **BUG-20260828-094120-settings-ai-model-r2**.

## Reproduction (validator, 3/3 cold-start cycles, all reproduced)

Each cycle: fresh cold navigation `/dashboard` -> `/settings/ai-model`, then fire two
`PUT /api/settings/preferences` requests concurrently (`Promise.all`) with different
`preferred_model` values via `fetch`, using the `auth_token` from `localStorage`. Baseline
before every trial: `eu.anthropic.claude-haiku-4-5-20251001-v1:0`.

- **Cycle 1** — A=`opus-4-6`, B=`sonnet-4-5`. Response A correctly reported `opus-4-6`.
  Response B (its own request asked for `sonnet-4-5`) reported **`opus-4-6`** — request A's
  value, not its own. `GET /api/settings/preferences` immediately after: DB = `opus-4-6`.
  Request B's write is gone, no error anywhere (200 on both).
- **Cycle 2** — A=`sonnet-4-5`, B=`haiku-4-5`. Response B (asked for `haiku-4-5`) reported
  `sonnet-4-5` (A's value). DB = `sonnet-4-5`. Request B's write lost, 200 on both.
- **Cycle 3** — A=`opus-4-6`, B=`opus-4-5`. This time it was response A (asked for `opus-4-6`)
  that reported `opus-4-5` (B's value). DB = `opus-4-5`. Request A's write lost, 200 on both.

The "losing" slot was **not** fixed to A or B across cycles — it varied, which is what you'd
expect from a genuine backend race rather than a client-side or fixed ordering artifact.
Baseline was restored to `eu.anthropic.claude-haiku-4-5-20251001-v1:0` after every cycle.

## Root cause

`backend/app/api/settings.py:316-342`:

```python
@router.put("/preferences", response_model=UserPreferencesResponse)
def update_preferences(
    payload: UserPreferencesUpdateRequest,
    user: User = Depends(get_current_user),
    db: Session = Depends(get_db),
) -> UserPreferencesResponse:
    model_id = payload.preferred_model
    ...
    user.preferred_model = model_id
    db.add(user)
    db.commit()
    db.refresh(user)

    return UserPreferencesResponse(
        preferred_model=user.preferred_model,   # <-- read AFTER refresh, not the value this
        available_models=AVAILABLE_MODELS,       #     request itself just wrote
    )
```

The handler is a **sync def** endpoint, so FastAPI runs it in a threadpool worker — each
concurrent request gets its own `Session` (via `Depends(get_db)`) but they share the same
`users` row. There is no version column, no `SELECT ... FOR UPDATE`, and no re-check between
`commit()` and `refresh()`. The response body is built from `user.preferred_model` **after**
`db.refresh(user)`, which re-reads the row's current DB state — not the value this specific
request wrote. If a second request's `commit()` lands in the window between this request's own
`commit()` and its `refresh()`, this request's response silently reports the *other* request's
value while its own write is overwritten with no error, no optimistic-lock conflict, no
indication to either caller that anything raced.

**Re-verified 2026-08-29 (3-analyzer), against the CURRENT file:** [FIX-361](20260829-0029-FIX-361.md)
landed after this card was authored and inserted a tier-entitlement check between validation and
mutation. `update_preferences` is now at `backend/app/api/settings.py:317-353`; the vulnerable
sequence is unchanged in shape, just shifted — `user.preferred_model = model_id` (345) ->
`db.add(user)` (346) -> `db.commit()` (347) -> `db.refresh(user)` (348) -> response built from
the refreshed object (350-353). The new 403 check (`settings.py:340-343`,
`can_use_model(user.tier, model_id)`) runs BEFORE the mutation and touches no DB row, so it
neither closes nor widens this race: a request that fails entitlement never reaches `db.commit()`
and so never participates in it. A fix must be written against these CURRENT line numbers, not
the 316-342 range quoted above (that range was correct at validation time; FIX-361 shifted
everything below it by one line per line added).

## Blast radius

Grepped every caller/consumer, not just the reported path (`grep -rn "preferred_model"
backend/`, `grep -rn "db.refresh(user)\|db.refresh(" backend/app/api/`, then read each hit):

- **Frontend caller (the reported path) — exactly one:**
  `frontend/src/components/settings/AccountSettings.tsx:143` (`handleSaveModel`), via
  `updatePreferences()` in `frontend/src/lib/api.ts:1396-1405` and the parallel wrapper
  `frontend/src/store/api/settings.ts:54-58`.
- **Downstream consumers of the corrupted persisted value** (not buggy themselves, but they
  silently inherit whichever value won the race): 8 sites in `backend/app/api/run_commands.py`
  read `user.preferred_model` / `current_user.preferred_model` to pick the Bedrock model for a
  real run — lines 1443, 1604, 2921, 3251, 3362, 3696, 3819, 3833 (independently re-confirmed by
  grep, matching FIX-361's own count) — plus `get_preferences` (`settings.py:306-314`), which
  reports the winner's value on the very next `GET`.
- **Same-file and cross-file siblings sharing the identical
  commit-then-refresh-then-respond-from-the-refreshed-object shape** (grepped every
  `db.refresh(` call site under `backend/app/api/` and read each): `upsert_github_pat`
  (`settings.py:114-176`) and, in a different file but the identical pattern, `admin.py`'s
  `update_user_tier` / `update_user_role`. Filed as [ISS-470](20260828-2310-ISS-470.md) and
  [ISS-471](20260828-2310-ISS-471.md) respectively.
- **Checked and ruled out** (same file shape, different mechanics): `create_api_key`
  (`settings.py:229-255`) inserts a brand-NEW row per request with its own generated id, so
  concurrent calls never share a row to overwrite; `set_constitution`
  (`settings.py:383-399`) builds its response from `payload.content` directly and never re-reads
  storage, so a race in the underlying `Workflow_Memory` store (if any) cannot surface as a
  wrong-value response; `GET /api/settings/preferences` is a pure read with no `commit()`, so any
  staleness it shows is ordinary DB eventual-consistency, not this code defect. `chats.py`,
  `handoff.py`, `mcp.py`, `user_agents.py`, `user_workflows.py`, and
  `run_commands.py:2469` were also grepped for `db.refresh(` and each either inserts a new row
  or is not reachable via two concurrent requests racing one shared field the way
  `update_preferences` is.

## Where the fix belongs

No single shared function wraps "mutate one field, commit, respond" today — each of the three
flawed handlers (`update_preferences`, `upsert_github_pat`, `admin.py`'s tier/role updates)
inlines its own commit/refresh/response. The fix is the SAME one-line change repeated at each of
the three sites, not a new abstraction for three call sites with three different response
models: stop building the response from the post-`db.refresh()` object and build it from the
value this request itself already validated and just committed.

For `update_preferences` specifically that means returning `preferred_model=model_id` (the
already-validated local variable, `settings.py:327`) instead of `user.preferred_model` read
post-refresh — `db.refresh(user)` becomes unnecessary for the response and can be dropped, since
no other returned field needs a DB-assigned value here. This satisfies the register entry's own
"Expected" bar verbatim: last-write-wins at the DB stays acceptable UX (no locking/migration
needed), but a `200` body must never report a value the request itself didn't send. The same
one-line pattern is the proposed fix for [ISS-470](20260828-2310-ISS-470.md) (source
`github_username`/`scopes` from the already-fetched local `gh_user`/`scopes_header`) and
[ISS-471](20260828-2310-ISS-471.md) (source `tier`/`is_admin` from `request.tier`/
`request.is_admin`). If a fourth instance of this shape turns up later, a shared helper becomes
worth it — three call sites with three different response models is not.

No invariant from `.knowledge/CONTEXT.md` section 2 is at risk: this is a plain FastAPI handler,
not the kernel, not a capability resolved through the registry, and the proposed fix needs no
schema migration.

## Expected vs actual

Expected (per the register entry): either a deterministic last-write-wins with each response
accurately reflecting what *that* request itself persisted, or the API serializes/rejects
overlapping writes (e.g. 409 via optimistic concurrency). A `200 OK` body must never report a
`preferred_model` different from the one that request itself sent.

Actual: one of two concurrent writes is silently discarded, and that losing request's own `200`
response body fabricates the winner's value instead of reporting its own request's persisted
state (or an error).
