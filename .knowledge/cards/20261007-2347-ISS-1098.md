# ISS-1098

Sibling of [ISS-1073](20261007-2135-ISS-1073.md) (QA-KB-096), filed by its analysis on 2026-10-07. **INFERRED.** The offline render shows it; no browser has
seen it, and the real page's timing is not established (see "Open" below). An unreproduced sibling is a lead, not a defect.

## Why the root cause implies it

[ISS-1073](20261007-2135-ISS-1073.md) says the 404 is a Preview-only request, yet the report lists it on every page (detail, steps, files, workspace, audit,
stream), and the validators only checked the detail page (the card says "per the reporter" for the rest). A Preview-only request can reach another route only if
the Preview mounts there. This is how it can.

## Mechanism (read, then rendered)

- `activeTab` is `useState<PanelTab>("preview")` (`PreviewPanel.tsx:814`).
- A deep link to another tab is applied AFTER the first commit, by effects: the deep-link consumer (`:1324-1332`, `setActiveTab(tab)`) and the state-keyed default
  (`:1350-1357`).
- On the first commit the Preview branch runs. With content present and no loading skeleton it reaches `renderDeliverable()`, which mounts the generic preview,
  and `SandboxPdfPreview`'s effect sends its read synchronously (`SandboxPdfPreview.tsx:22-34`).
- The tab switch then unmounts the pane. The request was already sent.
- Offline render (`evidence/qa-kb-096/15`, probe G): all five deep-link forms (steps, workspace, audit and files by `deepLinkTarget`, files by `initialTab`) sent
  `sandbox/file?path=Backlog.pdf&ref=v2`, and the Preview was gone afterwards.

## Expected vs actual

Expected: a request that belongs to the Preview pane is sent only when the Preview pane is on screen.
Actual (INFERRED for the real page): it is sent for the newest member too, where `displayRef` is undefined and the read is the live `Backlog.pdf`: a 200 of about
23 MB on a `/steps` load that never shows it. For an older member it is today's 404.

## Effect on ISS-1073's fix

After the fix the older member's transient mount sends only the listing (a cacheable 200) and the blob read never starts, because the resolve is async and the
component unmounts first. The newest member's live read still goes out. So the verifier of ISS-1073 should see no 404 on `/steps`, `/files`, `/workspace` or
`/audit` for run 78e185fb, and this card stays open for the newest member.

## Fix direction

Initialise `activeTab` from the route's tab on the first render (a `useState` initialiser that reads `initialTab` and `deepLinkTarget`), or render the tab
content only once the first deep link has been consumed. Do not gate on the run state alone.

## Open

- The Preview branch shows `RunDataSkeleton` while `isLoadingRunData` (`PreviewPanel.tsx:1895-1906`), so on a cold load the content may not exist yet on the first
  commit. Whether the page sets `deepLinkTarget` before or after the record loads decides if the transient mount happens in the real app. The offline render has
  no such gate.
- What would settle it: cold-load `/runs/b40eabd0-d7e2-4bc2-bc42-99ef6a147bff/steps` (the newest member, a 6.5 MB record) in a browser and watch the network for
  `GET .../sandbox/file?path=Backlog.pdf` answering 200.
