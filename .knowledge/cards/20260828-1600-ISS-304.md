# ISS-304

## Title

Run detail chat header's token total is read straight from the `pipeline_complete`
event's `total_tokens` field, which the backend computes to a DIFFERENT (larger) value
than the sum of the run's own `agent_complete` events — the same number the persisted
`token_usage` field (and the Run History list card) both agree on.

## Reproduction (BUG-20260828-051900-runs, confirmed 3/3, cold every cycle)

1. Sign in as `qa-admin`, navigate directly to
   `/runs/a0693fcd-9451-4c19-a9e7-61474ea03516` (a fresh `page.goto`, no
   click-through) — reproduced identically on 3 independent cold loads, no axis
   variation needed (not timing/tier/theme dependent).
2. The run detail header (`LaneRunHeader`, under the run title) reads "just now ·
   22m 0s · **17.9K tokens**".
3. `GET /api/runs/a0693fcd-9451-4c19-a9e7-61474ea03516` (the same figure the Run
   History list card shows) returns `token_usage.total_tokens: 10428` (10.4K).
4. `GET /api/runs/a0693fcd-9451-4c19-a9e7-61474ea03516/events` shows the actual
   mechanism: three `agent_complete` events —
   `{agent_id: ppt-brief-analyst, input_tokens: 2050, output_tokens: 186, total_tokens: 2236}`,
   `{agent_id: ppt-composer, input_tokens: 2050, output_tokens: 2046, total_tokens: 4096}`,
   `{agent_id: ppt-validator, input_tokens: 2050, output_tokens: 2046, total_tokens: 4096}`
   — summing to `input=6150, output=4278, total=10428`, exactly matching
   `token_usage.total_tokens`. But the terminal `pipeline_complete` event on the SAME
   run carries `total_input_tokens: 7549, total_output_tokens: 10382, total_tokens:
   17931` — a figure the backend computed independently of (and inconsistent with) its
   own three `agent_complete` events.

## Root cause (frontend mechanism; backend field is the actual source of the bad number)

`frontend/src/hooks/useWorkflow.ts`'s `pipeline_complete` case (~line 787) prefers the
event's own `total_tokens` over the value accumulated from `agent_complete` events:

```ts
totalTokens: (msg.total_tokens as number) || prev.totalTokens || 0,
```

`prev.totalTokens` at that point IS the correct accumulated sum (10428 — built by the
`agent_complete` case's `updated.reduce(...)` over per-agent `inputTokens`/`outputTokens`,
verified against the events endpoint above). The `pipeline_complete` event's own
`total_tokens` (17931) overrides it because the event carries a non-zero value, and that
event-level total is where the wrong number originates — the backend computes it
independently rather than deriving it from the same `agent_complete` totals it already
persisted. `LaneRunHeader.deriveLaneMeta` (frontend/src/components/chat/LaneRunHeader.tsx:76-77)
then renders `pipelineState.totalTokens` verbatim as "N tokens", so the header surfaces
whatever `pipeline_complete.total_tokens` says without ever reconciling it against the
per-agent sum or the persisted `token_usage` field.

This is the SAME authority-split pattern [ISS-150](20260813-0439-ISS-150.md) already
filed for `pipeline_complete.total_duration` vs `workflow_runs.duration` (there: two
numbers both answering "how long", computed by two different code paths, never
reconciled) — ISS-150 traced its duration field to `app/api/run_commands.py`; the
`pipeline_complete.total_tokens`/`total_input_tokens`/`total_output_tokens` fields are
very likely emitted by the same code path and warrant the same backend investigation,
not re-derived here (backend was not read this session — filed from the frontend
symptom + the events/run API evidence above).

## Backend root cause (CONFIRMED — analyzer addendum, backend read this session)

Two backend code paths independently compute "total tokens for this run" from different
result sets, and nothing reconciles them — the same authority-split shape as ISS-150, now
traced on the token side rather than inferred:

1. **The live/replayed `pipeline_complete` event** (`backend/agents/execution_engine/engine.py:3746-3757`):
   `"total_tokens": _tok_in + _tok_out`, where `_tok_in`/`_tok_out` (lines 3712-3717) start as
   the sum of each agent's `agent_complete` tokens, then get the SmartPlanner's
   (`usage_sink=aux_token_usage.append` at line 2122), a clarify one-shot's (line 2265), and
   the validation fix-loop sub-agent's (line 2443) token spend folded in via `aux_token_usage`
   (lines 3718-3726, comment "ISS-033: fold in every model call that ran OUTSIDE the per-agent
   stream ... so their tokens are COUNTED in the run totals instead of being silently dropped").
2. **The persisted `workflow_runs.token_usage` column** — read by `GET /api/runs` /
   `GET /api/runs/{id}` (hence the Run History card and this bug's own API cross-check) — is
   written by `_apply_terminal_output_columns` (`backend/app/api/run_commands.py:2953-2977`,
   "the SOLE writer of these columns" per its own docstring, shared by the launch path, both
   resume entry points, and the revision driver). Its `pipeline_complete` branch
   (`run_commands.py:3042-3045`) reads ONLY `final_output`/`deliverable_mimetype`/
   `deliverable_filename` off that event — it walks past the event's own `total_tokens`/
   `total_input_tokens`/`total_output_tokens` fields without reading them. A few lines later
   (`run_commands.py:3057-3065`) it independently RE-DERIVES the persisted totals by
   re-summing `agent_outputs_collector` (i.e. `agent_complete` events only) — silently
   excluding the exact `aux_token_usage` contribution the live event already folded in.

This is why `token_usage.total_tokens` (10428) matches the pure per-agent sum while
`pipeline_complete.total_tokens` (17931) is larger by ~7503 — the planner/clarify/fix-loop
spend on this run. **Confirmed further:** grepped every backend consumer of
`total_input_tokens`/`total_output_tokens` — `backend/app/api/analytics.py:189-195` also reads
only the persisted `token_usage` column, so Analytics KPI tiles and per-pipeline/per-model
charts undercount the same way, for every run that used the planner/clarify/fix-loop, not just
this one (filed separately as [ISS-418](20260828-2231-ISS-418.md)). Checked the inverse/adjacent
states: `pipeline_failed` and `pipeline_cancelled` (`useWorkflow.ts:819+`, `:855+`) never touch
`totalTokens`/`totalInputTokens`/etc, so a failed or cancelled run keeps the correct
per-agent-accumulated total — this bug is specific to a successful/degraded `pipeline_complete`.

**Where the fix belongs:** `_apply_terminal_output_columns` is already, by its own docstring,
the single funnel `token_usage` is written through for all four completion paths — the natural
fix point is there (consume the event's own totals instead of silently re-deriving a narrower
sum), not a frontend patch to `LaneRunHeader`/`TokenUsageSummary`, which would only mask the
symptom on those two renderers and leave Analytics undercounting untouched. INFERRED: whether
"total tokens for this run" should include planner/clarify/fix-loop overhead is a product call
this analysis can't make from the code alone — but whichever direction is chosen, unifying it
in this one function is what makes every reader (Run History card, `GET /api/runs/{id}`,
Analytics, and the frontend's `pipeline_complete`-driven state) agree.

**Frontend siblings found by grep** (same corrupted `pipelineState.totalTokens` object, not
independently reported): `TokenUsageSummary.tsx:19-28`, mounted in the Steps tab via
`AgentThinkingTab.tsx:321`, destructures the identical fields off the same `pipelineState`
object (one `useWorkflow()` call at `frontend/src/app/[...view]/page.tsx:2087`, shared via
props) — filed as [ISS-417](20260828-2230-ISS-417.md).

## Expected vs Actual

- Expected: the run detail header's token total equals `token_usage.total_tokens`
  (10.4K) and matches the figure already shown for the same run on the Run History
  list.
- Actual: the header shows 17.9K — a ~72% overstatement — sourced from
  `pipeline_complete.total_tokens`, a backend-computed field that disagrees with the
  backend's own `agent_complete` events and its own persisted `token_usage` summary.
