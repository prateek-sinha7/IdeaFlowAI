## Give AgentsPopup's own footer Save button the reopened workflow's identity

Fixes [ISS-167](20260819-1726-ISS-167.md) — see that card for the root cause.

**`frontend/src/lib/api.ts`:** added `saveUserWorkflow(token, userWorkflowId, body)` —
the one create-vs-update dispatch point (`userWorkflowId ? updateUserWorkflow(...) :
createUserWorkflow(...)`, stripping the create-only `base_pipeline_type`/`agent_ids`
before the PATCH call). `ComposerPage.tsx`'s `handleSave` already had this exact branch
inline (and was already correct — not a bug) — refactored to call the shared function
instead of carrying its own copy, per an explicit dedup request. This part is
independent of the actual bug and would stand on its own.

**`DashboardLayout.tsx`:** the `prototype`/`ppt` saved-workflow draft objects (built in
`handleLaunchSaved`) now include `id: saved.id, name: saved.name, description:
saved.description`, so the reopened row's identity survives the
`sessionStorage`/route-push hand-off into the wizard.

**`LaunchWizard.tsx`:** restores that `id`/`name`/`description` from the draft into
`userWorkflowId`/`savedName`/`savedDescription` state, and passes them down to
`<AgentsPopup>` as props — along with `initialSelections={selectionsRef.current}`
keyed on `key={userWorkflowId ?? "new"}` to force a remount the moment the draft
restore populates the selections ref (`AgentsPopup`'s own `initialSelections` only
seeds a `useState` initializer once at mount, so without the forced remount the popup
would still open empty despite the ref being correct by then).
**`LaunchWizard.tsx`'s own page-level Save button is UNCHANGED** — still
unconditionally `createUserWorkflow`, still always opens `NameWorkflowModal`. It was
tried with the same update-in-place treatment and reverted: whether that separate
button should behave the same way is unconfirmed, and this fix only covers the button
actually reported.

**`AgentsPopup.tsx`:** the actual fix. Added `userWorkflowId`/`savedName`/
`savedDescription` props; its own `handleSaveWorkflow` now calls the shared
`saveUserWorkflow(token, userWorkflowId, ...)` instead of `createUserWorkflow`
directly; its footer "Save workflow" button skips `NameWorkflowModal` entirely and
saves directly under the known name when `userWorkflowId` is set — matching
`ComposerPage`'s existing update-in-place behavior for the one button confirmed to
need it.
