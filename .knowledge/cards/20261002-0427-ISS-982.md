## Fixed (QA-KB-058, 2026-10-07)

Fixed by [FIX-721](20261007-1758-FIX-721.md) the way the "Fix placement" section below recommends, with no second guard.
`onOpenInCanvas` passes `() => router.push(canvas)` into the same `requestLeave` as Back, so it gets one signal and
one dialog. Prompting was chosen over carrying the state to the canvas, as the smaller change the section names.

Now reproduced and verified in a browser (`evidence/qa-kb-058/fix-05-canvas-exit-dialog.png`): with a typed brief,
the exit prompts, and Leave anyway reaches `/workflows/prototype/canvas`. Untouched, it goes straight through. The
unit case "ISS-982: Open in full canvas goes through the same guard" in `LaunchWizard.iss917.test.tsx` fails against
HEAD.

## INFERRED sibling of [ISS-917](20261001-2220-ISS-917.md) — the other user-initiated exit (not yet reproduced)

Derived while analyzing QA-KB-058, whose root card is [ISS-917](20261001-2220-ISS-917.md) (the wizard's header
Back discards typed input). The mechanism below is read from code and CONFIRMED by the lines cited; the visible
effect has not been observed in a browser, so this stays a lead until someone reproduces it.

## Condition

On any wizard route (`/create/{ppt|ppt_v2|prototype|prototype_v2}`, `/workflow/create`, a ppt/prototype
`/workflows/{id}/run`) the user types a brief and/or picks a template or design system, opens `Advanced`, and
clicks `Open in full canvas` (`AgentsPopup.tsx:2915-2924`). The wizard's handler is a bare navigation,
`frontend/src/components/workflow/LaunchWizard.tsx:1476-1479`:

```tsx
onOpenInCanvas={() => {
  setShowAgents(false);
  router.push(`/workflows/${encodeURIComponent(MODE_CONFIG[mode].agentPipeline)}/canvas`);
}}
```

## Why the root cause implies this

[ISS-917](20261001-2220-ISS-917.md)'s mechanism is: the wizard keeps its input in component state, persists none of it, and guards none of its
exits. Header Back is one exit. This is the second user-initiated one. The rest are Continue (hands off by design,
`:1053`) and a login redirect (`:374`, `:646`, `:654`), neither of which is a loss. `grep "router\." LaunchWizard.tsx`
returns exactly `:374`, `:1053`, `:1078` (Back, fallback branch) and `:1478` (this one).

- `/workflows/{pipeline}/canvas` parses to `screen: 'workflow-canvas'` (`frontend/src/lib/routes.ts:340`).
  `wizardModeFor` (`frontend/src/app/[...view]/page.tsx:349-366`) has no case for it, so the early return at
  `:4117-4121` stops rendering `LaunchWizard`, which unmounts and takes every `useState` with it. The page renders
  `DashboardLayout` with `builtinCanvasType` instead (`:4250-4252`).
- Nothing is handed over. The comment at `LaunchWizard.tsx:1472-1475` records the choice: "navigation only ... a
  sessionStorage handoff is unnecessary and was read by whatever mounted next, which blanked the launch panel on the
  way back". That dropped a hand-off of the roster. The brief, picks and attachments never had a channel.
- Contrast `IdeaInputPage.tsx:2257-2278`: its `onOpenInCanvas` passes the live `agentIds`, `manifestSteps`,
  `selections`, `brief` and `gateAgentIds` to the full canvas. The wizard sends none of it, and the canvas refetches
  the manifest by URL, so even roster edits made in the Advanced modal a moment earlier do not travel.
- Nothing persists in the meantime: the only `sessionStorage` writes in the wizard are the launch hand-off
  (`LaunchWizard.tsx:1044`, `:1049`, `:1052`).

## Expected vs actual (INFERRED)

**Expected:** the exit is guarded like Back (the in-app "Leave without saving?" dialog, Stay / Leave anyway, when the
wizard holds unsaved input), or the typed state travels with the user.

**Actual (inferred):** the wizard unmounts at once. Returning with the browser Back lands on `/create/{mode}` with an
empty brief and no picks.

## What would settle it

Browser, `/create/prototype`: type a brief, click `Advanced`, click `Open in full canvas`, then use the canvas page's
Back (or the browser Back). Expect the wizard with an empty brief and no `[role=dialog]` on the way out.

## Fix placement

Do not build a second guard. [ISS-917](20261001-2220-ISS-917.md)'s fix should write its guard as a function that
takes the navigation (`requestLeave(go)`): Back passes `() => goBackOr(router, ...)`, and this exit passes
`() => router.push(canvas)`. One dirty signal, one dialog, no drift. Whether this exit should prompt or carry the
state is a product call; prompting is the smaller change, because it reuses the signal and the dialog the Back guard
already needs.
