## What is broken (INFERRED: every link below was read, none was run)

Found while analysing QA-KB-011 (2026-10-01). `IdeaInputPage` is the second of exactly two callers that send
`overrides_pipeline_type` (`grep` over `frontend/src`, non-test: `LaunchWizard.tsx:972` and
`IdeaInputPage.tsx:1774`), which is the field that makes the server UPSERT over a user's override row. It was not
reported and has not been reproduced.

**Condition.** A user with an ENABLED override of `user_stories`, `app_builder`, `mulesoft_to_springboot` or
`dotnet_to_azure` (the four built-ins that render `IdeaInputPage` rather than `LaunchWizard`; the comment at
`IdeaInputPage.tsx:1095-1100` says so) opens `/create/<type>` and clicks "Save as my version" before
`GET /api/workflows/<type>` has resolved.

**Expected.** The button is disabled until that fetch has settled, so it can only save a roster the user has seen.

**Actual.** It is enabled as soon as the library roster fills `pipelineAgents`:

- `IdeaInputPage.tsx:1965`: `disabled={pipelineAgents.length === 0 || (isMigrationMeta && !migrationChoice)}`.
  "Save workflow" at `:1950` carries the same expression.
- While `getWorkflowDetail` (`:1135`) is in flight, `showOverride` is false and `overrideAgents` is null, so the
  roster effect (`:1343-1410`) puts the library roster in `pipelineAgents` (`systemRoster`, `:1403-1408`).
- `handleSaveAsOverride` (`:1743-1785`) sends `agent_ids: pipelineAgents.map(...)` (`:1766`), a `manifest` built from
  the same roster (`:1769-1773`) and `overrides_pipeline_type: workflowId` (`:1774`).
- The server replaces the real row: `backend/app/api/user_workflows.py:794-834` (`prior.agents = json.dumps(sorted_ids)`
  `:813`, `prior.manifest_json = ...` `:816`, `prior.override_enabled = True` `:827`). There is no version or
  concurrency check.

**Why the root cause implies it.** [ISS-284](20260828-1906-ISS-284.md)'s root cause is that a host publishes a
roster as authoritative from first paint and enables its save buttons before the async overlay that decides the real
roster has landed. `IdeaInputPage` has the identical shape (its own copy of the override effect, `:1116-1321`, and of
the roster derivation, `:1343-1410`) and gates on emptiness only.

### Why this host's existing gate does not protect it

`pipelineAgents.length === 0` closes the EMPTY window (library not loaded and no manifest agents). It was added so a
failed manifest fetch does not leave a runnable-looking empty screen (`:1108-1114`, ISS-374/ISS-375). It says nothing
about whether the override overlay has arrived, and in the window that matters the roster is NOT empty: it is the
library roster. That is the same split [ISS-284](20260828-1906-ISS-284.md) records for LaunchWizard: an empty roster
is rejected by the server (`agent_ids: list[str] = Field(min_length=1)`, `user_workflows.py:213`), a non-empty default
roster is accepted and written.

### What would settle it

- Browser, account with an enabled `user_stories` override (create one with "Save as my version" on
  `/create/user_stories` if the account has none; it is test data): `page.route('**/api/workflows/user_stories', hold)`,
  wait until the roster count is non-zero (library loaded), click "Save as my version", capture the POST
  `/api/user-workflows` and ABORT it (never let the write through). If the defect exists the captured body has
  `overrides_pipeline_type: "user_stories"` and `agent_ids` equal to the system roster, not the override's.
- Offline: a vitest in the IdeaInputPage harness (`IdeaInputPage.declaredCapabilities.test.tsx` already mocks
  `getWorkflowDetail`, `:44`) with a hand-held deferred and the library preloaded. Assert the button is disabled while
  the deferred is pending.

### Fix

Same shape as [ISS-284](20260828-1906-ISS-284.md), in this component only (the two hosts do not share a fetch effect):
a settle state set by the `getWorkflowDetail` effect (`:1135-1321`; it already has `loadError`, `:1114`), set on
SUCCESS. Gate "Save as my version" on success and "Save workflow" on not-loading, keeping the existing `length === 0`
and migration terms. Do not set it from a `.finally`: the `.catch` at `:1305-1317` degrades to "nothing declared", so
a failed GET would re-enable the UPSERT on the system roster, the same loss reached through a failed fetch instead of
a slow one.

### Not affected

- `handleRun` (`:1643-1655`) is not a loss path for an override user: whatever `agent_ids` it sends, the server
  resolves the caller's enabled override and replaces the roster (`backend/app/api/run_commands.py` at HEAD 024c03ef8,
  `:3630-3657`).
- `ComposerPage.handleSave` (`ComposerPage.tsx:919`): hardcodes `base_pipeline_type: "custom"` and never sends
  `overrides_pipeline_type`, so it can never UPSERT an override.

## Analysis (QA-KB-059, 2026-10-02, analyzer)

**Verdict.** Real and unfixed in the working tree. The fix belongs in `IdeaInputPage.tsx` only.

### Root cause (CONFIRMED)

One mechanism: `IdeaInputPage` has no state that says "the roster is final", the first roster is the library roster, and three consumers are enabled from the first render.

1. The first roster is the library's. `:1001-1012`: the lazy initialiser returns `LIBRARY_AGENTS.filter(...)` for the type, so on a warm library `pipelineAgents` is non-empty at first paint; on a cold one the roster effect (`:1367-1437`) fills it as soon as the library lands (`seeded = systemRoster`, `:1430-1434`).
2. The real roster arrives later and from elsewhere: `getWorkflowDetail(jwt, workflowId)` (`:1159`), whose `.then` writes `overrideAgents` / `showOverride` / `manifestAgents` (`:1193-1195`, `:1263`) and so makes the roster effect re-seed `pipelineAgents` (its deps, `:1437`). No state says the fetch has settled: `loadError` (`:1138`) records only a failure, and nothing reads it for a non-empty roster.
3. The consumers are gated on emptiness and migration only: "Save workflow" `:1983`, "Save as my version" `:1998`, and "Advanced" (`:2188-2189`) not at all.
4. The handlers read the roster at click time with no readiness check. `handleSaveAsOverride` (`:1773`) sends `agent_ids: pipelineAgents.map(...)` (`:1796`), a `manifest` built from it (`:1799-1803`) and `overrides_pipeline_type: workflowId` (`:1804`).
5. The server replaces the real row: `user_workflows.py:807-847`. `agent_ids` only has to be non-empty (`:214`), the built-in id only has to be supported (`:809`), and there is no version or concurrency check.

### Where the fix belongs

`frontend/src/components/workflow/IdeaInputPage.tsx`, nothing else: the state sits next to `loadError` (`:1138`), is written by the fetch effect (`:1140-1345`), and is read by three consumers (`:1983`, `:1998`, `:2188`). Not `LaunchWizard` (a separate fetch effect, already fixed), not `AgentsPopup` (shared by both hosts), not the backend: UPSERT-by-built-in is the specified behaviour (spec 016), the server cannot know the client was unsettled, and a concurrency token on the POST would be an API-contract change, a product decision this fix does not need.

### The fix, and three corrections to the QA-KB-059 triage sketch

The sketch ("a `detailSettled` state set true in the `.then`, success only") is right about where and wrong in three details:

1. **One boolean cannot express both gates.** The sketch labels the Save workflow gate "not-loading" and the Save as my version gate "success only", but a single flag set only on success gives both the second meaning. That disables "Save workflow" for good after any settled failure, including `migration`, whose GET 404s by design ([ISS-984](20261002-0429-ISS-984.md) has the read). The reverse mistake, a flag set in `.finally` or in both branches with no failure term, re-enables the UPSERT after a failed GET. Use the tri-state `LaunchWizard` already has (`overrideLoad: "loading" | "ready" | "failed"`, `LaunchWizard.tsx:295`; [FIX-701](20261002-0037-FIX-701.md)): "Save workflow" and "Advanced" disabled while `"loading"`, "Save as my version" disabled unless `"ready"` (with a `title` on `"failed"`). Equivalent and no bigger: one `detailSettled` flag set in BOTH `.then` and `.catch`, plus the existing `loadError` ("Save as my version" also needs `loadError === null`).
2. **Write it where the batch is.** Set `"ready"` first thing in the `.then` after the `cancelled` check (`:1161`), `"failed"` inside the `if (!cancelled)` of the `.catch` (`:1332`), and `"loading"` at the top of the effect after the two early returns. Both early returns (`!workflowId` `:1141`, `!jwt` `:1151`) must leave the state not-loading, or Save workflow never enables on a page with no `workflowId` (a lazy initialiser `workflowId ? "loading" : "ready"` also avoids a first-render flash). Do not rely on `.finally`.
3. **Gate Advanced too** ([ISS-983](20261002-0429-ISS-983.md)). Keep the existing `length === 0` and migration terms on the two Save buttons.

One caveat for the fixer: unlike `LaunchWizard`, where the `.then` writes the override roster directly, here the override roster reaches `pipelineAgents` through the roster effect, one commit after the render that carries the settle write. For that one commit "ready" and the pre-overlay roster coexist. It is practically unreachable by a click, but a test must `await` the enabled state rather than click on the same tick.
