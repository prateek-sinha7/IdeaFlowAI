## What was wrong (ISS-735)

**The seed path.** Every revision launch goes through one function:

- the REST `create_revision` path (`run_commands.py:5204`)
- `CHANNEL_REVISION` in `post_message` (`:1643`)
- the Concierge revision disposal (`:1899`)

All three call `_drive_revision_to_queue`, which calls
`ExecutionEngine._handle_revision` (`engine.py:11915`). That is where the revision's
seed is composed. It read these parent sources:

- the artifact ref, via the FR-014 chain: exact kind, then `deliverable`, then `summary`
- the version history
- `planning_context`, which is diagnostic only

It never read the parent's `WorkflowRun` row. So a parent that ended degraded seeded
exactly like a clean one. A degraded launch run is persisted with `status="degraded"`,
and the launch driver writes the reason to `WorkflowRun.error`
(`run_commands.py:3997`: `first_agent_error_msg or degraded_reason_msg or …`). The
compensation signals that write that reason are FIX-612, FIX-615 and FIX-634.

For `custom_revision` this block is the revision's **only** seed. The
`previous_run` provider does nothing for this pipeline:
`custom_revision/workflow.yaml` does not declare `revises_existing`, so
`is_revision_workflow` is False. `test_custom_workflow_migration_v3.py`'s module
docstring records the same.

**Seen before the change, not assumed.** The ISS-735 test was rewritten first and run
with `--runxfail` against the unchanged engine. Result: `1 failed, 4 passed`. The one
failure was ISS-735, and its seed was the bare three-section block:
`'=== ORIGINAL ARTIFACT (type: custom_output) ===\n# Report\n=== END ORIGINAL ARTIFACT ===\n\n=== VERSION HISTORY ===\n1 version(s) exist for this artifact.\n=== END VERSION HISTORY ===\n\n=== REVISION INSTRUCTION ===\nTighten the summary\n=== END REVISION INSTRUCTION ==='`.
The parent's `degraded` status was not in it.

## What changed and why there

One hunk: `backend/agents/execution_engine/engine.py:12064-12084`. It sits directly
after `revision_context` is composed.

```python
try:
    _parent_row = await ScopedStore(
        owner_id=owner_id, workspace_id=original.workspace_id
    ).get_run(parent_run_id)
except Exception:  # noqa: BLE001 — best-effort read, never block a revision
    _parent_row = None
if getattr(_parent_row, "status", None) == "degraded":
    revision_context += (
        "\n\n=== PARENT RUN STATUS ===\n"
        "The original run completed degraded: "
        f"{getattr(_parent_row, 'error', None) or 'no reason recorded'}\n"
        "=== END PARENT RUN STATUS ==="
    )
```

- **Why `_handle_revision`.** It is the one seam all three launch paths reach, so
  one read covers every revision pipeline. There is no `pipeline_type` branch, which
  keeps SC-001.
- **Why the `WorkflowRun` row.** Decision 2a names the parent's existing
  `status` / `degraded_reason`. `WorkflowRun.status` is the reconciled terminal
  status, and `run_commands.py:769` re-derives it across resumes.
  `WorkflowRun.error` is where the launch driver puts `degraded_reason`.
- **Why this workspace.** `original.workspace_id` is the parent run's workspace. The
  parent's `deliverable` ref is written by its own terminal block through
  `_dual_write_artifact` (`engine.py:7241-7249`). The run row is stamped with that
  same workspace by `set_run_scope`.
- **Why append, not prepend.** Every revision pipeline is `planner: skip`, so
  `_default_planning_context` builds `inferred_intent` from `user_message[:200]`. The
  removed world-block comment below this hunk records how a prepended block once
  corrupted `PLANNER.md`.
- **Ownership.** The read runs after `store.assert_owns(parent_run_id)`. No parent
  data is read before ownership is confirmed (L16).

Not touched: the `WorkflowRun` model, alembic (head still `0047_run_manifest_json.py`),
the `previous_run` provider, the frontend, and every agent prompt.

## Known ceiling (accepted by the decisions, stated rather than hidden)

- **FIX-634's zero-coverage signal needs a final step that declares `consumes`.** The
  base `custom` manifest declares none. So a validator on a consumes-less custom
  workflow that regenerates the whole deliverable is not flagged at run level. Option
  (a) of decision 1 names this consequence: "a validator can still pass a step whose
  real input never arrived".
- **A degraded revision parent has no `WorkflowRun.error`.** `_drive_revision_to_queue`
  never writes one. So its flag reads "no reason recorded". Filed as
  [ISS-857](20260923-0148-ISS-857.md).
