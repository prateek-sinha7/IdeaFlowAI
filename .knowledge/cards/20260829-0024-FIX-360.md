## What was wrong

Six of the eight global hooks rendered a "Compatible agents" section on
`/library/hooks/<hookId>` listing agent ids that exist nowhere in the app's
94-agent roster — `html-prototype-builder`, `prototype-polisher`,
`ppt-slide-architect`, `requirements-analyst`. The chips are non-interactive
`<div>`s, so a fictional agent was presented to the user as fact with no way
to detect it short of querying `GET /api/agents/library` independently. The
same array also feeds two exact-match suggestion filters in the composer, so
the stale data was not purely cosmetic.

## Root cause

`backend/app/agents/hooks_catalog.py:103` (pre-change) —
`compatible_agents=list(metadata.get("compatible_agents", []))` — copied the
`HOOK.md` YAML frontmatter array into `GlobalHookEntry` verbatim, with no
cross-check against the live roster. `compatible_agents` is hand-authored per
hook and was never updated when those four agents were renamed or retired, so
`backend/hooks/global/{post-design-quality,session-start,stop-console-log,stop-format-typecheck,stop-session-end}/HOOK.md`
still name them. Everything downstream inherits the array unchanged:
`app/api/hooks.py:35` (`asdict`), `frontend/src/hooks/useHooksCatalog.ts:29`,
then `LibraryPage.tsx:441,455` (chips + "How to use" prose),
`CanvasConfigRail.tsx:379` and `AgentsPopup.tsx:593`
(`h.compatible_agents.includes(agent.id)` suggestion filters).

## What changed and why there

One guard in `hooks_catalog.py`, the single function every consumer routes
through — `list_global_hooks()` has exactly one caller (`app/api/hooks.py`),
which serves the one payload all four renderers/filters read. A fix in
`LibraryPage.tsx` would have left both composer filters unguarded; a fix in
the five `HOOK.md` files would have gone stale again on the next agent rename.

- `list_global_hooks()` builds `real_agent_ids` once per scan from
  `agents.registry.get_all_agents_flat()` — the same function the Agents
  library endpoint (`app/api/agents.py:158`) serves from, so "real" cannot
  drift between the two payloads — and passes it into `_load_one`.
- `_load_one(hook_dir, real_agent_ids)` keeps only declared ids present in
  that set, preserving author order, and `logger.warning`s the dropped ones
  per hook so the data rot stays visible in the server log rather than being
  silently swallowed.

Import direction is the sanctioned one: `app.agents` -> `agents.registry`,
already established at `app/api/agents.py:21`. `agents.loader`/`agents.registry`
import only stdlib + `frontmatter`, and nothing under `agents/` imports
`app.agents.hooks_catalog`, so no cycle is introduced. Nothing under
`backend/agents/execution_engine/` was touched and no migration is involved.

Observed effect on the catalog (all 8 hooks still keep at least one valid
agent, so no hook degrades to an empty list): `post-design-quality`
`['app-ux-design']`; `session-start` and `stop-session-end` lose
`requirements-analyst`; `stop-console-log` and `stop-format-typecheck` lose
`html-prototype-builder` / `prototype-polisher`; `post-quality-gate`,
`pre-config-protection`, `pre-gateguard` unchanged.

## Not fixed here (still open, by design)

- [ISS-399](20260828-2308-ISS-399.md) — the composer's "Suggested hooks"
  filter can no longer match a fictional id, but the hook still does not
  suggest for whichever real agent inherited the retired agent's role. Closing
  that gap means deciding a successor mapping (e.g. `html-prototype-builder`
  -> `prototype-build`?, `prototype-polisher` -> `prototype-validate` or
  `prototype-revision-agent`?) and re-pointing the five `HOOK.md` files. That
  is a data/semantics decision, not a loader defect, and it is that card's.
- `backend/app/agents/skills_catalog.py:115` carries the identical unvalidated
  load for skills. Checked, not carded: all 186 catalog skills currently
  resolve cleanly against the same roster (0 stale ids), and R-33 gives skills
  a deliberate "empty means compatible with everything" fallback that hooks do
  not have — so there is no defect to file today, only the same latent shape.
