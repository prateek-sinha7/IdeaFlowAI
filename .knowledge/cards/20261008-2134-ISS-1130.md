# ISS-1130

**Register source:** sibling derived during the `QA-KB-103` analysis on 2026-10-08 (root [ISS-1118](20261008-1444-ISS-1118.md)). Not its own bug row.
It predates [FIX-766](20261008-1444-FIX-766.md): the inline door has compiled at `trust="user"` since [ADR-0016](20260824-1630-ADR-0016.md).
It is NOT part of the QA-KB-103 fix and needs a decision before anyone fixes it.

**Confidence:** INFERRED. The backend half is CONFIRMED by probe: the steps the canvas serializer emits for `prototype` from a manifest-seeded
roster are refused at `trust="user"` with `capability ('compaction', 'html_skeleton') is not user-allowed in step 'prototype-build'`
(`evidence/qa-kb-103/analysis-02`, `analysis-03`), and `launch_run` compiles an inline manifest at exactly that trust. The UI half was read, not
driven. What would settle it: open a built-in on the Composer canvas (`/workflows/prototype/canvas`), change the roster so it is no longer the
built-in's own (remove or reorder a step, so `unmodifiedBuiltin` at `ComposerPage.tsx:1193-1197` is false), press Run once on an unsaved
composition, and read the 422 body. Expect `invalid_workflow_manifest` naming `compaction`/`html_skeleton`. `needsFullManifest` already holds for
`prototype`, because `prototype-specify` declares `skills: [velocity-design]` in its `workflow.yaml`.

## Condition

- The Composer seeds its roster from a built-in's manifest steps through `manifestStepsToAgents(initialManifestSteps, ...)`
  (`ComposerPage.tsx:315-316`), so every step keeps its `extra` (`userWorkflows.ts:734`).
- An UNMODIFIED built-in launches as itself and never sends a manifest (`ComposerPage.tsx:1189-1199`).
- Once the roster differs from the built-in's own, the launch goes on to `needsFullManifest(pipelineAgents, runConfig)` (`ComposerPage.tsx:57-70`:
  a declared context provider, a custom agent, a prompt, a skill, a sub-agent tree or a route), and when that holds it carries either
  `user_workflow_id` (a saved row, compiled at `trust="db"`) or, for an unsaved composition, the tree inline:
  `manifest: { steps: agentsToManifestSteps(pipelineAgents, selections) }` (`ComposerPage.tsx:1140-1151`). The comment there says this
  "Compiles at trust="user" server-side — stricter than a saved row's trust="db" — so privileged grants are still refused."
- Server side an inline manifest is `_inline`, hence `_trust = "user"` (`run_commands.py:3361-3369`), compiled at `:3403-3407`.
- The built-in's own `compaction: html_skeleton` (prototype, prototype_feature_revision, prototype_large_revision) and `post_step`
  (app_builder, prototype_revision and the two revisions above) are registered `user_allowed=False`, and the canvas sends them back because
  the round trip is lossless on purpose (`00b61ff93`).

The saved-copy door is fine: "Save as copy" compiles at `trust="db"` and answers 201 (the validator's note on [ISS-1118](20261008-1444-ISS-1118.md)).
So the same composition runs after Save as copy and is refused when run inline.

## Expected vs actual

Expected: editing a built-in lightly on the canvas and pressing Run once runs it. Actual (INFERRED): the run is refused with
`invalid_workflow_manifest`, with no hint that the cause is the built-in's own engineer-only reference.

## Why the root cause implies it

Same mechanism as [ISS-1118](20261008-1444-ISS-1118.md): a `trust="user"` compile with no baseline, fed by the lossless client round trip. The
door is different (a run instead of a save) and so is the missing piece: an inline manifest carries no built-in identity (the Composer's base is
`custom`), so there is nothing to compare against.

## Decision needed (not for the QA-KB-103 fix)

Should an inline launch of an edited built-in be allowed to carry that built-in's own engineer-only references? If yes, the request must name the
built-in it was seeded from so the server can reuse the baseline decision of [ISS-1118](20261008-1444-ISS-1118.md). If no, the canvas should say
"Save as copy first" instead of surfacing the compiler text. The 422 is the safe default and nothing here is a security gap.
