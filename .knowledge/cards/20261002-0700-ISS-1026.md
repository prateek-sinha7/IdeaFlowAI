## What happened

INFERRED sibling of [ISS-941](20261001-2240-ISS-941.md) (QA-KB-084). Not reproduced in a browser.

Found while mapping every consumer of the `run-version` screen for the ISS-941 blast radius. ISS-941's own defect is
the arity guard in `routes.ts`; this one is a different mechanism in a different file. It is filed separately because
a fix to ISS-941 in `parseViewPath` does not touch it, and because both come from one design choice in the ISS-230
lift ([FIX-328](20260828-2014-FIX-328.md)): the bare pinned form `/runs/{id}/versions/{v}` was left as its own
`run-version` screen ("still resolves to `run-version`, unchanged"), instead of `run-detail` plus a `version`.
Every branch that keys on `run-detail` therefore misses its pinned twin.

## Condition, expected, actual

Condition: a completed run is pinned to a version and showing the Preview tab at `/runs/{id}/versions/{v}`. The user
clicks Steps (the URL becomes `/runs/{id}/versions/{v}/steps` through a shallow `window.history.pushState`), then
presses the browser Back button.

Expected: the URL returns to `/runs/{id}/versions/{v}` and the Preview tab is selected again, exactly as the
un-pinned pair does (`/runs/{id}/steps` then Back to `/runs/{id}` re-opens Preview).

Actual (by source read, INFERRED as behaviour): the URL returns to `/runs/{id}/versions/{v}`, which parses to
`run-version`, and no tab is requested, so the panel stays on Steps under a Preview URL.

## Root cause (CONFIRMED by source read; the behaviour is INFERRED)

1. The Preview tab's URL is the `run-version` form. `DashboardLayout.tsx:530` builds
   `"preview": routes.runDetail(contentSourceRunId, pin)`, and `routes.runDetail(id, version)`
   (`routes.ts:92-93`) returns `/runs/${id}/versions/${version}` when a pin is set. Executed against the working-tree
   `routes.ts` (node 22.23.1, `--experimental-strip-types`, scratch script outside the repo):
   `parseViewPath(['runs','r1','versions','2'])` is `{"screen":"run-version","runId":"r1","version":"2"}`.
2. The tab shortcut sits in the tracked-run branch of the T7 effect, `frontend/src/app/[...view]/page.tsx:3474-3490`.
   That branch is where a tab click and the Back/forward after it land, because the shallow `pushState` causes no
   remount (the `runTabShallowNav.test.ts` case "the already-tracked run branch still applies the URL's tab" pins
   this):

   ```ts
   const openTab = reopenTabFor(parsedView.screen)
     ?? (parsedView.screen === "run-detail" ? "preview" : undefined);
   if (openTab) runTabDeepLink.requestOpenTab(openTab, deepLinkAgentIdFor(parsedView));
   return;
   ```

   `reopenTabFor` (`page.tsx:274-292`) has cases for `run-preview-full`, `run-steps`, `run-steps-agent`, `run-files`,
   `run-workspace` and `run-audit`. It has none for `run-version`, and the `?? ... "run-detail"` fallback does not
   name it either, so `openTab` is `undefined` and nothing is requested. `run-version` appears in `page.tsx` only at
   `:175` (`initialMainViewFor`), `:216` (`reopenedRunIdFor`) and in two comments.
3. Nothing else moves the tab. `PreviewPanel` changes tab only on a fresh deep-link nonce or a state-derived default
   (`PreviewPanel.tsx:1262-1297`), never derives its tab from the pathname (its only `window.location` use is the
   share-link builder at `:1345`), and there is no `popstate` handler in application code (grep over `frontend/src`).

Why this follows from [ISS-941](20261001-2240-ISS-941.md)'s analysis: the `run-version` screen is the one the broken
arity guard returns, and listing its consumers shows three of four page-level selectors handle it
(`initialMainViewFor`, `reopenedRunIdFor`, `pinnedVersionFor`) while the tab selector does not. The cold-open
comment at `page.tsx:263-266` says `run-detail` and `run-version` both "use the panel's default", which is true for a
cold open and is why `reopenTabFor` correctly returns `undefined` for both. The warm branch at `:3486-3487` was
written later for the shallow-nav case and named only `run-detail`.

## Fix direction (not applied)

In `page.tsx` only, in the tracked-run branch: extend the fallback to
`parsedView.screen === "run-detail" || parsedView.screen === "run-version" ? "preview" : undefined`. Do NOT add
`run-version` to `reopenTabFor`: a cold open of a still-building run must keep its state-derived Steps default (the
comment at `page.tsx:3483-3485`). Keep the two strings `runTabShallowNav.test.ts` pins in that branch,
`reopenTabFor(parsedView.screen)` and `runTabDeepLink.requestOpenTab(openTab, deepLinkAgentIdFor(parsedView))`.
Independent of [ISS-941](20261001-2240-ISS-941.md)'s fix: the two can land in either order.
