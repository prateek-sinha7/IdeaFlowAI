# ISS-773

## Description

INFERRED sibling of [ISS-730](20260922-1343-ISS-730.md) (bug QA-PS-028's root card) — not
reproduced live. Filed because the root cause implies it, not because it was observed. Mirrors
the shape [ISS-735](20260922-1355-ISS-735.md) already established for `custom_revision` and
QA-PS-021, applied here to a different pipeline and a different trigger (QA-PS-028's
silent-content-drop, not QA-PS-021's missing-`write_files` compensation).

`backend/agents/registry.py:147` declares `REVISION_BASE_MAP["user_stories_revision"] =
"user_stories"`, and `backend/agents/workflows/user_stories_revision/` is a real, reachable
manifest (`user_launchable: false`, `is_beta: true` — reachable "from the generic chat-lane
revision channel", per its own comment, read in full). Its single step,
`user-story-revision-agent` (`backend/agents/prompts/user-story-revision-agent/AGENT.md`, read
in full), states directly: "The backlog under revision is seeded into your sandbox as
`user_stories.md` — read it with `read_file` before making any changes," and its contract is
explicit: "PRESERVE every other epic, story, acceptance criterion, story point, and priority
exactly as-is" and "Update the Backlog Summary section at the end with correct totals."

If the parent `user_stories` run's `backlog-compiler` step silently dropped an epic (this
bug), the seeded `user_stories.md` is already short one epic before the revision agent ever
reads it. The revision agent has no way to know an epic used to exist — it faithfully
"preserves" the gap (nothing to preserve, from its point of view) and recomputes the Backlog
Summary totals against the already-incomplete document, so the totals stay internally
consistent while the drop compounds one generation forward with zero new signal at the
revision layer either.

## Why the root cause implies this

Identical shape to [ISS-735](20260922-1355-ISS-735.md)'s already-established finding for
`custom_revision`: a revision pipeline seeds from the parent run's persisted deliverable and
nothing in the engine marks that deliverable as compensated/incomplete
(`_pipeline_complete_data`'s only signals are the exception/budget/commit set ISS-730 and
ISS-721 already confirm carry no content awareness). `user_stories_revision` is reached by the
SAME registry mechanism ISS-735 cites for `custom_revision` (`REVISION_BASE_MAP`), just a
different base pipeline — the propagation mechanism does not care which pipeline produced the
seed, only that nothing flags it as incomplete.

## What would confirm or refute this

Not reproduced — this card is the hypothesis, not the observation. To settle it: complete a
`user_stories` run known to have hit QA-PS-028 (or force the condition), launch a
`user_stories_revision` against it via `parent_run_id`/the chat-lane revision channel, and
inspect the revision agent's seeded `user_stories.md` for the missing epic, then confirm the
revision run's own Backlog Summary total is recomputed against the already-short document with
no warning anywhere in the run.

## Fix

No new engine mechanism needed beyond [ISS-730](20260922-1343-ISS-730.md)'s own fix
direction: a content-completeness signal at the parent run's completion (in `_execute_impl`'s
shared gate, `engine.py:7376-7457`) that correctly marks a truncated `backlog-compiler` output
as `degraded` would, by extension, give `user_stories_revision`'s seed step something real to
check (a degraded parent) before launch — today there is nothing to check because the parent
never gets marked degraded in the first place.
