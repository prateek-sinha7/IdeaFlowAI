# ISS-347

## Description

Found while fixing [ISS-218](20260828-1700-ISS-218.md) / [ISS-235](20260828-1830-ISS-235.md);
recorded, not fixed — it is the same "a leftover value outranks the run's own
brief" shape as ISS-235, one layer down, in the wizard rather than in
`DashboardLayout`.

`LaunchWizard`'s restore effect (`frontend/src/components/workflow/LaunchWizard.tsx:277-322`)
reads the two hand-off channels in a fixed order and **returns** on the first:

```ts
const chainBrief = sessionStorage.getItem("chain.brief");
if (chainBrief) {
  setBrief(chainBrief);
  sessionStorage.removeItem("chain.brief");
  sessionStorage.removeItem("chain.from");
  return;                       // <- ppt.draft / prototype.draft never read
}
const draftKey = initialMode === "prototype" ? "prototype.draft" : "ppt.draft";
```

`chain.brief` is written by `handleChainPipeline`
(`frontend/src/components/layout/DashboardLayout.tsx:1760`, `:1864`) immediately
before its own `router.push(wizardPath)`, so it is normally consumed on the very
next mount. If that mount does not happen — the push is abandoned, the user
navigates away first, a tab is left open — the key survives for the rest of the
tab's session, and the NEXT wizard open shows that chained brief plus the
"Continuing from your … — your brief is pre-filled" banner
(`LaunchWizard.tsx:890`) regardless of what the caller staged.

That includes the draft [FIX-331](20260828-2056-FIX-331.md) now writes for
"Edit brief & run again", and the one `handleLaunchSaved` has always written
(`DashboardLayout.tsx:1542`, `:1569`) for a saved ppt/prototype workflow.
`chain.context_block` is worse-behaved still: it is read at launch time
(`LaunchWizard.tsx:760-765`) and appended to the brief whether or not
`isChaining` is set, so a stale one silently rides into an unrelated run.

Not reproduced live — the trigger needs an abandoned chain push. Recorded as
INFERRED, the same standing ISS-235 carried.

## Expected vs Actual

- **Expected:** a caller that stages a brief for the wizard gets that brief;
  a chain hand-off applies only to the navigation that wrote it.
- **Actual:** any unconsumed `chain.brief` wins over every later hand-off, and
  an unconsumed `chain.context_block` is appended to whatever runs next.

## Disposition

Open, deferred — deliberately out of FIX-331's scope, which was scoped to
`handleEditBrief`. Fixing it belongs on the wizard side (the reader), not in
each caller: the hand-off wants to be scoped to one navigation, e.g. stamped
with the target mode and dropped when it does not match, rather than read as
ambient session state.

### Root cause

One mechanism: the wizard reads `chain.*` sessionStorage as ambient state with no tie to the
navigation that wrote it, and the restore effect gives it precedence over the caller's draft and
`return`s. Two effects consume it independently — pickup (`:372-395`: `chain.from`,
`chain.v2.source_status`) then restore (`:403-450`: `chain.brief`, then the draft) — in that
order.

### Where the fix belongs

The wizard — the one reader — as the Disposition says; not the seven writers. Four traps the
fixer will otherwise hit:

1. **`chain.from` is armed before the restore effect can see the draft.** A fix confined to
   `:404-414` (the sketch in BUGS.md) removes storage keys but cannot disarm `isChaining`, which
   the pickup effect already set from `chain.from` (the key it would remove is long gone). R2 is
   that state — draft applied, `chain.from` armed: `{"briefEditorVisible":false,
   "continuingBanner":true}`, so the user still cannot see the brief they came to edit (the key
   removal would defuse only the stale `sourceRunId`). Decide once, before either `setChainFrom`
   or `setBrief`: if a draft exists for this mode it wins and `setChainFrom` /
   `setChainSourceStatus` are never called.
2. **Clear unconditionally once decided.** `if (chainBrief)` (`:407`) is false for `""`, which
   `handleChainPipeline` can write (`cleanBrief = rawBrief || ctxBriefFallback`, `:1940-1941`); a
   truthiness-guarded cleanup leaves that key behind.
3. **The restore effect is re-entrant by design** (`:450` deps include `libraryAgents`, the T29
   cold-mount fix). R5: with the agent library arriving late, the first run applies the chain
   brief and strands the draft, the re-run applies the draft — same inputs, different outcome by
   timing, while `chain.from` stays armed. The decision must be latched (ref) or idempotent
   across re-runs.
4. **Keep the constraints that bound this code:** [FIX-331](20260828-2056-FIX-331.md)'s locked
   constraint (the seeded brief is always the VIEWED run's own), the FIX-005 one-shot draft
   ([FIX-005](20260616-FIX-005.md)), and the [BUG-014](20260716-2156-BUG-014-GROUNDED-CONTEXT.md)
   guard — a genuine chain still threads its source id (R6, green control). SC-001 / INV-1: the
   wizard is keyed on `mode` data; no workflow-name branch.

The second clause of "Expected" ("a chain hand-off applies only to the navigation that wrote
it") is met only by scoping both channels, not by precedence: see
[ISS-1001](20261002-0500-ISS-1001.md). "Draft wins + drop all chain keys + do not arm
`chainFrom`" closes the reported bug; ISS-1001 is the open design decision beyond it.

## Resolution: FIX-723 (2026-10-07)

Resolved by [FIX-723](20261007-1810-FIX-723.md) in `LaunchWizard.tsx` only, following "Where the fix belongs" above.

- **The decision moved into the pickup effect** (`:403-410`), ahead of `setChainFrom`. A present `<mode>.draft`
  (`draftKeyFor`, `:86`, which the restore effect also reads) removes `chain.from`, `chain.brief`,
  `chain.source_run_id` and `chain.v2.source_status`, whatever their value.
- **The restore effect** consumes an empty `chain.brief` too (`:438`).
- **Tests.** `LaunchWizard.chain.test.tsx` ISS-347 case: the it.fails body now passes. Proof cases R0-R6 in
  `evidence/qa-kb-062/`: 8 passed (before: 3 failed, 5 passed). R6, a genuine chain, still threads `run-42`.
- **Still open: ISS-1001.** The draft-less open (B1, R4 unchanged) and a stranded draft outranking a genuine chain (B2)
  stay with [ISS-1001](20261002-0500-ISS-1001.md).
