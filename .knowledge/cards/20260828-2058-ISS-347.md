# ISS-347

## Description

Found while fixing [ISS-218](20260828-1700-ISS-218.md) / [ISS-235](20260828-1830-ISS-235.md);
recorded, not fixed — it is the same "a leftover value outranks the run's own
brief" shape as ISS-235, one layer down, in the wizard rather than in
`DashboardLayout`.

`LaunchWizard`'s restore effect (`frontend/src/components/workflow/LaunchWizard.tsx:277-322`)
reads the two hand-off channels in a fixed order and **returns** on the first:

```ts
const chainBrief = sessionStorage.getItem("chain.brief");
if (chainBrief) {
  setBrief(chainBrief);
  sessionStorage.removeItem("chain.brief");
  sessionStorage.removeItem("chain.from");
  return;                       // <- ppt.draft / prototype.draft never read
}
const draftKey = initialMode === "prototype" ? "prototype.draft" : "ppt.draft";
```

`chain.brief` is written by `handleChainPipeline`
(`frontend/src/components/layout/DashboardLayout.tsx:1760`, `:1864`) immediately
before its own `router.push(wizardPath)`, so it is normally consumed on the very
next mount. If that mount does not happen — the push is abandoned, the user
navigates away first, a tab is left open — the key survives for the rest of the
tab's session, and the NEXT wizard open shows that chained brief plus the
"Continuing from your … — your brief is pre-filled" banner
(`LaunchWizard.tsx:890`) regardless of what the caller staged.

That includes the draft [FIX-331](20260828-2056-FIX-331.md) now writes for
"Edit brief & run again", and the one `handleLaunchSaved` has always written
(`DashboardLayout.tsx:1542`, `:1569`) for a saved ppt/prototype workflow.
`chain.context_block` is worse-behaved still: it is read at launch time
(`LaunchWizard.tsx:760-765`) and appended to the brief whether or not
`isChaining` is set, so a stale one silently rides into an unrelated run.

Not reproduced live — the trigger needs an abandoned chain push. Recorded as
INFERRED, the same standing ISS-235 carried.

## Expected vs Actual

- **Expected:** a caller that stages a brief for the wizard gets that brief;
  a chain hand-off applies only to the navigation that wrote it.
- **Actual:** any unconsumed `chain.brief` wins over every later hand-off, and
  an unconsumed `chain.context_block` is appended to whatever runs next.

## Disposition

Open, deferred — deliberately out of FIX-331's scope, which was scoped to
`handleEditBrief`. Fixing it belongs on the wizard side (the reader), not in
each caller: the hand-off wants to be scoped to one navigation, e.g. stamped
with the target mode and dropped when it does not match, rather than read as
ambient session state.
