## What happened

Derived while analysing QA-KB-012 (root card [ISS-348](20260828-2102-ISS-348.md), `/login/<sub-path>`),
alongside the concurrent QA-KB-013 analysis of [ISS-349](20260828-2102-ISS-349.md) (`/admin/<sub-path>`).
None of [ISS-238](20260828-1633-ISS-238.md), [FIX-344](20260828-2046-FIX-344.md),
[ISS-350](20260828-2102-ISS-350.md) / [FIX-462](20260901-2100-FIX-462.md), ISS-348 or ISS-349 lists the
`dashboard` head. With `register` (FIX-344) and `analytics` (FIX-462) guarded, the single-segment heads
still unguarded in `parseViewPath` are exactly `login` (ISS-348), `admin` (ISS-349) and `dashboard`
(this card).

INFERRED as a live defect: the parser result below was EXECUTED, but no render of `/dashboard/<x>` has
been reproduced in a browser.

## Root cause (CONFIRMED by source read and by running the parser)

`frontend/src/lib/routes.ts:274-276`:

```ts
if (head === 'dashboard') {
  return { screen: 'home' };
}
```

It matches `segments[0] === 'dashboard'` alone, with no `segments.length === 1`. Executed against the
current `routes.ts` (Node type-stripping, scratch script outside the repo, 2026-10-01):

| input | `parseViewPath` result |
|---|---|
| `['dashboard']` | `{"screen":"home"}` |
| `['dashboard','anything']` | `{"screen":"home"}` |
| `['register','anything']` (control, fixed by FIX-344) | `{"screen":"unknown"}` |
| `['analytics','anything']` (control, fixed by FIX-462) | `{"screen":"unknown"}` |

Unlike `login` / `admin`, a `home` descriptor IS rendered: `initialMainViewFor` has `case "home": return
"home";` (`frontend/src/app/[...view]/page.tsx:135-136`), so `DashboardLayout` mounts on its Home view.
There is no `app/dashboard/` folder (app tree listing: only `[...view]`, `admin`, `forgot-password`,
`handoff`, `login`, `preview-fullscreen`, `settings/security`, `workflow`), so the exact `/dashboard` is
itself served by the `[...view]` catch-all. The symptom is therefore the ISS-350 shape, not the
ISS-348 shape: the REAL Home dashboard renders under a bogus `/dashboard/<sub-path>` URL.

Nothing in the repo builds a `/dashboard/<x>` URL. `routes.home()` and `routes.dashboard()` return only
`'/dashboard'` (`routes.ts`, "Home & creation" builders), and a grep of `frontend/src`, `backend` and
`tests` for `/dashboard/<x>` string literals finds none. It is reachable only by a typed or shared URL,
or by the post-login `?redirect=` replay (`lib/authRedirect.ts` `buildLoginRedirect` stamps whatever
path the visitor was on).

## Expected vs actual

- **Expected:** an authenticated user at `/dashboard/<sub-path>` gets the not-found page
  (`page.tsx` `if (parsedView.screen === "unknown") { notFound(); }`, working-tree line 4044), as
  `/register/<x>` and `/analytics/<x>` now do.
- **Actual (INFERRED):** the address bar stays on `/dashboard/<sub-path>` and the Home dashboard
  renders underneath it, a URL and content mismatch per [ADR-0018](20260824-1631-ADR-0018.md).

## Why the root cause implies this

Same defect as ISS-348 / ISS-349: a `head`-only match in `parseViewPath` with no depth guard. ISS-348's
root cause is not specific to `login`; this branch has the identical shape, 18 lines below it.
