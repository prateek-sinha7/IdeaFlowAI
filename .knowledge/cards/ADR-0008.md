# ADR-0008: Whoever composed the run owns its roster

## Context and Problem Statement

ADR-0003 replaced two rosters with one: `agents` is rebuilt from `compiled.steps`
whenever the plan is non-empty. That framing counted two sources — the registry and
the plan — and concluded the plan should win.

There is a third, and it exists in no file. `run_commands.py:1642-1653`:

```python
if agent_ids:
    allowed_ids = allowed_custom_agent_ids(base_pipeline_type)
    ...
    agents = [load_agent_spec(aid) for aid in agent_ids]   # the user's picks
else:
    agents = get_pipeline_agents(base_pipeline_type)       # registry membership
```

`custom/workflow.yaml` declares 9 fixed steps. A user who selects 3 agents in the
composer sends `agent_ids` with 3 entries; the engine then overwrote `agents` with all 9
from the manifest. `_apply_selections` is called at `engine.py:1505` with
`[s.id for s in agents]` — the already-clobbered list — so it could not recover the
selection either. **The run executed 9 agents. The user asked for 3.**

Not caught by any test: `test_compiled_plan_runs.py` asserts the started agents equal
`compiled.steps`, which is tautological once the roster is built from `compiled.steps`.

Saved/composer workflows going through `user_workflows.py` are unaffected —
`synthesize_manifest(base_pipeline_type, agent_ids, …)` builds a per-selection manifest,
so the plan already equals the user's choice before the engine sees it. The revision path
takes no `agent_ids`. So the blast radius is launches against a *fixed* manifest that
also accept `agent_ids` — `custom` in practice.

## Considered Options

1. **Pass a flag** from the caller (`roster_is_user_composed=True`) and branch on it.
2. **Have `run_commands` synthesize a filtered manifest** for `custom`, the way
   `user_workflows` already does, so the plan equals the selection.
3. **Only fill the roster from the plan when the caller supplied none** —
   `if compiled.steps and not agents`.

## Decision Outcome

**Option 3.**

```python
if compiled.steps and not agents:
    agents = [load_agent_spec(s.agent_id) for s in compiled.steps]
```

The rule this encodes: **whoever composed this run owns its roster.**

| who composed it | roster |
| --- | --- |
| the caller — composer picks, or registry membership | the caller's list |
| the manifest — steps are template instances with no `AGENT.md` | `compiled.steps` |
| nobody — `reverse_engineer`, empty plan | empty |

`not agents` is the discriminator because it is a property of the *request*, not of the
workflow: a caller that has a roster passes one, and only a workflow the registry cannot
describe arrives with an empty list. No pipeline-type branch, no name list.

Option 1 was rejected as a redundant channel — the emptiness of `agents` already carries
the signal. Option 2 is the better long-term shape and is where `user_workflows` already
is; it was not taken here because it moves composition into the launch path, a larger
change than the bug warrants, and it can land later without invalidating this one.

## Consequences

**Positive.** The composer works again. Composed workflows still run: for
`sample_subagents` the registry returns `[]`, so the plan fills in exactly as ADR-0003
intended. The 14 file-backed pipelines are unaffected either way — their caller-supplied
registry roster is provably identical to the plan.

**Negative — ADR-0003's headline claim is now weaker than it reads.** "The compiled plan
is the single source of the run's agent roster" is true only when the caller has no
roster. In practice the caller always has one for file-backed pipelines, so the plan is
consulted only for template-instance workflows. ADR-0003's reasoning stands; its wording
overstates the outcome, and this ADR is the correction.

**Negative — one drift risk returns.** If a file-backed manifest and the registry ever
diverge, the engine now follows the caller (registry), not the plan. ADR-0003 already
removed the assertion that would have caught that, so the recommended runtime drift
warning becomes more valuable, not less.

**Neutral.** `_apply_selections` still receives `[s.id for s in agents]`, which is now the
user's list on the composer path — which is what it always expected.

## Confirmation

`tests/agents/test_compiled_plan_runs.py` — 16 passed after the change, including
`sample_subagents`, which now genuinely drives `execute()` end to end and proves the
plan-fills-in path still works.

The 17 golden characterization and wire-parity tests pass unchanged, confirming the 14
file-backed pipelines are byte-identical.

**Gap:** there is still no test for the bug itself — a `custom` launch with a
user-selected subset asserting that exactly those agents start. That test is the one that
would have caught this and should exist before the composer path changes again.
