## Symptom

A `ppt` run displayed the header **"USER STORIES"** with a `user-stories.md` run summary. Worse,
clicking the **Steps** tab on a run parked at `waiting_for_user` wiped the clarify panel — leaving
the run **unanswerable from the UI**, permanently.

## Root cause

Two separate remount paths, same mistake — refs re-seeded, data not.

1. **Tab routes** (`/runs/{id}/steps|files|audit`). The effect's `liveRunIds` branch set
   `activelyBuildingRunIdRef` / `trackedRunIdRef` and `return`ed, on the assumption that
   "subsequent live frames rebuild pipelineState". True for a streaming run; **false for one
   parked at `waiting_for_user`**, which emits nothing — its `questionnaire_ready` already fired
   before the click.

2. **The launch path.** `onStartPipeline` deliberately clears `contentSourceRunType` (a new run
   must not inherit the previous renderer) and nothing on that path ever set it again — only
   `handleSelectWorkflowRun` does, which a launch never goes through.

With `contentSourceRunType` null, `PreviewPanel`'s `detectedType` fallback chain ends in
`: "user_stories"`, so any run with no content yet renders as user stories.

## Fix

- Tab-route effect: drop the early `return` and fall through to `handleSelectWorkflowRun`. Safe
  **here specifically** — the launch race that shortcut guarded belongs to `/runs/{id}/stream`,
  which `reopenedRunIdFor` excludes by design, and nothing pushes a tab route at launch time.
- Launch path: persist `run_type:{id}` to sessionStorage beside the existing `run_brief:{id}`, and
  rehydrate it in the stream effect's `liveRunIds` branch.
