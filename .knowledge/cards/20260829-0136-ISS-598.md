## What is suspected

Every reproduction of ISS-383 and the register bug it comes from was scoped to "a completed 'Ppt
V2' run, header status 'Done'" — the wording in both the ledger repro and ISS-383's own
reproduction section. Reading `PreviewPanel.tsx`, the component that mounts `SandboxTab` (and
therefore `CodeView`), shows the Workspace tab's visibility and content are never conditioned on
run status at all:

- `workspaceRunId` (`PreviewPanel.tsx:753`) resolves to
  `viewingVersion?.id ?? pipelineState?.pipelineRunId ?? activeRunId ?? null` — whichever run is
  currently being viewed, full stop.
- The Workspace tab is filtered in/out of `tabsForRun` (`:755`) purely on
  `workspaceRunId ? TAB_CONFIG : TAB_CONFIG.filter(t => t.id !== "workspace")` — truthiness of an
  id, no status check.
- `pipelineState` is confirmed to be the LIVE, in-progress run's state object: `isStillRunning =
  !!(isStreaming || pipelineState?.isRunning)` (`:701`) reads an `isRunning` field directly off it.
  Since `workspaceRunId` falls back to `pipelineState?.pipelineRunId`, the exact same object that
  proves a run `isStillRunning` also supplies the id the Workspace tab mounts on.
- `SandboxTab` (`SandboxTab.tsx:842-849`, confirmed by [ISS-586](20260829-0258-ISS-586.md)'s own
  reading of the same props) takes exactly `runId` and `agentNameById` — no status or
  "is this run still writing" signal reaches it, so `CodeView` cannot special-case a running run
  even if it wanted to.

## Condition

- Launch (or open) a run that is still actively executing (`pipelineState.isRunning === true` /
  `isStreaming === true` on the live path — i.e. the header shows a running/in-progress status,
  not "Done").
- Switch to the Workspace tab while the run is still generating.
- Open any text file the agent has already written and either toggle to Code view or (per
  [ISS-597](20260829-0135-ISS-597.md)) view a markdown file's default Preview containing a fenced
  block.

## Expected vs actual

- **Expected:** same disposition as ISS-383 asks for a completed run — but arguably sharper for a
  still-running one: if the file the user is looking at is one the agent may still be actively
  writing, an editable-looking, unindicated surface is more likely to be mistaken for something
  that matters (e.g. "I can fix this typo before it ships") than on an already-immutable "Done"
  run.
- **Actual (predicted):** identical to ISS-383 — `.cm-content` is `contentEditable === true`, no
  lock icon, no "generating" or "read-only" indication tied to run status, typed edits insert live
  and are silently discarded on navigating away. Nothing in `CodeView` or its two call sites reads
  a status prop, because none is threaded to it.

## Why the root cause implies this

ISS-383's defect is in `CodeView`'s own extensions array (`SandboxTab.tsx:675-701`), which is
built from exactly three props — `code`, `lang`, `fill` — none of which carry run status. A defect
with that shape cannot be scoped to "completed runs only": the component has no way to know the
run is completed, running, or anything else. The register's repro used a `Done` run because that
was the run at hand, not because completion is a precondition of the bug — and `PreviewPanel`'s
own gating (`:753-755`) confirms no status check exists between "a run is being viewed" and "the
Workspace tab, and therefore `CodeView`, is mounted for it."

**Marked INFERRED**: not independently reproduced in a browser (this pass is read-only, and
reproducing it requires timing a check against a run that is still mid-execution rather than a
completed one already sitting in run history). What would confirm it: launch a new run, and while
its header still shows a running/in-progress status, switch to the Workspace tab, open a file the
agent has already written, and check `document.querySelector('.cm-content').isContentEditable`
the same way ISS-383 did on a completed run.

## Where the fix belongs

Same place as ISS-383 and [ISS-597](20260829-0135-ISS-597.md): `CodeView`'s own extension list
(`SandboxTab.tsx:675-701`). Because the defect is status-independent by construction, the fix does
not need a NEW status prop threaded through `PreviewPanel` -> `SandboxTab` -> `CodeView` to close
this sibling — the same guard that closes ISS-383 for a completed run closes it here too, since
`CodeView` behaves identically regardless of which run state reached it. Threading a status prop
would only be needed if the desired disposition is to treat "still generating" differently from
"completed" (e.g. a stronger warning on a live run) — not required for the baseline fix.
