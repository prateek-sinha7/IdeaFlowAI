# ISS-646

## What happened

Sibling of **ISS-645** (root cause of register bug **QA-PS-003**, `BUGS.md#qa-ps-003`),
derived while analyzing that root cause rather than reproduced independently. **Marked
INFERRED** — nobody has yet reproduced this specific card live; the mechanism is
confirmed by reading the source, the user-visible symptom is not yet observed.

## Why the root cause implies this (sibling derivation)

ISS-645 cites `backend/app/agents/chat_narrator.py` `_classify()`, lines 161-169, as the
place the "answered" confirmation text loses round identity:

```python
if etype in _CLARIFY_EVENTS:
    n = data.get("question_count")
    if n is None:
        n = len(data.get("questions", []) or [])
    if etype == "questionnaire_complete":
        text = f"{n} clarifications answered" if n else "Clarifications answered"
    else:
        text = "Before I build, I need to lock a few things down."
    return CARD_CLARIFY, text, f"clarify:{anchor}"
```

That `if/else` is ONE block handling BOTH halves of a clarify round's life-cycle —
`questionnaire_complete` (round answered, ISS-645 / QA-PS-003) and `questionnaire_ready`
(round posed, the `else` branch). The `else` branch returns the literal constant
`"Before I build, I need to lock a few things down."` — no round discriminator either.
`project_milestone_card` persists a `chat_reply` row for `questionnaire_ready` exactly
the same way it does for `questionnaire_complete` (both are members of `_CLARIFY_EVENTS`,
line 50), so a 2+-round run — which `ClarifyEngine.run` supports up to
`MAX_CLARIFICATION_ROUNDS = 3` (`backend/agents/execution_engine/clarify_engine.py:36`) —
would show this SAME "ready" prompt card, byte-identical, once per round in the transcript.
This is the adjacent-state sibling of QA-PS-003: same mechanism, one step earlier in the
same round life-cycle (posed vs. answered).

**This branch is structurally easier to fix than QA-PS-003's own branch, and that
asymmetry matters for the fix:** the `questionnaire_ready` event ALREADY carries a round
number in its payload —

```python
await websocket_send_fn(
    {
        "type": "questionnaire_ready",
        "data": {
            "pipeline_run_id": pipeline_run_id,
            "questions": questions,
            "round": round_num,
            "timestamp": _now_iso(),
        },
    }
)
```
(`backend/agents/execution_engine/clarify_engine.py:294-305`, read in full) — but
`_classify()` never reads `data.get("round")` anywhere in the `_CLARIFY_EVENTS` block. So
this sibling's fix is a pure consumer-side read of a field that already exists. By
contrast, QA-PS-003's own `questionnaire_complete` branch has no `round` key to read in
the first place — `clarify_engine.py`'s `questionnaire_complete` emit (lines 342-352)
sends only `pipeline_run_id`, `responses`, `updated_gate`, `timestamp`. Fixing QA-PS-003
needs both an emitter-side change (add `round`/`round_num` to that payload, mirroring
`questionnaire_ready`) AND the same `_classify()` consumer-side change this sibling needs
— so the two branches should be fixed together, in the same shared function, following
the numbering idiom `_classify()` already uses for `CARD_SPEC_REVISION`
(`f"Revising spec — cycle {attempt}"`, chat_narrator.py:151-159, via `_revision_index()`
reading `spec_revision_attempt`/`revision_index` from `data`).

## Expected vs actual

- **Expected:** round 1's "ready" prompt distinguishable from round 2's (e.g. mentioning
  the round number), matching QA-PS-003's stated expectation for the "answered"
  counterpart.
- **Actual (INFERRED, not yet reproduced live):** every round's ready-prompt card reads
  the identical `"Before I build, I need to lock a few things down."` in the transcript.

## Existing test lock-in (evidence this is a real, deliberate gap, not an oversight)

`backend/tests/unit/test_chat_narrator.py::TestProjection::test_clarify_card_from_questionnaire_ready`
(lines 38-48) asserts this exact fixed string as CORRECT, with a comment: *"KAN-114:
questionnaire_ready narrator text is now the fixed conversational message — the question
count is surfaced by the AwaitingCard in the lane, not duplicated in the chat bubble
text."* — confirming the constant text is intentional (for question COUNT, which KAN-114
had reason to drop) but nobody has since revisited it for round NUMBER, which is a
different discriminator. A fix touching this branch must update this assertion.

The sibling test, `test_clarify_card_from_questionnaire_complete` (lines 50-54), does not
assert on `card["text"]` at all — the QA-PS-003 branch has **zero** existing text
coverage, which is why this shipped unnoticed.

## What would settle this

Reproduce a 2+-round clarify run (same trigger ISS-645's cycle 3 found: submit round 1
with no answers selected so `ClarifyEngine` genuinely fires a second
`questionnaire_ready`) and check the transcript for two identical "Before I build…"
cards — or, cheaper, a unit test asserting
`project_milestone_card({"type": "questionnaire_ready", "data": {"round": 1, ...}})` and
`project_milestone_card({"type": "questionnaire_ready", "data": {"round": 2, ...}})`
produce different `text`.
