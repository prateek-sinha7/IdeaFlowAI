## What was wrong

This is bug report QA-KB-008. It covers two defects in the same branch of the reducer.

- [ISS-136](20260813-0005-ISS-136.md): the `pipeline_reconnected` arm of `handlePipelineMessage`
  decided whether a `live:false` verdict was terminal from its own list,
  `["completed", "failed", "cancelled", "error", "diverted"]` (`frontend/src/hooks/useWorkflow.ts:1505`
  before the change). The list had no `"degraded"`. A `degraded` verdict skipped the terminal
  branch, so `isRunning` stayed `true` and `sessionStorage.active_pipeline_run_id` was never
  cleared.
- [ISS-864](20261001-2103-ISS-864.md): the branch's hand-built patch (`:1515-1531` before the
  change) set `isRunning:false` and nothing else. It never stamped the `failed`, `cancelled` or
  `degraded` marker. As a result, `StepsOverviewSpine` showed a failed run that a reconnect had
  resolved as "Run complete".

## Root cause

[ISS-136](20260813-0005-ISS-136.md) holds the full diagnosis. The arm implemented "what terminal
looks like" by itself twice: once in its status list and once in its state patch. The same file
already has a shared definition for both:

- `TERMINAL_MARKER_BY_STATUS` (`useWorkflow.ts:379-385`). A test pins it equal to page.tsx's
  `REOPEN_TERMINAL_STATUSES`, and its members are the same five as the backend's
  `TERMINAL_RUN_STATUSES` (`backend/agents/execution_engine/engine.py:3393-3399`).
- `applyTerminalStatus` (`:401-469`), which uses `terminalMarkers` (`:388`).

The private list had already drifted once. Spec 014 added `diverted` to it, and nobody ever
added `degraded`.

## Change

One hunk in `frontend/src/hooks/useWorkflow.ts`, inside `case "pipeline_reconnected"` (now
`:1505-1518`):

- The private `TERMINAL_STATUSES` array is gone. The guard is now
  `Object.prototype.hasOwnProperty.call(TERMINAL_MARKER_BY_STATUS, status)`, the same membership
  test `applyTerminalStatus` makes at `:435`.
- The hand-built patch and its comment are replaced by
  `setPipelineState((prev) => applyTerminalStatus(prev, status))`.
- The `sessionStorage` clear and the `return true` did not change. A two-line comment at
  `:1505-1506` names ISS-136, ISS-864 and INV-12, so that a private list does not come back.

No other file was edited. The test file was already written by the test-writer, and its
`it.fails` markers stay in place for the verifier.

## Why there

Both production state containers reach this arm through one reducer, `handlePipelineMessage`
(`useWorkflow.ts:675`):

- `useWorkflow`'s `handleMessage` (`:141`)
- `useRunStateStore.handleFrame` (`frontend/src/hooks/useRunStateStore.ts:584`)

The fixer grepped this again at fix time and found no other non-test caller and no other terminal
list on this path. One edit covers both containers. The arm now uses the same definition as the
live arms (`terminalMarkers`) and the reopen reconcile (`applyTerminalStatus`).

## Behaviour deltas

Every change below is on a path that no production code reaches today. No production code emits
`pipeline_reconnected`. The backend names it only in comments and docstrings
(`backend/app/api/run_stream.py:22,24`). Only unit tests and the e2e mock
(`frontend/e2e/fixtures/mockSse.ts:307-308`) send it. See ISS-136, section "Reachability".

- A `degraded` verdict now resolves: `isRunning` becomes false, `degraded` becomes true, and the
  run id is cleared.
- A `failed`, `cancelled` or `degraded` verdict now stamps its marker.
- On those failure statuses and on `diverted`, agents that are still `running` or `thinking` move
  to `idle`. Before the change they were left as they were. This is what `applyTerminalStatus`
  already does on reopen. `completed` behaves as before: unfinished agents move to `done`.
- `"error"` no longer counts as terminal in this arm. Such a verdict now takes the non-terminal
  path, which keeps the run running and keeps the run id. `"error"` is not a run status anywhere:
  - `WorkflowStatus` (`frontend/src/types/index.ts:405`) does not include it.
  - The backend's `TERMINAL_RUN_STATUSES` (`engine.py:3393-3399`) does not include it.
  - The e2e contract sends only `completed|failed|running|null` (`frontend/e2e/FIXTURE-CONTRACT.md:56`).

  ISS-136 calls `"error"` a phantom member, and its recommended fix drops it. The QA-KB-008 Notes
  say to keep `"error"`, but that advice belonged to the add-one-token fix, which the analyzer
  overruled. `applyTerminalStatus` returns `prev` for any status it does not know. Keeping
  `"error"` would therefore need a second hand-rolled special case, which is the
  private-vocabulary pattern this fix removes.

  ISS-136's "alternative" fix. ISS-136 records that it needs the owner's sign-off. This change
  does not do it.
