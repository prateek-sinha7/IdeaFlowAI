# ISS-957

## What happened

INFERRED sibling of [BUG-024](20260827-BUG-024.md) (QA-KB-049), the adjacent-states case. Not reproduced in a browser.

The report says the run is `generating`. The funnel effect's input is not the run's status. It is
`pipelineState.isRunning`, which the reducer sets from replayed frames:

- `planner_start` sets `isRunning: true` and `pipelineRunId` (`frontend/src/hooks/useWorkflow.ts:1707-1712`)
- `pipeline_start` sets `isRunning: true` and `pipelineRunId` (`useWorkflow.ts:797-799`)
- `pipeline_reconnected` (a live attach) sets `isRunning: true` (`useWorkflow.ts:1496-1500`)

Only a terminal frame clears it, and gate frames do not: the `review_gate_ready` / `review_gate_approved` cases
(`useWorkflow.ts:1191-1199`) only toggle `gateOpen`, and `frontend/src/hooks/useRunStateStore.ts:550-554` documents
that they reach the reducer "for their TIMESTAMPS only ... these cases touch one boolean". So any non-terminal run
whose durable log holds one of the three frames above should redirect: `planning`,
`analyzing`, `revising`, `running` (the statuses in `AUTO_STREAM_STATUSES`,
`frontend/src/providers/RunConnectionProvider.tsx:69-75`) and `waiting_for_user` parked at a review gate or a
clarify round.

Expected: the URL and tab survive in every non-terminal state, the same as BUG-024's Expected.
Actual (INFERRED): `/runs/{id}/stream` with the Steps tab.

The inverse also follows. A terminal run is spared only because its replay ends in `pipeline_complete`,
`pipeline_failed` or `pipeline_cancelled`, or in `reconcileTerminalStatus` (`frontend/src/app/[...view]/page.tsx:3111-3131`),
inside the same synchronous batch, so `isRunning` is already false when React commits (that part is an inference
about batching; the report's own control, "the same URLs work once the run completes", agrees with it). And a
`generating` run whose log has no `planner_start` or `pipeline_start` yet is not redirected at all, which makes the
report's repro racy: `tests/integration/screens/14-run-states.feature.md:222-224` already notes "`generating` is a race
unless you launch and assert immediately".

## Root cause (CONFIRMED by source read; the behaviour is INFERRED)

`frontend/src/components/layout/DashboardLayout.tsx:823` gates the push on `if (pipelineState?.isRunning) {`, and
`:854-856` pushes `routes.runStream(incomingRunId)` with no read of the run's status or of the URL. Status is not an
input to that effect anywhere.

## What settles it

The unit test from [ISS-956](20261002-0316-ISS-956.md) cannot tell states apart, because status is not an input, so one
`isRunning: true` case covers all of them. To confirm the claim in a browser, cold-load `/runs/{id}/audit` for a run
parked at a review gate or clarify round (`waiting_for_user`); the e2e notes at
`tests/integration/screens/14-run-states.feature.md:222-224` say such a run has to be created on purpose.

## Fixed by the root fix?

Yes, and it is the reason the guard must key on the URL and not on `status === "generating"`: a status-keyed fix would
leave every state in this card redirecting.

## Fixed — QA-KB-049 (fixer, 2026-10-02): [FIX-712](20261002-1155-FIX-712.md)

The guard keys on the URL, not on status. It compares `parseViewPath(location.pathname).runId` with
`pipelineState.pipelineRunId`, so every non-terminal state that sets `isRunning` goes through the same check. As this
card predicted, one `isRunning: true` case covers them all: `frontend/src/components/layout/DashboardLayout.bug024.test.tsx`, 12 passed with the fix and 9 failed with
the guard removed. A gate-parked run was not driven in a browser.
