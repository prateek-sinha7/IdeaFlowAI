# ISS-1169

**Register source:** sibling derived during the `QA-KB-109` analysis on 2026-10-09 (root [ISS-1153](20261009-1340-ISS-1153.md)). Not its own bug row. Unlike its siblings this one is a separate mechanism with a separate fix, and it outlives the root's fix: it needs its own change and its own test.

**Confidence:** CONFIRMED offline: `evidence/qa-kb-109/analysis-02-probe-own-row-today.txt`, blocks `[P5]` and `[P5b]`, the real `AdminPage` in jsdom with `PATCH .../tier` rejected as the server does for the admin's own row. Label `"Enterprise"` before; `"Basic"` after the error toast, with the row's server-side tier unchanged; `"Enterprise"` again after the refresh button. Not driven in a live browser.

## Condition

Any `PATCH /api/admin/users/{id}/tier` that fails: the self-change 400 (`admin.py:301-305`), an invalid tier 400 (`:307-312`), a 404, or a 503 when the identity provider is unreachable (`_raise_for`, `:320-323`). The admin's own row is the one case where the failure is certain, so with [ISS-1153](20261009-1340-ISS-1153.md) open it is the first thing an admin sees when they touch their own plan.

## Mechanism (CONFIRMED by reading)

- `TierDropdown.handleSelect` (`page.tsx:73-84`) sets the label first, `setLocalTier(tier); // optimistic update` (`:77`), awaits `onUpdate(userId, tier)` and reverts only in its `catch` (`:80-82`).
- `onUpdate` is `handleUpdateTier` (`:238-249`). It wraps `adminUpdateTier` in its own try/catch, shows `showToast("error", msg)` and returns normally. It never rethrows, so `handleSelect`'s `catch` can never run.
- The only other reset is `useEffect(() => { setLocalTier(currentTier); }, [currentTier])` (`:68`). It fires when the prop changes, and a refused update leaves `users` untouched, so it stays silent. What clears the badge is a remount of the row: the refresh button (`loadUsers` replaces the table with the loading state at `:488-492`, so every row remounts with `localTier` taken from the server's value; `[P5b]`), a page reload, or a search that filters the row out and back (that last route INFERRED, not driven).

The comment at `:81` ("revert on error") records the intent; the error handling one level up defeats it.

## Expected vs actual

Expected: the badge returns to the tier the server holds when the change is refused, as the comment at `:81` says. Actual: the toast says the change was refused, and the badge says the change happened.

## Why the root cause implies it

[ISS-1153](20261009-1340-ISS-1153.md) leaves the own-row tier dropdown live (sibling [ISS-1168](20261009-1621-ISS-1168.md)), and that dropdown is the only control whose refusal is guaranteed. The root's fix removes that path but not the defect: a 503 or 404 on any other row takes the same route.

## Fix direction (INFERRED, not applied)

`handleUpdateTier` rethrows after the toast (or returns a result that `handleSelect` checks), so the existing `catch` reverts. `handleSelect` already catches, so nothing becomes an unhandled rejection. One function in `page.tsx`; no API change.

Resolved by [FIX-779](20261009-1659-FIX-779.md) (5-fixer, 2026-10-09): `handleUpdateTier` rethrows after its error toast, so `TierDropdown.handleSelect`'s existing catch reverts the badge. The test stage left no test for this card; FIX-779 added `frontend/src/app/admin/admin.iss1169.test.tsx` (another user's row, PATCH rejected, real `motion/react`), observed red first (expected `Pro`, received `Basic`), then XPASS after the change. `it.fails` left for the 6-verifier.
