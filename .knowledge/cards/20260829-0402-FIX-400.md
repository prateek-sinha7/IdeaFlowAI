## What was wrong

On the legacy `/workflow` builder, attach and remove were asymmetric.

- Attach (`frontend/src/components/workflow/WorkflowView.tsx:337-340`) pushed the files into
  `attachedFiles` AND appended a literal `[Attached: <names>]` block into `ideaInput`, the
  brief textarea's backing state.
- Remove (`WorkflowView.tsx:388`, pre-fix) did
  `setAttachedFiles((prev) => prev.filter((_, i) => i !== idx))` and nothing else.

So the marker the attach path wrote survived the removal forever: `textarea.value` still read
`[Attached: zz-hunt-test.txt]` with no chip anywhere on the page, and every reader of
`ideaInput` inherited that lie — the "Run Workflow" `disabled` gate stayed enabled for a
phantom attachment ([ISS-345](20260828-1900-ISS-345.md)), and `handleRun` would forward the
same orphaned text as the run brief once `onStartPipeline` is wired
([ISS-579](20260829-0234-ISS-579.md)).

## Root cause

`frontend/src/components/workflow/WorkflowView.tsx:388` (pre-fix) — the chip's remove
`onClick` mutated only one of the two states the attach handler had written together. The two
fields were treated as one linked state in the add direction and as independent state in the
remove direction.

## What changed and why there

Both changes are in `frontend/src/components/workflow/WorkflowView.tsx`:

1. New module-level helper `stripAttachmentMarker(text, filename)` (above `WorkflowView`),
   which rewrites `[Attached: ...]` blocks: it removes the first block-entry equal to
   `filename`, keeps every other name in that block, drops the whole block (and the `\n\n`
   separator that introduced it) when nothing is left, and stops after the first match so a
   file attached twice loses one marker entry per chip removed.
2. The chip's remove `onClick` now runs `setIdeaInput((prev) => stripAttachmentMarker(prev, file.name))`
   next to the existing `attachedFiles` filter.

The fix lands on the **write** site, not on either reader, exactly as
[ISS-579](20260829-0234-ISS-579.md) argued: patching the `disabled` gate alone would leave
`handleRun` forwarding the corrupted text, and patching both readers would leave any future
reader broken. A blanket `/\[Attached:.*\]/` clear was rejected per
[ISS-583](20260829-0234-ISS-583.md) — it would erase the marker for a file that is still
attached when 2+ files are involved.

## Blast radius verified

`grep -rn "\[Attached:" frontend/src` — three sites: the attach handler and this remove handler
in `WorkflowView.tsx`, and `SavedWorkflowsPage.tsx:68`, which only *reads* (strips markers for
display) and is unaffected. `IdeaInputPage.tsx:551 removeFile` (reused by `ComposerPage`,
`AgentsPopup`) already clears both `attachedFiles` and `attachedFileContents` and never injects
a marker into the textarea, so the sibling components were never broken. `WorkflowView`'s only
production mount is `frontend/src/app/workflow/page.tsx`.
