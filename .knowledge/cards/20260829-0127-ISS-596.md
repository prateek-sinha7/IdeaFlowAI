## Condition

`frontend/src/components/preview/PreviewPanel.appBuilderSearch.test.tsx` is the ISS-500
regression test — it drives the real (unmocked) `AppBuilderPreview` through
`PreviewPanel` → `AppBuilderIDEPreview`. After [FIX-394](20260829-0127-FIX-394.md) it is
still red, and the reason is inside the test, not the component.

Its final line is:

```tsx
expect(screen.getByText("app.js")).toBeInTheDocument();
```

The fixture markdown lists `src/app.js` first, so it becomes `files[0]`, and
`AppBuilderPreview`'s mount effect auto-selects `files[0]` and opens it as an editor tab
(`AppBuilderPreview.tsx`, the "Auto-expand top-level folders, select first file" effect).
"app.js" therefore renders twice — once as the tree row, once as the tab label
(`<span class="max-w-[120px] truncate">`) — and `getByText` throws
`Found multiple elements with the text: app.js`.

`AppBuilderPreview.searchFilter.test.tsx` does not hit this: its fixture's `files[0]` is
`index.html`, so the open tab and the searched-for filename differ.

## Expected vs actual

Expected: with FIX-394 applied, the ISS-500 test XPASSes like its four ISS-332/501/502
siblings, proving the fix reaches the embedded-Preview mount path.

Actual: the substantive assertion — `expect(screen.queryByText("styles")).not.toBeInTheDocument()`,
the one that encodes the bug — passes; execution reaches the next line and the ambiguous
`getByText` throws. The test stays "expected fail" for a reason unrelated to the defect it
guards.

## Evidence

Diagnosed on two throwaway copies of the file (both deleted afterwards; the real test was
not modified):

- `it.fails` → `it`: fails with `TestingLibraryElementError: Found multiple elements with
  the text: app.js`, listing the tree `<span class="... text-brand font-medium">` and the
  tab `<span class="max-w-[120px] truncate">`.
- Same copy with only the last line changed to
  `expect(screen.getAllByText("app.js").length).toBeGreaterThan(0)`: **1 passed**.

## What would settle it

Disambiguate the trailing sanity check — `getAllByText("app.js")`, or scope the query to
the sidebar (e.g. `within(...)` on the explorer region) — leaving both the `it.fails`
marker and the `queryByText("styles")` assertion exactly as they are. That is a test edit
and belongs to whoever owns the test, not to the fix: the app behaviour here (an open
editor tab keeps its label while the explorer filters) is correct and no card asks for it
to change.
