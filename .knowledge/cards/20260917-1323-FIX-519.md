## What was wrong

This is register bug **QA-PS-005**. With two or more pipelines running, clicking an entry in
the header's "N Running" dropdown sometimes did nothing: the menu closed and the page stayed
where it was. Sometimes a click opened a different run instead. The root cause is in
[ISS-647](20260917-1100-ISS-647.md). Its siblings are the single-pipeline badge
([ISS-655](20260917-1250-ISS-655.md)), the History resume button
([ISS-656](20260917-1250-ISS-656.md)), and the rapid re-click race
([ISS-657](20260917-1250-ISS-657.md)).

## Root cause

1. **Stale closure** (pre-fix line numbers): `AppHeader.tsx:224-240` `handleRunClick` and the
   single-badge fallback (`:308-321`) fired the async `onSwitchToLiveRun(run.id)` and then called
   `onGoToPipeline?.()` with no id. The one implementation (`DashboardLayout.tsx:2643-2653`) read
   `pipelineState?.pipelineRunId` from its last render. On a cold `/dashboard` load that value was
   undefined, so `if (runId)` skipped `router.push`. Otherwise it pushed the previously attached
   run. Only the reactive effect at `DashboardLayout.tsx:790` eventually navigated, roughly 1s
   later once the replay finished, or never if the replay failed.
2. **Reflow while open**: `runningPipelines` (`AppHeader.tsx:190`) was recomputed from polled
   `recentRuns` on every render, and the open menu (`:383`) mapped it live. A run finishing
   mid-click shifted the rows up, or unmounted the whole multi-badge when the count dropped from
   2 to 1.
3. **History clone** (ISS-656): `onViewRunningPipeline` (`DashboardLayout.tsx:2859-2873`) had the
   same stale-read shape. `WorkflowHistory.tsx:688` also dropped the `summary.id` that
   `RunDetailPage` already passes.
4. **Race** (ISS-657): `handleSwitchToLiveRun` (`page.tsx:2592-2680`) had no check after
   `await getRunEvents`. A slower, superseded fetch could replay, re-seed the transcript, and call
   `runStore.switchViewTo` for the old run after a newer switch.

## What changed, and why there

- `AppHeader.tsx`: the prop is now `onGoToPipeline?: (runId?: string) => void`.
  `handleRunClick` passes `run.id` (`:237`) and the single-badge fallback passes `runId` (`:324`).
  These are the only two callers that pair the call with a switch, and both route to the one
  implementation. The legacy badge (`:459`) was `onClick={onGoToPipeline}`, which would now hand
  the MouseEvent in as a run id, so it becomes `() => onGoToPipeline?.()`. The card says that path
  is unaffected and keeps its `pipelineState` fallback.
- `AppHeader.tsx`: the computed list is renamed `liveRunningPipelines`. `runningPipelines` is now
  `runningDropdownOpen ? runningDropdownSnapshot : liveRunningPipelines` (`:222`), and the toggle
  captures the snapshot on click (`:362`). Freezing that one variable also freezes the multi-badge
  mount condition, so the 2-to-1 case cannot unmount the menu under the cursor. The snapshot is
  React state set in the event handler, because a render-time ref write trips the React 19
  `react-hooks/refs` rule. A click on a frozen row resolves `recentRuns` live, so a run that has
  since finished opens through `onSelectWorkflowRun`.
- `DashboardLayout.tsx:2643-2655`: `const runId = clickedRunId ?? pipelineState?.pipelineRunId`.
  This matches the already-correct `onSelectWorkflowRun`/`onViewResults` shape: switch, then push
  the run the caller named.
- `DashboardLayout.tsx:2861-2875` + `WorkflowHistory.tsx:55,344,688`: `onViewRunningPipeline` now
  takes `(runId: string)`. `handleSelectRun` passes `run.id`, and RunDetailPage's own
  `onViewRunningPipeline(summary.id)` is passed straight through.
- `page.tsx:2651`: `if (trackedRunIdRef.current !== runId) return;` immediately after
  `await getRunEvents`, before the replay, the transcript seed and the final `switchViewTo`. Every
  other writer of `trackedRunIdRef` means the user has moved to a different run: a new launch's
  `pipeline_start` (`:1264`), the `activePipelineRunId ?? contentSourceRunId` sync effect (`:2188`,
  fed by the state this function sets before its await), and the reopen/route paths.
  `useRunStateStore` is per-instance (`useRef`/`useState`), so a superseded switch that finishes
  after the `router.push` remount only touches the dead instance's store.

Trade-offs and notes:

- Agent-progress counts in the open menu stay at their values from when it opened, until it
  closes.
- ISS-656's History path is low-exposure in practice. `RunDetailPage.isLive` and
  `handleSelectRun` both require `run.id === activeRunId`, and DashboardLayout passes
  `pipelineState?.pipelineRunId` from the same render. The change aligns the contract, which is
  what the card and its test pin.
- The now-unused `onGoToPipeline` prop on `NotificationPanel` (`:33,203`, never called) was
  already dead before this fix and is left alone.

Invariants: this is a frontend-only diff. SC-001/INV-1 holds: no workflow-name branch, only run
ids. No import was added, no backend file or migration was touched, and import-linter is not
applicable.
