## What happened

Register bug **QA-PS-003** (`BUGS.md#qa-ps-003`): on a User Stories run with two
clarification rounds, the concierge chat's confirmation message after each round reads
"Clarifications answered" with no round number, so round 1 and round 2 look identical in
chat history.

## Reproduction (CONFIRMED, cycle 3 of 3)

Page: Concierge chat, run detail. Route: `/runs/{id}`. Account: `qa-admin@flowinqa.com`.

- **Cycle 1** — cold start on an existing `waiting_for_user` User Stories run
  (`ba2dc857-eeeb-4619-90d7-0236c58aba23`), answered the 4 round-1 questions with
  "Use recommended", submitted. Only 1 clarify round fired before the run proceeded to
  build; confirmation card read **"Clarifications answered"**.
- **Cycle 2** — fresh `/create/user-stories` submission (brief: "github dashboard user
  story"), answered round 1 with "Use recommended" on all 4 questions. Again only 1
  round fired; confirmation card read **"Clarifications answered"**.
- **Cycle 3 (trigger found)** — fresh `/create/user-stories` submission, same brief, but
  round 1 was submitted with **no answers selected** (clicked "Submit answers & proceed"
  with every question left unset). This left the topic genuinely unresolved and
  `ClarifyEngine` (per `backend/agents/workflows/user_stories/workflow.yaml` `clarify.rounds:
  2` config) fired a real second round ("Five things to lock down first"). Both
  confirmation cards in the chat transcript read the exact same text:
  **"Clarifications answered"** for round 1 AND **"Clarifications answered"** for round
  2 — verbatim identical, exactly as QA-PS-003 describes. Evidence:
  `evidence/run-detail-concierge-chat/_scratch/qa-ps-003-cycle3-both-rounds-identical.png`
  (run id `5efb67f9-1cc1-468b-befb-d205f1be0180`).

**Named trigger:** leaving round 1's questions genuinely unresolved (not fully answering
with "Use recommended") is what makes `ClarifyEngine` actually fire a second round in
this pipeline — the identical-text defect itself is unconditional (see Root cause) and
fires on every round regardless of how round 1 was answered.

## Root cause

`backend/app/agents/chat_narrator.py` `_classify()`, lines 161-169:

```python
anchor = run_id or "run"
...
if etype in _CLARIFY_EVENTS:
    n = data.get("question_count")
    if n is None:
        n = len(data.get("questions", []) or [])
    if etype == "questionnaire_complete":
        text = f"{n} clarifications answered" if n else "Clarifications answered"
    else:
        text = "Before I build, I need to lock a few things down."
    return CARD_CLARIFY, text, f"clarify:{anchor}"
```

The `questionnaire_complete` confirmation text is derived only from `run_id`
(`anchor`) and an optional `question_count` (`n`) — there is no round index anywhere in
this branch, and the `clarify:{anchor}` dedup key is also round-agnostic. In production
the `questionnaire_complete` event's `question_count`/`questions` fields are empty for
this pipeline, so `n` is falsy and the code always falls back to the bare
`"Clarifications answered"` string on every round. Even when `n` is populated the text
would read `"{n} clarifications answered"` — still no round number, and coincidentally
identical whenever two rounds happen to have the same question count (4 vs 5 questions
in this repro would actually have differed by count, but the observed event payload
carried no count at all).

## Expected vs actual

- Expected: round 1 → "Clarifications round 1 answered", round 2 → "Clarifications round
  2 answered" (per QA-PS-003's stated expectation), so the chat history can distinguish
  rounds.
- Actual: both rounds render the literal string "Clarifications answered" — no
  discriminator of any kind.
