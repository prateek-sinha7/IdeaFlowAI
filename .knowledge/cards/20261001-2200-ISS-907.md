# ISS-907

Found during the QA-KB-007 fix ([FIX-692](20261001-2200-FIX-692.md)). The test plan in [ISS-135](20260813-0005-ISS-135.md) asked for a 2-hop case and
a caller-dict control beside the stored-row assertion. The test file carries only the stored-row assertion.

## Condition

`backend/tests/integration/repositories/test_run_events_payload_seq_db.py` holds two tests,
`test_store_retry_restamps_payload_seq` and `test_execute_wrapper_stored_payload_seq_matches_row`. Both assert the
STORED row after a single collision hop. Not covered:

- the caller's dict is not mutated (it is the live frame; on exhaustion it must keep the requested seq),
- a 2-hop retry stores the FINAL landed seq (re-stamp on every hop),
- the exhaustion path (`_max_attempts` spent: IntegrityError, no row, caller's dict unchanged).

## Proof (observed 2026-10-01; source untouched, each mutant swapped in by a scratch pytest plugin)

- Mutant A, in-place `payload_json["seq"] = attempt_seq`: the file reports `2 passed` under `--runxfail`, while a
  scratch check shows the caller's dict moved from seq 1 to seq 2.
- Mutant B, a copy re-stamped on the first hop only: `2 passed` under `--runxfail`, while with a stale first tail
  probe the row lands at 4 and stores payload seq 2.

Evidence: `evidence/qa-kb-007/05-fix-tests-and-constraint-checks.txt` (mutant plugin, both runs, the scratch checks).

## Disposition

Open. Fix shape: add to that file a 2-hop test (stale first `_max_event_seq`, expect landed 4 and stored 4), an
assertion that the passed dict still reads its original seq after a retry, and an exhaustion case
(`_max_attempts=1`). The five scratch checks in the evidence file are a ready template. Not added here: the
QA-KB-007 dispatch confines its fixer to `append_event_at_or_after`.

Update 2026-10-02 (QA-KB-079 analysis, below): the list above grew to six cases. The analysis adds the seq-less payload (mutant D) and the tail guard (mutant E), and splits exhaustion into a
store case and a sink case; the table under "Fix: where it belongs and what it must kill" is the authoritative list.

## Analysis (QA-KB-079, 2026-10-02)

### Root cause (CONFIRMED)

One mechanism. `test_run_events_payload_seq_db.py` is the ISS-135 repro pair kept as the regression guard (`:43-55`, `:58-80`). Each test asserts the STORED row after
exactly one collision hop (the plugin counts one real hop per test, `real_hops=2` for the file), passes a literal dict (`:48`) and never re-reads it, never forces a
second hop, never spends `_max_attempts`, and never retries a payload that has no `seq` key. [FIX-692](20261001-2200-FIX-692.md)'s locked constraints
(`backend/agents/authz.py:665-669`, and the exhaustion contract at `:670-674`) are therefore pinned only by the scratch script its fixer ran and did not commit
(`evidence/qa-kb-007/05-fix-tests-and-constraint-checks.txt`; `ls backend | grep qa_kb` is empty). `authz.py` is correct and stays untouched.

How the cases fell through: CONFIRMED that they were asked for and not written. The [ISS-135](20260813-0005-ISS-135.md) analysis listed them under "Tests (for the test writer)" ("a 2-hop case
... and a control that a payload without `seq` is stored byte-identical and the caller's dict is not mutated"); the file holds only the two repro tests; the fixer observed the constraints in a scratch
script instead (`evidence/qa-kb-007/05-...txt`); QA-KB-007 then closed on the two green tests. INFERRED, and it does not change the fix: the test-writer's "narrowest test per card" guidance
(`.claude/agents/4-test-writer.md` section 6) is why the extras were skipped; nothing in the cards records the reason. An obligation that lives in a card's prose and not in a test is advisory.

### Blast radius (CONFIRMED by grep and read)

`grep -rn append_event_at_or_after backend frontend/src tools` at HEAD finds three production callers; only the first carries a `seq` key.

| caller | payload | note |
|---|---|---|
| `_RunEventSink.persist` (`engine.py:3331`), fed by `execute()` (stamp `:4192`, persist `:4205`, re-stamp `:4208-4211`) and by `_drive_resumed_stream` (stamp `:15941`, persist `:15948`, re-stamp `:15951-15954`) | `data`, carries `seq` | exhaustion makes `persist` return `None` (`:3351`); the loops then skip the re-stamp |
| `_stamp_resume_marker` (`engine.py:13080`) | `pipeline_run_id`, `prior_status`, `reason` | no `seq` key (mutant D territory) |
| `_record_cancellation_in_the_durable_tail` (`backend/app/api/run_commands.py:464`) | `pipeline_run_id`, `reason` | no `seq` key (mutant D territory) |

Tests: the only test that asserts a STORED `payload_json["seq"]` is this file (`grep -rn 'payload_json\["seq"\]' backend/tests` hits `:55` and `:80` only). A retry hop is reached by
this file (1 per test), by `test_run_events_db.py` (1 per FIX-240 test) and by `test_durable_cancel_appends_past_an_already_occupied_seq` (`test_rest_answers_cancel_api.py:529`; 1 hop, asserts type
and seq, not payload). No test passes `_max_attempts` to `append_event_at_or_after`, so the exhaustion branch (`authz.py:674`) is never executed by any test. The resume driver has no collision test at
all: [ISS-1025](20261002-0645-ISS-1025.md).

### Why each gap matters (reading and runs; INFERRED parts marked)

- A (in place) is masked on the success path: `execute()` and the resume loop overwrite `data["seq"]` with the landed seq anyway (`engine.py:4208-4209`, `:15951-15952`), which is why
  `test_execute_wrapper_stored_payload_seq_matches_row` passes under A. It bites on exhaustion only: `persist` returns `None` (`:3351`), the loops do not re-stamp, and the live frame keeps whatever the
  store left in the dict. Through the sink with rows 1-10 present and every hop colliding, the frame ends as `{'seq': 9}` instead of `{'seq': 1}` (observed). The live frame's seq is the SSE `id:`
  (`backend/app/api/run_stream.py:553-558`), so a frame stamped with another event's seq would corrupt Last-Event-ID resumption (INFERRED end to end; a browser reconnect on such a run would settle it).
- B (first hop only): a second collision moves the row again and payload.seq stays one hop behind (landed 4, stored 2 in the validator's run).
- C (`RuntimeError` on exhaustion) escapes `_RunEventSink.persist`, which absorbs only `SQLAlchemyError` (`engine.py:3341-3342`): `RuntimeError: exhausted` (observed). The contract is written at
  `authz.py:670-674`. In `_drive_resumed_stream` the escape would land in its blanket `except` (`:15998`) and end the resumed drive; in `execute()` it would propagate (both INFERRED from reading; the escape is observed).
- D (stamps seq-less payloads): the `run_resuming` and `pipeline_cancelled` markers would gain a `seq` key on a retry. Replay merges `row.seq` over the payload (`run_stream.py:430-439`), so nothing visible
  breaks today; the stored payload would stop matching what the writer passed.
- E (guard removed): a rejection no tail explains is retried 8 times instead of once. The failed-audit cancel test (`test_rest_answers_cancel_api.py:578`, a NULL-workspace insert per its docstring) goes from
  4 appends and 2 probes to 11 and 9 across the three tests (observed), all green. This is the spin [FIX-240](20260812-1852-FIX-240.md) designed the guard to avoid ("a naive retry on IntegrityError would have spun 8 attempts per event").
- F (swallowed exhaustion): `persist` would report a landed seq for a row that was never written (`assert 9 is None`, observed), so the loop would re-stamp the frame onto a nonexistent row.
- P is unobservable and need not be tested: the re-stamp is on a copy and a raise discards the copy (P survives the proposed cases too, `07-analyze-run-output.txt` section 8). FIX-692's "after the guard"
  clause can only be pinned through the guard itself (E).

### Fix: where it belongs and what it must kill

Test-only, in this file (`backend/tests/integration/repositories/test_run_events_payload_seq_db.py`). `authz.py` is correct: a source change would be wrong. The cases need the fixtures the file already has
(in-memory SQLite, injected session) plus `_RunEventSink` from `agents.execution_engine.engine` (the file already imports `ExecutionEngine` from there). A validated template of six cases is
`evidence/qa-kb-079/05-analyze-proposed-cases-store-level.py.txt`: 6 passed on the real source, and every mutant above except P dies in at least one case (`07-analyze-run-output.txt` section 5).

| case | arrangement | kills |
|---|---|---|
| copy, not mutate | seed seq 1; `frame = {"seq": 1, "x": "y"}`; the retry lands at 2; assert stored `{"seq": 2, "x": "y"}` and `frame == {"seq": 1, "x": "y"}` | A, H |
| two hops | seed 1-3; the first `_max_event_seq` probe is stale (reports 1); assert 2 probes, landed 4, stored payload seq 4 | B, H |
| exhaustion, store | seed seq 1; `_max_attempts=1`; `pytest.raises(IntegrityError)` (not `RuntimeError`); no row for the event; caller's dict unchanged | A, C, F |
| exhaustion, sink | seed rows 1-10; a lagging probe (returns 1, 2, 3, ...) so all 8 attempts collide with the guard satisfied; `await sink.persist(...) is None`; 8 probes; no row; frame unchanged | A, C, F |
| seq-less payload | seed seq 1; a marker without `seq`; landed 2; stored payload equals the marker; marker unchanged | D |
| guard | duplicate `event_id` at a free seq (5); `pytest.raises(IntegrityError)`; exactly 1 append attempt and 1 probe | E |

Two traps in the sink case, both hit while validating it: a probe that always reports 1 trips the guard on the second attempt (`tail < attempt_seq`), so the exhaustion branch is never reached and C and F
survive; and asserting the probe count (8) is what proves the case reaches exhaustion.
