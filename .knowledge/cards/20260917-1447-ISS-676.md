# ISS-676

## Status: CONFIRMED (offline synthetic repro, QA-KB-035, 2026-10-01); ANALYZED 2026-10-01 (see "Analysis" at the end)

The 5-fixer found this while adding [FIX-521](20260917-1447-FIX-521.md)'s ISS-648 bridge to the
same block. It is read from code only. Confirm it live before treating it as a defect.

## What the code does (line numbers as of FIX-521)

`page.tsx:1722-1740`:

```ts
if (msg.type === "pipeline_cancelled" || msg.type === "pipeline_failed") {
  if (!isForeignFrame) {
    ...
    if (frameRunId) runStore.update(frameRunId, { questionnaireData: null });
    setReviewGateData(null);
    setQuestionnaireData(null);
    setActivePipelineRunId(null);
```

The block's own KAN-125 comment says its purpose is that "a FOREIGN concurrent run cancelling/failing
must not clear THIS tab's questionnaire/reviewGate/activePipelineRunId". But `isForeignFrame`
(`page.tsx:1370`) is false for every run in `launchedRunIdsRef`, meaning every run this tab
launched. A BACKGROUND run from this tab that fails or is cancelled therefore still runs the three
page-level resets, which belong to whichever run is on screen.

The store write (`runStore.update(frameRunId, ...)`) is correctly per-run. The three setters are not.

## Why it probably matters

- `activePipelineRunId` feeds `trackedRunIdRef` (`page.tsx:2203`,
  `activePipelineRunId ?? contentSourceRunId ?? trackedRunIdRef.current`) and `useRunChat`'s run id
  (`page.tsx:2322`). While the viewed run is clarify-paused, before its own `pipeline_start`, it has
  no `pipelineRunId`. That makes `activePipelineRunId` the only thing holding it.
- `page.tsx:618-626` (BUG-005) documents the same failure class for a different trigger: a foreign
  run's `pipeline_start` nulled `activePipelineRunId` and "the lane fell clarify→building".
- The legacy `setReviewGateData(null)` / `setQuestionnaireData(null)` may be invisible, since the
  block's own comment says the lane reads the store. That half is uncertain.

## What would confirm this

Launch run A and navigate away while it is still building. Launch run B and stay on its
clarification questions. Cancel run A without viewing it, for example with
`POST /api/runs/<A>/cancel`. Check whether
run B's lane leaves the clarify state or its chat lane re-points. No UI path for cancelling a
non-viewed run was checked.

## Likely fix shape (for the analyzer, not decided)

Gate the three page-level setters on the frame being for the tracked run
(`frameRunId === trackedRunIdRef.current`), the axis FIX-203 and FIX-521 already use for
"background". Leave the per-run store write as it is.

## Analysis (QA-KB-035 analyzer, 2026-10-01)

Line numbers in this section are the working tree (HEAD `024c03ef8` plus 5 uncommitted lines in
page.tsx; subtract 3 from page.tsx lines between 1344 and 3783 to get HEAD). The `page.tsx:1722-1740`,
`:1370`, `:2203`, `:2322` references above are stale: the block is now `page.tsx:1821-1858`.

### Verdict

1. ROOT CAUSE: CONFIRMED. The live terminal block uses the wrong "is this a background run" axis.
2. The reported lane symptom (clarify form disappears, lane shows "building"): NOT supported by the code.
   Two of the three setters write state nobody reads, and the third is masked by store reads. INFERRED
   that a browser run would show no lane change; settling it needs two paid concurrent runs.
3. The same root cause does have a visible reader: `lastCancelledRunId`, filed as
   [ISS-927](20261001-2224-ISS-927.md) (INFERRED).
4. Agreed minimal fix (BUGS.md QA-KB-035 notes): ACCEPTED, implemented through the existing shared
   predicate, with ONE extension: `setLastCancelledRunId` goes inside the guard too.

### Root cause (CONFIRMED, file:line read)

`isForeignFrame` (`page.tsx:1528-1535`) is true only when the tab launched nothing or the frame's run is
not in `launchedRunIdsRef` (`:683-705`, persisted to sessionStorage so it survives a remount). It answers
"did this tab launch the run?". The terminal block reuses it for a different question, "is this the run on
screen?":

```ts
if (msg.type === "pipeline_cancelled" || msg.type === "pipeline_failed") {   // :1821
  if (!isForeignFrame) {                                                     // :1822
    ...
    setReviewGateData(null);                                                 // :1837
    setQuestionnaireData(null);                                              // :1838
    setActivePipelineRunId(null);                                            // :1839
    if (msg.type === "pipeline_cancelled") { ... setLastCancelledRunId(cancelledId);   // :1846
```

Every run this tab launched, background or not, is `!isForeignFrame`, so its terminal frame writes slots
that belong to `trackedRunIdRef`, the run the tab is driving or viewing (`:664-672`). The same block already
uses the right axis for the notification a few lines above the setters (`:1825`, `frameRunId !== trackedRunIdRef.current`,
ISS-648), but the setters were never put behind it. The same class was closed for `pipeline_start`
(`isForeignRun`, `:1380-1396`, [BUG-005-sse](20260803-BUG-005-sse.md)) and for `pipeline_complete`
(`isForeignCompletion`, `:1594-1597`, [BUG-011-sse](20260803-BUG-011-sse.md)); both key on
`trackedRunIdRef`. Cancel/fail is the lifecycle frame that was left on the tab-ownership axis.

Offline reproduction (mine, `evidence/qa-kb-035/04-analyze-slice-trace.out.txt`): the live block sliced out
of page.tsx and run with recording stubs, `isForeignFrame=false`, tracked=VIEW, frame=BG. BOTH
`pipeline_cancelled` and `pipeline_failed` run `setReviewGateData(null)`, `setQuestionnaireData(null)`,
`setActivePipelineRunId(null)`; cancelled also runs `setLastCancelledRunId("BG")`. The validator's three
outputs print only the `pipeline_cancelled` iteration (the first failed `expect` ends the test), so the
`pipeline_failed` iteration is evidenced here. Controls: the tracked run's own terminal frame runs all of
them; a foreign-tab frame (`isForeignFrame=true`) runs nothing.

### What each write changes today (CONFIRMED by reading every reader; no browser run)

| write | readers | visible effect |
|---|---|---|
| `setQuestionnaireData(null)`, `setReviewGateData(null)` | none. The states (`page.tsx:850`, `:865`) are write-only; DashboardLayout receives `runStore.viewed.questionnaireData` / `.reviewGateData` (`:4412`, `:4417`) | none |
| `setActivePipelineRunId(null)` | (1) DashboardLayout prop `runStore.viewed.activePipelineRunId ?? activePipelineRunId` (`:4413`); (2) `useRunChat` run id (`:2429`); (3) the `trackedRunIdRef` sync effect (`:2309-2311`) | masked, see below |
| `setLastCancelledRunId(BG)` | `handleResumeRun`, first term (`DashboardLayout.tsx:2530`) | wrong run resumed, [ISS-927](20261001-2224-ISS-927.md) |

Why `setActivePipelineRunId(null)` is masked (this corrects "Why it probably matters" above):

1. Lane. `laneClarifyOpen` needs the `activePipelineRunId` PROP (`DashboardLayout.tsx:2592`), fed store
   first (`page.tsx:4413`). `questionnaire_ready` writes the store copy (`runStore.update(qRunId,
   { questionnaireData, activePipelineRunId: qRunId })`, `:2073-2076`) and nothing clears it (`initRun` and
   `remove` are never called from page.tsx). The block's own store write is keyed by the TERMINATING run
   (`:1836`, `runStore.update(frameRunId, ...)`), so VIEW's entry is untouched. BUG-005's lane flip was
   real because the lane then read the legacy global state; [FIX-201](20260807-1633-FIX-201.md) moved it to
   the per-run store.
2. Chat. The first term of the `useRunChat` run id is `runStore.viewed.pipelineState.pipelineRunId`. During
   clarify it is already set by `planner_start` (`backend/agents/execution_engine/engine.py:5413-5420`, before
   `_run_planner` at `:5423`, clarify at `:5545` and `pipeline_start` at `:5745`; every dispatchable manifest
   runs the planner, `engine.py:5365-5368`; reducer `useWorkflow.ts:1704-1713`). The third term,
   `contentSourceRunId`, is seeded on every switch, reopen and remount (`page.tsx:2781`, `:3506`, `:3601`).
   The earlier text ("before its own pipeline_start, it has no pipelineRunId ... the only thing holding it")
   overlooked `planner_start`. A lane message with a null run id would POST `/api/runs`
   (`RunConnectionProvider.tsx:494-496`) and 422, because `LaunchCommand` requires `message` and
   `pipeline_type` (`run_commands.py:2488-2489`); I could not construct a state that reaches it.
3. Tracking. `null ?? contentSourceRunId ?? trackedRunIdRef.current` leaves the tracked run unchanged unless
   `contentSourceRunId` names a different run.

So the fix is for correctness and as a guard rail (the two dead setters go live the day someone reads those
states again; the legacy slot becomes the sole holder the day a store mask is removed), not for a symptom a
user can reproduce today.

### Blast radius (every caller)

- The block is the ONLY handler of both frame types (the switch arm was deleted, ISS-139;
  `terminalReopenReconcile.source.test.ts:90-103`). `handleWebSocketMessage` has four callers: the live
  subscription (`page.tsx:2385`), the `handleSwitchToLiveRun` replay (`:2805`), the `handleSelectWorkflowRun`
  replay (`:3059`) and the T11 remount replay (`:3638`). The three replays pass the replayed run id as
  `sourceRunId` and point `trackedRunIdRef` at it first (`:2742`, `:3038`, `:3581`), so for them
  `frameRunId === tracked` and the guard changes nothing.
- Same wrong-guard shape, no visible reader: the `pipeline_failed` chat bubble (`:1760-1774`, `setMessages`
  under `!isForeignFrame`). The page-level `messages` never renders: `DashboardLayout.tsx:3283` is
  `runChatMessages ?? messages` and `runChatMessages` is always an array.
- Same class, different handler and slot: [ISS-744](20260922-1409-ISS-744.md) (`pipeline_complete` for
  revision runs re-points the content source). Not touched here.
- Reachability of the trigger: this page has no UI to cancel a non-viewed run (`postCancel` has two UI call
  sites, `DashboardLayout.tsx:2260` and `:2509`, both for the viewed run). A background terminal frame
  arrives from a natural failure, a cancel issued elsewhere (API, another tab, server side), or a Stop
  followed by a switch before the cooperative cancel lands.

### Where the fix belongs and what it must not break

One place: the terminal block, `page.tsx:1821-1858`; all callers route through it. Use the shared
predicate already imported at `:22`, `isForeignRunFrame(frameRunId, trackedRunIdRef.current)`
(`frontend/src/lib/wsReplayState.ts:80-86`, conservative: false unless both ids are known and differ). It is
exactly the agreed inline condition `!frameRunId || !tracked || frameRunId === tracked`, without
hand-rolling it a third time.

```ts
if (!isForeignRunFrame(frameRunId, trackedRunIdRef.current)) {
  setReviewGateData(null);
  setQuestionnaireData(null);
  setActivePipelineRunId(null);
}
...
if (cancelledId) {
  if (!isForeignRunFrame(frameRunId, trackedRunIdRef.current)) setLastCancelledRunId(cancelledId);
  detachRunRef.current?.(cancelledId);
}
```

Verified in memory on the sliced block (same trace file): a BG terminal skips all four writes; the tracked
run's own terminal frame is unchanged; `tracked=null` (the remount window, `page.tsx:3477`) and a frame with
no run id keep today's behaviour (residual, unchanged). Stay unconditional: `setBackgroundRunTransition`
(already conditional on `frameRunId !== trackedRunIdRef.current`), `runStore.update(frameRunId, {
questionnaireData: null })`, `detachRunRef`, `patchRecentRunStatus`.

Verdict on the agreed fix: ACCEPT the axis and the wrap of the three setters; OVERRULE "leave
`setLastCancelledRunId` unconditional" (a viewed-run slot with a real reader, see
[ISS-927](20261001-2224-ISS-927.md)). Considered and rejected: `setActivePipelineRunId(cur => cur ===
frameRunId ? null : cur)`, which keys on the slot instead of the tracked run; it introduces a third axis next
to `isForeignRun` / `isForeignCompletion` / ISS-648 and adds nothing for the reported scenario.

Tests that pin this block (keep green or update deliberately):
`frontend/src/app/[...view]/liveRunSwitch.fix201.test.ts:65-91` needs the literal `if (!isForeignFrame)` and
`runStore.update(frameRunId, { questionnaireData: null })` inside the block, and
`terminalReopenReconcile.source.test.ts:90-103` needs the block opener and the store write. Both cut the block
at the first `\n      return;\n`, so do not add a six-space-indented `return;` inside it. The predicate itself
is covered by `frontend/src/lib/__tests__/wsRunScope.test.ts`.

## Fixed (2026-10-02, QA-KB-035 fixer): [FIX-708](20261002-0144-FIX-708.md)
