# ISS-871

Found while tracing the consumers of `hookRuns` for QA-KB-005 ([ISS-107](20260812-1400-ISS-107.md)). **Confidence: INFERRED** as
a sibling — every file:line below was read and is CONFIRMED, but whether the product wants this bullet at all is not
recorded, and no run was launched to watch it.

## Condition

A run in which `secret_scan` blocks a write (`outcome=block`) and the run fails.

## Expected

`RunChatLane.deriveSecurityBullets` (`frontend/src/components/chat/RunChatLane.tsx:464-477`) adds "Secret scan blocked a
write ... containing <marker>" to the failure card. Its filter is
`h.outcome === "block" && /secret|scan/i.test(h.hook ?? "")` (`:469-471`) over `pipelineState.hookRuns`, which its own
comment (`:468`) says comes "from live hook_run events".

## Actual

No live row can satisfy that filter, whatever the frontend does. CONFIRMED by reading:

- `SecretScanHook.handle` (`backend/agents/capabilities/hooks/secret_scan.py:435-478`; the writes are at `:453`, `:456`,
  `:473`, `:476`) only calls `write_hook_run`, which goes through `ctx.runner.record_hook_run` to a `hook_runs` DB row
  (`hooks/write.py:21-31`). It never calls `emit_hook_event`.
- `KernelServices.emit_hook_event(self, detail)` (`backend/agents/execution_engine/kernel_services.py:538-563`) is the only
  producer of a `hook_run` frame (`:561`); a search for the quoted type string across non-test backend Python finds that one line.
  It has four callers, and every one sets `"outcome": "continue"` and none sets a `hook` key:
  `audit_logger._emit_ws` (`hooks/audit_logger.py:108,119-129`), the run-entry behavioral rows
  (`engine.py:5828-5862`, which carry `hook_name` / `event_type` instead of `hook` / `event`), the tool_call audit
  (`engine.py:10223-10262`) and the tool_result audit (`engine.py:10275-10305`).
- The DB writer takes `hook`, `event`, `outcome` as first-class parameters
  (`record_hook_run(self, hook, event, outcome, detail)`, `kernel_services.py:459-461`; `outcome` is one of
  `continue | warn | block`), but the WS emitter takes only `detail`. The frame therefore has no first-class hook
  identity. The reducer's `"audit_logger"` default is right by accident for three of the four sources (they persist as
  `audit_logger`) and wrong for the behavioral rows, which persist as `hook="behavioral"`, `event="run_start"`
  (`engine.py:5851-5853`).
- No backend test references `emit_hook_event` or a `hook_run` frame (a search of `backend/tests` finds nothing), so the
  frame shape is unpinned.

The persisted path is fine: `AuditTab` reads blocks from `GET /api/runs/{id}/hook-runs` (`AuditTab.tsx:477-482`).

## Why the root cause implies it

The QA-KB-005 repro frame (`hook: "secret_scan"`, `outcome: "block"`) is synthetic: the backend never produces it. A
reducer that faithfully mirrors the payload mirrors a payload that contains no blocks. So closing
[ISS-107](20260812-1400-ISS-107.md) does not revive the consumer that card names ("the only live consumer of `hookRuns` is
structurally dead"). Together with the allowlist sibling [ISS-870](20261001-2107-ISS-870.md) that makes three independent breaks
between a blocked write and the failure card's bullet.

## What would settle it

Backend offline unit test: fire `SecretScanHook.handle` with a secret-bearing `before_write` payload against a fake
`ctx.runner` whose `record_hook_run` and `emit_hook_event` are recording stubs, and assert the second is never called
today. `tests/unit/agents/test_hooks.py` is the natural home.

## Fix direction (a decision for the owner, not escalated)

1. `secret_scan` also calls `emit_hook_event`, and `emit_hook_event` gains first-class `hook` / `event` / `outcome` so the
   frame matches the row. Keep it queue-only: `kernel_services.py:551-559` explains that routing it through `execute()`
   would add a frame to the yield stream, a golden event-multiset change (INV-3).
2. Feed the bullet from the persisted rows the failure card can already fetch (what `AuditTab` does) and drop the
   live-frame dependency.
3. Delete bullet (1) of `deriveSecurityBullets` as dead.

Option 1 only pays off once [ISS-870](20261001-2107-ISS-870.md) and the QA-KB-005 reducer fix have landed. It would also
need a `file` key in `secret_scan`'s detail: the bullet reads `d.file` (`RunChatLane.tsx:474`), and the detail at
`secret_scan.py:445-452` / `:466-472` carries only `matched`, `marker`, `reason` (plus `binary`). Not escalated: which of
the three is wanted is a scope call for whoever fixes it.

## Test phase note

No test written. Whether a backend emitter should exist (fix option 1) versus feeding the bullet from persisted rows or deleting it (options 2/3) is a product/design decision, so a test asserting emission would presume option 1. Re-evaluate once the owner picks.

## Fix phase (2026-10-01): not fixed, left open

[FIX-683](20261001-2128-FIX-683.md) fixed [ISS-107](20260812-1400-ISS-107.md) and [ISS-870](20261001-2107-ISS-870.md)
and left this card alone on purpose. The choice between an emitter, persisted rows, or deleting the bullet is a design
decision. Option 1's precondition is now met: live `hook_run` frames reach `pipelineState.hookRuns` with their payload.
Status stays `open`.
