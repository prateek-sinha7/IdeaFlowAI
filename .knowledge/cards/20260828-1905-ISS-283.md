## What is suspected

[ISS-228](20260828-1758-ISS-228.md) root-caused the cold-mount `/workflows/{id}/run` override
loss to a specific mechanism inside `frontend/src/components/workflow/LaunchWizard.tsx`,
confirmed by reading the source: two `useEffect`s both key off `libraryAgents` (from
`useAgentLibrary()`, Redux state populated asynchronously post sign-in —
`frontend/src/hooks/useAgentLibrary.ts:16-20`, "populated by GET /api/agents/library via the
listenerMiddleware on app boot") transitioning from empty to populated:

- The "restore session draft" effect (`LaunchWizard.tsx:278-324`) reads the `{mode}.draft`
  sessionStorage payload the caller wrote and, once `libraryAgents.length > 0`, maps
  `d.agentIds` to `AgentDef`s and calls `setPipelineAgents(restored)` (`:303-307`) — this is what
  actually applies the saved override's real agent roster.
- The "re-derive once real agents arrive" effect (`LaunchWizard.tsx:335-338`) fires on the SAME
  `libraryAgents` transition and reads `pipelineAgents.length` from the SAME render's closure —
  i.e. the value from BEFORE the sibling effect above applied its update (React does not let one
  effect observe another effect's `setState` call within the same commit). It always sees `0` and
  unconditionally calls `setPipelineAgents(defaultAgentsFor(libraryAgents, mode))` — the generic
  per-pipeline library roster — which, since both effects issue a plain-value `setState` (not a
  functional updater) and this effect is declared (hence always runs) AFTER the restore effect,
  is the LAST write and wins.

The draft-writing side of this is not unique to the cold `/workflows/{id}/run` mount. Clicking
"Run" on a saved prototype/ppt workflow from the Saved-workflows list calls `handleLaunchSaved`
(`DashboardLayout.tsx:1475`), which for `base_pipeline_type === "ppt"` (`:1507-1531`) or
`"prototype"` (`:1534-1558`) writes the identical draft shape — including
`agentIds: saved.agent_ids` (`:1521`, `:1548`) — to the SAME `sessionStorage` keys
(`"ppt.draft"` / `"prototype.draft"`, `:1529`, `:1556`) and then `router.push`es to
`routes.workflowCreateLegacy(...)`, which `frontend/src/app/workflow/create/page.tsx:24` mounts
as `<LaunchWizard initialMode={mode} />` — the exact same component, the exact same two effects,
the exact same shared `libraryAgents` trigger.

## Condition

Sign in, and — before the agent-library fetch (`GET /api/agents/library`, dispatched on the
`signedIn` action) has resolved — click "Run" on a saved prototype or ppt workflow from the
Dashboard's Saved-workflows list. This is a narrower window than ISS-228's cold `/workflows/{id}/run`
mount (which is GUARANTEED to start with an empty `libraryAgents`, per the `useAgentLibrary`
Redux-populated-on-boot design), since a click-through happens after some in-SPA navigation has
usually already given the library fetch time to resolve — but it is not impossible, particularly
immediately post sign-in on a slow connection or a large agent-library payload.

## Expected vs actual

**Expected:** clicking "Run" on a saved workflow opens the wizard bound to that workflow's saved
agent roster, regardless of whether the agent-library fetch has resolved yet.

**Actual (predicted):** when the agent-library fetch is still in flight at the moment of the
click, the same last-write-wins effect race applies: the wizard opens showing the generic
per-pipeline default roster instead of the saved override's roster, with no error and no visual
indication — identical in kind to ISS-228's symptom, reached via a different entry point.

## Why the root cause implies this — and why it is a distinct defect, not the same report

ISS-228 was reproduced and filed specifically against the cold `/workflows/{id}/run` deep-link
path. The mechanism it root-caused, however, lives entirely inside `LaunchWizard.tsx` and is
triggered by ANY mount where `libraryAgents` is still empty when the component first renders and
a `{mode}.draft` with `agentIds` is present in `sessionStorage` — a condition `handleLaunchSaved`
also creates, through a different caller. This has to be tracked (and, once fixed, verified)
separately from ISS-228 because it is a different trigger path with a different (narrower,
timing-dependent) reproduction window, even though the underlying fix is the same one-effect
change inside `LaunchWizard.tsx`.

**Marked INFERRED**: this has not been driven in a browser — only the identical sessionStorage-draft
and mount-target shape has been confirmed by reading `DashboardLayout.tsx:1475-1558` and
`frontend/src/app/workflow/create/page.tsx:24`. What would confirm it: sign in fresh, and
immediately (before the Network panel shows `GET /api/agents/library` completing) click "Run" on
a saved prototype/ppt workflow from the Saved-workflows list; throttling the agents-library
request via `page.route` + a delay would make the window reliably reproducible for a test.
