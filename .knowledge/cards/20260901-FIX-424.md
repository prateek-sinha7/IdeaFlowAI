## What was wrong

The test account's run history holds **zero ppt-family runs**, so
`WorkflowHistory.tsx` never renders the Presentation chip
(`if (type !== "all" && count === 0) return null`, line 1047).
Four tests hard-coded `"Presentation"` / `"ppt"` as their test target:

| Scenario | Failure mode |
|----------|-------------|
| S-06-05 `test_filtering_by_type_narrows_the_list[Presentation]` | `chip().first.click()` timed out — chip not in DOM |
| S-06-07 `test_the_chip_label_and_its_url_value_are_different_words` | Same — chip not in DOM |
| S-06-13 `test_refresh_re_reads_without_losing_filters` | Same — chip not in DOM |
| S-06-08 `test_an_unrecognised_type_shows_an_empty_list_rather_than_an_error` | `chip_count("Presentation") > 0` was 0 — D-15 contradiction no longer demonstrable against this type |

`filterBucketFor` correctly buckets ppt runs to `ppt`; their absence is a data
fact, not a bucketing bug (confirmed in ISS-625).  D-15 was re-read before
touching S-06-08: the defect (a stale link with the wrong param shows an empty
list that looks like data loss while the chip beside it claims non-zero runs)
still exists as a category, but the `presentation` vs `ppt` illustration is
gone now that ppt has zero runs.

## Root cause — file:line

`tests/integration/e2e/suites/06_run_history/test_run_history.py`
— hard-coded `"Presentation"` / `"ppt"` references in four tests that
unconditionally click or count a chip that `WorkflowHistory.tsx` withholds when
its family count is zero.

## What changed

**File:** `tests/integration/e2e/suites/06_run_history/test_run_history.py`

1. **S-06-05** (`test_filtering_by_type_narrows_the_list`, parametrized) —
   added a `pytest.skip` guard before the click when `expected == 0`.  No
   parameter removed; the parametrize list still drives from `L.TYPE_PARAMS`
   so the test self-heals if ppt runs reappear.

2. **S-06-07** (`test_the_chip_label_and_its_url_value_are_different_words`) —
   retargeted from `"Presentation"` → `"ppt"` to `"User Stories"` →
   `"user_stories"`.  The scenario's intent is preserved: the chip label
   ("User Stories", two words with a space) is genuinely different from the URL
   parameter value ("user_stories", one token with an underscore).

3. **S-06-08** (`test_an_unrecognised_type_shows_an_empty_list_rather_than_an_error`) —
   retargeted from `?type=presentation` to `?type=user+stories` (the
   URL-encoded wrong guess for `user_stories`).  The same D-15 contradiction is
   now demonstrated against the `user_stories` chip, which has runs.  Docstring
   updated to explain the ISS-625 retargeting rationale and carry forward the
   self-documenting sentinel message.

4. **S-06-13** (`test_refresh_re_reads_without_losing_filters`) —
   retargeted from `"Presentation"` / `"ppt"` to `"User Stories"` /
   `"user_stories"`.

No app source touched.  No locator file touched — `L.TYPE_PARAMS` and
`L.chip()` are unchanged.

## Why user_stories

- Available on every tier (basic, hexaware, pro, enterprise).
- The default workflow fallback — guaranteed to have history in any seeded
  account.
- "User Stories" (label) vs `user_stories` (URL param) is a clear label≠value
  demonstration, preserving S-06-07's intent.
- S-06-09 already used `custom`; using `user_stories` here avoids overlap.
