## What was wrong

[ISS-471](20260828-2310-ISS-471.md), the third and most serious instance of the
shape [ISS-319](20260828-1804-ISS-319.md) proved in `update_preferences` and
[FIX-382](20260829-0223-FIX-382.md) fixed there — deliberately left open by that
card because `admin.py` sat outside its `applies_to.globs`.

`PATCH /api/admin/users/{id}/tier` and `PATCH /api/admin/users/{id}/role` both
mutate a privilege field, `db.commit()`, then `db.refresh(user)` and build the
`200` body from the refreshed object. Two concurrent admin requests against the
same target user each get their own `Session` via `Depends(get_db)` on one
`users` row. If request B's `commit()` lands in the window between request A's
own `commit()` and its `refresh()`, A's `200` body reports B's value — so an
admin who demoted a user is told, by their own successful response, that the
demotion took, when the row actually holds the other admin's value. The
same-shaped defect on `preferred_model` was a wrong preference; here it is a
wrong answer about who is an admin and what tier they hold.

Staged deterministically by the 4-test-writer rather than left to thread timing
(`backend/tests/unit/test_admin_privilege_race.py`): two SQLAlchemy sessions on
one `StaticPool` in-memory connection, with request B's whole handler call
spliced into request A's own `db.refresh` via a monkeypatch. Confirmed red
before the change — `2 xfailed, 1 warning in 1.06s`, i.e. the race reproduces.

## Root cause

`backend/app/api/admin.py` — `update_user_tier` (mutation at `:313`, return at
`:330` post-fix / `:324` pre-fix) and `update_user_role` (mutation at `:382`,
return at `:398` post-fix / `:389` pre-fix) — both ending in:

```python
user.tier = request.tier          # or: user.is_admin = request.is_admin
db.commit()
db.refresh(user)
...
return _to_response(user, db)     # <-- re-read of the ROW, post-refresh
```

`_to_response` (`admin.py:158-167`) reads `tier=user.tier` /
`is_admin=user.is_admin` straight off whatever object it is handed. The helper
itself is correct — it faithfully renders the object it is given. The defect is
handing it a POST-`refresh` object and expecting it to report the value THIS
request wrote.

## What changed, and why there

`backend/app/api/admin.py` only — the one file
[ISS-471](20260828-2310-ISS-471.md)'s `applies_to.globs` names. Two expressions,
one per handler, each at the `return`:

```python
return _to_response(user, db).model_copy(update={"tier": request.tier})
return _to_response(user, db).model_copy(update={"is_admin": request.is_admin})
```

An `# ISS-471:` comment above each records why, matching the file's existing
`# P1 fix (...)` convention so the re-read is not reintroduced as a
"simplification" later.

**Why at the two call sites and not inside `_to_response`.** Re-grepped every
`_to_response(` call site before editing (`backend/app/api/admin.py:330, 398,
454, 521` post-fix — the helper is module-private and has no callers outside this file;
`user_agents.py`'s same-named helper is a different function with a
single-argument signature). The card's blast radius still holds. The two
`create_user` sites at `454`/`521` INSERT a brand-new row that no concurrent
request can be writing, so they carry no instance of this race — pushing the
override into the shared helper would have meant a signature change rippling to
two call sites that do not need it, for no behaviour change. The bug lives at
the two sites that MUTATE an existing row, and that is where the guard went.
`list_users` (`admin.py:194-205`) inlines the same field reads but is a pure
read with nothing of its own to report, so it is untouched.

`model_copy(update=...)` rather than re-inlining all seven `AdminUserResponse`
fields at each site: it is the pydantic-v2 API for exactly this, it keeps
`_to_response` the single place the response shape is defined, and it makes the
overridden field the only thing a reader has to check.

**Downstream consumers are unaffected.** The single UI caller of each endpoint,
`frontend/src/app/admin/page.tsx:204` (`handleUpdateTier`) and `:217`
(`handleUpdateRole`), reads `updated.tier` / `updated.is_admin` to patch local
row state — same field, same type, same nullability, and now correct under
concurrency instead of silently writing the other admin's value into the table.
No frontend file changed.

## Not fixed by this card

Nothing deferred from this card's own scope. The lost UPDATE itself is
untouched and stays accepted last-write-wins per
[FIX-382](20260829-0223-FIX-382.md)'s locked constraint — this card closes only
the false-success response body, which is the bar
[BUG-096](20260829-1508-BUG-096.md) § "Expected" sets.

With `admin.py` closed, all three instances of the
commit-then-refresh-then-respond-from-the-refreshed-object shape found by
[BUG-096](20260829-1508-BUG-096.md)'s `db.refresh(` sweep of
`backend/app/api/` are now fixed ([ISS-319](20260828-1804-ISS-319.md),
[ISS-470](20260828-2310-ISS-470.md), [ISS-471](20260828-2310-ISS-471.md)). All
three landed as per-site one-liners rather than a shared helper, for the reason
[FIX-382](20260829-0223-FIX-382.md) gave: three differently-shaped response
models. A FOURTH instance should reopen that decision.
