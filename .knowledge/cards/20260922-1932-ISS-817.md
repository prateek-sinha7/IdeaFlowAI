# ISS-817

## Sibling of ISS-816 / QA-PS-042 — same missing-guard shape, different route family

INFERRED — derived from [ISS-816](20260922-1931-ISS-816.md)'s blast-radius
grep (`getMe(` has 5 real call sites app-wide), not yet reproduced in a
browser.

`frontend/src/components/workflow/LaunchWizard.tsx:361-372`'s mount effect:

```tsx
useEffect(() => {
  const token = getToken();
  if (!token) { router.replace(buildLoginRedirect()); return; }
  setAuthChecked(true);
  // ISS-321: the wizard is reached from two separate routes (the `[...view]`
  // catch-all's wizardMode branch and the standalone `/workflow/create`
  // page), so it owns the tier lookup rather than taking it as a prop...
  getMe(token).then((u) => setTier(u.tier)).catch(() => {});
  ...
```

No `useRef` in-flight flag, no `AbortController`, no cache — the identical
shape `admin/page.tsx` has (ISS-789/ISS-816). The component's own comment
(`ISS-321`) confirms it mounts from two independent entry points: the
literal `/workflow/create` route
(`frontend/src/app/workflow/create/page.tsx:48`,
`return <LaunchWizard initialMode={mode} />`, confirmed by direct read — a
literal route folder, bypassing `[...view]` the same way `/admin` does)
and the catch-all's wizardMode branch, which is how every
`/create/<workflow-type>` wizard (including QA-PS-043's
`/create/user-stories`) reaches this same component.

QA-PS-043's own validation card, [ISS-790](20260922-1821-ISS-790.md),
captured `GET /api/auth/me` as 1x (not duplicated) across its 3/3
cold-start cycles on `/create/user-stories` — consistent with this whole
card family's finding that a cold/hard load does not double-fire, only a
client-side (SPA) navigation does. This call site has not been exercised
via SPA nav in any existing card, which is why it has stayed unfound until
this blast-radius trace.

## Expected vs actual

Expected: opening any `/create/*` wizard or `/workflow/create` via in-app
navigation fires `GET /api/auth/me` once for the wizard's own tier lookup
(on top of whatever the catch-all's own effect fires, per
[ISS-794](20260922-1827-ISS-794.md)).

Actual (predicted, not yet measured): an additional `GET /api/auth/me` on
the same navigation, doubled again under dev StrictMode, whenever the
wizard is reached via SPA nav rather than a cold load.

## What would settle it

Reproduce via SPA click-through into `/create/user-stories` or
`/workflow/create` (not a cold `page.goto`) with
`browser_network_requests` / `performance.getEntriesByType('resource')`,
the same method ISS-789/ISS-790 used, and compare the `auth/me` count
against a cold load of the same route.

## Fix

Same shared choke point as ISS-816: a URL-keyed in-flight GET dedupe in
`request()` (`frontend/src/lib/api.ts:365-375`) closes this caller too,
with no per-component change needed here.

## Resolution — [FIX-626](20260922-2045-FIX-626.md), 2026-09-22

Resolved with NO code change at this call site. The fix this card asks for
("a URL-keyed in-flight GET dedupe … closes this caller too, with no
per-component change needed here") already exists: `getMe()`
(`frontend/src/lib/api.ts:609-615`) routes through `cachedGet()`, added for
[ISS-801](20260922-1834-ISS-801.md) after this card was written, and
`LaunchWizard.tsx:371` calls plain `getMe(token)` — so its StrictMode
second invoke is served from the shared 30 s entry rather than the network.

Honest limit: this is a resolution by direct read of the two files, not by
measurement. The SPA-nav reproduction this card asked for under "What would
settle it" was never run, here or anywhere else. `verification` therefore
stays `manual` / `pending` rather than being marked passed.
