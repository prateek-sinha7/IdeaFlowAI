# ISS-419

## State of this card when 5-fixer picked it up (2026-08-31)

The card was a STUB — front-matter plus the `<!-- RELATED -->` block and nothing else. No
"What happened", no root cause with `file:line`, no blast radius, no proposed fix. The domain
register (`.kiro/bug-fix-workflow/domains/14-backend-api.md`) had it at `TESTED`, so the
analyze phase is recorded as done but its output never landed here. There was nothing to fix
*against*.

Two further inconsistencies, noted rather than acted on: the card is filed under domain 14
(backend·api) with `backend/app/api/workflows.py` in its globs, but the only test that exists
for it is a pure frontend component test with no backend involvement; and its sibling root
[ISS-306](20260828-1745-ISS-306.md) was closed by [FIX-377](20260829-0158-FIX-377.md), which
explicitly declined this card's remaining claim rather than deferring it.

## Why this is ESCALATED, not fixed

The test left by 4-test-writer —
`frontend/src/components/workflow/ReviewGatesSection.test.tsx:234,247`, two `it.fails` cases —
asserts that a step whose manifest declares `gates: ["approval"]` (and separately
`gates: ["security"]`) renders the Review-gates checklist checkbox CHECKED on fresh load.
That assertion cannot be satisfied without breaking things that are locked. It is not
merely a style disagreement:

1. **It contradicts a locked constraint on a `status: done` card.**
   [FIX-377](20260829-0158-FIX-377.md)'s `locked_constraints` reads, verbatim: "ADR-0013's
   split holds: only the two HUMAN-REVIEW gates (`human`, `before-human`) seed the checkbox;
   `conditional`, `approval` and `security` do not." FIX-377's "Not fixed here" section names
   this card and says the wider claim is "DELIBERATELY not addressed". A test may not silently
   reverse a decision a shipped fix card locked.

2. **It puts the UI one click from a `CompilerError`.**
   [ADR-0013](20260824-1630-ADR-0013.md)'s locked constraint — enforced at
   `backend/agents/workflows/compiler.py:806-811` — is that a step may declare at most ONE of
   `human` / `before-human` / `approval`, because `gate_key` is
   `f"{run_id}:{agent_id}:{visit_count}"` and carries no gate name. The checklist's write path
   `withHumanGate()` (`ReviewGatesSection.tsx`) pushes `human` into the step's existing gate
   list. Seed an `approval` step checked and the first off-then-on toggle writes
   `gates: ["approval", "human"]` — a hard compile error naming the step.

3. **The runtime dedupe does not cover `approval`.**
   `backend/agents/execution_engine/engine.py:6491` gates the WR-02 dedupe on
   `name in ("human", "before-human")`. A checked step feeds `gate_agent_ids`, which arms the
   inline HITL review; a declared `approval` on the same step is NOT deduped against it, so
   both resolve on the same `gate_key` in the same visit — the exact double-resolution the
   compiler rule exists to prevent, only now at runtime where the compiler cannot see it
   (`gate_agent_ids` is a run payload, not a manifest).

4. **Both gates are registered engineer-only, and this repo already has a UI convention for
   that — and it is not "checked".**
   `backend/agents/capabilities/gates/approval.py:25` and
   `backend/agents/capabilities/gates/security.py:20` register both `user_allowed=False`;
   `compiler.py:418-442` (`_check_trust`, CAP-03) refuses either in a user/db manifest
   outright. The established affordance for `user_allowed=false` is visible-but-LOCKED —
   `CapabilityPaletteSection.test.tsx:121`, `WorkflowDialog.test.tsx:14-16`. A live, checked,
   user-toggleable checkbox is the one rendering that convention rules out.

5. **For `security` the assertion is simply factually wrong.**
   `security` is a default-deny policy gate (`gates/security.py:1-20`), not a HITL pause. The
   checklist's own body text is "Checked agents pause the pipeline for your review after they
   finish." Checking that box for a `security` gate makes the control state something untrue.

## What the underlying complaint still is

The card's real grievance survives all of the above and is legitimate: a `custom-agent` step
has no `AGENT.md`, so `AgentDef.gate` is `null` and the manifest `gates: [...]` array is its
ONLY gate declaration — and for `approval` / `security` there is currently **no on-load
indicator anywhere in this checklist** that the step carries a gate at all. The test's own
header comment concedes the fix might be "an equivalent indicator" rather than a checked box,
but the assertion as written (`expect(screen.getByRole("checkbox")).toBeChecked()`) admits no
such reading.

## Options for whoever takes the decision

- **A — re-scope the card and rewrite the test.** Render a read-only LOCKED row (lock glyph,
  `aria-disabled`, excluded from `checkedIds` / `gatedCount` / `gate_agent_ids`) for a declared
  engineer-only gate. Satisfies the real complaint, matches the `user_allowed=false`
  convention, breaks none of 1-5. New UI affordance ⇒ a design decision, and it needs a new
  assertion; the current one would still fail.
- **B — close ISS-419 as working-as-intended.** FIX-377 already covers the two human-review
  names; `approval`/`security` are engineer-only and out of this control's scope by design.
- **C — reverse ADR-0013 / FIX-377.** Genuinely make the checklist a general gate display.
  Requires the `gate_key` change ADR-0013 rejected as out of proportion. Not a bug fix.

Nothing was edited. The test was left exactly as written (still 2 expected-fail), no
production source was touched, and no FIX card was minted.
