## Why this must also be broken

[ISS-316](20260828-1952-ISS-316.md) traced BUG-20260828-085830-runs-cancelled to
`_reconcile_terminal_status`'s `resume_supersedes` flag
(`backend/app/api/run_commands.py:811-818`), which only fires when the resumed attempt
produced a LATER, non-degraded `pipeline_complete`. Read in full, the same function's
`complete_seqs` list (line 806-808) explicitly EXCLUDES any `pipeline_complete` carrying
`payload_json.status == "degraded"`:

```python
complete_seqs = [e.seq for e in completes
                 if not (isinstance(e.payload_json, dict)
                         and e.payload_json.get("status") == "degraded")]
```

`resume_supersedes` (line 811-818) is gated on `complete_seqs` being truthy. A resumed run
whose latest attempt ends in a DEGRADED completion (some agents failed, a partial deliverable
exists — a real, reachable terminal outcome the same reconciler handles correctly for a
non-resumed run via the `elif degraded:` branch) produces a `completes` entry that is excluded
from `complete_seqs`. `complete_seqs` stays empty, so `resume_supersedes` short-circuits to
`False` on the exact truthiness check ISS-316 already identified. The very first branch then
fires unconditionally:

```python
if cancelled and not resume_supersedes:
    new_status = "cancelled"
```

...persisting `"cancelled"` even though the resumed attempt genuinely produced a degraded
outcome. This is the identical mechanism ISS-316 found for a `pipeline_failed` resume outcome,
reached instead by a `pipeline_complete(status="degraded")` resume outcome. The
`elif degraded:` branch three lines below (line 821-822) is correct in isolation but is just as
unreachable here as ISS-316's `else: "failed"` D2 fail-safe is for the failed-resume case,
because `cancelled` is always `True` for this run (the earlier cancellation is durably in the
tail) and the first `if` branch already claimed it.

## Expected vs actual

**Expected:** once a resumed run's latest attempt produces a degraded `pipeline_complete` (a
later attempt than the original cancellation, per the same `reattempt_seqs` boundary check
`resume_supersedes` already uses), `_reconcile_terminal_status` should persist
`status="degraded"` — matching what the run's own body/deliverable actually reflects.

**Actual (INFERRED — not yet independently reproduced):** `status` stays `"cancelled"` forever,
identically to ISS-316's failed-resume case, because `complete_seqs`'s degraded-exclusion feeds
directly into `resume_supersedes`, which feeds directly into the same unconditional first
branch.

## What would confirm or refute this

Seed (or find) a run that was cancelled once, then resumed via "Run Again", where the resumed
attempt ends with `pipeline_complete` carrying `payload_json.status == "degraded"` (some agents
failed, not all) rather than a clean complete or a `pipeline_failed`. Reload `/runs/{id}` and
`GET /api/runs/{id}`: a hit shows `status: "cancelled"` while the page body renders whatever the
degraded-run affordance shows (partial deliverable / some failed agents). A miss would mean
`complete_seqs`'s degraded filter is not reached the way this analysis traces — refuting this
card without affecting ISS-316.

## Where the fix belongs

Same place as ISS-316: inside `_reconcile_terminal_status`
(`backend/app/api/run_commands.py:748-838`), not in either caller
(`_drive_user_resume:740` or `stop_run_driver`, `backend/app/api/run_shutdown.py:330-332`,
which calls the same function). Whatever generalizes `resume_supersedes` to also treat a later
`pipeline_failed` as superseding (ISS-316's proposed fix shape) needs to treat a later DEGRADED
`pipeline_complete` the same way — the "latest attempt wins" reasoning has to cover all three
terminal outcomes of the resumed attempt (complete / degraded / failed), not just clean
completion, or this card's scenario survives an ISS-316-only fix untouched.
