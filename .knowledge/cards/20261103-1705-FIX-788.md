## What was wrong
Gap 2 of the workflow-gaps review, already open as [ISS-876](20261001-2110-ISS-876.md) for `limits` and `input_providers`.
`WorkflowDetail` in `backend/app/api/workflows.py` exposed steps, `manifest_steps`, deliverable, planner, clarify and
context providers, and nothing else of the file manifest. The built-in canvas seed in `page.tsx` therefore passed no
`manifest`, `needsFullManifestOnSave` was true for a built-in canvas, and `buildWorkflowManifest(..., undefined)` wrote
a copy without the top-level keys. Probe over the 39 shipped manifests: `seed_files` is declared by 37, `limits` by 16,
`capabilities` by 13, `allowed_workers` by 2, `input_providers` and `design_mode` by 1 each. `prototype_v2` and
`backlog` declare `limits {max_subagents: 200, max_depth: 2, wall_clock_seconds: 10800}`; `prototype` declares
`input_providers: [run_images]`.
## What changed
Backend (`backend/app/api/workflows.py`): new `WorkflowAuthoringManifest` model, `_authoring_manifest()` and an additive
`WorkflowDetail.manifest` field. Only declared, non-empty keys are present (`capabilities`, `limits`, `input_providers`,
`seed_files`, `allowed_workers`, `model`, `chat`, `design_mode`, `context_providers`). The model drops `None`, so an
undeclared key never appears. `null` is returned only when the manifest file cannot be read.
Frontend:
- `frontend/src/lib/api.ts`: `WorkflowAuthoringManifest` interface and `WorkflowDetail.manifest`.
- `frontend/src/store/api/userWorkflows.ts`: `builtinAuthoringSeed(authoring)` returns a shallow copy as the
  passthrough source plus `runConfig` levers for the modeled keys (`contextProvider: "opendesign"` and `designMode`,
  only when the built-in lists `opendesign`).
- `page.tsx` `/workflows/{type}/canvas` seed passes `manifest: authoring.manifest` and spreads `authoring.runConfig`.
- `ComposerPage.tsx`: a one-shot effect adopts the first real `initialManifest.capabilities`, because a built-in canvas
  receives `initialManifest` after mount.
## Product question from ISS-876
ISS-876 asked whether a copy of a built-in should inherit its `limits` and `input_providers`. The implementation answers
yes. A copy that inherits limits above the default ceilings compiles at the caller's saved-row trust: `db` (trusted) for
tiers that may run the enterprise Composer, `user` otherwise, and `user` rejects raised limits at save. That rule was
not changed.
