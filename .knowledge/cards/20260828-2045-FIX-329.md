## What was wrong

Clicking "Start a new run" on a `diverted` run's detail page (`/runs/{id}`) POSTs
`/api/runs/{id}/resume`. The backend correctly answers `409 Conflict`
(`{"error":"Run is 'diverted'; only failed, degraded, or cancelled runs are
resumable","code":"run_not_resumable","recoverable":false}`) — a diverted run has already
handed off to a successor. The UI showed nothing: no toast, no banner, no state change on the
button. BUG-20260828-020430-runs-diverted, 3/3 in the browser.

The error was never lost — `handleResumeRun`
(`frontend/src/components/layout/DashboardLayout.tsx:2253-2320`) catches it, logs
`postResume failed`, and stores `"Could not resume the run — please try again."` in
`resumeError`, handed to `RunChatLane` as `relaunchError`
(`DashboardLayout.tsx:3025`). It was simply never rendered on that path.

## Root cause

`frontend/src/components/chat/RunChatLane.tsx:1694` — the shared `relaunch(label)` helper
rendered only a `<Button>`. The amber `relaunchError` banner was hand-duplicated into two of
the four terminal branches: `cancelled` (line 1722) and `failed` (line 1808, which does not
call `relaunch()` at all — it has bespoke buttons). The two branches that DO call the helper,
`degraded` (`relaunch("Run again")`, line 1865) and the no-marker fallback
(`return relaunch("Start a new run");`, line 1871), had no error rendering whatsoever.

A diverted run carries `divertedTo` as its only pipelineState marker
(`frontend/src/hooks/useWorkflow.ts:911`; `diverted: null` in `TERMINAL_MARKER_BY_STATUS`,
`useWorkflow.ts:329`) — never `cancelled`/`failed`/`degraded` — so it lands in the no-marker
fallback, the one branch with zero error rendering. The defect is per-BRANCH inside one render
function, not per-caller: `postResume` (`frontend/src/lib/api.ts:1257`) has one production
caller, which mounts into one `<RunChatLane>` (`DashboardLayout.tsx:2985`). Blast radius
re-grepped and still holds; only the line numbers had drifted from the ISS cards
(DashboardLayout `3014 -> 3025`, api.ts `1216 -> 1257`).

## What changed and why there

`frontend/src/components/chat/RunChatLane.tsx` only, one helper:

- The `relaunchError` amber-banner block moved INTO `relaunch(label)`, which now returns a
  fragment: banner (when `relaunchError` is set) + the existing `<Button>`. All three
  call-sites (`cancelled`, `degraded`, no-marker) sit inside a `space-y-2.5` stack, so the
  fragment's children pick up the same spacing they had when the banner was inline.
- The `cancelled` branch's hand-copied banner was deleted — otherwise that branch would render
  the banner twice. The `failed` branch keeps its own copy: it never calls `relaunch()` and
  places the banner inside the "Resume options" card, above bespoke buttons.

Fixing the helper closes both ISS cards in one diff instead of patching each branch, and any
future branch that renders a relaunch button inherits the error rendering rather than having to
remember to copy it.

Not changed: `handleResumeRun`'s message text or the fact that a diverted run's button reads
"Start a new run" while calling resume. The cards scope this fix to surfacing the rejection;
re-labelling the button or routing it to a genuine new launch is a product decision no card
covers.
