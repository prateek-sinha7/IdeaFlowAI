## What is suspected

[ISS-337](20260828-1900-ISS-337.md) root-caused the failed-login error banner in
`frontend/src/app/login/page.tsx` (the `{error && (<motion.div>{error}</motion.div>)}`
block, lines 271-279) having no `role`/`aria-live` and never receiving focus. Reading the
same file in full (559 lines) shows the identical shape one block above it:

```tsx
{isExpired && (
  <motion.div
    initial={{ opacity: 0, y: -4 }}
    animate={{ opacity: 1, y: 0 }}
    className="mb-5 rounded-[var(--radius-button)] border border-[var(--status-failed-border)] bg-[var(--status-failed-fill)] px-4 py-3 text-sm text-status-failed"
  >
    Your session expired. Please sign in again.
  </motion.div>
)}
```
— `frontend/src/app/login/page.tsx:261-269`. Same missing `role="alert"`/`role="status"`/
`aria-live`, same lack of any focus move.

This banner is reached differently than ISS-337's: `isExpired` is derived once from
`searchParams.get("expired") === "true"` at mount, and the only place that sets that query
param is `handleSessionExpiry()` (`frontend/src/lib/api.ts:175-179`, read in full):

```ts
export function handleSessionExpiry(): void {
  clearToken();
  if (typeof window !== "undefined") {
    window.location.href = routes.login({ expired: true });
  }
```
— a full browser navigation (`window.location.href =`), not a client-side
`router.push`/`replace`. So this banner is present at the very first paint of a fresh page
load, not injected reactively after a user action on an already-mounted page.

## Condition

Any session-expiry redirect: a 401 on an authenticated request whose silent refresh also
fails (per ADR-0024's ladder), reached from `fetchWithAuth`'s own 401 branch, the axios
interceptor in `store/api/http.ts`, or `useHandoffSocket.ts`'s JWT-expired WebSocket close —
all three funnel through this one `handleSessionExpiry()` per its own doc comment
(`frontend/src/lib/api.ts:163-168`).

## Expected vs actual

**Expected:** per WCAG 4.1.3 (Status Messages), a screen-reader user landing on `/login`
after an involuntary session-expiry redirect is told why they are there without having to
manually explore the page.

**Actual (predicted):** the banner carries no `role`/`aria-live`, and a full
`window.location.href` navigation does not by itself guarantee the banner's text is
announced — most screen readers announce the document `<title>` on a fresh load, not
arbitrary body content, so a user would still need to discover "Your session expired..."
by scanning the page manually, the same practical outcome ISS-337 already validated for the
runtime-injected error banner.

## Why the root cause implies this — and why it is a distinct defect, not the same report

Same file, same missing-attribute pattern, same author intent (a status banner meant to be
noticed immediately) — but a genuinely different trigger mechanism (full page navigation vs
in-place `setState` after a failed fetch), so fixing ISS-337's `error` block alone does not
touch this one; they are two separate JSX blocks that would need two separate `role`
attributes (or one shared local wrapper covering both — see
[ISS-337](20260828-1900-ISS-337.md)'s fix-location note).

**Marked INFERRED**: not independently reproduced in a live browser/screen-reader session —
what is CONFIRMED (by reading `frontend/src/app/login/page.tsx` lines 261-269 and
`frontend/src/lib/api.ts` lines 175-179 directly) is that the banner carries no ARIA
live-region semantics and that it is reached via a full navigation. What would confirm or
refute the practical impact: reproduce a session-expiry redirect (e.g. force a 401 on an
authenticated request so `handleSessionExpiry()` fires) with a screen reader running (or
`axe-core`/accessibility-tree inspection at the moment of load) and confirm whether the
banner text is announced.
