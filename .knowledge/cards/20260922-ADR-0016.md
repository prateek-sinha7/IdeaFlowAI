# ADR-0016

## Decision

Remove the SonarCloud/SonarQube integration completely: the `sonar-inline` job in
`ci.yml`, the `sonar-pr` job in `ci-authoritative.yml`, the `sonar-analysis` and
`sonar-quality-gate` signals, the `SONAR_TOKEN` secret and its `workflow_call`
declaration, `sonar-project.properties`, the scanner entry in
`ci/toolchain-lock.json`, and the `--defer` flag in `tools.ci.ci_gate`.

`ci-authoritative.yml` keeps its role as the sole publisher of `ci-required` for
pull requests, but it no longer performs analysis. It attests that the source run
is a `ci.yml` pull-request run for the current head of an open PR and that the
aggregate manifest is complete, for that SHA, and green — then writes the status.

## Context

ADR-0015 split pull-request CI into an unprivileged evaluator and a trusted
finalizer, and gave the finalizer the secret-bearing analysis. That was the
correct response to the constraint at the time, but the constraint came from the
external gate itself. Carrying it forced three structural compromises:

1. `ci.yml` had to be able to hold a secret, so it declared a
   `workflow_call.secrets` input and `deploy.yml` had to map it through the
   `gate` call. "Is the gate AWS-blind?" became a question about a mapping list
   rather than about the workflow's shape.
2. Two mandatory signals could not be produced on the pull-request path, so
   `ci_gate aggregate` grew a `--defer` flag that subtracted them from the
   required set. A pull-request manifest was, by construction, not the whole
   verdict, and a non-empty deferral also skipped the `aggregate_truth()`
   cross-check.
3. The finalizer had to check out fork source and place coverage files on a
   runner that simultaneously held a secret and, in the same workflow file, a
   status-writing token.

The finalizer is still required, but not for secrets: a fork-triggered
`pull_request` run receives a read-only token and cannot write a commit status at
all, so publishing must happen from a `workflow_run` context.

## Consequences

- The aggregate is authoritative on every event type. 33 leaf signals, all owned
  inside `ci.yml`; `signal_registry` holds 34 entries (33 leaves plus the
  `ci-required` aggregate).
- `ci-required` covers every mandatory signal, so it remains the only required
  status context the rulesets need.
- `ci.yml` holds no credential of any kind. A caller that tries to pass a secret
  to it is rejected by the workflow parser rather than by review.
- Fork PRs are evaluated identically to branch PRs. A job gated on the head
  repository is now a defect, not a precaution — `test_no_job_is_skipped_for_forks`
  enforces this.
- If an external gate is reintroduced, it must not reopen (2): give it an owner
  job inside `ci.yml` that runs on every event type, or accept that `ci-required`
  does not cover it and require it as a second status context. Do not restore a
  deferral flag.
- Operator actions: delete the `SONAR_TOKEN` repository secret; uninstall the
  SonarCloud GitHub App and the `velocityai` project binding; re-apply
  `.github/rulesets/main.json` (description prose changed).
