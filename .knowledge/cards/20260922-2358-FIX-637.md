# FIX-637

Closes `BUGS.md#qa-ps-048`: "Clicking any run detail tab fires multiple
duplicate API calls". Resolves [ISS-800](20260922-1633-ISS-800.md) (root) and
its siblings [ISS-829](20260922-2001-ISS-829.md),
[ISS-830](20260922-2002-ISS-830.md) and [ISS-831](20260922-2003-ISS-831.md).

## What was wrong

Opening a run's tabs fired the same GETs several times. ISS-800 reproduced it
3/3: on the Audit tab, `gate-events`, `validation-results`, `exec-runs`,
`hook-runs` and `/family` each fired twice. The report also saw `/sandbox`
fired 4x and the full run record (`GET /api/runs/{id}`, 829 KB on the
reporter's run) fetched more than once.

## Root cause (from the cards, not re-derived)

- `frontend/src/components/results/AuditTab.tsx:463-484` (pre-fix): one
  effect ran a four-way `Promise.all`. Its `cancelled` flag guarded only the
  `setState`, never the requests. `next dev` runs React Strict Mode
  (`next.config.ts` has no `reactStrictMode: false`). Strict Mode's
  mount → cleanup → mount therefore sent all four requests twice.
- None of the fetchers had any dedupe. `getRunGateEvents`,
  `getRunValidationResults`, `getRunExecRuns`, `getRunHookRuns`,
  `getWorkflow`, `getRunFamily` and `getRunSandbox` all called the bare
  `request()`. Other fetchers in the same file already dedupe, either through
  `cachedGet()` ([FIX-617](20260922-1935-FIX-617.md)) or through their own
  in-flight maps.
- Each endpoint also had a second caller. The Steps tab's gate strip
  (`AgentThinkingTab.tsx:167-180`) reads the same gate-events as the Audit
  tab (ISS-829). `SandboxTab.tsx:1035-1066` and PreviewPanel's download
  resolver (`PreviewPanel.tsx:1341-1401`) both list `/sandbox` (ISS-830).
  `getWorkflow` has 8+ call sites and `getRunFamily` has 4 (ISS-831).

I re-ran the blast-radius grep at fix time. Line numbers have shifted, but
the cards' list still holds:

- `getWorkflow`: `page.tsx:2999`, `DashboardLayout.tsx:2350,2839,3402`,
  `PreviewPanel.tsx:880,983,1380`, `AgentThinkingTab.tsx:226,235,243`,
  `FilesTab.tsx:517`, `StartingPointCard.tsx:95`,
  `WorkflowHistory.tsx:372,393`, plus `resolveRunDeliverable` in `api.ts`.
- `getRunFamily`: `page.tsx:3188,3710`, `DashboardLayout.tsx:717`,
  `WorkflowHistory.tsx:416`.
- `getRunSandbox`: `SandboxTab.tsx`, `PreviewPanel.tsx:1386`,
  `resolveRunDeliverable`.
- `getRunGateEvents`: `AuditTab.tsx`, `AgentThinkingTab.tsx:173`.

## What changed and why there

**1. `frontend/src/lib/api.ts`: the four audit projections go through
`cachedGet()`.** Changed at `api.ts:2432` (hook-runs), `:2513` (gate-events),
`:2534` (validation-results) and `:2556` (exec-runs). The existing 404 →
empty-envelope mapping is unchanged, and failures are still not cached.
These reads need a TTL, not an in-flight guard, because of ISS-829. The Audit
tab and the Steps strip read the same gate-events one tab switch apart, and
by then an in-flight guard has already let go of the first request.

The staleness this adds is bounded. These are append-only logs. On a run
that is still going, reopening a tab can show data up to 30 s old. Any
non-GET request drops the whole cache (`dropAccountReadsOnWrite`), and that
includes a gate decision. `cachedGet`'s header comment said only catalog and
summary GETs go through it. That is no longer true, so it is amended at
`api.ts:408`.

**2. `frontend/src/lib/api.ts`: new `singleFlightGet()` (`api.ts:481-495`),
used by `getWorkflow` (`:1056`), `getRunFamily` (`:1066`) and `getRunSandbox`
(`:1299`).** It is in-flight only and keyed on token + path. The entry is
dropped as soon as the request settles. This is the same pattern as
`inFlightWorkflowDetail` ([FIX-628](20260922-2057-FIX-628.md)) and
`inFlightWorkflows` ([FIX-616](20260922-1923-FIX-616.md)), but written once
for all three fetchers. Every call site routes through these three
functions, so the guard covers all of them without editing any caller. That
includes PreviewPanel's resolver and `resolveRunDeliverable`, so
`PreviewPanel.tsx` did not need touching.

**This deviates from ISS-800's literal proposal**, which was to route these
through `cachedGet()` as well. These three change while a run is live, and
their callers read them again to see the change:

- reopening the Workspace tab lists files the run has just written;
- the run record's status flips when the run completes;
- a new revision adds a member to the family.

A 30 s TTL would serve stale data in all three cases. The card offered "an
equivalent GET-scoped in-flight/TTL map" as its alternative, and in-flight is
the safe choice for these three. ISS-831's test only requires concurrent
calls to be merged, and this does that.

**3. `AuditTab.tsx:469-486` and `SandboxTab.tsx:1046-1051`: the fetch now
starts one microtask late, and only if the effect has not been cleaned up.**
This is needed in addition to the api layer for two reasons:

- ISS-800 and ISS-830 name the effects' own missing guard as part of the root
  cause.
- Their red tests mock `@/lib/api` wholesale, so they cannot see any change
  made inside api.ts.

At the network the api layer already merges the doubles. This gate stops the
component from calling into the api twice at all. It relies on React running
Strict Mode's cleanup and re-run synchronously within one commit, before any
microtask. Both tests prove that on React 19.2.4. If React ever changes that
ordering, the gate does nothing and the api layer still merges the requests.

**Not touched:** `AgentThinkingTab.tsx` and `PreviewPanel.tsx`. Both carry
other sessions' uncommitted edits, and the two api-layer guards above already
reach their calls.

## What this does NOT cover

- **[ISS-853](20260922-2359-ISS-853.md) (open).** The Steps tab still
  downloads the full run record once every time it opens:
  `AgentThinkingTab.tsx:235` calls `getWorkflow(token, runId)` only to read
  `status` and `parentRunId`. Separate tab opens happen one after another, so
  an in-flight guard cannot merge them, and a TTL on the run record is not
  safe for live runs (see point 2). ISS-831's "not on every subsequent tab
  click" expectation is therefore met only for concurrent calls.
- **The reported "run record fetched 3x on an Audit switch" was never
  reproduced.** ISS-800 saw it fetched once, on a 249K-token run. No browser
  was used in this phase, so the live counts after the fix have not been
  measured here. That is the 6-verifier's re-run.
