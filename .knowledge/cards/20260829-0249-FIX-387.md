## What was wrong

An admin who resubmitted an email that already belongs to another user got
**zero feedback**. The backend rejected the create correctly
(`POST /api/admin/users` -> `409`, `{"detail":"A user with this email already
exists."}`), `handleCreateUser` caught the `ApiError` and called
`showToast("error", err.message)` with the right text — and the toast was
never observably on screen. The modal stayed open with the values intact and
the button re-enabled, which is indistinguishable from "still working".

Reported as `BUG-20260828-103434-admin`; validated 3/3 in
[ISS-324](20260828-1815-ISS-324.md), which confirmed the 409 and ruled out a
network/backend cause but left the mechanism open.

## Root cause

`frontend/src/app/admin/page.tsx:141-144` (pre-change):

```ts
const showToast = useCallback((type: "success" | "error", text: string) => {
  setToast({ type, text });
  setTimeout(() => setToast(null), 3500);
}, []);
```

Each call scheduled its **own independent** 3.5s dismiss timer, and nothing
ever cancelled a still-pending one — the file contained no `clearTimeout` and
no `useRef` at all. So `toast` could be nulled by an *earlier* call's timer,
which was never told a newer toast had replaced it.

That is exactly the ISS-324 repro shape: create a throwaway user
(`showToast("success", ...)` arms timer A for T+3.5s), reopen the dialog and
resubmit the same email (`showToast("error", ...)` at T+Δ). With Δ < 3.5s —
which a scripted repro produces deterministically — timer A fires and wipes
the error toast, leaving a sub-second window no DOM check realistically
catches. [ISS-487](20260829-0138-ISS-487.md) established this mechanism and
ruled out the competing "modal re-render clobbers the toast mount" candidate:
the modal and the toast are sibling `<AnimatePresence>` trees on independent
state.

## What changed, and why there

`frontend/src/app/admin/page.tsx` — one ref plus a `clearTimeout` **inside
`showToast`**, and `useRef` added to the React import:

```ts
const toastTimer = useRef<ReturnType<typeof setTimeout> | null>(null);

const showToast = useCallback((type: "success" | "error", text: string) => {
  if (toastTimer.current) clearTimeout(toastTimer.current);
  setToast({ type, text });
  toastTimer.current = setTimeout(() => setToast(null), 3500);
}, []);
```

`showToast` is the single function **all nine** toast call sites on this page
route through — `loadUsers` failure (L163), `handleUpdateTier` success/failure
(L198/L201), `handleUpdateRole` success/failure (L211/L214), `handleCreateUser`
success/failure (L228/L230), `handleDeleteUser` success/failure (L243/L245).
Verified before editing: `grep -rln "showToast" frontend/src` returns this file
and no other, so the function is not exported and the blast radius is closed.
Guarding the shared function is a three-line diff that fixes every pair of
actions; guarding only `handleCreateUser`'s error path would have left the
other eight call sites — and the create SUCCESS toast itself — racing the same
stale timer.

No unmount cleanup was added: nothing in the card asks for one, and a
`setToast` after unmount is a no-op in React 18.
