# ISS-779

## Title

[ISS-775](20260922-1330-ISS-775.md) root-caused QA-SG-004 to `handleSwitchToLiveRun`'s in-flight
replay racing a `page.tsx` remount. `page.tsx` has a SECOND function with the identical
un-awaited-async-then-immediate-push shape — `handleSelectWorkflowRun`, the "reopen a run" path
used by History's row click and by every other "open this run" caller — and, read in full, it has
NO stale-response guard anywhere in its body, unlike `handleSwitchToLiveRun`'s own
[ISS-657](20260917-1250-ISS-657.md)-derived `trackedRunIdRef.current !== runId` check.

## Why ISS-775's root cause implies this

Every caller confirmed by direct read, none inferred:

- `DashboardLayout.tsx:2747-2751` — the `onSelectWorkflowRun` prop passed to `AppHeader`:
  `onSelectWorkflowRun?.(run); setMainView("execution"); router.push(routes.runStream(run.id));`
  — fires the callback without `await`, then pushes unconditionally.
- `DashboardLayout.tsx:2956` — `WorkflowHistory`'s `onOpenRun`:
  `onOpenRun={(run) => { onSelectWorkflowRun?.(run); setMainView("execution");
  router.push(routes.runDetail(run.id)); }}` — the History list's normal row click (any run that
  is NOT the currently-active one — see `WorkflowHistory.tsx:340-346`'s `handleSelectRun`, which
  routes to `onViewRunningPipeline` only when `run.id === activeRunId`, and to `onOpenRun`
  otherwise for every other row, live or completed).
- `page.tsx:4275` — `onSelectWorkflowRun={handleSelectWorkflowRun}`: DashboardLayout's prop is
  `page.tsx`'s `handleSelectWorkflowRun` directly, the same wiring pattern confirmed for
  `onSwitchToLiveRun={handleSwitchToLiveRun}` on the very next line (`:4276`).
- `page.tsx:2846-3289` (`handleSelectWorkflowRun`, the full function body) — sets
  `trackedRunIdRef.current = run.id` synchronously at entry (`:2868`) and again after its
  `getWorkflow` fetch resolves (`:2909`), then does its own `await getRunEvents` durable replay
  (`:2978-2985`) — structurally the same two-phase shape as `handleSwitchToLiveRun`. Grepped for
  `trackedRunIdRef.current !==` across the ENTIRE function body (lines 2846-3289): zero matches.
  There is no point anywhere in this function where a superseded call can detect it has been
  superseded and stop.

`handleSwitchToLiveRun` needed exactly this kind of guard for a plain same-instance double-click
([ISS-657](20260917-1250-ISS-657.md)/[FIX-519](20260917-1323-FIX-519.md)). `handleSelectWorkflowRun`
reopens both live AND completed runs (it is the general-purpose "open this run" path — the
comment at `page.tsx:2683` notes callers avoid it FOR a currently-live run specifically because it
resets pipeline state, but nothing stops it from being invoked for a DIFFERENT live run while one
is already streaming), so it is exposed to the identical remount race
[ISS-775](20260922-1330-ISS-775.md) confirmed, with strictly less protection.

## Expected (once reproduced)

Reopening a different run from History (or any other `onSelectWorkflowRun` caller) while already
viewing a different live run's stream page lands on the newly-selected run reliably, the same
guarantee expected of the bell panel and header paths.

## Actual (inferred, not yet observed independently)

Given the missing guard, this path is at LEAST as exposed as
[ISS-775](20260922-1330-ISS-775.md)'s bell panel to the stuck/delayed switch, and — because it also
handles COMPLETED runs, whose per-run store entry is deleted on unmount rather than preserved
(`useRunStateStore.ts`'s FIX-523 guard keeps only running entries across a remount) — a superseded
reopen of a FINISHED run risks a rebuilt entry with a wrong revision count, not merely a stuck
screen. Not independently reproduced; flagged from the code path alone.

## What would confirm this

1. View a live run A's own `/runs/A/stream` page with a second live run B also active.
2. Open Run History and click a DIFFERENT run's row (B, or a completed run C) — not A's own row.
3. Check whether the app lands on B/C immediately, stalls, or reverts to A; repeat with a rapid
   double-click on two different History rows to test the missing-guard theory directly.
