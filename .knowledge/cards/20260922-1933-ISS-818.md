# ISS-818

## Sibling of ISS-816 / QA-PS-042 — same file, adjacent mechanism (concurrent double-submit, not mount double-fire)

INFERRED — found while reading `admin/page.tsx` for
[ISS-816](20260922-1931-ISS-816.md)'s blast radius, not yet reproduced by
an actual double-click.

This is a DIFFERENT mechanism from ISS-816's root cause (that is a
mount-time GET duplication; this is a click-time mutation duplication),
filed because it is the same broad flaw — a network-triggering interaction
with no re-entrancy guard — confirmed in the same file during the same
trace, under the "Concurrent: two tabs, a double submit, a race with an
async update" derivation category.

Two of the four admin mutation handlers already guard against a
double-click:
- `handleCreateUser` (`admin/page.tsx:226-242`) — its button is
  `disabled={creating || ...}` (`admin/page.tsx:530`).
- `handleUpdateTier`, via `TierDropdown`'s own `loading` state
  (`admin/page.tsx:60`, `disabled={loading}` at `:86`).

Two do not:
- `handleDeleteUser` (`admin/page.tsx:244-255`) — the confirm modal's
  Delete button (`admin/page.tsx:571-574`) has no `disabled` attribute, and
  `handleDeleteUser` sets no loading/submitted flag, so a fast double-click
  fires two `adminDeleteUser` calls (`DELETE /api/admin/users/{id}`) before
  the first resolves.
- `handleUpdateRole` (`admin/page.tsx:213-224`) — its toggle button
  (`admin/page.tsx:429-437`) is `disabled` only for the self-demotion guard
  (`user.id === currentUserId && user.is_admin`), not for an in-flight
  request, so a fast double-click fires two `adminUpdateRole` calls.

## Expected vs actual

Expected: a rapid double-click on Delete or the admin-role toggle sends
exactly one mutation request, matching the guard already present on Create
and Tier-change.

Actual (predicted, not yet measured): two concurrent identical requests;
the second `DELETE` would 404 once the first completes (user already
gone), which — depending on how the surrounding `catch` block surfaces it —
may flash a spurious "Failed to delete user" toast even though the
deletion succeeded.

## What would settle it

Rapid double-click the Delete confirm button (or a role toggle) against a
live backend and watch the network panel for two requests instead of one;
check whether the second request's failure produces a visible error toast.

## Fix

Add the same `disabled`/loading guard `handleCreateUser` and
`TierDropdown` already use — a local `deleting`/`updatingRole` state (or a
`Set<string>` of in-flight user ids, since multiple rows can be acted on
independently) disabling the specific row's button while its request is in
flight. This is a per-handler UI guard, not a `lib/api.ts` change — unlike
ISS-816/817, dedupe-by-URL in the shared request layer would not obviously
be correct here (two rapid genuine user-intended deletes of DIFFERENT
users must not be coalesced), so the fix belongs locally in
`admin/page.tsx`, mirroring the pattern its own sibling handlers already
use.

## Resolution — [FIX-626](20260922-2045-FIX-626.md), 2026-09-22

Fixed exactly as prescribed above, locally in `admin/page.tsx`, not in
`lib/api.ts`:

- `deleting` (boolean — only one delete-confirm modal exists at a time):
  `handleDeleteUser` early-returns while a delete is in flight, and the
  modal's Delete button is now `disabled={deleting}`.
- `rolePending` (a list of user ids — separate rows are independent actions
  and must not block each other): `handleUpdateRole` early-returns for a
  user id already in flight, and that row's toggle is disabled alongside
  its existing self-demotion guard.

Honest limit: no double-click reproduction was ever run — this card was
INFERRED from a direct read and is closed the same way. The guards are
present in the source and the 23-scenario admin e2e suite
(`tests/integration/e2e/suites/11_admin/test_admin.py`: 22 passed, 1
skipped, 0 failed) shows they do not block the normal single-click paths,
but nothing asserts the double-click case. `verification` stays `manual` /
`pending`.
