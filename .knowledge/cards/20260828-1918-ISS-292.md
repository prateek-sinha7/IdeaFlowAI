## What happened

`/settings/ai-model`'s "Pipeline model" selector presents all 9 catalog models — including the
two "powerful"-tier (most expensive) models, Claude Opus 4.5 and Claude Opus 4.6 — to every
account regardless of subscription tier, with no lock icon, no "upgrade to unlock" copy, no
disabled option, and no tier badge gating the option itself (each option's own `tier` metadata —
`"fast"`/`"balanced"`/`"powerful"` — is rendered as plain descriptive text only). A `qa-basic`
tier account (`tier: "basic"`) can select either Opus model from the dropdown and click Save; the
request succeeds with a plain `200 OK`, shows the identical "Model preference saved" confirmation
any other model gets, and survives both an in-session reload and a fresh cold login.

Confirmed **CONFIRMED, 3/3, cold start every cycle** (fresh `localStorage.clear()` +
re-login as `qa-basic@flowinqa.com` before every attempt):

- **Cycle 1** (deep-link entry, `page.goto('/settings/ai-model')`): selected "Claude Opus 4.5 ·
  powerful", clicked Save → "Model preference saved" shown; a subsequent cold reload of the same
  URL confirmed Opus 4.5 still selected.
- **Cycle 2** (deep-link entry again, following on from cycle 1's persisted state): selected
  "Claude Opus 4.6 · powerful" (the single most expensive model in the catalog), clicked Save →
  saved identically, no rejection.
- **Cycle 3** (different entry path — account menu → "Account Settings" → "AI Model" tab, per
  `bug-hunter/velocity.json`'s documented `[role="menuitem"]` JS-click quirk, rather than a deep
  link): landed on `/settings/ai-model` with Opus 4.6 still selected from cycle 2, all 9 models
  still listed with zero gating.

Both entry paths (deep link and in-app click-through) and both premium models reproduce
identically — no variation was needed to name a trigger; the absence of gating is the trigger.

This is a genuine gap in the app's own stated tier model, not an oversight the app is silent
about elsewhere: the **same basic-tier session's dashboard already renders explicit tier gates**
(`Requires Pro plan` / `Requires Enterprise plan` disabled launch cards for restricted pipelines —
observed directly during cycle 3's account-menu navigation), and `/api/capabilities` carries
`security_gated`/`user_allowed` flags for exactly this purpose. `backend/app/api/settings.py`'s
`available_models` catalog builder and its `PUT` handler apply neither.

## Expected vs actual

- **Expected:** a basic-tier account should not be able to select or persist "powerful"-tier
  models (Opus 4.5/4.6) without an upgrade path, mirroring the tier-gating pattern already present
  on the dashboard's launch cards and in `/api/capabilities`.
- **Actual:** no tier restriction exists anywhere in the flow — not in the API's model catalog
  (`GET /api/settings/preferences`'s `available_models` is byte-identical across tiers), not in
  the save endpoint's validation (`PUT /api/settings/preferences` accepts any `preferred_model` id
  with `200 OK`, no 403/validation error), and not in the UI (`AccountSettings.tsx`'s model
  `<select>` renders `tier` as descriptive text only, no per-option disabling).

## Conditions established

- Route: `/settings/ai-model`, component `frontend/src/components/settings/AccountSettings.tsx`
  (AI Model tab).
- Tier: `qa-basic` (basic) — the account most exposed by the gap, given
  `TIER_PIPELINES["basic"]` in `backend/app/core/entitlements.py` restricts it elsewhere in the
  app.
- Entry path: reproduces identically via a cold deep link and via account-menu click-through; not
  a factor.
- Timing/session age: not a factor — reproduces on first click after page settle and survives
  both a same-session reload and a fresh cold login.
- Data/run state: not applicable to this page.

## Root cause

CONFIRMED — two independent gaps, one per layer, both traced to file:line.

**Backend (`backend/app/api/settings.py`):**
- `AVAILABLE_MODELS` (settings.py:46-54) is a module-level constant — the full 9-model
  `ModelCatalog().list()` projection, computed once at import time, before any request or user
  context exists. It carries no tier parameter by construction.
- `get_preferences` (settings.py:305-313) returns `available_models=AVAILABLE_MODELS` verbatim to
  every caller, regardless of `user.tier`.
- `update_preferences` (settings.py:316-342) validates `payload.preferred_model` only against
  `_VALID_MODEL_IDS` (settings.py:57, `set(ModelCatalog().ids())` — again the full catalog, no
  tier scoping) and never reads `user.tier` at all — the function has no tier-aware branch of any
  kind.
- There is no analog of `backend/app/core/entitlements.py`'s `TIER_PIPELINES`/`can_run_pipeline`
  for models (confirmed by reading `entitlements.py` in full — it maps tier to allowed *pipeline
  types* only, zero knowledge of `ModelEntry.tier`/`cost_class`). This is a genuinely ABSENT
  capability, not a wiring gap like `FIX-189` (which forgot to call an EXISTING
  `can_run_pipeline` check) — nobody ever built a model-tier gate.
- `agents/capabilities/model_catalog.py:16-18` says this outright: "No per-owner trust
  enforcement / `user_allowed` gating here (Phase 8, N11): every entry is `user_allowed=True`
  today, including both Opus tiers." That `user_allowed` is the CAP-03 *trust* flag (engineer- vs
  user-composable capability, `capabilities.py:9-15`) — a different axis from account
  subscription tier, and the two must not be conflated when this is fixed.

**Frontend (`frontend/src/components/settings/AccountSettings.tsx`):**
- `userTier` is fetched and stored (AccountSettings.tsx:124-125, `const t = (user.tier as Tier) ||
  "basic"; setUserTier(t);`) and used elsewhere on the same page (`getBasePipelines(tier)` at
  line 80-83, for the Usage & Limits tab) but never consulted by the model `<select>`.
- The model `<select>` (AccountSettings.tsx:361-376) maps `availableModels` unconditionally —
  `{availableModels.map(m => <option key={m.id} value={m.id}>{m.name} · {m.tier}</option>)}` — no
  `disabled`, no lock icon; `m.tier` is read only for display (the badge at line 389, inline text
  at line 374).
- Same recurring pattern as `ISS-321` (sibling bug on a different page,
  `app/[...view]/page.tsx`, under `BUG-20260828-094937-settings-usage-r2`): tier is fetched for
  display and never wired into a gate at the new surface. `HomeLaunchGrid.tsx:288`
  (`disabled={!allowed}`) is the one place in this codebase that DOES gate correctly, driving off
  `frontend/src/lib/entitlements.ts`'s `TIER_PIPELINES`/`canRunPipeline` — a hand-kept mirror of
  the backend's `entitlements.py`, with its own parity test
  (`backend/tests/unit/test_entitlement_parity.py`). No such mirror or parity test exists for
  models.

## Blast radius

Grepped every caller of `AVAILABLE_MODELS` / `_VALID_MODEL_IDS` (both private to `settings.py`;
no other backend module imports them) and every reader of `user.preferred_model`:

- `GET /api/settings/preferences` (settings.py:305-313) — ungated catalog visibility, every tier.
- `PUT /api/settings/preferences` (settings.py:316-342) — accepts and persists ANY catalog model
  id for ANY tier, 200 OK, no 403.
- `AccountSettings.tsx`'s AI Model tab (frontend:361-376) — renders every option unconditionally.
- **Not cosmetic** — CONFIRMED `user.preferred_model`, once persisted through the broken `PUT`, is
  read back and threads into REAL pipeline execution at 8 call sites in
  `backend/app/api/run_commands.py` (lines 1443, 1604, 2921, 3251, 3362, 3696, 3819, 3833), most
  concretely `run_commands.py:3251`'s `engine.execute(..., model_id=getattr(user,
  "preferred_model", None) or None, ...)` inside the live run-driving path — so a basic-tier
  account's unauthorized Opus selection genuinely drives Bedrock model choice (and premium-tier
  billing) on every subsequent run, not just the settings-page display. This confirms the
  register's "cost-driving" framing with file:line evidence rather than assumption.
- A second, currently-unreachable client (`frontend/src/store/api/settings.ts`'s
  `settingsApi.getPreferences`/`updatePreferences`) hits the identical unguarded endpoint but has
  zero live callers today (confirmed via grep across `frontend/src` for
  `.settings.getPreferences`/`updatePreferences`/`settingsApi.getPreferences`/`updatePreferences`
  — none found). Not part of the live blast radius; flagged only so a future wiring of that client
  doesn't reopen this silently.
- **Sibling caller with the identical flaw, filed separately:** [ISS-398](20260828-2106-ISS-398.md)
  — `_validate_model_overrides` (`backend/app/api/run_engine.py:547-607`), the per-agent
  `model_overrides` validator used by run launch (`run_commands.py:2900`) and composer save/
  update (`user_workflows.py:566`, `807`), checks `model_id` against the full `ModelCatalog.ids()`
  with no tier parameter at all — same missing check, different door.

## Proposed fix — where it belongs

The gate belongs in `backend/app/core/entitlements.py`, alongside `TIER_PIPELINES`/
`can_run_pipeline` — the existing single source of truth for tier gating, already the pattern
every launch-path consumer follows per `FIX-189`'s precedent. Concretely:

- Add a model-tier table (e.g. `TIER_MODEL_COST_CLASSES: dict[Tier, set[str]]` keyed off
  `ModelEntry.cost_class`, the same shape as `TIER_PIPELINES`) and a `can_use_model(user_tier,
  model_id)` helper next to `can_run_pipeline`.
- `settings.py`'s `get_preferences` filters `AVAILABLE_MODELS` by `user.tier` before returning, so
  the response is already scoped and the frontend needs no separate filtering logic.
- `settings.py`'s `update_preferences` calls `can_use_model(user.tier, model_id)` and 403s (not
  422 from `_VALID_MODEL_IDS`, to distinguish "unknown model" from "not entitled") on a disallowed
  model — mirroring `can_run_pipeline`'s 403 convention at launch.
- `run_engine.py`'s `_validate_model_overrides` ([ISS-398](20260828-2106-ISS-398.md)) takes the
  requesting user's tier as a parameter and calls the SAME `can_use_model` helper for every
  `model_id` in the override map.
- Import direction is safe: `backend/app/core/entitlements.py` is `app.core`, and the
  import-linter contract "agents.capabilities must not import the execution kernel or the web
  layer" (`backend/pyproject.toml:209-213`) is one-directional (`agents.capabilities -> app`
  forbidden; `app -> agents.capabilities` — which `settings.py` already does at line 19 — is the
  allowed direction). Confirmed by reading the contract; no import-linter change needed.
- One shared check, two write paths (`settings.py`, `run_engine.py`); every downstream reader of
  the persisted values (`run_commands.py`'s 8 `preferred_model` sites, the 3 `model_overrides`
  sites) inherits the fix automatically because they can never observe an unauthorized value
  having been stored in the first place — no per-caller guard needed.
