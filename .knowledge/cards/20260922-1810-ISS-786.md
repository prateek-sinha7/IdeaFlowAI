## What happened

INFERRED sibling of [ISS-741](20260922-1207-ISS-741.md) (root card for QA-SG-003,
`BUGS.md#qa-sg-003`) — not reproduced live. Filed because the root cause implies
it, not because it was observed.

ISS-741 root-caused the run-detail/run-history loop to `DashboardLayout.tsx`'s
`onBackToHistory` calling `router.push(routes.runHistory())` where `handleBackNav`
(`DashboardLayout.tsx:1811`, comment block starting `DashboardLayout.tsx:1767`)
already establishes the correct pattern: `window.history.length > 1 ?
router.back() : router.push(routes.home())`. The comment on `handleBackNav`
states plainly it is "the one handler all five page mounts already route
through" — a grep confirms exactly five `onBack`/`onClose` props inside
`DashboardLayout.tsx` are wired to it: `WorkflowHistory` at `:2942`,
`AccountSettings` at `:3025`, `AnalyticsPage` at `:3039`, `IdeaInputPage` at
`:3069`, `ComposerPage` at `:3122`.

Two more "Back"-labeled controls exist OUTSIDE that list, in components mounted
by their own standalone Next.js routes rather than by `DashboardLayout`'s
`mainView` switch, and each reimplements its own unconditional push instead of
routing through `handleBackNav`:

1. `frontend/src/components/workflow/LaunchWizard.tsx:1037-1038` —
   `onClick={() => router.push(routes.home())}`, `aria-label="Back to
   dashboard"`. Mounted by `frontend/src/app/workflow/create/page.tsx:48`
   (`return <LaunchWizard initialMode={mode} />;`), the "`/workflow/create` —
   the ONE unified deliverable-launch route (plan 37-07)" per that file's own
   docstring. This route is live, not dead code: `routes.ts:79`'s
   `workflowCreateLegacy` builder is called from
   `frontend/src/components/home/CreationHub.tsx:31,35` and
   `frontend/src/components/layout/DashboardLayout.tsx:1621,1648` — every
   prototype/ppt launch from Home funnels through it today (`routes.ts:71-76`
   documents it as legacy-but-live: "Not a MainView — `/create/ppt`,
   `/create/prototype`... redirect here today... Retired by FR-007/T17... kept
   as a builder... until that redirect lands").

2. `frontend/src/components/workflow/WorkflowView.tsx:176-178`'s `handleBack`
   (`if (step === "build") onClose();`), wired to the "Back" icon button at
   `WorkflowView.tsx:236-238` (`aria-label="Back"`). Mounted by
   `frontend/src/app/workflow/page.tsx:99` as `onClose={() =>
   router.push(routes.dashboard())}` — the standalone `/workflow` route.
   Unlike #1, no builder in `routes.ts` produces a bare `/workflow` path and no
   grep of the frontend finds an in-app link/push targeting it, so this
   instance's live reachability (as opposed to the code path existing on disk)
   is weaker than #1's — recorded here rather than dropped, per the "other
   callers with the same flaw" sweep, and flagged for a reachability check
   rather than asserted as reachable.

## Why the root cause implies this

Same shape as ISS-741: a control labeled "Back" performs an unconditional
`router.push(<fixed route>)` instead of `router.back()`. ISS-741's own
mechanism needs a SECOND control on the far side that legitimately calls
`router.back()` and lands back on the just-repushed entry to produce the
visible two-screen oscillation; that second half is not independently
confirmed for either instance here (the dashboard/home view is the app's
landing surface and was not shown, in this pass, to carry its own "back"
control). What IS confirmed by direct read is the shared anti-pattern itself
— push, not back, for a "Back"-labeled affordance — in components that
structurally sit outside the one place (`handleBackNav`) that already carries
the correct, guarded implementation, and that `DashboardLayout`'s own comment
says every other in-app "Back" routes through. Any push-based "Back" adds a
redundant history entry regardless of whether a second control turns that
into a visible loop; at minimum it corrupts the browser's native Back/Forward
stack for these two routes the same way ISS-741 corrupts it for run
detail/history.

## What would confirm or refute this

Not reproduced — this card is the hypothesis, not the observation. To settle
it:

- **LaunchWizard**: from Home, launch a prototype or ppt workflow (pushes
  `/workflow/create` via `workflowCreateLegacy`), click "Back to dashboard",
  then use the browser's native Back button (not an in-app control) and
  confirm whether it lands on `/workflow/create` again instead of wherever the
  user was before Home — the same class of stuck loop ISS-741 shows for run
  detail/history.
- **WorkflowView**: first confirm `/workflow` is still a supported entry point
  at all (no in-app control was found linking to it in this pass) rather than
  orphaned legacy code; if it is reachable, repeat the same native-Back check
  after clicking its "Back" icon.

## Fix

Same direction as ISS-741: route both controls through the existing
`window.history.length > 1 ? router.back() : router.push(<fallback>)` guard
instead of an unconditional push. Because neither component mounts inside
`DashboardLayout`, they cannot call its private `handleBackNav` directly — the
guard belongs in one small shared helper (e.g. `frontend/src/lib/routes.ts` or
a new `frontend/src/lib/navigation.ts`) that `DashboardLayout.handleBackNav`
and these two standalone routes all call, so ISS-741's fix and this one land
in the same place instead of three independently-maintained copies of the
same guard.
