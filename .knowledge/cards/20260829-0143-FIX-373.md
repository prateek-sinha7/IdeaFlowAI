## What was wrong

`/runs/a0693fcd-9451-4c19-a9e7-61474ea03516` rendered "just now · 22m 0s · **17.9K
tokens**" in the chat header under the run title, while the Run History list card for
the same run, `GET /api/runs/{id}`, and the Analytics page all showed 10.4K.
[ISS-304](20260828-1600-ISS-304.md) recorded it 3/3 on cold direct-URL loads — not a
stale-render artifact, not timing/tier/theme dependent.

Re-measured against the live app before editing (qa-admin, `POST /api/auth/login`),
and the card's numbers hold exactly:

```
GET /api/runs/a0693fcd-.../         token_usage.total_tokens = 10428  (in 6150 / out 4278)
GET /api/runs/a0693fcd-.../events   3666 rows
  agent_complete ppt-brief-analyst  2050 / 186  = 2236
  agent_complete ppt-composer       2050 / 2046 = 4096
  agent_complete ppt-validator      2050 / 2046 = 4096
  agent_complete SUM                6150 / 4278 = 10428   ← matches token_usage exactly
  pipeline_complete                 7549 / 10382 = 17931  ← what the header was showing
```

## Root cause

`frontend/src/hooks/useWorkflow.ts:791-796` (pre-change), the `pipeline_complete` case
of the shared `handlePipelineMessage` reducer:

```ts
// Prefer the backend's authoritative totals, but fall back to the
// values accumulated from agent_complete so a missing field never
// wipes the token card to zero.
totalInputTokens: (msg.total_input_tokens as number) || prev.totalInputTokens || 0,
totalOutputTokens: (msg.total_output_tokens as number) || prev.totalOutputTokens || 0,
totalTokens: (msg.total_tokens as number) || prev.totalTokens || 0,
```

The comment's premise is what is wrong: `pipeline_complete.total_*` is **not** the same
authority the rest of the app reads. Two backend paths compute "tokens for this run"
from different result sets and nothing reconciles them —

- the engine's event (`backend/agents/execution_engine/engine.py:3712-3726`) sums the
  per-agent results **plus** `aux_token_usage`: the SmartPlanner (`engine.py:2122`), a
  clarify one-shot (`engine.py:2265`) and the validation fix-loop sub-agent
  (`engine.py:2443`), folded in deliberately by ISS-033 so that spend is not dropped;
- the persisted `workflow_runs.token_usage` column — written **only** by
  `_apply_terminal_output_columns` (`backend/app/api/run_commands.py:3057-3065`, "the
  SOLE writer of these columns") — re-derives its totals from `agent_outputs_collector`,
  i.e. `agent_complete` events alone, and walks straight past the event's own totals
  (`run_commands.py:3042-3045` reads only `final_output`/`deliverable_mimetype`/
  `deliverable_filename`).

`prev.totalTokens` at the moment `pipeline_complete` lands is the `agent_complete`
reduction (`useWorkflow.ts:691-701`) — the *same* set `token_usage` is built from, so it
equals 10428 here. Taking `msg.total_tokens` instead put the aux-inflated 17931 on screen.
`LaneRunHeader.deriveLaneMeta` (`frontend/src/components/chat/LaneRunHeader.tsx:76-77`)
renders `pipelineState.totalTokens` verbatim, so the header surfaced it unreconciled.

Same authority-split shape as [ISS-150](20260813-0439-ISS-150.md) (`total_duration` vs
`workflow_runs.duration`), on the token axis.

## What changed and why there

One file, three expressions, `frontend/src/hooks/useWorkflow.ts:791-804`. The preference
is inverted and the event fields are demoted to the fallback:

```ts
totalInputTokens: prev.totalInputTokens || (msg.total_input_tokens as number) || 0,
totalOutputTokens: prev.totalOutputTokens || (msg.total_output_tokens as number) || 0,
totalTokens: prev.totalTokens || (msg.total_tokens as number) || 0,
```

**Why the reducer and not the renderer.** `handlePipelineMessage` is the single funnel
both transports route through — the live SSE stream and the cold-load durable REST
replay (`getRunEvents` → `handleWebSocketMessage`, `app/[...view]/page.tsx:2848` and the
five other replay entry points) — and the page makes exactly **one** `useWorkflow()` call
(`app/[...view]/page.tsx:2087`) whose `pipelineState` is passed by prop to every token
renderer. Blast radius re-grepped before editing and it still holds: `LaneRunHeader.tsx:76`
(ISS-304's reported surface), `TokenUsageSummary.tsx:19-28` mounted at
`AgentThinkingTab.tsx:321` ([ISS-417](20260828-2230-ISS-417.md)) and
`ChatTokenWidget.tsx:82-95` all read that one object and compute nothing of their own.
One expression in the reducer fixes all three; a patch to `LaneRunHeader` would have left
the other two wrong.

All three totals moved together on purpose. Moving only `totalTokens` would have left
`totalInputTokens + totalOutputTokens ≠ totalTokens` in `TokenUsageSummary` and
`ChatTokenWidget`, which both render the split beside the total — a new inconsistency in
place of the old one.

The `|| 0` tail and the original zero-guard intent are preserved: a run with no
`agent_complete` accumulation still falls back to the event's fields, so the token card
never blanks. `estimatedCostUsd`, `cacheReadTokens` and `cacheWriteTokens` were left on
their existing expressions — outside this card's claim, and changing the cost figure has
its own blast radius.

**Deliberately NOT done: the backend.** [ISS-304](20260828-1600-ISS-304.md)'s analyzer
addendum proposes `_apply_terminal_output_columns` as the fix point, and that is right
for the *aggregate undercount* — but it cannot be this fix, for two reasons recorded here
rather than silently:

1. It is a product decision the card itself declines to make ("whether 'total tokens for
   this run' should include planner/clarify/fix-loop overhead is a product call this
   analysis can't make from the code alone"), and it moves every historical Analytics
   figure. Per the fixer's escalation rule that is not a call to take inside a fix.
2. It cannot satisfy ISS-304's own **Expected** or the test written from it.
   `_apply_terminal_output_columns` writes at run terminal time only; run `a0693fcd-…`
   already holds `token_usage.total_tokens = 10428` and a durable `run_events` row
   carrying `total_tokens: 17931`. Neither is rewritten by a change to the writer, so
   no backend-only edit turns that header green. Verified against the live API above.

[ISS-418](20260828-2231-ISS-418.md) — the persisted column excluding real aux spend, and
Analytics undercounting because of it — is therefore **left open** and is the correct home
for that decision. This card makes the five readers agree on one number; ISS-418 decides
which number that should be.

## Observed, NOT fixed, NOT mine

- [ISS-418](20260828-2231-ISS-418.md) stays open by design — `workflow_runs.token_usage`
  still excludes `aux_token_usage`, so Analytics still undercounts planner/clarify/
  fix-loop spend. That is the product call, and it belongs in
  `_apply_terminal_output_columns`.
- [ISS-417](20260828-2230-ISS-417.md) is cured by construction — `TokenUsageSummary`
  reads the same `pipelineState` object this change repaired — but is left `open`
  because its own card asks for a live Steps-tab confirmation that was outside this
  dispatch's scope (cards given: ISS-304 only). One click on `tab-thinking` at
  `/runs/a0693fcd-9451-4c19-a9e7-61474ea03516` closes it.
- `useWorkflow.ts:800-801` sets `cacheReadTokens`/`cacheWriteTokens` from `agent_complete`'s
  `total_cache_read_tokens` by **overwrite, not sum**, so a multi-agent run keeps only the
  last agent's cache split. Pre-existing, unrelated to the token total, not touched.
