# ISS-925

**Bug register entry:** derived from QA-KB-020 (`BUGS.md#qa-kb-020`, `LEDGER.md`) — root-cause card [ISS-654](20260917-1250-ISS-654.md)

## Status: INFERRED — not yet reproduced

The code path below is CONFIRMED by reading it. Its visible effect (stale "review required"
lines in the lane) has NOT been observed in a browser. Whoever picks this up should confirm it
before treating it as a defect (see "What would confirm this").

## Why QA-KB-020's root cause implies this

[ISS-654](20260917-1250-ISS-654.md)'s mechanism is that a family transcript merges several runs'
gate cards into one array while the code that decides which card is "resolved" has no run
identity. `ChatMessage.resolved` is written in exactly TWO places in `useRunChat.ts`, and both
ignore run identity:

1. the `review_gate_approved` handler (`useRunChat.ts:574-583`) — ISS-654, picks the wrong card;
2. the terminal auto-resolve in `seedTranscript` (`useRunChat.ts:750-756`) — keyed on ONE flag
   for the whole merged transcript. [ISS-664](20260917-1310-ISS-664.md) is its over-resolution
   (a rejected/cancelled run reads "approved"). This card is its UNDER-resolution.

This card is also what leaves a later-positioned stale gate card in the array for ISS-654's
positional match to pick, so the two defects compound.

## Mechanism (CONFIRMED by reading the code)

The history-reopen family seed keeps only chat frames for every member except the opened run.
A member's `review_gate_approved` frame is not a chat frame, so it is dropped:

```ts
// frontend/src/app/[...view]/page.tsx:3164-3172
// Keep only chat frames — pipeline reducer frames for other members
// are intentionally excluded (they'd overwrite pipelineState which
// should reflect the OPENED run, not every family member's agents).
memberFramesByMemberId.set(
  m.id,
  result.value.filter(
    (f) => f.type === "chat_message" || f.type === "chat_reply",
  ),
);
```

The terminal flag handed to the seed describes the OPENED run only:

```ts
// frontend/src/app/[...view]/page.tsx:3222-3224
// Pass isTerminalRun=true for completed/failed/cancelled/degraded runs so
// gate chat_reply cards are auto-resolved (no pending review box).
seedRunChatTranscript(familyChatFrames, REOPEN_TERMINAL_STATUSES.has(fullRun.status));
```

and the hook resolves cards only when that flag is true:

```ts
// frontend/src/hooks/useRunChat.ts:750-756
if (isTerminalRun) {
  setMessages((prev) =>
    prev.map((m) =>
      (m.cardKind === "gate" || m.cardKind === "clarify") && !m.resolved ? { ...m, resolved: true } : m
    )
  );
}
```

So when the opened run is NOT terminal (a live or parked revision), every gate card of an
earlier or later family member is seeded `resolved: undefined`, even for a member that finished
long ago with all its gates approved. The revision-launch remount path does the same for every
member including the live run, with a hard-coded `false`:

```ts
// frontend/src/app/[...view]/page.tsx:3688-3698
const mFrames = mid === runId
  ? durableFrames
  : await getRunEvents(tok, mid);
const chatOnly = mFrames.filter(
  (f) => f.type === "chat_message" || f.type === "chat_reply"
);
allFrames.push(...chatOnly);
...
seedRunChatTranscript(allFrames, false);
```

The lane renders the transcript unfiltered (`DashboardLayout.tsx:3283`, `messages={runChatMessages ?? messages}`)
and an unresolved gate card renders as inline text plus a link:

```tsx
// frontend/src/components/chat/ResultCard.tsx:147-151, 165-175
: kind === "gate"
? message.agentName
  ? `${message.agentName} review required`
  : "Review required"
...
{kind === "gate" && !message.resolved ? ( <button ...>Open in Steps</button> ) : ...}
```

`MessageBubble.tsx:215-222` binds that link to the run that MINTED the card (`message.runId`),
so a stale card of another family member offers "Open in Steps" for a gate that is not open.

## Expected (once reproduced)

A gate card of a family member whose gate was approved reads "<Agent> review approved —
build continues", whichever family member is being viewed and whether or not the viewed run is
terminal. A gate that was never approved (rejected, failed) must NOT read as approved
(ISS-664).

## Actual (inferred, not yet observed)

Viewing a non-terminal run of a family that has a completed member shows that member's gate
cards as "<Agent> review required" with an "Open in Steps" link. A terminal opened run hides it:
`isTerminalRun: true` flips every gate card in the merged array, including other members'.

This is the COMMON revision flow, not a corner: the remount effect at `page.tsx:3569-3722` runs
when the page remounts onto a live run after `router.push` (the revision-launch path), and it
seeds every member chat-only with a hard-coded `false`. So "launch a revision from a completed
run that had review gates" would show the parent's gates as pending in the lane. By contrast
[ISS-654](20260917-1250-ISS-654.md)'s cross-run flip needs a revision minted while the parent is
still open, which the lane's own chat router never does.

## What would confirm this

1. Offline, mechanism only: `renderHook(useRunChat)`, then
   `seedTranscript([gate chat_reply with pipeline_run_id "P"], false)` — the card has
   `resolved` undefined. This proves the seed has no way to resolve it, not that the display is
   wrong.
2. In the browser, no paid run needed: find a family whose LATEST member is non-terminal
   (`GET /api/runs?limit=50`, look for a `*_revision` run in `waiting_for_user` / `revising`
   whose parent has a gate), open `/runs/<that id>`, and read the lane for "review required"
   lines that belong to the parent.

## Fix direction (INFERRED, not a decision)

The seed already holds what it needs: each member's own durable frames, and
`getRunFamily().members[].status` (`backend/app/api/runs.py:1594`).

- Preferred: keep each other member's `review_gate_approved` frames in the seed (extend the two
  chat-only filters, `page.tsx:3169-3172` and `:3691-3693`). It is faithful to what happened,
  so a rejected member stays unapproved (ISS-664) and an approved one resolves. Land it with or
  after the [ISS-654](20260917-1250-ISS-654.md) run-id guard, which is what makes folding another
  member's approvals safe.
- Alternative: resolve a member's gate cards from its terminal status. This must not mark a
  cancelled/failed member as approved, which is exactly ISS-664.

## Blast radius

Two seed sites in `page.tsx` (`:3164-3172` history reopen, `:3688-3698` revision remount, the
remount effect starts at `:3569`). `handleSwitchToLiveRun` seeds one run's FULL frames
(`page.tsx:2823`), so it is unaffected.
Display only: the Steps-panel gate UI is run-keyed (`page.tsx:2180-2188`).
