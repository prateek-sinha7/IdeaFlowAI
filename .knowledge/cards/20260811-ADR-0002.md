# ADR-0002

## Decision

In the context of two live vocabularies for one concept — `workflow` in the manifests
and `pipeline` in the engine and registry — facing a "temporary" migration alias that
outgrew the term it was aliasing, we decided that `workflow` is the only vocabulary the
system knows and `pipeline` is removed rather than deprecated, to achieve one name per
concept enforced by a grep gate, accepting a breaking wire-protocol rename and a
coordinated frontend/backend release.

**Area:** engine, registry, api, frontend, naming

## Implementation blast radius (measured 2026-08-31, 5-fixer)

The grep gate `backend/tests/unit/test_workflow_vocabulary_gate.py` is in place
and red: `4 xfailed` — all four governed files still carry `pipeline`
(loader.py 54 lines, registry.py 130, engine.py 435, CLAUDE.md 60).

It is **not implementable inside the four governed globs.** The `pipeline`
identifiers there are the system's public vocabulary, not local names:

- `pipeline_type` is the AGENT.md frontmatter key parsed by
  [backend/agents/loader.py:465](../../backend/agents/loader.py) — **94 AGENT.md
  files on disk** declare it.
- `SUPPORTED_PIPELINE_TYPES` (loader.py:624) is imported by 22 backend modules;
  `PIPELINE_AGENTS` by 26.
- `pipeline_type` / `pipeline_run_id` are the parameter names of the engine's
  public entrypoints `compile_for_run` (engine.py:645) and `execute`
  (engine.py:1080) and are emitted as **wire keys** in the event payload at
  [backend/agents/execution_engine/engine.py:134](../../backend/agents/execution_engine/engine.py) —
  consumed by 93 frontend `.ts/.tsx` files (`frontend/src/types/index.ts:149`).
- 122 backend `.py` files reference `pipeline_type`.
- Three **DB columns** carry the label: `workflow_definitions.base_pipeline_type`
  (alembic 0021), `workflow_definitions.overrides_pipeline_type` (alembic 0039),
  `handoff_tasks.pipeline_output` (alembic 0002).

**Blocking invariant:** those column renames are not additive, and
`.knowledge/CONTEXT.md` requires *"Database migrations are additive only."*
Separately, CONTEXT.md phrases INV-1/SC-001 itself as ``no `if pipeline_type ==` ``,
so the CI gate's own definition moves with the rename.

The ADR's own text accepts *"a breaking wire-protocol rename and a coordinated
frontend/backend release"* — that is a release decision, and this card remains
`status: deferred` pending it. Options, none of which a fixer may pick alone:

1. Execute the full rename as its own coordinated spec (backend + 94 AGENT.md +
   frontend + a non-additive migration waiver).
2. Narrow ADR-0002's `applies_to.globs` to the surface that can actually be
   renamed without a wire/DB break, and re-scope the gate to match.
3. Supersede ADR-0002 with a decision to keep `pipeline_type` as the on-disk /
   on-wire name and confine `workflow` to new surfaces.
