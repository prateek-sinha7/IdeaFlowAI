## Condition

[ISS-332](20260828-2041-ISS-332.md) reproduced the search/folder-filter + stale-footer-count bug
only via the standalone `/preview-fullscreen` route (`frontend/src/app/preview-fullscreen/page.tsx:118`).
The broken code — `FileTreeNode`'s unconditional folder branch and the footer's unfiltered
`files.length` read — lives entirely inside the shared `frontend/src/components/preview/AppBuilderPreview.tsx`
component, which is mounted from three OTHER call sites, none exercised by that reproduction:

- `frontend/src/components/preview/PreviewPanel.tsx:163`, inside `AppBuilderIDEPreview` (the
  embedded, non-fullscreen "Preview" tab shown for an in-progress or completed `app_builder`
  pipeline run — `AppBuilderIDEPreview` is defined at `PreviewPanel.tsx:111` and instantiated by
  `PreviewPanel` itself, the main export at `PreviewPanel.tsx:508`).
- `frontend/src/components/history/WorkflowHistory.tsx:838`, the `isAppBuilder` branch of the
  reopen-run modal (`files={ideFiles}`).
- `frontend/src/components/history/WorkflowHistory.tsx:877`, the `isGenericBundle` branch of the
  same reopen-run modal (`files={genericBundleFiles}`).

## Expected vs actual

Expected: search behaves consistently everywhere `AppBuilderPreview` is mounted — no orphaned
empty folders, an accurate footer count — since it is presented as one reusable file-explorer
widget.

Actual (INFERRED, not yet independently reproduced in these three surfaces): since all three call
sites render the exact same `AppBuilderPreview` component with the exact same unmodified
`FileTreeNode` and footer code (confirmed by reading `AppBuilderPreview.tsx` in full — neither the
folder branch at lines 169-198 nor the footer at line 556 take a prop that varies by caller), React
does not fork behavior per call site. The identical defect necessarily reproduces in the embedded
run-preview tab and in both reopen-modal branches.

## Why the root cause implies it

ISS-332's root cause is entirely internal to `AppBuilderPreview.tsx` (the folder branch never
checks `searchQuery`; the footer never reads it either) — none of the four callers pass a prop or
override that could suppress or alter that behavior. A bug with no dependency on the caller's
context reproduces at every caller.

## What would settle it

Reproduce ISS-332's exact repro steps (seed a 4+-file payload, expand nested subfolders, search a
nested filename) against: (a) a live `app_builder` run's embedded Preview tab via `PreviewPanel`,
and (b) a reopened `app_builder`/generic-bundle run via the History "reopen" modal. Confirm the
same orphaned folders and stale footer count in both.

## Fix note

Because the defect is entirely inside the shared component, the fix belongs in
`AppBuilderPreview.tsx` alone (see ISS-332's fix) — patching only the reported
`/preview-fullscreen` path would leave these three siblings broken; there is no per-caller variant
to separately patch.

## Resolution

Code defect fixed by [FIX-394](20260829-0127-FIX-394.md), in the shared component exactly as
this card predicted — there was no per-caller variant to patch.

`verification.status` is deliberately `pending`, not `passed`: this card's test file
`PreviewPanel.appBuilderSearch.test.tsx` is still red for a test-side reason
([ISS-596](20260829-0127-ISS-596.md)) — its trailing `getByText("app.js")` is ambiguous
because that fixture's `files[0]` is `src/app.js`, so the name also renders as the
auto-opened editor tab. The assertion that encodes THIS defect
(`queryByText("styles")` absent) does pass post-fix, and disambiguating only that last
query on a throwaway copy makes the whole file pass. The test itself was not edited.
