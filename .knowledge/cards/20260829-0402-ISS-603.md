## What is broken

The third case in `frontend/src/components/workflow/WorkflowView.attachmentRemove.test.tsx`
("ISS-579 — a run launched after removing an attachment does not forward its stale marker as
the brief") does:

```tsx
await attach(user, container, [makeFile("zz-hunt-run.txt")]);
await removeChip(user, "zz-hunt-run.txt");
await user.click(screen.getByRole("button", { name: /run workflow/i }));
expect(onStartPipeline).toHaveBeenCalled();
```

`onStartPipeline` can never have been called at that point, for two independent reasons:

1. The file it attaches is the ONLY content in the textarea, so once
   [FIX-400](20260829-0402-FIX-400.md) correctly strips the marker, `ideaInput` is `""` and
   `handleRun`'s `if (!ideaInput.trim() ...) return;` short-circuits. A run SHOULD NOT launch
   on an empty brief — the assertion contradicts correct behaviour.
2. The fixture mounts `<WorkflowView>` without stubbing `useAgentLibrary`, so
   `pipelineAgents.length === 0` and [ISS-328](20260828-1834-ISS-328.md)'s guard
   (`WorkflowView.tsx:177`, `disabled` at `:491`) blocks the run regardless of brief text.
   That guard landed after [ISS-579](20260829-0234-ISS-579.md)'s card was written, so the
   card's "what would settle it" recipe predates it.

Measured directly (instrumented copy of the same fixture, deleted after the run): after the
attach + remove cycle, `textarea.value === ""`, the Run button's `disabled === true`, and
`onStartPipeline.mock.calls.length === 0`.

## Why it matters

The case carries `it.fails`. A test that fails for the WRONG reason still satisfies `it.fails`,
so this case reports green forever and silently stops proving anything about
[ISS-579](20260829-0234-ISS-579.md). Its underlying mechanism IS cured by
[FIX-400](20260829-0402-FIX-400.md) — the marker no longer survives removal, so the only string
`handleRun` can forward is the user's own text — but that is a deduction from the ISS-345 case,
not an observed assertion, which is why ISS-579 stays `open`.

## What a correct fixture looks like

Type real brief text into the textarea FIRST (so a run is legitimately allowed after the
attachment is removed), stub `useAgentLibrary` so `pipelineAgents` is non-empty (or add agents
through the library UI), then attach, remove, click Run, and assert the second argument of
`onStartPipeline` equals the typed text and does not contain `[Attached:`.

**Not fixed here**: rewriting a test's assertions is the test-writer's call, not the fixer's —
changing a red assertion to make a run go green is exactly the inversion the fixer role is
forbidden from performing.
