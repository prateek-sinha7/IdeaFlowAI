# ISS-849

INFERRED sibling of [ISS-848](20260922-2138-ISS-848.md), QA-PS-051's root-cause card.
Derived from ISS-848's confirmed mechanism, not independently reproduced on any route
other than Library yet — filed as a lead, per the analyzer's own standard that an
unreproduced sibling is a lead, not a defect.

## Why the root cause implies this

[ISS-848](20260922-2138-ISS-848.md) confirms the defect's trigger is "does
`router.push`/`router.back` change which `[...view]` segment tree `page.tsx` renders" —
nothing in the mechanism (the `recentRunsRequestedRef` reset, the uncached `getWorkflows`
call) reads `pathname`, checks for `/library`, or otherwise singles out Library.
`grep -rl "router\.push(routes\." frontend/src` (excluding tests) shows nine call sites
beyond `LibraryPage.tsx`, each a candidate trigger for the identical double-fetch:

- `CreationHub.tsx` (Home page cards) -> any workflow-type route
- `SavedWorkflowsPage.tsx` -> opening a saved workflow
- `StepsOverviewSpine.tsx` -> agent-level navigation (one call site in this same file was
  already patched to shallow nav by [FIX-493](20260907-1240-FIX-493.md); worth checking
  whether a different transition in the same file still uses `router.push`)
- `DashboardLayout.tsx`, `LaunchWizard.tsx`, `admin/page.tsx`, `workflow/page.tsx`,
  `RunConnectionProvider.tsx`, `page.tsx` itself -> their own route entries/exits

Also implies the inverse direction: [FIX-493](20260907-1240-FIX-493.md) already
established that `router.back()` remounts `[...view]/page.tsx` identically to
`router.push` ("Both are real Next.js router navigations, so both remounted..."), so a
user who opens a Library detail page and then presses Back should reproduce the same
double-fetch on the return trip, not only on the way in — QA-PS-051's own repro only
tested the forward direction.

## Possible overlap flagged, not resolved here

[ISS-781](20260922-1630-ISS-781.md) (QA-PS-035, Settings page) independently measured
`GET /api/runs?limit=50` x2 on `/settings/profile`, and [FIX-618](20260922-1945-FIX-618.md)
attributed that instance to a *different* mechanism — `RunConnectionProvider`'s boot
fetch and `page.tsx`'s own mount effect landing "ticks apart," outside the in-flight
dedupe window, documented as "a design decision, not this fix." FIX-618 tested a COLD
direct load of `/settings/profile`. Whether reaching `/settings/profile` by navigating
there FROM another route (a `router.push`, not a cold load) adds a THIRD `runs?limit=50`
from the ISS-848 remount mechanism on top of that already-documented pair is not
established either way — nobody has tested that specific entry path. Left for
reproduction, not asserted as a fact.

## What would confirm this

1. Cold-navigate to `/dashboard`, wait for network idle, then click through to
   `/settings/profile`, `/library`, or any other non-wizard route via a real in-app link
   (not a reload). Count `GET /api/runs?limit=50` across both page states combined.
   ISS-848 predicts 2 from this mechanism alone; if `RunConnectionProvider`'s own
   conditional fetch also fires (only when the tab owns a previously-launched run, per
   `RunConnectionProvider.tsx:300-308`), possibly a 3rd, independent of this one.
2. Repeat using the browser Back button after step 1, for the reverse-direction claim.
3. Repeat from `/` (Home) through `CreationHub.tsx`'s card click into any workflow type.

## Evidence

- `grep -rl "router\.push(routes\." frontend/src` (this session, 2026-09-22) — the 9
  non-`LibraryPage.tsx` call sites listed above.
- [FIX-493](20260907-1240-FIX-493.md)'s own text, confirming `router.back()` remounts
  `[...view]/page.tsx` identically to `router.push`.
- [ISS-848](20260922-2138-ISS-848.md) — the confirmed mechanism this card generalizes.
