## Derivation (INFERRED — not yet reproduced)

Sibling of [ISS-198](20260828-1400-ISS-198.md), same root mechanism as
[ISS-207](20260828-1617-ISS-207.md) (search), applied to the sort control instead.

`frontend/src/components/history/WorkflowHistory.tsx`:
- `runs` never exceeds the fetched page (50, or `Math.max(50, runs.length)` on refresh —
  see [ISS-198](20260828-1400-ISS-198.md)'s root cause: `handleLoadMore` is dead code).
- The "Sort" segmented control (line ~1052-1095) offers "Newest" / "Longest" / "Tokens",
  keyed to `sortKey` (line ~177).
- `sections = bucketAndSortFamilies(visibleFamilies, sortKey)` (line ~950) — sorting
  happens entirely over `visibleFamilies`, itself filtered from `families =
  groupRunsByFamily(runs)` (line ~942). Every candidate the sort algorithm ever considers
  is drawn from the same ≤50-row window as [ISS-207](20260828-1617-ISS-207.md).

## Expected vs Actual

- Expected: sorting by "Longest" or "Tokens" surfaces the account's actual
  longest-duration / highest-token-usage run, regardless of how long ago it ran.
- Actual: for an account with more runs than the fetched page, "Longest"/"Tokens" sort
  only ranks the most-recently-created 50 against each other. A genuinely longer or
  costlier run sitting outside that window (any of the un-fetched runs — 223 of 273 for
  qa-admin, per [ISS-198](20260828-1400-ISS-198.md)) is never a candidate and never
  surfaces, with nothing in the UI indicating the sort is scoped to a partial set.

## What would confirm or refute this

Reproduction: identify (via `GET /api/runs?limit=100&offset=100` or `offset=200` for
qa-admin) a run with a longer `duration` or higher `token_usage.total_tokens` than any
run in the first `GET /api/runs?limit=50` page; select "Longest" (or "Tokens") sort in
the UI and confirm that run never appears at the top — or anywhere — in the sorted list.

## Why this is a sibling, not the same bug

Same mechanism as [ISS-207](20260828-1617-ISS-207.md) (capped `runs` array feeding a
client-side computation that implicitly claims full-history scope) but a distinct
symptom: sort produces a plausible-looking, silently-WRONG ranking rather than a
"nothing found" state. A user has no reason to suspect the "Longest" run shown isn't
actually their longest ever.
