## What was wrong

On `/login`, three synchronous clicks on "Sign in" fired three `POST /api/auth/login`
requests instead of one ([ISS-245](20260828-1631-ISS-245.md), CONFIRMED 3/3 from cold start).
The button's `disabled` attribute read `false` and its label read `"Sign in"` at click 2 and
click 3, so nothing stopped the extra submissions.

## Root cause

`frontend/src/app/login/page.tsx:80-100` — `LoginForm.handleSubmit` set `isLoading` on entry and
the submit `<Button>` read `disabled={isLoading}`, but `setIsLoading` is a React state update,
not a DOM mutation: the real `disabled` attribute only flips once React re-renders and commits,
one tick after the click event. A second or third click landing inside that pre-commit window
found an enabled button and re-entered `handleSubmit`, each call starting its own `login()`
fetch. The React state round-trip was the only guard, and it is structurally too slow for
back-to-back clicks in the same task.

`handleChallengeSubmit` (same file, `frontend/src/app/login/page.tsx:102-162`) had the identical
shape for `respondToLoginChallenge()` — named in ISS-245's proposed fix and filed separately as
[ISS-352](20260828-2101-ISS-352.md).

## What changed and why there

`frontend/src/app/login/page.tsx` only — no backend change, since the backend answered every
duplicate correctly (`200 OK`); this was a frontend submission-gating gap.

- Added `const submittingRef = useRef(false)` to `LoginForm` (`useRef` added to the existing
  `react` import). A ref mutation is synchronous and does not wait for a render, which is
  exactly the property `isLoading` lacks.
- `handleSubmit`: `if (submittingRef.current) return; submittingRef.current = true;` immediately
  after `e.preventDefault()`, before `setIsLoading(true)`; cleared in the existing `finally`
  beside `setIsLoading(false)`.
- `handleChallengeSubmit`: the same check-and-set, placed **after** the field-validation
  early-returns and immediately before `setIsLoading(true)`. Putting it at the top of that
  handler would leave the ref latched on a validation failure (those paths return without
  reaching the `try`/`finally`) and wedge the Continue button permanently.

Both handlers are the single funnel for their own form — `login()` and
`respondToLoginChallenge()` in `frontend/src/lib/api.ts` have exactly one caller each, both in
this file — so the guard belongs in the handlers, not at the call sites. `disabled={isLoading}`
is left in place: it still carries the visible pending state ("Signing in…" / "Verifying…"),
the ref carries the correctness.
