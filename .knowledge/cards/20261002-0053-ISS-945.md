## What is wrong (CONFIRMED by running it)

Found while fixing QA-KB-015 ([FIX-704](20261002-0053-FIX-704.md)). The ISS-921 case in
`frontend/src/components/settings/AccountSettings.iss372.test.tsx` opens the Constitution tab,
then waits on

```
83:    await waitFor(() => expect(fetch).toHaveBeenCalled());
```

before its two real assertions. That condition never holds. The Constitution GET goes through
`getConstitution(token)` (`AccountSettings.tsx:626`, ISS-799), and the test file mocks it at
`:16` as `getConstitution: () => Promise.resolve({ content: "" })`, which never touches `fetch`.
Nothing else on the page calls `fetch` before a Save. So the case throws at `:83` after the
1000 ms `waitFor` timeout, whatever the app does:

- HEAD source, case run without `it.fails`: `× ... 1303ms`,
  `AssertionError: expected "vi.fn()" to be called at least once`.
- FIX-704 source, same: `× ... 1302ms`, the same AssertionError.
- Under `it.fails` it therefore reads "expected fail" on both trees (1201 ms and 1193 ms), so it
  cannot show the XPASS that marks ISS-921 fixed.

A throwaway copy of the file with the `it.fails` markers and line `:83` removed ran
`4 passed (4)` against the FIX-704 source; the copy was deleted, and the official file was not
edited (the fixer may not edit a test to make it pass).

## Disposition

A test defect for the 4-test-writer, not an app defect. Drop line `:83`: the
`findByRole("textbox")` just above it already waits for the load, because the textarea renders
only after ConstitutionSection's `getConstitution` promise has set the draft and its loaded value.
Until then the 6-verifier must keep this one case's `it.fails` marker: removing it turns the case
red at `:83`, not at the app. ISS-921's behaviour is covered meanwhile by
`frontend/src/components/settings/AccountSettings.iss372.sources.test.tsx` (red on HEAD, green on
FIX-704).

### Root cause (CONFIRMED)

One mechanism: the file's module mock and its own synchronization point disagree, 67 lines apart.

- `AccountSettings.iss372.test.tsx:16`: `getConstitution: () => Promise.resolve({ content: "" })`. The load never reaches `fetch`.
- `AccountSettings.iss372.test.tsx:83`: `await waitFor(() => expect(fetch).toHaveBeenCalled());`. It waits for `fetch`.
- The real load is `getConstitution(token)` at `AccountSettings.tsx:626` (ISS-799, commit 2e2b1df47, already in HEAD; both iss372 test files
  are untracked, so the file was written against it). `AccountSettings.tsx` has two `authedFetch` call sites, Save (`:647`) and Clear
  (`:680`), and no case in this file clicks either. So `fetch` has zero calls and `waitFor` runs out its 1000 ms.
- Reproduced on a scratch copy with only `it.fails` -> `it`: `AssertionError: expected "vi.fn()" to be called at least once` at
  `:83:39` after 1284 ms (`02-analyze-scratch-runs.txt`, run A). The DOM dump at that moment already holds
  `<textarea aria-label="Constitution content">` and no spinner: the load had finished, only the wait could not.
- `AccountSettings.render.test.tsx:47-56` shows the intended shape. After ISS-799 that file made its `getConstitution` mock delegate to
  `fetch` ("Same delegation as `authedFetch` above and for the same reason"), and `:176-188` then waits on `fetch`. The iss372 file
  copied the `authedFetch` passthrough (`:15`) but not the `getConstitution` delegation.
- `:83` was redundant even with a delegating mock. The textarea mounts only after the load settled (`AccountSettings.tsx:727-741`;
  `.finally(() => setLoading(false))` at `:638` runs after the `.then` at `:627-636`), so `findByRole("textbox")` at `:82` already
  proves more than "fetch was issued".

### The app is correct (CONFIRMED)

Scratch variant b1 (the fix below) runs `Tests 4 passed (4)` against the current `AccountSettings.tsx`, the ISS-921 case in 212 ms
instead of the ~1.2 s timeout. With a saved value of "saved rules" (variant d1) it passes too. No app edit, and the 5-fixer's
"never bend the app to the test" rule does not apply: the app is right and the test asserts on a channel its own mock removed.

2. Drop `waitFor` from the `:9` import. Deleting `:83` alone leaves it unused, and `npx eslint` then exits 1:

   `04-analyze-eslint-trap.txt`). With the import dropped it exits 0.
3. `it.fails(` -> `it(` on `:78`. The BUGS.md sketch says line 80; the marker is on `:78` (`:80` is `const user = userEvent.setup();`),
