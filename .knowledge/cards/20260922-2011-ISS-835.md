## What is suspected

INFERRED sibling of [ISS-802](20260922-1638-ISS-802.md) (QA-PS-049's root
cause), derived from reading — not yet browser-reproduced independently.

`frontend/src/components/history/WorkflowHistory.tsx:434-445`:

```tsx
useEffect(() => {
  if (!selectedRun) { setClarifyRounds([]); return; }
  const token = getToken();
  if (!token) { setClarifyRounds([]); return; }
  let cancelled = false;
  setClarifyLoading(true);
  getRunArtifacts(token, selectedRun.id, { kind: "clarifications", includeContent: true })
    .then((resp) => { if (!cancelled) setClarifyRounds(parseClarificationArtifacts(resp.artifacts)); })
    .catch(() => { if (!cancelled) setClarifyRounds([]); })
    .finally(() => { if (!cancelled) setClarifyLoading(false); });
  return () => { cancelled = true; };
}, [selectedRun?.id]);
```

Identical shape to [ISS-802](20260922-1638-ISS-802.md)'s
`ArtifactVersionPicker.tsx:108-129`: one `useEffect` keyed on an id
(`selectedRun?.id`), a `cancelled` flag that blocks only the
post-resolution `setState` calls but not the fetch itself, no
in-flight/StrictMode guard, and `getRunArtifacts` itself has no dedupe —
confirmed in ISS-802 and independently re-read here: it calls `request()`
directly (`frontend/src/lib/api.ts:1200-1216`), never `cachedGet()`
(`api.ts:410-426`).

This is the second of exactly two production call sites of `getRunArtifacts`
app-wide — confirmed by
`grep -rn "getRunArtifacts" frontend/src --include="*.tsx" --include="*.ts"`
(excluding `*.test.tsx`/`*.test.ts`), which returns only
`ArtifactVersionPicker.tsx` and this file. The third match in that grep,
`ArtifactVersionPicker.tsx:149-157`, is a click-driven `select()` callback
guarded by its own `contentCache` ref and is not a mount effect — checked
and ruled out, not part of this defect's blast radius.

## Condition

Opening or switching `selectedRun` in Run History / Workflow History (i.e.
reopening a past run's detail view) under `next dev`'s default React
Strict Mode — confirmed live on this port: `next-server (v16.2.4)`'s parent
is `node .../frontend/node_modules/.bin/next dev` (pid chain verified via
`ps`), and `frontend/next.config.ts` sets no `reactStrictMode` override
(`grep -rn "reactStrictMode" frontend/` returns nothing), so Next 16.2.4's
`true` default applies.

## Expected vs actual

**Expected:** `GET /api/runs/{id}/artifacts?kind=clarifications&include=content`
fires once per reopened run.

**Actual (predicted):** it fires twice, doubled by the same
mount→cleanup→mount Strict Mode re-invoke ISS-802 confirmed 3/3 for
`ArtifactVersionPicker`'s copy of this same effect shape, against a
smaller (clarifications-only) payload each time.

## Why the root cause implies this

ISS-802 root-caused the Steps-tab duplication to "unguarded mount effect +
Strict Mode double-invoke + `getRunArtifacts` not routed through
`cachedGet()`." `WorkflowHistory.tsx:434-445` is byte-for-byte the same
defect shape against the same underlying function, confirmed by direct
reading — the only thing unverified is a live network trace confirming the
exact 2x count in the browser, which is why this stays INFERRED rather
than CONFIRMED.

## What would settle it

Cold-navigate to Run History, open (reopen) any past run so `selectedRun`
becomes set, watch DevTools Network filtered to
`artifacts?kind=clarifications`, and count requests — repeat 3x per this
line's own validation convention (fresh navigation each cycle, different
run each time).

## TEST-WRITER FINDING (QA-PS-049, 2026-09-22) — not reproducible

Attempted to settle this per the section above (a Vitest unit mount under
`<React.StrictMode>`, same technique that reproduced
[ISS-802](20260922-1638-ISS-802.md) for `ArtifactVersionPicker`). Two
independent problems, both checked directly against the shipped code:

1. **The `setSelectedRun` branch is unreachable from the live app.**
   `grep -n "<WorkflowHistory" frontend/src --include="*.tsx"` (excluding
   `*.test.tsx`) returns exactly one render site —
   `frontend/src/components/layout/DashboardLayout.tsx:2966` — and that
   call always passes `onOpenRun` (`:2985`). `WorkflowHistory.tsx:340-359`'s
   `handleSelectRun` only falls through to `setSelectedRun(run)` (the
   branch that keys this effect) when `onOpenRun` is absent OR
   `opts?.forChain` is true; `grep -n "forChain: true" frontend/src` (whole
   tree) returns **zero** matches — no UI element ever calls
   `handleSelectRun(run, { forChain: true })`. A plain row click always
   takes the `onOpenRun(run); return;` branch at `:357-359` and
   `router.push`es to `/runs/{id}` instead, which never sets
   `selectedRun`. So in the running app, `selectedRun` is never set at all
   and this effect never fires — not "fires twice", never fires.

2. **Even mounted directly (bypassing #1 via a unit test with no
   `onOpenRun` prop), the effect still would not double-fire.** React
   StrictMode's dev-only "double invoke" (mount -> cleanup -> mount) is
   specifically an INITIAL-MOUNT behaviour — it does not re-run on a later
   commit triggered by a dependency change on an already-mounted
   component. Verified directly with a minimal repro (`useEffect(fn, [k])`
   inside `<React.StrictMode>`, then `act(() => setK(1))`): the mount
   fired twice (2 calls) but the subsequent update fired once (net 3, not
   4). `WorkflowHistory` itself is one long-lived instance — `selectedRun`
   starts `null` and is only set later via `setSelectedRun` inside a click
   handler, so this effect's first (and only) real invocation is an
   UPDATE, not the component's initial mount. That is the mechanical
   difference from ISS-802: `ArtifactVersionPicker` gets a genuinely FRESH
   mount per agent selection (new component instance), so StrictMode's
   mount-time double-invoke applies there; `WorkflowHistory`'s clarify
   effect does not get that fresh mount, so it doesn't.

Both checks independently contradict the "same shape as ISS-802" theory
this card was built on. No test was written for this card — writing an
`xfail(strict=True)` test that could never observably fail for this
reason would misrepresent a defect that doesn't reproduce. Recommend this
card be closed as not-reproducible (or WONTFIX'd) rather than carried
forward as an open sibling of ISS-802; the bug's real, confirmed symptom
is already covered by ISS-802's test.

## Fixer pass (QA-PS-049, 2026-09-22): not changed by [FIX-636](20260922-2352-FIX-636.md)

FIX-636 did not touch `WorkflowHistory.tsx`. I checked the test-writer's disproof
again against the current tree, and both of its points still hold:

1. The branch cannot be reached in the running app. There is one render site,
   `DashboardLayout.tsx:2966`, and it always passes `onOpenRun`
   (`onOpenRun={(run) => { ... router.push(routes.runDetail(run.id)); }}`, :2985).
   `grep -rn "forChain" frontend/src` (excluding tests) finds only the declaration
   and the read, at `WorkflowHistory.tsx:340` and `:357`. Nothing passes
   `forChain: true`. The other setter, `handleSelectVersion` at
   `WorkflowHistory.tsx:388-406`, also goes through `onOpenRun` when it is set.
2. The effect cannot fire twice on mount. `selectedRun` starts as `null`
   (`useState<WorkflowRun | null>(null)`, `WorkflowHistory.tsx:176`). The two mount
   calls in StrictMode take the `if (!selectedRun)` early return and never fetch.
   The effect only fetches on a later update, and React calls effects twice only
   when a component first mounts, not when it updates. In Next's react-dom,
   `commitDoubleInvokeEffectsInDEV` runs straight after the passive mount pass
   (`react-dom-client.development.js:19946-19953`).

The predicted defect does not exist in the code, so there is nothing to fix and no
test to write. Suggested disposition: close this card as refuted, with
`verification.status: not_reproducible` kept. A single-flight guard in
`getRunArtifacts` would only guard a request that is never duplicated.
