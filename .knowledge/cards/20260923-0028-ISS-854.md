## Sibling of ISS-853, from QA-PS-048 re-analysis

[ISS-853](20260922-2359-ISS-853.md) covers `AgentThinkingTab.tsx`'s
divert-link effect (`:201-258`) re-fetching the full run record. The SAME
effect also fetches the entire workflow catalog, and that fetch has a worse
gap: no dedupe at all, not even the StrictMode-only guard `getWorkflow` got
from [FIX-637](20260922-2358-FIX-637.md)'s `singleFlightGet`.

## What is wrong

`frontend/src/components/results/AgentThinkingTab.tsx:215`, inside the
effect ISS-853 already describes:

```tsx
try { defs = await getWorkflowDefinitions(token); } catch { /* fall back to titles */ }
```

This runs BEFORE the `liveDivertedToRunId` / `self.status` checks — every
Steps-tab mount pays for it, including a run with no divert and no parent
(the common case). `defs` exists only to resolve a display label
(`labelFor`) for a divert-link row that, most of the time, is never shown.

`frontend/src/lib/api.ts:1929-1936`:

```tsx
export async function getWorkflowDefinitions(
  token: string
): Promise<WorkflowSummary[]> {
  return request<WorkflowSummary[]>("/api/workflows", {
    method: "GET",
    headers: authHeaders(token),
  });
}
```

A bare `request()` — no `cachedGet()`, no `singleFlightGet()`, no in-flight
map of its own. `getWorkflow`/`getRunFamily`/`getRunSandbox` all got
`singleFlightGet` in FIX-637 specifically because ISS-831 found them
unguarded; `getWorkflowDefinitions` was not on that list and is still bare.
Its own StrictMode double (both invocations of the effect) fires two fully
independent `GET /api/workflows` requests (~22-30 KB payload per FIX-637's
measurement), not one merged request the way `getWorkflow` now is.

`frontend/src/components/workflow/composer/CanvasNode.tsx:105` is the only
other caller (`getWorkflowDefinitions(token).catch(() => [])`) — a different
screen (workflow composer canvas), outside QA-PS-048's run-detail-tabs
scope, not folded into this card.

## Why this is a sibling, not a duplicate of ISS-853

Same effect, same "unconditional fetch of data that is not always needed"
root pattern, but a DIFFERENT function with a DIFFERENT (and currently
unmitigated) gap: `getWorkflow` already collapses a StrictMode double into
one network call today; `getWorkflowDefinitions` collapses nothing,
concurrent or not.

## What would settle it

Reset DevTools Network, open a completed run with no divert/parent link,
click Steps. Expect `GET /api/workflows` to fire even though no divert row
is ever shown. Fix target: zero when ISS-853's fix removes the need for
`defs` on a run with no link; else exactly one (StrictMode dedupe only) if
some label lookup still remains for the live-divert path.

## Suggested fix

Whichever fix ISS-853 lands for the `self`/`parent` reads should also stop
`labelFor`'s `defs` fetch from running when there is no divert link to
label — the `runFamily`-derived `status`/`parent_run_id` already tell the
effect that before it would otherwise call `getWorkflowDefinitions`. If a
label lookup is still needed for the live-divert path (`:225`, kept as-is by
ISS-853), route it through a dedupe wrapper the same way `getWorkflow` was —
`cachedGet()` (the catalog is not run-specific and changes rarely) or a new
`singleFlightGet()` call — whichever precedent the 5-fixer picks.
