## Expected vs Actual

**Expected:** `/library/skills/<id>` opens that skill's detail view (the full-viewport modal
`LibraryPage` seeds from the URL via its cold-mount effect) for any valid skill id.

**Actual:** For every skill id tested — hyphenated or not, including the two ids a prior bug
proved working — the detail view never opens; the underlying Skills tab listing renders instead,
under the correct detail URL, with no console error, no failed network request, and no indication
to the user that the specific skill was never resolved.

## Root-cause pointer (for the fix stage, not asserted as proven)

`frontend/src/components/library/LibraryPage.tsx`'s cold-mount seeding effect (~line 518-543) only
calls `setSelectedSkill` when `skillsStatus === "succeeded"` AND
`SKILLS.find(s => s.id === librarySlug.slug)` finds a match:

```ts
} else if (librarySlug.type === "skills" && skillsStatus === "succeeded") {
  const skill = SKILLS.find(s => s.id === librarySlug.slug);
  if (skill) {
    setMainTab("skills");
    setSelectedSkill(skill);
    librarySlugAppliedRef.current = true;
  }
}
```

If `skillsStatus` never reaches `"succeeded"` in time, or the `SKILLS` array/its `id` shape
changed, this effect silently never fires and the underlying list — which the detail modal is
meant to overlay — is all that remains visible. That matches the observed symptom exactly: no
console error, no failed network request, URL correct, listing visible, and (per network capture)
no per-skill lookup is even attempted, consistent with the effect's guard never being satisfied
rather than a failed fetch. Worth comparing against the screen-to-mainView mapping in
`frontend/src/app/[...view]/page.tsx` (`library-skill` -> `"library"`) and whatever changed in the
~6 hours between the narrow no-hyphen bug (`BUG-20260828-030430-library-skills-id`, 03:04 UTC) and
this full regression (`BUG-20260828-091300-library-skills-r2`, 09:13 UTC).

Register entry: `BUG-20260828-091300-library-skills-r2` (`bug-hunter/ledger.md`).

## Analyzer confirmation (ANALYZED pass on this bug)

Two things from the root-cause pointer above are now confirmed by reading further source, and one
scoping fact is added.

**CONFIRMED — every entry path funnels through this one effect.** Clicking a skill card does call
`setSelectedSkill(skill)` directly, synchronously, before any id lookup (`LibraryPage.tsx:822-824`)
— on its own that should not need `SKILLS.find` at all. But `frontend/src/app/[...view]/page.tsx:3195-3199`
documents (project-verified, not an inference): "Next.js does not preserve a dynamic-route page's
own instance across a client-side navigation to a new URL under the same catch-all — confirmed
live: a fresh render-instance id appears right after router.push." `FIX-298`
(`20260825-FIX-298.md`) already hit and fixed the identical remount for the run-stream route.
Because the click handler's own `router.push(routes.librarySkill(...))` call triggers exactly
this remount, the direct `setSelectedSkill(skill)` it just made is thrown away, and the fresh
mount's only way to reopen the modal is this card's cold-mount effect (T15, lines 518-543). That
is why cycle 3 (genuine card click) failed identically to cycles 1-2 (direct URL nav) above — they
are the same code path once the remount is accounted for, not two independently-broken paths.

**INFERRED, strengthened — why `SKILLS.find` itself never matches.**
`frontend/src/hooks/useSkillsCatalog.ts:17-26` returns a brand-new array via `.map()` on every
render, with no `useMemo`. Contrast `frontend/src/hooks/useAgentLibrary.ts:29-38`, which
explicitly memoizes and documents why in its own comment: "without this, every render produced
two fresh .filter() arrays, and a consumer effect keyed on libraryAgents would loop forever."
`ISS-303` (`20260828-1935-ISS-303.md`), filed AFTER this bug's 09:13 UTC window, independently
confirms the AGENTS branch of this exact same effect DOES open correctly on a cold URL (a "Coming
Soon" agent's full dialog opened 3/3) — the one branch backed by `useAgentLibrary`'s memoized
array. This is the strongest available evidence that the shared remount/re-derive mechanism is
sound and the failure is isolated to the unmemoized SKILLS/HOOKS branches — but static reading
alone did not trace the exact step where the unmemoized reference turns into a permanent miss on
the very first render of a fresh mount (the `librarySlugAppliedRef` guard tolerates repeated
re-invocation fine). Still not asserted as proven — see ISS-336's "What would confirm or refute
this" for the cheapest deterministic check.

**Sibling filed:** [ISS-336](20260828-1846-ISS-336.md) — the Hooks tab shares both facts above
(same effect, same unmemoized `useHooksCatalog` shape) and is therefore expected to exhibit the
identical symptom; unreproduced/INFERRED until checked.

## Resolution (FIX stage, 2026-08-28)

Resolved by [FIX-340](20260828-2230-FIX-340.md).

The mechanism above is CORRECTED there, not confirmed: the seed effect is not broken and
`SKILLS.find` does match. `skillsStatus` simply had not reached `"succeeded"` yet, because
`frontend/src/store/listenerMiddleware.ts` awaited `fetchWorkflows`/`fetchRecentRuns` to
completion BEFORE dispatching `fetchSkills` — measured 12.2s on a cold
`/library/skills/html-deck-to-pptx`, during which the listing is all there is to render. Removing
that intermediate await opens the modal 0.4s after the app's mount effects run. The in-app
card-click path re-measured as never broken (dialog present in the same tick as the click), so the
`FIX-298` remount reasoning above does not apply to this defect.
