## The gap

`.xlsx` is in `_PAGED_FORMATS`, so a workbook travels the same route a PDF does:
LibreOffice converts it to a PDF, and the pages of that PDF are materialised and
read back.

Spec 019 says in its own Out of scope section that this is the wrong shape,
twice over:

> it invents a pagination the workbook does not have (FR-034b), and it destroys
> the one structure that matters — the cell grid.

The pagination comes from print settings nobody set on purpose. The grid — rows,
columns, sheet names — is flattened into page text and does not come back.

## It is deferred, not rejected

Commit `0e2b5b442` (*docs(spec): record per-format handling as deferred, not
done*) moved this deliberately. The Out of scope list now carries two adjacent
and easily-confused entries:

- **Native Office extractors** — *rejected* by FR-026a, because they lose the
  overlay annotations the feature exists to preserve. See
  [ADR-0049](20260918-ADR-0049.md).
- **Per-format internal handling beyond text** — **DEFERRED**, with the next
  shape already agreed.

Nothing in the knowledge base carried that distinction, so someone reading spec
019 as done would not learn that a known-wrong route is still the one in
production.

## The tool already admits it at runtime

`extract_text`'s receipt appends, for `xlsx` only:

```
These N page(s) are LibreOffice's pagination of a spreadsheet, driven by its
print settings — not a structure the workbook itself has.
```

and `_pagination_note` adds the converter caveat on every converted format.
`_WORD_X_TOLERANCE = 1.5` (ADR-0049) at least keeps adjacent columns from fusing
into tokens that exist nowhere in the workbook. All three are honest patches on
a lossy path; none of them makes it the right path.

## The other half of the same gap

`.xlsx` is simultaneously **the only accepted upload type with no wizard-side
preview extractor**. `extract_upload_text` dispatches `pdf` / `docx` / `pptx` and
returns `""` for everything else, and `run_files._EXTRACTABLE_EXTS` deliberately
excludes `xlsx` (FR-037 — no openpyxl is vendored, and an empty sidecar reads as
"this document is blank").

The endpoint accepts it anyway and special-cases the empty result rather than
raising 422, because rejecting it outright is what silently dropped spreadsheets
before they ever uploaded: the chip rendered, the run received one document
fewer, and nothing said why.

The visible consequence: **a spreadsheet upload looks empty until an agent calls
the tool.** That is a correct decision given the current route, and it is the
same gap as the section above — the two currently have to be rediscovered
separately, which is why they are carded together.

## The agreed next shape

One CSV per sheet, attached as files. A **fourth route** in `extract_text`, not
a change to the existing three.

Nothing blocks it: the entry point already dispatches on format, and
`.extract/{format}/{slug}/` already has room beside `pages/` for whatever a
format's natural output is. A sheet is already tabular; emitting CSV keeps rows,
columns and sheet names intact and costs no renderer at all.

The same argument may later apply per format — a `.docx`'s heading structure, a
`.pptx`'s per-slide notes.
