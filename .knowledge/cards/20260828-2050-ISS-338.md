## Summary

On the Password card of `/settings/profile`, the "Current password" and "New password" inputs
each render an eye-icon button that toggles the field between `type="password"` and
`type="text"`. The adjacent "Confirm new password" input — whose entire purpose is letting the
user verify they retyped the new password correctly — has no such button and can never be
revealed. It is unconditional: reproduced on 3/3 cold-start visits, no special tier, theme, or
entry-path condition needed.

Originating register entry: `BUG-20260828-050900-settings-profile` in `bug-hunter/ledger.md`.

## Reproduction (validated 3/3, cold start each time)

1. Cold-navigate (fresh page load, not a soft re-click) to `/settings/profile` as `qa-admin`.
2. Query the DOM for a sibling `<button>` next to each password `<input>` in the Password card:
   - `input[placeholder="Enter current password"]` → toggle button present
   - `input[placeholder="At least 8 characters"]` (New password) → toggle button present
   - `input[placeholder="Re-enter new password"]` (Confirm new password) → **no toggle button**
3. Repeated across 3 independent cold loads (navigate away to `/dashboard`, reload
   `/settings/profile`) — identical result every cycle. Deterministic, not flaky; no axis needed
   to trigger it beyond visiting the page.

## Root cause

`frontend/src/components/settings/AccountSettings.tsx`:
- L96-97: `const [showCurrent, setShowCurrent] = useState(false);` /
  `const [showNew, setShowNew] = useState(false);`
- L283-288: "Current password" input (`id="current-password"`) wired to `showCurrent`, with a
  toggle `<button>` calling `setShowCurrent(!showCurrent)`.
- L295-300: "New password" input (`id="new-password"`) wired to `showNew`, with a toggle
  `<button>` calling `setShowNew(!showNew)`.
- L305-309: "Confirm new password" input (`placeholder="Re-enter new password"`) has no matching
  `showConfirm` state and no toggle button at all — it is hardcoded to render as a masked
  password field with no way to reveal it.

## Expected vs Actual

- **Expected:** all three password inputs in the same form offer the same show/hide affordance,
  or at minimum the confirm field is revealable like its siblings.
- **Actual:** "Current password" and "New password" have a working eye-icon visibility toggle;
  "Confirm new password" has none and can never be shown in plain text.

## Analysis note (added by 3-analyzer)

Re-read at analysis time: `FIX-341` landed after this card was filed and shifted the state
declaration down by two lines (`showCurrent`/`showNew` now at `AccountSettings.tsx:98-99`, was
`:96-97`; toggle buttons now at `:292-294`/`:304-306`). The mechanism this card describes is
unchanged, only the line numbers drifted.

Blast radius: `showCurrent`/`showNew`/`EyeOff` is local component state with no other caller in
the codebase (`grep -rn "showCurrent\|showNew\|EyeOff" frontend/src` matches only this file) — so
there is no shared function whose fix would cover multiple call sites here. The broader cause is
architectural: `frontend/src/components/ui/` has no reusable masked-password-input component, so
every password field's reveal toggle is opt-in per call site. That gap reproduces elsewhere in
the app — see the two sibling cards below, found by grepping every other `type="password"` input
in `frontend/src`.

Proposed fix location: a shared `PasswordInput`-style primitive in `frontend/src/components/ui/`
that owns its own show/hide state, used by all password fields (this card's three, plus the two
siblings') — not a `showConfirm` patch local to this one field, which would leave the sibling
fields broken.
