## Why the root cause implies this

[ISS-206](20260828-1609-ISS-206.md) established that `handleRunOnce` is NOT symmetrically broken
for a completely untouched built-in, because of a dedicated bypass (`ComposerPage.tsx:837-857`):

```ts
const builtinIds = (initialManifestSteps ?? []).map((st) =>
  st.agent === "custom-agent" ? st.instance_id : st.agent,
);
const currentIds = pipelineAgents.map((a) => a.id);
const unmodifiedBuiltin =
  !!builtinCanvasType &&
  builtinIds.length > 0 &&
  builtinIds.length === currentIds.length &&
  builtinIds.every((id, i) => id === currentIds[i]);

if (unmodifiedBuiltin) {
  onRun(builtinCanvasType as typeof dispatchType, brief, [], /* ... */);
  return;
}
```

When `unmodifiedBuiltin` is true, the run dispatches by the built-in's OWN `pipeline_type`
(`builtinCanvasType`), bypassing `runConfig` (and its Mechanism-2 race, ISS-206) entirely — this
is why a click-through of "open ppt canvas, immediately Run once" would not show the bug.

The condition is narrower than the comment above it ("A BUILT-IN opened on the canvas and not yet
changed runs as ITSELF") suggests: `unmodifiedBuiltin` compares ONLY the ordered list of agent
ids (`builtinIds.every((id, i) => id === currentIds[i])`), not any deeper equality — it says
nothing about `runConfig`, `capabilities`, or per-agent `skills`/`prompt`/`tools`. The instant a
user makes ANY edit that changes the id list — reorder two of the three steps, add an optional
agent, remove one — `unmodifiedBuiltin` flips to `false` for the rest of the session (there is no
path back to `true`), and `handleRunOnce` falls through to the generic branch
(`ComposerPage.tsx:859-864`) that uses `effectiveDeliverable = runConfig?.deliverable ??
deliverableOverride` (`ComposerPage.tsx:759`) — the SAME `runConfig` that ISS-206's Mechanism 2
leaves stuck on the hardcoded `streamed_text`/`output.md` default for a built-in. Nothing about
that edit needs to touch the Workflow tab at all: reordering agents is enough to lose the bypass
and expose the run to the wrong deliverable.

Concretely: open `/workflows/ppt/canvas`, drag `ppt-validator` before `ppt-composer` (a pure
reorder, no deliverable/skill/prompt change), click "Run once" — the run would dispatch with
`runConfig.deliverable` (`{strategy: "streamed_text", name: "output.md"}`) instead of `ppt`'s
real `{strategy: "ppt", name: "presentation.pptx"}`, producing a markdown/streamed-text run
instead of a PPTX one, with no save involved at all.

## Expected vs actual

**Expected:** "Run once" on a built-in canvas dispatches with the built-in's real deliverable
strategy regardless of whether the edit made was to agent order/composition or to the Workflow
tab — an edit to one should not silently corrupt the other.

**Actual (inferred, not yet reproduced):** any edit that changes `pipelineAgents`' id sequence —
even one unrelated to the deliverable — permanently disables the `unmodifiedBuiltin` bypass for
the rest of the session and exposes `handleRunOnce` to the same wrong `runConfig.deliverable`
Save has (ISS-206 Mechanism 2), independent of `needsFullManifest`/Mechanism 1 (Run's
`deliverable`/`planner`/`clarify` fields are sent unconditionally, `ComposerPage.tsx:811-813` —
it is purely the VALUE that is wrong, not whether it is sent).

## Status

**INFERRED.** The bypass condition and the fallthrough's use of `runConfig.deliverable` are both
read directly from source; the click-through (reorder → Run once → inspect the launch's
`deliverable` param or the resulting run's produced file type) has not been attempted. Cheapest
way to settle it: reorder two steps on the `ppt` canvas, click Run once, and check the fired
request's `deliverable`/`extraParams` the same way ISS-196 inspected the Save POST body.
