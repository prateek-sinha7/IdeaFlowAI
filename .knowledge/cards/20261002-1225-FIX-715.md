# FIX-715

## What was wrong

This fixes bug report QA-KB-051. The root cause comes from [BUG-127](20260918-BUG-127.md) and its 2026-10-02 analysis. It
is not re-derived here.

`tools/knowledge/build_context.py:431` was `OUT_PATH.write_text(body, encoding='utf-8', newline='\n')`. `Path.write_text`
has no `newline` parameter before Python 3.10. Every documented spelling of the rebuild uses a bare `python3`: the
`skills/velocity/cli.md` table, `.pre-commit-config.yaml:176`, and every bug-line agent. Here that resolves to
`/usr/bin/python3` 3.9.6.

The context stage therefore died with `TypeError: write_text() got an unexpected keyword argument 'newline'` whenever the
pack body changed. By then `index` had already rewritten `INDEX.md` and `state.yaml`, and `validate` never ran.

## What changed, and why there

One line, `tools/knowledge/build_context.py:431`:

    OUT_PATH.write_bytes(body.encode('utf-8'))

- **The fix is at the funnel.** Every entry point reaches this write:
  - the full rebuild
  - the cards-only rebuild
  - the sync-point stamp
  - `--hook` phase 3, which re-enters `main()` at `rebuild_knowledge.py:255`
  - a direct run of `build_context.py`

  Each of them runs the stage with `sys.executable` (`rebuild_knowledge.py:82`, `:165`). One call therefore fixes every
  `python3` spelling at once. No doc, hook or interpreter spelling changed.
- **Why `write_bytes` rather than dropping the kwarg.** The BUG-127 analysis traced the kwarg to `9d7bd554f`, a Windows
  encoding fix. A `write_text` without `newline=` writes CRLF on Windows. Encoding the string and writing bytes does no
  newline translation on any OS, which is what `newline='\n'` did. The encoding (`utf-8`) and the error mode (`strict`)
  are unchanged.
- **The output is byte-identical, measured.** Three writes of `main()`'s output have the same sha256 (`9211886c8b2ed78d`)
  and 0 CR bytes:
  - the new call under 3.9.6
  - the new call under 3.13.14
  - the old call writing the same body under 3.13.14

## Not fixed here

- **[ISS-971](20261002-0342-ISS-971.md) stays open.** A sync-point stamp still moves `last_sync_commit` and
  `last_sync_date` in the `index` stage (`build_index.py:375-381`), before `context` and `validate` run. This fix removes
  the trigger ISS-971 was reproduced with, not its mechanism. A `MissingInput` from `build_context.load_modules()` still
  trips it. Its card has no test (`test_files: []`).
- **[ISS-1047](20261002-1225-ISS-1047.md) is new and open.** It records BUG-127's second defect, the ordering half: a
  `context` failure still leaves `INDEX.md` and `state.yaml` rewritten while `CONTEXT.md` is stale.
  - BUG-127 lists three options for it and picks none.
  - No test was written for it.
  - `cli.md:67-76` already documents the non-atomic behaviour and its recovery, which is to re-run.
  - The report's Expected does not need it: "The rebuild completes under the interpreter the docs name (bare python3)".
- **The analysis also proposed an interpreter-independent guard, and it was not written as a test.** The guard is an `ast`
  scan of `tools/knowledge/*.py` for `newline=` on `write_text` or `read_text`. The py39 test skips on any machine whose
  `/usr/bin/python3` is 3.10 or newer, so on such a machine nothing guards against the next 3.10-only API. I ran the scan
  once by hand (see Verification). It was clean.

## For the 6-verifier

- **No server restart is needed.** Neither the backend nor the frontend loads `tools/knowledge/`.
- **Remove the `xfail(strict=True)` marker** on `test_build_context_runs_under_python39`.
- **Re-run the BUGS.md repro:** `/usr/bin/python3 tools/knowledge/rebuild_knowledge.py --skip-architecture` from the repo
  root. It reaches the old failure only when the CONTEXT.md body differs from the pack on disk; otherwise
  `build_context.py:426-430` returns early. A new card or a new commit is enough to make the body differ.
- **Or run the sandbox oracle,** `bash evidence/qa-kb-051/analysis-sandbox-repro.sh`. It forces the changed-body case
  without touching the tree.
