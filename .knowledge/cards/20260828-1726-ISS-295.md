## Summary

On `/admin`, the "Create New User" dialog's "Create User" button is enabled by
any non-empty Email + Password pair — there is no email-format check
client-side. Submitting a string with no `@` and no domain (e.g.
`not-an-email`) succeeds: the backend's `POST /api/admin/users` accepts it
without complaint and persists a real user row (`GET /api/admin/users` shows
`"email": "not-an-email"`, a real UUID, plan "Basic", `is_admin: false`). The
row renders normally in the admin table. Such an account can never sign in
through `/login` (nothing resembling an email was stored), so it becomes a
permanently orphaned record unless an admin notices and deletes it by hand.

Both layers are missing the check — the button-enable logic in the dialog
component (presence-only, not format), and the FastAPI handler behind
`POST /api/admin/users` in `backend/app/api/admin.py` (no email validator on
the request body / no `EmailStr`-equivalent constraint enforced before the
insert).

## Reproduction (3/3, cycle 1)

Reproduced on cycle 1 and confirmed identically on cycles 2 and 3, all from a
cold start (fresh navigation from `/dashboard` to `/admin`, not a soft
re-click of an already-open screen):

1. Sign in as `qa-admin@flowinqa.com`, navigate to `/dashboard`, then to
   `/admin` (fresh nav each cycle).
2. Click "Add user" to open the "Create New User" dialog.
3. Enter a malformed string with no `@`/domain in Email (`not-an-email`,
   `bademail2`, `bademail3` across the three cycles), and an 8+ character
   string in Password. Plan left at default "Basic", "Grant admin access"
   left unchecked.
4. Observe "Create User" is enabled (not blocked by the malformed email) as
   soon as both fields are non-empty.
5. Click "Create User".
6. Observe a success toast ("User \<value\> created") and a new row in the
   table with the literal malformed string as the email. Confirmed via
   `GET /api/admin/users` (fetched with the admin's own bearer token) that
   the record persists server-side.
7. Cleanup performed after each cycle: deleted the throwaway user via its
   row's Delete action + confirm dialog; verified via `GET /api/admin/users`
   that only the 4 original seeded users (`qa-admin`, `qa-enterprise`,
   `qa-pro`, `qa-basic`) remained before starting the next cycle.

No axis needed to be varied — reproduced identically on account (qa-admin),
theme (default/light), viewport (default), and both first-visit and
subsequent-visit entry paths.

## Expected vs Actual

**Expected:** The Email field is validated as a well-formed email address
before "Create User" is enabled client-side, and `POST /api/admin/users`
independently rejects a value with no `@`/domain server-side, returning a
validation error (422) rather than persisting the record.

**Actual:** Both layers accept the malformed string unconditionally. A new
user row is created and persisted with an unusable "email" value and no
error surfaced anywhere in the flow.
