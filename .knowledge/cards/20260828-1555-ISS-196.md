## Summary

Validated register entry `BUG-20260828-005700-workflows-ppt-canvas`. Reproduced 3/3 from cold
start (fresh `/dashboard` -> `/workflows/ppt/canvas` navigation each time, no narrowing needed —
deterministic on every attempt, cycle 1 through cycle 3 identical).

**Route:** `/workflows/ppt/canvas` (built-in canvas) and the resulting copy's own
`/workflows/{id}/edit`.

**Root cause:** `ComposerPage.tsx` never seeds its `runConfig` state from the opened built-in's
actual `deliverable`/tool-grant manifest. `runConfig` is initialized (around line 337) to a
hardcoded fallback:

```ts
const [runConfig, setRunConfig] = useState<WorkflowRunConfig>(
  initialRunConfig ?? {
    deliverable: { strategy: "streamed_text", name: "output.md" },
    planner: "skip",
    clarify: { mode: "skip", defaults: [] },
  },
);
```

For a saved user-workflow, `initialRunConfig` comes from that row's own `manifest_json`. For a
**built-in** opened via `/workflows/<type>/canvas`, there is no saved row, and nothing in the
mount path populates `initialRunConfig` from `GET /api/workflows/<type>`'s real `deliverable`
field — so the fallback default (`streamed_text` / `output.md` / `.md`) silently stands in for
the built-in's actual `deliverable.strategy: "ppt"` / `presentation.pptx`. This is why the
Workflow tab's "Deliverable strategy" combobox shows "Streamed text" with fully enabled,
editable-looking controls even though nothing about the built-in matches that value.

The consequence is not cosmetic: `handleSave`'s copy path builds and POSTs
`manifest: buildWorkflowManifest(pipelineAgents, capabilities, selections, runConfig)` (line
~629) from this same wrong `runConfig` plus the current `selections`/`capabilities` — none of
which carry the built-in's per-agent tool grants (`read_files`/`write_files`) or its `"ppt"`
deliverable strategy, because those never entered component state in the first place. The saved
copy is left permanently generic.

## Reproduction (cycle 1 of 3, all three identical)

1. Cold start: sign in as qa-admin (session already authenticated), navigate fresh to
   `/dashboard`, then fresh to `/workflows/ppt/canvas`.
2. Confirmed via `GET http://localhost:8000/api/workflows/ppt` that the real manifest is
   `deliverable: {"strategy":"ppt","name":"presentation.pptx"}`.
3. On the canvas, the Workflow tab's "Deliverable strategy" combobox reads "Streamed text —
   agent's raw output" (selected), not "ppt" — confirmed via accessibility snapshot.
4. Filled "Workflow name" ("Bug Hunter PPT Validate C1"), clicked "Save as copy".
5. `POST http://localhost:8000/api/user-workflows` -> `201`, response body:
   `{"id":"bd1ec6f4-...","base_pipeline_type":"custom","manifest":null,"agent_ids":["ppt-brief-analyst","ppt-composer","ppt-validator"],...}`.
6. Navigated to `/workflows/bd1ec6f4-.../edit` — `document.body.innerText.includes('pptx')` ===
   `false`; Workflow tab shows the same generic Streamed text/output/.md.
7. `GET /api/workflows/ppt` re-checked post-copy: still `deliverable.strategy: "ppt"` — the
   built-in itself was never mutated.
8. Cleaned up: `DELETE /api/user-workflows/bd1ec6f4-...` -> `204`.

Cycle 2 (fresh `/dashboard` -> `/workflows/ppt/canvas` reload, name "Bug Hunter PPT Validate C2")
and cycle 3 (same, name "...C3") both produced the byte-identical result: `manifest: null`,
`base_pipeline_type: "custom"` in the POST response, built-in confirmed pristine afterward. No
axis variation (timing, entry path, account, theme, viewport) was needed — the defect is
deterministic on every cold load and every save.

## Expected vs Actual

**Expected:** the canvas's Workflow tab reflects the opened built-in's real deliverable strategy
(or visibly indicates it cannot be represented), and "Save as copy" carries forward the full
manifest — tool grants and deliverable strategy — from the built-in it forks.

**Actual:** the canvas always shows the hardcoded `streamed_text`/`output.md` default regardless
of the built-in's real manifest, and "Save as copy" persists `manifest: null`, producing a copy
with no `.pptx` deliverable and no per-agent tool grants — a workflow whose sole purpose is
producing a PPTX deck becomes, once copied, a generic streamed-text/markdown workflow with no
in-UI signal that anything was lost.

## Relationship to ISS-183

Distinct from, but adjacent to, [ISS-183](20260825-2115-ISS-183.md) (`composerAlwaysSaysCustom`
— `base_pipeline_type` is unconditionally `"custom"`). ISS-183 is a type-label mismatch only;
this defect is the loss of the entire manifest object — deliverable strategy and per-agent tool
grants — verified via direct `POST`/`GET` API diff, not merely a label. Both trace through the
same component, `ComposerPage.tsx`, but are separate root causes at different lines.
