# FIX-749

## What was wrong

Register entry QA-KB-091 (Low, `/runs/{member}/versions/{n}`), root card [ISS-952](20261002-0147-ISS-952.md).
The shell is the run the URL names; the pin is a DIFFERENT family member with no stored output. The
shell's status won over the pin's:

- cancelled shell: "This run was cancelled";
- diverted shell: "did not complete successfully";
- failed or degraded shell: the Preview tab was dropped, Audit forced, and the header read "Run failed".

Two siblings come from the same root, both analysed with it:

- [ISS-1031](20261002-1040-ISS-1031.md): the header followed the shell. A pinned completed version
  WITH content, or one picked from the Version menu, read "Run failed" with Share and Download gone.
- [ISS-1032](20261002-1040-ISS-1032.md): a streaming shell showed "Building your deliverable…" over a
  settled pin with no output.

## Root cause (from ISS-952's analysis, re-checked on this tree before editing)

`hasContent` is PIN-keyed (built from the `eff*` slots that follow `viewingVersion`). Every
terminal-state signal ahead of FIX-709's pinned branch read the SHELL's raw props:

- `liveFailureSignal` (`PreviewPanel.tsx:1170`, `pipelineState.failed/.degraded`);
- `reopenFailureSignal` (`:1175-1178`), `isCancelledTerminal` (`:1185`) and `isDivertedTerminal`
  (`:1191`), all from `reopenedRunStatus`, the status of the run the URL names;
- `isStillRunning` (`:1168`), at the streaming branch (`:1882`).

An empty pin makes `!hasContent` true, so the shell's affordance branch (`:1853`), the tab drop
(`terminalFailureNoDeliverable` `:1202` -> `visibleTabs` `:1223`), the Audit default
(`defaultTabDiscriminator` `:1322`), the header (`headerFailed` `:1277` -> `failed=` `:1752`, the
download gate `:1457`) and the streaming branch all answered before the pinned branch (`:1907`).

Blast radius re-grepped before editing: the one production mount is still
`DashboardLayout.tsx:3392` (`liveRunId={contentSourceRunId}`, `reopenedRunStatus`, `pipelineState`,
`pinnedVersion`). Both pin routes, `handleSelectVersion` (`:923`) and the URL-pin effect (`:1041`),
feed the one `viewingVersion`, so a change where the signals are defined covers both.

## What changed, and why there

`frontend/src/components/preview/PreviewPanel.tsx`, variant C of the ISS-952 analysis
(`evidence/qa-kb-091/06-analyze-candidate-fix-diffs.txt`), applied as validated:

1. `:1101-1104`. One predicate beside `overrideActive`:
   `const shellOnScreen = viewingVersion == null || viewingVersion.id === unpinnedRunId;`
   It mirrors `handleSelectVersion`'s own "this member is what the un-pinned route shows" test
   (`memberId === unpinnedRunId`, `:947`).
2. `:1170`, `:1175-1178`, `:1185`, `:1191`. The four shell signals AND `shellOnScreen`. Every reader in
   ISS-952's blast-radius table routes through them: both affordance predicates, the tab drop, the
   Audit default, `headerFailed` and so the header badge, Share, Download and its resolve gate, and the
   FilesTab `runStatus` banner.
3. `:1882`. The streaming branch becomes `isStillRunning && shellOnScreen` (ISS-1032). `isStillRunning`
   itself is untouched: the header's "building" state and the Steps tab still follow the live run.

Why the definitions and not the consumers: one gate covers every consumer, and the triage sketch
(`!overrideActive` on the two affordance predicates) leaves the header failed. Why `shellOnScreen` and
not `!overrideActive`: the URL-pin effect can pin the shell run itself, and for that self-pin the shell
IS what is on screen. Probe row G4 and the ISS-952 self-pin control stay exactly as before.

## Deliberately not changed

- The test-writer's `it.fails` markers in `PreviewPanel.shellStatusForeignPin.iss952.test.tsx`; the
  6-verifier removes them.
- FIX-709's pinned branch, `versionViewFrom`, `reopenedRunStatus` and `terminalFailure`'s own shape.
- `showCancelledAffordance` (`:1205`) stays a dead constant (pre-existing; eslint already reports it).
- **Residual 1, recorded as [ISS-1070](20261007-2051-ISS-1070.md) (open):** under a failed or degraded
  shell, an empty foreign pin lands on Audit. The Preview tab is in the strip and shows the pin's copy
  once clicked, but the default-tab latch (`:1350`) already fired for the pre-pin "failed" render.
  Variant D would land on Preview, at the cost ISS-952 names (a pin whose fetch is in flight or failed
  is treated as foreign). C is the analysis's safer minimum, so D was not taken.
- **Residual 2, recorded as [ISS-1069](20261007-2051-ISS-1069.md) (open, needs a product call):** the
  reverse direction from ISS-1031. A pinned version that itself ended failed or degraded, WITH content,
  gets a settled header. Nothing in the header reads `viewingVersion.status`. This change does not
  touch it, but it widens one case: pinning a live revision that has just failed while `liveRunId`
  still names its parent now gets that same pinned surface.
