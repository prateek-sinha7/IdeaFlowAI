### BUG-003 — Revise-via-chat "Run refinement" fires nothing / launches no revision on an opened run  [🟠 major] [FIXED ✅]
- **RESOLVED:** FIXED (quick 260716-j1u, 8b4e2eb7) — offline-proven TS-U-09

- **Found:** 2026-07-16 · live Bedrock QA · surface run screen → left chat lane (`RunChatLane`) confirm-first refinement chip, on a **recents/history-opened COMPLETED od_ppt run** (`6c6f38c7`, "A 6-slide investor pitch for a B2B carbon-accounting SaaS").
- **Symptom:** On the opened run, typing a change and chat-send correctly HELDS it behind the confirm chip ("RUN A REFINEMENT WITH THIS CHANGE? … [Run refinement] [Dismiss]", 44-02 behavior — no POST on send, verified). Clicking **"Run refinement"** → **ZERO non-GET `/api/` requests fire**, the chip disappears, and **NO `*_revision` run is created**. The opened run's deliverable **Preview was also BLANK** (presentation.pptx did not render inline). Shots: `~/.claude/jobs/e660aea4/tmp/shots-qa/{revise-chip,revise-launched,revise-clean-after}.png`.
- **Root cause (investigation agent — read `.planning/IMPLEMENTATION-REGISTER.md` global + FE run-screen/revise phase sections 31/39/42/44 + Revision-Families B1 + LV-02/Phase-15; grep-confirmed od_ppt agent membership in `backend/agents/registry.py` and the od_ppt deliverable manifest):**
  - **The swallow (primary, deterministic) — `frontend/src/components/layout/DashboardLayout.tsx:493`.** `handleRevisePpt` opens with a pre-existing empty-content guard `if (!pptxCode && !pptContent) return;` that short-circuits BEFORE the self-sufficient REST path at `:504` (`if (contentSourceRunId) { postRevision(token, contentSourceRunId, { target_artifact_type, instruction }) … }`). On a reopened od_ppt run BOTH content fields are empty, so the handler returns immediately → no `postRevision`, no `onStartPipeline` → **zero network requests**. The confirm handler `confirmRefinement` (`frontend/src/components/chat/RunChatLane.tsx:712-715`) calls `setHeldRefinement(null)` **unconditionally** after invoking `onRevise`, so the chip vanishes even when `onRevise` no-ops — exactly the observed "chip disappears, nothing happens." Wire: chip button `data-testid="chat-refinement-confirm"` `onClick={confirmRefinement}` (`RunChatLane.tsx:803`) → `onRevise` = `activeReviseHandler` (`DashboardLayout.tsx:1717` ← selector `:1233-1240`) → `handleRevisePpt`.
  - **The empty/null fields (why both are empty on a reopened od_ppt run — VERIFIED):**
    - `pptxCode` (`DashboardLayout.tsx:481`) = `pipelineState?.agents.find(a => a.id === "ppt-code-generator" && a.status === "done")?.output`. **od_ppt has NO `ppt-code-generator` agent** — its agents are `od-ppt-brief-analyst` / `od-ppt-composer` / `od-ppt-validator` (`backend/agents/registry.py:53-57`); that agent belongs only to the legacy `ppt` pipeline. So `pptxCode` is **structurally always `undefined` for od_ppt** (live and reopened). The guard therefore reduces to `if (!pptContent) return;` for od_ppt — no second field can rescue it.
    - `pptContent` (a page.tsx prop, `page.tsx:83`) on reopen = `fullRun.output` (set at `page.tsx:1254`, `else if (fullRun.type === … "od_ppt" …) setPptContent(fullRun.output)`), but ONLY `if (fullRun.output && isContentTerminal)` (`:1250`). For this run `fullRun.output` was **empty**, so `pptContent` stayed `""` (cleared at reopen start `page.tsx:1169`, never repopulated). Empty `fullRun.output` is ALSO exactly why the Preview was blank — **the blank preview and the no-op revise are SIBLING symptoms of the same empty `output`.**
    - **Why od_ppt's `output` can be empty (LV-02, register lines 79/1487/1512/1553/1605):** od_ppt's deliverable is `strategy: ppt`, `name: presentation.pptx` (`backend/agents/workflows/od_ppt/workflow.yaml:11-13`); the `ppt` strategy unwraps the `od-ppt-validator`'s `<artifact>`-wrapped deck into `final_output`, persisted to `wr.output` only `if final_output:` (`backend/app/api/run_commands.py:1445-1446`). LV-02 is the KNOWN failure mode where the validator streams QA narration (or nothing parseable) instead of a deck → `final_output` empty/non-deck. Phase 15 "closed" LV-02 with an `od-ppt-validator` AGENT.md **output contract** (a prompt instruction, NOT a hard guarantee), so on a live Haiku run it CAN recur → empty `output` → blank preview + no-op revise.
  - **Aggravator (L2) — the selected handler may be the WRONG one on a completed reopen (BUG-001/002 class).** `workflowType` is DashboardLayout-internal state (`:250-256`, default `"user_stories"`); it is only rebound by the sync effect at `:330-345`, which is **gated on `if (pipelineState?.isRunning)`** and thus **never runs for a completed reopen** (`isRunning` is false). So on a reopened od_ppt run `workflowType` stays stale (likely `"user_stories"`), and the `onRevise` selector (`:1233-1240`) resolves to `handleReviseUserStory` (guard `if (!userStoryContent) return;`, `:541`) — NOT `handleRevisePpt`. Every run-lane revise handler has the same empty-content guard (`handleReviseUserStory:541`, `handleRevisePrototype:557`, `handleReviseAppBuilder:573`), and on a reopened run with empty `output` ALL content fields are empty — so whichever handler is picked, it no-ops identically. Crucially, `handleRevisePpt` is the ONLY one with the content-free REST bypass (`postRevision`), so a stale `workflowType` means even the path that COULD succeed is not reached. This is the same "reopen doesn't fully bind to the viewed run" defect as BUG-001 (viewed-run TITLE) and BUG-002 (viewed-run open path) — here the viewed-run TYPE.
  - **Confound verdicts (which is the true cause):** (1) **Blank preview / deliverable not loaded — TRUE, the trigger.** Empty `fullRun.output` → empty `pptContent` → guard fires. (2) **BUG-001 header mis-binding — NOT the cause.** `contentSourceRunId` IS correctly set to the od_ppt run id on reopen (`page.tsx:1187`); BUG-001 only mis-binds the lane TITLE. The revise no-op happens upstream of any `contentSourceRunId` read — the guard returns before `:504`. (The parallel `workflowType` mis-binding, L2, IS a genuine BUG-001-class sibling.) (3) **Run out of recents — NOT the cause.** `handleSelectWorkflowRun` binds by fetched run id regardless of scroll position.
  - **DEF-44-12-4 seed is NOT the gap.** The Steps/transcript seed (`page.tsx:1198-1241`) is separate from the deliverable-content seed (`:1250-1256`), which is an **unconditional** block that DOES set `pptContent` from `fullRun.output`. The gap is that `fullRun.output` itself was empty, not a missing seed.
  - **Pre-existing verdict — the guard is PRE-EXISTING; the DEFECT (guard blocking the REST path) is RECENT.** `git blame`: the guard line 493 + `handleRevisePpt` decl (line 492) = `dc9de28fa` **Prateek Sinha 2026-05-11** (the legacy text-injection revise era, where the guard was correct — that path embeds `pptContent`/`pptxCode` into the message and genuinely needs them). The `contentSourceRunId` REST branch at line 504 = `a931c066a` **imran-hex 2026-07-15** (Revision Families / `postRevision`). The REST path is self-sufficient (backend seeds the parent artifact server-side from `contentSourceRunId` — Strategy A byte-twin of `engine._handle_revision`), but was added BELOW the stale content guard without relaxing it → the guard now wrongly gates a path designed to work WITHOUT local content. So the swallow defect dates to **2026-07-15**.
  - **od_ppt-specific vs general.** In practice **specific to od_ppt** (two od_ppt-only aggravators: no `pptxCode` fallback + LV-02-fragile empty `output`). Text-deliverable types (user_stories / app_builder / prototype) reliably persist non-empty text `output`, so their content guards pass on reopen and their revises fire (via `onStartPipeline` + `source_workflow_run_id`). But the empty-content guard pattern is in all four handlers, so the **latent general mechanism** is: any reopened run whose `fullRun.output` fails to load silently no-ops its revise. Severity **🟠 major** (not 🔴): conditioned on empty `output`, not universal across opened runs.
- **Fix (PROPOSED — investigation only, not applied):** two edits (both needed for od_ppt reopen-revise end-to-end); minimal + SC-001-safe (keys only on generic run identity, zero workflow-name literal added):
  1. **`DashboardLayout.tsx:493`** — stop the empty-content guard from blocking the self-sufficient REST path:
     ```
     -    if (!pptxCode && !pptContent) return;
     +    if (!contentSourceRunId && !pptxCode && !pptContent) return;
     ```
     When `contentSourceRunId` is present (always, on a reopened/completed run), the handler proceeds to `postRevision` (`:504`), which reseeds the parent deck server-side — working even when the FE never loaded the deck. The legacy text-injection fallback (`:520-536`) is unchanged and only reached when `contentSourceRunId` is falsy (and already reads `pptContent`/`pptxCode` with `|| ""`).
  2. **Bind the revise-handler selection to the VIEWED run's type on reopen** so `onRevise` actually resolves to `handleRevisePpt` for a reopened od_ppt run. The sync effect at `DashboardLayout.tsx:330` is `isRunning`-gated and never fires for a completed reopen; thread the viewed run's type down from `page.tsx handleSelectWorkflowRun` (mirroring how it already threads `contentSourceRunId`/`submittedBrief`), or have the selector (`:1233-1240`) fall back to the reopened run's type when not running. (BUG-001/002-class viewed-run binding — for run TYPE.)
  - **Secondary hardening (recommended, not required):** make the confirm path never SILENTLY no-op — when a change can't be launched, surface an error/toast instead of clearing the chip with nothing fired (`RunChatLane.tsx:712-715`), so an empty-`output` condition is visible.
  - **Do NOT "fix" the empty `output` in the od_ppt resolver** — register line 1594 locks that `ppt.py`/`_artifact.py` are READ-ONLY; the upstream LV-02 remedy lives in the `od-ppt-validator` output contract. The FE guard relaxation is the correct FE-side resilience so a content-less-but-valid parent still revises over REST.
- **Verify (fail-before / pass-after):**
  1. **Fail-before:** open a COMPLETED od_ppt run from Home recents whose Preview is blank (empty `output`); type a change → confirm chip appears; click "Run refinement" → capture non-GET `/api/` traffic = EMPTY, chip clears, no new `*_revision` in `GET /api/runs`. (Reproduced live: `6c6f38c7`.)
  2. **Pass-after:** same click → exactly one `POST /api/runs/{contentSourceRunId}/revisions` fires (`target_artifact_type: "od_ppt_output"`), the returned run attaches over SSE (`runConnection.attachRun`), and a new `od_ppt_revision` appears in `GET /api/runs` linked to the parent — even with the deck content unloaded.
  3. **No-regression:** a fresh live od_ppt build (with `pptContent`) still revises; a reopened run WITH a loaded deck still revises; text-deliverable reopened runs (user_stories/app_builder/prototype) unaffected.
  4. **Unit:** a `DashboardLayout` vitest — `handleRevisePpt` with `contentSourceRunId` set but `pptContent`/`pptxCode` empty calls `postRevision` (not early-return); and the reopen path selects `handleRevisePpt` for an od_ppt viewed run. `tsc --noEmit` clean.
