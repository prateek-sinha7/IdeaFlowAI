## What happened (inferred — not yet reproduced)

[ISS-695](20260922-0800-ISS-695.md) confirmed that any `httpx.AsyncClient()` built with
default TLS verification fails every outbound HTTPS call in this environment (a
TLS-intercepting proxy whose CA sits outside certifi's bundle). `backend/app/services/
handoff_github.py` builds two more such clients, both used by the "Push to GitHub" handoff
pull-request flow:

- `get_repo_metadata` (`:292`) — `httpx.AsyncClient(timeout=15.0)`, fetches the target repo's
  default branch before the handoff workspace is prepared. Called from
  `backend/app/services/handoff_pipeline.py:378`.
- `create_pull_request` (`:334`) — `httpx.AsyncClient(timeout=30.0)`, opens the PR once the
  branch is pushed. Called from `backend/app/services/handoff_pipeline.py:570`.

Neither passes `verify=`, so both inherit the identical certifi-only default.

## Why the root cause implies it

Same construction (`httpx.AsyncClient()`, no `verify=` override) against the same class of
target (`api.github.com`, a public HTTPS host) that ISS-695 already proved fails in this
environment for `example.com`, `hexaware.com` and `www.google.com`.

## Expected vs actual (expected on reproduction)

- **Expected:** a handoff run with a valid GitHub PAT fetches the target repo's default
  branch, then opens a PR once the branch is pushed.
- **Actual (predicted):** both calls raise the same `httpx.ConnectError` /
  `SSLCertVerificationError`. Neither function catches anything narrower than
  `resp.status_code >= 400` (`handoff_github.py:302-306`, `:345-348`) — a transport-level
  exception is not a response, so it is not caught there and propagates uncaught up through
  `handoff_pipeline.py`'s call sites, most likely surfacing as a generic failed-handoff state
  rather than a specific message.

## Evidence

- `backend/app/services/handoff_github.py:292` —
  `async with httpx.AsyncClient(timeout=15.0) as client:`
- `backend/app/services/handoff_github.py:334` —
  `async with httpx.AsyncClient(timeout=30.0) as client:`
- `backend/app/services/handoff_github.py:302-306`, `:345-348` — both functions only branch on
  `resp.status_code >= 400`; nothing wraps the `client.get`/`client.post` call itself
- `backend/app/services/handoff_pipeline.py:378` (`get_repo_metadata` call site), `:570`
  (`create_pull_request` call site)
- [ISS-695](20260922-0800-ISS-695.md)'s direct-interpreter reproduction is the proof this
  construction pattern fails in this environment

## What would settle it

Run a handoff to a real GitHub repo with a valid PAT in this environment and observe whether
`get_repo_metadata` throws at the branch-metadata step.

## Test (test-writer pass, 2026-09-22) — refuted, not reproducible in this environment

Called both functions directly with a real (public) repo target and a fake PAT:

```
$ backend/.venv/bin/python -c "asyncio.run(get_repo_metadata(RepoTarget('octocat','Hello-World'), pat='ghp_faketoken0000000000000000000000'))"
RuntimeError (handled) GitHub repo metadata fetch failed (401): {"message": "Bad credentials", ...}
$ backend/.venv/bin/python -c "asyncio.run(create_pull_request(RepoTarget('octocat','Hello-World'), pat='ghp_faketoken0000000000000000000000', head_branch='x', base_branch='main', title='t', body='b'))"
RuntimeError (handled) GitHub PR creation failed (401): {"message": "Bad credentials", ...}
```

Both reach `api.github.com` cleanly and return the normal handled `RuntimeError` path — no
SSL/TLS error. As on [ISS-750](20260922-1403-ISS-750.md), this environment's TLS-intercepting
proxy does not intercept `api.github.com` (see [ISS-695](20260922-0800-ISS-695.md)'s "Test"
section for the host comparison). The analysis's generalization from ISS-695 does not hold
for this host in this environment — no test written; there is no defect here to assert
against today.

## Fix (fixer pass, 2026-09-22) — [FIX-607](20260922-1814-FIX-607.md)

Fixed with the root card, not separately: `get_repo_metadata` / `create_pull_request` (`backend/app/services/handoff_github.py:292,334`) now passes
`verify=default_ssl_context()` (`backend/app/core/http_client.py`), the same
shared context ISS-695's own call site uses. One keyword argument per call
site; the context can only widen the trusted-CA set, never narrow it.

Still `verification.status: not_reproducible` — the test-writer's refutation
stands (this environment's proxy does not intercept `api.github.com`, so
the failure never surfaced here). The call site is fixed anyway because the
mechanism is identical and the exemption is a property of this proxy's
allowlist, not of the code.
