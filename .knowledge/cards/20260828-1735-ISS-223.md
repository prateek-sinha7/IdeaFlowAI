## What this corrects

[FIX-325](20260828-1645-FIX-325.md) fixed both mechanisms
[ISS-206](20260828-1609-ISS-206.md) named, and the 6-verifier confirmed both on the live app:
the `/workflows/ppt/canvas` Workflow tab now shows `ppt` / `presentation.pptx`, and the
`POST /api/user-workflows` body now carries the full manifest with
`deliverable.strategy: "ppt"`. Copying `ppt_v2` (strategy `single_file`) now succeeds —
`201 Created`, manifest persisted — so [ISS-203](20260828-1610-ISS-203.md) /
[ISS-204](20260828-1611-ISS-204.md) / [ISS-205](20260828-1612-ISS-205.md) are genuinely cured.

For `ppt` itself the save is now refused outright: `422 Unprocessable Entity`, no row created.

## Root cause of the remaining failure

`backend/agents/capabilities/deliverables/ppt.py:47-51` registers the resolver **without**
`user_allowed`, and `CapabilityRegistry.is_user_allowed` defaults to `False`
(`backend/agents/capabilities/registry.py:385`). `_validated_manifest`
(`backend/app/api/user_workflows.py:137`) hands the saved manifest to `_compile_check_manifest`
(`:115`), which compiles at `trust="db"` — an UNTRUSTED source
(`backend/agents/workflows/compiler.py:204`, `_TRUSTED_SOURCES = {"file", "builtin"}`) — so
`WorkflowCompiler._check_trust` (`:418-441`) rejects the reference.

Reproduced directly, no browser (backend, `python3.11`):

```
>>> _validated_manifest({"steps": [{"agent": "ppt-brief-analyst"}, {"agent": "ppt-composer"},
...                                {"agent": "ppt-validator"}],
...                      "deliverable": {"strategy": "ppt", "name": "presentation.pptx"}},
...                     "workflow:copy-of-ppt")
HTTP 422 invalid workflow manifest (workflow:copy-of-ppt): capability ('deliverable', 'ppt') is
not user-allowed in workflow 'user-workflow-validate' — a user/db manifest may not reference it
(CAP-03)
```

The same call with `{"strategy": "single_file", "name": "presentation.html"}` returns `ACCEPTED`,
which is exactly the verifier's `ppt` vs `ppt_v2` contrast, measured one layer down.

Registry state, read at runtime:

| deliverable | registered | user_allowed |
|---|---|---|
| `streamed_text` | yes | **yes** |
| `single_file` | yes | **yes** |
| `serialized_sandbox` | yes | **yes** |
| `ppt` | yes | no |
| `repo_diff` | yes | no |

## Why this is a ruling, not a patch

[ADR-0027](20260825-2115-ADR-0027.md) — status `active` — already decided this exact question,
and its `compact_summary` names the same two capabilities:

> "A full user manifest **cannot compile** for `ppt`... Both `deliverable/ppt` and
> `context_provider/opendesign` lack the flag, so a DB-sourced ppt manifest is refused at
> `trust="db"`. The alternatives were to make those capabilities user-grantable — widening the
> trust surface for every user manifest, not just overrides — or to special-case ppt. Overlaying
> `steps` alone needs neither."

Its locked constraint is "An override supplies `steps` and nothing else; deliverable,
context_providers, planner, clarify, seed_files and limits always come from the file manifest."
The register entry's stated Expected — "a copy of a PPTX-producing workflow still produces a
PPTX" — contradicts that constraint for `ppt`, so no fixer may satisfy it by editing code.

## Options (a human picks one)

1. **Register `ppt` as `user_allowed=True`** — a one-line change at
   `backend/agents/capabilities/deliverables/ppt.py:47-51`. It makes the copy work end to end and
   is the only option that satisfies the register entry as written. Argument for: the resolver is
   import-pure — it string-transforms `ctx.last_streamed` and reads no sandbox file, so it is
   strictly *less* privileged than `single_file` and `serialized_sandbox`, both already
   `user_allowed=True` (`streamed_text.py:27-31` states that reasoning explicitly for itself).
   Argument against: ADR-0027 weighed and rejected exactly this ("widening the trust surface for
   every user manifest, not just overrides"), the same question immediately reopens for
   `repo_diff` and `context_provider/opendesign`, and the flag is a security boundary
   (CAP-03 / D-02), not a bug. Requires superseding or amending ADR-0027.
2. **Make "Save as copy" of a built-in an OVERRIDE, not a custom copy** — persist
   `overrides_pipeline_type: "ppt"` (the field already exists,
   `backend/app/api/user_workflows.py:236-243`) with steps only, so the deliverable comes from
   the file manifest at launch. This is the architecturally sanctioned shape
   ([ADR-0027](20260825-2115-ADR-0027.md), [ADR-0033](20260825-2115-ADR-0033.md)) and needs no
   trust change. Blocked by [ISS-183](20260825-2115-ISS-183.md): the composer hardcodes
   `base_pipeline_type: "custom"` deliberately, and that card is itself an unresolved design
   decision. Also changes what "Save as copy" *means* (ADR-0014), which is a product call.
3. **Filter the deliverable on the frontend** — send only user-allowed strategies (the
   capabilities API already publishes the flag, `backend/app/api/capabilities.py:9`) and surface
   a visible "this workflow's `ppt` deliverable cannot be carried into a copy" notice. Satisfies
   [ISS-196](20260828-1555-ISS-196.md)'s alternative Expected ("or visibly indicates it cannot be
   represented") and removes the 422, but the copy still runs `streamed_text`/`output.md` — the
   launch default at `backend/app/api/run_commands.py:2612` — i.e. the original symptom, minus
   the silence. It would also make ISS-196's regression test red again, since that test asserts
   the POST carries `deliverable.strategy: "ppt"`.
