# ISS-968

**INFERRED, not reproduced.** Derived while analysing QA-KB-052 ([ISS-472](20260829-0110-ISS-472.md)). Every link below was
read in source; what has not happened is anyone driving the screen as a locked tier and clicking Save. An unreproduced sibling
is a lead, not a defect.

Line numbers are the working tree on 2026-10-02 (HEAD `024c03ef8`); `IdeaInputPage.tsx`, `DashboardLayout.tsx` and `page.tsx`
carry uncommitted edits from other work, so they can sit a few lines off HEAD.

## Condition

A tier whose plan excludes the pipeline (for example `basic` on `app_builder`, or `basic`/`pro` on `custom`) on any launch
surface, pressing a Save button. The Run side of the same surfaces is [ISS-472](20260829-0110-ISS-472.md) (IdeaInputPage),
[ISS-474](20260829-0112-ISS-474.md) (ComposerPage) and [FIX-497](20260829-0242-FIX-497.md) (LaunchWizard, fixed).

## Why the root cause implies it (each step read)

The root cause of [ISS-472](20260829-0110-ISS-472.md) is that the client never consults the tier on these surfaces. A launch is not
the only action the backend gates by tier; saving is gated by the same predicate, so the same missing check shows up on every Save
control too.

- Backend: `user_workflows.py:703-707` in `create_user_workflow` (`:668`): `allowed, reason = can_run_pipeline(effective_tier(current_user, principal), body.base_pipeline_type)`
  then `raise HTTPException(status_code=status.HTTP_403_FORBIDDEN, detail=reason)`. Its own comment: "Entitlement gate (custom needs enterprise) — fail-fast before insert."
- IdeaInputPage "Save workflow": `IdeaInputPage.tsx:1982-1987`, `disabled={pipelineAgents.length === 0 || (isMigrationMeta && !migrationChoice)}` (`:1983`), no tier term.
  Its handler `handleSaveWorkflow` (`:1692`) closes the name modal first (`setShowSaveModal(false)`, `:1693`), then `createUserWorkflow(jwt, { ..., base_pipeline_type: effectiveType, ... })` (`:1710`).
  A rejection lands in `catch` as `setSaveError((e as Error)?.message ?? "Failed to save workflow.")` (`:1729`), rendered as small red text under the card (`:2037-2039`).
- IdeaInputPage "Save as my version": `:1997-2002`, same `disabled` (`:1998`). `handleSaveAsOverride` (`:1773`) calls `createUserWorkflow` with `base_pipeline_type: workflowId` (`:1789`), the same endpoint and gate; error at `:1816`.
- ComposerPage: `handleSave` (`ComposerPage.tsx:832`) saves with `base_pipeline_type: "custom"` (a literal, `:931`), which only the `enterprise` set contains (`backend/app/core/entitlements.py:67`);
  the button label is `builtinCanvasType ? "Save as copy" : "Save workflow"` (`:1418`). The file has zero tier references (`evidence/qa-kb-052/analysis-proof.out.txt` section 1).
- LaunchWizard (after [FIX-497](20260829-0242-FIX-497.md)): `locked` is applied to Continue (`:1437`) and `handleLaunch` (`:1001`) but not to Save workflow (`disabled={rosterSettling || pipelineAgents.length === 0}`, `:1410`)
  or Save as my version (`:1432`); both call `createUserWorkflow` (`:936`, `:970`). FIX-497 recorded this as "Also noted, not changed ... no card covers them"; it assumed the save "creates a catalogue row rather than a run" and so is harmless, but the endpoint gates the same predicate.

## Expected vs actual

- **Expected:** on a locked surface the Save controls are disabled (or absent) with the same upgrade copy as the Run control, because the save cannot succeed.
- **Actual (derived):** the control is live, the user types a name in the modal, and only then does the backend refuse; the message is the backend's
  "This pipeline requires Pro or higher. Upgrade your plan to unlock it." (`entitlements.py:117-123`) shown as a small red line. For ComposerPage on `/workflows/new` a
  `basic` or `pro` account composes a whole workflow whose Save and Run once both cannot succeed.

## Why this is INFERRED, and what settles it

The gate, the buttons and the call chain are read, and the "enabled" half is observed: the validator's captures for QA-KB-052 (`evidence/qa-kb-052/01`-`04-validate-attempt*-basic-*.png`, filed as `basic` on `/create/app`)
show "Save workflow" and "Save as my version" both enabled beside the Run button. Not observed: the exact text a locked account sees after pressing Save. Settle it by signing in as `basic@velocity.ai`
(`velocity.json`), opening `/create/app`, pressing "Save workflow" and naming it.

## Where the fix belongs

With the Run fix of [ISS-472](20260829-0110-ISS-472.md): the same `locked` value that disables Run also disables Save on that surface, so one predicate per surface covers both.
`LaunchWizard` needs the same one-line addition (`disabled={... || locked}` on its two Save buttons) because FIX-497 left them out.

## For the test-writer

Offline: with the same store the Run test uses (`auth.user.tier = "basic"`, `workflowType="app_builder"`, a seeded `app_builder` agent), assert "Save workflow" and "Save as my version" are disabled.
It fails today. Control: `tier: "pro"` leaves both enabled.
