## Source

Derived (analyzer pass) from the root-cause investigation of `BUG-20260828-010600-workflows-id-run`,
recorded on [ISS-273](20260828-1653-ISS-273.md). **INFERRED** — not independently reproduced in a
browser; filed from source reading alone (comparing the catch clause against its two working
siblings in the same file). See "What would settle it" below.

## This sibling

`frontend/src/app/[...view]/page.tsx`'s `/workflows/{id}/run` cold-mount catch (`:3692-3707`) reads:

```
if (err instanceof ApiError && err.status === 401) {
  handleSessionExpiry();
  return;
}
setWorkflowRunFailed(true);
```

Every OTHER error — a 500, a timeout, a network blip — falls through the 401 check and hits the
bare `setWorkflowRunFailed(true)`. Compare its two siblings in the same file, both narrowed to
treat ONLY 403/404 as an identity failure:

- `workflowEditAccessDenied` (`:3518`): `if (err instanceof ApiError && (err.status === 403 ||
  err.status === 404)) { setWorkflowEditAccessDenied(true); }` — anything else just logs (`:3508`)
  and leaves the Composer's existing state alone.
- `workflowDetailFailed` (`:3568`), with an explicit comment at `:3560-3567` documenting the
  narrowing was itself a prior audit fix ("F7 ... narrowed to match the run-detail and
  /workflows/{id}/edit catch blocks above — only a genuine 403 ... or 404 ... is an ownership
  failure. Every other error ... now falls through to the log-and-continue behavior ... instead of
  unconditionally rendering not-found for a transient failure on a legitimately-owned, existing
  workflow").

`workflowRunFailed` has no such narrowing — it is the one identity-style flag in this file that was
never brought in line with the F7 audit fix its two siblings already carry.

## Two distinct consequences

1. **Today:** a transient 5xx/network error while cold-mounting a VALID `/workflows/{id}/run`
   already produces ISS-273's exact wrong-Dashboard-fallback symptom, not just a genuine 404/
   malformed id — the current code cannot tell the two apart.
2. **Post-fix risk:** if ISS-273 is fixed by routing `workflowRunFailed` into `notFound()` without
   ALSO narrowing this catch to 403/404 (mirroring `workflowEditAccessDenied`/`workflowDetailFailed`),
   a transient failure on a real, owned workflow would newly render a PERMANENT not-found page
   instead of today's (wrong, but at least not identity-denying) Dashboard fallback — a regression
   introduced by the fix itself. The F7 comment at `:3560-3567` documents exactly why the other two
   flags were narrowed; the same reasoning applies here and belongs in the same change, not a
   second pass.

## Expected vs actual (INFERRED, needs live reproduction)

**Expected:** only a 403/404 on `GET /api/user-workflows/{id}` is treated as "this workflow does not
exist / is not yours"; a 5xx or network failure logs and lets the panel retry or show a
transient-error state, same as `workflowEditAccessDenied`/`workflowDetailFailed` already do.

**Actual (inferred):** any non-401 error — including a transient 500 or network blip on a real,
owned workflow — is indistinguishable from a genuine 404 in this catch, and today produces the same
wrong Dashboard-under-bogus-URL fallback ISS-273 describes.

## What would settle it

Reproduce live: intercept `GET /api/user-workflows/{id}` for a REAL saved workflow id and force a
500 (e.g. Playwright `page.route` fulfilling status 500), cold-navigate to that workflow's
`/workflows/{id}/run`, and confirm it renders the Dashboard fallback (today) or, after a naive
ISS-273 fix, an incorrect permanent not-found — rather than an honest transient-error/retry state.

## Fix

Same location and same change as ISS-273: narrow `frontend/src/app/[...view]/page.tsx:3692-3707`'s
catch to `err instanceof ApiError && (err.status === 403 || err.status === 404)` before setting
`workflowRunFailed`, exactly matching `workflowEditAccessDenied`'s (`:3518`) and
`workflowDetailFailed`'s (`:3568`) narrowing, and let every other error fall through to
log-and-continue. This belongs in the SAME catch block ISS-273's fix already touches — not a second
call site.

## Resolution

Resolved by [FIX-355](20260828-2358-FIX-355.md): the catch is now narrowed to
`err instanceof ApiError && (err.status === 403 || err.status === 404)`, matching its two
siblings, and shipped in the same change as ISS-273's `notFound()` gate so the post-fix
regression this card predicted never existed. **Verification stays `pending` on purpose** —
no forced-5xx reproduction was run, so the transient-error branch is unobserved.
