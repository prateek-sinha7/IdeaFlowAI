# FIX-755

Fixes QA-KB-072 (register `LEDGER.md`, detail `BUGS.md#qa-kb-072`). Resolves the root card
[ISS-899](20261001-2129-ISS-899.md). **This is a test-only change, made because the card says the test's expected
behaviour was misstated, not because the test was red.** ISS-899's analysis CONFIRMED the test is stale: it was
written (`1e329e47b`) on a branch without the redo refusal (`835793a99`, [FIX-500](20260831-1644-FIX-500.md)),
passes in the tree it was written in, and has failed since the two lines merged. The engine is right; no
application file was edited.

## What was wrong

`cd backend && ./.venv/bin/python -m pytest tests/agents/test_declared_gate_redo.py` reported
`test_non_redoable_declared_gate_unaffected_by_redo_action` failing after about 63 s: `_drive`'s
`asyncio.wait_for(gen.__anext__(), timeout=_EVENT_TIMEOUT_S)` expired while the engine sat at `await event.wait()`
in `_run_review_gate`.

## Root cause (ISS-899's analysis, re-checked on this tree before editing)

- The test's step has `redoable=False`. Its `_on_ready` answered the only `review_gate_ready` with
  `set_review_response(gate_key, approved=False, action="redo", instructions="ignored")` and nothing else.
- `backend/agents/execution_engine/engine.py:12530-12538` (anchor on the text, the file moves): `if not redoable:`
  logs `"Review gate redo REFUSED: pipeline=%s agent=%s — this firing published redoable=False; gate stays open
  (ISS-090)"`, then `event.clear()` and `continue`. That keep-waiting degrade is deliberate (approving would fail
  open on a HITL gate, rejecting would cancel the user's run). Nothing else answered the gate, so the drive timed
  out.
- The test was written against the pre-FIX-500 route, where `HumanGate` consumed the `_gate_redo` and ended the
  drive. Its docstring and the "consumed, not honoured" comment narrated that route.

Blast radius re-grepped before the edit (`grep -rn 'action="redo"' backend/tests`, 10 lines on this tree): the
other engine-driving tests that post a redo (`test_redoable_eligibility_fence.py:130`,
`test_gate_redo_enforcement.py:153`) already approve after the re-arm; the rest are store, REST and router level
with no engine loop. One test was broken, as the card said.

## What changed, and why there

`backend/tests/agents/test_declared_gate_redo.py` only, in the shape ISS-899's scratch run verified:

1. New module helper `_wait_until(pred, timeout=5.0)`, a copy of `test_redoable_eligibility_fence.py:104-111`
   (copied, not imported, as the sibling tests each do).
2. `test_non_redoable_declared_gate_unaffected_by_redo_action`: `_on_ready` still posts the redo, then starts a
   concurrent task that waits for `store.review_event_pending(gate_key)` (armed and unset, which only the
   refusal's `event.clear()` produces after the redo set the event), records `rearmed`, and approves. The task is
   awaited in a `finally` around `_drive`, so a failed drive cannot leak it.
3. New assertions: `rearmed`, `"review_gate_approved" in types`, `"pipeline_complete" in types`. Kept: the
   `redoable is False` check, `agent_start == 1`, `len(readies) == 1`.
4. Docstring and trailing comment reworded to the refusal route.

Why a concurrent task and not the bug report's sketch (poll inside `_on_ready`): the engine generator is suspended
at its `yield` while `_on_ready` runs, so an inline poll never sees the re-arm (hangs), and an inline approve
overwrites the redo in its one slot before the engine reads it (passes without the refusal ever running). ISS-899
ran all three variants (`evidence/qa-kb-072/06-analyze-scratch-variants-output.txt`).

The `@pytest.mark.xfail(reason="ISS-899 unfixed", strict=True)` marker the test-writer added is left in place;
the 6-verifier removes it.
