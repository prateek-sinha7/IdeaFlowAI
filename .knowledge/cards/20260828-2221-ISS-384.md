## What is broken

Deferred finding from [FIX-338](20260828-2221-FIX-338.md) (the
[ISS-228](20260828-1758-ISS-228.md) effect-race fix). Confirmed by source read plus a live
`--runxfail` run, not inferred.

`LaunchWizard` restores the saved row's identity from the `{mode}.draft` payload —
`setUserWorkflowId(d.id)` / `setSavedName(d.name)` / `setSavedDescription(d.description)`,
`frontend/src/components/workflow/LaunchWizard.tsx:311-313` — but `savedName` and
`savedDescription` are then consumed in exactly one place: as props on `<AgentsPopup>`
(`:1168-1169`), a modal whose `isOpen={showAgents}` is `false` until the user clicks "Advanced".
The page header renders `cfg.eyebrow` and `cfg.title` unconditionally (`:826-833`) — for the
`prototype` mode, the literal strings `"NEW PROTOTYPE"` and `"Configure your prototype"` from
`MODE_CONFIG` (`:100`).

Consequence: opening a saved workflow's own launch panel (`/workflows/{id}/run`, or click-through
Run) is visually identical to starting a brand-new one. The observed body text of the panel for
the seeded `"My prototype"` override (`656ca387-e69c-474d-b7ff-5fd9eb017cc0`) is, in full:

```
NEW PROTOTYPE / Configure your prototype / Describe what you're building / + Attach file /
Voice / Advanced / 2 agents / Template / Design System / Discovery / ... / Review gates /
1 agent pause for review / Add a brief / Save workflow / Save as my version / Continue
```

Nothing in it names the workflow the user opened.

## Why this is a distinct defect from ISS-228

[ISS-228](20260828-1758-ISS-228.md)'s **Expected** asks for the panel to render "'My prototype''s
name, description, and saved template/agent configuration", but its **Root cause** section
analyses only the agent-roster half: a same-commit effect-ordering race on `pipelineAgents`
(`LaunchWizard.tsx:335-338` over `:278-324`), fixed by [FIX-338](20260828-2221-FIX-338.md).

The missing name is not produced by that race and is not repaired by fixing it. It is a
presentation gap that predates the race and reproduces on the happy path too: even with
`libraryAgents` already populated at mount — no race possible — the header still says
"NEW PROTOTYPE / Configure your prototype", because no code path renders `savedName` outside the
modal. Verified after the FIX-338 change landed: both scenarios in
`tests/integration/e2e/suites/05_saved_workflows/test_iss228_launch_panel_override_binding.py`
still fail on `assert 'My prototype' in body`, and on nothing else.

## Disposition — needs a product decision, not just a patch

The shipped test asserts `PROTO_NAME in document.body.innerText` **while also** asserting
`"Configure your prototype"` stays visible (`:46`), so the name has to appear *in addition to* the
existing title, not replace it. Where it goes, and whether the description joins it, is a UI
decision no card covers, which is why FIX-338 did not invent one. Two ways to close this:

1. Render the saved identity in the header — e.g. `savedName` as a second line under the h1.
   Note the eyebrow slot is `uppercase`-transformed and `innerText` applies `text-transform`, so
   putting the name there returns `"MY PROTOTYPE"` and would not satisfy the test as written.
2. Decide the panel is intentionally anonymous, amend [ISS-228](20260828-1758-ISS-228.md)'s
   Expected, and have the test retargeted at the agent roster instead of the name.

## Note for whoever retargets the test

A roster assertion on THIS fixture will not discriminate fixed from unfixed: the seeded
`"My prototype"` row carries `overrides_pipeline_type: "prototype"`, so the spec-016 override
effect (`LaunchWizard.tsx:357-410`, `getWorkflowDetail(token, pipeline)` →
`setPipelineAgents(proj.agents)`) re-applies the correct roster asynchronously after the race
would have clobbered it. That masking is consistent with the test-writer's live finding recorded
on [ISS-284](20260828-1906-ISS-284.md) (roster and save both correct after a cold mount). A
discriminating fixture is a plain saved workflow that is NOT an enabled override of its built-in.
