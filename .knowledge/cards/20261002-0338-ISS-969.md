# ISS-969

**INFERRED, not reproduced.** Derived while analysing QA-KB-052 ([ISS-472](20260829-0110-ISS-472.md)). The code path is read end to end;
what nobody has done is drive it and look at the screen that results. An unreproduced sibling is a lead, not a defect.

Line numbers are the working tree on 2026-10-02 (HEAD `024c03ef8`); `page.tsx` and `DashboardLayout.tsx` carry uncommitted edits from
other work, so they can sit a few lines off HEAD.

## Condition

Any launch that goes through `onStartPipeline` and is refused by `POST /api/runs`. The case that matters here is the one
[ISS-472](20260829-0110-ISS-472.md) leaves open: a tier that does not include the pipeline (`403`, code `tier_not_entitled`). The same
path also swallows every other non-503 refusal (`400 empty_brief`, `400 invalid_agent_ids` as in [ISS-687](20260918-ISS-687.md), a mid-session downgrade).

## Why the root cause implies it (each step read)

[ISS-472](20260829-0110-ISS-472.md)'s root cause is that, on the Input panel, the backend is the only thing that enforces the tier. That
makes the *presentation of the backend's refusal* the whole of the user's feedback, and it has none:

1. `IdeaInputPage.tsx:1676-1681` calls `onRun(...)`, which is `handleRunPipeline` (`DashboardLayout.tsx:1759`). Its second statement is
   `setMainView("execution")` (`:1761`), **before** the POST is even sent (`onStartPipeline` at `:1816`). `IdeaInputPage` unmounts, so the typed brief goes with it.
2. `page.tsx:4256` is the `onStartPipeline` the layout was given. It calls `startPipeline(...)` (`:4333`), which returns `runConnection.sendCommand(null, payload)` (`useWorkflow.ts:128`).
3. `RunConnectionProvider.tsx:520-529`: on a non-2xx it reads the body and `throw new ApiError(res.status, detail)`. For a tier refusal the body is the `_reject` triple
   `{"error": <upgrade text>, "code": "tier_not_entitled", "recoverable": false}` (`run_commands.py:2534-2557`, raised at `:3510` through `_require_tier_entitlement`, `:2558-2601`).
4. `ApiError`'s constructor (`api.ts:277-311`) publishes to listeners in exactly two cases: `503` + a capacity detail (the `ServiceBusyProvider` modal) and `403` + admin-MFA detail. A
   `tier_not_entitled` 403 matches neither.
5. `page.tsx:4400-4413`, the `.catch`: `launchPendingRef.current = false; resetPipeline();` and `if (process.env.NODE_ENV !== "production") { console.error("Pipeline launch failed:", err); }`.
   Its own comment says the only rejection with a UI is the 503. In production this handler is silent.
6. No frontend file names the code: `grep -rn "tier_not_entitled|pipeline_not_entitled" frontend/src` (non-test) returns nothing (`evidence/qa-kb-052/analysis-proof.out.txt` section 5).

## Blast radius (grepped)

Every launch seam shares that one `.catch`. `grep -n "onStartPipeline(" DashboardLayout.tsx` finds 17 call sites: the four revision handlers (`:1217, :1229, :1249, :1261`) and their lane twins
(`:3067, :3077, :3087, :3097`), the staged wizard/deck launches (`:1389, :1457, :1522`), `handleRunPipeline` (`:1816`, the Input panel), chaining (`:2003, :2096`), the clarify-round relaunches
(`:2186, :2226`) and `ComposerPage`'s Run once (`:3227`). Each of those is refused silently the same way.

## Expected vs actual

- **Expected:** a refused launch shows the reason the backend gave ("This pipeline requires Pro or higher. Upgrade your plan to unlock it.") and the user keeps the form and the brief they wrote.
- **Actual (derived):** the screen changes to the execution view, nothing starts, the pipeline state is reset, and no message is shown. In a production build there is not even a console line.

## Why this is INFERRED, and what settles it

Read, not observed: what the execution view renders when `pipelineState` is reset with no run id (empty lane, or something that bounces back). Settle it by stubbing `POST /api/runs` to return
`403 {"detail": {"error": "...", "code": "tier_not_entitled", "recoverable": false}}` with Playwright `page.route`, typing a brief on any Input panel and pressing Run.

## Where the fix belongs

At the one seam, not per caller: either the `.catch` at `page.tsx:4400-4413` (all 17 sites route through it) or a third listener in the `ApiError` constructor beside the capacity and admin-MFA ones, which is the pattern
the codebase already uses for "one seam, every call site" (see the comment above `onAdminMfaRequired`, `api.ts:258-267`). Present `ApiError.message` (already extracted from `detail` by `errorMessageFromDetail`) and, for the
panels that unmount on launch, return to the form rather than leaving the user on the execution view. A client-side lock ([ISS-472](20260829-0110-ISS-472.md)) removes the tier trigger on the Input panel but not the generic silence.

## For the test-writer

Playwright with `page.route("**/api/runs", route => route.fulfill(status=403, json=...))`, signed in as any tier: press Run and assert a visible message that contains the backend text. It fails today.

## Analysis update 2026-10-09 (QA-KB-106, root [ISS-1137](20261009-0304-ISS-1137.md))

Re-read against the current tree, so the next reader does not repeat the derivation:

- The `.catch` is now at `page.tsx:4454-4467` (this card cites `:4400-4413`). The 17 `onStartPipeline(` sites in `DashboardLayout.tsx` are now at `:1242, :1254, :1274, :1286, :1414, :1482, :1547, :1841, :2028, :2121, :2211, :2251, :3085, :3095, :3105, :3115, :3246`.
- "Present `ApiError.message`" (Where the fix belongs) would print raw JSON: `errorMessageFromDetail` returns null for an object detail (`api.ts:169-176`), so for a `_reject` body `message` is `JSON.stringify(detail)`. The user-facing text is `ApiError.detail.error`.
- The predicted Input-panel screen ("moved off the form onto the execution view") is doubtful: `handleRunPipeline` does set `mainView="execution"` (`DashboardLayout.tsx:1786`), but the URL-sync effect (`:603-607`) returns it to `"input"` because the URL is still `/create/<type>`. See [ISS-1138](20261009-0304-ISS-1138.md).
- What this card did not cover is why Run once stays disabled afterwards: the FIX-614 submitting latch has no release on a refused launch. See [ISS-1137](20261009-0304-ISS-1137.md).

## Resolved 2026-10-09 by [FIX-773](20261009-0952-FIX-773.md)

The `.catch` this card names is now the one place that reports a refused launch, for all 17 call sites. It shows
`launchRefusalMessage(err)`, which is `detail.error` and not the raw-JSON `ApiError.message`, in a layout banner. It resolves `null`,
so the Composer and Input panels release their Run latch. On `/create/user-stories` a refusal leaves the user on the form with the
brief intact (`evidence/qa-kb-106/fix-06-stubbed-latch-check.txt`), so the predicted move to the execution view does not happen.
