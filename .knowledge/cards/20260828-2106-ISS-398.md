## What happened (derived, not yet independently reproduced)

Sibling of [ISS-292](20260828-1918-ISS-292.md) (root: `BUG-20260828-031200-settings-ai-model`),
filed by inference from the same root cause: **this codebase has no model-tier entitlement
concept anywhere** — no analog of `entitlements.py::TIER_PIPELINES`/`can_run_pipeline` scoped to
models. `_validate_model_overrides` (`backend/app/api/run_engine.py:547-607`) is the "security
chokepoint for MODEL-03" per its own docstring — explicitly written to guard against a
"cost-abuse" vector — yet it checks a submitted `{agent_id: model_id}` override map against
exactly two allow-lists, and neither is tier-scoped:

```python
# run_engine.py:588-606
allowed_model_ids = set(ModelCatalog().ids())          # the FULL 9-model catalog, no tier filter
for agent_id, model_id in model_overrides.items():
    ...
    if agent_id not in run_agent_ids:
        return f"...not part of this run's agents"
    if model_id not in allowed_model_ids:
        return f"...not an allowed model"
return None
```

The function signature (`_validate_model_overrides(model_overrides: dict, run_agent_ids:
set[str])`, line 547-549) never takes a user or tier argument at all, so it structurally cannot
consult `user.tier` — the same class of gap as `settings.py`'s `update_preferences`, in a
different function, guarding a different (per-agent, not account-wide) model-selection surface.

This one function is called from three live, non-test call sites, all of which persist or launch
with an unvalidated-by-tier `model_overrides` map:

- `backend/app/api/run_commands.py:2900` — the actual run-launch path (`_override_error =
  _validate_model_overrides(model_overrides, {spec.id for spec in agents})`).
- `backend/app/api/user_workflows.py:566` — saving a new composed workflow (`err =
  _validate_model_overrides(body.model_overrides or {}, set(body.agent_ids))`), whose own comment
  reads "model_overrides — same two-check allow-list as launch."
- `backend/app/api/user_workflows.py:807` — updating (`PATCH`) an existing saved workflow's
  `model_overrides` (`err = _validate_model_overrides(body.model_overrides, current_agent_ids)`).

If any of these are reachable from a per-agent model picker in the composer/canvas UI (the
architecture card and `FIX-019`/`ISS-168` both reference a "Canvas picker" for per-agent model
selection, though this card does not trace that frontend component), a basic-tier account could
set `model_overrides: {"<agent-id>": "eu.anthropic.claude-opus-4-6-v1"}` on a saved workflow or a
direct launch payload and have it accepted identically to any other model choice — the same
outcome as [ISS-292](20260828-1918-ISS-292.md), reached through a different door.

## Why this is INFERRED, not CONFIRMED

The analyzer read `_validate_model_overrides`'s implementation and all three call sites directly
(file:line evidence above) and confirmed the function has no tier parameter and performs no tier
check — that mechanism is solid. What is **not yet done**: driving this end-to-end as a
basic-tier account through either the real composer UI or a direct `PUT
/api/user-workflows/{id}`-style request with a premium `model_overrides` entry, to confirm the
request is actually accepted with 200/202 rather than rejected by some OTHER guard this card's
author did not read (e.g. `_compile_selections_trust_user`, the adjacent EMP-02 check at
`user_workflows.py:570-575`, governs capability *trust*, not model *tier*, and was read far
enough to rule out as the same check — but the full request path was not driven live).

## What would settle it

1. As `qa-basic@flowinqa.com`, save or update a custom workflow with `model_overrides` mapping
   one of its agent ids to `eu.anthropic.claude-opus-4-6-v1` (or `-4-5-...`) via the composer UI
   or the underlying `POST`/`PATCH /api/user-workflows` request, and confirm it is accepted
   (200/201) rather than rejected.
2. Launch that saved workflow (or launch directly with `model_overrides` in the run payload) as
   the same basic-tier account and confirm `run_commands.py:2900`'s `_validate_model_overrides`
   call does not reject it, and that the run actually proceeds against the premium model (mirrors
   the confirmed `run_commands.py` `preferred_model` consumption chain documented on ISS-292's
   root bug).

## Fix — same shared location as the root cause

Per [ISS-292](20260828-1918-ISS-292.md)'s proposed fix: a tier-scoped model allow-list belongs
next to `TIER_PIPELINES` in `backend/app/core/entitlements.py` (e.g. `TIER_MODEL_COST_CLASSES:
dict[Tier, set[str]]` keyed off `ModelEntry.cost_class`, mirroring how `TIER_PIPELINES` is keyed
off pipeline type). `_validate_model_overrides` should take the requesting user's tier as a
parameter and consult that table for EVERY `model_id` in the override map, not just
`ModelCatalog.ids()` membership — the same helper `settings.py`'s `update_preferences` would call.
One shared entitlement check, two call sites (`settings.py` and `run_engine.py`), all three
downstream routes (`run_commands.py`, `user_workflows.py` x2) inherit the fix automatically since
they all route through `_validate_model_overrides`.

## Analysis (QA-KB-017 analyzer, 2026-10-01)

**Verdict.** The root cause stated above is CONFIRMED and its meaning stands: no ingress validator for a user-supplied model id takes the caller's tier, and the helper written for it ([FIX-361](20260829-0029-FIX-361.md), `backend/app/core/entitlements.py:127-167`) is wired to the settings page only. What the first pass could not see is how many doors a model id enters through and which of them the product UI really uses. The "Fix" section above (one signature change, everything inherits) is incomplete; this section supersedes it where the two differ. Line numbers in the older text predate later edits: `_validate_model_overrides` is now `run_engine.py:546-606`, its call sites are `run_commands.py:3729`, `user_workflows.py:729` and `:972`, and `TIER_MODEL_COST_CLASSES` is no longer a proposal, it exists (`entitlements.py:136-141`). Everything below is current for branch `feat/user-stories-v2` at HEAD `024c03ef8` plus the uncommitted tree.

### Root cause (CONFIRMED)

- `backend/app/api/run_engine.py:546-606` and `backend/app/api/user_workflows.py:348-383` are two textual copies of `_validate_model_overrides(model_overrides, run_agent_ids)`. Neither has a tier parameter and neither imports `can_use_model`. Their only model check is membership of `ModelCatalog().ids()` (`run_engine.py:589,601`; `user_workflows.py:366,378`).
- `can_use_model` and `TIER_MODEL_COST_CLASSES` exist (basic = cheap and standard, hexaware/pro/enterprise = all three, `entitlements.py:136-167`) but are called from `settings.py` only (`:341`, `:374`, `:388`).
- Executed offline against the real functions (scratch probe, no database, no network): `can_use_model("basic", "eu.anthropic.claude-opus-4-6-v1")` is `(False, "This model requires Pro or higher. Upgrade your plan to unlock it.")`, and the same for `global.openai.gpt-5.6-sol` (also `cost_class="premium"`); hexaware, pro and enterprise are allowed. Both validator copies, called with the Opus id and a valid agent, return `None` (accept).

### What the UI actually sends

The Canvas never emits `model_overrides`. The Model lever (`frontend/src/components/workflow/composer/CanvasConfigRail.tsx:1035-1066`, whole catalog, no tier filter) writes `selections[id].model` (`AgentsPopup.tsx:2737-2744`; `IdeaInputPage.tsx:1624` on a run). On a full-manifest save it is serialised into `manifest.steps[i].model` (`frontend/src/store/api/userWorkflows.ts:359-368`; `ComposerPage.tsx:901-919`; the built-in "save my version" at `IdeaInputPage.tsx:1769-1774` and `LaunchWizard.tsx:972`) and on an inline "Run once" (`ComposerPage.tsx:1140`). `model_overrides` is emitted only by `AgentModelPicker`, which no component mounts any more, and by the replay of old saved rows. So against `/canvas`, the doors the product actually uses are the selections and manifest rows of the table; `model_overrides` is the public API contract the validator reproduced.

### Where the fix belongs

1. Policy stays in `entitlements.py` (`can_use_model`). Nothing new is needed there beyond an optional convenience such as `first_model_denial(tier, model_ids)`.
2. One app-layer gate that every door calls with `effective_tier(user, principal)`. `_require_tier_entitlement` (`run_commands.py:2555-2598`) is the precedent and its docstring forbids reading the projection ([ADR-0013](20260916-ADR-0013.md)). It has to see three shapes: `model_overrides.values()`, `selections[*].model`, and `manifest.steps[**].model.model` plus `.fallback[*]`, recursing `subagents.steps`.
3. Three call sites and nothing else. Create (`user_workflows.py`, next to the `can_run_pipeline` gate at `:702-706`). PATCH (`:967-977`; switch the dependency from `get_current_user` at `:937` to `get_current_principal` as create does at `:673`). Launch (`run_commands.py`, at the model_overrides block `:3722-3740`, outside the `launch_source is not USER_WORKFLOW_MANIFEST` guard so case 3 is covered). At launch it reads user-authored sources only: the body maps, the inline manifest or the saved row's `manifest_json`, and an enabled override's steps (`_ov_steps`, `:3627`). It never walks the compiled plan of a file-backed built-in, whose manifest and `AGENT.md` may declare premium models for every tier on purpose.
4. Denial shape: 403 with `can_use_model`'s reason as `detail` at save, and `_reject("tier_not_entitled", reason, http_status=403)` at launch. That is the shape of the existing tier gates (`user_workflows.py:706`, `run_commands.py:2594`) and of FIX-361's locked constraint (tier is 403, catalog is 422). Pre-mint: no row, no WorkflowRun, no engine call.
5. Not here: `ModelResolver`, the compiler and `selections.py` (all under `agents.*`, which import-linter forbids from importing `app`, `backend/pyproject.toml:383-393`), and not the frontend.
6. Separate hygiene: collapse the two `_validate_model_overrides` copies into one. `user_workflows.py` can import it from `run_engine` (module-level imports are light, `run_engine.py:18-35`; `run_commands.py` already imports it, `:101`). The `user_workflows.py` docstring (`:15-23`) promises "a saved row can never carry something launch would reject", which only holds while the two cannot drift. Not required if the gate lives in the shared helper of point 2; required if the tier check were added inside the validators instead.

### Verdict on the agreed minimal fix (BUGS.md Notes)

- Accept as the door-1 part: tier into both validators, `effective_tier(...)` at the call sites, PATCH moved to `get_current_principal`, tests updated. The existing unit tests call the validator in the two-argument form (`backend/tests/unit/app/test_run_pipeline_validation.py:558-663`, 12 tests in `TestModelOverrideValidation`, green today), so a signature change must update them. Make any new tier parameter required, with no default: a default lets a missed caller skip the gate silently.
- Overrule as sufficient. It leaves the selections door, the manifest door and the case 3 launch open, which are the doors the Canvas uses; a verifier driving `/workflows/user_stories/canvas` as basic would still see Save succeed.
- Overrule the status shape. Returning the reason as a string yields 422 on save and 400 `invalid_model_override` on launch; the tier decisions elsewhere are 403 (see point 4).
- Overrule the caveat. "Launches from saved workflows skip the validator, so the save and PATCH checks cover that path" is wrong in two ways: save never inspects manifest step models, and in case 3 the saved row's `model_overrides` is not what runs, the request body's map is (only case 2 copies the row's map, `run_commands.py:3319-3320`). The downgrade-after-save edge disappears if the launch gate reads stored manifests.

### Policy note: DECIDE-02 (Phase 22) versus FIX-361

The frozen `.planning/` archive records "premium models selectable by ALL tiers (no per-tier premium gating)" as MODEL-05 and DECIDE-02, decided in Phase 22 on 2026-06-14 (`.planning/REQUIREMENTS.md:64`, `:186`; `22-CONTEXT.md:88`). The cards do not carry that decision; this note uses the archive for it, and the archive is the older, unmaintained source. [FIX-361](20260829-0029-FIX-361.md) (2026-08-29, active) and [BUG-076](20260829-1508-BUG-076.md) (done) later introduced the tier table that holds basic off premium without mentioning DECIDE-02, and `can_use_model`'s own docstring names `run_engine.py`'s catalog check as an intended caller (`entitlements.py:147-150`). This analysis follows the later, in-code, `.knowledge`-recorded policy together with this bug's own Expected ("reject premium models for basic-tier accounts"). If the owner in fact still wants DECIDE-02 for per-agent models, this card and its siblings are void and FIX-361 is the outlier; that is the one question that would change this analysis.

Artifacts that still assert DECIDE-02 and should be reconciled in comments only: `AgentModelPicker.tsx:15-21,77-83`, `AgentsPopup.tsx:1655,2217`. The tests that cite it (`frontend/src/components/workflow/AgentModelPicker.test.tsx:102-110`, `frontend/e2e/tests/ts-e.model-picker.spec.ts:34-35,106-113`) assert only that the picker OFFERS the whole catalog, so a server-side gate does not break them; do not edit them to make a fix pass. The picker will keep offering models the server then refuses; a lock or disabled affordance is the [ISS-430](20260829-0029-ISS-430.md) pattern and is deliberately not part of this security fix.

### Invariants a fix must respect

- Tier comes from `effective_tier(user, principal)`, never `User.tier` (ADR-0013 locked constraint; see [ISS-937](20261001-2231-ISS-937.md) for the one place that already violates it).
- FIX-361's locked constraints: entitlement keys off `ModelEntry.cost_class`, never `user_allowed` (the CAP-03 trust flag); catalog membership stays the caller's 422, tier is 403.
- import-linter: `agents.workflows`, `agents.capabilities` and `agents.runtime` must not import `app` (`backend/pyproject.toml:383-409`); the kernel engine must not import `app.api` (`:358-370`). The gate is app-layer or an injected predicate, never a kernel import.
- SC-001 / INV-1: no tier or pipeline-name branch in the kernel.
- INV-3 parity: enterprise and pro callers, and basic callers using cheap or standard models, behave byte-identically; file-backed built-ins are never gated.
- Save equals launch (`user_workflows.py:15-23`): whatever save rejects, launch rejects, and vice versa.
