## What happened (derived, not yet independently reproduced)

Sibling of [ISS-292](20260828-1918-ISS-292.md) (root: `BUG-20260828-031200-settings-ai-model`),
filed by inference from the same root cause: **this codebase has no model-tier entitlement
concept anywhere** — no analog of `entitlements.py::TIER_PIPELINES`/`can_run_pipeline` scoped to
models. `_validate_model_overrides` (`backend/app/api/run_engine.py:547-607`) is the "security
chokepoint for MODEL-03" per its own docstring — explicitly written to guard against a
"cost-abuse" vector — yet it checks a submitted `{agent_id: model_id}` override map against
exactly two allow-lists, and neither is tier-scoped:

```python
# run_engine.py:588-606
allowed_model_ids = set(ModelCatalog().ids())          # the FULL 9-model catalog, no tier filter
for agent_id, model_id in model_overrides.items():
    ...
    if agent_id not in run_agent_ids:
        return f"...not part of this run's agents"
    if model_id not in allowed_model_ids:
        return f"...not an allowed model"
return None
```

The function signature (`_validate_model_overrides(model_overrides: dict, run_agent_ids:
set[str])`, line 547-549) never takes a user or tier argument at all, so it structurally cannot
consult `user.tier` — the same class of gap as `settings.py`'s `update_preferences`, in a
different function, guarding a different (per-agent, not account-wide) model-selection surface.

This one function is called from three live, non-test call sites, all of which persist or launch
with an unvalidated-by-tier `model_overrides` map:

- `backend/app/api/run_commands.py:2900` — the actual run-launch path (`_override_error =
  _validate_model_overrides(model_overrides, {spec.id for spec in agents})`).
- `backend/app/api/user_workflows.py:566` — saving a new composed workflow (`err =
  _validate_model_overrides(body.model_overrides or {}, set(body.agent_ids))`), whose own comment
  reads "model_overrides — same two-check allow-list as launch."
- `backend/app/api/user_workflows.py:807` — updating (`PATCH`) an existing saved workflow's
  `model_overrides` (`err = _validate_model_overrides(body.model_overrides, current_agent_ids)`).

If any of these are reachable from a per-agent model picker in the composer/canvas UI (the
architecture card and `FIX-019`/`ISS-168` both reference a "Canvas picker" for per-agent model
selection, though this card does not trace that frontend component), a basic-tier account could
set `model_overrides: {"<agent-id>": "eu.anthropic.claude-opus-4-6-v1"}` on a saved workflow or a
direct launch payload and have it accepted identically to any other model choice — the same
outcome as [ISS-292](20260828-1918-ISS-292.md), reached through a different door.

## Why this is INFERRED, not CONFIRMED

The analyzer read `_validate_model_overrides`'s implementation and all three call sites directly
(file:line evidence above) and confirmed the function has no tier parameter and performs no tier
check — that mechanism is solid. What is **not yet done**: driving this end-to-end as a
basic-tier account through either the real composer UI or a direct `PUT
/api/user-workflows/{id}`-style request with a premium `model_overrides` entry, to confirm the
request is actually accepted with 200/202 rather than rejected by some OTHER guard this card's
author did not read (e.g. `_compile_selections_trust_user`, the adjacent EMP-02 check at
`user_workflows.py:570-575`, governs capability *trust*, not model *tier*, and was read far
enough to rule out as the same check — but the full request path was not driven live).

## What would settle it

1. As `qa-basic@flowinqa.com`, save or update a custom workflow with `model_overrides` mapping
   one of its agent ids to `eu.anthropic.claude-opus-4-6-v1` (or `-4-5-...`) via the composer UI
   or the underlying `POST`/`PATCH /api/user-workflows` request, and confirm it is accepted
   (200/201) rather than rejected.
2. Launch that saved workflow (or launch directly with `model_overrides` in the run payload) as
   the same basic-tier account and confirm `run_commands.py:2900`'s `_validate_model_overrides`
   call does not reject it, and that the run actually proceeds against the premium model (mirrors
   the confirmed `run_commands.py` `preferred_model` consumption chain documented on ISS-292's
   root bug).

## Fix — same shared location as the root cause

Per [ISS-292](20260828-1918-ISS-292.md)'s proposed fix: a tier-scoped model allow-list belongs
next to `TIER_PIPELINES` in `backend/app/core/entitlements.py` (e.g. `TIER_MODEL_COST_CLASSES:
dict[Tier, set[str]]` keyed off `ModelEntry.cost_class`, mirroring how `TIER_PIPELINES` is keyed
off pipeline type). `_validate_model_overrides` should take the requesting user's tier as a
parameter and consult that table for EVERY `model_id` in the override map, not just
`ModelCatalog.ids()` membership — the same helper `settings.py`'s `update_preferences` would call.
One shared entitlement check, two call sites (`settings.py` and `run_engine.py`), all three
downstream routes (`run_commands.py`, `user_workflows.py` x2) inherit the fix automatically since
they all route through `_validate_model_overrides`.
