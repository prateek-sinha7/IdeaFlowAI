## What was wrong

`BUG-20260827-231407-register`: for an authenticated user, any nonexistent sub-path
under `/register` — `/register/anything`, `/register/abc123xyz`,
`/register/deep/nested/path` — left the address bar on that bogus URL while the full
authenticated dashboard rendered underneath it (heading "What would you like to build
today?", the workflow catalog, "Jump back in" history, Home active in the nav). Stable
across hard reloads, no console error, every dashboard API call 200. Signed-out users
hitting the same URL correctly fell through to `/login?redirect=...`, so the defect was
specific to the authenticated path. Validated 3/3 cold-start by the 2-validator.

## Root cause

`frontend/src/lib/routes.ts:231` (pre-change):

```ts
if (head === 'register') {
  return { screen: 'register' };
}
```

Matched on `segments[0]` alone, with no `segments.length === 1` guard — unlike the
sibling `create` (`:243`), `workflows` (`:264`), `runs`, `library` and `settings`
branches, which all check it. So `parseViewPath(['register', 'anything'])` returned the
same `{ screen: 'register' }` descriptor as the real, exact route.

The exact `/register` path never reaches this code — `frontend/src/app/register/page.tsx`
is a real Next.js route and wins over the `[...view]` catch-all — so `{ screen: 'register' }`
is a descriptor **nothing renders**: `frontend/src/app/[...view]/page.tsx` has zero
branches testing `parsedView.screen === "register"` (grep-confirmed), and
`initialMainViewFor` (`page.tsx:107-174`) has no `case "register":`, falling to
`default: return undefined`. That `undefined` becomes the `initialMainView` prop, and
`DashboardLayout.tsx:515-530`'s `useState<MainView>` initializer defaults to `"home"`
when it is falsy — the line that painted dashboard content under the bogus URL. Because
the parser never produced `unknown`, the file's one hard-404 gate,
`if (parsedView.screen === "unknown") { notFound(); }` at `page.tsx:3724`, was never
reached.

## What changed and why there

One file, one conjunct (`frontend/src/lib/routes.ts:231-236`):

```ts
if (head === 'register' && segments.length === 1) {
  return { screen: 'register' };
}
```

`/register/<sub-path>` now falls past every remaining branch to the function's existing
terminal `return { screen: 'unknown' }` (`routes.ts:430`), and `page.tsx:3724`'s existing
`notFound()` handles the 404 — no new branch in the page component, none in
`DashboardLayout`.

It belongs in `parseViewPath` because that is the single function every consumer routes
through. Blast radius re-confirmed by grep at fix time: the only callers are
`[...view]/page.tsx:376` (the sole render consumer), `error.tsx:24` /
`global-error.tsx:24` (screen-label telemetry only) and `LibraryPage.tsx:490` (its own
scoped call), and **no file anywhere reads `screen === "register"`** — the only
discriminant any consumer tests is `screen === "unknown"`. A guard in `page.tsx` or
`DashboardLayout.tsx` instead would have had to be repeated per caller and would have
left the telemetry labels still calling the bogus path "register".
