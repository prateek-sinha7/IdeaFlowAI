## The symptom

Register a fourth task parser. It appears in the composer's *Task source type*
dropdown with its description — that part is correct SC-001, the options come
from `/api/capabilities`. Select it, save, run: the manifest points it at
`build/tasks.json`, which is not its file.

## The root cause

The *file* each parser reads is a two-entry literal map in the rail
(`CanvasConfigRail.tsx:63-66`):

```ts
const PARSER_TARGET: Record<string, string> = {
  json_tasks: "build/tasks.json",
  screen_plan: "build/screens.json",
};
```

and the `Task source type` `onChange` at `:1402` reads:

```ts
const target = PARSER_TARGET[parser] ?? sel.task_source?.target;
```

For an unmapped parser the `??` falls through to whatever target the *previously
selected* parser left on the selection, and that value is written into the saved
manifest.

That is not benign. `parse_preferring_target` tries the declared `target`
**first**, before its own `fallback_targets` — so if `build/tasks.json` happens
to exist in the sandbox, the new parser reads and mis-parses the wrong file
rather than falling back to its own default.

## The fact is already owned three times, in the wrong places

- `json_tasks.py:205` — `fallback_targets: Sequence[str] = ("build/tasks.json",)`
- `screen_plan.py:180` — `fallback_targets: Sequence[str] = (DEFAULT_TARGET,)`
  (`DEFAULT_TARGET = "build/screens.json"`, `screen_plan.py:39`)
- `CanvasConfigRail.tsx:63-66` — the literal map above

Meanwhile the registry has a purpose-built slot standing empty. `@register`
accepts `config_schema`, recorded in `_META` alongside `_TRUST` as the *single*
source of truth for the palette's `description` + `config_schema`
(`registry.py:190-198`), which the API layer projects via `describe` — the
comment there explicitly names a second hardcoded source as the thing that erodes
SC-001. All three parsers pass `description` only and leave `config_schema`
unset: `json_tasks.py:83-88`, `screen_plan.py:154-159`, `heading_tasks.py:89-93`.

## Note on the sibling map

`FRIENDLY_NAMES` (`:55-61`) has the same literal-map shape but degrades
gracefully — `friendlyName` falls back to `humanize()` (`:67`), so an unnamed
capability is still selectable and readable. `PARSER_TARGET` has no such escape
hatch, which is what turns the same pattern into a data defect here.

## Fix

Put the target in `config_schema` on each `@register`, serve it through the
existing `describe` projection, and read it in the rail from the capability
option the dropdown already has in hand. Delete `PARSER_TARGET`. Until then, a
minimal stopgap is to drop the `?? sel.task_source?.target` fallback so an
unmapped parser saves *no* target and `parse_preferring_target` reaches its own
`fallback_targets`.

Directly relevant to reusing the code-step / code-expanded-parser pattern — see
ADR-0045 for the code-step recipe, and ISS-685 for the call sites that bypass
`parse_preferring_target` entirely.

Commit: `5b3540d71`.

## Analysis (QA-KB-025, analyze phase, 2026-10-01)

Read against the current tree (branch `feat/user-stories-v2`, including the uncommitted `task_identity.py` and strategy edits from [FIX-693](20261001-2204-FIX-693.md)). This analysis changed and ran nothing. Every claim is CONFIRMED by a line I read unless it is marked INFERRED.

**Verdict.** The root cause above stands and the card's meaning is unchanged, so there is no supersession. Its line numbers had drifted (`PARSER_TARGET` is now `:70-73` and the fallback is at `:1694`, not `:63-66` and `:1402`), and four things this card and the BUGS.md note missed are under "Corrections".

### Root cause, with current lines

- `CanvasConfigRail.tsx:70-73`: `PARSER_TARGET` maps `json_tasks` to `"build/tasks.json"` and `screen_plan` to `"build/screens.json"`, and nothing else.
- `CanvasConfigRail.tsx:1693-1694`, the "Task source type" `onChange`:

  ```ts
  const parser = e.target.value;
  const target = PARSER_TARGET[parser] ?? sel.task_source?.target;
  ```

  A parser with no map entry takes whatever target the previously selected parser left on the selection, and `:1695-1702` writes it. In a browser a `<select>` fires `change` only when the option changes, so every case that reaches the `??` carries a target that belongs to a different parser.
- The value is then what runs. `userWorkflows.ts:410-417` (leaf step) and `:384-392` (parent group) copy `ts.target` onto the saved step. `:829-835` and `:813-817` copy it back on load, verbatim, so nothing ever corrects it. At launch `engine.py::_apply_selections` (`:14269` at analysis time) replaces the step's whole `TaskSource` with the selection's (`patch["task_source"] = user_step.task_source`).
- Why a wrong target matters to a parser that honours it: `json_tasks.py:237-240` and `screen_plan.py:223` both try `target` before `fallback_targets`.

### Severity, sized honestly

BUGS.md and the ledger say High. The code supports **Low today (a latent landmine)**, not High.

- **Live today, harmless.** `heading_tasks` is a real, user-allowed parser (`heading_tasks.py:89-94`) and is deliberately absent from `PARSER_TARGET` because it reads the reply. So `json_tasks` to `## Task headings`, and `screen_plan` to `## Task headings`, already save the old parser's file as heading_tasks's `target` (on `sample_wave` that is `"tasks.json"`, `sample_wave/workflow.yaml:37`). This is a static read, not a browser reproduction with a real parser. No run reads it: `task_identity.py:182-184` calls `parser.parse(reply)` for any parser without `parse_preferring_target`, and `HeadingTasksParser` defines only `parse` (`heading_tasks.py:105`). Shipped manifests already carry an ignored `target: tasks.md` on heading_tasks (`prototype/workflow.yaml:75`, `sample_fanout/workflow.yaml:37`).
- **Harmful only for a parser that does not exist yet**: registered, honouring `target` through `parse_preferring_target`, and missing from the literal map. That is why the validator's 3/3 reproduction route-mocked `/api/capabilities` to add `zz_new_parser`. The mock proved the mechanism, not a live failure.
- **When it bites** (INFERRED from the two existing implementations): a json_tasks-style parser (`json_tasks.py:242-255`) moves on to its own fallback when the wrong file fails to parse, so only a wrong file that happens to parse is silently mis-read. A screen_plan-style parser (`screen_plan.py:222-233`) `break`s on the first non-empty file and then raises. Either way the author gets no hint, because the rail has no target field.

It is still worth fixing: once a fourth file-reading parser lands, "a new capability needs no frontend edit" (SC-001) is false for it, and the fix is small.

### Corrections to the BUGS.md framing and to this card

1. **"PARSER_TARGET covers all real parsers" is only half true.** It does not cover `heading_tasks`. The `??` is what makes heading_tasks save "something"; the right behaviour for it is to save no target.
2. **Four read sites, not one.** `PARSER_TARGET` is read at `:1559` (fan-out mode), `:1612` (source agent), `:1642` (the unknown-producer warning) and `:1694`. Only `:1694` carries a stale value over. The `:1559` and `:1612` handlers keep a target only together with the same explicitly chosen parser, which is correct, and give an unmapped parser no target. At `:1642` an unmapped file-reading parser gets the wrong instruction ("end its reply with `## Task N:` headings") instead of the file to write.
3. **A second literal lives in the Simple view.** `AgentsPopup.tsx:2443,2496` seeds `target: "tasks.json"`, which disagrees with `build/tasks.json`. Filed as sibling [ISS-918](20261001-2221-ISS-918.md).
4. **`taskParserOptions` cannot carry the fix as written.** It projects only `{ name, description }` (`AgentsPopup.tsx:1614`, `:1645-1648`), so the agreed step 2, `taskParserOptions.find(...)?.config_schema`, has nothing to read. `mechanicalOptions` (`:1650-1653`) already widens the same projection to carry `reads`, `process` and `writes`; mirror it. `CapabilityEntry.config_schema` is already typed `Record<string, unknown>` (`lib/api.ts:2212`, `store/api/capabilities.ts:9`), so no new type is needed, but reading it needs a narrowing guard.

### The agreed minimal fix: accept, with four amendments

| step | verdict | note |
|---|---|---|
| 4: drop `?? sel.task_source?.target` at `:1694` | **accept. This line alone removes the defect.** | Safe, because every file-reading parser owns its default (`json_tasks.py:214`, `screen_plan.py:216`), so an omitted target is runtime-equivalent to the seeded one, and heading_tasks ignores it. |
| 1: `config_schema` default on json_tasks and screen_plan | accept, amend | (a) Shape. All six existing non-empty schemas I opened are JSON Schema, `{"type": "object", "properties": {...}}` (`wave_scheduler.py:215-230`, `task_loop.py:131`, `security.py:47`, `fanout_batch.py:41`, `code_test.py:56`, `single_file.py:77`). The proposed `{"target": {...}}`, and the validator's mock `config_schema.target.default`, would be the lone flat one. Prefer `properties.target.default`. Either works only if the decorator, the backend test, the frontend fixture and the Verify mock all agree. (b) Add `DEFAULT_TARGET = "build/tasks.json"` to `json_tasks.py` (screen_plan already has one, `:40`) and use it in both the decorator and the `fallback_targets` default, so the registry-visible default cannot drift from the real one. |
| 2: replace `PARSER_TARGET` with a helper | accept, amend | Widen `taskParserOptions` first (correction 4). Make the helper a pure function over the options list, exported from `AgentsPopup.tsx` beside `useAgentCapabilities` (the rail already imports from there). No new hook call and no new fetch. |
| 3: use it at `:1559`, `:1612`, `:1642`, `:1694` | accept | Plus the two Simple-view literals ([ISS-918](20261001-2221-ISS-918.md)). |
| 5: types and tests | accept | Types: see correction 4. Tests: the `PALETTE` fixture at `CanvasConfigRail.test.tsx:53-69` has `config_schema: {}` on every parser and no `json_tasks` entry at all, so `:669-683` (screen_plan seeds `build/screens.json`) needs the fixture to carry the default. |

Alternative considered and not recommended: stop seeding a target entirely and rely on the parsers' fallbacks. It is runtime-equivalent but empties the saved manifest and the `:1642` hint, and it contradicts this card's locked constraint that the target belongs in `config_schema`.

### Blast radius (grepped)

- **Carries the stale value:** `CanvasConfigRail.tsx:1694` only.
- **Reads the literal map:** `CanvasConfigRail.tsx:1559`, `:1612`, `:1642`. Related copy that names the files for the three known parsers and degrades gracefully: `FRIENDLY_NAMES` `:62-68` and the InfoHint `:1659-1667`.
- **Second literal:** `AgentsPopup.tsx:2443`, `:2496` ([ISS-918](20261001-2221-ISS-918.md)).
- **Persist the value verbatim, both directions:** `userWorkflows.ts:384-392`, `:410-417`, `:813-817`, `:829-835`. Backend: `selections.py:174-188`, `compiler.py:1260-1267` (`target=raw_ts.get("target")`, no validation), `engine.py::_apply_selections`, and the projection `workflows.py:481-486`.
- **Runtime readers, all through `task_identity.parse_step_tasks` (`:173-184`):** `task_loop.py:218-220`, `wave_scheduler.py:268-277`, `fanout_batch.py:93-98`, and the three resume reconcilers in `engine.py` (`_compute_cumulative_boundaries`, `_compute_wave_orphan_allowsets`, `_first_incomplete_step`; their calls sat at `:14905`, `:15001` and `:15248` at analysis time, and the file is being edited concurrently, so go by name). Only `json_tasks` and `screen_plan` honour the value. No other writer of `task_source` carries a stale target: the Simple view and the fan-out toggle replace the object wholesale.

### Fix hazards for whoever implements it

- **Loading window.** `taskParserOptions` is empty until `/api/capabilities` returns. Only the parser `<select>` is `disabled={loading}` (`:1674`); the fan-out mode and source selects are not. A mode switch in that window would seed no target. That is runtime-safe (the parsers' fallbacks apply) but differs from today's always-seeded manifest. Accept it, or disable those two selects while `loading`.
- **The palette gains a gear.** `AgentsPopup.tsx:1252-1254` shows a configuration affordance for any capability with a non-empty `config_schema`, so json_tasks and screen_plan will gain one. `CapabilityPaletteSection.test.tsx` may pin the old rows.
- **Verify must use the same shape** as the decorator (step 1a), or the rail finds no default and saves no target, which hides the "points at its own file" half of the expectation.
- **Do not** add a fourth key to `PARSER_TARGET`, a parser-name branch in the rail or kernel, or a static metadata map in `app/api/` (`registry.py:246-253`). Do not import anything from `app.*` into `agents.capabilities.task_parsers.*`: the import-linter contract "agents.capabilities must not import the execution kernel or the web layer" (`backend/pyproject.toml`) forbids it, and a module constant needs no import.

### Seen and left alone

- Switching the fan-out mode resets the parser and target to the per-mode defaults (`:1550-1559`, documented intent), so a step's authored target (`build/writer-tasks.json` in `backlog`) is replaced when the author flips the mode away and back. That is design, not this bug, and it is not filed.
- `AgentsPopup.tsx:1329-1348` renders the top-level keys of `config_schema` as fields, which for a JSON-Schema-shaped schema would give rows named `type` and `properties` (read, not rendered). It is pre-existing and unrelated to the carry-over; the fix will make it visible on two more capabilities.
