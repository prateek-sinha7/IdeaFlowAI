# FIX-420

## What was wrong

One "Update the Specs" click opened the analyze review gate three times. Firing `[0]` is
the outer first-pass gate the user clicked at; `[2]` is the gate re-opened once the
revision pass returned. Firing `[1]` — the analyze re-run's own gate INSIDE
`_run_spec_revision_sub_pipeline` — was pure cost: it published the same producer's same
bytes that `[2]` was about to publish again (live `5ecb990f` seq 24652/24655, 11,974
bytes, sha1 `0136795fc392`), offered a strictly smaller action set (no "Update the Specs",
by [FIX-218](20260811-2246-FIX-218.md)'s design), and approving it had no externally
visible effect — only the SECOND approval reached `agent_start prototype-build`.
[FIX-220](20260812-0131-FIX-220.md) made the three firings *identifiable* on the wire but
suppressed none of them; [ISS-072](20260812-0131-ISS-072.md) is the deferred half that
suppresses `[1]`.

Suppressing `[2]` instead was disqualified before this work: it is the only
`update_specs_eligible=True` firing, so removing it deletes the sole entry to a second
cycle and regresses [ISS-064](20260812-0001-ISS-064.md).

## Root cause

`backend/agents/execution_engine/engine.py:6756` (the sub-pipeline's re-dispatch loop) ran
the analyze agent through the FULL `_run_agent` path, which reaches the review gate through
`_should_gate` (`engine.py:6187`) exactly as a first-pass dispatch does. Nothing
distinguished "this analyze dispatch is a re-run inside a pass whose result is about to be
gated by the caller" from "this analyze dispatch IS the caller". The engine had no
per-dispatch way to say *do not pause here*; the only in-flight signal available,
`ectx.revision_attempt`, is pass-wide and would have killed the specify and plan in-pass
gates too — and those are WANTED and demonstrably used (live seq 13640/23221, both
approved).

## What changed and why there

**`backend/agents/execution_engine/context.py:355`** — declares
`suppress_review_gate: bool = False`, the fourth member of the publish-around-one-dispatch
scratch family beside `spec_revision_context` / `spec_revision_prior_artifact`. Declared
rather than left as an undeclared attribute for the same reason `spec_revision_context` was
declared in quick-260811-si4: the save/restore reads it at entry and needs a real default.

**`backend/agents/execution_engine/engine.py:6759`** — the publisher, one line inside the
re-dispatch loop, immediately beside the existing `spec_revision_prior_artifact` publish and
using the identical name-free idiom:

```python
ectx.suppress_review_gate = sub_spec is analyze_spec
```

OBJECT IDENTITY against the spec, never an agent id or workflow name (INV-1 / SC-001), so
the specify/plan re-dispatches are untouched. Saved at entry (`engine.py:6716`) and RESTORED
in the same `finally` that restores the rest of the pass's scratch (`engine.py:6823`) — the
si4 restore-don't-clear discipline, kept so an inner pass can never zero an outer pass's
marker while the outer pass is on the stack.

**`backend/agents/execution_engine/engine.py:6221`** — the single honouring read, at the top
of `_should_gate`:

```python
if getattr(ectx, "suppress_review_gate", False):
    return False
```

Placed HERE, not at the gate branches, because `_should_gate` is the one predicate all five
call sites route through: `_run_agent`'s three gate branches (RESUME-17 restart re-entry
`:4494`, the pending-re-open short-circuit `:4625`, the live post-stream gate `:5765`) plus
the two dispatch-loop `inline_gated` dedupe reads (`:2799`, `:3026`). One guard, no caller
left behind (INV-12).

Saves 3 `run_events` and one human approval per revision cycle.

## What was deliberately NOT changed

[ISS-072](20260812-0131-ISS-072.md) prescribed also DELETING condition 2 of
`_update_specs_eligible` (`engine.py:8291`, the `not getattr(ectx, "revision_attempt", 0)`
term) on the grounds that it becomes unreachable once `[1]` is gone. It is **kept**. Its
"unreachable" status holds only for today's `_AGENT_KIND_MAP`, in which `prototype-analyze`
is the sole producer of the `analysis` kind; a second `analysis`-kind agent in a
specify/plan slot would make an in-pass gate eligible again. The term is a trust boundary —
it is what `_run_review_gate` refuses on and what the three REST ingresses answer 409
`update_specs_not_offered` from (ISS-053) — costs nothing, is dormant at both surviving
firings, and stays proven by
`test_update_specs_enforcement.py::test_three_gate_vector_is_enforced_and_leaves_a_second_cycle_reachable`.
Deleting a binding fence for tidiness is a decision, not a fix.

The empty-analysis backstop path (`engine.py:6689`, `index < 2` returns before the loop) is
unaffected: the marker is never published on it, so `[2]` still fires and remains the only
human checkpoint before the build — unchanged from pre-fix.

## Blast radius the card understated

[ISS-072](20260812-0131-ISS-072.md) named ONE test file. Three were affected, because the
firing this removes is the subject of two sibling cards' proofs:

- `test_gate_revision_discriminator.py` ([FIX-220](20260812-0131-FIX-220.md)) — the
  `(revision_cycle, revision_in_flight)` pair existed to separate `[1]` from `[2]`, which
  shared a cycle index, a `gate_key` AND their output bytes. With `[1]` gone the two
  surviving analyze firings differ in `revision_cycle` alone. `revision_in_flight` stays
  published and stays LIVE — it is still True at the specify/plan in-pass gates, which the
  frontend reads for the "Revision cycle N · in progress" chip
  (`InlineGateActions.tsx:264`) and the "Approve & finish the revision" label
  (`DashboardLayout.tsx:2490`). No frontend change was needed.
- `test_update_specs_enforcement.py` (ISS-053) — its three-gate vector harvested the
  in-pass eligibility value from a real drive. That value is no longer harvestable, so it
  is now taken from the rule itself; the three-verdict enforcement proof
  (`honored / refused / honored`) is intact.
- `test_spec_revision_cycles.py` — the two-cycle drives move from `{0, 2}` to `{0, 1}`, and
  the A-safety NESTING drive (BUGFIX-NESTED-REVISION defect A) passes a new
  `allow_in_pass_gate=True` to `_drive_cycles`, which stubs `_should_gate` down to its
  `gate_agent_ids` branch. That is the same deliberate fence-bypass the file already applies
  to `_run_review_gate` and for the stated reason: no client can reach a nested pass, and
  the safety net must be kept honest rather than left to rot behind the fence.
