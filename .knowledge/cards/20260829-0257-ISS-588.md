## What happened

Sibling defect derived while analyzing `BUG-20260828-082706-runs-id-files` (root card
[ISS-351](20260828-2103-ISS-351.md)) — found by grepping every other `.length`-as-bytes site in
the frontend, NOT by live browser reproduction. **INFERRED**: the mechanism is confirmed by
reading the source below, but nobody has yet reproduced the user-visible symptom in a running
browser. What would settle it: open an App Builder run whose generated code files contain
multi-byte UTF-8 characters (comments, string literals, or i18n text with non-ASCII characters),
and compare the file explorer footer's "X KB total" against the true summed byte size of every
file's content (`wc -c` on each, or `new Blob([content]).size` per file).

## Root cause

Same mechanism as [ISS-351](20260828-2103-ISS-351.md): `String.prototype.length` counts UTF-16
code units, not UTF-8 bytes. `AppBuilderPreview.tsx:556`, in the file explorer's footer stats:

```
{files.length} files · {(files.reduce((s, f) => s + f.content.length, 0) / 1024).toFixed(1)} KB total
```

Summing `f.content.length` across every generated code file and dividing by 1024, labelled
"KB total", repeats the identical arithmetic mistake ISS-351 found in `FilesTab.tsx`'s
`formatSize()` callers — an independent inline occurrence in a different component, not a call
into a shared, already-broken function. Because this is a SUM across every file, the understatement
compounds with file count as well as with non-ASCII density.

## Expected vs actual

- **Expected:** the footer's "X KB total" reflects the true summed UTF-8 byte size of every
  listed file's content.
- **Actual:** the footer sums `.length` (UTF-16 code units) per file, understating the total
  whenever any file's content contains multi-byte UTF-8 characters. `{files.length} files` (the
  file count half of the same line) is unaffected.
