## Symptom

```
test_all_agents_failed_emits_pipeline_failed_not_complete
  expected exactly one pipeline_failed, got [{'type': 'workflow_v…
test_partial_failure_emits_degraded_pipeline_complete            assert 5 == 1
test_clean_run_payload_carries_no_degraded_keys                  assert 6 == 2
test_recovered_timeout_agent_is_not_listed_as_failed             assert 6 == 2
test_unrecovered_failure_alongside_recovered_timeout_lists_only_the_failure  assert 5 == 1
test_engine_runner_error_arm::test_all_agents_error_ends_pipeline_failed
test_engine_runner_error_arm::test_partial_error_ends_degraded
```

Seven tests, one behaviour change: the terminal payload gained events these
assertions did not expect. Establish WHAT the extra events are before deciding
whether the engine or the assertions are wrong — a clean run carrying degraded
keys would be user-visible.

## Root cause

`backend/agents/execution_engine/engine.py:1720-1723` — the roster seam
(ADR-0003, refined by ADR-0008, landed in `bab17c0b9` alongside ppt_v2):

```python
_plan_ids = {s.agent_id for s in compiled.steps}
_roster_is_partial = bool(agents) and {a.id for a in agents} < _plan_ids
if compiled.steps and (not agents or _roster_is_partial):
    agents = self._specs_from_plan(compiled.steps)
```

Both harnesses build their roster as
`get_pipeline_agents("user_stories")[:2]` — a STRICT SUBSET of the 6-step
compiled `user_stories` plan — so the seam correctly expands 2 → 6 and the run
executes all six agents. Every count assertion (`== 1`, `== 2`) and every
`fail_ids` / `error_ids` set is computed against the stale 2-agent slice, so
four of the six agents complete unstubbed-for and the terminal payload reports
`agents_total=6`.

- `test_pipeline_failure_semantics.py:159` — 0 `pipeline_failed`, because 4 of
  6 completed: a 2-of-6 failure is a partial, not a total collapse.
- `:204` / `:396` — `assert 5 == 1` is `data["agents_completed"] == 1`; 5 of 6
  survived.
- `:231` / `:316` — `assert 6 == 2` is `data["agents_completed"] == 2`.
- `test_engine_runner_error_arm.py:153` / `:200` — identical, same `[:2]`
  slice in `_drive_execute`.

The card's original title is a misread of the pytest failure message:
`workflow_validated` is not a new event riding alongside `pipeline_failed`. It
is the unconditional Step-1 DAG validation event at `engine.py:1904`, present
since `4889e3a85` (the original engine commit) — it is merely the FIRST element
of the whole `events` list that `assert len(failed) == 1, f"...got {events}"`
dumps when it finds zero.

## Evidence — production satisfies every F3 contract today

Throwaway probe (deleted after the run): the SAME stubs and the SAME assertions
from `test_pipeline_failure_semantics.py`, with the harness driving the full
6-agent roster instead of `[:2]`. Zero application and zero test edits.

| scenario | terminal | state | `agents_completed` | `status` | `agents_failed` |
|---|---|---|---|---|---|
| all 6 fail | `pipeline_failed` ×1, `pipeline_complete` ×0 | `failed` | 0 / 6 | absent | all six ids, `error="no agent completed"` |
| 1 of 6 fails | `pipeline_complete` ×1 | `completed` | 5 / 6 | `degraded` | `['domain-analyst']` |
| clean | `pipeline_complete` ×1 | `completed` | 6 / 6 | **absent** | **absent** |
| recovered timeout (error + complete, same agent) | `pipeline_complete` ×1 | `completed` | 6 / 6 | **absent** | **absent** |

That is scenario (a), (b), (c) and the WR-05 recovered-timeout contract, all
green. The card's stated worry — "a clean run carrying degraded keys would be
user-visible" — is DISPROVED: the clean run's payload carries neither key, and
a recovered timeout is not listed as a failure.

## Why this was escalated instead of fixed

There is no application defect to fix, and the only available change is a test
edit — which this fixer does not make to turn a red green:

- Making the engine honour a strict-subset roster reverts the ADR-0008
  refinement and re-breaks ppt_v2, whose `get_pipeline_agents("ppt_v2")`
  returns only the two agents authored for it while the plan reuses
  `ppt-brief-analyst` / `ppt-composer` — the DAG resolver then rejects the run
  outright ("ppt-deck-qa-v2 consumes 'ppt-composer' but no upstream agent
  produces it"). That is the exact regression the seam exists to prevent.
- Loosening the count assertions to match 6 is bending the test to the code.
- The correct change is a harness rewrite: drop the `[:2]` slice in
  `_drive_engine` (`test_pipeline_failure_semantics.py:104`) and
  `_drive_execute` (`test_engine_runner_error_arm.py:67`), derive `fail_ids` /
  `error_ids` and the expected counts from the full roster, and drop the
  `assert len(specs) == 2` harness precondition. That is 4-test-writer work.

The three-line seam is not a `pipeline_type` branch and does not touch SC-001 /
INV-1; it discriminates on set containment against the compiled plan only.
