## What was wrong

QA-SG-002 (`BUGS.md#qa-sg-002`): on a simple launch panel
(`/create/user-stories`, `/create/app`, any `/create/<workflow_type>` that is
not `ppt`/`prototype`) the **Run workflow** button never disabled after being
clicked — no grey-out, no loading state, still clickable. A second click
landing before the SPA route push to `/runs/<id>/stream` re-entered the
handler and started a second, fully independent run.

[ISS-729](20260922-1338-ISS-729.md) confirmed it live 3/3 from cold: two
synchronous `.click()` calls produced two `POST /api/runs` with two distinct
run ids (`e76d1416-d01a-4a6d-86da-80e224585405` /
`17abafce-bdc7-4de1-a4bc-67e0ef7a36c0`).
[ISS-767](20260922-1445-ISS-767.md) is the same shape on the composer's
**Run once**, which is a separate implementation rather than a caller of the
first — neither file renders the other, so the defect had to be fixed twice,
once per launch surface.

## Root cause

Two independent launch handlers, neither carrying an in-flight flag, each
behind a `disabled` prop that only re-checks field validity:

- `frontend/src/components/workflow/IdeaInputPage.tsx:1504` — `handleRun`
  set no submitting flag, and the Run button's
  `disabled={!ideaInput.trim() || pipelineAgents.length === 0 || (isMigrationMeta && !migrationChoice)}`
  (same file, the Run button in the header's `rightSlot`) never reflected
  "a run is already being submitted".
- `frontend/src/components/workflow/composer/ComposerPage.tsx:985` —
  `handleRunOnce` likewise, behind `disabled={!onRun}`, which only asks
  whether the prop exists at all.

The mechanism is the one [FIX-345](20260828-2250-FIX-345.md) already
documented for `/login`: a React state update is not a DOM mutation. Even
had these handlers set an `isSubmitting` state on entry, the real `disabled`
attribute only flips on the next commit, one tick after the click event —
and the second click lands inside that window. State alone is structurally
too slow; the guard has to be synchronous.

`handleRun` is reached from two entry points (the button's `onClick` and the
brief's `onSubmitShortcut={handleRun}`, `IdeaInputPage.tsx:1862` — a detail
ISS-729's blast radius did not list), and `handleRunOnce` from two as well
(`ComposerPage.tsx:1323` and the Cmd/Ctrl+Enter shortcut at
`ComposerPage.tsx:1467`). That is why the guard belongs inside each handler
rather than on any call site.

## What changed and why there

Frontend only — the backend answered every duplicate correctly by minting a
second legitimate run; this was a submission-gating gap, not a server one.
Both files already imported `useRef`/`useState`, so no import changed.

**`frontend/src/components/workflow/IdeaInputPage.tsx`**

- `const submittingRef = useRef(false)` + `const [isSubmitting, setIsSubmitting] = useState(false)`
  declared immediately above `handleRun`.
- Inside `handleRun`, `if (submittingRef.current) return; submittingRef.current = true; setIsSubmitting(true);`
  placed **after** the existing early returns (`ideaInput.trim()`,
  `pipelineAgents.length`, `isMigrationMeta && !migrationChoice`,
  `designMissing`) and before `finalMessage` is built. FIX-345's placement
  rule: a latch set at the top of the handler is never released on a
  validation bail-out and wedges the button permanently. The
  `designMissing` path in particular is a normal, repeatable action — it
  opens the design picker and the user then clicks Run again.
- `isSubmitting` prepended to the Run button's `disabled` expression, which
  is what makes the button visibly grey out (`disabled:opacity-30
  disabled:cursor-not-allowed` were already on it) — the reporter's actual
  complaint.

**`frontend/src/components/workflow/composer/ComposerPage.tsx`**

- The same ref/state pair beside the existing `isSavingRef`
  (`ComposerPage.tsx:257`), the guard inside `handleRunOnce` after its own
  `!onRun` / empty-brief / zero-agent / `designMissing` early returns, and
  `isSubmitting` added to `disabled={!onRun || isSubmitting}`.

**Why nothing clears the latch.** Both handlers reach
`useWorkflow.startPipeline` (`frontend/src/hooks/useWorkflow.ts:66`), which
sets `isRunning: true` *synchronously, before* issuing the POST. The
DashboardLayout effect at
`frontend/src/components/layout/DashboardLayout.tsx:796-806` reacts to that
by forcing `setMainView("execution")`, which unmounts both
`<IdeaInputPage>` (`DashboardLayout.tsx:3062`) and `<ComposerPage>`
(`DashboardLayout.tsx:3103`, rendered under `mainView === "composer"`). The
transition is therefore unconditional — it does not wait on the POST — so a
failed launch cannot leave a latched ref behind a still-mounted button. This
is the one place the fix diverges from
[FIX-470](20260902-1200-FIX-470.md), which needed a `finally` because its
`handleSave` stays on the page. Observed in practice: the ISS-767 run's POST
returned `400` and the guard still behaved, exactly one POST sent. If
`onRun` ever gains a failure path that returns the user to these screens,
this latch needs a release.
