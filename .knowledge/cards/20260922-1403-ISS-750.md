## What happened (inferred — not yet reproduced)

[ISS-695](20260922-0800-ISS-695.md) confirmed that this environment's outbound HTTPS calls
fail TLS verification whenever they go through `httpx`'s default (certifi-only) trust store,
because a TLS-intercepting proxy sits in front of every outbound connection and its CA is not
in that bundle. `backend/app/api/settings.py`'s `upsert_github_pat` (the "Save GitHub PAT"
endpoint under Handoff settings) builds its own `httpx.AsyncClient(timeout=10.0)`
(`settings.py:130`) with the identical default — no `verify=` override — to call
`https://api.github.com/user` and validate the PAT before saving it.

## Why the root cause implies it

Same construction as the confirmed defect (`httpx.AsyncClient()`, no `verify=`), same class
of outbound target (a public HTTPS host outside this environment's trust chain). ISS-695
already proved by direct interpreter test that this class of construction fails against
multiple unrelated hosts (`example.com`, `hexaware.com`, `www.google.com`) in this
environment, so `api.github.com` is expected to fail identically — not yet verified live for
this specific endpoint.

## Expected vs actual (expected on reproduction)

- **Expected:** entering a valid GitHub PAT and clicking save calls
  `GET https://api.github.com/user`, validates the token, and stores it.
- **Actual (predicted):** the call raises the same `httpx.ConnectError` wrapping
  `ssl.SSLCertVerificationError` as ISS-695. Unlike `fetch_url_for_template`, **there is no
  catch-all around this call** — the route body (`settings.py:114-146`) goes straight from the
  empty-PAT check to `await client.get(...)` to the `resp.status_code != 200` check, with no
  try/except in between — so the exception propagates unhandled instead of surfacing as a
  friendly error. That is a worse failure mode than the reported bug, not just a duplicate of
  it.

## Evidence

- `backend/app/api/settings.py:130` — `async with httpx.AsyncClient(timeout=10.0) as client:`
  (read directly; no `verify=` argument)
- `backend/app/api/settings.py:114-146` — full route body; no try/except wraps the
  `client.get` call
- [ISS-695](20260922-0800-ISS-695.md)'s direct-interpreter reproduction (its "Trigger"
  section) is the proof that this construction pattern fails in this environment

## What would settle it

Enter a PAT in Settings → Handoff → "GitHub PAT" and click save in this same environment;
confirm either an unhandled 500 (predicted) or a normal 400 "GitHub rejected the PAT" response
(would refute this card).

## Test (test-writer pass, 2026-09-22) — refuted, not reproducible in this environment

Settled directly per the "What would settle it" section above: called `upsert_github_pat`
with a syntactically-valid-but-fake PAT (`ghp_faketoken0000000000000000000000`) and mocked
`user`/`db` (unused before the `client.get` call fails or succeeds):

```
$ backend/.venv/bin/python -c "asyncio.run(upsert_github_pat(GithubPATRequest(pat='ghp_faketoken0000000000000000000000'), user=MagicMock(), db=MagicMock()))"
HTTPException (handled) 400 GitHub rejected the PAT (401). Check that it has at least `repo` scope.
```

No SSL/TLS error — the call reaches `api.github.com` cleanly and returns the normal
400 "GitHub rejected the PAT" path. Direct comparison, same pass: `https://api.github.com/user`
succeeds (`401` cleanly) while `https://example.com/` and `https://github.com/` (no `api.`
subdomain) both fail with `SSLCertVerificationError` through the same unmodified
`httpx.AsyncClient()` construction — this environment's TLS-intercepting proxy does not
intercept `api.github.com`, only general/arbitrary domains (see
[ISS-695](20260922-0800-ISS-695.md)'s "Test" section for the fuller host comparison). The
analysis's generalization from ISS-695 (any external HTTPS host fails identically) does not
hold for this specific host in this environment — no test written; there is no defect here to
assert against today.

## Fix (fixer pass, 2026-09-22) — [FIX-607](20260922-1814-FIX-607.md)

Fixed with the root card, not separately: `upsert_github_pat` (`backend/app/api/settings.py:130`) now passes
`verify=default_ssl_context()` (`backend/app/core/http_client.py`), the same
shared context ISS-695's own call site uses. One keyword argument per call
site; the context can only widen the trusted-CA set, never narrow it.

Still `verification.status: not_reproducible` — the test-writer's refutation
stands (this environment's proxy does not intercept `api.github.com`, so
the failure never surfaced here). The call site is fixed anyway because the
mechanism is identical and the exemption is a property of this proxy's
allowlist, not of the code.
