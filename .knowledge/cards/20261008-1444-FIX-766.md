# FIX-766

Resolves [ISS-1092](20261007-2308-ISS-1092.md) (QA-KB-100, root) and its siblings [ISS-1111](20261008-1415-ISS-1111.md),
[ISS-1112](20261008-1415-ISS-1112.md) and [ISS-1113](20261008-1415-ISS-1113.md). It does NOT resolve
[ISS-1114](20261008-1415-ISS-1114.md), the non-override shape of the same exposure, which waits on a product decision.
The cards' analysis was used as written and not re-derived. Their callers were re-grepped at HEAD `d284eb258` and the blast
radius still held: `merge_override_steps` has two callers (`workflows.py:322` via `_overridden_plan`, `run_commands.py:3628`),
the four writers are the ones ISS-1112 lists, and `trust="db"` on a user row appears only in Case 3 and the trigger.

## What was wrong

A user's override of a built-in workflow is stored as a `source="user"` row with `overrides_pipeline_type` set. Its steps
were compiled at `trust="db"` everywhere they were read or written:

- the merge, `overrides.py:100` (pre-fix): `WorkflowCompiler().compile(parsed, registry, trust="db")`;
- the save, `user_workflows.py:117`: `_compile_check_manifest` compiles at `trust="db"`, and sync-from-file compiled nothing;
- launch by row id, `run_commands.py` Case 3 (`trust="user" if _inline else "db"`), and the conditional-route trigger,
  `kernel_services.py:1641` (pre-fix, the literal `trust="db"`).

`db` has been a TRUSTED source since `ea2db4e02` / [ADR-0039](20260904-1424-ADR-0039.md):
`_TRUSTED_SOURCES = frozenset({"file", "builtin", "db"})` (`compiler.py:228`). At that level `_check_trust` returns at
`if trusted: return` (`compiler.py:506-507`), the exec/network/secrets/spawn grant rejection under `if not trusted:`
(`compiler.py:1023`) is skipped, and `cap_key_for_trust("db")` picks the trusted permission cap (`permission_caps.py:75`).
So an override step could carry `security`/`approval` gates, `exec` and `spawn_subagents` grants and engineer-only hooks,
compaction and post_step, and a BASIC-tier caller could save it (201). The merge was written in `732adc245`, when `db` still
meant untrusted; the constant changed meaning under the call. Spec 016 (`spec.md:95-96`), [ADR-0027](20260825-2115-ADR-0027.md)
and [ADR-0044](20260901-0324-ADR-0044.md) all say override steps are untrusted.

## What changed, and why there

1. **`backend/agents/execution_engine/overrides.py`**. The isolated steps-only compile became one public function,
   `compile_override_steps(workflow_id, steps, registry)` (`:50-71`), at `trust="user"`, raising
   `ManifestValidationError` / `CompilerError`. `merge_override_steps` now calls it inside its existing narrow `try`
   (`:113`). Its fallback is unchanged: on a refusal it logs "failed to compile" and returns the file plan, the same object.
   That fixes both readers at once (the served plan and the launch of the built-in). The three comments that said `trust="db"`
   were corrected (module docstring, the placeholder note and the call-site comment).
2. **`backend/app/api/user_workflows.py`**, the four writers ([ISS-1112](20261008-1415-ISS-1112.md)).
   `_compile_check_override_steps` (`:139-168`) runs the same `compile_override_steps` and turns a refusal into a 422
   (`invalid workflow override (<source>): <compiler reason>`). `_validated_manifest` takes an optional `override_of` and calls
   it after its structural checks and the existing `db` compile (`:233-235`). Running it after the structural checks matters: a
   non-mapping step must still get the structural 422, not an `AttributeError` inside the parser. Callers: POST upsert and POST
   insert pass `_ov_target`, PATCH passes `row.overrides_pipeline_type`, and sync-from-file calls the helper directly on the
   file's `steps` when the row is an override (`:1136-1142`). It checks steps only, because the file's `deliverable: ppt` and
   `context_providers: [opendesign]` are never read off an override row and are not user-allowed. The `agents.execution_engine`
   imports are lazy, as `_compile_check_manifest` already does (the module docstring forbids a module-level import).
3. **`backend/app/api/run_commands.py`**, Case 3 ([ISS-1113](20261008-1415-ISS-1113.md)). The row snapshot now carries
   `overrides_pipeline_type` (`:3296`). One `_trust` (`:3356-3358`) is `"user"` for an inline manifest or an override row and
   `"db"` for every other saved row. It feeds the compile (`:3395`) and the persisted `_trust` (`:3408`), so a resume replays
   at the same level. No fourth `LaunchSource` was added ([ADR-0020](20260824-1831-ADR-0020.md)).
4. **`backend/agents/execution_engine/kernel_services.py`**, the conditional-route trigger ([ISS-1113](20261008-1415-ISS-1113.md)).
   `row_trust` is read inside the open session (`:1616`) and used for the compile (`:1644`). This is a truthiness test on a
   column, not a workflow-name branch; the SC-001 ratchet's INV-1 tests pass.

Not done, by design: `_TRUSTED_SOURCES` is unchanged, `_compile_check_manifest` was not flipped globally, and no gate-name
special case was added. Each of those would either break the Composer rows that ADR-0039 trusts or close only 5 of the 11
kinds (ISS-1092 "Traps").

## Consequences and what is left

- **Behaviour change, by the cards' design.** The 422 is the safe default ([ISS-1092](20261007-2308-ISS-1092.md) re-analysis). A
  canvas "Save as my version" of a built-in whose raw steps carry engineer-only keys (`app_builder`, `prototype` and six others,
  `analysis-04`) is now refused. Whether the canvas should strip those keys first is a UX call: [ISS-1118](20261008-1444-ISS-1118.md).
- A stored override whose steps now fail runs the file plan, and the existing "failed to compile" warning is logged. Launching it
  by id returns 422 `invalid_workflow_manifest`. `GET /api/workflows/{type}` still reports `is_overridden: true` and serves its
  raw `manifest_steps`. That is the display mismatch [ADR-0033](20260825-2115-ADR-0033.md) records as known-open
  ([ISS-181](20260825-2115-ISS-181.md) class). The writers can no longer create such a row.
- A run launched by override-row id before this fix carries `_trust: "db"` in its persisted manifest, and a resume replays that.
  ISS-1113 accepts this once the writers stop producing such rows, which they now do.
- ISS-1111's fix direction also asked to correct the docstrings that ADR-0039 left saying "user/db are UNTRUSTED". There are
  about 15 lines across `compiler.py`, `engine.py` and `_exec_support.py`, three of them runtime error strings. They were left
  alone so this security diff stays reviewable: [ISS-1116](20261008-1444-ISS-1116.md).
- ISS-1112's adjacent finding is split out: sync-from-file has no `can_run_pipeline` check on its source pipeline. See
  [ISS-1117](20261008-1444-ISS-1117.md).
- [ISS-1114](20261008-1415-ISS-1114.md) is unchanged: a plain manifest row with a caller-chosen `base_pipeline_type` still
  compiles at `db` (probe `fix-05` W5: 201, `exec=True`). That needs a decision.
- A human should annotate [ADR-0039](20260904-1424-ADR-0039.md) with its scope: Composer rows only, not overrides. An ADR is
  corrected by supersession, so it was not edited here.
- Restart: none needed. Only `*.py` changed and the dev server reloads on those. `compile_for_run`'s cache holds file plans, which
  this change does not alter, and the merge is not cached.
