## Decision

`extract_text` is one entry point with three routes, chosen by file extension:

| route | formats | behaviour |
|---|---|---|
| text | `txt` `md` `csv` `json` | content comes straight back in the tool result, capped at 100,000 chars |
| paged | `pdf` `docx` `xlsx` `pptx` | materialised into `.extract/{format}/{slug}/`; the receipt names `document.md`, content stays on disk |
| anything else | — | refused in readable text |

Materialising a `.txt` into pages of itself is work that buys the agent nothing,
which is why the text route exists. The refusal is deliberate rather than a
best-effort conversion attempt: the upload allow-list decides which bytes reach
this process (FR-040), and LibreOffice is a large C++ parser to aim at unknown
input.

The three `_CONVERTED_FORMATS` reach the paged route by being converted to PDF
once, cached at `.extract/{format}/{slug}/source.pdf`, and then materialised by
exactly the same code a native PDF uses.

## Why LibreOffice and not python-docx / openpyxl / python-pptx

This is the decision most likely to be "cleaned up" by someone who has not read
FR-026a, and the cleanup would delete the feature.

The apparent trade is bad on its face: drop a 400–600 MB office suite from the
image, parse natively with three small pure-Python libraries already familiar to
the codebase. The reason it is wrong is the same one behind
[ADR-0048](20260918-ADR-0048.md)'s render-crop rule, in a different costume:

> A screenshot carrying callout arrows is **one embedded picture PLUS separate
> DrawingML shapes**. `python-docx` / `python-pptx` image extraction returns the
> picture and drops the annotation, exactly as embedded-PDF extraction did.

Only a render composites the overlay onto the picture, and none of the three
formats has an in-process renderer. Three native extractors would reproduce,
three times over, the defect this spec exists to prevent.

The cost is carried honestly instead of hidden: RISK-09 records the image-size
estimate as unmeasured, and says that if it lands materially higher the trade is
worth re-opening — accepting lost annotations as the explicit price.

## Why the format is a directory level

`_doc_rel(format, slug)` returns `.extract/{format}/{slug}` — the format is a
directory **above** the slug, not a suffix on it.

`report.docx` and `report.pdf` produce the same slug on purpose (the slug is the
filename with the extension stripped). With neither separating mechanism they
name one folder, and then each extraction finds the other's `source_sha256`,
declares the folder stale, `rmtree`s it and re-materialises — **forever**, at
full cost, on every alternating call.

The level also reads well: `.extract/docx/` is "every Word document this run has
materialised". The price is on consumers, and it is stated in the contract: a
consumer enumerating documents must walk **two** levels, because one level down
finds format directories and no manifests (`_iter_document_dirs`).

## One soffice call site, one profile per call

`soffice.py` is the only place LibreOffice is invoked. Two callers need it — the
document materialiser here, and spec 017's `pptx_tools._render_slides` proving a
generated deck opens at all — and they share the module rather than each spawning
their own subprocess, because two copies of an invocation drift and the one that
drifts is the one nobody reads. (That consolidation also removed `pptx_tools`'
old `pdftoppm` branch; slide rendering is `pypdfium2` in-process now and needs no
second binary.)

**Every call gets its own `-env:UserInstallation` profile directory**, created
with `tempfile.mkdtemp` and removed in a `finally:`. A shared profile is not
concurrency-safe: two `soffice` processes against one profile race, and the loser
**exits successfully having produced nothing**. That is the worst available
failure mode — a silent empty success, which surfaces as "conversion produced no
output" and sends the reader to inspect a document that was never the problem.
ADR-0048's process pool makes the collision reachable, so this is not a
theoretical precaution.

The module never raises. Absent binary, 180s timeout, failure to start, and
refusal to open each return text naming which one it was, with up to 400
characters of converter output appended. `available()` answers the
is-it-installed question honestly rather than letting a missing binary read as a
pass — a developer machine usually has it from Homebrew, the built image has it
only if the Dockerfile says so.

## Word splitting on converted grids

`_WORD_X_TOLERANCE = 1.5` overrides `pdfplumber`'s default of `3.0`.

The default is tuned for prose, where a 3pt gap really is one word. A converted
spreadsheet breaks that assumption: a right-aligned number ends flush against the
next column's left-aligned value, so `46445` and `Yes` arrive as the single token
`46445Yes` — **a value that appears nowhere in the workbook**.

Measured before tightening: `1.5` separates those columns and leaves prose
byte-identical (15,072 characters on the 21-page reference PDF at every tolerance
from 3.0 down to 1.0). The change therefore costs nothing.

Note what this is: a repair on a route that is itself wrong for spreadsheets. See
[ISS-690](20260918-ISS-690.md).

## Dependency declaration

`pdfplumber==0.11.10` is declared in `backend/requirements.txt`. `pypdfium2` is
deliberately left unpinned there — it is a hard dependency of `pdfplumber`, and a
direct pin would assert a version contract this project does not own.

An undeclared extraction dependency is the ISS-057 / FIX-191 failure repeated:
the tool imports fine on the machine it was written on and returns "PDF libraries
unavailable" in every environment that installs from the file.

## What a future author must do

Do not replace the LibreOffice layer with native Office parsers without first
re-opening FR-026a and accepting the annotation loss in writing. Do not flatten
`.extract/{format}/{slug}/` to `.extract/{slug}/`. Do not share one soffice
profile across calls. Do not restore `_WORD_X_TOLERANCE` to the library default.
