## Resolution

Verified fixed in the current code on 2026-10-01 (feat/user-stories-v2 @ 3b08b2ba8) by static review: a first-pass check and an independent adversarial re-check both found every claim of this card fixed. No tests were run for this closure.

**Fixed by:** ff37f777a4

**Evidence:** Card has 2 defect claims: (1) ChatAttachments.tsx never renders the truncated flag; (2) _build_attached_files_block never reads it. (1) Fixed: ChatAttachments.tsx:163 does fileContents.find by name and :204-210 renders an amber "truncated" badge when contentEntry?.truncated is true. (2) Fixed: run_commands.py:1322 reads bool(entry.get("truncated")) and :1324-1326 appends "[Content truncated — showing first portion]". The flag reaches the backend: useChatAttachments.ts:254-259 and :284 set it, RunChatLane.tsx:1337/1350/1363 send file_contents, and useRunChat.ts:688-689 puts it in the payload. The backend uses the block at run_commands.py:2001, :2101 and :2174.

**Left over (outside this card's claims):** None for the card's claims. Two edge cases are outside the card. The badge matches by name, so a server-returned result.filename that differs from att.name (useChatAttachments.ts:282) would hide it. The final fallback sendMessage(effectiveText, attachments) in RunChatLane.tsx:1369 omits file_contents for run states other than the three handled. The card file still says status: open and was not updated.
