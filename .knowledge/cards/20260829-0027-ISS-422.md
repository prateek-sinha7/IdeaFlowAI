## Why this must also be broken

[ISS-312](20260828-1941-ISS-312.md)'s confirmed symptom family is "an oversized text
attachment is truncated with zero user-visible indication." The concierge chat lane
(`frontend/src/hooks/useChatAttachments.ts`) is a THIRD, independently-forked file-attach
implementation — not a caller of `handleFiles`/`useBriefAttachments` — and reaches the same
observable symptom through an adjacent mechanism: the flag is computed, then silently
dropped, rather than never computed at all.

For the client-read text path (`.txt/.md/.json/.csv`), `useChatAttachments.ts:245-254`
DOES compute the flag symmetrically with the binary path (unlike the two broken forks in
ISS-312 and [ISS-423](20260829-0026-ISS-423.md)):

```ts
// useChatAttachments.ts:245-254 (TEXT_CLIENT_CAP = 6_000, line 86)
const rawText = await fileToText(file);
const truncated = rawText.length > TEXT_CLIENT_CAP;
const text = truncated ? rawText.slice(0, TEXT_CLIENT_CAP) : rawText;
const entry: FileContentEntry = { name: file.name, text, truncated };
```

and for the binary path (`useChatAttachments.ts:274-278`), `result.truncated` from the
shared `extractFileText()` endpoint is forwarded the same way. So `FileContentEntry.truncated`
is correctly populated for both branches — this hook does not share ISS-312's exact
"missing computation" defect.

The flag is then dropped at BOTH of its two possible surfacing points:

1. **UI**: `grep -n "truncated" frontend/src/components/chat/ChatAttachments.tsx` shows the
   field is destructured (`fileContents`) and forwarded via `onFileContentsChange`, but never
   read for rendering — no badge, no tooltip, no chip text references `.truncated` anywhere in
   the component. Contrast with `.error`, which the module's own header comment says is
   "surfaced per-file" (via the Concierge's reply) — `truncated` has no equivalent path.
2. **Backend**: `backend/app/api/run_commands.py:_build_attached_files_block` (lines
   1088-1117), the function that turns `body.file_contents` into the prompt block the
   Concierge/agents actually read, never calls `entry.get("truncated")` — it reads only
   `name`, `error`, and `text`. It instead RE-DERIVES its own truncation note independently:

   ```python
   # run_commands.py:1113-1116  (_ATTACHED_FILE_TEXT_CAP = 6_000, line 1085)
   elif text:
       capped = text[:_ATTACHED_FILE_TEXT_CAP]
       suffix = "\n[Content truncated — showing first portion]" if len(text) > _ATTACHED_FILE_TEXT_CAP else ""
   ```

   For the client-read text path specifically, this recomputation is structurally dead: the
   frontend already capped `text` to `TEXT_CLIENT_CAP = 6_000` before sending it, and the
   backend's own cap is the SAME number (`_ATTACHED_FILE_TEXT_CAP = 6_000`), so
   `len(text) > 6_000` can never be true for content the frontend already pre-truncated to
   `<= 6_000`. The one signal that correctly knew truncation happened
   (`FileContentEntry.truncated`, computed client-side) is exactly the one field this function
   never reads.

Net effect: a `.txt`/`.md`/`.json`/`.csv` file attached in the concierge chat lane during a
run, whose content exceeds 6,000 chars, is silently cut with no signal in the chat UI and no
note in the prompt block the Concierge/agents receive — the same "zero user-visible
indication" symptom ISS-312 reports, reached through a different subsystem.

## Expected vs actual

**Expected:** the chat lane's already-correct `truncated` flag reaches either the user (a
visible marker on the attachment chip) or the agent (a note in the prompt block), the way
`.error` already does.

**Actual (INFERRED — not yet independently browser-reproduced):** neither surface reads the
flag; it is computed once in `useChatAttachments.ts` and discarded at both of its only two
consumers.

## What would confirm or refute this

Start a run, open the concierge chat lane, attach a `.txt` file with content over 6,000
chars, and inspect (a) the chip DOM for any truncation indicator and (b) the outgoing
`POST` body's `file_contents[].truncated` value alongside whatever prompt block the backend
actually builds from it — confirm `_build_attached_files_block`'s output carries no
truncation note for that entry despite `truncated: true` being present in the payload.

## Where the fix belongs

Two independent gaps, not one: (1) `ChatAttachments.tsx` should render `entry.truncated`
the same way it already threads `entry.error` to a user-visible signal; (2)
`_build_attached_files_block` in `backend/app/api/run_commands.py` should branch on
`entry.get("truncated")` (the value the frontend already computed correctly) instead of
re-deriving its own — which, for the client-capped text path, can never fire given the two
caps are equal. Both are narrower, more surgical fixes than ISS-312/[ISS-423](20260829-0026-ISS-423.md)'s
shared-helper recommendation, since here the missing piece is wiring an already-correct
value through, not computing a new one.
