# FIX-731

## What was wrong

Bug report QA-KB-071: "ISS-126 source-lock test fails 5 of 9: stale anchors after ISS-304 added tokenUsage args". The
root cause is the 2026-10-02 analysis on [ISS-898](20261001-2128-ISS-898.md) and its two siblings. It was not
re-derived here. Every cited line was re-read before editing, at HEAD `5b8b81b0f`. Neither `page.tsx` (sha1
`cea0847ef49a`) nor the lock had uncommitted edits.

- **[ISS-898](20261001-2128-ISS-898.md).** The lock pinned whole call text: `applyTerminalStatus(prev, fullRun.status)`
  five times and `reconcileTerminalStatus(fullRun.status);` once. Commit `7f9be3d60` appended
  `undefined, fullRun.tokenUsage` to both reopen calls (`page.tsx:3128`, `:3130`) for
  [ISS-304](20260828-1600-ISS-304.md). The behaviour [ISS-126](20260812-1852-ISS-126.md) pins still held. Only the anchors
  went stale, and that turned 5 of the 9 block cases red.
- **[ISS-1009](20261002-0540-ISS-1009.md).** The reviewGateData case sliced from `indexOf(...)`. With the anchor gone,
  `call` was -1, the window was `""`, and `not.toContain("reviewGateData: null")` passed without checking anything.
- **[ISS-1010](20261002-0540-ISS-1010.md).** The ordering case compared against the first
  `for (const frame of durableFrames)` in the file. That is the run-switch handler's loop (`:2824`), not the reopen loop
  (`:3074`). A reconcile placed between the reopen fetch (`:3069`) and the reopen loop stayed green, and that is the
  exact placement the lock exists to forbid. It has been blind since `2b25d3d05`.

## What changed, and why there

All changes are in `frontend/src/app/[...view]/terminalReopenReconcile.source.test.ts`, which is the only file the
cards allow (ISS-898's locked constraint). Line numbers below are from the new file.

- **`:25-28`.** `APPLY_CALL` and `RECONCILE_CALL`: two prefix-anchor constants, with no closing paren, so extra
  arguments cannot stale them again. Each matches once in `page.tsx`. The comment above them carries ISS-898's
  "never a bare `applyTerminalStatus(`" constraint (ISS-898, step 1).
- **`:42`, `:52`, `:64`, `:75`, `:85`, `:93`.** The six stale literals now read the constants (ISS-898).
- **`:65`.** `expect(call).toBeGreaterThan(-1)` before the slice (ISS-1009).
- **`:81-84`.** The ordering case computes the reopen handler's `fetchAt`, asserts it is above -1, and calls
  `indexOf("for (const frame of durableFrames)", fetchAt)` (ISS-1010).

### This is a test-file fix: the cards asked for it

Per the cards, the lock's expected text was misstated, not the app. ISS-898's analysis puts it this way: "The app change
is deliberate and measured ... so the test follows the app, not the reverse. No product decision is open." The
BUGS.md triage note says "Do not touch page.tsx." `page.tsx` was not edited.

The 4-test-writer's `terminalReopenReconcileLock.meta.test.ts` was not edited either. Its three `it.fails` markers are
left for the 6-verifier.

## Deliberately not done

- **[ISS-1060](20261007-1908-ISS-1060.md) (new, open, CONFIRMED by scratch mutation).** The
  `writes to the run STORE` case uses `lastIndexOf("runStore.updatePipelineState(", call)`. That matches any of the 6
  earlier store writes in `page.tsx`, so it stays green when the reopen reconcile writes only to a legacy setter. The
  cards never named it, so it is out of scope here.
- **ISS-898 step 5: an optional offline pin that `fullRun.tokenUsage` reaches both containers.** The card calls it
  "optional and not carded". The prefix anchors are blind to the arguments. Only the live e2e
  `tests/integration/e2e/suites/07_run_detail/test_iss304_header_token_total_mismatch.py` guards that.
- **`bridgeTerminality.source.test.ts:51` and `:67`.** These are closing-paren anchors, green today, that ISS-898
  flagged as at risk and did not card.
- **The lock's header comments** still cite old `page.tsx` line numbers (`:2171`, `:2234-2247`, `:1663-1672`). No card
  covers them.
