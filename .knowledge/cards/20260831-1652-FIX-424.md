## What was wrong

A step that BOTH declared `gates: [human]` AND ran a spawn-only strategy
(`fanout_batch` / `wave_scheduler`) got **no human gate at all** — silently. The
author declared a review pause, the run never paused, and nothing was emitted to
say the gate had been dropped. Full evidence in
[ISS-131](20260812-2116-ISS-131.md); it was filed as the known residual of
[FIX-242](20260812-2116-FIX-242.md) and deliberately left byte-unchanged there so
that fix's INV-3 dormancy argument stayed exact.

Not reachable from a file manifest (`sample_fanout` and `sample_wave` both declare
`gates: []`), so the reproduction is a **composed** selection — a user-composed
worker carrying `strategy: fanout_batch` and `gates: ["human"]` on the same agent,
opted into the run's `gate_agent_ids`.

## Root cause

The step-boundary dedupe predicts the inline gate instead of observing it.

- `backend/agents/execution_engine/engine.py:2815` (pre-step) and `:3043`
  (post-step, ISS-172a) passed `inline_gated=self._should_gate(spec, ectx)` into
  `_evaluate_gates`. The dedupe exists so a step whose agent is ticked in
  `gate_agent_ids` does not double-prompt — once pre-step with an empty payload
  from the declared gate, once post-step with the real output from the inline
  `_run_agent` → `_run_review_gate` path.
- `_should_gate` (`engine.py:6205`) answers "is this AGENT selected", not "will the
  inline path actually run". For every strategy that dispatches the step's own
  agent those are the same answer.
- [FIX-242](20260812-2116-FIX-242.md) broke that equivalence: a fan-out step's
  invocations are all `run_fanout` children, and `kernel_services.run_worker` /
  `run_merge_agent` pass `invocation_gated=False`, so the inline gate never fires
  for them. The step's own agent is never inline-invoked at all —
  `fanout_batch.py:119` and `wave_scheduler.py:328` call `runner.run_fanout(...)`
  and nothing else.
- So `inline_gated=True` at the step boundary became a **stale prediction**, and
  `_evaluate_gates:6491` skipped the declared `human` gate in favour of an inline
  gate that never opens.

Strictly better than the pre-FIX-242 behaviour (which HUNG on the same
combination), but still a silent loss of a declared control.

## What changed and why there

The kernel must not learn this from a strategy-name list — that is exactly the
capability-name branch SC-001/INV-1 forbids. So the **strategy declares the fact**
and the kernel reads it off the resolved capability, which is the shape
[ISS-131](20260812-2116-ISS-131.md) itself proposed.

**`backend/agents/capabilities/base.py`** (+10, no deletions) — `runs_agent_inline:
bool` on the `ExecutionStrategy` Protocol, documented as OPTIONAL: absent reads as
`True`, so no existing or third-party strategy has to be edited.

**`backend/agents/capabilities/strategies/fanout_batch.py`** (+7) and
**`wave_scheduler.py`** (+5) — `runs_agent_inline = False`, one class attribute
each. These are the only two spawn-only strategies: `single_shot:60`,
`task_loop:334` and `parallel_group:193` all call `ctx.runner.run_agent` for the
step's own agent, so they keep the default `True` and are unchanged.

**`backend/agents/execution_engine/engine.py`** (+~35, no deletions, no new
imports):

- `_strategy_runs_agent_inline(strategy_name, registry)` — placed directly below
  `_should_gate`, its only reader, so the invocation-scope rule and the
  strategy-scope rule sit together (INV-12 single home). It is
  `registry.resolve("strategy", name)` followed by
  `getattr(strategy, "runs_agent_inline", True)` — a capability resolve plus an
  attribute read, no name branch. `KeyError`/`RuntimeError` (an unresolvable name;
  a compile-validated plan never carries one) reads as `True`, the pre-change
  behaviour.
- One `_runs_agent_inline` local per step iteration, computed where
  `strategy_name` is already known and BEFORE the pre-step gate loop.
- Both call sites become
  `inline_gated=self._should_gate(spec, ectx) and _runs_agent_inline`.
  `_should_gate` is still evaluated per site so the `ectx.suppress_review_gate`
  (ISS-072) timing at each site is unchanged; only the strategy fact is ANDed in.

Fixed at the shared `_evaluate_gates` boundary rather than in the fan-out path,
because both `inline_gated` readers route through the same predicate — one local
covers the pre-step and post-step loops, and `wave_scheduler` (the sibling the bug
report did not name) is cured by the same edit.

### Deliberately NOT changed

- **`_should_gate` / `invocation_gated`** — the invocation-scope half from
  [FIX-242](20260812-2116-FIX-242.md) is correct and untouched. This is the
  orthogonal step-scope half.
- **The per-run `gate_agent_ids` deselect arm of the dedupe**
  (`engine.py:6491-6496`) — a different rule (user unchecked everything), still
  correct for a fan-out step.
- **[ISS-132](20260812-2116-ISS-132.md)** (the task-loop sibling: N *visible* sequential gates) — a product
  decision, not this defect. `task_loop` genuinely does run the step's agent
  inline, so `runs_agent_inline` is `True` for it and nothing here changes it.
