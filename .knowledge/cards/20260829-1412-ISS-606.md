## What's broken

Reported as `BUG-20260829-135100-runs-id-versions` in `bug-hunter/ledger.md`. Cold-navigating
(full `page.goto`, not a tab click) to a pinned-version Steps URL renders content that matches
neither the pinned version's own run record nor the other version's — both version URLs in the
same family render byte-identical Steps content.

Confirmed 3/3 across three independent cold-start cycles (fresh `page.goto` each time, no
soft-nav):

- Family: root/v1 `77f74563-fa19-4f0b-84fd-d0224f89a54a`, revision/v2
  `ef86e750-bbcd-404f-855a-fb0d5bee63f5` (`GET /api/runs/{id}/family` confirms 2 members).
- `/runs/77f74563-.../versions/1/steps` — cycle 1, 2, 3: "Run complete · 5 / 5 agents · 1m 32s".
- `/runs/77f74563-.../versions/2/steps` — cycle 1, 2, 3: **identical** "Run complete · 5 / 5
  agents · 1m 32s", despite the version-picker header correctly reading "Version v2" (button
  text confirmed via accessibility snapshot each cycle).
- Ground truth via direct API: root/v1 `GET /api/runs/77f74563-...` reports `agent_count: 5`,
  `duration: 3164.1s`, `token_usage.total_tokens: 8,567,417`. Revision/v2
  `GET /api/runs/ef86e750-...` reports `agent_count: 2`, `duration: 371s`,
  `token_usage.total_tokens: 2,388,072`. The UI's displayed "5 / 5 agents · 1m 32s" matches
  **neither** record.
- Network log (`network-validation.log`, this card's evidence) confirms
  `GET /api/runs/ef86e750-bbcd-404f-855a-fb0d5bee63f5` (the pinned v2 run) IS issued and
  returns 200 on the cold load of `/versions/2/steps` — the correct record is fetched over the
  wire, it simply never reaches what renders.

No axis-narrowing was needed: reproduced identically on cycle 1, 2 and 3 from cold navigation,
same tier (qa-admin), same account/theme/viewport throughout.

## Root cause

`frontend/src/components/preview/PreviewPanel.tsx`'s `viewingVersion`/`pinnedVersion` override
mechanism (state at line 525, `overrideActive`/`overrideContent` at 654-656) only computes and
swaps the **deliverable content** overrides — `effUserStoryContent` (656),
`effPptContent`/`effPrototypeContent` (same pattern) — for the Preview tab's rendered content.
It never computes an equivalent override for the pipeline/agent data:

- **`PreviewPanel.tsx:1422-1429`** — `<AgentThinkingTab agents={agents || []} ...
  pipelineState={pipelineState} ...>` (the Steps tab, `data-testid="tab-thinking"`). Both
  `agents` and `pipelineState` are the raw destructured props (line 512), never
  version-switched. Whatever the live/root run's `agents`/`pipelineState` were at mount time
  is what every version URL in the family renders, permanently.
- **`PreviewPanel.tsx:1394`** — `<FilesTab ... agentOutputs={agentOutputs} ...>`. Same raw
  prop, unlike the adjacent `userStoryContent={effUserStoryContent}` /
  `pptContent={effPptContent}` / `prototypeContent={effPrototypeContent}` on the same JSX line,
  which ARE version-aware (fixed by [FIX-334](20260828-2149-FIX-334.md)). This means FilesTab's
  "Final output" deliverable size is version-aware but its "Agent outputs" markdown list
  (`agentOutputs`-derived) is not — confirmed directly, contradicting this bug's own earlier
  Expected-section assumption that FIX-334 covered the Files tab fully.

Distinct from three related, already-resolved items on the same subsystem:
- **Not [ISS-300](20260828-1726-ISS-300.md) / [FIX-334](20260828-2149-FIX-334.md)** — those
  covered the raw `userStoryContent`/`pptContent`/`prototypeContent` → `eff*` swap for
  FilesTab's deliverable hero (size/name). This card is the sibling gap those left open:
  `agentOutputs`/`agents`/`pipelineState` were never given the same treatment.
- **Not [ISS-386](20260828-2228-ISS-386.md)** — that is `routes.runStepsAgent` missing a
  `version` param for deep-linking to one agent's own detail pane (has zero production
  callers). This card is the Steps tab's top-level pipeline summary/agent list, no `agentId` in
  the URL at all.
- **Not BUG-20260828-090732-runs-id-versions (closed)** — that was the version pin being
  dropped by a tab click (URL/network reverting to v1). Here the URL and network layer are
  both correct; only the render is stale.

## Expected vs actual

**Expected:** the Steps tab's pipeline summary and agent list, and FilesTab's Agent-outputs
list, should reflect the specific version pinned by the URL — v1's Steps view showing v1's own
5-agent/3164s run, v2's showing v2's own 2-agent/371s run — matching the version-aware behavior
`effUserStoryContent`/`effPptContent`/`effPrototypeContent` already provide for the Preview tab
and FilesTab's deliverable hero.

**Actual:** both version URLs render byte-identical Steps content ("5 / 5 agents · 1m 32s")
that matches neither version's real `agent_count`/`duration`/`token_usage`, even though the
correct run record for the pinned version is confirmed fetched over the network on each cold
load. Same unfixed prop path affects FilesTab's Agent-outputs list.
