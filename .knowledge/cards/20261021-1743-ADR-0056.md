## Decision

The admin Machines tab gets CPU / memory / disk / disk I/O / network / swap /
status-check history charts. They are served by a new admin-only endpoint,
`GET /api/admin/capacity/history?instance_id=&range=&period=`
(`backend/app/api/admin_capacity_history.py`), which calls CloudWatch
`GetMetricData` when an admin opens or refreshes the charts
(`backend/app/services/host_metrics_history.py`).

This is a deliberate exception to specs/014's rule that the request path never
touches AWS. The rule exists so a CloudWatch outage cannot reach the admission
gate. The exception keeps that property: the history path is separate from the
gate in code (own router module, own service module) and in data (it never
writes `capacity_state`).

## Options considered

- **A — on-demand reads (chosen).** One range query per chart view, cached 60s
  per (instance, range, period) via `HOST_CAPACITY_HISTORY_CACHE_SECONDS`, bounded
  by `HOST_CAPACITY_HISTORY_CACHE_MAX_ENTRIES`. Reuses `host_metrics._client`, so
  it inherits the tight botocore timeouts. Pagination capped at `MAX_PAGES`.
- **B — poller pre-fetch (rejected).** Keeps the rule literally intact, but the
  poller would fetch fixed ranges every tick that nobody may be viewing, and could
  not offer an arbitrary resolution.

Not built, by operator decision: gate-state history (blocking/allowing/blind
transitions are still log-only) and an alarm panel (would need
`cloudwatch:DescribeAlarms`).

## How it is bounded

- Admin-only through the shared `require_admin`; a non-admin gets 403 before
  query validation runs.
- `instance_id` must be in `current_snapshot().instances`, so the caller can never
  aim a query at an arbitrary id; unknown → 404 with no AWS call.
- Sync `def` handler, so the blocking boto3 call runs in FastAPI's threadpool,
  never on the event loop.
- Failures return 200 with per-series `error` (empty chart), never a 5xx.

## Metric sources

| Chart | Source | Why |
|---|---|---|
| CPU (100 − idle, user, system, iowait), memory, disk used % (`/`, `/var/lib/postgresql`), swap | CloudWatch Agent `VelocityAI/<Env>`, `[InstanceId]` / `[InstanceId, path]` rollups | Already published every 60s by `reconcile-host-config.sh` |
| Network in/out (B/s) | `AWS/EC2` NetworkIn/Out, Sum ÷ period | The agent `net` plugin collects loopback and Docker interfaces too |
| Disk I/O read/write (B/s) | `AWS/EBS` VolumeRead/WriteBytes summed over `ec2:DescribeVolumes` attached volumes | `AWS/EC2` DiskReadBytes is instance-store only (empty here); agent `diskio` rollup adds disks and partitions together |
| Status check | `AWS/EC2` StatusCheckFailed, Maximum | Built-in |

No IAM change: `capacity_read` already grants `cloudwatch:GetMetricData`, and
`cw_agent_describes` grants `ec2:DescribeVolumes`. Network bytes/s assumes
detailed monitoring (`modules/compute` default); with basic monitoring a
1-minute period would overstate it.

## Frontend

`MachinesPanel` composes the existing `CapacityMatrix` (rows are now selectable
buttons) with `CapacityHistoryPanel` (range 1h–90d, resolution from the
response's `allowed_periods`, Local/UTC, refresh). `useCapacityHistory` fetches
separately from the 15s table poll and refreshes every 60s while visible. Charts
use a new in-house `TimeSeriesChart` (SVG, design tokens, `role="img"` +
summary `aria-label`, min/max decimation so 21,600-point series keep spikes)
instead of adding a chart library; each chart card has its own loading, error
and "No data available" state.
