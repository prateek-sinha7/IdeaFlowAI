# ISS-784

## Description

On every cold load of `/dashboard`, three GETs each fire twice: `GET
/api/analytics/summary?range=all`, `GET /api/runs?limit=50`, and `GET
/api/workflows`. Confirmed CONFIRMED for bug **QA-PS-039** (see
`LEDGER.md` / `BUGS.md#qa-ps-039`).

## Reproduction

3/3 cold-start cycles, every cycle: navigate to `about:blank`, then
`http://localhost:3000/dashboard` (already signed in as
`qa-admin@flowinqa.com`). Verified per-load with
`performance.getEntriesByType('resource')` (not the MCP network-request log,
which does not reset across same-origin navigations in this environment):

- Cycle 1: `runs?limit=50` ×2, `analytics/summary` ×2, `workflows` ×2
- Cycle 2: `runs?limit=50` ×2, `analytics/summary` ×2, `workflows` ×2
- Cycle 3: `runs?limit=50` ×2, `analytics/summary` ×2, `workflows` ×2

100% reproducible, not intermittent — every cycle produced the duplicate,
so this is CONFIRMED outright (no axis-narrowing needed).

Evidence: `evidence/qa-ps-039/01-validate-attempt1-dashboard-loaded.png`,
`evidence/qa-ps-039/02-validate-attempt2-dashboard-loaded.png`,
`evidence/qa-ps-039/03-validate-attempt3-dashboard-loaded.png`.

## Root cause

`frontend/src/components/catalog/HomeLaunchGrid.tsx:198-211`:

```tsx
useEffect(() => {
  const fetchAnalytics = async () => {
    try {
      const token = getToken();
      if (!token) return;
      const summary = await getAnalyticsSummary(token, "all");
      setAnalytics(summary);
    } catch {
      // Tolerate analytics fetch failure; cards render without time estimate.
    }
  };
  void fetchAnalytics();
}, []);
```

A mount-only effect with no in-flight guard, abort controller, or cache. The
app runs under `next dev` (confirmed via `ps aux` — `next-server` process,
no `reactStrictMode: false` in `next.config.*`), so React 18's StrictMode
deliberately mounts → unmounts → remounts every component once in
development, firing this effect twice and producing two identical
`analytics/summary` calls back-to-back (observed ~1-3ms apart in
`performance.getEntriesByType('resource')`). The same double-invoke pattern
applies to whatever populates `reduxRecentRuns` (the `runs?limit=50` call)
and the workflows catalog fetch on the same dashboard mount — none of them
carry a dedupe guard either.

This reproduces under the exact environment QA/manual testing uses
(`localhost:3000` dev server). A production build (`next build && next
start`) does not double-invoke effects, so this specific symptom would not
appear there — but the underlying defect (no dedupe/cache on these
mount-time fetches) is real regardless of build mode; StrictMode is just
what makes it visible today.

**Discrepancy from the original report:** the reporter's DevTools capture
counted `analytics/summary` at 4× and `runs?limit=50` at 2×. All three
validation cycles here consistently showed exactly 2× for each of the three
endpoints — the reporter's 4× is most likely an artifact of the DevTools
Network panel accumulating across more than one load/interaction rather than
a single fresh navigation. The core defect — duplicate mount-time fetches
with no dedupe — is the same and is what this card targets.

## Expected vs actual

- Expected: `analytics/summary`, `runs?limit=50`, `workflows` each fire once
  per `/dashboard` load.
- Actual: each fires twice, every load.

## Impact

One of the duplicate `analytics/summary` calls took up to 3.7s in a single
cycle (recorded via `performance.getEntriesByType('resource')` during
validation), doubling backend load for that endpoint and delaying the
dashboard's analytics content.

## TEST COVERAGE — ISS-784

Manual verification only (no test suite exists for this dashboard fetch
path). Verified via `performance.getEntriesByType('resource')` across 3
independent cold-start cycles, all three showing identical 2× duplication
for `analytics/summary`, `runs?limit=50`, and `workflows`.
