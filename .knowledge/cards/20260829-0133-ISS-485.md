## What happened

[ISS-323](20260828-1810-ISS-323.md) reproduced the phantom-file defect through Format 2 of the
markdown parser (a `### heading` immediately followed by a fenced code block). The same file
(`PreviewPanel.tsx`, and its two forks, [ISS-483](20260829-0133-ISS-483.md)'s `FilesTab.tsx` and
[ISS-484](20260829-0133-ISS-484.md)'s `WorkflowHistory.tsx`) also defines a **Format 3**
"bold text before a fence" regex that shares the exact same unbounded-character-class flaw, and
it was never exercised by the hunted/validated reproduction, which only used a `###` heading.

## Root cause (INFERRED — mechanism confirmed by reading code; not yet reproduced against a live run)

In each of the three forks:

- `PreviewPanel.tsx:99` — `const boldRegex = /\*\*`?([\w./\-@][^\n`*]*\.\w+)`?\*\*\s*\n```[^\n]*\n([\s\S]*?)```/g;`
- `FilesTab.tsx:249` — identical pattern (`boldRegex`).
- `WorkflowHistory.tsx:102` — identical pattern (`r3`).

The capture group `([\w./\-@][^\n`*]*\.\w+)` has the same shape as the broken `headerRegex`/`r2`
that [ISS-323](20260828-1810-ISS-323.md) diagnosed: it starts with one path-safe character, then
`[^\n`*]*` allows **any** character — including spaces — up to a final `.\w+`, and is bounded only
by "not a newline, backtick, or asterisk" rather than by any path grammar. A bolded documentation
phrase such as `**Built with Vue.js**` or `**Powered by Chart.js**`, immediately followed by a
fenced example (a common documentation pattern — bolding a library/tool name right before showing
a usage snippet), matches this regex identically to a real bolded file path like
`` **`src/app.js`** ``. It then reaches the same `addFile`/`add` guard
(`PreviewPanel.tsx:60-68`, `FilesTab.tsx:218-224`, `WorkflowHistory.tsx:85-93`), whose only
file-shaped check is "the last path segment contains a dot" — true for "Built with Vue.js" purely
because of the dot in "Vue.js", exactly as `hasDot` accepted `"Via Node.js"` in
[ISS-323](20260828-1810-ISS-323.md).

Because Format 3 sits in the same function as the already-broken Format 2, in all three forks, a
fix that only tightens `headerRegex`/`r2` (Format 2) without also tightening `boldRegex`/`r3`
(Format 3) — in any of the three files — leaves this trigger shape reachable. This is a strong
argument for the fix's real home being one shared, path-validating `addFile`-equivalent guard
(e.g. rejecting any candidate whose captured text contains whitespace) that ALL of Format 1/2/3
route through, rather than three separate regex patches per fork.

## Expected vs actual

**Expected:** a bolded documentation phrase that merely contains a dot is never treated as a file
path, in any of the three parser forks.

**Actual (inferred):** `boldRegex`/`r3` accepts it identically to `headerRegex`/`r2`, producing the
same class of phantom Explorer entry / malformed download / polluted ZIP as
[ISS-323](20260828-1810-ISS-323.md), through a trigger shape the original hunt never tried.
