# ISS-235

## Description

INFERRED sibling of [ISS-218](20260828-1700-ISS-218.md) — same missing wiring, the
opposite-shaped symptom. ISS-218 established that clicking "Edit brief & run again" on a
FAILED run opens a **blank** composer because `handleEditBrief`
(`frontend/src/components/layout/DashboardLayout.tsx:2151-2157`) does a bare
`router.push(createRouteForType(effectiveReviseType))` with no brief handoff at all. This
card covers the other value that same missing handoff can leave behind: not blank, but a
**wrong, unrelated** brief.

`IdeaInputPage`'s `initialInput` prop is wired at `DashboardLayout.tsx:2860` as:

```tsx
initialInput={savedComposition?.brief ?? pendingHomeBrief}
```

`savedComposition` is null on the "Edit brief & run again" path (it is only populated by
the saved-workflow launch flow, `handleLaunchSaved`), so `initialInput` always falls
through to `pendingHomeBrief` here. `pendingHomeBrief` is set in exactly one place —
`handleHomeSelectFeature` (`DashboardLayout.tsx:1465-1468`):

```tsx
const handleHomeSelectFeature = useCallback((type: WorkflowType) => {
  setPendingHomeBrief(homeBrief.trim() || undefined);
  handleSelectFeature(type);
}, [homeBrief, handleSelectFeature]);
```

— the Home landing page's own brief textbox, captured right before a Home-driven launch.
It is cleared in exactly one place, `handleLaunchSaved` (`DashboardLayout.tsx:1478`,
`setPendingHomeBrief(undefined)`). It is **not** cleared by the normal run-submit path,
`handleRunPipeline` (`DashboardLayout.tsx:1606-1667`), by `handleBackNav`
(`DashboardLayout.tsx:1684-1695`), by `handleGoHome` (`DashboardLayout.tsx:1670-1677`), or
by `handleEditBrief` itself (confirmed by reading all four — none references
`pendingHomeBrief`).

`DashboardLayout` is mounted once for the life of the SPA session — its single JSX call
site (`frontend/src/app/[...view]/page.tsx:3805`) carries no `key` prop, so client-side
route pushes (exactly what `handleEditBrief` performs) do not remount it and its local
`useState` survives. So once a user types something into the Home brief box without
launching it, `pendingHomeBrief` sits non-empty in memory for the rest of the tab's
session — and `handleEditBrief` never looks at, overwrites, or clears it before handing
that same fallback slot to `IdeaInputPage`.

## Sequence that would trigger this (INFERRED, not reproduced live)

1. User opens Home, types a brief into the launcher textbox, then navigates away without
   clicking launch (e.g. to History, or picks a wizard-routed type that intercepts before
   `handleSelectFeature`'s plain-input branch).
2. `pendingHomeBrief` now holds that typed text; nothing on this path clears it.
3. Later, in the SAME tab/session, the user opens a **different, unrelated** FAILED run
   and clicks "Edit brief & run again".
4. `handleEditBrief` performs its `router.push` without touching `pendingHomeBrief` at
   all, so `IdeaInputPage` mounts with `initialInput` = the leftover Home-page draft —
   neither blank (ISS-218's reproduced case) nor the failed run's own brief.

## Why the root cause implies this

ISS-218's fix target is the same missing piece of state plumbing this card exercises:
`handleEditBrief` sets none of `pendingHomeBrief`, so whatever that variable already
holds — `undefined` (ISS-218's cold-session case, observed) or a leftover string (this
card's case, not yet observed) — is what silently surfaces. Same mechanism, different
starting value; not a new defect, a sibling shape of the one already confirmed.

**What would confirm or refute it:** in one browser tab/session, type a non-trivial brief
on the Home page, navigate away without launching, open a FAILED run, click "Edit brief &
run again", and read `document.querySelector('textarea').value` — CONFIRMED if it equals
the Home-page draft text rather than `""` or the failed run's own brief.

## Expected vs Actual

- **Expected:** "Edit brief & run again" always shows either the failed run's own brief
  (once ISS-218 is fixed) or, failing that, an empty field — never a different,
  previously-typed draft's text.
- **Actual (inferred):** if `pendingHomeBrief` holds a leftover value from an earlier,
  un-launched Home-page draft in the same session, that unrelated text silently appears
  in its place.

## Fix note

The same fix location as ISS-218 (`handleEditBrief`,
`frontend/src/components/layout/DashboardLayout.tsx:2151-2157`) closes this too, IF the
fix explicitly SETS `pendingHomeBrief` to the viewed run's own brief (e.g.
`viewedRun?.input || submittedBrief` — the same source `runHeaderTitleFull` already uses
at `DashboardLayout.tsx:2398`) rather than leaving it untouched. Setting it unconditionally
overwrites whatever stale value was sitting there, so one change closes both ISS-218 and
this card. A fix that instead threads the brief through the URL/query string alone, without
also clearing/overwriting `pendingHomeBrief`, would leave this card's path open even after
ISS-218's reported symptom is fixed.
