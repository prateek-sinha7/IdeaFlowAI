## Symptom

A `ppt` override containing one blank custom agent saved successfully, rendered correctly in
Advanced, and failed **every** launch:

```
POST /api/runs  agent_ids: ["custom-agent:1845dxd-wy6v9o","ppt-brief-analyst","ppt-composer","ppt-validator"]
400 {"error":"Invalid agent_ids for 'ppt': ['custom-agent:1845dxd-wy6v9o']","code":"invalid_agent_ids"}
```

## Root cause

The blank `custom-agent` template mints a dynamic `custom-agent:<instance_id>` node. That id has
no `AGENT.md` on disk and is absent from the static roster `allowed_custom_agent_ids(pipeline)`
builds, so the launch ingress rejects it. `load_agent_spec` would fail on it too.

This is the same shape the inline `manifest` field was added for — its own comment says those ids
"can never appear in the static allow-list `agent_ids` is checked against".

## Decision and fix

The allow-list is a real entitlement fence (its docstring records a reverted cross-pipeline
bypass, KAN-75), so it was **not** widened. Instead the affordance was removed where it cannot
work: `AgentLibrary` gained `allowCustomAgentTemplate`, default `true`, passed `false` from
`LaunchWizard`. The composer canvas keeps the template — a user-defined step is the point there,
and those launch via `USER_WORKFLOW_MANIFEST`, which has no flat allow-list to fail.

An earlier attempt resolved the override *before* the allow-list so such ids could pass. It was
**reverted** — the user's call was that an override should reuse built-in agents only, which keeps
the entitlement boundary untouched.
