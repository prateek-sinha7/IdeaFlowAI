# ISS-663

## Title

The ref-validation gate that guards three sandbox read endpoints accepts any tag in the
sandbox's shared git repository — not just a tag this run's own family created — so an
authenticated owner of ANY run can list, zip, or read sandbox content pinned at an unrelated,
repo-wide tag (e.g. `deploy-prod-20260603-014226`). Sibling of QA-PS-008 ([ISS-652](20260917-1244-ISS-652.md)).

## Status: INFERRED — mechanism confirmed by code, not yet exercised live

Filed from QA-PS-008's confirmed root cause (Defect 1), not from an independent reproduction
against a running backend. See "What would confirm this" below.

## Why QA-PS-008's root cause implies this

QA-PS-008's Defect 1 ([ISS-652](20260917-1244-ISS-652.md)) is: `LocalWorkspace.list_tags()`
(`backend/app/agents/runtime/local.py:875-891`) runs bare `git tag --list` and returns every
tag reachable in the sandbox's git repository, with no scoping to the calling run's family.
That defect was diagnosed from its effect on `GET /{run_id}/sandbox/refs` (the dropdown feed).
But the SAME `list_tags()` call is also the allow-list for `_validate_ref`
(`backend/app/api/run_files.py:604-641`):

```python
def _validate_ref(ref: str, sandbox: RunSandbox) -> str:
    list_tags_fn = getattr(sandbox, "list_tags", lambda: [])
    try:
        valid_tags: list[str] = list_tags_fn()
    except Exception:
        valid_tags = []
    if ref not in valid_tags:
        raise HTTPException(status_code=status.HTTP_400_BAD_REQUEST, detail="invalid ref")
    return ref
```

Its own docstring states the intent plainly: "The only refs this API will ever serve are real
version tags (`v1`, `v2`, …)" — i.e. this run family's own tags. But because `valid_tags` is
the repo-wide list, `ref not in valid_tags` only rejects a ref that doesn't exist ANYWHERE in
the shared history — it does nothing to confine the ref to THIS run's family.

`_validate_ref` gates three separate endpoints, confirmed by reading each call site:

- `GET /{run_id}/sandbox?ref=` (`run_files.py:704`) — ref-scoped file **listing**
  (`git ls-tree`, via `list_files_at_ref`).
- `GET /{run_id}/sandbox/zip?ref=` (`run_files.py:805`) — ref-scoped **archive** download
  (`git archive`, via `archive_at_ref`).
- `GET /{run_id}/sandbox/file?ref=` (`run_files.py:905`) — ref-scoped single-file **read**
  (`git show`, via `read_file_at_ref`).

All three call `_validate_ref(ref, sandbox)` before touching git, and all three trust it to
confine `ref` to something that legitimately belongs to `run_id`'s own version history. Since
`list_tags()` is repo-wide (Defect 1) and every family member's `/sandbox*` route resolves to
the SAME chain-root sandbox (`_resolve_chain_root_or_404`), any of these endpoints will happily
list/archive/read the shared sandbox's tree AT AN ARBITRARY, UNRELATED TAG for any run the
caller is authorized to view — `_resolve_owned_run` confirms ownership of `run_id`, but nothing
confirms the *ref* belongs to that run's family.

## Expected (once reproduced)

`_validate_ref`'s effective allow-list is the calling run family's own `git_tag` values only
(the same set `FIX-516`/`ISS-652`'s proposed fix would use to scope the dropdown) — a ref for
another tag, even a real one elsewhere in the shared repo, is rejected with 400 exactly like a
made-up string is today.

## Actual (inferred, not yet observed)

`GET /api/runs/{owned_run_id}/sandbox/file?path=<any-existing-path>&ref=deploy-prod-20260603-014226`
(or `v0.2.0`, or any of the other leaked tags from [ISS-652](20260917-1244-ISS-652.md)'s
reproduction) is expected to return 200 with whatever content existed at that path at that
unrelated historical commit — instead of the 400 the docstring's stated intent implies — for
any run the caller owns, since every one of those tags is a member of `list_tags()`.

## What would confirm this

1. Reproduce QA-PS-008 far enough to capture one of the leaked tag names (`v0.2.0` etc. — see
   [ISS-652](20260917-1244-ISS-652.md)'s reproduction).
2. Pick a completed run this test user owns and a path known to exist somewhere in the shared
   sandbox history (or just any path — a 404 from `git show` still proves the ref itself was
   ACCEPTED, which is the point).
3. Call `GET /api/runs/{run_id}/sandbox/file?path=<path>&ref=<leaked-tag>` directly (curl or
   the network tab) and confirm the response is not the 400 `"invalid ref"` that a truly
   unscoped string produces.

## Superseded by ISS-671 (2026-09-17)

This card's mechanism claim — `_validate_ref` trusts `list_tags()` as its allow-list with no
family scoping, exposing all three ref-scoped read endpoints — is correct and carried
forward unchanged. What was understated is the "Actual" impact above: the content served at
a leaked tag is not "an unrelated tag in the shared sandbox history," it is **this project's
own host source checkout** at that tag (see [ISS-671](20260917-1345-ISS-671.md)'s corrected
root cause). [ISS-671](20260917-1345-ISS-671.md) also adds the restore/write path
([ISS-672](20260917-1350-ISS-672.md)) and the legacy-chain read path that share this same
defect and were not covered here.
