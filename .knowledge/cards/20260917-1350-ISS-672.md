## Title

`POST /{run_id}/restore` (`backend/app/api/runs.py:2347`) is the WRITE-side twin of
[ISS-671](20260917-1345-ISS-671.md)'s read-side leak, and it is more severe: the same
unscoped `list_tags()` validates the requested tag, and the operations that follow don't
just read the host checkout, they run `git restore --worktree` and `git commit` with `cwd`
inside it.

## Status: INFERRED — mechanism confirmed by reading every step of the call chain; the
actual restore was NOT executed against a live sandbox, deliberately, to avoid writing a
real commit into this checkout's own git history

## Why ISS-671's root cause implies this

[ISS-671](20260917-1345-ISS-671.md) establishes that any `LocalWorkspace` git call against
a sandbox with no `.git` of its own resolves against the enclosing checkout, because
`_git()` (`local.py:372-390`) and friends set only `cwd`, and that
`RunSandbox.has_git`/`list_tags()` never checks whether `.git` actually exists
(`sandbox.py:546`, `:896`). `restore_version` walks straight through every stage of that
chain, one level deeper than the read endpoints:

1. **Sandbox construction, no override** (`runs.py:2427-2432`):
   `RunSandbox(current_user.id, revision_root_id, current_run_id=run_id,
   runs_root=settings.RUNS_ROOT)` — same pattern as every read endpoint in
   [ISS-671](20260917-1345-ISS-671.md), `has_git` defaults `True` regardless of whether
   `revision_root_id`'s directory has a `.git`.
2. **Tag validation trusts the same unscoped list** (`runs.py:2308-2328`,
   `_validate_tag_for_restore`): exact-match against `sandbox.list_tags()`. When the
   sandbox has no `.git`, that list is the host checkout's own tags (e.g. `v0.2.0`), and
   `body.tag = "v0.2.0"` passes as if it were this run family's own version — identical
   defect to `_validate_ref` in [ISS-671](20260917-1345-ISS-671.md), just the restore
   endpoint's private copy of the same gate.
3. **Materialize runs two more unscoped `_git()` calls** (`sandbox.materialize_tree_at_ref`
   → `local.py:1174-1203`): `self._git("rev-parse", f"{ref}^{{commit}}")` resolves the
   validated tag to a real commit SHA **in the host repo** (it exists there — that's why
   validation passed), then
   `self._git("restore", f"--source={commit_sha}", "--worktree", "--no-overlay", "--", ".")`
   runs with `cwd` still the sandbox directory, still inside the host checkout. This writes
   the tree tracked at that host commit (restricted by git's cwd-relative `.` pathspec to
   whatever the host repo tracks under that subdirectory's path) into the live working
   directory, and `--no-overlay` removes anything tracked at the host's current HEAD but
   absent from the target commit, at that same path.
4. **Commit runs inside the same directory** (`runs.py:2443` onward → `engine.py:348`
   `commit_in_sandbox`, "the ONE security-gated commit primitive for every sandbox Git
   commit" → `sandbox.commit_all` → `local.py:821-838`, `self._git("add", ...)` /
   `self._git("commit", "-m", message)`): with no ceiling and no `.git` in the sandbox, this
   is a real `git add` + `git commit` against the **host repository's actual history**, not
   a sandboxed one.

This is a write, not a read: worst case is a spurious commit landing in the real
development checkout's git history (or, depending on what the target path happens to track
at the host commit vs. the host's current HEAD, working-tree files under that path being
overwritten or removed by `--no-overlay`). That is qualitatively worse than
[ISS-671](20260917-1345-ISS-671.md)'s read-only disclosure, hence its own card and
`severity: critical` rather than folding it into the same one.

## Expected (once confirmed)

`POST /{run_id}/restore` on a sandbox with no `.git` of its own fails closed (tag
validation rejects every tag, since a ceiling-respecting `list_tags()` returns `[]`) —
exactly the fix direction [ISS-671](20260917-1345-ISS-671.md) already proposes at the
`_git()` layer. No separate fix is needed here beyond applying that same ceiling; this
card exists to make sure the fixer's blast-radius check includes the write path, since a
fix scoped only to `run_files.py`'s read endpoints would leave this open.

## Actual (inferred, not yet observed)

`POST /api/runs/{owned_run_id}/restore` with `{"tag": "<leaked host tag>", ...}` against a
revision-root sandbox with no `.git` is expected to pass validation and reach
`materialize_tree_at_ref` / `commit_in_sandbox`, executing real `git restore` and
`git commit` subprocesses with `cwd` inside the host checkout.

## What would confirm this — SAFELY, without touching this repo's real history

Do NOT reproduce this against the live backend with this checkout as the enclosing repo —
a successful repro is, by definition, a real commit (or working-tree mutation) in this
project's own git history. Confirm instead with a throwaway fixture, the same shape as the
offline probe [ISS-671](20260917-1345-ISS-671.md) already ran for the read path:

1. In the scratchpad, create a throwaway outer git repo with a tagged commit and no
   `RUNS_ROOT` involvement.
2. Nest an empty directory inside it (no `.git`) to stand in for a `RunSandbox` root; point
   a `LocalWorkspace`/`RunSandbox` at that nested directory directly (bypassing the API) to
   keep the blast radius inside the throwaway fixture.
3. Call `materialize_tree_at_ref(<outer tag>)` then `commit_all(...)` against it and inspect
   the OUTER throwaway repo's log/`git status` afterward — a new commit there (not in the
   nested directory, which has no `.git` of its own to receive one) confirms the mechanism.
4. Only after the ceiling-directory fix lands, re-run the same fixture and confirm both
   calls now raise "not a git repository" instead.

## Confirmed, then resolved by FIX-522 (2026-09-17)

Confirmed with this card's own safe recipe, never against this checkout.
`TestRestoreWritePathStaysInTheSandbox` in
`backend/tests/unit/test_run_files_ref_family_scope.py` builds a throwaway outer repo tagged
`deploy-prod-leaked` and nests a never-`git init`-ed `RunSandbox` inside it. Pre-fix, run with
`--runxfail`: `RunSandbox.commit_all` committed into the OUTER repo, moving its `HEAD` from
`638b84cd` to `1c679a28`. That happened because `RunSandbox.commit_all` checks `.git` only
after the workspace commit returns `no_change`. The write hazard is therefore real, and it is
`git add -A` over the enclosing repo's whole tree, not just the sandbox path.

[FIX-522](20260917-1449-FIX-522.md) closed it with the ceiling this card named. Post-fix, both
`materialize_tree_at_ref` and `commit_all` raise, the outer `HEAD` is unchanged, and the host
file stays untracked (XPASS strict). No `runs.py` change was needed. This checkout has 0
commits authored by `Flowin Runtime`, so the hazard had not fired here.
