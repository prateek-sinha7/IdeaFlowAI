# FIX-722

## What was wrong

This fix is for bug report QA-KB-061. The root cause comes from the 2026-10-02 analysis on
[ISS-949](20261002-0107-ISS-949.md) ("Analysis (QA-KB-061, 2026-10-02)"). It was not re-derived here. Every cited
line was re-read before editing and the card held; line numbers had moved by about 20. Line numbers below are as of
this fix, in the uncommitted tree.

- `launch_run` hands `_launch_run_core` the chain-ADMITTED source id: `_admitted_source_id = _chain_admission.source_id`
  (`backend/app/api/run_commands.py:3817`), passed as `source_workflow_run_id` (`:3834`). `admit_chain_launch` answers
  `declaration_gate` with `source_id=None` for every manifest without `deliverable.chains_from`, which is all ten
  `*_revision` manifests.
- `_launch_run_core` linked the revision parent from that same parameter:
  `_resolve_owned_parent_run_id(db, source_workflow_run_id, user.id) if pipeline_type.endswith("_revision")` (HEAD
  `:3015`). With `None` the resolver returns `None` without a query, so every REST-launched revision was minted with
  `parent_run_id` NULL: its own sandbox instead of the family's, no `previous_run` seed for the `revises_existing`
  types, `revision_ordinal` 1, and a separate root in History.
- The raw request id already reached `_launch_run_core` as `request_source_workflow_run_id` (`:3848`), but only the
  duplicate-context strip read it (`:2982`). The regression is `e7305f9dd` (2026-09-10).

The card's other five red tests were stale, and the card gives their direction as "the tests bend to the app":

- B: `test_foreign_source_drops_the_link_but_still_launches` and `test_unknown_source_drops_the_link_but_still_launches`
  posted `user_stories`, which declares `chains_from: true`, so admission answers 404 as
  `.kiro/specs/sandbox-git-versioning-v2/requirements.md:570-572` (Requirement 6 AC 1) requires.
- C: three driver stubs sent `agent_id` on `agent_start` only. `_apply_terminal_output_columns` keys rows on
  `(agent_id, task_id)` since `77b52bb3d`, as the engine emits them.
- [ISS-987](20261002-0440-ISS-987.md): three tests called `_mint_revision_row` without the `caller_tier` keyword it
  requires since `b2a621f84`.

## What changed, and why there

**App (cause A), one expression.** `_launch_run_core`, `run_commands.py:3011-3025`: the revision parent now resolves
from `request_source_workflow_run_id or source_workflow_run_id` (`:3019`), still through the owner-checked
`_resolve_owned_parent_run_id`, still only when `pipeline_type.endswith("_revision")`, under a two-line comment citing
ISS-949. `_launch_run_core` is the join point every launch passes through and already owned this resolution. Its other
caller, `run_trigger_workflow` (`backend/agents/execution_engine/kernel_services.py:1664`), passes
`parent_run_id_override` and no request id, so it is unaffected. Nothing else reads the request id: `source_run_id`
(`:3065`), `chain_source_run_id` (`:3224`) and the `chain_v2_accepted` flag (`:3237`) still read the admitted id. No
parameter, no import, no workflow-name branch.

**Tests.** These changed because the card says their expectation was misstated (the tests bend to the app), not
because they were red:

1. B, `test_rest_run_launch_api.py`: the two drop-the-link tests now post `user_stories_revision` (`:875`, `:898`), so
   they exercise the owner-checked resolver for real. Two new cases pin the chaining contract for `user_stories`: a
   foreign source answers 404 and only the seeded parent row exists (`:915`); an unknown source answers 404 and no row
   exists (`:934`). The section header no longer cites `run_commands.py:1204` / `body.source_workflow_run_id` and states
   both contracts. All four carry `@pytest.mark.issue("ISS-949")`.
2. C: `agent_id` added to every event after `agent_start` in `test_driver_persists_full_agent_history_like_ws`
   (`"a1"`), to `agent_complete` in `test_driver_persists_model_id_and_prices_non_circular` (`"a1"`), and to
   `agent_chunk` and `agent_complete` in `test_rest_revisions_api.py::test_driver_happy_path_persists_output_columns`
   (`"user-stories-revision-agent"`, the id on that test's `agent_start`). The revisions-file edit is the one ISS-949
   shares with [ISS-900](20261001-2132-ISS-900.md) (QA-KB-073). It is done here, once. QA-KB-073 still owns ISS-900's
   closure, its `test_run_row_token_usage.py` and ISS-1013; its fixer only needs to verify this edit.
3. ISS-987: `caller_tier` passed in the four calls, matching the tier each test gives its user: `"basic"` at
   `test_phase5_chaining.py:252`, `:329`, `:344` and `"pro"` at `test_chain_context_v3.py:142`. `_mint_revision_row`
   keeps the keyword required.

The `xfail(strict=True)` marker on `test_owned_source_links_the_child` is left in place for the 6-verifier.

## Not fixed

- [ISS-985](20261002-0432-ISS-985.md) (open): the `chain_v2_accepted` response flag still reads the admitted id
  (`run_commands.py:3237`). The frontend therefore still raises the false "backend version mismatch" notice for a
  REST-launched revision. The card's fix is one line at that flag. It asks for the owner's call on a chain into a
  non-chaining workflow before that notice is suppressed, and no test pins the flag yet.
- [ISS-986](20261002-0432-ISS-986.md) (open, now live): with the parent link restored, a REST-launched revision
  JOINS its family without `_mint_revision_row`'s family lock, 409 active-revision guard or `source_run_id` write.
  This is the behaviour before `e7305f9dd`. A guard needs the design call that card leaves open: (a) mint through
  `_mint_revision_row`, or (b) move the three legacy frontend handlers to `postRevision`. It also needs the product
  answer on Requirement 6 AC 16 versus Requirement 22 AC1/AC2 for `source_run_id`. The two-overlapping-runs race is
  still INFERRED, not run.
- ISS-949's fix plan also asked for a test over every `*_revision` type. It was not added: the fix is one
  type-agnostic expression, and the analyzer's probe, re-run on the real code, covers 9 of 10 types. Add it when the
  parent link gains a type-specific branch.
