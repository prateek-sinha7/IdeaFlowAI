# ISS-1072

Register bug QA-KB-095.

## Reproduction (3/3, cold start each time: localStorage cleared, fresh login as admin@velocity.ai, direct navigation)
1. `GET /api/runs/0f62f7bc-d3a2-4748-8004-0b534e1741ae/sandbox/refs` returns 200 with no refs.
2. Open `/runs/0f62f7bc-d3a2-4748-8004-0b534e1741ae`.
3. Network: `GET .../sandbox?ref=v1` returns 400 (`invalid ref`) in attempts 1, 2 and 3.

No cycle dependency: it fired on the first load every time.

## Conditions
Admin tier, direct deep link, old completed prototype_v2 run, light default theme. Not varied further because 3/3.

## Expected vs actual
Expected: no `?ref` (or the unpinned tree) when the sandbox lists no refs; no 4xx. Actual: 400 on every load.

## Suspected area (unverified, for analysis)
`PreviewPanel.tsx` computes `displayRef` (about line 890) from `sandboxSelectedRef` or the member's `git_tag`, and
`_validate_ref` (`run_files.py` about 870-882) accepts only tags that exist in the sandbox git repo. The run's DB
`git_tag` is probably "v1" while the sandbox has no such tag. Related: [ISS-893](20261001-2120-ISS-893.md) (400 on a swept workspace).

## Evidence
`evidence/qa-kb-095/01-validate-attempt1-run-page.png`, `02-...attempt2...`, `03-...attempt3...`.
Visible preview breakage not assessed.

## Analysis (QA-KB-095, 2026-10-07)

**Evidence status.** Root cause CONFIRMED four ways: a source read, a live probe of the running backend (`:8000`, pid 4327, started
21:12, after FIX-727), an offline render of the real components, and an in-process route probe on the repo's own fixtures. The husk's
origin is INFERRED (timing evidence, no request log). The analyzer did not drive a browser. All of it is in `evidence/qa-kb-095/04..13`.

### The chain (CONFIRMED)

1. **DB.** Run `0f62f7bc` is a completed `prototype_v2` with `git_tag = 'v1'`. Its family has a second member, `b7bdf6a3`, a
   `prototype_revision` that FAILED (`git_tag` NULL). `GET /api/runs/0f62f7bc/family` returns exactly those two
   (`04-analyze-db-rows-and-family-api.txt`).
2. **The page treats the root as "older".** `latestId` is the last member by `revision_index`, whatever its status
   (`PreviewPanel.tsx:867`), so the failed v2 is the newest and the root's own page is an older member. `displayRef` is then its DB tag
   (`PreviewPanel.tsx:890-891`):
   `const displayRef = sandboxSelectedRef ?? (activeMember && activeMember.id !== latestId ? activeMember.git_tag ?? null : undefined);`
   No pin is involved: `/runs/0f62f7bc` carries no `/versions/{n}` segment.
3. **The header resolve asks for it.** The deliverable effect (`PreviewPanel.tsx:1448-1511`) runs once the run is complete and calls
   `resolveRunDeliverable(token, activeRunId, declared, displayRef ?? undefined)` (`:1502`), which lists
   `getRunSandbox(token, runId, ref)` (`api.ts:1630`) and so sends `GET /api/runs/0f62f7bc/sandbox?ref=v1` (`api.ts:1582-1585`). The scratch
   render shows exactly that call while `getRunSandboxRefs` answers `[]` (`11-analyze-scratch-run.txt`, probe A). The controls, where the run
   is the family's newest member, send no ref (probes B and C).
4. **The sandbox is an empty directory.** `runs/2d626ad9-.../0f62f7bc-...` exists, holds nothing and has no `.git`. Birth 2026-10-07
   17:37:20, mtime the same, ctime 17:43:34 (`05-analyze-disk-husk.txt`). It is called a "husk" below.
5. **The API reads a husk as live.** `list_sandbox` decides `expired = not sandbox.root.is_dir()` (`run_files.py:941`), which is false for an
   empty directory, so ISS-893's guard `if ref is not None and not expired:` (`:948`) lets `_validate_ref` run. `list_tags()` answers `[]`
   with no git call because there is no `.git` (`sandbox.py:938`), so `ref not in valid_tags` and the route raises
   `HTTPException(400, "invalid ref")` (`run_files.py:878-882`). The same sandbox answers `GET /sandbox` with `200 expired:false files:[]`.
6. **The page swallows it.** The effect's `catch` (`PreviewPanel.tsx:1505-1508`) leaves `deliverableFile` null, so `canHeaderDownload` is
   false (`:1534`) and the Download button renders disabled (`RunHeader.tsx:532-536`, `cursor-not-allowed bg-brand/50`: the pale button in
   `01-validate-attempt1-run-page.png`). The only trace is the 400 in the network tab.

Run `87e02c32` is a six-member family of the same owner whose older members also carry DB tags, so its pages send the same `?ref=v1` and
get no 4xx. The page's request is therefore not wrong by itself; the husk is what turns it into a 400
(`06-analyze-live-probe-matrix.txt`). The in-process probe reproduces both columns on the repo's `env` fixture
(`13-analyze-scratch-backend-run.txt`), and a third case, a live sandbox with files and a `.git` but no `v1` tag, keeps answering 400.
That is correct and must stay (`test_tagless_git_sandbox_rejects_ref_400`).

### Where the husk came from (INFERRED, strong)

[ISS-996](20261002-0500-ISS-996.md) documents the mechanism. Before [FIX-727](20261007-1837-FIX-727.md), `GET /sandbox/refs` on a swept run
built the workspace (`_ws()` -> `ensure()` -> `mkdir`) and left an empty directory with a fresh mtime. The run completed on 2026-09-28 and its failed
revision ended on 2026-09-29 07:50, so the family directory was past the 168 h TTL (`config.py:406`) by 2026-10-06 at the latest. The directory was born at 17:37:20, three minutes before the report's 17:40, and its
ctime moved at 17:43:34, the pattern of repeated old-code `ensure()` calls (each one re-chmods). FIX-727 was committed at 18:42 (`b9d2099d9`,
`sandbox.py` edited 18:29) and the server now answering started at 21:12. Three cold page loads at 21:29 each mount `RunHeader`, which fetches
`/sandbox/refs`, and the directory's ctime is still 17:43:34, so the current server does not touch it. No request log names the creating call.

The husk is not a one-off in kind. [ISS-992](20261002-0458-ISS-992.md) (open) records two generators FIX-727 did not close:
`ReadOnlySandbox.list_prefix` and `resolve_ref_commit` re-create a swept chain source, so starting a chained run from an expired run should leave
an empty directory behind (probed at the sandbox level there; the chain-admission entry points were read, not run). And the sweeper judges a directory by its own mtime (`sandbox.py:1460`), so a husk is not removed for another
168 h: this one is not eligible before 2026-10-14 17:37.

Of the 16 older family members that carry a DB tag, 11 sit in a live sandbox that lists the tag, 4 sit in a properly swept family (expired

### Fix, and where it belongs

**The 400 is produced on the server, for a state the server already has a name for.** [ISS-893](20261001-2120-ISS-893.md) /
[FIX-691](20261001-2149-FIX-691.md) made "swept, so expired" win over ref validation. A husk is a swept sandbox that something re-created, so
this is the same family of fix, with one definition used everywhere:

- Give `RunSandbox` one expiry predicate, a read-only property next to `list_files` (`sandbox.py:746`): the workspace is gone when the
  directory is absent OR holds no entry at all, `not self.root.is_dir() or not any(self.root.iterdir())`.
- Replace the five inline `not sandbox.root.is_dir()` tests with it, keeping each site's own response (listing: the `expired` flag; zip,
  file, figma: 404 "Workspace expired"; restore: 404 "Sandbox not found").
- Effect: the listing answers `200 expired:true` for the husk as it does for an absent directory, so the Workspace tab says "Workspace
  expired" again, and zip, file and figma answer 404. No frontend change is needed for the reported symptom.
- Ceiling to record with a `ponytail:` comment: a LIVE run's directory is empty between `sandbox.ensure()` (`engine.py:4416`) and
  `git_init_sandbox()` (`engine.py:4427`), and for longer if git init fails (`has_git` degrades to False, `engine.py:4441`). A listing in that
  window reads as expired. Acceptable: the Workspace tab's Refresh re-lists. Do not add a run-status lookup to the routes for it.
- Optional, same area: let `sweep_expired` remove an empty, unprotected run directory regardless of its mtime, so existing husks go at the
  next sweep (at most 6 h) instead of after 168 h.

Why not the other candidates:

- **Loosen `_validate_ref`, or drop `?ref` for older members.** `_validate_ref` is the Requirement-16 security gate and is fail-closed against
  the sandbox's real tags (`run_files.py:846-883`; the leaked-tag history is ISS-663 / ISS-671). Dropping the ref would read the live tree,
  which is the NEWEST member's files ([FIX-717](20261002-1243-FIX-717.md)'s locked constraint). Neither is a fix.
- **Reconcile in the frontend only.** It would remove the request for this run, but the page would still say `expired:false` over an empty
  workspace, four routes would still 400 a husk for any other client, and it cannot help ISS-992's new husks. It is the right fix for the other
  state, a live sandbox that lost its tag: [ISS-1087](20261007-2244-ISS-1087.md) and [ISS-1090](20261007-2246-ISS-1090.md).
- **Delete the husk.** It clears this run until the next husk, and it is a data change the analyzer does not make. Worth doing alongside the
  code fix; the sweeper would remove it itself after 2026-10-14 17:37.

### What a naive fix would get wrong

- Treating `.git` absence, rather than emptiness, as expired. A pre-v2 legacy sandbox keeps its payload under `.chain/` with no `.git` and must
  stay live ([ISS-992](20261002-0458-ISS-992.md) Part 2). A live sandbox with files and no tag must keep answering 400.
- Carrying this in `list_tags` or `has_git`. [FIX-727](20261007-1837-FIX-727.md)'s constraints stand: `list_tags` returns `[]` before `_ws()` is
  built, `RunSandbox.__init__` keeps `has_git=True`, and `commit_all` / `materialize_tree_at_ref` still raise without a `.git`.
- Reordering `list_sandbox` so validation runs before expiry again. `if ref is not None and not expired:` (`run_files.py:948`) is ISS-893's fix.
- Fixing only `list_sandbox`. It is the one route the page calls on load, which is why the report names it; the other four read a husk the same way.
