# ISS-966

**Register source:** `QA-KB-048` in root `LEDGER.md` / `BUGS.md` (sibling, derived during its analysis on 2026-10-02).
**Root card:** [ISS-943](20261002-0037-ISS-943.md) holds the root cause (the wizard's plan-completion effect) and the fix location.
**Claim status:** the engine seam and `launch_run`'s pre-mint check are CONFIRMED offline by a hermetic probe
(`evidence/qa-kb-048/05-analyze-engine-seam-probe.py.txt`, output `06-analyze-engine-seam-probe-output.txt`: temp sqlite
database, scripted planner, `execute()` stopped at its first `pipeline_start`; no Bedrock, no Postgres, no server, no run; it calls
`presort_specs` and `ExecutionEngine.execute` directly, not `launch_run`).
That a real browser launch of a saved workflow behaves the same is INFERRED: nothing was launched. Whether it SHOULD behave
this way is not an engineering question, see "Decision needed".

## What is broken

**Condition.** A saved prototype / ppt / ppt_v2 workflow whose `agent_ids` is a STRICT SUBSET of the built-in's compiled plan,
opened through `/workflows/{id}/run`, with the wizard sending that roster on Continue. (Sending it is what [ISS-943](20261002-0037-ISS-943.md)'s
fix makes the wizard do; today the wizard sends the full plan.)

**Expected.** The run executes the saved roster and the progress chip reads N/N.

**Actual (probe, working tree on top of `024c03ef8`).**

| roster sent as `agent_ids` | `launch_run` pre-mint check | engine `pipeline_start.agent_count` | mint-time `agent_count` |
|---|---|---|---|
| ppt_v2: brief-analyst, composer, deck-qa (last step dropped) | ok | 4, all four agents, plus INFO "roster expanded from plan" | 3 |
| prototype: specify, plan, analyze, build (last step dropped) | ok | 5, all five agents, plus the same INFO line | 4 |
| ppt_v2: brief-analyst, composer, code-generator (QA step dropped) | `UnsatisfiableComposition` -> 422 `workflow_unsatisfiable` | not reached | not minted |
| prototype: plan only (the QA-KB-048 validator's roster) | `UnsatisfiableComposition` -> 422 `workflow_unsatisfiable` | not reached | not minted |

The mint-time column is read from `run_commands.py:3020`; the probe computes `len(agents)` and does not call `_launch_run_core`.

So after the ISS-943 fix, a satisfiable subset still executes the FULL built-in plan while the header chip counts N, and an
unsatisfiable subset is refused before the mint.

## Mechanism (read at file:line)

- A wizard launch carries no `user_workflow_id` (the launch params are built at `frontend/src/components/layout/DashboardLayout.tsx:1422-1442` without it; [ISS-920](20261001-2221-ISS-920.md) records the same), so `launch_run` takes `LaunchSource.FILE_PIPELINE`
  (`backend/app/api/run_commands.py:3284`). A non-empty `agent_ids` goes through the allow-list and becomes
  `agents = [load_agent_spec(aid) for aid in agent_ids]` (`:3520-3550`), then `presort_specs(agents)` (`:3563-3570`), which raises
  `UnsatisfiableComposition` and 422s a set whose consumer lacks its producer.
- The mint records `agent_count = len(compiled.steps) if compiled is not None else len(agents)` (`:3020`), and `compiled` is `None`
  here, so it records N. `_launch_run_core(agents=agents, compiled=compiled)` is called at `:3863-3867`.
- The engine compiles the BASE plan (`engine.py:4965-4969`: `compile_for_run(pipeline_type)` because there is no
  `compiled_override`) and then runs the roster seam (`:5004-5007`):

```python
_plan_ids = {s.agent_id for s in compiled.steps}
_roster_is_partial = bool(agents) and {a.id for a in agents} < _plan_ids
if compiled.steps and (not agents or _roster_is_partial):
    ...
    agents = self._specs_from_plan(compiled.steps)
```

  A strict subset of the plan is, to this seam, a partial roster, and the caller's explicit selection is replaced. The comment above it
  (`:4990-5003`) says why: ppt_v2's registry roster used to be 2 of 4 and the DAG resolver rejected the run.
- The no-`agent_ids` branch of the same function already completes a partial REGISTRY roster itself (`run_commands.py:3617-3622`,
  with the comment at `:3610-3611` naming the "0/2 for a run that executes four" chip), so the engine clause is no longer what
  protects that path. Since then `get_pipeline_agents("ppt_v2")` was also completed from the manifest (`registry.py:181-198`).

## Why the root cause implies it

[ISS-943](20261002-0037-ISS-943.md)'s expected value is "Continue launches the saved roster". Its fix makes the launch DRAFT carry that. The
server then decides again, and the user-visible symptom in the QA-KB-048 title ("launches the full built-in roster") survives
for satisfiable subsets. The reported reproduction (the launch draft) is satisfied by the frontend fix alone; the run is not.

## The UI half: removal is offered where it cannot stick

`AgentsPopup.tsx:177-181` lists every prototype and ppt (v1) agent as LOCKED, with the comments "all core, none removable".
`getRole` (`:210-248`) returns `"optional"` for any pipeline absent from its `pipelinePrefixes` table (`:243-244`), and that table has
no `ppt_v2` or `prototype_v2` entry, so `handleRemove` (`:2822-2826`) lets the user remove ANY ppt_v2 agent. The only wizard where a
user can trim and save a built-in's roster is therefore ppt_v2, which is the one whose subsets the server expands or refuses.
(INFERRED from the handler; the Remove button was not clicked.) prototype_v2 is the degenerate case: its steps are `custom-agent:*` instances
that the wizard strips from `agentIds` (`LaunchWizard.tsx:1028-1041`, with the comment at `:1037-1040`: the plan IS the roster and the popup edits
`selections`, not membership), so a removal there never reaches the server and the plan always runs in full, while the same Remove is offered.

## Decision needed

May a wizard launch (`pipeline_type` plus `agent_ids`, no `user_workflow_id`) of a built-in file pipeline run a strict subset of
that pipeline's steps?

Evidence for yes: [ADR-0008](20260811-ADR-0008.md) ("the caller's list wins whenever it has one"); `LaunchWizard.tsx:1028` calls `agent_ids` "a SUBSET selector";
the spec-016 override honours a user's lineup by replacing the plan (`run_commands.py:3653-3680`).
Evidence for no: `engine.py:4990-5003` deliberately treats a strict subset as partial; [ISS-877](20261001-2110-ISS-877.md) recorded that conflict as
"documentation drift ... an architect's call, so it is recorded here rather than carded"; the v1 core agents are locked.

| option | what changes | consequence |
|---|---|---|
| A. yes, honour the subset | `launch_run` hands the engine a plan restricted to the selected steps, so roster equals plan | ISS-943's fix delivers the user's intent end to end; Remove on ppt_v2 works |
| B. no, the plan is authoritative | lock every wizard agent (add ppt_v2 and prototype_v2 to `getRole`) and treat shorter saved rosters as legacy to complete | ISS-943's expected value changes: the completion effect is right and the QA-KB-048 test must be inverted |
| C. leave the server, label the UI | none in the backend | the screen shows N and the run executes the full plan; the silent-expansion class of ISS-877 stays visible to users |

## Where the fix belongs (if A)

Not per caller. One block in `launch_run` after the allow-list and presort (`run_commands.py:3550-3570`): the launch layer already
owns pre-expansion for the no-`agent_ids` branch (`:3617-3622`) and for overrides (`:3653-3680`), and it is the only layer that
knows whether a roster is a caller's explicit selection or a registry roster, which the engine seam (`engine.py:5004`) cannot tell
apart. Do not branch on a workflow name (INV-1). Whether a plan can be safely restricted to a subset (its `depends_on` and route
edges) was not prototyped here.

## What settles it

- Offline, cheap: in `backend/tests/integration/agents/test_roster_seam_log.py`, `_records_until_pipeline_start` with
  `_PIPELINE = "ppt_v2"` and three of the four agents. Today `agent_count == 4`; under option A it is 3.
- Browser, without a paid run: after the ISS-943 fix, hold `POST /api/runs` with `page.route`, open a saved ppt_v2 workflow with a
  3-agent roster, click Continue, read `agent_ids`, then abort the request.

## Not affected

A user with an ENABLED override (the server replaces `compiled` and `agents` with the override's steps, `run_commands.py:3653-3680`,
so a trimmed lineup runs as saved); launches without `agent_ids` (`:3593-3622`); composed `custom` workflows (their plan is derived
from the picks, per the comment at `engine.py:5000-5003`).
