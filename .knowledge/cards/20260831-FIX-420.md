## What was wrong

`SecuritySection`'s `toggleEmailMfa` handler was gated only by `disabled={pending}` on the
toggle button. `setPending(true)` is a React state update — the real `disabled` attribute only
flips after React re-renders and commits, leaving a pre-commit window where rapid back-to-back
clicks each re-enter the handler and fire concurrent `enableEmailMfa`/`disableEmailMfa`
requests. Because the handler also reads `emailOn` to decide direction, two clicks in the
same task can send conflicting requests whose out-of-order responses leave the displayed MFA
state inconsistent with the server's real state.

## Root cause

`frontend/src/components/settings/SecuritySection.tsx` — `toggleEmailMfa` (line ~112): the
handler had no synchronous in-task lock, only the React-commit-gated `disabled` prop.

## What changed and why there

**`frontend/src/components/settings/SecuritySection.tsx` only.**

1. Added `useRef` to the React import (was `useCallback, useEffect, useState`).
2. Added `const togglingRef = useRef(false)` immediately before the `toggleEmailMfa`
   callback — a synchronous in-task lock that does not wait for a render commit.
3. At the top of `toggleEmailMfa` (before any state mutation or API call):
   ```
   if (togglingRef.current) return;
   togglingRef.current = true;
   ```
   The early-return on the `!token` path also resets `togglingRef.current = false` before
   redirecting, so a session-expiry event does not wedge the button permanently.
4. In the `finally` block alongside `setPending(false)`:
   ```
   togglingRef.current = false;
   ```

`disabled={pending}` is left in place — it still carries the visible "Saving…" state. The
ref carries correctness. Pattern is identical to FIX-345's `submittingRef` in `login/page.tsx`.
