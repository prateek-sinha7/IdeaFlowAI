## Reproduction

Confirmed 3/3, every cycle from a cold start (fresh `/dashboard` -> `/library` navigation,
no soft re-click, no warm state carried over):

- **Cycle 1** — Agents tab (default `/library`), typed `qqqqnomatch12345` into
  `input[name='library-search']`. Grid area goes completely blank; category pills (`All 94`,
  `App Builder 15`, …) stay visible and unchanged.
- **Cycle 2** — deep-linked directly to `/library?tab=skills` (cold entry path, not a
  click-through), typed `zzzznonexistentquery`. Same blank grid under the Skills category pills.
- **Cycle 3** — deep-linked to `/library?tab=hooks`, typed `xyznohooksmatch999`. Same blank grid
  under the Hooks category pills.

All three cycles used `qa-admin@flowinqa.com`, light theme, default viewport. No console errors
or failed network requests observed in any cycle — the filtering is client-side and works
correctly (the grid genuinely empties, and clearing the search restores the cards), it is purely
the empty-state rendering that is missing.

## Page / route / component

- Page: Library (Agents / Skills / Hooks catalog)
- Routes: `/library`, `/library?tab=skills`, `/library?tab=hooks`
- Component: `frontend/src/components/library/LibraryPage.tsx`

## Root cause

`LibraryPage.tsx` computes `filteredAgents` (line 601), `filteredSkills`/`activeSkills`
(lines 620-628) and `filteredHooks` (line 631) from `searchQuery`/`skillSearch`/`hookSearch`,
then each tab's grid renders with a bare `.map()` over the filtered array
(`filteredAgents.map(...)` at line 735, `activeSkills.map(...)` at ~line 818, `filteredHooks.map(...)`
at line 914) with no `length === 0` branch anywhere in the file. When the array is empty the
`.map()` correctly returns `[]`, so React renders nothing — no conditional empty-state markup
exists to render instead. The header text (`94 agents · 186 skills · 8 hooks · tap any item to
see its capabilities`) is a static, unfiltered count computed independently of the search, so it
gives no signal that a search even ran.

## Blast radius (analyzer pass, 2026-08-28)

Re-confirmed the root cause by reading `LibraryPage.tsx` directly (matches the lines above:
`601-609` agents filter, `620-629` skills filter/`activeSkills`, `631-637` hooks filter; render
sites `732`/`735` agents, `793`/`815`/`818` skills, `893`/`911`/`914` hooks — each ternary branches
only on `*Status === "loading"`, never on the resulting array's `length`).

- **Consumers of `LibraryPage`:** exactly one — `DashboardLayout.tsx:10` imports it and mounts it
  for `mainView === "library"` (confirmed via `grep -rn "LibraryPage" frontend/src/`). No other
  call site exists, so the defect cannot be reached through any other route/component.
- **Within the file:** the same missing branch is independently present at all three grid render
  sites (agents `735`, skills-active `818`, hooks `914`) — this is exactly what the hunter/
  validator already reproduced 3/3 across all three tabs; no additional in-file render site shares
  the flaw.
- **Repo-wide check:** grepped every other search/filter-driven component
  (`Sidebar.tsx`, `AuditTab.tsx`, `WorkflowPickerModal.tsx`, `DesignSystemPicker.tsx`,
  `TemplateGallery.tsx`, `PPTTemplateGallery.tsx`, `WorkflowHistory.tsx`, `AppBuilderPreview.tsx`,
  `SavedWorkflowsPage.tsx`, `AgentLibrary.tsx`, `AgentsPopup.tsx`, `AgentSkillsPicker.tsx`) for the
  same "filter then bare `.map()`" shape. Every one of them already has its own `length === 0` /
  "no X found" branch (e.g. `Sidebar.tsx:180`, `WorkflowPickerModal.tsx:292`). `LibraryPage.tsx` is
  the only surface currently missing it — this is file-local, not a repo-wide gap. One earlier
  instance of the identical mistake was already fixed elsewhere in this codebase
  ([FIX-081](20260721-FIX-081.md), `AgentsPopup.tsx`, 2026-07-21: `{length > 0 && (...)}` with no
  else branch) — confirms this is a recurring **per-file** oversight pattern here, not evidence of
  a currently-broken shared component.
- **Derived (unreproduced) siblings**, filed because the same array-emptiness mechanism has two
  more paths than the reported search-box trigger: [ISS-335](20260828-2040-ISS-335.md) (category/
  event filter alone reaches the same unguarded map, no search text needed) and
  [ISS-330](20260828-2041-ISS-330.md) (a failed fetch, `status === "failed"`, falls through to the
  identical unguarded map since only `"loading"` is ever special-cased).

## Fix location

Belongs **inside `LibraryPage.tsx`**, not a new shared `components/ui` primitive — every other
empty-state instance in this codebase (see blast radius above) is implemented locally in its own
component, and this module's own architecture card documents that a single-file page is
proportionate here (`MOD-frontend-src-components-library.md` — "no server state, no cross-page
reuse"). All three grids already share one shape (`status === "loading" ? skeleton : list.map`)
and already share the "which value is the active search" logic (`LibraryPage.tsx:675-680`), so the
smallest diff that fixes every tab through one place is a single local helper (e.g.
`renderEmpty(label, activeQuery)`) called from the three sites (`735`, `818`, `914`), extending
each ternary to a third branch keyed on the array's `length`, not on whether a search string is
present — see [ISS-335](20260828-2040-ISS-335.md) for why keying on "search present" instead of
"array length" would silently miss the category-only trigger. Pasting near-identical JSX three
times would be the wrong shape; one guard per call site is fine only if it is the *same* guard.

## Expected vs actual

- **Expected:** a zero-result search shows explicit empty-state messaging (e.g. "No agents match
  'qqqqnomatch12345'" plus a way to clear the search), on all three tabs.
- **Actual:** the grid area renders completely blank — no text, icon, or affordance — on all
  three tabs, identically.
