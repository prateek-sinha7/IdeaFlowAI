## Why this must also be broken

This is the inverse of BUG-20260828-085830-runs-cancelled: instead of a genuine failure being
reported as the earlier terminal state (ISS-316: cancelled), a genuine SUCCESS is reported as
the earlier terminal state (failed) — same function, same missing "latest attempt wins"
reasoning, opposite direction.

`_reconcile_terminal_status` (`backend/app/api/run_commands.py:748-838`) computes `failed` the
same unscoped way it computes `degraded`
([ISS-436](20260828-2253-ISS-436.md)) — a bare `any()` over the run's ENTIRE durable tail
(`store.read_events(run_id, after_seq=0)`, line 780), with no attempt-boundary filter:

```python
failed = any(e.type == "pipeline_failed" for e in events)
```

A run whose FIRST attempt genuinely fails leaves a `pipeline_failed` event permanently in the
tail. Resuming a failed run is an established path — RunChatLane's failed-run "Reopen & fix"
button calls the same `handleResumeRun`/`onRelaunch` as ISS-316's cancelled-run "Run Again" (per
ISS-236 in the index). If that resumed attempt genuinely and cleanly succeeds (a fresh
`pipeline_complete`, no `status="degraded"`, no new `pipeline_failed`), the decision ladder
still sees the STALE `failed=True` from the original attempt:

```python
if cancelled and not resume_supersedes:
    new_status = "cancelled"
elif degraded:
    new_status = "degraded"
elif completes and not failed:
    new_status = "completed"
else:
    new_status = "failed"
```

`cancelled` is `False` (never cancelled) → branch 1 skipped. `degraded` is `False` (no degraded
complete anywhere in this scenario) → branch 2 skipped. Branch 3,
`elif completes and not failed:`, evaluates `completes=True` (the resumed attempt's clean
complete exists) **and** `not failed` — but `failed` is `True` (stale, from the original
attempt), so `not failed` is `False`, and the whole branch-3 condition is `False`. Control falls
through to the D2 fail-safe:

```python
else:
    new_status = "failed"
```

The run that just fully succeeded — with a real deliverable the same way a clean launch would
produce one — is persisted `"failed"` forever. This is arguably more severe than ISS-316's
original report: a genuinely completed run with a usable deliverable is buried behind a false
"Failed" badge on every surface that reads `status` (detail page, Run History list, API),
exactly the way ISS-316 documented for the cancelled case.

## Expected vs actual

**Expected:** once a resumed run's latest attempt produces a clean `pipeline_complete` (a later
attempt than the original failure), `_reconcile_terminal_status` should persist
`status="completed"` — the resumed attempt's real, current outcome, the same "latest attempt
wins" principle ISS-316's own fix is meant to establish.

**Actual (INFERRED — not yet independently reproduced):** `status` stays `"failed"` forever,
because `failed` is computed over the full multi-attempt tail with no reattempt-boundary filter,
and the D2 `else` fail-safe unconditionally wins once `not failed` is false.

## What would confirm or refute this

Seed a run whose first attempt ends `pipeline_failed`, click "Reopen & fix" / "Run again", and
let the resumed attempt complete cleanly with no agent errors. `GET /api/runs/{id}` should show
`status: "completed"`; a hit shows `"failed"` instead while the deliverable/output columns
(`_persist_resume_output_columns`, called immediately after this ladder at line 833) may still
correctly reflect the successful resume — the same kind of badge/body contradiction ISS-316's
own evidence captured for the cancelled case. A miss would mean `completes and not failed`
resolves differently than this trace predicts, refuting this card without affecting ISS-316,
[ISS-435](20260828-2253-ISS-435.md), or [ISS-436](20260828-2253-ISS-436.md).

## Where the fix belongs

Same function, same file: `_reconcile_terminal_status`
(`backend/app/api/run_commands.py:748-838`), not either caller
(`_drive_user_resume:740` or `stop_run_driver`, `backend/app/api/run_shutdown.py:330-332`). A
fix that only adds "a later `pipeline_failed` supersedes an earlier cancellation" (ISS-316's
literal fix shape) does not touch this branch at all — `failed`, like `degraded`
([ISS-436](20260828-2253-ISS-436.md)), needs the same `reattempt_seqs`-bounded "is this event
from the LATEST attempt" filter `resume_supersedes` already applies to `complete_seqs`. All four
flags (`cancelled`, `failed`, `degraded`, `completes`) read from the same tail and feed the same
ladder — the fix belongs in that one shared computation, scoping every flag to the latest
attempt symmetrically, not in a patch that only special-cases the one combination ISS-316
reported.
