## Summary

**Sibling of [ISS-202](20260828-1409-ISS-202.md), derived from its root
cause — INFERRED for this specific run (no export file was captured as
evidence), CONFIRMED as a code mechanism (the exporter file was read in
full).**

ISS-202 shows `AuditTab.tsx`'s `rows` state (`useState<AuditRow[]>`, set at
`AuditTab.tsx:588`) contains 96 fabricated `category: "gate"` /
`fineCategory: "gate"` entries built from ordinary `audit_logger` telemetry,
each carrying identical boilerplate `detailRows` (`Action: allowed` /
`Outcome: continue`, no per-row attribution) once `buildHookDetailRows`
(lines 151-182) falls through its fallback path.

The Audit tab's own header copy (quoted in the parent bug's ledger entry)
promises an "Immutable, owner- and workspace-attributed log" that is
"attributed **and exportable**" — and ships a Download menu backed by
`exportAuditCSV(rows, ...)` / `exportAuditJSON(rows, ...)` from
`frontend/src/lib/exporters/auditExporter.ts`. Reading that file in full
(lines 1-100) confirms both functions are unconditional pass-throughs:

- `exportAuditCSV` (lines 83-91): `collectHeaders(rows)` unions every row's
  own keys, then writes one CSV line per row via `escapeCsvCell(row[key])`
  for every key — no filtering, no re-derivation, no category check.
- `exportAuditJSON` (lines 96-98): `JSON.stringify(rows, null, 2)` — the
  exact in-memory `AuditRow[]` serialized verbatim.

Neither function distinguishes a real `gate_events` row from a fabricated
`hook_runs`-derived row; both consume whatever `AuditTab` already computed.
Since that computation is what ISS-202 shows is wrong, the exported file is
wrong in the same way: a CSV/JSON downloaded "for compliance review" (the
tab's own framing) would show 96 `category: gate` rows with identical
`Action`/`Outcome` values and no real governance checkpoint behind them —
the same misrepresentation ISS-202 documents on-screen, now persisted to a
file a reviewer may treat as an audit-of-record.

## What would confirm or refute this

1. On the same completed run ISS-202 reproduced against
   (`b9feac1c-ec21-4531-8ba7-bb391786993e`), open the Audit tab, click
   Export -> CSV (and separately -> JSON).
2. Inspect the downloaded file: count rows/objects with `category: "gate"`
   and confirm they include `audit_logger`-derived entries with the
   identical fallback `Action`/`Outcome` values ISS-202 documents on-screen.
3. If the export path turns out to filter or re-derive categories
   differently from the on-screen render, this card is refuted.

## Expected vs Actual

**Expected:** an exported audit record should carry the same real-vs-fake
distinction as a correctly-fixed on-screen view — real gates only in the
Governance/Gate category, `audit_logger` telemetry in an `activity`
category, and per-row detail specific to that event.

**Actual (predicted, unverified as an exported file):** the export
inherits ISS-202's fabrication verbatim, because it is a direct serialization
of the same `rows` state with no independent logic.

## Fix implication

No separate export-side fix is needed — `exportAuditCSV`/`exportAuditJSON`
are correct, generic serializers. Fixing ISS-202 at its source (the
hook_runs merge/`deriveFineCategory` call in `AuditTab.tsx`) corrects the
`rows` state itself, and both exporters inherit the fix automatically since
neither has its own categorization logic to also patch.

## Evidence

Code-only — `frontend/src/lib/exporters/auditExporter.ts` read in full;
no browser reproduction (no export file was actually downloaded and
