## What happened

On `/create/user-stories` (any built-in workflow launched via `LaunchWizard` reproduces the
same), opening the "Advanced N agents" button's Advanced Workflow Configuration modal with no
agent node selected shows the right-rail Workflow tab. All six of its controls — "Smart planning"
switch, "Confirm requirements first" switch, "Deliverable" strategy select, its dependent "Output
file name" text input and "Output format" select, and "Internet access" switch — render with the
HTML `disabled` attribute set, with no lock icon, no tooltip, no `title` attribute, and no
explanatory copy anywhere in the panel. The only affordance on each control is an `(i)` info icon
whose tooltip explains what the setting *does*, never why it cannot be changed. The sibling
"Brief instruction" textarea in the same panel, and an agent node's own "Tools" tab
(Read files/Write files switches), are genuinely interactive in the identical modal — proving the
app can and does render both editable controls and explained lock states elsewhere (e.g. the
canvas's "Core = locked" agent badge), just not here.

## Root cause

`frontend/src/components/workflow/LaunchWizard.tsx:234-240` seeds `declaredRunConfig` from the
built-in workflow's own declared configuration "so the Advanced rail shows what this workflow
actually does instead of CanvasView's blank-canvas defaults," and the surrounding comment states
plainly: "Read-only — no `onRunConfigChange` is forwarded, so nothing here is editable or sent;
it exists purely so the panel stops misreporting." This is a deliberate design choice — a
built-in's declared run config should not be silently editable from the launch panel — but the
mechanism that enforces it is a blanket `disabled` gate with no accompanying UI signal.

In `frontend/src/components/workflow/composer/CanvasView.tsx`, every Workflow-tab control is
gated on the presence of the callback prop:
- Smart planning switch: `disabled={!onRunConfigChange}` (~line 1624)
- Confirm requirements first switch: `disabled={!onRunConfigChange}` (~line 1639)
- Deliverable strategy select: `disabled={!onRunConfigChange}` (~line 1668)
- Output file name input: `disabled={!onRunConfigChange}` (~line 1703)
- Output format select: `disabled={!onRunConfigChange || formatLocked}` (~line 1719)
- Internet access switch: `disabled={!onCapabilitiesChange}` (~line 1750)

Because `LaunchWizard` never forwards either callback for a built-in launch, all six render
unconditionally disabled, but the `disabled` attribute is the only signal — there is no
conditional lock icon, tooltip, or copy keyed off `!onRunConfigChange`/`!onCapabilitiesChange` to
tell the user this is intentional read-only state versus a broken control. Contrast:
`ComposerPage.tsx:1135-1137` DOES forward both callbacks (`onCapabilitiesChange={setCapabilities}`,
`onRunConfigChange={setRunConfig}`) when the same `CanvasView` Workflow tab is used from the
Composer, where the controls are genuinely editable — confirming the disabled state is specific
to the LaunchWizard entry path, not a CanvasView-wide default.

## Reproduction (3/3, cycle 1 every time)

Each attempt from a cold start: fresh nav to `/dashboard`, then fresh nav to
`/create/user-stories`, click the "Advanced N agents" button. No agent node selected (default
state = Workflow tab). Verified via direct DOM property reads, not screenshots:

```js
document.querySelectorAll('[role="switch"]')  // Smart planning / Confirm requirements first / Internet access
  .map(s => s.disabled)                        // all true, all 3 attempts
document.querySelector('select[name=deliverable-strategy]').disabled  // true, all 3 attempts
document.querySelector('select[name=output-format]').disabled          // true, all 3 attempts
document.querySelector('input[name=output-filename]').disabled         // true, all 3 attempts
document.querySelector('textarea[name=brief]').disabled                // false, all 3 attempts (control)
```

No narrowing was needed — reproduced identically on cycles 1, 2, and 3, cold-load each time,
qa-admin tier, default viewport and theme (the disabled state is DOM-attribute driven, not a
styling/timing race).

## Expected vs actual

**Expected:** Workflow-level settings rendered as interactive-looking switches/dropdowns should
either be editable, or — if intentionally locked to a built-in's declared configuration — should
carry a visible reason (lock icon, disabled-state tooltip, or explanatory copy), consistent with
the canvas's own agent-level "Core = locked" affordance.

**Actual:** All six controls are unconditionally disabled via `!onRunConfigChange`/
`!onCapabilitiesChange` with zero explanation, so a user cannot tell whether this is deliberate
read-only behavior for a built-in workflow or a broken/loading control.
