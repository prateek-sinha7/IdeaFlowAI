# ISS-940

## What happened

Derived while analysing QA-KB-037 (root card [ISS-758](20260922-1421-ISS-758.md)). Same mechanism, an async
user selection that applies its result after an `await` with no check that it is still the latest selection,
in a second place that switches versions. NOT reproduced (source read only); reachability is niche.

## Root cause (CONFIRMED by source read; the behaviour is INFERRED)

`frontend/src/components/history/WorkflowHistory.tsx:389-407`:

```ts
const handleSelectVersion = useCallback(async (memberId: string) => {
  const token = getToken();
  if (!token) return;
  setLoadingDetail(true);
  try {
    const full = await getWorkflow(token, memberId);
    if (onOpenRun) {
      // …(two comment lines)
      onOpenRun(full);
    } else {
      setSelectedRun(full);
      setSelectedOutput(full.output || null);
    }
  } catch (err) {
    console.warn("[revision-family] version fetch failed", err);
  }
  finally { setLoadingDetail(false); }
}, [onOpenRun]);
```

The shell wires `WorkflowHistory`'s `onOpenRun` to
`(run) => { onSelectWorkflowRun?.(run); setMainView("execution"); router.push(routes.runDetail(run.id)); }`
(`DashboardLayout.tsx:3053`), so each RESOLVED pick navigates. Two picks A then B whose responses arrive B, A
both navigate, and the user ends on A.

The page-level guard cannot catch it. `handleSelectWorkflowRun` claims its switch generation at ENTRY
(`beginSwitchGeneration(run.id)` in `page.tsx`; module-scope helpers at `page.tsx:102-121`,
[ISS-780](20260922-1604-ISS-780.md) / [ISS-779](20260922-1602-ISS-779.md)) and, because History hands over the
full record (`run.input !== undefined`, [ISS-856](20260923-0028-ISS-856.md)), does no fetch inside it, so
`isSwitchGenerationStale` has nothing to trip on. The generation is taken in arrival order, after the race has
already been decided.

Same shape, lower plausibility, not carded separately:

- `WorkflowHistory.tsx:373-376`, `handleSelectRun`'s `forChain` branch: `setSelectedRun(full)` after
  `await getWorkflow`.
- `DashboardLayout.tsx:2907-2909` (notification) and `:3461-3463` (toast): `getWorkflow(...).then(
  onSelectWorkflowRun)` after a synchronous `router.push(routes.runStream(id))`.

## Reachability

`handleSelectVersion` is passed as `onSelectVersion` to `RunDetailPage` (`WorkflowHistory.tsx:684`), which
hands it to the version timeline chips (`RunDetailPage.tsx:363-372`). That pane is rendered only under
`if (selectedRun)` (`WorkflowHistory.tsx:589`), and with `onOpenRun` set `selectedRun` is reachable only
through a row's "Chain" action (`handleSelectRun(run, { forChain: true })`, `WorkflowHistory.tsx:341-361`).
Niche: two chip clicks inside one fetch window.

## Expected vs actual

- **Expected:** the last version chip clicked is the one the user lands on.
- **Actual (INFERRED):** the pick whose response arrives last wins, so a slow earlier pick can navigate the
  user to a version they already moved away from.

## Why the root cause implies it

Identical mechanism to ISS-758, one layer up: the handler awaits, then applies, and nothing compares the
selection it started for with the latest one. The History handler also feeds the shell's navigation, which
turns a stale apply into a stale route change rather than a stale panel.

## Fix direction (not applied)

A click-order guard inside the handler: a `useRef` counter bumped per call and checked before `onOpenRun` /
`setSelectedRun` (same shape as the ISS-758 agreed fix). No `onOpenRun` caller changes.

deferred `getWorkflow` promises resolved out of order, asserting the later pick is the last `onOpenRun` call.

## Fixed — QA-KB-037 (fixer, 2026-10-02): [FIX-711](20261002-0215-FIX-711.md)

The fix direction above was applied in `WorkflowHistory.tsx`:

- `const selectGen = useRef(0);` (`:391`);
- `const gen = ++selectGen.current;` as the first statement of `handleSelectVersion` (`:393`);
- `if (gen !== selectGen.current) return;` right after the await (`:399`), before `onOpenRun` / `setSelectedRun`.

The stale call still reaches its `finally`. Observed: `WorkflowHistory.staleVersionPick.test.tsx` XPASS on 3 of 3 runs.
As a plain `it` it failed before the edit (`expected 'false' to be 'true'`) and passes after. The 11 existing
`WorkflowHistory*.test.tsx` files give results identical to a HEAD copy of the file.

**Correction to "Reachability" above.** The fixer grep shows this path is not reachable from any user path at HEAD;
it is not merely niche. Commit `dfd167387` ([FIX-584](20260922-0925-FIX-584.md), 2026-09-22, an ancestor of HEAD
024c03ef8) deleted the row "Chain" action and its `handleChainAffordance`. That handler was the only caller of
`handleSelectRun(run, { forChain: true })`, and `grep forChain` in non-test source now finds only the definition
(`WorkflowHistory.tsx:341`, `:354`, `:358`). DashboardLayout always passes `onOpenRun` (`DashboardLayout.tsx:3053`), so
`selectedRun` is never set and the detail pane and its version chips never mount. The guard is defensive: it covers the
`!onOpenRun` branch that the tests exercise, and any future way back into that pane.
[ISS-953](20261002-0154-ISS-953.md) records the matching stale test.

**Split out.** The two `DashboardLayout.tsx` handlers listed above under "Same shape, lower plausibility" (notification
`:2907-2909`, toast `:3462-3464`) are live UI with no fix direction, so they are now [ISS-954](20261002-0215-ISS-954.md)
(open). `handleSelectRun`'s forChain branch (`:371-377`) has no caller and is not carded.
