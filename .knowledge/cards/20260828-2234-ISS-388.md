## Summary

Sibling of [ISS-285](20260828-1745-ISS-285.md) (root: BUG-20260828-014416-runs-id-preview-full),
derived from the same confirmed mechanism applied to a different `headerRunState` branch.
`reopenTabFor` (`frontend/src/app/[...view]/page.tsx:228-244`) has no case for the
`"run-preview-full"` screen — its switch only maps `run-steps`/`run-steps-agent`/`run-files`/
`run-workspace`/`run-audit`, falling through to `undefined` for everything else, including the
one route whose entire purpose is forcing the Preview tab open. For a TERMINAL-failed run with no
deliverable this makes `/preview/full` land on Audit (ISS-285's confirmed finding). The same gap
means a run that is still ACTIVELY BUILDING when `/preview/full` is opened should, by the
identical mechanism, land on the Steps ("thinking") tab instead — a different branch of the exact
same ternary, not a different bug.

## Mechanism (INFERRED from source; not independently re-driven in a browser)

`frontend/src/components/preview/PreviewPanel.tsx:812` —
`defaultTabDiscriminator = terminalFailureNoDeliverable ? "failed" : headerRunState`. For a
building run, `isStillRunning` is true, so `terminalFailureNoDeliverable` is false and
`defaultTabDiscriminator` becomes `headerRunState`, which resolves to `"building"` (or `"gate"`/
`"clarify"` mid-build) per the ternary at `:768-774`. The merged deep-link/default-tab effect's
target selection at `:830-834`:

```
defaultTabDiscriminator === "failed" ? "audit" :
headerRunState === "complete" ? "preview" :
(headerRunState === "gate" || headerRunState === "clarify" || headerRunState === "building") ? "thinking" :
null
```

sends a building run to `"thinking"` (Steps) unconditionally — with no check of which ROUTE asked
for the tab. Unlike the terminal-failed case, `visibleTabs` does NOT drop `"preview"` while
building (`terminalFailureNoDeliverable` is false at `:737-739`), so the Preview tab is present
and could render its own `isStillRunning` branch ("Building your deliverable…",
`PreviewPanel.tsx:1258-1266`) — but the dedicated force-preview route never reaches it, and
nothing on screen indicates a substitution occurred, mirroring ISS-285's missing-affordance
symptom exactly.

## Expected vs actual

- **Expected:** `/preview/full` on a building run either lands on Preview (showing the existing
  "Building your deliverable…" in-progress placeholder, which the tab already supports) or shows
  an explicit message that Preview isn't ready yet — not a silent, unexplained jump to Steps.
- **Actual (inferred, not yet reproduced in a browser session):** the route lands on Steps with no
  indication that Preview was requested and substituted.

## Why the root cause implies this

Identical shape to ISS-285: `reopenTabFor` never learns that `run-preview-full` wants `"preview"`
specifically, so PreviewPanel's generic per-state default silently wins regardless of which state
that default happens to be. ISS-285 proved the `"failed"` branch (→ Audit); this card is the
`"building"`/`"gate"`/`"clarify"` branch (→ Steps) of the exact same unconditional ternary. A fix
that teaches `reopenTabFor` to request `"preview"` for `run-preview-full`, and teaches
PreviewPanel's deep-link consumer to render an honest fallback when the requested tab isn't in
`visibleTabs`, resolves this card and ISS-285 together — they are the same defect surfacing on two
different `headerRunState` values, not two separate fixes.

**Status: INFERRED.** Not independently reproduced in a browser this pass — flagging what would

state) and confirm which tab is `[selected]`.
