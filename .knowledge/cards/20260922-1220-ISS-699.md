# ISS-699

## Description

In a custom workflow (`/create/custom`, run detail `/runs/{id}`), a downstream
step whose agent prompt assumes it can persist its own output files (e.g. the
Documentation agent producing a README, API docs, and an ADR as separate
files) never receives `write_file`/`edit_file` — no custom-workflow step ever
does, per ISS-698/QA-PS-019. Rather than failing cleanly, the agent discovers
mid-run that the tool is missing, narrates that discovery in first person, and
falls back to emitting the file content inline as chat-style prose. That
narration — not clean deliverable text — is what appears on the Steps tab
(testid `tab-thinking`) for the step, and lands in Files/Preview too whenever
that step is the pipeline's last one (the `streamed_text` deliverable
strategy takes the final step's raw output verbatim).

This is bug **QA-PS-021** (`BUGS.md#qa-ps-021`).

subset, itself worth a separate look but not this card's claim), then
`POST /api/runs/{id}/answers` with `{"responses": [], "skip_clarification":

## Expected vs actual

Expected: each step either produces its declared file-based deliverable via
`write_file`, or (if that tool genuinely should not be granted) returns its
content directly with no process narration mixed in.

Actual: the step's `.output` (what the Steps tab and, for the last step, the
Preview/Files tabs render) opens with first-person exploration/tool-absence
narration — "Let me...", "Now I'll...", "Since I cannot use write_file,
I'll compose them as responses to the user:" — before any real content, on
3/3 cold-start cycles, deterministic given the root cause below (not
conditional on timing, account tier, or theme).

## Root cause

Same mechanism as **ISS-698** (`BUGS.md#qa-ps-019`):
`backend/agents/execution_engine/engine.py`, `_apply_selections`
(~line 12767) has no `tools` overlay branch, so no step in any custom
workflow is ever granted `write_file`/`edit_file`, regardless of the
composer's per-step "Write files" selection or the agent's declared role.
A step whose prompt (e.g. `documentation-agent`, which is written to
`write_file` a README/API-doc/ADR as separate deliverables) assumes that
tool exists discovers its absence mid-generation and compensates by
narrating the discovery and emitting the file content as inline prose
instead — the model doing its best under a missing capability, with no
distinction in the engine between "clean output" and "ran into a missing
tool and improvised."

## Relationship to QA-PS-020

QA-PS-020 (`BUGS.md#qa-ps-020`, still `Open`, not yet validated) is the
**upstream** symptom: a writer step's own output never reaches disk because
it has no `write_file`. QA-PS-021 is the **downstream consequence**: a later
step either can't find that file, or (as reproduced here) lacks the same
tool itself, and both cases surface as narrated/diagnostic content instead
of a clean deliverable. Both trace to the same `_apply_selections` gap
already documented in ISS-698, whose fix direction (add a `tools` overlay
branch) would resolve this card's symptom too — this card exists to record
the downstream content-quality effect specifically, since it is visible
even on steps the user never intended to grant write access to.
