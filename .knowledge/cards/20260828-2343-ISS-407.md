## Summary

Derived while analyzing [ISS-298](20260828-1729-ISS-298.md), by checking the inverse of its
mechanism — if the `error==="quota"` branch over-reports failure (shows a dead end even when
valid data exists), does the plain (no-param) branch under-report it?

`frontend/src/app/preview-fullscreen/page.tsx`'s plain-route branch (the `setTimeout` block,
lines 52-76) reads `sessionStorage.getItem("__app_preview__")` and, on any of three distinct
failure conditions, calls `router.replace(routes.runHistory())` and returns WITHOUT ever calling
`setState` to a distinct error state:

- line 58: `!raw` (no `__app_preview__` key present at all)
- line 63: `!data.files?.length` (parsed but the `files` array is empty)
- line 70: the surrounding `catch` (a thrown error, e.g. `JSON.parse` on corrupt data)

`PageState` (line 14) is exactly `"checking" | "loading" | "ready" | "quota"` — there is no
`"error"` / `"empty"` member. All three exits above silently navigate the tab away to Run History;
the user who clicked "Full Screen" watches the tab they opened disappear into an unrelated page
with no message explaining that anything failed, let alone why.

This is the structural mirror of ISS-298: there, the `"quota"` branch unconditionally SHOWS an
error message even when valid data IS present (false positive). Here, the plain branch
unconditionally SUPPRESSES any message even when something genuinely IS wrong — missing, empty,
or unparseable sessionStorage (false negative) — silently routing the user elsewhere instead. Both
branches are read directly from the same `useEffect` (`page.tsx:36-76`) that ISS-298's root cause
lives in.

## Why the root cause implies this

Confirming ISS-298's root cause required reading this `useEffect` end to end, including the
branch this card describes. The "inverse case" question ("if quota over-reports, does the
no-param path under-report?") is answered directly by that same read, not by a separate
investigation: line 58/63/70 all fall through to the identical silent `router.replace(...)`, with
no state distinguishing "nothing to show, quietly leaving" from any of ISS-298's cases.

## Confidence

CONFIRMED mechanism — the three failure exits and the absence of an error `PageState` are read
directly at `page.tsx:56-72` and line 14. INFERRED as an currently-observed user complaint: no
independent browser reproduction of a genuine missing/corrupt-sessionStorage scenario (e.g. a
browsing context that partitions/blocks sessionStorage sharing, or the URL opened directly without
ever going through `handleFullscreen`) was run in this pass. That reproduction is what would
confirm this as a live defect rather than a documented gap in the same code ISS-298 already
proves is under-tested.

## Reproduction (to run)

1. Sign in `qa-admin`. Clear the key: `sessionStorage.removeItem('__app_preview__')`.
2. Navigate directly to `http://localhost:3000/preview-fullscreen` (no query params — simulating
   a bookmarked/copy-pasted URL, or any context where the opener's sessionStorage write never
   reached this tab).
3. Observe: after ~100ms the tab redirects to Run History with zero message — no toast, no
   banner, nothing explaining why the requested full-screen preview did not load.
4. Compare to `?error=quota` in the same "nothing usable in sessionStorage" circumstance: that
   branch always explains itself (even though ISS-298 shows it can do so wrongly, when data DOES
   exist). This branch explains nothing even though absence is exactly when an explanation is
   warranted.

## Where this bears on ISS-298's fix

If the fixer restructures `page.tsx`'s `useEffect` so the quota and plain branches share one
sessionStorage-read (the natural fix location for ISS-298), the plain branch's three silent exits
sit in the same function and are a small addition to cover in the same pass — not mandated here,
just flagged as adjacent.
