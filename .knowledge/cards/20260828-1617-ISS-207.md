## Derivation (INFERRED — not yet reproduced)

Sibling of [ISS-198](20260828-1400-ISS-198.md), same root mechanism, different consumer
of the same capped array.

`frontend/src/components/history/WorkflowHistory.tsx`:
- `runs` state is only ever populated by `getWorkflows(token, { limit: 50 })` (mount
  effect, line ~207) or `getWorkflows(token, { limit: Math.max(50, runs.length) })`
  (`refreshRuns`, line ~249) — both cap at 50 because `handleLoadMore` (the only code
  path that would grow `runs` past 50) is never invoked by any UI control (confirmed via
  `grep -n "handleLoadMore"` — one hit, its own definition; see ISS-198's root cause).
- `matchesFilter` (line ~430-435) does a client-side, case-insensitive substring match on
  `r.title` against `searchQuery` — purely in-memory over whatever `runs` currently holds.
- `visibleFamilies` (line ~943) = `families.filter((g) => g.members.some(matchesFilter))`,
  where `families = groupRunsByFamily(runs)` (line ~942) — so search only ever considers
  the ≤50 most-recently-created runs, never the account's full history.
- When zero families match, the component renders the FILTER-EMPTY state (line ~1160-1173,
  "No runs match this filter" + a "Show all runs" button that only clears `filterType`/
  `searchQuery` — it re-renders the same capped `runs`, it does not fetch more).

## Expected vs Actual

- Expected: searching for a run title matches against the account's full run history (or
  the UI plainly states search is scoped to "the N most recently loaded of M runs").
- Actual: for any account with more runs than the fetched page (e.g. qa-admin's 273 vs.
  the capped 50 — see [ISS-198](20260828-1400-ISS-198.md)), searching for a run title that
  exists only among the un-fetched remainder returns "No runs match this filter" — a false
  negative indistinguishable, from the user's side, from the run not existing at all.

## What would confirm or refute this

Reproduction: seed/identify a run title known to fall outside the most-recent 50 (e.g. via
`GET /api/runs?limit=50&offset=200` for qa-admin), search for that exact title in the
Run History search box, and confirm the FILTER-EMPTY state renders despite the run
existing per the API.

## Why this is a sibling, not the same bug

Distinct from [ISS-198](20260828-1400-ISS-198.md)'s header/chip mislabeling: that bug
shows a WRONG NUMBER; this one silently returns WRONG DATA (a false "does not exist")
with no numeric hint anything was excluded. Same mechanism (`runs` capped at 50, no
Load More), different user-visible symptom, independently reproducible and independently
fixable (see [ISS-198](20260828-1400-ISS-198.md)'s Fix location note on the search/sort
product decision).
