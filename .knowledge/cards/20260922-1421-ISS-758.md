# ISS-758

## Register entry

Sibling of [ISS-753](20260922-1413-ISS-753.md), filed from the same investigation. A DIFFERENT
mechanism from ISS-753's permanent "Starting point" staleness (this one is transient, and affects
agents/pipelineState/agentOutputs/content, not the Starting point field) — surfaced by the same
two browser sweeps supplied by the dispatch.

## Root cause — CONFIRMED (code) + corroborated by one observed instance

- `handleSelectVersion` (`PreviewPanel.tsx:808-838`) is `async`. Its body does:
  ```ts
  const run = await getWorkflow(token || "", memberId);
  setViewingVersion(versionViewFrom(run));
  ```
  with no check that `memberId` (or any request-generation marker) is still the most recently
  requested selection by the time the `await` resolves.
- Contrast the OTHER caller of `versionViewFrom`, the `/versions/{n}` URL-pin effect
  (`PreviewPanel.tsx:899-913`): it explicitly guards against exactly this —
  ```ts
  useEffect(() => {
    if (!pinnedMemberId) return;
    let cancelled = false;
    void (async () => {
      const run = await getWorkflow(getToken() || "", pinnedMemberId);
      if (!cancelled) setViewingVersion(versionViewFrom(run));
    })();
    return () => { cancelled = true; };
  }, [pinnedMemberId]);
  ```
  the standard React effect-cleanup race guard (`cancelled`, set `true` on re-run/unmount before
  a stale response is applied). `handleSelectVersion` has no equivalent — it is a plain
  `useCallback`, not an effect, so it has no cleanup phase at all to hook this into.
- Effect: if a user selects version A, then quickly selects version B before A's fetch resolves,
  and network timing delivers A's response AFTER B's (plausible on a large index jump — fetch
  latency does not guarantee request-issue order is response-arrival order), `setViewingVersion`
  applies A's now-stale data LAST, transiently showing A's agents/pipelineState/content under B's
  selection.

## Sweep corroboration (not independently reproduced by me — no browser used this pass)

The reverse+alternating sweep's own step 8 (`v6 -> v2`, a large non-adjacent jump) captured
exactly this shape: an immediate snapshot showed the agent panel still displaying v6's own entry
(same DOM node identity, same token/time numbers — "8s · 35.4K tok") under the v2 selection, and
the network log showed one sandbox-file request pairing the OLD run id (v6's) with the NEW ref
(`ref=v2`) before a correct request against v2's own run id landed; a snapshot ~10-12s later
showed it had self-corrected to v2's real numbers ("39s · 168.8K tok"). This matches the
missing-guard mechanism above: the OLD request's in-flight response (keyed to a stale
`memberId`/`run.id` closure) resolved after the newer one was issued, and nothing discarded it.
(`evidence/qa-ps-033/13-altpass-v2-selected-agents-stuck-on-v6.png`,
`.../14-altpass-v2-settled-agents-correct-starting-point-stale.png`, per the dispatch's own sweep
data.)

## Confidence

Mechanism: CONFIRMED — missing guard, read directly, contrasted against the sibling call site's
own present guard. Real-world frequency/severity: INFERRED beyond the one captured instance — it
self-corrects within roughly 10 seconds once the newer response lands, so this is a
transient-display bug, not a permanent one. What would fully settle it: a deliberate rapid-fire
repro (select several versions in quick succession, ideally with network throttling) to force
out-of-order resolution reliably rather than opportunistically.

## Fix direction (not applied — issue only)

Add the same guard pattern already used at `PreviewPanel.tsx:899-913` to `handleSelectVersion`
itself — either a `cancelled`-style ref keyed per invocation, or a monotonically increasing
"request generation" counter compared before calling `setViewingVersion`. Single place:
`handleSelectVersion` (`PreviewPanel.tsx:808-838`); no caller needs to change.

**What breaks if done carelessly:** a naive AbortController-based guard must not abort/ignore the
LATEST in-flight request when a newer one starts — only stale ones. `handleVersionMenuSelect`'s
own two call sites into `handleSelectVersion` (`PreviewPanel.tsx:854`, `:863`) plus the
`onSelectVersion`-driven paths must all still resolve to the CORRECT final state when they are the
most recent call, or version switching itself regresses.

## Blast radius

Every `eff*` value derived from `viewingVersion` (`effAgents`, `effPipelineState`,
`effAgentOutputs`, `effUserStoryContent`/`effPptContent`/`effPrototypeContent`,
`effGenericDeliverable` — `PreviewPanel.tsx:944-959`) is transiently at risk on a fast/distant
version switch — broader in SURFACE than [ISS-753](20260922-1413-ISS-753.md) (which is permanent
but Starting-point-only), though shorter-lived per occurrence.
