> **Status: proposed.** This overrides an active ADR and needs sign-off from
> ADR-0039's owner before merge.

## Problem

ADR-0039 put `db` into `_TRUSTED_SOURCES` and `TRUSTED_TRUST_LEVELS` so saved
workflows could raise `Limits` (a `wave_scheduler` build charging one subagent
per task died at task 9 under the ceiling of 8). It called itself "the crude
alternative" to ADR-0038 because budget and permissions ride one flag. The
cost was concrete:

- The compiler accepted `tools.exec: true` plus `gates: [security, approval]`
  on a saved step (`test_db_trust_exec_grant_survives_the_ceiling` locked it in).
- The exec allow-list includes `python` / `python3`; outbound network is not
  blocked, a risk accepted because "exec is engineer-only".
- The runtime security gate read `step.trust`, but `Step` had no such field,
  so it always saw `"file"` and passed.
- The approval gate is answered by the run's owner — the same user.

So any user who can save and launch a Composer workflow could get a Python
interpreter on the API server with its filesystem and network. This was
confirmed in the compiler and gate code, not end-to-end through the API.
Saved step overrides (`merge_override_steps`, compiled at `trust="db"`) gained
the same permissions without anyone deciding they should — the module was
written assuming saved rows are untrusted. `test_a_not_user_allowed_gate_is_rejected`
is what caught it.

A plain revert is not viable: compiling all 36 built-ins at the old untrusted
level fails 16 of them (`prototype_v2`'s `max_subagents: 200` — the exact
ADR-0039 case — `spawn_subagents` grants, and engine-internal pieces such as
`previous_run`, `html_skeleton` and the `ppt` deliverable). Composer copies of
those would break.

## Decision

`db` becomes its own trust level instead of a member of the trusted set.

| | file / builtin | **db (saved)** | user (inline) |
|---|---|---|---|
| Raise `Limits` | unbounded | up to `_LIMITS_SAVED_CEILING` | lower only |
| `spawn_subagents` | yes | **yes** | no |
| `exec` / `network` / `secrets` | yes (exec needs security+approval) | **no** | no |
| `gate: security` / `approval` | yes | **no** | no |
| `filesystem` / `postgres` MCP | yes (security+secrets) | **no** | no |
| `user_allowed=False` capability | yes | **only if `saved_workflow_allowed=True`** | no |
| Permission cap key | `trusted` | **`saved`** | `untrusted` |

Details:

1. **Saved ceiling.** `_LIMITS_SAVED_CEILING = {max_subagents: 200, max_depth: 2,
   wall_clock_seconds: 10800}` — the largest value any built-in declares
   (`prototype_v2`, `pdf_to_prototype`). Interim until ADR-0038 moves budget to
   its own setting.
2. **`saved` permission cap** (`permission_caps.py`): the untrusted cap plus
   `spawn_subagents` and the sandbox-confined tool sets built-ins grant
   (`file_extract`, `playwright`, `prototype_emit_only`, `ask_user`). `exec`,
   `network`, `git` off; no secrets.
3. **Per-capability opt-in** (`registry.register(..., saved_workflow_allowed=True)`),
   default off. Opted in after reading each implementation:

   | Capability | Why it is safe for a saved row |
   |---|---|
   | `compaction:html_skeleton` | pure stdlib string transform |
   | `deliverable:ppt` | pure string transform of the streamed deck |
   | `context_provider:previous_run` | reads the parent run only after `ScopedStore.assert_owns` (L16), fails closed |
   | `context_provider:uploaded_files` | reads only the run's own `.uploads/` |
   | `post_step:revision_validation` | validation fix-loop on the run's own deliverable via the kernel handle |
   | `post_step:api_prefix_audit` | runs the user-allowed `api_prefix` validator, event-free |

   **Not** opted in: `context_provider:repo` (brownfield repo context pack; only
   the unlaunchable `sample_brownfield` fixture uses it), `gate:security`,
   `gate:approval`, the powerful MCP servers. With the opt-ins, 35 of 36
   built-ins compile at `db`; `sample_brownfield` is the one that does not.
4. **`Step.trust`** is stamped by the compiler, so the runtime security gate's
   `trust not in {file, builtin}` check is now a real second line: a `db`/`user`
   step carrying exec (a tampered or hand-built plan) is blocked at run time.

## Rollout

Before shipping, run the read-only audit against every shared environment:

```
cd backend
uv run python -m tools.audit_saved_workflow_trust --only-problems
```

It lists every `workflows.source='user'` row that declares exec/network/secrets,
the security/approval gates or a powerful MCP server, and every row that no
longer compiles at `trust="db"` (ids and reasons only, no step content). Those
rows will start failing at launch; any that exist are worth a look. Local dev
had 0 saved rows (2026-09-29); dev/stage/prod not yet run.

## Residual risk

- `spawn_subagents` still multiplies cost for saved rows, bounded by the saved
  ceiling — the same budget exposure ADR-0039 accepted, now capped.
- The approval gate is still owner-answered; that no longer matters for saved
  rows because they cannot declare it, but it remains true for file manifests.
- Saved rows that relied on exec/security/approval stop working. That is the
  intended outcome; the audit finds them.

## Test coverage

Replaced the three ADR-0039 tests that locked the escalation
(`test_db_trust_allows_any_registered_reference`,
`test_db_trust_exec_grant_survives_the_ceiling`, `test_db_trust_may_raise_max_depth`)
with tests of the new posture in `test_compiler_trust.py`: host-reaching grants
rejected, spawn_subagents kept, Limits up to / above the saved ceiling, opt-in
honoured for db and not for user, security/approval rejected, `Step.trust`
stamped. `test_tool_grant_invariants.py` pins the three-row cap index and the
saved cap's contents. `test_a_not_user_allowed_gate_is_rejected` passes
unchanged.

## Superseded 2026-10-12

Not adopted. The owner kept ADR-0039: `db` stays fully trusted so file-based and saved
(Composer / override) workflows get equal access. Who can save a db-trust row is gated by
tier instead (QA-KB-126 `_saved_row_trust` / `_parent_run_trust`; override rows compile at
`user`, ISS-1113). This ADR arrived as code inside 75c58275c ("Fix/testcases #11") with
status `proposed` and author `TBD`. The merge of feat/user-stories-v2 into
feat/stale-bug-fixes put `db` back in `_TRUSTED_SOURCES` / `TRUSTED_TRUST_LEVELS`. The
`_SAVED_TRUST` branches and `saved_workflow_allowed` flags stay in the code, inert while
`db` is trusted.
