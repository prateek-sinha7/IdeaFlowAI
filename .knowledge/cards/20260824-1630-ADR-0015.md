# ADR-0015

## Decision

In the context of adding in-workflow branching and cross-workflow triggering to a
sequencer whose dispatch loop had always been a straight walk over an ordered list, we
decided that a `conditional` gate resolves a typed decision into one of two actions —
jump the dispatch cursor (`trigger: step`) or mint a NEW independent `WorkflowRun` and
STOP (`trigger: workflow`) — to achieve branching and delegation without a nested or
awaited sub-run, accepting that a diverted run produces no deliverable of its own and
that the two runs appear as two linked records rather than one timeline.

**Area:** engine, gates, workflow, run-lifecycle

## Why stop-and-hand-off rather than call-and-return

Awaiting the child would have made the parent's lifetime unbounded, put two runs on one
budget clock, and forced a merge of two event streams into one timeline. Stopping instead
means the existing single-run machinery is untouched: the child is minted through the SAME
`_launch_run_core` the HTTP launch handler uses, inherits `owner_id`/`workspace_id` (so its
spend lands in the same workspace ceiling) and carries `trigger_depth + 1`, which fails
closed at a fixed ceiling of 5.

The cost is real and was accepted: a diverted parent has no deliverable, and any UI that
assumed "a run ends in complete or failed" needed a third case.

## `diverted` is a distinct terminal status, not a flavour of cancelled

It is neither a failure nor a completion, and conflating it with either would have made
run history lie. This required a schema change — migration `0033` adds
`diverted_at_step_id` — so the record says not just THAT a run handed off but from WHICH
step. That column is what lets both directions of the history breadcrumb be rendered, and
it is the discriminator that distinguishes a divert-parent from an ordinary revision
parent, since both use `parent_run_id`.

## The frame it emits has to be a stream terminal

`pipeline_diverted` was added as an additive event and, on first implementation, was
absent from the stream-terminal sets on both sides. The connection then closed with no
recognised terminal type, the client rendered "Reconnecting…", reconnected, and only then
replayed the divert — so the user saw a spurious warning BEFORE the handoff. Any new
terminal frame must be added to `_STREAM_TERMINAL_TYPES`, the frontend's
`STREAM_TERMINAL_TYPES`, and the guard test that keeps them in sync, in the same change.
