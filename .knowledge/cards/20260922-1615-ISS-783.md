Confirmed 3/3 from a cold start against `/runs`: attempt 1 a fresh full
navigation (`http://localhost:3000/runs`) in an already-authenticated tab,
attempt 2 a second full navigation after leaving to `/dashboard` and back,
attempt 3 a brand-new browser tab loading `/runs` directly. Every cycle
produced the identical pattern via `mcp__lane2__browser_network_requests`:

- `GET /api/runs?limit=50` — **5x**
- `GET /api/runs?limit=6` — 1x
- `GET /api/auth/me` — 1x
- `GET /api/workflows` — 2x

This is BUGS.md QA-PS-037. Evidence:
`evidence/qa-ps-037/01-validate-attempt1-runs-loaded.png`,
`evidence/qa-ps-037/02-validate-attempt2-runs-loaded.png`,
`evidence/qa-ps-037/03-validate-attempt3-runs-loaded.png`.
(The reporter measured 6x/223KB; this run measured 5x on the current
backend seed — same defect, count varies with how many of the stacked
sources happen to fire before the network tab was sampled, see root cause
below. Both counts are far above the expected 1x.)

## Root cause — three stacked sources of the same call, all `getWorkflows(token, {limit: 50})` which internally calls `GET /api/runs`

**Source 1 — `WorkflowHistory.tsx`'s own mount effect double-fires.**
The T12 effect (`:218-223`) reads `type`/`sort` from the URL on mount and
calls `setFilterType(type)` (`:221`) even when `type` is the same value the
state already holds (`"all"`). The data-fetch effect (`:225-236`) is keyed
`[filterType]` and calls `getWorkflows(token, { limit: 50 })` (`:229`).
Because `setFilterType` always runs on mount regardless of whether the value
actually changed, React schedules a second commit and the `[filterType]`
effect's cleanup+refire behavior means this effect body runs twice for one
mount: once for the initial value, once again after T12's `setFilterType`
call lands.

**Source 2 — the `recentRuns`-keyed refetch effect (`:244-256`) fires a
third time once the parent populates `recentRuns` asynchronously.**
`page.tsx` initializes `recentRuns` as `[]` (`frontend/src/app/[...view]/page.tsx:792`)
and fills it in later via its own async fetch/SSE wiring. The effect at
`WorkflowHistory.tsx:245-256` skips only the very first render (comparing
against `recentRunsRef`'s initial value); the moment `page.tsx` sets a new
`recentRuns` array reference, this effect fires and calls `getWorkflows`
again (`:250`) — a second `limit=50` call this component makes for reasons
unrelated to the URL-driven fetch above.

**Source 3 — `RunConnectionProvider` fetches the same endpoint app-wide.**
Already root-caused in [ISS-781](20260922-1630-ISS-781.md): `getWorkflows()`
(`frontend/src/lib/api.ts:770-781`) builds `path = "/api/runs"` despite its
name, and `RunConnectionProvider.tsx:289`'s `refreshLiveRuns` calls it with
`limit: 50` on mount. That provider wraps the whole app in the root layout
(`frontend/src/app/layout.tsx:51`), so `/runs` pays for this fetch exactly
like every other route does — it is not scoped to the run-history page and
duplicates the two page-local calls above with the exact same query.

Together these three independent triggers explain 3 (and, once refresh
timing and StrictMode/dev-server double-invoke are folded in, up to 5-6)
identical `limit=50` calls on one cold load — matching both this run's 5x
and the reporter's 6x. `GET /api/workflows` (2x) is the real workflow-catalog
endpoint fetched separately elsewhere in the page tree, also undeduplicated.

## Expected vs actual

Expected: `/runs` cold load fires `GET /api/runs?limit=50` once, `GET
/api/workflows` once, `GET /api/auth/me` once (~3 requests).

Actual: `GET /api/runs?limit=50` fires 5x (reporter measured 6x), `GET
/api/workflows` fires 2x, confirmed 3/3 on the live backend.

## Resolution — [FIX-616](20260922-1923-FIX-616.md)

Fixed at the shared function rather than per caller: `getWorkflows()`
(`frontend/src/lib/api.ts:770`) now single-flights concurrent identical
requests through an `inFlightWorkflows` Map keyed by token + resolved path,
mirroring `refreshOnce()` (`api.ts:225-233`) in the same file. All four
sources above route through it, so the burst collapses to one fetch. The
entry is dropped on settle, so this dedups without caching. The `/api/workflows`
catalog duplication noted above is NOT covered by this fix and stays open under
[ISS-781](20260922-1630-ISS-781.md).
