## Summary

[ISS-221](20260828-1718-ISS-221.md) root-caused BUG-20260828-020430-runs-diverted to the shared
`relaunch(label)` helper in `frontend/src/components/chat/RunChatLane.tsx` (defined at line 1694):
it renders only a `<Button>`, never the `relaunchError` amber-banner block. That block is
hand-duplicated into only two of the four terminal sub-branches — `pipelineState?.cancelled`
(line 1722) and `pipelineState?.failed` (line 1808, which doesn't even call `relaunch()`, it has
its own bespoke buttons). The `pipelineState?.degraded` branch (lines 1844-1868) has the *exact
same shape* as the diverted-landing fallback ISS-221 already confirmed broken: it renders via
`relaunch("Run again")` (line 1865) with no `relaunchError` check anywhere in the branch.

Unlike a diverted run, a degraded run genuinely IS resumable per the backend's own rule (the 409
body BUG-20260828-020430-runs-diverted captured verbatim: `"only failed, degraded, or cancelled
runs are resumable"`), so most "Run again" clicks on a degraded run will succeed. But
`handleResumeRun` (`frontend/src/components/layout/DashboardLayout.tsx:2253-2311`) can still land
on `setResumeError(...)` for a degraded run through either of the two "any other error" exits it
already codes for: (a) the KAN-120 BUG-1 timing-race retry (line 2293-2298) itself failing a
second time (`retryErr` branch, line 2296), or (b) any other rejection reaching the generic catch
(line 2301-2309) — e.g. a genuine backend-side conflict that isn't the "generating" race. Whenever
either fires on a degraded run, the resulting `resumeError`/`relaunchError` is passed down to
`RunChatLane` exactly as it is for the diverted case (`DashboardLayout.tsx:3014`), and is silently
dropped for the identical reason: the branch that renders calls `relaunch()`, and `relaunch()`
does not render `relaunchError`.

## Why this is INFERRED, not CONFIRMED

This card is derived from the CONFIRMED root cause in ISS-221 by code-reading the `degraded`
branch (`RunChatLane.tsx:1844-1868`) and comparing its shape to the already-proven-broken
fallback branch (line 1871) — both call the same `relaunch()` helper, both lack any
`relaunchError &&` guard. It has **not** been reproduced in the browser: doing so requires
forcing `handleResumeRun`'s error path on a genuinely `degraded` run, which needs either winning
the KAN-120 BUG-1 timing race twice in a row (line 2293-2298's retry also failing) or another
concrete backend-side rejection for a degraded run's resume — neither was manufactured in this
analysis pass.

**What would confirm it:** seed or drive a `degraded` run, trigger a resume whose backend call
returns any error other than a first-attempt "generating" 409 (e.g. resume it from a second tab
concurrently, or stub/observe a slow DB commit twice in a row), and check whether the amber
`relaunchError` banner renders next to the "Run again" button. If it does not, this is the same
defect as ISS-221 with a different trigger condition.

## Expected vs Actual

- **Expected:** any error `handleResumeRun` captures into `resumeError` renders as the inline
  amber banner next to whichever relaunch button the user actually sees, regardless of which
  terminal marker (`cancelled`/`failed`/`degraded`/no-marker) put them there.
- **Actual (inferred):** only the `cancelled` and `failed` branches render it; the `degraded`
  branch shares the same blind spot as the diverted-landing fallback ISS-221 already proved.

## Fix note (for 5-fixer)

The natural fix site is the same one ISS-221 already points at: move the `relaunchError`
amber-banner block INTO the shared `relaunch(label)` helper (`RunChatLane.tsx:1694`) itself,
rather than patching the `degraded` branch individually — `degraded` (line 1865) and the
diverted-landing fallback (line 1871) both already call that one helper, so fixing it there
closes both branches (this card's and ISS-221's) in a single, smaller diff than patching either
branch separately.
