## What was wrong

`BUG-20260827-234030-create`. Signing in as a second account in a tab where an earlier
account had already loaded the home catalog showed the FIRST account's "Jump back in"
cards to the SECOND account — run titles, workflow type and, for completed runs, exact
token-usage and dollar-cost figures — even though the second account's own
`GET /api/runs?limit=50` returned a verified empty array. Validated 3/3 cold starts
([ISS-188](20260828-1300-ISS-188.md)). Two siblings share the mechanism: the same
mount-time fallback flashes the previous account's cards for at least one paint even when
the new account HAS its own history ([ISS-201](20260828-1607-ISS-201.md)), and the same
"no per-user scope, no invalidation on switch" shape exists one layer up in the Redux
preload ([ISS-200](20260828-1605-ISS-200.md)), where it covers the whole workflow catalog
and the Library's agents/skills/hooks, not just six runs.

## Root cause

Two independent caches, both keyed by "has this been fetched", never by "whose is it":

- `frontend/src/components/catalog/HomeLaunchGrid.tsx:37` —
  `CACHE_KEY_RECENTS = "vlc_home_recents_v1"` is one global `sessionStorage` key with no
  user component. `sessionStorage` outlives a soft account switch inside a tab, so the
  `useState(() => readCache(CACHE_KEY_RECENTS))` seed at `:135-139` hands the next account
  whatever the previous one cached. It is reached on EVERY account switch, because
  `recentRunsProp` and `reduxRecentRuns` are both genuinely empty at the instant the
  component mounts — the zero-run case (ISS-188) is only the variant where nothing ever
  arrives to overwrite it.
- `HomeLaunchGrid.tsx:149-166` — both refresh effects gate on the fresh list being
  `.length > 0`, with no `else`. A live fetch that genuinely resolved to zero runs is
  therefore indistinguishable from "not fetched yet" and can never clear a stale
  non-empty cache.
- `frontend/src/store/listenerMiddleware.ts:17-47` — the `signedIn` listener guards
  `fetchWorkflows`/`fetchRecentRuns` (and `fetchAgentLibrary`/`fetchSkills`/`fetchHooks`)
  on `workflowsStatus`/`recentRunsStatus` not already being `"loading"`/`"succeeded"`.
  That status carries no user identity. The only reset path was the `signedOut` listener
  at `:49-57`, and the sole `signedIn` dispatch site
  (`frontend/src/app/[...view]/page.tsx:817`, confirmed by grep — one site, app-wide)
  fires unconditionally on every mount with whatever token is in `localStorage`. So a
  token swap that skipped `handleLogout`'s explicit `signedOut()` and
  `handleSessionExpiry`'s hard navigation left the first account's data in `state.global`
  and made the second account's preload a no-op.

## What changed and why there

`frontend/src/components/catalog/HomeLaunchGrid.tsx` — the file is the sole owner of this
cache (grep: nothing else references `readCache`/`writeCache`/`vlc_home_recents_v1`), so
the fix is entirely local to it:

- New `recentsCacheKey()` derives `vlc_home_recents_v1:<sub>` from the JWT's `sub` claim.
  `sub` is the only user identity available at first paint — `state.auth.user` is filled
  in later by `getMe()` — and it is stable across a token refresh, which mints a new token
  for the same user. It returns `null` when there is no decodable identity;
  `readCache`/`writeCache` then no-op, so the failure mode is a lost instant-paint, never
  another account's data. `getToken()` was already imported and is `localStorage`-guarded,
  so the SSR path returns `null` before `atob` is reached.
- The redux-recents effect gained the missing `else if`: prop empty, redux empty,
  `recentRunsStatus === "succeeded"` and something still on screen means the fetch really
  did resolve to zero, so `recents` and the cache are cleared. This is what ISS-188's
  "Expected" asks for, and it also covers a same-user list that legitimately emptied.
  `recentRunsStatus` joins the dep array; the `void recentRunsStatus;` no-op that existed
  only to silence the unused-variable lint was removed because the value is now read.

`frontend/src/store/listenerMiddleware.ts` — one guard at the choke point every
`signedIn` routes through, rather than a check per dispatch site:

- The effect reads `listenerApi.getOriginalState().auth.token` (before its first `await`,
  as that API requires) and, when it differs from `action.payload.token`, calls
  `clearPreloads()` first. The existing status guards then see `"idle"` and refetch for
  the new user. A remount with the same token compares equal and still skips the refetch,
  so the preload's original purpose is intact.
- `clearPreloads()` is the four `*Cleared()` dispatches the `signedOut` listener already
  did, extracted so both listeners share one definition — no behaviour change on the
  `signedOut` path.

Deliberately NOT changed: `authSlice.ts`'s `signedIn` reducer. ISS-200 names it as part of
the root cause, but the reducer setting state unconditionally is correct — the identity
comparison belongs where the refetch decision is made, and putting it in the listener
covers the single dispatch site with one guard instead of teaching the reducer about
preload status. The trade-off accepted: a token REFRESH for the same user now costs one
redundant preload if a `signedIn` follows it, which is strictly safer than skipping one.
