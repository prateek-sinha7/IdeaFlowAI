# ISS-939

## What happened

Derived while analysing QA-KB-037 (root card [ISS-758](20260922-1421-ISS-758.md)). The ISS-758 card
attributes its sweep observation ("agent panel still showing v6's entry under the v2 selection, one
sandbox-file request pairing the OLD run id with the NEW ref, self-corrected ~10-12 s later") to the
out-of-order race. The race is real (validated 3/3, reproduced in jsdom), but those three observations are
what the PENDING WINDOW of a single, ordinary, slow pick looks like. That is a separate mechanism, and
ISS-758's agreed fix does not touch it.

## Root cause (CONFIRMED by source read, jsdom execution and the validator's screenshot)

`handleSelectVersion` (`PreviewPanel.tsx:884-921`) and its menu wrapper `handleVersionMenuSelect` write in two
halves:

| before the `await` (synchronous at click) | after the `await` (when the GET returns) |
|---|---|
| URL pin: `onTabSelect(tab, pin)` `:906`, which pushes the route (`DashboardLayout.tsx:551`) | `setViewingVersion(versionViewFrom(run))` `:914` |
| `sandboxSelectedRef` and `intendedSandboxRef`: `handleVersionMenuSelect` `:944-946` | |

`viewingVersion` is the ONLY input of `activeRunId` (`:847`), of `effAgents` / `effPipelineState` /
`effAgentOutputs` / `effRunInput` (`:1064-1069`) and of `isViewingOlder` (`:849`). For the latency of
`GET /api/runs/<id>`:

- the chip already reads `Viewing v2` (`RunHeader.tsx:86`, from `selectedRef`) and the URL names v2;
- the Preview tab shows its own `Loading v2…` (`RefVersionPreview`, `PreviewPanel.tsx:379-383`) because it
  follows `sandboxSelectedRef`;
- Steps, Files and Audit still render the PREVIOUS version's agents, tokens and Starting point, and no
  read-only banner shows (`isViewingOlder` is still false);
- the ref-scoped sandbox reads (`PreviewPanel.tsx:1443-1457`, keyed `[sandboxSelectedRef, activeRunId,
  deliverableFile]`) go out with the OLD run id and the NEW ref.

Evidence:

- Browser (validator): `evidence/qa-kb-037/11-validate-attempt1-steps-sample1.png`, taken ~0.4 s after the
  pick: chip `Viewing v2`, no amber banner, Steps still v8's "5 / 5 agents · 4m 31s" and footer "92.3K total".
  Compare `14-validate-attempt1-steps-sample4.png` once data has landed.
- jsdom (scratchpad harness, executed 2026-10-01). S2, pending: chip `Viewing v2`, Steps agents
  `live-v3-agent`, no banner; after the response: Steps `v2-agent` and banner `Viewing v2 (read-only)`. S2b,
  while `getWorkflow(v2)` is still pending: `getRunSandboxFile("member-v3", "user_stories.md", "v2")` twice
  (OLD run id, NEW ref); after the apply `("member-v2", …, "v2")` twice. Identical on the unmodified code and
  on a copy carrying the ISS-758 agreed fix: that fix leaves the window untouched.
- The ISS-758 sweep's own network log: OLD run id paired with the NEW ref, then a correct request.

## Expected vs actual

- **Expected** (BUGS.md, QA-KB-037): "Agent panel always shows the selected version's current data
  immediately."
- **Actual:** for the duration of one GET (at least ~1.5 s on the validator's runs, ~10 s on the sweep's large
  records) Steps shows another version's data under the new version's label, and the sandbox is asked for the
  wrong run's tag.

## Why the root cause implies it

Same handler, other side of the `await`: the apply is the only write of `viewingVersion` and nothing
represents "pick pending", so every surface keyed on `viewingVersion` lags the surfaces keyed on the URL and
on `sandboxSelectedRef`.

## Fix direction (not applied; needs a UX call)

(a) A pending marker set at the top of `handleSelectVersion` and cleared under the same
`gen === selectGen.current` guard as ISS-758's fix, rendered as a loading state by Steps, Files and Audit
(extend the existing `isLoadingRunData` path, [ISS-739](20260922-1407-ISS-739.md) /
[ISS-752](20260922-1409-ISS-752.md)). (b) Stage the chip and `sandboxSelectedRef` only when the view applies:
removes the mislabel, loses the Preview "Loading v2…" feedback. (c) Keep stale-while-loading and drop only the
mislabel. Whatever is chosen has to share ISS-758's counter, or the pending flag clears for a superseded pick.
