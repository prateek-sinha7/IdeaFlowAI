## What was wrong

A cold load of `/runs` fired `GET /api/runs?limit=50` 5-6 times — the same
37 KB run list, 186 KB of it redundant. Every one of those calls goes through
one function, `getWorkflows()` (`frontend/src/lib/api.ts:770`, which despite
its name builds `path = "/api/runs"`), from four independent callers that have
no knowledge of each other:

- `frontend/src/components/history/WorkflowHistory.tsx:229` — the `[filterType]`
  mount effect
- `frontend/src/components/history/WorkflowHistory.tsx:250` — the `[recentRuns]`
  refetch effect, itself downstream of the next one
- `frontend/src/app/[...view]/page.tsx:995` — the route resolver's own mount
  effect, gated only on `isAuthenticated`, so it fires on every route
- `frontend/src/providers/RunConnectionProvider.tsx:289` (`refreshLiveRuns`),
  mounted app-wide from the root layout (`frontend/src/app/layout.tsx:51`)

each doubled again by React StrictMode's dev-mode double-invoke. A fifth
caller, `refreshRuns` (`WorkflowHistory.tsx:271`), is the one call site in that
file with no `isRefreshingRuns` re-entry check — the auto-refresh timer effect
14 lines below it (`:305-309`) does check, the manual Refresh button does not —
so a double-click fired two concurrent identical requests as well
([ISS-795](20260922-1828-ISS-795.md)).

## What changed and why there

`frontend/src/lib/api.ts` only. The request half of `getWorkflows()` moved
verbatim into a new private `fetchWorkflowPage(path, token)`; `getWorkflows()`
keeps its signature and query-string building and now consults a
module-level `inFlightWorkflows` Map keyed by `${token}\n${path}` before
starting a request. A caller that arrives while an identical request is open
gets that same promise; the key is deleted in `.finally()`, so the guard
de-duplicates concurrent calls and does NOT cache — a refetch started after
the previous one settled still goes to the network.

This is the single point every caller routes through, so one guard here closes
all five call sites at once (both WorkflowHistory mount effects, its manual
Refresh button, page.tsx's mount effect, and RunConnectionProvider's app-wide
boot effect) instead of five per-caller guards. It deliberately mirrors the
`inFlightRefresh` / `refreshOnce()` single-flight pattern that already lives
45 lines above it in the same file (`api.ts:225-233`).

Line numbers here are the ones the ISS cards were written against
(`getWorkflows` at `api.ts:770`). A concurrent, uncommitted change to the same
file for ISS-782/ISS-796/ISS-799/ISS-801 (a `cachedAccountRead` + `cachedGet`
layer around `getMe`/`getCapabilities`/`getPreferences`) has since shifted them
— in the working tree at the time of writing `getWorkflows` is at `api.ts:873`
and `inFlightWorkflows` at `:871`. Both changes coexist in the file; neither
overwrote the other.

The token is part of the key so two identities can never share a run list.
Only `getWorkflows()` is guarded — the `/api/workflows` catalog endpoint is
still fetched twice on this page by a different mechanism, and stays open
under [ISS-781](20260922-1630-ISS-781.md).
