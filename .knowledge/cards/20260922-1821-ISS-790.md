## What happened

Register entry: QA-PS-043 (register: `LEDGER.md`, detail:
`BUGS.md#qa-ps-043`). Reported 2026-09-17: opening `/create/user-stories`
fired 9 requests totalling 76 KB, including `GET /api/user_stories` 4x
(11.6 KB), a duplicated `GET /api/me`, and an unused
`GET /api/runs?limit=50` (37.2 KB, "not needed on a create/wizard page").

Re-validated 2026-09-22 against the current app (`feat/git-versioning`
branch, `qa-admin@flowinqa.com`, light theme). The exact endpoint names have
moved since the report was filed (`/api/user_stories` is now
`/api/workflows/user_stories`; `/api/me` is now `/api/auth/me`), but the
core defect — duplicate/unnecessary XHRs firing on every wizard cold load —
reproduces every cycle.

### Reproduction (3/3 cold starts, cycle 1 already showed it)

1. Sign in as `qa-admin@flowinqa.com` / `flowin-e2e-pass`.
2. Cold-navigate to `/dashboard`, then to `http://localhost:3000/create/user-stories`
   (attempt 3 used a brand-new browser tab instead of same-tab navigation, to
   rule out an in-tab cache artifact — result was identical).
3. Inspect XHR/fetch network requests via `browser_network_requests`.

No narrowing was needed — no tier, theme, timing or entry-path axis flips
this; it fires on every attempt, identically, 3/3.

### Expected

Per the original report, `/create/user-stories` should fire only what a
brief-entry wizard needs: the workflow config endpoint once, `/api/workflows`
once (for the agent-count/duration chip), and `/api/auth/me` once. No run
history.

### Actual — observed 2026-09-22, all three cold-start attempts identical

```
GET /api/runs?limit=6              — 1x  (unused; wizard shows no run history)
GET /api/auth/me                   — 1x  (renamed from /api/me; not duplicated
                                            here, unlike the 2026-09-17 report)
GET /api/runs?limit=50             — 2x  (DUPLICATE, unused on this wizard)
GET /api/workflows/user_stories    — 2x  (DUPLICATE — the wizard's own config
                                            endpoint, renamed from /api/user_stories)
GET /api/workflows                 — 2x  (DUPLICATE)
GET /api/agents/library            — 1x  (catalog calls not present when the
GET /api/skills/library            — 1x   original report was filed)
GET /api/hooks/library             — 1x
```

Net effect — wasted/redundant network traffic on every wizard cold load — is
the same defect the report described, relocated to renamed endpoints as the
app evolved.

### Root cause — not traced here (analyze phase)

Not investigated in this validation pass. The `/api/runs?limit=50` x2,
`/api/runs?limit=6` x1, `/api/workflows` x2, and per-catalog `/api/*/library`
x1-each shape is byte-for-byte the same multiset [ISS-782](20260922-1610-ISS-782.md)
already root-caused on `/analytics` and [ISS-787](20260922-1815-ISS-787.md)
found again on `/library` — traced there to `DashboardLayout.tsx` statically
mounting every page component plus `RunConnectionProvider.tsx:289`
unconditionally calling `getWorkflows(t, { limit: 50 })` on mount, regardless
of the active route. This card's remaining piece — `GET
/api/workflows/user_stories` duplicated 2x — is specific to this wizard and
still needs its own call-site trace (candidate: a page-level component and a
layout-level component each independently fetching the same workflow config,
the same shape as `AnalyticsPage.tsx:210/237` in ISS-782).
