# ISS-114

## Title

ResultCard.test.tsx's LOCK-F case is RED and belongs to no register row, and the underlying LOCK-F guarantee may actually be broken in the product. The test labels the deliverable output 'Deliverable' (LOCK-F) and links to Preview throws TestingLibraryElementError: Unable to find an element with the text: Deliverable on its getByText("Deliverable") assertion. Cause: KAN-154 moved deliverable into the inline-render branch at ResultCard.tsx:141, which renders no title — only message.content plus the link — so the literal string "Deliverable" appears nowhere in the DOM for that path. ISS-076 covers the Playwright 33-red baseline, not vitest, and no row covers this one. The open question decides whether this is a test fix or a CODE fix, and it should not be answered by whichever is cheaper: LOCK-F says the run output is labelled "Deliverable", never a workflow-specific noun. If that guarantee still stands, the product is violating it and the test is right; if KAN-154 deliberately retired the label for the inline path, the comment at ResultCard.tsx:125-140 never says so — it explains the inline change without mentioning LOCK-F. Either way LOCK-F is currently unasserted for the deliverable path. Do not "fix" this by deleting or loosening the assertion. Baseline for whoever takes it: at f12d99ae and at 0312a0af the file reads 1 failed / 10 passed (11) and 1 failed / 12 passed (13) respectively, the single red being this case (line :56 before FIX-236, :57 after — the shift is one added comment line, same test ID, same throw).
