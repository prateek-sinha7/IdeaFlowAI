## What happened

Derived while analysing QA-KB-012 (root card [ISS-348](20260828-2102-ISS-348.md), `/login/<sub-path>`),
alongside the concurrent QA-KB-013 analysis of [ISS-349](20260828-2102-ISS-349.md) (`/admin/<sub-path>`).

The root cause behind [ISS-238](20260828-1633-ISS-238.md), ISS-348 and ISS-349 is not specific to a
screen name: `parseViewPath` treats a matched prefix as a full match. The single-segment heads are all
carded (`register` fixed by [FIX-344](20260828-2046-FIX-344.md), `analytics` by
[FIX-462](20260901-2100-FIX-462.md), `login` ISS-348, `admin` ISS-349, `dashboard`
[ISS-910](20261001-2220-ISS-910.md)). This card is the same flaw one level deeper, on the branches that DO
test `segments.length` somewhere but never at the leaf.

INFERRED as live defects: every parser result below was EXECUTED, but no render was reproduced in a
browser.

## Root cause (CONFIRMED by source read and by running the parser)

Each branch returns as soon as the segment it cares about matches, without checking that nothing
follows it. Executed against the current `frontend/src/lib/routes.ts` (Node type-stripping, scratch
script outside the repo, 2026-10-01):

| input | `parseViewPath` result | matching line (no arity check) |
|---|---|---|
| `['settings','profile','x']` (also `ai-model`, `usage`, `constitution`, `security`) | `settings-<tab>` | routes.ts:457-463 |
| `['create','ppt','x']` (also `prototype`, `app`, `user-stories`) | `create-<mode>` | routes.ts:283-287 |
| `['create','foo','bar']` | `create-workflow`, `pipelineType:"foo"` | routes.ts:298 |
| `['workflows','new','x']` | `workflow-new` | routes.ts:306-309 |

| `['runs','r1','files','x']` (also `workspace`, `audit`, `stream`) | `run-<tab>` | routes.ts:365-396 |

| `['library','agents','slug','x']` (also `skills`, `hooks`) | `library-<type>` | routes.ts:434-439 |

Controls that DO reject junk (same probe): `['register','x']`, `['analytics','x']`,
`['settings','bogus']`, `['workflows','w1','bogus']`, `['library','bogus','a']` and `['nonexistent']`
all return `{"screen":"unknown"}`. So a wrong verb or type is already rejected; only segments AFTER a
valid verb are tolerated.

Downstream (read, not executed): `initialMainViewFor` maps these screens to a real `MainView`
(`frontend/src/app/[...view]/page.tsx:156-188`, settings at `:189-194`), except `create-ppt` and
`create-prototype`, which have no case there and render `LaunchWizard` standalone through `wizardModeFor`
(`page.tsx:4097-4102`) and `workflow-run`, which renders through its own gate (`page.tsx:4117-4126`).
Either way the real screen renders under the bogus URL, the [ISS-350](20260828-2102-ISS-350.md) shape. `/settings/security/<x>`
is the login/admin shape instead: the exact `/settings/security` has its own static route
(`app/settings/security/page.tsx`), only the deeper path reaches the catch-all, and there
`initialSettingsSectionFor` maps `settings-security` to the Account Settings "security" tab
(`page.tsx:312-313`).

## What a fixer must not break

- Extra segments that are legitimate stay legal: `runs/<id>/steps/<agentId>` (`tail[3]`),
  `runs/<id>/preview/full`, `runs/<id>/versions/<v>` with or without a trailing tab,
  `library/<type>/<slug>`, `create/<catalog-type>` (segment 2 is open-ended by design, see the
  comment at routes.ts:289-297). Only segments BEYOND the intended arity are the defect.
- `runs` lifts `/versions/{v}` out first (routes.ts:355-363), so arity must be counted on `tail`, not on
  `segments`.
- The existing exact-path tests (`routes.test.ts` round trips for runs tabs, library detail, settings
  tabs, create modes) must stay green, and so must `routes.iss339.test.ts`, which pins bare `/settings`
  -> `settings-profile` and the legacy `/library/{agents,skills,hooks}` list shapes -> `library`.

## Why one card, not eleven

One mechanism, one function, one fix pass, none reproduced yet. Earlier cards split by head because each
had its own browser reproduction. If a hunter reproduces one of these, split that URL class out of this
card rather than widening it.

## Fix direction (not applied)

In `parseViewPath` only. It is the single function every consumer routes through (`page.tsx:426`,
`LibraryPage.tsx:465`, `error.tsx:24`, `global-error.tsx:24`), so one arity check per branch, in the
`segments.length === N` shape that `create` and `workflows` already use, fixes all four consumers at
once. A guard in `page.tsx` or `DashboardLayout` would leave the telemetry label and `LibraryPage`'s own
`parseViewPath` call wrong. Same file and same test file as the QA-KB-012 / QA-KB-013 fixes, so apply it
in the same pass or serialize it.

## Resolution (QA-KB-012 / QA-KB-013, fixer, 2026-10-01)

Fixed by [FIX-696](20261001-2235-FIX-696.md), one arity check per branch in `parseViewPath`:
- create: `segments.length > 2` -> unknown.
- workflows: `new` only at length 2, and `> 3` -> unknown before the action arms.
- runs: `tail.length === 3` on files/workspace/audit/stream and `=== 4` on steps/{agentId} and preview/full. Arity is
  counted on `tail`, so the `/versions/{v}` form keeps working.
- library: `>= 3` -> `=== 3`.
- settings: `> 2` -> unknown.

Every row of this card's table now parses to `{"screen":"unknown"}`, and every app-built or e2e-visited shape is
unchanged. A HEAD-vs-working-tree probe over 75 paths gave 52 unchanged and 23 changed, all to unknown
(`evidence/qa-kb-012/05-fix-parser-probe-head-vs-worktree.txt`). The one repo test is the it.fails
"ISS-911: /settings/profile/<extra> is unknown", which now reports "Expect test to fail". The other URL classes are
proven by that probe, not by a repo test. Before editing, the "What a fixer must not break" list was checked against
the builders, `proxy.ts:21`, `DashboardLayout.tsx:418`, `LaunchWizard.tsx:1458`, the library id sources and the e2e
suites, and nothing builds a deeper path. Still INFERRED at the render level: no browser cycle was run.
