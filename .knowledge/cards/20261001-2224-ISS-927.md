# ISS-927

## Why this must also be broken (derived from the ISS-676 root cause)

[ISS-676](20260917-1447-ISS-676.md)'s root cause is that the live `pipeline_cancelled` /
`pipeline_failed` block (`frontend/src/app/[...view]/page.tsx:1821-1858`) gates page-level writes that
belong to the run on screen behind `!isForeignFrame`, which only asks "did this tab launch the run?".
`setLastCancelledRunId(cancelledId)` (`page.tsx:1846`) is one of those writes, and it is the one whose
reader is NOT masked by the per-run store, so it is where the root cause becomes a visible defect.
The agreed minimal fix for ISS-676 leaves this call unconditional (see below), so applying it as
written would leave this sibling live.

## Condition

- One tab holds at least two launched runs (concurrent runs, KAN-125): VIEW on screen, BG not on screen.
- VIEW is terminal and its lane shows a relaunch button: cancelled "Run Again" (`RunChatLane.tsx:1796`),
  degraded "Run again" (`:1981`), other terminal "Start a new run" (`:1987`), failed "Reopen & fix from
  the failed step" (`:1930-1938`). Every one calls `onRelaunch`, wired to `handleResumeRun` at
  `DashboardLayout.tsx:3325`.
- BG's `pipeline_cancelled` lands while VIEW is on screen. This page has no UI to cancel a non-viewed
  run (`postCancel` has two UI call sites, `DashboardLayout.tsx:2260` and `:2509`, both addressing the
  viewed run), so the realistic triggers are: Stop on BG and then switch to VIEW before the frame arrives
  (the cancel is cooperative and "the pipeline_cancelled event drives the state reset", `DashboardLayout.tsx:2503-2504`),
  a cancel from another tab or the API (`POST /api/runs/{BG}/cancel`, as in QA-KB-035), or a server-side cancel.
- No navigation between BG's cancel frame and the click: `lastCancelledRunId` is `useState`, and the page
  remounts on every `router.push` (`useRunStateStore.ts:276-279`), which wipes it.

## Expected vs actual

- Expected: the relaunch button on VIEW calls `postResume(VIEW)`.
- Actual (by reading, not run): `handleResumeRun` computes
  `const runId = lastCancelledRunId ?? pipelineState?.pipelineRunId ?? contentSourceRunId ?? activePipelineRunId;`
  (`DashboardLayout.tsx:2530`). BG's cancel frame set `lastCancelledRunId` to BG
  (`page.tsx:1844-1846`: `const cancelledId = frameRunId ?? trackedRunIdRef.current; ... setLastCancelledRunId(cancelledId);`),
  so the click POSTs `/api/runs/<BG>/resume` and re-drives the cancelled background run (a paid pipeline)
  while VIEW stays terminal. `pipeline_failed` never writes the slot, so the trigger is a BG CANCEL; VIEW
  itself can be cancelled, failed or degraded.

## Evidence

CONFIRMED (the write): `evidence/qa-kb-035/04-analyze-slice-trace.out.txt` slices the live block out of
page.tsx and runs it with recording stubs, `isForeignFrame=false`, tracked=VIEW, frame=BG:

```
pipeline_cancelled -> setBackgroundRunTransition({"runId":"BG","to":"cancelled"}) ; runStore.update("BG",{"questionnaireData":null}) ;
  setReviewGateData(null) ; setQuestionnaireData(null) ; setActivePipelineRunId(null) ; setLastCancelledRunId("BG") ;
  detachRunRef("BG") ; patchRecentRunStatus("BG","cancelled")
```

CONFIRMED (the reader chain, all read): the slot has exactly two writers, `page.tsx:1470`
(`setLastCancelledRunId(null)`, inside the non-foreign `pipeline_start` branch) and `page.tsx:1846`; it
reaches DashboardLayout as a prop (`page.tsx:4414`) and its only consumer is `handleResumeRun`
(`DashboardLayout.tsx:2526-2530`, deps `:2580`). `handleResumeRun` returns early only when
`pipelineState?.isRunning` (`:2525`), which is false on a terminal VIEW.

INFERRED (the end-to-end click): needs two concurrent paid runs in a browser. Nothing in the code
re-points `lastCancelledRunId` at VIEW between BG's frame and the click.

## Why the agreed ISS-676 fix does not cover it

The QA-KB-035 notes in BUGS.md say to leave "the setLastCancelledRunId/detachRunRef/patchRecentRunStatus
calls unconditional". `detachRunRef` (releases a dead run's SSE focus, BUG-015) and `patchRecentRunStatus`
(global recents list) are correct for a background run. `setLastCancelledRunId` is not: its declared
purpose (`page.tsx:860-863`) is to let `handleResumeRun` find the run that was stopped on screen. A
background run needs no such pointer, because once the user opens it `pipelineState.pipelineRunId` and
`contentSourceRunId` already name it.

## Suggested fix (same block as ISS-676, one extra line)

Reuse the shared predicate that is already imported at `page.tsx:22`
(`isForeignRunFrame`, `frontend/src/lib/wsReplayState.ts:80-86`: false unless both ids are known and differ):

```ts
if (cancelledId) {
  if (!isForeignRunFrame(frameRunId, trackedRunIdRef.current)) setLastCancelledRunId(cancelledId);
  detachRunRef.current?.(cancelledId);
}
```

Verified in memory against the sliced block (script `evidence/qa-kb-035/04-analyze-slice-trace.js`):
BG cancel -> no `setLastCancelledRunId`; the tracked run's own cancel still sets it; a frame with no run id
still sets it (to the tracked id).

Not part of this card: `lastCancelledRunId` is never cleared except by a non-foreign `pipeline_start`
(`page.tsx:1470`), so within one mount a cancelled viewed run's id still outranks a later-viewed
terminal run's own id. That is an independent staleness question, not implied by the ISS-676 root cause.

## Fixed (2026-10-02, QA-KB-035 fixer): [FIX-708](20261002-0144-FIX-708.md)

Applied as suggested above, in the same hunk as ISS-676. Inside `if (cancelledId)`, the call is now
`if (!isBackgroundFrame) setLastCancelledRunId(cancelledId);` (`page.tsx:1866`), where
`isBackgroundFrame = isForeignRunFrame(frameRunId, trackedRunIdRef.current)` (`:1852`).
`detachRunRef` and `patchRecentRunStatus` still run for the background run.

"ISS-927: background cancel does not overwrite lastCancelledRunId" in
`bgTerminalClarify.qaKb035.source.test.ts` now reports "Expect test to fail" (XPASS). The marker is
left for the verifier.

The tracked run's own cancel still sets the slot. A frame with no run id still sets it to the tracked
id. The never-cleared staleness noted above is untouched, as that note says it should be. Not
exercised end to end in a browser: that needs two concurrent paid runs.
