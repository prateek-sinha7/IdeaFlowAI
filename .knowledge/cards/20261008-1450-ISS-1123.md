# ISS-1123

**Register source:** sibling derived during the `QA-KB-102` analysis on 2026-10-08 (root [ISS-1103](20261008-0016-ISS-1103.md)). Not its own bug row.

**Confidence:** CONFIRMED by the offline probe for the database, queue and registry state (`evidence/qa-kb-102/analysis-04-silent-resume-endpoint-probe.txt`, scenario G). INFERRED for what an already-attached browser stream does: it follows from `_cleanup_pipeline`'s own docstring (`run_engine.py:88-118`), not from an observed stream.

## Condition

The one place a failed user resume IS recorded: `_drive_user_resume` catches an exception out of `resume_run` and calls `_flip_back_to_failed(run_id, str(exc))` (`run_commands.py:794-796`). `resume_run` raises only from statements outside the funnel's swallow, for example the first `workflow_runs` read or `RunTrace(RunSandbox(...))` at `engine.py:15922-15928`.

## Expected vs actual

Expected: the "honest state" of T-50-06 includes the live view, the way the launch driver's failure branch does: an `error` frame, the failed status, then the sentinel and `_cleanup_pipeline` (`run_commands.py:4368-4399`).

Actual, scenario G (a `RuntimeError` raised from `RunTrace(...)`, user resume through the endpoint):

```
row after            status='failed'  error='scripted fault in RunTrace(...) construction ...'      (the DB is right)
flip-back calls      1
live queue items     []                                    (no frame, no sentinel)
registry after       driver task registered and done=True, producer queue still registered
```

`_flip_back_to_failed` is `_persist_resume_status` and nothing else (`run_commands.py:1008-1012`). No terminal frame is queued and `_cleanup_pipeline` is not called. [`_is_run_live`](../../backend/app/api/run_engine.py) heals a stale registration on its next call (`run_engine.py:197-212`), so a reload or a new attach recovers. A stream that attached while the entry existed is "parked ... at `await live_queue.get()`" until then (`_cleanup_pipeline` docstring, A3), and the lane stays on "Restarting run…" ([ISS-1121](20261008-1450-ISS-1121.md)).

## Why the root cause implies it

[ISS-1103](20261008-0016-ISS-1103.md): the resume tier has no way to tell the live client about a failure. The swallowed paths send a sentinel and no event; this path sends neither. A fix that gives the engine funnel a terminal event still leaves the pre-funnel faults on this DB-only path, so both must be covered or the helper must be the one place that records a failure.

## Fix direction (INFERRED, not applied)

Prefer routing the fault through the root card's engine helper, so there is one writer. If the wrapper does it itself, in `_drive_user_resume`'s `except`, after `_flip_back_to_failed`, queue the one failure frame the launch driver queues (`run_commands.py:4372-4381`) and call `_cleanup_pipeline(run_id)`; it must stay a single put, not an event ladder (the INV-12 fence in the docstring at `run_commands.py:770-773`). Keep the control: a fault before the funnel's try must still end `failed` with the fault as `.error`.

## Resolution (5-fixer, QA-KB-102, 2026-10-08)

Resolved by [FIX-768](20261008-1540-FIX-768.md). `_drive_user_resume`'s `except` puts one `pipeline_failed` frame on the queue, flips back as before, then calls `_cleanup_pipeline`. The frame is a `pipeline_failed`, not the launch driver's `error` frame, so the lane's terminal clear (ISS-1121) fires. It is not routed through `_fail_resume`, which keeps the wrapper off a private engine method; the stub engine of the T-50-06 test has none.
