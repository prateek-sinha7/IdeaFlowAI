## What is suspected

[ISS-356](20260828-1910-ISS-356.md) root-caused BUG-20260828-090219-runs-diverted to
`frontend/src/components/results/SandboxTab.tsx:1037-1043`: the `expired` branch hardcodes
"The deliverable is still on the Preview and Files tabs" with no check on the run's
`output`/`deliverable_filename`/status. Reading the component confirms the gap is broader than
"diverted was omitted from a check" (the shape [FIX-357](20260828-2210-FIX-357.md) already fixed
for PreviewPanel/WorkflowHistory/RunDetailPage) — `SandboxTab` was never given ANY status or
deliverable signal to check in the first place:

- `SandboxTabProps` (`SandboxTab.tsx:842-849`) accepts exactly two props, `runId` and
  `agentNameById` — nothing describing run status or deliverable presence.
- The component's only source for `expired` is its own workspace-listing fetch
  (`res.expired` at `SandboxTab.tsx:915`, from `getRunSandbox`/`SandboxListing.expired`).
- Backend-side, `expired` is purely a directory-existence check with no status awareness:
  `list_sandbox` (`backend/app/api/run_files.py:534`) computes `expired = not
  sandbox.root.is_dir()`, and its own docstring (`:524-527`, "`expired` is the real signal for
  a TTL-swept run — the sandbox sweeper removes the whole run dir after `RUN_DIR_TTL_HOURS`")
  and the setting's comment (`backend/app/core/config.py:308`, "Retention for a **finished
  run's** sandbox dir before the cleanup sweep removes it") both describe the sweep as applying
  to any finished run — not a diverted-specific one.

Grepping every render call site of `<SandboxTab` across `frontend/src` (excluding
`SandboxTab.test.tsx`/`SandboxTab.runs.test.tsx`) turns up exactly one production caller:
`frontend/src/components/preview/PreviewPanel.tsx:1406`,
`<SandboxTab runId={workspaceRunId} agentNameById={agentNameById} />` — no status/deliverable
prop passed, even though `PreviewPanel` has ALREADY computed exactly the booleans this branch
would need: `hasContent` (`:690`), `isDivertedTerminal`/`showDivertedAffordance` (`:724-725`),
`terminalFailureNoDeliverable`/`isCancelledTerminal` (`:718`, `:735`) — the same signals
[FIX-357](20260828-2210-FIX-357.md) threaded into `FilesTab`, `WorkflowHistory` and
`RunDetailPage` for this identical "terminal, no-deliverable status" pattern, but never into
`SandboxTab`.

## Condition

- A run whose status is `failed`, `cancelled`, or `degraded` (not `diverted` — that case is
  already ISS-356) that never produced a deliverable (`output: null`,
  `deliverable_filename: null`, the same signature ISS-356's diverted runs show).
- Its sandbox directory has since been removed by the TTL sweeper (`RUN_DIR_TTL_HOURS`, default
  168h / 7 days, `backend/app/core/config.py:311`) — or forced sooner in a dev/test environment
  by lowering that setting or deleting the run's directory under `RUNS_ROOT` directly.
- Navigate to `/runs/{id}/workspace` for that run.

## Expected vs actual

- **Expected:** the same honest treatment ISS-356 asks for — the empty state should not assert
  a deliverable exists on Preview/Files for a run that never produced one, regardless of which
  non-diverted terminal status caused the emptiness.
- **Actual (predicted):** identical copy to ISS-356 — "The deliverable is still on the Preview
  and Files tabs — only the raw working files are gone" — because `SandboxTab.tsx:1037`'s
  `if (expired)` branch is unconditional on anything besides `res.expired`, and `res.expired`
  cannot distinguish a diverted run from a failed/cancelled/degraded one; both hit `not
  sandbox.root.is_dir()` identically once the TTL passes.

## Why the root cause implies this

ISS-356's defect is not "SandboxTab forgot to special-case `diverted`" — it is that SandboxTab
was never given ANY status/deliverable signal to branch on. A defect with that shape cannot be
diverted-specific: the branch has no code path that could differentiate diverted from any other
no-deliverable terminal status, because none of those statuses are visible to the component at
all. The bug is in what data the component *receives*, not in which status values it
*recognizes* — so every status that can reach a real, finished, deliverable-less run reaches the
identical false claim once its workspace expires.

**Marked INFERRED**: not independently reproduced in a browser. What would confirm it: seed or
find a `failed`/`cancelled`/`degraded` run with `output: null`/`deliverable_filename: null`
whose sandbox directory is already gone (or force it by lowering `RUN_DIR_TTL_HOURS` /
deleting the run's dir under `RUNS_ROOT` in a dev environment), then load that run's
`/runs/{id}/workspace` tab and confirm the same false copy renders.

## Where the fix belongs

Same two-hop shape [FIX-357](20260828-2210-FIX-357.md) already established for this exact
family of bug — and the same edit closes both ISS-356 and this card, not two separate fixes:

1. `SandboxTabProps` (`SandboxTab.tsx:842-849`) gains a prop carrying whatever the caller
   already knows about deliverable presence (e.g. a `hasDeliverable: boolean`, or the richer
   `isDivertedTerminal`/`isCancelledTerminal`/`terminalFailureNoDeliverable` flags mirroring
   `DegradedRunAffordance`'s own `cancelled`/`diverted` props), and the `expired` branch
   (`:1037-1047`) branches its copy on that prop instead of one hardcoded string.
2. `PreviewPanel.tsx:1406` threads the already-computed `hasContent` / `isDivertedTerminal` /
   `terminalFailureNoDeliverable` / `isCancelledTerminal` (all computed at `:690-738`, just
   never passed to `SandboxTab`) through as that prop — no new computation needed, only wiring.

One guard at the `SandboxTab` render branch, fed by PreviewPanel's existing status booleans,
closes both ISS-356 (diverted) and this sibling (failed/cancelled/degraded) in the same edit —
there is no reason to special-case per-status inside `SandboxTab.tsx` itself.
