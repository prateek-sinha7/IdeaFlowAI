## Decision

A pipeline step can be run by code instead of a model. It is declared with a
`mechanical:` key on the step:

```yaml
- agent: custom-agent
  instance_id: publish
  name: Publisher
  mechanical: publish
  depends_on: ["custom-agent:story-layer"]
  gates: [validation]
  validators: [html_static, html_render]
```

Two kinds exist today: `publish` (copy the highest `publish_from_glob` match onto
the deliverable name, `agents/capabilities/publish_step.py`) and
`assemble_prototype` (pour `parts/*.html` into the fixed shell, validate coverage,
`agents/capabilities/assemble_step.py`). Both exist because every LLM asked to do
that work narrated into the file or re-authored a 60-90 KB document from memory
and truncated it.

In the composer this is the **Node type** control: *AI agent* or *Code step*, with
a second dropdown listing the available kinds. Both dropdowns enumerate the live
registry via `/api/capabilities` — there is no hardcoded kind list in the
frontend.

## Why `mechanical` is a sibling field and not a strategy value

This is the non-obvious part, argued at `plan.py:435-455`.

`strategy` names are validated against the self-registering capability registry
and resolved through `registry.resolve("strategy", …)`. A step that never calls
that resolve has no business being a registered *strategy*: it would be a
compile-time-only phantom entry with no impl reachable through the seam it
pretends to satisfy (INV-12 — no dual/parallel mechanism).

So `mechanical` is its own step field, validated as a plain closed set inside
`compiler.py`. The *kind* still registers in the capability registry — under kind
`"mechanical"`, not `"strategy"` — but only so the composer palette can enumerate
and describe it (SC-001: a newly registered capability appears in the live
enumeration WITH its metadata, never from a static map in `app/api/`). The
registered class is a stub (`_PublishRegistryStub`, `_AssembleRegistryStub`); it
is never instantiated by `resolve`.

**Rejected alternative:** registering `publish` as a strategy. It would have made
dispatch a one-liner, at the cost of a registry entry whose `resolve` path is
dead code.

## What a code step may and may not declare

- **No `tools:`** — a mechanical step runs no agent, so a tool grant has nothing
  to bind to. The compiler *raises* rather than ignoring it
  (`compiler.py:914-919`). This is the D-17 rule: accepted-but-dropped is a
  compile error.
- **No prompt, no model.** The compiler does not police these; the composer
  simply never emits them — `agentToManifestStep` returns early for a mechanical
  node after writing `mechanical` and `gates`
  (`userWorkflows.ts:305-308`).
- **Gates and validators stay legal, deliberately.** A human gate before publish,
  or `html_static`/`html_render` on the published file, are both meaningful.
  `pdf_to_prototype`'s publish step uses all of them plus `require_render: true`.
- It still carries an `agent:` (in practice `custom-agent` + `instance_id` +
  `name`) because the engine keys every step by agent id.

## Adding a sixth code step

Five edits across four source files, plus one test list. Do them in this order.

**1. `backend/agents/capabilities/<name>_step.py`** — new module. Copy
`publish_step.py`; it is the smaller of the two. It needs three things:

```python
class MyStepFailed(Exception): ...          # named failure, never a bare Exception

@register("mechanical", "<name>", user_allowed=True,
          description="Plain-English, end-user facing — this text IS the palette tooltip.")
class _MyRegistryStub:                      # never instantiated by resolve()
    ...

class MechanicalMyStrategy:                 # the thing the engine actually runs
    name = "<name>"
    def __init__(self, *, spec, index, total, results): ...
    async def run(self, step, ctx) -> AsyncIterator[dict]: ...   # yields engine events
```

The module must not import `agents.execution_engine` or `app.*` (INV-13). Reach
disk only through the `ctx.runner` / `ctx.deliverable` handle.

**2. `backend/agents/capabilities/registry.py`** — two edits in this one file:
add `("mechanical", "<name>")` to the `_KNOWN` literal (~line 171), and add
`"agents.capabilities.<name>_step"` to `discover()`'s `_builtin_modules` tuple
(~line 300). `_KNOWN` is what the compiler validates against with zero impls
bound; `discover()` is what makes `@register` actually fire.

**3. `backend/agents/workflows/compiler.py:198`** — add the name to
`_ALLOWED_MECHANICAL_KINDS`. This frozenset is hardcoded; it does **not** derive
from the registry. `test_compiler.py:576` asserts the two are equal, so skipping
this edit fails a test loudly rather than silently — but it is still an edit you
must make.

**4. `backend/agents/execution_engine/engine.py:5977-5990`** — add an
`elif getattr(step, "mechanical", None) == "<name>":` branch that constructs your
adapter with `spec=spec, index=cursor, total=len(ordered_agents), results=results`.

**Then** update `_EXPECTED_NAMES` in
`backend/tests/agents/test_registry_capabilities.py` (~line 72) — it asserts
`set(_KNOWN) == set(_EXPECTED_NAMES)`.

**Frontend: nothing.** The palette is SC-001. Optionally add a `FRIENDLY_NAMES`
entry in `CanvasConfigRail.tsx:55-61`; without one the name falls back to
`humanize()` and the step is still selectable.

**Step 4 is the one that fails silently if you skip it.** Steps 1-3 and the test
list all fail loudly. The engine has no parity test, so an unhandled mechanical
kind falls through the `else:` to `_registry.resolve("strategy", strategy_name)`,
resolves the `single_shot` default, and runs a model on an empty prompt. That
trap is recorded as ISS-646; read it before you start.

## Task parsers are not code steps

A `task_parser` is a different registry kind and is not a step at all. It turns
an upstream step's output *file* into `list[Task]` for a fan-out strategy
(`json_tasks` reads `build/tasks.json`, `screen_plan` reads `build/screens.json`).
Registering a new parser is a different recipe with its own traps — see ISS-648
for the composer's hardcoded parser→target map, and ISS-647 for the call sites
that still parse the model's reply instead of the file.

Together, code steps and code-expanded task parsers are the prototype-v3 thesis:
code owns the plumbing, so no model writes a plan, a shell or a verdict.
