## The symptom

A fan-out wave could reach `pipeline_complete` with children missing. A worker
whose model call failed on the provider side was counted complete, its fragment
was never written, and the merge quietly shipped a partial result.

## The root cause

`run_fanout`'s per-worker loop tracked only `agent_complete` (for token usage)
and caught raised exceptions. But a provider failure — expired credentials, a
rate limit, a mid-stream fault — is **yielded** as an `agent_error` event, not
raised. The loop saw it go past, forwarded nothing, and fell through to the
normal terminal path.

This is the still-open [ISS-129](20260812-2116-ISS-129.md), filed 2026-08-12:
"`run_fanout` swallows EVERY worker event, including terminal ones."

## What changed

Three things, all in `fanout.py`.

**The discriminator.** The worker loop now tracks `saw_complete` and
`agent_error_msg` separately, and after the loop:

```python
if agent_error_msg is not None and not saw_complete:
    status = "failed"
    worker_error = agent_error_msg[:400]
```

An error **with no** `agent_complete` is the signal. This is the whole semantic
and it is not obvious from either half alone.

**Timeouts stay complete.** A timeout yields BOTH `agent_error` and
`agent_complete`, and that worker is deliberately left complete — the
best-available output *was* delivered. Collapsing the two cases would fail runs
that succeeded.

**Siblings are not aborted.** A raised exception is still caught per worker
(`except Exception` → `status = "failed"`, `worker_error = f"{type(exc).__name__}: {exc}"[:400]`),
so one failure marks one row and every other worker runs to completion. The
reason is carried on the result event because without it a failed row can only
say "Failed", leaving the reader guessing between a budget refusal, a tool error
and a model error.

**The run then fails.** `run_fanout` raises `FanoutWorkerFailed(failed_workers)`
(`fanout.py:113`, raised at `:792`) — but only after every worker's
`subagent_result` has been yielded and every terminal child event emitted, and
BEFORE merge. Nothing here suppresses a per-child signal, and merge only ever
integrated `status == "complete"` fragments, so skipping it on any failure is
consistent with what would have been merged anyway. Fan-out cancel (FANOUT-11)
propagates via its own `CancelledError` path and is unaffected.

Worker `task_id` / `task_author_id` threading landed alongside in `05b7bce54`
(`fanout.py`, `kernel_services.py`), so a nested fan-out can name the parent task
it came from.

## Consequence

Fan-out is now fail-closed. That is correct, and it makes the transient-error
classifier load-bearing: one unlucky worker now ends the wave, which is exactly
the incident [FIX-564](20260918-FIX-564.md) exists to prevent. Read the two
together.
