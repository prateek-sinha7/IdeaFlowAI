# ISS-720

## Title

Root-cause card for **QA-PS-032**: Workspace tab shows 0 B for all file sizes when any
versioned ref is selected.

(Originally minted as ISS-702; renumbered to ISS-720 after a same-day id collision with an
unrelated QA-PS-054 card also claiming ISS-702 in this same concurrent batch — see Traceability.)

## Status: CONFIRMED — read directly in the live source, matches the validator's 3/3 repro

## Root cause

`backend/app/api/run_files.py:889-968` is `list_sandbox(run_id, ref=None)`. It has two
branches. When `ref` is supplied (920-944), it builds:

```python
files_payload = [
    {
        "path": p,
        "size": 0,                                    # run_files.py:930
        "kind": kind,
        "text": kind == "text",
        "deliverable": is_deliverable_relpath(p),
    }
    for p in raw_paths
    for kind in (_sandbox_kind(p.rsplit("/", 1)[-1]),)
]
```

`size` is a **literal `0`**, not an arithmetic error or a dropped key — it was never computed
for this branch. Contrast the `ref is None` branch immediately after (946-967): it starts from
`sandbox.list_files()` and spreads `**f`, where `f` already carries real `size`/`modified` from
`full.stat()` (`backend/app/agents/sandbox.py:793,796`: `st = full.stat()` /
`files.append({"path": relpath, "size": st.st_size, "modified": st.st_mtime})`).

`raw_paths` — the only input the ref branch has — comes from `sandbox.list_files_at_ref(ref)`
→ `LocalWorkspace.list_files_at_ref` (`backend/app/agents/runtime/local.py:1077-1098`), which
runs `git ls-tree -r <ref> --name-only` (`local.py:1090`) and returns `list[str]`: bare
relpaths, by construction. `--name-only` strips mode/type/blob-sha/size; nothing downstream
ever runs `git ls-tree -r -l <ref>` (long format — appends an object-size column) or a per-blob
`git cat-file -s`. The function's own return type (`list[str]`) makes a size structurally
unavailable to `run_files.py` for this branch — `0` is a placeholder standing in for data that
was never fetched, not a value that came out wrong.

Same shape for `modified`: the live branch's dict carries a `modified` key (`sandbox.py:796`);
the ref branch's dict never has one (`run_files.py:927-934` lists only
`path/size/kind/text/deliverable`). This is exactly the QA report's own aside — "Latest
(live)...plus a `modified` timestamp field absent from the ref response" — same root cause, one
symptom visible (`size`, because the UI renders it) and one silent (`modified` — nothing in
`SandboxTab.tsx` currently reads that key, confirmed by `grep -n "modified"` returning no hits
in that file, so there is no user-visible break to report for it today).

## Why this is NEITHER Defect A, B1, nor B2 (mapsToKnownDefect: new)

- **Not Defect A** (stale content replayed from v1 at every tag): Defect A is about the wrong
  BYTES being served at a tag. This bug reproduces identically whether or not Defect A is
  present — even with genuinely different content at each tag, `size` would still read `0` for
  every file, because the code that builds `size` never inspects content or blob length; it is
  a hardcoded literal, unconditional on tree contents.
- **Not B1** (`WorkflowRun.git_tag` stays NULL) **or B2** (`.git` silently rebuilt, orphaning
  tags): both are about a ref FAILING TO RESOLVE or a family losing its tags. All three of the
  validator's requests returned `200` with the correct file set — `_validate_ref` passed and
  `list_files_at_ref` returned real paths in every case. This defect is entirely downstream of
  a **successful** ref resolution.
- Independent confirmation: `kind`/`deliverable` (also derived from the same `raw_paths`) were
  correct in the QA report ("file names/kinds/deliverable flags were correct in every case") —
  only the one field nobody wired up (`size`) is wrong. That selectivity is what an unfilled
  placeholder looks like, not what a tag/content mixup would produce (which would also corrupt
  paths or content).

## Evidence (validator's reproduction)

- `GET .../f7000bbd.../sandbox?ref=v2` → 200, every file `"size":0`
- `GET .../e53d9b1f.../sandbox?ref=v1` → 200, every file `"size":0`
- `GET .../dfeb5949.../sandbox?ref=v3` → 200, every file `"size":0`
- `GET .../dfeb5949.../sandbox` (no ref) → 200, real sizes + a `"modified"` field

Matches `run_files.py:920-944` (ref branch, hardcoded `0`, no `modified` key) against `946-967`
(live branch, real `st.st_size`/`st.st_mtime`) exactly.

## Fix location (for the fixer — not applied here)

Belongs inside the ref branch of `list_sandbox` (`run_files.py:920-944`), fed by a size-aware
read of the git tree (e.g. `git ls-tree -r -l <ref>`, which appends a size column in long
format, parsed into a `{path: size}` map) — **not** by changing `list_files_at_ref`'s existing
`list[str]` return contract in place.

## Fix risk — what breaks if done carelessly

`list_files_at_ref` (`local.py:1077`) has a **second, unrelated caller**:
`backend/app/api/run_commands.py:4546` (`entries = src.list_files_at_ref(ref)`), which treats
the return as `list[str]` for chain-payload shape validation (`e.startswith(".chain/")`, set
membership against `_FIXED = {".chain/logs.jsonl", ".chain/summary.md"}`). Five test files also
pin the same `list[str]` contract: `backend/tests/agents/test_chain_exact_ref.py:126,491`,
`test_phase6_sandbox_versioning.py:310-328,743-781,990-1009`, `test_version_family_v5.py:172-295`,
`test_rollback_safety.py:191,668,728`, `test_revision_ordinal_v3.py:388`. Widening
`list_files_at_ref` itself to return sizes (e.g. `list[dict]`) breaks all of the above. The safe
shape is an additive sibling call used only by `run_files.py`'s ref branch, leaving
`list_files_at_ref` and its existing callers/tests untouched.

## Blast radius

- **Confirmed broken by the same missing-size data**: every row in the Workspace tab file list
  (`frontend/src/components/results/SandboxTab.tsx:905`, `formatBytes(file.size)`) when a ref is
  selected. The open-file viewer header reads the same field — filed separately as
  [ISS-703](20260922-1233-ISS-703.md) since the validator's repro never opened a file. Sort-by-size
  (`SandboxTab.tsx:149`) degrades to a no-op tie under a ref (every row reads `0`) — same view,
  not filed separately, just noted here.
- **Confirmed NOT broken**: `GET /{run_id}/sandbox/file?ref=` (single-file read via `git show`)
  serves raw bytes and never touches `size`.
- **Confirmed broken a different way**: `GET /{run_id}/sandbox/zip?ref=` — same missing-size data,
  but here it means the 64MB zip cap is skipped entirely rather than displayed wrong. Filed as
  [ISS-704](20260922-1234-ISS-704.md).
- `backend/app/api/run_commands.py:4546` also calls `list_files_at_ref`, but only for
  path-membership checks — no `size` read, unaffected.
