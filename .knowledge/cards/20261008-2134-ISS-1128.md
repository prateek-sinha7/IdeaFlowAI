# ISS-1128

**Register source:** sibling derived during the `QA-KB-103` analysis on 2026-10-08 (root [ISS-1118](20261008-1444-ISS-1118.md)). Not its own bug row.
It predates [FIX-766](20261008-1444-FIX-766.md): nothing FIX-766 changed produced it. What FIX-766 changed is that, for these built-ins, it is
now the only kind of save that gets through.

**Confidence:** the PAYLOAD is CONFIRMED. The real canvas serializer (`buildWorkflowManifest`, `agentsFromManifest`) was run against the live
`GET /api/workflows/{id}?original=true` and `GET /api/agents/library`, and its output was fed to the real `compile_override_steps`
(`evidence/qa-kb-103/analysis-02`, `analysis-07`, `analysis-06-serializer-payloads.json`). INFERRED: that a browser reaches the library seed on
the LaunchWizard (warm navigation), and what the engine does with `single_shot` where the file said `task_loop`. The validator did observe
the 201 for `app_builder` (4 attempts) and the three revision pipelines through the UI (`evidence/qa-kb-103/03-validate-attempt1-after-save-as-my-version.png`
to `05-validate-attempt3-...png`, `prototype_revision-after-save-as-my-version.png`, `prototype_feature_revision-...png`, `prototype_large_revision-...png`);
no stored row was read back, and the dev DB holds none (`analysis-04`).

What would settle it: from `/dashboard`, navigate (do not reload) to `/create/prototype` so the agent library is already in Redux, press
Save as my version, then read the row (`GET /api/user-workflows/{id}`, `manifest.steps`) and `GET /api/workflows/prototype`. Expect
`prototype-build.strategy == "single_shot"` and no `compaction`, `task_source`, `validators` or `require_render`.

## Condition

The roster behind "Save as my version" has three possible seeds, and only one of them carries the built-in's own step keys
([ISS-1118](20261008-1444-ISS-1118.md) "Why only some saves 422"):

- **LaunchWizard**: `pipelineAgents` starts as the library roster (`LaunchWizard.tsx:308`). The compiled plan replaces it only when the plan has MORE
  steps than the library found (`:538`: `planAgents.length <= prev.length` returns `prev`). `prototype` has five steps and the library has five
  agents for it, so after a warm navigation the library roster stays and `handleSaveAsOverride` (`:1054-1059`) posts library agents. Cold start
  is the other way round: the plan lands first, `prev` is empty, the plan roster wins and carries `extra` (that is the 422 of the root card).
- **IdeaInputPage**: the library roster when it is complete (`IdeaInputPage.tsx:1448-1451`), otherwise the hand-rolled `manifestAgents`
  projection (`:1284-1310`), which sets no `extra` and keeps `tools`, `skills`, `prompt` and `route`. Its own comment calls it a copy that
  "predates" `lib/manifestAgents.ts` (`:1264-1266`).
- A library `AgentDef` has no `extra` (`GET /api/agents/library` returns id, name, role, order, pipeline_type, prompt_body and presentation fields),
  and `agentToManifestStep` stamps `strategy: "single_shot"` on any leaf that declares none (`userWorkflows.ts:429-436`).

What a PASSING unchanged payload loses or alters against the built-in's own file steps (`analysis-07`, gates, depends_on and `exec: false` ignored):

| built-in | surface | seed | lost from the stored override | altered |
|---|---|---|---|---|
| prototype | LaunchWizard | library | `prototype-specify.skills` (velocity-design), `prototype-build.task_source`, `.validators`, `.require_render`, `.compaction` | `prototype-build.strategy` task_loop -> single_shot; `prototype-specify.tools.write_files` false -> true |
| prototype_feature_revision | IdeaInputPage | library | `prototype-revision-analyzer.produces_solution_plan`, `prototype-build.task_source`, `.validators`, `.require_render`, `.post_step`, `.compaction` | `prototype-build.strategy` -> single_shot |
| prototype_large_revision | IdeaInputPage | library | the same six | `prototype-build.strategy` -> single_shot |
| prototype_revision | IdeaInputPage | library | `produces_solution_plan`, `prototype-revision-agent.validators`, `.require_render`, `.post_step` | none |
| app_builder | IdeaInputPage | library | `app-infra-generator.post_step` (api_prefix_audit) | none |

`ppt`, `user_stories`, `chat`, `custom`, `mulesoft_to_springboot`, `dotnet_to_azure` and the `*_revision` pipelines of app_builder, ppt and
user_stories are faithful on every seed (`analysis-07`). The hand-rolled seed also loses 50 keys on `backlog` (its `produces`, `consumes`, `model`
and `mechanical` among them) and 21 on `prototype_v2`. Which surface hosts those two was NOT traced: both declare `launch_surface: wizard`, but
`selectWorkflowWizardPath` routes only ppt, ppt_v2 and prototype (`frontend/src/store/slices/globalSlice.ts:250-257`) and `LaunchMode` has no
`backlog` (`frontend/src/lib/launchDraft.ts:38`). If `/create/backlog` is hosted by IdeaInputPage, an unchanged save there loses those keys;
that is a lead for whoever reproduces this card, not a finding.

The override then REPLACES the file plan wholesale (`overrides.py:140`: `dataclasses.replace(compiled, steps=list(user_compiled.steps))`), so
the user's "version" of `prototype` runs a build step without the per-task loop that `backend/CLAUDE.md` describes ("Prototype build: per-task
sub-agents + validation") and without the render and static validators.

## Expected vs actual

Expected: an UNCHANGED Save as my version stores the built-in's own plan, so its version runs like the built-in until the user changes something.
That is what the register row for `QA-KB-103` asks for ("Saving an unchanged or lightly edited override of a built-in succeeds"). Actual: the save
succeeds with 201 and stores a different workflow, with no message.

## Why the root cause implies it

Same round trip, the other seed. The client's roster seed decides whether the built-in's engineer-only references are present (plan seed: 422)
or absent (library and hand-rolled seeds: silently dropped, plus the `single_shot` default). FIX-766 refuses the faithful payload and leaves the
degraded one passing, so a user who gets a 201 on `prototype` has, on this evidence, saved the worse plan. It also corrects a premise of
[ISS-1118](20261008-1444-ISS-1118.md): "Before FIX-766 such a save answered 201 and the override ran those engineer-only capabilities" is true only
for the plan seed. Library-seeded saves never carried them.

## Fix direction (INFERRED, not applied)

Make the save independent of the seed. Either (a) both surfaces build an override's roster from the manifest projection (`agentsFromManifest`,
which carries `extra`) and rely on the server's inherited-reference decision from [ISS-1118](20261008-1444-ISS-1118.md) to accept it, or (b) the server
overlays the baseline step's keys that the posted step lacks. Not a client strip: it would make the plan seed degrade the same way. Whichever is
chosen, `IdeaInputPage.tsx:1284-1310` is a duplicate of `lib/manifestAgents.ts` and should retire into it (`:1264-1266` says so).
