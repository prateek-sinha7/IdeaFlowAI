## Reproduction (each attempt from a cold navigation to /workflows/new)

Signed in as `qa-admin@flowinqa.com`. Attempt 1: direct `page.goto`. Attempt
2 and 3: navigate away to `/library` first, then `window.location.href` to
`/workflows/new` (full page load, not a client-side transition). Network
tab (Fetch/XHR) inspected via `mcp__lane1__browser_network_requests` after
each load.

All three attempts show the same duplicate pattern on `/workflows/new`:

| Request | Count each attempt |
|---|---|
| `GET /api/capabilities` | **2×** (identical ~27.5 KB response both times — confirmed via `content-length: 27565` on both calls in attempt 3) |
| `GET /api/workflows` | **2×** |
| `GET /api/runs?limit=50` | **2×** (~30 KB each, `content-length: 30228` — confirmed in attempt 3) — the composer shows no run history, this data is not rendered on the page |
| `GET /api/runs?limit=6` | 1× — fired by the dashboard-layout shell, not composer-specific, but still loaded on a route that shows no run list |
| `GET /api/auth/me` | 1× |
| `GET /api/agents/library`, `/api/skills/library`, `/api/hooks/library` | 1× each — new since the original 2026-09-17 report, not mentioned there |

validation confirms the CLASS of defect, not the original request count.

## Root cause

Two independent components mount together in the composer and each does its
own capability fetch with no shared cache, because the fetchers are plain
`fetch`-wrapper functions, not deduped/cached hooks:

- `getCapabilities` in `frontend/src/lib/api.ts:1687` (`request<CapabilitiesPalette>("/api/capabilities", ...)`)
- Also duplicated as `capabilitiesApi.get` in `frontend/src/store/api/capabilities.ts:36` (`http.get<CapabilitiesPalette>("/api/capabilities")`)

Callers that independently invoke `getCapabilities` on mount, both live in
the composer tree simultaneously:
- `frontend/src/components/workflow/AgentsPopup.tsx:24` (imported as `fetchCapabilities`)
- `frontend/src/components/workflow/AgentModelPicker.tsx:74` (`getCapabilities(jwt)` in its own effect)

Neither call is deduplicated/memoized (no RTK-Query cache, no SWR, no
in-flight promise sharing) — each mounted component fires its own network
request for the same data. The same pattern applies to the two `/api/workflows`
calls: `getWorkflows`-shaped fetchers exist in more than one place in
`frontend/src/lib/api.ts` (line 770 and the SURF-03 fetcher documented near
line 1735, "getWorkflows is already taken by the run-history fetcher"),
invoked independently by the app shell (nav/catalog) and by
`ComposerPage.tsx`.

`GET /api/runs?limit=50` firing on `/workflows/new` even though the
composer renders no run list is a separate, additive waste: it appears to
be a shell-level prefetch (dashboard layout / run-history hook) that is not
route-gated to skip on the composer.

## Decision — 2026-09-23 (user, option a)

For **QA-PS-046** the user chose option (a) (`ESCALATIONS.md#qa-ps-046`, recorded
01:34): the app shell's one `GET /api/runs?limit=50` (AppHeader's "N Running"
badge, the SSE live-run re-attach) and one `GET /api/workflows` per page are
intended. The "`GET /api/runs?limit=50` firing on `/workflows/new`" waste finding is superseded by that decision, and
`test_workflows_new_does_not_fetch_run_history` now asserts at most one
`runs?limit=50`. The waste that needed no decision — `runs?limit=6` preloaded on every
route, and a second owner of `runs?limit=50` — is removed by
[FIX-640](20260923-0207-FIX-640.md). Observed green on 2026-09-23 once the frontend was back on :3000: the
re-scoped test XPASSed (strict), its marker was removed, and a plain re-run
PASSED — `tests/integration/test-runs/2026-09-23T02-16-fix-640-qa-ps-046/`, then `2026-09-23T02-18-fix-640-qa-ps-046-plain-solo/`.
