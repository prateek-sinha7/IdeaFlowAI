## What was wrong

This is bug report QA-KB-033. The last assertion in
`frontend/src/app/[...view]/workflowDetailCatch.source.test.ts` counted the 403/404 narrowing
idiom (`if (err instanceof ApiError && (err.status === 403 || err.status === 404)) {`) across the
whole of `page.tsx` and pinned the count with `expect(occurrences).toBe(5)` (`:86-87` before this
fix). A new catch block that adopted the idiom correctly would fail it with "expected 6 to be 5",
a message that names no site. That had already happened twice. The ISS-380 fix and
[FIX-368](20260829-0106-FIX-368.md) each added a correct site, and each one needed a bump, from 3
to 5 (see [ISS-442](20260829-0106-ISS-442.md)). The exact pin was also blind in the other
direction. A site that regressed to swallow-all, plus an unrelated new site, nets to 5 and stays
green.

`launchImageAndRecents.source.test.ts:31-34` had the same shape
([ISS-867](20261001-2106-ISS-867.md), INFERRED, latent). It applied `toBe(2)` to the whole-file
count of `pending.images && pending.images.length > 0` as a stand-in for "both launch setters
carry images".

The application is correct, and this fix did not edit `page.tsx`. When the fix was checked
(21:17 to 21:19) the file matched HEAD. It had five narrowed catches (`:561`, `:3321`, `:3801`,
`:3851`, `:4019`) and two guarded spreads (`:2542`, `:2626`). At 21:20 a fixer working on another
bug added five lines to `page.tsx`: three at `:1341`, one at `:3784` and one at `:3985`. None of
those lines contains the idiom or the spread, and the counts are still 5 and 2. The catches are now
at `:561`, `:3324`, `:3805`, `:3855` and `:4024`, and the spreads at `:2545` and `:2629`. Both
files were green again at 21:26:48. The mirror runs below used the edited file.

## Root cause

[ISS-442](20260829-0106-ISS-442.md) holds the analysis. An exact count of text occurrences over
the whole file measures an aggregate as a stand-in for a property of each site. That makes it
over-sensitive, because a legitimate addition fails it, and under-sensitive, because a regression
offset by an addition passes it. The comment above the pin already said that only a drop matters
("a DROP means a catch block went back to swallowing every error"), so equality asserted more than
the test meant. [ISS-867](20261001-2106-ISS-867.md) is the same mechanism applied to the images
spread.

## Change

The change is in the two test files only. Each one changes one assertion, plus the `it` title and
the comment that describe it.

- `frontend/src/app/[...view]/workflowDetailCatch.source.test.ts:78-91`: `toBe(5)` became
  `toBeGreaterThanOrEqual(5)` (`:90`). The title is now "keeps a floor of 5 catch blocks on the
  narrowed 403/404 pattern (a drop fails, a new site does not)". The old title said "exact ... (no
  drift)". The comment names the five sites: the canvas seed fetch (FIX-368), run-detail (T24),
  `/edit` (T8), the read-view (T30) and `/run` (ISS-380). It also states the rule. Raise the floor
  when you add a site so the new site is protected too. Lower it only when a site is deliberately
  removed, and never to turn a regression green.
- `frontend/src/app/[...view]/launchImageAndRecents.source.test.ts:31-41`: `toBe(2)` became
  `toBeGreaterThanOrEqual(2)` (`:40`). The title is now "keeps a floor of 2 length-guarded images
  spreads, one per launch setter (prototype + ppt)". The old title claimed "BOTH", which a
  whole-file count cannot prove. The comment names `setPendingOdProtoParams` and
  `setPendingOdPptParams` and states the same raise and lower rule.

Two choices depart from the "agreed minimal fix" in BUGS.md. Both follow the ruling in the ISS-442
analysis:

- The floor is 5, not 3. A floor of 3 would let two of today's five sites revert silently
  (scenarios S4 and S2 in ISS-442).
- The test was kept, not deleted. This count is the only source-level lock on four of the five
  sites (T24, T8, FIX-368, ISS-380). Only T30's site has scoped assertions of its own.

The disposition in ISS-867 said "do not fix as part of QA-KB-033" and "decide once". The line then
put ISS-867 on this bug's ledger row, and the dispatch applied the ISS-442 floor decision to both
cards. That is why it is fixed here.

## Why there

The defect is in what the assertion claims, so the fix is in the assertion. Nothing in `page.tsx`
is wrong. A frontend test-only change cannot touch SC-001, the import-linter contracts or
migrations.

A floor has a known ceiling, which ISS-442 accepts knowingly. Like the exact count before it, a
floor cannot see a regression that is offset by a new site (the S3 rows below). A per-site form
would close that gap. For ISS-442 it would require, for each setter, that the text from the
nearest `catch` to the setter's `set...(true)` call contains the idiom. For ISS-867 it would slice
each setter call. Neither card requires this, and it was not done here.
