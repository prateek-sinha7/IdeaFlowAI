## What was wrong

On `/library/agents/<agentId>` the drawer's Skills tab rendered live "+" buttons. Clicking
one filled the button with a checkmark and put a count badge on the "Skills" header — full
success feedback — while firing zero network requests. The tab has no Save/Cancel control at
all, and a reload wiped the selection with no warning. Reported as
`BUG-20260828-092630-library-agents-id`, root-caused in
[ISS-318](20260828-1956-ISS-318.md).

## Root cause

`AgentSkillsPicker` documents the contract at
`frontend/src/components/workflow/composer/AgentSkillsPicker.tsx:44-49`: `readOnly` exists
for the mounts with nowhere to write back, and it names the Library page's agent drawer as
one of them. `AgentCapabilitiesModal` derives that flag from the caller —
`readOnly={!onSkillsChange}`, `frontend/src/components/workflow/AgentsPopup.tsx:873`.

`LibraryPage.tsx:1061` (pre-fix) supplied `onSkillsChange` anyway, whose whole body was
`savedSkillsRef.current[agentId] = skills` — a plain `useRef` scoped to `LibraryPage`'s own
mount lifetime (`LibraryPage.tsx:678` pre-fix). Supplying it flipped `readOnly` to `false`,
which is what turned the picker into an interactive surface, and the modal's `localSkills`
mirror (`AgentsPopup.tsx:561-568`) is what made the checkmark and badge repaint. A catalog
agent belongs to no workflow step, and no backend stores per-agent skill grants for one, so
nothing downstream ever read that ref: the deep-link path
(`LibraryPage.tsx:602` — `setSelectedAgent({ agent, index })`, no `savedSkills`) does not
even snapshot it, which is exactly the reload-wipe in the report.

## What changed and why there

One file, `frontend/src/components/library/LibraryPage.tsx` — the caller that violates the
contract, not the picker or the modal that implement it correctly:

- dropped the `onSkillsChange` prop from the `AgentCapabilitiesModal` mount, which is the
  single line that flips `readOnly`;
- removed what that prop orphaned: `savedSkillsRef`, the `savedSkills` field on the
  `selectedAgent` state, its open-time snapshot on the agent card's `onClick`, and the
  `agent={{...agent, skills: savedSkills ?? agent.skills}}` seed (now `agent={selectedAgent.agent}`).

`savedSelectionsRef` and the Config tab's `onSelectionsChange` are deliberately untouched —
that is [ISS-392](20260828-2250-ISS-392.md)'s separate defect.

Not fixed in `AgentsPopup.tsx` despite the register's "fix belongs in AgentCapabilitiesModal"
line: `readOnly={!onSkillsChange}` is the correct derivation of the documented contract, and
the other three mounts that pass the callback (`CanvasConfigRail`, `AgentRow`, and the
`AgentLibrary` add-agent modal under `ComposerPage`) genuinely persist through the composer's
`pendingSkills`. Changing the derivation would break them; `LibraryPage` was the only caller
lying about it (grepped every `AgentCapabilitiesModal` / `onSkillsChange` site in
`frontend/src`).

Result on the live app: the "Add &lt;skill&gt;" buttons render disabled, no count badge
appears, and the picker shows its own honest hint — "Attach skills to this agent in the
workflow composer." — which is where per-agent skills actually live (ADR-0010).

## The test does NOT confirm this — read before verifying

`tests/integration/e2e/suites/08_library/test_iss318_agent_skills_add_persists.py` asserts the
OTHER remedy from ISS-318's "Expected" section: that Add fires an `/api/agents*` or
`/api/skills*` request and that the grant survives a fresh navigation. That branch needs a
backend surface that does not exist — built-in filesystem agents carry no `skills` field at
all in `GET /api/agents/library` (`backend/app/api/agents.py:216-232`), and only
`user-agent:` rows have one — so it would take a new endpoint plus a migration, and
[ADR-0010](20260811-ADR-0010.md) decided the opposite ("runs with no per-agent UI ... can no
longer attach skills at all"). Both tests therefore still report XFAIL after this fix, and
the file was left exactly as written. Which remedy is the product answer is an open decision;
the register entry is ESCALATED, not FIXED, for that reason.
