# ISS-926

**Bug register entry:** derived from QA-KB-020 (`BUGS.md#qa-kb-020`, `LEDGER.md`) — root-cause card [ISS-654](20260917-1250-ISS-654.md)

## Status: INFERRED — not yet reproduced

The mechanism is CONFIRMED by reading the code. The user-visible effect has NOT been observed.
Whoever picks this up should confirm it offline first (see "What would confirm this"), which
needs no paid run.

## Why QA-KB-020's root cause implies this

[ISS-654](20260917-1250-ISS-654.md)'s premise is that `useRunChat`'s transcript is family-anchored
by design: frames of several runs fold into ONE array (`frontend/src/types/index.ts:123-125`,
`useRunChat.ts:400-407`), so any hook-level state that assumes a single run's stream is wrong
for a family. The gate handler's array-position match is one such assumption. `lastSeqRef` is
the hook's other transcript-global scalar, fed by frames of every run:

```ts
// frontend/src/hooks/useRunChat.ts:505-508  (handleFrame, no run check)
const seq = typeof data.seq === "number" ? data.seq : undefined;
if (typeof seq === "number" && seq > lastSeqRef.current) {
  lastSeqRef.current = seq;
}
```

## Mechanism (CONFIRMED by reading the code)

`run_events.seq` is unique per run, not across runs. The reader filters one run by it:

```python
# backend/agents/authz.py:407-412
query = session.query(RunEvent).filter(
    RunEvent.run_id == run_id,
    RunEvent.seq > after_seq,
)
```

and the page itself states the per-run scope when it has to merge family frames:
`page.tsx:3154-3159` ("seq is per-run-scoped (each run starts at 1)"), `engine.py:4197-4199`
("the chat lane allocates from this same per-run space").

A family seed folds every member's frames through `handleFrame` (`useRunChat.ts:744` over
`familyChatFrames`, `page.tsx:3210-3224`), so `lastSeqRef` ends at the HIGHEST seq of ANY member.
Two consumers then use that scalar against ONE run's seq space:

```ts
// frontend/src/hooks/useRunChat.ts:716-719  (re-fetch after a send, DEF-44-12-2)
if (!fetchEvents) return;
try {
  const newFrames = await fetchEvents(postRunId, lastSeqRef.current);
  for (const f of newFrames) handleFrame(f);
```

```ts
// frontend/src/app/[...view]/page.tsx:1661-1662  (FIX-172/176 completion recovery)
const afterSeq = getRunChatLastSeqRef.current?.() ?? 0;
const frames = await getRunEvents(tok, _completingRunId, afterSeq);
```

(`getRunChatLastSeqRef` is the hook's `getLastSeq`, `useRunChat.ts:809-811`; `page.tsx:2458-2462`.)
Those are the only two readers of the hook's cursor.

## Expected (once reproduced)

Each fetch asks the run it targets for events after THAT run's last seen seq.

## Actual (inferred, not yet observed)

When another family member's seq range exceeds the viewed run's (a long parent plus a shorter
revision is the natural case), `after_seq` is above every row of the viewed run and the fetch
returns nothing:

- A chat turn sent on the revision run: its Concierge reply is "durable-only (never queued → the
  live tail never carries it)" (`useRunChat.ts:698-704`; same words at `page.tsx:2443-2446`), and
  this re-fetch is the only thing that renders it, so the reply would not appear until a reload.
- FIX-172's recovery of the narrator "Delivered" card after `detachRun` (`page.tsx:1626-1662`)
  would find nothing for a revision whose seqs sit below the parent's. FIX-176's own comment
  assumes "the last event in a run ... arrive[s] after lastSeq", which only holds for a
  single-run transcript.

## What would confirm this

Offline, no paid run (one file, `frontend/src/hooks/useRunChat.test.ts` harness):

1. `renderHook(useRunChat({ runId: "R", subscribe, sendCommand, fetchEvents: vi.fn(async () => []) }))`.
2. `seedTranscript([...frames of run "P" with seq up to 500..., ...frames of run "R" with seq 1..20])`.
3. `await act(async () => { result.current.sendMessage("hi"); })`, then let the fire-and-forget
   async block settle (`vi.waitFor`).
4. Assert `fetchEvents` was called with `("R", 20)`. Today it is called with `("R", 500)`.

## Fix direction (INFERRED, not a decision)

Track the cursor per run (a `Record<runId, number>` keyed by the frame's `pipeline_run_id ??
run_id`), have the re-fetch and `getLastSeq` read the entry of the run being fetched, and keep a
global fallback for frames that carry no run id. Deliberately not designed here.

## Blast radius

`lastSeqRef` readers: `useRunChat.ts:718` and `getLastSeq` -> `page.tsx:1661`. The PAGE's own
`lastSeqRef` (`page.tsx:663`, `:1149-1150`) is a separate cursor and is not claimed here.

## Fixed (2026-10-02, QA-KB-020 fixer): [FIX-700](20261001-2242-FIX-700.md)

The fix direction above, frontend only. `lastSeqRef` is a `Record<string, number>` keyed by the
frame's `pipeline_run_id ?? run_id`. A frame that names no run is counted for the hook's `runId`
(the viewed run, since `chatSubscribe` delivers only its frames) rather than a separate global
slot. The post-send re-fetch reads `postRunId`'s entry, `seedTranscript` resets the map, and
`getLastSeq` takes the run it is asked about; its one caller, the FIX-172 completion recovery in
`page.tsx`, passes `_completingRunId`. The test-writer's `it.fails` ("re-fetch after a send asks
the viewed run for ITS last seq, not the family max") now reports "Expect test to fail", so
`fetchEvents` is called with `("R", 20)`. Marker left for the verifier. The effect itself was
reproduced offline only, never in a browser.
