## What happened

In the App Builder preview's IDE-style file explorer (`/runs/<id>` Preview tab and its
`/preview-fullscreen` popout), a markdown `###` subheading inside a generated documentation
file is mis-parsed as a standalone project file when the heading text happens to contain a
dot followed by word characters and is immediately followed by a fenced code block — the
exact shape of a normal-prose heading like `### Via Node.js` (library name with a version-like
dot) is indistinguishable, by this regex, from a real file path heading like `### src/app.js`.

Corresponds to register entry `BUG-20260828-105300-preview-fullscreen-r2` (round 2 of that
bug; round 1's report on the same fingerprint was flagged weaker evidence because it hand-seeded
`sessionStorage`).

## Root cause

`frontend/src/components/preview/PreviewPanel.tsx:92`, inside `parseAppBuilderFilesForIDE`:

```ts
// Format 2: ### path/to/file.ext\n```[lang]\n[content]\n```
const headerRegex = /###\s+([\w./\-@][^\n]*\.\w+)\s*\n```[^\n]*\n([\s\S]*?)```/g;
```

This regex exists to catch code-producing agents that label a file with a `### path/to/file.ext`
heading before a fenced block (used by feature-implementation/test-implementation/api-design/
devops agents). It has no way to distinguish that from a documentation heading that merely
*contains* a dot-plus-word-chars substring (a library name like "Node.js", "Vue.js", "Chart.js",
a version number, an abbreviation) directly followed by an unrelated fenced code sample — both
match `[\w./\-@][^\n]*\.\w+` identically. `addFile()` (`PreviewPanel.tsx:60-81`) then accepts the
match because its only file-shaped check is "the last path segment contains a dot"
(`hasDot = name.includes(".")`, line 66) — `"Via Node.js"` passes that check purely because of
the dot in "Node.js", not because it is a real path.

The phantom entry then flows unmodified through `buildTree()` (`AppBuilderPreview.tsx:71-92`,
listed as a root-level "file") and `CodeViewer.handleDownload()` (`AppBuilderPreview.tsx:248-254`):

```ts
const handleDownload = () => {
  if (!file) return;
  const blob = new Blob([file.content], { type: "text/plain" });
  const url = URL.createObjectURL(blob);
  const a = document.createElement("a");
  a.href = url;
  a.download = file.name;   // ← verbatim, no sanitization/extension fallback
  a.click();
  ...
```

`file.name` is used verbatim as the saved filename, so the browser download is literally named
`"Via Node.js"` — no extension, containing a space — and the file's `ext` field ("js", derived
from splitting on the dot in "Node.js") drives a bogus JS syntax highlight of what is actually a
markdown heading's neighboring code sample. The same phantom entry is included, unfixed, in
"Download ZIP" as a top-level extensionless entry alongside the real `.md` files.

## Reproduction — validated 3/3 cold-start cycles, 2026-08-28

The original run this was hunted against (`37aabc96-6e71-4d2b-ac30-90a827c8b862`, "A hello
world app.") no longer exists in `qa-admin`'s run history at validation time (`GET
/api/runs/<id>` → 404 "Workflow run not found" — the run was purged/rotated between the hunt
and this validation pass, an environment condition, not part of the bug). Round 2's evidence
folder (`bug-hunter/evidence/preview-fullscreen/BUG-20260828-105300-preview-fullscreen-r2/notes.md`)
had already captured that run's real README markdown verbatim, including the exact
`### Via Node.js` / fenced-`javascript` section that triggered the bug.

Each of the 3 cycles below ran the ACTUAL `parseAppBuilderFilesForIDE` regex (copied verbatim
from `PreviewPanel.tsx`) against that real captured markdown inside the live app (via
`page.evaluate`, executed against the genuine app origin), wrote the resulting `files[]` +
`projectName` into `sessionStorage["__app_preview__"]` — the same shape
`AppBuilderPreview.handleFullscreen()` itself writes before opening `/preview-fullscreen` — then,
from a cold navigation to `about:blank`-equivalent (`/dashboard`) with `sessionStorage.clear()`
run first, navigated fresh to `/preview-fullscreen` and exercised the real Explorer/CodeViewer/
Download UI:

- **Cycle 1:** Explorer showed 4 entries including `"Via Node.js"`, footer "4 files"; selected it
  in the code viewer (ext "js", "8 lines"); clicked Download → `download.suggestedFilename()` =
  `"Via Node.js"`.
- **Cycle 2:** same cold-start sequence (dashboard → clear sessionStorage → re-seed → fresh nav
  to `/preview-fullscreen`) → identical result, `suggestedFilename()` = `"Via Node.js"`.
- **Cycle 3:** same cold-start sequence again → identical result, `suggestedFilename()` =
  `"Via Node.js"`.

3/3. No axis variation was needed — the defect is a deterministic function of the regex over
already-generated markdown content, not timing/session/tier-dependent.

## Expected vs actual

**Expected:** the file explorer/preview should only list files that genuinely exist in the
generated project, and any per-file download should save with a valid filename/extension. A
markdown subheading whose text merely contains a dot should never be treated as a file path.

**Actual:** any `###` heading immediately followed by a fenced code block, whose heading text
contains a dot-plus-word-characters substring anywhere (not necessarily a real file extension at
the end, and not necessarily a real path), is added to the file list, shown in the Explorer,
counted in the footer, and downloadable — individually and via "Download ZIP" — as a malformed,
extensionless file named after the heading text verbatim.

## Conditions

- Page: App Builder preview — `/runs/<id>` Preview tab and `/preview-fullscreen` popout
  (both render `AppBuilderPreview`/share `parseAppBuilderFilesForIDE`)
- Account: qa-admin (enterprise) — not tier-specific; the defect is in client-side markdown
  parsing that runs identically regardless of tier
- Theme/viewport: not a factor — reproduced at default light theme, default viewport
- Trigger: any completed run whose agent output markdown contains a `###` heading (from
  Format 2 of `parseAppBuilderFilesForIDE`) with a dot-plus-word-chars substring in the heading
  text, directly followed by a fenced code block
