# ISS-1176

Sibling of [ISS-1157](20261009-1500-ISS-1157.md) (register QA-KB-116), derived from its root cause, and the one with the
widest population: it does NOT need an override. `agentsFromManifest` (`frontend/src/lib/manifestAgents.ts:157`) is also how
`LaunchWizard` reads the compiled PLAN of a built-in, and for `ppt_v2` that plan replaces the library roster.

Confidence: CONFIRMED at the component tier (jsdom render of the real `LaunchWizard` fed the live payload of a user with no
override); not yet observed in a browser. What would settle it in the app: sign in as `pro@velocity.ai` (no overrides),
open `/workflow/create?mode=ppt_v2`, expand "Review gates".

## Condition

Any user who opens the `ppt_v2` panel (`/workflow/create?mode=ppt_v2`, routed by `globalSlice.ts:250-257`). `ppt_v2` reuses
`ppt`'s first two agents, so the library roster for it (agents whose AGENT.md `pipeline_type` matches `ppt_v2`) is 2 rows
against a 4-step plan (analysis-01 P5: "plan rows=4, library roster rows=2").

## Expected vs actual

Expected: "Presentation Strategist Agent", "Deck Engineer Agent", "Deck QA Agent", "PPTX Code Generator" (the live library's
names for the same four ids). Actual, with the `pro@velocity.ai` payload (`has_override: false`), Review gates rows and the
roster handed to the Advanced popup (analysis-03, U3):

```
ppt-brief-analyst | ppt-composer | ppt-deck-qa-v2 | ppt-code-generator
```

The two rows the library roster DID name correctly before the plan landed (`ppt-deck-qa-v2`, `ppt-code-generator`) are
replaced by id-named ones too. `ppt` (3 steps) and `prototype` (5 steps) are unaffected without an override because their
library rosters are complete and the plan never wins (analysis-01 P6; U5 control).

## Why the root cause implies it

`frontend/src/components/workflow/LaunchWizard.tsx:525-541` completes a partial library roster from the plan:

```tsx
if (planAgents.length <= prev.length && !(planHasTree && !prevHasTree)) return prev;
return mergePlanWithLibrary(planAgents, libraryAgents);
```

`mergePlanWithLibrary` (`:187-209`) was written to give plan rows the library's presentation:
`name: step.name || lib.name` (`:197`), `icon: step.icon || lib.icon`, `estimated_duration: step.estimated_duration ||
lib.estimated_duration` (`:201`). Every one of those `step.x` arrives NON-EMPTY from the seam: the name is the agent id
(`userWorkflows.ts:718`), the icon the `decorate` placeholder (`manifestAgents.ts:149`), the duration the 60 s literal
(`userWorkflows.ts:724`). So the `|| lib.x` branch is unreachable for a built-in step, and the merge returns the plan's
placeholders. Its own unit test passes plan rows with `name: ""` and an empty icon (`mergePlanWithLibrary.test.ts:15`),
a state `agentsFromManifest` has not produced since `1e329e47b` (before it the name was the compiled step's name, never
empty). Probe output for the merged rows: `ppt-brief-analyst | name="ppt-brief-analyst" | icon="🧩" | est=60s` and the same
shape for the other three (analysis-01 P5).

## Fix location

The seam, not `mergePlanWithLibrary` (see ISS-1157): once `agentsFromManifest` names a built-in step from the compiled
step, the merge is a no-op for the name. Trap: do not also teach `mergePlanWithLibrary` that `name === id` means "unnamed";
that is a second source of truth for the same fact, and its test pins the empty-string contract.

## For the test-writer

`frontend/src/components/workflow/mergePlanWithLibrary.test.ts` covers the merge alone with hand-built plan rows, which is
why it stays green. The missing test composes the two: `mergePlanWithLibrary(agentsFromManifest(detail, "ppt_v2").agents,
library)` with the live `ppt_v2` payload must name the four rows from the library (analysis-01 C2 is that assertion, red
today under `it.fails`). Component tier: `evidence/qa-kb-116/analysis-plugins/uiRoster.probe.test.tsx` U3 (red) against U5
(control, `ppt`). Use real library names in fixtures, not `name: id`.
