# ISS-1127

**Register source:** sibling derived during the `QA-KB-105` analysis on 2026-10-08 (root [ISS-1125](20261008-1540-ISS-1125.md)). Not its own
bug row.

**Confidence:** the mechanism is OBSERVED offline (evidence below, with the DAG forced unsatisfiable) and CONFIRMED by reading. That a real
roster reaches the exit is INFERRED, exactly as for the root: the plan was satisfiable at launch (see "How often" on the root).

## Condition

A run is `waiting_for_user` at a durable open gate (a review gate or a clarify round) when the backend restarts, and the DAG that
`_execute_impl` validates on re-entry is no longer satisfiable (`engine.py:5239-5249`). A restart is the likeliest moment for that: it is
when a deploy's changed `produces`/`consumes` contracts go live.

`restore_non_terminal_runs` branch (a) (`engine.py:12680-12808`) re-arms the run: it recreates and clears the store waiter, then spawns
`_rearm_gate_run` (`:12775-12777`). That driver has no app wrapper. For a review gate it stamps a `run_resuming` marker and calls
`resume_run` (`:12998-12999`); for a clarify round it calls `_replay_clarify_run` (`:13006`). Both end in `_drive_resumed_stream`, which
returns normally on the exit (root [ISS-1125](20261008-1540-ISS-1125.md)).

## Expected vs actual

Expected: the first boot ends the run `failed` with one `pipeline_failed` carrying the reason, and the armed waiter is evicted. This is
what [FIX-768](20261008-1540-FIX-768.md) already gives the five fault exits of `_replay_clarify_run` ([ISS-1120](20261008-1450-ISS-1120.md)).

Actual (OBSERVED offline): nothing moves the state machine, so the row stays `waiting_for_user`. The funnel has persisted `workflow_validated`
and an `error` frame after the gate's `*_ready`, and the two readers of "is the gate still open" now disagree:

- `derive_open_gate` reads a generic `error` as a RESOLUTION of both gate kinds (`backend/agents/capabilities/gate_pendency.py:47` in
  `QUESTIONNAIRE_RESOLUTIONS`, `:60` in `REVIEW_RESOLUTIONS`). Every unfiltered reader therefore sees no gate: the chat backbone
  (`run_commands.py:1907`), the SSE re-emit (`backend/app/api/run_stream.py:173`, `:317-335`), and `_replay_clarify_run` itself
  (`engine.py:16328`). The derivation result is observed. What the chat backbone then does is CONFIRMED by reading, not probed end to end:
  it builds `RunState(status="waiting_for_user", open_gate=None)`, whose phase is `PHASE_RUNNING` (`RunState.phase`,
  `backend/app/api/chat_router.py`), so `route_chat_turn` sends the user's approve or structured answer to `CHANNEL_STEERING` as a note for
  a run nobody drives. The SSE re-emit's behaviour is INFERRED.
- The restart scan strips `error` first (`PREMATURE_STOP_EVENT_TYPES`, `gate_pendency.py:72-96`; used at `engine.py:12733-12735` and
  `:12983`), so it still sees the gate open and re-arms it again at the next boot.

Net: the run is parked for good, cannot be answered, and `POST /resume` refuses it because the row is not terminal
(`run_commands.py:688-693`, 409 `run_not_resumable`). The remaining lever is Stop (not probed). Each review-gate boot adds one more
`run_resuming`, `workflow_validated` and `error`. A clarify run is re-adopted once more and then leaves silently: its second boot's
`_replay_clarify_run` derives UNFILTERED, sees the `error`, and takes the "no open questionnaire gate - skipping" decision exit
(`engine.py:16329-16334`) that FIX-768 left silent on purpose. The output persister also stamps `completed_at` on the parked row
(`engine.py:16167-16169` into `run_commands.py:4033-4034`).

## Why the root cause implies it

`_rearm_gate_run` reaches the same `_drive_resumed_stream` funnel as every other resume driver, and it has no app wrapper to fall back on
(no `_reconcile_terminal_status`), so the funnel's failure recording is the only one. The root's exit bypasses it. The gate-parked row
differs from the root's `running` ghost in what the user sees: an approval card or questionnaire that goes nowhere, not a lane that says
"running".

## Fix direction

None of its own. The root's fix covers it: `_fail_resume` appends a `pipeline_failed` (a resolution in both sets) and moves the state
machine to `failed`, so the row leaves `waiting_for_user` on the first boot and the second boot never adopts it. The red test is G1 and
G2 with one extra assertion each: after the second boot there is still exactly one `pipeline_failed` and no second `run_resuming`.

Separate, not part of this fix: branch (a) and `_rearm_gate_run` derive the open gate through `strip_premature_stops`, while
`_replay_clarify_run` (`engine.py:16328`) does not. The two only disagree when a premature-stop marker is left in the tail, which this
exit does; with the root fixed it cannot.
