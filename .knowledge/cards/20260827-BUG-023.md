## Why it is high severity rather than cosmetic

The URL is the user's statement of intent, and it is honoured for every
open-ended pipeline (`/create/ex_A2_branch` works). Only the two hand-written
special cases silently substitute a different pipeline, and they do it without
any visible difference — both screens render `GENERATE PRODUCT REQUIREMENTS` /
`Advanced 7 agents`, so there is nothing on screen to contradict the URL.

## The fix has two shapes, and the second is better

Map `create-app` → `app_builder` and `create-user-stories` → `user_stories`;
or delete both special cases and let them fall through to the generic
`create-workflow` handling that already works. The second removes the class of
bug rather than this instance of it — the special cases exist to do what the
generic path already does correctly.

> **Corrected 2026-10-01:** the second shape is unsound, and the first is the fix. See "Correction" in the Analysis
> section below. The original text above is kept as written.

## Analysis 2026-10-01 (QA-KB-002)

**corrected** (the second fix shape). The blast radius, the executed proof and the tests that must change with the fix
are new. No browser was opened for this analysis; the reproduction is the validator's, in `evidence/qa-kb-002/`.

Baseline for line numbers: the working tree on 2026-10-01. `page.tsx` carries uncommitted edits from other work (three
hunks, all after line 1340, adding 3, 1 and 1 lines), so its numbers after 1340 are 3 to 5 higher than at HEAD
`024c03ef8`; lines 384-386 are identical at HEAD. Every other file cited here is clean against HEAD.

### Root cause (CONFIRMED, one mechanism)

1. `parseViewPath` resolves `/create/app` and `/create/user-stories` to dedicated screens before its generic branch
   (`frontend/src/lib/routes.ts:286-287`), so neither carries a `pipelineType`. Only the generic branch does
   (`routes.ts:298`).
2. `initialWorkflowTypeFor` returns a type for `create-workflow` only (`frontend/src/app/[...view]/page.tsx:384-386`):
   `return parsed.screen === "create-workflow" ? parsed.pipelineType : undefined;`
3. `page.tsx:4230` passes `initialWorkflowTypeFor(parsedView) ?? builtinCanvasType` down as `initialWorkflowType`, and
   `DashboardLayout.tsx:627-637` seeds `workflowType` once from it, falling through to `"user_stories"`.
4. `initialMainViewFor` is right (`page.tsx:150-152` returns `"input"`), which is why the launch panel opens at all, on
   the wrong workflow.
5. Origin: commit `c9ec0149c` (2026-08-24) added `initialWorkflowTypeFor` for the generic screen only. Before it
   nothing seeded a type from the URL, so `/create/app` has never opened on app_builder from a cold load.

**Executed, not just read.** The real `parseViewPath` and the real `initialWorkflowTypeFor` (sliced out of `page.tsx`),
transpiled and called on the actual URLs. Re-run it from `frontend/`:
`node ../evidence/qa-kb-002/analysis-proof-initialWorkflowTypeFor.cjs` (output saved beside it as `.out.txt`).

| URL | parseViewPath gives | initialWorkflowTypeFor gives |
| --- | --- | --- |
| /create/app | screen create-app | undefined |
| /create/user-stories | screen create-user-stories | undefined |
| /create/app_builder | create-workflow, pipelineType app_builder | "app_builder" |
| /create/user_stories | create-workflow, pipelineType user_stories | "user_stories" |
| /create/ex_A2_branch | create-workflow, pipelineType ex_A2_branch | "ex_A2_branch" |

**What the wrongly typed panel then does.** `IdeaInputPage` is mounted with `workflowType={workflowType}` and
`workflowId={workflowType}` (`DashboardLayout.tsx:3159-3175`). So on `/create/app` today "Run workflow" dispatches
`user_stories` (`resolveDispatchType(pipelineAgents, effectiveType)`, `IdeaInputPage.tsx:1589`), "Save workflow"
persists `base_pipeline_type: user_stories` (`:1686`) and "Save as my version" writes a `My user_stories` override
(`:1759-1765`). `/create/user-stories` only looks right because the default happens to be the same workflow.

### Correction: the second fix shape ("delete the special cases") is unsound

"The second removes the class of bug" does not hold. The generic branch passes the raw slug through as the pipeline id
(`routes.ts:298`, `decodeURIComponent(mode)`), and `app` and `user-stories` are not ids: `backend/agents/workflows/`
holds `app_builder` and `user_stories` (line 1 of each `workflow.yaml`) and neither `app` nor `user-stories`. Deleting
`routes.ts:286-287` would turn `/create/app` into `pipelineType: "app"`, a launch panel for a workflow that does not
exist. Making it work needs an alias table, or renaming the URLs to `/create/app_builder` and `/create/user_stories`,
which changes the routing contract (`specs/015-frontend-routing/contracts/route-map.md:23-24` promises `/create/app`
and `/create/user-stories`) and breaks every shared link. That is a contract change, not a bug fix. The contract also
settles what `/create/app` must serve ("App-builder wizard"), so this is not a product question.

### Blast radius

The broken thing has **one caller and one consumer**: `initialWorkflowTypeFor` is called once (`page.tsx:4230`) and its
only consumer is the `workflowType` initializer (`DashboardLayout.tsx:627-637`). The other users of `parseViewPath`
(`LibraryPage.tsx:465`, `error.tsx:24`, `global-error.tsx:24`) derive no workflow type. The other two creation screens
need nothing from it: `create-ppt` and `create-prototype` go through `wizardModeFor` (`page.tsx:349-366`).

Ways to land on the two URLs:

- A typed, refreshed or shared link. The reported case, 3/3 in `evidence/qa-kb-002/`.
- `/workflow/create?mode=app` and `?mode=user-stories`, which `frontend/src/proxy.ts:21` redirects to the same two URLs.
- In-app `router.push(createRouteForType(type))` at `DashboardLayout.tsx:1580` (Home tile) and `:2396` (Edit brief &
  run again). The same effect is expected, because that push remounts the page and the URL is all that survives.
  INFERRED; filed as [ISS-916](20261001-2220-ISS-916.md).

Interactions that need no new card: a cold `/create/app` will now show a submit-ready App Builder panel to any tier, as
every other `/create/<type>` already does ([ISS-321](20260828-2002-ISS-321.md)); the server still enforces the tier on
launch.

### Fix: the agreed minimal fix is accepted, and it belongs where it is

`frontend/src/app/[...view]/page.tsx`, in `initialWorkflowTypeFor` only:

```ts
function initialWorkflowTypeFor(parsed: ParsedView): string | undefined {
  switch (parsed.screen) {
    case "create-app": return "app_builder";
    case "create-user-stories": return "user_stories";
    case "create-workflow": return parsed.pipelineType;
    default: return undefined;
  }
}
```

The ids match `backend/agents/workflows/app_builder/workflow.yaml:1` and `user_stories/workflow.yaml:1` and the
`WorkflowType` union (`frontend/src/types/index.ts:395`). This is the single place every consumer routes through, so no
caller needs a guard. Leave `routes.ts` and its `toEqual({ screen: 'create-app' })` round trips
(`routes.test.ts:90-95`) alone, so the `ParsedView` contract does not move. Update the docblock at `page.tsx:378-383`,
which still describes only "a generic `/create/{type}` cold load". Do not touch `handleSelectFeature` or
`createRouteForType` (`DashboardLayout.tsx:404-419`, `:1569-1581`); both are right.

Invariants: [ADR-0018](20260824-1631-ADR-0018.md) holds (no path literal outside `routes.ts`; the fix compares screen
names, not paths). SC-001 / INV-1 concern the backend kernel; this is a frontend screen-to-type mapping, the dual of
`createRouteForType`'s existing type-to-URL one (`DashboardLayout.tsx:404-406`). No backend, import-linter or migration
surface is involved.

## Resolution (QA-KB-002, fixer, 2026-10-01)

Fixed by [FIX-699](20261001-2238-FIX-699.md) with the first fix shape, as the analysis said. `initialWorkflowTypeFor`
(`page.tsx:386-397`) is now a `switch`:
- `create-app` → `"app_builder"`
- `create-user-stories` → `"user_stories"`
- `create-workflow` → its own `pipelineType`
- anything else → `undefined`

Its docblock was rewritten too. Nothing else in `page.tsx` changed, and `routes.ts` / `ParsedView` were not touched.

**Test.** The three `it.fails` in `initialWorkflowType.bug023.source.test.ts` now report "Expect test to fail", which
is the pass signal. The markers are left for the verifier. The two guard tests stay green.

**Regressions.** The launch/create neighbours are unchanged. `tsc` shows the same 13 errors.

**Analysis proof.** Re-running it on the fixed code gives `/create/app` → `"app_builder"` and `/create/user-stories`
→ `"user_stories"` (`evidence/qa-kb-002/04-*`, `05-*`).

**Tests and docs that encoded the defect, re-pointed** (each one and its justification is in FIX-699):
- S-03-09 now asserts the app_builder panel, with `@defect` dropped, in both the test and the feature spec.
- The ISS-247 test now loads `/create/user-stories`.
- The S-03-08 "ONLY create route" sentence was removed.
- D-01 is marked resolved in `DEFECTS-OBSERVED.md`, `PAGES.md` and `MANIFEST.md`.
- `docs/PROGRESS.md` is generated, so it was not hand-edited.

**Not done here.** The e2e tier was not run (it needs a browser lane), and no browser observation was made.
