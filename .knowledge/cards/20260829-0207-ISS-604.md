## Condition

Deferred finding from [FIX-401](20260829-0206-FIX-401.md) — found while verifying that fix,
NOT caused by it and NOT fixed by it.

Open `/workflows/<type>/canvas` for a built-in whose manifest declares a non-default
deliverable (`ppt` → `strategy: ppt`, `presentation.pptx`) and read the "Deliverable
strategy" combobox immediately, in the window between first paint and the resolution of
`GET /api/workflows/<type>`. The combobox shows the from-scratch default
`Streamed text — agent's raw output`; a moment later it flips to the declared value.

## Mechanism (from the code, observed once live)

`frontend/src/app/[...view]/page.tsx:485-505` fetches the built-in's detail and builds
`savedComposition.runConfig` from its real `deliverable`. That arrives as a prop AFTER
mount, and `ComposerPage.tsx`'s `runConfig` is seeded by a `useState` initializer, so the
`seededRunConfig` effect (`ComposerPage.tsx:415-431`) is what adopts the late prop. Every
consumer of `runConfig` — CanvasView's combobox and, since
[FIX-401](20260829-0206-FIX-401.md), the Simple tab's "Deliverable type" — therefore renders
the `DEFAULT_RUN_CONFIG` value (`streamed_text`/`output.md`) for the first paint or two.

This is the non-determinism [ISS-340](20260828-1856-ISS-340.md)'s validation table already
recorded (cycle 1 "Streamed text", cycles 2-3 the correct `ppt` option) and explicitly
scoped out of that card. It is adjacent to, but not the same as,
[ISS-196](20260828-1555-ISS-196.md)/[ISS-206](20260828-1609-ISS-206.md), which cover what the
SAVE path did with an unseeded `runConfig`; this card is about what the user READS before
seeding.

## Observed impact

`tests/integration/e2e/suites/04_composer_canvas/test_iss340_simple_canvas_deliverable_agree.py::test_simple_and_canvas_agree_on_ppt_deliverable_type`
flakes on it: 4/5 XPASS on 2026-08-29, the one red run captured with `--runxfail` as

```
AssertionError: Simple shows 'ppt — declared by this workflow' but Canvas shows
"Streamed text — agent's raw output" for the identical unmodified workflow
```

— the Canvas value was read pre-seed, the Simple value post-seed. Both now come from the
same state and the same label lookup, so the only remaining way for them to differ is this
race.

## What would fix it

Not attempted here (outside [FIX-401](20260829-0206-FIX-401.md)'s cards): render the
deliverable controls from a loading state until `initialRunConfig` has arrived for a
built-in canvas, or remount the composer on the built-in type the way
`key={savedComposition?.id ?? "new"}` remounts it for a saved row — a design call on the
composer's seeding, not a label change.
