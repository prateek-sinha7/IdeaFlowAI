## Description

**INFERRED — derived from ISS-188's root cause, not yet reproduced in the browser.**

ISS-188 validated the leak for the boundary case where the newly-signed-in account has
**zero** real runs — in that case the leak is PERMANENT, because no fetch ever resolves
non-empty to trigger either overwrite effect. The same three lines that cause that,
read literally, are not conditioned on the new account being empty at all:

```
frontend/src/components/catalog/HomeLaunchGrid.tsx:135-139
const [recents, setRecents] = useState<WorkflowRun[]>(() => {
  if (recentRunsProp && recentRunsProp.length > 0) return recentRunsProp.slice(0, RECENTS_LIMIT);
  if (reduxRecentRuns.length > 0) return reduxRecentRuns.slice(0, RECENTS_LIMIT);
  return readCache<WorkflowRun>(CACHE_KEY_RECENTS);
});
```

`recentRunsProp` (from `dashboard/page.tsx`, confirmed at `page.tsx:723`:
`useState<WorkflowRun[]>([])`) and `reduxRecentRuns` (`state.global.recentRuns`) are
BOTH genuinely empty at the instant `HomeLaunchGrid` mounts for the newly-signed-in
account — neither has had time to resolve a live fetch yet, regardless of whether that
account's eventual real history is zero or nonzero. So this `useState` initializer falls
through to the stale global `sessionStorage` cache **on every account switch**, not only
a permanently-empty one. For an account with real history, `HomeLaunchGrid.tsx:149-155`
(the `recentRunsProp` effect) or `:159-166` (the `reduxRecentRuns` effect) will
eventually overwrite `recents` with the correct data once that account's own fetch
resolves non-empty — but for at least one paint before that happens, the "Jump back in"
section renders the PREVIOUS account's cards: real titles, workflow type, and (for
completed runs) exact token-usage/dollar-cost figures, exactly as ISS-188 documents,
just self-correcting instead of permanent.

## Why this is implied by the root cause (not imagined)

This is the direct "boundary and empty" pair to ISS-188: ISS-188 proved the "zero items"
case is a PERMANENT leak; this card is the "one-or-more items" case, implied by the same
unconditioned fallback in the same three lines — a TRANSIENT leak (one render) rather
than a permanent one, but the same real cost/token data is exposed on the same code
path, not a hypothetical extrapolation.

## Expected

`HomeLaunchGrid` should never paint a card belonging to an account other than the one
currently signed in, for any single frame — including the first one, and including
accounts with genuine run history.

## Actual (predicted — unreproduced)

Every account switch within a tab (given ISS-188's cache-write precondition: some
earlier account in this tab had recents cached) renders at least one frame of the
previous account's "Jump back in" cards before the live fetch overwrites `recents`,
regardless of whether the new account's own history is zero or nonzero.

## What would settle it

Repeat ISS-188's steps 1-2 (sign in as qa-admin so `vlc_home_recents_v1` is written),
then sign in as an account with genuine, non-zero run history (e.g. `qa-enterprise@`)
instead of the zero-run `qa-basic@`, and record the FIRST paint of `/create` (screen
recording or a render-count assertion in a component test) rather than only the
settled state — confirm whether qa-admin's cards are visible for a frame before
qa-enterprise's own cards replace them.

## Root cause pointer

`frontend/src/components/catalog/HomeLaunchGrid.tsx:135-139` — the same unscoped
`readCache(CACHE_KEY_RECENTS)` fallback ISS-188 identifies, reached whenever
`recentRunsProp`/`reduxRecentRuns` are both empty at mount — which is always true for an
instant, on every account switch, not only a permanently-zero-run one.
