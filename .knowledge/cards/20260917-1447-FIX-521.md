## What was wrong

This is register bug **QA-PS-002**. With pipelines running, the bell's notification panel showed
"0 of N agents" and 0% for every run, however long it had been going. The confirmed root cause is
[ISS-673](20260917-1420-ISS-673.md), and [ISS-674](20260917-1420-ISS-674.md) is the header badge and
"N Running" dropdown, which read the same array. [ISS-644](20260917-0930-ISS-644.md) was the first
analysis, now superseded. [ISS-658](20260917-1302-ISS-658.md) is the escalation trace that led to
ISS-673. Two siblings share the "only the viewed run is ever handled" shape:
[ISS-648](20260917-1100-ISS-648.md) (failure and cancellation) and
[ISS-649](20260917-1105-ISS-649.md) (review gate pause and resume).

## Root cause (pre-fix line numbers)

1. **Progress (ISS-673/674).** Every live row in the panel, the header's single badge and its
   dropdown read `agentsCompleted` from AppHeader's `runningPipelines`. For a run that is not the
   viewed one that value is `runAgentsCompletedMap?.[r.id] ?? 0` (`AppHeader.tsx:204`). page.tsx
   rebuilds the map inline on every render from `runStore.get(id).pipelineState.completedCount`
   (`page.tsx:3897-3903`). The store keeps that count correct in a ref, but `handleFrame` re-renders
   only `if (runId === viewedRunIdRef.current)` (`useRunStateStore.ts:476`). With no viewed run
   progressing, as on `/dashboard`, nothing re-rendered page.tsx, so the map stayed frozen at its
   last value. That value is usually 0, because people leave a run before its first agent finishes.
2. **Failure and cancellation (ISS-648).** `markFailed`/`markCancelled` were called only from the
   viewed-run effect gated on `currentPipelineNotifId.current` (`DashboardLayout.tsx:905-917`).
   Unlike completion (FIX-203's `backgroundCompletedRunId`), there was no bridge for a background
   run. Its notification stayed `"running"`, so it never reached the panel's terminal list, and the
   live row also dropped once `recentRuns` went terminal. The run vanished from the panel.
3. **Gate (ISS-649, narrowed claim).** `markGatePaused`/`markGateResumed` had the same viewed-only
   gate (`DashboardLayout.tsx:926-934`). The live row's GATE label already came from server status,
   but `unreadCount` counts only `!read && status !== "running"` (`useNotifications.ts:258`). A
   background run waiting at a gate therefore never raised the bell's unread badge.

## What changed, and why there

- **`useRunStateStore.ts:314-318, 471, 488-490` (ISS-673/674, post-fix lines).**
  - Added a state setter, `const [, setBackgroundProgressTick] = useState(0)`.
  - `handleFrame` records `completedBefore` before the reducer.
  - A new `else if (entry.pipelineState.completedCount !== completedBefore)` branch bumps the tick.

  This is the one producer all three render surfaces share, as the card asks. It is a narrow
  signal, not a projection of background state, so FIX-224's per-frame flicker guard is untouched.
  A background run costs one page render per finished agent. The tick is not returned: page.tsx
  owns the hook and builds the map in render with no memo, so the state change is enough.
  `update`/`updatePipelineState` got no tick for two reasons. No `update` caller passes
  `pipelineState`, and the only `updatePipelineState` callers are for the viewed run
  (`page.tsx:2248`, rAF sync) or a terminal reopen (`:2928`), which is never a live row.
- **`page.tsx:796, 1724-1728, 2051-2052, 2080-2083, 4153` + `DashboardLayout.tsx:157-162, 451,
  738-752` (ISS-648/649).** One bridge mirrors FIX-203.
  - page.tsx sets `backgroundRunTransition = { runId, to }` for a run that is not
    `trackedRunIdRef.current`:
    - `to` is `"failed"`/`"cancelled"` in the `pipeline_failed`/`pipeline_cancelled` block;
    - `"gate"` in the `else` of `review_gate_ready`'s existing tracked-run check;
    - `"running"` in `review_gate_approved`.
  - A single DashboardLayout effect, placed beside FIX-203's, finds the notification with FIX-203's
    lookup (`workflowRunId` or `pipeline-${runId}`), restricted to `running`/`gate`. It calls the
    matching `markFailed`/`markCancelled`/`markGatePaused`/`markGateResumed`.
  - The state is an object, not an id string, so a run's second review gate re-fires the effect. A
    string would keep the same value and not re-fire.
  - The prop type is declared once on `DashboardLayoutProps`, and page.tsx reads it through
    `DashboardLayoutProps["backgroundRunTransition"]` (a type-only import, INV-12).
  - A terminal notification never moves back, because the lookup requires `running`/`gate`.

Trade-offs:

- FIX-203's ceiling carries over. Two background transitions that land in the same React batch
  keep only the last one. Frames from different runs arrive as separate stream events, so this
  needs coincident timing.
- As before, a page reload drops running notifications (FIX-204), so after a reload the bridge
  finds nothing to mark. The progress fix is unaffected, because it does not use notifications.

## Tests left exactly as they were: two of them assert the superseded path

Neither was edited. Both still report `expected fail`, and **that is correct, not a missed fix**:

- **`DashboardLayout.iss644.test.tsx`** ([ISS-644](20260917-0930-ISS-644.md), superseded) asserts
  `notification.agentsCompleted` from `updateProgress`. That field is never drawn for a live run:
  DashboardLayout hands AppHeader only non-running/non-gate notifications
  (`DashboardLayout.tsx:2695`), and the panel filters them again (`NotificationPanel.tsx:212-214`).
  ISS-658 and ISS-673 both flagged this test.
- **`NotificationPanel.iss658.test.tsx`** ([ISS-658](20260917-1302-ISS-658.md)) passes a
  `status: "running"` notification carrying 5 and expects the live row to show it. The panel drops
  running items by design (`NotificationPanel.tsx:212-214`, "live runs come via liveRuns"), and
  DashboardLayout never passes one in production. Turning it green would mean merging notification
  counts into live rows at one render site. That is the approach ISS-673 rules out, it would be
  dead code in production, and it would read the stale ISS-644 field anyway.

Both need the test-writer to retire them or re-point them at ISS-673's mechanism. They are not
evidence against this fix.
