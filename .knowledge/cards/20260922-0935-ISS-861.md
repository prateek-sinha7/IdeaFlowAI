## What happened

During the offline test sweep a `custom_revision` was launched to build a family
fixture. `custom-revision-planner` looped calling `write_file` with a
`file_path` and **no `content`** — 75+ turns at ~51k input tokens each, roughly
**34 minutes**, until a human killed it.

`AGENT_RECURSION_LIMIT` is 400. Nothing would have stopped it for another ~325
turns.

## The defect

There is no detection of an agent repeating an **identical failing tool call**.
The only backstop is the recursion ceiling, which is a turn count, not a
progress check — so a loop that makes no progress costs the full ceiling in
tokens and wall-clock before anything intervenes. The failure mode is silent:
the run looks busy, not stuck.

A repeated call with identical arguments that returns the same error is the
cheapest possible signal that no progress is being made, and it is not being
read.

## Where it would go

The turn loop that dispatches tool calls — a hash of `(tool_name, arguments)`
against the last N calls, with a threshold well below 400.

## Why it is recorded from a test sweep

The loop was hit while building a fixture, not by a user, and the run was
deleted. That is how it was found, not evidence that only fixtures trigger it:
nothing about the loop is specific to a revision planner or to a seeded run.
