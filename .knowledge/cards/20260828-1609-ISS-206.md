## Root cause — analyzer pass over BUG-20260828-005700-workflows-ppt-canvas / ISS-196

[ISS-196](20260828-1555-ISS-196.md) (the validator's card) reproduced the symptom 3/3 and states
the mechanism as "nothing in the mount path populates `initialRunConfig`... from `GET
/api/workflows/<type>`'s real deliverable field." Reading the actual mount path shows that claim
is not quite right — something DOES populate it. The real mechanism has two parts, both required
to fully explain the symptom, and both need fixing:

### Mechanism 1 (CONFIRMED) — `needsFullManifest()` never looks at `runConfig`, so Save silently omits `manifest` for any untouched composition

`handleSave` decides what to send with (`ComposerPage.tsx:628-632`):
```ts
const selectionsBody = needsFullManifest(pipelineAgents)
  ? { manifest: buildWorkflowManifest(pipelineAgents, capabilities, selections, runConfig) }
  : Object.keys(selections).length > 0
    ? { selections }
    : {};
```
`needsFullManifest` (`ComposerPage.tsx:51-60`) only inspects each `AgentDef`'s `isCustom` /
`prompt` / `skills.length` / `children.length` / `route.outcomes` — never `runConfig`. For an
unmodified `ppt` built-in, all three stock agents (`ppt-brief-analyst`, `ppt-composer`,
`ppt-validator`) fail every one of those checks, so it returns `false`. `selections` is seeded
`{}` for a built-in canvas (`page.tsx:455`, confirmed below) and the built-in declares no gates,
so `Object.keys(selections).length > 0` is also false. `selectionsBody` resolves to `{}` — the
`manifest` key is never present in the POST body at all, and `buildWorkflowManifest` (the ONLY
function that folds `runConfig.deliverable`/`planner`/`clarify` into a save,
`userWorkflows.ts:397-399`) is never invoked. The backend receives no `manifest` field and the
row persists `NULL` — exactly the `manifest: null` ISS-196 observed. **This holds regardless of
whether Mechanism 2 below is ever fixed**: even a perfectly-resynced `runConfig` would still never
reach the wire, because the gate that decides whether to call `buildWorkflowManifest` at all does
not consult `runConfig`.

The second call site, `handleRunOnce` (`ComposerPage.tsx:798-810`), has the identical gate for the
*steps* portion of its payload — but separately sends `deliverable`/`planner`/`clarify` as
top-level `extraParams` UNCONDITIONALLY (`ComposerPage.tsx:811-813`, not gated by
`needsFullManifest`). That is why Run-once is not symmetrically broken (see ISS-205 for the one
case where it still is).

### Mechanism 2 (CONFIRMED) — `runConfig` has no resync effect, unlike its sibling composer state

`runConfig` is seeded once via a plain initializer (`ComposerPage.tsx:335-341`):
```ts
const [runConfig, setRunConfig] = useState<WorkflowRunConfig>(
  initialRunConfig ?? {
    deliverable: { strategy: "streamed_text", name: "output.md" },
    planner: "skip",
    clarify: { mode: "skip", defaults: [] },
  },
);
```
Contrast this with `pipelineAgents` and `selections`/gates in the SAME file, which each carry a
dedicated `useEffect` (`resyncedAgentsFromLibrary` at `ComposerPage.tsx:250-269`,
`seededFromManifest`/`resyncedGatesFromManifest` at `ComposerPage.tsx:305-329`) explicitly
written to re-derive state when the corresponding `initial*` prop arrives AFTER first mount — the
file's own comments name this "the SAME race, different state" twice. `runConfig` was never given
the same treatment; grep confirms no effect anywhere in the file watches `initialRunConfig`.

For the built-in-canvas route this race is real, not theoretical. `page.tsx:437-485` fetches the
built-in's real manifest asynchronously and builds `initialSavedComposition.runConfig` from
`detail.deliverable` (`page.tsx:458-478`) — the seed genuinely exists and is genuinely correct.
But `page.tsx:448-451` deliberately omits `id` from that object ("a built-in has no
WorkflowDefinition row"), and `DashboardLayout.tsx:2906` remounts `ComposerPage` via
`key={savedComposition?.id ?? "new"}` specifically to let a late-arriving `initial*` prop set land
via a fresh mount (comment at `DashboardLayout.tsx:2890-2905` documents this exact pattern, for
the saved-workflow-reopen case it was built for). Because a built-in's `savedComposition.id` is
always `undefined` — both before AND after the async fetch resolves — the key never changes, so
`ComposerPage` never remounts, and `runConfig`'s one-time initializer keeps the hardcoded
`streamed_text`/`output.md` default forever, even though `initialRunConfig` (from
`DashboardLayout.tsx:2943`, `initialRunConfig={savedComposition?.runConfig}`) is by then correct.
This is why the canvas visibly shows "Streamed text" for a `ppt` built-in and why a
saved-workflow *reopen* does not have this problem (its row has a real `id`, so the key changes
and the remount picks up the correct `initialRunConfig` on first mount).

### What is and is not actually lost

- **Deliverable strategy** (`runConfig.deliverable`) — always lost for any built-in whose
  strategy/name differs from `streamed_text`/`output.md`. Confirmed for `ppt`
  (`backend/agents/workflows/ppt/workflow.yaml:42-44`, `strategy: ppt`,
  `name: presentation.pptx`).
- **Planner / clarify** — same mechanism, same loss, whenever a built-in declares non-default
  values.
- **Tool grants** (`read_files`/`write_files`) — ISS-196 states these "never entered component
  state in the first place." That is not quite accurate either: `manifestStepToAgent`
  (`userWorkflows.ts:403-446`, specifically line 426, `agent.tools = step.tools ? {...step.tools}
  : undefined`) DOES load them onto `pipelineAgents[i].tools` from `initialManifestSteps`. What
  actually breaks is the WRITE path: `agentToManifestStep` (`userWorkflows.ts:207-248`) reads
  grants from the `selections` map (line 230, `selections?.[agent.id]?.tools`), not from
  `agent.tools` — and `manifestStepsToGateSelections` (`userWorkflows.ts:466-489`) only populates
  `selections[id].tools` "when the saved manifest actually deviates from the read+write default"
  (line 476-481). For `ppt` specifically, all three steps use the default `true`/`true`, so there
  is no OBSERVABLE grant loss for this exact built-in — but `ppt_v2` declares a genuine non-default
  grant (`backend/agents/workflows/ppt_v2/workflow.yaml:77`, `{read_files: true, write_files:
  false}`), and copying it WOULD silently lose that grant (see ISS-203). The gate (Mechanism 1)
  is what actually matters here too: none of this ever gets serialized regardless, because
  `buildWorkflowManifest` is never called.

- `handleSave` (`ComposerPage.tsx:582-698`) — the reported path.
- `handleRunOnce` (`ComposerPage.tsx:712-878`) — shares the `needsFullManifest` gate for the
  steps/manifest portion; insulated from Mechanism 2 for a *completely* untouched built-in only
  by the separate `unmodifiedBuiltin` bypass (`ComposerPage.tsx:837-857` — see ISS-205 for why
  that bypass is narrower than it looks).
- Every built-in reachable via `/workflows/{type}/canvas` (`handleOpenInCanvas`,
  `DashboardLayout.tsx:1453-1459`, gated only by `!COMPOSER_ENABLED_TYPES.has(workflowType)`,
  i.e. every type except `custom`) whose declared `deliverable` differs from
  `streamed_text`/`output.md` — see ISS-203 for the concrete list.
- Any from-scratch Composer save or any re-save (PATCH) of an all-stock-agent saved workflow that
  only touches the Workflow tab — see ISS-204; this is not built-in-specific at all.

## Fix — where it belongs so every caller routes through it

Both mechanisms live in `ComposerPage.tsx`, the single component every one of these paths already
shares — the fix belongs there, not in each caller:

1. **Mechanism 1**: broaden the persist-full-manifest decision so it also fires whenever this
   canvas was seeded from a real manifest (`builtinCanvasType` set, or `initialManifestSteps`
   non-empty) or whenever `runConfig` differs from the from-scratch default — e.g. an additional
   OR-condition alongside `needsFullManifest(pipelineAgents)` at both call sites
   (`ComposerPage.tsx:628` and `:798`), backed by one small helper so the two sites can't drift.
   `buildWorkflowManifest`/`agentsToManifestSteps` already serialize everything correctly once
   invoked — the missing piece is purely the decision to call them.
2. **Mechanism 2**: give `runConfig` the same resync treatment `pipelineAgents`/`selections`
   already have — a `useEffect` keyed on `initialRunConfig` that calls `setRunConfig` the first
   time a real value arrives, mirroring `seededFromManifest` (`ComposerPage.tsx:305-314`).
   Fixing this INSIDE `ComposerPage.tsx` (rather than trying to make the `DashboardLayout.tsx:2906`
   remount key cover built-ins too) keeps the fix local to the one component with the missing
   effect, and doesn't require inventing a synthetic per-built-in key.

Fixing only one of the two leaves the bug partially alive: Mechanism 2 alone fixes the on-screen
display but Save still omits `manifest`; Mechanism 1 alone makes Save call
`buildWorkflowManifest`, but with a `runConfig` still stuck on the wrong default.

## Note for reproduction / tests

ISS-196 already carries a verified 3/3 live reproduction of the end-to-end symptom for `ppt`. A
unit-level regression test should assert `needsFullManifest` (or its replacement condition)
returns `true` for a `pipelineAgents` array built via `manifestStepsToAgents` from a builtin's
`manifest_steps` when `runConfig.deliverable.strategy !== "streamed_text"`, and that `ComposerPage`
re-renders with the correct `runConfig` after `initialRunConfig` arrives on a later prop update
(not just at mount) — a plain RTL `rerender()` with a new `initialRunConfig` prop, no live browser
needed.
