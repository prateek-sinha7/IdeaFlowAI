# FIX-760

## What was wrong

This fix is for bug report QA-KB-096. The root cause comes from [ISS-1073](20261007-2135-ISS-1073.md)'s analysis of 2026-10-07.
It was not re-derived here, but every line cited below was re-read before the edit.

`SandboxPdfPreview` read the declared name at the member's tag. HEAD `SandboxPdfPreview.tsx:27` was
`getRunSandboxFileBlob(getToken() || "", runId, path, selectedRef)`, where:

- `path` was `deliverable.filename` (`PreviewPanel.tsx:231`);
- `selectedRef` was `displayRef` (`PreviewPanel.tsx:889-891`), which is the DB tag of any older member.

No tag holds the root `Backlog.pdf`. `backlog_export.py:583-593` gitignores it, so v2 to v8 carry only `.chain/Backlog.pdf`, and
v1 has no PDF at all. So `run_files.py:1165-1178` correctly answered 404, and the component's catch turned that into the
"could not be loaded" fallback. That happened on every older member: v1, plus v2, v3, v4, v5 and v7, whose PDF exists at the tag.

Every other reader of the deliverable resolves through `resolveRunDeliverable`. The PDF preview was the one reader that skipped
it. [FIX-717](20261002-1243-FIX-717.md) gave the preview a ref but kept the declared path, so wrong bytes became no bytes.

## What changed, and why there

In `frontend/src/components/preview/SandboxPdfPreview.tsx`, the effect at lines 33-44 now runs these steps in order:

1. Resolve first with `resolveRunDeliverable(token, runId, path, selectedRef)`.
2. Stop if the effect was cancelled.
3. A null hit sets `"missing"`, which renders `fallback`, and sends no file request. That is v1.
4. A hit reads `getRunSandboxFileBlob(token, runId, hit.path, hit.ref ?? selectedRef)`. On v2 that is `.chain/Backlog.pdf` at v2.

The `selectedRef === null` early return is unchanged, as are the loading and iframe rendering and the object-URL revoke. This is
the analysis's scratch prototype (`evidence/qa-kb-096/13`, probes F1 to F4), adapted to the real component's markup.

Both callers go through this one component: `PreviewPanel.tsx:229` (with `displayRef`) and `WorkflowHistory.tsx:1105` (no ref,
so the live tree). That made the shared component the root fix. This change did not touch `api.ts`, any backend file,
`PreviewPanel.tsx` or `RunHeader.tsx`.

## Test edits, assertions only stricter (audit this)

1. **Mock seam, as ISS-1073's "Test seam" section asked.** `SandboxPdfPreview.test.tsx` and `SandboxPdfPreview.ref.test.tsx`
   mock `@/lib/api` without `resolveRunDeliverable`. With the fix in place and no edit, they went red (observed: 1 failed / 1
   passed, and 1 failed). The cause is vitest throwing for an export the mock does not define, which the component's catch
   turned into the fallback.
   - Each mock gained one passthrough line: `resolveRunDeliverable: async (_t, _r, path, ref?) => ({ path, ref })`, meaning the
     tree holds the declared file at the root.
   - No assertion changed.
   - Direction proof (`17`): with HEAD's component, both edited files still pass (2 passed, 1 passed). The added mock is inert on
     the old code.
2. **One assertion ADDED to the ISS-1073 red test.** Test 1 of `SandboxPdfPreview.resolve.test.tsx` now also asserts
   `expect(mockResolve).toHaveBeenCalledWith("test-token", "run-1", "Backlog.pdf", "v2")`. The reason is a mutation run (`17`):
   with the fix but the resolver called WITHOUT the ref (the naive fix ISS-1073 warns about), both red tests still XPASSed and
   the ref test still passed. So that broken fix would have looked green. With the assertion added:
   - HEAD's component is still red (2 expected fail);
   - the mutation is caught on test 1 (1 failed / 1 expected fail);
   - the fix XPASSes both.

   The `it.fails` markers are left for the 6-verifier.
