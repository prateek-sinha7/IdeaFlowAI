## Why the root cause implies it

[ISS-1194](20261012-0735-ISS-1194.md)'s mechanism is general: the offline tier reads whatever the shared dev history holds, the Run History drops a chip at count 0, and only some tests guard for it. [ISS-625](20260831-0115-ISS-625.md) was the previous instance (the Presentation chip vanished, four tests timed out); its resolution retargeted S-06-07, S-06-13 and S-06-08 onto User Stories (`test_run_history.py:201-210` records it), which moved the dependency to the next-thinnest type. This is the third step of that chain: Prototype is the first one that broke visibly, User Stories is the one left, and one cancelled row holds it up.

## Where the fix belongs

The same two places as ISS-1194, so one change serves both:

- the shared chip guard in `framework/locators/run_history.py` (next to `chip_count`, whose docstring already says "an absent chip IS a count of zero"): S-06-07 and S-06-13 call it instead of clicking directly;
- the vacuous assertions: S-06-06 and S-10-08 should skip or assert a non-zero count when the type they filter to has no runs, so a pass means the filter worked;
- data: the owner's call, same as ISS-1194 (the live smoke suite 25 leaves one real row per card: `test_pipeline_smoke.py:37-41` names the cards).

## What would settle it

`pytest -rs` on `suites/06_run_history` and `suites/10_analytics` against the live stack, one file at a time, shows the skip reasons; a SELECT that returns the `user_stories` row count shows how close S-06-07 and S-06-13 are to failing.

## For the test-writer

The ISS-1194 AST guard (in every function that calls the run-history `.chip(` locator, a `pytest.skip(` call appears before the first `.chip(`; probe `evidence/qa-kb-123/analysis-05-chip-guard-ast-probe.py`) is red for S-06-07 and S-06-13 as well as the three prototype tests; that covers this card's guard half. The vacuous-pass half has no offline test worth writing: it is a judgement about assertions, not a mechanical rule.
