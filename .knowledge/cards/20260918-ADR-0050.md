## Decision

A **shard** is "what one agent can read in one pass". `_build_shards` computes
the division at materialisation time, from the token cost this extraction
actually measured per page, and publishes it in `manifest.json` under `shards`
and `shard_basis` plus one line of the `extract_text` receipt.

The planner **reads** a shard count. It never derives one. The same arithmetic
done by a model is the same arithmetic done wrong sometimes, and two runs of the
same document dividing differently is a class of bug with no cheap signal.

## The design doc is gone

`file_extract_tools.py:650` and `:1255` and `test_extract_shards.py:7` all cite
`SHARDING.md`. **That file does not exist** — not in this worktree, not in the
main checkout. The rationale below therefore survives only in code comments one
refactor away from deletion, which is why this card exists. Treat the citations
as dangling; do not go looking.

## The budget, and the reserve nobody prices

```
usable = safe_budget − agent_reserve
       = 120,000 − 15,000
       = 105,000            (default: Haiku 4.5)
```

`_SHARD_SAFE_BUDGET` is 60% of the model's context window — the conservative
fraction, `_SHARD_SAFE_BUDGETS` carries one per reading model (120K for the 200K
windows, 600K for the 1M ones). Haiku is the default because it is cheapest per
page and the only model on both Bedrock paths; the rest are listed so switching
model is a parameter rather than an edit.

`_SHARD_RESERVE_TOKENS` is the interesting number. **A run measured an agent that
read nothing at all still spending 12,856 tokens** on its system prompt, tool
schemas, task block and tool-call history. Sharding to the raw safe budget
overruns by exactly that amount, every time, on every shard. 15,000 is that
measurement rounded up.

No pricing table carries this correction, which is why it looks like a magic
number and why removing it looks free.

## Packing

Greedy first-fit **in page order**. Pages stay contiguous, so every shard is a
page *range* (`"page_range": "12-31"`) an agent can be told to read, not a
scattered set it has to be handed as a list. A shard flushes when the next page
would exceed `usable`, or when it already holds `_SHARD_PAGE_CAP = 100` pages
(the API's per-request page/image ceiling below a 1M context).

Two edge behaviours are deliberate:

- **An oversized single page ships anyway**, with `over_budget: true`. Dropping a
  page because it is large would lose content silently; flagging it tells the
  reading agent to expect a squeeze.
- **An unknown model name falls back to the default budget** rather than guessing
  a window. Guessing high builds shards no agent can actually read, which fails
  later and further away.

`model`, `page_cap` and `reserve` are all parameters, so a different reading
model or a re-measured overhead needs no code change.

## Published advisory-only — the sharp edge

This is the part worth knowing before trusting shards for anything.

**Nothing consumes the shards programmatically.** They are written into
`manifest.json` and printed as one receipt line:

```
Shards: 3 — report-s01 pages 1-20 (~98,400 tok), report-s02 pages 21-40 (~101,200 tok), …
```

They reach a model as text, and that is the whole delivery mechanism. `out`
(`shards/{id}/`) is a *suggested* output path, not a directory anything creates.

So a wave planner that reads the manifest and silently ignores `shards` — or
invents its own division — **fails no test and trips no assertion anywhere**. The
arithmetic is verified (13 tests in `test_extract_shards.py`); its *use* is not
verified at all. Any future claim that "the planner shards correctly" needs
evidence from a run, not from this module.

## What a future author must do

Do not move shard computation into a prompt. Do not delete
`_SHARD_RESERVE_TOKENS` because the pricing table does not mention it. Do not let
packing reorder pages. If you make shards load-bearing, add the check that fails
when a consumer ignores them — today there is none.
