# ISS-832

Reported as **QA-PS-046** (register: [LEDGER.md](../../LEDGER.md)). Completes
the root cause of [ISS-798](20260922-1631-ISS-798.md), which validated the
symptom 3/3 cold-start on 2026-09-22 16:31 — against the tree as it stood
**before** [FIX-617](20260922-1935-FIX-617.md) landed (19:35 the same day).
This card is a fresh direct-source read of the current tree, done for the
analyze phase, and it splits the reported waste into what that fix already
closes and what is still open.

## What is already closed (CONFIRMED, direct read 2026-09-22)

Every capability-fetching call site reachable from the composer routes
through the same `getCapabilities()` in `frontend/src/lib/api.ts:1801-1808`,
which [FIX-617](20260922-1935-FIX-617.md) wrapped in `cachedGet()`
(`frontend/src/lib/api.ts:407-433` — a `${token}\0${path}`-keyed, 30s-TTL,
failure-evicted cache):

- `AgentsPopup.tsx:24` — `getCapabilities as fetchCapabilities`, imported
  from `@/lib/api` (confirmed by the `from "@/lib/api"` on line 33 of the
  same import statement)
- `AgentsPopup.tsx:1128` — `CapabilityPaletteSection`'s own mount effect
  calls `fetchCapabilities(jwt)`
- `AgentsPopup.tsx:1530-1549` — the exported `useAgentCapabilities()` hook's
  own mount effect also calls `fetchCapabilities(jwt)`
- `composer/CanvasView.tsx:23,304` — calls `useAgentCapabilities()` on mount
- `composer/CanvasConfigRail.tsx:19,162` — `CanvasView`'s own child, calls
  `useAgentCapabilities()` again, independently — this is
  [ISS-796](20260922-1825-ISS-796.md)'s exact mechanism
- `AgentModelPicker.tsx:26,74` — calls `getCapabilities(jwt)` directly

`ComposerPage.tsx:231` initializes `view` to `"canvas"` by default
(`useState<"simple" | "canvas">("canvas")`), and `ComposerPage.tsx:1403-1404`
renders `<CanvasView>` whenever `view === "canvas"` — so a brand-new
`/workflows/new` load (no `workflowId`) mounts `CanvasView` +
`CanvasConfigRail` as part of its DEFAULT view, not behind an extra click.
That makes ISS-798's validated 2x `/api/capabilities` count on
`/workflows/new` a live reproduction of ISS-796's mechanism, which had been
filed INFERRED ("not yet reproduced live") against `/analytics`
(QA-PS-036) — this bug's own validation promotes it to CONFIRMED.
[FIX-617](20260922-1935-FIX-617.md) already resolves ISS-796 "in full" and
names `AgentModelPicker` explicitly among the callers `cachedGet()` closes.

`getMe()` (`frontend/src/lib/api.ts:609-614`) is likewise `cachedGet`-wrapped
now (`ISS-801`'s fix, comment at that line names the same shared-cache
reasoning), closing the reported `/api/me` x2 the same way.

## Correction to ISS-798

ISS-798 names a second capabilities implementation —
`capabilitiesApi.get` in `frontend/src/store/api/capabilities.ts:34-38`
(axios `http.get`, no cache) — as one of "the fetchers" behind the
duplication, and lists `AgentsPopup.tsx:24` as a caller of it. Direct read
shows `AgentsPopup.tsx:24` imports `getCapabilities as fetchCapabilities`
FROM `@/lib/api` (the cached implementation), not from
`store/api/capabilities.ts`. A repo-wide grep
(`grep -rn "capabilitiesApi\.get\|\.capabilities\.get(" frontend/src`) finds
**zero** call sites for the axios implementation anywhere in the frontend —
it is dead code today, not a second live source of the duplication ISS-798
reproduced. See [ISS-834](20260922-2003-ISS-834.md) for why that dead code
is still worth tracking.

## What is still open (CONFIRMED, direct read) — not composer-specific

`/workflows/new` has no literal route folder
(`find frontend/src/app -maxdepth 2 -type d` lists no `workflows/`); it is
served by the shared catch-all `frontend/src/app/[...view]/page.tsx` — the
same component every other route in this duplicate-request family goes
through. Two of that file's own mount effects are unconditional on which
view is active, and both are already root-caused for other routes by
existing cards:

- `page.tsx:985-1004` — `useEffect(..., [isAuthenticated])` calls
  `getWorkflows(currentToken, {limit:50})` unconditionally and stores the
  result into `setRecentRuns`, a state variable the composer never renders
  (the composer shows a blank canvas with no run history — BUGS.md's own
  QA-PS-046 report makes the same observation). `getWorkflows()`
  (`api.ts:873-895`) builds `path = "/api/runs"` despite its name (confirmed
  at `:877`) and only has an in-flight dedupe (`inFlightWorkflows`,
  FIX-616), not a cache, so this fires again on this route exactly as it
  does on `/dashboard`. This is the identical file:line
  [ISS-808](20260922-1850-ISS-808.md) already root-caused for
  QA-PS-039/`/dashboard` — it applies verbatim here.
  `RunConnectionProvider.refreshLiveRuns`
  (`frontend/src/providers/RunConnectionProvider.tsx:305-316`) is NOT a
  contributor to this anymore: FIX-617 made it skip its own `getWorkflows`
  call entirely when `tabOwnedIds.size === 0` (the common cold-load case,
  nothing launched yet this tab) — confirmed by direct read. `page.tsx`'s
  own effect is now the sole remaining source of the composer's unneeded
  `/api/runs?limit=50`.
- `page.tsx:876-897` — the auth-check effect dispatches `signedIn({token})`
  (`:887`) unconditionally, which `store/listenerMiddleware.ts:25-56`'s
  status-guarded listener turns into `dispatch(fetchWorkflows())`
  (`:52` — the `/api/workflows` catalog) plus `fetchAgentLibrary` /
  `fetchSkills` / `fetchHooks` (`:60-65` — the three additional
  `agents/library` / `skills/library` / `hooks/library` calls ISS-798 flags
  as "new since the original report"). The guard reads Redux status, not an
  in-flight lock, so React StrictMode's dev-mode mount-unmount-remount can
  dispatch `signedIn` twice before the first thunk's status write lands —
  the same race [ISS-794](20260922-1827-ISS-794.md) already root-caused for
  `/create/ppt`. Applies verbatim: the composer mounts through the
  identical `page.tsx` effect.

## Fix

Belongs in the choke points [ISS-808](20260922-1850-ISS-808.md) and
[ISS-794](20260922-1827-ISS-794.md) already name, not a composer-specific
patch: gate or remove `page.tsx:985-1004`'s `recentRuns` fetch on the routes
that actually render it, and close the StrictMode-vs-listenerMiddleware race
with an in-flight guard on the `signedIn` effect (or generalize
`cachedGet`/`inFlightWorkflows` into `fetchWorkflows()`'s Redux thunk).
Fixing either closes `/workflows/new` along with every other route already
carrying these two cards — a composer-local guard would fix only this one
caller and leave every sibling route still broken.

(`const liveRunsFromServer = recentRuns.filter((r) => LIVE_STATUSES.has(r.status));`)
and `:200` (`const hasServerData = recentRunsLoaded && recentRuns.length > 0;`)
turn that list into the "N Running" badge and its dropdown. "Gate it on the

`tests/integration/test-runs/2026-09-22T21-02-qa-ps-046-fix-measure/0-report.html`):

was filed for is gone; what is left is a single call that a rendered surface
