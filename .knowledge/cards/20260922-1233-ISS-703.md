# ISS-703

## Title

Sibling of [ISS-720](20260922-1232-ISS-720.md): the Workspace tab's open-file viewer header
shows "0 B" too, once a file is opened under a selected ref — a second render site the
validator's reproduction never exercised.

## Status: INFERRED — same payload proven broken, not independently clicked open

The mechanism is CONFIRMED by code (identical field, identical API response — see
[ISS-720](20260922-1232-ISS-720.md)); what is inferred is only that nobody has clicked a file
open while a ref was selected and read the header strip. All three of QA-PS-032's reproduction
attempts opened the Workspace tab's file LIST and stopped there; none opened a file's
content/detail view.

## Why ISS-720's root cause implies this

`SandboxTab.tsx` keeps exactly one `files` array per fetch (from `GET /sandbox?ref=`) and
derives `active` — the currently open file — from that same array. There is no second network
call for a file's own metadata, only for its content. Two render sites read `.size` off entries
from that one array:

- `SandboxTab.tsx:905` — the list row, `formatBytes(file.size)` — what QA-PS-032 observed.
- `SandboxTab.tsx:1404` — the viewer header strip, `formatBytes(active.size)`, shown once a
  file is opened (`SandboxTab.tsx:1399-1405`).

Since `active` is drawn from the same `files` payload [ISS-720](20260922-1232-ISS-720.md)
proved carries a hardcoded `size: 0` for every ref-scoped entry (`run_files.py:930`),
`active.size` is `0` too, by construction — there is no code path by which the header could
read differently from the row it came from.

## Expected

Opening a file while a version is selected shows the file's real byte size in the viewer
header, matching "Latest (live)" behaviour.

## Actual (inferred, not yet independently observed)

"0 B" in the header strip too, for every file, under every ref.

## What would confirm this

Select a ref in the version dropdown, click any file row to open it, and read the size next to
the filename in the viewer header strip (`SandboxTab.tsx:1401-1405`). Expect "0 B" there as
well as in the list.

## Fix

No separate fix needed — resolved by the same change as
[ISS-720](20260922-1232-ISS-720.md) (giving the ref-scoped listing a real `size`), since both
render sites read the same field off the same payload. Filed only so the fix's verification
checks BOTH render sites, not just the list row QA-PS-032 happened to look at.
