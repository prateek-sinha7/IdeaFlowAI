## What is broken

INFERRED sibling of [ISS-729](20260922-1338-ISS-729.md) (QA-SG-002 — Run
Workflow button does not disable after clicking). ISS-729's root cause is
that `IdeaInputPage.tsx`'s `handleRun` sets no in-flight/submitting flag and
its button's `disabled` prop never checks one. `ComposerPage.tsx`'s "Run
once" button — the equivalent launch action for a composed/custom workflow
— duplicates that exact shape independently (it is a separate
implementation, not a shared caller of `handleRun`; see ISS-729's Blast
radius section for the full grep confirming neither file renders the
other).

Root cause: `frontend/src/components/workflow/composer/ComposerPage.tsx:984`

```
const handleRunOnce = useCallback((instruction: string) => {
  if (!onRun) return;
  const trimmed = instruction.trim();
  if (!trimmed) return;
  if (pipelineAgents.length === 0) return;
  ...
```

No `submittingRef`/`isSubmitting` exists anywhere in this function or the
file (confirmed: `grep -n "submittingRef\|isSubmitting" ComposerPage.tsx`
returns nothing). The button's disabled prop,
`frontend/src/components/workflow/composer/ComposerPage.tsx:1315`:

```
disabled={!onRun}
```

only checks whether the `onRun` prop exists at all — never whether a
submission is already in flight. Worse than ISS-729's single entry point:
this handler has TWO unguarded call sites that both reach the same
unprotected function —

- the button's own `onClick` at `ComposerPage.tsx:1313`
  (`handleRunOnce(briefText)`), and
- the brief textarea's Cmd/Ctrl+Enter shortcut at `ComposerPage.tsx:1457`
  (`onSubmitShortcut={() => handleRunOnce(briefText)}`).

`onRun` is wired in `DashboardLayout.tsx` (`<ComposerPage onRun={(type,
brief, agentIds, extraParams) => { if (onResetPipeline) onResetPipeline();
if (onStartPipeline) onStartPipeline(type, brief, agentIds, attachedHooks,
extraParams); }} .../>`) straight into `onStartPipeline` with no guard at
that layer either, so a second invocation is not caught downstream.

**Expected:** the "Run once" button (and the Cmd/Ctrl+Enter shortcut) should
disable/guard immediately on first invocation and stay guarded until the
run starts or the handler's own early-return conditions changed.

**Actual (INFERRED, not yet live-reproduced):** two back-to-back
invocations of `handleRunOnce` — either two rapid clicks, or one click plus
one Cmd/Ctrl+Enter landing before React commits any state — would both pass
every early-return check and both reach `onRun`, producing two independent
`POST /api/runs` the same way ISS-729 confirmed for `IdeaInputPage`'s Run
button.

## What would confirm or refute it

The same recipe ISS-729 used: sign in as `qa-admin@flowinqa.com`, open the
Compose-a-custom-workflow canvas (`ComposerPage`), add ≥1 agent, enter a
brief ≥3 chars, then fire two synchronous `.click()` calls on the "Run
once" button inside one `page.evaluate()` (and separately, one click plus a
synchronous Cmd/Ctrl+Enter) while watching the Network tab for a second
`POST /api/runs`. Not run as part of this analysis — no browser session was
used; this card was filed from static code reading only, per the
in-flight-guard mechanism already confirmed live for ISS-729's twin.

## Fix

Same pattern as ISS-729's Fix section, applied to this file: a
`submittingRef = useRef(false)` guard set inside `handleRunOnce` (after its
existing `!onRun` / empty-brief / zero-agent / `designMissing` early
returns, matching FIX-345's placement rule), checked at the top of the
function so BOTH entry points (button click and the Cmd/Ctrl+Enter
shortcut) are covered by guarding the handler itself rather than either
call site — plus a `useState` companion threaded into `disabled` for the
visible loading state, exactly as
[FIX-345](20260828-2250-FIX-345.md)/[FIX-420](20260831-FIX-420.md)/[FIX-470](20260902-1200-FIX-470.md)
already did for the other three buttons in this codebase with the same
flaw. ISS-729 recommends doing both files in the same pass.
