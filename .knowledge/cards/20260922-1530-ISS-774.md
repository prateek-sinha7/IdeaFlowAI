# ISS-774

Derived while analyzing **QA-SG-013** (`BUGS.md`) as a sibling of
[ISS-768](20260922-1500-ISS-768.md), under the "other callers with the same flaw" category:
every OTHER workflow declaring `deliverable.strategy: streamed_text` hits the identical
disabled-button mechanism, not just `user_stories`.

## Why the root cause implies this

[ISS-768](20260922-1500-ISS-768.md) traced the mechanism precisely: `resolveRunDeliverable`
(`frontend/src/lib/api.ts:1183-1199`) exact-matches the declared deliverable name against the
sandbox root listing (`listing.files.find((f) => f.path === c)`); `build_flat_payload`'s
`streamed_text` branch (`backend/agents/execution_engine/engine.py`, materialization at
~1459-1464) writes that name ONLY into `.chain/<name>`, never `sandbox.root / <name>`. Nothing
in that mechanism is `user_stories`-specific — it fires for ANY workflow on the `streamed_text`
strategy whose pipeline has no agent that independently writes the deliverable to sandbox root
(the "Layer-2 exception" [ISS-726](20260922-1248-ISS-726.md)/ISS-723 document for
`ppt`/`ppt_revision`'s `ppt-composer`).

`backend/agents/workflows/custom/workflow.yaml:17-19` declares
`deliverable: {strategy: streamed_text, name: output.md}` (renamed to `output.html` etc. per
run via the composer's `__deliverable__` override — a DIFFERENT, already-tracked defect,
[ISS-770](20260922-1305-ISS-770.md): that card is about the override changing the FILENAME but
never the CONTENT; this card is about the resulting file never reaching sandbox root at all, so
the header button that would serve it never turns on in the first place — which is also why
ISS-770's own reproduction had to fetch the file via the Files tab / sandbox listing rather than
the header Download button). None of the 9 `custom` pipeline steps (market-research-agent
through task-list-planner) declares `tools: workspace` or any write/edit instruction for the
deliverable — they are read/text-only agents, the same shape ISS-726 documents for
`user-story-revision-agent`.

## Live confirmation (not merely inferred)

Checked directly against a real completed `custom` run, `qa-admin@flowinqa.com`:

```
GET /api/runs/e49b91e6-f2fe-479c-a941-75da2b53c05d
  status: "completed"
  deliverable_filename: "output.html"     (declared — truthy, so resolveRunDeliverable does
                                            NOT fall back to the ISS-313 bundle path)
  deliverable_mimetype: "text/markdown"   (ISS-770's own confirmed defect)

GET /api/runs/e49b91e6-f2fe-479c-a941-75da2b53c05d/sandbox
  root-level files: [".family.lock", "PLANNER.md"]  — no "output.html" at root
  only match for "output.html" anywhere in the listing: ".chain/output.html" (416 bytes)
```

`resolveRunDeliverable(token, runId, "output.html")` therefore returns `null` on this run —
`deliverableFile` stays `null`; `canHeaderDownload` (`PreviewPanel.tsx:1384`,
`!!deliverableFile || deliverableBundle`) is `false`. The header "Download the deliverable"
button is disabled on this run today, live — the same mechanism as ISS-768, reached the same
way (direct API read against a real run, not analogy). 22 completed/degraded `custom` runs
exist in this Postgres instance at analysis time; the mechanism is unconditional on the
declared name, so none of them can hit the root path either.

## Expected vs Actual

- Expected: a completed `custom` workflow run's header "Download the deliverable" button is
  enabled, serving the compiled `output.md`/`output.html` deliverable.
- Actual: permanently disabled on every completed `custom` run — the declared file exists only
  under `.chain/`, never at sandbox root, so `resolveRunDeliverable`'s exact-path match never
  hits.

## Fix direction

Same shared fix location as [ISS-768](20260922-1500-ISS-768.md) — this is exactly why the fix
belongs in the shared mechanism, not a per-workflow patch: either (a) give one agent per
`streamed_text` pipeline (here, `task-list-planner`, the final `custom` step) a real
`write_file` of its compiled output to sandbox root, or (b) make
`resolveRunDeliverable`/`build_flat_payload` aware that a `streamed_text` deliverable's
canonical location is `.chain/<name>`, not sandbox root, and resolve from there. Whichever
option is chosen for ISS-768 fixes this card too, PROVIDED the fix lives in the shared
`build_flat_payload`/`resolveRunDeliverable` mechanism rather than being special-cased to
`user_stories` alone — a `user_stories`-only guard leaves `custom` (and `user_stories_revision`,
[ISS-726](20260922-1248-ISS-726.md)) still broken. Not applied here — read-only analysis only.

## Ruled out from this same sibling sweep

Two other `streamed_text` workflows exist and were checked, but neither traces cleanly from
this root cause: `reverse_engineer` (`backend/agents/workflows/reverse_engineer/workflow.yaml`)
declares `steps: []` — zero pipeline agents, so no run of this type can reach `completed` at
all today; and `chat` (`backend/agents/workflows/chat/workflow.yaml`) declares
`user_launchable: false`, so it is not reachable through the `/runs/{id}` header-toolbar surface
this bug report describes. Neither was filed as a sibling.
