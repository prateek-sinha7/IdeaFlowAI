## Why this is implied by ISS-227's root cause

[ISS-227](20260828-1554-ISS-227.md) established that `frontend/src/proxy.ts:10`
(`NextResponse.redirect(new URL(\`/create/${mode}\`, request.url))`) performs **no
validation of `mode` whatsoever** — it is edge middleware that blindly redirects
based on an unauthenticated read of a query string, before any page component or
its own auth logic runs. That reproduction was done entirely on a `qa-admin`
session, so it could not (and explicitly did not claim to) observe whether the
same traversal is any less reachable, or any better contained, for a session
that is NOT an admin.

Reading the destination's own gate confirms the gap is real, not just untested:

```tsx
// frontend/src/app/admin/page.tsx:170
if (!user.is_admin) { router.replace(routes.dashboard()); return; }
```

This is a **client-side, post-mount** check — it runs inside a `useEffect`-style
gate after `AdminPage`'s component tree has already mounted and after `getMe()`
has already been dispatched (per the file's own gate-ordering comment and
`admin.reskin.test.tsx:16`, "the `is_admin` access gate remains: a non-admin user
is redirected" — i.e. redirected, not blocked pre-render). Nothing in
`proxy.ts`'s redirect path, and nothing server-side on the `/admin` route itself,
gates on role BEFORE that client effect fires. So for a non-admin session driven
into `/admin` via `?mode=../admin`, the open question is exactly how much of the
admin shell mounts and how many admin-only network calls (e.g. a `getMe()` or an
early `adminListUsers()`) fire in the window before `router.replace(routes.dashboard())`
executes — not whether the user eventually leaves `/admin` (they do), but whether
anything sensitive is exposed or requested during the gap. That gap is a direct
consequence of the SAME root cause: the middleware trusts `mode` with zero
authorization of its own, so whatever gating exists is exclusively whatever the
destination page happens to do internally, and that varies per destination.

## Expected vs Actual (hypothesized — unreproduced)

**Expected:** a non-admin (or unauthenticated) session hitting
`/workflow/create?mode=../admin` either never reaches `/admin`'s mounted shell,
or reaches it and is bounced with no admin-only network call fired first.

**Actual (unverified):** untested. Two plausible outcomes, either of which is
worth recording precisely because neither has been checked:
1. The `is_admin` effect fires fast enough that no sensitive call/render is
   observable — the flaw is then purely the namespace-escape ISS-227 already
   documents, with no additional exposure. Still means the fix belongs in the
   redirect (ISS-227's fix), not here.
2. The client-side gate leaves a window where `AdminPage` mounts, its own
   `getMe()`/data-fetch calls fire, or its shell paints before the
   `router.replace` redirect completes — i.e. a second, independent gap
   stacked on top of ISS-227's, in the destination page rather than the
   middleware.

## What would confirm or refute this

Reproduce ISS-227's exact steps (`http://localhost:3000/workflow/create?mode=../admin`)
signed in as `qa-basic@flowinqa.com` / `qa-pro@flowinqa.com` / `qa-enterprise@flowinqa.com`
(non-admin tiers) instead of `qa-admin`, and check via `browser_network_requests`
whether any `/api/admin/*` call fires, and via a DOM snapshot taken immediately
after navigation settles whether admin-only content (user table, stat tiles) is
present even momentarily before the bounce to `/dashboard`.
