## Source

`BUG-20260828-104200-workflows-nonexistent-r2` in `bug-hunter/ledger.md`.

## What is suspected

ISS-234's precondition is framed narrowly around a *dead* workflow id (`GET
/api/workflows/<bad-id>` returning 404). Reading the fetch that seeds the composer shows the
trigger is broader than "dead link":

```ts
// frontend/src/app/[...view]/page.tsx:452-499
useEffect(() => {
  if (!isAuthenticated || !builtinCanvasType) return;
  ...
  try {
    ...
    const detail = await getWorkflowDetail(jwt, builtinCanvasType);
    ...
    setInitialSavedComposition({ ... });
  } catch {
    if (!cancelled) setInitialSavedComposition(null);
  }
  ...
}, [isAuthenticated, builtinCanvasType]);
```

The `catch` is unconditional — it fires on *any* thrown error from `getWorkflowDetail`, not
specifically a 404. `builtinCanvasType` itself is set from the raw URL segment with no existence
check (`builtinCanvasTypeFor`, `page.tsx:345-347`), so this effect runs identically whether the
id is a well-formed, currently-existing built-in (`ppt`, `prototype`) or a bad one — the only
thing that varies is why the fetch fails. A transient network blip, a 500, or a timeout while
loading a **real, existing** `/workflows/{id}/canvas` sets `initialSavedComposition = null`
exactly as a genuine 404 does. `ComposerPage` then mounts with `pipelineAgents = []`
(`ComposerPage.tsx:251-281`, since `initialManifestSteps`/`initialAgentIds` are both absent), and
[ISS-234](20260828-1628-ISS-234.md)'s confirmed root cause takes over from there — the same
unguarded `handleRunOnce` fallthrough (`ComposerPage.tsx:939`) fires the identical full
custom-agent-pool substitution, for a workflow that was never dead.

This generalizes [ISS-299](20260828-1730-ISS-299.md), which already documented this exact
`catch`'s effect for the *Save as copy* consequence ("canvas seeds an empty manifest from a
workflowId with no existence check"). ISS-299 covers what happens when Save is clicked after this
swallow; this card covers the separate, more expensive consequence when Run once is clicked
instead — real Bedrock spend against an unrelated pipeline, not a wrongly-created saved row.

## Condition

Load `/workflows/{id}/canvas` for an id that genuinely exists, at a moment the
`GET /api/workflows/{id}` request fails for any reason other than "not found" (network
interruption, a transient 5xx, a timeout) — not a malformed or nonexistent id.

## Expected vs actual

**Expected:** a transient fetch failure is distinguished from "no such workflow" (e.g. retried,
or surfaced as an explicit error/retry state) — and in neither case should "Run once" ever be
reachable with an unpopulated roster.

**Actual (predicted):** the identical silent full-9-agent-pool substitution ISS-234 documents,
triggered by ordinary fetch flakiness on a real workflow rather than a bad URL — meaning a fix
scoped to "detect a 404 and show not-found" would leave this trigger unaddressed.

## Why the root cause implies this

ISS-234's and ISS-299's shared mechanism is that `page.tsx:494-496`'s catch cannot tell "this
workflow does not exist" apart from "this fetch failed for some other reason" — both collapse to
the identical `initialSavedComposition = null`. ISS-299 already established this ambiguity
matters for Save; the same ambiguity feeds directly into [ISS-234](20260828-1628-ISS-234.md)'s
Run once mechanism, since both consequences share the identical precondition
(`pipelineAgents = []`) produced by the identical swallow. Fixing ISS-234's backend/frontend gap
(reject or block a 0-agent "custom" launch) closes this trigger too without needing to fix the
catch itself — but until then, this card records that the trigger is not "a dead link," it is
"this catch ever firing," which is a strictly larger set of conditions.
