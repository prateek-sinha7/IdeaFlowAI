# ISS-660

## Title

The "From v{n-1}" base-version section of the Files tab reconciles the **parent** run's row
against its workspace file through the exact same unconditional override QA-PS-007
([ISS-651](20260917-1200-ISS-651.md)) found for the current run's row — so viewing a base
version whose underlying pipeline is `ppt`/`ppt_v2`/`ppt_revision` (or, per
[ISS-659](20260917-1305-ISS-659.md), `prototype`) shows the same generic name there too.

## Status: INFERRED — not yet reproduced

Filed from the root cause of QA-PS-007, not from an independent reproduction. Whoever picks
this up should confirm it live before treating it as a confirmed defect (see "What would
confirm this" below).

## Why QA-PS-007's root cause implies this

QA-PS-007's root cause is that `withWorkspaceFile()`
(`frontend/src/components/results/FilesTab.tsx:451-462`) unconditionally replaces a
content-derived row's `name` with the raw on-disk basename once the run's real workspace file
is resolved. That function has **two** call sites, and QA-PS-007's own trace
([ISS-651](20260917-1200-ISS-651.md)) only follows the current-run one (`FilesTab.tsx:665`).
The second call site is the base-version toggle:

- `frontend/src/components/results/FilesTab.tsx:482-517` (`handleToggleBase`) — on first
  expanding the "From v{n-1}" section, it derives `rows` for the **parent** run via
  `deriveDeliverableFiles(parentRun.type, ...)` (line 494, content-derived, correct), then at
  **line 509**: `if (hit) setBaseFiles([withWorkspaceFile(rows[0], parentRunId, hit),
  ...rows.slice(1)]);` — the identical unconditional override, applied to the parent run's
  first row with no exclusion for any row id (unlike the current-run call site, this one has
  no `prototype-figma-json` guard at all, though `deriveDeliverableFiles` itself never
  produces that row for a base fetch).

Since the parent run can itself be any pipeline type — including `ppt`/`ppt_v2`/`ppt_revision`
(this bug) or `prototype`/`prototype_revision` ([ISS-659](20260917-1305-ISS-659.md)) — the
same on-disk hardcoded filename (`presentation.html` / `prototype.html`) resolves via
`resolveRunDeliverable` and overwrites the parent's correctly content-derived name the same
way.

## Expected (once reproduced)

Expanding "From v{n-1}" on a ppt or prototype revision run shows the **parent** run's file
named after the parent's own topic/title, matching what the parent run's own Files tab would
show when opened directly.

## Actual (inferred, not yet observed)

The parent row's filename in the "From v{n-1}" section is always the generic on-disk name
(`presentation.html` for a ppt-family parent, `prototype.html` for a prototype-family parent),
regardless of the parent run's actual topic.

## What would confirm this

1. Sign in as `qa-admin@flowinqa.com`, open a `ppt_revision` (or `prototype_revision`) run
   that has a parent run (`v1`).
2. Open the Files tab, expand the "From v{n-1}" section.
3. Read the parent row's filename — if it reads `presentation.html` / `prototype.html`
   instead of a topic-derived name, this is confirmed.
