## What was wrong

This is register bug **QA-PS-006**. In the concierge chat, every pending review gate read
`Review required`, word for word. On a run with several gates you could not tell which agent's
output was waiting for review. The root cause is recorded in [ISS-653](20260917-1050-ISS-653.md).

## Root cause

`frontend/src/components/chat/ResultCard.tsx:146-147` (pre-fix): the unresolved half of the gate
ternary was the bare literal `"Review required"`.

[FIX-518](20260917-1321-FIX-518.md) had already added the plumbing ISS-653 said was missing:

- `backend/app/agents/chat_narrator.py:265` puts `agent_name` on the gate card.
- `frontend/src/hooks/useRunChat.ts:423` reads it into `ChatMessage.agentName`
  (`frontend/src/types/index.ts:115`).

Only the resolved half of the ternary printed it.

## What changed, and why there

`ResultCard.tsx:148-150`: an unresolved gate now reads `<agentName> review required`. With no
`agentName`, the old literal renders unchanged. This mirrors FIX-518's resolved branch two lines
above. The comment at `:139-140` now says so.

**Why here.** This ternary is the only thing that produces the text:

- every chat-lane turn renders through the single `<ResultCard>` in
  `frontend/src/components/chat/MessageBubble.tsx:220`;
- a gate card comes from one event only, `review_gate_ready` (`chat_narrator.py:51`), and that is
  the event FIX-518 reads the name from.

Nothing else needed to change.

**Only new gate cards get a name.** `chat_reply` rows are persisted when they are emitted. A
read-only `GET /api/runs/<id>/events` pass on 2026-09-17 at 13:36 found no `agent_name` on any gate
`chat_reply` in the last 50 runs. That includes the three ISS-653 repro runs `0ab2ba21`,
`81bc416e` and `3fcd25a9` (all `completed` by then), plus `a7279a95`. Those runs keep the bare text.
To check this fix in the UI, use a gate that opens after the backend loaded FIX-518's
`chat_narrator.py`.

Invariants:

- SC-001 holds: `grep -rn "if pipeline_type ==\|if spec.id ==" backend/agents/execution_engine/`
  returns 0.
- `ResultCard` checks only whether `agentName` is present, never its value.
- The change is frontend-only: no import added, no migration touched.

## Not fixed here

[ISS-664](20260917-1310-ISS-664.md) is the sibling on this bug's ledger row. Reopening a terminal
run still marks every gate card resolved, rejected ones included, and such a card now reads
`<agent> review approved`. The card stays `open` and its `it.fails` stays in place, for three
reasons:

- **Not reproduced.** The card is INFERRED and asks for a live repro before anyone fixes it.
- **Its test cannot see the fix its card describes.** The card blames the caller:
  `REOPEN_TERMINAL_STATUSES.has(status)` at `frontend/src/app/[...view]/page.tsx:3028`. The test at
  `useRunChat.test.ts:597` calls the hook directly with `true`, which is the same value a
  completed-run reopen passes. Narrowing the caller's flag cannot turn that test green.
- **Passing it inside the hook is a design decision.** The hook would have to keep a gate with no
  `review_gate_approved` frame pending even when told the run is terminal. That missing-approval
  case is exactly what the auto-resolve exists for (`useRunChat.ts:739-742`). Family members, for
  example, are seeded with chat frames only (`page.tsx:2974`). So the hook would need another way to
  tell approved from not approved:
  - store the gate's outcome on the persisted card;
  - match approval frames to gates by agent (see [ISS-654](20260917-1250-ISS-654.md));
  - or treat the opened run differently from its family members.

  Narrowing the caller's flag has its own cost too. Gates that were approved earlier in a cancelled
  or failed run would read `review required` again.
