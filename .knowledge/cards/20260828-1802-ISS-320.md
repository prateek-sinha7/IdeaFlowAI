## What happened

On `/settings/constitution`, the "Clear" button next to "Save constitution" is not a
form-reset control. `handleDelete` (`frontend/src/components/settings/AccountSettings.tsx:537-553`)
fires `DELETE http://localhost:8000/api/settings/constitution` synchronously on click and, on a
`200`, immediately sets `content` to `""` and `status` to `"deleted"` — no confirmation dialog,
no undo, and no requirement to also click "Save constitution". The button sits directly beside
"Save constitution", and the textarea never auto-saves, so its placement strongly implies a
local/pending-edit reset. It is in fact a destructive, irreversible, immediately-persisted
account-wide delete of the standing instructions the page itself says are "prepended to every
agent on every run".

## Reproduction — CONFIRMED 3/3, cold start each cycle

Account: qa-admin (default tier; not tier-specific). Baseline saved content before every cycle:
`"E2E S-09-12: answer in exactly one sentence."` (44/4000 chars), confirmed via
`GET /api/settings/constitution` before each attempt and restored via
`PUT /api/settings/constitution` + reload after each attempt.

- **Cycle 1** — cold nav `/dashboard` → `/settings/constitution`, saved value visible
  (44/4000), click "Clear" directly on the untouched saved value. Textarea instantly emptied to
  "0 / 4000 chars", status message "Constitution cleared." appeared, "Save constitution" became
  disabled. `GET /api/settings/constitution` immediately after → `{"content": null}`. **Failed
  (bug reproduced).**
- **Cycle 2** — cold nav `/dashboard` → `/settings/constitution` again (fresh page load,
  restored content re-verified present), click "Clear" on the untouched saved value again.
  Same result: `GET` → `{"content": null}` immediately after the click. **Failed (bug
  reproduced).**
- **Cycle 3** — cold nav `/dashboard` → `/settings/constitution`, this time typed an unsaved
  draft edit into the textarea first (never clicked "Save constitution"), then clicked "Clear".
  The backend's real saved value was deleted anyway — `GET` → `{"content": null}` — proving
  "Clear" acts on the persisted record, not the local draft, regardless of whether a draft is
  pending. **Failed (bug reproduced).**

All three cycles: `DELETE /api/settings/constitution` returns `204`, no confirm dialog/prompt
ever appears, and the deletion survives a full page reload (checked after cycle 1's restore).
Restored the original content after every cycle via `PUT` + reload before finishing.

## Expected vs actual

**Expected:** a destructive, irreversible action that erases a user's standing instructions for
every future agent run requires an explicit confirmation step (dialog, or at minimum requires
also clicking "Save constitution" to commit the empty state) before it reaches the backend —
consistent with how "Save constitution" itself requires a deliberate, separate click to persist
any change.

**Actual:** `handleDelete` calls `DELETE` on click with no confirmation gate at all, and does so
regardless of whether the textarea currently holds saved content, an unsaved draft, or a mix of
both — a single misclick permanently destroys the user's constitution.

## Resolution

Fixed by [FIX-385](20260829-0241-FIX-385.md): `handleDelete` now returns early
unless a `window.confirm` is accepted, so an unconfirmed "Clear" never sends
the DELETE. Verified directly against the running app — dismiss leaves the
persisted value intact, accept still deletes. The e2e test named below cannot
yet prove it for reasons of its own, recorded in
[ISS-581](20260829-0241-ISS-581.md).

**6-verifier confirmation (2026-08-29):** independently reran the manual repro
in real Chrome (qa-admin) and it matches FIX-385's evidence exactly — dismiss
preserves the saved value, accept deletes. `AccountSettings.render.test.tsx`
8/8 green, `tsc --noEmit` clean on the changed file. The e2e test
`test_clear_constitution_requires_confirmation_before_deleting` was run 5
times: 4× `xfail`, 1× hard `FAILED` on the same double-dialog-handler crash
already attributed to ISS-581 — never XPASS, so the `xfail` marker stays. This
is a genuine issue-fixed-but-test-still-blocked case: `verification.status`
is set to `passed` on the strength of the manual/unit evidence, not the e2e
test, which remains blocked by ISS-581.

## Root cause

`frontend/src/components/settings/AccountSettings.tsx:537-553` — `handleDelete` is wired
directly to the "Clear" button's `onClick` (line 617) with no intermediate confirm step (no
`window.confirm`, no modal, no two-step "are you sure"). Compare to `handleSave` (adjacent),
which is the only other write path and is a single explicit user action by design — "Clear"
should not have equal one-click weight for a destructive delete vs. a non-destructive save.
