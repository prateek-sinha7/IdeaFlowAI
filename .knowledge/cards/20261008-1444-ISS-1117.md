# ISS-1117

**Register source:** split out of [ISS-1112](20261008-1415-ISS-1112.md) ("Adjacent, not implied by the root cause ... split it if it
should be tracked alone") when [FIX-766](20261008-1444-FIX-766.md) resolved that card without fixing this.

**Confidence:** CONFIRMED that the check is missing (code read at HEAD `d284eb258`, and `evidence/qa-kb-100/analysis-05` W4: a
BASIC caller synced `sample_subagents_parallel`, which is enterprise-only, into its row and got **200** before FIX-766). The
launch of a synced plain row is INFERRED from the Case 3 code and analysis-05 W5. No run was launched.

## Condition

`sync_user_workflow_from_file` (`user_workflows.py:1096`) authenticates with `get_current_user`, not the principal. It checks
`body.pipeline_type in SUPPORTED_PIPELINE_TYPES` (`:1120`) and row ownership (`_owned`), loads the file manifest (`:1129`), and
stores it verbatim (`:1147`). It never calls `can_run_pipeline` on `body.pipeline_type`. Create does call it (`:740`), on the
caller-chosen `base_pipeline_type` only.

What FIX-766 already closes: when the target row is an override, the synced steps must now compile at `trust="user"`. A
privileged source (W4) is refused with 422 (`evidence/qa-kb-100/fix-06` F2).

What it leaves open:

1. **Plain row (no `overrides_pipeline_type`).** The whole file manifest is stored. At launch, Case 3 compiles it at `trust="db"`,
   and the tier gate keys on the row's own `base_pipeline_type`, which the caller chose (`run_commands.py:3413`, `:3458`). A basic
   user with a `ppt`-based row can therefore run, for example, `sample_subagents_parallel`'s steps with their `spawn_subagents`
   grants. This is [ISS-1114](20261008-1415-ISS-1114.md)'s shape, reached through a different door.
2. **Override row.** The user-allowed steps of an enterprise-only workflow can still be copied into a lower tier's override and run
   under that tier's built-in. They are not privileged, but they are an entitlement bypass for content.

## Expected vs actual

Expected: syncing from a pipeline the caller's effective tier may not run is refused (403), the same way create refuses a base it
may not run. Actual: 200.

## Fix direction (not applied)

Resolve the effective tier the way create does (`get_current_principal` plus `effective_tier`) and refuse with 403 when
`can_run_pipeline(tier, body.pipeline_type)` is false, before the file is read. Item 1 also depends on the
[ISS-1114](20261008-1415-ISS-1114.md) decision. A test belongs in `tests/integration/api/`, using the `_FakeUser(tier="basic")`
harness from `test_iss1112_override_writers_trust.py`.

## Analysis (QA-KB-104, analyzer, 2026-10-08, HEAD 135e6ea9b)

Read against HEAD `135e6ea9b` (no change under `backend/`, `agents/`, `frontend/` or `tools/` since `c9c4c630a`). Nothing was edited. The probes are offline (in-memory SQLite, the
run core stubbed, `DATABASE_URL=sqlite:///:memory:`), kept in `evidence/qa-kb-104/analysis-plugins/`. Every quote below is re-printable from
`evidence/qa-kb-104/analysis-06-source-excerpts.txt`.

### Root cause (CONFIRMED)

`sync_user_workflow_from_file` (`user_workflows.py:1095-1155`) stores the manifest of a pipeline the caller names and never asks whether the caller's tier may run it.
It authenticates with `current_user: User = Depends(get_current_user)` (`:1099`), so it has no `Principal` and could not compute `effective_tier` if it wanted to. Its
only gates are `if body.pipeline_type not in SUPPORTED_PIPELINE_TYPES` (`:1120`) and row ownership (`_owned`, `:1126`). It then writes `row.manifest_json = new_manifest`
and commits (`:1147-1148`). The same router's create door has both pieces: `Depends(get_current_principal)` (`:711`) and
`can_run_pipeline(effective_tier(current_user, principal), body.base_pipeline_type)` (`:740-744`).

How it got there (`git log -S`): create and its gate date from `9d733d543` (2026-06-14, Phase 21). The sync endpoint arrived in `1e329e47b` (2026-09-04) on `get_current_user`.
The Cognito migration (`b2a621f84`, 2026-09-17) moved create and PATCH onto the principal; the sync handler already existed and kept `get_current_user`. The
`DOMAIN-auth-and-entitlements` card records the class: the gate is a call placed per door, and "a new launch endpoint that never calls `can_run_pipeline`. Nothing
fails" ([ISS-055](20260812-0036-ISS-055.md), [FIX-189](20260806-1335-FIX-189.md) are the earlier instances).

Why a stored copy is a bypass: at launch the row dictates its own base type (`run_commands.py:3424`), the tier gate keys on that base (`:3469`, through
`_require_tier_entitlement`, `:2604-2612`), and a saved row that is not an override compiles at `trust="db"` (`:3367-3369`). So the base the caller picked passes, and the
foreign steps ride in under it. (The Condition section's `run_commands.py:3413` and `:3458` are these `:3424` and `:3469` at an older HEAD.)

### What was INFERRED on the card and is now CONFIRMED up to the mint

The launch of a synced plain row was INFERRED above. Probe C (`analysis-02-probe-launch-of-synced-row.txt`) drives the real `POST /api/runs` handler as a BASIC caller with
only `_launch_run_core` stubbed (so nothing is minted or spent). For each of `sample_subagents_parallel`, `app_builder`, `mulesoft_to_springboot` and `custom`: launching it
directly is **403 `tier_not_entitled`**; syncing it into the caller's plain `ppt` row is **200**; launching that row (`{pipeline_type: ppt, user_workflow_id}`) is **200**
and reaches the run core with `pipeline_type='ppt'`, `compiled.id` equal to the foreign pipeline (4, 15, 13 and 9 steps), `_trust='db'`, and `spawn_subagents` on one step of
`sample_subagents_parallel`. The run would be recorded as a `ppt` run. Still not driven: the mint itself and the run.

This is not a disclosure bug. `GET /api/workflows/{id}` already serves every known workflow's `manifest_steps` to any authenticated tier (`workflows.py:431`, `:535-539`; the
module docstring says "JWT-only"). The harm is the right to run, so reads must not be gated as part of this fix.

It is also not the only way to the same stored state. `_validated_manifest` returns the manifest dict whole (`user_workflows.py:236`) and a plain row compiles at `db`, so a caller
can POST or PATCH a hand-copied manifest and reach this card's end state. Closing the sync door makes it consistent with create and launch and removes the byte-exact copy; it does
not by itself stop a basic caller running an enterprise-only workflow's steps. That is [ISS-1114](20261008-1415-ISS-1114.md)'s decision and it stays open.

### Where the fix belongs

In the handler. It is the only caller of the loader, and the only code that holds the row, the body and (after the signature change) the principal. Not in
`_load_file_manifest_dict` (no principal there) and not in the request model.

```python
auth: tuple[User, Principal] = Depends(get_current_principal),   # was: current_user = Depends(get_current_user)
...
current_user, principal = auth
# right after the SUPPORTED_PIPELINE_TYPES check, before _owned and before the file is read:
allowed, reason = can_run_pipeline(effective_tier(current_user, principal), body.pipeline_type)
if not allowed:
    raise HTTPException(status_code=status.HTTP_403_FORBIDDEN, detail=reason)
```

`can_run_pipeline`, `get_current_principal` and `effective_tier` are already imported at `user_workflows.py:49-51`; no new import. Lifting create's inline block (`:740-744`)
and this one into one private helper is an optional refactor, not part of the fix. The handler docstring (`:1113-1115`) promises 422 for everything else and needs the 403 added.

### Traps

- `current_user.tier` is the advisory projection; `core/identity.py` and `run_commands.py:2582-2584` ("No gate may read the projection alone") require `effective_tier`.
- Changing the dependency to `get_current_principal` makes any fixture that overrides only `get_current_user` answer 401 (the [ISS-905](20261001-2149-ISS-905.md) shape). No backend test calls
  this endpoint today; the new one must override both, as `test_iss1112_override_writers_trust.py` does.
- Gate on the raw `body.pipeline_type`, as launch does (`run_commands.py:3465-3469`). `resolve_alias` is the identity today (`_OD_ALIAS_BASE` is `{}`, `registry.py:81`).
- Tiers are not a chain: hexaware cannot run the `ppt` family, pro cannot run `custom`. Use `can_run_pipeline`, never a tier rank.
- Visible behaviour change: the 10 types no tier may run answer 403 for enterprise too (200 today), which matches create and launch. If the gate runs before the file is read,
  `spec_kit` and `file_analyst` change from 422 to 403.
- `tests/integration/capture/_api.py::auth_of` does not know `get_current_principal` ([ISS-1065](20261007-1940-ISS-1065.md) section 3); the route will read as public in a regenerated snapshot,
  like the other principal routes. Not caused by this change.

### What the fix leaves open

- Rows already stored. The dev DB holds 0 rows in `workflows` (`analysis-03`), so nothing to remediate there. For a real database, a filled-from-file row is recognisable by a top-level `id`
  in `manifest_json` (a canvas or Composer save is `{"steps": [...]}` and launch adds the `id`, `run_commands.py:3373-3378`):
  `SELECT id, user_id, base_pipeline_type, overrides_pipeline_type, manifest_json->>'id' FROM workflows WHERE source='user' AND (manifest_json::jsonb) ? 'id'`, then compare each owner's
  Cognito tier with `can_run_pipeline`. The launch gate will not stop them (it keys on the base type); a content-following gate is [ISS-1114](20261008-1415-ISS-1114.md) option a.
- The trigger door, [ISS-1131](20261008-2216-ISS-1131.md).
