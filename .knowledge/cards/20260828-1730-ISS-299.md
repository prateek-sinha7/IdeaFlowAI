## Source

Register entry: **BUG-20260828-040400-workflows-nonexistent** in `bug-hunter/ledger.md`.

## Reproduction (3/3, cold start each cycle)

Reproduced on **all 3 cycles**, each a fresh, independent navigation from `/dashboard` (not a
soft re-click of the same screen), qa-admin tier, light theme (default), signed-in session:

- **Cycle 1:** cold-navigate to
  `http://localhost:3000/workflows/00000000-0000-0000-0000-000000000000/canvas`. Console fires
  `GET http://localhost:8000/api/workflows/00000000-0000-0000-0000-000000000000 => 404`. Page
  renders a fully interactive composer: header `00000000-0000-0000-0000-000000000000 · copy`,
  "0 agents", empty "Workflow name"/"Workflow description" fields, working Brief panel, and an
  enabled "Save as copy" button. No 404 page, no error text anywhere in the body.
- **Cycle 2:** cold-navigate (via `/dashboard` first) to a differently-shaped, non-uuid bad id,
  `http://localhost:3000/workflows/totally-bogus-id-12345/canvas`. Identical result — header
  `totally-bogus-id-12345 · copy`, "Save as copy" present and enabled.
- **Cycle 3:** cold-navigate (via `/dashboard` first) to a third, distinct uuid-shaped bad id,
  `http://localhost:3000/workflows/ffffffff-ffff-ffff-ffff-ffffffffffff/canvas`. Identical
  result — "Save as copy" present and enabled, no 404.

Conditions established: the trigger is any `workflowId`/`pipelineType` segment on the
`/workflows/{id}/canvas` route that does not resolve server-side — id shape (well-formed uuid,
malformed uuid, arbitrary string) does not matter, and it is not a caching artifact of one
specific id (three distinct ids across three independent cold loads, same result every time).
qa-admin tier and light theme were not varied further since 3/3 already named the trigger.

Not re-verified in this pass, but part of the original hunter's report and consistent with the
mechanism above: filling the "Workflow name" field, adding a real agent via "+ Add", and clicking
"Save as copy" fires `POST /api/user-workflows` which returns `201 Created` with a real, fresh,
persisted workflow — this route does not merely render a hollow shell, its primary action
actually completes and writes new data.

## Expected vs Actual

**Expected:** `/workflows/{id}/canvas`, like the bare workflow detail route and `/workflows/{id}/edit`
for the same bad id (both independently verified hardened in this investigation), should render
the app's generic 404 page when the source workflow does not exist. The frontend already receives
a genuine `404` from `GET /api/workflows/{id}` — it only needs to act on it.

**Actual:** The 404 is swallowed and the canvas route seeds an empty "copy" composer instead,
with no error/not-found UI anywhere. The composer is not inert: "Save as copy" is enabled and
successfully creates a real, persisted workflow via `POST /api/user-workflows` (`201`), so a
literally dead link can be used to originate new user data.

## Root cause (read, not fixed)

Same class of defect as [ISS-253](20260828-1646-ISS-253.md) — an unchecked 404 on a
`getWorkflowDetail(jwt, workflowId)` call — but a different call site and a materially worse
outcome (ISS-253's composer is permanently disabled; this one's completes a save).

- `frontend/src/app/[...view]/page.tsx` resolves the `workflow-canvas` screen
  (`case "workflow-canvas":`, line 135) and treats the URL segment purely as a
  `pipelineType`/`workflowId` string with no existence check (comment at line 433-436: "seed the
  composer straight from the manifest").
- `frontend/src/components/workflow/composer/ComposerPage.tsx:410-441` — the `declaredCapabilities`
  effect calls `getWorkflowDetail(jwt, workflowId)` and on failure does
  `.catch(() => { if (!cancelled) setDeclaredCapabilities(undefined); })` — a swallow intentional
  for the optional SURF-03 capability strip (documented at `frontend/src/lib/api.ts:1634-1640`:
  "An unknown id raises 404 server-side, the caller treats that as 'nothing declared'"), but
  reused as the only place that ever observes the fetch's outcome for the canvas mount overall.
  Unlike ISS-253's `/create/{slug}` path (where `pipelineAgents.length > 0` gates every action
  button so the composer dead-ends disabled), the canvas composer's "Save as copy" affordance is
  NOT gated on any fetched-workflow state — it operates purely on local composer state (name,
  description, added agents), so it stays enabled and functional regardless of whether the
  underlying workflow ever existed.
