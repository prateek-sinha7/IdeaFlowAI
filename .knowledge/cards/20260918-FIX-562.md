## The symptom

A `prototype_v2` launch from the wizard died on step one: `fi-planner` opens
`.uploads/manifest.json` and calls `extract_text` on the real files, and the
directory was empty. The workflow was unlaunchable from its own declared
`launch_surface: wizard`. Separately, the run that did start was running the
`prototype` pipeline, not `prototype_v2`, with no error anywhere.

## Root cause — two independent holes in the same four-hop plumbing

The hand-off is `LaunchWizard` → `buildLaunchDraft` → sessionStorage →
`page.tsx` pending/staged state → launch. Both defects are generic, not
`prototype_v2`-specific.

**1. Nothing was ever staged.** `LaunchWizard` only ever INLINED
`extractFileText`'s capped flat text into the brief. It never called
`stageRunFile` — unlike `useBriefAttachments`, which IdeaInputPage and
ComposerPage use. But `.uploads/` is populated solely from `staged_upload_ids`
(see [FIX-560](20260901-FIX-560.md) for the backend half), so **every** wizard
launch reached its agents with an empty uploads directory. Text documents were
worse off still: `.csv`/`.md`/`.txt`/`.json` are read client-side for the
inlined preview and were never staged at all, so an attached CSV arrived as
brief text and was missing from `.uploads/manifest.json` entirely.

**2. `pipelineType` was a deck-only field.** It was appended to the draft for
`ppt_v2` and threaded through the deck pending/staged shapes, but the web setter
in `page.tsx` had no `pipelineType` spread at all. A `prototype_v2` launch
therefore fell back to `prototype`.

## What changed

`LaunchWizard.tsx` (+133) — imports `stageRunFile` and `orderedStagedUploadIds`,
stages every text or binary attachment fire-and-forget with a synchronously
captured `attachIndex`, prunes `stagedUploads` when a chip is removed, and sends
`stagedUploadIds` on the draft. The extraction-failure message changed
deliberately: the `[could not be extracted]` block is now written only when the
server-side stage ALSO failed.

`launchDraft.ts` (+21) — new optional `stagedUploadIds` (length-guarded like
`images`), `prototype_v2` added to `LaunchMode` sharing `prototype`'s draft slot,
and `pipelineType` appended for `prototype_v2` as well as `ppt_v2`.

`page.tsx` (+30) — `stagedUploadIds` and `pipelineType` threaded through all four
pending/staged shapes, including the web setter that previously had no
`pipelineType` spread.

`LaunchWizard.test.tsx` (+95) — four `UPLD-05` tests: stage ids reach the draft
in attach order, text documents stage too, staging ADDS a path rather than
replacing the inlined text, and the key is omitted entirely when nothing was
attached.

## Verification

The four `UPLD-05` tests pass. Note for a future reader: two OTHER tests in the
same file (`WR-07` chaining and the `BUG-014` chain-source case) currently fail
on a null `prototype.draft`; this commit did not touch them and does not claim
them. Verified end to end on run `26a7e162`: all five documents present in
`.uploads/`.
