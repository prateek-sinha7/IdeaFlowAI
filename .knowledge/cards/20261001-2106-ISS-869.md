# ISS-869

## Title

**INFERRED sibling of [ISS-077](20260812-0212-ISS-077.md): `ArtifactVersionPicker` walks only the top level of the nested artifact tree, so versions linked by `derived_from` (gate Redo or Edit) are invisible and the picker renders nothing.**

## Provenance (read this first)

Derived by the analyzer from the root cause of [ISS-077](20260812-0212-ISS-077.md) while analysing QA-KB-029; no user reported it.

- CONFIRMED (code read, plus the real function executed on real data at unit level): the wire nests a derived version under `children`, and the unmodified `collapseVersions` returns 1 version where the run holds 2.
- INFERRED (not executed): the exact symptom in the browser; the middle-version no-op in a 3-deep chain; partial masking where a `produces` row happens to be a root.
- What settles the INFERRED parts: sign in as `admin@velocity.ai`, open run `8d4d2d70-9357-4780-a43f-405a25712807` (a `backlog_revision` whose human gate outcome is `redo`), Steps tab, agent `custom-agent:blr-analyst`. Expected: 2 versions and a picker. Predicted: no picker. Second run: `429dc032-8038-4f0a-9558-ee666c7f5da3`, agent `custom-agent:ask`.

## Condition

An agent in one run has a version whose `derived_from` names an EARLIER version of the same agent in the SAME run. The engine writes that edge on:

- gate Redo re-runs: `backend/agents/execution_engine/engine.py:10730` (`derived_from=_iter_derived`);
- gate Edit: `engine.py:9337`, `:9478`, `:10976`, `:11888` (`derived_from=_prior_ref`, resolved by `_latest_typed_ref_id`, `engine.py:13974`).

It does not write the edge on the `produces` rows (`engine.py:10743-10752`) and the Redo lineage local is assigned only from `_consume_redo` (`engine.py:9346`, `:9494`, `:10991`), so an `update_specs` re-run produces roots. That is why the shipped picker works for the case [FIX-222](20260812-0158-FIX-222.md) was built around (all-root `spec` v1-v3).

## Expected vs actual

- Expected: the Steps-tab picker lists every distinct version of the agent (v1..vN) and opens any of them.
- Actual (CONFIRMED): `GET /api/runs/{id}/artifacts` returns the tree from `_build_lineage_tree`; a node whose `derived_from` is in the response set is appended to its parent's `children` and is not a top-level element (`backend/app/api/runs.py:1448-1452`). `collapseVersions` loops over the array it is given (`frontend/src/components/results/ArtifactVersionPicker.tsx:70`, called with `resp?.artifacts` at `:124`), so the derived version is never seen; with one version left, `if (versions.length <= 1) return null;` (`:177`) hides the control entirely.
- Actual (INFERRED from reading `:162`): `select()` runs `rows.find((r) => r.id === v.id)` over the top level of a `?kind=` response, so in a chain of three the middle version cannot be opened: no row is found, `onSelect` is never called and the panel silently stays on the live output.

## Why the root cause (ISS-077) implies it

[ISS-077](20260812-0212-ISS-077.md) predicted that "the first consumer of the lineage tree will be type-checked against a lie". The lie is `children: string[]` (`frontend/src/lib/api.ts:1509`): nothing in the declared type tells a consumer that nodes nest, so the picker treats `artifacts` as a flat list. Its tests could not catch this: the `node()` helper in `ArtifactVersionPicker.test.tsx:32-51` hard-codes `derived_from: null, children: []` (the flat `update_specs` shape) and no fixture contains a nested chain. Correcting the types in ISS-077 does not change this behaviour; it needs its own code change.

## Evidence (read-only; full transcript in `evidence/qa-kb-029/02-analyze-wire-shape-and-picker-undercount.txt`)

- Real rows (Postgres, SELECT only): run `8d4d2d70-...` holds `summary` v1 `37b4c2fe` and v2 `d2fd00e6` with `derived_from = 37b4c2fe` for `custom-agent:blr-analyst`; its `gate_events` row is `('human','redo')`. Run `429dc032-...` holds `summary` v1 `15ba1296` and v2 `d9f069da` (`derived_from = 15ba1296`) for `custom-agent:ask`, written on a human-gate path (`gate_events`: human/pass, conditional/route). These are the only 2 same-run chains among the 15 `derived_from` rows in 1963 `artifact_refs` rows; the other 13 name a parent RUN's artifact, which is outside the response (`runs.py:1402-1409` restricts parents to in-set ids), so those surface as roots.
- Wire: `_build_lineage_tree` on the real ORM rows gives 5 rows to 4 top-level nodes (run `429dc032`) and 10 rows to 9 (run `8d4d2d70`), each with one nested child.
- Executed: the unmodified `collapseVersions`, transpiled from `ArtifactVersionPicker.tsx`, returns 1 version for each of the two agents on that wire; the same function on the flattened tree returns 2.

## Fix (proposed, not applied)

Walk `children` at both read sites in `ArtifactVersionPicker.tsx` (`:70`/`:124` and `:162`). Smallest form: one pure helper such as `const flattenArtifacts = (ns: ArtifactNode[]): ArtifactNode[] => ns.flatMap((n) => [n, ...flattenArtifacts(n.children)]);`, exported from `frontend/src/lib/api.ts` beside `ArtifactNode` so a later tree consumer routes through it. The `frontend/src/lib` module card records that artifact reads are deliberately returned raw (un-normalized), so the flattening belongs in a consumer-side helper, not inside `getRunArtifacts`. It needs the `children: ArtifactNode[]` correction from ISS-077 to type-check.

Caveats for the fixer:

1. Pre-order flattening keeps a derived chain chronological (a parent always precedes its child) but is not globally chronological across unrelated roots, and `collapseVersions` numbers versions by first-seen `content_hash`; the test must include roots interleaved with a chain.
2. Nodes carry no `created_at`, so do not re-sort by time.
3. `WorkflowHistory.tsx:441` and `parseClarificationArtifacts` also iterate the top level only but are unaffected today: 30 `clarifications` rows, 0 with `derived_from`, and `clarify_engine.py:1114` writes none. Leave them alone unless the helper is adopted there for consistency.

## Test notes

It fails today (renders nothing). Add a 3-deep chain and assert that opening the middle option calls `onSelect` with that version's content (covers `:162`).

## Fix (QA-KB-029, 2026-10-01)

Resolved by [FIX-679](20261001-2126-FIX-679.md). `ArtifactVersionPicker.tsx` now walks the tree with a module-local, pre-order `flattenArtifacts` in two places:

- inside `collapseVersions` (`:76`);
- where `select()` fills its per-kind content cache (`:165`), so the `find` at `:168` reaches nested versions.

**Placement deviation, with reason.** The helper is not exported from `lib/api.ts` as this card suggested. Every test that mounts the picker mocks `@/lib/api` with a two-export factory, and vitest throws when code reads any other export. The full reasoning is in FIX-679.

Observed results:

- `ArtifactVersionPicker.iss869.test.tsx` now fails its `it.fails` with "Expect test to fail", which is the pass signal. The marker is left for the verifier.
- On the analyze phase's real wire dumps, the fixed `collapseVersions` returns 2 versions for each of runs `429dc032` and `8d4d2d70`.
- A synthetic 3-deep chain numbers v1..v3 in order, and the middle version is found.
