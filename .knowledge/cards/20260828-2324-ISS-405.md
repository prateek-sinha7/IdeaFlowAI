## What is suspected — INFERRED, not reproduced

Sibling of [ISS-295](20260828-1726-ISS-295.md) (BUG-20260828-033400-admin's root card), derived from
the same root cause pushed to its "boundary and empty" extreme: ISS-295 establishes that
`POST /api/admin/users` performs **no email-format validation at all**, client or server. The
Create-User dialog's own client-side gate (`!newEmail`, `admin/page.tsx:213` and `:512`) DOES
block a literally empty string from the browser UI — but that gate lives only in the React
component, not in the API contract, and the whole point of ISS-295's "Expected" section is that
the backend must independently reject bad input regardless of what the client does. Since the
backend schema imposes no lower bound on `email` at all, a caller that skips the browser
(`curl`/Postman/an old client, with a valid admin bearer token) can submit `email: ""`, and
nothing rejects it before it reaches the DB and, on the next `/admin` load, a specific unguarded
line in the table renderer.

This is a plausible but **unverified** lead — no live request was sent in this analysis pass.
What would confirm it: `POST /api/admin/users` with body `{"email": "", "password": "abcd1234"}`
and a valid admin bearer token, then reload `/admin` in a browser and observe whether the page
renders or crashes to the `error.tsx` fallback.

## Root cause — the same missing check, at its extreme, exposing an unguarded consumer

**Confirmed by file:line read, chained across three files:**

1. `backend/app/api/admin.py:130-134` — `CreateUserRequest.email: str`, a bare Pydantic `str`
   field with no `EmailStr` type, no `Field(..., min_length=...)`, no pattern. Contrast
   `backend/app/models/schemas.py:15` (`RegisterRequest.email: EmailStr`) and `:22`
   (`LoginRequest.email: EmailStr`) — the codebase's own established pattern for a validated
   email field, not used here.
2. `backend/app/api/admin.py:392-512` (`create_user`, read in full) — the handler's own manual
   checks are: duplicate email → 409 (`:409-414`), tier allow-list → 400 (`:416-421`), password
   `len(...) < 8` → 400 (`:423-427`). None of these three checks reject an empty string —
   `""` is not a duplicate (assuming no prior empty-email row), passes the tier/password checks
   independently, and is written verbatim into `User(email=request.email, ...)` on the local-auth
   path (`:434-441`) or the Cognito path (`:477-486`).
3. `backend/app/models/user.py:29` — `email = Column(String, unique=True, index=True,
   nullable=False)`. `nullable=False` rejects `NULL`, but `""` is a valid non-null string, so the
   DB layer offers no backstop either.
4. `frontend/src/app/admin/page.tsx:391` — `{user.email[0].toUpperCase()}`, inside
   `filtered.map((user, i) => ...)` (`:379`), rendering the avatar-initial for **every** row in
   the users table, unconditionally, with no null/empty guard. In JavaScript, `""[0]` is
   `undefined`, and `undefined.toUpperCase()` throws `TypeError: Cannot read properties of
   undefined (reading 'toUpperCase')`. (For a non-empty malformed email like ISS-295's
   `not-an-email`, this same line is what produces the harmless "N" initial the original bug
   report observed — `"not-an-email"[0]` is `"n"`. It is specifically the EMPTY-string case that
   breaks it, which ISS-295's non-empty reproductions never exercised.)
5. `frontend/src/app/admin/page.tsx` has no local `ErrorBoundary` (confirmed — no such import in
   this file) and does not render through `DashboardLayout` (confirmed — no `DashboardLayout`
   import either; `AdminPage` is a standalone route component, `:118`). The nearest ancestor
   error boundary is the App Router's root `frontend/src/app/error.tsx`, which wraps the entire
   route segment tree, not an individual list row. A throw during the `filtered.map` render is
   therefore caught there, and its generic fallback replaces **the whole `/admin` page** — not
   just the one bad row.

## Why the root cause implies this

ISS-295's finding is "no email-format validation, client or server" — worded around the reported
repro (`not-an-email`, `bademail2`, `bademail3`: non-empty strings with no `@`). But the backend
gap it identifies (`CreateUserRequest.email: str`, no constraint) does not distinguish "no `@`"
from "zero characters" — both are simply strings that satisfy `str`. The client's presence check
(`!newEmail`) is the ONLY thing currently stopping an empty value, and it is explicitly a
**client-side** gate of exactly the kind ISS-295 says must not be trusted alone. Once the
boundary case (empty string) is pushed past that gate via a direct API call, it lands on a
downstream consumer (`page.tsx:391`) that assumes `email` is always non-empty — an assumption
that was previously always true (every legitimately-created account had gone through
Cognito/register, which do use `EmailStr`/real emails) and is only falsified by this same
validation gap.

## Expected vs actual (once reproduced)

- **Expected:** `POST /api/admin/users` with `email: ""` is rejected (422/400) before any row is
  written — the same expectation ISS-295 states for a non-empty malformed email.
- **Actual (predicted):** the row persists, and the very next `/admin` page load (by any admin,
  not just the one who made the request) crashes to the root `error.tsx` fallback instead of
  showing the user table — a strictly worse outcome than ISS-295's "permanently orphaned but
  harmless row," since it also removes the admin's ability to manage users from the UI until the
  bad row is deleted out-of-band (direct API call).

## What would settle this

1. `POST /api/admin/users` with `{"email": "", "password": "zzhuntpass123"}` and a valid admin
   bearer token — confirm it returns 2xx and a persisted row (or already 4xxs, which would refute
   this).
2. If persisted: reload `/admin` in a real browser and confirm whether the table renders (refutes
   the crash claim) or the page falls back to the `error.tsx` screen (confirms it).
3. Cleanup: delete the row via a direct `DELETE /api/admin/users/{id}` call if the UI cannot
   reach it.
