## Bug report

[QA-SG-007](../../BUGS.md#qa-sg-007) — "Changing workflow from notification tab sometimes fails to redirect to the selected workflow."

## Reproduction (validated 2026-09-22, browser lane3, qa-admin@flowinqa.com)

1. Start two parallel workflow runs (a `user_stories` run and a `prototype` run) so both are live
   at once — one landed on `waiting_for_user`, one `generating`.
2. Full page **reload** to `/dashboard` (not a client-side nav) — this is the condition that
   matters; the bug did not reproduce on an in-app client-side navigation to `/dashboard`.
3. Immediately click the bell ("Notifications" button in `AppHeader.tsx`).

**Cycle 1 (SPA nav, not reload):** panel populated correctly both times, clicks redirected to
`/runs/<id>` correctly. Pass.

**Cycle 2 (full reload):** panel opened to "No notifications yet" / "Pipeline completions will
appear here" — the true empty state — even though the same page's own "Jump back in" section, one
paint away, listed both runs as `waiting_for_user` (7m ago) and `generating` (7m ago). Screenshot:
`evidence/qa-sg-007/02-attempt2-notif-panel-empty-despite-active-runs.png`. Closing the bell and
immediately reopening it (no other action, ~1-2s later) showed both entries correctly and the
click redirected to the right `/runs/<id>/stream`.

**Cycle 3 (full reload):** panel populated correctly on first open; click redirected correctly.
Pass.

Result: 1/3 cold attempts reproduced the empty-panel symptom; the other 2 passed because
`recentRuns` had already resolved by the time the bell was clicked (attempt timing, not a fixed
trigger every reload). This is the same symptom family the reporter described ("no navigation
occurs... same workflow entry may work on a subsequent click") — when the panel is empty there is
nothing to click, which reads to the user as "clicking on my workflow does nothing."

## Mechanism (root cause)

All in `frontend/src/components/layout/AppHeader.tsx`:

- `:186` — `const hasServerData = recentRuns.length > 0;`
- `:187` — `const liveRuns = hasServerData ? liveRunsFromServer : null;`
- `:192-221` — comment explicitly names the race: "Falls back to the notification-based list only
  when recentRuns is not yet available (e.g. initial render before the page.tsx fetch completes)"
  — the fallback is `runningFromNotifs`, derived from the `notifications` prop (the `useNotifications`
  hook's in-memory/SSE-driven list).
- `:222` — `const runningPipelines = runningDropdownOpen ? runningDropdownSnapshot : liveRunningPipelines;`
  (the "N Running" badge's own open/close snapshot state; not implicated here since that dropdown
  was never opened during repro — `runningDropdownOpen` stayed `false`, so `runningPipelines ===
  liveRunningPipelines` throughout).
- `:482` — `<NotificationPanel ... liveRuns={runningPipelines} ... />` — the SAME derived value
  feeds the actual bell/`NotificationPanel.tsx` dropdown.

On a full page reload with pipelines that were started in a *previous* page load:
- `recentRuns` starts empty in the new mount and only becomes non-empty once `page.tsx`'s own
  fetch resolves (not instant).
- The `useNotifications` fallback (`runningFromNotifs`) is ALSO empty on a fresh mount for those
  same runs, because it only accumulates events received over SSE **since this mount** — it never
  replays `pipeline_start` for background runs that were already in flight before the reload.

So both the primary source and the documented fallback are empty for exactly the window between
mount and the `recentRuns` fetch resolving. Any bell click that lands in that window renders the
panel's genuine empty state. The panel is not stale/cached (closing and reopening fixes it) — it
correctly reflects `runningPipelines` at each render, but `runningPipelines` itself is wrong for
one render as no fallback covers "background run from before this mount."

## Expected

The bell should show currently-active pipelines as soon as they exist server-side, independent of
whether the client happens to reload mid-run — the "Jump back in" section on the very same page
gets this right on the very same render.

## Files

- `frontend/src/components/layout/AppHeader.tsx:186-222,482` — the empty-fallback race described above.
- `frontend/src/components/ui/NotificationPanel.tsx` — consumer; renders "No notifications yet" whenever both `notifications` and `liveRuns` are empty, with no loading state to distinguish "genuinely empty" from "still hydrating".

## Analysis (2026-09-22, 3-analyzer) — confirmed, blast radius, fix location

Every line cited above re-read fresh, plus the surrounding code. Two refinements and a full
blast-radius sweep, not a correction — the mechanism above holds.

### Refinement 1 — the fallback is not slow, it is structurally dead for this scenario

`useNotifications`'s `loadFromStorage()` (`frontend/src/hooks/useNotifications.ts:27-54`)
explicitly drops "running"/"gate" entries at hydration: `.filter((n) => n.status !== "running" &&
n.status !== "gate")` (`useNotifications.ts:44`) — FIX-204's deliberate anti-stale-spinner design
(its own comment, `:37-43`). Nothing re-adds a "running" entry for an already-in-flight
backgrounded run after a reload: `addRunningNotification` (the only function that can) fires from
a `pipeline_start` frame, and [ISS-679](20260917-1522-ISS-679.md) point 6 already proved SSE
resume is sequence-based (`RunConnectionProvider.tsx:210-216`, `afterSeq: readCursor(runId)`), so
`pipeline_start` is never redelivered for a run whose stream had already passed that sequence
before the reload. So `runningFromNotifs` (`AppHeader.tsx:181-183`) does not merely lag — it stays
`[]` for that run indefinitely. What actually ends the empty state in cycle 2 is `recentRuns`
resolving and `hasServerData` flipping true (`:186-187`), which bypasses the fallback branch
entirely (`:194` ternary) — the fallback never contributes a correct answer here; the primary
source simply arrives and wins.

### Refinement 2 — why "Jump back in" (same page, same paint) is unaffected

`HomeLaunchGrid.tsx:156-160` seeds its `recents` state with a three-way lazy initializer, checked
in this order: `recentRunsProp` (the same `page.tsx` `recentRuns`, also empty at this point) →
`reduxRecentRuns` (`state.global.recentRuns`) → `readCache<WorkflowRun>(recentsCacheKey())`
(`:159`) — a synchronous `localStorage`-backed read of the last-known list, written by
`writeCache` on every previous successful fetch (`:70`, `:174`, `:184`). Unlike `AppHeader`'s
`recentRuns`/`useNotifications` sources, this cache read happens synchronously at mount, before
first paint — it already holds pre-reload data the instant the component renders, because it is
reading a value written to disk before the reload happened, not racing a fresh fetch.
`readCache`/`writeCache`/`recentsCacheKey` (`:49-70`) are private to this file, not a shared
utility — extracting them so `AppHeader` could seed the same way is one alternative fix shape, not
taken below since the loading-state fix is smaller and does not touch this already-working file.

### Blast radius (grepped, not just the reported path)

`runningPipelines` (`AppHeader.tsx:222`) is read by exactly three render sites in one file — all
three race identically, all three share one fix:

- `AppHeader.tsx:304` — `{runningPipelines.length === 1 && (` — the single-pipeline badge.
- `AppHeader.tsx:349` — `{runningPipelines.length > 1 && (` — the "N Running" dropdown.
- `AppHeader.tsx:482` — `NotificationPanel`'s `liveRuns` prop (this card's reported path).

New sibling filed for the first two: [ISS-771](20260922-1507-ISS-771.md) — during the race window
they render NOTHING (not a wrong count — that is [ISS-680](20260917-1555-ISS-680.md)'s different
time window, after the badge is already showing), a more silent failure than the panel's at least
visible "No notifications yet".

`useNotifications()`, `<AppHeader`, and `<NotificationPanel` are each instantiated exactly ONCE in
the whole app (`DashboardLayout.tsx:671`, `:2710`; `AppHeader.tsx:474` — grepped:
`grep -rn "useNotifications(\|<AppHeader\|NotificationPanel" frontend/src --include="*.tsx" --include="*.ts"`),
so there is no second mounted copy of this header to also check. Two other `recentRuns`-driven
surfaces were checked directly and ruled out:

- `frontend/src/components/sidebar/Sidebar.tsx:182` has the identical `recentRuns.length === 0`
  empty-state pattern, but the component has zero importers anywhere under `frontend/src`
  (`grep -rln "sidebar/Sidebar"` returns nothing) — dead code, unreachable by a user.
- `WorkflowHistory.tsx` (the History page) receives `recentRuns` only as a change-signal to
  re-fetch; it loads its own run list independently on mount (`page.tsx:1757-1762`, comment read
  directly) — not driven by the same race.

### Fix — where it belongs

All three affected sites read one derivation, `AppHeader.tsx:171-222`. The fix belongs there once,
not in each branch: thread a `recentRunsLoaded`-style boolean down from `page.tsx` (the only place
that knows the initial `getWorkflows` fetch, `page.tsx:980-986`, is still in flight —
`AppHeader`/`NotificationPanel` cannot tell "not fetched yet" from "confirmed zero" from
`recentRuns=[]` alone) through `DashboardLayout` into `AppHeader`, and use it at `:186-187`
(`hasServerData`) to suppress the confident-empty render (badge, dropdown, and panel alike) until
`recentRunsLoaded` is true. Frontend-only, additive prop — no SC-001/INV-1 surface, no API
contract change; an implementation choice for engineering, not a product decision.

Making the `useNotifications` fallback itself correct (independent of `recentRuns`) is a larger
change already owned by [ISS-680](20260917-1555-ISS-680.md) (open, deferred) — out of scope here;
the loading-state fix above is independently sufficient for this symptom regardless of whether
ISS-680 is ever picked up.
