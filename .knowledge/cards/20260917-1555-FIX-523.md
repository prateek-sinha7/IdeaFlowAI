## What was wrong

This is register bug **QA-PS-002**: with pipelines running, the bell's notification panel, the
header's single-run badge and its "N Running" dropdown showed "0 of N agents" and 0% for every run
that was not on screen. [FIX-521](20260917-1447-FIX-521.md) made the page re-render when a
background run's count moves. The 6-verifier still saw "0 of 6" live, because after a navigation
the count never moved at all. [ISS-679](20260917-1522-ISS-679.md) is the confirmed root cause and
[ISS-658](20260917-1302-ISS-658.md)'s test reproduces it. [ISS-674](20260917-1420-ISS-674.md) is
the header half, which reads the same array.

The rest of this bug's card set is unchanged by this fix:

- [ISS-644](20260917-0930-ISS-644.md) stays superseded. `DashboardLayout.iss644.test.tsx` still
  reports "1 expected fail"; it asserts a field the panel never draws and should be retired.
- [ISS-648](20260917-1100-ISS-648.md) and [ISS-649](20260917-1105-ISS-649.md) were resolved by
  FIX-521 and their tests are still green.

## Root cause (pre-fix line numbers)

1. `runStore = useRunStateStore()` is called in the page component (`page.tsx:2170`). The store's
   maps were `useRef(new Map())` (`useRunStateStore.ts:274, 278`), so each page.tsx mount had its
   own.
2. Every `router.push` under the `[...view]` catch-all remounts page.tsx
   (`page.tsx:3269-3273`, "confirmed live"). That includes launching another run, the Home
   button, and opening a run. The new mount started with an empty map.
3. Only `pipeline_start` builds a run's roster (`useWorkflow.ts:403-563`). A background run's
   `pipeline_start` reached the old map, so its entry in the new map had `agents: []`.
4. `agent_complete` returns `prev` for an agent it cannot find (`useWorkflow.ts:705-706`), so
   `completedCount` stayed 0. `runAgentsCompletedMap` (`page.tsx:3912-3918`) then fed 0 to
   `AppHeader.tsx:204`.

## What changed, and why there (post-fix lines, `useRunStateStore.ts`)

The fix is ISS-679's recommended one: the store now lives above the router. All three screens read
the store through page.tsx, so this one file is the shared point.

- **Module-scope maps (`:263-264, 299, 303`).** `runStates` and `agentStartTimesByRun` are module
  constants, and the hook's two refs point at them. The rest of the store is unchanged, including
  FIX-521's tick (`:549`), which now has a roster to count against. A module-scope map was chosen
  over a context provider:
  - it has the same lifetime as a provider in `app/layout.tsx`: it survives client navigation and
    is empty after a reload;
  - it needs no layout change;
  - ISS-658's test renders the hook without a provider.

Making the maps outlive the page changed three assumptions the rest of the code relied on. Each
one got a guard, and each guard has its own test case that fails without it.

- **Only running runs cross an unmount (`:318-331`).** The effect's cleanup deletes every entry
  whose `pipelineState.isRunning` is false.
  - Why: page.tsx rebuilds a reopened run by replaying its whole durable log (T7/T11,
    `page.tsx:2879, 3420`). Replayed into an entry that already holds a finished run,
    `pipeline_start` resets `agentStartEventIds` (because `prev.isRunning` is false,
    `useWorkflow.ts:557`) but keeps the seq cursor (`:563`). `isRedelivery` (`:279`) then skips
    every replayed `agent_start`, so the spec-revision banner (ISS-063) reads 0.
  - Observed on the unguarded store: a second replay into a finished entry gave count 0 against
    1 on the first.
  - Running entries are safe to replay into: a second replay of a live run gave identical
    statuses, outputs, count and revision count.
  - This also bounds memory to runs still in flight.
- **An unmounted page's writes go nowhere (`:306, 309, 319, 381, 389`).**
  - The path: a reopen click runs `onSelectWorkflowRun` in the current page, then `router.push`
    (`DashboardLayout.tsx:2691, 2745, 2839, 2899`). That `handleSelectWorkflowRun` is still
    awaiting its fetch when the page unmounts. The new page replays the same run through T7/T11.
  - Before this fix, the old page's late replay wrote into a map nobody read. Now
    `getOrCreate`/`getAgentStartTimes` return throwaway objects once `mountedRef` is false, which
    keeps that behaviour.
  - Without this guard, the old page's replay lands first and the new page's replay zeroes the
    revision count, which is the same mechanism as the previous guard.
- **The maps belong to one user (`:266-277, 310-317`).** On mount, if the JWT `sub` differs from
  the one the maps were claimed under, they are cleared.
  - Why: logout and login are both client-side navigations (`page.tsx:3231`,
    `login/page.tsx:56,68`), and RunConnectionProvider keeps the previous focus. So user B pressing
    Back to user A's `/runs/<id>/stream` reaches T11's fast path. That path projects the store entry
    without an ownership check (`page.tsx:3373-3392`).
  - Keyed by `sub`, not the token: the token is refreshed silently (`useRunStream.ts`
    REFRESH_SKEW_MS), and clearing on every refresh would bring this bug back.
  - This is the same identity ISS-188/ISS-201 use for the recents cache
    (`HomeLaunchGrid.tsx:40-58`).

No change to page.tsx, AppHeader, DashboardLayout or the reducer.

## Invariants

- Frontend only. SC-001/INV-1 hold: there is no workflow-name branch. The guards key on run ids,
  `isRunning` and the JWT `sub`.
- import-linter does not apply, and there is no migration.
- No API or data shape changed. `RunStateStoreReturn` is unchanged.

## Not fixed here

- [ISS-680](20260917-1555-ISS-680.md): a **full page reload** still starts the store empty, and
  the SSE resume never re-sends `pipeline_start`. Background runs read "0 of N agents" after a
  reload until they are opened. To verify this fix, navigate client-side: launch a second run, or
  press Home. Do not reload.
- [ISS-681](20260917-1555-ISS-681.md): the reducer's re-announce drops a finished run's revision
  count when it is replayed twice in one page mount. This fix only guards the cross-remount case.
- [ISS-675](20260917-1447-ISS-675.md) (runs launched in another tab) is unchanged.
