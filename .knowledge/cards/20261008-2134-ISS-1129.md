# ISS-1129

**Register source:** sibling derived during the `QA-KB-103` analysis on 2026-10-08 (root [ISS-1118](20261008-1444-ISS-1118.md)). Not its own bug row.

**Confidence:** INFERRED. Both call sites were read; neither door was driven (`POST /api/runs` mints a run, and the trigger needs a conditional
gate to fire). It is not a live defect for new saves today: after [FIX-766](20261008-1444-FIX-766.md) no writer stores an engineer-only reference
(`analysis-04`: the dev DB holds 0 override rows). It becomes one the moment the fix for [ISS-1118](20261008-1444-ISS-1118.md) lets a writer store an
inherited reference, and it is already one for any row saved before FIX-766 in a database other than the dev one. What would settle it: a test that
stores a `prototype` override carrying the inherited `compaction` (after the ISS-1118 fix), then runs `launch_run` with that row's
`user_workflow_id` and the trigger compile on the same row, and asserts neither answers `invalid_workflow_manifest` / raises `CompilerError`
(harness: `backend/tests/integration/api/test_iss1113_override_row_launch_trust.py`).

## Condition

[FIX-766](20261008-1444-FIX-766.md) records a locked constraint: "Every reader and writer of an override row checks its steps through
agents.execution_engine.overrides.compile_override_steps." Reading the code, two readers do not:

- **Case 3**, `run_commands.py:3367-3369`: `_trust = "user" if _inline or user_workflow_row.overrides_pipeline_type else "db"`; the whole row
  manifest (with the deliverable, planner, clarify and capabilities synthesized around it) is then compiled at `:3403-3407`:
  `_WORKFLOW_COMPILER.compile(parsed_manifest, _CAPABILITY_REGISTRY, trust=_trust)`.
- **The conditional-route trigger**, `kernel_services.py:1616`: `row_trust = "user" if row.overrides_pipeline_type else "db"`, compiled at
  `:1643-1645` with the same call. The lines read (`:1626-1645`) have no local handler for `CompilerError`; what catches it above was not traced.

The consumers that DO go through the shared function are the merge (`overrides.py:113`, behind `workflows.py:322` and `run_commands.py:3645`) and
the four writers (`user_workflows.py:235`, `:1140`). So there are two decisions about the same steps, not one.

## Expected vs actual

Expected: whatever the writers accept, the merge applies and the launch-by-id and trigger doors compile. Actual, once the shared function learns to
admit a reference the built-in's own step declares: writers 201, merge applies, Case 3 answers 422 `invalid_workflow_manifest` and the trigger
compile refuses the same row, because both still hold every reference to `user_allowed` with no baseline.

## Why the root cause implies it

The root cause of [ISS-1118](20261008-1444-ISS-1118.md) is a `trust="user"` compile with no baseline for what the built-in itself declares. These two
doors are further callers with the same flaw, and they are the ones a fix confined to `compile_override_steps` would not reach.
[ISS-1113](20261008-1415-ISS-1113.md) put them at `user` precisely so they would agree with the merge; they stop agreeing the day the merge relaxes.

## Fix direction (INFERRED, not applied)

One decision, three entrances. Route both doors through the same baseline-aware decision (for example by having the shared function also compile
the row manifest, or by exposing the admitted set of inherited references to these two `compile(...)` calls), and keep the SC-001 constraint:
`row.overrides_pipeline_type` is a truthiness test on a column, which the INV-1 ratchet already accepts; a workflow-name comparison would not be.
Case 3 persists `_trust` on the run for resume (`run_commands.py:3418-3419`), so the resume recompile must see the same decision.

## Test notes

Integration, offline, same harness as `test_iss1113_override_row_launch_trust.py`. Red today only after the ISS-1118 change; until then pin the
current agreement so a later change cannot split the doors: one row, three compiles (merge, Case 3, trigger), one verdict.

## Fix (QA-KB-103, 2026-10-09, fixer)

Resolved by [FIX-769](20261009-0059-FIX-769.md), as item 3 of [ISS-1118](20261008-1444-ISS-1118.md)'s proposed fix: Case 3 and the
trigger now compile through `overrides.compile_with_baseline` with the row's `overrides_pipeline_type` (`None` for an inline
manifest), Case 3 persists `_overrides` beside `_trust`, and `resume_run` / `_replay_clarify_run` pop it and pass it, so the resume
recompile makes the launch's decision. Verified by a scripted probe, not a committed test (`verification.type: manual`):
`evidence/qa-kb-103/fix-02-doors-case3-trigger-resume-inline.txt` — an unchanged `prototype` override row reaches the mint through
`POST /api/runs` (200) and the trigger with `prototype-build` `compaction: html_skeleton`, a row with an ADDED reference is
refused at both, the persisted manifest recompiles, and an inline manifest still answers 422. The pin this card's Test notes ask
for (merge, Case 3 and trigger give one verdict on one row) is still worth committing as a test.
