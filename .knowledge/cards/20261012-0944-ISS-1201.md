# ISS-1201

**Register source:** sibling derived during the `QA-KB-121` analysis on 2026-10-12 (root [ISS-1199](20261012-0944-ISS-1199.md)). Not its own bug row.

**Confidence.** The mechanism is CONFIRMED by source read. The effect is INFERRED: no chat turn was sent. A SELECT over `run_events` (2026-10-12) found 0 persisted `chat_reply`
rows containing "the model call failed", so the branch has not fired in this database. What would settle it: send one message in a run's chat lane while the provider rejects the key.

## Condition

A user types in a run's chat lane (`POST /api/runs/{run_id}/messages`, `post_message`, `run_commands.py:1806`; it calls `concierge.converse(ctx, body.text, on_chunk=_on_chunk)` at `:2277`) and
the provider rejects the key. The concierge builds its own `DeepAgentRunner` (`concierge.py:624-630`), which swallows a non-throttle fault into `{"type": "error", "error": str(exc)}`
(`deep_agent_runner.py:1415-1416`).

## What happens (CONFIRMED by read)

The concierge's stream loop keeps the runner's string: `stream_error = str(event.get("error") or "").strip()` (`concierge.py:662-664`). When the model produced no text it answers with
`"I could not answer that — the model call failed:\n\n" + stream_error[:500]` (`concierge.py:683-689`). That text is returned as the reply, persisted as a durable `chat_reply` event
(`run_commands.py:2285-2294`, `"text": answer_text or ""`) and shown in the chat lane.

For the rejected key the reply is the botocore dump from the root card's probe case A: `An error occurred (AccessDeniedException) when calling the ConverseStream operation: API Key invalid`.
It is not classified, does not say the key must be rotated, and is not the sentence the run itself shows for the same fault.

## Expected vs actual

Expected: the chat reply carries the same classified, secret-free message as the run's failed step (the one [ISS-1199](20261012-0944-ISS-1199.md) improves). Actual: the unclassified
`str(exc)` of the provider, cut at 500 characters.

## Why the root cause implies it

Same swallow-to-string gap, second consumer. `_sanitize_agent_error` exists precisely because the runner's `str(exc)` "can carry ARNs / region / model-id / internal config" (the WR-02 comment
at `engine.py:415-421`), and the engine is the only caller of it. The concierge is the other consumer of the runner's `error` event and does not go through it, so (1) the improved message
will not reach the chat lane, and (2) any non-auth fault (a `ValidationException` or a model-not-found that quotes an inference-profile ARN) is shown to the user verbatim: the leak class the
sanitizer was written to close.

## Fix direction (INFERRED, not applied)

Run `stream_error` through the same classifier before composing the reply. The concierge is app-side and the engine is kernel-side: app may import the kernel, the kernel must not import `app.*`.
Importing `_sanitize_agent_error` from `engine.py` into `concierge.py` pulls the whole engine module; cleaner is to move the pure function and its table to a leaf module that both import
(`backend/agents/model_policy.py` is already imported by the runner and is a kernel-side leaf) and keep a re-export in `engine.py` so the existing test imports
(`from agents.execution_engine.engine import _sanitize_agent_error`) keep working.

Trap: the concierge must still answer when the model produced partial text and then failed (today the error is dropped when `answer` is non-empty, `concierge.py:683`); keep that behavior unless
the owner wants the failure appended.

## Test notes

Offline: drive `ConciergeCapability.converse` with a `ctx.model` that is a scripted model raising a `ClientError(AccessDeniedException)` (the offline seam its comment names at
`concierge.py:612-614`) and assert the returned text does not contain `An error occurred (` and does not contain an ARN-shaped string. Today it contains the botocore text.
