## What was wrong

`/library/skills/<id>` rendered the plain Library catalog listing under the
correct detail URL — no console error, no failed request, no `notFound()` — for
several seconds after the page was already interactive. Reported as "the detail
route falls back to the listing for EVERY skill id".

## Root cause

`frontend/src/store/listenerMiddleware.ts:49` (pre-change) —
`await Promise.all(preloadHome)`.

The `signedIn` preload ran in two *sequential* waves: workflows + recent runs
first ("both feed HomeLaunchGrid's first paint"), then agents + skills + hooks
("opened later, so they follow after"). A cold or deep-linked
`/library/{type}/{slug}` falsifies "opened later": it needs the catalog
immediately.

`LibraryPage.tsx:518-543`'s URL-seed effect can only open the detail modal once
its catalog reports `"succeeded"`, so the modal stayed shut for exactly as long
as the home wave took. The effect itself was never broken — the card's own
root-cause pointer (an unmemoized `useSkillsCatalog` array producing a permanent
`SKILLS.find` miss) is NOT what happens; the modal opens in the same 250 ms
sample tick that the skills counts appear.

Measured on a cold `page.goto("/library/skills/html-deck-to-pptx")`, request
timeline relative to navigation start:

```
2.08s  REQ  /api/workflows        (x2 — two concurrent callers)
2.09s  REQ  /api/runs?limit=6
3.44s  RES  /api/workflows        #1
14.25s RES  /api/workflows        #2   <-- the gate
14.26s REQ  /api/skills/library        <-- only now dispatched
14.32s RES  /api/skills/library
       dialog appears
```

The in-app card-click path was never affected (dialog present in the same tick
as the click), which is why the defect looked id-specific and intermittent: it
is purely a function of how long the home wave takes on that load.

## What changed and why there

One file, `frontend/src/store/listenerMiddleware.ts`: the intermediate
`await Promise.all(preloadHome)` is gone and the effect ends on
`await Promise.all([...preloadHome, ...preloadLibrary])`. All five thunks are
dispatched in the same synchronous pass.

This is the one place every cold Library entry routes through — the agents,
skills and hooks detail routes, and every consumer of the three catalogs — so
one guard here beats a per-catalog workaround in `LibraryPage`. Both status
guards read the same `state` snapshot captured before the first `await`, so
dropping the intermediate await changes concurrency only, not which thunks fire.
The home pair still resolves no later than it did before.

Same request timeline after the change:

```
3.65s  REQ  /api/workflows, /api/runs, /api/agents/library,
            /api/skills/library, /api/hooks/library   (all together)
3.72s  RES  /api/skills/library
4.06s  dialog present
```

## Not fixed here (deferred, still open)

- `/api/workflows` and `/api/runs?limit=50` are each requested TWICE on one
  cold load, and the second `/api/workflows` took 12.2s while the first took
  1.35s. Parallelising the preload takes that off the Library's critical path
  but does not explain or fix it. Backend/duplicate-caller concern, outside this
  card's globs.
- [ISS-336](20260828-1846-ISS-336.md) (Hooks tab, same effect) is expected to be
  cured by this change for the same reason — `fetchHooks` was in the same
  blocked wave — but it was not re-tested here and its own status is unchanged.
