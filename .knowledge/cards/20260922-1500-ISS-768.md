# ISS-768

Register entry: **QA-SG-013** (`BUGS.md`) — "Download button is disabled on user story run
detail page, cannot download deliverable".

## Reproduction (3/3, cycle 1 every time)

Cold-navigated directly to three different **completed**, base (non-revision) `user_stories`
runs as `qa-admin@flowinqa.com`, no version pinned (plain `/runs/{id}`, latest/v1):

- `8ff57cca-3064-4a4a-8031-6576c785aee1`
- `a1a8c82a-8333-4fe8-8ea6-9d29ccfd01bc`
- `a7279a95-8af1-4b5d-b1d1-04c8625a9c89`

All three: header `Download the deliverable` button rendered `disabled` on first paint,
no interaction needed to trigger it. Evidence:
`evidence/qa-sg-013/01-validate-attempt1-download-disabled.png`,
`evidence/qa-sg-013/02-validate-attempt2-download-disabled.png`,
`evidence/qa-sg-013/03-validate-attempt3-download-disabled.png`.

## Trigger

**Every completed base `user_stories` run**, unconditionally — not a timing, tier, theme,
or version-pinning issue. Confirmed via `GET /api/runs/{id}` (all 3): `status: "completed"`,
`deliverable_filename: "user_stories.md"` — populated, not null (rules out ISS-313's
mechanism). Confirmed via `GET /api/runs/{id}/sandbox` (all 3): the file listing never
contains a path `"user_stories.md"` — it only ever contains `".chain/user_stories.md"`.

## Root cause

`backend/agents/workflows/user_stories/workflow.yaml:29-31` declares
`deliverable: {strategy: streamed_text, name: user_stories.md}`. In
`backend/agents/execution_engine/engine.py`, `build_flat_payload`'s `streamed_text` branch
(`elif _streamed_text is not None:`, materialization at line ~1459-1464) writes the declared
basename only into the `.chain/` staging dir (`_staging_abs / _output_basename`) — never to
`sandbox.root / _output_basename`. This is BY DESIGN for chaining (the workflow.yaml comment
at line 32 notes `streamed_text` is what makes the run "chainable" downstream via
`context_providers: [chain_context]`), but it means no agent in the 6-step `user_stories`
pipeline ever writes a `user_stories.md` file at sandbox root.

On the frontend, `resolveRunDeliverable` (`frontend/src/lib/api.ts:1183-1199`) resolves the
`declared` name (`"user_stories.md"`, ext `md` — not `html`/`pptx`, so only one candidate) via
`listing.files.find((f) => f.path === c)` — an **exact path match against the declared
basename**. Since the sandbox listing only ever has `.chain/user_stories.md`, this never
matches; `resolveRunDeliverable` returns `null`; `deliverableFile` in
`PreviewPanel.tsx:1288-1361` (effect body, `hit` at line 1352-1354) stays `null`;
`canHeaderDownload` (`PreviewPanel.tsx:1384`: `!!deliverableFile || deliverableBundle`) is
`false` (the ISS-313 bundle fallback at line 1344-1349 only fires when `declared` itself is
falsy, which it is not here) — so the Download button is disabled on every run of this type,
permanently, regardless of run outcome.

This confirms, for the BASE `user_stories` workflow, the mechanism
[ISS-726](20260922-1248-ISS-726.md) left as INFERRED/unconfirmed for the sibling
`user_stories_revision` workflow (same `streamed_text`/`.chain/`-only materialization; ISS-726
explicitly notes "The BASE `user_stories` pipeline's own deliverable strategy is ALSO
`streamed_text` (unverified...)" — this card is that verification, and the answer is the
QA-PS-029 shape (permanently absent from sandbox root), not the "frozen at an earlier version"
shape ISS-726/723/727 describe for revisions.

## Fix direction

Either (a) give one `user_stories` agent (e.g. `backlog-compiler`, the final step) an actual
`write_file` of the compiled backlog to sandbox root instead of streaming it, matching how
`ppt`/`ppt_revision`'s `FIX-601` gave `ppt-revision-agent` a real edit instruction; or (b) make
`resolveRunDeliverable`/`build_flat_payload` aware that a `streamed_text`-strategy deliverable's
canonical location is `.chain/<name>`, not sandbox root, and read from there. (a) is consistent
with the fix direction already chosen for the `ppt_revision` sibling defect family
(`FIX-601`); (b) is a narrower, single-file frontend/engine change. Not applied here —
read-only validation only.
