## AgentsPopup's own footer Save button always created a new row on a reopened saved workflow

**Symptom, reproduced live:** from "My Workflows," opened the saved "Prototype-UPDATED"
workflow (Run), opened the Agents/canvas popup, changed a per-agent model, and clicked
that popup's own "Save workflow" button, intending to update the existing row so the
same workflow could be re-run with the change. It asked for a name every time instead,
creating a new row rather than updating in place.

**Root cause:** `AgentsPopup.tsx`'s footer "Save workflow" button (line ~2314-2343,
distinct from `LaunchWizard.tsx`'s own separate page-level Save button, which was NOT
the button in this report) unconditionally opened `NameWorkflowModal` and its
`handleSaveWorkflow` called `createUserWorkflow` directly — no per-agent-popup concept
of "this workflow already has an id." Two supporting gaps fed it:

1. `DashboardLayout.tsx`'s `handleLaunchSaved` special-cases `prototype`/`ppt`
   saved workflows: instead of the normal `savedComposition` state (which the Canvas
   uses and which does carry `.id`), it stashes a plain object into
   `sessionStorage["prototype.draft"]`/`["ppt.draft"]` and navigates to the wizard
   route fresh. That draft never included `id`/`name`/`description`, so nothing
   downstream had the reopened row's identity to work with.
2. Even with the identity available, `AgentsPopup` had no prop to receive it — its
   own save handler had no way to know it wasn't creating fresh.

**Fix:** [FIX-266](20260819-1726-FIX-266.md) gives `AgentsPopup.tsx`'s own footer button the identity it was
missing and routes it through the shared `saveUserWorkflow` dispatch.
