## What is broken

Selecting a version from the RunHeader `VersionMenu` dropdown (e.g. choosing "v1"
while on "v2") re-reads the Workspace at that git tag but keeps the Steps tab,
agent list, agent-output cards, and `AuditTab` fetches on the **latest/live run**.
The reading a user takes — "these steps produced these files" — is false.

The URL path still works correctly: cold-navigating to `/runs/{id}/versions/1`
goes through `pinnedMemberId` → `useEffect` → `getWorkflow` → `versionViewFrom` →
`setViewingVersion` (PreviewPanel.tsx:816-831). The menu regression sits ~300 lines
below that correct path.

This is a regression of ISS-606/608/609 (fixed by FIX-411), introduced by
Task 11.6 (`feat/git-versioning`). FIX-411 fixed the URL pin path; task 11.6
then re-wired the *menu* to the sandbox ref alone, reintroducing the exact defect
on the menu path.

## Root cause — CONFIRMED

`frontend/src/components/preview/PreviewPanel.tsx:785`:

```typescript
const handleVersionMenuSelect = useCallback((tag: string | null) => {
  setSandboxSelectedRef(tag);   // ← only this
}, []);
```

`setSandboxSelectedRef` updates only the git ref for the Workspace/Preview
ref-view. It never touches `viewingVersion`, so `effAgents`, `effPipelineState`,
and `effAgentOutputs` (the ISS-606 pipeline-data counterparts, lines 869-871)
keep falling back to the raw `agents`/`pipelineState`/`agentOutputs` props
passed from DashboardLayout — always the live/root run.

`handleSelectVersion` (PreviewPanel.tsx:762-776) IS the correct chokepoint: it
calls `getWorkflow(token, memberId)`, then `setViewingVersion(versionViewFrom(run))`,
and calls `onTabSelect` with the version ordinal to push the URL. The menu handler
must resolve the tag → member id and route through this same chokepoint.

`git_tag` is already on the family member row
(`frontend/src/types/index.ts:455`, `backend/app/api/runs.py:1688`), so
tag → member is a direct lookup on `sortedMembers` — no ordinal arithmetic needed.
`sortedMembers[N-1]` is a safe fallback for pre-versioning runs where `git_tag`
is null.

A third site has the same shape: `RefVersionPreview`'s "Back to latest" button
(PreviewPanel.tsx:1531) calls `setSandboxSelectedRef(null)` directly rather than
`handleBackToLatest`, leaving any member pin untouched if the user was previously
on a pinned URL version.

## Fix plan

Two hunks in `PreviewPanel.tsx`:

**Hunk 1 — `handleVersionMenuSelect`**: resolve the tag to its member id using
`runFamily.members` (already on props, available as `sortedMembers`), then call
the existing `handleSelectVersion(memberId)` chokepoint. This gives the menu
path the same fetch → `versionViewFrom` → `setViewingVersion` → URL-push sequence
the URL-pin effect already performs. When `tag` is `null` (Latest), call
`handleBackToLatest()` as before.

```typescript
const handleVersionMenuSelect = useCallback((tag: string | null) => {
  if (!tag) {
    setSandboxSelectedRef(null);
    void handleBackToLatest();
    return;
  }
  setSandboxSelectedRef(tag);
  const member = sortedMembers.find((m) => m.git_tag === tag)
    ?? sortedMembers[Number(tag.replace('v', '')) - 1];
  if (member) void handleSelectVersion(member.id);
}, [sortedMembers, handleSelectVersion, handleBackToLatest]);
```

**Hunk 2 — narrow the `activeRunId` reset effect** (line 742,
`useEffect(() => { setSandboxSelectedRef(null); }, [activeRunId])`): this effect
already fires when a new live run supersedes the view, which is correct. No change
needed here — `handleSelectVersion` sets `viewingVersion` and the effect that clears
it on `liveRunId` change (line 799) handles supersession correctly.

**Tests**: `VersionSwitch.integration.test.tsx` and
`PreviewPanel.sandboxRef.test.tsx` (14 tests) need a `runFamily` fixture whose
members carry `git_tag`, since they mount without one today. Add two new assertions:
(a) selecting a tag via the menu fires `handleSelectVersion` with the resolved
member id (not just `setSandboxSelectedRef`); (b) the Steps tab's `agents` prop
reflects the selected member, not the live run.
