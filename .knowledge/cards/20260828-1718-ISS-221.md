## Summary

On a `diverted` run's detail page (`/runs/{id}`), the primary chat-lane action button reads
"Start a new run". Clicking it invokes `onRelaunch` → `handleResumeRun` in
`frontend/src/components/layout/DashboardLayout.tsx` (line ~2253), which POSTs
`/api/runs/{id}/resume`. The backend correctly rejects this for a diverted run with `409
Conflict` (`{"error":"Run is 'diverted'; only failed, degraded, or cancelled runs are
resumable","code":"run_not_resumable","recoverable":false}`), since a diverted run has already
handed off to a successor run. `handleResumeRun`'s catch block (line ~2302) does the right thing
in principle — `console.error("postResume failed", e)` then `setResumeError("Could not resume
the run — please try again.")` — and `resumeError` is passed down to `RunChatLane` as the
`relaunchError` prop (`DashboardLayout.tsx:3014`). But `relaunchError` is never rendered for
this code path: in `RunChatLane.tsx`, the `relaunchError && (...)` inline-error block (the "KAN-120
BUG-4" amber banner) is hand-duplicated into exactly two of the four `renderComposer` terminal
branches — `pipelineState?.cancelled` (~line 1720) and the failed/"Resume options" branch
(~line 1808) — but is absent from the shared `relaunch(label)` helper itself (defined at
~line 1694) and from the `degraded` branch (`{relaunch("Run again")}`, ~line 1863) and the plain
"Start a new run" branch a diverted run falls into (`return relaunch("Start a new run");`, line
1871). Since a diverted run matches none of `cancelled`/`failed`/`degraded`, it renders via
`relaunch("Start a new run")`, whose JSX is just the button — no `relaunchError` block exists in
that branch to display the amber banner. The 409 is caught, logged to console, and stored in
state, but the state is never rendered on this path: no toast, no inline error, no
disabled/loading-state change, no navigation. The button appears to do nothing.

This is BUG-20260828-020430-runs-diverted from the bug-hunter register.

## Reproduction (3/3, cold start each time)

- **Cycle 1** — cold login (localStorage/sessionStorage cleared) → direct navigate to
  `/runs/940ca699-b21b-4666-8e44-3370a08a4561` ("Ex A4 Human Divert", diverted) → waited ~1.5s for
  the page to settle → clicked "Start a new run". `POST /api/runs/940ca699.../resume` → `409`.
  Console: `Failed to load resource...409` and `postResume failed ApiError: {...run_not_resumable}`.
  Page unchanged before/after (screenshots identical structurally); no error text found anywhere
  in the page snapshot.
- **Cycle 2** — fresh cold navigation to a second, independent seeded diverted run
  `/runs/277bc03a-d2ba-4405-876d-d0aa861bc9ed` → same result: `409`, identical console errors, no
  visible UI change. Confirms this is systemic to the diverted-run page, not one run's data.
- **Cycle 3** — cold navigate back to the first run and click "Start a new run" **immediately**,
  without waiting for the page to settle (timing variation) → same 409, same silent failure. Not a
  timing-dependent race; reproduces on the very first click.

3/3 CONFIRMED. No axis variation was needed — the defect is unconditional on entry path or
timing.

## Root cause

`frontend/src/components/chat/RunChatLane.tsx` — the `relaunch(label)` helper at line 1694 (used
by the `degraded` and plain-terminal/"Start a new run" branches) renders only the `<Button>`;
the `relaunchError` amber-banner block that surfaces `handleResumeRun`'s caught error is
hand-copy-pasted into only the `cancelled` (line 1720) and `failed` (line 1808) branches, not
into the shared helper or the other two branches that also call `onRelaunch`. A diverted run's
terminal state has no `pipelineState?.cancelled`/`?.degraded` marker and isn't the `failed`
branch, so it falls through to `return relaunch("Start a new run");` (line 1871) — the one branch
with no error-rendering wired in at all, even though `DashboardLayout.tsx`'s `handleResumeRun`
already computes and passes the right message via the `relaunchError` prop.

## Expected vs Actual

- **Expected:** "Start a new run" on a diverted run should either genuinely start a new run, or,
  since resuming a diverted run is intentionally rejected by the backend, the 409 should surface
  as a visible inline error (the same amber banner already built for the cancelled/failed paths).
- **Actual:** The 409 is caught and stored in `resumeError`/`relaunchError` but never rendered on
  this path — the button appears to silently do nothing.
