# ISS-644

## Title

Notification panel shows "0 of N agents" / 0% for actively-running pipelines regardless of true progress (QA-PS-002).

## Reproduction (3/3, cycle 1 — reproduced on the first cold-start attempt, confirmed again on 2 further cold-start attempts)

1. Sign in as `qa-admin@flowinqa.com`.
2. Launch a "Generate product requirements" (User Stories) run — 6 agents — via `/create/user-stories`.
3. Answer/skip the clarification gate ("Skip the rest") so the run enters `generating`.
4. Navigate away from the run's own `/runs/<id>/stream` page to `/dashboard` — a fresh, cold navigation each attempt.
5. Open the Notifications panel (bell icon, top nav).
6. Compare the panel's per-run "X of N agents" / "Y%" against the SAME run's own `/runs/<id>` stream page "Pipeline running · X / N" indicator, checked at essentially the same wall-clock moment.

### Conditions

qa-admin tier, light theme (default), any viewport, run state = actively `generating` (not `waiting_for_user`/completed), notification panel is global (route-independent). Every one of 3 cold-start attempts reproduced it — no axis-narrowing was needed.

## Expected

The notification panel's "X of N agents" and percentage track the run's real agent-completion count as it climbs (e.g. 2/6, then 3/6), matching what the run's own `/runs/<id>` stream page shows at the same moment.

## Actual

The panel is frozen at "0 of N agents" / 0% for the entire time the run is actively generating and never increments, even though the SAME run's own stream page correctly shows live, incrementing progress (2/6, then 3/6) queried at the same wall-clock moments:

- Cycle 1: panel shows "0 of 6 agents / 0%" for run `ba2dc857-eeeb-4619-90d7-0236c58aba23` while its own status is `generating`.
- Cycle 2: panel still "0 of 6 agents / 0%"; the run's own `/runs/<id>` stream page independently showed "Pipeline running · 2 / 6" at the same moment.
- Cycle 3: panel still "0 of 6 agents / 0%"; the run's own stream page by then showed "Pipeline running · 3 / 6".

## Root cause (code-read, not yet fix-verified)

`frontend/src/components/layout/DashboardLayout.tsx`, the "Update notification progress as agents complete" effect (~line 937-941):

```ts
useEffect(() => {
  if (pipelineState?.isRunning && currentPipelineNotifId.current) {
    updateProgress(currentPipelineNotifId.current, pipelineState.completedCount);
  }
}, [pipelineState?.completedCount, pipelineState?.isRunning]);
```

`pipelineState` here is `DashboardLayout`'s own locally-mounted stream/SSE state for whichever pipeline view is currently active in THIS component instance — it is not a global/shared progress store. Once the user navigates away from the run's stream view (e.g. to `/dashboard`), this component's `pipelineState.completedCount` stops advancing for that run, so `updateProgress` never fires again. The notification (`frontend/src/components/ui/NotificationPanel.tsx` ~line 134-143, reading `n.agentsCompleted ?? 0` / `n.agentsTotal`) stays pinned at its initialized `0` (`frontend/src/hooks/useNotifications.ts` line 143, `agentsCompleted: 0` at creation) for the lifetime of the run, even though the run keeps progressing server-side and its own dedicated stream page (which re-subscribes independently when visited) shows the correct live count.

## Analysis missed (2026-09-17)

- This card blamed `updateProgress` in `DashboardLayout.tsx:937-941` (updates
  `notification.agentsCompleted`), but `DashboardLayout.tsx:2670` filters that notification out
  before drawing, so the panel never shows it.
- The panel's live "X of N agents" rows actually come from `AppHeader.tsx:200-211` via
  `runAgentsCompletedMap`, which reads 0 when a background run has no store entry
  (`page.tsx:3894-3900`: the map only gets entries for runs whose SSE stream reached this tab).
- Fixing this card's data path (`updateProgress`) would leave the panel showing "0 of N agents"
  unchanged. See [ESCALATIONS.md#qa-ps-002](../../ESCALATIONS.md#qa-ps-002) for the full trace
  and decision options.
