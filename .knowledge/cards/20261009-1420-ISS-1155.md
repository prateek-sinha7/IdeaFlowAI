# ISS-1155

Register entry QA-KB-119 (Medium). Found by the validate-bugs full smoke on :8001; revalidated against :8000.

## Reproduction (validated 3/3, cold start each: fresh login, new request, 2026-10-09)

Signed in as admin@velocity.ai. `GET /api/runs/78e185fb-c032-4154-8552-774781b6e5df/events` with no params, three times:

| Attempt | Status | Bytes | Time |
|---|---|---|---|
| 1 | 200 | 52,909,786 | 5.4 s |
| 2 | 200 | 52,909,786 | 4.7 s |
| 3 | 200 | 52,909,786 | 5.4 s |

The body holds 107,409 events. The reporter saw 13 s under concurrent load; the size is identical, only the time varies.

## Conditions

Any run with a large `run_events` log, any tier, no query params. No timing, theme or entry-path dependence (an API call).

## Cause (read from code)

`backend/app/api/runs.py` `get_run_events` declares only `after: int = 0` and calls `store.read_events(workflow_id, after_seq=after)` with no limit, then serialises every row (payload_json included) into one JSON response. The SSE twin in `run_stream.py` also drains via `read_events(run_id, after_seq=after_seq)` (replay on connect).

## Expected vs actual

Expected: a bounded page (default limit plus a cursor, `after` already exists) or a hard cap. Actual: the whole log in one response, so one call can hold ~53 MB in server memory and on the wire.

## Analysis (QA-KB-119, 2026-10-09)

**Verdict.** Root cause CONFIRMED (source read plus two measurements). The "Cause" section above is right but stops
short of the part that makes this more than a large download: the entire call runs on the event loop, so one bare GET
freezes the whole process. Two siblings filed, both INFERRED: [ISS-1166](20261009-1620-ISS-1166.md) (the SSE twin) and
[ISS-1167](20261009-1620-ISS-1167.md) (what the browser does with the payload). Register severity is Medium; a
whole-process stall reachable by any signed-in user on their own large run arguably deserves more, which is the owner's
call.

### Root cause (CONFIRMED)

One mechanism: the durable-log reader contract is "every row past a cursor, materialised at once", and nothing between
the table and the wire bounds it.

1. **No bound on the endpoint.** `backend/app/api/runs.py:1522-1525`:
   ```python
   @router.get("/{workflow_id}/events")
   async def get_run_events(
       workflow_id: str,
       after: int = 0,
   ```
   There is no `limit`, no `has_more` and no next cursor in the reply (`{"workflow_id", "after", "events"}`,
   `runs.py:1561-1583`).
2. **No bound in the reader.** `backend/agents/authz.py:412`: `return query.order_by(RunEvent.seq.asc()).all()`: every
   column of every row, JSON payloads included.
3. **It runs on the event loop.** The endpoint builds its store with the request session (`runs.py:1549-1553`,
   `session=db`), and `_run_bounded` runs the body in-line when a session is injected (`authz.py:161-162`:
   `if self._session is not None: return body(self._session)`). The worker-thread path and its 10 s `StoreTimeout`
   (`authz.py:74`, `:173-177`) apply only to session-less stores. So the sync `.all()` over 107,409 rows blocks the loop,
   and nothing times it out.
4. **Encoding runs on the loop too.** The route has no `response_model`
   (`tests/integration/capture/API-CONTRACT.json`: `"handler": "get_run_events"`, `"response_model": null`), so FastAPI
   takes `else: return jsonable_encoder(response_content)`
   (`backend/.venv/lib/python3.13/site-packages/fastapi/routing.py:340-341`, FastAPI 0.141.1), inline, and then renders
   the `JSONResponse`.
5. **The reader is unbounded by design, so the obvious fix is a trap.** `authz.py:476-479`: "``read_events``
   deliberately does NOT gain a LIMIT: it is the replay primitive behind SSE resume, the events API and engine resume --
   capping it would silently truncate replays. Bounded READERS get this sibling instead". [FIX-688](20261001-2140-FIX-688.md)
   made that a locked constraint ("`read_events` is for callers that need the rows"), and its root
   [ISS-639](20260831-1645-ISS-639.md) already classified every whole-log reader.

Effect beyond the caller:

- The stall is process-wide. Anything else on that loop waits: other requests, SSE pings, and the execution engine's own
  coroutines for every live run. CONFIRMED for requests (the `/health` probe); INFERRED for live runs (below).
- Production starts ONE uvicorn process per container (`backend/docker-entrypoint.sh:31-36`, no `--workers`), so a
  replica's whole traffic stalls per call.
- Two tabs or a doubled effect multiply it: N calls are N consecutive stalls.

### Fix: where it belongs

Three places, because the cost is paid at three layers and every consumer reaches the endpoint through the first two.

1. `backend/agents/authz.py`: add a bounded forward reader next to `read_events_of_types`, for example
   `read_events_page(run_id, after_seq, *, limit)`: the same `seq > after_seq` and `_scope_owner_ws` filter,
   `ORDER BY seq ASC LIMIT :limit`, served by `uq_run_events_scope_seq` (`backend/app/models/run_event.py:61-67`).
   `read_events` stays as it is: that is the file's own convention (`authz.py:478-479`), FIX-688's locked constraint, and
   seven test modules define their own `read_events(self, run_id, after_seq)` fake
   (`backend/tests/integration/api/test_sse_stream_api.py:971,1204,1440,1468`,
   `backend/tests/unit/agents/test_concierge_capability.py`, `test_step_retry.py:117`, `test_conversation_provider.py:63`,
   `backend/tests/agents/test_backlog_plan_coverage.py:114`, `test_resume_mechanical_steps.py:52`,
   `backend/tests/unit/agents/execution_engine/test_iss685_resume_parses_task_file.py:51`). The scope filter is
   mandatory: this is the default-deny surface.
2. `backend/app/api/runs.py:1522` (`get_run_events`): `after: int = Query(0, ge=0)` and
   `limit: int = Query(1000, ge=1, le=5000)` (the idiom already at `runs.py:745`); read `limit + 1` rows to learn
   `has_more` without a COUNT; add `has_more` and `next_after` (the last returned seq, or `after` when empty).
   Additive: `workflow_id`, `after` and `events[*]` keep their shape (including `created_at` from
   [ISS-413](20260828-2357-ISS-413.md)).
3. `frontend/src/lib/api.ts:1477` (`getRunEvents`): loop while `has_more`, asking for the max page, and return the same
   concatenated `DurableFrame[]`. Treat a missing `has_more` as false so an old backend or the mock catch-all `{}` ends
   the loop (the `res?.events ?? []` tolerance at `:1473-1475` must survive). The seven page.tsx sites and `useRunChat`
   then need no change.

Sizing, interpolated from the measured curve: 1,000 rows hold the loop roughly 0.1-0.15 s, 5,000 rows roughly 0.3 s; the
107,409-event trace becomes 22 requests at 5,000 instead of one 4.4 s stall. A row cap does not bound bytes (one event is
1.23 MB) but the worst 1,000-event window on this run is 1.5 MB.

Traps for a naive fix: adding LIMIT to `read_events` silently truncates SSE resume and engine resume / gate re-arm
(`authz.py:476-479`); capping the endpoint without step 3 makes every history reopen replay only the first page (missing
agents, outputs, chat turns and the terminal event); renaming `events` breaks `RunEventsResponse` (`api.ts:1450-1455`);
a new reader without `_scope_owner_ws` would be an authorization hole.

Why not just move the read off the loop: the in-line mode is deliberate, because an injected request session "is
request-scoped and NOT thread-safe, so it can never be handed to a worker thread" (`authz.py:32-37`). The session-less
alternative (what the SSE path does, BUG-004) would trade the stall for a 10 s `StoreTimeout` on a bigger log and would
still build and send 53 MB. Paging keeps the injected session and makes each in-line hold about 0.1 s. The same class of
defect (sync work on the loop) is what the 2026-09-02 postmortem, `_run_bounded` and [FIX-577](20260901-0324-FIX-577.md)
already fixed elsewhere.

**Decision recorded by the analyzer (reversible).** Default cap, not opt-in: an opt-in `limit` would leave the reported
repro (a bare GET) unfixed. The in-repo consumers are enumerated above, so the contract change is contained. A
zero-contract alternative exists: stream the same envelope from keyset batches. It removes the freeze and the server
memory but still puts 53 MB on the wire, so it does not answer the report. Not escalated: nothing here needs a product
answer the code cannot supply.

### INFERRED (not measured; what settles each)

- **Live runs stall too.** The engine's coroutines and the SSE fan-out share this loop. Launching a revision of the 8-run
  family fires site 5 (`page.tsx:3765`) against the 107k-event root during the new run's first seconds. Settle: with a run
  streaming over SSE, issue the bare GET and record the inter-frame gap (expect ~4.4 s; subscriber queues hold 1,000
  frames, `config.py:281`, and the ping is 15 s, `config.py:275`, so drops are not expected).
- **Server memory.** About 53 MB of JSON exists as ORM rows, dicts, the `jsonable_encoder` copy and the encoded bytes at
  the same time. Settle: RSS before and after one call.
- **The loop-lag watchdog should have seen it.** `backend/app/core/watchdog.py` ([FIX-547](20260904-FIX-547.md)) warns when
  a 1 s sleep wakes up 2 s or more late (`WARN_LAG_SECONDS = 2.0`), so the dev server's terminal should hold a lag warning of
  about 4 s per probe above. That terminal is not readable from here, so this is unverified. It is also the post-fix
  regression signal: a bare GET must leave no watchdog warning.
- **Log size ceiling.** The content readers and the SSE replay sit under the 10 s `StoreTimeout`; ISS-639 measured 2-7 s
  per call at 37k-137k rows. Covered by [ISS-1166](20261009-1620-ISS-1166.md).
