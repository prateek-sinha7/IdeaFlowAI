# ISS-081

## Title

deriveSpecRevisionCount takes max over ALL agents, but prototype-build restarts once per task. Even with ISS-080's double-counting fully fixed, the derivation is wrong on any real prototype build: replaying run 6e38b9a7's real log through the current code yields 10 for a run with one revision, because the build agent restarted 11 times across its task loop and the max picks it up. Run d5dbc9f2 hid this because it never reached the build phase — it is paused at a spec gate, so prototype-specify (3 starts) happened to be the max. This will surface on the next completed prototype build, which is the common case. The count must be scoped to the agent that actually produces the revised artifact rather than taken across the whole roster. Design constraint the fixer must respect: scoping it by hardcoding prototype-specify would be an SC-001 violation (kernel/FE must not branch on a workflow-specific agent name) — derive the identity generically, e.g. from the agent that produces the gated spec artifact, and say in the fix why it is name-free. Same defective expression as ISS-080 (useWorkflow.ts:213-219), different mechanism: ISS-080 is *multiplicity*, ISS-081 is *scope*.

## Source / evidence

Found 2026-08-12 by the joint ISS-080/ISS-075 root-cause investigation, which replayed a second run's real event log through the real reducer rather than stopping at the first reproduction. Filed separately because fixing either one alone still leaves a wrong number on screen. CLOSED 2026-08-12 by FIX-225 (commit c46c8160). deriveSpecRevisionCount now counts restarts of the pipeline HEAD only — state.agents[0].id — instead of max over every agent. SC-001/INV-1 safety: the head is POSITIONAL, the first step of whatever roster the compiled manifest announced on pipeline_start; there is no agent id, no workflow name and no artifact kind anywhere in the expression, so a custom workflow gets the same rule for free. Verified against both real logs: d5dbc9f2 head=3 starts → 2 (durable truth: spec v1/v2/v3), 6e38b9a7 head=2 starts → 1 (durable truth: 1 revision) with prototype-build's 11 task-loop starts correctly ignored. Known and accepted limitation, recorded here rather than hidden: a workflow whose revision window excludes step 0 UNDER-reports (banner hidden) instead of over-reporting — a strictly better failure mode than the 10x over-report it replaces. Pinned by 5 new cases (incl. the predicted live symptom "0 revisions on a run whose only repeated agent is the task loop", seen RED at 10).
