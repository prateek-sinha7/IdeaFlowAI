# ISS-438

**Register source:** analyzer pass on `BUG-20260828-085400-runs-failed` in
`bug-hunter/ledger.md` (root card [ISS-317](20260828-1755-ISS-317.md)).

## Why the root cause implies this

[ISS-317](20260828-1755-ISS-317.md) traced the reported "Run failed" label to
`StepsOverviewSpine.tsx` reading `agents.some(a => a.status === "error")`. Tracing one
level deeper (past what that card cites) finds the actual carry-over site: the
`pipeline_start` reducer case in `frontend/src/hooks/useWorkflow.ts:403-541`. On a
same-run re-announcement (`isSameRunReannounce`, `:434-435` — true for every resume,
since "Reopen & fix"/"Run Again" resume the SAME `run_id`), the incoming roster is
merged onto `prev.agents` by identity:

```ts
// useWorkflow.ts:446-458
const carried = isSameRunReannounce
  ? new Map(prev.agents.map((a) => [a.id, a]))
  : undefined;
const agentStates: AgentRunState[] = agents.map((a, idx) => {
  const identity = { id: a.id, name: a.name, role: a.role, icon: a.icon || "🤖", index: idx };
  const existing = carried?.get(a.id);
  if (existing) return { ...existing, ...identity };
  ...
```

`{ ...existing, ...identity }` carries forward **every** field from the pre-resume
attempt except identity — including `status` and `error`. The only place that later
clears a specific agent's stale `"error"` is that agent's own next `agent_start` event
(`useWorkflow.ts:573-594`, confirmed: `status: "running", ..., error: null` on restart).
Until that agent's own event lands, `pipelineState.agents` — the ONE array every consumer
reads — still carries `status: "error"` for it.

`RunChatLane.tsx` is a second, independent consumer of that same array, not funnelled
through `StepsOverviewSpine`:

```ts
// RunChatLane.tsx:1906
const agents = pipelineState?.agents ?? [];
```

wired into the live, `building`-mode `<PipelineMini agents={agents} .../>` at
`RunChatLane.tsx:2062-2069` (the collapsible "Pipeline · {agents.length} agents" strip
with the pulsing `{completedCount} / {agents.length}` badge — confirmed live-only via the
`building` prop and the animate-pulse dot at `:2050`). Inside `PipelineMini`:

```ts
// RunChatLane.tsx:579
const errored = a.status === "error";
```

drives that agent's row circle to `bg-status-failed` (`:586-587`) regardless of
`pipelineState.isRunning`. Same array, same stale element, same resume — a second UI
surface renders the identical stale failure independently of whatever fix lands in
`StepsOverviewSpine.tsx` alone.

## Expected vs actual (predicted, not yet observed)

- **Expected:** while a resumed run is actively `generating`, every agent's chip in the
  chat lane's "Pipeline · N agents" strip reflects its CURRENT status (idle/running/done),
  not a state left over from the attempt that was just superseded by the resume.
- **Predicted actual:** the specific agent that carried `status: "error"` into the resume
  keeps its red/failed pip in `PipelineMini` for as long as every UI surface fed by
  `pipelineState.agents` does — until that agent's own `agent_start` event arrives, which
  can be tens of seconds into the resume if earlier agents must complete first (matches
  the ~20s window [ISS-317](20260828-1755-ISS-317.md) observed for the Steps-panel label).

## Status

**INFERRED — not independently reproduced.** Derived from the shared-array argument
above (both halves read from source: the merge at `useWorkflow.ts:457-458` and the
consumer at `RunChatLane.tsx:579`), not from a browser repro cycle. What would confirm
it: repeat [ISS-317](20260828-1755-ISS-317.md)'s cold-start protocol against the same
seeded run, and while the run is confirmed `generating`, expand the chat lane's
"Pipeline · N agents" strip and check whether the previously-failed agent's pip renders
red before its own `agent_start` fires.

## Fix

Belongs in the shared reducer, not in `RunChatLane.tsx` or `StepsOverviewSpine.tsx`
individually — `useWorkflow.ts`'s `pipeline_start` merge (`:457-458`) is the one seam
every consumer of `pipelineState.agents` routes through. A guard scoped to
`StepsOverviewSpine.tsx` alone (ISS-317's first proposed option: gate `failed` on
`!isRunning`) would fix that one label but leave this card's `PipelineMini` pip — and
[ISS-439](20260829-0057-ISS-439.md)'s `AgentDetailPanel` badge — still reading the same
stale `status: "error"` directly.
