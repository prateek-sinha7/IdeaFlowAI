# ISS-665

## Title

`FilesTab`'s deliverable-name resolution reads the live/HEAD sandbox tree even when the tab is
showing an older, correctly-pinned version — so the deliverable row's name/size/bytes can
silently reflect the CURRENT file, not the version actually being viewed. Sibling of QA-PS-008
([ISS-652](20260917-1244-ISS-652.md)).

## Status: INFERRED — mechanism confirmed by code, not yet exercised live

Filed from QA-PS-008's confirmed root cause (Defect 2's "ref-blind" resolver), not from an
independent reproduction. See "What would confirm this" below.

## Why QA-PS-008's root cause implies this

QA-PS-008's Defect 2 ([ISS-652](20260917-1244-ISS-652.md)) traces Preview's hang to
`resolveRunDeliverable` (`frontend/src/lib/api.ts:1175-1192`) resolving the deliverable file
against the run's live-tree listing and never considering the pinned ref:

```ts
export async function resolveRunDeliverable(
  token: string,
  runId: string,
  declared?: string | null,
): Promise<SandboxFile | null> {
  ...
  const listing = await getRunSandbox(token, runId);   // <-- no ref argument, ever
  return candidates.map((c) => listing.files.find((f) => f.path === c)).find(Boolean) ?? null;
}
```

The function signature has no `ref` parameter at all — it is structurally incapable of
resolving "the deliverable at version N," only "the deliverable on the live tree." Confirmed by
contrast: `getRunSandbox` itself already accepts an optional `ref` (`api.ts:1139-1151`), and
`SandboxTab.tsx` (the Workspace tab) correctly threads its own `selectedRef` through every
sandbox call it makes (`getRunSandbox`, `getRunSandboxFile`, `getRunSandboxFileBlob`,
`getRunSandboxZip` — `SandboxTab.tsx:1002,1041,1062,1075`). `resolveRunDeliverable` is the one
consumer that never got that treatment.

`resolveRunDeliverable` has two call sites in `FilesTab.tsx`, and BOTH are reachable while the
Files tab is displaying a pinned, non-live version — via the already-working URL-pin /
`handleSelectVersion` path (`BUG-124`/`FIX-516`), not only via QA-PS-008's broken leaked-tag
path:

- `FilesTab.tsx:526-539` — the **current run's own deliverable** row. `FilesTab` receives
  `runId={activeRunId}` (`PreviewPanel.tsx:1683`), and `activeRunId` correctly becomes the
  pinned member's id once `handleSelectVersion` runs (`PreviewPanel.tsx:726`,
  `viewingVersion?.id ?? unpinnedRunId`). The effect calls
  `resolveRunDeliverable(token, runId)` with no ref — so even for a CORRECTLY pinned older
  version, the row's name/size is read from the shared sandbox's live/HEAD tree.
- `FilesTab.tsx:482-517` — the **"From v{n-1}" base-version** section, expanded on demand.
  Calls `resolveRunDeliverable(getToken() || "", parentRunId, parentRun.deliverableFilename)`
  (`FilesTab.tsx:507`) — again no ref, and `parentRunId` resolves to the SAME shared
  chain-root sandbox as the current run (`_resolve_chain_root_or_404`), so this section reads
  the live tree too, not the parent's own tagged snapshot.

Both sites fail closed today (a `try/catch` leaves the derived-only row standing when
`resolveRunDeliverable` throws or returns null — `FilesTab.tsx:510`, `:537-539`), so this does
not hang the way Preview does. It is a quieter defect: whenever the live tree's matching file
differs from what existed at the pinned/parent version (renamed, moved, or a different sibling
extension resolved — see the ISS-251 sibling-preference comment at `FilesTab.tsx:443-450`), the
row silently shows the WRONG file's name/size/bytes, labeled as the older version.

## Expected (once reproduced)

Viewing an older, correctly-pinned family member's Files tab (or expanding "From v{n-1}") names
and sizes the deliverable row from THAT version's own git-tagged snapshot, matching what
`SandboxTab` already shows for the same pinned ref.

## Actual (inferred, not yet observed)

For a run family whose deliverable file's name, path, or bytes changed between versions (e.g. a
revision renamed `prototype.html`'s referenced asset, or a ppt_v2 revision produced the `.pptx`
where the parent only had the `.html` deck), pinning the OLDER version and viewing its Files tab
(or expanding "From v{n-1}") is expected to show the NEWER/live file's name and size, mislabeled
as the older version — or silently keep the plain derived row with no workspace metadata at all
if the live tree has no candidate matching that older declared name.

## What would confirm this

1. Create a run family where the deliverable's on-disk filename genuinely differs between v1
   and v2 (e.g. a revision that changes the declared extension, per the ISS-251 sibling
   preference).
2. Navigate to `/runs/{id}/versions/1` (the working URL-pin path) and open the Files tab; note
   the deliverable row's name/size.
3. Compare against `GET /api/runs/{id}/sandbox/file?path=<v1's own file>&ref=v1` fetched
   directly — if the Files tab row doesn't match that ref-scoped content, this is confirmed.

## Analysis missed (2026-09-17, fix stage for QA-PS-008)

Not fixed under QA-PS-008. [FIX-522](20260917-1449-FIX-522.md) fixed that bug's root cause
and left this card open. The mechanism above is right: `resolveRunDeliverable` has no ref.
But threading a ref into it, which is all this card's test pins, would not deliver the
card's "Expected" (name AND size AND bytes from the pinned version's snapshot):

1. **Sizes.** `GET /api/runs/{id}/sandbox?ref=` returns `"size": 0` for every file
   (`backend/app/api/run_files.py:713`). `withWorkspaceFile` then sets
   `size: formatSize(file.size)` (`frontend/src/components/results/FilesTab.tsx:458`), so
   every pinned row would read `0 B`, which is worse than today's live size.
2. **Bytes.** The row's workspace descriptor has no ref (`FilesTab.tsx:158`), and its Download
   calls `getRunSandboxFileBlob(token, runId, path)` with no ref (`FilesTab.tsx:700`). It would
   still download LIVE bytes under an older version's label.
3. **A third caller.** `frontend/src/components/preview/PreviewPanel.tsx:1239` also resolves
   ref-blind. That is part of the Preview hang now tracked in
   [ISS-677](20260917-1449-ISS-677.md).

A complete fix needs either:

- ref-aware sizes from the backend (e.g. `git ls-tree -r -l`, which is outside this card's
  frontend-only globs) plus a ref on the row's workspace descriptor and its Download; or
- a decision to hide size for pinned rows.

`frontend/src/lib/api.resolveRunDeliverableRef.test.ts` was left untouched. Its `it.fails`
still expects the ref-forwarding change. Needs re-analysis before a fix.
