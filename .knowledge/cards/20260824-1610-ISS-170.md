Found while live-testing [FIX-268](20260824-1610-FIX-268.md)'s `ex_A4_human_gate` (a
spec-014 human-gate conditional-branch fixture) through the actual UI, both via
`tools/api/runs/run.ex_A4_human_gate.http` and via a full browser run (launch -> edit the
review-gate content -> "Approve with edits & build").

## Symptom

Answering the human gate with `"dutch"` — including doing it through the real UI (typed
into the gate's Edit box, not just the API) — twice resulted in the **English** branch
(`say-hello`, "Hello, world!") running instead of the Dutch branch (`say-hallo`, "Hallo,
wereld!"). The pipeline reported `pipeline_complete` (success) both times, with no error
surfaced anywhere in the UI.

## Root cause (two layers)

1. **Proximate trigger**: `pick-language`'s prompt
   (`backend/agents/workflows/ex_A4_human_gate/workflow.yaml:90-94`) requires the reply be
   *exactly* one line of JSON (`{"decision": "dutch"}`). In both failing runs the model
   replied conversationally instead (observed raw output: `"Hallo! 👋 Wat ben je aan het
   doen?"`). `ConditionalGate._read_decision`
   (`backend/agents/capabilities/gates/conditional.py:146-188`) correctly fails closed:
   `json.loads()` raises on non-JSON text, so it returns `None` rather than crashing.

2. **The actual bug**: `ex_A4_human_gate` deliberately declares no `route.default_next`
   (`workflow.yaml:107`, "an unrecognised choice terminates the run here"). With
   `decision is None`, `ConditionalGate.evaluate`
   (`conditional.py:115-144`) correctly computes `GATE_BLOCK` and emits a `gate_blocked`
   event — the documented, intentional "nowhere to go" hard-stop (spec 014 R-13). **But
   `ExecutionEngine`'s POST-step gate loop
   (`backend/agents/execution_engine/engine.py`, ~lines 2938-3220 — where `conditional`
   actually runs, since it needs the step's own just-produced output) only has a handling
   arm for `_outcome == "route"`.** There is no `elif _outcome == "block":` there. Compare
   the PRE-step loop (`engine.py:2777-2836`), which explicitly catches a `block` outcome,
   transitions the state machine to `failed`, persists the budget snapshot, and yields one
   `pipeline_failed` — the POST-step loop has no equivalent.

   Consequence: the `gate_blocked` event is still forwarded to the client (visible in the
   raw event stream), but nothing halts the step. `_routed` stays `False`; `pick-language`
   is not a leaf step (`step.is_leaf` is false — it declares a `route`), so control falls
   through to the plain fallback at `engine.py:3255-3257` (`cursor = cursor + 1`) —
   landing on whichever branch is declared **first** in the manifest (`say-hello`), purely
   as an array-order artifact, not because anything selected it. The run then finishes
   normally and reports `pipeline_complete`.

## Why it stopped reproducing (and why that does NOT close this issue)

The trigger (a non-JSON model reply) is a reliability problem, not a deterministic one —
once the backend was confirmed to be calling a properly configured AWS Bedrock model
(every later `agent_complete` event carried `model_id:
"eu.anthropic.claude-haiku-4-5-20251001-v1:0"`, vs. an earlier, unrelated failure mode
where every agent call in this same fixture was rejected outright with `"The model
rejected this request."` — 0/5 agents completed, `pipeline_failed`/"no agent completed";
per the user this traces to an Ollama misconfiguration, resolved in a parallel session,
not a code fix), `pick-language` began reliably producing well-formed JSON, and 4/4
subsequent live-UI runs (english/spanish/dutch×2) routed correctly. **The engine-level gap
is unpatched and will resurface on any future model reply that doesn't follow the
strict-format instruction exactly** — which is inherently possible for any model,
occasionally, and is exactly the case this fixture's `route.default_next`-omission was
designed to fail loudly on.

## Suggested fix (not applied — this session was `/frontend`-scoped, and the file is
actively being edited by a parallel session)

Add an `elif _outcome == "block":` arm to the POST-step gate loop in `engine.py`
(~line 2938+), mirroring the PRE-step loop's existing handling (transition to `failed`,
persist the budget snapshot, yield `pipeline_failed`, return). **Scope it to the
`conditional` gate specifically** — the `gate_blocked` event already carries
`data.gate == "conditional"` (`conditional.py`'s `write_gate_event` call) — rather than
hard-stopping on *any* post-step block: the `validation` gate's post-step `block` is
currently intentional and soft (event-only, no halt; see `engine.py:2926-2929`'s existing
comment), and a blanket fix would regress that.

Already documented in more procedural detail (the PRE- vs POST-step split, and this exact
gap) in `.knowledge/architecture/DOMAIN-hitl-gating.md`, step 19 — added by the parallel
session concurrently with this investigation. This card is the trackable event-record;
that architecture card is the standing description of the mechanism.

## Independently reproduced — spec-014 backend session, 2026-08-24

Confirmed by the parallel backend session on the SAME day, and the second reproduction
widens the blast radius in a way that matters for the fix:

**It is not specific to the human-gate fixture, nor to a conversational reply.** It
reproduced on `ex_A2_branch` (no human gate at all) with a reply that CONTAINED valid
JSON — the model appended prose after it:

```
language output:  '{"decision": "english"}Hello! How can I help you today?'
gate_event:       conditional BLOCK   decision=null
then:             say-hello ran, pipeline_complete
```

So the trigger is any reply `json.loads()` cannot take whole, not merely a reply that
ignored the format. And the resulting run looked MORE convincing than in the A4 case:
`say-hello` is also the branch an `english` decision would legitimately select, so the
run appeared to route correctly. Nothing distinguished "routed to say-hello" from "fell
through to say-hello" except the absence of `agent_skipped` events for the untaken
branches — which is exactly what the assertion below now checks.

**A leniency fix was attempted and deliberately reverted.** Making
`_read_decision` recover the first balanced `{...}` span would have made this fixture
pass, and it was rejected on the user's explicit instruction: the engine is not to be
loosened to accommodate a model that ignores its instructions. A gate failing closed on
unparseable input is the gate working. That leaves the engine-side arm described above as
the only correct fix, and it is still the recommendation.

**Regression guard added (this issue stays open regardless).** Every branching `.http`
runner now asserts no `gate_blocked` event occurred:

```js
const blocked = events.filter(e => e.type === 'gate_blocked').map(e => payloadOf(e).step);
if (blocked.length === 0) apiLine('✓ no gate_blocked — the conditional gate actually routed');
else apiLine('✗ conditional gate BLOCKED at ' + blocked.join(', ') + ' — the run fell through', 'error');
```

`run.ex_A1_loop.http` already had an equivalent check; `ex_A2_branch{,_hola,_dutch}`,
`ex_A3_divert{,_spanish,_dutch}` and `ex_A4_human_gate{,_auto}` did not, which is why a
blocked run scored green. This makes the symptom LOUD in the test suite — it does not fix
the engine, and a run launched from the UI is still unguarded.
