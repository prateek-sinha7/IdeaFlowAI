# ISS-706

## Title

QA-PS-054 (`LEDGER.md`): "Download button serves the latest version while a pinned older
version is on screen." The validator reproduced this 3/3 from cold, on the healthy-git
`e53d9b1f`/`f7000bbd`/`dfeb5949` family, and captured the network requests directly: the
preview's own fetch for the pinned version always carried `&ref=vN`; the header Download click
fired a separate request to the identical path with **no `ref` param at all**, in all 3 attempts,
across 3 different pinned versions, from 3 different cold loads.

## Root cause — CONFIRMED

`frontend/src/components/preview/PreviewPanel.tsx:1333-1354`:

```tsx
const handleHeaderDownload = useCallback(() => {
  if (onDownload) return onDownload();
  if (!activeRunId || (!deliverableFile && !deliverableBundle)) return;
  void (async () => {
    const token = getToken();
    if (!token) return;
    const blob = deliverableFile
      ? await getRunSandboxFileBlob(token, activeRunId, deliverableFile)   // <-- no ref
      : await getRunSandboxZip(token, activeRunId);                        // <-- no ref
    const url = URL.createObjectURL(blob);
    const name = deliverableFile
      ? deliverableFile.split("/").pop() || deliverableFile
      : `workspace-${activeRunId.slice(0, 8)}.zip`;
    downloadBlob(url, name, blob.type);
    setTimeout(() => URL.revokeObjectURL(url), 5000);
  })();
}, [onDownload, deliverableFile, deliverableBundle, activeRunId]);
```

Neither branch passes `sandboxSelectedRef` (`PreviewPanel.tsx:732`, the pinned-tag state), even
though:

1. **It is already in this component's closure and already used nearby.** The sibling effect
   directly above, `PreviewPanel.tsx:1316-1330`, fetches the SAME resolved `deliverableFile` at
   the pinned ref and says so in its own comment (`:1311-1314`: *"Reuses the SAME resolved path
   the header Download button already found — just read at the pinned ref instead of the live
   tree — via the existing `getRunSandboxFile(token, runId, deliverableFile, ref)`"*):
   ```tsx
   getRunSandboxFile(token, activeRunId, deliverableFile, sandboxSelectedRef)   // :1322, HAS ref
   ```
2. **The callee functions both already accept it.** `getRunSandboxFileBlob` and `getRunSandboxZip`
   (`frontend/src/lib/api.ts:1239-1244`, `:1260`) both take an optional 4th/3rd `ref?: string`
   parameter and both forward it (`runSandboxFileUrl(runId, path, ref)` at `api.ts:1206-1210`
   appends `&ref=...` only when `ref` is truthy). Nothing on the client blocks passing it — the
   call sites simply never supply it.

`onDownload` (the early-return guard at `:1334`) is a `PreviewPanelProps` override that no
caller ever passes — `grep -rn "onDownload=" frontend/src/` outside `PreviewPanel.tsx` itself
returns nothing, and the sole mount site (`DashboardLayout.tsx:3285-3337`) passes no
`onDownload` prop — so that branch is always false in production and the ref-less fetch below
it is what actually runs on every click.

**Why the backend then serves the wrong version.** `backend/app/api/run_files.py:1080-1097`'s
own docstring states the contract: *"When `ref` is supplied the file bytes come from `git show
<ref>:<path>` — HEAD never moves... Omitting `ref` is byte-identical to today (Requirement 17
AC4)."* The handler's own branch confirms it: `ref: str | None = None` (`:1084`),
`if ref is not None:` (`:1121`) gates the entire `git show`-based read; when `ref` is absent that
whole block is skipped and execution falls through to `target = sandbox.path_for(rel)` /
`data = target.read_bytes()` (`:1158,1180`) — a plain filesystem read of the sandbox's live
working tree. A request with no `ref` query param therefore always returns the CURRENT/latest
content, independent of which version the UI is displaying.

**Careless-fix trap, also CONFIRMED by reading:** the `useCallback` dependency array at `:1354`
is `[onDownload, deliverableFile, deliverableBundle, activeRunId]` — it does **not** list
`sandboxSelectedRef`. Threading the ref into the two calls without also adding it here would
still ship a stale closure: `deliverableFile` is typically the *same string* across different
pinned versions (they usually share a filename, e.g. `presentation.html`), so React's
`useCallback` would frequently skip recreating `handleHeaderDownload` when only the pinned ref
changes, leaving the button downloading whatever ref was captured the last time one of the
*other* three deps actually changed — not necessarily the version currently on screen.

## Not Defect B2 — ruled out, not guessed

The bug's own dispatch brief floated Defect B2 (`git_init_sandbox()` idempotent only via
`.git.exists()`, silently rebuilding an ancestry-free repo and orphaning earlier tags,
`local.py:678-707`) as a hunch. Evidence rules it out for this symptom:

- B2 would make the pinned tag **unresolvable** — `_validate_ref` (`run_files.py:820-856`)
  checks the ref against `list_tags()`, so a ref lost to a B2 rebuild 400s. The validator's own
  capture shows the opposite: the `ref=vN` preview request returned **200** in all 3/3 attempts,
  on 3 different tags, on the exact family Defect A's own writeup already establishes as
  git-healthy ("all three tags exist").
- The download request's defect is not "the ref was invalid" — it is "the ref was never sent."
  A healthy or unhealthy tag store cannot explain a request that never included the parameter
  at all; the omission happens entirely client-side, before any network call.
- Not Defect B1 either (`WorkflowRun.git_tag` staying `NULL` — `engine.py:2349-2456`) for the
  same reason: this family's tags are populated and resolve correctly for every ref-bearing
  request observed.
- Not Defect A (revision content never written back into git so every tag's `presentation.html`
  is byte-identical) either — Defect A is a confound that happens to make the two responses'
  *bytes* look the same on this specific family (both 18715 bytes), which is exactly why the
  validator correctly relied on the **request URL**, not content, to confirm this bug. Defect A
  explains why byte-diffing can't prove this defect; it does not explain why the request omits
  `ref` in the first place. Once Defect A is fixed (revisions actually diverge in git), this
  bug's effect becomes visibly wrong downloads instead of a silent no-op difference — Defect A
  masks the symptom's visibility, not its mechanism. (Defect A's own bug is tracked separately,
  see `LEDGER.md` QA-PS-030 — not filed here, out of this card's scope.)

**Conclusion: genuinely new.** Independent of A, B1 and B2 — a plain frontend argument-omission
bug in one `useCallback`, coincidentally in the same version-pinning feature area.

## Not a duplicate of ISS-661

[ISS-661](20260917-1305-ISS-661.md) is the same function (`handleHeaderDownload`) but a
different line and a different defect: it is about the saved file's **name**
(`deliverableFile.split("/").pop()` vs. a content-derived name, `:1348-1349` today). This card
is about the **bytes** (`:1343-1345`, the `ref`-less fetch). A fix for one does not touch the
other; noted here only because a fixer touching this function should know both defects live in
it.

## Fix direction (not applied — issue only)

One place: `handleHeaderDownload` (`PreviewPanel.tsx:1333-1354`). Pass `sandboxSelectedRef ??
undefined` as the trailing argument to both the `getRunSandboxFileBlob` call and the
`getRunSandboxZip` call, **and** add `sandboxSelectedRef` to the `useCallback` dependency array
at `:1354` — omitting the second half ships a fix that is correct in a diff review and stale at
runtime (see "Careless-fix trap" above). `SandboxTab.tsx` is the existing, already-correct
pattern to copy from in the same codebase.

Out of this card's scope, left for the fixer to weigh: this fix alone does not make downloads of
a pinned OLDER version show genuinely different bytes on the `e53d9b1f` family, because Defect A
(QA-PS-030) still writes identical `presentation.html` content into every tag. The two fixes are
independent and both needed for the full user-visible correction; this card's fix alone is
still correct and necessary (it is what makes the *request* honest), and is directly observable
today via the request URL even before Defect A is fixed.
