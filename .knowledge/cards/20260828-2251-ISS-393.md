## Why this must also be broken

[ISS-392](20260828-2250-ISS-392.md) established that `AgentCapabilitiesModal`
(`AgentsPopup.tsx:476`) has no backend persistence path for its Config-tab Model/Validator/Gate/
Retry levers under ANY caller, and that `LibraryPage.tsx`'s caller at least routes the (non-durable)
value into a same-session ref. `AgentCapabilitiesModal` has exactly two production render call
sites (`grep -rn "<AgentCapabilitiesModal" frontend/src/ --include="*.tsx"` —
`LibraryPage.tsx:1030` and `AgentLibrary.tsx:332`, plus one test file). The second one is worse:

```tsx
// AgentLibrary.tsx:332-338
<AgentCapabilitiesModal
  agent={capAgent.agent}
  agentIndex={capAgent.index}
  onClose={() => setCapAgent(null)}
  onSkillsChange={onSkillsChange}
/>
```

No `onSelectionsChange` prop at all. Inside `AgentCapabilitiesModal`, `effectiveOnSelectionsChange`
(`AgentsPopup.tsx:538-541`) is:

```tsx
const effectiveOnSelectionsChange = (next: SelectionsMap) => {
  setLocalSelections(next);
  onSelectionsChange?.(next);
};
```

With `onSelectionsChange` undefined, the `onSelectionsChange?.(next)` call is a true no-op — not
even a ref write happens (unlike `LibraryPage.tsx`'s case). Clicking "Save agent"
(`AgentsPopup.tsx:772-793`) still calls `onSelectionsChange?.(localSelections)` (also a no-op
here), still flashes "✓ Saved", and still closes — with literally nothing surviving even the
current page session, let alone a reload.

`AgentLibrary` (the component that owns this mount) is itself rendered from four production call
sites (`grep -rn "<AgentLibrary\b" frontend/src/ --include="*.tsx"`, excluding tests):

- `frontend/src/app/workflow/page.tsx:67`
- `frontend/src/components/workflow/AgentsPopup.tsx:2526` — i.e. even the "Advanced Workflow
  Configuration" modal's own "+ Add agent" picker (a DIFFERENT surface from the
  `handleSelectionsChange`/`selectionsRef` mechanism [ISS-363](20260828-2129-ISS-363.md)/
  [ISS-364](20260828-2130-ISS-364.md) cover for that modal's outer levers) opens this same broken
  Config tab when previewing/configuring an agent before adding it.
- `frontend/src/components/workflow/WorkflowView.tsx:556`
- `frontend/src/components/workflow/composer/ComposerPage.tsx:1368`

Every one of these is a "browse the agent library and configure/preview an agent" surface reached
while composing a workflow, distinct from the `/library/agents/<id>` route ISS-287/ISS-392 cover.

## Expected vs actual

**Expected:** clicking "Save agent" inside the library/add-agent picker's Config tab either
applies the override to the agent being added, or the control does not present a working-looking
Save affordance for a change that has nowhere to go.

**Actual (INFERRED — not yet independently reproduced):** the click is a pure no-op — the "✓
Saved" flash appears, the drawer closes, and the selection is gone immediately, not just after a
reload. Because the mechanism (`effectiveOnSelectionsChange` short-circuiting on an undefined
`onSelectionsChange`) is identical to ISS-392's confirmed code read, only the browser-observable
behavior is unconfirmed.

## What would confirm or refute this

Open the agent picker from any of the four hosts above (e.g. `composer/ComposerPage.tsx`'s "+ Add
agent" flow), open an agent's Config tab, change the Model dropdown, click "Save agent", then
reopen the SAME agent's Config tab without leaving the page. Expected-per-this-card: Model is back
at "Default" immediately (no reload needed) — a miss would mean some other code path feeds
`onSelectionsChange` into this mount that this read did not find, refuting this card without
affecting [ISS-392](20260828-2250-ISS-392.md).

## Where the fix belongs

Same place as [ISS-392](20260828-2250-ISS-392.md): inside `AgentCapabilitiesModal`
(`AgentsPopup.tsx`), once. Both callers share the identical Config tab render; a guard there (read-
only levers, or a real backend-writing `onSelectionsChange` implementation) closes this sibling
for free, without touching `AgentLibrary.tsx` or any of its four hosts.
