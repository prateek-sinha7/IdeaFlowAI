# ISS-171

## What was found

The admin page generates an eight-character temporary password and calls
`adminResetUserPassword(token, userId, tempPassword, false)`. The frontend API client posts
`{new_password, permanent}` and expects a `{message, requires_new_password_at_next_login}`
response.

The backend declares an empty `ResetPasswordRequest` with `extra="forbid"`. Its handler delegates
to the Cognito lifecycle service to generate a temporary password internally—never exposing it to
the administrator—and returns `{"status": "temporary_password_set"}`. The frontend's two extra
fields therefore fail validation before the intended reset behavior can run.

## Impact

An administrator cannot use the reset action as implemented. More importantly, a naive repair
that merely accepts the frontend password would violate the committed security model by allowing
an administrator to know a recipient's credential.

## Required resolution

Choose the backend-owned temporary-password contract: make the client issue an empty POST, type
and consume the `status` response, and retain the existing UI message that the recipient must
change the password at next login. Add an end-to-end contract test covering the accepted empty
body, rejection of password-bearing input, response shape, and the UI action.
