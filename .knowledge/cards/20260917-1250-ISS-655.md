# ISS-655

## Title

The single-pipeline header badge (shown when exactly one pipeline is running, no dropdown) routes through the exact same broken click handler as the "N Running" dropdown from QA-PS-005 ([ISS-647](20260917-1100-ISS-647.md)), so it can produce the identical silent no-op with only 1 concurrent run — the dropdown's list-reflow mechanism plays no part here at all.

## Status: INFERRED — not yet reproduced

Filed from the root cause of QA-PS-005, not from an independent reproduction. Whoever picks this up should confirm it live before treating it as a confirmed defect (see "What would confirm this" below).

## Why QA-PS-005's root cause implies this

QA-PS-005's second, confirmed mechanism ([ISS-647](20260917-1100-ISS-647.md) § "Root cause — second mechanism") is that `onGoToPipeline` (`frontend/src/components/layout/DashboardLayout.tsx:2643-2653`) reads `pipelineState?.pipelineRunId` from a stale closure immediately after `onSwitchToLiveRun` fires (asynchronously, unresolved), rather than using the run id the user actually acted on. That stale-closure gate lives entirely inside `handleRunClick` (`frontend/src/components/layout/AppHeader.tsx:224-240`) — and `handleRunClick` is not exclusive to the dropdown:

- `frontend/src/components/layout/AppHeader.tsx:299-341` — the single-pipeline badge (`runningPipelines.length === 1`), rendered whenever exactly one pipeline is live. Its `onClick` (lines 308-321):
  ```tsx
  onClick={() => {
    const serverRun = recentRuns.find(r => r.id === runningPipelines[0].workflowRunId);
    if (serverRun) {
      handleRunClick(serverRun);
    } else {
      const runId = runningPipelines[0].workflowRunId;
      if (runId && onSwitchToLiveRun) { onSwitchToLiveRun(runId); }
      onGoToPipeline?.();
    }
  }}
  ```
  Both branches end the same way as the dropdown: `onSwitchToLiveRun(...)` fired synchronously, immediately followed by a bare `onGoToPipeline?.()` that reads the same stale `pipelineState?.pipelineRunId`.

This case does not need 2+ concurrent runs or the dropdown's own reflow bug — it only needs the single live run to differ from (or simply not yet equal) whatever `pipelineState.pipelineRunId` currently is, e.g. the user started the run, navigated to `/library` before it was ever "attached" as the viewed run, then clicked the badge from there.

## Expected (once reproduced)

Clicking the single-pipeline badge always switches to and navigates into that run's execution view, without a multi-second-or-longer delay and without ever failing to navigate.

## Actual (inferred, not yet observed)

The click can silently do nothing (badge click registers, dropdown/nothing closes, page stays put) when `pipelineState.pipelineRunId` was not already this run at click time, exactly as QA-PS-005 reproduces for the dropdown — recovering only once the unrelated reactive effect at `DashboardLayout.tsx:757-838` (line 790) eventually fires after the async switch resolves, or not at all if it doesn't.

## What would confirm this

1. Sign in, start exactly one pipeline run so the header shows the single "Running" badge (not the "N Running" dropdown).
2. Immediately navigate away to `/library` or `/dashboard` (anywhere that does not attach/view this run) before the app has had a chance to treat it as the tracked `pipelineState` run.
3. Click the single-pipeline badge and observe whether navigation happens immediately, is delayed ~1s+, or never happens on that click.
4. Compare against clicking it a second time immediately after — per QA-PS-005's own report, a retry is expected to be more likely to succeed.
