## What broke

Revisions 0041–0050 were written with plain `op.add_column` / `op.create_table`
/ `op.create_index`. The idempotency ratchet (`test_migration_idempotency.py`)
starts at 0038, but these ten shipped after it without the guards. Any database
that already held their objects while `alembic_version` said otherwise failed on
the first one:

- `docker-entrypoint.sh` runs `alembic upgrade head` under `set -eu`, so the
  container crash-looped.
- Locally, a DB stamped `0040` with 0041–0050 physically applied failed on
  `ALTER TABLE workflow_runs ADD COLUMN diverted_at_step_id` (seen 2026-09-23,
  see `UNIT-TESTS.md`).

## Fix

Each revision now calls the guarded helpers from `backend/alembic/migration_helpers.py`,
so re-applying against an existing schema is a no-op. The upgrade end-state is
byte-identical on both paths; `downgrade()` is untouched. `versions.lock`
fingerprints were regenerated for all ten revisions.

## Not verified here

The idempotency test needs Postgres (`requires_postgres`), so it is not part of
the offline tier and was not run during this sync.
