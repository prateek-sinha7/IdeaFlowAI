## Why this must also be broken

`_reconcile_terminal_status` (`backend/app/api/run_commands.py:748-838`) reads the run's ENTIRE
durable tail across every attempt (`store.read_events(run_id, after_seq=0)`, line 780) and
computes `degraded` with no attempt-boundary awareness whatsoever:

```python
completes = [e for e in events if e.type == "pipeline_complete"]
degraded = any(
    isinstance(e.payload_json, dict)
    and e.payload_json.get("status") == "degraded"
    for e in completes
)
```

Unlike `resume_supersedes` (line 811-818), which at least attempts a `reattempt_seqs` boundary
check between a cancellation and a later completion, `degraded` is a bare `any()` over EVERY
`pipeline_complete` event in the run's whole history — the original attempt's outcome and every
subsequent resume's outcome are pooled together with no notion of "latest." A run whose FIRST
attempt ends in a degraded `pipeline_complete` and is then resumed (the same "Run again"
`handleResumeRun` path a degraded run already exposes, per
[ISS-237](20260828-1741-ISS-237.md)) leaves that degraded event permanently in the tail. On the
decision ladder immediately below:

```python
if cancelled and not resume_supersedes:
    new_status = "cancelled"
elif degraded:
    new_status = "degraded"
elif completes and not failed:
    new_status = "completed"
else:
    new_status = "failed"
```

`cancelled` is `False` for a degraded-then-resumed run (it was never cancelled), so branch 1
never fires — but branch 2 (`elif degraded`) fires unconditionally on the STALE flag regardless
of what the LATEST attempt actually did:

- If the resumed attempt cleanly completes (a fresh, non-degraded `pipeline_complete`, no new
  `pipeline_failed`): `degraded` is still `True` (from the old event), so
  `new_status = "degraded"` — even though the run just fully succeeded.
- If the resumed attempt genuinely fails (`pipeline_failed`, no new `pipeline_complete`):
  `degraded` is still `True` (from the old event), so `new_status = "degraded"` — even though
  the run just failed outright.

Both are reached before the ladder ever consults `completes and not failed` or the `else`
fail-safe, because `elif degraded` sits ahead of them and nothing scopes it to "this attempt."

## Expected vs actual

**Expected:** the run's persisted status should reflect the LATEST attempt's own outcome —
`"completed"` if the resume cleanly finishes, `"failed"` if it genuinely fails — the same
"latest attempt wins" principle ISS-316's fix is meant to establish for the cancelled case.

**Actual (INFERRED — not yet independently reproduced):** `status` stays `"degraded"`
indefinitely regardless of the resumed attempt's real outcome, because the `degraded` flag is
computed over the full multi-attempt tail with no reattempt-boundary filter at all.

## What would confirm or refute this

Seed a run whose first attempt ends `pipeline_complete(status="degraded")`, click "Run again",
and let the resumed attempt either (a) complete cleanly or (b) fail outright. `GET
/api/runs/{id}` should then show `"completed"` or `"failed"` respectively; a hit shows
`"degraded"` in both cases instead. A miss on either variant narrows which half of this card is
real without affecting ISS-316 or [ISS-435](20260828-2253-ISS-435.md).

## Where the fix belongs

Same function, same file: `_reconcile_terminal_status`
(`backend/app/api/run_commands.py:748-838`), not either caller
(`_drive_user_resume:740` or `stop_run_driver`, `backend/app/api/run_shutdown.py:330-332`).
The `degraded` computation needs the same `reattempt_seqs`-bounded "is this from the LATEST
attempt" filter `resume_supersedes` already applies to `complete_seqs` — otherwise a fix that
only adds "a later `pipeline_failed` supersedes an earlier cancellation" (ISS-316's literal fix
shape) leaves this gap open, along with the mirror-image failed-flag gap in
[ISS-437](20260828-2253-ISS-437.md).
