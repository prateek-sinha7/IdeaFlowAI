## What happened

INFERRED sibling of [ISS-782](20260922-1610-ISS-782.md) (root card for
QA-PS-036, `BUGS.md#qa-ps-036`) — not reproduced live in this pass. Filed
because ISS-782's own root cause (mechanism 1: page components call
`getCapabilities`/`getPreferences` directly instead of reading from a shared
cached provider) directly implies it, once the caller set of `getCapabilities`
is traced past Analytics/Settings.

## Why the root cause implies this

ISS-782 confirmed `getCapabilities` (`frontend/src/lib/api.ts`) is called
independently, with no shared cache, by `AnalyticsPage.tsx:237` and (per
[ISS-781](20260922-1630-ISS-781.md)) `AccountSettings.tsx:141`. Grepping every
caller of the API (`getCapabilities`, aliased `fetchCapabilities` in this
file) finds two more independent call sites inside `AgentsPopup.tsx`, both on
live, reachable UI (the workflow composer), not dead code:

1. `CapabilityPaletteSection` (`AgentsPopup.tsx:1101`, mount effect
   `:1119-1146`, `fetchCapabilities(jwt)` at `:1128`) — rendered at
   `AgentsPopup.tsx:2789`.
2. `useAgentCapabilities` (`AgentsPopup.tsx:1525`, mount effect starting
   `:1534`, `fetchCapabilities(jwt)` at `:1544`, deps `[token]`) — a React
   hook, not a shared cache: every call site gets its OWN `useState`/
   `useEffect` pair, so calling it from N places fires N independent
   `/api/capabilities` requests.

`useAgentCapabilities` has 4 call sites: `AgentsPopup.tsx:1726`,
`AgentsPopup.tsx:1892`, `CanvasView.tsx:304`, `CanvasConfigRail.tsx:162`. The
last two are not merely siblings that COULD both mount —
`CanvasConfigRail` is rendered INSIDE `CanvasView` itself
(`CanvasView.tsx:2653`, the agent-config-tab branch), so opening the
composer's per-agent config tab mounts both at once.

`CanvasView.tsx:300-304`'s own comment states the intent explicitly:
"Lifted here (not called per-node) so every CanvasNode's model pill reads the
SAME fetched catalog instead of each node firing its own `/api/capabilities`
request" — the hook call was deliberately hoisted to `CanvasView` to avoid
per-node duplication, but `CanvasConfigRail`'s own independent call to the
same hook (`CanvasConfigRail.tsx:158-162`) reintroduces exactly the
duplicate-fetch problem that hoist was meant to prevent. `AgentsPopup.tsx:
1889-1890`'s comment on the second `AgentsPopup` call site says the fetch
state comes from "the SHARED hook (SC-001) — the same source the Canvas
inline config rail uses (INV-3, no forked fetch/filter)" — confirming the
codebase's own intent was single-flight, de-duplicated capability data; the
hook's implementation does not deliver that, because a hook's state is
per-call-site, not per-app.

## Expected vs actual

Expected: `GET /api/capabilities` fires once per composer/AgentsPopup session
and is reused by every consumer (`CapabilityPaletteSection` and all 4
`useAgentCapabilities` call sites).

Actual (inferred from the confirmed call graph, not yet measured live):
opening the composer's agent-config tab alone fires `GET /api/capabilities`
at least twice (`CanvasView.tsx:304` + `CanvasConfigRail.tsx:162`), before
counting whatever `CapabilityPaletteSection` and the other two
`useAgentCapabilities` call sites (`AgentsPopup.tsx:1726`/`:1892`) add if
reached in the same session — the same missing-cache shape as
[ISS-782](20260922-1610-ISS-782.md) (Analytics) and
[ISS-781](20260922-1630-ISS-781.md) (Settings), on a third surface neither of
those cards' `applies_to.globs` cover.

## What would confirm or refute this

Not reproduced. Open the workflow composer (`/workflow/create`, or a saved
workflow's canvas), click into an agent's config tab, and capture
`performance.getEntriesByType('resource')` filtered to `/api/capabilities`
right after the click — expect >=2 identical requests from one tab-open,
independent of React StrictMode (StrictMode would double whatever count this
produces, same as [ISS-784](20260922-1812-ISS-784.md)/[ISS-789](20260922-1818-ISS-789.md)
diagnosed elsewhere).

## Fix

Same direction as ISS-782/ISS-781/ISS-787/ISS-788: give `getCapabilities`
(and `getPreferences`, `getAnalyticsSummary`) one shared, cached/de-duped
implementation every caller routes through — a module-level in-flight-request
cache in `frontend/src/lib/api.ts` (keyed by URL + token) is the smallest
version, since a React hook alone (as `useAgentCapabilities` already
demonstrates) cannot share state across its own call sites without one. That
single change collapses `useAgentCapabilities`'s 4 call sites and
`CapabilityPaletteSection`'s own call down to one real network request,
without touching any individual call site.

## Resolution (2026-09-22)

Fixed by [FIX-617](20260922-1935-FIX-617.md), and confirmed live in the same
pass that this card said had never reproduced it: the e2e test now XPASSes, so
opening the agent-config tab fires no second `/api/capabilities`.

The fix is the card's own "smallest version" with one correction. A pure
in-flight cache would NOT have closed this one — `CanvasConfigRail` asks
seconds after `CanvasView`'s fetch has already resolved (the test clicks the
rail tab `SETTLE_MS` = 5 s after the nodes render), so the shared entry has to
survive settlement. `cachedGet()` (`frontend/src/lib/api.ts`) keeps the
resolved promise for a 30 s TTL, keyed URL + token. No call site changed, so
`useAgentCapabilities`'s four call sites and `CapabilityPaletteSection` all
collapse onto one request exactly as this card predicted.
