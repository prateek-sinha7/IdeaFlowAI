# ISS-1178

**Register source:** sibling derived during the `QA-KB-120` analysis on 2026-10-09 (root [ISS-1159](20261009-1530-ISS-1159.md)). Not its own bug row. It is the same flaw as the root, on the two payload entries the root does not touch.

**Confidence.**

- CONFIRMED by execution, with a SIMULATED write failure: sections `[E1]` and `[E2]` of `evidence/qa-kb-120/analysis-02-probe-build-flat-payload.txt` drive the real `build_flat_payload` and the real `finalize_terminal_run` (DB sessions mocked the way `test_finalizer_v2.py` does it) on a real `RunSandbox` and real git, and patch only the one write.
- INFERRED, a lead and not yet a defect: that a real run ever fails one of these writes. No log line, DB row or run id shows it. The dev database holds 3 finalizations with `non_chainable_reason = 'payload_blocked'` (`evidence/qa-kb-120/analysis-03-db-select.txt`, Q2). The row cannot say whether the block was a secret-scan hit or this `staging_failed`: the block reason is logged and not stored. A run log line `snapshot commit BLOCKED run=<id> reason=staging_failed` next to a `failed to write logs.jsonl` or `failed to write summary.md` warning for the same run id would settle it.

## Condition

A terminal pass whose declared output IS materialized, so `build_flat_payload` returns `chainable=True` and the full allowlist, but one of the two files the engine writes itself is absent from `.chain/` after the swap:

- `logs.jsonl`: the copy sits in a bare `try / except Exception` that logs a warning and carries on (`engine.py:1580-1595`).
- `summary.md`: `render_summary_md` plus the write, same shape (`engine.py:1700-1717`).

The allowlist was fixed before either write (`engine.py:1554`), and only the text form is taken back out when its copy fails (`engine.py:1667-1674`).

## What the probe shows

| scenario (probe section) | `build_flat_payload` | finalizer record | committed `.chain/` |
|---|---|---|---|
| `[E1]` the `logs.jsonl` copy raises `PermissionError` | warning `failed to write logs.jsonl`, then `stage_exact failed` (git 128), staged `[]` | `degraded`, `payload_materialized=False`, `payload_chainable=False`, `non_chainable_reason='payload_blocked'`, `git_tag=None` | `summary.md` only |
| `[E2]` the first `render_summary_md` call raises `OSError` | warning `failed to write summary.md`, then `stage_exact failed`, staged `[]` | same | `summary.md` only |

In both, the output file was written and the run's candidate was `completed`. The log sequence in the probe is `stage_exact failed`, then `commit_in_sandbox: staging failed`, then `finalize_terminal_run: snapshot commit BLOCKED ... reason=staging_failed — resetting index and rebuilding metadata-only`.

## Expected vs actual

Expected: a payload file that could not be written is reported as that. `stage_exact` is not asked to add a path that is not there, and the run is not described as a secret-scan block. Whether the run may still publish a chainable payload that lacks one of its three files is a product question (below).

Actual: the phantom entry reaches `commit_in_sandbox(force_add=...)` (`engine.py:2423`), whose per-path `git add --force` (`engine.py:616-618`) fails and is turned into `blocked / staging_failed` (`engine.py:625-638`). The blocked branch retries as a metadata-only snapshot and degrades with the fixed label `payload_blocked`, whatever the real block reason was (`engine.py:2439-2485`, the label at `:2485`). A materialized run ends degraded, untagged, not chainable, and named after the secret scan.

## Why the root cause implies it

Same function, same flaw as [ISS-1159](20261009-1530-ISS-1159.md): the allowlist is the declared names, fixed before anything is written, and reconciled with disk for one entry only. The root card is the output entry. This is the other two.

The consequence is different, which is why it is a card of its own. For an unmaterialized output the finalizer discards the whole payload anyway (`build_metadata_only_snapshot` resets the index first, `engine.py:1879-1889`), so the root is log noise. Here the payload is the real one and nothing discards it, so the phantom entry decides the outcome.

## Fix direction, and the question for the owner (INFERRED, not applied)

The reconcile that ISS-1159 adds for the output generalizes: build the allowlist from what is on disk under `.chain/` after the swap (`engine.py:1721-1728`), always as an exact-path subset of `payload_allowlist(...)` (`sandbox.py:272-320`). On its own that changes the outcome from "degraded / payload_blocked" to "published completed and tagged, with two of three payload files", which cuts against [ADR-0041](20260907-ADR-0041.md): "The payload is FLAT and is exactly three things". So the owner picks first. This is not an escalation of the root bug, whose fix is independent:

- (a) a missing payload file degrades the run under an honest reason (`payload_build_failed` is already a label the finalizer uses, `engine.py:2368-2370`), and the label at `engine.py:2485` stops being a constant; or
- (b) a payload that lacks `logs.jsonl` or `summary.md` is still published as chainable.
