# ISS-1044

**Source.** This was deferred from [ISS-967](20261002-0320-ISS-967.md), which [FIX-714](20261002-1159-FIX-714.md)
resolved for QA-KB-048 on 2026-10-02. ISS-967's "Fix direction" left one question undecided: "Whether an id that
resolves to nothing should be dropped silently or surfaced is a product call, not decided here." This card exists so
that question outlives ISS-967.

**Claim status.** INFERRED. The code below was read in the working tree on top of `024c03ef8`, and nothing was run.

## What is broken

**Condition.** A saved prototype, ppt or ppt_v2 workflow lists an agent id in `agent_ids` that the agent library no
longer returns. For example, the agent's AGENT.md was removed or renamed after the save.

**Behaviour.** The draft restore (`frontend/src/components/workflow/LaunchWizard.tsx:434-436`) looks each id up and
discards the misses:

```ts
const restored = d.agentIds
  .map((id) => allAgents.find((a) => a.id === id))
  .filter(Boolean) as AgentDef[];
```

The id is gone, and no message, marker or log says so. The screen, the launch draft and the next Save workflow all
lack it. If the server had received the id, it would have refused it loudly with `invalid_agent_ids`.

**What FIX-714 changes about it.** Before FIX-714, a restored roster shorter than the plan was replaced by the plan,
which hid the gap. Now a restored roster that differs from the library default is kept as it is. So a roster
missing a retired agent launches without it. If that agent produced input for a later step, `presort_specs` refuses
the launch with a 422 `workflow_unsatisfiable`. Otherwise the server's own roster handling applies
([ISS-966](20261002-0320-ISS-966.md)).

## Decision needed

What should happen when a restored saved workflow names an agent that no longer exists?

| option | consequence |
|---|---|
| A. keep dropping silently | today's behaviour; the user never learns their saved workflow changed |
| B. drop it and tell the user (inline notice naming the missing id) | the user can re-save or pick a replacement |
| C. keep the id and let the launch fail | the server's `invalid_agent_ids` error surfaces, but the workflow can't run until it's edited |

## What settles it

Run an offline vitest in `LaunchWizard.savedRoster.iss943.test.tsx`'s harness. Seed `prototype.draft` with
`agentIds: ["prototype-specify", "retired-agent-x"]`, preload the five prototype agents, click Continue, and read
`prototype.draft.agentIds`. Today that gives `["prototype-specify"]`, with nothing rendered about the missing id.
