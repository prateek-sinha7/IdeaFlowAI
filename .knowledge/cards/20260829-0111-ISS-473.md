## Why this must also be broken

[ISS-321](20260828-2002-ISS-321.md) root-caused the missing tier gate inside
`frontend/src/app/[...view]/page.tsx`'s `wizardMode` render branch (lines 3833-3838). That branch
is reached through the single catch-all `[...view]` tree ADR-0018 designates as the sole URL
entry point. But `frontend/src/app/workflow/create/page.tsx` is a **separate, sibling Next.js
file-system route** (`/workflow/create`), entirely outside that catch-all tree. Read in full:
`CreateRoute()` (lines 15-25) reads only `?mode=` from the URL and returns
`<LaunchWizard initialMode={mode} />` directly (line 24) -- with `mode` limited to `"ppt"` /
`"ppt_v2"` / default `"prototype"`. No tier check exists here, and none could reach this component
today even if someone wanted to add one locally: `user.tier` only lives inside `[...view]/page.tsx`'s
own component state, and this file has no access to it (its own comment at line 17-18 says "Auth
is owned by LaunchWizard" -- there is no tier-adjacent gate at all, just auth).

A comment in `frontend/src/app/[...view]/page.tsx:3628-3633` states: "next.config.ts's T17
redirect sends `/workflow/create?mode=X` straight back to `/create/{mode}}`" -- implying this
route is neutralized and unreachable in practice. Reading the actual `frontend/next.config.ts` in
full shows exactly four redirect rules (`/library/agents`, `/library/skills`, `/library/hooks`,
`/settings`) and **no rule for `/workflow/create`**. No `middleware.ts` exists anywhere under
`frontend/` either (`find frontend -maxdepth 2 -iname "middleware*"` returns nothing). The
redirect the comment describes does not exist in the code as it stands today.

This route is also not merely reachable by a stray bookmark -- the app itself pushes to it from
inside two live user flows: `frontend/src/components/layout/DashboardLayout.tsx:1547,1574`
(`handleLaunchSaved`'s ppt/prototype branch, i.e. re-launching a saved workflow from "My
Workflows") and `frontend/src/components/home/CreationHub.tsx:31,35`, both via
`router.push(routes.workflowCreateLegacy(mode))` (`frontend/src/lib/routes.ts:56`). Neither of
those call sites performs a tier check before the push (confirmed by reading the surrounding
`handleLaunchSaved` code, which switches only on `saved.base_pipeline_type`).

## Expected vs actual

**Expected:** every URL in the app renders behind the one required catch-all segment (ADR-0018),
and any tier gate added at that choke point applies uniformly to every way `LaunchWizard` can be
reached.

**Actual (INFERRED -- not yet independently reproduced live):** `/workflow/create?mode=prototype`
should be directly navigable by a basic-tier session (bypassing `routes.ts`/`[...view]` entirely)
and should render the fully interactive wizard the same way `/create/prototype` does per ISS-321 --
because it is the exact same `<LaunchWizard>` component with the exact same absence of a tier
check, just reached from a different page file. Re-launching a saved `prototype`-type workflow
from "My Workflows" as a basic-tier account should reach the identical ungated surface via
`handleLaunchSaved`'s push to this same route.

## What would confirm or refute this

Sign in as `qa-basic@flowinqa.com` and navigate directly to
`http://localhost:3000/workflow/create?mode=prototype`. If the browser lands on the interactive
wizard (not redirected to `/create/prototype` or anywhere else), this is confirmed live. Separately,
save a `prototype`-type workflow (as any tier that can), switch to `qa-basic`, open "My Workflows",
and click to relaunch it -- confirm the URL bar shows `/workflow/create?mode=prototype` and the
wizard is fully interactive. A redirect intercepting either case (from a layer not found in this
read -- e.g. a reverse proxy, or a Next `redirects()` config this search missed) would refute the
"bypasses the catch-all" half of this card, though the missing-tier-check half would still hold
for whatever page actually renders in that case.

## Where the fix belongs

This is the sibling that most directly argues the fix must NOT live only inside
`[...view]/page.tsx`'s `wizardMode` branch, or the gate is one grep away from disappearing behind
a code path that never runs through it. The two soundest options: (a) push the
`canRunPipeline(tier, pipelineType)` check into `LaunchWizard` itself (`frontend/src/components/workflow/LaunchWizard.tsx`),
since that is the actual shared component both `[...view]/page.tsx` and this file render --
one guard there closes every current and future caller; or (b) if `LaunchWizard` cannot reach
`user.tier` today (it currently owns only auth, per the file's own comment), add the check to
this file's `CreateRoute()` as well as to `[...view]/page.tsx`, and separately confirm whether the
T17 redirect should be restored (closing this route entirely) as the more root-cause fix, per
ADR-0018's single-catch-all invariant. Either way, a fix that only edits `[...view]/page.tsx`
leaves this route's `<LaunchWizard>` render (line 24) completely unfixed.
