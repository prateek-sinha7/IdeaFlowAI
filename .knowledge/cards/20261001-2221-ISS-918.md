# ISS-918

**Status of the claim: INFERRED.** The two literals and their disagreement are CONFIRMED by reading the lines cited below. That the disagreement has any runtime effect is INFERRED, and the reading says it has none that fails a run today. Nobody has reproduced it in a browser or a test. This is a sibling of [ISS-686](20260918-ISS-686.md) (bug QA-KB-025), derived from its root cause.

## Why the root cause of ISS-686 implies this

ISS-686's root cause is that the composer owns a parser-to-file fact as a frontend literal instead of reading it from the registry. The Canvas rail is not the only composer. The Simple view (`AgentsPopup.tsx`) is the other hand-written surface over the same selections map (the same duplication [ISS-765](20260922-1428-ISS-765.md) found for the fan-out lever), and it carries its own copy of the fact, with a different value.

## The condition

Fan out over a list, choose Waves, then compare the two views:

| view | writes for json_tasks waves | where |
|---|---|---|
| Simple (`AgentsPopup.tsx`) | `target: "tasks.json"` | `:2443` (mode select) and `:2496` (source select) |
| Canvas (`CanvasConfigRail.tsx`) | `target: "build/tasks.json"` | `PARSER_TARGET` `:70-73`, applied at `:1559` and `:1612` |
| the parser itself | `build/tasks.json` | `json_tasks.py:214`, `fallback_targets` default |

The same user action saves two different manifests depending on which view the author used. The Simple view's two lines:

```tsx
...(wave ? { target: "tasks.json" } : {}),     // AgentsPopup.tsx:2443
...(waveOn ? { target: "tasks.json" } : {}),   // AgentsPopup.tsx:2496
```

History (`git log -S`): the Simple-view literal arrived in `897fe7dbb`, `PARSER_TARGET` in `5b3540d71`. They were written at different times and never reconciled.

## Impact: Low, nothing fails today

`json_tasks.parse_preferring_target` tries `[target, *fallback_targets]` in order and moves on when a candidate is absent, empty or unparseable (`json_tasks.py:237-264`), so a Simple-view wave reads `tasks.json` first and `build/tasks.json` second. A planner that writes either file is found. What it costs:

- a stale `tasks.json` at the sandbox root wins over the planner's `build/tasks.json`;
- the saved manifest and `GET /api/workflows/{id}` (`workflows.py:481-486`) name a different file than the Canvas does for the same step;
- opening the step in the Canvas and switching the fan-out mode rewrites the Simple view's value to `build/tasks.json` (`CanvasConfigRail.tsx:1559`).

The repo's own manifests use both conventions (`sample_wave/workflow.yaml:37` has `tasks.json`; `backlog/workflow.yaml:199` and `prototype_v2/workflow.yaml:122` have `build/tasks.json`), so neither literal can be called wrong from the code. That is the point: the default belongs to the parser, and a step's authored target belongs to the step.

## Fix

Do not fix this on its own. It routes through the same helper as [ISS-686](20260918-ISS-686.md): read the default target from the capability option (registry `config_schema`) in both views, or drop the literal and let the parser's own `fallback_targets` apply. `useAgentCapabilities` is defined in `AgentsPopup.tsx:1610` and the rail already imports it from `../AgentsPopup`, so one helper exported next to it serves both views. The Simple view's fan-out lever lives in `AdvancedExpander` (`:1976`), which calls the hook at `:2002` but destructures only `{ validatorOptions, gateOptions, modelOptions, loading, error }`, so `taskParserOptions` has to be added to that destructuring before the lever can use the helper.

## For the test-writer

`AdvancedExpander.test.tsx:241-272` already drives the Simple view's Waves select and asserts `task_source` with `toMatchObject` and no `target`, so it passes whichever value is written. A guard has to compare the two views: pick Waves in each and assert both write the same `task_source.target` (or both write none).
