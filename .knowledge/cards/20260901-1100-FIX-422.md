## What was wrong

`frontend/src/lib/routes.ts:98-100` — `runStepsAgent: (id: string, agentId:
string): string => `/runs/${id}/steps/${agentId}``. Every sibling run-tab
builder (`runSteps`, `runFiles`, `runWorkspace`, `runAudit`) accepted an
optional `version?` second parameter and produced the versioned form
`/runs/${id}/versions/${version}/${tab}` when supplied. `runStepsAgent`
lacked the parameter entirely, so no code in the app could ever construct a
version-pinned per-agent Steps URL through the typed builder, even though
`parseViewPath` already returned `{ ..., version }` for that screen (`:339`).

## Root cause

`routes.ts:98-100` — missing `version?: string` param on `runStepsAgent`.
See [ISS-386](20260828-2228-ISS-386.md) for full evidence.

## What changed and why there

**`frontend/src/lib/routes.ts`** — `runStepsAgent(id, agentId, version?)`:
added the optional `version?` parameter and the same conditional path shape
all sibling builders use. One line of change; no other route builder or
caller needed editing (zero production callers of `runStepsAgent` confirmed
by grep before fixing).

**`frontend/src/lib/routes.test.ts`** — added one `testRoundTrip` case:
`routes.runStepsAgent('run-789', 'agent-1', 'v3')` must round-trip to
`{ screen: 'run-steps-agent', runId: 'run-789', agentId: 'agent-1', version: 'v3' }`.
The existing non-versioned test case is kept intact.

SC-001: the version string is opaque. No branch anywhere keys on a workflow
name. `reopenTabFor`'s screen→tab mapping is unchanged.
