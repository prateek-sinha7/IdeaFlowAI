# FIX-752

## What was wrong

Register entry QA-KB-055 (Medium). The root card is [ISS-745](20260922-1400-ISS-745.md) and the sibling is
[ISS-1074](20261007-2140-ISS-1074.md). A `*_revision` launched earlier in this tab on family A keeps streaming after
the user opens family B. Opening a terminal run does not replace the sticky focus (`page.tsx` `if
(!REOPEN_TERMINAL_STATUSES.has(fullRun.status)) { runConnection.attachRun(fullRun.id); }`). When A's revision
completed, the run-detail screen switched to family A: the chip, header, family and Preview body all changed, while the
URL still named B.

Root cause, at HEAD `e93aa40ed` (page.tsx unchanged since `8a0128685`), in `handleWebSocketMessage`'s
`pipeline_complete` branch:

- `page.tsx:1617`: `const isRevisionCompletion = typeof completingPipelineType === "string" &&
  completingPipelineType.endsWith("_revision");`. This is a suffix test, so it does not check lineage.
- `page.tsx:1629`: `if (completingRunId && (!isForeignCompletion || isRevisionCompletion)) {`. The OR let any
  revision bypass `isForeignCompletion` and call `setContentSourceRunId(completingRunId)`.
- `page.tsx:1625`: the [FIX-203](20260807-1929-FIX-203.md) background bridge excluded every revision, so a foreign-family revision got neither the
  bridge nor the guard.
- `page.tsx:1688-1731` (ISS-1074): the four Preview slot writes (`setUserStoryContent`, `setPptContent`,
  `setPrototypeContent`, `setGenericDeliverable`) had no gate at all. Even with the id guard fixed, any foreign
  completion, revision or not, still replaced the viewed body.

## What changed, and why there

All three writes are made in the one `pipeline_complete` branch. That branch is where the fix goes, behind one
decision.

- `frontend/src/lib/wsReplayState.ts:104` adds `isSameRunFamily(family, viewedRunId)`, next to `isForeignRunFrame`.
  It checks membership of the owned family returned by `GET /api/runs/{id}/family` (root plus every owned descendant,
  `runs.py` `get_run_family`). That makes it a family-ROOT comparison, not the parent check the BUGS.md sketch
  proposed. A missing family or a missing viewed id returns false.
- `page.tsx:1629` `const applyCompletion = (sameFamily: boolean) => { ... }` now wraps the three existing writes. Their
  bodies are byte-identical apart from a 2-space re-indent (`git diff -w` shows only the guards):
  - `:1636` bridge: `if (completingRunId && isForeignCompletion && !sameFamily)`. It now also covers another family's
    revision. `:1640` releases that run's sticky focus ([BUG-015](20260803-BUG-015-sse.md) detach), which the old hijack branch did on this path.
  - `:1643` content source: `if (completingRunId && (!isForeignCompletion || sameFamily))`.
  - `:1708` slots: `if (finalOutput && pipelineType && (!isForeignCompletion || sameFamily))` (ISS-1074).
- `page.tsx:1753-1762` makes the call. Only a foreign revision resolves lineage:
  `getRunFamily(lineageToken, completingRunId)` → `isSameRunFamily(family, trackedRunIdRef.current)`. It re-reads the
  tracked ref on resolve, as ISS-745 asks, and `.catch(() => false)` falls back to background on failure. Every other
  completion calls `applyCompletion(false)` synchronously, as before.
- Lineage source: this is option (a) of ISS-745's analysis. There is no SSE payload change, no engine change and no new
  import (`getRunFamily` was already imported in `page.tsx`). It costs one GET, and only on the rare foreign-revision
  branch.
- The KAN-125 comment (`page.tsx:1507-1510`) said this handler "intentionally saves content for ALL tab-local
  completions". ISS-1074 makes that false, so the comment was corrected.

Preserved:

- Launch→watch: an own completion takes the synchronous path, gated exactly as before.
- [FIX-088](20260722-FIX-088.md) / [FIX-603](20260922-1440-FIX-603.md): the un-pinned same-family follow-to-latest still happens, one GET later, when the viewed member is
  older than the completing revision. `PreviewPanel.pinSurvival.test.tsx` GREEN control is still green.
- FIX-203: the bridge for foreign non-revisions is unchanged.
- [FIX-172](20260805-1853-FIX-172.md) / [FIX-173](20260805-1853-FIX-173.md): the transcript recovery is unchanged and runs inside `applyCompletion`.

Test edits, both asked for by ISS-745's Test notes:

- `contentSourceRunScope.source.test.ts`: the literal pin
  `if (completingRunId && (!isForeignCompletion || isRevisionCompletion)) {` now reads `... || sameFamily)) {`. The
  card said "the fix has to update it deliberately". The assertion's intent, that a genuinely foreign completion is
  refused, is kept.
- `wsRunScope.test.ts`: added five `isSameRunFamily` cases: same family, deeper chain (viewing a1 while a3, a child of
  a2, completes), different family, unresolved, and own completion still decided by `isForeignRunFrame`.

## Deliberately NOT fixed

- **[ISS-1077](20261007-2142-ISS-1077.md) is escalated, not resolved**: `ESCALATIONS.md#qa-kb-055`. Its assertion
  (`foreignRevisionHijack.qaKb055.source.test.ts:47-49`) requires that `DashboardLayout.tsx` NOT contain
  `postRevision(getToken() ?? "", contentSourceRunId,`. `revisionFamilyLinkage.source.test.ts:28` requires that it
  DOES. That test pins Revision Families B1, whose contract is the `DashboardLayout.tsx` prop note "Every revision
  launch path sources parent linkage from this". The two tests cannot both pass.
  - The card's first fix direction is a route-derived parent. That would revise the older member the URL names after
    the same-family advance above has put the newer revision on screen.
  - Its second direction is refuse-on-mismatch, which adds a new UX surface.
  - With this fix, the only background writer of `contentSourceRunId` is family-gated. Every other writer is navigation
    or launch (`page.tsx:2801`, `:2940`, `:2980`, `:3528`, `:3623`, `:4307` at HEAD).
- The `{ fails: true }` placeholder in `PreviewPanel.pinSurvival.test.tsx` (`it("ISS-745 (INFERRED, unconfirmed) ...`)
  stays an expected fail. It re-renders PreviewPanel with a foreign `liveRunId`, which this fix stops at the page and
  so never reaches PreviewPanel. FIX-603 and ISS-745's Test notes say no PreviewPanel change can turn it green for the
  right reason. Retire it; do NOT just drop `fails: true`, or it goes red.
- Live browser repro: not run. Reproducing it costs a real revision run, so the owner must approve it. ISS-745's Test
  notes give the steps.
