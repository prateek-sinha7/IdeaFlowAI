# ISS-647

## What happened

Root cause investigation for register bug **QA-PS-005** (`BUGS.md#qa-ps-005`, "Clicking a
pipeline entry in the 'N Running' header dropdown sometimes does nothing").

**Reproduction (cycle 3 of a clean 3-cycle cold-start sweep, plus two direct follow-up
tests that isolated the mechanism):**

- Cycles 1 and 2 (cold `page.goto('/dashboard')`, open the dropdown, click a stable
  `waiting_for_user` entry): the click **always eventually navigated**, but only after an
  unexplained ~800ms–1.4s delay before the route changed — not an instant SPA nav.
- Cycle 3 (cold load, click the badge and a menu entry *immediately*, without waiting
  for the page to settle): the click landed on the dropdown but the app stayed on
  `/dashboard`; the intended run only loaded ~1s later.
- Follow-up A: opened the dropdown with a short-lived 1-agent run's entry present,
  polled with a role locator on that entry as it finished — got a Playwright
  "element was detached from the DOM, retrying" failure, i.e. the entry vanished from
  the menu out from under an in-flight interaction.
- Follow-up B (isolates the exact failure mode): opened the dropdown, captured the
  screen coordinate of a short-lived run's menu entry, waited for that run to complete
  and disappear from "Active Pipelines" (confirmed via `getByRole('menuitem').count()`
  going to 0), then fired a raw `page.mouse.click(x, y)` at the **original** coordinate
  (i.e. exactly what a real user's mouse does when they click where the entry used to
  be). The click landed on and activated **a different run's button** that had shifted
  up to fill the vacated row — navigating to the wrong run, not the one the user saw
  and clicked.

## Root cause

`AppHeader.tsx`'s `runningPipelines` array (source for the "N Running" dropdown, around
line 190) is recomputed from `liveRuns`/`recentRuns` on every render, and `recentRuns` is
driven by live polling/SSE. The dropdown (`role="menu"`, opened at line 368) renders one
`<button role="menuitem">` per pipeline in that array (line 383) with no snapshot/freeze
of the list while `runningDropdownOpen` is true. When any listed run changes status while
the menu is open — a fast 1-agent workflow completing, or a review gate being resolved
elsewhere — the array shrinks or reorders and React reflows the button list immediately,
including under an in-flight click.

Two concrete failure shapes follow directly from this:
- If the vanishing run is **not last**, the rows below shift up to fill its slot; a click
  aimed at the visual position of one run now lands on a different run's button, which
  still fires normally — the app navigates, just to the wrong run (observed in Follow-up
  B above).
- If the vanishing run **is last**, the row it occupied disappears entirely with nothing
  to shift into its place; a click aimed at that now-empty space inside the menu
  registers on no element at all — this is the literal "does nothing" the register entry
  describes, and it is intermittent by construction: it only triggers when a background
  refresh removes exactly the row the user is clicking, in the same frame.

The ~800ms–1.4s pre-navigation delay seen on cycles 1–2 is a separate, milder symptom of
the same volatility (the click handler resolves `recentRuns.find(...)` against
still-refreshing data before calling `onSwitchToLiveRun`/`onGoToPipeline`), and likely
compounds user-perceived "nothing happened" — a user who does not wait ~1s may conclude
the click failed and click elsewhere or re-open the dropdown, at which point the list has
already moved on.

## Expected vs actual

- **Expected:** clicking any listed pipeline entry navigates to that run's detail page,
  every time, regardless of what else changes in the background.
- **Actual:** while the dropdown is open, a background status change to any listed run
  reflows the menu under the pointer; a click can silently resolve to the wrong run, or
  to nothing, depending on whether the vanishing row was last in the list.

  — screenshot taken during the cold-start immediate-click attempt (cycle 3) while the

## Conditions established

- Tier: `qa-admin@flowinqa.com` (default; not tier-specific — header is global).
- Route: any page rendering the shared `AppHeader` (dropdown itself only appears when
  `runningPipelines.length > 1`, i.e. 2+ concurrently active runs).
- Trigger requires **2+ concurrently active pipelines** with the dropdown open and at
  least one of them changing status (completing, or a review gate resolving) while the
  user is clicking — a single always-running long pipeline will not exhibit this.
- Not theme- or viewport-dependent; reproduced at default light desktop viewport.

## Root cause — second mechanism (analysis phase, CONFIRMED by direct code read)

The reflow above is not the only mechanism, and does not by itself explain the register
entry's "the same entry may work on a subsequent click." A second, independent defect in
the same click path does:

`AppHeader.tsx`'s `handleRunClick` (`frontend/src/components/layout/AppHeader.tsx:224-240`):

```tsx
const handleRunClick = (run: WorkflowRun) => {
    setRunningDropdownOpen(false);
    if (LIVE_STATUSES.has(run.status)) {
      if (onSwitchToLiveRun) {
        onSwitchToLiveRun(run.id);
      }
      onGoToPipeline?.();
    } else { ... }
};
```

fires `onSwitchToLiveRun(run.id)` and, on the very next line, `onGoToPipeline()` —
synchronously, without awaiting anything. `onSwitchToLiveRun` here is wired at
`frontend/src/components/layout/DashboardLayout.tsx:2655-2664` to call
`handleSwitchToLiveRun` (`frontend/src/app/[...view]/page.tsx:2592`), which is `async`:
it runs `runStore.switchViewTo(runId)` synchronously (page.tsx:2624) but then
`await getRunEvents(...)` (page.tsx:2648) and replays each durable frame
(page.tsx:2651-2659) before the per-run `pipelineState` the rest of the app reads is
fully populated — a real network round trip, wrapped in a bare
`catch { /* Non-fatal: pipelineState and transcript will populate via live SSE frames. */ }`
(page.tsx:2673-2676) if it fails.

`onGoToPipeline`, however, does not wait for any of that. Its one and only implementation
(`frontend/src/components/layout/DashboardLayout.tsx:2643-2653`):

```tsx
onGoToPipeline={() => {
  const runId = pipelineState?.pipelineRunId;
  if (runId) {
    onSwitchToLiveRun?.(runId);
    setMainView("execution");
    router.push(routes.runStream(runId));
  }
}}
```

is a closure captured at DashboardLayout's LAST completed render, so `pipelineState` here
is whatever run was attached BEFORE this click — not the run the user just clicked. Two
outcomes follow directly, both synchronous and deterministic given that stale value:

- If no run was previously attached (`pipelineState?.pipelineRunId` is `undefined`) —
  e.g. a cold `/dashboard` load, matching this card's own Cycle 3 — `if (runId)` is
  false and the entire block, including `router.push`, is skipped. Nothing visibly
  happens on that click.
- If a DIFFERENT run was previously attached, this closure re-navigates to that OLD run
  instead of the one just clicked, potentially undoing the switch `onSwitchToLiveRun`
  just issued.

The only thing that does eventually route to the newly-clicked run is a separate,
unrelated `useEffect` (`frontend/src/components/layout/DashboardLayout.tsx:757-838`,
the push itself at line 790: `if (incomingRunId) { router.push(routes.runStream(incomingRunId)); }`),
which re-fires because `pipelineState?.pipelineRunId` is in its dependency array
(line 838) — but only once the async chain above actually completes and re-renders.
That gap is this card's own reproduced 800ms–1.4s delay (Cycles 1–2); if the chain never
resolves to a `pipelineRunId` change (the swallowed-`catch` case, or a background run
whose SSE frames aren't reaching this tab), that effect never fires either and the click
is a permanent no-op until something else nudges `pipelineState` — which is exactly why
"the same entry may work on a subsequent click" (the second click's own async chain gets
a fresh chance to resolve, or by then the first one already has).

Contrast with the sibling handlers in the SAME file that are NOT affected, because they
push using the run id passed into the handler directly instead of re-deriving it from
`pipelineState`: `onSelectWorkflowRun` (`DashboardLayout.tsx:2665-2669` and `:2874`) and
`onViewResults` (`DashboardLayout.tsx:2675-2708`, `router.push(routes.runStream(targetRunId))`
at `:2708` using its own resolved `targetRunId`). This is the working shape the broken
call sites should match.

## Blast radius (analysis phase — every caller grepped)

`grep -rn "onGoToPipeline" frontend/src` — 5 files. Non-test hits:

- `frontend/src/components/layout/AppHeader.tsx:232` — the reported dropdown entry click
  (`handleRunClick`, this card's original subject).
- `frontend/src/components/layout/AppHeader.tsx:308-321` — the single-pipeline header
  badge (`runningPipelines.length === 1`) calls the identical `handleRunClick` →
  `onSwitchToLiveRun` + `onGoToPipeline()` pairing. Filed as [ISS-655](20260917-1250-ISS-655.md).
- `frontend/src/components/layout/AppHeader.tsx:451` — the "legacy-run-badge" fallback
  (`runningPipelines.length === 0 && isPipelineRunning`) calls bare `onGoToPipeline` with
  no preceding `onSwitchToLiveRun` call — there is no run-switch to race, so
  `pipelineState.pipelineRunId` is already the one being resumed. NOT affected — checked
  and ruled out.
- `frontend/src/components/layout/DashboardLayout.tsx:2643` — the one implementation
  (the bug).
- `frontend/src/components/layout/DashboardLayout.tsx:2859-2873` — `onViewRunningPipeline`
  (passed to `WorkflowHistory`) is a byte-for-byte structural clone of the same buggy
  shape (`const runId = pipelineState?.pipelineRunId; if (runId) { onSwitchToLiveRun?.(runId); ...; router.push(...); }`).
  Filed as [ISS-656](20260917-1250-ISS-656.md).
- `frontend/src/components/ui/NotificationPanel.tsx:33,203` — accepts an `onGoToPipeline`
  prop but never calls it anywhere in that file (`grep -n "onGoToPipeline("` in this file
  returns nothing). Dead reference, not part of the blast radius.

No in-flight guard exists anywhere in `handleSwitchToLiveRun` (`page.tsx:2592-2680`)
against a second call starting before the first's `await getRunEvents` resolves — a rapid
re-click/double-click compounds the same race. Filed as [ISS-657](20260917-1250-ISS-657.md).

## Fix (where it belongs)

Two separate, independent fixes — different files, different mechanisms, neither blocks
the other:

1. **The stale-closure race** (this section): change `onGoToPipeline`'s signature from
   `() => void` to `(runId: string) => void` and have `handleRunClick`
   (`AppHeader.tsx:232`) and the single-badge caller (`AppHeader.tsx:319`) pass the run id
   they already have (`onGoToPipeline?.(run.id)`) instead of calling it bare. Update the
   ONE implementation (`DashboardLayout.tsx:2643-2653`) to navigate using the passed
   `runId` argument instead of re-deriving it from `pipelineState?.pipelineRunId` —
   matching the already-correct `onSelectWorkflowRun`/`onViewResults` shape in the same
   file. One guard in that one implementation fixes the dropdown, the single badge, and
   (once `onViewRunningPipeline` is changed the same way) the History page's resume
   button, rather than three independent per-caller patches.
2. **The list reflow** (this card's original section, above): freeze/snapshot
   `runningPipelines` in `AppHeader.tsx` (e.g. a ref or a `useMemo` locked at the moment
   `runningDropdownOpen` becomes true) so the menu does not reorder under an open click.
   Belongs in `AppHeader.tsx` only.
