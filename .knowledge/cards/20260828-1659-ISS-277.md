## Reproduction (3/3, cold start each time)

Confirmed CONFIRMED — reproduced on all 3 attempts, each from a fresh
`page.goto` (not a soft re-click), signed in as `qa-admin`, run
`b9feac1c-ec21-4531-8ba7-bb391786993e`:

- **Cycle 1** — fresh nav to `/runs/{id}/steps/ppt-brief-analyst`: Steps tab
  selected in the tablist, but content pane shows only the bare 4-button
  lane list (Presentation Strategist Agent, Deck Engineer Agent, Deck QA
  Agent, PPTX Code Generator). No breadcrumb, no expanded detail.
- **Cycle 2** — fresh nav to `/runs/{id}/steps/ppt-composer` (different
  agent id, cold nav via an intermediate `/dashboard` visit): identical —
  bare list, no detail, no breadcrumb.
- **Cycle 3** — fresh nav to `/runs/{id}/steps/ppt-brief-analyst` again
  (cold, via `/dashboard` first): bare list again. Then manually clicked
  the "Presentation Strategist Agent" row in that list: the breadcrumb
  "Steps / Presentation Strategist Agent" and the full detail pane
  (Reasoning toggle, Specification JSON, "Full input prompt 7,804 chars",
  Agent output) rendered correctly — but `location.href` was verified via
  `page.evaluate('() => location.href')` to be byte-identical to the URL
  before the click: `http://localhost:3000/runs/b9feac1c-ec21-4531-8ba7-bb391786993e/steps/ppt-brief-analyst`.
  The in-page selection never syncs the URL, so this state is not
  reloadable/shareable/bookmarkable.

## Page / route / component

- Page: Completed run — Steps tab, single-agent detail pane
- Route: `/runs/{id}/steps/{agentId}` (`ParsedView` screen `run-steps-agent`,
  `frontend/src/lib/routes.ts:69-70` builds it, `:311-312` parses it back
  into `{ screen: 'run-steps-agent', runId, agentId }` — the agentId IS
  parsed correctly)
- Component: `frontend/src/app/[...view]/page.tsx` — `reopenTabFor()`
  (`page.tsx:214-224`) maps `run-steps-agent` → `"thinking"`, the same tab
  name as plain `run-steps`, discarding `parsedView.agentId` entirely. That
  string alone is handed to `runTabDeepLink.requestOpenTab(openTab)`
  (`page.tsx:3175`, `:3223`) via the `useTabDeepLink` hook, which opens the
  Steps tab but has no channel to also request a specific agent be
  selected within it. `PreviewPanel`'s Steps view is left to its own
  default (unselected) state.

## Root cause

`reopenTabFor(screen): "thinking" | "files" | "workspace" | "audit" |
undefined` (`page.tsx:210-224`) is typed to return only a tab name, so the
`agentId` that `parseView` already extracted for `run-steps-agent`
(`routes.ts:311-312`) is silently dropped at the one call site that could
use it — there is no plumbing from `ParsedView.agentId` through
`useTabDeepLink`/`requestOpenTab` into the Steps lane's own
selected-agent state. The manual in-page click that DOES select an agent
(confirmed working, Cycle 3) writes only to component state, never calling
`router.push`/`replace` to reflect the selection in the URL — so the two
gaps compound: deep-linking IN doesn't select, and selecting doesn't
deep-link OUT.

## Expected vs actual

- **Expected:** a fresh nav, reload, or bookmarked `/runs/{id}/steps/{agentId}`
  opens directly to that agent's detail pane (matching a manual row click),
  since the app itself both defines this URL shape (`routes.ts:69`) and
  links to it (breadcrumb, "Answer in Steps" chat buttons per the BUG-ID
  register entry).
- **Actual:** the `{agentId}` segment is inert on every load path (real id,
  different real id, or a nonexistent id — all three render identically per
  the register's step 6); only an in-page click reveals detail, and that
  click never updates the URL, so the detail state cannot be reloaded,
  shared, or bookmarked.

## 3-analyzer addendum (2026-08-28)

Root cause confirmed and traced one layer deeper than this card's own
evidence: the dropped `agentId` has no channel anywhere downstream of
`reopenTabFor`, not just at that one function. `TabDeepLinkTarget`
(`frontend/src/hooks/useTabDeepLink.ts:28-33`) carries only `{tab, nonce}`;
`PreviewPanel`'s deep-link consumer effect (`PreviewPanel.tsx:814-837`)
reads only `.tab` and calls `setActiveTab`; `AgentThinkingTab` is invoked
with no `agentId`-shaped prop at all (`PreviewPanel.tsx:1360-1384`,
`AgentThinkingTabProps` at `AgentThinkingTab.tsx:22-46`); and
`selectedAgentId` (`AgentThinkingTab.tsx:84`) is plain `useState<string |
null>(null)` with no prop-driven initializer. The fix therefore belongs in
this whole chain, not a patch to `reopenTabFor` alone — widen
`TabDeepLinkTarget`/`requestOpenTab` (the one seam every deep-link producer
already routes through, per this file's own doc comment) to optionally
carry an agent id, thread it through `PreviewPanel` into a new
`AgentThinkingTab` prop, and seed `selectedAgentId` from it.

Two siblings filed from this deeper trace:
[ISS-386](20260828-2228-ISS-386.md) (`routes.runStepsAgent` has no
`version` param, unlike its four sibling builders) and
[ISS-387](20260828-2228-ISS-387.md) (the same missing-history-sync
mechanism this card names for the OUT direction also breaks the browser
Back button, confirmed by grep: no `router`/`window.history` call exists
anywhere in `AgentThinkingTab.tsx`, `StepsOverviewSpine.tsx`, or
`AgentDetailPanel.tsx` except one unrelated divert-link push).
