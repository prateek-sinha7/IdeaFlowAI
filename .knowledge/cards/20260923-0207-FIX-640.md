# FIX-640

The shared root cause behind **QA-PS-035, QA-PS-036, QA-PS-038, QA-PS-041 and
QA-PS-046** (`LEDGER.md` / `BUGS.md`). One change, applied once.

## The decision this implements

The user chose **option (a)** on 2026-09-23 (recorded 01:34), for all five
escalations (`ESCALATIONS.md#qa-ps-035` and its four siblings): the app shell's
single `GET /api/runs?limit=50` and single `GET /api/workflows` per page are
intended — they feed AppHeader's "N Running" badge and RunConnectionProvider's
SSE live-run re-attach. Remove only the waste. Each bug's "zero run-list /
workflows calls" test is re-scoped to "at most one". The analysis is
`reports/20260923-escalation-group-runlist.md` §1 and §2.

## What was wrong

Two waste mechanisms rode along with the intended shell traffic:

1. **Two owners of one list.** `page.tsx` fetched `getWorkflows(token, { limit: 50 })`
   for the header, and `RunConnectionProvider.refreshLiveRuns` fetched the same
   list for the reattach, derived `autoIdsRef` and threw the rows away
   ([FIX-617](20260922-1935-FIX-617.md) then skipped that query on tabs owning no
   runs, *because* the rows were discarded). `api.ts`'s single-flight joins only
   exactly-concurrent callers, and the two sites ran ticks apart, so both hit the
   network whenever the tab owned runs.
2. **A home-only seed fetched on every route.** The `signedIn` listener dispatched
   `fetchRecentRuns()` (`runs?limit=6`), and `signedIn` fires from the `[...view]`
   catch-all on every route, yet `state.global.recentRuns` has one reader,
   `HomeLaunchGrid`, which renders only on the home view.

## Root cause (pre-fix `file:line`)

- `frontend/src/app/[...view]/page.tsx:1056-1100` — the `recentRuns` fetch effect,
  its per-mount `recentRunsRequestedRef` (`:843`, [FIX-630](20260922-2115-FIX-630.md)),
  the module-scope `recentRunsSnapshot` (`:118`, [FIX-632](20260922-2221-FIX-632.md))
  and the snapshot's keep-fresh effect (`:1102-1113`).
- `frontend/src/providers/RunConnectionProvider.tsx:305-331` — `refreshLiveRuns`:
  FIX-617's empty-tab skip at `:312-316`, rows discarded after the filter.
- `frontend/src/store/listenerMiddleware.ts:54-56` — `fetchRecentRuns()` in the
  `signedIn` effect.
- Consumers, unchanged: `HomeLaunchGrid.tsx:148` (only reader of the Redux seed);
  `AppHeader.tsx:188/200/328/371` (the badge, fed by the `recentRuns` prop).

## What changed, and why there

1. **`RunConnectionProvider.tsx`** — the single owner, because it sits above the
   router and already ran the query. `refreshLiveRuns` keeps the rows as
   `recentRuns` and exposes them on the context with `recentRunsLoaded` (ISS-757's
   "settled" flag), `setRecentRuns` (page.tsx's write paths) and `loadRecentRuns`
   (fetch unless already loaded or in flight for the current token). It now
   queries even when the tab owns no runs — FIX-617's skip is removed, since the
   badge depends on the rows; an empty tab-owned set simply attaches nothing.
   Identity: the list is keyed by token — a different token empties it
   synchronously before its fetch, a response for a no-longer-current token is
   dropped, and a failed first load is forgotten so the next ask retries it (the
   three rules FIX-632's snapshot held). Boot goes through `loadRecentRuns`, so
   page.tsx's ask (a child effect, which runs first) and the boot share one fetch.
2. **`page.tsx`** — the fetch effect, `recentRunsRequestedRef`, `recentRunsSnapshot`
   and the keep-fresh effect are deleted. `recentRuns` / `recentRunsLoaded` /
   `setRecentRuns` come from `useRunConnection()`, and a mount effect calls
   `loadRecentRuns()`. Every write path is unchanged — the SSE status patches
   (`patchRecentRunStatus`), the `pipeline_diverted` refetch and the post-launch
   refresh (FIX-195) — they now write provider state, which survives the remount
   a `router.push` causes. That is [ISS-848](20260922-2138-ISS-848.md)'s property,
   now kept without a module-scope snapshot. FIX-630's `/create/*` gate went with
   the effect: the provider's boot fetch runs on every route, so there was
   nothing left for it to spare. FIX-633's comment lost its now-dangling
   `recentRunsSnapshot` comparison; its guard is untouched.
3. **`listenerMiddleware.ts`** — `signedIn` no longer dispatches `fetchRecentRuns()`.
   `fetchWorkflows()` is untouched, so ISS-232's parallel preload is intact.
4. **`HomeLaunchGrid.tsx`** — dispatches `fetchRecentRuns()` on its own mount,
   with the listener's guard (`!== "loading" && !== "succeeded"`) read from the
   store at dispatch time.
5. **`globalSlice.ts`** — two comments only (they named the old preload owner).

Not touched: the ISS-232 `/api/workflows` preload, and the three
mutation-observing `getWorkflows` calls (divert, post-launch,
`WorkflowHistory.tsx`), per `api.ts:404-406`. No backend change.

Post-fix floor per cold load, per report §5: `/settings/profile`, `/analytics`,
`/workflows`, `/workflows/new` — at most one `/api/runs` and one
`/api/workflows` (the five re-scoped tests pass). Exact list observed on one
cold catch-all load, `/workflows/{id}`, in the QA-PS-041 run's ISS-813
capture: `runs?limit=50` ×1, `runs?limit=6` ×0, `/api/workflows` ×1,
`/api/auth/me` ×1.
