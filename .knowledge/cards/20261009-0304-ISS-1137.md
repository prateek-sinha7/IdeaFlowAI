# ISS-1137

Register bug `QA-KB-106` (SMOKE-1, Medium; `LEDGER.md`, `BUGS.md#qa-kb-106`). Route `/workflows/{id}/canvas` -> `POST /api/runs`. Analysed 2026-10-09 on branch
`feat/stale-bug-fixes`. `page.tsx`, `DashboardLayout.tsx` and `ComposerPage.tsx` carry uncommitted edits from other lanes, so line numbers can sit a few off HEAD
(`cc39cc852`). [ISS-969](20261002-0338-ISS-969.md) holds the first derivation of the `.catch` half (its `page.tsx:4400-4413` is now `:4454-4467`); this card adds the
second half (why Run once stays dead), the current lines, and the blast radius. The report calls the handler `onLaunch`; in the code it is `onStartPipeline`.

**Confidence.** The mechanism is CONFIRMED: every line below was opened and read. The outcome was OBSERVED 3/3 by the validator on 2026-10-09
(`evidence/qa-kb-106/01..04`). What is INFERRED is in the second-to-last section, with what would settle it.

## Condition

A launch on the Composer canvas that `POST /api/runs` refuses after the client checks pass (brief of at least 3 characters, at least one agent, design picked): 503
`model_provider_unavailable` (`run_commands.py:2960-2968`), 403 `tier_not_entitled` (the canvas has no tier lock, [ISS-474](20260829-0112-ISS-474.md)), 422
`invalid_workflow_manifest` / `workflow_unsatisfiable` / `no_agents_selected`, 400 `empty_brief` / `invalid_agent_ids`. All of them come from `_reject(...)`:
`HTTPException(detail={"error": <text>, "code": <code>, "recoverable": <bool>})` (`run_commands.py:2554-2575`).

## Expected vs actual

- **Expected** (`BUGS.md`): the user sees the backend's message in a toast or inline, and Run once is enabled again.
- **Actual** (observed 3/3 with 503, 403 and 422 stubs on `/workflows/ex_A1_loop/canvas`): exactly one POST, URL unchanged, no alert/status/toast element and none of the
  backend text anywhere in the page, the typed brief still in the box, and "Run once" greyed out (it was enabled before the click). The red "1 Issue" pill in the
  screenshots looks like the Next dev overlay reporting the dev-only `console.error` below; it is not product UI.

## Root cause: a launch's outcome has nowhere to go

One mechanism, two symptoms. `onStartPipeline` is fire-and-forget, so the refusal is visible only inside the handler that swallows it, and the panel that latched itself on
the click is never told.

1. `ComposerPage.handleRunOnce` latches before calling out: `submittingRef.current = true; setIsSubmitting(true);` (`ComposerPage.tsx:1040-1042`), then calls
   `onRun(...)` (`:1213`, `:1222`) and ignores the result. `onRun` is typed `=> void` (`:133-138`).
2. The layout's lambda (`DashboardLayout.tsx:3243-3248`) calls `onResetPipeline()` then `onStartPipeline(...)` and returns nothing; the prop is `=> void`
   (`DashboardLayout.tsx:113`).
3. The handler (`page.tsx:4310`) ends `void Promise.resolve(startPipeline(...)).then(...).catch(...)` (`:4386-4467`). It returns nothing, by construction.
4. `useWorkflow.startPipeline` returns `runConnection.sendCommand(null, payload)` (`useWorkflow.ts:128`), which on a non-2xx does
   `throw new ApiError(res.status, detail)` (`RunConnectionProvider.tsx:520-528`). So the refusal does reach the `.catch`.
5. The `.catch` (`page.tsx:4454-4467`) is the only handler: `launchPendingRef.current = false; resetPipeline(); if (process.env.NODE_ENV !== "production") {
   console.error("Pipeline launch failed:", err); }`. In production it is silent. Its comment says the 503 has its own seam and "this handler's only job is to recover
   the local UI state".
6. `ApiError`'s constructor has two UI seams: 503 `host_capacity_exhausted` (the `ServiceBusyProvider` modal) and 403 admin-MFA (`api.ts:288-309`). A launch refusal
   matches neither.

### Why Run once stays disabled

FIX-614's latch has no release, and the reason it gave for needing none is wrong. `ComposerPage.tsx:1035-1039` says "Nothing clears it: `onRun` reaches startPipeline, which
flips isRunning=true synchronously, and the surface auto-transitions to mainView="execution" — this page unmounts whether or not the POST itself succeeds"
([FIX-614](20260922-1850-FIX-614.md) says the same; `DashboardLayout.tsx:3241-3242` and `IdeaInputPage.tsx:1598-1604` repeat it). It does not unmount:

- The layout leaves the composer when ITS `pipelineState.isRunning` is true (effect `DashboardLayout.tsx:836-846`, deps `:920`). That prop is
  `displayedPipelineState = runStore.viewed.pipelineState` (`page.tsx:4210`, `:4249`; in the tree since `887ccfe96`, 2026-08-21, a month before the latch), not the hook
  state that `startPipeline` writes (`useWorkflow.ts:72-73`).
- The bridge from the hook state into the store returns while there is no run id: `const runId = pipelineState.pipelineRunId; if (!runId) return;` (`page.tsx:2396-2397`),
  then two more guards on the building and viewed run ids (`:2398-2399`). A refused launch never gets a run id, so the store never reports `isRunning` and the view never
  changes.
- The canvas `onRun` lambda has no `setMainView("execution")` (compare `handleRunPipeline`, `DashboardLayout.tsx:1786`).
- So the same `ComposerPage` instance stays mounted (observed: the typed brief is still there, and `briefText` is plain `useState("")`, `ComposerPage.tsx:276`). In that file
  `submittingRef` is written only at `:1040-1041` and `setIsSubmitting` only at `:1042`; nothing sets either back. `disabled={!onRun || isSubmitting}` (`:1371`) and the
  Cmd/Ctrl+Enter path (`:1519` -> `handleRunOnce` -> `if (submittingRef.current) return;` at `:1040`) are both dead until a reload, or navigating away and back.

The Save button in the same file releases its latch in a `finally` and on every guard exit (`isSavingRef`, `ComposerPage.tsx:850-879`, `:986`) and reports errors through
`saveError` (`:984`, banner at `:1696-1700`). Run once copied the latch with neither half. FIX-614 even wrote the condition down: "If `onRun` ever gains a failure path that
returns the user to these screens, this latch needs a release." The failure path was always there. Its "the ISS-767 run's POST returned `400` and the guard still behaved,
exactly one POST sent" is this bug seen from the other side: one POST because the button never came back.

## Blast radius (grepped)

- **One launch POST in the whole frontend.** `grep -rn "sendCommand(null" frontend/src` (non-test) finds only `useWorkflow.ts:128`; `startPipeline` has one caller,
  `page.tsx:4387`, inside the one handler. (`app/workflow/page.tsx:105` passes a stub `handleStartPipeline` that never POSTs.)
- **17 call sites feed that handler** (`grep -n "onStartPipeline(" DashboardLayout.tsx`): revision handlers `:1242, :1254, :1274, :1286`; start-on-connect `:1414`; staged
  wizard launches `:1482`, `:1547`; `handleRunPipeline` `:1841` (the Input panels); chain `:2028`; history re-run `:2121`; clarify relaunches `:2211`, `:2251`; the
  RunChatLane twins `:3085, :3095, :3105, :3115`; composer Run once `:3246`. All 17 are refused silently (the message half).
- **Two panels latch on a launch** (`grep -rln "submittingRef" frontend/src`, minus `login/page.tsx` and `SecuritySection.tsx`, which are not launches): `ComposerPage`
  (this bug) and `IdeaInputPage` ([ISS-1138](20261009-0304-ISS-1138.md)).
- **The wizards** (`/create/ppt`, `/create/prototype`) reach the same `.catch` and have no form left to return to ([ISS-1139](20261009-0304-ISS-1139.md)). The handlers that
  register a notification before the POST leave it running ([ISS-1140](20261009-0304-ISS-1140.md)).
- **The one refusal that has a UI leaves the button dead too.** `ServiceBusyProvider` says "You can try again now." (`ServiceBusyProvider.tsx:121`) while the composer latch is
  still set. INFERRED: the validator drove 503 `model_provider_unavailable`, 403 and 422, not the capacity gate.
- **A launch that yields no run id is the same dead end without an exception.** `sendCommand` returns `null` for no token (`RunConnectionProvider.tsx:493`), an
  unparseable 2xx body (`:632-634`) or a 2xx body with neither `run_id` nor `id` (`:597`). The `.then` else-branch is `else { launchPendingRef.current = false; }`
  (`page.tsx:4453`): no message, no reset, latch still set. Any fix has to treat a null id as a refusal too. It is reachable in practice only when another tab clears the
  token; no separate card.
- **Not traced:** the `.catch` calls `resetPipeline()` with no `thisLaunchSeq` guard, while the `.then` has one (`page.tsx:4430`). What a late refusal of an older launch does
  to a newer launch was not followed through the store bridge, so no card is filed for it.

## Where the fix belongs

- **The message: once, at the outcome handler** (the `.catch` at `page.tsx:4454-4467` plus the null-id else at `:4453`), not in 17 call sites; 15 of them have no form to put
  an inline message in. The established pattern for "one seam, every call site" is a module-level pub/sub in `api.ts` (`onCapacityRejected`, `:207-230`) with one app-level
  subscriber (`ServiceBusyProvider`). A launch refusal cannot be recognised in the `ApiError` constructor (it does not know it is a launch), so the publisher is the `.catch`.
- **The latch: released on refusal only, in the two panels that own one** (`ComposerPage.tsx:1040`, `IdeaInputPage.tsx:1605`). The smallest channel is for `onStartPipeline`
  to return its promise (`DashboardLayout.tsx:113`, `ComposerPage.tsx:133-138`, `IdeaInputPage.tsx:792`, and both `onRun` lambdas return it), and for each panel to `.catch` ->
  release the latch + its existing inline banner (`saveError`).
- **The text is `ApiError.detail.error`, not `ApiError.message`.** `errorMessageFromDetail` returns null for an object (`api.ts:169-176`), so `message` is
  `JSON.stringify(detail)` (`api.ts:282`), e.g. `{"error":"...","code":"tier_not_entitled","recoverable":false}`. [ISS-969](20261002-0338-ISS-969.md)'s "present
  `ApiError.message`" would print raw JSON for every `_reject` body.
- Correct the three comments that say the page unmounts (`ComposerPage.tsx:1035-1039`, `IdeaInputPage.tsx:1598-1604`, `DashboardLayout.tsx:3241-3242`).

## Fixes that would break something

  double-click window FIX-614 closed; `tests/integration/e2e/suites/04_composer_canvas/test_iss767_run_once_double_click_guard.py` goes red. Release on refusal only; the
  success path keeps the latch until the page unmounts.
- A catch in each of the 17 call sites, or a per-panel copy of the message logic (INV-12: one definition).
- Showing `err.message` (raw JSON, above).

- Hand-written paths: navigation goes through `routes.ts`.
- `page.tsx` is pinned by source-lock tests that slice on text anchors (`freshLaunchTranscriptReset.source.test.ts`: `if (!isRevision) {` ... `// For revisions, keep existing
  content`). Keep those anchors when restructuring the handler. No test anchors on the `.catch` text itself.

## Fix status 2026-10-09 (5-fixer, applied, NOT yet verified)

The fix is in the working tree, uncommitted. The e2e has not passed yet, so nothing here is resolved and no FIX card exists yet. Files:
`frontend/src/app/[...view]/page.tsx`, `frontend/src/lib/api.ts`, `frontend/src/components/layout/DashboardLayout.tsx`,
`frontend/src/components/workflow/composer/ComposerPage.tsx`, `frontend/src/components/workflow/IdeaInputPage.tsx`.

- `page.tsx` `onStartPipeline` returns its outcome: the run id, or null when the launch was refused. It never rejects. A null run id throws into
  the `.catch`, which resets, shows the reason once (`setLaunchError(launchRefusalMessage(err))`) and resolves null. Its dev-only log is
  `console.warn` (see the last point).
- `api.ts` `launchRefusalMessage(err)` returns `detail.error` for a `_reject` body, the `msg` fields of a 422 list, or a string detail. Anything else
  gets a generic line. It returns null for `host_capacity_exhausted`, which `ServiceBusyProvider` already shows.
- `DashboardLayout.tsx` shows the `launchError` banner (`role="status"`, Dismiss) beside the connection banners, so all 17 `onStartPipeline` sites
  get the message. The prop is typed `Promise<string | null>`, and the composer `onRun` lambda and `handleRunPipeline` return it.
- `ComposerPage.tsx` and `IdeaInputPage.tsx` release the FIX-614 latch when the outcome is null. They keep it on a run id, while the launch is
  pending, and when `onRun` returns nothing.
- Deviation from "Where the fix belongs": the panels do not also write the reason into their `saveError` banner. One banner shows it once, and a
  second copy of the same text would fail the test's `get_by_text` in Playwright strict mode.

Observed: frontend `tsc --noEmit` reports 0 errors outside test files. eslint findings per touched file are identical to HEAD. 20 existing vitest files
