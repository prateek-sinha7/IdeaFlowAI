# `surface/` — the read layer

Everything here is **generated**. `README.md` is the single exception: it describes
the generators, so it cannot be one of their outputs.

Nothing in this folder is a source of truth. Delete every generated file, run
`python3 scripts/knowledge/build_index.py`, and they come back identical apart from
the build timestamp in each header — verified, not assumed. Every one is a pure
function of `.knowledge/cards/` plus four checkable inputs.

That property is the point. A hand-maintained index drifts, and a confident stale map
is worse than no map.

---

## Why this layer exists

`.planning/` holds 16.5 MB across 1064 files. The registers mix four kinds of
knowledge with different lifecycles — durable rules, unbounded history, current state,
and specs — in single files, so reading any of it means reading all of it.
`IMPLEMENTATION-REGISTER.md` alone is 982 KB, about 240 K tokens. Per-task relevant
fraction is under 2%.

The fix is not a smaller register. It is a **three-tier split** where only the cheapest
tier is ever loaded by default:

| Tier | What | Size | Read into context |
|---|---|---:|---|
| 1 | `.planning/**` — the untouched registers | 16.5 MB | **never** wholesale |
| 2 | `.knowledge/cards/` — 532 cards, one per record | ~750 KB | only via `ctx.py --show` |
| 3 | **this folder** | ~48 KB loaded | **yes, every session** |

`INDEX.md` + `RULES.md` ≈ **11.6 K tokens** for total awareness of the project's
history, against ~383 K for the auto-injected registers. The remaining files here are
read on demand or by tools only.

## What each file is

| File | Generated by | Derived from | Read it |
|---|---|---|---|
| `ARCHITECTURE.md` | `build_architecture.py` | `STATE.md` frontmatter · `pyproject.toml` contracts · dirs on disk · decision cards | **first** |
| `ENTRY.md` | `build_surface.py` | card type + area counts | when the gate redirects you |
| `INDEX.md` | `build_index.py` | the 241 primary cards | every session |
| `RULES.md` | `build_index.py` | decision cards, `accepted` + `proposed` | every session |
| `CATALOG.md` | `build_index.py` | the 291 secondary cards | on demand |
| `index.json` | `build_index.py` | every card's frontmatter | tools only |
| `links.json` | `build_index.py` | `files:` / `relates:` / `produces:` fields | tools only |
| `stamp.json` | `build_index.py` | frontmatter hash + source config | `check.py` only |

### `ARCHITECTURE.md` — the present

The only file here that is not history. Milestone and phase in flight, the four
import-linter contracts CI enforces, the 18 registered workflows, the ADRs in force,
and a **gaps section listing what it cannot know** — printed on every build rather
than discovered later.

Its stage block is why `.planning/STATE.md` is *excluded* from the card store rather
than carded: STATE.md changes every session, so a card would freeze it, while
regenerating keeps it current by construction.

### `ENTRY.md` — the redirect target

What the `PreToolUse` read-gate serves instead of a register. One entry point for all
nine gated files; the register you actually asked for is named in the hook's
`additionalContext`, so the file itself does not need to vary. There used to be nine
near-identical per-register stubs — they carried no information the context message
did not.

### `INDEX.md` / `CATALOG.md` — the split that keeps tier 3 cheap

`INDEX.md` carries the **primary** types (`decision`, `fix`, `issue`, `phase`) — 241
cards, one line each. `CATALOG.md` carries the **secondary** types (`bug`, `test`,
`req`, `doc`, `task`) — 291 cards, not loaded by default but fully searchable through
`ctx.py`.

The split is a budget decision, not a quality judgement. Loading all 532 lines would
double the always-on cost to buy pointer cards that mostly say "this document exists
at this path". **If `INDEX.md` has no answer, search before concluding nothing
exists** — the answer is often in `CATALOG.md`.

### `index.json` — filtering, not searching

```json
{ "count": 532, "generated": "...",
  "facets": { "type": {...}, "status": {...}, "area": {...} },
  "fields": ["id","type","status","date","area","files","summary","source","path"],
  "entries": [ ... ] }
```

`facets` carries value→count maps so a tool can offer filters without scanning all 532
entries. `path` on each entry points at the card file, which is what `--show` follows.

### `links.json` — the graph, such as it is

```
by_file        157 paths  → the cards that touch each
by_area         15 areas  → the cards tagged with each
rules_by_file    1 path   → the decisions binding a file      ← thin, see below
edges           32        → relates / produces / derived_from
backlinks       30        → the reverse of edges
```

Walked out of card frontmatter by a few dozen lines of Python. No graph database, no
embeddings — at 532 nodes that would buy bi-temporal reasoning nobody needs, and
supersession is one field. **File paths are the join key** to the code graph
`ba-ready` already builds, so "what must I know before touching this, and what breaks
if I do" is answerable from two cheap indexes with no shared store.

`rules_by_file` has exactly one entry because only one ADR exists. That number is the
honest measure of how much `RULES.md` is currently worth.

## Rebuilding

```bash
python3 scripts/knowledge/build_index.py     # regenerates every file above
python3 scripts/knowledge/check.py           # 0 clean · 1 warnings · 2 broken
```

`build_index.py` calls `build_surface.py` and `build_architecture.py` itself, so there
is one command, not three. It takes about two seconds and involves no model call —
this layer is a projection, and projections are cheap.

Run it after **any** card change. `check.py` will tell you if you forgot.

## The drifts, and which are detected

Three ways this layer can lie. All three are reported rather than silently tolerated.

| Drift | Detected by | Why it happens |
|---|---|---|
| index vs cards | `frontmatter_sha1` in `stamp.json` | a card was added or hand-edited without a rebuild |
| architecture vs `STATE.md` | rendered date vs `last_updated` | **invisible to the hash** — STATE.md is not a card, so cards can be perfectly fresh while the stage is a milestone behind |
| cards vs code | every `files:` path stat'd | a file was renamed or deleted; the card's claim can no longer be verified |
| cards vs registers | source ref + highest id extracted | someone appended to a register the old way |
| coverage | every `.planning/` file carried or excluded | a new planning file appeared and nobody carded it |

`cards vs code` currently warns on 10 of 387 paths. Most are
`backend/app/api/websocket.py`, cited by eight fixes and deleted in the websocket→SSE
migration. Those cards are history, not guidance — that is the correct state, not a
bug to fix.

## Reading this layer without spending the registers

```bash
python3 scripts/knowledge/ctx.py "<symptom words>"   # search everything
python3 scripts/knowledge/ctx.py --for <path>        # rules + history for a file
python3 scripts/knowledge/ctx.py --rules <area>      # rules in force
python3 scripts/knowledge/ctx.py --show FIX-122      # one card, full prose
```

`ctx.py` searches `index.json` and `links.json` and nothing else. It opens a card file
only for `--show <ID>`, and reaches `.planning/` only when that card's body is not
stored locally — `records.resolve_body()` then extracts the one section it needs, never
the whole register.

`RULES.md` lists `proposed` decisions alongside `accepted` ones, flagged with their
status. A rule under discussion still constrains what you should write, and hiding it
until it is ratified is how a decision gets re-litigated in code.

`--for <path>` before editing a file is the cheapest way to find the rule you are
about to break.

## What this layer is not

- **Not evidence about current behaviour.** Cards describe the code as it was when the
  entry was written. When a card and the source disagree, **the source wins** and the
  card is stale.
- **Not a replacement for the registers.** `.planning/` is untouched and remains the
  source of truth. Card bodies are not even copied — each card anchors back to its
  register and resolves prose on demand, which is why `.planning/` is load-bearing.
  `compact.py --materialize` writes the bodies in first if that ever needs to change.
- **Not complete on rules.** One decision card exists against 196 fixes and bugs.
  Roughly one fix in five establishes a rule, so most of what this project actually
  follows is still implicit in fix prose. `knowledge-consolidate` is the loop that
  promotes them, and it needs human approval by design.

See `../docs/schema.md` for the card format, `../docs/ENFORCEMENT.md` for the read-gate,
and `../docs/PLAN.md` for why it was built this way.
