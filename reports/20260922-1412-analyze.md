## QA-SG-004 — ANALYZED

Switching between parallel workflow runs from the notification bar is unreliable, sometimes
fails or delayed.

- **Root cause (CONFIRMED):** `NotificationPanel`'s live-run row click
  (`DashboardLayout.tsx:2757-2791 onViewResults`) fires `page.tsx`'s `handleSwitchToLiveRun`
  without awaiting it, then unconditionally calls `router.push(routes.runStream(targetRunId))`.
  `router.push` under the shared `[...view]` catch-all remounts `page.tsx` (confirmed by an
  existing dated comment at `page.tsx:3374-3378`, independently at `DashboardLayout.tsx:529`),
  flipping `useRunStateStore`'s `mountedRef` to `false` mid-flight (`useRunStateStore.ts:335`) so
  the in-flight `getRunEvents` replay is silently redirected to a throwaway object
  (`useRunStateStore.ts:392-397,404-410`) instead of the real store. Recovery then depends on the
  freshly-mounted instance's own independent T11 replay effect (`page.tsx:3458-3608`) — an
  uncoordinated second fetch, which is the "sometimes delayed / works on retry" symptom. The
  rarer "URL never changes at all" variant is explicitly marked **INFERRED**, not settled by a
  code read — needs live `router.push` instrumentation.
- **Blast radius:** the same unguarded "fire async switch, then unconditional push, no
  re-entrancy guard, no cross-remount guard" shape exists on 3 other callers never tested against
  a real remount — the header's "N Running" dropdown/single badge (`onGoToPipeline`), and
  `onSelectWorkflowRun`/`handleSelectWorkflowRun` (general run-reopen, zero `trackedRunIdRef`
  guard anywhere in its ~440-line body).
- **Proposed fix:** belongs in the one shared function every caller funnels through,
  `handleSwitchToLiveRun` (`page.tsx:2706-2797`) — not scattered per-caller patches, mirroring
  FIX-519's own stated precedent. Must preserve FIX-519's and FIX-523's locked constraints.
- **Cards:** [ISS-775](.knowledge/cards/20260922-1330-ISS-775.md) (root, updated with Root
  cause / Blast radius / Fix), [ISS-778](.knowledge/cards/20260922-1600-ISS-778.md) (sibling,
  header dropdown/badge, INFERRED), [ISS-779](.knowledge/cards/20260922-1602-ISS-779.md)
  (sibling, `onSelectWorkflowRun`/History reopen/Home, INFERRED),
  [ISS-780](.knowledge/cards/20260922-1604-ISS-780.md) (sibling, ISS-657's guard is
  instance-local, INFERRED).
- **Tests:** none written this phase — analyze only. Note left on the root card: unit tests

## QA-SG-014 — ANALYZED

Custom workflow output generates markdown instead of the selected format, always produces .md
files.

- **Root cause (CONFIRMED):** the custom-workflow composer's "Output format" control (and the
  `__deliverable__` override it sends through `_apply_selections`) only ever renames
  `DeliverableSpec.name`'s file extension; no capability in the deliverable-resolver layer —
  `streamed_text`'s resolver (always returns the last agent's raw text verbatim) or
  `single_file`'s unwritten-file fallback (same raw text when no step wrote the declared
  filename) — ever converts an agent's output into the picked format. Every `streamed_text`
  custom run, and any `single_file` run with no matching writer agent, always emits raw
  markdown/plain text under whatever extension the user chose.
- **Blast radius:** the composer's Output-format select (`CanvasView.tsx:1895-1964,2592-2601`)
  and its read-only render in `AgentsPopup.tsx`; `ComposerPage.tsx:1048`'s
  `effectiveDeliverable`; the separate `IdeaInputPage.tsx` launch surface (no Output Format UI
  at all, live-mounted at `DashboardLayout.tsx:3062`); the shared `_apply_selections` seam
  (`engine.py:12767-12951`); `build_flat_payload`'s `streamed_text` branch
  (`engine.py:1328-1468`); the `StreamedTextResolver`/`SingleFileResolver`/`_mimetype`
  capability files.
- **Proposed fix:** belongs in the `("deliverable", strategy)` capability layer, not a per-page
  patch — either give the resolver layer a real format-conversion step, or stop the composer
  from promising a conversion no resolver performs (collapse `streamed_text`'s format options to
  `.md`, gate `single_file`'s `.html` option on an actual writer step).
- **Cards:** [ISS-770](.knowledge/cards/20260922-1305-ISS-770.md) (root, confirmed),
  [ISS-776](.knowledge/cards/20260922-1557-ISS-776.md) (sibling, `single_file` + HTML,
  INFERRED), [ISS-777](.knowledge/cards/20260922-1558-ISS-777.md) (sibling, IdeaInputPage has no
  Output Format control, INFERRED).
- **Tests:** none written this phase. Note left for the 4-test-writer: pure backend unit-test
  target — compile the `custom` workflow, call `_apply_selections(compiled,
  {"__deliverable__": {"strategy": "streamed_text", "name": "output.html"}})`, assert
  `StreamedTextResolver.resolve`/`default_mimetype` still returns markdown/`text/markdown`
  despite the `.html` name.
- **Invariants at risk:** a naive fix that hardcodes conversion logic keyed on
  `pipeline_type == "custom"` inside the engine (rather than extending the registered
  `("deliverable", strategy)` capability or `DeliverableSpec`) would violate INV-1
  (kernel stays workflow-agnostic) and the "every capability resolves through
  `CapabilityRegistry.resolve(kind, name)`" invariant.
