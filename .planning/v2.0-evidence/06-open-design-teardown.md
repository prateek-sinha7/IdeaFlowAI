# open-design (`nexu-io/open-design`) — Chat Panel Teardown & Adoption Verdict

## Bottom line up front

**Do not adopt open-design's chat panel wholesale, and do not treat it as "better than reviving the in-repo kit." It is a 14,000-line, copy-only, product-branded monolith styled in a global-CSS model your product doesn't use, riding a transport and attachment model built for a local desktop daemon rather than your server WebSocket.** But it is an excellent *reference implementation*: its architecture (durable event-log + replay-on-reconnect, a normalized agent-event union feeding an events→blocks renderer, a clean deep-link-into-tabs seam) is philosophically the same as your bespoke protocol, and there are ~8 isolated, dependency-light mechanisms genuinely worth copying. My recommendation is unchanged from your default plan: **revive and own your in-repo kit, and cherry-pick specific open-design mechanisms and patterns into it.** Details and the specific pieces to steal are below, all verified against the clone.

One caveat on confidence: everything here is from reading the source of a shallow clone (commit `02c6841`, last push 2026-07-07). I did not build or run the app, so runtime behavior (e.g. exact streaming smoothness) is inferred from the code, not observed.

## 1. Repo facts

- **Popularity / activity:** 75,786 stars, 8,647 forks, 531 open issues (GitHub API). Created 2026-04-28, last push 2026-07-07 (today) — roughly ten weeks old, ~2,660 commits. Very high velocity.
- **Bus factor:** Moderate, org-backed (not a solo project). Top contributors by commits: `lefarcen` (307), `PerishCode` (140), `cursoragent` (116 — a bot/AI agent), `pftom` (115), then a long tail. The lead has ~2× the next human; healthy but with a clear primary author.
- **Tech stack (the web app, `apps/web/package.json`):** Next.js 16.2.6, **React 18.3.1** (you are on React 19 — a version gap), **Tailwind CSS v4 (4.3.0) but effectively unused** (see §6), **motion 12.40.0** (matches your animation lib), Lexical 0.36 (composer), micromark + shiki (markdown/highlight, *not* react-markdown), `@anthropic-ai/sdk` + `openai` (BYOK). State is plain React hooks — no Redux/Zustand/Jotai.
- **Layout:** pnpm monorepo. `apps/{web,desktop,daemon,...}`, `packages/{components,contracts,agui-adapter,...}`. It is a **product** (a local-first desktop app, "the open-source Claude Design alternative"), not a library or template.
- **Consumability — the decisive fact: the chat panel is copy-only, not a package.** The chat lives entirely in `apps/web/src/components/` inside the `private: true` `@open-design/web` app. The shared `@open-design/components` package is also `private: true` and exports only low-level primitives — `Button`, `Dialog`, `Input/Select/Textarea`, `VisuallyHidden` (`packages/components/src/index.ts`); no chat components. There is no `npm install` path. Adoption means forking source files plus their dependency tail (`@open-design/contracts` types, `runtime/*`, i18n, Lexical).

## 2. Chat panel anatomy

**Component tree.** A thin adapter `components/workspace/SideChatTab.tsx` (170 lines) calls `useConversationChat()` and renders one `<ChatPane>`. `ChatPane.tsx` (4,232 lines) is a **~114-prop** container (`Props` at `ChatPane.tsx:446`) holding ~40 co-located declarations: header + conversation-history dropdown, a `.chat-log` scroll region, `<ChatRows>` (the list), a dynamic tail-spacer, a scroll-to-latest button, a queued-send strip, and the composer slot. Messages render through `AssistantMessage.tsx` (3,289 lines) and an in-file `UserMessage`.

**Bubble variants.** Only **two roles** exist: `ChatRole = 'user' | 'assistant'` (`packages/contracts/src/api/chat.ts:18`). There is no `system`/`tool`/`error` message role — those are *events inside* an assistant message or *separate top-level cards*. The **user** message is the only filled bubble (right-aligned, capped width, `styles/chat.css:373`), rendered as plain pre-wrapped text (not markdown). The **assistant** message is bubble-less — a one-sided transcript block (`.msg.assistant`, `AssistantMessage.tsx:780`) like Claude/ChatGPT, not a symmetric two-bubble chat. If you want symmetric bubbles, that's your design, not theirs.

**Streaming rendering.** Token deltas append to `message.content`; the whole accumulated string is re-parsed and re-rendered each delta by a **custom 734-line markdown renderer** (`runtime/markdown.tsx`) — a hand-rolled block parser (`parseBlocks`, headings/lists/tables/code/bold/italic/links) that emits typed React elements with no `dangerouslySetInnerHTML` except for shiki-highlighted code (`:482`). Partial markdown "just works" because it re-parses the full prefix each frame; unclosed constructs degrade gracefully. This is competent but **redundant for you** — you already have react-markdown + remark-gfm.

**Composer.** A **Lexical** rich contenteditable (`components/composer/LexicalComposerInput.tsx`, 809 lines), not a textarea. Its one real payoff is atomic **@mention pills** in token mode (`MentionNode.ts:151`) across six kinds (file/plugin/skill/mcp/connector/workspace), plus slash/mention trigger detection, custom key routing (Enter=send, Shift-Enter=newline, IME-aware), paste interception, and undo. It is `PlainTextPlugin` — no rich formatting — and serializes to a plain `@token` string. The editor is well-encapsulated behind an imperative handle, but `ChatComposer.tsx` around it is a **5,555-line god-component** (121 hooks, 41 local imports, 153 i18n calls).

**Quick actions / suggestions.** A "+" menu (`ComposerPlusMenu.tsx`: connectors/plugins/skills/mcp/toolbox/library/Figma/upload), a tabbed @-mention popover, thin slash commands (`/mcp`, `/search`), and `NextStepActions.tsx` (1,070 lines) — post-turn chips that **seed the composer draft** (they don't auto-send) and are static constant arrays, not model-generated. No inline model switcher (routes to settings).

**Cards/embeds inside messages.** `ProducedFiles` (result-file cards with Open/Download, `AssistantMessage.tsx:2066`), `ToolGroupCard` (collapsed tool runs), `OdCardView` (parses `<od-card>{json}` blocks in prose), `FileOpsSummary`, `LiveArtifactBadges` (decorative status pills only, `LiveArtifactBadges.tsx`), plus the NextStepActions card gated to the last message.

**Thread/session management.** Conversations with a **fork** primitive ("Fork from here", `AssistantMessage.tsx:1501`) — this is your parent/child thread-continuity mechanism. On failed runs there's a resumable "Continue" affordance (`ChatMessage.resumable`, `packages/contracts/src/api/chat.ts:398,534`).

**Scroll & virtualization.** **Custom virtualization, no library** (react-window/virtuoso/tanstack all absent), engaging at >80 messages (`CHAT_MESSAGE_VIRTUALIZE_THRESHOLD = 80`, `ChatPane.tsx:663`) via a `ResizeObserver`-measured window (`useMeasuredVirtualWindow`, `:3059`). The scroll/anchor engine (`ChatPane.tsx:1478-1855`) is genuinely sophisticated: 80px bottom-pin cutoff, instant scrollTop-during-streaming, ChatGPT-style anchor-new-turn-to-top with a growing spacer, question-form scroll-into-view, and scroll-position persistence across tab unmounts.

**Error/retry states.** A top-level `.run-error` card (not per-message, `ChatPane.tsx:~2329`) driven by `resolveRunFailureUi()` with branchable primary actions (authorize / launch-terminal-auth / switch-model / recharge / retry) and a collapsible diagnostics accordion. Retry resends from the originating user turn reusing the failed assistant id; regenerate is implemented as fork. There is **no in-place edit of a past user message** (only a copy button).

## 3. Transport & state

**Transport is Server-Sent Events over HTTP to a local daemon — not WebSocket.** The flow (`providers/daemon.ts`): `POST /api/runs` creates a run and returns a `runId` (`:663`), then the client consumes `GET /api/runs/{runId}/events?after={lastEventId}` as an SSE stream (`:1034`). Frames are parsed by `providers/sse.ts` (standard `event:`/`id:`/`data:` with JSON payloads). Event types on the wire: `stdout`, `stderr`, `agent` (with subtype `tool_input_delta`), `start`, `error`, `end` (`:1092-1184`).

**This is architecturally the same philosophy as your bespoke protocol, on a different wire.** The daemon mirrors the SSE stream to a durable per-run JSONL event log (`eventsLogPath`, `packages/contracts/src/api/chat.ts:399`), and the client tracks `lastEventId` and **replays from it on reconnect** (`?after=`, up to 5 reconnects with backoff reset on progress, `daemon.ts:1015,1030,1187`). That is exactly your durable-event-log + seq/event_id idempotent replay, just SSE instead of WebSocket. Crucially, the wire is decoupled from the UI by a **normalized handler seam** (`onDelta`, `onAgentEvent`, `onToolInputDelta`, `onError`, `onRunStatus`, `onRunEventId`) and a `translateAgentEvent()` normalizer (`:1300`). Swapping SSE→WebSocket touches only this stream function, not the renderer.

**State.** Plain React hooks; `useConversationChat.ts` owns the message list and the callback seam. Optimistic send is real but lives in the parent, not the composer: the user message renders immediately and a client-generated `assistantMessageId` placeholder is streamed into. On reload, the client re-attaches to an in-flight run via `reattachDaemonRun(initialLastEventId)` and replays. Persistence is daemon-side (SQLite + the JSONL log).

## 4. Attachments & multimodal

**No client-side byte handling at attach time — this is the sharpest mismatch for you.** Because it's a local-first desktop app, a raw `File` is multipart-`POST`ed to the daemon (`/api/projects/:id/upload`, batched 12, `providers/registry.ts:2011`), which writes it into the project folder and returns `{name, path, size}`. The composer then holds a **path reference** (`ChatAttachment = {path, name, kind, size, order}`, `packages/contracts/src/api/chat.ts:430`), not bytes. There is **no client-side size/type validation** (all server-side). Previews render via a daemon raw URL (`projectRawUrl`). Paste (Lexical `PastePlugin` + async Clipboard API screenshot fallback) and drag-drop both route to the same upload path. Bytes reach the model two ways: the daemon agent reads files by path (and `api-attachment-context.ts` inlines file text as markdown, 24k chars/file, 64k total budget), or the BYOK path re-fetches bytes → base64 → native Anthropic image block (`providers/api-proxy.ts:202`). **Your product sends bytes over a WebSocket to a server with no local filesystem** — so this entire pipeline (upload endpoint, path references, raw-URL previews) is not portable; you'd rebuild it around your transport.

## 5. Agent-ness

This is the richest part of the codebase and where the most reusable ideas live. Everything renders off a persisted `PersistedAgentEvent[]` on each message — a discriminated union: `text | thinking | status | tool_use | tool_result | usage | live_artifact | live_artifact_refresh | plugin_candidate | diagnostic | conversation_title | raw` (`packages/contracts/src/api/chat.ts:469`). `AssistantMessage.buildBlocks()` (`:3148`) coalesces this stream into render blocks.

- **Tool calls:** a three-tier dispatch (`ToolCard.tsx:37`): a `Map`-based renderer **registry** (`runtime/tool-renderers.ts`, a clean AG-UI-shaped `({status,name,args,result,isError}) => ReactNode` extension point — but it ships empty), then hardcoded family cards for the Claude-Code tool vocabulary (Write/Edit/Read/Bash/Glob/Grep/WebFetch/WebSearch), then a `GenericCard` fallback. Same-family runs collapse into one `ToolGroupCard`.
- **Streaming tool args:** live code preview for Write/Edit via `tool_input_delta` frames accumulated into `liveToolInput`, extracted by a hand-rolled `extractStreamingJsonString` (`AssistantMessage.tsx:2786`). A separate truncation-tolerant JSON repairer, `runtime/partial-json.ts`, powers the streaming `<question-form>` (not tool cards).
- **Reasoning/thinking:** first-class `{kind:'thinking'}` deltas rendered by a collapsed-by-default `ThinkingBlock` with a client-measured "Thought for Xs" timer (`AssistantMessage.tsx:2603`).
- **Multi-step progress:** a TodoWrite-backed plan (`runtime/todos.ts` + `TodoCard`, `ToolCard.tsx:214`), pinned once at conversation level, plus a `FileOpsSummary` "files this turn" strip (`runtime/file-ops.ts`).
- **Human-in-the-loop — clarification only, NOT approval gates.** The agent emits a `<question-form>` artifact in its text stream, parsed into a very broad typed-form renderer (`QuestionForm.tsx`: radio/checkbox/select/text/number/range/date/color/file/switch + design "direction cards") hosted in a Questions tab, with one-by-one reveal and a 10-minute auto-continue. The answer is sent back as a **normal follow-up user turn** (`formatFormAnswers`/`parseSubmittedAnswers`). There is **no approve/reject-a-tool-call or permission-gate surface anywhere** (the only "gate" is a pre-run billing check). If you need real approval/steering gates, open-design gives you the rendering substrate but not the gating protocol.
- **Token usage:** a first-class `{kind:'usage', inputTokens, outputTokens, costUsd, durationMs}` event rendered in the message footer as "elapsed · output tokens · $cost" (`AssistantMessage.tsx:1468`).
- **Deep-link into tabs (your explicit need — clean and liftable):** a nonce'd callback chain with no router/postMessage/custom-events. A markdown link or a `ProducedFiles`/live-artifact click calls `preventDefault()` → `onRequestOpenFile(tabId)` → `ProjectView` sets `{name, nonce}` → `FileWorkspace` `useEffect` → `setActiveTab(name)` (`AssistantMessage.tsx:2385`, `ProjectView.tsx:2423`, `FileWorkspace.tsx:1101`). Tab ids are plain strings with sentinels (`live:<id>`, `QUESTIONS_TAB`, `chat:<id>`). Live-artifact SSE events auto-open tabs the same way. This is the seam your WebSocket result-cards would call.

## 6. Theming

**~100% hand-authored global CSS with semantic class names driven by CSS custom properties — zero Tailwind utilities, no CSS modules in the chat.** The chat resolves against one ~2,700-line global sheet (`apps/web/src/styles/chat.css`) plus a centralized token file (`apps/web/src/styles/tokens.css`). **Tailwind is vestigial**: it's in `package.json` and PostCSS, but there is no `tailwind.config`, no `@theme`, and no `@import "tailwindcss"` — no utilities are generated. **This is a real styling-model mismatch with your Tailwind-v4 product**: copying chat components means importing a large global stylesheet and its ~47 tokens, not Tailwind classes.

The token system itself is clean and reskinnable. Full light/dark support (`[data-theme]` + `prefers-color-scheme`) with a runtime accent engine (`state/appearance.ts`) that derives accent shades from one value via `color-mix`. **The brand accent is terracotta `--accent:#c96442`, and fonts are a system stack — not your `#3C2CDA` blue or Manrope/Heebo.** Reskinning a *copied chat component* to your palette is a few-hours token job (accent is nearly a one-value change; there's already a blue swatch preset; fonts are one `--sans` token + a `@font-face`); a whole-app reskin would chase ~147 hardcoded hex literals in sibling sheets. The chat JSX has zero inline color logic. But note: you'd be reskinning *global CSS into Tailwind*, which for your stack is closer to a rewrite of the styling layer than a token swap.

## 7. Quality signals

- **Tests: strong.** Vitest + Testing Library + jsdom, ~59 chat-relevant test files (`apps/web/tests/`), covering feedback gating, streaming states, scroll preservation, tool rendering, composer/Lexical, question forms — plus Playwright E2E for chat flows. A real asset *if* you copy the code they test.
- **Accessibility: uneven.** Composer menus/popovers are properly ARIA-patterned (`role="menu"/"dialog"/"tablist"/"listbox"`, real focus management). But **streamed assistant output is not an `aria-live`/`role="log"` region** (screen readers won't announce streaming text), `AssistantMessage` has zero keyboard handlers, and `QuestionsPanel` is nearly bare (1 aria attr, 0 roles). Expect a11y remediation.
- **Code quality: severe God-component debt.** ~14,000 lines across five chat files; `ChatComposer.tsx` 5,555 lines / 48 `useState` / 53 `case`; `ChatPane.tsx` 4,232 lines / **~114 props**; `AssistantMessage.tsx` 3,289 lines / ~50 props with a hand-maintained memo allow-list. (The surrounding run-detail page `ProjectView.tsx` is 9,530 lines and `FileWorkspace.tsx` 5,709 — the monolith smell is pervasive.) Notably there are almost no `TODO/HACK`/`@ts-ignore` markers — the debt is architectural (size + coupling), not littered hacks. Roughly 30-40% of each chat file is generic chat plumbing; 60-70% is open-design product surface (AMR/BYOK auth, plugins, design systems, brand browser, skills, toolbox, comments) you'd delete.
- **Coupling to its own backend/domain: high.** Beyond transport and data-model coupling, the chat is bound to a 4,042-key i18n system (~360 `t()` calls across the chat files) and `@open-design/contracts` types throughout.
- **Lineage — relevant collision risk.** The naming overlaps your product's `od_*`/`opendesign` namespaces, but not by shared color tokens or any "flowin" reference (I checked; none). The CLI binary is literally `od` (root `package.json:10`), the design system uses an `od-` class prefix, there are `open-design:*` custom DOM events, an `open-design.json` per-project sidecar, a `@open-design/*` contracts package, and a first-class "Share to Open Design" contribution flow baked into the chat. This suggests shared design-language DNA — but it also means adopting the chat unmodified imports open-design's brand identity and would **collide** with your own `od_*`/`opendesign` names. Budget a de-branding rename pass.

## 8. Verdict — against the "revive the in-repo kit" baseline

**(a) Adopt the panel wholesale — No.** Disqualified on multiple independent grounds, any one of which is close to fatal: it's copy-only (not a package); the three core files are God-components (114-prop `ChatPane`, 5,555-line composer); the styling model is global CSS, not your Tailwind v4; the transport is SSE-to-local-daemon and attachments are filesystem paths, both wrong for your server WebSocket + byte-upload; the markdown renderer is a redundant reimplementation of your react-markdown; **there is no voice input at all** (open-design's "voice" is TTS output only — nothing to reuse for your nice-to-have); there are **no approval/steering gates**; and it carries `od-*`/`open-design` branding that actively collides with your namespaces. Reviving your in-repo kit is strictly less work and lands you on your own stack.

**(b) Copy specific components/patterns — Yes, selectively.** This is where open-design earns its keep. These are dependency-light and framework-neutral enough to lift into your revived kit:
- `apps/web/src/runtime/partial-json.ts` (`repairJsonPrefix`/`parsePartialJson`, lines 16-93) — self-contained, zero-dep, truncation-tolerant streaming-JSON repair. **Steal as-is.**
- `extractStreamingJsonString` (`AssistantMessage.tsx:2786`) — single-field extractor from an open JSON fragment, for live tool-arg/code previews. **Steal the function.**
- The **tool-renderer registry pattern** (`runtime/tool-renderers.ts` + dispatch `ToolCard.tsx:37-77`, `deriveToolStatus`/`toRenderProps` are pure) — the registry → family-card → generic-fallback shape with try/catch isolation. **Steal the architecture**, supply your own tool vocabulary.
- The **events→blocks reducer** `buildBlocks` (`AssistantMessage.tsx:3148`) — the coalescing model (merge consecutive text/thinking, group same-family tools). This is the core of good agent rendering.
- The **scroll/anchor engine + measured virtualizer** (`ChatPane.tsx:1478-1855` and `useMeasuredVirtualWindow` at `:3059`) — depends only on a scroll ref + a messages array. The most reusable non-trivial UI mechanism here, and likely more robust than your dormant kit's auto-scroll.
- The **nonce'd deep-link-into-tabs seam** (`onRequestOpenFile(tabId)` → `{name,nonce}` → `setActiveTab`, string tab ids) — directly maps to your result-cards-deep-linking-into-Preview/Steps/Files/Audit requirement.
- `runtime/todos.ts` + `TodoCard`, `runtime/file-ops.ts`, and `ThinkingBlock` (`AssistantMessage.tsx:2603`) — small, mostly-pure building blocks for multi-step progress, file-ops summaries, and reasoning display, if your dormant kit lacks them.
- `QuestionForm.tsx` as a **reference** for a broad typed-form HITL renderer and the turn-based answer round-trip — take the pattern, not the file.

**(c) Ignore — Yes, the shell and the plumbing.** Don't take `ChatPane.tsx`/`ChatComposer.tsx`/`AssistantMessage.tsx` wholesale, the daemon transport (`providers/daemon.ts`), the attachment pipeline, the custom markdown renderer, `NextStepActions` content, `HandoffButton`/`ContinueInCliButton`, or the Lexical composer (unless you specifically decide you want atomic @mention pills, in which case the `composer/` folder — ~1,300 lines behind a clean string interface — is the only cleanly liftable composer piece).

**Net:** open-design's chat is not *better* than your in-repo kit as a thing to own — it's larger, more coupled, on the wrong styling and transport models, and missing two of your features (voice, gates). What it is better at is **demonstrating agent-rendering mechanics** your dormant kit may not yet have: streaming tool cards, thinking blocks, todo/plan progress, question-form HITL, tab deep-links, and measured virtualization. And its architecture validates your protocol design — the durable-event-log + replay-on-reconnect + normalized-event-union approach is exactly what open-design does, which is a reassuring signal that your bespoke WebSocket design is sound. Revive your kit; borrow the six-to-eight mechanisms above; skip the rest.
