## Shared root cause (BUG-R01 + BUG-R02) — the "empty agent list" re-arm no-op for id-aliased pipelines

**One sentence:** On restart, both gate re-arm drivers rebuild the run's agent roster with `get_pipeline_agents(wr.type)` using the RAW stored type WITHOUT resolving the `od_prototype -> prototype` id-alias, so for every `od_prototype` run the roster is empty, the driver early-returns ("empty agent list"), and no server-side coroutine is ever re-created to await the gate response — the answer/approval is persisted but nothing consumes it.

### The two live warnings that name the defect
- clarify: `WARNING _replay_clarify_run(75979e2c-...): empty agent list — nothing to replay` (engine.py:7609-7611)
- review:  `WARNING resume_run(0139f9de-...): empty agent list — nothing to resume` (engine.py:7305)

### Happy path — what a live (never-restarted) run holds
A live gate is a coroutine blocked on an in-memory `asyncio.Event`, driven by the run's `_execute_impl` task:
- **Clarify:** `ClarifyEngine.run` (clarify_engine.py:191) emits `questionnaire_ready` then blocks at `await event.wait()` (clarify_engine.py:299), where `event = store.get_resume_event(run_id)` (clarify_engine.py:283; store.py:53-60). `POST /{id}/answers` -> `submit_answers` (run_commands.py:253-277) -> `store.set_questionnaire_responses` (store.py:62-86) stores the responses AND calls `event.set()` (store.py:80-81) on that same event, unblocking clarify_engine.py:299 -> merge/persist -> the run proceeds into planner/agents dispatch.
- **Review:** `_run_review_gate` (engine.py:5000) blocks at `await event.wait()` (engine.py:5105), where `event = store.get_review_event(gate_key)` (store.py:111-116). `POST /{id}/gate` -> `resolve_gate` (run_commands.py:165-...) -> `store.set_review_response` (store.py:118-144) stores the action AND calls `event.set()` (store.py:143-144), unblocking engine.py:5105 -> the 5-action consumer (approve/reject/edit/redo/update_specs) drives the run forward.

A `kill -9` + restart destroys BOTH the awaiting coroutine (the `_execute_impl` task) AND the per-process `store._resume_events` registry (store.py:42). The durable event log survives (questions/gate + spec preserved); the in-memory waiter does not.

### The re-arm path and where it breaks
`restore_non_terminal_runs` branch (a) (engine.py:5226-5343) handles a `waiting_for_user` run: `compile_for_run(wr.type)` **succeeds** (engine.py:5244) because `compile_for_run` resolves the alias internally (`manifest_id = resolve_alias(pipeline_type)`, engine.py:563 inside 547-565), so the run is classified compilable, `derive_open_gate` finds the open gate, `_is_resumable_in_flight` is True -> the store event is re-created and cleared (engine.py:5286-5294) and `_rearm_gate_run` is spawned (engine.py:5312-5314). **Status correctly stays `waiting_for_user`** (this is the KAN-88 re-arm; the live restore logs "restored N resumable run(s)"). `_rearm_gate_run` (engine.py:5423-5476) dispatches on the gate kind: `review -> resume_run(run_id)` (engine.py:5469), `questionnaire -> _replay_clarify_run(run_id)` (engine.py:5476).

Both drivers then rebuild the roster from the RAW stored type:
- `_replay_clarify_run` (engine.py:7556): `pipeline_type = wr.type` (7584) -> `agents = get_pipeline_agents(pipeline_type)` (7601) -> **`if not agents:`** log "empty agent list — nothing to replay" + `_fire_resume_cleanup` + **`return`** (7608-7613). It NEVER reaches `_drive_resumed_stream` (7682), so `_execute_impl` is never re-driven with `_clarify_replay`, so `ClarifyEngine.run`'s `await event.wait()` is never re-entered.
- `resume_run` (engine.py:7233): `pipeline_type = wr.type` (7265) -> `agents = get_pipeline_agents(pipeline_type)` (7298) -> **`if not agents:`** log "empty agent list — nothing to resume" + `_fire_resume_cleanup` + **`return`** (7304-7308). It NEVER reaches `_compute_resume_offset` (7314) or the 49-02 offset-override/`gate_reentry` re-entry, so `_run_review_gate`'s `await event.wait()` is never re-entered.

The store event exists (armed at 5286-5294) but no coroutine awaits it. `set_questionnaire_responses`/`set_review_response` then `.set()` an event with no listener -> **black hole**; status stays `waiting_for_user` forever.

### Why the roster is empty — the id-alias, verified
`get_pipeline_agents` (registry.py:224-244) discovers agents whose `AGENT.md` declares that exact `pipeline_type`. `od_prototype` is a routing **id-alias with no AGENT.md of its own** (the prototype agents declare `pipeline_type: prototype`); it must be resolved to `prototype` before the lookup. Empirically confirmed offline (python3.11, no server):
```
resolve_alias("od_prototype")            == "prototype"
get_pipeline_agents("od_prototype")      -> len 0      # the bail
get_pipeline_agents("prototype")         -> len 5      # what a fresh/aliased run gets
```
The register documents this exact gotcha: line 254 ("od_ alias gotcha: `od_prototype` ... have NO AGENT.md of their own ... `get_pipeline_agents` returns none for them ... resolve the alias for agent LOOKUP"); lines 464-465 ("`od_prototype` is the SOLE id-alias -> `prototype`, no own dir"). A **fresh** run applies exactly this: `_execute_impl` resolves via `compile_for_run` (563) and takes membership from `get_pipeline_agents(compiled.id)` (engine.py:1678, where `compiled.id` is the RESOLVED id) with a `PIPELINE_AGENTS.get(compiled.id, [])` fallback (1679-1683). `resume_run` and `_replay_clarify_run` skip that resolution -> pass `wr.type="od_prototype"` -> empty.

### Classification — v3.0 / Phase 49 REGRESSION (headline-breaking)
- **Symptom is a Phase 49 regression.** Before Phase 49, branch (a) marked every restart-`waiting_for_user` run **failed** with an honest WR-05 message ("start a new run") — the KAN-88 behavior. Phase 49 flipped fail->re-arm (engine.py:5226-5343) but the re-arm driver bails for `od_prototype`, converting the honest failure into a **silent black hole**. Phase 49 both introduced `_replay_clarify_run` with the alias omission fresh AND newly routed review-gate-parked runs into `resume_run`, which already had it.
- **The `resume_run` half of the defect pre-exists since Phase 12 (12-03)** (resume_run born there) but was DORMANT: pre-49, gate-parked runs were failed not re-armed. NOTE (code-verified, not live-observed in this pass): branch (b) mid-build auto-resume of an `od_prototype` run (status generating/etc.) ALSO routes through `resume_run` (engine.py:5376-5377) and would ALSO bail at 7305 -- i.e. NO restart-resume of any `od_prototype` run works today. Only the two gate-parked cases were live-reproduced here.
- **Scope of blast radius:** `od_prototype` is the SOLE non-self entry in `_OD_ALIAS_BASE` (registry.py:263-265) and the primary user-facing prototype pipeline. `od_ppt`/`od_ppt_revision` are REAL registry keys (self-aliasing), so `get_pipeline_agents(wr.type)` is non-empty for them -- they are NOT affected. The defect is specific to `od_prototype` (and any future non-self id-alias).

### The coverage hole that let this ship
Every `test_restart_resume.py` restart test drives through `_ResumeHarness`, which monkeypatches `get_pipeline_agents` so the fixture type returns non-empty specs: `_patched_gpa` = "return `list(specs)` if `pt == _FIXTURE_ID`" (test lines 244-245), with `_FIXTURE_ID = "sample_wave"` (line 58) and `_seed_workflow_run(..., type_="sample_wave")` by default (line 375). So the driver's `get_pipeline_agents(wr.type)` is ALWAYS non-empty in tests. The only non-fixture type any test seeds is `type_="__nonexistent_pipeline__"` (line 1077) -- the *uncompilable* negative case (correctly WR-05-fails). **No test ever seeds a COMPILABLE-yet-aliased type (`od_prototype`) against the REAL `get_pipeline_agents`** -- the exact case where `compile_for_run` succeeds (re-arm) but `get_pipeline_agents(raw)` is empty (bail).

The two Phase 49 twin tests stop one assertion short of the bug:
- KAN-88 `test_waiting_for_user_run_is_rearmed_not_driven` (lines 887-909): asserts status stays `waiting_for_user` AND `resume_run` is NOT called. The re-arm satisfies both. It does NOT submit an answer/gate and assert progression.
- `test_clarify_parked_run_replays_durable_questions_and_proceeds` (line 2827) and `test_gate_reentry_all_five_actions_post_restart` (line 1251): these DO drive the answer/gate forward, but only because the fixture roster is non-empty. They never exercise the aliased-empty-roster path, so the missing `resolve_alias` is invisible to them.

### Fix (design only -- not implemented here)
Resolve the id-alias before the roster lookup in BOTH drivers, exactly as the fresh path does:
- `resume_run` (engine.py:7298): `agents = get_pipeline_agents(resolve_alias(pipeline_type))`
- `_replay_clarify_run` (engine.py:7601): `agents = get_pipeline_agents(resolve_alias(pipeline_type))`

`resolve_alias` is already module-level in engine.py (defined 532, used by `compile_for_run` at 563). For full parity with the fresh path, mirror `_execute_impl`'s membership fallback (engine.py:1678-1683): `get_pipeline_agents(resolve_alias(pt)) or PIPELINE_AGENTS.get(resolve_alias(pt), [])` (also covers the ppt/od_ppt `get_pipeline_agents` quirk registered as WR-01). Everything downstream of the bail is already correct: for clarify, `_drive_resumed_stream` (7421) -> `_execute_impl` with `_clarify_replay` (1716, forces the gate at 1723-1727, replays at 1852-1889 -> re-enters `await event.wait()`); for review, `resume_run`'s 49-02 offset-override + `gate_reentry` sentinel re-enter `_run_review_gate`'s wait. The alias resolution is the ONLY missing piece.

**Guardrails (register):** INV-12 -- reuse `resolve_alias` + the two existing drivers; no third driver, no new machinery. INV-1/SC-001 -- `resolve_alias` is a generic data map (`_OD_ALIAS_BASE`), no workflow-name literal in the kernel branch (banned-pattern gate stays green). INV-3 -- `resolve_alias` is identity for real registry keys, so scripted golden runs are byte/event-identical (goldens 10/10). No new WS types, no migration, no FE.

**Coverage fix (mandatory, closes the hole):** add a regression test that seeds `wr.type="od_prototype"` against the REAL `get_pipeline_agents` (NOT `_patched_gpa`) and asserts RED->GREEN: pre-fix the driver logs "empty agent list" and no `_drive_resumed_stream`/offset-override runs (POST answers/gate does not advance); post-fix the alias resolves to `prototype`'s 5 agents and the run drives forward. This must fail on the current code before the fix is trusted.

### BUG-R03 — restart-auto-resumed run completes with an UNDER-POPULATED workflow_runs row: `output`/`agent_outputs`/`token_usage`/`duration` empty (status written by the engine state machine, output columns written only by the app-layer launch driver the resume tier never replicates)  [severity 🟠 moderate] [FIXED ✅]
- **Found by:** R-A4 on 2026-07-19 · run id `15c4372f-7682-4288-aa80-299788337e84` (user_stories, `kill -9` mid-build then restart-auto-resumed at step offset 2/6)
- **Symptom:** A user_stories run was crashed mid-build (`kill -9`) and AUTO-RESUMED by the restart restore scan (`restore_non_terminal_runs` -> "auto-resumed 1 in-flight run"; `resume_run(...): resuming pipeline=user_stories at step offset 2/6`). It ran to completion correctly — all 6 agents, deliverable produced. BUT the completed run's DB row is under-populated: `workflow_runs.output` is EMPTY (NULL/0-length) and `workflow_runs.agent_outputs` is EMPTY, while `status` IS `completed`. By contrast three normal (never-resumed) completed user_stories runs have both populated: `97a97b7b` (output 52386, agent_outputs 320771), `c7b8e26b` (34866/291040), `ab90f5f4` (44292/264355). The deliverable itself IS durably present: `artifact_refs` row `producer_agent='backlog-compiler', kind='deliverable', version=1, length=47109`, and the FE renders it fine (FE reads artifacts, never the `output` column). So this is NOT a lost-deliverable bug; it is a run-row persistence gap on the resume-completion path. `/summary` returned `{}` for the deliverable/KPI fields live. DISTINCT from BUG-R01/R02: those are the od_prototype id-alias empty-roster BAIL (run never progresses); this is a real registry key (user_stories -> `get_pipeline_agents` non-empty -> `resume_run` does NOT bail -> the run COMPLETES and the output-persistence gap bites). Different root cause, different code, different pipeline.
- **Expected:** a restart-auto-resumed run that completes persists the SAME terminal `workflow_runs` columns as a never-restarted completion — `output`, `agent_outputs`, `token_usage`, `duration`, `deliverable_mimetype/filename` — so `/summary`, `/chain-context`, export, and analytics read the same row a normal completion writes (RESUME-10; the design-draft §5.6 mandate "the terminal status ladder must stay behaviorally identical to the just-fixed fail-safe launch driver").
- **Investigation (root cause, file:line):**
  - **The asymmetry (verified by grep):** the terminal `workflow_runs` output columns are written in exactly ONE place in the whole backend — the APP-LAYER launch driver `_drive_launch_to_queue`'s post-stream terminal block (`app/api/run_commands.py:1677-1745`): `wr.output = final_output` (1704-1705), `wr.agent_outputs = json.dumps(agent_outputs_collector)` (1710-1711), `wr.deliverable_mimetype/filename` (1706-1709), `wr.token_usage` (1723-1738), `wr.duration` (1741-1742), `wr.completed_at` (1739-1740), `db.commit()` (1743). Both payloads are built by the driver CONSUMING the engine's live event stream: `final_output` from the `pipeline_complete` event (`run_commands.py:1655-1659`) and `agent_outputs_collector` from the `agent_start`/`agent_complete`/`tool_*` branches (`run_commands.py:1599-1654`). The ENGINE itself writes NONE of these columns: a backend-wide grep finds zero `.output =`/`.agent_outputs =`/`.token_usage =` writes in `agents/execution_engine/engine.py`, and the only `wr.status =` writes there are three `"failed"` in the restore scan (`engine.py:5251, 5333, 5401`).
  - **Why status IS `completed` but output is empty (the anomaly resolved):** status is NOT written by the launch driver alone — it is written by the engine STATE MACHINE inside `_execute_impl`'s "Step 5: Pipeline complete": `if current_state not in ("cancelled", "failed"): self._state_machine.transition(pipeline_run_id, "completed")` (`engine.py:2512-2513`), and `StateMachine._persist` writes ONLY `wr.status = new_state` (`agents/execution_engine/state_machine.py:100-118`, write at :117 — no other column). BOTH the normal launch AND the resume drive `_execute_impl`, so BOTH reach 2513 and get `status=completed` from the state machine. The launch path ADDITIONALLY runs the driver's 1677-1745 block (output/agent_outputs/etc.); the resume path does NOT. Hence: status yes (engine state machine, both paths), output no (app-layer driver, launch path only).
  - **The resume path writes no output columns (traced):** restart branch (b) spawns bare `asyncio.create_task(self.resume_run(pipeline_run_id))` (`engine.py:5376-5378`) — NOT wrapped in any app-layer driver. `resume_run` (`engine.py:7233`) ends by awaiting `_drive_resumed_stream` (`engine.py:7406-7419`) with NO post-drive terminal persistence. `_drive_resumed_stream` (`engine.py:7421`) drives `_execute_impl` (7456-7474), persists each event to the durable run_events sink (`sink.persist`, 7484) and pushes to the live_queue (7489-7495), and its `finally` (7526-7554) does ONLY cleanup + live-ectx unregister — it writes NOTHING to the `workflow_runs` row. So the resume tier is structurally silent on every output-bearing column; only the engine state-machine `status` write lands.
  - **The Phase 50 user-resume path shares the identical gap (BY DESIGN, cited):** `_drive_user_resume` (`run_commands.py:413`) is documented (docstring 419-425) to add "ONLY the two status writes the resume tier structurally lacks" and carries a "HARD FENCE (INV-12 / Pitfall 7): this body MUST NOT contain an `async for ... engine.execute(` event ladder and MUST NOT clone `_drive_launch_to_queue`'s per-event accumulation. It is NOT a third driver." Its `_reconcile_terminal_status` (`run_commands.py:440-493`) reads the durable run_events tail and computes status (482-488) -> `_persist_resume_status` (`run_commands.py:503-517`) writes ONLY `swr.status` (511), `wr.error` (513), `completed_at` (514). So NEITHER resume entry point (Phase 46 restart auto-resume NOR Phase 50 user-resume) persists output/agent_outputs/token_usage/duration. The observed run hit the restart auto-resume path (branch b), where even the app-layer status reconcile does not run — status came purely from the engine state machine.
  - **Downstream impact (each verified):**
    - **Deliverable render (FE): SAFE.** FE reads the durable `artifact_refs` (kind=deliverable, present, length 47109), never the `output` column.
    - **Revision / family revise: SAFE.** `_handle_revision` (`engine.py:5575`) reads the PARENT run's artifacts via the owner-scoped `ScopedStore` against `artifact_refs` (F2/13-05 fallback chain — link 2 = the `kind="deliverable"` completion ref), NOT `wr.output`.
