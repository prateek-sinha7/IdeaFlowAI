# Fix ISS-053 — enforce `update_specs` eligibility server-side

`update_specs_eligible` is computed by `_update_specs_eligible`, stamped onto every
`review_gate_ready`, shipped to the frontend — and then **never read again**.
`_run_review_gate` acts on the client-supplied `action` string alone
(`engine.py:5576`), so a replayed or crafted gate POST runs the spec-revision
sub-pipeline at gates that advertised the affordance as unavailable.

`gate_key = f"{run_id}:{agent_id}"` identifies a gate **slot**, not a **firing**
(`engine.py:5481`), so this needs no crafting: replaying a legitimate earlier click on
the same agent resolves whichever firing is currently armed.

## Task boundary

**In scope:** make the published eligibility verdict binding, at the engine and at every
ingress; give the two declared gates the `_gate_update_specs` branch they never got.

**Out of scope** (found during investigation, reported, deliberately NOT fixed here —
each is a distinct defect and would be scope creep):

- The unknown-action fail-open at `run_commands.py:239-243` (`else: # approve`) — any
  unrecognised action string silently approves. The Concierge sibling takes the opposite,
  safer default and says so (`run_commands.py:982`, "M1").
- `GateCommand.action` is an open `str` with no enum, while the frontend declares the
  closed union (`frontend/src/lib/api.ts:690`).
- `_AGENT_KIND_MAP` covers only prototype agents, so `_artifact_kind_for`'s `summary`
  fallback makes **every** gate eligible on `od_ppt` / `user_stories` / `app_builder` and
  every composed workflow. Narrowing the advertisement is a separate correctness item.
- `analysis_report` has no length cap.

## Design — two layers, ONE rule (INV-3 / INV-12)

The eligibility RULE stays solely in `_update_specs_eligible` (`engine.py:6578`). Neither
layer restates it: layer 2 reads the parameter that helper produced; layer 1 reads the
value that helper published. If the rule ever changes, both layers change with it and no
third copy exists.

### Layer 2 — `engine.py::_run_review_gate` (unbypassable)

`update_specs_eligible` is already a parameter of this function (`:5450`). It is the only
choke point that sees **both** the action and the eligibility decision, and it sits
downstream of all three ingresses.

Degrade = **keep waiting**. Re-arm the event and re-await.

- NOT approve — that is fail-open, and it is exactly the defect the Phase-23 F1a redo
  defence exists to prevent. WR-07 says HITL gates fail closed (`engine.py:5028-5041`).
- NOT reject — that cancels the run, a semantic change the caller never asked for.

Mechanically: wrap the wait-and-dispatch tail in a loop; the ineligible branch logs a
warning, `event.clear()`s and `continue`s. Every other branch still returns exactly as it
does today. No new event is emitted, so a client cannot use a refused action to generate
stream traffic; the cost of a refusal is one store read and one log line.

The re-arm race (a legitimate response landing between the response read and the
`event.clear()`) is the **same** race the shipped redo loop already has, and much narrower
— redo re-runs a whole agent between its yield and the re-entry `event.clear()`. Not a new
class of defect; not solved here.

### Layer 1 — one shared predicate, wired into all three ingresses

`.kiro/steering/backend-api.md:31,35` designates `run_engine.py` as the home of the
owner/terminal fences and says **"Do NOT duplicate"** them in `run_commands.py` /
`run_stream.py`. The new predicate goes there, beside `_review_gate_owned_by` and
`_review_gate_run_is_terminal`, and follows their exact idiom: sync, its own `_get_db()`
session, a direct ORM query, keyed on the run id parsed out of `gate_key`.

```
_review_gate_advertises_update_specs(gate_key) -> bool
```

Reads the highest-`seq` `review_gate_ready` row for the run and returns **False only when
that row is for exactly this `gate_key` and explicitly published
`update_specs_eligible: False`.** Everything else returns True and defers to layer 2:

- no row (event persistence is best-effort — `_RunEventSink.persist` degrades a DB failure
  to a warning), or
- the row is for a different `gate_key`, or
- the key is absent from the payload (a pre-KAN-101 row).

**Abstaining on "unknown" is the point.** Layer 1 is caller feedback; it must never
manufacture a verdict it did not read, or a degraded persist would 409 a legitimate
revision. It is safe to abstain precisely because layer 2 never fails open.

Deliberately **not** owner-scoped: ownership is already established at all three ingresses
before this runs, exactly as `_review_gate_run_is_terminal` relies on. (Verified against
`backend/dev.db`: `run_events.owner_id` equals `workflow_runs.user_id` on 206,368/206,368
rows, so scoping would change nothing today — but an owner-scoped read could produce a
false 409 the moment that ever drifted, and a false 409 blocks legitimate work.)

Wired at all three `set_review_response` writers. A sweep of the whole backend confirms
there are exactly three in production code — the WS handler is gone — so this is complete,
not a sample:

| # | Ingress | Site |
|---|---|---|
| 1 | `POST /api/runs/{id}/gate` | `run_commands.py:228` |
| 2 | `POST /api/runs/{id}/messages` — Concierge `gate_action` disposal | `run_commands.py:989` |
| 3 | `POST /api/runs/{id}/messages` — `CHANNEL_GATE` route | `run_commands.py:1206` |

Response: **409** `{"code": "update_specs_not_offered", "recoverable": false}`, matching
the shape of the terminal fence beside it. A silently-ignored 200 would be worse than the
current behaviour, not better.

### Declared gates — the missing `_gate_update_specs` branch

`gates/human.py` and `gates/approval.py` handle `_gate_rejected` / `_gate_redo` /
`_gate_edited` but have **no** branch for `_gate_update_specs`. It therefore hits the
`yield event` fall-through and the outcome resolves to `GATE_PASS` — a silent approve on a
declared `gates:[human]` / `gates:[approval]` step, plus a leak of an internal signal onto
the SSE wire (`.kiro/steering/backend-engine.md:39` says internal `_gate_*` signals never
reach the wire; `run_commands.py:2188` enqueues with no type filter).

Fix is the F1a redo treatment applied verbatim to its sibling: consume it, never yield it,
map it to `GATE_WAIT_HUMAN`. Reject still wins.

## Tests

### The "mandatory extra" eligibility-vector test ALREADY EXISTS

The brief asked for a test asserting the vector is True at the OUTER analyze gate, False
at the IN-PASS gate and True at the RE-OPENED gate, on the grounds that this has no test
today. **That is not correct.**
`test_spec_revision_cycles.py::test_update_specs_not_offered_while_a_revision_is_in_flight`
(`:241-265`) asserts exactly `[True, False, True]`, and it is **green at HEAD** (verified —
5 passed). It will not be duplicated.

What it does **not** cover is the thing this change adds: it replaces `_run_review_gate`
with a stub, so it proves what the engine *passes* to the gate and nothing about what the
gate *does* with it. That is the real gap, and it is also the load-bearing proof the brief
actually wants — that enforcement leaves a second revision cycle reachable.

### New — `tests/agents/test_update_specs_enforcement.py`

1. **Ineligible action keeps the gate waiting** (RED pre-fix) — real `_run_review_gate`,
   `update_specs_eligible=False`, client posts `update_specs`: no `_gate_update_specs`, no
   `review_gate_approved`, no `_gate_rejected`. A later approve then resolves it normally,
   proving the gate stayed open rather than being consumed.
2. **Eligible action still fires** (green before AND after) — the dormancy guard.
3. **Three-gate verdict, against the real gate** (RED pre-fix) — takes the eligibility
   values the engine actually computes at the outer / in-pass / re-opened analyze gates
   (read from the drive, never hardcoded) and feeds each into the real `_run_review_gate`
   with an `update_specs` post. Expect **honored / REFUSED / honored**.
   If enforcement plus the current rule ever made the re-opened gate unreachable, this
   test fails — which is the signal to stop, not to loosen the rule.
4. **Declared gates consume `_gate_update_specs`** (RED pre-fix) — human and approval:
   never yielded, outcome is not `GATE_PASS`.

### New — `tests/unit/test_update_specs_ingress_fence.py`

`review_gate_ready` published `False`, with `set_review_response` proven un-called; 200 when
