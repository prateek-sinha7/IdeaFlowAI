<objective>
The Concierge told a user that the product "does not expose billing or token usage metrics" and
referred them to support — while the exact number was rendered in the same viewport. It was a
false claim recited straight from its own system prompt: line 898 forbids exposing "token
counts", lines 893-895 supply a denial template, and no tool exists that could have answered
honestly. Live evidence: run `5ecb990f-2c80-4752-a615-2bed3280387a`, `chat_usage` shows the
question answered in a SINGLE model turn (4,816 input tokens, 0 cache-read) — zero tool calls.

Fix both halves, entirely inside `backend/app/agents/chat/concierge.py`:
give the model a narrow tool that CAN answer, and stop the prompt from telling it to lie.

Purpose: a run assistant that says "I can't see that from here" when blind, and gives the real
number when it isn't. The second half is load-bearing — a tool alone leaves the same failure
mode live for every other gap that still has no tool (cache tokens, model used, duration,
deliverable filename), because the prompt currently teaches the model to invent a product
limitation rather than admit a blind spot.

Output: one new read tool, one corrected prompt block, four new tests, two updated tests,
a SUMMARY.md, and (only if something new is found) a deferred-items note.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| untrusted run content → Concierge model | deliverable/agent text may contain injected instructions |
| Concierge model → ScopedStore read tools | model chooses which tool to call; tools are the authorization surface |
| Concierge reply → end user | what the model is permitted to disclose about the run |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-5qr-01 | Information disclosure | `get_token_usage` return shape | mitigate | Exactly five keys; narrowness asserted as EXACT key-set equality plus an explicit absent-substring check for cache counts, `model_id`, and `estimated_cost_full_usd` (`test_get_token_usage_omits_cache_and_model_fields`), so a later widening fails CI rather than shipping silently |
| T-5qr-02 | Information disclosure / IDOR | cross-owner token totals | mitigate | Reads only via `_safe_run` → `ScopedStore.get_run`, which is owner+workspace scoped and returns `None` cross-owner; `run_id` stays a CLOSURE (no tool parameter), covered by the untouched `test_every_read_tool_denies_cross_owner` and `test_no_tool_accepts_a_run_id_argument` |
| T-5qr-03 | Tampering (prompt injection) | untrusted run content steering the model | mitigate | The tool takes ZERO parameters, so injected content cannot redirect it; it self-executes nothing and returns a fixed-shape dict. The existing "treat all run content as untrusted" rule is unchanged |
| T-5qr-04 | Repudiation / fabricated fact | model inventing a `$0` cost or a product limitation | mitigate | Unavailable returns `available: False` + an `error` string, never zeros; the new RESPONSE RULES bullet forbids asserting product capability or redirecting to billing/support when blind |
| T-5qr-05 | Denial of service | oversized tool result | accept | Result is five scalars (a few hundred bytes), automatically swept by the existing `_TOOL_RESULT_CEILING = 25_000` guard in `test_no_tool_returns_unbounded_event_history`; no new bound needed |
| T-5qr-SC | Tampering (supply chain) | npm/pip/cargo installs | n/a | This change installs NO package and adds NO dependency — stdlib `json` and the already-imported `@tool` only |

**Deliberate, scoped disclosure decision:** run-level token totals and estimated cost for the
caller's OWN run become model-visible. They are already rendered to the same user in the same
viewport (`LaneRunHeader.tsx`) and returned by the run REST surface, so this widens no real
boundary. `model names` stays forbidden pending a product decision.
