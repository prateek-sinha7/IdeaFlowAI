## The defect (root cause, verified line-by-line against HEAD)

`page.tsx:1196-1201` sits inside `if (pipelineTypes.includes(msg.type)) {` (opens `:694`,
`return`s `:1204`). Both `"pipeline_cancelled"` and `"pipeline_failed"` are members of
`pipelineTypes` (`:677-678`), so **this is the live handler** and the `switch (msg.type)` at
`:1207` is never entered for them.

That block clears three legacy React states and nothing else:

```ts
setReviewGateData(null); setQuestionnaireData(null); setActivePipelineRunId(null);
```

The lane does not read any of them. It reads the **store**: `page.tsx:2749` passes
`questionnaireData={runStore.viewed.questionnaireData}` down to `DashboardLayout`. Nothing on
the live terminal path clears the store's `questionnaireData`.

`DashboardLayout.tsx:1862` (path: `frontend/src/components/layout/DashboardLayout.tsx`):

```ts
const laneClarifyOpen = questionnaireQuestions.length > 0 && (!!pendingPipelineRun || !!activePipelineRunId);
```

`laneClarifyOpen` is the **one** lane branch NOT AND-ed with `isRunning` — deliberately, because
clarify precedes `pipeline_start`. And it is evaluated *before* the terminal branch in the
`runLaneState` ternary (`:1865-1871`):

```
gate > clarify > building > terminal > complete > idle
```

So a lingering store `questionnaireData` **outranks** the terminal markers the frame already
applied correctly. `runLaneState` resolves to `"clarify"`, and `RunChatLane.tsx:1068-1069`
derives `isRunning = runState === "building" || "clarify" || "gate"` — clarify literally
re-asserts `isRunning=true`, so Stop stays rendered on a run that is already dead.
