# Quick 260812-1nz — fix ISS-052 (disambiguate the doubled analyze gate)

## Goal

One "Update the Specs" click opens the analyze gate **three** times — `[0]` the outer
first-pass gate, `[1]` the analyze re-run **inside** the revision sub-pipeline, `[2]` the
gate re-opened after the pass returns. `[1]` and `[2]` carry the **same `gate_key` and the
same output bytes** (live run `5ecb990f`: sha1 `0136795fc392`, 11,974 chars, 5 ms apart),
so nothing on the wire distinguishes them — yet they carry **opposite affordances**
(`update_specs_eligible` False vs True). The user cannot tell which one they are on.

Fix as **(b) DISAMBIGUATE**. Publish a durable, generic per-firing discriminator on
`review_gate_ready` and render it. **Suppress no gate.**

## Decisions (locked before planning — from the ISS-052 investigation report)

1. **Do NOT suppress `[2]`.** It is the only firing with `update_specs_eligible=True`;
   removing it deletes the sole entry point to a second revision cycle and regresses
   ISS-064, closed 2026-08-12.
2. **Do NOT suppress `[1]` here either.** That option ("suppress the in-pass gate") rewrites
   six assertions in `test_spec_revision_cycles.py` and, by INV-12, forces deletion of
   condition 2 of `_update_specs_eligible` (the one-day-old FIX-218 fence). It is filed as
   **ISS-072**, not done here.
3. **Reject FE-side dedupe** of "same gate_key + same output". It converts a redundant gate
   into a **hang** (the engine is blocked on `event.wait()`), and it would eat legitimate
   restart-resume re-opens, whose signature is identical (live: `5ecb990f` seq 8402/8406,
   `d5dbc9f2` seq 24788/24792, each preceded by `workflow_validated` + `pipeline_start`).
4. **No new state.** Both discriminator sources already exist and are already declared on
   `ExecutionContext`: `revision_high_water` (monotone, never restored) and
   `revision_attempt` (non-zero for exactly the pass's duration).
5. **SC-001**: no `if pipeline_type ==`, no workflow/agent-id literal, on either side.
6. **INV-3**: the 10 goldens contain **zero** `review_gate_ready` events
   (`_scripted_model.py:649` passes `gate_agent_ids=[]`), so golden silence proves nothing.
   The new keys go into `_VOLATILE_STRIP_KEYS` anyway (the established parity-neutral
   pattern, demanded by `test_sc001_gate_flag.py::test_new_keys_are_in_volatile_strip_set`),
   and correctness is proven at **test** level, not by golden silence.

## The discriminator

Two additive keys on `review_gate_ready.data`, threaded in as parameters exactly like
`redoable` / `update_specs_eligible`:

| key | type | source | `[0]` | `[1]` | `[2]` |
|---|---|---|---|---|---|
| `revision_cycle` | `int` | `ectx.revision_high_water` | `0` | `1` | `1` |
| `revision_in_flight` | `bool` | `bool(ectx.revision_attempt)` | `False` | `True` | `False` |

The **pair** is unique per firing — which is what the `InlineGateActions` latch and the FE
label both need. `revision_cycle` alone cannot separate `[1]` from `[2]`.

`revision_cycle` is also the durable per-cycle signal **ISS-063** needs (its FE state
`specRevisionCount` at `dashboard/page.tsx:357` is `useState(0)`, incremented only from a
live FE-armed inference and never back-filled). ISS-063 must consume this field rather
than invent a third counter.
