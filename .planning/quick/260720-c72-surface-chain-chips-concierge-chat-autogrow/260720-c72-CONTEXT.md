## Implementation Decisions

### Change 1 — FE chain chips in RunChatLane (VERIFIED wiring)
- The chain data + action ALREADY reach the lane: `DashboardLayout.tsx:1430-1434` computes `laneSuggestions: LaneSuggestion[]` (from the static `CHAIN_OPTIONS` allow-list in `frontend/src/lib/workflowChaining.ts` — e.g. from `user_stories` you can chain to `prototype`/`ppt`, filtered to exclude the current type), and `DashboardLayout.tsx:1790-1791` passes `suggestions={laneSuggestions}` + `onSuggestion={handleLaneSuggestion}` into `RunChatLane`.
- `RunChatLane.tsx:798-799` destructures `suggestions` + `onSuggestion` — but they are NEVER rendered/invoked. The completed-state composer (`RunChatLane.tsx:1087-1098`, `case "complete"`) renders ONLY `<FreeTextComposer>`. The code comment there says the "Suggested next steps" chip block was removed for "Mock fidelity (D39-1)", props "kept here, unrendered".
- **Decision:** add a `renderChainSuggestions()` helper that maps `suggestions` → clickable chips calling `onSuggestion(id)`; invoke it in the composer container `<div data-testid="chat-composer">` (`RunChatLane.tsx:1448-1462`) as a sibling BETWEEN `renderHeldRefinement()` (`:1460`) and `renderComposerBody()` (`:1461`) — i.e. just above the chat input — gated to `runState === "complete"` AND `suggestions?.length`. Mirror the existing chip-block idiom (`renderProposals()` `:980`, `renderHeldRefinement()` `:1030-1063`).
- **DS chip:** use the shared primitive `frontend/src/components/ui/Pill.tsx` (`Pill` — "shared run-screen chip primitive (SC-1, D-15)", `--radius-pill`, `border-line-control`, `bg-surface-white`, DS tokens, NO raw hex) as the visual basis. Since the chips are ACTIONABLE, render them as `<button>`s styled in the Pill idiom (or `Pill` wrapping a button), matching the run-lane chip look already used by `renderHeldRefinement` (brand accent, `rounded-[var(--radius-pill)]`, `border-line-control`, `bg-surface-white`, `text-[11px]`). A small "Suggested next" / "Chain into" label above the chips is fine (match the `renderHeldRefinement` uppercase-label pattern), but keep it compact so it sits cleanly with the settled `DeliverableCard`/`SettledSummaryStrip` already in the lane. Give the row a `data-testid` (e.g. `chat-chain-suggestions`) and each chip a stable testid.
- **Restore** the stale docstring bullet at `RunChatLane.tsx:16` that claimed the suggestions were removed.

### Change 2 — BE Concierge chain-awareness (VERIFIED gap; reuse the static list)
- Concierge is LIVE end-to-end (Phase 43, Bedrock-proven). A settled-run "ask" already routes to it: `RunChatLane.tsx:942` (`classifyFreeText === "ask"` → `sendMessage({concierge:true})`) → `useRunChat.ts` → POST `/api/runs/{id}/messages` → `chat_router.py:203` CHANNEL_CONCIERGE → `run_commands.py:1136` → `concierge.py:267` `converse` → SSE `chat_reply_chunk`.
- Concierge context TODAY (`concierge.py:414-444` `_compose_system_prompt`): fixed role + `ctx.conversation_context` (NEVER set on the live path) + `compiled.chat` (empty `{}`). Plus this-run-only READ tools. It has NO knowledge of chainable next-workflows. `_ConciergeCtx` (`run_commands.py:720-738`) carries only `run_id/scoped_store/owner_id/workspace_id/model/compiled`.
- **The gap:** there is NO server-side "which workflow can consume this" logic. The only chain policy is the FE static `CHAIN_OPTIONS`. To stay MVP AND avoid a dual implementation (INV-3), do NOT duplicate that policy in the backend.
- **RECOMMENDED approach (BE-1, primary):** thread the FE-computed chain suggestions into the Concierge turn. The FE already has `laneSuggestions` on a completed run; include them as an ADDITIVE optional field on the existing chat POST (e.g. `chain_hints: [{id,label}]` on the `/messages` body / `Launch/ChatTurn` payload), thread onto `_ConciergeCtx` (new optional field, mirroring how M3 added `compiled`), and render into the system prompt in `_compose_system_prompt` as a GENERIC data block (e.g. "This completed run can be chained into: Prototype, PPT. If the user asks what to do next, you may suggest running one of these with this run's output."). Single source of truth (FE `CHAIN_OPTIONS`); the Concierge merely reflects it. Read via `getattr` so absence degrades gracefully.
- **Constraints on this change (hard):** the block must be GENERIC DATA — NO `pipeline_type`/workflow-name `if/elif` branch inside `concierge.py` or the ctx build (INV-1/SC-001; the existing `_extract_chain_context` name-branch is app-layer-tolerated but is the anti-pattern to avoid — do not add a new one). The chat POST field is ADDITIVE + optional; every non-Concierge branch keeps its exact JSON contract; the Concierge reply still streams over the existing `chat_reply_chunk`/`chat_reply` frames (NO new event type). No migration.
- **Alternative (BE-2, only if the checker rejects BE-1):** compute the chainable-next list server-side from the existing `GET /api/workflows` `user_launchable` catalogue (`workflows.py:171`) filtered by the run's type, thread onto `_ConciergeCtx`. Server-authoritative but risks diverging from the FE curated `CHAIN_OPTIONS` (chips vs Concierge could suggest different sets) — acceptable only if kept consistent. Planner + plan-checker settle BE-1 vs BE-2; default to BE-1 (non-dual, matches the chips exactly).
- Optionally also inject the run's own deliverable name (`ctx.compiled.deliverable`, already on ctx, currently unread at `concierge.py:437`) so the suggestion is grounded — small and safe, but secondary.

### Change 3 — FE chat input auto-grow (VERIFIED fixed-height)
- `FreeTextComposer` (`RunChatLane.tsx:698-772+`) renders `<textarea rows={1} … className="… resize-none …">` (`:734-747`). It does NOT grow with content.
- **Decision:** make the textarea auto-resize to its content height on input (up to a max height, e.g. ~5–6 rows / a `max-h`), then overflow-scroll. Standard pattern: a `ref` + an effect/handler that sets `el.style.height = 'auto'; el.style.height = min(scrollHeight, MAX) + 'px'` on value change, reset to one row after send (`setValue("")` at `:717` must also reset height). Keep `resize-none` (no manual drag handle), keep Enter=send / Shift+Enter=newline (`:737-742`). This applies to the single `FreeTextComposer` component, so it benefits ALL composer states (clarify/gate/complete/terminal), which is desirable. Preserve existing styling/tokens; do not change the container chrome (`:733`).
