# Quick task 260812-4ss

Three defects that live in the same reopen-replay path — two of them in the same
expression. Fixed as ONE change because fixing any one alone still leaves a wrong
number on the screen.

Root causes are already proven by the deep investigation
(`scratchpad/REOPEN-REPLAY-ANALYSIS.md`); this plan does not re-diagnose them.

## The three defects

| id | defect | site | mechanism |
|---|---|---|---|
| **ISS-080** | banner over-counts by exactly 2x on reopen | `useWorkflow.ts:369-376` | `agentStartCounts[agentId] += 1` has NO identity key, so it counts *deliveries*, not *distinct events*. On reopen each durable event is delivered twice (REST replay + SSE replay) because the trailing same-run `pipeline_start` fires `resetReplayState` (`page.tsx:774`) and wipes the dedupe seen-set mid-replay. |
| **ISS-081** | banner over-counts ~10x on any live prototype build | `useWorkflow.ts:213-219` | `deriveSpecRevisionCount` takes `max` over **all** agents; `prototype-build` restarts once per task, so a one-revision run reads 10. |
| **ISS-075** | reopened run's trace repaints all-idle ("0 / 5 agents") | `useWorkflow.ts:252-266,274,277` | the log's last agents-touching frame is a resume `pipeline_start` with `resume_offset: 0`, which REBUILDS every agent as `idle` and zeroes `completedCount`. |

**Shared missing concept:** the FE has no predicate for *"this `pipeline_start`
re-announces the run I am already showing"*. FIX-221 introduced it for exactly one
field (`useWorkflow.ts:306-309`). This task promotes it (INV-12: extend, don't add a
second one).

## Tasks

### T1 — close the test gap FIRST (RED before GREEN)

All 15 FIX-221 tests call `runFrames(REAL_FRAMES)` exactly once: they vary frame
*order* but never *multiplicity*, which is why a fix with 15 green tests still
over-counted in a real browser.

Add to `frontend/src/hooks/useWorkflow.specRevisionCount.test.ts`:

1. **duplicate delivery** — `runFrames([...REAL_FRAMES, ...REAL_FRAMES])` must still
   yield 2. (Today: 5.)
2. **build-loop shape** — run `6e38b9a7`'s real agent_start shape (build restarting 11x
   for ONE revision) must yield 1. (Today: 10.)
3. **roster survives the trailing resume frame** — a same-run `pipeline_start` with
   `resume_offset: 0` arriving after three agents are `done` must not downgrade them to
   `idle` nor zero `completedCount`. (Today: all idle, 0.)

The REAL_FRAMES fixtures gain `event_id`/`seq` stamps, which every durable row and
every live SSE event actually carries — the un-stamped fixtures were themselves part of
why the multiplicity bug was invisible.

Verify: each new test observed RED against unmodified source, GREEN after T2/T3.

### T2 — identity-keyed restart history (ISS-080) + head-scoped derivation (ISS-081)

`frontend/src/types/index.ts`, `frontend/src/hooks/useWorkflow.ts`,
`frontend/src/hooks/useRunStateStore.ts`.

- REPLACE `agentStartCounts?: Record<string, number>` with
  `agentStartEventIds?: Record<string, string[]>` — a SET of event identities per agent
  (INV-3/INV-12: replace, do not shadow). Adding an id that is already present is a
  no-op, so the value is immune to any delivery multiplicity from any transport.
  Un-stamped legacy frames (no `event_id`, no `seq`) fall through un-deduped exactly as
  `shouldApplyEvent` already treats them (`wsReplayState.ts:36`).
- `deriveSpecRevisionCount` counts restarts of **the pipeline head** (`agents[0]`), not
  `max` over all agents.
  **SC-001 safety:** the head is *positional* — the first step of whatever roster the
  compiled manifest emitted on `pipeline_start`. No agent id, no workflow name, no
  artifact `kind`. Verified against both real runs: `d5dbc9f2` head=3 starts -> 2 (truth
  2); `6e38b9a7` head=2 starts -> 1 (truth 1, build's 11 ignored).
- Single writer (`useRunStateStore.ts:424`) passes the pipeline state instead of the
  bare counts map, so the derivation can see the roster.

### T3 — same-run re-announce predicate (ISS-075 + the class-level half of ISS-080)

`frontend/src/hooks/useWorkflow.ts`, `frontend/src/app/dashboard/page.tsx`.

- Reducer: compute `isSameRunReannounce` ONCE inside the `pipeline_start` updater and
  use it for (a) MERGING the roster — identity fields from the frame, live
  `status`/`output`/`duration`/tokens preserved — (b) `completedCount` /
  `currentAgentIndex` as `max(existing, resumeOffset)`, (c) the proto task carry-overs,
  (d) the existing restart-history carry.
- `page.tsx`: skip `resetReplayState` when the `pipeline_start` names the run this tab
  is already tracking. Scope: `resetReplayState` ONLY — the four sibling clears
  (`reviewGateData`, `questionnaireData`, `activePipelineRunId`, `lastCancelledRunId`)
  are still wanted on a genuine resume and are left untouched.
- The predicate is captured BEFORE the launch-window block re-points
  `trackedRunIdRef`, or a fresh launch would misread as "same run".

**Engine untouched.** Changing `resume_offset` emission would move the characterization
goldens; the investigation is explicit that the backend must not be touched.
