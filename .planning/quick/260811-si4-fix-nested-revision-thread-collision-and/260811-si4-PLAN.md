<decision>
## The coupling, resolved — with evidence

The brief asks for a deliberate choice between (i) wiring B up and giving A stack discipline,
and (ii) withdrawing the affordance at the re-opened gate. **Three facts, each REPRODUCED
offline during planning against `c0d7b46b`, change the shape of that choice.**

### Fact 1 — nesting is ALREADY reachable and does NOT depend on fixing B

The analyze re-run inside the sub-pipeline is a full `_run_agent`, so it opens its own live
post-stream gate (`:4353`) with `update_specs_eligible=True`. Clicking there re-enters
consumer C at `:4444` and starts a depth-2 pass **today**. Probe, one revision cycle with a
second click at that in-pass gate:

```
thread_ids (7), unique=4:
  probe-nest:story-estimator
  probe-nest:domain-analyst:rev1   probe-nest:epic-architect:rev1   probe-nest:story-estimator:rev1
  probe-nest:domain-analyst:rev1   probe-nest:epic-architect:rev1   probe-nest:story-estimator:rev1
```

So Defect A is **not** a consequence of fixing B. It is a live, independent defect, and it
would survive option (ii) untouched.

### Fact 2 — wiring B creates NO nesting; it is a SIBLING call

`_run_spec_revision_sub_pipeline`'s `finally` (`:5325`) runs *before* its terminal yield
(`:5335`), and consumer C's `async for` (`:4480-4512`) runs the generator to exhaustion before
`break`ing. By the time control reaches the re-opened gate the pass is fully unwound. Probe,
`ectx.revision_attempt` sampled inside the gate at each firing of one cycle:

```
[0] outer first-pass gate                      revision_attempt=0  ctx_set=False
[1] in-pass analyze gate (inside sub-pipeline) revision_attempt=1  ctx_set=True
[2] re-opened gate (after sub-pipeline)        revision_attempt=0  ctx_set=False
```

A sub-pipeline call from `:3545` therefore sits at the SAME stack depth as the one at `:4444`
— the REDO-GATE F2 flat-loop shape, not recursion. The brief's premise that "B's obvious fix
is exactly what creates the depth-2 nesting" is, verifiably, not the case.

### Fact 3 — (ii) would be dishonest, and the engine's own comment says so

`engine.py:4513-4514` states the re-opened gate exists "so the user can Accept **or request
another revision cycle**." A second cycle is not a feature to decide on: it already ships and
already runs — one gate earlier, at the in-pass gate, where it works apart from the id
collision. Suppressing the affordance at the re-opened gate would leave two visually identical
gates for the same agent, back to back, one accepting revisions and one refusing — hiding a
working capability rather than fixing a broken one.

### Chosen: (i), in its flat-sibling form

1. **Wire B at `:3545`** as a flat sibling cycle. The outer `_run_agent`'s
   `spec_revision_attempt` local already increments 1 → 2 → 3 across sibling cycles, so cycle 2
   naturally threads `:rev2`.
2. **Withhold the affordance while a pass is in flight** —
   `update_specs_eligible = kind_is_eligible and not ectx.revision_attempt`. Verified against
   the probe above: True at the outer gate, **False** at the in-pass gate, True at the
   re-opened gate. This is not suppression of a capability; it moves the single supported
   entry point to the one gate where the cycle is flat, and the user reaches it with the same
   number of clicks. Revision cycles become uniformly flat, matching the F2 precedent that
   exists precisely because unbounded human-paced operations must not recurse.
3. **Fix A structurally anyway.** `_run_review_gate:5470` acts on `action == "update_specs"`
   **without ever consulting `update_specs_eligible`** — the flag is an FE affordance, not a
   server-side fence. A replayed or crafted gate POST at an in-pass gate still nests. So the
   sub-pipeline is made properly re-entrant: a monotone per-run high-water index (no two passes
   at any depth can mint the same `:rev{N}`) and a save/restore `finally` (an inner pass cannot
   strip the outer's index or report). Verified pre-fix clobber:

   ```
   [3] gate after the NESTED pass returned, outer pass still on the stack:
       revision_attempt=0  ctx_set=False      <-- outer's 1 / its report, both destroyed
   ```

**Deliberately NOT done:** server-side *enforcement* of `update_specs_eligible` (it would
change gate semantics and is unnecessary once nesting is safe), and collapsing the redundant
double analyze gate (the real UX fix, a behaviour change outside this brief). Both are
ALREADY FILED — the double gate as **ISS-052** and the missing enforcement as **ISS-053**
(`.planning/ISSUES-REGISTER.md:89-90`, landed in `de42a7bf` after this plan was first drafted).
Task 3 cross-references them; it must NOT re-file them.
</decision>
