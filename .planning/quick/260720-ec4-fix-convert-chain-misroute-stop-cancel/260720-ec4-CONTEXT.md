## BUG-1 — "convert it into presentation" (chat) launches a REVISION instead of chaining

### Root cause (VERIFIED)
`classifyFreeText` (`frontend/src/components/chat/RunChatLane.tsx:300-305`) is binary (`"ask"` | `"change"`). `CHANGE_INTENT` (`:247`) is a 40+-verb alternation that LITERALLY includes `convert` (also `turn`, `make`, `set`), and it is tested FIRST (`:302 if (CHANGE_INTENT.test(t)) return "change"`), ASK second, default `"change"`. So "convert it into presentation" → `"change"`. On a completed run `handleFreeText` (`:961-992`, esp. the `runState === "complete"` block ~`:984`) routes `"change"` → `setHeldRefinement(text)` → the "Run a refinement with this change?" chip (`renderHeldRefinement`, ~`:1069`) → `confirmRefinement` → `onRevise(heldRefinement)` → `DashboardLayout.tsx:1788` `activeReviseHandler` → `handleRevisePpt` (`:502-535`, `POST /revisions`) / `handleRevisePrototype` (`:574-587`, `*_revision` launch) — a **revision of the CURRENT run**, feeding the whole sentence to the revision agent. It never reaches the Concierge ASK branch (so c72's `chain_hints` never engage) nor the chain path. Pre-existing since Phase 43 (the regex was born with `convert` in it; commit `7cf574d1`, never edited); 44-02 added the confirm chip (gating) not the classification.

### The existing chain seam to route INTO (do not rebuild)
The visual "Presentation"/"Prototype" chips (c72) fire `onSuggestion(id)` → `handleLaneSuggestion` (`DashboardLayout.tsx:1435-1437`) → `handleChainPipeline` (`:923-961`) — the correct chain-into-a-new-workflow action. `RunChatLane` already receives `suggestions: {id,label}[]` (destructured `:798`) and `onSuggestion` (`:799`); `laneSuggestions` = `CHAIN_OPTIONS` minus the current base type, mapped to `{id, label}` (`DashboardLayout.tsx:1430-1434`; labels e.g. `{id:"ppt", label:"Presentation"}`, `{id:"prototype", label:"Prototype"}`).

### Fix (Task 1 — FE-only, INV-1/SC-001-safe)
In `RunChatLane.tsx`, detect a **chain-into-a-known-target** phrase BEFORE the change-check and route it to the chain action instead of a revision:
- Add a small helper (e.g. `matchChainTarget(text, suggestions): id | null`) that fires ONLY when the text has a transform-shape (`\b(convert|turn|make|transform|change|render|export|generate)\b .* \b(into|to|as)\b`) AND its tail names one of the CURRENTLY-AVAILABLE `suggestions` — matched case-insensitively against each `suggestion.label` (word/substring). Returns the matched `suggestion.id` or null. **This is the SC-001-safe key: match against the DATA-DRIVEN `suggestions[].label` passed into the lane, NEVER a hardcoded `"ppt"`/`"presentation"`/workflow-name literal.** (If broader synonym coverage — "deck"/"slides"/"mvp" — is wanted, the planner MAY enrich `laneSuggestions` with a `keywords` field sourced generically from `CHAIN_OPTIONS.description` in `DashboardLayout.tsx:1430` + `workflowChaining.ts`; still data-driven, still no literal. Keep it optional — label-match satisfies the reported "presentation" case.)
- In `handleFreeText`, on a completed run, call the matcher FIRST: if it returns an id AND `onSuggestion` is present → `onSuggestion(id)` and return (fire the chain); else fall through to the existing `classifyFreeText` ask/change behavior UNCHANGED. **Require a named available target** — no match ⇒ existing behavior, so genuine same-run edits ("convert the buttons into pills", "make it bigger", any transform with no available chain target) still classify as `"change"` → revise. Do NOT reorder or weaken `CHANGE_INTENT`/`ASK_INTENT` themselves.
- Keep everything else (`setReplyPending`, the ASK `chain_hints` fold from c72, the plain-send fallthrough) intact.

## BUG-2 — Stop button is a no-op when the run is parked at clarify or a declared gate

### Root cause (VERIFIED)
Stop is COOPERATIVE (Phase 16 — register :1661/:1679): FE `handleStopPipeline` (`DashboardLayout.tsx:1352-1360`) → `POST /api/runs/{id}/cancel` (`api.ts:703-713`) → `run_commands.py:285-306` `_CANCEL_EVENTS[run_id].set()`; the FE binds the LIVE run id (`pipelineState.pipelineRunId ?? activePipelineRunId` — NOT the viewed run; the 260716 binding class is refuted), single-worker uvicorn + single nginx upstream (multi-process refuted), and `_CANCEL_EVENTS[run_id]` is present for the whole live run (cleaned only in terminal `finally`, `run_commands.py:2018-2019/2214-2215`). The endpoint sets the SAME `asyncio.Event` object the engine holds. Stop is a no-op ONLY because the engine is parked in a cancel-UNAWARE blocking wait in two states:

- **Condition A — parked at CLARIFY (broadest; the strong hypothesis for what the user hit — every workflow clarifies first).** `cancel_event` appears **0×** in `backend/agents/execution_engine/clarify_engine.py` (verified `grep -c` = 0); `ClarifyEngine.run` (`:191`) blocks at `await event.wait()` (`:325`) on the questionnaire resume event; the engine's clarify DRAIN loop (`backend/agents/execution_engine/engine.py` ~`:1928`, `event = await asyncio.wait_for(event_queue.get(), timeout=1.0)` — a 1-second heartbeat) never checks `cancel_event`. So Stop sets the flag (the endpoint even returns `cancelled: true`) but nothing acts until the user manually answers/skips.
- **Condition B — parked at a DECLARED `gate: human` step (composed/custom workflows).** The delegate `KernelServices.run_human_gate` (`backend/agents/execution_engine/kernel_services.py:1079`, call at `:1109`) invokes `self._engine._run_review_gate(...)` WITHOUT `cancel_event`, so it blocks at `await event.wait()` (`engine.py:5147`) on only the review event. By contrast the INLINE gate sites (`engine.py:3107/3251/4091`) DO pass `cancel_event` → the cancel-aware race (`engine.py:5126-5143`) fires → Stop works there.

Stop already WORKS during active model streaming (`engine.py:3592` per-chunk `cancel_event.is_set()` → `CancelledError`) and at build/validation boundaries (`:4408`).

### Fix (Task 2 — engine-side, REUSE the shipped cooperative-cancel pattern)
- **Condition A (recommended: engine-loop check — keeps the cancel policy engine-owned, no ClarifyEngine signature change, INV-1):** in the engine's clarify drain loop (`engine.py` ~`:1928`, which already wakes on the 1s `wait_for` timeout), when `cancel_event` is set → cancel the clarify task and yield the existing terminal `pipeline_cancelled`, then return (mirror the inline-gate race's action). - **Condition B:** thread `cancel_event` from `KernelServices.run_human_gate` (`kernel_services.py:1079/1109`) into `_run_review_gate(..., cancel_event=…)` so the EXISTING cancel-aware race (`engine.py:5126-5143`) fires exactly as it does at the inline sites.
