# Quick task 260812-77g — outcome

The artifact-version picker now moves the **whole** agent panel. Selecting v1 repaints
the "Specification · N pages" / "Governance checks" card, not only the raw output
underneath it.

## What was actually wrong

Not the picker. `AgentDetailPanel` held **two** answers to *"what am I looking at"*:
`shownOutput = viewed?.content ?? agent.output` reached exactly one of four consumers
(`OutputPreviewSection`), while the other three went back to the agent for the same
information — `parseSpecSections(agent.output)`, `parseSpecOverview(agent.output)` and
`<AnalysisPreview content={agent.output}/>` — because `SettledArtifactCards` was handed
the raw `agent`. The card TYPE was chosen the same way. So the prominent card always
showed the newest version while the less prominent section changed under it, and the
user reasonably concluded the control was inert.

## The change (`frontend/src/components/results/AgentDetailPanel.tsx`)

| line(s) | change |
|---|---|
| 745-753 | `displayed = viewed ? { ...agent, output: viewed.content } : agent` — this agent AS OF the version on screen. `shownOutput` derives **from** `displayed`, so the two names provably cannot disagree. |
| 770 | `deriveArtifactCardModel(displayed, …)` — the discriminator follows the selection. |
| 608-616, 687 | `SettledArtifactCards` prop `agent: AgentRunState` **replaced** by `output: string`; the three internal `agent.output` reads become `output`. |
| 856 | `<SettledArtifactCards output={shownOutput} model={cardModel} />` |
| 121-126, 838-848 | the two deliberate boundaries documented in-line. |

`SettledArtifactCards` is module-local, so the exported `deriveArtifactCardModel`
signature is untouched and the 42-09 card tests needed no edit.

## Decision — `discriminateArtifact` follows the selection

Yes, deliberately. It picks **which renderer draws the content**, and an artifact's type
is a property of that artifact, not of the agent. Two consequences of the alternative:
an older version of a different shape renders through the wrong renderer, and — the
concrete case — FIX-039 clears `agent.output` on every `agent_start`, so during an
`update_specs` cycle `discriminateArtifact("")` returns `null` and the panel showed v1's
text with **no card at all**, at exactly the moment ISS-065 exists to serve. Pinning the
type to the latest is the same bug one level up. It is a pure content sniff, so following
the selection costs nothing.

## Left pinned to the agent, on purpose

- `validationPassed` / `validationIssues` (checks badge), `protoCompletedTasks` (task
  rows), `dagEdges` (handoff) — run/agent state, not artifact content, and not versioned
  anywhere in the FE. Following the selection would mean inventing data. Filed as
  **ISS-087**.
- The `(live)` reasoning card keeps reading `agent.output`: it is labelled live, and
  pinning it to an older version would leave no way to watch the re-run it announces.

Hiding the cards while a version is selected was explicitly rejected — the cards are the
information the user came for.

## Harness lesson (recorded — it nearly cost real money)

The reusable *"sweep every `header button` until Run History appears"* idiom in the older
live scripts clicks the sidebar **run pill** and opens whatever run is active — during
this task that was a `waiting_for_user` prototype parked at a clarify gate. Drive the
"Jump back in" card by its exact accessible name
(`getByRole('button', { name: /<run title>/ })`) instead, and open an agent's L2 detail
via `getByTestId('steps-agent-row').filter({ hasText: <agent name> })` — a bare
`getByText(<agent name>)` matches the chat transcript on the left and is intercepted.
