# Quick 260812-8j4: a redo must show the agent its own prior output — Summary

**"Request changes" now hands the agent the document it is being asked to change.** The
re-dispatch carries the agent's own prior output, rendered *before* the instruction, at all
three gate consumer sites — with zero new state, zero new prompt blocks, two consumer copies
deleted, and the first (non-redo) dispatch proven byte-identical.

## The defect, and why it was not a routing accident

The engine modelled `redo` as **regenerate from scratch** and *enforced* it: `_run_agent`
published exactly one thing before re-composing — `ectx.redo_directive` — then minted a fresh
`:redo{N}` checkpoint thread whose stated purpose is to stop the model seeing its rejected
output. The UI ships that same action as **"Request changes"** with an instruction box, so the
user writes a delta and the model, having no subject, writes only the delta.

Live measurement (run `a0d17afa`): the owner asked the Task Planner to "add 2 more pages" and
got **one** task. `task_list` v1 → v2 = **12,542 → 3,495 chars**, headings **7 → 1**, **0 of 7
kept**. The redo dispatch was **106 bytes** larger than the first — the instruction alone.

Three channels were closed at once, which is why nothing accidentally compensated:

| channel | why it could not carry the prior output |
|---|---|
| `consumes` routing | `_filter_consumed_outputs` **breaks** on `upstream.id == spec.id` — self-consumption is structurally impossible |
| checkpoint replay | the redo deliberately threads a FRESH `{run}:{agent}:redo{N}` id |
| filesystem | gated authoring agents declare `tools: []` |

**Root cause at the level of a decision:** FIX-217 hit this identical fork on the revision path
and resolved it by pairing the fresh thread (D3) **with** an explicit prior-artifact injection
(D1). **P23 shipped only the fresh-thread half of that pair.** This task completes the pairing.

## What changed

| # | File | What |
|---|---|---|
| 1 | `engine.py` | New **`_consume_redo`** — the ONE `_gate_redo` consumer, driven by all three gate branches. Returns `(directive, derived_from, prior_artifact)`; `redo_attempt` stays at the call site, mirroring `spec_revision_attempt` at the `_consume_update_specs` sites. |
| 2 | `engine.py` | The publish site in `_run_agent`'s redo loop **save/restores** `ectx.spec_revision_prior_artifact` around the one `_compose_context_message` call, inside a `try/finally`. |
| 3 | `engine.py` | The `PRIOR ARTIFACT UNDER REVISION` block **moved above** `ADDITIONAL INSTRUCTIONS (REVISE)`, and its prose generalised. |
| 4 | `context.py` | The field's doc records **two publishers, one field, one renderer**. |

Exactly **one** `_gate_redo` consumer implementation remains, with **three** call sites.

**The subject is read off the same kind-scoped max-version ref the lineage stamp already
computes** — no extra read, and kind-scoped by construction. That last part matters: a
producer-only lookup would break on `prototype-build`, which writes both `html_file` **and**
`file_bundle`, so max-version across kinds would serve the wrong document.

## Decisions taken, with the reasoning that binds them

- **Reuse FIX-217's seam; do not mint a second one (INV-12).** One field, one renderer, two
  publishers. A redo-specific field plus a `=== PRIOR OUTPUT ===` block would be two things
  meaning one thing, diverging on the next edit.
- **Save/restore, never clear.** A redo can fire at a gate opened *inside* a revision pass, and
  zeroing would strip the outer pass's subject mid-flight — the FIX-218 defect-A shape.
  **Side benefit:** a redo inside a pass now publishes the *rejected draft* rather than the
  pre-pass version the pass read once before its loop, closing the "specify-inside-a-pass
  staleness" open question from the analysis §14.
- **Block order is load-bearing.** The REVISE block was appended *above* the prior-artifact
  block, so reusing the seam without moving it would have read instructions-first,
  subject-second — the inverse of FIX-217's rule. INV-3-safe because `redo_directive` is empty
  on the revision path, so PRIOR → REPORT keeps its relative order there.
- **Blank redo stays a regenerate.** The FE's own placeholder reads *"leave blank to just
  regenerate"*, and that is precisely the P23 semantics the fresh thread enforces. Only a
  non-blank instruction asks for an amendment.
- **Per-task build dispatch is skipped.** It already carries a compacted skeleton of the same
  document; injecting the full artifact would double-inject the deliverable.
- **A `finally` around the compose call.** Not gold-plating — the change widened a pre-existing
  unguarded window from one published field to two, and `_compose_context_message` reads
  template / design-system files, so a missing one propagates out of the one region *not*
  covered by `_run_agent`'s own `try`. Byte-identical on the success path.

**Collapsing the three consumers closed the re-open branch's thin-copy defects for free:** it
set only the directive, so it also lost `derived_from` lineage, left a **duplicate `results`
entry** for the same `agent_id`, and wrote **no audit row** — under-seeding
`_seed_gate_reentry_attempts` and risking a colliding `:redo{N}` after a restart. All three are
now asserted by test #5.

## Rejected, with the reason (do not re-adopt)

- **Drop the `:redo{N}` suffix so the checkpointer replays the prior turn.** A one-line deletion
  that appears to work. It revives the documented P23 "it's already done" failure; and it makes
  correctness depend on replay, which FIX-217 D3 proved is **empty after a restart** on the
  InMemory saver — so the redo would work in one session and silently fail after a restart, the
  worst possible failure shape.
- **Add the agent to its own `consumes`.** Structurally impossible.
- **Relabel the FE button.** Amend-don't-regenerate is the *desired* product behaviour; the
  engine should honour what the UI promises.

## Deviations from plan

**One — a `try/finally` around the compose call, not in the plan.** Found during adversarial
self-review: the plan's straight-line save/restore left both published fields stranded if
`_compose_context_message` itself raised, which is the one region outside `_run_agent`'s own
`try`. Since the change *widened* that pre-existing window from one field to two, owning it is
part of the change (fable-coding rule 5). Two lines; byte-identical on the success path;
re-verified against the full gate battery afterwards.
