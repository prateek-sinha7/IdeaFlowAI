# Quick 260812-8j4 — ISS-086: a redo must show the agent its own prior output

## The defect, in one sentence

The engine models `redo` as **regenerate from scratch** and enforces it, but the UI ships
that action as **"Request changes"** with an instruction box — so a user writes a delta
("add 2 more pages"), the model receives the delta with **no subject**, and it returns only
the delta. Measured live: `task_list` v1 → v2 = 12,542 → 3,495 chars, headings 7 → 1, **0 of
7 kept**.

Root cause (a decision, not a mechanism): Phase 23 modelled a re-run as a regeneration and
minted a fresh `:redo{N}` checkpoint thread to *stop* the model seeing its rejected output.
FIX-217 hit the identical fork on the `update_specs` revision path and resolved it by pairing
the fresh thread **with** an explicit prior-artifact injection. **P23 shipped only the
fresh-thread half of that pair. This task completes the pairing.**

Three channels are closed at once, so the injected block is the only one left:

| channel | why it cannot carry the prior output | evidence |
|---|---|---|
| `consumes` routing | `_filter_consumed_outputs` **breaks** on `upstream.id == spec.id` | engine.py:8642-8644 |
| checkpoint replay | the redo deliberately threads a FRESH `{run}:{agent}:redo{N}` id | engine.py:3751-3759 |
| filesystem | gated authoring agents declare `tools: []` | FIX-217; `agents/prompts/*/AGENT.md` |

## Scope fence

Fix the engine so a **non-blank** redo re-dispatch carries the agent's own prior output,
generically, at all three consumer sites. **Not** in scope: relabelling the FE button
(the owner's intent — amend, don't regenerate — is the desired product behaviour);
`redoable` server-side eligibility (ISS-053's sibling); the tool-bearing-agent
`read_file` channel question.

## Design (accepted — reuses FIX-217's seam, INV-12)

**F1 — one shared `_consume_redo`.** The three `_gate_redo` branches (engine.py:3429 the
RESUME-17 re-entry, :3549 the post-revision re-open, :4459 the live post-stream gate) are
near-identical, and :3549 is a **thin copy** missing `derived_from`, `results.pop()` and the
audit row. Collapse them into one `async` helper returning
`(directive, derived_from, prior_artifact)` — the shape FIX-218 used for
`_consume_update_specs`. `redo_attempt += 1` stays at the call site, mirroring
`spec_revision_attempt` at the `_consume_update_specs` call sites. Collapsing fixes the
thin-copy defects for free.

**F2 — capture the subject where the lineage is already computed.** The live and re-entry
consumers already build the kind-scoped candidate list to stamp `derived_from`; the same
`max(_cands, key=version)` object's `.content` **is** the prior artifact. Zero new reads,
zero new state, and kind-scoped by construction — which sidesteps the multi-kind hazard
(`prototype-build` writes both `html_file` and `file_bundle`; a producer-only lookup would
return the wrong document).

Withheld in two cases:
* **a blank redo** — the FE's own placeholder reads *"leave blank to just regenerate"*, and
  regenerate-from-scratch is exactly the P23 semantics the `:redo{N}` thread exists for;
* **a per-task build dispatch** (`ectx.build_task_number` set) — that dispatch already
  carries a compacted skeleton of the same document.

**F3 — publish on the EXISTING seam, with save/restore, at the ONE publish site**
(engine.py:3619-3627). `spec_revision_prior_artifact` + its renderer already exist; a second
field and a second block would be the dual implementation the project bans (INV-12).
**Save/restore, not clear** — the FIX-218 defect-A shape: a redo can fire at a gate opened
*inside* a revision pass (proven live, run `ec7fb984`), and clearing would strip the outer
pass's own subject mid-flight. At the outer level the saved value is `""`, so this is
byte-equivalent to a clear (INV-3).

**F4 — move the `PRIOR ARTIFACT` block ABOVE `ADDITIONAL INSTRUCTIONS`, and generalise its
prose.** The REVISE block is appended at engine.py:8867, the prior-artifact block at :8881 —
i.e. instructions before subject, the inverse of FIX-217's stated rule ("subject first,
instructions second"). The prose also reads spec-specific ("the document the analysis report
below refers to") and there is no report on a redo. The move is INV-3-safe: on the
`update_specs` path `redo_directive` is `""`, so PRIOR → REPORT keeps its relative order.

## Invariants

- **SC-001** — keyed on generic scratch fields and the existing kind-scoped lineage
  expression. No agent id, no workflow name. Proven by parametrizing the tests over ids read
  from the registry, across two pipelines.
- **INV-3** — dormant on every non-redo dispatch. Proven twice: 10/10 goldens, and a
  byte-diff of the first dispatch dumped before and after the change.
- **INV-12** — reuses the field, the renderer and the harness; **deletes** two consumer
  copies and one thin copy.
- **INV-1 / INV-2** — kernel learns no workflow name; per-run scratch only.

## Rejected

- **Drop the `:redo{N}` suffix so the checkpointer replays the prior turn.** Revives the
  documented P23 "it's already done" failure, and makes correctness depend on replay that is
  empty after a restart — works in one session, silently fails after a restart.
- **Add the agent to its own `consumes`.** Structurally impossible —
  `_filter_consumed_outputs` breaks on `upstream.id == spec.id`.
- **A redo-specific `redo_prior_output` field + a new block.** Two fields and two blocks
  meaning one thing (INV-12).
