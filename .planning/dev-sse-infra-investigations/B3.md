##### I3. Root cause -- confirmed, corrected, or replaced

**A. The dossier's mechanism is correct.** [V]

CloudWatch Logs addresses a stream by the pair `(logGroupName, logStreamName)`; `CreateLogStream` is
per-group-scoped and "Log stream names must be unique within the log group"
(AWS CloudWatch Logs API Reference, `CreateLogStream`). Two `collect_list` entries that resolve to
the same pair are therefore two independent file tailers writing into one stream object.

Machine-proven against the rendered config rather than read by eye -- I rendered §14's heredoc with
`ENVIRONMENT=dev` and parsed the JSON:

```
$ ENVIRONMENT=dev ENV_TITLE=Dev bash -c \
    '{ echo "cat <<EOF"; sed -n "963,1000p" infra/scripts/bootstrap-ec2.sh; } | bash' \
    > cwagent-rendered.json
$ python3.11 -c "...collections.Counter over (log_group_name, log_stream_name)..."
VALID JSON; collect_list entries: 8
DUPLICATE (group,stream) pairs: {('/velocityai/dev/system', '{instance_id}'): 2}
```

Exactly one duplicate pair, exactly the one the dossier names. The full table is in I4.A.

**B. CORRECTION -- the dossier understates the harm, and misses a second defect on the same two
entries.** [V, from the AWS agent configuration reference]

The dossier calls the harm "sequence-token contention and interleaved output". Two refinements:

1. *Sequence tokens are no longer the mechanism.* `PutLogEvents` has not required a
   `sequenceToken` since 2023; a stale token is accepted rather than rejected. The real harm is
   simpler and worse: **two tailers, one ordered stream, no field distinguishing which file a line
   came from.** An auditd `type=SYSCALL msg=audit(...)` record and an unattended-upgrades
   `INFO Starting unattended upgrades script` line land adjacent with nothing to tell them apart,
   so any future metric filter or Insights query over `/velocityai/<env>/system` must
   pattern-discriminate on message content instead of filtering by stream. That is the durable
   cost, and it is why this is worth fixing before B1/B2 make the group live rather than after.

2. *`"timezone": "UTC"` is inert on **all eight** entries.* The agent reference states plainly for
   `timezone`: "This parameter is ignored if you don't specify a value for `timestamp_format`."
   And for `timestamp_format`: "If you omit this field, the current time is used." **No entry in
   the `collect_list` sets `timestamp_format`** (proven in the I4.A table -- the `ts_fmt` column is
   `-` for all eight). So today every shipped event would carry the agent's *ingestion* time, and
   the `"timezone": "UTC"` on every line is decoration. This is invisible today only because B1
   means nothing has ever shipped.

**C. Why it occurred -- the dossier's account is right, with one addition.**

The dossier says `{instance_id}` "is the natural stream name for a host-scoped log, and it is
correct for *one* file per group". True. The addition: the config was **materialized verbatim from
`docs/SIMPLE_AWS_DEPLOYMENT.md` Section 10.1**, which the §14 header comment says explicitly
(`bootstrap-ec2.sh:954`: "materialized from SIMPLE_AWS_DEPLOYMENT.md 10.1"). That document
(`:1236-1242`) has the same seven entries with the same duplicate pair. So the defect was
*inherited*, not authored -- which means fixing only the script leaves the generator intact and a
future re-materialization reintroduces it. My fix therefore updates both (I5, step 5).

**D. Causal chain, trigger to symptom.**

```
docs/SIMPLE_AWS_DEPLOYMENT.md 10.1 authored with 2 files -> /flowin/prod/system, both {instance_id}
  -> bootstrap-ec2.sh 14 materialised verbatim (577523b9), prefix-renamed (e1a3a495)
  -> agent config on disk declares 2 tailers with an identical (group, stream) pair
  -> [today] B1 crash-loop means the agent never runs, so the collision is latent
```

##### I5. The complete fix

**Shape.** One contiguous rewrite of `bootstrap-ec2.sh:988-995` (the eight `collect_list` entry

**The naming rule this establishes (state it in the file, because five agents edit this block):**

> Every `collect_list` entry's `log_stream_name` is `{instance_id}/<source-slug>`, where
> `<source-slug>` is unique across the whole list. `{instance_id}` alone is banned.

*Why the uniform scheme and not just renaming the two colliding entries?* Because the minimal
variant leaves five entries reading `{instance_id}`, and the very next edit to this block -- **B4,
which adds a third file to the `system` group** -- is an author copying a neighbouring line. Under
the minimal variant the neighbours they copy are `{instance_id}`, and B3 comes straight back. Under
the uniform variant the pattern is self-evident and the rule is checkable by inspection. It costs
nothing: I4.B proves no consumer reads a stream name, and B1 means no stream exists yet to orphan.
The `{instance_id}/docker` entry already in the file is the convention -- this applies it
consistently rather than inventing one.

*Why no `multi_line_start_pattern`, when the brief asked me to check it.* I checked, and the honest
answer is that adding it is a net risk here:

- Default behaviour with the field omitted is documented: "multi-line mode is disabled, and any line
  that begins with a non-whitespace character closes the previous log message and starts a new log
  message" [V]. So whitespace-indented continuations already attach to their parent event. That is
  correct for `audit.log` (one record per line, every line starts `type=`) and adequate for
  `unattended-upgrades.log` and `postgres` (whose DETAIL/HINT/STATEMENT continuations are TAB-indented).
- The natural value would be `"multi_line_start_pattern": "{timestamp_format}"`, which means "a new
  event starts on a line matching the timestamp regex". If the `timestamp_format` guess is even
  slightly wrong, **no line matches and the agent concatenates indefinitely** -- a far worse failure
  than the one being fixed. A wrong `timestamp_format` *alone* degrades safely (unmatched lines fall
  back to ingestion time, i.e. today's behaviour); a wrong `timestamp_format` *plus*
  `{timestamp_format}` multi-line does not.
- I cannot observe the file to eliminate the guess. So: `timestamp_format` yes (safe degradation),
  `multi_line_start_pattern` no. It is registered as an optional follow-up gated on an on-box
  observation (I11 / I12.6).

**Step 4 (repo, durable) -- the offline validator that makes the rule checkable.**

```bash
#!/usr/bin/env bash
# Renders §14's CloudWatch-agent config out of bootstrap-ec2.sh and asserts the
# invariants that block cannot express in JSON:
#   1. the rendered document is valid JSON
#   2. every (log_group_name, log_stream_name) pair is unique
#   3. every log_stream_name is a legal CloudWatch stream name (no ':' or '*',
#      1..512 chars once {instance_id} is substituted)
#   4. no entry sets retention_in_days (Terraform owns retention; the instance
#      role has no logs:PutRetentionPolicy)
# Offline, no AWS calls. Run from the repo root.
set -euo pipefail

SCRIPT="${1:-infra/scripts/bootstrap-ec2.sh}"
START=$(grep -n 'amazon-cloudwatch-agent.json <<EOF' "$SCRIPT" | head -1 | cut -d: -f1)
[ -n "$START" ] || { echo "FAIL: could not locate the agent-config heredoc in $SCRIPT" >&2; exit 1; }
BODY_START=$((START + 1))
BODY_END=$(awk -v s="$BODY_START" 'NR>=s && $0=="EOF" {print NR-1; exit}' "$SCRIPT")
[ -n "$BODY_END" ] || { echo "FAIL: could not locate the heredoc terminator" >&2; exit 1; }

RENDERED=$(ENVIRONMENT=dev ENV_TITLE=Dev bash -c \
  "{ echo 'cat <<EOF'; sed -n '${BODY_START},${BODY_END}p' '$SCRIPT'; } | bash")

printf '%s' "$RENDERED" | python3 -c '
import collections, json, re, sys
doc = json.load(sys.stdin)                      # invariant 1
entries = doc["logs"]["logs_collected"]["files"]["collect_list"]
fail = []
pairs = [(e["log_group_name"], e["log_stream_name"]) for e in entries]
for pair, n in collections.Counter(pairs).items():
    if n > 1:
        fail.append("duplicate (group, stream) pair %r used by %d entries" % (pair, n))
for _, stream in pairs:                          # invariant 3
    rendered = stream.replace("{instance_id}", "i-0123456789abcdef0")
    if re.search(r"[:*]", stream):
        fail.append("stream name %r contains a character the CreateLogStream API forbids (: or *)" % stream)
    if not 1 <= len(rendered) <= 512:
        fail.append("stream name %r renders to %d chars (limit 1..512)" % (stream, len(rendered)))
for e in entries:                                # invariant 4
    if "retention_in_days" in e:
        fail.append("entry %r sets retention_in_days; Terraform owns retention" % e["file_path"])
if fail:
    print("FAIL:"); [print("  -", f) for f in fail]; sys.exit(1)
print("OK: %d collect_list entries, all (group, stream) pairs unique, all stream names legal" % len(entries))
'
```

##### I6. Ripple-effect analysis -- assume the fix is wrong; where does it break?

**A. "A `/` in a stream name is rejected by the API."** Falsified. [V]
AWS CloudWatch Logs API Reference, `CreateLogStream`, `logStreamName`: *Length Constraints: Minimum
length of 1. Maximum length of 512. Pattern: `[^:*]*`*, and the naming guidance is explicitly
"Don't use ':' (colon) or '*' (asterisk) characters." `/` is legal. Longest rendered name is
`i-092d5961f5aca87a6/unattended-upgrades` = **39** chars, well under 512 (machine-checked).
Note the confusable: the *agent* documentation lists "a-z, A-Z, 0-9, '_', '-', '/', '.'" as allowed
characters -- **for `log_group_name`, not `log_stream_name`**. Do not carry that restriction across;
the stream constraint is the looser API pattern above.

**B. "The agent will not substitute `{instance_id}` when a literal follows it."** Falsified twice.
[V] The agent reference for `log_stream_name`: "**As part of the name**, you can use `{instance_id}`,
`{hostname}`, `{local_hostname}`, and `{ip_address}` **as variables within the name**" -- partial
substitution is the documented behaviour. And the file already ships `{instance_id}/docker`
(`:995`), authored by the same commit, so the pattern is the config's own precedent rather than
something I am introducing.

**C. "The IAM policy will deny `CreateLogStream` on a slashed stream name."** No. [V]
`infra/terraform/policies/cloudwatch-write.json` grants `CreateLogStream` / `PutLogEvents` /
`DescribeLogStreams` on
`arn:${partition}:logs:${region}:${account_id}:log-group:/velocityai/${environment}/*`. Stream-level
ARNs are `...:log-group:<group>:log-stream:<stream>`; the trailing `*` spans the remainder of the
ARN including the `:log-stream:` segment and anything after it -- **[I]** by ARN structure, but
corroborated in-repo: the monitoring module's own CloudTrail role uses exactly the same idiom,
`resources = ["${aws_cloudwatch_log_group.audit_trail.arn}:*"]` with the comment "scope to
`log-stream:*` under the audit-trail group ARN" (`main.tf:1103-1104`). The `/` inside the stream name
is data, not an ARN delimiter, so it does not escape the wildcard.
Also confirmed: the role has **no** `logs:CreateLogGroup` -- correct, because Terraform pre-creates
all seven groups; and **no** `logs:PutRetentionPolicy` -- which is the second reason step 1 forbids
`retention_in_days`.

**D. Throttling and per-stream behaviour.** More streams is the *safe* direction, not the risky one.
[V for the documented limit, [I] for the operational read]
- `CreateLogStream` is limited to 50 TPS per account/region (API reference). This change adds at
  most 8 (soon 9) `CreateLogStream` calls per agent start, once. Nowhere near 50 TPS.
- `PutLogEvents` quota is per-stream. Two files sharing one stream *concentrate* throughput against
  one stream's quota; splitting them halves the per-stream rate. Splitting strictly reduces
  throttling pressure.
- Sequence tokens: no longer required by `PutLogEvents`, so there is no token-contention regression
  either way. The dossier's "sequence-token contention" framing is stale but its conclusion holds.

**E. Retention and cost.** No change, in either direction. [V]
`retention_in_days` is a property of the **log group**, set by Terraform
(`monitoring/main.tf:45`, `lookup(var.log_retention_overrides, each.value, var.log_retention_days)`).
Streams do not carry retention. CloudWatch Logs bills on ingested bytes and stored bytes; the same
lines split across two streams ingest and store the same bytes. There is no per-stream charge and
no per-stream minimum. **Net cost delta: zero.**
One real trap, already fenced in step 1: if a future editor adds `retention_in_days` to a
`collect_list` entry and a sibling entry in the *same group* has a different value, the agent
"will stop, returning an error" (agent reference). With `system` now multi-entry, that trap is newly
reachable -- hence the explicit ban in the header comment.

**F. Partial application.** Every combination is benign:
- *Repo applied, host not* (the default until C1 lands): dev is unchanged; the fix is inert until
  someone re-runs bootstrap or rebuilds. No regression.
- *Host applied, repo not*: dev is correct; the next instance rebuild reverts it. This is the C1
  failure mode, not a B3 one.
- *Stream names applied, `timestamp_format` omitted* (the step-2 fallback): B3's actual defect is
  fixed; events keep ingestion timestamps, i.e. today's behaviour. Fully acceptable.
- *`timestamp_format` applied and wrong*: unmatched lines fall back to ingestion time -- today's
  behaviour again. This is precisely why no `multi_line_start_pattern` accompanies it (I5).

**G. Concurrency, startup/shutdown, restart, resume, fan-out, two browsers, slow clients,
memory, connection pool.** All not applicable and not hand-waved: this change never enters the
Python process, the SSE stream, the DB, or the browser. It edits a JSON file read once by a Go
daemon at `fetch-config` time. The only "concurrency" in scope is two file tailers inside that
daemon -- which is the thing being separated.

**H. What if the agent restarts mid-write of the config?** The host-side script writes with
`json.dump` to the same path (not atomic). Mitigation: the very next line re-parses the file and
restores the backup on failure, and the agent is only restarted afterwards by B1/B5's single
`fetch-config`. A torn file therefore never reaches a running agent.

**I. The one genuinely irreversible consequence -- and it argues for sequencing.**
CloudWatch log events cannot be moved between streams. If B1 + B2 land and the agent runs for any
period before B3 lands, the interleaved audit+unattended history in the `{instance_id}` stream of
`/velocityai/dev/system` **stays interleaved forever**. The dossier's verification text ("After
B1/B2 land, ...") reads as if B3 follows B1/B2. It should ship *in the same change set*. See I10.

##### I9. Rollback

**Repo half.** `git revert <commit>` on the two commits (I10), or `git checkout <sha> --
infra/scripts/bootstrap-ec2.sh docs/SIMPLE_AWS_DEPLOYMENT.md`. Fully reversible. The next `dev` push
re-uploads the reverted script to
`s3://velocityai-dev-pg-dumps-577954642302/config/bootstrap-ec2.sh` (the `filemd5` `source_hash`
detects the change). Verify with:

```bash
aws s3api head-object --bucket velocityai-dev-pg-dumps-577954642302 \
  --key config/bootstrap-ec2.sh --query '[LastModified,ContentLength]'
```

**Host half.** The step-6 payload writes `/root/cwagent-backup-<UTC-timestamp>/` **before** touching
anything, containing both `amazon-cloudwatch-agent.json` and the `amazon-cloudwatch-agent.d/`
directory (the `fetch-config`-materialised copy, which is what the agent actually reads). To undo:

```bash
BK=/root/cwagent-backup-<TS>
cp -a "$BK/amazon-cloudwatch-agent.json" /opt/aws/amazon-cloudwatch-agent/etc/
cp -a "$BK/agent.d/." /opt/aws/amazon-cloudwatch-agent/etc/amazon-cloudwatch-agent.d/
/opt/aws/amazon-cloudwatch-agent/bin/amazon-cloudwatch-agent-ctl -a fetch-config -m ec2 -s \
  -c file:/opt/aws/amazon-cloudwatch-agent/etc/amazon-cloudwatch-agent.json
/opt/aws/amazon-cloudwatch-agent/bin/amazon-cloudwatch-agent-ctl -m ec2 -a status   # expect "running"
```

**What the pre-change backup MUST capture** (both, or the rollback is incomplete):
1. `/opt/aws/amazon-cloudwatch-agent/etc/amazon-cloudwatch-agent.json` -- the source config.
2. `/opt/aws/amazon-cloudwatch-agent/etc/amazon-cloudwatch-agent.d/` -- the `file_`-prefixed copy
   `fetch-config` materialises. Restoring only (1) without re-running `fetch-config` leaves the
   agent on the *new* config.

**What is NOT reversible:**
- **There are no EBS snapshots on `velocityai-dev-root`** and `delete_on_termination = true`. The
  file-level backup above is the *only* restore point for any host change. This is a property of the
  environment, not of this fix.
- **Log events already written cannot be moved between streams.** Whatever landed in
  `i-092d5961f5aca87a6` before the rename stays there under that name; whatever lands after goes to
  the suffixed streams. Reverting recreates the bare stream and appends to it; it does not
  re-merge history. This is the sequencing argument in I6.I and I10.
- The old bare-`{instance_id}` stream object is not deleted by the rename. It simply stops receiving
  events. If B1+B2 ran before B3, it will sit there holding the interleaved history until its
  group's retention expires it. Leave it -- deleting a stream is a destructive operation with no
  upside, and it is genuine forensic data.

##### I11. Open questions requiring a human decision

1. **The `app` log group's design (B3-ADJ-1) -- genuine product/ops decision, not a config typo.**
   Terraform documents `app` as "journald-shipped uvicorn + Next.js combined log group (filterable
   per unit via `_SYSTEMD_UNIT`)" (`monitoring/main.tf:8-9`), but the agent ships a Docker json-file
   glob into a single stream, and the agent has no container-name placeholder to separate them. The
   `db_conn_error` (`:500`), `ws_disconnect` (`:640`) and `agent_error_rate` (`:855`) metric filters
   all watch this group and work either way (they are group-scoped), so nothing is broken today --
   but per-service triage is impossible.
   - *Option A -- `awslogs` Docker log driver per service in `docker-compose.yml`.* Backend and
     frontend get their own streams natively; drop the glob entry. Cost: compose change, and
     `docker compose logs` stops working locally (the reason the original doc rejected it).
   - *Option B -- journald + `_SYSTEMD_UNIT`,* matching Terraform's documented intent. Cost: a
     different agent collector section and a compose logging-driver change.
   - *Option C -- accept one combined `app` stream* and fix only the false documentation claim.
   **My recommendation: C now, A later.** C is a doc edit inside this change set and removes the
   misleading claim; A is the right long-term shape but is a delivery change (compose + deploy) that
   does not belong in an observability-repair pass.

2. **`unattended-upgrades.log` timestamp format -- needs one on-box read, not a decision.** I could
   not observe it (no SSH permitted; AWS credentials expired). Step 2 makes it a hard pre-flight
   gate with an explicit fallback, so this is a *verification* item rather than a judgement call --
   listed here only so the operator does not skip it.

3. **`timestamp_format` for the remaining six entries -- deferred, needs an owner.** All six
   currently stamp at ingestion time with an inert `"timezone": "UTC"`. `nginx-access` belongs to E1
   (its format is changing). The other five (`nginx-error`, `postgres`, `auth`, `letsencrypt`,
   `app`) have no owner in this dossier. **Recommendation: open a single follow-up** covering all
   five, each gated on an on-box `head -3`, and with the same "no `multi_line_start_pattern` without
   a verified `timestamp_format`" rule. Not folded into B3 -- five unverified format guesses is
   exactly the shortcut this investigation is meant to reject.

No other human decision is required. The stream-name change itself has no product-behaviour,
spend, or ownership implication.

##### I12. Shortcuts and alternatives explicitly rejected

1. **Merge the two files into one group deliberately and just live with it.**
   Rejected: it makes `/velocityai/<env>/system` permanently un-queryable per source. An incident
   responder filtering auditd records would have to pattern-match `type=` prefixes, and any future
   metric filter on the group would have to carry that discriminator too. The cost of the fix is
   eight edited lines; the cost of not fixing is paid on every future query.

2. **Move `unattended-upgrades.log` to its own log group.**
   Rejected: it requires a Terraform change (`monitoring/main.tf` `log_groups`), which drags in a
   `terraform apply` and a new group with its own retention -- a much larger blast radius than
   renaming a stream, for the same outcome. It also contradicts the deliberate grouping decision
   (`system` = host-level OS logs) that the Terraform comment records.

3. **Rename only the two colliding entries (`{instance_id}/audit`, `{instance_id}/unattended-upgrades`),
   leaving five as bare `{instance_id}`.** This is the dossier's literal proposal and it is
   *correct* -- I rejected it only on the "next editor" argument. The specific failure it invites is
   concrete and imminent: **B4 adds a third file to the same `system` group**, and an author copying
   a neighbouring line under this variant copies `{instance_id}` (five of the eight neighbours say
   exactly that) and reintroduces the collision. The uniform scheme costs five extra edited lines and
   zero consumers (I4.B). Kept as the documented fallback if a reviewer insists on the minimal diff.

4. **Use `{hostname}` or `{ip_address}` instead of a literal suffix.**
   Rejected: those are host identifiers, not source identifiers. Both files are on the *same* host,
   so both placeholders resolve identically and the collision survives. They also make the stream
   name unstable across an instance replacement, which is worse than `{instance_id}` (the EIP is
   stable, `eipalloc-0098c8fa703931a5e`, but the hostname is not).

5. **Set `retention_in_days` per entry while editing the block.**
   Rejected twice over: the instance role has no `logs:PutRetentionPolicy` (the call would fail),
   and Terraform already owns retention with per-group overrides. Worse, with `system` now
   multi-entry, *mismatched* values across sibling entries make the agent exit with an error
   (agent reference). Explicitly banned in the header comment instead.

6. **Add `"multi_line_start_pattern": "{timestamp_format}"` to `unattended-upgrades.log` while
   separating the streams.** The brief invited this; I rejected it on a specific failure. If the
   `timestamp_format` guess is wrong, *no* line matches the start pattern and the agent concatenates
   without a natural boundary -- turning a cosmetic timestamp error into structural log corruption.
   A wrong `timestamp_format` *alone* degrades to today's behaviour. Since I cannot observe the file,
   I take the safe half and register the other half as a gated follow-up (I11.3).

7. **Give `audit.log` a `timestamp_format` "for symmetry".**
   Rejected on evidence: auditd stamps epoch seconds, and the agent's symbol vocabulary has no epoch
   token [V]. Any format written there would silently never match. The header comment in step 3
   exists specifically to stop a future agent from making this change.

8. **Add a `{filename}` / `{container_name}` placeholder to the docker glob to split it "the same
   way".** Rejected: no such placeholder exists. The documented `log_stream_name` variables are
   exactly `{instance_id}`, `{hostname}`, `{local_hostname}`, `{ip_address}` [V]. Inventing one
   would produce a stream literally named `i-.../{container_name}`.

9. **Drop `/var/log/letsencrypt/letsencrypt.log` from the `collect_list`** (B2 offers this as an
   alternative to ACL-ing the `0700` directory). Rejected on behalf of B2, with evidence: two metric
   filters (`:758`, `:803`) and two alarms depend on that group, and
   `cert-renew-heartbeat-stale` is `treat_missing_data = "breaching"` -- with no producer it fires
   forever, reproducing the exact E2 `PgDumpHeartbeat` failure this dossier is trying to eliminate.

10. **Fix only the script and not `docs/SIMPLE_AWS_DEPLOYMENT.md`.**
    Rejected: `bootstrap-ec2.sh:954` names that document as the source the block was materialised
    from, and `git blame` confirms the duplicate was carried across verbatim. Leaving the generator
    intact guarantees the defect returns on the next re-materialisation. Fixing the generator is

11. **Write a pytest under `backend/tests/` instead of a standalone validator.**

    grant it, and the stream holds genuine forensic data. Let group retention expire it.
