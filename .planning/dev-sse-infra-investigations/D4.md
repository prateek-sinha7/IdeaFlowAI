##### I3. Root cause - confirmed, corrected

**Re-derived independently. The dossier's mechanism is right.** The three dicts are
per-run coordination state hung off a module-level singleton
(`store.py:173-184`, `get_artifact_store()`), written on four lines, and read by five
call sites - with **no removal path in production code anywhere**. Verified by exhaustive
grep (I4.1): every `.pop` / `del` / `.clear` on the three names in the whole repo is in a
test fixture.

Causal chain, trigger to symptom:

1. A run starts. If it clarifies, `POST /api/runs/{id}/answers` ->
   `run_commands.py:274 set_questionnaire_responses(run_id, ...)` writes
   `_questionnaire_responses[run_id]` (`:78`) and `_questionnaire_force_proceed[run_id]`
   (`:79`) and creates `_resume_events[run_id]` (`:59` via `get_resume_event`).
2. For each gated agent, `engine._run_review_gate` (`engine.py:5109`) builds
   `gate_key = f"{pipeline_run_id}:{agent_id}"` and `get_review_event(gate_key)` creates
   `_resume_events[f"review:{gate_key}"]` (`:115`). Resolving it writes
   `_questionnaire_responses[f"review:{gate_key}"]` (`:137`) holding
   `{approved, edited_content, action, instructions}`.
3. The run terminates by any path - complete, cancel, fail, unhandled exception. The
   driver's `finally` (`run_commands.py:2184-2186`) drains the queue and calls
   `_cleanup_pipeline`, which pops `_PIPELINE_QUEUES` / `_PIPELINE_TASKS` /
   `_CANCEL_EVENTS` and **nothing else**.
4. Every entry from steps 1-2 survives for the life of the uvicorn process.

**Five corrections to the dossier's analysis.**

**C1 (the important one) - `_resume_events` and `_questionnaire_responses` each hold TWO
key namespaces in one dict.** The dossier does not say this, and it is the single fact
that decides whether `forget_run(run_id)` can find its entries at all:

| Dict | Key shapes |
|---|---|
| `_resume_events` | `"{run_id}"` (clarify, `:59`) **and** `"review:{run_id}:{agent_id}"` (review gate, `:115`) |
| `_questionnaire_responses` | `"{run_id}"` (clarify, `:78`) **and** `"review:{run_id}:{agent_id}"` (review, `:137`) |
| `_questionnaire_force_proceed` | `"{run_id}"` only (`:79`) |

`gate_key` is built in exactly one place - `engine.py:5109`,
`f"{pipeline_run_id}:{agent_id}"` - and reached from four call sites (`engine.py:3132`,
`:3276`, `:4120` inline; `kernel_services.py:1109` for the declared `gates:[human]` path,
which passes `pipeline_run_id=self.run_id, agent_id=spec.id`). So a naive
`d.pop(run_id, None)` would miss **every review-gate entry** - i.e. the large ones. The
exact matching rule is specified and proven in I5.

**C2 - "Grows per run *and* per gate" is right about gates but wrong about rounds.**
`set_review_response` **assigns** (`:137`), it does not append. On dev the busiest
gate_key was re-emitted **34 times** (a redo loop:
`43a0d562-...:prototype-specify`) and still occupies exactly one entry. Measured: **65
distinct gate_keys ever, across 32 gated runs - at most 3 per run.** So the per-run
entry count is small and bounded; the growth is in the *number of runs*, not in redo
depth.

**C3 - the dossier names the wrong dominant payload.** It says
*"`set_review_response` stores the **full user-edited artifact body**"*. True, but
`edited_content` is `None` for a plain approve (`resolve_gate` passes
`body.edited_content`, which the FE sends only on an actual edit). The realistic large
retained value is **`instructions` on `action="update_specs"`**, which
`run_commands.py:232` sets to the full `analysis_report`. Measured gate outputs on dev:
`prototype-specify` median 42,623 B (max 89,108), `prototype-plan` median 12,741 B (max
95,165), `prototype-analyze` median 9,053 B.

**C4 - the "~34 KB average" figure is the EVENT payload, not what is retained.**
Confirmed as an event statistic (mean 33,923 B over n=284). What the *store* retains is
much smaller in the common case. Measured directly, by building a real `ArtifactStore`
and deep-sizing the three dicts:

| Run shape | Retained across the three dicts |
|---|---|
| ungated clarify-only (`user_stories`) | **~1,355 B** |
| gated, approve-only (`prototype`, 3 gates) | **~3,257 B** |
| gated with one edit (42,623 B) + one `update_specs` (9,053 B) | **~56,123 B** |

So the honest characterisation is: **~1-3 KB per ordinary run, ~50-150 KB for a run the
user actually edited or re-specced** (worst observed per-run gate-output total on dev:
145,761 B). At the dev rate (134 runs in a month) this is not an outage; it is a strict,
unbounded, never-released monotonic climb in a process expected to live for weeks. The
dossier's "Memory grows monotonically ... never released" is exactly right; its implied
magnitude is high by roughly an order of magnitude for the common run.

**C5 - one addition the dossier omits.** The `asyncio.Event` objects in `_resume_events`
are cheap, but they are also the mechanism the *only* remaining reader,
`review_event_pending` (`store.py:156-166` -> `run_commands.py:149 _gate_is_pending`),
consults to decide whether a gate is live. That makes the timing of the clear a
**correctness** question, not merely a memory one - which is why I4.3 exists.

**Verdict: the root cause is CONFIRMED.** The proposed fix shape (an explicit
`forget_run(run_id)` called from the existing terminal hook; no TTL sweeper) is
**correct** and is the right one. It needs the composite-key rule (C1) to actually work,
and it needs the lifetime proof (I4.3) to be safe.

###### I4.3 The lifetime question - can any reader legitimately fire after the clear?

This is the section that decides whether the fix is safe. The hazard is precise: a
waiter holds a **direct object reference** (`event = await get_review_event(gate_key)`,
`engine.py:5112`). If `forget_run` pops that key while the waiter is blocked on
`event.wait()`, then a later `POST /gate` is rejected at `_gate_is_pending` (the key is
gone -> `review_event_pending` False -> HTTP 404 `gate_not_pending`), the write never
happens, and **the waiter hangs forever**. That is the BUG-R01/R02 shape recorded in
IMPL `:4089`. So the fix is safe iff `_cleanup_pipeline` can never fire while a gate
waiter is alive.

###### I4.3a Site 3 is THREE paths, not one - correcting this document (raised by A3)

A3's I10 (`A3.md:818-836`) objects that `_cleanup_pipeline` is the wrong home for D4/D5

```python
        db = SessionLocal()

            wr = db.query(WorkflowRun)...first()            # :5516
```

**(3b) is reachable with a durably-open review gate.** Branch (a) armed

the gate having been resolved between the two derivations - in which case there is no
open gate and clearing is trivially right.

branch on which neither `resume_run` nor `_replay_clarify_run` is awaited, so

```python
    # Run lifecycle (D4) — the ONE removal path for the per-run HITL state
    # ------------------------------------------------------------------

    def forget_run(self, run_id: str) -> int:
        """Drop every per-run HITL entry for ``run_id``. Returns the count removed.

        These three registries are per-RUN coordination state living on a
        process-lifetime singleton, and until now nothing ever removed an entry —
        so a completed run's response slots and ``asyncio.Event``s were retained
        for the life of the uvicorn process (D4). ``forget_run`` is that missing
        removal path; the caller that knows a run has ended
        (``app.api.run_engine._cleanup_pipeline``) invokes it. NOT a TTL sweeper:
        the lifecycle is known exactly, so it is tied to the existing terminal hook.

        KEY SHAPES (why this is not three ``pop``s). Two of the three registries
        hold TWO key namespaces:

          * ``_resume_events``            — ``"{run_id}"`` (clarify, :59)
                                            and ``"review:{run_id}:{agent_id}"`` (:115)
          * ``_questionnaire_responses``  — ``"{run_id}"`` (clarify, :78)
                                            and ``"review:{run_id}:{agent_id}"`` (:137)
          * ``_questionnaire_force_proceed`` — ``"{run_id}"`` only (:79)

        ``gate_key`` is minted in exactly one place — ``engine._run_review_gate``,
        ``f"{pipeline_run_id}:{agent_id}"`` — so the review namespace is always
        ``review:`` + run + ``:`` + agent. The match is therefore: the bare id, OR
        the ``review:{run_id}:`` prefix. The bare ``review:{run_id}`` form is also
        matched so the rule is TOTAL over the key space (that shape is unreachable
        today — an agent id is never empty — but a partial match would silently
        leak, and the extra comparison is free).

        SYNCHRONOUS BY DESIGN — every other method here is ``async def`` but none
        of them awaits. This one MUST NOT, because its caller ``_cleanup_pipeline``
        is synchronous precisely so its registry mutations are atomic against the
        event loop (no ``await`` ⇒ no preemption). Making it awaitable would
        destroy that property. ``review_event_pending`` is the same shape (IN-02).

        Idempotent: a second call, or an unknown/empty ``run_id``, removes nothing.
        """
        if not run_id:
            return 0
        exact_review = f"review:{run_id}"
        prefix_review = f"review:{run_id}:"
        removed = 0
        for registry in (self._resume_events, self._questionnaire_responses):
            # Materialize the key list first — deleting during iteration raises.
            doomed = [
                k
                for k in registry
                if k == run_id or k == exact_review or k.startswith(prefix_review)
            ]
            for k in doomed:
                del registry[k]
                removed += 1
        if self._questionnaire_force_proceed.pop(run_id, None) is not None:
            removed += 1
        if removed:
            logger.debug(
                "ArtifactStore: forget_run(%s) released %d HITL entries",
                run_id, removed,
            )
        return removed


# ------------------------------------------------------------------
# Module-level singleton
# ------------------------------------------------------------------
```

`logger` already exists at `store.py:26`. No new import.

Why `int` and not `None`: it makes the reclaim measurable and testable, and it is the
only way to clear the dossier's own uncertainty about magnitude without a profiler. Why
`del` over `pop`: `del` on a key we just proved present is the honest expression and
counts correctly.

##### I6. Ripple-effect analysis - assume the fix is wrong

**"The clear strands a live gate waiter."** The one genuinely dangerous outcome.
Excluded by exhaustively tracing all 12 (13 with A4) call sites in I4.3: every one is
post-drive or pre-drive. The residual risk is a *future* caller added mid-drive - which
is why the docstring says so explicitly and why the test at I8-T3 pins the pre-condition.

**"The clear breaks the Phase-49 restart re-arm."** Analysed in I4.3. Clarify: no
observable change (`POST /answers` writes unconditionally). Review: 200-silent-noop
becomes 404-silent-console-error, only on the three unresumable-run early returns. Not a
regression; arguably the honest outcome. Declared in I11.

**Concurrency / ordering.** `forget_run` is synchronous and contains no `await`, so on
the single-threaded event loop it is atomic: no coroutine can observe a half-cleared
store. This preserves the exact property A2's design relies on ("only two interleavings
exist"). Making it `async def` would break that - the reason the docstring pins it.
Mutation-during-iteration is avoided by materializing the key list first (proven in the
prototype below).

**Restart.** After a process restart all three dicts are empty anyway; the fix changes
nothing about restart behaviour. The Phase-49 branch-(a) re-arm still rebuilds what it
needs from the durable log.

**Resume (`POST /api/runs/{id}/resume`).** A resumed run reuses the same `run_id`. The
sequence is: run fails -> driver `finally` -> `_cleanup_pipeline` -> `forget_run` -> user
resumes -> `resume_run` re-drives -> `_run_review_gate` arms a **fresh** Event
(`get_review_event` create-if-absent) and `event.clear()`s it before waiting. There is no
read of a pre-existing entry anywhere on that path (`get_review_response` is called only
*after* `event.wait()` returns, i.e. only after a fresh `set_review_response`). Clean.
Note the fix also removes a latent stale-read hazard: today an approved response for
`review:{run}:{agent}` survives, and only `event.clear()` at `engine.py:5113` prevents a
re-opened gate from consuming it.

**Two browsers / unattached client / slow client (A2 territory).** The store is not on
the SSE path at all (I4.5). No interaction.

**Fan-out run.** Workers open no gates (IMPL Phase 11 D-01). The parent's clear touches
only its own keys. Verified by the prefix rule (below).

**Revision run.** Separate uuid, separate keys, artifacts read from the DB (I4.4).

**Crashed run.** A run whose driver dies without running its `finally` leaks today and
still leaks after this change - **unless A4 lands**, in which case the next SSE attach
self-heals it via `_is_run_live` -> `_cleanup_pipeline` -> `forget_run`. A4 makes D4
strictly better; D4 does not depend on A4.

**Partial application.** If Step 1 lands without Step 2 the method is dead code (zero
behaviour change). If Step 2 landed without Step 1 the guarded `except` would log a
warning per run and change nothing. Neither half can break the system.

**Memory / pool.** Strictly reclaims. No new allocation, no DB connection, no file
handle.

**Cross-run deletion by a crafted `gate_key`.** `POST /gate` accepts a client-supplied
`gate_key`, but (a) `_review_gate_owned_by` (`run_engine.py:324-348`) parses

`_gate_is_pending` requires the key to be **already armed by the engine**. So an
attacker cannot plant a key under another run's prefix. And `forget_run` only ever
deletes keys under **its own** run's prefix - it can never reach a neighbour.

###### Disagreement with A3, and its resolution (arbitrated 2026-07-30)

**A3's objection** (`A3.md:818-836`): `_cleanup_pipeline` is the wrong home for D4/D5,
because "nine of twelve paths are pre-drive early returns where the run is still parked
and genuinely alive. Clearing `_resume_events[run_id]` there would destroy the
`asyncio.Event` a human gate or clarify round is waiting on - the BUG-R04 lost-wakeup
class." It singles out `engine.py:5551` firing on a run "deliberately left parked (the
`open_kind` fall-through)".

**What A3 got right, and this document had wrong.** The `open_kind` fall-through is real,
`engine.py:5551` does fire on it, and my original site-3 row described that site as
unconditionally post-drive. **Corrected** in I4.3 / I4.3a: site 3 is three paths, two of
them pre-drive.

**Why the objection does not change the design.** A3's stated harm requires an
`asyncio.Event` that something is *waiting on*. On every pre-drive path - including the
fall-through - no driver was ever awaited, so `_run_review_gate` never ran and nothing is
blocked at `engine.py:5157/:5176` (proof, including the exclusion of a concurrent driver,
in I4.3a). And the gate those paths leave behind is **already** a 200-silent-noop black
hole today (traced step by step in I4.3a, matching IMPL `:4093` BUG-R02) - so nothing
that works today stops working.

**Both of A3's proposed alternatives were evaluated against the code and rejected:**

- *Clear only the bare `{run_id}` namespace at `_cleanup_pipeline`, the `review:`
  namespace only at the genuine terminal sites.* This leaves the **large** entries - the
  40-90 KB `edited_content` / `update_specs` bodies that are the entire point of D4 -
  leaking unless the same call is added at those terminal sites anyway. It buys one
  lifecycle split into two rules (INV-12 smell) and does not even remove the 200-to-404
  delta; it relocates it.
- *A `forget_run_state` called from "the three terminal `finally` blocks".* Two of the
  three are app-layer (`run_commands.py:2186`, `:2489`), but the third is
  `engine.py:7830` - inside the **kernel**, which may not import `app.api`
  (import-linter). Reaching it needs an injected callback, and the injected callback that
  already exists for exactly this purpose is `_resume_cleanup` ->
  `_cleanup_pipeline`. The proposal therefore collapses back into the current design,

  all four `postGate` call sites in `dashboard/page.tsx` are `void ... .catch(console.error)`.
  Recovery is identical either way (the next restart re-derives from the **durable** log;
  `forget_run` is in-memory only). Option (b) would add an INV-12 dual mechanism to
  preserve a lie.
- *What would change this answer:* if someone makes those paths genuinely resolvable -
  e.g. by persisting the gate response durably so a later restart can consume it - then
  the 200 would start meaning something and the clear would need re-scoping. That is a
  larger change, and it is currently foreclosed by the Phase-23 lock (IMPL `:2433`:
  "Do not add a DB column for redo state").

No other decision is required: no spend, no mailbox ownership, no product behaviour
change, no infrastructure change.

##### I12. Shortcuts and alternatives explicitly rejected

**1. `pop(run_id)` on all three dicts and call it done.** The obvious one-liner, and it
is **wrong**: it misses every `review:{run_id}:{agent_id}` key - i.e. every review-gate
entry, which is where the 40-90 KB `edited_content` / `instructions` payloads actually
live (I3-C1/C3). It would reclaim ~1 KB of the ~56 KB a real edited prototype run
retains, and the leak would look fixed while the dominant term kept growing.

**2. An injected callback (`_forget_run_hook`) mirroring `_resume_register_queue` /
`_resume_cleanup`.** Rejected. That pattern exists solely because the **kernel** may not
import `app.api` (import-linter, IMPL Phase 12-09 `:1214`). Here the direction is
`app.api -> agents.*`, which is unrestricted and already used at `run_commands.py:47`. An
injected callback would add a wiring site in `app/main.py`, a nullable attribute, and a
"dormant when unset" failure mode - all to avoid an import that is already legal. Pure
indirection tax.

**3. A TTL sweeper / periodic janitor.** The dossier rejects it and is right: the
lifecycle is known **exactly** (a run ends at a specific, already-instrumented moment), so
a timer would be a second lifecycle mechanism (INV-12) that is strictly less accurate,
adds a background task, and introduces a window in which a *live* gate could be swept -
reintroducing the hang hazard I4.3 exists to exclude. Note D6 argues for a sweeper for
*sandboxes*; that is a different case (the filesystem has no in-process terminal hook).

**4. Persist the gate response durably and drop the in-memory dict entirely.** Tempting
and architecturally cleaner, but it **contradicts a locked decision**: IMPL Phase 23 §5
(`:2433`) - *"No migration (Q3 additive) ... the resume decision is in-memory only. Do
not add a DB column for redo state."* It is also a much larger change (a migration, a new
read path, a new race between the durable write and the waiter) for a memory bug.

**5. Clear at the endpoints instead (in `resolve_gate` / `submit_answers` after the
write).** Wrong by construction: those are the moments the entry is *created and needed*,
not released. Clearing there would break the very gate being resolved.

**6. Make `forget_run` `async def` for consistency with its siblings.** Rejected: it
would introduce an `await` into `_cleanup_pipeline`, destroying the no-preemption
atomicity that A2's lock-free subscribe/close correctness argument explicitly depends on
("asyncio never preempts between two non-awaiting statements"). `review_event_pending`
already establishes the synchronous-accessor precedent (IN-02).

**7. Reach into `store._resume_events` from `run_engine.py` and delete keys there.**
Rejected: it would re-open the private-dict peek that Phase 44 IN-02 / Phase 49 closed
(IMPL `:3718`, `:4067`), and it would put the key-shape knowledge in two places.

**8. Add a bounded LRU / cap on the dict sizes.** Rejected: an eviction policy would drop
a **live** gate's entry under load - the exact hang. Bounding is the right answer for a
subscriber queue (A2), never for coordination state whose absence means "no gate here".

**9. Do nothing - "it is only a few KB per run".** Rejected on the measurement: ~1-3 KB
for an ordinary run but ~56 KB (worst observed gate-output total 145,761 B) for an edited
one, monotonic, never released, in a process expected to run for weeks with no restart
discipline and - per B1 - no memory metric to notice it. The fix is ~70 lines with no
migration and no host change. The dossier's own framing is right: this and D5 are the
same shape, and the terminal hook already exists.

**Alternatives the dossier lists that I verified rather than re-derived:** its rejection
of the TTL sweeper (item 3 above) is correct, and its identification of the driver
`finally` as the correct home is correct - with the mechanical refinement that the call
belongs **inside** `_cleanup_pipeline` (covering all 12 sites uniformly) rather than
beside it at the two app-layer `finally` blocks, which would miss all ten engine-side
resume paths and would need an engine->app callback to reach them.
