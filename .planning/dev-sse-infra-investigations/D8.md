##### I3. Root cause - confirmed, corrected, or replaced

The dossier's stated root cause - "`backend/app/main.py` ends with `yield` / `logger.info(...)`; that is the entire shutdown path" - is **factually correct but is not the root cause of the symptom it claims**. There are two distinct defects stacked, and the dossier only sees the second.

**Defect 1 (the dossier misses this one entirely): the lifespan shutdown is unreachable.**

`backend/docker-entrypoint.sh` runs `exec uvicorn ...` with no `--timeout-graceful-shutdown`. In uvicorn 0.34.0 (`requirements.txt:2`, verified installed):

```python
# uvicorn/server.py Server.shutdown()
for connection in list(self.server_state.connections):
    connection.shutdown()
await asyncio.sleep(0.1)
try:
    await asyncio.wait_for(self._wait_tasks_to_complete(),
                           timeout=self.config.timeout_graceful_shutdown)   # <- None by default
except asyncio.TimeoutError:
    for t in self.server_state.tasks: t.cancel(...)
if not self.force_exit:
    await self.lifespan.shutdown()                                          # <- our body
```

Three facts compose into a hang:

1. `H11Protocol.shutdown()` on a connection whose response is still streaming does **not** close the transport - it only sets `self.cycle.keep_alive = False`. The SSE connection stays in `server_state.connections`.
2. `_wait_tasks_to_complete()` is `while self.server_state.connections and not self.force_exit: await asyncio.sleep(0.1)`.
3. `Config.timeout_graceful_shutdown` defaults to `None`, and `asyncio.wait_for(..., timeout=None)` waits forever. `force_exit` is set only by a **second SIGINT** (`if self.should_exit and sig == signal.SIGINT`) - a second SIGTERM does not set it, and `docker stop` sends one SIGTERM then SIGKILL.

`sse-starlette` 3.0.2 monkeypatches `Server.handle_exit` (`sse.py:70-71`) intending to release streams, but its `AppStatus.handle_exit` signals `_exit_event_context.get(None)` - a **`contextvars.ContextVar`** read in the *signal handler's* context, while each stream's `_listen_for_exit_signal` created and awaits its own event inside its *own task* context (`sse.py:58-63`). The events are different objects. The mechanism does not fire.

**Measured, not inferred.** A minimal FastAPI app reproducing the exact shape (`EventSourceResponse` over an `asyncio.Queue.get()` that never completes, plus an untracked `create_task` driver), started with the same flags:

| Case | SSE stream open | `--timeout-graceful-shutdown` | Elapsed after SIGTERM | Process exited | Lifespan body ran | Driver cancelled |
|---|---|---|---|---|---|---|
| A | yes | (default `None`) | **>60 s** | **NO - SIGKILL** | **NO** | NO |
| B | no | (default `None`) | 0.24 s | yes | **YES** | NO |
| C | yes | `5` | 5.24 s | yes | **YES** | NO |

Case A server log, verbatim:

```
INFO:     Shutting down
INFO:     Waiting for connections to close. (CTRL+C to force quit)
```

...and nothing further for 60 s. `SHUTDOWN-BODY-REACHED` never printed.

So in production: any browser holding a run screen open pins the deploy. `docker compose up -d` -> `docker stop` -> SIGTERM -> uvicorn spins -> SIGKILL at 30 s. **The full 30-second grace window is spent doing nothing, and the lifespan body - empty today, and whatever the dossier's fix puts there tomorrow - never executes.** The dossier's proposed fix, applied as written, would be dead code under exactly the conditions it is meant to handle. Case C proves the flag is sufficient to make it reachable.

This also explains a symptom nobody has connected: **every dev deploy with an active user takes a hard 30 seconds of downtime and ends in SIGKILL.** With B1 fixed, that would show as a container-restart pattern in `/velocityai/dev/app`.

**Defect 2 (the dossier's stated cause, confirmed): the reachable body is empty.** Once reachable, nothing cancels `_PIPELINE_TASKS`, nothing awaits `_CONCIERGE_STREAM_TASKS`, nothing closes the checkpointer pool, nothing logs a count. Case C confirms uvicorn's forced cancel reaches only `server_state.tasks` (ASGI request tasks); the bare `asyncio.create_task` drivers are untouched and are destroyed when the loop closes.

**Correction to the dossier's symptom claim.** "In-flight runs are abandoned mid-write" overstates it. On SIGKILL, rows stay `running` and `restore_non_terminal_runs` classifies them on the next boot - branch (b) auto-resume (live-proven in RESUME-QA 2026-07-19) or branch (c) an honest `failed`. Nothing is silently lost. The real, provable damage is narrower and different:

- the checkpointer `AsyncConnectionPool` is never closed - Postgres logs `connection was closed unexpectedly` per pooled connection (D7's own verification criterion);
- an in-flight Concierge turn's durable `chat_reply` row is never written - the user's question persists with no answer, permanently;
- SSE sockets are RST rather than closed, so every attached browser reconnects at once into a process that is simultaneously running D9's uncapped restore - the thundering herd D9 describes, amplified by A1's rate limit;
- a deepagents `write_file` can be torn mid-write (self-healing on resume via the Phase-46 per-task cursor + `_rematerialize_artifacts_to_disk`, but only because that machinery exists);
- 30 s of avoidable downtime per deploy.

**The causal chain, end to end:**
`docker compose up -d` -> `docker stop` (SIGTERM, grace 30 s) -> uvicorn `handle_exit` sets `should_exit` -> `Server.shutdown()` -> `H11Protocol.shutdown()` leaves the streaming SSE connection open -> `wait_for(..., timeout=None)` blocks forever -> `lifespan.shutdown()` never runs -> 30 s elapse -> SIGKILL -> pools/tasks/sockets die abruptly.

##### I5. The complete fix

**Design decision that shapes everything below.** The dossier says "signal the cancel events for in-flight runs so they can persist a terminal state." Verified consequence: **every** stop path - cooperative `cancel_event` (`engine.py:2493`, `:1948`, the pre-agent path) and destructive `task.cancel()` (`run_commands.py:2155`) - makes the engine yield `pipeline_cancelled`, which `engine.py:1032` persists durably with no type filter, and makes the driver write `WorkflowRun.status = "cancelled"`. `cancelled` is not in `NON_TERMINAL` (`engine.py:5263-5266`), so `restore_non_terminal_runs` never sees the run and **auto-resume is gone**.

There is no third way. You cannot stop a run and keep it auto-resumable: the durable tail would carry a terminal `pipeline_cancelled` while the row said `running`, and the FE replay would render "Cancelled by you" on a run the backend then silently resumes.

So the fix ships in two parts:

- **Part 1 (STEP 1-6): unconditional, no product decision.** Make the shutdown reachable, protect the Concierge's durable write, close the pools, drain the registries, log the counts. Preserves auto-resume exactly as today.
- **Part 2 (STEP 7): gated on the I11 decision.** Whether to additionally stop the pipeline drivers, which converts every in-flight run to `cancelled` and trades auto-resume for user-initiated resume.

Part 1 is what I recommend landing. Part 2 is written out in full so an executor can apply it if the human chooses Option T.

**STEP 3 - New module: the shutdown orchestrator.**

New file: `backend/app/api/run_shutdown.py` (complete, 1 file, ~130 lines).

*Why a new module and not `main.py` or `run_engine.py`:* the registries live in two modules (`run_engine._PIPELINE_TASKS`/`_CANCEL_EVENTS`/`_PIPELINE_QUEUES`, `run_commands._CONCIERGE_STREAM_TASKS`/`_LIVE_ECTX`). `run_engine` cannot import `run_commands` (that is the cycle - `run_commands.py:72-74` already imports `run_engine`). `main.py` should not reach into private registries.
```python
"""Graceful application-shutdown orchestration for the run transport (D8).

The FastAPI lifespan's shutdown half was a bare log line: nothing cancelled the
in-flight pipeline drivers, nothing awaited the Concierge turns that own their own
durable ``chat_reply`` write, and nothing closed the LangGraph checkpointer's
Postgres pool - despite ``checkpointer.py:12`` saying to. This module is that body.

Reachability prerequisite (D8, measured): uvicorn's ``timeout_graceful_shutdown``
defaults to ``None`` and ``H11Protocol.shutdown()`` does NOT close a connection
whose response is still streaming, so a single live SSE stream makes
``lifespan.shutdown()`` unreachable and docker SIGKILLs at ``stop_grace_period``.
``docker-entrypoint.sh`` passes ``--timeout-graceful-shutdown 5`` so this code runs.

Ordering is load-bearing and is NOT the dossier's "signal then cancel":
  1. Concierge drive tasks are AWAITED first (never cancelled first) - a cancel
     landing inside ``converse()`` skips the durable ``chat_reply`` persist
     entirely, losing the user's answer with no record.
  2. Run-transport teardown (A2 pumps / queue sentinels) - releases attached
     consumers before their producers vanish.
  3. ``close_checkpointer()`` LAST among the awaits - it tears down a pool that
     step 1/2 tasks may still hold a connection from.
  4. Counts are logged so D9's thundering herd is measurable (D11 pairs the same
     JSON shape on the stream side).

By default this does NOT stop the pipeline drivers and does NOT write any
``WorkflowRun.status``. That is deliberate: every stop path makes the engine yield
``pipeline_cancelled``, which ``engine.py:1032`` persists unconditionally and which
makes the driver write ``status="cancelled"`` - and ``cancelled`` is outside
``restore_non_terminal_runs``' ``NON_TERMINAL`` set (``engine.py:5263``), so the run
would never auto-resume on the next boot. Leaving the row ``running`` is what keeps
the Phase 45-50 resume tier working. See ``stop_pipeline_drivers`` below and the
D8 investigation section I11 for the alternative.

Workflow-agnostic - keyed by run id only, no workflow/agent-name literal (SC-001).
"""

from __future__ import annotations

import asyncio
import logging
import time
from typing import Any

from app.core.config import settings

logger = logging.getLogger("app.api.run_shutdown")


async def _drain(tasks: set[asyncio.Task], timeout: float) -> tuple[int, int]:
    """Await ``tasks`` up to ``timeout``. Returns ``(finished, still_pending)``."""
    if not tasks:
        return 0, 0
    done, pending = await asyncio.wait(tasks, timeout=timeout)
    return len(done), len(pending)


async def shutdown_run_infrastructure() -> dict[str, Any]:
    """Quiesce the run transport. Returns a JSON-safe summary for the caller to log.

    Never raises - a shutdown path that throws would abort the rest of the teardown
    and (via uvicorn's ``lifespan.shutdown_failed``) turn a clean exit into an error
    exit. Every step is individually guarded.
    """
    t0 = time.monotonic()
    # Deferred imports: this module is a leaf, but keeping them here also means an
    # import failure in one registry's module cannot break the whole shutdown.
    from app.api.run_commands import _CONCIERGE_STREAM_TASKS, _LIVE_ECTX
    from app.api.run_engine import _CANCEL_EVENTS, _PIPELINE_QUEUES, _PIPELINE_TASKS

    summary: dict[str, Any] = {
        "event": "app_shutdown",
        "runs_in_flight": len(_PIPELINE_TASKS),
        "run_ids_in_flight": sorted(_PIPELINE_TASKS.keys()),
        "live_queues": len(_PIPELINE_QUEUES),
        "cancel_events": len(_CANCEL_EVENTS),
        "live_ectx": len(_LIVE_ECTX),
        "concierge_turns_in_flight": len(_CONCIERGE_STREAM_TASKS),
        "concierge_persisted": 0,
        "concierge_lost": 0,
        "pipeline_drivers_stopped": 0,
        "queues_sentinelled": 0,
        "checkpointer_closed": False,
        "errors": [],
    }

    # ── 1. Concierge turns: AWAIT, never cancel-first. ──────────────────────────
    # run_commands.py:1401 holds these deliberately ("NEVER cancel it on generator
    # teardown"); the durable chat_reply row is written at :1356 inside _drive's
    # SECOND try, so a CancelledError raised inside converse() at :1347 skips it.
    try:
        done, pending = await _drain(
            set(_CONCIERGE_STREAM_TASKS), settings.SHUTDOWN_CONCIERGE_DRAIN_SECONDS
        )
        summary["concierge_persisted"] = done
        summary["concierge_lost"] = pending
        if pending:
            logger.warning(
                "shutdown: %d Concierge turn(s) exceeded the %.1fs drain budget - "
                "their chat_reply rows will NOT be written (the user's question row "
                "persists with no answer).",
                pending, settings.SHUTDOWN_CONCIERGE_DRAIN_SECONDS,
            )
    except Exception as exc:  # noqa: BLE001
        summary["errors"].append(f"concierge_drain: {exc}")
        logger.warning("shutdown: concierge drain failed: %s", exc)

    # ── 2. Run-transport teardown. ──────────────────────────────────────────────
    # Release every attached consumer before its producer disappears. Today that is
    # a per-run None sentinel on the shared queue; AFTER A2 lands, _close_run is the
    # single idempotent teardown (pops the liveness key, cancels the pump, sentinels
    # every subscriber) and the branch below MUST switch to it - see I10.
    try:
        for run_id in list(_PIPELINE_QUEUES.keys()):
            try:
                _PIPELINE_QUEUES[run_id].put_nowait(None)
                summary["queues_sentinelled"] += 1
            except Exception:  # noqa: BLE001 - a full/absent queue must not abort
                pass
    except Exception as exc:  # noqa: BLE001
        summary["errors"].append(f"queue_sentinel: {exc}")

    # ── 3. Optional: stop the pipeline drivers (see stop_pipeline_drivers). ─────
    if settings.SHUTDOWN_STOP_RUNS:
        try:
            summary["pipeline_drivers_stopped"] = await stop_pipeline_drivers()
        except Exception as exc:  # noqa: BLE001
            summary["errors"].append(f"stop_runs: {exc}")

    # ── 4. Close the checkpointer pool LAST among the awaits (D7). ──────────────
    # checkpointer.py:12 has said to do this since Phase 3; it has never had a
    # caller. Steps 1-3 may still hold a pooled connection, so this runs after them.
    try:
        from app.agents.checkpointer import close_checkpointer

        await close_checkpointer()
        summary["checkpointer_closed"] = True
    except Exception as exc:  # noqa: BLE001
        summary["errors"].append(f"close_checkpointer: {exc}")
        logger.warning("shutdown: close_checkpointer failed: %s", exc)

    summary["elapsed_seconds"] = round(time.monotonic() - t0, 3)
    # D9 measurability: runs left non-terminal here are exactly the set the next
    # boot's restore_non_terminal_runs will classify (branch b auto-resume /
    # branch c fail). This is the number the D9 semaphore must be sized against.
    summary["runs_left_for_boot_restore"] = (
        0 if settings.SHUTDOWN_STOP_RUNS else summary["runs_in_flight"]
    )
    return summary


async def stop_pipeline_drivers() -> int:
    """Cooperatively stop, then cancel, every live pipeline driver. Returns the count.

    NOT called by default (``SHUTDOWN_STOP_RUNS`` is False). Enabling it converts
    every in-flight run to ``WorkflowRun.status = "cancelled"`` and removes it from
    the boot-time auto-resume set. See I11 - this is a product decision, not a
    technical one.

    Reuses the ONE sanctioned stop mechanism (Phase 16-02 / quick 260720-ec4): set
    the per-run cooperative ``cancel_event``, which the engine observes at the
    per-chunk (:2514/:3621), pre-agent (:2287), clarify-drain-heartbeat (:1943),
    review-gate-race (:5155), task-loop (:4437/:4566) and wave (:5012) boundaries.
    Escalate to ``task.cancel()`` only for drivers that cannot observe it in time
    (the mid-Bedrock-call case: the per-chunk check only fires when a chunk arrives,
    and ``model_factory.py:112`` sets ``read_timeout=600``). Both paths end in the
    driver's own terminal write (``run_commands.py:2155`` launch /
    ``:2473`` revision), so the outcome is deterministic either way.
    """
    from app.api.run_engine import _CANCEL_EVENTS, _PIPELINE_TASKS

    tasks = set(_PIPELINE_TASKS.values())
    if not tasks:
        return 0
    for ev in list(_CANCEL_EVENTS.values()):
        ev.set()
    _done, pending = await asyncio.wait(tasks, timeout=settings.SHUTDOWN_TASK_DRAIN_SECONDS)
    if pending:
        logger.warning(
            "shutdown: escalating task.cancel() for %d driver(s) that did not observe "
            "the cooperative cancel within %.1fs (mid-model-call).",
            len(pending), settings.SHUTDOWN_TASK_DRAIN_SECONDS,
        )
        for t in pending:
            t.cancel()
        _done2, still = await asyncio.wait(
            pending, timeout=settings.SHUTDOWN_TASK_DRAIN_SECONDS
        )
        if still:
            logger.error(
                "shutdown: %d driver(s) survived cancel; their runs stay non-terminal "
                "and will be classified by restore_non_terminal_runs on the next boot.",
                len(still),
            )
    return len(tasks)
```

##### I6. Ripple-effect analysis - why nothing else breaks

I assumed the fix is wrong and went looking.

**"`--timeout-graceful-shutdown 5` will chop a legitimate long request."** The only responses that outlive 5 s are the four streaming endpoints (dossier A1's table). Two of them (`GET /events/stream`, the Concierge `POST /messages`) are *designed* to be long-lived and are already cancel-tolerant: the SSE client reconnects (`useRunStream.ts:389`), and the Concierge's durable write is protected by step 1 running *before* uvicorn's cancel could matter - no, correction: uvicorn's cancel happens *before* the lifespan, so a Concierge SSE *response* is cancelled at 5 s, but its `_drive` **task** is separate (`run_commands.py:1401`) and is what step 1 awaits. That separation is exactly why the design works. `POST /api/runs/user_message` and `POST /api/prototype/run` are the same shape. A plain REST call (`/api/runs`, `/api/auth/me`) completes in well under 5 s.

**"Cancelling SSE responses will spam ERROR logs."** It does. Measured, probe 2:

```
ERROR:    Exception in ASGI application
  ...
  File ".../sse_starlette/sse.py", line 255, in __call__
    async with anyio.create_task_group() as task_group:
  ...
asyncio.exceptions.CancelledError: Task cancelled, timeout graceful shutdown exceeded
```

One ERROR traceback **per open SSE stream, per deploy**. With 20 attached browsers that is 20 tracebacks. This is cosmetic (uvicorn's own force-cancel, not an app fault) but it interacts with E1: an `{ $.level = "ERROR" }` metric filter on `/velocityai/dev/app` would fire on every deploy. **Named as a required note in the E1 filter design** - see I10. It is not a reason to skip the flag; without the flag the same streams die by SIGKILL, which is strictly worse and invisible.

**Concurrency and ordering hazards.**
- *Step 1 before step 4 (Concierge before checkpointer).* Required: `converse()` reaches Bedrock through `DeepAgentRunner`, which uses the checkpointer. Closing the pool first would break an in-flight turn.
- *Step 2 before step 3.* Sentinelling before stopping means an attached consumer is released before its producer vanishes. Reversed, a consumer could park on a queue whose producer already returned.
- *`asyncio.wait` on an empty set raises `ValueError`.* Guarded (`if not tasks: return 0, 0`).
- *Mutation during iteration.* `_CONCIERGE_STREAM_TASKS` has a `done_callback` that discards from the set (`run_commands.py:1403`); iterating it directly while tasks complete would raise `RuntimeError: Set changed size during iteration`. Guarded by `set(_CONCIERGE_STREAM_TASKS)` - a snapshot. Same for `list(_PIPELINE_QUEUES.keys())` and `list(_CANCEL_EVENTS.values())`.
- *Re-entrancy.* `close_checkpointer` is idempotent by construction (`_pool = None` in its `finally`). `shutdown_run_infrastructure` is only ever called once, from the lifespan.

**Behaviour under each scenario:**

| Scenario | Today | After the fix (Part 1) |
|---|---|---|
| No client attached | clean exit ~0.2 s, pools leaked | clean exit, pools closed, counts logged |
| One browser on a run screen | **SIGKILL at 30 s** | clean exit at ~5-8 s |
| Slow client (a stalled SSE reader) | SIGKILL at 30 s | uvicorn cancels its response at 5 s |
| Crashed run (driver already dead) | n/a | `_PIPELINE_TASKS` already popped by `_cleanup_pipeline`; count is 0 |
| Restart with 20 in-flight runs | 20 rows `running`, SIGKILL, boot resumes all 20 uncapped | 20 rows `running`, clean exit, boot resumes all 20 - **unchanged, and now measurable** (`runs_left_for_boot_restore: 20`), which is what D9 needs |
| Resume in progress (`_drive_user_resume`) | destroyed | same registry, same handling |
| Fan-out run | workers are `run_fanout` children joined by `asyncio.gather` inside the driver task (IMPLEMENTATION-REGISTER `:536` A2 note) - they die with the parent | unchanged |
| Revision run | `_drive_revision_to_queue` in `_PIPELINE_TASKS` | same handling; its `except CancelledError` at `:2473` is the twin |
| Two browsers on one run | both SSE streams cancelled at 5 s, both reconnect | unchanged in kind |

**Memory and connection-pool effects.** Strictly negative (good): `close_checkpointer()` returns up to 10 Postgres connections that are currently leaked on every restart. The SQLAlchemy pool (20 + 40 overflow, `database.py:24-27`) is released when the process exits either way. No new allocation - the summary dict is one small object.

**Partial application.** Each step is independently safe:
- STEP 1 alone: shutdown becomes reachable and the empty body runs. Deploy downtime drops 30 s -> ~5 s. Zero risk. **This is the single highest-value line in the whole issue.**
- STEP 3+4 without STEP 1: correct code that never executes. Harmless, useless.
- STEP 4 without STEP 3: `ImportError` caught by the `try/except` and logged. Degrades to today.

**Where the dossier already argues safety, I checked rather than restated.** The dossier's "order matters: cancelling before signalling loses the chance to write a terminal status" is correct in spirit but is not the binding ordering constraint. Verified: `task.cancel()` on `_drive_launch_to_queue` **does** write the terminal status (`run_commands.py:2155-2166`), so cancelling-first does not lose it. The constraints that actually bind are (a) Concierge before checkpointer, (b) sentinel before stop, (c) `set(...)` snapshots against the done-callback mutation.

```python
def _free_port() -> int:
    with socket.socket() as s:
        s.bind(("127.0.0.1", 0))
        return s.getsockname()[1]


def _run(tmp_path: Path, extra_args: list[str]) -> tuple[bool, str]:
    """Start uvicorn, open an SSE stream, SIGTERM, and report (exited, stdout)."""
    (tmp_path / "sse_probe_app.py").write_text(_APP)
    port = _free_port()
    env = {**os.environ, "PYTHONPATH": str(tmp_path)}
    proc = subprocess.Popen(
        [sys.executable, "-m", "uvicorn", "sse_probe_app:app",
         "--host", "127.0.0.1", "--port", str(port), *extra_args],
        cwd=tmp_path, env=env,
        stdout=subprocess.PIPE, stderr=subprocess.STDOUT, text=True,
    )
    try:
        deadline = time.time() + 20
        while time.time() < deadline:            # wait for the port to accept
            try:
                with socket.create_connection(("127.0.0.1", port), timeout=0.5):
                    break
            except OSError:
                time.sleep(0.2)
        else:
            pytest.fail("probe server never came up")

        # Hold a live SSE stream open with a raw socket (no client library needed).
        sse = socket.create_connection(("127.0.0.1", port), timeout=5)
        sse.sendall(
            b"GET /stream HTTP/1.1\\r\\nHost: 127.0.0.1\\r\\nAccept: text/event-stream\\r\\n\\r\\n"
        )
        sse.recv(64)                              # block until headers arrive
        time.sleep(1.0)

        proc.send_signal(signal.SIGTERM)
        try:
            out, _ = proc.communicate(timeout=25)
            return True, out
        except subprocess.TimeoutExpired:
            proc.kill()
            out, _ = proc.communicate(timeout=10)
            return False, out
        finally:
            sse.close()
    finally:
        if proc.poll() is None:
            proc.kill()
```

##### I11. Open questions requiring a human decision

**Q1 (the only real one) - on shutdown, should in-flight runs be left auto-resumable, or marked terminal?**

This is the D8/D9 conflict, and it is a product decision, not a technical one. The dossier's D8 asks for a terminal status; the dossier's D9 depends on runs *not* being terminal. Both cannot hold.

The technical constraint that forces the choice (verified, `engine.py:1032` + `engine.py:5263-5266` + `run_commands.py:2155`): **any** mechanism that stops a run persists a durable `pipeline_cancelled` and writes `status = "cancelled"`, which removes the run from `restore_non_terminal_runs`' scan. There is no way to stop a run and keep it auto-resumable without leaving the durable tail contradicting the row.

| | **Option R - leave runs non-terminal (recommended, and the default in I5)** | **Option T - stop and mark terminal (the dossier's literal ask)** |
|---|---|---|
| What the shutdown does to runs | nothing - the driver task dies with the loop | sets `cancel_event`, then `task.cancel()`; each driver writes `cancelled` |
| Row after shutdown | `running` | `cancelled` |
| Durable tail | no terminal event | `pipeline_cancelled` (already replayable, no new type) |
| On next boot | `restore_non_terminal_runs` branch (b) **auto-resumes**; branch (c) fails the stateless ones | nothing resumes |
| User experience | the run continues by itself after the deploy | the run shows "Cancelled by you"; the user clicks **Run again** (`POST /resume` accepts `cancelled`, `run_commands.py:379`, FIX-105 live-proven) |
| Risk it carries | a driver may be mid-`write_file` when the loop closes (self-heals on resume via the Phase-46 per-task cursor + `_rematerialize_artifacts_to_disk`); the checkpointer pool closes while a driver may hold a connection | **silently retires the auto-resume half of the Phases 45-50 / RESUME-QA capability** - the most expensive thing in the codebase - on every deploy |
| Interaction with D9 | D9's semaphore stays necessary and is the right control | D9 becomes almost moot: nothing to restore |
| Honesty of the "Cancelled by you" label | n/a | **misleading** - the user did not cancel it; a deploy did. Fixing that needs a copy change the dossier does not budget for |

**My recommendation: Option R.** Reasons, in order:

1. It preserves a shipped, live-proven capability. Option T would quietly convert automatic recovery into a manual button-press on every deploy, and nobody would notice until a user complained.
2. Option R's determinism requirement is already satisfied - just not at shutdown. The outcome is deterministically `running` at shutdown and deterministically classified at boot by machinery that exists, is tested, and was live-verified on 2026-07-19. "Deterministic" does not have to mean "decided at shutdown."
3. Option T's honest-labelling problem is real and unbudgeted.
4. Option R is strictly better than today on every other axis (pools closed, Concierge replies saved, counts logged, 30 s -> 5 s downtime) at zero behavioural risk.

The code in I5 implements both. `SHUTDOWN_STOP_RUNS` is the switch; it defaults to `False` (Option R). Flipping it is a one-line change plus commit 3 in I10.

**Q2 (small, but a real product call) - is a lost Concierge answer acceptable past the 10-second drain?**

If a Concierge turn is still calling Bedrock when the budget expires, its durable `chat_reply` row is never written. The user's question row persists with no answer, permanently, and the transcript shows a question with no reply. Options: (a) accept it and log it (what I5 does, with an explicit `WARNING` naming the count); (b) raise `SHUTDOWN_CONCIERGE_DRAIN_SECONDS` toward 20 s, which eats the margin under the 30 s docker grace; (c) write a placeholder `chat_reply` row saying the answer was interrupted, which is a new durable side effect in a shutdown path. **Recommend (a)**: it is honest, bounded, and visible; a 2-8 s turn (the live-measured range) is comfortably inside 10 s, so this fires only on a genuinely stalled call.

Everything else in this issue is a technical judgement I have made and justified in-line. No other human decision is required.

##### I12. Shortcuts and alternatives explicitly rejected

**1. "Just write the shutdown body; skip the uvicorn flag."** This is the dossier's fix as literally stated. **Rejected because it does not work.** Measured (case A): with one open SSE stream the body never executes. It would pass every unit test, appear correct in review, and do nothing on the box - the worst possible outcome, because it would close D8 while leaving the defect.

**2. `--timeout-graceful-shutdown 30` (match the docker grace).** Rejected: the full timeout is spent whenever any SSE stream is open, because a stream never closes on its own. Setting it to 30 s means the lifespan body starts *at* the SIGKILL boundary and never finishes. The flag's value must be small enough that the lifespan budget fits underneath it.

**3. Set the timeout via `UVICORN_TIMEOUT_GRACEFUL_SHUTDOWN` in `/etc/velocityai/app.env`.** Rejected: that is host state written by `velocityai-load-secrets`, which is exactly the C1 class - a change that cannot reach a running box and evaporates on instance replacement. The entrypoint ships in the image.

**4. Force the SSE streams closed from our own SIGTERM handler, before uvicorn's wait.** Tempting, because it would let us send each client a clean "server restarting" frame. **Rejected on evidence:** `sse-starlette` already monkeypatches `uvicorn.main.Server.handle_exit` (`sse.py:70-71`) and its own `contextvars`-based event is already broken (I3). Chaining a second monkeypatch onto the same method, in a library whose first one silently does not fire, is how you get a shutdown that hangs in a *new* way. The forced cancel at 5 s produces the same client outcome (reconnect) with none of the fragility.

**5. `task.cancel()` on `_PIPELINE_TASKS` first, and rely on each driver's `except CancelledError` to write the terminal status.** This is the most tempting shortcut because it *works* - verified, `run_commands.py:2155-2166` does write `cancelled`. **Rejected as the default** for one reason the dossier misses: it takes the shortcut branch, which sets `status` and `completed_at` but **skips `_apply_terminal_output_columns`** (`run_commands.py:2146`), so the run lands with no `output`, no `agent_outputs`, no `token_usage`, no `duration` - the exact BUG-R03 gap that quick `260719-hvn` spent a whole task closing. Even under Option T the cooperative `cancel_event` must be tried first, because the cooperative path exits through the *normal* terminal block that does call the mapping.

**6. Suppress the driver's terminal write during shutdown with a `_SHUTTING_DOWN` flag, so we can cancel the drivers AND keep the runs resumable.** I designed this, then rejected it. It stops the *row* from being written but not the durable `pipeline_cancelled` event, which `engine.py:1032` persists with no type filter before the driver ever sees it. The result is a run whose row says `running` and whose replay tail says cancelled - the FE would render "Cancelled by you" on a run the backend then auto-resumes. Strictly worse than either coherent option.

**7. Classify each run at shutdown with `_is_resumable_in_flight` and cancel only the non-resumable ones.** Elegant on paper - it uses the existing classifier and both outcomes are internally consistent. **Rejected on cost:** `_is_resumable_in_flight` (`engine.py:5585`) calls `store.read_events(run_id, after_seq=0)`, the unbounded read A5 exists to kill. On the dev database's largest run that is 97,694 rows and ~104 MB per call (A5's own measurement). Doing that for 20 runs inside a 23-second budget is a guaranteed timeout. The classification already happens at boot, where it has 30 s and no client waiting; do it there.

**8. Add a `pipeline_interrupted` event type so the FE can distinguish a deploy from a user cancel.** Rejected: Phase 25 locked decision D5, "ZERO new WS event types - a new event enters the golden event multiset (the one confirmed INV-3 tripwire)" (IMPLEMENTATION-REGISTER `:2533`). Under Option R no event is needed; under Option T the existing `pipeline_cancelled` is already durable and replayable.

**9. Add a `WorkflowRun.interrupted_by_shutdown` column so boot can re-resume cancelled runs.** Rejected: it is a migration (Q3 permits additive ones, so that alone is not fatal) but it also requires widening `restore_non_terminal_runs`' scan to include `cancelled` runs - which risks silently re-resuming runs a **user** cancelled. A new failure mode strictly worse than the one it fixes.

**10. Cancel `_CONCIERGE_STREAM_TASKS` alongside the pipeline drivers.** Rejected on code evidence: `run_commands.py:1401` carries the explicit contract "NEVER cancel it on generator teardown / client disconnect," and the structure at `:1346-1378` means a `CancelledError` raised inside `converse()` propagates out of the *first* `try` and never enters the second, so the durable `chat_reply` persist at `:1356` is skipped entirely. The user's answer is lost with no record. Awaiting is the only correct treatment.

**11. Do nothing about the ERROR-level traceback that uvicorn's forced cancel produces per SSE stream.** Not rejected so much as *scoped out with a warning*: it is cosmetic (uvicorn cancelling its own task, not an app fault), but with 20 attached browsers it is 20 ERROR tracebacks per deploy, and E1's proposed metric filters would count them. **E1's filter design must exclude `CancelledError: Task cancelled, timeout graceful shutdown exceeded`** or every deploy pages someone. Named here so it is not discovered at 2 a.m.

**12. Fix `handoff.py:327`'s untracked background task in this change.** Rejected as scope creep - it is a different subsystem (`/ws/handoff`, the D10 survivor with its own contract test) and folding it in would dilute the proof of this fix. Named in I4 so it is not lost; it deserves its own task.
