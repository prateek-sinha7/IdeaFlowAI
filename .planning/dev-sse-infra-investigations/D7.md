##### I3. Root cause -- confirmed, corrected, or replaced

**The defect is real. The dossier's mechanism is right; three of its factual claims are wrong, and
it misses two further defects inside `close_checkpointer` itself.**

**Confirmed.** On Postgres, `get_checkpointer()` (`checkpointer.py:91-99`) opens an
`AsyncConnectionPool` and caches it in the module global `_pool`. Nothing in production ever calls
`close_checkpointer()`. The lifespan's entire shutdown body is `logger.info("...Shutting down...")`
(`main.py:169`). On SIGTERM the process exits with the pool still open, so the server-side
connections are dropped rather than closed -- Postgres logs each as an unexpected disconnect and
reaps them on its own schedule.

**Correction 3 -- the hazard mechanism in the dossier's D8 text is wrong.** D8 asserts the ordering
matters because closing "while a LangGraph graph is mid-checkpoint corrupts or errors that write".
It does not. From the installed `psycopg_pool 3.3.1` source [V]:

```python
    async def close(self, timeout: float = 5.0) -> None:
        """...
        All the waiting and future clients will fail to acquire a connection
        with a `PoolClosed` exception. Currently used connections will not be
        closed until returned to the pool.
        ...
        """
        if self._closed:
            return
        async with self._lock:
            self._closed = True
            ...
```

A connection already checked out by an in-flight `AsyncPostgresSaver._cursor()` is **not** taken
away; the write completes and the connection is simply closed on `putconn`. The real hazard is the
**next** acquisition: `getconn` -> `_check_open_getconn()` -> `raise PoolClosed("the pool ... is
already closed")` [V, source read]. So the ordering requirement is genuine but its justification is
"a driver that reaches its *next* checkpoint write after close raises `PoolClosed`", not
"corruption".

**New defect A (mine, not in the dossier) -- a failing close poisons the singleton permanently.**
Today's body:

```python
async def close_checkpointer() -> None:
    global _checkpointer, _pool
    if _pool is not None:
        try:
            await _pool.close()
        finally:
            _pool = None
    _checkpointer = None       # <-- OUTSIDE the try/finally
```

If `_pool.close()` raises, the `finally` nulls `_pool`, the exception propagates out of the `if`
block, and `_checkpointer = None` is **never reached**. The stale `AsyncPostgresSaver` survives
holding a half-closed pool. A later `get_checkpointer()` short-circuits on `if _checkpointer is not
None` and hands back that poisoned saver, whose every operation now raises `PoolClosed` forever.
Empirically reproduced [V]:

```text
7) close() PROPAGATES the pool error: boom | _pool now: None | _checkpointer now: <object at 0x...>
```

On the shutdown path the propagating exception would also abort the rest of D8's sequence.

**New defect B (mine) -- `get_checkpointer()` silently resurrects the pool after close.** There is
no closed latch. `close_checkpointer()` nulls both globals, so the very next `get_checkpointer()`
builds a **brand-new** `AsyncConnectionPool`, awaits `open()` (which grows to `min_size=4`
connections) and re-runs the `.setup()` DDL round-trip -- a pool nothing will ever close.
Empirically reproduced [V]:

```text
5) get AFTER close returns a NEW object: True -> InMemorySaver
```

This is exactly the straggler case: a detached `_PIPELINE_TASKS` driver that reaches
`engine.py:1429` after the lifespan has closed the pool resurrects it. Note the psycopg docstring
"you cannot currently re-open a closed pool" [V] -- so the resurrection is a genuinely new pool
object, not a reuse.

**The causal chain, end to end.**

1. Phase-0 of the deepagents migration wrote `close_checkpointer()` and documented the contract
   ("wire on shutdown") in the module docstring (`:12`).
2. Phase 02 locked "do not close per-run; it is an app-shutdown concern"
   (`02-CONTEXT.md:113`), and the engine carries that note verbatim at `:1414-1427`.
3. The lifespan's startup half then grew for 40+ phases (restore scan, resume hooks, live-ectx
   registry, milestone sink, output-persist sink -- `main.py:129-166`) while the shutdown half
   stayed the one-line placeholder it began as (`main.py:169`). Nothing enforces symmetry; there is
   no `on_event("shutdown")`, no `atexit`, no signal handler anywhere in `app/` [V, grepped].
4. So on every deploy/restart the pool is dropped, not closed -- and, because there is no latch,
   there is no safe way to add the close without also handling straggler tasks.

##### I5. The complete fix

Two halves. **Half A is D7-owned and lands standalone. Half B is one line inside D8's body.**

---

**Half A -- harden `close_checkpointer` and latch `get_checkpointer` (D7 owns this entirely).**

File: `backend/app/agents/checkpointer.py`.

*A.1 -- add the closed latch beside the two existing singletons.*

Anchor: lines 25-26.

BEFORE:

```python
_checkpointer = None  # cached process-wide singleton
_pool = None          # AsyncConnectionPool when on Postgres
```

AFTER:

```python
_checkpointer = None  # cached process-wide singleton
_pool = None          # AsyncConnectionPool when on Postgres
# One-way shutdown latch. Set by close_checkpointer() and NEVER cleared: once the
# app has torn the pool down, a straggler task must fail loudly rather than
# silently open a SECOND pool that nothing will ever close (psycopg cannot re-open
# a closed pool, so get_checkpointer() would build a brand-new AsyncConnectionPool,
# grow it to min_size, and re-run the .setup() DDL). Only ever True during
# shutdown, so every normal run -- and every offline/golden run, which never calls
# close_checkpointer() -- is byte-identical.
_closed = False
```

*Why a one-way latch and not "just null the globals"?* Nulling is what the code already does, and
it is exactly what produces the resurrection (empirically proven, I3 defect B). The latch is the
only thing that makes "closed" observable.

*A.2 -- guard the acquisition.*

Anchor: the function head at line 33, immediately after the docstring and before
`if _checkpointer is not None:`.

BEFORE:

```python
    global _checkpointer, _pool
    if _checkpointer is not None:
        return _checkpointer
```

AFTER:

```python
    global _checkpointer, _pool
    if _closed:
        # The app is shutting down (or has shut down) and the pool is gone. A late
        # caller here is a straggler run-driver task; opening a fresh pool for it
        # would leak a pool + 4 idle connections past process exit. Fail loudly.
        raise RuntimeError(
            "Checkpointer is closed (application shutdown in progress); refusing "
            "to re-open the LangGraph checkpointer pool."
        )
    if _checkpointer is not None:
        return _checkpointer
```

*Why raise rather than return `None`?* `engine.py:1429` assigns the result straight onto
`ectx.checkpointer` and every downstream `create_runner` treats `None` as "HITL disarmed"
(`deep_agent_runner.py:381`: `self._hitl_armed = bool(interrupt_on) and checkpointer is not None`).
Returning `None` would let a straggler run *silently* without durable state -- worse than an error.
Raising surfaces in the driver's existing exception path.

*A.3 -- rewrite `close_checkpointer` (idempotent, never raises, always consistent).*

Anchor: lines 104-112, the whole function.

BEFORE:

```python
async def close_checkpointer() -> None:
    """Close the Postgres pool on app shutdown (idempotent)."""
    global _checkpointer, _pool
    if _pool is not None:
        try:
            await _pool.close()
        finally:
            _pool = None
    _checkpointer = None
```

AFTER:

```python
async def close_checkpointer(*, timeout: float = 5.0) -> None:
    """Close the LangGraph checkpointer's Postgres pool on app shutdown.

    Idempotent and NON-RAISING -- it is called from the lifespan shutdown, where a
    raise would abort every later teardown step. Latches the module closed so a
    straggler task cannot silently re-open a pool (see ``_closed``).

    Ordering contract (the caller's responsibility, NOT enforced here): every
    in-flight run-driver task must already have been signalled, awaited and (if it
    overran) cancelled before this is called. ``AsyncConnectionPool.close()`` does
    NOT abort a connection that is already checked out -- an in-flight checkpoint
    write completes normally -- but any task that reaches ``getconn()`` AFTER the
    close raises ``psycopg_pool.PoolClosed`` on its next checkpoint write.

    Args:
        timeout: seconds to let the pool's internal worker tasks finish. Bounded
            so shutdown cannot hang inside the docker ``stop_grace_period``.
    """
    global _checkpointer, _pool, _closed

    # Latch FIRST, then take the references and null the globals in one step, so
    # the module is left in a consistent state even if the close below fails.
    _closed = True
    pool, _pool = _pool, None
    saver, _checkpointer = _checkpointer, None

    if pool is None:
        logger.info("Checkpointer: nothing to close (%s).",
                    type(saver).__name__ if saver is not None else "never acquired")
        return

    try:
        await pool.close(timeout=timeout)
        logger.info("Checkpointer: Postgres pool closed cleanly.")
    except Exception:  # noqa: BLE001 -- shutdown must not abort on a teardown error
        logger.exception(
            "Checkpointer: Postgres pool close failed; connections will be dropped "
            "at process exit."
        )
```

Three non-obvious choices, each with its reason:

- **`saver, _checkpointer = _checkpointer, None` happens BEFORE the `await`, not after.** That is
  the fix for defect A: today `_checkpointer = None` sits after the try/finally and is skipped when
  the close raises, leaving a stale saver bound to a dead pool that `get_checkpointer()` will hand
  back forever.
- **`except Exception` + `logger.exception`, not a bare re-raise.** `close_checkpointer()` is the

**The ordering contract, stated precisely (this is D7's real deliverable to D8).**

At the moment the lifespan shutdown body starts, uvicorn has already drained every HTTP request
task (I4 item 9), but the detached run drivers in `_PIPELINE_TASKS` are still running. The close
must therefore be the **last** thing that touches the database, and it must be preceded by:

| # | Step | Why it must precede the close | Owner |
|---|---|---|---|
| 1 | `for ev in list(_CANCEL_EVENTS.values()): ev.set()` | Gives each driver its cooperative exit so it can write a terminal status *while the pool is still open*. Cancelling first would lose that write. | D8 |
| 2 | `await asyncio.wait(list(_PIPELINE_TASKS.values()), timeout=DRAIN)` | A cooperatively-cancelled driver stops at its next check point; those are per-chunk (`engine.py:2514`), pre-agent (`:2287`), the clarify drain's 1s tick (`:1943`), the review-gate race (`:5155-5168`) and the fan-out gather (`fanout.py:668`) [V]. Latency is bounded by one model chunk. | D8 |
| 3 | hard-`cancel()` whatever is still pending, then `await asyncio.wait(..., timeout=2)` suppressing `CancelledError` | Bounds the whole thing inside the 30s `stop_grace_period`, minus whatever uvicorn already spent. | D8 |
| 4 | drain/sentinel the per-run queues | Releases any SSE generator still parked on `live_queue.get()` (interacts with A2/A3, not with D7). | D8 |
| **5** | **`await close_checkpointer()`** | **After 1-3 there is no task left that can call `getconn`.** | **D7** |
| 6 | `engine.dispose()` (SQLAlchemy) | Separate pool; closing it before step 2 would break the drivers' status writes. | D8 (recommended, not required by D7) |

Suggested budget, given `stop_grace_period: 30s` and an unbounded uvicorn pre-wait: `DRAIN = 10s`
(step 2) + `2s` (step 3) + `timeout=5.0` (step 5) = 17s worst case, ~13s of headroom. **[I]** on
the headroom -- I could not measure how long uvicorn's own wait takes in production.

**Nothing is deleted by this fix (INV-3).** There is no superseded implementation: today the
behaviour is absent, not duplicated. The one thing that *would* become a dual implementation is
adding a second shutdown hook beside the lifespan -- explicitly rejected in I12.

##### I6. Ripple-effect analysis -- why nothing else breaks

Assuming the fix is wrong, where does it break?

**Concurrency / ordering.**

- *A driver reaches `getconn` after close.* Raises `PoolClosed`. Mitigated by steps 1-3 above. If
  D8's drain window is exceeded and a task is hard-cancelled mid-`_cursor`, the cancellation
  unwinds the `async with` and returns the connection via `putconn`, which `_maybe_close_connection`
  handles without raising [V, source read]. No hang, no leak.
- *A driver reaches `get_checkpointer()` after close* (a resumed run spawned right at the
  boundary). Raises the new `RuntimeError` instead of silently opening a second pool. This is a
  behaviour change and it is the intended one; before the fix it leaked.
- *Two concurrent `close_checkpointer()` calls.* The globals are taken and nulled **before** the
  first `await`, and asyncio does not preempt between non-awaiting statements, so the second caller
  sees `pool is None` and returns. Proven empirically with a fake pool that raises on a second
  close [V]:
  `6) double close_checkpointer with a live pool: pool.close() called exactly once -> PASS`.
  Belt and braces: `AsyncConnectionPool.close()` itself begins `if self._closed: return` [V].
- *`close_checkpointer()` racing an in-flight `get_checkpointer()` that is mid-`await _pool.open()`.*
  The latch is set first, so the in-flight caller finishes building a pool that is no longer
  referenced by the module. That pool is then orphaned. **This is the one residual hole**, and it is
  unreachable in practice because the only production acquisition site is `engine.py:1429`, reached
  from a driver task, and step 3 has already cancelled those. Documented, not defended against with
  a lock -- adding an `asyncio.Lock` around acquisition would introduce an await into a path that
  runs on every agent dispatch, for a race that requires a task to survive D8's cancel.

**Startup / shutdown interaction.**

- *SIGTERM immediately after boot, while `restore_non_terminal_runs()` is still spawning resume
  tasks (D9's population).* Those tasks land in `_PIPELINE_TASKS` via `_register_resume_task`
  (`run_engine.py:111`) [V], so D8's steps 1-3 cover them; any that slip through hit the latch and
  raise instead of leaking. Strictly better than today.
- *Startup fails before `get_checkpointer()` was ever called.* `_pool is None` -> the function logs
  "nothing to close" and returns. No crash.
- *Dev/SQLite.* `_is_postgres()` is False -> `_pool` stays `None` for the whole process; the close
  is a log line. Verified empirically [V]: `3) close() with _pool=None -> ok`.
- *Windows dev fallback* (`checkpointer.py:64-84`, ProactorEventLoop -> `InMemorySaver`): same, no
  pool.

**Client and run scenarios.**

- *Unattached client / slow client / two browsers / SSE:* D7 touches no SSE code. SSE streams are
  already terminated by `sse-starlette`'s `handle_exit` patch before the lifespan runs (I4 item 9),
  so they neither block nor observe the close.
- *Crashed run / restart / resume:* both `_execute_impl` entry points behave identically; a resumed
  run acquires the same singleton.
- *Fan-out run:* workers are joined by `_gather_or_cancel` which already races `cancel_event`
  (`fanout.py:653-676`) [V], so step 1 propagates into them.
- *Revision run:* rides `_execute_impl` -> same path.
- *Run paused at a human review gate:* this is the case most likely to look scary and is in fact the
  safest. The engine's inter-agent review gate is an in-memory `asyncio.Event`, **not** a LangGraph
  interrupt (documented at `_resume_child.py:17-26` and `test_phase8_resume.py:11-27`) [V], so a
  gate-paused run holds no pool connection and has no pending checkpoint write. The tool-level
  `interrupt_on` gate *is* a real interrupt, but by the time it is observable the checkpoint write
  has already committed. Closing under either is safe.

**Memory and connection-pool effects.** The fix strictly reduces both: 4-10 psycopg connections
released at shutdown instead of dropped, and the resurrection leak (a whole extra pool + its
`min_size=4`) becomes impossible. The SQLAlchemy pool is untouched.

**Partial application.** If only Half A lands, behaviour is identical to today (the latch is never
set) plus two latent bugs fixed. If only Half B lands (the `await` without the hardening), a raising
`pool.close()` would abort the lifespan and leave the poisoned singleton -- so **Half A must land
first or in the same commit**. Stated as a hard sequencing constraint in I10.

**Verifying the dossier's own safety argument.** D8 asserts "Order matters: cancelling before
signalling loses the chance to write a terminal status." I checked this independently: the
cooperative path emits `pipeline_cancelled` through the normal persisted+drained route
(`run_engine.py:41-47` comment, and the observation points listed in I5 step 2), whereas a bare
`task.cancel()` raises `CancelledError` inside the driver. The register records exactly this lesson
in Phase 16 (`IMPLEMENTATION-REGISTER.md:1661, :1679`: cooperative `cancel_event.set()` replaced the
destructive `task.cancel()` for the user-Stop path). **The dossier's ordering claim is correct and
register-backed.** [V]

**INV-3 / golden neutrality.** The characterization harness drives `engine.py:1429` on every run and
gets `InMemorySaver` (sqlite DATABASE_URL). It never calls `close_checkpointer()`, so `_closed`
stays `False` and the new guard is a single `if False:` test. `_pool` stays `None` so nothing else
changes. Goldens are byte/event-identical by construction; measured baseline is unchanged (I8).

"""tests/unit/test_checkpointer_shutdown.py -- D7 regression.

The LangGraph checkpointer's Postgres pool must be closed exactly once on shutdown,
must never be silently re-opened afterwards, and must never leave a stale saver
bound to a closed pool.

OFFLINE by construction: every test drives ``app.agents.checkpointer`` with a fake
pool object injected into the module singletons, so no Postgres server, no docker
and no network are required. The one assertion that genuinely needs a live pool
(``pool.closed is True`` on a real ``AsyncConnectionPool``) is deliberately NOT
here -- it belongs with the docker-gated Phase-8 resume harness.

House style: async bodies are driven with ``asyncio.run`` inside sync test
functions (``asyncio_mode`` is unset in pyproject; see
``tests/unit/test_run_stream_pool_leak.py``).
"""

from __future__ import annotations

import asyncio

import pytest

import app.agents.checkpointer as ck


class _FakePool:
    """Stands in for ``psycopg_pool.AsyncConnectionPool`` (no server needed).

    Mirrors the real ``close(self, timeout: float = 5.0)`` signature so the test
    can assert the teardown is bounded.
    """

    def __init__(self, *, raise_on_close: bool = False) -> None:
        self.close_calls: list[float] = []
        self._raise = raise_on_close

    async def close(self, timeout: float = 5.0) -> None:
        self.close_calls.append(timeout)
        if self._raise:
            raise RuntimeError("simulated pool.close() failure")


@pytest.fixture(autouse=True)
def _isolate_module_singletons():
    """Snapshot/restore the module globals.

    ``app.agents.checkpointer`` is a process-wide singleton shared with the rest of
    the suite (``engine.py`` acquires it on every characterization drive), so these
    tests must leave it exactly as they found it.
    """
    saved = (ck._checkpointer, ck._pool, getattr(ck, "_closed", False))
    ck._checkpointer = None
    ck._pool = None
    ck._closed = False
    yield
    ck._checkpointer, ck._pool, ck._closed = saved


def test_close_closes_the_pool_exactly_once_and_is_idempotent():
    """A double close must not double-close the pool (shutdown may retry)."""
    pool = _FakePool()
    ck._pool = pool
    ck._checkpointer = object()

    async def _drive():
        await ck.close_checkpointer()
        await ck.close_checkpointer()

    asyncio.run(_drive())

    assert len(pool.close_calls) == 1, "pool.close() must be awaited exactly once"
    assert ck._pool is None
    assert ck._checkpointer is None


def test_close_bounds_the_pool_teardown_with_a_finite_timeout():
    """Shutdown lives inside docker's 30s stop_grace_period -- the pool teardown
    must be bounded, not open-ended."""
    pool = _FakePool()
    ck._pool = pool
    ck._checkpointer = object()

    asyncio.run(ck.close_checkpointer())

    assert pool.close_calls, "pool.close() was never awaited"
    t = pool.close_calls[0]
    assert isinstance(t, (int, float)) and 0 < t < 30, (
        f"pool.close() must carry a small finite timeout, got {t!r}"
    )


def test_close_nulls_the_saver_even_when_the_pool_close_fails():
    """Defect A: today ``_checkpointer = None`` sits AFTER the try/finally, so a
    raising pool.close() leaves a stale AsyncPostgresSaver bound to a dead pool --
    which ``get_checkpointer()``'s ``if _checkpointer is not None`` then hands back
    forever, so every later checkpoint op raises PoolClosed."""
    pool = _FakePool(raise_on_close=True)
    ck._pool = pool
    ck._checkpointer = object()

    asyncio.run(ck.close_checkpointer())  # must NOT propagate

    assert ck._pool is None
    assert ck._checkpointer is None, (
        "a failing pool.close() must not leave a stale saver bound to a dead pool"
    )


def test_get_checkpointer_refuses_to_reopen_after_close():
    """Defect B: today ``get_checkpointer()`` after a close silently builds a
    BRAND-NEW AsyncConnectionPool (grown to min_size=4) and re-runs the .setup()
    DDL -- a pool nothing will ever close."""
    ck._pool = _FakePool()
    ck._checkpointer = object()
    asyncio.run(ck.close_checkpointer())

    with pytest.raises(RuntimeError, match="clos"):
        asyncio.run(ck.get_checkpointer())

    assert ck._checkpointer is None
    assert ck._pool is None


def test_get_checkpointer_is_unchanged_before_close():
    """Non-vacuity: the latch must not perturb the normal (pre-shutdown) path --
    this is the path every characterization/golden run takes."""
    if ck._is_postgres():
        pytest.skip("needs a live Postgres; this assertion is for the dev/sqlite path")

    got = asyncio.run(ck.get_checkpointer())
    assert got is not None
    assert asyncio.run(ck.get_checkpointer()) is got, "must stay a cached singleton"


def test_close_is_safe_when_the_checkpointer_was_never_acquired():
    """Startup can fail before the first acquisition; shutdown must not care."""
    asyncio.run(ck.close_checkpointer())
    assert ck._pool is None and ck._checkpointer is None

produce a clean log unless D8's task drain lands too -- a driver killed mid-connection at the 30s
SIGKILL still produces that entry.

##### I9. Rollback

**Repo level.** The change is two files and no migration:
`git revert <sha>` restores `checkpointer.py` to its 112-line form and removes the one `await` from
`main.py`. There is no schema, no data, no cache, no generated artifact to unwind. Ship it as its
own commit (I10) precisely so this revert is clean.

**Host level.** A rollback is a redeploy: `docker compose pull && up -d` with the previous image
tag from `deploy.env` (the per-environment pinned `<env>-<sha>`, `IMPLEMENTATION-REGISTER.md`
Appendix-2 equivalent in the dossier at lines 2017-2023). No host config, no nginx, no SSM, no
bootstrap edit is involved -- **D7 is repo-only, so C1's "no host-configuration change can reach a
running instance" blocker does not apply to it.**

**Not reversible / what a pre-change backup must capture.** Nothing. Concretely:

- No filesystem state is written (the root volume has zero EBS snapshots -- dossier Appendix 2 --
  but D7 writes nothing to it).
- No database rows are created, altered or deleted; alembic head is unchanged.
- The only durable side effect of the *fixed* behaviour is that Postgres sees clean `DISCONNECT`
  instead of `unexpected EOF` in its log. Reverting simply returns to the noisier log.
- In-flight runs at the moment of a rollback deploy are lost exactly as they are today -- that
  exposure is D8's, not D7's.

**Partial-rollback hazard.** If Half B were reverted while Half A stayed, the result is today's
behaviour plus two bug fixes -- safe. If Half A were reverted while Half B stayed, the lifespan
would call the *old* raising, poison-on-failure `close_checkpointer()` -- **do not do this**.
Because they ship in one commit (I10) the hazard is structural only.

##### I12. Shortcuts and alternatives explicitly rejected

**1. `@app.on_event("shutdown")` instead of the lifespan.** Deprecated in FastAPI, and mixing it
with a `lifespan=` argument creates two shutdown mechanisms -- a textbook INV-12 dual
implementation. Concrete failure: FastAPI ignores `on_event` handlers entirely when a `lifespan` is
supplied, so the close would silently never run and the fix would look applied while doing nothing.

**2. `atexit.register(...)` or a `signal.add_signal_handler(SIGTERM, ...)`.** `atexit` cannot await
a coroutine, so it would need `asyncio.run()` on an already-closed loop -> `RuntimeError: Event loop
is closed`. A signal handler would fire *before* uvicorn drains anything (it competes with
`sse-starlette`'s own `handle_exit` patch, `sse.py:70-71`), closing the pool while every driver is
still mid-run -> `PoolClosed` on every in-flight checkpoint write. This is exactly the ordering
inversion the fix exists to avoid.

**3. Close the pool per-run, in the engine's `finally`.** This is the shortcut the code already
warns about at `engine.py:1420-1427` and that Phase 02 locked against (`02-CONTEXT.md:113`). The
singleton is shared: closing after run A breaks every later run. Rejected by an existing lock, not
just by judgement.

**4. Skip the latch -- "just null the globals" (i.e. keep today's `close_checkpointer` shape and
only wire the call).** This is the *tempting minimal* fix and it is wrong. Empirically, a
straggler's `get_checkpointer()` after the close builds a whole new pool and re-runs the `.setup()`
DDL [V] -- so the fix that was supposed to stop leaking a pool leaks a *second* one during shutdown.
The dossier's proposed fix is exactly this shape; it is the main reason the verdict is
CONFIRMED-WITH-CORRECTIONS rather than CONFIRMED.

**5. Let `close_checkpointer()` keep propagating exceptions.** It is step 5 of 6 in D8's sequence;
a raise aborts steps 6+ and surfaces as an unhandled lifespan error. Worse, today's ordering bug
means the raise also leaves the poisoned singleton (defect A). Non-raising + `logger.exception` is
the correct teardown posture and does not hide anything.

**6. Guard the acquisition with an `asyncio.Lock` to close the last residual race** (a
`get_checkpointer()` mid-`await _pool.open()` when the close lands). Rejected: it adds an `await`
to a path that runs on every agent dispatch, to defend a window that requires a task to have
survived D8's cooperative signal, its bounded await, and its hard cancel. Documented in I6 instead.

**7. Wrap the whole shutdown in `asyncio.wait_for(..., timeout=30)` to match `stop_grace_period`.**
Tempting, wrong: uvicorn has *already spent* an unknown, unbounded amount of that 30s waiting for
request tasks (`timeout_graceful_shutdown` is unset -- `docker-entrypoint.sh`) [V], so a 30s budget
inside the lifespan can exceed the real remaining window. Per-step bounds that sum to well under 30s
(I5's 10 + 2 + 5) are the honest shape.

**8. Add `--timeout-graceful-shutdown` to the uvicorn command to bound uvicorn's own wait.** A
genuinely good idea and it *is* the right long-term shape -- but it is a **host/entrypoint** change
in `backend/docker-entrypoint.sh`, which is baked into the image and therefore ships on a normal
deploy (unlike `bootstrap-ec2.sh`). It is nonetheless outside D7's stated scope (the checkpointer
pool), it changes shutdown semantics for every request type, and it belongs with D8 who owns the
shutdown story. Flagged here, not taken.

**9. Right-size the checkpointer pool (`min_size=1, max_size=2`) while in the file.** Correct
observation (I4 item 3), wrong change to smuggle into a lifecycle fix: it alters runtime connection
behaviour and would need its own measurement. Rejected as scope creep.

**Rejections the dossier itself lists:** D7's entry lists none. D8's adjacent text asserts one
ordering constraint ("cancelling before signalling loses the chance to write a terminal status") --
I verified it independently and it holds (I6), backed by the Phase-16 cooperative-cancel decision
(`IMPLEMENTATION-REGISTER.md:1661, :1679`).
