##### I3. Root cause — confirmed, corrected, or replaced

**The dossier's root cause is CORRECT and I re-derived it independently.**

`bootstrap-ec2.sh:712-715` defines a space-delimited access-log format carrying `$status` and
`$request_time` and **no `$upstream_*` variable at all**:

```nginx
log_format velocityai '$remote_addr - $remote_user [$time_local] '
                  '"$request_method $uri $server_protocol" '
                  '$status $body_bytes_sent "$http_referer" '
                  '"$http_user_agent" rt=$request_time';
```

Causal chain, trigger -> symptom:

1. nginx is the only component that can distinguish "I rejected this myself" from "the upstream
   rejected it". The distinguishing evidence is `$upstream_addr`: nginx sets it when it proxied,
   and leaves it unset when it answered from its own `limit_req` / `limit_conn` / `return`. [V] —
   measured, see I8 table.
2. That variable is not in the format, so the evidence is **destroyed at write time**. No downstream
   consumer can recover it.
3. Therefore a `429` from `limit_req zone=velocityai_api` (`:823`) and a `429` returned by FastAPI
   are byte-indistinguishable in `/var/log/nginx/access.log`.
4. The A1 investigation had to resolve that ambiguity by inspecting the response body for an nginx
   `Server` header — an out-of-band probe available only to a human sitting in front of the box.
5. A metric filter has no such option: `[ip, id, user, ts, request, status_code=5*, ...]`
   (`main.tf:469`) can extract `$status` positionally but there is no `upstream_addr` field to test.
   So "we are throttling our own users" (A1, the reported outage) is **unrepresentable** as an alarm
   against this format.

**The dossier's "why it occurred" is right for the right reason** — the format is a reasonable
evolution of `combined`, written before the app had a streaming transport, and because nothing was
ever shipped (B1) nobody ever wrote a query against it and hit the gap.

**One structural addition to the root cause the dossier misses.** The format is not the only
problem: **the log file is not homogeneous.** The `listen 80` server block (`:746-759`) declares no
`access_log`, so it inherits the `http`-level directive from Ubuntu's stock `/etc/nginx/nginx.conf`
(`access_log /var/log/nginx/access.log;` — no format name, therefore `combined`). Both server blocks
write to the **same file** in **different formats**.

- The nginx inheritance mechanism is **[V]** — I proved it: a second server block with no
  `access_log` had its 301 land in the `http`-level file while the block that *did* declare one wrote
  only to its own file (I8, "inheritance probe").
- That Ubuntu's stock `nginx.conf` carries an `http`-level `access_log` is **[I]** — I cannot read the
  box (expired credentials). It is strongly corroborated: the dossier's own Appendix 2 records
  `worker_processes auto` and `worker_connections 768` as "Ubuntu stock — bootstrap never sets it",
  which is exactly the stock file, and `bootstrap-ec2.sh` never writes `/etc/nginx/nginx.conf`
  (grep: the only `access_log` occurrences in the script are `:801` and `:834`).

Today this is harmless: **both** formats are space-delimited with the same first six fields, so
`[ip, id, user, ts, request, status_code=5*, ...]` matches both. The moment the 443 block goes JSON,
the `:80` lines stop matching every filter. A 5xx served on `:80` (an ACME-challenge failure, a
misconfigured redirect) becomes invisible. See I5 step 2 for the one-line fix.

##### I5. The complete fix

Three files. Two halves that **must ship together** — the nginx format and the filters that parse it.

###### Step 1 — `infra/scripts/bootstrap-ec2.sh`, the limits file (§13)

The heredoc at `:706` is **quoted** (`<<'EOF'`), so `$` characters pass through verbatim: **do not
escape anything in this block.**

**BEFORE** (`:706-716`, verbatim):

```bash
cat > /etc/nginx/conf.d/velocityai-limits.conf <<'EOF'
limit_req_zone $binary_remote_addr zone=velocityai_login:10m rate=10r/m;
limit_req_zone $binary_remote_addr zone=velocityai_register:10m rate=5r/m;
limit_req_zone $binary_remote_addr zone=velocityai_change_pw:10m rate=10r/m;
limit_req_zone $binary_remote_addr zone=velocityai_api:10m rate=120r/m;

log_format velocityai '$remote_addr - $remote_user [$time_local] '
                  '"$request_method $uri $server_protocol" '
                  '$status $body_bytes_sent "$http_referer" '
                  '"$http_user_agent" rt=$request_time';
EOF
```

**AFTER:**

```bash
cat > /etc/nginx/conf.d/velocityai-limits.conf <<'EOF'
limit_req_zone $binary_remote_addr zone=velocityai_login:10m rate=10r/m;
limit_req_zone $binary_remote_addr zone=velocityai_register:10m rate=5r/m;
limit_req_zone $binary_remote_addr zone=velocityai_change_pw:10m rate=10r/m;
limit_req_zone $binary_remote_addr zone=velocityai_api:10m rate=120r/m;

# --- E1: structured (JSON) access log ---------------------------------------
# The space-delimited predecessor carried no $upstream_* variable at all, so a
# 429 emitted by limit_req was byte-indistinguishable from a 429 returned by
# FastAPI. $upstream_addr is the discriminator: nginx sets it when it proxied
# and leaves it unset when it answered by itself.
#
# escape=json (nginx >= 1.11.8) and $request_id (>= 1.11.0); the box runs 1.24.0.

# escape=json escapes every VALUE, but it renders an UNSET variable as an EMPTY
# STRING -- NOT as nginx's usual "-" sentinel. The CloudWatch filter that
# identifies an nginx-generated rejection keys on upstream_addr == "-", so
# normalise that ONE field back. Measured on nginx 1.24.0: without this map a
# limit_req 429 logs "upstream_addr":"" and { $.upstream_addr = "-" } never
# matches -- i.e. the alarm that catches "we are throttling our own users"
# silently never fires. Do not delete this map without changing the filter.
map $upstream_addr $velocityai_upstream_addr {
    default $upstream_addr;
    ""      "-";
}

# $status is formatted "%03ui", so a request logged before any response status
# was set renders as "000" (and an HTTP/0.9 request as "009"). Emitted unquoted
# that is invalid JSON (leading zeros) and CloudWatch drops the ENTIRE line from
# every JSON filter. Strip the padding so the field is always a legal JSON number.
map $status $velocityai_status {
    default          $status;
    ~^0+(?<d>[0-9])$ $d;
}

# $uri -- NOT $request / $request_uri / $args. The query string is deliberately
# omitted to mitigate token leakage (docs/SIMPLE_AWS_DEPLOYMENT.md, "Access log":
# "$uri intentionally instead of $request -- strips the query string").
# Do NOT "improve" this to log the full request line.
log_format velocityai escape=json
  '{"time":"$time_iso8601","remote_addr":"$remote_addr","xff":"$http_x_forwarded_for",'
  '"method":"$request_method","uri":"$uri","proto":"$server_protocol",'
  '"status":$velocityai_status,"upstream_status":"$upstream_status",'
  '"upstream_addr":"$velocityai_upstream_addr",'
  '"bytes_sent":$body_bytes_sent,"request_time":$request_time,'
  '"upstream_connect_time":"$upstream_connect_time",'
  '"upstream_header_time":"$upstream_header_time",'
  '"upstream_response_time":"$upstream_response_time",'
  '"connection":$connection,"connection_requests":$connection_requests,'
  '"ssl_protocol":"$ssl_protocol","request_id":"$request_id",'
  '"referer":"$http_referer","user_agent":"$http_user_agent"}';
EOF
```

Why each non-obvious choice, and not the obvious thing:

- **`map` on `$upstream_addr` rather than `{ $.upstream_addr = "" }` in the filter.** An empty-string
  equality is not in the documented CloudWatch JSON-pattern vocabulary and I have no way to test it
  without credentials, whereas `= "-"` is the exact shape already proven in this repo
  (`main.tf:1520`). Normalising in nginx keeps the pattern in the documented subset and keeps the
  JSON honest: `"-"` is nginx's own "no upstream" sentinel, an empty string is ambiguous.
- **Only `upstream_addr` is normalised, not every field.** It is the only one a filter keys on. The
  others read better as `""` (genuinely absent) and normalising them would be noise.
- **`map` on `$status` rather than quoting it.** Quoting (`"status":"$status"`) also produces legal
  JSON, but then `>= 500` is impossible and the filter degrades to a `"5*"` wildcard. Keeping the
  field numeric preserves exact numeric comparison. The map costs four lines and I measured it as
  a pass-through for every real status (I8).
- **Fields are ordered so the two filter keys (`status`, `upstream_addr`) sit adjacent** — a human
  reading a raw line sees the discriminating pair together.

**3b. Add, immediately after the `nginx_5xx_spike` alarm (i.e. after `:497`):**

```hcl
# --- E1: 429 accounting -----------------------------------------------------
#
# Two metrics, deliberately. `Nginx429` is the TOTAL; `NginxLimitReject` is the
# subset nginx produced itself. `upstream_addr == "-"` is the discriminator:
# nginx sets that variable when it proxied and leaves it unset when it answered
# from limit_req / limit_conn / return. The velocityai log_format normalises the
# unset case to "-" with a `map` (escape=json would otherwise emit ""), so this
# pattern matches exactly as written. Measured on nginx 1.24.0.
#
# `Nginx429 - NginxLimitReject` is the count FastAPI returned. If they are
# equal, every 429 a user saw was us throttling ourselves.
resource "aws_cloudwatch_log_metric_filter" "nginx_429" {
  name           = "${var.name_prefix}-nginx-429"
  log_group_name = aws_cloudwatch_log_group.groups["/velocityai/${var.environment}/nginx-access"].name
  pattern        = "{ $.status = 429 }"

  metric_transformation {
    name          = "Nginx429"
    namespace     = var.cw_metric_namespace
    value         = "1"
    default_value = "0"
  }
}

resource "aws_cloudwatch_metric_alarm" "nginx_429_spike" {
```

##### I6. Ripple-effect analysis — why nothing else breaks

Assume the fix is wrong and hunt for it.

**"`escape=json` will emit `-` for missing values like the default escaping does."** It does not, and
this is the single most important thing I found. Measured on nginx 1.24.0 [V]: a `limit_req` 429
logged `"upstream_addr":""`, `"upstream_status":""`, `"ssl_protocol":""` — empty strings, not `-`.
The dossier's `NginxLimit429` pattern `{ $.status = 429 && $.upstream_addr = "-" }` **would never
have matched a single line.** The headline alarm would have been installed, gone green, and been
believed. The `map` in step 1 restores `-`; I then re-measured and got
`"upstream_addr":"-"` on the 429 and `"upstream_addr":"127.0.0.1:9001"` on the proxied requests. [V]

**"A malformed line will poison the filter."** No — CloudWatch evaluates a JSON pattern per event; an
unparseable line matches nothing and affects no other line. The two residual sources of unparseable
lines are both handled: `000`/`009` statuses (the `$status` map) and `:80` combined-format lines (the
`access_log` in step 2). Anything still unparseable is caught by the `nginx-log-parse-stalled` alarm
if it becomes the whole stream.

**Interaction with A1 — `limit_conn` returns 503 and `Nginx5xx` counts it.** A1 deliberately leaves
`limit_conn_status` at the default 503 so that "429 means rate-limited (the bug), 503 means connection
cap reached (working)". Those 503s carry `upstream_addr = "-"` and **are** matched by
`{ $.status >= 500 }`, so a stream-cap event would feed `nginx-5xx-spike` (`Sum > 10`/min for 5 min).
Reaching that needs >10 cap rejections per minute for five consecutive minutes against a cap of 64
concurrent streams per IP — implausible on dev, but it is a genuine coupling and I have named it in
the `nginx_5xx` comment. I did **not** narrow the pattern to exclude nginx-generated 5xx: that would
also drop nginx's own internal 500s, which are exactly the ones nobody else can report. See I10 for
the coordination with A1.

**Interaction with A1 — the new SSE location.** A1 adds
`location ~ ^/api/runs/[^/]+/events/stream/?$`. That location declares no `access_log`, so it inherits
the 443 server's (`:801`) — JSON, correctly. Its requests carry `uri = /api/runs/<id>/events/stream`,
matching `SseStreamClosed`. No interaction beyond the 503 note.

**Interaction with A2/A3/A4/A5.** None. Those are Python changes inside
`app/api/run_engine.py` / `run_stream.py` / `agents/authz.py`. This change touches no `.py` file.

**Interaction with B1/B2/B3/B4.** Strictly **downstream**. Until B1 (agent crash-loop) and B2 (cwagent
cannot read the files) land, `/velocityai/dev/nginx-access` has zero streams, so `Nginx5xx` has never
produced a datapoint and `nginx-5xx-spike` has never been meaningful. E1 is therefore
**observably inert until B1+B2 land** — which is exactly why it is safe to ship first, and exactly why
its verification (I8) has to be done with `aws logs test-metric-filter` and a local nginx rather than
by waiting for real data.

**Interaction with B6 (nobody is subscribed).** The three new alarms will fire into
`velocityai-dev-alerts`, whose only subscription is `PendingConfirmation`. So they are silent until
B6 is closed. B6's own guidance is "fix B1 and B2 first, then subscribe" — E1's `breaching` alarms
add to the pile of alarms that must be quiet **before** anyone confirms the subscription. Named in
I10.

**Interaction with C1.** C1 is the delivery mechanism, not a dependency of the design. Both halves of
step 4 (SSM now, repo for durability) are C1's prescribed pattern.

**Interaction with D3 (`/_next/static/` drops the security headers).** Same file, different lines
(`:908-913` vs `:706-716`/`:746-759`). Textually disjoint. Both are nginx-config edits that need the
same `nginx -t` + reload + SSM delivery, so **batch them into one reload** rather than two.

**Interaction with D11 (`run_stream.py` has no logging).** Complementary, and D11's own text says
"Pair this with E1 so the two are consistent". Both make their side structured; a joined query then
becomes possible. The join key is discussed below.

**Interaction with D10 (`SSE_STREAM_IDLE_TIMEOUT_SECONDS` is dead config).** None — different file,
different layer. Mentioned only because both are "a knob that reads as handled and is not".

**Restart / reload behaviour.** `systemctl reload nginx` sends `SIGHUP`; the master parses the new
config in a new process, and only on success starts new workers and gracefully drains the old ones.
In-flight SSE streams are held by the OLD workers until they close — **no stream is dropped by a
reload**. If `nginx -t` fails, nothing happens at all: the live master keeps its in-memory config.
Downtime on a failed validation is zero.

**Concurrent viewers / fan-out / revision runs / two browsers.** Irrelevant — this change writes one
log line per HTTP request at request close and reads no application state.

**Memory / connection pool.** Two `map` directives add two hash tables of two entries each. The JSON
line is ~371 bytes larger (measured). No pool, no session, no allocation on the request path beyond
the wider buffer.

**Partial application.** The dangerous partial is **filters without format**: `Nginx5xx` returns
nothing, and `notBreaching` keeps the alarm OK — a silent monitoring loss. The reverse partial
(**format without filters**) is loud rather than silent: `Nginx5xx` stops matching, and if
`nginx-log-parse-stalled` has already landed it fires within 24 hours. So the correct ordering is
**format first, then filters** (I10), and the parse-stalled alarm is the net under the ordering.

##### I9. Rollback

- The pre-change backup **must** capture both files, because the change spans two:

###### `$request_id` end-to-end: what it does and does not buy

The dossier's format includes `"request_id":"$request_id"`. I checked what it can correlate with:

```
$ grep -rn "X-Request-ID\|x-request-id\|request_id\|correlation" backend/app backend/agents
backend/app/agents/types.py:85:    # correlation and ArtifactStore keying. Generated lazily if not supplied.
backend/agents/guardrails/mulesoft.md:33:- Log correlation IDs through all error paths ...
$ grep -rn "X-Request-Id\|request_id" infra/
(nothing)
```

**There is no correlation id anywhere.** The proxy-headers snippet (`bootstrap-ec2.sh:718-726`)
forwards `Host`, `X-Real-IP`, `X-Forwarded-For`, `X-Forwarded-Proto` and sets
`proxy_http_version 1.1` — **it does not forward `X-Request-ID`**. And the backend's log format is
`"%(asctime)s | %(levelname)-8s | %(name)-25s | %(message)s"` (`backend/app/main.py:39`) — plain
pipe-delimited text with no request scope at all. So `$request_id` today is a per-line dedup key and
nothing more: you cannot join an nginx line to a backend line.

Making it a real correlation id needs three things, and **all three are outside E1**:

1. `proxy_set_header X-Request-ID $request_id;` in the proxy-headers snippet (one line,
   `bootstrap-ec2.sh:718-726` — same file, adjacent section);
2. FastAPI middleware putting that header into a `contextvar`;
3. the backend log format emitting it — which is **D11's territory**, since D11 already proposes
   switching `run_stream.py` to structured JSON logging.

**I am keeping `$request_id` in scope and steps 1-3 out of scope**, for one reason: emitting it costs
nothing (it is already generated per request whether logged or not), and it is the *prerequisite*
half — you cannot build the join later without it in the nginx log. Doing steps 1-3 inside E1 would
mean editing the proxy-headers snippet that A1 depends on and touching a Python file, and it would
make D11 and E1 mutually blocking. **Recommendation: log it now, and have D11 close the loop** by
adding the `proxy_set_header` line plus the backend side as one change. Flagged to D11 in I11.

##### I12. Shortcuts and alternatives explicitly rejected

1. **Keep the space-delimited format and just add `$upstream_addr` to the end.**
   Tempting because it is a two-word edit and the existing filter keeps working. **Why it is wrong:**
   the pattern `[ip, id, user, ts, request, status_code=5*, ...]` is *positional*. Appending a field
   is survivable (the trailing `...` absorbs it) but any future insertion silently shifts every
   field after it and the filter starts reading the wrong column — with no error, just wrong numbers.
   And a positional pattern cannot express `status = 429 AND upstream_addr = "-"` at all, because
   `upstream_addr` would be inside the unnamed `...` tail. The whole point of E1 is to make the
   discriminator *testable*, and positional patterns cannot test two fields at once.

2. **Set `run_as_user: root` / other B-cluster shortcuts.** Out of scope, and the dossier already
   rejects them for B1. Noted only so nobody folds them in while editing the same file.

3. **Keep the old space-delimited filter alongside the new JSON one "for the transition".**
   Superficially the safe move: neither environment loses coverage. **Why it is wrong:** it is a dual
   implementation with no removal trigger (INV-3/INV-12), and it produces double-counted metrics for
   whichever environment is emitting a format both can read — which is nobody, since a line is either
   JSON or space-delimited. So it costs the complexity of two filters and buys a metric that is
   correct in exactly one configuration. The **`nginx-log-parse-stalled` alarm is the correct answer
   to the same fear**: instead of covering the mismatch, it *detects* it, and it has a natural end
   state (it stays OK).

4. **`limit_conn_status 429` on A1's stream location so both limiters report the same code.**
   Would make `NginxLimitReject` a single clean number. **Why it is wrong:** A1 explicitly chose 503
   so that "429 means rate-limited (the bug), 503 means connection cap reached (working)" — and that
   distinction is worth more than a tidy metric. Not E1's decision to reverse.

5. **Emit `$request` instead of `$uri` "because a JSON access log should carry the full request
   line".** **Why it is wrong:** it re-introduces the query string, reversing the documented
   token-leakage mitigation (`docs/SIMPLE_AWS_DEPLOYMENT.md:821`, "$uri intentionally instead of
   $request"). This is the most likely well-intentioned regression in the whole change, which is why
   step 1 carries an explicit in-file comment forbidding it.

6. **Quote `$status` as a string and use `{ $.status = "5*" }`.** A legitimate alternative that also
   solves the `000` problem. **Why I did not pick it:** it trades an exact numeric comparison for a
   wildcard, and it silently changes the semantics of any future `>` / `<` predicate someone adds.
   The four-line `map` keeps the field numeric and I measured it as a pass-through on every real
   status.

7. **Filter empty strings directly: `{ $.status = 429 && $.upstream_addr = "" }`.** Would avoid the
   `map`. **Why I did not pick it:** empty-string equality is not a construct I can point to
   anywhere in this repo or verify without credentials, whereas `= "-"` is exactly the shape already
   in production at `main.tf:1520`. Guessing at a pattern that silently matches nothing is precisely
   the failure mode this issue exists to fix.

8. **Ship the dossier's `SseStreamSlow` as written.** **Why it is wrong:** `request_time` on a stream
   is the stream's lifetime, measured at 6.007s on a 6-second stream. `> 1` matches every stream, so
   an alarm on it would fire on normal operation and a human reading the metric name would draw the
   wrong conclusion. Renamed to `SseStreamClosed` and the predicate dropped.

9. **Add a `timestamp_format` to the `collect_list` while in the neighbourhood** so CloudWatch uses
   the log's `time` field instead of ingestion time. Genuinely useful and now possible. **Why not
   here:** it edits `bootstrap-ec2.sh:988-995`, which is B3's and B4's block, and it changes event
   timestamps — a behaviour change that deserves its own verification. Belongs with B3/B4.

10. **Fold in the `X-Request-ID` correlation chain** (proxy header + FastAPI middleware + backend log
    format). **Why not:** it would make E1 depend on D11 and touch the proxy-headers snippet A1 also
    depends on. Logging `$request_id` now is the free half; the join belongs to D11 (see I10).

11. **Do nothing until B1 and B2 land, since the filters are inert anyway.** **Why it is wrong:** the
    nginx format change has to be applied to the box by hand (C1), and there is exactly one
    nginx change window planned — the one A1 needs. Missing it means a second SSM run, a second
    `nginx -t`, a second reload, and a second chance to get it wrong on a box with no snapshots.
