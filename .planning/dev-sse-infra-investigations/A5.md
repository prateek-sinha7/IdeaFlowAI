##### I3. Root cause -- confirmed, corrected, or replaced

**The dossier's root cause is correct.** Re-derived independently:

1. `_iter_sse_frames` performs **two** unbounded reads per attach.
   - `:151` `rows = await store.read_events(run_id, after_seq=after_seq)` -- the replay.
     On a fresh attach `after_seq == 0`, so this is the entire log.
   - `:184` `full_log = await store.read_events(run_id, after_seq=0)` -- the entire log,
     **unconditionally, on every attach**, solely to feed the 15-line list scan
     `_dangling_review_gate`.
2. `ScopedStore.read_events` (`authz.py:315-330`) has no `LIMIT` and materializes every
   matching row as an ORM object: `return query.order_by(RunEvent.seq.asc()).all()`.
3. Both lists are **retained for the generator's lifetime**, not just during attach. `rows`
   is bound at `:151` and never rebound; `full_log` is bound at `:184`; the generator then
   parks in `await live_queue.get()` at `:197` for the run's whole duration. Confirmed by
   reading `:135-206`: after the replay loop nothing reads `rows` again.

**Measured, on this machine, against a real `RunEvent` table (5,000 rows, `review_gate_ready`
at seq 4,990):** `[V]`

```text
PRE-FIX  read_events(after_seq=0): rows=5000  94.7 ms  peak=11.90 MB
POST-FIX last_event_of_types    : rows=1      2.82 ms  peak=0.0828 MB
         -> row 4990 type=review_gate_ready gate_key=gk
```

Ratio: 5,000x fewer rows materialized, ~34x faster, ~144x less peak allocation for the
gate-derivation read. (The dossier's own 50,000-row figures -- 924 ms / 103.7 MB -- are
consistent with mine scaled 10x.)

**Causal chain, trigger to symptom:**

```text
client opens GET /api/runs/{id}/events/stream
  -> stream_run_events resolves after_seq from Last-Event-ID (0 on a fresh attach)
  -> _iter_sse_frames:151  read_events(after_seq=after_seq)   [N rows -> ORM list, RETAINED]
  -> replay loop yields N frames                              [rows still bound]
  -> _iter_sse_frames:184  read_events(after_seq=0)           [N rows -> 2nd ORM list, RETAINED]
  -> _dangling_review_gate scans it in Python for ONE row
  -> generator parks at :197 await live_queue.get() for the run's lifetime
  => steady-state RSS cost ~= 2 x (log size) x (concurrent live streams)
  => attach latency ~= 2 x (full-table scan + ORM hydration)
  => an authenticated attach/abort loop is a DB + CPU + allocator amplifier
```

**Two things the dossier states that I independently verified rather than accepted:**

  today is ~2x the log per live stream."* Verified by reading `:151-206` in full -- `rows`

- *"`read_events` has no `LIMIT`."* Verified -- the only `.limit(` in `authz.py` after my
  change would be the new method's. `[V]`

**One thing the dossier gets right for a slightly wrong reason.** It presents the
`after_seq > 0` guard as an *optimization that rests on an application invariant*
("Every `run_events` writer produces `seq >= 1`... it rests on an application invariant
rather than a schema `CHECK`, so a reviewer can drop it"). That is weaker than the truth.
**Today the re-arm at `after_seq == 0` is already structurally dead code**: `full_log` is
`read_events(run_id, after_seq=0)`, whose filter is `RunEvent.seq > 0`, so every row in
`full_log` has `seq >= 1`, so `dangling.seq <= 0` can never be true. The guard is a
**provable behavioural no-op** at code level, independent of any data invariant. This
matters for the fix -- see I5 correction (2).

**A defect the dossier's own fix would introduce.** The dossier's `last_event_of_types`
filters only on `run_id`, `type IN (...)`, and the owner scope -- **no `seq >` filter**. The
deleted `read_events(run_id, after_seq=0)` had one (`seq > 0`). A legacy row with `seq <= 0`
is therefore invisible to the pre-fix code and *visible* to the dossier's query.
Demonstrated: `[V]`

```text
SEQ<=0 TRAP  pre-fix read_events(after_seq=0) sees: [(1, 'agent_chunk')]
             dossier query (no seq filter) -> (0, 'review_gate_ready')   <-- DIVERGES
             corrected query (seq > 0)     -> None                       <-- parity
```

At `after_seq == 0` the outer guard hides it; at `after_seq > 0` it does not
(`0 <= after_seq` is true), so the dossier's version would re-arm a gate the old code
ignored. My fix carries `after_seq` on the primitive (default 0) so the equivalence is
unconditional and the live-DB `SELECT min(seq)` gate becomes unnecessary.

##### I6. Ripple-effect analysis -- why nothing else breaks

Assume the fix is wrong. Where would it show?

**1. A gate that should re-arm does not.** The only way is if the bounded query misses the
open ready. It cannot: the query considers exactly the rows whose type is in `V`, and the
proof in I4.4 shows the max-`seq` element of `V` decides the answer. The 1,004-case
differential includes every length-0-3 sequence over the relevant alphabet.
**Live-observable symptom if wrong:** F5 during a paused gate shows a running pipeline with
no Approve button -- caught by `test_attach_replay_matrix.py:424` and the live check in I8.

**2. A gate re-arms that should not.** Two sub-cases. (a) A resolved gate: proven `None` by
the same argument, pinned by `test_sse_stream.py:410` and `test_attach_replay_matrix.py:448`.
(b) A gate the replay already delivered: the `dangling.seq <= after_seq` comparison is
unchanged, pinned by `test_sse_stream.py:450` (Phase-29 CR-01). **If either broke, the
`_assert_contiguous_deduped_ordered` helper (`test_attach_replay_matrix.py:224-248`) fails
on the duplicate-seq assertion** -- because `_replay_only` (`:206-213`) filters out only
`stream_attached`, so a spurious re-arm lands in the sequence it checks. That is a real,
already-armed tripwire, not a hoped-for one.

**3. Concurrency and ordering.** The new read is a single `SELECT` on its own short-lived
session; it holds no lock and takes no write path. It is issued at the same point in the
generator as the read it replaces, so the interleaving with the live queue is unchanged.
The read is a *snapshot*: a gate resolved between the replay read and the gate read would
be seen as resolved -- identical to today (today's `full_log` is also a later, separate
snapshot). No new race.

**4. Startup / shutdown.** No module-level state, no task, no registry. `app/main.py` is
untouched. `restore_non_terminal_runs` and the resume tier do not call the new method.

**5. Unattached client / slow client / crashed run / restart / resume / fan-out /
revision / two browsers.**
   - *Unattached*: the generator never runs; no change.
   - *Slow client*: strictly better -- the pinned memory per parked generator drops from
     ~2x log to ~0.
   - *Crashed run (no terminal, no gate)*: the bounded query's worst case (I4.5) -- it walks
     that run's index entries and returns `None`. Still strictly cheaper than today, which
     walks the same entries plus hydrates every row.
   - *Restart*: `test_attach_replay_matrix.py::TestRestartReArm` is precisely this, with an
     empty in-memory gate registry. Covered.
   - *Resume*: the resume tier reads `run_events` through its own `read_events` calls
     (I4.1 rows 3-13); none is changed.
   - *Fan-out / wave*: emit through the same engine sink; no interaction.
   - *Revision*: a child run has its own `run_id`; the query is `run_id`-scoped.
   - *Two browsers*: each opens its own generator; each now retains ~0 instead of ~2x log.
     This is the interaction with A2 -- see I10.

**6. Memory and connection pool.** The new method's `finally: if owned: session.close()`
is what keeps the connection returned. If an executor omitted it, BUG-004 reopens -- one
leaked connection per *reconnecting* stream (not per fresh attach, because of the guard),
which is exactly the case the existing pool-leak test does **not** cover. That is why I8 T6
is mandatory, not optional.

**7. Partial application.** If Step 1 lands without Steps 2-5: an unused method, zero
behaviour change. If Steps 2-5 land without Step 1: `AttributeError: 'ScopedStore' object
has no attribute 'last_event_of_types'` on the first reconnect with a `Last-Event-ID` --

```python
class _CountingStore:
    """Wraps a real ScopedStore and records (method, rows_returned) per call.

    Duck-typed: ``_iter_sse_frames`` types ``store`` as ``Any``, so this drops in.
    Pre-fix it records two ``read_events`` calls; post-fix one ``read_events`` plus (only
    when ``after_seq > 0``) one ``last_event_of_types``.
    """

    def __init__(self, inner):
        self._inner = inner
        self.reads: list[tuple[str, int]] = []

    async def read_events(self, run_id, after_seq):
        rows = await self._inner.read_events(run_id, after_seq)
        self.reads.append(("read_events", len(rows)))
        return rows

    async def last_event_of_types(self, run_id, types, after_seq: int = 0):
        row = await self._inner.last_event_of_types(run_id, types, after_seq)
        self.reads.append(("last_event_of_types", 0 if row is None else 1))
        return row

    @property
    def rows_materialized(self) -> int:
        return sum(n for _, n in self.reads)


def _seed_big_log(db, *, n=5000, gate_at=4990):
    rows = [(i, "agent_chunk", {"seq": i, "text": "x" * 64}) for i in range(1, n + 1)]
    rows[gate_at - 1] = (gate_at, "review_gate_ready", {"seq": gate_at, "gate_key": "gk"})
    _seed_events(db, rows)


class TestGateRearmBounded:
    def test_gate_rearm_materializes_at_most_one_row(self, db_session):

        _seed_big_log(db_session, n=5000, gate_at=4990)

        store = _CountingStore(_store(db_session))
        frames = asyncio.run(
            _collect(
                _iter_sse_frames(
                    run_id="run-1", store=store, after_seq=5000, live_queue=None
                )
            )
        )
        parsed = [_parse(f) for f in frames]

        assert len(rearmed) == 1, "a paused gate past the cursor must re-arm exactly once"
        assert rearmed[0]["id"] == "4990"
        assert rearmed[0]["data"]["gate_key"] == "gk"
```

##### I9. Rollback

**Repo-side, and only repo-side.** There is no host component: no nginx location, no
systemd unit, no SSM document, no CloudWatch config, no IAM change, no S3 object, no
migration.

- **Full revert:** `git revert` the three commits in reverse order (Step 4, then Steps
  2/3/5, then Step 1). Each is independently revertable *except* that Steps 3 and 5 are one
  commit by construction.
- **Partial revert:** reverting only commit 3 (`rows = ()` / `r = None`) restores the old
  retention with no correctness effect. Reverting only commit 2 restores the full-log read
  and leaves commit 1's method unused and harmless.
- **Runtime rollback:** redeploy the previous image tag. Because the change is entirely in
  the Python source, the deployed container is the unit of rollback; the CodeBuild pipeline
  already pins `<env>-<sha>` per environment (register: no floating tags).
- **Not reversible / no rollback available:** nothing. There is no data mutation, no schema
  change, and no host file written. **The pre-change backup needs to capture nothing** --
  which is worth stating explicitly because the environment has *no* EBS snapshots and no
  filesystem-level rollback (Appendix 2); A5 is one of the few fixes in this dossier where
  that does not matter.
- **Detecting a bad rollout:** the observable failure mode is a paused gate that does not
  re-open on reload. After D11 lands, the close-reason log would show it; today it is only
  visible from the browser. Keep the live check in I8 as the post-deploy smoke.

##### I11. Open questions requiring a human decision

**1. The replay cap (deferred by the dossier, and correctly so).** A 97,694-event run
replays 97,694 frames on a fresh attach. A5 makes that *transient* rather than *retained*,
but it does not make it *small*. Capping it is a **product behaviour change** and needs a
decision.

- *Options:* (a) do nothing -- accept a slow first paint on a huge run; (b) cap the replay
  at the last K events and signal truncation to the client; (c) cap only `agent_chunk`
  frames (the 97,549-of-97,694 bulk) and replay every other type in full.
- *The contract a cap would need, if chosen:* a new field on the existing
  `stream_attached` frame -- e.g. `{"replay_truncated": true, "oldest_replayed_seq": N}` --
  so the client knows its transcript is partial and can fetch older history through the
  existing `GET /api/runs/{id}/events?after=N` REST twin (`runs.py:940`). It must go on
  `stream_attached` rather than a new event type, because a new type would have to be added
  to `_DOCUMENTED_EVENT_TYPES` and could perturb the golden event multiset (the Phase-28
  CHAT-06 rule). The frontend would need a "load earlier" affordance in the Steps trace and
  the chat transcript, and `useRunStream`'s cursor logic would need to tolerate a first
  frame whose `seq` is not 1. That is a frontend contract change and a UX decision.
- *My recommendation:* **(c) later, not now.** A5 removes the retention (the part that
  scales with concurrent streams). The remaining cost is per-attach and one-shot. Measure it
  after A1+A5 land, with D11's open/close log giving the actual replay sizes and durations,
  and decide with data rather than the 97,694 anecdote.

**2. Whether to fold `engine.py:5585` into this change.** `if await store.read_events(wr.id,
after_seq=0):` materialises the entire log to answer a boolean at boot. It is the single
worst unbounded read in the repo and a one-line fix with the same primitive
(`last_event_of_types` is not the right shape; it wants an `EXISTS`/`LIMIT 1`). It runs
once per non-terminal run at startup and interacts with **D9** (boot re-launches every
non-terminal run at once). *My recommendation:* **not in A5** -- it is a different hot path
with a different blast radius (the restart classifier), and folding it in would dilute A5's
proof. Log it as a D9 companion.

Nothing else. I have not invented decisions to defer.

##### I12. Shortcuts and alternatives explicitly rejected

The dossier lists four rejections. I verified all four and add five more.

**Verified from the dossier:**

1. **Push the CR-01 guard into the query** (`... AND seq <= :after_seq ORDER BY seq DESC
   LIMIT 1`). **Wrong, and tempting.** Counter-example confirmed by construction:
   ready@5, approved@12, `after_seq=8`. Correct answer: no re-arm (the last
   gate-vocabulary row is the approval). The filtered query returns ready@5 and `5 <= 8`
   passes -> an **already-approved gate is re-opened**, emitted after the replay already
   delivered the approval. The `seq <= after_seq` comparison must stay *outside* the query,
   applied to the unfiltered max.
2. **Bound the scan to the last K events.** Breaks semantics: an open gate can legitimately
   sit far from the tail behind chat-lane rows (`chat_message`/`chat_reply` land in the same
   `run_events` table via `append_event_next_seq`), and "far" has no provable bound.
   Confirmed: those writers are real (`chat_narrator.py:280`, `run_commands.py:726/913/1263/1356`).
3. **Two aggregate queries** (max ready seq, max resolution seq). Two round trips, and
   without a `type` index each scans the same range -- strictly worse than one `LIMIT 1`.
4. **Reuse `derive_open_gate`.** Right vocabulary home (`gate_pendency.py:68`), wrong shape:
   a pure function over a caller-supplied list. Using it *keeps* the unbounded read that is
   the bug. Verified by reading it -- it takes `events: list`.

**Added by this investigation:**

5. **Ship the dossier's `last_event_of_types` verbatim (no `seq > after_seq` filter).**
   Rejected because it is **not equivalent**: it surfaces `seq <= 0` rows the deleted
   `read_events(run_id, after_seq=0)` filtered out, which at any `after_seq > 0` would
   re-arm a gate the pre-fix code ignored. Demonstrated live in I3. The failure is silent
   (a spurious Approve panel on reconnect), data-dependent, and would not be caught by any
   existing test.
6. **Rely on the `SELECT min(seq) >= 1` data gate instead of the `seq >` filter.** Rejected
   because it makes a *code* property depend on a *data* audit that must be re-run on every
   environment forever -- and I cannot run it at all here (`aws sts` returns `ExpiredToken`,
   no `psql`). The `seq > after_seq` filter makes the property unconditional and free.
7. **Skip the `after_seq > 0` guard "because it is only an optimisation".** Rejected: a
   fresh attach with no `Last-Event-ID` is both the most common attach and the
   attach-churn amplification vector A5 exists to close. Skipping the query there is a
   provable no-op (I3) and is where the saving is largest. Keeping the guard costs one
   `if`.
8. **`rows = ()` only, leaving `r` bound.** Rejected: measured 1/400 rows still alive; for a
   run whose last replayed row is an `agent_input` that is ~214 KB pinned per live stream,
   for one extra line. Add `r = None`.
9. **Convert the `:151` replay to a server-side cursor / `yield_per` / chunked pagination.**
   Rejected for the dossier's two reasons, both of which I verified rather than accepted:
   - *A cursor reintroduces BUG-004.* Streaming requires holding the session open across
     yields to `sse_starlette`, which awaits the client socket, so a slow client pins a
     pooled connection for the whole replay. The pool is `pool_size=20, max_overflow=40,
     pool_timeout=30` (`database.py:19-28`) -- 60 connections app-wide. Trading a memory
     ceiling for **pool exhaustion** is a worse failure mode, and is exactly what the
     `run_stream.py:251-265` comment and `test_run_stream_pool_leak.py` exist to prevent.
     `[V]`
   - *Chunked keyset pagination widens a correctness race.* Today the replay is one
     `SELECT` -- one consistent snapshot. Chunking turns one snapshot into ~98 for a
     97,694-row run, widening the window in which a newly-appended row is both replayed
     *and* drained -> a duplicate `seq` on the wire, violating
     `_assert_contiguous_deduped_ordered` (`test_attach_replay_matrix.py:224-248`, verified
     to assert `len(seqs) == len(set(seqs))` at `:235`). `[V]`
10. **Pre-emptively add a partial index** whose predicate matches the gate vocabulary.
    Rejected for now: `run_events` is append-heavy (741,914 rows per the dossier `[I]` --
    I cannot verify without DB access) so any new index taxes the hottest write path; and
    the predicate would hard-code `REVIEW_RESOLUTIONS`, so changing that frozenset would
    then require a migration -- coupling a Python constant to the schema. Decide with
    `EXPLAIN (ANALYZE, BUFFERS)` on a real large run, after A5 is live.
11. **Delete the D-14g re-arm entirely** ("the replay covers it"). Rejected: it does not.
    The re-arm exists precisely for the case the replay filter excludes -- a client whose
    cursor is already *past* the gate row. `test_attach_replay_matrix.py:437-438` documents
    this in the test itself ("Client cursor already PAST the gate frame -- without D-14g
    re-arm it would never re-open"), and it is the P23/F4 hole the feature was built to
    close.
