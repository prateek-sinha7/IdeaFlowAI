##### I3. Root cause — confirmed, corrected, or replaced

**CONFIRMED, and independently reproduced.** Re-derived from the code, not from the dossier:

1. `run_engine.py:64-67` creates **one** `asyncio.Queue` per `run_id` and hands the *same object* to
   every caller.
2. Nine-plus producer sites write to it (full list in I4). `run_stream.py:197`
   `event = await live_queue.get()` is the **only** consumer in production — I proved this by grepping
   every `.get()`/`get_nowait()` in `backend/`: the only other queue reads are `engine.py:1931/1958`,
   which operate on a **function-local** `asyncio.Queue` created at `engine.py:1899` for the clarify
   drain, not on `_PIPELINE_QUEUES`.
3. `asyncio.Queue.get()` is consume-once. N concurrent generators therefore partition the stream.

**My reproduction** (`scratchpad/repro_before_paced.py`, driving the REAL `_iter_sse_frames` with a
scripted store and three consumers, one event per 10 ms — realistic pacing):

```
TAB-A: [3, 6, 9, 12]
TAB-B: [4, 7, 10]
TAB-C: [5, 8, 11]
overlap A∩B: []
stranded-forever consumers: ['TAB-A', 'TAB-C']
```

Perfect round-robin partition, **zero overlap**, and 2 of 3 consumers never terminate. With an
un-paced burst the shape changes (one consumer monopolises: `TAB-A [3..12]`, B and C get nothing)
— the *distribution* is scheduling-dependent, but the two invariants hold in both: **the halves are
disjoint** and **only the consumer that happens to take the sentinel terminates**.

**Causal chain, trigger → symptom:**

```
user opens a running run in a 2nd tab (History → page.tsx:1632 → attachRun)
  → RunConnectionProvider unions the focus in            (RunConnectionProvider.tsx:363-370)
  → a 2nd GET /api/runs/{id}/events/stream               (run_stream.py:208)
  → run_stream.py:281 hands BOTH streams the SAME Queue  (run_engine.py:64-67)
  → both park on `await live_queue.get()`                (run_stream.py:197)
  → engine emits event N → driver put()s it ONCE         (run_commands.py:2084)
  → asyncio wakes exactly ONE waiter                     (asyncio.Queue semantics)
  → tab A gets N, tab B never sees N (and vice versa)
  → `agent_chunk` text is split → garbled output in BOTH tabs
  → `review_gate_ready` / `questionnaire_ready` land in ONE tab → the other is un-actionable
  → the sole `None` sentinel (run_commands.py:2185) releases ONE generator
  → the rest park forever; run_stream.py:195 checks disconnect BEFORE the get(), never after
```

**The "durable replay cannot heal it" argument — verified, and the mechanism is subtler than the
dossier states.** The replay filter is `RunEvent.seq > after_seq` (`authz.py:324`), and the client
cursor is a strict high-water mark (`useRunStream.ts:255-263`, `dashboard/page.tsx:447` — both
`>` comparisons). **But the two cursors are different objects and only one of them matters:**
`useRunStream`'s `cursorRef` is what becomes `Last-Event-ID` (`:334-336`), and it advances on *every
frame the tab receives*. So tab A, receiving 3/6/9/12, advances its cursor to 12 — putting 4,5,7,8,10,11
permanently below its own resume cursor. Confirmed. `dashboard/page.tsx`'s `lastSeqRef` is a second,
independent cursor used by nothing on the SSE path (`getRunEvents` re-fetches read `lastSeqRef` only
inside `useRunChat`), so it is not the load-bearing one — the dossier's citation of `:447` is
directionally right but the operative anchor is `useRunStream.ts:255-263`.

**One correction to the dossier's severity framing.** It says "The terminal event does self-heal
about a second late, because `pipeline_complete` carries the highest seq". That is only true for
whichever tab *receives* `pipeline_complete`. The other tab receives the `None` sentinel or nothing;
it never sees a terminal, so its stream either closes silently (sentinel → generator returns → close
→ `sawNonLiveAttachRef` is false → **reconnect** → full replay from its stale cursor → it DOES
eventually self-heal on the terminal, one reconnect later) or it hangs forever. So the terminal
self-heal is real but arrives via a reconnect, not directly.

```python
# ---------------------------------------------------------------------------
# ``_PIPELINE_QUEUES[run_id]`` is a POINT-TO-POINT channel: ``asyncio.Queue.get()``
# delivers each item to exactly ONE awaiting consumer. That was correct while a run
# had exactly one attached connection (the deleted ``/ws/chat`` drainer). It is not
# correct now: the SSE transport is per-run MULTI-ATTACH (two browser tabs, or a tab
# plus a reopened-from-History view), and N consumers on one queue round-robin the
# events between them — silent, unrecoverable data loss (replay is ``seq > cursor``
# and every client cursor is a high-water mark, so a stolen event is never replayed).
#
# The bus makes the SOURCE queue single-consumer again: exactly ONE pump task per run
# drains it and re-publishes each event to every subscriber's own bounded queue.
#
# Invariants a future change must preserve:
#   * ``subscribe`` / ``unsubscribe`` / ``_publish`` / ``_evict_subscriber`` /
#     ``_close_run`` / ``_ensure_pump`` are ALL SYNCHRONOUS. That is what makes the
#     subscribe-vs-close race lock-free: asyncio never preempts between two
#     non-awaiting statements, so ``subscribe`` either sees the liveness key present
#     (and is therefore in the set when ``_close_run`` sentinels) or sees it absent
#     (and returns ``None``). Introducing an ``await`` destroys that argument — this

#     single-threaded loop and costs the atomicity.
#   * ``_PUMPS`` is keyed by ``(task, source_queue)``. Identity matters: a run id can
#     be RE-registered with a NEW source queue (``_cleanup_pipeline`` pops the entry,
#     then ``POST /{id}/resume`` step 4 re-creates it) while the previous pump task is
#     still scheduled. Without the identity check the stale pump's ``finally`` tears
#     down the NEW registration and sentinels the new subscribers immediately —
#     proven: the resumed run's client receives ``[None]`` and nothing else.

#     mutate: ``_iter_sse_frames`` (run_stream.py:200-205) only reads it.

# reference was a local would be garbage-collected mid-run.
```

```python
def _publish(pipeline_run_id: str, event: Any) -> None:
    """Deliver one event to every subscriber of ``pipeline_run_id``.

    Iterates a ``list(...)`` snapshot so an eviction inside the loop cannot mutate the
    set under iteration. Hands the SAME object to every subscriber (no copy).
    """
    for q in list(_SUBSCRIBERS.get(pipeline_run_id, ())):
        try:
            q.put_nowait(event)
        except asyncio.QueueFull:
            _evict_subscriber(pipeline_run_id, q)


def _evict_subscriber(pipeline_run_id: str, q: asyncio.Queue) -> None:
    """Drop a subscriber that fell ``SSE_SUBSCRIBER_QUEUE_MAXSIZE`` events behind.

    Eviction beats dropping because it is SELF-HEALING: the sentinel ends that client's
    SSE response; the client saw ``stream_attached {live:true}`` so
    ``useRunStream.sawNonLiveAttachRef`` is false and it schedules a reconnect
    (useRunStream.ts:398-404) carrying ``Last-Event-ID`` (:334-336); the server replays
    exactly the missing range from ``run_events``. Dropping would corrupt the stream
    with no recovery path — the frontend has no gap detection.

    The ENTIRE backlog is drained, not just one slot. Draining only enough to fit the
    sentinel would let the client consume the remaining ~999 queued events and advance
    its high-water cursor PAST the one event that was dropped — recreating exactly the
    unrecoverable hole this whole change exists to close.
    """
    subs = _SUBSCRIBERS.get(pipeline_run_id)
    if subs is not None:
        subs.discard(q)
        if not subs:
            _SUBSCRIBERS.pop(pipeline_run_id, None)
    try:
        while True:
            q.get_nowait()
    except asyncio.QueueEmpty:
        pass
    try:
        q.put_nowait(None)
    except Exception:  # noqa: BLE001 — eviction must never raise into the pump
        pass
    logger.warning(
        "sse_subscriber_evicted run_id=%s maxsize=%s reason=slow_consumer",
        pipeline_run_id,
        settings.SSE_SUBSCRIBER_QUEUE_MAXSIZE,
    )


def _close_run(pipeline_run_id: str, source: asyncio.Queue | None = None) -> None:
    """End the bus for a run: pop the liveness key FIRST, then sentinel every subscriber.

    Popping first is what makes ``subscribe`` race-free without a lock (see the invariant
    note). Idempotent.

    ``source`` is the queue the CALLING pump was draining. When it no longer matches the
    registered queue, this call comes from a STALE pump whose run id has since been
    re-registered with a new source — it must NOT tear the newer registration down.
    """
    if (
        source is not None
        and pipeline_run_id in _PIPELINE_QUEUES
        and _PIPELINE_QUEUES.get(pipeline_run_id) is not source
    ):
        return
    _PIPELINE_QUEUES.pop(pipeline_run_id, None)
    _PUMPS.pop(pipeline_run_id, None)
    for q in list(_SUBSCRIBERS.pop(pipeline_run_id, ()) or ()):
        try:
            q.put_nowait(None)
        except Exception:  # noqa: BLE001
            pass


async def _pump(pipeline_run_id: str, source: asyncio.Queue) -> None:
    """The SOLE consumer of a run's source queue; re-publishes to every subscriber."""
    try:
        while True:
            event = await source.get()
            if event is None:  # sentinel: the run's producer is finished
                return
            _publish(pipeline_run_id, event)
    except asyncio.CancelledError:
        raise
    except Exception:  # noqa: BLE001 — a pump crash must not take the process with it
        logger.exception("sse_pump_crashed run_id=%s", pipeline_run_id)
    finally:
        _close_run(pipeline_run_id, source)


def _ensure_pump(pipeline_run_id: str) -> None:
    """Start the run's pump if it is not already draining the CURRENT source queue.

    No-ops when: there is no source queue; a live pump is already on THIS source; or
    there is no running event loop (a synchronous caller — import time, a sync test).
    In the last case ``subscribe`` will arm the pump on the first attach.
    """
    source = _PIPELINE_QUEUES.get(pipeline_run_id)
    if source is None:
        return
    entry = _PUMPS.get(pipeline_run_id)
    if entry is not None:
        task, pumped = entry
        if not task.done() and pumped is source:
            return
        if not task.done():
            # A stale pump on a REPLACED source: cancel it. Safe because _close_run's
            # source guard stops its finally from clobbering this newer registration.
            task.cancel()
    try:
        asyncio.get_running_loop()
    except RuntimeError:
        return
    _PUMPS[pipeline_run_id] = (
        asyncio.create_task(
            _pump(pipeline_run_id, source), name=f"sse-pump:{pipeline_run_id}"
        ),
        source,
    )


def subscribe(pipeline_run_id: str) -> asyncio.Queue | None:
    """Register one SSE consumer. ``None`` when the run has no live source queue.

    MUST be called from inside the response generator's body, never from the endpoint
    handler — see the note in ``run_stream.py::_subscribed_sse_frames``.
    """
    if pipeline_run_id not in _PIPELINE_QUEUES:
        return None
    q: asyncio.Queue = asyncio.Queue(maxsize=settings.SSE_SUBSCRIBER_QUEUE_MAXSIZE)
    _SUBSCRIBERS.setdefault(pipeline_run_id, set()).add(q)
    _ensure_pump(pipeline_run_id)
    return q


def unsubscribe(pipeline_run_id: str, q: asyncio.Queue) -> None:
    """Deregister one SSE consumer. Idempotent; drops the empty set entry."""
    subs = _SUBSCRIBERS.get(pipeline_run_id)
    if subs is None:
        return
    subs.discard(q)
    if not subs:
        _SUBSCRIBERS.pop(pipeline_run_id, None)
```

```python
async def _subscribed_sse_frames(
    *,
    run_id: str,
    store: Any,
    after_seq: int,
    request: Optional[Request] = None,
) -> AsyncIterator[dict]:
    """Register this client on the run's fan-out bus, then delegate to ``_iter_sse_frames``.

    Two properties are load-bearing and must not be "simplified":

    1. **``subscribe`` happens INSIDE the generator body, not in the endpoint handler.**
       An async generator's body does not run until its first ``__anext__``. If the
       request aborts before ``EventSourceResponse`` starts iterating, the body never
       runs — so an endpoint-body ``subscribe`` would leak a registration with no
       matching ``finally``. (``sse_starlette==3.0.2`` never calls ``aclose()`` on the
       body iterator except on a send-timeout, and ``aclose()`` on a NEVER-STARTED
       async generator does not execute the body at all — both verified.)

    2. **``subscribe`` happens BEFORE the durable replay** (which is the first thing
       ``_iter_sse_frames`` does). The replay is a snapshot; any event committed after
       the snapshot but before the subscribe would be in neither the replay nor this
       client's queue, and is unrecoverable because replay is ``seq > after_seq`` and
       the client cursor is a maximum. The resulting overlap is SAFE because
       persistence precedes publication (``engine.py:1032-1033``): a duplicate is the
       same row with the same ``event_id``, dropped at the single frontend dedup site
       (``dashboard/page.tsx:436-442`` -> ``wsReplayState.ts:32-40``) BEFORE the cursor
       advances (``page.tsx:445-448``).

    The ``finally`` is reached on every exit: normal completion, the terminal-event
    early return, the sentinel, and client disconnect (anyio cancels ``_stream_response``
    while it is suspended inside this generator, which raises ``CancelledError`` into
    the frame and unwinds through the ``finally`` — verified). ``unsubscribe`` is
    synchronous, so it completes even inside a cancelled scope.
    """
    live_queue = subscribe(run_id)
    try:
        async for frame in _iter_sse_frames(
            run_id=run_id,
            store=store,
            after_seq=after_seq,
            live_queue=live_queue,
            request=request,
        ):
            yield frame
    finally:
        if live_queue is not None:
            unsubscribe(run_id, live_queue)
```

##### I6. Ripple-effect analysis — why nothing else breaks

I assumed the fix was wrong and went looking. Here is what I found, including one thing that **is**

**FAILURE FOUND — the stale-pump / replaced-source race (the dossier's design is broken here).**
The dossier specifies `_PUMPS: dict[str, asyncio.Task]` and a bare `_close_run(run_id)`. Sequence:

```
launch:   _get_or_create_queue(R)      -> queue Q1, pump P1 (draining Q1)
driver finally: put(None) on Q1; _cleanup_pipeline(R)   # pops _PIPELINE_QUEUES[R]
                                                        # (no await -> P1 has not run yet)
resume:   POST /{id}/resume step 3 mutex passes (both registries popped)
          step 4 _get_or_create_queue(R) -> NEW queue Q2
                 _ensure_pump sees P1 not done -> returns -> Q2 HAS NO PUMP
client:   subscribe(R) -> a queue
loop runs: P1 sees the sentinel -> finally -> _close_run(R) -> pops Q2's registration
                                            -> sentinels the client's queue
```

I built both versions and ran them (`scratchpad/race_test.py`):

```
DOSSIER-FORM : subscriber received [None]
CORRECTED    : subscriber received [{'type': 'agent_chunk', 'data': {'seq': 1}}]
```

The resumed run is **dead on arrival** under the dossier's design: the client's stream closes the
instant it attaches and no event is ever delivered. My fix is the `(task, source)` tuple in `_PUMPS`
plus the `source` guard in `_close_run` (Step 2c above). Both are in the corrected text.

**Concurrency and ordering.**

- *Subscribe vs `_close_run`.* Verified the dossier's argument holds **for the corrected code**:
  both functions are synchronous, `_close_run` pops the liveness key before broadcasting, and asyncio
  does not preempt between non-awaiting statements. Two interleavings only. My prototype: a
  pre-close subscriber is sentinel-released; a post-close `subscribe()` returns `None`, so
  `_iter_sse_frames` takes its existing `live_queue is None` early return at `:192-193`.
- *Churn.* 59 attach/detach cycles interleaved with 60 events, plus a witness subscriber: the witness
  received all 60 contiguously, zero stranded, and all three registries empty afterwards.
- *Event ordering across subscribers.* `_publish` is a synchronous loop over a snapshot, so every
  subscriber receives events in the same order the pump saw them. Per-subscriber ordering is FIFO by
  construction. Verified at N = 2, 3, 5 — identical ordered sets in every case.
- *Same-object publication.* `_iter_sse_frames:200-205` only reads (`event.get`, `data.get`), and
  `_sse_frame` -> `json.dumps` is read-only. No mutation. Confirmed by reading the code.

**Startup / shutdown.**

- *Startup.* `app/main.py:141-143` injects `_register_resume_queue`, which delegates to
  `_get_or_create_queue`, which arms the pump. `restore_non_terminal_runs` runs inside the lifespan
  where a loop exists, so the pump starts. No `main.py` edit needed.
- *Shutdown — this is a real gap and it belongs to D8.* Pumps are bare `asyncio.create_task`s with
  no shutdown hook. On `SIGTERM` the loop closes with pumps pending and Python logs
  "Task was destroyed but it is pending". Not a correctness bug (nothing is persisted by a pump) but
  it is noise and it should be closed by D8's shutdown body, which already lists
  *"Drain and sentinel the per-run queues (after A2, the pumps handle this — `_close_run` per run)"*.
  I flag the dependency in I10 rather than absorbing D8's work.

**Client scenarios.**

- *Unattached client (zero subscribers).* The pump drains and discards. This is the sign-off item —
  treated adversarially in its own subsection below.
- *Slow client.* Bounded at `SSE_SUBSCRIBER_QUEUE_MAXSIZE`, then evicted. Verified with the bound
  shrunk to 8 and a deliberately-stuck subscriber: exactly one eviction; the stuck queue ended
  holding only the sentinel; a healthy subscriber on the same run received all 40 events contiguously.
- *Crashed run.* The driver's `except`/`finally` still puts the sentinel (`run_commands.py:2185`),
  the pump exits, `_close_run` sentinels every subscriber. Every attached client's stream ends
  cleanly instead of hanging — a strict improvement.
- *Restart.* Everything is in-process and rebuilt from `restore_non_terminal_runs`; nothing persists.
- *Resume.* Covered above (the race) — corrected.
- *Fan-out run.* Highest event volume, therefore the biggest eviction-pressure case. Worker events
  ride the same `yield` path, so nothing structural differs. The 1000-slot bound is the only knob.
- *Revision run.* `_drive_revision_to_queue` writes to a registered queue; pump behaves identically.
- *Two browsers.* The whole point. Verified at N = 2, 3, 5.

**Memory and connection pool.**

- Worst theoretical case: 1000 queued `agent_input` events at A5's measured ~214 KB average = ~214 MB.
  Mitigated three ways: (i) `agent_input` fires once per agent (5-15 per run), the bulk is

```python
class TestConcurrentClients:

    publish / sentinel path end to end.

    @staticmethod
    def _register_live(run_id: str):
        """Register a live source queue the way a launch driver does."""
        from app.api import run_engine as rev

        return rev._get_or_create_queue(run_id)

    @staticmethod
    def _reset_registries():
        from app.api import run_engine as rev

        for name in ("_PIPELINE_QUEUES", "_PIPELINE_TASKS", "_CANCEL_EVENTS",
                     "_SUBSCRIBERS", "_PUMPS"):
            reg = getattr(rev, name, None)
            if isinstance(reg, dict):

    @staticmethod
    async def _open(app, run_id: str, after_seq: int = 0):
        """Build the endpoint's EventSourceResponse and return its body_iterator."""
        from app.api.run_stream import stream_run_events

        class _Req:
            async def is_disconnected(self):
                return False

        # Resolve the app's dependency overrides the same way the TestClient does.
        user = app.dependency_overrides[get_current_user]()
        db_dep = app.dependency_overrides[get_db]
        db = next(db_dep())
        resp = await stream_run_events(
            run_id,
            _Req(),                       # type: ignore[arg-type]
            last_event_id=str(after_seq) if after_seq else None,
            current_user=user,
            db=db,
        )
        return resp.body_iterator

            body = json.loads(frame["data"])
            out.append({"id": frame["id"], "type": body["type"]})
            if stop_after_terminal and body["type"] == "pipeline_complete":
                break
        return out

    def test_two_concurrent_clients_observe_the_same_ordered_seq_set(self, api, db_session):
        """RED on dev: the two clients round-robin the tail and their seq lists differ."""
        client, state = api

            ta = asyncio.create_task(self._drain(a))
            tb = asyncio.create_task(self._drain(b))

                await asyncio.sleep(0.005)
```

##### I12. Shortcuts and alternatives explicitly rejected

**Verifying the dossier's own rejections:**

- **A lazy pump (start on first subscribe, stop on last unsubscribe).** The dossier rejects it for
  three reasons; all three check out. (i) It preserves the unbounded source growth while nobody is
  attached — the exact memory behaviour the eager pump removes. (ii) It adds start/stop races: with
  the *corrected* `_ensure_pump`, a stop-on-last-unsubscribe would have to cancel a task and then
  restart it against the *same* source, which reintroduces the identity problem I proved is real,
  now on a much hotter path (every tab close). (iii) The next attacher absorbs the whole backlog as
  a duplicate burst — up to 100k events on a long run (A5 measured a single run with 97,694 events),
  every one of which is then deduped away by `shouldApplyEvent`, i.e. pure waste. **Rejected.**
- **An eager pump with a bounded retention ring.** Re-introduces memory growth to do a job
  `run_events` already does correctly and durably, and creates a *second* replay source that can
  disagree with the durable log. **Rejected.**
- **Copying `websocket_handoff.py`'s `asyncio.Lock`.** Verified as actively harmful here, not merely
  unnecessary: `subscribe` would need `async with _LOCK`, which inserts an `await` between the
  liveness check and the set-add, destroying the no-preemption atomicity the whole race argument
  rests on. It buys nothing on a single-threaded event loop. **Rejected** — and I added a comment at
  the registry declaration saying so, because the next reader will otherwise "fix" the missing lock.
- **Merging the two subscriber registries.** Different key space (handoff token vs run id), different
  producer contract (`dispatch_event` is called directly; there is no shared source queue to own).
  A false unification. **Rejected.**

**Additional rejections I add:**

- **Hoisting `subscribe()` into the endpoint handler** (the obvious readable form). Proven wrong:
  `sse_starlette==3.0.2`'s `__call__` never calls `aclose()` on the body iterator except on
  send-timeout, and an aborted request means the generator body — and therefore the `finally` — never
  runs. Result: a permanently registered subscriber queue that the pump fills forever. **Rejected**,
  with the reason written into `_subscribed_sse_frames`'s docstring so it is not "cleaned up" later.
- **`_PUMPS: dict[str, asyncio.Task]` (the dossier's form).** Proven to break: the stale pump's
  `finally` tears down a re-registered run and the resumed client receives `[None]` and nothing else.
  Measured, both forms, side by side. **Rejected in favour of the `(task, source)` tuple.**
- **Draining only enough of an evicted subscriber's queue to fit the sentinel.** The natural reading
  of "drain with `get_nowait()` to make room". It is wrong: the client then consumes the remaining
  ~999 events, advances its high-water cursor past them, and the ONE dropped event sits permanently
  below the cursor — recreating exactly the unrecoverable hole the change exists to close.
  **Rejected in favour of draining the whole backlog.**
- **Making the mocked e2e `MockSse` consume-once so TS-SSE-RESILIENCE-04 tests the real property.**
  That is D1's decision and D1 already rejects it correctly: it would produce a permanently red test
  that no backend fix could turn green (the mock *is* the server in that suite), which is a worse lie
  than the current false green. **Rejected.**
- **Modifying `_iter_sse_frames` to take a subscriber factory instead of a queue.** Tempting (one
  function instead of two) and wrong: 28 existing tests drive `_iter_sse_frames` directly with a
  hand-built `asyncio.Queue`, and every one of them would need rewriting — turning a surgical fix
  into a test-suite rewrite and destroying the fail-before evidence those tests currently provide.
  **Rejected.**
- **Fixing it in the frontend** (e.g. electing one tab as the sole SSE consumer via a
  `BroadcastChannel` leader). It would leave the backend defect in place for every non-browser
  consumer, and it does not help the reopened-from-History case in the *same* tab. **Rejected.**
