##### I2. Register findings - prior art, locked decisions, collisions

**The line D5 must delete has a name: FIX-105.** `git blame` puts `run_commands.py:412` on commit
`bac1e556` (2026-07-23, *"feat(api): implement Run Again to resume cancelled pipeline [KAN-120]"*)
= **FIX-105** (`FIX-REGISTER.md:47`, detailed entry `:3316-3357`). Its root-cause #2 reads
verbatim:

> "when a run is cancelled then resumed in the **same process session**, the in-memory
> `StateMachine._states` dict has `"cancelled"` locked as terminal. `_execute_impl` subsequently
> calls `self._state_machine.transition(run_id, "generating")` which raises `StateMachineError:
> Cannot transition from terminal state 'cancelled'`. For failed runs resumed after a **restart**
> this never occurs (new process = empty dict), so it was never caught before."
> - `FIX-REGISTER.md:3325`

and its own safety argument (`:3356`):

> "The state machine pop is safe: DB status is already `"running"` (step 5) when the pop happens;
> the in-memory entry is an intra-process mirror written by the same process when it cancelled -
> clearing it is ownership-safe."

**This is the single most load-bearing register finding for D5**: FIX-105 already established, as a
shipped and reviewed decision, that (a) the post-terminal `_states` entry is a liability, not an
asset, and (b) clearing it is ownership-safe. It also proves the guard is *already absent* across a
restart, so the system is designed to work without it post-terminal.

**The guard's origin.** `git blame -L 84,98` puts the whole `TERMINAL_STATES` guard on `4889e3a8`
(2026-06-02) - the pre-milestone base commit. It was designed in as the Phase-2 lifecycle invariant
(`state_machine.py:3-4` "Phase 2: in-memory dict persistence"), **not** added to close a named bug.
Nothing in either register attributes a bug to it. What the registers *do* record is what it
protects, and one bug it caused:

  cancel/reject terminals on top of it.

##### I3. Root cause - confirmed, corrected, or replaced

**The dossier is right, and right for the right reason.** Re-derived independently:

1. `StateMachine._states` is a `dict[str, str]` on an object created once per process
   (`_MACHINE`, `state_machine.py:133-141`) and bound onto the engine singleton at
   `engine.py:812` (`self._state_machine = get_state_machine()`). Nothing ever replaces either
   singleton - grep for assignments to `_MACHINE` / `_state_machine` returns only those two
   construction sites.
2. `transition()` writes `self._states[run_id] = new_state` unconditionally
   (`state_machine.py:106`), for terminal states too. Confirmed by reading every one of the 18
   `self._state_machine.transition(...)` sites in `engine.py`: the terminal writes are `:2492`
   (`cancelled`), `:2305`/`:2371`/`:3145`/`:3240`/`:3289`/`:4135`/`:4268` (`cancelled` on the
   various cancel/reject paths), `:2523`/`:2556` (`failed`), `:2580` (`completed`).
3. There is no eviction anywhere except `run_commands.py:412`, which fires only on
   `POST /api/runs/{id}/resume` - a path most runs never take.
4. Therefore: **one entry per run, retained for the life of the process.**

**Measured cost (corrected).** 123.4 bytes/entry, 11.77 MB per 100,000 runs, on this runtime:

```console
$ python3.11 -c '...100k uuid4 keys...'
dict object growth for 100k entries: 3844800 bytes
sum of 100k uuid-str key objects: 8500000 bytes
total incl. keys: 12344800 bytes = 11.77 MB
per entry: 123.4 bytes
```

The dossier's 172 B / 17 MB is ~40% high. The severity conclusion is unchanged: this is slow,
bounded-by-uptime growth, not an incident. It is worth fixing because it shares a hook with D4
(which is genuinely large - `review_gate_ready` payloads average ~34 KB per gate) and because it
closes a real correctness *inconsistency*, described next.

**The part the dossier does not say, and it matters most.** The dossier frames D5 purely as memory.
The stronger justification is **behavioural consistency**: FIX-105 proved that the surviving
terminal entry makes the *same* user action behave differently depending on whether a restart
happened in between:

| Scenario | `_states[run_id]` at resume time | Result before FIX-105 |
|---|---|---|
| cancel -> resume, same process | `"cancelled"` | `StateMachineError`, resume broken |
| cancel -> restart -> resume | absent (new process) | works |

FIX-105 patched the *symptom* at one call site. D5 removes the divergence at the source: after the
terminal hook, the in-process state matches the post-restart state - which the system is already
designed and shipped to handle correctly.

**What the dossier gets slightly wrong.** *"It is also load-bearing - the guard at `:86-90` requires
the entry to persist during the run - so it cannot simply be dropped at transition time."* Correct
conclusion, imprecise premise. The guard is an **intra-`execute()`** invariant. Every one of its
readers is inside the generator:

```console

```
All twelve are inside `_execute_impl` / `_run_agent` / `_run_review_gate` /
`_run_spec_revision_sub_pipeline`. **There is no reader of `get_state` outside the engine, and no
reader at all after `execute()` returns.** That is what makes the driver's `finally` a provably
safe eviction point, and it is the precise ordering claim I5 pins.

**Causal chain, trigger to symptom:**
`POST /api/runs` (or any run start) -> `engine.execute()` -> first `transition()` writes
`_states[run_id]` -> ... -> terminal `transition()` overwrites it with `completed|failed|cancelled`
-> `execute()` returns -> driver `finally` pops `_PIPELINE_QUEUES` / `_PIPELINE_TASKS` /
`_CANCEL_EVENTS` but **not** `_states` -> the entry survives -> repeat N times -> ~123 B x N held
for the process lifetime, plus the FIX-105 same-session-resume divergence.

##### I5. The complete fix

Three edits, two files touched plus one deletion; **no engine edit, no migration, no config, no
frontend**.

**Step 1 - add the public eviction seam to the class that owns the state.**
File `backend/agents/execution_engine/state_machine.py`. Anchor: immediately after `get_state`
(currently ending `:64`), before `def transition` (`:66`).

BEFORE
```python
    def get_state(self, run_id: str) -> str | None:
        """Return the current state of a run, or None if unknown."""
        return self._states.get(run_id)

    def transition(self, run_id: str, new_state: str) -> str:
```

AFTER
```python
    def get_state(self, run_id: str) -> str | None:
        """Return the current state of a run, or None if unknown."""
        return self._states.get(run_id)

    def forget_run(self, run_id: str) -> None:
        """Evict a FINISHED run's in-memory lifecycle entry (D5).

        ``_states`` lives on a PROCESS-LIFETIME singleton and ``transition`` writes
        it on every transition INCLUDING the terminal one, so without an explicit
        eviction it grows monotonically for the life of the process (~123 bytes
        per run, measured).

        Call this ONLY from the single terminal hook
        ``app.api.run_engine._cleanup_pipeline``, which runs in the run driver's
        ``finally`` — i.e. strictly AFTER ``execute()`` recorded its terminal
        transition and after every in-run reader of ``get_state`` has run.
        Evicting while a run is LIVE would defeat the terminal-state guard in
        ``transition``: an already-cancelled run could then be re-transitioned to
        ``completed``, and ``_run_agent``'s ``StateMachineError`` arm
        (engine.py:4322) would stop firing.

        Post-eviction the in-process view matches the post-RESTART view (an empty
        dict), which every resume path is already designed for — see FIX-105.

        Idempotent and run-scoped: an unknown id is a no-op, no other run is
        touched. Pure ``dict.pop`` — it cannot raise, so the terminal hook needs
        no ``try/except`` around it.
        """
        self._states.pop(run_id, None)

    def transition(self, run_id: str, new_state: str) -> str:
```

*Why a method and not `._states.pop(...)` from the caller:* it closes the same private-dict reach
the project already fixed once (Phase 29 IN-02 -> Phase 49 `ArtifactStore.review_event_pending`),
and it gives D4 a symmetrical name (`ArtifactStore.forget_run`) so the shared hook reads as one
mechanism rather than two ad-hoc pokes.

**Step 2 - call it from the ONE terminal hook (the seam D4 shares).**
File `backend/app/api/run_engine.py`. Anchor: `def _cleanup_pipeline` at `:70`.

BEFORE
```python
def _cleanup_pipeline(pipeline_run_id: str) -> None:
    _PIPELINE_QUEUES.pop(pipeline_run_id, None)
    _PIPELINE_TASKS.pop(pipeline_run_id, None)
    _CANCEL_EVENTS.pop(pipeline_run_id, None)
```

AFTER
```python
def _cleanup_pipeline(pipeline_run_id: str) -> None:
    """The ONE terminal hook: drop every per-run entry this process holds.

    Reached from the run drivers' ``finally``
    (``run_commands._drive_launch_to_queue`` :2186 / ``_drive_revision_to_queue``
    :2489) and — via the ``_resume_cleanup`` callback injected at
    ``app/main.py:143`` — from every ``engine._fire_resume_cleanup`` exit path.
    It is therefore the single place that already knows "this run is over", which
    is why the per-run state held by the PROCESS-LIFETIME singletons is evicted
    here rather than by a TTL sweeper (D5; D4 adds the ``ArtifactStore`` sibling
    on the next line).

    ORDERING (load-bearing): every caller invokes this AFTER the run's event
    stream has been fully drained, so the state-machine entry has already been
    written by the terminal transition and read by every in-run reader
    (``engine.py`` reads ``get_state`` at 2303/2369/2540/3072/3143/3238/3287/
    4133/4266/4324/5015/5117 — all inside ``execute()``). Do NOT move this call
    earlier, and do NOT evict from inside the engine: the terminal-state guard in
    ``StateMachine.transition`` must keep protecting the LIVE run.

    Every operation is a pure ``pop`` — this hook cannot raise, so it can never
    mask a run's outcome from the ``finally`` it runs in.
    """
```

##### I6. Ripple-effect analysis - why nothing else breaks

Assuming the fix is wrong, here is where it would show.

**"You removed a safety net."** The terminal guard stops protecting a *finished* run. Three reasons
that is not a loss: (i) it already does not protect a finished run after a restart - the dict is
empty - and every resume path is built for that (FIX-105's own words); (ii) the two things it could
have accidentally blocked are already blocked by stronger, DB-and-registry-backed guards (I5,
grounds 2 and 3); (iii) it keeps protecting the LIVE run in full, which is the only place any
reader exists. The one behaviour that genuinely changes: a second `execute()` on an
*already-completed* run id in the same process would now start a fresh lifecycle instead of
raising. No production path can do that (the only re-entry is `POST /resume`, gated on DB status),
and no test does it either - the three harnesses that could, deliberately mint unique ids
(I4(i)).

**Concurrency and ordering.** `_cleanup_pipeline` is synchronous with no `await`, so on the single
event loop it is atomic against every other coroutine: no run can observe a half-cleaned state. It
is keyed on `pipeline_run_id`, so two concurrent runs never touch each other's entry (asserted by
the new `test_forget_run_is_idempotent_and_run_scoped`). The eviction happens *inside* the same
synchronous block that drops `_PIPELINE_TASKS`, so there is no window in which the resume mutex is
open while the stale terminal state is still present - the FIX-105 hazard is closed at the same
instant it becomes reachable.

**Startup / shutdown (D8, D9).** On startup `restore_non_terminal_runs` runs against an empty
`_states`, so every early-bail `_fire_resume_cleanup` is a no-op. On shutdown the lifespan does
nothing today (D8) - abandoned tasks may never reach their `finally`, so entries can survive an
unclean stop; but the process is exiting, so the memory goes with it. If D8 later cancels
`_PIPELINE_TASKS` and awaits them, those `finally` blocks will run and evict properly - D5 composes
with D8 rather than conflicting.

**Unattached client / slow client / crashed run.** The SSE layer never reads `_states`
(`grep _states run_stream.py` = 0); liveness is `workflow_id in _PIPELINE_QUEUES`. A slow or absent
client cannot delay the eviction, because the driver's `finally` does not wait on the consumer - it
enqueues the `None` sentinel and cleans up.

**Restart.** Unchanged: the dict starts empty either way; the DB `workflow_runs.status` (written by
`_persist`, untouched here) remains the cross-restart source of truth that
`restore_non_terminal_runs` and the resume eligibility check read.

**Resume - the risk the brief singles out.** Traced, one path at a time, for a run that reached
terminal and had its entry cleared:
- *(a) user hits `POST /api/runs/{id}/resume`.* Step 1 owner gate (DB), step 2 eligibility (DB
  `status`), step 3 overlap mutex (`_PIPELINE_TASKS`/`_PIPELINE_QUEUES`), steps 4-5 register + flip,
  step 7 spawn. **None reads `_states`.** Then `resume_run -> _drive_resumed_stream ->
  _execute_impl` calls `transition(run_id, "generating")` against an absent entry -> succeeds. This
  is exactly what FIX-105's pop bought, now bought earlier and once.
- *(b) a revision run is launched from it.* `POST /api/runs/{id}/revisions` mints a NEW child
  `workflow_run_id` (`_mint_revision_row`) and `_handle_revision` dispatches
  `self.execute(pipeline_run_id=<the child id>)`. Different key space; the parent's absent entry is
  irrelevant. **Absence handled: N/A, never read.**
- *(c) `restore_non_terminal_runs` picks it up after a restart.* It selects on
  `WorkflowRun.status in NON_TERMINAL` from the DB and never consults `_states`; branch (c) writes
  `wr.status = "failed"` directly on the row without a `transition`. In a fresh process the dict is
  empty regardless. **Absence handled: it is the normal case.**
- *(d) a stale SSE client re-attaches.* `run_stream.stream_run_events` does the two-layer owner
  check, replays from `run_events`, and decides liveness from `_PIPELINE_QUEUES`. **Absence handled:
  `_states` is never consulted on this path.**

**Alias-related resume bugs (BUG-R01/R02 era) - do they touch this?** Checked, and the answer is
**no**, but the check is worth recording because the failure shape looks adjacent. BUG-R01/R02
(quick `260719-ghn`, commit `e1866317`) were `get_pipeline_agents(wr.type)` called on the raw
`od_prototype` alias without `resolve_alias`, so both re-arm drivers hit the "empty agent list" bail

contact with D5 is that those early-bail paths call `_fire_resume_cleanup` -> `_cleanup_pipeline`,
and D5 makes that call additionally evict a `_states` entry that provably does not exist at that
point (startup = empty dict; user-resume = nothing written yet). Verified by reading `resume_run`
`:7511-7605` and `_replay_clarify_run` `:7864-7956`: every bail precedes `_drive_resumed_stream`.

**Fan-out / wave runs.** `run_fanout` spawns workers as `subagent_runs` rows, never as
`workflow_runs`, and workers never call `transition` - the state machine sees only the parent run
id. Unaffected.

**Two browsers.** Both attach to the same `_PIPELINE_QUEUES` entry; neither reads `_states`.
Unaffected (that is A2's problem, not this one).

**Memory and connection pool.** The change frees memory and allocates none. It opens no DB session

##### I12. Shortcuts and alternatives explicitly rejected

1. **Clear inside the engine, right after the terminal `transition()`** (the obvious "fix it where
   the state is written"). **Rejected - it breaks 13 existing tests and the golden harness.**
   `tests/unit/test_pipeline_failure_semantics.py:171/199/223/309`,
   `tests/agents/test_engine_runner_error_arm.py:166/208/399/425/563`,
   `test_declared_gate_streaming.py:495` and `test_model_fallback.py:369` all assert
   `engine._state_machine.get_state(run_id) == "<terminal>"` immediately after `execute()` returns;
   an engine-side clear makes every one of them read `None`. Worse, it silently changes the
   characterization harness contract: `_scripted_model.py:620-621` mints unique run ids *because*
   entries persist, and an engine-side clear would make run-id reuse suddenly legal, weakening the
   harness's own isolation without anyone noticing. The app-layer hook keeps both properties.

2. **Clear inside `StateMachine.transition` when `new_state in TERMINAL_STATES`.** **Rejected -
   it deletes the guard.** `transition` reads `self._states.get(run_id)` on entry (`:85`); if the
   terminal write immediately popped the key, a second terminal transition would see `current is
   None` and succeed, and `engine.py:4322-4327`'s `StateMachineError` arm (which *uses* the raise as
   the signal to stop the agent loop after a cancel) would never fire - a live run could keep
   dispatching agents after the user cancelled it. This is the exact regression the brief warns
   about.

3. **A TTL sweeper / periodic janitor over `_states`.** **Rejected - the lifecycle is known
   exactly.** D4's own text rejects it for the same reason (`:1589`). A sweeper adds a timer, a
   tunable, and a window in which a *live* long run (prototype builds run 20-40 minutes) could be
   swept mid-flight, re-opening rejection 2's failure. The terminal hook is deterministic and free.

4. **Bound `_states` with an `OrderedDict` / LRU cap.** **Rejected - it evicts by age, not by
   lifecycle.** Under concurrent load the oldest entry can be a *live* long-running build while the
   newest are finished quick runs; an LRU would evict the live one and re-open rejection 2. It also
   adds a capacity knob nobody can size honestly.

5. **Leave `run_commands.py:412` in place alongside the new hook** ("belt and braces"). **Rejected -
   INV-12, and it keeps a real defect alive.** Two eviction mechanisms for one concern is exactly
   what the project bans, it preserves the private-dict reach the Phase-29 IN-02 / Phase-49
   `review_event_pending` precedent already closed once, and it leaves the four
   `test_rest_resume.py` `AttributeError` reds red for no benefit.

6. **Fix the reds by giving `_StubEngine` a `_state_machine`.** **Rejected - it papers over the
   design smell.** Adding a fake attribute to a test stub so the app layer can keep reaching into
   another class's private dict is the definition of adapting the test to the code. Deleting the
   reach fixes both.

7. **Also cover `ndjson_adapter.run_od_prototype_pipeline` with an injected cleanup callback.**
   **Rejected as out-of-lane and not worth it.** It is kernel-side and may not import `app.api`, so
   covering it means a fourth injected callback and a `main.py` wiring line - for an endpoint with
   zero frontend callers (verified: `grep -rn "prototype/run" frontend/src frontend/e2e` = no
   output). Documented as a residual in I4(k); the right fix is to retire the dead endpoint, which
   is separate work.

8. **Wrap the new call in `try/except`.** **Rejected as noise.** `get_state_machine()` is a lazy
   global read and `forget_run` is a `dict.pop` - neither can raise, and the three `pop`s already in
   `_cleanup_pipeline` are unguarded. Adding a guard would also force a new `logging` import into a
   module that currently has none. The docstring records the condition under which a future
   forgetter *must* add one.
