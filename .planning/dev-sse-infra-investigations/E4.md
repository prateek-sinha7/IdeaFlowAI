**Fact 1 - `logs:DescribeLogGroups` does not support resource-level permissions.** [V]

Source: AWS's own machine-readable Service Reference (the feed AWS publishes precisely so tools can
determine resource-level support), fetched 2026-07-30 from
`https://servicereference.us-east-1.amazonaws.com/v1/logs/logs.json` (89,158 bytes):

```json
{
 "Name": "DescribeLogGroups",
 "Annotations": { "Properties": { "IsList": true, "IsWrite": false, ... } },
 "SupportedBy": { "IAM Access Analyzer Policy Generation": true, "IAM Action Last Accessed": true }
}
```

There is **no `Resources` key**. Contrast its three siblings in the same feed, which all have one:

| Action | `Resources` in the AWS feed | Meaning |
|---|---|---|
| `logs:DescribeLogGroups` | *(absent)* | No resource type -> only `Resource: "*"` can ever match |
| `logs:DescribeLogStreams` | `[{ "Name": "log-group" }]` | Scopable to a log-group ARN |
| `logs:CreateLogStream` | `[{ "Name": "log-stream" }]` | Scopable to a log-**stream** ARN |
| `logs:PutLogEvents` | `[{ "Name": "log-stream" }]` | Scopable to a log-**stream** ARN |

ARN formats from the same feed:

```
log-group  : arn:${Partition}:logs:${Region}:${Account}:log-group:${LogGroupName}
log-stream : arn:${Partition}:logs:${Region}:${Account}:log-group:${LogGroupName}:log-stream:${LogStreamName}
```

Two corroborating sources agree:

- The AWS managed policy `CloudWatchAgentServerPolicy` (v3, edited 2024-02-06) puts
  `logs:DescribeLogGroups` - together with `PutLogEvents`, `PutRetentionPolicy`,
  `DescribeLogStreams`, `CreateLogStream`, `CreateLogGroup`, `cloudwatch:PutMetricData`,
  `ec2:DescribeVolumes`, `ec2:DescribeTags` - in a single statement with `"Resource" : "*"`.
- AWS's own CloudWatch Logs IAM guidance treats `DescribeLogGroups` as the exception that must use
  `Resource: "*"` while `CreateLogStream`/`GetLogEvents` etc. can be ARN-scoped.

**Therefore the statement at `cloudwatch-write.json:14-21` grants nothing.** IAM does not error on
it: the policy is syntactically valid, `aws iam put-role-policy` accepts it, Terraform applies it,
and it simply never matches an authorization request. It is a silent no-op. [V]

###### I4.5 Multi-environment scope — exactly what a dev apply changes

The template is shared; **the apply is not.** Three independent scoping mechanisms, all read
directly:

1. **Rendering is per-env by variable.** `${environment}` in the template is fed by
   `module.iam.environment = var.environment` (`foundation/main.tf:87`), and `var.environment` comes
   from `-var-file="${ENVIRONMENT}.tfvars"`. `foundation/dev.tfvars:12` is `environment = "dev"`.
2. **State is per-env.** `buildspec.yml:152-158`:
   `-backend-config="key=velocityai/${ENVIRONMENT}/foundation.tfstate"`. A dev build initialises
   against `velocityai/dev/foundation.tfstate` and can only plan/apply resources recorded there.
3. **Resource names are per-env.** `foundation/locals.tf:5-6`:
   `name_suffix = var.environment == "prod" ? "" : "-${var.environment}"`,
   `name_prefix = "velocityai${local.name_suffix}"`. The dev apply's only IAM target is the role
   `velocityai-dev-instance` and the inline policy `velocityai-dev-cloudwatch-write`. The stage and
   prod roles (`velocityai-stage-instance`, `velocityai-instance`) are not in dev's state file and
   are therefore not addressable by a dev plan.

**Proof that no stage/prod resource moves:** a dev `foundation apply` produces exactly one change:

```
# module.iam.aws_iam_role_policy.cloudwatch_write will be updated in-place
~ resource "aws_iam_role_policy" "cloudwatch_write" {
      id     = "velocityai-dev-instance:velocityai-dev-cloudwatch-write"
      name   = "velocityai-dev-cloudwatch-write"
    ~ policy = jsonencode({...}) -> jsonencode({...})
  }

Plan: 0 to add, 1 to change, 0 to destroy.
```

`[I]` on the literal plan text (credentials expired); `[V]` on the reasoning - the diff touches one
file, whose only deployed consumer is `module.iam`, whose only IAM write for this file is the
`cloudwatch_write` resource, and dev's state contains only dev's copy of it.

**Two guards make this belt-and-braces** [V]: `module.account_guard` aborts plan/apply on an
account mismatch (`foundation/variables.tf:9-16`, `expected_account_id` passed from
`aws sts get-caller-identity` at `buildspec.yml:143`); and each env has its own CodeBuild project
`velocityai-gitlab-runner-<branch>` (`bootstrap/cicd.tf:64`) triggered by its own branch.

**Timing note the executor must internalise:** the *file* is shared, so the moment the commit is on
`dev`, a subsequent `stage` or `prod` build will render the new policy for that environment too.
That is not a dev apply leaking - it is the normal promotion path, and it is desirable (the same
no-op exists in all three). But it means **"dev only" is true of the apply, not of the source
tree**, and the executor must say so on the PR rather than claiming the other environments are
untouched forever.

###### I4.6 The security consequence of `Resource: "*"` on this action

This is the question that decides delete-vs-widen, so I answer it concretely.

**Are dev, stage and prod in the same AWS account?** **Yes** [V], from the repo's own words:

- `infra/terraform/bootstrap/cicd.tf:33` - "isolation requires separate AWS accounts."
- `:57` - "needs separate accounts (see the isolation note above / README)."
- `:170` - "radius in a single account."
- `:244` - "the residual shared blast radius in a single account."
- All three CodeBuild runners are created by one `bootstrap/cicd.tf` under one
  `data.aws_caller_identity.current.account_id`; no tfvars pins a per-env account; the tfstate
  bucket, lock table and CMK are shared (dossier Appendix 2). Dossier header: account
  `577954642302`, region `eu-central-1`, single-region by design (`.checkov.yaml`: "single-region
  project").

**So `Resource: "*"` would let the dev EC2 instance role enumerate every log group in
`577954642302` / `eu-central-1`, which is every log group the project has:**

| Group family | Source | Count |
|---|---|---|
| `/velocityai/dev/{nginx-access,nginx-error,app,postgres,system,auth,letsencrypt}` | `modules/monitoring/main.tf:15-23` | 7 |
| `/velocityai/stage/...` and `/velocityai/prod/...` (same 7 each) | same module, other envs | 14 |
| `/velocityai/{dev,stage,prod}/cloudtrail-audit` | `modules/monitoring/main.tf:1004-1005` | 3 |
| `/aws/codebuild/velocityai-gitlab-runner-{dev,stage,prod}` | `bootstrap/cicd.tf:326-328` | 3 |
| VPC flow-log groups | `modules/network/main.tf:432` | 3 |

**What is actually exposed:** `DescribeLogGroups` returns metadata only - `logGroupName`, `arn`,
`creationTime`, `retentionInDays`, `metricFilterCount`, `storedBytes`, `kmsKeyId`,
`dataProtectionStatus`, `logGroupClass`. **No log content.** And the instance role holds **zero**
log-read actions:

```
$ grep -rn 'GetLogEvents\|FilterLogEvents\|StartQuery\|GetQueryResults\|GetLogRecord' infra/terraform/
(no matches)
```

So the realistic harm is reconnaissance, not exfiltration: an attacker with the instance credential
learns that stage and prod exist, their naming scheme, that a CloudTrail audit group exists, how
much each stores, and which CMK encrypts them. It is a meaningful step in a chain (it tells you
where to aim the next privilege) and it crosses an environment boundary the whole design is built
to hold - but it is not, by itself, a data breach.

**Can a condition narrow it?** **Essentially no, here.** [V] From the same AWS feed,
`DescribeLogGroups` has **no `ActionConditionKeys`**, and the service-wide condition keys
(`aws:RequestTag/*`, `aws:ResourceTag/*`, `aws:TagKeys`, `logs:DeliveryDestinationResourceArn`,
`logs:LogGeneratingResourceArns`, `logs:data_source_name`, `logs:data_source_type`) do not apply to
a list operation with no resource. The only lever left is the global `aws:RequestedRegion` - and in
a **single-region** project where dev, stage and prod all live in `eu-central-1`, that condition
does not separate anything. It still blocks cross-region replay of a stolen credential (the reason
`modules/iam/main.tf:154-156` uses it), which is real but orthogonal.

**Is that acceptable for this instance role? No - and this is the decisive argument.** The role
belongs to an internet-facing host (`https://63-181-129-187.nip.io`, port 443 open to the world,
`CKV_AWS_260` accepted for 0.0.0.0/0 on port 80) that executes user-supplied natural-language
prompts through an LLM with a code-execution capability layer in-tree (currently gated OFF -
`CLAUDE.md`: `exec`/`network`/`secrets`/`spawn_subagents` default OFF). The threat model that
justifies scoping `logs:PutLogEvents` to `/velocityai/dev/*` at all is exactly the threat model
that argues against handing the same principal account-wide, cross-environment log-group
enumeration. **Accepting that exposure would be defensible if the grant bought something. It buys
nothing** - the action is never called. Paying a real (if modest) confidentiality cost for a
provably zero functional benefit is not a trade a least-privilege policy should make.

##### I6. Ripple-effect analysis — assume the fix is wrong and hunt for the failure

**Hypothesis 1: something else in the account or on the box uses `logs:DescribeLogGroups` via this
role, and deletion breaks it.**

Everything running on the instance under this role, enumerated: the CloudWatch agent (analysed
exhaustively in I3 - never calls it here); the backend/frontend containers (they call Bedrock, SSM,
S3 and KMS - `grep -rn 'DescribeLogGroups\|describe_log_groups' backend/ frontend/` returns
nothing); `velocityai-pg-dump` and `velocityai-skills-backup` (S3 + KMS only); and
`velocityai-stuck-workflows-check` (`bootstrap-ec2.sh:1105-1106`, `cloudwatch put-metric-data` -
covered by the `cwagent-describe` policy, not this one). **Nothing breaks.**

**Hypothesis 2: some future code path silently loses a permission and fails opaquely.**

The only realistic one is the retention path, and it is *already* broken today: if someone adds
`retention_in_days` to a `collect_list` entry, the agent will start calling `DescribeLogGroups`
**and** `PutRetentionPolicy`, and the role has neither - so it fails identically before and after
this change. Deletion does not create that hazard, it inherits it. Three mitigations are in place:
(a) the Step-2 comment names the exact precondition; (b) B3's fix ships a machine guard that
**fails the build** if any `collect_list` entry sets `retention_in_days` (`B3.md:542-543`); (c) B4's
fix ships the agent's own log to CloudWatch, so an `AccessDenied` would be visible within minutes
instead of invisible for a month.

**Hypothesis 3: the deletion is wrong because the agent version on the box differs from `main`.**

Real risk, honestly stated. `bootstrap-ec2.sh:941-945` installs from
`.../ubuntu/amd64/latest/amazon-cloudwatch-agent.deb`, so the box has whatever was latest around
2026-07-01; I read `main` at 1.300071.0 (2026-07-22). Two things bound the risk:

- The `Retention > 0` gate is not new. `RELEASE_NOTES` shows the retention feature landing long ago
  ("Support log retention policy when writing or creating a log group (#250)") and the
  `DescribeLogGroups`-before-`PutRetentionPolicy` optimisation arriving in **1.300053.0
  (2025-02-26)** ("Reduce PutRetentionPolicy calls by checking existing policy"). An agent *older*
  than that has **fewer** `DescribeLogGroups` call sites, not more - it would go straight to
  `PutRetentionPolicy`, still gated on retention. Either way, with no retention configured, neither
  fires.
- The failure mode if I am wrong is benign and self-announcing: an `AccessDenied` line in
  `/var/log/amazon-cloudwatch-agent.log`, shipped to CloudWatch by B4, on a code path whose only
  purpose is to *reconcile a retention value Terraform already owns*. Log delivery itself is
  untouched (`CreateLogStream` + `PutLogEvents` are the delivery path and are unchanged).

**Hypothesis 4: the apply has a blast radius I have not seen.**

- *Does the role get replaced?* No - `aws_iam_role_policy` body change is an in-place update on a
  child resource. The role's `prevent_destroy` (`:40`) is not engaged.
- *Does the instance restart?* No. IAM inline-policy updates propagate to the instance's credential
  session without any instance action, typically within seconds. No `user_data` change, so
  `ignore_changes` / `user_data_replace_on_change = false` (`modules/compute/main.tf:81,134-151`)
  never come into play.
- *Does the exclusive-policy list drift?* No - name unchanged. (If an executor deviates and adds a
  new `aws_iam_role_policy` resource instead, the very next apply **deletes it** unless
  `modules/iam/main.tf:228-237` is amended. Do not deviate.)
- *Partial application?* A `foundation apply` that fails mid-run leaves either the old or the new
  policy body, never a half-written one - `PutRolePolicy` is a single atomic API call. There is no
  intermediate state in which the agent has *fewer* permissions than it needs, because it needs none
  of the removed one.
- *Concurrency / ordering?* None. There is no queue, no event loop, no client, no run. This is a
  one-shot control-plane write with no relationship to SSE streams, run state, resume, fan-out,
  revisions, gates, or anything an unattached/slow client or a second browser could observe. All of
  the AGENT-BRIEF's §I6 concurrency prompts are structurally inapplicable, and saying so is more
  honest than inventing scenarios.

**Hypothesis 5: CI rejects the change.**

Addressed empirically in I4.4 rather than by prediction: the tree already carries two

```python
#!/usr/bin/env python3.11
"""Assert no instance-role policy scopes an action to a resource ARN when the
action does not support resource-level permissions (such a statement is a
silent no-op that IAM accepts and never matches).

Ground truth is AWS's published machine-readable Service Reference:
    https://servicereference.us-east-1.amazonaws.com/v1/<svc>/<svc>.json
An action entry with no "Resources" key supports no resource type and can only
be granted with Resource "*".

This is the check that would have caught E4 (logs:DescribeLogGroups scoped to
arn:...:log-group:/velocityai/<env>/*) at authoring time.

Run:  python3.11 infra/terraform/policies/policy_resource_support_test.py
Exit: 0 = clean, 1 = at least one no-op statement.
"""
from __future__ import annotations

import json
import pathlib
import re
import sys
import urllib.request

HERE = pathlib.Path(__file__).resolve().parent
IAM_MAIN = HERE.parent / "modules" / "iam" / "main.tf"
REF = "https://servicereference.us-east-1.amazonaws.com/v1/{svc}/{svc}.json"

# templatefile() substitutions; values are irrelevant to the check, only shape.
SUBS = {
    "partition": "aws",
    "region": "eu-central-1",
    "account_id": "000000000000",
    "environment": "dev",
    "model_id": "MODEL",
    "inference_profile_id": "PROFILE",
    "kms_key_arn": "arn:aws:kms:eu-central-1:000000000000:key/K",
    "bucket_arn": "arn:aws:s3:::bucket",
    "name_prefix": "velocityai-dev",
}

# IAM service prefix -> Service Reference slug (they differ for CloudWatch).
SLUG = {"cloudwatch": "cloudwatch", "logs": "logs", "ec2": "ec2",
        "bedrock": "bedrock", "ssm": "ssm", "kms": "kms", "s3": "s3", "ecr": "ecr"}

_cache: dict[str, dict | None] = {}


def actions(svc: str) -> dict | None:
    if svc not in _cache:
        slug = SLUG.get(svc)
        if slug is None:
            _cache[svc] = None
        else:
            with urllib.request.urlopen(REF.format(svc=slug), timeout=60) as r:
                doc = json.load(r)
            _cache[svc] = {a["Name"]: a for a in doc["Actions"]}
    return _cache[svc]


def render(text: str) -> str:
    for k, v in SUBS.items():
        text = text.replace("${%s}" % k, v)
    return text


def audit(label: str, doc: dict, failures: list[str], unknown: list[str]) -> None:
    for st in doc["Statement"]:
        acts = st["Action"]
        acts = [acts] if isinstance(acts, str) else acts
        res = st.get("Resource")
        res = [res] if isinstance(res, str) else res
        wildcard_only = res == ["*"]
        for act in acts:
            svc, _, name = act.partition(":")
            table = actions(svc)
            if table is None or name not in table:
                unknown.append(f"{label} [{st.get('Sid','')}] {act}: not in Service Reference")
                continue
            supports_resource = "Resources" in table[name]
            if not supports_resource and not wildcard_only:
                failures.append(
                    f'{label} [{st.get("Sid","")}] {act}: action supports NO resource type '
                    f'but is scoped to {res[0]!r} -> statement is a silent no-op. '
                    f'Either grant it on Resource "*" (with a narrowing Condition if the '
                    f'action supports one) or remove it.'
                )


def main() -> int:
    failures: list[str] = []
    unknown: list[str] = []

    for path in sorted(HERE.glob("*.json")):
        audit(path.name, json.loads(render(path.read_text())), failures, unknown)

    # The one inline (HCL) policy document on the same role. Parsed structurally
    # so the check cannot silently stop covering it.
    hcl = IAM_MAIN.read_text()
    block = re.search(
        r'data\s+"aws_iam_policy_document"\s+"cw_agent_describes"\s*\{(.*?)\n\}',
        hcl, re.S)
    assert block, "cw_agent_describes block not found in modules/iam/main.tf"
    body = block.group(1)
    inline_actions = re.findall(r'"([a-z0-9-]+:[A-Za-z]+)"', body)
    assert inline_actions, "no actions parsed from cw_agent_describes"
    inline_resources = re.search(r'resources\s*=\s*\[(.*?)\]', body, re.S).group(1)
    audit("modules/iam/main.tf::cw_agent_describes",
          {"Statement": [{"Sid": "CloudWatchAgentMetricPut",
                          "Action": inline_actions,
                          "Resource": ["*"] if '"*"' in inline_resources else ["ARN"]}]},
          failures, unknown)

    for u in unknown:
        print("NOTE:", u)
    for f in failures:
        print("FAIL:", f)
    print(f"\n{len(failures)} no-op statement(s) found.")
    return 1 if failures else 0


if __name__ == "__main__":
    sys.exit(main())
```

`VelocityAI/Backups`. Doing it before E2 and E3 land would break both. **Do not fold a namespace
condition into E4.** Named here because E4 is the issue that surfaces the fact.

**vs Cluster A (A1-A5) and Cluster D - zero interaction.** Different subsystem entirely (SSE

**Commit boundaries.** **One commit.** The change is two files, one logical unit (remove the no-op +

##### I11. Open questions requiring a human decision

**Q1 — Delete or widen? (the only decision this fix needs)**

- **Option A, delete** *(recommended)*. The action is provably never called
  (`pusher/target.go:79` gate + `logfile/fileconfig.go:155-156` default + no `retention_in_days`
  anywhere in the `collect_list`), so the grant is pure cost. Widening it to `Resource: "*"` hands
  an internet-facing instance role the ability to enumerate every log group in account
  `577954642302` / `eu-central-1` - including `/velocityai/stage/*`, `/velocityai/prod/*`, all three
  `cloudtrail-audit` groups, the CodeBuild runner groups and the VPC flow-log groups - and **no
  condition key can narrow it** (no `ActionConditionKeys`; `aws:RequestedRegion` does not separate
  environments in a single-region project).
- **Option B, widen with `aws:RequestedRegion`**. Correct if the reviewer's priority is "the policy
  should describe the agent's documented permission set even where unused" (that is, after all, what
  AWS's own `CloudWatchAgentServerPolicy` does). Costs the exposure above; buys nothing functional
  today; makes a future `retention_in_days` addition one grant closer to working (though it would
  still need `logs:PutRetentionPolicy`, also on `Resource: "*"`).
- **My recommendation: A.** The deciding argument is not preference, it is that the exposure is
  unnarrowable and the benefit is provably zero. If the team is uncomfortable with deletion, A plus
  B3's build-failing `retention_in_days` guard plus B4's agent-log shipping is a strictly better
  package than B alone, because it makes the *absence* of the grant loud rather than silent.

**Q2 — Should the T2 policy-audit script become a CI gate?** *(a real decision, not a deferral)*
Wiring it into `buildspec.yml` closes the defect class permanently at the cost of a build-time
dependency on `servicereference.us-east-1.amazonaws.com`. The alternative is a committed snapshot of
the eight service-reference feeds (about 1.5 MB, refreshed on demand), which removes the network
dependency but adds a file that will drift. **Recommendation: land the script now as a runnable
check; wire it into CI in a separate commit with the committed snapshot**, so the security fix is
not blocked on a CI-policy discussion.

**Q3 — `cloudwatch:PutMetricData` namespace hardening.** Not part of E4; logged so it is not lost.
The instance role grants `PutMetricData` on `Resource: "*"` with only a region condition
(`modules/iam/main.tf:157-174`). AWS's feed shows a `cloudwatch:namespace` action condition key, so
it can be narrowed to the namespaces actually in use. **Gated on E2 and E3 landing first** (I10),
because today three different namespaces are or will be published from this host. Someone should own
this as its own task after E2/E3.

Nothing else. I am not inventing decisions to defer.

##### I12. Shortcuts and alternatives explicitly rejected

1. **"Just do what the dossier says: move it into its own statement with `Resource: "*"`."**
   Rejected as the *default*. Two concrete problems. (a) It is already its own statement
   (`cloudwatch-write.json:14-21`, `Sid: DescribeLogGroups`), so "move" describes an edit that does
   not exist - an executor following it literally would either no-op or invent a restructure. (b)
   Widening trades a harmless no-op for account-wide cross-environment log-group enumeration by an
   internet-facing role, to enable a call path that is provably unreachable. The failure it causes
   is not a crash - it is a permanent, unnarrowable, unnecessary widening of a security boundary the
   rest of this module works hard to hold. Retained as Option B only because the reviewer may
   legitimately prefer policy-describes-the-agent over strict least privilege.

2. **Add `logs:DescribeLogGroups` to the existing `cw_agent_describes` HCL block
   (`modules/iam/main.tf:157-174`) instead of touching the JSON.** Superficially attractive - that
   block is literally the file's home for "actions that cannot be scoped by Resource", and it
   already carries the right condition. Rejected because it splits CloudWatch **Logs** permissions
   across two policies (`cloudwatch-write` and `cwagent-describe`), so a future auditor reading
   `velocityai-dev-cloudwatch-write` no longer sees the whole logs story. It also changes a *second*
   policy for no functional gain. If Option B is chosen, keep it in the JSON where the other `logs:`
   actions live.

3. **Create a new `aws_iam_role_policy` resource for the wildcard action.** Rejected, and this one
   is actively dangerous: `aws_iam_role_policies_exclusive.instance` (`modules/iam/main.tf:226-238`)
   is a sealed set of policy names, and the file's own comment warns that "anyone adding a new
   `aws_iam_role_policy.X` to this module MUST add its name to the inline list below or apply will
   silently delete it." The concrete failure: the first apply creates the policy, the *same* apply's
   exclusive-list reconciliation deletes it, and the executor sees a green apply with the fix
   missing. Even done correctly it adds a fourth CloudWatch-related policy to a role that already
   has two.

4. **Attach the AWS managed `CloudWatchAgentServerPolicy` and delete the bespoke ones.** Rejected.
   It grants `logs:CreateLogGroup`, `logs:PutRetentionPolicy` and five `xray:*` actions the project
   does not use, all on `Resource: "*"` - it would *unscope* `PutLogEvents` and `CreateLogStream`,
   which are currently correctly confined to `/velocityai/<env>/*`. That is a large real regression
   traded for tidiness. It would also require adding the ARN to
   `aws_iam_role_policy_attachments_exclusive.instance` (`:240-250`), whose comment documents the
   same silent-deletion hazard as #3.

5. **Set `retention_in_days` in the `collect_list` so the action becomes genuinely needed, then
   grant it.** Rejected on three independent grounds: Terraform already owns retention
   (`modules/monitoring/main.tf:44` with per-group overrides), so this creates two writers for one
   value; the role has no `logs:PutRetentionPolicy`, so the agent would call `DescribeLogGroups`,
   discover a mismatch, attempt `PutRetentionPolicy` and fail with `AccessDenied` every five seconds
   (`target.go:180` ticker); and B3 is independently shipping a build-failing guard against exactly
   this config (`B3.md:542-543`). Manufacturing a need for a permission is the wrong direction.

6. **While in the file, also remove `logs:DescribeLogStreams` (also unused by the modern agent).**
   Tempting and correct-in-principle - the tree-wide grep found zero production call sites, and the
   agent's own service interface (`internal/pusher/sender.go:17-24`) does not declare it. Rejected
   for this change: it is correctly scoped to a resource type it genuinely supports, so it is not
   the E4 defect class; the older agent versions that may be installed on the box *did* call it (it
   was the sequence-token path); and removing it would mean this commit both fixes a defect and
   prunes an unrelated grant, so a bisect could not tell which caused a regression. Log it as its
   own low-priority task if the team wants it.

7. **Grant `logs:CreateLogGroup` "for safety" while in the file.** Rejected. Terraform pre-creates
   all seven groups with `prevent_destroy` (`modules/monitoring/main.tf:15-23`, `:37+`), so
   `CreateLogStream` never returns `ResourceNotFoundException` and the agent never reaches its
   `createLogGroup` branch (`target.go:108-109`). Granting it would let the instance role create
   arbitrary `/velocityai/<env>/*` groups outside Terraform's control - real drift, in exchange for
   a path that cannot execute. (The genuine latent risk here - that a *new* `collect_list`
   destination with no matching Terraform group would silently never ship - is a `bootstrap-ec2.sh`
   / `monitoring` consistency concern, not an IAM one, and belongs with B3/B4.)

8. **Verify with the dossier's own step: "after B1, confirm no `AccessDenied` on
   `DescribeLogGroups`."** Rejected as the verification. It is vacuous: the call never happens, so
   "no AccessDenied" is true on the broken tree, true after Option A, and true after Option B. A
   test that passes in all three states tests nothing. I8/T4 replaces it with the discriminating
   assertions - **zero `DescribeLogGroups` events** in the agent log and **zero** matching CloudTrail
   events for the role - which are the only observations that could falsify this investigation.

9. **Skip the code comment; the commit message records the reasoning.** Rejected. This defect was
   authored by someone who had written the correct rule down 45 lines away in the same file
   (`modules/iam/main.tf:151-156`) and still missed it in a sibling file. A commit message is not
   read by the next person editing the policy; a comment above the resource is. The specific failure
   this prevents is a future least-privilege sweep noticing a "missing" `DescribeLogGroups` and
   re-adding it ARN-scoped - reintroducing the exact no-op.

10. **Run the backend pytest suite / `lint-imports` / the goldens to "verify" the change.**
    Rejected. The diff contains zero Python and zero TypeScript bytes, so those suites cannot
    observe it; and their baselines on `dev` are already red (goldens 10 failed / 6 passed,
    `lint-imports` 1 broken contract). Running them would either produce theatre-green or invite
    someone to read a pre-existing red as this change's regression. The right gates are
    `terraform validate`, the T2 policy audit, and the T3 IAM simulation.
