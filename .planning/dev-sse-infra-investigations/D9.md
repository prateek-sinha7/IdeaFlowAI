##### I3. Root cause — confirmed, corrected, or replaced

**The dossier's stated cause is correct as far as it goes and I re-derived it independently:**
`app/main.py:164` awaits `restore_non_terminal_runs()`; `engine.py:5278` iterates **every** row
returned by an unbounded `SELECT … WHERE status IN (7 non-terminal values)` (`:5270-5274`) and, for
each resumable one, calls `asyncio.create_task(...)` with **no admission control** — at
`:5383-5385` (branch a) and `:5447-5449` (branch b). N in-flight runs at restart ⇒ N driver
coroutines scheduled in the same event-loop iteration.

**Correction 1 — there are TWO create_task sites, not one.** The dossier names only
`engine.py:5244` generically. Branch (a) (`_rearm_gate_run`) is *not* a cheap re-arm: for a
review-open run it calls `await self.resume_run(run_id)` at `:5540`. Any fix that gates only branch
(b) leaves half the burst uncapped.

**Correction 2 — "a single event loop and a bounded thread pool" is the wrong mechanism.**
Nothing on this path is offloaded to a thread pool. Phase 5 **D-08 (`:558`)** locked "the DB is FULLY
SYNC — no `AsyncSession`", and `ScopedStore._acquire` (`authz.py:88-99`) opens a plain
`SessionLocal()`. Every `read_events`/`db.query(...)` in the restore path is **synchronous
SQLAlchemy executed inside `async def` with no executor**, so it blocks the single event-loop thread
for its full duration. The consequence is the opposite of what the dossier implies: the N tasks do
**not** overlap their DB work — they head-of-line-block each other and everything else on the loop,
then all burst into parallel network I/O at once. So the harm decomposes into two distinct things:

  * **(i) A serial, unbounded, readiness-blocking preamble.** Per resumable run the scan does
    `_is_resumable_in_flight` → `read_events(after_seq=0)` (`:5585`) and `_stamp_resume_marker` →
    `read_events(after_seq=0)` (`:5626`); branch (a) adds a third at `:5341`. Each driver then does
    `_compute_resume_offset` → `_recover_workspace_id` + `_first_incomplete_step` reads, and a fourth
    full `read_events` for the seq seed (`:7628`). `read_events` has **no `LIMIT`** (`authz.py:315-330`).
    A5 measured this exact query: **50,000 rows → 924 ms, 103.7 MB peak alloc**, and dev's largest run
    holds **97,694 events** with `run_events` at **741,914 rows**. So the boot scan alone is
    `O(sum of full event logs)` over every non-terminal run, serialised, **before the port is bound**.
    [V] for the code + A5's measurements; [I] for any extrapolated wall-clock on dev.
  * **(ii) A synchronised burst of expensive external work.** Once past the preamble each driver
    reaches `_execute_impl` → `create_runner` → `build_model` → a streaming Bedrock call. N drivers ⇒
    N concurrent `ConverseStream` invocations against one account quota, plus N × the token cost
    (memory `prototype-token-cost`: 5-21M input tokens per `od_prototype` build).

**Correction 4 — a lifetime lease introduces a starvation deadlock.** This is the most important
correction. `_run_review_gate` transitions the run to `waiting_for_user` (`engine.py:5126`) and then
blocks on the review event with **no timeout** (`:5157-5162` racing cancel, or the bare
`await event.wait()` at `:5176`). The clarify twin does the same (`engine.py:1904` →
`clarify_engine.py:325`). A resumed run that reaches a gate therefore keeps its coroutine — and any
semaphore slot held across it — alive for a **human-paced, unbounded** duration. Worse,
**branch (a) parks by construction**: its whole purpose (Phase 49, `:4066`) is to re-enter *at* the
gate, emit `review_gate_ready`, and wait. So the dossier's literal fix ("cap concurrent restores
with a semaphore and queue the remainder, processing them as slots free") would, on a box that
restarts with a handful of gate-parked runs, hold every slot forever and **never restore anything
else** — converting an intermittent burst into a permanent silent stall. That is strictly worse than
the bug.

```python
    async def _admission_gated_restore(
        self,
        run_id: str,
        driver_factory: "Callable[[], Awaitable[None]]",
        admission: "asyncio.Semaphore | None",
        stagger_seconds: float,
    ) -> None:
        """Admission-gate ONE restore driver (D9) so a restart cannot burst.

        ``restore_non_terminal_runs`` creates one task per resumable run. Without a
        gate every task starts in the same event-loop iteration, so N runs issue N
        first model calls at once and N sequential (synchronous, Phase-5 D-08) DB
        preambles head-of-line block the single event loop. This wrapper bounds that
        BURST — and only the burst.

        The slot is an ADMISSION TOKEN, not a lifetime lease: it is released
        ``stagger_seconds`` after the driver starts, whether or not the driver has
        finished. That is load-bearing, not laziness. A resumed run that reaches a
        human review gate transitions to ``waiting_for_user`` and then blocks on the
        review event with NO timeout (``_run_review_gate``, engine.py:5126 →
        :5157/:5176; the clarify twin at engine.py:1904 → clarify_engine.py:325), and
        the branch-(a) gate re-arm parks there BY DESIGN (:5540). Holding a slot for
        a run's lifetime would therefore let a handful of parked runs starve every
        remaining restore permanently — strictly worse than the unbounded burst.

        Error handling — one bad run must never stall the queue: any non-cancel
        exception is logged and swallowed, and the live-registry entries the restore
        create_task site registered are dropped via the idempotent bridge cleanup.
        ``resume_run`` has no outer ``try/finally``, so without this an exception
        raised between its early-return guards and ``_drive_resumed_stream`` leaves a
        permanently stale ``_PIPELINE_TASKS``/``_PIPELINE_QUEUES`` entry (the A4
        stale-registration source). ``CancelledError`` is re-raised untouched so a
        graceful-shutdown cancel behaves exactly as it does today.
        """
        released = False

        def _release() -> None:
            nonlocal released
            if admission is not None and not released:
                released = True
                admission.release()

        timer = None
        if admission is not None:
            if admission.locked():
                _queued_at = time.monotonic()
                logger.info(
                    "restore admission: run=%s QUEUED behind the admission gate",
                    run_id,
                )
                await admission.acquire()
                logger.info(
                    "restore admission: run=%s admitted after %.1fs",
                    run_id, time.monotonic() - _queued_at,
                )
            else:
                await admission.acquire()
            timer = asyncio.get_running_loop().call_later(stagger_seconds, _release)

        try:
            await driver_factory()
        except asyncio.CancelledError:
            raise
        except Exception:  # noqa: BLE001 — one bad run must not stall the queue
            logger.exception("restore driver failed for run=%s", run_id)
            self._fire_resume_cleanup(run_id)
        finally:
            if timer is not None:
                timer.cancel()
            _release()
```

##### I6. Ripple-effect analysis — why nothing else breaks

Assume the fix is wrong and hunt for the failure.

**"The semaphore deadlocks."** It cannot. A slot is released by a `loop.call_later` timer that is
armed **immediately after** the acquire and fires unconditionally after `stagger_seconds`, plus a
`finally` release, plus an idempotent `released` flag so a double release can never raise
`ValueError: Semaphore released too many times`. There is no path on which a slot is acquired and
never released: the timer fires even if the driver never returns; the `finally` fires if the driver
returns, raises, or is cancelled. **This is the single property the whole design turns on and it is
enforced two independent ways.**

**"A gate-parked run starves the queue."** The scenario that breaks the dossier's fix. Here: the
parked run's slot is released `stagger_seconds` after it started, long before it reaches the gate in
any realistic run, and unconditionally regardless. Covered by a dedicated test (I8, test 2).

**"A cancelled wrapper leaks a slot or a registry entry."** `CancelledError` propagates through the
`except asyncio.CancelledError: raise` arm, but the `finally` still runs — `timer.cancel()` and
`_release()`. The registry entry is dropped by the driver's own `finally` chain
(`_rearm_gate_run:5548`, `_drive_resumed_stream`) exactly as today; D8's shutdown owns the rest.
**D9 introduces no untracked background task** — the wrapper *is* the task registered in
`_PIPELINE_TASKS`, so D8's "cancel `_PIPELINE_TASKS` and await with a timeout" covers it by
construction. (Contrast A2's new `_PUMPS`, which D8 flagged as untracked; D9 adds nothing of that
shape.) The `call_later` handle is a loop callback, not a task, and is cancelled in the `finally`.

**"Ordering hazards inside the scan."** The gate adds one `await admission.acquire()` **inside the
spawned task**, never inside the scan loop. The scan's own sequence — register queue → register task
→ `create_task` — is byte-unchanged, so the Phase-12 WR-02 "no live task without a queue" invariant
and the Phase-50 mutex ordering both hold. There is no new `await` between the mutex-relevant
registrations.

**"Startup/shutdown interaction."** Startup: the scan is unchanged in duration (the gate only
affects what the spawned tasks do), so the readiness window is neither lengthened nor shortened by
D9. Shutdown: see above; and if D8's cancel arrives while a driver is queued on the semaphore, the
`acquire()` raises `CancelledError` immediately, the `finally` releases nothing (never acquired,
`released` guard) and the task ends cleanly. **Verify:** `asyncio.Semaphore.acquire()` is cancel-safe
in CPython 3.11 (it removes its own waiter on cancellation). [I] — from the stdlib contract, not run.

**"Unattached client."** A deferred run's queue is registered, so `_get_or_create_queue` returns a
real queue and events accumulate. That is *today's* behaviour for any unattached run and is exactly
what A2 changes (its pump discards with no subscriber). A2 and D9 compose: with A2, a deferred run's
pump drains into nothing until a client subscribes, then the durable replay covers the gap.
**Affected: no.**

**"Slow client / two browsers."** Orthogonal — D9 changes when a run *starts*, not how its events
fan out.

**"Crashed run."** A driver that raises is logged, its registry entries dropped, its slot released.
The next queued driver is admitted. **This is the brief's explicit requirement and it is the
`except` arm.** Contrast today: the exception escapes a bare `create_task`, is swallowed by asyncio's
default handler (logged as "Task exception was never retrieved" *only* when the task is garbage
collected), and the registry entry leaks permanently (A4 source 1).

**"Restart during a restart."** Two processes both scanning is out of scope by locked decision
(Phase 12 T-12-03-CROSSNODE, `:1248`: single-node only, N8 v1). The `run_resuming` marker
(`_stamp_resume_marker`) remains the double-drive guard, unchanged.

**"Resume / fan-out / revision runs."** A resumed fan-out run's *internal* worker concurrency is
still capped by `fanout.py:533`'s own `Semaphore(min(declared, 4))`. The two gates are independent
and multiplicative in the safe direction. A revision run is a normal `WorkflowRun` and takes the same
path. **Affected: no.**

**"Memory / connection pool."** The gate strictly reduces peak concurrency, so both improve. The one
thing it does *not* improve is the serial scan's per-run full-log reads (I4 §8), because those happen
before any task starts — an honest limitation of D9's scope, handed to A5.

**"Partial application."** If step 1 lands without step 2, the settings are inert (nothing reads
them) — harmless. If step 2 lands without step 1, `getattr(..., default)` supplies 4 / 15.0 — the fix
still works. **The steps are independently safe in either order**, which is why I wrote both reads
defensively.

**"The dossier's own safety argument."** D9 makes none to verify beyond "do D8 first", which I
address in I10.

@pytest.mark.asyncio
async def test_a_parked_driver_does_not_starve_the_restore_queue(monkeypatch):
    """The property a lifetime-lease semaphore would violate.

    The first CAP drivers never return (the human-gate park). Every remaining

    _tune(monkeypatch)
    session, db_engine = _make_session()
    ids = _seed(session, 5, "d9b")
    started: list[str] = []
    park = asyncio.Event()          # never set — the drivers hang forever
    all_started = asyncio.Event()

    with _ResumeHarness(session, {}, fail_on=set(), db_engine=db_engine) as h:
        engine = h.make_engine()

        async def _resumable(wr):
            return True

        async def _parking_driver(rid):
            started.append(rid)
            if len(started) == len(ids):
                all_started.set()
            await park.wait()       # mirrors _run_review_gate's untimed wait

        engine._is_resumable_in_flight = _resumable      # type: ignore[assignment]
        engine.resume_run = _parking_driver              # type: ignore[assignment]

##### I10. Sequencing and dependencies

**Verifying the dossier's stated ordering.** The dossier says "do D8 first" because D9 "becomes much
less dangerous once D8 lets runs shut down cleanly". **The conclusion is right; the reason is wrong.**
Under D8's recommended **Option R (leave runs resumable)**, D8 does *not* make runs shut down
cleanly in the sense of finishing them — it closes the checkpointer, drains queues, sentinels pumps,
and leaves the in-flight runs non-terminal on purpose. So after D8 the restore still finds exactly
the same N runs and D9's danger is **unchanged**. The correct reasons to sequence D8 first are:
(i) D8 determines *whether the restore has anything to do at all* (Option R vs Option S — see I11),
and (ii) D8 emits the in-flight count that tells an operator whether the default cap is sane.

**On the D8 conflict, explicitly.** I agree with **Option R (leave runs resumable)** and would
escalate against Option S. Evidence, not preference:

- Option S makes the **entire v3.0 resume milestone dead code on the only path that routinely

- Option S is **not** a clean substitute, because `POST /api/runs/{id}/resume` accepts `cancelled`

**What my gate does under each option, and to SIGKILLed-mid-write runs.**
- **Option R (recommended):** runs stay `running`/`generating` ⇒ inside `NON_TERMINAL`

- **Option S:** runs become `cancelled` ⇒ outside `NON_TERMINAL` ⇒ the scan skips them ⇒ the gate is
  **dormant** and costs nothing. No code change needed either way.
- **SIGKILLed mid-write (today's reality per D8's measurement):** the durable tail is always a
  **prefix**, never a torn row — `ScopedStore.append_event` does `session.add(row); session.commit()`

  the offset from that prefix. **My gate is indifferent to how the process died** — it only bounds how
  many drivers start at once. [V]

**Does my cap sizing change under either option? No.** The gate bounds a *rate*, not a population, so
it is independent of N: it behaves identically for 2 runs and for 200. (This is another concrete
advantage over the dossier's lifetime lease, whose correct size *would* depend on the in-flight count
and on how many of them park.)

##### I11. Open questions requiring a human decision

**1. The D8 Option R / Option S product decision (owned by D8, but D9 is the dependent).**
Should a graceful shutdown mark in-flight runs terminal?

- **Option R — leave resumable (D8's default, and my recommendation).** Runs stay non-terminal;
  the boot restore continues to auto-resume them; the shipped, live-proven v3.0 resume tier keeps
  working; D9's gate bounds the resulting burst.
- **Option S — stop runs on shutdown.** Runs become `cancelled`; the restore finds nothing; D9's gate
  goes dormant. Costs: the v3.0 resume tier becomes dead on the deploy path; every in-flight run
  needs a manual resume via an FE affordance that is not built (`:4077`); the shortcut terminal write
  at `run_commands.py:2155` reopens BUG-R03's empty-output-column gap; and the herd relocates to the
  un-gated user-resume endpoint.
- **Recommendation: R.** I would only revisit if a human decides resumed runs are more dangerous
  than lost ones — which the 2026-07-19 live proof argues against.

**2. Is the cap a rate bound or a hard concurrency bound?** D9 as specified bounds the **start
rate** (at most `cap` drivers admitted per `stagger` window). It does **not** enforce a steady-state
ceiling on how many resumed runs are executing at once, because holding a slot for a run's lifetime
deadlocks against human gates (I3 correction 4).

- **Option A — ship the rate bound (recommended).** Simple, starvation-proof, cap-size independent of
  N, and it targets the actual defect (a synchronised burst). It also avoids throttling a legitimately
  busy system down to 4 concurrent runs for hours after every deploy, which would be worse product
  behaviour than the burst it prevents.
- **Option B — a true concurrency ceiling.** Achievable by releasing the slot when the run parks:
  a shared watchdog polling `self._state_machine.get_state(run_id) == "waiting_for_user"` (the flip at
  `engine.py:5126` happens on the same process singleton, so it is observable) and releasing the slot
  for parked runs. ~20 extra lines, one extra background task, and it leans on `StateMachine._states`
  — which D5 documents as a leaky, never-cleared structure. **I recommend against it unless an
  operator explicitly needs a hard ceiling**; the cheaper 90 % is Option A.

**3. Should the boot restore stop blocking readiness at all?** Today the port is not bound until the
scan finishes (I3 correction 5), and the scan is `O(sum of full event logs)`. D9 does not change this
because backgrounding it breaks the Phase-12 WR-02 invariant (I12 #4). The two honest paths are
(a) shrink the scan (A5's bounded primitive, I10) or (b) split the scan into a synchronous
register-only phase and a background classify-and-drive phase — a genuinely larger change with a real
correctness argument to make. **Recommendation: (a) first, measure, then decide on (b).** Raised here
because it is a product/ops risk decision (deploy reliability), not a purely technical one.

##### I12. Shortcuts and alternatives explicitly rejected

1. **The dossier's own fix verbatim — "a semaphore held for the run's lifetime, queue the
   remainder".** Rejected because it **deadlocks by starvation**: `_run_review_gate` blocks on an
   untimed human wait (`engine.py:5126` → `:5157`/`:5176`) and branch (a) parks there by design
   (`:5540`), so a handful of gate-parked runs hold every slot forever and no further run is ever
   restored. The failure is silent (the runs simply never start), permanent (nothing releases the
   slot), and strictly worse than the burst it replaces. This is not a theoretical edge — it is the
   designed behaviour of Phase 49's re-arm path.

2. **`cap = 24` "for a 4-vCPU box".** Rejected on two counts. The basis is wrong: nothing on this
   path is CPU-parallel (single event loop, sync DB inside `async def`, Phase-5 D-08), so vCPU count
   predicts nothing. And the number is wrong: 24 is **2.4× the LangGraph checkpointer pool's
   `max_size=10`** (`checkpointer.py`), which every dispatched agent contends for and which
   user-launched runs share — so 24 concurrent restores would push that pool into
   `pool_timeout`-shaped failures inside the graph, surfacing as agent errors rather than as a
   recognisable capacity problem.

3. **"Size it to the same figure as any global run-admission limit."** Rejected because, verified by
   reading all 285 lines of `app/core/config.py`, **no such limit exists.** Repeating the dossier's
   assumption would have produced a comment citing a setting that isn't there. The nearest real
   figures are `budget.DEFAULT_MAX_CONCURRENCY = 4` and the checkpointer pool's 10; I cite both and
   pick 4.

4. **Move the whole restore off the readiness path (`asyncio.create_task(restore(...))` before
   `yield`).** Tempting, and it would fix the deploy-gate ripple outright. Rejected because it breaks
   the **Phase-12 WR-02 invariant** (IMPLEMENTATION-REGISTER `:1247`): the queue and task are
   registered *synchronously before* `create_task` precisely so that, by the time any client can
   connect, every resumable run is already live in the registry. Backgrounding the scan reopens the
   exact window WR-02 closed — and it is now *worse* than in Phase 12, because a client that attaches
   before registration gets `live: false`, and BUG-015's `sawNonLiveAttachRef` guard
   (quick 260717-1c1) then deliberately suppresses the reconnect. The user sees a permanently frozen
   run screen. **The register warned about this exact hang ("the UAT Gap 2 'running forever' hang");
   I am not re-introducing it.**

5. **Fix the scan's unbounded `read_events` here (`:5585`, `:5626`, `:5341`).** Correct diagnosis
   (I4 §8), wrong owner. It needs a bounded primitive in `agents/authz.py`, the file A5 is already
   modifying in the same window. Two sibling primitives added by two agents to one file is a merge
   conflict plus an INV-12 duplication risk. Handed to A5 with the exact one-line shape (I10).

6. **Cap the SQL query itself (`.limit(N)` on the non-terminal scan at `:5270-5274`).** Rejected: it
   silently *abandons* runs beyond N — they stay non-terminal forever with no driver, which is
   exactly the "phantom-live row" the WR-05 branch (c) exists to prevent (`:5466-5477`). Bounding
   concurrency must never bound *coverage*.

7. **Add a fixed `asyncio.sleep(i * delay)` schedule instead of a semaphore.** Functionally similar
   and simpler, but it hard-codes an ordering assumption on the loop index that breaks the moment the
   scan is reordered or filtered, and it offers no natural extension point if Option B (I11 #2) is
   later wanted. The semaphore makes the intent self-documenting and leaves the park-aware release as
   a one-line addition.

8. **Reuse `budget.BudgetManager` for admission.** Rejected: `BudgetManager` is per-run and reserves
   *fan-out worker* units (`budget.py:165-191`, Phase 11 FANOUT-09). Overloading it with a
   process-global boot concern would conflate two locked scopes and drag `agents.execution_engine.budget`
   into `app.core.config`.

9. **An `asyncio.wait_for(sem.acquire(), timeout=T)` "cap that yields".** Rejected: every waiter
   starts waiting at the same instant, so every timeout fires at the same instant — it degenerates
   into "delay everything by T, then thundering-herd anyway". Worse than no gate, because it also
   delays the runs.

10. **Do nothing on the grounds that "twenty simultaneous runs is a pre-existing property".** Partly
    true — a user *can* launch twenty runs by hand, and nothing caps that. Rejected because the boot
    case is different in kind: it is **synchronised** (every run starts in the same event-loop
    iteration), it is **automatic** (no human pacing), it happens **on every deploy**, and it lands on
    a process that has just started with cold caches and an unbound port. That combination is what
    makes it "plausibly the real cause of unexplained post-deploy incidents", and it is exactly what
    an admission gate is for.
