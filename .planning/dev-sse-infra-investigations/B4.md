##### I3. Root cause -- confirmed, corrected, or replaced

**The defect, independently re-derived [V].** The agent's own diagnostic sink is declared at
`bootstrap-ec2.sh:966` (`"logfile": "/var/log/amazon-cloudwatch-agent.log"`). The set of files the
agent ships is declared 22 lines later at `:987-996`. `/var/log/amazon-cloudwatch-agent.log` is not
in that set. Both facts are in the same heredoc, 22 lines apart. The agent therefore writes its
entire diagnostic stream to a file that exists only on a box no one can reach without SSM.

**Why it occurred -- the dossier does not say, and the answer matters.** Git blame:

```text

e1a3a4959 (sharas_hx 2026-07-01 995)           {"file_path": "/var/lib/docker/containers/*/*-json.log", ...
```

The `collect_list` was **rewritten wholesale on 2026-07-01** (`e1a3a495`, the CodeBuild/Terraform
restructure) and the agent's own log still was not added. This is not an ancient oversight that
nobody revisited -- it survived a deliberate rewrite of exactly the block it belongs in. The reason
is visible in the comment the author left at `:954-960`: *"The collect_list mirrors the doc
(nginx access/error, postgres, audit, auth, unattended-upgrades, letsencrypt) PLUS the Docker JSON
log path."* The `collect_list` is a **transcription of `docs/SIMPLE_AWS_DEPLOYMENT.md` section 10.1**, and
that doc's list (verified, `docs/SIMPLE_AWS_DEPLOYMENT.md:1234-1243`) also omits the agent's own
log. The omission is in the design document, and the script is faithful to it. **Fixing the script
without fixing the doc re-arms the same drift** -- the next transcription reproduces the bug.

**Correction 1 to the dossier -- B4 does not cover B1.** The dossier's B1 (`:1068-1071`) frames B4
as the missing signal for B1: *"the one signal that would have named it was the one thing not
collected... Even a working agent would not have shipped its own diagnostics. This is why a month
passed."* The first half is true; the conclusion is not. B1's observed failure is:


The agent **could not open the file**. It therefore wrote zero bytes to it, and a `collect_list`
entry pointing at a nonexistent file ships nothing. Had B4 been in place on day one, `/velocityai/dev/system`

signal that would have fired from outside was **`AWS/Logs IncomingLogEvents` = 0** (E1). B4's real
value is a different, larger failure class (I4.6) -- it is worth doing, but not for the reason B1
gives.

**Correction 2 -- "why a month passed" is over-attributed to B4.** The dossier's own Appendix 2 and
C1 establish that dev's userData has no firstboot service and bootstrap never re-runs, so no deploy

agent dead), with B4 as an aggravating factor that removed the diagnostic once someone did look.

**Causal chain, corrected:**

```text

collect_list (transcribed from a doc that omits it) --------> agent's own log NOT tailed
```

###### I4.3 The feedback loop -- the question the dossier does not ask

**Setup.** If the agent tails its own log, does the act of shipping produce a log line that is
itself shipped?

**What the agent writes, and at what level.** The agent's logger is level-prefixed -- the dossier's
own live capture shows `I!` (info) and `E!` (error) forms:

```text
I! Valid Json input schema.
E! failed to create logger: open sink "/var/log/amazon-cloudwatch-agent.log": permission denied
```

At **INFO** (the level in force today, since `debug` is absent from `:964-968` [V]), the logs plugin
writes on **lifecycle transitions only** -- tailer start, offset reset, rotation detected, publish
error, throttle, config reload -- and **not per published batch** [I]. Per-batch detail is a `D!`
line, emitted only when `debug: true` [I].

**Therefore, at the current level, the loop's gain is zero.** Publishing a batch writes nothing, so
there is nothing new for the self-tailer to read, so nothing new to publish. Self-tailing is a
one-shot: at agent start the plugin logs "starting tailer for /var/log/amazon-cloudwatch-agent.log",
that single line ships, and steady state is silent. **No amplification. [I], but structurally sound
and I show the reasoning rather than asserting it.**

**With `debug: true`, the loop is real and geometric.** Each publish writes >= 1 `D!` line; the
self-tailer reads it; the next flush publishes it, writing another `D!` line. With N tailed files
and a ~5s force-flush interval [I], the self-stream's own content grows by roughly
`(lines per publish) x N` per cycle. With N = 9 that is a gain far above 1: the self-stream, the
agent's disk usage, and CloudWatch ingestion all diverge. **This is a genuine hazard, not a
theoretical one, and it is created *by* B4** -- before B4 the loop cannot exist because the file is
not tailed.

**Mitigation, in the order I actually recommend it:**

1. **Do not enable `debug` while the self-entry is present.** It is off today [V]; my fix does not
   turn it on [V]; and `test_agent_debug_logging_is_not_enabled_while_self_tailing` (written and run
   in I8) makes the pair a CI-enforced invariant. This is the whole mitigation -- the loop is
   *absent*, not *dampened*.
2. **If DEBUG is ever needed for live troubleshooting, remove the self-entry first.** Exact
   procedure in I5, step H4. It is three commands and it is reversible.
3. **REJECTED:** an `exclude` filter on the self-entry to drop `D!` lines. Two reasons. (a) It is an
   unverified schema key -- same catastrophic-rejection risk as I4.1. (b) It makes the loop
   *invisible* rather than absent: the agent still writes the debug lines and still burns the disk
   and the CPU reading and discarding them, and the moment the filter expression drifts from the
   agent's log format the loop returns silently. Damping a positive-feedback loop with a text
   pattern is not a fix.

**Crash-loop against a file the agent also tails.** Three cases, and they behave differently:

| Case | What lands in the file | What ships | Does B4 help? |
|---|---|---|---|
| **A. Logger construction fails** (B1's exact failure) | nothing -- the open() itself failed | nothing | **No.** Signal is stderr -> journald. |
| **B. Logger OK, agent dies within seconds; systemd restarts ~1/min** (the observed `restart counter 977` cadence) | startup banner + fatal error, appended on every restart. At ~1-3 KB per attempt that is ~1.5-4 MB/day. | **nothing** -- the logs plugin batches on a ~5s force-flush [I]; a process that lives 2s never reaches a flush | **No.** Signal is E1's meta-alarm (zero incoming events). |
| **C. Agent healthy, one sub-component sick** (B2 permission denial, E4 `AccessDenied` on `DescribeLogGroups`, PutLogEvents throttling, rotation confusion, a rejected config reload) | the `E!`/`W!` line naming the exact path and errno | **yes** -- the agent is alive and flushing | **Yes. This is what B4 buys.** |

Case B's disk growth is bounded and harmless: root is 32% used with 4% inodes [V, dossier Appendix
2] on a 60 GB volume (`app/dev.tfvars: root_volume_size_gb = 60`), so 4 MB/day is noise. It never
reaches CloudWatch, so it costs nothing.

###### I4.4 Rotation and truncation

**What rotates this file today: nothing in this repo.**

```text
grep -rn "logrotate" infra/ docs/SIMPLE_AWS_DEPLOYMENT.md
(no matches)
```

No `/etc/logrotate.d/` drop-in is authored by bootstrap, and the deployment doc never mentions
rotation. Whatever rotation exists is whatever the `amazon-cloudwatch-agent` deb and the agent's own
internal logger provide (the agent is understood to self-rotate its `logfile` [I]; I cannot verify
the size/backup thresholds from here).

**I deliberately do not add a logrotate rule.** An external rotation of a file an internal rotator
already owns is a fight with two bad outcomes: `create` mode renames out from under the agent's open
fd (writes vanish until the agent notices), `copytruncate` mode leaves the writer's offset intact
and produces a sparse NUL hole that the tailer then ships. The agent's file tailer handles rotation
of files it tails through inode tracking plus its on-disk state file, and tailing a self-rotated
file is the same code path as tailing nginx's logrotate'd `access.log`. Leave it alone.

**Truncation on a fresh boot -- and the correction to B1 this forces. MEASURED [V]:**

```text
$ printf 'old content\n' > t.log ; ino_before=$(stat -f %i t.log)
$ exec 9>>t.log                       # simulate the running agent's open write fd
$ install -m 0644 /dev/null t.log     # B1's proposed pre-create line
$ ino_after=$(stat -f %i t.log)
$ printf 'written-after-install\n' >&9

inode before=102570225 after=102570226  same=NO
content of t.log:  (empty)
size = 0
```

`install /dev/null <target>` **replaces the inode**. The write issued through the pre-existing fd
went to the now-unlinked old inode and is unrecoverable. Against a *running* agent this means:

- the agent's writer fd points at an unlinked inode -- every subsequent diagnostic is written into
  the void;
- the new tailer follows the new, permanently-empty inode;
- **the self-log stream goes silent forever, with no error anywhere.** B4 is defeated, silently, by
  B1's own fix line.

This is not hypothetical: **C1's entire purpose is to create a path that re-runs section 13/section 14 on a live
box.** The first reconcile after the fix would break it.

Measured control, same harness [V]:

```text
$ printf 'existing\n' > s.log ; exec 7>>s.log
$ touch s.log ; chmod 0640 s.log
$ printf 'after-touch\n' >&7

touch inode before=102570857 after=102570857 same=YES
content: existing / after-touch
```

`touch` + `chmod` preserve the inode and the open fd. **B1's pre-create must be
`touch` + `chown` + `chmod`, not `install /dev/null`.** (The measurement is BSD `install` on macOS;
GNU coreutils `install` on the Ubuntu target may instead `O_TRUNC` in place [I] -- but that outcome
is *also* bad, producing a sparse NUL hole that the tailer ships when it detects `size < offset`.
Both variants are avoided by the same three-command form, so the fix is correct either way.)

**Does a legitimate truncation cause duplicates or loss?** No duplicates. The agent's tailer keeps a
byte offset per file in its state directory; when the file shrinks below the recorded offset it
treats that as a rotation and resets to 0, re-reading only what is currently there. Since the old
content is gone, nothing is re-shipped. The exposure is *loss* (anything truncated before it
flushed), which is acceptable and unavoidable, and is exactly why the pre-create must be
non-destructive on the re-run path.

###### I4.5 Stream naming, destination group, retention, cost

**Stream name: `{instance_id}/cwagent`.** Requirements: distinct from `{instance_id}` (B3 is
retiring that for `system` anyway), distinct from `{instance_id}/docker` (a different group, but
consistency matters), and self-describing. It follows the in-file precedent at `:995` and matches
the unix account name. Rejected `{instance_id}/agent` -- "agent" means an LLM agent everywhere else
in this product's vocabulary and would read as an application log.

**Group: `/velocityai/<env>/system`, NOT a dedicated group. This is a fence decision, not a
preference.** `local.log_groups` lives in `infra/terraform/modules/monitoring/main.tf:15-23`, a
module instantiated by **dev, stage and prod** (`app/main.tf:169-170`). Adding a ninth name there
would create a new log group in **all three** environments on their next apply -- a direct
violation of the user's "dev environment only -- do not plan changes to `stage` or `prod`
resources." Reusing `system` needs **zero Terraform change**, so there is no plan, no apply, and no
cross-environment reach. It also inherits `prevent_destroy`, the CMK, and retention for free.

The cost of that choice is honest and small: the agent's log shares a group with auditd and
unattended-upgrades, so a future per-group retention override or metric filter cannot target it
independently. Per-stream filtering (`aws logs tail ... --log-stream-names`) covers the operational
need.

**Retention.** `app/dev.tfvars:23` sets `log_retention_days = 14` and `log_retention_overrides` is
unset (default `{}`, `modules/monitoring/variables.tf:41-46`), so every dev group -- including
`system` -- is **14 days**. No change required.

**Cost at DEBUG volume.** Arithmetic shown; the eu-central-1 unit price is [I] (~$0.63/GB ingested,
~$0.03/GB-month stored):

| Scenario | Volume | Ingest/month |
|---|---|---|
| INFO, healthy (today's level) | a few KB/day | effectively $0 |
| INFO, crash-looping 1/min (the observed cadence) | ~4 MB/day = 120 MB/mo -- but see I4.3 case B: **it never ships** | $0 |

**The conclusion to internalise: DEBUG's danger here is amplification, not spend.** Nobody will

##### I6. Ripple-effect analysis -- why nothing else breaks

Assume the fix is wrong and hunt for the failure.

**"The agent rejects the new config and the box loses ALL shipping."** The realistic version of this
is an invalid key or malformed JSON, and it is why H3 uses `jq` (which cannot emit invalid JSON) and
H3b validates before the swap, and why R4's offline test parses the rendered heredoc. The
`collect_list` entry itself uses only the four keys already present on all eight existing entries --
no new key anywhere in the config. **This is also the concrete reason I refuse to add `debug` or a
rotation key** (I4.1). If it still fails, H4's status assertion restores the backup automatically.

**"Two writers, one stream."** Impossible by construction and by test:
`test_every_group_stream_pair_is_unique` asserts uniqueness across the whole array, and it fails on
the tree *today* (B3's real collision), so it is proven non-vacuous.

**"The self-tail deadlocks or reenters."** The tailer and the logger are separate concerns in the
same process: the logger appends, the tailer reads at an offset. There is no lock shared between
them and no ordering dependency. The only coupling is content (I4.3), and it is gain-zero at the
configured level.

**"A restart replays the whole file and duplicates events."** The agent persists a per-file byte
offset in its state directory and resumes from it. On a genuine truncation it resets to 0 and
re-reads only what is present -- see I4.4. The one case that *would* duplicate is the file being
replaced by a *different* inode with the same content, which is exactly the `install /dev/null`
hazard I am removing.

**Startup / shutdown ordering.** The pre-create (H1) must precede `fetch-config` (H4) so the tailer
finds an existing, readable file at start; if it did not, the agent logs "file not found" and
retries -- degraded, not fatal. In the durable path, bootstrap's line order already gives this for
free (the pre-create sits in section 14 before the `cat > ...json` heredoc).

**Under a slow client / unattached client / crashed run / restart / resume / fan-out / revision /
two browsers.** All null. This change touches no backend process, no SSE stream, no queue, no DB
row, no HTTP route. There is no shared state between the CloudWatch agent and the application: the
agent reads Docker's JSON log files from disk, which the app writes to via stdout regardless.

**Memory and connection-pool effects.** None. The agent is a separate process with its own memory;
BUG-004's pool-leak class (`FIX`/quick 260716-heb) is a FastAPI `get_db` teardown issue and shares
no code with this.

**Partial application.** Four sub-cases, all benign:
- Repo change lands, host not patched: the file is source-of-truth-correct and inert until C1's
  reconcile or an instance rebuild. Nothing breaks.
- Host patched, repo not: the next instance rebuild loses it. Detectable by the offline test
  failing. Do not do this -- I10 orders repo-first.
- B4 lands without B3: the new `{instance_id}/cwagent` stream is still unique, so B4 works; B3's
  pre-existing audit/unattended collision persists unchanged. **B4 does not depend on B3 for
  correctness** -- only for the block alignment being done once.
- B4 lands without B1: the file does not exist, the agent logs "no such file" once per retry, and
  nothing ships from that entry. Harmless but pointless. B1 is a hard prerequisite for *value*, not
  for *safety*.

**The one genuine new hazard this fix creates** is the DEBUG amplification loop (I4.3). It did not
exist before, because the file was not tailed. It is mitigated by a config invariant plus an
executable test, and documented at the point of change (R2). I would rather name it plainly than let
a future operator discover it.

**Where the dossier already argues safety, verified rather than restated:** B4 says the fix is
"destination `/velocityai/<env>/system` and a distinct stream name per B3." I verified the
destination exists in Terraform, is CMK-encrypted, has 14-day retention on dev, is covered by the
existing IAM grant, and **has zero metric filters** -- so the "safe" claim holds for a stronger
reason than the dossier gives.

```python
"""Offline guards on the CloudWatch-agent config emitted by bootstrap-ec2.sh.

Pure-stdlib text/JSON assertions over two infra files. No AWS, no network, no
backend import -> cannot perturb INV-3 goldens and is invisible to
import-linter (backend/tests is not an import-linter root package).
"""
import json
import os
import re
from pathlib import Path

import pytest

REPO = Path(os.environ.get("FLOWIN_REPO", Path(__file__).resolve().parents[3]))
BOOTSTRAP = REPO / "infra" / "scripts" / "bootstrap-ec2.sh"
MONITORING = REPO / "infra" / "terraform" / "modules" / "monitoring" / "main.tf"

AGENT_SELF_LOG = "/var/log/amazon-cloudwatch-agent.log"


def _render_agent_config(environment: str = "dev") -> dict:
    """Extract the section-14 heredoc and render it exactly as bash would."""
    text = BOOTSTRAP.read_text(encoding="utf-8")
    m = re.search(
        r"cat > /opt/aws/amazon-cloudwatch-agent/etc/amazon-cloudwatch-agent\.json <<EOF\n(.*?)\nEOF\n",
        text,
        re.S,
    )
    assert m, "could not locate the amazon-cloudwatch-agent.json heredoc in bootstrap-ec2.sh"
    body = m.group(1)
    # Unquoted heredoc: ${ENVIRONMENT}/${ENV_TITLE} interpolate; \${aws:...} does not.
    body = body.replace("${ENVIRONMENT}", environment)
    body = body.replace("${ENV_TITLE}", environment.capitalize())
    body = body.replace("\\${", "${")
    return json.loads(body)


def _terraform_log_groups(environment: str = "dev") -> set[str]:
    text = MONITORING.read_text(encoding="utf-8")
    m = re.search(r"log_groups\s*=\s*\[(.*?)\]", text, re.S)
    assert m, "could not locate local.log_groups in the monitoring module"
    names = re.findall(r'"([^"]+)"', m.group(1))
    return {n.replace("${var.environment}", environment) for n in names}


def _collect_list(cfg: dict) -> list[dict]:
    return cfg["logs"]["logs_collected"]["files"]["collect_list"]


def test_agent_config_is_valid_json():
    cfg = _render_agent_config()
    assert cfg["agent"]["run_as_user"] == "cwagent"
    assert cfg["agent"]["logfile"] == AGENT_SELF_LOG


def test_agent_self_log_is_collected():
    """B4: the observability system must observe itself."""
    paths = [e["file_path"] for e in _collect_list(_render_agent_config())]
    assert AGENT_SELF_LOG in paths, (
        "the CloudWatch agent's own log (agent.logfile) is not in collect_list -- "
        "an in-agent failure produces no external signal (B4)"
    )


def test_every_group_stream_pair_is_unique():
    """B3: two files on one (group, stream) contend for a sequence token."""
    pairs = [
        (e["log_group_name"], e["log_stream_name"])
        for e in _collect_list(_render_agent_config())
    ]
    dupes = {p for p in pairs if pairs.count(p) > 1}
    assert not dupes, f"colliding (log_group, log_stream) pairs in collect_list: {sorted(dupes)}"


def test_every_destination_group_exists_in_terraform():
    """Name drift = alarms watching a group nothing writes to."""
    declared = _terraform_log_groups()
    used = {e["log_group_name"] for e in _collect_list(_render_agent_config())}
    assert used <= declared, f"collect_list ships to undeclared log group(s): {sorted(used - declared)}"


def test_agent_debug_logging_is_not_enabled_while_self_tailing():
    """DEBUG + self-tail is a publish->log->publish amplification loop."""
    cfg = _render_agent_config()

            "agent.debug is on while the agent's own log is tailed -- "
            "each published batch logs a line that is itself published"
        )
```

##### I9. Rollback

**Repo half.** `git revert <sha>`. One commit, three files, no migration, no schema, no state. The
`aws_s3_object.bootstrap_script` `source_hash = filemd5(...)` re-uploads the reverted script to
`s3://velocityai-dev-pg-dumps-577954642302/config/bootstrap-ec2.sh` on the next dev push, and
nowhere else (per-env bucket, verified at `app/main.tf:79-94`). Fully reversible.

**Host half.** The payload writes `/root/cwagent-backup-<ts>/amazon-cloudwatch-agent.json` before
touching anything, and H4 restores it automatically if the agent is not `running` after reload.
Manual rollback:

```bash
cp -a /root/cwagent-backup-<ts>/amazon-cloudwatch-agent.json \
      /opt/aws/amazon-cloudwatch-agent/etc/amazon-cloudwatch-agent.json
/opt/aws/amazon-cloudwatch-agent/bin/amazon-cloudwatch-agent-ctl \
    -a fetch-config -m ec2 -s -c file:/opt/aws/amazon-cloudwatch-agent/etc/amazon-cloudwatch-agent.json
```

**What is NOT reversible, and what the pre-change backup must capture.**

- **There is no filesystem-level rollback.** `velocityai-dev-root` has `delete_on_termination = true`
  and **zero snapshots** [V, dossier Appendix 2]. The `/root/cwagent-backup-<ts>/` copy is the only
  restore point for the config, and it lives on the same volume it protects. If the box is
  terminated, both are gone -- recovery is then "rebuild from the repo," which is fine because the
  repo half is the source of truth.
- **Log data already ingested cannot be un-ingested.** Irrelevant here: 14-day retention on dev, and
  the content is the agent's own diagnostics -- no secrets, no PII, no credentials. Worth stating
  because it is the only irreversible side effect of the change.
- **What the backup MUST capture, and does:** the pre-change
  `amazon-cloudwatch-agent.json` (the only mutated file). It must **not** try to capture
  `/var/log/amazon-cloudwatch-agent.log` -- H1 is deliberately non-destructive, so the file's content
  survives the change untouched. That is the whole point of the `install`-to-`touch` correction.

##### I12. Shortcuts and alternatives explicitly rejected

**Verifying the dossier's own rejections first.** B1 rejects `run_as_user: root` ("widens the blast
radius of a log-shipping daemon for no reason"). **Verified and agreed, with an additional reason
the dossier misses:** running as root would also make the self-log root-owned, which then needs
either a wider mode or an ACL for nothing -- the `cwagent`-owned file needs neither (I5 H2). The
dossier lists no rejections for B4 itself; these are mine.

1. **Set `agent.debug: true` "so the self-log is actually useful."**
   Fails: it creates the amplification loop (I4.3). The useful content -- errors and warnings -- is
   already at `E!`/`W!` and ships at the default level. DEBUG adds per-batch chatter that is exactly
   the thing that feeds itself.

2. **Add `logfile_backup_count` (or any rotation key) to bound the file.**
   Fails: I cannot verify the key exists in this agent version's JSON schema, and the agent
   validates the config before loading. If the schema is closed, an unknown key makes `fetch-config`
   reject the whole config and the box loses **all** log and metric shipping -- a strictly worse
   outcome than the problem. Rotation is already the agent's own concern (I4.4), and the growth even
   in the crash-loop case is ~4 MB/day against a 32%-used 60 GB volume.

3. **Add an `/etc/logrotate.d/amazon-cloudwatch-agent` drop-in.**
   Fails: two rotators, one file. `create` mode renames out from under the agent's open fd (writes
   vanish silently); `copytruncate` leaves the writer's offset intact and produces a sparse NUL hole
   that the tailer then ships. This is a real bug I would be introducing to solve a non-problem.

4. **Create a dedicated `/velocityai/<env>/cwagent` log group.**
   Fails the user's scope fence. `local.log_groups` lives in a module instantiated by dev, stage and
   prod (`app/main.tf:169-170`); adding a name creates the group in **all three** on their next
   apply. Reusing `system` requires zero Terraform, so there is no plan and no cross-environment
   reach. The cost -- no independent retention or metric filter for the agent's stream -- is
   recoverable with `--log-stream-names`.

5. **Add an `exclude` filter on the self-entry to break the DEBUG loop.**
   Fails twice: unverified schema key (see 2), and it damps rather than removes the loop -- the
   agent still writes, reads and discards the debug lines, and a drift between the filter expression
   and the agent's log format silently restores the amplifier.

6. **Ship the agent's log to the `app` group instead of `system`.**
   Fails: `app` carries **three** metric filters (`db_conn_error` `:502`, `ws_disconnect` `:642`,
   `agent_error_rate` `:857`). `agent_error_rate` in particular is a pattern-matched counter over
   application text; feeding it a stream full of lines the CloudWatch agent prefixes with `E!` is
   a plausible false-positive source and would corrupt a live alarm. `system` has zero filters
   (I4.2). This is the sharpest reason the group choice is not arbitrary.

7. **Use `install -o cwagent -g cwagent -m 0644 /dev/null <file>` as B1 proposes.**
   Fails, measured: it replaces the inode (I4.4), orphaning a running agent's write fd and leaving
   the tailer on a permanently empty file. Silent, permanent, and triggered by the very reconcile
   path C1 is building. `touch` + `chown` + `chmod` is the correct form and is verified
   inode-preserving.

8. **Skip the doc update (`docs/SIMPLE_AWS_DEPLOYMENT.md` section 10.1) as "just docs."**
   Fails: `bootstrap-ec2.sh:954` names that doc as the source the `collect_list` is transcribed
   from, and the doc's list is where the omission actually lives (I3). Fixing only the script leaves
   the defect in the specification and guarantees the next transcription -- or the next environment
   built from the doc -- reproduces it.

9. **Skip the offline test because "it is only a config line."**
   Fails: a config line with no test is precisely what shipped this defect, survived a full rewrite
   of the surrounding block on 2026-07-01, and hid for a month. The repo has **no** shellcheck, no
   JSON validation, and no test for `bootstrap-ec2.sh` (verified). Four of the five assertions cost
   nothing to run (0.07s, stdlib only) and two of them are red on the tree today.

10. **Deliver the host change by re-running `bootstrap-ec2.sh` over SSM.**
    Fails: the script rewrites nginx, Postgres, systemd units and the app stack, and `ENVIRONMENT`
    silently defaults to `prod` if `/etc/velocityai/bootstrap.env` was not sourced
    (`bootstrap-ec2.sh:79`) -- which would ship dev's logs into prod's log groups. The targeted `jq`
    payload (I5 H3) touches one file, validates before swapping, and hard-fails on an unset
    environment.
