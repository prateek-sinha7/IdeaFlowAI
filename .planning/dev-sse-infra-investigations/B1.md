**Where the dossier's REMEDY needs correcting - the three latent regressions in
`install -o cwagent ... /var/log/amazon-cloudwatch-agent.log`:**

1. **Internal rotation cannot work in a directory cwagent does not own.** The agent rotates its
   own log itself (size-based, no external tool). Rotation is rename-then-create in the same
   directory, which needs write+execute on `/var/log`. cwagent has neither. Pre-creating the
   *file* fixes `open()`; it does not fix `rename()`. [I - the rotation mechanism is my
   knowledge of the agent, not observed here; the permission arithmetic is [V] from the
   dossier's `/var/log` root-ownership finding.]
2. **A future logrotate stanza silently re-breaks it.** There is **no logrotate config for this
   file anywhere in the repo** - `grep -rn "logrotate" infra/` returns nothing [V] - and none
   is expected from the package or the distro [I]. But that is an assumption, and it is exactly
   the assumption an operator will invalidate the first time they see a large
   `/var/log/amazon-cloudwatch-agent.log` and write the obvious four-line stanza. logrotate's
   `create` directive with no owner arguments recreates the file **root:root**, and the agent
   dies again on the next rotation - weeks later, with no alarm, and with the one log that
   would explain it now root-owned and unreadable by the process that needs to write it.
   That is a perfect repeat of today's failure.
3. **`install` is not idempotent in the way this needs.** `install ... /dev/null <dest>`
   overwrites the destination's contents. Under C1's reconcile - which explicitly re-runs
   §13/§14 on every deploy - this **truncates the agent's live diagnostic log on every
   deploy**, and if the running agent holds the fd it may keep writing to a replaced inode,
   losing output until the next restart. [V - `install` copies `/dev/null` over the target
   by definition.]

All three vanish if the sink lives in a directory cwagent owns. See I5.

**(e) NEW DEFECT the dossier misses - the five alarms will most likely NOT self-heal**

The dossier says the five `treat_missing_data = "breaching"` alarms "will resolve themselves the
moment metrics start flowing." **I do not believe they will**, and the reason is in the repo.

The alarms specify these dimension sets:

| Alarm | file:line | `dimensions` |
|---|---|---|
| `cpu-high` | `monitoring/main.tf:376-378` | `{ InstanceId }` |
| `mem-high` | `:401-403` | `{ InstanceId }` |
| `disk-root-high` | `:426-429` | `{ InstanceId, path = "/" }` |
| `disk-data-high` | `:452-455` | `{ InstanceId, path = "/var/lib/postgresql" }` |
| `inode-low-*` (x2, `for_each`) | `:1643-1646` | `{ InstanceId, path = each.key }` |

The agent config will publish with:

- `append_dimensions = {InstanceId, InstanceType}` (`bootstrap-ec2.sh:979-982`) on **every** metric;
- plus the cpu plugin's own `cpu` tag (`totalcpu: true` -> `cpu=cpu-total`);
- plus the disk plugin's own `path`, `device`, `fstype` tags (no `drop_device` set).

So the published metrics carry `{InstanceId, InstanceType, cpu}`, `{InstanceId, InstanceType}`, and
`{InstanceId, InstanceType, path, device, fstype}` respectively. **A CloudWatch alarm matches an
exact dimension set - it cannot match a subset.** None of the five alarms' dimension sets exist
as published metrics, so all five stay `INSUFFICIENT_DATA`, and with `treat_missing_data =
"breaching"` that renders as ALARM. Forever. Even with a perfectly healthy agent.

The Terraform author was aware of the extra dimensions and reasoned about them incorrectly -
`monitoring/main.tf:1641-1642` says, verbatim:

> `# Match the disk_used_percent alarm dimensions: InstanceId + path. The CW`
> `# Agent also emits device + fstype but those add fragility (a remount`
> `# changes them) for no extra precision in our single-instance design.`

That is a decision to *omit* dimensions the agent emits - which does not produce a looser match,
it produces **no match at all**. [V for the config and the alarm dimensions; **[I]** for the
conclusion, because it rests on (1) the agent publishing no aggregated rollup when
`aggregation_dimensions` is absent, and (2) CloudWatch alarm dimension matching being exact.
Both are standard behaviour but I could not confirm them against the live account.]

**Why this matters for B1 specifically.** It changes the sequencing contract with B6. The dossier
says "fix B1 and B2 first, then subscribe." If this finding holds, subscribing after B1+B2 still
delivers five permanently-ALARM emails to a freshly-confirmed mailbox on day one - the exact
alarm-fatigue outcome B6 exists to prevent. **The gate on B6 must be a measured dimension check,
not the mere fact that B1 landed.** That check is one read-only call and is in my verification
plan (I8). The fix itself is out of my lane (Terraform alarms, or an `aggregation_dimensions`
key in §14) - see I10 and I11.

**(g) Cost - what shipping these log groups actually costs**

Retention is **14 days** on dev (`app/dev.tfvars:23`). The honest arithmetic:

```
monthly = (GB_ingested_per_month * ingest_$/GB)
        + (avg_GB_stored * storage_$/GB-month)
        + (KMS GenerateDataKey requests / 10,000 * $0.03)
```

- **Ingestion dominates.** `~$0.50-0.63/GB` in eu-central-1 [I - I could not hit the pricing API].
- **Volume estimate for dev** [I]: nginx-access ~10-20 MB/day (E1's JSON format roughly doubles
  line size, ~200 -> ~400 B, which is the dossier's own `$1.30/env/month` figure); the Docker
  JSON `app` group is the wildcard at ~50-200 MB/day under active use (note `uvicorn.access` is
  pinned to `WARNING` at `backend/app/main.py:54`, so there are no per-request lines); postgres
  5-20 MB/day; auth.log 5-50 MB/day on a public EIP; `/var/log/audit/audit.log` is the real
  unknown - auditd can be very loud depending on the installed ruleset and is worth measuring
  on day one. **Band: 0.1-1 GB/day -> 3-30 GB/month -> roughly $2-$20/month.**
- **Storage is negligible.** 14 days retained, stored compressed, at `$0.03/GB-month`: on the
  order of `$0.01-0.05/month`.
- **KMS adds ~$0.20/month.** CW Logs caches data keys, so roughly one `GenerateDataKey` per group
  per 5 minutes: `7 x 288 x 30 = ~60k requests` at `$0.03/10k`. [I]

**Correction to the brief's framing.** Retention does **not** bound this bill in any meaningful
way - it bounds *storage*, which is under 5% of it. **The only levers on ingestion are the
`collect_list` contents and per-source verbosity.** If cost becomes a concern the actions are:
drop `letsencrypt` (near-zero value, tiny anyway), reduce auditd rules, or - the real one -
measure `IncomingBytes` per group for a week and then decide. Do not lower retention expecting
a saving.

Total: **on the order of $3-$25/month for dev**, with the honest caveat that the range is wide
because nothing has ever been measured. The very first thing the fix produces is the data
needed to replace this estimate with a number.

##### I5. The complete fix

Three changes, all in `infra/scripts/bootstrap-ec2.sh` §14, plus the host-side application.
This covers **B1 only**. B2 (permissions), B3 (stream collision), B4 (collect the agent log)
and B5 (exit-status check) are separate edits to the same section - see I10 for how they compose.

**Design decision: relocate the sink, do not pre-create it in `/var/log`.**
The agent's vendor-default log path is inside its own installation tree, which the agent's
own tooling owns. Putting the sink there means cwagent owns the *directory*, so `open()` and
`rename()` (rotation) both work, no logrotate stanza is ever needed or tempting, and the setup
step is `install -d` (idempotent) instead of `install <file>` (destructive on re-run). One
extra line buys the removal of all three latent regressions from I3.

##### I6. Ripple-effect analysis - why nothing else breaks

*Assume the fix is wrong. Where does it hurt?*

- **The agent starts and immediately floods a group with a backlog.** The tailers start at the
  *end* of each file by default for a first-time state, so there is no historical replay of
  months of nginx logs. If the agent did start from byte 0 on eight files the first-minute
  ingestion spike would be bounded by current file sizes on a 60 GB root volume at 32% used
  [V, dossier] - tens of MB, one-off, a few cents. Not a risk worth gating on, but worth
  watching `IncomingBytes` for the first hour.
- **The agent starts, and B2 has not landed.** Then it runs, opens its own log successfully, and
  logs a permission-denied line **per configured file, repeatedly**. That is the intended
  outcome - it is exactly how B2 becomes visible instead of silent - but it means B1 alone
  produces a noisy `system` group. It also means **B1 must not be shipped and then left**: the
  window between B1 and B2 is the only window where the agent writes mostly errors. Ship them
  together (I10).
- **Feedback loop from collecting the agent's own log (B4).** The agent tailing its own log is
  the classic amplification worry. It does not amplify here: the tailer records position in its
  state directory and does not log per shipped line, so one error line produces one shipped
  event, not N. The genuinely dangerous variant is "agent logs an error about shipping its own
  log", which would loop - but that requires the agent's own log destination to be broken while
  the agent is otherwise healthy, and B1+B2 remove exactly that condition. Worth one look at
  `IncomingBytes` on `/velocityai/dev/system` in the first hour anyway.
- **Concurrency / ordering inside bootstrap.** `install -d` at the new position runs after
  `dpkg -i` (`:945`) and after the `getent` assertion, and before the `cat >` heredoc (`:962`)
  and before `fetch-config` (`:1005`). Nothing between those points touches
  `/opt/aws/amazon-cloudwatch-agent`. Under `set -euo pipefail` a failure at any of the three
  new lines aborts the script - which is correct: sections 15-20 (deploy user, backups, systemd
  units, app start) all depend on a coherent host, and silently continuing is what produced
  this bug in the first place.
- **Startup/shutdown and reboot.** `install -d` is not order-sensitive relative to systemd; the
  agent unit is package-enabled and starts on boot, finds an existing cwagent-owned directory,
  and opens its sink. On a re-run of the whole script, `install -d` re-applies mode/ownership
  and the config `cat >` overwrites identically - no divergence.
- **Partial application.** If the SSM command dies after `install -d` but before the config
  rewrite: harmless (an empty owned directory). If it dies after the config rewrite but before
  `fetch-config`: the on-disk JSON says the new path but the running (crash-looping) agent still
  uses the old translated TOML - i.e. exactly today's state, no worse. If it dies after
  `fetch-config`: the fix is applied. **Every intermediate state is either today's behaviour or
  the fixed behaviour.** There is no state in which the fix makes things worse.
- **The shared-script hazard (the one real cross-environment risk).** `bootstrap-ec2.sh` is one
  file used by dev, stage and prod. The dev-only scope fence holds for *application*
  (`--instance-ids i-092d...` only), but the **repo edit is inherently shared** - it lands in
  every environment's S3 copy on that environment's next build, and takes effect on any future
  instance replacement in stage or prod. That is desirable (stage and prod have the identical
  bug) but it must be stated, not discovered. The change is strictly safer everywhere:
  `install -d` is idempotent, and the relocated path is the vendor default.
- **Does anything read `/var/log/amazon-cloudwatch-agent.log`?** No. It does not exist on the
  box [V, dossier], nothing in the repo references it except the config line being changed and
  the design doc, and it is not in the `collect_list` (machine-verified). Moving it strands
  nothing.
- **Unattended reboot at 04:00.** `bootstrap-ec2.sh:169-172` enables auto-reboot. A reboot
  restarts the agent, which re-opens the same sink in the same owned directory. No interaction.
- **Slow client / crashed run / fan-out / two browsers / resume.** Not applicable - this change
  is entirely host-side and touches no request path, no queue, no connection pool, and no
  in-process state. Cluster A's SSE work and this fix are disjoint at the file level.

**New test - complete code.** Place at `backend/tests/unit/test_bootstrap_cloudwatch_agent.py`.
It follows the house idiom for repo-root resolution used by

```python
"""Offline gate on the CloudWatch-agent block of infra/scripts/bootstrap-ec2.sh (B1..B4).

The bootstrap script has ZERO automated coverage today: `infra/buildspec.yml`
pre_build runs python compileall, terraform fmt/validate, gitleaks, checkov and
trivy -- no shell syntax check and no validation of the agent config it renders.
That is why a config which has never once produced a working agent survived
2.5 months of CI.

This gate renders the §14 heredoc exactly the way bootstrap does (unquoted
`<<EOF`, so bash expands ${ENVIRONMENT} / ${ENV_TITLE} and the agent's own
\\${aws:...} placeholders survive escaped), parses the result as JSON, and
pins the four properties whose violation is silent in production:

  1. the config is valid JSON at all;
  2. the agent's telemetry sink lives in a directory the run_as_user owns --
     the B1 root cause (a sink in root-owned /var/log means the agent exits 1
     before doing any work, forever, with no external signal);
  3. the agent's own log is in the collect_list -- the B4 root cause (the
     observability system must observe itself, or its total failure produces
     no signal);
  4. every (log_group_name, log_stream_name) pair is unique -- the B3 root
     cause (two tailers on one CloudWatch stream contend for its sequence
     token and interleave).

Offline and deterministic: it shells out to bash for the render (bash is
present wherever this suite runs) and touches no network and no AWS API.
"""

from __future__ import annotations

import json
import re
import subprocess
from pathlib import Path

import pytest

# backend/tests/unit/<this file> -> repo root is parents[3]
_REPO = Path(__file__).resolve().parents[3]
_BOOTSTRAP = _REPO / "infra" / "scripts" / "bootstrap-ec2.sh"

_RUN_AS_USER_OWNED_PREFIXES = ("/opt/aws/amazon-cloudwatch-agent/",)


def _heredoc_body_lines() -> tuple[int, int]:
    """Return the 1-based [start, end] line range of the agent-config heredoc body.

    Located structurally (by the `cat > <path> <<EOF` opener and its `EOF`
    terminator) rather than by hardcoded line numbers, so the gate survives
    edits elsewhere in the file.
    """
    lines = _BOOTSTRAP.read_text().splitlines()
    start = None
    for i, line in enumerate(lines, start=1):
        if re.match(r"^cat > \S*amazon-cloudwatch-agent\.json <<EOF\s*$", line):
            start = i + 1
            break
    assert start is not None, "could not find the agent-config heredoc opener in bootstrap-ec2.sh"
    for j in range(start, len(lines) + 1):
        if lines[j - 1].rstrip() == "EOF":
            return start, j - 1
    raise AssertionError("agent-config heredoc has no EOF terminator")


def _render_agent_config(environment: str = "dev") -> dict:
    start, end = _heredoc_body_lines()
    body = "\n".join(_BOOTSTRAP.read_text().splitlines()[start - 1 : end])
    script = f"cat <<EOF\n{body}\nEOF\n"
    out = subprocess.run(
        ["bash", "-c", script],
        capture_output=True,
        text=True,
        check=True,
        env={
            "ENVIRONMENT": environment,
            "ENV_TITLE": environment.capitalize(),
            "PATH": "/usr/bin:/bin",
        },
    ).stdout
    return json.loads(out)


def test_bootstrap_script_is_syntactically_valid():
    """`bash -n` on the whole script -- the gate that does not exist in CI today."""
    subprocess.run(["bash", "-n", str(_BOOTSTRAP)], check=True)


def test_agent_config_renders_to_valid_json():
    cfg = _render_agent_config()
    assert cfg["agent"]["run_as_user"] == "cwagent"
    assert cfg["metrics"]["namespace"] == "VelocityAI/Dev"
    # the agent's own placeholders must survive the unquoted heredoc verbatim
    assert cfg["metrics"]["append_dimensions"]["InstanceId"] == "${aws:InstanceId}"


def test_agent_logfile_lives_in_a_run_as_user_owned_directory():
    """B1: a sink in root-owned /var/log makes the agent exit 1 before doing any work."""
    cfg = _render_agent_config()
    logfile = cfg["agent"]["logfile"]
    assert logfile.startswith(_RUN_AS_USER_OWNED_PREFIXES), (
        f"agent.logfile is {logfile!r}; run_as_user={cfg['agent']['run_as_user']!r} cannot "
        "create or rotate a file in a directory it does not own -- the agent exits 1 before "
        "shipping anything (B1)."
    )


def test_bootstrap_owns_the_agent_log_directory_after_the_user_exists():
```

##### I9. Rollback

**Repo half.** One commit touching two files (`infra/scripts/bootstrap-ec2.sh`,
`docs/SIMPLE_AWS_DEPLOYMENT.md`) plus one new test file. `git revert <sha>` is complete and
safe: nothing else in the tree references the new path, and the revert restores a state that is
broken-but-known (today's).

**Host half.** The SSM payload backs up both the source JSON and the translated `.d` copy to
`/root/cwagent-backup-<ts>/` before touching anything. To undo:

```bash
cp -a /root/cwagent-backup-<ts>/amazon-cloudwatch-agent.json \
      /opt/aws/amazon-cloudwatch-agent/etc/amazon-cloudwatch-agent.json
/opt/aws/amazon-cloudwatch-agent/bin/amazon-cloudwatch-agent-ctl \
  -a fetch-config -m ec2 -s -c file:/opt/aws/amazon-cloudwatch-agent/etc/amazon-cloudwatch-agent.json
```

`install -d` leaves an empty owned directory behind. **Do not remove it** - it is inert, and
`/opt/aws/amazon-cloudwatch-agent/logs` is where the vendor default points anyway.

**What is NOT reversible, stated plainly:**

- **There are no EBS snapshots on any root volume, in any environment** [V, dossier Appendix 2].
  `velocityai-dev-root` has zero. There is no filesystem-level rollback for anything this fix
  does on the host. The `/root/cwagent-backup-<ts>/` copies are the only restore point, which is
  why the SSM payload takes them before the first mutation and not after.
- **Log data, once ingested, is billed and cannot be un-ingested.** If the fix causes an
  unexpected ingestion spike (see I6), the mitigation is forward (drop a `collect_list` entry
  and re-run `fetch-config`), not backward.
- **The pre-change backup must capture** exactly two files:
  `/opt/aws/amazon-cloudwatch-agent/etc/amazon-cloudwatch-agent.json` (the source of truth we
  rewrite) and
  `/opt/aws/amazon-cloudwatch-agent/etc/amazon-cloudwatch-agent.d/file_amazon-cloudwatch-agent.json`
  (what `fetch-config` actually reads). Backing up only the first leaves the agent running the
  old translated config after a partial revert.
- **Blast-radius note:** the SSM command is scoped to one instance id with a `Name` pre-flight.
  There is no path by which it reaches stage or prod. The *repo* change does reach them on their
  next build, and that is not revertable per-environment - see I6's shared-script hazard.
