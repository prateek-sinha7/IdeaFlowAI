##### I3. Root cause - confirmed, corrected, or replaced

**The dossier's root cause is correct but incomplete. Three corrections.**

The dossier says: *"If `res.ok` is false the streaming branch is skipped and the function falls
through to `return null` with no error path at all."* That is exactly right for the chat path, and I
reproduced the control flow by reading `RunConnectionProvider.tsx:386-463` line by line. But the
function has **four** silent-discard exits, not one, and only three of them are the same bug.

**Correction 1 - there are three silent-discard exits on the request path, not one.**

```
sendCommand(runId, payload)
  :391  const t = getToken();
  :392  if (!t) return null;          <-- EXIT A: no token. Chat message vanishes. UNDOCUMENTED.
  :396  const res = await fetch(url, {...})   <-- no AbortController, no try/catch
  :412  if (runId) {                          <-- the /messages branch
  :414    if (res.ok && res.body && ct.includes("text/event-stream")) { ...drain... }
  :448    return null;                <-- EXIT B: covers BOTH "OK + JSON" (correct) and
                                          "not OK" (the D2 bug). One return, two meanings.
  :449  }
  :452  if (!res.ok) return null;     <-- EXIT C: launch branch. Different symptom
                                          (optimistic "Running" screen), same shape.
```

Exits A and B are both "the chat message is silently lost". Exit C is the Phase-51 launch finding.

**Correction 2 - the dossier's "no error path at all" understates it: there IS a path, and it is
worse than nothing.** A *hard network failure* (DNS, connection reset, CORS) makes `fetch` itself
reject. `sendCommand` has no `try/catch`, and `useRunChat.ts:511-521` wraps the call in
`void (async () => { await sendCommand(...); ... })()` with the `try/catch` positioned **around the
`fetchEvents` re-fetch only**, not around `await sendCommand`. So today a network error produces an
**unhandled promise rejection** plus a stranded optimistic bubble. Same for the launch caller
(`page.tsx:1955`, a `.then()` with no `.catch`). The dossier does not mention this; it matters
because it means "make `sendCommand` throw" is not a free change - it converts a *silent* failure
into an *unhandled rejection* unless both callers are given handlers in the same commit. That is the
single biggest correctness risk in this fix and it is why I4 enumerates callers exhaustively.

**Correction 3 - the 429 is not the only reachable trigger, and A1 does not close it.** The dossier
says "This becomes considerably less likely once A1 lands, but a transient 5xx will still hit it."
Confirmed, and there is more:

- A1's fix exempts **only** `GET /api/runs/{id}/events/stream` from `limit_req`. A1's own text
  (dossier `:210-226`) is explicit that `POST /api/runs/{id}/messages` **stays inside the rate-limited
  `/api/` block on purpose** (it triggers a Bedrock call). So **A1 does not reduce D2's 429 exposure
  at all on the chat path**; it removes the *stream* from the shared bucket, which slightly reduces
  bucket pressure but leaves `/messages` metered at 120 r/m burst 20 per client IP - and the whole
  office shares one NAT egress IP (dossier A1 fix note 1).
- The backend's own 4xx set on this route is reachable in normal use: **404** (owner mismatch /
  missing run, `run_commands.py:1048`, `:1076`), **409** (KAN-100 terminal fence, `:1141`), **404**
  "Unknown proposal" (`:1247`), **400** `invalid_image_input` (`:1094` via `_reject`). Every one of
  those is silently discarded today.

request failed", because at the time SSE was flag-off dead code (`IMPLEMENTATION-REGISTER.md:3007`)
and there was no rate limiter in front of it.

```ts
/**
 * D2 — the FAILED-SEND marker. When the up-channel REJECTS (the command was never
 * accepted: 429 from the shared /api/ rate limiter, a 409 terminal fence, a 4xx,
 * a transient 5xx, a missing credential, or a hard network error), the optimistic
 * user bubble would otherwise sit in the transcript looking delivered forever.
 *
 * This appends the app's EXISTING transcript error row rather than inventing a
 * second error mechanism (INV-3): ChatPanel already detects an assistant turn whose
 * content starts with "Error: " and renders <ErrorMessage> with a Try-Again that
 * re-sends the nearest preceding USER turn (ChatPanel.tsx:210-257). The
 * `[code:…] [recoverable:…]` markers are that surface's parsed contract
 * (ChatPanel.tsx:224-234), already produced by page.tsx:1085-1089.
 *
 * TRANSPORT-AGNOSTIC (the hook must not import the REST client): the HTTP status is
 * read STRUCTURALLY off the thrown value (`ApiError.status`), so any error shape
 * works and a plain Error degrades to the generic, retryable case.
 *
 * Retryable = the request may succeed unchanged on a second attempt: a rate limit
 * (429), a server fault (5xx), or a transport failure (no status). A 4xx that is not
 * 429 is a rejected request — retrying it verbatim cannot help, so the row renders
 * ErrorMessage's non-recoverable copy instead of a Try-Again button.
 */
function failedSendMarker(
  messageId: string,
  runId: string | null,
  err: unknown,
): ChatMessage {
  const raw = (err as { status?: unknown } | null)?.status;
  const status = typeof raw === "number" ? raw : 0;
  const recoverable = status === 0 || status === 429 || status >= 500;
  const cause =
    status > 0
      ? `the server returned ${status}`
      : "it could not reach the server";
  return {
    id: `send-error:${messageId}`,
    chatSessionId: runId ?? "",
    role: "assistant",
    content:
      `Error: Your message was not sent — ${cause}.` +
      ` [code:send_failed${status > 0 ? `_${status}` : ""}]` +
      ` [recoverable:${recoverable}]`,
    createdAt: new Date().toISOString(),
    runId: runId ?? undefined,
  };
}
```

##### I6. Ripple-effect analysis - why nothing else breaks

Assuming the fix is wrong, here is where it would break.

**1. Unhandled promise rejections (the biggest risk).** Enumerated exhaustively in I4-A: exactly two
callers. Caller 2 gets the `try/catch` (step 2b); caller 1 gets the `.catch` (step 4). A third caller
appearing later would be an unhandled rejection - mitigated by the contract comment at the top of
`sendCommand` and by the type signature staying `Promise<string | null>` (a caller that awaits it in
an async fn already has to think about rejection).

**2. Breaking the streaming Concierge reply.** The only structural change inside the OK path is
dropping the now-redundant `res.ok &&` from `:414` (a non-2xx already threw) and wrapping the drain
in `try/catch`. Proved safe by reading every `return` in `run_commands.py post_message`: an
`EventSourceResponse` is only constructed at `:1414` on the success path. A mid-stream read error
now degrades to a warn + the DEF-44-12-2 re-fetch instead of an unhandled rejection - strictly
better, because the server's driver task is explicitly not cancelled on client disconnect
(`run_commands.py:1394-1403`, `_CONCIERGE_STREAM_TASKS`).

**3. A stuck or double "thinking" spinner.** On the settled-run ASK path `RunChatLane` sets
`replyPending = true` before `sendMessage` (`:1152`). The marker is `role: "assistant"`, so the effect
at `:1018-1022` clears the spinner as soon as it lands - the user waits ~1 network round-trip instead
of the 45s `REPLY_PENDING_TIMEOUT_MS` safety net. `ChatPanel`'s TypingIndicator gate
(`:434-438`) also hides once the tail is an assistant turn. **Both improve; neither breaks.** The 45s
net stays as belt-and-braces for the "200 but no reply ever arrives" case.

**4. Transcript ordering / duplicate rows.** The marker is appended in the same microtask as the
rejection, strictly after the optimistic bubble (which was appended synchronously in `sendMessage`).
Order is always `[... , user turn, error row]` - exactly what `ChatPanel`'s Try-Again walk-back
(`:246-251`) needs. Double-append is impossible: the `prev.some(m => m.id === marker.id)` guard plus
the derived `send-error:{messageId}` id (React StrictMode double-invokes the IIFE only if
`sendMessage` itself is called twice, and then `messageId` differs).

**5. Concurrency / ordering with two rapid sends.** Each `sendMessage` mints its own `messageId`, so
two failing sends produce two distinct markers interleaved correctly with their user turns. Two sends
where the first fails and the second succeeds produce
`[user1, error1, user2, reply2]` - correct.

**6. Two browsers / A2 event stealing.** Irrelevant: the marker is local client state derived from
this client's own POST response, not from the shared `_PIPELINE_QUEUES` fan-out. A2's fix does not
interact.

**7. Run switching, resume, reopen, revision, fan-out.** `seedTranscript` (`useRunChat.ts:533-544`)
clears `messages` on an explicit history-open and on a fresh non-revision launch
(`page.tsx:1940`, BUG-021), so a stale marker never leaks across runs. A *revision* launch
deliberately does not clear (BUG-021 lock) - correct, since the family transcript accumulates and a
prior failed send is genuine history. Fan-out and resume never touch the chat transcript.

**8. Crashed run / unattached client / slow client.** All of these change what the *stream* delivers,
not what the *POST* returns. D2's branch keys only on the POST's own status.

**9. Memory / connection pool.** Nothing added. The `res.json()` on the error path consumes a body
that today is left undrained (a micro-improvement for connection reuse, not a regression).

**10. Partial application.** If only step 1 lands (throw, no callers updated) -> unhandled rejections
on both paths and no marker: **worse than today**. If only step 2 lands (catch, no throw) -> dead
code, no behaviour change, harmless. **Therefore steps 1, 2 and 4 must be ONE commit.** Step 3 (the
testid) and step 5 (tests) can be separate.

**11. The 401 throw on a missing token.** `getToken()` reads `localStorage` synchronously
(`api.ts:24-26`) and returns null only when genuinely signed out or during SSR. `sendCommand` is only
ever called from a user gesture on the client, so a null token there means "signed out" - which is
exactly what the marker should say. Verified there is no boot window where a signed-in user's
`sendCommand` could see a null token: `RunConnectionProvider` mounts and the dashboard requires auth
before rendering a composer.

less likely once A1 lands". I checked and **partially disagree** - A1 exempts only the stream URL and

##### I12. Shortcuts and alternatives explicitly rejected

**R-1. Add a `failed?: boolean` to `ChatMessage` and render a failed-state user bubble.**
Tempting because it marks the *actual* failed turn rather than appending a sibling row. Rejected:
`ChatPanel.tsx:210-257` already owns the transcript's error presentation, including a Try-Again that
re-sends the preceding user turn. A second error presentation on the user bubble would be two
mechanisms for one concept - the exact INV-3 dual-implementation the project treats as
"phase not done". It would also need a new `MessageBubble` variant, a new `ChatMessage` field and a
new retry wiring, all duplicating what already exists.

**R-2. Return a discriminated union `{ok: true, runId} | {ok: false, error}` instead of throwing.**
Rejected on two counts. (a) It changes `RunConnectionContextValue.sendCommand`'s public type, forcing
edits in `useWorkflow.startPipeline`'s return type, `UseRunChatConfig.sendCommand`'s type, the
`page.tsx` adapter, and `DEFAULT_VALUE` - a much larger diff for the same outcome. (b) It would be a
*third* error convention in a codebase that already has exactly one
(`throw new ApiError(status, detail)`, `api.ts:113-117`, repeated at six more sites) - INV-12.

**R-3. Only fix the `/messages` branch; leave the launch branch's `return null`.**
Genuinely tempting: it halves the blast radius and D2's title is about a *chat message*. Rejected
because it leaves one function with two contradictory contracts ("not-OK throws, except when it
doesn't"), which is precisely the ambiguity that created the bug - `return null` already meant two
things. The cost of doing it properly is one `.catch` at one call site (step 4), and that `.catch` is
explicitly behaviour-preserving, so it buys correctness for free.

**R-4. Also wrap `sendCommand` in the `api.ts` 30s `AbortController` (BUG-013 Part B parity).**
Rejected with a concrete failure: the fresh-Concierge `/messages` response is an `EventSourceResponse`
held open for the *entire* streamed reply (`run_commands.py:1414`). A blanket 30s abort would
truncate every reply longer than 30s mid-sentence and, worse, would then look like a *failed send*
even though the durable `chat_reply` row was written. The correct shape would be a
response-*headers* timeout that stops once streaming begins - real, but a separate design with its
own tests. Note the pool-starvation hazard BUG-013 identified is genuinely reduced by A1 (fewer
stream sockets held), so the pressure for this is lower than it was.

**R-5. Auto-retry the send on 429 with backoff.**
Rejected. A retry loop on a *user-authored message* risks duplicate delivery (the backend's
`message_id` idempotency covers the durable row, but a duplicate `CHANNEL_REVISION` dispatch would
mint a second revision run - exactly FIX-118's bug class). And an invisible retry keeps the user
uninformed, which is the defect. The existing Try-Again puts the retry decision with the user, where
FIX-118/119 already established it belongs.

**R-6. Roll the optimistic "Running" screen back on a failed launch, inside D2.**
Rejected as scope. It is a real defect (Phase-51 carry-forward finding 2) with a real product
decision behind it (reset to home? keep the screen with an error banner? what about the already
-cleared preview content at `page.tsx:1920-1941`?). Folding it in would make D2's own fail-before/
pass-after ambiguous - the reviewer could not tell which change fixed what. Step 4's `.catch` is
deliberately a no-op so the launch path's behaviour is byte-identical to today.

**R-7. Make `DEFAULT_VALUE.sendCommand` throw too.**
Rejected: it is the documented inert no-provider stub (`RunConnectionProvider.tsx:112-116`), and
`layout.tsx:43` mounts the provider above the router, so it is unreachable in the running app.
Throwing there would only break unit tests that render `DashboardLayout`/`useWorkflow` outside the
provider - real cost, zero user-facing benefit.

**R-8. Fix the 6 red `RunConnectionProvider.test.tsx` tests while in the file.**
Rejected. They are red because FIX-137 (`63a8d795c`, 2026-07-29) added the `tabOwnedIds` gate without
updating the suite - a different fix's debt. Repairing them means seeding
`sessionStorage["tab_launched_run_ids"]` in the fixture, which is a judgement call about what
FIX-137's contract should be, not D2's. The brief's rule 8 (stay in your lane) and rule 6 (never
weaken a test) both point the same way. **Report it, do not touch it.** Same for the 9 red
`RunChatLane.test.tsx` tests (FIX-115/116 debt).

**R-9. Delete the now-dead `classifyFreeText` (`RunChatLane.tsx:334-344`).**
Noticed while tracing (`rg -n 'classifyFreeText' src/` returns only the definition; FIX-115/116
superseded it with the server `classifyIntent`). It is genuine INV-3 dead code, but it belongs to
FIX-115/116's cleanup, not D2's, and deleting it would put an unrelated hunk in D2's diff. Reported,
not touched.

**R-10. Sniff the response body / `Server: nginx` header to distinguish an nginx 429 from a FastAPI
429.**
Rejected: brittle, and the *user-facing* answer is identical either way ("not sent, retry"). The
operator-facing distinction is E1's job, server-side, via
`{ $.status = 429 && $.upstream_addr = "-" }` - the right place for it.
