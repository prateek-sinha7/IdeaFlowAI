##### I5. The complete fix

One file, one function, one commit.

**Step 1 (the only production change).** `backend/app/api/run_engine.py`. Anchor: the
function `_cleanup_pipeline`, currently lines 70-73.

BEFORE (exact current text):

```python
def _cleanup_pipeline(pipeline_run_id: str) -> None:
    _PIPELINE_QUEUES.pop(pipeline_run_id, None)
    _PIPELINE_TASKS.pop(pipeline_run_id, None)
    _CANCEL_EVENTS.pop(pipeline_run_id, None)
```

AFTER (exact replacement text):

```python
def _cleanup_pipeline(pipeline_run_id: str) -> None:
    """Drop a run's live registrations AND release anyone attached to its queue.

    A3. Popping ``_PIPELINE_QUEUES`` is only half of "this run is no longer live":
    an SSE client that attached while the entry existed is parked in
    ``run_stream._iter_sse_frames`` at ``await live_queue.get()`` (``run_stream.py:197``)
    holding a direct reference to the queue OBJECT, so the dict pop does not reach it.
    Of the twelve paths that reach this function, only three (the launch driver's
    ``finally`` at ``run_commands.py:2185-2186``, the revision driver's at ``:2488-2489``,
    and ``engine._drive_resumed_stream``'s at ``engine.py:7823+7830``) send the ``None``
    sentinel first; the nine resume/re-arm paths that reach it through
    ``engine._fire_resume_cleanup`` do not, and their attached client hangs until the
    socket drops. Sending the sentinel HERE makes "stop tracking this run" and "release
    its readers" one atomic operation instead of two things every caller must remember.

    The sentinel goes onto the SOURCE queue we just popped, never to a consumer, so it
    QUEUES BEHIND anything still pending: on the three already-sentinelled paths this is
    a harmless second sentinel the reader never reaches (it returns on the first), and no
    tail is truncated. ``put_nowait`` is used because this function is synchronous and is
    called from both sync and async contexts; the queue is unbounded (``maxsize=0``,
    ``_get_or_create_queue``) so ``QueueFull`` is unreachable -- the guard is there only so
    a future bound queue degrades instead of raising inside a cleanup path. The pops stay
    unconditional (Phase-12 WR-01: every exit path must drop the task entry) and the
    function stays idempotent -- a second call pops ``None`` and sends nothing.
    """
    queue = _PIPELINE_QUEUES.pop(pipeline_run_id, None)
    _PIPELINE_TASKS.pop(pipeline_run_id, None)
    _CANCEL_EVENTS.pop(pipeline_run_id, None)
    if queue is not None:
        try:
            queue.put_nowait(None)
        except Exception:  # noqa: BLE001 -- releasing readers must never raise in cleanup
            pass
```

**Nothing to delete (INV-3/INV-12).** There is exactly one implementation of
`_cleanup_pipeline` and it is not superseded -- it is extended in place. No caller changes,
no shim, no second cleanup path. Concretely: I did **not** add a `_close_run`-style sibling,
and I did **not** move the sentinel responsibility out of the two driver `finally` blocks
(see I12 for why removing them would be wrong).

**No config addition.** The fix has no tunable. A knob here would be a knob for "should a
finished run release its readers", which has one correct answer.

**No host-side half.** This is pure repo-side application code; it ships with the normal
CodeBuild -> Docker -> EC2 deploy and is fully durable. Nothing evaporates.

Why `put_nowait` and not `await queue.put(None)`: `_cleanup_pipeline` is `def`, not
`async def`, and two of its callers (`_fire_resume_cleanup`, and `_is_run_live` after A4)
are synchronous. Verified `[V]` that `put_nowait` is safe with no running loop and cannot
raise on an unbounded queue (I12).

Why pop first, then sentinel: popping first closes the window in which a *new* attach could
bind to a queue that is about to be sentinelled. Since there is no `await` between the two
statements, the pair is atomic on the single event loop -- an attacher either sees the entry
(and is released by the sentinel) or does not (and gets `live: false`). There is no third
case. This is the same no-preemption argument the resume overlap mutex at
`run_commands.py:386-390` already relies on.

##### I6. Ripple-effect analysis -- why nothing else breaks

Assume the fix is wrong. Where would it show?

**"The second sentinel truncates the live tail on the launch path."** It cannot. Measured
(`case 5`): with `agent_chunk` -> `None` -> `_cleanup_pipeline`'s second `None` on the queue,
the client received `agent_start, stream_attached, agent_chunk` -- the full tail -- and the
second sentinel was left unread (`leftover_qsize=1`) on a now-unreferenced queue, which is
then garbage-collected. The reader returns on the first `None` (`run_stream.py:198-199`) and
never looks again.

**"The sentinel arrives while the client is mid-REPLAY, so it is lost."** The brief asks
this explicitly. It is not lost, and I measured it (`case 2` vs `case 4`, and the shipping
test `test_cleanup_releases_a_client_still_in_replay`). The endpoint binds `live_queue` to
the queue *object* at `run_stream.py:281` before the generator body ever runs, and passes it
as a parameter. The dict pop does not detach it. The sentinel sits in the queue while the
generator finishes step 1 (durable replay), step 2 (handshake) and step 3 (gate re-arm), and
is consumed at step 4 on the first `get()`. The client receives its complete replay plus the
handshake and then closes cleanly -- exactly what it would have got had it attached one
millisecond later with `live: false`.

**"It releases a client that should still be live."** Only if `_cleanup_pipeline` could run
while a driver is still producing. I enumerated all twelve paths in I3/I4: every one of them
is either a driver `finally` (loop already ended) or a pre-drive early return (loop never
started). After A4, `_is_run_live` adds a thirteenth, gated on `task.done()`, which by
definition means the driver's `finally` already ran. There is no path where a live producer
is racing the cleanup.

**Concurrency and ordering.** The two statements are adjacent and non-awaiting, so on
asyncio's single thread they are atomic. `put_nowait` waking a getter is a synchronous
`future.set_result` on the same loop -- verified `[V]`. There is no cross-loop hazard: every
queue in this process lives on the one uvicorn loop.

**The one real behaviour change, and it is on the frontend.** Today a stranded client sits
in phase `live` forever, receiving nothing, silently. After the fix the stream closes. In
`useRunStream.ts` the close branch (`:395-403`) checks `sawNonLiveAttachRef`. On these nine
paths the client attached while the queue existed, so it saw `stream_attached {live: true}`
and the ref is `false` -> `scheduleReconnect()` fires. The reconnect reattaches, now finds
no queue, receives `stream_attached {live: false}`, sets the ref `true` (`:272`), and the
next close settles quietly at `setPhase("disconnected")` (`:400`). Net effect: **one extra
reconnect round-trip and one brief "Reconnecting..." banner, then a correct quiescent
state**, replacing an indefinite silent hang. That is strictly better -- but it is a visible
change and the executor should expect to see it.

**Interaction with A1 (unfixed).** On `dev` today that single reconnect hits the
rate-limited `/api/` nginx block and may 429 a few times before landing, with the banner
flapping on the `1s -> 2 -> 4 ...` backoff. Still bounded, still self-healing, still better
than a permanent hang -- but it is a reason to prefer landing A1 first (see I10).

**Unattached client.** `queue is not None` but nobody is waiting: the sentinel is appended
to a queue that immediately becomes unreferenced. Zero cost.

**Slow client.** The sentinel queues behind whatever it has not drained. It gets everything,
then terminates. No truncation.

**Crashed run / restart / resume / fan-out / revision / two browsers.** Crashed run: the
driver `finally` still runs, unchanged. Restart: the nine paths are *exactly* the restart
paths -- this is where the fix does its work. Resume: verified by the shipping tests plus
the untouched `test_resume_ws_bridge.py` suite. Fan-out: `run_fanout` workers never touch
`_PIPELINE_QUEUES` (register Phase 11 `:1136`, dossier A2 `[V]`); only the parent run has a
queue. Revision: the child run has its own queue and its own driver `finally` -- unchanged.
**Two browsers: the fix releases only one of them** (measured 1 of 3). This is the A2
dependency, not a regression -- the second browser is no worse off than today.

**Memory and connection-pool effects.** Strictly positive. Each released client frees an
HTTP connection, a generator frame, a session-less `ScopedStore`, and one nginx upstream
slot. The BUG-004 pool-leak fix (`run_stream.py:262-265`, quick `260716-heb`) means the
stranded stream was not holding a DB connection, so there is no pool delta -- but the
`worker_connections 768` budget (Appendix 2) does benefit.

**Partial application.** If the executor applies the pops but not the sentinel, the tree is
byte-identical to today. If they apply the sentinel but drop a pop, WR-01 regresses (task
leak). The diff is four lines; review it as a unit.

**Two paths this fix deliberately does NOT cover** -- stated so nobody thinks A3 closes
them:

1. **An exception escaping `resume_run` past the early returns.** `_compute_resume_offset`
   (`engine.py:7598`) is awaited outside any `try`. If it raises on the user-resume path,
   the exception reaches `_drive_user_resume`'s `except` (`run_commands.py:459-463`), which

**Ship A3 as its own commit.** It is four lines, independently revertable, and independently

##### I12. Shortcuts and alternatives explicitly rejected

**1. Sentinel the subscribers directly instead of the source queue** (the dossier's own
named trap). Rejected, and I verified the premise it rests on rather than taking it on
faith:

```
after `await q.put('A')`      -> pump ran: []
after `await q.put('B')`      -> pump ran: []
after `await q.put(None)` + sync stmt -> pump ran: [] | sync side effect already done
after one sleep(0)            -> pump ran: ['A', 'B', None]
put_nowait x2, no await yet   -> pump2 ran: []
```

`await asyncio.Queue.put(x)` on an unbounded queue performs **zero yields** -- it appends and
returns without ever suspending. So on the launch path `await event_queue.put(None)` at
`:2185` and `_cleanup_pipeline(...)` at `:2186` execute as one atomic step before any pump or
consumer has run. A subscriber-side sentinel would therefore be *appended ahead of* the
entire final flush the pump has not yet forwarded, and every subscriber would return on it,
discarding the tail. **The concrete failure is a truncated `pipeline_complete`** -- the run
would visibly never finish in the UI. The source queue is the only ordering-safe place.

**2. Leave `_cleanup_pipeline` alone and add `await queue.put(None)` at each of the nine call
sites.** Rejected. It is nine edits across two modules instead of one, it re-creates the
exact two-part protocol that produced the bug (the tenth caller added next year forgets
again), and six of the nine sites are in `engine.py`, which would need the queue object --
which it does not have and must not import (`agents.execution_engine.engine -> app.api` is
the forbidden contract). It is not merely uglier; it is architecturally impossible without
a boundary violation.

**3. Give `_iter_sse_frames` a timeout on `live_queue.get()`** (e.g.
`asyncio.wait_for(..., 30)`) so a stranded client eventually gives up. Rejected: it papers
over the missing terminal with a heuristic, it would fire on every legitimate quiet period
(a human review gate can be parked for hours -- `run_stream.py`'s own comment at `:190-191`
says the keepalive ping is what covers idle), and it converts a correctness bug into a
timing bug. It also directly contradicts the Phase-17 locked decision (register `:1778`,
`:1806`) that a clarify/gate wait is deliberately no-timeout.

**4. Have the SSE generator poll `_PIPELINE_QUEUES` membership between `get()` calls.** It
cannot: the generator is *blocked inside* `get()`, so there is nothing between calls. To
poll you would need `wait_for` with a short timeout -- see rejection 3.

**5. Make the queue bounded so the sentinel can be forced.** Rejected on the dossier's own
grounds (A2, verified): bounding the source queue applies backpressure to the engine,
changing pipeline timing, and `kernel_services.emit_hook_event` (`:386`) uses `put_nowait`
and would start raising `QueueFull` mid-run.

**6. Add a sibling `_close_and_release(run_id)` and leave `_cleanup_pipeline` as-is, letting
callers pick.** Rejected as a textbook INV-3/INV-12 dual implementation: two functions, one
correct and one subtly wrong, with nothing forcing a new caller to the right one. That is the
same failure mode as the two-part protocol in rejection 2, dressed as a refactor.

**7. Remove the now-redundant `await event_queue.put(None)` from the two driver `finally`
blocks, since `_cleanup_pipeline` sentinels anyway.** Tempting (it looks like deleting
superseded code, which INV-3 usually demands) and **wrong**. The driver sentinel is
`await ...put(None)` on the queue the driver *owns and is still referencing*; the cleanup
sentinel is `put_nowait` on whatever the registry happened to hold. They are not the same
guarantee: if a future change ever pops the entry earlier (A2's `_close_run` does exactly
this), the cleanup's `queue is not None` branch would not fire and the driver's own sentinel
would be the only thing terminating its readers. Deleting it would make correctness depend
on registry timing. Keep both; the second is provably harmless (measured, `case 5`).

**8. Fix the four `_StubEngine` reds in `test_rest_resume.py` while in the neighbourhood.**
Rejected for this commit. They are real (a missing `_state_machine` on a test double, drifted
since FIX-105) and worth a one-line follow-up, but folding them in would mean A3's commit no
longer has a clean "same 7 failures before and after" delta, which is the whole proof that
A3 regresses nothing.
