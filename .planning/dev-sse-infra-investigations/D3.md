##### I3. Root cause — confirmed, corrected, or replaced

**The dossier's mechanism is correct.** nginx's `add_header` is inherited from an outer configuration
level **if and only if** no `add_header` is declared at the current level — replace, not merge.
`location /_next/static/` declares `add_header Cache-Control` at `:912`, which discards all five
server-level `add_header` directives from `:791/792/797/798/799`.

I did not take that on faith. **Reproduced on nginx 1.24.0** — the exact version on the dev box —
in a throwaway container (`nginx:1.24-alpine`, already cached locally), with a fake Next.js upstream
that sets `Cache-Control: public, max-age=31536000, immutable` and `X-Powered-By: Next.js` just as
the real one does. Full matrix [V]:

duplicate `Cache-Control` today.** The dossier does not mention this. Next.js 16.2.4 sets the header
itself. Proof, from the installed dependency
(`frontend/node_modules/next/dist/server/lib/router-server.js:394-400`) [V]:

```js

    if (opts.dev && !isNextFont(parsedUrl.pathname)) {
        res.setHeader('Cache-Control', 'no-cache, must-revalidate');
    } else {
        res.setHeader('Cache-Control', 'public, max-age=31536000, immutable');

```

`nextStaticFolder` is everything under `/_next/static/`, and prod is not `dev`

value is **byte-identical** to the nginx one. `add_header` *appends* — it never replaces an upstream
header — so today every `/_next/static/` 200 carries the header twice. That is measured live and
reproduced locally. Consequence: **deleting `:912` costs nothing** and is strictly better than the
dossier's two suggestions.

**Correction 2 — the loss is not confined to 200s.** Measured: the drop also applies to **304 Not
Modified** (the common repeat-visit path, which the browser hits for every hashed asset it already
has) and to an upstream **404**. The dossier's one-line symptom understates the reach.

**Correction 3 — `always` is not what is broken.** The location's `add_header Cache-Control` has no

`add_header` at the level, not whether it fires, is what disables inheritance. This kills a
plausible-looking "fix" (adding `always` to `:912`) before anyone tries it.

**Causal chain, end to end.**

1. `27483e6a` (2026-05-11) adds a security-header block at server level and, in the same commit, a

3. The effect is invisible from the app: the page itself (`/login`) carries all five, so any

4. It has never been observable from inside either, because nginx access logs are not shipped (B1)

5. It survived `0e9c410e` and `e1a3a495` because neither author had reason to look at the other block.

##### I5. The complete fix

Three ordered steps. Steps 1 and 2 are the repo (durable); step 3 is the running box (evaporates on
instance replacement or a bootstrap re-run — see I9).

###### Step 1 (commit 1) — delete the redundant directive. This alone closes D3.

File: `infra/scripts/bootstrap-ec2.sh`. Anchor: the `location /_next/static/` block, currently
lines 908-913.

**BEFORE**

```nginx
    location /_next/static/ {
        proxy_pass         http://velocityai_frontend;
        include            /etc/nginx/snippets/velocityai-proxy-headers.conf;
        proxy_cache_valid  200 1y;
        add_header Cache-Control "public, max-age=31536000, immutable";
    }
```

**AFTER**

```nginx
    # Hashed, content-addressed assets. Deliberately declares NO add_header:
    # nginx's add_header is REPLACE-NOT-MERGE across levels, so a single
    # add_header here silently discards every security header inherited from
    # the server block (measured 2026-07-30: 0 of 5 on every .js/.css, on 200,
    # 304 and 404 alike). The immutable Cache-Control this block used to set is
    # already emitted by the upstream itself - Next.js
    # router-server.js sets "public, max-age=31536000, immutable" for every
    # nextStaticFolder output - so nginx was only ever duplicating it.
    # proxy_cache_valid was inert: no proxy_cache zone exists anywhere.
    # If this block ever genuinely needs an add_header, it MUST also carry
    #   include /etc/nginx/snippets/velocityai-security-headers.conf;
    location /_next/static/ {
        proxy_pass         http://velocityai_frontend;
        include            /etc/nginx/snippets/velocityai-proxy-headers.conf;
    }
```

Why delete rather than re-declare: measured, the upstream already sends the byte-identical
`Cache-Control`, so the directive adds nothing and currently produces a duplicate header. Why also
drop `proxy_cache_valid`: it is provably inert (no `proxy_cache` zone in the repo) and wiring one
would be actively harmful — see I11/I12.

###### Step 2 (commit 2) — move the five headers into a snippet. One source, no second copy.

This is a **move**, not an addition (INV-3/INV-12): the inline directives are deleted in the same
change. Proven byte-equivalent — a server-level `include` of the snippet yields the identical 5/5
[V].

**2a.** Insert a new heredoc immediately after the existing proxy-headers heredoc (after `:726`,
before the comment at `:728`):

```bash
# Response security headers, in a snippet so there is exactly ONE copy.
# nginx's add_header is REPLACE-NOT-MERGE across configuration levels: any
# location that declares its own add_header silently discards every add_header
# inherited from the server block. Keeping the set in one file means such a
# location can restore them with a single include line instead of a divergent
# copy of a 400-character CSP.
#
# NOTE the heredoc is UNQUOTED on purpose - ${DOMAIN} must expand at install
# time. There are deliberately NO nginx variables in this file; a $host or
# $scheme here would be eaten by bash. (Contrast the proxy-headers snippet
# above, which is QUOTED precisely because it is full of nginx variables.)
cat > /etc/nginx/snippets/velocityai-security-headers.conf <<EOF
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
add_header X-Content-Type-Options "nosniff" always;
# SAMEORIGIN (not DENY): the prototype/ppt template + design-system galleries
# embed their own /api/.../preview endpoints in same-origin <iframe>s. DENY
# blocks all framing (incl. same-origin), which renders the previews blank.
# SAMEORIGIN keeps cross-origin clickjacking protection (CSP frame-src is 'self').
add_header X-Frame-Options "SAMEORIGIN" always;
add_header Referrer-Policy "strict-origin-when-cross-origin" always;
add_header Content-Security-Policy "default-src 'self'; img-src 'self' data: blob:; font-src 'self' data:; style-src 'self' 'unsafe-inline' https://cdnjs.cloudflare.com; script-src 'self' 'unsafe-inline' 'unsafe-eval' https://cdn.jsdelivr.net https://cdnjs.cloudflare.com; connect-src 'self' https://\${DOMAIN} wss://\${DOMAIN}; frame-src 'self' blob:" always;
EOF
```

The `\${DOMAIN}` escaping is deliberate and load-bearing. This new heredoc is nested inside no other
heredoc, so `${DOMAIN}` would expand unescaped — which is what we want. **Verify after editing that
the rendered snippet on disk contains the literal FQDN and not the string `${DOMAIN}`**; that is the
single thing most likely to be got wrong here, and it is the exact quoted-heredoc trap E3 documents
at `:1105-1106`. (If the executor writes the heredoc without any backslash, `${DOMAIN}` expands at
`cat` time — correct. The backslash form above is for the case where this text is itself pasted
inside another expanding context; pick one and check the rendered file.)

**2b.** Replace lines `791-799` of the site heredoc:

**BEFORE**

```nginx
    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
    add_header X-Content-Type-Options "nosniff" always;
    # SAMEORIGIN (not DENY): the prototype/ppt template + design-system galleries
    # embed their own /api/.../preview endpoints in same-origin <iframe>s. DENY
```

###### Step 3 (commit 3, or fold into A1's) — the standing guard.

The snippet makes the remedy one line; it does **not** make the mistake impossible, because an
`include` is opt-in. What makes it *detectable* is an assertion. Add this to the same place A1's
apply script lives (and, per C1's "later" half, to `infra/scripts/reconcile-host-config.sh` once it
exists):

```bash
# Header-parity ratchet. A location that declares its own add_header silently
# drops every inherited security header (D3). Assert the invariant instead of
# trusting the convention. Run AFTER `systemctl reload nginx`.
assert_security_headers() {
  local base="$1" path="$2" n
  n=$(curl -sSk -o /dev/null -D - --max-time 10 "$base$path" \
      | tr -d '\r' \
      | grep -icE '^(strict-transport-security|x-content-type-options|x-frame-options|referrer-policy|content-security-policy):')
  if [ "$n" -ne 5 ]; then
    echo "FATAL: $path returned $n/5 security headers (expected 5)" >&2
    return 1
  fi
  echo "OK: $path 5/5 security headers"
}

BASE="https://${DOMAIN}"
ASSET=$(curl -sSk --max-time 10 "$BASE/login" \
        | grep -oE '"/_next/static/[^"]+\.(js|css)"' | tr -d '"' | head -1)
[ -n "$ASSET" ] || { echo "FATAL: could not discover a /_next/static asset" >&2; exit 1; }
assert_security_headers "$BASE" /login   || exit 1
assert_security_headers "$BASE" "$ASSET" || exit 1
```

##### I6. Ripple-effect analysis — why nothing else breaks

Assume the fix is wrong. Where would it show?

- **A browser rejects an asset it used to accept.** The only header with a blocking mode is
  `nosniff`, and it blocks only on a wrong `Content-Type` for a script or stylesheet destination.
  Measured: `.js -> application/javascript`, `.css -> text/css` [V]. Correct. Fonts and maps are not
  nosniff-blocked destinations.
- **The CSP breaks something.** It cannot: a CSP on a subresource is not enforced against the
  loading document, and the only enforcing consumer (a worker) is proven absent [V]. The document's
  CSP is unchanged — this fix does not touch the policy string, only where it is *also* emitted.
- **Caching regresses and every page load re-downloads the bundle.** The single most important
  ripple, and it is measured away: the upstream sets the identical `Cache-Control` unconditionally
  for `nextStaticFolder` (`router-server.js:394-400` [V]), and the live response proves it arrives
  (the duplicate is *both* copies). After the fix the client sees exactly one
  `public, max-age=31536000, immutable`. Same value, same semantics, one fewer header. Verify with
  the `cc=1` assertion in I8.
- **`proxy_cache_valid` removal changes caching.** It cannot: there is no `proxy_cache` zone
  anywhere in the repo [V], so nginx has been ignoring the directive since 2026-05-11.
- **Concurrency / ordering.** None. `add_header` is evaluated per-response in the header filter
  chain; there is no shared state, no queue, no task.
- **Startup / shutdown.** `nginx -t` runs in a throwaway process against the on-disk config; a
  failed validation leaves the running master's in-memory config untouched, so downtime on a bad
  edit is zero (A1 establishes this and it applies unchanged here). A successful `reload` forks new
  workers and drains the old ones — **in-flight SSE streams on the old workers are not cut**; nginx
  keeps old workers alive until their connections close (`worker_shutdown_timeout` default is
  unlimited). So a reload during an active run does not kill the stream. [I] on the exact drain
  semantics for this box's `worker_shutdown_timeout` (not set in the repo, so the default applies).
- **Unattached client / slow client / crashed run / restart / resume / fan-out / revision / two
  browsers.** All of these are A2/A3/A4/A5 territory on `/api/runs/*/events/stream`. This change
  touches only `/_next/static/`, which serves static files from the Next.js process and participates
  in no run lifecycle. Zero interaction.
- **Memory / connection pool.** None. No upstream behaviour changes; the same `keepalive 32` pool to
  `velocityai_frontend` is used identically.
- **Partial application.** The two `sed` deletes are independent and each idempotent. If only the
  `add_header` delete lands, D3 is fixed and an inert `proxy_cache_valid` survives — harmless. If
  only the `proxy_cache_valid` delete lands, nothing changes at all (still 0/5). If step 2 lands
  without step 1, the location still declares `add_header` and is still 0/5 — the snippet does not
  fix it on its own (measured: `add_header` + server-level `include` still yields 0/5 at the
  location [V]). **So step 1 is the load-bearing one and must not be skipped.**
- **Someone reverts only the repo half.** Then the box keeps the fix until it is rebuilt, and the
  rebuild silently reintroduces D3. This is C1's structural problem, not a defect of this fix — but
  it is why the guard in step 3 belongs in the reconcile path, not only in a one-off script.

Where the dossier already argues safety, I verified rather than restated: its "either re-declare or
snippet" both work (measured, 5/5 each) — I am rejecting one of them for a reason it did not state,
not because it is wrong.

```bash

# Fail-before / pass-after harness for D3. Requires docker + a local nginx:1.24-alpine image.

sec_block() {

    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;

probe() {  # $1 = path -> "<sec-count> <cache-control-count>"

    2>/dev/null | tr -d '\r' | sed -n '1,/^$/p' > "$T/h"

}

echo "AFTER  -> $(run after)"
```

##### I11. Open questions requiring a human decision

**1. `proxy_cache_valid 200 1y` — remove (recommended) or wire a real `proxy_cache`?**
The dossier says "worth removing or wiring while in the file" without choosing. I recommend
**remove**, and the choice has a real cost side, so it is a decision rather than a detail:

- *Remove* (recommended). It is provably inert today [V]. The assets are content-hash-immutable and
  already carry `public, max-age=31536000, immutable`, so the browser cache already does this job.
- *Wire it* would mean adding `proxy_cache_path` + `proxy_cache` + a key. Costs: (a) it stores a
  second copy of every build's JS/CSS on the **root volume, which has zero snapshots and
  `delete_on_termination = true`** — the one disk with no rollback; (b) every deploy mints new
  hashed filenames, so the cache accumulates the union of all past builds until `max_size` evicts —
  the same unbounded-growth shape as D6; (c) the "origin fetch" it would save is a loopback read
  from `127.0.0.1:3000` of a file already in the OS page cache, and no latency problem has been
  measured; (d) it adds stale-asset and cache-lock failure modes for zero gain. If asset delivery
  ever needs caching, the right layer is a CDN in front of nginx, not a disk cache on the app box.

**2. Should the step-3 header assertion become a deploy gate?**
Making it a gate means a failing assertion fails the build. That is the right posture for a security
invariant and it matches B5's "a deploy that touches the agent must fail the build when the agent is
not running afterwards". But it puts a network probe of the live box in the deploy path, which can
fail for reasons unrelated to the change. Recommendation: **run it and fail loudly in the reconcile
script** (which only runs when host config is being changed), and **log-only** in the steady-state
container deploy. Needs whoever owns C1's pipeline half to agree.

No other open decisions. Nothing here changes product behaviour, costs money, or needs a mailbox
owner.

   already changed once: `0e9c410e` flipped `DENY` to `SAMEORIGIN`). Under this project's own
   INV-3/INV-12 that is a dual implementation. It also leaves the duplicate `Cache-Control` in place.

2. **Keep `add_header Cache-Control` and add `include .../velocityai-security-headers.conf`**
   (the dossier's second option, applied without deleting). Works — measured 5/5. Rejected because
   the directive it preserves is provably redundant: the response still carries `Cache-Control`
   **twice** (measured), and a directive whose only effect is to duplicate an upstream header and
   disable inheritance has no reason to exist. Strictly dominated by deleting it.

3. **Add `always` to the location's `add_header Cache-Control`.** The most plausible-looking wrong
   fix, because `always` is what makes the *server-level* headers appear on errors. It does nothing
   for inheritance: `always` selects which status codes a header is emitted for; it does not affect
   whether the level inherits. Proven by the 404 case — the non-`always` directive does not fire
   there (one `Cache-Control`, from upstream) yet inheritance is **still** killed (0/5) [V].

4. **Move the five `add_header` directives to `http{}` level** (into
   `conf.d/velocityai-limits.conf`). Rejected: the replace-not-merge rule is evaluated level by
   level, so a location's `add_header` still wins over an `http`-level set — the bug survives
   unchanged. It would additionally apply HSTS to the plaintext :80 server, where the client must
   ignore it. [I] on the http-level measurement specifically; the rule is the same documented one
   and I measured the server->location case directly.

5. **Use `more_set_headers` (headers-more-nginx-module), which merges instead of replacing.**
   Rejected: the module is not in Ubuntu's stock `nginx` package. Installing it means switching to
   `nginx-extras` or a custom build on a box that **cannot be re-provisioned** (C1) and whose root
   volume has no snapshot. A packaging change to work around a five-line config rule is not
   proportionate.

6. **Set the five headers in Next.js `next.config.ts` `headers()` instead of nginx.** Rejected:
   every non-Next path — `/api/`, `/health`, `/openapi.json`, `/mcp/`, `/install/`, `/ws/handoff/` —
   would lose them, and the paths nginx also covers would get duplicates. It moves a
   perimeter-wide security control into one of the two upstreams. Also, two CSP headers on one
   response are enforced as the **intersection**, so a future divergence between the two sources
   becomes a silent, hard-to-diagnose breakage rather than a visible one.

7. **Wire a `proxy_cache` zone rather than deleting `proxy_cache_valid`.** Rejected on the grounds
   in I11 (unsnapshotted disk, unbounded growth across builds, no measured latency problem, new
   failure modes). Recorded as an open decision rather than a unilateral one because the dossier
   left it open.

8. **Fix only the repo and wait for the next provision.** Rejected: C1 proves dev will never re-run
   `bootstrap-ec2.sh` on its own — its live userData is 68 lines with no `velocityai-firstboot`
   service and `/var/lib/velocityai/.bootstrap-done` does not exist. The box would stay 0/5
   indefinitely. Both halves are required.

9. **Fix only the box and skip the repo commit.** Rejected: the change evaporates on instance
   replacement (root volume `delete_on_termination = true`, zero snapshots) or on any deliberate
   bootstrap re-run, and stage/prod would never get it.

10. **Add the snippet without deleting the inline directives** (i.e. create the file and include it
    while `:791-799` remain). Rejected outright — that is literally two copies of the header set,
    the INV-12 violation the snippet is supposed to prevent. The extraction is a move or it is not
    worth doing.

11. **Skip the snippet and rely on a comment.** Tempting, since after step 1 no location needs the
    include and a snippet with exactly one consumer looks like pure indirection. Rejected on
    balance: the snippet costs nothing (proven byte-equivalent [V]), and it is what turns A1's
    hazard — and every future location's — from "copy the CSP correctly" into one line. But it is
    the weakest of the three commits and is the one to drop first if the change must be minimised.

**One trap worth recording for whoever executes this**, because it cost me a measurement: extracting
an asset URL from the HTML with a bare character class
(`grep -oE '/_next/static/[A-Za-z0-9._/-]+'`) produces truncated and merged paths such as
`/_next/static/chunks/03` and `/_next/static/chunks/02i7dfk78`. Anchor on the surrounding double
quotes (`grep -oE '"/_next/static/[^"]+"'`) or the verification probes hit URLs that do not exist
and report a misleading 404.
