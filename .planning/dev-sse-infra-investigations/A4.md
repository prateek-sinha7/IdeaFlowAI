##### I3. Root cause -- confirmed, corrected, or replaced

**Confirmed:** dict membership is the liveness signal at exactly two production sites, and a
surviving entry with no live driver is indistinguishable from a live run. Both symptoms are real,
reachable, and permanent for the process lifetime.

**Corrected, correction 1 -- the named raise sources cannot raise.** The dossier says the leak is
"if anything between `:7594` and `:7704` raises -- `_compute_resume_offset`, the durable-tail read,
`get_pipeline_agents`". All three are wrapped:

```python
def _is_run_live(run_id: str) -> bool:
    """True iff ``run_id`` has a LIVE in-process driver task.

    Replaces the two ``run_id in _PIPELINE_QUEUES`` membership tests that treated a
    surviving registry entry as proof a run is live. Membership is NOT liveness: a
    driver that raises before its cleanup runs (``engine.resume_run``'s unguarded DB
    read; a ``CancelledError`` at any of its pre-drive awaits) leaves the queue + task
    entries behind for the process lifetime, which made the run permanently
    un-attachable (the SSE attach blocks on a queue nobody feeds) and permanently
    un-resumable (``POST /{id}/resume`` -> 409 forever).

    The authoritative signal is the DRIVER TASK, because every one of the seven
    registration sites registers the queue and the task with NO ``await`` between them
    (run_commands.py :399/:421, :991/:1003, :1204/:1216, :1775/:1796, :2383/:2395;
    engine.py :5372/:5388, :5440/:5457) -- so on a single-threaded event loop a
    registered queue is never observable without its task. And every driver's cleanup
    (``_cleanup_pipeline`` / the engine's injected ``_fire_resume_cleanup``) runs INSIDE
    the driver, i.e. strictly before its task transitions to ``done()``. A ``done()``
    task whose registry entries survive is therefore unambiguously stale.

    SIDE EFFECT (deliberate, and the reason this is not named ``_run_is_live``): a stale
    registration is SELF-HEALED here via ``_cleanup_pipeline`` -- the single registry
    teardown (INV-12). After A3, ``_cleanup_pipeline`` also sentinels the run's pump, so
    the heal additionally releases any client already blocked on the orphaned queue.

    Fail-safe: anything we cannot PROVE is finished is reported LIVE. A task object with
    no callable ``done`` (``tests/unit/test_rest_resume.py:260`` seeds a bare ``object()``
    sentinel and expects the overlap mutex to still return 409) and a ``done()`` that
    raises both take the live branch -- never self-heal something whose state is unknown.

    SC-001: keyed on ``run_id`` only. No workflow name, no pipeline type.
    Synchronous by contract: ``resume_run_endpoint``'s double-POST atomicity argument
    (run_commands.py:346) requires NO ``await`` between the overlap mutex and the
    registration that closes it. Do not make this a coroutine.
    """
    task = _PIPELINE_TASKS.get(run_id)
    if task is not None:
        done = getattr(task, "done", None)
        if not callable(done):
            # Un-introspectable sentinel -> assume live (never heal what we cannot prove).
            return True
        try:
            finished = bool(done())
        except Exception:  # noqa: BLE001 - an unreadable task is treated as live
            return True
        if not finished:
            return True

    # Not live. Self-heal any surviving registration. Evidence is the QUEUE or TASK entry
    # only -- NOT _CANCEL_EVENTS: ``launch_run`` registers the cancel event at :1734
    # before the queue at :1775, so a lone cancel-event entry is a legitimate mid-launch
    # state, not staleness. ``_cleanup_pipeline`` pops all three, which is correct once a
    # queue/task entry has proven the run dead.
    if run_id in _PIPELINE_QUEUES or run_id in _PIPELINE_TASKS:
        logger.warning(
            "stale run registration self-healed: run=%s task_present=%s "
            "task_done=%s queue_present=%s",
            run_id,
            task is not None,
            None if task is None else getattr(task, "done", lambda: None)(),
            run_id in _PIPELINE_QUEUES,
        )
        _cleanup_pipeline(run_id)
    return False
```

*Why the fail-safe direction is "live", not "not live":* `test_resume_already_running_409` is green
today and seeds a bare `object()`. If the fallback returned `False`, `_is_run_live` would pop that
sentinel and the endpoint would return 200 instead of 409 -- a genuine regression of a passing test
and, worse, of the double-POST mutex. The dossier says the `getattr`/`callable` shape "preserves
that" but does not say which way the fallback resolves; it must be **live**.

*Why the log line and not silence:* D11 established that this whole module is unobservable. A
self-heal is the one place in the fix where the system silently changes a run's fate; it must leave a
trace. The extra `getattr(task, "done", lambda: None)()` in the log arguments is safe because that
branch is only reached when the task is absent or `done()` already returned truthy without raising.

##### I6. Ripple-effect analysis -- why nothing else breaks

Assuming the fix is wrong, where does it break?

**Concurrency and ordering.** `_is_run_live` performs `dict.get`, `task.done()`, two `in` tests and
possibly `_cleanup_pipeline` -- all synchronous, no `await`, no lock. On a single-threaded event loop
it cannot interleave. The `resume_run_endpoint` atomicity argument therefore survives verbatim: steps
3 through 7 remain one uninterrupted synchronous block. If a future refactor makes `_is_run_live`
async, that argument silently breaks -- hence the docstring warning and the I8 source-lock test.

**The genuinely-live-but-unregistered-task inversion.** Covered in I4.2: only reachable if
`_register_resume_task` raises, which two dict assignments and an `asyncio.Event()` cannot do. If it
somehow did, the heal pops a live run's queue -> the driver pushes into an orphaned object -> attached
clients get `live:false` on the next attach and fall back to durable replay. Degraded, not corrupting
(persistence precedes publication -- `engine.py` `sink.persist(...)` before `live_queue.put_nowait`,
`_drive_resumed_stream:7774` then `:7781`). The warning log names the run.

**A task that is `done()` while the run legitimately continues.** Is there any driver whose task
finishes while the run keeps emitting? Checked all seven: `_drive_launch_to_queue`,
`_drive_revision_to_queue`, `_rearm_gate_run`, and `_drive_resumed_stream` each push the `None`
sentinel and call `_cleanup_pipeline` in a `finally` *before* returning, so by the time the task is
`done()` the registry is already empty and `_is_run_live` returns `False` without healing anything.
`_drive_user_resume` finishes only after `await engine.resume_run(...)` returns, by which point
`_drive_resumed_stream`'s `finally` has cleaned up. **No driver outlives its own registry entries.**

**The brief window where cleanup has run but the task has not finished.** `_drive_resumed_stream`'s
`finally` pops at `:7830`, then still `await`s `_resume_output_persist_sink` at `:7857`, then returns
into `resume_run`, then into `_rearm_gate_run`/`_drive_user_resume`. During that window: no queue, no
task entry -> `_is_run_live` returns `False` with **no** heal (nothing to pop) -> an attach gets
`live:false` + durable replay. Identical to today's behaviour (`workflow_id in _PIPELINE_QUEUES` is
also False). No delta.

**Unattached client / slow client / crashed run.** `_is_run_live` runs once per attach and once per
resume POST; it holds no state and does not interact with subscriber pacing. A2's eviction path is
independent.

**Restart.** Module-level dicts are per-process; a restart empties them. `_is_run_live` on a fresh
process returns `False` for everything and heals nothing. `restore_non_terminal_runs` then registers
what it spawns. No cross-restart interaction.

**Resume.** The main beneficiary. One subtlety worth stating: after the heal, `POST /{id}/resume`
proceeds to step 4 and re-registers the queue. If the *original* driver were somehow still alive
(the inversion above), two drivers would now write to two different queue objects. Bounded by the
same unreachability argument; and `_stamp_resume_marker`'s double-drive guard is a second line.

**Fan-out run.** `run_fanout` workers are `subagent_runs` rows, never `workflow_runs`, and never
register in `_PIPELINE_QUEUES` (IMPL-REG `:1140` "Children are `subagent_runs` rows, NEVER
`workflow_runs` rows"). One registry entry per parent run. No delta.

**Revision run.** A revision is a child `workflow_runs` row with its own `child_run_id` registration
(sites 2/3/5) and its own `_drive_revision_to_queue` `finally`. Independent key. No delta.

**Two browsers.** Both call `_is_run_live` on attach. The first may heal; the second then finds
nothing and also returns `False`. Both get `live:false` + replay. Idempotent -- `_cleanup_pipeline` is
three `pop(..., None)` calls. This is also the A2 interaction: under A2, `subscribe()` returns `None`
for both, so neither is added to the subscriber set and no pump starts for a dead run.

**Memory / connection pool.** Strictly better. Today a poisoned run accumulates one held HTTP
connection + one suspended generator frame per attach attempt, and the orphaned unbounded queue grows
forever if any producer still writes to it. After the fix each attach terminates. The pool-leak guard
`test_run_stream_pool_leak.py` covers the connection side and is unaffected (I4.4).

**Partial application.** If Step 1 lands without Steps 2-3, `_is_run_live` is dead code (harmless, but
vulture may flag it -- the repo pins `vulture` per IMPL-REG `:225`; add it to the allow-list or land
the steps together). If Step 2 lands without Step 3, the SSE symptom is fixed and the 409 persists.
If Step 3 lands without Step 2, the reverse. Neither ordering corrupts anything. **Land all three.**

##### I12. Shortcuts and alternatives explicitly rejected

**Rejected, and why -- specific failure, not "it is a hack":**

1. **Call `task.done()` directly instead of `getattr` + `callable`.** `tests/unit/test_rest_resume.py:260`
   seeds `_PIPELINE_TASKS[run_id] = object()`; `object().done()` raises `AttributeError`, which

   `test_resume_already_running_409` -- currently green -- goes red. Measured: that test passes today

2. **Make the `getattr` fallback return "not live".** Same test: `_is_run_live` would pop the sentinel
   and the endpoint would answer 200. Worse than the AttributeError, because it silently defeats the
   double-POST mutex for any non-`asyncio.Task` value.
3. **Keep membership but add a TTL / timestamp / grace period.** Re-introduces a window in which a
   stale entry is honoured -- i.e. the bug, shortened. Also needs a new per-run timestamp dict (a
   fourth registry, INV-12) and a clock to tune. The task's `done()` is exact and already exists.
4. **Sweep the registries on a timer (a janitor task).** Adds a background task to a process that
   currently has none, needs its own shutdown handling (which D8 shows does not exist), and still
   leaves a stale entry live for up to one sweep interval. `_is_run_live` heals at the exact moment
   the answer is needed, with no new lifecycle.
