**C1-a. There is no fourth path, and I proved the negative.** `aws_ssm_association`,
`aws_ssm_document` and any CloudWatch-agent SSM parameter are absent from `infra/` (grep exit 1).
`aws ssm send-command` occurs once in executable code (`buildspec.yml:304`) and twice in comments
(`bootstrap-ec2.sh:19`, `:60`). [V]

**C1-b. The "someone re-runs bootstrap" escape hatch is worse than the dossier implies -- it is
destructive on a live box.** Re-running the whole script does far more than rewrite nginx: it
`apt-get -y full-upgrade`s (:93), `systemctl restart postgresql@16-main` (:298),
`docker compose down --remove-orphans` (:1240) and `systemctl restart velocityai-app.service`
(:1264). On a box serving traffic with runs in flight that is an outage plus abandoned runs
(compounding D8/D9). "A human re-runs the script" is therefore **not** an acceptable fallback for a
config change, which strengthens the case for extraction rather than weakening it.

**C1-c. Root cause of the root cause: `bootstrap-ec2.sh` conflates two lifecycles.** The file mixes
genuinely once-per-instance provisioning (partition + mkfs the data EBS, `initdb`, issue the TLS
cert, create the `velocityai-deploy` user, install the sudoers stanza) with *pure declarative
host configuration* (nginx site, agent config, ACLs) that is idempotent and safe to re-apply on any
schedule. Because the two share one file, the once-only latch that the first correctly needs is
inherited by the second, which does not. That -- not any of the three gates -- is the defect.
Every gate is right for provisioning; none is right for configuration. The fix is to separate the
lifecycles, not to weaken a gate.

**Where the dossier is right for a slightly wrong reason:** it frames the fix as "extract §13/§14".
§13 as written is *not* wholly re-runnable: lines 919-935 issue a TLS certificate. That block is
provisioning, must stay behind the latch, and must be carved out of the extraction (see I5 step 2).
The dossier does not mention this and an executor following it literally would move
`certbot certonly` into a script the pipeline runs on every deploy.

**The instance-id guard and the tag footgun, in my own words.** `aws ssm send-command` accepts
either `--instance-ids` or `--targets Key=tag:...`. Tag targeting resolves at send time to *every*
instance matching the tag, and the resolution is invisible in the command you typed. In this account
six of the eight tags on the dev, stage and prod instances -- `Project`, `Owner`, `CostCenter`,
`Repo`, `ManagedBy`, `Component` -- are byte-identical across all three environments (dossier
Appendix 2, `[V]`). `Component = "compute"` is set literally in `compute/main.tf:131` with no
environment interpolation, so it is provably identical by construction [V]. Only `Environment` and
`Name` differ. A `--targets Key=tag:Component,Values=compute` therefore fans a *dev* config change
out to *prod* -- silently, with a single `Success`, and with no filesystem rollback anywhere
because no root volume in any environment has ever been snapshotted. `--instance-ids` names one
opaque, unforgeable identifier and cannot fan out. The `Name`-tag assertion the dossier prepends is
belt-and-braces on top of that: it converts a mistyped instance id from "silently reconfigure the
wrong host" into "refuse and exit 1".

##### I5. The complete fix

**Design principle.** Ship the *mechanism* first, provably inert; let the sibling issues' *content*
ride it afterwards. That gives a falsifiable gate for C1 alone
(`sha256sum /etc/nginx/sites-available/velocityai` unchanged after reconcile) which is impossible if
mechanism and content land together.

**Delivery decision (this replaces the dossier's proposal, which cannot run).**

| Option | Verdict |
|---|---|
| (a) `bash infra/scripts/reconcile-host-config.sh` inside the SSM payload | **impossible** -- no repo on the box (I4.5) |
| (b) inline base64 the script into every SSM payload | works, but the script then exists in two shapes (repo file + pipeline-embedded copy), and *two* pipelines must each carry the embedding -- an INV-12 smell and double the port cost |
| (c) emit the script from a heredoc inside `bootstrap-ec2.sh` to `/usr/local/bin/` | matches 5 in-file precedents (`velocityai-load-secrets` :604-701, `velocityai-pg-dump` :1062-1078, `velocityai-skills-backup` :1080-1092, `velocityai-stuck-workflows-check` :1094-1111, `velocityai-update-image-tag` :1017-1040) -- but the body becomes opaque to `bash -n`, and on the dev box (bootstrap never re-runs) the file would never appear |
| **(d) a repo file uploaded to S3 as a 4th `config/` object with `filemd5`, fetched by both bootstrap and the pipeline** | **CHOSEN** |

Why (d): it is *the exact mechanism already proven for `bootstrap-ec2.sh` itself*; the instance role
already has `s3:GetObject` on `config/*` and `kms:Decrypt` via S3 (I4.3) so **zero IAM change**;
`filemd5` gives free change-detection with no pipeline edit for the upload; the script is a
standalone file so CI can `bash -n` it; there is exactly **one** copy of the logic in the repo and
one on the box; and it is the same category `origin/fix/infra-uki` explicitly preserves
("infrastructure, not deploy output", I4.8).

**Ordering decision.** Land the durable half **first**, then run one SSM command that carries **no
logic at all** -- only fetch-and-run. That means there is never, at any instant, a second copy of
the reconcile logic anywhere. It also means the dev push that lands the change *already uploads the
object* (`$TF/app apply` runs on every dev build, `buildspec.yml:189-203`), so the operator step is
three lines.

**Step 1 -- NEW FILE `infra/scripts/reconcile-host-config.sh`** (mode 0755).

This is a *faithful* extraction of §13 (minus cert issuance) and §14 as they exist today. It must be
byte-equivalent in output so that C1 alone is a provable no-op.

```bash
#!/usr/bin/env bash
# VelocityAI host-configuration reconcile.
#
# The DECLARATIVE half of infra/scripts/bootstrap-ec2.sh: nginx site + limits +
# proxy-header snippet, and the CloudWatch agent config + ACLs. Everything here
# is idempotent and safe to re-apply on a running host at any time.
#
# It exists because bootstrap-ec2.sh runs exactly ONCE per instance
# (velocityai-firstboot.service is gated by ConditionPathExists on
# /var/lib/velocityai/.bootstrap-done), while these values legitimately change
# with the application. Provisioning that is genuinely once-per-instance --
# partitioning the data EBS, initdb, ISSUING the TLS certificate, creating the
# deploy user + sudoers -- deliberately stays in bootstrap-ec2.sh.
#
# Callers (all three run the SAME file -- there is no second copy):
#   1. bootstrap-ec2.sh  -- first boot, after the cert block
#   2. the CI deploy     -- every deploy, via SSM RunCommand
#   3. an operator       -- ad hoc, same SSM one-liner
#
# Contract: FAIL-CLOSED. A bad nginx template must fail the caller loudly, not
# be reloaded. `nginx -t` parses the on-disk config in a throwaway process; the
# running master keeps its in-memory config until a SUCCESSFUL reload, so a
# validation failure costs zero downtime. On failure we restore the backup and
# exit non-zero.
set -euo pipefail

# --- context ---------------------------------------------------------------
# bootstrap.env is written by Terraform's compute user_data and persists on the
# root volume. Re-sourcing it here (rather than inheriting exported vars) is
# what makes this script runnable standalone. Same idiom as
# /usr/local/bin/velocityai-load-secrets.
if [[ ! -f /etc/velocityai/bootstrap.env ]]; then
    echo "[reconcile] FATAL: /etc/velocityai/bootstrap.env missing -- this box is not bootstrapped." >&2
    echo "[reconcile]        Refusing to render host config from defaults." >&2
    exit 1
fi
# shellcheck source=/dev/null
. /etc/velocityai/bootstrap.env

# FAIL-CLOSED on ENVIRONMENT -- deliberately NOT `${VELOCITYAI_ENVIRONMENT:-prod}`.
#
# bootstrap-ec2.sh:79 defaults this to "prod" because on first boot a missing
# value could only mean the earliest single-environment deployment. Here that
# default is a LIVE HAZARD: this script renders
#   metrics.namespace          -> "VelocityAI/${ENV_TITLE}"        (agent JSON)
#   logs.*.log_group_name      -> "/velocityai/${ENVIRONMENT}/..." (8 entries)
# so an unset value would silently ship DEV logs into the PROD log groups and
# DEV metrics into the PROD namespace -- cross-environment data contamination
# with no error, no alarm, and no way to un-publish. A hard failure is the only
# safe behaviour: it costs a re-run, the default costs prod's data integrity.

  --document-name AWS-RunShellScript \
  --comment "velocityai dev host-config reconcile" \
  --timeout-seconds 600 \
  --parameters file:///tmp/ssm-params.json \
  --region "$REGION" \
  --query Command.CommandId --output text)
echo "SSM command: $CMD_ID"

while true; do
  STATUS=$(aws ssm get-command-invocation --command-id "$CMD_ID" --instance-id "$DEV" \
            --region "$REGION" --query Status --output text 2>/dev/null || echo Pending)
  case "$STATUS" in
    Success) aws ssm get-command-invocation --command-id "$CMD_ID" --instance-id "$DEV" \
               --region "$REGION" --query StandardOutputContent --output text; break ;;
    Failed|Cancelled|TimedOut)
      aws ssm get-command-invocation --command-id "$CMD_ID" --instance-id "$DEV" \
        --region "$REGION" --query StandardErrorContent --output text; exit 1 ;;
    *) sleep 5 ;;
  esac
done
```

**Which half is durable and which evaporates.** Steps 1-4 are durable (repo + S3 + pipeline). Step 5
is a one-shot operational action; it leaves no artefact except the backup directory and the applied
config. If the instance is replaced, steps 1-4 reproduce everything and step 5 is unnecessary.

##### I6. Ripple-effect analysis -- assume this is wrong, and hunt

**Assumption under attack: "the extraction is faithful."** It is the single point of failure. If a
byte of the nginx site changes, `nginx -t` may still pass while behaviour shifts (a dropped
`include`, a lost `\$` escape). Mitigations, in order of strength: (a) the executor cuts the bodies
with `sed`, never by hand (step 1b); (b) the acceptance gate is a **sha256 comparison of the
rendered output before and after**, not a visual diff (I8 T1); (c) the live box's current hash is
already known and independently reproduced (`5f090af1...4083d`), so the post-reconcile hash on the
box must equal it exactly.

**`nginx -t` passes but the reload breaks live traffic.** Not possible for a config error --
`nginx -t` parses the same files the master would load. It *is* possible for a *semantic* error
(e.g. a location that matches too broadly). But C1 alone changes no semantics; the sha256 gate
catches any accidental change. When A1/D3/E1 add semantics, each brings its own probe (A1's
probe pair, D3's header count, E1's `aws logs test-metric-filter`).

**Reload during an in-flight SSE stream.** `systemctl reload nginx` sends `SIGHUP`: the master forks
new workers with the new config and asks old workers to **finish their current connections** before
exiting (graceful shutdown). An open `/api/runs/{id}/events/stream` connection is served to
completion by its old worker. It does *not* drop. There is a bounded window in which two worker
generations coexist -- irrelevant here since C1 changes nothing. Note `worker_shutdown_timeout`
defaults to 4 hours on nginx and is not set in this config, so even a multi-hour run's stream
survives.

**The agent restart drops in-flight log lines.** `fetch-config -s` ends in `systemctl restart`. The
agent restarts and resumes tailing from its stored file position (`/opt/aws/amazon-cloudwatch-agent/logs/state`).
Today the agent is dead anyway (B1), so there is nothing to drop. After B1 lands, a restart per
deploy is a sub-second gap and the file positions are persisted -- no loss. Worth stating because
"we restart the log shipper on every deploy" sounds alarming and is not.

**Concurrency: two deploys at once.** `buildspec.yml` has no concurrency control on the SSM step;
two overlapping dev builds could both `aws s3 cp` and both run the reconcile. Every operation is a
truncating write followed by `nginx -t` + reload -- the outcome is the same file either way, and the
worst case is two reloads. Not a corruption risk. The `fix/infra-uki` deploy.yml does add
`concurrency` on the `deploy` job (its comment at lines 58-65), which is strictly better.

**Interleaving with the app restart.** In buildspec I place the reconcile *before* ECR login and
`docker compose up -d`. So the order is: host config -> containers. If reconcile fails, the
containers are untouched and the previously-deployed image keeps serving behind the previous nginx
config -- a clean, fully-consistent abort. If I had put it after, a green build could ship a broken
proxy. In `deploy.yml` I place it before `systemctl restart velocityai-app.service` for the same
reason.

**Partial application.** The script is a linear sequence of truncating writes. If it dies midway
(SSM timeout, instance reboot), the possible states are: nginx files written but not validated
(previous config still running -- nginx has not been reloaded); or nginx done and the agent
half-done (agent config written, `fetch-config` not run -- the agent keeps its previous config).
Neither state is corrupt, and re-running the script converges. `restore_and_die` covers the one
state that matters (invalid nginx template).

**Crashed run / restart / resume / fan-out / revision / two browsers.** None of these touch host
config. The only interaction is the nginx reload, addressed above. Specifically: a run parked at a
human review gate holds an SSE connection open on the *old* worker across the reload and is
unaffected; `restore_non_terminal_runs` is a backend-process concern and no container is restarted
by the reconcile.

**Memory / connection pool.** No process is added. The agent's own memory is unchanged (same
config). nginx briefly runs two worker generations during a graceful reload; `worker_processes auto`
on a 4-vCPU box means a few extra processes for the duration of the longest in-flight request.

**The bootstrap script gets longer to reason about, not shorter.** It loses 305 lines and gains ~35.
`bash -n` must still pass (I8 T0). The removed §14 was *after* §13 and *before* §15; nothing between
them reads a variable set by them, so removing both leaves no dangling reference. I checked: the
only downstream reference to anything §13/§14 sets is
`bootstrap-ec2.sh:1271` (a log line naming `/opt/velocityai/docker-compose.yml`) -- unrelated.

**The `set -euo pipefail` interaction.** `bootstrap-ec2.sh:27` sets it. The new
`bash /opt/velocityai/reconcile-host-config.sh` is a plain command; a non-zero exit aborts bootstrap.
That is intended (fail-closed) but it means a transient S3 failure on first boot now aborts
provisioning, where previously §13 would have run from the inline body. Mitigation: the firstboot

new failure mode the change introduces.

Three independent guards now make it impossible:
1. **The script refuses to start** on an unset `VELOCITYAI_ENVIRONMENT` (`:?` not `:-`) and on any

   guard is a re-run, the cost of the default is prod's data integrity.
2. **The SSM payload refuses to fetch** unless `VELOCITYAI_ENVIRONMENT = dev` (step 5b) -- so a
   mis-typed instance id that somehow passed the `Name`-tag check still cannot reconcile.
3. **The operator sees the value before anything runs** (step 5a pre-flight), including the
   *current* on-box agent config, which already reads `VelocityAI/Dev`.

The script also echoes its resolved environment on every run
(`[reconcile] environment=dev -> log groups /velocityai/dev/*, namespace VelocityAI/Dev`), so the
SSM output and the CodeBuild log both carry the proof.

filesystem-level rollback for any host change.** The file-level backup the reconcile script writes
is the only restore point that exists.

| `/etc/nginx/snippets/velocityai-proxy-headers.conf` | the `include`d snippet |
| `/opt/aws/amazon-cloudwatch-agent/etc/amazon-cloudwatch-agent.json` | agent config |
| `getfacl -pR /var/lib/docker/containers` | the ACL state B2 will change |
| `id cwagent` | the group membership B2 will change |

Backups go to `/root/host-config-backup-<UTC-timestamp>/`, mode 0700, one directory per run, never
overwritten. Sizing: the four files total ~14 KB; the ACL dump grows with container count but is
kilobytes. Root is 32% used (dossier `[V]`), so unbounded accumulation is not a near-term risk, but
the executor should note that nothing prunes them.

**Rollback by change class:**

| Change | Reverse | Cost |
|---|---|---|
| **Repo (steps 1-4)** | `git revert <sha>` on `dev`, push | one build; the app layer re-uploads the old `bootstrap-ec2.sh` and *leaves* `config/reconcile-host-config.sh` behind as an orphan (Terraform destroys the object because the resource is gone -- verify with `head-object` -> 404). The reverted buildspec no longer calls it. |
| **nginx config on the box** | `cp -a /root/host-config-backup-<ts>/velocityai /etc/nginx/sites-available/velocityai && nginx -t && systemctl reload nginx` | seconds, zero downtime |
| **limits / proxy-headers** | same `cp -a` + `nginx -t` + reload | seconds |
| **agent config** | `cp -a .../amazon-cloudwatch-agent.json /opt/aws/.../etc/ && amazon-cloudwatch-agent-ctl -a fetch-config -m ec2 -s -c file:...` | seconds |
| **ACL / group changes (B2's payload, not C1's)** | `setfacl --restore=/root/host-config-backup-<ts>/docker-containers.acl`; `gpasswd -d cwagent adm` | seconds. **`--restore` is the only reliable inverse** -- there is no "undo" for a mask recomputation. |
| **A failed `nginx -t`** | nothing to roll back -- the reload never happened, the running config is untouched, and `restore_and_die` puts the files back too | zero |
| **The instance itself** | **NO ROLLBACK.** Root volume is `delete_on_termination`, unsnapshotted. If the box is destroyed, Postgres data survives only on the separate data EBS (`prevent_destroy = true`) and would have to be re-attached by hand (`compute/main.tf:106-110` says exactly this). | catastrophic; never touch `disable_api_termination` |

**One rollback trap.** If step 5 is run and *then* the repo change is reverted, the box keeps the
reconciled config (identical to before, by T5) but the pipeline stops re-applying it. That is the
pre-C1 state -- safe. The reverse order (revert first, then run the one-shot) would fetch a
404 for the S3 object and fail loudly. Either way, no half state.

##### I11. Open questions requiring a human decision

**Q1. Does the reconcile run on every deploy, or only when the script changes?**
Every deploy (my recommendation, and what step 4 implements). *Options:* (a) unconditional -- ~2s
per deploy, self-healing against manual drift, and the failure mode is loud; (b) conditional on an
S3 ETag/hash compare -- saves ~2s, but adds state to reason about and lets manual drift persist
silently. **Recommend (a).** The `chown` precedent at `buildspec.yml:291` is unconditional for the
same reason.

**Q2. Fail-closed or fail-open when the reconcile fails?**
Fail-closed (my recommendation, and what step 1's contract implements). *Options:* (a) fail-closed --
a bad nginx template or a dead agent aborts the deploy; the app keeps running the previous
image behind the previous, still-valid config, so downtime is zero, but an unrelated app deploy is
blocked by a config bug; (b) fail-open with a warning -- app deploys never blocked, but a broken
proxy or a dead log shipper ships green, which is precisely the B1/B5 failure this whole cluster
exists to end. **Recommend (a).** This is genuinely a product/ops judgement, not a technical one,
which is why it is here.

**Q3. Should the now-dead `location /ws/chat` block be removed while the file is open?**
It is dead config -- Phase 44 deleted `/ws/chat` from the backend (IMPL `:3683`) and the CI ratchet
`test_sse_cutover_banned_patterns.py` bans the token in `backend/app`, `backend/agents` and
`frontend/src` -- but `infra/` is **not** in that ratchet's scan set, so nothing forces it.
*Options:* (a) leave it -- C1 stays a provable no-op (my strong preference for this commit);
(b) remove it in a follow-up, alongside A1, with its own probe. **Recommend (a) now, (b) later.**
Note the block sits three lines from the live `/ws/handoff/` survivor, so this is a
read-carefully edit, not a delete-the-block edit.

**Q4. Who owns the backup directories under `/root/`?**
Nothing prunes `/root/host-config-backup-*`. At one per deploy and ~14 KB each this is negligible
for a year, but it is unbounded. *Options:* (a) accept; (b) keep the last N in the script;
(c) a `tmpfiles.d` rule. **Recommend (a)** and revisit if root usage moves off 32%.

##### I12. Shortcuts and alternatives explicitly rejected

**1. Remove `user_data` from `ignore_changes` and let Terraform re-render.**
Fails catastrophically. `user_data_replace_on_change = false` means the attribute updates in state
but the running instance is never re-provisioned -- so it changes nothing. Set *that* to `true` as
well and Terraform **replaces the instance**: Postgres 16 runs on the box, the root volume is
`delete_on_termination = true` with zero snapshots, and the replacement cascades into destroying the
data EBS `volume_attachment`, which needs a stop, which `disable_api_stop` blocks
(`compute/main.tf:106-112`, `:143-149`). Total data loss or a stuck apply. Not a shortcut -- an
outage.

**2. Delete the `.bootstrap-done` sentinel and let firstboot re-run.**
Two reasons it fails. (a) The dev instance's live userData has no `velocityai-firstboot.service` at
all (dossier `[V]`), so there is nothing to re-trigger. (b) Even where the unit exists, re-running
the *whole* bootstrap on a live box does `apt-get -y full-upgrade` (:93),
`systemctl restart postgresql@16-main` (:298), `docker compose down --remove-orphans` (:1240) and
`systemctl restart velocityai-app.service` (:1264) -- an outage plus abandoned in-flight runs
(compounding D8/D9), to change two config files.

**3. `aws ssm send-command --targets Key=tag:...` instead of `--instance-ids`.**
Rejected. Six of the eight tags are byte-identical across dev/stage/prod (`Component = "compute"` is
literally hard-coded with no interpolation at `compute/main.tf:131`). Tag targeting silently fans
out; there is no filesystem rollback in any environment. `--instance-ids` cannot fan out.

**4. Add an `aws_ssm_association` with `AWS-RunShellScript` on a schedule.**
Tempting -- it is the "AWS-native" answer and would make reconcile continuous. Rejected for now
because: it introduces a *second* actor mutating host config on a schedule the pipeline cannot see
(so a deploy and an association could interleave mid-write); associations target by tag or instance
id and the tag path is the footgun above; and there is no association anywhere in the repo today, so
it is a new operational concept for a one-line problem. Worth revisiting only if the pipeline-driven
reconcile proves insufficient.

**5. Put the nginx config in the container / behind an ALB.**
Rejected. `docker-compose.yml` has only `backend` and `frontend`; nginx terminates TLS on the host
and the cert lives in `/etc/letsencrypt`. Introducing an ALB is a topology change with its own
certificate, DNS and cost story, and the dossier's Appendix 2 already establishes that horizontal
scaling is blocked on externalising `_PIPELINE_QUEUES` / `_CANCEL_EVENTS` / `_LIVE_ECTX` /
`_CONCIERGE_STREAM_TASKS` anyway.

**6. Patch the on-box files directly with `sed`/`grep -q` append, and skip the extraction.**
This is what the dossier proposes for the "now" half. Rejected as the *primary* plan because it
creates two divergent sources of truth from the first minute: the box gets an appended block, the
repo gets an edit inside a heredoc, and nothing proves they match. The extraction-first ordering
(durable half, then a fetch-and-run one-shot) makes the box's content *derived from* the repo, and
the sha256 gate proves it. It is barely more work and it is the difference between a fix and a
patch.

**7. Inline base64 the reconcile script into every SSM payload (`deploy.yml`'s D-2 idiom).**
Genuinely tempting -- it is the pattern the target branch already uses for `docker-compose.yml`, and
it needs no S3 object. Rejected because the script would then exist as a repo file *and* as an
embedded copy in each of two pipelines, so a change to one pipeline's embedding could drift from the
other (INV-12), and the `bootstrap` caller still needs a *third* delivery path (it has no runner to
base64 from). The S3 object is one artefact serving all three callers.

**8. Emit the reconcile script from a heredoc inside `bootstrap-ec2.sh` to `/usr/local/bin/`.**
The closest rival, and it matches five in-file precedents. Rejected for two concrete reasons: the
body becomes invisible to `bash -n` and shellcheck (a quoted heredoc is opaque to the outer parse),
losing test T0; and on the dev box specifically it would never appear, because bootstrap never
re-runs -- the exact problem being fixed.

**9. Put the pipeline invocation only in `.github/workflows/deploy.yml`.**
The dossier's instruction. Rejected on the facts: that file does not exist on `dev`
(`git ls-tree -r --name-only dev -- .github` -> empty), so a `dev`-branch executor cannot write it,
and leaving `buildspec.yml` untouched means the reconcile stays a manual SSM run for as long as
`fix/infra-uki` remains unmerged -- which reinstates C1. The correct answer is both, sequenced, and
the throwaway cost is three lines against a `git rm`.

**10. Skip `nginx -t` because the template is generated and therefore trusted.**
Rejected. The template is generated *from a shell heredoc with hand-escaped `$`*, which is precisely
the class that produces a syntactically valid file with the wrong content, or an invalid file from a
missed escape. `nginx -t` costs milliseconds and is free of downtime by construction.

**11. Extract §13 wholesale, including the certbot block.**
The literal reading of the dossier's "extract §13/§14". Rejected: `certbot certonly` hits a
rate-limited external CA (5 duplicate certificates per registered domain per week) and mutates
`sites-enabled` mid-flight. Running it on every deploy would burn the rate limit and, once
exhausted, leave the box in a state where the temporary `bootstrap-http` site is enabled and the
real one is not -- i.e. a self-inflicted outage on a routine deploy.

**13. Carry `ENVIRONMENT="${VELOCITYAI_ENVIRONMENT:-prod}"` across verbatim, "because that is what
bootstrap does".**
The single most dangerous shortcut available here, and the one a faithful-extraction mindset walks
straight into. `bootstrap-ec2.sh:79` defaults to `prod`, so a literal copy-paste preserves it -- and
a literal copy-paste is exactly what T1's byte-fidelity gate rewards. Rejected: the default is
defensible for a once-per-instance provisioner (the earliest deployment had one environment) and
indefensible for a script that runs on **every deploy** and renders `VelocityAI/${ENV_TITLE}` plus
eight `/velocityai/${ENVIRONMENT}/*` log-group names. Unset variable -> dev's nginx/auth/audit logs
and container stdout land in `/velocityai/prod/*`, dev's CPU/memory/disk metrics land in
`VelocityAI/Prod`, prod's alarms start evaluating two hosts, and CloudWatch offers no
delete-by-content. The failure is silent (`exit 0`) and irreversible. `:?`-fatal plus a
`dev|stage|prod` allow-list costs one re-run; the default costs prod's data integrity. This is the
one place where "faithful to the original" is the wrong instinct, and the T1 hash gate deliberately
does **not** cover it (T1 renders the nginx site, not the agent JSON's namespace) -- which is why
T-pre exists as a separate, blocking gate.

**14. Make the reconcile a `systemd` timer on the box instead of a pipeline step.**
Rejected. A timer reconciles against whatever is in S3, on its own schedule, with no relationship to
the deploy that changed it -- so a deploy would appear to succeed while the config it depends on
lands minutes later. Coupling reconcile to the deploy is what makes the deploy's success mean
something.
