###### I3.2 The Docker half - the dossier's root cause is wrong; here is the real one

The dossier says:

> `setfacl -m` recalculates the mask from the union of named entries unless `-n` is passed or the
> mask is set explicitly; combining `u:cwagent:rX` with `o::r` in a single `-R` invocation over a
> tree whose directories have differing base permissions produced a mask that drops the read bit.

I reproduced the exact command on a fresh 0710 directory in `ubuntu:24.04`. **setfacl's own output
is correct** - the mask is recalculated to the *union*, which includes read:

```
===== E1  setfacl -m u:cwagent:rX,o::r on a fresh 0710 dir  (mask recalculated?) =====
before mode=710 owner=root:root
after  mode=754
    # file: /t1
    user::rwx
    user:cwagent:r-x
    group::--x
    mask::r-x            <-- read bit PRESENT
    other::r--
```

So the command as written does the right thing. The dossier's mechanism is not what happened.
The next experiment shows what did:

```
===== E2  now chmod 0710 /t1 =====
after chmod mode=710
    user::rwx
    user:cwagent:r-x	#effective:--x
    group::--x
    mask::--x            <-- read bit GONE
    other::---
-- can cwagent list the dir?
    LIST: DENIED
```

That is **byte-for-byte the state the dossier measured on the live box** - including the loss of
`o::r`, which the dossier's excerpt did not quote but which is implied by the same `chmod`.

The reason is the POSIX-ACL/`chmod` interaction: on an inode carrying an extended ACL, the *group*
bits of `st_mode` are the **mask**, not `group::`. A `chmod 0710` therefore rewrites the mask to
`--x` and zeroes `other::`, leaving `group::` untouched - exactly the observed shape.

**Who runs that `chmod`?** `dockerd`. Reproduced end to end with a nested daemon
(`docker.io` 29.1.3 on Ubuntu 24.04, one version family off the box's Docker CE):

```
===== apply bootstrap-ec2.sh :951-952 verbatim =====
after setfacl: mode=754
  user:cwagent:r-x
  mask::r-x
  other::r--
  default:mask::r-x
  default:other::r--

===== kill dockerd, restart it  <-- discriminating step =====
while stopped: mode=754

===== RESULT after dockerd restart =====
mode=710 owner=root:root
  user:cwagent:r-x	#effective:--x
  mask::--x
  other::---
  default:mask::r-x          <-- default ACL SURVIVES
  default:other::r--
```

`dockerd` calls `MkdirAllAndChown(<data-root>/containers, 0710, ...)` at startup, whose
`setPermissions` helper chmods whenever `stat.Mode().Perm() != mode.Perm()`. Since **any** ACL that
gives `cwagent` an effective read bit necessarily raises the mode above 0710 (mask `r-x` -> group
bits `5`), `stat != 0710` is guaranteed and the chmod is guaranteed. This is a **structural
conflict, not a race**: a one-shot `setfacl` cannot survive a daemon restart, no matter how it is
written.

**A second, independent mechanism breaks it even without a restart.** New per-container directories
are created mode 0710. POSIX default-ACL inheritance intersects the inherited mask with the
creation mode's group bits:

```
===== E4  DEFAULT ACL inheritance -> new SUBDIR created mode 0710 =====
-- parent:
    mask::r-x
    default:mask::r-x
-- new subdir (mkdir 0710):
    user:cwagent:r-x	#effective:--x
    mask::--x            <-- born masked
    default:mask::r-x
-- can cwagent list the new subdir?
    LIST: DENIED

===== E5  new FILE created mode 0640 =====
    user:cwagent:r-x	#effective:r--
    mask::r--
-- can cwagent read the json log?
    READ: OK
-- can cwagent GLOB /t4/*/*-json.log ?
    ls: cannot access '/t4/*/*-json.log': No such file or directory
```

This is the answer to the brief's question *"do new container dirs inherit the default ACL? this is
why `-d` matters; prove it"*. They inherit the **entries** but are born with mask `--x`, so `-d` is
necessary but **not sufficient**. The json log *file* is readable (E5), but the agent can never
reach it because it cannot enumerate either directory level.

`docker compose up -d --remove-orphans` runs on **every** CI deploy (`infra/buildspec.yml:298`), and
recreating a container creates a new `<id>` directory. So mechanism 2 fires on every deploy, and
mechanism 1 on every reboot or `systemctl restart docker`.

**Causal chain, trigger to symptom:**

1. Bootstrap runs `setfacl` once at `:951-952`. Correct at that instant (mask `r-x`, mode 0754).
2. Section 17 starts the containers. Each `<id>` dir is created 0710 -> inherited mask `--x`
   (E4). The glob is already dead **on a pristine first boot, before any reboot**.
3. The first `systemctl restart docker` / reboot / Docker-CE upgrade chmods the parent back to 0710
   -> parent mask `--x` (E2, dind) -> even the top-level enumeration dies, and `o::r` is lost.
4. `sudo -u cwagent ls /var/lib/docker/containers/*/*-json.log` -> `Permission denied`, exactly as
   the dossier observed.
5. `/velocityai/dev/app` is empty. Because B1 keeps the agent crash-looping, no denial was ever
   even attempted, so nothing surfaced.

**The root cause, at the level of a broken assumption:** the design assumed a filesystem permission
grant is a one-time provisioning act. For `/var/lib/docker/containers` that assumption is false -
the directory is *owned by a reconciling daemon* that re-asserts mode 0710 as an invariant, and the
kernel's default-ACL inheritance re-applies that invariant to every child. Any grant here must be a
**reconciler**, not a one-shot. That is why the fix changes shape, not just arguments.

###### I3.3 Why the dossier's proposed fix does not hold

```bash
setfacl -R -m m::rx,u:cwagent:rX /var/lib/docker/containers
setfacl -R -d -m m::rx,u:cwagent:rX /var/lib/docker/containers
```

- Setting `m::rx` explicitly *is* correct as far as it goes - it produces mask `r-x` (E3, first
  half). But mode then becomes 0750, and the very next `dockerd` start chmods to 0710 and the mask

- It **drops `o::r`**. `setfacl -m` only modifies the entries named, so today's `other::` is left

**What the fix must add for durability, stated as the brief demands:** for the six `adm` paths,
nothing - group membership is an attribute of the *reading process*, entirely orthogonal to

precisely so that certbot's recreation of `letsencrypt.log` cannot revoke it. For Docker, no
static grant is durable at all, which is why the fix installs a reconciler.

###### I4.3 The Docker ACL mask mechanics (the brief's second question, answered with measurements)

- **Does `setfacl -m` recalculate the mask?** Yes, to the union of `group::` and all named entries.
  Measured (E1): `u:cwagent:rX` on a 0710 dir -> `mask::r-x`. The dossier's claim that the
  recalculation *dropped* the read bit is false.
- **Is `-n` required?** No - and it is counterproductive. With `-n` the pre-existing `--x` mask is
  left in place and the named entry is masked off (E3b). The dossier lists `-n` as one of the two
  ways to avoid the (non-existent) problem; following that advice would leave the bug in place.
- **Is an explicit `m::` required?** Yes, but for a different reason than the dossier gives. On the
  *parent* the union recalculation already yields `r-x`, so `m::` is redundant there. On a
  **freshly created `<id>` subdirectory** the inherited mask is `--x` and `group::` is `--x`, so
  the union is still `--x` - the recalculation cannot rescue it. Only an explicit mask does. That
  is the real justification for `m::rX`.
- **Recursive plus default.** Both are needed and they do different jobs: `-R -m` fixes the
  directories that exist *now* (including every `<id>` dir born masked), `-R -d -m` seeds the
  default ACL so *files* created later (rotated json logs, per-container `/etc/hosts`) inherit the
  named entry. Neither substitutes for the other, and neither is durable against `dockerd`'s chmod
  or a new `mkdir 0710` - hence the reconciler.
- **Containers created after the ACL is applied.** Proven in E4: they inherit the entries with mask
  `--x` and are not listable. This is the single most important correction in this report, because
  it means the failure recurs on **every deploy**, not only on reboot.

###### I4.4 Security consequence of `adm`, and whether `adm` is the right group everywhere

`adm` on Debian/Ubuntu is the conventional "read system logs" group. Adding `cwagent` to it grants
read on: nginx access+error, `auth.log` (which contains sudo/sshd records), `syslog`, `kern.log`,
`mail.log`, `audit.log`, the postgres cluster log, and the unattended-upgrades logs.

**Worth stating, and my assessment:** this is a *widening* of what the log-shipping daemon can read
beyond the eight configured paths - it can read every `adm` log on the box, not only the ones in
`collect_list`. Three things bound the risk to acceptable:

1. It is **read-only** and confers no write, no execute, and no group ownership of anything.
2. The agent already has an IAM role that can `PutLogEvents` to `/velocityai/dev/*`; the *content*
   of `auth.log` and `audit.log` is already destined for CloudWatch by design
   (`monitoring/main.tf:12-13` names `auth` as a log group and the module's variable docstring at
   `variables.tf:28` explicitly reasons about "auth/auditd long-forensics" retention). Group `adm`
   is the mechanism the distro provides for exactly this.
3. It is **narrower than the alternatives.** `run_as_user: root` (I11) grants everything; the
   `docker` group is root-equivalent (the `bootstrap-ec2.sh:340` comment already says so).

`adm` is the right group for entries 1-6 - verified per-path in I3.1, including the two the brief
flagged: `audit.log` (Ubuntu ships `log_group = adm`, dir `0750 root:adm`) and postgres
(`pg_createcluster` chowns to `postgres:adm`). It is **not** the right mechanism for entry 7
(letsencrypt: the directory is `root:root`, so a group grant needs a `chgrp` anyway - at which
point `chgrp adm` + `chmod 0750` *is* the group mechanism, consistently with the other five log
directories) and it is **not available** for entry 8 (Docker's dirs are `root:root` and dockerd
chowns them back).

BEFORE (`:339-356`):

```bash
# POSIX ACL so cwagent can read /var/lib/docker/containers/*.log without
# being in the docker group (docker.sock = root-equivalent). `|| true`
# because the cwagent user may not exist yet — repeated after cwagent install

# `o::r` is intentional and load-bearing. /var/lib/docker/containers is
# mode 0710 by default — owner:root, group:root, other:---. When setfacl
# sets a default ACL it inherits the dir's current "other" bits as the

# (notably /etc/hosts, which docker generates per container and bind-mounts

# added via `extra_hosts: host.docker.internal:host-gateway` fail with
# "Temporary failure in name resolution". Forcing `o::r` here restores the
# normal world-readable /etc/hosts so app containers can use the host.
setfacl -R -m u:cwagent:rX,o::r /var/lib/docker/containers || true
setfacl -R -d -m u:cwagent:rX,o::r /var/lib/docker/containers || true
```

AFTER:

```bash

# directory back to 0710 at every daemon start (which rewrites the ACL mask and

# therefore a reconciler — /usr/local/sbin/velocityai-cwagent-docker-acl, driven
```

```bash
# The Docker container-log ACL is a RECONCILER, not a one-shot — see the script
# header for why. Install it, arm the timer, and run it once now.
install -m 0755 /dev/null /usr/local/sbin/velocityai-cwagent-docker-acl
cat > /usr/local/sbin/velocityai-cwagent-docker-acl <<'ACLSCRIPT'
#!/bin/bash
# Re-assert the POSIX ACL that lets the CloudWatch agent's `cwagent` user read
# the Docker json-file container logs.
#
# WHY THIS IS A RECONCILER AND NOT A ONE-SHOT
# ------------------------------------------------------------------------------
# /var/lib/docker/containers is mode 0710 root:root. On an inode carrying an
# extended ACL the GROUP bits of st_mode are the ACL MASK, so any grant that
# gives cwagent an effective read bit necessarily raises the mode above 0710.
# Two independent mechanisms then revert it:
#
#   1. dockerd calls MkdirAllAndChown(<data-root>/containers, 0710, ...) at every
#      daemon start, whose setPermissions helper chmods whenever the current mode
#      differs from 0710. chmod on an ACL-bearing inode rewrites the MASK, so the
#      read bit is zeroed. Because a working grant ALWAYS leaves mode != 0710,
#      this chmod is guaranteed, not racy. Fires on `systemctl restart docker`,
#      on reboot, and on a docker-ce package upgrade.
#
#   2. Each per-container <id> directory is created mode 0710. POSIX default-ACL
#      inheritance intersects the inherited mask with the creation mode's group
#      bits, so a NEW container directory is born with mask --x however correct
#      the parent's default ACL is. Fires on every `docker compose up -d` that
#      recreates a container, i.e. on every deploy.
#
# A single setfacl at provisioning time therefore cannot hold. The systemd timer
# beside this script re-runs it; the agent re-evaluates its glob and picks the
# files up.
#
# WHY `m::rX` IS EXPLICIT
# ------------------------------------------------------------------------------
# `setfacl -m` recalculates the mask as the UNION of group:: and the named
# entries. On the parent that already yields r-x. But on a freshly created <id>
# directory both group:: and the inherited mask are --x, so the union is still
# --x and the recalculation cannot rescue it. Only an explicit mask does. (Do NOT
# use `-n`: it suppresses recalculation entirely and leaves the read bit masked.)
#
# WHY `o::r` STAYS
# ------------------------------------------------------------------------------
# /var/lib/docker/containers defaults to other::---, and the DEFAULT ACL is what
# per-container bind-mount files inherit — notably the /etc/hosts docker
# generates per container. Without world-read there, a container running as the
# non-root uid 10001 our Dockerfile sets cannot read /etc/hosts, and every DNS
# lookup for the `extra_hosts: host.docker.internal:host-gateway` entry fails
# with "Temporary failure in name resolution". This was a real production
# failure; do not drop it.
set -u
DIR=/var/lib/docker/containers
[ -d "$DIR" ] || exit 0
id -u cwagent >/dev/null 2>&1 || exit 0
setfacl -R -m  m::rX,u:cwagent:rX,o::r "$DIR" || exit 1
setfacl -R -d -m m::rX,u:cwagent:rX,o::r "$DIR" || exit 1
exit 0
ACLSCRIPT
chmod 0755 /usr/local/sbin/velocityai-cwagent-docker-acl

cat > /etc/systemd/system/velocityai-cwagent-docker-acl.service <<'ACLUNIT'
[Unit]
Description=Re-assert the cwagent read ACL on Docker container logs
Documentation=file:/usr/local/sbin/velocityai-cwagent-docker-acl
After=docker.service

[Service]
Type=oneshot
ExecStart=/usr/local/sbin/velocityai-cwagent-docker-acl
ACLUNIT

cat > /etc/systemd/system/velocityai-cwagent-docker-acl.timer <<'ACLTIMER'
[Unit]
Description=Periodically re-assert the cwagent read ACL on Docker container logs

[Timer]
OnBootSec=2min
OnUnitActiveSec=1min
AccuracySec=10s
Unit=velocityai-cwagent-docker-acl.service

[Install]
WantedBy=timers.target
ACLTIMER

systemctl daemon-reload
systemctl enable --now velocityai-cwagent-docker-acl.timer
systemctl start velocityai-cwagent-docker-acl.service
```

Note the `install -m 0755 /dev/null <path>` before the heredoc: it creates the file with the right
mode atomically even on a re-run where the previous file was left non-executable. The trailing
`chmod 0755` is belt-and-braces for the case where the file already existed.

*Why a timer and not a `.path` unit:* a `systemd.path` unit with `PathModified=` would fire the
instant a container directory appears, which is more elegant. I cannot verify systemd's inotify
mask for `PathModified=` on a **directory** offline, and an unverified trigger that silently never
fires is exactly the failure class this whole dossier is about. The timer's semantics are
unambiguous and its worst case is a bounded delay (see I6). The `.path` unit is recorded as a
deferred optimisation in I12.

*Why `OnUnitActiveSec=1min` and not something longer:* the work is two `setfacl` calls over a tree
of two container directories - microseconds. The cost of a shorter period is nil; the cost of a
longer one is a longer gap in the `/app` log group after a deploy.

##### I6. Ripple-effect analysis - why nothing else breaks

Assume the fix is wrong. Where does it bite?

**1. `usermod -a -G adm cwagent` aborts bootstrap if group `adm` is missing.** `set -euo pipefail`
is in force (`:26`), so a failure aborts before sections 16/17 (the pg_dump cron and the app
service). `adm` is created by `base-passwd`, is present on every Ubuntu image, and is already
depended on implicitly by `rsyslog`/`auditd`/`nginx` packaging. If it were somehow absent, failing
loudly at provisioning is the correct outcome and matches B5's philosophy. **Verified present** in
the probe container: `adm:x:4:ubuntu`.

**2. Does the agent actually honour supplementary groups?** **This is the one load-bearing thing I
could not verify, and I am flagging it rather than asserting it.** The shipped systemd unit
(`/etc/systemd/system/amazon-cloudwatch-agent.service`, read from the current
`amazon-cloudwatch-agent.deb`) has **no `User=`**:

```
[Service]
Type=simple
ExecStart=/opt/aws/amazon-cloudwatch-agent/bin/start-amazon-cloudwatch-agent
KillMode=process
Restart=on-failure
RestartSec=60s
```

and `amazon-cloudwatch-agent-ctl` (459 lines) contains no `runas`/`run_as_user` handling. So the
agent starts as root and drops privileges **itself**, inside the Go binary, from the config's
`run_as_user`. Whether that drop uses `setgroups(execUser.Sgids)` (which honours `/etc/group`) or a
bare `setuid` (which would not) I could not confirm: I ran the real binary under Rosetta and it
exited before `/proc/<pid>/status` could be sampled, and `strings` over the stripped binary
returned nothing for the symbol names. **[I]** - my belief, from the agent's use of the
`libcontainer/user` resolver, is that supplementary groups *are* applied, and AWS's guidance to
grant the `cwagent` user read access to log files only makes sense on that assumption. **The fix
carries its own proof:** I8 test T3 is an on-box `grep Groups /proc/<agent-pid>/status` that must
show `4` (adm). If it does not, the fix as specified is insufficient for entries 1-6 and the
decision escalates to I11's `run_as_user: root` option. The executor must run T3 before declaring
B2 done.

**3. The letsencrypt directory mode change breaks certbot.** Considered and rejected. certbot's
`util.set_up_core_dir` -> `make_or_verify_dir(directory, mode, uid, strict)` runs with
`strict=config.strict_permissions`, which is **False** by default; with `strict` false it verifies
ownership only, not mode, and does not chmod an existing directory. Ownership is unchanged (`root`
stays the owner; only the group changes). `certbot.timer` renewals therefore continue unaffected.
Residual: if an operator ever passes `--strict-permissions`, certbot would complain. That flag is
not used anywhere in the repo (`grep -rn 'strict-permissions' infra/` -> no output).

**4. Widening `/var/log/letsencrypt` from 0700 to 0750 root:adm exposes ACME material.** The
directory holds `letsencrypt.log*` only; private keys live under `/etc/letsencrypt/`, which is not
touched. The log does contain hostnames and ACME account URLs, which are already going to
CloudWatch by design (that is the whole point of collecting it).

**5. The reconciler's `o::r` makes json container logs world-readable.** True - and it is the
**status quo**, not a new exposure: `bootstrap-ec2.sh:951` already applies `-R ... o::r` to the
whole tree today. I deliberately did not tighten it in the same change (one variable at a time),
because `o::r` is what the section-8 comment records as load-bearing for container DNS. Tightening
it to the default ACL only is recorded in I12 as a separate, testable follow-up.

**6. The timer runs `setfacl -R` forever on a growing tree.** `/var/lib/docker/containers` holds one
directory per *existing* container - two today (`backend`, `frontend`), transiently three during a
compose recreate. Stopped-and-removed containers have their directories deleted by Docker. The tree
does not grow. Worst case is a handful of inodes per minute.

**7. Timer versus a new container: how long is the gap?** Up to 60 s from the `mkdir` to the ACL
re-assert. During that window the agent's glob cannot see the new file. The agent re-evaluates
`file_path` globs on its own schedule, so the file is picked up on the next scan after the ACL
lands. **[I]** on the agent's exact re-glob cadence - T5 in I8 measures it on the box. If the agent
turned out to glob only once at startup, the gap would be permanent for containers created after
the agent started, and the fix would additionally need `ExecStartPost` chaining. T5 exists to
discover that.

**8. Concurrency.** `Type=oneshot` plus systemd's per-unit job serialisation means two invocations
cannot overlap; a start requested while one is running is queued or coalesced. Two concurrent
`setfacl -R` runs would in any case be idempotent and convergent.

**9. Startup/shutdown ordering.** The `.service` carries `After=docker.service` so a boot-time run
cannot race the daemon creating the directory; and the script's `[ -d "$DIR" ] || exit 0` guard
makes an early run a clean no-op rather than an error. `OnBootSec=2min` gives docker time to come
up before the first timed run.

**10. A partially applied fix.** Each of the three grants is independent: group membership alone
fixes six entries; the letsencrypt `chmod` alone fixes the seventh; the reconciler alone fixes the
eighth. There is no ordering dependency between them and no state one leaves that another needs.
A partial application degrades to "fewer log groups populated", never to a broken box.

**11. Does any of this touch the application?** No. Nothing in `backend/`, `frontend/`, the engine,
the SSE transport, the run queues, or the database is read or written. An unattached client, a slow
client, a crashed run, a restart, a resume, a fan-out run, a revision run, two browsers - all
unaffected by construction, because no application code path exists in the change. Memory and
connection-pool effects: none (the change adds one short-lived root process per minute).

**12. The one interaction with a sibling issue that could bite.** If B1 has **not** landed, the
agent is still crash-looping on `/var/log/amazon-cloudwatch-agent.log` and `systemctl restart
amazon-cloudwatch-agent` in step 4 will restart a process that immediately exits 1 again. B2's own
verification (T2/T3) would then be unrunnable. That is a sequencing constraint, not a defect - see
I10.

```bash
#!/bin/bash
# Proves the two mechanisms that make a one-shot setfacl insufficient on
# /var/lib/docker/containers, and that the reconciler's argument form is the one
# that survives them. Run:
#   docker run --rm -v "$PWD/infra/scripts/tests/acl-mechanism.sh:/t.sh:ro" \
#     ubuntu:24.04 bash -c 'apt-get update -qq >/dev/null 2>&1;
#       apt-get install -y -qq acl util-linux >/dev/null 2>&1; bash /t.sh'
set -u
fail=0
ok()   { printf 'PASS  %s\n' "$1"; }
bad()  { printf 'FAIL  %s\n' "$1"; fail=1; }

id -u cwagent >/dev/null 2>&1 || useradd -r -s /usr/sbin/nologin cwagent
listable() { setpriv --reuid=cwagent --regid=cwagent --clear-groups ls "$1" >/dev/null 2>&1; }

# M1: chmod back to 0710 rewrites the mask (what dockerd does at daemon start).
rm -rf /m1 && mkdir -m 0710 /m1
setfacl -m u:cwagent:rX,o::r /m1
listable /m1 || bad "M1 precondition: dir should be listable right after setfacl"
chmod 0710 /m1
if listable /m1; then bad "M1: chmod 0710 should have masked off the read bit"
else ok "M1: chmod 0710 clobbers the ACL mask (dockerd's daemon-start chmod)"; fi

# M2: a new 0710 subdir inherits the entries but is born with mask --x.
rm -rf /m2 && mkdir -m 0710 /m2
setfacl    -m m::rX,u:cwagent:rX,o::r /m2
setfacl -d -m m::rX,u:cwagent:rX,o::r /m2
mkdir -m 0710 /m2/newcontainer
if listable /m2/newcontainer; then
  bad "M2: a fresh 0710 subdir should NOT be listable from the default ACL alone"
else ok "M2: new container dir is born mask --x (default ACL is necessary, not sufficient)"; fi

# R: the reconciler's exact argument form repairs BOTH, on the parent and the child.
setfacl -R -m  m::rX,u:cwagent:rX,o::r /m2
setfacl -R -d -m m::rX,u:cwagent:rX,o::r /m2
listable /m2                && ok  "R: parent listable after reconcile" \
                            || bad "R: parent still not listable"
listable /m2/newcontainer   && ok  "R: child listable after reconcile"  \
                            || bad "R: child still not listable"

# R2: the reconciler does NOT drop o::r (container /etc/hosts must stay world-readable).
getfacl -p /m2 2>/dev/null | grep -qx 'other::r--' \
  && ok  "R2: access o::r preserved" || bad "R2: access o::r was dropped"
getfacl -p /m2 2>/dev/null | grep -qx 'default:other::r--' \
  && ok  "R2: default o::r preserved" || bad "R2: default o::r was dropped"

# N: `-n` is the wrong tool — it leaves the read bit masked.
rm -rf /n1 && mkdir -m 0710 /n1
setfacl -n -m u:cwagent:rX /n1
if listable /n1; then bad "N: -n unexpectedly worked"
else ok "N: -n leaves the inherited --x mask (do not use it)"; fi

exit $fail
```

##### I9. Rollback

**Repo half.** `git revert <commit>` restores `bootstrap-ec2.sh` exactly. The next `dev` push
re-uploads the reverted script to S3 via `aws_s3_object.bootstrap_script`'s `filemd5` hash. Fully
reversible, no state.

**Host half.** The SSM payload writes a timestamped backup to `/root/cwagent-acl-backup-<ts>/`
capturing, before any change: `id cwagent`, `getfacl -p /var/lib/docker/containers`,
`stat -c '%a %U:%G' /var/log/letsencrypt`, and the pre-existing unit listing. To undo:

```bash
BK=/root/cwagent-acl-backup-<ts>          # printed as BACKUP=... by the payload

systemctl disable --now velocityai-cwagent-docker-acl.timer
rm -f /etc/systemd/system/velocityai-cwagent-docker-acl.{timer,service}
rm -f /usr/local/sbin/velocityai-cwagent-docker-acl
systemctl daemon-reload

gpasswd -d cwagent adm                    # reverse of `usermod -a -G adm cwagent`
chgrp root /var/log/letsencrypt
chmod 0700 /var/log/letsencrypt

setfacl -R -b /var/lib/docker/containers  # strip the ACL entirely
setfacl -R --restore="$BK/containers.acl.before"   # restore the captured state
systemctl restart amazon-cloudwatch-agent
```

Two honest caveats:

- `getfacl -p` output is `setfacl --restore` compatible, so the ACL restore is exact **for the
  inodes that existed at capture time**. Container directories created after the capture have no
  recorded prior state; `setfacl -R -b` returns them to the plain 0710 they were born with, which
  is the correct pre-fix state anyway.
- **`gpasswd -d cwagent adm` does not affect the already-running agent process** - supplementary
  groups are captured at start. The `systemctl restart` at the end is what makes the revocation
  effective. Without it the agent keeps its adm access until the next restart.

**What is not reversible, and what the pre-change backup must capture.** There is **no
filesystem-level rollback**: `velocityai-dev-root` has `delete_on_termination = true` and zero
snapshots. The `/root/cwagent-acl-backup-<ts>/` directory is the only restore point, and it lives
on that same unsnapshotted volume - so it survives a reboot but not an instance replacement. On
instance replacement the host half is gone entirely and the repo half re-applies from S3, which is
the desired end state, so replacement is not a rollback hazard for this change.

Nothing in this fix is destructive: it adds a group membership, loosens one directory's group and
mode, and adds ACL entries. It deletes no file, no log, no data, and no configuration the box was
relying on (the two `setfacl` pairs it removes from the *script* are re-implemented by the
reconciler; the removal only takes effect on a future bootstrap run).

##### I11. Open questions requiring a human decision

**Q1 - If the agent does not honour supplementary groups, do we run it as root?**

This is contingent on T3. If `/proc/<agent-pid>/status` shows `Groups: 0` while `Uid: 997`, then
`run_as_user: cwagent` cannot read any `adm` log no matter what we grant, and the fix must change
shape.

- **Option A - `run_as_user: root` (`bootstrap-ec2.sh:967`).** One-line change. Removes the need
  for the `adm` grant, the letsencrypt directory change, **and** the entire Docker reconciler -
  root reads everything, and `dockerd`'s chmod becomes irrelevant. This is also AWS's own default
  for the agent.
- **Option B - keep `cwagent` and add `AmbientCapabilities=CAP_DAC_READ_SEARCH`** via a
  `docker`-style drop-in on `amazon-cloudwatch-agent.service`. Narrower than root (read-only bypass,
  no write, no exec). But the capability is attached to the unit, and an agent package upgrade that
  ships a new unit file would silently drop it - the same class of invisible failure this whole
  dossier documents.
- **Option C - keep `cwagent` and drop the `adm` paths from `collect_list`**, shipping only nginx
  (which is `adm` too, so this collapses to shipping almost nothing). Not viable.

**My recommendation: A, but only if T3 forces it.** The dossier's B1 rejects root as "widening the
blast radius of a log-shipping daemon for no reason" - and for B1's problem (a missing sink file
that one `install` command creates) that rejection is correct. B2 is the case where there *is* a
reason: root would eliminate three separate host-permission mechanisms including the one that needs
a background reconciler. If T3 passes, none of this arises and `cwagent` stays. **This is a genuine
fork and I am not resolving it unilaterally, because it contradicts a position a sibling issue took
explicitly.**

**Q2 - Do we accept a background systemd timer on the dev host?**

The Docker reconciler is a permanent, if tiny, moving part on a box with no filesystem rollback.
The alternative that removes it entirely is to stop reading Docker's json logs and switch the
compose `logging.driver` to `awslogs`, letting Docker ship container stdout to CloudWatch directly
using the instance role. That is first-party, needs no host permissions, and survives everything.
Its cost is real: **`docker logs` and `docker compose logs` stop working on the box** (the
`awslogs` driver does not support read-back), and the buildspec's deploy failure path prints
`docker compose logs --tail=80 backend` (`infra/buildspec.yml:301`) - that diagnostic would go dark.

**My recommendation: keep json-file plus the reconciler.** Losing `docker logs` on the only box
with no other debugging surface is a worse trade than one oneshot unit per minute. But an operator
who values a zero-moving-parts host over local `docker logs` could reasonably choose otherwise, and
the choice is theirs.

##### I12. Shortcuts and alternatives explicitly rejected

**Rejected - the dossier's own fix, `setfacl -R -m m::rx,u:cwagent:rX` plus the `-d` twin.** Not a
hack, just insufficient. Verified failures: (a) it leaves mode 0750, so the next `dockerd` start
chmods to 0710 and the mask returns to `--x` (E3, second half - measured); (b) it does nothing for
container directories created afterwards, which are born mask `--x` (E4 - measured), so the glob
breaks again on the very next deploy; (c) it silently abandons `o::r`, the grant
`bootstrap-ec2.sh:344-354` documents as load-bearing for container DNS. It would make the box work
until the next `systemctl restart docker` or `docker compose up -d`, i.e. hours.

**Rejected - `setfacl -n`.** The dossier offers it as one of the two ways to stop the mask being
"recalculated wrongly". Measured (E3b): with `-n` the pre-existing `--x` mask is preserved and the
named entry is masked off, so it is strictly worse than doing nothing clever. The mask
recalculation was never the problem.

**Rejected - a single `setfacl` at bootstrap with no reconciler.** This is what exists today. It is
correct for the few seconds between running and the first container start, and dead thereafter.
Proven twice over (E4 for container creation, dind for daemon restart).

**Rejected - adding `cwagent` to the `docker` group.** The `docker` group grants access to
`docker.sock`, which is root-equivalent; `bootstrap-ec2.sh:340` already says so. It also would not
help: the container directories are `root:root`, not `root:docker`.

**Rejected - `chown -R :adm /var/lib/docker/containers` + `chmod -R g+rX`.** `dockerd`'s
`MkdirAllAndChown` chowns the parent back to `root:root` and chmods to 0710 at every daemon start.
Same failure as the one-shot ACL, with the added risk of confusing the daemon's own expectations.

**Rejected - `chattr +i` on the container directory to stop `dockerd` chmodding it.** The chmod
would fail and `dockerd` would fail to start. Trading a missing log group for a dead box.

**Rejected - enumerating container log paths explicitly instead of globbing.** Container ids change
on every recreate; there is nothing stable to enumerate.

**Rejected - `setcap cap_dac_read_search+ep` on the agent binary.** Would work, and is narrower
than root. But an `amazon-cloudwatch-agent` package upgrade replaces the binary and silently drops
the file capability, reproducing exactly the "invisible failure" mode this dossier exists to
eliminate. Recorded as Q1 Option B rather than adopted.

**Rejected - dropping `/var/log/letsencrypt/letsencrypt.log` from the `collect_list`** (the
dossier's stated alternative). Verified cost: `monitoring/main.tf:758-805` attaches two metric
filters and two alarms to `/velocityai/<env>/letsencrypt`, and the success-side heartbeat is
`treat_missing_data = "breaching"` - so dropping the path silently disables cert-renewal-failure
detection **and** creates a new permanently-breaching alarm feeding B6's fatigue problem. The
directory fix is three idempotent commands and durable across rotation.

**Rejected - putting an ACL on `/var/log/letsencrypt` instead of changing group and mode.** An ACL
is the heavier tool and it is unnecessary here: the log file is already `0644`, so only the
directory's traverse+list bit is missing, and a plain `chgrp adm` + `chmod 0750` matches the
convention every other log directory on the box already uses (`/var/log/nginx` is `root:adm`,
`/var/log/audit` is `root:adm 0750`, `/var/log/unattended-upgrades` is `root:adm 0750`). Fewer
mechanisms, same result.

**Rejected - a `systemd.path` unit with `PathModified=/var/lib/docker/containers` instead of the
timer.** More elegant and instant. Rejected because I could not verify offline which inotify events
systemd's `PathModified=` subscribes to for a **directory**, and an unverified trigger that never
fires is indistinguishable from no fix at all until someone checks the log group weeks later. The
timer's semantics are unambiguous. **Recorded as a deferred optimisation:** once someone can test
it on a real host, `PathModified=` plus a `docker.service` `ExecStartPost` drop-in would reduce the
worst-case gap from 60 s to milliseconds. Not worth touching `docker.service` on an unsnapshotted
box for that today.

**Rejected - tightening `o::r` to the default ACL only, dropping it from the access ACL.** Almost
certainly correct (only the *inherited* `other::` matters for the per-container `/etc/hosts`), and
it would stop the json container logs being world-readable. Rejected **for this change** because it
is a second variable in a fix whose primary job is to stop a documented production incident from
recurring, and because the world-readability is the status quo (`:951` already does it), not a new
exposure. Worth a separate, separately-testable follow-up.

**Rejected - running the reconciler from `cron` instead of a systemd timer.** No advantage;
systemd gives ordering (`After=docker.service`), `journalctl` visibility, and `systemctl
list-timers` introspection for free. The box already runs an hourly `pg_dump` from cron, so cron
exists - but the reconciler genuinely wants the docker ordering dependency.

**Rejected - "just restart the agent after every deploy" from the buildspec.** Would not help: the
problem is the ACL on the directory, not the agent's process state. Restarting a correctly-
configured agent that cannot read the files changes nothing.

**Rejected - declaring B2 done on `sudo -u cwagent test -r <path>` alone** (the dossier's
verification). That check exercises *a* process running as cwagent, not *the agent*. It cannot
distinguish "the grant is right" from "the agent does not use the grant" - which is exactly the
uncertainty flagged in I6 item 2. T3's `/proc/<agent-pid>/status` check is the one that closes it,
and T6 (a real stream appearing in `/velocityai/dev/app`) is the one that proves the whole chain.
