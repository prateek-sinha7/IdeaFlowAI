The dossier's root cause is right and its severity is understated. Its **fix is a
data-loss bug as written**: `sweep_expired()`'s expiry test is a directory mtime, and a
POSIX directory mtime is not a liveness signal. Wiring the function as-is deletes the
sandbox of a run that is parked at a human review gate, and of a run that is actively
building. I reproduced both, against the real function, in seconds. The ordering the
dossier prescribes (sweep before `restore_non_terminal_runs()`) is also backwards.

The fix below keeps one filesystem walker, gives it a **required** protected-segment
argument derived from the durable `workflow_runs` rows plus the in-process live registry,
and keeps mtime only as a second necessary condition (it closes the snapshot race). It
also raises the TTL, because arming the sweep at the shipped 48h silently regresses
prototype revision quality for any parent older than two days.

##### I3. Root cause -- confirmed, corrected, or replaced

**Confirmed:** `sweep_expired` exists, has zero callers, and run sandboxes therefore
accumulate forever. [V]

**Corrected, twice.**

**(1) The location is wrong.** Run sandboxes are on the **root** volume, not the EBS data
volume, and dev's root volume is **60 GiB**, not 30 GiB.

```
infra/scripts/bootstrap-ec2.sh:85   DATA_DEV=/dev/nvme1n1
infra/scripts/bootstrap-ec2.sh:86   DATA_MOUNT=/var/lib/postgresql
infra/scripts/bootstrap-ec2.sh:176  mkdir -p /opt/velocityai /opt/velocityai/data/skills \
                                             /opt/velocityai/data/runs ...
docker-compose.yml:104              - /opt/velocityai/data/runs:/app/runs
infra/terraform/app/dev.tfvars:17   root_volume_size_gb = 60
```

There is **no** `mount`/`fstab`/`mkfs` line anywhere in `bootstrap-ec2.sh` targeting
`/opt/velocityai` [V]. `docker-compose.yml:100-102` carries a comment claiming the runs
bind-mount is on "the same EBS data volume so a paused run's files survive instance
replacement" -- that comment is **false** and should be corrected in the same change
(the root volume has `delete_on_termination = true` and zero snapshots, per Appendix 2).

Consequence: the alarms this defect drives are **`velocityai-dev-disk-root-high`**
(`path = "/"`) and **`velocityai-dev-inode-low-root`**, not `disk-data-high`. Both are
currently in ALARM for a different reason (B1: CWAgent never ran, `treat_missing_data =
breaching`), so today they carry no signal either way.

**(2) The severity is understated, and the dossier's own fix is the vector.** The dossier
frames D6 as unbounded disk growth. It is that, but the moment you wire the function as
the dossier prescribes it becomes **deletion of live run data**, because the expiry test
is a directory mtime:

```python
# backend/app/agents/sandbox.py:180
if run_dir.is_dir() and run_dir.stat().st_mtime < cutoff:
    shutil.rmtree(run_dir, ignore_errors=True)
```

A POSIX directory's mtime advances only when an **entry is added, removed, or renamed in
that directory**. Measured [V]:

```
run-dir mtime after overwrite-in-root  changed: False
run-dir mtime after NEW file in SUBdir changed: False
run-dir mtime after NEW file in root   changed: True
```

Both no-change cases are on the hot path:

- **Overwrite in root.** The prototype build loop writes `prototype.html` with `write_file`
  on task 1 and `edit_file` from task 2 onward (`backend/CLAUDE.md`, "Runtime essentials":
  "`write_file` won't overwrite ... prototype Task 1 uses `write_file`, all later tasks +
  fixes use `edit_file`"). Every subsequent task and every fix-loop attempt is an
  overwrite. The run dir mtime freezes at task 1.
- **New file in a subdir.** Fan-out children land at `{run}/subagents/{step}/{i}/`
  (`local.py:450-464`), so a whole wave of worker writes leaves the run dir mtime alone.

And the wait is unbounded: the human review gate is `await event.wait()` raced only
against `cancel_event` (`engine.py:5157-5176`) -- there is **no timeout**. Phase 23 locked
"unbounded redos per gate (human-paced; no cap)". A run can sit at a gate for a week.

**Causal chain, trigger to symptom.**

```
sweep_expired wired on a timer with the shipped mtime predicate
  -> a run is parked at a review gate (or building via edit_file) for > TTL
  -> its run-dir mtime is older than cutoff, because nothing added an ENTRY to the run root
  -> rmtree(<RUNS_ROOT>/<user>/<run>)
  -> user approves the gate / the next build task starts
  -> the build agent's read_file("prototype.html") / read_file("design.md") returns nothing
  -> the run continues on a destroyed workspace and produces a broken or empty deliverable
```

**Reproduced, against the real function, on `dev` @ `3429d2d9`** [V]:

```
CASE B dir-mtime age after the fresh overwrite (h): 72.0
sweep_expired returned: 2
A) parked-at-gate sandbox survives?  False
B) actively-building sandbox survives? False
```

(Case A: a run parked at a review gate for 72h. Case B: a run whose `prototype.html` was
overwritten **one second before the sweep ran**, still reporting a 72.0h-old directory
mtime. TTL 48h. Full script in I8.)

**(3) The dossier's ordering is backwards.** "Call it on application startup in the
lifespan, before `restore_non_terminal_runs()`" is precisely the worst moment for the
mtime predicate: `restore_non_terminal_runs` (`engine.py:5244`) scans exactly the
non-terminal runs -- `("running","planning","clarifying","waiting_for_user","generating",
"analyzing","revising")` (`:5263`) -- and is about to auto-resume or re-arm them. After a
box has been down for longer than the TTL, or with any run parked at a gate, sweeping
first deletes the sandboxes the restore is about to need. See I5 for the correct ordering.

**Four secondary defects in the same function, all [V] by reading it:**

- `shutil.rmtree(..., ignore_errors=True)` means a failed delete is silently counted as a
  success; the returned count can exceed the number of directories actually removed.
- No guard on `runs_root`: `sweep_expired(runs_root="/")` walks `/` two levels deep and
  `rmtree`s every `/*/*`. A misconfigured env var is an unbounded `rm -rf`.
- `user_dir.is_dir()` follows symlinks, so a symlinked user directory makes the loop
  iterate and `rmtree` entries **outside** `RUNS_ROOT`.
- Empty `<user>/` directories are never reclaimed, so inodes leak at one per user forever
  -- directly relevant to the `inode-low-root` alarm.

Plus one operational defect the dossier does not mention: the walk (`iterdir`, `stat`,
`os.walk`, `rmtree`) is **blocking I/O**. Called naively from the lifespan or an asyncio
timer it stalls the single event loop -- which also serves every live SSE stream (A1/A2)
-- for the duration of the walk. It must run in a thread.

current disk usage below is therefore **[I]**, derived from the dossier's own [V]
measurement (`/` at 32% used, 4% inodes) and from repo configuration.

**Determining the real minimum safe TTL.**

| Consumer | Needs the sandbox after the run? | Evidence |
|---|---|---|
| Preview / Files / Audit / download / history reopen | No -- all DB | (b), (c) [V] |
| `WorkflowRun.output`, `/artifacts`, `/summary`, analytics, export | No -- all DB | (b) [V] |
| Auto-resume + user resume | No -- rebuilt from `artifact_refs` | (e) [V] |
| Chained run context | No -- DB | (g) [V] |
| Uploaded-document **text** context | No -- `upload_text` durable mirror | (e) [V] |
| Uploaded-document **raw bytes** | Sandbox-only, but no post-run reader exists | (e) [V] |
| **Revision parent seed (`spec.md`/`design.md`/`tasks.md`)** | **Yes -- unbounded window** | (f) [V] |

So the **correctness floor is 0 hours** -- provided liveness is gated by the database
rather than by mtime. Nothing breaks. What the TTL actually buys is **revision quality**,
and that has no natural bound: a user can revise a prototype whenever they like.

**The number: 168 hours (7 days).** Reasoning:

1. It must exceed a weekend by a working margin. The shipped 48h does **not**: a build
   finished Friday 17:00 and revised Monday 09:00 is 64h old, so its `design.md` seed
   would already be gone and FIX-050's mandatory read would fail. That single scenario is
   the argument against 48.
2. 7 days covers "I built it last Friday, I am revising it this Friday", which is the
   realistic upper end of an interactive revision loop.
3. Changing the constant is **free of regression risk** because it is currently dead
   (zero callers), so there is no existing behaviour to preserve.
4. It is a setting, so ops can tighten it once the dry-run audit (I5, step 5) produces a
   real per-run byte figure.

Disk arithmetic, **[I]** because I cannot `du` the box: dev's root volume is 60 GiB with
`/` reported at 32% used, leaving roughly 40 GiB. A prototype run's sandbox is
`prototype.html` + `spec.md` + `design.md` + `tasks.md` + a seeded `template.html` capped
at `EXAMPLE_MAX_CHARS = 120_000` (FIX-032), so order 0.3-1 MB; a code-gen run is larger;
a run with uploads is capped at 40 MB aggregate (`run_files.py` `_MAX_AGGREGATE_BYTES`).
At 7 days of retention this is bounded and small relative to 40 GiB, and it is a strict
improvement on today's unbounded growth. The dry-run audit replaces this estimate with a
measurement before anyone tunes it.

```python
# ---------------------------------------------------------------------------
# Expired-sandbox reclamation (D6)
# ---------------------------------------------------------------------------
#
# TWO independent NECESSARY conditions must hold before any rmtree:
#
#   1. the run dir's mtime is older than the TTL, AND
#   2. its directory NAME is not in ``protected_segments``.
#
# (1) alone is NOT a liveness signal and never was. A POSIX directory's mtime
# only advances when an ENTRY is added / removed / renamed IN THAT directory.
# Overwriting an existing file (the task_loop ``edit_file`` path from task 2
# onward) or creating a file in a SUBdirectory (a fan-out worker writing under
# ``subagents/``) leaves the run dir's mtime frozen -- so a run that has been
# live for longer than the TTL looks expired. Measured: a run parked at a human
# review gate for 72h, and a run whose prototype.html was overwritten one second
# ago, were BOTH deleted by the pre-D6 predicate.
#
# (2) is the real gate. The caller derives it from the durable ``workflow_runs``
# rows plus the in-process live registry and maps DB id -> disk segment FORWARD
# via ``run_dir_segment``.
#
# (1) is RETAINED as the second necessary condition because it closes the
# snapshot race: a run created AFTER the protected set was computed has a fresh
# mtime, so it is never a candidate no matter how stale the protected set is.

# A runs root must be at least this many path segments deep. Guards against a
# misconfigured RUNS_ROOT ("/", "/app") turning a janitor into `rm -rf /*/*`.
_MIN_RUNS_ROOT_DEPTH = 2


class UnsafeRunsRoot(ValueError):
    """The configured runs root is too shallow to sweep. Never swallowed."""


@dataclass(frozen=True)
class SweepResult:
    """One sweep cycle's outcome -- the audit record for the janitor."""

    scanned: int = 0                 # level-2 run dirs examined
    protected: int = 0               # skipped: live or recently terminal
    too_young: int = 0               # skipped: mtime >= cutoff
    removed: int = 0                 # actually deleted (always 0 when dry_run)
    failed: int = 0                  # raised on delete -- retried next cycle
    bytes_removed: int = 0           # measured immediately before delete
    empty_users_removed: int = 0     # reclaimed <user>/ dirs (inode hygiene)
    candidates: tuple[str, ...] = () # "<user_seg>/<run_seg>" per candidate
    dry_run: bool = False


def _validated_runs_root(runs_root: str | None) -> Path:
    root = Path(runs_root or settings.RUNS_ROOT).resolve()
    meaningful = [p for p in root.parts if p not in ("/", "\\")]
    if len(meaningful) < _MIN_RUNS_ROOT_DEPTH:
        raise UnsafeRunsRoot(
            f"refusing to sweep {str(root)!r}: a runs root must be at least "
            f"{_MIN_RUNS_ROOT_DEPTH} path segments deep"
        )
    return root


def _dir_size_bytes(path: Path) -> int:
    """Bytes under ``path`` (never follows symlinks; unreadable entries skipped)."""
    total = 0
    for dirpath, _dirnames, filenames in os.walk(path, onerror=lambda _e: None):
        for name in filenames:
            try:
                total += os.lstat(os.path.join(dirpath, name)).st_size
            except OSError:
                continue
    return total


def sweep_expired(
    *,
    protected_segments: Collection[str],
    ttl_hours: int | None = None,
    runs_root: str | None = None,
    dry_run: bool = False,
) -> SweepResult:
    """Remove EXPIRED and NOT-PROTECTED run dirs under ``<RUNS_ROOT>/<user>/<run>``.

    ``protected_segments`` is REQUIRED and has no default. A caller must state
    explicitly which directory names are off-limits; passing an empty collection
    is a deliberate assertion that nothing is live, never an accidental default.
    Derive it with :func:`run_dir_segment` -- see ``app.agents.sandbox_sweeper``.

    Walks exactly two levels. Symlinked ``<user>/`` and ``<run>/`` entries are
    skipped (a symlinked user dir would otherwise make the walk rmtree entries
    OUTSIDE the runs root). A candidate is re-checked for containment under the
    validated root after ``resolve()``.

    ``dry_run=True`` performs the full walk and returns the candidate list
    WITHOUT deleting anything -- the auditable first pass.

    Deletion uses ``rmtree`` WITHOUT ``ignore_errors``: a failure is counted and
    logged, never silently reported as a success. A partially-removed tree is
    retried on the next cycle.

    Raises:
        UnsafeRunsRoot: the configured root is too shallow to sweep safely.
    """
    root = _validated_runs_root(runs_root)
    if not root.is_dir():
        return SweepResult(dry_run=dry_run)

    ttl = settings.RUN_DIR_TTL_HOURS if ttl_hours is None else ttl_hours
    cutoff = time.time() - (ttl * 3600)
    protected = frozenset(protected_segments)

    scanned = protected_hits = too_young = removed = failed = 0
    bytes_removed = empty_users = 0
    candidates: list[str] = []

    for user_dir in sorted(root.iterdir()):
        if user_dir.is_symlink() or not user_dir.is_dir():
            continue
        survivors = 0
        for run_dir in sorted(user_dir.iterdir()):
            if run_dir.is_symlink() or not run_dir.is_dir():
                survivors += 1
                continue
            scanned += 1
            rel = f"{user_dir.name}/{run_dir.name}"
            if run_dir.name in protected:
                protected_hits += 1
                survivors += 1
                continue
            try:
                mtime = run_dir.stat().st_mtime
            except OSError:
                survivors += 1
                continue
            if mtime >= cutoff:
                too_young += 1
                survivors += 1
                continue
            try:
                if not run_dir.resolve().is_relative_to(root):
                    survivors += 1
                    continue
            except OSError:
                survivors += 1
                continue
            candidates.append(rel)
            if dry_run:
                survivors += 1
                continue
            size = _dir_size_bytes(run_dir)
            try:
                shutil.rmtree(run_dir)
            except OSError as exc:
                failed += 1
                survivors += 1
                logger.warning("sandbox sweep: failed to remove %s: %s", rel, exc)
                continue
            removed += 1
            bytes_removed += size
            logger.info(
                "sandbox sweep: removed run dir %s age_h=%.1f bytes=%d",
                rel, (time.time() - mtime) / 3600.0, size,
            )
        if not dry_run and survivors == 0:
            try:
                user_dir.rmdir()  # succeeds only when genuinely empty
                empty_users += 1
            except OSError:
                pass

    logger.info(
        "sandbox sweep: root=%s ttl_h=%s dry_run=%s scanned=%d protected=%d "
        "too_young=%d removed=%d failed=%d bytes_removed=%d empty_users_removed=%d",
        root, ttl, dry_run, scanned, protected_hits, too_young, removed, failed,
        bytes_removed, empty_users,
    )
    return SweepResult(
        scanned=scanned,
        protected=protected_hits,
        too_young=too_young,
        removed=removed,
        failed=failed,
        bytes_removed=bytes_removed,
        empty_users_removed=empty_users,
        candidates=tuple(candidates),
        dry_run=dry_run,
    )
```

*Why a required keyword and not a default of `frozenset()`:* a default makes the unsafe
call the easy one. This is the same reasoning that makes A2's fan-out subscribe live
inside the generator rather than the endpoint body -- put the safe thing where forgetting
it is impossible.

*Why keep mtime at all:* dropping it would make the sweep depend entirely on a snapshot
of the database, and a run created between the snapshot and the walk would be deleted.
With mtime as an AND condition, a freshly-created run dir cannot be a candidate.

```python
"""app/agents/sandbox_sweeper.py -- the periodic run-sandbox janitor (D6).

``app.agents.sandbox.sweep_expired`` is the filesystem half: given the set of
directory segments that must be preserved, it deletes the rest. This module is
the other half. It derives that protected set from the DURABLE ``workflow_runs``
rows (plus the in-process live registry the caller supplies) and drives one sweep
on a periodic asyncio task owned by the FastAPI lifespan.

Why the split:
  * ``sandbox.py`` is imported by the engine on every run and must stay free of a
    database dependency;
  * keeping the walker pure (filesystem + an explicit protected set) is what makes
    it unit-testable without a database.
There is exactly ONE walker and exactly ONE liveness source (INV-12).

Why a periodic asyncio task and not a host cron or a scheduler library:
  * a host cron cannot see the application's notion of liveness without a second
    implementation of the protection query (INV-12), and per C1 a host-side change
    cannot reach a running instance at all;
  * APScheduler would be a new dependency for something ``asyncio.create_task`` +
    ``asyncio.sleep`` already does, and the codebase has no scheduler precedent;
  * the app is single-process by construction (module-level ``_PIPELINE_QUEUES``
    etc. already block horizontal scaling -- dossier Appendix 2), so an in-process
    timer has no cross-node coordination problem to solve.

Why the walk runs in a thread: ``iterdir``/``stat``/``os.walk``/``rmtree`` are
blocking, and the single event loop also serves every live SSE stream. The house
idiom for this is ``asyncio.to_thread`` (``app/services/handoff_pipeline.py:390``).
"""

from __future__ import annotations

import asyncio
import logging
from collections.abc import Callable, Collection
from datetime import datetime, timedelta, timezone

from app.agents.sandbox import SweepResult, UnsafeRunsRoot, run_dir_segment, sweep_expired
from app.core.config import settings

logger = logging.getLogger("app.agents.sandbox_sweeper")

LiveRunIdsProvider = Callable[[], Collection[str]]

_SWEEPER_TASK: asyncio.Task | None = None


def _protected_from_db(ttl_hours: int) -> set[str]:
    """Disk segments that must never be swept, derived from ``workflow_runs``.

    Protects a run when EITHER
      * its status is non-terminal (it is live, parked at a gate, or awaiting a
        restart resume), OR
      * it finished (or, lacking a completion timestamp, was created) inside the
        retention window.

    Both the run id and the workspace id are protected: an exec-granting plan
    provisions a SECOND level-2 directory keyed on ``workspace_id``
    (``app/agents/runtime/local.py:665``, reached from ``engine.py:2106``).
    """
    from sqlalchemy import and_, or_

    from app.models.database import SessionLocal
    from app.models.workflow import NON_TERMINAL_RUN_STATUSES, WorkflowRun

    # NAIVE UTC. ``created_at`` / ``completed_at`` are ``DateTime`` without
    # ``timezone=True``, so they round-trip naive on both SQLite and Postgres
    # (verified). Comparing them against an AWARE parameter makes Postgres cast
    # the column using the session TimeZone; a naive cutoff avoids the cast and
    # matches exactly how the rows were written.
    cutoff = datetime.now(timezone.utc).replace(tzinfo=None) - timedelta(hours=ttl_hours)

    db = SessionLocal()
    try:
        rows = (
            db.query(WorkflowRun.id, WorkflowRun.workspace_id)
            .filter(
                or_(
                    WorkflowRun.status.in_(NON_TERMINAL_RUN_STATUSES),
                    WorkflowRun.completed_at >= cutoff,
                    and_(
                        WorkflowRun.completed_at.is_(None),
                        WorkflowRun.created_at >= cutoff,
                    ),
                )
            )
            .all()
        )
    finally:
        db.close()

    protected: set[str] = set()
    for run_id, workspace_id in rows:
        if run_id:
            protected.add(run_dir_segment(run_id))
        if workspace_id:
            protected.add(run_dir_segment(workspace_id))
    return protected


def _protected_now(ttl_hours: int, provider: LiveRunIdsProvider | None) -> set[str]:
    protected = _protected_from_db(ttl_hours)
    if provider is not None:
        try:
            protected |= {run_dir_segment(rid) for rid in provider() if rid}
        except Exception:  # noqa: BLE001 -- a provider bug must never widen the sweep
            logger.warning(
                "sandbox sweep: live-run-id provider failed -- relying on the DB "
                "protected set only", exc_info=True,
            )
    return protected


async def run_sweep_once(
    *,
    live_run_ids_provider: LiveRunIdsProvider | None = None,
    dry_run: bool = False,
) -> SweepResult:
    """One sweep cycle: derive the protected set, walk, then delete.

    Two passes. Pass 1 walks and stats only, producing the candidate list. Pass 2
    RE-DERIVES the protected set immediately before deleting, so a run that went
    live between the two passes (a user resume; a launch) is picked up. The
    remaining window is milliseconds, and any run created inside it has a fresh
    mtime and is filtered by the TTL condition anyway.
    """
    ttl = settings.RUN_DIR_TTL_HOURS

    protected = await asyncio.to_thread(_protected_now, ttl, live_run_ids_provider)
    first = await asyncio.to_thread(
        sweep_expired, protected_segments=protected, ttl_hours=ttl, dry_run=True
    )
    if dry_run or not first.candidates:
        return first

    protected = await asyncio.to_thread(_protected_now, ttl, live_run_ids_provider)
    return await asyncio.to_thread(
        sweep_expired, protected_segments=protected, ttl_hours=ttl, dry_run=False
    )


async def _sweeper_loop(live_run_ids_provider: LiveRunIdsProvider | None) -> None:
    # Let the boot storm drain first (D9: restore_non_terminal_runs re-launches
    # every resumable run at once, uncapped). The sweep must not compete with it
    # for the event loop or the thread pool.
    await asyncio.sleep(settings.SANDBOX_SWEEP_INITIAL_DELAY_SECONDS)
    first_cycle = True
    while True:
        # The FIRST cycle after every process start is always a dry run, so each
        # deploy leaves an auditable "here is what I would have deleted" record
        # without requiring an ops flag flip (which, per C1, is awkward to land on
        # a running instance). SANDBOX_SWEEP_DRY_RUN extends that indefinitely.
        dry = settings.SANDBOX_SWEEP_DRY_RUN or first_cycle
        try:
            result = await run_sweep_once(
                live_run_ids_provider=live_run_ids_provider, dry_run=dry
            )
            if dry and result.candidates:
                logger.info(
                    "sandbox sweep [DRY-RUN]: %d run dir(s) WOULD be removed: %s",
                    len(result.candidates), ", ".join(result.candidates[:50]),
                )
        except asyncio.CancelledError:
            raise
        except UnsafeRunsRoot as exc:
            logger.error("sandbox sweep DISABLED -- %s", exc)
            return
        except Exception:  # noqa: BLE001 -- one bad cycle must not kill the janitor
            logger.exception("sandbox sweep cycle failed -- continuing")
        first_cycle = False
        await asyncio.sleep(settings.SANDBOX_SWEEP_INTERVAL_SECONDS)


def start_sandbox_sweeper(*, live_run_ids_provider: LiveRunIdsProvider | None = None) -> None:
    """Start the janitor. Idempotent. Must be called AFTER the restore scan."""
    global _SWEEPER_TASK
    if not settings.SANDBOX_SWEEP_ENABLED:
        logger.info("sandbox sweeper disabled (SANDBOX_SWEEP_ENABLED=false)")
        return
    if _SWEEPER_TASK is not None and not _SWEEPER_TASK.done():
        return
    # A STRONG module-level reference: asyncio holds only weak references to
    # tasks, so a task whose only reference was local could be collected mid-sleep.
    _SWEEPER_TASK = asyncio.create_task(
        _sweeper_loop(live_run_ids_provider), name="sandbox-sweeper"
    )
    logger.info(
        "sandbox sweeper started ttl_h=%d interval_s=%d initial_delay_s=%d dry_run=%s",
        settings.RUN_DIR_TTL_HOURS,
        settings.SANDBOX_SWEEP_INTERVAL_SECONDS,
        settings.SANDBOX_SWEEP_INITIAL_DELAY_SECONDS,
        settings.SANDBOX_SWEEP_DRY_RUN,
    )


async def stop_sandbox_sweeper() -> None:
    """Cancel and await the janitor. Idempotent; safe to call when never started."""
    global _SWEEPER_TASK
    task, _SWEEPER_TASK = _SWEEPER_TASK, None
    if task is None or task.done():
        return
    task.cancel()
    try:
        await asyncio.wait_for(task, timeout=10)
    except (asyncio.CancelledError, TimeoutError):
        pass
    logger.info("sandbox sweeper stopped")
```

##### I6. Ripple-effect analysis -- why nothing else breaks

Assume the fix is wrong and hunt for the failure.

**"The protected set is computed, then a run goes live, then you delete its dir."**
Three defences. (i) mtime: a run that just started has a fresh dir mtime and is never a
candidate. (ii) Pass 2 re-derives the protected set immediately before deleting, so the
exposure window is milliseconds rather than a whole walk. (iii) The in-process registry is
consulted, and `POST /resume` registers the task **before** flipping the row (Phase 50's
ordering pin: owner -> eligibility -> overlap -> queue-register -> status-flip), so the
registry leads the database. Residual: a run resumed inside those milliseconds could have
its rematerialised files deleted. Consequence is a **wasted re-run**, not data loss --
`_rematerialize_artifacts_to_disk` rebuilds from `artifact_refs` and the step re-executes.
Stated, not hidden.

**"A run whose row was deleted from History."** FIX-004's `delete_run` removes the row and
nine child tables but not the sandbox [V]. Such a directory is unprotected by construction
and is reclaimed once its mtime ages past the TTL -- which is the desired outcome and the
one thing a DB-only predicate would have missed.

**"A run that has no `WorkflowRun` row at all."** `agents/factory.py:211` falls back to
`RunSandbox(ctx.user_id or "anon", ctx.run_id or "adhoc")`, so a `ctx.run_id`-less
invocation lands in a shared `anon/adhoc` directory. Not reachable from the REST launch
path (which always supplies a run id) [V]; if it ever occurs, the directory is treated as
an orphan and aged out on mtime. That is correct.

**"Two runs, one directory."** Impossible for real runs: `WorkflowRun.id` is a `uuid4`
string (`app/models/workflow.py:19`) and `_safe_segment` is the identity map over uuid4 --
proven over 2,000 samples [V]. The only collisions the map can produce require ids longer
than 128 characters or containing characters outside `[A-Za-z0-9._-]`, neither of which a
uuid4 has.

**"An unattached client / a slow client."** Irrelevant -- the janitor never touches the
SSE path. It does hold the event loop only for `await`s; the walk itself is in a thread.

**"A crashed run."** Its row is left non-terminal until the next `restore_non_terminal_runs`
scan, so it is protected. When the scan flips it to `failed` (branch (c)), it becomes
sweepable -- with `completed_at` still NULL, so the query falls back to `created_at`, and
if the run is younger than the TTL it stays protected. That is correct: a user may click
"Reopen & fix" (Phase 50), which rebuilds from `artifact_refs` anyway.

**"A restart."** The janitor's first cycle after every start is a dry run, so a restart
during an incident cannot cause a deletion for at least
`INITIAL_DELAY + INTERVAL` = 300s + 3600s.

**"A resume."** Covered above and in I4(e): every resume path rebuilds the sandbox from
the durable store.

**"A fan-out run."** Workers write under `{run}/subagents/...` (level 3). The two-level
walk cannot orphan a child, and the parent is protected while the run is live.

**"A revision run."** The one real behaviour change -- see I11 open decision 1. A revision
whose parent is older than the TTL loses its `spec.md`/`design.md`/`tasks.md` seed. It does
not crash (`previous_run` logs and continues) but the output degrades, exactly the failure
FIX-050 fixed. This is why the TTL rises to 168h and why the honest mitigation
(re-point `read_parent_file` at the durable typed artifacts, with disk first) is named as a
sequenced follow-up rather than smuggled in here.

**"Two browsers."** No interaction.

**"Memory / connection-pool effects."** The protection query is one bounded `SELECT` per
pass returning two columns; it opens and closes its own `SessionLocal` in a `finally`,
matching the BUG-004 discipline documented at `run_stream.py:251-265`. Two sessions per
cycle, hourly. Negligible against `pool_size=20, max_overflow=40`.

**"Event-loop starvation."** The walk and every `rmtree` run in `asyncio.to_thread`. The
default thread pool is `min(32, cpu+4)`; one long-lived worker per cycle is fine on a
4-vCPU box, and it is the same idiom `handoff_pipeline.py` already uses for git.

**"Partial application."** Each step is independently safe:
- Steps 1-3 alone: pure refactor, no behaviour change.
- Step 4 alone: `sweep_expired` still has zero callers, so it is a signature change to
  dead code. Strictly safer than today (it cannot be called without a protected set).
- Step 5 alone: a new module nobody imports.
- Step 6 alone: raises a dead constant and adds four unread settings.
- Step 7 without steps 4-6: `ImportError` at startup -- caught by the surrounding
  `try/except` and logged non-fatally, so the app still boots. Land 4-6 before 7.

**"The 'nothing else reads the sandbox' claim is wrong."** The two searches that would
have caught a missed reader are in I4(b) and I4(c): every `FileResponse`/`StreamingResponse`
in `app/` and every `RunSandbox(` construction outside tests. Both are exhaustive greps,
both are quoted with their output.

**"The dossier already argued this is safe."** It did not argue safety at all -- it
proposed a wiring and moved on. The one safety-adjacent claim it makes ("Startup alone is
insufficient for a long-lived process") is true and I keep it; the ordering claim
("before `restore_non_terminal_runs()`") is wrong and I reverse it.

```python
Fully offline: a temp RUNS_ROOT + an in-memory SQLite ``workflow_runs`` table.
No Bedrock, no Postgres, no network.

does not advance when an existing file is overwritten (the task_loop ``edit_file``

parked at a human gate, or actively building, looked expired and was deleted.

import os
import time
from datetime import datetime, timedelta, timezone
from pathlib import Path

import pytest

from app.agents import sandbox as sandbox_mod
from app.agents.sandbox import (
    RunSandbox,

TTL_H = 48
OLD = 72 * 3600          # older than the TTL
YOUNG = 1 * 3600         # inside the TTL

RUN_A = "aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa"
RUN_B = "bbbbbbbb-bbbb-4bbb-8bbb-bbbbbbbbbbbb"
RUN_C = "cccccccc-cccc-4ccc-8ccc-cccccccccccc"

def _seed(root: Path, user: str, run_id: str, *, age_s: int, files=(("out.md", "x"),)):
    sb = RunSandbox(user, run_id, runs_root=str(root))
    sb.ensure()
    for rel, content in files:
        sb.write(rel, content)
    stamp = time.time() - age_s
    os.utime(sb.root, (stamp, stamp))
    return sb

def test_live_run_dir_survives_an_ancient_mtime(tmp_path):

    root = tmp_path / "runs"
```

##### I9. Rollback

**Repo-side.** The change is one new file plus five edited files, all in one commit range.
`git revert` restores the previous state exactly. Nothing persists outside the process:
no migration, no table, no column, no host file, no AWS resource, no SSM parameter.

**Instant kill switch, no deploy.** Set `SANDBOX_SWEEP_ENABLED=false` in the backend
container environment and restart the container. `start_sandbox_sweeper` returns
immediately and no walk ever runs. Setting `SANDBOX_SWEEP_DRY_RUN=true` is the softer
option -- the janitor keeps reporting candidates but deletes nothing.

**What is NOT reversible.** A deleted sandbox directory. There is no filesystem-level
rollback: the root volume carries `delete_on_termination = true` with **zero snapshots**
(dossier Appendix 2), and the run sandboxes are on that volume (see I3). This is exactly
why the fix is built around a required protected set, a first-cycle dry run, and the
mtime condition as a second gate -- there is no undo, so the deletion must be impossible
rather than unlikely.

**What a pre-change backup must capture, if one is taken at all.** The honest answer is
that a full copy of `/opt/velocityai/data/runs` is unnecessary and probably impractical:
by I4's evidence, nothing user-facing reads it, and the only content that is
sandbox-only-and-not-in-the-database is (a) raw uploaded bytes under `.uploads/` and
(b) the `spec.md`/`design.md`/`tasks.md` that a future revision would want to seed from.
If a backup is wanted before the first non-dry cycle, capture exactly those:

```bash
tar -czf /root/runs-seed-backup-$(date +%s).tar.gz \
  -C /opt/velocityai/data/runs \
  $(cd /opt/velocityai/data/runs && find . -maxdepth 3 \
      \( -name spec.md -o -name design.md -o -name tasks.md -o -path '*/.uploads/*' \) -print)
```

Store it off the root volume (the pg-dump S3 bucket already exists for dev).

**If the janitor deletes something it should not have.** The dry-run log line names every
candidate before the first real cycle, and every real deletion is logged with run id, age
and bytes -- so the blast radius is enumerable after the fact. Recovery for a run whose
sandbox was wrongly deleted is: resume it (`POST /api/runs/{id}/resume`), which rebuilds
the file-backed artifacts from `artifact_refs`.

##### I11. Open questions requiring a human decision

**1. Revision quality for parents older than the retention window. (Product.)**

Arming the sweep at any TTL introduces a behaviour change the dossier does not mention:
a revision of a parent older than the TTL loses its `spec.md`/`design.md`/`tasks.md` seed.
`prototype_revision` is `single_shot`, so that seed is its **only** source of `design.md`,
and FIX-050 made reading it MANDATORY precisely because skipping it made the agent invent
CSS. The revision does not fail; it gets worse.

- **Option A (recommended, and what the plan above implements):** ship at 168h.
  Covers a full working week, so the overwhelming majority of revisions keep their seed;
  disk growth is bounded. Cost: a revision of a >7-day-old parent degrades silently.
- **Option B:** ship at 168h **and** sequence a follow-up that re-points
  `kernel_services.read_parent_file` at the durable typed artifacts (`spec` / `plan` /
  `task_list` in `artifact_refs`, which already carry the same content inline) with disk
  first and the store as fallback -- exactly the pattern Phase 47 used for uploads. This
  removes the disk dependency entirely and makes the TTL a pure disk-hygiene knob.
  **This is the right end state**; it is out of D6's scope because it changes the revision
  seed path.
- **Option C:** keep 48h. Rejected -- it does not survive a weekend (64h), so it would
  regress the common case on day one.

Recommendation: **A now, B as a named follow-up ticket.**

**2. Who owns the disk budget, and what is the target retention? (Ops.)**

168h is chosen from the revision window, not from measurement -- I could not `du` the box
(expired credentials, and SSM is out of scope). The first non-dry cycle's log line reports
`bytes_removed`, and the dry-run cycle reports the candidate count, which together give
the real per-run figure. Someone must look at that number and decide whether 168h fits the
60 GiB root volume with the headroom they want. Until then the setting is a guess with a
documented rationale, not a measurement.

Recommendation: **land at 168h, review the first week's numbers, tune the setting.**

**3. Should the janitor also reclaim orphaned sandboxes on `DELETE /api/runs/{id}`?**
(Product/scope.) FIX-004 deletes the run row and its children but leaves the sandbox. The
janitor reclaims it after the TTL, which is correct but slow if a user deletes a run
specifically to free space. Adding a `RunSandbox(...).cleanup()` to `delete_run` is a
three-line change in a different file with a different owner.

Recommendation: **out of D6's scope; log it as its own small ticket.** The janitor already
guarantees the space comes back.

##### I12. Shortcuts and alternatives explicitly rejected

**1. The dossier's fix as written: call it on startup before `restore_non_terminal_runs()`,
plus a timer.** Rejected: it deletes live run data. Reproduced -- a run parked at a review
gate for 72h and a run whose `prototype.html` was overwritten one second earlier were both
deleted at TTL=48h. The startup-first ordering compounds it, because the restore scan is
about to resume exactly the runs the naive sweep just destroyed.

**2. Keep the mtime predicate and just "touch" the run dir periodically while a run is
live.** Rejected: it makes correctness depend on a heartbeat that a crash, a pause, or a
missed code path silently defeats -- and the failure mode is deletion. It also adds a
write to the hot path for every live run. The database already knows which runs are alive.

**3. Drop mtime entirely and sweep purely from the database.** Rejected for two concrete
reasons. (a) It loses the snapshot race: a run created between the protected-set query and
the walk would have no protecting row in the snapshot and would be deleted. (b) Sandboxes
whose run row was deleted by FIX-004's `delete_run` have no row at all and would be
immortal -- the exact unbounded growth D6 is about. Both conditions are necessary.

**4. Use the in-process registries (`_PIPELINE_TASKS` / `_PIPELINE_QUEUES`) as the sole
liveness signal.** Rejected: they are empty at startup and after every restart, so the
first cycle after a deploy would consider every run dead -- including the ones
`restore_non_terminal_runs` is resuming. They are used as an **additional** protection
source, never the only one.

**5. Delete the sandbox at run terminal (hang it off the driver `finally`, or off D4/D5's
proposed `forget_run` hook).** Tempting because the lifecycle is known exactly -- and D4's
own text argues for precisely that shape for the in-memory dicts. Rejected for the
sandbox: it breaks two shipped features outright. The revision path reads the parent's
sandbox after the parent terminates (`previous_run` -> `read_parent_file`), and Phase 50's
"Reopen & fix" resumes a **failed** run whose sandbox would already be gone. A TTL is not
laziness here; the lifetime genuinely extends past the run.

**6. A host cron in `bootstrap-ec2.sh`.** Rejected on three counts. (a) Per C1 a host-side
change cannot reach a running instance, so it would be unshippable to dev without an SSM
action. (b) A cron cannot see the application's liveness without a second implementation
of the protection query -- an INV-12 dual implementation of the most safety-critical part
of the fix. (c) It would run as root outside the container against a bind mount, widening
the blast radius of a delete loop for no benefit.

**7. APScheduler (or any scheduler dependency).** Rejected: a new runtime dependency for
what `asyncio.create_task` + `asyncio.sleep` already does, in a codebase with no scheduler
precedent and an explicit "extend, don't replace" stack constraint.

**8. `shutil.rmtree(..., ignore_errors=True)` (keeping the current call).** Rejected: it is
what makes today's return value a lie -- a directory that failed to delete is still
counted as removed. A janitor whose audit line cannot be trusted is worse than none.

**9. Skip the runs-root depth guard because "RUNS_ROOT is always /app/runs".** Rejected:
`RUNS_ROOT` is a pydantic setting readable from the environment (`config.py:173`), the
function also takes an explicit `runs_root` argument, and the operation is an unbounded
`rm -rf` two levels deep. A three-line guard against a config typo that has no undo is not
optional.

**10. Compute `bytes_removed` only in dry-run mode to save syscalls.** Rejected: the byte
figure on the real cycle is the number that answers "is 168h the right TTL", which is open
question 2. The extra `os.walk` costs a fraction of the `rmtree` that immediately follows.

**11. Ship with `SANDBOX_SWEEP_DRY_RUN = True` as the default so the first production run
is auditable.** Rejected -- that is how D6 happened. A mechanism that ships inert and
requires someone to remember a flag is a mechanism that never runs. The
first-cycle-is-always-dry design gives the same audit on every deploy with no ops action,
and the flag remains available for a longer window.

**12. Reuse `state_machine.TERMINAL_STATES` as the liveness vocabulary.** Rejected: it is
`{completed, failed, cancelled}` and omits `degraded`, which is terminal at the DB level
(`app/models/workflow.py:24-29`). Using it would leave every degraded run's sandbox
protected forever. The two sets are genuinely different and must stay separate.

**13. Add a fourth copy of the `NON_TERMINAL` tuple in the sweeper.** Rejected on INV-12.
There were already three (`engine.py:5263`, `scripts/cutover_legacy_runs.py:28`, and the
prose at `:5419`/`:5601`); the fix collapses them onto one constant rather than adding to
the pile.

**14. Put the DB query inside `sandbox.py`.** Rejected: `sandbox.py` is imported by
`agents/factory.py` and `agents/execution_engine/engine.py` on every run and currently
depends only on `app.core.config`. Giving it a database dependency couples the hot path to
the ORM and makes the walker untestable without a database. The split keeps one walker and
one liveness source while preserving both properties.

**15. Bound the walk to the last N directories, or sample.** Rejected: correctness of a
delete decision must not depend on where a directory happens to sort. The walk is
`stat`-only per directory and runs hourly in a thread; there is no cost problem to
optimise away.
