**CONFIRMED, and independently reproduced.** I did not take the dossier's measurements on
faith. I stood up nginx 1.24.0 (the live box's exact version) in Docker, fed it the site file
**rendered verbatim from `bootstrap-ec2.sh`**, the verbatim `velocityai-limits.conf`, and the

The SSE URL lands in the rate-limited `/api/` prefix location. [V]

```

21/19, matching the dossier's `21 x 200, 19 x 429`. The 21 is `burst=20` plus the one request
the `120r/m` bucket admits immediately. [V]

**Causal chain, re-derived from first principles:**

1. `run_stream.py:64` declares `prefix="/api/runs"`; `:208` declares `/{workflow_id}/events/stream`.
   The effective URL is `/api/runs/<uuid>/events/stream`. [V]
2. The frontend builds exactly that: `useRunStream.ts:338`
   `const url = \`${ENV.API_URL}/api/runs/${runId}/events/stream\``, and in production
   `ENV.API_URL` resolves to `""` (same-origin) -- `frontend/src/lib/env.ts` `resolveApiUrl()`
   returns `""` for any non-localhost browser host. So the live request line is literally
   `GET /api/runs/<uuid>/events/stream`, **no query string, no trailing slash**. [V]
3. nginx has **no regex location and no `^~` prefix location** in this server block
   (`grep -cE '^\s*location\s+~'` = 0; `grep -cE '\^~'` = 0). [V] So the longest prefix match
   wins, which is `/api/` -- carrying `limit_req zone=velocityai_api burst=20 nodelay`.
4. `velocityai_api` is `rate=120r/m` = **2 requests per second per `$binary_remote_addr`**,
   shared with every other `/api/` call the page makes. A run screen's normal REST chatter
   (`/api/runs`, `/api/runs/{id}`, `/api/runs/{id}/events`, `/api/analytics/summary`,
   `/api/agents/library`, `/api/capabilities`, `/api/workflows`) drains the burst; the stream
   attach then draws a 429.
5. `useRunStream.ts:359-360` treats any non-OK as fatal (`throw`); `:405-408` catches and calls
   `scheduleReconnect()`; `:296-309` sets `phase = "reconnecting"` and backs off
   `1 -> 2 -> 4 -> 8 -> 16 -> 30s` (`MAX_RETRY_DELAY_MS = 30000`, `:98`). `dashboard/page.tsx:44`
   maps that phase to the banner. Navigating away unmounts the hook, resetting
   `retryCountRef` -- hence the "go Home and come back" workaround. [V]

**Where the dossier is right for the right reason:** the assumption that broke is "every URL
under `/api/` is a short request". That is a *category* error, not a tuning error. Raising the
rate would not fix it (a stream is not a rate phenomenon) and would weaken a limiter that
protects genuinely expensive endpoints.

**Six corrections / refinements:**

- **C1 (material).** The dossier does not state that a `limit_conn` rejection re-enters the
  **same** `!res.ok` throw at `useRunStream.ts:359` and produces the **same** "Reconnecting..."

  undersized `limit_conn` reproduces the exact reported symptom, just with a 503 in the access
  log instead of a 429. This is why the cap must be generous and why leaving
  `limit_conn_status` at the default 503 (so the two are distinguishable) is essential, not
  cosmetic. See I6.1.
- **C2.** The dossier claims all three non-exempt streaming endpoints "emit a comment frame
  every 15 seconds regardless of what the body generator is doing". True for the two
  `EventSourceResponse` endpoints (`run_commands.py:1414`, `:2601`) -- and I confirmed the

  (`prototype_templates.py:287`): that is a bare Starlette `StreamingResponse`, which has no

- **C3.** The dossier tags the HTTP/2 `limit_conn` accounting as an assertion. I proved it.

##### I4. Blast-radius sweep -- every place this reaches

**I4.1 -- Every location in the server block, and what the new regex does to it.**

`nginx` picks locations in this order: exact `=` matches, then prefix matches (remembering the
longest), then **regex in definition order** -- unless the longest prefix match used `^~`.
There are currently zero regex locations and zero `^~`, so a single new regex wins over every
prefix location regardless of where it sits. I proved this by placing the block **last**, after
`/_next/static/`:

```
### AFTER -- 40 concurrent GETs to the SSE path, regex placed LAST
  40 200
--- location that matched ---
  40 200 LOC=sse-regex
```

Then I checked every other location still routes as before:

```
/health                -> 200
/openapi.json          -> 200
/docs                  -> 404   (exact match still beats the regex)
/redoc                 -> 404   (exact match still beats the regex)
/ws/chat               -> 200  LOC=/ws/chat
/mcp/x                 -> 200  LOC=/mcp/
/install/x             -> 200  LOC=/install/
/_next/static/a.css    -> 200  LOC=/_next/static/
/                      -> 200  LOC=/
/api/_ratelimit_probe  -> 429  LOC=/api/     (limiter intact)

All unaffected. [V] The exact-match locations are safe by nginx's own precedence rule (exact
beats regex), and I confirmed it empirically rather than trusting the rule.

**I4.2 -- Can the regex match anything other than the SSE route?** Measured, one request per
shape, reading the `$loc` the access log recorded:

```
/api/runs/abc/events/stream                -> LOC=sse-regex
/api/runs/abc/events/stream/               -> LOC=sse-regex   (the /?$ branch)
/api/runs/abc/events/stream?after=5        -> LOC=sse-regex   (query string is not part of $uri)
/api/runs/abc/events/stream/extra          -> LOC=/api/       (anchored $)
/api/runs/abc/events                       -> LOC=/api/
/api/runs/abc/messages                     -> LOC=/api/
/api/runs/a/b/events/stream                -> LOC=/api/       ([^/]+ rejects a 2-segment id)
/api/runs//events/stream                   -> LOC=/api/       (empty id)
/api/runsX/abc/events/stream               -> LOC=/api/
/api/runs/abc/events/streamX               -> LOC=/api/
/prefix/api/runs/abc/events/stream         -> LOC=/           (anchored ^)
```

[V] The regex is tight: it matches the SSE route and nothing else. `[^/]+` is the correct
segment class because `WorkflowRun.id` is `str(uuid.uuid4())`
(`backend/app/models/workflow.py:19`), which contains no `/`. [V] Percent-encoding is not a
bypass: nginx decodes `%XX` before location matching, so `%2F` in the id decodes to `/` and
*fails* the `[^/]+` class -- i.e. it falls back to the rate-limited `/api/` block, which is the
safe direction. No authorization is affected either way; the endpoint's own two-layer owner
check (`run_stream.py:225-249`) is untouched.

`^/api/runs/[^/]+/events/stream/?` -- an **unanchored** regex that would also swallow
`/api/runs/x/events/stream/anything`. `[^/]+` needs no escaping (`^` is only special to bash
inside `[[ ]]`, not in a heredoc). Verify after editing:

**Six load-bearing details, each with its reason:**

1. **`limit_conn`, not nothing.** Removing all metering leaves an authenticated attach-churn
   amplifier: every attach runs two unbounded `read_events` queries until A5 lands
   (`run_stream.py:151` and `:184`).
2. **64, not a small number, and not unlimited.** Per-IP is blunt behind corporate NAT (the
   whole office shares one `$binary_remote_addr`). A user legitimately holds one stream per
   *actively-building* run plus one sticky focused run -- `AUTO_STREAM_STATUSES` at
   `RunConnectionProvider.tsx:66` plus `focusedRunIdRef`, the BUG-013 bounding. Typical is 1-3
   per tab. 64 therefore admits roughly 20-60 concurrent users from one egress IP, while
   sitting an order of magnitude under the nginx ceiling (~1536 proxied streams box-wide,
   I4.13). And because a rejection produces the *same* banner as the bug being fixed (C1),
   erring small re-creates the symptom.
3. **No `limit_conn_status`.** Leave the default 503. After this ships, **429 on
   `/api/runs/.../events/stream` means the fix did not apply** (still on the `/api/` bucket)
   and **503 means the cap was genuinely reached**. Setting it to 429 destroys that
   distinction and makes E1's `NginxLimit429` metric filter ambiguous.
4. **The `include` is mandatory.** Omitting it drops `proxy_http_version 1.1` (`:719`),

5. **Position is free but fragile.** Proven: placed last, it still won 40/40. The comment
   records the one way to break it later.
6. **No `add_header` in this block, ever** (D3 coordination). `add_header` is

   declares none of its own**. The block as written declares none and I measured 5/5 inherited

   author adds to an SSE location, and it would silently drop all five -- I measured that
   exact injection firing the guard. It is also **unnecessary**: `sse-starlette` force-sets
   the header on every response (`sse_starlette/sse.py:140`, an unconditional assignment, not
   a `setdefault`), and `proxy_buffering off` two lines above is the real control. Hence the
   in-block comment and the dedicated pin `test_sse_location_declares_no_add_header` (I8).

##### I6. Ripple-effect analysis -- why nothing else breaks

I assumed the fix was wrong and went looking.

**1. A `limit_conn` 503 produces the reported symptom.** The real hazard. `useRunStream.ts:359`
throws on **any** non-OK; `:405-408` catches and reconnects; `sawNonLiveAttachRef` (BUG-015)
only guards the close branch at `:398`. So a 503 loops on the same 1/2/4/8/16/30s backoff and
shows the same banner. The frontend cannot tell 429 from 503. Mitigations, in order:
(a) size at 64, well above realistic usage; (b) leave the status at 503 so operators can tell
them apart in the log; (c) once E1 lands, the `NginxLimit429` filter (`upstream_addr = "-"`)
catches the 429 case and a sibling `{ $.status = 503 && $.upstream_addr = "-" }` would catch
this one. I recommend adding that second filter to E1's set -- see I10. I am deliberately
**not** proposing an `useRunStream` change (that is D2's family, and a fatal-on-429 is
arguably correct behaviour for a genuinely capped resource).

**2. Concurrency and ordering.** `limit_conn` state is per-worker-shared-memory and
lock-protected; the counter is released when the request is finalized. Under HTTP/2 each stream
is a separate request with its own pool, hence per-stream accounting -- which I measured
(4 admitted of 8 multiplexed over one TCP connection). No ordering hazard: nginx admits or
rejects at the preaccess phase before any upstream connection is made.

**3. Reload while streams are open.** `systemctl reload` is a graceful `SIGHUP`. Old workers
finish their in-flight requests -- including open SSE streams -- with the **old** config and
exit; new connections use the new config. No stream is cut. The one caveat is that shared
memory zones are re-created on reload, so in-flight counters reset -- harmless for a cap, and
the old workers' streams are not counted against the new zone (they will be undercounted for
the life of those workers). Not a correctness problem for a DoS brake.

**4. Unattached client / slow client / crashed run / restart / resume.** All backend-side and
untouched. A crashed run's stream still terminates via the `None` sentinel or the terminal
event (`run_stream.py:198`, `:204`); a stale registry entry still hangs the client (that is A4,
unchanged); a restart still drops every stream and the frontend reconnects (unchanged). A1
changes only whether the *reconnect* is admitted.

**5. Fan-out and revision runs.** A fan-out run is one `WorkflowRun` with one queue and
therefore **one** stream -- worker events ride the parent stream (`fanout.py`, confirmed in
IMPL Phase 11 `:1155`). It does not multiply the `limit_conn` count. A revision run is a child
`WorkflowRun` with its own id and therefore its own stream; the frontend attaches it via
`attachRun` and the sticky focus **replaces** rather than accumulates (BUG-013,
`RunConnectionProvider.tsx:339-342`). So the per-user stream count stays bounded.

**6. Two browsers / many tabs.** Each tab opens its own set. Two tabs on one run = 2 streams
= 2 of the 64. This is exactly the scenario A2 concerns, and it is the reason A1 must land
first: today the second attach is often 429'd away, which is precisely what makes A2's
corruption intermittent rather than deterministic. A1 does not cause A2 -- it exposes it. See
I10.

**7. Memory and connection pool.** `limit_conn_zone ... 10m` holds on the order of 160k per-IP
states; the box will never approach that. Each admitted stream costs 2 nginx connection slots
of ~3072, and (post-BUG-004) **zero** idle DB connections. The DB pressure comes from A5's
double full-log read at attach time, which is A5's to fix -- A1 raises how often it happens, so
A5 should not lag far behind.

**8. Partial application.** If step 1 (the zone) lands without step 2 (the location), nothing
changes -- an unused zone is inert. If step 2 lands without step 1, **`nginx -t` fails**
(`unknown limit_conn zone`) and the guarded script restores the backup, so the box is never
left in that state. If the host half lands but the repo half does not, the box is fixed until
someone re-runs bootstrap or replaces the instance -- which is exactly the C1 failure mode and
the reason both halves are mandatory.

**9. Does it weaken security?** No. The route's own authorization is untouched: two-layer owner
check at `run_stream.py:225-249`, cross-owner and missing both resolve to 404. The five
security headers are inherited (measured 5/5). The only thing removed is a *rate* limit on a
route that requires a valid JWT and can only ever stream the caller's own run. The remaining
per-IP concurrency cap is a strictly better-shaped control for this route.

**10. What the dossier argues that I re-checked rather than restated.** Its
"`proxy_read_timeout` was never a contributing factor" claim -- verified from the
`sse-starlette` source (independent ping task, I4.8), not from the prose. Its "position is
free" claim -- verified by placing the block last and measuring. Its HTTP/2 accounting claim --
verified by multiplexing 8 streams on one connection.

##### I9. Rollback

**Repo half.** `git revert <commit>` on `dev`. The next `dev` push re-uploads the reverted
script to the per-env S3 key. Fully reversible, no state.

**Host half.** The patch script writes `/root/nginx-backup-<UTC timestamp>/` containing
`velocityai-limits.conf` and `velocityai` **before** it edits anything. To roll back:

```bash
BK=/root/nginx-backup-<ts>
cp -a "$BK/velocityai-limits.conf" /etc/nginx/conf.d/velocityai-limits.conf
cp -a "$BK/velocityai"             /etc/nginx/sites-available/velocityai
nginx -t && systemctl reload nginx
```

Alternatively, re-render from the reverted repo and diff against the box.

**What is NOT reversible.** `velocityai-dev-root` has `delete_on_termination = true` and
**zero snapshots** (dossier Appendix 2). There is no filesystem-level rollback for anything on
that host. The `/root/nginx-backup-<ts>/` copy is the **only** restore point for these two
files -- so the backup step is not optional, and the executor must confirm the backup exists
(the script echoes its path) before trusting the guarded reload. Note also that `/root` lives
on that same undamaged-but-unsnapshotted root volume: if the instance is replaced, both the
change and its backup are gone -- which is precisely why the repo half is mandatory.

**Failure of `nginx -t`.** Zero downtime, zero manual action: the script restores the backup
and exits non-zero. The live master never loaded the bad config.

##### I12. Shortcuts and alternatives explicitly rejected

1. **Raise `velocityai_api` from `120r/m` to something large.** Wrong shape and a real
   regression: it weakens the limiter for every genuinely rate-sensitive endpoint under
   `/api/` -- notably `POST /api/runs/{id}/messages`, which drives a Bedrock call per request.
   And it does not actually fix the stream: at high enough concurrency a *rate* bucket still
   rejects a burst of attaches, so the banner returns under exactly the load that produced it.
2. **`limit_req_status 200` or removing `limit_req_status` from `/api/`.** Turns a rejection
   into a lie. The frontend would see a 200 with an nginx error body and fail on the parse
   instead of the status -- strictly worse to diagnose.
3. **Exempt the whole `/api/runs/` prefix.** Sweeps in `POST /api/runs/{id}/messages` (the
   Concierge Bedrock call), `POST /api/runs/{id}/revisions` (mints a whole run),
   `POST /api/runs/{id}/files` (uploads), `POST /api/runs/{id}/gate`, and the launch endpoint
   itself. Hands an authenticated caller unmetered model spend and unmetered run creation.
4. **Set `limit_conn_status 429`.** Tempting for consistency, and actively harmful: it makes
   the verification ambiguous (I5 detail 3) and blinds E1's `NginxLimit429` filter to the
   difference between "we are throttling attaches" and "we are at the concurrency cap" -- the
   exact distinction operators will need if 64 turns out to be too small.
5. **No metering at all on the stream.** Leaves an authenticated attach-churn amplifier: every
   attach runs two unbounded `read_events` (`run_stream.py:151`, `:184`) until A5 lands, so a
   loop of attach-then-abort is a database and CPU amplifier from a single JWT.
6. **Drop `/?$` from the regex.** Measured: a trailing slash then misses the regex and falls
   back to the rate-limited `/api/`. The frontend does not currently send one, but a future
   caller or a normalising intermediary would silently reinstate the bug.
7. **Use `location ^~ /api/runs/` plus a nested exemption.** A `^~` prefix location suppresses
   regex matching for everything under it, which would break the very mechanism the fix relies
   on and would need re-deriving if a second regex is ever added. It also over-captures
   (rejection 3).
8. **Fix it in the frontend -- retry the 429 with a longer backoff, or treat 429 as
   non-fatal.** Papers over a server misconfiguration in client code, leaves the 429s in the
   access log for the next person to re-diagnose, and does nothing for any other client
   (curl, a future mobile app, the e2e suite). The server is wrong; fix the server.
9. **Skip the host patch and rely on the committed script.** Verified impossible on dev:
   `velocityai-firstboot.service` is gated on `ConditionPathExists=!/var/lib/velocityai/.bootstrap-done`,
   `user_data` is under `ignore_changes` with `user_data_replace_on_change = false`, the CI
   deploy only does `docker compose pull && up -d`, and dev's live userData has **no** firstboot
   service at all. The committed change would sit in S3, unapplied, indefinitely. (This is C1;
   it is why both halves are mandatory.)
10. **Skip the repo half and only patch the host.** The fix then evaporates on instance
    replacement or on any deliberate bootstrap re-run, with no trace in the repo of why the box
    ever differed. That is how the current situation was created.
