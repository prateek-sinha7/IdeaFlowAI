**Correction 2 — the dimension trap, checked explicitly (orchestrator point 3).**

CloudWatch alarm-to-metric matching is **exact on the full dimension set**; an alarm with dimension
set *D* matches only datapoints published with dimension set *D*, not a superset and not a subset.
A sibling agent found this class of defect in the same module for the CWAgent host alarms, and I
verified it independently:

- The agent config sets `append_dimensions: {"InstanceId": ..., "InstanceType": ...}`
  (`bootstrap-ec2.sh:979-982`), so **every** agent-emitted metric carries at least
  `{InstanceId, InstanceType}` (plus plugin dimensions: `cpu` for the cpu plugin with
  `"totalcpu": true`, and `path`/`device`/`fstype` for `disk`). [V]
- `cpu_high` and `mem_high` specify `dimensions = { InstanceId = ... }` only
  (`:376-378`, `:401-403`); `disk_*` and `inode_low` specify `{InstanceId, path}`
  (`:426-429`, `:452-455`, `:1643-1646`). [V]
- Those alarms therefore cannot match the agent's datapoints even once B1/B2 make the agent work.
  Not mine to fix — flagged for E1/B6 — but it is precisely the trap I must not repeat.

**Correction 4 — a latent shell hazard in the exact place the publisher must go.** Discovered by
running it, not by reading. `velocityai-pg-dump` installs `trap 'rm -rf "$TMP"' EXIT` at `:1069`.
In bash, when a script aborts on a **parameter-expansion error** (`: "${VAR:?msg}"`) while an `EXIT`
trap is installed, the script's exit status becomes the status of the **last command in the trap** —
here `rm -rf`, which succeeds:

```
=== :? with EXIT trap whose last cmd succeeds ===
bash: NOPE: required
  rc=0                     <-- the failure is MASKED
=== :? with NO trap ===
  rc=1
=== set -e abort (failed simple command) WITH succeeding EXIT trap ===
  rc=1                     <-- NOT masked
```
[V] (measured on bash 3.2; the Ubuntu target is bash 5.x, so this specific status behaviour on the
box is `[I]` — which is exactly why the fix below avoids `:?` entirely rather than relying on it.)

The existing `: "${VELOCITYAI_BACKUP_BUCKET:?...}"` guards at `:1065-1066` are unaffected because
they run **before** the trap is installed at `:1069`. Any guard added *after* `:1069` — i.e. mine —
would fail silently. The publisher therefore uses an explicit `if ...; then echo >&2; exit 1; fi`.
E3's script has **no** `EXIT` trap (`:1094-1110`), so `:?` is safe there; that asymmetry must be
communicated or E3 will copy the wrong idiom.

###### Artefact 1 (E3 introduces, E2 consumes) — the ONE shared namespace mechanism

**File:** `infra/scripts/bootstrap-ec2.sh`, new sub-section immediately before the existing
`# -- 16. Backups: ...` header at `:1061`.

**Why a runtime helper and not a bake-in.** `ENV_TITLE` (`:82`) is an *install-time* bash variable
inside the bootstrap process. The publishers run hourly, in a different process, hours to months
after bootstrap exited. "Reuse `ENV_TITLE`" therefore has exactly two implementations: bake its
value into the emitted script at install time, or re-derive the same mapping at publish time. Baking
is **fail-open**: `ENVIRONMENT="${VELOCITYAI_ENVIRONMENT:-prod}"` (`:79`) means a box whose
`bootstrap.env` lacked the variable would bake `VelocityAI/Prod` with no runtime signal — which is
the E3 defect, recreated. The orchestrator's binding constraint is fail-closed, so I re-derive at
publish time, **once**, in a shared helper.

**Why an explicit `case` and not a second `${x^}`.** `${x^}` is bash-4+ only, proven:

```
### interpreter: /bin/bash (GNU bash 3.2.57)
  ns-caret env=dev       rc=1  ${VELOCITYAI_ENVIRONMENT^}: bad substitution
  ns-map   env=dev       rc=0  VelocityAI/Dev
  ns-map   env=stage     rc=0  VelocityAI/Stage
  ns-map   env=prod      rc=0  VelocityAI/Prod
  ns-map   env=pre-prod  rc=1  refusing unknown environment 'pre-prod'
  ns-map   env=<unset>   rc=1  VELOCITYAI_ENVIRONMENT is required
```
[V] The Ubuntu target is bash 5.x so `:82` is fine where it is; the point is that `${x^}` and
Terraform's `title()` are **different functions** that merely coincide on the three values
`app/variables.tf:35` allows (`title("pre-prod")` -> `Pre-Prod`; `${x^}` -> `Pre-prod`). An explicit
three-way map is *provably* equal to the Terraform side for exactly the permitted set and refuses
everything else, so the two can never silently diverge.

```bash
# -- 16a. Shared CloudWatch metric namespace for on-host publishers --------
#
# ONE derivation site for the per-environment namespace used by every on-host
# `aws cloudwatch put-metric-data` caller (the pg-dump heartbeat in section 16 and
# the stuck-workflows probe in the same section). It must stay byte-equal to the
# Terraform monitoring module's
#     cw_metric_namespace = "VelocityAI/${title(var.environment)}"
#   (infra/terraform/app/main.tf:173)
# and to this script's own CloudWatch-agent namespace at section 14
#   ("namespace": "VelocityAI/${ENV_TITLE}", :970).
#
# FAIL-CLOSED by design. This script's ENVIRONMENT falls back to "prod" (:79) for
# its install-time needs; propagating that fallback into a metric namespace is
# exactly the defect E3 fixes (dev publishing into VelocityAI/Prod and corrupting
# prod's metric). A publisher that cannot resolve its environment must refuse to
# publish, loudly, rather than guess.
#
# The three-way map mirrors the Terraform variable validation
# (infra/terraform/app/variables.tf:34-37, environment in dev|stage|prod). It is
# used in preference to bash's ${VAR^} because ${VAR^} and Terraform's title()
# are different functions that only agree on those three values -- and because
# ${VAR^} needs bash 4+.
cat > /usr/local/bin/velocityai-cw-namespace <<'EOF'
#!/usr/bin/env bash
# Print the CloudWatch metric namespace for this environment, or fail.
# Reads VELOCITYAI_ENVIRONMENT, which systemd supplies to every publisher unit
# via EnvironmentFile=/etc/velocityai/bootstrap.env (written by Terraform's
# compute module user_data, user_data.sh.tpl:52-53).
set -euo pipefail
if [[ -z "${VELOCITYAI_ENVIRONMENT:-}" ]]; then
    echo "velocityai-cw-namespace: VELOCITYAI_ENVIRONMENT is unset" \
         "(expected from /etc/velocityai/bootstrap.env) - refusing to guess" >&2
    exit 1
fi
case "$VELOCITYAI_ENVIRONMENT" in
    dev)   _env_title=Dev   ;;
    stage) _env_title=Stage ;;
    prod)  _env_title=Prod  ;;
    *)
        echo "velocityai-cw-namespace: unknown environment" \
             "'${VELOCITYAI_ENVIRONMENT}' - refusing to publish" >&2
        exit 1
        ;;
esac
printf 'VelocityAI/%s\n' "$_env_title"
EOF
chmod 0755 /usr/local/bin/velocityai-cw-namespace
```

No systemd unit file changes are required: both publisher units already carry
`EnvironmentFile=/etc/velocityai/bootstrap.env` (`:1149` and `:1207`), so `VELOCITYAI_ENVIRONMENT` is
in their environment already. This is a deliberate design goal — it keeps the host patch to plain
file writes with no `daemon-reload` and no timer restart.

# declares no `dimensions` block, and CloudWatch matches an alarm to a metric on
# the EXACT dimension set. A heartbeat published with any dimension would create
# a different timeseries and leave the alarm permanently breaching -- the same
# class of defect the CWAgent host alarms already have (they specify
# {InstanceId} while the agent appends {InstanceId, InstanceType}).
#
# --region is explicit and mandatory: the instance role's PutMetricData grant is
# conditioned on aws:RequestedRegion (infra/terraform/modules/iam/main.tf:168-172)
# and this unit runs as User=postgres with no ~/.aws/config. Same expression the
# `aws s3 cp` above uses.
#
# The guard below is an explicit `if`, NOT `: "${VAR:?...}"`. A :? abort while the
# `trap ... EXIT` above is installed exits with the TRAP's status (rm -rf, which
# succeeds), so the failure would be silently reported as success. The guards at
# the top of this script are safe only because they precede the trap.
if [[ -z "${VELOCITYAI_CW_NAMESPACE:-}" ]]; then
    CW_NAMESPACE="$(/usr/local/bin/velocityai-cw-namespace)" || {
        echo "velocityai-pg-dump: cannot resolve the CloudWatch namespace;" \
             "backup WAS uploaded but the heartbeat was NOT published" >&2
        exit 1

else
    CW_NAMESPACE="$VELOCITYAI_CW_NAMESPACE"
fi

aws cloudwatch put-metric-data \
    --namespace "$CW_NAMESPACE" \
    --metric-name PgDumpHeartbeat \
    --value 1 \
    --region "${VELOCITYAI_REGION:-eu-central-1}"

# the pipeline RAN; this proves the artefact is not degenerate, so a dump that
# silently collapses (wrong database, empty schema) is detectable. No alarm is
# wired to it yet -- see I11.
aws cloudwatch put-metric-data \
    --namespace "$CW_NAMESPACE" \
    --metric-name PgDumpBytes \
    --value "$DUMP_BYTES" \
    --unit Bytes \
    --region "${VELOCITYAI_REGION:-eu-central-1}"
EOF
chmod 0755 /usr/local/bin/velocityai-pg-dump

Two non-obvious choices, each with its reason:

- **`--value 1` with no `--unit` on the heartbeat.** The alarm's statistic is `SampleCount`, which
  counts datapoints and ignores the value, so `1` is conventional. `--unit` is omitted deliberately:
  the alarm declares no `unit`, so unit is not part of the match today, and adding one creates a
  second attribute that must stay in sync forever. It also keeps the call byte-shaped like E3's
  existing publisher. `PgDumpBytes` does carry `--unit Bytes` because no alarm watches it and the
  unit is genuinely informative.
- **`DUMP_BYTES` hoisted out of the `echo`.** `:1076` already computes `stat -c%s "$DUMP"` inline;
  hoisting it lets the gauge reuse the value instead of stat-ing a second time, and keeps the log
  line byte-identical.

##### I6. Ripple-effect analysis — why nothing else breaks

Adversarial: assume the fix is wrong and hunt for the failure.

**"The Terraform edit changes stage and prod."** It does not, in effect. Terraform state is per
environment (`velocityai/<env>/app.tfstate`, Appendix 2 `:2014`) and the pipeline runs
`$TF/app apply` for the pushed environment only. Editing the shared module changes stage's and
prod's *plan*, so the next apply of those environments will move their alarms to
`VelocityAI/Stage` / `VelocityAI/Prod` — at which point they will be **breaching until those boxes
also get the publisher**. That is the correct, honest outcome (an unwatched backup should alarm), and
it is strictly better than the alternative, which is prod silently reading dev's heartbeat. It is
also **exactly the same posture E1 and E3 have**, so it does not introduce a new class of drift.
Flagged for the operator in I11.

**"The alarm will flap while the first datapoint lands."** It cannot flap; it can only improve.
Pre-change state is ALARM. Post-change, the alarm remains ALARM until the first datapoint lands in
the trailing 2h window, then transitions to OK. There is no state in which it is worse than today.
Manually starting the unit (Half A step 4) makes the first datapoint immediate.

**"A failed `put-metric-data` now fails the backup unit."** It fails the unit *after* the backup is
safely in S3. Verified by execution (see the matrix below): case E leaves `s3=1, heartbeat=0, rc=1`.
The dump is not lost. The unit is `Type=oneshot` with **no `Restart=`** (`:1145-1153`), so there is no
retry storm; the next hourly tick runs normally. And a single missed heartbeat does not fire the
alarm (SampleCount over a 2h window with two runs). The trade is: a transient CloudWatch blip marks
one unit run failed. I accept that, because the alternative — swallowing the publish failure with
`|| true` — recreates the silent-signal-loss bug that E2 exists to fix.

**"The `postgres` user cannot call CloudWatch."** It can. The same script already calls
`aws s3 cp` as `postgres` and the dossier verified the objects landing (`:1879`). IMDS credentials
are not user-scoped. The one real hazard is region resolution, closed by the explicit `--region`.

**"The helper is a new failure point in the backup path."** It is invoked *after* the upload, so it
cannot prevent a backup. On a box where it is missing or broken, the backup still completes and the
heartbeat is skipped with a loud message and a non-zero exit — which the alarm then reports after 2h.
Fail-closed, degrading in the safe direction.

**"E3 lands first and E2's helper write clobbers it."** Both writes are byte-identical `cat >` +
`chmod` of the same content, so the second is a no-op. The Half-A payload additionally guards with
`grep -q`/idempotence. If the two agents' texts ever diverged, that would be an INV-3 violation and
the I8 test (`cmp` the two rendered helpers) catches it.

**"Concurrency / ordering."** Nothing concurrent. Two systemd `oneshot` timers, hourly and every 15
minutes, each a short-lived process. `RandomizedDelaySec` prevents thundering-herd alignment. No
shared mutable state beyond the helper file, which is read-only at run time.

**"Startup / shutdown / restart."** No unit file changes, so no `daemon-reload`, no restart, no
interaction with `velocityai-app.service` or the deploy path. A reboot re-arms both timers from their
existing `[Install] WantedBy=timers.target`.

**"Partial application."** Enumerated, and every intermediate state is safe:

| Landed | Result |
|---|---|
| Helper only | Nothing publishes. Identical to today. |
| Helper + publisher, no Terraform | Heartbeat lands in `VelocityAI/Dev`; the alarm still watches `VelocityAI/Backups` and stays in ALARM. Same as today, plus a correct metric waiting. **No cross-env harm** — this is why publishing to the per-env namespace is safe to land first. |
| Terraform only, no publisher | Dev's alarm moves to `VelocityAI/Dev::PgDumpHeartbeat`, still absent, still ALARM. Same as today. |
| All three | Alarm goes OK within one timer tick. |
| **The dossier's literal fix** (publisher into `VelocityAI/Backups`, no Terraform) | Dev's alarm goes OK **and so do stage's and prod's**, off dev's data. **The only unsafe intermediate state, and it is the one the dossier prescribes.** |

**"Application-layer ripple."** None. Zero files under `backend/` or `frontend/`. No unattached
client, slow client, crashed run, restart, resume, fan-out run, revision run or two-browser scenario
is reachable from this change — those all live in cluster A. Memory and connection-pool effects: none;
the publisher is two short-lived `aws` CLI invocations per hour on the host, outside the container.

**Verifying the dossier's own safety argument rather than restating it.** The dossier asserts
(`:1885-1887`) that *"this alarm currently fires on dev, stage and prod, so a fix in
`bootstrap-ec2.sh` benefits all three whenever they are next rebuilt — but per the dev-only
constraint, only apply it to the dev box."* The first clause is true. The second clause is what
breaks: with a shared, dimensionless metric, applying the publisher to **one** box does not benefit
one alarm — it satisfies **all three**. The dossier treats the alarms as three independent things
because they have three names. They are not; they are one metric with three watchers.

##### I9. Rollback

**Repo half.** `git revert` the two commits (Terraform, then bootstrap) and push to `dev`. The next
`$TF/app apply` returns dev's alarm to `namespace = "VelocityAI/Backups"` and re-uploads the previous
`bootstrap-ec2.sh` to the per-env S3 config prefix. Fully reversible; no state migration, no
destroy/recreate — `aws_cloudwatch_metric_alarm` namespace is an in-place update.

**Host half.** Restore from the pre-change backup the payload took:

```bash
aws ssm send-command --instance-ids i-092d5961f5aca87a6 --document-name AWS-RunShellScript \
  --parameters commands='[
"set -euo pipefail",
"BK=$(ls -1dt /root/e2-backup-* | head -1); echo restoring from $BK",
"cp -a $BK/velocityai-pg-dump /usr/local/bin/velocityai-pg-dump",
"chmod 0755 /usr/local/bin/velocityai-pg-dump",
"bash -n /usr/local/bin/velocityai-pg-dump",
"rm -f /usr/local/bin/velocityai-cw-namespace   # only if E3 has NOT landed",
"systemctl start velocityai-pg-dump.service && systemctl is-failed velocityai-pg-dump.service || echo restored"
]'
```

**What is NOT reversible, and what the backup must therefore capture.** There are **no EBS snapshots
of any root volume in any environment**, and all carry `delete_on_termination = true` (dossier
`:2033-2034`). The `/root/e2-backup-<ts>/` file copy is the **only** restore point for
`/usr/local/bin/velocityai-pg-dump`. It must be taken **before** the first write, and it must include
`velocityai-cw-namespace` if that file already exists (i.e. if E3 landed first) so a rollback of E2
cannot delete E3's helper out from under it. The payload in I5 does both.

**Irreversible side effects of the change itself: none.** CloudWatch datapoints already published
cannot be deleted, but they expire on the standard retention schedule and are inert. No data is
mutated, no S3 object is removed, no IAM is changed, no systemd unit is altered.

**Rollback of the last resort — deleting the alarm.** If the fix cannot be made to work at all, the
alarm can be removed rather than left as noise (`terraform state rm` is *not* the way; delete the
resource block and apply). I argue against it in I12, but it is a clean exit.

##### I12. Shortcuts and alternatives explicitly rejected

**1. The dossier's literal prescription: publish to `VelocityAI/Backups`, dev only, no Terraform
change.** Rejected. The alarm has no dimensions and the namespace is shared, so one zero-dimension
datapoint satisfies all three environments' alarms. Prod's backup timer could be dead and prod's
alarm would read OK. **The specific failure: a false negative on the production RPO-1h control.**
This is the correction that motivates the whole plan.

**2. Publish with an `Environment` dimension into `VelocityAI/Backups`** (and add
`dimensions = { Environment = var.environment }` to the alarm). Rejected, though it is *defensible*
and would work. Three reasons: it still requires the same monitoring-module edit, so it buys nothing
in blast radius; it introduces a **new** dimension key that must match exactly between publisher and
alarm forever — the precise trap that already broke the CWAgent host alarms in this very file; and it
leaves `VelocityAI/Backups` as a second namespace scheme alongside `var.cw_metric_namespace`, which
is the INV-3 duplication the project forbids. **The specific failure it risks:** someone later adds a
second dimension on one side only, and the alarm silently returns to permanent ALARM with no error
anywhere.

**3. Delete the alarm** (the dossier's stated alternative). Rejected — and it deserves a real
argument, not a slogan.

The case *for* deleting is not weak. An alarm nobody is subscribed to (B6: zero confirmed subscribers
on every current-stack topic) that has been in ALARM since the day it was created is not monitoring;
it is one of the 41 entries generating the alarm fatigue that is itself a documented finding. Deleting
it would reduce noise immediately, at zero risk, with one line of Terraform.

The case *against* is decisive: `pg_dump` to S3 is one of only two backup mechanisms
(`docs/SIMPLE_AWS_DEPLOYMENT.md:28`: EBS snapshot nightly plus `pg_dump` hourly, "RPO 1 hour, RTO 30
min"), and it is the one that carries the hourly RPO. It runs on a `Type=oneshot` unit with **no
`Restart=`** (`:1145-1153`), driven by a timer, on a box whose root volume has **zero snapshots**. If
that timer dies, the RPO silently degrades from 1 hour to 24 hours and **nothing else in the system
would notice** — there is no other watcher on the backup path. The dossier's line, *"a backup you are
not alerted about is not a backup"*, is correct. The alarm is also cheap and already written; the only
thing missing is four lines of shell.

**Deleting is therefore rejected — but with a precondition:** it is only true monitoring once someone
is subscribed (B6). Landing E2 without B6 converts a noisy false positive into a quiet true negative
that still pages nobody. **E2 and B6 are complements; ship both.**

**What "good" actually looks like, and the gap this fix does NOT close.** The brief asks whether the
heartbeat proves the dump is RESTORABLE or only that a file was written. **Only that a file was
written**, and I will not claim otherwise. Precisely:

- It proves `pg_dump` exited 0 through a `pipefail` pipeline into `gzip -9` (so a mid-pipe `pg_dump`
  failure *is* caught — verified, T1 case B), and that `aws s3 cp` to the KMS-encrypted prefix
  returned 0 (T1 case C).
- It does **not** prove the object is readable, that it decompresses, that it parses as SQL, that it
  restores into an empty Postgres, or that the restored database is complete. **Nothing in this
  system has ever read a dump back.** The DR path is documented (`SIMPLE_AWS_DEPLOYMENT.md:1649`) and
  deliberately uses a *different* identity — the instance role is write-only under `postgres/` — so
  the box that writes the backups structurally cannot verify them.
- It does not detect a *degenerate* dump: `pg_dump` against an empty or wrong database exits 0 and
  produces a small valid file. `PgDumpBytes` (Artefact 2) is the cheap partial mitigation and is why
  I included it, but with no alarm wired it is currently only forensic.

**The honest statement to carry forward:** after this fix the system alerts on *"the backup pipeline
stopped running"*. It still does **not** alert on *"the backups are not restorable"*. Closing that
needs a periodic restore drill from the DR identity into a scratch database, publishing its own
heartbeat — a separate, larger piece of work that must not be smuggled into this change. Name it in
the backlog rather than let the green alarm imply a guarantee it does not make.

**4. Alarm on S3 `PutObject` activity instead of a custom metric** (the `docs/INFRA_AUDIT.md:93`
suggestion: *"alarm on 'no PutObject under `s3://.../postgres/` for >2h'"*). Rejected. S3 request
metrics are a paid per-bucket feature and are filterable by prefix only with a configured metrics
filter; the CloudTrail-data-event route needs a trail with S3 data events, which the account
deliberately does not have (Appendix 2, and `monitoring/main.tf:928-935` notes data events are
management-events-only here). It would also be a **weaker** signal: an object landing proves less
than a script reaching the end of its own success path, because a partial or degenerate upload still
produces an object.

**5. Bake the namespace into the script at install time from `${ENV_TITLE}`** via the unquoted-prelude
technique E3's dossier entry proposes. Rejected for **E2** specifically. It is fail-**open**: `:79`
defaults `ENVIRONMENT` to `prod`, so a box whose `bootstrap.env` lacked `VELOCITYAI_ENVIRONMENT` bakes
`VelocityAI/Prod` permanently, with no runtime signal and no way to detect it short of reading the
file on the box. **The specific failure: dev silently publishing into prod's namespace — the exact E3
defect, recreated by the fix for it.** The orchestrator's fail-closed constraint rules it out.
(The technique itself is sound and remains the right answer for values that genuinely must be fixed
at install time.)

**6. Carry the namespace in a new `EnvironmentFile` (`/etc/velocityai/cw-namespace.env`).**
Rejected — a near-miss. It reuses `ENV_TITLE` most literally, but it requires editing **two systemd
unit files** plus `daemon-reload` on the host, and it inherits the same `:-prod` fail-open unless a
separate guard is added at the derivation site. With `EnvironmentFile=` unprefixed, a missing file
makes the unit fail — which would break the **backup**, not just the heartbeat. With `EnvironmentFile=-`
it degrades silently, which is the bug. The runtime helper achieves the same single-derivation
property with **zero systemd churn** and an unambiguous failure mode.

**7. Append the namespace to `/etc/velocityai/app.env`.** Rejected on evidence:
`velocityai-load-secrets` **regenerates that file wholesale** on every
`velocityai-app.service` start — it writes a `mktemp` file and `mv`s it over `$OUT`
(`bootstrap-ec2.sh:617-701`). Anything appended is destroyed on the next deploy. [V]

**8. Swallow publish failures with `|| true`.** Rejected. It makes the heartbeat unreliable in exactly
the way that produces the bug being fixed: a run that "succeeded" while the signal was lost. The
alarm's 2h/SampleCount window already absorbs a single transient failure, so there is nothing to gain.

**9. Bound the fix to the host and skip the repo commit.** Rejected. Root volumes are
`delete_on_termination = true` with zero snapshots; the host change dies with the instance. The repo
half is what makes it survive a rebuild, and it costs one commit that the existing
`aws_s3_object.bootstrap_script` + per-env `$TF/app apply` already delivers with no new pipeline step.

**10. Use `${VELOCITYAI_ENVIRONMENT^}` in the helper** rather than the explicit three-way map.
Rejected on measurement: `${x^}` is bash-4+ only (proven to fail on bash 3.2), and more importantly
it is a *different function* from Terraform's `title()`. They agree on `dev|stage|prod` and diverge on
anything hyphenated. The explicit map is provably equal to the Terraform side for exactly the
permitted set and refuses everything else, so the two sides cannot silently drift apart if the
`environment` validation is ever widened.

**11. Target the SSM command by tag.** Rejected — dossier Appendix 2 `:2025-2027`: `Project`, `Owner`,
`CostCenter`, `Repo`, `ManagedBy` and `Component` are **byte-identical** across dev, stage and prod.
A tag-targeted command would patch production. `--instance-ids` plus the `Name` assertion is the only
safe form.
