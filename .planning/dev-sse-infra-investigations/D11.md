The defect is real and every anchor is exact. Three material corrections to the *fix*:
(1) the four `return` sites are **not** where a stream usually ends in production — the
dominant teardown is a `CancelledError` thrown into the generator while it is parked in
`await live_queue.get()`, which none of the four sites observes, so a `try/except/finally`
is required rather than four call-site emits; (2) **"emit as JSON" is wrong for this
deployment** — the backend's stdout is wrapped by Docker's `json-file` driver before the
CloudWatch agent tails it, so app-emitted JSON lands as an escaped *string* inside `$.log`
and is no more structurally queryable than plain text, while every existing metric filter
on `/velocityai/<env>/app` is already a term filter; (3) `evicted` does not belong in the
close-reason vocabulary — it is not observable from inside the generator and is better
served by A2's own `_evict_subscriber` warning, whose shape this issue specifies.

##### I3. Root cause — confirmed, corrected, or replaced

**The dossier's statement of the defect is exactly right.** `run_stream.py` is 300 lines
with zero logging calls, no logger and no `logging` import [V], and `uvicorn.access` is
pinned to `WARNING` at `main.py:54` [V], so not even a request line survives. The sole run
transport for the entire product produces no server-side record that a stream existed.

**Independently re-derived causal chain (trigger -> symptom):**

1. Phase 29-02 wrote `run_stream.py` to a *parity* contract: its frames had to be
   byte-identical to the retired `/ws/chat` drainer's, proven by `test_wire_parity.py`
   (IMPL `:2778`). Under a parity mandate, anything the old drainer did not emit is a
   liability, and the old drainer logged nothing on the run path either.
2. LOCK-B (IMPL `:2789`) forbade touching `websocket.py`, which pushed 29-02 toward the
   smallest possible additive module. A logger is not part of a transport shim.
3. Phase 44-07 deleted `/ws/chat` and made this shim the *sole* run transport
   (IMPL `:3679`, `:3696`) — but 44-07 was a deletion phase. Nothing in it revisited the
   surviving module's observability, and no plan since has owned it.
4. Meanwhile the module's blast radius grew: BUG-004 (a DB-connection leak per stream),
   BUG-013 (browser connection-pool exhaustion), BUG-015 (a terminal-run reconnect loop),
   BUG-016 (approve closing the live stream) — four production defects on this path in one
   week (IMPL `:3899`, `:3953`, `:3994`). Every one was diagnosed from the *browser* or
   from a synthetic harness.
5. Symptom today: the three A-cluster defects are invisible from inside the process. A1's
   429s never reach uvicorn at all (nginx rejects them at the edge). A2's event stealing
   produces two healthy-looking half-streams with no server-side trace. A4's stale queue
   entry makes every subsequent attach park forever on a sentinel that will never arrive —
   a *silent* leaked generator and open socket, forever.

**The dossier's "why it occurred" is right for the right reason,** and its two-line design
(one open, one close, closed reason vocabulary) is the correct shape. Three things are
wrong with the fix as written, all found by reading the code and the runtime library:

**Correction 1 — the four `return` sites are the *minority* exit path.** I read
`sse_starlette==3.0.2` (`sse.py`, installed at
`~/Library/Python/3.11/lib/python/site-packages/sse_starlette`) [V]:

- `EventSourceResponse.__call__` (`:248-270`) opens an `anyio` task group and starts four
  children through `cancel_on_finish`, which **cancels the whole group as soon as any one
  returns** (`:257-259`).
- `_listen_for_disconnect` (`:194-203`) awaits `receive()` and returns on `http.disconnect`.
- Therefore, on a real client disconnect, `_stream_response`'s `async for data in
  self.body_iterator` (`:177`) is **cancelled**, throwing `CancelledError` into our
  generator at whatever `await` it is parked on — in the common case
  `await live_queue.get()` at `:197`. The `return` at `:196` never runs.
- `request.is_disconnected()` at `:195` is additionally unreliable: it and
  `_listen_for_disconnect` are two consumers of the same ASGI `receive` callable, so
  whichever calls first consumes the single `http.disconnect` message. `:196` fires only
  in the narrow window where the poll wins the race *and* the generator happened to loop
  around after a yield.
- A send timeout takes a fifth path entirely: `sse.py:186-187` calls
  `await self.body_iterator.aclose()`, which raises **`GeneratorExit`** at the suspended
  `yield`.

Proven empirically, not asserted — a throwaway harness driving a real async generator
through all four teardowns
(`scratchpad/gen_exit.py`):

```
('return', 'returned')
('aclose', 'generator_exit')
('cancel', 'cancelled')
('raise', 'error:RuntimeError')
```

and exactly-once finalisation across return + `aclose`-after-exhaustion + GC-finalizer
(`scratchpad/once.py`):

```
[('return', 'returned'), ('gc', 'generator_exit')]
return-emits: 1 gc-emits: 1
```

[V] both. Consequence: **the close emit must be a `finally`, and the reason must be set by
`except asyncio.CancelledError` / `except GeneratorExit` / `except Exception` clauses as
well as by the four returns.** Four call-site emits would silently miss the majority of
real closes and would produce unpaired open lines — the exact failure the metric filter
would then mis-report as "leaked streams".

Both `asyncio.CancelledError` and `GeneratorExit` derive from `BaseException`, **not**
`Exception`, on this interpreter (Python 3.11.15) [V] — so a bare `except Exception` does
not catch them and the clause ordering below is load-bearing.

**Correction 2 — "Emit as JSON" buys nothing here.** Fully argued in I4 with the measured
evidence. Short form: the backend's stdout passes through Docker's `json-file` driver
(`docker-compose.yml:130`, `:182` [V]) into `/var/lib/docker/containers/*/*-json.log`,
which the CloudWatch agent tails **raw** (`bootstrap-ec2.sh:996` [V]). The CloudWatch
record is therefore Docker's envelope; app-emitted JSON is an escaped string inside
`$.log` and `{ $.evt = "sse.open" }` cannot match it.

**Correction 3 — `evicted` is not observable from inside the generator.** After A2, a
subscriber whose queue overflows is evicted by A2's `_evict_subscriber`, which "drains with
`get_nowait()` ... `put_nowait(None)`" (dossier A2 fix table). From `_iter_sse_frames` that
`None` is indistinguishable from the normal end-of-run sentinel. Making it distinguishable
requires coupling D11's vocabulary to A2's internals. It should not be in the vocabulary —
see I5 and I10.

**(b) The JSON-vs-text decision, resolved with evidence.**

The dossier says "Emit as JSON. The current format is plain pipe-delimited text
(`main.py:39`), which no CloudWatch metric filter can parse structurally." The premise is
right; the conclusion does not follow **for this log group**.

Measured facts:

1. `docker-compose.yml:130` and `:182` — both services use `driver: json-file` [V].
2. `infra/scripts/bootstrap-ec2.sh:996` — the agent's `collect_list` entry is
   `{"file_path": "/var/lib/docker/containers/*/*-json.log", "log_group_name":
   "/velocityai/${ENVIRONMENT}/app", "log_stream_name": "{instance_id}/docker", ...}` [V].
   There is no processor, no multiline rule, no envelope-unwrap.
3. So a CloudWatch record in `/velocityai/dev/app` is
   `{"log":"<one app line>\n","stream":"stdout","time":"..."}`.
   `$.log` is a **string**; `$.evt` does not exist. A `{ $.evt = "sse.open" }` filter cannot
   match. **[I]** on CloudWatch's evaluation semantics (I could not run
   `aws logs test-metric-filter` — see the honesty note below); **[V]** on the record shape.
4. Corroborating, from the repo itself: **every existing metric filter on the `/app` group
   is a term filter, and the only JSON-pattern filters in the whole module are on the
   CloudTrail group** (which genuinely is top-level JSON) [V]:

   ```
   modules/monitoring/main.tf:503   pattern = "OperationalError ?could not connect"           # /app
   modules/monitoring/main.tf:643   pattern = "?\"WebSocket disconnected\" ?\"WebSocketDisconnect\" ..."   # /app
   modules/monitoring/main.tf:862   pattern = "?\"AGENT [\" ?\"FAILED\" ?\"CONFIG ERROR\" ?\"agent_error\""  # /app
   modules/monitoring/main.tf:1520  pattern = "{ ($.eventSource = \"ssm.amazonaws.com\") && ... }"          # cloudtrail-audit
   ```

   **nginx-access**, whose file the agent tails directly at `bootstrap-ec2.sh:988` with no
   envelope — which is exactly why JSON works there and not here.

**Decision: keep the app's pipe-delimited text format; put `key=value` tokens in the
message, with a stable leading discriminator (`evt=sse.open` / `evt=sse.close
reason=<r>`).** Cost: field *values* (duration, frame counts) cannot become metric-filter
metric *values* — they are Logs Insights queries instead (query given in I5). Counts, which
is what alarms need, work perfectly via term filters, the same shape the three existing
`/app` filters use. Consistency with the other 78 loggers is preserved (INV-3's spirit: one
convention, not two).

The brief offered two options; I am taking neither, and both are costed in I12:
"JSON for this module only" would produce a **mixed** stream that a term filter can still
scan but a JSON filter still cannot parse (the envelope defeats it either way) — i.e. all
of the inconsistency and none of the benefit; "app-wide structured logging" is a genuinely
bigger change that must *also* replace the Docker `json-file` driver with `awslogs` (or add
an agent-side unwrap) before a single `$.field` filter works — a B-cluster change touching
`docker-compose.yml`, IAM and `bootstrap-ec2.sh` §14, and it would break the three existing
`/app` term filters at `main.tf:503/643/862`.

After (complete replacement; the docstring keeps its existing text plus the D11 paragraph):

```python
async def _iter_sse_frames(
    *,
    run_id: str,
    store: Any,
    after_seq: int,
    live_queue: Any = None,
    request: Optional[Request] = None,
    user_id: str = "-",
) -> AsyncIterator[dict]:
    """Yield the SSE frame dicts for one attached client.

    Order: durable replay (``seq > after_seq``) -> ``stream_attached`` handshake ->
    D-14g gate re-arm (if paused) -> live queue drain (until the ``None`` sentinel or
    client disconnect). ``live_queue is None`` means the run has no live task, so the
    replayed durable tail + the handshake are the complete response.

    D11: emits EXACTLY two log lines per stream — ``evt=sse.open`` as its first
    statement and ``evt=sse.close reason=<r>`` from a ``finally``. Both live INSIDE
    the generator, never in the endpoint body: if the request aborts before the
    response body starts, the generator body never runs, so neither line is emitted
    and the pair stays balanced (the same argument A2 makes for its ``subscribe``).
    The reason is set at the four ``return`` sites AND by the ``except`` clauses —
    a real client disconnect cancels the task group in ``sse-starlette``
    (``sse.py:257-270``), which throws ``CancelledError`` into this frame while it is
    parked in ``live_queue.get()``; none of the four returns runs on that path.
    """
    _t0 = time.monotonic()
    _replayed = 0
    _live_frames = 0
    # Default is the honest one: if an exception escapes before any named exit is
    # reached, the close line must say so rather than claim a clean end.
    _reason = _CLOSE_ERROR

    logger.info(
        "evt=sse.open run=%s user=%s after_seq=%d attached=%d",
        run_id,
        user_id,
        after_seq,
        1 if live_queue is not None else 0,
    )
    try:
        # 1. Durable replay — the run_events tail past the client cursor, ascending seq.
        rows = await store.read_events(run_id, after_seq=after_seq)
        replayed_through_seq = after_seq
        for r in rows:
            yield _sse_frame(r.seq, r.type, r.payload_json)
            replayed_through_seq = r.seq
            _replayed += 1

        # 2. stream_attached handshake — the new-transport replacement for the legacy
        #    pipeline_reconnected ack. `live` reflects whether a live queue is attached;
        #    `replayed_through_seq` mirrors the last replayed seq (legacy semantics). Its
        #    id: line carries the same cursor so a resume from it re-reads nothing new.
        is_live = live_queue is not None
        yield _sse_frame(
            replayed_through_seq,
            "stream_attached",
            {
                "pipeline_run_id": run_id,
                "live": is_live,
                "replayed_through_seq": replayed_through_seq,
            },
        )

        # 3. D-14g gate re-arm — unchanged (CR-01 guard included).
        full_log = await store.read_events(run_id, after_seq=0)
        dangling = _dangling_review_gate(full_log)
        if dangling is not None and dangling.seq <= after_seq:
            yield _sse_frame(dangling.seq, "review_gate_ready", dangling.payload_json)

        # 4. Live drain.
        if live_queue is None:
            _reason = _CLOSE_NO_LIVE_QUEUE
            return
        while True:
            if request is not None and await request.is_disconnected():
                _reason = _CLOSE_CLIENT_DISCONNECT
                return
            event = await live_queue.get()
            if event is None:  # sentinel: pipeline finished
                _reason = _CLOSE_SENTINEL
                return
            data = event.get("data", {}) if isinstance(event, dict) else {}
            seq = data.get("seq", replayed_through_seq) if isinstance(data, dict) else replayed_through_seq
            yield _sse_frame(seq, event.get("type", "message"), data)
            _live_frames += 1
            replayed_through_seq = seq
            if event.get("type") in _STREAM_TERMINAL_TYPES:
                _reason = _CLOSE_TERMINAL_EVENT
                return
    # CancelledError and GeneratorExit both derive from BaseException, NOT Exception,
    # so they must be named explicitly and BEFORE the Exception clause. Each re-raises:
    # swallowing GeneratorExit raises RuntimeError("async generator ignored
    # GeneratorExit"), and swallowing CancelledError breaks cooperative cancellation.
    except asyncio.CancelledError:
        _reason = _CLOSE_CANCELLED
        raise
    except GeneratorExit:
        _reason = _CLOSE_GENERATOR_EXIT
        raise
    except Exception:
        _reason = _CLOSE_ERROR
        raise
    finally:
        # No await and no yield in here — a yield after GeneratorExit is a RuntimeError,
        # and an await during cancellation re-raises immediately. logger.log is sync.
        logger.log(
            logging.WARNING if _reason == _CLOSE_ERROR else logging.INFO,
            "evt=sse.close reason=%s run=%s user=%s dur_s=%.1f replayed=%d live_frames=%d",
            _reason,
            run_id,
            user_id,
            time.monotonic() - _t0,
            _replayed,
            _live_frames,
        )
```

Field-order rationale, not cosmetic: `reason` is placed **immediately after** `evt` so that
a CloudWatch *phrase* filter (`"evt=sse.close reason=error"`) works as well as a bare term
filter. CloudWatch phrase filters match a contiguous substring; with `reason` after
`run`/`user` the compound phrase would never match and every filter would have to be a
two-term AND. `attached` (open) and `live_frames` (close) are deliberately different names
so the two lines never collide on a key with different meaning.

##### I6. Ripple-effect analysis — why nothing else breaks

Assume the fix is wrong and hunt for the failure.

**"The `finally` swallows `GeneratorExit` and Python raises `RuntimeError: async generator
ignored GeneratorExit`."** It cannot: the `except GeneratorExit` clause re-raises, and the
`finally` contains only a synchronous `logger.log`. The rule that breaks this is *yielding*
inside the `finally`, which the code does not do. Verified behaviourally in
`scratchpad/gen_exit.py` — the `aclose` case reached the `finally` and propagated cleanly.

**"The `finally` runs twice and every metric doubles."** Proven not to, across the three
ways a generator can be finalised (`scratchpad/once.py`): normal return followed by an
explicit `aclose()` on the exhausted generator emitted **once**, and a partially-consumed
generator dropped to the loop's async-gen finalizer emitted **once**. A Python generator
frame finalises at most once by construction.

**"`logger.log` inside a `finally` during cancellation raises."** `logging` is fully
synchronous and never awaits. The one real hazard would be an `await` in the `finally`
(which re-raises `CancelledError` immediately in a cancelled context) — there is none.

**"The `except Exception` clause swallows a cancellation."** It cannot: on 3.11
`issubclass(asyncio.CancelledError, Exception)` is `False` and
`issubclass(GeneratorExit, Exception)` is `False` [V]. Both are caught by their own
clauses, which are ordered first, and both re-raise.

**"An exception inside `logger.log` kills the stream."** The only way `%`-formatting can
raise is an argument count mismatch, which is a compile-time-constant property of the two
call sites and is covered by the I8 tests. Even then, `logging` swallows formatting errors
by default (`logging.raiseExceptions` prints to stderr rather than propagating).

**Concurrency and ordering.** Nothing shared is written. Two streams on the same run each
have their own generator frame and their own `_t0`/`_replayed`/`_live_frames` locals. The
logger is process-global but `logging` is internally locked and the handler is a single
`StreamHandler(sys.stdout)` (`main.py:46`), so interleaving is line-atomic. Under A2's
fan-out, N subscribers produce N independent open/close pairs on one run — which is the
point.

**Startup / shutdown.** On graceful uvicorn shutdown, `sse-starlette`'s
`_listen_for_exit_signal` (`sse.py:206-219`) returns, `cancel_on_finish` cancels the group,
and every open stream logs `reason=cancelled`. That is a *feature* — D8 ("the lifespan
shutdown does nothing") becomes measurable: the count of `reason=cancelled` in the second
around a restart is the number of streams abandoned. It also means `SseCancelled` will
spike once per deploy; the alarm design above deliberately puts no alarm on it.

**Unattached client.** No stream, no lines.

**Slow client.** `sse-starlette` `move_on_after(self.send_timeout)` -> `aclose()` ->
`reason=closed`. A distinct reason from a plain disconnect, which is exactly the
discrimination the current system lacks.

**Crashed run.** The driver's `finally` calls `_cleanup_pipeline`; pre-A3 that sends no
sentinel on eight of ten call sites, so the attached client parks forever and logs *only*
the open line. **That asymmetry is the A3 detector**: an open with no close for minutes is
the leaked generator. Post-A3 the same stream logs `reason=sentinel` promptly, and the gap
closes. Measuring A3's fix is a direct benefit.

**Restart.** All in-flight streams log `reason=cancelled`; after boot, D9's uncapped
`restore_non_terminal_runs` produces a burst of new runs and the reattaching clients
produce a matching burst of `evt=sse.open`. That burst is the first-ever quantitative
measurement of D9's thundering herd.

**Resume.** `resume_run` and `_drive_user_resume` do not touch this module. A resumed run's
reattaching client is an ordinary open/close pair with `after_seq > 0`.

**Fan-out / wave run.** Worker events are yielded through `_execute_impl` into the same
per-run queue (dossier A2, "Not changed, deliberately"), so a fan-out run is one stream with
a large `live_frames`. No change.

**Revision run.** A `*_revision` child is its own `run_id` and its own stream. Two lines.

**Two browsers.** Today: two open lines, two half-populated `live_frames` counts summing to
the run total, and the Insights query above names it in one shot. That is the A2 smoking
gun the dossier had to reproduce three separate ways.

**Memory and connection pool.** Zero new allocations that outlive the frame — three ints,
one float, one string. **No session, no cursor, no connection.** This is the one property
that must not regress, because `tests/unit/test_run_stream_pool_leak.py` (BUG-004) counts
pooled connections around the endpoint. `logging` opens none.

**Partial application.** If step 3 lands without step 4, every line reads `user=-`: still
useful, never wrong. If steps 1-4 land without step 5, the lines sit in the container log
and `docker compose logs` — still the single biggest diagnostic improvement available, and
step 5 is inert until B1/B2 make CloudWatch work at all.

**Verifying the dossier's own safety claims rather than restating them.** D11's text makes
one safety claim — that the close emit can sit "at the four exits". I checked it against
`sse-starlette` and it is **false for the common path** (I3, Correction 1). Its second
claim, that "after A2 ... the wrapper generator's `finally` ... is a single site", is true
about A2's structure but wrong as a placement: A2's wrapper cannot see `_reason`,
`_replayed` or `_live_frames`, all of which are locals of `_iter_sse_frames`. Both lines
must stay in `_iter_sse_frames` in both the pre-A2 and post-A2 world — which is also what
keeps A2's own promise that "`_iter_sse_frames` itself unchanged preserves every existing
test" *nearly* true (A2 leaves it unchanged; D11 changed it first, and A2 rebases onto that).

```python
_LOGGER_NAME = "app.api.run_stream"

# The ONLY two message shapes this logger may ever emit. Anchored on both ends so
# an extra field, a reordered field or any run title / brief / payload / filename

_OPEN_RE = re.compile(

)
_CLOSE_RE = re.compile(
    r"^evt=sse\.close reason=(?P<reason>no_live_queue|client_disconnect|sentinel"
    r"|terminal_event|cancelled|closed|error)"
    r" run=\S+ user=\S+ dur_s=\d+\.\d+ replayed=\d+ live_frames=\d+$"
)

    return [r for r in caplog.records if r.name == _LOGGER_NAME]

    """Assert exactly one open + one close line, both well-formed. Returns the
    parsed close reason."""
    msgs = _messages(caplog)

    closes = [m for m in msgs if m.startswith("evt=sse.close")]

    m = _CLOSE_RE.match(closes[0])
    assert m, f"close line off-contract: {closes[0]!r}"
    return m.group("reason")
```

**Recommended order: D11 -> A5 -> A2.** Reasons, in order of weight:

1. **D11 first is the cheapest and it measures the others.** It is additive, offline-testable
   today, and needs nothing else to land. Landing it first means A3's sentinel fix, A4's
   self-heal and A2's fan-out are each *observable* the moment they deploy — you can see the
   `no_live_queue` share fall, the open/close gap close, and the per-run stream count
   double-with-equal-frame-counts. Landing it last means every one of those is shipped
   blind, which is the exact failure mode this dossier exists to end.
2. **A5 second.** Its edits sit inside the `try:` block D11 introduces — a mechanical
   rebase with one genuine hazard, called out below.
3. **A2 last**, as the dossier already sequences it (A2's live verification requires A1).

**The one hard interaction with A5.** A5 rebinds `rows = ()` after the replay loop to free
the retained ORM rows. Therefore:

> **Do not compute `_replayed` as `len(rows)` after the loop.** It must be incremented
> inside the loop, as written in I5. After A5 lands, `len(rows)` is `0` and the metric
> silently reads zero for every stream — a wrong number is worse than no number.

I wrote it as an in-loop increment specifically so the two commits compose in either order.
A5 should carry a one-line comment at its `rows = ()` rebinding noting that `_replayed` is
already counted.

**The one hard interaction with A2 — the `evicted` reason.** My brief asked for the close
vocabulary to cover `evicted` and for both a pre-A2 and post-A2 form. My finding is that
**it should not be a close reason at all**, and the two forms are therefore identical:

- From inside `_iter_sse_frames`, an eviction is a `None` on the subscriber queue —
  byte-identical to the normal end-of-run sentinel. It is not observable.
- Making it observable requires coupling: either A2's `_evict_subscriber` stamps a private
  attribute on the `asyncio.Queue` for D11's `finally` to read
  (`q._sse_close_cause = "evicted"`), or A2 pushes a distinguishable non-dict marker ahead
  of the sentinel, which the drain at `:200-202` would then have to special-case or crash
  on. Both put A2's internals inside D11's vocabulary for one bit of information.
- A2's design **already** specifies that `_evict_subscriber` "log a warning naming the run".
  So the count is available regardless. D11's contribution is to fix its *shape* so the same
  term-filter family can read it: `evt=sse.evicted run=%s pending=%d`, WARNING, on a new
  `logging.getLogger("app.api.run_engine")` (that module has no logger today [V]).

**Therefore: the `evt=sse.evicted` line belongs in A2's commit, and this is a hard ordering
constraint in the other direction — D11 must land first so A2 has a vocabulary to conform
to.** If A2 lands first, its warning will be free-form and E1's filter will need rewriting.
An evicted stream's own close line will read `reason=sentinel`; the eviction is joined by
`run=` in Insights. I record this as the one place where I did not implement the brief's
literal instruction, with the reason.

##### I11. Open questions requiring a human decision

**One, and it is small.**

**Should `user_id` be logged?** It is an opaque UUID (`User.id` is
`str(uuid.uuid4())`, `models/user.py:18` [V]), never the email, and it is already logged
this way at `agents.py:251`, `agents.py:332` and `file_extract.py:144`. Under GDPR a
stable pseudonymous identifier is still personal data, and these lines will sit in
CloudWatch for 30 days (`modules/monitoring/variables.tf:31`).

- **Option A (recommended): keep it.** It is the only way to answer "whose client is
  churning", which is the first question in any reconnect incident, and it is consistent
  with three existing precedents. The retention is already governed centrally, and the
  field is a UUID that resolves to a person only via the `users` table.
- **Option B: drop it,** logging only `run_id`. `run_id` -> `WorkflowRun.user_id` is one
  join away for anyone with DB access, so the privacy gain is small and the operational
  loss is real (you cannot see the pattern from CloudWatch alone).
- **Option C: log a truncated hash.** Adds a mapping step and buys nothing over A given
  that `run_id` already resolves to a user.

Everything else in this issue is a technical judgement I have made and evidenced, not a
product decision: the format (I4b), the vocabulary (I3), the placement (I5), and the
`evicted` disposition (I10).

##### I12. Shortcuts and alternatives explicitly rejected

**1. Emit the close line at the four `return` sites, as the dossier specifies.** Rejected
because it is *wrong*, not merely inelegant: the dominant production close is a
`CancelledError` thrown into the generator while it is parked at `live_queue.get()`
(sse-starlette cancels its task group on `http.disconnect`, `sse.py:257-270`) and a
`GeneratorExit` on the send-timeout path (`sse.py:186-187`). Neither runs any of the four
returns. Concrete failure: every ordinary "user closed the tab" would produce an open line
with **no** close line, so `SseStreamsOpened - SseStreamsClosed` — the leaked-generator
metric, the whole reason to want this — would read as a permanent, growing leak on a
perfectly healthy system, and A3's real leak would be invisible inside the noise.
[V] via `scratchpad/gen_exit.py`.

**2. Emit as JSON (the dossier's explicit instruction).** Rejected because the CloudWatch
record for this log group is Docker's `json-file` envelope, not the app's line
(`docker-compose.yml:130`/`:182` -> `bootstrap-ec2.sh:996`), so app JSON arrives as an
escaped string inside `$.log` and `{ $.evt = "sse.open" }` cannot match it. Concrete
failure: you would pay the inconsistency (one JSON module among 78 text loggers, unreadable
in `docker compose logs`) and gain **zero** structural queryability. The repo already
demonstrates the correct answer — all three existing `/app` filters
(`main.tf:503/643/862`) are term filters and the only `{ $.… }` filters
(`main.tf:1520/1546`) are on the CloudTrail group, which is genuinely top-level JSON. The
one command that would settle it definitively is in I8 and is blocked on expired
credentials; the claim is **[I]** on CloudWatch semantics and **[V]** on the record shape.

**3. Adopt app-wide structured logging (the brief's second offered option).** Rejected as
out of scope and, on its own, ineffective. To make `$.field` filters work it is not enough
to change the Python formatter: you must also stop the Docker envelope, i.e. switch both
services to the `awslogs` log driver (a `docker-compose.yml` change, new IAM on the instance
role, and a change to the agent's `collect_list`) **or** add an envelope-unwrap on the agent
side. That is a B-cluster change touching three files outside this issue, and it would break
the three existing `/app` term filters in the same stroke. It is a legitimate follow-up; it
is not D11.

**4. Put the emit in A2's wrapper generator's `finally` ("a single site").** Rejected: the
wrapper cannot see `_reason`, `_replayed` or `_live_frames`, which are locals of
`_iter_sse_frames`. Moving the emit there would reduce the close line to
`evt=sse.close run=… dur_s=…` with no reason and no counts — which deletes the entire
diagnostic value. The correct single site is `_iter_sse_frames`'s own `finally`, and it is
the same site before and after A2.

**5. Put the open line in the endpoint body, where `current_user` is already in scope.**
Rejected: the endpoint returns before the response body starts. If the client aborts in
that window, `aclose()` on a never-started async generator does not execute the body, so
the open line would be emitted with no matching close. Unpaired lines break the one metric
the pair exists to produce. (This is the same argument A2 gives for putting `subscribe()`
inside its wrapper rather than in the endpoint.)

**6. Add `evicted` to the close vocabulary by stamping the queue
(`q._sse_close_cause = "evicted"`).** Rejected: it puts a private attribute on a stdlib
`asyncio.Queue` and makes D11's vocabulary depend on A2's internal eviction mechanics for
one bit. A2 already specifies a warning at that site; specifying its *shape*
(`evt=sse.evicted run=%s pending=%d`) achieves the same measurement with no coupling, and
the join is `run=` in Insights.

**7. Log a periodic progress line (every N events, or every 30s).** Rejected: it would turn
a 97,694-event run into hundreds of lines, and the two-line design already yields the
throughput figure at close via `live_frames=`. Volume is not the objection — the cost is
under a cent a month either way (I4g) — the objection is signal-to-noise in a group that
also carries every engine log.

**8. Sample the logging, or gate it behind a settings flag.** Rejected: at 543 bytes per
stream and an upper-bound estimate of $0.11/month at 100x expected traffic, a sampling rate
is pure complexity, and a flag guarantees it will be off in the environment where it is
needed. Nothing about this is expensive enough to make configurable.

**9. Log `Last-Event-ID` as received.** Rejected: it is an untrusted client-supplied header.
Log the parsed integer `after_seq` (`:271-276` already bounds it to `>= 0` and degrades a
non-int to 0), never the raw string.

**10. Reuse the run's title or the workflow type as a log field, "for readability".**
Rejected: `WorkflowRun.title` is derived from the user's brief (FIX-087/FIX-130 exist
precisely because raw brief text leaked into it), and `pipeline_type` would introduce a
workflow-name literal into a module that has none. The whitelist test in I8 makes both a
test failure.

**11. Fold D10 (`SSE_STREAM_IDLE_TIMEOUT_SECONDS`) into this change "since it is the same
area".** Rejected: different file, different kind of change (deletion for comprehension vs
addition for measurement), and bundling makes reverting either drag the other. The dossier
correctly separates them, and the register logs the dead constant twice as its own item
(IMPL `:2815`, `:3718`).

**12. Fix the stale `run_stream.py:9-14` docstring (it still names the deleted
`websocket.py`) while in the file.** Rejected here, flagged in I1: A2 rewrites that exact
import line and should correct the prose in the same commit. Putting a prose-only edit in a
logging commit muddies the revert.

**Alternatives the dossier already rejected, verified rather than restated.** D11's text
offers no rejected alternatives of its own, so there was nothing to re-check. The adjacent
rejections I did verify are A5's four (the `seq <= :after_seq` filtered query is genuinely
wrong for the ready@5/approved@12/`after_seq=8` case; `derive_open_gate` genuinely keeps the
unbounded read) and A2's two (a lazy pump; a bounded retention ring) — none of which
interacts with D11.
