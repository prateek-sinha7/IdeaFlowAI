##### I3. Root cause — confirmed, corrected, or replaced

The dossier's *substance* is right and its *title* is wrong. Independently re-derived:

**The title is wrong.** "`fetch-config` exit status is never checked" is not what happens. The script
runs under `set -euo pipefail` (`:27`, verified), and `:1005-1007` is one simple command with line
continuations — not part of a pipeline, not on the LHS of `||`, not in an `if`. A non-zero exit from
`fetch-config` therefore **does** abort the script. The exit status is checked, by `set -e`. The
dossier's own "Why it occurred" paragraph concedes this ("the command genuinely *succeeded*"), so the
finding is internally inconsistent with its own headline.

**The substance is right.** The real defect is a **missing liveness assertion**: a zero exit proves
the agent was *asked* to start, not that it is running. The causal chain, re-derived:

1. `-s` makes `agent-ctl` perform its `start` action after installing and translating the config.
   `[I]` — on a systemd host that action ends in `systemctl restart amazon-cloudwatch-agent`.
2. `systemctl restart` on a non-`notify` unit returns as soon as `fork()` succeeds; it does not wait
   for readiness. So `agent-ctl` returns 0.
3. The agent then fails to construct its logger (`open sink "/var/log/amazon-cloudwatch-agent.log":
   permission denied` — B1's `[V]` journal read) and exits 1, ~milliseconds later.
4. systemd's `Restart=` re-launches it; the journal's `restart counter is at 977` is systemd's own
   `NRestarts`. `[V]` from the dossier's journal excerpt.
5. Bootstrap, having seen a 0, proceeds through §15-§20 and writes the completion sentinel.

**A load-bearing inference the dossier does not draw.** Step 2's premise ("the unit is not
`Type=notify` with a readiness gate") is not an assumption — it is *entailed by the observed
evidence*. If the unit gated on readiness, `systemctl restart` would have returned non-zero, `set -e`
would have aborted at `:1005`, and §16/§17 would never have installed the pg_dump timer. The dossier
itself proves those ran (hourly `pg_dump` objects in S3, latest 2026-07-29T18:01, `[V]`). Therefore
`agent-ctl` demonstrably returned 0 over a dying agent. The chain is closed without needing the unit
file.

**A second correction — the "not a live defect" claim about `systemctl enable`.** The dossier says an
explicit enable is "belt-and-braces, not a live defect. (Measured: it *is* currently `enabled`.)"
That measurement is real but the inference is wrong in one direction. The unit is enabled *because*
something downstream of a successful config-translate enabled it — either the deb postinst (the
script's comment at `:1003-1004`) or `agent-ctl`'s own `start` action; `[I]`, I cannot read the ctl
script from here. Either way the enable is **incidental to fetch-config getting far enough**. In the
narrower failure mode where fetch-config dies *before* its start action (malformed JSON, translate
failure), `set -e` aborts at `:1005` **and the unit is left disabled** — and on dev there is no
`velocityai-firstboot.service` to ever re-run this script (`[V]` from the dossier's C1 finding:
dev's live userData is the pre-`bdc9e537` 68-line version), so the agent would be gone after every
reboot with no self-heal. So: an explicit enable is defence-in-depth for a *narrower* failure than
B5's, but it is not merely cosmetic.

**A third correction — the dossier's fix snippet is broken as written.** Two independent defects,
both proven by execution:

- *No PATH.* `amazon-cloudwatch-agent-ctl` is not on the default `PATH`; the script itself always
  uses the absolute `/opt/aws/...` path. Run with a realistic `PATH`, the bare invocation produces
  `command not found`, takes the `||` failure branch and exits 1 — **on a perfectly healthy box, on
  every boot**. `[V]`:

  ```
  $ bash -c 'set -euo pipefail; PATH=/usr/bin:/bin
    amazon-cloudwatch-agent-ctl -m ec2 -a status | grep -q "\"status\": *\"running\"" || {
      echo "DOSSIER SNIPPET -> exit 1 (on a HEALTHY box too)"; exit 1; }'
  bash: line 1: amazon-cloudwatch-agent-ctl: command not found
  DOSSIER SNIPPET -> exit 1 (on a HEALTHY box too)
  ```

- *No settle window.* The check runs immediately after a `systemctl restart`. On a healthy agent the
  unit can legitimately still read `activating` and the ctl can still report `stopped`. `[V]` with a
  stub that emits exactly that: the naive check takes the failure branch. This is the same
  distinction the dossier's own B1 *verification* section flags ("must be `active`, not
  `activating`") and then forgets in B5's fix.

**A fourth correction — `exit 1` in place is catastrophic.** See I4. This is the single most important
finding and the dossier does not evaluate it.

The dossier's regex itself is sound: `'"status": *"running"'` cannot false-match
`"configstatus": "configured"`, because the pattern requires a `"` immediately before `status` and
`configstatus` has a `g` there. Proven `[V]` in both directions, including a hostile
`"configstatus": "running"` input.

**Step 1 — declare the degraded accumulator.**

Find (`dev`:31-36, the root check followed by §0's header):

```bash
if [[ "$EUID" -ne 0 ]]; then
    echo "[bootstrap] ERROR: must run as root (or via sudo)" >&2
    exit 1
fi

# ── 0. Wait for cloud-init to finish ───────────────────────────────────
```

Replace with:

```bash
if [[ "$EUID" -ne 0 ]]; then
    echo "[bootstrap] ERROR: must run as root (or via sudo)" >&2
    exit 1
fi

# ── Degraded-completion accumulator ────────────────────────────────────
# Some checks must be LOUD but must NOT abort the run. Aborting mid-script
# strands every later section (see the rationale block above §14a), which is
# strictly worse than finishing with a reported defect. Such a check appends a
# short tag here; §20 writes the completion sentinel, prints the tags and exits
# non-zero — the box ends up fully provisioned AND the invoking SSM command /
# CI step reports failure.
BOOTSTRAP_DEGRADED=()

# ── 0. Wait for cloud-init to finish ───────────────────────────────────
```

*Why an array and not a boolean:* so the §19 `/health` probe and the sibling checks in I4(c) can join
the same mechanism later without a second one (INV-12 in spirit). *Why `${#arr[@]}` guards
everywhere:* `"${arr[@]}"` on an empty array is an unbound-variable error under `set -u` on bash 3.2;
the count form is portable. Verified `[V]` on bash 3.2.57 (macOS) — if it passes there it passes on
Noble's 5.2.

**Step 2 — replace the whole of `dev`:1003-1007.**

Find exactly:

```bash

# enable` separately — the agent's deb postinst already does that.
/opt/aws/amazon-cloudwatch-agent/bin/amazon-cloudwatch-agent-ctl \
    -a fetch-config -m ec2 -s \
```

Replace with:

```bash
# ── 14a-fn. CloudWatch agent liveness assertion (used just below) ──────
# Kept beside §14 so C1's later extraction of §13/§14 into
# infra/scripts/reconcile-host-config.sh is a pure move, not a rewrite.
#
# ORACLE CHOICE. systemd is the AUTHORITATIVE readiness oracle here, not the
# agent's own `-a status` text: `systemctl is-active` is a stable contract,
# whereas the ctl's JSON is an undocumented third-party output whose wording
# could drift and turn a healthy boot into a permanent red. The ctl output is
# used only to CORROBORATE — it can fail the check when it explicitly says the
# agent is not running, but an unparseable/absent blob only warns.
#
# The five knobs are `:-` defaults purely so the function can be exercised by
# infra/scripts/tests/test-cwagent-assert.sh with stub binaries on PATH;
# production never sets them.
CW_AGENT_CTL="${CW_AGENT_CTL:-/opt/aws/amazon-cloudwatch-agent/bin/amazon-cloudwatch-agent-ctl}"
CW_AGENT_UNIT="${CW_AGENT_UNIT:-amazon-cloudwatch-agent}"
CW_AGENT_SETTLE_SECONDS="${CW_AGENT_SETTLE_SECONDS:-60}"
CW_AGENT_STABILITY_SECONDS="${CW_AGENT_STABILITY_SECONDS:-12}"
CW_AGENT_POLL_SECONDS="${CW_AGENT_POLL_SECONDS:-3}"

_cw_agent_status_blob() {
    [[ -x "$CW_AGENT_CTL" ]] || { printf ''; return 0; }
    "$CW_AGENT_CTL" -m ec2 -a status 2>/dev/null || true
}
_cw_unit_state()    { systemctl is-active "$CW_AGENT_UNIT" 2>/dev/null || true; }
_cw_restart_count() { systemctl show -p NRestarts --value "$CW_AGENT_UNIT" 2>/dev/null || true; }
_cw_diag()          { journalctl -u "$CW_AGENT_UNIT" -n 40 --no-pager >&2 || true; }

# 0 iff the agent is RUNNING and STAYS running. Prints its own diagnosis and
# never exits — the caller decides whether the failure is fatal.
assert_cloudwatch_agent_running() {
    local blob state deadline stable_deadline r0 r1

    if [[ ! -x "$CW_AGENT_CTL" ]]; then
        echo "[bootstrap] ERROR: $CW_AGENT_CTL missing or not executable — the agent package did not install correctly." >&2
        return 1
    fi

    # 1. Settle. `systemctl restart` (which `-s` ends in) returns as soon as
    #    the process forks, so an immediate check reads "activating" on a
    #    perfectly HEALTHY agent. Poll instead of guessing a sleep.
    deadline=$(( SECONDS + CW_AGENT_SETTLE_SECONDS ))
    while :; do
        state="$(_cw_unit_state)"
        [[ "$state" == "active" ]] && break
        if (( SECONDS >= deadline )); then
            echo "[bootstrap] ERROR: amazon-cloudwatch-agent never reached 'active' within ${CW_AGENT_SETTLE_SECONDS}s (last state: '${state:-<none>}')." >&2
            echo "[bootstrap]        agent-ctl -a status = $(_cw_agent_status_blob)" >&2
            _cw_diag
            return 1
        fi
        sleep "$CW_AGENT_POLL_SECONDS"
    done

    # 2. Corroborate with the agent's own view — only when it is parseable.
    blob="$(_cw_agent_status_blob)"
    if printf '%s' "$blob" | grep -Eq '"status"[[:space:]]*:'; then
        if ! printf '%s' "$blob" | grep -Eq '"status"[[:space:]]*:[[:space:]]*"running"'; then
            echo "[bootstrap] ERROR: systemd reports the unit active but the agent reports itself not running." >&2
            echo "[bootstrap]        agent-ctl -a status = ${blob}" >&2
            _cw_diag
            return 1
        fi
    else
        echo "[bootstrap] WARN: could not parse 'agent-ctl -a status' output; relying on systemd only. Output was: ${blob:-<empty>}" >&2
    fi
    if printf '%s' "$blob" | grep -Eq '"configstatus"[[:space:]]*:' \
       && ! printf '%s' "$blob" | grep -Eq '"configstatus"[[:space:]]*:[[:space:]]*"configured"'; then
        echo "[bootstrap] WARN: agent reports configstatus != configured — fetch-config may not have installed the JSON. Output was: ${blob}" >&2
    fi

    # 3. Stability. A crash-looping agent is 'active' for a fraction of each
    #    restart period, so a single sample can be a false green. Require the
    #    unit to STAY active, and cross-check systemd's own restart counter
    #    (the same number the journal prints as "restart counter is at N").
    r0="$(_cw_restart_count)"
    stable_deadline=$(( SECONDS + CW_AGENT_STABILITY_SECONDS ))
    while (( SECONDS < stable_deadline )); do
        sleep "$CW_AGENT_POLL_SECONDS"
        state="$(_cw_unit_state)"
        if [[ "$state" != "active" ]]; then
            echo "[bootstrap] ERROR: amazon-cloudwatch-agent did not stay active for ${CW_AGENT_STABILITY_SECONDS}s (observed '${state:-<none>}') — crash-looping." >&2
            _cw_diag
            return 1
        fi
    done
    r1="$(_cw_restart_count)"
    if [[ "$r0" =~ ^[0-9]+$ ]] && [[ "$r1" =~ ^[0-9]+$ ]] && (( r1 > r0 )); then
        echo "[bootstrap] ERROR: amazon-cloudwatch-agent restarted ${r0}->${r1} during the observation window — crash-looping." >&2
        _cw_diag
        return 1
    fi

    echo "[bootstrap] OK: amazon-cloudwatch-agent active and stable for ${CW_AGENT_STABILITY_SECONDS}s (NRestarts=${r1:-n/a})."
    return 0
}

# Enable the unit EXPLICITLY, before fetch-config.
#
# The previous comment here claimed the deb postinst enables the unit. Whether
# it is the postinst or `agent-ctl`'s own `start` action (which `-s` triggers)
# is not observable from this script — and it does not matter, because BOTH
# are downstream of a fetch-config that gets far enough to start the agent. If
# fetch-config dies earlier (bad JSON, translate failure) the unit is left
# DISABLED and the agent is gone after the next reboot, with nothing to
# re-run this script on dev (its userData has no firstboot service). One
# idempotent line closes that hole.
systemctl enable "$CW_AGENT_UNIT" >/dev/null 2>&1 \
    || echo "[bootstrap] WARN: systemctl enable $CW_AGENT_UNIT failed — unit file missing?"

# fetch-config installs the JSON, translates it and (because of -s) starts the
# agent. Its exit status IS checked — `set -e` aborts on a non-zero — but a
# zero here only proves the agent was ASKED to start: the wrapper ends in
# `systemctl restart`, which returns as soon as the process forks. The agent
# can (and on this fleet did) exit 1 milliseconds later and crash-loop forever
# while bootstrap reports success. §14a asserts the thing we actually want.
/opt/aws/amazon-cloudwatch-agent/bin/amazon-cloudwatch-agent-ctl \
    -a fetch-config -m ec2 -s \
    -c file:/opt/aws/amazon-cloudwatch-agent/etc/amazon-cloudwatch-agent.json

# ── 14a. Assert the agent is actually running (not just asked to run) ──
#
# WHY THIS IS NOT `exit 1` IN PLACE. Everything from §15 to §20 runs after
# this point: the velocityai-deploy user + its restricted sudoers, the
# pg_dump / skills-backup / stuck-workflow scripts, EVERY systemd unit
# including velocityai-app.service, the first velocityai-load-secrets run
# that materialises DATABASE_URL and SECRET_KEY into /etc/velocityai/app.env,
# the app start, and the completion sentinel. Aborting here would leave a box
# with Postgres, nginx and TLS but no application, no backups, no boot-time
# start and no sentinel — strictly worse than a blind CloudWatch agent. So the
# failure is recorded and the script continues; §20 exits non-zero.
#
# The nearest precedent in this file is the §8b IMDSv1 drift check, which
# deliberately does not exit and says "the log line is the operator signal;
# cwagent ships it". That reasoning is exactly what a dead cwagent breaks, so
# a log line alone is not sufficient here — hence the deferred non-zero exit.
assert_cloudwatch_agent_running || BOOTSTRAP_DEGRADED+=("cloudwatch-agent")
```

Per-choice rationale for the non-obvious bits:

- *Absolute path in a variable, not a bare command name.* Why this and not the obvious thing: the
  bare name is not on `PATH` and would make the check fail 100% of the time (proven, I3).
- *systemd as the authoritative oracle, ctl as corroboration.* Why: a hard dependency on an
  undocumented third-party JSON string is a permanent-red risk. The observed B1 failure is caught by
  systemd alone (a 1-restart-per-minute agent is `active` for ~0.3% of samples), so nothing is lost.
- *Polling settle window instead of `sleep N`.* Why: a fixed sleep is either too short (false fail)
  or wastes time on every healthy boot. Polling costs ~0s when healthy.
- *A stability window on top of `is-active`.* Why: a single `is-active` can be a false green in a
  crash loop. This is the false-green trap the registers repeatedly record.
- *`NRestarts` as a cross-check, never the sole gate.* Why: it is exactly the counter the journal
  prints ("restart counter is at 977"), but a 60-second restart period would not increment inside a
  12-second window, so it strengthens the check rather than carrying it. Degrades silently if the
  property is unavailable. `[I]` on `NRestarts` being present on Noble's systemd 255.
- *`configstatus` is a WARN, not a failure.* Why: the observed defect is liveness; a string-literal
  dependency should not be able to redden a build; and the "config not installed" mode is caught
  independently by the liveness check on a fresh boot and by E1's `IncomingLogEvents` alarm.
- *`enable` before `fetch-config`.* Why: it must survive a fetch-config that hard-fails and aborts
  the script (I3, third correction).
- *`:-` defaults on the five knobs.* Why: the function is otherwise untestable offline. Production
  never sets them; anyone who can set them is already root.

##### I6. Ripple-effect analysis — why nothing else breaks

Assuming the fix is wrong, where does it break?

- **A healthy agent is declared dead (false fail) -> every bootstrap goes red.** The two mechanisms
  that could cause this are (a) the ctl not being on `PATH` — eliminated by using the absolute path;
  (b) the check racing the restart — eliminated by the 60s polling settle window, proven with an
  `activating→active` stub. A third, subtler one — the ctl's JSON wording drifting — is eliminated by
  making systemd authoritative and the ctl merely corroborating. Residual risk: a healthy agent that
  takes >60s to reach `active`. Not observed; the knob exists.
- **A dead agent is declared healthy (false green).** The single-sample crash-loop window. Mitigated
  by requiring sustained `active` across 12s plus the `NRestarts` cross-check. Proven with a
  `active,active,failed,active` stub and with an `NRestarts 5→9` stub.
- **Added wall-clock.** Healthy path: settle breaks on the first poll (0s) + a fixed 12s stability
  window ≈ **+12s** on a ~6-minute bootstrap. Failure path: +60s settle then fail. Well inside
  `velocityai-firstboot.service`'s `TimeoutStartSec=1800` and inside the buildspec's
  `--timeout-seconds 1800`.
- **Shell-semantics hazards.** `(( ))` used only in guarded positions (`if`/`while`) — a bare false
  `(( ))` is an errexit trap on bash ≥4 and my code never uses one. `arr+=(x)` on the RHS of `||`
  does not trip errexit. `${#arr[@]}` is safe on an empty array under `set -u` on bash 3.2 and above;
  `"${arr[*]}"` is only reached inside the `count > 0` guard. All four verified by execution.
- **`journalctl` unavailable / noisy.** Guarded with `|| true`; only runs on the failure path.
- **Re-run idempotency.** The whole change is read-only observation plus one idempotent
  `systemctl enable`. Re-running bootstrap is unaffected.
- **Partial application.** If only Step 2 lands without Step 1, `BOOTSTRAP_DEGRADED+=` on an
  undeclared array under `set -u`… actually appends fine (`+=` creates it), but Step 3's `${#...}`
  would then be the only reader — so Steps 1 and 3 must land together. If only Steps 1+3 land,
  nothing ever appends and the gate is inert. **Ship all three in one commit** (I10).
- **Concurrency / ordering.** None — bootstrap is single-threaded and this runs between two existing
  sequential sections.
- **Unattached client / slow client / restart / resume / fan-out / two browsers.** Not applicable:
  this is a host provisioning script with no runtime, no request path and no state shared with the
  application.
- **The dossier's own safety argument.** It offers none for B5 beyond "fail loudly". I evaluated that
  argument and rejected it with the enumerated §15-§20 loss (I4a) and the corroborating
  `fix/infra-uki` rationale (I4d).

##### I11. Open questions requiring a human decision

1. **Should a DEGRADED bootstrap fail the CI deploy?** With this fix, a bootstrap or reconcile that
   finds a dead CloudWatch agent exits non-zero. In a C1 reconcile invoked from a pipeline, that turns
   the deploy red even though the application is healthy. Options: **(a)** as specified — a dead
   observability agent blocks the deploy, forcing it to be fixed (my recommendation: the dossier's
   own framing is that a month of blindness cost more than any deploy delay, and the alternative has
   already been tried by accident); **(b)** exit 0 and rely solely on E1's alarm (rejected: the alarm
   does not exist yet, and B5 then delivers nothing beyond a log line the dead agent cannot ship);
   **(c)** exit non-zero only on the reconcile path, exit 0 on first boot (rejected: two behaviours
   for one condition, and first boot is exactly when a permanently-blind instance is created).

2. **Is `+12s` on every healthy boot acceptable?** The stability window is a fixed cost. Options:
   keep 12s (my recommendation — it is 0.03% of the 1800s firstboot budget and it is what buys the
   crash-loop guarantee); reduce to 6s (halves the confidence for a 2× shorter loop period); or drop
   the window entirely and rely on the single `is-active` sample plus `NRestarts` (rejected — a
   single sample is the false-green the registers repeatedly warn about).

##### I12. Shortcuts and alternatives explicitly rejected

**The dossier's own snippet, as written.** Rejected for two proven defects, not for style: the bare
command name is not on `PATH` and makes the check fail on every healthy box (`[V]`), and the absent
settle window makes it fail on a healthy-but-still-activating agent (`[V]`). Either one alone would
have produced a permanently-red bootstrap that the next engineer deletes.

**`exit 1` in place, at §14.** Rejected. Strands §15-§20 — the deploy user and sudoers, all three
backup/probe scripts, every systemd unit including `velocityai-app.service`, the first
`velocityai-load-secrets` run that supplies `DATABASE_URL`/`SECRET_KEY`, the app start, and the
completion sentinel. The resulting box serves 502s, has no backups and does not start the app on
reboot; on stage/prod `velocityai-firstboot.service` then re-runs the whole bootstrap on every boot;
the subsequent CI redeploy skips its sentinel wait (docker is present), brings up a backend with no
secrets, and times out on `/health`. The `origin/fix/infra-uki` branch independently reached the same
conclusion for §18/§19 in its own diff. Failure mode: converting an observability outage into a
service outage.

**Withholding the sentinel to force a retry.** Rejected. `ConditionPathExists=!` would re-run a
1800-second bootstrap on every reboot against a failure that reboots cannot fix, and
`infra/buildspec.yml:245-252` would block a genuine first deploy for 900 seconds and then `exit 1`.
Failure mode: an infinite retry loop plus a broken first deploy.

**`systemctl is-active` as the sole check.** Rejected. In the observed 1-restart-per-minute loop the
unit *is* briefly `active`; a single sample can be a false green. Failure mode: the exact false-green
class the registers document three separate times (Phase 17 `_TRACER`, Phase 11 dead wiring, Phase 33
dormant Concierge).

**`agent-ctl -a status` as the sole check.** Rejected. It makes a build depend on an undocumented
third-party output string; a wording change in a future agent release would redden every boot.
Failure mode: a permanent red that gets "fixed" by deleting the check.

**Parsing the status blob with `jq`.** Rejected even though `jq` is installed (`dev`:100). The ctl's
output is not contractually pure JSON; a `jq` parse failure is indistinguishable from "not running",
so a formatting change would become a hard failure. The anchored `grep -E` is tolerant and its
false-match safety is proven in both directions.

**A fixed `sleep 20` before the check.** Rejected. Too short is a false fail; too long is dead time on
every boot. The polling settle window costs ~0s when healthy and bounds the wait when not.

**`systemctl is-failed` / `--wait`.** Rejected. `is-failed` returns false during the auto-restart
`activating` window, so it misses a crash loop; `systemctl restart --wait` is not applicable because
the restart happens inside the ctl wrapper, not in our command.

**Publishing a CloudWatch metric from bootstrap so the failure is visible without CloudWatch Logs.**
Tempting — the instance role does carry `cloudwatch:PutMetricData`, and E2 already establishes the
`put-metric-data`-from-bootstrap pattern. Rejected because it duplicates E1's `AWS/Logs
IncomingLogEvents` meta-alarm, which detects the same condition continuously rather than once at
provisioning time, and adds a second detector for one fact (INV-12 in spirit). Recorded here so it is
not re-proposed: the residual weakness it would have covered — the exit code being a weak signal on
the unattended `velocityai-firstboot.service` path — is explicitly E1's to close.

**Making `configstatus != configured` a hard failure.** Rejected in favour of a WARN. The observed
defect is liveness; the "config not installed" mode is caught independently by the liveness check on
a fresh boot and by E1's alarm thereafter; and a hard dependency on a second undocumented string
doubles the drift surface for marginal gain.

**Absorbing the §19 `/health` probe or the §14 `setfacl` effective-permission check into this fix.**
Rejected on scope. `/health` is a genuinely valuable addition to the same accumulator but is a
behaviour change to a different section and belongs in its own task; the `setfacl` effective-mask
problem is **B2** and absorbing it would corrupt that issue's proof.

**Reformatting or "tidying" the surrounding §14 code.** Rejected. Four sibling issues (B1, B2, B3,
B4) edit this exact section; every gratuitous reflow is a merge conflict scheduled for someone else.
