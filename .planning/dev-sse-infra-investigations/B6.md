**4.2 `velocityai-dev-unexpected-kms-decrypt` specifically.** My brief asks what it means
that this is firing and whether it needs its own investigation.

The filter (`main.tf:1546`) is:

```text
{ ($.eventSource = "kms.amazonaws.com")
  && ($.eventName = "Decrypt")
  && ($.resources[0].ARN = "<project CMK arn>")
  && ($.userIdentity.sessionContext.sessionIssuer.arn != "<instance role arn>") }
```

Exactly **one** principal is excluded: the EC2 instance role. But the project CMK
(`local.fnd.kms_key_arn`) encrypts **everything** in the environment - all 8 CloudWatch log
groups (`main.tf:46`, `:1007`), the SNS topic (`:83`), both EBS volumes
(`compute/main.tf:57`, `:120`), every config object in the backup bucket
(`app/main.tf:88`, `:120`, `:147`), the SSM SecureStrings, and the AWS Backup recovery
points. Legitimate `kms:Decrypt` callers therefore include the CloudWatch Logs service
principal, the AWS Backup service principal, S3/SSE-KMS, the CodeBuild deploy role, and
any operator SSO session - **none of which is the instance role.**

Whether the service-principal calls match turns on one thing I could not settle offline:
how a CloudWatch Logs JSON filter evaluates `!=` against a field that is **absent**
(service-principal events carry `userIdentity.type = "AWSService"` and no
`sessionContext.sessionIssuer.arn`). If absent-field `!=` matches, every log-group decrypt
matches and the alarm is a pure false positive. If it does not match, the firing signal is
a real assumed-role principal - an operator, CodeBuild, or something that genuinely
warrants attention. I will not guess. `[I]`

**Disposition: triage BEFORE subscribing, not after.** The reason is not caution for its
own sake - it is that this is the one alarm you can never afford to train a human to
ignore. Subscribing a person to a *security* page that fires on routine platform activity
is precisely the mechanism that killed the legacy `flowin-*` topics. The decisive
observation is one CLI call:

```bash
aws logs filter-log-events \
  --log-group-name /velocityai/dev/cloudtrail-audit \
  --filter-pattern '{ ($.eventSource = "kms.amazonaws.com") && ($.eventName = "Decrypt") }' \
  --max-items 20 \
  --query 'events[].message' --output text \
  | python3 -c 'import sys,json;[print(json.loads(l).get("userIdentity",{}).get("type"),
      json.loads(l).get("userIdentity",{}).get("sessionContext",{}).get("sessionIssuer",{}).get("arn"))
      for l in sys.stdin if l.strip()]' | sort | uniq -c
```

If the principals are `AWSService` / `logs.amazonaws.com` / the CodeBuild role, the filter
is under-scoped and must gain an exclusion list before anyone subscribes. If they are
unexpected human or role identities, that is a real security finding and outranks
everything else in this dossier.

   `user_data` is not unconditionally ForceNew - it forces replacement only when
   `user_data_replace_on_change = true`.
3. **The experiment is non-vacuous.** Run C produced a real `must be replaced`, so the
   harness is capable of showing the failure I am claiming does not happen.

replace `velocityai-dev-app`. The dossier's claim is CONFIRMED and now proven rather than

##### I6. Ripple-effect analysis - why nothing else breaks

Assuming my fix is wrong, here is where it would show.

**"The apply replaces the instance and I lose Postgres."** The catastrophic case. Ruled out
by two independent guards, each proven sufficient in isolation (4.6). Additionally fenced
by the mandatory plan assertion in Part B, and by `disable_api_termination` /
`disable_api_stop` (`compute/main.tf:111-112`) which would make a destroy fail loudly
rather than silently. Residual risk: an executor who runs `apply` without reading the plan.
Mitigation: the plan assertion is written as a stop-loss with an explicit abort condition.

**"Confirming makes the new subscriber's inbox unusable."** Real, and the entire reason for
the ordering gate. Post-B1/B2/E2/E3 the expected steady state is **0 firing velocityai-dev
alarms** - unless `unexpected-kms-decrypt` (4.2) or `billing-monthly` (#20) is a true
positive, which is exactly why both are triaged before subscription rather than after.

**"The `-var-file` override silently stops working."** It would take someone converting the
CI call from `-var-file` to `-var` for the same variable, or removing `-var-file` entirely.
Both are visible one-line diffs in `buildspec.yml:198`. And after the infra-uki migration
`-var-file` becomes the *only* source, so the risk decays to zero.

**"Two subscriptions to the same mailbox means duplicate mail."** Yes - by design. The
eu-central-1 topic carries 19 alarms plus backup-job events; us-east-1 carries the billing
alarm only. They never carry the same event. No duplication.

**Concurrency / ordering.** SNS `Subscribe` is idempotent for an identical
`(topic, protocol, endpoint)` triple `[I]`; two operators running Part A concurrently
produce one pending subscription and two confirmation mails, either of which works. There
is no lock to contend and no queue to drain.

**Startup / shutdown, unattached clients, slow clients, crashed runs, restarts, resumes,
fan-out runs, revision runs, two browsers.** All null. B6 changes no runtime code path.
The application does not read the SNS topic, does not read `alert_email`, and does not know
alarms exist. The only in-application coupling is `VELOCITYAI_ACME_EMAIL`, which is read
once at first boot by `bootstrap-ec2.sh:83` and passed to `certbot --email` at `:932` - and
that script does not re-run (C1's finding: dev's userData has no firstboot service and
`/var/lib/velocityai/.bootstrap-done` does not exist).

**The ACME side effect, examined properly.** Changing `alert_email` changes the ACME
registration address baked into the *S3-hosted* bootstrap script's environment. Three
reasons this is inert on dev: (i) `user_data` is in `ignore_changes`, so the on-box
`/etc/velocityai/bootstrap.env` is not rewritten; (ii) even if it were, bootstrap does not
re-run; (iii) certbot's registered ACME account is already created and renewal does not
re-register. The only visible effect would be on a **future rebuilt** instance, where the
new address would receive Let's Encrypt expiry notices - which is arguably an improvement.
`[V]` on (i) and (ii); `[I]` on (iii).

**Memory / connection-pool effects.** None. No process changes.

**Partial application.** Part A is two independent CLI calls; if the second fails you have
a confirmed eu-central-1 topic and a still-pending us-east-1 one - degraded, not broken
(you lose only the billing alarm). Part B is a single Terraform apply of two resources; if
it fails after destroying and before creating, re-running converges (the resource is
`count`-gated on a non-empty string that is still non-empty). Part C is read-only and
cannot fail the build (`|| echo None`, and WARN-only).

**Where the dossier already argues safety, I verified rather than restated:** the
`ignore_changes` claim (4.6, proven with a non-vacuous control), the destroy/recreate claim
(4.7, proven), the per-env isolation claim (4.5, read from the buildspec state keys), and
the "16 stuck legacy alarms cannot reach us" implication (4.4, read from the topic policy).

##### I9. Rollback

**Part A (confirmation).** Reversible: `aws sns unsubscribe --subscription-arn <arn>`. Note
the consequence - Terraform's state still holds the pre-confirmation
`...:PendingConfirmation` handle, so after unsubscribing, the next `app apply` will plan a
create and mint a fresh pending subscription. That is convergent, not broken.

**Part B (`dev.tfvars`).** `git revert` the commit and let the next dev push apply, or
apply by hand. The revert destroys and recreates the subscriptions back to the CI-supplied
address, in `PendingConfirmation` - i.e. a revert returns you to the *current* broken state
rather than to a working one. Say that out loud before reverting.

**Part C (buildspec guard).** `git revert`; it is read-only and WARN-only, so reverting has
no side effect beyond losing the warning.

**Not reversible, and the reason the plan assertion in T2 is non-negotiable:** an EC2
instance replacement. `velocityai-dev-root` has `delete_on_termination = true`
(`compute/main.tf:121`) and **zero snapshots** (dossier Appendix 2). Postgres lives on that
volume. There is no filesystem-level rollback for the dev box. The data EBS
(`aws_ebs_volume.data`) survives with `prevent_destroy = true` (`compute/main.tf:66`) and
the EIP survives with `prevent_destroy = true` (`:189`) - but the root volume, and with it
every host-level fix B1/B2/B3/B4/B5 and A1 apply, does not.

**What a pre-change backup must capture.** Under my recommended path, nothing on the host
is touched, so no host backup is required for B6 itself. But if this change is executed in
the same window as A1/B1/B2 (which do touch the host), the shared prerequisite is theirs:
`/root/nginx-backup-<ts>/` for the nginx config (C1's requirement) and a copy of
`/opt/aws/amazon-cloudwatch-agent/etc/amazon-cloudwatch-agent.json` before B1 rewrites it.
For B6 specifically the only "backup" worth taking is a record of the current state, so a
revert is informed rather than guessed:

```bash
aws sns list-subscriptions-by-topic --region eu-central-1 --topic-arn "$DEV_TOPIC"    > /tmp/b6-subs-eu.json
aws sns list-subscriptions-by-topic --region us-east-1    --topic-arn "$DEV_TOPIC_US" > /tmp/b6-subs-us.json
terraform -chdir=infra/terraform/app state show \
  'module.monitoring.aws_sns_topic_subscription.email[0]' > /tmp/b6-tfstate-sub.txt
```

##### I12. Shortcuts and alternatives explicitly rejected

**1. "Just click the link in the original confirmation email."** The dossier's Option 1 as
literally written. **Rejected: the token expired ~4 weeks ago** (I3, Correction 2). Nothing
about the pending subscription is clickable any more. This is the single most likely way an
executor wastes a day.

**2. `aws sns subscribe` a personal address, untracked.** The dossier flags it; I reject it
harder, on INV-12 grounds. It creates a **second, parallel delivery mechanism** alongside
the Terraform-managed one: Terraform will not remove it, will not reproduce it on a
rebuild, and the next `app apply` will still show one pending subscription forever. Worse,
it makes the Part-C guard lie - `SubscriptionsConfirmed` becomes 1 while the
Terraform-managed subscription is still dead, so the check that exists to catch this exact
failure now reports OK.

**3. Repoint via `TF_VAR_alert_email` (the dossier's Option 2).** **Rejected as written.**
It requires a `bootstrap apply`, and the bootstrap layer runs on local state that does not
exist in this repository or on this machine (I3, Correction 3). An apply from here would
run against empty state and attempt to create the state bucket, lock table and CMK against
a live account. Even with the correct state in hand, the channel it edits is deleted by
`origin/fix/infra-uki` (4.8). `-var-file` achieves the same result with one reviewable file
and no bootstrap involvement, and is proven to take precedence (I3, Correction 4).

**4. `terraform apply -replace` on the subscription to force a fresh confirmation mail.**
Works (4.7 proves the mechanism), but writes to `velocityai/dev/app.tfstate` and, if a
confirmed subscription ever exists, destroys it to create a pending one. A plain
`Subscribe` call achieves the same re-send with zero state mutation. Rejected as a
strictly worse instrument for the same job.

**5. Set `treat_missing_data = "notBreaching"` on the six host alarms so they stop firing.**
The tempting one-line "fix" for the symptom. **Rejected:** the module's own comment
(`main.tf:355-361`) explains why `breaching` is correct - *"With `notBreaching`, a dead
agent leaves every host alarm in OK state while the disk fills, OOM-killer fires, etc."*
Flipping it converts a loud, correct alert into permanent silence and would have made B1
undetectable forever. The alarms are not wrong; the agent is dead. Fix B1.

**6. Delete the alarms that are currently firing.** Same class of error. Two of them
(#7 `pg-dump-heartbeat-stale`, #17 `stuck-running-workflows`) genuinely have no working
publisher - but the correct fix is E2's and E3's *publisher*, not the alarm. Deleting
`pg-dump-heartbeat-stale` in particular would remove the only backstop on the documented
RPO of 1 hour. E2 already argues this and I agree.

**7. Confirm only the eu-central-1 topic.** The obvious reading of the dossier, and it
leaves the billing alarm mute because it is the sole publisher to the us-east-1 topic
(4.1 #20, I3 Correction 1). Rejected.

**8. Add the `SubscriptionsConfirmed` check as a hard build gate.** Rejected in favour of
WARN-only: a bounced or decommissioned mailbox would then block every deploy, trading a
monitoring gap for an availability gap. The warning is loud and appears in every build log.

**9. Fold E2/E3 into B6 because "we're in the area".** Rejected. They edit
`infra/scripts/bootstrap-ec2.sh`, which C1 has established cannot reach a running instance
without an SSM push - a fundamentally different delivery mechanism with a different risk
profile and a different verification. Folding them in would put a host-mutating change
inside a change whose entire safety argument is "this touches no host". Keep the blast
radii separate.

**10. Fix alarm #12 (`ws-disconnect-spike`) here, since I found it dead.** Rejected as
scope creep, and recorded instead: its replacement signal does not exist yet. D11 adds
`run_stream.py` logging with a closed vocabulary of close reasons
(`client_disconnect | terminal_event | sentinel | no_live_queue | evicted`); retuning #12
to that vocabulary should be D11's follow-up or E1's, not B6's. The finding is the
contribution; the fix has a better owner.
