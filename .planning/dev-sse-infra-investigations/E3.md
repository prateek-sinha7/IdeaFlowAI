##### I3. Root cause — confirmed, corrected, or replaced

**The dossier's mechanical claim is correct.** `infra/scripts/bootstrap-ec2.sh:1094` opens the
generator heredoc with a **quoted** delimiter:

```bash
cat > /usr/local/bin/velocityai-stuck-workflows-check <<'EOF'
```

A quoted heredoc delimiter suppresses **all** parameter expansion, command substitution and
arithmetic expansion in the body. The body is therefore written to
`/usr/local/bin/velocityai-stuck-workflows-check` byte-for-byte, including `:1106`'s literal
`--namespace VelocityAI/Prod`. Every environment that runs bootstrap installs the identical
generated script, so dev, stage and prod all `put-metric-data` into `VelocityAI/Prod`. [V]

Verified by direct reproduction — a prototype that writes the three variants and runs them
(`/private/tmp/.../scratchpad/e3_proto.sh`):

```
### grep the GENERATED files for the namespace token
before: namespace VelocityAI/Prod
naive : namespace VelocityAI/${ENV_TITLE}"   <-- literal ${ENV_TITLE}, NOT expanded
fixed : CW_NAMESPACE=VelocityAI/Dev
```

The `naive` line is the negative control that kills the obvious fix: putting `${ENV_TITLE}` inside
the *still-quoted* heredoc emits the literal five-character string `${ENV_TITLE}` into the
generated file, so the probe would call `put-metric-data --namespace 'VelocityAI/${ENV_TITLE}'`
and create a garbage namespace. [V]

**Correction 1 — the derivation the dossier proposes to introduce already exists.**
The dossier's fix says *"Then derive the namespace as `VelocityAI/${ENV_TITLE}`."* That derivation
is already in the file, at `:80-82`:

```bash
# Capitalize first letter for CloudWatch namespace ("prod" -> "Prod"). Matches
# the monitoring module's `cw_metric_namespace = "VelocityAI/${title(env)}"`.
ENV_TITLE="${ENVIRONMENT^}"
```

and it is already consumed, correctly, 888 lines later at `:970` inside the **unquoted** agent
config heredoc: `"namespace": "VelocityAI/${ENV_TITLE}",`. It matches the Terraform side exactly
(`infra/terraform/app/main.tf:173`: `cw_metric_namespace = "VelocityAI/${title(var.environment)}"`).
So the question is **not** what the derivation should be — it is *how a value computed in the
bootstrap shell reaches the execution context of a script generated inside a quoted heredoc*, and
the answer must be a **thread**, not a second derivation (INV-12). [V]

**Correction 2 — the "why it occurred" is not quite what the dossier says.** The dossier writes:
*"the namespace literal was written inside it without noticing that it therefore could not be
templated."* `git blame` says otherwise:

```
27483e6ae (imran-hex       2026-05-11 1104) COUNT=${COUNT:-0}
27483e6ae (imran-hex       2026-05-11 1105) aws cloudwatch put-metric-data \
e1a3a4959 (sharas_hexaware 2026-07-01 1106)     --namespace VelocityAI/Prod \
27483e6ae (imran-hex       2026-05-11 1107)     --metric-name StuckRunningWorkflows \
```

The surrounding script is from `27483e6a` (2026-05-11), when **prod was the only environment** —
`Flowin/Prod` was then simply correct. `e1a3a4959` (2026-07-01, *"migrate CI/CD and infrastructure
to CodeBuild and restructured Terraform"*) is the multi-environment restructure, and its own diff
shows both lines changing in the same commit:

```
-    "namespace": "Flowin/${ENV_TITLE}",          <- agent config, line ~958
+    "namespace": "VelocityAI/${ENV_TITLE}",
...
-    --namespace Flowin/Prod \                    <- the probe, line ~1094
+    --namespace VelocityAI/Prod \
```

So the author *did* have the templated form in hand, in the same commit, one screen above. What
actually happened is a **mechanical vendor-prefix rename** (`Flowin/` → `VelocityAI/`) applied
across a multi-env restructure: the rename correctly swept the prefix on both lines, but the
*environment segment* could only be templated on the unquoted one, and nothing flagged the
asymmetry. The quoted-heredoc boundary is why the fix wasn't available in place; the rename sweep
is why nobody looked. [V]

**Correction 3 — the defect is larger than the namespace: the probe's SQL is semantically
near-blind.** The query is:

```sql
SELECT count(*) FROM workflow_runs
 WHERE status='running' AND created_at < NOW() - INTERVAL '60 minutes'
```

But `'running'` is **not** the status an executing run carries. `StateMachine._persist`
(`state_machine.py:100-125`) writes every lifecycle transition straight to
`workflow_runs.status`, and the engine transitions through
`planning` (`engine.py:1733`) → `clarifying` (`:1885`) → `waiting_for_user` (`:1904`) →
`generating` (`:1970`) → terminal. The engine's own authoritative non-terminal set is
(`engine.py:5263-5266`):

```python
NON_TERMINAL = (
    "running", "planning", "clarifying", "waiting_for_user",
    "generating", "analyzing", "revising",
)
```

`'running'` appears in only two places in the whole system: the ORM INSERT default
(`app/models/workflow.py:23`) and the user-resume endpoint's deliberate flip back
(`app/api/run_commands.py:403`). A run therefore carries `'running'` **only in the seconds between
row insert and the first state transition** — and after a resume, again only until the first
transition. A run that crashes mid-build is left at `generating`; a run whose orchestrator died at
a review gate is left at `waiting_for_user`. **The probe sees neither.** [V]

So `StuckRunningWorkflows` counts essentially nothing. Two failure modes it *would* catch —
a row inserted and then abandoned before `planning`, and a resume that dies before its first
transition — are both far rarer than the crash-mid-execution case the alarm description names
("*orchestrator crash, DB drop, or A4 regression*", `modules/monitoring/main.tf:910`).

**Correction 4 — this alarm is NOT one of B6's 41.** `modules/monitoring/main.tf:919` sets
`treat_missing_data = "missing"`, with an explicit comment at `:915-917` saying so deliberately
(*"absence is benign in low-traffic windows"*). A CloudWatch alarm with `missing` and no datapoints
resolves to **INSUFFICIENT_DATA**, which `aws cloudwatch describe-alarms --state-value ALARM`
does not return. The dossier's own B6 text is consistent with this — it lists
`PgDumpHeartbeat` and "the hardcoded prod namespace" as *"two dead signals to fix while here"*,
separate from the 41 — but the brief I was given asserts it is "among the 41". It is not. [V]

**Causal chain, corrected end to end:**

1. 2026-05-11 (`27483e6a`): the probe is authored for a single prod environment;
   `--namespace Flowin/Prod` is correct.
2. 2026-07-01 (`e1a3a495`): multi-environment restructure. `ENVIRONMENT`/`ENV_TITLE` are
   introduced at `:79-82`; the agent config at `:970` is templated. The probe's line is inside a
   quoted heredoc, so the rename sweep can only change the vendor prefix.
3. Every bootstrap run, in every environment, writes an identical
   `/usr/local/bin/velocityai-stuck-workflows-check` pinned to `VelocityAI/Prod`.
4. The systemd timer (`:1213-1225`, `OnCalendar=*:0/15`) invokes it every 15 minutes on all three
   hosts. IAM permits it: `cloudwatch:PutMetricData` on `Resource: "*"`, region-conditioned only,
   with **no namespace condition** (`modules/iam/main.tf:157-173`).
5. `VelocityAI/Dev::StuckRunningWorkflows` and `VelocityAI/Stage::StuckRunningWorkflows` never
   receive a datapoint → both alarms sit INSUFFICIENT_DATA forever.
6. `VelocityAI/Prod::StuckRunningWorkflows` receives three environments' values interleaved. Prod's
   alarm uses `statistic = "Maximum"` with `GreaterThanThreshold` and `threshold = 0`, so **a
   single stuck run on dev would raise the PROD alarm** — a cross-environment false positive, not
   merely noise. [V]
7. That has never actually happened, because of correction 3: the query is near-blind, so all
   three environments have been publishing `0` and prod's alarm has been steadily, meaninglessly
   OK. **Prod's `StuckRunningWorkflows` alarm has never carried information.** [I — the reasoning
   is `[V]` from code; the "has never fired" claim cannot be checked without CloudWatch access,
   which is unavailable (see the AWS note below).]

**Dimension-set check — verified, not assumed.** The brief asked me to check for the
`{InstanceId}`-mismatch class a sibling found in this same file. **There is no mismatch here.**
The alarm resource has **no `dimensions` block at all** (I read the full resource body,
`:908-926` — every attribute is listed above). The publisher calls
`aws cloudwatch put-metric-data --namespace X --metric-name StuckRunningWorkflows --value N
--region R` with **no `--dimensions`**. A CloudWatch alarm with no dimensions matches only
datapoints with no dimensions, and vice versa — so the two sides agree exactly, and the alarm
would evaluate correctly the moment data arrives in its namespace. [V]

Contrast with the CW-agent alarms in the same file, which is where the sibling's finding lives:
the agent config appends `InstanceId` **and** `InstanceType`
(`bootstrap-ec2.sh:983-986`, `append_dimensions`), so an alarm specifying only `{InstanceId}`
cannot match. `StuckRunningWorkflows` is immune to that class because neither side declares any
dimension. **This is a load-bearing constraint on the fix: do not add an `Environment` dimension
to the publisher** — it would permanently break the alarm on all three environments. (I12 #5.)

**What happens to prod's alarm when dev's data stops arriving.** Precisely:

- Prod's alarm evaluates `Maximum(StuckRunningWorkflows)` over one 1800-second period against
  `> 0`, `treat_missing_data = "missing"`.
- Today, prod's namespace receives up to three publishes per 15 minutes (one per host, jittered by
  `RandomizedDelaySec=60`), i.e. ~6 datapoints per 30-minute window from three environments.
- After the fix, prod's namespace receives ~2 datapoints per window, from prod only.
- Because the values have all been `0` (correction 3), the `Maximum` was `0` before and stays `0`
  after: **no state change.** [I — the "values have all been 0" step is inferred from the code;
  I cannot query CloudWatch.]
- The *behavioural* change that matters is forward-looking: today a stuck run on **dev** would
  raise **prod's** alarm (`Maximum` across the merged series); after the fix it raises dev's. That
  cross-environment false-positive path is closed.
- Prod's alarm also stops being able to *mask* a dev problem — with `Maximum`, a genuinely stuck
  prod run and a healthy dev were indistinguishable in one series.
- If prod's own probe were ever to stop (host dead), the alarm goes INSUFFICIENT_DATA, not ALARM —
  by design (`:915-917`). That is a separate, accepted gap; `cpu_high`/`mem_high` with
  `treat_missing_data = "breaching"` are the intended dead-host signal.

**Has prod's alarm ever been meaningful?** No. Two independent reasons: (i) the series was a
three-environment merge with no dimension to disentangle it, and (ii) the underlying query is
near-blind (correction 3), so the merged series has been a constant `0`. A constant-`0`
`GreaterThanThreshold 0` alarm is permanently OK and carries no information. [I on the constancy;
[V] on both mechanisms.]

**Historical contaminated data in prod's namespace — the honest answer.** **CloudWatch metric
datapoints cannot be deleted.** There is no `DeleteMetricData` API; `aws cloudwatch delete-alarms`
removes alarms, not data. A published datapoint is immutable and expires only on CloudWatch's
retention schedule (1-minute data → 15 days, 5-minute → 63 days, 1-hour → 455 days; sub-hour
data is rolled up, never removed early). So:

- The contaminated `VelocityAI/Prod::StuckRunningWorkflows` history stays as-is until it ages out.
- Nothing needs to be done about it operationally, because the alarm evaluates **only the most
  recent `evaluation_periods × period` = one 30-minute window**. It self-heals within 30 minutes
  of dev and stage ceasing to publish.
- The only lasting cost is that any *retrospective* analysis of that series (a dashboard, a
  `get-metric-statistics` over the last quarter) is untrustworthy for the pre-fix period and must
  be read as "≤ 3 environments merged". If someone later needs a clean history, the only options
  are to start a differently-named metric or to accept the gap — both are documentation, not
  remediation.
- Do **not** attempt to "correct" it by publishing compensating datapoints. `Maximum` is not
  invertible and back-publishing is both impossible (timestamps older than 2 weeks are rejected)
  and dishonest.

Four non-obvious choices, each with its reason:

1. **`printf 'CW_NAMESPACE=%q\n'`, not `echo "CW_NAMESPACE=$CW_NAMESPACE"`.** `%q` emits a
   shell-requoted form, so a namespace containing a space or a quote (impossible today, but
   `ENVIRONMENT` is externally supplied) cannot inject shell syntax into the generated file. For
   the real values it is a no-op: bash 3.2 emitted bare `VelocityAI/Dev` in the prototype. [V]
2. **The shebang is `printf`'d, not left in the heredoc.** A shebang must be the *first* line of
   the file; putting the assignment first would demote it to a comment and the file would be
   executed by the caller's shell. Moving it out is mandatory, not stylistic.
3. **A second `:?` guard on `CW_NAMESPACE` inside the generated script.** Defence in depth for the
   partial-application case: if someone hand-edits the file and drops the assignment line,
   `put-metric-data` would otherwise be called with `--namespace ""` and either error opaquely or
   (worse, on some CLI versions) be dropped. The guard makes it fail loudly.
4. **`AWS_REGION="${VELOCITYAI_REGION:-eu-central-1}"`** replaces `"${AWS_REGION:-eu-central-1}"`.

   the probe consistent with its two sibling scripts (`:1073`, `:1088`) and removes a second

##### I6. Ripple-effect analysis — why nothing else breaks

Assuming the fix is wrong, here is where it would break.

**1. The `:?` guard aborts bootstrap on a host without `VELOCITYAI_ENVIRONMENT`.** This is the
biggest behaviour change and I want it. Failure point is `:83`, before `apt-get update` (`:91`),
before any file write, before Postgres, Docker, nginx, or systemd. The host is left exactly as
cloud-init left it. Contrast with the alternative: silently installing a prod-namespaced probe and
prod-named log groups on a dev box, which is what happens today. On the dev box specifically the
guard will pass (evidence in I5 Edit 1). *Residual risk:* a future environment provisioned by a
hand-written `bootstrap.env` would now fail loudly instead of silently mis-publishing. Accepted.

**2. The orchestrator's fail-closed hazard: `ENVIRONMENT` defaults to `prod`.** Covered twice.
At install time by the `:?` guard (Edit 1). At run time by the generated script's own
`: "${CW_NAMESPACE:?...}"` (Edit 3, choice 3). Critically, the runtime guard checks
`CW_NAMESPACE`, **not** `VELOCITYAI_ENVIRONMENT` — so the probe can never re-derive, and can never
re-introduce the `:-prod` door. The value is baked once, by the one derivation, or the script
refuses to run. This is the specific reason I rejected the runtime-derivation design (I12 #3).

**3. `printf '%q'` under a different bash.** `%q` is a bash builtin since bash 2; behaviour on a
value with no metacharacters is identical across bash 3.2 (verified locally) and bash 5.2 (Ubuntu
Noble). `${ENVIRONMENT^}` at `:82` requires bash 4+ and is **pre-existing** — the script already
depends on it, and on `${DATABASE_URL//a/b}`. The shebang is `#!/usr/bin/env bash` and Noble ships
bash 5.2. No new version dependency. [V for bash 3.2; [I] for Noble's 5.2 — inferred from the
`apt-get`-based Ubuntu Noble provisioning, unverifiable without host access.]

**4. Concurrency: the timer fires mid-patch.** Real hazard — bash reads a script incrementally, so
truncating and rewriting a file that a running `bash` has open can execute a spliced hybrid. The
host payload writes to a `mktemp` file and `mv -f`s it (atomic rename within the same filesystem),
so a running invocation keeps its original inode and completes cleanly; the next tick gets the new
file. The repo half regenerates the whole file during bootstrap, when the timer is not yet enabled
(`systemctl enable --now` is at `:1229-1232`, after `:1111`).

**5. Partial application.** Repo-only: the dev box is unchanged and keeps publishing to
`VelocityAI/Prod` — no worse than today, and the next instance is correct. Host-only: correct
immediately, reverted by any bootstrap re-run — which on dev cannot happen automatically (C1
survival matrix). Neither ordering leaves a broken state; both halves are needed for durability.

**6. Commit 2 changes what the metric measures.** After the fix the probe will report non-zero on
a dev box that has abandoned runs. With `threshold = 0` and `GreaterThanThreshold`, **one** such
row raises the alarm. On dev, D8 (the lifespan shutdown does nothing) means every deploy abandons
in-flight runs mid-write, and D9 (uncapped restore) re-launches them all at boot. Between the
crash and the restore, and for any run the restore marks `failed` via branch (c), the row is
non-terminal and older than 60 minutes → counted. **Expect the dev alarm to start firing.** That
is the metric working, but it interacts with B6: confirming the SNS subscriber and shipping
commit 2 on the same day buries a freshly-confirmed inbox. Sequencing in I10.

**7. D8/D9 change what "stuck" means.** After D8 lands, a graceful shutdown will write terminal
statuses, so the deploy-time burst shrinks. After D9 lands, runs waiting for a restore semaphore
slot stay non-terminal for longer — a *legitimate* transient that the corrected query will count.
Both argue for the widened window in I11 Q2, and both argue for landing commit 2 **before** D9 so
the baseline is observed without the semaphore's queueing effect confounding it.

**8. `waiting_for_user` exclusion could hide a real failure.** A run whose clarify or review gate
was armed and then lost (the KAN-88 class, closed by Phase 49) sits at `waiting_for_user` forever
and my query will not see it. That is a deliberate trade: including it makes the alarm fire on
every normal paused run. The correct coverage for that failure is a separate signal (an
`ArtifactStore.review_event_pending` check, or `waiting_for_user` older than *N hours* with no
`run_events` in the window) — noted as a follow-up, not smuggled in.

**9. Unattached client / slow client / restart / resume / fan-out / revision / two browsers.**
None reachable. The probe is an out-of-band 15-minute cron over a Postgres table; it holds no
queue, no SSE stream, no `_PIPELINE_QUEUES` entry, and no SQLAlchemy pool connection. It cannot
interact with A1-A5, C1's nginx, or the run transport.

**10. Memory and connection-pool effects.** One short-lived `psql` process per tick against
`127.0.0.1:5432`. `postgresql.conf`'s `max_connections` is untouched. The widened `IN (...)` reads
the same table with the same plan shape. No effect on the app's `pool_size=20, max_overflow=40`.

**11. Verifying the dossier's own safety argument.** The dossier asserts the quoted heredoc is
*"correctly [quoted], because it contains runtime shell variables that must survive."* I verified
which ones: `$DATABASE_URL` (from `app.env` at run time), `$HOST_DB_URL`, `$COUNT`, `$AWS_REGION`,
and the `${DATABASE_URL//host.docker.internal/127.0.0.1}` substitution. All four would be
destroyed by unquoting. The dossier's argument holds — which is exactly why the assignment-line
technique, not unquoting, is the fix.

##### I11. Open questions requiring a human decision

**Q1 — Should a run parked at a human review/clarify gate count as "stuck"?**
My fix excludes `waiting_for_user`. A run can legitimately sit there for hours (the whole point of
the human gate), so including it makes the alarm fire on normal product use. But a gate whose
resume event was lost — the KAN-88 failure class, closed by Phase 49 — also sits there forever, and
nothing else watches for it.
*Options:* (a) exclude, as specified — the alarm stays about crashes; (b) include with a much
longer window (e.g. `> 24 hours`), which needs a second metric or a `MetricMath` alarm.
**Recommendation: (a) now**, and log a separate follow-up for a `waiting_for_user`-aged signal.
This is a product judgement about what "stuck" means to an operator, not a technical one.

**Q2 — The 60-minute window and the `created_at` clock.**
`workflow_runs` has no `updated_at` column, so `created_at` is the only clock available without a
migration. The register records a real 39-minute `app_builder` run
(`IMPLEMENTATION-REGISTER.md`, dossier A5), so a legitimately long run plus a fix loop can exceed
60 minutes and be counted. My commit 2 deliberately leaves both alone so exactly one thing changes.
*Options:* (a) leave at 60 and accept some false positives; (b) widen to 90 minutes; (c) add an
additive nullable `updated_at` (Q3-compliant, one migration) or derive last activity from
`max(run_events.created_at)` and use that as the clock.
**Recommendation: (b) as a one-line follow-up after a week of observation, (c) as the durable
answer.** Both change what the alarm means, hence a decision.

**Q3 — Should `bootstrap-ec2.sh:79` and `:621`'s prod defaults be made globally fail-closed?**
`ENVIRONMENT="${VELOCITYAI_ENVIRONMENT:-prod}"` (`:79`) and
`PREFIX="${VELOCITYAI_PARAM_PREFIX:-/velocityai/prod}"` (`:621`, inside `velocityai-load-secrets`)
both silently fall back to **prod** on a mis-provisioned host. `:79` would then produce
prod-named log groups; `:621` would make a dev box read prod's SSM SecureStrings. Neither is live
today (`user_data.sh.tpl:53-56` always writes both), and both are outside E3's lane.
*Options:* (a) leave them, with E3's targeted guard covering only the namespace; (b) change both to
`:?`, which affects B1/B3/B4's log-group naming and the secrets path.
**Recommendation: (b), as a separate cross-cutting infra commit** — a default that silently selects
production is the same defect class this whole issue is about. But it must be a deliberate choice,
not a side effect of E3.

**Q4 — E2's `VelocityAI/Backups` namespace (see I10).**
`PgDumpHeartbeat` publishes to a hardcoded, dimensionless, cross-environment namespace whose alarm
uses `SampleCount < 1`, so a healthy prod would mask a dead dev backup timer. Fixing it properly
requires a Terraform change on **all three environments**, which the dev-only scope fence forbids
without a decision.
*Options:* (a) `var.cw_metric_namespace` + publish to `$CW_NAMESPACE`; (b) keep the shared
namespace and add an `Environment` dimension to both sides; (c) defer.
**Recommendation: (a)** — it reuses the derivation this issue introduces and matches every other
alarm in the module. But it needs sign-off on touching stage and prod Terraform.

##### I12. Shortcuts and alternatives explicitly rejected

1. **Unquote the heredoc** (`<<'EOF'` → `<<EOF`) **and let `${ENV_TITLE}` expand.**
   Destroys the generated script: `$DATABASE_URL`, `$HOST_DB_URL`, `$COUNT`, `$AWS_REGION` and
   `${DATABASE_URL//host.docker.internal/127.0.0.1}` would all be evaluated at *install* time. At
   install time `DATABASE_URL` is unset, so the `:?` guard at `:1098` would abort bootstrap
   immediately — and if it did not, the generated file would contain a frozen, empty connection
   string and a frozen `COUNT`. The dossier's own safety note is correct on this.

2. **Unquote and backslash-escape everything else** (`\$DATABASE_URL`, `\${DATABASE_URL//…}`).
   Technically possible, six escapes deep, and it converts a file that is currently *obviously*
   verbatim into one where every future edit must remember the escaping rule. The nginx block at
   `:730-915` already pays this tax and needs a three-line comment to explain it. Adding a second
   such block for one interpolation is a poor trade; the buildspec technique gets the same result
   with zero escaping.

3. **Read `$VELOCITYAI_ENVIRONMENT` at *run* time inside the generated script** and do
   `ENV_TITLE="${VELOCITYAI_ENVIRONMENT^}"; --namespace "VelocityAI/$ENV_TITLE"`.
   This *works* — the unit already has `EnvironmentFile=/etc/velocityai/bootstrap.env` (`:1207`) —
   which is exactly why it must be named and rejected. Two concrete failures: **(i)** it is a
   **second derivation** of a value the script already derives at `:82`, which is precisely the
   dual implementation INV-12 forbids, and the two would drift the next time someone changes the
   naming convention; **(ii)** it is **fail-open through a different door** — if `bootstrap.env`
   ever lost the key, `${VELOCITYAI_ENVIRONMENT^}` yields the empty string and the probe publishes
   to `VelocityAI/`, or, if anyone "helpfully" adds a `:-prod` default (as `:79` and `:621` both
   do), it silently re-creates the original bug. The orchestrator's fail-closed requirement rules
   it out.

4. **`sed -i` the generated file immediately after the heredoc** —
   `sed -i "s|VelocityAI/Prod|VelocityAI/${ENV_TITLE}|" /usr/local/bin/velocityai-stuck-workflows-check`.
   Leaves the wrong literal in the source of truth, so the file on disk and the file in the repo
   disagree about what the namespace is. Every future reader of `bootstrap-ec2.sh:1106` sees
   `VelocityAI/Prod` and has to find the `sed` 3 lines later to know it is a lie. It also creates an
   order dependency (any later edit that regenerates the file must remember to re-run the `sed`).

5. **Add an `Environment` dimension to the publisher instead of splitting the namespace.**
   `--dimensions Environment=$ENVIRONMENT` would separate the three environments *within*
   `VelocityAI/Prod`. It **permanently breaks all three alarms**: `aws_cloudwatch_metric_alarm.stuck_workflows`
   declares no `dimensions`, and a dimensionless alarm matches only dimensionless datapoints — so
   every environment's alarm would go INSUFFICIENT_DATA forever. Fixing that means a Terraform
   change on stage and prod (scope-fenced) and it would diverge from `cw_metric_namespace`, which
   the other 22 alarms in the module already use. The namespace, not a dimension, is this
   codebase's environment discriminator.

6. **Delete the alarm.** Cheapest and genuinely tempting once you know the query is near-blind
   (I3 correction 3): the alarm has never carried information, so deleting it loses nothing
   *today*. But it is the only signal anywhere in the stack for a crashed orchestrator leaving
   rows non-terminal — the exact failure D8 and D9 make more likely, not less. Deleting it trades a
   broken signal for no signal.

7. **Fix the namespace and leave the SQL alone.**
   This is what the dossier scopes E3 to, and it is worse than it looks. Post-fix, `VelocityAI/Dev`
   would receive a steady stream of `0`s, the dev alarm would leave INSUFFICIENT_DATA and settle on
   **OK**, and the verification step in the dossier (*"Confirm `VelocityAI/Dev` gains a
   `StuckRunningWorkflows` metric and the dev alarm leaves INSUFFICIENT_DATA"*) would **pass** —
   while the alarm remains incapable of detecting a stuck run. A green alarm that cannot fire is
   worse than a grey one, because it stops anyone looking. Hence commit 2, separated but
   recommended.

8. **Change `treat_missing_data` from `"missing"` to `"breaching"`** so the dev alarm's silence
   becomes an alert. `modules/monitoring/main.tf:915-917` explains the current setting deliberately
   (*"absence is benign in low-traffic windows and we already alarm separately on a dead host"*),
   and B6 shows that `breaching` on a metric with no publisher is exactly what produces
   permanently-firing alarms nobody reads. The correct fix for absence is to make the publisher
   work, which is this issue.

9. **Hardcode `VelocityAI/Dev` on the dev box only.** Fixes the symptom on one host, guarantees the
   repo and the box disagree, and is silently reverted the moment anyone re-runs `bootstrap-ec2.sh`
   — a re-run that C1's durable half is explicitly designed to make possible.

10. **Add an index on `workflow_runs.status`** to "make the widened query fast." No measured need:
    `workflow_runs` is one row per run, the probe runs every 15 minutes, and the query already
    seq-scans today. It would also be a migration (Q3 review surface) and would tax the insert
    path for a cron job. Rejected on "prove, don't presume".

11. **Write the fix into `origin/fix/infra-uki` instead of `dev`.** That branch migrates CI to
    GitHub Actions and deletes `infra/buildspec.yml` (−324 lines), so C1 correctly routes *pipeline*
    work there. But E3 needs **no pipeline change** — it rides the existing
    `aws_s3_object.bootstrap_script` upload, and the branch does not touch `bootstrap-ec2.sh`
    lines `79-84`, `970` or `1094-1111` (verified: its only hunks in that file are at
    `@@ -544 @@`, `@@ -1239 @@`, `@@ -1261 @@`). Putting E3 on the unmerged branch would delay a
    working fix behind an unrelated migration for no benefit.
