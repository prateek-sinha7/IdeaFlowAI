**Step 1 — `frontend/e2e/fixtures/mockSse.ts`: add the live re-delivery channel.**

*Why this and not the obvious thing:* the obvious thing is to push a second copy of the frame onto `this.frames`. That is **wrong and would be silently vacuous** — `framesAfter(cursor)` (`:408-411`) filters `f.data.seq > cursor`, so the moment the consumer's cursor passes that seq the duplicate is never served again, and the test would pass without any duplicate ever reaching the browser. It is also *unfaithful*: the backend filters only the **durable replay** (`authz.py:325`, `RunEvent.seq > after_seq`); the **live queue** re-publishes rows verbatim and is not cursor-filtered — which is exactly why the FE dedup exists. A cursor-exempt one-shot channel models the real mechanism.

**1a.** Insert after the `lastAttachCursor` declaration (currently `mockSse.ts:124`), i.e. immediately before `/** Every recorded up-channel command … */` at `:126`:

```ts
  /**
   * Frames queued for LIVE re-delivery — served EXACTLY ONCE on the next stream
   * serve and EXEMPT from the `Last-Event-ID` cursor filter.
   *
   * Models the A2 subscribe-before-replay overlap FAITHFULLY. The backend
   * cursor-filters only the DURABLE replay (`RunEvent.seq > after_seq`,
   * `backend/agents/authz.py`); the LIVE queue re-publishes rows verbatim, so a
   * row already covered by the replay CAN arrive a second time carrying the SAME
   * `event_id` and the SAME `seq` (any other shape is impossible —
   * `uq_run_events_scope_event` is UNIQUE on `(run_id, owner_id, workspace_id,
   * event_id)`). Pushing a second copy onto the DURABLE tail would NOT model
   * this: `framesAfter()` would drop it as soon as the consumer's cursor passed
   * that seq, and a dedup test built on it would pass vacuously.
   *
   * Empty unless a spec calls `redeliver()`, so every other spec in the suite is
   * served a byte-identical body.
   */
```

##### I6. Ripple-effect analysis — why nothing else breaks

Assuming the fix is wrong, here is where it would show.

**Concurrency / ordering.** The new test's determinism rests on one claim: *emits issued in a single synchronous block all land in the same serve.* Verified mechanically — `emit()` (`mockSse.ts:169-176`) calls `wakeStreams()` (`:414-418`), which only *resolves* promises; the awaiting `handleStream` continuation is a microtask and cannot run until the spec's synchronous statements complete. This is the same guarantee TS-J-02 (`ts-j.streaming.spec.ts:44-46`) and TS-K-03 (`ts-k.wave-tree.spec.ts:40-42`) already rely on. If it were false those specs would already be flaky, and they are not (the whole mocked suite ran 132/0 twice at 42-11).

**Race between the app's attach and the emits.** Two cases, both safe. (i) The app is already attached and long-polling → the first emit wakes it, and by then the whole block including `redeliver()` is queued. (ii) The app has not attached yet → `framesAfter(null)` returns the full tail *and* `liveRedeliveries` is drained on the first serve. In both cases the duplicate is delivered, and `redeliveredCount` proves it.

**Reconnect churn between the two serves.** After serve 1 the mock closes the response; `useRunStream` sees the close and calls `scheduleReconnect()` (`:296-309`, 1 s backoff) → reattaches with `Last-Event-ID: 4`. BUG-015's suppression (`:389`) only applies after a `stream_attached{live:false}` or a `pipeline_cancelled`/`pipeline_failed`; the new test emits none of those, so the reconnect happens. `framesAfter(4)` is empty → long-poll → `agentComplete` (seq 5) wakes it. Cost ≈ 1 s inside a 45 s timeout. `liveRedeliveries` is already empty, so no second count.

**A slow / aborted client.** If `route.fulfill` throws (the app aborted mid-serve), the drained entries are put back (`slice(redeliverCount)` is only applied inside the `try`, after a successful fulfil), so the duplicate is retried on the next serve. `redeliveredCount` never over-counts.

**A `redeliver()` racing an in-flight fulfil.** `redeliverCount` is snapshotted **before** the `await`; the post-fulfil consume uses that snapshot, so an entry pushed during the await survives to the next serve. Without the snapshot, `this.liveRedeliveries.slice(this.liveRedeliveries.length)` would have silently dropped it.

**Unattached client / crashed run / restart / resume / fan-out / revision run.** All out of reach: `liveRedeliveries` is empty for every spec but the new one, and the new one models none of those flows.

**Two browsers.** Test 04 still opens a second page. My change removes nothing there — `tab2.route(SSE_URL_RE, …)` and `tab2.close()` are preserved, so the tab-lifecycle behaviour of the suite is unchanged.

**Memory / connection pool.** `liveRedeliveries` holds at most the frames a spec explicitly queues (one, here) and is emptied on the next serve. `redeliveredCount` is a number. No sockets, no DB.
