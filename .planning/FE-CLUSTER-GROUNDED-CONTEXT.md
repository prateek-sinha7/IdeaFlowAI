# FE run-screen cluster — grounded fix spec (BUG-001 / 002 / 003 / 005)

> Four live-QA bugs, **one class**: *the run-screen live state is not bound to the run being VIEWED* (it binds to the launched/latest run, or accepts frames from any concurrently-attached run). Pre-existing (Phases 29/32/36/39); the WS→SSE cutover + the DEF-44-12-4 fix (which made opened runs actually render) EXPOSED them. **Full per-bug root causes (verified to file:line + empirically): `.planning/SSE-QA-BUG-LOG.md` → BUG-001/002/003/005 — READ THOSE FIRST.** This file is the executable spec for a `gsd-quick --validate`. Frontend-only.

## The four fixes (each already root-caused; sequence as atomic commits)

### Piece 1 — BUG-005 (highest priority): run-scope the reducer so a CONCURRENT run's frame can't wipe the VIEWED run's clarify
- **Cause:** the page SSE subscriber (`frontend/src/app/dashboard/page.tsx:909-912`) forwards EVERY frame from EVERY attached run into the global reducer, and the `pipeline_start` branch (`page.tsx:462-482`) UNCONDITIONALLY runs `setQuestionnaireData(null)` (:481) + `setActivePipelineRunId(null)` (:482) + clears the seen-set (:463) with **no run-identity guard**. So a *different* attached run entering BUILD wipes the viewed run's clarify → "0/0 BUILDING", no questions. (Reproduced under concurrent load: two runs 120ms apart + the QA campaign's ~10 live runs.)
- **Fix (targeted, lower-risk — preferred):** guard the `pipeline_start` reset at `page.tsx:462` so it only fires for the run being viewed/tracked: `if (data.pipeline_run_id && data.pipeline_run_id !== (activePipelineRunId ?? contentSourceRunId ?? pipelineState.pipelineRunId)) { /* foreign run — do not reset the viewed run's clarify/seen-set */ }`. **Systemic alternative (more thorough, higher-risk):** run-scope the subscriber itself at `page.tsx:909-912` so foreign-run frames never reach the reducer at all. Planner to choose; the targeted guard is the safe default. **MUST preserve the primary launch flow** — the just-launched run's own `pipeline_start` MUST still reset+seed (it IS the viewed run: `activePipelineRunId`/`pipelineRunId` match).
- **Secondary (defense):** guard the double-mint (two identical launches 120ms apart) if cheap; optional.

### Piece 2 — BUG-001: bind the run-lane TITLE to the viewed run, not `recents[0]`
- **Cause:** `frontend/src/components/layout/DashboardLayout.tsx:1323` `const latestRunTitle = recentRuns?.[0]?.title;` — always the most-recent run, wins the ternary at `:1325` over `submittedBrief`, so the lane title (`LaneRunHeader` `data-testid="lane-run-title"`) never tracks the viewed run.
- **Fix:** resolve the viewed run first — `const viewedRun = contentSourceRunId != null ? recentRuns?.find(r => r.id === contentSourceRunId) : recentRuns?.[0]; const latestRunTitle = viewedRun?.title;` — keep the existing ternary. Byte-identical for the launch flow (`contentSourceRunId` null → `recents[0]`); correct on complete/reopen; falls back to `submittedBrief` (the viewed run's own brief) if outside the recents window.

### Piece 3 — BUG-002: route History-list tap through the shared run screen (with the left chat/revise lane), not the divergent `RunDetailPage`
- **Cause:** the History mount (`DashboardLayout.tsx:1506-1508`) passes NO `onSelectWorkflowRun`; `WorkflowHistory.handleSelectRun` (`frontend/src/components/history/WorkflowHistory.tsx:155-162`) only routes to the execution view when `run.id === activeRunId`, else falls to `setSelectedRun` → the internal `RunDetailPage` (one-shot `getRunSummary`, no SSE attach, no chat lane, stale "QUEUED", "No agent data"/"No preview").
- **Fix:** add an `onOpenRun?` prop to `WorkflowHistoryProps`; have `handleSelectRun` call `onOpenRun(run)` instead of `setSelectedRun`; at `DashboardLayout.tsx:1506` pass `onOpenRun={(run) => { onSelectWorkflowRun?.(run); setMainView("execution"); }}` (byte-identical to the Home-recents line 1475). **Carry-over to preserve before retiring RunDetailPage:** cross-workflow chaining ("Suggested next steps"/`onChainPipeline`) is the one genuine gap — keep it reachable (the History list's family rows + the run-screen chain affordance); the VersionTimeline version-switch stays reachable via the History list.

### Piece 4 — BUG-003: stop the revise "Run refinement" from silently no-op'ing on an opened run
- **Cause:** `handleRevisePpt` (`DashboardLayout.tsx:493`) opens with `if (!pptxCode && !pptContent) return;` which short-circuits BEFORE the self-sufficient REST path (`postRevision(token, contentSourceRunId, …)` at `:504`, which reseeds the parent deck server-side and needs no local content). On a reopened od_ppt run both are empty (od_ppt's `fullRun.output` can be empty — LV-02), so it returns firing nothing; `confirmRefinement` (`RunChatLane.tsx:712-715`) then clears the chip unconditionally.
- **Fix:** relax the guard to `if (!contentSourceRunId && !pptxCode && !pptContent) return;` so the REST path fires whenever a parent run id exists; AND bind the revise-handler selection to the viewed run's TYPE on reopen (the `workflowType` sync effect at `DashboardLayout.tsx:330` is `isRunning`-gated, so a completed reopen may resolve `onRevise` to the wrong handler — thread the viewed run's type from `handleSelectWorkflowRun`). Check the sibling handlers (`onReviseUserStory`/`onRevisePrototype`/`onReviseAppBuilder`) share the guard pattern — apply the same relaxation where the REST path is self-sufficient.
