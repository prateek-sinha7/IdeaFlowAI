### BUG-003 — Revise-via-chat "Run refinement" fires nothing / launches no revision on an opened run  [🟠 major] [FIXED ✅]
- **RESOLVED:** FIXED (quick 260716-j1u, 8b4e2eb7) — offline-proven TS-U-09

- **Found:** 2026-07-16 · live Bedrock QA · surface run screen → left chat lane (`RunChatLane`) confirm-first refinement chip, on a **recents/history-opened COMPLETED od_ppt run** (`6c6f38c7`, "A 6-slide investor pitch for a B2B carbon-accounting SaaS").
- **Symptom:** On the opened run, typing a change and chat-send correctly HELDS it behind the confirm chip ("RUN A REFINEMENT WITH THIS CHANGE? … [Run refinement] [Dismiss]", 44-02 behavior — no POST on send, verified). Clicking **"Run refinement"** → **ZERO non-GET `/api/` requests fire**, the chip disappears, and **NO `*_revision` run is created**. The opened run's deliverable **Preview was also BLANK** (presentation.pptx did not render inline). Shots: `~/.claude/jobs/e660aea4/tmp/shots-qa/{revise-chip,revise-launched,revise-clean-after}.png`.
- **Root cause (investigation agent — read `.planning/IMPLEMENTATION-REGISTER.md` global + FE run-screen/revise phase sections 31/39/42/44 + Revision-Families B1 + LV-02/Phase-15; grep-confirmed od_ppt agent membership in `backend/agents/registry.py` and the od_ppt deliverable manifest):**
  - **The swallow (primary, deterministic) — `frontend/src/components/layout/DashboardLayout.tsx:493`.** `handleRevisePpt` opens with a pre-existing empty-content guard `if (!pptxCode && !pptContent) return;` that short-circuits BEFORE the self-sufficient REST path at `:504` (`if (contentSourceRunId) { postRevision(token, contentSourceRunId, { target_artifact_type, instruction }) … }`). On a reopened od_ppt run BOTH content fields are empty, so the handler returns immediately → no `postRevision`, no `onStartPipeline` → **zero network requests**. The confirm handler `confirmRefinement` (`frontend/src/components/chat/RunChatLane.tsx:712-715`) calls `setHeldRefinement(null)` **unconditionally** after invoking `onRevise`, so the chip vanishes even when `onRevise` no-ops — exactly the observed "chip disappears, nothing happens." Wire: chip button `data-testid="chat-refinement-confirm"` `onClick={confirmRefinement}` (`RunChatLane.tsx:803`) → `onRevise` = `activeReviseHandler` (`DashboardLayout.tsx:1717` ← selector `:1233-1240`) → `handleRevisePpt`.
  - **The empty/null fields (why both are empty on a reopened od_ppt run — VERIFIED):**
    - `pptxCode` (`DashboardLayout.tsx:481`) = `pipelineState?.agents.find(a => a.id === "ppt-code-generator" && a.status === "done")?.output`. **od_ppt has NO `ppt-code-generator` agent** — its agents are `od-ppt-brief-analyst` / `od-ppt-composer` / `od-ppt-validator` (`backend/agents/registry.py:53-57`); that agent belongs only to the legacy `ppt` pipeline. So `pptxCode` is **structurally always `undefined` for od_ppt** (live and reopened). The guard therefore reduces to `if (!pptContent) return;` for od_ppt — no second field can rescue it.
    - `pptContent` (a page.tsx prop, `page.tsx:83`) on reopen = `fullRun.output` (set at `page.tsx:1254`, `else if (fullRun.type === … "od_ppt" …) setPptContent(fullRun.output)`), but ONLY `if (fullRun.output && isContentTerminal)` (`:1250`). For this run `fullRun.output` was **empty**, so `pptContent` stayed `""` (cleared at reopen start `page.tsx:1169`, never repopulated). Empty `fullRun.output` is ALSO exactly why the Preview was blank — **the blank preview and the no-op revise are SIBLING symptoms of the same empty `output`.**
    - **Why od_ppt's `output` can be empty (LV-02, register lines 79/1487/1512/1553/1605):** od_ppt's deliverable is `strategy: ppt`, `name: presentation.pptx` (`backend/agents/workflows/od_ppt/workflow.yaml:11-13`); the `ppt` strategy unwraps the `od-ppt-validator`'s `<artifact>`-wrapped deck into `final_output`, persisted to `wr.output` only `if final_output:` (`backend/app/api/run_commands.py:1445-1446`). LV-02 is the KNOWN failure mode where the validator streams QA narration (or nothing parseable) instead of a deck → `final_output` empty/non-deck. ### BUG-004 — DB connection-pool exhaustion (QueuePool 5+10) under concurrent runs → 500 on submit_answers/_review_gate_owned_by  [🟠 major] [FIXED ✅]
- **RESOLVED:** FIXED (quick 260716-heb, d418b5a1/56deb5c4) — live-proven (25 streams)

- **Found:** 2026-07-16 · live Bedrock QA under concurrent load (~10+ simultaneous runs — several `generating`/streaming, some at clarify/gates) · surface: `POST /api/runs/{id}/answers` (clarify-skip) and any transactional REST command. Worked (200) earlier with fewer active runs; became a consistent 500 once ~10+ runs were live. Traceback: `~/.claude/jobs/e660aea4/tmp/uvicorn44.log`.
- **Symptom:** `submit_answers` (`run_commands.py:261`) → `_review_gate_owned_by` (`run_engine.py:344`, the `.first()`) raises `sqlalchemy.exc.TimeoutError: QueuePool limit of size 5 overflow 10 reached, connection timed out, timeout 30.00` → HTTP 500. i.e. all 15 SQLAlchemy connections were checked out and NONE freed within the 30s pool_timeout.
- **Root cause (investigation agent — read `.planning/IMPLEMENTATION-REGISTER.md` global + Phase-5 D-08 sync-DB idiom, Phase-29 SSE endpoint, Phase-44 WS→SSE cutover; verified against installed fastapi 0.115.6 / starlette 0.41.3 / sqlalchemy 2.0.36; empirically reproduced the leak):**
  - **This is a genuine CONNECTION LEAK on the SSE down-channel, not merely a too-small pool.** The failing endpoint is the *victim*: `_review_gate_owned_by` (`run_engine.py:339-348`) opens `_get_db()` and correctly `finally: db.close()`; it blocks on `.first()` only because the pool is already fully drained by leaked stream connections.
  - **The leaker — `app/api/run_stream.py` (the SSE endpoint `stream_run_events`, the SOLE run-event transport since 44-07).** It declares `db: Session = Depends(get_db)` (`run_stream.py:208`), builds `store = ScopedStore(owner_id=…, workspace_id=…, session=db)` (`:233-237`), and passes that store into the streaming generator `_iter_sse_frames`, which calls `store.read_events(...)` INSIDE the stream body at `:145` (durable replay) and `:178` (gate re-arm full-log read).
  - **Why the injected session leaks a pool connection (mechanism, verified in installed source):** FastAPI ≥0.106 tears down `yield` dependencies BEFORE the streaming response body runs. In `fastapi/routing.py::get_request_handler`, `solve_dependencies` + `run_endpoint_function` run *inside* `async with AsyncExitStack() as async_exit_stack:`; the handler then `return response` and Starlette does `await response(scope, receive, send)` *outside* that block — so `get_db`'s `finally: db.close()` (`database.py:43-49`) fires before `_iter_sse_frames` yields its first frame. When the generator then calls `store.read_events` on that already-closed session, `ScopedStore._acquire` sees an injected session (`authz.py:87-99`) → `owned=False` → the query RE-BEGINS a transaction and checks out a FRESH QueuePool connection, and `read_events`'s `finally: if owned: session.close()` (`authz.py:328-330`) does NOT close it (owned=False) — while `get_db`'s finally has ALREADY run. Nothing deterministically returns that connection; it is reclaimed only when the orphaned `Session` is garbage-collected.
  - **Empirical proof (`/tmp/sse_pool_repro2.py`, same interpreter/versions, QueuePool pool_size=1):** ordered log — `EXIT get_db (finally close) checkedout=0` at 1.5ms (FastAPI closes the request session BEFORE streaming) → `after read_events in gen, checkedout=1` at 1.8ms (generator re-acquires) → `gen done, checkedout=1` (held the whole stream) → `client stream closed, checkedout=1` → `after 0.3s settle, checkedout=1` (STILL held) → `after gc.collect(), checkedout=0` (released ONLY by GC). This reproduces the leak exactly; a plain StreamingResponse that does NOT query inside the generator keeps `checkedout=0` (repro v1), confirming the query-on-injected-session-inside-the-generator is the trigger.
  - **Connection math / does it structurally exceed 15:** pool = `create_engine(..., pool_pre_ping=True)` with NO explicit sizing (`database.py:12-16`) → SQLAlchemy defaults `pool_size=5 + max_overflow=10 = 15` max, `pool_timeout=30`. Each live SSE stream leaks exactly 1 connection (the generator's re-acquired session; the `get_current_user` session + the two pre-stream owner-check queries at `:220`/`:239` return normally). N concurrent live streams → up to N leaked connections held at once, PLUS connections from recently-ended/reconnected streams that are orphaned-but-not-yet-GC'd (the browser's native EventSource auto-reconnect, duplicate tabs, and React remounts each open a new stream that leaks again on teardown). So under the reported ~10+ concurrent runs the held count reaches/exceeds 15 and the pool saturates; the next transactional command (`submit_answers` → `_review_gate_owned_by` → `_get_db().query().first()`) waits 30s and 500s. GC is the only reclaim path, so under sustained streaming load the leak outruns reclamation.
  - **Checkpointer is NOT the cause (ruled out).** The LangGraph Postgres checkpointer uses a SEPARATE psycopg `AsyncConnectionPool(max_size=10)` (`app/agents/checkpointer.py:91-96`), independent of the SQLAlchemy engine/QueuePool — it adds its own ~10-conn load to Postgres but does not draw from (or exhaust) the 15-conn QueuePool named in the traceback.
  - **Sibling sweep (only run_stream.py has the leak pattern):** the 2nd SSE endpoint — chat, `run_commands.py:1819` — is SAFE: its generator opens its OWN `_get_db()` and closes it in `finally` (`:1795`/`:1815`). `runs.py:838`/`:888` also use `ScopedStore(session=db)` but are non-streaming JSON handlers (query runs within request scope → returned normally). `prototype_templates.py:259` StreamingResponse touches no DB in its generator. The correct idiom is exactly what `post_message` uses (`run_commands.py:758` — `ScopedStore` with NO injected session, so every store op self-manages its SessionLocal).
  - **Pre-existing vs recent:** the default-pool config (`database.py:12`, no `pool_size`/`max_overflow`) is PRE-EXISTING — commit `34ac261e` (2026-05-10). The leaky SSE endpoint shipped `7020bf82` (2026-07-08, Phase 29-02) behind a flag, but became the ALWAYS-ON SOLE run-event transport on `7b79b972` (2026-07-15, 44-07, feat/ui-2) — one day before this was observed live. So a latent leak went hot exactly when SSE replaced WS as the sole down-channel; the small pool (pre-existing) is what makes the leak fatal quickly.
- **Fix (PROPOSED — investigation only, NOT applied; a leak fix is more correct than just enlarging the pool):**
  1. **PRIMARY — stop the SSE generator from using the request session (removes the leak).** In `run_stream.py`, do NOT hand the `Depends(get_db)` session to the store consumed inside `_iter_sse_frames`. Construct the generator's store WITHOUT a session — `store = ScopedStore(owner_id=current_user.id, workspace_id=workflow_run.workspace_id)` (session=None) — so each `read_events` opens AND closes its own `SessionLocal` (`authz.py:95-99` owned=True → `:328-330` closes). Keep the request `db` only for the pre-stream Layer-1/Layer-2 owner checks (`:220`, `:239`). Net effect: the replay reads become 2 brief open/close checkouts and NO connection is held during the idle live-drain loop. This mirrors the safe pattern already in `post_message`/the chat SSE. (Alternative but weaker: wrap `_iter_sse_frames` in `try/finally: db.close()` — still holds one connection idle for the entire stream; prefer the session-less store.)
  2. **SECONDARY — right-size the pool (defense-in-depth, pre-existing config).** `database.py:12` — set explicit `pool_size`/`max_overflow` to the concurrent-run target plus resiliency, e.g. `pool_size=20, max_overflow=40, pool_timeout=30, pool_recycle=1800` (tune to expected concurrency; `pool_pre_ping=True` already present). NOTE: sizing ALONE does not fix the leak — with the leak, a bigger pool only delays exhaustion under sustained streaming; #1 is the actual fix, #2 is warranted regardless for multi-run scale.
  3. **Optional hardening:** consider a NullPool/short `pool_recycle` only if #1+#2 prove insufficient; not needed once the leak is closed.
- **Verify (fail-before / pass-after — proposed):**
  1. **Fail-before:** open N≥15 concurrent SSE streams (or fewer with reconnect churn) against a Postgres-backed instance; poll `engine.pool.checkedout()` → climbs to 15 and stays (does not fall between streams); a concurrent `POST /api/runs/{id}/answers` 500s with the `QueuePool limit … timed out` TimeoutError. (Matches the live traceback + `/tmp/sse_pool_repro2.py` `checkedout=1` held-until-GC.)
  2. **Pass-after (#1 applied):** same load → `checkedout()` stays near 0 during idle live-drain (only brief spikes during replay reads); the concurrent `submit_answers` returns 200; no TimeoutError. Re-run repro with the session-less store → `after read_events in gen, checkedout=0` (no post-query hold).
  3. **No-regression:** SSE frames + durable replay + D-14g gate re-arm still correct (owner-scoped reads unchanged — same `ScopedStore`, only its session-acquisition mode changes); the two owner checks still 404 cross-owner.

### BUG-007 — One UI launch mints TWO runs (double POST /api/runs)  [🟡 minor] [FIXED ✅]
- **RESOLVED:** FIXED (quick 260716-lb6, c959fe44) — dev-only, offline-proven

- **Found:** 2026-07-16 · test LJ-04 (independently seen in the BUG-005 investigation) · surface prototype LaunchWizard → select design system → "Continue" → the Network panel shows `POST /api/runs` fire **twice**, minting two `od_prototype` runs. BUG-005 measured the pair **120 ms apart** (`created_at` 10:30:45.246 & .368). The extra run wastes tokens and doubles the concurrent-run load that triggers BUG-004/BUG-005.
- **Symptom:** A single "Continue" click → 2× `POST /api/runs` → 2 sibling runs for one launch intent.
- **VERDICT UP FRONT — dev-only React-StrictMode artifact, NOT a production double-mint (verified).** In a production build the launch mints **once**; the second POST appears **only** under `next dev` (React StrictMode's dev-only mount-effect double-invoke). See the dev-vs-real analysis below. Severity **🟡 minor** per the task rubric (a prod build does not double-mint).
- **Root cause (investigation agent — grounded on the live launch/staging source as ground truth + `IMPLEMENTATION-REGISTER.md` prior-art on this exact consumer, lines 2900 / 3168-M4 / 3404; the 797 KB register was not read line-by-line, the code was traced directly):**
  - **The launch has exactly ONE mint path (ruled out a second launch site).** `LaunchWizard.handleLaunch` (`frontend/src/components/workflow/LaunchWizard.tsx:436-483`) only writes `sessionStorage` (draft `:469`, `od_prototype.pending="true"` `:477`) then `router.push("/dashboard")` (`:478`) — **it does not mint.** The sole mint is the staged path: staging effect → `pendingOdProtoParams` state → DashboardLayout consumer effect → `onStartPipeline` → `startPipeline` → `POST /api/runs`.
  - **The actual mint has NO in-flight/idempotency guard.** `useWorkflow.startPipeline` (`frontend/src/hooks/useWorkflow.ts:54-127`) unconditionally calls `runConnection.sendCommand(null, payload)` (`:126`) — `runId=null` ⇒ launch ⇒ `POST /api/runs`. Every call mints; there is no "already launching" latch. So one extra `onStartPipeline` call = one extra run.
  - **The double-fire is in the CONSUMER effect (`frontend/src/components/layout/DashboardLayout.tsx:636-679`, deps `[pendingOdProtoParams]`).** Its ONLY guard is `if (!pendingOdProtoParams) return;` (`:637`); it then "clears" via `onClearPendingOdProto()` (`:642`) = `page.tsx:1554` `() => setPendingOdProtoParams(null)` — an **async parent setState** — and mints at `onStartPipeline("od_prototype", …)` (`:668`). Because the clear is async, it does **not** null the param **between** StrictMode's two *synchronous* mount invocations, so both invocations pass the `!pendingOdProtoParams` guard and both mint.
  - **Why the consumer effect runs on MOUNT with a non-null param (the enabling ordering).** DashboardLayout is gated out of the tree by `page.tsx:1412` `if (!mounted || !isAuthenticated) return null;` — `mounted` flips post-hydration (`:64`/`:72`) and `isAuthenticated` flips only after the **async** auth/profile fetch (`:66`/`:219`). Meanwhile the staging effect (`page.tsx:1004-1072`, deps `[effectiveConnectionStatus]`) is a hook registered *before* that early return, so it runs anyway, and `effectiveConnectionStatus` is **"connected" from the first render** because `phaseToConnectionStatus` maps the provider's initial `idle` phase → `"connected"` (`page.tsx:36-52`; provider initial `phase:"idle"` at `RunConnectionProvider.tsx:108`, mounted in the ROOT `frontend/src/app/layout.tsx:43` so it persists across the wizard→dashboard client nav). Net timeline: connection is connected → staging effect consumes the flag and `setPendingOdProtoParams(objA)` **while the render gate still returns null** → async auth resolves → **DashboardLayout mounts for the first time with `pendingOdProtoParams` already non-null** → its consumer effect fires on MOUNT (not on a dep-change) → StrictMode double-invokes the mount → **2 mints.** (Because idle→connected almost always beats the async auth round-trip, this is the *common* dev case, not a rare race — consistent with it being reproduced live.)
  - **Why the STAGING effect is NOT vulnerable but the consumer IS (the asymmetry).** The staging effect consumes its trigger **synchronously before** the side effect: `pendingOdProtoRef.current = null` + `sessionStorage.removeItem("od_prototype.pending")` + `removeItem("prototype.draft")` (`page.tsx:1039-1041`) run *before* `setPendingOdProtoParams` (`:1053`). Refs and `sessionStorage` persist across StrictMode's mount double-invoke, so the 2nd invocation reads the already-cleared flag and returns at `:1010` — **idempotent.** The consumer effect has no such synchronous consume; it relies on an async parent setState, which is exactly what StrictMode's synchronous re-invoke defeats. That missing synchronous latch is the root defect.
- **Dev-StrictMode-vs-real (the critical distinction, verified):**
  - **StrictMode IS enabled here, by default.** `frontend/next.config.ts` omits `reactStrictMode`; installed Next 16.2.4 resolves that to ON for the App Router: `node_modules/next/dist/build/define-env.js:144` — `'process.env.__NEXT_STRICT_MODE_APP': config.reactStrictMode === null ? true : config.reactStrictMode`, consumed at `node_modules/next/dist/client/app-index.js:217` — `StrictModeIfEnabled = process.env.__NEXT_STRICT_MODE_APP ? React.StrictMode : React.Fragment`. So the tree is wrapped in `<React.StrictMode>`.
  - **StrictMode's extra setup→cleanup→setup of effects is DEV-ONLY.** In a React **production** build `<React.StrictMode>` is an inert passthrough (no mount double-invoke). The Docker/standalone deploy runs a prod build — `frontend/Dockerfile` builds `.next/standalone` and runs `CMD ["node","server.js"]` with `ENV NODE_ENV=production` (compose `frontend` service uses this image) — so it **cannot** double-invoke.
  - **In production the launch mints exactly once (verified by mechanism, no StrictMode path):** (1) the staging effect is `sessionStorage`-idempotent (consume-before-set), so `pendingOdProtoParams` is set at most once per staged launch even if `effectiveConnectionStatus` re-fires the effect; (2) the consumer effect fires once per committed param value — mint once, then `onClearPendingOdProto` nulls it and the re-fire returns at `:637`. No non-StrictMode double-mint path exists (handleLaunch doesn't mint; the `connectionStatus==="connected"` branch at `:667` is if/else with the `pendingStartOnConnectRef` queue, never both).
  - **Therefore:** the two POSTs are the **StrictMode dev double-invoke of the consumer mount effect** — a `next dev` artifact.
