## 1. Goal

Chat becomes a **first-class lane on every workflow run** — the left column (~390px) of the redesigned run screen — in three modes: **pre-run composer** (refine brief conversationally), **mid-run steering** (interact with the running workflow), **post-run iteration** (conversational revisions in the same transcript). Plus: image upload (vision input), file/context upload (workspace + launch context, sticky for all subsequent agent calls), chat-history **compaction**, and the **run-screen redesign** to the Hexaware Run design (chat lane + Preview/Steps/Files/Audit tabs, drill-down Steps), followed by **shell convergence** (all remaining pages).

**Core constraint (inherited, non-negotiable):** zero kernel edits beyond one generic name-free seam; everything lands as registered capabilities + app-layer wiring (SC-001/INV-1); deepagents-only (INV-13); additive migrations only (Q3); the 5 characterization goldens stay byte/event-identical (INV-3); import-linter 4/0.

## 2. Locked architecture decisions

- **D-01 Transport & persistence.** *(REWRITTEN 2026-07-07 evening — full transport cutover locked, see D-13.)* Chat turns enter as **REST commands** — `POST /api/runs/{id}/messages` (`text`, `attachments[]`, client `message_id` idempotency) — and persist as `run_events` rows (new event types `chat_message`, `chat_reply`) through the single stamping boundary → seq ordering, `event_id` idempotent replay, owner+workspace default-deny. All server→client traffic (chunks, thinking, cards, gates) rides the **per-run SSE stream** `GET /api/runs/{id}/events/stream` (`id:` = `seq`; browser-native `Last-Event-ID` resume; `stream_attached {live, replayed_through_seq}` handshake replaces `pipeline_reconnected`); REST reopen (`GET /api/runs/{id}/events`) unchanged. **Zero new tables in v1.** Legacy `user_message`/`ChatRunner` free-chat is PORTED to a POST+stream shim in the cutover (golden drives ChatRunner directly, untouched); retirement stays ND-3.
- **D-02 Family-anchored chat.** The transcript spans the **run family**, not a single run. Each turn persists on the run active at that moment; the FE stitches the thread across parent/child runs via `GET /api/runs/{id}/family` (P25). Revisions announce in-lane ("v2 created — open in Preview →"); the version timeline stays authoritative.
- **D-03 Interaction model — one conversation with the run, three delivery classes.** (a) **Immediate** when paused (clarify answers, gate approve/reject/redo) — resolves the pause; (b) **next-dispatch steering** while agents run — honest UX: "queued — applies at the next step" (mid-generation injection is impossible: an agent invocation runs to completion); (c) **revision turn** when terminal → child run in the family. No per-agent DMs — agents are short-lived workers; the run is the durable counterpart.
- **D-04 Mechanical router first, Concierge as escalation.** A server-side app-layer router keys on run state: clarify_waiting → `set_questionnaire_responses`; gate_paused → `approve_review` with **four** actions: approve / reject / redo+instructions / **`update_specs`** (the KAN-101 spec-revision loop, shipped 2026-07-07 — an analyze-gate action that re-runs specify→plan→analyze in-run and loops back to the same gate; the router ROUTES to it, never re-builds spec revision as a steering note or child run); running → steering note; terminal → `run_revision`. Zero model calls for routable turns. Free-form turns escalate to the Concierge (D-05). Router facts (post-merge): gates are **event-driven, not manifest-driven** — a declared gate may not fire when `gate_agent_ids` excludes the agent (KAN-94); `approve_review` on a terminal run is fenced with the `pipeline_not_running` error (KAN-100), so gate actions must be hidden post-terminal.
- **D-05 Orchestrator = ONE implementation, per-run instances, per-workflow declaration.** A single `chat:concierge` registered capability (deepagents via the sanctioned `deep_agent_runner`, Haiku default, prompt-cached). Each run gets its own *instance* whose workflow-specificity comes from **context** (compiled manifest, artifacts, events, conversation) — never per-workflow code. Tools: **read** (run events/artifacts/steps via `ScopedStore`, owner-scoped) + **proposal-only** (`propose_steering_note`, `propose_revision`, `propose_gate_action` — whose action set includes `update_specs` alongside approve/reject/redo) — the app layer executes proposals through the same channels as the router, consequential ones behind a confirm chip. The Concierge proposes; the engine disposes. Optional per-workflow customization = declared manifest data (e.g. `chat:` key: suggestions, concierge notes), compiled as data (INV-5).
- **D-06 Steering seam (generalized Redo).** New consume-once `ectx.steering_notes` queue; `_compose_context_message` renders pending notes as a `=== USER GUIDANCE ===` block (the `redo_directive` idiom). **Sticky vs one-shot:** uploaded context persists for all subsequent dispatches; directives are consume-once. *(Amended 2026-07-07:)* the engine now carries **two shipped** consume-once injection seams — `redo_directive` (P23) and KAN-101's `spec_revision_context`/`spec_revision_pending_output` — so `steering_notes` is the THIRD of the family. Phase 29 must decide unify-vs-coexist (ND-11) instead of adding a parallel fourth path, and must reconcile the **thread-id divergence**: Redo forks fresh `:redo{N}` checkpoint threads while the KAN-101 sub-pipeline re-runs agents on their BASE threads (an unaudited replay risk the sibling comment at the redo site warns about).
- **D-07 Uploads.** *(Amended 2026-07-07 — the image half LANDED same-day via `IMAGE-INPUT-PLAN.md` waves `edw`/`frv`/`gvq`, offline-proven for `prototype`.)* **As-built image path:** images are **payload-transient** — FE picker (base64, preview chips) → `run_pipeline` `images` → WS validation (mime allow-list, ~3.75 MB/image, ≤20, ~8 MB aggregate, vision-model guard, `IMAGE_INPUT_ENABLED`) → `ectx.run_images` → `HumanMessage` content blocks. Images deliberately **never touch the sandbox, DB, or `run_events`** (out-of-band guarantee) — the POR's original "Images → RunSandbox" wording was wrong; consequence: **images do not survive reopen/replay/resume** (ND-10). **Remaining D-07 scope (documents + files):** `POST /api/runs/{id}/files` (multipart, two-layer owner check → 404) persisting bytes to `RunSandbox`; document text-extraction into sticky context **and** raw bytes into the sandbox for agent `read_file`; new `context_provider:uploaded_files` capability; client-side image resize; per-turn image carrier (rides the Phase 29 `chat_message` path).
