### 3. Capabilities, Modules, Schema & API Added

**BE (additive, parity-neutral) — the ENTIRE backend change (`20-SPEC.md §4`):**
- `WorkflowManifest` gains 5 **inert discovery-metadata** fields (`backend/agents/workflows/manifest.py`): `user_launchable` (bool, default `False`) + `display_name`/`description`/`icon`/`launch_surface` (`str | None`, default `None`). Plus two validators: `_optional_bool` (bool-accept-only) and `_optional_str`. The 5 keys added to `_ALLOWED_TOP_KEYS`.
- Surfaced through the **EXISTING authenticated `GET /api/workflows`** (`backend/app/api/workflows.py`): 4 fields added to `WorkflowSummary`; `list_workflows` enumerates generically over `PIPELINE_AGENTS`, additively reads the manifest, and populates them with a `display_name or _display_name(id)` fallback. The endpoint stays **DB-free** (module docstring: "this router issues no DB query at all") and **off the golden path**.
- 7 launchable manifests flagged in **data** (the `user_launchable` YAMLs): `app_builder`, `user_stories`, `custom`, `mulesoft_to_springboot`, `dotnet_to_azure` (plain-run) + `prototype`, `ppt` (also `launch_surface: "wizard"`). Everything else (revisions, `od_*`, `reverse_engineer`, `chat`, `sample_*`) stays unflagged → `user_launchable=False` → excluded by gate 1 **without any name-based filter**.

**FE (generic, reuse-pure, SC-001):**

- Tests: `WorkflowCatalog.test.tsx` (vitest two-gate filter + friendly-label fallback) and `frontend/e2e/tests/ts-z.catalog.spec.ts` (mocked Playwright; per-spec `page.route('**/api/workflows*')` reverse-registered to win over the fixtures' `**/api/**` catch-all — no fixture edit).

### 5. Key Decisions & Locked Constraints (do NOT contradict)

- **SC-001 — launchability keys on a DECLARED flag, never a name list (LOCKED).** Gate 1 (`user_launchable`) is a declared manifest flag enumerated generically over `PIPELINE_AGENTS`; gate 2 is the pre-existing `canRunPipeline` tier check. The `CreationHub` `WORKFLOWS` const is genuinely **absent** from the catalog (`20-REVIEW.md` Summary, `20-VERIFICATION.md` Truth 1). **A brand-new manifest setting `user_launchable: true` joins the catalog with ZERO FE/BE edit.** To add a workflow to the catalog: set the manifest flag — do NOT add a hardcoded name. REJECTED hack (do not reintroduce): a hardcoded type dropdown (ships broken template-gated buttons + exposes test fixtures — the exact reason ISS-015 was WONTFIX'd, `ISSUES-REGISTER.md` line 59).
- **Additive-only — NO new tables/migrations in P20 (LOCKED).** Manifests are version-controlled `workflow.yaml` data; the endpoint is DB-free. Persistence of *user-authored* workflows is **Phase 21**, not here (Q5: file-backed manifests now, DB-backed user workflows later).
- **INV-3 — 5 characterization goldens byte-identical (LOCKED).** `prototype` / `od_prototype` (alias) / `prototype_revision` / `od_ppt` / `app_builder`. The 5 new fields default `False`/`None` and are **never read by the compiler/kernel** (the compiler reads only `steps/context_providers/deliverable/planner/clarify/seed_files/allowed_workers/limits`) → `CompiledWorkflow` byte-identical, run/event path untouched. Same inert posture as the shipped `model`/`limits` forward fields (D-06). The plan RAN the goldens (no `SNAPSHOT_UPDATE`) to prove identity, not rewrite baselines.
- **INV-5 — strict-key still rejects `when/if/for/expr` (LOCKED).** `_ALLOWED_TOP_KEYS` widened ONLY with the 5 non-control-flow presentation/visibility keys; the strict-key rejection test is preserved unchanged → no DSL. Do NOT add control-flow keys to the allow-list.
- **Ports & Adapters — `lint-imports` 4 kept / 0 broken (LOCKED).** `manifest.py` is pure-data (gains no import); `workflows.py`'s new `_WORKFLOWS_DIR` import from `agents.execution_engine.engine` is a permitted `app → agents` edge. No source→forbidden edge created.
- **Reuse-bound UI — net-new styling is a defect (LOCKED, `20-UI-SPEC.md §0`).** The catalog introduces NO new visual language; every pixel inherits a reused component's Tailwind classes. NO raw API `name` rendered; NO `od_*`/`*_revision`/`sample_*` rows visible; in-dashboard view (not a Next route).
- **Two gates ANDed (LOCKED).** A row shows iff `user_launchable` (product workflow) AND `can_run_pipeline(tier, type)` (this user). Gated-but-launchable rows render the lock/upgrade affordance (shown-locked, NOT hidden — discoverable upgrade path). Tiers are **basic/pro/enterprise** (no `admin`).
- **Launchability is discovery metadata, NOT authorization (LOCKED, threat T-20-02).** `user_launchable` does NOT authorize a run — launch still crosses the server-side `can_run_pipeline` gate in the existing `run_pipeline` WS path. A client forging `user_launchable=true` cannot launch a workflow its tier forbids. The catalog is **not a new trust boundary**.
- **`prototype`/`ppt` route to the wizard, never a bare run (LOCKED).** They require template + design-system (the wizard `canContinue` gate); the catalog only does the `router.push` to `/workflow/{type}/templates`. `custom` seeds zero agents → lands on the idea page needing AgentsPopup assembly first (disabled-Run state, not an error).
