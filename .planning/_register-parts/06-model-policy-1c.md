### 1. Goal & Success Criteria (what was PLANNED)
A `ModelResolver` carried on `ExecutionContext` resolves the effective model per agent invocation by fixed precedence (user per-agent override > `step.model` > AGENT.md agent default > `workflow.model` > run default = session `model_id` else global Haiku), drives `build_model` through a `ModelPolicy` (id + `cost_class` metadata + ordered `fallback`), switches to the next chain model on a sustained throttle, and persists the per-run `model_overrides` map — with no-override runs resolving to today's Haiku/session outcome unchanged (→ 06-SPEC.md "Goal"). Backend-only; the `GET /api/capabilities` endpoint + frontend picker are Phase 8, `cost_class`→BudgetManager enforcement is Phase 11, manifests authoring `step.model` is Phase 7 (→ 06-SPEC.md "Boundaries"). Ambiguity score 0.138 ≤ 0.20 (→ 06-SPEC.md "Ambiguity Report"). 13 falsifiable acceptance checks (→ 06-SPEC.md "Acceptance Criteria"). **Depends-on:** Phase 4 (the inert `ModelPolicy`/`Step.model`/`CompiledWorkflow.model` fields + name-only registry pattern D-07) and Phase 5 (the per-run-helper-on-ctx pattern `scoped_store`, `ScopedStore.record_capabilities`, the reserved `run_capabilities.model_overrides` column) (→ 06-CONTEXT.md "Canonical References").

### 7. Gotchas, Survivors & Carry-Forward
- **`_resolve_model` resolver-or-fallback helper (live survivor):** direct unit-style `_run_agent`/`_run_build_task_loop` invocations build an `ExecutionContext` WITHOUT going through `execute()`, so `model_resolver is None`. `_resolve_model` returns the threaded `model_id` in that case (parity-safe). Do NOT assume the resolver is always present in `_run_agent` (→ 06-03-SUMMARY.md "Deviations from Plan"). The resolver-absent path runs exactly one attempt — no fallback (→ 06-05-SUMMARY.md key-decisions).
- **Chain must be armed on the resolved id STRING, not `ctx.model`:** 06-05 captures `_resolved_model_id` BEFORE `create_runner` (because `create_runner` may replace `ctx.model` with a model OBJECT); arming on the object yields an empty chain. A future change to the fallback loop must preserve this ordering (→ 06-05-SUMMARY.md "Deviations" #1).
- **Chain exhaustion does NOT raise out of `_run_agent`** — the last throttle escapes into the engine's existing recoverable `agent_error` path (visible WS event, no silent blank), matching the engine's fault-degradation contract. The "no live Bedrock / re-raise" wording in earlier plan text means "surfaced, not swallowed", not "raised exception" (→ 06-05-SUMMARY.md "Deviations" #2 + key-decisions).
- **CR-02 live-checkpointer fallback restart — deferred item now CLOSED.** The `{base}:retry{n}` fresh-thread fix was proven offline (InMemory, 4/4); live confirmation against a Postgres checkpointer + Bedrock throttle was deferred, then **`06-UAT.md` status flipped to `complete` — closed by the 2026-06-12 milestone-end live re-pass**. The item is also carried in **Phase 22's consolidated LIVE-01 sweep** (re-confirm consolidated to the milestone-end live pass) (→ 06-UAT.md frontmatter; Phase 22 §6 / 22-LIVE-01-EVIDENCE.md). No outstanding item remains for the phase.
- **Pre-existing environmental test failures (NOT this phase):** ~7–9 failures in `tests/unit/test_logout.py` (HTTP 403 "Self-registration is disabled") and `tests/unit/test_pipeline_cancel.py` (expired AWS SSO token / `ExpiredTokenException`) recur across all 5 plans.
