Fix the four backend Concierge defects (M1/M2/M3/H1) and the dead proposal-drain so the
`chat:concierge` capability is offline-correct against the `POST /api/runs/{id}/messages`
contract — before any live transport flip (A.0: SSE stays OFF this plan). Today the

forge a consequential action. This is the backend half of A.1 (the CRUX); the FE half is 43-02.

existing channels behind confirm chips).

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| FE client → POST /messages (confirm_proposal) | Untrusted client body; a caller may forge/replay any channel+params |
| run content (events/artifacts) → Concierge model | Untrusted run text can carry prompt-injection instructions |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-43-01-H1 | Elevation / Tampering | post_message confirm branch | mitigate | Dispose ONLY from the durable owner-scoped `concierge-proposal:{message_id}:{channel}` pending row; client body locates, never supplies, params; missing/cross-owner/non-pending → 404 |
| T-43-01-IDOR | Information disclosure | confirm-row lookup | mitigate | Row read goes through ScopedStore default-deny (owner+workspace); cross-owner resolves to nothing → 404, never 403 or existence-leak |
| T-43-01-M1 | Elevation | gate-action default | mitigate | Missing action degrades to request_changes (non-consequential), never approve |
| T-43-01-INJ | Tampering | Concierge system prompt / read tools | accept | Read tools remain proposal-only + owner-scoped; injected instructions can at most produce a HELD proposal (confirm-gated). Existing untrusted-content preamble retained |
| T-43-01-SC | Tampering | package installs | accept | No new packages introduced this plan |
</threat_model>
