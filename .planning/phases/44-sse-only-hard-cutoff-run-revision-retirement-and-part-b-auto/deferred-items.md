### DEF-44-12-1 — 🔴 LIVE-FOUND (44-12 smoke) — run-chat send misroutes to launch on a HISTORY-OPENED run
- **Symptom (live, real browser + Bedrock, 2026-07-16):** open a completed run from history/recents → the run-lane composer is shown → ask the Concierge ("What is the current status of this run?"). The turn renders optimistically but the send goes to **`POST /api/runs`** (launch) with a chat body `{text, attachments, message_id, concierge}` → **422** (LaunchCommand wants `pipeline_type`/`message`). No `POST /{id}/messages`, no reply.
- **Root cause:** `useRunChat({ runId: pipelineState.pipelineRunId ?? activePipelineRunId })` (`dashboard/page.tsx:~934`) — both fields track the LIVE pipeline, so they are **null for a history-opened run**. `RunConnectionProvider.sendCommand(null, payload)` then routes `runId===null → POST /api/runs` (the launch branch). The SSE/REST cutover EXPOSED this: the deleted WS up-channel was connection-scoped (the socket carried the run context, no run_id needed in the frame); the REST up-channel needs the run_id in the URL path.
- **Verified NOT a backend regression:** `POST /api/runs/{id}/messages {..,message_id,concierge:true}` → **200, channel:concierge, grounded reply** (curl, this session). The backend Concierge is correct; the bug is the FE run_id binding.
- **Likely pre-existing binding (Phase 31 `useRunChat.runId`), newly REACHABLE post-cutover.** Fix: bind `useRunChat.runId` (and the steering/revision sends) to the **currently-viewed** run id when a run is opened from history (a third state field, not just the live-pipeline ids), OR hide/disable the composer on a history-opened terminal run if chat-on-history is out of scope. Affects Concierge + steering + revision equally on opened runs.
- **Owner:** 44-12 live pass finding → a SRC follow-up (run-chat state binding). Not a transport/cutover defect — the SSE-only transport itself is proven live (0 `/ws/chat` connections; SSE stream unconditional).

### DEF-44-12-2 — 🟠 LIVE-FOUND — Concierge reply on a TERMINAL/history-opened run persists but doesn't PUSH to the transcript
- **Symptom:** after the DEF-44-12-1 send-fix, the Concierge turn on a completed/history-opened run POSTs correctly and the backend persists the grounded `chat_reply`, but the UI transcript does NOT render it (only the optimistic question shows).
- **Root cause:** a TERMINAL run has no live `_PIPELINE_QUEUES` entry, so `run_stream.py` attaches durable-replay only (no live tail). `useRunChat` is subscribe-based (SSE down-channel), so an out-of-band `chat_reply` persisted AFTER attach never pushes; it only appears on a fresh durable replay (reload/reattach).
- **Scope:** affects the Concierge on history-opened terminal runs. The PRIMARY case — a LIVE run you're watching — has a live queue, so the push should work (verified in the 44-12 live-run smoke). Fix options for the terminal case: re-fetch the run's recent events after a `POST /{id}/messages` that returns `reply:true`, OR attach a bounded SSE reader for the viewed terminal run. SRC follow-up.
