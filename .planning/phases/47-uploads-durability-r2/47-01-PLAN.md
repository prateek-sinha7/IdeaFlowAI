<objective>
Close the `.uploads/` disk-only durability hole (POR Gap G / Q6). Today `POST /api/runs/{id}/files` writes uploaded documents' raw bytes + extracted-text sidecars + `manifest.json` under the sandbox `.uploads/` prefix — DISK ONLY — and the `uploaded_files` context provider re-reads them from disk on every dispatch, silently degrading to `{}` when a fresh sandbox (crash / TTL / environment loss) has none. A resumed run loses all uploaded-document context and Postgres cannot restore it.

This plan adds:
- RESUME-12 (Task 1): the upload endpoint dual-writes each document's EXTRACTED TEXT + the rewritten manifest durably as immutable `artifact_refs` rows under a NEW additive kind `upload_text`, owner+workspace-scoped, best-effort, via the endpoint's already-owner-checked Layer-2 `ScopedStore`.
- RESUME-13 (Task 2): the kernel-pure `uploaded_files` provider falls back to that durable mirror (via `ctx.scoped_store`) when the sandbox `.uploads/` manifest is missing, producing a BYTE-EQUIVALENT context block — sticky semantics fully restored on a wiped sandbox.

Purpose: any interruption that loses the sandbox (crash / TTL / fresh worker) keeps a resumed run's uploaded-document context in every subsequent `agent_input`, agent-agnostically, with zero engine edits.
Output: `upload_text` durable mirror at ingest + provider durable fallback; both suites extended (never weakened); goldens dormant/byte-identical.

Fences honored (LOCKED — CONTEXT/RESEARCH):
- Raw PDF/DOCX bytes stay sandbox-only — ONLY extracted text + manifest go durable (honestly documented).
- Images stay payload-transient (ND-10) — the 415 rejection is byte-unchanged; ZERO image storage anywhere.
- Caps byte-unchanged (per-file 10MB / count ≤20 / aggregate 40MB / ext allow-list / image 415) — all validated BEFORE any write (disk OR durable); a rejection writes nothing anywhere.
- The `.uploads/` re-materialization fence + `_FILE_KINDS` exclusion in `engine.py:6023-6031` are ALREADY SHIPPED (comment literally reads "Phase-47 fence"). This plan CONFIRMS they hold — it MUST NOT re-add or modify them, and MUST NOT re-materialize uploads to disk (the provider reads durably).
- ZERO engine edits (SC-001); `extract_upload_text` stays the single extraction impl (INV-12); `run_files._read_manifest` and `uploaded_files._read_manifest` stay DELIBERATELY separate across the app/kernel boundary (IN-02) — do NOT unify or import one into the other.
</objective>
