<objective>
Cluster E (CR-05, CR-07) — the core-value SC-001 findings. Today `task_loop.py`
(:185,188,243,316-317) + `kernel_services.py` (:265,273) + `engine.py` (:1988) hardcode
`"prototype.html"` (13×) and the step ids `"prototype-plan"`/`"prototype-specify"`;

`previous_run` ignores the declared `compiled.seed_files`, using the constant
`_SEED_FILES = ("spec.md","design.md","tasks.md")`; `task_loop._write_reference_files` has the
identical hardcoded twin. The result: a `task_loop` workflow producing `app.py` gets empty
dual-writes, skipped validation, and a fix prompt naming `prototype.html` — so SC-001 fails
for every task_loop workflow except prototype.

`run_validation_fix_loop` + `engine._run_validation_fix_loop` (NO prototype default); (2) add a
declared `TaskSource.source_step` for the plan/spec source steps; (3) plumb `compiled.seed_files`
into `previous_run.load()` + the task_loop writer (declared list, `_SEED_FILES` fallback —
CR-07/INV-5); (4) add the SC-001 proof: a brand-new NON-prototype `task_loop` fixture
(manifest + AGENT.md only) running end-to-end with its own deliverable name and validation/fix
on that name — ZERO engine edits.

Purpose: the phase's owed core-value proof. The kernel/capabilities must be workflow-agnostic
in NAME, not just dispatch — prototype filenames in the "generic" capabilities are the
contradiction the deep review surfaced (07-REVIEW-DEEP.md systemic[1]).

non-prototype task_loop SC-001 fixture; 5-pipeline parity preserved.
