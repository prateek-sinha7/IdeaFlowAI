<objective>
Complete RESUME-17 with the clarify twin — the asymmetric sibling of the review re-entry — and lock the whole v3.0 restart tier at its delta floor with a dormancy + regression sweep.

This plan implements ROADMAP Phase 49 SC-4 (clarify re-arm; questions replayed from the durable event; answers via the unchanged `POST /answers`) and the INV-3 dormancy proof for SC-5. It fleshes out 49-01's `_rearm_gate_run` questionnaire path.

Purpose: A clarify gate is pre-dispatch — a resumed run SKIPS planner AND clarify (engine.py:1708), so it CANNOT route through the review offset override. It needs a dedicated replay driver that recreates the questionnaire waiter without re-generating the answered round via the LLM.
Output: the clarify replay driver, the clarify-twin test (the KAN-88 twin), the goldens/banned/lint/sse dormancy sweep, and the full at-risk battery held at baseline.

PINNED DECISION A5 (clarify re-entry seam, MEDIUM risk): use a THIN REPLAY DRIVER, NOT a re-entry of `ClarifyEngine.run`. Rationale (verified): `ClarifyEngine.run` (clarify_engine.py:244-331) calls `_generate_questions` at the TOP of every round (:247) — re-entering it would RE-GENERATE the open round's questions via the LLM, violating "replay from the durable payload, no model re-run". The asymmetry (engine.py:1695/1708): a resumed run (`_resume_from > 0`) skips planner+clarify; a clarify-parked run has NO produced steps → `_first_incomplete_step` = 0 → `_resuming = False` → a naive `resume_run` would re-run the planner AND LLM-regenerate the questions. So the driver: (1) reads the durable `questionnaire_ready` payload's `questions` + `round` from `run_events`; (2) `get_resume_event(run)` → `clear` → re-emit `questionnaire_ready` (the EXISTING type, engine-counter seq) → `await event.wait()` — a pure REPLAY, no `_generate_questions`; (3) answers ride the UNCHANGED `POST /{id}/answers` (`set_questionnaire_responses` sets the same `_resume_events[run]` event, store.py:80); (4) on submit, the run converges into the standard post-clarify dispatch by merging the answers via the EXISTING `ClarifyEngine._merge_answers`/`_persist_qa` helpers (INV-12 — reuse, no second questionnaire machine) and driving the pipeline from planning with clarify satisfied for the replayed round. Multi-round semantics (`clarify.rounds`): the driver replays the OPEN round only; if the answered round leaves `missing_information`, the subsequent round's `_generate_questions` is the SAME LLM call a live run would make (acceptable — it is NOT a re-run of an already-answered round). Status stays `waiting_for_user` throughout (the KAN-88 twin assertion). The clarify-twin test pins this observable contract; the exact merge-and-proceed wiring reuses the clarify_engine helpers named above.
</objective>
