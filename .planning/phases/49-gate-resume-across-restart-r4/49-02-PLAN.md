<objective>
Make the review gate SURVIVE a restart by re-entering `_run_agent`'s run+gate loop AT its gate phase — reconstructing the gated output from the durable `artifact_refs` with ZERO model call, re-emitting `review_gate_ready`, re-arming the store event, and falling into the SHIPPED five-action consumer so approve/reject/edit/redo/update_specs all work identically post-restart.

This plan implements ROADMAP Phase 49 SC-3 (review re-entry at the gate phase; all five actions; fresh `:redo{N}` threads; update_specs sub-pipeline). It builds on 49-01's `_rearm_gate_run` driver and shared `derive_open_gate`.

Purpose: The crux is the CLASSIFIER, not the wait — a produced-but-ungated step classifies "complete" at the produced-disjunct and gets skipped; the override makes the open gate the resume point. Re-entry then clones the shipped `pending_revision_output` short-circuit exactly, so the entire five-action consumer comes for free.
Output: the offset override, the `gate_reentry` sentinel + skip-model re-entry, the redo/update_specs continuation seeding, the A2 audit row, and the five-actions + redo-numbering + D-14g-compatibility tests.

PINNED DECISION A2 (spec-revision durable count): the inline `_gate_update_specs` consumer (engine.py:3918-3988) writes NO audit row today (only `_gate_redo` does, at :3901-3916), so a post-restart `spec_revision_attempt` has no direct durable count. FIX: add a 1-line best-effort `record_gate_event(spec.id, "human", "update_specs", {"has_report": bool(analysis_report)})` in the inline `_gate_update_specs` consumer RIGHT AFTER `spec_revision_attempt += 1` (engine.py:3927), mirroring the redo audit at :3901-3916 EXACTLY (same `getattr(ectx,"runner")` guard, same `try/except` "audit never aborts a run", same dormant-on-goldens property — update_specs never fires on the 5 characterization runs). This makes the spec-revision count symmetric with redo and derivable post-restart. Then seed BOTH counters fail-safe HIGH: `redo_attempt = max(gate_events_redo_count, artifact_version_count - 1)` and `spec_revision_attempt = max(gate_events_update_specs_count, spec_kind_version_count)`. Rationale: the FAILURE MODE to avoid is REUSING a `:redo{N}`/revision thread id (collision = the P23 checkpointer-replay bug where the model "remembers" its rejected output). Over-estimating N is always safe (a fresh unused thread id); under-estimating collides. MAX of both durable signals guarantees the next id is strictly greater than any pre-restart id.
</objective>
