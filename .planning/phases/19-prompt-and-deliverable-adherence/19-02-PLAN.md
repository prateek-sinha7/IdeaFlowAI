<objective>
Close ISS-005 (`app-infra-generator` ignored its own `/api/v1` rule live) with a DETERMINISTIC backstop. The `/api/v1` standard lives only as prose in 3 AGENT.md bodies — zero code enforcement. Add a pure-stdlib `api_prefix` `Validator` capability (modeled verbatim on `spec_plan_coverage.py`) and wire it as an EVENT-FREE `post_step` on the app_builder infra-generator step, so it flags infra endpoints lacking `/api/v1` and writes a `validation_results` audit row WITHOUT adding any event to the run.

Purpose: a prompt is a flaky enforcement mechanism; a registered, declared validator is deterministic. The INV-3-CRITICAL decision is event-free post_step (NOT a `gates:[validation]` gate — the validation gate emits a `validation_warning` event → the 85-event app_builder golden has no such event → breaks parity). Prove both directions: event-free passes; gate-wired fails.
Output: a new validator module + a post_step shim module + their registry entries + the manifest wiring + a unit/fault-injection test.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| run sandbox files → validator | The validator reads infra files written into the per-run sandbox by the live model. Untrusted file content + file PATHS cross here (path-traversal surface). |
| validator → validation_results DB | The validator writes an owner/workspace-scoped audit row via the runner handle. |
| post_step → run event stream | The post_step MUST NOT emit events; emitting one would corrupt the deterministic stream the golden pins (INV-3). |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-19-02-01 | Tampering | api_prefix.py sandbox file globbing | mitigate | Glob/read ONLY within the run sandbox root via the sandbox's own root/path_for (mirror spec_plan_coverage's confinement); a path that escapes the run dir is never read; a read failure degrades to [] (never crashes, never leaks other runs' files). |
| T-19-02-02 | Denial of Service | api_prefix.py regex over infra files | mitigate | Linear single-pass regex (no nested quantifiers / catastrophic backtracking — mirror the existing validators' regex discipline); bounded to the small set of infra files in one run sandbox. |
| T-19-02-03 | Information Disclosure | validation_results row content | accept | The row carries the run's own (owner_id, workspace_id) via the ScopedStore (AUTHZ-01 / T-08-04-ID, already enforced by record_validation_result); the issue message names only the run's own infra paths. |
| T-19-02-04 | Tampering | post_step event-freeness (INV-3) | mitigate | The post_step emits NO events (side-effects only, mirror revision_validation); proven by the app_builder golden staying byte/event-identical AND the gate-wiring fault-injection showing the alternative FAILS. |
| T-19-02-05 | Elevation of Privilege | new capability registration | mitigate | The validator is `user_allowed=True` (read-only audit, like spec_plan_coverage); the post_step is internal wiring (not user-composable on the infra step beyond the allow-list). No exec/network/secrets/spawn flags touched. |
| T-19-SC | Tampering | npm/pip/cargo installs | accept | No package installs (pure-stdlib validator + a shim module + manifest/registry/test edits). |
</threat_model>
