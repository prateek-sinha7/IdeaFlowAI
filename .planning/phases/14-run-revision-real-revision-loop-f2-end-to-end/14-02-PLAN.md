<objective>
Move the WS `run_revision` branch off the inline `await _rev_engine._handle_revision(...)`
(websocket.py:946) onto the proven background-task + per-run-queue + drainer pattern the
`run_pipeline` path already uses, and make the revision run's terminal status follow the
actual terminal event instead of an unconditional `"completed"` flip.

Why now: the inline await was fine for the instant Phase-3 stub, but once 14-03 dispatches
real model runs (~minutes), the socket's receive loop would freeze — no cancel, no ping,
no reconnect (RESEARCH Pitfall 3, Open Q1 resolved: adopt the queue pattern). And the
unconditional `status = "completed"` (websocket.py:956-964) would record a `pipeline_failed`
dispatch as a clean success — which the FE revision-of-revision lookup
(`r.status === "completed"`, DashboardLayout.tsx:382) would then offer as a revision parent
(RESEARCH Pitfall 4).

This plan is STUB-COMPATIBLE and independent of 14-03 (Wave 1, parallel): the current stub
emits `pipeline_complete` through the same send-fn seam, so behavior with the stub is
unchanged except the fixes (status fidelity, agent_count, non-blocking receive loop). The
new handler test drives a recording stub engine — no scripted models needed.

Purpose: ROADMAP Phase 14 success criterion 1 (live cancel/reconnect viability for the
milestone-end pass) + the Pitfall-4 half of criterion 2.
Output: extracted `_handle_revision_execution` coroutine + handler-level regression suite.
</objective>
