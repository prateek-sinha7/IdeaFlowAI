<objective>
Close CR-01 and CR-02 — the two durable-resume/replay BLOCKERS that make RESUME-03
("reconnect = durable replay from run_events via after=<last_seq>") dead on arrival in
production.

- CR-01: `resume_run` (engine.py:4029-4046) seeds its event seq counter with
  `itertools.count(1)`, identical to a fresh run. The pre-restart run already persisted
  run_events with seq 1..N (plus the `run_resuming` marker at N+1 that `_stamp_resume_marker`
  carefully computed as max(seq)+1). Every resumed event then re-uses seq 1, 2, 3…, colliding
  silently (run_events has no unique constraint on (run_id, seq)). A reconnecting client that
  sends `after_seq=N` (its last pre-crash seq — exactly what the FE `lastSeqRef` sends) never
  receives ANY resumed event because they all carry seq ≤ N.
- CR-02: the WS reconnect replay branch (websocket.py:607) constructs
  `ScopedStore(owner_id=user.id)` with `workspace_id=None`. `read_events` applies
  `_scope_owner_ws` which predicates `RunEvent.workspace_id == self._workspace_id` — i.e.
  `workspace_id IS NULL`. Every production run_events row is stamped with the run's real
  non-null workspace_id by the engine sink, so the replay query matches ZERO rows for every
  real run.

Purpose: make the durable WS replay tail actually visible to a reconnecting client after a
restart — without either defect, RESUME-03 returns nothing in production.

Output: a seq-seeding fix in resume_run; a workspace_id-recovery fix in the WS replay branch;
two new tests that fail on the pre-fix code paths (production-shaped ScopedStore with no
explicit workspace_id; resumed seq continuity past the durable tail).
</objective>
