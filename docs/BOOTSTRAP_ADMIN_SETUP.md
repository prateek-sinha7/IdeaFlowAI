# Initial administrator bootstrap

How a freshly deployed environment gets its first administrator without anyone
logging into the VM.

## The problem this solves

Self-registration is disabled — `/api/auth/register` always returns 403 — and
the only other user-creation path, `POST /api/admin/users`, requires an already
authenticated administrator. A brand-new environment therefore has no way in.

The old answer was to open a shell on the host and seed a user by hand, which
does not work when nobody is permitted onto production hosts.

## The rule

```
users table has zero rows  ->  create exactly one administrator
users table has any row    ->  do nothing, successfully
```

"Any row", not "no administrator exists". That is deliberate:

- an existing user is never modified, promoted, or re-hashed;
- a database that has users but no administrator is **not** backfilled — that is
  a recovery scenario, not something an unattended deploy step should do;
- deleting the last administrator does not silently re-open bootstrap.

The created account is `tier = enterprise`, `is_admin = true`, with the password
bcrypt-hashed through the application's own `hash_password`. No migration is
needed: every column already exists on the `users` model.

## How it runs

Three components, in order:

1. **`.github/workflows/deploy.yml`** writes the credentials to SSM Parameter
   Store under `/velocityai/<env>/bootstrap/` — the email as a `String`, the
   password as a KMS-encrypted `SecureString`. Both use the existing `put_param`
   helper with `delete-if-empty` semantics, so clearing the value in GitHub
   removes the parameter rather than leaving a stale one behind.
2. **`.github/scripts/remote-deploy.sh` §12** runs after the health gate and
   asks the container whether bootstrap is needed. Only if the answer is yes does
   it fetch the credentials.
3. **`backend/app/scripts/bootstrap_admin.py`** does the work inside the backend
   container, taking a PostgreSQL table lock before it looks at the table.

Ordering matters: migrations run in the container entrypoint
(`alembic upgrade head`), and §12 sits after the health gate so we never
bootstrap into a stack that is about to be rolled back.

### Why two phases

The check needs no secret. On every redeploy — the overwhelmingly common case —
the password is never decrypted, never leaves SSM, and never reaches the host.

### How the password travels

```
GitHub Environment secret
  -> step env: (never echoed, never in $GITHUB_OUTPUT)
  -> SSM SecureString, encrypted with the environment's CMK
  -> aws ssm get-parameter --with-decryption
  -> pipe
  -> container stdin
  -> bcrypt hash
```

It is never an argv element (visible in `ps`), never an environment variable
(visible in `docker inspect`, inherited by subprocesses), never a temp file,
never a Terraform value, and never in the SSM RunCommand payload. It is not
assigned to a shell variable on the host at any point.

The host secrets loader (`velocityai-load-secrets`, generated by
`infra/scripts/bootstrap-ec2.sh` §12) has an explicit `bootstrap/*` skip branch,
so these parameters never reach `/etc/velocityai/app.env` or the long-running
container environment.

## Setup

For each environment (`dev`, `stage`, `prod`), under **Settings → Environments**:

| Kind | Name | Value |
|---|---|---|
| Variable | `BOOTSTRAP_ADMIN_EMAIL` | the operator address, e.g. `admin@example.com` |
| Secret | `BOOTSTRAP_ADMIN_PASSWORD` | 24–32 random characters, minimum 16 |

Notes:

- Use a **different** password per environment.
- Save the plaintext in your password manager first — GitHub will not show it
  again.
- Require reviewers on the `prod` environment.
- Do not expose these to pull-request workflows.

The existing IAM grants already cover this: the deploy role has
`ssm:PutParameter` on `/velocityai/<env>/*`, and the instance role has
`ssm:GetParameter` plus `kms:Decrypt` scoped through
`kms:ViaService = ssm.<region>.amazonaws.com`. No IAM change is required.

Then deploy as usual (push to `dev`/`staging`, or tag `v*` for prod).

## What you will see in the deploy log

First deploy into an empty database:

```
[deploy] checking whether an initial administrator is needed...
[deploy] users table is empty — bootstrapping the initial administrator
[deploy] initial administrator will be: admin@example.com
[deploy] streaming the bootstrap password from SSM (never logged)...
[bootstrap-admin] initial administrator created: admin@example.com
[deploy] initial administrator ready — change this password after first login
```

Every later deploy:

```
[deploy] checking whether an initial administrator is needed...
[deploy] users table already initialised — no bootstrap needed
```

## After first login

Change the password through the existing `POST /api/auth/change-password`
endpoint. That stamps `password_changed_at`, which blanket-revokes every JWT
issued before the rotation.

Once you have confirmed access, delete `BOOTSTRAP_ADMIN_PASSWORD` from the
GitHub Environment if you do not want to retain it. The next deploy will clear
the SSM parameter (`delete-if-empty`) and will not need it, because the database
is no longer empty.

## Command reference

```bash
# Is bootstrap needed?  0 = no, 10 = yes, 1 = could not tell
python -m app.scripts.bootstrap_admin --check-only

# Create it. 0 = created or already initialised, 1 = error
printf '%s' "$PASSWORD" | python -m app.scripts.bootstrap_admin \
    --email admin@example.com --password-stdin
```

`10` is deliberately distinct from `1`: the deploy script has to tell "the
database is empty, go fetch credentials" apart from "something broke".

The password must be at least 16 characters — stricter than the 8-character
floor on `/api/admin/users`, because this one is machine-generated, stored in a
secret manager, and typed by a human at most once.

`--check-only` cannot be combined with `--email`/`--password-stdin`; silently
ignoring credentials would hide a scripting mistake that leaves an environment
un-bootstrapped.

## Failure behaviour

| Situation | Result |
|---|---|
| Empty database, valid credentials | one admin created, deploy succeeds |
| Any user already exists | no-op, deploy succeeds, password never fetched |
| Empty database, password parameter missing | no user created, **deploy fails** |
| Empty database, email parameter missing | no user created, **deploy fails** |
| Password shorter than 16 characters | no user created, **deploy fails** |
| Database unreachable / migrations incomplete | **deploy fails** |
| Two callers race | one inserts, the other observes the row and no-ops |
| Crash before commit | transaction rolls back, next deploy retries |
| Users exist but none is an admin | no-op — use a break-glass procedure |

A bootstrap failure fails the deploy but does **not** roll back the images. The
stack is healthy, and no earlier image can log anyone in either, so reverting
would fix nothing.

## Tests

```bash
cd backend
uv run pytest tests/unit/test_bootstrap_admin.py          # 48 tests, no server needed
```

The unit suite uses a private in-memory SQLite database per test with the
session factory injected into the command, following the pattern in
`tests/unit/test_logout.py`. It covers the exit-code contract, idempotency,
validation, rollback, lock ordering, secret hygiene (the password must not appear
in stdout, stderr, or logs), and the CLI surface.

Two things SQLite cannot model — the real `LOCK TABLE ... IN SHARE ROW
EXCLUSIVE MODE` statement and genuine cross-connection contention — live in an
**opt-in** PostgreSQL suite:

```bash
createdb bootstrap_admin_test
BOOTSTRAP_ADMIN_TEST_DATABASE_URL=postgresql://user:pass@localhost:5432/bootstrap_admin_test \
    uv run pytest tests/integration/test_bootstrap_admin_postgres.py -v
```

It skips when that variable is unset, so the default `uv run pytest` and CI
(which has no PostgreSQL service) stay green. It creates and drops tables, so it
refuses to run unless the URL is supplied explicitly, differs from the
application's `DATABASE_URL`, and names a database containing `test`. Point it at
a scratch database; never relax those guards.

Beyond the unit and PostgreSQL suites, the shell and workflow changes were
checked with `bash -n` on both scripts and a YAML parse of the workflow.
`ruff`, `pyright` and `vulture` are clean on the new module. The
pre-existing `lint-imports` failure (`agents.capabilities -> app`) and the
`vulture` findings in `app/api/chat_router.py` are unrelated to this change.

## Design notes

**Why a table lock.** `COUNT` followed by `INSERT` is a race: two callers can
both observe an empty table. `SHARE ROW EXCLUSIVE` conflicts with itself *and*
with the plain `INSERT` locks taken by `/api/admin/users`, so it serialises
against the API too. A PostgreSQL advisory lock would only coordinate with
callers that agreed to take the same advisory lock, which the API does not. The
unique index on `users.email` protects one address, not the global "no user
existed" invariant.

**Why the lock is dialect-gated.** Production is always PostgreSQL. The gate
exists so the check-then-insert logic can be exercised on in-memory SQLite in
the unit suite; a unit test asserts that the PostgreSQL branch still emits the
exact `LOCK TABLE` statement, so a regression that drops it fails without
needing a server.

**Why the credentials are not in `app.env`.** Putting the password there would
place it in the long-running container's environment — readable via
`docker inspect`, inherited by every subprocess — for the whole life of the
deployment, to serve a step that runs at most once.

**Why not a `/setup-admin` endpoint.** An unauthenticated, network-exposed
account-creation route is a race between you and whoever finds it first.

## Possible follow-ups

Not implemented, listed so the gaps are explicit:

- **Forced rotation at first login.** The app supports changing a password and
  revoking prior tokens, but nothing forces it. That needs a `must_change_password`
  column plus a frontend redirect.
- **Break-glass recovery** for a lost administrator, as an audited command
  separate from bootstrap.
- **SSO / OIDC**, which would remove the initial password entirely.
