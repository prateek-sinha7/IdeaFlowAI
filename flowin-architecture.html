Flowin — the Universal AI Workflow Runtime

Flowin (backend product name VelocityAI / historically IdeaFlowAI) is a full-stack, multi-agent AI platform. It sequences fleets of LLM agents to turn a plain-language brief into real deliverables — product backlogs, executive slide decks, navigable HTML prototypes, complete applications, and code-modernization plans — all driven by declarative workflow manifests rather than hardcoded pipelines.

The one idea that explains everything: SC-001

✓ SC-001 — the kernel knows no workflow by name

A brand-new custom workflow can replicate the entire prototype pipeline using a manifest + AGENT.md files only, with zero edits to the engine. Every behavior that used to be hardwired for a specific pipeline — the per-task build loop, validation and fix-loops, context injection, deliverable resolution, clarify defaults — is now a declared, registered capability any workflow can opt into. This invariant is proven by tests and enforced by CI.

If you remember one thing about this codebase, remember that. The execution engine is a small, generic sequencer. It reads a compiled plan and runs steps. It never contains a branch like if pipeline_type == "ppt". All the "what makes PPT different from a prototype" lives in data (YAML manifests + Markdown agent prompts) and in plug-in capability classes that self-register by name.

Architecture

Flowin is a Ports & Adapters (hexagonal) system. A small workflow-agnostic kernel depends only on capability ports (Python Protocols); concrete implementations self-register and are resolved by name. The web layer calls into the kernel; the kernel never reaches back up. Boundaries are enforced mechanically by import-linter contracts in CI.

The invariants (the rules every change must respect)

INV-1

Kernel is name-free

Zero if pipeline_type == … or spec.id == … branches in the kernel. Routing is by declared capability name only. Guarded by a banned-pattern CI grep.

INV-2

No per-run state on the singleton

The engine is a process-wide singleton and is stateless after __init__. All per-run data lives on a fresh ExecutionContext threaded explicitly through the call tree.

INV-3

Behavioral parity

Existing pipelines stay semantically event-parity and byte-identical where deterministic — locked by 5 characterization "golden" snapshot tests that must never be re-baselined.

INV-5

Compiler is thin, no DSL

Manifests are pure data. Any control-flow key (when/if/for/${…}) is rejected by strict-key validation. Control flow lives inside strategy capabilities.

INV-12

Move, don't copy

Adding an abstraction without deleting the code it supersedes is "not done". Deletion is an exit gate, ratcheted by a migration ledger with commit SHAs.

INV-13

deepagents only

Every agent runs on LangChain deepagents==0.6.7. create_deep_agent is called only inside the allow-listed deep_agent_runner.py. Enforced by a banned-pattern gate.

Enforced import boundaries

These import-linter contracts live in backend/pyproject.toml and run as lint-imports (steady state: 4/0 passing). They make an accidental inward dependency a CI failure, not a code-review catch.

agents.execution_engine.engine   ↛  app.api            # kernel must not import the web layer
agents.workflows                 ↛  agents.execution_engine, app   # declaration layer is inner
agents.capabilities              ↛  agents.execution_engine, app   # capability ports are inner
agents.runtime                   ↛  agents.execution_engine, app   # runtime port is inner (ECS-swap seam)
🧭 Why hexagonal here?

Because the product's whole thesis is "add a workflow without touching the engine". Ports & Adapters is the structural guarantee of that promise: the kernel depends on abstractions (ports), and new behavior arrives as adapters that plug into the registry. The agents.runtime contract even reserves the seam for a future ECS/remote runtime as a backend swap rather than an engine rewrite.

Data Flow — one run, end to end

This is the life of a single workflow run, from a user clicking "Generate" to a deliverable streaming back into the browser. Use the controls to step through; each step highlights and expands. The path is identical for every pipeline — the differences are all in the compiled plan.

Step 1 / 12
1
Browser sends run_pipeline WebSocket
useWorkflow.startPipeline() serializes { type:"run_pipeline", pipeline_type, message, agent_ids?, attached_skills?, attached_hooks?, model_overrides?, gate_agent_ids?, template_id? } and sends it through the socket opened by useWebSocket (JWT carried in the bearer.<jwt> subprotocol).
2
FastAPI WS handler authenticates & validates app/api/websocket.py
Re-validates the JWT (catches mid-session logout/revocation), rejects overlapping runs, allow-list-validates model_overrides against the ModelCatalog, re-checks persisted per-step selections with trust="user", creates the WorkflowRun row, and kicks a background task with a per-run event queue.
3
Engine compiles the workflow compile_for_run()
resolve_alias(pipeline_type) → load_manifest() reads agents/workflows/<id>/workflow.yaml → WorkflowCompiler.compile() name-resolves every capability against the CapabilityRegistry, topo-validates the Step DAG, and returns a typed CompiledWorkflow. Result is lru_cached.
4
Per-run ExecutionContext constructed context.py
One instance per run holds run_id, owner_id, the typed ArtifactGraph, workspace_id, the ScopedStore, ModelResolver, BudgetManager, checkpointer, cancel event, and the compiled deliverable spec. Nothing per-run touches the engine singleton (INV-2).
5
DAG validation + Deep-Planner resolver.py
WorkflowResolver validates the typed produces/consumes DAG. Then the deep-planner agent runs (120s timeout, defaults to PROCEED) inferring intent and deciding whether clarification is required.
6
Optional clarify gate (HITL) ClarifyEngine
If clarify.mode: auto (the default for most workflows), the engine emits a questionnaire and pauses, awaiting a submit_questionnaire message. Durable via the checkpointer, so it survives a reconnect. Capped at ~5 questions per round.
7
Topo-loop over Steps engine.execute()
For each compiled Step the engine resolves the step's strategy capability (single_shot, task_loop, fanout_batch, wave_scheduler) and hands control to it. Review gates (gate: human) can pause between steps.
8
Agent runner built & streamed factory.create_runner()
create_runner() loads the AGENT.md spec, composes the system prompt (injects → guardrails → skills → hooks → constitution → body), resolves tools, builds a DeepAgentRunner over a deepagents graph, and astream_events() maps LangGraph events → engine events.
9
Model call build_model()
build_model() selects ChatAnthropic (local, ANTHROPIC_API_KEY) or ChatBedrockConverse (prod). Model is user-selectable per agent (Haiku 4.5 default). Native filesystem tools write into the shared per-run RunSandbox on disk.
10
Validation & fix-loop (declared) validators + post_step
Steps that declare validators run them (e.g. prototype build runs html_static + html_render in a headless Chromium) with a bounded internal fix-loop. _select_issues_to_fix() chooses regressions vs. baseline. Hooks (audit_logger, secret_scan) fire around writes.
11
Deliverable resolved DeliverableResolver
At run end the declared deliverable strategy (single_file, serialized_sandbox, streamed_text, ppt, repo_diff) reads the sandbox and produces the final artifact + a declared mimetype. Persisted to Postgres with lineage.
12
Events + deliverable stream back WS → React
Throughout, the engine emits WS events (agent_chunk, tool_call, task_progress, validator_result, pipeline_complete…). handlePipelineMessage reduces them into PipelineRunState. PreviewPanel dispatches on the deliverable mimetype (HTML→iframe, md→markdown, zip→bundle). Events are also persisted to run_events for durable replay on reconnect.
🔁 Reconnect & resume

Runs can take hours. If the socket drops, useWebSocket reconnects with exponential backoff (no retry cap) and re-sends reconnect_pipeline; the server replays the durable run_events tail. If the backend restarts mid-run, restore_non_terminal_runs() on startup re-registers waiting runs and resumes them (mid-wave resume is supported). The ExecutionContext.is_resuming flag drives this.

Two entry paths

Pipeline path (the above)

run_pipeline → ExecutionEngine. Deterministic, manifest-driven, multi-agent. This is the primary product surface.

Free-chat path

user_message → ChatRunner (app/agents/chat_runner.py). A separate conversational subsystem (Discovery → Requirements → …) with its own 7-agent internal "chat" pipeline. Not driven by the kernel.

Execution Kernel — agents/execution_engine/

The kernel is the deterministic sequencer that replaced the legacy WorkflowOrchestrator.execute(), run_od_prototype_pipeline, and run_od_ppt_pipeline. It decides which agent runs next by reading the compiled plan; the LLM never decides sequencing. It is workflow-agnostic by construction (INV-1).

The compile-for-run seam

This is the single point where a run label becomes an executable plan. Note there is no legacy pipeline_type dispatch fallback (INV-12) — a dispatchable run always sources its agent list from the compiled plan.

@functools.lru_cache(maxsize=None)
def compile_for_run(pipeline_type: str) -> CompiledWorkflow:
    manifest_id = resolve_alias(pipeline_type)        # od_prototype -> prototype; else itself
    manifest    = load_manifest(manifest_id, _WORKFLOWS_DIR)   # reads workflow.yaml
    return _WORKFLOW_COMPILER.compile(manifest, _CAPABILITY_REGISTRY)   # -> typed CompiledWorkflow

The ExecutionContext (per-run state)

A plain, mutable @dataclass — one per execute() call. It is the reason concurrent and fan-out runs never clobber each other. Selected fields:

Identity & ownership

run_id, owner_id (persisted principal, anon:<session> if unauthenticated), disk_principal (decoupled sandbox key), workspace_id, depth.

Typed substrate

artifacts: ArtifactGraph (the sole inter-agent handoff), scoped_store (owner+workspace-scoped DB), model_resolver, model_overrides, budget.

Run wiring

checkpointer, deliverable (compiled spec), current_step, seed_files, cancel_event, prewarmed_constitution, prewarmed_mcp_tools.

Loop scratch

completed_tasks, current_task_block, build_task_number/total, failed_invocations, revision baselines, is_revision_workflow, is_resuming.

Notable kernel machinery

_ChunkStreamSanitizer — strips fabricated tool XML from the live stream

Live Haiku sometimes fabricates Claude-internal tool syntax (<function_calls>/<invoke>) as plain text when a tool-less agent's prompt implies actions. Because the engine yields each raw chunk as agent_chunk before accumulation, this per-stream buffer routes each chunk through the runner's sanitize_output and holds an unterminated opener across chunk boundaries so a span split across two deltas is still stripped. It is an identity no-op for tool-using agents (gated on the runner capability, never a workflow name — SC-001).

_RunEventSink — durable event persistence (PERSIST-03)

Every stamped event (with seq + event_id) is appended to the run_events table so a reconnecting client can replay the tail. The write is best-effort for the DB case only: a SQLAlchemyError (e.g. offline harness) degrades to a warning so the live stream is never perturbed; any other exception propagates as a real bug.

_select_issues_to_fix — pure validation fix-loop selection

A pure function over a StaticCheckResult + RenderResult that produces the ordered, de-duplicated fix list. On a build (empty baseline) it selects all issues; on a revision (populated baseline) only new static issues + new console errors, while hard render-breakage (uncaught page errors, dead nav links) is always included. Both the loop and its tests import the same normalization.

Client-facing error sanitization

_sanitize_agent_error() returns a fixed generic message ("The model rejected this request.") on the client-facing agent_error event, keeping raw provider text (ARNs, region, model-id) server-side only. This makes a secret leak structurally impossible on the wire.

Strategies — how a step actually runs

The engine delegates each step to its declared ExecutionStrategy capability. This is where per-workflow control flow lives (never in the compiler):

StrategyBehavior
single_shotRun the agent once over the composed context message. The default for most steps.
task_loopParse a task list (via a task_parser) and launch one isolated sub-agent per task, injecting a === CURRENT TASK === block. Used by the prototype build step; runs validators + a bounded fix-loop after each task.
fanout_batchSpawn N workers in parallel (or a heterogeneous named-worker set) with per-worker isolated sandboxes, then merge. Bounded by the BudgetManager.
wave_schedulerTopo-schedule tasks into parallel "waves", persist wave_runs, and support mid-wave durable resume.

Manifests & Compiler — agents/workflows/

This is the declaration layer: how a workflow is described (a YAML manifest) becomes how it is executed (a typed, validated plan). It imports only stdlib + itself + the capability registry — never the kernel or the web layer.

manifest.py

load_manifest(id, base_dir) reads <id>/workflow.yaml with yaml.safe_load only (no !!python/object RCE surface) into a typed WorkflowManifest dataclass. Not Pydantic. Strict-key rejection: only keys in _ALLOWED_TOP_KEYS are permitted — a DSL/control-flow key has nowhere to live.

compiler.py

WorkflowCompiler.compile() does exactly two things: (1) name-resolve every capability reference against the CapabilityRegistry (unknown name = CompilerError naming it), and (2) map each raw step → a typed Step and topo-validate the DAG (cycle-free, no dup agents).

plan.py

The typed contract the kernel executes: CompiledWorkflow, Step, ToolPermissions, ModelPolicy, TaskSource, FixPolicy, FanoutSpec, RetryPolicy, RepoSpec, Limits, DeliverableSpec, ClarifySpec, Task.

Anatomy of a compiled Step

Each raw step dict is mapped to a typed Step with a strict key allow-list. Consumed fields today: agent_id, strategy, gates, hooks, task_source, validators, compaction, post_step, tools, model, fanout, on_conflict, retry, injects, depends_on.

Trust model & secure defaults

The compiler takes a trust level. file/builtin manifests (engineer-authored, version-controlled) are trusted; user/db manifests (from the composer / saved workflows) are untrusted and additionally checked against each capability's user_allowed flag.

Untrusted manifests can't escalate

A user/db manifest referencing a non-user-allowed capability (exec, secrets, spawn_subagents, powerful runtimes) is a CompilerError naming the (kind, name). Budget Limits may only be lowered, never raised above the default ceiling.

exec requires gates

A step granting tools.exec must declare both the security and approval gates, or the compile fails. The compiler raises — it never auto-injects the gates.

Least privilege by default

Effective tool permissions = owner ∩ workflow_ceiling ∩ step_grant (an AND-mask that can only lower). Ungranted steps keep read_files on, everything else off.

Default audit hooks (KAN-73)

A step that declares no hooks: automatically gets audit_logger + secret_scan injected, so every agent execution produces an audit trail and is security-scanned by default.

Catalog metadata (Phase 20)

Manifests carry inert presentation fields the data-driven Workflow Catalog reads via GET /api/workflows — never a hardcoded list (SC-001): user_launchable, display_name, description, icon, launch_surface. The compiler/kernel never read these, so goldens stay byte-identical.

Capabilities — the plug-in catalog

Every unit of workflow behavior is a capability: a small class that satisfies a Protocol port and self-registers via @register(kind, name, user_allowed=…, description=…). The kernel resolves them by name; manifests reference them by name. Adding one is "add a module + register" — no kernel edit. Below is the live _KNOWN registry set, grouped by kind. 🧩 The registry contract

_KNOWN is the compiler's membership set (validated at compile time with zero impls bound). discover() explicitly imports the impl modules (no auto-walk) so each @register fires. CapabilityRegistry.resolve(kind,name) is a static dict lookup — no dynamic name resolution, no eval. The user_allowed flag is the trust gate that keeps exec/secrets/spawn_subagents off the user palette.

Agents & Runtime

An agent is a folder with an AGENT.md file: YAML frontmatter (identity + metadata) plus a Markdown system-prompt body. There are ~80 of them in agents/prompts/. The runtime is how an agent becomes a running LangChain deepagents graph.

The AGENT.md schema

The loader (agents/loader.py) parses each AGENT.md into a validated AgentSpec (cached). Key frontmatter fields:

Prompt composition (factory._compose_system_prompt)

A single fixed injection order, assembled by the registered PromptAssemblyPolicy ("default"):

tool_availability  →  injects  →  guardrails  →  skills  →  hooks  →  constitution  →  prompt_body
   (anti-fab)         (od only)   (files)       (UI)     (UI)     (per-user)     (AGENT.md)

Guardrails

9 version-controlled rule files in agents/guardrails/: agile, typescript, react, accessibility, html-prototype, openapi, java-spring, mulesoft, dotnet. Injected verbatim under ## Guardrail: {name}.

Skills

User-attached capability docs, per-session, passed in AgentContext.attached_skills (from the UI). Versioned via the ui skill provider.

Hooks

User-attached behavioral guideline blocks (## Active Behavioral Hooks). Distinct from executable lifecycle hooks (audit_logger etc.).

The runner (create_runner → DeepAgentRunner)

create_runner(agent_id, ctx) is the live entry point the engine calls for every agent. It loads the spec, composes the prompt, resolves tools via the tool_provider registry, builds the per-run sandbox, and constructs a DeepAgentRunner that wraps a deepagents.create_deep_agent graph. astream_events() maps the LangGraph event stream onto the WS event vocabulary the frontend already consumes.

Sandbox vs. checkpoint thread

The on-disk RunSandbox is keyed on run_id only and shared across a run's agents, so a file one agent writes persists for the next. The LangGraph checkpoint thread_id is per agent-invocation (f"{run_id}:{agent_id}", plus :task in the build loop) so agents never collide on one checkpoint.

Model selection (build_model)

Picks ChatAnthropic (local, ANTHROPIC_API_KEY) or ChatBedrockConverse (prod, IAM or bearer-token). User-selectable per agent (Haiku 4.5 default). Botocore read-timeout + adaptive retries live in one place.

Tool filtering

The library sub-agent dispatch tool (task) is always excluded so the model can't spawn its own sub-agents — the engine orchestrates fan-out itself. Enforced by a per-graph _ToolFilterMiddleware.

Recursion backstop

No per-agent iteration cap; AGENT_RECURSION_LIMIT = 400 (LangGraph recursion_limit) is the only runaway-loop guard. Library auto-summarization replaced the old cross-agent summarizer.

Prototype build: per-task sub-agents + Both-validation

The prototype-build step doesn't run once. The engine writes spec.md/design.md/tasks.md into the sandbox, then launches one isolated sub-agent per task. After each task it runs Both-validation — static_check (stdlib: routes↔sections, handlers, is-active) + render_check (headless Chromium: nav switches, no console errors) — with a bounded internal fix-loop (N=2). Revision runs the same validation as a smart-hybrid policy seeded from the parent run.

The two hooks that run everything

useWebSocket.ts

Owns the socket lifecycle. Connects with subprotocols [bearer.<jwt>, flowin.v1] (JWT off the URL, out of logs); server echoes flowin.v1. Exponential-backoff reconnect capped at 30s with no retry limit (runs can last hours); 20s client ping to survive idle proxies; a 4001 close clears the token and redirects to login; filters heartbeats/pongs.

Infrastructure & Deployment

Flowin deploys as a single-EC2 stack on AWS (branded velocityai in infra): the backend + frontend run as Docker Compose containers pulled from ECR, while Postgres and nginx run natively on the host. Everything is Terraform-managed in a layered reference format, applied by per-environment CodeBuild runners.

Runtime topology (one EC2 instance)

🌐 Internet → nginx (host, native)
TLS terminator. Certs at /etc/letsencrypt/live/<fqdn>, renewed by the host's certbot timer — outside the app image rebuild cycle. Proxies to the two loopback-bound containers.
▼
🐳 frontend container
Next.js standalone, 127.0.0.1:3000, 1G limit. NEXT_PUBLIC_API_URL/WS_URL baked at build. Waits for backend health.
🐳 backend container
FastAPI/uvicorn, 127.0.0.1:8000, 8G limit. Volumes: /app/skills + /app/runs (EBS). 30s stop-grace to drain WS. Headless Chromium + node baked in.
▼  host.docker.internal:5432
🐘 PostgreSQL (host, native)
On a separate encrypted EBS volume at /var/lib/postgresql — that volume is what EBS-snapshot backups capture. Bound to 127.0.0.1:5432. Left native so backups and pg_dump/psql from systemd timers stay simple.
Why Postgres & nginx are not containerized

Postgres stays on the host so its data dir lives on the encrypted EBS volume the backup/DR story depends on (no extra fs/UID/fsync layer). nginx stays native because it consumes Let's Encrypt certs that renew on a different cadence than app-image rebuilds. Clean separation: nginx + Postgres are infrastructure; the app is the deployable.

Security Notes

The platform has strong security defaults in several places and a few items worth flagging. This reflects what is verifiable in the current code.

Strong by default

✓

SECRET_KEY boot guard

config.py raises SecretKeyMisconfigured and refuses to boot if SECRET_KEY is empty, the shipped default, or <32 chars — unless ENV=development. A predictable signing key would let anyone forge JWTs.

✓

JWT off the URL

The WebSocket carries the JWT in the bearer.<jwt> subprotocol, not the query string — keeping it out of nginx logs and Referer headers. Tokens are revocable (logout jti + password-change blanket revocation), re-checked per message.

✓

Least-privilege capabilities

Tool permissions default off (exec/network/secrets/spawn_subagents). exec requires the security+approval gates. User/db manifests can't reference non-user-allowed capabilities or raise budget ceilings.

✓

Safe by construction

Manifests parse with yaml.safe_load only (no !!python/object RCE); capability resolution is a static dict lookup (no eval/dynamic import); client-facing agent_error is sanitized so provider ARNs/region/model-id never reach the browser. Default audit_logger + secret_scan hooks fire on every step.

✓

Ownership everywhere

Runs, artifacts, saved workflows, and review-gate responses are owner-scoped (ScopedStore + per-row owner_id/workspace_id); cross-run writes are IDOR-guarded (unknown/unowned → 404).

✓

Secrets never in code/CI

Terraform generates SECRET_KEY/db_password into SSM SecureStrings (project CMK); the host composes app.env at start. CI scans with gitleaks/checkov/trivy before merge.

Worth flagging

⚠

CORS is hardcoded

app/main.py sets allow_origins=["http://localhost:3000","http://127.0.0.1:3000","http://localhost:3001"] — it does not read the existing settings.CORS_ORIGINS. Fine for local dev; a non-local deployment relying on same-origin nginx is unaffected, but any cross-origin browser client would need this widened (and it should be driven by config, not a literal).

⚠

Deprecated WS ?token=

The WebSocket still accepts a transitional ?token=<jwt> query param alongside the subprotocol path (it logs a deprecation warning on every use). Query-string tokens can land in logs — worth removing once no in-flight clients use it.

Note on scope

These are observations from reading the code, not a security audit. A full assessment would also cover dependency CVEs, rate limiting, the MCP credential flow, and the gated-exec sandbox boundary in depth.

Glossary

SC-001

The core success criterion: a new workflow can replicate prototype by manifest + AGENT.md only, zero engine edits. The kernel knows no workflow by name.

Manifest

A workflow.yaml describing a pipeline: steps, per-step strategy/gates/validators, deliverable, clarify config. Pure data, no control flow.

CompiledWorkflow

The typed, validated plan the kernel executes — output of the WorkflowCompiler. A topo-validated Step DAG plus workflow-level config.

Capability

A self-registering plug-in (@register(kind,name)) satisfying a Protocol port. Strategies, validators, deliverables, gates, hooks, tools, providers.

ExecutionContext

The per-run value object holding all run state (INV-2). One instance per execute(), threaded through the call tree; the engine singleton stays stateless.

AgentSpec / AGENT.md

An agent's identity + system prompt. YAML frontmatter (id, pipeline_type, order, tools, guardrails, gate…) plus a Markdown prompt body.

DeepAgentRunner

The adapter that wraps a LangChain deepagents graph and maps its LangGraph event stream onto Flowin's WS event vocabulary (INV-13).

RunSandbox

A per-run, traversal-proof on-disk directory (<RUNS_ROOT>/<user>/<run>/) shared across a run's agents so files persist agent-to-agent.

HITL gate

Human-in-the-loop pause. A gate: human step (or clarify questionnaire) suspends the run, durable via the checkpointer, resumed by a client message.

Ports & Adapters

The hexagonal architecture: the kernel depends on abstract ports; concrete adapters plug in via the registry. Enforced by import-linter.

Fan-out / Wave

Parallel execution. fanout_batch spawns N isolated workers then merges; wave_scheduler topo-schedules tasks into parallel waves with durable resume.

Deliverable resolver

The capability that produces a run's final artifact from the sandbox: single_file, serialized_sandbox, streamed_text, ppt, repo_diff.
