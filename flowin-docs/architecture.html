Architecture

Flowin is a Ports & Adapters (hexagonal) system. A small workflow-agnostic kernel depends only on capability ports; concrete implementations self-register and are resolved by name. The web layer calls into the kernel; the kernel never reaches back up. The boundaries are enforced mechanically by import-linter in CI.

The invariants

INV-1

Kernel is name-free

Zero if pipeline_type == … branches. Routing is by capability name only. Guarded by a banned-pattern CI grep.

INV-2

No per-run state on the singleton

All run state lives on a fresh ExecutionContext, threaded explicitly. The engine is stateless after init.

INV-3

Behavioral parity

Existing pipelines stay byte-identical where deterministic — locked by 5 characterization golden tests.

INV-5

Compiler is thin, no DSL

Manifests are pure data. Control-flow keys are rejected. Control flow lives in strategy capabilities.

INV-12

Move, don't copy

Adding an abstraction without deleting what it supersedes is "not done". Deletion is a ratcheted exit gate.

INV-13

deepagents only

Every agent runs on deepagents==0.6.7; create_deep_agent is called only in deep_agent_runner.py.

Enforced import boundaries (import-linter, steady state 4/0)

agents.execution_engine.engine   ↵  app.api                          # kernel ↵ web layer
agents.workflows                 ↵  agents.execution_engine, app     # declaration is inner
agents.capabilities              ↵  agents.execution_engine, app     # capability ports are inner
agents.runtime                   ↵  agents.execution_engine, app     # runtime port is inner (ECS-swap seam)
🧭 Why hexagonal here?

The product's thesis is "add a workflow without touching the engine". Ports & Adapters is the structural guarantee: the kernel depends on abstractions; new behavior arrives as adapters that plug into the registry. The agents.runtime contract even reserves the seam for a future ECS/remote runtime as a backend swap, not an engine rewrite.
