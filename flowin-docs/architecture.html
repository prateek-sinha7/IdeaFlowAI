System design

Architecture

Flowin is a Ports & Adapters (hexagonal) system. A small workflow-agnostic kernel depends only on capability ports; concrete implementations self-register and are resolved by name. The web layer calls into the kernel; the kernel never reaches back up. The boundaries are enforced mechanically by import-linter in CI.

In plain terms. The codebase is split into rings, like an onion. A small, stable core in the middle does the orchestrating; everything workflow-specific lives in outer rings that plug into the core. The rule that makes it all work: outer rings may depend on the core, but the core may never depend on them. That one-way rule is what lets someone add a brand-new workflow without ever touching the engine.
What it is

A hexagonal (Ports & Adapters) layering: a generic kernel surrounded by pluggable, self-registering adapters.

Why it exists

The whole product promise — "add a workflow without editing the engine" (SC-001) — is only true if the dependency arrows point one way.

How it works

The kernel depends only on abstract ports; adapters register by name and are resolved at runtime; import-linter fails CI if the direction is ever violated.

The invariants

Not a stylistic wish-list — each one is asserted by a real, CI-run gate (a banned-pattern grep, an import-linter contract, a byte-diff against a golden fixture, or a migration-ledger check). .planning/PROJECT.md is the source of record; this table is a readable index into it.

INV-1

Kernel is name-free

Zero if pipeline_type == … / if spec.id == … branches anywhere in the kernel. Routing is by capability name only. Proven — 16 legacy couplings (L1–L16) were found and deleted from engine.py across Phase 7; a banned-pattern hard-fail CI gate plus a migration-ledger ratchet keep it that way.

INV-2

No per-run state on the singleton

All run state lives on a fresh ExecutionContext dataclass, threaded explicitly as a parameter (never contextvars). The engine singleton holds only its three construction-time collaborators (_resolver/_store/_state_machine) and is stateless after __init__.

INV-3

Behavioral parity

Existing pipelines (prototype, PPT, revisions, code-gen) stay deterministic byte-identical where the run is deterministic, and at semantic-event parity elsewhere — locked by 5 characterization golden tests taken pre-refactor. The lone sanctioned exception: the Phase 3 HTML-skeleton token-trim, an approved non-byte-identical change with its own parity proof.

INV-4

Every reference is validated

A manifest naming an unregistered capability fails compilation with an error naming the bad reference — never a silent no-op or a runtime AttributeError. Enforced by CapabilityRegistry.is_registered, checked by the compiler before anything else.

INV-5

Compiler is thin, no DSL

Manifests are pure data. Strict-key rejection means a control-flow key (when/if/for/${…}) has nowhere to live, at any nesting level. Control flow lives exclusively inside strategy capabilities, never in the manifest.

INV-7

Engine-owned fan-out

Agents never call a raw task-spawning primitive themselves. spawn_subagents is a spawn-free request-emitter tool (user_allowed=False); the kernel's run_fanout is the sole spawn path, enforcing depth/concurrency/budget caps before any child agent starts.

INV-8

Ownership, default-deny

Every run has an explicit owner_id — never None; an unauthenticated run gets anon:<session_id>. Parent-run ownership is explicitly re-checked on revision seeding (a user cannot revise a run they don't own by guessing its id).

INV-9

Least-privilege tools by default

exec/network/secrets/spawn_subagents default OFF for every step. Effective permissions are an AND-mask (owner ∩ workflow_ceiling ∩ step_grant) that can only narrow, never widen. A step granting exec must also declare the security and approval gates or the compile fails outright.

INV-10

Typed, owner-scoped artifacts

Inter-agent handoff flows through one typed ArtifactGraph/ArtifactRef substrate — content-addressed and stamped with owner_id/workspace_id — replacing the untyped dict mirror the original engine used. It is the sole artifact source since the legacy mirror was deleted in Phase 5.

INV-12

Move, don't copy

A phase that adds an abstraction without deleting the code it supersedes is, by definition, "not done". The only ever-sanctioned temporary duplication was the accumulated_outputs mirror during the Phase 5 migration — itself removed on schedule. Deletion is a ratcheted exit gate per phase, not an afterthought.

INV-13

deepagents only

Every agent runs on the real deepagents==0.6.7 package — canonical import from deepagents import create_deep_agent. No hand-rolled deep-agent loop, no local shadow module. create_deep_agent is called from exactly one place: deep_agent_runner.py. A banned-pattern CI gate enforces it.

Enforced import boundaries — the real [tool.importlinter] contracts

Four forbidden-type contracts in backend/pyproject.toml, rooted at ["agents", "app"]. All four hold (exit 0) on the current tree — they are non-vacuous, not aspirational.

root_packages = ["agents", "app"]

[[contracts]]  # 1 — the kernel scaffold: today's monolith must not call back into the web layer
name = "kernel imports only capability ports (scaffold)"
source_modules    = ["agents.execution_engine.engine"]
forbidden_modules = ["app.api"]

[[contracts]]  # 2 — declaration layer is inner
name = "agents.workflows must not import the execution kernel or the web layer"
source_modules    = ["agents.workflows"]
forbidden_modules = ["agents.execution_engine", "app"]

[[contracts]]  # 3 — capability ports are inner
name = "agents.capabilities must not import the execution kernel or the web layer"
source_modules    = ["agents.capabilities"]
forbidden_modules = ["agents.execution_engine", "app"]

[[contracts]]  # 4 — the runtime port reserves the future ECS-swap seam
name = "agents.runtime must not import the execution kernel or the web layer"
source_modules    = ["agents.runtime"]
forbidden_modules = ["agents.execution_engine", "app"]
Why contract #1 is a "scaffold", not the final form

A comment block directly above contract #1 in pyproject.toml explains the compromise: today's "kernel" is still the monolithic agents.execution_engine.engine module — the split into a slim agents.kernel + capabilities/base.py was a later-phase target. Since engine.py transitively reaches almost every agents.* subpackage (engine → factory → nearly everything), a forbidden rule naming any broad agents.* target would already be red on day one. So the scaffold anchors on a boundary that is already true — the kernel never imports app.api — which is real and non-vacuous (verified: engine.py reaches app.agents/app.core/app.models/app.services, but never app.api). The documented intended final form only ever adds a source module and forbidden targets — it's designed to be a diff, never a rewrite.

🧭 Why hexagonal here?

The product's thesis is "add a workflow without touching the engine". Ports & Adapters is the structural guarantee: the kernel depends on abstractions; new behavior arrives as adapters that plug into the registry. The agents.runtime contract even reserves the seam for a future ECS/remote runtime as a backend swap, not an engine rewrite.

Inside the capability registry (agents/capabilities/registry.py)

This module is how the inward-only rule stays true while still being extensible — the registry is the one place adapters and the kernel actually meet, and it does so through four small, deliberately separated maps.

_KNOWN — the membership set

A literal set[tuple[kind, name]] populated at registry-module import, with zero implementations bound. This is the compiler's INV-4 surface: is_registered(kind, name) is a pure set lookup, so a manifest can be validated for unknown capability references with no impl code imported at all — a test (test_registry_capabilities.py) explicitly asserts this.

_IMPLS — the bound instances

A separate dict[(kind,name), object], populated only when discover() runs and each impl module's @register decorator fires. resolve(kind, name) checks _KNOWN first (raises KeyError naming the bad reference before any lookup), then reads _IMPLS — a known-but-unbound name raises RuntimeError telling the caller to call discover().

_TRUST — the user-allowed flag

Per-(kind,name) boolean recorded by @register(..., user_allowed=...). Defaults to False — the safe default that keeps privileged capabilities (exec, secrets, spawn_subagents) off the user-composable palette (CAP-03) unless explicitly opted in.

_META — palette display data

description + config_schema per capability (D-08), the single source of truth the /api/capabilities endpoint projects to the UI palette. There is deliberately no second, static metadata map in app/api/ — that would silently drift from what's actually registered.

discover() is lazy — it fires at engine import / first execute() / first resolve(), never at compiler import — and it is an explicit list of module imports, never a namespace auto-walk. The comments in the source are blunt about why: auto-discovery gives non-deterministic ordering, silently pulls in unintended modules, and the import-linter can't reason about a dynamic import graph. A package that fails to import (missing optional dependency, syntax error) is logged as a warning and skipped rather than aborting all of discovery — one broken adapter degrades gracefully instead of taking the whole registry down.
