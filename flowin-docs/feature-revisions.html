Revisions

"Change this, keep the rest." Every major deliverable can be revised in place: the user's instruction plus the original artifact seed a short revision pipeline that edits the existing output rather than regenerating from scratch.

In plain terms. "Change this, keep the rest." Instead of regenerating a deliverable from scratch when you want a tweak, a short revision pipeline loads the original and edits it in place, guided by your instruction. That keeps the good parts and makes iterating cheap.
What it is

In-place revision of any major deliverable (stories, deck, prototype, app build).

Why it exists

Iterating should be fast and shouldn't throw away work you were happy with.

How it works

Seed the original via the previous_run provider → edit per the instruction → validate against a baseline (only new issues count) → persist with derived_from lineage.

REVISION_BASE_MAP (in agents/registry.py) maps each revision id to its base pipeline.

Seeded from the parent

The original artifact is seeded into the run via the previous_run context provider. The manifest's deliverable.revises_existing = true flag (not a workflow-name check) gates the in-place edit + parent seed — so the four regenerating workflows that also read previous_run aren't misclassified.

Smart-hybrid validation

A prototype revision runs the same Both-validation as a build, but with baselines: only new static/console issues count as regressions, while hard render-breakage is always fixed. This is the _select_issues_to_fix baseline path.

prototype_revision/workflow.yaml, the one revision manifest with the full picture

Of the 5 revision manifests, prototype_revision is the only one that sets revises_existing: true — the others (ppt/user_stories/app_builder/od_ppt revisions) regenerate their whole artifact rather than editing it in place, so they correctly leave the flag false. Its single step is worth reading closely because it wires together three separate mechanisms into one coherent flow:

gates: [validation]

A post-edit validation gate on the revision step — the run pauses only if a critical issue survives, per the default block-critical/warn-non-critical policy.

validators: [html_static, html_render]

The same Both-validation the build loop runs, declared explicitly on this step rather than implied by the strategy.

post_step: revision_validation

After the edit, this capability computes the pre-edit baseline, runs the post-edit Both-validation + bounded fix-loop, and folds the result in — the exact machinery documented on the Execution Kernel page's KernelServices.compute_revision_baseline section.

The manifest's own header comment flags a real historical gotcha worth knowing: clarify.defaults for revisions intentionally falls back to the generic "custom" pipeline defaults (target_audience, key_objectives, scope, priority) rather than the richer prototype defaults — documented in the source as "parity trap #2", a subtlety the original engine's hardcoded dict reproduced and the manifest had to match exactly to hold byte-identical parity (INV-3) during the migration.
