Capabilities

Every unit of workflow behavior is a capability: a small class that satisfies a Protocol port and self-registers via @register(kind, name, user_allowed=…). The kernel resolves them by name; manifests reference them by name. Adding one is "add a module + register" — no kernel edit. Filter and search the live registry below.

In plain terms. Capabilities are the Lego bricks of behavior. Each brick does exactly one small job — "run a step this way", "validate the HTML", "produce the final file", "pause for a human" — and snaps into the engine by name. To teach Flowin something new, you add a brick and register it; you never re-carve the baseplate (the engine).
What it is

Small, self-registering plug-in classes, each implementing one Protocol port (strategy, validator, deliverable, gate, hook, tool, provider…).

Why it exists

So new behavior is "add a module + register it", never an engine edit — the mechanical basis of SC-001.

How it works

A class decorated with @register(kind,name) is discovered at startup; the compiler validates the name; the kernel resolves it by a static dict lookup.

How a capability is resolved at runtime

🧩 The registry contract

_KNOWN is the compiler's membership set (validated at compile time with zero impls bound). discover() explicitly imports the impl modules (no auto-walk) so each @register fires. resolve(kind,name) is a static dict lookup — no dynamic name resolution, no eval. The user_allowed flag keeps exec/secrets/spawn_subagents off the user palette.
