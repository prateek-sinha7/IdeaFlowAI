Reconnect & resume

🔁 Runs can last hours

If the socket drops, useWebSocket reconnects with exponential backoff (no retry cap) and re-sends reconnect_pipeline; the server replays the durable run_events tail from the client's last sequence. If the backend restarts mid-run, restore_non_terminal_runs() on startup re-registers waiting runs and resumes them — including mid-wave. The ExecutionContext.is_resuming flag drives this behavior.

Two entry paths

Pipeline path

run_pipeline → ExecutionEngine. Deterministic, manifest-driven, multi-agent. This is the primary product surface and the flow shown above.

Free-chat path

user_message → ChatRunner (app/agents/chat_runner.py). A separate conversational subsystem (Discovery → Requirements → …) with its own 7-agent internal "chat" pipeline. Not driven by the kernel.
