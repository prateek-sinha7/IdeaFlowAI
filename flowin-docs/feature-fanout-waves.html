Fan-out & Waves

Parallelism, owned by the kernel — never by the model. A step can fan out into N isolated workers that run in parallel and then merge, and a wave scheduler can topo-schedule tasks into parallel "waves" with durable mid-wave resume.

In plain terms. When a step has lots of independent work, Flowin can split it across several workers running at once and then stitch the results back together. The important safety detail: the engine decides to parallelize, never the model — with strict budgets and isolated scratch spaces so workers can't step on each other.
What it is

Kernel-owned fan-out (parallel workers + merge) and a wave scheduler (dependency-ordered parallel batches).

Why it exists

To speed up independent work safely, with budget caps and durable, resumable progress.

How it works

run_fanout reserves budget, spawns isolated workers, then a merge capability combines outputs; waves persist to the DB for mid-wave resume.

A fan-out step, end to end

fanout_batch strategy

Declared via a step's fanout: block (mode, max_parallel, agent/count for self×N, or workers for a heterogeneous set). The kernel's run_fanout owns the spawn control flow; each worker gets an isolated child sandbox so two workers writing the same path can't cross-contaminate before the merge.

wave_scheduler strategy

Parses a structured task list (json_tasks), topo-schedules tasks into waves by dependencies, runs each wave's tasks in parallel, and persists wave_runs. Prototype stays sequential; waves are opt-in per manifest.

Isolation, merge & budget

ConcernMechanism
SpawnThe spawn_subagents tool is engineer-only (user_allowed=false); the kernel emits the spawn, the model never does. The library task tool is always excluded.
IsolationEach worker runs in a _ChildSandbox rooted at its own dir (passed as run_sandbox to create_runner).
MergeA merge capability combines worker outputs: copy_disjoint, git_3way, json, or html_fragment. On conflict, the step's on_conflict policy applies (human_gate / merge_agent / partial / abort).
BudgetThe per-run BudgetManager caps max subagents / depth / wall-clock / tokens; a per-workspace aggregate ceiling guards against a multi-run fork-bomb. reserve() runs before any spawn.
Persistencesubagent_runs + wave_runs tables make fragments durable pre-merge, so a mid-wave resume re-fans-out only the incomplete workers.
📊 Watching it live

The UI's WaveTreePanel renders the wave/worker tree from the additive wave_started/completed/failed + subagent_spawned/result events (statuses only — no live token stream per worker). N parallel workers of the same agent render as N distinct leaves keyed by worker index.

Inside run_fanout — the one spawn path, step by step

fanout.py's own docstring numbers five sequential steps, and both entry points — the declarative fanout_batch strategy and the runtime spawn_subagents tool's structured request — funnel through this exact same function. Nothing else in the codebase spawns a subagent.

1 · Select workers

A named worker must pass two checks — present in allowed_workers AND resolvable in the agent registry — both reached through the runner handle, never a direct import. A disallowed or unknown worker raises FanoutError before anything else happens: zero subagent_runs rows, no workspace allocated.

2 · Reserve budget

budget.reserve() runs before any spawn (Pitfall 4 — enforcement-point discipline). A refused reservation emits a budget_warning event naming the breached dimension, then re-raises — with genuinely zero side effects, since nothing was spawned yet.

3 · Select isolation

The scope is derived solely from the base workspace's has_git flag — never from the manifest. This is a deliberate INV-7 enforcement: a user-authored manifest has no field that could downgrade a worker's isolation, even if it wanted to.

4 · Spawn, bounded

Parallel mode runs under asyncio.Semaphore(min(declared, DEFAULT_MAX_CONCURRENCY)) — the engine enforces its own concurrency ceiling regardless of what the manifest asks for. A manifest requesting 100 parallel workers still runs at most DEFAULT_MAX_CONCURRENCY at a time (a direct DoS mitigation, T-11-01-02).

5 · Persist fragments, then merge

Before any merge runs, every file a worker wrote is persisted as its own lineage-tracked fragment ArtifactRef — so a worker's complete output survives an abort or cancel even if the merge itself never happens. Only after that does the engine resolve a MergeStrategy by name and attempt the merge.

What happens when a worker crashes, or you hit Stop, mid fan-out

One worker failing never aborts its siblings

Inside _run_one, a worker's exception is caught, logged, and turned into a status="failed" result — the other workers keep running. Only a genuinely unexpected non-worker exception (say, a budget boundary raising mid-gather) triggers the harsher cancel-everything path.

Cancellation mirrors that same discipline

A cooperative cancel is checked before the wave starts, between sequential workers, and before the merge. Mid-flight, every outstanding task is cancelled and awaited, each in-flight worker flips its own subagent_runs row to cancelled, and a finally block reclaims every allocated isolated workspace — whether the run finished, crashed, or was cancelled. No leaked worktrees, no orphaned sandbox directories.

One more detail worth knowing if you ever look at a worktree-isolated fan-out's git history: a completed worker's edits are explicitly committed onto its own per-worker branch inside _run_one — without that commit, the subsequent git_3way merge would see nothing to integrate and the worktree teardown would silently destroy the uncommitted work.
