MCP & Integrations

Agents can reach external systems through the Model Context Protocol. An allow-listed catalog of MCP servers plus thin integration-provider bridges surface tools (GitHub / GitLab / Jira / Slack) into an agent's runner via the same prewarm seam — one mechanism, no parallel SDK path.

How MCP tools reach an agent

The catalog (trust-gated)

github
Read-scoped · user-grantable
gitlab
Read-scoped · user-grantable
jira
Read-scoped · user-grantable
slack
Post-scoped · user-grantable
filesystem
Powerful · user_allowed=false
postgres
Powerful · user_allowed=false

The powerful servers (filesystem, postgres) are gated off the user palette. Integration providers (github/gitlab/jira/slack) are thin MCP-backed bridges that surface the matching catalog server's tools.

Prewarm seam

The McpClientAdapter awaits get_tools() once at the async engine run-entry; the resolved tools are stashed on ExecutionContext / AgentContext.prewarmed_mcp_tools. The sync create_runner then unions them into the runner tool set without awaiting inside the running loop.

Credentials

MCP secrets are stored encrypted in the mcp_credential table (field encryption via app/core/crypto.py). They are referenced by key, never logged by value.

🔗 One mechanism

Integrations and raw MCP servers share the same runner-binding path (INV-13: tools augment the deepagents runtime, they never replace it). A granted integrations scope composes an MCP server-config fragment the run-entry hands to the client adapter — no second SDK path.
