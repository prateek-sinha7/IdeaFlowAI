Execution Kernel

The deterministic sequencer that replaced the legacy WorkflowOrchestrator.execute(), run_od_prototype_pipeline, and run_od_ppt_pipeline. It decides which agent runs next by reading the compiled plan — the LLM never decides sequencing. It is workflow-agnostic by construction (INV-1).

In plain terms. The kernel is the conductor of the orchestra, not a musician. It decides which agent plays next and when, but it never plays a note itself — the LLM does the actual work. Crucially, the conductor doesn't know it's conducting "the prototype symphony" or "the PPT symphony"; it just reads the sheet music (the compiled plan) in front of it.
What it is

The workflow-agnostic sequencer that executes a compiled plan, step by step.

Why it exists

Centralizing orchestration deterministically means the model never controls sequencing, so runs are repeatable and testable.

How it works

execute() validates the DAG, runs the planner, threads a per-run context, loops the steps via their strategies, and emits events.

The compile-for-run seam

The single point where a run label becomes an executable plan. There is no legacy pipeline_type dispatch fallback (INV-12).

@functools.lru_cache(maxsize=None)
def compile_for_run(pipeline_type: str) -> CompiledWorkflow:
    manifest_id = resolve_alias(pipeline_type)        # od_prototype -> prototype; else itself
    manifest    = load_manifest(manifest_id, _WORKFLOWS_DIR)
    return _WORKFLOW_COMPILER.compile(manifest, _CAPABILITY_REGISTRY)

The per-run ExecutionContext

A plain mutable dataclass — one per execute() call. It is why concurrent and fan-out runs never clobber each other.

Identity & ownership

run_id, owner_id (anon:<session> if unauthenticated), disk_principal (decoupled sandbox key), workspace_id, depth.

Typed substrate

artifacts: ArtifactGraph (the sole inter-agent handoff), scoped_store, model_resolver, model_overrides, budget.

Run wiring

checkpointer, deliverable, current_step, seed_files, cancel_event, prewarmed_constitution, prewarmed_mcp_tools.

Loop scratch

completed_tasks, current_task_block, build_task_number/total, failed_invocations, revision baselines, is_revision_workflow, is_resuming.

Why a plain mutable dataclass, not frozen or contextvars

The docstring in context.py is explicit about both choices. Not frozen: the prototype build loop appends to completed_tasks and reassigns current_task_block mid-run, and the revision-seeding block populates the revision_* fields after construction — a frozen dataclass would make both illegal. Not contextvars: the context is an explicit parameter threaded through the call tree (D-03) precisely so a fan-out worker's context can never leak into its parent's or a sibling's via ambient/implicit state — explicit is safer than magic here. Every mutable-default field uses field(default_factory=...) so two concurrent runs never accidentally share one list/dict/set instance.

Field provenance: owner_id vs. disk_principal (the byte-identity guard)

Two principals exist on purpose. owner_id is the persisted DB principal — always a real, non-None value (user_id or f"anon:{session_id}" for an unauthenticated run), used for the AUTHZ-01 owner+workspace scope filter on every persisted row. disk_principal stays user_id or "anon" — the exact value the sandbox used for on-disk path keying before the ownership refactor. Decoupling the two let owner_id become the more precise anon:<session_id> for DB scoping without silently moving every anonymous user's sandbox files to a new disk path underneath them. Disk-keying call sites must use disk_principal, never owner_id — enforced by a grep gate in CI.

How the DAG gets validated — WorkflowResolver

Before any agent runs, the compiled step list's produces/consumes graph must be provably satisfiable. This isn't advisory — an unsatisfiable graph halts the run before a single token is generated.

1 · Map every producer

Build artifact_type → [(index, agent_id), …] for every declared produces entry, indexed by declaration order (used later for tie-breaking).

2 · Match every consumer

For each agent's consumes entries, filter producers to only those declared upstream (lower index). planning_context and constitution are exempt — always available, never type-matched.

3 · Tie-break, then topo-sort

Multiple upstream producers of the same type? The latest declared one wins (highest index) — an approximation of "fewest DAG edges". Then Kahn's algorithm produces the final deterministic execution order.

Any unmatched consumes entry becomes an UnresolvedEdge and an error naming the offending agent + artifact type; a dependency cycle is caught by DFS before the topo-sort even runs. Both failure modes return satisfiable=False with the exact reason — never a generic "workflow invalid".

Run lifecycle — StateMachine

Nine valid states, three of them terminal. A transition into a terminal state can never be transitioned out of again — attempting one raises StateMachineError rather than silently no-opping.

In-flight states

planning (Deep-Planner running) → clarifying / waiting_for_user (HITL pause) → analyzing (a Validation_Gate agent) → generating (domain agents) → revising (a revision run).

Terminal states

completed / failed / cancelled. Every transition is persisted before the method returns — so a crash mid-transition leaves the run in the new state, not the old one (the safer failure mode to resume from).

In-memory dict is authoritative for the current process; a best-effort DB write to workflow_runs.status makes the state survive a restart for cross-process resumability (a write failure is logged and swallowed — non-fatal, since the in-memory state is still correct for this process).

Fan-out spend control — BudgetManager

A per-run object (never on the engine singleton — INV-2) enforcing caps on subagents, concurrency, nesting depth, wall-clock time, and tokens. The single kernel run_fanout spawn path calls reserve() before every spawn, so a refused reservation leaves zero side effects — no orphaned subagent_runs row for a spawn that never happened.

A budget_warning event fires once any dimension crosses 80% of its cap (BUDGET_WARN_THRESHOLD = 0.8) via warn_threshold_reached() — so a run approaching its ceiling surfaces a warning in the UI well before it's forced to abort with partial results.

Notable machinery

_ChunkStreamSanitizer — strips fabricated tool XML from the live stream

Live Haiku sometimes fabricates Claude-internal tool syntax (<function_calls>/<invoke>) as plain text. This per-stream buffer routes each chunk through the runner's sanitize_output and holds an unterminated opener across chunk boundaries so a span split across two deltas is still stripped. Identity no-op for tool-using agents (gated on the runner capability, never a workflow name).

_RunEventSink — durable event persistence

Every stamped event (with seq + event_id) is appended to run_events so a reconnecting client can replay the tail. Best-effort for the DB case only (a SQLAlchemyError degrades to a warning so the live stream is never perturbed); any other exception propagates.

_select_issues_to_fix — pure validation fix-loop selection

A pure function over a StaticCheckResult + RenderResult producing the ordered, de-duplicated fix list. On a build (empty baseline) it selects all issues; on a revision (populated baseline) only new static issues + new console errors, while hard render-breakage (uncaught page errors, dead nav links) is always included.

Client-facing error sanitization

_sanitize_agent_error() returns a fixed generic message on the client-facing agent_error event, keeping raw provider text (ARNs, region, model-id) server-side only — a leak is structurally impossible on the wire.

KernelServices — the D-03 handle at ctx.runner

Capabilities are forbidden from importing agents.execution_engine (the import-linter contract). So how does a strategy actually run an agent, or a validator reach a headless browser? Through exactly one object: ctx.runner, a KernelServices instance the engine constructs once per run and attaches to the context. Every capability reaches the kernel dynamically through its attributes — never by importing the module that defines it.

run_agent / run_validation_fix_loop

Delegate to the engine's own _run_agent / _run_validation_fix_loop rather than reimplementing them. The strangler discipline: nothing in KernelServices re-implements a legacy leak — it just gives capabilities a legal door into the existing primitive, so the routed path stays byte/event-identical (INV-3) while the leak's original hardcoded call sites were deleted.

static_check / render_check

The two validators every DeliverableContext.runner can call: pure-stdlib structural checks, and a headless-Chromium render pass. A Validator capability never imports app.agents.render_check itself — it calls target.runner.render_check(path).

The record_* audit writers

record_gate_event, record_validation_result, record_hook_run, record_exec_run, record_subagent_run, record_wave_run — one best-effort writer per audited event kind, all sharing one shape: reach the per-run ScopedStore, catch broadly, log a warning, return None. An audit write must never be the reason a run fails.

Budget + isolation seams

workspace_budget_spent() feeds the per-workspace ceiling check before a fan-out reserve; persist_budget_snapshot() writes the final BudgetSnapshot to workflow_runs.budget_snapshot_json; allocate_isolated_workspace() is how run_fanout reaches the git-owning LocalWorkspace for a worker's sub_sandbox or worktree without importing it directly.

🔒 One rule, everywhere: never abort the run

Look closely at every record_*/persist_* method and they share the identical defensive shape: if store is None: return None, then a broad except Exception that logs a warning and degrades gracefully. Audit, telemetry, and budget bookkeeping are all best-effort by deliberate design — a database hiccup during a 20-minute app-build run must never be the reason the run itself fails.

DeliverableContext — what a Validator actually sees

A small dataclass: name, path, runner (the same KernelServices handle), step, task_meta, and a lazy content property that reads the file from disk only when first accessed — so a validator that only checks the path never pays for an unnecessary read.

FixPolicy — the fix-loop is config, not code

Carries deliverable name, max_attempts (default 2), and block_critical/warn_non_critical flags. The Both-validation fix-loop that used to be hardcoded to prototype.html now runs against whatever deliverable name the manifest's policy declares — run it with deliverable="app.py" and it fixes app.py, with the prototype manifest reproducing the exact legacy behavior byte-for-byte.

The ClarifyEngine — the HITL questionnaire gate

clarify_engine.py runs the pause-ask-resume loop behind the clarify.mode: auto manifest flag. It never hardcodes which workflow is asking — question phrasing is looked up by a small keyword library, not by pipeline name branches.

Up to 3 rounds

MAX_CLARIFICATION_ROUNDS = 3. Each round asks up to 5 questions (capped from the planner's missing_information list); if ambiguities remain after round 3, the engine emits clarification_limit_reached and proceeds anyway — it never blocks a run indefinitely.

Pause via an asyncio.Event

Emits questionnaire_ready, then await event.wait() on a per-run resume event from the artifact store. The event is cleared before emitting the questionnaire so a fast responder (or a reconnect racing in with an already-submitted answer) can never have its set() wiped by a later clear().

Owner-scoped persistence

Each Q&A pair is persisted as a typed clarifications ArtifactRef through the owner-scoped store (migrated off a legacy thin store in Phase 5). run() raises ValueError immediately if owner_id is falsy (AUTHZ-03) — it refuses to silently persist an ownerless row.

Question phrasing: a keyword-matched library, not a workflow switch

A missing-information item like "key_screens" or "target_audience" is matched (by substring, then by word overlap) against a ~30-entry QUESTION_LIBRARY of pre-written question text + multiple-choice options. A per-pipeline TOPIC_BY_PIPELINE table adjusts only the generic "topic" question's phrasing for context (e.g. presentations vs. prototypes ask a differently-worded topic question) — the mechanism is still name-lookup on a dict, not an if pipeline_type == "ppt" branch in control flow. An unmatched item falls back to a generic templated question with generic options, so an unfamiliar ambiguity label still produces something askable. Each question is also classified into one of 11 ambiguity taxonomy categories (Functional Scope, Data Model, Security, Edge Cases, …) by the same keyword-matching approach.

ISS-027 — "Skip all & run directly" actually skips

A force-proceed flag the frontend sets explicitly on a "skip" submission. Before this fix, an empty submit left missing_information unchanged and the loop would re-ask the same questions up to 3 times, ignoring the user's clear intent to move on. Now a force-proceed response short-circuits the whole loop immediately, setting execution_gate: PROCEED without re-evaluating remaining ambiguities.
