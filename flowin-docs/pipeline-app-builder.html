In plain terms. This is a whole software team compressed into one run. Fifteen agents take a brief from requirements all the way to a tested, deployable application — design, APIs, database, code, tests, infrastructure, DevOps, and governance — each handing the right documents to the next.
What it is

A 15-agent pipeline that runs a full software-development lifecycle in a single pass.

Why it exists

To scaffold a complete application — code plus tests, infra, and governance — from a description, not just a snippet.

How it works

Requirements → design → API/DB → code → tests → infra → DevOps → governance, wired by typed produces/consumes contracts; output is a file bundle.

The 15 agents, in order

How the artifacts flow

Inter-agent context is routed by each AGENT.md's typed produces/consumes contracts (validated by the WorkflowResolver as a DAG), not a hardcoded context map. An agent may consume from non-adjacent upstream agents (common here) — e.g. the code generator consumes the system design, API design, and database design.

📦 Deliverable: serialized_sandbox

The many files the agents write into the shared RunSandbox are serialized into a filename:-block bundle by serialize_sandbox_deliverable(). The frontend renders it as a file-bundle (application/zip) in AppBuilderPreview + the Files tab.

An event-free audit step: post_step: api_prefix_audit

The app-infra-generator step (step 10) is the one step in this manifest that declares a post_step — and the manifest's own comment explains a subtle design choice worth understanding. After the infra-generator writes its ~12 infra files, the engine runs the api_prefix_audit post-step to catch endpoints missing an /api/v1 prefix.

🔄 Why a post_step, not a gates: [validation] entry

A validation gate would emit a validation_warning WebSocket event — but the 5 characterization golden tests captured before this feature existed have no slot for that event at this position in the stream, so adding it would break byte-for-byte parity (INV-3). A post_step runs the exact same check but purely as a side effect: it writes a validation_results audit row for later inspection and emits nothing on the wire. Same detection, zero parity risk — a neat illustration of how INV-3 sometimes shapes which capability kind a feature uses, not just whether it exists.

Catalog metadata: user_launchable: true, display_name: "Build an end-to-end application". Clarify defaults were widened (KAN-74) to 8, adding user_journeys, data_model, integrations, performance — all judged critical to full-stack app-generation quality.
