Workflow Catalog & Saved Workflows

The catalog is data-driven: it lists workflows straight from the manifests (never a hardcoded list), so a new manifest appears automatically. Users can also compose their own workflow from the capability palette and save it — persisted, owner-scoped, and re-validated at launch.

In plain terms. The catalog is a storefront of ready-made workflows — and it builds itself from the manifests, so a new workflow appears automatically. Beyond that, you can assemble your own workflow from the capability palette and save it for reuse. Both the storefront and your saved workflows come from data, never a hardcoded list.
What it is

A data-driven workflow catalog plus DB-backed, user-authored saved workflows.

Why it exists

To let users discover and reuse workflows (including their own compositions) without any engineering.

How it works

The catalog reads manifest metadata via /api/workflows; saved workflows persist a composer triple, re-validated with trust=user at both save and launch.

From browse to launch to save

Data-driven catalog (Phase 20)

GET /api/workflows derives the catalog from every manifest's inert presentation fields (user_launchable, display_name, description, icon, launch_surface). WorkflowCatalog.tsx renders the rows. Adding a manifest with user_launchable: true makes it launchable — zero FE edits (SC-001 at the product layer).

Saved workflows (Phase 21)

/api/user-workflows CRUD persists a user-authored workflow as pure data: {base_pipeline_type, agent_ids, model_overrides, selections} + a name. Stored as source="user" rows via migration 0021 on the reused workflows table (not a new table).

The composer & capability palette (Phase 22)

GET /api/capabilities exposes the full registry palette (all ~64 capabilities + the model catalog) with trust flags. The user composes a run in IdeaInputPage (agents, per-agent model overrides via AgentModelPicker, review gates, skills/hooks), and can persist it. The latent model:/retry:/injects: manifest keys were wired live in Phase 22.

🔒 Save == launch (re-validation)

A saved row is re-compiled with trust="user" both at save time and at launch time — so a tampered manifest_json that references a non-user-allowed capability (or raises a budget ceiling) is rejected before execute(), not at run time. Per-step model selections are also allow-list-checked against the ModelCatalog.
