Manifests & Compiler

The declaration layer: how a workflow is described (a YAML manifest) becomes how it is executed (a typed, validated plan). It imports only stdlib + itself + the capability registry — never the kernel or the web layer.

In plain terms. A workflow is a recipe written in YAML — a list of steps and the ingredients (capabilities) each step uses. The compiler is the sous-chef that reads the recipe, checks every ingredient actually exists, makes sure the steps can be done in a valid order, and hands the kernel a clean, ready-to-cook plan. If the recipe calls for something that doesn't exist, the compiler refuses — before any cooking starts.
What it is

The layer that reads a workflow.yaml and produces a typed, validated CompiledWorkflow.

Why it exists

So workflows can be pure data — editable and safe, with no executable code — yet still fully validated before they run.

How it works

Load → strict-key validate → name-resolve every capability against the registry → topo-check the step DAG → emit the plan. No DSL, no eval.

How a manifest becomes a plan

manifest.py

load_manifest(id, base_dir) reads <id>/workflow.yaml with yaml.safe_load only (no RCE surface) into a typed WorkflowManifest. Not Pydantic. Strict-key rejection: only _ALLOWED_TOP_KEYS are permitted.

compiler.py

WorkflowCompiler.compile() does exactly two things: name-resolve every capability against the registry (unknown = CompilerError), and map each raw step → a typed Step + topo-validate the DAG.

plan.py

The typed contract: CompiledWorkflow, Step, ToolPermissions, ModelPolicy, TaskSource, FixPolicy, FanoutSpec, RetryPolicy, DeliverableSpec, ClarifySpec, Task.

A real manifest — prototype/workflow.yaml

Every value is a capability name the compiler resolves; there is no imperative logic.

id: prototype
planner: run
clarify:
  mode: auto
  defaults: [target_audience, scope, priority, style, user_journeys, key_screens, interactions, personas]
deliverable:
  strategy: single_file          # DeliverableResolver capability
  name: prototype.html
context_providers: [opendesign]  # ContextProvider capability
steps:
  - agent: prototype-specify
    strategy: single_shot
    gates: [human]               # HITL review gate
  - agent: prototype-plan
    strategy: single_shot
    gates: [human]
  - agent: prototype-build
    strategy: task_loop          # one sub-agent per task
    task_source: {kind: parsed, parser: heading_tasks, target: tasks.md,
                  source_step: prototype-plan, spec_step: prototype-specify}
    validators: [html_static, html_render]
    compaction: html_skeleton
  - agent: prototype-validate
    strategy: single_shot

Trust model & secure defaults

The compiler takes a trust level. file/builtin manifests are trusted; user/db manifests (from the composer / saved workflows) are untrusted and additionally checked against each capability's user_allowed flag.

Untrusted can't escalate

A user/db manifest referencing a non-user-allowed capability (exec, secrets, spawn_subagents) is a CompilerError. Budget Limits may only be lowered, never raised above the default ceiling.

exec requires gates

A step granting tools.exec must declare both the security and approval gates, or the compile fails. The compiler raises — it never auto-injects.

Least privilege

Effective tool permissions = owner ∩ workflow_ceiling ∩ step_grant (an AND-mask that can only lower). Ungranted steps keep read_files on, everything else off.

Default audit hooks

A step that declares no hooks: automatically gets audit_logger + secret_scan injected (KAN-73) — audit trail + security scan by default.

🔒 Safe parsing

yaml.safe_load only (a !!python/object tag cannot construct an arbitrary object). Any control-flow / DSL key (when/if/for/${…}) at any level is rejected by strict-key validation — that is exactly what keeps manifests pure data (INV-5).

Every top-level key, and what happens if you misspell one

_ALLOWED_TOP_KEYS in manifest.py is the exhaustive list — nothing else is legal at the top of a workflow.yaml. A typo or an unsupported field doesn't get silently ignored; load_manifest raises a ManifestValidationError naming the exact unknown key(s), before the compiler even sees the manifest.

KeyRequired?TypePurpose
idrequiredstrThe manifest id, e.g. prototype.
stepsrequiredlistRaw step dicts. May be [] — the reverse_engineer workflow is an intentional empty plan.
deliverablerequireddict{strategy, name} — which resolver capability produces the final artifact.
plannerrequiredstr"run" or "skip" — whether the deep-planner agent runs before the steps.
clarifyrequireddict{mode, defaults} — HITL clarify gate config.
versionoptionalintDefaults to 1. Rejects a bool explicitly (a bool is an int subclass in Python — version: true is caught, not silently coerced to 1).
context_providersoptionallistNames of ContextProvider capabilities to inject (e.g. opendesign, repo).
seed_filesoptionaldictWhich files to seed from a prior run (revision workflows).
allowed_workersoptionallistThe named-worker allow-list a heterogeneous fan-out step may spawn from.
model / limitsoptionaldictForward/inert in earlier phases; model now feeds the per-workflow default tier, limits feeds BudgetManager.from_limits.
user_launchableoptionalboolGates catalog visibility only — never authorizes a run (launch stays tier-gated server-side). Strictly type-checked: 1 is rejected, not coerced.
display_name / description / icon / launch_surfaceoptionalstrPure presentation metadata for the catalog UI. Never read by the compiler or kernel.

Note what's not in that list: no when, no if, no for, no template expression syntax. That absence is the whole point of INV-5 — there is structurally nowhere in a manifest to write control flow, so a manifest can never do anything more dangerous than name capabilities and configure them.

The typed plan a manifest compiles into (plan.py)

Every dataclass below started life "declared but inert" — present in the schema with a safe default, but not yet consumed by any kernel behavior — and was switched on phase by phase as the corresponding capability landed. That staging is deliberate: the full shape of the eventual system was designed up front, so later phases only had to activate fields, never restructure the contract.

Step

One compiled DAG node: agent_id, strategy, gates, hooks, task_source, post_step, plus the forward fields tools (a ToolPermissions), model, validators, fix, compaction, fanout, on_conflict, retry, injects, depends_on.

ToolPermissions

The least-privilege grant set (INV-9): read_files defaults ON, everything else (write_files/exec/git/network/spawn_subagents) defaults OFF. intersect_permissions(owner, workflow, step) is a pure AND-mask across all three levels — the result can only ever narrow, never widen a grant.

FanoutSpec

agent/count for a self×N fan-out, or workers (a list of named worker ids) for a heterogeneous one — every named worker must also appear in CompiledWorkflow.allowed_workers AND the agent registry before run_fanout will spawn it.

RetryPolicy

max_attempts + backoff_seconds + on (error classes — only "transient" is wired today, reusing the single _is_transient_throttle classifier). A step declaring no retry is byte-identical to before the field existed — the wrapper is fully dormant.

DeliverableSpec

strategy + name + the important revises_existing flag: this — not a provider-name proxy check, not a workflow-id branch — is what tells the kernel a run edits an artifact in place rather than regenerating it fresh. Only prototype_revision sets it True today.

RepoSpec & Limits

RepoSpec.index is a pure opt-in flag — the compiler only records it; the actual decision to build a symbol index lives inside the repo_index capability, never the compiler (INV-5 again). Limits feeds BudgetManager.from_limits directly.

The one universal design rule across every one of these types, stated directly in the source comments: declare the full field now, consume it later, and never let a Phase-N behavior key off a field that isn't live yet. That's how 22 phases landed without ever rewriting the manifest schema out from under itself.
