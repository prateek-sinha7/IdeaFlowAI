Manifests & Compiler

The declaration layer: how a workflow is described (a YAML manifest) becomes how it is executed (a typed, validated plan). It imports only stdlib + itself + the capability registry — never the kernel or the web layer.

How a manifest becomes a plan

manifest.py

load_manifest(id, base_dir) reads <id>/workflow.yaml with yaml.safe_load only (no RCE surface) into a typed WorkflowManifest. Not Pydantic. Strict-key rejection: only _ALLOWED_TOP_KEYS are permitted.

compiler.py

WorkflowCompiler.compile() does exactly two things: name-resolve every capability against the registry (unknown = CompilerError), and map each raw step → a typed Step + topo-validate the DAG.

plan.py

The typed contract: CompiledWorkflow, Step, ToolPermissions, ModelPolicy, TaskSource, FixPolicy, FanoutSpec, RetryPolicy, DeliverableSpec, ClarifySpec, Task.

A real manifest — prototype/workflow.yaml

Every value is a capability name the compiler resolves; there is no imperative logic.

id: prototype
planner: run
clarify:
  mode: auto
  defaults: [target_audience, scope, priority, style, user_journeys, key_screens, interactions, personas]
deliverable:
  strategy: single_file          # DeliverableResolver capability
  name: prototype.html
context_providers: [opendesign]  # ContextProvider capability
steps:
  - agent: prototype-specify
    strategy: single_shot
    gates: [human]               # HITL review gate
  - agent: prototype-plan
    strategy: single_shot
    gates: [human]
  - agent: prototype-build
    strategy: task_loop          # one sub-agent per task
    task_source: {kind: parsed, parser: heading_tasks, target: tasks.md,
                  source_step: prototype-plan, spec_step: prototype-specify}
    validators: [html_static, html_render]
    compaction: html_skeleton
  - agent: prototype-validate
    strategy: single_shot

Trust model & secure defaults

The compiler takes a trust level. file/builtin manifests are trusted; user/db manifests (from the composer / saved workflows) are untrusted and additionally checked against each capability's user_allowed flag.

Untrusted can't escalate

A user/db manifest referencing a non-user-allowed capability (exec, secrets, spawn_subagents) is a CompilerError. Budget Limits may only be lowered, never raised above the default ceiling.

exec requires gates

A step granting tools.exec must declare both the security and approval gates, or the compile fails. The compiler raises — it never auto-injects.

Least privilege

Effective tool permissions = owner ∩ workflow_ceiling ∩ step_grant (an AND-mask that can only lower). Ungranted steps keep read_files on, everything else off.

Default audit hooks

A step that declares no hooks: automatically gets audit_logger + secret_scan injected (KAN-73) — audit trail + security scan by default.

🔒 Safe parsing

yaml.safe_load only (a !!python/object tag cannot construct an arbitrary object). Any control-flow / DSL key (when/if/for/${…}) at any level is rejected by strict-key validation — that is exactly what keeps manifests pure data (INV-5).
