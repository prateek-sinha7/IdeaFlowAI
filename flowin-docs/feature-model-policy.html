Model Policy

Which LLM runs each agent is a resolved decision, not a hardcoded constant. A ModelResolver applies a strict precedence over an allow-listed ModelCatalog, with fallbacks and cost classes. build_model() then constructs the right client.

Default: Claude Haiku 4.5Providers: Bedrock / AnthropicCap: MAX_OUTPUT_TOKENS = 32768
In plain terms. Not every agent needs the biggest, most expensive model. Flowin picks the model for each agent using a clear order of precedence — a per-run user choice wins over a per-step setting, which wins over the agent's own default, and so on. And because letting users pass arbitrary model names is risky, those choices are checked against an allow-list before anything runs.
What it is

A model-selection policy (ModelResolver) over an allow-listed catalog, plus the build_model() client factory.

Why it exists

To balance cost and quality per agent and to block abuse via unknown/arbitrary model ids.

How it works

A 5-tier precedence resolves the id; the factory builds ChatAnthropic or ChatBedrockConverse with token caps, timeouts, and a fallback chain.

app/agents/model_factory.py. Selects ChatAnthropic when ANTHROPIC_API_KEY is set (local dev), else ChatBedrockConverse (prod — IAM instance role or a bearer token). Botocore read-timeout + adaptive retries live here in one place. Per-call total timeout is LLM_CALL_TIMEOUT_SECONDS = 900.

Token ceiling

The API requires a finite max_tokens, so "no capping" means "run at the model max" — MAX_OUTPUT_TOKENS = 32768 is applied uniformly by the factory, overriding the documented per-agent max_tokens in AGENT.md.

🔒 The security chokepoint

model_overrides is untrusted run-payload input. _validate_model_overrides() checks each entry against two allow-lists — model_id ∈ ModelCatalog.ids() and agent_id ∈ this run's agents — and rejects the run with code: "invalid_model_override" before execute(). This blocks unknown-provider / cost-abuse / invalid-model-crash vectors.

Why tier-3 validation is deferred until it actually wins

ModelResolver.resolve() has a deliberately subtle ordering worth calling out: it computes all 5 precedence tiers with a plain or-chain first, and only after that resolves does it catalog-validate whichever tier actually won. Why not validate every tier upfront? Because a higher-precedence override must be able to rescue a run even when a lower tier is broken — e.g. if an AGENT.md declares a retired model id (tier 3) but the user supplied a valid per-run override (tier 1), the override should win cleanly, and the stale AGENT.md value should never even be checked. Validating eagerly would incorrectly reject that run. The resolver validates tier-2 (step.model, sourced from a user-composed selections map) and tier-3 (AGENT.md) only when each is the tier that actually resolved — a real "defense in depth, but don't over-defend" design call.

Fallback chains: tier-descent by cost class, not a hardcoded list

When a model call hits a transient error, the engine doesn't just retry the same model — it walks a fallback chain. ModelResolver.chain_for(model_id) derives this automatically from the catalog's cost_class field (premium → standard → cheap): a premium model's default chain is [standard, cheap] (roughly Opus → Sonnet → Haiku), a standard model's is [cheap], and a cheap model has nowhere left to fall back to. A manifest can override this with an explicit fallback list, but every entry in it is still catalog-validated — an explicit fallback naming an unknown model id raises just as loudly as an unvalidated override would.

The resolver doesn't just compute the chain once — it owns an active cursor (set_chain / current / advance) that the engine's retry loop drives directly, so one object is responsible for both which model to try first and what to try next when that fails.

Classifying "worth switching models" — _is_transient_throttle

Not every model error should trigger a fallback. A ValidationException or an AccessDeniedException will fail identically on a fallback model too — retrying just wastes time and tokens. The classifier is a three-layer defensive check, because the exact exception shape depends on which client library wrapped it:

1 · botocore ClientError shape

Checks exc.response["Error"]["Code"] against a set of known-transient Bedrock codes (ThrottlingException, ServiceUnavailableException, …), or the HTTP status against {429, 500, 503, 529}.

2 · a status attribute

Anthropic-style clients expose status_code/http_status directly on the exception — checked against the same transient-status set.

3 · substring match, defensively

As a last resort, the exception's type name + stringified message is searched for substrings like "throttl", "rate limit", "overloaded" — because langchain-aws/langchain-anthropic sometimes wrap the real error in ways that lose the structured fields.

Anything that doesn't match any of the three layers returns False, and the caller re-raises without switching models — a fail-loud default rather than silently masking a real configuration problem behind a model swap.
